# Защита своего кода 1С: разбор вариантов (29.10.2026)

Шаг З.1 сводного плана (`docs-project/core-improvement-plan.md`): «очень сильный инструмент для обфускации кода и чтобы можно было закрывать модули на замок» — для внешних обработок и отчётов, расширений и модулей конфигурации. Разбор — только про защиту **своего** кода; снятие чужой защиты в задачу не входит и не изучается.

## Слои защиты

| Слой | Что даёт | Стойкость | Ограничения |
|---|---|---|---|
| Обфускация текста (сборочный шаг) | текст модулей нечитаем; годится для ЛЮБЫХ модулей, включая формы и клиентские | средняя: обратима трудом | неприкосновенны имена, на которые ссылаются метаданные и другие модули (экспортные методы, обработчики форм, подписки, регламентные задания, команды); `Перейти` не поддерживается в веб-клиенте ([std547](https://v8std.ru/std/547/), АПК:249); `Вычислить` на сервере — только в безопасном режиме ([std770](https://v8std.ru/std/770/)), на клиенте — нежелателен ([std801](https://v8std.ru/std/801/)); замедление и рост кода |
| Поставка без исходного текста (платформа) | в поставке только скомпилированный код | по отзывам, байт-код вскрывается общедоступными инструментами — не проверено | **нельзя** для модуля управляемого приложения, модулей форм и команд, модулей с инструкциями препроцессора и клиентских общих модулей управляемого режима (`1c-platform-kb`: `its-docs/dev-gl37-gl38-hranilishche-postavka-podderzhka.md`, 38.2). В 8.3.27 — настройка поставки в конфигураторе вручную; пакетно — с 8.5.1 `/ModuleSetSourceCodeAccess` (режим `hidden`, необратимо) и `/ModuleGetSourceCodeAccess` (`its-docs/otlichiya-8.5.1-ot-8.3.27.md`). Проверка генерации образов — `/CheckConfig -DistributiveModules` (`its-docs/adm-pr07-parametry-zapuska-1cv8-p2.md`) |
| Пароль на модуль | закрывает текст от случайного взгляда | слабая | в пакетном режиме 8.3.27 модули с паролем пропускаются с диагностическим сообщением (`adm-pr07…-p1.md`); с 8.5.1 — пакетно `/ModuleSetSourceCodeAccess` режим `encrypted` |
| Запрет изменений на поддержке | правило поставщика «Изменения запрещены»: объект не изменить, не сняв с поддержки всю конфигурацию (`dev-gl37-gl38…`, 38.2) | организационная: код виден | только конфигурация на поддержке |
| Подпись расширения `Copyright` (8.5.1) | изменённое расширение блокируется при исполнении (`/SignCfg -SignType Copyright`) | против подмены, не против чтения | только расширения, только 8.5.1 |
| 1С:СЛК | защищённые модули исполняются только с ключом; ключ привязан к компьютеру или носителю ([инструкция 1С:ТОИР](https://solutions.1c.ru/upload/reestr/bc3/p22abgt4tp67u9ug5wk0rhqfmhdg9ujs/Instruktsiya-po-ustanovke-TOIR-KORP.pdf)) | высокая против копирования | ключи, договор с 1С, внешний компонент |
| Логика на своём сервере | секретная часть не покидает свой сервер; клиент её вызывает | полная | нужен свой сервис и связь с ним |

Не берём: SaaS-обфускация («Нетленка») — тексты модулей уходят наружу, против правила «код наружу не уходит».

## Движки обфускации — кандидаты

- **[Obfuscator-1C](https://github.com/LazarenkoA/Obfuscator-1C)** — MIT, Go, на разборщике [1c-language-parser](https://github.com/LazarenkoA/1c-language-parser); на 29.10.2026 — 39 звёзд, обновлялся 28.10.2026, релизов и запуска из командной строки нет (библиотека: `obfuscator.NewObfuscatory(ctx, Config{…}).Obfuscate(code)`). Приёмы (флаги `Config`): `RepExpByTernary`, `RepLoopByGoto` (циклы — через `Перейти`), `RepExpByEval` (выражения — через `Вычислить`), `HideString` (строки — base64 и XOR с расшифровкой в рантайме), `ChangeConditions`, `AppendGarbage`, `CallStackHell`. Для клиентского кода `RepLoopByGoto` и `RepExpByEval` выключаются — иначе веб-клиент и стандарты. Go на машине мастера нет (29.10.2026).
- **Свой движок на Python** — переименование локальных имён, шифрование строк, мусорные ветки без `Перейти`; без новой программы, полный контроль, но дольше и на старте слабее.
- На Infostart — обфускаторы байт-кода и операционного кода ([2621315](https://infostart.ru/public/2621315/), [1677514](https://infostart.ru/1c/tools/1677514/), [1296504](https://infostart.ru/public/1296504/)): коммерческие или без открытого репозитория — не проверены; [обсуждение поставки без исходников](https://forum.infostart.ru/forum104/topic191203/).

## Решения владельца (29.10.2026)

1. **От кого защищаем — и то, и другое:** получатели поставки (клиенты, партнёры) и подрядчики с доступом к своим базам. Первым строится защита поставки, вторым — замок в своих базах.
2. **«Замок» — все три вида:** без исходного текста, пароль на модуль, запрет изменений на поддержке.
3. **Движок — по итогу пробы обоих:** Obfuscator-1C с нашей обёрткой против простого своего среза на Python; критерии — доля модулей, разобранных без ошибки, синтаксис после обфускации, работа клиентского кода в веб-клиенте, скорость, рост кода.
4. **После пробы — движок на Java поверх `bsl-parser` 0.40.0** (отдельно с Maven Central со сверкой сумм), отдельной частью ядра с лицензией GPL-3.0 — `docs-project/adr/0007-obfuscation-engine-java-bsl-parser.md`.

## Проба движков (29.10.2026)

Корпус — копии модулей в черновике сессии: 300 модулей английской типовой выгрузки из пилота обновления на релиз (по 60 общих, форм, объектов, менеджеров, команд; около 118 тыс. строк) и 177 русских модулей из `tools/cc-1c-skills`. Obfuscator-1C — коммит `e758f73`, разборщик `461cd76`, Go 1.27.3, своя обёртка запуска из командной строки; на сервере — все приёмы, на клиенте — без `RepLoopByGoto` и `RepExpByEval`. Свой срез — переименование параметров и локальных переменных и снятие комментариев; в модулях форм, объектов и команд неявные локальные переменные без метаданных не трогаются; метод с `Выполнить`/`Вычислить` не переименовывается. Синтаксис — `bsl-analyzer` по папке до и после.

| Критерий | Obfuscator-1C | Свой срез |
|---|---|---|
| Английский код (два проекта владельца) | 0 из 300: разборщик знает только русские ключевые слова (`ast/tokens.go`) | 292 из 300 |
| Русский код (три проекта владельца) | 168 из 177; сбой на процедуре с именем `Выполнить` и на двойном BOM | 174 из 177 |
| `Асинх`/`Ждать`, препроцессор `#Если` | в разборщике нет | лексемы проходят как есть |
| Веб-клиент | `Перейти` в 94 из 106 клиентских модулей даже с выключенным `RepLoopByGoto` — его вставляют мусорные ветки (`AppendGarbage`); АПК:249 | `Перейти` не добавляется |
| Стандарты | 14 новых `ExecuteExternalCode` (`Вычислить` на сервере без безопасного режима, std770) | 0 новых ошибок анализатора |
| Имена переменных | остаются: переименование параметров в движке закомментировано | 7235 имён переименовано |
| Строки и тексты запросов | прячет (base64 и XOR, расшифровка в рантайме) | пока не прячет |
| Запутывание ветвлений | есть: тернарные выражения, мусорные ветки, ложные вызовы | нет |
| Рост кода | ×22 клиент, ×69 сервер | ×0,65–0,99 (без комментариев) |
| Доказательство корректности | разбирается анализатором; равенство поведения не доказано | лексемы до и после совпадают с точностью до переименования; несовпадение — модуль не записывается (11 из 477 отклонены так) |
| Зависимости | Go для сборки, своя обёртка | Python, уже в ядре |

Вывод пробы: у Obfuscator-1C сильнее запутывание (строки, ветвления), но он не годится как основа для проектов владельца — не разбирает английский код, современный синтаксис и препроцессор, ломает веб-клиент и раздувает код в десятки раз. Свой срез корректен и годится для обоих языков, но слабее; сила добирается своими слоями — сокрытие строк с расшифровкой по контексту исполнения, запутывание ветвлений без `Перейти` и `Вычислить`, переименование неявных локальных переменных по метаданным выгрузки — и замком платформы для серверных модулей.

### Разборщик на Java — по предложению владельца (29.10.2026)

Владелец предложил движок на Java как более сильный. Проверено: сила обфускации задаётся точностью понимания кода, а на Java есть полный разборщик BSL — [`1c-syntax/bsl-parser`](https://github.com/1c-syntax/bsl-parser) (грамматика ANTLR4, на нём работает BSL Language Server; лицензия **GPL-3.0**; выпуск v0.40.0 от 14.10.2026). Проба — классы `BSLTokenizer`/`BSLParser` версии 0.37.2 из уже установленного BSL Language Server 1.0.7 (библиотеки `BOOT-INF/lib` его исполняемого архива, без скачивания), OpenJDK 21: английский корпус — 300 из 300 модулей без синтаксических ошибок (3583 метода), русский — 170 из 177 (7 отказов — эталоны тестов проверки форм `module-handler-orphan`, `literal-comment` и др.; позже выяснилось, что их не разбирает сам `bsl-parser`, а tree-sitter и `bsl-analyzer` считают их исправными — ADR-0009); всё — около секунды. Это сильнее и Obfuscator-1C (0 из 300 английских), и разбора по лексемам своего среза (97%): дерево разбора даёт области видимости, вызовы, присваивания — основу для безопасного переименования и перестройки кода.

Последствия: движок, собранный с `bsl-parser`, при распространении — тоже GPL-3.0 (отдельная часть со своей лицензией); на защищаемый код 1С лицензия инструмента не распространяется. Java 21 и компилятор на машине мастера есть.

## Срез 1 движка (29.10.2026)

`tools/obfuscator` (README там же; **с вехи 104 движок — закрытый на tree-sitter, ADR-0009; описанное ниже на `bsl-parser` — проба среза 1, прежний движок снят**): переименование параметров, `Перем`, переменных циклов и неявных локальных переменных по дереву разбора `bsl-parser` 0.40.0, снятие комментариев и отступов; сверка — результат разбирается без ошибок, лексемы основного канала совпадают с исходными с точностью до переименования. На корпусе пробы: 300 из 300 английских и 170 из 177 русских модулей (7 не разбирает `bsl-parser`, см. ADR-0009), 9525 имён переименовано, код на 11–20% короче, новых ошибок `bsl-analyzer` — 0 на всех 470 модулях. По дороге найдены и исправлены два места, которые сверка честно отклоняла: перевод строки в конце файла после строки препроцессора (лексема `PREPROC_NEWLINE` скрытого канала) и хвостовой пробел строки многострочного литерала. Регресс — `contour-tests` §42.

## Срезы 2–6 и живая проба (29.10.2026)

Срезы — `tools/obfuscator` (README там же), решения — `docs-project/adr/0008-obfuscation-slices-string-flow-metadata.md`: сокрытие строк (`--strings`), запутывание ветвлений (`--flow`), переименование по списку неприкосновенных имён (`--keep`), замок штатными средствами (`lock.py`), конвейер поставки (`build-protected.py`). Регресс — `contour-tests` §42–§48.

Проба на корпусе 2815 модулей (1000 английских типовой выгрузки по 200 каждого вида + 1815 русских `cc-1c-skills`), `bsl-analyzer` до и после по каждому модулю:

| Режим | Записано | Новых ошибок анализатора | Размер |
|---|---|---|---|
| срез 1 (переименование) | 2808 из 2815 | 8 в 2 модулях | ×0,81 |
| + `--strings` | 2808 | 2 | ×1,91 |
| + `--flow` | 2808 | 8 (те же, что у среза 1) | ×0,85 |
| все приёмы | 2808 | 2 | ×1,95 |

7 отказов — эталоны тестов скилла проверки форм, которые не разбирает сам `bsl-parser` (процедура с именем `Выполнить`, строка-комментарий `//|` в многострочном литерале, `;КонецФункции`); tree-sitter и `bsl-analyzer` считают их исправными (ADR-0009). Повтор даёт тот же результат на всех 2808. Оставшиеся диагностики присущи любому переименованию: `UsingHardcodeNetworkAddress` — анализатор не считает `"0.0.0.0"` адресом по имени переменной `…Version`; `TypeMismatch` — тип параметра анализатор берёт из комментария-описания, а обфускация его снимает. Поведение кода они не меняют.

Ограничения, найденные пробой и закреплённые в движке: литералы `НСтр`/`СтрШаблон` не прячутся (текст для пользователя; без литерала анализатор не видит плейсхолдеры и языки); прячутся только строки тела метода (значения параметров по умолчанию и аннотации — константы); декодер ставится перед первым методом (после кода тела модуля объявлять методы нельзя), а строка из другой ветки `#Если`, чем декодер, не прячется; методы с `&ИзменениеИКонтроль` не меняются ничем (платформа сверяет их текст с оригиналом); `--flow` не оборачивает обработчики записи (проверка `ОбменДанными.Загрузка` на верхнем уровне, АПК:75) и методы с внешними соединениями (таймаут); модуль не в UTF-8 отклоняется, не роняя партию.

## Живая приёмка (30.10.2026)

Проверено на платформе 8.3.27 на тестовой базе мастера. Модуль расширения со строками, ветвлениями и циклом собран приёмами `--strings --flow`: переименовано 5 имён, спрятано 17 строк, обёрнуто 4 блока, открытых литералов в тексте нет. Загружены по очереди открытый и защищённый модули: один и тот же тест YAXUnit с пятью проверками зелёный в обоих прогонах (по отчётам — тот самый тест, а не старый), затем расширение возвращено. Значит, платформа компилирует защищённый код и он считает то же самое.

**Замок на 8.5.1** проверен на отдельной файловой базе, платформа 8.5.1.1343: `/ModuleGetSourceCodeAccess` дал строку `CommonModule.<Имя>.Module:open:` — формат, который ждёт `lock.py`; файл SET из `lock.py plan`, затем `/ModuleSetSourceCodeAccess`, `/UpdateDBCfg` и `/CheckConfig -DistributiveModules` прошли с кодом 0, повторный список показал `hidden`. **Замок сам по себе текст не закрывает (проверка 31.10.2026).** Модуль в `.cf` хранится вложенным контейнером со страницами по 512 байт. Записи `image`, `info`, а у `encrypted` ещё `text` занимают страницу не целиком, и платформа не обнуляет её хвост: там остаётся кусок исходного текста. `v8unpack` читает записи по их длине и хвостов не видит, поэтому прежний вывод «в `.cf` текста нет» был ошибкой. Свой разбор контейнера `after.cf` нашёл в хвостах тело метода, комментарий и имя у обоих режимов: `hidden` — в хвостах `image` и `info`, `encrypted` — в хвосте `info`, пароль не нужен. Контроли: в данных записи `image` имя метода найдено, несуществующая строка не найдена нигде. XML-выгрузка показывает тот же контейнер `Module.bin`: до и после обратной загрузки `.cf` файлы совпали по хэшу. Хвост содержит случайный остаток памяти процесса, и попадает туда не только текст модуля, но и посторонние данные. Значит, надёжно закрывает текст только обфускация, а замок ставится поверх неё.

**Замер объёма 31.10.2026**, 8.5.1.1343, файл `/DumpCfg` и файл поставки `/CreateDistributionFiles` дали одно и то же:

| Модуль | Режим | Скомпилированный образ | Исходный текст в хвостах |
|---|---|---|---|
| 1 функция | `hidden` | 192 байта | есть, почти весь модуль |
| 1 функция | `encrypted` | 192 байта | есть, почти весь модуль (замер на `after.cf` пробы `encrypted`) |
| 3 функции | `hidden` | 1,3 КБ | есть, до 497 байт |
| 30 функций | `hidden` | 13 КБ | есть, до 497 байт |
| 30 функций | `encrypted` | 13 КБ | нет |
| 200 функций | `hidden` | 89 КБ | нет |
| 200 функций | `encrypted` | 89 КБ | нет |
| 200 функций, обфускация | `hidden` | 145 КБ | нет |

Предел — хвост записи `info` (470–497 байт), а у образа меньше страницы ещё и хвост `image`. Малый модуль может оказаться там целиком, от большого остаётся кусок. Точной границы по размеру нет: в хвост попадает то, что было в памяти, поэтому отсутствие текста у больших модулей — наблюдение, а не гарантия. Пароль `encrypted` в блоках обоих файлов не найден.

**Дефект `lock.py` до 5.2.1:** файл SET писался с концами строк LF, а платформа ждёт CRLF, как в файле GET. Из политики на три модуля закрылся только первый, остальные остались открытыми, платформа ошибки не дала, код 0. С CRLF закрылись все шесть модулей следующей политики. Поэтому после замка список GET снимается заново и режимы сверяются с политикой.

**Сброс замка при частичной загрузке (проба 31.10.2026).** Список GET показывает конфигурацию базы данных, поэтому до `/UpdateDBCfg` он не меняется.

| Файл модуля в папке | В списке загрузки есть `Configuration.xml` | Режим после `/UpdateDBCfg` |
|---|---|---|
| открытый `Module.bsl` | да | `open`: замок снят без предупреждения |
| открытый `Module.bsl` | нет | `encrypted` |
| `Module.bin` из свежей выгрузки | да | `encrypted` |
| файла нет | да | `encrypted` |

Поэтому режимы сверяются командой `lock.py verify` после обновления базы, а не только сразу после замка.

**Проверено живьём 31.10.2026:**

| Проверка | Итог |
|---|---|
| Вызов метода после `hidden` на 8.5.1 | работает, значение совпало |
| Режим `encrypted` на 8.5.1 | применён, вызов после обратной загрузки `.cf` работает |
| Скорость, 8 пар замеров, клиент и сервер | замедления нет, суммы совпали |
| Движок из выпуска 5.2.0 | ставится, защищает обработку |

`lock.py` теперь в плагине (`plugin/tools/obfuscator/`): `/ones-core:protect` показывает план замка в проекте, а не только обещает его.

## Каркас инструмента (до пробы)

Исходники в git не трогаются — защищается копия в сборочной папке. Политика защиты — файлом: какие модули и какими приёмами, отдельно для клиентского и серверного кода. Неприкосновенные имена собираются из метаданных выгрузки. Сборка — скиллами `epf-build`/`erf-build`, конфигурация и расширения — загрузкой в тестовую базу; замок платформы — пакетно на 8.5.1, на 8.3.27 — инструкцией ручного шага. Проверка — синтаксис, те же тесты YAXUnit на исходниках и на сборке, запуск формы в веб-клиенте, замер скорости; отчёт «что защищено и чем».
