## Разбор «самых нужных» (verified)

### onec-mcp — possible, но не сейчас
- **Осуществимость:** ✅ готовый `onec-mcp-windows-amd64.exe` (Releases v1.0.0), HTTP, без внешних БД.
- **Ценность:** не дублирует базу — это **бизнес-отчётность 1С:ERP для LLM** (продажи, остатки, касса, дебиторка, резолвинг ссылок).
- **Почему не connect-now:** это **только шлюз**. Он не читает 1С напрямую — нужно **самостоятельно разработать и опубликовать внутри 1С:ERP HTTP-сервис** с эндпоинтами `/mcp/reports/*`, `/mcp/resolve/*`, `/mcp/admin/*` (в репо только спецификация + BSL-псевдокод, готового `.epf` нет). Проект сырой (1 релиз, ~1★). Безопасность: по умолчанию слушает `0.0.0.0`, привилегированные админ-эндпоинты — включать OAuth/bind 127.0.0.1.
- **Вывод:** подключать только если реально нужна ERP-отчётность через LLM и есть готовность писать 1С-сторону.

### bsl-analyzer (MCP-режим) — possible, но лучше CLI
- **Осуществимость:** ✅ готовый Rust `.exe` (**уже в базе** — `bsl-analyzer.exe`, папка программ плагина), stdio через `BSL_MCP_BROKER=0`.
- **Проблема:** MCP-инструменты дублируют подключённое — `reference`-профиль ≈ bsl-platform; `workspace`-профиль ≈ edt-mcp/1c-toolkit/code-index (и умеет execute BSL/SDBL на живой 1С — риск на проде).
- **Вывод:** **уникальная ценность — статический линтер BSL — доступна как CLI**, а не MCP: `bsl-analyzer analyze -s <src> --format jsonl` (SARIF/JSONL) или `bsl-analyzer lsp` в IDE. Это и есть рекомендуемый способ закрыть пробел с линтером.

### spring-mcp-1c-copilot — skip
Нет готового jar (только Source code в релизе → сборка Gradle недоступна), обязателен облачный токен 1С:Напарник (`code.1c.ai`, код уходит наружу), нестандартная лицензия (некоммерческая). Пересмотреть, только если появится опубликованный jar и выданный токен.

## NotebookLM / Gemini Notebook Enterprise (разбор 03.08.2026)

Запрос: «работать через NotebookLM». Проверено по первоисточникам Google — вывод короткий: **официальный путь легален, но для агента пустой**.

**Публичного API нет.** Для личных аккаунтов Google программного доступа не даёт; официальный — только **Gemini Notebook Enterprise API**, статус **Preview**, endpoint `https://{REGION}-discoveryengine.googleapis.com/v1alpha/projects/{PROJECT_NUMBER}/locations/{LOCATION}/notebooks…` (регионы `us`/`eu`/`global`), авторизация OAuth-токеном (`gcloud auth print-access-token`).

**Что API умеет:**
- ноутбуки — `notebooks.create` · `get` · `listRecentlyViewed` (последние 500) · `batchDelete` · `share`;
- источники — `sources.batchCreate` · `uploadFile` · `get` · `batchDelete`; типы: Google Drive (Docs/Slides), сырой текст, web-URL, YouTube; файлы PDF/TXT/MD/DOCX/PPTX/XLSX, аудио, изображения (для Drive нужен `gcloud auth login --enable-gdrive-access`).

**Чего API НЕ умеет — и это решает вопрос:** в документации **нет метода «задать вопрос ноутбуку» и получить ответ/summary**. Программно можно только наполнить ноутбук и управлять им; собственно ценность NotebookLM — диалог по источникам со ссылками — остаётся в UI, для человека. То есть «агент работает через NotebookLM» технически не складывается: складывается «агент наполняет ноутбук, человек читает».

**Цена входа:** GCP-проект + подписка Gemini Notebook Enterprise + лицензия на каждого пользователя (порядка $9/мес за лицензию по публичным обзорам) + IAM-роли `Cloud NotebookLM Admin`/`User`. Личный Google-аккаунт не подходит. API — `v1alpha`/Preview, интерфейс может меняться.

**Неофициальные MCP-обёртки — отклонены:** работают браузерной автоматизацией (Patchright/Playwright) поверх внутренних эндпоинтов; условия Google запрещают автоматизированный доступ (риск для аккаунта пользователя), интерфейс недокументирован (тихо ломается), а содержимое — код 1С и доки — уезжает в облако против [[secrets-and-production-database]].

**Вердикт:** не подключать. Осмысленный сценарий появляется только при уже оплаченной подписке — тогда это не MCP, а простой скрипт «сложить подготовленные материалы в ноутбук» (create + `sources.batchCreate`), а чтение и вопросы остаются за человеком в UI. Локальная альтернатива под задачу «вопросы к корпусу» — поиск/RAG по нашим исходникам; часть таких кандидатов в матрице выше отклонялась из-за отсутствия Python, а он в среде **появился** (см. Ground truth) — при необходимости матрицу можно пересмотреть.

### Замеры на корпусе БСП (19.08.2026, наш стек, версия 0.47.0)

Бенчмарк соседей судил `bsl-indexer` **v0.15.0**. Перемерили свою текущую версию на реальном корпусе — выгрузке БСП 3.1.12.238:

- **индексация:** 8667 файлов за **30.7 с** (ядро 18.6 + extras 10.9 + запись 1.3);
- **построено:** 38 310 процедур, **190 015** прямых рёбер вызовов + **82** ребра подписок + **4358** рёбер событий форм.

Второе важнее первого: **0.47.0 сам строит косвенные рёбра** (подписка → обработчик, событие формы → обработчик) — то самое, что мы в июле забирали из codebase-memory как концепт и делали руками через `nkdk`/`edt-mcp`. Бенчмарк этого видеть не мог: в 0.15.0 их не было. Вердикт «наш слабее» на текущую версию **не переносится**.

**Но замер вскрыл собственную проблему — не в индексе, а в том, как мы его зовём.** Один и тот же запрос (11 функций с именем `ОтправитьСообщение`):

| Способ | В контекст |
|---|---|
| `query --json` как есть — **с телами функций** | **24 633 симв.** |
| сырой `grep -rn` по тем же файлам | 5 442 симв. |
| компактная выжимка (имя + сигнатура + строки) | **396 симв.** |

То есть **неаккуратный вызов индекса в 4,5 раза хуже обычного grep**, а правильный — в 14 раз лучше. Именно об этом rlm-tools-bsl: ценность не в индексе, а в том, что уходит в контекст (у них — только `print()` из скрипта в песочнице). У нас этот принцип уже реализован в 9-м контуре `enrich-code-facts` (отдаёт выжимку, не тела), но при ручных вызовах MCP-инструментов он не соблюдался нигде — см. [[token-economy-and-local-tools]].

⚠️ **Чего замер НЕ доказывает:** это сравнение форм вывода на одном запросе, а не e2e-качество ответов на бизнес-задачах. Полноценный прогон по методике `perform_comparison` (10 задач × агент) не выполнялся, и `rlm-tools-bsl` **не устанавливался** — установка стороннего пакета с исполнением произвольного кода на хосте требует отдельного решения владельца.

### Что эта волна сказала про нас

1. **Наш `code-index` публично проиграл** конкуренту по токенам (288K против 160K) — пусть и в версии 0.15.0. Это первый случай, когда наш инструмент замерил кто-то со стороны.
2. **Три дисциплины оказались слабее, чем у соседей:** проверка шла всегда полным сетом (у них — по классу правки), след прогона не отделял «не применимо» от «не смог», а живость источника правил не подтверждалась вовсе.
3. **«Штатное прежде своего» держалось на памяти скилла** — при живом открытом источнике исходников БСП.

### Метод: сверка слоя скиллов через skills.sh

API вычислен из `src/find.ts` репозитория `vercel-labs/skills`, ставить ничего не нужно:

```
https://skills.sh/api/search?q=<URL-кодированный запрос>&limit=100[&owner=<gh-owner>]
```

- Ответ: `{query, searchType: fuzzy|semantic, searchVersion, skills:[{id, skillId, name, installs, source}], count, duration_ms}`. Запрос короче двух символов даёт HTTP 400, заголовков rate-limit нет.
- **1С-срез отдаётся только на кириллицу:** «1С», «1с», «БСП» и семантический «1c enterprise» возвращают 1С-каталог. Латинские `1c`, `bsl`, `edt` дают шум.
- Порог по установкам в 1С-нише не применять: у нашего апстрима около 25 установок на скилл.
- API не документирован (`searchVersion: "legacy"`) — перед сверкой sentinel: `q=%D0%A1` (кириллическое «С») обязан вернуть `count > 0` и `nikolay-shirokov/cc-1c-skills`.
- Необязательный внешний сигнал риска: `https://add-skill.vercel.sh/audit?source=<owner/repo>&skills=<slug>` (ath, socket, snyk). Он вспомогательный: у лидера `code-review` оценки расходятся от safe до high. Хост телеметрический — запрос раскрывает, что мы проверяем.
- Очередь следующей волны (не проверено, в том числе на приманку): `reason-machines/devtools-skills`, `membranedev/application-skills` (1c), `vladimir-kharin/1c-batch`, `vgtitov/claude-1c-toolkit`, `ntin60775/cc-1c-skills`.

Подробности установки, конфига и проверенного контракта — [[installed-tools-and-servers]], раздел «ssh-mcp».
