# Управляемые формы 1С: практикум

Опорный документ по разработке форм 1С. Цель — не править `.form` вслепую, а работать штатными средствами, видеть результат и проходить форму поэлементно. Правило поведения — [[forms-skills-and-visual-check]].

## Инструментарий (что использовать)
- **Скиллы `form-*`** — основной путь: `form-info` (анализ), `form-patterns` (справочник раскладок), `form-compile` (собрать из JSON), `form-edit` (точечно менять), `form-validate` (проверка), `form-add` (добавить форму объекту).
- **`1c-standards`** — проверка формы на UI-стандарты 1С.
- **`edt-mcp` скриншоты** — `get_form_screenshot` / `get_form_layout_snapshot`. Требуют флаг рендера в EDT (см. [[edt-mcp-pitfalls]] → «Скриншот формы: флаг рендера в `1cedt.ini`»). Без флага PNG пустой (серый).
- **`1c-formsserver`** — генерация из JSON-спеки/шаблона, валидация, **конвертация Конфигуратор↔Managed↔EDT**, поиск по примерам. Подключён как MCP-сервер **`1c-forms`** (`http://localhost:8011/mcp`; инструменты `generate_form`/`validate_form`/`convert_form`/…, см. [[installed-tools-and-servers]]). Каркас в формате EDT у него неполон — сверять по [[forms-from-edt-metadata]].
- **Ручная правка `.form`** — крайняя мера; байтобезопасно (см. [[edt-mcp-pitfalls]] → правка .form).

## Эскиз формы в ответе (нотация)

Эскиз нужен для согласования замысла до генерации ([[forms-skills-and-visual-check]] п.0б): владелец читает его как мокап, а не как JSON. Нотация минимальная и своя, по мотивам языка «Накидки» (`crimsongoldteam/md_design`, MIT; их синтаксис не копируется — взята идея текстового мокапа):

```text
--- Заголовок формы ---
Реквизит: значение-пример        | кнопки поля: [сп] список, [оч] очистка, [от] открытие
[ ] Флажок                       | [x] — включённый по умолчанию
#Группа слева      #Группа справа   | две группы в строке = колонки
    вложенный элемент                | вложенность — отступом
/Страница                         | страницы формы
< Кнопка | Кнопка >               | командная панель
[таблица] Строки: Колонка1 | Колонка2 | Колонка3
```

Правила эскиза: имена реквизитов — настоящие (из `form-info` или ТЗ, не выдуманные); типы указываются, когда влияют на решение; эскиз одной формы — один блок; после согласования эскиз переносится в JSON-определение `form-compile` **один к одному**, расхождение называется вслух.

## Три формата формы
| | Конфигуратор (`logform`) | Managed | EDT |
|---|---|---|---|
| Файл | `Form.xml` | `Form.xml` | `Form.form` |
| Элемент | `<InputField name id>` | `<InputField><Name><Id>` | `<items xsi:type="form:FormField"><name><id><type>` |
| DataPath | `<DataPath>Объект.Поле</DataPath>` | так же | `<dataPath><segments>Объект.Поле</segments></dataPath>` |
| ExtInfo | нет | нет | `<extInfo xsi:type="form:...ExtInfo">` |

В EDT-проекте работаем с форматом **EDT** (`.form`). Конвертация между форматами — через `1c-formsserver`.

## Структура `.form` (EDT)
- Дерево `items`: `FormField`, `FormGroup`, `Table`, `Button`, `Decoration`, `SearchStringAddition`…
- У каждого элемента: `name` (**уникально в пределах формы**), `id`, `dataPath` (`segments`), `type`, `extInfo` (по типу), companion-узлы `contextMenu` + `extendedTooltip` (со своими id), `handlers` (событие → процедура).
- **`id` — своя нумерация у каждой коллекции:** элементы, реквизиты, команды; у колонок — своя у каждого реквизита-таблицы. На реальной выгрузке (≈4,8 тыс. форм, сверено 19.09.2026) реквизиты почти всегда нумеруются с 1 и пересекаются с `id` элементов, колонки каждого реквизита тоже идут с 1. При вставке брать `id` по соседям той же коллекции, а не «максимум по файлу + 1» (по мотивам `bigsofter/tiny1C`, CC BY 4.0: реквизит с `id` из ряда элементов уронил форму — на 8.3 не проверено).
- **Нет тега = умолчание МОДЕЛИ EDT, а оно не всегда совпадает с платформенным.** EDT пишет только отличия: `<visible>true</visible>` стоит у каждого видимого элемента явно, у скрытого тег просто опущен (на той же выгрузке — ни одного `visible=false` на сотни явных `true`). Узел, вставленный скриптом без `visible`, импортируется молча и невидим; если это корневая группа или страницы — форма пуста (по мотивам `bigsofter/tiny1C`). Новый узел копировать с работающего элемента того же вида целиком. Отсутствие `showTitle`/`pagesRepresentation` тоже значит «умолчание», а не «не задано»; что реально стоит — `get_metadata_details` с `assignable: true` или сверка с формой-эталоном.
- `autoCommandBar` у формы и у таблицы. **Порядок сериализации:** блок `<handlers>` таблицы ставится **после** `</autoCommandBar>` (канон EDT — иначе перезапишет при пересохранении).
- **Обработчики: два места регистрации.** События формы (`OnCreateAtServer`, `OnOpen`, `NotificationProcessing`…) — корневой `<handlers>`; события формы ОБЪЕКТА (`OnReadAtServer`, `BeforeWrite`, `BeforeWriteAtServer`, `OnWriteAtServer`, `AfterWrite`, `AfterWriteAtServer`) — `<handlers>` внутри корневого `<extInfo>` (сверено на реальной выгрузке форм документов). В узле пара `<event>` + `<name>`, где `<name>` — имя ПРОЦЕДУРЫ. Обработчик без регистрации (или не в том месте) молча не вызывается: ни `bsl-analyzer`, ни `get_project_errors` этого не видят — ловится только прогоном живой формы.
- Реквизиты формы — в `attributes` (главный — `Объект`, `main=true`).

**Что EDT требует сверх того, что генератор проставляет сам** (проверять, если форма не рендерится или колонки ведут себя странно):
- **Корневой `extInfo` по типу владельца** — `form:ObjectFormExtInfo` (обработка/отчёт), `form:CatalogFormExtInfo`, `form:DocumentFormExtInfo`, `form:InformationRegisterFormExtInfo`. Без него дизайнер EDT может показать пустую форму.
- **`commandInterface`** с вложенными `navigationPanel`/`commandBar` — требуется моделью; EDT дописывает при сохранении, но лучше задать явно.
- **Команды формы — тег `formCommands`** (в EDT-формате именно так, не `commands`, как в logform): `name` + `id` + `action`.
- **Колонки реквизита-`ValueTable` — обязательный `<id>` у каждой колонки** плюс `view`/`edit`. Без `id` платформа не связывает `FormField` в таблице с колонкой: симптом — **все колонки показывают заголовок первой** при правильных `dataPath`. `id` колонок уникальны в пределах своего реквизита (канон EDT — с 1, см. «`id` — своя нумерация» выше; в одном из экземпляров нумеровали от 500+ — тоже работало). `copy.deepcopy` узла уносит его `<id>` → `form-legacy-emf-check` «Duplicate id». Без `view`/`edit` колонки помечены крестиком в дизайнере.
- **Реквизит `DynamicList`** — свой `title` обязателен; группа колонок — `xsi:type="form:FormGroup"` с `<type>ColumnGroup</type>`, иначе EDT молча отбрасывает её вместе с детьми _(наблюдения экземпляра)_. «Использовать всегда» у поля списка в `.form` — это `<notDefaultUseAlwaysAttributes>` у реквизита-списка (сверено на реальной выгрузке).
- Префикс `form:` только на корне (канон EDT) либо на всех узлах (так пишет lxml) — **оба варианта валидны**; если форма не рендерится, причина не в префиксе.

## Чек-лист свойств — проходить ПОЭЛЕМЕНТНО (главное, что нельзя пропускать)

При ревью/правке формы проходить по **каждому** элементу и смотреть его **свойства**, а не только заголовок и локализацию. Покрытие — **сплошное**: автоаудит скриптом по `Form.form`/`.mdo` или через `get_metadata_details`/`get_project_errors`, чтобы охватить ВСЕ элементы, а не выборочно. Если элемент отображается не так — диагностировать **свойствами через инструменты**, а не догадками («кэш», «артефакт отрисовки»); версию/состояние подтверждать инструментом ДО правки. *(Кейс живого экземпляра, бекпорт 12.07.2026: «пустые» вкладки-страницы оказались следствием свойства `showTitle` — пустой самозакрывающийся `<extInfo PageGroupExtInfo/>`, а не кэша.)*

**Поле ввода (`FormField`/InputField):**
`dataPath` существует в объекте · `titleLocation` (Auto/None/Left/Top) · `showTitle` · `visible`/`enabled`/`userVisible` · `skipOnInput` · `width`/`autoMaxWidth`/`horizontalStretch` · `choiceParameterLinks` (связанный отбор, напр. `Filter.Owner`) · `editMode` · `wrap`/`chooseType`/`quickChoice` · привязаны ли `OnChange`/`StartChoice`.

**Таблица (`Table`):**
`dataPath` · `titleLocation` · `height`/`heightControlVariant` · `horizontalStretch`+`verticalStretch` (обычно `true`) · `autoCommandBar` (кнопки) · `changeRowSet`/`autoInsertNewRow` · события `OnActivateRow`/`BeforeAddRow`/`BeforeDeleteRow` · состав и свойства колонок.

**Группа (`FormGroup`):**
`type` (UsualGroup/Page/Pages/ButtonGroup) · `extInfo.group` (Vertical/Horizontal/**AlwaysHorizontal**/HorizontalIfPossible) · `united` · `showTitle` (у группировочных групп по умолчанию свой — проверять) · `horizontalStretch` · представление/заголовок.

**Кнопка (`Button`):**
`type` (CommandBarButton/UsualButton/Hyperlink) · `commandName` (`Form.Command.X` / `*.StandardCommand.*`) или `handler` · `representation` (Text/Picture/PictureAndText) · `placementArea` · картинка.

## Каталог событий (назначение)
**Форма:** `ПриСозданииНаСервере` (OnCreateAtServer — инициализация), `ПриОткрытии` (OnOpen), `ПередЗаписьюНаСервере`/`ПриЗаписиНаСервере`/`ПослеЗаписиНаСервере`, `ПередЗакрытием`, `ОбработкаВыбора` (когда форма — выбор).
**Поле:** `ПриИзменении` (OnChange), `НачалоВыбора` (StartChoice), `ОбработкаВыбора` (ChoiceProcessing), `Очистка` (Clearing), `АвтоПодбор` (AutoComplete), `ОкончаниеВводаТекста`.
**Таблица:** `ПриАктивизацииСтроки` (OnActivateRow), `ПередНачаломИзменения`, `ПередДобавлением`/`ПередУдалением`, `ПриАктивизацииЯчейки`, перетаскивание.
Событие в форме привязано в `.form` (`handlers`), процедура — в модуле формы. **Проверять привязку в обе стороны** (нет процедур-сирот и событий без обработчика).

## Паттерны раскладки
Архетипы и **имена групп** (шапка в две колонки, страницы, подвал, номер и дата в одну строку) — только по скиллу `form-patterns` и эталонам реальных форм проекта; своих имён здесь не вводим (до 16.10.2026 тут стояли другие имена колонок шапки, чем в скилле). Свойства, которые проверить у готовой формы:
- у полей шапки `horizontalStretch=false` — иначе колонки разъезжаются;
- таблица на весь размер — `horizontalStretch` и `verticalStretch` = `true`;
- многострочный комментарий — `wrap=true`.

## Точный порт формы из другой конфигурации

Переносимую форму воспроизводить **точь-в-точь**, а не упрощать в скелет: генерация «с нуля» по метаданным (`create_metadata` с `generateContent`+`objectFields`) даёт упрощённый каркас — теряет многоколоночную шапку, командную панель с кнопками, служебные поля, вложенные подгруппы, вкладки, индикаторы. Раскладку не придумывать — воспроизводить.

1. **Визуальный эталон оригинала — ДО работы:** скриншот исходной формы (`get_form_screenshot` со второго EDT-моста, где открыта исходная конфигурация, — или скриншот от пользователя).
2. `get_metadata_details` исходной формы — точная структура: элементы, реквизиты формы с типами, команды, обработчики.
3. **Полный порт исходного `.form`** (скрипт-трансформ, байтобезопасно — см. [[edt-mcp-pitfalls]]): ремап имён в `<segments>` под целевые метаданные (шапка + ТЧ + `RegisterRecords`), ремап типов реквизитов формы и ссылок на объекты источника → целевые; **снять ВСЕ чужие `<handlers>` и обработчики команд** (пока модуль пуст, форма — визуальный скелет без логики); блоки с отсутствующими зависимостями (картинки, колонки ТЧ) — сперва проверить, не перенесена ли зависимость под другим именем (тогда ремапить ссылку), иначе удалить; стандартные `StdPicture.*` оставлять, если имя существует в платформе (несуществующее EDT и анализаторы пропускают, а платформа форму не грузит).
   - **Ремап имён — только в структурных тегах** (`<name>`, `<commandName>`, `<segments>`/`<dataPath>`, `<parent>`, `<source>`); тексты `<title>`/`<toolTip>` — отдельным проходом по словарю фраз, иначе портятся заголовки. Значения перечислений в `choiceList` (`Enum.X.EnumValue.Y`) — своей картой: EDT их не проверяет, падает `update_database`.
   - Имена элементов, к которым общие модули обращаются напрямую (`Форма.Элементы.X` без `Найти`), берутся из контракта модуля, а не из ремапа; имена колонок и служебных полей — из уже портированных форм своей подсистемы.
   - Запись `.form` через `xml.etree` теряет объявление `xmlns:core` (префикс живёт только в значениях `xsi:type`), пишет декларацию в одинарных кавычках и съедает финальный перевод строки — после записи проверить `head -2` и наличие `core:`; `copy.deepcopy` переносит `<id>` (см. «Колонки…» выше).
   - Сироты порта, которых `get_project_errors` не видит: `<source>` в дополнениях таблицы (`searchStringAddition`/`viewStatusAddition`/`searchControlAddition`), заголовки донора (поле с `dataPath` и так берёт синоним реквизита), `<handlers>` без процедур в модуле.
4. `create_metadata` пустой формы (регистрация в модели EDT + `setAsDefault`) → **overwrite** её `Form.form` портом → `revalidate_objects` → `get_form_screenshot` цели → **поэлементная сверка со скриншотом оригинала**.

Сборку «из кубиков» (пересоздание раскладки блоками `create_metadata`) для точь-в-точь не использовать — упрощает раскладку; только запасной вариант.

## Дополнительно (куда копать)
- **Условное оформление** (`conditionalAppearance`) — цвет/видимость/доступность по условию, без обработчиков событий. Настраивать его рекомендуется **кодом формы при её создании** (std710 п.2.1–2.2: переносимо в общие модули, переживает объединение конфигураций, ловит переименования синтаксическим контролем); при порте формы `conditionalAppearance` из разметки переписывается кодом.
- **Параметры формы** (`parameters`) — как форма получает вход (Ключ, Отбор, режим выбора).
- **Программное изменение** — `Элементы.Добавить`/`ИзменитьФорму` в `ПриСозданииНаСервере` для динамики.
- **Функциональные опции/роли** — видимость элементов без правки формы.

## Грабли (реальные)
- Не править `.form` вслепую — использовать скиллы/скриншот; ручной XML → байтобезопасно (см. [[edt-mcp-pitfalls]]).
- `handlers` таблицы — после `</autoCommandBar>`.
- Стандартный реквизит даты — `Объект.Дата` (не `Date`).
- Подчинённый справочник в поле — `choiceParameterLinks` (`Filter.Owner`).
- `id` элементов уникальны среди элементов формы (у реквизитов и команд — своя нумерация, см. «Структура .form»); companion-узлы (`contextMenu`/`extendedTooltip`) тоже имеют id.
- Кнопки перехода к движениям — не свои кнопки, а стандартные `*.StandardCommand.OpenByRecorder` в `navigationPanel` (по умолчанию невидимы — включать явно).
- После удаления реквизита/элемента обращения `Элементы.<Имя>` в модуле остаются, `get_project_errors` их не видит — сверять множество `Элементы.*` модуля с `<name>` формы, корни `dataPath` — с `attributes`, `<handlers>` — с процедурами модуля.
- **Заголовок поля динамического списка стирается молча.** Пока у реквизита-списка `autoFillAvailableFields = true`, EDT выводит состав полей из текста запроса и при КАЖДОЙ перегенерации переписывает блок `<fields>` в `DynamicListExtInfo` целиком — вместе с заголовками. Ни ошибки, ни предупреждения. Подпись колонки задавать **заголовком ЭЛЕМЕНТА формы** (`Field` в дереве элементов) — он живёт в разметке и перегенерацией не затрагивается. Кейс живого экземпляра (28.07.2026): после серии правок формы через модель исчезли сразу три заголовка, жившие там с момента порта эталона.
- **Локальная переменная в модуле формы не должна называться как реквизит формы или как свойство элемента.** В `&НаСервере`-методе присвоение `ИмяРеквизита = …` **перезаписывает реквизит формы**, а не заводит локальную переменную: изменение уезжает на клиент и роняет форму. Опасные имена свойств: `Параметры`, `ПараметрыВыбора`, `СвязиПараметровВыбора`, `СписокВыбора`, `ПараметрыОтбора`, `ОтборСтрок` (платформа трактует присваивание как установку свойства элемента → «Несоответствие типов»). На форме отчёта БСП особо опасны реквизиты `НастройкиОтчета` и `Результат`: затёртый `НастройкиОтчета` теряет ключ `СвойстваРезультата`, и клик по табличному документу падает с «Поле объекта не обнаружено (СвойстваРезультата)» — причём только **после** кастомной серверной операции формы, отчего баг выглядит плавающим. Именовать с контекстом: `ПараметрыВыбораНоменклатуры`, `НастройкиОтчетаДетализация`, `ВидПоля`. Диагностика любого «поле объекта не обнаружено» после серверной операции формы — сперва искать локальную переменную с именем реквизита. Смежная диагностика — `acc:2` (обращение к зарезервированному имени); список свойств практический и может быть неполным — при подозрении проверять в конфигураторе. То же касается **свойств самой формы** (`ФормаКлиентскогоПриложения`, сверено `bsl-platform getMembers`): `Группировка`, `Заголовок`, `Элементы`, `Команды`, `Параметры`, `Доступность`, `ТолькоПросмотр`, `Модифицированность`, `Ширина`, `Высота`, `Окно`, `ВладелецФормы`, `ТекущийЭлемент` — присваивание локальной «переменной» с таким именем пишет в свойство формы. В модуле объекта так же затирается имя табличной части.

*Требования EDT к `.form` и грабля зарезервированных имён перенесены знанием из `rules/` набора Desko77 (MIT); разбор источника — [[external-skills-review]].*

## Рантайм-грабли управляемых форм (чекеры молчат)

Пункты ниже проходят EDT, `bsl-analyzer` и `form-validate` и всплывают только на живой форме. Наблюдения экземпляров; что сверено инструментом — указано.
- **`ТекущиеДанные` динамического списка содержат только выведенные колонки** — `visible=false` не помогает. Колонке, нужной алгоритму, ставить «Использовать всегда» (std702 п.2.1–2.2 — и только там, где значение правда нужно); ссылку текущей строки можно брать из `ТекущаяСтрока`.
- **Поля активной строки** выводятся путём данных `Элементы.<Таблица>.ТекущиеДанные.<Колонка>` — без реквизитов-дублей и обработчика `ПриАктивизацииСтроки`.
- **Смена `ИзменятьСоставСтрок` на другое значение пересобирает автокомандную панель таблицы**, подменю «Создать на основании» пересоздаётся: сделанное с ними в `ПриСозданииНаСервере`/`ПриЧтенииНаСервере` теряется — восстанавливать после пересборки. Присваивание того же значения панель не трогает.
- **Автоэлементы командной панели с источником «Форма» выводятся перед явно размещёнными кнопками.** Нужны явные «Провести…» первыми — место автогруппы задавать программно (`Элементы.Переместить`) в общей точке, которая вызывается и при пересборке панели; не нужен код — не размещать стандартные кнопки явно. На EDT-скриншоте автогрупп нет — порядок проверяется только в клиенте.
- **`multiLine` + расширенное редактирование множественных значений подменяет кнопку выбора** — `НачалоВыбора` не вызывается. Диагностика таких случаев — сравнить полный список свойств элемента с таким же элементом рабочей формы.
- **Обработчик `ОписаниеОповещения("Имя", ЭтотОбъект)` обязан быть `Экспорт`** — имя ищется строкой в рантайме. EDT может пометить такой метод неиспользуемым — экспорт не снимать.
- **Тип реквизита формы против кода:** у `ДанныеФормыДерево` есть `ПолучитьЭлементы()`, у `ДанныеФормыКоллекция` — нет (сверено `bsl-platform`). «Метод объекта не обнаружен» после правки — сперва сверить тип реквизита формы с кодом.
- **Серверный код, вызванный из формы, не записывает объект, открытый в этой же форме** — блокировка своим же сеансом. Данные возвращать в форму; необязательную запись — в `Попытку` с записью в журнал регистрации. Воспроизводить `ЗаблокироватьДанныеДляРедактирования` через `execute_code` — только на тестовой базе.
- **Вызов клиентского общего модуля из `&НаСервере` EDT не ловит** — форма просто не открывается. Сопоставлять директиву метода с флагами модуля ([[edt-mcp-pitfalls]] → «Общие модули»).
- **Состояние-число картинкой** — поле картинки с `valuesPicture` (полоса кадров): значение 0 показывается штатно, а условное оформление картинкой на 0 не срабатывало.

## Приёмы
- **Ограничить выбор — декларативно:** `listChoiceMode=true` (РежимВыбораИзСписка) и список выбора, заполняемый в `ПриСозданииНаСервере`, без обработчиков `НачалоВыбора`/`ПриИзменении` (на реальной выгрузке так устроены сотни форм). У любого поля со списком выбора `РежимВыбораИзСписка = Истина` требует std765 п.5 (АПК:448). Представления элементов списка — на всех языках профиля ([[language-profile]]), иначе на другом языке показывается само значение (по мотивам `bigsofter/tiny1C`, CC BY 4.0).
- **Заголовки:** у таблиц и групп — явно (std765 п.2, АПК:446); у колонок динамического списка, вычисленных в запросе или с собственным псевдонимом, — явно на всех языках профиля (std765 п.4, АПК:464), иначе виден псевдоним на языке разработки.
- **Выбор из одного варианта:** состав вариантов задан конфигурацией — поле скрывать функциональной опцией (см. «Антипаттерны»); единственный вариант возникает от данных — подставлять его в пустое поле при открытии формы и при смене строки.
- **«Время не задано» и «полночь»** в типе `Дата` неразличимы — один реквизит с составом «Дата и время» и видимым значением по умолчанию лучше скрытого правила.
- **Автосохранение формы** (`СохранениеДанныхВНастройках`) хранит реквизиты, помеченные «Сохраняемые данные»; значение, которое должно жить между сеансами независимо от формы, — `ОбщегоНазначения.ХранилищеОбщихНастроекСохранить`/`…Загрузить` (БСП, сверено `bsp_api.py`). Сохраняются ли автоматически подчинённые реквизиты основного реквизита `Объект` — не проверено.
- **Защита ячеек табличного документа:** `Защита` области действует только в режиме просмотра (справка платформы: недоступны ячейки, у которых установлено свойство `Защита`), а `ТабличныйДокумент.Защита = Истина` защищает весь документ — его можно только распечатать. Частичная защита — свойство у нужных областей, документ целиком не защищать. _(Схема из экземпляра прогоном не подтверждена.)_
- **Динамический список:** соединение с подзапросом в его запросе запрещено (`v8cs:ql-join-to-sub-query`, std655 п.1.1), а временных таблиц у него нет — обход: `Ссылка В (ВЫБРАТЬ …)` или расчёт в `ПриПолученииДанныхНаСервере` _(приём экземпляра)_.

## Поле HTML-документа: мост BSL ↔ JS

_Наблюдения одного из экземпляров на мобильном клиенте; на тонком и веб-клиенте — не проверено._
- **Проверка только вживую:** WYSIWYG EDT и `get_form_screenshot` поле не рендерят, headless не проверить.
- **Формат EDT:** `extInfo` поля — `form:HtmlFieldExtInfo` (для XML-выгрузки не проверено). `get_project_errors` соответствие `extInfo` типу поля не проверяет — неверный проходит валидацию и падает только при загрузке в платформу; `modify_metadata` меняет `type` поля, но не `extInfo`.
- **1С → JS:** `defaultView` документа доступен после события `ДокументСформирован` (DOM грузится асинхронно). Строка через `defaultView` теряла фигурные скобки и переводы строк — передавать JSON с URL-кодированием; присваивание реквизиту поля доходит без потерь.
- **JS → 1С:** `ПриНажатии` с `ДанныеСобытия.Href` (из JS — `location.assign(...)`) или скрытый элемент со свойством-событием.
- **События — только `onclick`** плюс `<meta name="viewport">`: `ontouchstart` вместе с `onclick` вызывает обработчик дважды, один `ontouchstart` на прокручиваемом списке открывает элемент при прокрутке.
- **Разметка:** `<!DOCTYPE html>` первым символом, `html, body { height: 100% }`. CSS: `gap` во flex не работает — отступы через `margin`; рискованны `place-items`, `aspect-ratio`, `:is()`.
- **CSS и JS — в общих макетах** (текстовый документ), подставлять через `СтрЗаменить` (у `СтрШаблон` проблемы с `%` — со слов источника). HTML экранировать; спецсимволы поиска через `ПОДОБНО` — по std726. Большие списки — порционная загрузка.

## Антипаттерны компоновки — «когда НЕ надо»

Наш `form-patterns` отвечает на вопрос «как сделать». Этот раздел — про обратное: типовые решения, которые **выглядят разумно и ломают форму**. Проекция гайда `Oxotka/1CDesignGuide` (MIT, 186★, сверено 19.08.2026) на наш процесс — правила пересказаны, не скопированы.

**Выбор элемента:**
- **Декорация — не заголовок поля.** Заголовок надписью ломает автофокус на поле, и двоеточие регулярно забывают. Заголовок — свойство самого поля.
- **Декорация — не средство выравнивания.** Для этого есть группы с их свойствами.
- **Гиперссылка ведёт, кнопка делает.** Действие на гиперссылке и переход на кнопке — перепутанные роли; пользователь не угадывает поведение по виду.
- **Флажок — только для очевидной пары состояний.** Неочевидное «включено/выключено» — переключатель. **Отрицательные формулировки в заголовке запрещены**: выключенный флажок «Не проводить» читается двойным отрицанием.
- **Тумблер не для двух значений** (непонятно, что выбрано) и без повторяющихся слов в вариантах — общее слово выносится в заголовок.
- **Составной тип — не платформенным выбором типа**, а явным выбором («Контрагент / Физическое лицо»).
- **Поле выбора с единственным значением не нужно** — реквизит заполняется кодом, поле скрывается функциональной опцией (если единственность зависит от данных — см. «Приёмы»).

**Компоновка:**
- **Поле, меняющее состав формы, идёт первым** (классически — «Вид операции»). Нижнее поле не должно перестраивать верхние.
- **Порядок по зависимости данных:** сначала то, от чего зависит выбор (Контрагент), потом зависимое (Договор) — иначе смена верхнего поля молча обесценивает уже заполненное нижнее.
- **В свёртываемых и всплывающих группах не место обязательному и часто используемому.** У всплывающей группы обязателен внятный заголовок — пользователь должен понимать, что за ним.
- **Симметрия колонок — не цель.** Слева важное, справа второстепенное; неравное число полей нормально.
- **Условное оформление — оформление, а не видимость строк** (std710 п.1.1: скрытие строк целиком тормозит веб-клиент и искажает таблицу).
- **Ориентир минимального разрешения — 1280×768**; горизонтального расположения избегать, если оно не обязательно.

⚠️ Это **рекомендации по проектированию**, а не диагностики: ни один наш чекер их не проверяет, `form-validate` смотрит структуру, а не удобство. Поэтому они применяются на этапе проработки формы ([[design-before-code]] разд. 8) и в ревью, а не «после».

## Протокол проверки формы (обязательный, до слова «готово»)
1. `form-validate` / `revalidate_objects` → `get_problem_summary` = 0.
2. **Увидеть результат:** `get_form_screenshot`/`get_form_layout_snapshot` (нужен флаг рендера) или прогон через `web-test`. Скриншот отвечает на «как выглядит», а не на «что в данных»: снимок тулкита сразу после открытия формы показывал её до отрисовки строк табличной части. Состояние (строки, списки выбора, свойства) проверять чтением — `execute_code` тулкита в клиентском контексте (`execution_context: "client"`, по README тулкита) через `ПолучитьФорму(...)`; в серверном контексте `ПолучитьФорму` недоступна, из клиентского зонда возвращать простые значения (числа, булево), форму документа без `Ключ` так не получить. Только тестовая база ([[installed-tools-and-servers]]).
3. Пройти **поэлементно** по чек-листу свойств (раздел «Чек-лист свойств — проходить ПОЭЛЕМЕНТНО» выше): покрытие **сплошное** — КАЖДЫЙ элемент и его свойства, не только заголовки/локализация; автоаудит через `get_metadata_details`/`get_project_errors` или скриптом по `Form.form`. Элемент отображается не так — диагностировать **свойствами через инструменты**, а не догадками про кэш (кейс: «пустые» вкладки из-за пустого `<extInfo>`/`showTitle`).
4. События привязаны в обе стороны (`.form` ↔ модуль).
5. Прогнать сценарий (открыть/заполнить/провести) — и только потом «готово».

Эталоны раскладки брать из реальных форм проекта (EDT-сериализация) — как образец канона.
