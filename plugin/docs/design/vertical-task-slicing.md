# Правило: нарезка работы — вертикальными срезами; широкий рефактор — expand–contract

ТЗ отвечает на вопрос «что делаем» ([[design-before-code]]), консилиум — «как спроектировано» ([[five-role-design-review]]). Это правило отвечает на третий вопрос — **как резать работу на задачи**, чтобы каждый шаг заканчивался проверяемым результатом, а не полуфабрикатом.

Синтезировано по мотивам практик из mattpocock/skills (MIT, Matt Pocock) — принципы пересказаны своими словами и спроецированы на 1С; англоязычный жаргон не переносится: роль «шва» в 1С играют штатные механизмы (экспортный API общего модуля, подписки, функциональные опции).

**Why:** конфигурация 1С — это связный граф ссылок, а не набор независимых слоёв. Нельзя «сначала сделать все метаданные, потом весь код»: промежуточное состояние физически невалидно (реквизит есть — кода нет, код есть — объекта нет), чекеры красные, зелёной сборки нет ни на одном шаге, и откатывать приходится всё сразу. Вертикальный срез даёт обратное свойство: после каждого среза конфигурация загружается, обновляется и проходит полный набор чекеров ([[full-checker-set-before-done]]) — значит, в любой момент есть точка отката и понятный процент готовности. Отдельно про широкий рефактор: в 1С он опаснее, чем в обычном коде, потому что за метаданными стоят **данные в базе** — «поменять тип реквизита на месте» это не рефакторинг, а потеря данных.

**How to apply:**

1. **Единица работы — вертикальный срез, проверяемый сам по себе** (исключение — явно включённый владельцем режим массового переноса, [[full-checker-set-before-done]] п.7). Срез: объект/реквизит метаданных; экспортный метод общего модуля; элемент формы; право в роли; тест YAXUnit; загрузка на тестовую базу (`db-load-xml` + `db-update`). Критерий среза один: после него конфигурация валидна и чекеры зелёные. **Горизонтальная нарезка запрещена** — «сначала все метаданные, потом весь код, потом все формы» оставляет висячие ссылки и не даёт зелёной сборки ни на одном шаге.

2. **Пре-рефакторинг вперёд: «сделай изменение лёгким, потом сделай лёгкое изменение».** Если фича не встаёт в текущую структуру — вынос логики в общий модуль (или расшивка обработчика) идёт **отдельным первым срезом**, до фичи. Это не нарушает [[coding-discipline]] п.3 (хирургический дифф): пре-рефакторинг **явно заказан планом** и имеет свой тикет и свою зелёную проверку, а не сделан походя внутри чужой правки.

3. **Размер среза = один свежий контекст.** Срез, который не помещается в одну сессию с запасом, режется дальше. Состояние работы держит **письменный тикет**, а не память сессии: контекст сжимается и хвост теряется ([[claude-code-context-engineering]]), журнал и веха — в [[work-journals-and-commits]].

4. **Тикет среза: цель, критерий приёмки, шов, статус, блокеры.**
   - **Содержимое.** В тикете **не место** путям к XML-файлам и кускам кода — они протухают быстрее тикета; факты о текущем коде добываются инструментами в момент исполнения. В тикете — только: **цель**; **критерий приёмки** (assert «годно/не годно») со ссылкой на требование `Т-n` из ТЗ; **шов приёмки** — конкретная точка, **через которую** проверяется этот критерий **именно у этого среза** (экспортный метод серверного общего модуля / движения регистра после проведения / результат СКД / метод модуля менеджера). Различать: критерий = *что* проверяем, шов = *через что*. Шов наследуется из ТЗ п.6 ([[design-before-code]]), но **пиннится на срез** — иначе исполнитель среза (свежий контекст, п.3) выводит его заново из ТЗ, и заявленное «срез проверяем сам по себе» (п.1) не выполняется без дереференса ТЗ.
   - **«Блокируется» и фронтир.** Фронтир работы = тикеты, у которых блокеры закрыты; берём только из фронтира. ⚠ **Граф блокеров ацикличен.** Цикл в «Блокируется» (A блокирует B, B блокирует A) = **дефект нарезки**: срезы не вертикальны, либо пре-рефактор (п.2) поставлен *после* разблокируемой им фичи. Ацикличность **не следует** из «вертикальности» автоматически — два вертикально-валидных среза можно ошибочно замкнуть; проверяется мысленным топосортом. Тулинг топосорта не заводить, пока граф мал ([[coding-discipline]] п.2 — не строить под несуществующую проблему).
   - **Статус тикета — 4 состояния:** **открыт** → **в работе** → **на проверке** (полный сет [[full-checker-set-before-done]] запущен, ещё не зелёный) → **готов** (= «зелёный срез» из п.1: конфигурация валидна, чекеры зелёные). Расширенные оси (отдельный приоритет, review/deferred/cancelled) не заводить — порядок задаёт фронтир, а не ось приоритета ([[coding-discipline]] п.2). Поля «шов приёмки» и словарь статуса — 1С-проекция поля `testStrategy` и статусов Taskmaster ([[external-mcp-servers-review]]; MIT+Commons Clause — концепт, не текст).

5. **Широкий рефактор — исключение, и делается expand–contract** (расширяем — мигрируем — сжимаем). **Важно: к переименованию объектов метаданных expand–contract неприменим** — двух имён у объекта не бывает, промежуточного состояния нет. Массовый rename делается **атомарно** ([[task-recipes]] §8): `nkdk rename_item` или `edt-mcp rename_metadata_object` — они сохраняют ссылочную целостность; ручной переброс имён по XML запрещён. Expand–contract применяется к двум вещам:
   - **(а) Экспортный API общего модуля.** Новый метод добавляется рядом; старый становится обёрткой над новым с пометкой «Устарела» (конвенция 1С/БСП); вызовы мигрируются **батчами по радиусу поражения** (impact-анализ — `code-index`, `find_references`, [[task-recipes]] §3), каждый батч — свой тикет с полным зелёным набором чекеров; когда вызовов не осталось — старый метод удаляется отдельным срезом.
   - **(б) Изменение схемы при живых данных.** Смена типа реквизита или измерения, разделение реквизита на два — **новый реквизит рядом → миграция данных обработкой → удаление старого**. Менять тип «на месте», когда в базе есть данные, — потеря данных, а не рефакторинг. Имена новых реквизитов — по [[naming-and-module-design]]; миграционная обработка и удаление старого реквизита — отдельные срезы, каждый со своей приёмкой.

6. **Триаж риска — при нарезке, а не только перед коммитом.** Тяжесть процесса подбирается по цене ошибки среза, а не одним шаблоном на всё. Класс риска прикидывается по плану среза тем же классификатором, что и по диффу ([[task-recipes]] §19, [[full-checker-set-before-done]] п.8; второй не заводится), чтобы глубина проверки и согласование были заложены в срез заранее, а не всплыли при сдаче. Размер диффа класс не понижает: триггеры 🔴 «независимо от размера диффа» перечислены в таблице [[task-recipes]] §19 (классификатор один). Сверх таблицы сомнение трактуется вверх для контракта экспортного метода (меняется — только expand–contract, п.5а) и связанных метаданных (переименование, удаление, новый объект, сразу используемый кодом). Идея триггеров — по мотивам comol/ai_rules_1c (лицензии нет — только идея, своими словами).

**Принуждение (с 4.8.0):** напоминание каждого хода (`tools-gate.md`, словарь статусов в блоке матрицы) и проверка после факта п.4: `lint-project-docs` после правки проектного дока в `docs-project/` сверяет статусы тикетов (поле «Статус:» рядом с полями «Критерий приёмки» / «Шов приёмки» и колонку «Статус» таблицы тикетов) со словарём открыт → в работе → на проверке → готов и сразу говорит модели о расхождении; регресс — `contour-tests` §25. Вертикальность, размер среза и ацикличность блокеров не проверяются.
