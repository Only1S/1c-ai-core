# База знаний dev_core

Оглавление `docs/` — только переиспользуемое ядро. `dev_core` — ядро «работа с 1С» для новых проектов (инструменты, подключения, правила). Всё своё этой копии — журналы (worklog/changelog/project-status) и проектные доки — живёт в `docs-project/` со своим оглавлением `INDEX.md` ([project-knowledge-folder](process/project-knowledge-folder.md)).

## Порядок работы с владельцем
- [project-knowledge-folder](process/project-knowledge-folder.md) — Знания разделены границей папок — docs/ = правила и справочники ядра (в проект приходят плагином, в проекте не правятся), docs-project/ = всё своё проекта (журналы worklog/changelog/project-status + проектные доки + INDEX.md); маршрутизация по происхождению; приоритет проектного правила — только с явной пометкой «Переопределяет»; раскладка docs-project — по виду документа
- [run-checks-quietly-in-background](process/run-checks-quietly-in-background.md) — Проверки (health-check/contour-tests/mcp-smoke) и операции выпуска и обновления (release-core, обновление проектов) гонять в ФОНЕ и показывать только итог-вердикт, а не полный вывод — простыни логов в чат не выводить
- [capture-knowledge](process/capture-knowledge.md) — Постоянное правило — новое знание записывается сразу и в нужное место — правило или предпочтение пользователя, присланное API или документация, сам найденный грабль инструмента; затем подтверждение одной строкой. Включает бывшее правило о присланных API (save-apis-and-docs)
- [ask-before-changing](process/ask-before-changing.md) — Не действовать автономно — до изменений спрашивать «делать или нет», особенно в общих модулях, ролях, корне конфигурации и вне узкой задачи; Workflow, фоновые и многоагентные прогоны — только после явного «да» на конкретный запуск
- [questions-as-options](process/questions-as-options.md) — Любой вопрос/выбор задавать через окно вариантов (AskUserQuestion), а не свободным текстом; рекомендуемый вариант — первым; при выборе инструмента или способа — сперва самому исследовать сеть и экосистему и положить свои варианты с источниками, а не только выбирать из названных владельцем
- [work-journals-and-commits](process/work-journals-and-commits.md) — Постоянное правило — вести журнал работы (worklog), детальный changelog (строка на правку, метка до секунды) и git-коммиты ПО ВЕХАМ (завершённое правило/инструмент/аудит/обкатка — один коммит; trailer Co-Authored-By НЕ добавлять — прямое распоряжение владельца 23.07.2026); КАЖДАЯ копия (мастер и каждый экземпляр) ведёт собственный git; необратимое решение (фильтр трёх условий) оформляется ADR, веха даёт ссылку на него; строка «Следующий шаг» до 60 символов обновляется на каждой вехе
- [subagents-on-explicit-consent](process/subagents-on-explicit-consent.md) — Субагенты/Workflow/фоновые прогоны — только после явного «да» владельца на конкретный запуск (ultracode и auto-режим согласием не считаются), и только когда нужна широта охвата; другие сессии приложения Claude (start_session, hand_off_to_session, карточки «New session») не предлагать и не создавать — только по прямой просьбе владельца; по умолчанию solo + локальные MCP (подчинено ★token-economy-and-local-tools)
- [token-economy-and-local-tools](process/token-economy-and-local-tools.md) — Постоянное правило — не транжирить токены (сжатие, точечные чтения) и максимально использовать локальные MCP; НО при разработке корректность-через-инструменты важнее экономии — глубокое обдумывание и сверка со стандартами/БСП токенами не ограничиваются
- [journal-placement](process/journal-placement.md) — Журнал 1С-работы форков конфигурации ведётся в репозитории КОНФИГУРАЦИИ (config-монорепо) по веткам форков, слияние через хаб; docs-project/ экземпляра держит журнал ЯДРА/ТУЛИНГА на main. Шов по происхождению правки; уточняет work-journals-and-commits для форков
- [tool-calls-not-chat-text](process/tool-calls-not-chat-text.md) — Вызов инструмента выполняется настоящим вызовом, а не его текстом в ответе — команды, скрипты и тела вызовов, которые предполагалось выполнить, в чат не выводятся; git-сообщение — коротким -m без heredoc; длинный execute_code с кириллическим BSL дробить или отдавать субагенту; короткие фрагменты кода в объяснениях, находках ревью и пунктах проработки разрешены
- [file-and-folder-names](process/file-and-folder-names.md) — Имена файлов и папок ядра и проектов — латиница, строчные буквы через дефис, осмысленные английские слова (rules/forms/forms-via-skills.md, docs-project/tasks/stock-transfer.md); имя называет содержимое, а не его историю; имена объектов 1С внутри файлов не меняются
- [mod-mockup-before-code](process/mod-mockup-before-code.md) — Новый мод или правка его видимой части начинаются с макета в окне Claude Code Desktop — что, где и как будет выглядеть; код пишется только после согласования владельцем, а место на экране подтверждается живьём (распоряжение владельца 31.10.2026)

## Код 1С
- [naming-and-module-design](code/naming-and-module-design.md) — Думать как архитектор — префикс подсистемы и суффиксы общих модулей по std469, без дублей, имена выверяются инструментом; модуль оценивается по ГЛУБИНЕ, интерфейс = экспортные сигнатуры плюс флаги контекста, тест удаления отсеивает прокладки, шов — только штатным механизмом и от двух реализаций
- [language-profile](code/language-profile.md) — Языковой профиль проекта — язык кода (en|ru) спрашивается ОДИН раз при развертывании и определяет весь код и все имена метаданных; комментарии всегда по-русски; ВСЁ видимое пользователю на всех языках профиля — не только синонимы/представления, но и сообщения/предупреждения/вопросы/заголовки в коде через НСтр (std761); техническое/внутреннее не локализовать (std764); новые языки в конфигурацию — только по согласованию
- [two-axis-code-review](code/two-axis-code-review.md) — Ревью кода 1С — двухосевое: ось «Стандарты» (жёсткое нарушение с номером v8std/BSLLS против суждения) и ось «Спека» (дифф против ТЗ — не сделано / сделано сверх / сделано мимо критериев приёмки); зона ответственности задаётся диффом от merge-base ветки форка, но чекеры гоняются по целому объекту; оси не сливаются — итог по худшей находке в каждой; в чек-листе — тест удаления модуля
- [coding-discipline](code/coding-discipline.md) — Четыре дисциплины кодинга против типовых ошибок LLM (по мотивам наблюдений Андрея Карпатти) — думать до кода (допущения вслух), минимализм без спекулятивного, хирургический дифф (не трогать соседнее), задача → проверяемая цель; спроецировано на 1С/BSL и правила ядра
- [bug-diagnosis-loop](code/bug-diagnosis-loop.md) — Баг ловится петлёй, а не догадкой — сперва детерминированное автоматическое репро (YAXUnit/харнесс/execute_code на тесте/реплей ТЖ), затем минимизация, фальсифицируемые гипотезы, один зонд на гипотезу, регрессионный тест КРАСНЫМ до фикса; закрытие — зелёные чекеры, пустой grep по метке DEBUG и верная гипотеза в журнале
- [edit-project-sources-directly](code/edit-project-sources-directly.md) — Правки кода и метаданных вношу прямо в исходники проекта (XML-выгрузка при Designer-XML, проект EDT через edt-mcp и скиллы), а не фрагментами на ручную вставку; фрагменты — только по явной просьбе, целыми методами с местом вставки и отдельным списком метаданных «руками в Конфигураторе»; в ответе — список изменённых файлов или дифф; приёмка перевыгрузки владельца — git diff, без git — сверка с отданными эталонами
- [comment-budget](code/comment-budget.md) — Бюджет комментариев в модулях 1С — описание метода одной строкой, без абзацев прозы в шапке, без поясняющих комментариев в теле (остаются только директивы анализаторов); обоснования — в журнал конфигурации; проверка и чистка — tools/1c/bsl-comment-audit.py; маркеры вставок в типовые объекты не трогать
- [code-situation-standards-map](code/code-situation-standards-map.md) *(справочник)* — Карта «ситуация в коде → номера стандартов 1С» — какие стандарты v8std открыть до правки и на ревью (always / conditional / optional) по действию в коде и признакам в тексте; каждый номер сверен с v8std 19.09.2026; по мотивам axelboman277/v8std-standards-harness (MIT)
