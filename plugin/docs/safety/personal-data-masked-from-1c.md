# Правило: ПДн из 1С — только под маской

Решение владельца 29.10.2026 (окно вариантов): к базам с настоящими ПДн пускать, но только под маской — «нужно, чтобы ты тоже ничего не видел и чтобы всё было очень строжайшее». Перечень ПДн — по законодательству Узбекистана и РФ.

**Why:** всё, что вернул инструмент, попадает в контекст модели, журнал сессии и может уйти дальше (в ответ, документ, коммит). Тестовая копия рабочей базы обычно несёт те же настоящие ФИО, телефоны и паспорта, поэтому правило [[secrets-and-production-database]] («боевую базу не регистрировать») от утечки ПДн не защищает.

**How to apply:**
1. **Каналы данных базы** — `1c-toolkit` (`execute_query`, `get_object`, журнал регистрации, скриншоты форм), OData, выгрузки DT/XML с данными — отдают модели только то, что прошло фильтр ПДн. Значение поля ПДн заменяется меткой `[ПДн: <вид>]`: ФИО, телефон, e-mail, адрес, дата рождения, ПИНФЛ, ИНН, СНИЛС, паспорт, номер карты, банковский счёт.
2. **Карта полей ПДн проекта** — из самой конфигурации: `ЗащитаПерсональныхДанныхПереопределяемый.ЗаполнитьСведенияОПерсональныхДанных` (поля доступа по объектам, см. скилл `bsp`, `references/protection-pd.md`), плюс имена полей и шаблоны значений: Узбекистан — ПИНФЛ (14 цифр), паспорт (`AA1234567`), телефоны `+998`; РФ — ИНН, СНИЛС, паспорт, телефоны `+7`; общие — e-mail, номер карты (проверка по Луну), счёт.
3. **Отметка `pd` у каждой базы** в `.v8-project.json`: `none` — данных о людях нет, `masked` — копия обезличена, `raw` — настоящие ПДн. Нет отметки — считать `raw`.
4. **На `raw`:** только через фильтр; `execute_code` запрещён; запрос без `ПЕРВЫЕ N` — отказ; поля ПДн в запросе — только в агрегатах (`КОЛИЧЕСТВО`), `ПРЕДСТАВЛЕНИЕ` объекта-субъекта ПДн — тоже ПДн.
5. **Фильтр не активен** (мод не загрузился, флаг выкатки модулей не пришёл, сбой) — данные базы не запрашивать. Сбой фильтра — отказ, не пропуск.
6. **Без обходов:** не читать данные через Bash/`curl`/WebFetch к `/odata/`, не обращаться к порту тулкита мимо MCP, не читать таблицы базы клиентом СУБД (исключение — `psql` и `sqlcmd` на базе с `pd: none`, если сервер и база в команде совпали с `dbServer` и `dbName` её записи в реестре; решение владельца 30.10.2026), не гонять тесты, сценарии и веб-клиент на базе не `none`/`masked`, не открывать выгрузки DT/XML с данными и снимки форм с данными, не просить владельца прислать данные текстом.
7. **Журнал доступа** — база, инструмент, отпечаток запроса, число строк и замен; самих значений в журнале нет.

**Состояние на 29.10.2026 — первый срез (волна 1):** хук `guard-personal-data` до вызова пропускает инструменты `1c-toolkit`, отдающие данные базы, только к базе с отметкой `pd: none` или `pd: masked` в `.v8-project.json`; нет отметки = `raw` — отказ; без отметки проходят только инструменты без данных (метаданные, справка); какую базу обслуживает тулкит — файл состояния, его пишет `/ones-core:toolkit`; любой сбой — отказ. Маски значений в ответе ещё нет, поэтому на `raw` данные не запрашиваются вовсе (п.5). Второй рубеж (волна 2 п.2.20, 30.10.2026): мод «чистка входящих» тем же решением `guard-personal-data` заменяет заглушкой `[ПДн: …]` весь ответ такого вызова, если он всё же пришёл (хук до вызова не сработал, отметку базы сняли во время вызова); сбой мода — тоже заглушка; в мастере моды не грузятся.

**С 30.10.2026 (замер перед 5.2.0):** файлу состояния барьер больше не верит на слово: чистая база сверяется с командной строкой процесса 1С, который слушает порт (на Windows; порт держит не 1С или процесс не определить — сверяется процесс из записи). Реестр `.v8-project.json` и файл состояния закрыты от записи: `Write`/`Edit` — `guard-skills`, Bash и PowerShell — `guard-destructive` (`sed -i`, перенаправление, `tee`, `cp`/`mv` в файл, запись из `python -c` и heredoc, `Set-Content`, `Out-File`, `WriteAllText`). Прогоны на базе — те же данные: харнессы `run-tests.py` и `run-scenario.py` (код на базе, текст падений идёт к модели) и `web-test` (`start`, `run`, `test`: строки списков и формы идут к модели) отказывают на базе не `none`/`masked`; `--dry-run` базу не открывает. Если база с настоящими ПДн, прогон не идёт, пока владелец не поставит отметку. `guard-destructive` отклоняет обращение к порту тулкита мимо MCP (адрес `/mcp`; штатные `/health` и `/api/close_1c_session` проходят) и чтение таблиц данных клиентом СУБД, в том числе через ssh и ssh-mcp (системные каталоги и `SELECT count(*)` проходят).

**Не покрыто:** OData и выгрузки с данными через Bash (п.6), скрипт в файле и имя файла, собранное из частей (их текста барьер не видит), `pg_dump` и файл запросов `psql -f`, вывод Bash вторым рубежом не проверяется, отчёт `logs/yaxunit` на чистой базе, разбор текста запроса (п.4), журнал доступа (п.7) — следующие срезы. Регресс — `contour-tests` §38, §87, §124, §125 ([[rule-enforcement-map]]).
