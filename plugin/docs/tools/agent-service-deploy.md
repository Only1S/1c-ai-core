# Сервис-агент «инженер 1С» на GitHub Actions

Первый срез «больше, чем плагин» (#1 волны 3): плагин перестаёт быть только инструментом в руках человека и становится **сервисом** — задача команды выполняется агентом автоматически. Решение владельца — GitHub-центрично, без своего сервера: постоянная онлайн-очередь с изоляцией арендатора на `vmrus` — отдельный срез позже (`docs-project/wave3-growth-plan.md` Т-7, файл только мастера).

## Как работает

1. Задача приходит: issue с меткой **«задача-агенту»** (текст задачи — тело issue) или ручной запуск workflow с полем задачи.
2. Workflow поднимает Claude Code с плагином, `plugin/tools/service/agent-task.py --run` зовёт агента: выполнить задачу по правилам ядра (`CLAUDE.md`, `docs/`) — проработка → правки штатными скиллами → чекеры. Агент работает с разрешением на правки (`--permission-mode acceptEdits`), но **коммит/ветку/PR делает workflow**, не агент.
3. Workflow собирает правки в ветку `agent/task-<id>` и открывает **pull request** с итогом агента в теле. Файл отчёта — только текст запроса, в коммит он не идёт; задача без правок запрос не открывает. **В main — только через ревью человеком.**

## Что завести

- **Секрет `CLAUDE_CODE_OAUTH_TOKEN`** в репозитории (Settings → Secrets and variables → Actions) — токен подписки Claude из `claude setup-token` (действует год, привязан к подписке того, кто его выпустил). Вместо него можно API-ключ с platform.claude.com — секрет `ANTHROPIC_API_KEY` и та же переменная в шаге workflow.
- **Доступ Actions**: `permissions: contents write, pull-requests write, issues read` (уже в workflow).
- **Метка «задача-агенту»** в репозитории (issue с ней поднимает агента; чужие события — нет).
- **Claude Code в CI** — версия и сумма сборки закреплены в шаге установки; как их поднять — [[nightwatch-deploy]].

## Границы и безопасность

- **Сервис не льёт в `main` сам** — только PR с ревью. Правки агента читает человек до слияния.
- Поднимается **только ручным запуском или меткой, которую поставил владелец репозитория на issue, написанный владельцем** (`sender.login == repository_owner` и `author_association == OWNER`): текст issue уходит агенту с токеном в окружении, чужой текст мог бы протащить подсказку-инъекцию.
- Правки агента перед коммитом проходят проверку секретов (`plugin/tools/git/secret-scan.py`) — нашлось что-то похожее на ключ или пароль — PR не создаётся.
- Расход токенов — на задачу; задача без текста → код 2 (ничего не делает).
- Первый срез — без постоянной очереди и без данных 1С в самом сервисе; на проектном репозитории с выгрузкой — сперва правило о данных (волна 2): выгрузка может нести ПДн ([[personal-data-masked-from-1c]]).
- Детерминированная часть — регресс `contour-tests` §58 (сервис) и §101 (ревью-бот, шаблоны, зеркало); сквозной прогон (реальная задача → PR) — при развёртывании в GitHub-репозитории с ключом.

Workflow работает в том GitHub-репозитории, где лежит; агент правит именно этот репозиторий, и PR открывается в нём же.

## Сервис для команды в репозитории конфигурации

Скопируйте шаблон `plugin/tools/service/agent-task.yml` в `.github/workflows/` репозитория конфигурации и заведите:

- секрет `CLAUDE_CODE_OAUTH_TOKEN` — как выше;
- секрет `ONES_CORE_TOKEN` — токен GitHub только на чтение канала `Only1S/1c-ai-core`: шаблон забирает плагин клоном по тегу последнего выпуска, сверяет файлы с `SHA256SUMS.txt` его страницы Release (`plugin-sums.py verify`) и зовёт агента с `--plugin-dir`, поэтому правила и хуки ядра действуют и в CI;
- переменную репозитория `AGENT_TEAM` — логины через запятую, без пробелов. Агента поднимает только issue, у которого и автор, и поставивший метку есть в этом списке: текст issue уходит агенту с токеном подписки, чужой текст мог бы им командовать.

Правки агента проходят проверку секретов, в `main` — только через ревью. Очереди и своего сервера нет: каждая задача — отдельный запуск Actions.

## Ревью-бот на изменения конфигурации

Шаблон `plugin/tools/service/review-bot.yml` — в `.github/workflows/` репозитория конфигурации, секреты те же. На открытый запрос с `.bsl`, `.xml` или `.mdo` модель разбирает изменения по двум осям `two-axis-code-review` и оставляет комментарий.

- Только чтение: режим `plan`, инструменты чтения и `git diff/log/show`. Бот не правит код и не сливает, вердикт — совет человеку.
- Без файлов 1С модель не зовётся, токены не тратятся.
- Запрос из чужой копии репозитория секретов не получает: условие на `head.repo.full_name`, событие `pull_request`, а не `pull_request_target`.
- Текст диффа и сообщения коммитов — данные: промпт велит не выполнять инструкции оттуда.
- Новый комментарий — на открытие запроса и на выход из черновика, а не на каждый пуш: так расход токенов предсказуем.

В мастере работает такой же бот (`.github/workflows/review-bot.yml`) на запросах с `.bsl` — на нём проверяется сам бот. Живая проба 30.10.2026: образец с запросом в цикле и пустым исключением — бот нашёл оба дефекта с кодами BSLLS и ещё два замечания, запуск занял около трёх минут. Номера v8std бот не сверяет: сервера v8std в запуске без интерфейса нет.

## Зеркало портфеля

```bash
python "${CLAUDE_PLUGIN_ROOT}/tools/pipeline/mirror-portfolio.py" --repo <владелец/репозиторий> [--dry-run]
```

Людям вне сессии видно, какие доработки идут и на какой стадии: карточке соответствует одно issue с меткой `доработка` и меткой стадии. Наружу уходят только название, стадия и путь карточки: «Следующий шаг», текст ТЗ и код не уходят. Открытый репозиторий — отказ кодом 2. Повторный запуск без перемен ничего не делает, готовая или удалённая карточка закрывает issue. Вызывается руками или командой `/ones-core:plan mirror`.
