# Замер качества кода 1С: эталон 1C Code Bench «с плагином/без»

> Программы замера `tools/bench/*.py` есть только в мастере ядра: в плагин они не входят, и в проекте их нет.

Направление #7 волны 3 (`docs-project/wave3-growth-plan.md` Т-3, файл только мастера): измерить, **помогает ли плагин ones-core писать код 1С**, на внешнем независимом эталоне, а не на своём замере. Эталон нашёлся — **1C Code Bench** (github.com/1cbench/bench, лидерборд 1cbench.github.io): 147 задач, каждая — обработка `.epf` с эталонным решением и валидатором; модель пишет решение, оценщик компилирует и прогоняет его, считает **компиляцию %** и **корректность %**.

## Почему он нам подходит даром

Оценщик `run_bench.py` гоняет каждое решение **через MCP на `http://localhost:6003/mcp`** — это ровно наш `1c-toolkit` (MCP_Toolkit.epf, порт 6003, [[installed-tools-and-servers]]). Их Docker-путь так и называется — «1С + MCP Toolkit». То есть раннер эталона = наш стек; отдельной инфраструктуры оценки заводить не нужно.

Шов «с плагином/без» — **CSV между генерацией и оценкой**:
- их `generate_for_bench.py` пишет колонку `output` **голой моделью** (фиксированный системный+пользовательский промпт, без навыков) — это «без плагина»;
- наш `tools/bench/gen-with-plugin.py` пишет тот же CSV **агентом с плагином ones-core** (`claude -p`, навыки 1С доступны) — это «с плагином»;
- оба CSV подаются в их `run_bench.py` → наш `compare-bench.py` сверяет два отчёта.

Baseline уже есть в самом эталоне: в `data/` лежат выгрузки моделей (`output_trial8_opus46.csv`, `output_trial8_sonnet46.csv` и др.) — это готовое «без плагина» для сверки. Лидерборд на момент разбора (30.10.2026): Gemini 3 Pro 74.2%/51.7%, **Claude Opus 4.6 — 76.9% компиляция / 46.9% корректность**, Sonnet 4.6 — 54.4%/32.0%.

## Инвариант прав: эталон не вшиваем

**У репозитория эталона НЕТ файла лицензии** (`licenseInfo: null`, `/license` → 404 на 30.10.2026) — по умолчанию это «все права авторов». Поэтому ([[use-own-mcp-servers-only]] дух «чужое не ставим как есть»; [[vendor-patches]]):
- **задачи эталона (`.epf`, CSV) в ядро/канал НЕ копируем** — владелец клонирует эталон сам по URL;
- наш слой (`tools/bench/`) ссылается на эталон по адресу и лишь добавляет колонку `output`, сохраняя все исходные колонки CSV — тогда файл байт-совместим с их `run_bench.py` (читает `task_id`, `env`, `output`);
- если решим использовать эталон регулярно — сперва запросить у авторов лицензию/разрешение, зафиксировать в [[vendor-patches]].

## Наш слой (в мастере, config-agnostic)

- **`tools/bench/gen-with-plugin.py <tasks.csv>`** — генерация «с плагином». Берёт их `data/stage_tasks6.csv` (колонки `task_id, env, task, context, ...`), на каждую задачу зовёт `claude -p` с плагином (режим `plan` — правок не вносит, навыки 1С доступны), вырезает код между `` ```1c `` и `` ``` `` (та же логика, что у эталона), пишет `output_<label>.csv`. Идемпотентно (повтор дописывает пустые `output`), `--limit N` — пилот, `--dry-run` — только формат. Без входного CSV или без `claude` — код 2.
  - **Режим генерации — ручка настройки.** На тонких задачах `plan` склонен «планировать» вместо выдачи кода; флаг `--mode plan|acceptEdits|default` и текст промпта владелец настраивает на реальном прогоне. Честный A/B: рамка задачи та же, что у эталона, отличие — только доступ к навыкам плагина.
- **`tools/bench/compare-bench.py <baseline.json> <plugin.json>`** — сверка двух отчётов `run_bench`: таблица дельт (компиляция, корректность: было→стало), поимённое движение задач (какие стали проходить корректность с плагином, какие просели), вердикт. Детерминирован (модель не зовёт), под самотестом `contour-tests` §59. Результат — строка для реестра `docs-project/rules-under-measure.md` (только мастер) и замера `core-measurement`. С `--quality-out <отчёт.json> --commit <коммит>` пишет тот же замер отчётом для гейта выпуска (ниже).

## Свой дешёвый набор: `claude plugin eval` и гейт выпуска (волна 3 п.3.1)

Эталон выше дорог (демо-база, 147×2 генераций), поэтому для каждого выпуска есть свой малый набор в формате `claude plugin eval` (Claude Code 2.1.312, зонд `--help`): **`tools/bench/evals/<кейс>/prompt.md` + `graders/*.md`**, 7 кейсов — запрос остатков с параметрами виртуальной таблицы, сообщение через `НСтр`, транзакция по стандарту, вызов сервера без контекста, `ПРЕДСТАВЛЕНИЕ` в запросе, длительная операция БСП и кейс «не должен срабатывать» (задача на Python). Оценщики — регулярные выражения по последнему ответу (бесплатные); `tool_used: Skill` — только показатель «скилл сработал», в оценку не входит. В плагин набор не входит.

- **`python tools/bench/plugin-eval.py run --out <отчёт.json>`** — собирает плагин из мастера (`build-plugin.py`) во временную папку, кладёт туда набор и гоняет `claude plugin eval <папка> --no-publish --trust-plugin --runs 2` (по умолчанию CLI идёт в двух плечах: с плагином и без; два прогона — с 04.11.2026: при одном прогоне промах шума и сломанный кейс неразличимы — два замера одного содержимого 04.11.2026 дали «без плагина» 100% и 92,9%). Отчёт не публикуется; `--trust-plugin` — только своей сборке. Серверы MCP плагина в прогоне не стартуют (у набора нет заглушек) — меряются правила, скиллы и хуки. `--plugin-dir <папка>` — замер готовой сборки, например прошлого тега. Платно: кейсы × прогоны × 2 плеча агентом Claude под учётной записью владельца; потолок — `--max-cost-usd` (по умолчанию 8). `convert <результат --json>` — тот же перевод без прогона; прогонов на кейс меньше `MIN_RUNS` (минимум по кейсам) — отказ без отчёта, прогоны пишутся в шапку и в каждый кейс.
- **Отчёт** — формат `ones-core-quality/1` (`tools/lib/quality_report.py`): по кейсу доли «с плагином/без» и отпечаток кейса, коммит мастера, флаг незакоммиченного содержимого. Отчёт с прогона, оборванного потолком стоимости, или где плагин не загрузился, не пишется.
- **Гейт в `release-core.py`** — до сборки: `--quality-report <отчёт>` кандидата против последнего годного замера прошлых тегов — `docs-project/quality/core-v*.json` того же источника, не новее прошлого тега, у `plugin-eval` не меньше `MIN_RUNS` прогонов на кейс; тег базы гейт пишет в вывод выпуска (решение владельца 20.11.2026: выпуски 5.6.1–5.6.3 шли с пропуском замера, файла прошлого тега нет). Явная база — `--quality-baseline <файл>`. Сравниваются общие кейсы с одинаковым отпечатком (не меньше 3): средняя доля «с плагином» не ниже прошлой больше чем на один промах в одном прогоне одного кейса — допуск 1/(кейсы × прогоны кандидата), при 7 кейсах и 2 прогонах 7,1 п.п. Отказ — просадка, отчёт снят с другого содержимого плагина (коммит отчёта → HEAD с правками плагина), незакоммиченное содержимое, нет отчёта или годной базы, неизвестный источник замера, замер `plugin-eval` с одним прогоном на кейс у кандидата или базы (`MIN_RUNS` в `quality_report.py`, прогоны — минимум по кейсам). Осознанный пропуск — `--skip-quality-gate` и строка «Пропуск замера качества: <почему>» в записи `RELEASES.md`. После публикации отчёт кандидата сохраняется в `docs-project/quality/<тег>.json` — база следующего выпуска. Регресс — `contour-tests` §80.
- **Набор растёт из провалов** (решение владельца 04.11.2026, [[ai-agent-courses-review]]). Провал качества ответа модели — найденный живой пробой или записанный в `docs-project/observations.md` — в той же вехе становится кейсом `tools/bench/evals/<кейс>/` (`prompt.md` + `graders/*.md`). Провал хука или скрипта ловит самотест `contour-tests`, а не кейс замера.

**Пилот 30.10.2026** (`docs-project/quality/pilot-2026-10-30.json`, сборка мастера `ea0f2f4`, 7 кейсов × 1 прогон × 2 плеча, $2,31, 6 минут): **7 из 7 в обоих плечах, разница «с плагином − без» = 0** — потолок: голая модель решает эти задачи сама. Плагин дороже ($1,79 против $0,51) и медленнее; показатель «скилл вызван» стоит на трёх кейсах (два запроса и БСП) — вызов был во всех трёх. Вывод: набор годится как страж регресса (плагин не мешает), но прирост не различает — для довода «плагин помогает» нужны кейсы труднее (на реальных метаданных, с проверкой стандартов) или эталон выше.

## Как прогнать полный замер (операция владельца)

Тяжёлая операция — нужны ключ модели, демо-база и токены на 147 генераций; поэтому это явный прогон владельца, не автозапуск ([[subagents-on-explicit-consent]], [[token-economy-and-local-tools]]):

1. Клонировать эталон: `git clone https://github.com/1cbench/bench` (скачивание — с ведома владельца).
2. Поднять окружение эталона: `uv sync`; `.env` с `DESIGNER_PATH` (1cv8.exe) и `DATABASE_PATH` (демо-база эталона — выгрузка с их Google Drive, развернуть локально).
3. Поднять `1c-toolkit` на `:6003` против демо-базы (их оценщик стучится на `MCP_URL=http://localhost:6003/mcp`).
4. «С плагином»: `python tools/bench/gen-with-plugin.py <клон>/data/stage_tasks6.csv -o <клон>/data/output_plugin.csv --single-function` (пилот — `--limit 10`; готовые решения за пределом `--limit` в файле остаются, `--dry-run` существующий файл не трогает); «без» — тот же вызов с `--no-plugin`. Ключ `--single-function` кладёт в задание обоих режимов требование формата эталона (одна целевая функция без вспомогательных) — без него сравнение искажает ловушка оценщика ниже.
5. Оценить оба: `uv run run_bench.py data/output_plugin.csv -o report_plugin.json` и baseline `uv run run_bench.py data/output_trial8_opus46.csv -o report_base.json`.
6. Сверить: `python tools/bench/compare-bench.py report_base.json report_plugin.json -o docs-project/core-measurement-<дата>.md` → строка в `docs-project/rules-under-measure.md`.

**Ловушка оценщика — вспомогательные методы.** `run_bench` берёт из ответа только целевую функцию по имени задачи и отбрасывает остальные методы. Ответ, разбитый на целевую функцию и вспомогательные (так велят стандарты и [[coding-discipline]]), падает «Ошибкой инициализации модуля» и засчитывается как «не компилируется». Поэтому сравнивать «с плагином» и «без» надо и в целом, и на задачах, где оба ответа — одна функция; иначе разница — артефакт формата, а не качество кода. Пример — полный замер 30.10.2026 (Opus 5.5, сборка 5.0.1): на всех 147 задачах компиляция 66,0% → 63,9%, корректность 44,9% → 45,6%; все 10 потерь компиляции из-за «ошибки инициализации» — ответы с вспомогательными методами (их у плагина 47 из 147, без него 40); на 98 задачах с ответом из одной функции — компиляция 88,8% → 91,8%, корректность 63,3% → 64,3%. Прежние +6,1 п.п. на выборке из 49 задач были везением выборки. Честная постановка — в задании обоих режимов сказать о формате эталона (ключ `--single-function`). **Перемер 30.10.2026 с этим ключом** (Opus 5.5, та же сборка 5.0.1, 147×2, пустых ответов 0 в обоих режимах): компиляция **81,6% → 87,8%**, корректность **56,5% → 62,6%** (+6,1 п.п. по обоим); стали проходить 14 задач, перестали — 5 (task_002, task_003, task_010, task_115, task_146 — к разбору). Ориентир лидерборда эталона — Opus 4.6: 76,9% / 46,9%. Расход: «без» — 4,1 млн токенов, «с плагином» — 11,6 млн.

**Границы:** задачи с `env=client` их pack-путь не поддерживает (только server-side) — они выпадают из прогона. Демо-база эталона — синтетическая, но правило «тест, не боевая» и ПДн действует ([[personal-data-masked-from-1c]], [[secrets-and-production-database]]); ключ модели — только в окружении/`.env`, в репозиторий не коммитим.

## Связь с самообучением (Т-4)

Замер — топливо цикла самообучения (`docs-project/rules-under-measure.md`, только мастер): правило-суждение из наблюдений, поднявшее корректность на эталоне без регрессий, получает довод «оставить»; просадка — довод «разобрать/откат». До этого эталона замер был только свой (`core-measurement`, полуручной); теперь есть независимая внешняя шкала.
