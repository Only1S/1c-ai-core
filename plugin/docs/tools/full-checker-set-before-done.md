# Правило: проверять всеми чекерами, а не одним

Правило пользователя от 10.07.2026 (бэкпорт с живого экземпляра ядра, обезличено).

**Всегда**, после содержательной правки кода 1С (и перед тем, как отчитаться о готовности), прогонять **весь** набор проверок, а не ограничиваться валидацией EDT:

| Что | Чем | Зачем |
|---|---|---|
| Синтаксис, метаданные, ссылки | `edt-mcp`: `revalidate_objects` → `get_project_errors`; первый прогон — без фильтра по отдельной проверке (сузить допустимо только по серьёзности), частности — после него ([[edt-mcp-pitfalls]]) | компиляция, неразрешённые имена; фильтрованный прогон не заменяет полный |
| Диагностики BSL | линтер `bsl-analyzer` (CLI, `bsl-analyzer.exe` из папки программ плагина) | то, что EDT не ловит: сложность, дубли, мёртвый код |
| Стандарты разработки 1С | скилл `1c-standards` (локально) + MCP `v8std` (`explain_snippet` — разбор процедуры, `search` и `explain_diagnostics` — по номеру и теме) | оформление, именование, структура, ACC/BSLLS-коды |
| Соответствие БСП | скилл `bsp` | штатные методы БСП вместо самописных |
| Запросы | `edt-mcp`: `validate_query` | поля/типы/UNION до вклейки в модуль |
| Формы | скриншот `edt-mcp` + `1c-forms` | видеть результат, не верить XML |
| Автотесты | YAXUnit — [[task-recipes]] §12 (тестовое расширение; headless `1cv8c /C"RunUnitTests=…"` — **пилот пройден 11.07.2026**, jUnit + exitcode 0/1) | регрессия поведения; красные тесты = правка не готова |
| Покрытие (ретроспективно) | детектор непокрытых швов — [[task-recipes]] §17 (`code-index` − вызовы из тест-расширения) | карта «где теста нет» на легаси/заимствованных модулях (только структура; эталоны — ручные) |
| Приём платформой | загрузка в **тестовую** базу: EDT `update_database` → состояние «обновлено» ([[edt-mcp-pitfalls]]); без EDT — `db-load-xml` + `/CheckConfig` ([[designer-batch-runs]]) | «0 ошибок EDT» необходимо, но не достаточно: в одном из экземпляров платформа отвергла то, что приняла модель EDT (тип в определяемом типе, новый вид модуля) |
| Рантайм (тестовая база) | `1c-toolkit` ([[installed-tools-and-servers]]): права на новые/изменённые объекты у **рабочих** ролей, журнал регистрации за период после выкладки, дымовой вызов экспортного API через `execute_code` — только на тесте | статика не видит прав и поведения живой базы: в одном из экземпляров новая обработка при чистом EDT была доступна только полной роли |
| Функционально | чек-лист прогона на реальных данных — [[task-recipes]] §10; кодовые кейсы — сам, в транзакции с откатом (раздел ниже) | статически чистый код ещё не работает |

**Why:** EDT-валидация показывает только `ERRORS`/`BLOCKER` и часть диагностик. «0 ошибок в EDT» ≠ «код соответствует стандартам 1С»: стилевые и архитектурные нарушения EDT либо не проверяет, либо прячет в `MINOR`.

**How to apply:**
1. Прогнать чекеры **по всему затронутому объекту**, а не только по своим строкам.
2. Замечания разделить: **внесённые мной / пред-существующие**. Свои — исправить; чужие — показать списком и спросить, чинить ли.
3. В отчёте назвать **каждый** использованный инструмент и его результат. Не писать «проверено», если инструмент не запускался.
4. Не подменять запуск чекера рассуждением о том, что он «наверняка бы сказал».
5. ⚠️ Ловушка `bsl-analyzer` на одиночном файле/без загрузки конфигурации. Из блокировки PostToolUse-хука `validate-bsl.py` исключены **5 семейств** (канонический список — `FALSE_FAMILIES` в `plugin/hooks/validate-bsl.py`; его состав ассертится в `contour-tests`, чтобы ослабление контура не прошло молча): `QueryToMissingMetadata`, `UnresolvedMethodCall`, `MissingCommonModule`, `UnresolvedField` — ложные, потому что анализатор **не резолвит метаданные**; `InvalidCharacterInFile` — типографика («—», «…») в русских комментариях легитимна, а реальный мусор в коде всё равно даёт блокируемый `ParseError`. Эти семейства не считать находками и при ручных прогонах.

   **Корень, а не догадка** (замер в живом экземпляре 27.07 и 05.08.2026): `bsl-analyzer` **не понимает выгрузку EDT** (`.mdo`) — в логе запуска `METADATA LOAD: … common_modules=0 metadata_objects=0`, то есть BSL разбирается вообще без модели конфигурации. Отсюда систематическая ложь всех метаданно-зависимых правил. Контрольный замер по `UnresolvedField`: в одном менеджерском модуле 26 находок, среди них **две на типовое `Enums.BarcodeTypes`**; не резолвится ни одно перечисление и ни один справочник — ни свои, ни типовые, при том что EDT по тем же объектам даёт 0 замечаний. До исключения этого семейства любая правка модуля с обращением `Enums.X`/`Catalogs.X` давала `exit 2` и блокировала работу.

   **Ослабление контура — только с доказательством, что он не ослаб.** После расширения списка обязателен контрольный прогон: файл со сломанным синтаксисом по-прежнему обязан блокироваться по `ParseError` (в `contour-tests` этот кейс постоянный). Известно ещё одно ложное семейство — `UnusedLocalVariable` (без модели анализатор принимает присваивание **реквизиту объекта** за неиспользуемую переменную), но оно **намеренно НЕ исключено**: то же правило ловит и настоящие неиспользуемые переменные, а цена пропуска ниже цены слепоты.

   5а. **Совет линтера применять после проверки семантики** (дополнение 19.09.2026; наблюдалось на `bsl-analyzer` 0.2.58 — наблюдение экземпляра — в одном из экземпляров):
   - `MissingCodeTryCatchEx` (`std499`) указывает на строку `Попытка`, а не на блок `Исключение`: прежде чем чинить, открыть блок и убедиться, что он пуст — в одном модуле все 13 срабатываний оказались ложными. Семейство при этом не ложное (в прошлом проекте давало настоящие находки — [[installed-tools-and-servers]]), в исключения хука его не добавлять.
   - Замена `ОБЪЕДИНИТЬ` на `ОБЪЕДИНИТЬ ВСЕ` — только после проверки, что одна и та же строка не может прийти из обеих выборок (условие правила 7 скилла `query-optimize`). Намеренную дедупликацию оставить с предупреждающим комментарием: совет линтера тут вносит баг — двойную запись.
   - EDT-маркер «запрос в цикле» не различает мощность цикла: цикл по трём сегментам и по тысячам позиций выглядят одинаково — оценивать число итераций.
   - «Неиспользуемая переменная» — повод разобрать происхождение, а не механически удалить ([[two-axis-code-review]], ось 1 п.5).
6. Финальный контур — **функциональный прогон** ([[task-recipes]] §10): статическая чистота не заменяет проверку на данных.
7. **Каденция — не всё и не всегда одинаково.** **Быстрый контур — на каждом шаге внутри среза** ([[vertical-task-slicing]]): PostToolUse-хук `bsl-analyzer` (срабатывает сам), `edt-mcp revalidate_objects` по затронутому объекту, **целевой** YAXUnit-тест текущего шага. **Полный сет из таблицы выше + функциональный прогон — на закрытии тикета/среза и ОБЯЗАТЕЛЬНО перед отчётом о готовности**: «готово» без полного сета — не факт, а мнение. Прогон полного сета в середине среза — не запрещён, но и не обязателен (он дорог; экономия здесь легитимна — [[token-economy-and-local-tools]]).
   - **Повторный прогон на неизменённом содержимом запрещён** (19.09.2026; идея comol/ai_rules_1c, лицензии нет — пересказ): чекер, уже давший результат по этому состоянию файла, второй раз не гоняется — повтор ничего не доказывает и сжигает время. Нет чистого подтверждающего прогона на последнем состоянии — пункт идёт в категорию **«не проверено»** (п.9), а не «проверено».
   - **Режим массового переноса — только явный опт-ин владельца** (19.09.2026, по находке экземпляра): при переносе пачки однотипных правок чекеры и загрузка в ИБ идут раз на пачку, а не на каждую правку; до и после пачки — гейт дельты (что изменилось по `git diff`); решения по умолчанию со списком постфактум — только для неархитектурных мелочей. Проверки на ложный зелёный, секреты, деструктив и правки поставщика — всегда через вопрос. Без явного «включаем массовый режим» действует обычная каденция.

**Принуждение (с 17.10.2026, решение владельца): блокирующий гейт конца хода** (`stop-guard`, `{"decision": "block"}`) — ход или задание помощника с правкой кода или метаданных 1С (Edit/Write модуля или файла 1С вне служебных зон, запись модуля через EDT, скрипт скилла-генератора) не завершается, пока в нём же нет: проверки по стандартам (v8std или скилл `1c-standards`), `validate_module` bsl-context с `path` каждого изменённого модуля после его последней правки (модуль вне корня выгрузки сервера — текстом, см. ниже), парного `*-validate` после генератора и перечня инструментов в ответе. Два отказа подряд в одном ходе — пропуск с видимой пометкой и записью в `logs/answer-check.jsonl`. Переключатель `stopGate` в `.v8-project.json` (`block` по умолчанию, `warn`, `off`), понижение модели запрещено. Регресс — `contour-tests` §8c. Остальные чекеры таблицы (EDT, 1c-standards по форме, БСП, скриншот формы) гейт не требует — их держат прежние механизмы и дисциплина.

**Поправки вехи 40 (17.10.2026, живая проба в проекте):** `validate_module` гейт засчитывает только по ответу сервера с полем `valid` (состоявшаяся проверка, а не отказ); в проекте с плагином вызывать с `path=` и `repo="default"` — bsl-context теперь запущен с источником имён на исходники проекта. Граница хода — настоящий запрос владельца: отказ гейта и системные напоминания её не сдвигают. `validate-bsl` блокирует только ошибки анализатора в строках правки, прежние ошибки модуля — подсказка.

**Модуль вне корня выгрузки (30.10.2026, замер: 12 пропусков гейта в рабочем проекте за 20–28.10).** Сервер читает файлы только под своим корнем (`ONEC_PROJECT_SRC`), а проект живёт в нескольких деревьях: второй конфигурации, расширения, форка. Для такого модуля `path=` невыполним, поэтому гейт засчитывает `validate_module` с `source=` (текст модуля) и `module_path=` с ответом `valid`, если вызов сделан после правки. Модуль считается вне корня, когда сервер ответил «путь выходит за корень выгрузки» или абсолютный путь лежит не под `ONEC_PROJECT_SRC`. Вызов без `module_path` к модулю не привязан и закрывает модуль, только если такой остался один. Внутри корня текст по-прежнему не засчитывается. У модуля вне корня путь с тем же хвостом не засчитывается: сервер проверил бы двойника из основного дерева. Регресс — `contour-tests` §132.

Связано: [[work-through-tools]] (п.5 «артефакт → валидатор» — этот док задаёт полный сет), [[vertical-task-slicing]] (каденция внутри среза), [[bug-diagnosis-loop]] (красный чекер → диагностика, а не подгонка), [[two-axis-code-review]], [[work-through-tools]], [[forms-skills-and-visual-check]].

8. **Глубину задаёт КЛАСС ПРАВКИ, а не привычка.** П.7 отвечает «когда», этот пункт — «сколько». Класс берётся из [[task-recipes]] §19 (тот же дифф, тот же классификатор — второй заводить нельзя):
   - 🟢 **низкий** (комментарии, `НСтр`, форматирование, доки) — гигиена файла: кодировка/BOM, языковой профиль. Полный сет тут — ритуал, а не проверка.
   - 🟡 **средний** (логика внутри метода, форма, макет, неэкспортное) — быстрый контур п.7.
   - 🔴 **высокий** (экспортный API с ненулевым числом вызывающих, транзакции и блокировки, новый общий модуль, роли и права, структура объекта с данными в базе) — **полный сет + функциональный прогон** ([[task-recipes]] §10), без исключений. Если в диффе новый объект, роли или права — строка «Рантайм» таблицы обязательна; тестовой базы нет — это категория «НЕ проверено» п.9, а не пропуск.

   ⚠️ Класс **вычисляется по диффу**, а не назначается по ощущению «правка мелкая». Сомнение трактуется в сторону БОЛЬШЕЙ глубины: цена лишнего прогона несопоставима с ценой пропущенной регрессии в проведении.

   **Класс печатает ИНСТРУМЕНТ, а не я по этой таблице** (15.10.2026, волна H — [[external-skills-review]]; приём трёх осей и фиксации `driver` из `Romandredan/1c-quality-gate`, MIT, таблицы составлены заново под наш стек):

   ```bash
   python tools\setup\change-profile.py --json
   ```

   В проекте с плагином тот же скрипт лежит в плагине и смотрит git проекта: `python "${CLAUDE_PLUGIN_ROOT}/tools/setup/change-profile.py" --json`.

   Три оси вместо одной: **объём** (`C0` косметика → `C3` структурная), **архетипы кода** как набор меток с индивидуальным минимумом на каждый контур (запрос, транзакция, движения регистра, обработчик объекта, интеграция и HTTP, права и RLS, CFE-перехват, фон и регламент, клиент-сервер, модуль формы, асинхронный клиент, новый общий модуль) и **сложность** — она закрывает случай «строк мало, но код тяжёлый» (вложенность от 4, метод свыше 120 строк, 7 и более параметров, рекурсия). Итог: `глубина = max(объём, максимум минимумов сработавших архетипов, сложность)`, и отдельно печатается **`driver`** — что именно подняло глубину.

   Асимметрия минимумов сознательная и в одномерный «множитель риска» не сворачивается: **транзакция** требует глубокого разбора КОДА и архитектуру не поднимает, **новый общий модуль** наоборот оставляет код на низком уровне, но поднимает АРХИТЕКТУРУ до верхнего. Регресс каждой оси — `contour-tests` §17 на фикстурах суите полноты; словарь класса (`низкий`/`средний`/`высокий`) ассертится там же, чтобы инструмент и эта таблица не разошлись.

   Расхождение моей оценки с выводом инструмента решается в пользу инструмента ([[work-through-tools]] п.2: факт — вызовом, не по памяти).

8а. **Исключение класса C0 — правка только комментариев и пустых строк** (решение владельца 10.11.2026 по разбору [[quality-gate-review]]). Модуль, который в сравнении с `HEAD` изменился только комментариями и пустыми строками, полного сета не требует: хватает автоматических проверок хука `validate-bsl` — анализатора, гигиены файла, бюджета комментариев. Гейт конца хода (`stop-guard`) не требует для такого модуля проверки по стандартам и `validate_module`. Решает тот же классификатор, что и п.8: `change-profile.cosmetic` — каждая добавленная и каждая снятая строка диффа к `HEAD` — комментарий или пустая. **Не C0:** закомментированный или удалённый код (снятая строка кода), правка отступов и строк `#Область`, новый модуль, которого нет в `HEAD`, модуль вне git. Любая другая правка — полный сет по п.7–8, без исключений. Регресс — `contour-tests` §189.

9. **Отчёт о проверке содержит ТРИ категории, а не одну.** «Проверено» без границ читается как гарантия, которой нет — та же дисциплина, что в [[rule-enforcement-map]] (колонка «что не покрыто»), только на уровне прогона:
   - **проверено** — инструмент запущен, вердикт получен (назвать инструмент и результат, п.3);
   - **пропущено** — проверка неприменима к этой правке (назвать причину: «XML не затронут», «ролей в диффе нет»);
   - **НЕ проверено** — проверка применима, но выполнить её не удалось: нет платформы, не поднята тестовая база, нет индекса, сервер не ответил. **Эта категория обязательна и не может быть молча пустой.** Неотличимость «не применимо» от «не смог» — самый дешёвый способ выдать дыру за чистоту.

   **У отчёта появился файловый носитель** (15.10.2026, волна H): `tools/checks/gate-evidence.py --checked … --skipped … --not-verified …` дописывает те же три категории в `logs/gate-evidence.md` и снимает взвод гейта качества, который поставила правка `.bsl` ([[enforcement-hooks]]). До этого отчёт жил только в тексте ответа — после сессии от него не оставалось ничего, и «прогнал ли я полный сет по этой правке» нельзя было ни проверить, ни опровергнуть. Скрипт **отказывается** писать след без `--checked` и без `--not-verified`: след без содержания — подлог, а не формальность.

9а. **Ошибки и предупреждения исправляются, а не пропускаются** (распоряжение владельца 05.11.2026: «Ошибки и предупреждение нужно обязательно исправлять, их нельзя пропускать»). Каждая ошибка и каждое предупреждение любой проверки — анализатора, EDT, самотестов `contour-tests`, `health-check`, валидаторов скиллов — исправляется. Отметка «прежнее», «не моё», «состояние машины» вместо исправления — пропуск.
   - **Строки правки** — сразу: `validate-bsl` блокирует и `error`, и `warning` анализатора (`note` — нет; ложные семейства из одиночного файла — нет). Регресс — `contour-tests` §182.
   - **Прежние замечания в своём коде правленного модуля** — отдельным шагом этой же задачи, не «отдельной задачей потом» ([[coding-discipline]] п.3, исключение).
   - **Объект поставщика на поддержке** — список владельцу: правку запрещает барьер `support-guard`.
   - **Предупреждение о состоянии машины** (сервер не поднят, задача планировщика, устаревший отчёт) — устранить причину или назвать владельцу, что сделать и где. Перевести проверку в INFO, чтобы она замолчала, — подгонка проверки ([[bug-diagnosis-loop]] Ф5). Исключение — ложное предупреждение, и то с «да» владельца: сервер по требованию (`edt-mcp` живёт вместе с EDT, `1c-toolkit` — на открытой тестовой базе) без своего приложения не нужен, поэтому `health-check` пишет о нём INFO с подсказкой, как поднять (решение владельца 05.11.2026). Постоянный сервер (`1c-forms`) не поднят — WARN, поднять лаунчером `tools\run-formsserver.cmd`.
   - **Подавить замечание директивой** — только после «да» владельца ([[bug-diagnosis-loop]] Ф5).

10. **Живость источника подтверждается ДО ссылки на него (sentinel).** Прежде чем написать «соответствует std436» или «bsl-analyzer чисто», убедись, что источник действительно ответил: MCP `v8std` вернул страницу стандарта (`v8std_get_page` по известному номеру отдаёт `found=true`), `bsl-analyzer` вернул SARIF (а не пустой результат из-за пути), `code-index` отдал непустой индекс. Молчащий источник даёт **тот же вывод, что и чистый код**, и это ровно тот класс дефектов, который ядро ловило уже пять раз ([[claude-code-hook-fields]], [[rule-enforcement-map]]). Не подтвердил живость — пиши в категорию «не проверено» из п.9, а не в «проверено».

11. **Три слоя завершения: «зелёный unit» — это первый слой, а не последний.** (14.10.2026; концепт лекции 9 `walkinglabs/learn-harness-engineering`, MIT — пересказ своими словами с проекцией на 1С, разбор в [[external-skills-review]], волна F.) П.7 отвечает «когда», п.8 — «сколько», этот — «до какого рубежа»:
    - **Слой 1 — статика:** хук `validate-bsl` / `bsl-analyzer`, EDT `revalidate_objects` → `get_project_errors`, парный `*-validate` каждого порождённого артефакта.
    - **Слой 2 — приём платформой и целевые тесты:** загрузка в тестовую базу (`update_database` или `db-load-xml` + `/CheckConfig`) — конфигурация **реально обновилась**, плюс YAXUnit по затронутым швам.
    - **Слой 3 — сквозной сценарий:** от команды в интерфейсе до движения в регистре и строки журнала регистрации, **включая путь отказа** (та же схема, что в [[readiness-matrix-and-process-diagram]]).

    Статус «готов» ставится только после слоя 3; слои 1–2 дают «на проверке» ([[vertical-task-slicing]]). Три класса дефектов, которые ниже слоя 3 **принципиально** не ловятся: **рассогласование интерфейсов** (каждая сторона зелена на своих заглушках, а договор между ними никто не проверял), **несогласованность состояния между слоями** (структуру обновили, а предопределённые значения, настройки или кеш остались от прежней версии), **зависимость от окружения** (прав рабочей роли нет, параметр сеанса не установлен, внешний сервис недоступен). Первые два в 1С особенно дёшево пропустить: и EDT, и YAXUnit на моках зелены.

    ⚠️ **Рефакторинг до зелёного слоя 3 запрещён.** Он сдвигает границу между проверенным и непроверенным кодом: то, что работало неявно, перестаёт, и у диагностики пропадает точка опоры ([[bug-diagnosis-loop]] — петля первее гипотез; [[coding-discipline]] — хирургический дифф). Порядок строгий: **корректность → производительность → стиль**. «Заодно причешу» на незелёной правке — не аккуратность, а потеря связи между симптомом и причиной.

Пункты 8–10 — проекция концептов `Romandredan/1c-quality-gate` (адаптивная глубина по классу правки, машиночитаемый след с `not_verified`, sentinel живости источника правил; разбор 19.08.2026 — [[external-mcp-servers-review]]). Взяты **своими словами**: у проекта нет лицензии, поэтому ни текст, ни код не заимствуются.

## Обращения к реквизитам сверять с метаданными — «0 ошибок EDT» их не ловит

EDT-валидация **не проверяет**, существует ли реквизит, к которому обращается код: `Объект.НетТакогоРеквизита` даёт зелёный проект и падает уже в 1С:Предприятии (`ScriptRuntimeError «Поле объекта не обнаружено»`). После правки формы, модуля или запроса сверять:

- каждое `Объект.<реквизит>` и dot-путь — с фактическим составом реквизитов (`meta-info`, `edt-mcp`);
- каждый текст запроса — через `validate_query` (он резолвит поля и таблицы против метаданных);
- каждое `Перечисления.<Имя>.<Значение>` (`Enums.X.Y`) — с фактическим составом значений перечисления (`meta-info`, `edt-mcp`). `DESIGNER /CheckConfig` этот класс **не ловит**: в одном из экземпляров обращение к несуществующему значению не дало в журнале проверки ни строки и упало только в рантайме («Поле объекта не обнаружено»). В профиле без EDT, где `/CheckConfig` — единственный синтаксический контроль, сверка обязательна: grep всех обращений `Перечисления.X.Y` → сравнение со списком значений в XML/`.mdo`.

⚠️ **Запрос, СКЛЕЕННЫЙ из кусков в разных модулях, не проверяет никто.** Кейс живого экземпляра (31.07.2026): форма подавала свои поля выборки в базовый запрос параметром и ссылалась на алиас соединения, которое из базового запроса убрали, — падение при открытии. Валидатор видит только собранный текст, а он собирается в рантайме. Такие места проверять прогоном на **тестовой** базе, а не глазами.

## Слепые зоны: что зелёный чекер не доказывает (дополнение 19.09.2026)

**Дополнение 16.10.2026 (бекпорт из экземпляров, три слепые зоны, каждая стоила живого дефекта):**
- **`bsl-analyzer` и формат EDT.** Линтер разбирает исходники выгрузки Конфигуратора; на дереве EDT (`*.mdo`, модули внутри `src/`) он находит меньше, а аннотации расширений (`&Вместо`, `&После`, `&ИзменениеИКонтроль`) трактует как неизвестные директивы — отсюда и ЛОЖНЫЕ находки, и пропуски. Поэтому на профиле EDT зелёный линтер не закрывает ось «Стандарты»: нужна валидация EDT (`revalidate_objects` → `get_project_errors`) как первая линза, а линтер — как вторая.
- **Директива перехватчика расширения.** Несовпадение директивы компиляции перехватчика с директивой заимствованного метода линтер не видит вовсе — ловит только валидация EDT. Чем закрывать: `revalidate_objects` по расширению перед сдачей.
- **Расчётный артефакт (отчёт, обработка, пересчёт).** «Запрос выполняется и числа появились» не доказывает, что числа ВЕРНЫЕ. Приёмка расчётного артефакта — **второй независимый счёт от первички** (другой алгоритм, не копия того же запроса) плюс **сверка за N прошлых дат**, где ответ уже известен из факта. Без этих двух частей статус «готов» по расчётному артефакту не ставится ([[readiness-matrix-and-process-diagram]]: клетка «чего не хватает» остаётся непустой).

Классы, которые в экземплярах прошли через зелёные EDT, `bsl-analyzer` и `*-validate` и всплыли позже. Строка здесь — не повод отказаться от чекера, а указание, чем добрать:

| Что не ловится | Чем закрывать |
|---|---|
| Имя, запрещённое платформой, у реквизита (`ForbiddenMetadataName`, `std474`): `meta-validate` сверяет имена только со стандартными реквизитами своего типа (проверка 7b) | после `meta-compile`/`meta-edit` — ещё и `bsl-analyzer analyze -s <корень выгрузки>`: в одном из экземпляров реквизит «Документ» у обработки поймал только он |
| Допустимость имени типа: зелёный `*-validate` проверяет структуру, а не то, что `<v8:Type>` существует; генераторы-близнецы (`meta-compile`/`meta-edit`) могут расходиться | сериализацию нового или редкого типа сверять с вендорным образцом в той же конфигурации (grep того же типа в выгрузке или `meta-info` объекта, где он уже есть) |
| Полнота переименования идентификатора: свой grep по придуманным образцам пропускает вхождения, `bsl-analyzer` неопределённую переменную может не увидеть | гейт компиляции: EDT `revalidate_objects` → `get_project_errors`, без EDT — `/CheckConfig` ([[designer-batch-runs]]); в одном из экземпляров пятое вхождение поймал только `/CheckConfig` |
| Баланс `#Область`/`#КонецОбласти`: `bsl-analyzer` 0.2.79 (версия ядра на 19.09.2026) незакрытую область не замечает (зонд 19.09.2026) | детерминированная сверка счётчиков открытий и закрытий по модулю |
| Имя обработчика в `ОписаниеОповещения` — строка, резолвится только в рантайме; процедура обязана быть экспортной (`ИмяПроцедуры` по справке `bsl-platform`) | сверить, что процедура есть в модуле-адресате и помечена `Экспорт` |
| Переменная с именем встроенной функции (`Строка`, `Дата`, `Тип`, `Формат`) затеняет её | ревью имён локальных переменных |
| Реквизит формы, создаваемый в рантайме (`ИзменитьРеквизиты`), к которому обращается код | объявить реквизит статически в форме |
| Запрос, собранный `СтрШаблон` или конкатенацией: `validate_query` видит только литерал | `validate_query` по фактическому собранному тексту (вывести его на тестовой базе) |
| Свойства и методы платформенных типов у значения без статического типа | `bsl-platform` (`getMembers` по типу) |
| Фасеты XDTO (`FractionDigits`, `MaxLength`) | только рантайм: сериализация на тестовой базе |

Когда поведение непонятно, сначала повторить то же на вендорном объекте, который заведомо работает, — метод контрольного опыта ([[bug-diagnosis-loop]], Ф3).

## Проверка самой правки: чекеры смотрят содержимое, а не факт правки (дополнение 19.09.2026)

1. **Правка может не доехать до диска.** Отчёт скрипта «записано N байт» — не доказательство. После записи перечитать файл с диска и найти в нём правку; после коммита — `git show HEAD:<путь>`. В одном из экземпляров в коммит ушла прежняя версия файла; причина не установлена (гипотеза экземпляра — параллельный `/CheckConfig` по тому же каталогу).
2. **Замена блока «от маркера А до маркера Б» молча съедает методы**, оказавшиеся между маркерами: баланс `Процедура`/`КонецПроцедуры`, `bsl-analyzer` и `/CheckConfig` молчат, а число строк может даже вырасти. После такой замены — дифф инвентаря методов до и после (grep по `^(Асинх )?(Процедура|Функция) <имя>`). Список методов не выдавать эталоном для сверки, пока инвентарь не сверен.
3. **Результат генератора мерить диффом против git, а не глазами.** В корневом `Configuration.xml` должны быть только строки регистрации нового объекта. Число одиночных LF в изменённых файлах сравнивать с `HEAD`, а не считать абсолютно: в вендорской выгрузке одиночный LF бывает законным (перенос внутри значения синонима), и глобальная нормализация переводов строк портит вендорские данные ([[config-git-forks-and-merges]]: `.gitattributes` с `* -text`, страховка `autocrlf=false`). Возможный шум: `meta-edit` и `form-add` приводят `encoding="utf-8"` в заголовке XML к `UTF-8` — строка в диффе появится, если исходный файл был в нижнем регистре.
4. **Ручной разбор выгрузки регулярным выражением врёт молча**: пустой результат неотличим от честного «нет». Структуру брать `*-info` ([[use-skills-not-manual-edits]]), а отрицательный вывод («такого нет») подтверждать вторым независимым способом — grep обращений `<Менеджер>.<Объект>.<Имя>` по конфигурации. Предопределённые элементы лежат в отдельном `<Объект>/Ext/Predefined.xml` (спецификация `cc-1c-skills`), а не в файле объекта, и `meta-info` их не показывает — смотреть сам файл.
5. **Проверка обязана отличать «сравнили и совпало» от «сравнивать было нечего».** Сравнение двух величин, которые обе не извлеклись, даёт зелёный на пустоте: `$null -eq $null` — истина. Поймано 15.10.2026 на своём же регрессе — счётчик выдирался регуляркой по русской формулировке из вывода, прочитанного в OEM, не совпадал никогда, и проверка паритета месяцами печаталась зелёной, не сравнив ни одного числа (о причине — [[designer-batch-runs]] п.10). Поэтому: сперва ассерт, что вход **извлечён** (совпадение найдено, файл непуст, инструмент ответил), и только потом сравнение; в тексте вердикта печатать само значение — пустое место в «(по X: переносимых)» было видимым признаком ещё до разбора. Это та же дисциплина, что п.10 основного списка (живость источника) и п.4 выше (пустой результат неотличим от честного «нет»), но на уровне **самой проверки**: зелёный, который не может покраснеть, — не проверка.

## Функциональный прогон кодом: транзакция с откатом (дополнение 19.09.2026)

Кейсы матрицы, проверяемые кодом, можно гонять самому через `1c-toolkit` `execute_code` — **только на тестовой базе** ([[secrets-and-production-database]]); кейсы интерфейса (формы, печать, предпросмотр) по-прежнему исполняет пользователь ([[task-recipes]] §10). Порядок:

1. До прогона снять контрольные показатели: счётчики документов и записей регистров, ключевые реквизиты.
2. Всё пишущее — внутри `НачатьТранзакцию` … `ОтменитьТранзакцию`. В блоке `Исключение` первой строкой `ОтменитьТранзакцию`; до неё к базе не обращаться (`std783` п.1.3, шаг 4, и п.1.4.4).
3. После прогона снять те же показатели и сверить, что в базе ничего не осталось.

Транзакция не откатывает внешние эффекты — файлы, HTTP и веб-сервисы, почту, фоновые и регламентные задания, запись в журнал регистрации. Такие кейсы в транзакционный прогон не брать. `guard-destructive` этот вызов не видит, а `guard-personal-data` пускает его только к базе с отметкой `pd` `none` или `masked` ([[enforcement-hooks]]): код вызова и то, что база тестовая, хук не проверяет, поэтому осторожность здесь держится на правиле.
