# Playbooks: задача → инструменты по шагам

Делает [[work-through-tools]] операционным: не «задействуй весь стек», а конкретная цепочка. Для каждого шага — самый специализированный инструмент; экономия токенов — тай-брейк ([[token-economy-and-local-tools]]).

## 0. Карта представлений и мостов (маршрут любой задачи)

Конфигурация живёт в 5 представлениях; инструмент выбирается ПОСЛЕ маршрута «где вход → где выход → какие мосты».

| Представление | Инструменты | Мост к соседнему |
|---|---|---|
| **Живая ИБ** | `1c-toolkit`, скиллы `db-*`, ТЖ (`OneSTools.PS.TechLog`) | ↔ Designer-XML: `DumpConfigToFiles`/`LoadConfigFromFiles` (скиллы `db-dump-xml`/`db-load-xml`) |
| **EDT (`.mdo`)** | `edt-mcp` (код, метаданные, формы; запуск YAXUnit — `run_yaxunit_tests` в 2.17.1, живьём не проверен — §12; основной путь — headless `1cv8c`) | ↔ Designer-XML: экспорт/импорт EDT (GUI; headless `1cedtcli` в этой среде не работает) |
| **Designer-XML** | `code-index`, `bsl-analyzer`, `1c-forms`, скиллы `meta-*`/`cf-*`/`form-*`/`role-*`/`skd-*`/`epf-*` | ↔ YAML: `nkdk import_from_xml`/`sync_to_xml` |
| **YAML (для AI)** | `nkdk` (`get_schema`, `validate_project`, `rename_item`, `delete_item`) | — |
| **СУБД (PostgreSQL)** | **мостов из ядра пока нет** (на 14.10.2026): ни одного MCP, `psql`/`docker` в среде отсутствуют. Единственный путь — §21 | ↔ Живая ИБ: словарь `ПолучитьСтруктуруХраненияБазыДанных` + `DBMSSQL` из ТЖ (§21) |

Поверх всех представлений — слой знаний/валидации (`v8std`, `bsl-platform`, `bsl-context`, `1c-standards`, `bsp`) и `headroom` (сжатие больших выводов).
⚠️ **Один конфиг — один канал правки за раз** (EDT ↔ XML ↔ YAML ↔ база не автосинхронизируются); синхронизация только мостами.

**Шаг → цена (токены).** Конвейер [[work-through-tools]] с ценником; дефолтная полоса (0–5) — ~10–30k на содержательную задачу:

| Шаг | Что происходит | Цена |
|---|---|---|
| 0. Маршрут | представление входа/выхода + мосты — решение, вызовов нет | ≈0 |
| 1. Параллельный веер | 3–6 одновременных вызовов (`code-index` ∥ `edt-mcp` ∥ `v8std`/`bsl-platform`) | ●●○ ~5–15k |
| 2. Конвейер + валидатор шага | код→`bsl-context`+`bsl-analyzer`, форма→`validate_form`+скриншот, YAML→`validate_project` | ●○○ точечно, до ~2k/шаг |
| 3. Сверка дублёрами | только критичные факты; +1 вызов на факт | ●●○ |
| 4. Зонд при сбое | `--help`/хендшейк/мини-прогон — дешевле повторной итерации после ошибки | ●○○ |
| 5. Фиксация | связка → playbooks, грабли → тул-док, правки → [[changelog]] | ●○○ окупается переиспользованием |
| Эскалация | многоагентный Workflow (веер линз + состязательная проверка) — **по нужде в широте / по согласию** ([[subagents-on-explicit-consent]]); перед ним всегда бесплатный `health-check.py` (§6) | ●●● сотни k (пример: аудит ядра 10 агентов ≈ 907k) |

Экономия — **сжатием и точечностью** (headroom −60–95%, `Read offset/limit`+Grep, готовые рецепты отсюда), не отказом от инструментов; равнозначные инструменты — тай-брейк по токенам ([[token-economy-and-local-tools]]).

## 1. Ревью присланного модуля 1С
1. `code-index` — где модуль используется: `get_callers`, `get_call_tree`, impact map.
2. `edt-mcp` — `read_module_source` / `get_module_structure`; ошибки — `get_project_errors`.
3. `v8std` + скилл `1c-standards` — стандарт под каждую находку (не «я так решил»).
4. `bsl-context` `validate_module` — проверить **каждый предложенный фрагмент** против API платформы (ловит галлюцинации до вставки).
5. `bsl-analyzer.exe analyze` (CLI) — машинные диагностики, кросс-сверка с ручными находками.
6. Правку применять `edt-mcp write_module_source`; зафиксировать в [[changelog]] и [[worklog]] ([[work-journals-and-commits]]).

Чек-лист — [[two-axis-code-review]].

## 2. Создание/правка управляемой формы (гибрид)
1. `edt-mcp` `get_metadata_details` — реквизиты, ТЧ, допустимые `DataPath`.
2. Спецификацию формы собрать самому из метаданных.
3. `1c-forms` — `generate_form` → `validate_form`; конвертация форматов — `convert_form`.
4. `edt-mcp` `get_form_screenshot` — **увидеть результат**.
5. Скилл `1c-standards` — UI-стандарты; поэлементный чек-лист — [[managed-forms-guide]].

Правило — [[forms-from-edt-metadata]] (встроенный EDT-режим `1c-forms` не используем).

## 2а. Правка обычной формы (обычное приложение, `Form.bin`)
1. Где код по всем формам — `form-bin-module` (зеркало модулей); саму форму — `form-ordinary` `unpack` и `brief` (досье: что видит пользователь, что меняется от действий).
2. Правка — `form-ordinary` `edit --ops` строго в объёме просьбы; последняя строка отчёта называет масштаб («затронуто N из M»), перекомпоновка всей формы — только по прямой просьбе.
3. Проверка — `validate`, `lint`, `render --before` «до / после»; `edit` сам обновляет `Form.bin`.
4. Загрузка в тестовую базу (`db-load-xml`) и проверка конфигурации — без неё не «готово»: загрузку изменённой формы мы у себя ещё не проверяли ([[platform-version-and-optional-edt]] п.4).

## 3. Поиск дублей / impact-анализ
1. `code-index` — `search_function`, `grep_code`, `get_call_tree`, `get_callers`.
2. `edt-mcp` — `find_references`, `get_method_call_hierarchy` (по живой модели EDT).
3. Нужна широта охвата — многоагентный веер + состязательная проверка ([[subagents-on-explicit-consent]]; по нужде или по просьбе, не по умолчанию).

**⚠ Карта связей 1С БОГАЧЕ call-graph — не путать вид ребра с провенансом.** Синтаксический call-graph (шаги 1–2) видит только **вызовы в коде**. Но самые опасные для impact связи в 1С **невидимы** ему — платформа вызывает, а вызова в тексте нет. Полный радиус поражения = три вида рёбер, и каждое помечается **провенансом** (иначе выведенное выдаётся за гарантированный вызов):

| Вид ребра | Примеры 1С | Провенанс — чем подтверждается |
|---|---|---|
| **Статическое** (вызов) | обычный вызов метода/функции | ✅ гарантировано: `code-index` (`get_callers`/`get_call_tree`), `edt-mcp` `find_references` |
| **Косвенное** (декларативная связь метаданных) | подписка → обработчик; документ → движение регистра (проведение); команда/событие формы → обработчик; регламент → метод; план обмена + правила регистрации | 🟡 выведено из метаданных: `nkdk`/`meta-info`/`edt-mcp` (состав подписок, регистраторы, состав подсистемы) — **не** из код-вызова |
| **Динамическое / неоднозначное** | `ОбщегоНазначения.ОбщийМодуль("Имя")`, `Выполнить`/`Вычислить`, вызов по строке-имени, рефлексия | 🔴 кандидат: `grep_code` находит место, но связь статикой **не подтверждается** — требует ручной проверки |

Правило: **косвенное/динамическое ребро не выдавать за гарантированный вызов** — помечать как выведенное/кандидат и подтверждать вторым инструментом ([[work-through-tools]] «≥2 независимых инструмента»). Классический пропуск: поменял метод общего модуля → сломался **обработчик подписки**, к которому код-вызова нет; чистый call-graph его не находит — ищи косвенные рёбра через метаданные (`nkdk`/`edt-mcp`). Концепт типизации+провенанса рёбер — проекция графов кода codebase-memory/graphify на 1С ([[external-mcp-servers-review]]; инструменты BSL не поддерживают, взят только концепт).


**🔴 закрывается рантаймом, а не рассуждением.** Динамический вызов (`ОбщегоНазначения.ОбщийМодуль("Имя")`, `Выполнить`/`Вычислить`, вызов по строке) статикой не подтверждается **по построению** — сколько ни смотри в код, гарантии не будет. Зато его подтверждает **факт исполнения**: технологический журнал. Это §7 наоборот — не «долгая операция → найти виновный код», а «неподтверждённое ребро → искать его в журнале»:

```powershell
. tools\OneSTools.PS.TechLog\Import-TechLog.ps1
$ev = Get-TechLog -Path 'D:\techlog\*\*.log'
$ev | Group-TechLog -GroupProperty EventName          # 1) какие события ВООБЩЕ собраны
$ev | Where-Object { $_.Properties.Context -match 'ИмяМодуля\.ИмяМетода' } |
      Select-Object DateTime, EventName -First 20      # 2) встречается ли искомый вызов
```

Порядок именно такой: **сперва узнать фактический состав событий** в этом журнале, потом фильтровать. Состав задаётся `logcfg.xml` конкретной базы — пустая выборка может означать не «вызова нет», а «событие не собиралось». Имена событий не берутся по памяти: парсер их не нормализует и отдаёт как есть.

⚠️ **Журнал доказывает НАЛИЧИЕ вызова, но не его ОТСУТСТВИЕ.** Встретилось — ребро переводится 🔴 → ✅ с пометкой «подтверждено рантаймом» и **указанием окна наблюдения**. Не встретилось — ребро **остаётся 🔴**: редкий сценарий, сезонный регламент, ветка под правом или функциональной опцией просто могли не попасть в окно. Отрицательный вывод из ТЖ — самая частая ошибка при его чтении, и она опаснее исходной неопределённости, потому что выглядит как доказательство.

Концепт — проекция `ingest_traces` (`codebase-memory-mcp`: рантайм-трейсы валидируют статически выведенные рёбра; разбор дельты 19.08.2026 — [[external-mcp-servers-review]]). Взят механизм, не сервер: BSL он не поддерживает.

## 4. Работа с живой базой
1. Только **тестовая** база; боевую не регистрировать ([[secrets-and-production-database]]).
2. `1c-toolkit` `execute_query` — данные и метаданные (read-only путь по умолчанию).
3. `execute_code` — осознанно и только на тесте.
4. Массовые операции — скиллы `db-*` (бьют только по базам из `.v8-project.json`).

## 5. Обновление инструментов
1. Скачал бинарник — **сверить sha256 с официальным (а если `checksums.txt` у релиза НЕТ — сверить размер ассета через `gh api repos/<репо>/releases/tags/<тег>` и зафиксировать СВОЙ sha256 в поле `sha256` записи программы в `plugin/tools/setup/tools-manifest.json`, чтобы провенанс был хотя бы воспроизводимым: установщик `install-tools.py` сверяет с ним скачанный ассет и при расхождении не ставит программу) с официальным `checksums.txt` релиза** до установки ([[probe-tool-capabilities]] п.6); распаковка чужого архива — с проверкой, что пути не ведут за пределы целевого каталога.
2. Перепроверить контракт (`--help`, конфиг) — [[probe-tool-capabilities]].
3. Для MCP-сервера контракт доказывается **хендшейком, а не `--version`**: `tools\checks\mcp-smoke.py` (initialize → tools/list → якорные имена). Изменился состав инструментов — обновить якоря в скрипте и тул-док. ⚠️ **Граница (16.10.2026):** якорный хендшейк `mcp-smoke` делает только для **stdio**-серверов; у http-серверов (`1c-forms`, `edt-mcp`, `1c-toolkit`; `bsl-context` с 4.0.0 — stdio, проверяется якорным хендшейком) он проверяет порт и `/health` — это «сервер жив», а не «инструменты те же», состав их `tools/list` сверяется отдельным зондом.
4. **Заменил бинарник, который стережёт контур** (`bsl-analyzer` — контур 1, `bsl-indexer` — обогатитель 9) — в той же правке прогнать `contour-tests` по этому контуру, а не только `--version`: новая версия может начать выдавать `level=error` там, где раньше было чисто, и барьер начнёт блокировать правки (риск подтверждён релиз-нотами 0.3.x, прогон 16.10.2026 дал FAIL=0).
4. Переналожить патчи из [[vendor-patch-registry]] и прогнать их проверки.
5. Обновить тул-доки под факт ([[docs-match-reality]]) и счётчики ([[regenerate-doc-index]]).
6. Прогнать самопроверку (ниже).

### 5а. BLS (bsl-language-server)
Обновление — запуском хука плагина, интерактивный `/plugin` НЕ нужен:
```powershell
powershell -ExecutionPolicy Bypass -File tools\claude-code-bsl-lsp\hooks\check-bsl-ls.ps1
```
Хук сам качает `bsl-language-server_win.zip` из releases/latest в `%LOCALAPPDATA%\Programs\bsl-language-server\<ver>\`, обновляет `SERVER-INFO` и удаляет старую версию. После обновления обязательно:
1. Проверить **версионный сегмент в User PATH**: старый путь `…\vX.Y.Z\` становится битым — заменить на путь новой версии.
2. Смоук: `bsl-language-server --version`.

**Плагин не провижен** (`tools\claude-code-bsl-lsp\` нет: клон стоит в `.gitignore` и не попадает ни в срез, ни в git-копию) — хука нет, обновление ручное. Весь путь меняет окружение пользователя вне репозитория (каталог в `%LOCALAPPDATA%`, `SERVER-INFO`, User PATH), поэтому — **только с явного согласия** ([[ask-before-changing]]):
1. Скачать релизный zip и сверить sha256 по §5 п.1.
2. Распаковать в `%LOCALAPPDATA%\Programs\bsl-language-server\v<версия>\` — exe должен лечь в `…\v<версия>\bsl-language-server\bsl-language-server.exe`.
3. Вписать `"version": "v<версия>"` в `SERVER-INFO`. Лаунчер `tools/servers/run-bsl-ls-mcp.cmd` плагина (в мастере — `plugin/tools/servers/`) берёт версию сперва оттуда, иначе — наибольшую по сравнению версий.
4. Поправить версионный сегмент User PATH и прогнать смоук (пункты выше).

Если строки `bsl-ls` в `.mcp.json` проекта нет, отставание версии на рабочий стек не влияет. Если есть (как в мастер-ядре) — обновлять.

### 5б. cc-1c-skills (инструментальные скиллы)
Источник скиллов апстрима — `tools\cc-1c-skills\.claude\skills` (соседний `.claude_off` — старый снимок, не источник).

1. `git fetch` в клоне `tools\cc-1c-skills`. Клон часто оказывается в **detached HEAD** — тогда сперва `git checkout main`, иначе ff-merge некуда делать.
2. Сверить **baseline** до слияния: файлы клона на текущем HEAD против `.claude\skills` (сравнением хешей). Разойтись должны **ровно** скиллы из [[vendor-patch-registry]] — лишнее расхождение разбирать до обновления. Файл, который не совпал ни со старым, ни с новым HEAD клона, — ещё не обязательно наша правка: он мог приехать обновлением промежуточной версией апстрима. Разбор — **по истории апстрима**: `git -C tools\cc-1c-skills rev-list origin/main -- .claude/skills/<путь>`, затем по каждому коммиту блоб `git -C tools\cc-1c-skills rev-parse <коммит>:.claude/skills/<путь>` сравнить с `git hash-object .claude\skills\<путь>`. Совпал с каким-то коммитом — это отставший апстрим, обновлять безопасно. Не совпал ни с одним — это локальная правка, она обязана быть в [[vendor-patch-registry]]. `hash-object` применяет фильтры репозитория: при `core.autocrlf=true` CRLF снимается, BOM — нет. На проверенном образце оба файла в LF, и хеши совпали. Приём — по мотивам одного из экземпляров: там разбор показал, что 51 «лишнее» расхождение — отставший апстрим.
3. ff-merge: `git merge --ff-only origin/main`.
4. Взять список изменённых скилл-папок из дельты: `git diff --name-only <старый_HEAD> <новый_HEAD> -- .claude/skills` → первый сегмент пути, уникальные.
5. **Бэкап** папок из списка, затем **трёхстороннее слияние по файлам** ([[vendor-patch-registry]] п.6; так шла пересинхронизация 29.10.2026, журнал вехи 80): для каждого файла дельты `git merge-file <наш .claude\skills\…> <база — версия клона под нашими скиллами> <новая версия клона>`. Файл, который мы не правили, берётся как есть; наш и апстрима сливаются; конфликт **не применять**, а разобрать вручную. Новые файлы и папки апстрима приезжают как есть. База и новая версия берутся `git cat-file blob <коммит>:<путь>` с перенаправлением в Bash (не `>` в PowerShell — UTF-16, п.8 правила). Прежний способ — `robocopy /MIR` по папкам с последующим переналожением — затирал и файлы, которых апстрим не касался (18.09.2026 так пропали все шесть патчей), и больше не используется.
6. **ПРОВЕРИТЬ вендор-патчи** по [[vendor-patch-registry]]: каждый патч-скрипт `tools/patches/*.py` с `--check` (то же делает `health-check` §8b), идемпотентные без `--check` — повторным прогоном (0 изменений), остальные записи реестра — по колонке «Проверка». Слетевший патч переналожить тем же скриптом; сверять с бэкапом диффом — так видно, что именно поменял апстрим.
7. Патч мог стать **ненужным**: если апстрим исправил ту же проблему сам (в 2026-08 так ушли оба патча `mxl-*` — спека переехала внутрь скилла в `reference/`), патч не восстанавливать, а вычеркнуть из реестра с отметкой «устранено апстримом».
8. Пересчитать счётчик скиллов ([[regenerate-doc-index]]) + health-check (§6).

## 6. Самопроверка ядра (перед дорогими аудитами)
```powershell
python tools\checks\health-check.py
```

## 12. Юнит-тесты YAXUnit (автотест-чекер)

Предпосылка: движок/плагин YAXUnit установлен ([[edt-plugins-installed]]); тесты живут **отдельным расширением** (не в основной конфигурации).

1. **Структура:** тестовое расширение `<Префикс>_Тесты`; общий модуль на объект тестирования; экспортная процедура `ИсполняемыеСценарии()` регистрирует тесты, сами тесты — экспортные процедуры с говорящими именами (язык — по языковому профилю проекта, [[language-profile]]).
2. **Писать:** проверки через API YAXUnit (`Ожидаем.Что(...)`-стиль); один тест — одно поведение; подготовка данных — во временных объектах тестовой базы (только тест-база, [[secrets-and-production-database]]).
3. **Запуск headless — ПРОВЕРЕНО живым прогоном 11.07.2026** (позитив: 1 тест зелёный, exitcode=0; негатив: сломанное утверждение → failures=1, exitcode=1):
   ```
   1cv8c.exe ENTERPRISE /F"<база>" /DisableStartupDialogs /DisableSplash /C"RunUnitTests=<путь>\run-config.json"
   ```
   `run-config.json`: `filter.extensions=["<ИмяРасширенияТестов>"]`, `reportPath` (jUnit XML), `reportFormat:"jUnit"`, `closeAfterTests:true`, `exitCode` (файл с 0/1 — признак для CI), `logging.file/enable/level`. Движок — `YAxUnit-<версия>.cfe`: в проекте — папка программ плагина `bin/yaxunit/` (ставит установщик программ), в мастере ядра — та же папка данных плагина; в базу через `ibcmd`. В `edt-mcp` 2.17.1 запуск есть: `run_yaxunit_tests` (фоновая задача с `jobId`, фильтры `extensions`/`modules`/`tests`/`tags`, отчёт JUnit + `report.md`; нужна конфигурация запуска клиента и расширение YAXUnit в базе) и `debug_yaxunit_tests` — зонд jar 18.09.2026, живым вызовом не подтверждено (в 11.07.2026 на 2.5.1 инструмента не было). Headless `1cv8c` остаётся основным путём: работает без запущенной EDT.
4. **Ловушки установки/запуска (пойманы живой диагностикой пилота либо применены как шаги установки — не теория):**
   - **Хост обязан ОПРЕДЕЛЯТЬ `ПриНачалеРаботыСистемы()`** в модуле управляемого приложения (хотя бы пустую): движок цепляется `&После("ПриНачалеРаботыСистемы")` — без обработчика в хосте расширению не к чему подключиться, клиент **молча висит открытым**.
   - **YAxUnit 25.12 цепляется и к `ОбработкаОтображенияОшибки` — под ОБОИМИ именами** (`&После("ОбработкаОтображенияОшибки")` и `&After("ErrorDisplayProcessing")`). Для `ПриНачалеРаботыСистемы`/`OnStart` платформа сопоставляет имена сама, для этого события — нет: без обоих методов в модуле приложения хоста расширение «загружено, но не применится» («Не найден метод "ErrorDisplayProcessing"…»). Хосту нужны оба пустых метода с сигнатурой `(ИнформацияОбОшибке, ТребуетсяЗавершениеСеанса, СтандартнаяОбработка)` — проверено на тестовой базе мастера 30.10.2026. Второе имя — исключение языкового профиля ([[language-profile]], решение владельца 30.10.2026): требование движка, как латинские аббревиатуры платформы.
   - **Модуль тестов — без флагов «Вызов сервера» и «Глобальный»**: движок такие модули пропускает («Пропущен, это не тестовый модуль» в логе) — прогон даёт 0 тестов. Сокращение `context: "server"` скилла `meta-compile` ставит Сервер + ВызовСервера, поэтому модуль тестов создавать явными флагами (`"server": true`, при клиентских тестах ещё `"clientManagedApplication": true`).
   - **Синтаксическая проверка расширения тестов в одиночку** (`db-cfe-admin check -Name <тесты>`) даёт «Переменная не определена (ЮТест)»: проверка одного расширения не видит модули другого. Это предел проверки, а не ошибка; решает прогон харнесса.
   - **`ConfigurationExtensionCompatibilityMode` хоста ≤ режима расширения**: у свежесозданных конфигураций он равен текущей версии платформы (напр. 8.3.27), а движок собран в 8.3.10 → расширение молча не применяется. Понизить у хоста (корень, `Configuration.xml`).
   - **`ibcmd config apply` гонять ПО КАЖДОМУ расширению** (`--extension=<имя> --force`): apply без `--extension` обновляет только основную конфигурацию, расширение остаётся без «поколения» и в сеанс не подключается. Маркер успеха — `[INFO] Создано поколение расширения конфигурации`.
   - **`safe-mode=no` + `unsafe-action-protection=no`** расширениям: `ibcmd config extension update --name=<имя> --safe-mode=no --unsafe-action-protection=no`.
   - **Запуск клиента — никогда `Start-Process -Wait`**: при любой из ловушек выше клиент висит вечно (зомби-процессы). Правильно: `-PassThru` + поллинг файла `exitCode`/отчёта с дедлайном (~120с) + принудительный kill по таймауту.
   - Диагностика «тесты не бегут»: журнал регистрации ошибок применения НЕ пишет; проверять зондом в обработчике хоста (`Вычислить("ЮТИсполнительСлужебныйКлиент")` → ATTACHED/NOT_ATTACHED) и логом движка (`logging.file`).
5. Результат прогона — в отчёт по [[full-checker-set-before-done]] (автотесты — один из чекеров); красные тесты = правка не готова (движок честно даёт exitcode=1 — проверено негативным прогоном).
6. **Регрессионный тест на баг пишется ДО фикса и наблюдается КРАСНЫМ** — иначе неизвестно, что он проверяет именно этот симптом; зелёный после правки — единственное доказательство починки ([[bug-diagnosis-loop]] Ф5). Кейс из §10 автоматизируется, где возможно.

### Каким должен быть тест YAXUnit

**Шов** — точка, через которую поведение вообще можно проверить: экспортные методы **серверных общих модулей**, методы **модулей менеджеров**, модули объектов (проведение → движения регистров), результат СКД. Логика, оставленная в модуле формы или в теле `ОбработкаПроведения`, швом не является — её не вызвать ничем, и это находка (архитектурный дефект, [[naming-and-module-design]]), а не повод пропустить тест.
**Шов согласуется с пользователем ДО написания тестов** (в идеале — до кода, [[design-before-code]] п.6): выбор шва меняет архитектуру, а не только тест. Брать шов **максимально высоко** (сценарий целиком, а не внутренняя функция); швов — минимум; существующий шов предпочтительнее нового.

Три антипаттерна (каждый даёт тест, который врёт):
1. **Связанность с реализацией** — тест знает про внутренние функции, порядок вызовов, приватные структуры: краснеет от любого рефакторинга при живом поведении. Проверять наблюдаемый результат (возврат, движения регистров, записанные данные), а не путь к нему.
2. **Тавтологичность** — эталон вычислен **тем же кодом**, который проверяется (ожидаемое = вызов той же функции, запрос по тому же алгоритму). Такой тест зелёный при любом баге. **Эталон обязан быть НЕЗАВИСИМ от кода:** литерал, ручной расчёт, цифра из ТЗ, эталонный макет.
3. **Горизонтальная нарезка** — тесты «на модуль» и «на метод» вместо «на поведение»: два десятка проверок функций и ни одной на сценарий. Один тест — одно поведение end-to-end через шов; имя теста называет поведение, а не имя метода.

## 14. Прототип для снятия неопределённости

Прототип строится, когда проектный вопрос **нельзя закрыть рассуждением** — только руками. Условия законности (один записанный вопрос, вне конфигурации, только тест-база, без полировки, выход — ответ, а не код) — [[design-before-code]] п.2. Здесь — как прогнать.

**Ветка «ЛОГИКА»** (вопрос вида «ляжет ли механизм?», «что реально получится на этих данных?»):
1. Скилл `epf-init` → внешняя обработка `Прототип_<вопрос>` — **вне конфигурации** ([[use-skills-not-manual-edits]]).
2. Сценарий целиком — **в модуле объекта** обработки (форма прототипу не нужна).
3. **Полное состояние — ПОСЛЕ КАЖДОГО ШАГА**, в `Сообщить()` или в табличный документ. Не только итог: прототип отвечает на вопрос «где ляжет не так», а это видно в промежуточных состояниях, не в финальном результате.
4. `epf-build` → прогон на **тестовой** базе ([[secrets-and-production-database]]); точечный зонд — `1c-toolkit` `execute_code`. Для ERF — не через `ВнешниеОтчеты.Создать` на сервере: вызов висит до 504 шлюза тулкита, обход через схему из `Template.xml` — [[installed-tools-and-servers]], раздел 1c-mcp-toolkit.
5. Выход — **ответ**: абзац/раздел ТЗ + строка в [[work-journals-and-commits]]. Обработка архивируется; перенос её кода в конфигурацию без ТЗ и полного сета чекеров запрещён.

**Ветка «ИНТЕРФЕЙС»** (вопрос «какая форма удобнее?»):
1. **2–3 радикально разных** варианта формы (не косметические вариации одного) — формами **одной** обработки (`form-add`/`form-compile`, [[forms-skills-and-visual-check]]).
2. Скриншот каждого — `edt-mcp` `get_form_screenshot` ([[forms-from-edt-metadata]]); показать пользователю рядом.
3. Выбор — **окном вариантов** ([[questions-as-options]]). Выбранный вариант описывается в ТЗ; прототип выбрасывается.

## 15. Ревизия архитектурного долга конфигурации

> Ревью **по модульной декомпозиции** — границы бизнес-возможностей, владение данными, формы, собранные из нескольких возможностей, слои внутри модуля — скилл `architecture-review` (подход Udi Dahan / Particular Software). Этот рецепт — горячие точки долга по сигналам; скилл берёт их как вход своего шага 4.

Задача «посмотри, что тут не так» приходит без адреса. Долг ищется **по сигналам, а не по вкусу**; сигналы — в порядке убывания силы:

1. **Объекты, снятые с поддержки или изменённые относительно поставщика** (скиллы `support-edit`, `cf-info`) — это фактическая карта доработок конфигурации и самый сильный сигнал: долг живёт там, где типовое уже тронули.
2. **Частота изменений по `git log`** — **только если история есть**. В экземпляре часто одна выгрузка одним коммитом → сигнал не работает: **сказать это вслух**, а не подменять догадкой.
3. **Диагностика `v8cs:redundant-export-method`** (проверки v8-code-style в EDT: маркеры `edt-mcp`; в `bsl-analyzer` и скилле `1c-standards` такого правила нет) — улика модуля-прокладки: экспортный метод без вызывающих. Без EDT — считать вызывающих экспортных методов через `code-index` (`get_callers`) и сказать вслух, что считалось вручную. Однострочный делегат эта диагностика не ищет, а область `ПрограммныйИнтерфейс` намеренно пропускает: прокладку в ней ищут шагом 5.
4. **Направление, названное пользователем** — берётся как есть, но не отменяет 1–3.

Далее:

5. **Веер по горячим точкам** (топ-5–7): по каждой параллельно — `code-index` (`get_callers`, `get_call_tree`, дубли `search_function`) ∥ `edt-mcp` (`get_module_structure`, `find_references`). Нужна широта — субагентами ([[subagents-on-explicit-consent]]).
6. **Карточка кандидата** (единый формат): *что* (объект/модуль/метод) · *в чём трение* (чем это платится сегодня) · *предложение* · *выигрыш* · **сила рекомендации** (уверен / стоит обсудить / гипотеза).
7. **Тест удаления — обязателен для каждого кандидата-прокладки:** прежде чем предлагать «вынести/обобщить», проверить, не лучше ли **вычеркнуть** слой и звать напрямую ([[naming-and-module-design]]). Слой, не переживающий вопрос «что сломается, если его убрать?», не рефакторят, а удаляют.
8. **Выбор направлений — окном вариантов** ([[questions-as-options]]); **реализация — ТОЛЬКО через ТЗ** ([[design-before-code]]) и полный сет чекеров ([[full-checker-set-before-done]]). Сама ревизия кода не меняет.
9. **Отчёт** — проектный док в `docs-project/` ([[project-knowledge-folder]]) + `.docx` людям ([[office-formats-for-people]]), не HTML-артефакт.

## 17. Ретроспективный детектор непокрытых швов (карта «где теста нет»)

Парный к **проспективному шву** Тестировщика ([[five-role-design-review]], [[design-before-code]] п.6): там шов выбирают ДО кода, здесь — зазор ищут постфактум на **легаси/заимствованных** модулях порождённого проекта, где тесты не закладывались. Задача — найти **экспортные методы серверных общих модулей, не покрытые ни одним тестом YAXUnit** (реальный зазор внедрения, а не гипотеза).

Алгоритм — вычитание двух множеств:
1. **Экспортные методы серверных общих модулей** — `code-index` (`search_function`/`get_function` по экспортным) либо grep по Designer-XML-выгрузке (`Процедура|Функция … Экспорт` в модулях серверного контекста).
2. **Вызовы из тест-модулей YAXUnit** (тестовое расширение `<Префикс>_Тесты`, §12) — grep/`code-index` по телам тестов: какие методы реально дёргаются.
3. **Вычесть** (1) − (2) → список **непокрытых** экспортных методов.
4. **Приоритизировать по НЕОБРАТИМОСТИ**: методы, двигающие регистры / участвующие в проведении — выше (цена бага больше); чистые расчётные функции — ниже.

Инструменты — **только локальные**: `code-index` + grep по тест-расширению. Никаких vector-DB, демонов, heartbeat ([[use-own-mcp-servers-only]]; экономия — [[token-economy-and-local-tools]]).

⚠️ **Честная граница** ([[docs-match-reality]]): авто даёт **только СТРУКТУРУ** — список непокрытых швов. **Эталонные значения теста всегда ручные** ([[design-before-code]] п.6 — эталон независим от кода, системой не вычисляется). Это **НЕ автогенерация работающих тестов**, а карта пробелов: она говорит «здесь тесту место», но что проверять и с каким ожидаемым — решает человек.

📌 **Это РЕЦЕПТ (алгоритм + инструменты), а не готовый оттестированный скрипт.** Для прогона нужны живой `code-index` и тест-расширение YAXUnit; в мастере 1С-конфига нет — на нём не гонялось. Материализовать в `.ps1`/связку — когда появится живая мишень (порождённый проект с легаси-модулями).

## 18. Statusline экземпляра (опт-ин)

📌 **Маргинальное, честно low-priority: UX, не корректность.** В мастере не обязателен; заводится осознанно в экземпляре.

Непрерывная строка-состояние Claude Code рендерится **из уже считаемого состояния** — без новых вычислений, демонов и heartbeat-скриптов ([[use-own-mcp-servers-only]]; экономия — [[token-economy-and-local-tools]]). Полезные для 1С-экземпляра поля:
- **активный alias** конфигурации/форка — из манифеста (`env`, [[server-ports-per-project]]);
- **профиль** — EDT / Designer-XML ([[platform-version-and-optional-edt]]);
- **ветка git** конфигурации-монорепо ([[config-git-forks-and-merges]]);
- **последний вердикт health-check** — FAIL/WARN из свежего прогона (§6), не из нового вызова.

Механика — **штатный statusline Claude Code**; точный формат/ключ конфига **подтвердить зондом/докой перед настройкой**, не по памяти ([[probe-tool-capabilities]]). Строка только **отражает готовое состояние** — никакого фонового демона/heartbeat, ничего не пересчитывает.

## 19. Радиус поражения по диффу (перед коммитом / перед сдачей среза)

Отвечает на вопрос «что я задел» **до** того, как это выяснит тестировщик. Вход — не имя метода (как в §3), а **git-дифф**; выход — затронутые объекты с классом риска.

1. **Что изменено.** `git diff --name-only` (или `--cached` перед коммитом) → список файлов выгрузки.
2. **Во что превратить.** Файл → объект конфигурации и метод: для `.bsl` — `code-index` `get_file_summary` (какие функции лежат в файле), для XML/`.mdo` — соответствующий `*-info` (`meta-info`, `role-info`, `form-info`, `skd-info`), **не чтением сырого XML** ([[use-skills-not-manual-edits]]).
3. **Радиус.** По каждому изменённому экспортному методу — §3 целиком: `get_callers`/`get_call_tree` (статические рёбра) + метаданные (косвенные) + `grep_body` (динамические кандидаты).
3а. **Профиль правки печатает инструмент** (с 15.10.2026): `python tools\setup\change-profile.py --json` даёт объём (`C0`–`C3`), набор архетипов кода, ось сложности, итоговые `code`/`arch`, класс и **`driver`** — что именно подняло глубину. Это вход для п.4, а не замена ему: радиус по вызывающим (п.3) инструмент не считает. Полное описание осей — [[full-checker-set-before-done]] п.8.

4. **Класс риска — три уровня, и он вычисляется, а не назначается по ощущению:**

   | Класс | Признак (проверяемый) | Что требует |
   |---|---|---|
   | 🔴 **высокий** | тронут **экспортный** метод общего модуля с ненулевым числом вызывающих; либо роль/право; либо структура объекта с данными в базе (тип реквизита, измерение); **независимо от размера диффа** (19.09.2026): обработчики проведения и записи (`ОбработкаПроведения`, `ПередЗаписью`, `ПриЗаписи`), явные транзакции, заимствованный объект расширения, подписка на событие, регламентное задание, условие RLS | полный сет [[full-checker-set-before-done]] + функциональный прогон §10 + явное согласование ([[ask-before-changing]]) |
   | 🟡 **средний** | тронут метод, вызываемый только внутри своего модуля; либо форма/макет; либо неэкспортная логика | полный сет чекеров |
   | 🟢 **низкий** | комментарии, тексты `НСтр`, форматирование, доки | чекеры по правилу, без функционального прогона |

5. **Что сказать вслух.** Список изменённых объектов, класс риска по каждому и **непокрытое**: динамические рёбра, оставшиеся 🔴 после §3 — они и есть то, что тесты не поймают.

⚠️ **Классификатор не заменяет §3, он его вызывает.** Отдельного «анализатора рисков» не заводить, пока список изменённых файлов помещается в один экран ([[coding-discipline]] п.2): весь рецепт — это последовательность уже существующих вызовов, а не новый инструмент. Признак «пора автоматизировать» — регулярный дифф на десятки объектов, а не желание красивой таблицы.

Концепт — проекция `detect_changes` (`codebase-memory-mcp`: git diff → затронутые символы + blast radius с классификацией риска; разбор дельты 19.08.2026 — [[external-mcp-servers-review]]). У них это делает граф; у нас — связка `git` + `code-index` + `*-info`, потому что графа мы не строим.

## 20. «Штатное прежде своего» — проверка ФАКТОМ по исходникам БСП

Правило [[work-through-tools]] п.3 требует не писать своё при живом штатном механизме. До 19.08.2026 эта проверка держалась на **памяти скилла** `bsp` — то есть была ровно тем, что правило запрещает. Теперь у неё есть источник фактов: полная XML-выгрузка БСП по версиям (`1c-syntax/ssl_3_1`, CC-BY-4.0, теги вида `3.1.12.238`).

**Клон — по требованию и ВНЕ КОРНЯ ядра** (≈1 ГБ, 8667 файлов):

```bash
git clone --depth 1 --branch 3.1.12.238 --single-branch https://github.com/1c-syntax/ssl_3_1.git D:/1c-bsp-src
```

⚠️ **Почему снаружи, а не в `tools/`** — проверено замером 19.08.2026, а не из вкуса: клон внутри корня попадает в рекурсивные сканы `health-check` (секреты, утечки путей, самолокация), и тот вырос **с ~7 до 66 с**, выдавая вдобавок ложные «возможный секрет» по чужим `Module.bsl`. А health-check стоит в `git pre-commit` и на старте КАЖДОЙ сессии. После выноса наружу — 20 с. Тот же приём, что с индексом `code-index` ([[code-index-outside-sources]]): большой чужой массив живёт вне зоны сканов ядра. Исключения `ssl-bsp` в `health-check` оставлены как страховка на случай клонирования внутрь, но правильный путь — снаружи.

Версию тега брать **ту, что стоит в проекте**, а не последнюю: механизм мог появиться позже или уже быть объявлен устаревшим.

1. **Есть ли штатное?** Искать по экспортному API общих модулей БСП, а не по названию задачи:
   ```bash
   grep -rn "Функция .*Экспорт" D:/1c-bsp-src/src/cf/CommonModules/<Модуль>/Ext/Module.bsl | grep -i "<что ищем>"
   ```
   Ориентир масштаба: в выгрузке 3.1.12.238 — **1122 общих модуля**, в одном `ОбщегоНазначения` — 211 экспортных методов (проверено зондом 19.08.2026).
2. **Как это вызывается правильно** — читать не только сигнатуру, но и шапку метода: в БСП контракт (параметры, возвращаемое, ограничения) описан комментарием над методом.
3. **Не устарело ли** — искать рядом пометку «Устарела» и указание на замену: вызвать устаревший метод хуже, чем написать своё.
4. **Вердикт в проработку** — «штатное есть: `ОбщийМодуль.X.Y`, вызывается так-то» либо «штатного нет, проверено по БСП <версия>, поэтому пишем своё». Формулировка «в БСП вроде было» — не вердикт.

⚠️ **Границы.** Выгрузка отвечает на вопрос «что есть в БСП», а **не** «что есть в этой конфигурации»: состав подсистем БСП в проекте может быть урезан, а версия — отличаться. Факт о проекте по-прежнему добывается `nkdk`/`edt-mcp`/`*-info` по его собственной выгрузке. Клон — источник **знания о штатном**, не замена анализу конфигурации.


## 21. Медленный запрос 1С: от техжурнала до плана PostgreSQL (слой СУБД, уровень L0)

Справочник слоя СУБД — скилл `1c-platform-kb`: `postgresql/06` (мониторинг и диагностика запросов), `postgresql/10` (запросы 1С на PostgreSQL; разд. 2 — чек-лист «что дорого» с номерами стандартов), `postgresql/08` (типовые проблемы 1С + PostgreSQL); для MS SQL — `mssql/`.

Введено 14.10.2026 (волна G — [[external-skills-review]]). **Пробел, который этот рецепт закрывает:** 1С работает на PostgreSQL, а в ядре слоя СУБД нет вовсе — ни сервера в `.mcp.json`, ни `psql`, ни `docker` в среде (зонд 14.10.2026). Поэтому вопросы «почему запрос медленный», «кто кого ждёт», «не раздулась ли таблица регистра» закрывались **следами** (текст запроса, техжурнал), а не планом, статистикой и ожиданиями. L0 — путь, который работает **уже сейчас и без PostgreSQL вообще**.

**Главное: без словаря сопоставления любой pg-инструмент бесполезен.** План покажет `_reference123` и `_accumrgt456`, а разработчику нужно имя объекта метаданных. Словарь отдаёт сама платформа — `ПолучитьСтруктуруХраненияБазыДанных` (подтверждено `bsl-platform`: «информация о структуре таблиц базы данных для переданных имён объектов метаданных», возврат — таблица значений).

| Шаг | Что делаем | Чем |
|---|---|---|
| 1 | Поймать долгое событие `DBMSSQL` (текст SQL + длительность) и `TLOCK`/`TDEADLOCK`/`TTIMEOUT` | ТЖ, §7 этого дока |
| 2 | Снять словарь «объект метаданных → имя таблицы и поля в СУБД» на **тестовой** базе | `1c-toolkit` `execute_code` → `ПолучитьСтруктуруХраненияБазыДанных` |
| 3 | По имени таблицы из §1 найти объект метаданных | словарь из §2 (имена в PostgreSQL ожидаются в нижнем регистре — **гипотеза, зондом не подтверждена**) |
| 4 | От объекта — к коду: кто формирует этот запрос | `code-index` (`grep_body`, `get_callers`), `edt-mcp`, `Properties.Context` события ТЖ |
| 5 | Решение — в метаданных и тексте запроса, а не в СУБД | `query-optimize`, `v8std` (std652 «несоответствие индексов и условий», std658, std729, std791 про дополнительные индексы), `meta-edit` |

**Жёсткие границы слоя СУБД** (обязательны для любого будущего инструмента, [[secrets-and-production-database]]):
1. **Схему таблиц 1С ведёт только платформа.** Ручной `CREATE INDEX`/`ALTER TABLE` на `_Reference*`/`_Document*`/`_AccumRg*` запрещён и будет снесён реструктуризацией. Индексы задаются метаданными («Индексировать», «Индексировать с доп. упорядочиванием») и std791 (дополнительные индексы — КОРП, параметр ИБ, перестроение при обновлении с реструктуризацией). Рекомендация любого «советника индексов» входит как **текст предложения**, исполняется как правка метаданных.
2. **Боевая база — не наш контур.** Нынешний барьер (`.v8-project.json` + `permissions.deny` + `guard-destructive`) стережёт путь **через платформу**; строка подключения к PostgreSQL его **обходит** — это новый класс доступа, и без отдельного барьера (список разрешённых хостов, отдельная read-only роль СУБД, `default_transaction_read_only`) слой не включается.
3. **Read-only обеспечивается РОЛЬЮ СУБД, а не разбором SQL** (приём из `supabase/supabase`, Apache-2.0): отдельный логин без прав записи, права вида «читать статистику». Флаг клиента `--readonly` — удобство, а не гарантия.
4. **Пароль только в окружении** (`${PG_DSN}`), в `.mcp.json` — плейсхолдер: иначе секрет-скан валит коммит.
5. **На боевой допустим максимум оффлайн-артефакт** (снимок метрик, текст плана), который приносит администратор, а не подключение агента.
6. **План и текст SQL наружу не отправлять:** в них имена таблиц и значения параметров. Разбор плана — локальным средством, не веб-сервисом.

**Дисциплина измерения** (оттуда же): статистику **не сбрасывать** ради «чистой базовой линии» — сравнивать два снимка по ключу (база, пользователь, идентификатор запроса) и считать приращение; на время самой диагностики отключать учёт её собственных запросов, иначе прибор пачкает показания; «возраст запроса» ≠ «время ожидания блокировки», и отмену сеанса по одному возрасту не предлагать. Вердикт проверки — одно из трёх: **найдено** · **чисто** · **нечем оценить** (последнее — готовая формулировка для клетки «чего не хватает» в [[readiness-matrix-and-process-diagram]], которая не бывает пустой).

**Чего L0 не даёт** честно: плана (`EXPLAIN (ANALYZE, BUFFERS)`), накопленной статистики, ожиданий на уровне СУБД, раздувания и автовакуума, серверных параметров. Это уровни L1 (оффлайн-снимок и локальный разбор плана) и L2 (пилот read-only MCP к PostgreSQL) — кандидаты с лицензиями перечислены в [[external-mcp-servers-review]], волна G; решение по ним отдельное.

**Первое проверяемое действие, которое закладывает слой:** на тестовой базе снять словарь по одному регистру накопления и найти его физическое имя в тексте события `DBMSSQL` из ТЖ той же базы — мост «метаданные → СУБД → журнал» замкнулся на реальных строках. Сейчас не выполнено: `1c-toolkit` недоступен (ECONNREFUSED — нужен запущенный `MCP_Toolkit.epf`).


## 22. Карта проекта со связями (локально, код никуда не уходит)

Когда нужно увидеть конфигурацию целиком: «подсистемы → объекты → общие модули» и кто кого вызывает — для входа в чужой проект, оценки радиуса поражения до проработки, разговора с владельцем о границах.

1. Карта: `python <папка плагина>/tools/1c/project-map.py --src <корень XML-выгрузки>` (в мастере — `plugin/tools/1c/…`). Выход — одна страница `.archify/project-map-<время>/project-map.html` в текущей папке (в проекте `.archify/` в `.gitignore`): поиск, дерево подсистем, карточка объекта с кликабельными связями «вызывает / вызывается из», схемой соседства и флагами контекста общего модуля; внешних адресов на странице нет.
2. Источник вызовов — индекс `code-index` (таблицы `files`/`calls`, только чтение), если он лежит в `<выгрузка>/.code-index` или `<родитель>/.code-index` (в том числе по алиасам) либо указан `--code-index`, **и** построен по этой выгрузке (сверка путей файлов); иначе — разбор модулей `.bsl` выгрузки (вызовы «Модуль.Метод(» и «Менеджер.Имя.Метод(» без комментариев и строк). Какой источник сработал — в шапке страницы. Вызовы через переменные, `Выполнить()` и `ОбщегоНазначения.ОбщийМодуль("Имя")` не видны ни тому, ни другому.
3. Схема связей одного объекта: `--focus CommonModule.Имя` кладёт рядом кандидат `archify` (вид `class`: вызывающие → объект → вызываемые, до 6 с каждой стороны) и, если есть `node`, рисует его `archify render`; вылизать схему — скиллом `archify` (`finalize`).
4. Страницу открывают в браузере из файла. Структура одного объекта — по-прежнему `*-info`, точные вызыватели метода — `code-index get_callers`.

Границы: формат EDT (`.mdo`) пока не поддержан — карта строится по XML-выгрузке (скилл `db-dump-xml`); ссылки через типы реквизитов (`СправочникСсылка.X`) на карту не выводятся. Замер 30.10.2026 на выгрузке пилота `cf-vendor-update` («1С:ERP WE»: 9150 объектов, 327 подсистем, 1606 общих модулей, ~9 тыс. модулей): разбор модулей — 48 с, страница — 6,9 МБ. Регресс — contour-tests §86.

## 23. Оценка ТЗ для ИИ без остановки

Просят оценить ТЗ или срок доработки — скилл `spec-estimate`. Единица — активный час ИИ, а не час программиста. Сначала сверка требований с конфигурацией и запретами платформы: готовое в типовой меняет итог сильнее любых норм. Скорость — из журналов сессий (`ai-throughput.py`), арифметика — скриптом (`estimate.py`), календарь — с лимитом тарифа. Регресс — contour-tests §178.
