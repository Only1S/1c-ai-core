# EDT-MCP: рабочие приёмы и грабли

Практические уроки работы с конфигурацией 1С через EDT-MCP (проверены на реальных задачах). Конфигурационно-независимы — применимы в любом проекте с плагином ones-core.

## Синхронизация диск ↔ модель EDT

Внешние (дисковые) правки EDT подхватывает **по-разному**: надёжный путь зависит от типа правки и от того, нужна ли правка только в маркерах и на скриншоте или уже в базе.

**Единое указание.** Сперва путь без диска — инструмент модели. Пошли по диску — `revalidate_objects([FQN])` на время итерации: маркеры и скриншот увидят правку. Правка должна дойти до базы — один `clean_project` (DISK → MODEL) в конце серии дисковых правок, перед `update_database`: выгружается модель, и без него обновление вернёт `UPDATED`, не перенеся ничего (раздел «Обновление базы»). После каждой правки `clean_project` не запускать: он дорог (раздел «Скорость») и теряет несохранённые правки модели (описание инструмента).

⚠️ **Живым зондом на EDT-MCP 2.22.1 это не перепроверено** (EDT выключена, 30.10.2026). Опоры: описание инструмента в jar (DISK → MODEL — с 2.7.1, совет про правки вне EDT — с 2.5.1) и заметки экземпляра от 13.08 и 18.08.2026, сборка в них не названа. Отдельного замера «до и после» в них нет. При первом подъёме EDT проверить: правка `.mdo` существующего объекта и `.form` на диске → `revalidate_objects` → `update_database`, затем то же с `clean_project`.

| Тип внешней правки | Чем подхватывается | Надёжный путь |
|---|---|---|
| `.mdo` **существующего** объекта (поля, синонимы, tooltip) | `revalidate_objects` — нет: модель держит старое и переэкспортирует поверх диска. `clean_project` — сведения расходятся: июль 2026 (матрица от 13.07.2026, сборка не зафиксирована, новейший jar в пуле на ту дату — 2.6.1) — нет; заметки экземпляра от 13.08 и 18.08.2026 и описание инструмента — да | `modify_metadata` (для членов путь `….Attribute.X`/`.EnumValue.X`, LOCALIZED_STRING — с `language`). Он не справляется — правка `.mdo` с согласия, `clean_project`, затем читать `get_metadata_details`: значение должно прийти из модели, а не с диска |
| `.mdo` **свежесозданного** объекта (сразу после `create_metadata`) | `revalidate_objects` (наблюдение июля 2026; перенос в базу сверять сигналами раздела «Обновление базы») | правка `.mdo` + `revalidate_objects([FQN])` — выручает там, где `modify_metadata` не справляется (смена типа на `DefinedType` в старых сборках таймаутила; в одном из экземпляров с 15.09.2026 `modify_metadata` принимает `{kind:'DefinedType', ref:'<Имя>'}` — сборка не зафиксирована) |
| `.form` (раскладка/ширины/заголовки, в т.ч. массово) | `revalidate_objects` — для итерации: скриншот и маркеры видят правку. До базы она так не доходит (18.08.2026, экземпляр: обновление рапортовало `UPDATED`, правки `.form` в базу не попали, лечение — `clean_project`) | правка `.form` → `revalidate_objects([FQN])` → скриншот для итерации (маркеры модуля формы при этом не пересчитываются — см. «Залипшие маркеры»); перед `update_database` — один `clean_project` |
| `.bsl` модуль | дисковая правка не нужна — есть штатный инструмент | `write_module_source` (меняет модель напрямую: диск и модель в синхроне) |
| **Новый объект** метаданных | с диска модель НЕ подхватывает | только `create_metadata` (не дописывать `.mdo` руками); после — проверить, что объект появился на диске, а не только регистрация в `Configuration.mdo` |
| `Configuration.mdo`; очистка свойства пустым значением | `modify_metadata` не умеет (корень недоступен ему и `rename_metadata_object`; пустым значением свойство не очищает) | правка на диске **при закрытой EDT** или сразу обновить проект в EDT (F5) ДО `update_database` — иначе EDT перезапишет файл своей моделью |

`resync_to_disk` выгружает модель **НА диск** (не читает диск!) — в режиме записи это перезапись внешних правок моделью. Для проверки целостности гонять в **режиме отчёта** (`cleanDanglingReferences=false`, `fullExport=false`) → ждать 0 висячих ссылок.

## Скорость: НЕ доводить до `clean_project`

Кейс живого экземпляра: один `clean_project` сбросил инкрементальную привязку проекта к ИБ и превратил обновление базы в заливку **3 584 объектов** (из 4 127 верхнеуровневых) — десятки минут вместо секунд.

Порядок действий, от дешёвого к дорогому:
1. **Правки — инструментами, а не по диску.** `modify_metadata`/`create_metadata`/`write_module_source` меняют модель EDT напрямую: диск и модель в синхроне, обновлять проект не нужно вовсе.
2. **Если правка всё же пошла на диск** (напр. построчный порт `.form`, для которого инструмента нет) — точечно `revalidate_objects([FQN])`; собственное описание `clean_project` в EDT советует то же: «For a single externally-edited object prefer revalidate_objects». Это итерация: в базу правка уйдёт только через п.3.
3. **`clean_project` — только когда без него никак** (залипшие маркеры, которые не сняла точечная правка — таблица ниже; пересборка производных данных; дисковая правка должна дойти до базы — один раз в конце серии, перед `update_database`); цена — валидация всех объектов + сброс инкрементальной привязки к ИБ → следующая заливка в базу идёт целиком.
4. **Обновлять базу часто и мелкими порциями** — пока привязка к ИБ жива, EDT грузит только изменённое.
5. **Не дёргать `get_applications` и другие ИБ-инструменты во время идущего обновления** — они открывают соединение поверх монопольной операции.

Смежное: авто-подхват внешних правок в воркспейсе по умолчанию выключен (`org.eclipse.core.resources.prefs`); включение `refresh.enabled=true` + `refresh.lightweight.enabled=true` избавляет от `clean_project` после внешних правок — менять файл **только при закрытой EDT**. Антивирусные исключения (workspace EDT, `<корень проекта>\tools`, процессы `1cv8*.exe`/`ragent`/`rphost`/`javaw`) заметно снимают CPU-фон. Записи ERROR `com._1c.g5.v8.derived` «AP dump» в `.metadata/.log` — диагностический дамп монопольной операции, не сбой.

Порт плагина хранится в `<workspace>\.metadata\.plugins\org.eclipse.core.runtime\.settings\com.ditrix.edt.mcp.server.prefs` (ключ `mcpServerPort`). Новая запись в prefs сокет не переносит — нужен перезапуск EDT; факт проверять `Get-NetTCPConnection -LocalPort <порт инстанса> -State Listen` и воркспейсом процесса `javaw` за портом, а не содержимым prefs ([[server-ports-per-project]]). _Наблюдение, не проверено:_ в одном из экземпляров после `clean_project` плагин перестал отвечать на порту при работающей EDT, позже порт вернулся — не считать это падением EDT и не повторять `clean_project`: дождаться конца сборки и проверить порт.

### Прямой JSON-RPC к edt-mcp (клиент сессии отвалился)

Если MCP-клиент сессии отвалился, сервер edt-mcp обычно жив — к **своему** инстансу ([[use-own-mcp-servers-only]]) можно ходить напрямую `POST http://localhost:<порт инстанса>/mcp`:
1. На каждом запросе — `Content-Type: application/json` и `Accept: application/json, text/event-stream`.
2. `initialize` → из **заголовков ответа** взять `Mcp-Session-Id` и передавать его во всех следующих запросах.
3. `notifications/initialized` (без `id`) → `tools/call`.
4. Ответ приходит SSE-строками `event: message` / `data: {json}`, результат — в `result.content`. Тяжёлым вызовам — увеличенный тайм-аут клиента.

Грабли Windows PowerShell 5.1: тело отправлять **UTF-8 байтами** (`Invoke-RestMethod … -Body ([Text.Encoding]::UTF8.GetBytes($json))`), иначе кириллица в аргументах инструмента портится; JSON строкой аргумента нативной команде (`curl.exe -d "…"`) PowerShell 5.1 лишает внутренних кавычек — тело передавать файлом (`curl.exe -d @body.json`) или байтами через `Invoke-RestMethod` _(про кавычки — наблюдение экземпляра, зондом в мастере не проверено)_.

Рецепт — для нынешней (legacy) ревизии протокола. Ревизия MCP 2026-07-28 убирает рукопожатие `initialize` и сессии с `Mcp-Session-Id`: если edt-mcp перейдёт только на неё, рецепт перестанет работать — тогда сверяться со спецификацией `modelcontextprotocol/modelcontextprotocol` (разбор — [[external-mcp-servers-review]]).

### Залипшие маркеры: что их снимает

| Маркер / ситуация | Не помогает | Помогает |
|---|---|---|
| `form-legacy-check-event-handler` / `…-command-handler` на форме | `revalidate_objects` по объекту и полный, F5 | правка самой формы через модель (`modify_metadata`) → `revalidate_objects`; сперва убедиться `read_method_source`, что метод есть. Не помогло — `clean_project` с согласия |
| `module-unused-method` + `module-structure-form-event-regions` после привязки обработчика через модель | ревалидация формы | правка `.bsl` (`write_module_source`) → `revalidate_objects`; до этого проверить таблицу обработчиков в `get_metadata_details` |
| маркеры модуля после ручной правки `.form` | `revalidate_objects` (форму подхватывает, маркеры модуля не пересчитывает) | правка `.bsl` или `clean_project` с согласия |
| ложное `bsl-legacy-check-static-feature-access-for-unknown-left-part` на новом экспортном методе | ревалидация по объекту | только **полная** `revalidate_objects` без списка объектов; признак ложного — метод помечен `Export` в `get_module_structure`, замечание стоит на строках этой же правки |

- Итоги `get_problem_summary` после объектной и после полной перевалидации **несопоставимы** (в одном из экземпляров инкрементальная дала 0, полная — 2 вендорных): сравнивать только в одном режиме и записывать режим рядом с числом; вклад своей правки доказывать `git stash` + одинаковой перевалидацией до и после. Честная базовая линия — после полной пересборки, а она — только с согласия (шаг 3).
- Маркер, переживший `clean_project`, — настоящий, а не залипший (пример — «Общие модули» ниже).

## Инварианты «не в обход модели EDT» (no-bypass)

- **Метаданные править только инструментами edt-mcp** (`create_metadata`/`modify_metadata`/`rename_metadata_object`/`write_module_source`), не скриптами по `.mdo` напрямую: скриптовый обход копит рассинхрон, а `update_database` выгружает в базу МОДЕЛЬ, не диск. Дисковая правка — крайняя мера строго по матрице выше.
  - **Узкое исключение — корневой `Configuration.mdo` при частичном порте ветки** (решение владельца 19.09.2026). Корень недоступен `modify_metadata` и `rename_metadata_object` (матрица выше), а порт части ветки требует дописать или убрать регистрации объектов. Допустима правка скриптом по якорям — **только с явного согласия владельца на этот порт** и при закрытой EDT либо с обновлением проекта до `update_database`. Обязательный round-trip: `get_configuration_properties` до и после (что изменилось — ровно задуманное), сверка регистраций с каталогами объектов в обе стороны, `get_project_errors` без фильтра — не больше, чем до правки. Не сошлось — откат из git, а не донастройка.
- **Дисковая правка не считается сделанной, пока не прошла ROUND-TRIP.** Байтобезопасность (`perl :raw`, порядок блоков, кириллица байтами) отвечает лишь за то, что файл **не побит**, — но не за то, что платформа поняла правку так, как задумано. `form-validate`/`meta-validate` смотрят структуру, а не смысл. Проверка фактом — цикл на **тестовой** базе ([[secrets-and-production-database]]): `db-load-xml` → `db-update` → `db-dump-xml` → сравнить выгруженное с ожидаемым. **Дифф после круга обязан быть ровно целевым**: лишние изменения — это то, что платформа переписала по-своему (порядок элементов, служебные атрибуты, UUID), а пустой дифф по нашему изменению означает, что правку просто не приняли. Круг обязателен для правок форм, СКД и структуры объектов; для `.bsl` он не нужен — там есть `write_module_source`.

  _Концепт round-trip verify — из разбора `vgtitov/bsl-ai-toolkit` (MIT, 19.08.2026, [[external-mcp-servers-review]]): у них это движок правки метаданных, у нас — дисциплина поверх уже имеющихся скиллов `db-*`, потому что своего движка мы не пишем._

- **`clean_project` и `resync_to_disk` в режиме записи — только с явного согласия пользователя** (деструктивны и каскадны; частный случай [[ask-before-changing]]).
- **Перед `update_database` после внешних правок — контрольный `resync_to_disk` в режиме отчёта** (0 висячих ссылок) + выборочная сверка модели с диском: у произвольного объекта обработчик/свойство видны в модели, число регистраций в `Configuration.mdo` совпадает с числом объектов на диске по типу.
- **Эвристика «сломалось всё сразу»** (у всех подписок/ролей/форм разом «пропало» одно и то же) — почти всегда рассинхрон модели EDT, а не порча исходников: пока индекс не собран, EDT не резолвит ссылки и показывает/выгружает пустоту. Сначала проверить диск (mtime, содержимое) — и только потом искать «пропавшую» правку. Маркер рассинхрона: в выгрузке всплывают объекты, которых на диске нет вообще, — значит, выгружалась модель, а не диск.

## Запись BSL: режимы `write_module_source` и откат

Самая дорогая ошибка в работе с кодом через edt-mcp — не синтаксис, а **режим записи**: неверный стирает модуль целиком, и штатного undo у инструмента нет.

Значения `mode` сервер принимает только в camelCase — ровно шесть: `searchReplace`, `replace`, `append`, `replaceMethod`, `insertBefore`, `insertAfter` (сверено по классу `WriteModuleSourceTool` в jar EDT-MCP 2.21.1, 30.10.2026; режима по диапазону строк нет ни в одной версии 2.5.1–2.21.1). При включении EDT — сверить с живым `tools/list` ([[probe-tool-capabilities]]).

| Режим (`mode`) | Что делает | Обязательно | Риск |
|---|---|---|---|
| `searchReplace` (умолчание) | заменяет фрагмент `oldSource` на `source` | `oldSource` | низкий — умолчание для точечной правки |
| `replaceMethod` | заменяет метод `methodName` целиком; вид метода (Функция/Процедура) не меняет | `methodName`, `expectedHash` | низкий — штатный путь правки метода |
| `insertBefore` / `insertAfter` | вставка перед / после метода-якоря `methodName` | `methodName`, `expectedHash` | низкий |
| `append` | дописывает в конец модуля | — | низкий |
| `replace` | **перезаписывает ВЕСЬ модуль** | у существующего модуля — `expectedSource` (содержимое последнего чтения) или `overwrite=true` | **высокий** |

- **`replace` для одного метода — запрещено.** Передал метод — стёр остальные сотни строк без отката. `replace` оправдан только при создании модуля с нуля, на пустом/крошечном модуле с полным содержимым, либо при явно согласованной полной перезаписи ([[ask-before-changing]]). Очистить ненужный модуль можно им же: пустой `source` + `expectedSource` из чтения — а не удалением файла.
- **`searchReplace`: фрагмент должен встречаться ровно один раз.** Ноль совпадений или больше одного — операция отклоняется. Это не помеха, а доказательство, что ты видел актуальный код. При отказе — **не ретраить вслепую**: `read_method_source` и расширить фрагмент до уникального.
- **Якорь не разрывает многострочный оператор.** Вставка между частями присваивания текста запроса или конкатенации (`Запрос.Текст = <вставка> "ВЫБРАТЬ…"`) ломает разбор модуля, а встроенная проверка инструмента такое пропускала. Якорь брать по границе оператора.
- **Новый метод перед соседом — якорь по первой строке его doc-комментария**, а не по строке `Функция`/`Function`: иначе шапка соседа остаётся над новым методом. Надёжнее `insertAfter` по предыдущему методу. Признак ошибки — замечания `doc-comment-*` на новом методе с виду правильным описанием.
- **Предохранитель от потерянной правки — хэш и содержимое, а не номера строк.** Режимы по методу требуют `expectedHash` — `contentHash` из `read_module_source`/`read_method_source`; `replace` поверх существующего модуля — `expectedSource`. Модуль изменился после чтения (правка рядом, открытый редактор EDT) — запись отклоняется, файл остаётся целым: перечитать и повторить с новым хэшем, а не ставить `overwrite=true`.
- **Отката нет — он держится на твоём контексте.** До подтверждения успеха держать и старый фрагмент, и новый. Записали не туда — **немедленно** обратная `searchReplace` (новый текст → в поиск, старый → в замену), пока файл не подхватил открытый редактор EDT. Обратная замена невозможна (текст не уникален либо прошёл `replace`) — **остановиться и спросить пользователя**, не реконструировать модуль по памяти: восстановление из открытой в EDT копии надёжнее.
- **`.bsl` не править `Edit`/`Write` напрямую** — только через `write_module_source`, иначе EDT не увидит правку до refresh и теряется авто-проверка (тот же no-bypass, что и для метаданных).
- `skipSyntaxCheck=true` ради «обхода» ошибки баланса блоков — почти всегда маскировка настоящего бага. Исключение — подтверждённая ложная тревога (ниже), и только с обязательной проверкой сразу после записи.
- После записи — прочитать ответ инструмента, затем **полный** `get_project_errors` по затронутому объекту (семантика): без фильтра по отдельной проверке (допустим только фильтр по серьёзности «ошибки»), и лишь потом сужать под частности — прогон с фильтром по одной проверке уже пропускал поломку разбора модуля. Есть новые проблемы — не коммитить ([[full-checker-set-before-done]]).

### Встроенная проверка записи ошибается в обе стороны

Наблюдения экземпляров; версии платформы и моста не зафиксированы — на других сборках не проверено.

- **Ложная тревога.** Однострочные `Если … Тогда …; КонецЕсли;` в модуле валят встроенную проверку каскадом ошибок в строках, которые правка не трогала. Только при этих двух признаках допустим `skipSyntaxCheck=true`, и сразу за записью — `revalidate_objects` + `get_project_errors` (уровень «ошибки») по объекту.
- **Ложная тишина.** `syntaxCheck: passed` не доказывает, что модуль компилируется: цепочка «конструктор → метод» (`Новый ОписаниеТипов("Число").ПривестиЗначение(Х)`) прошла проверку, а модуль не скомпилировался — писать через промежуточную переменную. Симптом в рантайме: вызовы **одного** модуля висят до тайм-аута, соседние отвечают; сломанная версия живёт в базе до следующего `update_database`.
- **Парсер EDT и платформа расходятся:** `#Если` внутри цепочки `ИначеЕсли` EDT отвергает, а платформа принимает — в вендорном коде это не наша ошибка.
- **Баланс `#Область`/`#КонецОбласти` не проверяет никто:** ни встроенная проверка записи, ни `get_project_errors` (в одном из экземпляров незакрытую область поймал пользователь — форма не открылась), ни `bsl-analyzer` (зонд 19.09.2026: на модуле с двумя `#Область` и одной `#КонецОбласти` — только `UnusedLocalMethod`). После правки, меняющей структуру модуля, — явный подсчёт (`grep '^…'` недосчитывает первую строку с BOM, поэтому PowerShell):
  ```powershell
  $t = Get-Content -LiteralPath <Module.bsl> -Encoding UTF8
  @($t -match '^\s*#(Область|Region)(\s|$)').Count; @($t -match '^\s*#(КонецОбласти|EndRegion)').Count
  ```
- **Дубль имени метода после вставки** EDT в экземпляре пропустил. Проверка:
  ```powershell
  Select-String -LiteralPath <Module.bsl> -Encoding UTF8 -Pattern '^\s*(Процедура|Функция|Procedure|Function)\s+([\p{L}\d_]+)' |
    ForEach-Object { $_.Matches[0].Groups[2].Value } | Group-Object | Where-Object Count -gt 1
  ```

## Ошибки проекта: `get_project_errors`, а не `get_markers`

- `get_markers` отдаёт закладки и TODO, фильтры молча игнорирует — средством проверки не является.
- `objectFqns` — точный адрес объекта; нерезолвленные FQN возвращаются в `objectsNotFound`. `objects` — поиск подстроки в локации: часть замечаний (например `form-invalid-item-id` на самом объекте формы) не находит.
- `severity` — точное совпадение уровня; без него приходят все уровни. Часть замечаний живёт только на младших уровнях (непривязанный обработчик формы всплывал лишь как MINOR).
- **Неизвестный параметр отбрасывается молча** (`objectNames`, `filePath`, `objectFqn` вместо `objectFqns`) → пустой ответ ещё не значит «чисто». Имена параметров сверять по `get_tool_guide('<инструмент>')`, а не по памяти ([[probe-tool-capabilities]]).

_Наблюдения нескольких экземпляров на edt-mcp 2.x (сборка не зафиксирована); на установленной версии зондом не перепроверено._

## Роли и права
- В `Rights.rights` при `setForNewObjects=true` **неуказанные права трактуются как разрешённые** → опасные права гасить **явными `false`**: интерактивное удаление, пометка/снятие/удаление предопределённых данных, ТолстыйКлиент, ВнешнееСоединение, Automation, АдминистрированиеРасширений.
- Роль надёжнее создавать через `create_metadata` (модель). Признак роли-пустышки: рядом с `.mdo` нет `Rights.rights`, `get_metadata_details` отвечает «has no editable rights model», `modify_metadata` с правами падает «Failed to persist reference value…RoleDescriptionImpl». Создаёт ли `create_metadata` файл прав, зависит от сборки edt-mcp (в одних — нет, в новых — да) → проверять по файлу; существующий `Rights.rights` не перезаписывать, пустую роль не оставлять.
- Права — через модель (`modify_metadata`). Ручная запись `Rights.rights` — крайняя мера по матрице, с согласия (guard-skills такую правку отправляет в edt-mcp). Корень файла — `<Rights xmlns="http://v8.1c.ru/8.2/roles" xsi:type="Rights">` (пространство имён платформы; так у всех ролей реальной выгрузки, сверено 19.09.2026): с чужим пространством EDT-валидация и `get_metadata_details` чисты, падает только `update_database` на экспорте. `modify_metadata` с правами не адресует вложенные подсистемы и права уровня конфигурации; один нерезолвленный элемент отменяет весь вызов.
- **Командный интерфейс** (по мотивам `bigsofter/tiny1C`, CC BY 4.0; автор проверял на 8.5.1, на 8.3 не проверено):
  - право на команду раздела бесполезно без права `View` на подсистему раздела (`Subsystem.<Имя>` в роли) — ни раздела, ни команды пользователь не увидит; роли для команды выбирать среди тех, кто видит раздел (`grep '<name>Subsystem.<Имя></name>' Roles/*/Rights.rights`), а не «по смыслу»;
  - у обработки без `useStandardCommands=true` нет стандартной команды «Открыть» — размещать в интерфейсе нечего, а ошибки нет;
  - своя навигационная команда объекта (`<commands>` с группой `NavigationPanel*`) без явной видимости в `.cmi` раздела встаёт рядом со стандартной — дубль пункта меню; видимость обеих задавать явно.

## Рефакторинг rename_metadata_object / delete_metadata
- Обновляет типы, формы, тексты запросов и права — но **может ошибочно переименовать в BSL обращения к одноимённым реквизитам** (например, поле регистра `Склад` при переименовании справочника `Склад`→`Склады`). После переименования — проверить BSL и вернуть поля.
- Элемент формы `modify_metadata` не переименовывает («Renaming via the 'name' property is not allowed here») — только `rename_metadata_object` (preview → confirm); companion-узлы (`…ContextMenu`, `…ExtendedTooltip`) он переименует сам. После — сверить `title`: производный заголовок может смениться автопереводом нового имени. Переименование команды формы процедуру-обработчик не переименовывает — сверить модуль.
- **Удаление и переименование — md-рефакторинг: EDT выгружает МОДЕЛЬ поверх `.form` затронутых форм, в том числе несвязанных** — пропадают привязки `<handlers>` и свежие файловые добавления, `Module.bsl` может обнулиться; удаление к тому же каскадно чистит ссылки в коде. Перед операцией — коммит; после — `<handlers>` и размер модулей затронутых форм (симптомы: пара `module-unused-method` + `module-structure-form-event-regions`; при обнулённом модуле — `form-legacy-check-event-handler`). Привязку восстанавливать через модель (`create_metadata …Form.<Форма>.Field.<Элемент>.Handler.<Событие>` с явной процедурой), модуль — `git checkout`; `resync_to_disk` тут не помогает.

## Правка .form на диске
- Байтобезопасно (perl `:raw`, нормализация CRLF в сниппетах, кириллица якорей — байтами `\x{..}`), иначе ломается UTF-8. Блок `<handlers>` таблицы ставить **после** `</autoCommandBar>` (канон сериализации EDT), иначе EDT перезапишет файл при пересохранении.

### Модель EDT пере-экспортирует `.form` целиком

`Form.form` — один файл на всю форму, и EDT пишет его из модели целиком. Отсюда:
- `create_metadata`/`modify_metadata` по форме затирают всё, что было вписано файлом до этого. Порядок: сперва все операции модели → потом файловые правки → `revalidate_objects([FQN])` (матрица) → греп по признакам правки (одного `success` мало).
- Сохранение формы из отставшей модели (правили текстом, проект не обновили) тихо откатывает соседние блоки — текст запроса динамического списка, кэш полей, обработчики. Откаченное состояние валидно, чекеры его не видят. Перед правкой в EDT — обновить проект; после — читать дифф **всей** `Form.form`: посторонние блоки = откат чужой правки, пока не доказано обратное (по мотивам `bigsofter/tiny1C`, CC BY 4.0; дополняет round-trip из no-bypass).
- Удаление и переименование объектов переписывают формы — раздел «Рефакторинг» выше.
- Массовые «Переменная `ЭтотОбъект`/`Элементы`/`Параметры` не определена» в модуле формы и пустой `get_form_layout_snapshot` после внешней записи `.form` — сломан контекст формы, а не код. В `<workspace>/.metadata/.log` (только читать) — NPE в `FormItemPropertyContextDefInferrer` (`getValueType() is null`). Триггер — параметр формы без `<valueType>` вместе с группой кнопок `<commandSource>Form</commandSource>` (нетипизированный параметр сам по себе безвреден). Лечение: тип параметру → `clean_project` с согласия (`revalidate_objects` производные данные формы не пересобирает). Профилактика — генератор всегда типизирует параметры. _(Наблюдение одного из экземпляров, EDT 2025.2.)_

## Обновление базы: тайм-аут — это отказ, пока не доказано обратное

`update_database` почти всегда возвращает тайм-аут на уровне инструмента — обновление идёт дольше лимита. Тайм-аут обрывает **ожидание ответа, а не операцию**: обновление может дойти само (полное — дольше 8 минут), а повторные вызовы встают в очередь за первым. Отсюда приём: подождать в фоне и проверить состояние. У приёма есть ловушки.

- **Состояние осталось `INCREMENTAL_UPDATE_REQUIRED`, ответа не было → обновление, скорее всего, ПРОВАЛИЛОСЬ.** Увеличивать ожидание бессмысленно: текст отказа не приходит в тайм-аут, он приходит **в ответ**. Чтобы его увидеть — запустить обновление ещё раз: на повторе платформа падает рано и успевает отдать ошибку. **Но не при окне блокировки** (ниже) и не пока первое ещё идёт — тогда повтор лишь встаёт в очередь.
- **Проверять `stateAfter: UPDATED`, а не `success: true`** — успешный вызов не означает применённое обновление. И `stateAfter` — условие необходимое, но не достаточное (таблица ниже).
- **Правка шла внешним редактором файла (не через модель EDT) → сначала `clean_project`**, дождаться `ready`, и только потом обновлять: иначе обновление вернёт `UPDATED`, не перенеся ничего — выгружается МОДЕЛЬ, а не диск. `revalidate_objects` этого шага не заменяет (единое указание — в начале файла).

| факт в самой базе | решает спор: объект/реквизит есть, форма изменилась; у расширения — `РасширенияКонфигурации.Получить()`: `Активно`, `БезопасныйРежим` |

Идентификатор поколения сохраняется только внутри экспорта, поэтому флаг держится сам собой и гасится реальной правкой главной конфигурации. Отличие от провала — в том, что ответ пришёл. _(Наблюдалось на EDT 2025.2 с плагином 2.5–2.6; на 2.17.1 не проверено.)_
- **Какая ИБ обновляется, из MCP не видно:** `get_applications`/`list_configurations` строку соединения не отдают. Истина — строка `1cv8.exe DESIGNER /S <сервер>\<ИБ>` в `trace.log`; сверять ДО вызова.
- **Параметры:** `projectName` + `applicationId` (из `get_applications`, `applications[].id`) или `launchConfigurationName`; последний может ответить «cannot derive update target» — тогда пара `projectName` + `applicationId`. У проектов-расширений своих приложений нет (`inheritedFromProject`): расширение накатывается с `projectName` базового проекта, и один вызов обновляет главную конфигурацию и каждое расширение. Имена параметров сверять по `get_tool_guide('update_database')`.
- **Правки, внесённые в базу Конфигуратором,** по умолчанию (`externalInfobaseChanges=override`) молча затираются — передавать `cancel`. _(Со слов экземпляра; имя и значения параметра схемой не сверены.)_
- Один владелец обновления на поток работ: либо `update_database`, либо платформенный путь (`db-update`), не вперемешку. Запуск тонкого клиента из EDT тоже обновляет БД.

**Живые сеансы.**
- `terminateRunningClients` по умолчанию `true` (в предпросмотре — `willTerminateRunningClients`) и закрывает **только клиенты, запущенные EDT** (в ответе `terminatedClient: true`). Вместе с ними умирает `1c-toolkit`, и `false` его не спасает — реструктуризация рвёт соединение. Порядок: правки копить, живые зонды тулкитом — ДО обновления, тулкит поднимать после `UPDATED` (`restart_1c_session` — [[installed-tools-and-servers]]).
- Сеанс, открытый вручную, и фоновое/регламентное задание EDT не видит: на шаге обновления в EDT встаёт модальное окно «Ошибка исключительной блокировки» (Отмена / Повторить / Обновить динамически), вызов MCP висит до тайм-аута. Держатели блокировки перечислены в `<workspace>\.metadata\.log` (запись «Платформа 1С:Предприятие запрашивает выбор»). «Обновить динамически» оставляет живой сеанс на старых модулях.
- Снимать блокирующий сеанс — только на ТЕСТОВОЙ базе и по согласованию ([[ask-before-changing]]: у человека может быть несохранённая работа); на боевой — никогда ([[secrets-and-production-database]]). В актуальном README апстрима для этого есть `infobase_sessions` (`list` перед обновлением; сеанс `Designer` блокирующим не считается — это может быть агент самой EDT); в установленной версии не сверено.

**EDT залип или просто долго.** Сначала исключить посторонние сеансы — они дают ту же картину (ноль CPU у EDT, `INCREMENTAL_UPDATE_REQUIRED`). Дальше замер: CPU процесса EDT за минуту почти не растёт, процесс `1cv8` не появляется, предпросмотр отвечает мгновенно, в `get_mcp_history` нет новых записей `update_database` — задание висит внутри EDT: перезапуск EDT силами пользователя. Ошибка файловой операции `v8srvr://…/Config/<uuid>` при `update_database` указывает на испорченный кэш EDT — `clean_project` его не лечит; дальше — «Когда не чинить самому» ниже.

## Экспорт в ИБ: `RuntimeCoreException: Файл не обнаружен 'zip:///…'`

Коварство в том, что **EDT-валидация чистая** (`get_project_errors` = 0), а падает уже платформа при выгрузке/запуске ИБ: инкрементальный экспорт собирает zip из модели, и в нём не оказывается файла, который EDT считает подразумеваемым.

- **Типовой случай — своя подсистема с `includeInCommandInterface=true`, но без `CommandInterface.cmi` рядом с `.mdo`.** Ошибка: `Файл не обнаружен 'zip:///…/Ext/CommandInterface.xml'`. Лечится созданием минимального файла рядом с `.mdo` подсистемы: `<cmi:CommandInterface xmlns:cmi="http://g5.1c.ru/v8/dt/cmi"/>` → `clean_project` (с согласия) + `revalidate_objects`. У типовых подсистем `.cmi` может отсутствовать без последствий — там индекс EDT давно собран; для свежесозданных в расширении создавать явно.
- **Диагностика по шагам:** извлечь путь из текста ошибки → определить уровень (корневой `Ext/…`, подсистема `Subsystems/X/Ext/…`, объектный) → найти EDT-источник (`.cmi`/`.form`/`.mdo`) → отсутствует — создать минимальный валидный, повреждён — сверить с эталоном соседней типовой → `clean_project` + `revalidate_objects` → повторить экспорт.
- **Профилактика при создании объектов:** у новой подсистемы — уникальное имя с префиксом ([[naming-and-module-design]]), все `content`-ссылки на существующие объекты, регистрация в `Configuration.mdo`; у общей формы — существующие `Form.form` **и** `Module.bsl` (пустой модуль всё равно нужен) плюс ссылка `<form>` в `.mdo`; у общей команды — корректный `commandParameterType` и `CommandModule.bsl` с `ОбработкаКоманды`; у заимствованного объекта — `objectBelonging=Adopted` и никаких своих `predefined`.
- **Когда не чинить самому:** `clean_project` + минимальный источник не помогли — просить пользователя перезапустить EDT (`File → Restart`), `.metadata` воркспейса руками не трогать. **Узкое исключение — испорченный кэш** (ошибка файловой операции `v8srvr://…/Config/<uuid>`, `clean_project` не помогает; 19.09.2026): при **остановленной** EDT (остановку проверять по тому, что порт моста не слушает) перенести в резерв, **не удаляя**, четыре производных каталога `.metadata/.plugins` — `com._1c.g5.v8.dt.core`, `com._1c.g5.v8.dt.search.core`, `com._1c.g5.v8.derived`, `com._1c.g5.v8.dt.bm.index.rights`; `.projects` и `.settings` не трогать. Делает пользователь или агент — только с явного согласия владельца на этот случай. После запуска EDT пересобирает кэш сама; не помогло — каталоги вернуть из резерва. Ошибка касается типового объекта, а не нашего расширения — не править: нужен `Reset to base` со стороны пользователя.

*Разделы «Запись BSL» и «Экспорт в ИБ» перенесены знанием из `rules/` набора Desko77 (MIT) и сверены с составом инструментов нашего edt-mcp; разбор источника — [[external-skills-review]].*

## Чекеры EDT зелёные — платформа отвергает (или падает рантайм)

`get_project_errors` = 0 — условие необходимое, но не достаточное: XML для платформы EDT сериализует сам, и часть ошибок всплывает только при загрузке в ИБ или в рантайме. Для метаданных с нетривиальными типами, новых видов модулей и форм финальная проверка — обновление **тестовой** базы. Первый шаг диагностики — путь из текста ошибки (`zip:///…`), а не разбор исходников.

| Симптом | Причина | Что делать |
|---|---|---|
| «Исключение XDTO … Form.xml … Свойство 'ValuesPicture'» | `valuesPicture` без `InternalInfo` | инкрементальное → `fullUpdate:true` → штатная выгрузка + платформенный `LoadConfigFromFiles` (скилл `db-load-xml`, [[designer-batch-runs]]) |
| «Исключение XDTO … Свойство 'Type'» на форме | параметр формы типа «Массив» (`cfg:Array`) | другой тип параметра |
| форма не грузится, EDT и анализаторы молчат | несуществующее имя `StdPicture.X` | имя сверить со списком картинок платформы |
| «Исключение XDTO … Свойство 'Picture'» в форме расширения | команда/элемент ссылается на общую картинку, не заимствованную в расширение | заимствовать картинку (EDT — `adopt_metadata_object`, XML-выгрузка — скилл `cfe-borrow`; там же ловит проверка `cfe-validate`); сверка: картинки, на которые ссылаются формы расширения, против заимствованных |
| «Неверное имя команды элемента формы … StandardCommand.WriteAndClose» | у проводимого документа нет `WriteAndClose`, у непроводимого — `Post*`; при смене «Проведения» ссылка ломается во ВСЕХ формах документа | меняя «Проведение», проверить стандартные команды всех форм документа; нужная кнопка — своей командой формы (по мотивам `bigsofter/tiny1C`, CC BY 4.0; на 8.3 не проверено) |
| «Недопустимый тип» на измерении | `ЛюбаяСсылка` внутри определяемого типа (модель молча превращает её в пустой `<type/>`) | `AnyRef` прямо в измерении или определяемый тип с конкретным типом-затравкой (в БСП — `CatalogRef.MetadataObjectIDs`); тип ставить `modify_metadata` |
| «Свойство Module не входит в состав объекта Constant» | `write_module_source` с `moduleType=Module` создал `Module.bsl` у константы | у константы — `ValueManagerModule.bsl` через `modulePath`; имя файла модуля брать по соседу того же вида |
| «Ошибка SDBL: Тип поля … несовместим с типом поля FldNNNN» и обрыв сеанса (похоже на отвал тулкита) | реквизит объекта без `<type>` | прочерк в колонке Type у `get_metadata_details` → тип через `modify_metadata` → `update_database` |
| поле-картинка/флажок в таблице формы молча пусты | колонка реквизита формы с пустым `<valueType/>` | тип колонке, на которую смотрит типизированное поле (пустой тип законен у реквизита произвольного типа) |
| падение на каждой записи объекта | общий модуль без `Module.bsl` под активной подпиской | «Общие модули» выше |
| падает только `update_database` на экспорте | `Rights.rights` в чужом пространстве имён | «Роли и права» выше |

_(Наблюдения нескольких экземпляров на платформе 8.3.27; версия платформы и EDT — свойство профиля, [[platform-version-and-optional-edt]].)_

## Расширения в EDT

Наблюдения экземпляров; сценарии `adopt_metadata_object`/`modify_metadata` перед опорой сверить с текущей версией edt-mcp.
- `adopt_metadata_object` приносит пустую оболочку: каждый член (ТЧ, реквизит ТЧ, значение перечисления) заимствуется отдельно. `revalidate_objects` заимствование не подхватывает — нужен `clean_project` (с согласия). Однажды инструмент упал с внутренним null-project — резерв: заимствование по образцу соседнего объекта или скилл `cfe-borrow` в XML-выгрузке.
- `validate_query` в проекте-расширении видит только заимствованные объекты.
- Новое расширение рождается без языков: сперва заимствовать `Language.*`, иначе `НСтр` даёт «неизвестный код языка». При создании проекта расширения `compatibilityMode` ставится по платформе, а `keepMapping`, `defaultLanguage` и блок расширения не пишутся — сверять теги верхнего уровня с расширением, созданным руками.
- Своя команда формы расширения — `FormCommandHandlerContainer`, а не `FormExtensionCommandHandlerContainer` с `callType=After`.
- Удаляешь объект основной конфигурации — сперва убрать его заимствование и контроль типа (`Type`) в расширениях, иначе платформа не загрузит.
- Заимствованная форма тянет ссылки на предопределённые элементы и стили → «Ссылка на неизвестный предопределенный элемент».
- Определяемый тип расширения, указывающий на объект основной конфигурации, даёт «необработанный Proxy», пока сам объект не заимствован.
- `.cfe` EDT не импортирует — только XML-дамп (скилл `db-dump-xml` с `-Extension`) через импорт «Расширение из XML-файлов».
- Обновление ИБ — с `projectName` базового проекта (раздел «Обновление базы»).

## Новые проекты EDT ложатся в воркспейс
- `create_project` и `import_configuration_from_xml` создают **новый** проект в воркспейсе EDT, путь не задаётся; «Загрузить конфигурацию из информационной базы» в меню EDT — тоже. Нужен проект в репозитории: закончить правки → `delete_project(deleteContent=false)` → перенести каталог → «Import Existing Projects» без копирования.
- Удаление старого одноимённого проекта «вместе с содержимым» физически стирает файлы из связанного git-каталога. После любого импорта — первым делом `git status`: массовые `D` лечатся `git checkout -- .`, ничего не коммитить до восстановления; из воркспейса переносить только целевые объекты (по мотивам `bigsofter/tiny1C`, CC BY 4.0). `deleteContent=true` — только с согласия ([[ask-before-changing]]).
- В актуальном README апстрима `DitriXNew/EDT-MCP`: привязка «ветка ↔ ИБ» — `set_branch_infobase`; внешние обработки/отчёты проекта внешних объектов собирает `build_external_objects`; деструктивные операции ждут подтверждения в окне EDT (120 с, потом отказ). Переменную `EDT_MCP_DESTRUCTIVE_CONSENT=allow`, снимающую этот гейт, агент сам не выставляет. Наличие в установленной версии не сверено.
