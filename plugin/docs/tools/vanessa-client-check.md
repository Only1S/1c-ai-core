# Проверка доработки в клиенте 1С через Vanessa Automation

Направление #8 волны 3 (`docs-project/wave3-growth-plan.md` Т-6, файл только мастера): после сборки доработки проверить её поведение в **клиенте** 1С сценарием Vanessa Automation (BDD) на **тестовой** базе — UI-приёмка, дополняющая YAXUnit (юнит). Два слоя: генерация+проверка сценария и его прогон.

## Слой 1 — скилл `vanessa` (генерация + проверка)

Вендорен из [va-ai](https://github.com/Nikolay-Shirokov/va-ai) (MIT, [[vendor-patches]]): `ai-knowledge/` (guide, templates, steps-library.json — 1569 шагов) + валидатор `scripts/validate.py`. Агент генерирует `.feature` **только из шагов библиотеки**, затем парный валидатор:

```bash
PYTHONIOENCODING=utf-8 python "${CLAUDE_SKILL_DIR}/scripts/validate.py" "<feature>" \
  --library "${CLAUDE_SKILL_DIR}/ai-knowledge/steps-library.json" --ai-format
```

rc 0 — все шаги в библиотеке; rc 1 — шаг не из библиотеки (отчёт с подсказками) или ошибка структуры: строка без ключевого слова, сценарий без шагов, файл без сценариев. Проверяется шаг на любом ключевом слове и в любом виде сценария, условия `Если` и `ИначеЕсли` тоже; блоки `"""` не разбираются ([[vendor-patches]], `gherkin_walk.py`). Красный валидатор — в клиент не идём. Первая строка `.feature` обязана быть `# encoding: utf-8`, вторая `# language: ru`.

## Слой 2 — харнесс `plugin/tools/vanessa/run-scenario.py` (прогон)

Config-agnostic обёртка над vanessa-runner: берёт `.feature` + тестовую базу из `.v8-project.json` проекта, зовёт `vrunner test vanessa`, вердикт по junit-отчёту.

```bash
python plugin/tools/vanessa/run-scenario.py <feature> --project <dir> [--base <id>] [--dry-run]
```

- База — `default` из `.v8-project.json` (или `--base`); **только зарегистрированная** (незарегистрированная = боевая, отказ кодом 2).
- **Учётка базы — ТОЛЬКО из окружения**: `ONEC_DB_USER_<id>` / `ONEC_DB_PWD_<id>` (в `.v8-project.json` и в вывод не попадает, [[secrets-and-production-database]]); нет — интегрированная аутентификация.
- Вердикт: `pass` — только по непустому junit-отчёту без падений; `fail` — падение/ошибка; **«не выполнен»** — отчёт пуст (клиент не прошёл аутентификацию или не стартовал) либо за `--timeout` его не появилось — это НЕ pass.
- Код выхода: 0 pass, 1 fail/не выполнен, 2 нет feature/toolchain/базы.

## Toolchain (OneScript + vanessa-runner + vanessa-add)

vanessa-runner — пакет OneScript; сам сценарий гоняет `bddRunner.epf` из vanessa-add. **С 30.10.2026 ставится установщиком плагина** (решение владельца), один раз на машину, в папку программ плагина:

```bash
python "${CLAUDE_PLUGIN_ROOT}/tools/setup/install-tools.py" --only onescript vanessa-runner vanessa-add vanessa-automation
```

Что ставится (`plugin/tools/setup/tools-manifest.json`, записи необязательные — обычная установка их не тянет): OneScript 2.2.0 (`OneScript-2.2.0-win-x64.zip`, GitHub, SHA256 совпадает с суммой, которую публикует GitHub), пакеты `vanessa-runner` 3.0.2 и `add` 6.9.5 (`.ospx` с закреплёнными суммами; ставит их `opm` самого OneScript). **Предел цепочки поставки:** зависимости vanessa-runner (около 40 пакетов OneScript) `opm` берёт из каталога hub.oscript.io по версиям из метаданных пакета — без сумм; каталог отвечает только по `http`, поэтому у пакета `opm` с закреплённой суммой это допустимый адрес. `lib/` OneScript изменяемая (`opm` обновляет в ней пакеты) — «установлено» сверяет остальное. Проба 30.10.2026: чистая установка из локальных копий — 3 из 3, повтор — «уже установлена».

**Движок сценариев — Vanessa Automation 1.2.043.45** (`vanessa-automation-single.epf`, BSD-3-Clause, сумма — та, что публикует GitHub). Харнесс находит его (`$ONEC_VANESSA_EPF`, иначе `${CLAUDE_PLUGIN_DATA}/bin/vanessa-automation/`) и передаёт vrunner ключом `--bddrunner-path`, а с ним — файл настроек `<отчёт>.vaparams.json`: `ВыполнитьСценарии` (без него движок только открывается и ждёт кнопку — журнал базы, проба 30.10.2026), `ЗавершитьРаботуСистемы`, закрыть клиент тестирования; значения — строки «Истина». vrunner сливает файл с настройками отчёта и отдаёт движку ключом `VBParams`. Если движок не закрыл клиент, а отчёт готов, или истёк `--timeout` (900 с), клиент закрывает сам харнесс: только процессы этой базы с `/TESTMANAGER` или `/TESTCLIENT`, сеанс человека в той же базе не трогается. **Первый запуск движка из новой папки платформа спрашивает «Предупреждение безопасности»** — один раз подтвердить в окне клиента, иначе прогон уйдёт в таймаут с вердиктом «не выполнен». **Почему не add 6.9.5** (2023): его `bddRunner` превращает режим совместимости в число заменой «Версия» → «» и «_» → «.» и падает «Преобразование значения к типу Число» на режиме «Не использовать» (режим равен версии платформы) и на английских конфигурациях («Version…») — проба 30.10.2026 на тестовой базе мастера. **Версия платформы** для vrunner берётся из `v8path` реестра (у базы, иначе общий); нет — отказ: без версии vrunner взял новейшую 8.5.1 на базе 8.3.27, и клиент повис.

Вручную (без установщика): распаковать `OneScript-<ver>-win-x64.zip` в папку, затем `oscript lib/opm/src/cmd/opm.os install vanessa-runner` и `… install add` (без add vrunner падает «Не найден каталог установки vanessa-add», если движок не передан ключом `--bddrunner-path`; харнесс его передаёт — вывод из исходника vanessa-runner, живьём не проверялось).

Харнесс ищет OneScript через `ONEC_ONESCRIPT_HOME`, затем в папке программ плагина (`${CLAUDE_PLUGIN_DATA}/bin/onescript`), затем `D:/tools/onescript*` и PATH. `opm.bat`/`vrunner.bat` зовут `oscript` без пути — вне PATH их зовут через `oscript <lib>/.../main.os` напрямую (как делает харнесс).

## Живая проба (30.10.2026)

На файловой тестовой базе мастера: зелёный сценарий — `pass` (тестов 1, падений 0), красный — `fail` (тестов 1, падений 1), клиент закрывает сам движок, код vrunner 0. Журнал базы показывает, что делал движок: события `VanessaAutomation.*` — первое место, куда смотреть при зависании.

Первая проба: пилот (read-only: пауза + закрыть окна) провалидирован (rc 0) и прогнан `run-scenario.py` на серверной тестовой базе проекта (платформа 8.3.27.2214): **toolchain и харнесс сквозь запускают 1С:Предприятие против базы** — путь жив. Платформа ответила «Пользователь ИБ не идентифицирован»: база требует учётку, которую сессия не вводит (пароль — прерогатива владельца, [[secrets-and-production-database]]). С заданными `ONEC_DB_USER_<id>`/`ONEC_DB_PWD_<id>` сценарий выполнится в клиенте; это шаг владельца. Конкретный проект и база пробы — в журнале проекта/мастера, не в этом доке ядра.

## Границы

- UI-приёмка сценарием, **не** замена YAXUnit (юнит-логика).
- Тестовая база, не боевая; данные тестовые ([[personal-data-masked-from-1c]]).
- Журнал проверки самой доработки на проекте — в репозитории проекта, а не ядра ([[journal-placement]]).
- Детерминированная часть (валидатор valid/invalid, сборка команды харнессом, отказы) — регресс `contour-tests` §60, §151 и §152; живой прогон сценария — на тестовой базе с учёткой владельца.
