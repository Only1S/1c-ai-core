# MCP-серверы для работы с 1С

Найдены через каталог open-source 1С-проектов **openyellow.org** (сообщество OpenBSL). Четыре MCP-сервера под 1С.

**Окружение (проверено на машине-хосте):** Java 17+ ✓ (первой в PATH — Liberica JDK 21.0.11, 18.09.2026); платформа 1С 8.3.27.2214 (`C:\Program Files\1cv8\8.3.27.2214`) ✓; EDT-workspace проекта (напр. `D:\EDT\PROJECT`); конфигурация — текущего проекта. Уже подключён MCP [[v8std-mcp-server]] (стандарты/диагностики).

> ⚠️ Это база `dev_core`. Пути на **выгрузку исходников** и **базы данных** ниже указаны как плейсхолдеры `<КОРЕНЬ_ВЫГРУЗКИ>\src` / «тестовая база проекта» — при подключении к конкретному проекту подставить реальные значения (см. `CLAUDE.md` → «Подключение проекта» и [[plugin-in-project]]).

## Рекомендованный стек (для «хорошо изучить 1С»)
1. **mcp-bsl-platform-context** — синтаксис и объектная модель платформы. Дополняет v8std (тот про *стандарты/диагностики*, этот про *API платформы*). Поставить проще всего: `java -jar mcp-bsl-context-*.jar --platform-path "C:\Program Files\1cv8\8.3.27.2214"`. Низкий риск.
2. **EDT-MCP** — для изучения и правки конфигурации проекта прямо в EDT (читать модули, метаданные, call-hierarchy, искать по коду). Ставится как плагин в EDT (Help → Install New Software → `https://ditrixnew.github.io/EDT-MCP/`). Нужна EDT 2025.2+.
3. **1c-mcp-toolkit** — когда нужно запрашивать данные/метаданные у живой базы проекта (мощнее OData). ⚠️ Содержит `execute_code` — на боевой базе использовать крайне осторожно/только чтение; лучше на копии.

`1c_mcp` — альтернатива toolkit, но требует развёртывания расширения в конфигурации; без явной нужды пропускаем.

## Статус установки (в базе dev_core)
- ✅ **bsl-platform-context v0.3.2** — проверен (поиск `HTTPСоединение` → реальные методы платформы). JAR: папка программ плагина, `bin/bsl-platform/mcp-bsl-context.jar` (ставит установщик программ). Сервер плагина `bsl-platform` (stdio). 5 инструментов: search/info/getMember/getMembers/getConstructors.
  - ⚠️ **Кодировка (важно):** Java 17 на русской Windows по умолчанию CP1251 → кириллица в stdin/stdout ломалась (`HTTPСоединение`→`HTTPРЎРѕ…`). Исправлено добавлением в args JVM-флагов: `-Dfile.encoding=UTF-8 -Dsun.stdin.encoding=UTF-8 -Dsun.stdout.encoding=UTF-8`. После этого кириллица корректна. (UTF-8 по умолчанию только с Java 18+, JEP 400.)
  - ⚠️ SSE-режим в этой среде не стартует (Netty не может создать loopback-селектор — ограничение песочницы/хоста); для MCP это неважно, т.к. используется stdio.
  - 📁 **Лог сервера:** logback внутри jar пишет `mcp-server.log` (+ ротация `.gz`) в **cwd процесса** = корень проекта; путь переопределяем свойством `${LOG_FILE}` — в args добавлен `-DLOG_FILE=<ONEC_KERNEL_HOME>\logs\mcp-server.log` (контракт подтверждён живым зондом 12.07.2026: файл создаётся по заданному пути вкл. автосоздание подпапки, в cwd ничего не остаётся; вступает в силу с перезапуска сессии).
  - 💥 **Аварийные дампы JVM (урок одного из экземпляров).** stdio-JVM `bsl-platform` упала через несколько секунд после старта: на машине кончился лимит commit. Эргономика JVM по умолчанию берёт `MaxHeapSize` около четверти RAM (на хосте с 32 ГБ — 8 ГБ) и `CICompilerCount=12`, а каждая сессия Claude Code поднимает свою JVM и делит commit с EDT. Дампы `hs_err_pid*.log` и `replay_pid*.log` (сотни КБ, внутри имя пользователя и PATH) легли в cwd — корень проекта. Теперь в args: `-XX:ErrorFile=<ONEC_KERNEL_HOME>\logs\hs_err_pid%p.log` и `-XX:ReplayDataFile=<ONEC_KERNEL_HOME>\logs\replay_pid%p.log`. Оба флага в Java 21.0.11 помечены `{product}` (зонд `java -XX:+PrintFlagsFinal -version`, 19.09.2026), `UnlockDiagnosticVMOptions` не нужен, JVM с ними стартует. `-Xmx` и `-XX:CICompilerCount` **пока не заданы**: слишком малый `-Xmx` уронит загрузку справки платформы, ставить только после замера установившегося RSS.
- ⚠️ **EDT-MCP: на 30.10.2026 в текущей установке EDT 2026.2.2 стоит 2.22.1** (`bundles.info` `1C_EDT 2026.2` от 30.10 11:32: `com.ditrix.edt.mcp.server,2.22.1,…,4,false` — бандл установлен, живым ответом не подтверждён, EDT выключена; сервер молчит — сперва проверить запуск EDT и порт; прежней установки 2026.1 больше нет; подробности — [[edt-plugins-installed]]). Прежнее состояние: в EDT 2026.1 20.10.2026 стоял **2.21.1** (замер 29.10.2026), до того — **v2.20.1** (сверка 16.10.2026: `bundles.info` установки «1C_EDT 2026.1» → `com.ditrix.edt.mcp.server,2.20.1,…,4,false` — бандл установлен, `4,false` — ленивая активация, а не доказательство работы; прежняя оговорка «собирается под 2026.2, в 2026.1 живьём не проверено» в силе до первого успешного smoke — в 2026.1 живым ответом сервера пока не подтверждён. Опись инструментов сервера снята на 2.17.1 и под 2.20.1 живым `tools/list` НЕ перепроверялась) — сервер слушает `http://localhost:8765/mcp` (protocol 2025-11-25, status running). Прописан в `.mcp.json` как `edt-mcp` (type http). Требует, чтобы **EDT была запущена** с открытым проектом. Активируется после перезапуска Claude Code.
  - ⚠️ **Порт EDT — свойство инстанса**, не константа: `8765` — лишь дефолт плагина, в реальных проектах порт свой (`<порт>`). Одна запущенная EDT = один сервер; при работе с несколькими базами (цель/источник переноса/тест/UT) регистрируются **несколько** серверов (`edt-mcp`/`edt-src`/`edt-test`/`edt-ut`) на своих портах. Порт задаётся переменной `EDT_MCP_PORT` манифеста (см. [[plugin-in-project]]); где плагин хранит порт в воркспейсе и почему правка prefs без рестарта EDT сокет не переносит — [[edt-mcp-pitfalls]].

## Каталог openyellow.org — дополнительные инструменты
Инструменты под среду без node/cargo/python (готовые Windows-бинарники).

### ✅ bsl-analyzer (itrous) — машинный линтер BSL
- Назначение: статический анализатор/линтер + LSP + MCP для BSL (архитектура rust-analyzer: Salsa/Rowan/HIR/CFG). Машинные диагностики (console/jsonl); дополняет v8std (правила) и edt-mcp (маркеры).
- Установка: готовый нативный `.exe` (Rust, **cargo не нужен**). `bsl-analyzer-windows-amd64.exe` → папка программ плагина, `bin/bsl-analyzer/bsl-analyzer.exe` (ставит установщик программ). Это **лаунчер**: при первом запуске сам тянет/проверяет реальный бинарник (~75 МБ: 0.4.0 = 78 577 664 Б, сверено 29.10.2026 — размер брать у ассета релиза, версия движка намеренно не пинится; движок 0.4.0 лаунчер 0.3.2 подтянул сам 26.10.2026, лаунчер обновлён до 0.4.0 29.10.2026) `bsl-analyzer-app` в кеш `%USERPROFILE%\.bsl-analyzer\bin\`. ⚠️ Версия app **плавает** (лаунчер автообновляется) — номера в доках не пинить, актуальную смотреть `bsl-analyzer.exe --version` / `logs\weekly-report.md` (дрейф ловит weekly-регламент). Версию фиксировать через `BSL_ANALYZER_VERSION` / `--launcher-use`; обновление app — `--launcher-update`. ⚠️ Если докачка app падает по таймауту — качать ассет `bsl-analyzer-app-windows-amd64.exe` вручную (`curl -L --retry 8 -C -`), сверить sha256 с `checksums.txt` релиза и положить в кеш как `bsl-analyzer-<ver>` + копию `bsl-analyzer-app.exe`, обновив `current` и `.app-version` (см. [[worklog]] 07.07.2026).
- Запуск: `bsl-analyzer.exe analyze -s <папка-исходников> --format jsonl`. Исходники конфигурации на диске: `<КОРЕНЬ_ВЫГРУЗКИ>\src\...` (выгрузка EDT). Формат вывода — записи `{type:"file", path, diagnostics:[{code,message,severity,start_line}], metrics}`.
- ⚠️ Scoping: прогон по ОДНОЙ папке даёт ложные `UnresolvedMethodCall`/`QueryToMissingMetadata` (не видит общие модули/документы вне папки) и раздувает `UnusedLocalMethod`/`UnusedParameters` обработчиками событий формы. Для точного baseline гнать по корню `src`.
- **Пример кросс-проверки (прошлый проект):** машинный прогон по пакетной папке модулей ПОДТВЕРДИЛ ручной аудит: `DeprecatedPlatformApi` (ТекущаяДата→ТекущаяДатаСеанса), `SelfAssign`, `MissingCodeTryCatchEx` (тихое подавление ошибок), `CommentedCode`, `CognitiveComplexity`, локализация (`MultilingualStringHasAllDeclaredLanguages`), query-style (`JoinWithVirtualTable`/`QueryNestedFieldsByDot`). То есть линтер — хорошая машинная проверка ручных находок.
- **Формы вывода и ловушки** (проверено в одном из экземпляров на 0.2.67): полный список диагностик дают только `--format jsonl` (в stdout) и `-r sarif`; `console`, `json` и `-o` без репортера возвращают одни счётчики. В jsonl `start_line` считается с 0, в SARIF `startLine` — с 1. `-r sarif` без `-o` молча кладёт `bsl-analyzer.sarif` в текущий каталог (контур `validate-bsl` вызывает с `-o`). Ложный `TypeMismatch` у `AccessRight(<право>, <объект из Metadata.X.Find()>)` есть и в типовых модулях `AccessManagement` БСП: свой код ради него не переписывать, в белый список контура не вносить, сверять валидатором EDT.
- MCP-режим (`bsl-analyzer.exe mcp install ...`) — включать после калибровки профиля правил, чтобы не плодить шум.
- ⛔ **Подавление у источника ломает линтер на кириллице — и это ЛОЖНЫЙ ЗЕЛЁНЫЙ.** Комментарии `// BSLLS:<Rule>-off` / `-on` парсер подавлений режет **по байтам, а не по символам**, и на многобайтовом символе падает: `panicked at crates\ide-diagnostics\src\suppression.rs: end byte index … is not a char boundary; it is inside 'я'`. В модуле 1С кириллица есть почти всегда → анализ обрывается, а вызывающий видит «ошибок нет». Проверено зондом в живом экземпляре (17.07.2026, v0.2.59). **Вывод: не ставить inline-подавления в файлах с кириллицей**; нужное исключение — через конфиг диагностик, а не комментарием в коде. Контур `validate-bsl` (PostToolUse) читает SARIF: при падении отчёт пуст, и это неотличимо от «чисто» — второй случай того же класса, что фикс `--changed-files` в 2.5.0.

### ✅ code-index-mcp (Regsorm) — индексатор кода
MCP-индексатор кода (Rust, готовые Windows-бинарники `code-index.exe`+`bsl-indexer.exe`, без node/cargo) → папка программ плагина, `bin/code-index/` (версия и контрольная сумма — в манифесте программ `plugin/tools/setup/tools-manifest.json`; с v1.0.0 имена инструментов и форма ответов объявлены стабильными — **но апстрим это обещание уже нарушал**: в 1.12.0 сняты виды обращений `template`, `common_template`, `picture` и параметр `owner_ref` у `extract_code_usages` (разбор CHANGELOG 16.10.2026), поэтому совместимость сверять по `get_stats`/`health` (`data_version`), а не по обещанию). Индексируется выгрузка конфигурации проекта (`<КОРЕНЬ_ВЫГРУЗКИ>\src`). Пример объёма (прошлый проект): **2762 файла, 26 902 функции, 288 107 вызовов** (индекс `…\src\.code-index\index.db`, ~74 МБ). Прописан в `.mcp.json` как `code-index` (stdio, `bsl-indexer.exe serve --path <КОРЕНЬ_ВЫГРУЗКИ>\src`, env `CODE_INDEX_HOME`). Подхват после **перезапуска Claude Code**.
- **Демон обязателен для FTS-инструментов MCP** (`search_function`/`get_callers`/`get_call_tree`/…): `serve` — read-only клиент к демону. Запуск: `bsl-indexer daemon run` (читает `…\code-index\daemon.toml`: `[[paths]] path=…\src, alias='default', language='bsl'`). MCP-инструмент `get_stats` и CLI-команды (`stats -p …`, `search-function -p …`) работают и БЕЗ демона (читают индекс напрямую). ⚠️ В CLI подкоманда называется `stats`, а не `get_stats`.
- **Постоянная работа:** общий индексатор плагина — один на машину; автозапуск при входе — файл `ones-core code-index.vbs` в папке Автозагрузка, его ставит `/ones-core:setup` по согласию (`code-index-daemon.py autostart on`). Scheduled Task не подходит без прав админа; папка Автозагрузка — без админа. Управление: `code-index-daemon.py start|stop|restart|status|reload`, убрать выгрузку — `remove --src` ([[code-index-outside-sources]]). Первый запуск с `language='bsl'` строит полный BSL-слой (call graph, data_links, form_events, объекты, формы) — далее кэш в `index.db`, watcher инкрементальный.
- ⚠️ Команды требуют `-p/--path <корень>` (индекс лежит рядом с исходниками, не в cwd; без `--path` падает «БД readonly»). Переиндексация: `bsl-indexer.exe index <КОРЕНЬ_ВЫГРУЗКИ>\src` (5–6 с). **20 MCP-инструментов** на каталоге без исходников 1С (зонд `tools/list`, v1.2.3 — на заглушке мастера); с v1.2.0 при `--path` на исходники 1С добавляются 1С-инструменты (по релиз-нотам — 32; на реальных исходниках не проверено). Для рёбер «форма → модуль объекта» уже проиндексированную базу переиндексировать `bsl-indexer index <путь>` без `--force` при остановленном демоне. Базовый набор: поиск и чтение (`find_path`, `find_symbol`, `list_files`, `read_file`, `stat_file`, `get_file_summary`), символы (`search_function`/`get_function`, `search_class`/`get_class`, `get_imports`), граф (`get_callers`, `get_callees`, `get_call_tree`), поиск по тексту и телам (`grep_code`, `grep_text`, `grep_body`, `search_text`), служебные (`get_stats`, `health`) — по выгрузке на диск — **дополняет edt-mcp** (тот — по живой модели EDT, этот — быстрый файловый граф без Eclipse).
- ⚠️ Артефакт `.code-index` по умолчанию пишется внутрь `src` выгрузки EDT. **Так не храним:** каталог индекса выносится junction'ом в папку проекта Claude Code (`<проект>\.code-index`, при нескольких выгрузках — `<проект>\.code-index\<алиас>`), в `src` остаётся только ссылка — исключить из git и EDT. Правило и команды — [[code-index-outside-sources]].
- **Проект с расширениями (CFE):** в `daemon.toml` — **отдельный алиас на хост и на каждое расширение** (`default` + `<расширение1>`/`<расширение2>`…, каждый со своим `path` на свой `src`) — граф кода расширений ищется так же, как хостовый (паттерн живого экземпляра).
- **Один сервер на все алиасы — `serve --config`.** Вместо N серверов или `serve --path alias=dir` в `.mcp.json` можно дать `bsl-indexer.exe serve --config <данные плагина>\code-index\daemon.toml`: репозитории и алиасы берутся из `[[paths]]`, в вызове инструмента передаётся `repo=<alias>` (без него — `default`). Флаг подтверждён `serve --help` на 1.2.3; если заданы и `--path`, и `--config`, побеждает `--path`, конфиг игнорируется. Так в одном из экземпляров живёт хост с тремя расширениями. Два наблюдения оттуда (на 0.44.3, на 1.2.3 не проверено): при `http_port = 0` демон брал случайный порт, и MCP-клиент устойчиво видел `daemon_offline` при живой базе — лечилось закреплением порта; без `CODE_INDEX_HOME` демон не читает `daemon.toml` (её задаёт автозапуск плагина). Как клиент находит порт демона — не выяснено: у общего индексатора плагина `http_port = 0`, а два индексатора с одним фиксированным портом на одном хосте столкнутся.
- `serve --transport http` по умолчанию слушает порт `8011` (`--help` 1.2.3) — тот же, что у `1c-forms`. При переходе на HTTP задавать `--port` из блока портов экземпляра ([[server-ports-per-project]]).

### ✅ cc-1c-skills (Nikolay-Shirokov) — инструментальные скиллы 1С

Для прогона на файле класть временную копию в каталог, доступный этой учётной записи, только с тестовыми или обезличенными данными ([[secrets-and-production-database]]), и удалять сразу после прогона. К файловой базе не относится. Имя служебной учётной записи на стенде не проверялось.

- **Запуск из командной строки 1С** — возможность самой обработки (появилось в v1.7.1, README_FULL «Автоматический запуск обработки из командной строки»). Обработка открывается через `/Execute` и сразу поднимает встроенный сервер по параметру `/C "startup;..."`:
  ```powershell
  1cv8.exe ENTERPRISE /S "<сервер>\<база>" /WA /Execute "<путь>\MCP_Toolkit.epf" /C "startup;mode=embedded;port=6003;auth=windows"
  ```

Неуказанное берётся из сохранённых настроек обработки. **Вход — `/WA` + `auth=windows`**: вариант `/P` + `pwd=` кладёт пароль в командную строку и скрипт — против [[secrets-and-production-database]].
  ⚠️ `ENTERPRISE` — живой сеанс, а не пакетный запуск: `Start-Process -Wait` из [[designer-batch-runs]] на нём повиснет навсегда; готовность сервера — по порту и `/health`.
  **Запуск — команда `/ones-core:toolkit [база] [порт]`** (скрипт плагина `tools/1c/run-1c-toolkit.py`, с core-v4.1.0; аргументы — с core-v4.3.0): открывает тестовую базу из `.v8-project.json` скиллом `db-run` с `/WA` и `auth=windows`, ждёт порт (до 3 мин) и `/health`; если порт уже слушает — второй сеанс не открывает. Автозапуска нет.
  **Остановить сеанс** — штатно, REST `POST /api/close_1c_session` (или MCP-инструмент того же имени): обработка сама закрывает свой сеанс. Процессы 1С не убивать (`taskkill` по PID — крайний случай и только для своего сеанса на своей базе, по пути базы — [[designer-batch-runs]]).
- **`ВнешниеОбработки.Создать(<путь>, Ложь)` виснет headless.** Небезопасный режим (`БезопасныйРежим = Ложь`) поднимает предупреждение безопасности внешней обработки — в сеансе тулкита (нет интерактива) `execute_code` не возвращается до таймаута шлюза. Для доверенной тестовой обработки брать `Истина` (безопасный режим; строковой/числовой логике он не мешает). Проверено на приёмке обфускатора (веха 105): с `Ложь` — таймаут, с `Истина` — мгновенно.
- **Переподключить проектный MCP-сервер в середине сессии программно нельзя.** `reconnect_session_connector` работает только с коннекторами; проектный `1c-toolkit` после подъёма бэкенда переподключает лишь пользователь через `/mcp`. Обход без ожидания пользователя — звать HTTP-эндпоинт тулкита напрямую (`http://127.0.0.1:<порт>/mcp`, MCP JSON-RPC: `initialize` → `notifications/initialized` → `tools/call`; ответ — SSE, склеить строки `data:`). Мини-клиент на `urllib` — приём вехи 105.
  Там же с v1.7.0: `restart_1c_session` (сеанс перезапускается сам, например после обновления конфигурации) и `close_1c_session` (закрывает сеанс для монопольного доступа и отдаёт готовую команду лаунчера). При **первом** перезапуске платформа может спросить подтверждение запуска внешней программы — это разовое ручное действие.
- **Почему версия не ниже 1.8.0:** в 1.8.0 закрыт обход запрета опасных операций через `Выполнить`/`Вычислить`/`Execute`/`Eval`, флаги опасных операций переживают программный перезапуск, добавлены токен доступа (`Authorization: Bearer`) и выбор интерфейса привязки. Флаги автоматического разрешения опасных операций по умолчанию выключены — не включать.

- **Барьер ядра**: `guard-destructive` повешен и на `mcp__ssh-mcp__.*` — удалённая команда (параметр `command`) проверяется теми же правилами, что `Bash`; `localPath` у `sftp-upload-file`/`sftp-download-file` не может быть секретом или учётными данными, скачивание — только во временную папку (самотест §31).
- **Живая проба в сессии Claude Code (приложение для Windows, 20.10.2026)**: инструменты `mcp__ssh-mcp__*` появились после перезапуска сессии; `list-connections`, `read-command` (`hostname`, `df`) и `run-command` с безопасной командой (`systemctl is-active …`) — ответы без вопросов; удалённый `rm -rf` и `sftp-download-file` в каталог проекта отклонил **барьер ядра** до сервера. **Окна подтверждения нет**: на опасную команду (`find … -delete`) и на `sftp-download-file` во временную папку сервер получил `APPROVAL_DENIED` («User did not approve»), владелец окна не видел — клиент отвечает отказом сам. Итог: через `ssh-mcp` проходят только классы «только чтение» и «безопасные»; опасное и `sudo` — прежним путём (вкладка терминала, пароль владельца). `sftp-download-file`/`sftp-upload-file` без `transferRoot` в конфиге сервер отклоняет и сам. `read-command` пропускает только белый список: `systemctl is-active` для него «safe» — такое через `run-command`. Команду с циклом и подстановкой `$(…)` сервер не разбирает и относит к опасным — без окна подтверждения это отказ; писать простыми командами через `;`. Вывод проходит маскировку по энтропии: не-секретный кусок (в пробе — часть пути к `usr1cv8.keytab` в `systemctl show -p Environment`) может прийти как `[REDACTED:entropy:N]`.

### 🧪 chrome-devtools (ChromeDevTools) — наблюдатель за веб-клиентом 1С (пилот с 14.10.2026)

**MCP-сервер** `chrome-devtools-mcp` v1.12.0 (пин; обновлено 29.10.2026 с 1.11.0, до того 16.10.2026 с 1.10.1), Apache-2.0, официальный проект команды Chrome DevTools. Подключён в **профиле «наблюдатель»**: читает консоль, сеть и трассировки живого Chrome через его отладочный протокол (CDP по пайпу), но **не действует** в странице. Действия в веб-клиенте 1С остаются за скиллом `web-test`.

**Зачем — измеренный пробел:** в `web-test` **ноль** обработчиков консоли и **ноль** трассировок/heap (грепом по скиллу, 14.10.2026); сетевых обработчиков четыре, но они служат детектором «страница успокоилась», а не журналом. То есть ошибки JS в управляемой форме, HTTP-обмен с публикацией и время открытия формы не наблюдались ничем.

**Проверенный контракт** (живой хендшейк, не README): версия сервера `chrome_devtools 1.11.0` (сверка 16.10.2026; на 1.10.1 было то же при 20 инструментах), **22 инструмента** вместо 59 по умолчанию, пишущая категория Input отсутствует полностью, `evaluate_script` отсутствует. Якоря в `tools/checks/mcp-smoke.py` — `list_console_messages`, `list_network_requests`, `performance_start_trace`.

**Профиль в `.mcp.json`** (флаги проверены `--help` самого бинарника — они **camelCase**, а не kebab-case):
`--headless --isolated --categoryInput=false --javascriptEvaluation=false --redactNetworkHeaders=true --usageStatistics=false --performanceCrux=false --allowedUrlPattern "http://localhost:*/*" --allowedUrlPattern "http://127.0.0.1:*/*"`, плюс `CHROME_DEVTOOLS_MCP_NO_UPDATE_CHECKS=1` и `CHROME_DEVTOOLS_MCP_NO_USAGE_STATISTICS=1` в `env`.

- **Транспорт — stdio, порт НЕ поднимается** (`pipe: true` внутри сервера): конвенция портов ([[server-ports-per-project]]) не затрагивается. Порт нужен только в режимах `--browserUrl`/`--wsEndpoint`/`--autoConnect` (9222, общий на машину) — такие режимы нам противопоказаны.

  - **`pageId` обязателен.** `--pageIdRouting` включён по умолчанию, и инструменты страницы (`navigate_page`, `list_console_messages`, `list_network_requests`, `performance_*`) **отказывают** без `pageId`.   - **Запись файлов ограничена каталогом TEMP**, если клиент не согласовал MCP roots (`--filesystemRoot`/`--workspace`, дефолт — временный каталог). `--allowUnrestrictedPaths` помечен deprecated — не использовать.
  - **`--allowedUrlPattern` требует Chrome 149+** (у нас 155) и запирает и навигации, и подресурсы.
