# Правило: четыре дисциплины кодинга (по мотивам Карпатти)

Синтез принципов из наблюдений Андрея Карпатти о типовых ошибках LLM в коде (источник-вдохновение: github.com/multica-ai/andrej-karpathy-skills, 13.07.2026; репозиторий без лицензии — текст не копируется, принципы пересказаны своими словами и спроецированы на 1С). 17.10.2026 дополнено идеями конституции [swarm-forge](https://github.com/unclebob/swarm-forge) (тоже без лицензии — пересказ; сопоставление — [[external-skills-review]]). Смещение — в сторону осторожности; для тривиального — по здравому смыслу.

## 1. Думать до кода: допущения — вслух
Не додумывать молча. Перед реализацией: явно назвать свои допущения (не уверен — спросить, [[questions-as-options]]); несколько трактовок задачи — показать все, а не выбрать тихо; видишь путь проще заказанного — скажи и обоснуй (возражать — нормально); что-то непонятно — остановись и назови, что именно. В ядре это усилено консилиумом ([[five-role-design-review]]) и гейтом фактов ([[work-through-tools]]) — но принцип действует и в мелких правках, где консилиум не собирается. **Ожидаемой раскладки нет — стоп:** нет выгрузки или проекта EDT, нет тестового расширения, YAXUnit не подключён, валидатор не отвечает — остановиться и сказать, чего не хватает, а не работать молча в другом месте или строить обход.

## 2. Минимализм: ничего спекулятивного
Минимум кода, решающего задачу. Не делать: фич сверх запрошенного; абстракций под одноразовый код (общий модуль ради одного вызова, «универсальный» параметр «на вырост»); «гибкости/настраиваемости», которую не просили; обработки невозможных ситуаций (Попытка вокруг того, что не падает). Самопроверка: «сеньор 1С назвал бы это переусложнением?» — да → упростить. Написал 200 строк там, где хватит 50 — переписать. Дополняет [[naming-and-module-design]] (компактно, без дублей) и стандарт «сначала штатное БСП/платформа». **Самодельная замена штатного проверочного инструмента** — тоже спекулятивный код: своя проверка регулярками при живых BSL LS, `1c-standards`, v8std, `*-validate`. Нужного инструмента нет — сказать об этом ([[full-checker-set-before-done]]), а не писать его подобие и выдавать за проверку.

## 3. Хирургический дифф: трогать только своё
Правя существующий модуль: не «улучшать» соседний код, комментарии и форматирование; не рефакторить неломаное; повторять стиль модуля, даже если сам писал бы иначе; заметил чужой мёртвый код — назови в отчёте, но не удаляй без запроса ([[ask-before-changing]]). Свои сироты — убирать: переменные/процедуры/серверные вызовы, которые осиротели ИЗ-ЗА твоей правки, вычищаются в той же правке. Тест: каждая изменённая строка диффа прослеживается к запросу пользователя. **То, что порождает инструмент, руками не правится:** выгрузка платформы, `ConfigDumpInfo.xml`, сгенерированные индексы и счётчики, `package-lock.json` и другие манифесты — перегенерировать тем же инструментом. (Не конфликтует с [[two-axis-code-review]]: там приведение к стандартам — явно заказанная работа.) **Исключение — замечания проверок** (распоряжение владельца 05.11.2026): прежние ошибки и предупреждения анализатора в своём коде правленного модуля исправляются отдельным шагом той же задачи, а не откладываются ([[full-checker-set-before-done]] п.9а); код поставщика на поддержке — только списком владельцу.

## 4. Задача → проверяемая цель
Формулировку превращать в верифицируемый критерий до начала работы: «добавь проверку» → «тест на невалидные входы падает, потом проходит» (YAXUnit, [[task-recipes]] §12); «почини баг» → «тест, воспроизводящий баг, красный → зелёный»; «отрефакторь» → «весь набор чекеров зелёный до и после» ([[full-checker-set-before-done]]). Многошаговое — коротким планом «шаг → чем проверю». Сильный критерий позволяет замкнуть цикл самостоятельно; слабый («сделай чтобы работало») — это вопрос пользователю, а не задача.

**Петля среза** ([[vertical-task-slicing]]): одно поведение за раз — тест YAXUnit на это поведение, который упал бы на правдоподобной ошибочной реализации → красный → минимальный код до зелёного → чистка при зелёном наборе, без нового поведения → следующий срез. Не писать несколько поведений впрок с тестами «потом»; функциональный кейс не заменяет юнит-тест ядра. Где тест первым невозможен (форма без логики, разовый перенос данных) — сказать, чем проверено вместо него. **Тяжёлые проверки — по одной:** загрузка в тестовую базу, YAXUnit, полная проверка EDT и полный прогон BSL LS на одной базе и одном проекте параллельно не гонять — делят базу и память и дают ложные провалы.

**Правило работает, если:** в диффах меньше несвязанных изменений, меньше переписываний из-за переусложнения, а уточняющие вопросы приходят ДО реализации, а не после ошибки.

**Принуждение (с 4.7.0):** напоминание каждого хода — строка в `plugin/hooks/tools-gate.md` (ссылка на правило и фрагмент «хирургический дифф» держит `contour-tests` §24). Сами дисциплины автоматически не проверяются.
