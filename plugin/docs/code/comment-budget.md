# Бюджет комментариев в модулях 1С

**Правило.** В своём коде (модули с префиксом доработки проекта):

- описание метода — **одна строка**: что метод делает;
- между описанием и секциями `Параметры:` / `Возвращаемое значение:` **нет абзацев прозы**;
- внутри тела метода **нет поясняющих комментариев** — ни отдельной строкой, ни в конце строки с кодом.
  Остаются только директивы анализаторов (`// @skip-check …`, `// BSLLS:<Правило>-off/-on`, подавления `// ACC:…` и `// АПК:…`),
  метки строк для перевода (`// @NON-NLS-1`, `// @query-part-1`, `// @Access-right-1`, `// @NStr-1`) и маркеры-заглушки;
- «почему так сделано», решения владельца с датами, номера замечаний, прежнее поведение —
  в журнал работы проекта (`docs-project/changelog.md`, в репозитории конфигурации — его собственный журнал по [[journal-placement]]), не в код.

Описание экспортных методов обязательно по std453 п. 2; у приватных — по std453 пп. 3–4, только
если назначение не следует из имени и параметров.

**Почему.** Правило и инструмент родились в живом экземпляре (распоряжение владельца 01.10.2026) и подняты в ядро бекпортом 16.10.2026. Замер в экземпляре в день появления правила: 23 модуля доработки, **707 нарушений** — около 460 комментариев в телах методов, 196 многострочных описаний, 51 абзац прозы в шапках, причём больше всего в самых правленых модулях: код обрастает обоснованием каждой правки, и это обоснование место в журнале, а не в теле метода. Тот же дефект независимо наблюдался во втором экземпляре — то есть он не специфика конфигурации, а свойство самого способа работы.

**Как применять.**

- Новый код сразу пишется по правилу. Перед сдачей правки — аудит изменённых модулей (инструмент лежит в ядре, `tools/1c/bsl-comment-audit.py`):
  `python <папка плагина>/tools/1c/bsl-comment-audit.py <файл.bsl> …` (в мастере ядра — `plugin/tools/1c/…`; папку плагина называет сообщение в начале сессии). Код возврата 1 — есть нарушения.
- Чистка: `python <папка плагина>/tools/1c/bsl-comment-audit.py --fix --out <папка> <файл.bsl> …`. Исправленные
  копии пишутся в `<папка>`, исходник не меняется. Без `--out` правка идёт на место — так только
  для Designer-XML-выгрузки; модули EDT-проекта грузятся через `write_module_source`
  ([edt-mcp-pitfalls](../tools/edt-mcp-pitfalls.md)).
- Инструмент отказывает, если изменилось хоть что-то кроме комментариев: сравнивается
  «отпечаток» строк без комментариев до и после. Многострочное описание он сокращает до первого
  предложения и печатает результат. Если предложение длиннее 120 символов — пишет «ВРУЧНУЮ»:
  такое описание формулируется вручную.
- **Не трогать вставки в типовые объекты.** Маркеры вида `// <--[автор]` … `// -->` в модулях
  конфигурации поставщика нужны для сравнения при обновлении типовой. Инструмент их не отличает
  от пояснений, поэтому он запускается только по модулям, целиком принадлежащим доработке.
- После чистки — полный набор проверок ([full-checker-set-before-done](../tools/full-checker-set-before-done.md)),
  а затем загрузка всех затронутых модулей в базы.

**Принуждение (с 17.10.2026):** проверка модуля после правки (`validate-bsl`) прогоняет этот аудит по строкам, которые записала правка (кусок правки или место `new_string`; новый файл — целиком), и при нарушении отдаёт блокирующий фидбек. Маркеры вставок в типовые (`// <--`, `// -->`, `//++`, `//--`) нарушением не считаются, чужие комментарии вне правки не трогаются. Запись модуля через EDT целиком (`write_module_source`) и правка через Bash или скрипты не проверяются — для них остаётся аудит перед сдачей. С 30.10.2026 инструмент видит и комментарий в конце строки с кодом: `//` внутри строкового литерала, в том числе многострочного, комментарием не считается, директива и маркер вставки в конце строки не нарушение, комментарий, стоявший в конце строки до правки, не судится (его записала не эта правка), `--fix` снимает только комментарий. Регресс — `contour-tests` §1c (и сам инструмент: три вида нарушений, директивы, `--fix --out` не трогает исходник) и §134.
