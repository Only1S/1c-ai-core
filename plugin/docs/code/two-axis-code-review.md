# Правило: ревью кода 1С — две оси, два вердикта

Присланный модуль 1С (общий, объекта, формы) или ветку доработки нужно прочитать и разобрать **по двум независимым осям**: соответствует ли код **стандартам 1С** и соответствует ли он **ТЗ** ([[design-before-code]]). Оси считаются отдельно и в один вердикт не сливаются.

**Why:** ревью «только по стандартам» пропускает самый дорогой класс дефектов — код чистый, оформлен по `std455`, все чекеры зелёные, а сделано **не то, что заказано**: половина требований не реализована, зато добавлена «гибкость», которую никто не просил. И наоборот: соответствие ТЗ не индульгенция для кода, нарушающего стандарты платформы. Это два разных вопроса к одному диффу, и ответ на один не заменяет ответа на другой. Слив осей в единый рейтинг всегда съедает более слабую находку.

## Комментарии в модулях: коротко и по факту (распоряжения владельца)

- **Никаких шапок-баннеров** (27.07.2026): в общих модулях и модулях объектов не писать вводный блок из строк `////////` с описанием назначения модуля, автора и истории. Модуль объясняет себя именем и структурой областей.
- **Документирующий комментарий метода — очень короткий** (29.07.2026): по факту параметры, возвращаемое значение и одна строка описания. Не пересказывать, откуда метод перенесён, почему возвращает именно это и как эволюционировал.
- **Без вводных простыней** в начале метода: то, что видно из кода, комментарием не дублируется.

Правила выработаны в живом экземпляре и подняты в ядро бекпортом 04.08.2026 — они про стиль работы, а не про конкретную конфигурацию.

## Фиксированная точка: что именно ревьюируем

**Зону ответственности задаёт дифф от merge-base ветки форка** ([[config-git-forks-and-merges]]): «внесено этой работой» — это ровно то, что показывает `git diff <merge-base>...<ветка>`. Это автоматизирует деление находок «моё / пред-существующее», которое [[full-checker-set-before-done]] п.2 требует делать руками.

Оговорки, без которых правило врёт:
- **Чекеры всё равно гоняются по ЦЕЛОМУ объекту**, а не по строкам диффа: анализ BSL **не диффо-локален** — сложность метода, дубль, мёртвый код, неиспользуемый экспорт видны только на модуле целиком. Дифф отвечает на вопрос «за что я отвечаю», а не «что запускать».
- **Радиус правки — не только код-вызовы.** Оценивая impact изменённого метода, учитывать **косвенные рёбра** (подписки, движения регистров, регламенты, динамические вызовы) — их call-graph не находит, а сломать они могут: правка общего модуля рвёт обработчик подписки без единого код-вызова к нему (карта видов рёбер — [[task-recipes]] §3). Инвентарь точек записи во внешний сервис — в два прохода: литералы адресов, затем методы-отправители, собирающие адрес конкатенацией (база + относительный метод), и все их вызовы; поиск по литералам такие методы пропускает (в одном из экземпляров первый проход не увидел отправителя с десятью вызовами).
- **Удаление или перетипизация объекта** (например, перечисление → справочник): нулевой grep по старому имени остатков не исключает. Искать функции-конвертеры «значение ↔ имя строкой» и их вызовы, `ЗНАЧЕНИЕ(Перечисление.…)` в текстах запросов, типы реквизитов форм; превью удаления в одном из экземпляров видело только типизированные связи.
- **Модуль, присланный в чат, — вырожденный случай**: merge-base нет, зоной ответственности считается весь текст.

## Ось 1 — СТАНДАРТЫ

Чек-лист на каждый модуль:

1. Структура: области `#Область/#Region` (ПрограммныйИнтерфейс → СлужебныйПрограммныйИнтерфейс → ОбработчикиСобытий → СлужебныеПроцедурыИФункции), корректный порядок.
2. Директивы компиляции `&НаКлиенте/&НаСервере/&НаСервереБезКонтекста` — корректны и оптимальны.
3. **Без модальности/синхронных вызовов** — конфиг `modalityUseMode = DontUse`, см. `std703`: синхронные Вопрос/Предупреждение/ОткрытьФормуМодально → асинхронные.
4. Именование процедур/функций/переменных/экспортных методов (с описанием) — по стандартам.
5. **Дубли** → вынести в общую процедуру/функцию. **Мёртвый код**, неиспользуемые переменные/параметры, закомментированный код → удалить, **но сперва разобрать происхождение**. Улики недоделанной логики: комментарий обещает поведение, которого в коде нет; переменной присвоено значение, пригодное аргументом соседнего вызова, но туда не переданное; параметр есть в описании метода, но не в сигнатуре. Есть улика — это находка оси «Спека» или вопрос владельцу, а не удаление. В одном из экземпляров из двух «неиспользуемых» переменных одна была мусором, а вторая — непереданной датой среза, из-за чего часть данных молча не загружалась.
6. Запросы: эффективные, без обращения к виртуальным таблицам без параметров, без тяжёлых вызовов в цикле.
6а. **Три сигнала запроса не требуют метаданных и замера.** Размер таблицы, индексы и скорость по фрагменту не видны, но эти три случая не снимаются фразой «неизвестно», и номер входит в список находок:
   - `ПОМЕСТИТЬ` без `ИНДЕКСИРОВАТЬ ПО`, таблица участвует в соединении или в `В (…)`, а размер кодом не ограничен (нет `ПЕРВЫЕ`, одной строки, короткого перечня значений) → `std777` п.3.1, класс СУЖДЕНИЕ: индекс нужен, если строк 1000 и больше.
   - `ПОДОБНО` с шаблоном, который начинается с `%` или `_`, в том числе собранным в коде → жёсткое нарушение, индекс неприменим при любых метаданных: `std652` и `std658` п.3 вместе.
   - `СОЕДИНЕНИЕ` с виртуальной таблицей регистра, у которой пустые параметры отбора → `std657` п.1 и `std655` п.2 вместе, класс СУЖДЕНИЕ: таблица читается без отбора, поэтому замер скорости для находки не нужен.
   Обычное условие по реквизиту находкой не считается: индекс по тексту не виден, он сверяется по метаданным. Виртуальная таблица с отбором в параметрах под третий сигнал не подпадает.
7. Обработка ошибок: Попытка/Исключение + запись в журнал регистрации; корректные транзакции. Транзакция короткая и неделимая по бизнес-смыслу (`std783` п.2): внутри — ни внешних и сетевых вызовов, ни ожиданий. Привилегированный режим — только в сценариях `std485` (проверка прав логически снимается для конкретной операции; полученные так данные на клиент не уходят), а не как обход RLS «чтобы заработало».
7а. **Необратимый внешний эффект** (класс СУЖДЕНИЕ; печать на оборудовании, отправка во внешнюю систему), который наступает раньше записи данных: отказ — на клиенте **до** вызова эффекта, сервер вторым уровнем идемпотентен и возвращает уже созданное; барьер стоит в одной воронке, через которую идут все точки входа; точки входа перечисляются grep-ом по вызову эффекта — обработчик в обход воронки считается дефектом. Вывод сделан по одному случаю в одном из экземпляров: там кнопка вызывала эффект напрямую, минуя все проверки.
7б. **Тихий отказ — отдельный класс находок** (бекпорт из экземпляров 16.10.2026). Проверяемое требование: нераспознанное, пустое или неожидаемое значение НЕ подменяется нулём, пустой строкой или значением по умолчанию — оно становится отказом с сообщением пользователю и записью в журнал регистрации. Проявления, каждое — находка: пустой блок `Исключение` или `Исключение` без `ВызватьИсключение` и без записи в журнал; разбор значения по фиксированному набору ветвей БЕЗ ветви по умолчанию (новый вид значения молча проваливается мимо); `Попытка` вокруг преобразования типа с подстановкой нуля; проверка `Если ЗначениеЗаполнено(...)` без ветви `Иначе`. Почему это ось «Стандарты», а не суждение: требование формулируется как наблюдаемый признак в коде и подтверждается номером (std499 перехват исключений, std498 журнал регистрации).
8. Минимум серверных вызовов (`std487`); строки интерфейса через `НСтр()` — **на всех языках профиля проекта** ([[language-profile]]).
9. **Тест удаления модуля.** Нужен ли этот общий модуль **вообще**? Улики прокладки: экспортных методов больше, чем содержательной реализации; методы — обёртки один-к-одному над БСП/платформой (`Функция Х(П) Экспорт Возврат ОбщегоНазначения.Х(П); КонецФункции`); экспортный метод не вызывается ниоткуда (диагностика **`v8cs:redundant-export-method`** — «модули не должны содержать неиспользуемые экспортные процедуры и функции», `std467`). Такой модуль предлагать **свернуть**, а не улучшать. Критерий — [[naming-and-module-design]], раздел «Глубина и швы». Исключение: процедура — обработчик `ОписаниеОповещения`, назначенный через `ЭтотОбъект` или модуль, **обязана** быть экспортной (`ИмяПроцедуры` — «имя экспортируемой процедуры», справка `bsl-platform`), хотя код-вызовов к ней нет; замечание «неиспользуемый экспорт» для неё ложное.
10. Каждую находку обосновывать: стандарт/диагностика через MCP **v8std**, корректность API платформы через **bsl-platform** ([[installed-tools-and-servers]]).

**Находки этой оси делятся на два класса — и это деление обязано быть видно в отчёте:**

| Класс | Что это | Как подан |
|---|---|---|
| **Нарушение стандарта** | Есть **номер**: `std…`, `BSLLS:…`, `ACC:…`, `v8cs:…` | Констатация: «нарушен `std703`, вот исправление» |
| **Суждение** | Номера нет — читаемость, декомпозиция, «я бы назвал иначе» | Именно как мнение, с обоснованием; спорное — вопросом ([[questions-as-options]]) |

Суждение, поданное как нарушение, — ложь ревьюера, и она обесценивает настоящие находки.

### Подчек-лист «Сигналы переинженеринга» (класс СУЖДЕНИЕ)

Не жёсткое нарушение, а повод спросить «а нужно ли это вообще»: дифф решает задачу тяжелее, чем позволяет штатный механизм 1С. Только реально новые сигналы — уже покрытое ниже идёт кросс-ссылкой, не разбором.

- **NATIVE** — код там, где хватило бы механизма: флаг-константа + ветвление в коде вместо **функциональной опции**; самопальная обвязка вместо **подписки на событие** / **регламентного задания**; проверка в коде вместо **свойства объекта или ограничения в СТРУКТУРЕ метаданных**; самопальная таблица вместо **регистра**. Зеркало ступени 2 лестницы [[work-through-tools]] п.3 (платформенный декларатив прежде своего кода).
- **YAGNI-const** — константа / функциональная опция заведена под **неизменное** значение: конфиг ради того, что никогда не меняется, — это код на ровном месте.
- **STDLIB-reinvent** — переизобретено то, что даёт БСП/платформа: назвать конкретный штатный метод и заменить на него (скилл `bsp`, [[work-through-tools]] п.3).
- **Позитивный терминал.** Проход по этому подчек-листу может закончиться подтверждением «чисто, резать нечего». Минимальность — валидный исход ревью, а не только список находок.

Уже покрыто — здесь **только назвать сигнал и сослаться**, не дублировать разбор: интерфейс/фабрика с единственной реализацией, обёртка 1:1 → тест удаления (п. 9 выше, [[naming-and-module-design]]); scaffolding «на потом», абстракция под одноразовый код → [[coding-discipline]] п.2; глушитель `Попытка/Исключение` вместо корневого фикса → [[bug-diagnosis-loop]].

Сигналы — из `ponytail` (DietrichGebert, MIT); синтез и проекция на 1С — свои.

## Ось 2 — СПЕКА

Дифф сверяется с утверждённым ТЗ ([[design-before-code]], разделы 3–6 и 10). Три вида находок:

1. **Не реализовано.** Требование `Т-n` в ТЗ есть, в диффе — нет (или реализовано частично).
2. **Сделано СВЕРХ ТЗ.** В диффе есть объекты, реквизиты, методы, параметры «на вырост», которых ТЗ не требует. **Scope creep — предмет ревью, а не только дисциплина автора** ([[coding-discipline]] п.2): найденное — назвать и потребовать либо убрать, либо провести через ТЗ.
3. **Реализовано неверно.** Код есть, но не удовлетворяет **критериям приёмки** (раздел 10 ТЗ): другое поведение на границах, другая семантика полей, логика оставлена там, где её не достанет тест.

**Вердикт — на каждое `Т-n`, а не на дифф целиком** (дополнение 19.09.2026; идеи — trailofbits/skills, CC-BY-SA-4.0, текст свой). Словарь уточняет три вида выше:
- **реализовано** — путь пройден по коду: имя метода не доказательство, вызываемый метод открыт и ветка пройдена;
- **частично** (вид 1) — назвать непокрытые пути: другой вид операции, групповая обработка, обмен/загрузка, серверный вызов в обход формы, фоновое задание;
- **противоречит** (вид 3) — код есть, но расходится с критерием приёмки;
- **отсутствует** (вид 1) — только с журналом поиска «где искал → что нашёл», со сменой словаря (в ТЗ «скидка», в коде «Процент»/«Бонус»): `code-index` (`grep_body`, `find_symbol`), подписки на события, модули менеджера, общие модули, роли и RLS. «Искал, не нашёл» без журнала — не вердикт;
- **строже ТЗ** (вид 3) — неописанное ограничение; отличать от «сверх ТЗ» (вид 2, лишние объекты);
- **непроверяемо** — формулировка `Т-n` не даёт критерия; это находка против раздела 10 ТЗ и вопрос владельцу.

**Обратный проход:** достижимое извне поведение, которого нет в ТЗ (команды, HTTP- и веб-сервисы, регламентные задания, подписки, права), — кандидат в вид 2. Серьёзность находки — по последствиям, а не по дистанции от текста ТЗ.

**Отсутствие ТЗ — это САМА НАХОДКА**, а не повод пропустить ось. Формулировка: «сверять не с чем — ТЗ нет; для содержательной доработки это дефект процесса ([[design-before-code]])». Ревью в этом случае идёт по одной оси, и вердикт по оси «Спека» — **не «зелено», а «невозможно»**.

## Оси не сливаются

Итог ревью — **по худшей находке В КАЖДОЙ оси отдельно**:

> **Стандарты:** нарушений нет / есть жёсткие (список) + суждения (список).
> **Спека:** соответствует ТЗ / расходится (список) / **сверить не с чем — ТЗ отсутствует**.

Оси не переранжируются и не усредняются: чистый по стандартам код, делающий не то, — **не «почти готов»**. Ровно наоборот: реализация мимо ТЗ дороже неверного отступа.

**Формат ответа (по умолчанию):** исправленный модуль целиком + два блока находок (по осям) с обоснованием (номера стандартов — в оси 1, номера требований `Т-n` — в оси 2). Если модуль в EDT и edt-mcp доступен — читать/править прямо в проекте (`read_module_source`/`write_module_source`). Полный сет чекеров перед вердиктом — [[full-checker-set-before-done]].

**Важно:** вариант встроенного языка (scriptVariant), языковой профиль и режим совместимости — **свойства проекта, не константы ядра**: берутся из вводных проекта (строка «Языковой профиль» в `CLAUDE.md` проекта — [[plugin-in-project]]), реальный синтаксис дополнительно уточнять по присланному коду.

Двухосевое ревью и тест удаления — синтез из `code-review` / `codebase-design` (mattpocock/skills, MIT); разбор — [[external-mcp-servers-review]].

**Наблюдение (с 17.10.2026, расширено в 4.8.0):** на окончании работы помощника-ревьюера (`SubagentStop`, тип с `review` в имени) и, с 4.8.0, в основном ходе, где владелец просил ревью кода 1С, `stop-guard` проверяет, что в ответах есть оба вердикта — «Стандарты:» и «Спека:»; срабатывание пишется в `logs/answer-check.jsonl`, с 4.8.0 `answer-feedback` показывает его модели в начале следующего хода. Регресс — `contour-tests` §8b, §25.
