# Правило: пакетные запуски платформы 1С — с ожиданием и только по своей базе

**Любой пакетный вызов `1cv8.exe` (`CREATEINFOBASE`, `/LoadConfigFromFiles`, `/CheckConfig`, `/DumpDBCfg`, `/UpdateDBCfg`) запускаю через `Start-Process -FilePath ... -Wait -PassThru`, а не через `&`.** Ожидание и любые действия над процессами `1cv8*` фильтрую по пути СВОЕЙ базы. **Чужие сеансы 1С не жду, не закрываю и не убиваю — никогда.**

**Why:** грабля живого экземпляра (04.08.2026) — три неудачных захода подряд на синтакс-проверке правки обмена.

1. `1cv8.exe` **отсоединяется от консоли**: `& $bin DESIGNER ...` возвращает управление немедленно, `$LASTEXITCODE` остаётся пустым. Три шага (создание базы → загрузка XML → `/CheckConfig`) стартовали параллельно; проверка легла на ещё загружающуюся базу и вернула «Ошибка блокировки информационной базы… уже открыта Конфигуратором». Скрипт при этом отрапортовал «ГОТОВО» — **ложно-зелёный результат**, который легко принять за пройденный гейт.
2. Попытка починить через `Get-Process -Name '1cv8*' | Wait-Process` оказалась хуже: под маску попали **чужие процессы** — Конфигуратор пользователя (`/IBName"..."`) и агент EDT к серверной базе (`/S сервер\база /AgentMode`). Скрипт 30 минут ждал посторонние сеансы и упал по таймауту. Шаг «а теперь убить зависшие» уничтожил бы рабочую сессию пользователя.
3. `.ps1` с кириллицей, записанный БЕЗ BOM, PowerShell читает в OEM-кодовой странице и падает на парсинге («Недопустимая лексема»), не выполнив ни строки — тоже похоже на «отработало вхолостую». Это тот же инвариант, что задаёт `.editorconfig` (`[*.ps1] charset = utf-8-bom`) — [[text-encoding-and-line-endings]]; автоматической проверки BOM у `.ps1` нет, поэтому после записи проверять первые три байта (п.6).

**How to apply:**
1. Вызов — `Start-Process -FilePath $bin -ArgumentList $арг -Wait -PassThru -NoNewWindow`; код возврата брать из `.ExitCode` возвращённого объекта, а не из `$LASTEXITCODE`. **Исключение — прогон тестов YAXUnit в режиме предприятия** (`1cv8c ENTERPRISE … /C"RunUnitTests=…"`, команда `/tests`): клиент может не завершиться сам, поэтому `-PassThru` без `-Wait` и ожидание файла `exitCode` с дедлайном; по таймауту останавливается только этот процесс — по `.Id` объекта из `-PassThru` (п.4), чужие сеансы не трогаются.
2. Аргументы передавать массивом, **но элемент с пробелом кавычить самому**: `Start-Process -ArgumentList` склеивает массив пробелами и кавычек НЕ добавляет. Путь вида `C:\Program Files\...` или `/Out"<путь с пробелом>"` распадается на токены, и лишний токен связывается с соседним **позиционным** параметром — вызов отрабатывает с кодом 0, но по чужим данным. Зонд 15.10.2026 на своём же скрипте: значение из двух слов ушло в `-Checked`, второе слово — в `-Skipped`, третье — в `-Files`, и «снятие взвода» сработало по несуществующему файлу. Через Bash-инструмент пакетные ключи `/Key` не запускать — MSYS их коверкает ([[probe-tool-capabilities]]); только PowerShell.
3. Ожидание чужих процессов: отбирать по командной строке своей базы, не по имени процесса.
   `Get-CimInstance Win32_Process -Filter "Name LIKE '1cv8%'" | Where-Object { $_.CommandLine -and $_.CommandLine.Contains('<путь_своей_базы>') }`
4. **Остановка процессов 1С — только своих и только по этому же фильтру.** Увидел чужой сеанс — сообщить пользователю, а не трогать ([[ask-before-changing]]).
5. Шаги выполнять последовательно и каждый проверять: база создана (есть `1Cv8.1CD` ненулевого размера) → загрузка завершилась (разобрать `/Out`-лог) → только затем `/CheckConfig`.
6. `.ps1` со скриптом сохранять в **UTF-8 с BOM**; после записи проверять первые три байта.
7. **«Скрипт напечатал ГОТОВО» ≠ «проверка прошла».** Вердикт — из `/Out`-лога и кода возврата; нет лога — гейт НЕ пройден ([[docs-match-reality]]).
8. Долгие прогоны — в фоне, наружу только вердикт ([[run-checks-quietly-in-background]]). Фон — **только штатный `run_in_background`** инструмента, не `&` внутри команды: в одном из экземпляров bash-`&` в вызове инструмента завершил родительскую оболочку раньше платформы, `1cv8` остался сиротой, а журнал `/Out` оборвался на середине (дополнение 19.09.2026).
9. **Сигнал завершения — от своего скрипта, а не «процесса 1С больше нет».** Между шагами (создание → загрузка → проверка) процесс `1cv8` на секунды исчезает, и ожидатель «процессов нет» срабатывает в этом зазоре — в одном из экземпляров так за один вечер получили четыре коротких журнала. Ждать выхода `Start-Process -Wait` или финального маркера, который скрипт печатает после последнего шага. Маркер значит «прогон завершён», а не «прошёл»: вердикт по-прежнему даёт п.7 и сигналы ниже.
10. **Вывод дочернего процесса читать с ЯВНОЙ кодировкой.** `Start-Process -RedirectStandardOutput` пишет файл в кодировке консоли (OEM): русский текст в нём рассыпается, и любая последующая сверка регуляркой по русской формулировке не совпадёт НИКОГДА. Это не «находок нет», а «сравнивать было нечего» — и выглядит зелёным. Читать через `ProcessStartInfo` с `StandardOutputEncoding = UTF8`; если дочерний скрипт печатает сам — выставлять в нём `[Console]::OutputEncoding = [Text.Encoding]::UTF8`. Цена граблю известна: наш собственный регресс паритета `forward-port-diff` так давал зелёный, не сравнив ничего (поймано 15.10.2026 — по stderr, не по вердикту; запрет такого зелёного — [[full-checker-set-before-done]], «Проверка самой правки», п.5). То же у захвата вывода через конвейер PowerShell (`$x = python …`, `git … | …`): PowerShell раскодирует чужой вывод кодировкой консоли, и UTF-8-текст бьётся (тире «—» стало «тАФ» в заголовке страницы выпуска) — на время вызова `[Console]::OutputEncoding = [Text.Encoding]::UTF8` (наблюдение 16.10.2026, разобрано 29.10.2026).
11. **Файл из git-объекта извлекать ПОБАЙТОВО, а не как текст.** `& git cat-file blob <rev>:<путь>` в PowerShell отдаёт **массив строк**: теряется BOM и нормализуются переводы строк. Для `.ps1` это фатально — PS 5.1 без BOM читает кириллицу как ANSI, скрипт падает на парсинге, и контур уходит в fail-open МОЛЧА. Копировать поток как есть: `ProcessStartInfo` + `$p.StandardOutput.BaseStream.CopyTo($fs)`. Поймано 16.10.2026 при переносе ядра в экземпляр: 398 файлов уехали без BOM и с переписанными переводами строк, хуки экземпляра перестали парситься. Проверка после записи обязательна: байты записанного файла равны байтам блоба (кроме намеренных замен) — без неё дефект не виден, потому что содержимое «на глаз» правильное.
12. **Разовый помощник пишет только по абсолютному пути от ПЕРЕДАННОГО корня.** Скрипт, собранный «на один раз» из прежнего (который правил другой каталог), наследует и его корень: запись по одному имени (`open(basename, 'w')`, `Set-Content $rel`) уходит в ТЕКУЩИЙ каталог, а не в тот репозиторий, над которым идёт работа. Поймано 16.10.2026: резолвер конфликтов форвард-порта, запущенный для трёх экземпляров, вывалил 103 их файла прямо в корень мастера и подменил `CLAUDE.md`, `RELEASES.md`, `THIRD-PARTY.md`. Содержимое «на глаз» правильное — это настоящие доки ядра, только из экземпляра и на 8 релизов старее, — поэтому молча прошли все контуры, включая pre-commit, и веха ушла зелёной; вскрылось случайно, когда понадобилась запись релиза. Отсюда три требования: корень — ПАРАМЕТР, и каждый путь внутри собирается от него (`Join-Path $Root $rel` / `os.path.join(root, rel)`), cwd в расчёт не берётся; после любой операции над ЧУЖИМ репозиторием — `git status` своего (чужой файл в своём корне = кросс-запись); существование результата проверять по полному пути, а не по имени. Остаток класса стережёт гейт закрытого корня в `health-check` (корневые файлы — закрытый список), но только для того, что попало под версионный контроль.
13. **Пакетный запуск — с `/DisableStartupDialogs` и `/DisableStartupMessages`** (документация 8.3.27, «Руководство администратора», 7.3.11; конспект — скилл `1c-platform-kb`, `its-docs/adm-pr07-…-p1`). С первым вместо диалога выбора базы, авторизации или входа в хранилище платформа выдаёт ошибку — без него запуск может повиснуть на окне, которого никто не видит; второй снимает стартовые вопросы, в том числе «Конфигурация базы данных не соответствует сохраненной конфигурации. Продолжить?». Ограничение: при отключённых диалогах `CREATEINFOBASE` на кластере с администратором завершается ошибкой. `/Out` пишется в UTF-8 и в пакетном режиме без буферизации — его можно читать по ходу; `-NoTruncate` после имени файла не очищает его.
14. **`grep -q` в конце конвейера при `set -o pipefail` даёт ложное «нет».** `grep -q` выходит на первом совпадении, первая команда конвейера получает SIGPIPE, и `pipefail` возвращает ошибку конвейера — проверка «есть ли строка» отвечает «нет» при совпадении. Повторялось дважды (20 и 21.10.2026), опаснее всего в предохранителях сценариев. Нужно: `grep -c … >/dev/null` или вывод в переменную и проверка её, а не `| grep -q` под `pipefail`.
15. **Сессии Claude Code останавливать только инструментами приложения** (`ccd_session_mgmt`: `list_sessions` → `stop_session`), никогда — убийством процессов `claude.exe`. Отбор по потомкам с именем проекта в командной строке захватывает корневой процесс приложения: так однажды закрылось всё приложение Claude (17.10.2026). Без процессов не обойтись — цель только процесс, у которого САМОГО в командной строке путь своего проекта, и только после показа владельцу списка.
16. **Версию платформы брать из пути каталога, а не из ключа `--version`.** Такого ключа у `1cv8.exe` нет: команда открывает окно запуска 1С и висит, пока его не закроют (замечено 30.10.2026 на 8.3.27). Версия — имя папки `C:\Program Files\1cv8\<версия>\bin`.

## Вердикт по нескольким сигналам (дополнение 18.09.2026)

Код возврата `1cv8.exe` — лишь один из каналов, и ноль при проваленной операции для платформы штатен. Поэтому вердикт сводится из пяти сигналов, по порядку:

1. **Код возврата** (`.ExitCode` из `Start-Process -PassThru`): не ноль — провал; ноль сам по себе ничего не доказывает.
2. **Файл результата** (ключ `/DumpResult <файл>`): число не ноль — провал даже при нулевом коде. Файла нет или он пуст — сигнал недоступен (часть операций его не пишет): отметить в выводе, но вердикт на этом не строить.
3. **Журнал `/Out`**: строку сперва сверять со списком формулировок *успеха* целиком («Ошибок не обнаружено», «Предупреждений: 0») и только потом — со списком фатальных. Поиск по корням «ошибк»/«предупрежд» ошибается в обе стороны, а сверка по началу строки («операция завершена») примет за успех «операция завершена с ошибками». Список фатальных пополнять парой наборов: что обязано ловиться и на чём обязано молчать.
4. **Постусловие на диске**: артефакт операции существует **и создан этим запуском** (файл базы, `.cf`, `.epf`, каталог выгрузки). Три чистых сигнала без артефакта — самый дорогой ложный успех: следующий шаг возьмёт файл прошлого прогона.
5. **Полнота журнала** (дополнение 19.09.2026, урок одного из экземпляров): общее число строк `/Out` сверять с эталонным прогоном той же операции на той же конфигурации — например, `/CheckConfig` вендорской конфигурации без правок. Журнал заметно короче эталона при нуле новых находок — не зелёный, а оборванный прогон: обрезанный `/CheckConfig` по содержанию неотличим от чистого. Эталона нет — сигнал недоступен, отметить это в выводе.

Ещё четыре следствия:
- **Уникальный каталог на запуск** для `/Out` и `/DumpResult`: при постоянном имени неудачный старт платформы прочитает журнал прошлого прогона как свой; удаление файла перед стартом не спасает от двух параллельных запусков.
- **Пароль маскировать при печати** командной строки, а не при сборке аргументов — иначе он уходит в вывод, журнал и расшифровку сессии ([[secrets-and-production-database]]); касается и пароля базы, и пароля хранилища.
- **Предупреждение на проверочном прогоне** (`/CheckConfig`, синтаксический контроль, проверка применимости расширения) — находка, а не шум: строгое обновление позже отвергнет то же содержимое. На загрузке/выгрузке предупреждение может быть информационным — список фатальных задаётся на операцию.
- **Одна пакетная команда — один запуск.** По комментарию в скриптах вендорных скиллов (`db-cfe-admin`, `epf-build`, `db-update`: список `V8_BATCH_KEYS`) `DESIGNER` выполняет только последнюю пакетную команду строки, а остальные молча отбрасывает: загрузка XML вместе с проверкой применимости расширения дала код 0, пустой журнал и не состоялась (так сказано в комментарии вендорного скрипта — «проверено на 8.3.24»; это не наш патч, в этой среде не перепроверено). Цепочку шагов собирать отдельными запусками, а не ключами в одной строке.

Ключи `/EraseData`, `/DeleteCfg -AllExtensions`, `/ManageCfgSupport -disableSupport` и изменяющая форма `/IBCheckAndRepair` из автоматизации не запускаются: их последствия не видны ни в одном из сигналов. Это операция пользователя с его резервной копией — команда выдаётся ему на руки ([[ask-before-changing]]).

Источник подхода — правило `rules/designer-batch-verdict.md` из Desko77/claude-code-skills-1c (MIT, коммит `4d0542dc`), пересказано своими словами; ключи `/DumpResult` и формулировки журнала на живом запуске в этой среде не перепроверялись. Пятый сигнал и одна команда на запуск — уроки экземпляров и вендорных скиллов, не из этого источника.

## Предпосылки базы (дополнение 19.09.2026)

1. **«Пользователь ИБ не идентифицирован»** на пакетной выгрузке — значит, на базе вход по паролю. Пароль у пользователя не запрашивать и в чат или скрипты не класть. Решение — **тестовая** база, на которой владелец своими руками завёл пользователя без пароля или включил ОС-аутентификацию. Если пароль всё же приходит из окружения — действует маскирование из раздела выше ([[secrets-and-production-database]]). Требования к входу для `1c-toolkit` — в [[installed-tools-and-servers]].
2. **Открытый Конфигуратор владельца держит блокировку** — выгрузка и сборка падают. Попросить владельца закрыть его на время операции; процессы не трогать (п.4).
3. Учётных данных к тестовой базе нет вовсе — одноразовая файловая база (следующий раздел).

## Синтаксический контроль без учётных данных: одноразовая файловая база (дополнение 19.09.2026)

Маршрут Designer-XML ([[platform-version-and-optional-edt]] п.3), когда тестовой базы нет или её нельзя трогать:

1. `db-create` — пустая файловая база в scratchpad, каталог уникальный на прогон;
2. `db-load-xml` — вся выгрузка;
3. `DESIGNER /CheckConfig` по контекстам профиля проекта.

Каждый шаг — по правилам этого дока: отдельный запуск, `Start-Process -Wait`, вердикт по сигналам, через PowerShell. Замечания делить так: контексты, которых у профиля нет (веб- и тонкий клиент у обычного приложения), не учитывать; остальное сравнивать с базовой линией — журналом прогона до правки или фильтром по модулям доработки. Это не противоречит «предупреждение — находка»: новое замечание в релевантном контексте остаётся блокирующим. В одном из экземпляров на вендорской конфигурации обычного приложения прогон дал сотни унаследованных замечаний, почти все — в контекстах веб- и тонкого клиента, в модулях доработки — ноль. Сравнение с эталонным журналом по дельте для `/CheckConfig` — обобщение, живым прогоном не проверено (там отсекали фильтром по префиксу модулей). Что `/CheckConfig` не ловит — [[full-checker-set-before-done]], «Слепые зоны».

## Лестница проверки расширения (дополнение 19.09.2026, не проверено)

Ступени — отдельными запусками, стоп на первом провале: синтаксис модулей (`/CheckModules` с ключом режима) → применимость расширения (`/CheckCanApplyConfigurationExtensions`, скилл `db-cfe-admin`) → `/CheckConfig` → обновление конфигурации БД с `-WarningsAsErrors` (скилл `db-update`). Откат: редактируемая конфигурация и конфигурация БД — разные состояния; откатывать до обновления БД, а существующее расширение как средство отката не удалять. Порядок — по мотивам comol/ai_rules_1c (лицензии нет, пересказ идеи). Имена ключей есть в скриптах скиллов, но порядок ступеней и поведение на 8.3.27 зондом не проверены ([[probe-tool-capabilities]]).

С 30.10.2026 `;` и `|` внутри кавычек (текст сообщения коммита, `echo`, шаблон `grep`) команду не режут, а текст вложенной оболочки и `Start-Process` оболочки судится как команды (§92).
