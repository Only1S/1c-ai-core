# Правило: порты — конвенцией и под ассертом

Все порты локальных серверов проекта — **TIER B** (свойство инстанса, не константа ядра). На одной машине живут несколько экземпляров и несколько EDT — без конвенции порты сталкиваются (прецедент пойман вживую: сервер соседнего экземпляра на «своём» порту).

**Why:** дефолты ядра (bsl-context `:8007`, edt-mcp `:8765`, 1c-toolkit `:6003`, 1c-forms `:8011`) одинаковы у каждого проекта — два проекта, поднятые одновременно, молча делят порт: инструменты одного проекта отвечают фактами другого. Это худший класс ошибок — «работает, но не про то».

**How to apply:**
1. **Один проект = один блок портов.** При подключении (`/ones-core:setup`) выяснить, какие порты на машине уже заняты соседями, и развести: `1c-toolkit` (`--toolkit-port` → переменная `ONEC_TOOLKIT_PORT`), EDT-мосты — подряд от `EDT_MCP_PORT` (`--edt-port`; primary `N`, дополнительные мосты `edt-<alias>` → `N+1`, `N+2`, …), сервер форм (`--forms-port`). Серверы плагина `bsl-context`, `bsl-platform`, `code-index`, `bsl-ls` работают без порта.
   - **Порт сервера форм живёт в его `.env`:** лаунчер `run-formsserver.cmd` заводит его из `.env.example` с вендорным дефолтом — сервер и `.mcp.json` расходятся молча, пока `.env` не поправлен (ловит п.3). Формсервер занимает **два** порта: `PORT` и `HEALTH_PORT = PORT+1` — шаг блока не меньше 2.
   - **Порт `1c-toolkit` живёт в двух местах:** порт `1c-toolkit` проекта (переменная `ONEC_TOOLKIT_PORT`, её пишет `/ones-core:setup`) и параметр `port=N` в строке запуска обработки в 1С (`/C "…;port=N;…"`, [[installed-tools-and-servers]]), которую ведёт владелец. Разошлись — сервер недостижим (прецедент: тулкит подняли на другом порту, а `.mcp.json` остался на `6003`). Числа `6003`/`8007`/`8011`/`8765` в доках ядра — дефолты и примеры; **фактический порт проекта — только в его `.mcp.json` и переменных**.
2. **Карта портов** — док в `docs-project/` проекта (таблица: мост/сервер → порт → назначение); источник истины — `.mcp.json` + манифест, карта обязана им соответствовать.
3. **Ассерты ниже есть только у health-check мастера ядра;** в проекте на плагине health-check не поставляется (`session-start.py` плагина называет его инструментом мастера) — там сверка ручная: порты в `.mcp.json` и переменных проекта попарно уникальны и не совпадают с блоками соседних проектов, факт — `Get-NetTCPConnection -LocalPort <порт> -State Listen` и владелец процесса. Пересечения МЕЖДУ проектами (`ONEC_TOOLKIT_PORT`, `EDT_MCP_PORT*`, url в `.mcp.json` соседей) не ловит ни одна проверка — health-check мастера видит только свой `.mcp.json`; сверять вручную по картам портов соседей (п.2).
   **Ассерты health-check:** порты в собственном `.mcp.json` попарно уникальны (дубль = FAIL); `EDT_MCP_PORT` манифеста совпадает с url сервера `edt-mcp` (расхождение = FAIL); у слушающего порта владелец-процесс из-под чужого корня с сигнатурой инструментов ядра = WARN «возможен соседний экземпляр». С 18.09.2026 ещё два:
   - **порт на стороне сервера = url клиента:** `PORT` в `.env` сервера форм против url `1c-forms` в `.mcp.json` (у `bsl-context` порта нет — stdio) (расхождение = FAIL; файла нет — INFO);
   - **за портом `edt-mcp` — EDT с НАШИМ воркспейсом:** `-data <workspace>` из командной строки процесса-владельца порта; воркспейс наш, если `ONEC_PROJECT_SRC` лежит под ним или проект есть в его `.metadata\.plugins\org.eclipse.core.resources\.projects\` (импорт из git-клона без копирования). Чужой = WARN, `-data` не определён = INFO.

   **Порт в настройках ≠ сокет.** Порт EDT-моста хранится в воркспейсе: `<workspace>\.metadata\.plugins\org.eclipse.core.runtime\.settings\com.ditrix.edt.mcp.server.prefs`, ключ `mcpServerPort` (сверено на машине мастера 19.09.2026: ключ есть в каждом воркспейсе с плагином). Правка файла сокет не переносит — нужен рестарт EDT (наблюдение экземпляра); у двух воркспейсов порт в prefs может совпасть — тогда сокет у той EDT, что поднялась, и ответы идут по чужому проекту. Факт смотреть не в prefs, а `Get-NetTCPConnection -LocalPort <порт> -State Listen` + `-data` владельца.

   **Частая причина WARN «чужой процесс на нашем порту» — Автозагрузка.** Свой файл плагина там — `ones-core code-index.vbs`: это сам `.vbs`, не ярлык; его пишет `/ones-core:setup` (`code-index-daemon.py autostart`, снять — `autostart off`) с абсолютными путями папки данных плагина — `code-index` и `bin\code-index\bsl-indexer.exe`. **Подозрительны** другие `.vbs`: старые копии с жёстко прописанным корнем мастера или соседа при входе поднимают серверы ЧУЖОГО корня на дефолтных портах, и экземпляр с теми же портами молча ходит в них. Проверка — `Get-ChildItem "$env:APPDATA\Microsoft\Windows\Start Menu\Programs\Startup"` и чтение каждого `.vbs`: путь в нём ведёт не в свой корень и не в папку данных плагина = подозрение (на машине мастера 19.09.2026 так и было — три копии с жёсткими путями). Лечение — убрать чужие копии или заменить ярлыками на самолокующийся `*-autostart.vbs` своего корня; регистрирует автозапуск **пользователь сам**: агенту это только с явного согласия ([[ask-before-changing]]), классификатор блокирует такую запись как несанкционированную персистентность.
4. Мульти-конфиг/мульти-EDT: порт каждого дополнительного моста — суффиксной переменной манифеста `EDT_MCP_PORT_<alias>` ([[plugin-in-project]]); поднятие форка со своим EDT-инстансом — [[config-git-forks-and-merges]].
   **Серверы второй и третьей конфигурации в `.mcp.json` проекта** (`code-index-<alias>` и т.п.) не видят переменных из `env` в `.claude/settings.local.json`: проба 16.10.2026 (`claude -p`, статус серверов в первой строке `stream-json`) — сервер проекта с `${VAR}` из `settings.local.json` не подключился, тот же сервер с переменной окружения системы и контрольный с абсолютным путём — подключились. Серверы **плагина** эти переменные видят (та же проба через `--plugin-dir`), поэтому `ONEC_PROJECT_SRC` и `ONEC_PLATFORM_BIN` для них задаёт `/ones-core:setup`. В `.mcp.json` проекта путь к программе плагина пишется от переменной системы — `${USERPROFILE}/.claude/plugins/data/ones-core-ones-core/bin/code-index/bsl-indexer.exe` (при своём `CLAUDE_CONFIG_DIR` — от него), папка выгрузки — значением по умолчанию: `${ONEC_PROJECT_SRC_<ALIAS>:-<путь>}`.
5. **Порты `code-index`.** По умолчанию `serve` работает по stdio и порта не занимает, но `serve --transport http` без `--port` садится на **8011 — дефолт `1c-forms`** (по `serve --help`, code-index 1.2.3): при переводе на http порт задавать явно из блока экземпляра. Демон слушает `http_port` из своего `daemon.toml` (`0` = случайный; клиент находит его по `daemon.json` — [[code-index-outside-sources]] п.1). В одном из экземпляров на 0.44.3 случайный порт давал устойчивый `daemon_offline` при живой базе — вылечилось закреплением `http_port`; на 1.2.3 не проверено. Воспроизвелось — закреплять значением из блока экземпляра, не константой.
6. **Переменные `ONEC_*` в Windows глобально не задавать.** Переменная, уже заданная в окружении процесса Claude Code, берёт верх над `env` из `.claude/settings.local.json` проекта при подстановке в `.mcp.json` плагина: сессия, запущенная из другой сессии, отдала серверу `code-index` выгрузку чужого проекта (17.10.2026). Проверки проектов из сессии мастера запускать с очищенными `ONEC_*`.
