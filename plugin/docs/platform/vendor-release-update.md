# Обновление доработанной конфигурации на новый релиз

Справочник к скиллу `cf-vendor-update`. Грабли собраны автором `alonehobo/1c-cf-vendor-merge` на обновлении ERP 2.5.22 → 2.5.27 (около 13 тыс. изменённых файлов заказчика) и пересказаны своими словами — у репозитория нет лицензии, текст и код не взяты. Свои факты помечены «проверено у нас».

## Подготовка

- **Только полные релизы** `.cf` или `.dt`. Файл обновления `.cfu` содержит разницу, а не конфигурацию.
- **Одна платформа на все три выгрузки.** Формат выгрузки (атрибут `version` у `MetaDataObject`) у всех трёх одинаковый, иначе разница засорится служебными отличиями. `make-branches.py` это проверяет.
- **Выгрузка релиза — через временную базу** (проверено у нас 19.10.2026, платформа 8.3.27): `ibcmd infobase create --create-database --load=<.cf>` в свой каталог `--data`/`--db-path`, затем `ibcmd config export` (в 8.3.27 равноценен `ibcmd infobase config export` — «Руководство администратора», прил. 4, разд. 4.10.5; конспект — скилл `1c-platform-kb`). `config export --file=<.cf>` без базы отказывает («информационная база не обнаружена»): без подключения к базе `--file` работает только с 8.5.4 (V8Update 8.5.4; там же — `1c/06` скилла), на 8.5.4+ временная база для выгрузки не нужна. Без явных `--data` и `--db-path` ibcmd берёт каталог автономного сервера в профиле пользователя — так нельзя. Вывод ibcmd — в UTF-8. ERP 600 МБ: загрузка ~50 с, выгрузка ~90 с, ~32 тыс. файлов.
- **Каталог работы — не в облачной папке:** десятки тысяч файлов синхронизация не переварит.
- **Ветка заказчика — потомок старого релиза.** Если коммиты лежат линейно или на разных корнях, общий предок неверный и всё станет «добавлено с обеих сторон».
- **Коммит выгрузки — без checkout:** временный индекс (`GIT_INDEX_FILE`), `add -A` с `--work-tree` на каталог выгрузки, `write-tree`, `commit-tree`. Checkout 30+ тыс. файлов на каждую ветку — долго.
- **`ConfigDumpInfo.xml` в ветки не класть:** он свой у каждой выгрузки и даёт ложный конфликт, для полной загрузки не нужен.

## Слияние

- **`-X no-renames`:** детектор переименований git склеивает похожие XML разных объектов (формы, макеты).
- **Число конфликтов не пугает:** у реального обновления их было 859, из них 745 — «поставщик удалил» с шумом выгрузки на нашей стороне.
- **Шум выгрузки** — отличия заказчика от старого релиза, которые не доработки: удалённый язык, отсутствующие стандартные реквизиты, англоязычные имена служебных элементов форм, пустые модули. Правило шума добавляется только с примером, на котором сработало; действующие правила и примеры — `references/noise.md` скилла.
- **Шум не должен съедать пробел внутри строки** (проверено у нас 30.10.2026): правило «убрать все пробельные символы» считало шумом правку литерала или синонима, а по шуму удаление поставщика принимается само. Сравнение — построчно с обрезкой краёв строки.
- **«Удалённый язык» по составу языков не определить** (проверено у нас 30.10.2026): у ERPWEENG 2.5.20.85 в составе один язык, а синонимы несут строки vi, it, pl, en, ru; поставщик между 2.5.15.49 и 2.5.20.85 удалил 4 языка, строки на них остались.
- **XML метаданных сливать структурно, не построчно:** построчный git дал 262 ложных конфликта в одном `Document.xml`. У нас — `resolve-merge.py` (`xml_merge.py`): основа — текст поставщика, наши правки — поддеревьями, ключ элемента — `uuid`/`name`, единственный тег у родителя, текст листа, дочерний `<name>`/`<v8:lang>`. Сливаются только файлы с корнем `MetaDataObject` и `Rights`. Проверено у нас 30.10.2026: на 40 изменённых поставщиком документах ERP 2.5.20 слияние с неизменённой нашей стороной даёт байт в байт версию поставщика; документ 900 КБ с нашим реквизитом сливается за 0,4 с без потери строк поставщика.
- **Построчная склейка без конфликта тоже бывает неверной** (проверено у нас на синтетике): один и тот же объект, добавленный в права роли с обеих сторон в разных местах, git склеивает без конфликта — получается дубль. Поэтому XML описаний и прав из «слито автоматически» пересобирается структурно.
- **Внутри значений бывает одиночный LF при CRLF в разметке** (проверено у нас на ERP 2.5.20.85): приводить переводы строк вставляемого фрагмента можно только при другом стиле нашей версии, иначе меняются сами значения.
- **Не сливать поэлементно** макеты MXL (позиционные форматы), настройки диаграмм и СКД внутри форм: поэлементное слияние тестовых данных диаграммы дало ошибку XDTO при импорте. Такие файлы берутся целиком с одной стороны.
- **После слияния форм — уникальность `id`:** у элементов, реквизитов и команд свои пространства номеров.
- **Двойник:** объект с одним именем у заказчика и у поставщика, uuid разные (заказчик сделал раньше). uuid поставщика — новый объект; таблица заказчика при обновлении базы удалится вместе с данными. По умолчанию объект заказчика переименовать в `Удалить…` с сохранением uuid, взять объект поставщика, дописать строку в `Configuration.xml`.
- **Поставщик «удаляет» переименованием** (`Удалить…`, `…До2020`) с тем же uuid: ссылки заказчика переименовать, а не удалять. Права в ролях конфигуратор ведёт за объектом по uuid — в своих ролях право переименовать.
- **Поле регистра сменило вид** (ресурс ↔ измерение ↔ реквизит): право переименовать, а не удалять.
- **Сирота:** поставщик удалил объект целиком, а у заказчика там своя форма или модуль — удалить вместе с объектом и сообщить.

## BSL

- **Основа — код поставщика, доработка переносится по смыслу;** маркеры конфликтов не склеивать.
- **Типовой код переезжает между модулями** (например, в `…Проведение`, `…Служебный`, `…Локализация`): помощник не правит чужой файл, а описывает перенос, применяет его основная сессия.
- **Правка инструментом Edit срезает пробелы в конце строк** — для больших вставок в типовой код байтовая запись скриптом.
- **Ссылки кода на реквизиты форм, которых нет ни у кого,** — существовавшая проблема или программное создание: не чинить молча, сообщить.

## Проверки до импорта

- **Сирота остаётся и после слияния** (проверено у нас на пилоте 30.10.2026): git удаляет описание объекта, а наш модуль или форма внутри него остаются в индексе без конфликта — импорт на таком файле остановится. `check-merge.py` отмечает каждый такой объект.
- **Что ищет `check-merge.py`:** неразрешённые пути и маркеры конфликта, XML, который не разбирается, расхождение состава `Configuration.xml` с файлами, правки без `git add` (импорт и коммит берут индекс, а проверка читает диск), сироты, ссылки на исчезнувшие объекты в XML и модулях (менеджеры, тексты запросов в модулях, схемах и формах, строки типов, типы с любым префиксом `current-config`, общие модули), права ролей на исчезнувшие объекты и подчинённые объекты, ссылки нашей дельты на объекты `Удалить…`/`Delete…`, повтор `id` в формах. Подсказка переименования — по uuid старого объекта.
- **Поставщик английской конфигурации помечает устаревшее префиксом `Delete`** (проверено у нас: в ERPWEENG 2.5.20.85 таких объектов 36; между 2.5.15.49 и 2.5.20.85 шесть объектов переименованы так с тем же uuid).
- **Пространства `id` формы** (проверено у нас на 3682 формах ERP 2.5.20): элементы формы — одно пространство на всю форму; у реквизитов, команд, колонок реквизита и каждого набора `AdditionalColumns table=…` номера свои, у разных наборов совпадают.
- **Зонд на целом релизе** (30.10.2026): все 29 996 файлов 2.5.20.85 против дельты поставщика — ложных находок в правах, составе и ссылках нет, проверка заняла 250 с. Нашлась одна настоящая висячая ссылка в коде самого поставщика: строка `"CommonTemplate.DocumentScanningAddIn"`, а шаблон переименован в `DocumentScanningAddIn_3_0_1_1033`. В отчёт по нашей дельте такие ссылки поставщика не попадают.

## Проверка импортом

- **Импорт в пустую базу останавливается на первом сломанном файле** (5–8 минут на итерацию у ERP) — поэтому сперва проверки ссылок и автослитого, потом импорт.
- **Висячие ссылки заказчика, которые живая база терпит, а импорт XML — нет** (команды ввода на основании без самого ввода, права на несуществующие реквизиты): не ошибка слияния, но чинить придётся.
- **«Неизвестный объект метаданных»** не валит импорт; обычно это права ролей на удалённые реквизиты.
- **Шаг у нас — `import-check.py`:** выгрузка индекса без checkout → `ibcmd infobase create` в каталоге прогона → `ibcmd config import` → `DESIGNER /CheckModules` с `/Out` и `/DumpResult`, отдельными запусками ([[designer-batch-runs]]). `/DisableStartupMessages` обязателен: импорт меняет основную конфигурацию, не применяя её к базе, и без ключа конфигуратор спросит о несоответствии. Вердикт — код (0, 1, 101), `/DumpResult` и журнал этого запуска. Базовая линия — тот же прогон по новому релизу (`--rev vendor-<версия>`), его строки журнала не считаются новыми. Живой импорт 30.10.2026 (ERP 2.5.20.85, 32 878 файлов, файловая база, платформа 8.3.27): новый релиз — 348 с, результат слияния пилота — 330 с (импорт 144 с, `/CheckModules` 163 с), оба прошли. Журнал подтверждён только для успешного исхода: одна строка «Синтаксических ошибок не обнаружено», `module_lines` = 0; формат строк с ошибками модулей живым прогоном не подтверждён, регресс — на моках.

## Расширения

- **Заимствованные формы в выгрузке из базы бывают без `ExtendedConfigurationObject`** (у автора — 199 из 246 ещё до обновления); после загрузки такая форма молча перестаёт применяться. Влияние релиза на перехватчики — скилл `cfe-update-impact`; сам он пустое `ExtendedConfigurationObject` не отмечает (сверено по коду 30.10.2026), это делает `extensions-impact.py`.
- **Пара для `cfe-update-impact` при обновлении доработанной конфигурации** — ветка `custom` (под неё расширения написаны) и результат слияния, а не старый и новый релизы поставщика: расширение перехватывает и наши доработки. `extensions-impact.py` выгружает обе стороны без checkout и прогоняет каждое расширение.
- **`&ИзменениеИКонтроль`** при изменённом методе — расширение не подключится; **`&Вместо` без `ПродолжитьВызов`** молча теряет изменения поставщика; **новый параметр метода** — поправить объявление и передачу.

## Загрузка результата в рабочую базу (только по прямой команде владельца)

- **Настройки поддержки** `Ext/ParentConfigurations.bin` git возьмёт с одной из сторон. Для рабочей базы нужна версия заказчика: она ссылается на копию поставщика, которая есть в этой базе. Файл из выгрузки нового релиза не подходит — ссылается на копию, которой в базе нет.
- **Порядок:** «Обновить конфигурацию» новым `.cf` → в сравнении снять все флажки → сохранить без обновления базы → выгрузить и сверить с git (отличия — только настройки поддержки). Либо, если обновление уже было с откатом, взять из базы новые `ParentConfigurations.bin` и `ParentConfigurations/<имя>.cf`, положить в исходники, загрузить полностью и сверить повторной выгрузкой.
- **Резервная копия до загрузки:** выгрузка `.cf` основной конфигурации и каждого расширения.
- **Конфигуратор — через `Start-Process -Wait`** ([[designer-batch-runs]]): при запуске из Bash файлы, которые он пишет, могут не появиться.
- **Строку соединения с кавычками внутри** PowerShell и Python портят при передаче; без пробелов и `;` в именах — передавать без кавычек.
