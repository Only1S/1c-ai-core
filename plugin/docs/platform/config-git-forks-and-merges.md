# Git-воркфлоу конфигурации и её форков (EDT)

Рабочая 1С-конфигурация (config + подключённые расширения) ведётся под git как **монорепо**. Параллельные направления работы (перенос подсистемы, интеграция, эксперимент) — отдельными **форками в git-ветках**. **Механизм форка зависит от профиля проекта** ([[platform-version-and-optional-edt]]):

- **Профиль без EDT (Designer-XML)** — форк = **`git worktree`** из основного репо (git-родной способ: общий объектный store, история не дублируется, легче по диску, **bare-хаб не нужен**). Это предпочтительный вариант, если EDT в проекте нет.
- **Профиль с EDT** — форк = **отдельный КЛОН** из общего **bare-хаба** (ниже): EGit (git внутри 1С:EDT) worktree физически не открывает — вынужденный, но обязательный обход. Клон тяжелее (дублирует историю) и требует хаба-синхронизатора.

> ⚠ **git ≠ EDT (несмотря на имя этого правила).** Само подключение к git — это **выгрузка конфигуратора в файлы** (`DumpConfigToFiles`, скилл `db-dump-xml`), а НЕ EDT. Способ старше EDT и работает для **любой** платформы 8.3 и любой конфигурации — включая **обычные формы**, десктопную и мобильную разработку. EDT — лишь git-родной редактор поверх, удобный для управляемых форм. Нет EDT (или конфигурация на обычных формах, которую EDT не открывает) → **git всё равно есть**, профилем Designer-XML: форк = `git worktree`, редактирование — XML-скиллами/`.bsl` в выгрузке. Честная граница: обычная форма версионируется, но в выгрузке — грубый блоб, дифф по ней малочитаем ([[platform-version-and-optional-edt]] пп.2,4). Этот док описывает **форк-механику** (worktree vs клон) и **слияние** — они общие; профиль С EDT ниже отличается лишь тем, что EGit навязывает клон вместо worktree.

Конвенция config-agnostic: подставляй `<config>`, `<hub>`, `<форк>`, порты — из порт-конвенции ниже.

## Топология — общий bare-хаб (профиль с EDT)
> Без EDT bare-хаб не нужен: `git worktree add <GIT_HUB>\<config>-<форк> <форк>` из основного репо даёт форку рабочее дерево на общем объектном store; порт/ИБ/мост EDT в этом профиле не заводятся. Ниже — форма для профиля **с EDT**, где клон обязателен.
```
<GIT_HUB>\<config>.git   (bare-хаб — только история, ветки main + <форк-1> + <форк-2> …)
   ▲push ▼pull                       ▲push ▼pull
Primary (экземпляр)                  Форк <форк>
<ONEC_PROJECT_SRC>\… · ветка main    <GIT_HUB>\<config>-<форк> · ветка <форк>
EDT primary (порт из манифеста)      своя EDT (свой порт) · своя тест-ИБ · свой code-index
```
Обе стороны — **клоны хаба** (`origin = <GIT_HUB>\<config>.git`): primary отслеживает `origin/main`, форк — `origin/<форк>`. В bare-хабе рабочее дерево не выгружено → любую ветку (в т.ч. `main`) пушить безопасно.

**Место хаба — переменной манифеста `ONEC_GIT_HUB`** (по умолчанию, напр., `D:\GIT`), чтобы путь не хардкодился; сам хаб — вне EDT-воркспейса и вне корня экземпляра.

**Выгрузка и репо конфигурации — тоже вне корня копии** (в любом профиле; путь — `ONEC_PROJECT_SRC[_<alias>]`). Общий скан health-check (секрет-скан, гейт имён) рекурсивно проходит корень по `*.xml`/`*.bsl`, а в мастере ядра health-check стоит в SessionStart (таймаут 60 с) и в pre-commit (в проекте на плагине health-check нет, его pre-commit проверяет секреты только в подготовленных к коммиту файлах): выгрузка внутри корня превращает каждый старт сессии и каждый коммит в минуты. Замер в одном из экземпляров: ~13,7 тыс. файлов выгрузки — ≈173 с на один проход поиска при нескольких проходах за прогон; с выгрузкой за корнем `health-check --strict` — 14 с. Прецедент того же класса — клон БСП, вынесенный из скана.

**Монорепо-гигиена:** в репо — только `src` конфигурации и расширений (+ `docs/` журналов форка, см. [[journal-placement]]); `.gitignore` — `.metadata/`, `**/.code-index`, `**/bin`; переводы строк — версионируемым `.gitattributes` с `* -text` (главное) плюс локальный `core.autocrlf=false` (страховка); локально же `core.quotepath=false` и `core.longpaths=true`. Почему именно так — грабли ниже.

### Грабли git в 1С-выгрузке (Windows)
Пойманы на реальной выгрузке в одном из экземпляров; пп. 1, 3, 4 перепроверены зондом на git 2.54 (игрушечный репо). Первые четыре не дают ошибки — портят результат молча.
1. **Неанкорённое правило `ext/` в `.gitignore` прячет весь код.** На Windows `core.ignorecase=true` по умолчанию, и правило `ext/` (например, заведённое, чтобы не брать каталог расширений) совпадает с КАЖДЫМ `Ext/` выгрузки — а там модули, формы и макеты. На реальной выгрузке так скрылось 10 138 файлов из 17 600. Правило анкорить (`/ext/`) или не заводить; проверка — `git check-ignore -v <путь к модулю>`.
2. **После `git add` сверять по типам, а не общим счётчиком.** Число `.bsl`, форм (`Form.xml`/`Form.bin`), макетов в индексе (`git ls-files`) = числу на диске; бинарники, если хранятся, — ненулевого размера; число форм и объектов — паспорту конфигурации (`cf-info`). Общий счётчик файлов «почти сходится» и при потере целого класса.
3. **`core.quotepath=false` — до любых сверок.** С умолчанием git экранирует кириллические пути и берёт их в кавычки — строка кончается на `"`, и проверка по расширению (`grep '\.bsl$'`) молча даёт 0 (зонд: 0 против 1). Заодно `status`/`diff` становятся читаемыми. Настройка отображения, на байты выгрузки не влияет — рекомендация, не требование.
4. **`.gitattributes` с `* -text` главнее `core.autocrlf`.** `autocrlf` — локальная настройка, не версионируется: клон на машине с глобальным `autocrlf=true` нормализует CRLF в LF (зонд: так и есть). Атрибут едет вместе с репо и держит выгрузку байт в байт для обратной загрузки независимо от машины. Для **уже существующего** репо ввод `.gitattributes` требует ренормализации (`git add --renormalize .` отдельным коммитом) — только с согласия владельца ([[ask-before-changing]]), автоматически не выполнять.
5. **`core.longpaths=true`** (локально в репо конфигурации). Пути выгрузки (`<Тип>\<Объект>\Forms\<Форма>\Ext\Form\…`) с длинными кириллическими именами легко выходят за 260 символов, а поддержка длинных путей в Git for Windows по умолчанию выключена (его документация `git-config`). Там же оговорка: Проводник, `cmd.exe` и msys-инструменты длинные пути не поддерживают — поэтому настройка локальная, не `--global`.

## Форк: worktree (без EDT) или КЛОН (с EDT) ⭐
**По умолчанию worktree — он лучше:** `git worktree` — git-родной механизм, делит один объектный store, не дублирует историю, не требует bare-хаба. КЛОН применяется **только когда его навязывает EGit**, а не как общий выбор.
- **Без EDT** → `git worktree add <путь> <ветка>` из основного репо. Точка.
- **С EDT** → **отдельный КЛОН** из bare-хаба: EGit («групповая разработка» в 1С:EDT) worktree **не открывает** — падает `Bare Repository has neither a working tree, nor an index` (у worktree `.git` — файл-указатель, а не папка). У клона `.git` — обычная папка → EGit цепляется штатно: **Import → Git → «Проекты из Git» → Existing local repository → `<GIT_HUB>\<config>-<форк>`** («Копировать в workspace» — снять). В этом профиле тулинг ядра поднимает форк клоном; встретил у форка worktree-`.git` под EDT — пересоздай клоном.

## Как поднять новый форк
1. `git clone <GIT_HUB>\<config>.git <GIT_HUB>\<config>-<форк>` + `git checkout -b <форк>` (или `checkout <форк>`, если ветка-заготовка уже в хабе).
2. Пользователь: новый EDT-инстанс (свой порт), Import → Git → Projects from Git → `<GIT_HUB>\<config>-<форк>` (оба проекта).
3. Мост `edt-<форк>` в `.mcp.json` (+ карта портов + счётчик серверов), code-index alias на `…\<config>-<форк>\…\src` (junction вне EDT — [[code-index-outside-sources]]), тестовая ИБ в `.v8-project.json` (боевую НЕ вносить — [[secrets-and-production-database]]).
4. Перезапуск Claude Code → инструменты `mcp__edt-<форк>__*`.

> **2-я волна (автоматизация):** шаги 1,3 — кандидат в скрипт new-config-fork.py, пока не написан (клон/worktree ветки по профилю + выделение свободного порта из конвенции + регистрация моста/alias/junction/тест-ИБ + бамп счётчика; под EDT — только КЛОН).

## Слияние — через хаб
1. Форк: `git push origin <форк>` → хаб.
2. Primary: `git fetch origin` → `git merge --no-ff origin/<форк> -m "Merge <форк>: <суть вехи>"` в `main` → `git push origin main` → хаб.
3. **reload primary EDT** → прогнать весь набор [[full-checker-set-before-done]] (метаданные после reload могут разойтись — [[edt-mcp-pitfalls]]).

**Слияние форка — всегда `--no-ff`** (бекпорт решения владельца одного из экземпляров). Без него fast-forward вливает коммиты форка в линию `main`, и граница работы форка на графе исчезает: не видно, что пришло одной вехой, и её не откатить одним revert merge-коммита. Тема merge-коммита — `Merge <форк>: <суть вехи>`. Граф смотреть `gitk --all` / `git log --graph --oneline --all` или EDT → Team → Show in History.

> **2-я волна:** поток слияния — кандидат в скрипт fork-merge.py, пока не написан (вливает с `--no-ff`) со встроенным напоминанием reload + запуском чекеров (чтобы шаг 3 не забывался).

## Перенос между ветками (частичный порт)
По мотивам уроков одного из экземпляров (бекпорт, обезличено).
- **По умолчанию — `merge` или `cherry-pick`.** Перенос копированием файлов даёт ветке-приёмнику те же файлы без общей истории — при следующем слиянии это add/add-конфликты без базы (в экземпляре — 5 конфликтов против 0 у нормальной истории). Копирование — только исключение, записанное в журнал форка ([[journal-placement]]).
- **Цену слияния — заранее, без касания дерева:** `git merge-tree --write-tree --name-only <ветка-A> <ветка-B>` печатает конфликтующие файлы (код возврата 1 при конфликте; зонд на git 2.54). Прогонять попарно, включая форки между собой.
- **Часть ветки — в отдельном `git worktree`**, рабочее дерево EDT не трогать. Такой worktree в EDT не открывается и не должен: он только для git-операций, правилу «под EGit — клон» не противоречит.
- **Граница среза** — `git grep` по ссылкам на переносимые объекты (кто на них ссылается и на что ссылаются они).
- **Корневой файл конфигурации** при порте правится штатными средствами, а если их не хватает — по узкому исключению из no-bypass с обязательным round-trip и согласием владельца ([[edt-mcp-pitfalls]], раздел no-bypass).
- **Доказательство среза:** состав корневого файла конфигурации сверен с каталогами в обе стороны; `git grep` старых имён даёт пустой остаток; `bsl-analyzer` в порте и в ветке-источнике даёт одинаковые числа по перенесённым модулям. Правка корневого файла конфигурации (`Configuration.mdo`/`Configuration.xml`) при этом — только штатными средствами ([[edt-mcp-pitfalls]], [[use-skills-not-manual-edits]]).

## Обновление на релиз поставщика (с 19.10.2026)
Доработанная типовая переводится на новый релиз тем же механизмом — слиянием, а не «Обновить конфигурацию» вслепую: старый релиз поставщика — общий предок, ваша конфигурация (`custom`) и новый релиз — две ветки. Выгрузка релизов, ветки и разбор конфликтов по классам — скилл `cf-vendor-update`; грабли (шум выгрузки, двойники с другим uuid, объекты `Удалить…`, макеты и СКД целиком, права по uuid, расширения, настройки поддержки при загрузке в рабочую базу) — [[vendor-release-update]]. Разрешение конфликтов — по разделу ниже, хвост слияния — тот же.

## Разрешение конфликтов слияния

Слияние веток в 1С расходится с обычным git тем, что **половина репозитория — не код, а машинная выгрузка**, и текстовое слияние её убивает. Поэтому конфликт разрешается не по строкам, а по типу артефакта и по намерению сторон.

**Спина процесса** (одинакова для любого конфликта):
1. **Увидеть состояние:** `git status`, `git diff --name-only --diff-filter=U` — какие файлы конфликтуют и к какому типу относятся (развилка ниже).
2. **Понять НАМЕРЕНИЕ каждого куска — обеих сторон:** что делал код в `main` и что в форке (коммиты, журнал форка [[journal-placement]], ТЗ). Конфликт — столкновение двух намерений, а не двух текстов; выбирать сторону, не поняв обе, нельзя.
3. **Сохранить ОБА намерения**, если они совместимы (обе правки нужны — сшить их).
4. **Несовместимы — выбрать по цели слияния и ЗАПИСАТЬ trade-off:** что проиграло, почему, что теперь не работает — строкой в журнал форка. Молчаливый выбор стороны = потерянная работа, о которой никто не узнает.
5. **Не выдумывать новое поведение**, которого не было ни в одной ветке. Разрешение конфликта — выбор и сшивка существующего; новое поведение — это новое ТЗ ([[design-before-code]]), а не «компромисс в редакторе».
6. **Автопроверки по ходу**, а не в конце: разрешил `.bsl` — сразу `bsl-analyzer` / `edt-mcp get_project_errors` по этому модулю.
7. **Довести до конца:** полуразрешённый merge не оставляют (см. про `--abort` ниже).

### Развилка по типу артефакта ⭐

| Артефакт | Как сливать |
|---|---|
| **Тела модулей** (`.bsl`) | Сливаются **в git** — по намерению и **целыми методами**: единица разрешения — процедура/функция целиком, а не строка между `<<<<<<<` и `>>>>>>>`. Радиус поражения выбранной стороны — до правки: `code-index` (`get_callers`, `get_call_tree`), `edt-mcp` `find_references`, по живой базе — `1c-toolkit` `find_references_to_object` |
| **Выгрузка метаданных** (`.mdo`/`.xml`, `ChildObjects`, `ConfigDumpInfo.xml`, UUID) | **Текстом в git НЕ СЛИВАТЬ ВООБЩЕ.** Штатное прежде своего: **«Сравнение, объединение конфигураций»** Конфигуратора либо штатное объединение EDT → и **перевыгрузить** исходники (`db-dump-xml`, [[use-skills-not-manual-edits]]). Ручное слияние XML даёт битую выгрузку и убитые UUID: идентичность объектов теряется, база видит «объект удалён и создан заново» |

Технически закрыть конфликтный файл выгрузки в git можно только целой стороной (`git checkout --ours|--theirs <файл>`) — но это лишь способ снять маркеры; **содержательное объединение делает штатный механизм**, а его результат возвращается в репозиторий перевыгрузкой.

### `git merge --abort` — разрешён, брошенный merge — нет
`--abort` — **законное осознанное решение**: слияние оказалось шире, чем думали; нужен штатный механизм объединения; сперва требуется ТЗ. Условие одно — **причина записывается в журнал форка** ([[journal-placement]]).
**Запрещено:** бросить полуразрешённый merge и «дособрать» компромиссный код, которого не было ни в одной ветке. Либо сливаем до конца, либо `--abort` с записанной причиной.

### Хвост слияния — обязателен
1. **`db-load-xml` на тестовую ИБ** ([[secrets-and-production-database]]) — главный детектор битой выгрузки и убитых UUID: если результат слияния не загружается, слияние не состоялось.
2. **reload EDT** → `revalidate_objects` → `get_project_errors` = 0 ([[edt-mcp-pitfalls]]).
3. **Полный сет** [[full-checker-set-before-done]] (включая тесты).
4. **Строка в changelog** + журнал форка ([[work-journals-and-commits]], [[journal-placement]]).

Merge не завершён, пока хвост не зелёный; красный хвост — откат (`git merge --abort`, если ещё в merge, иначе `git reset --hard` до merge-коммита), а не «поправим потом».

## Обновление доработанной типовой на новый релиз вендора (git)
По мотивам методики [yellow-hammer/dev-rules](https://github.com/yellow-hammer/dev-rules) (`docs/version-control/git/vendor-update.md`, CC-BY-SA-4.0) — пересказ своими словами, встроенный в нашу развилку по типу артефакта. **Статус: пилота на реальной типовой в ядре не было — не проверено.** Git-механика ветки вендора (привязка, база трёхстороннего слияния, дифф доработок) проверена зондом на игрушечном репо (git 2.54).

**Идея.** Долгоживущая ветка `vendor` хранит **только чистые поставки** — по коммиту `vendor <версия>` на релиз, в том же формате исходников, что и `main` (в профиле с EDT — поставка, импортированная в формат проекта, иначе дифф бессмыслен; не проверено). Тогда:
- `git diff vendor main` — полный перечень наших доработок против текущего релиза: это карта того, что обновление обязано сохранить;
- база трёхстороннего слияния для нового релиза — прежний коммит `vendor`, то есть git видит и что поменял вендор, и что поменяли мы.

**Привязка существующего проекта** (история `main` началась без вендора): поставку, на которой `main` стоит сейчас, закоммитить в orphan-ветку `vendor` и влить её `git merge -s ours --allow-unrelated-histories vendor` — дерево `main` не меняется (зонд: tree hash тот же), а `vendor` становится предком. Со следующего релиза merge-base считается штатно.

**Цикл релиза:**
1. **Чистая поставка** нового релиза: `.cf` в пустую тестовую базу (`db-create` → `db-load-cf`) → `db-dump-xml` **в пустой каталог** → содержимое ветки `vendor` заменяется выгрузкой целиком (удалённые вендором объекты тоже должны уйти, иначе дифф врёт) → коммит `vendor <версия>`. Скиллы — обязательный путь ([[use-skills-not-manual-edits]]).
2. **Ветка обновления:** `git switch -c update/vendor-<версия> main` → `git merge --no-ff vendor`. Локально в репо конфигурации (не `--global`): `git config merge.conflictStyle zdiff3` (в маркерах видна и база) и `git config rerere.enabled true` (однажды разрешённый конфликт повторно разрешается сам в следующих релизах).
3. **Разрешение — по развилке выше:**
   - `.bsl` — в git, целыми методами, по намерению: вендор переписал метод, который мы дорабатывали, — наша доработка переносится на **новый** текст вендора, а не наоборот. Неуверенно разрешённое место помечать комментарием `// MERGE-REVIEW: <что проверить>`; в сомнении доработку не выбрасывать.
   - выгрузка метаданных (`.xml`/`.mdo`) — текстом не сливать: штатное обновление/объединение в Конфигураторе (или EDT) на тестовой базе с `main` и новой поставкой → перевыгрузка поверх ветки обновления.
   - бинарные файлы выгрузки (`Form.bin`, `Template.bin`, картинки), которых мы не меняли относительно прежней поставки, — из новой поставки (`git checkout --theirs <файл>`); которые меняли — только штатным объединением.
4. **Опция `.gitattributes`: `*.xml -merge` / `*.mdo -merge`** — git перестаёт сливать выгрузку текстом: файл, изменённый с обеих сторон, всегда уходит в конфликт, в дереве остаётся наша версия (зонд: правки в разных строках XML дали конфликт, а не автослияние). Механически закрепляет правило «выгрузку текстом не сливать»; на реальной выгрузке не проверено — кандидат на пилот.
5. **Финал:** `git diff --check` пуст (ловит забытые маркеры конфликта — зонд: «leftover conflict marker»); `git grep -n "MERGE-REVIEW"` пуст либо весь список показан владельцу; **хвост слияния** выше целиком + проверки расширений ниже; затем `update/vendor-<версия>` → `main` через `merge --no-ff`.

**Расширения (CFE) — готовить к обновлению заранее** (конвенция швов — [[naming-and-module-design]]):
- **Выбор аннотации перехвата:** `&После` → `&Перед` → `&ИзменениеИКонтроль` → `&Вместо`. `&Вместо` — последним и только с обоснованием в комментарии: он заменяет метод целиком, и новые строки вендора в этом методе после обновления молча не выполняются. `&ИзменениеИКонтроль`, наоборот, сам сообщает о расхождении с эталоном при проверке применимости. v8std согласуется: диагностика EDT `change-and-validate-instead-of-around` предлагает `&ИзменениеИКонтроль` вместо `&Вместо` без `ПродолжитьВызов` (с 8.3.16); расхождение описания расширяющего метода с исходным после обновления — АПК:1314.
- **Нарезка под обновление:** правки схем СКД и крупные заимствованные формы — в отдельные расширения `<Префикс>_<Назначение>`, чтобы после релиза точечно отключить конфликтующее, не роняя остальное (урок одного из экземпляров).
- **После обновления:** применимость расширений на тестовой базе (`db-cfe-admin`), состав и перенос (`cfe-diff`), актуализация перехватчиков под новый оригинал (`cfe-patch-method`), затем проверка конфигурации с включёнными расширениями и регресс-кейсы ([[full-checker-set-before-done]]).

**Из источника не берём:** глобальный `git config --global merge.tool` (постоянная настройка пользователя — только с его согласия), текстовое слияние XML (противоречит развилке выше), промпт-шаблоны агента (share-alike, дословно не переносим).

## Порт-конвенция мульти-EDT
Один живой EDT = одна папка проекта → параллельная работа с несколькими конфигурациями/форками требует **нескольких EDT-инстансов, каждый на своём порту** и со своим мостом `edt-*` в `.mcp.json`. Порт EDT — свойство инстанса, не константа. Конвенция: primary — `EDT_MCP_PORT` из манифеста; дополнительные мосты — соседние свободные порты (база+offset), зафиксированы картой в `docs-project/` экземпляра; локальные серверы (`bsl-context`/`1c-forms`/`1c-toolkit`) при нескольких экземплярах на машине — тоже развести (слой B проекта — [[plugin-in-project]]). В мастере health-check (§1d; регресс — `contour-tests`) проверяет отсутствие коллизий портов в `.mcp.json` (в проекте этой проверки нет — порты разводит `/ones-core:setup`, [[server-ports-per-project]] п.3) и то, что за портом `edt-mcp` стоит EDT с НАШИМ воркспейсом: порт моста хранится в настройках воркспейса, а сокет держит та EDT, что поднялась, — при двух воркспейсах с одним портом запросы молча уходят в чужой проект ([[server-ports-per-project]] п.3).

## Пределы и грабли (проверено на живом экземпляре)
- Один живой EDT = одна папка → параллельный live `edt-mcp` только через отдельные EDT-инстансы; RAM-потолок — несколько инстансов на машину.
- **EGit не поддерживает worktree** → форку в профиле С EDT нужен КЛОН (папка `.git`); без EDT — worktree предпочтителен.
- EGit кэширует репо: «Close Project» не отпускает `.git` (lock на pack) — нужен «Remove Repository» из Git Repositories view либо рестарт EDT.
- Мосты грузятся при старте Claude Code (набор полустатичен на сессию).
- ИБ — только тестовые ([[secrets-and-production-database]]); EDT капризен к внешним `.mdo` при reload ([[edt-mcp-pitfalls]]).
- **Одна ветка — одно рабочее дерево.** Проекты одной конфигурации (основной и расширения) бывают открыты в EDT из РАЗНЫХ клонов/worktree — правки тогда расползаются по деревьям. Детект: пути проектов в `list_projects` (edt-mcp), вид `.git` у каждого (папка = клон, файл-указатель = worktree), `git worktree list`; кто чей предок — проверять из хаба. Лечение — свести правки в одно дерево (патч со сверкой `--numstat`), лишний проект отцепить от EDT без удаления файлов; переимпорт делает человек.
- **Удаление worktree — `git worktree remove`, не `rm -rf`, и сперва `git status --ignored`.** Зонд (git 2.54): `worktree remove` даже БЕЗ `--force` удаляет worktree, в котором кроме отслеживаемого лежат только игнорируемые файлы, — и уносит их молча (`bin/`, локальные базы, логи). Junction индекса внутри worktree — отдельная грабля ([[code-index-outside-sources]] п.3).

### Git рядом с живой EDT владельца
Уроки одного из экземпляров (бекпорт, обезличено) — для профиля, где владелец правит в EDT параллельно с агентом.
- **Коммитить только своё:** `git add <свои пути>`, не `git add -A` — иначе в коммит уезжает параллельная правка владельца. Дифф метаданных смотреть отдельно: `git diff --stat -- '*.mdo' '*.form'` (профиль Designer-XML — `'*.xml'`). Чужую правку не прицеплять молча: оставить в дереве или спросить ([[questions-as-options]]). Особое внимание — свойствам, меняющим структуру таблиц (длина кода/наименования, длины и типы реквизитов, состав измерений): по наблюдению экземпляра, сокращение длины при реструктуризации обрезает данные молча — перед обновлением базы с данными такие правки сверять отдельно.
- **Неотслеживаемую папку (`?? dir/`) индексировать целиком** и после `git add` проверить парность файлов (EDT: `.mdo` + `.bsl` (+ `.form`); Designer-XML: `.xml` + `Ext/`) — по одному файлу легко закоммитить модуль без его объекта.
- **Незнакомая правка в дереве** — показать диффом и спросить окном вариантов («ваша / откатить / не знаю»), а не «чинить»: она может быть намеренной. Происхождение записать в changelog ([[ask-before-changing]], [[work-journals-and-commits]]).

**Инструменты форков (в плагине, `tools/git/`; с 17.10.2026 на Python):** `fork-status.py` — карта форков одним взглядом: отставание каждого от ствола, свои коммиты, последний коммит (хаб — `--hub`, иначе `ONEC_GIT_HUB`, иначе `origin`); `fork-port.py --from <форк> --paths <путь> …` — перенос среза работы из другого форка в текущий клон напрямую, минуя ствол (`--preview` — только показать; стейдж без коммита); `git-branches.py` — обзор монорепо: граф хаба и таблица «клон → ветка → впереди/позади». Запуск — `python <папка плагина>/tools/git/<скрипт>` из клона конфигурации (путь к папке плагина называет сообщение в начале сессии).

**Принуждение (с 4.8.0):** напоминание каждого хода (`tools-gate.md`, фрагмент «а не копированием файлов», `contour-tests` §24) и проверка после факта: команда копирования (`cp`, `Copy-Item`, `robocopy`, `xcopy`, `shutil.copy`), затрагивающая два рабочих дерева одного репозитория (`git worktree list`), — `stop-guard` пишет срабатывание в `logs/answer-check.jsonl`, `answer-feedback` показывает его модели в начале следующего хода (§25). Пропуск чекеров после слияния не ловится.
