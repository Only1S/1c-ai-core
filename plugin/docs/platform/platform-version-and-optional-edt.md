# Правило: платформа и EDT — профиль проекта, не требования ядра

Ядро **не привязано** к версии платформы 8.3.27 и к наличию EDT; работает на любой 8.3 и на 8.5 (на стенде профильная 8.3.27.2214, рядом установлены 8.3.27.1719 и 8.5.1.1343, серверные агенты обеих линий запущены — сверено 16.10.2026). У проекта может быть 8.3.25 и конфигурация на **обычных формах** (равно как десктопное или мобильное приложение) — с ней работают через **XML-выгрузку конфигуратора** (`DumpConfigToFiles`), **включая версионирование в git**; это полноценный поддерживаемый профиль. Вид разработки (десктоп / мобильная / управляемые формы / обычные формы) — это профиль проекта: git-механизм у всех **один** (выгрузка в файлы), различается лишь доступность EDT-инструментов.

**Why:** упоминания «8.3.27» в доках — примеры/факты стенда, а не требования: инструменты версию не зашивают (`bsl-platform` читает справку из каталога платформы по `ONEC_PLATFORM_BIN` (манифест передаёт его флагом `-p` в `.mcp.json`), а `bsl-context` получает каталог платформы от запускалки плагина `tools/servers/run-bsl-context.py` — родитель папки из `ONEC_PLATFORM_BIN` (до ones-core 4.0.0 это был http-сервер со своим `config.toml`, и платформа правилась в нём отдельно) (сверено 16.10.2026; прежняя формулировка объединяла два разных источника); db-скиллы зовут `1cv8`/`ibcmd` из `v8path`; `code-index`/`bsl-analyzer`/скиллы `cf-*`/`meta-*`/`form-*`/`skd-*`/`role-*`/`nkdk` работают по XML-выгрузке любой версии). Жёсткое «8.3.27+ и EDT обязательны» отсекало бы реальные проекты без причины.

**How to apply:**
1. **Версия платформы** — только из манифеста (`ONEC_PLATFORM_BIN`), спрашивается командой `/ones-core:setup` (шаг 1; передаётся в `connect-project.py` как `--platform-bin`); в доках версии писать как «пример/проверено на», не как требование. Несколько платформ на машине — путь на нужную.
2. **EDT опциональна.** Профиль «без EDT»: сервер `edt-mcp` не включается в `.mcp.json` проекта (`/ones-core:setup` без EDT — `connect-project.py` вызывается без `--edt-port`), переменная `EDT_MCP_PORT` опускается; health-check при отсутствии сервера ничего не требует. Все задачи идут маршрутом **Designer-XML** (карта [[task-recipes]] §0): выгрузка/загрузка — `DumpConfigToFiles`/`LoadConfigFromFiles` (скиллы `db-dump-xml`/`db-load-xml`), правка метаданных — скиллы `meta-*`/`cf-*`/`subsystem-*`/`role-*` + `nkdk`, код — правка `.bsl` в выгрузке + `bsl-analyzer`/`bsl-context` (валидация), индекс — `code-index` по той же выгрузке, живая база — `1c-toolkit`/db-скиллы.
   - **git ≠ EDT.** Подключение к git — это **та же выгрузка конфигуратора** (`DumpConfigToFiles` → файлы → git), способ **старше EDT** и работающий для любой конфигурации на любой 8.3. EDT — лишь git-родной **редактор** поверх, удобный для управляемых форм, а **не** механизм версионирования. Поэтому конфигурация, которую EDT физически не открывает (**обычные формы**), под git ложится нормально — маршрутом Designer-XML; форк такой конфигурации — `git worktree` ([[config-git-forks-and-merges]]). «Нет EDT» и «нельзя в git» — **не связаны**.
3. **Чего нет без EDT** (честные границы): `revalidate_objects`/`get_project_errors` (замена: `db-load-xml` на тестовую базу — конфигуратор сам валидирует при загрузке, затем `/CheckConfig`; нет доступа к тестовой базе — одноразовая файловая база, [[designer-batch-runs]]; что `/CheckConfig` не ловит — [[full-checker-set-before-done]], «Слепые зоны»), скриншоты форм (замена: скриншот от пользователя или `web-test`), рефакторинг-rename с обновлением ссылок (замена: `nkdk rename_item` + grep-сверка).
4. **Формы:** скиллы `form-*` и `1c-forms` работают с **управляемыми** формами. **Обычная (ordinary) форма в выгрузке `DumpConfigToFiles` — бинарь** (исправлено 19.09.2026; прежде здесь стояло «точечная правка XML», это неверно): форма лежит в `Forms/<Форма>/Ext/Form.bin` (контейнер 1С, сигнатура `FF FF FF 7F`), и **модуль обычной формы — внутри него**, отдельного `.bsl` нет; меню обычного приложения так же лежит бинарём в `Interfaces/<Интерфейс>/Ext/Interface.bin`. Правкой XML их не изменить. Модуль такой формы не видят `Read`/`Edit`, `code-index` (по данным одного проекта индексирует только управляемые формы), `bsl-analyzer` и хук `validate-bsl`. Найти код по модулям всех обычных форм — скилл `form-bin-module` (зеркало `.bsl` вне выгрузки). **Разобрать, поправить, нарисовать и собрать одну форму — скилл `form-ordinary`** (с 19.10.2026): `unpack` раскладывает `Form.bin` на `form.frm`, `form.bsl` (модуль — текстом) и `info.txt`; `edit --ops` правит форму в объёме просьбы и сам обновляет контейнер; `validate`, `lint` и `render --before` (приближённая картинка «до / после») — проверка. На копиях 1617 форм реальной конфигурации разбор и сборка `form.frm` байт в байт — 1616 из 1617 (одна форма — отказ с названной причиной), модули совпали с `form-bin-module`. **Загрузку изменённой формы в базу у нас ещё не проверяли** (автор скилла проверял в 1С 8.3.27): каждая правка подтверждается загрузкой в тестовую базу (`db-load-xml`) и проверкой конфигурации — до этого не «готово». `v8unpack` (скилл `cf-unpack`) для правки форм не годится: у него нет карты формата, повреждение не поймает ни один чекер.
   - **XML-путь дать пользователю новую форму или кнопку — управляемая форма рядом** (`form-add`/`form-compile`, `Forms/*/Ext/Form.xml`): она загружается и компилируется в конфигурации с режимом запуска «обычное приложение» (по данным одного экземпляра: 8.3.27, режим совместимости 8.3.18, `/CheckConfig` по пяти контекстам). Влияет ли на её открытие в толстом клиенте свойство `UseManagedFormInOrdinaryApplication` — не проверено. Вендорскую обычную форму в управляемый скелет не «упрощать» без запроса.
   - **Под git** обычная форма версионируется, но её дифф бинарный — код формы в git не диффится; `.bsl` модулей объекта и менеджера, макеты и XML метаданных диффятся нормально. EDT-инструменты для неё недоступны (нет `form-*`-скиллов, скриншотов, `revalidate_objects`/`get_project_errors`) — см. п.3; вместо скриншота — `form-ordinary render` (картинки платформы в плагине нет — на их месте серые квадраты). Бинарность `Form.bin` проверена на выгрузке 8.3.27 (режим совместимости 8.3.18); есть ли у `DumpConfigToFiles` режим, разворачивающий обычные формы в текст, — не проверено, и документация об этом молчит: «Руководство разработчика» 8.3.27, гл. 2, описывает выгрузку формы только как `Ext/Form.xml` и `Ext/Form/Module.bsl` (конспект — скилл `1c-platform-kb`, `its-docs/dev-gl02`), так что `Form.bin` обычной формы — наблюдение, а не документированный формат.
5. Инструмент, реально требующий минимальной версии (встретится — например, фича `ibcmd` конкретной сборки), фиксирует это **у себя в тул-доке** зондом ([[probe-tool-capabilities]]), а не глобальным требованием ядра.

**Принуждение (с 4.7.0):** проверка при старте сессии в проекте — `plugin/hooks/session-start.py`: в папке `ONEC_PLATFORM_BIN` нет `1cv8.exe` — предупреждение модели; регресс `contour-tests` §24б.
