# Правило: своё проекта — в `docs-project/`

В **каждом проекте** (и в мастере ядра) знания разделены границей папок — файлы ядра и файлы проекта не смешиваются. «Project» в имени папки = **«личное этого проекта»**, а не «1С-проект»: у мастера его «проект» — само ядро, поэтому журналы разработки ядра тоже лежат в `docs-project/` (аналогия: `docs/` — прошивка, приходит с плагином целиком; `docs-project/` — пользовательские данные, обновление их не трогает):

| Папка | Что живёт | Кто меняет |
|---|---|---|
| `docs/` | знание ядра (правила `type: feedback`, справочники `type: reference`) + оглавление `MEMORY.md` | в проекте приходит с плагином ones-core и руками не правится ([[plugin-in-project]]); в мастере — обычные правки ядра |
| `docs-project/` | ВСЁ своё проекта: **журналы** (`worklog`, `changelog`, `project-status`), оглавление `INDEX.md`, специфика конфигурации, присланные проектные API, ТЗ, планы консилиума, чек-листы прогонов, ревью модулей | сам проект |

**Why:** пользователь зафиксировал (12.07.2026) — файлы ядра и проекта не должны смешиваться, чтобы ядро обновлялось быстро и безболезненно. До разделения «проектное» отличалось от «ядрового» только фронтматтером — граница не была машинно-проверяемой. Отдельная **верхнеуровневая** папка даёт дизъюнктный префикс путей: сборка плагина берёт только `docs/`, и своё проекта в чужие проекты не уезжает по построению.

**How to apply:**
1. **Маршрутизация — по происхождению знания, не по `type:`.** Написал проект (любой тип — правило конфигурации, проектный API, план) → `docs-project/<slug>.md` + строка в её оглавлении `docs-project/INDEX.md`. Ядро приходит плагином и в проекте не копируется. Правило, полезное всем проектам, → предложение в ядро через `/ones-core:report-issue` (в мастере — правка `docs/`), не правка файлов плагина в проекте.
2. **Журналы — в `docs-project/`:** `worklog`/`changelog`/`project-status` — контент проекта (решение пользователя 12.07.2026); путь в хуке после компакции один и тот же в мастере и в проектах. `MEMORY.md` — оглавление ядра — остаётся в `docs/`. В журналах допустим нарратив об операциях над конкретными проектами с их именами (по прямой просьбе владельца); поэтому скан утечек имён health-check покрывает только ядровую часть, `docs-project/` исключён (решение пользователя 12.07.2026). Исключение — правки самой конфигурации 1С, если она ведётся в своём git: их журнал — в её репозитории ([[journal-placement]]).
3. **Оглавление проектной папки — `docs-project/INDEX.md`:** одна строка на док (формат как у `MEMORY.md`). Полноту в мастере стережёт health-check (§4b), если папка существует и непуста; в проекте health-check нет — там новый док, не внесённый в `INDEX.md`, отмечает подсказка `lint-project-docs` при его заведении (Write), когда `INDEX.md` уже есть.
4. **Wikilinks:** `[[слаг]]` резолвится по обеим папкам; **коллизия слага** между `docs/` и `docs-project/` запрещена (health-check FAIL). Ядровые доки на проектные не ссылаются (иначе ссылка уедет с плагином в чужой проект) — **кроме слагов, которые есть в каждом проекте по построению:** `[[worklog]]`/`[[changelog]]`/`[[project-status]]` (журналы) — ссылка резолвится на файл того проекта, где док читается ([[work-journals-and-commits]]). Ссылки на **прочие** проектные доки (планы, специфика, правила мастера) из ядровых доков давать НЕ wikilink'ом, а бэктик-упоминанием; с 30.10.2026 такую вики-ссылку ловит health-check (FAIL), регресс — `contour-tests` §137.
5. **В мастере `docs-project/` — журналы и знания самого мастера + `INDEX.md`**, в том числе правила, нужные только мастеру (работа как ядро, выпуск версии — `docs-project/rules/`). В проекте папку заводит `/ones-core:setup`: свежие журналы и `INDEX.md`; чужую `docs-project/` целиком не брать.
6. **В плагин папка не попадает:** сборка плагина (`tools/release/build-plugin.py`) берёт только `docs/` мастера, поэтому `docs-project/` мастера и проектов в чужие проекты не уезжает.
7. **Конфликты и приоритет (решение пользователя 12.07.2026):** проектное правило **переопределяет ядровое** (специфичное выше общего), но только с явной строкой «**Переопределяет: [[слаг]]**» в проектном доке; непомеченное противоречие проект↔ядро = находка: показать владельцу и предложить в ядро через `/ones-core:report-issue` (в мастере его ловит ревизия `/audit`). **Инварианты безопасности ядра не переопределяются** проектными доками ([[secrets-and-production-database]]: секреты, боевая база, запрет обхода pre-commit) — только явным решением пользователя. Противоречия внутри ядра и дубли — по протоколу [[capture-knowledge]]: показать пользователю, решение зафиксировать правкой/слиянием.
8. **Раскладка `docs-project/` — сначала по виду документа, внутри — по темам (решение владельца 17.10.2026).** Документы разного вида не смешиваются в одной папке: **документация внешних API** (разобранные API сервисов, коллекции, спецификации) — отдельно; **внутренняя документация** проекта (знания о своей конфигурации, решения, приёмы) — по темам; **ТЗ** — своя папка; **сведения о других конфигурациях** (смежные базы, эталоны, чужие приложения как образцы) — своя папка; журналы, `INDEX.md` и `project-status` — в корне. Названия папок — латиница через дефис ([[file-and-folder-names]]); при раскладке существующих документов — показать владельцу таблицу «папка → документы» до переноса, а имена файлов с вики-ссылками на них менять только вместе со ссылками.
