# Журнал форков — в репозитории конфигурации, по веткам

**Правило.** Каждый форк 1С-конфигурации пишет свой журнал в **свою git-ветку** — в репозитории **конфигурации** (config-монорепо, хаб `<GIT_HUB>\<config>.git` — [[config-git-forks-and-merges]]), а НЕ в общий `docs-project/changelog` экземпляра на `main`.

**Почему так.** Все чат-сессии над разными форками делят **один каталог** экземпляра → одна git-ветка за раз (ветка — свойство рабочего дерева, не сессии). Ветвить журналы форков внутри экземпляра без worktree/дублирования всего тулинга нельзя. Зато в config-монорепо ветки форков **уже есть** — журнал 1С-правок едет вместе с 1С-кодом, который описывает, и наследует готовый поток слияния через хаб.

## Шов: куда какая запись (по происхождению правки)
- **1С-правки** (метаданные / формы / BSL / роли конфигурации и её форков) → **config-репо**: `docs/worklog.md` + `docs/changelog.md`, на ветке форка. Слияние в config-`main` — через хаб.
- **Тулинг / ядро** (правила, хуки, MCP-конфиг, доки, скрипты экземпляра) → **экземпляр**: `docs-project/worklog.md` + `docs-project/changelog.md`, на `main`.

Тот же принцип происхождения, что и шов `docs/` (ядро) ↔ `docs-project/` (своё) — [[project-knowledge-folder]], только для журналов: место записи определяется тем, ЧТО правилось, а не тем, кто правил.

## Раскладка в config-репо
Корень config-монорепо (primary и клоны форков) несёт папку `docs/` (не игнорируется git, лежит рядом с проектами конфигурации и расширений):
- `docs/worklog.md` — нарратив 1С-работы;
- `docs/changelog.md` — посекундная хронология правок (строка на файл), формат как в [[work-journals-and-commits]].

**Один файл на ветку** (не на форк-имя): изоляция достигается ветвлением. При слиянии форк→`main` возможен tail-конфликт в append-таблице — разрешать сохранением **обеих** записей в хронологии (журнал сливается тем же коммитом, что и 1С-правки).

## Пропагация на ветки форков
`docs/` заводится на config-`main`. Чтобы ветка форка получила журнал: при поднятии/актуализации форка `git merge origin/main` (или ветка создаётся от актуального main).

## Граница во времени
При переходе экземпляра на эту схему историческая 1С-работа **до даты перехода** остаётся заморожённой в `docs-project/` экземпляра. С даты перехода новые **1С-записи** — в config-репо `docs/`. Ретро-миграция не делается (без потери контекста).

## Что остаётся в экземпляре (не переезжает)
`worklog.md` / `changelog.md` в `docs-project/` продолжают вести **тулинг-хронику** (правила, инструменты, аудиты, обновления ядра, health-check) на `main` — форки её не касаются.

**Уточняет** [[work-journals-and-commits]] для **всех правок конфигурации, которая ведётся в своём git** — основной ветки и форков (work-journals-and-commits остаётся в силе для журнала проекта: инструменты, правила, хуки). Общие правила ([[capture-knowledge]], [[project-knowledge-folder]], `CLAUDE.md`) ссылаются сюда. Связано: [[config-git-forks-and-merges]], [[project-knowledge-folder]], [[regenerate-doc-index]].

**Принуждение (с 4.8.0):** напоминание каждого хода — строка в `plugin/hooks/tools-gate.md` (фрагмент «в журнал ЕЁ репозитория» держит `contour-tests` §24) и после сжатия контекста. Проверка после факта: в ходе правились файлы 1С в git-репозитории конфигурации (`ONEC_PROJECT_SRC`), журнал проекта (`docs-project/worklog.md` / `changelog.md`) правился, а `docs/worklog.md` / `docs/changelog.md` её репозитория — нет: `stop-guard` пишет срабатывание в `logs/answer-check.jsonl`, `answer-feedback` показывает его модели в начале следующего хода (§25).
