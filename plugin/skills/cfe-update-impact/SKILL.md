# /cfe-update-impact — что релиз типовой сделает с расширением

Сравнивает **старую и новую** версии конфигурации и по дельте показывает, какие части расширения она задевает. Только читает выгрузки и выдаёт отчёт, ничего не правит. Код выхода `1`, если есть хотя бы одна `ПРОБЛЕМА`.

## Чем отличается от соседних скиллов

| Скилл | Что видит |
|---|---|
| `/cfe-diff` | **одна** версия: состав расширения, перечень перехватчиков и callType, перенос `#Вставка` |
| `/cfe-patch-method -Check/-Actualize` | **одна** версия: дрейф `&ИзменениеИКонтроль` против текущей конфигурации и перенос правок. Понимает оба написания аннотаций и маркеров — русское и английское (`#Вставка`/`#Insert`, `&ИзменениеИКонтроль`/`&ChangeAndValidate`; проверено по коду 16.10.2026) |
| `/db-cfe-admin check` | вердикт платформы, уже после загрузки в базу |
| **`/cfe-update-impact`** | **дельта релиза** по трём выгрузкам: все четыре вида перехвата, обработчики форм, заимствованные объекты и макеты |

## Входы

Три выгрузки Конфигуратора (DumpConfigToFiles, `/db-dump-xml`):
- **старая** версия конфигурации — та, под которую расширение написано сейчас;
- **новая** версия — релиз, на который обновляемся;
- **расширение**.

Формат EDT не поддерживается: нужна выгрузка через платформу. Например, выгрузить тестовую базу до и после обновления конфигурации или загрузить CF обоих релизов во временную базу по очереди.

## Команда

```bash
PYTHONIOENCODING=utf-8 python "${CLAUDE_SKILL_DIR}/scripts/cfe-update-impact.py" -ExtensionPath <расширение> -OldConfigPath <старая> -NewConfigPath <новая>
```

| Параметр | Смысл |
|---|---|
| `-ExtensionPath`, `-OldConfigPath`, `-NewConfigPath` | три выгрузки (обязательны) |
| `-ShowOk` | показывать и неизменённые пункты (по умолчанию только их число) |
| `-Diff` | печатать дифф изменённого оригинала: старая → новая |
| `-DiffLimit N` | строк диффа на метод, по умолчанию 60 |
| `-Json <файл>` | дополнительно записать отчёт в JSON (разделы, уровни, сводка) |

Коды выхода: `0` — проблем нет, `1` — есть `ПРОБЛЕМА`, `2` — ошибка входа (нет `Configuration.xml`, передан EDT, перепутаны расширение и конфигурация).

## Что проверяется

Уровни: **ПРОБЛЕМА** — расширение сломается или молча потеряет правки вендора; **ИНФО** — изменение есть, но перехват продолжит работать, сверить логику; **ОК** — дельта не задела.

**1. `&Перед` / `&После` / `&Вместо`.** Метод-оригинал ищется в том же модуле старой и новой версии, путь модуля тот же, что в расширении.
- модуль или метод исчез → ПРОБЛЕМА; при совпадении тела подсказывает новое имя метода;
- число параметров перехватчика ≠ оригиналу новой версии → ПРОБЛЕМА. Сигнатура разбирается целиком: запятая внутри строкового значения параметра по умолчанию подсчёт не ломает;
- изменился вид метода (процедура/функция) или директива компиляции → ПРОБЛЕМА; `&Перед`/`&После` на функции → ИНФО (перехват не меняет возвращаемое значение; запрет платформой не подтверждён, поэтому не ПРОБЛЕМА);
- тело оригинала изменилось: `&Вместо` → ПРОБЛЕМА (отдельно помечено, вызывается ли `ПродолжитьВызов`), `&Перед`/`&После` → ИНФО;
- изменились только комментарии или форматирование → ИНФО.

**2. `&ИзменениеИКонтроль`.** Контрольная часть перехватчика — тело без блоков `#Вставка` и без маркеров `#Удаление` — сверяется с оригиналом построчно. Отступы и пустые строки не важны, комментарии важны, как в правилах `/cfe-patch-method`.
- оригинал изменился в релизе → ПРОБЛЕМА «переналожить вставки». Сюда же попадает правка, где у вендора изменился только комментарий: контроль всё равно разойдётся;
- правки расширения уже есть в новом оригинале → ПРОБЛЕМА «перенесены в основную, перехватчик можно удалить»;
- оригинал не менялся, а контроль расходится → ПРОБЛЕМА «дрейф был и до обновления».

**3. Обработчики форм с callType.** Берутся события уровня формы, события **любых** элементов (не только полей ввода) и `Action` команд из заимствованной формы с `BaseForm`. Базовый обработчик ищется в старой и новой `Form.xml`, его тело сравнивается в модуле формы. Соответствие: `Before` = `&Перед`, `After` = `&После`, `Override` = `&Вместо`.
- элемент или команда исчезли, у события пропал базовый обработчик → ПРОБЛЕМА;
- тело базового обработчика изменилось, или вендор добавил обработчик: `Override` → ПРОБЛЕМА, `Before`/`After` → ИНФО;
- владельца нет в базовой форме, то есть это собственный элемент расширения → ИНФО.

**4. Заимствованные объекты, формы и макеты** (`ObjectBelonging=Adopted`).
- объект удалён в новой версии → ПРОБЛЕМА. Если в том же каталоге найден объект с тем же uuid, подсказывает новое имя;
- uuid объекта в новой версии ≠ `ExtendedConfigurationObject` расширения (вендор пересоздал объект) → ПРОБЛЕМА;
- заимствованный реквизит/ТЧ/значение удалён у вендора → ПРОБЛЕМА, изменён → ИНФО; прочие изменения объекта → ИНФО со счётчиками;
- заимствованная форма изменилась у вендора → ИНФО (`BaseForm` расширения — снимок прежней формы);
- макет (в т.ч. СКД) изменён у вендора, а в расширении своя копия, отличная от новой → ПРОБЛЕМА. Копии нет → ИНФО.

## Как сравнивается

- Методы находятся по токенам, а не регуляркой по `КонецПроцедуры`: строки, многострочные литералы (`|…`) и комментарии учтены. Слово `КонецПроцедуры` внутри строки или комментария метод не обрывает.
- «Тело изменилось» считается без пробелов и комментариев; регистр идентификаторов не различается, как и в самом языке.
- XML сравнивается в канонической форме, пробельный текст отброшен.
- Аннотации и маркеры понимаются в обоих написаниях: `&Around`, `&ChangeAndValidate`, `#Insert`/`#Delete`. Хвостовой комментарий на строке маркера допустим.

## Дальше по отчёту

1. `&ИзменениеИКонтроль`: `/cfe-patch-method -Check`, затем `-Actualize` с `-ConfigPath` = **новая** версия. Английское написание аннотаций скилл понимает (исправлено поставщиком по issue Nikolay-Shirokov/cc-1c-skills#97; сверено по коду 16.10.2026).
2. `&Вместо` с изменённым оригиналом: перенести правки вендора в перехватчик. Если `ПродолжитьВызов` нет, подумать о переходе на `&ИзменениеИКонтроль` (диагностика v8cs `change-and-validate-instead-of-around`): тогда платформа сама сообщит о следующем расхождении.
3. Формы: новая форма через `/form-info`, правка обработчика, затем `/form-validate`.
4. Макеты: перенести правки вендора в копию расширения (`/mxl-decompile`, `/skd-info`).
5. Итог: `/cfe-validate` → загрузка на тестовую базу → `/db-cfe-admin check`.

## Ограничения

- Только отчёт. Трёхсторонней автосклейки нет, правки делаются скиллами из п. «Дальше».
- Переименования угадываются эвристикой: метод — по совпадению тела в том же модуле, объект — по uuid в том же каталоге. Перенос метода в другой модуль не распознаётся: будет «метод исчез».
- Метаданные объекта сравниваются целиком; подробно, по именам, разбираются только заимствованные дочерние объекты.
- Проверено 19.09.2026: синтетические выгрузки на 25 ожиданий (каждый статус; без дельты — 0 проблем, код 0) и реальная выгрузка расширения с его базой. Разбор 400 крупнейших модулей реальной конфигурации: 25 222 метода, набор имён совпал с построчным подсчётом объявлений, каждый метод заканчивается на строке `КонецПроцедуры`/`КонецФункции`. Прогона на паре настоящих релизов ещё не было.

## Происхождение

Скилл наш, Python 3, только стандартная библиотека. Идея и перечень проверок взяты по мотивам [xnd1124/CfeUpdater](https://github.com/xnd1124/CfeUpdater). У репозитория нет лицензии, поэтому код, регулярки и тестовые наборы не брались, реализация своя. В отличие от исходной обработки скилл работает без GUI, внешней компоненты и программы сравнения, разбирает сигнатуру вместо подсчёта запятых и проверяет все элементы формы и команды.
