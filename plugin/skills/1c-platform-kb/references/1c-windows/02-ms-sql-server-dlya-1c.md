Опасные исправлены прямо в тексте: `STOPAT` в каждом `RESTORE LOG` (разд. 9.4), однопользовательский режим и `AUTO_UPDATE_STATISTICS_ASYNC` (разд. 9.5). Остальные перечислены здесь:
> 1. **Флаг 2371** на 2016+ теряет действие только при уровне совместимости базы 130 и выше; при 120 и ниже он по-прежнему нужен (`mssql/01`, `mssql/02`).
> 2. **`sys.dm_tran_version_store_space_usage`** есть с SQL Server 2016 SP2, а не с 2017.
> 3. **Пометки, которые подтверждены:**
>    - онлайн-перестроение индексов — только в Enterprise;
>    - `REBUILD` сохраняет `ALLOW_PAGE_LOCKS = OFF` (параметры берутся из `sys.indexes`);
>    - `sp_updatestats` обновляет только изменённую статистику;
>    - логические имена `modeldev`/`modellog`;
>    - Full-Text для 1С не нужен (ИТС-КС разд. 2.2.3.1);
>    - запрос к `ring_buffer` сеанса `system_health`;
>    - названия отчётов Query Store;
>    - порт 1433 и `IPAll` — факты Microsoft.
> 4. **`ONLINE = ON`** держит не одну блокировку в конце, а три: короткую S в начале, IS в основной фазе и Sch-M в конце.
> 5. **Настройки файлов базы `model`** (прирост `FILEGROWTH`) новая база **не наследует** — копируется только начальный размер файла данных. Скрипт с `FILEGROWTH = 512MB` для `modeldev`/`modellog` прирост новых баз не задаёт (`mssql/02`, разд. 11.1).
> 6. **«Без `/SQLSVCACCOUNT` служба получит виртуальную учётную запись»** — не подтверждено: в справке setup параметр помечен обязательным. В примере `setup.exe /Q` нужен ещё `/SUPPRESSPRIVACYSTATEMENTNOTICE`.
> 7. **«Shared Memory включить» — источник указан неточно.** ИТС-мет 5904 советует включать протокол при сервере 1С на той же машине, а то, что он включён по умолчанию, — факт Microsoft. С Shared Memory не работает оптимизированная реструктуризация (`UpdateDBCfg=v2`, ИТС-адм прил. 3.17.23).
> 8. **OLE DB Driver.** Версия 19 по умолчанию `Encrypt=Mandatory` и проверяет сертификат при любом сервере; 18 и **более ранние** по умолчанию не шифровали.
> 9. **`COLLATE Cyrillic_General_CI_AS`** в примере создания базы — ⚠: какую сортировку ожидает платформа, ИТС прямо не пишет; у пользователя конфигурации WE (`mssql/03`, разд. 3.6).
> 10. **Ежедневная очистка кеша планов** на 2016+ не обязательна (`mssql/05`, разд. 7.1). Ежедневный `FULLSCAN` по всем таблицам после ночного `REBUILD` дублирует работу — обновлять только изменённую статистику (`mssql/05`, разд. 12.2).
> 11. **Модель восстановления у новых баз** («Express — простая, Standard/Enterprise — полная») MS Learn конкретно не называет — это практика.
> 12. **`sqlcmd` из SQL Server 2025** (ODBC) по умолчанию проверяет сертификат — в заданиях с самоподписанным сертификатом нужен `-C` (`mssql/04`).
> 13. **Поле «Соединение с СУБД» сеанса** описано в ИТС-КС разд. 5.2.11.1.
> 14. **Сценарий 1С для Extended Events есть** — в ИТС 6006 (`../its-metod/vzaimoblokirovki-i-oshibki-blokirovok.md`, 2.4.6).
> 15. **Блокировка всей таблицы в автоматическом режиме** бывает, когда остатки пустой таблицы регистра проверяются запросом `ДЛЯ ИЗМЕНЕНИЯ` (ИТС-мет 2707).

## Кратко — главные факты и команды

1. **MS SQL — только при рабочих серверах 1С на Windows**: рабочие процессы и автономный сервер на Linux с ним не работают [ИТС-КС разд. 2.3; ИТС-адм разд. 7.2]. Сам SQL Server может стоять на Linux [v8.1c.ru].
2. **Версии для 8.3.27:** 2000 SP1 (реком. SP4), 2005 SP3, 2008 SP1, 2008 R2, 2012, 2014, 2016, 2017, 2019, **2022**; при режиме совместимости выше 8.3.7 — минимум 2005 [ИТС-КС разд. 1.5.4]. В 8.5.1 список тот же [`otlichiya-8.5.1`]. **SQL Server 2025 нет ни в ИТС, ни на v8.1c.ru (19.10.2026)** ⚠.
3. **Поддержка Microsoft** [MS Learn]: 2016 — закончилась 14.07.2026 (дальше платные ESU); 2017 — до 12.10.2027; 2019 — до 08.01.2030; 2022 — основная до 11.01.2028, расширенная до 11.01.2033. Новая установка на октябрь 2026 — **2022 с последним CU**.
4. **Express**: 1 сокет или 4 ядра, 1410 МБ буферного пула, база до 10 ГБ (2022) / 50 ГБ (2025), без SQL Server Agent [MS Learn] — только малые базы.
5. **Драйвер на рабочих серверах 1С** — OLE DB Driver for SQL Server или Native Client [ИТС-КС разд. 1.5.4]; Native Client с SQL Server 2022 не поставляется; OLE DB Driver 19 по умолчанию требует шифрования [MS Learn]. На рабочих местах драйвер не нужен — с СУБД работают только процессы кластера [ИТС-КС разд. 2.1].
6. **Права логина кластера**: роль `processadmin` или `sysadmin` [ИТС-КС разд. 3.2.3]; создание базы — `sa`/`dbcreator`, готовая база — владелец + чтение `master` + `tempdb` [ИТС-адм разд. 5.2.1.3.2]; **свой логин на каждую ИБ** [ИТС-КС прил. 3, разд. 3.7].
7. **Смещение дат** `0`/`2000` задаётся один раз; при регистрах накопления или бухгалтерии — **2000** [ИТС-адм разд. 5.2.1.3.2]. Умолчания разные: `SQLYOffs` — 0 [ИТС-адм прил. 7, разд. 7.7.4], `ibcmd --date-offset` — 2000 [ИТС-адм прил. 4, разд. 4.10.4.2]. Указывать явно.
8. **Установка**: смешанная проверка подлинности (`/SECURITYMODE=SQL`) [ИТС-мет 5904, 2019; MS Learn]; сортировка экземпляра берётся из языка ОС — на узбекской (`Uzbek_Latin_90_CI_AS`) или английской Windows задать явно, для русских конфигураций `Cyrillic_General_CI_AS` [MS Learn] ⚠; IFI — `/SQLSVCINSTANTFILEINIT=True` [MS Learn; ИТС-мет 5904].
9. **Память**: `max server memory (MB)` обязательно; при сервере 1С на той же машине — оставить долю 1С и не включать Lock Pages in Memory [ИТС-мет 5904, 2019]; Microsoft — ~75 % свободной памяти [MS Learn].
10. **`max degree of parallelism` = 1** [ИТС-мет 5904, 2019; 6008, 2023]; на время реструктуризации — `0`, потом вернуть [ИТС-мет 5945, 2018]. Microsoft советует до 8 — для 1С сознательно отступаем.
11. **tempdb**: 4–8 файлов одного размера (1С — 4 [ИТС-мет 5904]; Microsoft — по числу логических процессоров, не больше 8 [MS Learn]).
12. **Флаги трассировки** [ИТС-мет 5946, 2019]: на 2016+ флаги 610, 1117, 1118, 2371, 8048 без действия [MS Learn]; смысл сохраняют **1224** (или 1211) и **4199**; для SQL Server 2014 флаг 4199 требует сама платформа [ИТС-адм разд. 5.2.1.3.2].
13. **Протоколы**: TCP/IP вкл., Named Pipes выкл. [ИТС-мет 5904]. **Оптимизированная реструктуризация (`UpdateDBCfg=v2`) — только по TCP/IP**, не через `lpc:` [ИТС-адм прил. 3, разд. 3.17.23].
14. **Изоляция**: управляемые блокировки на SQL Server 2005+ — Read Committed Snapshot, автоматические — Repeatable Read/Serializable [ИТС-разр гл. 9, разд. 9.2.3.2]; версии строк — в `tempdb`. Монопольный режим 1С не переводит базу в `SINGLE_USER` [ИТС-адм разд. 6.7].
15. **С 8.3.22 у индексов 1С выключены страничные блокировки** — `REORGANIZE` на них падает: включить `ALLOW_PAGE_LOCKS`, реорганизовать, выключить [ИТС-мет 5837, 2022; MS Learn].
16. **Копии — средствами СУБД**, `.dt` — не резервная копия [ИТС-КС разд. 5.1.1; ИТС-адм разд. 6.7]; журнал регистрации и хранилище двоичных данных копируются отдельно [ИТС-адм разд. 6.9.2]. `WITH CHECKSUM`, внеплановые — `COPY_ONLY`, регулярное тестовое восстановление [MS Learn; ИТС-мет 5904, 5899].
17. **Журнал**: для загрузки `.dt` — модель «Простая» или «С неполным протоколированием» [ИТС-адм разд. 6.8]; `BACKUP LOG … WITH TRUNCATE_ONLY` [ИТС-мет 2373, 2008] **удалён** [MS Learn]; причина роста — `log_reuse_wait_desc`.
18. **Регламент** [ИТС-мет 5837, 2022]: статистика ежедневно `FULLSCAN` + очистка кеша планов (на 2016+ — `ALTER DATABASE SCOPED CONFIGURATION CLEAR PROCEDURE_CACHE` только своей базы [MS Learn]); индексы еженедельно; `DBCC CHECKDB` [ИТС-КС разд. 5.5.8; MS Learn].
19. **Медленная работа**: сначала ожидания (`sys.dm_os_wait_stats`) [ИТС-мет 6008, 2023]; лидеры — `sys.dm_exec_query_stats` [ИТС-мет 5861, 5813]; история — Query Store (в 2022 включён для новых баз) [MS Learn]; связь с кодом — техжурнал `DBMSSQL` + `<plansql/>` [ИТС-адм прил. 3, разд. 3.24]. DAC — `remote admin connections` = 1, вход `admin:sql01` [ИТС-мет 6008; MS Learn].
20. **Перенос на PostgreSQL**: `ibcmd infobase replicate --dbms=MSSQLServer … --target-dbms=PostgreSQL … --target-create-database` [ИТС-адм разд. 7.4.17] — запускать на Windows.
21. **PostgreSQL для 1С на Windows** поддерживается [ИТС-КС разд. 3.2.5.1]; совет `MaxUserPort` [ИТС-мет 1933, 2010] устарел — с Windows Server 2008 временные порты 49152–65535, настройка `netsh` [MS Learn].

## 1. Где MS SQL Server применим и что меняется в смешанной среде

### 1.1. Ограничения платформы

| Ситуация | Работает ли MS SQL | Источник |
|---|---|---|
| Рабочие серверы 1С на Windows x86-64 | да | [ИТС-КС разд. 1.2.1, 1.5.4] |
| Рабочие серверы на Linux (как у вас), ARM64, E2K | **нет** | [ИТС-КС разд. 2.3, 1.5.4] |
| `ibsrv` на Linux / на Windows | нет / да (без логина — аутентификация ОС от имени процесса `ibsrv`) | [ИТС-адм разд. 7.2; прил. 4, разд. 4.9] |
| SQL Server на Linux при рабочих серверах 1С на Windows | да | [v8.1c.ru] |
| MS SQL как **внешний источник данных** для сервера 1С на Linux (unixODBC) | да — это ВИД, не база ИБ | [ИТС-КС разд. 1.3.3]; `../1c/09`, п. 15 |
| Разная разрядность сервера 1С и СУБД | допустима | [ИТС-КС разд. 1.1, 1.2.1] |

Для ВИД на Linux: ODBC Driver 18 по умолчанию, по-видимому, требует шифрования — нужен доверенный сертификат SQL Server или `TrustServerCertificate=yes` в DSN ⚠ (не сверялось; для OLE DB Driver 19 подтверждено — 3.5).

### 1.2. Кто и чем подключается к SQL Server

- Каждая ИБ хранится в отдельной базе СУБД, с СУБД работают процессы кластера, а не клиенты [ИТС-КС разд. 2.1]: драйвер SQL и порт 1433 нужны **только рабочим серверам 1С** (и машине администратора с SSMS) [практика].
- Смешанная среда «клиенты Windows + сервер 1С на Linux»: к MS SQL никто не подключается; старые базы на MS SQL — перенести в PostgreSQL (12.2) или держать отдельный кластер на Windows.
- В консоли кластера «Соединение с СУБД» — идентификатор процесса сервера БД (на MS SQL — `session_id`), «Заблокировано СУБД» — кто блокирует [ИТС-КС разд. 5.2.12.2]: мост к DMV (разделы 7, 11).

### 1.3. MS SQL или PostgreSQL на Windows

Обе СУБД поддерживаются [ИТС-КС разд. 1.5.4, 1.5.8]. Против MS SQL при новом внедрении [практика]: платная лицензия (кроме Express/Developer; лицензирование SQL Server для 1С, в том числе «runtime»-лицензии, в источниках этой сессии не описано ⚠), невозможность позже перевести сервер 1С на Linux без переноса базы. За MS SQL: из консоли кластера можно разорвать соединение с долгим запросом — для PostgreSQL команда ничего не делает [ИТС-КС разд. 5.2.12.3]; зрелые штатные средства копирования и диагностики.

## 3. Установка экземпляра SQL Server для 1С

### 3.1. Размещение

- Сервер 1С и SQL Server — на одной машине или на разных, по нагрузке [ИТС-мет 2926, 2008]; при разнесении сеть между ними — 1 Гбит/с и выше [ИТС-КС разд. 1.3.1]. При совмещении — уменьшить `max server memory` на долю 1С и не включать Lock Pages in Memory [ИТС-мет 5904, 2019].
- Данные и журналы — на разных массивах; отклик «диска» данных 10–20 мс, журналов 1–5 мс [ИТС-мет 5904; 6008]. Разделы выровнены по 1024 КБ, кластер NTFS 64 КБ, без сжатия NTFS; файлы баз исключить из файлового резервного копирования [ИТС-мет 5904]; исключения антивируса ⚠ (в источниках этой сессии не описаны).
- Электропитание — «Высокая производительность» [ИТС-мет 5904; 5899]. Java на серверах 1С нужна для оптимизированной реструктуризации на MS SQL и PostgreSQL [ИТС-КС разд. 1.3.1].

```powershell
# PowerShell от имени администратора [практика]
fsutil fsinfo ntfsinfo D: | Select-String 'Bytes Per Cluster'   # ожидается 65536
powercfg /getactivescheme
powercfg /setactive SCHEME_MIN                                  # схема «Высокая производительность»
# только для ПУСТОГО диска — уничтожает данные тома:
# Format-Volume -DriveLetter D -FileSystem NTFS -AllocationUnitSize 65536 -NewFileSystemLabel SQLData
```

### 3.2. Выбор в мастере установки

| Шаг мастера | Что выбрать для 1С | Источник |
|---|---|---|
| Компоненты | только Database Engine Services (`SQLEngine`); Full-Text для 1С не нужен — у платформы свой полнотекстовый поиск ⚠ | [MS Learn] (имя компонента); ⚠ |
| Экземпляр | экземпляр по умолчанию `MSSQLSERVER` (порт 1433) — проще; именованный требует SQL Server Browser или фиксированного порта | [практика] |
| Учётные записи служб | по умолчанию — виртуальная учётная запись `NT SERVICE\MSSQLSERVER`; для копий на сетевую папку — доменная учётная запись или управляемая (gMSA); виртуальная выходит в сеть как учётная запись компьютера `ДОМЕН\ИМЯКОМПЬЮТЕРА$` | [MS Learn] |
| Право IFI | флажок «Grant Perform Volume Maintenance Task privilege…» (`/SQLSVCINSTANTFILEINIT=True`) | [MS Learn; ИТС-мет 5904] |
| Сортировка | для русских конфигураций — `Cyrillic_General_CI_AS` | [MS Learn] — таблица сортировок; ⚠ — для 1С (см. ниже) |
| Режим проверки подлинности | смешанный (`/SECURITYMODE=SQL`, пароль `sa` — `/SAPWD`) | [ИТС-мет 5904; MS Learn] |
| Администраторы SQL | доменная группа администраторов СУБД (`/SQLSYSADMINACCOUNTS`) | [MS Learn] |
| Каталоги, tempdb, MaxDOP, память (2019+) | данные, журналы, tempdb и копии — на разных томах; 4–8 файлов tempdb; MaxDOP `1`; `max server memory` — параметры в 3.3 | [MS Learn; ИТС-мет 5904] |

**Сортировка** экземпляра берётся из языка ОС и становится сортировкой системных баз, в том числе `tempdb` [MS Learn]: «Русский» и «Узбекский (кириллица)» → `Cyrillic_General_CI_AS`, «Узбекский (латиница)» → `Uzbek_Latin_90_CI_AS`, «Английский (США)» → `SQL_Latin1_General_CP1_CI_AS`, «Казахский» → `Kazakh_90_CI_AS` [MS Learn]. Какую сортировку платформа задаёт своей базе и важна ли ей сортировка `tempdb`, ИТС не описывает ⚠; известно лишь, что для страны «Казахстан» платформа берёт порядок как для «Россия» (в тексте ИТС — `Cyrillic_Generic_CI_AS`, у Microsoft имя `Cyrillic_General_CI_AS`) [ИТС-разр прил. 8, разд. 8.4]. Правило [практика] ⚠: сортировка экземпляра = сортировке баз 1С; для русских конфигураций — `Cyrillic_General_CI_AS`, для международных (WE, как у вас) — посмотреть на тестовой установке, какую сортировку получает база, созданная платформой. Смену языка ИБ на MS SQL ИТС не ограничивает (в отличие от PostgreSQL и Db2) [ИТС-адм разд. 6.5], кроме разделителя типа «Строка» [ИТС-разр гл. 24].

### 3.3. Установка из командной строки

Пример автоматической установки (командная строка от имени администратора, из каталога дистрибутива; параметры — [MS Learn, «Install SQL Server from the command prompt»]; значения — для 1С):

```bat
setup.exe /Q /IACCEPTSQLSERVERLICENSETERMS /ACTION=Install /FEATURES=SQLEngine ^
  /INSTANCENAME=MSSQLSERVER /SQLCOLLATION=Cyrillic_General_CI_AS ^
  /SECURITYMODE=SQL /SAPWD="<пароль sa>" /SQLSYSADMINACCOUNTS="CORP\sql-admins" ^
  /SQLSVCINSTANTFILEINIT=True /TCPENABLED=1 /NPENABLED=0 ^
  /SQLUSERDBDIR="D:\MSSQL\Data" /SQLUSERDBLOGDIR="L:\MSSQL\Log" ^
  /SQLTEMPDBDIR="T:\TempDB" /SQLTEMPDBFILECOUNT=4 /SQLTEMPDBFILEGROWTH=512 ^
  /SQLBACKUPDIR="E:\Backup" /SQLMAXDOP=1 /SQLMAXMEMORY=49152 /SQLMINMEMORY=0
```

- Без `/SQLSVCACCOUNT` служба получит виртуальную учётную запись `NT SERVICE\MSSQLSERVER` [MS Learn].
- `/SQLMAXDOP`, `/SQLMAXMEMORY`, `/SQLMINMEMORY` — для SQL Server 2019 и новее [MS Learn].
- Пароль `sa` в командной строке остаётся в истории и журналах установки [практика] — после установки смените его и отключите `sa` (`ALTER LOGIN [sa] DISABLE;`), если он не нужен.

Проверка после установки (SSMS или `sqlcmd -S sql01 -E`) [практика]:

```sql
SELECT SERVERPROPERTY('ProductVersion')     AS version,
       SERVERPROPERTY('ProductUpdateLevel') AS cu,
       SERVERPROPERTY('Edition')            AS edition,
       SERVERPROPERTY('Collation')          AS server_collation,
       SERVERPROPERTY('IsIntegratedSecurityOnly') AS windows_auth_only;   -- 0 = смешанный режим
SELECT servicename, service_account, instant_file_initialization_enabled
FROM sys.dm_server_services;                                             -- [MS Learn]
SELECT sql_memory_model_desc FROM sys.dm_os_sys_info;                    -- CONVENTIONAL / LOCK_PAGES [MS Learn]
```

### 3.4. После установки: службы, сеть, брандмауэр

- **Последние обновления** (CU) — обязательны [ИТС-мет 5904, 2019]; список выпусков — страница Microsoft «Latest updates and version history for SQL Server» [MS Learn].
- **Протоколы** (SQL Server Configuration Manager → Сетевая конфигурация SQL Server): TCP/IP — включить; Named Pipes — выключить; Shared Memory — по умолчанию включён [ИТС-мет 5904, 2019]. Изменение протоколов вступает в силу после перезапуска службы.
- **Порт**: экземпляр по умолчанию слушает TCP 1433 [практика]; для именованного экземпляра задайте статический порт в свойствах TCP/IP (IPAll → TCP Port) [практика].
- **Брандмауэр** на SQL Server — пустить порт только с рабочих серверов 1С и машин администраторов (PowerShell от имени администратора) [практика]:

```powershell
New-NetFirewallRule -DisplayName 'SQL Server 1433 from 1C' -Direction Inbound -Protocol TCP `
  -LocalPort 1433 -RemoteAddress 10.10.0.21,10.10.0.22 -Action Allow
# проверка с рабочего сервера 1С:
Test-NetConnection sql01 -Port 1433
```

- **Учётную запись службы** менять только через SQL Server Configuration Manager, не через оснастку «Службы» — иначе ломаются права (например, задания SQL Agent) [MS Learn].
- **DAC** для удалённого аварийного входа — включить сразу (раздел 6.7).
- **Database Mail, операторы и оповещения** в планах обслуживания при ошибках — настроить [ИТС-мет 5904, 2019] (в Express нет [MS Learn]).
- После всех настроек — перезапуск служб SQL Server [ИТС-мет 5904, 2019].

### 3.5. Драйвер на рабочих серверах 1С: OLE DB Driver, Native Client, шифрование

- Нужен Microsoft OLE DB Driver for SQL Server актуальной версии или SQL Server Native Client; наличие проверяется при создании, загрузке ИБ и обновлении конфигурации БД [ИТС-КС разд. 1.5.4]. Native Client с SQL Server 2022 и новее не поставляется, последний — версия 11 (2012) [MS Learn].
- Провайдер выбирается при первом соединении — от самого нового к старому до первого успешного; событие техжурнала `DBMSSQLCONN`, свойства `hResultOLEDB`, `hResultNC2005`, `hResultNC2008`, `hResult2012` [ИТС-адм прил. 3, разд. 3.24.2.3, 3.24.2.4.2]; в 8.5.1 добавлены `hResultMSOLEDBSQL19`, `hResultMSOLEDBSQL` [`otlichiya-8.5.1`, п. 16].
- **OLE DB Driver 19 по умолчанию требует шифрования (`Encrypt=Mandatory`) и проверяет сертификат**; 18 и старше по умолчанию не шифровали. Клиент 19 с умолчаниями не подключится к серверу, который требует шифрования и использует недоверенный сертификат. Версии 18 и 19 ставятся рядом (`MSOLEDBSQL`, `MSOLEDBSQL19`); реестровая Force Protocol Encryption (`0` Optional, `1` Mandatory, `2` Strict) и строка подключения — берётся более строгое [MS Learn].

Как платформа задаёт `Encrypt`/`TrustServerCertificate` и поддерживает ли 8.3.27 драйвер 19, ИТС не пишет ⚠. Порядок [практика]: на 8.3.x — актуальный OLE DB Driver 18; для 8.5 — сверить с `1cv8upd`; при драйвере 19 — доверенный сертификат SQL Server (доменный УЦ); проверить выбранный провайдер (`DBMSSQLCONN`) и `encrypt_option`.

```powershell
# сервер 1С, PowerShell: установленные драйверы и зарегистрированные провайдеры OLE DB [практика]
Get-ItemProperty HKLM:\SOFTWARE\Microsoft\Windows\CurrentVersion\Uninstall\* |
  Where-Object DisplayName -like '*OLE DB Driver*' | Select-Object DisplayName, DisplayVersion
(New-Object System.Data.OleDb.OleDbEnumerator).GetElements() | Select-Object SOURCES_NAME, SOURCES_DESCRIPTION
```

```xml
<!-- logcfg.xml: какой провайдер выбрала платформа [ИТС-адм прил. 3, разд. 3.24.2.3] -->
<config xmlns="http://v8.1c.ru/v8/tech-log">
  <log location="D:\1c_logs\dbconn" history="24">
    <event><eq property="name" value="DBMSSQLCONN"/></event>
    <property name="all"/>
  </log>
</config>
```

```sql
-- протокол и шифрование соединений 1С со стороны SQL Server [практика]
SELECT c.session_id, c.net_transport, c.encrypt_option, c.client_net_address, s.program_name
FROM sys.dm_exec_connections AS c JOIN sys.dm_exec_sessions AS s ON s.session_id = c.session_id
WHERE s.login_name = N'buh_1c';
```

Устарело: проверка `sqloledb.dll`/`ntwdblib.dll`, `cliconfg.exe`/`svrnetcn.exe` [ИТС-мет 2926, 2008], «установить MDAC» [ИТС-мет 5908, 2022] — это эпоха Windows 2000/2003; на современной Windows ошибка «Компоненты OLE DB провайдера не найдены» лечится установкой OLE DB Driver [практика].

## 4. Учётные записи и права: кластер 1С ↔ SQL Server

### 4.1. Под кем кластер подключается к SQL Server

- В свойствах ИБ указываются «Пользователь базы данных» и пароль. **Если их не указать, кластер подключается с аутентификацией ОС** — от имени пользователя, под которым работает конкретный рабочий процесс `rphost` [ИТС-адм разд. 5.2.1.3.2]. Обычно это `USR1CV8` (см. `01-ustanovka-servera-i-sluzhba-windows.md`), а при `swpuser.ini` — отдельный пользователь рабочих процессов [ИТС-КС разд. 1.3.2].
- Минус аутентификации ОС: одинаковые права на все базы кластера; поэтому рекомендуется аутентификация SQL Server с отдельным логином [ИТС-мет 2926, 2008]. Документация безопасности: пользователь СУБД — только с нужными кластеру привилегиями, **для каждой ИБ — свой пользователь** [ИТС-КС прил. 3, разд. 3.7]; имя пользователя СУБД совпадает с именем ИБ — так быстрее расследовать проблемы на общем сервере СУБД [ИТС-мет 5899, 2016].

### 4.2. Какие права нужны — сводка по ИТС

| Требование | Где сказано |
|---|---|
| Пользователь, от имени которого сервер 1С обращается к SQL Server, — член фиксированной серверной роли `processadmin` или `sysadmin` | [ИТС-КС разд. 3.2.3]; [ИТС-адм разд. 5.2.1.3.2] |
| Пользователь базы — `sa` либо владелец базы (если она уже есть); во втором случае — чтение `master` и полный доступ к `tempdb` | [ИТС-адм разд. 5.2.1.3.2] |
| `processadmin` нужен, чтобы из консоли кластера разрывать соединение, выполняющее запрос на сервере СУБД | [ИТС-мет 1595, 2007]; [ИТС-КС разд. 5.2.12.3] |
| Пользовательские табличные пространства (КОРП) — право `ALTER` на базу | [ИТС-КС разд. 5.5.5.2.1] |
| SQL Server 2014: без флага 4199 платформа включает его на каждое соединение — без прав администратора СУБД ошибка | [ИТС-адм разд. 5.2.1.3.2] |
| Чек-лист 2019: логин на каждую базу, роли `public`, `dbcreator` (`processadmin` не упомянут, но нужен) | [ИТС-мет 5904, 2019] |

На уровне SQL Server [MS Learn]: `processadmin` завершает сеансы **во всём экземпляре**, `dbcreator` создаёт, изменяет, удаляет и восстанавливает **любую** базу. Поэтому на общем экземпляре `dbcreator` после создания базы снимать [ИТС-мет 2926, 2008], `sysadmin` не давать [практика].

### 4.3. Сценарий А: базу создаёт кластер 1С

Скрипт (SSMS, под администратором SQL; база `master`):

```sql
USE master;
CREATE LOGIN [buh_1c] WITH PASSWORD = N'<сложный пароль>',
     DEFAULT_DATABASE = master, CHECK_POLICY = ON, CHECK_EXPIRATION = OFF;
ALTER SERVER ROLE dbcreator    ADD MEMBER [buh_1c];
ALTER SERVER ROLE processadmin ADD MEMBER [buh_1c];
```

- `CHECK_EXPIRATION = OFF` [практика]: кластер хранит пароль у себя и после истечения срока перестанет подключаться (у Oracle ИТС описывает ровно эту проблему со сроком пароля [ИТС-адм разд. 5.2.1.3.5]).
- После создания ИБ логин становится владельцем базы; `dbcreator` можно снять, если этот логин не должен создавать другие базы [ИТС-мет 2926, 2008]: `ALTER SERVER ROLE dbcreator DROP MEMBER [buh_1c];`.

### 4.4. Сценарий Б: базу заранее создаёт администратор СУБД

Подходит, когда нужно сразу задать размещение файлов и размеры (рекомендации — раздел 6.4):

```sql
USE master;
CREATE DATABASE [buh] COLLATE Cyrillic_General_CI_AS
ON PRIMARY (NAME = N'buh',     FILENAME = N'D:\MSSQL\Data\buh.mdf',    SIZE = 10GB, FILEGROWTH = 512MB)
LOG ON     (NAME = N'buh_log', FILENAME = N'L:\MSSQL\Log\buh_log.ldf', SIZE = 2GB,  FILEGROWTH = 512MB);
ALTER AUTHORIZATION ON DATABASE::[buh] TO [buh_1c];       -- логин становится владельцем (dbo)
ALTER SERVER ROLE processadmin ADD MEMBER [buh_1c];
```

Затем в 1С при регистрации базы флажок «Создать базу данных в случае ее отсутствия» можно не ставить: найдя пустую базу, платформа инициализирует в ней новую ИБ, а найдя существующую ИБ — подключится к ней [ИТС-адм разд. 5.2.1.3.7]. ⚠ Совпадение сортировки заранее созданной базы с той, что выбрала бы платформа, ИТС не проверяет и не описывает — надёжнее дать базе создаться из 1С (сценарий А), а размеры и рост файлов поменять после.

### 4.5. Проверка прав

```sql
SELECT IS_SRVROLEMEMBER('processadmin', 'buh_1c') AS processadmin,
       IS_SRVROLEMEMBER('dbcreator',    'buh_1c') AS dbcreator,
       IS_SRVROLEMEMBER('sysadmin',     'buh_1c') AS sysadmin;
SELECT name, SUSER_SNAME(owner_sid) AS owner FROM sys.databases WHERE name = N'buh';
```

Со стороны 1С проверка — создание тестовой ИБ и пробное «Удалить» соединения в консоли кластера во время долгого запроса [практика].

### 4.6. Права пользователя ОС `USR1CV8` (кратко)

Для процессов кластера на Windows: полные права на каталог данных кластера; «Список содержимого папки» на каталог временных файлов; права «Вход в качестве службы» и «Вход в качестве пакетного задания»; членство в группе «Пользователи журналов производительности» [ИТС-КС разд. 1.3.2]. Подробно — `01-ustanovka-servera-i-sluzhba-windows.md`. Если выбрана аутентификация ОС к SQL Server, логин Windows для `USR1CV8` (или для пользователя из `swpuser.ini`) создаётся в SQL Server с теми же ролями, что в 4.2 [практика].

## 5. Создание информационной базы на MS SQL

### 5.1. Параметры базы

[ИТС-адм разд. 5.2.1.3.2, 5.2.1.3.6]:

| Поле | Значение для MS SQL |
|---|---|
| Тип СУБД | Microsoft SQL Server (`MSSQLServer` в строках соединения и утилитах [ИТС-адм прил. 7, разд. 7.7.4; прил. 4, разд. 4.10.2]) |
| Сервер баз данных | имя компьютера (один экземпляр) или имя экземпляра; в ИТС пример записан как `Server/instance` — в нотации Microsoft это `Server\instance` ⚠ (какой разделитель принимает платформа, текст не уточняет; обычно используют `\` [практика]) |
| Общая память (тот же компьютер) | префикс `lpc:` — `lpc:Server/instance`; в ИТС условие — установлен Native Client [ИТС-адм разд. 5.2.1.3.2] |
| Имя базы данных | первый символ — латинская буква или `_`, далее латиница, цифры, `_`, `$`; до 63 символов; без пробелов; не зарезервированное слово [ИТС-адм разд. 5.2.1.3.2]; плюс общий запрет символов «<», «>», «#», «%», «"», «{», «}», «[», «]», «\|», «\\», «^», обратного апострофа и кодов 0–31, 127 [ИТС-адм разд. 5.2.1.3.1] |
| Пользователь и пароль БД | см. раздел 4; пусто — аутентификация ОС от имени `rphost` |
| Смещение дат | `0` или `2000` — раздел 5.2 |
| Создать базу данных в случае ее отсутствия | создаёт базу, если её нет на сервере СУБД [ИТС-адм разд. 5.2.1.3.6] |
| Установить блокировку регламентных заданий | в новой ИБ регламентные задания запрещены — обязательно для копий рабочих баз [ИТС-адм разд. 5.2.1.3.6] |
| Язык (Страна) | национальные настройки; можно изменить позже в конфигураторе [ИТС-адм разд. 5.2.1.3.6] |

**`lpc:` и оптимизированная реструктуризация — конфликт.** Чек-лист 1С советует при совмещении сервера 1С и SQL Server включить протокол Shared Memory [ИТС-мет 5904, 2019], а документация говорит, что оптимизированная реструктуризация (`UpdateDBCfg=v2` в `conf.cfg`) на MS SQL работает **только по TCP/IP** и не поддерживается при подключении через «Разделяемую память» или «Именованные каналы» [ИТС-адм прил. 3, разд. 3.17.23]. Значение по умолчанию `UpdateDBCfg` — `v1` [там же]. Вывод: если пользуетесь v2 (а она заметно ускоряет обновление конфигурации), указывайте сервер без `lpc:`. Какой протокол драйвер выбирает для локального имени без префикса — не подтверждено ⚠: проверьте `net_transport` запросом из раздела 3.5 и при необходимости укажите `tcp:sql01` (префикс протокола в нотации Microsoft) ⚠.

**Одна база СУБД — одна ИБ.** Платформа не запрещает зарегистрировать две ИБ на одну базу данных, но тогда не работают блокировка ИБ, объектные и управляемые блокировки, отметка времени — возможно разрушение данных; допустимо только для отладки [ИТС-адм разд. 5.2.1.3.8].

### 5.2. Смещение дат: подробно

- Тип `DATETIME` SQL Server хранит даты с 1 января 1753 года; в 1С записываются даты с 0001 по 3999 год; нулевая дата 01.01.0001 — значение по умолчанию, даты 01.01.0001 00:00:00–23:59:59 — «время без даты» [ИТС-мет 4055, 2010].
- Смещение `0`: «время без даты» переводится в 01.01.1753, даты со 02.01.1753 пишутся как есть, а **запись дат от 02.01.0001 до 01.01.1753 даёт ошибку** [ИТС-мет 4055, 2010].
- Смещение `2000`: при записи прибавляется 2000 лет, при чтении вычитается — любые даты 1С записываются; цена — незначительное замедление и «странные» даты при просмотре базы сторонними средствами [ИТС-мет 4055, 2010; ИТС-адм разд. 5.2.1.3.2].
- **Если в конфигурации есть регистры накопления или бухгалтерии — только 2000.** Если база уже создана с `0` — выгрузить в `.dt`, создать новую базу со смещением 2000, загрузить [ИТС-адм разд. 5.2.1.3.2]. После создания параметр не меняется [ИТС-адм разд. 5.2.1.3.2; ИТС-мет 4055].
- Хранится в служебной таблице `_YearOffset`, поле `Offset`; таблица есть только на MS SQL [`../its-metod/razmeshchenie-dannyh-tablicy-i-polya.md`].
- На PostgreSQL параметр не используется (`../1c/10`, табл. раздела 7).

**Умолчания различаются — указывайте явно:**

| Инструмент | Параметр | Умолчание | Источник |
|---|---|---|---|
| Диалог добавления ИБ (8.2+) | «Смещение дат» | предлагается 2000 | [ИТС-мет 4055, 2010] (⚠ для 8.3 не перепроверено) |
| `1cv8 CREATEINFOBASE` / строка соединения | `SQLYOffs` | **0** | [ИТС-адм прил. 7, разд. 7.7.4] |
| `ibcmd infobase create` | `--date-offset` | **2000** | [ИТС-адм прил. 4, разд. 4.10.4.2] |
| `ibcmd infobase replicate` | `--target-date-offset` | 2000 | [ИТС-адм прил. 4, разд. 4.10.4.6] |
| `rac infobase create` | `--date-offset` | ⚠ (сверить с `rac help infobase`) | `../1c/03` |

Проверка в существующей базе: `SELECT Offset FROM [buh].dbo._YearOffset;`.

### 5.3. Способы создания

**Из клиента** — «Добавить» → «Создание новой информационной базы» → «На сервере 1С:Предприятия» и поля из 5.1 [ИТС-адм разд. 5.2.1.3].

**Пакетно, `1cv8 CREATEINFOBASE`** [ИТС-адм прил. 7, разд. 7.2.3, 7.7.4] — синтаксис: `1cv8 CREATEINFOBASE <строка соединения> [/AddToList [<имя ИБ>]] [/UseTemplate <файл .cf или .dt>] [/DumpResult <файл>]`; строка соединения — фрагменты `Имя=Значение` через `;`, значения с пробелами — в двойных кавычках. Пример (cmd; путь к платформе подставьте свой, кавычки внутри строки удвоены — [практика]):

```bat
"C:\Program Files\1cv8\8.3.27.1688\bin\1cv8.exe" CREATEINFOBASE ^
 "Srvr=""srv1c"";Ref=""buh"";DBMS=""MSSQLServer"";DBSrvr=""sql01"";DB=""buh"";DBUID=""buh_1c"";DBPwd=""<пароль>"";SQLYOffs=2000;CrSQLDB=Y;SchJobDn=Y;Locale=ru_RU" ^
 /DumpResult C:\Temp\create_buh.txt
type C:\Temp\create_buh.txt
```

Параметры: `Srvr` — кластер (по умолчанию порт 1541), `Ref` — имя ИБ в кластере, `DBMS`, `DBSrvr`, `DB`, `DBUID`, `DBPwd`, `SQLYOffs`, `CrSQLDB` (по умолчанию `N`), `SchJobDn` (по умолчанию `N`), `Locale`; если в кластере есть администраторы — `SUsr`, `SPwd` [ИТС-адм прил. 7, разд. 7.7.4]. Результат `0` в файле `/DumpResult` — успех [ИТС-адм прил. 7, разд. 7.2.3]. Значение `Locale=ru_RU` ⚠ — по документации допустимые значения «как у форматной строки `Формат()`».

**`rac infobase create`** (кластер на Windows; синтаксис сверить с `rac help infobase` своей версии) — `../1c/03`, раздел о `infobase create`:

```bat
rac.exe infobase create --cluster=<uuid> --create-database --name=buh --dbms=MSSQLServer ^
  --db-server=sql01 --db-name=buh --db-user=buh_1c --db-pwd=<пароль> --date-offset=2000 ^
  --locale=ru --scheduled-jobs-deny=on
```

⚠ имена `--locale`, `--scheduled-jobs-deny` и умолчания — по `../1c/03` и `rac help`, в документации ИТС параметры `rac` не перечислены.

**`ibcmd infobase create`** (автономный режим, без кластера) [ИТС-адм разд. 7.4.4, 7.4.6; прил. 4, разд. 4.10.2, 4.10.4.2]:

```bat
ibcmd infobase create --dbms=MSSQLServer --database-server=sql01 --database-name=buh ^
  --database-user=buh_1c --request-database-password --date-offset=2000 ^
  --create-database --data="D:\ss-data\buh" --load="D:\cf\1Cv8.cf" --apply --force
```

`--db-user` и `--database-user` — синонимы (в примерах ИТС встречаются оба написания) [ИТС-адм прил. 4, разд. 4.10.2]; `--request-database-password` (`-W`) спрашивает пароль СУБД из стандартного ввода — пароль не остаётся в истории команд [там же]; `--restore=<файл.dt>` вместо `--load` создаёт базу и загружает выгрузку [ИТС-адм прил. 4, разд. 4.10.4.2]. Без `--apply` конфигурация загружается, но конфигурация базы данных не обновляется [ИТС-адм разд. 7.4.4]. Автономный сервер нельзя направлять на базу, которая сейчас работает под кластером, — возможна порча [ИТС-адм разд. 7.2].

### 5.4. Что проверить после создания

```sql
SELECT name, collation_name, recovery_model_desc, compatibility_level,
       is_read_committed_snapshot_on, snapshot_isolation_state_desc,
       page_verify_option_desc, is_auto_update_stats_async_on, is_query_store_on,
       log_reuse_wait_desc, SUSER_SNAME(owner_sid) AS owner
FROM sys.databases WHERE name = N'buh';
SELECT name, physical_name, size / 128 AS size_mb, growth, is_percent_growth
FROM [buh].sys.database_files;
```

- Модель восстановления — по политике копий (раздел 8); новая база наследует её от `model` [ИТС-мет 5904, 2019].
- Размеры и рост файлов — по 6.4; рост в процентах заменить на фиксированный в МБ [MS Learn].
- `compatibility_level` — у новой базы — уровень `model` (по умолчанию — уровень текущей версии); после обновления SQL Server существующие базы сохраняют прежний уровень, повышать — осознанно, с тестом (Query Store помогает сравнить «до» и «после») [MS Learn].
- `is_read_committed_snapshot_on` — раздел 7.1.

### 5.5. Копия рабочей базы для тестов

1. Восстановить копию под новым именем (`RESTORE … WITH MOVE`, раздел 9.4).
2. Зарегистрировать в кластере новую ИБ на эту базу **с «Установить блокировку регламентных заданий»** (`SchJobDn=Y`), иначе на тестовой копии сразу запустятся обмены, рассылки, загрузки банка [ИТС-адм разд. 5.2.1.3.6]. Смещение дат — то же, что у оригинала (⚠ поведение при несовпадении не описано).
3. Если копия на другом экземпляре — сопоставить пользователя базы с логином: `USE [buh_test]; ALTER USER [buh_1c] WITH LOGIN = [buh_1c];` («осиротевший» пользователь после переноса) [практика].

### 6.2. Память

- `max server memory` ограничивает только буферный пул; часть памяти SQL Server расходует вне него (стеки потоков, другие компоненты) [MS Learn]. Расчёт Microsoft для одного экземпляра: из памяти ОС вычесть размер стека × расчётное число рабочих потоков, затем ещё 25 % на прочие выделения — остаток и есть `max server memory` [MS Learn].
- Ставить `max` и `min` равными или почти равными не рекомендуется; слишком малое значение может не дать SQL Server стартовать — тогда запуск с параметром `-f` и исправление [MS Learn].
- Lock Pages in Memory — право «Блокировка страниц в памяти» (gpedit/secpol → Локальные политики → Назначение прав пользователя) учётной записи службы или её SID `NT SERVICE\MSSQLSERVER`, затем перезапуск; состояние — `sys.dm_os_sys_info.sql_memory_model_desc` (`CONVENTIONAL` — нет, `LOCK_PAGES` — есть) [MS Learn]. 1С: при сервере 1С на той же машине не включать [ИТС-мет 5904, 2019].
- В ВМ задать `min server memory`, чтобы гипервизор не отбирал буферный пул [MS Learn].
- Устарело: `awe enabled`, ключи `/3GB` и `/PAE` в `boot.ini` [ИТС-мет 2371, 2008] — для 32-разрядных SQL Server 2000/2005 на Windows 2000/2003.

Пример для выделенного сервера SQL с 64 ГБ (оставить ОС ~8 ГБ) и для совмещённого с 1С (сервер 64 ГБ, 1С нужно ~20 ГБ) [практика]:

```sql
EXEC sp_configure N'show advanced options', 1; RECONFIGURE;
EXEC sp_configure N'max server memory (MB)', 57344; RECONFIGURE;   -- выделенный: 56 ГБ
-- EXEC sp_configure N'max server memory (MB)', 36864; RECONFIGURE; -- совмещённый с 1С: 36 ГБ
SELECT name, value, value_in_use FROM sys.configurations
WHERE name IN (N'max server memory (MB)', N'min server memory (MB)');
```

Значения применяются сразу, без перезапуска [MS Learn].

### 6.3. Параллелизм

Почему 1С держит `MAXDOP = 1` [ИТС-мет 5945, 2018; 6008, 2023]: один тяжёлый запрос с неудачным планом (например, отчёт с полем составного типа «через точку» и RLS) распараллеливается и съедает процессоры у всех; время выполнения одного и того же запроса «скачет»; появляются ожидания `CXPACKET` и изредка внутризапросные взаимоблокировки — ошибки `Intra-query parallelism caused your server command … to deadlock` и `… deadlocked on thread communication buffer resources …` [ИТС-мет 5834, 2015; 2379, 2008]. `MAXDOP = 1` ограничивает только параллелизм внутри одного запроса — разные запросы по-прежнему выполняются параллельно [ИТС-мет 5834, 2015].

Microsoft советует иное (для сервера с одним узлом NUMA и более чем 8 логическими процессорами — 8 и т. п.) [MS Learn] — это общая рекомендация для смешанной нагрузки; для OLTP-нагрузки 1С с тысячами мелких запросов рекомендация 1С сохраняет силу [практика]. Если экземпляр общий с другими приложениями, параллелизм можно ограничить только для базы 1С (SQL Server 2016+) [MS Learn]:

```sql
USE [buh];
ALTER DATABASE SCOPED CONFIGURATION SET MAXDOP = 1;
```

Реструктуризация (особенно новым механизмом 8.3.11+) хорошо параллелится: на время обновления конфигурации ставят `max degree of parallelism = 0` (СУБД сама выбирает число потоков), следят за ожиданиями и дисками, затем возвращают 1 [ИТС-мет 5945, 2018]. В замерах 1С ускорение этапов реструктуризации составило 18–65 % [там же]. Изменение `sp_configure` действует без перезапуска [ИТС-мет 5945, 2018; MS Learn]:

```sql
EXEC sp_configure N'show advanced options', 1; RECONFIGURE;
EXEC sp_configure N'max degree of parallelism', 0; RECONFIGURE;   -- перед обновлением конфигурации
-- … обновление конфигурации БД …
EXEC sp_configure N'max degree of parallelism', 1; RECONFIGURE;   -- сразу после
```

Внимание: параметр общий для экземпляра — на время реструктуризации пользователи других баз получают параллельные планы [практика].

### 6.4. tempdb, `model`, рост файлов

**tempdb в 1С нагружена сильно**: временные таблицы платформы, сортировки и группировки (`GROUP BY`, `UNION`, `DISTINCT`) [ИТС-мет 2374, 2008], а при управляемых блокировках — ещё и хранилище версий строк (раздел 7.1).

- Число файлов: 1С — 4 [ИТС-мет 5904, 2019]; Microsoft — по числу логических процессоров, не больше 8, при конкуренции добавлять кратно 4, размеры одинаковые; с 2016 установщик создаёт их сам, файлы растут вместе, выделение однородными экстентами — флаги 1117/1118 не нужны [MS Learn].
- Размер: tempdb на отдельном диске — 50 % диска / число файлов; вместе с базами — 1–10 ГБ; прирост 512 МБ [ИТС-мет 5904, 2019].
- Рост tempdb — обычно длинные транзакции и «зависшие» соединения; уменьшить — перезапуском службы или `DBCC SHRINKFILE` в тихое время [ИТС-мет 2374, 2008] (умолчание прироста «10 %» оттуда устарело — с 2016 64 МБ [MS Learn]).

```sql
USE tempdb;
SELECT name, physical_name, size / 128 AS size_mb, growth / 128 AS growth_mb
FROM sys.database_files;                                  -- логические имена файлов
ALTER DATABASE tempdb MODIFY FILE (NAME = tempdev, SIZE = 8GB, FILEGROWTH = 512MB);
ALTER DATABASE tempdb ADD FILE (NAME = tempdev5, FILENAME = N'T:\TempDB\tempdev5.ndf',
                                SIZE = 8GB, FILEGROWTH = 512MB);
-- свободное место и хранилище версий
SELECT SUM(unallocated_extent_page_count) / 128 AS free_mb FROM tempdb.sys.dm_db_file_space_usage;
SELECT DB_NAME(database_id) AS db, reserved_space_kb / 1024 AS version_store_mb
FROM sys.dm_tran_version_store_space_usage;               -- SQL Server 2017+ [MS Learn]
```

Перенос tempdb на другой диск — `ALTER DATABASE tempdb MODIFY FILE (NAME = …, FILENAME = '…')` для каждого файла и перезапуск службы [ИТС-мет 2377, 2008] — способ актуален и сейчас [практика]; логические имена посмотреть запросом выше.

**`model`** — новая база копирует её настройки [ИТС-мет 5904, 2019]: начальный размер данных 1–10 ГБ, журнала 1–2 ГБ, прирост 512 МБ, модель восстановления — по политике копий, «Auto update statistics asynchronously» = True [там же]. Для рабочей базы: начальный размер данных — ожидаемый размер за длительный срок; журнал — такого размера, чтобы не расти между `BACKUP LOG` [там же]. Microsoft: рост журнала задавать в МБ, а не в процентах, и не больше 1024 МБ; умолчания с SQL Server 2016 — 64 МБ для данных и журнала [MS Learn].

```sql
ALTER DATABASE [model] SET AUTO_UPDATE_STATISTICS_ASYNC ON;
ALTER DATABASE [model] MODIFY FILE (NAME = modeldev, FILEGROWTH = 512MB);
ALTER DATABASE [model] MODIFY FILE (NAME = modellog, FILEGROWTH = 512MB);
```

Логические имена `modeldev`/`modellog` ⚠ — стандартные, но проверьте `SELECT name FROM model.sys.database_files;`.

### 6.5. Флаги трассировки

| Флаг | Что делает | 1С [ИТС-мет 5946, 2019] | Microsoft Learn | Вывод на 2019/2022 |
|---|---|---|---|---|
| 610 | минимальное протоколирование массовых вставок в индексированные таблицы | включать | с SQL Server 2016 не нужен — поведение по умолчанию | не нужен |
| 1117 | все файлы файловой группы растут вместе (для 1С — tempdb) | включать | с 2016 управляется `AUTOGROW_ALL_FILES`, флаг без действия | не нужен |
| 1118 | только однородные экстенты (меньше конкуренции за SGAM в tempdb) | включать | с 2016 управляется `MIXED_PAGE_ALLOCATION`, флаг без действия | не нужен |
| 1211 | запрет эскалации блокировок всегда, даже при нехватке памяти | включать (в списке вместе с 1224) | может вызвать ошибку 1204 «нет ресурса блокировки»; при обоих флагах 1211 главнее; лучше 1224 | **1224** |
| 1224 | запрет эскалации по числу блокировок; по памяти (40 %) эскалация остаётся | включать; при обоих действует 1211 | рекомендуется вместо 1211 | **включить** |
| 2330 | отключает сбор статистики использования индексов (`sys.dm_db_index_usage_stats`) | включать в продуктиве | в справочнике флагов нет (недокументированный) | ⚠ по ситуации |
| 2371 | линейный порог автообновления статистики | включать (2008 R2 SP1+) | с 2016 при уровне совместимости 130+ без действия | не нужен |
| 4199 | исправления оптимизатора из CU/SP | включать; для 2014 обязателен [ИТС-адм разд. 5.2.1.3.2] | без флага исправления прошлых версий включены на последнем уровне совместимости, а исправления после выпуска (post-RTM) — только с флагом | включить после теста |
| 8048 | секционирование объектов памяти (ожидания `CMEMTHREAD`) | включать (2008+) | с 2014 SP2 и 2016 поведение динамическое | не нужен |

Как включить [ИТС-мет 5946, 2019; MS Learn]:

- **Постоянно** (рекомендуемый способ): SQL Server Configuration Manager → свойства службы SQL Server → «Параметры запуска» → добавить `-T1224` (каждый флаг — отдельным параметром `-T4199`), перезапуск службы.
- **Сразу до перезапуска**: `DBCC TRACEON (1224, -1);` (`-1` — глобально).
- **Проверка**: `DBCC TRACESTATUS (-1);`.

Альтернатива флагам для одной таблицы — `ALTER TABLE … SET (LOCK_ESCALATION = DISABLE)` [MS Learn]; для таблиц 1С не применять — схемой управляет платформа, при реструктуризации настройка пропадёт ⚠.

### 6.6. Сеть

- TCP/IP включён, Named Pipes выключен [ИТС-мет 5904, 2019]. Старый совет «TCP/IP первой строкой, Named Pipes второй» [ИТС-мет 2926, 2008] устарел.
- Протокол реальных соединений 1С — запрос `net_transport` из раздела 3.5.
- Проблемы с большим числом соединений на Windows Server 2003 SP1 (`SynAttackProtect`) [ИТС-мет 1986, 2008] к современным ОС неприменимы. Сетевой стек рабочих серверов 1С (`MaxFreeTcbs`, `TcpTimedWaitDelay` [ИТС-мет 5908, 2022]) — в `01-ustanovka-servera-i-sluzhba-windows.md`.

### 6.7. Выделенное административное подключение (DAC)

Когда SQL Server перегружен и обычные подключения не проходят, DAC даёт отдельные зарезервированные ресурсы [ИТС-мет 6008, 2023; MS Learn]:

```sql
EXEC sp_configure N'remote admin connections', 1; RECONFIGURE;    -- разрешить DAC по сети
```

Подключение: в SSMS «Имя сервера» — `admin:sql01` (или `admin:sql01\ЭКЗЕМПЛЯР`); из командной строки — `sqlcmd -S sql01 -E -A`. Одновременно возможно только одно DAC-подключение (иначе ошибка 17810); в SSMS открывайте DAC через «Новый запрос», а не через Обозреватель объектов, и отключите IntelliSense — он пытается открыть второе соединение; порт DAC — 1434, если свободен, иначе динамический (виден в журнале ошибок SQL Server) [MS Learn].

### 6.8. Скрипт настройки экземпляра целиком

```sql
-- выполнять под sysadmin; значения памяти подставить свои
EXEC sp_configure N'show advanced options', 1;               RECONFIGURE;
EXEC sp_configure N'max server memory (MB)', 57344;           RECONFIGURE;
EXEC sp_configure N'max degree of parallelism', 1;            RECONFIGURE;

-- проверка

WHERE name IN (N'max server memory (MB)', N'max degree of parallelism',

```

## 7. Блокировки, версионность и уровни изоляции

### 7.1. Как 1С использует уровни изоляции на MS SQL

[ИТС-разр гл. 9, разд. 9.2.3.2]:

| Режим блокировок | MS SQL Server | Уровень изоляции | Чтение вне транзакции |
|---|---|---|---|
| Автоматический | блокировки записей | Repeatable Read или Serializable | «грязное» |
| Управляемый, SQL Server 2000 | записей | Read Committed | «грязное» |
| **Управляемый, SQL Server 2005 и новее** | записей | **Read Committed Snapshot** | **согласованное** |

Неявная транзакция при чтении объектов с табличными частями на MS SQL 2005+ в управляемом режиме: при режиме совместимости 8.2.16 и ниже — да, с 8.2.17 — нет (вместо неё двойное чтение `ВерсияДанных`) [ИТС-разр гл. 9, разд. 9.2.3.2]. Управляемый режим рекомендуется для новых решений; автоматический — только для совместимости [там же].

Что это значит на стороне SQL Server:

- Read Committed Snapshot — это `READ COMMITTED` при включённом параметре базы `READ_COMMITTED_SNAPSHOT`: чтения не ставят разделяемых блокировок и видят снимок данных на начало оператора за счёт версий строк [MS Learn]. В SQL Server параметр по умолчанию выключен [MS Learn]. ⚠ Что платформа включает `READ_COMMITTED_SNAPSHOT` для своей базы сама (при создании или подключении), в прочитанных текстах ИТС прямо не сказано — проверяйте: `SELECT is_read_committed_snapshot_on FROM sys.databases WHERE name = N'buh';` и **не меняйте вручную**.
- Версии строк хранятся в `tempdb`: длинная транзакция не даёт их чистить, tempdb растёт; контроль — `sys.dm_tran_version_store_space_usage` (2017+) и 11.6 [MS Learn; ИТС-мет 2374].
- В автоматическом режиме (`SERIALIZABLE`) при пустой таблице блокируется вся таблица до конца транзакции — деградация при параллельном вводе [`../its-metod/ekspluataciya-krupnoj-sistemy-blokirovki-tranzakcii.md`, п. 19].

### 7.2. Эскалация

- В SQL Server эскалация укрупняет блокировки строк/страниц до таблицы, что резко снижает параллельность; 1С рекомендует её запрещать (флаги 1211 и 1224) [ИТС-мет 5946, 2019]; Microsoft предпочитает 1224 (6.5) [MS Learn].
- У самой платформы своя эскалация управляемых блокировок: более 100 000 блокировок на одно пространство может приводить к блокировке всего пространства (при независимых разделителях — в пределах набора значений разделителей) [ИТС-разр гл. 9, разд. 9.2.3.6]. Это уровень менеджера блокировок 1С, а не SQL Server.

### 7.3. Особенности, о которых часто спрашивают

- **Монопольный режим ИБ не переводит базу MS SQL в `SINGLE_USER`** [ИТС-адм разд. 6.7, 6.10.2]. Для восстановления поверх базы переводите её сами (раздел 9.5).
- **Страничные блокировки индексов отключены начиная с 8.3.22** — следствие для регламента в разделе 10.1 [ИТС-мет 5837, 2022].
- Ограничения MS SQL для запросов 1С [ИТС-разр прил. 8, разд. 8.4]: запись таблицы — не больше 8060 байт; запись индекса — не больше 900 байт (ошибка возникает не при обновлении конфигурации, а при вставке слишком длинного ключа); до 256 таблиц в запросе — ограничение только SQL Server 2000/2005; особенности `ИМЕЮЩИЕ` и группировок по датам — только SQL Server 2000.
- Общие для всех СУБД: в индексе не больше 16 полей; сравнение строк в языке запросов игнорирует концевые пробелы [ИТС-разр прил. 8, разд. 8.1].

### 7.4. Диагностика блокировок на SQL Server

Кто кого блокирует сейчас (запрос — [практика]; `blocking_session_id` — `session_id` блокирующего; в консоли кластера это «Заблокировано СУБД» и «Соединение с СУБД» [ИТС-КС разд. 5.2.12.2]):

```sql
SELECT r.session_id, r.blocking_session_id, r.wait_type, r.wait_time, r.wait_resource,
       DB_NAME(r.database_id) AS db, s.host_name, s.program_name, s.login_name,
       SUBSTRING(t.text, 1, 400) AS sql_text
FROM sys.dm_exec_requests AS r
JOIN sys.dm_exec_sessions AS s ON s.session_id = r.session_id
CROSS APPLY sys.dm_exec_sql_text(r.sql_handle) AS t
WHERE r.blocking_session_id <> 0 OR r.session_id IN (SELECT blocking_session_id FROM sys.dm_exec_requests)
ORDER BY r.wait_time DESC;
```

Последние взаимоблокировки из системного сеанса расширенных событий `system_health` [практика] ⚠ (имена целевых объектов — по практике, в этой сессии не сверялись):

```sql
SELECT x.ev.value('@timestamp', 'datetime2') AS ts, x.ev.query('.') AS deadlock_report
FROM (SELECT CAST(t.target_data AS xml) AS data
      FROM sys.dm_xe_session_targets AS t
      JOIN sys.dm_xe_sessions AS s ON s.address = t.event_session_address
      WHERE s.name = N'system_health' AND t.target_name = N'ring_buffer') AS d
CROSS APPLY d.data.nodes('RingBufferTarget/event[@name="xml_deadlock_report"]') AS x(ev);
```

Счётчики производительности для блокировок [ИТС-мет 2923, 2008]: `SQL Server: Locks \ Lock Wait Time (ms)` — суммарное ожидание за секунду (не должно превышать «время отклика × число активных пользователей»), `SQL Server: Locks \ Average Wait Time (ms)` — не больше заданного времени отклика, `SQL Server: Locks \ Number of Deadlocks/sec` — должен быть 0.

Полная методика расследования блокировок и взаимоблокировок (ЦУП, техжурнал `TLOCK`/`TDEADLOCK`, `<dbmslocks/>`, Profiler, расширенные события, `DBCC PAGE`) уже законспектирована: `../its-metod/vzaimoblokirovki-i-oshibki-blokirovok.md` (разделы 1.6, 2.4.3–2.4.7) и `../its-metod/sbor-dannyh-dlya-rassledovaniya-problem.md`. Старая методика «SQL Trace, событие `Lock:Acquired` с Duration ≥ 1» [ИТС-мет 1738, 2007] устарела: SQL Trace и SQL Server Profiler объявлены устаревшими, Microsoft советует расширенные события [MS Learn].

Разрыв соединения из консоли кластера при длительном запросе к MS SQL сработает только при правах логина (`processadmin`); при успехе пользователь увидит «Сеанс работы завершен администратором» [ИТС-КС разд. 5.2.12.3]. Нельзя разорвать соединение, пока вызов «стоит» на одной строке кода вне СУБД (долгий COM или HTTP-вызов) [там же].

## 8. Модель восстановления и журнал транзакций

### 8.1. Модели

| Модель | Резервные копии журнала | Восстановление на момент времени | Журнал | Источник |
|---|---|---|---|---|
| Простая (SIMPLE) | нет | нет, только на момент полной/разностной копии | очищается автоматически | [MS Learn] |
| Полная (FULL) | обязательны | да | растёт до `BACKUP LOG` | [MS Learn] |
| С неполным протоколированием (BULK_LOGGED) | обязательны | ограниченно | массовые операции протоколируются минимально | [MS Learn] |

Умолчание — у Express «Простая», у Standard и Enterprise «Полная» (наследуется из `model`) [MS Learn]. В простой модели нельзя: доставку журналов, группы доступности, восстановление на момент времени [MS Learn].

Позиция 1С: для ускорения **загрузки `.dt`** (и реструктуризации [`../its-docs/dev-gl02-rabota-s-konfiguraciej.md`]) — «Простая» или «С неполным протоколированием», на время операции или постоянно, если восстановление на момент не нужно; **перед сменой модели — резервная копия** [ИТС-адм разд. 6.8]; в целом модель — по политике копий [ИТС-мет 5904, 2019]. Схема [практика]: «Полная» + копии журнала каждые 15–60 минут; на загрузку `.dt` или большую реструктуризацию — BULK_LOGGED (цепочка не рвётся), затем FULL и копия журнала.

```sql
ALTER DATABASE [buh] SET RECOVERY BULK_LOGGED;   -- перед загрузкой .dt / реструктуризацией
-- … операция …
ALTER DATABASE [buh] SET RECOVERY FULL;
BACKUP LOG [buh] TO DISK = N'E:\Backup\buh_log_after_bulk.trn' WITH CHECKSUM;
```

### 8.2. Почему растёт журнал и что делать

Причину показывает `log_reuse_wait_desc` [MS Learn]: `LOG_BACKUP` — в полной модели не делаются копии журнала; `ACTIVE_TRANSACTION` — длинная транзакция (часто — «забытый» сеанс 1С или зависший обмен).

```sql
SELECT name, recovery_model_desc, log_reuse_wait_desc FROM sys.databases;
DBCC SQLPERF (LOGSPACE);                                       -- заполненность журналов всех баз
SELECT COUNT(*) AS vlf_count FROM sys.dm_db_log_info(DB_ID(N'buh'));   -- число VLF (2016 SP2+) [MS Learn]
```

**Устаревший рецепт** `BACKUP LOG … WITH TRUNCATE_ONLY` + `DBCC SHRINKFILE` [ИТС-мет 2373, 2008] не работает: параметры `WITH NO_LOG` и `WITH TRUNCATE_ONLY` удалены; чтобы разорвать цепочку журналов, переключают базу в простую модель [MS Learn]. Современные варианты:

```sql
-- Вариант 1: цепочку сохраняем (FULL)
BACKUP LOG [buh] TO DISK = N'E:\Backup\buh_log_now.trn' WITH CHECKSUM, COMPRESSION;
USE [buh];
DBCC SHRINKFILE (N'buh_log', 4096);          -- целевой размер в МБ; логическое имя — из sys.database_files

-- Вариант 2: восстановление на момент времени не нужно (цепочка рвётся!)
ALTER DATABASE [buh] SET RECOVERY SIMPLE;
USE [buh]; CHECKPOINT;
DBCC SHRINKFILE (N'buh_log', 4096);
ALTER DATABASE [buh] SET RECOVERY FULL;
BACKUP DATABASE [buh] TO DISK = N'E:\Backup\buh_full_restart.bak' WITH CHECKSUM, COMPRESSION;  -- новая цепочка
```

Внимание: сжатие файлов — не регулярная операция; файлы, выросшие от обычной работы, сжимать не нужно; сжатие файлов данных фрагментирует индексы; `AUTO_SHRINK` по умолчанию выключен и включать его не рекомендуется [MS Learn]. Мелкий шаг роста журнала порождает слишком много VLF и замедляет работу, слишком крупный — слишком мало крупных VLF [MS Learn].

**IFI и журнал.** 1С пишет, что мгновенная инициализация не работает для журнала, поэтому размер журнала нужно задавать заранее [ИТС-мет 6008, 2023]. Уточнение Microsoft: начиная с SQL Server 2022 рост журнала до 64 МБ тоже использует мгновенную инициализацию (и не требует права `SE_MANAGE_VOLUME_NAME`), рост крупнее — по-прежнему с обнулением [MS Learn]. Вывод тот же: журнал с запасом, рост фиксированный.

## 9. Резервное копирование и восстановление

### 9.1. Что говорит 1С

- Резервную копию делают **перед любой операцией, которая может повредить данные** [ИТС-КС разд. 5.1.1].
- Клиент-серверную ИБ копируют **средствами СУБД** — это точная копия с возвратом в то же состояние; выгрузка `.dt` предполагает корректные данные и может не загрузиться [ИТС-КС разд. 5.1.1]. `.dt` как резервную копию не рекомендуется использовать: может не загрузиться при ошибках в базе, долго, нужен монопольный доступ, много памяти [ИТС-адм разд. 6.7]. SQL Server копирует базу без остановки работы пользователей [ИТС-мет 2922, 2008].
- Состав копии ИБ [ИТС-адм разд. 6.9.2]: (1) база данных; (2) журнал регистрации — если нужен после восстановления; (3) хранилище двоичных данных — встроенным языком или стандартной функцией «Управление хранилищем двоичных данных». Средствами СУБД журнал регистрации и хранилище двоичных данных не копируются [ИТС-КС разд. 5.1.1]. Восстановление — в том же порядке; **журнал регистрации восстанавливать при остановленном кластере** [ИТС-адм разд. 6.9.2].
- Во время восстановления средствами СУБД к ИБ не должно быть подключений — конфигуратора, клиентов, фоновых и регламентных заданий, средств администрирования [ИТС-КС разд. 5.1.1].
- Проверить восстановление: после первого автоматического бэкапа восстановить базу на резервном сервере и проверить работу [ИТС-мет 5904, 2019]; хотя бы раз провести тестовое восстановление с замером времени [ИТС-мет 5899, 2016].

### 9.2. Схема и параметры

| Что | Как | Источник |
|---|---|---|
| Полная копия | ежедневно ночью | [практика] |
| Разностная | при больших базах — днём или между полными | [практика] |
| Журнал | каждые 15–60 мин (только FULL/BULK_LOGGED) | [практика] |
| Внеплановая копия перед обновлением | `WITH COPY_ONLY` — не ломает базу разностных копий и цепочку | [MS Learn] |
| Контрольные суммы | `WITH CHECKSUM` | [MS Learn] |
| Сжатие | `WITH COMPRESSION` или `backup compression default = 1` (не в Express) | [MS Learn] |
| Проверка файла | `RESTORE VERIFYONLY … WITH CHECKSUM` — читает весь набор, но структуру данных не проверяет | [MS Learn] |
| Проверка по-настоящему | регулярное восстановление на тестовый сервер + `DBCC CHECKDB` | [ИТС-мет 5904; MS Learn] |
| Где хранить | не только на диске самого SQL Server: при отказе машины теряются и база, и копия | [ИТС-мет 2378, 2008] |

### 9.3. Команды

```sql
-- полная копия с датой в имени файла
DECLARE @f nvarchar(400) = N'E:\Backup\buh_full_' + FORMAT(SYSDATETIME(), 'yyyyMMdd_HHmm') + N'.bak';
BACKUP DATABASE [buh] TO DISK = @f WITH CHECKSUM, COMPRESSION, STATS = 10;

-- разностная
DECLARE @d nvarchar(400) = N'E:\Backup\buh_diff_' + FORMAT(SYSDATETIME(), 'yyyyMMdd_HHmm') + N'.bak';
BACKUP DATABASE [buh] TO DISK = @d WITH DIFFERENTIAL, CHECKSUM, COMPRESSION;

-- журнал
DECLARE @l nvarchar(400) = N'E:\Backup\buh_log_' + FORMAT(SYSDATETIME(), 'yyyyMMdd_HHmm') + N'.trn';
BACKUP LOG [buh] TO DISK = @l WITH CHECKSUM, COMPRESSION;

-- внеплановая копия перед обновлением конфигурации — на сетевую папку
BACKUP DATABASE [buh] TO DISK = N'\\backup01\sql$\buh_before_update.bak'
WITH COPY_ONLY, CHECKSUM, COMPRESSION, STATS = 10;

-- проверка файла копии
RESTORE VERIFYONLY FROM DISK = N'\\backup01\sql$\buh_before_update.bak' WITH CHECKSUM;
RESTORE HEADERONLY   FROM DISK = N'\\backup01\sql$\buh_before_update.bak';
RESTORE FILELISTONLY FROM DISK = N'\\backup01\sql$\buh_before_update.bak';
```

**Сетевая папка.** В 2008 году приходилось создавать устройство через `sp_addumpdevice`, а SQL Server должен был работать под доменной учётной записью [ИТС-мет 2378, 2008]. Сейчас путь UNC указывают прямо в `TO DISK` [практика]; права на запись в папку нужны **учётной записи службы SQL Server**: если служба работает под виртуальной учётной записью `NT SERVICE\MSSQLSERVER`, в сеть она выходит как учётная запись компьютера `ДОМЕН\SQL01$` — ей и дают права на общую папку и NTFS [MS Learn]. Без домена (рабочая группа) — служба под локальной учётной записью с таким же именем и паролем на файловом сервере ⚠ [практика].

История копий [практика]:

```sql
SELECT TOP (30) bs.database_name, bs.type,              -- D = полная, I = разностная, L = журнал
       bs.backup_start_date, bs.backup_finish_date, bs.is_copy_only, bs.has_backup_checksums,
       CAST(bs.compressed_backup_size / 1048576.0 AS decimal(18,1)) AS size_mb,
       bmf.physical_device_name
FROM msdb.dbo.backupset AS bs
JOIN msdb.dbo.backupmediafamily AS bmf ON bmf.media_set_id = bs.media_set_id
WHERE bs.database_name = N'buh'
ORDER BY bs.backup_finish_date DESC;
```

При частых копиях журнала сообщения об успешных копиях засоряют журнал ошибок SQL Server — их подавляет флаг 3226 [MS Learn].

```sql
RESTORE DATABASE [buh_test] FROM DISK = N'E:\Backup\buh_full_20261019_0100.bak'
WITH MOVE N'buh'     TO N'D:\MSSQL\Data\buh_test.mdf',

```

На момент времени (полная + разностная + журналы) [практика]:

```sql
RESTORE DATABASE [buh_pit] FROM DISK = N'E:\Backup\buh_full_20261019_0100.bak'
  WITH MOVE N'buh' TO N'D:\MSSQL\Data\buh_pit.mdf', MOVE N'buh_log' TO N'L:\MSSQL\Log\buh_pit_log.ldf', NORECOVERY;
RESTORE DATABASE [buh_pit] FROM DISK = N'E:\Backup\buh_diff_20261019_0900.bak' WITH NORECOVERY;
```

### 9.5. Восстановление поверх рабочей базы

⚠ **Разрушающая операция: текущие данные базы будут полностью заменены.** Перед ней — `COPY_ONLY`-копия текущего состояния (или копия «хвоста» журнала `BACKUP LOG … WITH NORECOVERY` — после неё база уходит в состояние восстановления; но Microsoft предупреждает, что для монопольного доступа **перед** этой копией может понадобиться однопользовательский режим [MS Learn, tail-log-backups-sql-server]).

Если для базы включён `AUTO_UPDATE_STATISTICS_ASYNC` (так рекомендует ИТС-мет 5904), фоновый поток статистики может занять единственное подключение, и `SET SINGLE_USER` не сработает. Перед переводом выключить его: `ALTER DATABASE [buh] SET AUTO_UPDATE_STATISTICS_ASYNC OFF;` [MS Learn, ALTER DATABASE SET options; уточнено 20.10.2026, подробно — `../mssql/04-…`].

1. В 1С: установить блокировку начала сеансов и регламентных заданий, завершить сеансы — консоль кластера или `rac infobase update … --sessions-deny=on --scheduled-jobs-deny=on` (ключи сверить с `rac help`; `../1c/03`). Требование ИТС: никаких подключений к ИБ во время восстановления [ИТС-КС разд. 5.1.1].
2. В SQL Server (монопольный режим 1С не переводит базу в однопользовательский [ИТС-адм разд. 6.7]):

```sql
USE master;
ALTER DATABASE [buh] SET SINGLE_USER WITH ROLLBACK IMMEDIATE;    -- обрывает оставшиеся соединения
RESTORE DATABASE [buh] FROM DISK = N'E:\Backup\buh_full_20261019_0100.bak' WITH REPLACE, STATS = 10;
ALTER DATABASE [buh] SET MULTI_USER;
```

3. Если нужен журнал регистрации на момент копии — остановить кластер и вернуть каталог журнала регистрации ИБ; затем хранилище двоичных данных (если используется) [ИТС-адм разд. 6.9.2].
4. Снять блокировки в 1С, проверить вход и регламентные задания.

### 9.6. Express и копии по расписанию без SQL Server Agent

В Express нет SQL Server Agent [MS Learn] — планировщик Windows и `sqlcmd` [практика]; `C:\Scripts\backup_buh.sql` — команды из 9.3:

## 10. Регламентное обслуживание

### 10.1. Что рекомендует 1С (2022) и что из этого устарело

[ИТС-мет 5837, редакция 18.11.2022]: в крупных системах автоматики СУБД недостаточно — регламент автоматизировать планами обслуживания и контролировать по истории выполнения. Документация 1С допускает на уровне СУБД (без изменения структуры базы) проверку целостности, реиндексацию, дефрагментацию, реорганизацию, резервное копирование, очистку процедурного кеша, сбор статистики, а для MS SQL ещё шифрование (2008+), кластер СУБД, перенос файлов базы и журнала [ИТС-КС разд. 5.5.2–5.5.8].

| Операция по 5837 | Как и как часто по 1С | Оценка по Microsoft Learn |
|---|---|---|
| Статистика | `sp_msforeachtable N'UPDATE STATISTICS ? WITH FULLSCAN'`, не реже раза в день; «горячие» таблицы — чаще; не блокирует | `sp_msforeachtable` недокументирована [практика] — скрипт 10.2; реорганизация статистику не обновляет, перестроение — обновляет полным просмотром [MS Learn] |
| Очистка кеша планов | `DBCC FREEPROCCACHE` сразу после статистики | чистит **весь экземпляр**; с 2016 — `ALTER DATABASE SCOPED CONFIGURATION CLEAR PROCEDURE_CACHE` для одной базы [MS Learn] |
| Дефрагментация | `DBCC INDEXDEFRAG`, не реже раза в неделю; не блокирует | `DBCC INDEXDEFRAG` устарела → `ALTER INDEX … REORGANIZE` [MS Learn] |
| Реиндексация | `DBCC DBREINDEX`, раз в неделю в минимальную нагрузку; **блокирует таблицу** | `DBCC DBREINDEX` устарела → `ALTER INDEX … REBUILD`; `ONLINE = ON` держит блокировку только в конце [MS Learn] |
| **С 8.3.22** | перед дефрагментацией `ALTER INDEX … SET (ALLOW_PAGE_LOCKS = ON, ALLOW_ROW_LOCKS = ON)`, после — `ALLOW_PAGE_LOCKS = OFF` | `REORGANIZE` при `ALLOW_PAGE_LOCKS = OFF` невозможна — «Reorganize Index Task» плана обслуживания на базах 8.3.22+ не работает; `REBUILD` работает [MS Learn] |
| Пороги фрагментации (> 25 % [ИТС-мет 1794, 2007]) | — | универсальных порогов Microsoft больше не даёт: пользу определять опытом (Query Store «до/после»), плотность страниц часто важнее; перестроение нередко заменяется обновлением статистики; маленькие индексы перестраивать бесполезно [MS Learn] |

Вывод [практика]: ежедневно — статистика и очистка кеша планов **своей базы**; еженедельно — индексы по фактическим размерам, фрагментации и плотности с учётом 8.3.22+; регулярно — `DBCC CHECKDB`; после крупных операций (перепроведение, свёртка, загрузка `.dt`) — внеплановое обновление статистики.

### 10.2. Скрипты

**Статистика всех пользовательских таблиц с полным просмотром** (замена `sp_msforeachtable`; в контексте базы 1С) [практика]:

```sql
USE [buh];
DECLARE @s nvarchar(max) = N'';
SELECT @s += N'UPDATE STATISTICS ' + QUOTENAME(SCHEMA_NAME(schema_id)) + N'.' + QUOTENAME(name)
           + N' WITH FULLSCAN;' + NCHAR(10)
FROM sys.tables WHERE is_ms_shipped = 0;
EXEC sys.sp_executesql @s;
ALTER DATABASE SCOPED CONFIGURATION CLEAR PROCEDURE_CACHE;   -- кеш планов только этой базы (2016+)
```

Более лёгкий вариант — `EXEC sp_updatestats;` (обновляет только изменившуюся статистику, с выборкой по умолчанию) ⚠ — для 1С по ИТС нужен `FULLSCAN`.

**Обслуживание индексов с учётом 8.3.22+** — алгоритм 5837 в виде скрипта (пороги 10 %/30 % и 1000 страниц — стартовые значения, подбирать по опыту) [практика]:

```sql
USE [buh];
SET NOCOUNT ON;
DECLARE @schema sysname, @table sysname, @index sysname, @frag float, @pagelocks bit,
        @obj nvarchar(600), @sql nvarchar(max);
DECLARE c CURSOR LOCAL FAST_FORWARD FOR
  SELECT s.name, t.name, i.name, ips.avg_fragmentation_in_percent, i.allow_page_locks
  FROM sys.dm_db_index_physical_stats(DB_ID(), NULL, NULL, NULL, 'LIMITED') AS ips
  JOIN sys.indexes AS i ON i.object_id = ips.object_id AND i.index_id = ips.index_id
  JOIN sys.tables  AS t ON t.object_id = i.object_id
  JOIN sys.schemas AS s ON s.schema_id = t.schema_id
  WHERE ips.index_id > 0 AND ips.alloc_unit_type_desc = N'IN_ROW_DATA'
    AND ips.page_count >= 1000 AND ips.avg_fragmentation_in_percent >= 10;
OPEN c;
FETCH NEXT FROM c INTO @schema, @table, @index, @frag, @pagelocks;
WHILE @@FETCH_STATUS = 0
BEGIN
  SET @obj = QUOTENAME(@index) + N' ON ' + QUOTENAME(@schema) + N'.' + QUOTENAME(@table);
  BEGIN TRY
    IF @frag >= 30
      EXEC (N'ALTER INDEX ' + @obj + N' REBUILD;');          -- REBUILD работает и без страничных блокировок
    ELSE IF @pagelocks = 0
    BEGIN
      EXEC (N'ALTER INDEX ' + @obj + N' SET (ALLOW_PAGE_LOCKS = ON, ALLOW_ROW_LOCKS = ON);');
      EXEC (N'ALTER INDEX ' + @obj + N' REORGANIZE;');
      EXEC (N'ALTER INDEX ' + @obj + N' SET (ALLOW_PAGE_LOCKS = OFF, ALLOW_ROW_LOCKS = ON);');
    END
    ELSE
      EXEC (N'ALTER INDEX ' + @obj + N' REORGANIZE;');
  END TRY
  BEGIN CATCH
    PRINT N'Ошибка на ' + @obj + N': ' + ERROR_MESSAGE();
    IF @pagelocks = 0   -- вернуть исходное состояние, если REORGANIZE упал
      EXEC (N'ALTER INDEX ' + @obj + N' SET (ALLOW_PAGE_LOCKS = OFF, ALLOW_ROW_LOCKS = ON);');
  END CATCH;
  FETCH NEXT FROM c INTO @schema, @table, @index, @frag, @pagelocks;
END
CLOSE c; DEALLOCATE c;
```

- `REBUILD` без `ONLINE` блокирует таблицу на время работы [ИТС-мет 5837; MS Learn] — только в окно обслуживания; в Enterprise можно добавить `WITH (ONLINE = ON)`.
- Реорганизации нужно свободное место в том же файле данных, иначе ошибка 1105 [MS Learn].
- Индекс, перестроенный через `REBUILD`, сохраняет `ALLOW_PAGE_LOCKS = OFF` (параметры индекса не меняются) ⚠ [практика] — проверить выборкой `SELECT name, allow_page_locks FROM sys.indexes WHERE allow_page_locks = 1 AND object_id IN (SELECT object_id FROM sys.tables);` после регламента: у баз 8.3.22+ включённых страничных блокировок оставаться не должно ⚠.

Фрагментация и плотность страниц (образец Microsoft; режим `SAMPLED` быстрый, `DETAILED` точный и долгий) [MS Learn]:

```sql
SELECT OBJECT_NAME(ips.object_id) AS table_name, i.name AS index_name,
       ips.avg_fragmentation_in_percent, ips.avg_page_space_used_in_percent, ips.page_count
FROM sys.dm_db_index_physical_stats(DB_ID(), DEFAULT, DEFAULT, DEFAULT, 'SAMPLED') AS ips
JOIN sys.indexes AS i ON i.object_id = ips.object_id AND i.index_id = ips.index_id
ORDER BY ips.page_count DESC;
```

### 10.3. Проверка целостности: `DBCC CHECKDB`

- Проверяет физическую и логическую целостность базы SQL Server; работает по внутреннему снимку базы, не блокируя пользователей [MS Learn].
- `WITH PHYSICAL_ONLY` — значительно быстрее на больших базах, рекомендуется для частого запуска в продуктиве; полный `CHECKDB` — периодически [MS Learn].
- При найденных ошибках Microsoft рекомендует **восстановление из последней исправной копии**; `REPAIR_ALLOW_DATA_LOSS` — не замена восстановлению [MS Learn].
- «Тестирование и исправление ИБ» в конфигураторе — другой уровень (логическая и ссылочная целостность данных 1С, пересчёт итогов, реиндексация таблиц ИБ) и требует монопольного режима [ИТС-адм разд. 6.10.2]; одно другое не заменяет [практика].

```sql
DBCC CHECKDB (N'buh') WITH NO_INFOMSGS, ALL_ERRORMSGS;   -- полная проверка
DBCC CHECKDB (N'buh') WITH PHYSICAL_ONLY;                 -- быстрая, для частого запуска
```

Хороший приём [практика]: полную проверку запускать на тестовом сервере по восстановленной копии — так проверяются сразу и копия, и база.

## 11. Расследование медленной работы

### 11.1. Порядок

1. Убедиться, что тормозит именно SQL Server (Монитор ресурсов, счётчики) [ИТС-мет 5813, 2015; 5861, 2015]. Диспетчер задач может показать неверную картину: SQL Server сам управляет памятью и потоками через SQLOS [ИТС-мет 6008, 2023].

Накопленная статистика ожиданий (с момента старта или сброса; список «безопасных» — сокращённый из [ИТС-мет 6008]):

```sql
SELECT TOP (20) wait_type, waiting_tasks_count,
       wait_time_ms / 1000 AS wait_s, signal_wait_time_ms / 1000 AS signal_s,
       CAST(100.0 * wait_time_ms / SUM(wait_time_ms) OVER () AS decimal(5,2)) AS pct
FROM sys.dm_os_wait_stats
WHERE wait_time_ms > 0 AND wait_type NOT LIKE N'%SLEEP%'
  AND wait_type NOT IN (N'BROKER_TASK_STOP', N'BROKER_TO_FLUSH', N'CHECKPOINT_QUEUE',
      N'CLR_AUTO_EVENT', N'DIRTY_PAGE_POLL', N'DISPATCHER_QUEUE_SEMAPHORE', N'LOGMGR_QUEUE',
      N'ONDEMAND_TASK_QUEUE', N'REQUEST_FOR_DEADLOCK_SEARCH', N'SQLTRACE_INCREMENTAL_FLUSH_SLEEP',
      N'WAITFOR', N'XE_DISPATCHER_WAIT', N'XE_TIMER_EVENT', N'FT_IFTS_SCHEDULER_IDLE_WAIT',
      N'HADR_FILESTREAM_IOMGR_IOCOMPLETION', N'QDS_PERSIST_TASK_MAIN_LOOP_SLEEP')
ORDER BY wait_time_ms DESC;
-- сброс перед замером «с чистого листа» [ИТС-мет 6008]:
-- DBCC SQLPERF ('sys.dm_os_wait_stats', CLEAR);
```

### 11.3. Лидеры по процессору, чтениям, частоте (кеш планов)

Идея [ИТС-мет 5861, 2015; 5813, 2015]: `sys.dm_exec_query_stats` хранит статистику по планам в кеше — найти базу и запросы с наибольшим `total_worker_time` (CPU), `total_physical_reads`/`total_logical_reads` (диск), `execution_count` (частота); нагрузка не должна быть «размазана» по всем запросам — если размазана, переходить к трассировке (11.7). Компактные версии запросов из статей [практика]:

```sql
-- нагрузка на CPU по базам (атрибут dbid плана — у параметризованных запросов 1С dbid текста бывает NULL)
WITH db_cpu AS (
  SELECT CONVERT(int, pa.value) AS database_id, SUM(qs.total_worker_time) AS cpu_us
  FROM sys.dm_exec_query_stats AS qs
  CROSS APPLY sys.dm_exec_plan_attributes(qs.plan_handle) AS pa
  WHERE pa.attribute = N'dbid'
  GROUP BY CONVERT(int, pa.value))
SELECT DB_NAME(database_id) AS db, cpu_us / 1000 AS cpu_ms,
       CAST(100.0 * cpu_us / SUM(cpu_us) OVER () AS decimal(5,2)) AS pct
FROM db_cpu WHERE database_id > 4 AND database_id <> 32767
ORDER BY cpu_us DESC;

-- топ-20 запросов по суммарному CPU
SELECT TOP (20) qs.execution_count,
       qs.total_worker_time / 1000 AS total_cpu_ms,
       qs.total_worker_time / qs.execution_count / 1000 AS avg_cpu_ms,
       qs.total_logical_reads / qs.execution_count AS avg_reads,
       qs.total_elapsed_time / qs.execution_count / 1000 AS avg_ms,
       qs.last_execution_time,
       SUBSTRING(t.text, qs.statement_start_offset / 2 + 1,
         (CASE qs.statement_end_offset WHEN -1 THEN DATALENGTH(t.text)
               ELSE qs.statement_end_offset END - qs.statement_start_offset) / 2 + 1) AS stmt,
       qp.query_plan
FROM sys.dm_exec_query_stats AS qs
CROSS APPLY sys.dm_exec_sql_text(qs.sql_handle) AS t
CROSS APPLY sys.dm_exec_query_plan(qs.plan_handle) AS qp
ORDER BY qs.total_worker_time DESC;
-- для диска: ORDER BY qs.total_physical_reads DESC; для частоты: ORDER BY qs.execution_count DESC
```

Ограничение [практика]: статистика есть только для планов, которые сейчас в кеше; после `DBCC FREEPROCCACHE`, перезапуска или вытеснения она теряется — для истории нужен Query Store (11.4).

Задержки по файлам (какой файл какой базы «тормозит») [практика]:

```sql
SELECT DB_NAME(vfs.database_id) AS db, mf.physical_name,
       vfs.num_of_reads,  vfs.io_stall_read_ms  / NULLIF(vfs.num_of_reads, 0)  AS avg_read_ms,
       vfs.num_of_writes, vfs.io_stall_write_ms / NULLIF(vfs.num_of_writes, 0) AS avg_write_ms
FROM sys.dm_io_virtual_file_stats(NULL, NULL) AS vfs
JOIN sys.master_files AS mf ON mf.database_id = vfs.database_id AND mf.file_id = vfs.file_id
ORDER BY vfs.io_stall DESC;
```

Сравнивать с ориентиром 10–20 мс для данных и 1–5 мс для журналов [ИТС-мет 5904; 6008]. То же в Activity Monitor — группа Data File I/O [ИТС-мет 6008].

Память: какая база сколько занимает в буферном пуле — `sys.dm_os_buffer_descriptors`; клерки памяти — `sys.dm_os_memory_clerks` [ИТС-мет 5813, 2015]. **В запросе из 5813 колонка `single_pages_kb` есть только в SQL Server 2008–2008 R2; с 2012 — `pages_kb`** [MS Learn]:

```sql
SELECT DB_NAME(database_id) AS db, COUNT(*) * 8 / 1024 AS buffer_mb
FROM sys.dm_os_buffer_descriptors GROUP BY database_id ORDER BY buffer_mb DESC;
SELECT TOP (20) [type], SUM(pages_kb) / 1024 AS mb
FROM sys.dm_os_memory_clerks GROUP BY [type] ORDER BY mb DESC;
```

### 11.4. Query Store

- С SQL Server 2016; **в 2022 и новее включён по умолчанию (`READ_WRITE`) для новых баз**, в 2016–2019 — выключен [MS Learn]. Есть во всех редакциях, включая Express [MS Learn]. Хранит историю запросов, планов и статистики выполнения в самой базе — переживает перезапуск и очистку кеша [MS Learn].
- База 1С, созданная платформой на SQL Server 2022, получает Query Store по умолчанию, если в `model` не изменено иное ⚠ (вывод из документации Microsoft, на 1С не проверялось). Для старых баз:

```sql
ALTER DATABASE [buh] SET QUERY_STORE = ON (OPERATION_MODE = READ_WRITE);   -- [MS Learn]
-- топ запросов за сутки по суммарной длительности [практика]
SELECT TOP (20) q.query_id,
       SUM(rs.count_executions) AS execs,
       SUM(rs.avg_duration * rs.count_executions) / 1000 AS total_ms,
       SUM(rs.avg_cpu_time * rs.count_executions) / 1000 AS cpu_ms,
       SUM(rs.avg_logical_io_reads * rs.count_executions) AS reads,
       MAX(qt.query_sql_text) AS sql_text
FROM sys.query_store_query AS q
JOIN sys.query_store_query_text AS qt ON qt.query_text_id = q.query_text_id
JOIN sys.query_store_plan AS p ON p.query_id = q.query_id
JOIN sys.query_store_runtime_stats AS rs ON rs.plan_id = p.plan_id
JOIN sys.query_store_runtime_stats_interval AS i ON i.runtime_stats_interval_id = rs.runtime_stats_interval_id
WHERE i.start_time >= DATEADD(HOUR, -24, SYSUTCDATETIME())
GROUP BY q.query_id
ORDER BY total_ms DESC;
```

- В SSMS: база → Query Store → «Top Resource Consuming Queries», «Regressed Queries» [практика]. Хорош для сравнения «до/после» при обновлении SQL Server, смене уровня совместимости и регламенте индексов [MS Learn].
- ⚠ Дополнительная нагрузка Query Store на очень загруженных базах 1С в первоисточниках этой сессии не оценивалась — включать с мониторингом.

### 11.5. Связь запроса SQL с кодом 1С: техжурнал `DBMSSQL`

- События `DBMSSQL` (операторы SQL) и `DBMSSQLCONN` (первое соединение, выбор провайдера) [ИТС-адм прил. 3, разд. 3.24.2.3]; свойства `Sql`, `planSQLText` (с `<plansql/>`), `Context` (стек), `Dbpid` (`session_id` в СУБД), `Database` (`ИмяСервера\ИмяБазы`) [ИТС-адм прил. 3, разд. 3.24.2.4.2]. Сбор планов замедляет запросы — только на время анализа [ИТС-адм прил. 3, разд. 3.24.2.10.1].
- План MS SQL упрощён: `Rows`, `Executes`, `EstimateRows`, `EstimateIO`, `EstimateCPU`, `AvgRowSize`, `TotalSubtreeCost`, `EstimateExecutions`, `StmtText` через запятую, `StmtText` — до конца строки [ИТС-адм прил. 3, разд. 3.24.2.10.3].

«Узкий» техжурнал на один запрос (фильтр по именам таблиц из DMV) [ИТС-мет 5861, 2015; 5813, 2015]:

```xml
<?xml version="1.0" encoding="UTF-8"?>
<config xmlns="http://v8.1c.ru/v8/tech-log">
  <log location="C:\Sql_Reads" history="2">
    <event>
      <eq property="Name" value="DBMSSQL"/>
      <like property="Sql" value="%SELECT TOP%Reference5774%"/>
    </event>
    <property name="all"/>
  </log>
  <plansql/>
</config>
```

⚠ **Ловушка при копировании из методичек:** в примерах [ИТС-мет 5861] и [ИТС-мет 5813] путь записан как `С:\Sql_Reads`, где буква «С» — **кириллическая** (проверено по байтам текста 5861: `D0 A1`). Такой путь не совпадёт с диском `C:` — техжурнал не появится или появится в неожиданном месте. Набирайте букву диска вручную. В 5813 к тому же испорчено пространство имён `xmlns`.

Стек кода 1С будет в конце события с запросом [ИТС-мет 5861]. Имена таблиц (`_Reference5774`, `_InfoRg13229`…) сопоставляются с объектами метаданных функцией `ПолучитьСтруктуруХраненияБазыДанных()` [`../its-metod/razmeshchenie-dannyh-i-indeksy.md`].

### 11.6. Длинные транзакции

```sql
SELECT st.session_id,                                  -- «Соединение с СУБД» в консоли кластера [ИТС-мет 5813]
       at.transaction_begin_time,
       DATEDIFF(MINUTE, at.transaction_begin_time, GETDATE()) AS minutes,
       s.host_name, s.program_name, s.login_name, DB_NAME(s.database_id) AS db
FROM sys.dm_tran_session_transactions AS st
JOIN sys.dm_tran_active_transactions  AS at ON at.transaction_id = st.transaction_id
JOIN sys.dm_exec_sessions             AS s  ON s.session_id = st.session_id
ORDER BY at.transaction_begin_time;
```

Полная версия с планом и текстом — в [ИТС-мет 5813, 2015]; там же — транзакции хранилища версий `sys.dm_tran_active_snapshot_database_transactions`. Длинная транзакция держит журнал (`ACTIVE_TRANSACTION`, раздел 8.2) и хранилище версий в tempdb (раздел 7.1). Порядок [ИТС-мет 5813]: найти сеанс в консоли кластера по `session_id`, записать номер и время начала сеанса, завершить, разобрать по журналу регистрации, что он делал.

### 11.7. «Размазанная» нагрузка и высокая загрузка CPU

[ИТС-мет 5861, 2015] предлагает два подхода: (1) лидеры по DMV (11.3) → сеансы по `session_id` → техжурнал → исправление; дополнительно — самые частые запросы и индексы с высокими издержками обслуживания (`sys.dm_db_index_usage_stats`); (2) то же за последний час, а если нагрузка «размазана» по множеству мелких запросов (пакетные и динамически собираемые тексты) — **трассировка + техжурнал** [ИТС-мет 5910, 2016]: одновременно собрать серверную трассировку (`sp_trace_create`, события `RPC:Completed` и `SQL:BatchCompleted`, фильтр по базе, 15–20 минут; **не SQL Server Profiler** — он нагружает сервер и теряет события) и техжурнал `DBMSSQL` по этой базе; нормализовать тексты (параметры, `#tt…`, пробелы), посчитать MD5, сгруппировать и соединить с контекстами (первая и последняя строки стека) — получится вклад каждого места кода в CPU или чтения.

Актуальность: SQL Trace и Profiler объявлены устаревшими, Microsoft рекомендует расширенные события [MS Learn]. Методика 1С пока работает ⚠, но новые сборы лучше делать сеансом расширенных событий (`rpc_completed`, `sql_batch_completed`) ⚠ — готового сценария 1С для XE нет; загрузка `.xel` через `sys.fn_xe_file_target_read_file` — `../its-metod/vzaimoblokirovki-i-oshibki-blokirovok.md`, разд. 2.4.6. Без трассировки — Query Store (11.4).

## 12. Объём таблиц и базы; перенос MS SQL → PostgreSQL

### 12.1. Сколько занимают таблицы

[ИТС-мет 2497, 2008]: `sp_spaceused` — строки, зарезервированное и использованное место таблицы и её индексов или всей базы; по всем таблицам — `sp_MSforeachtable @command1 = "sp_spaceused '?'"`, по всем базам — `sp_MSforeachdb 'Use [?] exec sp_spaceused'` (обе процедуры недокументированные [практика]). Без них [практика]:

```sql
USE [buh];
EXEC sp_spaceused;                                           -- вся база
SELECT TOP (50) t.name AS table_name,
       SUM(CASE WHEN ps.index_id IN (0, 1) THEN ps.row_count ELSE 0 END) AS rows,
       SUM(ps.reserved_page_count) * 8 / 1024 AS reserved_mb,
       SUM(CASE WHEN ps.index_id IN (0, 1)
                THEN ps.in_row_data_page_count + ps.lob_used_page_count + ps.row_overflow_used_page_count
                ELSE 0 END) * 8 / 1024 AS data_mb
FROM sys.dm_db_partition_stats AS ps
JOIN sys.tables AS t ON t.object_id = ps.object_id
GROUP BY t.name
ORDER BY reserved_mb DESC;
```

В SSMS то же — стандартный отчёт «Использование дисковой памяти верхними таблицами» [`../its-metod/sbor-dannyh-dlya-rassledovaniya-problem.md`]. Имя таблицы → объект 1С: `ПолучитьСтруктуруХраненияБазыДанных()` [`../its-metod/razmeshchenie-dannyh-i-indeksy.md`]. Типичные лидеры роста — регистры сведений с историей, журналы, версии объектов, таблицы изменений планов обмена [практика].

### 12.2. Перенос базы с MS SQL на PostgreSQL (кратко)

- Через `.dt`: выгрузка → новая ИБ в PostgreSQL → загрузка [ИТС-КС разд. 5.1.2; ИТС-адм разд. 6.7–6.8]. Перед выгрузкой — тестирование и исправление [ИТС-адм разд. 6.7].
- Без промежуточного файла (8.3.23+): `ibcmd infobase replicate` [ИТС-адм разд. 7.4.17; прил. 4, разд. 4.10.4.6]:

```bat
ibcmd infobase replicate --data=D:\ss-data\replicate --dbms=MSSQLServer --database-server=sql01 ^
  --database-name=buh --database-user=buh_1c --request-database-password ^
  --target-dbms=PostgreSQL --target-database-server=srv-1c-db --target-database-name=buh ^
  --target-database-user=buh_1c --target-request-database-password --target-create-database ^
  --jobs-count=4 --target-jobs-count=4 --force
```

Параметры: `--batch-size` (строк в порции, по умолчанию 10 000), `--batch-data-size` (байт, по умолчанию 10 485 760), `--jobs-count`/`--target-jobs-count` (потоки, по умолчанию — число логических ядер), `--force` — принудительно завершить сеансы исходной ИБ; из файловой базы в клиент-серверную реплицировать нельзя [ИТС-адм прил. 4, разд. 4.10.4.6]. Пароли в примере ИТС в открытом виде даны «исключительно в демонстрационных целях» [ИТС-адм разд. 7.4.17]. ⚠ Где запускать: автономный сервер на Linux с MS SQL не работает [ИТС-адм разд. 7.2] — надёжно запускать `ibcmd.exe` на Windows-машине с платформой той же версии, а в `pg_hba.conf` целевого PostgreSQL разрешить её адрес (`../1c/10`, раздел 7). Для вашей площадки целевой сервер — «PostgreSQL для 1С» на `srv-1c-db` (ветка 16, локаль `en_US.UTF-8` — `../guides/07-postgresql-dlya-1c-s-1c-postgres-ru.md`).
- Что меняется после переезда (смещение дат не используется, `mchar`/`mvarchar`, другие планы запросов, удаление соединений из консоли невозможно) — `../1c/10`, раздел 7.

## 13. PostgreSQL для 1С на Windows (кратко)

Сборки, установка и настройка подробно описаны для Linux в `../postgresql/01`–`09` и `../guides/07`; здесь — только специфика Windows.

- PostgreSQL работает и под Windows, и под Linux; кластер — в UTF-8; табличные пространства `v81c_data`/`v81c_index` используются, если есть [ИТС-КС разд. 3.2.5.1]. Нужна сборка с патчем 1С или от Postgres Pro, версии до 18 [ИТС-КС разд. 1.5.8]. Сборка 1С для Windows — `postgresql-<Версия>-1.1C.msi` [ИТС-КС разд. 3.2.5.2]; «PostgreSQL для 1С» от Postgres Professional — только 64-разрядные Windows и Linux [`../postgresql/01`, разд. 2.3].
- Пользователю СУБД `SUPERUSER` нужен только на время создания ИБ (потом `alter user dbuser with nosuperuser;`); нестандартный порт — `localhost port=6432;` в поле сервера [ИТС-адм разд. 5.2.1.3.3].
- Отличия от Linux ⚠ [практика]: служба Windows вместо `systemd` (имя и каталоги задаёт установщик: `Get-CimInstance Win32_Service | Where-Object Name -like '*postgres*' | Select-Object Name, PathName`), `pg_hba.conf`/`postgresql.conf` — в каталоге данных, правило брандмауэра на 5432; тюнинг из `../postgresql/02` переносить с проверкой.
- **Ошибка `could not send data to server: No buffer space available (0x00002747/10055)`** — исчерпаны временные TCP-порты; совет `MaxUserPort = 65534` в `HKLM\SYSTEM\CurrentControlSet\Services\Tcpip\Parameters` [ИТС-мет 1933, 2010] относится к Windows до Vista/2003 (порты 1025–5000). С Windows Server 2008 диапазон по умолчанию 49152–65535 и настраивается `netsh` (минимум 255 портов, начало не ниже 1025) [MS Learn]:

```bat
netsh int ipv4 show dynamicport tcp
netsh int ipv4 set dynamicport tcp start=10000 num=55535
```

  Перед расширением проверьте, что порты действительно исчерпаны (`netstat -ano | find /c "TIME_WAIT"`), и что диапазон не накрывает порты служб, в том числе 1С (1540, 1541, 1560–1591 [ИТС-КС прил. 3, разд. 3.8]) [практика].
- Правило проекта: «PostgreSQL для 1С» — только для баз 1С; базы сервисов (GlitchTip, Redmine, NetBox) — в отдельном PostgreSQL.

## Что не удалось подтвердить

- ⚠ Поддержка платформой **SQL Server 2025** и **Windows Server 2025** — нет в ИТС 8.3.27, изменениях 8.5.1 и на v8.1c.ru (19.10.2026).
- ⚠ Включает ли платформа `READ_COMMITTED_SNAPSHOT` для базы сама (ИТС называет только уровень изоляции).
- ⚠ Какую сортировку платформа задаёт базе для разных «Языков (стран)», в том числе для конфигураций WE, и важна ли сортировка экземпляра (`tempdb`).
- ⚠ Поддержка OLE DB Driver 19 в 8.3.27 и параметры шифрования в строке подключения платформы; `lpc:` с OLE DB Driver; протокол для локального имени без префикса; префикс `tcp:`; разделитель `Server/instance` или `Server\instance`.
- ⚠ Умолчание «Смещения дат» в диалоге 8.3 и в `rac infobase create`; поведение при подключении к базе с другим смещением; ключи `rac` — сверять с `rac help`.
- ⚠ Флаг 2330 (недокументирован); сохранение `ALLOW_PAGE_LOCKS = OFF` после `REBUILD`; онлайн-перестроение только в Enterprise; ODBC Driver 18 на Linux и шифрование по умолчанию.
- ⚠ Запросы с пометкой [практика] (в том числе `system_health`) не выполнялись; нагрузка Query Store на больших базах 1С не оценена.
- ⚠ Исключения антивируса, лицензирование SQL Server для 1С; службы и каталоги PostgreSQL для 1С на Windows; `ibcmd infobase replicate` с источником MS SQL на Linux.
