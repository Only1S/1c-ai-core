**Условные обозначения, которыми пользуется глава**

| Обозначение | Что означает |
|---|---|

## 4.1. Общая информация

**Только Windows.** При установке в меню «Пуск — Программы» создаётся папка «1С Предприятие 8» (пример для Windows 10) с пунктами:

| Пункт меню | Назначение |
|---|---|
| 1C Предприятие (A.B.C.D) | (в таблице назначений документации пункт не описан) |
| ReadMe — Дополнительная информация | Сведения, не вошедшие в документацию |
| Регистрация утилиты администрирования серверов (A.B.C.D) | Регистрирует `radmin.dll` конкретной версии; после этого утилитой администрирования можно подключаться к серверам этой версии |
| Администрирование серверов 1С Предприятия | Утилита администрирования кластера (есть, если ставились компоненты доступа к кластеру серверов) |
| Запуск сервера (A.B.C.D) | Запуск сервера как сервиса (если при установке стоял флажок «Установить сервер 1С:Предприятия 8 как сервис Windows») или как приложения (если флажка не было; тогда остановка — закрытием приложения) |
| Установка драйвера защиты | Запуск установки драйвера защиты |
| Удаление драйвера защиты | Запуск удаления драйвера защиты |

Правила именования пунктов:
- пункт без номера версии использует программу/файл из версии, установленной последней по времени;
- пункт с `(A.B.C.D)` повторяется для каждой установленной версии (две версии — две строки «Запуск сервера (…)»);
- у 64-разрядной установки в названии папки и пунктов присутствует `x86-64`.

Общие положения (для всех ОС):
- При запуске компонентов сервера активно используется интерфейс командной строки (его подробное описание — в отдельном разделе документации, в этой главе не приводится).
- Сервер, установленный в режиме «для пользователя», не может работать как сервис Windows (только Windows).

## 4.2. Запуск агента сервера

### 4.2.1. Общая информация

Чтобы запустить кластер серверов, достаточно запустить агент сервера (`ragent`) — остальное система делает сама.

Алгоритм старта агента:
1. Агент ищет список кластеров, зарегистрированных на этом компьютере.
2. Список найден — агент запускает перечисленные в нём менеджеры кластеров, через них узнаёт, какие рабочие процессы должны работать в каждом кластере, и запускает их сам либо через агентов других рабочих серверов кластера.
3. Список не найден — агент создаёт кластер по умолчанию.

Характеристики кластера по умолчанию:

| Характеристика | Значение |
|---|---|
| Сетевой порт кластера | 1541 |
| Диапазон сетевых портов | 1560:1591 |
| Порт сервера отладки (при запуске в отладочном режиме по протоколу HTTP) | 1550 |
| Рабочие процессы | один; порт берётся из указанного диапазона |

Полное описание командной строки `ragent` находится в другом разделе документации (в этой главе только примеры).

### 4.2.2. Для ОС Linux

#### 4.2.2.1. Общая информация

- Программа установки настраивает серверные процессы на работу в режиме «демона» — без привязки к управляющему терминалу.
- При необходимости агент можно запускать и вручную, с ключами командной строки.
- **Ограничение:** в режиме «демона» отладка по протоколу HTTP не поддерживается.

Подсистема управления службами зависит от архитектуры процессора:

| Архитектура | Подсистема | Инструменты |
|---|---|---|
| x86 / x86-64, ARM64 | systemd | утилита `systemctl`; настройка — через юниты (service-файлы) |
| E2K | init | зависят от дистрибутива и формата пакетов Linux |

- Автозапуск кластера при старте ОС настраивается средствами соответствующей подсистемы.
- Для работы с подсистемой управления службами нужны права суперпользователя (root). В примерах документации `sudo` опущен для краткости; на практике команды выполняются из консоли root либо с префиксом `sudo`:

```
sudo systemctl list
sudo chkconfig --add <УникальноеИмяСкрипта>
```

Первая команда, по тексту документации, получает список работающих сервисов; вторая добавляет скрипт запуска кластера в стартовый скрипт системы (RPM-дистрибутивы).

#### 4.2.2.2. Запуск как приложения

Агент сервера можно запустить как обычное приложение. Простейший пример:

```
/opt/1cv8/x86_64/8.3.27.100/ragent /d "~/cluster data" /debug -HTTP
```

Что задаёт пример:
- версия платформы 8.3.27.100, 64-разрядная (путь `/opt/1cv8/x86_64/8.3.27.100/`);
- `/d "~/cluster data"` — каталог служебных файлов кластера серверов;
- `/debug -HTTP` — кластер запущен в режиме отладки по протоколу HTTP.

Связанные разделы документации (в этой главе не раскрыты): командная строка запуска `ragent`; конфигурационный файл настройки пользователей сервера отладки.

#### 4.2.2.3. Запуск как сервиса

##### 4.2.2.3.1. Подсистема systemd

**Только для архитектур x86/x86-64 и ARM64.**

Чтобы сервер работал как сервис и мог стартовать при загрузке ОС, юнит кластера серверов нужно зарегистрировать в systemd. Путь к юниту при регистрации указывается полностью.

Для Linux (кроме CentOS 7):

```
systemctl link /opt/1cv8/arch/A.B.C.D/srv1cv8-A.B.C.D@.service
```

Для CentOS 7 — в два шага. Сначала создаётся жёсткая ссылка (или копия) файла `srv1cv8-A.B.C.D@.service` под именем `srv1cv8-A.B.C.D@default.service`:

```
ln /opt/1cv8/arch/A.B.C.D/srv1cv8-A.B.C.D@{,default}.service
```

Затем регистрируется юнит:

```
systemctl link /opt/1cv8/arch/A.B.C.D/srv1cv8-A.B.C.D@default.service
```

В командах `arch` заменяется на `i386` (32-разрядная версия) или `x86_64` (64-разрядная версия).

Свойства поставляемого юнита:
- Файл юнита лежит в каталоге версии: `/opt/1cv8/arch/A.B.C.D/srv1cv8-A.B.C.D@.service` — это шаблон (имя экземпляра передаётся после `@`).
- Юнит из дистрибутива регистрирует экземпляр сервиса кластера с именем `default`.
- Для одновременной работы нескольких экземпляров кластера на одном компьютере требуются дополнительные настройки; они разные для случая «одна версия платформы» (см. 4.3.2.3) и «разные версии платформы» (см. 4.3.2.2).
- После регистрации в список автоматически запускаемых служб попадает запуск кластера серверов конкретной версии и разрядности.

Управление экземпляром сервиса после регистрации:

| Действие | Команда |
|---|---|
| Включить автозапуск при старте ОС | `systemctl enable srv1cv8-A.B.C.D@instName` |
| Отключить автозапуск | `systemctl disable srv1cv8-A.B.C.D@instName` |
| Запуск | `systemctl start srv1cv8-A.B.C.D@instName` |
| Остановка | `systemctl stop srv1cv8-A.B.C.D@instName` |
| Получение статуса | `systemctl status srv1cv8-A.B.C.D@instName` |

Уникальное имя сервиса — `srv1cv8-A.B.C.D@instName`, где `instName` — имя экземпляра; у экземпляра с параметрами по умолчанию имя `default` (то есть `srv1cv8-A.B.C.D@default`).

##### 4.2.2.3.2. Подсистема init

**Только для архитектуры E2K.**

Порядок настройки автозапуска сервера при загрузке ОС:

1. Скопировать файл `srv1cv83` из каталога нужной версии в `/etc/init.d`.
2. Переименовать копию так, чтобы имя было уникальным в пределах `/etc/init.d` (это и есть `<УникальноеИмяСкрипта>`). Допустимо включить в имя полный номер версии: для 8.3.22.100 — `srv8-3-22-100`.
3. Скопировать конфигурационный файл `srv1cv83.conf` из каталога нужной версии:
   - RPM-системы — в `/etc/sysconfig`;
   - DEB-системы — в `/etc/default`.
4. В каталоге назначения у скопированного конфигурационного файла:
   - убрать расширение;
   - дать ему то же имя, что и у стартового скрипта из п. 2 (для примера — `srv8-3-22-100`). Этот файл хранит параметры запуска одноимённого сервера.
5. Добавить скрипт в стартовый скрипт системы.

Для RPM-систем:

```
chkconfig --add <УникальноеИмяСкрипта>
chkconfig <УникальноеИмяСкрипта> on
```

Для DEB-систем:

```
update-rc.d <УникальноеИмяСкрипта> defaults
service <УникальноеИмяСкрипта> start
```

Итог: в список автоматически запускаемых служб добавляется запуск сервера конкретной версии и разрядности.

##### 4.2.2.3.3. Подсистема init: скрипт управления работой

- Кластером управляет скрипт, сделанный на основе `srv1cv83` из каталога конкретной версии — копированием или символической ссылкой.
- Скрипт размещается в `/etc/init.d` и должен иметь уникальное имя (см. п. 2 раздела 4.2.2.3.2).
- Исходный `srv1cv83` из каталога версии не предназначен для запуска прямо из этого каталога.
- У всех скриптов, сделанных на основе `srv1cv83`, одинаковая командная строка:

```
script-from-srv1cv83 start|stop|restart|info|status
```

| Команда | Действие |
|---|---|
| `start` | Запускает сервер. Скрипт запускает один экземпляр сервера — тот, что задан при настройке |
| `stop` | Останавливает сервер. Останавливается только тот сервер, который был запущен этим же скриптом (командой `start`) |
| `restart` | Перезапуск; равносилен последовательности `stop` и `start` |
| `status` | Состояние сервера: запущен или нет, а если запущен — работает ли в данный момент |
| `info` | Настройки сервера: порты, заданные при запуске, каталог кластера, статус режима отладки конфигурации, уровень безопасности соединений |

#### 4.2.2.4. Редактирование параметров экземпляра кластера серверов

##### 4.2.2.4.1. Подсистема systemd

**Только для архитектур x86/x86-64 и ARM64.**

Параметры экземпляра кластера меняются командой:

```
systemctl edit srv1cv8-A.B.C.D@instanceName
```

В открывшемся файле нужно создать секцию `[Service]` (если её ещё нет) и перечислить в ней изменяемые параметры в нотации systemd:

```
[Service]
Environment=SRV1CV8_REGPORT=1541
```

Разбор строки:
- `Environment` — обязательное слово, его требует синтаксис описания юнита systemd;
- `SRV1CV8_REGPORT` — имя параметра кластера серверов (полный список — в 4.2.2.4.3);
- `1541` — значение параметра (зависит от того, какой параметр задаётся).

##### 4.2.2.4.2. Подсистема init

**Только для архитектуры E2K.**

- Параметры экземпляра правятся в его конфигурационном файле любым текстовым редактором.
- Имя конфигурационного файла совпадает с именем скрипта запуска; файл должен быть без расширения.
- Расположение: RPM-системы — `/etc/sysconfig`, DEB-системы — `/etc/default`.

##### 4.2.2.4.3. Параметры конфигурационного файла

Параметры, доступные для редактирования (одни и те же имена используются и в `Environment=` для systemd, и в конфигурационном файле init):

| Параметр | Назначение | Допустимые значения | Значение по умолчанию |
|---|---|---|---|
| `SRV1CV8_DATA` | Каталог данных сервера: полный путь к каталогу служебных файлов кластера серверов (в том числе список кластеров и список информационных баз кластера) | путь | `/home/usr1cv8/.1cv8/1C/1cv8` |
| `SRV1CV8_DEBUG` | Признак запуска кластера в режиме отладки | пусто — отладка выключена; `-debug` — отладка по TCP; `-debug -tcp` — отладка по TCP; `-debug -http` — отладка по HTTP | пустое значение |
| `SRV1CV8_KEYTAB` | Путь к keytab-файлу, который кластер серверов использует для аутентификации операционной системы | путь | `/opt/1cv8/x86_64/A.B.C.D/usr1cv8.keytab` |
| `SRV1CV8_PINGPERIOD` | Период проверки системы отслеживания разрыва соединений, в миллисекундах | число, мс | 1 000 |
| `SRV1CV8_PINGTIMEOUT` | Таймаут проверки системы отслеживания разрыва соединений, в миллисекундах | число, мс | 5 000 |
| `SRV1CV8_PORT` | Номер сетевого порта агента сервера (`ragent`) | номер порта | 1540 |
| `SRV1CV8_RANGE` | Диапазоны сетевых портов для динамического выбора | диапазоны портов (в примерах главы — запись вида `2560:2591`) | `1561:1590` |
| `SRV1CV8_REGPORT` | Номер сетевого порта главного менеджера кластера (`rmngr`) | номер порта | 1541 |
| `SRV1CV8_SECLEV` | Уровень безопасности соединений | `0` — выключено; `1` — установка соединения; `2` — постоянно | `0` |

Примечания к таблице:
- **`SRV1CV8_PINGPERIOD` и `SRV1CV8_PINGTIMEOUT`.** Значения можно менять и инструментами администрирования кластера. Правило приоритета: если в настройках кластера хотя бы один из параметров «Период проверки» / «Таймаут проверки» не равен 0, действуют значения из настроек кластера; в противном случае берутся параметры командной строки запуска кластера серверов.
- **`SRV1CV8_DEBUG`.** ⚠ в источнике неясно: среди допустимых значений есть `-debug -http`, но в 4.2.2.1 сказано, что при работе сервера в режиме «демона» отладка по HTTP не поддерживается; как эти два утверждения соотносятся, глава не поясняет.
- **`SRV1CV8_RANGE`.** Умолчание `1561:1590` отличается от диапазона кластера по умолчанию `1560:1591` из 4.2.1 (см. пометку в начале конспекта).
- Для параметров портов, периода/таймаута проверки и уровня безопасности документация отсылает к другим разделам (подробности в этой главе не приведены).

### 4.2.3. Для ОС Windows

#### 4.2.3.1. Запуск как приложения

**Только Windows.** Пример простейшего запуска агента как приложения:

```
"C:\Program Files\1cv8\8.3.27.100\bin\ragent.exe" /d "D:\Рабочий каталог\1C srvinfo\" /debug -HTTP
```

Версия 8.3.27.100 (разрядность определяется разрядностью ОС), каталог служебных файлов кластера — `D:\Рабочий каталог\1C srvinfo\`, отладка по HTTP.

#### 4.2.3.2. Запуск как сервиса

**Только Windows.**
- Если при установке выбран запуск агента центрального сервера как сервиса, сервис стартует уже в ходе установки и далее при каждом старте ОС. Если агент ставился как приложение, сервис можно зарегистрировать вручную и затем запустить.
- Имя сервиса: 32-разрядная версия — `1C:Enterprise 8.3 Server Agent`; 64-разрядная — `1C:Enterprise 8.3 Server Agent (x86-64)`.
- Регистрация, отмена регистрации, запуск и остановка сервиса `ragent` выполняются от имени администратора; при нехватке привилегий выдаётся запрос на их повышение.
- Запуск и остановка — стандартной оснасткой служб Windows (служба «Агент сервера 1С:Предприятия 8» / 1C:Enterprise 8 Server Agent).
- Для упрощения регистрации и её отмены есть примеры командных файлов (в другом разделе документации).

Регистрация сервиса (простейший вид) и отмена регистрации:

```
C:\Program Files\1cv8\8.3.27.100\bin\ragent /srvc /agent /d "D:\Рабочий каталог\1C srvinfo\"
ragent /rmsrvc
```

## 4.3. Обеспечение совместной работы нескольких серверных процессов

### 4.3.1. Общая информация

Обычная ситуация — один агент сервера на одном рабочем сервере. Кто отвечает за отсутствие конфликтов портов:

| Ситуация | Кто следит за конфликтами |
|---|---|
| Несколько кластеров под управлением одного агента сервера — сетевые порты этих кластеров | агент сервера (автоматически) |
| Кластеры под управлением разных агентов сервера — порты менеджеров кластера | администратор, вручную |
| Диапазоны портов рабочих процессов на сервере, который задействован в разных кластерах | администратор, вручную — всегда, даже если кластеры работают под одним и тем же агентом |

Два и более агента сервера на одном компьютере, каждый со своим набором кластеров, — нормальная, но редкая и специфичная конфигурация. Типичная причина: на одном компьютере нужны разные версии сервера «1С:Предприятия».

Условия параллельной работы двух агентов сервера, обслуживающих разные кластеры:
- у агентов разные сетевые порты;
- агенты работают с разными каталогами служебных файлов;
- кластеры, создаваемые для каждого агента, имеют разные сетевые порты;
- диапазоны портов рабочих процессов на этом сервере не пересекаются (если сервер участвует в разных кластерах).

**Ограничение:** смена сетевых портов у работающего экземпляра сервера не предусмотрена. Единственный путь — зарегистрировать другой экземпляр кластера серверов и перенести информационные базы в новый кластер (порядок — в 4.3.2.4).

### 4.3.2. Для ОС Linux

#### 4.3.2.1. Общая информация

- Раздел описывает запуск на одном компьютере более одного экземпляра кластера серверов.
- Программа установки не даёт поменять сетевые порты сервера, поэтому сразу после установки новый экземпляр сервера работать не сможет (как настроить экземпляры — в следующих подразделах).
- Установка сервера для Linux всегда выполняется в режиме демона.
- Выбор подсистемы управления службами, требование прав root и замечание про `sudo` — те же, что в 4.2.2.1 (x86/x86-64, ARM64 — systemd и `systemctl`; E2K — init).

#### 4.3.2.2. Разные версии «1С:Предприятия» для разных экземпляров кластера

##### 4.3.2.2.1. Как сервис

- В подсистеме управления службами регистрируется нужное число экземпляров служб, и у каждого экземпляра корректно настраиваются параметры.
- Для каждой службы выполняется обычная последовательность установки автоматического запуска (см. 4.2.2.3: для systemd — `systemctl link` юнита соответствующей версии, для init — копирование скрипта и конфигурационного файла).
- Дальше каждым экземпляром управляют штатными средствами используемой подсистемы управления службами.

##### 4.3.2.2.2. Как приложение

Несколько экземпляров сервера разных версий запускаются как приложения из командной строки:

```
/opt/1cv8/x86_64/8.3.27.200/ragent -port 1540 -regport 1541 -range 1560:1590 -d /home/usr1cv8/.1cv8/1C/srv1
/opt/1cv8/x86_64/8.3.27.300/ragent -port 2540 -regport 2541 -range 2560:2590 -d /home/usr1cv8/.1cv8/1C/srv2
```

| | 1-й кластер | 2-й кластер |
|---|---|---|
| Версия (64-разрядная) | 8.3.27.200 | 8.3.27.300 |
| Сетевые порты | 15xx (`-port 1540`, `-regport 1541`, `-range 1560:1590`) | 25xx (`-port 2540`, `-regport 2541`, `-range 2560:2590`) |
| Каталог данных кластера (`-d`) | `/home/usr1cv8/.1cv8/1C/srv1` | `/home/usr1cv8/.1cv8/1C/srv2` |

Ключи `ragent`, встречающиеся в примерах главы для Linux: `-port`, `-regport`, `-range`, `-d` (каталог данных кластера); в примере 4.2.2.2 ключи записаны через косую черту — `/d`, `/debug -HTTP`. Расшифровки ключей в этой главе нет (значения в примерах совпадают по смыслу с параметрами `SRV1CV8_PORT`, `SRV1CV8_REGPORT`, `SRV1CV8_RANGE`, `SRV1CV8_DATA` из 4.2.2.4.3); полное описание командной строки `ragent` — в другом разделе документации.

#### 4.3.2.3. Одна версия «1С:Предприятия» для разных экземпляров кластера

##### 4.3.2.3.1. Как сервис

###### Подсистема systemd

**Только для архитектур x86/x86-64 и ARM64.**

Несколько экземпляров кластера одной версии получают параметризацией шаблона юнита `srv1cv8-8.X.Y.Z@.service`: после символа `@` передаётся произвольное имя экземпляра.

Порядок действий (в примере документации новый экземпляр называется `2xports`):

1. Выбрать имя нового экземпляра — например, `2xports`.
2. Создать конфигурационный файл экземпляра:

```
systemctl edit srv1cv8-A.B.C.D@2xports.service
```

3. Внести в файл текст:

```
[Service]
Environment=SRV1CV8_DATA=/home/usr1cv8/.1cv8/1C/1cv8_2xports
Environment=SRV1CV8_PORT=2540
Environment=SRV1CV8_REGPORT=2541
Environment=SRV1CV8_RANGE=2560:2591
```

4. Указать (или поправить) в открытом файле значения `SRV1CV8_DATA`, `SRV1CV8_PORT`, `SRV1CV8_REGPORT` и `SRV1CV8_RANGE`.
5. Зарегистрировать новый юнит в systemd:

```
systemctl link /opt/1cv8/arch/A.B.C.D/srv1cv8-A.B.C.D@2xport.service
```

6. Новым сервисом управляют так же, как описано для автоматического запуска кластера (таблица команд `enable` / `disable` / `start` / `stop` / `status` в 4.2.2.3.1).

⚠ в источнике неясно: в шагах 1–3 экземпляр назван `2xports`, а в команде шага 5 и в шаге 6 — `2xport` (без «s»); по смыслу это один и тот же экземпляр, расхождение имён есть в самой документации. Откуда в каталоге версии берётся файл `srv1cv8-A.B.C.D@<имя>.service` для команды `systemctl link`, в этом разделе не поясняется (для сравнения: в 4.2.2.3.1 для CentOS 7 файл с именем экземпляра создаётся жёсткой ссылкой на шаблон).

###### Подсистема init

**Только для архитектуры E2K.**

Для одновременной работы двух кластеров повторяются шаги 1–4 из 4.2.2.3.2:

1. Скопировать `srv1cv83` из каталога версии в `/etc/init.d`.
2. Дать копии уникальное в пределах `/etc/init.d` имя (`<УникальноеИмяСкрипта>`; пример для 8.3.22.100 — `srv8-3-22-100`).
3. Скопировать `srv1cv83.conf` из каталога версии в `/etc/sysconfig` (RPM) или `/etc/default` (DEB).
4. Убрать у копии расширение и назвать её так же, как стартовый скрипт.

Затем в созданном конфигурационном файле задаются корректные параметры нового экземпляра (перечень — 4.2.2.4.3), после чего экземпляр запускается скриптом из п. 2 (команды скрипта — 4.2.2.3.3).

##### 4.3.2.3.2. Как приложение

Запуск нескольких экземпляров сервера как приложений из командной строки:

```
/opt/1cv8/x86_64/8.3.27.200/ragent -port 1540 -regport 1541 -range 1560:1590 -d /home/usr1cv8/.1cv8/1C/srv1
/opt/1cv8/x86_64/8.3.27.200/ragent -port 2540 -regport 2541 -range 2560:2590 -d /home/usr1cv8/.1cv8/1C/srv2
```

Оба кластера запускаются 64-разрядной версией 8.3.27.200; первый обслуживает порты 15xx и хранит данные в `/home/usr1cv8/.1cv8/1C/srv1`, второй — порты 25xx и каталог `/home/usr1cv8/.1cv8/1C/srv2`. (Вводная фраза раздела в документации говорит о «разных версиях», хотя пример — про одну версию.)

#### 4.3.2.4. Замена сетевых портов работающего экземпляра сервера «1С:Предприятие»

Смена портов у уже работающего экземпляра не предусмотрена. Если она нужна:

1. Создать новый экземпляр сервера с нужными сетевыми портами и остальными параметрами.
2. Зарегистрировать в новом сервере существующие информационные базы.
3. Перевести клиентов на новый сервер.
4. Остановить и удалить старый экземпляр сервера вместе с данными кластера.

### 4.3.3. Для ОС Windows

#### 4.3.3.1. Общая информация

**Только Windows.** Второй экземпляр сервера рекомендуется ставить как приложение, а не как сервис; зарегистрировать его сервисом можно позже, сразу с нужными параметрами. Операции с сервисом `ragent` — от имени администратора (иначе запрос повышения привилегий). Программа установки не позволяет сменить порты, поэтому новый экземпляр после установки работать не сможет. Для 32-разрядного сервера на 64-разрядной ОС в примерах вместо `C:\Program Files` используется `C:\Program Files (x86)`.

#### 4.3.3.2. Вспомогательные инструменты

**Только Windows.** Программа установки всегда изменяет параметры запуска одной-единственной службы кластера. Штатных средств регистрации нескольких экземпляров сервиса в платформе нет — используется утилита `sc` (регистрация и отмена регистрации); у всех одновременно работающих экземпляров должны быть разные наборы портов и разные каталоги кластера. Готовые пакетные файлы приведены в другом разделе документации.

#### 4.3.3.3. Разные версии «1С:Предприятия» для разных экземпляров кластера

##### 4.3.3.3.1. Как сервис

**Только Windows.** Используется командный файл `register-agent.bat` (текст файла — в другом разделе документации). В примере ему передаются три аргумента — номер версии, число `15` или `25` и каталог кластера (смысл аргументов глава отдельно не расписывает, он виден из результата регистрации ниже):

```
register-agent 8.3.26.100 15 "c:\cluster_data\cluster 1"
register-agent 8.3.27.200 25 "c:\cluster_data\cluster 2"
```

| | Первая строка | Вторая строка |
|---|---|---|
| Версия | 8.3.26.100 | 8.3.27.200 |
| Имя службы | `1C:Enterprise 8.3 Server Agent 1540 8.3.26.100` | `1C:Enterprise 8.3 Server Agent 2540 8.3.27.200` |
| Порты | 1540, 1541, 1560:1591 | 2540, 2541, 2560:2591 |
| Каталог реестра кластера | `C:\cluster_data\cluster 1` | `C:\cluster_data\cluster 2` |
| Описание службы | «Агент сервера 1С:Предприятия 8.3. Параметры: 8.3.26.100, 1540, 1541, 1560:1591» | «Агент сервера 1С:Предприятия 8.3. Параметры: 8.3.27.200, 2540, 2541, 2560:2591» |

> Примечание составителя (19.10.2026): «Руководство администратора», прил. 4, разд. 4.12.2 (тот же `register-agent.bat`) даёт имя службы без префикса — `Server Agent 2540 8.3.27.100` (конспект `adm-pr04-komandnye-stroki-utilit-p3.md`). Расхождение внутри документации. Фактическое имя смотреть в тексте `register-agent.bat` своей версии или после регистрации — `Get-Service *Agent*`. Разбор — `kb/1c-windows/01-ustanovka-servera-i-sluzhba-windows.md`.

##### 4.3.3.3.2. Как приложение

**Только Windows.** Запуск из командной строки через `start` (заголовки окон — `Server 1` и `Server 2`):

```
start "Server 1" "C:\Program Files\1cv8\8.3.27.200\bin\ragent.exe" /port 1540 /regport 1541 /range 1560:1590 /d d:\ClusterData\Srv1
```

Порты 15xx и 25xx, каталоги данных `d:\ClusterData\Srv1` и `d:\ClusterData\Srv2`; разрядность — по разрядности ОС. ⚠ в источнике неясно: раздел называется «разные версии», но в обеих строках примера указана одна версия 8.3.27.200.

#### 4.3.3.4. Одна версия «1С:Предприятия» для разных экземпляров кластера

##### 4.3.3.4.1. Как сервис

**Только Windows.** Тот же `register-agent.bat`, одна версия, разные параметры и разные имена служб:

Вторая служба: порты 2540, 2541, 2560:2591, каталог `C:\cluster_data\cluster 2`. ⚠ в источнике неясно: имя второй службы в документации записано так же, как у первой (`... ##### 4.3.3.4.2. Как приложение

**Только Windows.** Команды те же, что в 4.3.3.3.2 (две строки `start ... ragent.exe` версии 8.3.27.200 с портами 15xx / 25xx и каталогами `d:\ClusterData\Srv1` / `d:\ClusterData\Srv2`). ⚠ в источнике неясно: в пояснении к этому примеру каталоги данных названы Linux-путями `/home/usr1cv8/.1cv8/1C/srv1` и `/home/usr1cv8/.1cv8/1C/srv2`, что не совпадает с командами.

## Что важно администратору Linux

1. **На x86-64 и ARM64 сервер 1С управляется через systemd, на E2K — через init.** Разделы про `srv1cv83`, `/etc/init.d`, `chkconfig`, `update-rc.d` относятся только к E2K; для обычного сервера на x86-64 рабочий инструмент — `systemctl`.
2. **Юнит нужно зарегистрировать по полному пути:** `systemctl link /opt/1cv8/arch/A.B.C.D/srv1cv8-A.B.C.D@.service` (`arch` = `x86_64` или `i386`). Поставляемый юнит — шаблон, экземпляр с параметрами по умолчанию называется `default`.
3. **Имя сервиса включает полный номер версии:** `srv1cv8-A.B.C.D@instName`. Автозапуск — `systemctl enable`, управление — `start` / `stop` / `status` / `disable` с тем же именем. Регистрируется запуск кластера конкретной версии и разрядности.
4. **Параметры экземпляра меняются через `systemctl edit srv1cv8-A.B.C.D@instanceName`:** в секции `[Service]` строками `Environment=ИМЯ=значение`. Доступные имена: `SRV1CV8_DATA`, `SRV1CV8_DEBUG`, `SRV1CV8_KEYTAB`, `SRV1CV8_PINGPERIOD`, `SRV1CV8_PINGTIMEOUT`, `SRV1CV8_PORT`, `SRV1CV8_RANGE`, `SRV1CV8_REGPORT`, `SRV1CV8_SECLEV`.
5. **Умолчания:** агент — порт 1540, главный менеджер кластера — 1541, `SRV1CV8_RANGE` — `1561:1590`, каталог данных — `/home/usr1cv8/.1cv8/1C/1cv8`, keytab — `/opt/1cv8/x86_64/A.B.C.D/usr1cv8.keytab`, период/таймаут проверки соединений — 1 000 / 5 000 мс, уровень безопасности — 0.
6. **Кластер по умолчанию создаётся сам**, если агент при старте не нашёл список кластеров: порт 1541, диапазон 1560:1591, один рабочий процесс. В документации диапазон кластера по умолчанию (1560:1591) и умолчание `SRV1CV8_RANGE` (1561:1590) не совпадают (⚠ в источнике неясно, какое из значений действует для сервиса).
7. **Отладка по HTTP в режиме «демона» не поддерживается.** Пример запуска с отладкой по HTTP в документации дан для запуска агента как приложения: `ragent /d "<каталог>" /debug -HTTP`; сервер отладки при этом использует порт 1550.
8. **`SRV1CV8_PINGPERIOD` / `SRV1CV8_PINGTIMEOUT` могут не действовать:** если в настройках кластера хотя бы один из параметров «Период проверки» / «Таймаут проверки» отличен от 0, применяются значения из настроек кластера.
9. **Порты работающего экземпляра сменить нельзя.** Нужен новый экземпляр с нужными портами, регистрация в нём существующих информационных баз, перевод клиентов и удаление старого экземпляра вместе с данными кластера.
10. **Второй экземпляр кластера на том же хосте** требует четырёх отличий: порт агента, каталог служебных файлов, порт кластера, непересекающийся диапазон портов рабочих процессов. Программа установки порты не меняет, поэтому новый экземпляр «из коробки» не заработает.
11. **Экземпляр той же версии** создаётся параметризацией шаблона юнита (имя после `@`) и набором `Environment=SRV1CV8_DATA/PORT/REGPORT/RANGE` через `systemctl edit`; в примере документации — порты 2540, 2541, 2560:2591 и каталог `/home/usr1cv8/.1cv8/1C/1cv8_2xports`. В самом примере документации имя экземпляра записано непоследовательно (`2xports` в `systemctl edit`, `2xport` в `systemctl link`) — ⚠ в источнике неясно.
12. **Экземпляры разных версий** — отдельная регистрация юнита каждой версии и настройка параметров каждого экземпляра; как приложения они запускаются командами `ragent -port … -regport … -range … -d …` из каталогов соответствующих версий.
13. **Конфликты диапазонов портов рабочих процессов** администратор отслеживает сам всегда — даже когда кластеры работают под одним агентом; автоматически агент разводит только порты кластеров, которыми управляет сам.
14. **Все операции с подсистемой управления службами требуют root** (в примерах документации `sudo` опущен). Установка сервера на Linux всегда выполняется в режиме демона.
