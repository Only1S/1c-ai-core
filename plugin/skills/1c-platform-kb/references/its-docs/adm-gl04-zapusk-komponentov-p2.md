## 4.3.9. Использование сертификатов

### 4.3.9.1. Общая информация

**Зачем.** При работе через публичные каналы (Интернет) передаваемые данные нужно защищать от перехвата и подмены. Раздел описывает, как такое соединение организуется в системе на базе «1С:Предприятия».

**На чем основано.** Используется инфраструктура открытых ключей (PKI): открытый ключ привязывается к личности владельца через удостоверяющий центр (УЦ).

**Аналогия из документации** (для понимания ролей):

| Образ в аналогии | Что это в реальной схеме |
|---|---|
| Прохожий | Клиентское приложение «1С:Предприятия» |
| Полицейский | Веб-сервер, через который клиент получает доступ к информационной базе |
| Министерство Выдачи Документов, Министерство Управления Полиции | Удостоверяющие центры |
| Паспорт Прохожего, удостоверение Полицейского | Сертификаты, используемые при установке HTTPS-соединения |

Смысл аналогии: каждая сторона проверяет документ другой стороны в том ведомстве, которое его выдало. Если проверяющий не знает ведомство-издателя («другая страна»), проверка не срабатывает — то есть сертификат, выданный неизвестным проверяющей стороне УЦ, подтвердить нельзя.

**Общая последовательность установки защищенного соединения:**

1. Клиентское приложение подключается к веб-серверу и проверяет сертификат сервера. Проверка идет через УЦ, указанный в сертификате веб-сервера, — при условии, что этот УЦ присутствует в списке корневых УЦ на компьютере клиента.
2. Если проверка успешна, клиент предъявляет веб-серверу свой (клиентский) сертификат.
3. Веб-сервер проверяет клиентский сертификат по своему списку корневых УЦ.
4. Если и эта проверка успешна, стороны устанавливают защищенное HTTPS-соединение.

**Шифрование (как сформулировано в документации):** клиент шифрует передаваемые данные открытым ключом сервера (и расшифровывает полученные от сервера); сервер шифрует и расшифровывает данные своим закрытым ключом. Закрытые ключи клиента и веб-сервера разные, и другой стороне они неизвестны.

Это общая схема; детальные варианты — в 4.3.9.2.

### 4.3.9.2. Схемы установки защищенного соединения

Защищенное соединение устанавливается между **тонким клиентом или веб-клиентом** и **веб-сервером**, через который идет подключение к информационной базе. Схем несколько — они зависят от того, какие сертификаты есть на каждой стороне.

Важно: при любом варианте установленное HTTPS-соединение **шифруется**. Таблица ниже описывает только то, чьи сертификаты проверяются.

Обозначения:

- **Сертификат+ / Сертификат-** — сертификат есть / отсутствует. Для сервера это серверный сертификат, для клиента — клиентский.
- **Корневые+ / Корневые-** — есть / отсутствует список сертификатов удостоверяющих центров (УЦ, CA), которым можно проверить предъявленный сертификат. Список должен позволять проверить именно тот сертификат, который предъявила другая сторона (клиентское приложение или веб-сервер).

| № | Сервер | Клиент | Что получается |
|---|---|---|---|
| 1 | Сертификат+, Корневые- | Сертификат-, Корневые- | Не проверяются сертификаты ни сервера, ни клиента. **До версии 8.3.3 был доступен только этот режим** |
| 2 | Сертификат+, Корневые- | Сертификат-, Корневые+ | Проверяется только сертификат сервера; сертификат клиента не проверяется |
| 3 | Сертификат+, Корневые+ | Сертификат-, Корневые- **или** Сертификат-, Корневые+ | **Не поддерживается** |
| 4 | Сертификат+, Корневые+ | Сертификат+, Корневые- | Сертификат сервера не проверяется, сертификат клиента проверяется |
| 5 | Сертификат+, Корневые+ | Сертификат+, Корневые+ | Проверяются сертификаты обеих сторон |

Откуда берутся сертификаты и списки корневых на клиентской стороне:

- **Веб-клиент** — наличие/отсутствие сертификата и списка корневых определяется тем, что установлено в хранилище сертификатов, с которым работает используемый веб-браузер.
- **Тонкий клиент** — сертификат и списки корневых сертификатов задаются параметрами командной строки запуска либо параметрами запуска информационной базы (в источнике — ссылка «см. здесь» на другой раздел; сами имена параметров в этой части не приведены).

### 4.3.9.3. Источники и форматы сертификатов

**Хранилища-источники сертификатов:**

| Источник | Для каких ОС | Примечание |
|---|---|---|
| Системное хранилище сертификатов | macOS, Windows | — |
| Хранилище сертификатов ОС Linux — каталог `/etc/ssl/certs` | Linux | **Все сертификаты, лежащие в этом каталоге, считаются доверенными** |
| Файловые сертификаты | Linux, macOS, Windows | Форматы — см. ниже |

**Дополнительные расположения корневых сертификатов, поддерживаемые на отдельных дистрибутивах Linux:**

| Дистрибутивы | Путь |
|---|---|
| Debian, Mint, Ubuntu | `/etc/ssl/certs/ca-certificates.crt` |
| CentOS, Fedora, RedHat | `/etc/ssl/certs/ca-bundle.trusted.crt` или `/etc/pki/tls/certs/ca-bundle.crt` |
| Alt Linux | `/etc/share/ca-certificates/ca-bundle.crt` |

⚠ в источнике неясно: эти пути в документации названы «каталогами», хотя все они оканчиваются на `.crt`; путь для Alt Linux приведен именно так, как в источнике (`/etc/share/...`).

**Допустимые форматы файловых сертификатов:**

| Формат | Что это | Особенности |
|---|---|---|
| **PEM** (base-64 encoded X.509) | Зашифрованные ключи и сертификаты стандарта X.509 в текстовом виде; данные сертификатов и ключей закодированы в base-64 | Закрытые ключи сертификатов защищены паролем. Этот формат по умолчанию использует, например, веб-сервер Apache. **Если закрытый ключ клиентского сертификата лежит в отдельном файле — его содержимое нужно дописать в файл клиентского сертификата** |
| **P12/PFX** (PKCS#12) | Зашифрованные ключи и сертификаты стандарта PKCS#12 | Файл может быть защищен паролем. Основной формат экспорта/импорта системных хранилищ сертификатов Windows; используется, например, Microsoft IIS. **Файл клиентского сертификата должен содержать его закрытый ключ** |

**Как определяется формат файла — по расширению:**

| Расширение | Формат |
|---|---|
| `*.p12`, `*.pfx` | P12 |
| `*.pem` | PEM |
| любое другое (по умолчанию) | PEM |

### 4.3.9.4. Самоподписанные сертификаты

#### 4.3.9.4.1. Общая информация

- Для TLS сертификат нужен обеим сторонам: на сервере — для аутентификации сервера, на клиенте — для аутентификации клиента. Каждый должен быть удостоверен доверенным центром сертификации.
- Для **производственных** информационных баз сертификаты должны быть выданы доверенными УЦ и соответствовать регламентам национального законодательства / национальных регуляторов.
- Для **тестирования** и для инфраструктуры **во внутренней сети (интранете)** сертификаты доверенного УЦ могут быть избыточны (стоимость, невозможность быстро выпускать произвольное количество и т. п.) — тогда допустимы самоподписанные. Технически они ничем не отличаются от выданных доверенным УЦ.

| Плюсы самоподписанных | Минусы самоподписанных |
|---|---|
| Можно создавать неограниченное количество сертификатов | Стороннее ПО не знает ваш «удостоверяющий центр» |
| Создание бесплатно | Третьи лица не доверяют такому сертификату |
| | Сертификат невозможно отозвать |
| | Повышенный риск потери данных, передаваемых по соединению, защищенному такими сертификатами |

Вывод документации: применять для тестов и внутренних систем предприятия — если перечисленными рисками можно пренебречь.

#### 4.3.9.4.2. Создание сертификатов

##### Общая информация

Создается набор из трех сертификатов:

1. сертификат корневого удостоверяющего центра;
2. сертификат сервера;
3. клиентский сертификат.

Примеры даны для двух инструментов — **OpenSSL** и **Java (keytool)**; результат одинаковый, два варианта приведены для наглядности. Пример строится для домена `server.com`.

Параметры, которые вводятся в консоли при создании сертификатов:

| Поле | Корневой сертификат | Сертификат сервера |
|---|---|---|
| Country Name | `RU` | `RU` |
| State or Province Name | `Moscow` | `Moscow` |
| Locality Name | `Moscow` | `Moscow` |
| Organization Name | `Company` | `Company` |
| Organizational Unit Name | `Department` | `Department` |
| Common Name | `Root CA` | `server.com` |
| Email Address | `admin@company.site` | `admin@company.site` |

Оговорка документации: примеры только демонстрируют механизм, они не законченные и не исчерпывающие; тему и документацию к OpenSSL/Java нужно изучать самостоятельно.

##### Создание сертификата корневого удостоверяющего центра

Этим сертификатом затем заверяется сертификат тестового сервера.

OpenSSL:

```
openssl req -x509 -days 3652 -newkey rsa:2048 -keyout root-ca.key -out root-ca.crt
```

Java:

```
keytool -genkey -alias root-ca -keyalg RSA -keystore root-ca.jks -keysize 2048 -startdate 2023/01/01 -validity 3652
```

Особенности примеров:

- Срок действия — 10 лет (`-days 3652` / `-validity 3652`).
- Начало срока действия: OpenSSL — с момента генерации; Java — с даты из параметра `-startdate`.
- Параметры сертификата (таблица выше) вводятся в консоли в ходе создания.
- Обе утилиты сначала запрашивают пароль, которым шифруется закрытый ключ корневого УЦ.

Для варианта Java файл сертификата нужно дополнительно выгрузить из хранилища JKS:

```
keytool -exportcert -rfc -keystore root-ca.jks -alias root-ca -file root-ca.crt
```

Что получается:

| Инструмент | Файл | Содержимое |
|---|---|---|
| OpenSSL | `root-ca.key` | закрытый ключ корневого сертификата |
| OpenSSL | `root-ca.crt` | корневой сертификат |
| Java | `root-ca.jks` | хранилище сертификатов Java (Java KeyStore) |
| Java | `root-ca.crt` | корневой сертификат |

##### Создание сертификатов сервера

Сертификат сервера выпускается на основе корневого. Шаги для OpenSSL и Java различаются.

**Вариант OpenSSL.** В каталоге с сертификатами создается файл `server.ext`:

```
authorityKeyIdentifier=keyid,issuer
basicConstraints=CA:FALSE
subjectAltName = @alt_names
[alt_names]
DNS.1 = server.com
```

Затем выполняются команды:

```
openssl req -newkey rsa:2048 -keyout server.key -out server.csr
openssl x509 -req -CAkey root-ca.key -CA root-ca.crt -in server.csr -out server.crt -CAcreateserial -days 365 -extfile server.ext
```

- Первая команда создает закрытый ключ сертификата сервера (`server.key`) и файл запроса сертификата (`server.csr`); параметры вводятся в командной строке в ходе формирования ключа.
- Вторая команда выпускает сертификат сервера (`server.crt`), заверенный корневым сертификатом из предыдущего шага.
- Срок действия — 365 дней, отсчет с даты создания.

**Вариант Java:**

```
keytool -genkey -alias server.com -keyalg RSA -keystore server.jks -keysize 2048
keytool -certreq -keystore server.jks -alias server.com -ext san=dns:server.com -file server.csr
keytool -gencert -rfc -infile server.csr -outfile server.crt -keystore root-ca.jks -alias root-ca -ext honored=all -startdate 2023/01/01 -validity 365
```

- Первая команда создает закрытый ключ сертификата сервера и помещает его в хранилище `server.jks`; параметры вводятся в командной строке.
- Вторая команда формирует запрос на сертификат для сервера `server.com`.
- Третья команда выпускает сертификат сервера, заверенный корневым сертификатом.
- Срок действия — 365 дней, отсчет с даты из параметра `-startdate`.

Получение закрытого ключа сервера из хранилища Java (нужен пакет OpenSSL):

```
keytool -importkeystore -srckeystore server.jks -destkeystore server.p12 -deststoretype PKCS12
openssl pkcs12 -in server.p12 -nocerts -nodes -out server.key
```

Итог обоих вариантов: закрытый ключ сервера `server.key` и сертификат тестового сервера `server.crt`.

##### Создание клиентских сертификатов

Делается по аналогии с серверным; шаги для OpenSSL и Java различаются.

**Вариант OpenSSL.** В каталоге с сертификатами создается файл `client.ext`:

```
authorityKeyIdentifier=keyid,issuer
basicConstraints=CA:FALSE
```

Команды:

```
openssl req -newkey rsa:2048 -keyout client.key -out client.csr
openssl x509 -req -CAkey root-ca.key -CA root-ca.crt -in client.csr -out client.crt -CAcreateserial -days 365 -extfile client.ext
```

- Первая команда создает закрытый ключ сертификата клиента (`client.key`) и файл запроса сертификата (`client.csr`); параметры вводятся в командной строке.
- Вторая команда выпускает клиентский сертификат (`client.crt`), заверенный корневым сертификатом.
- Срок действия — 365 дней, отсчет с даты создания.

**Вариант Java:**

```
keytool -genkey -alias client -keyalg RSA -keystore client.jks -keysize 2048
keytool -certreq -keystore client.jks -alias client -file client.csr
keytool -gencert -rfc -infile client.csr -outfile client.crt -keystore root-ca.jks -alias root-ca -ext honored=all -startdate 2023/01/01 -validity 365
```

- Первая команда создает закрытый ключ сертификата клиента и помещает его в хранилище `client.jks`; параметры вводятся в командной строке.
- Вторая команда формирует запрос на сертификат для клиента.
- Третья команда выпускает клиентский сертификат, заверенный корневым сертификатом.
- Срок действия — 365 дней, отсчет с даты из параметра `-startdate`.

**Сводка файлов, появляющихся в примерах:**

| Файл | Назначение | Чем создается |
|---|---|---|
| `root-ca.key` | закрытый ключ корневого УЦ | OpenSSL |
| `root-ca.jks` | файл хранилища сертификатов Java для корневого УЦ | keytool |
| `root-ca.crt` | сертификат корневого УЦ | OpenSSL / keytool (`-exportcert`) |
| `server.ext` | файл расширений сертификата сервера (в т. ч. `subjectAltName`) | вручную, для OpenSSL |
| `server.key` | закрытый ключ сервера | OpenSSL (либо извлекается из `server.jks` через `server.p12`) |
| `server.csr` | запрос на сертификат сервера | OpenSSL / keytool |
| `server.crt` | сертификат сервера | OpenSSL / keytool |
| `server.jks` | хранилище Java с ключом сервера | keytool |
| `server.p12` | промежуточное хранилище PKCS12 для извлечения ключа | keytool (`-importkeystore`) |
| `client.ext` | файл расширений клиентского сертификата | вручную, для OpenSSL |
| `client.key` | закрытый ключ клиента | OpenSSL |
| `client.csr` | запрос на клиентский сертификат | OpenSSL / keytool |
| `client.crt` | клиентский сертификат | OpenSSL / keytool |
| `client.jks` | хранилище Java с ключом клиента | keytool |

#### 4.3.9.4.3. Использование самоподписанных сертификатов

##### Общая информация

Сертификат содержит открытый ключ соответствующего объекта и вспомогательные сведения (срок действия и т. п.). Он предназначен для установки на компьютер пользователя и является публичной информацией.

##### Установка самоподписанных сертификатов на веб-сервер

Выполняется по документации используемого веб-сервера (в документации «1С» шаги не приводятся).

##### Для веб-клиента

На клиентском компьютере нужно дать веб-браузеру понять, что серверный сертификат можно проверять самоподписанным сертификатом УЦ (`root-ca.crt`). Для этого может быть достаточно импортировать `root-ca.crt` в личное хранилище сертификатов компьютера, с которого выполняется доступ.

##### Для тонкого клиента

Если база опубликована на веб-сервере с самоподписанным сертификатом, в настройках подключения тонкого клиента задается:

| Где | Что указать |
|---|---|
| Путь к базе | URL на веб-сервере со схемой HTTPS |
| Дополнительные настройки подключения, группа **Выберите клиентский сертификат** | значение **Файл сертификата**, файл `client.crt`. Для организации защищенного соединения между тонким клиентом и веб-сервером указывать этот сертификат **не требуется** |
| Дополнительные настройки подключения, группа **Выберите способ проверки сертификата сервера** | значение **Файл сертификатов CA**, файл `root-ca.crt` |

##### Для мобильного клиента

Если база опубликована на веб-сервере с самоподписанным сертификатом, настройки делаются в **сборщике мобильных приложений**:

1. Открыть список **Сертификаты для работы по HTTPS** и загрузить в него `client.crt` и `root-ca.crt`; для второго установить флажок **Для проверки сертификата сервера**.
2. При настройке списка приложений в поле **Адрес веб-сервера** указать URL на веб-сервере со схемой HTTPS.
3. В поле **Способ проверки сертификата сервера** выбрать **Указанный сертификат**; в поле **Сертификат сервера** выбрать элемент, соответствующий `root-ca.crt`.
4. В поле **Клиентский сертификат** выбрать сертификат, соответствующий `client.crt`. Для организации защищенного соединения между мобильным клиентом и веб-сервером указывать его **не требуется**.

##### Для системы взаимодействия

Чтобы собственный сервер системы взаимодействия работал по защищенному соединению (протокол **WSS**), сервер взаимодействия настраивается по его документации: `https://its.1c.ru/db/csdoc/bookmark/cs/TI000000020`. В качестве значения `<cs_keystore_path>` задается **полный путь к файлу `server.jks`**.

## 4.4. Перезапуск системы

**Суть.** Бывают ситуации, когда клиентское приложение не может получить доступ к информационной базе. Система сообщает об этом пользователю и предлагает повторить попытку соединения через **60 секунд**.

**Ситуации, в которых это происходит:**

| № | Ситуация |
|---|---|
| 1 | Запускается Конфигуратор, а для этой информационной базы конфигуратор уже запущен |
| 2 | Для информационной базы установлен монопольный режим работы |
| 3 | Версии клиентского приложения и сервера «1С:Предприятия» различаются |
| 4 | Не обнаружен сервер «1С:Предприятия» |
| 5 | Не обнаружен сервер баз данных |
| 6 | Установлен запрет соединения с информационной базой — блокировка начала сеансов, заданная через командную строку запуска клиентского приложения, через консоль кластера или методом встроенного языка `УстановитьБлокировкуСеансов()` |
| 7 | Установлен запрет соединения с информационной базой — сервисом внешнего управления сеансами |

**Диалог ожидания перезапуска** (в документации — рис. 34 «Ожидание перезапуска»): показывается причина (в примере документации — база открыта конфигуратором) и выбор: автоматический перезапуск системы через 1 минуту либо отказ от запуска.

**Простой или форматированный текст причины.** Описание ситуации в диалоге может выводиться обычным текстом или форматированной строкой. Система пытается показать форматированную строку в трех случаях:

| Случай | Условие вывода форматированной строкой |
|---|---|
| Установлен монопольный режим | Текст сообщения при установке монопольного режима задан значением типа `ФорматированнаяСтрока` |
| Блокировка начала сеансов методом `УстановитьБлокировкуСеансов()` | Параметр `БлокировкаСеансов.Сообщение` задан значением типа `ФорматированнаяСтрока` |
| Начало сеанса запрещено сервисом внешнего управления сеансами | Сервис вернул параметр `ErrorDescription`, значение которого получено из значения типа `ФорматированнаяСтрока` выражением `СериализаторXDTO.XMLСтрока()` |

(Подробности про монопольный режим, блокировку начала сеансов и сервис внешнего управления сеансами — в других разделах документации, в источнике ссылки «см. здесь».)

**Критерий «текст — это форматированная строка».** Текст считается форматированной строкой, если истинно выражение:

```
Строка(СериализаторXDTO.XMLЗначение(Тип("ФорматированнаяСтрока"), Текст)) <> Текст
```

где `Текст` — строка, переданная сторонними приложениями (сервис внешнего управления сеансами, консоль кластера, утилита `rac` и т. д.).

**Другие случаи перезапуска:**

- Конфигуратор: после загрузки информационной базы из `.dt`-файла по завершении загрузки предлагается перезапустить конфигуратор.
- Режим 1С:Предприятие: при критической ошибке система предлагает перезапустить клиентское приложение с теми же параметрами, что были у аварийно завершающегося клиентского приложения.

## Что важно администратору Linux

1. **Доверенное хранилище в Linux — каталог `/etc/ssl/certs`.** Все сертификаты, лежащие в нем, считаются доверенными. Для Debian/Mint/Ubuntu дополнительно поддерживается `/etc/ssl/certs/ca-certificates.crt`. «Системное хранилище сертификатов» документация называет источником только для macOS и Windows; для Linux источники — этот каталог и файловые сертификаты.
2. **Формат файлового сертификата определяется по расширению.** `*.p12` / `*.pfx` — PKCS#12, `*.pem` — PEM, всё остальное (в том числе `*.crt` из примеров) трактуется как PEM.
3. **Клиентский сертификат должен идти вместе с закрытым ключом.** Для PEM: если ключ лежит отдельным файлом — его содержимое дописывается в файл клиентского сертификата. Для P12/PFX: файл клиентского сертификата обязан содержать закрытый ключ.
4. **HTTPS шифруется всегда**, независимо от того, проверяются ли сертификаты. Проверка подлинности сторон — отдельный вопрос, определяемый наличием сертификатов и списков корневых УЦ (таблица в 4.3.9.2).
5. **Неподдерживаемая комбинация:** на веб-сервере есть серверный сертификат и список корневых УЦ, а у клиента нет клиентского сертификата (есть у клиента список корневых или нет — неважно). По таблице 4.3.9.2 при списке корневых УЦ на сервере рабочими остаются только варианты, где у клиента клиентский сертификат есть (строки 4 и 5).
6. **Режим «никто никого не проверяет»** (сертификат только на сервере, списков корневых нет ни у кого) — единственный, что был до версии 8.3.3. Сертификат сервера проверяется только в тех вариантах, где у клиента есть список корневых УЦ (строки 2 и 5 таблицы).
7. **Тонкий клиент и самоподписанный сертификат сервера:** путь к базе — URL со схемой HTTPS; в дополнительных настройках подключения способ проверки сертификата сервера — «Файл сертификатов CA» с файлом корневого сертификата (`root-ca.crt`). Клиентский сертификат для самого защищенного соединения не обязателен.
8. **Веб-клиент** опирается на хранилище сертификатов, с которым работает браузер: чтобы браузер проверял серверный сертификат самоподписанным сертификатом УЦ (`root-ca.crt`), может быть достаточно импортировать его в личное хранилище сертификатов клиентского компьютера.
9. **Установка сертификата на веб-сервер** в документации платформы не описана — делается по документации самого веб-сервера. PEM — формат по умолчанию для Apache.
10. **В примерах серверный сертификат выпускается с `subjectAltName`**, содержащим DNS-имя сервера: в варианте OpenSSL оно задается файлом `server.ext` (`DNS.1 = server.com`), в варианте keytool — `-ext san=dns:server.com`. Клиентский сертификат в примерах выпускается без `subjectAltName`.
11. **Сроки из примеров:** корневой сертификат — 3652 дня (10 лет), серверный и клиентский — 365 дней. Самоподписанные сертификаты нельзя отозвать, поэтому документация ограничивает их область тестами и интранетом; для производственных баз — сертификаты доверенного УЦ.
12. **Собственному серверу системы взаимодействия (WSS) указывается хранилище Java**: значение `<cs_keystore_path>` — полный путь к `server.jks` (файл из варианта с `keytool`). Получить из `server.jks` файл `server.key` можно через `keytool -importkeystore ... -deststoretype PKCS12` и `openssl pkcs12 -in server.p12 -nocerts -nodes -out server.key`.
13. **Если пользователи видят диалог «повторить через 60 секунд»** — причина одна из перечисленных в 4.4: запущен конфигуратор, монопольный режим, несовпадение версий клиента и сервера «1С:Предприятия», недоступен сервер «1С:Предприятия» или сервер баз данных, блокировка начала сеансов, запрет от сервиса внешнего управления сеансами.
14. **Текст сообщения блокировки, заданный через консоль кластера или `rac`,** может быть показан пользователю как форматированная строка — если для переданной строки выполняется критерий-выражение из 4.4.
15. **После загрузки `.dt` в конфигураторе** платформа предлагает перезапуск конфигуратора — это штатное поведение.
