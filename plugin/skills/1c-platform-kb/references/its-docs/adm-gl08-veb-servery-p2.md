## 8.7. Публикация HTTP-сервисов (окончание раздела)

⚠ в источнике неясно: заголовки 8.7, 8.7.1, 8.7.2 и 8.7.2.1 остались в части 1. Подраздел 8.7.2 идёт парой к 8.7.3 «Для ОС Windows», а в его примерах используются пути `/var/www/...` и `/etc/apache2/...`, то есть это публикация под Linux.

### Общая схема (одинакова для 8.7.2.2 – 8.7.2.4)

Публикация выполняется одним из двух способов.

**Способ 1 — диалог публикации на веб-сервере (конфигуратор).** В поле «Веб-сервер» выбирается нужная версия Apache; остальные параметры при необходимости задаются на вкладке «Прочие» диалога.

**Способ 2 — утилита `webinst` с файлом-шаблоном.** Сначала в конфигураторе готовится файл-шаблон:

1. В поле «Веб-сервер» указать нужную версию Apache.
2. Установить флаг «Публиковать HTTP-сервисы».
3. Выбрать параметры публикуемых HTTP-сервисов.
4. При необходимости настроить остальное на вкладке «Прочие».
5. Кнопкой «Сохранить» сохранить файл-шаблон (в примерах документации — `apache-template.vrd`).

Затем публикация выполняется командой `webinst` с ключом `-descriptor <файл-шаблон>`.

Сводка по версиям Apache (раздел 8.7.2):

| Раздел | Значение поля «Веб-сервер» | Ключ `webinst` | `-confpath` в примере |
|---|---|---|---|
| 8.7.2.2 | Apache 2.0 | `-apache2` | `/etc/apache2/httd.conf` |
| 8.7.2.3 | Apache 2.2 | `-apache22` | `/etc/apache2/httd.conf` |
| 8.7.2.4 | Apache 2.4 | `-apache24` | в примере не указан |

Ключи `webinst`, встречающиеся в примерах этой части (их полное описание — в разделе об утилите `webinst`, вне этой части):

| Ключ | Значение в примерах |
|---|---|
| `-publish` | режим публикации |
| `-apache2` / `-apache22` / `-apache24` / `-iis` | тип веб-сервера: Apache 2.0 / 2.2 / 2.4 / IIS |
| `-wsdir` | `demo-ws` (в примере для IIS — `demo-hs`) |
| `-dir` | `/var/www/demo-ws` (Linux), `"c:\inetpub\demo-ws"` (Windows) |
| `-connstr` | `"Srvr=server:1741;Ref=demo;"` |
| `-confpath` | `/etc/apache2/httd.conf` (только в Linux-примерах для Apache 2.0 и 2.2) |
| `-descriptor` | файл-шаблон: `apache-template.vrd` / `iis-template.vrd` |

### 8.7.2.2. Apache версии 2.0

#### 8.7.2.2.1. Диалог публикации
В поле «Веб-сервер» — `Apache 2.0`; прочие параметры — вкладка «Прочие».

#### 8.7.2.2.2. Утилита webinst
Шаблон готовится по общей схеме (веб-сервер `Apache 2.0`, имя шаблона `apache-template.vrd`). Пример публикации:

```
webinst -publish -apache2 -wsdir demo-ws -dir /var/www/demo-ws -connstr "Srvr=server:1741;Ref=demo;" -confpath /etc/apache2/httd.conf -descriptor apache-template.vrd
```

⚠ в источнике неясно: имя файла в `-confpath` записано как `httd.conf` (без «p») — так в тексте документации. Раздел 8.10.1.2 называет файлы конфигурации иначе: `httpd.conf` (Apache 2.0) и `apache2.conf` (Apache 2.2 / 2.4).

### 8.7.3. Для ОС Windows

> Только Windows — кратко.

#### 8.7.3.1. Общая информация
Описана публикация HTTP-сервисов на веб-серверах под Windows; предполагается, что веб-сервер уже установлен. Для установки IIS может понадобиться дистрибутив ОС.

#### 8.7.3.2. Internet Information Services

- **8.7.3.2.1. Общее описание.** Помимо параметров публикации нужно выдать права учётной записи, от которой выполняются запросы: `IUSR_<PC_NAME>` для IIS 5.1 / 6.0 или группе `IIS_IUSRS` для IIS 7.x и старше (`<PC_NAME>` — имя компьютера с IIS, например `IUSR_IIS-COMP`):
  - чтение — на каталог `bin` конкретной версии «1С:Предприятия»;
  - изменение — на каталог информационной базы (только файловый вариант).
- **8.7.3.2.2. Диалог публикации.** Поле «Веб-сервер» — `Internet Information Services`; прочее — вкладка «Прочие».
- **8.7.3.2.3. Утилита webinst.** Шаблон готовится по общей схеме, имя в примере — `iis-template.vrd`:

```
webinst -publish -iis -wsdir demo-hs -dir "c:\inetpub\demo-ws" -connstr "Srvr=server:1741;Ref=demo;" -descriptor iis-template.vrd
```

#### 8.7.3.3 – 8.7.3.5. Apache версий 2.0, 2.2, 2.4 под Windows

- **Общее описание (8.7.3.3.1, 8.7.3.4.1, 8.7.3.5.1) — одинаково для всех трёх версий.** Пользователю, от имени которого запущен Apache, нужны права: на каталог `bin` конкретной версии «1С:Предприятия» — чтение и выполнение; на каталог информационной базы — чтение и запись (файловый вариант).
- **Диалог публикации (8.7.3.3.2, 8.7.3.4.2, 8.7.3.5.2).** Поле «Веб-сервер» — `Apache 2.0` / `Apache 2.2` / `Apache 2.4`.
- **Утилита webinst (8.7.3.3.3, 8.7.3.4.3, 8.7.3.5.3).** Шаблон `apache-template.vrd` — по общей схеме. Примеры (без `-confpath`):

```
webinst -publish -apache2 -wsdir demo-ws -dir "c:\inetpub\demo-ws" -connstr "Srvr=server:1741;Ref=demo;" -descriptor apache-template.vrd
webinst -publish -apache22 -wsdir demo-ws -dir "c:\inetpub\demo-ws" -connstr "Srvr=server:1741;Ref=demo;" -descriptor apache-template.vrd
webinst -publish -apache24 -wsdir demo-ws -dir "c:\inetpub\demo-ws" -connstr "Srvr=server:1741;Ref=demo;" -descriptor apache-template.vrd
```

## 8.8. Настройка поддержки OpenID-аутентификации

Роли: **зависимая сторона** (информационная база, пользователи которой аутентифицируются через OpenID) и **OpenID-провайдер** (в примерах документации — другая информационная база «1С:Предприятия»). Обе роли настраиваются в файле `default.vrd`, которым опубликована соответствующая база, либо через закладку «OpenID» диалога публикации на веб-сервере.

| Роль базы | Элементы `default.vrd` | Что задаётся |
|---|---|---|
| Зависимая сторона (использует OpenID) | `<openid>` → `<rely url="...">` | URL OpenID-провайдера |
| OpenID-провайдер | `<openid>` → `<provider>` → `<lifetime>` | признак провайдера и время жизни аутентификационных данных, сек |

### 8.8.1. Настройки для использования OpenID

Если база использует OpenID-аутентификацию, в её `default.vrd` указывается адрес провайдера — элементы `<openid>` и `<rely>` (атрибут `url`). Пример из документации (провайдером служит база «1С:Предприятия», опубликованная по адресу `https://myserver.org/users-ib`):

```xml
<?xml version="1.0" encoding="UTF-8"?>
<point xmlns=http://v8.1c.ru/8.2/virtual-resource-system xmlns:xs=http://www.w3.org/2001/XMLSchema xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance"
  base="/demo"
  ib="Srvr=&quot;tcp://Server&quot;;Ref=&quot;demo&quot;;"
  enable="false">
  <openid>
    <rely url="https://myserver.org/users-ib/e1cib/oid2op"/>
  </openid>
</point>
```

⚠ в источнике неясно: в тексте документации значения первых двух атрибутов `xmlns` и `xmlns:xs` приведены без кавычек (воспроизведено как есть).

То же самое настраивается в диалоге публикации, закладка «OpenID».

### 8.8.2. Настройка информационной базы, выступающей в роли OpenID-провайдера

В `default.vrd` базы-провайдера добавляются элементы `<openid>` и `<provider>`; вложенный `<lifetime>` — время жизни аутентификационных данных в секундах.

```xml
<?xml version="1.0" encoding="UTF-8"?>
<point xmlns=http://v8.1c.ru/8.2/virtual-resource-system xmlns:xs=http://www.w3.org/2001/XMLSchema xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance"
  base="/users-ib"
  ib="Srvr=&quot;tcp://Server&quot;;Ref=&quot;oidusers&quot;;"
  enable="false">
  <openid>
    <provider>
      <lifetime>432000</lifetime>
    </provider>
  </openid>
</point>
```

Что означает пример:

- база работает как OpenID-провайдер;
- время жизни аутентификационных данных — 432 000 секунд (5 суток);
- адрес провайдера для элемента `<rely>` зависимых баз при имени хоста `myserver.org` будет `https://myserver.org/users-ib/e1cib/oid2op`, то есть `<адрес публикации>/e1cib/oid2op`.

Особенность: для базы-провайдера флажок «Публиковать доступ для клиентских приложений» (атрибут `enable` элемента `point`) **не влияет** на возможность интерактивного входа. Причина — протокол OpenID требует интерактивной аутентификации в самом провайдере, а при отключённом доступе клиентских приложений она была бы невозможна (в примерах стоит `enable="false"`).

Настройка также доступна на закладке «OpenID» диалога публикации.

### 8.8.3. Дополнительный интерфейс для использования внешними ресурсами

К провайдеру, реализованному «1С:Предприятием», можно обращаться по стандартному протоколу OpenID 2.0 с оговорками:

- В запросах интерактивной и неинтерактивной аутентификации (`openid.mode` = `checkid_immediate` или `checkid_setup`) параметры `openid.claimed_id` и `openid.identity` должны иметь значение `https://specs.openid.net/auth/2.0/identifier_select` — идентификатор пользователя определяет провайдер.
- Неинтерактивный запрос с любыми другими значениями `openid.claimed_id` и `openid.identity` приводит к запросу интерактивной аутентификации, в ходе которой эти значения определяет провайдер.
- В провайдере есть собственная форма ввода имени пользователя и пароля для интерактивной аутентификации.

Сверх стандарта доступны вспомогательные команды для сторонних систем. Сокращения документации: `ProviderIB` — информационная база OpenID-провайдера; `RPID` — информационная база зависимой стороны (⚠ в источнике неясно: в URL-примерах она записана как `RPIB`). Параметры запросов передаются в UTF-8.

#### Сводка команд

| Команда | URL | Параметры |
|---|---|---|
| XRDS-документ провайдера | `https://example.com/ProviderIB/e1cib/oid2op` | — |
| XRDS-документ зависимой стороны | `https://example.com/RPIB/e1cib/oid2rp` | — |
| Настройки окна аутентификации | `https://example.com/ProviderIB/e1cib/oid2op?cmd=additionalAuthSettings` | `version` |
| Запрос аутентификации | `https://example.com/ProviderIB/e1cib/oid2op?cmd=auth` | `openid.auth.user`, `openid.auth.pwd`, `openid.auth.Data2FA`, `opeind.auth.short`, `openid.auth.check`, `openid.return_to` |
| Проверка аутентификации (второй фактор) | `https://example.com/ProviderIB/e1cib/oid2op/2FACheck?user=xxx` | `user` |
| Проверка активной аутентификации | `https://example.com/ProviderIB/e1cib/oid2op?cmd=lookup` | `openid.return_to`, `openid.auth.check` |
| Проверка ответа провайдера | `https://example.com/ProviderIB/e1cib/oid2op?cmd=check` | `openid.auth.user`, `openid.auth.uid` |
| Отмена аутентификации для зависимой стороны | `https://example.com/RPIB/e1cib/oid2op?cmd=logout` | — |
| Отмена аутентификации для провайдера | `https://example.com/ProviderIB/e1cib/oid2op?cmd=logout` | `openid.return_to` |

#### Запрос XRDS-документа провайдера OpenID

- URL: `https://example.com/ProviderIB/e1cib/oid2op`
- Возвращает XRDS-документ со свойствами OpenID-провайдера.

#### Запрос XRDS-документа зависимой стороны OpenID

- URL: `https://example.com/RPIB/e1cib/oid2rp`
- Возвращает XRDS-документ со свойствами зависимой стороны.

#### Запрос данных для настройки окна аутентификации

- URL: `https://example.com/ProviderIB/e1cib/oid2op?cmd=additionalAuthSettings`
- Параметр `version` (обязательный) — номер версии протокола, поддерживаемой клиентским приложением; допустимо только значение `1`.
- Заголовок ответа `1C-AuthSettingsProtoVersion` — число, номер используемой версии протокола. Клиент и сервер перед получением параметров диалога согласуют версию, поддерживаемую обеими сторонами. Клиентское приложение версии 8.3.26 умеет работать и по протоколу версии 1 (он и описан в этом разделе), и по протоколу, применявшемуся в 8.3.25 и ранее. При смене версии протокола новая начинает поддерживаться с определённой версии системы, старые остаются для совместимости.
- Тело ответа — JSON с настройками диалога аутентификации.

Ключи JSON-ответа:

| Ключ | Тип | Обязательность | Назначение |
|---|---|---|---|
| `allowSaveForReauthentication` | Булево | обязательное | Показывать ли флажок сохранения пароля на форме аутентификации: Истина — показывать, Ложь — нет |
| `helpURL` | Строка | необязательное | URL страницы помощи; если поля нет или строка пустая — иконка помощи не показывается |
| `lcinfo` | JSON-объект | необязательное | Настройки окна аутентификации (структура ниже) |
| `passwordRecoveryMehod` | Число | обязательное | Способ восстановления забытого пароля: `0` — через специальную форму; `1` — формой отправки письма (стандартный сервис); `2` — формой отправки письма (пользовательские настройки почтового сервера); `3` — восстановление отключено |
| `passwordRecoveryURL` | Строка | необязательное | URL страницы восстановления пароля; если восстановление отключено или строка пустая — ссылка не показывается |
| `savedAuthenticationParametersLifeTime` | Число | обязательное | Время жизни сохранённого входа, сек |
| `saveForReauthenticationByDefault` | Булево | обязательное | Значение по умолчанию для флажка сохранения пароля (если флажок отображается) |

⚠ Имя ключа `passwordRecoveryMehod` (без буквы «t») — так в источнике.

Структура объекта `lcinfo`:

| Ключ | Тип | Обязательность | Назначение |
|---|---|---|---|
| `auth` | JSON-объект | необязательное | Настройки сохранения пароля окна аутентификации для данной публикации; переопределяют настройки, заданные для информационной базы |
| `authTypes` | JSON-массив | необязательное | Разрешённые типы аутентификации (перечень типов — в другом разделе документации) |

Структура объекта `auth` (все ключи необязательные):

| Ключ | Тип | Назначение |
|---|---|---|
| `allowSaveForReauthentication` | Булево | Показывать ли флажок сохранения пароля: Истина — да, Ложь — нет |
| `savedAuthenticationParametersLifeTime` | Число | Время жизни сохранённого входа, сек |
| `saveForReauthenticationByDefault` | Булево | Значение по умолчанию для флажка сохранения пароля (если он отображается) |

#### Запрос аутентификации

- URL: `https://example.com/ProviderIB/e1cib/oid2op?cmd=auth`

Параметры:

| Параметр | Обязательность | Назначение |
|---|---|---|
| `openid.auth.user` | обязательный | Имя пользователя в том виде, в каком оно задано в базе провайдера |
| `openid.auth.pwd` | обязательный | Пароль пользователя |
| `openid.auth.Data2FA` | необязательный | Данные второго фактора; зависят от типа поставщика дополнительной аутентификации. Состав: тип проверки второго фактора, идентификатор сессии и необязательный секретный код, разделённые символом `:` |
| `opeind.auth.short` | необязательный | При значении `true` аутентификация действует в пределах сессии веб-браузера, но не дольше значения `lifetime` из `default.vrd` публикации базы-провайдера. ⚠ Написание `opeind` — так в источнике |
| `openid.auth.check` | необязательный | `true` — требуется проверка ответа на этот запрос; имеет смысл только вместе с `openid.return_to` |
| `openid.return_to` | необязательный | URL, на который выполняется переход после обработки запроса |

Результат **без** `openid.return_to` — пустой документ с кодом HTTP:

| Код | Смысл |
|---|---|
| `200` | аутентификация успешна |
| `400` | аутентификация не выполнена |
| `402` | логин и пароль приняты, требуется второй фактор; в ответе есть заголовок `Status2FA` |

Значения заголовка `Status2FA` (ответ `402`):

| Код | Смысл |
|---|---|
| 1 | второй фактор проверяет простой поставщик дополнительной проверки, секретным кодом (тип проверки второго фактора) |
| 2 | код введён неверно |
| 3 | второй фактор проверяет внешний поставщик дополнительной проверки (тип проверки второго фактора) |
| 4 | не используется |
| 5 | не найден сеанс дополнительной проверки доступа |
| 6 | не найден сеанс дополнительной проверки доступа для простого поставщика |
| 7 | не найден сеанс дополнительной проверки доступа для внешнего поставщика |
| 8 | истекло время действия дополнительной проверки доступа |
| 9 | истекло время действия кода дополнительной проверки доступа |
| 10 | истекло время действия проверки доступа внешнего провайдера |
| 11 | ошибка отправки запроса поставщику дополнительной проверки доступа |
| 12 | ошибка отправки запроса на проверку прохождения второго фактора внешнему поставщику |
| 13 | внешний поставщик дополнительной проверки доступа ответил ошибкой |
| 14 | шаблон настройки дополнительной проверки доступа не найден в информационной базе |
| 15 | неподдерживаемый тип шаблона настройки дополнительной проверки доступа |
| 16 | ни один из настроенных шаблонов дополнительной проверки доступа не прошёл проверку |
| 17 | не используется |
| 18 | не соблюдён протокол OpenID для второго фактора аутентификации |
| 19 | простой поставщик дополнительной проверки доступа вернул ошибку |
| 20 | недействительный адрес запроса (URL) дополнительной проверки доступа |
| 21 | недействительный адрес запроса (URL) на проверку прохождения второго фактора внешнему поставщику |

Сопутствующие заголовки:

- `Descr2FA` — текстовое описание ошибки; передаётся для всех кодов-ошибок (все, кроме 1 и 3).
- `opsid` — идентификатор сессии (GUID); возвращается для кодов 1 и 3.

Порядок прохождения второго фактора:

- Ответ `402` с `Status2FA` = 1 или 3 означает, что имя и пароль проверены и нужно пройти второй фактор: кодом (1) или проверкой у внешнего поставщика (3).
- К телу предыдущего запроса добавляется параметр `openid.auth.Data2FA` = `<тип из Status2FA>:<opsid>:<секретный код>`:
  - проверка кодом: `1:<opsid>:Секретный_код`;
  - проверка у внешнего поставщика: `3:<opsid>:` — код не добавляется, сервер сам отправит запрос на проверку и проверит второй фактор.
- К моменту получения такого ответа запрос на выполнение второго фактора уже отправлен OpenID-провайдером поставщику второго фактора.
- Провайдер, обнаружив необходимость второго фактора, проверяет логин и пароль, но пользовательский сеанс не создаёт. Сеанс создаётся при следующем обращении, когда заново проверяются логин, пароль и второй фактор.

Пример: провайдер вернул заголовки `Status2FA: 1` и `opsid: 5d75e5a2-9cbc-48d5-9b40-c922e3404a1f`. Следующий запрос должен содержать (в источнике это названо «заголовком», хотя выше говорится о теле запроса — ⚠ в источнике неясно):

```
openid.auth.Data2FA=1:5d75e5a2-9cbc-48d5-9b40-c922e3404a1f:123456&openid.auth.user=myuser&openid.auth.pwd=mypassword
```

Результат **с** `openid.return_to` — переадресация на указанный адрес:

- при успехе к URL добавляются `openid.auth.user` (имя пользователя) и `openid.auth.uid` (одноразовый идентификатор для проверки ответа; добавляется, только если в запросе был `openid.auth.check`);
- при неудаче — переход по URL без дополнительных параметров.

#### Запрос OpenID-провайдера на проверку аутентификации

- URL: `https://example.com/ProviderIB/e1cib/oid2op/2FACheck?user=xxx`
- Параметр `user` (обязательный) — имя пользователя, аутентификацию которого нужно проверить.
- Возвращает пустой документ с кодом HTTP:
  - `200` — пользователь аутентифицирован с помощью второго фактора;
  - `400` — аутентификация не выполнена: не указан `user`; перед этим запросом не было обычного запроса на аутентификацию; аутентификация не выполнена; время аутентификации истекло.

#### Запрос OpenID-провайдера для проверки активной аутентификации

- URL: `https://example.com/ProviderIB/e1cib/oid2op?cmd=lookup`
- Параметры: `openid.return_to` (обязательный) — URL перехода после обработки; `openid.auth.check` (необязательный) — `true`, если ответ нужно будет проверить.
- Всегда выполняется переадресация на `openid.return_to`. При успешной аутентификации к URL добавляются `openid.auth.user` и (если был `openid.auth.check`) `openid.auth.uid`; при неудаче параметры не добавляются.

#### Выполнить проверку ответа OpenID-провайдера

- URL: `https://example.com/ProviderIB/e1cib/oid2op?cmd=check`
- Назначение: проверка ответа провайдера на запросы `cmd=auth` и `cmd=lookup`, если в них передавался `openid.auth.check` со значением `true`.
- Параметры (оба обязательные): `openid.auth.user` — имя пользователя, полученное из одноимённого параметра запроса; `openid.auth.uid` — одноразовый идентификатор ответа провайдера, полученный из одноимённого параметра запроса (то есть значения, которые провайдер добавил к URL `openid.return_to`).
- Возвращает документ `text/plain`:
  - `is_valid:true` — ответ действительно сформирован этим провайдером, код HTTP `200`;
  - `is_valid:false` — провайдер такой ответ не формировал, код HTTP `400`.

#### Запрос отмены аутентификации для зависимой стороны

- URL: `https://example.com/RPIB/e1cib/oid2op?cmd=logout`
- Используется, когда URL провайдера неизвестен. Завершает текущий сеанс, отменяет аутентификацию на провайдере и перезапускает веб-клиент; веб-клиент сам выполнит запрос отмены аутентификации к провайдеру.

#### Запрос отмены аутентификации для OpenID-провайдера

- URL: `https://example.com/ProviderIB/e1cib/oid2op?cmd=logout`
- Параметр `openid.return_to` (необязательный) — URL перехода после обработки.
- Если `openid.return_to` указан — переадресация на него, иначе пустой ответ с кодом HTTP `200`.

### 8.8.4. Требования к внешним OpenID-провайдерам

Обязательные требования к стороннему (не «1С») провайдеру, через который должны аутентифицироваться пользователи информационных баз:

- Поддержка спецификации OpenID Authentication 2.0 и расширения этого протокола, реализованного в платформе «1С:Предприятие».
- Для работы с тонким клиентом провайдер должен использовать cookie с именем `vrs_oid2op_auth`.
- Если пришёл запрос с HTTP-заголовком `Accept`, запрещающим HTML в ответе, провайдер не должен применять перенаправление через HTML-формы (раздел 5.2.2 спецификации OpenID Authentication 2.0).
- Возвращаемые базам «1С:Предприятия» параметры `openid.claimed_id` и `openid.identity` должны иметь формат `<адрес OpenID-провайдера>?lid=<логин-пользователя>`, например `https://myserver.org/users-ib/e1cib/oid2op?lid=user1`.

Полезные особенности поведения самой платформы:

- Обращаясь к провайдеру, база «1С:Предприятия» всегда передаёт в `openid.claimed_id` и `openid.identity` значение `https://specs.openid.net/auth/2.0/identifier_select`.
- База не использует общий секретный ключ (алгоритм Диффи — Хеллмана) для проверки подлинности сообщений провайдера. Подлинность проверяется прямым запросом к провайдеру (раздел 11.4.2 спецификации OpenID Authentication 2.0).

Ссылки из документации:

- OpenID Authentication 2.0: `https://openid.net/specs/openid-authentication-2_0.html`
- раздел 5.2.2: `https://openid.net/specs/openid-authentication-2_0.html#indirect_comm`
- раздел 11.4.2: в источнике дана та же ссылка `...#indirect_comm` (⚠ в источнике неясно — совпадает со ссылкой на 5.2.2)
- «Дополнительные требования к OpenID-провайдеру» — отдельный раздел документации (вне этой части).

## 8.9. Безопасность при работе через Интернет

### 8.9.1. Аутентификация

Общая схема обращения клиента к интернет-сервису показана в документации на рис. 88 «Соединения интернет-сервиса» (в текстовой копии рисунка нет). Различаются три вида аутентификации.

**1. На прокси-сервере.** К веб-серверу прямого отношения не имеет, но её надо учитывать, если интернет-сервис используется из сети, находящейся за прокси.

**2. На веб-сервере** — три варианта:

| Вид | Как работает | Что получает «1С:Предприятие» |
|---|---|---|
| Анонимная | Все запросы, приходящие от веб-сервера, выполняются под специальным пользователем «анонимного» соединения | Аутентификация в «1С» — по имени и паролю из HTTP-запроса |
| Basic | Клиент передаёт веб-серверу имя и пароль в HTTP-запросе | Те же имя и пароль должны подходить и для веб-сервера, и для «1С:Предприятия». Если пользователь из HTTP-запроса не имеет доступа к веб-серверу, интернет-сервисом он пользоваться не сможет |
| Аутентификация ОС | Веб-сервер определяет пользователя ОС, обращающегося к нему, и передаёт «1С» и характеристики пользователя ОС, и данные из HTTP-запроса | Если в HTTP-запросе есть имя и пароль — используются они, данные пользователя ОС игнорируются; если нет — используются данные пользователя ОС |

Про аутентификацию ОС для тонкого клиента (при подключении по HTTP через веб-сервер) и веб-клиента: она опирается на имперсонализацию пользователя веб-браузера или тонкого клиента в потоке веб-сервера, исполняющем HTTP-запросы. Возможность имперсонализации зависит от типа и настроек браузера, типа и настроек веб-сервера, прав отдельных пользователей, политик безопасности домена и т. д.; она возможна не всегда. Эти настройки — задача администрирования сетевого окружения и в документации по «1С:Предприятию» не описываются.

**3. Аутентификация «1С:Предприятия».**

- Расширение веб-сервера использует имя и пароль, переданные веб-сервером (при Basic-аутентификации или аутентификации ОС на веб-сервере).
- Если на веб-сервере включена анонимная аутентификация, «1С:Предприятие» само запросит у вызывающей стороны Basic-аутентификацию.
- Логин и пароль ожидаются в кодировке UTF-8.
- При обращении к интернет-сервису из Microsoft Internet Explorer не рекомендуется использовать нелатинские символы в имени пользователя и пароле.

Дополнительно:

- Взаимодействие с веб-сервером можно вести по защищённому каналу (см. 8.9.2).
- Для файлового варианта информационной базы пользователи, от имени которых идёт доступ к системе, должны иметь право на исполнение файлов нужной версии «1С:Предприятия» и права на чтение и изменение данных в каталоге информационной базы.

### 8.9.2. Работа по защищенному каналу

Обмен между клиентом и сервером интернет-сервисов может идти по защищённому каналу — он предотвращает несанкционированный просмотр и изменение данных.

Поддерживаемые протоколы и алгоритмы:

| Параметр | Значение |
|---|---|
| Протокол защищённого канала | TLS |
| Поддерживаемые версии TLS | 1.0 – 1.3 |
| SSL 3.0 | не поддерживается (устаревший) |
| Криптоалгоритмы ГОСТ при установке TLS-соединения | ГОСТ Р 34.10-94, Р 34.10-2001, Р 34.10-2012, Р 34.11-94, Р 34.11-2012, 28147-89 |
| Клиентские сертификаты при TLS 1.3 | поддерживаются только использующие перечисленные алгоритмы ГОСТ |
| Серверные сертификаты | могут использовать любые криптографические алгоритмы |
| URL-схема и порт по умолчанию для HTTP поверх TLS | `HTTPS`, порт `443` |

Кратко о TLS (как это изложено в документации):

- TLS (Transport Layer Security) обеспечивает защищённое взаимодействие клиента и сервера и опирается на взаимную аутентификацию сторон, цифровые подписи (целостность данных) и шифрование (конфиденциальность). Протокол допускает разные варианты шифров, подписей и сертификатов — под требуемую стойкость канала.
- Защищённое соединение устанавливается через TLS-сессию — обмен последовательностью сообщений, в ходе которого могут выполняться: выбор алгоритмов шифрования и цифровой подписи, установка сессионного ключа, аутентификация сервера на клиенте, аутентификация клиента на сервере.
- Для аутентификации используются сертификаты — документы с набором параметров субъекта (например, имя пользователя или имя веб-сайта сервера) и цифровой подписью для проверки действительности.
- Сертификаты образуют цепочки: Центр Сертификации выдаёт сертификат, подписанный своим закрытым ключом; получатель сам может выступать Центром Сертификации для других. Корень цепочки — корневой Центр Сертификации, обычно общеизвестная организация.
- Клиент принимает сертификат, только если в его списке доверенных есть сам сертификат либо любой сертификат из его цепочки (как правило — корневого Центра Сертификации).

Ограничение платформы по сертификатам: «1С:Предприятие» корректно работает только с сертификатами, поля которых содержат данные в US ASCII либо символы, закодированные Punycode. Данных в Unicode в полях сертификата быть не должно.

Поведение клиентской части механизма Web-сервисов:

- По URL-схеме (`HTTPS`) расположения Web-сервиса она автоматически определяет, что обмен должен идти по защищённому каналу.
- Требует, чтобы с сервером был связан действительный сертификат, выданный известным клиенту Центром Сертификации.
- Сертификат сервера действителен, если: цифровая подпись соответствует содержимому, срок действия не истёк, веб-сайт в сертификате совпадает с веб-сайтом сервера. Если сертификат недействителен (например, не совпал веб-сайт), клиент не сможет работать по TLS с Web-сервисами этого сайта.

Что нужно для включения TLS:

1. Получить серверный сертификат для веб-сайта, где планируется TLS (выдаётся Центром Сертификации и привязывается к этому сайту).
2. Включить поддержку TLS на веб-сервере.
3. В приложении, использующем Web-сервис, явно указать защищённое соединение: при создании объектов `WSОпределения` и `WSПрокси` задать параметр `ЗащищенноеСоединение`, передав в него объект `ЗащищенноеСоединениеOpenSSL`.

## 8.10. Особенности настройки веб-серверов

### 8.10.1. Apache

#### 8.10.1.1. Общие особенности

**Linux, Apache 2.2 и выше:**

- Рекомендуемый модуль мультипроцессной обработки (MPM) — `worker`. Описание модуля: `https://httpd.apache.org/docs/2.2/mod/worker.html` или `https://httpd.apache.org/docs/2.4/mod/worker.html` (на английском).
- Если публикация обслуживает **файловый** вариант информационной базы — не рекомендуется разрешать веб-серверу создавать несколько рабочих процессов для одной публикации.
- Если в файловой базе используются **фоновые задания** — число рабочих процессов в используемом пуле должно быть равно 1, иначе механизм работает некорректно.
- Количество рабочих процессов задаётся параметром `ServerLimit 1` в разделе настроек модуля worker (`<IfModule worker.c> </IfModule>`) конфигурационного файла веб-сервера.
- Если используется другой MPM — настройку числа рабочих процессов нужно искать в документации к этому модулю.

В документации это дано описанием, без готового примера; фрагмент, собранный по этому описанию (имя раздела и значение параметра — из документации):

```apache
<IfModule worker.c>
ServerLimit 1
</IfModule>
```

**Только Windows, Apache 2.2, файловый вариант базы:** рекомендуется добавить в `httpd.conf` фрагмент ниже; при проблемах с исчерпанием стека на стороне веб-сервера значение `ThreadStackSize` рекомендуется увеличить. Описание параметра: `https://httpd.apache.org/docs/2.2/mod/mpm_common.html#ThreadStackSize` (на английском).

```apache
<IfModule mpm_winnt_module>
ThreadStackSize 8388608
</IfModule>
```

#### 8.10.1.2. Алгоритм поиска установленного веб-сервера

Как платформа определяет, что веб-сервер Apache нужной версии установлен, и где ищет его конфигурационный файл.

**Linux:**

| Раздел | Версия Apache | Искомый файл конфигурации | Каталог поиска |
|---|---|---|---|
| 8.10.1.2.1 | 2.0 | `httpd.conf` | `/etc/httpd/conf/` |
| 8.10.1.2.2 | 2.2 | `apache2.conf` | `/etc/apache2/` |
| 8.10.1.2.3 | 2.4 | `apache2.conf` | `/etc/apache2/` |

**Windows (только Windows)** — для каждой версии последовательно применяются три способа; сервер считается обнаруженным, если по вычисленному пути существует файл:

1. **Обнаружение сервиса.** Читается параметр реестра `HKEY_LOCAL_MACHINE\SYSTEM\CurrentControlSet\Services\<Служба>\ImagePath`; в значении фрагмент `Apache2.exe` заменяется на `conf\httpd.conf`.
2. **Каталог установки в реестре.** Открывается раздел `HKEY_LOCAL_MACHINE\Software\Apache Software Foundation\Apache\<Версия>`, при неудаче — `HKEY_CURRENT_USER\Software\Apache Software Foundation\Apache\<Версия>`; из него читается параметр `ServerRoot`, к значению добавляется `conf\httpd.conf`.
3. **Каталог установки по умолчанию.** Ищется `httpd.conf` в стандартном каталоге.

| Раздел | Версия | `<Служба>` | `<Версия>` в реестре | Каталог по умолчанию |
|---|---|---|---|---|
| 8.10.1.2.1 | 2.0 | `Apache2` | `2.0` | `C:\Program Files\Apache Software Foundation\Apache2\conf` |
| 8.10.1.2.2 | 2.2 | `Apache2.2` | `2.2` | `C:\Program Files\Apache Software Foundation\Apache2.2\conf` |
| 8.10.1.2.3 | 2.4 | `Apache2.4` | `2.4` | `C:\Program Files\Apache Software Foundation\Apache2.4\conf` |

#### 8.10.1.3. Встраивание веб-клиента

Если веб-клиент нужно встроить в сторонний сайт, рекомендуется настроить заголовок ответа `X-Frame-Options` в разделе нужной публикации конфигурационного файла веб-сервера (`httpd.conf`).

| Ситуация | Значение `X-Frame-Options` |
|---|---|
| Внешний сайт и веб-клиент опубликованы на одном веб-сервере | `sameorigin` |
| Внешний сайт и веб-клиент на разных веб-серверах | `allow-from %ВебСайт%`, где `%ВебСайт%` — URL внешнего сайта (протокол, домен и порт) |
| Встраивание веб-клиента во внешний сайт должно быть запрещено | `deny` |

Строки конфигурации:

```apache
# один веб-сервер
LoadModule headers_module modules/mod_headers.so
Header set X-Frame-Options "sameorigin"

# разные веб-серверы
LoadModule headers_module modules/mod_headers.so
Header set X-Frame-Options "allow-from %ВебСайт%"

# запрет встраивания
LoadModule headers_module modules/mod_headers.so
Header set X-Frame-Options "deny"
```

Если тонкая настройка не нужна — достаточно убедиться, что в конфигурационном файле **нет** пары строк варианта «запрет встраивания» (`LoadModule headers_module modules/mod_headers.so` и `Header set X-Frame-Options "deny"`).

См. также в документации: «Встраивание веб-клиента во внешний веб-сайт» (вне этой части).

### 8.10.2. Internet Information Services

> Только Windows — кратко, но с сохранением имён параметров.

#### 8.10.2.1. 32-разрядный вариант расширения веб-сервера в 64-разрядном варианте IIS
При 32-разрядном расширении веб-сервера на 64-разрядной ОС нужно разрешить IIS выполнять 32-разрядные приложения:

- IIS 5.1, IIS 6.0 — команда:

```
cscript %SYSTEMDRIVE%\inetpub\adminscripts\adsutil.vbs SET W3SVC/AppPools/Enable32bitAppOnWin64 1
```

- IIS 7.0 и старше — Диспетчер служб IIS → сервер → Пулы приложений → нужный пул → Дополнительные параметры → «Разрешены 32-разрядные приложения» = Истина (True).

#### 8.10.2.2. Настройки пула приложений
- В одном пуле приложений не может исполняться более одного модуля расширения веб-сервера, если модули различаются только третьей и четвёртой цифрами версии. Нужно столько пулов, сколько разных версий модулей расширения используется; каждое виртуальное приложение веб-клиента привязывается к своему пулу вручную.
- Для файлового варианта базы не рекомендуется несколько рабочих процессов в одном пуле; при использовании фоновых заданий в файловой базе число рабочих процессов должно быть равно 1. Параметр: Пулы приложений → нужный пул → Дополнительные параметры → «Максимальное число рабочих процессов» (группа «Модель процесса»).

#### 8.10.2.3. Настройка представления ошибок
Если ошибки «1С:Предприятия» в IIS 7.x и старше показываются как «500 — внутренняя ошибка сервера…», нужно: Диспетчер служб IIS → сервер → сайты → Default Web Site → виртуальное приложение → Страницы ошибок → «Изменить параметры…» → «Если сервер обнаружил ошибку, возвратить» = «Подробные сообщения об ошибках».

#### 8.10.2.4. Настройка допустимой длины URL
URL стандартного интерфейса OData может быть очень длинным, а IIS по умолчанию ограничивает URL 260 символами. Решение: в разделе реестра `HKEY_LOCAL_MACHINE\SYSTEM\CurrentControlSet\Services\HTTP\Parameters` создать (с правами администратора) параметр `UrlSegmentMaxLength` типа DWORD со значением больше максимальной длины используемых запросов либо `0` (длина не ограничена); затем перезагрузить компьютер с IIS.

> Примечание составителя (19.10.2026): по документации Microsoft (Http.sys registry settings) `UrlSegmentMaxLength` = 260 ограничивает длину **одного сегмента** пути URL, а не всего URL. Длину всего адреса ограничивают `requestFiltering`/`requestLimits` `maxUrl` (по умолчанию 4096) и `maxQueryString`, а также `MaxFieldLength` в Http.sys. Для длинных запросов OData проверять все три. Подробно — `kb/1c-windows/03-veb-publikaciya-iis.md`, разд. 8.

#### 8.10.2.5. Настройка HTTPS-соединения
При ошибках загрузки больших объёмов данных по HTTPS через IIS рекомендуется попробовать TLS 1.2 или TLS 1.1. Для IIS 7.5 и старше (Windows 7 и последующие) их можно включить: в разделах `HKEY_LOCAL_MACHINE\SYSTEM\CurrentControlSet\Control\SecurityProviders\SCHANNEL\Protocols\TLS 1.1\Server` и `...\Protocols\TLS 1.2\Server` создать параметр `DisableByDefault` типа DWORD = `0` (от имени администратора), затем перезагрузить компьютер с IIS.

> Примечание составителя (19.10.2026): у Microsoft параметр SCHANNEL называется **`DisabledByDefault`** (документация Microsoft «TLS registry settings»). В написании ИТС он, по-видимому, не действует. Рецепт написан для Windows 7 / Server 2008 R2; в Windows Server 2016+ TLS 1.2 включён по умолчанию. Разбор — `kb/1c-windows/03-veb-publikaciya-iis.md`, разд. 9.

#### 8.10.2.6. Обновление клиентского приложения
Для обновления клиентского приложения расширению `.zip` должен соответствовать MIME-тип `application/x-zip-compressed` (настройка IIS по умолчанию) или `application/zip` (рекомендация IANA). Проверка и настройка — «Типы MIME» в группе IIS: на уровне всего веб-сервера, сайта или страницы сайта; если записи для `.zip` нет — её нужно создать.

#### 8.10.2.7. Встраивание веб-клиента
Те же значения заголовка ответа `X-Frame-Options` для приложения веб-клиента, что и для Apache: `sameorigin` (один веб-сервер), `allow-from %ВебСайт%` (разные веб-серверы; `%ВебСайт%` — протокол, домен и порт внешнего сайта), `deny` (запрет). Без тонкой настройки достаточно убедиться, что в настройках приложения веб-клиента нет заголовка `X-Frame-Options` со значением `deny`.

### 8.10.3. Reverse Proxy

Reverse proxy (обратный прокси-сервер) ретранслирует запросы клиентов из внешней сети на один или несколько серверов внутренней сети; применяется для балансировки нагрузки и повышения безопасности.

Проблема: если к веб-серверам с опубликованными информационными базами обращаются через reverse proxy, то запрос на веб-сервер «1С:Предприятия» приходит не от внешнего клиентского приложения, а от компьютера с reverse proxy. При ненадлежащей настройке прокси из-за этого могут перестать работать некоторые механизмы. «Внешнее» клиентское приложение здесь — то, которое подключается к reverse proxy, а тот уже переадресует запрос веб-серверу с публикацией.

Чтобы платформа корректно определяла исходный HTTP-запрос и параметры клиентского приложения, reverse proxy должен при переадресации формировать заголовки запроса:

| Заголовок | Для чего нужен |
|---|---|
| `X-Forwarded-Port` | «восстановление» исходного HTTP-запроса |
| `X-Forwarded-Host` | «восстановление» исходного HTTP-запроса |
| `X-Forwarded-Proto` | «восстановление» исходного HTTP-запроса |
| `X-Forwarded-For` | корректное определение IP-адреса внешнего клиентского приложения |

Конкретная настройка обратного прокси в документации «1С» не описана — её нужно искать в документации веб-сервера, используемого в этой роли.

## Что важно администратору Linux

1. **Публикация HTTP-сервисов на Apache под Linux** делается либо из диалога публикации конфигуратора, либо утилитой `webinst` с заранее сохранённым из конфигуратора файлом-шаблоном `.vrd` (ключ `-descriptor`). В шаблоне обязательно должен быть установлен флаг «Публиковать HTTP-сервисы» и выбраны публикуемые сервисы.
2. **Ключ версии Apache в `webinst`:** `-apache2` (2.0), `-apache22` (2.2), `-apache24` (2.4). Пример для 2.4: `webinst -publish -apache24 -wsdir demo-ws -dir /var/www/demo-ws -connstr "Srvr=server:1741;Ref=demo;" -descriptor apache-template.vrd`.
3. **Где платформа ищет конфигурацию Apache на Linux:** для 2.2 и 2.4 — файл `apache2.conf` в `/etc/apache2/`; для 2.0 — `httpd.conf` в `/etc/httpd/conf/`. В примерах для 2.0 и 2.2 путь передаётся явно ключом `-confpath`, в примере для 2.4 этого ключа нет.
4. **Опечатки в самой документации**, которые нельзя переносить в рабочие команды без проверки: `-confpath /etc/apache2/httd.conf` (имя файла), параметр `opeind.auth.short`, ключ JSON `passwordRecoveryMehod`, отсутствие кавычек у `xmlns` и `xmlns:xs` в примерах `default.vrd`, обозначение `RPID` / `RPIB` для базы зависимой стороны.
5. **MPM для Apache 2.2+ на Linux:** рекомендован `worker`. Для файловой базы не допускать нескольких рабочих процессов на одну публикацию; если в файловой базе есть фоновые задания — строго один процесс: `ServerLimit 1` в `<IfModule worker.c>`. При другом MPM — искать аналогичную настройку в его документации.
6. **Reverse proxy** перед веб-сервером с публикациями обязан передавать `X-Forwarded-Port`, `X-Forwarded-Host`, `X-Forwarded-Proto` (восстановление исходного запроса) и `X-Forwarded-For` (IP клиента). Без них часть механизмов платформы может не работать. Как именно это настроить — документация «1С» не описывает.
7. **TLS:** поддерживаются версии 1.0 – 1.3, SSL 3.0 не поддерживается; порт HTTPS по умолчанию — 443. Поддерживаются алгоритмы ГОСТ (Р 34.10-94/2001/2012, Р 34.11-94/2012, 28147-89); при TLS 1.3 клиентские сертификаты — только на алгоритмах ГОСТ, серверные — на любых.
8. **Сертификаты:** поля должны быть в US ASCII или Punycode, никакого Unicode — иначе платформа работает с сертификатом некорректно. Клиент Web-сервисов отвергнет сервер, если подпись сертификата не сходится, срок истёк или имя сайта в сертификате не совпадает с сайтом сервера; сертификат (или любой из его цепочки) должен быть в списке доверенных клиента.
9. **Клиентский код Web-сервисов по HTTPS:** в `WSОпределения` и `WSПрокси` нужно явно передать параметр `ЗащищенноеСоединение` с объектом `ЗащищенноеСоединениеOpenSSL`.
10. **Аутентификация:** при анонимной аутентификации на веб-сервере «1С:Предприятие» само запрашивает Basic; логин и пароль ожидаются в UTF-8. При Basic на веб-сервере те же учётные данные должны быть действительны и для веб-сервера, и для «1С». При аутентификации ОС имя и пароль из HTTP-запроса имеют приоритет над пользователем ОС; имперсонализация возможна не всегда и зависит от браузера, веб-сервера, прав и доменных политик.
11. **Файловый вариант базы через веб-сервер:** пользователям, от имени которых идёт доступ, нужны права на исполнение файлов нужной версии платформы и на чтение/изменение каталога информационной базы.
12. **OpenID настраивается в `default.vrd`:** зависимая база — `<openid><rely url="https://хост/публикация/e1cib/oid2op"/></openid>`; база-провайдер — `<openid><provider><lifetime>секунды</lifetime></provider></openid>` (в примере 432000 = 5 суток). У провайдера атрибут `enable` элемента `point` не влияет на интерактивный вход.
13. **HTTP-интерфейс провайдера OpenID** (`.../e1cib/oid2op`): `?cmd=auth` отвечает кодами 200 / 400 / 402 (402 — нужен второй фактор, детали в заголовках `Status2FA`, `Descr2FA`, `opsid`); `?cmd=lookup`, `?cmd=check` (`is_valid:true` / `is_valid:false`), `?cmd=logout`, `?cmd=additionalAuthSettings` (параметр `version=1`, заголовок ответа `1C-AuthSettingsProtoVersion`), `/2FACheck?user=...`. XRDS зависимой стороны — `.../e1cib/oid2rp`.
14. **Внешний OpenID-провайдер** должен поддерживать OpenID Authentication 2.0 с расширением «1С», использовать cookie `vrs_oid2op_auth` (для тонкого клиента), не перенаправлять через HTML-формы при запрете HTML в `Accept` и возвращать `openid.claimed_id` / `openid.identity` в виде `<адрес провайдера>?lid=<логин>`.
15. **Встраивание веб-клиента в сайт (Apache):** управляется заголовком `X-Frame-Options` через `mod_headers` — `sameorigin`, `allow-from <URL сайта>` или `deny`; если тонкая настройка не нужна, достаточно убедиться, что в конфигурационном файле нет `Header set X-Frame-Options "deny"`.
