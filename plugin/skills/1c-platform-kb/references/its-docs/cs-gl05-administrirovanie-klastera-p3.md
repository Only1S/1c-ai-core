## 5.3. Программные средства администрирования кластера серверов

### 5.3.1. Доступ к кластеру серверов из встроенного языка

Есть два независимых способа: через COM-соединение (только Windows) и через сервер администрирования `ras` (любая ОС).

| Критерий | COM-соединение (5.3.1.1) | Сервер администрирования (5.3.1.2) |
|---|---|---|
| ОС приложения, из которого администрируют | только Windows | Linux, macOS, Windows |
| Совпадение версии приложения и кластера | обязательно, номер версии в точности тот же | не требуется (с учётом особенностей самого сервера администрирования, см. 5.3.3.1) |
| Откуда можно вызывать | — (в источнике не уточняется) | и из клиентского, и из серверного приложения |
| Объекты | «Соединение с агентом сервера», «Соединение с рабочим процессом» (через `V83.COMConnector`) | объект `АдминистрированиеСервера` |
| Раздел синтакс-помощника | Средства интеграции и администрирования → Менеджер COM-соединений → Администрирование кластера серверов | Средства интеграции и администрирования → Администрирование сервера "1С:Предприятия" |

#### 5.3.1.1. С помощью COM-соединения

**Только Windows.** Условия применимости: приложение «1С:Предприятие», из которого идёт администрирование, работает под Windows и имеет точно такой же номер версии, что и администрируемый кластер.

Используются два объекта, оба получают от COM-соединителя:

```bsl
COMСоединитель = Новый COMОбъект("V83.COMConnector");
СоединениеСАгентомСервера   = COMСоединитель.ConnectAgent("TestSrv");
СоединениеСРабочимПроцессом = COMСоединитель.ConnectWorkingProcess("TestSrv:1562");
```

| Объект | Метод получения | Аргумент в примере | Что умеет |
|---|---|---|---|
| Соединение с агентом сервера | `ConnectAgent()` | `"TestSrv"` | см. перечень ниже |
| Соединение с рабочим процессом | `ConnectWorkingProcess()` | `"TestSrv:1562"` | см. перечень ниже |

Возможности **соединения с агентом сервера**:

- администраторы центрального сервера и администраторы кластера: аутентификация, добавление, удаление, получение списка;
- кластеры: создание, удаление, список;
- серверы: создание, удаление, список;
- рабочие процессы кластера: создание, удаление, список;
- список сервисов кластера;
- список сеансов информационной базы;
- список соединений кластера;
- список соединений информационной базы;
- список информационных баз, зарегистрированных в кластере;
- список блокировок кластера;
- получение прочей информации.

Возможности **соединения с рабочим процессом**:

- аутентификация пользователей информационных баз;
- информационные базы, зарегистрированные в кластере: создание, удаление, список;
- список соединений информационной базы;
- разрыв соединения информационной базы;
- соединение с информационной базой (COM-соединение);
- получение прочей информации.

#### 5.3.1.2. С помощью сервера администрирования кластера серверов

##### 5.3.1.2.1. Общая информация

- Через сервер администрирования (`ras`) можно управлять произвольным числом кластеров.
- Схема (рис. 89 документации): клиентское приложение → подключение к какому-либо серверу администрирования → через него подключение к связанному с ним кластеру.
- Объектная модель встроенного языка для работы через `ras` по сути повторяет возможности утилиты командной строки `rac`.

Условия и свойства этого способа:

- ОС приложения-администратора: Linux, macOS, Windows.
- Версии приложения-администратора, сервера администрирования и кластера совпадать не обязаны (с оговорками, действующими для сервера администрирования — см. 5.3.3.1).
- Управлять можно и с клиента, и с сервера.
- Клиентское приложение, выполняющее администрирование, может работать с файловой информационной базой и никак не быть связано по данным с администрируемым кластером.

Типовой порядок действий:

1. Подключиться к нужному серверу администрирования.
2. Аутентифицировать администратора центрального сервера кластера (если он задан).
3. Получить список кластеров, доступных на выбранном центральном сервере.
4. Аутентифицировать администратора конкретного кластера (если он задан).
5. Выполнять операции администрирования.

##### 5.3.1.2.2. Простой пример использования сервера администрирования

Минимальный сценарий: подключение к `ras` на `localhost`, порт `1545`, обход кластеров и вывод имени и описания каждой информационной базы.

```bsl
Агент = Новый АдминистрированиеСервера("localhost", 1545);
Агент.ВыполнитьАутентификацию();
Кластеры = Агент.ПолучитьКластеры();
Для каждого Кластер Из Кластеры Цикл
    Кластер.ВыполнитьАутентификацию();
    ИнфоБазы = Кластер.ПолучитьИнформационныеБазы();
    Для каждого ИнфоБаза Из ИнфоБазы Цикл
        Сообщить(ИнфоБаза.Имя + ", " + ИнфоБаза.Описание);
    КонецЦикла;
КонецЦикла;
```

Задействованные члены объектной модели: конструктор `АдминистрированиеСервера(<хост>, <порт>)`, методы `ВыполнитьАутентификацию()` (у агента и у кластера), `ПолучитьКластеры()`, `ПолучитьИнформационныеБазы()`, свойства информационной базы `Имя`, `Описание`.

См. также: сервер администрирования кластера серверов — раздел 5.3.3.

##### 5.3.1.2.3. Аутентификация ключевой парой

Суть: открытый ключ лежит на стороне кластера, закрытый — только у клиента и является конфиденциальным. Отсюда правило: **закрытый ключ нельзя хранить в данных формы или в базе данных** — его читают из файла на диске непосредственно перед аутентификацией и нигде не сохраняют.

Протокол:

1. Клиент сообщает серверу, что хочет аутентифицировать конкретного пользователя.
2. Сервер формирует запрос (с учётом имени этого пользователя) и отдаёт его клиенту.
3. Клиент подписывает запрос закрытым ключом — получается ответ.
4. Клиент отправляет ответ серверу.
5. Сервер проверяет подпись открытым ключом; если данные не изменены — аутентификация выполнена.

Ограничения запроса: срок жизни — **120 секунд** до момента подписи; после проверки подписи запрос становится недействительным (одноразовый).

Пример на стороне клиентского приложения:

```bsl
Пользователь = "admin";
РабочийСервер = Новый АдминистрированиеСервера();
// запрос от сервера
Запрос = РабочийСервер.ПолучитьДанныеДляАутентификацииОткрытымКлючом(Пользователь);
// ответ клиента (подпись закрытым ключом)
Ответ = Ждать СформироватьОтветДляАутентификацииОткрытымКлючомАсинх(Запрос, ПриватныйКлюч);
// собственно аутентификация
РабочийСервер.ВыполнитьАутентификациюОткрытымКлючом(Пользователь, Ответ);
Сообщить("Рабочий сервер версии " + РабочийСервер.ПолучитьВерсию());
```

| Метод | Назначение |
|---|---|
| `ПолучитьДанныеДляАутентификацииОткрытымКлючом(Пользователь)` | получить от сервера запрос для указанного пользователя |
| `СформироватьОтветДляАутентификацииОткрытымКлючомАсинх(Запрос, ПриватныйКлюч)` | сформировать ответ клиента (асинхронный, вызывается через `Ждать`) |
| `ВыполнитьАутентификациюОткрытымКлючом(Пользователь, Ответ)` | выполнить аутентификацию |
| `ПолучитьВерсию()` | версия рабочего сервера |

Переменная `ПриватныйКлюч` должна содержать содержимое файла приватного ключа; способ чтения файла — любой удобный.

⚠ в источнике неясно: в этом примере конструктор `АдминистрированиеСервера()` вызван без параметров (в 5.3.1.2.2 — с хостом и портом); пояснений к этому в тексте нет.

### 5.3.3. Сервер администрирования кластера серверов

#### 5.3.3.1. Общая информация

Состав: собственно сервер администрирования — **`ras`** и утилита командной строки — **`rac`**, которой управляют кластером (рис. 90 документации). Оба исполняемых файла входят в состав компонентов сервера «1С:Предприятия» при установке системы (ссылка в документации на описание установки).

**Совместимость версий.** Версия `ras` должна совпадать с версией кластера серверов. Для пары `rac` ↔ `ras` действуют группы совместимости:

| Версия `rac` | С какими версиями `ras` работает |
|---|---|
| 8.3.1, 8.3.2 | только 8.3.1, 8.3.2 |
| 8.3.3, 8.3.4 | только 8.3.3, 8.3.4 |
| 8.3.5 – 8.3.8 | только 8.3.5 – 8.3.8 |
| 8.3.9 и новее | только 8.3.9 и новее |

Для группы «8.3.9 и новее»: если версия `rac` меньше версии сервера администрирования, доступна только та функциональность, которая была в платформе версии самой утилиты. Чтобы пользоваться новой функциональностью, нужна `rac` той версии, где она появилась (в пределах перечисленных групп).

**Топология и режимы работы:**

- `ras` и `rac` работают в любой поддерживаемой ОС.
- К одному кластеру одновременно может быть подключено несколько серверов администрирования.
- Один сервер администрирования взаимодействует с одним агентом сервера.
- `ras` запускается как приложение, как служба Windows или как демон Linux.

**Как это работает:**

1. Запускается `ras` (приложение либо служба/демон).
2. `rac` соединяется с `ras` и передаёт ему команды.
3. `ras` подключается к кластеру только на время выполнения операции и после неё отключается.

Следствие: при регламентных работах с остановкой или перезапуском кластера останавливать `ras` не нужно. Исключение — смена версии кластера: тогда `ras` нужно перевести на ту же версию, что и кластер.

**Сетевой порт.** Обмен между `rac` и `ras` идёт через порт **1545** (по умолчанию); переопределяется параметром `--port` командной строки запуска `ras`.

**Чего `rac` не умеет.** Утилита покрывает весь объём задач администрирования кластера, кроме одного: аутентификация средствами ОС для администраторов кластера серверов, рабочего сервера и информационной базы не поддерживается.

**Интерфейс `rac` (важно для скриптов):**

| Аспект | Поведение |
|---|---|
| Ввод | все параметры передаются в командной строке |
| Вывод результата | стандартный поток вывода (stdout) |
| Код возврата при успехе | `0` |
| При ошибке | код возврата отличен от `0`, текст ошибки — в стандартный поток ошибок (stderr) |
| Формат результата | описание одного или нескольких объектов; каждая пара — с новой строки в виде `<Имя параметра> : <Значение параметра>` |
| Разделитель объектов | пустая строка — признак конца описания объекта |
| Имена параметров | совпадают с именами ключей командной строки утилиты |
| Параметры, не задаваемые через командную строку (или только для чтения) | имя образуется из имени свойства соответствующего COM-объекта: слова (сокращения) записываются в нижнем регистре через `-`. Пример: `MemoryExcessTime` → `memory-excess-time` |
| Команды создания элементов кластера | при успехе выводят идентификатор созданного элемента в том же формате; исключение — создание администраторов |
| Строки с произвольными символами | выводятся в двойных кавычках; двойная кавычка внутри строки удваивается |
| Даты | формат XML dateTime (http://www.w3.org/TR/2012/REC-xmlschema11-2-20120405/#dateTime) |

Формат строки вывода:

```text
<Имя параметра> : <Значение параметра>
```

Встроенная справка по параметрам:

```bash
ras help
rac help
```

Дополнительно: на диске ИТС поставляется пакет Java-архивов для работы с сервером администрирования из программ на Java без консольной утилиты — http://its.1c.ru/db/metod8dev#content:4985:hdoc.

#### 5.3.3.2. Запуск сервера администрирования

##### 5.3.3.2.1. Общая информация

Полное описание командной строки запуска `ras` находится в другом разделе документации (ссылка в документации). В этой части приведён только общий вид строки запуска; назначение параметров `--monitor-address`, `--monitor-base`, `--monitor-port` и аргумента `<host[:port]>` здесь не раскрыто (⚠ в этой части источника не описано — смотреть раздел с описанием командной строки `ras` или `ras help`). Про `--port` известно из 5.3.3.1: порт взаимодействия `ras` и `rac`, по умолчанию 1545.

Параметры, фигурирующие в строках запуска:

| Параметр | Значение в шаблоне | Что известно из этой части |
|---|---|---|
| `cluster` | — | первый аргумент строки запуска `ras`; отдельно в этой части не пояснён |
| `--daemon` | — | запуск в режиме демона (Linux) |
| `--port` | `<port>` | порт для взаимодействия `ras` и `rac`; умолчание 1545 |
| `--monitor-address` | `<address>` | назначение в этой части не описано |
| `--monitor-base` | `<location>` | назначение в этой части не описано |
| `--monitor-port` | `<port>` | назначение в этой части не описано |
| `<host[:port]>` | позиционный аргумент | назначение в этой части не описано |

##### 5.3.3.2.2. Для ОС Windows

**Только Windows.** В режиме приложения:

```bat
ras cluster --port=<port> --monitor-address=<address> --monitor-base=<location> --monitor-port=<port> <host[:port]>
```

В режиме сервиса: `ras` нужно зарегистрировать как службу; это делается командным файлом на основе утилиты `sc` (пример командного файла — в другом разделе, ссылка в документации). Запуск командного файла требует прав администратора; в примере документации аргументом передан номер версии:

```bat
register-ras 8.3.24.100
```

##### 5.3.3.2.3. Для ОС Linux

В режиме приложения:

```bash
./ras cluster --port=<port> --monitor-address=<address> --monitor-base=<location> --monitor-port=<port> <host[:port]>
```

В режиме демона — та же строка с дополнительным ключом `--daemon`:

```bash
./ras cluster --daemon --port=<port> --monitor-address=<address> --monitor-base=<location> --monitor-port=<port> <host[:port]>
```

## 5.4. Хранилище двоичных данных

### 5.4.1. Общая информация

**Лицензия:** механизм доступен только для лицензии КОРП (о видах лицензий — ссылка в документации).

**Назначение.** Большие данные (документы, изображения и т. п.) обычно лежат в реквизитах типа `ХранилищеЗначения` прямо в информационной базе. Хранилище двоичных данных — компромисс между хранением в базе и самодельным внешним файловым хранилищем: данные выносятся из базы, а платформа берёт на себя прозрачный доступ и администрирование.

Два вида хранилища:

| Вид | Где лежат данные | Что даёт платформа |
|---|---|---|
| Встроенное хранилище | дисковый накопитель (каталог данных кластера, см. 5.4.3.2.4) | прозрачная работа с данными + программный интерфейс администрирования, включая резервное копирование и восстановление |
| Хранилище S3 | внешнее хранилище, доступное по протоколу Amazon S3 | прозрачная работа с данными; резервное копирование — средствами провайдера (см. 5.4.5.3) |

«Прозрачность» означает, что прикладной код менять не нужно: работа по-прежнему идёт через значение типа `ХранилищеЗначения`, которое пишется в реквизит объекта и читается из него.

Что настраивается:

- пороговый размер данных, при превышении которого данные уходят в хранилище;
- использование хранилища для каждого отдельного реквизита типа `ХранилищеЗначения` — безусловное либо условное (в зависимости не только от размера, но и от других параметров);
- при нескольких подключённых хранилищах — в каком хранилище лежат данные какого реквизита какого объекта (стандартной функцией в клиентском приложении или встроенным языком).

**Условия применимости (все одновременно):**

- клиент-серверный вариант информационной базы;
- 64-разрядная версия кластера серверов.

**Перенос информационной базы на другой компьютер или кластер:**

| Используемое хранилище | Что нужно сделать | Если не сделать |
|---|---|---|
| Встроенное | перенести хранилище двоичных данных вместе с информационной базой | данные «потеряны», работать с ними нельзя |
| S3 | обеспечить доступ к программному интерфейсу хранилища с нового места размещения базы (способ зависит от конкретного внешнего хранилища) | данные так же «потеряны» |

**Особенность записи (влияет на объём).** Если значение реквизита уходит в хранилище двоичных данных, то запись в хранилище происходит при **любой** записи экземпляра объекта — независимо от того, менялись ли сами двоичные данные. Последствия:

- встроенное хранилище: дублирование устраняется объектной дедупликацией (см. 5.4.3.2.2);
- хранилище S3: дубли убираются резервным копированием или операцией очистки хранилища (см. 5.4.4); до этого в S3 будет лежать больше данных, чем ожидается.

### 5.4.2. Настройка размещения данных

#### 5.4.2.1. Общая информация

Инструменты управления: включение/выключение блочного хранения двоичных данных (для предшествующих режимов совместимости), выбор места хранения конкретного реквизита, распределение данных между несколькими хранилищами.

Уровни настройки:

- метаданные — в Конфигураторе;
- работающее прикладное решение — в режиме «1С:Предприятие», встроенным языком.

**Приоритет:** настройки, выполненные в режиме «1С:Предприятие», сильнее настроек из Конфигуратора. Это надо учитывать всегда, когда выясняют, попадёт ли реквизит в хранилище и в какое именно.

Запись значения реквизита в хранилище выполняется только при соблюдении всех описанных в разделе 5.4.2 условий; иначе значение пишется в информационную базу.

#### 5.4.2.2. Хранение двоичных данных

**Блочное хранение в клиент-серверном варианте.** Значения реквизитов типа `ХранилищеЗначения` хранятся в специальной системной таблице базы данных, блоками:

| Параметр | Значение |
|---|---|
| Максимальный размер блока | 448 Мбайт |
| Какие данные попадают в системную таблицу | размером более 2 Кбайт |
| Данные крупнее 448 Мбайт | занимают несколько записей (число записей кратно размеру блока) |
| Файловый вариант | блочное хранение не используется — все данные в таблицах «своих» объектов |
| Загрузка из dt-файла | размещение двоичных данных выполняется согласно режиму использования блочного хранения загружаемой конфигурации |

Смысл блочного хранения — обойти ограничения разных СУБД на максимальный размер двоичных данных (BLOB) в поле таблицы.

**Управление блочным размещением (платформа 8.3.26 и режим совместимости):**

| Условие | Поведение |
|---|---|
| Режим совместимости выше значения «Версия 8.3.26» (для самой платформы 8.3.26 это значение «Не использовать») | всегда используется специальная системная таблица; другого режима нет |
| Режим совместимости ниже значения «Версия 8.3.26» («Версия 8.3.25», «Версия 8.3.24» и более ранние) | в свойствах конфигурации доступно свойство **«Режим использования блочного хранения двоичных данных»** |

⚠ в источнике неясно: поведение при режиме совместимости, равном «Версия 8.3.26», отдельно не описано (текст говорит только «выше» и «ниже» этого значения).

Значения свойства «Режим использования блочного хранения двоичных данных» и эффект от его изменения:

| Значение | Что происходит |
|---|---|
| Использовать | существующие реквизиты в системную таблицу не переносятся; в неё пишутся двоичные данные, записанные после включения блочного хранения |
| Не использовать | данные из системной таблицы переносятся в таблицы «своих» объектов конфигурации |

**Режимы записи и чтения относительно хранилища.** Управляются методами `ПолучитьРежимРазмещенияКопийДанныхВХранилищеДвоичныхДанных()` и `УстановитьРежимРазмещенияКопийДанныхВХранилищеДвоичныхДанных()`; значения — системное перечисление `РежимРазмещенияКопийДанныхВХранилищеДвоичныхДанных`:

| Значение перечисления | Запись | Чтение | Сценарий |
|---|---|---|---|
| `РазмещениеДанныхВХранилищеИВБазеДанныхПриНедоступностиХранилища` | в хранилище; если запись в хранилище невозможна — в информационную базу | при недоступном хранилище прочитать можно только то, что оказалось в информационной базе | — |
| `РазмещениеДанныхТолькоВХранилище` | в хранилище | сначала из хранилища, при ошибке чтения — из информационной базы | — |
| `РазмещениеКопийДанныхВХранилищеПриЗаписиВБазуДанных` | и в хранилище, и в информационную базу | сначала из хранилища, при ошибке чтения — из информационной базы | отказоустойчивое хранение в базе, хранилище — как кеш быстрого доступа |
| `РазмещениеКопийДанныхВХранилищеПриЧтенииИзБазыДанных` | в информационную базу | сначала из хранилища, при ошибке чтения — из базы; если данных в хранилище нет, они синхронно копируются туда из базы | хранилище как кеш быстрого доступа, наполняемый после первого чтения |

#### 5.4.2.3. Управление хранением реквизита

Три связанных механизма; каждый следующий требует включения предыдущего:

1. **Общий порог для информационной базы** — пороговый размер данных. Значение реквизита крупнее порога сохраняется в хранилище (подробнее — 5.4.3.1).
2. **Безусловное включение/выключение для реквизита** типа `ХранилищеЗначения` — свойство реквизита **«Использование хранения в хранилище двоичных данных»** = «Использовать». Тогда все данные этого реквизита, превышающие порог, идут в хранилище.
3. **Условное включение для реквизита** — дополнительно к п. 2 заполняется свойство **«Поле использования хранения в хранилище двоичных данных»**. Данные попадут в хранилище, если одновременно:
   - реквизит, указанный в свойстве «Поле использования хранения в хранилище двоичных данных», имеет значение `Истина`;
   - размер значения превышает пороговое значение записи.

Условное управление действует для каждого элемента данных отдельно: решение принимается в момент записи объекта (например, элемента справочника) по текущему значению управляющего реквизита.

#### 5.4.2.4. Управление составом данных для конкретного хранилища

Применяется, когда к базе подключено больше одного хранилища: данные разных объектов конфигурации можно развести по разным хранилищам. Способы — интерактивно стандартной функцией **«Управление хранилищем двоичных данных»** либо встроенным языком.

Правила:

- один реквизит в каждый момент времени хранится только в одном хранилище двоичных данных; попытка назначить один реквизит нескольким хранилищам даёт исключение при установке состава;
- если для реквизита не задано «персональное» хранилище, значение пишется в **хранилище по умолчанию**;
- хранилище по умолчанию может быть только одно; при собственной реализации интерфейса разработчик обязан сам следить за этим;
- назначить хранилище умолчанием можно, только если для него разрешена запись данных.

Программный интерфейс состава хранимых данных:

| Элемент интерфейса | Где | Примечание |
|---|---|---|
| `УстановитьСоставХранимыхДанных()` / `ПолучитьСоставХранимыхДанных()` | методы менеджера хранилища двоичных данных (встроенное) | установка требует монопольного доступа к информационной базе |
| `СоставХранимыхДанных` | свойство менеджера внешнего хранилища двоичных данных | — |
| `СоставХранимыхДанныхХранилищаДвоичныхДанных` | тип значения состава | коллекция элементов `ЭлементСоставаХранимыхДанныхХранилищаДвоичныхДанных` |
| `ЭлементСоставаХранимыхДанныхХранилищаДвоичныхДанных.Метаданные` | свойство элемента | ссылка на объект метаданных, описывающий реквизит (реквизит объекта, ресурс регистра или константа с типом `ХранилищеЗначения`) |
| `ЭлементСоставаХранимыхДанныхХранилищаДвоичныхДанных.Хранение` | свойство элемента | нужно ли хранить реквизит в хранилище; значение перечисления `ИспользованиеХраненияВХранилищеДвоичныхДанных` |

Программный интерфейс хранилища по умолчанию:

| Вид хранилища | Элемент интерфейса | Примечание |
|---|---|---|
| Встроенное | `УстановитьИспользованиеКакХранилищаПоУмолчанию()` / `ПолучитьИспользованиеКакХранилищаПоУмолчанию()` менеджера хранилища двоичных данных | установка требует монопольного доступа к информационной базе |
| Внешнее (S3) | свойство `ХранилищеПоУмолчанию` менеджера внешнего хранилища двоичных данных | — |

Интерактивно хранилище по умолчанию назначается стандартной обработкой «Управление хранилищем двоичных данных».

#### 5.4.2.5. Определение используемого хранилища для записи двоичных данных

Алгоритм выбора места записи значения типа `ХранилищеЗначения`:

1. С реквизитом связан элемент состава какого-либо хранилища → действует правило из этого элемента состава.
2. Элемента состава нет → используется хранилище по умолчанию, если оно доступно для записи.
3. Во всех остальных случаях → запись в информационную базу.

### 5.4.3. Использование хранилища

#### 5.4.3.1. Общая информация

Шаги для начала работы:

1. Настроить кластер серверов (для встроенного хранилища) либо организовать хранилище S3.
2. Включить использование механизма в прикладном решении — встроенным языком или стандартной обработкой (ссылка в документации).

**Настройка кластера** сводится к созданию требования назначения функциональности (в тексте раздела оно названо «требование управления функциональностью»), которое разместит соответствующий сервис кластера на нужном рабочем сервере. Если кластер состоит из одного сервера, требование создавать не нужно. После настройки кластер перезапускают, затем выполняют настройки в прикладном решении.

**Хранилище S3** организуется по правилам провайдера. Провайдер может ограничивать размер передаваемого файла и число запросов в секунду; платформа обходит это так:

| Ограничение / параметр | Поведение платформы |
|---|---|
| Ограничение на объём передаваемого файла | составная (multipart) загрузка и выгрузка: файл передаётся фрагментами фиксированного размера, после передачи всех частей они объединяются |
| Размер фрагмента при передаче **в** S3 | выбирается автоматически |
| Размер фрагмента при получении **из** S3 | фиксирован — 100 Мбайт, изменить нельзя |
| Ограничение на число запросов в секунду | платформа распознаёт ситуацию и повторяет запрос: до 4 повторений с нарастающим интервалом |
| Пауза между двумя подряд идущими запросами | не более 20 секунд |

**Пороговый размер данных.** Задаётся для каждого подключённого хранилища. Если размер данных, записываемых в информационную базу (в сериализованном виде), превышает порог — данные автоматически пишутся в хранилище, а в базе сохраняется признак размещения в хранилище. Если размер меньше порога — данные остаются в базе, в хранилище ничего не попадает.

**Удаление.** При удалении объекта в информационной базе его данные в хранилище физически не удаляются, а помечаются на удаление (по аналогии с пометкой удаления в базе). Физическая очистка помеченных объектов происходит либо в ходе операции резервного копирования хранилища, либо специальным методом.

См. также: резервное копирование — 5.4.5; очистка помеченных на удаление объектов — 5.4.4.

#### 5.4.3.2. Встроенное хранилище

##### 5.4.3.2.1. Работа из встроенного языка

Точка входа — свойство глобального контекста **`ХранилищеДвоичныхДанных`** (менеджер хранилища двоичных данных); вызовы имеют вид `ХранилищеДвоичныхДанных.ИмяВызываемогоМетода()`.

| Метод | Назначение | Примечание |
|---|---|---|
| `ПолучитьДоступностьХранилищаДвоичныхДанных()` | поддерживает ли текущая версия платформы хранилище двоичных данных | проверять перед началом использования; правила ниже |
| `УстановитьРежимИспользованияХранилищаДвоичныхДанных()` | включить использование хранилища | требует монопольного режима работы с информационной базой |
| `ПолучитьРежимИспользованияХранилищаДвоичныхДанных()` | узнать текущий режим использования | — |
| `ПолучитьМинимальныйРазмерЗаписываемыхДанных()` / `УстановитьМинимальныйРазмерЗаписываемыхДанных()` | пороговый размер данных, записываемых в хранилище | — |
| `ПолучитьРежимЧтенияЗаписиХранилищаДвоичныхДанных()` / `УстановитьРежимЧтенияЗаписиХранилищаДвоичныхДанных()` | управление возможностью записи без отключения хранилища | позволяет перевести хранилище в режим «только для чтения» |

Режим «только для чтения»: все новые данные пишутся в базу данных, а не в хранилище; уже лежащие в хранилище данные остаются прозрачно доступными пользователю.

Результат `ПолучитьДоступностьХранилищаДвоичныхДанных()`:

| Условие | Результат |
|---|---|
| Режим совместимости от «Версия 8.3.10» до «Версия 8.3.21» включительно, свойство конфигурации «Режим хранилища двоичных данных» = «Использовать» | `Истина` |
| Тот же диапазон режимов совместимости, свойство «Режим хранилища двоичных данных» = «Не использовать» | `Ложь` |
| Режим совместимости «Версия 8.3.22» и последующие | всегда `Истина` |
| Файловый вариант информационной базы | хранилище всегда недоступно |

⚠ в источнике неясно: поведение для режимов совместимости ниже «Версия 8.3.10» не описано.

##### 5.4.3.2.2. Дедупликация данных в хранилище

Дедупликация ищет и удаляет повторяющиеся объекты; логическое состояние хранилища не меняется, сокращается только занимаемое место.

| Способ | Когда | Что считается совпадением |
|---|---|---|
| При записи | в момент записи нового объекта в хранилище | полное бинарное совпадение данных |
| В фоне | автоматически | совпадение файлов целиком, а также совпадающие фрагменты в файлах формата Microsoft Compound File Binary File Format (файлы Microsoft Office до версии 2003 включительно) и в документах PDF |

- Фоновая дедупликация затрагивает только записанные данные и только те, с момента последнего обращения к которым прошло более 2 месяцев, — то есть только неиспользуемые объекты.
- Механизм полностью автоматический, инструментов управления нет.
- Количество совпавших объектов видно в объекте `ИнформацияХранилищаДвоичныхДанных` (см. 5.4.3.2.3).

##### 5.4.3.2.3. Получение информации о хранилище

Метод `ХранилищеДвоичныхДанных.ПолучитьИнформацию()` возвращает объект **`ИнформацияХранилищаДвоичныхДанных`**:

| Свойство | Содержание | Единица |
|---|---|---|
| `ДатаПоследнейОчистки` | дата и время последней успешной очистки хранилища от устаревших данных | дата/время |
| `КоличествоДедуплицированныхЭлементов` | число удалённых дубликатов хранимых объектов | штук |
| `КоличествоУдаленныхЭлементов` | число объектов, удалённых логически (стоит «пометка удаления»), но ещё занимающих место на диске | штук |
| `КоличествоХранимыхЭлементов` | число объектов в хранилище без учёта удалённых | штук |
| `ОбъемУдаленныхДанных` | размер, занимаемый устаревшими объектами | байт |
| `ОбъемХранимыхДанных` | размер, занимаемый хранимыми объектами | байт |
| `ОбъемХранимыхДанныхНаДиске` | размер, который хранилище занимает на дисковом накопителе | байт |

##### 5.4.3.2.4. Изменение расположения хранилища двоичных данных

- Каталог с данными встроенного хранилища находится **в каталоге данных кластера на том рабочем сервере, который обслуживает сервис кластера «Сервис хранилища двоичных данных»**.
- Как задаётся каталог данных сервиса и как его менять — описано в другом разделе (ссылка в документации).
- Перенос каталога нужен не только при физическом перемещении в пределах одного рабочего сервера, но и, например, при переносе сервиса хранилища двоичных данных на другой рабочий сервер требованием назначения функциональности.

#### 5.4.3.3. Хранилище S3

##### 5.4.3.3.1. Работа из встроенного языка

Точка входа — свойство глобального контекста **`ВнешниеХранилищаДвоичныхДанных`** (менеджер внешних хранилищ; термины «внешнее хранилище» и «внешнее хранилище двоичных данных» равнозначны). Вызовы: `ВнешниеХранилищаДвоичныхДанных.ИмяВызываемогоМетода()`.

**Параметры подключения** — объект `ПараметрыПодключенияВнешнегоХранилищаДвоичныхДанных`:

| Свойство | Назначение |
|---|---|
| `URL` | адрес точки подключения к хранилищу |
| `ТипURL` | стиль адреса контейнера (корзины, bucket) у провайдера; значение перечисления `ТипURLВнешнегоХранилищаДвоичныхДанных` |
| `Каталог` | папка внутри существующего контейнера — когда провайдер ограничивает число контейнеров на пользователя и хранилище создают внутри уже имеющегося |

Полный адрес внешнего хранилища формируется как `URL + "/" + Каталог`.

Значения перечисления `ТипURLВнешнегоХранилищаДвоичныхДанных`:

| Значение | Стиль | Суть |
|---|---|---|
| `ВиртуальныйХостS3` | virtual-hosted-style | имя контейнера входит в доменное имя (вместе с прочими параметрами провайдера); идентификатор ресурса образует путь в домене |
| `ХостS3СБакетомВСоставеПути` | path-style | доменный адрес фиксирован; имя контейнера входит в путь вместе с идентификатором ресурса |

**Параметры доступа** — объект `ПараметрыДоступаВнешнегоХранилищаДвоичныхДанных`:

| Свойство | Термин S3 | Назначение |
|---|---|---|
| `ИдентификаторДоступа` | Access Key ID | публичный уникальный идентификатор клиента хранилища S3 |
| `СекретныйКлюч` | Secret Access Key | конфиденциальная часть; для доступа нужны и идентификатор, и секретный ключ |
| `Регион` | — | регион размещения хранилища; используется при получении доступа, например для регионо-зависимых хранилищ |

**Подключение хранилища:**

1. Сформировать параметры подключения и параметры доступа.
2. Вызвать метод `Добавить()` менеджера внешних хранилищ — на вход имя создаваемого внешнего хранилища и параметры доступа к нему (⚠ в источнике неясно: точный состав аргументов не приведён; сказано лишь, что имя и параметры, использованные при создании, затем доступны в свойствах `Имя`, `ПараметрыПодключения`, `ПараметрыДоступа`).
3. Записать созданный объект методом `Записать()` — только после этого хранилище S3 начинает использоваться.

**Объект `МенеджерВнешнегоХранилищаДвоичныхДанных`** — управление остальными параметрами:

| Член объекта | Назначение |
|---|---|
| `Имя` | имя хранилища, заданное при создании |
| `ПараметрыПодключения` | параметры подключения, использованные при создании |
| `ПараметрыДоступа` | параметры доступа, использованные при создании |
| `МинимальныйРазмерЗаписываемыхДанных` | порог, после которого данные пишутся в это хранилище |
| `РежимЧтенияЗаписи` | включение/выключение использования хранилища; работает как пара методов `…РежимЧтенияЗаписиХранилищаДвоичныхДанных()` встроенного хранилища |
| `ДатаПоследнейОчистки` | дата последней очистки |
| `ОчиститьНеиспользуемоеМестоПоУниверсальнойДате()` | физическая очистка от удалённых объектов, уменьшение занимаемого места (см. 5.4.4.3) |
| `СоставХранимыхДанных` | состав данных, хранимых в этом хранилище (см. 5.4.2.4) |
| `ХранилищеПоУмолчанию` | признак хранилища по умолчанию (см. 5.4.2.4) |

### 5.4.4. Очистка данных

#### 5.4.4.1. Общая информация

Проблема: при удалении данных в информационной базе связанные с ними данные хранилища (устаревшие данные) лишь помечаются как удалённые. Хранилище не уменьшается, место на сервере или во внешнем хранилище расходуется впустую. Физическое удаление выполняется специальным программным интерфейсом, свой для каждого вида хранилища.

**Рекомендуемый порядок очистки:**

1. Резервная копия информационной базы.
2. Резервная копия хранилища двоичных данных.
3. Очистка хранилища от устаревших данных; граничная дата — момент, **предшествующий началу** резервного копирования хранилища.

#### 5.4.4.2. Встроенное хранилище

- Метод `ОчиститьНеиспользуемоеМестоПоУниверсальнойДате()` объекта `МенеджерХранилищаДвоичныхДанных`.
- Параметр — граничная дата: физически удаляются все данные, помеченные на удаление раньше этой даты.
- Альтернатива: очистка сразу после создания резервной копии хранилища — пороговый момент передаётся параметром метода создания резервной копии (см. 5.4.5.2).

#### 5.4.4.3. Хранилище S3

- Метод `ОчиститьНеиспользуемоеМестоПоУниверсальнойДате()` объекта `МенеджерВнешнегоХранилищаДвоичныхДанных`.
- Параметр и смысл те же: удаляются данные, помеченные на удаление раньше указанной даты.

### 5.4.5. Резервное копирование

#### 5.4.5.1. Общая информация

Хранилище двоичных данных нужно резервировать так же, как и саму информационную базу. Способ зависит от вида (видов) подключённых хранилищ.

#### 5.4.5.2. Встроенное хранилище

Два вида копий:

| Вид копии | Метод создания | Содержимое | Рекомендуемое расширение файла | Метод восстановления | Что нужно для восстановления |
|---|---|---|---|---|---|
| Полная | `СоздатьПолнуюРезервнуюКопию()` | все файлы хранилища | `.sbf` (Storage Backup, Full) | `ЗагрузитьПолнуюРезервнуюКопию()` | один файл — сама копия |
| Дифференциальная | `СоздатьДифференциальнуюРезервнуюКопию()` | только изменения с момента начала предыдущего полного копирования, т. е. всё, что не вошло в полную копию, указанную как «база» | `.sbd` (Storage Backup, Differential) | `ЗагрузитьДифференциальнуюРезервнуюКопию()` | два файла: полная копия и дифференциальная, созданная именно на основании этой полной |

Детали:

- Имя файла копии передаётся параметром метода создания.
- Расширения `.sbf` / `.sbd` рекомендованы потому, что стандартная обработка управления хранилищем двоичных данных по умолчанию предлагает выбирать файлы именно с ними.
- Минусы полной копии — занимаемое место и время выполнения. Дифференциальная оправдана, когда хранилище пополняется не слишком интенсивно.
- Дифференциальную копию нельзя сделать, не имея хотя бы одной полной.
- `ПолучитьУниверсальнуюДатуСозданияРезервнойКопии()` — возвращает момент, который система считает началом полного резервного копирования; на вход — файл полной резервной копии. Этот момент удобно использовать как пороговую дату в методе очистки хранилища.
- Необязательный параметр **`УниверсальнаяДатаДоКоторойВыполнятьОчистку`** методов `СоздатьПолнуюРезервнуюКопию()` и `СоздатьДифференциальнуюРезервнуюКопию()`: если он задан, после резервного копирования выполняется однократная очистка и сжатие хранилища.

**Когда достаточно копии одной базы.** Если установлен режим `РазмещениеКопийДанныхВХранилищеПриЗаписиВБазуДанных` или `РазмещениеКопийДанныхВХранилищеПриЧтенииИзБазыДанных` (методом `УстановитьРежимРазмещенияКопийДанныхВХранилищеДвоичныхДанных()`), то минимально допустимый вариант — резервировать только информационную базу без хранилища; восстанавливать тогда тоже достаточно только базу. Тем не менее документация рекомендует и при таких настройках копировать (и восстанавливать) хранилище при каждой операции создания резервной копии.

**Особенность восстановления.** При восстановлении хранилища из копии снимаются все «пометки на удаление» его элементов: копирование и восстановление хранилища в общем случае не связаны с состоянием информационной базы, поэтому ради минимизации потерь все данные восстанавливаются как актуальные.

См. также: очистка от устаревших данных — 5.4.4; хранение двоичных данных — 5.4.2.2.

#### 5.4.5.3. Хранилище S3

- Резервное копирование выполняется средствами провайдера хранилища.
- При смене провайдера нужно полностью перенести данные из контейнера старого провайдера в контейнер нового, иначе данные в информационной базе станут недоступны.

### 5.4.6. Администрирование хранилища двоичных данных

#### 5.4.6.1. Общая информация

Инструменты:

| Инструмент | Где | Примечание |
|---|---|---|
| Диалог Конфигуратора | Главное меню → Администрирование → Управление хранилищами двоичных данных | описан в этом разделе |
| Стандартная функция | режим «1С:Предприятие» | по возможностям идентична диалогу Конфигуратора, отличается только местом вызова и выполнения; описание — в её справке |

#### 5.4.6.2. Список хранилищ

Команда меню открывает форму со списком хранилищ двоичных данных, к которым подключена текущая информационная база.

| Команда | Действие |
|---|---|
| Добавить | открывает диалог добавления хранилища (рис. 91 документации) |
| Изменить | настройка параметров выбранного хранилища (см. 5.4.6.3) |
| Удалить | платформа перестаёт использовать это хранилище при работе с двоичными данными; **содержимое хранилища при этом не удаляется** |

Виды хранилища в диалоге добавления:

- **Встроенное хранилище** — встроенное хранилище кластера серверов;
- **Внешнее хранилище по протоколу S3**;
- **Внешнее хранилище по протоколу S3 (виртуальный хост)**.

Для S3 указываются данные подключения, полученные у провайдера (различие стилей адреса и параметры доступа — см. 5.4.3.3.1). После нажатия **ОК** выполняется подключение, и хранилище становится доступным в режиме **«только для чтения»** — запись нужно разрешить отдельно (5.4.6.3).

#### 5.4.6.3. Действия с выбранным хранилищем

Диалог настройки хранилища; каждой задаче — своя закладка:

| Закладка | Что делает |
|---|---|
| Общие настройки | переключатель **«Разрешить запись»** включает режим записи; после этого в хранилище попадают новые данные, размер которых больше значения поля **«Минимальный размер данных (байт)»** |
| Создание резервной копии | полная или дифференциальная копия выбранного хранилища; для дифференциальной указывается файл полной копии (см. 5.4.5) |
| Восстановление из резервной копии | восстановление из полной или дифференциальной копии; для дифференциальной дополнительно указывается файл полной копии (см. 5.4.5) |
| Информация о хранилище | текущие параметры выбранного хранилища (состав — см. 5.4.3.2.3) |
| Очистка хранилища | операция очистки хранилища (см. 5.4.4) |

### 5.5.5. Управление табличными пространствами

#### 5.5.5.1. Возможность изменения положения предопределенных табличных пространств

Предопределённые табличные пространства:

| Назначение | IBM Db2 | Oracle Database | PostgreSQL |
|---|---|---|---|

| Данные | `V81C_LARGESPACE` | `V81C_DATA` | `V81C_DATA` |
| LOB | `V81C_LOBSPACE` | `V81C_LOB` | — |
| Временное | пользовательское временное — `V81C_USERTEMP`; системное временное — `V81C_SYSTEMPBP` | `V81C_TEMP` | произвольное наименование, задаётся через конфигурационный файл `postgresql.conf` |

#### 5.5.5.2. Управление пользовательскими табличными пространствами

##### 5.5.5.2.1. Общая информация

**Лицензия:** доступно только для лицензии КОРП.

Помимо перемещения предопределённых пространств, можно создавать пользовательские табличные пространства и размещать в них таблицы и индексы базы данных. Три взаимосвязанных инструмента:

1. Свойство конфигурации **«Режим использования табличных пространств»**.
2. Стандартная функция **«Управление табличными пространствами базы данных»**.
3. Механизм тестирования и исправления информационной базы.

Поддерживаемые СУБД: IBM Db2; Microsoft SQL Server; Oracle Database; PostgreSQL (все поддерживаемые).

Права пользователя, от имени которого выполняется подключение к СУБД, необходимые для создания пользовательских табличных пространств:

| СУБД | Требуемые права |
|---|---|
| IBM Db2 | `SYSCTRL` или `SYSADM` |
| Microsoft SQL Server | право `ALTER` на базу данных |
| Oracle Database | привилегии `CREATE TABLESPACE` и `DROP TABLESPACE` |
| PostgreSQL | входить в роль `SUPERUSER` |

Ограничения:

- пользовательские табличные пространства относятся к конкретной базе данных;
- настройки табличных пространств **не переносятся** между базами при выгрузке информационной базы в dt-файл и загрузке в другую СУБД;
- не поддерживается для Дата акселератора и для файлового варианта информационной базы.

См. также (ссылки в документации): свойства конфигурации; стандартные функции; механизм тестирования и исправления информационной базы.

##### 5.5.5.2.2. Добавление табличного пространства

Порядок действий:

1. Включить возможность использования табличных пространств — в Конфигураторе; нужно для режима совместимости «Версия 8.3.22» и предыдущих.
2. Запустить клиентское приложение (тонкий клиент или веб-клиент).
3. Открыть стандартную функцию «Управление табличными пространствами базы данных».
4. Создать новое табличное пространство (одно или несколько). **Каталоги, указанные при создании, должны уже существовать на компьютере сервера СУБД к моменту нажатия кнопки «Сохранить».**
5. Разместить в созданных пространствах нужные таблицы и индексы.
6. Нажать **«Сохранить»**; при успехе — перейти к следующему шагу.
7. Конфигуратором (интерактивно или пакетно) обновить размещение таблиц информационной базы:
   - интерактивно: функция «Тестирование и исправление информационной базы» с обязательным выбором режима **«Обновление размещения таблиц информационной базы»**;
   - пакетно: команда `/IBCheckAndRepair` с параметром `-RefreshTableLocation`.

При успешном завершении табличные пространства созданы и используются.

```text
/IBCheckAndRepair -RefreshTableLocation
```

**Подключение к уже существующему табличному пространству:**

1. Выяснить точное имя существующего табличного пространства и каталог, где лежат его файлы.
2. Открыть стандартную функцию управления табличными пространствами.
3. Добавить новое пользовательское табличное пространство, указав: в качестве имени — имя существующего пространства; в качестве пути — каталог размещения его файлов.
4. Выполнить остальные шаги добавления (размещение объектов, сохранение, обновление размещения таблиц).

##### 5.5.5.2.3. Удаление табличного пространства

1. Открыть стандартную функцию «Управление табличными пространствами базы данных».
2. Исключить из удаляемого пространства все таблицы и индексы.
3. Конфигуратором обновить размещение таблиц информационной базы — интерактивно (режим «Обновление размещения таблиц информационной базы» функции «Тестирование и исправление информационной базы») или пакетно (`/IBCheckAndRepair -RefreshTableLocation`). При успехе табличные пространства в СУБД больше не используются.
4. Снова открыть стандартную функцию «Управление табличными пространствами базы данных».
5. Удалить неиспользуемые табличные пространства.

##### 5.5.5.2.4. Использование встроенного языка

Точка входа — свойство глобального контекста **`ТабличныеПространстваБазыДанных`** (менеджер табличных пространств базы данных); вызовы: `ТабличныеПространстваБазыДанных.ИмяВызываемогоМетода()`.

Текущая конфигурация табличных пространств считывается в момент запуска системы «1С:Предприятие». Коллекцию обходят итератором `Для каждого` либо обращаются оператором `[]`:

```bsl
Для каждого ТабличноеПространство Из ТабличныеПространстваБазыДанных Цикл
    Сообщить("Имя: " + ТабличноеПространство.Имя + ", путь: " + ТабличноеПространство.ПутьДоПространства);
КонецЦикла;
```

Методы менеджера табличных пространств (`ТабличныеПространстваБазыДанных`):

| Метод | Назначение |
|---|---|
| `Добавить(<имя>, <путь>)` | добавить табличное пространство (сигнатура — по примеру ниже) |
| `Найти()` | получить менеджер табличного пространства по известному имени |
| `НайтиПоИспользуемомуСоставуДанных()` | в каком пространстве сейчас лежат таблицы данных объекта конфигурации |
| `НайтиПоИспользуемомуСоставуИндексов()` | в каком пространстве сейчас лежат индексы объекта конфигурации |
| `НайтиПоИзмененномуСоставуДанных()` | в каком пространстве окажутся таблицы данных после обновления размещения таблиц |
| `НайтиПоИзмененномуСоставуИндексов()` | в каком пространстве окажутся индексы после обновления размещения таблиц |

Элемент коллекции — объект **`МенеджерТабличногоПространстваБазыДанных`**:

| Член объекта | Назначение |
|---|---|
| `Имя` | идентификатор табличного пространства |
| `ПутьДоПространства` | путь к файлам табличного пространства |
| `ИспользуемыйСоставДанных` | текущий состав: таблицы, физически находящиеся в этом пространстве сейчас |
| `ИспользуемыйСоставИндексов` | текущий состав: индексы, физически находящиеся в этом пространстве сейчас |
| `ИзмененныйСоставДанных` | «будущий» состав: таблицы, которые переедут сюда после обновления размещения таблиц |
| `ИзмененныйСоставИндексов` | «будущий» состав: индексы, которые переедут сюда после обновления размещения таблиц |
| `Записать()` | сохранить изменения (используется в примере) |

Типы:

- `СоставТабличногоПространстваБазыДанных` — тип значений всех четырёх свойств состава; обычная коллекция со стандартным набором методов управления; элементы — `ЭлементСоставаТабличногоПространстваБазыДанных`.
- `ЭлементСоставаТабличногоПространстваБазыДанных` — единственное свойство `Метаданные`: объект метаданных, чьи таблицы данных или индексы размещаются в табличном пространстве.

Пример из документации — два пространства (для данных и для индексов) справочника «Товары», без каких-либо проверок:

```bsl
Элемент = Новый ЭлементСоставаТабличногоПространстваБазыДанных;
Элемент.Метаданные = Метаданные.Справочники.Товары;

ТабличноеПространствоДанных = ТабличныеПространстваБазыДанных.Добавить("ExtraData", "d:\data\data-files");
ТабличноеПространствоДанных.ИзмененныйСоставДанных.Добавить(Элемент);
ТабличноеПространствоДанных.Записать();

ТабличноеПространствоИндекс = ТабличныеПространстваБазыДанных.Добавить("ExtraIndex", "d:\data\index-files");
ТабличноеПространствоИндекс.ИзмененныйСоставИндексов.Добавить(Элемент);
ТабличноеПространствоИндекс.Записать();
```

Пути в примере документации — в стиле Windows (`d:\data\...`); это каталоги на сервере СУБД. После выполнения такого кода нужно обновить размещение таблиц базы данных — интерактивно или пакетным запуском Конфигуратора (см. 5.5.5.2.2, шаг 7).

## Что важно администратору Linux

1. **COM-администрирование на Linux недоступно.** Способ через `V83.COMConnector` требует, чтобы администрирующее приложение работало под Windows и имело точно ту же версию, что и кластер. На Linux остаются сервер администрирования `ras` + утилита `rac` и объект встроенного языка `АдминистрированиеСервера` (работает на Linux, macOS, Windows, совпадения версий приложения и кластера не требует).
2. **Версия `ras` должна совпадать с версией кластера.** При обновлении платформы `ras` обновляется вместе с кластером. В остальных случаях (остановка, перезапуск кластера) останавливать `ras` не нужно: он подключается к кластеру только на время выполнения операции.
3. **Запуск `ras` демоном:** `./ras cluster --daemon --port=<port> --monitor-address=<address> --monitor-base=<location> --monitor-port=<port> <host[:port]>`. Порт взаимодействия `ras` ↔ `rac` по умолчанию — 1545, меняется ключом `--port`. Назначение `--monitor-*` и `<host[:port]>` в этой части не раскрыто — смотреть `ras help` или раздел с описанием командной строки.
4. **Один `ras` — один агент сервера**, но к одному кластеру можно подключить несколько серверов администрирования.
5. **`rac` удобна для скриптов:** код возврата `0` при успехе, иначе ненулевой код и текст ошибки в stderr; вывод в stdout строками `<имя> : <значение>`, объекты разделены пустой строкой; строки с произвольными символами — в двойных кавычках с удвоением внутренних кавычек; даты — в формате XML dateTime; команды создания (кроме администраторов) печатают идентификатор созданного элемента.
6. **Имена полей в выводе `rac`** совпадают с ключами командной строки; для полей только для чтения имя получается из свойства COM-объекта по правилу «слова в нижнем регистре через дефис» (`MemoryExcessTime` → `memory-excess-time`).
7. **`rac` не поддерживает аутентификацию ОС** для администраторов кластера, рабочего сервера и информационной базы — это нужно учитывать при выборе способа аутентификации администраторов.
8. **Совместимость `rac` и `ras`:** группы 8.3.1–8.3.2, 8.3.3–8.3.4, 8.3.5–8.3.8, 8.3.9 и новее. В последней группе `rac` меньшей версии работает с более новым `ras`, но только в объёме функциональности своей версии.
9. **Аутентификация ключевой парой:** закрытый ключ читается из файла непосредственно перед аутентификацией и нигде не сохраняется; запрос сервера живёт 120 секунд до подписи и одноразовый.
10. **Хранилище двоичных данных** — только лицензия КОРП, только клиент-серверный вариант и 64-разрядный кластер. Каталог встроенного хранилища лежит в каталоге данных кластера на рабочем сервере, обслуживающем «Сервис хранилища двоичных данных»: его нужно учитывать при планировании дисков, резервного копирования и при переносе базы (без хранилища данные реквизитов будут потеряны).
11. **Место само не освобождается.** Удаление объектов в базе лишь помечает данные в хранилище; физическая очистка — метод `ОчиститьНеиспользуемоеМестоПоУниверсальнойДате()` либо параметр `УниверсальнаяДатаДоКоторойВыполнятьОчистку` при создании копии. Кроме того, двоичные данные пишутся в хранилище при каждой записи объекта, даже если не менялись (во встроенном хранилище это сглаживает дедупликация, в S3 — только очистка или резервное копирование).
12. **Порядок обслуживания хранилища:** копия информационной базы → копия хранилища (`.sbf` полная, `.sbd` дифференциальная, для которой обязательна полная) → очистка с граничной датой раньше начала копирования хранилища. При восстановлении хранилища из копии все пометки на удаление снимаются.
13. **После подключения хранилище доступно только для чтения** — запись включается отдельно (переключатель «Разрешить запись», порог «Минимальный размер данных (байт)»). Удаление подключения содержимое хранилища не удаляет.
14. **PostgreSQL, табличные пространства:** предопределённые `V81C_INDEX` (индексы) и `V81C_DATA` (данные) можно перемещать; временное табличное пространство имеет произвольное имя и задаётся в `postgresql.conf`. Пользовательские табличные пространства — только лицензия КОРП; пользователь подключения к СУБД должен входить в роль `SUPERUSER`; каталоги должны существовать на сервере СУБД до нажатия «Сохранить»; после изменения состава обязательно обновление размещения таблиц (`/IBCheckAndRepair -RefreshTableLocation`); настройки не переносятся через dt-файл.
15. **Что документация разрешает делать на стороне PostgreSQL:** использовать кластер серверов (п. 5.5.3), перемещать предопределённые табличные пространства, менять местоположение журнала транзакций, выполнять административные задачи (проверка целостности, реиндексация, дефрагментация, реорганизация, резервное копирование, очистка процедурного кеша, сбор статистики). Шифрование на уровне СУБД, сжатие на уровне СУБД и изменение положения файла базы данных для PostgreSQL в перечнях не значатся.
