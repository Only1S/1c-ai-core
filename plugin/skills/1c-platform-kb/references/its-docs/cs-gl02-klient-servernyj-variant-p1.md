## 2.1. Общее устройство системы

### Программные уровни клиент-серверного варианта

| Уровень | Что это | Примечание |
|---|---|---|
| Клиентское приложение | Обычный (толстый) клиент, тонкий клиент или веб-клиент | Это то, с чем работает конечный пользователь. Веб-клиенту нужен только веб-браузер |
| Веб-сервер | Промежуточное звено | Нужен только веб-клиенту и тонкому клиенту, подключённому через веб-сервер. В этом случае с кластером общается именно веб-сервер, а уже он — с клиентами |
| Кластер серверов «1С:Предприятия» | Промежуточный слой между клиентом и СУБД | Клиенты **не имеют прямого доступа** к серверу баз данных — только через кластер |
| Сервер баз данных | СУБД | Хранит жизненно важные данные ИБ. Каждая информационная база целиком лежит в **отдельной базе данных** СУБД. Могут использоваться различные СУБД (перечень — по ссылке «см. здесь» в документации, в этой части не приведён) |

### Ключевые положения

- **Кластер серверов — логическое понятие:** совокупность рабочих серверов (на одном или нескольких компьютерах) плюс список информационных баз, размещённых в этом кластере.
- **Распределение работы.** Архитектура рассчитана на перенос максимума функциональности в кластер и на «лёгкого» клиента:
  - в кластере: вся работа прикладных объектов; подготовка форм к отображению (чтение объектов из ИБ, заполнение данных формы, расположение элементов, запись данных формы после изменения); подготовка командного интерфейса; формирование отчётов; выполнение фоновых заданий;
  - на клиенте: только отображение подготовленной информации, взаимодействие с пользователем и вызовы серверных методов.
- **Что хранится на серверах кластера (кроме СУБД):** файлы журналов регистрации информационных баз, зарегистрированных на данном сервере, и другие служебные файлы. Эти данные **не являются жизненно необходимыми**: их потеря не делает информационные базы неработоспособными.
- **Установка и настройка.** Кластер устанавливается программой установки «1С:Предприятия»; настраивается утилитой администрирования кластера серверов из комплекта поставки.
- **Аппаратный ключ защиты сервера не сетевой.** Он должен быть подключён к **каждому** компьютеру, на котором работают рабочие процессы кластера.
- **Термин.** Если не оговорено иное, далее в документации «клиентское приложение» = обычный клиент, тонкий клиент **или веб-сервер**.

## 2.2. Устройство кластера серверов

## 2.2.1. Общие понятия

### Словарь сущностей

| Сущность | Процесс / файл | Суть |
|---|---|---|
| Рабочий сервер | — | Основная единица кластера: компьютер, на котором выполняется агент сервера |
| Агент сервера | `ragent` | «Представляет» рабочий сервер в кластере. Формально в состав рабочего сервера не входит, а обеспечивает его работу. Ведёт реестр сервера |
| Реестр сервера | файл `1cv8wsrv.lst` | Лежит в каталоге данных сервера. Содержит: список кластеров, в которые входит данный рабочий сервер; список администраторов данного рабочего сервера. По нему агент «знает», для каких кластеров сервер является центральным |
| Центральный сервер | свойство рабочего сервера **Центральный сервер** | В кластере должен быть минимум один. Максимум не ограничен — признак можно поставить всем рабочим серверам. Сервер может быть центральным в одном кластере и обычным в другом. Центральный сервер может служить точкой подключения к своему кластеру |
| Менеджер кластера | `rmngr` | Обеспечивает работу рабочего сервера и взаимодействие с другими рабочими серверами кластера |
| Главный менеджер кластера | `rmngr` на центральном сервере | Ведёт реестр кластера |
| Рабочий процесс | `rphost` | Непосредственно обслуживает клиентские приложения, работает с сервером БД, исполняет серверный код прикладного решения |
| Реестр кластера | файл `1cv8clst.lst` | Лежит в каталоге данных кластера (см. ниже) |
| Каталог данных кластера | каталог `reg_PORT` внутри каталога данных сервера | `PORT` — порт менеджера кластера. Если на рабочем сервере работают процессы нескольких кластеров, таких каталогов несколько — по одному на кластер |

### Содержимое реестра кластера (`1cv8clst.lst`)

- список информационных баз, зарегистрированных в кластере;
- список рабочих серверов кластера;
- список рабочих процессов кластера;
- список менеджеров кластера;
- список сервисов кластера;
- список администраторов кластера.

### Правила и ограничения

- **Несколько рабочих серверов на одном компьютере** возможны (например, для отладки), но у них должны быть **разные номера сетевых портов**, идентифицирующих рабочий сервер, и **разные каталоги данных кластера**. Для систем в промышленной эксплуатации это не рекомендуется.
- Кластер состоит из одного или нескольких рабочих серверов; сколько рабочих серверов работает на одном физическом компьютере — для описания и работы кластера неважно.
- **Рабочая часть рабочего сервера** = менеджер кластера (`rmngr`) + рабочий процесс (`rphost`).
- **Количество рабочих процессов** определяется настройками рабочего сервера, настройками кластера и физическими характеристиками компьютера.
- **Количество менеджеров кластера:** минимум один на рабочий сервер; максимум равен количеству сервисов кластера. Если рабочий сервер входит в несколько кластеров, для каждого кластера создаётся минимум один менеджер.
- **Несколько центральных серверов:** реестр кластера ведёт каждый главный менеджер, а между главными менеджерами центральных серверов идёт постоянная синхронизация реестра.
- Простейший случай — рабочий сервер и кластер целиком на одном компьютере.

## 2.2.2. Взаимодействие клиентского приложения с кластером серверов

Процессы кластера общаются между собой и с клиентами по **TCP/IP**; каждый процесс адресуется парой «имя рабочего сервера : номер порта».

### Сетевые порты по умолчанию

| Компонент | Порт по умолчанию | Примечание |
|---|---|---|
| Агент сервера (`ragent`) | `1540` | Адрес центрального сервера: `<сервер>:1540` |
| Менеджер кластера (`rmngr`) | `1541` | Адрес кластера: `<сервер>:1541`. Этот же номер входит в имя каталога `reg_PORT` |
| Диапазон динамического выбора | `1560:1591` | Из диапазона по мере необходимости выделяются порты: по одному на каждый рабочий процесс и по одному на каждый дополнительный менеджер кластера |

- Дополнительные менеджеры кластера создаются в зависимости от настройки **Менеджер под каждый сервис** в свойствах рабочего сервера.
- Номера портов и диапазон при необходимости можно изменить.

### Порядок подключения клиента (пример из документации: сервер `1C_Serv`)

1. Клиент обращается по адресу кластера, то есть к менеджеру кластера: `1C_Serv:1541`.
2. Менеджер кластера выбирает рабочий процесс и сообщает клиенту его адрес (в примере — `1C_Serv:1561`).
3. Клиент соединяется с назначенным рабочим процессом; тот выполняет аутентификацию пользователя ИБ и ведёт всё дальнейшее взаимодействие с информационной базой.

В примере: центральный сервер — `1C_Serv:1540`, кластер — `1C_Serv:1541`, рабочий процесс — `1C_Serv:1561`.

> **ВНИМАНИЕ. Версии клиента и сервера должны совпадать полностью.** Пример из документации: сервер 8.3.24.100 и клиент 8.3.24.150 вместе работать не будут.

## 2.2.3. Сервисы кластера

## 2.2.3.1. Список сервисов

Вся функциональность менеджера кластера разбита на независимые сервисы. У каждого — свой набор характеристик.

### Обозначения характеристик

| Обозначение | Смысл |
|---|---|
| **Диск** | Ресурсоёмкий сервис: повышенная нагрузка на дисковую подсистему |
| **Память** | Ресурсоёмкий сервис: повышенная нагрузка на процессор и оперативную память |
| **Репликация** | Поддерживается репликация между основным и резервными экземплярами сервиса. Возникает, когда уровень отказоустойчивости кластера отличен от 0. Для сервисов конфигурации кластера и состояния кластера — когда в кластере зарегистрировано несколько рабочих серверов с признаком **Центральный сервер** |
| **Деление по ИБ** | Для каждой информационной базы существует свой экземпляр сервиса |
| **Перенос+** | Сервис может мигрировать между рабочими серверами **без потери** данных |
| **Перенос-** | Сервис может мигрировать между рабочими серверами **с потерей** данных |
| **Не переносится** | Сервис не мигрирует и размещается только на компьютере центрального сервера кластера. Для таких сервисов нельзя создать требования назначения функциональности |
| **Один сервер** | Сервис не мигрирует, но может размещаться на любом одном рабочем сервере (не обязательно центральном) |
| **Каталог** | Для сервиса можно изменить каталог хранения данных (см. 2.2.3.2) |

### Важные подробности по отдельным сервисам

- **Сервис лицензирования.**
  - Если сервис временно недоступен, а лицензии через него уже получались, то временно выдаются такие же лицензии, какие уже были получены ранее, — но **не дольше 20 секунд**.
  - Для надёжного получения лицензий процессам `rphost` и `rmngr` нужны права на **создание, чтение и изменение** файла `1cv8conn.pfl`.
- **Сервис обновления конфигурации базы данных.** Перемещение его на другой менеджер кластера требует **остановки всех рабочих процессов**. При этом останавливается системное фоновое задание, поэтому после перемещения фоновое обновление окажется в **приостановленном** состоянии.
- **Распределение.** Сервисы кластера равномерно распределяются по рабочим серверам кластера — по типам сервисов, информационным базам и сеансам.
- **Процесс `rmstt`.** Если в кластере зарегистрирована хотя бы одна модель распознавания речи, запускается специальный менеджер кластера для сервиса распознавания речи. Его запуск не зависит от флажка **Менеджер под каждый сервис**; в списке процессов он называется `rmstt`.

⚠ в источнике неясно: у сервиса WebSocket в списке стоит отметка «Каталог», но в таблице сервисов с переносимым каталогом (2.2.3.2) его нет; сервис «Дата акселератора», наоборот, в таблице 2.2.3.2 есть, а отметки «Каталог» в списке не имеет. В тексте обозначений вариант с потерей данных записан как «Перенос–», в таблице — «Перенос-» (это одно и то же).

## 2.2.3.2. Изменение положения каталогов с данными сервисов

> Доступно **только для лицензии КОРП**.

Для сервисов с отметкой «Каталог» можно переназначить каталог хранения данных. Данные лягут в указанный каталог, но внутренняя структура хранения остаётся такой же, как при размещении по умолчанию.

### Сервисы с переносимым каталогом данных

| Сервис | Идентификатор | Путь по умолчанию |
|---|---|---|
| Дата акселератора | `DataAcceleratorService` | `<sdf>/1Сv8DbDA/<uuid-db>` |
| Журналов регистрации | `EventLogService` | `<sdf>/reg_<port>/<uuid-db>/1Cv8Log` |
| Мониторинга счетчиков потребления ресурсов | `CounterService` | `<sdf>/reg_<port>/rescntsrv.lst` |
| Полнотекстового поиска | `FulltextSearchService` | `<sdf>/reg_<port>/<uuid-db>/1Cv8FTxt` |
| Полнотекстового поиска, версия 2 | `FullTextSearchServiceV2` | `<sdf>/reg_<port>/<uuid-db>/1Cv8FTxt2` |
| Сеансовых данных | `SessionDataService` | `<sdf>/reg_<port>/snccntx/<uuid-rmngr>` |
| Управления моделями распознавания речи | `SpeechToTextModelManagementService` | `<sdf>/reg_<port>/STT` |
| Хранилища двоичных данных | `BinaryDataStorageService` | `<sdf>/reg_<port>/BinDataStrg/<uuid-db>` |

Обозначения в путях:

| Обозначение | Смысл |
|---|---|
| `<sdf>` | Каталог данных сервера. При расположении по умолчанию в точности совпадает с каталогом, указанным при запуске агента сервера (параметр `/d` командной строки агента) |
| `<port>` в `reg_<port>` | Номер сетевого порта главного менеджера кластера (параметр `/regport` командной строки агента) |
| `<uuid-db>` | Уникальный идентификатор информационной базы в данном кластере |
| `<uuid-rmngr>` | Уникальный идентификатор менеджера кластера |

⚠ в источнике неясно: в имени каталога `1Сv8DbDA` буква «С» набрана кириллицей (в остальных именах — `1Cv8Log`, `1Cv8FTxt`, `1Cv8FTxt2` — латинская «C»); вероятна опечатка, фактическое имя каталога сверять на сервере. Параметры агента в источнике записаны в виде `/d` и `/regport`. Обратите внимание на регистр в идентификаторах: `FulltextSearchService` (строчная «t»), но `FullTextSearchServiceV2` (заглавная «T»).

### Как меняется путь после переназначения

Заменяется только та часть пути, которая соответствует каталогу данных сервера (`<sdf>`); остальные фрагменты пути сохраняются. Пример из документации (каталог данных кластера `d:\cluster_data`, для хранилища двоичных данных задан новый путь `e:\storage\bds`):

```text
До:    d:\cluster_data\reg_1541\BinDataStrg\<uuid-db>
После: e:\storage\bds\reg_1541\BinDataStrg\<uuid-db>
```

### Сервисы с делением по информационным базам

- Если сервис делится по ИБ, но конкретные базы в настройке не указаны, используется общий каталог для всех баз кластера (как и в настройках по умолчанию).
- Для такого сервиса можно задать и общий каталог, и каталог отдельной информационной базы. Тогда:
  - базы, явно указанные в настройках, получают «персональные» каталоги (структура каталогов сохраняется);
  - все остальные базы размещаются в общем каталоге (или в каталоге по умолчанию).

### Предупреждения

- **Журналы регистрации и хранилище двоичных данных:** при смене каталога перенос данных **обязателен**. Без него кластер может стать **неработоспособным**.
- **Перенос данных выполняет администратор вручную** — кластер автоматически данные не переносит.
- Для остальных сервисов смена каталога работающего сервиса без переноса данных может привести к замедлению кластера и временной неработоспособности части функциональности.
- **Не рекомендуется** назначать рабочим каталогом сервиса сетевой ресурс — падает производительность кластера.
- **Не рекомендуется** назначать один и тот же каталог сервисам из разных кластеров. Эту уникальность администратор отслеживает сам.
- Каталог меняется через объект **настройки сервисов**. Управлять такими объектами можно интерактивно (консоль управления кластером серверов или стандартная обработка управления серверами) и программно (объектная модель встроенного языка).
- Изменённые каталоги фактически применяются **только при запуске кластера**. Поэтому перезапускать нужно весь кластер, даже если меняется каталог журнала регистрации одной-единственной базы. Размещение новых каталогов стоит продумать до создания настроек и переноса данных.

### Общая схема переноса каталога данных сервиса

1. Администратор кластера создаёт настройки сервисов для выбранных сервисов.
2. Запрещается подключение пользователей и начало работы регламентных заданий.
3. Завершаются все фоновые задания.
4. Завершается работа всех пользователей.
5. Применяются созданные настройки.
6. Останавливается кластер серверов.
7. Данные сервисов переносятся в новые каталоги.
8. Кластер запускается — сервисы работают уже с новыми каталогами.
9. Возвращается возможность работы пользователей и регламентных заданий.

Связанные темы, на которые ссылается документация: механизм распознавания речи; администрирование рабочего сервера; работа с настройками сервисов.

## 2.2.4. Сеансы и соединения

## 2.2.4.1. Общая информация

### Сеанс

Сеанс определяет активного пользователя информационной базы и его поток управления. Активным пользователем считается:

- экземпляр клиентского приложения «1С:Предприятия»;
- экземпляр веб-приложения, в котором исполняется веб-клиент;
- экземпляр внешнего соединения (полученный из объекта `V83.COMConnector`);
- один экземпляр фонового задания;
- одно обращение к Web-сервису.

### Активные и спящие сеансы

Сеанс бывает активным или спящим. Одно из назначений спящего сеанса — сохранить работоспособность клиентского приложения после перехода клиентского компьютера в режим энергосбережения.

| Событие | Условие |
|---|---|
| Переход в спящее состояние, вариант 1 | Нештатный разрыв соединения, назначенного сеансу, — для толстого клиента, внешнего соединения, тонкого клиента при прямом соединении с сервером. При физическом отключении сети сервер обнаруживает разрыв в течение 2–3 минут |
| Переход в спящее состояние, вариант 2 | Истёк интервал, в течение которого клиентское приложение не проявляло активности, — для веб-клиента и тонкого клиента при подключении через веб-сервер |
| Пробуждение | Любая активность клиентского приложения, использующего сеанс |
| Завершение спящего сеанса, вариант 1 | Истекло время жизни спящего сеанса |
| Завершение спящего сеанса, вариант 2 | Блокировки, установленные спящим сеансом, конфликтуют с блокировками, которые пытаются установить активные сеансы |

Числа и настройки:

| Параметр | Значение |
|---|---|
| Интервал неактивности до засыпания, по умолчанию | **1200 секунд** |
| Где настраивается время засыпания и время жизни спящего сеанса | В диалоге параметров информационной базы в конфигураторе |
| Как бездействующий клиент поддерживает сеанс | Если компьютер не в энергосбережении и пользователь ничего не делает, клиент сам периодически вызывает сервер с интервалом 5–10 минут; тонкий клиент и веб-клиент обращаются к кластеру не реже 1 раза в 10 минут |
| Рекомендация | Не ставить время засыпания сеанса **меньше 10 минут** |
| Условие перевода в спящее состояние | За интервал неактивности не было ни одного обращения к кластеру **и** сеанс не назначен соединению |

**Лицензии и спящие сеансы.** Засыпая, сеанс освобождает занятую клиентскую лицензию. При пробуждении он пытается получить её снова (если занимал до засыпания). Если лицензию получить не удалось — невосстановимое исключение и завершение сеанса.

### Данные сеанса

Данные сеанса — всё, что кластер хранит для одного активного пользователя и что актуально только на время его работы:

- информационная база;
- номер сеанса;
- аутентифицированный пользователь информационной базы;
- язык интерфейса;
- значения параметров сеанса;
- временные хранилища;
- статистика работы сеанса;
- информация форм управляемого приложения;
- некоторые внутренние данные платформы.

Особенности хранения:

- Данные сеансов хранит менеджер кластера — сервис сеансовых данных (см. 2.2.3.1).
- **При перезапуске кластера серверов данные сеансов сохраняются.**
- Для ускорения доступа данные сеансов кешируются в рабочих процессах и в толстых клиентах.
- В списке активных пользователей показывается список активных сеансов.
- Изменения данных сеанса, сделанные за один вызов сервера, лежат в рабочем процессе и передаются менеджеру кластера только при возврате управления клиенту (как штатном, так и в результате программного исключения).
- Изменения **не сохраняются** в менеджере кластера, если:
  - во время вызова сервера аварийно завершился рабочий процесс;
  - при возврате управления клиенту произошла ошибка передачи данных.

### Соединение

Соединение — средство доступа сеансов к кластеру. Оно содержит ограниченный набор данных соединения и **не отождествляется с активным пользователем**. Соединения также служат для взаимодействия процессов кластера между собой. Чтобы клиент мог обратиться к кластеру, сеанс назначается соединению; пока обращений нет, сеанс может не быть назначен ни одному соединению.

### Как разные клиенты работают с сеансами и соединениями

| Вариант | При старте / в начале обращения | При завершении / в конце обращения |
|---|---|---|
| Конфигуратор и толстый клиент | При старте: устанавливает соединение, начинает сеанс, назначает его соединению | При завершении: отменяет назначение, заканчивает сеанс, разрывает соединение |
| Одно обращение к Web-сервису; одно выполнение фонового или регламентного задания | В начале обращения: берёт соединение из пула, создаёт сеанс, назначает его соединению | В конце обращения: отменяет назначение, заканчивает сеанс, возвращает соединение в пул |
| Тонкий клиент и веб-клиент | Сеанс начинается при старте клиента. В начале каждого обращения к кластеру из пула берётся соединение и ему назначается сеанс клиента | Сеанс заканчивается при завершении клиента. В конце каждого обращения назначение отменяется, соединение возвращается в пул |

### Где видна информация о сеансах

- журнал регистрации;
- консоль кластера;
- средства программного администрирования;
- технологический журнал;
- глобальный контекст.

### Что может администратор кластера

| Действие | Средства | Последствия |
|---|---|---|
| Получить список сеансов по всему кластеру или по отдельной информационной базе | Утилита администрирования кластера; средства программного администрирования | — |
| Принудительно завершить сеанс | То же | Работа активного пользователя завершается аварийно. Если сеанс был назначен соединению, это соединение разрывается |
| Установить блокировку установки сеансов | То же | Новые сеансы начать нельзя; существующие сеансы продолжают работать |

## 2.2.4.2. Виды соединений

Соединения делятся на два вида: соединения с информационной базой и служебные соединения с рабочими процессами кластера.

| Признак | Соединение с информационной базой | Служебное соединение |
|---|---|---|
| С чем устанавливается | С конкретной информационной базой кластера | С рабочим процессом; с конкретной ИБ не связано |
| Код на встроенном языке | Может выполняться | Не выполняется |
| Принудительный разрыв | Возможен — командой консоли кластера или средствами встроенного языка | Невозможен; создаётся и завершается системой |
| Переустановка | Может переустанавливаться с течением времени | — |
| Влияние на остановку и запуск рабочего процесса | Наличие таких соединений **препятствует** остановке и запуску рабочего процесса | **Не препятствует** остановке и запуску рабочих процессов |

## 2.2.4.2.1. Соединения с информационной базой

Перечень видов: Толстый клиент; Тонкий клиент; Конфигуратор; Модуль расширения веб-сервера; COM-соединение; Фоновое задание; Системное фоновое задание.

| Вид соединения | Что это и для чего | Когда создаётся / сколько живёт |
|---|---|---|
| **Толстый клиент** | Соединение толстого клиента с ИБ: изменение данных и выполнение функциональности конфигурации | При интерактивном запуске толстого клиента в режиме 1С:Предприятие или при подключении через Automation Client/Server (COM-объект `V83.Application`) |
| **Тонкий клиент** | Соединение тонкого клиента с ИБ: изменение данных и выполнение функциональности конфигурации | При интерактивном запуске тонкого клиента или при подключении через Automation Client/Server (COM-объект `V83С.Application` — см. пометку ниже) |
| **Конфигуратор** | Соединение конфигуратора с ИБ: создание и изменение конфигурации, административные и регламентные действия | — |
| **Модуль расширения веб-сервера** | Соединение веб-сервера с рабочим процессом сервера: работа веб-клиента, интернет-сервисов, тонкого клиента по HTTP, мобильного клиента | Создаётся в момент обращения к интернет-сервису либо обращения веб-клиента, тонкого клиента (HTTP) или мобильного клиента к серверу. Существует до перезапуска веб-сервера или пока находится в пуле соединений модулей расширения веб-сервера (пока не истечёт время жизни в пуле или пока его не вытеснят другие соединения) |
| **COM-соединение** | Соединение процесса, использующего внешнее соединение «1С:Предприятия», с ИБ: изменение данных и выполнение функциональности конфигурации | При подключении к ИБ по технологии COM (COM-объект `V83.COMConnector`, метод `Connect`) |
| **Фоновое задание** | Соединение рабочего процесса кластера с ИБ для выполнения кода процедуры фонового задания | См. перечень ниже. Существует, пока существует контекст исполняемой процедуры; после выполнения процедуры или формирования отчёта закрывается |
| **Системное фоновое задание** | Соединение рабочего процесса кластера с ИБ для операций, которые система сама выполняет с ИБ во время работы кластера | См. перечень ниже |

**Когда создаётся соединение «Фоновое задание»:**

- платформа получает список регламентных заданий, зарегистрированных в ИБ;
- платформа запускает зарегистрированное в ИБ регламентное задание;
- фоновое задание запускается из встроенного языка;
- фоновое исполнение отчёта;
- фоновый поиск по подстроке;
- фоновый запрос списка;
- запуск фоновой реструктуризации.

**Что выполняется в соединении «Системное фоновое задание»** (перечень в документации не исчерпывающий):

- фоновое обновление конфигурации информационной базы (соединение существует, пока идёт фоновая реструктуризация);
- обработка оповещений копий базы данных;
- обработка оповещений механизма копий базы данных;
- обработка изменений административных параметров и профиля безопасности информационной базы;
- сервисные операции с ИБ:
  - предварительная загрузка контекста информационной базы в резервном рабочем процессе;
  - пересчёт итогов;
  - параллельная загрузка и выгрузка информационной базы;
  - тестирование и исправление.

**Примеры из документации** (комментарии пересказаны; в примерах ИБ `TestBase` в кластере 1541 центрального сервера `TestSrv`):

```bsl
// Толстый клиент через Automation
AutomationСервер = Новый COMОбъект("V83.Application");
AutomationСервер.Connect("Srvr="TestSrv";Ref="TestBase");
```

```bsl
// Тонкий клиент через Automation
AutomationСервер = Новый COMОбъект("V83С.Application");
AutomationСервер.Connect("Srvr="TestSrv";Ref="TestBase");
```

```bsl
// Внешнее (COM) соединение
COMСоединитель = Новый COMОбъект("V83.COMConnector");
СоединениеСИнформационнойБазой = COMСоединитель.Connect("Srvr="TestSrv";Ref="TestBase");
```

```bsl
// Запуск фонового задания из встроенного языка
ФоновоеЗадание = ФоновыеЗадания.Выполнить("РегламентныеПроцедуры.ОбновлениеИндексаПолнотекстовогоПоиска");
```

⚠ в источнике неясно: в строке соединения `"Srvr="TestSrv";Ref="TestBase"` кавычки не сбалансированы — приведено так, как в текстовой копии документации. В идентификаторе `V83С.Application` буква «С» в источнике набрана кириллицей (вероятная опечатка). Пометка конспекта: COM/Automation в этих примерах — только Windows.

## 2.2.4.2.2. Служебные соединения

Перечень видов: Планировщик заданий; Отладчик; Консоль кластера; Сервер администрирования; COM-администратор.

| Вид соединения | Что это и для чего | Когда создаётся / сколько живёт |
|---|---|---|
| **Планировщик заданий** | Соединение планировщика заданий с рабочим процессом: управление фоновыми заданиями, в том числе запуск регламентных заданий по расписанию. Используется и для других обращений менеджера кластера (`rmngr`) к рабочему процессу (`rphost`) — например, при получении списка сеансов | Создаётся при первом запуске фонового задания. Может порождать соединение фонового задания с ИБ в том же рабочем процессе. После завершения фонового задания **не закрывается** — живёт, пока рабочий процесс не будет выключен или удалён |
| **Отладчик** | Соединение отладчика с рабочим процессом, находящимся в режиме отладки: управление ходом отладки и поиск имеющихся предметов отладки | Создаётся при подключении предмета отладки или при поиске предметов отладки. Живёт, пока предмет отладки не отключён или не завершил работу |
| **Консоль кластера** | Соединение консоли кластера серверов (mmc) с рабочим процессом: администрирование информационных баз кластера | Создаётся в момент обращения к данным рабочего процесса (например, при получении параметров ИБ или подробного списка соединений ИБ). Пометка конспекта: консоль mmc — только Windows |
| **Сервер администрирования** | Соединение сервера удалённого администрирования кластера с рабочим процессом: администрирование информационных баз кластера | Создаётся в момент обращения к данным рабочего процесса (те же случаи: параметры ИБ, подробный список соединений ИБ и т. п.) |
| **COM-администратор** | Соединение с рабочим процессом сервера по технологии COM: администрирование информационных баз кластера | Создаётся при подключении к выбранному рабочему процессу через COM (объект `V83.COMConnector`, метод `ConnectWorkingProcess`). Пометка конспекта: COM — только Windows |

Пример из документации (подключение к рабочему процессу на порту 1562 в кластере 1541 центрального сервера `TestSrv`):

```bsl
COMСоединитель = Новый COMОбъект("V83.COMConnector");
СоединениеСРабочимПроцессом = COMСоединитель.ConnectWorkingProcess("tcp://TestSrv:1562");
```

## 2.2.4.3. Виды сеансов

Полный перечень видов сеансов:

- COM-администратор;
- COM-соединение;
- WS-соединение;
- Веб-клиент;
- Запрос системы аналитики;
- Клиент системы аналитики;
- Консоль кластера;
- Конфигуратор;
- Мобильный клиент;
- Сервер администрирования;
- Толстый клиент;
- Тонкий клиент;
- Фоновое задание.

В целом описание сеанса совпадает с описанием одноимённого соединения. Отличающиеся виды:

| Вид сеанса | Что представляет | Через какое соединение | Когда создаётся и завершается |
|---|---|---|---|
| **Веб-клиент** | Экземпляр веб-клиента в кластере; изменение данных ИБ и выполнение функциональности конфигурации | Модуль расширения веб-сервера | Создаётся при интерактивном запуске веб-клиента; живёт до завершения сеанса интерактивной работы с ИБ (закрыто последнее окно веб-браузера) |
| **Запрос системы аналитики** | Систему аналитики в кластере; выполнение запросов системы аналитики к кластеру | Модуль расширения веб-сервера | Стартует, когда системе аналитики нужно получить данные от кластера. Параметры завершения определяются параметрами пула сеансов |
| **Клиент системы аналитики** | Систему аналитики в кластере; взаимодействие системы аналитики и кластера, кроме выполнения запросов | Модуль расширения веб-сервера | Стартует при запуске системы аналитики из клиентского приложения «1С:Предприятие». Завершается при выходе пользователя из системы либо по параметрам автоматического завершения сеанса (как у веб-клиента) |
| **Мобильный клиент** | Экземпляр мобильного клиента в кластере; изменение данных ИБ и выполнение функциональности конфигурации | Модуль расширения веб-сервера | Создаётся при запуске мобильного клиента на мобильном устройстве; живёт до завершения сеанса работы с ИБ (закрыто мобильное приложение) |

## 2.2.5. Отказоустойчивый кластер

Отказоустойчивый кластер обеспечивает бесперебойную работу пользователей в двух случаях:

- перезапуск рабочих процессов и менеджеров кластера — плановый или аварийный;
- выход из строя сервера, входящего в кластер.

Механизмы, которые это обеспечивают, описаны в подразделах 2.2.5.1 – 2.2.5.6.

## 2.2.5.1. Транзакционность сеансовых данных

Сеанс переживает различные сбои, и после переустановки соединения работа может быть продолжена. Исключения, при которых система завершает сеанс и предлагает перезапустить клиентское приложение:

- во время вызова сервера, **после фиксации первой за этот вызов транзакции**, аварийно завершился рабочий процесс;
- при возврате управления клиенту произошла ошибка передачи данных.

## 2.2.5.2. Повтор последнего вызова

Ошибка передачи данных во время вызова сервера может означать обрыв канала связи либо аварийное завершение рабочего процесса.

| Ситуация | Что происходит |
|---|---|
| Клиент вызвал сервер **вне транзакции**, и ошибка получена **до** фиксации первой за вызов транзакции | Клиент автоматически заново устанавливает соединение с сервером и повторяет тот же вызов; работа продолжается |
| Ошибка получена **после** фиксации первой за вызов транзакции | Сеанс клиента завершается; для продолжения нужен перезапуск клиентского приложения |

## 2.2.5.3. Повтор интерактивного действия

- Если клиент вызвал сервер **в транзакции** (обычный режим работы, не режим управляемого приложения), ошибка передачи данных считается восстановимой: аварийно завершается интерактивное действие, но не само клиентское приложение.
- Платформа при этом **не гарантирует целостность данных приложения**, если интерактивное действие состоит более чем из одной транзакции или меняет состояние данных приложения (кроме данных, имеющих логику кеширования).

## 2.2.5.4. Резервирование рабочих процессов

**Проблема.** При аварийном завершении рабочего процесса кластер запускает новый и пытается перенести на него все клиентские сеансы упавшего процесса. Пользователи при этом видят заметные паузы: клиент не реагирует на команды и выглядит «зависшим».

**Решение — резервные рабочие процессы.** Резервирование включается в разрезе информационных баз (такие базы называются резервируемыми); администратор указывает, для каких ИБ создавать резервные процессы.

Логика работы:

1. На рабочих серверах, обслуживающих резервируемые ИБ, запускаются резервные рабочие процессы.
2. Они заранее загружают метаданные резервируемых информационных баз.
3. При необходимости клиентские сеансы переключаются на резервный процесс, в который уже загружено всё нужное, — переключение проходит достаточно быстро.
4. Когда резервный процесс становится обычным, признак резервного с него снимается, а кластер восстанавливает нужное количество резервных процессов, запуская новые.

Настройки и признаки:

| Что | Где | Назначение |
|---|---|---|
| Свойство **Количество ИБ на процесс** | Свойства рабочего сервера | Определяет количество резервных рабочих процессов |
| Флажок **Резервирование рабочих процессов** | Свойства информационной базы (в консоли кластера) | Включает резервирование рабочих процессов для данной ИБ |
| Флажок **Резервный** | Свойства рабочего процесса | Установлен, пока процесс выступает резервным; сбрасывается, когда процесс становится активным |

## 2.2.5.5. Уровень отказоустойчивости

**Определение.** Уровень отказоустойчивости — максимальное количество рабочих серверов кластера, одновременный выход из строя которых не приводит к аварийному завершению сеансов подключённых пользователей. Под «выходом из строя» понимаются отключение питания компьютера, разрыв сетевого кабеля, проблемы операционной системы, не позволяющие запустить процесс, и подобное.

Диапазон значений:

| Рабочих серверов в кластере | Возможный уровень отказоустойчивости | Смысл |
|---|---|---|
| 1 | только 0 | Отказ единственного сервера аварийно завершает работу всех пользователей |
| 4 | от 0 до 3 | 0 — фатален отказ любого рабочего сервера; 3 — кластер работоспособен при отказе 3 серверов из 4 |

Что важно учитывать:

- **Цена.** Повышение уровня отказоустойчивости снижает производительность: кластер тратит ресурсы на синхронизацию данных между рабочими серверами.
- **Связь с центральными серверами.** Количество центральных серверов определяет возможность создавать **новые** соединения.
  - Пример: 3 рабочих сервера, из них 2 центральных — при аварии одного центрального пользователи по-прежнему могут подключаться (остаются один центральный и один обычный сервер).
  - Если центральный сервер один, его авария делает кластер недоступным для пользователей, хотя ещё 2 рабочих сервера исправны.
- **Формула:** `Количество центральных серверов = Уровень отказоустойчивости + 1`.
  - Буквальное следование формуле несколько снижает производительность — часть мощности уходит на синхронизацию реестра кластера.
  - Нужен баланс между отказоустойчивостью и приемлемой производительностью с учётом оборудования компьютеров кластера.

Разбор сценариев из документации (кластер: 3 рабочих сервера, 1 из них центральный, уровень отказоустойчивости = 1):

| Сценарий | Укладывается в уровень отказоустойчивости | Результат |
|---|---|---|
| Отказ одного обычного рабочего сервера | Да | Кластер продолжает обслуживать пользователей; новые подключения возможны, так как центральный сервер работает |
| Отказ центрального сервера | Да | Тем не менее **кластер прекращает работу**, так как завершился его единственный центральный сервер |
| Отказ двух обычных рабочих серверов, центральный работает | Нет, уровень превышен | Сеансы пользователей, которых обслуживали отказавшие серверы, завершаются. Пользователи, обслуживаемые центральным сервером, продолжают работу; новые подключения возможны |

## 2.2.5.6. Система отслеживания разрыва соединений

### Назначение

Балансировка нагрузки и отказоустойчивость кластера опираются на TCP-соединения между компонентами кластера; TCP используется и при прямом (без веб-сервера) подключении тонкого и толстого клиентов к серверу. Если доступность компонентов определяется неверно, зависящие от неё механизмы работают некорректно. Поэтому существует система отслеживания разрыва соединений.

Что отслеживается:

- соединения между процессами кластера (на одном компьютере и между компьютерами);
- соединения между кластером и расширением веб-сервера;
- соединения между клиентским приложением и кластером.

Цели: оперативно обнаруживать разрыв соединения между компонентами и снизить накладные расходы на отслеживание целостности соединений.

### Направление проверки

Направление проверки — группа соединений между компонентами кластера, объединённых по правилу:

| Тип соединений | По чему группируются |
|---|---|
| Исходящие | По целевому адресу — имя компьютера и порт, однозначно определяющие компонент кластера |
| Входящие от расширения веб-сервера | По уникальному идентификатору, однозначно определяющему публикацию информационной базы на веб-сервере |
| Остальные входящие | По уникальному идентификатору, однозначно определяющему процесс-источник |

### Механизм проверки

- По каждому направлению периодически отправляется небольшой пакет данных и ожидается ответ.
- Проверка идёт с обеих сторон — и на стороне источника соединений, и на целевой стороне. Параметры проверки передаёт сторона источника.
- Пакеты ходят по **UDP и TCP**. Сначала используется UDP. Если за всё время жизни направления по UDP не пришло ни одного ответа, то по наступлении таймаута устанавливается TCP-соединение и проверка продолжается через него; направление при этом продолжает считаться доступным.
- Проверка по TCP менее точна и при небольших таймаутах может давать ложные срабатывания.
- **Рекомендация по сети:** обеспечить взаимную доступность между всеми компьютерами кластера, а также между компьютерами кластера и компьютерами веб-серверов **и по TCP, и по UDP — с теми же номерами портов**.

Управляющие параметры:

| Параметр | Смысл |
|---|---|
| **Период проверки** | Интервал между отправками тестового пакета |
| **Таймаут проверки** | Время, за которое отправитель должен получить хотя бы один ответный пакет по направлению. Отсчитывается от предыдущего полученного ответа (или от начала работы системы) |

Что происходит при срабатывании таймаута:

- Если за таймаут не пришло ни одного пакета с противоположной стороны, направление признаётся недоступным (кроме случая переключения с UDP на TCP).
- Все соединения этого направления помечаются непригодными и будут разорваны при первом же следующем обращении к ним.
- Одновременно все доступные компоненты кластера оповещаются о разрыве соединений этого направления, чтобы кластер успел отреагировать — в том числе снять блокировки, относящиеся к недоступному процессу.

### Значения периода и таймаута по умолчанию

| Соединение | Период проверки | Таймаут проверки | Можно ли изменить |
|---|---|---|---|
| Толстый клиент — кластер | 12 с | 60 с | Нет, фиксировано |
| Тонкий клиент — кластер | 3 с | 15 с | Нет, фиксировано |
| Расширение веб-сервера — кластер | 3 с (по умолчанию) | 15 с (по умолчанию) | Да — параметрами публикации информационной базы на веб-сервере |
| Процессы кластера между собой | 1 с (по умолчанию) | 5 с (по умолчанию) | Да — параметрами запуска агентов сервера |

Имена самих параметров публикации и параметров запуска агента в этой части главы не приведены (в документации стоят ссылки на другие разделы).

### Контроль качества соединений через технологический журнал

- Каждые **10 секунд** в технологический журнал записывается статистика проверки соединений за прошедшие 10 секунд, включая среднее и максимальное время ответа.
- Событие технологического журнала — **`CONN`**.
- По этой статистике подбирают таймауты проверки: такие, чтобы не было ложных срабатываний, но система оставалась надёжной.

### Режим при нулевом значении параметра (не рекомендуется)

Если **период проверки или таймаут проверки установлен в 0**, система переходит на другой алгоритм:

| Характеристика | Поведение |
|---|---|
| Кто проверяет | Только сторона, инициировавшая сетевое соединение |
| Частота отправки тестовых пакетов | Каждые 5 секунд |
| Когда приёмник фиксирует разрыв | Если не получил ни одного пакета за 200 секунд |
| Когда источник узнаёт о разрыве | Только после таймаута TCP-соединения, который определяется настройками операционной системы |
| Настройка периода и таймаута | Недоступна |
| Статистика в технологическом журнале | Не выводится |

Документация такой вариант настроек применять **не рекомендует**.

## Что важно администратору Linux

1. **Процессы сервера:** `ragent` (агент сервера), `rmngr` (менеджер кластера), `rphost` (рабочий процесс), а при зарегистрированной модели распознавания речи — ещё `rmstt` (отдельный менеджер кластера под сервис распознавания речи).
2. **Порты по умолчанию:** `1540` — агент, `1541` — менеджер кластера, `1560:1591` — рабочие процессы и дополнительные менеджеры (по одному порту на процесс). Клиент сначала идёт на `<сервер>:1541`, затем на порт выданного ему `rphost` — в межсетевом экране открывать нужно весь набор.
3. **Открывать порты и по TCP, и по UDP** (с теми же номерами) между всеми компьютерами кластера и между кластером и веб-серверами: система отслеживания разрыва соединений начинает проверку с UDP, а проверка только по TCP менее точна и при малых таймаутах даёт ложные разрывы.
4. **Служебные файлы:** реестр сервера `1cv8wsrv.lst` — в каталоге данных сервера; реестр кластера `1cv8clst.lst` — в подкаталоге `reg_<порт менеджера>` (по умолчанию `reg_1541`). В реестре кластера — список ИБ, рабочих серверов, процессов, менеджеров, сервисов и администраторов кластера.
5. **Что лежит в каталоге данных кластера помимо реестра** (пути по умолчанию): журнал регистрации `reg_<port>/<uuid-db>/1Cv8Log`, полнотекстовый индекс `1Cv8FTxt` и `1Cv8FTxt2`, сеансовые данные `reg_<port>/snccntx/<uuid-rmngr>`, хранилище двоичных данных `reg_<port>/BinDataStrg/<uuid-db>`, счётчики ресурсов `reg_<port>/rescntsrv.lst`, модели речи `reg_<port>/STT`. Сервисы с отметкой «Диск» (журналы регистрации, полнотекстовый поиск, сеансовые данные, хранилище двоичных данных и др.) создают повышенную нагрузку на дисковую подсистему.
6. **Потеря журналов регистрации и служебных файлов на сервере 1С не ломает информационные базы** — жизненно важные данные хранятся в СУБД, каждая ИБ — в отдельной базе данных.
7. **Лицензии.** Процессам `rphost` и `rmngr` нужны права на создание, чтение и изменение файла `1cv8conn.pfl` — это условие надёжного получения программных лицензий. При временной недоступности сервиса лицензирования выдаются такие же лицензии, как полученные через него ранее, но не дольше 20 секунд. Аппаратный ключ серверной лицензии не сетевой — он нужен на каждом компьютере, где работают рабочие процессы кластера.
8. **Версии клиента и сервера должны совпадать до сборки** — обновлять сервер и клиентов нужно согласованно.
9. **Перенос каталогов данных сервисов — только лицензия КОРП**, применяется только при запуске кластера и требует полного останова. Данные переносит администратор вручную; для журналов регистрации и хранилища двоичных данных перенос обязателен, иначе кластер может стать неработоспособным. Сетевые ресурсы под каталоги сервисов и общий каталог для разных кластеров не рекомендуются.
10. **Спящие сеансы:** засыпание по умолчанию через 1200 секунд неактивности; ставить меньше 10 минут не рекомендуется. Спящий сеанс отпускает клиентскую лицензию, а при пробуждении может завершиться, если лицензию получить не удалось. Данные сеансов переживают перезапуск кластера.
11. **Остановке и запуску рабочего процесса мешают только соединения с информационной базой**; служебные соединения (планировщик заданий, отладчик, консоль кластера, сервер администрирования, COM-администратор) не мешают.
12. **Принудительное завершение сеанса** аварийно обрывает работу пользователя; для планового обслуживания есть блокировка установки сеансов — она запрещает новые сеансы, не трогая существующие.
13. **Отказоустойчивость:** `центральных серверов = уровень отказоустойчивости + 1`. При единственном центральном сервере его отказ останавливает кластер даже при ненулевом уровне отказоустойчивости. Каждая дополнительная единица уровня и каждый дополнительный центральный сервер стоят производительности из-за синхронизации.
14. **Резервирование рабочих процессов** (флажок в свойствах ИБ плюс свойство рабочего сервера «Количество ИБ на процесс») сокращает «зависания» клиентов после падения `rphost`: сеансы переключаются на процесс с уже загруженными метаданными.
15. **Таймауты проверки соединений между процессами кластера** — по умолчанию период 1 с и таймаут 5 с, меняются параметрами запуска агента; между веб-сервером и кластером — 3 с и 15 с, меняются параметрами публикации. Подбирать их стоит по статистике события `CONN` технологического журнала (пишется каждые 10 секунд). Обнулять период или таймаут не следует: включается другой алгоритм, при котором приёмник фиксирует разрыв лишь через 200 секунд без пакетов, а статистика в журнал не пишется.
