## Глава 9. Блокировки и уровни изоляции по СУБД

Сводная таблица документации для PostgreSQL:

| Режим блокировок конфигурации | Вид блокировок СУБД | Уровень изоляции транзакций |
|---|---|---|
| Автоматический | таблиц | Serializable |
| Управляемый | записей | Read Committed |

Для сравнения: MS SQL Server в автоматическом режиме — блокировки записей, Repeatable Read или Serializable; в управляемом — Read Committed (2000) или Read Committed Snapshot (2005 и новее). Файловая база в обоих режимах — блокировки таблиц, Serializable.

Чтение вне транзакции на PostgreSQL в обоих режимах согласованное. Неявная транзакция при чтении объекта с табличными частями на PostgreSQL не открывается.

Документация рекомендует вести разработку в режиме управляемых блокировок; автоматический режим оставлен для совместимости со старыми решениями.

## Приложение 8, раздел 8.6. Особенности PostgreSQL

- В автоматическом режиме используются табличные блокировки: транзакция, захватившая одну запись, блокирует всю таблицу. Для реальной эксплуатации автоматический режим не рекомендуется.
- При сортировке по возрастанию значения `NULL` оказываются последними, по убыванию — первыми.
- При интенсивном удалении и добавлении записей (например, при перепроведении документов) возможна деградация производительности; документация советует регулярно выполнять `REINDEX` или `VACUUM` для часто изменяемых таблиц.
- Производительность сильно зависит от дисковой подсистемы, потому что параметр `fsync` включён по умолчанию. Отключать его документация допускает только при RAID-контроллере с энергонезависимым кешем и источнике бесперебойного питания.
- `ПОЛНОЕ ВНЕШНЕЕ СОЕДИНЕНИЕ` в запросах использовать не рекомендуется (реализовано в СУБД недостаточно эффективно); одновременно с обращением к табличным частям в списке полей оно не допускается.
- В операции `ПОДОБНО` квадратные скобки считаются специальными символами только в текстовом литерале, но не в выражении.

Общее для всех СУБД (раздел 8.1): в индекс входит не более 16 полей (в файловой базе — 256); сравнение строк в языке запросов не учитывает концевые пробелы, во встроенном языке — учитывает.

## Глава 17, раздел 17.7.3. Повторное использование сеансов интернет-сервисов

- У Web-сервиса и HTTP-сервиса есть свойства «Повторное использование сеансов» и «Время жизни сеанса». Время жизни 0 равносильно значению «Не использовать».
- При значении «Использовать» сеансом управляет клиент заголовком HTTP-запроса `IBSession`:
  - `IBSession: start` — создаётся сеанс; если создать нельзя, клиент получает `406 Not Acceptable`; при успехе в ответе приходит `Set-Cookie: ibsession=<ID сеанса>`;
  - в следующих запросах клиент передаёт `Cookie: ibsession=<ID сеанса>`; несуществующий или завершённый идентификатор даёт `400 Bad Request`;
  - `IBSession: finish` вместе с `Cookie: ibsession=<ID сеанса>` завершает сеанс;
  - без заголовка `IBSession` сеанс создаётся и завершается при каждом вызове;
  - если за время жизни в сеансе не было действий, он завершается сам;
  - разделители и безопасный режим, изменённые в запросах после старта сеанса, игнорируются.
- Параметры в `default.vrd` описаны в «Руководстве администратора» — см. `adm-pr03-sluzhebnye-fajly-p2.md`.
- Для стандартного интерфейса OData по умолчанию включено автоматическое повторное использование, время жизни сеанса — 20 секунд.

## Глава 17. Проверка сертификата сервера при HTTPS

Второй параметр конструкторов `ЗащищенноеСоединениеOpenSSL` и `ЗащищенноеСоединениеКриптоПро` задаёт, чем проверять сертификат сервера:

- `Неопределено` — сертификат сервера не проверяется;
- `СертификатыУдостоверяющихЦентровФайл` — сертификаты удостоверяющих центров берутся из указанного файла;
- `СертификатыУдостоверяющихЦентровОС` — из системного хранилища той ОС, где выполняется код; этот вариант документация рекомендует.

Пример из документации: `Новый ЗащищенноеСоединениеOpenSSL(, СертификатыУдостоверяющихЦентровОС)`.

## Глава 23. Криптография в Linux

- В Windows платформа работает с модулями криптографии через Microsoft CryptoAPI, в Linux и macOS — через интерфейс КриптоПро CSP. В списке поддерживаемых средств назван только КриптоПро; тип модуля криптографии — `80`.
- Порядок поиска модуля КриптоПро в Linux и macOS (раздел 23.6.2):
  1. путь из параметра `ПутьМодуляКриптографии` конструктора `МенеджерКриптографии`;
  2. каталоги из параметра `CryptoAPILibraryLocation` файла `conf.cfg`;
  3. стандартные пути расположения модуля КриптоПро (сами пути документация не называет).

## Глава 31. Отладка

- Протокол отладки TCP/IP: диапазон портов по умолчанию 1560–1591, меняется параметрами компонентов или файлом `debugcfg.xml`. Порты должны быть открыты на всех компьютерах, участвующих в отладке.
- Протокол отладки HTTP: используется сервер отладки `dbgs`; в клиент-серверном варианте он по умолчанию занимает порт 1550. Открыть порт нужно только на компьютере сервера отладки. Отладчик и предметы отладки напрямую не связываются — всё идёт через сервер отладки.
- В конфигураторе протокол выбирают в диалоге «Сервис — Параметры», закладка «Отладка», свойство «Протокол отладки».
- Отладчик и предметы отладки ищут друг друга по адресу `127.0.0.1`; имя `localhost` должно разрешаться в этот адрес.

## Глава 32. Внешние компоненты

- Системное перечисление `ТипПодключенияВнешнейКомпоненты`: `НеИзолированно` — компонента загружается в тот же процесс, где выполняется встроенный язык, и её падение роняет весь процесс вместе с его сеансами; `Изолированно` — компонента работает в отдельном хост-процессе, и при её падении страдает только он.
- Компоненты, установленные методом `УстановитьВнешнююКомпоненту()`, в Windows попадают в каталог `%APPDATA%\1C\1Cv8\ExtCompT`. Этот каталог не считается кешем и не очищается ключом `/ClearCache`. Путь для Linux документация не называет.

## Глава 33. Кроссплатформенная разработка

- Имена файлов в Linux чувствительны к регистру; дисков и UNC-путей нет, сетевые ресурсы нужно монтировать.
- Разделитель пути получают функциями `ПолучитьРазделительПути()`, `ПолучитьРазделительПутиКлиента()`, `ПолучитьРазделительПутиСервера()`; маску «все файлы» — `ПолучитьМаскуВсеФайлы()` и её клиентским и серверным вариантами (маска `*.*` в Linux означает только имена с точкой).
- Последовательные порты в Linux называются `/dev/ttyS0`, `/dev/ttyUSB0` и так далее.
- Обычному пользователю на запись доступны домашний каталог и каталог временных файлов; `КаталогПрограммы()` доступен только на чтение.
- Шрифты: рекомендуются стилевые шрифты или набор Microsoft Core Fonts.
- Механизмы COM, OLE и ActiveDocument в Linux и macOS недоступны; COM-компоненты рекомендуется переписать на Native API.

## Глава 37, раздел 37.4. Сервер хранилища конфигурации

- Доступ к хранилищу возможен тремя способами одновременно: как к общему каталогу, по TCP и по HTTP. Все хранилища одного сервера должны лежать в одном корневом каталоге.
- Запуск в Linux: `./crserver -daemon -port <порт> -d <каталог>` (имя ключа и значение разделяются пробелом).
  - `-d` — корневой каталог хранилищ; по умолчанию `/home/usr1cv8/.1cv8` или `~/.1cv8`;
  - `-port` — рабочий порт, по умолчанию 1542;
  - `-daemon` — запуск демоном.
- При ошибке вида «too many open files» нужно поднять предел `nofile` для пользователя сервера хранилища в `/etc/security/limits.conf`; значение подбирают опытным путём.
- В Windows: `crserver.exe -instsrvc | -rmsrvc -usr <пользователь> -pwd <пароль> -start | -stop -port <порт> -d <каталог>`; каталог по умолчанию `%LOCALAPPDATA%\1C\1Cv8\`.
- Пользователю, от имени которого работает сервер хранилища, нужны права чтения и записи на каталог хранилища (файл `1Cv8DDB.1CD` и каталог `data`).
- Адрес хранилища: `tcp://<сервер>/<относительный путь>` или `<адрес файла описания>/<относительный путь>`, например `tcp://RepServ/MyConfRep` и `http://www.MyCompany.ru/VirtualFolder/storage.1ccr/MyConfRep`. Путь считается от корневого каталога; если он не указан, открывается хранилище по умолчанию — каталог `maincr`, который создаётся при первом запуске сервера.
- Версии конфигуратора и сервера хранилища должны совпадать, иначе работа невозможна.
- Публикация через веб-сервер Apache: загрузить модуль расширения веб-сервера (`LoadModule _1cws_module …`), создать виртуальный каталог и зарегистрировать для него обработчик с идентификатором `1c-application`, положить в каталог файл с расширением `.1ccr`. Пример из документации для Linux:

```apache
Alias "/repos" "/var/1C/www/repos"
<Directory "/var/1C/www/repos">
    AllowOverride None
    Options None
    Order allow,deny
    Allow from all
    SetHandler 1c-application
</Directory>
```

  Пример дан в синтаксисе Apache 2.2 (`Order allow,deny`); для Apache 2.4 вместо двух этих строк пишут `Require all granted`. Содержимое файла `.1ccr`: `<storage connectString="tcp://RepServ"/>` (формат описан в `adm-pr03-sluzhebnye-fajly-p1.md`).
