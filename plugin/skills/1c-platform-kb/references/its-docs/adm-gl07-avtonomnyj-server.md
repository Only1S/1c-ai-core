# ИТС-конспект: Руководство администратора — Глава 7. Автономный сервер
> Источник: документация «1С:Предприятие 8.3.27», its.1c.ru/db/v8327doc. Это конспект своими словами, не дословный текст. Составлен 2026-10-10.

Глава описывает автономный сервер (`ibsrv`) и приёмы работы с утилитой администрирования `ibcmd`. Полные справочники командной строки `ibsrv`, командной строки `ibcmd` и формата конфигурационного файла автономного сервера находятся в других частях документации (глава на них только ссылается) — здесь собрано то, что упомянуто именно в главе 7.

Условные обозначения:
- «⚠» — место, где источник неясен, противоречив или содержит вероятную опечатку; в конспекте оно сохранено как в источнике и помечено.
- В источнике для ряда ключей встречаются две формы записи (`--database-user` / `--db-user`, `--database-path` / `--db-path`, `--request-database-password` / `--request-db-pwd`). В главе 7 прямо не сказано, что это синонимы; в конспекте указана та форма, которая стоит в соответствующем месте источника.
- Примеры в документации даны в основном с Windows-путями и СУБД Microsoft SQL Server; в конспекте они сохранены как есть. Для Linux нужно учитывать ограничение из п. 7.2: автономный сервер под Linux не работает с Microsoft SQL Server.

## 7.1. Общая информация

Автономный сервер — отдельное серверное приложение, которое обслуживает информационную базу **управляемого приложения** для любых клиентских приложений и для Конфигуратора.

| Свойство | Что говорит документация |
|---|---|
| Исполняемый файл сервера | `ibsrv` — в нём реализовано всё необходимое для работы сервера «1С:Предприятия»; при работе использует компоненты установленного экземпляра платформы своей версии |
| Утилита администрирования | `ibcmd` — специальная утилита командной строки |
| Протоколы взаимодействия с клиентом | HTTP и TCP/IP (что доступно — определяется настройками автономного сервера) |
| Количество баз | В каждый момент времени сервер работает с одной базой данных; для разных баз одновременно запускают несколько экземпляров автономного сервера |
| Что может быть базой данных | База одной из поддерживаемых СУБД либо файл `1Cv8.1CD` (файловый вариант) |
| Веб-сервер | Встроенный; внешний веб-сервер для публикации информационной базы не требуется |
| Функциональность | В основном совпадает с возможностями кластера серверов той же версии (в том числе при работе с файловым вариантом ИБ); отличия — в п. 7.2 |
| Администрирование | Инструменты существенно отличаются от инструментов кластера серверов (см. п. 7.2 и 7.3.5) |

## 7.2. Особенности и ограничения

Автономный сервер **не поддерживает**:

| № | Не поддерживается | Комментарий из документации |
|---|---|---|
| 1 | Обслуживание нескольких информационных баз одним автономным сервером | — |
| 2 | Работа нескольких автономных серверов с одной информационной базой | — |
| 3 | Обычное приложение | Обслуживаются только базы управляемого приложения |
| 4 | Подключение толстого клиента по протоколу TCP/IP | — |
| 5 | Применение инструментов автономного сервера (`ibsrv`, `ibcmd`) к базам, которые в этот момент работают под управлением кластера серверов | Такие попытки могут **разрушить базу данных** |
| 6 | Внешнее соединение (COM-соединение) с информационной базой | — |
| 7 | СУБД Microsoft SQL Server, если автономный сервер работает под ОС Linux | — |
| 8 | Управление через сервер `ras` | — |
| 9 | Графические инструменты управления | Аналога консоли кластера нет |
| 10 | Фоновая реструктуризация | — |
| 11 | Управление через COM-объект `V83.ComConnector` | — |
| 12 | Работа по протоколу HTTPS | Для HTTPS нужен произвольный веб-сервер в режиме reverse proxy, который отдаёт клиенту HTTPS |
| 13 | Аутентификация операционной системы | — |
| 14 | Работа с системой «1С:Аналитика» | — |
| 15 | Сервисы интеграции | — |
| 16 | Боты системы взаимодействия | — |
| 17 | Загрузка конфигурации из XML-файлов, выгруженных в линейном формате | Поддерживается только иерархический формат (см. п. 7.4.13) |

## 7.3. Использование механизма

### 7.3.1. Системные требования

Те же, что у кластера серверов «1С:Предприятия» (включая работу с файловым вариантом ИБ). Исключение одно: автономный сервер не работает под 32-разрядными ОС семейства Windows (только Windows).

### 7.3.2. Установка

Автономный сервер ставится одновременно с кластером серверов «1С:Предприятия»; отдельной установки не требуется.

### 7.3.3. Запуск автономного сервера

#### 7.3.3.1. Общая информация

- И сервер (`ibsrv`), и утилита управления (`ibcmd`) запускаются из командной строки.
- Все нужные параметры задаются либо в конфигурационном файле автономного сервера, либо в командной строке.
- Сведения о ходе выполнения выводятся в стандартный поток вывода (`stdout`).
- Код возврата: `0` — успех; отличный от `0` — ошибка, сообщения об ошибке при этом попадают в стандартный поток ошибок (`stderr`).
- `ibsrv` подключается к базе данных в **разделяемом** режиме.

Встроенная справка есть и у сервера, и у утилиты:

```
ibsrv help
ibcmd help
```

Справка по конкретному режиму утилиты (пример для режима `server`) и её сохранение в файл перенаправлением вывода:

```
ibcmd help server
ibcmd help server > .\server.desc
```

#### 7.3.3.2. Запуск автономного сервера

**Варианты запуска:**

| Вариант | Как |
|---|---|
| Обычное приложение ОС | `ibsrv <параметры>` |
| Сервис ОС Windows | ключ `--service` в командной строке службы (только Windows) |
| Демон ОС Linux | ключ `--daemon` |

Встроенных средств регистрации себя в качестве сервиса ОС у автономного сервера нет; средств запуска и остановки сервиса он тоже не предоставляет. Для этого используются средства операционной системы (в источнике названа утилита `sc`). ⚠ В источнике для Linux описан только запуск с ключом `--daemon`; о том, какими средствами ОС Linux оформлять автозапуск и остановку, в главе ничего не сказано.

**Конфигурационный файл автономного сервера:**

- Задаёт параметры экземпляра автономного сервера; его читает и сам сервер, и утилита администрирования.
- Формат — YAML (описание формата — в отдельном разделе документации).
- Через него можно управлять **всеми** параметрами сервера, **кроме путей служебных каталогов** автономного сервера (те задаются ключами командной строки, см. п. 7.4.10).
- Часть параметров можно задать и ключами командной строки (сервера или утилиты), и в файле.
- **Расположения по умолчанию у файла нет**: при каждом запуске сервера или утилиты путь к файлу надо указывать явно (`--config`).
- Создаётся либо командой `ibcmd server config init`, либо целиком вручную.

**Порядок определения параметров при запуске:**

1. Берутся значения, заданные в командной строке запуска.
2. Недостающие значения ищутся в конфигурационном файле сервера.
3. Для того, чего нет и там, применяются значения по умолчанию.

Значения из командной строки имеют приоритет над значениями из конфигурационного файла.

**Правила совместного доступа:**

- С одним **каталогом данных** в один момент времени может работать либо один экземпляр автономного сервера, либо одна утилита управления.
- Ключ `--data` (каталог данных) обязателен при одновременной работе нескольких копий автономного сервера и практически для любой операции с автономным сервером.
- С одной **базой данных** в каждый момент времени может работать только одно приложение из списка:
  - автономный сервер;
  - утилита управления автономным сервером в offline-режиме;
  - кластер серверов «1С:Предприятия»;
  - клиентские приложения, работающие с файловым вариантом ИБ напрямую (не через автономный сервер).

Во всех примерах подразумевается запуск из каталога `bin` нужной версии платформы.

**Запуск как приложения, файловый вариант.** Каталог данных — `c:\db\ss-data\demo`, остальные параметры — по умолчанию:

```
ibsrv --data="c:\db\ss-data\demo"
```

Файл базы `1Cv8.1CD` в этом случае ищется в подкаталоге `db-data` каталога данных (`c:\db\ss-data\demo\db-data`).

Запуск совсем без параметров — попытка стартовать с файловой ИБ, лежащей в каталоге данных по умолчанию.

**Запуск как приложения, клиент-серверный вариант.** В примере документации: СУБД Microsoft SQL Server, пользователь СУБД `dbUser` с паролем `dbUserPassword`, имя базы в СУБД `dbName`; предполагается, что база уже существует и является базой «1С:Предприятия».

```
ibsrv --dbms=mssqlserver --database-server=dbServerName --database-user=dbUser --database-password=dbUserPassword --database-name=dbName --data="D:\ss-data\dbName-data"
```

**Файловая ИБ по умолчанию.** Если при запуске не указаны оба ключа — `--database-path` и `--dbms`, — сервер стартует с файловой ИБ из каталога:

| ОС | Каталог |
|---|---|
| Linux | `~/.1cv8/standalone-server/db-data` |
| Windows | `%LOCALAPPDATA%\1C\1cv8\standalone-server\db-data` |

**Регистрация сервера службой (только Windows).** Документация даёт образец командного файла `register-ss.bat` с четырьмя аргументами: `%1` — полный номер версии платформы, `%2` — номер экземпляра службы (по службе на каждую обслуживаемую базу; существование службы с таким номером пример не проверяет), `%3` — полный путь к конфигурационному файлу экземпляра (в двойных кавычках; у каждого экземпляра свой файл со всеми параметрами запуска, включая параметры базы), `%4` — полный путь к каталогу данных ИБ (журнал регистрации, индекс полнотекстового поиска, временный каталог и т. д.). Суть файла — `sc stop`, `sc delete`, затем `sc create` со строкой запуска вида:

```
"C:\Program Files\1cv8\<версия>\bin\ibsrv.exe" --service --config="<файл>" --data="<каталог данных>"
```

Параметры `sc create` в образце: `start= auto`, `obj=` и `password=` (учётная запись службы), `displayname=`; имя службы — `Standalone server <номер>`. Пример вызова (нужны права администратора): `register-ss.bat 8.3.24.100 2 "d:\1C DB\ss-data\demo\demoma.yml" "d:\ss-data\demoma"`. Управление: `sc start "Standalone server 2"`, `sc stop "Standalone server 2"`, `sc delete "Standalone server 2"`. К моменту запуска службы конфигурационный файл должен содержать все нужные параметры.

**Запуск сервера в режиме демона (ОС Linux):**

```
ibsrv --daemon --config="путь к файлу конфигурации" --data="путь к каталогу данных"
```

К моменту запуска в режиме демона конфигурационный файл должен содержать все параметры, необходимые для запуска и работы автономного сервера.

### 7.3.4. Подключение к автономному серверу

Клиенты подключаются так же, как к кластеру серверов, по HTTP или по TCP/IP.

| Протокол | Кто может подключаться |
|---|---|
| HTTP | Только клиентское приложение |
| TCP/IP | Только тонкий клиент и Конфигуратор; толстый клиент по TCP/IP не поддерживается |

**Имя информационной базы при подключении по TCP/IP** должно в точности совпадать с именем, указанным при запуске автономного сервера (ключ `--name` командной строки `ibsrv` или соответствующий параметр конфигурационного файла). При расхождении клиент подключиться не сможет.

Пример. Сервер запущен с файловой ИБ:

```
ibsrv.exe --name=docs-db --data="D:\ss-data\fs-data"
```

Конфигуратор на том же компьютере запускается так:

```
1cv8.exe designer /S localhost\docs-db
```

Если имя исказить (`/S localhost\docsdb`), вместо подключения откроется диалог создания новой информационной базы.

Тонкий клиент — через HTTP и прямым подключением:

```
1cv8c.exe enterprise /WS"http://localhost:8314"
1cv8c.exe enterprise /S localhost\docs-db
```

Веб-клиент — адрес в браузере:

```
http://localhost:8314
```

Все адреса приведены для настроек по умолчанию; если параметры публикации менялись, строку запуска нужно привести в соответствие с фактическими параметрами сервера.

### 7.3.5. Управление автономным сервером

#### 7.3.5.1. Способы подключения к автономному серверу

##### 7.3.5.1.1. Общая информация

Экземпляр автономного сервера, которым управляет `ibcmd`, задаётся одним из трёх способов:

| Ключ `ibcmd` | Режим | Что означает | Пример значения |
|---|---|---|---|
| `--data` | Offline-режим | Утилита работает с той информационной базой, которую описывает указанный каталог данных. Запущенный `ibsrv` не нужен; более того, если с этим каталогом данных запущен экземпляр автономного сервера, offline-режим недоступен | `--data="D:\ss-data\cs-data"` |
| `--pid` | Локальный запущенный экземпляр | Утилита подключается к работающему `ibsrv` на том же компьютере. Значение — номер процесса ОС этого экземпляра (в нумерации той ОС, под которой работает сервер) | `--pid 16453` |
| `--remote` | Удалённый запущенный экземпляр | Утилита подключается к `ibsrv` на другом компьютере. На сервере должен быть настроен доступ к ИБ и серверу по протоколу SSH. Экземпляр определяется URL и портом, который обслуживает автономный сервер | `ssh://server1C:8282` |

Замечания:

- При работе через `--pid` или `--remote` (документация оба случая называет работой с «удалённым» сервером) ключ `--data` и любые параметры доступа к информационной базе указывать не нужно: всё это уже известно запущенному серверу из его конфигурационного файла или командной строки `ibsrv`.
- При работе с «удалённым» сервером доступны не все команды утилиты (см. п. 7.3.5.1.3 и 7.3.5.1.4).
- Каталог, указанный как каталог данных (`--data`) **запущенного** экземпляра автономного сервера, нельзя использовать:
  - для запуска другого экземпляра автономного сервера;
  - для работы утилиты администрирования в offline-режиме.

**Сеанс и права.** Любая команда, которой нужен доступ к информационной базе, создаёт сеанс ИБ; пользователь этого сеанса должен иметь права на выполняемое действие. Если команде не нужен доступ к ИБ, но нужен доступ к серверу в целом (например, получение списка сеансов), она должна выполняться от имени пользователя с административными правами в базе, которую обслуживает экземпляр.

Аутентификация — интерактивно либо ключами командной строки:

| Ключ | Назначение |
|---|---|
| `--user` | Имя пользователя информационной базы |
| `--password` | Пароль пользователя |

Порядок создания сеанса и аутентификации:

- Удалённое подключение (SSH) — сеанс создаётся от имени пользователя, аутентифицированного в шлюзе SSH.
- Локальное подключение (выбран экземпляр на локальном компьютере) или настройка конфигурационного файла — сеанс создаётся от имени системного пользователя «1С:Предприятия», обладающего полными административными правами.

##### 7.3.5.1.2. Offline-режим

- Доступны **все** команды утилиты управления.
- Работать можно только на том компьютере, где находится каталог с данными информационной базы.
- Одновременная работа автономного сервера и утилиты управления с одним каталогом данных (`--data`) не поддерживается.

##### 7.3.5.1.3. Подключение к экземпляру автономного сервера на локальном компьютере

Доступны все команды утилиты, **кроме**:

| Недоступно | Команда |
|---|---|
| Инициализация конфигурации автономного сервера | все команды группы `config` |
| Создание информационной базы | `ibcmd infobase create` |
| Восстановление целостности информационной базы | `ibcmd infobase repair` |

##### 7.3.5.1.4. Подключение к экземпляру автономного сервера по протоколу SSH

Через `ibcmd` доступны все команды, кроме тех же трёх исключений, что и в п. 7.3.5.1.3: вся группа `config` (инициализация конфигурации сервера), `ibcmd infobase create`, `ibcmd infobase repair`.

Когда у автономного сервера включена поддержка SSH, он дополнительно начинает вести себя как Конфигуратор, запущенный в режиме агента: к нему можно подключаться не только `ibcmd`, но и сторонними SSH- и SFTP-клиентами. Набор команд SSH-клиента аналогичен набору команд агента конфигуратора, но поддерживаются **только** перечисленные ниже.

| Группа | Команда | Назначение |
|---|---|---|
| `help` | — | Справка по командам |
| `common` (общие команды) | `connect-ib` | Подключение к информационной базе |
| | `disconnect-ib` | Отключение от информационной базы |
| `options` (настройки текущей сессии) | `get` | Получить значение параметра |
| | `list` | Получить список параметров |
| | `set` | Установить значение параметра |
| `config` (редактирование конфигурации) | `dump-cfg` | Сохранение конфигурации в файл |
| | `dump-config-to-files` | Выгрузка конфигурации в XML-файлы |
| | `dump-external-data-processor-or-report-to-files` | Выгрузка внешней обработки/отчёта в XML-файлы |
| | `extensions` | Работа с расширениями конфигурации |
| | `generation-id` | Получить идентификатор «поколения» метаданных |
| | `load-cfg` | Загрузка конфигурации из файла |
| | `load-config-from-files` | Загрузка конфигурации из XML-файлов |

| | `manage-cfg-support` | Снятие конфигурации с поддержки |

#### 7.3.5.2. Доступные возможности автономного сервера

Отдельные возможности автономного сервера можно включать и отключать — ключами командной строки запуска либо параметрами секции `features` конфигурационного файла.

| Возможность | Включить (ключ) | Выключить (ключ) | Параметр секции `features` | По умолчанию | Что теряется при отключении |
|---|---|---|---|---|---|
| Шлюз прямого подключения (TCP/IP) | `--enable-direct-gate` | `--disable-direct-gate` | `direct-gate: true` / `direct-gate: false` | включён | Подключение толстым клиентом и вообще любым клиентским приложением по TCP/IP; отладка по TCP/IP |
| Шлюз подключения по HTTP | `--enable-http-gate` | `--disable-http-gate` | `http-gate: true` / `http-gate: false` | включён | Подключение любых клиентов по HTTP (включая веб-клиент, мобильный клиент и т. д.); отладка по HTTP |
| Шлюз подключения к ИБ по SSH и выполнение команд по этому протоколу | `--enable-ssh-gate` | `--disable-ssh-gate` | `ssh-gate: true` / `ssh-gate: false` | включён | В источнике отдельно не расписано; по смыслу п. 7.3.5.1 — управление через `ibcmd --remote` и подключение SSH/SFTP-клиентами |
| Расширенная функциональность Конфигуратора | `--enable-extended-designer-features` | `--disable-extended-designer-features` | `extended-designer-features: true` / `extended-designer-features: false` | **выключена** | Некоторые возможности автономного сервера, например запись конфигураций для мобильных устройств в файл |

⚠ В описании шлюза прямого подключения источник упоминает подключение «толстым клиентом» по TCP/IP, хотя в п. 7.2 и 7.3.4 сказано, что толстый клиент по TCP/IP не поддерживается; формулировка сохранена как в источнике.

Подробности — в описаниях шлюзов автономного сервера и управления его возможностями (другие разделы документации).

### 7.3.6. Отладка с использованием автономного сервера

#### 7.3.6.1. Общая информация

- Автономный сервер поддерживает все протоколы отладки, включая внешний сервер отладки при использовании протокола HTTP.
- Отладка включается ключом командной строки `--debug` либо секцией `debug` конфигурационного файла.
- Доступность отладки по TCP/IP и по HTTP зависит от того, включены ли соответствующие шлюзы (п. 7.3.5.2).

Если указан `--debug` без уточнения, способ отладки выбирается в таком порядке:

1. Отладка по TCP/IP — если не отключён шлюз прямого подключения.
2. Отладка по HTTP — если не отключён шлюз подключения по HTTP.
3. Отладка по HTTP через внешний сервер отладки — если его параметры заданы в командной строке (`--debug-server-url`) или в конфигурационном файле.
4. Во всех остальных случаях отладка выключена.

Следствия:

- Если отладка включена «по умолчанию» и оба шлюза (прямой и HTTP) работают, отладка пойдёт по TCP/IP. Чтобы выбрать другой способ, его нужно указать явно — значением ключа `--debug` (плюс сопутствующие ключи) или в конфигурационном файле.
- Одновременно использовать оба протокола отладки (TCP/IP и HTTP) нельзя, поэтому документация рекомендует всегда явно указывать нужный вид отладки.

Значения ключа `--debug`, встречающиеся в главе: `tcp`, `http` (см. п. 7.4.8).

См. также секции `gates` и `debug` конфигурационного файла автономного сервера (описаны в другом разделе документации).

#### 7.3.6.2. Использование внешнего сервера отладки

Схема работы:

1. Запускается сервер отладки.
2. Запускается автономный сервер с указанием этого сервера отладки. Конфигурация информационной базы автономного сервера должна в точности совпадать с конфигурацией, которую предстоит отлаживать.
3. База автономного сервера служит только источником структуры конфигурации и исходных текстов; данные при отладке берутся из отлаживаемой базы данных.

Расположение сервера отладки задаётся ключом:

```
--debug-server=<dbgs-адрес>
```

Адрес составляется из имени компьютера, на котором запущен сервер отладки, и порта, указанного при его запуске. Для запуска по умолчанию адрес — `http://localhost:1550`.

Автономный сервер можно запустить с адресом сервера отладки, даже если сам сервер отладки ещё не запущен; его допустимо поднять позже, когда понадобится отладка.

⚠ В источнике ключ назван по-разному: в п. 7.3.6.1 — `--debug-server-url`, в п. 7.3.6.2 — `--debug-server=<dbgs-адрес>`. Точное имя следует сверять со справочником командной строки автономного сервера (`ibsrv help`).

### 7.3.7. Выгрузка информационной базы в файл

`ibcmd` умеет выгружать информационную базу в dt-файл:

```
ibcmd infobase dump --dbms=mssqlserver --database-server=dbServerName --database-user=dbUser --database-password=dbUserPassword --database-name=docs-db --data="d:\ss-data\dbName-data" 1cv8.dt
```

- На время выгрузки с выгружаемой базой данных не должно быть **никаких** подключений; в том числе запрещена работа с ней нескольких серверных приложений (и автономных, и обычных). Иначе возможна потеря целостности создаваемого dt-файла.
- Выгрузка в dt-файл **не является** средством резервного копирования информационной базы. Для резервных копий следует применять соответствующие инструменты (документация отсылает к отдельным разделам).

## 7.4. Примеры управления и запуска автономного сервера

### 7.4.1. Общая информация

Примеры раздела не являются законченными решениями — они только демонстрируют отдельные возможности.

Рекомендации и общие правила:

- **Имя информационной базы** рекомендуется всегда задавать явно — параметром `infobase.name` конфигурационного файла или ключом `--name`. В примерах оно иногда опущено ради краткости; в реальной работе указывать настоятельно рекомендуется.
- Для любой команды утилиты управления (как и для самого сервера) нужно полностью определить используемую информационную базу и её каталог данных одним из способов:
  - ключами командной строки (работа на локальном компьютере);
  - путём к конфигурационному файлу автономного сервера в командной строке (работа на локальном компьютере);
  - указанием экземпляра автономного сервера на локальном или удалённом компьютере.
- Операции с информационной базой требуют аутентификации: `--user` и `--password`. В примерах используется пользователь `ibuser` с паролем `123` — в реальных системах такой пароль недопустим.

> ⚠ О примерах YAML в этом разделе: в текстовой копии источника, с которой составлялся конспект, отступы в примерах конфигурационных файлов потеряны (все строки идут с начала строки). Ниже порядок и текст строк сохранены точно, а вложенность восстановлена по смыслу (с опорой на упоминаемые в тексте главы имена `infobase.name`, `http.zones`, «секция `features`» и т. п.). Точную структуру файла следует сверять с разделом документации «Конфигурационный файл автономного сервера» или с выводом `ibcmd server config init`.

### 7.4.2. Создать конфигурационный файл по параметрам командной строки

```
ibcmd server config init --dbms=postgresql --database-server=dbServerName --db-user=dbUser --database-password=dbUserPassword --database-name=dbName --name=docsIB --http-base=/webAccess
```

Команда выводит сформированный конфигурационный файл в `stdout`:

```yaml
server:
  address: localhost
  port:
database:
  dbms: PostgreSQL
  server: dbServerName
  name: dbName
  user: dbUser
  password: dbUserPassword
infobase:
  id: 7b88938e-5aa8-4933-afea-8a9ec121724f
  name: docsIB
  distribute-licenses: yes
  schedule-jobs: allow
http:
  base: /webAccess
```

- Сохранить результат в файл можно ключом `--out` утилиты `ibcmd` либо перенаправлением вывода (`> file.ext`).
- Сервер, запущенный с таким файлом, открывает веб-клиент по адресу `http://localhost:8314/webAccess`.
- В выводе примера значение `port:` в секции `server` пустое (так в источнике).

### 7.4.3. Создать конфигурационный файл по параметрам информационной базы сервера

Импорт описания базы из данных кластера серверов:

```
ibcmd server config import --cluster-data="d:\1C srvinfo" --name=demoma --out=d:\ss-cfgs\demoma.yml
```

| Ключ | Назначение |
|---|---|
| `--cluster-data` | Каталог данных кластера серверов (в примере `d:\1C srvinfo`) |
| `--name` | Имя информационной базы, зарегистрированной в кластере (в примере `demoma`) |
| `--publication` | Путь к файлу `default.vrd` — одновременно импортировать параметры публикации |
| `--out` | Файл, в который записать результат |

Результат (файл `d:\ss-cfgs\demoma.yml`):

```yaml
server:
  address: localhost
  port: 8314
database:
  dbms: MSSQLServer
  server: <имя сервера>
  name: <имя базы данных>
  user: sa
  password: <пароль пользователя>
infobase:
  id: 1a39d42c-4da6-4f1c-bd78-98884d27578b
  name: demoma
  distribute-licenses: yes
```

Смысл: если базы уже зарегистрированы в работающем кластере, переносить их параметры в конфигурационный файл автономного сервера вручную не обязательно.

Импорт вместе с параметрами публикации:

```
ibcmd server config import --cluster-data="d:\1C srvinfo" --name=demoma --publication=c:\inetpub\wwwroot\demoma\default.vrd --out=d:\ss-cfgs\demoma.yml
```

- Результат — единый конфигурационный файл автономного сервера (описание базы плюс параметры публикации).
- При импорте файла публикации строка доступа к информационной базе из атрибута `ib` элемента `point` файла `default.vrd` **игнорируется**. Соответствие базы и файла публикации контролирует сам администратор.

### 7.4.4. Создать информационную базу из файла конфигурации (*.cf)

Вариант в два шага — сначала конфигурационный файл сервера, затем создание базы по нему:

```
ibcmd server config init --database-path="D:\ss-data\file-db\db-data" --name=docsIB --http-base=/webAccess --out="D:\ss-data\file-db\file-db.yml"
ibcmd infobase create --config="D:\ss-data\file-db\file-db.yml" --load="D:\Cfgs\MyApp\1Cv8.cf" --data="D:\ss-data\file-db"
```

1. `ibcmd server config init` формирует конфигурационный файл автономного сервера.
2. `ibcmd infobase create` создаёт информационную базу (и файл базы данных) на основании файла конфигурации.

Два шага удобны, когда параметры базы задаются в одном месте информационной системы, а создаётся база в другом — по готовому конфигурационному файлу. Если нужно только создать базу из `.cf`, достаточно одной команды:

```
ibcmd infobase create --data="D:\ss-data\fs-data" --database-path="D:\ss-data\file-db\db-data" --load="D:\Cfgs\MyApp\1Cv8.cf"
```

Вывод в `stdout`:

```
[ INFO] Создание информационной базы...
[ INFO] Создание информационной базы успешно завершено
[ INFO] Загрузка конфигурации...
[ INFO] Загрузка конфигурации успешно завершена
```

- Если к моменту выполнения файл базы данных (`1Cv8.1CD`) уже существует, команда завершается с ошибкой.
- ⚠ В источнике сказано, что база будет создана в каталоге `D:\ss-data\fs-db\db-data`, тогда как в командах указан путь `D:\ss-data\file-db\db-data` (а в одношаговом варианте каталог данных — `D:\ss-data\fs-data`); пути в примере между собой не согласованы.

**Клиент-серверный вариант** принципиально не отличается, но требует больше параметров:

```
ibcmd infobase create --dbms=mssqlserver --database-server=dbServerName --db-user=dbUserName --database-password=dbUserPassword --database-name=my-db --name=docsIB --data="D:\ss-data\cs-data" --create-database --load="D:\Cfgs\MyApp\1Cv8.cf" --apply
```

В СУБД создаётся база `my-db`, в неё загружается конфигурация из `D:\Cfgs\MyApp\1Cv8.cf`. Повторный запуск закончится ошибкой, так как база уже существует.

Создание базы из `.cf` само по себе **не создаёт конфигурацию базы данных**. Чтобы структура базы данных соответствовала загруженной конфигурации, нужен специальный параметр, отвечающий за обновление конфигурации базы данных; пример из документации:

```
ibcmd infobase create --dbms=mssqlserver --database-server=dbServerName --db-user=dbUser --database-password=dbUserPassword --database-name=my-db --name=docsIB --data="D:\ss-data\cs-data" --create-database --load="D:\Cfgs\MyApp\1Cv8.cf" --apply --force
```

Вывод в этом случае дополняется сведениями об обновлении конфигурации базы данных:

```
[INFO] Создание информационной базы...
[INFO] Создание информационной базы успешно завершено
[INFO] Загрузка конфигурации...
[INFO] Загрузка конфигурации успешно завершена
[INFO] Обновление конфигурации базы данных...
[INFO] Проверка корректности метаданных...
[INFO] Обработка структуры базы данных...
[INFO] Обработка данных
…
[INFO] Сбор служебной информации...
…
[INFO] Принятие изменений...
[INFO] Построение индекса справки...
[INFO] Построение индекса справки успешно завершено
[INFO] Обновление конфигурации базы данных успешно завершено
```

⚠ В источнике неясно, какой именно ключ назван «специальным параметром»: в первом клиент-серверном примере уже присутствует `--apply`, во втором к нему добавлен `--force`; назначение каждого из ключей в главе отдельно не расписано (сверять со справочником `ibcmd`).

Ключи `ibcmd infobase create`, встречающиеся в главе:

| Ключ | Назначение (по тексту главы) |
|---|---|
| `--config` | Путь к конфигурационному файлу автономного сервера |
| `--data` | Каталог данных |
| `--database-path` | Каталог файловой базы данных |
| `--dbms`, `--database-server`, `--database-name`, `--db-user`, `--database-password` | Параметры доступа к СУБД |
| `--name` | Имя информационной базы |
| `--create-database` | Создать базу данных в СУБД (см. также п. 7.4.6: «в случае отсутствия создать базу данных») |
| `--load=<файл .cf>` | Загрузить конфигурацию из файла |
| `--restore=<файл .dt>` | Загрузить информационную базу из файла выгрузки (п. 7.4.6) |
| `--apply`, `--force` | Связаны с обновлением конфигурации базы данных (см. ⚠ выше) |

### 7.4.5. Загрузить конфигурацию из файла (*.cf)

```
ibcmd infobase config load --user=ibuser --password=123 --dbms=mssqlserver --database-server=dbServerName --db-user=dbUser --database-password=dbUserPassword --database-name=docs-db --data="D:\ss-data\cs-data" --name=docsIB 1Cv8.cf
ibcmd infobase config apply --user=ibuser --password=123 --dbms=mssqlserver --database-server=dbServerName --db-user=dbUser --database-password=dbUserPassword --database-name=docs-db --name=docsIB --data="D:\ss-data\cs-data" --force
```

- Первая команда (`config load`) загружает конфигурацию в информационную базу.
- Вторая (`config apply`) обновляет конфигурацию базы данных, при необходимости с реструктуризацией.

Вывод:

```
>ibcmd infobase config load …
[INFO] Загрузка конфигурации...
[INFO] Загрузка конфигурации успешно завершена
>ibcmd infobase config apply …
[INFO] Обновление конфигурации базы данных...
[INFO] Проверка корректности метаданных...
[INFO] Принятие изменений...
[INFO] Создано поколение конфигурации: 99bf6cd4045c8f43a86244a0dab4f24000000000
[INFO] Обновление конфигурации базы данных успешно завершено
```

Особенности:

- **Файл указывается без именованного параметра, последним значением в командной строке.** Так устроены все команды, которым нужен файл в качестве входного параметра.
- **Поколение конфигурации** позволяет проверить, что конфигурация не менялась с момента последнего обновления:
  - поколение, созданное при обновлении (`ibcmd infobase config apply`), видно в журнале обновления — строка `[INFO] Создано поколение конфигурации:`;
  - текущее поколение возвращает команда `ibcmd infobase config generation-id`;
  - сведения о созданном поколении выводятся также при выполнении `config update-db-cfg` агента конфигуратора и при подключении к автономному серверу по SSH.
- **Динамическое обновление** управляется параметром `--dynamic` команды `ibcmd infobase config apply`: им можно запретить динамическое обновление либо, наоборот, принудительно его выполнить (допустимые значения параметра в главе не приведены).

### 7.4.6. Создать информационную базу из файла выгрузки (*.dt)

```
ibcmd infobase create --dbms=mssqlserver --database-server=dbServerName --db-user=dbUser --database-password=dbUserPassword --database-name=docs-db --data="D:\ss-data\cs-data" --create-database --restore=1cv8.dt
```

Вывод:

```
[ INFO] Создание информационной базы...
[ INFO] Создание информационной базы успешно завершено
[ INFO] Загрузка информационной базы...
[ INFO] Загрузка информационной базы успешно завершена
```

Что происходит:

- на сервере СУБД `dbServerName` создаётся база данных `docs-db` (`--create-database` — создать базу, если её нет);
- доступ к СУБД — под пользователем `dbUser` с паролем `dbUserPassword`;
- после создания в базу загружаются данные из файла `1cv8.dt`, который лежит в каталоге, откуда запущена команда.

### 7.4.7. Загрузить в информационную базу данные из файла выгрузки (*.dt)

Offline-вариант (с полным описанием базы в командной строке):

```
ibcmd.exe infobase restore --user=ibuser --password=123 --dbms=mssqlserver --database-server=dbServerName --db-user=dbUser --database-password=dbUserPassword --database-name=docs-db --data="D:\ss-data\cs-data" --database-name=dbName .\1cv8.dt
```

Вывод:

```
[ INFO] Загрузка информационной базы...
[ INFO] Загрузка информационной базы успешно завершена
```

- dt-файл указывается без именованного параметра, последним значением в командной строке.
- ⚠ В примере источника ключ `--database-name` указан дважды с разными значениями (`docs-db` и `dbName`) — вероятная опечатка документации.

Если база в этот момент обслуживается работающим автономным сервером, загрузку выполняют через этот сервер — одной из команд:

```
ibcmd.exe --pid=ProcessID infobase restore .\1cv8.dt
ibcmd.exe --remote=ssh://Server1C:8282 infobase restore .\1cv8.dt
```

| Вариант | Где работает автономный сервер | Значение |
|---|---|---|
| `--pid` | На том же компьютере, что и `ibcmd` | `ProcessID` — номер процесса ОС запущенного автономного сервера |
| `--remote` | На другом компьютере | `ssh://Server1C:8282` — адрес настроенного SSH-шлюза автономного сервера, который выполнит загрузку |

### 7.4.8. Запуск автономного сервера в режиме отладки

Предполагается, что нужные шлюзы в конфигурационном файле (если он используется) не отключены; если шлюз отключён, его нужно явно включить в командной строке запуска (`--enable-direct-gate`, `--enable-http-gate`).

Отладка по TCP/IP:

```
ibsrv --dbms=mssqlserver --database-server=dbServerName --db-user=dbUser --database-password=dbUserPassword --database-name=docs-db --name=docs-db --data="D:\ss-data\cs-data" --debug=tcp
```

Отладка по HTTP:

```
ibsrv --dbms=mssqlserver --database-server=dbServerName --db-user=dbUser --database-password=dbUserPassword --database-name=docs-db --name=docs-db --data="D:\ss-data\cs-data" --debug=http
```

### 7.4.9. Запрос пароля пользователя СУБД через стандартный поток ввода

Проблема: пароль пользователя СУБД, от имени которого работает автономный сервер, лежит в конфигурационном или командном файле в открытом виде, что может быть недопустимо.

Решение — специальная команда, по которой пароль читается из стандартного потока ввода (`stdin`). В тексте источника она названа `--request-db-pwd`, в примерах записана как `--request-database-password`:

```
ibsrv --dbms=mssqlserver --database-server=dbServerName --db-user=dbUser --database-name=docs-db --name=docsIB --data=d:\ss-data\cs-data --request-database-password
```

- Сервер ждёт пароль пользователя СУБД (в примере — `dbUser`) из `stdin` и **не выводит никакого приглашения** к вводу.
- Пароль можно подать перенаправлением файла или вывода другой программы в `stdin` сервера:

```
ibsrv --dbms=mssqlserver --database-server=dbServerName --db-user=dbUser --name=docsIB --database-name=docs-db --data=d:\ss-data\cs-data --request-database-password < sqlpwd.txt
```

### 7.4.10. Указание расположения служебных каталогов автономного сервера

Сервисы автономного сервера хранят служебные данные на диске, каждый — в своём каталоге. Базовый каталог — **каталог данных автономного сервера**: по умолчанию все служебные каталоги лежат в нём.

- У каталога данных есть расположение по умолчанию (см. описание ключа `--data` в справочнике командной строки), но документация рекомендует для **каждой** информационной базы под автономным сервером задавать свой, уникальный каталог данных.
- Причина: служебные данные в каталоге данных и его подкаталогах специфичны для конкретной информационной базы. Использование того же каталога с другой базой может привести к непредсказуемым последствиям, вплоть до невозможности нормальной эксплуатации.
- Совет документации на случай, когда каталог данных оказался использован «повторно»: при **остановленном** автономном сервере либо очистить текущий каталог данных, либо назначить базе другой каталог данных. При очистке помнить, что файловая информационная база по умолчанию лежит в подкаталоге `db-data` каталога данных — **её удалять нельзя**.
- Перенос каталога данных переносит и все служебные каталоги, расположение которых не задано явно. Каждый служебный каталог можно разместить индивидуально:

| Ключ автономного сервера | Что хранится | Каталог по умолчанию (внутри каталога данных сервера) | Примечание |
|---|---|---|---|
| `--binary-storage-data` | Хранилище двоичных данных | `binary-storage-data` | — |
| `--clnt-notif-data` | Данные сервиса уведомлений клиентского приложения со стороны сервера | `clnt-notif-data` | — |
| `--data` | Каталог данных автономного сервера (фактически каталог данных информационной базы); в нём по умолчанию лежат остальные служебные каталоги | — | Обязательный параметр, кроме случаев, когда указан запущенный экземпляр автономного сервера или параметры сервера заданы через конфигурационный файл |
| `--db-path` | Каталог файловой базы данных «1С:Предприятия» | `db-data` | Относительный путь разворачивается относительно каталога данных сервера |
| `--ftext2-data` | Индекс полнотекстового поиска для версии 2 полнотекстового поиска в данных | `ftext2-data` | — |
| `--ftext-data` | Индекс полнотекстового поиска | `ftext-data` | — |
| `--log-data` | Журнал регистрации | `log-data` | — |
| `--openid-data` | Контексты OpenID-аутентификации | `openid-data` | — |
| `--session-data` | Сеансовые данные | `session-data` | — |
| `--temp` | Временные файлы информационной базы | `temp` | Временные файлы самого автономного сервера создаются в каталоге временных файлов пользователя, от имени которого запущен сервер; этот каталог переопределяется переменной окружения ОС `TEMP` |
| `--users-data` | Конфигурационные данные пользователей | `users-data` | — |

Напоминание из п. 7.3.3.2: пути служебных каталогов — единственное, чем **нельзя** управлять через конфигурационный файл; они задаются только ключами командной строки.

### 7.4.11. Публикация информационной базы

- «Публикация» для работы через веб-сервер выполняется автоматически при запуске автономного сервера; веб-сервером выступает сам автономный сервер.
- Доступны те же способы доступа, что и при обычной публикации: веб-клиент, тонкий клиент через веб-сервер, интернет-сервисы, стандартный интерфейс OData.
- Какие способы доступа разрешены — определяется параметрами конфигурационного файла (секция `http`).

Часть параметров публикации задаётся ключами командной строки `ibsrv`:

| Ключ | Назначение | По умолчанию | Значения / примеры |
|---|---|---|---|
| `--http-base` | Путь к ресурсу, по которому доступно приложение | `/` (веб-клиент по адресу `http://localhost:8314`) | `--http-base=/standalone/example` → адрес `http://localhost:8314/standalone/example` |
| `--http-port` | Сетевой порт доступа к приложению | `8314` | — |
| `--http-address` | Сетевой интерфейс, через который доступна публикация | `localhost` | `any` — все доступные сетевые интерфейсы; `xxx.xxx.xxx.xxx` — интерфейс с указанным адресом IPv4; `xxxx:xxxx:xxxx:xxxx:xxxx:xxxx:xxxx:xxxx` — интерфейс с указанным адресом IPv6 |

Пример. Сервер с файловой базой, запущенный так:

```
ibsrv --database-path="c:\db\ss-data\demo"
```

доступен только с того же компьютера по адресу по умолчанию. ⚠ В источнике здесь указан адрес `http://localhost:8341` — вероятная опечатка: порт по умолчанию во всех остальных местах главы — `8314`.

Чтобы база открывалась по адресу `http://<pc-addr>:8080/standalone/demo`:

```
ibsrv --database-path="c:\db\ss-data\demo" --http-base=/standalone/demo --http-port=8080 --http-address=<pc-addr>
```

`<pc-addr>` — адрес одного из сетевых интерфейсов компьютера, на котором работает автономный сервер (в источнике в команде написано `<pc-addrt>` — опечатка).

**Несколько публикаций одной информационной базы** автономный сервер обслуживать умеет, но задать это можно **только в конфигурационном файле**. Пример из документации (⚠ отступы восстановлены по смыслу, см. примечание в п. 7.4.1; в частности, принадлежность строк `publish` и `reuse-sessions` элементу списка `service` либо узлу `odata` определена по порядку строк, а не по отступам источника):

```yaml
server:
  address: localhost
database:
  dbms: PostgreSQL
  server: dbServerName
  name: dbBase
  user: postgres
  password: postgres
infobase:
  name: clusterDbName
  distribute-licenses: yes
  schedule-jobs: deny
http:
  - base: /lk
    odata:
      publish: true
      reuse-sessions:
        mode: dontuse
  - base: /partner
    web-services:
      service:
        - name: RemoteManagement
          alias: RemoteManagment.1cws
          publish: true
          reuse-sessions:
            mode: autouse
    odata:
      publish: true
      reuse-sessions:
        mode: dontuse
```

Параметры конфигурационного файла, которые встречаются в примерах главы (полное описание — в разделе о конфигурационном файле автономного сервера):

| Секция | Параметр | Значения в примерах |
|---|---|---|
| `server` | `address` | `localhost` |
| `server` | `port` | пусто; `8314` |
| `database` | `dbms` | `PostgreSQL`, `MSSQLServer` |
| `database` | `server`, `name`, `user`, `password` | сервер СУБД, имя базы, пользователь и пароль СУБД (пароль — открытым текстом) |
| `infobase` | `id` | UUID информационной базы |
| `infobase` | `name` | имя информационной базы (рекомендуется задавать всегда) |
| `infobase` | `distribute-licenses` | `yes` |
| `infobase` | `schedule-jobs` | `allow`, `deny` |
| `http` | `base` | путь публикации: `/webAccess`, `/lk`, `/partner`, `/clients` |
| `http` | `odata` → `publish` | `true` |
| `http` | `reuse-sessions` → `mode` | `dontuse`, `autouse` |
| `http` | `web-services` → `service` → `name`, `alias`, `publish` | `RemoteManagement`, `RemoteManagment.1cws`, `true` |
| `http` | `zones` → `specify`, `safe` | `true` / `false` (п. 7.4.12) |
| `features` | `direct-gate`, `http-gate`, `ssh-gate`, `extended-designer-features` | `true` / `false` (п. 7.3.5.2) |
| `debug` | — | секция настройки отладки (п. 7.3.6); состав в главе не раскрыт |
| `gates` | — | секция шлюзов (упомянута в п. 7.3.6.1); состав в главе не раскрыт |

### 7.4.12. Работа с разделителями

Работа с разделителями настраивается в конфигурационном файле автономного сервера, в секции `http.zones`.

Пример (⚠ отступы восстановлены по смыслу, см. примечание в п. 7.4.1):

```yaml
http:
  - base: /clients
    zones:
      - specify: false
        safe: false
      - specify: true
        safe: false
```

Что описано в примере:

- базовый каталог веб-доступа — `/clients`;
- в прикладном решении два разделителя;
- первый разделитель: в URL не указывается (`specify: false`), изменить его из встроенного языка нельзя (`safe: false`);
- второй разделитель: должен быть указан в URL (`specify: true`), изменить его из встроенного языка нельзя (`safe: false`).

| Параметр элемента `zones` | Смысл |
|---|---|
| `specify` | `true` — значение разделителя должно быть указано в URL доступа; `false` — не должно |
| `safe` | `false` — изменение разделителя из встроенного языка невозможно (значение `true` в главе не описано) |

Список разделителей информационной базы, которую обслуживает конкретный экземпляр автономного сервера:

```
ibcmd --pid=ProcessID infobase config data-separation list
```

`ProcessID` — идентификатор процесса экземпляра автономного сервера; утилита подключается к его информационной базе и читает из неё список разделителей.

### 7.4.13. Выгрузка и загрузка конфигурации в файлы

- Автономный сервер выгружает и загружает конфигурацию в XML-файлы **только в иерархическом формате**; линейный формат не поддерживается.
- Поддерживаются и полная, и частичная выгрузка/загрузка.

Полная выгрузка:

```
ibcmd infobase config export --user=ibuser --password=123 --config=config.yml d:\cfg_xml
```

Синхронизация конфигурации и каталога выгрузки (ключ `--sync`):

```
ibcmd infobase config export --user=ibuser --password=123 --sync --config=config.yml d:\cfg_xml
```

Обновление (а не полная перевыгрузка) каталога `d:\cfg_xml` выполняется, если одновременно:

- каталог содержит файл `ConfigDumpInfo.xml`;
- уникальные идентификаторы корневых объектов в конфигурации и в `ConfigDumpInfo.xml` совпадают;
- номера версий формата выгрузки в XML у конфигурации и в `ConfigDumpInfo.xml` совпадают;
- выгрузка в каталоге — в иерархическом формате;
- синхронизация не требует полной выгрузки конфигурации.

Полная загрузка (формат загружаемой выгрузки определяется автоматически):

```
ibcmd infobase config import --user=ibuser --password=123 --config=config.yml d:\cfg_xml
```

Эта команда **полностью заменяет** конфигурацию в информационной базе, описанной файлом `config.yml`.

Частичная загрузка (список файлов передаётся по конвейеру на вход утилиты):

```
type d:\fileList.lst|ibcmd infobase config import files --user=ibuser --password=123 --http-base-dir d:\cfg_xml
```

- загружаются только файлы, перечисленные в `d:\fileList.lst`;
- в `d:\fileList.lst` — полные пути к загружаемым файлам, по одному пути в строке;
- `d:\cfg_xml` — каталог с выгрузкой.
- ⚠ Имя ключа `--http-base-dir` приведено как в источнике; в главе оно не поясняется — сверять со справкой `ibcmd help`.

### 7.4.14. Получение списка сеансов

```
ibcmd --pid=ProcessID session list
```

`ProcessID` — идентификатор процесса экземпляра автономного сервера; утилита подключается к информационной базе этого сервера и возвращает список её сеансов. (По п. 7.3.5.1.1 такая команда требует пользователя с административными правами в базе.)

### 7.4.15. Получение списка блокировок

```
ibcmd --remote=ssh://Server1C:8282 lock list
```

`ssh://Server1C:8282` — адрес SSH-шлюза, через который доступен конкретный экземпляр автономного сервера. Настройка доступа по SSH описана в отдельном разделе документации.

### 7.4.16. Создание и загрузка расширения в информационную базу

```
ibcmd --pid=ProcessID infobase config extension create --user=ibuser --password=123 --name=PatchExtension1 --name-prefix=patchEx1 --purpose patch
ibcmd --pid=ProcessID infobase config load --user=ibuser --password=123 --extension=PatchExtension1 patchExt1.cfe
ibcmd --pid=ProcessID infobase config apply --user=ibuser --password=123 --extension=PatchExtension1 --force
```

Три шага: создание расширения (`extension create` с ключами `--name`, `--name-prefix`, `--purpose`; в примере назначение — `patch`), загрузка файла `.cfe` в расширение (`config load --extension=<имя>`), применение (`config apply --extension=<имя> --force`). `ProcessID` — идентификатор процесса экземпляра автономного сервера.

### 7.4.17. Миграция между информационными базами без выгрузки в dt-файл

Перенос информационной базы между двумя SQL-серверами напрямую, без промежуточного dt-файла:

```
ibcmd infobase replicate --data=d:\ss-data\cs-data --dbms=MSSQLServer --database-server=localhost --database-name=dbMsSql --database-user=msUser --database-password=123 --target-dbms=PostgreSQL --target-database-server=localhost --target-database-name=dbPgSql --target-database-user=pgUser --target-database-password=123 --target-create-database
```

| Ключ | Значение в примере | Смысл |
|---|---|---|
| `--data` | `d:\ss-data\cs-data` | Каталог данных автономного сервера |
| `--dbms` | `MSSQLServer` | СУБД-источник (Microsoft SQL Server) |
| `--database-server` | `localhost` | Сервер СУБД-источника |
| `--database-name` | `dbMsSql` | База-источник |
| `--database-user`, `--database-password` | `msUser`, `123` | Доступ к СУБД-источнику |
| `--target-dbms` | `PostgreSQL` | СУБД-приёмник |
| `--target-database-server` | `localhost` | Сервер СУБД-приёмника |
| `--target-database-name` | `dbPgSql` | База-приёмник |
| `--target-database-user`, `--target-database-password` | `pgUser`, `123` | Доступ к СУБД-приёмнику |
| `--target-create-database` | — | Создать базу данных в приёмнике, если её нет |

В примере обе СУБД работают на локальном компьютере. Имена пользователей и пароли даны только для демонстрации; в производственных базах такие параметры доступа использовать настоятельно не рекомендуется.

## Замеченные неясности и расхождения в источнике

Собрано в одном месте, чтобы при сверке других статей базы знаний не принимать эти места за установленный факт.

1. Примеры YAML: в текстовой копии источника потеряны отступы; вложенность в конспекте восстановлена по смыслу (п. 7.4.1, 7.4.2, 7.4.3, 7.4.11, 7.4.12).
2. Порт по умолчанию: везде `8314`, но в одном месте п. 7.4.11 написано `http://localhost:8341` — вероятная опечатка.
3. Имя ключа внешнего сервера отладки: `--debug-server-url` (п. 7.3.6.1) и `--debug-server=<dbgs-адрес>` (п. 7.3.6.2).
4. Ключ чтения пароля из `stdin`: `--request-db-pwd` в тексте и `--request-database-password` в примерах (п. 7.4.9).
5. Парные формы ключей `--database-user` / `--db-user` и `--database-path` / `--db-path` используются в разных местах главы без пояснения.
6. П. 7.4.4: каталог, в котором «будет создана база» (`D:\ss-data\fs-db\db-data`), не совпадает с путями в командах (`D:\ss-data\file-db\db-data`); неясно, какой из ключей `--apply` / `--force` назван «специальным параметром» обновления конфигурации базы данных.
7. П. 7.4.7: в примере ключ `--database-name` указан дважды с разными значениями.
8. П. 7.4.11: в команде опечатка `<pc-addrt>` вместо `<pc-addr>`.
9. П. 7.4.13: ключ `--http-base-dir` в команде частичной загрузки не поясняется.
10. П. 7.3.5.1.4: команда `restore-ib` описана как «загрузка конфигурации из файла».
11. П. 7.3.5.2: при отключении шлюза прямого подключения упомянута потеря подключения «толстым клиентом», хотя по п. 7.2 и 7.3.4 толстый клиент по TCP/IP не поддерживается вовсе.
12. П. 7.3.3.2: средством управления сервисом ОС названа утилита `sc` (это средство Windows); для Linux средства ОС в главе не названы.

## Что важно администратору Linux

1. **Отдельной установки нет.** Автономный сервер (`ibsrv`) и утилита `ibcmd` ставятся вместе с кластером серверов и запускаются из каталога `bin` нужной версии платформы; системные требования — как у кластера серверов.
2. **Под Linux автономный сервер не работает с Microsoft SQL Server** — остаются PostgreSQL (в примерах `--dbms=postgresql`, в конфигурационном файле `dbms: PostgreSQL`) и файловый вариант. Примеры главы с `--dbms=mssqlserver` на Linux-сервер напрямую не переносятся; применимость примера миграции `ibcmd infobase replicate` из MS SQL при запуске с Linux-хоста в главе не оговорена.
3. **Никогда не запускать `ibsrv` и `ibcmd` на базе, которая сейчас работает под кластером серверов** — документация прямо предупреждает о возможном разрушении базы данных. С одной базой одновременно работает только что-то одно: автономный сервер, `ibcmd` в offline-режиме, кластер серверов или прямое файловое подключение клиентов.
4. **Запуск демоном:** `ibsrv --daemon --config="<файл>" --data="<каталог данных>"`. У конфигурационного файла нет пути по умолчанию — `--config` нужно указывать при каждом запуске и сервера, и утилиты; к моменту запуска в файле должны быть все параметры. Встроенных средств регистрации сервиса и управления им у `ibsrv` нет — это задача средств ОС (какие именно для Linux — в главе не сказано).
5. **Каждой базе — свой каталог данных (`--data`).** В нём лежат журнал регистрации (`log-data`), индексы полнотекстового поиска (`ftext-data`, `ftext2-data`), сеансовые данные, временные файлы и т. д. Повторное использование каталога для другой базы ведёт к непредсказуемым последствиям. Без `--data`, `--database-path` и `--dbms` сервер поднимет файловую базу в `~/.1cv8/standalone-server/db-data` пользователя, от имени которого он запущен.
6. **Пути служебных каталогов задаются только ключами командной строки** (`--log-data`, `--temp`, `--session-data` и др.), в конфигурационный файл их вынести нельзя. Временные файлы самого сервера идут во временный каталог пользователя и переопределяются переменной окружения `TEMP`.
7. **По умолчанию веб-доступ слушает только `localhost:8314`.** Для доступа с других машин нужен `--http-address=any` либо конкретный IPv4/IPv6-адрес; порт и путь меняются через `--http-port` и `--http-base`. Несколько публикаций одной базы — только через секцию `http` конфигурационного файла.
8. **HTTPS автономный сервер не умеет** — нужен внешний веб-сервер в режиме reverse proxy. Аутентификация операционной системы также не поддерживается.
9. **Привычных средств администрирования кластера нет:** ни `ras`, ни консоли кластера, ни `V83.ComConnector`. Всё управление — через `ibcmd` в одном из трёх режимов: `--data` (offline, сервер должен быть остановлен; доступны все команды), `--pid=<PID>` (локальный работающий экземпляр), `--remote=ssh://<хост>:<порт>` (через SSH-шлюз). В двух последних режимах недоступны группа `config`, `infobase create` и `infobase repair`.
10. **Три шлюза (TCP/IP, HTTP, SSH) по умолчанию включены.** Каждый можно отключить (`--disable-direct-gate`, `--disable-http-gate`, `--disable-ssh-gate` или секция `features` конфигурационного файла); от шлюзов TCP/IP и HTTP зависит и доступность соответствующего вида отладки. При включённом SSH-шлюзе сервер принимает сторонние SSH/SFTP-клиенты и выполняет подмножество команд агента конфигуратора, включая `erase-data` и `restore-ib`.
11. **Пароль СУБД в конфигурационном файле хранится открытым текстом.** Альтернатива — ключ `--request-database-password` (в тексте также `--request-db-pwd`): пароль читается из `stdin` без приглашения, его можно подать перенаправлением файла или вывода другой программы.
12. **Имя базы задавать явно** (`--name` / `infobase.name`): при подключении по TCP/IP клиент должен указать ровно это имя, иначе подключиться не удастся (в примере с Конфигуратором вместо входа открывается диалог создания новой базы). По TCP/IP подключаются только тонкий клиент и Конфигуратор.
13. **Выгрузка в dt (`ibcmd infobase dump`) — не резервная копия**, и на время выгрузки не должно быть ни одного подключения к базе. Для резервного копирования документация отсылает к специальным инструментам (описаны в другом разделе).
14. **Удобно для скриптов:** код возврата `0` — успех, иначе ошибка с текстом в `stderr`; обычный вывод — в `stdout`; входные файлы (`.cf`, `.dt`, каталог XML) передаются последним позиционным аргументом; результат `ibcmd infobase config apply` содержит строку с идентификатором созданного поколения конфигурации, а текущее поколение даёт `ibcmd infobase config generation-id`.
15. **Перенос базы из кластера на автономный сервер:** `ibcmd server config import --cluster-data=<каталог данных кластера> --name=<имя базы> [--publication=<default.vrd>] --out=<файл.yml>` формирует готовый конфигурационный файл; строка подключения из атрибута `ib` файла `default.vrd` при этом игнорируется. Учитывать ограничения п. 7.2: нет фоновой реструктуризации, сервисов интеграции, «1С:Аналитики», ботов системы взаимодействия, внешнего (COM) соединения и обычного приложения.
