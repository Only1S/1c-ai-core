## Обзор приложения

Приложение описывает четыре вспомогательных сервиса. Три из них — Web-сервисы, которые нужно реализовать и опубликовать самостоятельно (в документации даны описания интерфейсов и демонстрационные примеры); четвёртый — встроенный HTTP-сервис метрик, который включается при запуске `ras` или `ibsrv`.

| Раздел | Что это | Кто обращается к сервису | Имя сервиса / ресурса | Тайм-ауты | Лицензия |
|---|---|---|---|---|---|
| 6.1 | Выдача списка общих информационных баз через Интернет | интерактивная программа запуска `1cv8s` | Web-сервис `WebCommonInfoBases` | 3 с на любой метод | только КОРП |
| 6.2 | Выдача дистрибутива клиентского приложения нужной версии | тонкий клиент `1cv8c` | Web-сервис `WebDistributiveLocation` | 3 с на любой метод; 600 с на загрузку файла дистрибутива | только КОРП |
| 6.3 | Внешнее управление сеансами (разрешить или запретить сеанс) | кластер серверов | имя Web-сервиса не специфицируется | 5 с по умолчанию либо значение параметра `tout` | пометки «только КОРП» в этом разделе источника нет |

## 6.1. Интернет-сервис получения списка общих информационных баз

### 6.1.1. Общая информация

- **Только для лицензии КОРП.**
- Зачем нужен: при удалённой работе (например, через веб-сервер) параметр `CommonInfoBases` файла `1cestart.cfg` не позволяет получить список общих информационных баз. Вместо него список публикуют через Интернет-сервис.
- В источнике сказано, что список можно получать и HTTP-запросами, и через Web-сервисы; в самом приложении раскрыт только вариант Web-сервиса (6.1.2). ⚠ в источнике неясно: вариант «через HTTP-запросы» в этом приложении не описан.
- При получении списка по HTTPS сертификат сервера, отдающего список, проверяется по сертификатам корневых удостоверяющих центров из системного хранилища соответствующей ОС.

### 6.1.2. Получение через Web-сервис

Нужно опубликовать специальный Web-сервис, возвращающий список.

#### 6.1.2.1. Описание функционирования

Кто и когда обращается:

- Интерактивная программа запуска `1cv8s` умеет брать список общих баз и из локальной сети, и через Интернет.
- Через Интернет список запрашивается **только при интерактивном запуске** и только если задан адрес сервиса — параметр `InternetService` или `WebCommonInfoBases` файла `1cestart.cfg`.

Обязательные требования к механизму:

| Требование | Суть |
|---|---|
| `WebCommonInfoBases.CheckInfoBases()` | вызов должен быть анонимным |
| `WebCommonInfoBases.GetInfoBases()` | вызов должен идти с аутентификацией |
| Пользователи | информационная база, отдающая списки, должна содержать пользователей, которым разрешено запрашивать список |

Последовательность работы:

1. `1cv8s` анонимно вызывает `CheckInfoBases()`.
   - Самый первый вызов для данного компьютера и данного пользователя: в `ClientID` и `InfoBasesCheckCode` передаётся `00000000-0000-0000-0000-000000000000`.
   - Последующие вызовы: передаются код клиента и код, идентифицирующий текущий (уже полученный) список баз.
2. Метод решает, надо ли обновлять список для этого клиента:
   - надо — выходной параметр `InfoBasesChanged` = Истина, `URL` = адрес Web-сервиса, где реализован `GetInfoBases()` (этот адрес требует аутентификации);
   - не надо — `InfoBasesChanged` = Ложь, `URL` = пустая строка.
3. Если обновление нужно, `1cv8s` вызывает `GetInfoBases()` по адресу из параметра `URL`.
4. `GetInfoBases()` сопоставляет пользователя, под которым прошла аутентификация Web-сервиса, с кодом клиента и возвращает три значения:
   - код клиента (если он ещё не был задан);
   - список общих информационных баз в формате v8i (описание формата — в другой главе документации);
   - код, идентифицирующий выданный список; он будет передан в `CheckInfoBases()` при следующей проверке.
   - При первом получении списка входной `ClientID` равен `00000000-0000-0000-0000-000000000000`.

Про код списка:

- Алгоритм определения «изменился ли список» не регламентирован, может быть любым.
- Программа запуска сама код не вычисляет — она только хранит значение, полученное при предыдущем вызове Web-сервиса, и возвращает его при следующей проверке.

Варианты сопоставления пользователя и списка:

| Вариант | Как работает | Что должно быть в списке пользователей базы сервиса |
|---|---|---|
| «Персональный» | пользователь входит под личным именем и паролем, получает личный список баз | все пользователи, которые могут запускать `1cv8s`, подключённую к Web-сервису |
| «Ролевой» | пользователь обозначает принадлежность к роли (например Оператор, Кладовщик), получает список, общий для роли | достаточно завести имена ролей |

Особенности публикации:

- Базу с Web-сервисом `WebCommonInfoBases` нужно опубликовать **в две разные публикации**: разные методы требуют разного уровня аутентификации (`CheckInfoBases()` — анонимно, `GetInfoBases()` — с аутентификацией).
- Анонимный доступ организуется явным указанием пользователя в файле `default.vrd` (в строке соединения с базой).
- Пользователь анонимного доступа не должен иметь возможности вызвать метод получения списка баз — только сообщать, изменился ли список для переданного `ClientID`.
- Ни одна из публикаций, обслуживающих `WebCommonInfoBases`, не должна давать возможность работать веб-клиентом.
- Если список используется мобильным клиентом, в файле списка для баз, которые должны отображаться в мобильном клиенте, должны быть корректные значения параметра `MobilePublicKey`.

#### 6.1.2.2. Описание Web-сервиса

- Имя Web-сервиса: `WebCommonInfoBases`.
- Тайм-аут выполнения любого метода: **3 секунды**.

**Метод `CheckInfoBases`** — вызывается программой запуска `1cv8s`, чтобы понять, нужно ли получать список общих баз.

| Параметр | Направление | Тип | Назначение |
|---|---|---|---|
| `ClientID` | входной | Строка | идентификатор клиента, для которого проверяется актуальность списка |
| `InfoBasesCheckCode` | входной | Строка | код, идентифицирующий список баз. Должен однозначно определять текущий список; при любом изменении списка код обязан смениться и не совпадать ни с одним кодом, ранее использованным для этого идентификатора клиента |
| `InfoBasesChanged` | выходной | Булево | признак, что список нужно получить заново |
| `URL` | выходной | Строка | адрес, по которому запрашивать список, если он изменился с прошлого обращения |
| возвращаемое значение | — | произвольный | значение игнорируется |

**Метод `GetInfoBases`** (в источнике поле «Описание» пустое; по смыслу 6.1.2.1 — выдаёт список).

| Параметр | Направление | Тип | Назначение |
|---|---|---|---|
| `ClientID` | входной/выходной | Строка | идентификатор клиента, для которого выдаётся список. Если не задан (равен `00000000-0000-0000-0000-000000000000`), метод должен назначить идентификатор и вернуть его в этом же параметре |
| `InfoBasesCheckCode` | выходной | Строка | код, идентифицирующий список, возвращаемый в параметре `InfoBases` |
| `InfoBases` | выходной | Строка | список общих информационных баз в формате v8i |
| возвращаемое значение | — | произвольный | значение игнорируется |

#### 6.1.2.3. Пример реализации

Источник подчёркивает: пример не законченный, только демонстрация механизма.

Конфигурация-пример: один справочник и один Web-сервис.

Справочник `СписокОбщихБаз`:

| Элемент | Значение |
|---|---|
| Тип кода | Строка, длина 36 символов |
| Реквизит `КодСписка` | тип УникальныйИдентификатор |
| Реквизит `СписокИБ` | Строка неограниченной длины |
| Остальное | по умолчанию |

Что хранится: стандартный реквизит Код — идентификатор клиента; `СписокИБ` — список общих баз; `КодСписка` — текущая версия списка. Версия — уникальный идентификатор, который меняется при каждой записи элемента: в обработчике `ПередЗаписью` модуля объекта реквизиту `КодСписка` присваивается новый УникальныйИдентификатор.

Web-сервис `WebCommonInfoBases`, операции `CheckInfoBases` и `GetInfoBases`: свойство «Тип возвращаемого значения» = `string`, флажок «Возможно пустое значение» установлен, остальное по умолчанию. Параметры — как в 6.1.2.2.

Сигнатуры из примера (обратите внимание: третий параметр в коде примера назван `InfoBaseChanged`, а в описании метода — `InfoBasesChanged`; ⚠ в источнике неясно, какое написание верное):

```bsl
Функция CheckInfoBases(ClientID, InfoBasesCheckCode, InfoBaseChanged, URL)
Функция GetInfoBases(ClientID, InfoBasesCheckCode, InfoBases)
```

Логика `CheckInfoBases` в примере:

1. Если и `ClientID`, и `InfoBasesCheckCode` равны нулевому идентификатору — это первое обращение: признак изменения = Истина, `URL` = `"/listservice2/ws/WebCommonInfoBases"`.
2. Иначе клиент ищется в справочнике по коду (`НайтиПоКоду(ClientID)`):
   - не найден — признак изменения = Ложь;
   - найден и `InfoBasesCheckCode` совпадает с `КодСписка` клиента — список не менялся: Ложь, `URL` = `""`;
   - найден, код отличается — Истина, `URL` = `"/listservice2/ws/WebCommonInfoBases"`.
3. Функция возвращает пустую строку.

Логика `GetInfoBases` в примере:

1. Если `ClientID` равен нулевому идентификатору — заводится новый элемент справочника: Код = строковое представление уникального идентификатора текущего пользователя ИБ (`ПользователиИнформационнойБазы.ТекущийПользователь()`), Наименование = имя пользователя, `СписокИБ` = пустая строка. После записи в выходные параметры кладутся `КодСписка`, `СписокИБ` и Код нового элемента.
2. Иначе клиент ищется по коду: не найден — `InfoBasesCheckCode` и `InfoBases` пустые; найден — возвращаются его `КодСписка` и `СписокИБ`.
3. Функция возвращает пустую строку.

Публикация: Web-сервис публикуется на веб-сервере **дважды**. В примере адреса такие:

| Адрес | Назначение |
|---|---|
| `http://localhost/listservice` | анонимный Web-сервис |
| `http://localhost/listservice2` | Web-сервис с аутентификацией |

В базе должны существовать пользователь `Анонимный` и, например, пользователи `Оператор`, `Кладовщик`, `Бухгалтер`.

`default.vrd` анонимной публикации (`http://localhost/listservice`) — пользователь задан прямо в строке соединения; у корневого элемента `point` стоит `enable="false"`, у вложенного `point` Web-сервиса — `enable="true"`:

```xml
<?xml version="1.0" encoding="UTF-8"?>
<point xmlns="http://v8.1c.ru/8.2/virtual-resource-system"
       xmlns:xs="http://www.w3.org/2001/XMLSchema"
       xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance"
       base="/listservice"
       ib="File=X:\DB\ListBase;Usr=Анонимный"
       enable="false">
  <ws>
    <point name="WebCommonInfoBases"
           enable="true"/>
  </ws>
</point>
```

`default.vrd` публикации с аутентификацией (`http://localhost/listservice2`) отличается только двумя атрибутами — пользователь в строке соединения не указан:

```xml
       base="/listservice2"
       ib="File= X:\DB\ListBase;"
```

Обязательные условия настройки:

- **На веб-сервере должна быть запрещена обработка HTTP-запроса `HEAD`** — как минимум для виртуальных каталогов, через которые идёт обращение к Web-сервису. Иначе Web-сервис использоваться не будет.
- В форме настройки окна запуска добавляется Интернет-сервис с адресом анонимной публикации и суффиксом `ws`: `http://localhost/listservice/ws/`.

Проверка работы: запускается программа запуска; на запрос имени и пароля для доступа к Web-сервису «1С:Предприятия» вводятся имена `Оператор`, `Кладовщик`, `Бухгалтер`. В справочнике `СписокОбщихБаз` появляются соответствующие записи. Если в реквизит `СписокИБ` каждого элемента поместить свой список в формате v8i, он будет добавляться в список баз программы запуска после аутентификации.

## 6.2. Интернет-сервис получения дистрибутива клиентского приложения

### 6.2.1. Общая информация

- **Только для лицензии КОРП.**
- Зачем нужен: при удалённой работе через веб-сервер, когда на сервере «1С:Предприятия» (или веб-сервере) сменили версию платформы, клиенту нужно автоматически получить дистрибутив новой версии. Поиск через параметр `DistributiveLocation` конфигурационных файлов в такой схеме может ничего не дать — тогда дистрибутив публикуют через Интернет-сервис.
- В источнике упомянуто получение и HTTP-запросами, и через Web-сервисы; подробно раскрыт Web-сервис (6.2.2), а получение по URL упомянуто как механизм № 2 в 6.2.2.1.
- При получении по HTTPS сертификат сервера проверяется по корневым удостоверяющим центрам из системного хранилища ОС.
- Прочие способы обновления клиентского приложения описаны в другой главе документации.

### 6.2.2. Получение через Web-сервис

Нужно опубликовать специальный Web-сервис, который сообщает, где лежит дистрибутив.

#### 6.2.2.1. Описание функционирования

Тонкий клиент `1cv8c` пытается установить нужную версию, если его версия не совпадает с версией кластера серверов «1С:Предприятия» или расширения веб-сервера. Механизмы применяются в таком порядке:

| № | Механизм | Где настраивается |
|---|---|---|
| 1 | Поиск дистрибутива в локальной сети | параметр `DistributiveLocation` файлов `1cestart.cfg` и `1cescmn.cfg` |
| 2 | Получение дистрибутива по URL | `default.vrd` (атрибут элемента `point`) или `conf.cfg` (параметры `PublishDistributiveLocation*`); **приоритет у значения из `default.vrd`** |
| 3 | Web-сервис получения дистрибутива | адрес сервиса в `1cestart.cfg` (параметр `InternetService` или `WebDistributiveLocation`) либо в диалоге настройки окна запуска |

Как клиент обрабатывает ответ Web-сервиса:

- `Size` = 0 → нужного дистрибутива нет; выдаётся ошибка о несоответствии версий клиентского приложения и сервера.
- `Size` ≠ 0 → пользователю показывается запрос на скачивание и установку с указанием размера дистрибутива. При согласии — скачивание, установка новой версии и перезапуск клиентского приложения нужной версии.

Ограничения:

- Тайм-аут операции загрузки файла дистрибутива — **600 секунд**.
- При загрузке дистрибутива **перенаправление (redirect) на стороне веб-сервера не поддерживается**.

#### 6.2.2.2. Описание Web-сервиса

- Имя Web-сервиса: `WebDistributiveLocation`.
- Тайм-аут выполнения любого метода: **3 секунды**.

**Метод `GetDistributiveInfo`** — вызывается тонким клиентом `1cv8c` для получения дистрибутива нужной версии в двух случаях (оба — при подключении через веб-сервер):

- клиент-серверный вариант: версии клиентского приложения и сервера не совпадают;
- файловый вариант: версии клиентского приложения и расширения веб-сервера не совпадают.

| Параметр | Направление | Тип | Назначение и допустимые значения |
|---|---|---|---|
| `DistributiveType` | входной | Строка | тип операционной системы, для которой нужен дистрибутив. Значения: `Linux`, `LinuxDEB`, `LinuxRPM`, `MacOS`, `Windows` |
| `Arch` | входной | Строка | архитектура ОС. Значения: `x86`, `x86_64` |
| `Version` | входной | Строка | номер версии клиентского приложения, дистрибутив которой нужен |
| `Size` | выходной | Число | размер дистрибутива в байтах; если запрошенного дистрибутива нет — вернуть `0` |
| `URL` | выходной | Строка | адрес для скачивания дистрибутива. Файл должен быть доступен веб-серверу, а у пользователя, который будет скачивать, должны быть права на скачивание этого файла |
| возвращаемое значение | — | произвольный | значение игнорируется |

Дистрибутив клиентского приложения — это zip-архив файлов дистрибутива (состав архива описан в другой главе документации).

#### 6.2.2.3. Пример реализации

Источник подчёркивает: пример не законченный, только демонстрация механизма.

Конфигурация-пример содержит только Web-сервис `WebDistributiveLocation` с одной операцией `GetDistributiveInfo` (тип возвращаемого значения `string`, флажок «Возможно пустое значение» установлен, остальное по умолчанию). Дистрибутивы лежат в каталоге, доступном веб-серверу.

Сигнатура из примера (первый параметр в коде назван `OS`, хотя в описании метода он называется `DistributiveType`):

```bsl
Функция GetDistributiveInfo(OS, Arch, Version, Size, URL)
```

Логика примера:

1. Заданы две переменные (в примере — Windows-значения): `КаталогДистрибутивов = "C:\inetpub\Distribs\"` и `URLДистрибутивов = "http://host/site/distribs/"`.
2. Имя архива формируется выражением:

```bsl
ИмяФайла = "tc-" + НРег(OS) + "-" + Arch + "-" + Version + ".zip";
```

3. Если файл с таким именем в каталоге существует — `Size` = размер файла, `URL` = `URLДистрибутивов + ИмяФайла`; иначе `Size = 0`, `URL = ""`.
4. Функция возвращает пустую строку.

Что нужно настроить:

- `КаталогДистрибутивов` — реальный путь к каталогу с архивами, как его видит Web-сервис; `URLДистрибутивов` — адрес того же каталога при обращении через веб-сервер.
- Имя файла должно иметь вид `tc-windows-x86-8.3.24.100.zip` или аналогичный (зависит от вида ОС и архитектуры запрашиваемого клиента). Такой шаблон имени — не требование платформы, а следствие кода демонстрационного Web-сервиса.
- Web-сервис публикуется на веб-сервере; в примере — по адресу `http://localhost/getdistr`.
- В форме настройки окна запуска добавляется Интернет-сервис с этим адресом и суффиксом `ws`: `http://localhost/getdistr/ws`.

Результат: когда клиенту понадобится дистрибутив, он обратится к Web-сервису; если в каталоге `КаталогДистрибутивов` на компьютере с Web-сервисом есть zip-архив нужного дистрибутива, файл будет передан на запросивший компьютер.

## 6.3. Web-сервис внешнего управления сеансами

### 6.3.1. Общая информация

- Для внешнего управления сеансами нужно реализовать Web-сервис с определённым набором методов и собственной логикой управления.
- Реализовать его можно как средствами «1С:Предприятия», так и сторонними средствами.
- Структура типа `Sessions` зависит от используемой версии Web-сервиса.
- Пометки «только КОРП» в этом разделе источника нет (в отличие от 6.1, 6.2 и 6.4).

### 6.3.2. Описание Web-сервиса

- Имя Web-сервиса **не специфицируется**.
- Тайм-аут выполнения методов: **5 секунд по умолчанию** либо значение, заданное параметром `tout` при вызове Web-сервиса.

Сводка по версиям интерфейса:

| Версия | Что входит / что добавлено |
|---|---|
| 1 | методы `onStartSession`, `onFinishSession`, `synchronize` |
| 2 | добавлены `onHibernateSession` и `onWakeupSession` — учёт перехода сеанса в состояние «Спящий» и возврата в рабочее состояние |
| 3 | в `onStartSession` добавлены параметры `SessionNumber` и `ClientIPAddress`; `ErrorDescription` может содержать сериализованную форматированную строку; изменена формулировка, для каких сеансов вызывается метод |
| 4 | в объект `Session` (элементы коллекции `CurrentSessions` метода `synchronize`) добавлены поля `SessionNumber` и `ClientIPAddress` |

В строке подключения сервиса из примера 6.3.3 присутствует ключ `wsver=4`; полное описание строки находится в другой главе документации.

#### 6.3.2.1. Версия 1

**Метод `onStartSession`** — вызывается кластером серверов при начале сеанса, которому требуется клиентская лицензия:

- конфигуратор;
- толстый клиент;
- внешнее соединение;
- тонкий клиент;
- веб-клиент;
- мобильный клиент;
- клиент системы «1С:Аналитика».

Метод решает, можно ли создать сеанс с такими параметрами, и сообщает решение кодом возврата.

| Параметр | Направление | Тип | Назначение |
|---|---|---|---|
| `CallNo` | входной | Число | порядковый номер вызова. При каждом вызове Web-сервиса кластером увеличивается на 1; по нему сервис может понять, что нужна синхронизация. Уникален в разрезе информационной базы |
| `ClusterID` | входной | Строка | идентификатор кластера серверов (строковое представление UUID) |
| `ClusterName` | входной | Строка | имя кластера серверов, в котором расположена информационная база |
| `InfoBaseName` | входной | Строка | имя информационной базы, для которой создаётся сеанс |
| `SessionID` | входной | Строка | идентификатор сеанса (строковое представление UUID) |
| `UserID` | входной | Строка | идентификатор пользователя (строковое представление UUID) |
| `UserName` | входной | Строка | имя пользователя |
| `AppID` | входной | Строка | имя приложения, пытающегося получить доступ к базе; возможные значения — см. описание функции глобального контекста `ПредставлениеПриложения()` |
| `Zone` | входной | Строка | начальные значения разделителей создаваемого сеанса в формате ключа командной строки `/Z` |
| `LanguageCode` | входной | Строка | код языка сообщений создаваемого сеанса |
| `ErrorDescription` | выходной | Строка | понятное пользователю описание причины запрета; заполняется, когда метод возвращает 1 |

Возвращаемое значение — Число:

| Код | Смысл | Что делает кластер |
|---|---|---|
| `0` | сеанс может быть создан | создаёт сеанс |
| `1` | сеанс не может быть создан | пользователь получает ошибку входа с текстом из `ErrorDescription`; если `ErrorDescription` пуст — с текстом «Начало сеанса запрещено сервисом внешнего управления сеансами» |
| `2` | требуется синхронизация | кластер вызывает `synchronize` со списком сеансов, **не включающим этот сеанс**, затем повторяет вызов `onStartSession` |

Про синхронизацию: вызовы внешнего управления сеансами между собой не синхронизируются; решать, нужна ли синхронизация списка сеансов, должен сам сервис. Исходная информация для этого — номер вызова `CallNo`: пропуск каких-то номеров после некоторого ожидания можно считать поводом для синхронизации.

**Метод `onFinishSession`** — вызывается при завершении сеанса.

| Параметр | Направление | Тип | Назначение |
|---|---|---|---|
| `CallNo` | входной | Число | порядковый номер вызова (уникален в разрезе информационной базы) |
| `ClusterID` | входной | Строка | идентификатор кластера серверов (UUID строкой) |
| `SessionID` | входной | Строка | идентификатор сеанса (UUID строкой) |

Возвращаемого значения нет.

**Метод `synchronize`** — синхронизирует данные о созданных сеансах между кластером серверов и Web-сервисом. Кластер вызывает его, когда `onStartSession()` вернул 2.

| Параметр | Направление | Тип | Назначение |
|---|---|---|---|
| `CallNo` | входной | Число | порядковый номер вызова (уникален в разрезе информационной базы) |
| `ClusterID` | входной | Строка | идентификатор кластера серверов (UUID строкой) |
| `ClusterName` | входной | Строка | имя кластера серверов, в котором расположена информационная база |
| `InfoBaseName` | входной | Строка | имя информационной базы, для которой синхронизируется информация о количестве сеансов |
| `CurrentSessions` | входной | `Sessions` | данные обо всех сеансах, созданных для этой базы с использованием внешнего управления сеансами. Содержит свойство `Content` — коллекцию объектов `Session` (по одному на сеанс); коллекция может быть пустой. Описание типа — в 6.3.2.5 |

Возвращаемого значения нет.

#### 6.3.2.2. Версия 2

| `SessionID` | входной | Строка | идентификатор сеанса (UUID строкой) |

Возвращаемого значения нет.

|---|---|---|---|
| `CallNo` | входной | Число | порядковый номер вызова; увеличивается на 1 при каждом вызове, по нему сервис может запросить синхронизацию. Уникален в разрезе информационной базы |
| `ClusterID` | входной | Строка | идентификатор кластера серверов (UUID строкой) |

Правила определения необходимости синхронизации те же, что для `onStartSession` (по пропускам в `CallNo`).

### 6.3.3. Пример реализации

Источник подчёркивает: пример не законченный, только демонстрация механизма.

Схема работы примера:

- администратор ограничивает число одновременных сеансов для информационной базы: указывает имя базы и допустимое количество сеансов;
- если базы в списке нет — число сеансов с ней не ограничено;
- в процессе работы в списке видно, какие сеансы существуют у базы.

Конфигурация-пример: один справочник и один Web-сервис.

Справочник `ДоступныеСеансы`:

| Элемент | Значение |
|---|---|
| Длина кода | 0 |
| Длина наименования | 50 |
| Реквизит `Количество` | Число(2), неотрицательное |
| Реквизит `ПоследнийНомерВызова` | Число(10), неотрицательное |
| Табличная часть `ТекущиеСеансы` | реквизиты: `SessionID` — Строка(40) переменной длины; `UserID`, `UserName`, `AppID`, `Zone`, `LanguageCode` — Строка неограниченной длины; `Hibernate` — Булево |

Что хранится: Наименование — имя информационной базы; `Количество` — максимум одновременных сеансов; `ПоследнийНомерВызова` — номер последнего вызова Web-сервиса (по нему определяется необходимость синхронизации между кластером и сервисом). Табличная часть — сеансы, которые сервис разрешил начать: строка создаётся в `onStartSession()` и удаляется в `onFinishSession()`. Решение о допуске нового сеанса принимается сравнением лимита и числа запомненных сеансов. При использовании второй версии интерфейса дополнительно фиксируются засыпание и пробуждение: при засыпании строка не удаляется, а помечается (`Hibernate`).

Web-сервис должен ссылаться на пакет XDTO `http://v8.1c.ru/SessionManagement`, описывающий объект `Sessions` (см. 6.3.2.5).

Сигнатуры операций из примера (соответствуют интерфейсу версий 1–2: без `SessionNumber` и `ClientIPAddress`; в коде примера метод синхронизации написан с заглавной буквы — `Synchronize`, в описании — `synchronize`):

```bsl
Функция onStartSession(CallNo, ClusterID, ClusterName, InfoBaseName, SessionID, UserID, UserName, AppID, Zone, LanguageCode, ErrorDescription)
Функция onFinishSession(CallNo, ClusterID, SessionID)
Функция Synchronize(CallNo, ClusterID, ClusterName, InfoBaseName, CurrentSessions)
Функция onHibernateSession(CallNo, ClusterID, SessionID)
Функция onWakeupSession(CallNo, ClusterID, SessionID, ErrorDescription)
```

Логика операций в примере:

| Операция | Что делает |
|---|---|
| `onStartSession` | Ищет базу по наименованию (`НайтиПоНаименованию(InfoBaseName, Истина)`). Нет в справочнике — ограничений нет, возврат `0`. Иначе увеличивает `ПоследнийНомерВызова` на 1; если результат не равен `CallNo` — возврат `2` (нужна синхронизация). Затем считает строки табличной части с `Hibernate = Ложь`: если «неспящих + 1» больше `Количество` — записывает объект, заполняет `ErrorDescription` текстом о превышении максимального числа сеансов и возвращает `1`; иначе добавляет строку сеанса (`SessionID`, `UserID`, `UserName`, `AppID`, `Zone`, `LanguageCode`, `Hibernate = Ложь`), записывает и возвращает `0` |
| `onFinishSession` | Запросом находит элементы справочника, в табличной части которых есть данный `SessionID`; удаляет соответствующие строки, записывает в `ПоследнийНомерВызова` значение `CallNo`. Возвращает `Неопределено` |
| `Synchronize` | Ищет базу по наименованию; нет — выход. Иначе очищает табличную часть и заново заполняет её из `CurrentSessions.Content` (переносятся `SessionID`, `UserID`, `UserName`, `AppID`, `Zone`, `LanguageCode`; признак `Hibernate` в коде примера не переносится), записывает `ПоследнийНомерВызова = CallNo`. Возвращает `Неопределено` |
| `onHibernateSession` | Тем же запросом находит элементы с данным `SessionID`, ставит строкам `Hibernate = Истина`, записывает `ПоследнийНомерВызова = CallNo`. Возвращает `Неопределено` |
| `onWakeupSession` | Тем же запросом ищет сеанс. Не найден — `ErrorDescription` с текстом о том, что старт сеанса не зафиксирован сервисом, возврат `1`. Если `ПоследнийНомерВызова + 1` не равен `CallNo` — возврат `2`. Иначе проверяет лимит: при превышении `Количество` — `ErrorDescription` о превышении максимального числа сеансов, возврат `1`; иначе снимает признак `Hibernate`, записывает `ПоследнийНомерВызова = CallNo`, возврат `0` |

⚠ в источнике неясно: в коде `onWakeupSession` переменная с именем `Неспящих` заполняется количеством строк, у которых `Hibernate = Истина`; пример заявлен как незаконченный, переносить его в рабочую систему без проверки логики нельзя.

Публикация и подключение (значения из примера):

| Параметр примера | Значение |
|---|---|
| Имя публикации | `sc` |
| Имя Web-сервиса | `SessionControl` |
| Пространство имён Web-сервиса | `http://v8.1c.ru/SessionManagement` |
| Обязательный пакет XDTO | `http://v8.1c.ru/SessionManagement` |
| Компьютер публикации | `localhost` |
| Управляемая клиент-серверная база | `TestDB` (любая, можно пустая) |

После публикации и проверки её корректности формируется строка, указывающая кластеру на Web-сервис (формат строки описан в другой главе документации). Строка из примера:

```text
wsdl=http://localhost/sc/ws/SessionControl?wsdl;ns=http://v8.1c.ru/SessionManagement;srvc=SessionControl;port=SessionControlSoap;wsver=4;
```

Части строки из примера. Официальное описание ключей находится в другой главе документации и в это приложение не входит; столбец «Чему соответствует» составлен только по совпадению значений с исходными данными примера:

| Ключ | Значение в примере | Чему соответствует в исходных данных примера |
|---|---|---|
| `wsdl` | `http://localhost/sc/ws/SessionControl?wsdl` | публикация `sc` на `localhost`, Web-сервис `SessionControl` |
| `ns` | `http://v8.1c.ru/SessionManagement` | пространство имён Web-сервиса |
| `srvc` | `SessionControl` | имя Web-сервиса |
| `port` | `SessionControlSoap` | ⚠ в источнике не пояснено (в тексте примера это значение отдельно не описано) |
| `wsver` | `4` | ⚠ в источнике не пояснено; по контексту раздела — номер версии интерфейса (версии 1–4 описаны в 6.3.2) |

Параметр `tout` (тайм-аут вызова методов, по умолчанию 5 с) упомянут только в 6.3.2; в строке примера его нет, и где именно он записывается, в этом приложении не показано.

Порядок действий в примере:

1. Создать конфигурацию сервиса, опубликовать Web-сервис, проверить публикацию.
2. Создать клиент-серверную информационную базу `TestDB`.
3. В консоли кластера в свойствах этой базы: в свойство **«Внешнее управление сеансами»** вписать строку `wsdl=…`, установить флажок **«Обязательное использование внешнего управления»**.
4. Запустить базу сервиса в режиме 1С:Предприятие и создать в справочнике `ДоступныеСеансы` элемент с Наименованием `TestDB` и `Количество` = 2.
5. Результат: в `TestDB` можно войти не более двух раз одновременно.

## 6.4. HTTP-сервис получения параметров производительности

### 6.4.1. Общая информация

- **Только для лицензии КОРП.**
- Платформа отдаёт показатели производительности кластера серверов по HTTP-запросам. Синонимы в документации: «показатели производительности», «метрики производительности», «метрики».
- Источники метрик:
  - сервер администрирования кластера серверов — `ras`;
  - автономный сервер — `ibsrv`.
- **Метрики файлового варианта информационной базы не поддерживаются.**
- Формат выдачи — OpenMetrics.

Адрес сервиса имеет вид `http://server.host:port/resource`:

| Часть адреса | Что это |
|---|---|
| `http://server.host:port` | адрес сервера администрирования кластера (`ras`) или соответствующего шлюза автономного сервера |
| `resource` | имя ресурса, при обращении к которому выдаются метрики; задаётся при настройке доступа к показателям производительности |

Как включить HTTP-сервис:

| Где | Что сделать |
|---|---|
| Сервер администрирования `ras` | запустить `ras` с явным указанием значения какого-либо из параметров управления сервисом, например `--monitor-base=/metrics`. Имя ресурса всегда должно начинаться с символа `/` |
| Автономный сервер `ibsrv` | запустить так, чтобы к автономному серверу был разрешён доступ по протоколу HTTP и был инициализирован шлюз показателей производительности. Делается параметрами командной строки запуска автономного сервера либо его конфигурационным файлом |

Остальные параметры управления сервисом (кроме `--monitor-base`) в этом приложении не перечислены; источник отсылает к разделам о запуске `ras` и о шлюзе монитора производительности автономного сервера.

Аутентификация:

- Если в кластере серверов **заданы администраторы** — запрос к HTTP-сервису требует аутентификации.
- Если администраторы кластера **не заданы** — запрос выполняется без аутентификации.
- Используется basic-аутентификация. Учётные данные — имя и пароль одного из администраторов кластера серверов.

Способы передать учётные данные:

| Способ | Как |
|---|---|
| Заголовок HTTP-запроса | заголовок `Authorization` со значением вида `Basic base64(username:password)`: `Basic` — признак basic-аутентификации; `username:password` — имя и пароль администратора кластера; `base64()` — эту пару нужно закодировать в Base64 |
| Встроенный язык «1С:Предприятия» | свойства `Пользователь` и `Пароль` объекта `HTTPСоединение` — в них имя и пароль одного из администраторов кластера |

Пример заголовка из документации:

```text
Authorization: Basic YWxhZGRpbjpvcGVuc2VzYW1l
```

Смотри также (по источнику):

- описание формата OpenMetrics: `https://github.com/OpenObservability/OpenMetrics/blob/main/specification/OpenMetrics.md`;
- раздел о запуске сервера администрирования кластера серверов;
- раздел о шлюзе монитора производительности автономного сервера.

### 6.4.2. Способы фильтрации метрик производительности

Метрики выбираются «языком запросов» — набором параметров в строке HTTP-запроса. Основные понятия:

- у каждой метрики есть имя и набор **меток**, у каждой метки — значение;
- отбор по значению метки одновременно оставляет только метрики, имеющие такую метку, и только те из них, где метка равна заданному значению;
- аналогия из документации: метки — как измерения регистра сведений, метрики — как его ресурсы;
- можно отбирать метрики и по именам, используя подмножество регулярных выражений.

Параметры запроса:

| Параметр | Назначение | Значения | По умолчанию |
|---|---|---|---|
| `<label>=<value>` | отбор по значению метки | только равенство, строгое соответствие значения | — |
| `filter=<value>` | отбор по имени метрики; значение — шаблон с операторами (см. ниже) | шаблон | — |
| `managers=<value>` | включить/выключить метрики менеджеров кластера | `true`, `1` — включить; `false`, `0` — выключить | `true` |
| `processes=<value>` | включить/выключить метрики рабочих процессов | `true`, `1` / `false`, `0` | `true` |
| `servers=<value>` | включить/выключить метрики рабочих серверов | `true`, `1` / `false`, `0` | `true` |
| `sessions=<value>` | включить/выключить метрики сеансов информационных баз | `true`, `1` / `false`, `0` | **`false`** |

Операторы шаблона в `filter`:

| Оператор | Смысл |
|---|---|
| `*` | ноль или более любых символов |
| `?` | один любой символ |
| `[!abc]` | любой символ, кроме указанных |
| `[abc]` | любой из указанных символов |
| `[a-z]` | любой символ из указанного диапазона |

Правила объединения параметров:

- несколько **одноимённых** параметров объединяются по **ИЛИ**;
- **разноимённые** параметры объединяются по **И**.

### 6.4.4. Примеры получения метрик производительности

Подготовка для кластера серверов:

1. Запустить кластер серверов, в котором есть информационная база.
2. Запустить одно или несколько клиентских приложений, работающих с этой базой.
3. Запустить сервер администрирования с включением метрик:

```bash
ras cluster --monitor-base=/monitor
```

Подготовка для автономного сервера — в командной строке запуска должен присутствовать параметр управления механизмом мониторинга (многоточие — остальные параметры запуска, в источнике не раскрыты):

```bash
ibsrv … --monitor-base=/monitor
```

Примеры запросов (в источнике использован адрес `localhost` и порт `1555`):

| Адрес | Что вернётся для кластера серверов | Что вернётся для автономного сервера |
|---|---|---|
| `http://localhost:1555/monitor` | показатели по рабочим серверам, менеджерам кластера, рабочим процессам, информационным базам | показатели по информационной базе |
| `http://localhost:1555/monitor?sessions=1` | то же плюс показатели по сеансам запущенных приложений | показатели по информационной базе и по сеансам запущенных приложений |
| `http://localhost:1555/monitor?sessions=1&filter=*total*` | только показатели, в имени которых есть слово `total` | то же |

Откуда берётся порт `1555` и как его изменить, в этом приложении не объясняется (источник отсылает к разделам о запуске `ras` и о шлюзе монитора производительности автономного сервера).

## Что важно администратору Linux

1. **Метрики кластера включаются одним параметром запуска `ras`**: `ras cluster --monitor-base=/monitor`. Имя ресурса обязано начинаться с `/`. Выдача — в формате OpenMetrics по адресу `http://<хост>:<порт>/<ресурс>` (в примерах документации — `http://localhost:1555/monitor`). Возможность доступна только при лицензии КОРП.
2. **Файловые базы метрик не дают.** Источники метрик — только `ras` (кластер серверов) и `ibsrv` (автономный сервер). У автономного сервера набор урезан: из метрик базы — `e1c_infobase_session_count` и `e1c_infobase_active_session_count`, у метрик сеансов нет меток `cluster` и `session_number`.
3. **Аутентификация метрик зависит от наличия администраторов кластера.** Заданы — нужен заголовок `Authorization: Basic <base64(имя:пароль)>` с учётными данными администратора кластера. Не заданы — метрики отдаются без аутентификации.
4. **Метрики сеансов по умолчанию выключены** (`sessions=false`), остальные группы (`managers`, `processes`, `servers`) включены. Чтобы увидеть сеансы, нужен параметр `?sessions=1`.
5. **Правила отбора**: одноимённые параметры запроса складываются по ИЛИ, разноимённые — по И; отбор по метке — только строгое равенство; `filter` принимает шаблон с `*`, `?`, `[abc]`, `[!abc]`, `[a-z]` (пример: `?sessions=1&filter=*total*`).
6. **Имена метрик нужно брать буква в букву**, включая написания `e1c_session_dmbs_transmitted_total`, `e1c_session_dmbs_received_total` и `e1c_process_available_perfomance` — иначе отбор по имени ничего не найдёт.
7. **Метрики, связанные с СУБД** (для связки с PostgreSQL): по сеансу — `e1c_session_dbms_calls_*`, `e1c_session_dbms_time_*`, `e1c_session_dbms_transaction_time_current` (время с момента захвата соединения с СУБД, 0 — не захвачено), `e1c_session_dmbs_transmitted_*`, `e1c_session_dmbs_received_*`; по рабочему процессу — `e1c_process_avg_db_call_time`; по блокировкам — `e1c_session_lock_time_*`, `e1c_process_avg_lock_time`.
8. **Состояние рабочих процессов** читается из `e1c_process_state` (`-1` ошибка, `0` пассивный, `1` активный) и метки `status` (`on` / `off` / `reserved`); по серверу есть готовые счётчики `e1c_server_error_process_count`, `e1c_server_active_process_count`, `e1c_server_passive_process_count`.
9. **Внешнее управление сеансами** подключается в свойствах информационной базы в консоли кластера: свойство «Внешнее управление сеансами» (строка вида `wsdl=…;ns=…;srvc=…;port=…;wsver=4;`) и флажок «Обязательное использование внешнего управления». Сервис отвечает кодами `0` (разрешить), `1` (запретить, текст в `ErrorDescription`), `2` (сначала синхронизация). Тайм-аут вызова — 5 с по умолчанию или значение `tout`.
10. **Версии интерфейса управления сеансами**: 1 — базовые три метода; 2 — учёт спящих сеансов (`onHibernateSession`, `onWakeupSession`); 3 — в `onStartSession` приходят номер сеанса и IP-адрес клиента, метод вызывается для всех сеансов, кроме фоновых заданий и WS-соединений; 4 — номер сеанса и IP-адрес клиента появляются и в объекте `Session` при `synchronize`. Сервис можно написать как на 1С, так и сторонними средствами.
11. **Сервис списка общих баз (`WebCommonInfoBases`) публикуется дважды**: анонимная публикация (пользователь прописан в `ib=` файла `default.vrd`) для `CheckInfoBases` и публикация с аутентификацией для `GetInfoBases`. Ни одна из них не должна давать работать веб-клиентом (в примерах `default.vrd` у корневого `point` стоит `enable="false"`, у `point` Web-сервиса — `enable="true"`). На веб-сервере для этих каталогов обязательно запретить метод `HEAD`, иначе сервис не используется.
12. **Сервис дистрибутивов (`WebDistributiveLocation`) различает Linux-пакеты**: `DistributiveType` принимает `Linux`, `LinuxDEB`, `LinuxRPM`, `MacOS`, `Windows`; `Arch` — `x86`, `x86_64`. Дистрибутив отдаётся zip-архивом; файл должен быть доступен веб-серверу и скачивающему пользователю; на загрузку 600 с, редиректы веб-сервера не поддерживаются; ответ `Size = 0` означает «дистрибутива нет».
13. **Порядок поиска дистрибутива тонким клиентом**: сначала `DistributiveLocation` (`1cestart.cfg`, `1cescmn.cfg`), затем URL из `default.vrd` или `conf.cfg` (`PublishDistributiveLocation*`, приоритет у `default.vrd`), и только потом Web-сервис (`InternetService` или `WebDistributiveLocation` в `1cestart.cfg`).
14. **Все три Web-сервиса должны отвечать быстро**: 3 с на метод у `WebCommonInfoBases` и `WebDistributiveLocation`, 5 с у сервиса управления сеансами. При HTTPS сертификат сервера проверяется по корневым удостоверяющим центрам из системного хранилища соответствующей ОС.
15. **Примеры в документации — Windows-ориентированные и незаконченные**: пути `X:\DB\ListBase`, `C:\inetpub\Distribs\`. Linux-вариантов путей источник не приводит; при переносе на Linux их нужно заменить своими, а логику примеров — проверить (см. раздел о расхождениях выше).
