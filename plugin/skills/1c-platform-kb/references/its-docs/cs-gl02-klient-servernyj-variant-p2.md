## 2.2.6. Масштабируемость кластера серверов

Два способа масштабирования:
- **вертикально** — нарастить мощность компьютера, на котором работает единственный рабочий сервер кластера;
- **горизонтально** — добавить в кластер один или несколько новых рабочих серверов.

Ключевые факты:
- Кластер сам выполняет все действия по масштабированию; администратор влияет на его поведение через **свойства рабочего сервера**.
- В список рабочих серверов можно добавлять серверы и менять свойства существующих. **Изменённые свойства действуют только на новые соединения и сеансы.**
- Удалять рабочий сервер нужно по особой процедуре, чтобы не оборвать аварийно пользователей, которых он обслуживает (ссылка на другой раздел документации).
- **Нельзя удалить последний рабочий сервер кластера с признаком «Центральный сервер».**
- При создании кластера по умолчанию рабочий сервер того компьютера, где создаётся кластер, автоматически попадает в список рабочих серверов и получает флажок **«Центральный сервер»**.
- Нагрузка между рабочими серверами распределяется автоматически; цель — минимальное время обслуживания клиентских приложений. Сервисы кластера распределяются по рабочим серверам равномерно — по типам сервисов, информационным базам и сеансам.
- При установке соединения с ИБ выбираются рабочие серверы с максимальной доступной производительностью **на момент выбора**. Уже существующие соединения могут быть перенесены на другой рабочий сервер (механизм — в 2.2.7).

## 2.2.7. Балансировка нагрузки в кластере

### 2.2.7.1. Доступная производительность рабочего процесса

У каждого рабочего процесса есть свойство **«Доступная производительность»** — показатель того, насколько быстро процесс выполняет эталонные операции по сравнению с другими рабочими процессами.

Состав эталонных операций:
- работа с памятью: выделение массива, его заполнение, освобождение;
- работа с файлами: создание, запись, удаление;
- оценка степени загрузки процессоров компьютера, где работает процесс, и количества потоков, ожидающих исполнения, — это значение **увеличивает** (корректирует в большую сторону) время выполнения эталонного вызова.

Числовые параметры механизма:

| Что | Значение |
|---|---|
| Формула | `Доступная производительность = 10 000 / (среднее за 5 минут время выполнения эталонных операций данным рабочим процессом)` |
| Частота замера эталонных операций | каждые 5 секунд |
| Окно усреднения | 5 минут |
| Доступная производительность рабочего **сервера** | равна производительности самого быстрого (с максимальным значением) рабочего процесса этого сервера |
| Порог «существенного» различия | более 25 % |
| Срок динамического перераспределения клиентов при изменении соотношения производительностей | не более 10 минут |

Поведение:
- Клиенты распределяются между рабочими процессами так, чтобы доступная производительность всех процессов была примерно одинаковой.
- При выключении рабочего процесса его клиенты динамически перераспределяются между оставшимися включёнными процессами.

**Только Windows:** пользователь, от имени которого работает сервер, должен входить в группу «Пользователи журналов производительности» (Performance Log Users); иначе степень загрузки процессора не определяется. Для Linux аналогичных требований в этом разделе не приводится.

### 2.2.7.2. Установка нового соединения

#### 2.2.7.2.1. Прямое соединение с сервером

> Примечание документации к разделу: «доступно только для лицензии КОРП». ⚠ В источнике неясно, к чему именно относится примечание — оно стоит перед описанием выбора режима распределения нагрузки.

Способ выбора рабочего процесса при новом соединении задаётся свойством кластера **«Режим распределения нагрузки»**. Допустимые значения:
- **«Приоритет по производительности»**;
- **«Приоритет по доступной памяти»**.

Сравнение режимов:

| Шаг | Приоритет по производительности | Приоритет по доступной памяти |
|---|---|---|
| Список подходящих рабочих серверов | сервер с максимальной доступной производительностью + серверы, у которых она меньше максимальной **не более чем на 25 %** | сервер с максимальной доступной производительностью + серверы, у которых она меньше максимальной **не более чем на 75 %** |
| Какие рабочие процессы рассматриваются | на каждом подходящем сервере выбирается «лучший» процесс (критерии ниже) | только процессы, уже обслуживающие нужную ИБ; если таких нет — все процессы на серверах списка |
| Куда назначается соединение | на лучший рабочий процесс **случайного** сервера из списка | на **случайный** рабочий процесс (из рассматриваемых) на сервере с **наибольшим объёмом свободной оперативной памяти** |
| Когда существующее соединение может быть переустановлено с другим процессом | текущий процесс выключен **или** его доступная производительность **менее 75 %** производительности самого производительного рабочего сервера | текущий процесс выключен **или** его доступная производительность **менее 25 %** производительности самого производительного рабочего сервера |

В обоих описаниях в источнике после формулировки списка стоит пометка в скобках «первый выбранный рабочий сервер» — ⚠ в источнике неясно, что именно она уточняет.

Критерии «лучшего» рабочего процесса (режим по производительности), в порядке перечисления в документации — предпочтительнее процесс, который:
1. уже обслуживает ИБ, с которой устанавливается соединение (а не тот, что её не обслуживает);
2. активный, а не резервный;
3. имеет больше соединений с этой ИБ;
4. имеет больше соединений с любыми ИБ.

Условия, при которых переустановка соединения возможна (для обоих режимов; должны выполняться **все**):
- клиентский поток в данный момент не исполняется на сервере;
- нет открытой транзакции;
- не создано ни одной временной таблицы.

#### 2.2.7.2.2. Соединение через расширение веб-сервера

Обращение к серверу от имени **нового сеанса**:
1. берётся любое соединение из пула соединений расширения веб-сервера;
2. если свободных соединений в пуле нет — создаётся новое соединение по правилам параметра кластера «Режим распределения нагрузки».

Обращение от имени **существующего сеанса**:
1. в пуле ищется соединение с тем же рабочим процессом, через который шёл предыдущий вызов; найдено — используется оно;
2. иначе выбирается рабочий процесс согласно режиму распределения нагрузки, причём приоритет у процесса, через который шло предыдущее обращение. Другой процесс выбирается, только если он **существенно лучше** «старого» (по производительности или свободной памяти). Если к выбранному процессу есть свободные соединения — берётся одно из них;
3. иначе создаётся новое соединение согласно режиму распределения нагрузки.

⚠ В источнике один и тот же параметр кластера назван то «Режим распределения нагрузки», то «Режим распределения загрузки» — по смыслу это одно свойство.

### 2.2.7.3. Запуск регламентных заданий при отсутствии активных сеансов

Кластер умеет «прореживать» запуск регламентных заданий в базах, где нет активных сеансов пользователей. Управляющие параметры кластера:
- **«Минимальный период запуска регламентных заданий»**;
- **«Максимальный сдвиг запуска регламентных заданий»**.

Определения:
- **Пассивная ИБ** — в ней нет не спящих сеансов пользователей и обслуживающих их соединений.
- **Активная ИБ** — все остальные случаи.

Что считается «сеансом пользователя» для этого механизма:

| Считаются сеансами пользователей | НЕ считаются сеансами пользователей |
|---|---|
| Конфигуратор | Сеансы через соединение «Модуль расширения веб-сервера» (в источнике: «…WS-соединение»), не являющиеся клиентскими приложениями: интернет-сервисы (HTTP- и Web-сервисы) |
| Толстый клиент | COM-соединение с временем работы **менее 20 секунд** |
| Тонкий клиент с прямым подключением к кластеру серверов | Фоновое задание (включая боты и сервисы интеграции) |
| Сеансы через соединение «Модуль расширения веб-сервера»: веб-клиент, запрос системы аналитики, клиент системы аналитики, мобильный клиент, тонкий клиент через веб-сервер | |
| COM-соединение с временем работы **более 20 секунд** | |

⚠ В источнике неясно: формулировка «соединение Модуль расширения веб-сервера WS-соединение» в строке про интернет-сервисы, по-видимому, склеена из двух названий видов соединений; случай COM-соединения длительностью ровно 20 секунд не оговорён.

Правила запуска:

| Ситуация | Поведение |
|---|---|
| Активная ИБ | Задания запускаются строго по расписанию |
| Пассивная ИБ, оба параметра = `0` | Задания запускаются строго по расписанию |
| Пассивная ИБ, параметры ненулевые | От момента последнего запуска задания по расписанию в ещё активной базе отсчитываются интервалы длиной «Минимальный период…». Все задания, которые по расписанию должны были стартовать в течение интервала, запускаются после его окончания через случайное время от `0` до «Максимальный сдвиг…». Запуски группируются, чтобы выполнить их за одну загрузку контекста ИБ. Задание одного объекта `РегламентноеЗадание` запускается не более 1 раза. Если заданий много — стартуют не одновременно, а с небольшим смещением |
| Перезапуск процесса менеджера кластера | Первый запуск регламентных заданий пассивной ИБ — через случайный интервал после старта менеджера кластера: от **60 секунд** (минимальная задержка) до **60 + «Максимальный сдвиг…» секунд** (максимальная задержка) |
| ИБ перешла из активного состояния в пассивное | Интервал «Минимальный период…» отсчитывается от момента запуска последнего регламентного задания в активной базе |
| ИБ перешла из пассивного состояния в активное | Все задания, ожидавшие запуска в рамках текущего интервала, выполняются вместе с ближайшим запуском регламентного задания по расписанию, но **не позднее чем через 20 секунд** после активации базы. Если заданий много — с небольшим смещением |

Пример из документации:

```
Задания:
  №1 — каждые 2 часа, старт в 00:00
  №2 — раз в 24 часа, старт в 01:00
Кластер:
  Минимальный период запуска регламентных заданий  = 3 часа (10 800 секунд)
  Максимальный сдвиг запуска регламентных заданий  = 1 час  (3 600 секунд)

Активная ИБ:
  №1: сутки 1 — 00:00, 02:00, 04:00, 06:00, 08:00, 10:00, 12:00, …, 20:00, 22:00; сутки 2 — 00:00, 02:00, 04:00 …
  №2: сутки 1 — 01:00; сутки 2 — 01:00 …

В 00:30 база стала пассивной. Пассивная ИБ:
  №1: сутки 1 — 03:30, 06:30, 09:30, 12:30, 15:30, 18:30, 21:30; сутки 2 — 00:30, 03:30, 06:30 …
  №2: сутки 1 — 03:30; сутки 2 — 03:30 …
```

⚠ В источнике неясно: для пассивной базы приведены фиксированные моменты (03:30 и далее с шагом 3 часа); как они соотносятся с отсчётом интервала от последнего запуска в активной базе (00:00) и со случайным сдвигом 0…1 час — в документации не пояснено.

### 2.2.7.4. Требования назначения функциональности

#### 2.2.7.4.1. Общая информация

**Лицензионные ограничения:**
- Полнофункциональное использование — только с лицензией **КОРП**.
- Серверная лицензия **ПРОФ** допускает ТНФ, только если **во всех** требованиях пусты свойства **«Имя ИБ»** и **«Значение дополнительного параметра»**. В частности, на ПРОФ разрешено выносить на отдельные рабочие серверы сервисы кластера (пример из документации — сервис лицензирования).

**Суть механизма.** Кластер предоставляет набор функциональных возможностей — *объектов требований*, размещением которых по рабочим серверам можно управлять (например, выполнять все фоновые задания на выбранном сервере). Чтобы направить соединение или сервис на рабочий сервер (или запретить это), для этого сервера создаётся *требование назначения функциональности* — оно задаёт, может или не может данный сервер выполнять ту или иную работу.

Из чего состоит требование:

| Поле | Назначение | Значения / примечания |
|---|---|---|
| **Объект требования** | К чему относится требование | Некоторые сервисы кластера (только те, для которых отмечена возможность переноса), клиентские соединения, а также произвольный объект требования (в примерах — «Любой объект требования»). В примерах встречаются: «Клиентское соединение с ИБ», «Сервис лицензирования», «Сервис работы с внешними источниками данных», «Сервис Дата акселератора», «Любой объект требования» |
| **Тип требования** | Как использовать рабочий сервер | «Не назначать», «Назначать», «Авто» (см. ниже) |
| **Имя ИБ** | Уточнение по информационной базе | Применимо к клиентским соединениям и ко всем сервисам кластера, способным быть объектом требования, **кроме сервиса лицензирования**. Имя ИБ **регистронезависимо** |
| **Значение дополнительного параметра** | Уточнение при размещении клиентского соединения, нового сеанса в сервисе сеансовых данных или сервиса Дата акселератора | Одно или несколько слов через точку `.`; правила сравнения — ниже |

Типы требования:

| Тип | Смысл |
|---|---|
| **Не назначать** | Сервер не будет обслуживать объект требования, подходящий под условия требования |
| **Назначать** | Сервер становится одним из кандидатов на обслуживание объекта (если таких серверов несколько) |
| **Авто** | Сервер может быть использован, если нет сервера с явным указанием использования («Назначать») |

Совет документации: «Авто» уместен, когда в списке требований сервера уже есть требование с более широкими условиями, а нужно исключение для более узких. Пример: сервер не обслуживает клиентские соединения всех ИБ, кроме одной, для которой обслуживание разрешено.

**Правила сравнения дополнительного параметра:**
- у размещаемого объекта (клиентского соединения, нового сеанса в сервисе сеансовых данных, сервиса Дата акселератора) есть собственный дополнительный параметр — слова, разделённые `.`;
- сравнение идёт **по словам, слева направо**;
- объект соответствует требованию, если **все слова параметра требования** совпали с соответствующими словами параметра объекта (т. е. требование задаёт «префикс по словам»);
- **пустое** значение в требовании соответствует любому значению параметра объекта.

**Значения дополнительного параметра — размещение нового сеанса в сервисе сеансовых данных:**

| Вид сеанса | Значение |
|---|---|
| Конфигуратор | `Designer` |
| Толстый клиент | `1CV8` |
| Тонкий клиент | `1CV8C` |
| Тонкий клиент при прямом подключении к серверу «1С:Предприятия» | `1CV8CDirect` |
| Веб-клиент | `WebClient` |
| COM-соединение | `COMConnection` |
| Вызов Web-сервиса | `WSConnection` |
| Вызов HTTP-сервиса | `HTTPServiceConnection` |
| Вызов стандартного интерфейса OData | `ODataConnection` |
| Бот системы взаимодействия | `BotConnection` |
| Мобильный клиент | `MobileClient` |
| Клиент системы «1С:Аналитика» | `AnalyticsSystemClient` |
| Запрос системы «1С:Аналитика» | `AnalyticsSystemQuery` |

**Применение требований.** Созданные требования начинают действовать только после операции **применения**, которая выполняется в консоли администрирования кластера (ссылка на другой раздел документации).

**Как кластер обрабатывает требования при размещении объекта:**
1. На всех серверах кластера просматриваются их списки требований. Обход серверов и требований — **в том порядке, в каком они расположены в консоли кластера**.
2. В каждом списке берётся **первое** требование, которому удовлетворяет размещаемый объект — по самому объекту, по информационной базе и по дополнительному параметру.
3. Полученный список рабочих серверов сортируется по типу требования: первыми идут серверы с явным «Назначать». Серверы, у которых подходящее требование — явный запрет («Не назначать»), из списка исключаются. Далее:
   - есть серверы с явным «Назначать» — объект обслужит один из них;
   - таких серверов нет — используются серверы с типом «Авто» либо серверы, для которых требований не задано.
4. При размещении **клиентского соединения** из доступных серверов выбирается тот, в составе которого есть рабочий процесс с наивысшей доступной производительностью (2.2.7.1); выбор процесса внутри сервера — 2.2.7.4.3.

**Клиентское приложение, инициировавшее размещение, завершается аварийно**, если:
- список рабочих серверов для объекта оказался пустым (нет ни одного сервера, способного обслужить объект) — объект не размещается, вызывается исключение;
- разместить объект на выбранном сервере невозможно (например, сервер вышел из строя) и альтернативных рабочих серверов нет.

#### 2.2.7.4.2. Назначение объектов требований

Что может быть объектом требования для сервисов кластера:
- сервис одного типа — если сервис не делится по информационным базам;
- сервис одного типа для одной ИБ — если сервис делится по информационным базам;
- сервис сеансовых данных;
- сервис лицензирования.

Правила распределения сервисов по подходящим рабочим серверам:

| Правило | Детали |
|---|---|
| Отбор серверов | Из серверов, отобранных по ТНФ, берутся работоспособные в данный момент; из них — серверы с **максимальным значением свойства «Приоритет»**. Если работоспособных серверов нет — попытка размещения сервиса заканчивается ошибкой |
| Равномерность | Среди отобранных серверов сервисы распределяются равномерно |
| Сервисы с поддержкой репликации | Могут назначаться на несколько серверов. Число серверов = **уровень отказоустойчивости кластера + 1**. Один экземпляр активный, остальные резервные; служебные данные сервиса реплицируются на резервные. Репликация **асинхронная**, синхронизация — **каждую секунду** |
| Сервисы без поддержки переноса (характеристика «Не переносится») | Назначаются на **все** рабочие серверы с установленным флажком «Центральный сервер» |
| Сервис сеансовых данных | Для каждого сеанса создаётся отдельный экземпляр сервиса. При отборе серверов учитываются дополнительные параметры требования. Из доступных выбираются серверы с **минимальным количеством обслуживаемых сервисов кластера**. Число серверов = уровень отказоустойчивости + 1 |
| Сервис лицензирования | Нужно **явно** выбрать рабочий сервер, к которому привязывается программная лицензия, и **явно** описать требованием размещение сервиса на этом сервере |
| Остальные сервисы | Назначаются в единственном экземпляре |

Когда происходит переназначение сервисов между рабочими серверами:

| Событие | Что переназначается | Как |
|---|---|---|
| Добавление рабочего сервера | Частичное переназначение сервисов | Автоматически |
| Удаление рабочего сервера из кластера или его недоступность | Только те объекты требований, которые обслуживал выбывший сервер | Автоматически |
| Добавление или удаление информационной базы в кластере | Частичное переназначение | Автоматически |
| Администратор выполнил полное или частичное применение требований | Переназначение (объём в источнике не уточнён) | Вручную, из консоли кластера |

#### 2.2.7.4.3. Назначение рабочих процессов

При запуске кластера на каждом рабочем сервере стартует **по одному рабочему процессу**, и начинается вычисление доступной производительности для каждого рабочего сервера (2.2.7.1).

Порядок установки соединения клиентского приложения с кластером:

1. **Выбор рабочего сервера** — по требованиям назначения и ограничениям по оперативной памяти.
   - Ограничения по памяти учитываются, только если соединение запрашивается к ИБ, к которой на выбранном рабочем сервере ещё **нет установленных соединений**.
   - Сервер, превысивший лимит использования оперативной памяти, исключается из списка — при условии, что есть другой сервер, лимит не превысивший.
   - Исключаются также серверы, которые не могут обслужить соединение по требованиям назначения.
2. **Список доступных рабочих процессов** выбранного сервера. Процесс доступен, если:
   - не достигнуто максимальное число обслуживаемых ИБ — свойство рабочего сервера **«Количество ИБ на процесс»**;
   - не достигнуто максимальное число обслуживаемых соединений — свойство рабочего сервера **«Количество соединений на процесс»**;
   - процесс не находится в состоянии подготовки к автоматическому перезапуску.
3. **Выбор процесса из доступных:** предпочтение — процессам, уже обслуживающим соединения нужной ИБ; если таких нет — берётся процесс с максимальным количеством обслуживаемых соединений.
4. **Если ни один процесс выбрать не удалось** — на этом рабочем сервере запускается новый рабочий процесс, он и обслужит соединение.

Соединение от имени **существующего сеанса** (если не удалось повторно использовать соединение предыдущего вызова сервера): предпочтение — рабочему процессу, обслуживавшему предыдущее соединение этого сеанса. Другой процесс может быть выбран, если его доступная производительность выше текущего **не менее чем на 25 %**.

**«Устаревшие» рабочие процессы:**
- Условие: на одном рабочем сервере **в течение 20 минут** существуют 2 рабочих процесса, у которых суммарное количество обслуживаемых соединений и различных ИБ меньше значений свойств «Количество соединений на процесс» и «Количество ИБ на процесс».
- Тогда процесс с меньшим числом соединений помечается как устаревший и будет остановлен после разрыва последнего соединения.
- Существующим соединениям устаревшего процесса при ближайшем серверном вызове «предлагается покинуть» его.
- Устаревший процесс не участвует в распределении запросов на обслуживание новых объектов требований.

При подсчёте числа обслуживаемых соединений учитываются и соединения, создаваемые отладчиком для проверки прав доступа на отладку.

|---|---|---|---|---|

Кластер из одного рабочего сервера: нужны первые два требования в указанном порядке. Одно-единственное правило с типом «Не назначать» применить не получится — такова особенность механизма требований.

#### 2.2.7.5.10. Назначение сеансов пользователей

Задача: `SRV1` обслуживает все сеансы пользователя с именем `ВнешнийСервис` (например, от его имени работают все HTTP- и Web-сервисы внешнего доступа к данным ИБ); `SRV2` — только пользователей, у которых «Ключ требования назначения» равен `Аналитики`.

| Сервер | Объект требования | Тип требования | Имя ИБ | Значение дополнительного параметра |
|---|---|---|---|---|
| SRV1 | Клиентское соединение с ИБ | Назначать | — | `UserName.ВнешнийСервис` |
| SRV2 | Клиентское соединение с ИБ | Назначать | — | `UserAssignmentRuleKey.Аналитики` |

- Чтобы правила действовали только для одной ИБ, нужно заполнить поле «Имя ИБ» именем этой базы.
- Ограничение: «Значение дополнительного параметра» — это либо **одно** значение `UserName.<имя>`, либо **одно** значение `UserAssignmentRuleKey.<имя>`. Комбинации значений, регулярные выражения и иные способы задать несколько вариантов **не поддерживаются**.

## 2.2.8. Профили безопасности

### 2.2.8.1. Общая информация

> Доступно только для лицензии **КОРП**.

**Зачем.** Прикладное решение использует внешние ресурсы: каталоги файловой системы, COM-объекты (на Windows), внешние компоненты, приложения ОС и т. д. По соображениям безопасности конкретному решению можно оставить только часть этих ресурсов. Типовые задачи из документации: отдельный каталог временных файлов для каждой области разделённой ИБ; перечень ресурсов Интернета, доступных решению.

**Что такое профиль безопасности.** Набор явно заданных разрешений на использование внешних ресурсов (с перечнем ресурсов), который назначается информационным базам, зарегистрированным в кластере. Создаёт профили администратор кластера.

| № | Разрешение | Свойство / примечание | Список ресурсов |

| 2 | Доступные ресурсы файловой системы сервера | Виртуальные каталоги, см. 2.2.8.2 | да |

| 4 | Доступные внешние компоненты | См. 2.2.8.4 | да |
| 5 | Внешние модули, исполнение которых возможно в небезопасном режиме | Внешние отчёты; внешние обработки; расширения конфигурации; код, исполняемый оператором `Выполнить()` и функцией `Вычислить()`. См. 2.2.8.5 | да |

**Логика флажка и списка** (для разрешений со списком ресурсов, на примере доступа к Интернету):

| Состояние | Результат |

### 2.2.8.2. Ресурсы файловой системы сервера

**Принцип — виртуальные каталоги.** В профиле безопасности описывается виртуальная файловая система из каталогов; каждый виртуальный каталог по заданным правилам отображается на реальную файловую систему. Прикладной код передаёт в функции путь в виртуальной ФС, платформа преобразует его в реальный путь и работает с ним.

- Прикладное решение **не может узнать**, в какой физический путь отображён виртуальный каталог.
- Если в профиле заданы виртуальные каталоги, доступ возможен **только к ним**; обращение к любому другому каталогу (реальному или виртуальному) невозможно.

**Параметры виртуального каталога:**

| Параметр | Назначение | Правила |
|---|---|---|
| **Логический URL** | Адрес, которым пользуется прикладное решение | Должен выглядеть как начало реального пути соответствующей файловой системы (Windows или Linux). Путь в прикладном коде должен начинаться со значения, **в точности совпадающего** с логическим URL. Уникален в пределах профиля |
| **Физический URL** | Физическое размещение логического URL в файловой системе сервера | Может содержать подстановочные символы (таблица ниже). При файловой операции все подстановки заменяются; каждая последовательность символов, недопустимых в URL, заменяется на `_`. Можно указывать как локальные каталоги компьютера с «1С:Предприятием», так и сетевые ресурсы — с учётом особенностей файловой системы и работы с сетью той ОС, где работает сервер |
| **Разрешено чтение данных** | Флажок | Разрешает или запрещает чтение файлов из виртуального каталога |
| **Разрешена запись данных** | Флажок | Разрешает или запрещает запись файлов в виртуальный каталог |

Пример точного совпадения (из документации): при логическом URL `\storage` путь `\storage\document.txt` попадёт в виртуальный каталог, а путь `storage\document.txt` — нет.

**Предопределённые логические URL** (используются методами системы):

| Логический URL | Что это | Каким методом используется |
|---|---|---|
| `/bin` | Каталог загрузочных модулей текущей версии «1С:Предприятия» | `КаталогПрограммы()` |
| `/temp` | Каталог временных файлов | `КаталогВременныхФайлов()` |

**Важно:** в общем случае прикладное решение само обязано следить за тем, чтобы физическое отображение виртуального каталога существовало.

### 2.2.8.3. COM-объекты сервера

**Только Windows** — возможность применима лишь для серверов под управлением ОС Windows; для сервера на Linux раздел неактуален. Кратко:
- Профиль может содержать список разрешённых классов COM-объектов. Если использование COM-объектов в профиле ограничено, создать можно только объекты из списка; попытка создать любой другой — исключение.
- Объект соответствует элементу списка, если совпадает «Компьютер COM-объекта» и совпадают непустые значения «Файл (моникер)» и «Идентификатор COM-класса».
- Параметры разрешённого класса: **«Имя»** (уникально в профиле); **«Файл (моникер)»** (используется методом `ПолучитьCOMОбъект()` при неуказанном параметре `ИмяКлассаCOM`); **«Идентификатор COM-класса»** (строка в формате реестра Windows без фигурных скобок; используется конструктором нового COM-объекта и `ПолучитьCOMОбъект()`); **«Компьютер COM-объекта»** (используется конструктором; `localhost` — текущий компьютер, пустая строка — любой компьютер). Про файл-моникер документация отсылает к MSDN (статья на английском языке).

### 2.2.8.4. Внешние компоненты

- Профиль может содержать список внешних компонент, разрешённых прикладному решению.
- Если использование внешних компонент в профиле ограничено, доступны только компоненты из списка. Вызов `ПодключитьВнешнююКомпоненту()` для компоненты вне списка — исключение.
- **Пустой список** = профиль не разрешает никакие внешние компоненты.

Параметры разрешённой внешней компоненты:

| Параметр | Описание |
|---|---|
| **Имя** | Имя внешней компоненты, уникальное в пределах профиля |
| **Контрольная сумма** | SHA1 разрешённой компоненты в формате base64 |

- Контрольную сумму можно получить объектом `ХешированиеДанных` и методом глобального контекста `Base64Строка()`.
- **Native API:** для каждого типа платформы, поддерживаемого компонентой, нужно **отдельное разрешение**. Компонента для всех платформ — это 4 разрешения: Windows 32 и 64 бит, **Linux 32 и 64 бит**.

### 2.2.8.5. Внешние модули

- Внешние модули здесь — внешние отчёты и обработки, а также расширения конфигурации.
- Профиль может содержать список внешних модулей, которые разрешено использовать из прикладного кода **без включения безопасного режима**.
- Если использование внешних модулей в профиле ограничено: без безопасного режима работают только модули из списка; попытка использовать модуль вне списка без безопасного режима — исключение.
- **Пустой список** = ни один внешний модуль нельзя использовать без включения безопасного режима.

**`Выполнить()` и `Вычислить()`** управляются этим же элементом профиля:
- флажок **«Разрешен полный доступ: к внешним модулям»** сброшен → `Выполнить()` и `Вычислить()` можно использовать только в безопасном режиме (явно включая его перед вызовом);
- если прикладное решение использует `Выполнить()` и `Вычислить()` в технологических целях (в небезопасном режиме) — профиль со сброшенным флажком «Разрешен полный доступ: к внешним модулям» для него применять **нельзя**.

Параметры разрешённого внешнего отчёта или обработки:

| Параметр | Описание |
|---|---|
| **Имя** | Имя внешнего модуля, уникальное в пределах профиля |
| **Контрольная сумма** | SHA1 разрешённого внешнего отчёта или обработки в формате base64 |

Как получить контрольную сумму:
- для отчёта/обработки — объект `ХешированиеДанных` и метод глобального контекста `Base64Строка()`;
- для расширения конфигурации — программным интерфейсом либо в Конфигураторе: главное меню — «Конфигурация» — «Расширения конфигурации» — «Действия» — «Показать контрольную сумму».

## Что важно администратору Linux

1. **Изменение свойств рабочего сервера не трогает уже работающих пользователей** — новые значения действуют только на новые соединения и сеансы (2.2.6). Последний рабочий сервер с флажком «Центральный сервер» удалить нельзя; любой рабочий сервер удаляют по особой процедуре, чтобы не оборвать сеансы.
2. **Доступная производительность — это замер реальной скорости сервера:** каждые 5 секунд процесс выполняет эталонные операции с памятью и файлами и учитывает загрузку процессоров и очередь потоков; значение = 10 000 / среднее время за 5 минут (2.2.7.1). То есть показатель зависит от скорости операций с памятью и файлами и от загрузки CPU на данном компьютере. Требование про группу Performance Log Users относится только к Windows.
3. **Пороги балансировки:** существенным считается различие более 25 %; перераспределение клиентов занимает до 10 минут. В режиме «Приоритет по производительности» в кандидаты попадают серверы в пределах 25 % от лучшего, в режиме «Приоритет по доступной памяти» — в пределах 75 %, и соединение идёт на сервер с наибольшим объёмом свободной оперативной памяти (2.2.7.2.1).
4. **Соединение не переедет на другой рабочий процесс**, пока на сервере исполняется клиентский поток, открыта транзакция или создана хотя бы одна временная таблица (2.2.7.2.1).
5. **Регламентные задания в «пассивных» базах могут запускаться не по расписанию** — это штатное поведение при ненулевых параметрах кластера «Минимальный период запуска регламентных заданий» и «Максимальный сдвиг запуска регламентных заданий». Чтобы задания всегда шли строго по расписанию, оба параметра должны быть `0` (2.2.7.3).
6. **Базу не делают активной** сеансы HTTP- и Web-сервисов, COM-соединения короче 20 секунд и фоновые задания (включая боты и сервисы интеграции). После перезапуска менеджера кластера первый запуск заданий пассивной базы откладывается на 60…(60 + максимальный сдвиг) секунд; после «пробуждения» базы накопившиеся задания стартуют не позднее чем через 20 секунд (2.2.7.3).
7. **Требования назначения функциональности не работают, пока не выполнено «применение»** в консоли кластера. Порядок требований важен: на каждом сервере берётся первое подходящее требование; имя ИБ регистронезависимо; дополнительный параметр сравнивается по словам слева направо, пустой — подходит всему (2.2.7.4.1).
8. **Лицензии:** полноценные ТНФ и профили безопасности — только КОРП. На ПРОФ требования допустимы лишь с пустыми «Имя ИБ» и «Значение дополнительного параметра» (например, вынос сервиса лицензирования на отдельный сервер) (2.2.7.4.1, 2.2.8.1).
9. **Ошибка в требованиях может аварийно завершать клиентские приложения:** если после обработки требований список рабочих серверов для объекта пуст или выбранный сервер недоступен и альтернативы нет — объект не размещается и возникает исключение (2.2.7.4.1).
10. **Сервис лицензирования закрепляют явно:** требование «Сервис лицензирования — Назначать» на сервере, к которому привязана программная лицензия; при активации лицензии указывается имя именно этого сервера, иначе кластер лицензию не использует (2.2.7.4.2, 2.2.7.5.3). В учебном примере таким выделенным сервером служит Linux-сервер `SRV2`.
11. **Число рабочих процессов определяется свойствами рабочего сервера** «Количество ИБ на процесс» и «Количество соединений на процесс»: при старте кластера — один процесс на сервер, новый запускается, когда ни один существующий процесс не доступен (лимиты достигнуты либо процесс готовится к автоматическому перезапуску). «Лишний» процесс через 20 минут помечается устаревшим и останавливается после ухода последнего соединения. Изоляция «одна база — один процесс» достигается значением «Количество ИБ на процесс» = 1 на каждом сервере (2.2.7.4.3, 2.2.7.5.5).
12. **Отказоустойчивость сервисов:** сервисы с репликацией и сервис сеансовых данных размещаются на (уровень отказоустойчивости + 1) серверах, репликация асинхронная с синхронизацией каждую секунду; непереносимые сервисы живут на всех центральных серверах; при отборе серверов учитывается свойство «Приоритет» (2.2.7.4.2).
13. **Дата акселератор на одиночном сервере запрещается двумя требованиями в строгом порядке:** сначала «Любой объект требования — Назначать», затем «Сервис Дата акселератора — Не назначать»; одно запрещающее правило применить нельзя (2.2.7.5.9).
14. **Профиль безопасности и файловая система Linux:** логический URL виртуального каталога должен выглядеть как начало реального пути в файловой системе ОС сервера и совпадать с началом пути в коде в точности; предопределены `/bin` и `/temp`. Существование физического каталога платформа не гарантирует — за ним следит прикладное решение. Каталоги с подстановками `%s`, `%c`, `%p` удаляются автоматически при завершении сеанса, соединения и выходе из безопасного режима соответственно (2.2.8.2).
15. **COM-объекты в профиле — только Windows.** Для внешних компонент Native API нужны отдельные разрешения на каждую платформу (для Linux — 32 и 64 бит отдельно), с контрольной суммой SHA1 в base64. Профиль со сброшенным «Разрешен полный доступ: к внешним модулям» нельзя назначать базе, конфигурация которой вызывает `Выполнить()`/`Вычислить()` вне безопасного режима (2.2.8.3 – 2.2.8.5).
