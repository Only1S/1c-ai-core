## 6.2.10.6. С помощью JWT

**Что это.** Токен — средство идентификации пользователя или отдельного сеанса в приложении. JWT (JSON Web Token) — стандарт токенов доступа на базе JSON, описан в RFC 7519 (https://datatracker.ietf.org/doc/html/rfc7519). Применяется для аутентификации в клиент-серверных приложениях.

**Ограничения и точки настройки.**

| Что | Значение |
|---|---|
| Где работает | Только в информационных базах, опубликованных на веб-сервере |
| Как передаётся токен | Параметр командной строки запуска клиентского приложения `AccessToken` |
| Где настраивается публикация | Файл `default.vrd` опубликованной базы |
| Корневой элемент настройки в `default.vrd` | `accessTokenAuthentication` |
| Свойство пользователя ИБ | «Аутентификация токеном доступа» (должно быть включено у тех, кому разрешён JWT) |
| Объект встроенного языка для выпуска токена | `ТокенДоступа` |

**Порядок настройки (5 шагов).**

1. Опубликовать информационную базу на веб-сервере.
2. Пользователям, которым разрешён вход по JWT, включить свойство «Аутентификация токеном доступа».
3. В `default.vrd` публикации создать элемент `accessTokenAuthentication` с корректными параметрами. Учитывать:
   - атрибут `authenticationUserPropertyName` элемента `issuer` — задаётся, если пользователя нужно искать не по имени пользователя ИБ, а по другому полю;
   - атрибут `name` элемента `issuer` (⚠ в источнике неясно: пункт оборван, пояснение к атрибуту отсутствует; из шага 4 следует, что это значение должно совпадать с эмитентом токена);
   - подчинённый элемент `accessTokenRecepientName` — уникальное имя приложения, которое будет использоваться при формировании JWT.
4. Для каждого пользователя подготовить токен доступа объектом `ТокенДоступа`.
5. Строковое представление токена передать пользователю — он указывает его как значение параметра `AccessToken` при запуске клиентского приложения.

**Соответствие свойств токена, настроек `default.vrd` и претензий (claims) JWT.**

| Свойство объекта `ТокенДоступа` | Откуда брать значение | Претензия полезной нагрузки |
|---|---|---|
| `Эмитент` | Значение атрибута `name` элемента `issuer` из `default.vrd` | `iss` |
| Список получателей | Значение элемента `accessTokenRecepientName` из `default.vrd` | `aud` |
| `КлючСопоставленияПользователя` | Значение ключевого поля нужного пользователя (какое поле — определяется атрибутом `authenticationUserPropertyName` элемента `issuer`) | `sub` |
| Остальные параметры токена | Заполнить корректно, затем получить строковое представление токена | — |

См. также в документации: описание работы с JWT; описание файла `default.vrd`.

## 6.2.10.7. По QR-коду

**Идея.** Работает связка «мобильное приложение (мобильный клиент), где пользователь уже аутентифицирован» + «другое клиентское приложение, в котором тот же пользователь хочет войти в ту же базу». Клиентское приложение показывает QR-код, пользователь сканирует его мобильным приложением — вход подтверждается фактом владения мобильным устройством с аутентифицированным приложением.

**Условия.**

- Информационная база опубликована на веб-сервере и специально настроена; настройка публикации — через `default.vrd`.
- Пользователь уже аутентифицирован в мобильном приложении, причём в той же информационной базе, в которую входит со второго устройства.
- Список мобильных приложений, пригодных для доступа к базе (для разных мобильных ОС), настраивается элементом `<mobileApps>` в `default.vrd`.

**Два этапа (сценария).**

| Этап | Последовательность |
|---|---|
| На мобильном устройстве нет нужного мобильного приложения | 1) В диалоге аутентификации выбирается вход по QR-коду. 2) Клиентское приложение показывает QR-код. 3) Пользователь сканирует его любым сканером QR-кодов и переходит по URL, зашитому в код. 4) Прикладное решение показывает ссылки на мобильные приложения, подходящие для доступа к этой базе (источник списка — `<mobileApps>` в `default.vrd`). 5) Пользователь выбирает и устанавливает приложение. 6) Далее — сценарий «приложение установлено». |
| На мобильном устройстве нужное приложение установлено | 1) Пользователь работает с нужной базой через мобильное приложение. 2) На другом устройстве запускает клиентское приложение и в диалоге аутентификации выбирает вход по QR-коду. 3) В мобильном приложении выбирает «Главное меню — Настройки и сервис — Войти на другом устройстве» и сканирует QR-код, показанный на другом устройстве. 4) Информационная база аутентифицирует новый сеанс пользователя. |

См. также: файл `default.vrd`.

## 6.2.10.8. Через электронную почту

Один из видов беспарольной аутентификации.

**Как выглядит для пользователя.**

1. В диалоге выбора пользователя выбирается этот вид аутентификации.
2. Вводится адрес электронной почты — тот, что был указан при создании пользователя.
3. Система отправляет на адрес письмо с кодом подтверждения.
4. Код вводится в форму, открывающуюся после отправки письма; при верном коде аутентификация пройдена.

**Что нужно настроить (оба пункта обязательны).**

- Разрешить такую аутентификацию в диалоге «Дополнительные настройки аутентификации».
- Включить возможность аутентификации через электронную почту у конкретного пользователя.

**Ограничение.** Не поддерживается в пакетном режиме запуска и при отключении стартовых диалогов при запуске клиентского приложения.

См. также: параметры пользователя; диалог выбора пользователя; дополнительные настройки аутентификации.

## 6.2.10.9. Двухфакторная аутентификация

### 6.2.10.9.1. Общая информация

- Платформа либо аутентифицирует пользователя сама, либо доверяет результату внешнего ресурса (операционная система или провайдер OpenID). В обоих случаях пользователь вводит логин и пароль; слабое место схемы — простые и повторяющиеся пароли.
- Двухфакторная аутентификация требует два из трёх типов аутентификационных данных:
  - то, что пользователь знает (логин и пароль);
  - то, чем он владеет (мобильный телефон, электронная почта);
  - то, что ему присуще (отпечаток пальца, портрет, рисунок радужки).
- Первый фактор проверяет сама платформа «1С:Предприятие»; для второго фактора используется сторонний сервис — **провайдер второго фактора**.
- **Провайдер второго фактора** — это HTTP-сервис с программным интерфейсом. Им может быть: информационная база «1С:Предприятия» с набором HTTP-сервисов (пересылка сообщений или аутентификация); сторонний сервис рассылки по SMS или электронной почте; сервис, генерирующий коды второго фактора; сервис, работающий с пользователем через своё мобильное приложение. Единственное требование — доступность через HTTP-запросы.
- **Область применения:** только для аутентификации средствами «1С:Предприятия» (стандартная аутентификация); работает в любом варианте информационной базы и для любого клиентского приложения.

### 6.2.10.9.2. Варианты использования второго фактора

Стандартная аутентификация (первый фактор): клиент запрашивает логин и пароль и передаёт их серверу → сервер проверяет → если второй фактор пользователю не нужен, вход разрешён. При включённой двухфакторной аутентификации первые два шага те же, затем применяется второй фактор одним из двух способов.

| | Вариант 1: второй фактор формирует и проверяет сервер «1С:Предприятия» | Вариант 2: аутентификацию выполняет провайдер |
|---|---|---|
| Роль провайдера | Только транспорт — доставить значение второго фактора пользователю | Сам аутентифицирует пользователя и сообщает серверу результат (успешно / неуспешно) |
| Что знает сервер 1С | И сервер, и пользователь знают канал доставки значения | Сервер не знает, какой вид второго фактора используется; способ доставки определяет провайдер. Сервер знает только, что существует доверенный сервис |
| Канал доставки | Электронная почта или SMS-сообщение | На усмотрение провайдера |

**Последовательность варианта 1.**

1. Сервер сообщает клиентскому приложению, что нужен второй фактор.
2. Клиентское приложение показывает форму ввода второго фактора.
3. Сервер формирует значение второго фактора (например, число) и отправляет его пользователю (e-mail или SMS).
4. Пользователь получает значение и вводит его в форму; клиент отправляет его серверу.
5. Сервер сравнивает введённое значение со сформированным.
6. При совпадении пользователь считается идентифицированным и получает доступ.

**Последовательность варианта 2.**

1. Сервер сообщает клиенту, что пользователь должен пройти второй фактор на стороне провайдера.
2. Клиент показывает форму, в которой пользователь должен выполнить действие после прохождения аутентификации у провайдера.
3. Сервер отправляет провайдеру HTTP-запрос с просьбой аутентифицировать пользователя.
4. Провайдер начинает процедуру аутентификации (способ — на его усмотрение).
5. По окончании пользователь сообщает об этом клиентскому приложению.
6. Клиент передаёт это серверу, сервер запрашивает у провайдера результат аутентификации.
7. Провайдер возвращает результат; при успехе пользователь идентифицирован и получает доступ.

### 6.2.10.9.3. Настройка второго фактора

Настройка состоит из трёх частей: шаблоны запросов к провайдерам → привязка шаблона к пользователю ИБ → параметризация запросов.

**Объект `ШаблонНастройкиВторогоФактораАутентификации`** (описывает HTTP-запрос к провайдеру; создаётся через `ШаблоныНастроекВторогоФактораАутентификации.СоздатьШаблон()`).

| Свойство | Назначение | Когда используется |
|---|---|---|
| `Имя` | Собственное имя шаблона — по нему шаблон идентифицируется при дальнейших действиях | Всегда |
| `HTTPЗапросНаАутентификацию` | Описание HTTP-запроса (объект типа `HTTPЗапрос`), начинающего применение второго фактора | Оба варианта |
| `МетодHTTPЗапросаНаАутентификацию` | HTTP-метод запроса к провайдеру | Оба варианта |
| `HTTPЗапросНаПроверкуРезультатаАутентификации` | Запрос проверки результата аутентификации; выполняется после того, как пользователь сообщил клиенту, что прошёл аутентификацию у провайдера | Только вариант 2 |
| `МетодHTTPЗапросаНаПроверкуРезультатаАутентификации` | HTTP-метод запроса проверки результата | Только вариант 2 |

Выбор варианта второго фактора делается именно набором заполненных свойств шаблона: только запрос на аутентификацию — вариант 1; плюс запрос на проверку результата — вариант 2.

**Особенности формирования HTTP-запросов.**

- HTTP-метод задаётся строкой (спецификация HTTP допускает собственные глаголы/методы).
- Текст запроса может содержать **параметры** — текст, начинающийся с символа `&` (например, `&user_name`). Параметры заменяются реальными значениями в момент отправки запроса. Смысл: запросы для разных пользователей почти одинаковы и отличаются только пользовательскими данными. Пример условного запроса отправки SMS: `http://provider.example.com/sendsms/&phone_number` — при отправке `&phone_number` заменяется на фактический номер телефона пользователя.
- Предопределённая переменная платформы **`&secret`** содержит значение второго фактора, сформированное платформой.

**Пример шаблона для варианта 1** (платформа формирует, отправляет, обеспечивает ввод и проверку):

```bsl
Запрос = Новый HTTPЗапрос;
Запрос.АдресРесурса = "&addr";
Запрос.УстановитьТелоИзСтроки("Введите значение &secret. Никому не говорите это значение!", "utf-8");
Провайдер = ШаблоныНастроекВторогоФактораАутентификации.СоздатьШаблон();
Провайдер.HTTPЗапросНаАутентификацию = Запрос;
Провайдер.МетодHTTPЗапросаНаАутентификацию = "POST";
Провайдер.Имя = "Запрос - ответ";
Провайдер.Записать();
```

Первые три строки формируют HTTP-запрос, остальные создают шаблон провайдера, отправляющий запрос методом POST, с именем «Запрос - ответ».

Для варианта 2 пример перерабатывается так: запрос на аутентификацию приводится к требованиям конкретного провайдера и дополнительно задаётся запрос на проверку результата аутентификации.

**Привязка к пользователю** — два свойства объекта `ПользовательИнформационнойБазы` (после установки объект пользователя нужно записать). Одному пользователю можно назначить несколько шаблонов и указать порядок их обработки.

| Свойство | Назначение |
|---|---|
| `НастройкиВторогоФактораАутентификации` | Массив объектов типа `НастройкаВторогоФактораАутентификации` (⚠ в источнике неясно: в тексте свойство названо `НастройкаВторогоФактораАутентификации`, в примере кода — `НастройкиВторогоФактораАутентификации`) |
| `ОбработкаНастроекВторогоФактораАутентификации` | Что делать платформе, если задано несколько провайдеров и первый по порядку обхода вернул ошибку. В примере используется значение `ТипОбработкиНастроекВторогоФактораАутентификации.ИспользоватьСледующийПриОшибке` (другие значения перечисления в этой части источника не перечислены) |

**Объект `НастройкаВторогоФактораАутентификации`** — источник значений для подстановки параметров.

| Поле | Назначение |
|---|---|
| `ИмяШаблонаНастройки` | Имя шаблона настройки провайдера — то, что указано в свойстве `Имя` шаблона |
| `Параметры` | Соответствие: столько элементов, сколько параметров в шаблоне, кроме `&secret`. Ключ — имя параметра без символа `&`, значение — значение переменной |

**Пример назначения двухфакторной аутентификации пользователю:**

```bsl
ПараметрыПровайдера = Новый Соответствие;
ПараметрыПровайдера.Вставить("addr", "http://example.com/resource");
НастройкаПользователя = Новый НастройкаВторогоФактораАутентификации;
НастройкаПользователя.ИмяШаблонаНастройки = "Вопрос - ответ";
НастройкаПользователя.Параметры = ПараметрыПровайдера;

НастройкиПользователя = Новый Массив;
НастройкиПользователя.Добавить(НастройкаПользователя);

Пользователь = ПользователиИнформационнойБазы.НайтиПоИмени("Продавец");
Пользователь.НастройкиВторогоФактораАутентификации = НастройкиПользователя;
Пользователь.ОбработкаНастроекВторогоФактораАутентификации = ТипОбработкиНастроекВторогоФактораАутентификации.ИспользоватьСледующийПриОшибке;
Пользователь.Записать();
```

⚠ в источнике неясно: в первом примере шаблон записан с именем «Запрос - ответ», а во втором примере пользователю назначается шаблон с именем «Вопрос - ответ» — имена не совпадают (вероятно, опечатка документации; по смыслу имя в `ИмяШаблонаНастройки` должно совпадать со свойством `Имя` шаблона).

**Где платформа подставляет значения параметров:**

- свойство `HTTPЗапрос.АдресРесурса`;
- свойство `HTTPЗапрос.Заголовки`;
- тело запроса объекта `HTTPЗапрос` (способ задания тела на подстановку не влияет);
- свойство `ШаблонНастройкиВторогоФактораАутентификации.МетодHTTPЗапросаНаАутентификацию`;
- свойство `ШаблонНастройкиВторогоФактораАутентификации.МетодHTTPЗапросаНаПроверкуРезультатаАутентификации`.

**Риски и оговорки.**

- Если назначенный пользователю провайдер второго фактора недоступен — пользователь не сможет войти в базу. «Недоступен» = любое событие, мешающее провайдеру выполнить задачу: нет Интернета от сервера до провайдера, нет Интернета от провайдера до пользователя, ошибка на стороне провайдера и т. п.
- Услуги стороннего провайдера могут быть платными, провайдер может накладывать собственные условия и ограничения — это вне рамок документации «1С:Предприятия».

### 6.2.10.9.4. Аутентификация OpenID и двухфакторная аутентификация

Если используется OpenID-аутентификация, второй фактор должен запрашивать OpenID-провайдер. Это верно и тогда, когда OpenID-провайдером служит информационная база «1С:Предприятия»: двухфакторную аутентификацию настраивают в той базе, которая выступает OpenID-провайдером.

## 6.2.10.10. Использование биометрии для быстрого входа в мобильном клиенте

На устройствах с биометрией (датчик отпечатка, сканер лица, сканер радужки и т. д.) в диалогах настройки информационной базы мобильного клиента и в диалогах аутентификации на мобильном устройстве появляется флажок **«Использовать биометрию»**.

**Механизм при включённом флажке.**

- После первого успешного входа введённые имена пользователей и пароли (информационной базы, OpenID и веб-сервера) помещаются в безопасное хранилище.
- При следующем входе:
  1. Сначала делается попытка входа без данных хранилища — проверяется, не требуется ли аутентификация вовсе и нет ли актуальных аутентификационных данных провайдера OpenID. Если актуальные данные на устройстве есть, биометрия будет запрошена только после истечения их времени жизни.
  2. Если шаг 1 не удался — предлагается биометрическая аутентификация через интерфейс мобильной ОС; запрашивается тот вид биометрии, который задан в настройках устройства.
  3. Пользователь отказался от биометрии → переход к стандартному диалогу (имя пользователя и пароль).
  4. Биометрия принята → из безопасного хранилища берутся данные прошлой успешной аутентификации и используются для входа.
  5. Биометрия не принята → данные прошлой успешной аутентификации удаляются из хранилища, затем переход к стандартному диалогу.

**Ограничение для OpenID Connect.** Биометрия не применяется при аутентификации через OpenID Connect: вход выполняется на защищённой веб-странице провайдера, куда нельзя автоматически подставить сохранённые логин и пароль; кроме того, OpenID Connect и так обеспечивает повторную аутентификацию на устройстве без ввода логина и пароля неограниченное время.

**Приоритет.** Если на мобильном устройстве поддерживается OpenID Connect — используется он. При отказе от OpenID Connect становится доступен быстрый вход по биометрии. Чтобы снова попробовать OpenID Connect, должна произойти неудачная попытка входа.

## 6.4. Работа с сеансами

### 6.4.1. Внешнее управление сеансами

**Лицензионные требования.** Для клиент-серверного варианта информационной базы требуется лицензия КОРП; для файлового варианта достаточно лицензии ПРОФ.

**Какие задачи решает.**

- Ограничение числа одновременно работающих пользователей одной информационной базы.
- Гарантированный запас лицензий (пример: при 100 лицензиях гарантировать вход двум пользователям с фиксированными именами).
- Другие аналогичные задачи.

**Как устроено.** Нужен специализированный Web-сервис, который разрешает или запрещает создание сеанса. Механизм работает и с клиент-серверными, и с файловыми базами.

Условия для файловой базы (одновременно):

- клиентское приложение «1С:Предприятие» версии 8.3.22 и новее;
- Web-сервис внешнего управления сеансами версии 4 и новее.

**Схема работы.**

1. При попытке начать сеанс платформа сообщает Web-сервису о необходимости создания сеанса и передаёт параметры, описывающие сеанс (имя информационной базы, имя пользователя, IP-адрес клиентского приложения и т. д.).
2. Web-сервис решает — разрешить или запретить — и возвращает управление. При необходимости ведёт учёт созданных сеансов в нужных разрезах.
3. При завершении сеанса платформа также уведомляет Web-сервис.
4. При переводе сеанса в состояние «Спящий» и выходе из него платформа уведомляет Web-сервис о каждом событии — только если Web-сервис поддерживает протокол версии 2 и новее.

В итоге система внешнего управления точно знает количество сеансов в обслуживаемых базах.

**Для каких сеансов вызывается сервис** — только для требующих клиентскую лицензию:

- конфигуратор;
- толстый клиент;
- внешнее соединение;
- тонкий клиент;
- веб-клиент;
- мобильный клиент;
- клиент системы «1С:Аналитика».

При старте сеансов других видов сервис не вызывается.

**Где настраивается.**

| Вариант ИБ | Место настройки |
|---|---|
| Файловый | Конфигурационный файл `conf.cfg` |
| Клиент-серверный | Свойства информационной базы кластера серверов |

Описание самого Web-сервиса внешнего управления сеансами — в отдельном разделе документации (в этой части не приводится).

### 6.4.2. Блокировка установки сеансов пользователями

#### 6.4.2.1. Вручную, для всех

**Назначение.** Запретить установку новых сеансов с информационной базой и показать пользователям сообщение о причине. Типовой случай — административные работы: текущие пользователи должны завершить сеансы, а новые не должны подключаться.

**Интерактивный способ.**

- В клиент-серверном варианте блокировка устанавливается утилитой администрирования кластера серверов «1С:Предприятия».
- Вход в обход блокировки: параметр командной строки `UC` и параметр строки соединения `UC`.
- Если при установке блокировки задан непустой **код разрешения**, его нужно передать в параметре `UC`. Код с пробелами заключается в кавычки.
- Для веб-клиента и тонкого клиента, работающего через веб-сервер, помимо параметра `UC` в командной строке запуска, код разрешения можно указать в параметре `UC` строки соединения файла-дескриптора. В этом случае рекомендуется выполнять дополнительную публикацию информационной базы на веб-сервере.

Пример: блокировка начала сеансов установлена, код разрешения `123` — для входа в обход блокировки в командной строке запуска клиентского приложения указывается:

```
/UC123
```

**Программный способ** (работает в любом режиме информационной базы).

| Элемент встроенного языка | Назначение |
|---|---|
| Объект `БлокировкаСеансов` | Создаётся конструктором; в нём задаются свойства блокировки установки соединений |
| Свойство `БлокировкаСеансов.Сообщение` | Сообщение пользователю; может быть простой текстовой строкой или форматированной строкой |
| Метод глобального контекста `УстановитьБлокировкуСеансов()` | Устанавливает созданную блокировку |
| Метод глобального контекста `ПолучитьБлокировкуСеансов()` | Возвращает установленную блокировку |

#### 6.4.2.2. Автоматически, при попытке подбора пароля

Механизм защиты от перебора пароля. **Работает только в клиент-серверном варианте информационной базы.**

**Параметры** (диалог: Главное меню — Администрирование — Параметры информационной базы):

| Параметр | Назначение | Значения / примечания |
|---|---|---|
| Максимальное количество неуспешных попыток аутентификации | Сколько раз подряд можно ввести неверный пароль до блокировки | Блокировка срабатывает на N-й неудачной попытке подряд (N — значение параметра). При N = 3 пользователь блокируется после 3-й неудачной попытки. Сообщение о блокировке показывается начиная с попытки N+1. **0 — механизм отключён**, контроль числа неудачных попыток не ведётся |
| Длительность блокировки при превышении количества неудачных попыток аутентификации (в секундах) | Сколько времени пользователь не сможет пытаться аутентифицироваться после исчерпания попыток | В секундах |
| Коды дополнения имен пользователя при блокировке аутентификации | Дают заблокированному пользователю ещё один блок попыток | Коды разделяются символом `;`. «Дополнительный» пользователь = реальное имя заблокированного пользователя + один из кодов дополнения. Ему даётся столько же попыток, сколько обычному; после их исчерпания он тоже блокируется |

**Как работает.**

1. Злоумышленник вводит имя пользователя и перебирает пароли; при достижении лимита ошибок имя пользователя блокируется системой.
2. Настоящий пользователь при входе под своим именем и верным паролем получает сообщение, что пользователь заблокирован.
3. Если в базе настроены коды дополнения, пользователь вводит своё имя, дополненное кодом.

**Правила разбора кодов дополнения.**

- Анализ кода дополнения начинается только тогда, когда введённое имя **не найдено** в списке пользователей информационной базы.
- От такого имени последовательно «вычитаются» все коды дополнения из настроек, и проверяется, есть ли пользователь ИБ с получившимся именем.
- Следствие 1: не создавать коды дополнения, совпадающие с окончанием имени реального пользователя — если такого пользователя заблокируют, войти с кодом дополнения он не сможет.
- Следствие 2 (рекомендация): начинать код дополнения с «технических» символов, которых не бывает в именах пользователей, например `!`, `^` и т. п.

**Просмотр блокировок.**

- Конфигуратор: Главное меню — Администрирование — **Блокировки аутентификации**. Форма доступна пользователю с правом `Администрирование` или `АдминистрированиеДанных`.
- Информация о блокировках пользователей также попадает в журнал регистрации.

**Где хранится состояние и что из этого следует.** Сведения о заблокированных пользователях хранит **сервис вспомогательных функций кластера серверов**. Поэтому:

- если заблокирован единственный администратор, для входа под ним во время блокировки нужно **перезапустить кластер серверов**;
- счётчик ошибочных попыток ведётся с момента последнего успешного входа и не имеет срока давности; однако **перезапуск кластера серверов сбрасывает все счётчики** для всех пользователей информационной базы.

**Управление из встроенного языка.**

| Элемент | Назначение |
|---|---|
| Объект глобального контекста `БлокировкаАутентификации` | Управление механизмом блокировок |
| Методы `ПолучитьНастройки()` / `УстановитьНастройки()` | Чтение и изменение настроек механизма |
| Метод `ПолучитьБлокировки()` | Список текущих блокировок — массив объектов `БлокировкаАутентификацииПользователяИнформационнойБазы` |
| Метод `Разблокировать()` объекта `БлокировкаАутентификацииПользователяИнформационнойБазы` | Принудительная разблокировка конкретного пользователя |

Порядок принудительной разблокировки всех или выбранных пользователей: получить список текущих блокировок → по свойствам объектов отобрать нужных пользователей → вызвать для них `Разблокировать()`.

### 6.4.3. Завершение сеанса при бездействии

**Лицензионное требование.** Доступно только для лицензии КОРП.

**Назначение.** Отключать пользователя, который некоторое время не выполняет интерактивных действий: для экономии лицензий и для снижения риска несанкционированного доступа.

**Параметры информационной базы (оба нужно задать):**

| Параметр | Назначение |
|---|---|
| Время завершения сеанса при бездействии | Интервал, по истечении которого сеанс без активности пользователя будет завершён |
| Время предупреждения о завершении сеанса при бездействии | Через какой интервал предупредить пользователя, что сеанс будет автоматически завершён, если он не возобновит работу |

(Единицы измерения, значение 0 и методы встроенного языка — см. раздел 6.6.3.)

**На какие сеансы действует.** Только клиентские сеансы в приложениях: тонкий клиент, толстый клиент, мобильный клиент, мобильное приложение. **Сеанс «Конфигуратор» таким образом завершён быть не может.**

**Что считается пользовательской активностью.**

| Клиент | Активность |
|---|---|
| Тонкий и толстый клиент | Нажатия клавиш, движение мыши в окне приложения, участие в видеоконференции системы взаимодействия |
| Мобильный клиент и мобильное приложение | Нажатие экранных кнопок, прокрутка форм, касания различных частей форм |

**Поведение.** В диалоге предупреждения показывается таймер обратного отсчёта. По его истечении сеанс завершается, но само приложение не закрывается: выводится диалог о том, что работа завершена из-за неактивности, с предложением завершить работу или перезапустить клиентское приложение.

**Предостережение.** Не рекомендуется одновременно включать сохранение аутентификации и завершение сеанса при бездействии, если цель последнего — защита от несанкционированного доступа: с сохранённой аутентификацией злоумышленник всё равно получит доступ к данным, принудительное завершение сеанса не поможет.

См. также: параметры информационной базы; сохранение аутентификации.

## 6.5. Региональные установки информационной базы

**Вызов:** Администрирование — **Региональные установки ИБ** (рис. 73).

**На что влияет:** формат отображения даты, времени, чисел, логических констант, а также порядок сортировки строк в списках информационной базы.

**Общее правило:** если свойство не задано, формат чисел, даты и времени берётся из установок по умолчанию, принятых в «1С:Предприятии» для указанного языка (страны). Язык (страна) определяется при создании информационной базы. В нижней части диалога показываются примеры отображения числа, даты и времени с выбранными установками.

### Свойства диалога

| Свойство | Назначение и правила |
|---|---|
| Язык (Страна) | Выбор языка (страны) для данной установки информационной базы. Ограничения по СУБД — см. ниже |
| Первый день недели | С какого дня начинается неделя. `Авто` — по стране из свойства «Язык (Страна)»: для английского — Воскресенье, для арабского — Суббота. Можно явно выбрать любой день недели. Особенности по версиям — см. ниже |
| Использовать региональные установки текущего сеанса | Значения типов `Число` и `Дата` отображаются (в том числе в полях ввода, календаре и калькуляторе) по региональным настройкам текущего сеанса. Они определяются региональными установками клиентского компьютера и могут быть переопределены параметром `/VL` |
| Разделитель дробной части | Символ-разделитель целой и дробной частей числа; выбирается из списка или вводится вручную (пример символа показывается слева от поля) |

| Представление отрицательных чисел | Вид отрицательных чисел из выпадающего списка. `Авто` — по установкам операционной системы |
| Формат даты | Форматная строка даты — см. таблицу ниже |

| Логическое ложь, Логическое истина | Вид логических констант; выбирается из списка или вводится вручную |

Значения типа `Булево` отображаются в соответствии с языком интерфейса платформы; язык интерфейса можно указать параметром `/L`.

### Ограничения смены «Язык (Страна)» по СУБД

| СУБД | Правило |
|---|---|
| **PostgreSQL** | Для существующей базы язык (страну) нельзя менять произвольно: допустима замена только на такое значение, которое использует **тот же порядок сортировки строк (collation) СУБД**, что и текущее. Пример из документации: «русский (Россия)» можно заменить на «белорусский (Беларусь)», но нельзя — на «украинский (Украина)» |
| IBM Db2 | Смена языка (страны) не поддерживается |

### «Первый день недели»: зависимость от версии и режима совместимости

| База создана в версии | Режим совместимости | Поведение |
|---|---|---|
| 8.3.6 и ниже (значение в ИБ не хранится) | 8.3.6 и младше | Первый день — Понедельник, изменить нельзя |
| 8.3.6 и ниже | «Не используется» или версия совместимости строго старше 8.3.6 | Первый день определяется по «Язык (Страна)»; свойство считается равным `Авто` |
| 8.3.7 и старше (значение хранится в ИБ; при создании = `Авто`) | «Не использовать» или строго старше 8.3.6 | Значение можно менять, оно сохраняется в ИБ |
| 8.3.7 и старше | 8.3.6 и младше | Первый день — Понедельник, редактирование свойства недоступно; реальная настройка при этом сохраняется и снова начнёт действовать, когда режим совместимости будет установлен в «Не использовать» (или версия совместимости станет строго старше 8.3.6) |

Попытка отредактировать региональные настройки платформой версии 8.3.6 и младше приводит к **потере** значения свойства «Первый день недели».

### Группировка цифр

Формат: `<A><символ-разделитель><B>`. Символ-разделитель — любой символ, кроме цифры. Строка задаёт одну или две группы цифр, считая справа налево; `A` и `B` — количество цифр в соответствующей группе.

Примеры на числе 987654321 при разделителе групп `/` (описание справа налево):

| Группировка | Представление | Пояснение |
|---|---|---|
| `3,2` | `98/76/54/321` | Первая группа — три цифры; затем разделитель групп (из настроек ОС или из свойства «Разделитель групп»); все оставшиеся цифры — по две |
| `3,0` | `987/654/321` | В каждой группе по 3 цифры, между группами — разделитель |
| `4` | `98765/4321` | Первая группа — 4 цифры, затем разделитель; остальные цифры идут без группировки и разделителей |

### Формат даты

Символы можно комбинировать в любой последовательности; между днём, месяцем и годом допустимы различные символы-разделители.

| Символы (как в источнике) | Описание |
|---|---|
| `D` | Число месяца; меньше 10 — без лидирующего нуля |
| `Dd` | Число месяца; меньше 10 — с лидирующим нулём |
| `M` | Номер месяца; меньше 10 — без лидирующего нуля |
| `MM` | Номер месяца; меньше 10 — с лидирующим нулём |
| `MMMM` | Наименование месяца словами |
| `Y` | Две последние цифры года; меньше 10 — без лидирующего нуля |
| `Yy` | Две последние цифры года; меньше 10 — с лидирующим нулём |
| `Yyyy` | Год четырьмя цифрами |

⚠ в источнике неясно: регистр символов дня и года (`D`, `Dd`, `Y`, `Yy`, `Yyyy`) приведён так, как он стоит в тексте источника; заглавная первая буква может быть артефактом вёрстки таблицы документации.

### Формат времени

Символы можно комбинировать в любой последовательности; между часами, минутами и секундами допустимы различные символы-разделители.

| Символы | Описание |
|---|---|
| `h`, `H` | Часы в 12-часовом (`h`) или 24-часовом (`H`) формате; меньше 10 — без лидирующего нуля |
| `hh`, `HH` | Часы в 12-часовом (`hh`) или 24-часовом (`HH`) формате; меньше 10 — с лидирующим нулём |
| `m` | Минуты; меньше 10 — без лидирующего нуля |
| `mm` | Минуты; меньше 10 — с лидирующим нулём |
| `s` | Секунды; меньше 10 — без лидирующего нуля |
| `ss` | Секунды; меньше 10 — с лидирующим нулём |

**Внимание:** если региональные настройки используются для представления даты в поле ввода, выбирать нужно только такие настройки, которые поддерживаются полем ввода.

### 6.6.2. Закладка «Аутентификация»

Параметры (рис. 74) делятся на две группы: общие (группа «Аутентификация») и описываемые политикой паролей (группа «Требования к паролям»).

**Группа «Аутентификация».**

| Параметр | Описание |
|---|---|
| Максимальное количество неуспешных попыток аутентификации | См. 6.4.2.2 |
| Длительность блокировки при превышении количества неуспешных попыток аутентификации (в секундах) | См. 6.4.2.2 |
| Коды дополнения имен пользователя при блокировке аутентификации | См. 6.4.2.2 |
| Алгоритм хеширования паролей пользователей | См. ниже |

**Алгоритм хеширования паролей пользователей.**

Пароли хранятся в базе не в открытом виде, а как результат хеш-функции, не позволяющей восстановить пароль; даже получив список пользователей, злоумышленник не увидит паролей.

| Алгоритм | Относительная «скорость» по документации (SHA-1 принят за 1) | Примечание |
|---|---|---|
| `SHA-1` | 1 | Единственный вариант, если к базе должны подключаться **любые** версии «1С:Предприятия». «Соль» не добавляется |
| `SHA-256` | 2*SHA-1 | Версия 8.3.26 и новее; с «солью» |
| `SHA-512` | 3*SHA-1 | Версия 8.3.26 и новее; с «солью» |
| `PBKDF2-SHA256` | 1915*SHA-1 (в тексте также: работает примерно в 2 000 раз медленнее, чем SHA-1) | Версия 8.3.26 и новее; с «солью». Максимально затрудняет подбор пароля перебором |

(По контексту «скорость» здесь означает кратность замедления относительно SHA-1.)

Правила выбора:

- нужен доступ из любой версии платформы → `SHA-1`;
- доступ только из версии 8.3.26 и последующих → можно любую хеш-функцию;
- нужна максимальная стойкость к перебору → `PBKDF2-SHA256`, но при этом **обязательно обеспечить защиту базы от DOS/DDOS-атак**: при попытке подбора пароля большим числом соединений кластер серверов будет занят только вычислением хешей паролей для проверки аутентификации.

«Соль» — произвольная случайная строка, добавляемая к паролю при хешировании, чтобы одинаковые пароли не давали одинаковый хеш. Используется для всех алгоритмов, кроме SHA-1; меняется при каждой смене пароля и для каждого пользователя.

Способы смены алгоритма и проверки:

| Способ | Элемент |
|---|---|
| Интерактивно | Диалог настройки параметров информационной базы — в конфигураторе или из стандартных функций |
| Встроенный язык, чтение/установка для ИБ | Методы глобального контекста `ПолучитьТипАлгоритмаХешированияПаролейПользователей()` / `УстановитьТипАлгоритмаХешированияПаролейПользователей()` |
| Встроенный язык, алгоритм конкретного пользователя | Свойство `ПользовательИнформационнойБазы.ТипАлгоритмаХешированияПароля` |

Рекомендованная последовательность смены алгоритма:

1. Администратор меняет алгоритм хеширования любым доступным способом.
2. Администратор завершает все активные сеансы пользователей, чтобы все заново прошли аутентификацию.
3. При аутентификации пользователи заново вводят пароль — он хешируется по новому алгоритму; новое значение хеша записывается в объект `ПользовательИнформационнойБазы` вместе с новым алгоритмом.
4. Через некоторое время (например, 1 месяц) администратор проверяет, у кого остался прежний алгоритм, принудительно меняет таким пользователям пароли и рассылает новые по электронной почте (выполнимо средствами встроенного языка).

Побочный эффект: если у пользователей были запомнены параметры аутентификации, после смены хеш-функции все выпущенные токены становятся недействительными — потребуется повторный вход с установленным флажком «Запомнить».

**Группа «Требования к паролям».** Набор параметров, применимых как к базе в целом, так и к отдельным пользователям; работа с политиками паролей описана в отдельном разделе документации.

См. также: параметры пользователя информационной базы; политики паролей пользователей; аутентификация пользователя информационной базы.

## Что важно администратору Linux

1. **Смена «Язык (Страна)» на PostgreSQL ограничена collation.** Для существующей базы допустима замена только на язык с тем же порядком сортировки строк СУБД (русский → белорусский можно, русский → украинский нельзя). Язык (страна) определяется при создании информационной базы (6.5).
2. **Блокировка при подборе пароля работает только в клиент-серверном варианте**, а её состояние хранит сервис вспомогательных функций кластера. Перезапуск кластера серверов сбрасывает все блокировки и счётчики; если заблокирован единственный администратор, для входа под ним во время блокировки документация предписывает перезапустить кластер серверов (6.4.2.2).
3. **Значение 0** отключает: контроль неуспешных попыток аутентификации; предупреждение о завершении сеанса при бездействии; само завершение сеанса при бездействии (6.4.2.2, 6.6.3).
4. **Коды дополнения имён** (разделитель `;`) — запасной вход для заблокированного пользователя. Начинать их с символов, невозможных в именах (`!`, `^`), и не допускать совпадения с окончаниями реальных имён пользователей (6.4.2.2).
5. **Вход в обход блокировки сеансов** — параметр `UC` командной строки или строки соединения, например `/UC123`; код с пробелами — в кавычках. Для веб-клиента и тонкого клиента через веб-сервер код можно задать в параметре `UC` строки соединения файла-дескриптора — тогда рекомендуется дополнительная публикация базы на веб-сервере (6.4.2.1).
6. **Алгоритм хеширования паролей:** SHA-256, SHA-512 и PBKDF2-SHA256 доступны только при работе из версии 8.3.26 и новее; при необходимости доступа из любых версий — только SHA-1. PBKDF2-SHA256 примерно в 2 000 раз медленнее SHA-1 (коэффициент 1915) — нужна защита от DOS/DDOS, иначе кластер будет занят подсчётом хешей (6.6.2).
7. **После смены алгоритма хеширования** нужно завершить все активные сеансы; сохранённые токены («Запомнить») становятся недействительными; хеш пользователя пересчитывается только при его следующем входе, поэтому через время стоит проверить «отставших» по свойству `ПользовательИнформационнойБазы.ТипАлгоритмаХешированияПароля` (6.6.2).
8. **Изменение «Времени ожидания блокировки данных»** требует административных прав и устанавливает монопольный режим доступа к базе — это нужно учитывать при работающих пользователях. Изменение действует сразу для всех СУБД, кроме IBM Db2 (то есть и для PostgreSQL); рестарт СУБД нужен только для IBM Db2 (6.6.3).
9. **«Количество заданий пересчета итогов»** — по умолчанию 4, только клиент-серверный вариант; это число системных фоновых заданий пересчёта итогов регистров при реструктуризации и при тестировании и исправлении базы (6.6.3).
10. **Сеансы до аутентификации:** переводятся в «Спящий» не более чем через 20 секунд бездействия клиентского приложения, а спящий сеанс уничтожается не позднее чем через 20 минут; после аутентификации действуют параметры «Время засыпания пассивного сеанса» и «Время завершения спящего сеанса» (6.6.3).
11. **Завершение сеанса при бездействии** требует лицензию КОРП, не действует на сеансы конфигуратора и не закрывает само клиентское приложение. Совмещать с сохранением аутентификации в целях безопасности не рекомендуется (6.4.3).
12. **Внешнее управление сеансами:** для клиент-серверной базы — лицензия КОРП, настройка в свойствах информационной базы кластера; для файловой — ПРОФ, `conf.cfg`, клиент 8.3.22+ и Web-сервис версии 4+. Уведомления о «Спящем» состоянии — при протоколе версии 2+. Сервис вызывается только для сеансов, потребляющих клиентскую лицензию (6.4.1).
13. **JWT и QR-код работают только при публикации базы на веб-сервере** и настраиваются в `default.vrd`: элемент `accessTokenAuthentication` (`issuer` с атрибутами `name` и `authenticationUserPropertyName`, подчинённый элемент `accessTokenRecepientName`) и элемент `<mobileApps>`; токен передаётся параметром запуска `AccessToken` (6.2.10.6, 6.2.10.7).
14. **Двухфакторная аутентификация зависит от доступности провайдера второго фактора по HTTP с сервера 1С:** нет связи с провайдером — пользователь не войдёт в базу. Действует только для стандартной аутентификации «1С:Предприятия»; при OpenID второй фактор настраивается в базе-провайдере OpenID (6.2.10.9).
15. **Аутентификация через электронную почту** не поддерживается в пакетном режиме запуска и при отключении стартовых диалогов при запуске клиентского приложения; требует и общей настройки в диалоге «Дополнительные настройки аутентификации», и включения у конкретного пользователя (6.2.10.8).
