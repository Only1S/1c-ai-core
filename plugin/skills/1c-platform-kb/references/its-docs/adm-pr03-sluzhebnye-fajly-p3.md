# 3.21. default.vrd (окончание)

## 3.21.9. (окончание раздела о настройке аутентификации OpenID Connect; заголовок и начало раздела — в предыдущей части)

### 3.21.9.3. Разные версии ЕСИА

Платформа умеет работать с разными версиями ЕСИА (Единая система идентификации и аутентификации). Какая версия используется — определяется по адресам, заданным в описании провайдера ЕСИА в свойствах:

- `providerconfig.authorization_endpoint`
- `clientconfig.authority`
- `providerconfig.token_endpoint`

| Версия ЕСИА | Точка получения кода авторизации | Точка получения токена доступа |
|---|---|---|
| 2.90 и новее | `https://<hostname>/aas/oauth2/v2/ac` | `https://<hostname>/aas/oauth2/v3/te` |
| предыдущие | `https://<hostname>/aas/oauth2/ac` | `https://<hostname>/aas/oauth2/te` |

Правила:

- Версия протокола выбирается по URL точки получения **кода авторизации**.
- Смешивать нельзя: если точка кода авторизации — от 2.90+, а точка токена — от старой версии, аутентификация через ЕСИА работать не будет.
- Для ЕСИА 2.90+ в клиентской конфигурации появляется свойство `client_certificate_hash`. Оно необязательное:
  - не задано — платформа сама вычисляет хеш и при необходимости добавляет его в запрос к ЕСИА;
  - задано в `default.vrd` — автоматический расчёт не выполняется, берётся значение из файла.
- Для ручного расчёта хеша предназначена утилита `http://esia.gosuslugi.ru/public/calc_cert_hash_unix.zip` (в архиве есть краткая инструкция). Применять её имеет смысл, только если на стороне ЕСИА поменяли алгоритм расчёта хеша, а используемая версия платформы этого изменения ещё не содержит.
- Рекомендуется ЕСИА 2.90 и новее: поддержку старых версий провайдер ЕСИА может отключить в любой момент без предупреждения.

### 3.21.9.4. Элемент `<allowStandardAuthentication>`

Управляет тем, показывается ли на форме аутентификации (при входе в веб-клиент) гиперссылка для перехода к обычной форме аутентификации «1С:Предприятия».

| Значение | Поведение |
|---|---|
| `true` | Можно открыть форму аутентификации «1С:Предприятия». **Умолчание.** |
| `false` | Открыть форму аутентификации «1С:Предприятия» нельзя. |

Важно: этот элемент управляет только отображением ссылки на форме. Разрешить или запретить саму аутентификацию «1С:Предприятия» конкретному пользователю можно только в свойствах этого пользователя.

### 3.21.9.5. Сценарий работы

Аутентификация через провайдера OpenID Connect возможна, только если в `default.vrd` описан хотя бы один провайдер. При обращении клиентского приложения (тонкий, мобильный или веб-клиент) к информационной базе:

1. Если провайдер явно указан в командной строке клиента — переход выполняется по параметрам этого провайдера из `default.vrd`.
2. Иначе платформа строит форму запуска (вид зависит от клиента) со всеми настроенными в `default.vrd` провайдерами OpenID Connect. В зависимости от настроек на ней может быть и кнопка стандартной аутентификации «1С:Предприятия».
3. После выбора провайдера пользователь перенаправляется на его страницу аутентификации и проходит аутентификацию любым способом, доступным у этого провайдера.
4. Провайдер перенаправляет пользователя обратно на специальную страницу «1С:Предприятия» и передаёт результат аутентификации в виде JSON Web Token (JWT). Адрес страницы — свойство `redirect_uri` структуры `clientconfig` элемента `provider`.
5. Из результата платформа получает ключевой параметр, идентифицирующий пользователя. По умолчанию это адрес электронной почты; переопределяется в `default.vrd` полем `authenticationClaimName`.
6. По ключевому параметру ищется пользователь информационной базы. По умолчанию поиск идёт по свойству `Имя`; переопределяется полем `authenticationUserPropertyName`.
7. Аутентификация считается успешной, запуск приложения продолжается.

Если аутентификация у провайдера не удалась — поведение провайдера документацией не определено.

## 3.21.11. Элемент `<standardOData>`

Управляет доступностью стандартного интерфейса OData для публикуемой базы. Подчинён корневому `<point>`; допускается один элемент или ни одного. **Если элемента в `default.vrd` нет — стандартный интерфейс OData через публикацию недоступен.**

| Атрибут | Назначение | Значения / умолчание |
|---|---|---|
| `enable` | Доступность стандартного интерфейса OData через данную публикацию | `true` — работа с данными через OData возможна; `false` — недоступна |
| `reuseSessions` | Режим повторного использования сеансов | `dontuse` — сеансы повторно не используются (**умолчание**); `use` — повторное использование определяется клиентом и регулируется параметрами HTTP-запроса; `autouse` — автоматическое повторное использование |
| `sessionMaxAge` | Время бездействия сеанса, после которого он завершается принудительно, секунды | умолчание `20` |

## 3.21.12. Элемент `<analytics>`

Управляет интеграцией «1С:Предприятия» с сервером системы «1С:Аналитика». В том числе задаёт параметры пула сеансов, через который система аналитики работает с кластером серверов.

| Атрибут | Назначение | Значения / умолчание |
|---|---|---|
| `enable` | Включение/выключение интеграции | `true` — работа с сервером «1С:Аналитика» через публикацию возможна (**умолчание**); `false` — недоступна |
| `sessionMaxAge` | Время бездействия сеанса до принудительного завершения, секунды | умолчание `20` |
| `poolSize` | Максимальное число сеансов в пуле | умолчание `500` |
| `poolTimeout` | Сколько секунд ждать свободного сеанса после заполнения пула; если за это время сеанс создать не удалось, клиент получает ошибку | умолчание `5` |

## 3.21.14. Элемент `<accessTokenAuthentication>`

### 3.21.14.1. Описание элемента

Настройки JWT-аутентификации. Элемент можно разместить в трёх местах (в каждом — один или ни одного):

| Где размещён | Что разрешает |
|---|---|
| в корневом `<point>` | JWT-аутентификацию для доступа к информационной базе |
| в `<ws>/<point>` | доступ к конкретному Web-сервису |
| в `<httpServices>/<service>` | доступ к конкретному HTTP-сервису |

Атрибутов у элемента нет. Подчинённые элементы — `<issuers>` и `<accessTokenRecepientName>`, каждый в единственном числе.

Пример для доступа к информационной базе:

```xml
<point xmlns="http://v8.1c.ru/8.2/virtual-resource-system"
       xmlns:xs="http://www.w3.org/2001/XMLSchema"
       xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance"
       base="/InfoBase"
       ib="File=&quot;C:\InfoBase&quot;;">
    <accessTokenAuthentication>
        <accessTokenRecepientName>InfoBaseJWT</accessTokenRecepientName>
        <issuers>
            <issuer name="limitedAccess"
                    authenticationClaimName="sub"
                    authenticationUserPropertyName="name"
                    keyInformation="EgH23sF8nL3xEGT2kEmAgxWyaKWvcf3p"/>
        </issuers>
    </accessTokenAuthentication>
</point>
```

Смысл примера: токен должен содержать `aud` = `InfoBaseJWT` и `iss` = `limitedAccess`, иначе доступ к базе не будет предоставлен.

### 3.21.14.2. Элемент `<accessTokenRecepientName>`

Атрибутов нет. Значение элемента — идентификатор получателя: с ним сравнивается претензия `aud` полезной нагрузки предъявленного токена (проверка, что токен выпущен именно для этого сервиса). Если значение не указано, идентификатором получателя считается имя интернет-сервиса или публикации.

Пример с тремя уровнями размещения:

```xml
<?xml version="1.0" encoding="UTF-8"?>
<point ...>
    ...
    <accessTokenAuthentication>
        <accessTokenRecepientName>ibRecepientName</accessTokenRecepientName>
    </accessTokenAuthentication>
    <ws>
        <point ...>
            ...
            <accessTokenAuthentication>
                <accessTokenRecepientName>wsRecepientName</accessTokenRecepientName>
            </accessTokenAuthentication>
        </point>
    </ws>
    <httpServices>
        <service ...>
            ...
            <accessTokenAuthentication>
                <accessTokenRecepientName>restRecepientName</accessTokenRecepientName>
            </accessTokenAuthentication>
        </service>
    </httpServices>
</point>
```

Значения `aud` в токенах должны совпадать: `ibRecepientName` — для информационной базы, `wsRecepientName` — для конкретного Web-сервиса, `restRecepientName` — для конкретного HTTP-сервиса.

### 3.21.14.3. Элемент `<issuers>`

Подчинён `<accessTokenAuthentication>`. Список приложений, которым разрешено обращаться к публикации по JWT. Содержит один или несколько элементов `<issuer>`.

### 3.21.14.4. Элемент `<issuer>`

Подчинён `<issuers>`. Описывает одно приложение (эмитента токенов), которому разрешён доступ.

| Атрибут | Назначение | Значения / умолчание |
|---|---|---|
| `name` | Имя приложения; сравнивается с претензией `iss` предъявленного токена | — |
| `authenticationClaimName` | Имя претензии токена, в которой лежит имя для аутентификации предъявителя | если не указан — претензия `sub` |
| `authenticationUserPropertyName` | Свойство пользователя «1С:Предприятия», по которому ищется пользователь (значение берётся из претензии, заданной в `authenticationClaimName`) | `name` — свойство `Имя` (**умолчание**); `OSUser` — `ПользовательОС`; `email` — `АдресЭлектроннойПочты`; `matchingKey` — поле поиска берётся из свойства `КлючиСопоставленияПользователя`, а ключом поиска служит значение свойства `name` описания приложения |
| `keyInformation` | Сертификат в формате PEM для проверки подписи JWT | для алгоритмов `HS256`, `HS384`, `HS512` — симметричный ключ; в остальных случаях — открытый ключ |

Токен, подходящий под пример из 3.21.14.1:

```json
{
  "alg": "HS256",
  "typ": "JWT"
}
{
  "exp": 1709936634,
  "aud": "InfoBaseJWT",
  "sub": "ФедоровБМ",
  "nbf": 1709733034,
  "iat": 1709733034,
  "iss": "limitedAccess"
}
```

Пояснения к примеру:

- `alg` = `HS256` — симметричный алгоритм, поэтому в `point/accessTokenAuthentication/issuers/issuer/keyInformation` лежит симметричный ключ (в тексте документации этот путь записан с опечаткой — `…/issue/keyInformation`). `HS256` взят только для иллюстрации. Для систем, к которым обращаются из-за периметра безопасности организации, рекомендованы асимметричные алгоритмы (например, `RS256`); симметричные допустимо рассматривать при доступе изнутри защищённого периметра.
- `aud` = `InfoBaseJWT` — имя получателя, заданное в `point/accessTokenAuthentication/accessTokenRecepientName`.
- `iss` должен совпасть с атрибутом `name` одного из элементов `issuer` в `point/accessTokenAuthentication/issuers`; в примере доступ даётся при `iss` = `limitedAccess`.

## 3.21.15. Элемент `<authentication>`

### 3.21.15.1. Описание и атрибуты элемента

Настройки отображения дополнительных видов аутентификации в диалоге аутентификации при входе в информационную базу. Подчинён `<point>`; один или ни одного. Должен содержать один элемент `<logonView>`.

Что можно настроить:

- разрешить или запретить сохранение параметров аутентификации на локальном компьютере пользователя;
- срок действия запомненной аутентификации (после истечения пользователь аутентифицируется заново);
- способ аутентификации по умолчанию;
- порядок следования видов аутентификации в нижней части диалога.

| Атрибут | Назначение | Тип / значения / умолчание |
|---|---|---|
| `allowSaveForReauthentication` | Разрешает сохранять параметры аутентификации для повторного входа в базу через данную публикацию. Запоминание работает для стандартной аутентификации (любой способ подключения и любой вид базы) и для OpenID-аутентификации. Удалить запомненные параметры последнего входа (и список из не более чем 4 последних имён пользователей) можно ключом командной строки клиента `/ResetSavedAuth` | Булево; умолчание `false` |
| `savedAuthenticationParametersLifeTime` | Время жизни (в секундах) токена (JWT), используемого для повторного входа; по его истечении система снова запросит имя пользователя и пароль | Число, от `1` до `999 999 999`; значение меньше 1 заменяется на 1, больше максимума — на 999 999 999; умолчание `432 000` |

Пример:

```xml
<authentication allowSaveForReauthentication="true" savedAuthenticationParametersLifeTime="60">
    <logonView saveForReauthenticationByDefault="false">
        <method type="standard" visible="true"/>
        <method type="qr" visible="false"/>
        <method type="openid" visible="true"/>
        <method type="openidconnect" visible="true"/>
        <method type="email" visible="true"/>
    </logonView>
</authentication>
```

Порядок видов аутентификации в диалоге, если он не настроен (показываются только настроенные для публикации):

1. стандартная аутентификация;
2. аутентификация через электронную почту;
3. OpenID;
4. OpenID Connect.

### 3.21.15.2. Элемент `<logonView>`

Задаёт порядок видов аутентификации в нижней части диалога — он равен порядку вложенных элементов `<method>`. Первый указанный вид становится видом аутентификации по умолчанию для этой публикации.

Если порядок не настроен, вид по умолчанию выбирается так:

1. OpenID Connect — если настроен для базы;
2. OpenID — если настроен для базы;
3. аутентификация «1С:Предприятия».

| Атрибут | Назначение | Тип / умолчание |
|---|---|---|
| `saveForReauthenticationByDefault` | Значение по умолчанию флажка «Запомнить» на форме аутентификации для нового пользователя базы | Булево; умолчание `false` |

### 3.21.15.3. Элемент `<method>`

Описывает один вид аутентификации, показываемый в диалоге.

| Атрибут | Назначение | Значения / умолчание |
|---|---|---|
| `type` | Вид аутентификации | `email` — через электронную почту; `openID` — OpenID; `openIDConnect` — OpenID Connect; `qr` — по QR-коду; `standard` — аутентификация «1С:Предприятия» |
| `visible` | Показывать ли вид аутентификации на форме. Имеет приоритет над настройкой этого вида аутентификации для базы, доступной через публикацию | Булево; умолчание `true` |

⚠ в источнике неясно: в перечне значений `type` написано `openID` и `openIDConnect`, а в примере из 3.21.15.1 — строчными (`openid`, `openidconnect`). Чувствительность к регистру документацией не оговорена.

# 3.22. inetcfg.xml

Задаёт настройки прокси по умолчанию. Имеет **приоритет** над системными настройками прокси в Windows и над переменными окружения в Linux и macOS.

- Расположение: каталог конфигурационных файлов «1С:Предприятия».
- Файл необязателен.

Откуда берутся настройки прокси:

| ОС | Файл есть | Файла нет |
|---|---|---|
| **Linux** | из файла | из переменных окружения `http_proxy`, `https_proxy`, `ftp_proxy`, `ftps_proxy` (по используемому протоколу); если они не заданы — из `all_proxy`. Некорректные значения переменных игнорируются |
| macOS | из файла | так же, как в Linux: `http_proxy`, `https_proxy`, `ftp_proxy`, `ftps_proxy`, затем `all_proxy`; некорректные значения игнорируются |
| Windows | из файла | из настроек Microsoft Internet Explorer; сценарий автоматической настройки не поддерживается (только Windows) |

Для правил на самом прокси можно опираться на `User-Agent` HTTP-запроса:

| Клиент | User-Agent |
|---|---|
| тонкий клиент | `1CV8C` |
| Web-сервис | `1C + Enterprise/8.3` |
| веб-клиент | формируется веб-браузером |

Пример файла:

```xml
<InternetProxy
    protocols="http=10.1.0.8:8080 10.1.0.9:8080"
    user="proxyUser"
    password="proxyPassword"
    bypassOnLocal="true"
    bypassOnAddresses="127.0.0.1 *.master"
/>
```

Корневой элемент — `InternetProxy`. Все атрибуты необязательные.

| Атрибут | Тип | Назначение | Значения / умолчание / примечание |
|---|---|---|---|
| `ntlm` | Булево | Использовать ли NTLM-аутентификацию | `true` — включена; `false` — выключена. **По умолчанию включена** |
| `protocols` | Строка | Хост и порт прокси для протоколов | Формат — см. ниже |
| `user` | Строка | Имя пользователя для аутентификации на прокси | пример: `user="proxyUser"` |
| `password` | Строка | Пароль пользователя для аутентификации на прокси | пример: `password="proxyPassword"` |
| `bypassOnLocal` | Булево | Обходить ли прокси для локальных адресов | `true` — прокси для локальных адресов **не** используется; `false` — используется |
| `bypassOnAddresses` | Строка | Список адресов, для которых прокси не используется | Формат — см. ниже |

**Формат `protocols`:**

```text
ПараметрыПроксиПротокола1 ПараметрыПроксиПротокола2 …ПараметрыПроксиПротоколаN
ПараметрыПроксиПротокола:=[Протокол"="]хост":"порт
```

- Элементы списка разделяются пробелами.
- Каждый элемент: необязательное имя протокола, знак `=`, затем `хост:порт`.
- Элемент без имени протокола действует для всех протоколов, которым параметры не заданы явно.
- Допустимые имена протоколов: `HTTP`, `HTTPS`, `FTP`. Регистр значим, другие имена не поддерживаются.
- Пример: `protocols="http=10.1.0.8:8080 10.1.0.9:8080"` — для HTTP прокси `10.1.0.8:8080`, для остальных (HTTPS, FTP) — `10.1.0.9:8080`.

⚠ в источнике неясно: имена протоколов перечислены прописными (`HTTP`, `HTTPS`, `FTP`) с оговоркой «регистр значим», но в примере там же используется строчное `http=`.

**Как определяется «локальный» адрес (`bypassOnLocal`):** по отсутствию точки в DNS-имени. Следствия:

- любой IP-адрес локальным **не считается**;
- фактически локальный адрес с точкой в имени тоже не будет распознан как локальный;
- для всех таких адресов исключения надо прописывать в `bypassOnAddresses`.

**Формат `bypassOnAddresses`:**

```text
хост1 хост2 … хостN
```

- Имена хостов разделяются пробелами.
- Допустимы маски: `*` — любое количество символов, `?` — один любой символ.
- Все хосты домена: `*.<имя домена>`.
- Пример: `bypassOnAddresses="127.0.0.1 *.master"` — прокси не используется для `127.0.0.1` (localhost) и для всех адресов домена `master`.

# 3.24. logcfg.xml

## 3.24.1. Общее описание

Файл настраивает **технологический журнал** (ТЖ) и механизм **генерации дампов памяти** при аварийном завершении «1С:Предприятия».

- Расположение: каталог конфигурационных файлов «1С:Предприятия».
- Файл необязателен.

Настройки по умолчанию, когда файла нет:

| Что | Значение по умолчанию |
|---|---|
| Технологический журнал (элемент `<log>`) | выключен |
| Технологический журнал по умолчанию (элемент `<defaultlog>`) | формирование включено; время жизни 24 часа; уровень формирования событий `<system>` для всех компонентов системы — `Error` |
| Каталог журнала по умолчанию, **Linux** | `~/.1cv8/logs` |
| Каталог журнала по умолчанию, Windows | `%LOCALAPPDATA%\1C\1cv8\logs` |
| Дампы аварийного завершения (актуально только для Windows) | минимальные дампы (`type="1"`), каталог `%LOCALAPPDATA%\1C\1cv8\dumps` |

Пример файла:

```xml
<config xmlns="http://v8.1c.ru/v8/tech-log">
    <log location="c:\v8\logs" history="1">
        <event>
            <eq property="name" value="conn"/>
        </event>
    </log>
    <dump location="c:\v8\dumps" create="1" type="2"/>
</config>
```

Что задаёт пример:

- в ТЖ пишутся все события установки и разрыва клиентского соединения с сервером (`conn`);
- файлы ТЖ лежат в `C:\v8\logs` и хранятся 1 час;
- дампы пишутся в `C:\v8\dumps` и содержат всю доступную информацию (вся память процесса, `type="2"`).

Для редактирования файла удобна обработка «Настройка технологического журнала» с ИТС (Технологическая поддержка → 1С:Предприятие 8 → Универсальные отчеты и обработки): `https://its.1c.ru/db/metod8dev/content/3474/hdoc`.

**Нотация, принятая в документации:**

- `element.attribute` — атрибут `attribute` элемента `element`;
- `element1/element2/element3` — элемент `element3`, вложенный в `element2`, вложенный в `element1`;
- записи комбинируются, например `config/log.location`.

## 3.24.2. Структура конфигурационного файла

### 3.24.2.1. Общее описание

Корневой элемент — `<config>`. Общий вид:

```xml
<config…>
    <log…>…</log>
    <log…>…</log>
    <log…>…</log>
    <dump … />
    <leaks>…</leaks>
    <mem/>
    <ftextupd …/>
    <query …/>
    <plansql/>
    <dbmslocks/>
    <inputbystring …/>
    <scriptcircrefs/>
    <sessiondatacontext>
    <system … />
    <system … />
    <system … />
    <defaultlog … />
</config>
```

(Это схема из документации, а не готовый XML: многоточия условные, `<sessiondatacontext>` в источнике записан без закрытия.)

| Элемент | Назначение | Сколько может быть |
|---|---|---|
| `<log>` | Каталог технологического журнала и его состав (отбор событий) | один или несколько |
| `<dump>` | Каталог для записи дампов аварийного завершения | один или ни одного |
| `<leaks>` | Отслеживание утечек памяти, которые могут быть вызваны ошибками в коде конфигурации. Несколько снижает производительность | один или ни одного |
| `<mem>` | Учёт используемой памяти | один или ни одного |
| `<plansql>` | Сбор планов запросов, формируемых при работе различных СУБД. Сами планы попадают в свойство `planSQLText` событий, связанных с СУБД | один или ни одного |
| `<dbmslocks>` | Сбор информации о блокировках СУБД | один или ни одного |
| `<ftextupd>` | Сбор информации о процессах обновления индекса полнотекстового поиска | один или ни одного |
| `<query>` | Запись в ТЖ сведений о полях, содержащих `NULL` при выполнении запроса к внешнему источнику данных, когда такое значение для поля недопустимо | один или ни одного |
| `<inputbystring>` | Сбор информации об использовании механизма ввода по строке | один или ни одного |
| `<scriptcircrefs>` | Отслеживание циклических ссылок при выполнении встроенного языка | один или ни одного |
| `<sessiondatacontext>` | Вывод списка операций изменения данных сеанса и их контекстов | один или ни одного |
| `<defaultlog>` | Каталог и время жизни технологического журнала по умолчанию | один или ни одного |
| `<system>` | Настройки формирования системных событий | один, несколько или ни одного |

**Три группы элементов:**

1. **Управляют формированием события:** `<dump>`, `<leaks>`, `<mem>`, `<plansql>`, `<ftextupd>`, `<system>`, `<query>`, `<scriptcircrefs>`, `<inputbystring>`. Если нужного элемента в файле нет, соответствующее событие системой вообще **не формируется**. Пример: без `<mem>` отбор по событию `MEM` в `<log>` ничего не даст — события просто не существует.
2. **Задают отбор уже сформированных данных:** `<event>` и `<property>`. Ими можно только **уменьшить** объём того, что пишется в файлы ТЖ.
3. **Управляют расположением файлов** (журнал и дампы): `<log>`, `<defaultlog>`, `<dump>`.

### 3.24.2.2. Элемент `<log>`

Определяет каталог технологического журнала и условия отбора, по которым в него попадают сформированные события.

**Внимание:** не рекомендуется настраивать больше 20 элементов `<log>` в одном `logcfg.xml` — большое число журналов может существенно замедлить систему.

| Атрибут | Назначение | Значения / умолчание |
|---|---|---|
| `compress` | Сжатие устаревших файлов ТЖ | `none` — без сжатия (**умолчание**); `zip` — устаревшие файлы сжимаются алгоритмом ZIP в момент ротации |
| `format` | Формат файлов ТЖ | `text` — простой текст (**умолчание**); `json` — последовательность объектов JSON |
| `history` | Через сколько часов информация удаляется из ТЖ | `0` — удаление устаревших файлов отключено; чистить каталог тогда должны сторонние средства администрирования, иначе диск переполнится |
| `location` | Каталог технологического журнала | В `<log>`, `<dump>` и `<defaultlog>` в `location` нужно указывать **разные** каталоги |
| `placement` | Структура хранения файлов ТЖ | `folders` — в подкаталогах с особыми именами (**умолчание**); `plain` — плоская структура без подкаталогов |
| `rotation` | Схема ротации файлов ТЖ | `period` — по времени (**умолчание**); `size` — по размеру файла |
| `rotationperiod` | Период (в часах), после которого включается ротация | умолчание `1` час |
| `rotationsize` | Размер файла (в мегабайтах), после которого включается ротация | умолчание `100` Мбайт |

Внутрь `<log>` вкладываются `<event>` и `<property>`: первые задают условие записи события, вторые — условие записи каждого свойства события. **Если в `<log>` нет ни одного `<event>`, в журнал не пишется ничего.**

(Хранение, формат и структура файлов ТЖ описаны в другом разделе документации.)

### 3.24.2.3. Элемент `<event>`

Последовательность элементов `<event>` задаёт условие записи события в журнал:

- условия **внутри** одного `<event>` объединяются по **И**;
- **разные** элементы `<event>` объединяются по **ИЛИ**;
- событие пишется, если оно удовлетворяет всем условиям хотя бы одного `<event>`.

Элементы условий:

| Элемент | Сравнение |
|---|---|
| `eq` | равно |
| `ne` | не равно |
| `gt` | больше |
| `ge` | больше или равно |
| `lt` | меньше |
| `le` | меньше или равно |
| `like` | соответствие маске |

Каждый элемент, кроме `like`, — простое сравнение значения параметра события (имя — в атрибуте `property`) со значением атрибута `value`.

```xml
<event>
    <eq property="name" value="proc"/>
</event>
```

Здесь в журнал попадают события группы `PROC`.

#### Элемент `like` и шаблоны маски

`like` проверяет, соответствует ли свойство события маске. Пример: `<like property="SDBL" value="%reference%"/>` — свойство `SDBL` сверяется с маской `%reference%`.

| Шаблон | Значение |
|---|---|
| `%` | 0 или более произвольных символов |
| `_` | ровно 1 произвольный символ |
| `[...]` | один из перечисленных символов; внутри допустимы произвольные символы и диапазоны вида `с-С` (начальный–конечный символ) |
| `[^...]` | один любой символ, кроме перечисленных в скобках |
| `\` | префикс (экранирование): сам игнорируется, а следующий за ним символ трактуется как обычный, а не как шаблон |
| прочие символы | означают сами себя; регистр букв при сравнении не различается |

Примеры масок:

| Маска | Чему соответствует |
|---|---|
| `шаблон` | строка с конкретным текстом; в этом случае `like` равносилен `eq`. Регистр не различается |
| `%reference%` | строка, содержащая `reference` в любом месте. Регистр не различается |
| `reference%` | строка, начинающаяся с `reference`. Регистр не различается |
| `%reference` | строка, заканчивающаяся на `reference`. Регистр не различается |
| `%[a-z]` | строка, оканчивающаяся строчной английской буквой от `a` до `z` |
| `%[^a-z]%` | строка, содержащая хотя бы один символ, отличный от строчной английской буквы |

Замечание: отбор по шаблонам (`like`) работает медленнее остальных сравнений; сложная фильтрация событий и свойств ТЖ может несколько замедлить работу «1С:Предприятия».

Пример — журнал с событиями групп `PROC`, `SCOM`, `CONN`, `EXCP` и `DBMSSQL`:

```xml
<log location="c:\logs" history="1">
    <event>
        <eq property="name" value="proc"/>
    </event>
    <event>
        <eq property="name" value="scom"/>
    </event>
    <event>
        <eq property="name" value="conn"/>
    </event>
    <event>
        <eq property="name" value="excp"/>
    </event>
    <event>
        <eq property="name" value="dbmssql"/>
    </event>
</log>
```

### 3.24.2.4. Элемент `<property>`

#### 3.24.2.4.1. Общая информация

`<property>` задаёт условие попадания в журнал **значения свойства** события (имя свойства — атрибут `name`), при условии что само событие в журнал попадает. Условия записываются вложенными `<event>` по тем же правилам, что и для событий.

Правила:

- Свойство пишется, **только если для него есть элемент `<property>`**. Нет `<property>` с таким именем — свойство не пишется.
- `<property>` без вложенных `<event>` (пустое условие) — свойство пишется для всех попадающих в журнал событий, у которых оно есть.
- `<property>` с вложенными `<event>` — свойство пишется только для событий, удовлетворяющих условию (если событие записывается и имеет это свойство).
- `<property name="all"> </property>` — включает запись всех свойств событий.
- У события может быть несколько свойств с одинаковыми именами.
- Имена свойств можно использовать для фильтрации и событий, и свойств; регистр букв в именах при сравнении не различается.

Пример: пишутся события процесса, серверного контекста, соединения, исключений и исполнения операторов SQL; текст оператора SQL — только если он выполнялся дольше секунды. Журнал в `C:\logs`, хранится 1 час.

```xml
<log location="c:\logs" history="1">
    <event>
        <eq property="name" value="proc"/>
    </event>
    <event>
        <eq property="name" value="scom"/>
    </event>
    <event>
        <eq property="name" value="conn"/>
    </event>
    <event>
        <eq property="name" value="excp"/>
    </event>
    <event>
        <eq property="name" value="dbmssql"/>
    </event>
    <property name="sql">
        <event>
            <eq property="name" value="mssql"/>
            <gt property="duration" value="10000"/>
        </event>
    </property>
</log>
```

Пояснение к числу: `duration` измеряется в сотнях микросекунд (см. свойство `Duration` ниже), поэтому `10000` = 1 секунда.

⚠ в источнике неясно: в условии свойства `sql` указано `value="mssql"`, тогда как событие в перечне и в отборе событий этого же примера называется `DBMSSQL` (`dbmssql`). Пример перенесён как в документации.

#### Контекст исполнения в технологическом журнале

Через `<property>` в ТЖ можно записывать контекст исполнения. Он бывает двух видов.

**Контекст встроенного языка** — список операторов встроенного языка; содержит:

- название модуля;
- номер строки модуля;
- текстовое представление элемента списка вызовов встроенного языка для соответствующей строки модуля.

Пример вида в файле ТЖ:

```text
Документ.ПриходнаяНакладная:23:Движения.УчетНоменклатуры.Записать();
МодульПриложения:18:ПроверитьПодключениеОбработчикаОжидания(Истина);
МодульПриложения:230:ЕслинпПолучитьЗначениеПоУмолчанию(глТекущийПользователь,"ИспользоватьНапоминания")
ОбщийМодуль.нпНастройкиПользователей:481:Выборка=Запрос.Выполнить().Выбрать();
```

**Интерфейсный контекст** содержит:

- полное имя формы;
- тип активного элемента формы;
- имя активного элемента формы;
- имя кнопки командной панели (если она была нажата);
- действие, выполняемое элементом формы.

Пример вида в файле ТЖ:

```text
{Документ.Документ1.ФормаСписка}/{ТабличноеПоле:
ДокументСписок}/{ОбновлениеОтображения}
{Документ.Документ1.Форма.ФормаДокумента}/{КоманднаяПанель:
ОсновныеДействияФормы}/{ОсновныеДействияФормыОК}
{Документ.Документ1.Форма.ФормаДокумента}/{Кнопка:
Кнопка1}/{Нажатие}
```

**Как включить запись контекста:** добавить среди фильтров свойств элемент `<property name="context">` или `<property name="all">`. (В тексте документации имя написано как `Сontext` с кириллической «С» — это опечатка источника; в XML-примере там же — `context` латиницей.)

События `SDBL` (SDBL-запросы) и `DBMSSQL` (операторы SQL к MS SQL Server) **с контекстом** исполнения:

```xml
<config xmlns="http://v8.1c.ru/v8/tech-log">
    <log location="c:\v8\logs" history="1">
        <event>
            <eq property="name" value="sdbl"/>
        </event>
        <event>
            <eq property="name" value="dbmssql"/>
        </event>
        <property name="context">
        </property>
    </log>
</config>
```

Те же события **без контекста** исполнения (элемента `<property>` нет вовсе):

```xml
<config xmlns="http://v8.1c.ru/v8/tech-log">
    <log location="c:\v8\logs" history="1">
        <event>
            <eq property="name" value="sdbl"/>
        </event>
        <event>
            <eq property="name" value="dbmssql"/>
        </event>
    </log>
</config>
```

*(На этом часть 3 заканчивается; остальные элементы `logcfg.xml` — `<dump>`, `<leaks>`, `<mem>`, `<system>`, `<defaultlog>` и др. — в этой части только упомянуты, их описание находится дальше по документации.)*

## Что важно администратору Linux

1. **`logcfg.xml` необязателен, но журнал по умолчанию всё равно пишется.** Без файла основной ТЖ (`<log>`) выключен, а журнал по умолчанию (`<defaultlog>`) включён: каталог `~/.1cv8/logs`, время жизни 24 часа, системные события уровня `Error`. Умолчания для дампов аварийного завершения в документации отмечены как актуальные только для Windows.
2. **Для PostgreSQL событие называется `DBPOSTGRS`.** Примеры в документации написаны для MS SQL Server (`dbmssql`). Свойства, которые перечень прямо относит к `DBPOSTGRS`: `Database`, `DBCopy`, `Dbms` (значение `DBPOSTGRS`), `Dbpid` (идентификатор соединения в терминах сервера БД), `planSQLText`. Общие свойства перечня, описывающие работу с базой данных (без привязки к конкретному событию): `Sql`, `Rows`, `RowsAffected`, `Trans`.
3. **Отбор двухступенчатый.** Нет ни одного `<event>` в `<log>` — в журнал не пишется ничего. Нет `<property>` — не пишутся свойства; чтобы писать все свойства, нужен `<property name="all">`. Внутри `<event>` условия соединяются по И, между `<event>` — по ИЛИ.
4. **Часть событий надо сначала «включить» отдельным элементом.** `<mem>`, `<leaks>`, `<plansql>`, `<ftextupd>`, `<query>`, `<scriptcircrefs>`, `<inputbystring>`, `<system>`, `<dump>` управляют самим формированием событий: без `<mem>` отбор по `MEM` бесполезен, без `<plansql>` не будет планов запросов в `planSQLText`.
5. **Единицы длительности.** `Duration` — сотни микросекунд (`10000` = 1 с), `Durationus` — микросекунды. Это надо учитывать в условиях вида `<gt property="duration" value="…"/>`.
6. **Следите за диском.** `history` — срок хранения в часах; `history="0"` отключает автоудаление, и чистку каталога придётся делать своими средствами. Массовые события (`SDBL`, `DBPOSTGRS`, `DBMSSQL`, `DB2`, `DBORACLE`) быстро раздувают журнал; редкие и компактные — `PROC`, `SCOM`, `EXCP`, `CONN`, `ADMIN`.
7. **Ротация и формат настраиваются атрибутами `<log>`:** `rotation` (`period`/`size`), `rotationperiod` (по умолчанию 1 час), `rotationsize` (по умолчанию 100 Мбайт), `compress` (`none`/`zip`, сжатие при ротации), `format` (`text`/`json`), `placement` (`folders`/`plain`).
8. **Каталоги не должны совпадать.** В `location` элементов `<log>`, `<dump>` и `<defaultlog>` нужно указывать разные каталоги. Больше 20 элементов `<log>` заводить не рекомендуется — система заметно замедляется.
9. **`SYSTEM` — только по указанию техподдержки «1С»** и только на время воспроизведения проблемы. Отбор через `like` медленнее прочих сравнений; сложные фильтры тоже замедляют работу.
10. **Контекст исполнения** (модуль, номер строки, оператор либо интерфейсный контекст формы) пишется только при наличии `<property name="context">` или `<property name="all">`.
11. **Прокси на Linux.** Если в каталоге конфигурационных файлов есть `inetcfg.xml` — используется он (приоритет над окружением). Если файла нет — берутся `http_proxy`, `https_proxy`, `ftp_proxy`, `ftps_proxy`, а при их отсутствии `all_proxy`; некорректные значения молча игнорируются.
12. **`bypassOnLocal` не покрывает IP-адреса.** «Локальным» считается только имя без точки, поэтому `127.0.0.1`, адреса внутренней сети и FQDN нужно явно перечислять в `bypassOnAddresses` (маски `*` и `?`, разделитель — пробел).
13. **OData через веб-публикацию выключен, пока в `default.vrd` нет `<standardOData>`.** Умолчания: `reuseSessions="dontuse"`, `sessionMaxAge="20"` секунд.
14. **JWT-доступ к базе, Web- и HTTP-сервисам** настраивается в `default.vrd` элементом `<accessTokenAuthentication>`: `aud` токена сверяется с `<accessTokenRecepientName>`, `iss` — с `issuer.name`, подпись проверяется по `keyInformation`. Для доступа из-за периметра рекомендованы асимметричные алгоритмы (например, `RS256`).
15. **Запоминание входа в веб-публикации** включается атрибутом `authentication.allowSaveForReauthentication` (по умолчанию `false`), срок — `savedAuthenticationParametersLifeTime` (по умолчанию 432 000 секунд); сброс запомненных данных на клиенте — ключ запуска `/ResetSavedAuth`.
