## 2.2.8. Профили безопасности (окончание)

### 2.2.8.6. Приложения операционной системы

Профиль безопасности может содержать список приложений ОС, которые разрешено запускать из прикладного решения.

- Если ИБ ссылается на профиль, где запуск приложений ограничен, доступны только исполняемые файлы из списка разрешённых приложений этого профиля.
- Вызов `ЗапуститьПриложение()` с приложением или параметрами, которым не соответствует ни одна запись списка, завершается исключением.
- Пустой список = профиль не разрешает запуск никаких приложений.

Параметры записи «разрешённое приложение»:

| Параметр | Назначение |
|---|---|
| Имя | Имя приложения; уникально в пределах профиля безопасности |
| Шаблон строки запуска | Последовательность шаблонных слов через пробел. Шаблонное слово — произвольные символы, допускаются символы подстановки. Слово, которое может содержать пробелы, заключается в кавычки |

Символы подстановки в шаблоне строки запуска:

| Символ | Значение |
|---|---|
| `%` | произвольная последовательность символов |
| `_` | один произвольный символ |
| `*` | имя файла. Если шаблонное слово начинается с `*`, параметр трактуется как маршрут от виртуального каталога; перед выполнением виртуальный каталог подменяется реальным |
| `\` | префикс: поставленный перед шаблонным словом, делает слово не шаблонным (буквальным) |

Правила сопоставления:

- Проверяется имя запускаемого приложения и каждый параметр из команды запуска. Если для какого-то из них нет соответствующего шаблонного слова — шаблон считается не подходящим к строке запуска.
- Параметры в строке запуска разделяются одним или несколькими пробелами.
- Строка в кавычках (`"`) — один параметр.
- Одним параметром считается последовательность слов, если первое и последнее слово содержат нечётное число одиночных кавычек. Если открывающее слово с кавычкой есть, а закрывающего нет — параметром считается всё до конца строки.
- Кавычка внутри параметра без кавычек записывается парой `\"`.
- Кавычка внутри параметра, заключённого в кавычки, записывается как `\"` либо как `""`.

Пример шаблона из документации (копирование произвольного файла из виртуального каталога `/temp` в виртуальный каталог `/userdata`):

```
xcopy */temp/% */userdata/%
```

### 2.2.8.7. Ресурсы сети Интернет

Профиль безопасности может содержать список интернет-ресурсов, к которым разрешено обращаться из серверного кода прикладного решения.

Если в профиле использование интернета ограничено:

- объект `ИнтернетСоединение` запрещён полностью;
- объекты `ИнтернетПочта`, `HTTPСоединение`, `FTPСоединение`, `WSОпределения` могут обращаться только к ресурсам из списка разрешённых;
- обращение к любому другому ресурсу вызывает исключение;
- пустой список = запрещены обращения к любым интернет-ресурсам.

Параметры записи «разрешённый ресурс»:

| Параметр | Назначение / значения |
|---|---|
| Имя | Идентификатор ресурса; уникален в пределах профиля безопасности |
| Адрес | Адрес ресурса без указания протокола |
| Порт | Номер порта для взаимодействия с ресурсом. `0` — разрешён любой порт |
| Тип ресурса (протокол) | Протокол взаимодействия; регистр символов не важен (перечень ниже) |

Допустимые значения «Тип ресурса (протокол)»:

| Значение | Что это |
|---|---|
| `imap` | почтовый сервер по протоколу IMAP |
| `pop3` | почтовый сервер по протоколу POP3 |
| `smtp` | почтовый сервер по протоколу SMTP |
| `http` | веб-сервер |
| `https` | защищённое соединение с веб-сервером |
| `ftp` | ftp-сервер |
| `ftps` | защищённое соединение с ftp-сервером |

### 2.2.8.8. Привилегированный режим

Когда сеанс работает в безопасном режиме под управлением профиля безопасности, поведение привилегированного режима определяют два параметра профиля:

- флажок **«к привилегированному режиму»** в группе **«Разрешен полный доступ»**;
- свойство **«Роли привилегированного режима»**.

| Флажок «к привилегированному режиму» | Свойство «Роли привилегированного режима» | Что происходит при включении привилегированного режима |
|---|---|---|
| установлен | (не важно) | Привилегированный режим включается полностью: контроль прав и ограничения доступа к данным отключаются |
| сброшен | роли указаны | В сеансе начинают действовать права (и ограничения доступа к данным) перечисленных ролей. При выключении привилегированного режима любым способом возвращаются роли и ограничения, действовавшие до включения |
| сброшен | роли не указаны | Продолжают действовать роли и ограничения доступа к данным, действовавшие на момент установки режима; контроль прав и ограничения доступа сохраняются в полном объёме |

Доступ к внешним ресурсам этим не регулируется — он определяется остальными параметрами установленного профиля безопасности.

См. также в документации: «Безопасный режим», «Привилегированный режим» (ссылки без адресов в текстовой копии).

### 2.2.8.9. Функции криптографии

Доступ к криптографии на стороне сервера управляется отдельным разрешением (флажком) профиля безопасности. Флажок установлен — доступны любые методы объекта `МенеджерКриптографии`; сброшен — вызов методов приводит к исключению.

Методы `МенеджерКриптографии`, на которые влияет разрешение:

- `Зашифровать()`
- `Подписать()`
- `ПолучитьИнформациюМодуляКриптографии()`
- `ПолучитьСертификатыИзПодписи()`
- `ПолучитьХранилищеСертификатов()`
- `ПроверитьПодпись()`
- `ПроверитьСертификат()`
- `Расшифровать()`

В этом пункте содержится только отсылка: использование профиля безопасности для регулирования возможности расширения прав доступа описано в другом месте документации (ссылка без адреса в текстовой копии).

### 2.2.8.11. Расширение всех модулей конфигурации

Действует в клиент-серверном варианте, когда при подключении расширения указан конкретный профиль безопасности либо когда ИБ назначены профили обычного и безопасного режима: «серверная» часть расширения расширяется так, как задано в соответствующем профиле.

Свойства профиля, управляющие расширением «серверной» части:

| Свойство профиля | Действие |
|---|---|
| Флажок **«к расширению всех модулей»** (группа «Разрешен полный доступ») | Если установлен — для всех расширений, подключённых с этим профилем, разрешено расширение всех серверных общих модулей |
| **«Доступные для расширения модули»** | Список имён модулей, которые можно расширять; разделитель — `;` |
| **«Недоступные для расширения модули»** | Список имён модулей, которые расширять нельзя; разделитель — `;` |

Что считается «серверной» частью расширения:

- расширения серверных методов управляемой формы, созданные аннотациями (а не конструктором панели свойств);
- серверные неглобальные общие модули.

## 2.2.9. Безопасность кластера серверов

### 2.2.9.1. Общая информация

Принцип: в клиент-серверном варианте доступ к данным «1С:Предприятия» должен идти только через механизмы самой платформы. Все клиентские приложения и внешние соединения работают с данными только через кластер серверов и обязаны пройти аутентификацию «1С:Предприятия»: перед началом работы приложение передаёт кластеру имя пользователя 1С и пароль; работа продолжается, только если такой пользователь с таким паролем зарегистрирован в ИБ.

Данные кластера делятся на ИБ и служебные данные. Области обеспечения безопасности (номера — по рис. 11 «Общая схема безопасности» в документации):

| № области | Что защищается | Кто обеспечивает |
|---|---|---|
| 1 | обмен между клиентом и кластером серверов | кластер серверов |
| 2 | обмен между консолью кластера серверов и кластером | кластер серверов |
| 3 | хранение служебных данных в кластере серверов | кластер серверов |
| 4 | обмен данными внутри кластера | кластер серверов |
| 5 | сама ИБ в базе данных и обмен между кластером и сервером баз данных | средства используемой СУБД |
| 6 | обмен между клиентским приложением и веб-сервером (при подключении к ИБ через веб-сервер) | используемый веб-сервер |
| 7 | обмен между кластером серверов и веб-сервером | кластер серверов |

### 2.2.9.2. Безопасность данных, передаваемых между клиентом и кластером серверов

#### 2.2.9.2.1. Общая информация

Защита — шифрование передаваемых данных. Три уровня безопасности (от низшего к высшему):

1. **выключено**
2. **только соединение**
3. **постоянно**

Транспорт — безопасное соединение по TCP/IP с шифрованием алгоритмами **RSA** и **Triple DES**.

Сводка по уровням:

| Уровень | Что шифруется | Ход обмена после установки соединения | Влияние на производительность |
|---|---|---|---|
| выключено | практически ничего | первый обмен — RSA, далее данные без шифрования | самый производительный уровень |
| только соединение | только пароли (ключевая информация) | первый обмен — RSA, затем Triple DES до окончания аутентификации, далее без шифрования | практически не снижает производительность |
| постоянно | весь поток: и пароли, и данные | первый обмен — RSA, весь дальнейший обмен — Triple DES | возможно значительное снижение производительности |

#### 2.2.9.2.2. Уровень безопасности «постоянно»

- Полностью защищает весь поток данных между клиентом и кластером (пароли и собственно данные).
- Документация отдельно предупреждает: возможно значительное падение производительности системы.
- Протокол одинаков для менеджера кластера (`rmngr`) и рабочего процесса (`rphost`): после установки соединения первый обмен шифруется RSA, весь последующий — Triple DES.

Где задаётся и хранится уровень безопасности:

- Задаётся при создании ИБ.
- Сохраняется и на клиенте (в списке информационных баз), и в кластере (в реестре кластера).
- После создания ИБ уровень безопасности, записанный для неё в реестре кластера, **изменить нельзя**.

Зависимость от вида клиентского приложения:

| Клиент | Как определяется уровень безопасности соединения |
|---|---|
| Тонкий клиент | Всегда уровнем, заданным при создании ИБ |
| Толстый клиент, внешнее соединение, Конфигуратор | Может быть повышен по инициативе клиента — командой `/SLev` командной строки запуска клиентского приложения |

Порядок согласования (рис. 12 в документации):

1. Клиент после установки соединения генерирует приватный и публичный ключи RSA и отправляет кластеру публичный ключ. Конфигуратор, толстый клиент и внешнее соединение дополнительно передают уровень безопасности, указанный для этой ИБ на клиенте (параметр `/SLev`).
2. Кластер берёт максимум из двух значений: уровень из реестра кластера для этой ИБ и уровень, присланный клиентом (если прислан). Результат — **фактический уровень безопасности**.
3. Кластер генерирует сеансовый ключ Triple DES и отправляет его клиенту вместе с фактическим уровнем безопасности, зашифровав эти данные публичным ключом клиента.
4. Дальнейший обмен идёт согласно фактическому уровню; и клиент, и сервер шифруют данные сеансовым ключом по Triple DES.

#### 2.2.9.2.3. Уровень безопасности «только соединение»

- Частичная защита: шифруются только пароли. Компромисс между безопасностью и производительностью.
- Данные ИБ идут в открытом виде; так как они составляют основную массу потока, производительность практически не падает.
- Пароли передаются только зашифрованными: при перехвате трафика можно получить лишь незначительную часть данных ИБ, но нельзя аутентифицироваться в ИБ, получить доступ ко всем данным или выполнять с ИБ произвольные действия.
- Ход обмена (рис. 13): первый обмен — RSA; затем Triple DES до конца процедуры аутентификации; после этого — нешифрованный обмен.

#### 2.2.9.2.4. Уровень безопасности «выключено»

- Самый низкий по защите и самый производительный уровень; почти все данные идут без шифрования.
- Ход обмена (рис. 14): первый обмен после установки соединения — RSA; дальше — нешифрованные данные.
- Особый случай: если клиентское приложение и кластер серверов находятся на одном компьютере и уровень безопасности «выключено», шифрование между клиентом и кластером не выполняется вообще.

### 2.2.9.3. Безопасность данных, передаваемых между консолью кластера серверов и кластером серверов

- Также обеспечивается шифрованием, с теми же тремя уровнями: выключено, только соединение, постоянно.
- Консоль кластера взаимодействует с агентом сервера (процесс `ragent`).
- Желаемый уровень безопасности задаётся при старте агента сервера.
- Фактический уровень агент выбирает как максимум из: уровня, указанного при старте агента, и уровней безопасности всех кластеров, расположенных на данном центральном сервере.
- Уровень безопасности кластера задаётся при его создании (программно или интерактивно).

### 2.2.9.4. Безопасность данных, хранящихся в кластере серверов

#### 2.2.9.4.1. Общая информация

Служебные данные кластера (список кластеров сервера, реестры кластеров и др.) — это набор файлов в двух каталогах:

- каталог данных приложения;
- каталог временных файлов.

Идеология: прямой доступ к служебным данным должны иметь только менеджер кластера (`rmngr`) и агент сервера (`ragent`). Рабочие процессы (`rphost`) пользуются служебными данными только через менеджера кластера, так как считаются потенциально опасными — в них может исполняться код конфигураций.

#### 2.2.9.4.2. Безопасность каталога данных приложения

- При установке кластера серверов в каталоге данных приложения создаётся специальный каталог, предназначенный только для файлов кластера «1С:Предприятия» (рис. 15).
- Пользователю `USR1CV8`, от имени которого по умолчанию стартует агент сервера, назначаются полные права на этот каталог; остальным пользователям доступ запрещается. Перечень прав, которые нужно предоставить `USR1CV8`, описан в другом месте документации (ссылка без адреса в текстовой копии).
- Менеджер кластера запускается агентом сервера от имени того же пользователя, от которого работает сам агент.
- Рабочие процессы тоже запускает агент сервера; по умолчанию — от имени пользователя агента.
- Можно завести дополнительного пользователя ОС, от имени которого будут стартовать только рабочие процессы. Это закрывает коду конфигураций прямой доступ к служебным данным.
- Чтобы рабочий процесс запускался не от имени пользователя агента, в каталоге данных приложений, относящемся к пользователю агента сервера, размещают файл **`swpuser.ini`**. Формат файла в этой части не приводится — описан в другой книге документации (в текстовой копии название книги не указано — ⚠ в источнике неясно).

#### 2.2.9.4.3. Безопасность каталога временных файлов

- Системный каталог временных файлов общедоступен, поэтому права ограничиваются для каждого временного файла по отдельности (рис. 16).
- При создании временного файла кластером пользователю `USR1CV8` выдаются полные права на этот файл, остальным пользователям доступ запрещается. Так содержимое временных файлов защищается от несанкционированного доступа.

#### 2.2.9.4.4. Шифрование паролей, хранимых в служебных данных кластера серверов

Пароли администраторов кластера и пароли доступа к ИБ хранятся в кластере в зашифрованном виде. Используются два алгоритма:

| Алгоритм | Для каких паролей | Свойство |
|---|---|---|
| **SHA1** | Пароли, которые проверяет сама система «1С:Предприятие» (например, пароль администратора кластера, администратора центрального сервера) | Исходный текст восстановить нельзя; возможна только сверка контрольной суммы введённого пароля с хранимой |
| **AES128** | Пароли, исходный текст которых нужно восстанавливать (например, пароли доступа к СУБД) | Обратимое шифрование |

### 2.2.9.5. Безопасность данных, передаваемых внутри кластера серверов

- Обмен внутри кластера (например, между рабочими процессами и менеджером кластера) защищается шифрованием с теми же тремя уровнями: выключено, только соединение, постоянно.
- Рабочий процесс ↔ менеджер кластера: используется уровень безопасности кластера.
- Агент сервера ↔ менеджер кластера: максимум из уровня безопасности, с которым запущен агент сервера, и уровня безопасности кластера, обслуживаемого данным менеджером.

### 2.2.9.6. Безопасность данных, передаваемых между кластером серверов и СУБД

- Канал «кластер ↔ СУБД» защищается средствами используемой СУБД.
- Все поддерживаемые СУБД позволяют настроить свои клиентские компоненты, установленные в кластере, на шифрование трафика до СУБД.
- Все поддерживаемые СУБД могут использовать протокол SSL.

### 2.2.9.7. Безопасность данных, передаваемых между клиентским приложением и веб-сервером

- Канал «веб-клиент ↔ веб-сервер» и «тонкий клиент ↔ веб-сервер» защищается криптографическими протоколами SSL или TLS через HTTPS-соединение с веб-сервером.
- На сервере нужен действительный серверный сертификат, подтверждающий клиенту подлинность открытого ключа сервера, которым шифруются данные.
- Дополнительно можно применять клиентские сертификаты, подтверждающие серверу подлинность клиента.
- Ограничение Linux: клиентское приложение под ОС Linux не поддерживает клиентские сертификаты из хранилища сертификатов Windows.

### 2.2.9.8. Безопасность данных, передаваемых между веб-сервером и кластером серверов

- Канал «кластер ↔ веб-сервер» защищается алгоритмами шифрования самой платформы: **RSA** и **Triple DES**.
- Защиту этого соединения выполняет только кластер, исходя из свойств ИБ, к которой идёт подключение (подробности — по ссылке в документации, адрес в текстовой копии не указан).
- Дополнительно возможен алгоритм **AES-256**. Для его включения нужны файлы `wskey.pem`:

| Где размещается `wskey.pem` | Что содержит |
|---|---|
| Каталог служебных файлов кластера на **каждом** из центральных рабочих серверов | Перечисление **открытых** ключей RSA пар ключей доступа, применяемых для защиты обмена между кластером и веб-сервером |
| Каталог виртуального приложения веб-сервера | **Закрытый** ключ RSA из пары ключей доступа |

Для каждого виртуального приложения используется своя пара ключей.

### 2.2.9.9. Администраторы центрального сервера и администраторы кластера

- Администрирование кластера возможно с аутентификацией администраторов и без неё.
- **По умолчанию после установки кластера серверов аутентификация администраторов не используется.** В этом режиме любой пользователь, подключившийся к центральному серверу кластера, может выполнять все административные действия и с центральным сервером, и с любым кластером на нём.
- Для ограничения круга лиц создаются список администраторов центрального сервера и списки администраторов каждого кластера на этом сервере.
- Области действия прав администраторов центрального сервера и администраторов кластеров **не пересекаются**:
  - аутентификация администратора центрального сервера даёт право на административные действия с центральным сервером, но не с конкретным кластером;
  - для действий с кластером нужно аутентифицироваться как администратор этого кластера; дополнительная аутентификация администратором сервера при этом не требуется.
- Механизм аутентификации включается автоматически, как только в соответствующем списке (центрального сервера или кластера) появляется хотя бы один администратор.

Что доступно без аутентификации при включённом механизме:

| Кто | Что может |
|---|---|
| Не аутентифицирован как администратор центрального сервера | Только просматривать и изменять параметры подключения к центральному серверу в консоли администрирования кластера серверов |
| Не аутентифицирован как администратор кластера | Только просматривать свойства кластера. Средствами встроенного языка может создавать объекты кластера, ИБ и пр., но не может зарегистрировать их в кластере |

## 2.2.10. Механизм блокировок информационной базы

Механизм блокировок обеспечивает согласованную конкурентную работу с тремя составляющими:

- конфигурация;
- информационная база;
- база данных.

Работу механизма видно в утилите администрирования кластера серверов.

Виды блокировок:

| Вид | Назначение |
|---|---|
| Разделяемая | Совместная работа нескольких сеансов |
| Исключительная (монопольный режим) | Исключает изменение данных другими сеансами |

Кто ставит исключительную блокировку:

- на конфигурацию и на информационную базу — устанавливается и снимается автоматически самой системой в некоторых случаях (см. таблицу);
- на базу данных — система автоматически **или** разработчик вызовом метода встроенного языка `УстановитьМонопольныйРежим()`.

Важно: это блокировки механизмов «1С:Предприятия», отвечающих за доступ к базе данных. Исключительная блокировка базы данных **не мешает** обращаться к базе другим приложениям, которые работают с ней в обход механизмов «1С:Предприятия».

Исключительные блокировки по объектам:

| Объект блокировки | Что означает | Когда устанавливается |
|---|---|---|
| Конфигурация | К одной ИБ не могут подключиться несколько конфигураторов | Системой при запуске конфигуратора |
| Информационная база | Может существовать только один сеанс любого вида | Обновление конфигурации базы данных; загрузка ИБ; выгрузка ИБ; создание начального образа ИБ; конвертация ИБ для новой версии платформы; тестирование и исправление |
| База данных | Может существовать один сеанс вида Конфигуратор и только один дополнительный сеанс произвольного вида | Выполнение `УстановитьМонопольныйРежим()` — когда нужны согласованные изменения базы, не укладывающиеся в одну транзакцию (пример из документации: массовое удаление объектов в большой ИБ); групповое проведение документов (только толстый клиент) |

Поведение при переходе в монопольный режим:

- Служебные соединения с ИБ не препятствуют установке монопольного режима (ни к информационной базе, ни к базе данных).
- Наличие сеансов препятствует переходу в монопольный режим (сеанс = активный пользователь). Исключение — сеанс консоли кластера.
- При попытке перехода неявно разрываются все соединения с ИБ, которым не назначен сеанс.
- Пока установлен монопольный доступ к информационной базе или базе данных, новые сеансы начать нельзя.
- Если с ИБ соединены веб-серверы, при попытке установить монопольный доступ к ним идёт обращение с целью очистки пула соединений.

## 2.2.11. Статистика загруженности рабочих процессов

Для каждого рабочего процесса кластер вычисляет показатели загруженности за период примерно **10 минут**:

- среднее время реакции кластера серверов;
- среднее время, затраченное кластером серверов;
- среднее время, затраченное СУБД;
- среднее время, затраченное менеджером блокировок;
- среднее количество клиентских потоков.

Пояснения:

- Среднее время реакции кластера серверов — время, которое кластер потратил на обслуживание одного клиентского соединения. Его составляющие по документации: время, затраченное рабочим процессом; время, затраченное СУБД; время, затраченное менеджером блокировок.
- Среднее количество клиентских потоков — среднее число потоков, выполняемых рабочим процессом одновременно.
- Каждое клиентское соединение рабочий процесс обслуживает в отдельном потоке. Одновременно выполняемых клиентских потоков, как правило, меньше, чем соединений, так как не все соединения активны постоянно.
- ⚠ в источнике неясно: в начале раздела сказано, что все показатели считаются за период около 10 минут, а про среднее количество клиентских потоков в конце раздела сказано «среднее (за сутки)». Противоречие присутствует в самой документации.

## 2.2.12. Система мониторинга кластера

Подсистема мониторинга в составе кластера регулярно собирает сведения о состоянии процессов кластера. «Процесс» здесь — любой компонент кластера: агент сервера (`ragent`), менеджер сервера (`rmngr`), рабочий процесс (`rphost`).

### Что проверяется

| Проверка | Примечание |
|---|---|
| Соединение с процессом | Таймаут проверки соединения — 20 секунд |
| Доступная производительность рабочего процесса | Вычисляется; при определении «проблемных» процессов этот показатель из анализа исключается |
| Объём памяти, занимаемой процессом | Применимо к менеджеру кластера и рабочему процессу |
| Рабочие процессы, удалённые из реестра кластера | Процесс считается проблемным, если не завершился за **7,5 секунды** после удаления из реестра кластера |

Что означает «память, занимаемая процессом» (процесс = рабочий процесс или менеджер кластера):

| ОС | Значение |
|---|---|
| **Linux** | сумма показателей `vmSwap` и `vmRSS` из информации о памяти процесса |
| Windows | значение `PagefileUsage` структуры `PROCESS_MEMORY_COUNTERS` |

### Порядок опроса

- Периодичность проверки — каждые **5 секунд**.
- Таймаут при проверке соединения — **20 секунд**.
- Проверки идут последовательно: следующая не начинается, пока не закончилась предыдущая.
- Отрицательные результаты проверки пишутся в ТЖ событием **`ATTN`**.
- Опрос процессов кластера выполняет только агент **центрального** сервера. Процессы на дополнительных рабочих серверах опрашиваются через агентов этих серверов.
- Часть операций (например, проверка объёма памяти процесса) выполняется через соответствующих агентов серверов — тем самым заодно проверяется работоспособность самих агентов.
- При ошибке соединения с агентом сервера сообщения об ошибках появляются в ТЖ агента центрального сервера.

### Контроль объёма памяти

Сравнивается **суммарная** память всех рабочих процессов и менеджеров кластера (в указанном выше смысле) с параметрами рабочего сервера:

| Параметр рабочего сервера | Спецзначения | Что происходит при превышении |
|---|---|---|
| **Временно допустимый объем памяти процессов** | `-1` — проверка не выполняется; `0` — берётся 80% оперативной памяти компьютера рабочего сервера | На рабочий сервер перестают назначаться новые соединения. Дальше — в зависимости от параметра «Интервал превышения допустимого объема памяти процессов» |
| **Интервал превышения допустимого объема памяти процессов** | Учитывается, если не равен нулю | По истечении интервала сравнение повторяется. Если превышение сохраняется — **неаварийно** перезапускается столько рабочих процессов (начиная с самого «тяжёлого» по памяти), чтобы суммарная память оставшихся рабочих процессов и менеджеров не превышала «Временно допустимый объем памяти процессов» |
| **Критический объем памяти процессов** | `-1` — проверка не выполняется; `0` — берётся 95% оперативной памяти компьютера рабочего сервера | **Аварийно** завершается (и затем запускается заново) столько рабочих процессов, начиная с потребляющего больше всего памяти, чтобы суммарная память оставшихся рабочих процессов и менеджеров не превышала заданное значение |
| **Записывать дамп процесса при превышении критического объема памяти** | — | Управляет записью дампов при аварийном завершении процессов из-за превышения критического объёма |

На каждой итерации мониторинга при обнаружении превышения критического объёма памяти в ТЖ пишется событие `ATTN` с идентификаторами всех процессов кластера и объёмом памяти каждого.

### Проблемные процессы и принудительное завершение

Процессы, не прошедшие проверки мониторинга (без учёта показателя доступной производительности), признаются проблемными. Далее анализируются параметры **кластера**:

| Параметр кластера | Назначение |
|---|---|
| **Принудительно завершать рабочие процессы** | Разрешает кластеру аварийно (средствами ОС) завершать процессы кластера, которые не удалось завершить штатно |
| **Проблемные процессы завершать через** | Время от момента, когда кластер определил, что процесс не завершился штатно, до принудительного (аварийного) завершения средствами ОС |

- «Зависшие» процессы **никогда** не завершаются принудительно средствами ОС, если флажок «Принудительно завершать рабочие процессы» сброшен **или** «Проблемные процессы завершать через» равно `0`.
- Процессы на дополнительных серверах завершаются запросами к соответствующим агентам кластера.

### Дампы аварийного завершения

| ОС | Правила |
|---|---|
| **Linux** | Используются настройки ОС. Запись дампа при таком завершении инициируется отправкой процессу сигнала **`SIGABRT`**. Обычный дамп аварийного завершения формируется по сигналу **`SIGSEGV`** |
| Windows | Используются настройки из файла `logcfg.xml` |

Подробная настройка формирования дампов описана в другой книге документации (в текстовой копии название книги не указано — ⚠ в источнике неясно).

### События ТЖ, упомянутые в разделе

| Событие | Что отражает |
|---|---|
| `ATTN` | Отрицательные результаты проверок мониторинга; превышение критического объёма памяти (с идентификаторами всех процессов кластера и их объёмами памяти) |
| `CALL` | Серверные вызовы, регулярно выполняемые в ходе работы кластера |
| `EXCP` | Ошибки, возникающие при выполнении вызовов |

Замечание про `EXCP`: само по себе событие `EXCP` в ТЖ не означает реальной проблемы сервера. Пример из документации: при выборе рабочего порта из доступного диапазона каждый занятый порт фиксируется как `EXCP`, но это штатная ситуация — поиск просто переходит к следующему порту.

### Какие проблемы помогает решать мониторинг

- «Зависание» процессов сервера в памяти — как во время работы, так и при попытке завершения процесса.
- Неактуальные сведения о памяти рабочего процесса, отображаемые в консоли кластера.
- Повышенное потребление памяти процессами кластера.

См. также в документации: «Параметры кластера серверов», «Параметры рабочего сервера».

## 2.2.13. Расположение служебных файлов менеджера кластера

- Служебные файлы кластера серверов на конкретном рабочем сервере лежат в **каталоге данных сервера**.
- Путь к каталогу задаётся значением команды **`/d`** командной строки запуска агента сервера.
- Предостережение: если на компьютере центрального сервера кластер уже создавался, то при смене варианта запуска агента (сервис ↔ приложение) или при смене пользователя, от имени которого работает агент, нужно следить за правильным указанием пути к каталогу служебных файлов. **Если при запуске агент сервера не найдёт реестр сервера, он создаст новый кластер на этом сервере.**

Каталог данных сервера по умолчанию:

| ОС / способ запуска | Каталог по умолчанию | Примечание |
|---|---|---|
| **Linux** | `/home/usr1cv8/.1cv8/1C/1cv8` (сокращённо `~/.1cv8/1C/1cv8`) | Можно изменить командой `/d` командной строки запуска агента сервера |
| Windows, запуск «как сервис» (только Windows) | `<корневой каталог установки>\srvinfo` | Первый запуск агента происходит в процессе установки, от имени пользователя, выбранного в диалоге установки; каталог явно прописан в параметрах сервиса командой `/d` |
| Windows, запуск «как приложение» (только Windows) | `%LOCALAPPDATA%\1C\1cv8` — если `/d` не указана | При установке сервер не запускается; агент сервера нужно запустить самостоятельно после установки |

См. также в документации: «Запуск агента сервера».

## 2.3. Особенности работы в ОС Linux

Ограничения кластера серверов «1С:Предприятия» под ОС Linux:

| Ограничение | Подробности |
|---|---|
| Нет работы с Microsoft SQL Server | Рабочий процесс кластера не может взаимодействовать с СУБД Microsoft SQL Server |
| Нет работы с COM-объектами | Рабочий процесс не может взаимодействовать с COM-объектами. Серверные модули, работающие с COM-объектами, компилируются, но при попытке выполнения такого модуля выдаётся сообщение об ошибке |
| Аутентификация — Kerberos и/или имя и пароль | Аутентификация выполняется на основе Kerberos и/или по имени и паролю пользователя. Для сравнения документация отмечает: Windows-версия поддерживает протокол NTLM, который, в частности, может обеспечить аутентификацию без PDC |
| Нет `ИнтернетСоединение` | Функциональность объекта `ИнтернетСоединение` недоступна |

Для некоторых возможностей сервера «1С:Предприятия» под Linux требуются дополнительные библиотеки. Перечень библиотек и возможностей, для которых они нужны, в этой части не приводится — документация отсылает к другому разделу (ссылка без адреса в текстовой копии).

## Что важно администратору Linux

1. **Каталог данных сервера на Linux по умолчанию — `/home/usr1cv8/.1cv8/1C/1cv8`**; переопределяется командой `/d` при запуске агента сервера (`ragent`). Там лежат служебные файлы кластера (реестр).
2. **Не найдя реестр сервера, агент создаёт новый кластер.** При смене пользователя, от имени которого работает агент, или варианта запуска агента нужно проверять, что путь к каталогу служебных файлов кластера указан правильно (команда `/d`).
3. **Под Linux сервер 1С не работает с Microsoft SQL Server и с COM-объектами**, недоступен объект `ИнтернетСоединение`, а аутентификация выполняется на основе Kerberos и/или по имени и паролю (протокол NTLM документация называет возможностью Windows-версии).
4. **«Память, занимаемая процессом» на Linux = `vmRSS` + `vmSwap`.** Именно эта сумма по всем `rphost` и `rmngr` сравнивается с порогами рабочего сервера.
5. **Пороги памяти рабочего сервера:** «Временно допустимый объем памяти процессов» (`0` → 80% ОЗУ, `-1` → проверка отключена) и «Критический объем памяти процессов» (`0` → 95% ОЗУ, `-1` → проверка отключена). Превышение первого — новые соединения на сервер не назначаются, а по истечении «Интервала превышения…» идёт мягкий перезапуск самых «тяжёлых» рабочих процессов; превышение второго — аварийное завершение и перезапуск рабочих процессов.
6. **Мониторинг опрашивает процессы каждые 5 секунд, таймаут соединения 20 секунд**, опрос ведёт только агент центрального сервера. Отрицательные результаты проверок и превышение критического объёма памяти фиксируются в ТЖ событием `ATTN`.
7. **«Зависшие» процессы не будут убиты средствами ОС**, если в свойствах кластера сброшен флажок «Принудительно завершать рабочие процессы» или «Проблемные процессы завершать через» равно `0`.
8. **Дампы на Linux управляются настройками ОС**, а не `logcfg.xml`: принудительное завершение с дампом делается сигналом `SIGABRT`, обычный аварийный дамп — по `SIGSEGV`. Запись дампа при аварийном завершении из-за превышения критического объёма памяти управляется параметром рабочего сервера «Записывать дамп процесса при превышении критического объема памяти».
9. **Событие `EXCP` в ТЖ — не всегда авария** (например, перебор занятых портов из рабочего диапазона даёт `EXCP` на каждый занятый порт).
10. **Аутентификация администраторов кластера по умолчанию выключена**: любой, кто подключился к центральному серверу, может администрировать и сервер, и кластеры. Она включается автоматически после добавления первого администратора в список; списки администраторов центрального сервера и администраторов кластера независимы.
11. **Уровень безопасности соединения (выключено / только соединение / постоянно) задаётся при создании ИБ и в реестре кластера потом не меняется.** Повысить его можно по инициативе клиента (толстый клиент, внешнее соединение, Конфигуратор) параметром `/SLev`; тонкий клиент всегда использует уровень, заданный при создании ИБ. Уровень «постоянно» может заметно снизить производительность.
12. **Канал «кластер ↔ СУБД» защищается средствами самой СУБД**, а не платформы: шифрование трафика настраивается в клиентских компонентах СУБД, установленных в кластере (все поддерживаемые СУБД могут использовать SSL). Канал «клиент ↔ веб-сервер» защищает веб-сервер (HTTPS), канал «веб-сервер ↔ кластер» — платформа (RSA и Triple DES, дополнительно возможен AES-256 через файлы `wskey.pem`).
13. **Пароли доступа к СУБД в служебных данных кластера хранятся с восстановлением исходного текста (AES128)**, пароли администраторов кластера и центрального сервера — в виде SHA1. Полные права на каталог служебных данных выдаются только пользователю `USR1CV8`; чтобы код конфигураций не имел прямого доступа к служебным данным, рабочие процессы можно запускать от отдельного пользователя ОС через файл `swpuser.ini`.
14. **Монопольный режим 1С — это блокировка механизмов платформы**: приложениям, работающим с базой данных в обход механизмов «1С:Предприятия», исключительная блокировка базы данных не мешает. Открытые сеансы препятствуют переходу в монопольный режим (кроме сеанса консоли кластера), служебные соединения — нет.
15. **Профиль безопасности ограничивает серверный код** по нескольким направлениям из этой части: запуск приложений ОС (шаблоны строки запуска с `%`, `_`, `*`, `\`; пустой список = запуск запрещён), доступ к интернет-ресурсам (адрес, порт, протокол `imap`/`pop3`/`smtp`/`http`/`https`/`ftp`/`ftps`; пустой список = всё запрещено), привилегированный режим, функции криптографии и расширение модулей.
