# Глава 21. Временное хранилище, работа с файлами и картинками

## 21.1. Временное хранилище

- Хранилище значений, **привязанное к сеансу**; основное назначение — временно держать данные при клиент-серверном взаимодействии до переноса в базу данных (типичный случай — передача файла с клиента на сервер, в том числе из веб-клиента).
- Нельзя поместить значения типов, не поддерживающих сериализацию (в том числе внутри коллекций).
- Значение идентифицируется **адресом**, который возвращают методы помещения.
- Время жизни:
  - значение привязано к форме — живёт, пока существует форма;
  - не привязано — удаляется при следующем запросе формы, следующем серверном вызове из клиентского общего модуля, при клиентских вызовах из формы, при серверном вызове из модуля команды (то есть доживает до следующего серверного вызова, где его используют).
- Хранилище одного сеанса недоступно из другого. Исключение — передача результата из фонового задания в сеанс, который его запустил.
- Рекомендация: файлы передавать на сервер именно как файлы и разбирать уже на сервере.

**Где физически лежат данные.** При помещении значение не сериализуется сразу: в хранилище попадает ссылка на значение в кеше; через **20 минут** (с момента помещения или последнего обращения) значение сериализуется, **записывается на диск в хранилище сеансовых данных** и удаляется из кеша. Для администратора это означает: большие объёмы во временном хранилище расходуют сначала память рабочего процесса, а затем место в каталоге сеансовых данных кластера.

## 21.3. Методы (обзорно)

- Помещение: `ПоместитьВоВременноеХранилище()`, помещение файлов с клиента (`ПоместитьФайлНаСерверАсинх()` и родственные методы для одного и нескольких файлов).
- Получение: `ПолучитьИзВременногоХранилища()` (на сервере значение получается по ссылке на кеш); удаление: `УдалитьИзВременногоХранилища()`; проверка адреса: `ЭтоАдресВременногоХранилища()`.
- **Все файловые операции на стороне клиента асинхронные** в любом клиентском приложении; на сервере используются синхронные методы.
- В веб-клиенте для ряда операций нужно расширение работы с файлами и разрешение пользователя (можно запросить разрешение сразу на группу операций).

### 21.3.9. Результат фонового задания

1. Родительский сеанс вызывает `ПоместитьВоВременноеХранилище()` с пустым значением и получает адрес.
2. Адрес передаётся в фоновое задание через его параметры.
3. Фоновое задание вызывает `ПоместитьВоВременноеХранилище()` с этим адресом — результат копируется в родительский сеанс.

Данные становятся доступны родительскому сеансу **только после завершения фонового задания**.

### 21.3.10. Стандартные каталоги

- **Рабочий каталог данных пользователя** — привязан к паре «пользователь + информационная база»; создаётся при первом обращении (если создать нельзя — исключение). Методы: `РабочийКаталогДанныхПользователя()`, `РабочийКаталогДанныхПользователяАсинх()`, `НачатьПолучениеРабочегоКаталогаПользователя()`.
- **Каталог документов** операционной системы — `КаталогДокументов()`, `КаталогДокументовАсинх()`, `НачатьПолученниеКаталогаДокументов()` (так в документации). Физическое расположение зависит от ОС и приведено в синтакс-помощнике.

## 21.4. Картинки (обзорно)

Объект `Картинка` даёт характеристики изображения и операции преобразования; поле картинки в форме умеет показывать картинку по адресу во временном хранилище или в базе данных.

# Глава 25. История данных

## 25.1. Что это

- **История данных (версионирование)** — хранение в базе данных версий объектов: данные объекта на момент изменения и состояние метаданных на этот момент.
- Поддерживается для: общих реквизитов, констант, планов обмена, справочников, документов, планов видов характеристик, планов счетов, планов видов расчёта, бизнес-процессов, задач, **регистров сведений**.
- Включается в конфигураторе или **из встроенного языка — без изменения конфигурации и без снятия её с поддержки**.
- Работа с историей регулируется правами доступа и протоколируется в журнале регистрации.
- **История данных не переносится механизмами распределённой информационной базы.**

## 25.2. Устройство

- **История хранится в специальных таблицах той же информационной базы.** Вместе с данными хранятся версии метаданных версионируемых объектов; типы реквизитов не хранятся — только значения.
- Формирование версии идёт в несколько шагов:
  1. При записи объекта факт изменения попадает в **очередь версий**.
  2. Метод **`ИсторияДанных.ОбновитьИсторию()`** переносит данные из очереди в таблицы истории. До этого версии «не существует» — получить её нельзя. Каждое изменение фиксируется и переносится отдельно, независимо от частоты обновления.
  3. Если для версии запрошена постобработка, она попадает в **очередь постобработки**; обработка выполняется в `ОбработкаПослеЗаписиВерсийИсторииДанных()` модулей менеджера (вызывается из `ОбновитьИсторию()` или `ИсторияДанных.ВыполнитьОбработкуПослеЗаписиВерсий()`).
  4. Обработанную версию нужно явно убрать из очереди постобработки — `ИсторияДанных.УдалитьИзОбработкиПослеЗаписиВерсий()`, иначе она будет передаваться в обработчик снова и снова.
- **Обновление истории нужно запускать регулярно — регламентным заданием** (по аналогии с обновлением индекса полнотекстового поиска). Частота зависит от числа версионируемых объектов и интенсивности изменений. Многоэтапная схема сделана, чтобы снизить нагрузку на базу данных при массовых изменениях.

Следствия для администратора:

- если история включена, а регламентное задание обновления истории не работает (например, регламентные задания заблокированы для базы), **очередь версий растёт**, а в интерфейсе история не появляется;
- история увеличивает размер базы данных — её объём нужно учитывать при планировании места и времени резервного копирования; сократить можно методами удаления версий (ниже).

### Настройка в конфигураторе

- У объекта свойство «История данных» = «Использовать»; затем создаётся регламентное задание обновления истории.
- Значения по умолчанию: сами объекты (справочники, документы, регистры сведений и т. д.) — «Не использовать»; реквизиты, стандартные реквизиты, реквизиты табличных частей, ресурсы регистров сведений — «Использовать»; измерения регистров сведений — всегда «Использовать». То есть объект включается явно, а реквизиты исключаются явно.
- С точки зрения механизма включение версионирования реквизита равносильно созданию реквизита, а отключение — удалению.

## 25.3. Программный интерфейс (свойство глобального контекста `ИсторияДанных`)

### Управление использованием

- Настройки из конфигуратора: `Метаданные.<…>.ИсторияДанных`.
- Настройки, сделанные в режиме предприятия: `ПолучитьНастройки(<объект метаданных>)` → `НастройкиИсторииДанных` (`Неопределено` — изменений относительно конфигуратора нет); `УстановитьНастройки()` со свойствами `Использование` и `ИспользованиеПолей` (соответствие «имя реквизита → признак»; реквизит табличной части — `ТабличнаяЧасть.Реквизит`). Вызов `УстановитьНастройки()` со вторым параметром `Неопределено` возвращает настройки к заданным в конфигурации.
- `ПолучитьМетаданные()` — все реквизиты объекта, попадающие в историю.

### Запись версии

- Автоматически при любой записи версионируемого объекта. Через свойство объекта `ЗаписьИсторииДанных` можно:
  - **отказаться от версии** — `ЗаписьИсторииДанных.Отказ = Истина` (например, при массовых служебных изменениях);
  - добавить дополнительные данные — `ДобавитьДополнительныеДанные(Имя, Значение, Представление)`;
  - запросить постобработку и ускоренную обработку — свойства `ВыполнятьОбработкуПослеЗаписиВерсии`, `ОбновлятьИсториюСразуПослеЗаписи`.
- `ЗаписатьВерсию()` — запись сразу в таблицы истории, минуя очередь (для переноса истории из другого хранилища).
- **Ускоренная обработка** (история формируется сразу, без ожидания регламентного задания): флажок объекта «Обновлять историю данных сразу после записи» — **не рекомендуется для объектов с большим числом элементов и интенсивными изменениями**; либо свойство `ОбновлятьИсториюСразуПослеЗаписи` при записи; либо `ОбновитьИсторию(<объект>)`.

### Чтение, комментарии, различия (обзорно)

- Список версий с отбором (только условия равенства); получение данных версии; комментарий к версии — `ЗаписатьКомментарий()`, до 1024 символов; различия — `ПолучитьРазличияВерсий()` (сравниваются две указанные версии без анализа промежуточных).

### Удаление версий

`УдалитьВерсии()`:

| Вызов | Что удаляет |
|---|---|
| `УдалитьВерсии(Метаданные.Справочники.Товары)` | всю историю объекта конфигурации |
| `УдалитьВерсии(Метаданные.Справочники.Товары, <дата>)` | историю объекта конфигурации ранее даты |
| `УдалитьВерсии(<ссылка>, <начало>, <окончание>)` | версии одного объекта данных за интервал |
| `УдалитьВерсии(<ссылка>, <дата>)` | версии одного объекта данных ранее даты |

Всю историю в базе удаляет также метод глобального контекста `УдалитьДанныеИнформационнойБазы()` (он удаляет не только историю — см. `dev-gl24-razdelenie-dannyh.md`).

### История данных и расширения

- Собственный объект расширения: история ведётся как обычно; **после полного удаления расширения история удаляется**.
- Заимствованный объект: настраивается история только для реквизитов, добавленных расширением; удаление расширения историю не очищает.
