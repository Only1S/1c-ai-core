## Настройка центрального сервера кластера «1С:Предприятия» (подраздел без номера; Kerberos на Linux)

> ⚠ В источнике неясно: в этой части подраздел идёт без номера (заголовок самого нижнего уровня) и начинается с середины раздела. Номер родительского раздела и предшествующие шаги (настройка контроллера домена, создание файла секретного ключа) находятся в части 1 главы 3.

**Исходное условие:** кластер серверов «1С:Предприятия» уже установлен и работает на центральном сервере кластера.

### Данные примера, на котором построен раздел

| Объект | Значение в примере |
|---|---|
| Домен (DNS-суффикс поиска) | `krb.local` |
| Realm Kerberos | `KRB.LOCAL` — по документации это NETBIOS-имя контроллера домена, которое, как правило, равно имени домена в верхнем регистре |
| Контроллер домена (он же DNS-сервер и KDC) | `main` / `main.krb.local`, IP `192.168.29.150`, KDC на порту `88` |
| Центральный сервер кластера 1С | `srv1c` / `srv1c.krb.local` |
| Доменный пользователь для проверки | `user` (`user@KRB.LOCAL`) |
| Имя службы (principal) сервера 1С | `usr1cv8/srv1c.krb.local@KRB.LOCAL` |
| Файл секретного ключа | `usr1cv8.keytab` (получен при настройке контроллера домена) |
| Каталог установки сервера 1С (по умолчанию) | `/opt/1cv8/i386/A.B.C.D` (32-разрядная версия) или `/opt/1cv8/x86_64/A.B.C.D` (64-разрядная версия) |
| Владелец/группа/права файла ключа | `usr1cv8:grp1cv8`, `600` |

KDC (Key Distribution Center, центр распределения ключей) — эту роль выполняет контроллер домена.

### Шаг 1. DNS-сервер для центрального сервера кластера

- Сервером DNS для центрального сервера кластера должен быть DNS контроллера домена.
- Способ настройки зависит от дистрибутива Linux; в примере документации вручную правится `/etc/resolv.conf` — туда вписывается IP-адрес контроллера домена и домен поиска.

Итоговое содержимое файла по документации:

```
nameServer 192.168.29.150
search krb.local
```

> ⚠ В источнике неясно: ключ записан как `nameServer` (с заглавной S) — написание передано как в текстовой копии документации; возможно, это искажение регистра при вёрстке.

Проверка разрешения имён — командой `ping` по короткому имени контроллера домена:

```
srv1c:~# ping main -c 1
PING main.krb.local (192.168.29.150) 56(84) bytes of data.
64 bytes from 192.168.29.150: icmp_seq=1 ttl=128 time=0.177 ms
--- main.krb.local ping statistics ---
1 packets transmitted, 1 received, 0% packet loss, time 0ms
```

Признак успеха: короткое имя `main` разворачивается в `main.krb.local` и получен ответ.

> Примечание к листингам: в текстовой копии источника в ряде строк листингов пропали пробелы (например, после приглашения `srv1c:~#` и внутри вывода `ping`); в конспекте пробелы в командах восстановлены, сами команды, ключи и значения не менялись.

### Шаг 2. Синхронизация времени

- **Важно:** у компьютеров, участвующих в аутентификации, системные часы не должны заметно расходиться — аутентификационные пакеты (тикеты) действуют ограниченное время.
- Время центрального сервера кластера синхронизируется с контроллером домена командой `ntpdate`:

```
srv1c:~# ntpdate main
4 Jun 11:51:53 ntpdate[2527]: step time Server 192.168.29.150 offset -56.766439 sec
```

### Шаг 3. Настройка Kerberos — файл `/etc/krb5.conf`

Для настройки нужно знать NETBIOS-имя контроллера домена (в примере `KRB.LOCAL`). Файл из документации:

```
[logging]
Default = FILE:/var/log/krb5libs.log
Kdc = FILE:/var/log/krb5kdc.log
admin_Server = FILE:/var/log/kadmind.log
[libdefaults]
default_realm = KRB.LOCAL
dns_lookup_realm = false
dns_lookup_kdc = false
default_tkt_enctypes = rc4-hmac
default_tgs_enctypes = rc4-hmac
[realms]
KRB.LOCAL = {
kdc=main.krb.local:88
default_domain=krb.local
}
[domain_realm]
krb.local = KRB.LOCAL
.krb.local = KRB.LOCAL
KRB.LOCAL = KRB.LOCAL
.KRB.LOCAL = KRB.LOCAL
[kdc]
Profile = /var/kerberos/krb5kdc/kdc.conf
[appdefaults]
Pam = {
Debug = true
ticket_lifetime = 36000
renew_lifetime = 36000
forwardable = false
krb4_convert = false
}
```

> ⚠ В источнике неясно: регистр ключей `Default`, `Kdc`, `admin_Server`, `Profile`, `Pam`, `Debug` передан так, как он записан в текстовой копии документации; возможно, это искажение регистра при вёрстке.

Параметры файла из примера (секция → параметр → значение в примере):

| Секция | Параметр | Значение в примере |
|---|---|---|
| `[logging]` | `Default` | `FILE:/var/log/krb5libs.log` |
| `[logging]` | `Kdc` | `FILE:/var/log/krb5kdc.log` |
| `[logging]` | `admin_Server` | `FILE:/var/log/kadmind.log` |
| `[libdefaults]` | `default_realm` | `KRB.LOCAL` |
| `[libdefaults]` | `dns_lookup_realm` | `false` |
| `[libdefaults]` | `dns_lookup_kdc` | `false` |
| `[libdefaults]` | `default_tkt_enctypes` | `rc4-hmac` (если RC4-HMAC не поддерживается — `des-cbc-crc des-cbc-md5`) |
| `[libdefaults]` | `default_tgs_enctypes` | `rc4-hmac` (если RC4-HMAC не поддерживается — `des-cbc-crc des-cbc-md5`) |
| `[realms]` → `KRB.LOCAL` | `kdc` | `main.krb.local:88` |
| `[realms]` → `KRB.LOCAL` | `default_domain` | `krb.local` |
| `[domain_realm]` | `krb.local`, `.krb.local`, `KRB.LOCAL`, `.KRB.LOCAL` | все отображаются в `KRB.LOCAL` |
| `[kdc]` | `Profile` | `/var/kerberos/krb5kdc/kdc.conf` |
| `[appdefaults]` → `Pam` | `Debug` | `true` |
| `[appdefaults]` → `Pam` | `ticket_lifetime` | `36000` |
| `[appdefaults]` → `Pam` | `renew_lifetime` | `36000` |
| `[appdefaults]` → `Pam` | `forwardable` | `false` |
| `[appdefaults]` → `Pam` | `krb4_convert` | `false` |

Вариант для случая, когда алгоритм RC4-HMAC не поддерживается:

```
default_tkt_enctypes = des-cbc-crc des-cbc-md5
default_tgs_enctypes = des-cbc-crc des-cbc-md5
```

### Шаг 4. Проверка системы аутентификации (kinit / klist / kdestroy)

| Команда | Что делает в рамках проверки | Признак успеха |
|---|---|---|
| `kinit <имя>` | Запрашивает тикет для произвольного пользователя, зарегистрированного в домене (в примере `user`); спрашивает пароль | Никаких сообщений после ввода пароля |
| `klist` | Показывает локальный кеш тикетов | В кеше есть ticket-granting ticket от KDC: `krbtgt/KRB.LOCAL@KRB.LOCAL` |
| `kdestroy` | Очищает локальный кеш тикетов — возврат в исходное состояние перед следующими шагами | — |

```
srv1c:~# kinit user
Password for user@KRB.LOCAL:
srv1c:~# klist
Ticket cache: FILE:/tmp/krb5cc_0
Default principal: user@KRB.LOCAL
Valid starting Expires Service principal
06/04/08 11:29:21 06/04/08 21:28:28 krbtgt/KRB.LOCAL@KRB.LOCAL
renew until 06/05/08 11:29:21
Kerberos 4 ticket cache: /tmp/tkt0
Klist : You have no tickets cached
srv1c:~# kdestroy
```

### Шаг 5. Размещение файла секретного ключа `usr1cv8.keytab`

- Файл `usr1cv8.keytab`, полученный при настройке контроллера домена, любым способом передаётся на центральный сервер кластера.
- Место по умолчанию — каталог, в который установлен сервер «1С:Предприятия»: `/opt/1cv8/i386/A.B.C.D` либо `/opt/1cv8/x86_64/A.B.C.D` (64-разрядная версия).
- Владелец и права задаются так:

```
srv1c:~# cd /opt/1cv8/i386/A.B.C.D
srv1c:i386# chown usr1cv8:grp1cv8 usr1cv8.keytab
srv1c:i386# chmod 600 usr1cv8.keytab
```

- **Другое расположение файла** допустимо: тогда в конфигурационном файле нужно изменить переменную `SRV1CV8_KEYTAB`, чтобы она указывала на новое место файла с секретным ключом.

> ⚠ В источнике неясно: в этой части не уточняется, о каком именно конфигурационном файле идёт речь для переменной `SRV1CV8_KEYTAB` (сказано только «в конфигурационном файле»).

### Шаг 6. Проверка содержимого keytab-файла

```
srv1c:~# klist -e -k -t /opt/1cv8/i386/A.B.C.D/usr1cv8.keytab
```

Ожидаемый вывод для примера (RC4-HMAC):

```
Keytab name: FILE: /opt/1cv8/i386/A.B.C.D/usr1cv8.keytab
KVNO Principal
---- -------------------------------------------------------------
13 usr1cv8/srv1c.krb.local@KRB.LOCAL (ArcFour with HMAC/md5)
```

Если RC4-HMAC не поддерживается, строка ключа выглядит так:

```
13 usr1cv8/srv1c.krb.local@KRB.LOCAL (DES cbc mode with RSA-MD5)
```

Что проверять в выводе:

| Что смотрим | Что должно быть |
|---|---|
| Колонка `Principal` | То самое имя службы, которое задавалось при создании файла секретного ключа (`usr1cv8/srv1c.krb.local@KRB.LOCAL`) |
| Алгоритм шифрования в скобках | `ArcFour with HMAC/md5` — для RC4-HMAC; `DES cbc mode with RSA-MD5` — для DES |

### Шаг 7. Проверка работы Kerberos без пароля, по секретному ключу

Команде `kinit` указывается взять аутентификационные данные из keytab-файла и прочитать оттуда ключ службы `usr1cv8/srv1c.krb.local@KRB.LOCAL`:

```
srv1c:~# kinit -k -t /opt/1cv8/i386/A.B.C.D/usr1cv8.keytab usr1cv8/srv1c.krb.local@KRB.LOCAL
```

(для 64-разрядной версии путь к файлу — `/opt/1cv8/x86_64/A.B.C.D/usr1cv8.keytab`).

Признак успеха: `kinit` отрабатывает молча, пароль не спрашивает и возвращает управление в командную строку.

Затем результат смотрят командой `klist`. При успехе:

```
srv1c:~# klist
Ticket cache: FILE:/tmp/krb5cc_0
Default principal: usr1cv8/srv1c.krb.local@KRB.LOCAL
Valid starting Expires Service principal
06/04/08 11:44:54 06/04/08 21:43:58 krbtgt/KRB.LOCAL@KRB.LOCAL
renew until 06/05/08 11:44:54
Kerberos 4 ticket cache: /tmp/tkt0
klist: You have no tickets cached
```

Если что-то настроено неверно:

```
srv1c:~# klist
klist: No credential scache found (ticket cache FILE:/tmp/krb5cc_1000)
Kerberos 4 ticket cache: /tmp/tkt1000
klist: You have no tickets cached
```

(текст сообщения «No credential scache found» приведён так, как записан в источнике).

### Итог настройки

- Успешная проверка означает, что с этого момента сервер кластера «1С:Предприятия» способен обрабатывать запросы на аутентификацию.
- **Перезапуск сервера не требуется.** Исключение — случай, когда в конфигурационном файле было изменено расположение файла с секретным ключом (переменная `SRV1CV8_KEYTAB`).

Сводка команд раздела:

| Команда | Назначение |
|---|---|
| `ping main -c 1` | Проверка DNS (разрешение имени контроллера домена) |
| `ntpdate main` | Синхронизация времени с контроллером домена |
| `cat /etc/krb5.conf` | Просмотр конфигурации Kerberos |
| `kinit <имя>` | Получение тикета для доменного пользователя (с вводом пароля) |
| `klist` | Просмотр кеша тикетов |
| `kdestroy` | Очистка локального кеша тикетов |
| `chown usr1cv8:grp1cv8 usr1cv8.keytab` | Назначение владельца файла ключа |
| `chmod 600 usr1cv8.keytab` | Права на файл ключа |
| `klist -e -k -t <путь>/usr1cv8.keytab` | Просмотр записей keytab-файла с типом шифрования |
| `kinit -k -t <путь>/usr1cv8.keytab usr1cv8/srv1c.krb.local@KRB.LOCAL` | Получение тикета по ключу из keytab, без пароля |

## 3.2. Установка серверов баз данных

## 3.2.1. Общая информация

СУБД, которые могут выступать сервером баз данных «1С:Предприятия»:

| СУБД | ОС, для которых указана | Ограничения по архитектуре кластера серверов (из разделов 3.2.2–3.2.4) |
|---|---|---|
| IBM Db2 | Windows и Linux | Не поддерживается, если кластер серверов работает на процессорах ARM64 или E2K |
| Microsoft SQL Server | только Windows | Не поддерживается, если кластер серверов работает на процессорах ARM64 или E2K |
| Oracle Database | Windows и Linux | Не поддерживается, если кластер серверов работает на процессорах E2K |
| PostgreSQL | Windows и Linux | В источнике ограничений по архитектуре не указано |

## 3.2.2. Установка IBM Db2

- **Ограничение:** не поддерживается при использовании кластера серверов на процессорах архитектуры ARM64 или E2K.
- Сервер ставится с дистрибутивов IBM Db2.
- Поддерживаемые версии IBM Db2 опубликованы на сайте http://v8.1c.ru/requirements/.

**Групповая переменная реестра `DB2_WORKLOAD`.** Для упрощения настройки под «1С:Предприятие» в IBM Db2 предусмотрено значение `1C` этой переменной: при `DB2_WORKLOAD=1C` Db2 сам выставляет все нужные переменные реестра для оптимальной работы с платформой.

| Команда | Назначение | Примечание |
|---|---|---|
| `db2set DB2_WORKLOAD=1C` | Задать значение групповой переменной реестра | После установки значения сервер баз данных нужно перезапустить |
| `db2set -gd DB2_WORKLOAD=1C` | Показать список переменных реестра IBM Db2 и их значений, которые соответствуют `DB2_WORKLOAD=1C` | Позволяет заранее узнать, что будет выставлено |

```
db2set DB2_WORKLOAD=1C
db2set -gd DB2_WORKLOAD=1C
```

> ⚠ В источнике неясно: в первой команде значение записано латиницей (`1C`), а во второй команде и в окружающем тексте — с кириллической «С» (`1С`). В конспекте обе команды приведены с латинской `C`, как в первой.

**Если сервер «1С:Предприятия» запущен как сервис**, требуется:

- включить пользователя, от имени которого запускается сервер «1С:Предприятия» (по умолчанию `USR1CV8`), в группу `DB2ADMNS`;
- для используемой копии Db2 установить параметр `SYSADM_GROUP` в значение `DB2ADMNS`.

Ссылки из документации:

| Тема | Адрес |
|---|---|
| Назначение переменных реестра профиля IBM Db2 | http://www.ibm.com/support/knowledgecenter/en/SSEPGG_11.1.0/com.ibm.db2.luw.admin.regvars.doc/doc/c0012181.html |
| Синтаксис команды `db2set` | http://www.ibm.com/support/knowledgecenter/en/SSEPGG_11.1.0/com.ibm.db2.luw.admin.cmd.doc/doc/r0002025.html |
| Установка IBM Db2 v11.1 (англ.) | http://www.ibm.com/support/knowledgecenter/SSEPGG_11.1.0/com.ibm.db2.luw.qb.server.doc/doc/r0025127.html |

## 3.2.3. Установка Microsoft SQL Server

**Только Windows** (по разделу 3.2.1 эта СУБД — только для Windows), кратко:

- **Ограничение:** не поддерживается при использовании кластера серверов на процессорах архитектуры ARM64 или E2K.
- Ставится с дистрибутивных носителей Microsoft SQL Server.
- Для Microsoft SQL Server 2000 обязателен Service Pack 2 (рекомендуется Service Pack 4) — иначе безошибочная работа «1С:Предприятия» не обеспечивается.
- Пользователь, от имени которого сервер «1С:Предприятия» обращается к MS SQL Server, должен входить в фиксированную серверную роль `processadmin` или `sysadmin`.
- Документация содержит ссылки на инструкции по установке для версий: 2005, 2008, 2008 R2, 2012, 2014, 2016 (msdn.microsoft.com), 2017, 2019 (docs.microsoft.com), 2022 (learn.microsoft.com).

## 3.2.4. Установка Oracle Database

- **Ограничение:** не поддерживается при использовании кластера серверов на процессорах архитектуры E2K.
- Ставится с дистрибутивов Oracle Database.
- Поддерживаемые версии Oracle Database опубликованы на сайте http://v8.1c.ru/requirements/.

Ссылки на документацию по установке (все на английском языке):

| База данных | Схема данных |

При создании информационной базы в «1С:Предприятии» в Oracle Database создаётся пользователь и его схема данных.

**Табличные пространства (tablespace), которые использует «1С:Предприятие 8»:**

| Имя | Назначение | Поведение |
|---|---|---|
| `V81C_DATA` | данные | Если существует — используется; если нет — создаётся при создании информационной базы, datafiles получают пути по умолчанию |
| `V81C_INDEX` | индексы | то же |
| `V81C_LOB` | LOB | то же |
| `V81C_TEMP` | временные файлы | то же |
| `V81_INDEX_BIG` | индексы | Создаётся, когда создание индекса привело к ошибке `ORA-01450`; если такое табличное пространство уже есть — используется оно |

> Имя `V81_INDEX_BIG` приведено так, как записано в источнике (без буквы `C` после `V81`, в отличие от остальных четырёх).

**Обязательный параметр DATABASE:** при создании DATABASE параметр `CHARACTER SET` должен быть установлен в `AL32UTF8`.

**Настройка multilingual collation** — выполняется до начала использования сервера Oracle Database с «1С:Предприятием»:

1. Скопировать файл `lx327c6.nlt` из каталога `Additional\OracleDatabase` дистрибутивного диска «1С:Предприятия» в пустой каталог на жёстком диске компьютера с Oracle Database.
2. Запустить Oracle Locale Builder (`lbuilder`).
3. Запустить генерацию nlb-файлов (меню Tools — Generate NLB), указав папку с файлом `lx327c6.nlt`.
4. Остановить все сервисы Oracle Database, запущенные из домашнего каталога Oracle Database (`ORACLE_HOME`).
5. Сделать резервную копию файлов `lx0boot.nlb` и `lx1boot.nlb` из папки `ORACLE_HOME/nls/data`.
6. Скопировать файлы `lx1boot.nlb` и `lx327c6.nlb` из папки, где их создал Oracle Locale Builder, в `ORACLE_HOME/nls/data`; на предложение перезаписать `lx1boot.nlb` ответить утвердительно.
7. Запустить сервисы Oracle Database.

## 3.2.5. Установка PostgreSQL

### 3.2.5.1. Общая информация

- Сервер баз данных устанавливается с дистрибутивных носителей «1С:Предприятия».
- СУБД PostgreSQL может работать под управлением как Windows, так и Linux.
- **Кодировка:** при инициализации кластера базы данных следует указывать `UTF-8`.

**Табличные пространства (tablespace), которые поддерживает «1С:Предприятие 8» при работе с PostgreSQL:**

| Имя | Назначение | Поведение |
|---|---|---|
| `v81c_data` | данные | Если существует — используется; если нет — рекомендуется создать |
| `v81c_index` | индексы | Если существует — используется; если нет — рекомендуется создать |
| `pg_default` | — | Используется, когда указанных выше табличных пространств нет |

Команды создания из документации (`<Имя папки>` — полный путь к каталогу, в котором будут лежать файлы создаваемого табличного пространства):

```sql
create tablespace v81c_index location <Имя папки>;
create tablespace v81c_data location <Имя папки>;
```

**Какая сборка PostgreSQL нужна:**

- Для совместной работы с «1С:Предприятием» необходима **модифицированная версия PostgreSQL**.
- Где взять: диск ИТС или https://releases.1c.ru/project/AddCompPostgre (нужен доступ к разделу технической поддержки).

**С кластерами каких версий PostgreSQL может работать «1С:Предприятие»** (кластер, созданный с использованием указанных версий):

| Версия PostgreSQL | Условие / примечание |
|---|---|
| PostgreSQL `8.1.5-X.1C` — `9.1.2-1.1C` | — |
| PostgreSQL `9.2.1-2.1C` | — |
| Стандартная версия PostgreSQL | Только при совпадении национальных установок (locale) кластера и создаваемой информационной базы. Работа с кластером, созданным стандартной версией PostgreSQL, допускается только с использованием дистрибутива PostgreSQL, выпущенного фирмой «1С» |

**Совместимость версий платформы и PostgreSQL:**

- Изменение версии «1С:Предприятия» (и повышение, и понижение) без смены версии PostgreSQL не требует никаких дополнительных действий.
- Информационные базы, созданные с использованием PostgreSQL версии `9.2.1-2.1C` и выше, невозможно использовать с более ранними версиями «1С:Предприятия» — `8.3.2` и ранее.
- Следствие: не следует создавать информационные базы на PostgreSQL версии `9.2.1-2.1C`, если с такой базой потребуется работать более ранними версиями платформы.

### 3.2.5.2. Установка PostgreSQL для Windows

**Только Windows**, кратко: распаковать zip-архив с дистрибутивом PostgreSQL → запустить `postgresql-<Версия>-1.1C.msi` (`<Версия>` — номер устанавливаемой версии PostgreSQL) → следовать указаниям программы установки.

### 3.2.5.3. Установка PostgreSQL для Linux

Документация описывает установку модифицированной версии PostgreSQL из rpm-пакетов. Пакеты ставятся **в указанном порядке**:

| № | Пакет |
|---|---|
| 1 | `postgresql-libs-8.3.<X>-<Y>.1C.i386.rpm` |
| 2 | `postgresql-8.3.<X>-<Y>.1C.i386.rpm` |
| 3 | `postgresql-Server-8.3.<X>-<Y>.1C.i386.rpm` |
| 4 | `postgresql-contrib-8.3.<X>-<Y>.1C.i386.rpm` |

`<X>` и `<Y>` — соответствующие позиции в номере версии PostgreSQL.

> ⚠ В источнике неясно: сказано, что дистрибутив модифицированной версии PostgreSQL «состоит из 11 пакетов», но перечислено только четыре (приведены выше). Имя третьего пакета записано с заглавной буквой — `postgresql-Server-...` — так в источнике.

**Что появляется в системе после установки пакетов:**

| Объект | Описание |
|---|---|
| Пользователь `postgres` | Создаётся в системе при установке |
| Скрипт `/etc/init.d/postgresql` | Запуск и остановка СУБД |

**Первичное создание базы (инициализация):**

1. Задать желаемое значение переменной окружения `LANG`.
2. Запустить `/etc/init.d/postgresql` — при первом запуске выполняется первичное создание базы.

Одной командой:

```
LANG=ru_RU.utf-8 /etc/init.d/postgresql start
```

| Параметр | Значение |
|---|---|
| Каталог созданной базы | `/var/lib/pgsql/data` |
| Требуемые права | Все действия раздела выполняются с правами суперпользователя (`root`) |
| Локаль в примере | `ru_RU.utf-8` (через `LANG`) |

Пакеты формата deb, дистрибутивы Ubuntu/Debian, 64-разрядные сборки и версии PostgreSQL новее упомянутых в этой части документации не описаны.

## Что важно администратору Linux

1. **PostgreSQL инициализируется в UTF-8.** Документация требует кодировку `UTF-8` при инициализации кластера базы данных; локаль в примере задаётся переменной `LANG=ru_RU.utf-8` перед первым запуском СУБД.
2. **Нужна сборка PostgreSQL от фирмы «1С».** Требуется модифицированная версия (диск ИТС или https://releases.1c.ru/project/AddCompPostgre, нужен доступ к техподдержке). Кластер, созданный стандартной версией PostgreSQL, допускается только при совпадении locale кластера и создаваемой информационной базы и только при использовании дистрибутива PostgreSQL, выпущенного «1С».
3. **Табличные пространства `v81c_data` и `v81c_index`.** Если они существуют, платформа разместит в них данные и индексы соответственно; если их нет — используется `pg_default`. Документация рекомендует их создать (`create tablespace ... location ...`).
4. **Смена версии платформы без смены версии PostgreSQL** (в любую сторону) никаких действий со стороны СУБД не требует.
5. **Обратная несовместимость:** базы, созданные на PostgreSQL `9.2.1-2.1C` и выше, не работают с платформой `8.3.2` и более ранними.
6. **Описание установки PostgreSQL для Linux в этой главе ограничено** rpm-пакетами версии `8.3.<X>-<Y>.1C` для i386, скриптом `/etc/init.d/postgresql` и каталогом данных `/var/lib/pgsql/data`. Про Ubuntu, deb-пакеты и актуальные версии PostgreSQL в этой части ничего нет; кроме того, заявлено 11 пакетов, а перечислено 4. Ссылки на http://v8.1c.ru/requirements/ для PostgreSQL в этой части нет (она дана только для IBM Db2 и Oracle Database).
7. **Kerberos на Linux-сервере 1С — предварительные условия:** DNS-сервером центрального сервера кластера должен быть DNS контроллера домена (в примере — правка `/etc/resolv.conf`), а часы должны быть синхронизированы с контроллером домена (`ntpdate`): большое расхождение системных часов не допускается, поскольку тикеты имеют ограниченное время действия.
8. **`/etc/krb5.conf`:** в примере `default_realm = KRB.LOCAL`, `dns_lookup_realm = false`, `dns_lookup_kdc = false`, KDC `main.krb.local:88`, типы шифрования `default_tkt_enctypes` / `default_tgs_enctypes` = `rc4-hmac`; если RC4-HMAC не поддерживается — `des-cbc-crc des-cbc-md5`.
9. **Файл ключа `usr1cv8.keytab`:** по умолчанию кладётся в каталог установки сервера (`/opt/1cv8/x86_64/A.B.C.D` для 64-разрядной версии, `/opt/1cv8/i386/A.B.C.D` для 32-разрядной), владелец `usr1cv8:grp1cv8`, права `600`. Другое место задаётся переменной `SRV1CV8_KEYTAB` в конфигурационном файле.
10. **Порядок проверки Kerberos:** `kinit <пользователь>` → `klist` → `kdestroy`; затем `klist -e -k -t <keytab>` (principal `usr1cv8/<fqdn-сервера>@<REALM>` и тип шифрования) → `kinit -k -t <keytab> <principal>` (должен отработать молча, без запроса пароля) → `klist` (должен показать `krbtgt/<REALM>@<REALM>` для principal службы).
11. **Перезапуск сервера 1С после настройки Kerberos не нужен** — кроме случая, когда менялось расположение keytab-файла в конфигурационном файле.
12. **Ограничения по архитектуре процессоров кластера серверов:** IBM Db2 и Microsoft SQL Server не поддерживаются для кластера на ARM64 и E2K, Oracle Database — на E2K. Microsoft SQL Server как СУБД указан только для Windows.
13. **Db2 и Oracle на Linux (если понадобятся):** для Db2 — `db2set DB2_WORKLOAD=1C` с последующим перезапуском СУБД, а если сервер 1С запущен как сервис — его пользователь (по умолчанию `USR1CV8`) в группе `DB2ADMNS` и `SYSADM_GROUP=DB2ADMNS`; для Oracle — `CHARACTER SET AL32UTF8`, табличные пространства `V81C_DATA` / `V81C_INDEX` / `V81C_LOB` / `V81C_TEMP` и обязательная настройка multilingual collation файлом `lx327c6.nlt` до начала работы.
