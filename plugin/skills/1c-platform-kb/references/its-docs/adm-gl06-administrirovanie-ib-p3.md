### 6.6.4. Параметры с доступом только из встроенного языка

Два параметра информационной базы не имеют интерактивной настройки — читаются и меняются только кодом на встроенном языке:

| Параметр | Методы встроенного языка | Примечание |
|---|---|---|
| Часовой пояс информационной базы | `ПолучитьЧасовойПоясИнформационнойБазы()` / `УстановитьЧасовойПоясИнформационнойБазы()` | — |
| Год начала столетия | `ПолучитьНачалоСтолетияИнформационнойБазы()` / `УстановитьНачалоСтолетияИнформационнойБазы()` / `НачалоСтолетияСеанса()` | Нужен, чтобы восстановить полный год по двум последним цифрам. Значение по умолчанию — `1950`: тогда «49» трактуется как 2049, а «50» — как 1950 |

Поведение при установке параметра внутри транзакции — что вернёт метод получения:

| Где читают | Ситуация | Что возвращается |
|---|---|---|
| Тот же сеанс | до окончания транзакции | последнее установленное значение |
| Тот же сеанс | после фиксации | последнее установленное значение |
| Тот же сеанс | после отмены | значение, действовавшее на начало транзакции |
| Другой сеанс | чтение вне транзакции, блокировочные СУБД (Microsoft SQL Server, IBM Db2) | последнее установленное значение — не позднее чем через 20 секунд после установки; при отмене транзакции — значение на начало транзакции, не позднее чем через 20 секунд после отмены |
| Другой сеанс | чтение в транзакции, а также версионные СУБД (файловый вариант, PostgreSQL, Oracle Database) | последнее установленное значение — не позднее чем через 20 секунд после фиксации той транзакции, где оно было установлено |

В клиент-серверном варианте значение, установленное из клиентского кода толстого клиента, сразу видно серверному коду, и наоборот.

## 6.7. Выгрузка информационной базы в файл

- Запуск: Конфигуратор, меню **Администрирование — Выгрузить информационную базу данных в файл**; далее стандартный диалог выбора каталога и имени файла.
- Состав выгрузки: все данные самой ИБ плюс данные всех подключённых хранилищ двоичных данных. Хранилище двоичных данных попадает в выгрузку при двух условиях: выгрузка идёт из клиент-серверной ИБ и для этой ИБ хранилище создано.
- Назначение механизма:
  - получить образ ИБ, не зависящий от способа хранения данных;
  - перенести ИБ между СУБД или между СУБД и файловым вариантом (в любую сторону).
- Перед выгрузкой советуют прогнать тестирование ИБ (конфигуратором или отдельной утилитой) и устранить найденные проблемы.
- Использовать выгрузку как способ резервного копирования **не рекомендуется**. Причины:
  - если в исходной базе были ошибки, файл выгрузки может оказаться незагружаемым;
  - выгрузка идёт долго;
  - нужен монопольный доступ к базе;
  - большие затраты оперативной памяти.
- Примечание: монопольный режим ИБ не переключает базу MS SQL в однопользовательский режим (single user).

## 6.8. Загрузка информационной базы из файла

- Запуск: Конфигуратор, меню **Администрирование — Загрузить информационную базу данных из файла**; далее стандартный диалог выбора файла.
- Свободное место под временные файлы: примерно столько же, сколько занимает загружаемая ИБ в развёрнутом виде. Где именно оно требуется:
  - файловый вариант — на компьютере, где выполняется загрузка;
  - клиент-серверный вариант — на компьютере сервера «1С:Предприятия».
- Итоговая база данных может быть в несколько раз больше исходного файла `.dt`.
- **Текущая ИБ при загрузке заменяется полностью.**
- Только MS SQL Server: для ускорения загрузки модель восстановления базы советуют ставить «Простой» или «С неполным протоколированием» — на время загрузки или постоянно (если не нужно восстановление на произвольный момент времени). Перед сменой модели восстановления — сделать резервную копию базы.
- Совместимость файлов `.dt` по версиям:
  - `.dt`, созданный версиями 8.1 и 8.2, загружается в 8.3;
  - если режим совместимости конфигурации платформе неизвестен — выдаётся ошибка с указанием требуемой версии;
  - файл `1cv8.dt`, созданный в 8.3.1 и новее, запрещено загружать в версиях младше 8.3.1. Исключение — когда в 8.3.1 и выше свойство конфигурации «Режим совместимости» равно «Версия 8.2.16».

## 6.9. Резервное копирование информационной базы

### 6.9.1. Файловый вариант информационной базы

- Копию нужно делать перед любой операцией, способной повредить данные ИБ.
- Во время создания копии и во время восстановления к файловой ИБ не должно быть ни одного подключения, включая конфигуратор.
- Способ: любым файловым менеджером скопировать файл `1Cv8.1CD` из каталога ИБ в отдельный каталог. Восстановление — вернуть сохранённый файл в прежний каталог. (В этом месте источника имя файла набрано с кириллической «С»; в разделе 6.10.2 то же имя — латиницей, `1Cv8.1CD`.)
- Допустимо применять и специализированные программы резервного копирования и восстановления.
- В копию рекомендуется включать журнал регистрации — подкаталог `1Cv8Log` каталога ИБ. Восстанавливать базу тогда желательно вместе с этим каталогом: будет видна история действий до момента создания копии.

### 6.9.2. Клиент-серверный вариант информационной базы

- Копию нужно делать перед любой операцией, способной повредить данные ИБ.
- Во время восстановления средствами СУБД к ИБ не должно быть никаких подключений: ни конфигуратора, ни клиентских приложений, ни фоновых и регламентных заданий, ни средств администрирования.
- Рекомендуемый инструмент — штатные средства используемой СУБД.

Порядок резервного копирования:

1. Копия самой базы данных.
2. Копия журнала регистрации — если после восстановления нужно иметь возможность его просматривать.
3. Копия хранилища двоичных данных — делается средствами встроенного языка или стандартной функцией «Управление хранилищем двоичных данных».

Порядок восстановления (тот же):

1. База данных из резервной копии.
2. Журнал регистрации (если копировался). **Восстанавливать журнал регистрации нужно при остановленном кластере серверов.**
3. Хранилище двоичных данных (если копировалось).

### 6.9.3. Мобильное устройство

- На мобильной платформе: в iOS — штатные средства ОС, в Android — специализированные программы.
- Можно настроить копирование прямо на устройстве, в двух вариантах: перед обновлением приложения; автоматически (перед запуском приложения).
- Путь к настройке: диалог изменения свойств приложения → кнопка **Администрирование** → пункт **Резервное копирование**.

Настройки формы:

| Настройка | Назначение | Умолчание / особые значения |
|---|---|---|
| Расположение резервных копий (на этом устройстве) | путь в локальной файловой системе устройства для копий | по умолчанию каталог `backup` в каталоге документов устройства |
| Создавать резервную копию при обновлении приложения | включает копирование перед обновлением | переключатель |
| Период автоматического создания резервных копий (дней) | периодичность автокопирования | `0` — автокопирование отключено; иначе копия делается перед фактическим запуском приложения, если с предыдущей копии прошло больше указанного срока |
| Количество резервных копий | размер хранимого стека копий | `0` — число копий системой не ограничено (только свободным местом на накопителе); копии, сделанные перед обновлением, тоже входят в стек |

Кнопки формы: **Создать резервную копию** и **Восстановить…** (предлагает выбрать копию из списка, который строится автоматически по содержимому каталога из настройки расположения).

## 6.10. Тестирование и исправление информационной базы

### 6.10.1. Общая информация

- Причины некорректного состояния ИБ: сбои питания, зависание ОС, отказы оборудования и т. п. в момент записи изменений — особенно в файловом варианте. Проявления разные, вплоть до невозможности запуска.
- Процедура «Тестирование и исправление информационных баз» диагностирует и устраняет ошибочные состояния ИБ и файлового, и клиент-серверного формата; применима и для ПК, и для мобильных устройств.

### 6.10.2. На платформе для персонального компьютера

Запуск: Конфигуратор, **Администрирование — Тестирование и исправление ИБ**.

Доступные проверки и режимы (выбираются независимо друг от друга):

| Проверка / режим | Файловый вариант | Клиент-серверный вариант | Примечания |
|---|---|---|---|
| Проверка логической целостности | да | да | может быть ограничена списком видов объектов конфигурации |
| Проверка ссылочной целостности | да | да | может быть ограничена списком видов объектов конфигурации |
| Пересчёт итогов | да | да | — |
| Реструктуризация базы данных | да | да | — |
| Реиндексация таблиц информационной базы | да | да | перестраивает все индексы таблицы, включая дополнительные индексы объектов |
| Сжатие таблиц информационной базы | да | нет | только файловый вариант |
| Проверка целостности хранения двоичных данных | нет | да | может быть ограничена списком видов объектов конфигурации |
| Проверка логической целостности расширений конфигурации | ⚠ в источнике применимость по вариантам не уточнена | | не требует монопольного режима (см. ниже) |
| Реструктуризация таблиц расширений конфигурации | ⚠ в источнике применимость по вариантам не уточнена | | включается только вместе с проверкой логической целостности расширений и только в режиме «Тестирование и исправление» |
| Проверка и включение функциональности уровня КОРП | ⚠ в источнике применимость по вариантам не уточнена | | см. ниже |

Детали:

- Ограничение списком видов объектов полезно, чтобы сократить время или проверить только подозрительные объекты (например, только регистры сведений). Однако при проверке логической и ссылочной целостности часть проверок всё равно выполняется по всем таблицам всех объектов конфигурации, сколько бы типов метаданных ни выбрали.
- Распределённые ИБ: если в базу могут приходить данные со ссылками на объекты, которых в тестируемой базе нет, снятие флажка **Проверка ссылочной целостности информационной базы** отключает создание «несуществующих» данных — и они не уйдут в другие узлы РИБ.
- Предопределённые элементы: при тестировании и исправлении проверяется, что в основной таблице объекта (справочник, план видов характеристик, план видов расчётов, план счетов) на каждый предопределённый элемент в каждой области данных приходится не более одной записи. У найденных дублей снимается признак предопределённости и ставится пометка удаления.
- Расширения в разделённой ИБ: если расширения входят в состав разделителей (свойство **Разделение расширений конфигурации** = **Использовать** у одного или нескольких разделителей), в таблице **Разделение данных расширений конфигурации** задаётся, в каких областях данных работать с расширениями: одна строка — одна область данных, по колонке на каждый разделитель.
- **Проверка и включение функциональности уровня КОРП**: в режиме «только тестирование» проверяет, в режиме «тестирование и исправление» приводит состояние ИБ в соответствие настройкам. Зависит от параметра ИБ **Использовать дополнительные индексы**:
  - параметр установлен — найденные дополнительные индексы сверяются с описанными в конфигурации; несоответствующие пересоздаются с нужной структурой, соответствующие не трогаются; отсутствующие в базе, но описанные в конфигурации — создаются. Выводится диагностическое сообщение со списком объектов, для которых индексы созданы;
  - параметр сброшен — все найденные дополнительные индексы удаляются из ИБ. Выводится диагностическое сообщение со списком объектов, для которых индексы удалены.

Группы настроек под списком режимов:

1. Что выполнять: только **тестирование** (проверка без каких-либо изменений в ИБ) или **тестирование и исправление** (выполняются директивы второй группы).
2. Что делать при ссылках на несуществующие объекты и при частичной потере данных существующих объектов.
3. Выполнение длительного тестирования в несколько сессий:
   - флажок **Прервать выполнение проверки через** — интервал времени, после которого тестирование прерывается, а его параметры сохраняются до следующей сессии конфигуратора;
   - флажок **Продолжить прерванное ранее тестирование** — продолжение с места остановки в прошлой сессии.

Запуск и ход выполнения:

- Кнопка **Выполнить** запускает процесс; прервать можно сочетанием `Ctrl + Break`.
- События тестирования и исправления пишутся в журнал регистрации; протокол операции выводится в окно сообщений.
- Монопольный режим:
  - если выбраны только **Проверка логической целостности расширений конфигурации** и/или **Реструктуризация расширений конфигурации** — монопольный режим для всей ИБ не требуется и не устанавливается;
  - в остальных случаях делается попытка установить монопольный режим. При неудаче — предупреждение: «Не удалось переключить доступ в монопольный режим. Имеются работающие пользователи». Кто работает — смотреть в **Администрирование — Активные пользователи**;
  - если монопольный режим был установлен перед операцией, по её окончании он снимается.
- Примечание: монопольный режим ИБ не переводит базу MS SQL в однопользовательский режим (single user).
- **Сжатие таблиц информационной базы** (файловый вариант): дополнительно размещает данные, нужные для открытия ИБ, в начале файла `1Cv8.1CD` одним непрерывным блоком. Это ускоряет открытие базы, особенно при большом числе таблиц и размещении базы на сетевом ресурсе. После реструктуризации с изменением структуры таблиц эффект пропадает — сжатие рекомендуется повторить.
- Те же действия в пакетном режиме конфигуратора выполняет команда командной строки `/IBCheckAndRepair` (параметры — в описании пакетного режима конфигуратора, др. раздел документации).
- В поставку входит утилита восстановления файловой базы данных `chdbfl` (описана в др. разделе документации).

### 6.10.3. На мобильной платформе

- Запуск: диалог изменения свойств приложения → **Администрирование** → **Тестирование и исправление**.
- В форме указывают: виды выполняемых действий; только тестирование или тестирование с исправлением (флажок **Исправлять автоматически**); поведение при ссылках на несуществующие объекты; поведение при частичной потере данных объектов.
- Запуск — кнопка **Выполнить** (правый верхний угол формы). Во время работы показывается диалог хода процесса с кнопкой **Отмена**, которая прерывает операцию.

## 6.11. Отмена назначения главного узла распределенной информационной базы

- Команда пакетного запуска конфигуратора: `/ResetMasterNode`.
- Эквивалент во встроенном языке: вызов `УстановитьГлавныйУзел(Неопределено)` у объекта `ПланыОбменаМенеджер`.
- Когда нужно: например, при выделении поддерева РИБ в самостоятельную ИБ или при переподчинении узла РИБ.

---

## 6.12. Удаление данных области данных или информационной базы

- Команда пакетного запуска конфигуратора: `/EraseData`.
- Удаляемая область данных задаётся параметром командной строки запуска `/Z`.
- Условия: пользователь, от имени которого выполняется удаление, имеет право **Администрирование**; к ИБ можно получить монопольный доступ.
- **Внимание:** если в сеансе не используется ни один разделитель либо ИБ неразделённая — удаляются **все данные информационной базы**.

## 6.13. Журнал регистрации

### 6.13.1. Общая информация

- Назначение: история работы пользователей — кто, когда и что делал (изменение данных, регламентные операции, подключение и отключение и т. д.).
- **Журнал регистрации не хранится в базе данных и не попадает в выгрузку/загрузку ИБ** (файл `.dt` его не содержит).
- Работает и в режиме Конфигуратор, и в режиме 1С:Предприятие (в последнем — стандартная функция «Журнал регистрации»).

Форматы журнала:

| Формат | Расширение | Статус |
|---|---|---|
| Последовательный | `.lgf` | используется по умолчанию в актуальных версиях (см. таблицу ниже и 6.13.2) |
| SQLite | `.lgd` | появился в 8.3.5. Начиная с 8.3.22 не используется в новых ИБ и конвертация в него не поддерживается; поддержка будет прекращена в следующих версиях. Описание работы с ним — в документации предыдущих версий |

Формат по умолчанию в зависимости от версии платформы:

| Версии | Формат по умолчанию | Смена формата |
|---|---|---|
| 8.3.4 и более ранние | только последовательный | — |
| 8.3.5 – 8.3.11 | SQLite | не поддерживается |
| 8.3.12 и новее | последовательный | поддерживается |
| 8.3.22 и новее | последовательный (для новых ИБ) | отключена; журнал в формате SQLite можно только просматривать |

- Выбранный при смене формат запоминается в самой ИБ. Поэтому при восстановлении ИБ из резервной копии или из `.dt` восстанавливается и формат журнала. Это важно, когда в 8.3.22 и новее поднимают базу, в которой был установлен формат SQLite и которая выгружена в `.dt` более старой версией.
- Идентификация событий: каждое событие — строка. Системные события используют сочетания символов `_$` и `$_`, например `_$InfoBase$_.MasterNodeUpdate` (в интерфейсе показывается как «Информационная база. Изменение главного узла») или `_$PerformError$_`.
- В именах событий, которые пишет прикладной код методом `ЗаписьЖурналаРегистрации()`, использовать эти сочетания запрещено; такие события показываются «как есть».

### 6.13.2. Журнал регистрации формата .lgf

Файлы журнала (текстовые):

| Файл | Содержимое |
|---|---|
| `1Cv8.lgf` | общая информация журнала регистрации |
| `*.lgp` | фрагмент журнала регистрации |
| `*.lgx` | индексный файл одноимённого фрагмента; занимает примерно 10 % от размера «своего» файла журнала |

Индексирование:

| Вариант работы | Индексирование | Индексные файлы |
|---|---|---|
| Файловый | не выполняется | не создаются и не используются |
| Клиент-серверный | выполняется | создаются и используются. Число потоков индексирования = половина количества рабочих ядер компьютера менеджера кластера, но не менее 1 и не более 8 |

Расположение:

- файловый вариант — подкаталог `1Cv8Log` каталога ИБ;
- клиент-серверный вариант — подкаталог `1Cv8Log` каталога информационной базы внутри каталога служебных файлов кластера. Имя каталога конкретной ИБ определяется по файлу реестра данных кластера.

### 6.13.3. Сохранение журнала регистрации

- Открыть журнал, меню **Файл — Сохранить копию**; выбрать каталог, файл и тип файла. По умолчанию тип — журнал регистрации `*.lgf`; возможна также выгрузка в XML.

Показательный фрагмент XML-выгрузки:

```xml
<v8e:EventLog
    xmlns:v8e = "http://v8.1c.ru/eventLog"
    xmlns:xsd = "http://www.w3.org/2001/XMLSchema"
    xmlns:xsi = "http://www.w3.org/2001/XMLSchema-instance">
  <v8e:Event>
    <v8e:Level>Warning</v8e:Level>
    <v8e:Date>Дата события</v8e:Date>
    <v8e:Application>Enterprise</v8e:Application>
    <v8e:ApplicationPresentation>1С:Предприятие</v8e:ApplicationPresentation>
    <v8e:EventName>имя события</v8e:EventName>
    <v8e:EventPresentation>презентация события</v8e:EventPresentation>
    <v8e:UserID>00000000-0000-0000-0000-000000000001</v8e:UserID>
    <v8e:UserName>Иванов</v8e:UserName>
    <v8e:Computer>Ivanov</v8e:Computer>
    <v8e:MetadataName>Справочники.Номенклатура</v8e:MetadataName>
    <v8e:MetadataPresentation>Справочники Номенклатура</v8e:MetadataPresentation>
    <v8e:Comment>Комментарий</v8e:Comment>
    <v8e:Data xsi:type="xsd:string">Какие-то данные</v8e:Data>
    <v8e:DataPresentation>Описание данных</v8e:DataPresentation>
  </v8e:Event>
</v8e:EventLog>
```

Элементы записи `v8e:Event` в примере: `Level`, `Date`, `Application`, `ApplicationPresentation`, `EventName`, `EventPresentation`, `UserID`, `UserName`, `Computer`, `MetadataName`, `MetadataPresentation`, `Comment`, `Data`, `DataPresentation`. Пространство имён — `http://v8.1c.ru/eventLog`.

### 6.13.4. Просмотр архива журнала регистрации

- В Конфигураторе: **Главное меню — Файл — Открыть**, тип файла **Журнал регистрации (*.lgd, *.lgf)**, выбрать файл архива. Индексация открываемого файла идёт в фоне; индексные файлы создаются в каталоге временных файлов Конфигуратора и удаляются после окончания работы с журналом.
- В стандартной функции просмотра журнала регистрации: **Еще — Просмотреть из файла**, выбрать файл архива.
- Автообновление и его интервал настраиваются штатным механизмом настройки списка табличного поля.
- Архивы журнала, созданные версиями 8.0 и 8.1, не открываются.

### 6.13.5. Настройка журнала регистрации

#### 6.13.5.1. Общая информация

- Конфигуратор, **Администрирование — Настройка журнала регистрации**: задаётся подробность регистрации событий.
- При сетевой работе настройку удаётся сохранить, только когда с конфигурацией, кроме администратора, никто не работает.
- Умолчания для новой ИБ: регистрируются события всех уровней важности; периодичность разделения на файлы — неделя.
- Поле **Разделять хранение журнала регистрации по периодам**: записи хранятся в файлах, каждый файл — за свой период. Новый файл открывается с началом каждого нового: часа / дня / недели / месяца / года.

#### 6.13.5.2. Сокращение журнала регистрации

- В окне настройки журнала — кнопка **Сократить**.
- Поле **Удалить события до**: удаляются записи с датой строго меньше указанной. Все записи пограничного дня (с 00:00 этой даты) и более поздние остаются.
- При сокращении учитывается фактический режим разделения журнала — и текущий, и действовавший во все прошлые периоды.
- Флажок **Записать удаляемые записи в файл** + имя файла-архива — чтобы сохранить удаляемое.
- Флажок **Сохранять разделение хранения журнала по периодам и объединять с сохраненным ранее журналом** (вместе с записью удаляемых записей в файл) — позволяет регулярно сокращать журнал и при этом просматривать уже удалённые события.
- В пакетном режиме конфигуратора сохранение разделения по периодам даёт команда:

```
/ReduceEventLogSize KeepSplitting
```

#### 6.13.5.3. Преобразование журнала регистрации в последовательный формат

- Если журнал текущей ИБ в формате SQLite, его можно конвертировать в последовательный. **Обратная конвертация не поддерживается.**
- Требуемый доступ:
  - файловый вариант — монопольный доступ к файлу ИБ;
  - клиент-серверный вариант — можно выполнять при работающих пользователях. При этом:
    - события, записанные во время смены формата и после неё, не теряются;
    - при ошибке конвертации: если ошибка возникла при записи в последовательный формат — продолжает использоваться SQLite; если ошибка связана с чтением из SQLite — начинает использоваться последовательный формат.
- Смена формата фиксируется в журнале событием «Информационная база. Изменение параметров журнала регистрации» (`_$InfoBase$_.EventLogSettingsUpdate`); в комментарии указывается, в какой формат преобразованы данные.
- Если текущий журнал в формате SQLite, при открытии формы настройки журнала показывается диалог об устаревании формата. Гиперссылка **Перейти на последовательный формат (рекомендуется)** открывает диалог настройки конвертации; там же можно задать разделение журнала по периодам.
- Смена формата занимает существенное время.
- После успешной смены формата файл журнала в формате SQLite удаляется.

## 6.14. Технологический журнал

### 6.14.1. Общая информация

- Технологический журнал (ТЖ) собирает сведения от всех приложений системы «1С:Предприятие». Назначение: поиск ошибок эксплуатации, диагностика службой техподдержки фирмы «1С», анализ технологических характеристик работы системы. Его могут использовать и разработчики прикладных решений.
- Физически это набор текстовых файлов в разных каталогах.
- Состав и свойства событий ТЖ могут меняться от обновления к обновлению платформы.
- ТЖ можно вести на любом компьютере, где установлена система «1С:Предприятие».

Что описывает конфигурационный файл ТЖ:

- каталог размещения файлов журнала;
- состав помещаемой в журнал информации;
- срок хранения файлов журнала;
- структуру хранения файлов, правила ротации, формат и необходимость архивации;
- параметры дампа, создаваемого при аварийном завершении приложения.

Ключевые факты:

| Что | Значение |
|---|---|
| Имя конфигурационного файла | `logcfg.xml` |
| Где лежит | каталог конфигурационных файлов системы «1С:Предприятие» |
| По умолчанию | файл отсутствует |
| Что происходит без файла (формулировка раздела 6.14.1) | ТЖ включён и настроен на сохранение минимальных дампов при аварийном завершении в каталог `%LOCALAPPDATA%\1C\1cv8\dumps` (для Windows). Уточнение из 6.14.2 — см. ниже |
| Период опроса каталогов конфигурационных файлов | каждые 60 секунд: платформа ищет `logcfg.xml` и разбирает его |
| Перезапуск приложений при смене настроек | не нужен — параметры ТЖ меняются «на ходу» |

- ⚠ в источнике неясно: в одном предложении раздела 6.14.1 сказано, что отдельным конфигурационным файлом настраивается «журнал регистрации»; по контексту (имя `logcfg.xml`, раздел про ТЖ) речь идёт о технологическом журнале.
- Только Windows: пользователю процесса, пишущего ТЖ, нужны полные права на каталог ТЖ и право чтения владельца этого каталога.
- **Дампы аварийного завершения через конфигурационный файл ТЖ настраиваются только под ОС Windows. В Linux и macOS формирование дампов настраивается инструментами самой операционной системы.**

### 6.14.2. Конфигурационный файл технологического журнала

Простейший пример:

```xml
<config xmlns="http://v8.1c.ru/v8/tech-log">
  <log location="c:\1c\logs" history="1">
    <event>
      <eq property="name" value="conn"/>
    </event>
  </log>
  <dump location="c:\1c\dumps" create="1" type="2"/>
</config>
```

Что означает этот файл:

- пишутся все события установки и разрыва клиентского соединения с сервером (событие `conn`);
- файлы ТЖ лежат в `C:\1c\logs`;
- файлы ТЖ хранятся один час (`history="1"`);
- дампы складываются в `C:\1c\dumps`;
- дампы содержат всю доступную информацию — содержимое всей памяти процесса (`type="2"`).

Элементы и атрибуты, встречающиеся в этой части документации (полное описание структуры файла — в др. разделе документации):

| Элемент | Атрибуты (из примеров) | Назначение по примерам |
|---|---|---|
| `<config>` | `xmlns="http://v8.1c.ru/v8/tech-log"` | корневой элемент |
| `<log>` | `location` — каталог журнала; `history` — срок хранения в часах (`1` — один час, `168` — неделя) | описание одного журнала; если в файле нет ни одного `<log>`, ТЖ не ведётся |
| `<event>` | — | условие отбора событий; внутри — элементы сравнения |
| `<eq>` | `property`, `value` | свойство равно значению |
| `<ne>` | `property`, `value` | свойство не равно значению (`<ne property="name" value=""/>` — все события) |
| `<gt>` | `property`, `value` | свойство больше значения |
| `<property>` | `name` (`all` — все свойства) | какие свойства событий выводить |
| `<dump>` | `location` — каталог дампов; `create` — создавать ли дамп (в примерах `1` и `false`); `type` — тип дампа (в примерах `2` — вся память процесса, `3` — «полный дамп») | параметры дампа аварийного завершения (действует только в Windows) |
| `<defaultlog>` | (в этой части не раскрыты) | изменение настроек ТЖ по умолчанию, см. 6.14.3 |
| `<system>` | (в этой части не раскрыты) | правила формирования событий для ТЖ по умолчанию, см. 6.14.3 |

Параметры при отсутствии конфигурационного файла (формулировка раздела 6.14.2):

| Параметр | Состояние |
|---|---|
| Технологический журнал | выключен |
| Технологический журнал по умолчанию | включён (см. 6.14.3) |
| Дампы | минимального размера |
| Каталог дампов | `%LOCALAPPDATA%\1C\1cv8\dumps` профиля текущего пользователя |

- ⚠ в источнике неясно: раздел 6.14.1 говорит, что без файла «технологический журнал включён», а 6.14.2 и 6.14.6.1 — что обычный ТЖ выключен (не создаётся), включён только ТЖ по умолчанию. Согласованное прочтение: без `logcfg.xml` работает только ТЖ по умолчанию и пишутся минимальные дампы.

Особенности Linux и macOS (в остальном работа с файлом такая же, как в Windows):

- файл должен лежать в каталоге конфигурационных файлов системы «1С:Предприятие»;
- каталог, где будет формироваться ТЖ, должен быть доступен на запись пользователю, от имени которого работает пишущее в журнал приложение (сервер, клиентские приложения, расширения веб-сервера и т. д.).

### 6.14.3. Технологический журнал по умолчанию

- Предназначен для событий, возникающих в критических (с точки зрения платформы) ситуациях.
- Фильтр событий фиксированный, формируется платформой, изменить его нельзя.

Настройки ТЖ по умолчанию:

| Параметр | Значение |
|---|---|
| Каталог, Windows | `%LOCALAPPDATA%\1C\1cv8\logs` |
| Каталог, Linux | `~/.1cv8/1C/1cv8/logs` |
| Каталог, macOS | `~/.1cv8/1C/1cv8/logs` |
| Срок хранения | информация удаляется через 24 часа |
| Состав событий | события `SYSTEM` с уровнем `ERROR` |

- Эти настройки меняются элементом `<defaultlog>` файла `logcfg.xml`.
- Правила формирования событий, попадающих в ТЖ по умолчанию, настраиваются элементом `<system>`.

### 6.14.4. Структура технологического журнала

ТЖ — это каталог, в подкаталогах которого лежат файлы с собранными технологическими данными. Описание файлов журнала и описание конфигурационного файла вынесены в другие разделы документации.

### 6.14.5. Настройка формирования дампов памяти

Настройка дампов аварийного завершения компонентов «1С:Предприятия» описана в другом разделе документации (в этой части только ссылка).

### 6.14.6. Примеры файлов настройки технологического журнала

- Примеры в документации написаны для Windows: предполагается стандартная установка в `C:\Program Files\1cv8`, каталоги журналов и дампов — вида `C:\v8\logs`, `C:\v8\dumps`. На Linux в `location` указывается каталог, доступный на запись пользователю процесса (см. 6.14.2), а дампы через конфигурационный файл ТЖ не настраиваются (см. 6.14.1).
- При некоторых настройках объём ТЖ очень велик — на диске с каталогом журнала должно быть достаточно свободного места.

Сводка примеров:

| Раздел | Что пишется | События в фильтре | Срок хранения |
|---|---|---|---|
| 6.14.6.1 | ничего (только настройка дампов) | нет элементов `<log>` | — |
| 6.14.6.2 | все события со всеми свойствами | `name` ≠ пустой строке | 168 ч |
| 6.14.6.3 | обращения к СУБД и ошибки | `dbmssql`, `dbpostgrs`, `db2`, `dboracle`, `excp` | 168 ч |
| 6.14.6.4 | действия администратора и ошибки | `admin`, `conn`, `excp`, `proc`, `qerr`, `scom` | 168 ч |
| 6.14.6.5 | то же + отбор по длительности более 10 секунд | `admin`, `conn`, `excp`, `proc`, `qerr`, `scom`, у каждого `duration` > `100000` | 168 ч |

#### 6.14.6.1. Технологический журнал выключен

- Если `logcfg.xml` в каталоге конфигурационных файлов отсутствует, ТЖ не создаётся.
- Если файл нужен только ради настройки дампов, в нём не должно быть ни одного элемента `<log>`.
- Пример: строить полный дамп приложения при аварийном завершении, дампы класть в `C:\v8\dumps`:

```xml
<config xmlns="http://v8.1c.ru/v8/tech-log">
  <dump location="C:\v8\dumps" create="1" type="3"/>
</config>
```

#### 6.14.6.2. Полный технологический журнал

- Выводятся все события со всеми свойствами; хранение — неделя (168 часов).
- Объём очень большой. Рекомендуется для этапа тестирования и для расследования ошибок, в том числе сложных нештатных ситуаций.

```xml
<config xmlns="http://v8.1c.ru/v8/tech-log">
  <log location="C:\v8\logs" history="168">
    <event>
      <ne property="name" value=""/>
    </event>
    <property name="all">
    </property>
  </log>
</config>
```

#### 6.14.6.3. Обращения к СУБД

- В журнал попадают только обращения «1С:Предприятия» к СУБД и сведения об ошибочных ситуациях.

#### 6.14.6.5. Ошибки и долгие операции

- По описанию документации — к предыдущему варианту добавляются все операции длительностью более 10 секунд (поиск долгих действий пользователей для последующей оптимизации).
- **Длительность событий выражается в сотнях микросекунд**: 10 секунд = `100000`.
- В примере из документации условие по `duration` стоит внутри каждого элемента `<event>` рядом с условием по имени события; дампы отключены (`<dump create="false"/>`).

```xml
<?xml version="1.0" encoding="UTF-8"?>
<config xmlns="http://v8.1c.ru/v8/tech-log">
  <dump create="false"/>
  <log location="C:\v8\logs" history="168">
    <event>
      <eq property="name" value="admin"/>
      <gt property="duration" value="100000"/>
    </event>
    <event>
      <eq property="name" value="conn"/>
      <gt property="duration" value="100000"/>
    </event>
    <!-- такие же блоки <event> с <gt property="duration" value="100000"/>
         для событий excp, proc, qerr, scom -->
    <property name="all"/>
  </log>
</config>
```

## 6.15. Контроль ссылочной целостности

### 6.15.1. Основные понятия

- Значительная часть данных хранится в виде ссылок (реквизит документа, выбранный из списка, — ссылка на элемент списка). Это избавляет от многократной правки одного и того же: исправили наименование контрагента в списке — оно изменилось во всех документах.
- Обратная сторона: если объект удалить, в использовавших его объектах остаются «неразрешённые ссылки» — ссылки на несуществующий объект.
- Механизм контроля ссылочной целостности делит удаление объектов, на которые могут быть ссылки (списки и документы), на два этапа:
  1. Пользователи помечают объекты на удаление. Помеченный объект в работе почти не отличается от обычного.
  2. Администратор или иной пользователь с правом `ИнтерактивноеУдалениеПомеченных` (на соответствующие виды списков и документов) запускает стандартную функцию **Удаление помеченных объектов**. Она анализирует все ссылки на помеченные объекты; удаляются только те объекты, на которые ссылок нет либо ссылки находятся в объектах, тоже помеченных на удаление.
- Удаление помеченных объектов — по сути регламентная процедура; её рекомендуют выполнять периодически, по мере накопления помеченных объектов.

### 6.15.2. Включение режима контроля ссылочной целостности

Два режима удаления информации:

| Режим | Суть |
|---|---|
| Непосредственное удаление объектов | использование удаляемого объекта в других объектах базы не анализируется |
| Контроль ссылочной целостности | объект сначала помечается на удаление, затем проверяется наличие ссылок на него в других объектах |

- Права удаления задаются для каждой роли по каждому виду объектов (списков и документов) на этапе проектирования прикладного решения.
- Право `ИнтерактивноеУдаление` у роли на вид объектов = возможность непосредственного удаления объектов этого вида пользователями с этой ролью.
- Аналогично, отдельными правами, даётся возможность ставить и снимать пометку удаления и удалять помеченные объекты.
- Самый радикальный способ включить контроль — убрать во всей конфигурации права непосредственного удаления: пользователи смогут только помечать объекты. Только отключение права `ИнтерактивноеУдаление` в конфигурации гарантирует, что механизм используют согласованно все пользователи.
- Режим непосредственного удаления повышает ответственность и пользователя, и администратора, который определяет права и действия системы при неразрешённых ссылках; он может применяться, например, при отладке прикладного решения. Без контроля возможно появление неразрешённых ссылок.
- Объекты можно удалять непосредственно и средствами встроенного языка — то есть прикладной код конкретной конфигурации может обходить контроль ссылочной целостности; ответственность за целостность данных в этом случае на разработчике такого механизма.

### 6.15.3. Непосредственное удаление объектов

Если у пользователя на данный вид объектов есть право `ИнтерактивноеУдаление`, в списках и журналах документов доступен пункт меню **Удалить непосредственно** (сочетание `Shift + Del` или кнопка панели инструментов). Объект удаляется без проверки ссылок на него.

### 6.15.4. Установка и снятие пометки удаления

- В списках и журналах документов в меню **Еще** (**Все действия**) есть пункт **Пометить на удаление/Снять пометку**: для обычного объекта ставит пометку, для помеченного — снимает. Помеченный объект отмечается в левой колонке списка значком с перечёркнутым изображением объекта.
- Проведённый документ при пометке на удаление становится непроведённым.
- При снятии пометки документ проведённым не становится — его нужно провести заново.
- Возможность ставить пометку и возможность снимать пометку регулируются правами доступа раздельно.

### 6.15.5. Особенности использования объектов, помеченных на удаление

- Помеченные объекты в основном ведут себя как обычные: видны в списках, участвуют в поиске, их можно открыть и изменить.
- Помеченный на удаление документ провести нельзя: выдаётся сообщение, проведение не выполняется.

## Что важно администратору Linux

1. **Выгрузка в `.dt` — не резервная копия.** Документация прямо не рекомендует её для бэкапа: файл может не загрузиться при ошибках в исходной базе, выгрузка долгая, требует монопольного доступа и много памяти. `.dt` — инструмент переноса между СУБД/вариантами и получения образа базы.
2. **Бэкап клиент-серверной базы = три части:** база данных средствами СУБД, журнал регистрации (если нужен после восстановления), хранилище двоичных данных (встроенным языком или стандартной функцией «Управление хранилищем двоичных данных»). Восстановление — в том же порядке; при восстановлении средствами СУБД к базе не должно быть никаких подключений, включая фоновые и регламентные задания и средства администрирования.
3. **Журнал регистрации лежит не в базе данных**, а в подкаталоге `1Cv8Log` каталога ИБ внутри каталога служебных файлов кластера (имя каталога ИБ — по файлу реестра данных кластера). В `.dt` и в бэкап СУБД он не попадает — копировать отдельно. **Восстанавливать его нужно при остановленном кластере серверов.**
4. **Загрузка `.dt` в клиент-серверную базу требует места на сервере «1С:Предприятия»** под временные файлы — примерно в объёме развёрнутой базы; итоговая база может быть в несколько раз больше `.dt`. Текущая база заменяется целиком.
5. **PostgreSQL относится к версионным СУБД:** параметры ИБ, установленные в транзакции (часовой пояс, год начала столетия), становятся видны другим сеансам не позднее чем через 20 секунд после фиксации этой транзакции.
6. **Формат журнала регистрации:** начиная с 8.3.22 новые базы используют только последовательный формат (`.lgf`/`.lgp`/`.lgx`), смена формата отключена, SQLite (`.lgd`) можно лишь просматривать и конвертировать в последовательный (в одну сторону). Формат хранится в самой ИБ, поэтому старая база из `.dt` может «приехать» с форматом SQLite — тогда его стоит конвертировать; в клиент-серверном варианте это делается без остановки пользователей, но занимает существенное время.
7. **Объём и нагрузка от журнала регистрации:** индексные файлы `*.lgx` добавляют около 10 % к размеру фрагментов; индексирование в клиент-серверном варианте идёт на компьютере менеджера кластера в число потоков, равное половине рабочих ядер (от 1 до 8). Для новой базы пишутся события всех уровней с разделением по неделям.
8. **Сокращение журнала регистрации** удаляет записи с датой строго меньше указанной; в пакетном режиме конфигуратора есть команда `/ReduceEventLogSize`, параметр `KeepSplitting` сохраняет разделение по периодам.
9. **Технологический журнал настраивается файлом `logcfg.xml`** в каталоге конфигурационных файлов «1С:Предприятия». Платформа перечитывает его каждые 60 секунд — перезапуск сервера не нужен. Каталог журнала (`location`) должен быть доступен на запись пользователю, от имени которого работает процесс (сервер, клиент, расширение веб-сервера).
10. **Дампы в Linux через `logcfg.xml` не настраиваются** — элемент `<dump>` относится только к Windows; в Linux дампы аварийного завершения настраиваются средствами ОС.
11. **ТЖ по умолчанию в Linux пишется в `~/.1cv8/1C/1cv8/logs`** (домашний каталог пользователя процесса), хранится 24 часа, содержит события `SYSTEM` уровня `ERROR`; параметры меняются элементами `<defaultlog>` и `<system>`. Без `logcfg.xml` работает только он.
12. **Для диагностики PostgreSQL в ТЖ используется событие `dbpostgrs`** (плюс `excp` для ошибок). `history` задаётся в часах (168 = неделя); порог длительности в фильтре `duration` — в сотнях микросекунд (`100000` = 10 секунд). Полный ТЖ и журнал обращений к СУБД могут быть очень большими — следить за свободным местом на диске.
13. **Тестирование и исправление ИБ** почти всегда требует монопольного режима (исключение — только проверки расширений конфигурации); в пакетном режиме — `/IBCheckAndRepair`. Сжатие таблиц доступно только для файловых баз; для клиент-серверных есть проверка целостности хранения двоичных данных. Длительное тестирование можно разбивать на сессии.
14. **Опасные пакетные команды конфигуратора:** `/EraseData` без разделителей (или в неразделённой базе) удаляет все данные ИБ; `/ResetMasterNode` снимает назначение главного узла РИБ.
15. **Консоль кластера работает только под Windows**; её аналог, доступный из режима 1С:Предприятие, — стандартная функция «Управление серверами» (нужен развёрнутый сервер администрирования кластера и включённый «Режим технического специалиста»).
