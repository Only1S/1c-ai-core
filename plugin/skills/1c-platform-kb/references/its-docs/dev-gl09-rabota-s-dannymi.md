# ИТС-конспект: Руководство разработчика — Глава 9. Работа с данными

> Источник: документация «1С:Предприятие 8.3.27», «Руководство разработчика», глава 9 (`https://its.1c.ru/db/v8327doc/content/54/hdoc`, нужен вход по подписке). Прочитана полностью 11.10.2026.
> Пересказ своими словами; имена методов, свойств и значений приведены точно.

## 9.1. Механизм транзакций

### 9.1.1. Общая информация

- Транзакция — неделимая последовательность операций с данными: выполняется целиком либо не выполняется вовсе.
- Платформа сама открывает **неявную транзакцию** при любом изменении данных: все обработчики событий модулей объектов и наборов записей, связанные с записью, выполняются в транзакции.
- Чтение (обращение к свойствам «через точку», `ПолучитьОбъект()`, открытие формы объекта) обычно идёт **вне транзакции** — ради параллельности. Состояние прочитанного объекта при этом соответствует базе на момент начала чтения; для целостного чтения платформа может открыть неявную транзакцию (см. 9.2.3.2).
- Явное управление: `НачатьТранзакцию()`, `ЗафиксироватьТранзакцию()`, `ОтменитьТранзакцию()`.

### 9.1.2. Явные транзакции

- Если вызовов `НачатьТранзакцию()` больше, чем завершений, платформа сама отменит транзакцию: при окончании выполнения встроенного языка (обработчик события, внешнее соединение, automation-сервер) и при передаче управления с сервера на клиент.
- Лишний вызов `ЗафиксироватьТранзакцию()` или `ОтменитьТранзакцию()` вызывает исключение.
- Ошибки базы данных делятся на два вида:
  - **невосстановимые** — работа платформы прекращается, изменения транзакции отменяются;
  - **восстановимые** — операция прерывается, возникает исключение, которое можно перехватить конструкцией `Попытка … Исключение … КонецПопытки`. Транзакция при этом автоматически **не отменяется**.
- Если исключение вызвано ошибкой **базы данных**, транзакция помечается как ошибочная: продолжить или зафиксировать её нельзя, можно только отменить и повторить заново. Если ошибка с базой не связана — транзакцию можно продолжать.
- Типовая схема: в `Попытка` — `НачатьТранзакцию()`, операции, `ЗафиксироватьТранзакцию()`; в `Исключение` — `ОтменитьТранзакцию()`.

### 9.1.3. Вложенные вызовы

Вложенных транзакций платформа **не поддерживает**. Повторный `НачатьТранзакцию()` внутри открытой транзакции новой транзакции не создаёт: действует только транзакция верхнего уровня. Отмена во «вложенном» вызове в итоге отменяет всю внешнюю транзакцию, а фиксация во «вложенном» вызове игнорируется.

### 9.1.4. Транзакции и программные объекты

Откат транзакции не меняет состояние объектов встроенного языка в памяти — их нужно перечитать самому. Исключения: при отмене восстанавливается признак проведения документа; у объекта, созданного и записанного в транзакции, очищается ссылка; у объекта, созданного вне транзакции и получившего в ней автоматический код или номер, этот код очищается.

## 9.2. Блокировки

### 9.2.1. Виды блокировок

- **Объектные** — защищают объект при интерактивной работе в формах (редактирование, удаление).
- **Транзакционные** — обеспечивают конкурентный доступ к данным внутри транзакций.

### 9.2.2. Объектные блокировки

**Пессимистическая** — запрещает другим сеансам начать редактирование объекта, пока блокировка не снята.

- Ставится расширением формы в момент, когда пользователь начинает менять объект, снимается при закрытии формы.
- Если объект уже редактируется, платформа сообщает об этом. В клиент-серверном варианте можно начать редактирование с потерей чужих изменений; при доступной системе взаимодействия можно написать блокирующему пользователю.
- Из встроенного языка: `ЗаблокироватьДанныеДляРедактирования()` и `РазблокироватьДанныеДляРедактирования()`; для нестандартной формы — методы формы `ЗаблокироватьДанныеФормыДляРедактирования()` и `РазблокироватьДанныеФормыДляРедактирования()`.
- Блокировка **с идентификатором формы** живёт, пока жива форма; снимается также при завершении сеанса, через 1 минуту после сброса признака модифицированности, при закрытии формы с незавершёнными фоновыми заданиями.
- Блокировка **без идентификатора формы** снимается при завершении сеанса, при возврате управления с сервера или при завершении транзакции.
- Блокировки с идентификатором формы и без него на один объект несовместимы.
- Сама по себе блокировка **не мешает записать или удалить объект**: защита работает, только если каждый изменяющий код сначала пытается заблокировать объект. Попытка заблокировать занятый объект даёт исключение, которое можно обработать без отката транзакции.

**Оптимистическая** — проверка перед записью: при чтении объекта запоминается его версия; если к моменту записи версия в базе другая (объект изменён или удалён), запись отклоняется. Это гарантирует, что чужие изменения не будут затёрты.

### 9.2.3. Управляемые блокировки

#### 9.2.3.1. Правила работы с данными

- Вне транзакции допускается только чтение, и оно «безответственное»: может вернуть устаревшие данные.
- В транзакции чтение должно быть воспроизводимым, актуальным и не содержать незафиксированных изменений.

#### 9.2.3.2. Два режима и что они означают для СУБД

- **Автоматический** режим: правила обеспечивает платформа за счёт высокого уровня изоляции в СУБД. Разработчику проще, но при интенсивной одновременной работе возникает много конфликтов блокировок.
- **Управляемый** режим: в СУБД используется низкий уровень изоляции, параллельность выше, но воспроизводимость чтения разработчик обеспечивает сам — управляемыми блокировками.

| СУБД | Автоматический режим | Управляемый режим |
|---|---|---|
| Файловая база | блокировки таблиц, Serializable | блокировки таблиц, Serializable |
| MS SQL Server | блокировки записей, Repeatable Read или Serializable | записей; Read Committed (2000), Read Committed Snapshot (2005 и новее) |
| IBM Db2 | записей, Repeatable Read или Serializable | записей, Read Committed |
| **PostgreSQL** | **таблиц, Serializable** | **записей, Read Committed** |
| Oracle Database | таблиц, Serializable | записей, Read Committed |

Документация рекомендует разрабатывать в управляемом режиме; автоматический оставлен для совместимости и для реальной эксплуатации не рекомендуется.

Чтение вне транзакции (динамические списки, отчёты):

| СУБД | Автоматический | Управляемый |
|---|---|---|
| Файловая база | «грязное» | «грязное» |
| MS SQL Server | «грязное» | согласованное (2005 и новее), «грязное» (2000) |
| IBM Db2 | «грязное» | согласованное с версии 9.7 |
| **PostgreSQL** | согласованное | согласованное |
| Oracle Database | согласованное | согласованное |

- Объекты с табличными частями и наборы записей читаются согласованно всегда. Для этого платформа может открыть неявную транзакцию; на PostgreSQL и Oracle она **не открывается** ни в одном режиме.
- Без неявной транзакции в управляемом режиме версия объекта (`ВерсияДанных`) читается дважды — в начале и в конце; при расхождении выдаётся ошибка транзакционной блокировки.
- Наборы записей регистров сведений всегда читаются в неявной транзакции; в управляемом режиме ставится разделяемая блокировка по регистратору (для независимого регистра — по значениям основного отбора).

#### 9.2.3.3. Где задаётся режим

- Свойство конфигурации «Режим управления блокировкой данных»: `Автоматический`, `Управляемый` (по умолчанию для новой конфигурации), `Автоматический и управляемый`. В последнем случае режим берётся из одноимённого свойства каждого объекта.
- Режим объекта действует для транзакций, которые открывает сама платформа. Для явной транзакции режим задаёт параметр `РежимБлокировок` метода `НачатьТранзакцию()`; его значение по умолчанию — `РежимУправленияБлокировкойДанных.Автоматический`, поэтому управляемый режим нужно указывать явно.

#### 9.2.3.4. Объект `БлокировкаДанных`

- Коллекция элементов (`ЭлементБлокировкиДанных`), каждый описывает одно **пространство блокировок**. Метод `Заблокировать()` ставит все блокировки; они снимаются при завершении транзакции. Вызов вне транзакции или в автоматическом режиме даёт исключение.
- Пространства: `Справочник.<имя>`, `Документ.<имя>`, `ПланОбмена.<имя>`, `ПланСчетов.<имя>`, `БизнесПроцесс.<имя>`, `Задача.<имя>`, `ПланВидовРасчета.<имя>`, `ПланВидовХарактеристик.<имя>` (поля: `Ссылка` и поля из свойства «Поля блокировки данных»); `РегистрСведений.<имя>` (период и измерения), `РегистрСведений.<имя>.НаборЗаписей` (регистратор); аналогично для регистров накопления, бухгалтерии, расчёта; `Последовательность.<имя>`, `Константа.<имя>`, `ВнешнийИсточникДанных.<источник>.Таблица.<таблица>`.
- Нельзя блокировать по реквизитам типа «строка неограниченной длины», «хранилище значения», по значениям плана видов характеристик и составным типам с ними, а также по полям `Предопределенный` и `ИмяПредопределенныхДанных`.
- Условия задаются методом `УстановитьЗначение()` (равенство или объект `Диапазон`) либо через источник данных: свойство `ИсточникДанных` (результат запроса, табличная часть, набор записей, таблица значений) и метод `ИспользоватьИзИсточникаДанных()`.
- Режимы элемента (`РежимБлокировкиДанных`): `Разделяемый` — данные не могут быть изменены другой транзакцией; `Исключительный` — не могут быть ни изменены, ни прочитаны транзакцией, ставящей разделяемую блокировку. Совместимы только две разделяемые блокировки.
- При записи данных платформа сама ставит неявные исключительные управляемые блокировки. При **чтении** объекта блокировка не ставится — её нужно ставить явно до обращения к данным.
- При изменении объекта блокировка ставится и по старым, и по новым значениям полей блокировки.

#### 9.2.3.5. Режим «Автоматический и управляемый»

- Нужен, чтобы перевести на управляемые блокировки отдельные «узкие» объекты, не переделывая всю конфигурацию.
- Управляемые блокировки при записи ставятся в любом случае, поэтому транзакции разных режимов могут конфликтовать друг с другом.
- Фактический режим определяет транзакция верхнего уровня: в автоматической транзакции вложенная управляемая выполнится как автоматическая; попытка начать автоматическую внутри управляемой даёт исключение. Поэтому управляемый режим должен быть задан и документу, и регистрам, в которые он пишет.

#### 9.2.3.6. Эскалация и поглощение

- Если на одно пространство наложено более **100 000** блокировок, возможна эскалация: блокируется всё пространство (при независимых разделителях — только в пределах текущих значений разделителей). Если эскалация конфликтует с уже стоящими блокировками, она не выполняется.
- Блокировка, заданная по меньшему числу измерений, поглощает более детальные с теми же значениями. Вместо множества блокировок, различающихся одним измерением, документация советует ставить одну без этого измерения.

#### 9.2.3.7. Перевод конфигурации на управляемые блокировки

- Блокировки нужны там, где данные читаются, чтобы потом быть изменёнными; где читается согласованный набор данных; где важно, чтобы прочитанное не изменилось до конца транзакции. Типичный пример — запрос остатков при проведении документа.
- Исключительный режим — для данных, которые будут изменены в этой же транзакции (это предотвращает взаимоблокировки); разделяемый — для данных, которые только читаются.
- Два способа: объект `БлокировкаДанных` либо свойство `БлокироватьДляИзменения` у наборов записей регистров накопления и бухгалтерии — тогда платформа ставит блокировку сама при записи набора.

## 9.3. Монопольный режим

- В монопольном режиме с базой работает только один сеанс. Его требуют конфигуратор и некоторые методы (например, `УдалитьОбъекты()`).
- Методы: `УстановитьМонопольныйРежим()`, `МонопольныйРежим()`, `ПолучитьПараметрыМонопольногоРежима()`. В активной транзакции состояние режима изменить нельзя.
- Установить режим можно, только если нет других сеансов. Новые сеансы запрещены, кроме **одного фонового задания**, запущенного из монопольного сеанса: оно «забирает» монопольный режим, и родительский сеанс до его завершения менять данные не может.
- В монопольном режиме управляемые блокировки не устанавливаются.
- Чтобы пользователь понял, почему не может войти, в параметре `Параметры` передают объект `ПараметрыМонопольногоРежима` со свойством `Сообщение` (строка или форматированная строка).
- Свойство `РазрешитьЗавершатьПриНачалеСеанса` вместе с правом доступа `ЗавершениеМонопольногоРежимаПриНачалеСеанса` добавляет в диалог кнопку, которой пользователь может завершить монопольный сеанс и войти. Кнопка появляется только в клиент-серверном варианте или при доступе к файловой базе через веб-сервер.
- Причину отказа в начале сеанса можно сообщить также через сервис внешнего управления сеансами (метод `onStartSession`) и блокировку начала сеансов.

## 9.4. Дополнительные индексы объектов метаданных

> Лицензия: доступно только для лицензии КОРП.

- Платформа сама создаёт для каждого объекта набор индексов (описаны в методической статье ИТС, см. `../its-metod/razmeshchenie-dannyh-i-indeksy.md`). Разработчик влияет на них только признаком индексирования реквизитов.
- Дополнительные индексы — некластерные, неуникальные, обычные или составные. Доступны для справочников, документов, всех видов регистров, бизнес-процессов, задач, журналов документов, последовательностей, планов видов характеристик, счетов и обмена.
- У индекса есть имя, **индексируемые** (ключевые) поля и **дополнительные** (неключевые) поля; если СУБД неключевые поля не поддерживает, они игнорируются.
- Ограничения: не более 16 физических полей в индексе (поле составного типа занимает три физических поля); в ключ нельзя включать `ХранилищеЗначения` и строки неограниченной длины; в один индекс входят поля только одной таблицы — основной, табличной части или виртуальной (для регистров). Для виртуальной таблицы платформа создаёт индексы во всех физических таблицах, из которых она строится.
- Индексы, приводящие к одному и тому же индексу в СУБД, физически создаются один раз.
- Фактическое создание управляется параметром информационной базы «Использовать дополнительные индексы» либо методами `УстановитьИспользованиеДополнительныхИндексов()` и `ПолучитьИспользованиеДополнительныхИндексов()`.
- Физически индексы создаются и удаляются только:
  - при обновлении конфигурации базы данных — если реструктуризируется объект с такими индексами;
  - при тестировании и исправлении с режимом «Проверка и включение функциональности уровня КОРП»;
  - командой пакетного запуска `/IBCheckAndRepair` с параметром `-CheckAndEnableCORPFunctionality`.
- Настраиваются только в конфигураторе; из встроенного языка состав можно лишь прочитать (свойство `ДополнительныеИндексы`, объекты `ДополнительныйИндекс` и `ПолеИндекса`).
- Обратная сторона: лишние индексы замедляют запись и занимают место — иногда больше, чем сами данные.

## 9.5. Динамические выборки

- Методы `Выбрать()`, `ВыбратьИерархически()`, `ВыбратьПоСсылкам()` читают данные не целиком, а **блоками по 25 записей** по мере вызовов `Следующий()`; блок содержит объекты полностью, с табличными частями.
- Отбор и упорядочивание ограничены так, чтобы обход шёл по одному из индексов.
- Актуальность не гарантируется даже в транзакции: если данные меняются во время обхода, запись может попасть в выборку дважды, не попасть вовсе или оказаться уже удалённой.
- `Выборка.ПолучитьОбъект()` заполняет объект уже прочитанными данными выборки (быстро), а `Выборка.Ссылка.ПолучитьОбъект()` перечитывает объект из базы.
- При удалении иерархических данных обычной выборкой вместе с элементом удаляются подчинённые, уже прочитанные в блоке; иерархическая выборка от этого защищена.
- Применять для задач, не требующих ответственного чтения, и для регламентных операций в монопольном режиме.
