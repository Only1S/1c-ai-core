## 2.1–2.13. Работа в конфигураторе (по оглавлению)

## 2.14. Работа с конфигурацией базы данных

### 2.14.1–2.14.2. Обновление конфигурации базы данных

- В информационной базе две конфигурации: редактируемая (основная) и **конфигурация базы данных**. Расхождение показывается знаком `<!>` в заголовке окна после сохранения основной конфигурации.
- Два способа обновить:
  - «Конфигурация — Обновить конфигурацию базы данных» — перед реструктуризацией показывается диалог со списком изменений, можно отказаться;
  - «Конфигурация — Конфигурация базы данных — Обновить конфигурацию базы данных на сервере» — без диалога, реструктуризация выполняется безусловно.
- Обновление требует **монопольного доступа** конфигуратора. Что предложит конфигуратор:
  - ошибка исключительной блокировки — если есть сеансы, подключённые не через веб-сервер, и нужна реструктуризация;
  - «Завершить сеансы и повторить» — если нужна реструктуризация, а с файловой базой работают клиенты через веб-сервер. Завершение сеансов — аварийное для пользователей;
  - в остальных случаях — **динамическое обновление**.
- При пяти и менее мешающих сеансах выводится их подробный список, иначе только число.
- Для Microsoft SQL Server: монопольный режим базы 1С не переводит базу SQL Server в однопользовательский режим; для ускорения реструктуризации рекомендуется модель восстановления «Простая» или «С неполным протоколированием» (перед сменой — резервная копия).

**Динамическое обновление:** изменения записываются как версия изменений, конфигурация базы данных не меняется, пользователи продолжают работать со старой конфигурацией до перезапуска клиента. Проверка из кода — `КонфигурацияБазыДанныхИзмененаДинамически()`. После полноценного обновления все динамические версии удаляются.

### 2.14.2.4. Механизм реструктуризации

- **Обычный** — для каждой изменяемой таблицы создаётся копия, строки преобразуются по одной (в конфигураторе или на сервере). Единственный вариант в версиях 8.3.10 и младше.
- **Оптимизированный** — только клиент-серверный вариант на **Microsoft SQL Server или PostgreSQL**: максимум действий выполняет СУБД, существующие данные и индексы изменяются на месте, без копирования.
- Выбор при запуске из конфигуратора — параметр `UpdateDBCfg` файла `conf.cfg` **на компьютере, где запущен конфигуратор**. В пакетном режиме (`/UpdateDBCfg`) механизм указывается в командной строке; если не указан — берётся из `conf.cfg`.

### 2.14.3. Фоновое обновление конфигурации базы данных

> Лицензия: доступно только для лицензии КОРП.

- Только клиент-серверный вариант; может идти при закрытом конфигураторе; большая часть работы, включая реструктуризацию, выполняется **без монопольного доступа**.
- Во время фонового обновления нельзя: редактировать конфигурацию, отлаживать, запускать обычное обновление, менять планы счетов и планы видов расчёта, связанные с обновляемыми регистрами.
- Не работает: в режиме совместимости с 8.1; если подключены расширения, расширяющие данные; на IBM Db2 9.1.
- Три фазы:
  1. **Обработка** — долгая; пользователи работают; реструктурируется основной объём данных справочников, документов, журналов, регистров, последовательностей, планов счетов, бизнес-процессов и задач; изменения, сделанные пользователями за это время, регистрируются.
  2. **Актуализация** — запускается автоматически, итерациями с интервалом 1 минута; пользователи работают; догоняются накопленные изменения.
  3. **Принятие изменений** — нужен монопольный доступ; пользователи не работают; последняя актуализация, быстрая реструктуризация остального, фиксация.
- «Паузу» можно держать не более **48 часов**, затем обновление отменяется.
- После остановки сервера или аварии рабочего процесса фоновое обновление остаётся приостановленным — его нужно возобновить вручную (защита от зацикливания, если причиной аварии было само обновление). Обработка продолжается с незавершённого объекта, итерация актуализации — заново.
- Если завершать не планируется — обновление следует отменить: пока оно висит, платформа продолжает регистрировать изменения.
- Диалог: кнопки «Запустить», «Приостановить», «Продолжить», «Завершить», «Отменить»; флажки «Разрешить динамическое обновление» и «Выполнять на сервере». С флажком «Выполнять на сервере» достаточно права `ОбновлениеКонфигурацииБазыДанных` без права «Администрирование».

### 2.14.4–2.14.6. Прочее

- «Сохранить конфигурацию БД в файл» — нужен для сравнения и объединения.
- «Сравнить, объединить с конфигурацией БД».
- «Вернуться к конфигурации БД» — отказ от несохранённых в базу изменений; недоступно, когда база подключена к хранилищу конфигурации.

## 2.15. Запуск «1С:Предприятия» из конфигуратора

«Сервис — 1С:Предприятие» или «Отладка — Начать отладку». Если конфигурация изменена, конфигуратор предложит обновить конфигурацию базы данных. При запуске из списка баз с необновлённой конфигурацией платформа спросит, продолжать ли со старой.

## 2.16. Выгрузка и загрузка файлов конфигурации

Выгрузка отдельных свойств объектов в файлы: `.htm` (справка, HTML-макеты), `.txt` (модули, текстовые макеты), `.mxl` (табличные макеты), `.geo`, `.grs`, `.bin`; права ролей — в XML (права, ограничения доступа, шаблоны ограничений). Справка — отдельный файл на каждый язык (`….Справка.ru.htm`).

## 2.17. Выгрузка и загрузка конфигурации в файлы (XML)

### Общее

- Команды: «Конфигурация — Выгрузить конфигурацию в файлы» и «Загрузить конфигурацию из файлов». Главный файл — `Configuration.xml`.
- Так же выгружаются расширения.
- Для ролей выгружаются только права, отличающиеся от значений по умолчанию.
- Обычные формы и интерфейсы обычного приложения выгружаются в двоичном виде.

Выгрузка всегда идёт в формате текущей платформы. Загрузка удаётся, только если версия файлов **не новее** версии платформы.

### 2.17.3. Форматы

**Иерархический** (рекомендуемый):

- Корневой каталог: путь желательно не длиннее 30 символов. Полный путь к файлу ограничен 255 символами, поэтому не рекомендуется более трёх уровней вложенных подсистем.
- Каталоги по видам объектов (перечень из таблицы документации): `AccumulationRegisters`, `BusinessProcesses`, `Catalogs`, `ChartsOfAccounts`, `ChartsOfCalculationTypes`, `ChartsOfCharacteristicTypes`, `CommandGroups`, `CommonCommands`, `CommonForms`, `CommonModules`, `CommonPictures`, `CommonTemplates`, `Constants`, `DataProcessors`, `DefinedTypes`, `DocumentJournals`, `Documents`, `Enums`, `ExchangePlans`, `Ext`, `ExternalDataSources`, `FilterCriteria`, `FunctionalOptions`, `FunctionalOptionsParameters`, `HTTPServices`, `InformationRegisters`, `Languages`, `Reports`, `Roles`, `ScheduledJobs`, `Sequences`, `SessionParameters`, `SettingsStorages`, `StyleItems`, `Styles`, `Subsystems`, `Tasks`, `WebServices`, `WSReferences`, `XDTOPackages`. Регистры бухгалтерии и расчёта в таблице документации не названы.
- Объект — файл `<Имя>.xml` и каталог `<Имя>` с подкаталогами `Forms`, `Commands`, `Templates`, `Ext`. Реквизиты и табличные части описаны в самом XML объекта.
- В `Ext`: `ObjectModule.bsl`, `ManagerModule.bsl`, `RecordSetModule.bsl`, `ValueManagerModule.bsl`, `CommandModule.bsl`, `Predefined.xml`, `Schedule.xml` (расписание регламентного задания), `Rights.xml` (права роли), `Help.xml`; для конфигурации — `ManagedApplicationModule.bsl`, `SessionModule.bsl`, `ExternalConnectionModule.bsl`, `OrdinaryApplicationModule.bsl`.
- Форма: `Forms/<Имя>.xml`, `Forms/<Имя>/Ext/Form.xml`, `Forms/<Имя>/Ext/Form/Module.bsl`.

**Линейный** — устаревший, не рекомендуется; автономный сервер его не поддерживает. Все файлы в одном каталоге с именами вида `Catalog.Товары.Form.ФормаЭлемента.Form.Module.txt`.

### 2.17.4. Выгрузка

- В каталог или в zip-архив.
- Флажок «Выполнять на сервере» (клиент-серверный вариант): выгрузку ведут несколько системных фоновых заданий; «Количество заданий выгрузки» = 0 — платформа подбирает сама.
- Кроме `Configuration.xml` создаётся файл версий `ConfigDumpInfo.xml`. При повторной выгрузке в тот же каталог выгружаются только изменившиеся объекты (**инкрементальная выгрузка**). Полная выгрузка выполняется, если файла версий нет, конфигурация или объект переименованы, объект удалён, изменены предопределённые данные или диаграмма бизнес-процесса.
- Формат в каталоге должен совпадать с форматом новой выгрузки.

### 2.17.5. Загрузка

- Платформа **не проверяет корректность настроек поддержки** при загрузке из XML — ответственность на том, кто загружает.
- **Полная загрузка** заменяет основную конфигурацию. Нельзя загрузить в конфигурацию, подключённую к хранилищу; конфигурацию на поддержке — только при включённой возможности изменений для всех объектов.
- **Частичная загрузка** — только ключом пакетного режима `/LoadConfigFromFiles` с параметром `-files`; интерактивно не поддерживается, с несколькими расширениями не работает. Объект загружается целиком с подчинёнными. При ошибке происходит возврат к сохранённой конфигурации, несохранённые изменения теряются. Диагностику даёт ключ `/Out`.
  - Добавление объекта: загрузить объект и его родителя. Удаление: загрузить родителя без упоминания объекта. Переименование и изменение: загрузить объект со всеми подчинёнными (и родителя — при переименовании).
  - Если загружается корневой элемент без файла `ParentConfigurations.bin`, конфигурация снимается с поддержки.
  - Пример: `1cv8 DESIGNER /IBName "IBName" /LoadConfigFromFiles D:\Source -files D:\Source\Catalogs\Контрагенты\Ext\ObjectModule.bsl`

## 2.25. Работа с конфигурацией из встроенного языка

- Свойство глобального контекста `Метаданные` — объект `ОбъектМетаданныхКонфигурация`.
- Анализ конфигурации или расширения из файла: `Новый ОбъектМетаданныхКонфигурация(Новый ДвоичныеДанные(<путь>))`.
- Краткие сведения (имя, версия, поставщик) — `Новый ОписаниеКонфигурации(…)`.
- Сведения из файла обновления `.cfu` (какая версия получится и какие версии обновляются) — `Новый ОписаниеОбновленияКонфигурации(…)`.
