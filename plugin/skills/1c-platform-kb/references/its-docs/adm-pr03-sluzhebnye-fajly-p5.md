### 3.24.2 (продолжение). Элементы файла logcfg.xml

Точные заголовки разделов 3.24 и 3.24.2 — в предыдущей части; здесь только подразделы 3.24.2.7–3.24.2.15.

#### 3.24.2.7. Элемент `<mem>`

Назначение: включает в процессах сервера «1С:Предприятия» учёт памяти — считаются

- количество выделенных и не освобождённых фрагментов памяти;
- суммарный объём таких фрагментов.

Когда появляется событие `MEM`: сравниваются два соседних момента «простоя» процесса сервера (когда процесс не выполняет ни одного вызова и ни одного регламентного задания). Если между ними число выделенных, но не освобождённых фрагментов выросло — формируется событие `MEM`.

Свойства события `MEM`:

| Свойство | Смысл |
|---|---|
| `sz` | общий объём выделенной процессом и не освобождённой памяти |
| `szd` | изменение `sz` с момента вывода предыдущего события `MEM` |
| `cn` | общее количество выделенных и не освобождённых фрагментов |
| `cnd` | изменение `cn` с момента вывода предыдущего события `MEM` |

Длительность события `MEM` = интервал между последним и предпоследним моментами простоя процесса (именно за это время выросло число занятых фрагментов).

Предупреждение документации: наличие `<mem>` несколько снижает производительность, особенно при параллельной работе нескольких пользователей.

Одного фильтра по событию недостаточно. Такая настройка память НЕ собирает и `MEM` не выводит (нет элемента `<mem/>`):

```xml
<config xmlns="http://v8.1c.ru/v8/tech-log">
<log location="C:\ProgramFiles\1cv8\logs" history="24">
<event>
<eq property="name" value="mem"/>
</event>
<property name="all"/>
</log>
</config>
```

А такая — собирает объём распределённой памяти и при его росте выводит `MEM`:

```xml
<config xmlns="http://v8.1c.ru/v8/tech-log">
<log location="C:\ProgramFiles\1cv8\logs" history="24">
<event>
<eq property="name" value="mem"/>
</event>
<property name="all"/>
</log>
<mem/>
</config>
```

#### 3.24.2.8. Элемент `<ftextupd>`

Включает расширенную информацию о процессе обновления индексов полнотекстового поиска (событие `FTEXTUpd`). Если элемента в файле нет — расширенная информация в ТЖ не попадает.

⚠ в источнике неясно: имя события в одном месте написано как `FTETXUpd`, в другом как `FTEXTUpd` (первое, по всей видимости, опечатка).

| Атрибут | Значения | Смысл |
|---|---|---|
| `logfiles` | `0` (`false`) — не включать; `1` (`true`) — включать | наличие расширенной информации в событии `FTEXTUpd` |

#### 3.24.2.9. Элемент `<query>`

Управляет записью в ТЖ сведений о полях, которые при исполнении запроса к **внешнему источнику данных** содержат `NULL`, хотя такое значение для них не допускается (событие `QERR`). Включённое отслеживание может существенно замедлить выполнение запросов.

| Атрибут | Значения | Смысл |
|---|---|---|
| `checkActualNullable` | `1` (`true`) — информация о полях собирается; `0` (`false`) или элемент `<query>` отсутствует — не собирается | управление сбором |

#### 3.24.2.10. Элемент `<plansql>`

##### 3.24.2.10.1. Общее описание

- Присутствие элемента `<plansql>` включает сбор планов запросов, которые СУБД формирует при выполнении запросов «1С:Предприятия».
- Сам план попадает в свойство `planSQLText` событий, связанных с исполнением запросов конкретной СУБД.
- Совет документации: вместе со свойством `planSQLText` включать в состав регистрируемых свойств и свойство `SQL` (текст запроса, для которого получен план).

```xml
<?xml version="1.0"?>
<config xmlns="http://v8.1c.ru/v8/tech-log">
<log location="c:\log" history="24">
<event>
<eq property="name" value="dbmssql"/>
</event>
<property name="sql"/>
<property name="plansqltext"/>
</log>
<plansql />
</config>
```

Разбор примера: отбор по событию `dbmssql` (Microsoft SQL Server), `<plansql />` включает сбор планов, `<property name="plansqltext"/>` — запись плана, `<property name="sql"/>` — запись текста запроса. (В источнике в этом месте сказано, что планы пишутся «в журнал регистрации»; по контексту имеется в виду технологический журнал.)

Ограничения и предупреждения:

- Получение планов замедляет выполнение запросов к СУБД; для некоторых СУБД — существенно. В обычном режиме работы планы не собирают, только на время анализа производительности запросов.
- Для внешних источников данных (событие `EDS`) план получается только если СУБД внешнего источника — IBM Db2, Microsoft SQL Server, Oracle Database или PostgreSQL. Для остальных СУБД в ТЖ пишется только текст запроса.

##### 3.24.2.10.2. Информация по планам запросов СУБД

- Как читать план — описано в документации конкретной СУБД.
- **PostgreSQL и Oracle Database**: формат плана в точности совпадает с форматом из документации СУБД.
- **Microsoft SQL Server и IBM Db2**: формат упрощён относительно оригинального, но названия полей сохранены оригинальные; интерпретация полей — по документации СУБД (детали — в 3.24.2.10.3 и 3.24.2.10.4).

##### 3.24.2.10.3. Формат плана запроса MS SQL Server

`planSQLText` состоит из строк (разделитель — перевод строки), в каждой строке поля через запятую в таком порядке:

1. `Rows`
2. `Executes`
3. `EstimateRows`
4. `EstimateIO`
5. `EstimateCPU`
6. `AvgRowSize`
7. `TotalSubtreeCost`
8. `EstimateExecutions`
9. `StmtText`

Последнее поле (`StmtText`) читается до конца строки — запятые внутри него разделителями не считаются.

##### 3.24.2.10.4. Формат плана запроса IBM Db2

`planSQLText` состоит из строк (разделитель — перевод строки), поля через запятую. Имена полей совпадают с полями таблиц объяснений (explain tables); в скобках — таблица, из которой взято поле:

1. `OPERATOR_TYPE` (`EXPLAIN_OPERATOR`)
2. `TOTAL_COST` (`EXPLAIN_OPERATOR`)
3. `STREAM_COUNT` (`EXPLAIN_STREAM`)
4. `IO_COST` (`EXPLAIN_OPERATOR`)
5. `CPU_COST` (`EXPLAIN_OPERATOR`)
6. `COMM_COST` (`EXPLAIN_OPERATOR`)
7. `BUFFERS` (`EXPLAIN_OPERATOR`)
8. `PREDICATE_TEXT` (`EXPLAIN_PREDICATE`)

- Последнее поле (`PREDICATE_TEXT`) читается до конца строки, запятые в нём игнорируются.
- В конце плана добавляется строка, начинающаяся с `Optimized query:` — текст запроса, сформированный оптимизатором СУБД (заканчивается концом строки). Исходный текст запроса — в свойстве `SQL` события. Идентификаторы из оптимизированного запроса используются в колонке `PREDICATE_TEXT`.

##### 3.24.2.10.5. Формат плана запроса файловой версии

Общая структура:

```
<План запроса>
 [CONST <Условия>]
<Поля списка выборки>
[<Описание источника> [<Описание связи> […]]]
[WITHOUT DUPLICATES]
[GROUPING]
[SORTING [CUTTING TOP]]
[UNION [ALL] <План запроса>]
```

| Ключевое слово | Смысл |
|---|---|
| `WITHOUT DUPLICATES` | данные получаются без дубликатов |
| `GROUPING` | выполняется группировка результата |
| `SORTING` | выполняется сортировка результата |
| `CUTTING TOP` | после сортировки берётся только часть записей |

Условия:

```
<Условия>
 WHERE [(POST) | (END)] <Условие> [AND <Условие> […]]
```

- `(POST)` — условия проверяются после выполнения соединения;
- `(END)` — условия проверяются после выполнения соединений между всеми таблицами.

Поля списка выборки:

```
<Поля списка выборки>
 Fields:(<Выражение из списка выборки> [,<Выражение из списка выборки>])
```

Описание сканирования:

```
<Описание сканирования>
 {{NOT SCAN} | {FULL SCAN} | {DISTINCT SCAN} | {RANGE SCAN}} [UNTIL FIRST NOT NULL] [USING [REVERSE] INDEX (<Имя индекса>)[(<Количество используемых полей индекса> fields)]]
```

| Ключевое слово | Смысл |
|---|---|
| `NOT SCAN` | содержимое таблицы не сканируется |
| `FULL SCAN` | таблица сканируется полностью |
| `DISTINCT SCAN` | обход различных значений по индексу |
| `RANGE SCAN` | сканируется участок таблицы по индексу |
| `UNTIL FIRST NOT NULL` | сканирование до первой записи со значением не `NULL` |
| `USING INDEX` | для обхода используется индекс |
| `REVERSE` | индекс используется в обратной последовательности |

Описание источника и связи:

```
<Описание источника>
 {<Имя таблицы> [(TWICE)] <Описание сканирования>} |
{NESTED SELECT <Описание сканирования> (<План запроса>)}
<Условия>

<Описание связи>
 {{ NESTED [OUTER] LOOP <Имя таблицы> [(TWICE)] <Описание сканирования>} |
{ NESTED [OUTER] LOOP BY SELECT <Описание сканирования> (<План запроса>)}}
<Условия> [<Условия>]
```

| Ключевое слово | Смысл |
|---|---|
| `(TWICE)` | таблица используется в запросе несколько раз |
| `NESTED LOOP` | для каждой записи левой таблицы выполняется цикл обхода записей правой |
| `OUTER` | если в правой таблице нет записи, подходящей по условию связи, запись целиком не пропадает |

#### 3.24.2.11. Элемент `<defaultlog>`

Задаёт параметры **технологического журнала по умолчанию**. У этого журнала фильтр событий фиксирован платформой и изменению не подлежит; условно он эквивалентен такой настройке:

```xml
<log location="C:\Users\<UserName>\AppData\Local\1C\1cv8\logs" history="24" >
<event>
<eq property="name" value="system"/>
<eq property="level" value="error"/>
</event>
<property name="all"/>
</log>
```

- В журнал по умолчанию пишутся события, критические для функционирования системы; состав событий не документируется.
- Детализация формирования событий настраивается элементом `<system>` (см. 3.24.2.12).
- В отличие от обычного ТЖ, файлы журнала по умолчанию создаются только тогда, когда соответствующее событие действительно возникло.

| Атрибут | Описание | Умолчание |
|---|---|---|
| `history` | через сколько часов информация удаляется из журнала по умолчанию. Значение `0` — **отключает** запись журнала по умолчанию | `24` |
| `location` | каталог журнала по умолчанию | если не задан: Linux — `~/.1cv8/logs`; Windows — `%LOCALAPPDATA%\1C\1cv8\logs` |

Требование: в атрибутах `location` элементов `<log>`, `<dump>` и `<defaultlog>` должны быть указаны **разные** каталоги.

#### 3.24.2.12. Элемент `<system>`

Управляет формированием событий `SYSTEM` в ТЖ.

- В `logcfg.xml` элемент может отсутствовать, быть один или их может быть несколько.
- Если `<system>` отсутствует — уровень формирования системных событий для всех компонентов системы равен `ERROR`.
- События `SYSTEM` попадают одновременно во все настроенные технологические журналы, включая журнал по умолчанию.

| Атрибут | Описание |
|---|---|
| `class` | имя класса, для которого настраивается формирование системных событий. **Регистрозависимое** |
| `component` | имя компоненты, для которой настраивается формирование системных событий. **Регистрозависимое** |
| `level` | минимальный уровень формируемых событий (см. ниже). События ниже заданного уровня системой не формируются |

Значения `level` в порядке возрастания значимости:

| Уровень | Смысл |
|---|---|
| `TRACE` | максимально подробный уровень |
| `DEBUG` | отладочная информация: события для отладки механизмов платформы или расследования особо трудно обнаруживаемых ошибок |
| `INFO` | информационный: события о нормальном функционировании механизмов платформы |
| `WARNING` | предупреждения: нештатные, но не критичные для механизма платформы ситуации |
| `ERROR` | ошибки: ошибочные с точки зрения механизма платформы ситуации |
| `NONE` | фиксация системных событий отключена |

Пример: `<system level="info" />` — формируются события уровней `INFO`, `WARNING` и `ERROR`.

Пример комбинации:

```xml
<system level="info"/>
<system level="debug" class="core::FileSystem" />
<system level="warning" component="core82" />
```

- для всех объектов системы — события `SYSTEM` уровня `INFO` и выше;
- для класса `core::FileSystem` — уровня `DEBUG`;
- для всех классов компоненты `core82` — уровня `WARNING` и выше.

#### 3.24.2.13. Элемент `<dbmslocks>`

Включает сбор информации о блокировках СУБД в ТЖ. Нет элемента — информация о блокировках СУБД в журнал не попадает. Информация выводится специальными («блокировочными») свойствами событий — см. 3.24.5.

#### 3.24.2.14. Элемент `<scriptcircrefs>`

Включает сбор информации о циклических ссылках в ТЖ. Нет элемента — информация о циклических ссылках не собирается. Подробнее — 3.24.6.

```xml
<?xml version="1.0"?>
<config xmlns="http://v8.1c.ru/v8/tech-log">
<log location="D:\V82\logs" history="96">
<event>
<eq property="name" value="SCRIPTCIRCREFS"/>
</event>
<event>
<eq property="name" value="Excp"/>
</event>
<property name="all"/>
</log>
<scriptcircrefs/>
</config>
```

В примере: включён сбор сведений о циклических ссылках (`<scriptcircrefs/>`), в журнал пишутся только события `SCRIPTCIRCREFS` и `EXCP`, со всеми свойствами (`<property name="all"/>`).

#### 3.24.2.15. Элемент `<sessiondatacontext>`

Управляет выводом списка операций изменения данных сеанса и их контекстов. При включении работа системы замедляется — использовать только на время анализа проблем.

Куда выводится: в свойство `Context` события `CALL` технологического журнала **менеджера кластера (`rmngr`)** для методов `seanceParametersCommit` и `finishSeance` (это значения свойства `MName` события `CALL`).

Для каких операций:

| Операция | Смысл |
|---|---|
| `SET` | установка значения параметра сеанса |
| `COPY` | копирование значения параметра в другой сеанс |
| `DELETE` | удаление параметра сеанса |

Из чего состоит контекст:

- наименование вызванного ресурса информационной базы;
- стек встроенного языка от дна к вершине (как в свойстве `Context` других событий ТЖ);
- строки кода платформы, где выполнено изменение данных сеанса (для операции `SET`).

Формат списка контекстов:

```
<список_контекстов>: <один_контекст> [конец_строки # конец_строки <список_контекстов>]
<один_контекст>: <список_операций> конец_строки <контекст>
<список_операций>: <операция> [конец_строки <список_операций>]
<операция>: {SET, <идентификатор>, <размер>} | {DELETE, <идентификатор>} | {COPY, <идентификатор>, <номер_целевого_сеанса>}
<идентификатор>: число, crc32 идентификатора параметра сеанса
<размер>: число, объём сериализованного значения параметра в байтах.
<номер_целевого_сеанса>: число, номер сеанса, в который копируется параметр (аналогично значению свойства SessionID).
<контекст>: операция, при выполнении которой сделано изменение данных сеанса
```

### 3.24.3. Файлы технологического журнала

#### 3.24.3.1. Общая информация

ТЖ — это каталог с файлами данных. Структура каталога определяется настройками хранения, а содержимое файлов — настройками отбора событий и свойств в `logcfg.xml`.

#### 3.24.3.2. Хранение и правила именования файлов технологического журнала

Каталог размещения задаёт атрибут `log.location`, структуру внутри него — атрибут `log.placement`:

| `log.placement` | Структура |
|---|---|
| `folders` | файлы лежат в подкаталогах с именами вида `<appName_pid>`: `appName` — имя процесса ОС, пишущего журнал (`1cv8`, `1cv8c`, `rphost` и т. д.), `pid` — идентификатор процесса в ОС |
| `plain` | подкаталоги не создаются, файлы лежат прямо в каталоге `log.location` |

Полное имя файла зависит от трёх вещей: структуры хранения, схемы ротации и того, сжимается ли файл после ротации. Общий шаблон:

```
appName_pid_timestamp.log.counter.zip
```

| Часть имени | Смысл |
|---|---|
| `appName` | имя процесса ОС, формирующего файл (`1cv8`, `1cv8c`, `rphost` и т. д.) |
| `pid` | идентификатор процесса в ОС |
| `timestamp` | отметка времени создания файла вида `yymmddhh` (`yy` — две последние цифры года, `mm` — месяц с ведущим нулём, `dd` — день месяца с ведущим нулём, `hh` — час создания файла). Значение кратно периоду ротации |
| `log` | расширение файла данных ТЖ |
| `counter` | монотонно возрастающий целочисленный счётчик |
| `zip` | расширение упакованного файла |

Все части одновременно в имени не встречаются. Условия появления (как записано в источнике):

| Фрагмент имени | Когда присутствует |
|---|---|
| `appName_pid` | `log.location="plain"` или `log.rotation="size"` |
| `timestamp` | `log.location="folders"` или `log.rotation="period"` |
| `counter` | `log.rotation="size"` |
| `zip` | `log.comperssion="zip"` |

⚠ в источнике неясно: в этой таблице значения `plain`/`folders` приписаны атрибуту `log.location`, хотя по смыслу и по тексту выше это значения атрибута `log.placement`. Атрибут сжатия в таблице назван `log.comperssion`, а в разделе 3.24.3.3 — `log.compress`; точное имя атрибута нужно сверять с описанием элемента `<log>` (предыдущая часть главы).

#### 3.24.3.3. Удаление, ротация и архивирование файлов технологического журнала

**Удаление (глубина хранения) — `log.history`:**

- значение — число часов, после которых файлы ТЖ удаляются. Например, `24` — в каталоге ТЖ не остаётся файлов, не использовавшихся более 24 часов;
- если после удаления устаревших файлов каталог опустел — он тоже удаляется, так что в дереве ТЖ не остаётся устаревших файлов и папок;
- удаляются файлы **только тех приложений, которые выполняются в момент удаления**;
- очистка работает для любого размещения (иерархического и плоского) и для любого вида ротации (по размеру и по времени).

**Ротация — `log.rotation`** (создание нового файла ТЖ при выполнении критерия):

| `log.rotation` | Критерий | Настраивающий атрибут | Особенности | Примеры имён |
|---|---|---|---|---|
| `period` | по периоду времени, в часах; минимум 1 час | `log.rotationperiod` | последние 2 символа имени файла — номер часа начала записи файла, кратный `log.rotationperiod` | `23080116.log`, `23080117.log`, `23080118.log` |
| `size` | по размеру файла, в мегабайтах; минимальный шаг 1 МБ | `log.rotationsize` | новый файл создаётся, когда текущий превысит `log.rotationsize`; устаревшему файлу добавляется суффикс `.counter` (монотонно растущий счётчик). **Чем меньше счётчик, тем старее журнал в файле** | `ragent_18972.log`, `ragent_18972.log.1`, `ragent_18972.log.2` |

**Сжатие — `log.compress`:**

- файлы ТЖ — регулярный текст с большим числом повторов, сжимаются хорошо;
- если атрибут имеет значение `zip`, при ротации соответствующий файл сжимается и получает расширение `.zip`;
- примеры: `23080116.log.zip`, `23080117.log.zip`, `23080118.log`, `ragent_18972.log`, `ragent_18972.log.1.zip`, `ragent_18972.log.2.zip` (текущий, ещё не ротированный файл остаётся несжатым).

#### 3.24.3.4. Формат файлов технологического журнала

Формат задаёт атрибут `log.format`:

| `log.format` | Формат |
|---|---|
| `text` | «плоский» текстовый формат |
| `json` | список JSON-объектов |

**Текстовый формат, иерархическое размещение (`log.placement="folders"`).** Пример строки:

```
45:31.831006-1,SCALL,2,level=INFO,process=1cv8,OSThread=13476,ClientID=1,Interface=7f58f27d-5ad8-43a1-aa1e-c982f41bed5c,IName=IRemoteCreatorService,Method=0,CallID=13126,MName=createRemoteInstance,DstClientID=0
```

Шаблон строки: `mm:ss.tttttt-d,<событие>,<вложенность>,<уровень>,<свойства>`

| Часть | Смысл |
|---|---|
| `mm` | номер минуты в текущем часе |
| `ss` | номер секунды в текущей минуте |
| `tttttt` | номер микросекунды текущей секунды |
| `d` | длительность события **в микросекундах** |
| `<событие>` | наименование события |
| `<вложенность>` | уровень события в стеке текущего потока |
| `<уровень>` | уровень события технологического журнала |
| `<свойства>` | выбранные свойства события со значениями через запятую, каждое в виде `<имя>=<значение>` |

Экранирование значений свойств: если в тексте есть символ конца строки или запятая, текст заключается в кавычки или апострофы — выбирается тот символ, которого в строке меньше; сами кавычки/апострофы внутри текста удваиваются.

**Текстовый формат, плоское размещение (`log.placement="plain"`).** Меняется только начало строки — дата и время пишутся полностью, в формате XML:

```
2023-08-01T15:01:45.259000-14998,SCALL,0,level=INFO,process=1cv8c,OSThread=2732,ClientID=8,Interface=bc15bd01-10bf-413c-a856-ddc907fcd123,IName=IVResourceRemoteConnection,Method=0,CallID=26018,MName=send,DstClientID=122
```

В начале `2023-08-01T15:01:45.259000-14998`:

- `2023-08-01T15:01:45` — дата и время с точностью до секунды;
- `259000` — микросекунды текущей секунды (аналог `tttttt`);
- `14998` — длительность события в микросекундах (аналог `d`).

Остальные поля не меняются.

**Формат JSON (`log.format="json"`).** Безымянные поля строки получают имена:

| Что это | Идентификатор в JSON |
|---|---|
| дата и время события (с точностью до микросекунды) | `ts` |
| длительность события (в микросекундах) | `duration` |
| уровень события в стеке текущего потока | `depth` |
| имя события | `name` |

```json
{"ts":"2023-08-02T08:48:05.982000","duration":"46998","name":"SCALL","depth":"0","level":"INFO","process":"1cv8c","OSThread":"15968","ClientID":"8","Interface":"bc15bd01-10bf-413c-a856-ddc907fcd123","IName":"IVResourceRemoteConnection","Method":"0","CallID":"28284","MName":"send","DstClientID":"122"}
```

Каждое свойство — пара «ключ–значение» стандартного JSON (в примере все значения — строки). Дата и время — в формате XML (описание формата: https://www.w3.org/TR/xmlschema-2/#dateTime).

### 3.24.4. Вывод контекстов исключений

- Контекст исключения — последовательность событий ТЖ типа `EXCPCNTX`.
- Каждое `EXCPCNTX` соответствует одному из длительных событий, которые начались, но не завершились к моменту нештатной ситуации.
- События выводятся в порядке **убывания** уровня вложенности.
- Тип исходного события записывается в свойство `SrcName` события `EXCPCNTX`.

Контекст исключения выводится, если ТЖ включён (в `logcfg.xml` есть хотя бы один элемент `log`) и случилось одно из двух:

1. исключение операционной системы — процесс (клиент или сервер) завершился аварийно, построен дамп аварийного завершения;
2. исключение в базе данных, которое привело к показу сообщения об ошибке и закрытию приложения «1С:Предприятия».

При любой ошибке базы данных в ТЖ записывается событие `EXCP` — если оно проходит условия отбора, заданные в `logcfg.xml`.

### 3.24.5. Вывод информации о взаимных блокировках

Механизм:

- при любом обращении к СУБД, но **не чаще 1 раза в 2 секунды**, выполняется дополнительный запрос к СУБД: какой поток заблокирован и каким потоком;
- результат — таблица пар («жертва блокировки», «источник блокировки»): жертва — идентификатор соединения с СУБД, ожидающего блокировку; источник — идентификатор соединения с СУБД, установившего блокировку;
- если в кластере несколько рабочих процессов, запрос выполняет один из них; такие запросы нумеруются;
- сбор выполняется **только при наличии элемента `<dbmslocks>`** в `logcfg.xml`.

Как данные попадают в журнал:

- данные таблицы добавляются к контексту каждого потока, которому соответствуют найденные идентификаторы соединений с СУБД;
- блокировочные свойства дописываются к очередному событию ТЖ, которое завершится в этом потоке;
- у потока-жертвы сведения очищаются после вывода; у потока-источника — при закрытии или откате транзакции;
- порядок добавления: потоку-жертве, если он ещё «не знает» о блокировке, устанавливаются номер запроса и идентификатор потока-источника; потоку-источнику номер запроса добавляется, только если у него есть жертвы, которые ещё об этом не знали.

Состав информации о блокировке: поток — источник и момент обнаружения; поток — жертва и момент обнаружения; номер запроса (для жертвы); список номеров запросов (для источника); номер соединения источника (для жертвы).

Блокировочные свойства событий:

| Свойство | Смысл | Пример |
|---|---|---|
| `lka` | `lka='1'` — поток является источником блокировки | `'1'` |
| `lkp` | `lkp='1'` — поток является жертвой блокировки | `'1'` |
| `lkpid` | номер запроса к СУБД «кто кого заблокировал» (только для потока-жертвы) | `'423'` |
| `lkaid` | список номеров запросов к СУБД «кто кого заблокировал» (только для потока-источника) | `'271,273,274'` |
| `lksrc` | номер соединения источника блокировки (если поток — жертва) | `'23'` |
| `lkpto` | время в секундах с момента обнаружения, что поток — жертва | `'15'` |
| `lkato` | время в секундах с момента обнаружения, что поток — источник блокировок | `'21'` |

Методика анализа из документации:

1. в ТЖ процессов `rphost` найти первое событие со свойствами `lka` и `lkp`;
2. взять значения `lkaid`, `lkpid`;
3. найти все события с этими значениями в журналах **всех** рабочих процессов кластера;
4. по найденной группе событий определить, кто кого заблокировал, на какое время и что при этом делал каждый.

Дополнительно: в свойстве `Txt` события `TLOCK` может отображаться пространство имён, в котором наложена блокировка.

### 3.24.6. Вывод информации о циклических ссылках

Циклическая ссылка — данные, которые прямо или косвенно ссылаются сами на себя. Простейший пример на встроенном языке:

```bsl
Структура1 = Новый Структура("СсылкаНаСтруктуру2");
Структура2 = Новый Структура("СсылкаНаСтруктуру1");
Структура1.СсылкаНаСтруктуру2 = Структура2;
Структура2.СсылкаНаСтруктуру1 = Структура1;
```

Последствия: память под такие данные не освобождается (например, при закрытии формы с таким кодом), процесс, обслуживающий сеанс, с каждым открытием формы занимает всё больше оперативной памяти. Итог — аварийное завершение прикладного решения либо очень большой расход памяти, общее замедление компьютера, невозможность открыть внешнюю обработку после внесения изменений и т. п.

Инструменты поиска (четыре):

| № | Инструмент | Как включается | Область действия | Поведение при обнаружении |
|---|---|---|---|---|
| 1 | Настройка ТЖ | элемент `<scriptcircrefs>` в `logcfg.xml` | платформа начинает анализ циклических ссылок; попадут ли события `SCRIPTCIRCREFS` в журнал — зависит от остальных настроек ТЖ (отбор событий) | пишутся события `SCRIPTCIRCREFS`, выполнение прикладного решения **не прерывается** |
| 2 | Командная строка клиента (тонкого или толстого) | параметр `/EnableCheckScriptCircularRefs`; он же подставляется, если в конфигураторе установлен флажок «Проверка циклических ссылок встроенного языка» (Главное меню — Сервис — Параметры — Запуск 1С:Предприятия — Дополнительные) | клиентский код прикладного решения | работа прерывается с сообщением, продолжить нельзя |
| 2 | Командная строка сервера | запуск сервера с параметром `/enableCheckScriptCircularRefs` | все сеансы, обслуживаемые сервером, запущенным с этим параметром | работа прерывается с сообщением, продолжить нельзя |
| 3 | Параметр `conf.cfg` | `EnableCheckScriptCircularRefs` = `true` | все экземпляры «1С:Предприятия», использующие этот `conf.cfg` | работа прерывается с сообщением, продолжить нельзя |
| 4 | Метод встроенного языка | метод глобального контекста `ПроверитьЦиклическиеСсылкиВстроенногоЯзыка()` | проверяется переменная, переданная параметром, либо все локальные переменные, доступные в момент вызова | работа прерывается с сообщением, продолжить нельзя |

Когда выполняется проверка:

- при завершении метода встроенного языка — анализируются все локальные переменные метода и его параметры;
- при установке параметра сеанса — анализируется устанавливаемое значение;
- в местах вызова специального метода встроенного языка.

Предупреждение документации: любой из этих инструментов существенно снижает производительность. В обычном режиме работы их не используют — только при целенаправленном поиске циклических ссылок для исправления прикладного решения.

Связанные разделы: элемент `<scriptcircrefs>` (3.24.2.14), файл `conf.cfg`, общие команды запуска.

## 3.25. nethasp.ini

### 3.25.1. Общее описание

Назначение: настройка взаимодействия «1С:Предприятия» с HASP License Manager (HASP LM).

**Расположение.** Файл лежит в каталоге конфигурационных файлов «1С:Предприятия»; его наличие необязательно. Если в каталогах конфигурационных файлов его нет, поиск идёт так:

| ОС | Порядок поиска |
|---|---|
| Linux | 1) текущий каталог; 2) домашний каталог пользователя; 3) каталог `/etc` |
| macOS | 1) текущий каталог; 2) домашний каталог пользователя; 3) каталог `/etc` |
| Windows (только Windows) | каталог исполняемых файлов запущенной версии; текущий каталог; `%SYSTEMROOT%\System32` (32-разрядная ОС) или `%SYSTEMROOT%\SysWOW64` (64-разрядная ОС); `%SYSTEMROOT%\System`; `%SYSTEMROOT%`; каталоги из `PATH` |

**Образец файла.** При установке платформы образец `nethasp.ini` копируется в каталог `conf` установочного каталога «1С:Предприятия». Он почти целиком состоит из закомментированных строк, умолчаний не переопределяет, но содержит наиболее полный список параметров.

**Структура.** Четыре секции:

| Секция | Назначение |
|---|---|
| `[NH_COMMON]` | общие (глобальные) настройки для всех разделов файла |
| `[NH_IPX]` | настройки протокола IPX |
| `[NH_NETBIOS]` | настройки протокола NetBIOS |
| `[NH_TCPIP]` | настройки протокола TCP/IP |

Правила:

- в каждой секции допустимы параметры, специфические для неё, и параметры, общие для всех секций;
- общий параметр, заданный в секции протокола, для этого протокола имеет **больший приоритет**, чем тот же параметр в `[NH_COMMON]`;
- комментарий начинается с `;` и продолжается до конца строки;
- регистр букв в именах параметров не важен.

|---|---|---|---|
| `NH_SERVER_ADDR` | `<Адрес1>, <Адрес2>` | IP-адреса всех HASP LM. Число адресов не ограничено; допустимы и IP-адреса, и текстовые имена хостов. Примеры из документации: IP-адрес `192.168.0.65`, имя локального узла `hasp.local` | — |
| `NH_SERVER_NAME` | `server1, server2, ...` | имена серверов, на которых ищется HASP LM. Не более 6 имён, каждое не длиннее 7 символов | — |
| `NH_PORT_NUMBER` | `<Число>` | номер сетевого порта | `475` |
| `NH_TCPIP_METHOD` | `TCP`, `UDP` | каким пакетом обращаться — TCP или UDP. **Значение `TCP` игнорируется: обращение к HASP LM всегда идёт по UDP** | `UDP` |
| `NH_USE_BROADCAST` | `Enabled`, `Disabled` | использовать широковещательный механизм UDP | `Enabled` |
| `NH_SESSION` | `<Число>` | интервал в секундах для попыток установить соединение с HASP LM | 2 секунды |
| `NH_SEND_RCV` | `<Число>` | максимальное время получения или отправки пакета | 1 секунда |

## 3.29. swpuser.ini

Назначение: переопределить пользователей ОС, от имени которых работают **рабочие процессы (`rphost`)** и **менеджер кластера (`rmngr`)**. По умолчанию оба работают от имени того же пользователя, что и агент сервера (`ragent`).

**Порядок замены пользователей** (начинать нужно с пользователя агента сервера):

1. выдать будущим пользователям компонентов кластера необходимые права доступа;
2. создать корректный файл `swpuser.ini`;
3. изменить настройки запуска (автозапуска) агента сервера, чтобы он стартовал от имени требуемого пользователя;
4. запустить агент сервера (и весь кластер) с новыми настройками.

**Особенности по ОС:**

| | Linux | Windows (только Windows) |
|---|---|---|
| Агент сервера (`ragent`) | должен быть запущен от имени суперпользователя (`root`) | пользователь должен входить в группу администраторов и иметь права «Настройка квот памяти для процесса» (Adjust memory quotas for a process) и «Замена маркера уровня процесса» (Replace a process level token); членство в администраторах этих прав не гарантирует |
| Пароли в `swpuser.ini` | параметры `password` и `rmngr_pass` при запуске рабочих процессов и менеджеров кластера **игнорируются** | особенностей в источнике не указано |
| Пользователи `rphost` / `rmngr` | нужны права доступа, описанные в документации (ссылка в источнике не раскрыта), и **полный доступ к каталогу `/var/1C`** | те же права и полный доступ к `%ALLUSERSPROFILE%\1C\1cv8` |

Общие требования для любой ОС:

- для всех пользователей, от имени которых запускаются рабочие процессы и менеджеры кластера, должны существовать **профили операционной системы** (создаются при создании пользователя либо однократным интерактивным входом). После создания профиля интерактивный вход можно запретить, если ОС это позволяет;
- смена пользователя агента сервера обязана сопровождаться явным указанием пользователей `rphost` и `rmngr` через `swpuser.ini`. Иначе все процессы кластера будут работать от имени администратора системы — документация называет это крайне небезопасным сценарием, недопустимым в промышленных системах.

**Расположение файла:** каталог данных кластера, рядом с файлом списка кластеров, с которым работает агент сервера.

**Формат:**

```
user=<имя пользователя для rphost>
password=<пароль пользователя для rphost>
[rmngr_user=<имя пользователя для rmngr>
[rmngr_pass=<пароль пользователя для rmngr>]]
[registry=<каталог реестра кластера>]
[<port>:
[user=<имя пользователя для rphost>
[password=<пароль пользователя для rphost>]]
[rmngr_user=<имя пользователя для rmngr>
[rmngr_pass=<пароль пользователя для rmngr>]]
[registry=<каталог реестра кластера>]]
```

| Параметр | Назначение | Если не указан |
|---|---|---|
| `user`, `password` | пользователь и пароль, от имени которого работают рабочие процессы во всех кластерах на данном компьютере | рабочие процессы работают от имени пользователя агента сервера |
| `rmngr_user`, `rmngr_pass` | пользователь и пароль, от имени которого работают менеджеры кластера во всех кластерах данного компьютера | менеджер кластера работает от имени пользователя агента сервера |
| `registry` | корневой каталог для каталогов данных кластера всех кластеров данного центрального сервера | используется каталог вида `reg_<PORT>` в каталоге данных главного менеджера кластера (задаётся параметром `/d` при запуске агента) |
| `<port>:` | раздел с номером порта менеджера кластера — индивидуальный набор тех же параметров (`user`, `password`, `rmngr_user`, `rmngr_pass`, `registry`) для конкретного кластера | действуют общие параметры |

Замечания:

- при смене каталога реестра кластера (общего или индивидуального) пользователь, от имени которого работает менеджер кластера, должен иметь **полные права** на этот каталог;
- имя пользователя с доменом записывается в виде `\\имя-домена\имя-пользователя`;
- пароли в примере документации демонстрационные; использовать такие (или похожие) в промышленной эксплуатации настоятельно не рекомендуется;
- параметр агента сервера, задающий каталог данных, в тексте источника записан как `/d`, а в примере ниже — как `-d`.

**Пример из документации.** На компьютере два кластера (порты `1541` и `1641`), агент запущен с параметром `-d"d:\cluster\main"`, файл `swpuser.ini` лежит в `d:\cluster\main`:

```
user=srv_1c_rphost
password=123
rmngr_user=srv_1c_rmngr
rmngr_pass=123
registry=d:\cluster\common
1541:
user=srv_1c_rphost_1541
password=123
rmngr_user=srv_1c_rmngr_1541
rmngr_pass=123
registry=d:\cluster\one
```

Результат:

- кластер `1541`: реестр кластера в `d:\cluster\one`, рабочие процессы — от `srv_1c_rphost_1541`, менеджер кластера — от `srv_1c_rmngr_1541` (ему нужен полный доступ к `d:\cluster\one`); фактический каталог данных кластера — `d:\cluster\one\reg_1541`;
- кластер `1641` и все кластеры, которые добавятся позже (пока файл не изменён): реестры в подкаталогах `d:\cluster\common`, пользователи `srv_1c_rphost` и `srv_1c_rmngr`; фактический каталог данных — `d:\cluster\common\reg_1641` и т. д.

## 3.31. Файл списка объектов

### 3.31.1. Общее описание

XML-файл со списком объектов, используемый при операциях сравнения конфигураций и при работе с хранилищем конфигурации.

```xml
<Objects…>
<Configuration…/>
<Object…>
<Subsystem…/>
</Object>
</Objects>
```

Пространство имён: `http://v8.1c.ru/8.3/config/objects`.

### 3.31.2. Элемент `<Objects>`

Корневой элемент. Может содержать не более одного элемента `<Configuration>` и один или несколько элементов `<Object>`.

| Атрибут | Обязательность | Тип | Описание |
|---|---|---|---|
| `version` | обязательный | Строка | версия списка файлов. Поддерживается только `1.0`; для любой другой — ошибка «Версия файла списка объектов x.x не поддерживается данной версией платформы» |

### 3.31.3. Элемент `<Configuration>`

Описывает корневой объект конфигурации. Может быть указан один раз или отсутствовать.

| Атрибут | Обязательность | Тип | Описание |
|---|---|---|---|
| `includeChildObjects` | обязательный | Булево | включать ли в операцию подчинённые (на полную глубину) объекты корневого элемента конфигурации |

### 3.31.4. Элемент `<Object>`

Описывает один объект конфигурации (возможно, вместе с подчинёнными), участвующий в операции. Элементов может быть несколько или ни одного. Элементу может быть подчинено не более одного элемента `<Subsystem>`.

| Атрибут | Обязательность | Тип | Описание |
|---|---|---|---|
| `fullName` | при работе с хранилищем — обязательный; при сравнении конфигураций — должен быть указан либо он, либо `fullNameInSecondConfiguration` | Строка | полное имя объекта в первой конфигурации. Используется и при настройке сравнения конфигураций, и при работе с хранилищем |
| `fullNameInSecondConfiguration` | при сравнении конфигураций — должен быть указан либо он, либо `fullName` | Строка | полное имя объекта во второй конфигурации. Используется только при настройке сравнения конфигураций |
| `includeChildObjects` | обязательный | Булево | включать ли в операцию подчинённые (на полную глубину) объекты объекта, указанного в `fullName`. Для подсистемы подчинёнными считаются **подчинённые подсистемы**, а не объекты, входящие в подсистему; чтобы включить объекты состава подсистемы, используется вложенный тег `<Subsystem>` |

⚠ Текст части 5 на этом обрывается: описание элемента `<Subsystem>` и остаток раздела 3.31 — в части 6.

## Что важно администратору Linux

1. **Журнал по умолчанию на Linux лежит в `~/.1cv8/logs`** (если у `<defaultlog>` не задан `location`). Глубина хранения по умолчанию — 24 часа; `history="0"` полностью отключает этот журнал. Файлы в нём появляются только при возникновении события.
2. Каталоги в `location` у `<log>`, `<dump>` и `<defaultlog>` должны быть **разными**.
3. Диагностические элементы `<mem>`, `<plansql>`, `<query checkActualNullable>`, `<sessiondatacontext>`, `<scriptcircrefs>` замедляют работу (по документации — от «несколько» до «существенно»). Включать их только на время расследования и убирать после.
4. Событие `MEM` не появится от одного лишь отбора `name=mem` — нужен отдельный элемент `<mem/>`. Аналогично планы запросов требуют `<plansql/>`, а блокировочные свойства — `<dbmslocks/>`.
5. Для PostgreSQL план в свойстве `planSQLText` имеет «родной» формат СУБД (как в документации PostgreSQL). Документация советует вместе с `plansqltext` выводить и свойство `sql` — текст запроса, план которого записан.
6. Разбор взаимных блокировок СУБД: включить `<dbmslocks>`, искать в журналах `rphost` события со свойствами `lka`/`lkp`, затем по `lkaid`/`lkpid` собрать события из журналов всех рабочих процессов. Опрос СУБД о блокировках идёт не чаще раза в 2 секунды.
7. Имена файлов ТЖ: при `placement="folders"` — подкаталоги `<имя_процесса>_<pid>` с файлами `yymmddhh.log`; при `placement="plain"` всё лежит в одном каталоге, а в строках события дата и время пишутся полностью. Длительность событий — в микросекундах.
8. Объём ТЖ ограничивается тремя механизмами: `history` (часы хранения), ротация (`rotation="period"` + `rotationperiod` в часах или `rotation="size"` + `rotationsize` в мегабайтах) и сжатие в zip при ротации. Удаление по `history` затрагивает только файлы приложений, выполняющихся в момент очистки.
9. `format="json"` даёт журнал в виде списка JSON-объектов с полями `ts`, `duration`, `depth`, `name` плюс свойства события.
10. `nethasp.ini` на Linux ищется в каталоге конфигурационных файлов платформы, затем в текущем каталоге, в домашнем каталоге пользователя и в `/etc`. В секции `[NH_TCPIP]` адреса менеджеров лицензий задаёт `NH_SERVER_ADDR`, порт — `NH_PORT_NUMBER` (по умолчанию 475), широковещательный поиск по UDP — `NH_USE_BROADCAST` (по умолчанию `Enabled`); обращение к HASP LM всегда идёт по UDP, `NH_TCPIP_METHOD=TCP` игнорируется.
11. `nhsrv.ini` для HASP License Manager на Linux не имеет пути по умолчанию — его нужно передавать параметром `-c`. Лимит одновременных подключений `NHS_USERLIST` по умолчанию 250; `NHS_IP_LIMIT` ограничивает обслуживаемые адреса.
12. `swpuser.ini` на Linux: агент сервера должен работать от `root`, параметры `password` и `rmngr_pass` игнорируются, пользователям `rphost`/`rmngr` нужен полный доступ к `/var/1C` и существующий профиль ОС. Если агент запущен от суперпользователя, а `swpuser.ini` не задан, весь кластер работает с правами администратора — так делать нельзя.
13. Через `swpuser.ini` (параметр `registry`, в том числе в секции `<port>:`) можно вынести реестр кластера в другой каталог; фактический каталог данных — `<registry>/reg_<порт>`, и у пользователя менеджера кластера должны быть на него полные права.
14. Реестр модулей утилиты `ring` на Linux: общий — `/etc/1C/1CE/ring-commands.cfg`, пользовательский — `~/.1C/1CE/ring-commands.cfg` (YAML, UTF-8 без BOM).
15. `rescntsrv.lst` в каталоге данных центрального сервера хранит значения счётчиков потребления ресурсов (обновление раз в 20 секунд) и нужен для их восстановления после перезапуска кластера. Порты автоматизированного тестирования веб-клиента по умолчанию — 1538–1539 (`testcfg.xml`).
