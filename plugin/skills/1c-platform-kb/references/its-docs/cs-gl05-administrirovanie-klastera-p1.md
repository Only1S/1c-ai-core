## 5.1. Администрирование информационной базы

### 5.1.1. Операции резервного копирования в клиент-серверном варианте

Общее правило: резервную копию делают перед любой операцией, способной повредить данные информационной базы (ИБ).

Сравнение двух способов получить копию:

| Способ | Что даёт | Ограничение |
|---|---|---|
| Резервная копия средствами СУБД | Максимально точная копия базы данных; возврат ровно к тому состоянию, с которого снята копия | — |
| Выгрузка ИБ в файл и последующая загрузка | Файл выгрузки ИБ | Рассчитана на корректное состояние данных. Если в базе данных есть нарушения, выгрузка может пройти, а загрузка — завершиться неудачей |

Рекомендованный способ резервного копирования:

| Вариант работы | Чем копировать | Условие |
|---|---|---|
| Файловый | Копирование файла `1Cv8.1CD` | К ИБ не должно быть ни одного подключения, включая конфигуратор |
| Клиент-серверный | Средства резервного копирования используемой СУБД | Подробности — в разделе о резервном копировании ИБ (ссылка на другой раздел документации) |

Что **не попадает** в резервную копию СУБД и должно копироваться отдельно:

- **Журнал регистрации.** Его файлы рекомендуется включать в состав резервной копии, чтобы копия была информативнее. Средствами СУБД журнал регистрации скопировать нельзя — нужно подобрать подходящий инструмент самостоятельно. При восстановлении ИБ рекомендуется восстанавливать и журнал регистрации: тогда вместе с данными доступна история действий в этой ИБ.
- **Хранилище двоичных данных** (если оно включено в ИБ). Оно обязательно должно быть зарезервировано. Средствами СУБД это сделать нельзя — используются либо соответствующие инструменты платформы, либо внешние инструменты (см. также 5.2.7.4).

Ограничение при восстановлении: пока идёт восстановление ИБ средствами СУБД, к ИБ не должно быть **никаких** подключений — ни конфигуратора, ни клиентских приложений, ни фоновых и регламентных заданий, ни средств администрирования.

Документация отсылает к связанным разделам: «Резервное копирование информационной базы», «Журнал регистрации», «Хранилище двоичных данных» (ссылки на другие разделы документации).

### 5.1.2. Преобразование информационной базы для использования в клиент-серверном варианте

Перевод ИБ из файлового варианта в клиент-серверный выполняется через выгрузку/загрузку ИБ в файл.

Обязательное условие: перед выгрузкой и перед загрузкой закрыть все сеансы работы с этой ИБ.

Порядок действий:

1. В исходной (файловой) ИБ: `Администрирование — Выгрузить информационную базу данных`.
2. Создать пустую ИБ в клиент-серверном варианте.
3. Открыть созданную ИБ в режиме Конфигуратор.
4. Выполнить `Администрирование — Загрузить информационную базу данных`.

## 5.2. Администрирование кластера серверов

### 5.2.1. Общая информация

- Утилита администрирования кластера серверов — подключаемый модуль (snap-in) Консоли управления Microsoft (MMC). Работает только там, где установлена Microsoft Management Console, то есть **только Windows**. При установке «1С:Предприятия» для клиент-серверной работы пункт запуска утилиты добавляется в меню Пуск, раздел `1С Предприятие 8`.
- Набор задач, которые решает утилита, аналогичен возможностям программного администрирования кластера серверов (ссылка на другой раздел документации).
- Данные в консоли **не обновляются автоматически**. Чтобы увидеть актуальное состояние, нужно выполнить `Действия — Обновить` (или `Обновить` в контекстном меню).

### 5.2.2. Запуск утилиты администрирования

Только Windows (нужна MMC):

- 32-разрядная утилита: `Пуск — Программы — 1С Предприятие 8 — Дополнительно — Администрирование серверов 1С Предприятия`.
- 64-разрядная утилита: `Пуск — Программы — 1С Предприятие 8 (x86-64) — Дополнительно — Администрирование серверов 1С Предприятия`.
- Альтернатива: запустить консоль командой `mmc`, затем `Консоль — Добавить или удалить оснастку…` → `Добавить` → в списке выбрать оснастку `1С:Enterprise 8.3 Servers` → `Добавить` → `Закрыть` → `ОК`.

```
mmc
```

### 5.2.3. Регистрация экземпляра рабочего сервера

- При первом запуске утилита показывает в дереве центральных серверов только рабочий сервер того компьютера, где запущена сама утилита (при условии, что агент сервера на нём запущен).
- Список центральных серверов находится в ветке `1C:Enterprise 8.3 Central Servers`.
- Центральный сервер в дереве идентифицируется именем компьютера, на котором он запущен. В списке справа для каждого сервера видны сетевой адрес и описание.

#### 5.2.3.1. Подключение утилиты к центральному серверу

Команда: `Создать — Центральный сервер 1С:Предприятия 8.3` (контекстное или главное меню). Открывается диалог свойств центрального сервера.

| Поле | Назначение | Значения / умолчание |
|---|---|---|
| Протокол | Протокол, по которому утилита подключается к агенту центрального сервера | Выбор из списка; по умолчанию `tcp`; поддерживается единственное значение — `tcp` |
| Имя | Сетевой адрес центрального сервера, на котором запущен агент сервера | — |
| IP порт | Сетевой порт агента сервера на центральном сервере | По умолчанию `1540`. Порт агента задаётся при запуске агента (ссылка на другой раздел документации) |
| Описание | Произвольное описание центрального сервера | — |

Важное примечание об адресах: при настройке кластера и центрального сервера адрес одного и того же сервера должен быть записан **везде одинаково**. Тождественность разных написаний одного сервера система не проверяет. Пример из документации: если центральный сервер в консоли кластера назван `Server`, то и в списке рабочих серверов он должен называться `Server`, а не `54.34.86.12` (даже если DNS сопоставляет `Server` с этим адресом) и не `localhost`.

#### 5.2.3.2. Просмотр и изменение свойств центрального сервера

Выбрать сервер в списке центральных серверов → `Свойства`. Открывается тот же диалог, что и при подключении (5.2.3.1).

#### 5.2.3.3. Отключение утилиты от центрального сервера

Выбрать сервер в списке центральных серверов → `Удалить`. Больше источник об этой операции ничего не сообщает; отличие от «отсоединения» видно из 5.2.3.4, где прямо сказано, что параметры подключения сохраняются.

#### 5.2.3.4. Отсоединение утилиты от центрального сервера

Выбрать сервер → `Отсоединить`. Утилита отсоединяется от центрального сервера, но параметры подключения к нему **не удаляются**.

### 5.2.4. Работа со списком администраторов центрального сервера

- Список администраторов центрального сервера нужен, чтобы часть административных действий (примеры из документации: добавление нового кластера, просмотр списка администраторов центрального сервера) была доступна только аутентифицированным пользователям.
- **По умолчанию список пуст** — в этом случае аутентификация администратора центрального сервера для перечисленных действий не запрашивается.
- В утилите список находится в ветке `Администраторы` выбранного центрального сервера. Администратор идентифицируется именем; в списке видны имя и описание.
- Требование к рабочему серверу, который **не является центральным сервером кластера** и при этом имеет непустой список администраторов центрального сервера: в этом списке должен быть
  - либо администратор с аутентификацией ОС для того пользователя, от имени которого запущен `ragent` центрального сервера кластера,
  - либо администратор, чьи имя и пароль совпадают с именем и паролем одного из администраторов центрального сервера кластера.

#### 5.2.4.1. Добавление администратора центрального сервера

Команда: ветка `Администраторы` → `Создать — Администратор`. Свойства администратора:

| Свойство | Назначение | Значения / умолчание / примечание |
|---|---|---|
| Имя | Имя администратора центрального сервера | Должно быть уникальным в пределах каждого центрального сервера |
| Описание | Произвольное описание | — |
| Аутентификация паролем | Признак аутентификации паролем | По умолчанию установлен |
| Пароль | Пароль администратора | — |
| Подтверждение пароля | Повторный ввод пароля | — |
| Аутентификация паролем только с локального компьютера | Если установлен, администратор может войти по паролю только с того компьютера, где работает `ragent` кластера серверов | Сбрасывать флажок не рекомендуется: это снижает безопасность доступа к административным функциям кластера |
| Аутентификация операционной системы | Признак аутентификации средствами ОС | — |
| Пользователь | Пользователь операционной системы | Формат: `\\имя домена\имя пользователя`, пример: `\\domainname\username`. Вводится вручную либо выбирается кнопкой «…» среди пользователей ОС, видимых с компьютера, где запущена утилита |
| Аутентификация открытым ключом | Если установлен, администратор может аутентифицироваться в консоли кластера парой «открытый ключ / закрытый ключ»; при входе предъявляется закрытый ключ своей пары | Документация рекомендует именно этот способ для повышения безопасности доступа к административным функциям кластера |
| Открытый ключ | Открытый ключ пары, удостоверяющей данного администратора (заполняется, если включена аутентификация открытым ключом) | Пару ключей можно создать любой доступной утилитой создания ключей; для ОС Windows названа `ssh-keygen.exe` |

Способы аутентификации администратора центрального сервера (допускается несколько):

| Способ | Что вводит пользователь |
|---|---|
| Открытым ключом | В диалоге аутентификации — имя пользователя и путь к закрытому ключу |
| Паролем | В диалоге аутентификации — имя пользователя и пароль |
| Средствами ОС | Ничего; диалог не показывается. Система определяет, от имени какого пользователя ОС выполняется подключение, и по нему находит соответствующего администратора центрального сервера |

Предупреждение: если у администратора не выбран **ни один** вид аутентификации, он может выполнять только те действия, которые аутентификации не требуют.

#### 5.2.4.2. Просмотр и изменение свойств администратора центрального сервера

Выбрать администратора → `Свойства`. Редактировать можно все свойства, **кроме имени**. Значения полей `Пароль` и `Подтверждение пароля` скрыты.

#### 5.2.4.3. Удаление администратора центрального сервера

Выбрать администратора → `Удалить`.

#### 5.2.4.4. Аутентификация администратора центрального сервера

- Диалог аутентификации система вызывает сама — при попытке выполнить действие, требующее аутентификации, и только если список администраторов центрального сервера не пуст.
- Кнопкой в нижней части диалога переключается режим: «имя пользователя и пароль» ↔ «пара ключей доступа».

| Поле диалога | Назначение | Когда доступно |
|---|---|---|
| Имя | Имя администратора центрального сервера | При любом способе аутентификации |
| Пароль | Пароль администратора | При аутентификации по паролю |
| Приватный ключ | Полное имя файла закрытого ключа пары ключей доступа; вводится вручную или выбирается кнопкой «…» | При аутентификации по открытому ключу |

Кнопка `ОК` запускает попытку аутентификации с указанными параметрами.

### 5.2.5. Работа со списком кластеров

- Список кластеров, зарегистрированных на центральном сервере, — ветка `Кластеры` выбранного центрального сервера.
- Кластер идентифицируется **номером сетевого порта**. В списке видны номер порта кластера и описание кластера.

#### 5.2.5.1. Добавление кластера

Команда: ветка `Кластеры` → `Создать — Кластер`. Открывается диалог свойств кластера.

Сводная таблица свойств кластера (подробности по сложным свойствам — ниже таблицы):

| Свойство | Назначение | Значения / умолчание / примечание |
|---|---|---|
| Имя кластера | Произвольное описание кластера | — |
| Компьютер | Имя центрального сервера, на котором размещается кластер | Не редактируется |
| IP Порт | Сетевой порт менеджера кластера | По умолчанию `1541`. Порты менеджеров кластеров должны быть уникальны в пределах каждого центрального сервера |
| Защищенное соединение | Уровень безопасности кластера | Выбор из списка: `выключено`, `только соединение`, `постоянно`. По умолчанию — `выключено`. Об уровнях безопасности — ссылка на другой раздел документации. При изменении на работающем кластере требуется перезапуск кластера (см. 5.2.5.2) |
| Разрешать запись событий аудита прав доступа | Управляет записью событий аудита прав доступа для всех ИБ кластера | Доступно только для лицензии КОРП |
| Расписание перезапуска | Строка с расписанием перезапуска рабочих процессов кластера | cron-формат (заимствован у утилиты `cron` ОС Linux/Unix; описание формата — ссылка на другой раздел документации). Расписание рабочего сервера имеет приоритет над расписанием кластера. Если расписание не задано ни у кластера, ни у рабочего сервера — перезапуск по расписанию не выполняется |
| Принудительно завершать проблемные процессы | Разрешает принудительное завершение рабочих процессов, которые механизм мониторинга кластера признал проблемными | На сам мониторинг флажок не влияет. Описание мониторинга — ссылка на другой раздел документации |
| Записывать дамп процесса при превышении критического объема памяти | Нужно ли формировать дамп аварийного завершения рабочего процесса, когда кластер принудительно завершает рабочий процесс | Ситуация возникает, когда при мониторинге состояния кластера нарушено значение параметра рабочего сервера `Критический объем памяти процессов`. Дамп формируется по текущим настройкам формирования дампов аварийного завершения (ссылка на другой раздел документации) |
| Проблемные процессы завершать через __ секунд | Интервал, по истечении которого проблемный рабочий процесс принудительно останавливается независимо от наличия соединений | Все соединения с этим процессом при этом завершаются аварийно. Значение можно менять во время работы кластера. `0` — принудительное завершение не выполняется. Менеджер кластера при стойком превышении предельного объёма используемой памяти перезапускается всегда и без ожидания |
| Уровень отказоустойчивости | Максимальное число рабочих серверов кластера, одновременный выход из строя которых не приводит к аварийному завершению сеансов подключённых пользователей | Подробности — ссылка на другой раздел документации |
| Режим распределения нагрузки | Критерий выбора рабочего процесса при установке нового соединения | Перечень значений в этой части не приведён (ссылка на другой раздел документации) |
| Период проверки | Период проверки системы отслеживания разрыва соединений | Миллисекунды. См. правило ниже |
| Таймаут проверки | Таймаут проверки системы отслеживания разрыва соединений | Миллисекунды. См. правило ниже |

Правило для пары `Период проверки` / `Таймаут проверки`: если в настройках кластера **хотя бы один** из двух параметров отличен от `0`, используются значения из настроек кластера. В противном случае (оба равны `0`) берутся параметры командной строки запуска кластера серверов (ссылка на другой раздел документации).

**Как выполняется перезапуск рабочего процесса по расписанию** (свойство `Расписание перезапуска`):

1. Существующий («старый») рабочий процесс выключается. В выключенном состоянии он:
   - продолжает обслуживать старые соединения с ИБ;
   - принимает новые соединения с теми ИБ, которые он уже обслуживает;
   - не принимает новые соединения с ИБ, которые он не обслуживает.
2. В кластере регистрируется и запускается «новый» рабочий процесс.
3. В новом процессе создаются контексты тех ИБ, которые обслуживает останавливаемый процесс, и в них загружаются конфигурации ИБ. Контексты создаются системными фоновыми заданиями (их особенности — ниже).
4. Когда контексты ИБ в новом процессе сформированы, старый процесс:
   - перестаёт принимать любые новые соединения;
   - «передаёт» существующие соединения новому процессу.
5. Старый процесс завершается при выполнении любого из условий (логическое ИЛИ):
   - все существующие соединения успешно переданы;
   - истекло время `Проблемные процессы завершать через`.
6. Регистрация старого рабочего процесса в кластере отменяется.

Особенности системных фоновых заданий, создающих контексты ИБ:

| Характеристика | Значение |
|---|---|
| Как видны в списке соединений | Название приложения `Системное фоновое задание`, идентификатор приложения `SystemBackgroundJob` |
| Требования назначения функциональности | При запуске не учитываются |
| Сеанс и журнал регистрации | Работает без создания сеанса; в журнале регистрации не отражается |
| Прерывание | Может быть прервано средствами администрирования кластера серверов |

Порядок при нескольких процессах и серверах:

- несколько рабочих процессов на одном рабочем сервере перезапускаются **последовательно** — сначала один (полный цикл, описанный выше), затем следующий и т. д.;
- на разных рабочих серверах кластера перезапуск идёт **параллельно**.

#### 5.2.5.2. Просмотр и изменение свойств кластера

Выбрать кластер в списке → `Свойства`. Открывается диалог свойств кластера.

Если у работающего кластера изменено свойство `Защищенное соединение`, новое значение начнёт использоваться только после **перезапуска кластера**.

#### 5.2.5.3. Вызов операции применения требований назначения функциональности

- Требования назначения функциональности (ТНФ) начинают действовать только после операции **применения**. До неё список требований, редактируемый в консоли кластера, на работу кластера не влияет.
- Применение бывает частичным и полным.

| Вид применения | Что переназначается | Риск |
|---|---|---|
| Частичное | Сервисы, поддерживающие миграцию между рабочими серверами без потери данных. Остальные сервисы переназначаются только если новые требования не позволяют им остаться на прежнем месте либо недоступны рабочие серверы, на которых они работали на момент вызова операции | Аварийное завершение клиентских приложений возможно, если принято решение переназначить все сервисы, а не только допускающие перемещение без потери данных |
| Полное | Все сервисы, без учёта их формальных характеристик | Могут аварийно завершиться **все** клиентские приложения, подключённые к этому кластеру |

Команды контекстного меню кластера:

- `Применить требования назначения функциональности (частичное)`;
- `Применить требования назначения функциональности (полное)`.

#### 5.2.5.4. Удаление кластера

Выбрать кластер в списке → `Удалить`. Удаление кластера аварийно завершает **все соединения** с ним.

### 5.2.6. Работа со списком рабочих серверов кластера

- Список рабочих серверов кластера — ветка `Рабочие серверы` выбранного кластера.
- Рабочий сервер идентифицируется сетевым именем. В списке видны имя сервера, сетевой порт агента сервера, запущенного на нём, и описание.
- При создании кластера рабочий сервер, на котором кластер создан, по умолчанию включается в его состав, и для него устанавливается флажок `Центральный сервер`.

#### 5.2.6.1. Добавление рабочего сервера в кластер

Команда: ветка `Рабочие серверы` → `Создать — Рабочий сервер`. Открывается диалог свойств рабочего сервера.

Сводная таблица свойств рабочего сервера (алгоритмы и пояснения — ниже таблицы):

| Свойство | Назначение | Значения / умолчание / примечание |
|---|---|---|
| Описание | Произвольное описание сервера кластера | — |
| Компьютер | Сетевой адрес рабочего сервера, на котором запущен агент сервера | Если указан IP-адрес в точечной нотации, наличие его в DNS (файле `hosts`) не требуется |
| IP Порт | Сетевой порт агента сервера на указанном компьютере | По умолчанию `1540` |
| Диапазоны IP портов | Диапазон сетевых портов, из которого система назначает адреса рабочим процессам, создаваемым на этом сервере | По умолчанию `1560:1591` |
| Безопасный расход памяти за один вызов | Объём памяти (в байтах), расход которого в ходе одного вызова сервера считается безопасным и не приводит к прерыванию вызова при превышении ограничения `Временно допустимый объем памяти процессов` | Только лицензия КОРП. Диапазон: от `-1` до `9 223 372 036 854 775 807`. `-1` — любой вызов сервера прерывается при превышении `Временно допустимый объем памяти процессов`. `0` — значение определяется автоматически как 10% от используемого значения `Временно допустимый объем памяти процессов` |
| Критический объем памяти процессов | Суммарный объём памяти процессов кластера (рабочих процессов и менеджеров кластера) на рабочем сервере, превышение которого может значительно снизить производительность сервера | Используется механизмом мониторинга работы кластера. Диапазон: от `-1` до `9 223 372 036 854 775 807`. `-1` — не ограничено. `0` — 95% объёма оперативной памяти рабочего сервера. По умолчанию `0` |
| Временно допустимый объем памяти процессов | Объём памяти (в байтах), занимаемой процессами кластера (рабочими процессами и менеджерами кластера) на рабочем сервере, при превышении которого сервер считается теряющим производительность и на него перестают назначаться новые соединения с ИБ | Диапазон: от `-1` до `9 223 372 036 854 775 807`. `-1` — не ограничено. `0` — 80% объёма оперативной памяти компьютера рабочего сервера. По умолчанию `0` |
| Интервал превышения допустимого объема памяти | На какое время объём памяти, занятой процессами кластера, может превышать `Временно допустимый объем памяти процессов` | По умолчанию `300` секунд. Учитывается, только если значение не равно `0` и `Временно допустимый объем памяти процессов` отличен от `-1`. Используется механизмом мониторинга работы кластера |
| Имя службы (SPN) сервера 1С:Предприятия | Непустое значение используется как имя службы (Service Principal Name, SPN) сервера «1С:Предприятия» | Нужно при аутентификации Windows для настройки ограниченного делегирования Kerberos в домене. Если не задано — аутентификация ОС при ограниченном делегировании не работает для кластера, работающего под управлением ОС Windows. Создание службы сервера — ссылка на другой раздел документации |
| Расписание перезапуска | Строка с расписанием перезапуска рабочих процессов данного рабочего сервера | cron-формат. Имеет приоритет над расписанием кластера: если заданы оба — исполняется расписание рабочего сервера; если у сервера не задано — исполняется расписание кластера (когда оно задано). Сам процесс перезапуска описан в 5.2.5.1 |
| Количество ИБ на процесс | Сколько ИБ может обслуживать (по соединениям) один рабочий процесс данного сервера | Только лицензия КОРП. `0` — ограничение не установлено. При превышении кластер создаёт на этом рабочем сервере дополнительный рабочий процесс |
| Количество соединений на процесс | Сколько соединений с ИБ может обслуживать один рабочий процесс данного сервера | `0` — ограничение не установлено. При превышении кластер создаёт на этом рабочем сервере дополнительный рабочий процесс |
| Порт главного менеджера кластера | Сетевой порт главного менеджера кластера, запущенного на данном рабочем сервере; из него формируется адрес кластера для клиентского приложения | Формат адреса: `<Свойство Компьютер>:<Порт главного менеджера кластера>`, пример: `COMP1:2541`. Игнорируется, если не установлен флажок `Центральный сервер` |
| Менеджер под каждый сервис | Выделять ли отдельный менеджер кластера под каждый тип сервиса | Установлен — для каждого типа сервиса создаётся свой менеджер кластера; сброшен — все сервисы назначаются на один менеджер кластера данного рабочего сервера. Каждый дополнительный менеджер занимает один порт из диапазона сетевых портов для динамического выбора (задаётся при запуске кластера серверов) |
| Центральный сервер | С таким рабочим сервером выполняется синхронизация реестра кластера, а его адрес может использоваться клиентским приложением для подключения к кластеру | Флажок |
| Установить запрещающее требование назначения функциональности | При создании нового рабочего сервера блокирует назначение на него каких-либо сеансов | Имеет смысл и доступно только при создании нового рабочего сервера |

**Безопасный расход памяти за один вызов — дополнительное поведение.** Если объём свободной физической памяти текущего сервера становится меньше этого значения, а в кластере есть другие серверы, на которых это не так, текущий сервер перестаёт использоваться кластером для клиентских вызовов, для назначения новых клиентских соединений и для сервисов кластера.

**Временно допустимый объем памяти процессов — два вида контроля:**

1. Контроль памяти рабочих процессов в целом — выполняется механизмом мониторинга работы кластера (ссылка на другой раздел документации).
2. Контроль памяти отдельного серверного вызова — алгоритм:
   - каждый рабочий процесс вычисляет объём памяти, занятой процессами кластера на своём рабочем сервере (в документации условно `ПамятьПроцессов`); значение обновляется один раз в две секунды;
   - в начале вызова сервера фиксируется текущее значение (`ПамятьПроцессовТекущая`) и вычисляется `ПределПамятиЗаВызов` = `Временно допустимый объем памяти процессов` − `ПамятьПроцессовТекущая`;
   - если `ПределПамятиЗаВызов` получился меньше `Безопасный расход памяти за один вызов`, то `ПределПамятиЗаВызов` принимается равным `Безопасный расход памяти за один вызов`;
   - по ходу вызова считается память, израсходованная этим вызовом (`ПамятьЗаВызов`);
   - если при очередном выделении памяти `ПамятьЗаВызов` превышает `ПределПамятиЗаВызов`, вызов прерывается исключением и завершается аварийно;
   - в технологический журнал при этом пишется событие `EXCP`, содержащее текст исключения и контекст исключения.

**Менеджер под каждый сервис — именование менеджеров:**

- дополнительный менеджер: `Дополнительный менеджер кластера (<Описание сервиса>)`, пример: `Дополнительный менеджер кластера (Сервис сеансовых данных)`;
- главный менеджер всегда называется `Главный менеджер кластера`.

Совет документации: устанавливать это свойство можно в процессе опытной эксплуатации. Типы сервисов описаны в другом разделе (ссылка на другой раздел документации).

**Установить запрещающее требование назначения функциональности — что создаётся.** Флажок нужен, когда настройки рабочего сервера по умолчанию администратора не устраивают: сервер создаётся «закрытым», донастраивается, после чего назначение сеансов разрешается частичным применением требований. При установленном флажке на новом сервере создаётся (и сразу применяется) требование со следующими параметрами:

| Параметр требования | Значение |
|---|---|
| Объект требования | `Любой объект требования` |
| Тип требования | `Не назначать` |
| Имя ИБ | не указано |
| Значение дополнительного параметра | не указано |
| Приоритет | `0` |

#### 5.2.6.2. Просмотр и изменение свойств сервера кластера

Выбрать сервер в списке серверов кластера → `Свойства`. Открывается диалог свойств рабочего сервера.

- Кроме свойств, доступных при создании, для существующего сервера показывается **служебный сетевой порт агента сервера**. Он назначается системой автоматически при запуске агента сервера и используется для взаимодействия процессов кластера.
- По тексту документации, в свойствах существующего сервера для изменения доступен **только диапазон сетевых портов**.

#### 5.2.6.3. Исключение сервера из кластера

Удаление рабочего сервера может привести к аварийному завершению клиентских соединений. Безопасная последовательность:

1. Добавить для удаляемого сервера требование назначения функциональности с **максимальным приоритетом**:

   | Параметр требования | Значение |
   |---|---|
   | Тип объекта | `Любой объект требования` |
   | Тип требования | `Не назначать` |
   | Имя ИБ | не указывать |
   | Значение дополнительного параметра | не указывать |

2. Применить новый набор требований.
3. Дождаться разрыва существующих соединений.
4. Удалить рабочий сервер командой `Удалить` (контекстное или главное меню).

Ограничение: последний рабочий сервер с установленным признаком `Центральный сервер` удалить нельзя.

#### 5.2.6.4. Требования назначения функциональности

- Где смотреть: центральный сервер → кластер → рабочий сервер → ветка `Требования назначения функциональности`.
- Создание: `Создать — Требование назначения функциональности` (контекстное меню или меню `Действие`). Состав полей требования в этой части не расписан — подробное описание ТНФ находится в другом разделе (ссылка на другой раздел документации).
- Порядок обработки: требования обрабатываются в том порядке, в каком стоят в списке требований конкретного сервера. Приоритет определяется колонкой `Номер`: чем меньше номер, тем раньше обрабатывается требование и тем выше его приоритет.
- Изменение приоритета: выделить требование → `Повысить приоритет требования` или `Понизить приоритет требования`.
- Требования начинают работать только после операции применения (см. 5.2.5.3).

#### 5.2.6.5. Настройки сервисов кластера

Доступно только для лицензии КОРП.

- Где смотреть: центральный сервер → кластер → рабочий сервер → ветка `Настройки сервисов`. Подробности о настройках сервисов кластера — ссылка на другой раздел документации.
- Создание: `Создать — Настройка сервиса` (контекстное меню или меню `Действие`).

| Поле настройки | Назначение |
|---|---|
| Имя сервиса | Сервис, для которого меняется каталог хранения данных |
| Каталог данных сервиса | Новый каталог хранения данных сервиса |
| Имя ИБ | Имя информационной базы — указывается, если настраиваемый сервис может разделяться по информационным базам |

Правила:

- После сохранения настройка к кластеру ещё **не применена**.
- Чтобы кластер начал использовать новые каталоги данных сервисов, нужно выполнить команду `Применить настройки` для того рабочего сервера, для которого настройки сервисов создавались или удалялись.
- Существующую настройку сервиса изменить нельзя — её удаляют и создают новую для того же сервиса кластера.

### 5.2.7. Работа со списком информационных баз

- Список ИБ, зарегистрированных в кластере, — ветка `Информационные базы` выбранного кластера.
- ИБ идентифицируется именем. В списке видны имя ИБ и её описание.

#### 5.2.7.1. Регистрация новой информационной базы

Два способа регистрации ИБ в кластере серверов:

| Способ | Как происходит |
|---|---|
| Из клиентского приложения | При добавлении новой ИБ в клиентском приложении регистрация в кластере выполняется системой автоматически |
| Непосредственно в кластере серверов | В утилите администрирования: ветка `Информационные базы` → `Создать — Информационная база`; открывается диалог свойств ИБ |

- Параметры ИБ в диалоге эквивалентны параметрам новой ИБ, создаваемой через окно запуска «1С:Предприятия»; их описание — в другой книге документации (ссылка на другую книгу; в этой части перечень параметров не приведён).
- Имена ИБ должны быть **уникальными в пределах одного кластера**.

Параметр `Разрешить выдачу лицензий сервером 1С:Предприятия` — управляет выдачей клиентских лицензий сервером «1С:Предприятия»:

| Значение | Поведение |
|---|---|
| `Да` | Сервер выдаёт клиентские лицензии в тех случаях, когда клиентское приложение не смогло получить клиентскую лицензию самостоятельно. Особенности получения клиентских лицензий через сервер — в другой книге документации |
| `Нет` | Сервер клиентские лицензии не выдаёт. Клиентское приложение, не получившее лицензию самостоятельно, показывает сообщение: `Не найдена лицензия. Не обнаружен ключ защиты программы или полученная программная лицензия!` |

Что делает система при регистрации новой ИБ — проверяет, есть ли на указанном сервере баз данных база с таким именем:

| Ситуация на сервере СУБД | Результат |
|---|---|
| База данных с таким именем существует | Устанавливается соединение с ней |
| Существующая база уже содержит данные ИБ «1С:Предприятия» | Устанавливается связь с уже существующей ИБ |
| Существующая база не содержит данных ИБ | В ней инициализируется новая ИБ «1С:Предприятия» |

Случай, когда базы данных с таким именем на сервере СУБД нет, в этой части не описан.

#### 5.2.7.2. Просмотр свойств информационной базы

Выбрать ИБ в списке → `Свойства`.

Редактируемые параметры подключения к СУБД: имя сервера базы данных, имя используемой базы данных, тип используемой СУБД, имя пользователя базы данных и его пароль.

Свойства блокировки и прочие свойства ИБ, доступные для редактирования:

| Свойство | Назначение | Значения / примечание |
|---|---|---|
| Блокировка начала сеансов включена | Включает блокировку начала сеансов с ИБ | Поведение при установленном флажке — см. ниже |
| Начало (дата/время начала актуальности блокировки) | Момент начала действия блокировки | Блокировка начинает действовать, когда текущее время превышает это значение |
| Конец (дата/время конца актуальности блокировки) | Момент окончания действия блокировки | Действие блокировки заканчивается, если значение отлично от нулевой даты и меньше либо равно текущему времени |
| Сообщение | Текст, включаемый в сообщение об ошибке при попытке установить соединение с заблокированной ИБ | — |
| Код разрешения | Строка, которую нужно добавить к параметру командной строки `/UC` или к параметру строки соединения `UC`, чтобы соединиться с ИБ вопреки блокировке установки соединений | — |
| Параметр блокировки | Произвольный текст | Может использоваться в конфигурациях для различных целей |

| Внешнее управление сеансами | Строка с параметрами Web-сервиса внешнего управления сеансами | Пример — ниже. Подробное описание строки и работы механизма — ссылки на другие разделы документации |
| Обязательное использование внешнего управления | Поведение при недоступности Web-сервиса внешнего управления сеансами | Установлен: при недоступности Web-сервиса возникает ошибка, подключение к ИБ невозможно. Сброшен: при недоступности Web-сервиса подключение возможно, ограничения на число одновременных сеансов не накладываются |
| Профиль безопасности | Имя профиля безопасности; при его указании прикладное решение на стороне сервера «1С:Предприятия» работает с ограничениями этого профиля | Вводится вручную или выбирается из выпадающего списка (в список попадают существующие профили, подходящие для этого поля) |

| Задержка выгрузки конфигурации рабочим процессом | Время (в секундах), через которое рабочий процесс освобождает данные ИБ после разрыва последнего соединения с этой ИБ в данном рабочем процессе | Допустимые значения: от `0` до `4 294 967`. Пояснения — ниже |

| Максимальный сдвиг запуска регламентных заданий | Максимальное опоздание момента запуска каждого регламентного задания ИБ (в секундах) относительно положенного по расписанию, с учётом `Минимальный период запуска регламентных заданий`, при отсутствии в ИБ активных сеансов пользователей | Допустимые значения: от `0` до `4 294 967`. Используется только при ненулевом `Минимальный период запуска регламентных заданий`. Пояснения — ниже |

**Блокировка начала сеансов включена — что разрешено и что запрещено:**

| Действие | Статус |
|---|---|
| Продолжение работы существующих сеансов | разрешено |
| Запуск фоновых заданий существующими сеансами | разрешено |
| Установка соединений существующими сеансами | разрешено |
| Начало новых сеансов | запрещено |
| Установка новых соединений (кроме соединений от имени существующих сеансов) | запрещено |

**Внешнее управление сеансами — пример строки описания Web-сервиса:**

```
wsdl=http://server/sm/ws/manager?wsdl;ns=http://www.sessioncontrol.org;srvc=manager;port=managerSoap;tout=10;wsver=4;
```

В примере использованы параметры `wsdl`, `ns`, `srvc`, `port`, `tout`, `wsver`; их расшифровка в этой части не приведена (ссылка на другой раздел документации).

**Задержка выгрузки конфигурации рабочим процессом — пояснения:**

- пока данные ИБ не освобождены, установка новых соединений и запуск фоновых заданий выполняются существенно быстрее;
- данные могут быть освобождены раньше срока, если завершается рабочий процесс либо запрошен монопольный доступ к ИБ или к базе данных;
- параметр целесообразен, когда мощность сервера рассчитана на одновременную работу пользователей во всех ИБ, зарегистрированных в кластере;
- эффект: снижаются накладные расходы на запуск регламентных заданий за счёт исключения лишних выгрузок/загрузок данных конфигурации.

**Минимальный период запуска регламентных заданий — пояснения:**

- снижает нагрузку на сервер в период, когда в ИБ нет интерактивных пользователей, без изменения конфигурации;
- запуск множества заданий одной ИБ группируется по времени, чтобы минимизировать накладные расходы на загрузку/выгрузку данных конфигурации.

**Максимальный сдвиг запуска регламентных заданий — пояснения:**

- в сочетании с `Минимальный период запуска регламентных заданий` позволяет исключить пиковые нагрузки на сервер: регламентные задания разных ИБ выполняются в разное время в пределах значения этого параметра;
- оба параметра целесообразны, если в кластере зарегистрировано много ИБ, в значительной части которых пользователи не работают одновременно, и мощность сервера не рассчитана на одновременную работу пользователей во всех базах.

Поведение системы при отсутствии активных сеансов описано в другом разделе (ссылка на другой раздел документации).

#### 5.2.7.3. Удаление информационной базы

Выбрать ИБ в списке → `Удалить`. Система задаёт вопрос `Удалить информационную базу?`; при положительном ответе предлагает один из трёх режимов:

| Режим | Регистрация ИБ в кластере | База данных на сервере СУБД |
|---|---|---|
| `Удалить базу данных` | Удаляется | Удаляется сама база данных |
| `Очистить базу данных` | Удаляется | Удаляются все данные из базы данных; сама база данных на сервере баз данных остаётся |
| `Оставить без изменений` | Удаляется | Никаких изменений |

Особый случай: выбран режим `Удалить базу данных`, но с этой базой данных есть соединения пользователей. Тогда регистрация ИБ в кластере всё равно удаляется, а при попытке удаления базы данных сервер баз данных возвращает сообщение об ошибке.

#### 5.2.7.4. Работа со списком хранилищ двоичных данных

В клиент-серверном варианте ИБ может быть подключена к одному или нескольким хранилищам двоичных данных. Операции, доступные администратору в консоли:

| Вид хранилища | Доступные операции |
|---|---|
| Встроенное хранилище | Резервное копирование, восстановление, очистка хранилища |
| Хранилище S3 | Очистка хранилища |

- Создание и удаление хранилищ двоичных данных в консоли управления кластером **не поддерживается**.
- Где смотреть: выбрать ИБ → ветка `Хранилища двоичных данных`.
- Открыть диалог управления: выбрать хранилище в списке → команда `Управление` (контекстное или главное меню).

Диалог управления встроенным хранилищем — три операции:

**1. Создание резервной копии**

| Элемент диалога | Назначение |
|---|---|
| Тип резервной копии | Переключатель: полная или дифференциальная |
| Имя файла полной резервной копии | Имя файла полной копии |
| Имя файла дифференциальной резервной копии | Имя файла дифференциальной копии |
| Флаг очистки хранилища после создания резервной копии | Выполнить очистку хранилища после создания копии (⚠ в источнике неясно: точная надпись флага не приведена, сказано лишь «одноимённый флаг») |
| Сохранять удаленные данные за последние Х дней | Оставить неиспользуемые данные за указанный интервал относительно текущей даты |
| Кнопка `Создать` | Запускает настроенную операцию |

Дифференциальная копия всегда выполняется относительно какой-либо полной резервной копии.

**2. Закладка `Восстановление из резервной копии`** — восстановление встроенного хранилища из ранее созданной копии.

| Элемент диалога | Назначение |
|---|---|
| Тип резервной копии | Из какой копии восстанавливать: полной или дифференциальной |
| Имя файла полной резервной копии | Имя файла полной копии |
| Имя файла дифференциальной резервной копии | Имя файла дифференциальной копии |
| Кнопка `Восстановить` | Запускает настроенную операцию |

Для восстановления из дифференциальной копии нужно указать **тот же** файл полной резервной копии, относительно которого дифференциальная копия создавалась.

**3. Закладка `Очистка хранилища`** — очистка хранилища от неиспользуемых данных без привязки к резервному копированию.

| Элемент диалога | Назначение |
|---|---|
| Очистить данные до даты | Дата и время, до которых (в направлении «из прошлого») удаляются удалённые (неиспользуемые) данные |
| Кнопка `Очистить` | Запускает операцию |

Связанные разделы документации: «Хранилище двоичных данных», «Резервное копирование встроенного хранилища» (ссылки на другие разделы документации).

## Что важно администратору Linux

1. **Оснастка MMC на Linux-сервере не запускается.** Утилита администрирования кластера из раздела 5.2 — подключаемый модуль Microsoft Management Console, то есть работает только на Windows-компьютере; к агенту центрального сервера она подключается по `tcp`, порт агента по умолчанию `1540`. По словам документации, те же задачи решаются программным администрированием кластера; утилиты командной строки в этой части главы не описаны.
2. **Свойства объектов кластера от ОС не зависят.** Перечни свойств кластера (5.2.5.1), рабочего сервера (5.2.6.1) и ИБ (5.2.7.2) — справочник смысла и значений по умолчанию независимо от того, каким средством администрирования они задаются.
3. **Порты по умолчанию:** агент сервера — `1540`, менеджер кластера — `1541`, диапазон портов рабочих процессов — `1560:1591`. Каждый дополнительный менеджер кластера (флажок `Менеджер под каждый сервис`) занимает ещё один порт из диапазона динамического выбора. Порты менеджеров кластеров уникальны в пределах центрального сервера.
4. **Адрес сервера пишите одинаково везде.** Идентичность разных написаний одного сервера (имя, IP, `localhost`) не проверяется; центральный сервер и запись в списке рабочих серверов должны называться одинаково. Если рабочий сервер указан IP-адресом в точечной нотации, запись в DNS/`hosts` для него не нужна.
5. **Резервная копия клиент-серверной ИБ — средствами СУБД,** но журнал регистрации и хранилище двоичных данных в такую копию не попадают: их резервируют отдельно (журнал — любым удобным инструментом, хранилище — инструментами платформы или внешними). Выгрузка в файл не заменяет копию СУБД: при нарушениях в данных выгрузка может пройти, а загрузка — нет.
6. **При восстановлении базы средствами СУБД не должно быть никаких подключений к ИБ:** конфигуратор, клиенты, фоновые и регламентные задания, средства администрирования.
7. **Память рабочего сервера, значения по умолчанию:** `Критический объем памяти процессов` = `0` → 95% ОЗУ; `Временно допустимый объем памяти процессов` = `0` → 80% ОЗУ; `Интервал превышения допустимого объема памяти` = `300` с; `Безопасный расход памяти за один вызов` = `0` → 10% от временно допустимого объёма (свойство только для КОРП). Значение `-1` у критического и временно допустимого объёмов снимает ограничение; у безопасного расхода `-1` означает, что при превышении временно допустимого объёма прерывается любой вызов сервера. Учитывается память рабочих процессов и менеджеров кластера на этом сервере.
8. **Прерывание серверного вызова по памяти оставляет след в технологическом журнале:** когда вызов прерван из-за контроля памяти отдельного вызова (ограничение `Временно допустимый объем памяти процессов`), в журнал пишется событие `EXCP` с текстом и контекстом исключения.
9. **Перезапуск рабочих процессов по расписанию** задаётся строкой в cron-формате на уровне кластера и/или рабочего сервера; расписание сервера приоритетнее; без расписаний перезапуска нет. Перезапуск идёт с передачей соединений: в новом процессе системные фоновые задания (`SystemBackgroundJob`, без сеанса и без записи в журнал регистрации) создают контексты ИБ, существующие соединения передаются новому процессу, старый процесс завершается после передачи либо по истечении `Проблемные процессы завершать через`. На одном сервере процессы перезапускаются по очереди, на разных серверах — параллельно.
10. **`Проблемные процессы завершать через` = `0` отключает принудительное завершение** проблемных рабочих процессов; ненулевое значение по истечении интервала рвёт все соединения процесса аварийно. Менеджер кластера при стойком превышении предельного объёма памяти перезапускается всегда и без ожидания.
11. **Требования назначения функциональности и настройки сервисов не действуют, пока их не применили.** Полное применение ТНФ может аварийно завершить все клиентские приложения кластера; частичное переносит только сервисы, допускающие миграцию без потери данных.
12. **Вывод рабочего сервера из кластера:** сначала запрещающее требование (`Любой объект требования` / `Не назначать`, максимальный приоритет), применить, дождаться разрыва соединений, затем удалять. Последний сервер с признаком `Центральный сервер` удалить нельзя. Удаление кластера аварийно рвёт все соединения.
13. **Блокировка начала сеансов ИБ:** `Блокировка начала сеансов включена` + `Начало`/`Конец` + `Сообщение`; войти вопреки блокировке можно с кодом разрешения через параметр запуска `/UC` или параметр строки соединения `UC`. Регламентные задания блокируются отдельным флажком. Существующие сеансы при блокировке продолжают работать.
14. **Удаление ИБ из кластера имеет три режима** — с удалением базы данных, с очисткой базы данных или только снятие регистрации. При активных соединениях с базой данных режим `Удалить базу данных` снимет регистрацию, а на попытку удалить саму базу сервер СУБД ответит ошибкой.
15. **Администраторы центрального сервера по умолчанию не заданы** — административные действия выполняются без аутентификации. Документация рекомендует аутентификацию открытым ключом и не рекомендует снимать флажок `Аутентификация паролем только с локального компьютера`. Только для лицензии КОРП: запись событий аудита прав доступа, `Безопасный расход памяти за один вызов`, `Количество ИБ на процесс`, настройки сервисов кластера.
