## Кратко — главные факты

1. **Ошибка СУБД приходит в 1С «обёрнутой»**: «Ошибка СУБД:» или «Конфликт блокировок при выполнении транзакции:», имя провайдера, текст SQL Server и строка `HRESULT=…, SQLSrvr: SQLSTATE=…, state=…, Severity=…, native=…, line=…` [ИТС-мет 2379, 2008; ИТС-мет 6006, 2022]. Главное — `native`, номер сообщения SQL Server: по нему ищется раздел (таблица 1.3).
2. **Причину отказа во входе (18456) клиент не видит** — номер состояния пишется только в журнал ошибок SQL Server: `EXEC sys.sp_readerrorlog 0, 1, N'Login failed';` [MS Learn]. Для 1С чаще всего: 8 — пароль, 58 — нет смешанного режима, 7 — логин отключён, 38/46 — нет базы.
3. **«Компоненты OLE DB провайдера не найдены»** — на рабочем сервере 1С нет OLE DB Driver или Native Client; проверяется при создании, загрузке ИБ и обновлении конфигурации БД [ИТС-КС разд. 1.5.4; ИТС-мет 5908, 2022]. Драйвер — на каждый рабочий сервер, клиентам не нужен.
4. **OLE DB Driver 19 по умолчанию шифрует и проверяет сертификат** («The certificate chain was issued by an authority that is not trusted»); реестром проверку не ослабить — берётся более строгое значение [MS Learn]. Драйверы 18.7.4+ и 19.3.5+ не поддерживают SQL Server 2014/2012 [MS Learn].
5. **Рабочие процессы 1С на Linux к MS SQL не подключаются в принципе** [ИТС-КС разд. 2.3] — это ограничение платформы, а не ошибка настройки.
6. **Три вида сообщений о блокировках**: «Превышено максимальное время ожидания предоставления блокировки» и «Неустранимый конфликт блокировок» — управляемые блокировки 1С [ИТС-мет 5809, 2025]; «Конфликт блокировок при выполнении транзакции:» + текст SQL Server — блокировки СУБД (`native=1222` тайм-аут, `1205` взаимоблокировка) [ИТС-мет 6006, 2022].
7. **При 1222 SQL Server отменяет только оператор**, при 1205 — сам откатывает транзакцию жертвы [MS Learn]; в 1С после любой ошибки СУБД транзакцию можно только отменить [ИТС-мет 2313, 2019]. Предел ожидания — параметр ИБ «Время ожидания блокировки данных» (и для СУБД, и для управляемых блокировок; изменение ставит монопольный режим) [ИТС-адм разд. 6.6.3].
8. **Кто кого держит**: `blocking_session_id` в `sys.dm_exec_requests` [MS Learn]; в консоли кластера — «Заблокировано СУБД» и «Соединение с СУБД» (`session_id`) [ИТС-КС разд. 5.2.11.1, 5.2.12.2]; в ТЖ — `lka`, `lkp`, `lksrc` при `<dbmslocks/>` [ИТС-адм прил. 3, разд. 3.24.5].
9. **Взаимоблокировки SQL Server пишутся без настройки**: сеанс `system_health` собирает `xml_deadlock_report` [MS Learn].
10. **«Intra-query parallelism caused your server command … to deadlock»** — взаимоблокировка потоков одного параллельного запроса; решение 1С — `max degree of parallelism` = 1 и оптимизация запроса [ИТС-мет 5834, 2015; ИТС-мет 6008, 2023].
11. **Эскалация**: не меньше 5000 блокировок одного оператора на одну ссылку на таблицу или 40 % лимита памяти блокировок (= 24 % буферного пула) [MS Learn]. 1С советует флаги 1211 и 1224 [ИТС-мет 5946, 2019]; Microsoft — 1224, так как 1211 ведёт к ошибке 1204 [MS Learn].
12. **9002** — причину называет `log_reuse_wait_desc`; у баз 1С почти всегда `LOG_BACKUP` или `ACTIVE_TRANSACTION`; если журнал ни разу не копировался, нужны две копии журнала [MS Learn].
13. **`tempdb` у 1С нагружена втройне**: временные таблицы `#tt…`, сортировки и хеши, хранилище версий Read Committed Snapshot [ИТС-мет 2374, 2008; ИТС-разр разд. 9.2.3.2; MS Learn]. Переполнение — 1105/9002, нехватка места под версии — 3959 и 3967 в журнале ошибок, 3966 и 3958 — ошибки, которые получает клиент (в журнал ошибок не пишутся); хранилище держит самая старая транзакция, даже читающая [MS Learn].
14. **Память**: 701 — общий дефицит, 8645 и `RESOURCE_SEMAPHORE` — очередь за грантами под сортировки и хеши, 1204 — память блокировок, 8623 — слишком сложный запрос [MS Learn].
15. **Реструктуризация**: на время — `max degree of parallelism` = 0, потом 1 [ИТС-мет 5945, 2018]; механизм v2 работает с MS SQL только по TCP/IP [ИТС-адм прил. 3, разд. 3.17.23] и требует Java [ИТС-КС разд. 1.3.1]; MAXDOP базы перекрывает серверный [MS Learn].
16. **Смещение дат** (0 или 2000) задаётся при создании ИБ; при регистрах накопления или бухгалтерии — 2000; исправить — только через `.dt` [ИТС-адм разд. 5.2.1.3.2; ИТС-мет 4055, 2010]. При 2000 внешние инструменты видят даты на 2000 лет позже.
17. **Запрос 1С на сервере — параметризованный оператор** через `sp_executesql`: в ТЖ — `?` и `p_0: …`, на сервере — `@P1`, `@P2`…; таблицы `_Reference85`, `_InfoRg13229`, поля `_IDRRef`, `_Fld13230RRef`, временные таблицы `#tt` с номером [ИТС-мет 5808, 2015; 5861, 2015; 5910, 2016]. Каждый запрос пакета — отдельный запрос к СУБД [ИТС-разр разд. 8.4.7.4].
18. **Первый индекс временной таблицы (`ИНДЕКСИРОВАТЬ ПО НАБОРАМ`) на MS SQL — кластерный**, остальные обычные [ИТС-разр разд. 8.4.10.4].
19. **Изоляция**: управляемый режим на SQL Server 2005+ — Read Committed Snapshot, автоматический — Repeatable Read или Serializable [ИТС-разр разд. 9.2.3.2]; ИТС относит MS SQL к «блокировочным» СУБД [ИТС-адм разд. 6.6.4].
20. **`ПОЛНОЕ СОЕДИНЕНИЕ` на MS SQL — настоящий `FULL OUTER JOIN`**: хеш-соединение его поддерживает, подсказку `LOOP` с `FULL` задать нельзя [MS Learn], на практике — хеш или слияние; ограничения стандарта 435 продиктованы PostgreSQL [std 435].
21. **Без изменения кода** администратор SQL Server 2022+ может навязать запросу подсказку (`sys.sp_query_store_set_hints`), с 2016 — закрепить план (`sp_query_store_force_plan`) [MS Learn]; для 1С это хрупко ⚠ — только временная мера.
22. **CPU**: база и запросы-лидеры по `sys.dm_exec_query_stats` → ТЖ `DBMSSQL` с отбором по таблице → стек на встроенном языке [ИТС-мет 5861, 2015]; «размазанная» нагрузка — группировка по нормализованному тексту и контексту [ИТС-мет 5910, 2016]. **Диск**: `PAGEIOLATCH_*` — данные, `WRITELOG` — журнал; ориентир — 10–20 и 1–5 мс [ИТС-мет 5904, 2019; 6008, 2023].

## 1. Как читать ошибку: от сообщения 1С до SQL Server

### 1.1. Где видна ошибка и как она выглядит

Цепочка расследования: окно ошибки у пользователя → журнал регистрации → техжурнал `rphost` (событие `EXCP` с `Exception=DataBaseException`, текст — в `Descr`, стек на встроенном языке — в `Context` [ИТС-мет 6006, 2022]; при событиях `DBMSSQL` — сами запросы со свойствами `Sql`, `Rows`, `RowsAffected`, `Trans`, `Dbpid`, при `<plansql/>` — `planSQLText` [ИТС-адм прил. 3, разд. 3.24]) → SQL Server: журнал ошибок, журнал приложений Windows (источник `MSSQLSERVER`), `system_health`, DMV [MS Learn].

Образец записи техжурнала с ошибкой блокировки СУБД (из методики ИТС, MS SQL Server; обрезано) [ИТС-мет 6006, 2022]:

```text
42:01.559001-0,EXCP,6,process=rphost,p:processName=test600,…,SessionID=2,Usr=DefUser,AppID=1CV8C,dbpid=107,
Exception=DataBaseException,Descr='Конфликт блокировок при выполнении транзакции:
Microsoft SQL Server Native Client 11.0: Lock request time out period exceeded.
HRESULT=80040E31, SQLSrvr: SQLSTATE=HYT00, state=33, Severity=10, native=1222, line=1
',Context='Форма.Вызов : Обработка.Дедлоки.Форма.Форма.Модуль.ТаймаутСУБДНаСервере …'
```

Как читать: первая строка `Descr` — вид ошибки 1С («Ошибка СУБД:» или «Конфликт блокировок при выполнении транзакции:») [ИТС-мет 2379; 6006]; далее — провайдер, реально использованный платформой (важно для 2.4); `native` — номер сообщения SQL Server, ключ поиска; `SQLSTATE=HYT00` — тайм-аут (уточнено 20.10.2026 по MS Learn, ODBC «Appendix A: ODBC error codes»: HYT00 — «Timeout expired»; в этом примере истекло ожидание блокировки, а не время выполнения команды); `HRESULT` сам по себе причину не называет [MS Learn]; `dbpid` — `session_id` на SQL Server [ИТС-адм прил. 3, разд. 3.24]; `Context` — стек, который передаётся разработчику. Язык текстов зависит от языка логина и экземпляра ⚠ — ищите по номеру `native`, а не по тексту.

### 1.2. Где смотреть на стороне SQL Server

**Журнал ошибок SQL Server** — единственное место, где видны причины отказа во входе, рост файлов, сообщения о хранилище версий, дампы [MS Learn]:

```sql
-- securityadmin или VIEW SERVER STATE (2022+: также VIEW ANY ERROR LOG);
-- 0 = текущий журнал (1 = ERRORLOG.1 и т. д.); 2-й параметр: 1 = SQL Server, 2 = SQL Server Agent; 3-й и 4-й — фильтры
EXEC sys.sp_readerrorlog 0, 1, N'Login failed';
EXEC sys.sp_readerrorlog 0, 1, N'18456';
EXEC sys.sp_readerrorlog 1, 1, N'tempdb';          -- предыдущий журнал (ERRORLOG.1)
```

Параметры `@p1`…`@p4` и их смысл — по документации `sp_readerrorlog` [MS Learn]. Журнал на диске — файл `ERRORLOG` в каталоге `…\MSSQL\LOG` экземпляра (по умолчанию `<диск>:\Program Files\Microsoft SQL Server\MSSQL.<n>\MSSQL\LOG\ERRORLOG`; предыдущие — `ERRORLOG.1`, `ERRORLOG.2`…; подтверждено 20.10.2026, MS Learn «View the SQL Server error log»; путь зависит от установки — см. `mssql/02-…`). **SQL Server на Linux** пишет журнал в `/var/opt/mssql/log/errorlog` в UTF-16; читать `sudo cat`, перекодировать — `sudo iconv -f UTF-16LE -t UTF-8 errorlog -o errorlog.utf8`; дампы — там же (`.mdmp`, `.tar.gz2`) [MS Learn].

**Связь сеанса 1С и сеанса SQL Server.** В консоли кластера у сеанса и соединения есть «Соединение с СУБД» — идентификатор процесса сервера БД (на MS SQL это `session_id`), и «Заблокировано СУБД» — кто держит блокировку, которую ждёт сеанс (у сеанса — номер сеанса 1С, у соединения — идентификатор процесса) [ИТС-КС разд. 5.2.11.1, 5.2.12.2]; в `rac` — поля `db-proc-info` и `blocked-by-dbms` (сверять с `rac help` своей версии; `../1c/03-administrirovanie-klastera-ras-rac.md`). «Соединение с СУБД» у сеанса видно, только пока соединение захвачено сеансом: идёт вызов СУБД, открыта транзакция или удерживается менеджер временных таблиц с хотя бы одной таблицей [ИТС-КС разд. 5.2.11.1]; в свойствах соединения — только если в момент открытия диалога соединение обращается к базе [ИТС-КС разд. 5.2.12.2].

С какого адреса и под каким логином 1С ходит в SQL Server, видно по сеансам [практика; колонки — MS Learn]:

```sql
SELECT s.session_id, s.login_name, s.host_name, s.program_name, s.status,
       s.open_transaction_count, s.transaction_isolation_level, s.lock_timeout,
       c.client_net_address, c.net_transport, c.encrypt_option
FROM sys.dm_exec_sessions AS s
JOIN sys.dm_exec_connections AS c ON c.session_id = s.session_id
WHERE s.is_user_process = 1 AND s.login_name = N'buh_1c'
ORDER BY s.session_id;
```

`host_name` и `client_net_address` — рабочий сервер 1С, а не компьютер пользователя: с СУБД работают процессы кластера [ИТС-КС разд. 2.1]. `transaction_isolation_level`: 1 — ReadUncommitted, 2 — ReadCommitted, 3 — RepeatableRead, 4 — Serializable, 5 — Snapshot; `lock_timeout` — в миллисекундах [MS Learn]. Какое значение `program_name` выставляет платформа, в документации 1С не сказано ⚠ — посмотрите у себя и используйте в фильтрах.

### 1.3. Номер ошибки → раздел

| `native` / сообщение | Суть | Раздел |

## 2. Подключение к SQL Server

### 2.1. «Компоненты OLE DB провайдера не найдены»

**Симптом.** При создании ИБ, первом подключении, загрузке `.dt` или обновлении конфигурации БД: «Ошибка создания информационной базы: Компоненты OLE DB провайдера не найдены» [ИТС-мет 2926, 2008; ИТС-мет 5908, 2022].

**Причина.** На рабочем сервере 1С, через который идёт обращение, нет Microsoft OLE DB Driver for SQL Server или SQL Server Native Client. При режиме совместимости выше 8.3.7 платформе нужен «Microsoft OLE DB Driver for SQL Server актуальной версии или SQL Server Native Client for SQL Server 2005 и старше», версия Native Client — не младше версии SQL Server; наличие проверяется при создании ИБ, её загрузке и обновлении конфигурации БД [ИТС-КС разд. 1.5.4].

**Решение.**

1. Установить на **каждый** рабочий сервер актуальный OLE DB Driver (x64-установщик ставит 64- и 32-битный драйвер; предварительно нужен Visual C++ Redistributable — и x64, и x86) [MS Learn]; Native Client с SQL Server 2022 не поставляется [MS Learn]. Выбор между 18 и 19 — 2.4.
2. Какой провайдер выбрала платформа — событие `DBMSSQLCONN` (первое соединение, выбор провайдера), свойства `hResultOLEDB`, `hResultNC2005`, `hResultNC2008`, `hResult2012` [ИТС-адм прил. 3, разд. 3.24]; в 8.5.1 — `hResultMSOLEDBSQL19`, `hResultMSOLEDBSQL`, `hResultNC2012` [`../its-docs/otlichiya-8.5.1-ot-8.3.27.md`, п. 16].

```xml
<!-- logcfg.xml на рабочем сервере: какой провайдер выбран [ИТС-адм прил. 3, разд. 3.24] -->
<config xmlns="http://v8.1c.ru/v8/tech-log">
  <log location="D:\1c_logs\dbconn" history="24">
    <event><eq property="name" value="DBMSSQLCONN"/></event>
    <property name="all"/>
  </log>
</config>
```

3. Проверить установленные драйверы (PowerShell, локальный администратор) [практика]:

```powershell
Get-ItemProperty HKLM:\SOFTWARE\Microsoft\Windows\CurrentVersion\Uninstall\* |
  Where-Object DisplayName -like '*OLE DB Driver*' | Select-Object DisplayName, DisplayVersion
```

**Устарело:** проверка версии `sqloledb.dll` и `ntwdblib.dll`, выдача пользователю `USER1CV8SERVER` прав на каталог `OLE DB` [ИТС-мет 2926, 2008] и совет «установить MDAC» [ИТС-мет 5908, 2022] относятся к Windows 2000/2003. Встроенный в Windows провайдер SQLOLEDB находится в режиме сопровождения и не обновляется [MS Learn].

### 2.2. Сеть и экземпляр: ошибки 26, 40/53, 10061, тайм-аут

Тексты (провайдер подставляет своё имя) [MS Learn]:

| Сообщение (фрагмент) | Что значит | Что проверить |
|---|---|---|
| `SQL Network Interfaces, error: 26 - Error Locating Server/Instance Specified` | не найден именованный экземпляр | служба SQL Server Browser и UDP 1434 до сервера; имя экземпляра |
| `Named Pipes Provider, error: 40 - Could not open a connection to SQL Server` (… `Error: 53`) | сервер не найден или недоступен (клиент дошёл до именованных каналов) | DNS, имя сервера, включён ли TCP/IP, брандмауэр |
| `TCP Provider, error: 0 - No connection could be made because the target machine actively refused it` (`Error: 10061`) | на порту никто не слушает | служба запущена? TCP/IP включён? порт экземпляра? |
| `Timeout expired` при входе | сеть или сервер перегружен | тайм-аут входа ≠ тайм-аут команды [MS Learn] |

Порядок проверки с рабочего сервера 1С (PowerShell / cmd, любой пользователь) [MS Learn; практика]:

```powershell
Resolve-DnsName sql01
Test-NetConnection sql01 -Port 1433                     # экземпляр по умолчанию
sqlcmd -S tcp:sql01,1433 -E -Q "SELECT @@SERVERNAME, @@VERSION"   # явный протокол и порт; -E — проверка подлинности Windows
```

Синтаксис `-S [protocol:]server[\instance_name][,port]`, ключи `-E`, `-Q`, `-A` (DAC) — по документации `sqlcmd` [MS Learn]. Если явный `tcp:сервер,порт` работает, а имя экземпляра — нет, виновато обнаружение экземпляра (Browser, UDP 1434) [MS Learn].

Особенности 1С:

- Имя сервера БД в свойствах ИБ — имя компьютера или `Server/instance`; для разделяемой памяти на одном компьютере — префикс `lpc:` (по тексту ИТС — когда на компьютере установлен Native Client) [ИТС-адм разд. 5.2.1.3.2]. Принимает ли платформа обратную косую черту `Server\instance` и порт через запятую — в ИТС не сказано ⚠ (при нестандартном порте надёжнее псевдоним в SQL Server Configuration Manager или запущенный Browser [практика]).
- Оптимизированная реструктуризация не работает через разделяемую память и именованные каналы [ИТС-адм прил. 3, разд. 3.17.23] — `lpc:` для баз, которые обновляются механизмом v2, не использовать.
- Протокол реального соединения — колонка `net_transport` в `sys.dm_exec_connections` (запрос в 1.2) [MS Learn].
- Брандмауэр, порты и служба Browser — `mssql/02-ustanovka-i-nastrojka-ekzemplyara.md`.

### 2.3. Отказ во входе: 18456, 18452, 4064, 916

**Сообщение клиенту** намеренно скрывает причину: «Login failed for user '…'» (`native=18456`, символическое имя `LOGON_FAILED`). Причина — номер состояния в журнале ошибок: `Error: 18456, Severity: 14, State: 8.` [MS Learn]:

| State | Значение [MS Learn] | Типично для 1С [практика] |
|---|---|---|
| 2, 5 | неверный идентификатор пользователя | опечатка в «Пользователь сервера БД»; логина нет на этом экземпляре после переноса |
| 6 | Windows-логин с SQL-аутентификацией | в свойствах ИБ `ДОМЕН\user` с паролем |
| 7 | логин отключён, пароль неверный | `sa` отключён после включения смешанного режима |
| 8 | неверный пароль | пароль сменили, а в свойствах ИБ или скриптах `ibcmd` — старый |
| 11, 12 | логин верен, доступа к серверу нет | (11) доступ через локальных администраторов без повышения прав |
| 18 | пароль надо сменить | логин с `MUST_CHANGE` — 1С сменить не умеет |
| 38, 46, 126 | нет запрошенной базы | база переименована, отключена, восстанавливается |
| 58 | только Windows-аутентификация (или не совпали SID) | экземпляр без смешанного режима |

Включить смешанный режим (sysadmin; **нужен перезапуск службы SQL Server**, а также Agent, если запущен) [MS Learn]:

```sql
EXECUTE xp_instance_regwrite N'HKEY_LOCAL_MACHINE',
    N'Software\Microsoft\MSSQLServer\MSSQLServer', N'LoginMode', REG_DWORD, 2;   -- 2 = смешанный, 1 = только Windows
```

Проверить после перезапуска: `SELECT SERVERPROPERTY('IsIntegratedSecurityOnly');` — 0 означает смешанный режим, 1 — только Windows [MS Learn].

Другие сообщения о входе [MS Learn]:

- **18452** «Login failed. The login is from an untrusted domain and cannot be used with Integrated authentication.» — Windows-логин из недоверенного домена или сервер только с Windows-аутентификацией [MS Learn]. В 1С — когда в свойствах ИБ **не** указаны пользователь и пароль: кластер входит от имени учётной записи `rphost` [ИТС-адм разд. 5.2.1.3.2], ей нужен Windows-логин на SQL Server.
- **«… 'NT AUTHORITY\ANONYMOUS LOGON'» / «Cannot generate SSPI context»** — Kerberos/SPN службы SQL Server [MS Learn]; разбор — `../1c-windows/04-domen-kerberos-klienty-terminalnyj-server.md`.
- **4064** «Cannot open user default database. Login failed.» — база по умолчанию логина недоступна или в ней нет пользователя [MS Learn]. Логинам 1С базой по умолчанию ставить `master` [ИТС-мет 2926, 2008]: `ALTER LOGIN [buh_1c] WITH DEFAULT_DATABASE = [master];`.
- **916** «The server principal "…" is not able to access the database "…" under the current security context.» — нет пользователя базы или он «осиротел» после восстановления на другом сервере [MS Learn]: `USE [buh]; ALTER USER [buh_1c] WITH LOGIN = [buh_1c];` [практика; `mssql/03-…`].
- **17809** «Could not connect because the maximum number of '…' user connections has already been reached.» — исчерпан параметр `user connections` (верхний предел экземпляра — 32 767 соединений) [MS Learn]; у 1С обычно означает утечку соединений или кем-то ограниченный параметр — проверить `EXEC sp_configure 'user connections';` [практика].

**Права логина кластера.** Логин, под которым сервер 1С обращается к SQL Server, должен быть членом `processadmin` или `sysadmin` [ИТС-КС разд. 3.2.3; ИТС-адм разд. 5.2.1.3.2]; иначе «Удалить» соединение в консоли кластера не прервёт долгий запрос к СУБД — пользователь не получит «Сеанс работы завершен администратором», запрос продолжит работу [ИТС-КС разд. 5.2.12.3; ИТС-мет 1595, 2007]. Подробно о правах — `mssql/03-…`.

**SQL Server 2014 и флаг 4199.** На SQL Server 2014 платформа требует флаг трассировки 4199; если он не включён глобально, она пытается включить его для каждого соединения от имени пользователя базы, а при нехватке прав выдаёт ошибку [ИТС-адм разд. 5.2.1.3.2]. Решение — `-T4199` в параметрах запуска службы (`mssql/02-…`) или обновление SQL Server: 2014 не поддерживается Microsoft с 09.07.2024 [MS Learn, см. `mssql/01-…`].

### 2.4. Шифрование: OLE DB Driver 19 и сертификат

**Симптом.** После установки OLE DB Driver 19 (или после включения Force Encryption на сервере) подключение отвергается с ошибкой TLS: «The certificate chain was issued by an authority that is not trusted» или несовпадение имени в сертификате [MS Learn].

**Причина** [MS Learn]:

| | Драйвер 18 и более ранние | Драйвер 19 и новее |
|---|---|---|
| `Encrypt` по умолчанию | `no` (не шифровать, если сервер не требует) | `Mandatory` (шифрование обязательно) |
| Проверка сертификата | пропускается при `Encrypt=no` | выполняется всегда, когда соединение шифруется |
| Имя провайдера | `MSOLEDBSQL` | `MSOLEDBSQL19` |
| Установка рядом | — | да, 18 и 19 ставятся параллельно |

Драйвер 19 с настройками по умолчанию не подключится к серверу, который шифрует соединение недоверенным сертификатом [MS Learn]. В строке подключения это лечится `TrustServerCertificate=yes` или `Encrypt=Optional`, но **как платформа 1С формирует строку подключения и передаёт ли эти ключи, в ИТС не описано** ⚠.

**Реестр клиента проверку не ослабит**: ключи `HKLM\SOFTWARE\Microsoft\MSSQLServer\Client\SNI19.0\GeneralFlags\Flag1` (шифрование `0`/`1`/`2` = Optional/Mandatory/Strict) и `…\Flag2` (доверие сертификату `0`/`1`), из реестра и строки подключения драйвер берёт **более безопасное**; установщик 19 до 19.4.1 мог выставить в реестре недоверие, если стоял драйвер 18 [MS Learn].

**Решение** [MS Learn; практика]: (1) сертификат доменного УЦ на SQL Server с именем, по которому обращается 1С, и доверие корневому сертификату на рабочих серверах (`mssql/02-…`); (2) для 8.3.x до появления сертификата — драйвер 18 последней версии, выбранный провайдер — по `DBMSSQLCONN` (2.1); поддержку драйвера 19 в 8.3.27 ИТС не описывает ⚠, 8.5.1 его знает [`otlichiya-8.5.1`, п. 16]; (3) проверка — `encrypt_option` в `sys.dm_exec_connections` (1.2).

**Совместимость** [MS Learn]: драйверы 18.7.4+ и 19.3.5+ не поддерживают SQL Server 2014 и 2012, 19.4.2+ — Windows 10 и Windows Server 2012/2012 R2. SQL Server 2014 ещё есть в списке 8.3.27 [ИТС-КС разд. 1.5.4], но с новыми драйверами официально не поддерживается.

### 2.5. Смешанная среда: сервер 1С на Linux

- **Симптом:** на кластере с рабочими серверами Ubuntu нельзя создать или открыть базу на MS SQL. **Причина:** рабочий процесс на Linux не может взаимодействовать с MS SQL Server [ИТС-КС разд. 2.3]; автономный сервер на Linux тоже [ИТС-адм разд. 7.2]. **Решение:** перенести базу в PostgreSQL (`ibcmd infobase replicate` — см. `../1c-windows/02-…`, раздел 12.2) или держать для неё отдельный кластер с рабочими серверами на Windows.
- MS SQL как **внешний источник данных** для сервера 1С на Linux (через ODBC; в требованиях к Linux для этого есть библиотека unixODBC [ИТС-КС разд. 1.3.3]) — другая история: это не база ИБ, а ВИД [`../1c-windows/02-…`, разд. 1.1].

Методика ИТС требует идти по шагам: (1) убедиться, что очередь именно на блокировках, а не на процессоре, диске или виртуализации; (2) исключить ожидания на управляемых блокировках; (3) разбирать блокировки СУБД; (4) анализировать и устранять — причём при снятии блокировок растёт параллельность и нагрузка на оборудование, следить за ним нужно до конца [ИТС-мет 6006, 2022].

### 3.2. Тайм-аут блокировки СУБД (1222)

**Симптом.** У пользователя «Конфликт блокировок при выполнении транзакции: … Lock request time out period exceeded.», в техжурнале `EXCP` с `native=1222` [ИТС-мет 6006, 2022]; проведение или запись «висят» до предела ожидания, затем падают.

**Механизм.**

- SQL Server прерывает **оператор**, ждавший блокировку дольше `LOCK_TIMEOUT`, и возвращает 1222; транзакцию он при этом **не откатывает** — это обязанность приложения [MS Learn]. Текущее значение — `@@LOCK_TIMEOUT` или колонка `lock_timeout` (мс) в `sys.dm_exec_sessions` [MS Learn].
- Предел ожидания в 1С задаёт параметр ИБ «Время ожидания блокировки данных (в секундах)»: максимальное время, которое текущая транзакция ждёт снятия чужой транзакционной блокировки сервера БД; тот же параметр регулирует ожидание управляемых блокировок; изменение требует прав администратора и монопольного режима, на MS SQL действует сразу [ИТС-адм разд. 6.6.3]. Умолчание параметра в прочитанных текстах не названо ⚠; каким оператором платформа передаёт его в SQL Server (вероятно, `SET LOCK_TIMEOUT`), в ИТС не описано ⚠ — проверьте колонку `lock_timeout` у сеансов 1С (запрос 1.2).
- После ошибки базы данных транзакцию 1С уже нельзя ни продолжить, ни зафиксировать — только отменить и при необходимости повторить с начала [ИТС-мет 2313, 2019]. Отсюда частое следствие в журнале регистрации — повторные ошибки той же транзакции [практика].

**Диагностика «здесь и сейчас»** (sysadmin или `VIEW SERVER STATE`; колонки — [MS Learn]).

```sql
-- 1. Кто ждёт и кого (цепочки)
SELECT r.session_id, r.blocking_session_id, r.wait_type, r.wait_time AS wait_ms, r.wait_resource,
       DB_NAME(r.database_id) AS db, r.command, r.open_transaction_count,
       SUBSTRING(t.text, r.statement_start_offset / 2 + 1,
           (CASE r.statement_end_offset WHEN -1 THEN DATALENGTH(t.text)
                 ELSE r.statement_end_offset END - r.statement_start_offset) / 2 + 1) AS current_statement
FROM sys.dm_exec_requests AS r
OUTER APPLY sys.dm_exec_sql_text(r.sql_handle) AS t
WHERE r.blocking_session_id <> 0
ORDER BY r.wait_time DESC;

-- 2. «Головы» цепочек: держат других, сами ничего не ждут (часто — sleeping с открытой транзакцией)
SELECT s.session_id, s.status, s.login_name, s.host_name, s.open_transaction_count,
       s.last_request_start_time, s.last_request_end_time, ib.event_info AS last_batch
FROM sys.dm_exec_sessions AS s
OUTER APPLY sys.dm_exec_input_buffer(s.session_id, NULL) AS ib      -- SQL Server 2014 SP2+ [MS Learn]
WHERE s.session_id IN (SELECT blocking_session_id FROM sys.dm_exec_requests WHERE blocking_session_id <> 0)
  AND s.session_id NOT IN (SELECT session_id FROM sys.dm_exec_requests WHERE blocking_session_id <> 0);
```

```sql
-- 3. Что заблокировано и кем: блокировки по таблицам базы buh (выполнять в базе ИБ)
USE [buh];
SELECT x.request_session_id, x.resource_type, x.request_mode, x.request_status, x.table_name, COUNT(*) AS locks
FROM (SELECT l.request_session_id, l.resource_type, l.request_mode, l.request_status,
             CASE WHEN l.resource_type = N'OBJECT'
                  THEN OBJECT_NAME(CAST(l.resource_associated_entity_id AS int))
                  ELSE OBJECT_NAME(p.object_id) END AS table_name
      FROM sys.dm_tran_locks AS l
      LEFT JOIN sys.partitions AS p
             ON p.hobt_id = l.resource_associated_entity_id
            AND l.resource_type IN (N'KEY', N'PAGE', N'RID', N'HOBT')
      WHERE l.resource_database_id = DB_ID()) AS x
GROUP BY x.request_session_id, x.resource_type, x.request_mode, x.request_status, x.table_name
ORDER BY locks DESC;
```

Для `KEY`, `PAGE`, `RID`, `HOBT` колонка `resource_associated_entity_id` — это `sys.partitions.hobt_id`, для `OBJECT` — идентификатор объекта [MS Learn]; отсюда соединение с `sys.partitions` и запуск в самой базе. При 1222 Microsoft советует искать держателя через `sys.dm_os_waiting_tasks` (`blocking_session_id`, `resource_description`) и `sys.dm_tran_locks` [MS Learn]. Имена `_AccumRg…`, `_Reference…` переводятся в объекты конфигурации методом `ПолучитьСтруктуруХраненияБазыДанных()` [ИТС-мет 6006].

**Связь с сеансом 1С.** В консоли кластера у ждущего сеанса «Заблокировано СУБД» — сеанс-держатель, «Соединение с СУБД» — `session_id` [ИТС-КС разд. 5.2.11.1]. С `<dbmslocks/>` платформа не чаще раза в 2 секунды запрашивает у СУБД пары «жертва — источник» (на MS SQL — запросом к `master.dbo.sysprocesses` с `blocked > 0 AND lastwaittype LIKE 'LCK_%'`) и дописывает к событиям ТЖ `lka`/`lkp`, `lkpid`/`lkaid`, `lksrc`, `lkpto`/`lkato` [ИТС-адм прил. 3, разд. 3.24.5; ИТС-мет 6006, 2022]. Готовый `logcfg.xml` (`DBMSSQL`, `SDBL` с `Func` = `BeginTransaction`/`CommitTransaction`/`RollbackTransaction`, `<plansql/>`) — `../its-metod/vzaimoblokirovki-i-oshibki-blokirovok.md`, раздел 2.4.3.

**История блокировок** (когда «висело ночью»). Отчёт о заблокированном процессе включается параметром `blocked process threshold` (секунды, от 5 до 86 400; монитор блокировок просыпается раз в 5 секунд; по умолчанию отчётов нет; действует без перезапуска) [MS Learn]:

```sql
-- sysadmin
EXEC sp_configure 'show advanced options', 1; RECONFIGURE;
EXEC sp_configure 'blocked process threshold', 10; RECONFIGURE;   -- отчёт о каждом, кто ждёт дольше 10 с

CREATE EVENT SESSION [blocked_1c] ON SERVER
ADD EVENT sqlserver.blocked_process_report
ADD TARGET package0.event_file (SET filename = N'E:\XE\blocked_1c.xel', max_file_size = 100, max_rollover_files = 5);
ALTER EVENT SESSION [blocked_1c] ON SERVER STATE = START;
-- после расследования: ALTER EVENT SESSION [blocked_1c] ON SERVER STATE = STOP;
--                      EXEC sp_configure 'blocked process threshold', 0; RECONFIGURE;
```

Событие `blocked_process_report` — из методики ИТС [ИТС-мет 6006, 2022]; параметры `event_file` (`filename` с расширением `.xel`, `max_file_size` в МБ, `max_rollover_files`) — [MS Learn]; каталог должен существовать и быть доступен службе SQL Server [практика]. Чтение — SSMS или `sys.fn_xe_file_target_read_file` [MS Learn]; загрузка в таблицу — `../its-metod/vzaimoblokirovki-i-oshibki-blokirovok.md`, раздел 2.4.6.

**Типичные причины 1222 в базах 1С и кто их снимает.**

| Причина | Признак | Кто и что делает |
|---|---|---|
| Автоматический режим: Serializable блокирует диапазоны (соседние по индексу записи), а проверка остатков с `ДЛЯ ИЗМЕНЕНИЯ` по пустой таблице регистра — всю таблицу до конца транзакции [ИТС-мет 2707, 2008] | ожидания `LCK_M_RS_*`, `LCK_M_RIn_*` (блокировки диапазонов ключей [MS Learn]) на таблицах регистров | разработчик: управляемый режим [ИТС-разр разд. 9.2.3.2; std 460]; не трогать в транзакции пустые таблицы [ИТС-мет 2707, 2008, в `../its-metod/ekspluataciya-krupnoj-sistemy-blokirovki-tranzakcii.md`, разд. 3] |
| Запрос без подходящего индекса сканирует таблицу и ставит лишние блокировки | `Index Scan` в плане запроса внутри транзакции, много блокировок у сеанса | разработчик [std 652, 658]; администратор — статистика и индексы (`mssql/05-…`) |
| Долгая транзакция | у «головы» `open_transaction_count > 0` и давний `last_request_start_time` | контекст по ТЖ; длинные обмены и закрытие месяца — дробить [практика] |
| Эскалация до таблицы | событие `lock_escalation`, блокировка `OBJECT` | 3.5 |
| Две роли с разными RLS на одно право | `ИЛИ` во всех запросах к объекту | [std 658, п. 7] |

Блокировки диапазонов (`LCK_M_R…`) в управляемом режиме появляться не должны — их наличие в базе 1С указывает на автоматический режим или явную транзакцию в автоматическом режиме [практика ⚠].

### 3.3. Режим блокировок 1С и что на самом деле ставит SQL Server

[ИТС-разр разд. 9.2.3.2]:

| Режим блокировок 1С | Уровень изоляции на SQL Server | Чтение вне транзакции | Неявная транзакция при чтении объектов с табличными частями |
|---|---|---|---|
| Автоматический | Repeatable Read или Serializable, блокировки записей | «грязное» | да |
| Управляемый, SQL Server 2000 | Read Committed | «грязное» | да |
| Управляемый, SQL Server 2005+ | **Read Committed Snapshot** | **согласованное** | да при режиме совместимости 8.2.16 и ниже, нет — с 8.2.17 |

- Режим транзакции определяется транзакцией верхнего уровня; в режиме «Автоматический и управляемый» вложенная транзакция в управляемом режиме внутри автоматической выполнится в автоматическом, а наоборот — исключение [ИТС-разр разд. 9.2.3.5]. Поэтому «конфигурация управляемая, а Serializable всё равно встречается» — нормальная картина для смешанного режима.
- Явная транзакция `НачатьТранзакцию()` без параметра выполняется в **автоматическом** режиме (умолчание параметра `РежимБлокировок`) [ИТС-разр разд. 9.2.3.3].
- В управляемом режиме `ДЛЯ ИЗМЕНЕНИЯ` в запросах смысла не имеет; данные, которые будут изменены, защищаются явной управляемой блокировкой **до** чтения [std 460].
- В автоматическом режиме SQL Server может довести дело до взаимоблокировки всего из двух запросов двух транзакций, если совпали три условия: автоматический режим, запрос с `ДЛЯ ИЗМЕНЕНИЯ` и сканирование таблицы или индекса в плане; лечится устранением любого из трёх [ИТС-мет 4051, 2025].

Проверка на сервере: `transaction_isolation_level` сеансов 1С (запрос 1.2: 2 — ReadCommitted, 3 — RepeatableRead, 4 — Serializable) и `is_read_committed_snapshot_on` базы (раздел 11.4) [MS Learn].

### 3.4. Взаимоблокировки (1205) и «Intra-query parallelism»

**Симптом 1205.** «Конфликт блокировок при выполнении транзакции: … Transaction (Process ID N) was deadlocked on lock resources with another process and has been chosen as the deadlock victim. Rerun the transaction.» [MS Learn; ИТС-мет 4052, 2010 — среди типовых ошибок методики ЦУП]. Вместо `lock` бывает `communication buffer` или `thread` [MS Learn].

**Механизм.** Монитор блокировок ищет циклы раз в 5 секунд (при частых взаимоблокировках — до 100 мс), выбирает жертвой транзакцию, которую дешевле откатить (если не задан `SET DEADLOCK_PRIORITY`), прерывает её пакет, откатывает транзакцию и возвращает 1205 [MS Learn]. Повтор транзакции обычно проходит; лечение — одинаковый порядок захвата ресурсов и короткие транзакции [MS Learn]; в терминах 1С — сразу максимальный уровень блокировки, одинаковый порядок захвата, «искусственная» управляемая блокировка, управляемый режим [ИТС-мет 4051, 2025].

**Где взять граф.** Сеанс `system_health` включён по умолчанию и собирает `xml_deadlock_report`, отдельной настройки не нужно; в SQL Server 2012+ это рекомендуемый способ вместо графа взаимоблокировок Profiler и флагов 1204/1222 [MS Learn]. Запрос Microsoft к цели `ring_buffer` (sysadmin) [MS Learn]:

```sql
SELECT xdr.value('@timestamp', 'datetime') AS deadlock_time,
       xdr.query('.') AS event_data
FROM (SELECT CAST(xt.target_data AS XML) AS target_data
      FROM sys.dm_xe_session_targets AS xt
      JOIN sys.dm_xe_sessions AS xs ON xs.address = xt.event_session_address
      WHERE xs.name = N'system_health' AND xt.target_name = N'ring_buffer') AS XML_Data
CROSS APPLY target_data.nodes('RingBufferTarget/event[@name="xml_deadlock_report"]') AS XEventData(xdr)
ORDER BY deadlock_time DESC;
```

XML сохранить в `.xdl` и открыть в SSMS — будет графическая схема; SSMS рисует её и по цели `event_file` (`ring_buffer` конечен и при остановке сеанса очищается — давние случаи ищите в `event_file`) [MS Learn]. Связать граф с кодом 1С — техжурнал `EXCP`, `EXCPCNTX`, `SDBL`, `DBMSSQL` с `<dbmslocks/>`; для SQL Server 2012+ ИТС просит прикладывать `xml_deadlock_report` [ИТС-мет 6005, 2022]. Схемы 1С — `../its-metod/vzaimoblokirovki-i-oshibki-blokirovok.md`, разд. 1.3–1.8. Флаги 1204/1222 (вывод в журнал ошибок) на нагруженных системах Microsoft не советует [MS Learn].

**«Intra-query parallelism».** Тексты [ИТС-мет 5834, 2015]:

```text
Intra-query parallelism caused your server command (process ID #XX) to deadlock. Rerun the query without intra-query parallelism by using the query hint option (maxdop 1)
Transaction (Process ID #XX) was deadlocked on thread communication buffer resources with another process and has been chosen as the deadlock victim
```

Это взаимоблокировка потоков одного параллельного запроса (обычно с неоптимальным планом). Решение 1С — `max degree of parallelism` = 1 для экземпляра (параллельность между разными запросами при этом сохраняется) или оптимизация запроса [ИТС-мет 5834, 2015; ИТС-мет 2379, 2008]. Подробнее — раздел 7.1. Параллельные запросы участвуют во взаимоблокировках и с другими процессами через ресурсы exchange-портов [MS Learn].

### 3.5. Эскалация блокировок и нехватка памяти блокировок (1204)

**Пороги SQL Server** (без оптимизированной блокировки) [MS Learn]:

- один оператор T-SQL набрал **не меньше 5000 блокировок на одну ссылку на таблицу** (не суммарно по индексам и не по разным ссылкам при самосоединении) — попытка эскалации;
- **память блокировок**: при `locks` = 0 порог — 24 % памяти Database Engine. Поддержка Microsoft раскладывает это так: память блокировок ограничена 60 % видимого буферного пула, порог эскалации — 40 % от неё, то есть 24 % буферного пула; если память блокировок дошла до 60 % (что вероятнее при отключённой эскалации), новые блокировки не выделяются — ошибка **1204** [MS Learn];
- если эскалации мешают чужие несовместимые блокировки, попытка повторяется через каждые 1250 новых блокировок; блокировки строк и ключей эскалируются сразу до таблицы, не до страниц [MS Learn].

**Чем опасна для 1С.** Эскалация превращает тысячи блокировок строк в блокировку таблицы (`X` при записи) — все остальные пользователи регистра встают в очередь; 1С поэтому рекомендует в продуктиве эскалацию запрещать флагами **1211** и **1224** [ИТС-мет 5946, 2019].

**Флаги** [MS Learn]:

| Флаг | Действие | Риск |
|---|---|---|
| 1224 | запрещает эскалацию по числу блокировок; по памяти она остаётся (в описании флага — 40 % памяти Database Engine при `locks` = 0; в руководстве по блокировкам порог по памяти — 24 %, см. выше) | минимальный — рекомендуется Microsoft вместо 1211 |
| 1211 | запрещает эскалацию всегда, даже при нехватке памяти; при обоих флагах действует 1211 | при множестве блокировок — ошибка 1204, замедление |

Включение — параметр запуска `-T1224` (постоянно) и `DBCC TRACEON (1224, -1);` (сразу, до перезапуска); проверка — `DBCC TRACESTATUS (-1);` [ИТС-мет 5946, 2019; MS Learn]. На SQL Server на Linux — `sudo /opt/mssql/bin/mssql-conf traceflag 1224 on` и перезапуск службы [MS Learn]. Подробная таблица флагов для 1С — `mssql/02-ustanovka-i-nastrojka-ekzemplyara.md`.

**Ошибка 1204** «The instance of the SQL Server Database Engine cannot obtain a LOCK resource at this time. …»: нет памяти (другие клерки, `max server memory`), менеджер блокировок упёрся в 60 %, нестандартное `locks` или **флаги 1211/1224 при запросах с огромным числом блокировок** [MS Learn]:

```sql
-- у кого больше всего блокировок
SELECT request_session_id, COUNT(*) AS num_locks
FROM sys.dm_tran_locks GROUP BY request_session_id ORDER BY COUNT(*) DESC;
-- какой клерк съел память (OBJECTSTORE_LOCK_MANAGER — менеджер блокировок)
SELECT TOP (10) pages_kb, type, name FROM sys.dm_os_memory_clerks ORDER BY pages_kb DESC;
EXEC sp_configure 'locks';          -- должно быть 0
```

1204 прерывает оператор и откатывает активную транзакцию, откат сам может блокировать других [MS Learn]. Если 1204 появилась после включения 1211 — заменить на 1224 [MS Learn].

**Наблюдение за эскалацией** — расширенное событие `lock_escalation` (Microsoft приводит сессию с целью `histogram` по `database_id`) [MS Learn]:

```sql
CREATE EVENT SESSION [lock_escalation_1c] ON SERVER
ADD EVENT sqlserver.lock_escalation (
    SET collect_database_name = 1, collect_statement = 1
    ACTION (sqlserver.database_id, sqlserver.database_name, sqlserver.sql_text))
ADD TARGET package0.histogram (SET source = N'sqlserver.database_id');
ALTER EVENT SESSION [lock_escalation_1c] ON SERVER STATE = START;
```

Поля события `escalated_lock_count` и `escalation_cause` показывают, сработал порог по числу или по памяти [MS Learn]. Если событий `lock_escalation` нет, блокировки вызваны не эскалацией [MS Learn].

**Чего не делать.** `ALTER TABLE … SET (LOCK_ESCALATION = DISABLE)` Microsoft предлагает как альтернативу флагам [MS Learn], но таблицами 1С управляет платформа: при реструктуризации настройка, скорее всего, пропадёт ⚠, а менять структуру базы средствами СУБД ИТС не разрешает (допустимые действия — [ИТС-КС разд. 5.5]). `ROWLOCK` эскалацию не предотвращает [MS Learn].

**Эскалация в самой 1С** — другое: больше 100 000 управляемых блокировок на одно пространство платформа может заменить блокировкой всего пространства [ИТС-разр разд. 9.2.3.6]; «Неудачная попытка эскалации управляемой блокировки» к SQL Server не относится [ИТС-мет 6006, 2022].

**Оптимизированная блокировка** (TID-блокировка, LAQ) почти исключает эскалацию, требует включённого ADR, а её часть LAQ работает только при RCSI [MS Learn], но есть только в **SQL Server 2025** (`ALTER DATABASE … SET OPTIMIZED_LOCKING = ON`), которого нет в списках 1С [ИТС-КС разд. 1.5.4; `otlichiya-8.5.1`] — для баз 1С не применять ⚠.

### 3.6. Страничные блокировки индексов 1С (8.3.22+)

С 8.3.22 дефрагментацию индексов 1С выполняют так: включить страничные блокировки (`ALLOW_PAGE_LOCKS = ON`), дефрагментировать, выключить обратно [ИТС-мет 5837, 2022] — индекс с `ALLOW_PAGE_LOCKS = OFF` реорганизовать нельзя, задача «Reorganize Index Task» падает [MS Learn]. Скрипт — `mssql/05-obsluzhivanie-indeksy-statistika.md`.

### 3.7. Как снять зависший сеанс

> **Внимание.** Снятие сеанса откатывает его транзакцию: пользователь теряет несохранённые изменения, откат большой транзакции может идти дольше, чем она работала, и всё это время держит блокировки. Сначала выясните, что делает сеанс (запросы 3.2), и по возможности завершите его средствами 1С.

1. **Средствами 1С** (предпочтительно): консоль кластера → сеанс → «Завершить» или соединение → «Удалить». При длительном запросе к MS SQL сервер 1С сам пытается разорвать соединение с СУБД — получится, если у логина ИБ есть `processadmin` или `sysadmin`; при успехе пользователь увидит «Сеанс работы завершен администратором» [ИТС-КС разд. 5.2.12.3]. Нельзя разорвать соединение, пока исполнение «стоит» на одной строке встроенного языка вне СУБД (долгий COM- или HTTP-вызов) [там же].
2. **Средствами SQL Server** (sysadmin или `processadmin`): `KILL 57;` где 57 — `session_id` («Соединение с СУБД»). Ход отката — `KILL 57 WITH STATUSONLY;` (сам ничего не прерывает) [MS Learn]. Список сеансов — `sys.dm_exec_sessions`, `sys.dm_exec_requests` [MS Learn].
3. Проверка. Уточнено 20.10.2026 по MS Learn (KILL, `sys.dm_exec_requests`): пока идёт откат, `KILL 57 WITH STATUSONLY;` показывает процент выполнения и оставшееся время, а `sp_who` — `KILLED/ROLLBACK` в колонке `cmd`; для колонки `command` в `sys.dm_exec_requests` это значение в документации не описано, зато `percent_complete` заполняется и для `ROLLBACK`. После отката сеанса нет, у ждавших `blocking_session_id = 0`. Право на `KILL` — `ALTER ANY CONNECTION` (входит в `sysadmin` и `processadmin`) [MS Learn].

## 4. Журнал транзакций переполнен (9002)

### 4.1. Симптом

Любые записи в ИБ падают с «Ошибка СУБД: … The transaction log for database 'buh' is full. To find out why space in the log cannot be reused, see the log_reuse_wait_desc column in sys.databases.» (`native=9002`, `LOG_IS_FULL`) [MS Learn]. Если журнал заполнился при работе базы, она остаётся в сети, но **только для чтения**; если при восстановлении — база помечается `RESOURCE PENDING` [MS Learn]. Уточнено 20.10.2026 по спискам сообщений Database Engine (MS Learn): в SQL Server 2017 и 2019 текст 9002 — «The transaction log for database '%ls' is full due to '%ls'.», в 2022 и 2025 к нему добавлено «… and the holdup lsn is %S_LSN.»; на место второго `%ls` подставляется причина (на практике — значение вида `LOG_BACKUP`, как в `log_reuse_wait_desc`). Текст без причины, приведённый выше, — из страницы ошибки MSSQLSERVER_9002.

### 4.2. Причина — `log_reuse_wait_desc`

```sql
-- sysadmin: причина и заполненность для всех баз
SELECT d.name, d.recovery_model_desc, d.log_reuse_wait, d.log_reuse_wait_desc
FROM sys.databases AS d ORDER BY d.name;
DBCC SQLPERF (LOGSPACE);                       -- размер и % заполнения журналов всех баз
USE [buh];
SELECT total_log_size_in_bytes / 1048576 AS log_mb, used_log_space_in_percent,
       log_space_in_bytes_since_last_backup / 1048576 AS since_last_log_backup_mb
FROM sys.dm_db_log_space_usage;                -- текущая база [MS Learn]
```

| `log_reuse_wait_desc` (код) | Значение [MS Learn] | Типично для 1С [практика] | Что делать |
|---|---|---|---|
| `LOG_BACKUP` (2) | нужна копия журнала | модель FULL, а копии журнала не настроены (умолчание Standard/Enterprise — FULL из `model`) | `BACKUP LOG` по расписанию; если журнал не копировали ни разу — **две** копии журнала подряд [MS Learn] |
| `ACTIVE_TRANSACTION` (4) | долгая или отложенная транзакция | многочасовой обмен, загрузка данных, закрытие месяца, «забытая» транзакция внешней обработки | найти и завершить транзакцию (4.3), затем копия журнала |
| `ACTIVE_BACKUP_OR_RESTORE` (3) | идёт резервное копирование или восстановление | долгий `BACKUP DATABASE` ночью | дождаться или отменить (`sys.dm_exec_requests`, `command LIKE 'BACKUP%'`) |
| `CHECKPOINT` (1) | не было контрольной точки | обычно кратковременно | `USE [buh]; CHECKPOINT;` |
| `AVAILABILITY_REPLICA` (9) | вторичная реплика группы доступности не применила журнал | отставшая реплика Always On | `mssql/07-…` |
| `REPLICATION` (6) | репликация/CDC не доставили изменения | в базах 1С не используется [практика] | — |

Сценарий Microsoft целиком (курсор по всем базам с рекомендациями по каждому коду) — статья «Troubleshoot a full transaction log (SQL Server Error 9002)» [MS Learn]; сокращённая версия — выше.

### 4.3. ACTIVE_TRANSACTION: найти долгую транзакцию и её сеанс 1С

```sql
-- самая старая активная транзакция базы (sysadmin)
DBCC OPENTRAN (N'buh') WITH TABLERESULTS;

-- транзакции базы с сеансами и объёмом журнала [MS Learn]
SELECT st.session_id, dt.database_transaction_begin_time,
       DATEDIFF(MINUTE, dt.database_transaction_begin_time, GETDATE()) AS minutes,
       dt.database_transaction_log_record_count, dt.database_transaction_log_bytes_used / 1048576 AS log_mb,
       s.host_name, s.login_name, s.status, ib.event_info AS last_batch
FROM sys.dm_tran_database_transactions AS dt
LEFT JOIN sys.dm_tran_session_transactions AS st ON st.transaction_id = dt.transaction_id
LEFT JOIN sys.dm_exec_sessions AS s ON s.session_id = st.session_id
OUTER APPLY sys.dm_exec_input_buffer(st.session_id, NULL) AS ib
WHERE dt.database_id = DB_ID(N'buh')
ORDER BY dt.database_transaction_begin_time;
```

Расширенный вариант с планом и состоянием транзакции (`transaction_type`, `transaction_state`) — в методичке 1С о дисковой нагрузке; там же пояснено, что `session_id` — это «Соединение с СУБД» в консоли кластера [ИТС-мет 5813, 2015]. По `session_id` найти сеанс 1С, по журналу регистрации — что он делал; завершить средствами 1С или `KILL` (с оговорками 3.7) [MS Learn; ИТС-мет 5813].

### 4.4. Освободить место, не сломав цепочку копий

> **Внимание.** Перед любыми действиями с журналом убедитесь, что есть свежая полная копия базы. Перевод в SIMPLE рвёт цепочку копий журнала: восстановление на момент времени станет невозможным до новой полной копии.

```sql
-- 1. Модель FULL, причина LOG_BACKUP: сделать копию журнала (если журнал ни разу не копировали — дважды)
BACKUP LOG [buh] TO DISK = N'E:\Backup\buh_log_now.trn' WITH CHECKSUM, COMPRESSION;

-- 2. Диск журнала забит до отказа, копию сделать некуда: временно добавить второй файл журнала на другой диск
ALTER DATABASE [buh] ADD LOG FILE (NAME = N'buh_log_tmp', FILENAME = N'X:\Temp\buh_log_tmp.ldf',
                                   SIZE = 8GB, FILEGROWTH = 1GB);
-- после копии журнала и устранения причины — удалить (файл удаляется, только если он пуст — MS Learn, ALTER DATABASE … REMOVE FILE)
ALTER DATABASE [buh] REMOVE FILE [buh_log_tmp];

-- 3. Проверить, что место освободилось
DBCC SQLPERF (LOGSPACE);
```

- Несколько файлов журнала — временная мера; журнал не класть на сжатую файловую систему [MS Learn]. Усечение и сжатие файла (`DBCC SHRINKFILE`) — разные операции; регулярно журнал не сжимают [MS Learn; `mssql/04-…`].
- Упёрлись в `MAXSIZE` или выключен рост — `ALTER DATABASE [buh] MODIFY FILE (NAME = N'buh_log', MAXSIZE = UNLIMITED, FILEGROWTH = 1GB);` (имя — из `sys.database_files`; `UNLIMITED` для файла журнала означает не больше 2 ТБ [MS Learn]); база в `RESOURCE PENDING` — после освобождения места `ALTER DATABASE [buh] SET ONLINE;` [MS Learn].
- `BACKUP LOG … WITH TRUNCATE_ONLY` [ИТС-мет 2373, 2008] удалён [MS Learn].

**Профилактика**: журнал такого размера, чтобы хватало между копиями журнала без роста [ИТС-мет 5904, 2019]; копии журнала по расписанию при FULL; мониторинг `log_reuse_wait_desc` и места на `L:`; для загрузки `.dt` — BULK_LOGGED или SIMPLE на время операции [ИТС-адм разд. 6.8] (подробно — `mssql/04-rezervnoe-kopirovanie-i-vosstanovlenie.md`).

**ADR** (ускоренное восстановление базы, SQL Server 2019+) даёт «агрессивное усечение журнала» при долгих транзакциях и мгновенный откат, а версии строк хранит в самой базе (PVS) [MS Learn]. Официальной позиции 1С по ADR в прочитанных текстах нет ⚠ — включать только после нагрузочного теста.

### 4.5. 1105 и 1101: нет места в файловой группе базы

«Could not allocate space for object '…' in database '…' because the 'PRIMARY' filegroup is full …» (1105, `NO_MORE_SPACE_IN_FG`) или «Could not allocate a new page for database '…' because the '…' filegroup is full …» (1101) — закончилось место в файлах данных: диск заполнен, файл упёрся в `MAXSIZE` или выключен автоприрост; даже `UNLIMITED` ограничен 16 ТБ на файл [MS Learn]. Решения — включить рост, добавить файл в файловую группу, освободить диск [MS Learn]. Пользовательские файловые группы платформа сама не использует [ИТС-мет 5946, 2019], но управлять пользовательскими табличными пространствами (файловыми группами) из 1С можно — только с лицензией КОРП и при праве `ALTER` на базу у пользователя подключения к СУБД [ИТС-КС разд. 5.5.5.2.1]. `ALTER INDEX REORGANIZE` может вернуть 1105, если индекс лежит в нескольких файлах и один полон, — тогда `REBUILD` [MS Learn].

```sql
USE [buh];
SELECT name, type_desc, physical_name, size / 128 AS size_mb,
       CASE max_size WHEN -1 THEN N'UNLIMITED' ELSE CAST(max_size / 128 AS nvarchar(20)) END AS max_mb,
       growth, is_percent_growth
FROM sys.database_files;
ALTER DATABASE [buh] MODIFY FILE (NAME = N'buh', MAXSIZE = UNLIMITED, FILEGROWTH = 512MB);   -- имя файла — из запроса
```

## 5. `tempdb`: рост, 1105/9002, хранилище версий

### 5.1. Что 1С кладёт в `tempdb`

- **Временные таблицы платформы** (`ПОМЕСТИТЬ`, менеджер временных таблиц) — локальные временные таблицы `#tt…` [ИТС-мет 5910, 2016; ИТС-мет 2374, 2008]. Удаляются автоматически при отключении создавшего сеанса [MS Learn].
- **Внутренние объекты**: рабочие таблицы спулов, сортировок, хеш-соединений и хеш-агрегатов, промежуточные результаты `GROUP BY`, `ORDER BY`, `UNION` [MS Learn; ИТС-мет 2374, 2008].
- **Хранилище версий**: при управляемых блокировках на SQL Server 2005+ уровень Read Committed Snapshot [ИТС-разр разд. 9.2.3.2] — значит, все изменения в базе ИБ версионируются в `tempdb` (если для базы включён ADR — в самой базе, PVS) [MS Learn].
- Операции в `tempdb` протоколируются минимально; база пересоздаётся при каждом запуске службы [MS Learn].

### 5.2. Симптомы и сообщения

| Сообщение | Что значит | Источник |
|---|---|---|
| 1105 / 1101 для `tempdb` | кончилось место в файлах данных `tempdb` | [MS Learn] |
| 9002 для `tempdb` | заполнен журнал `tempdb` (долгая транзакция с временными объектами) | [MS Learn] |
| 3959 в журнале ошибок | `tempdb` полна: изменения продолжают выполняться, но **версии не создаются** | [MS Learn] |
| 3967 в журнале ошибок | при сжатии хранилища версий самая долгая транзакция, ещё не создававшая версий, помечена жертвой | [MS Learn] |
| 3966 | жертва попыталась прочитать версию — транзакция откатывается | [MS Learn] |
| 3958 | транзакция обратилась к версии, которая не была создана из-за переполнения | [MS Learn] |

Для 1С это выглядит как ошибки СУБД у читающих пользователей (отчёты, списки) при заполненной `tempdb` [практика].

### 5.3. Диагностика

```sql
-- 1. Чем занята tempdb (МБ) [MS Learn]
SELECT SUM(unallocated_extent_page_count)      * 8.0 / 1024 AS free_mb,
       SUM(version_store_reserved_page_count)  * 8.0 / 1024 AS version_store_mb,
       SUM(internal_object_reserved_page_count)* 8.0 / 1024 AS internal_objects_mb,
       SUM(user_object_reserved_page_count)    * 8.0 / 1024 AS user_objects_mb
FROM tempdb.sys.dm_db_file_space_usage;

-- 2. Хранилище версий по базам (SQL Server 2016 SP2+) [MS Learn]
SELECT DB_NAME(database_id) AS db, reserved_space_kb / 1024 AS version_store_mb
FROM sys.dm_tran_version_store_space_usage ORDER BY reserved_space_kb DESC;

-- 3. Самые старые транзакции с версионированием — они не дают чистить хранилище [MS Learn]
SELECT TOP (10) a.session_id, a.transaction_id, a.is_snapshot, a.elapsed_time_seconds,
       s.host_name, s.login_name, s.status
FROM sys.dm_tran_active_snapshot_database_transactions AS a
LEFT JOIN sys.dm_exec_sessions AS s ON s.session_id = a.session_id
ORDER BY a.elapsed_time_seconds DESC;

-- 4. Кто сколько выделил в tempdb (временные таблицы и внутренние объекты по сеансам) [MS Learn]
SELECT session_id,
       (user_objects_alloc_page_count - user_objects_dealloc_page_count) * 8 / 1024 AS user_objects_mb,
       (internal_objects_alloc_page_count - internal_objects_dealloc_page_count) * 8 / 1024 AS internal_mb
FROM sys.dm_db_session_space_usage
WHERE database_id = 2
ORDER BY (user_objects_alloc_page_count - user_objects_dealloc_page_count)
       + (internal_objects_alloc_page_count - internal_objects_dealloc_page_count) DESC;
-- псевдоним столбца в ORDER BY допустим только сам по себе, не внутри выражения [MS Learn — ORDER BY clause]
```

Точнее (с выполняющимися задачами из `sys.dm_db_task_space_usage`) — запрос из статьи «tempdb database», раздел «Monitor tempdb use» [MS Learn]; те же представления использует методичка 1С [ИТС-мет 5813, 2015]. Счётчики `SQLServer:Transactions`: `Free Space in tempdb (KB)`, `Version Store Size (KB)`, `Version Generation rate (KB/s)`, `Version Cleanup rate (KB/s)`, `Longest Transaction Running Time`; оценка хранилища — 2 × (объём версий, создаваемых за минуту) × (длительность самой долгой транзакции в минутах) [MS Learn]. В чек-листе 1С порог оповещения по журналу `tempdb` — более 70 ГБ [ИТС-мет 5899, 2016].

### 5.4. Причины роста и решения

| Причина | Признак | Решение |
|---|---|---|
| Долгая транзакция (в том числе только читающая в версионированной базе) | большое `version_store_mb`, старая запись в запросе 3 | найти сеанс 1С по `session_id`, завершить операцию; дробить долгие обработки [MS Learn; практика] |
| Сетевой обрыв: SQL Server не знает, что клиент пропал, транзакция «жива» | сеанс `sleeping` с `open_transaction_count > 0` | завершить сеанс; ИТС-2008 называет 2 часа по умолчанию для TCP keep-alive Windows ⚠ (значение для современных Windows не сверялось) [ИТС-мет 2374, 2008] |
| Огромные временные таблицы 1С | большое `user_objects_mb` у одного сеанса | разработчик: не помещать сотни тысяч строк, обрабатывать порциями [std 777] |
| Сортировки и хеши с нехваткой памяти (сброс в `tempdb`) | большое `internal_mb`, ожидания `RESOURCE_SEMAPHORE` | раздел 6.2; индексы, условия [std 652, 658] |
| Конкуренция за страницы распределения и метаданные | ожидания `PAGELATCH_UP`/`PAGELATCH_EX` на ресурсах `2:…` | число файлов `tempdb` (`mssql/02-…`); метаданные в памяти (2019+) |

**Конкуренция за метаданные `tempdb`** (сеансы 1С массово создают и удаляют `#tt…`): с SQL Server 2019 есть «Memory-optimized TempDB metadata» — `ALTER SERVER CONFIGURATION SET MEMORY_OPTIMIZED TEMPDB_METADATA = ON;` + перезапуск, проверка `SELECT SERVERPROPERTY('IsTempdbMetadataMemoryOptimized');`; включать только при подтверждённой конкуренции (диагностический запрос по `PAGELATCH_*` — в статье «tempdb database») [MS Learn]; для 1С не проверялось ⚠. С 2016 временные таблицы кешируются, с 2019 страницы PFS обновляются под разделяемой защёлкой [MS Learn].

### 5.5. Уменьшить `tempdb`

> **Внимание.** Сжатие `tempdb` под нагрузкой может упереться в блокировки и взаимоблокировки; надёжный способ — в окно обслуживания.

Способы [MS Learn]: перезапуск службы (`tempdb` пересоздаётся с последним явно заданным размером); `ALTER DATABASE tempdb MODIFY FILE (NAME = 'tempdev', SIZE = …)` в режиме минимальной конфигурации `sqlservr -c -f -mSQLCMD` (только исходные `tempdev` и `templog`); без перезапуска — `DBCC SHRINKFILE (N'tempdev', 8192)` (целевой размер в МБ) или `DBCC SHRINKDATABASE (tempdb, 10)` (10 — процент свободного места, который останется в файлах; меньше последнего явно заданного размера не сожмёт). Большой размер `tempdb` на производительность не влияет [MS Learn] — сжимать, только если нужен диск; важнее причина (5.4). Совет ИТС уменьшать `tempdb` перезапуском или `DBCC SHRINKDATABASE` [ИТС-мет 2374, 2008] верен, умолчание прироста «10 %» оттуда устарело [MS Learn; `../1c-windows/02-…`, разд. 6.4].

## 6. Память и ресурсы: 701, 802, 8645, 8651, 8623, рабочие потоки

### 6.1. Какая ошибка о чём

| Номер | Текст (фрагмент) [MS Learn] | Суть |
|---|---|---|
| 701 | «There's insufficient system memory to run this query.» | SQL Server не смог выделить память запросу; виноватый запрос обычно не тот, что упал |
| 802 | «There is insufficient memory available in the buffer pool.» | исчерпан буферный пул |
| 8645 | «A timeout occurred while waiting for memory resources to execute the query in resource pool '…' (…). Rerun the query.» | запрос не дождался гранта памяти под сортировку или хеш (максимум ожидания — 24 часа, текущий тайм-аут — `timeout_sec` в `sys.dm_exec_query_memory_grants`) |
| 8651 | «Could not perform the requested operation because the minimum query memory is not available. …» | не хватает минимальной памяти запроса (`min memory per query`) |
| 1204 | «… cannot obtain a LOCK resource at this time …» | память блокировок, раздел 3.5 |
| 8623 | «The query processor ran out of internal resources and could not produce a query plan. …» | запрос слишком сложен для оптимизатора (состояние 1 — тайм-аут оптимизации, 2 — память) |

### 6.2. Гранты памяти: 8645 и ожидание `RESOURCE_SEMAPHORE`

**Механизм.** Память выполнения нужна сортировкам, хеш-соединениям и хеш-агрегатам, массовой вставке, построению индексов; если её нет, запрос ждёт с типом `RESOURCE_SEMAPHORE`, а после тайм-аута получает 8645 [MS Learn]. Для запросов 1С типичные потребители — большие `УПОРЯДОЧИТЬ ПО`/`ИТОГИ`, `СГРУППИРОВАТЬ ПО`, `ПОЛНОЕ СОЕДИНЕНИЕ` (обычно хеш или слияние, раздел 11.5), соединения больших виртуальных таблиц без условий в параметрах [std 657, 733; практика].

```sql
-- Кому выделено и кто ждёт память (granted_query_memory — в 8-КБ страницах) [MS Learn]
SELECT r.session_id, r.wait_type, r.wait_time, r.granted_query_memory, t.text
FROM sys.dm_exec_requests AS r
CROSS APPLY sys.dm_exec_sql_text(r.sql_handle) AS t
WHERE r.granted_query_memory > 0 OR r.wait_type = N'RESOURCE_SEMAPHORE';

-- Очередь за грантами: grant_time IS NULL — ещё не выделено [MS Learn]
SELECT session_id, requested_memory_kb, granted_memory_kb, required_memory_kb, ideal_memory_kb,
       query_cost, dop, wait_time_ms, timeout_sec
FROM sys.dm_exec_query_memory_grants
WHERE grant_time IS NULL
ORDER BY wait_time_ms DESC;

-- Семафоры памяти: сколько ждут и сколько было тайм-аутов
SELECT resource_semaphore_id, target_memory_kb, available_memory_kb, granted_memory_kb,
       grantee_count, waiter_count, timeout_error_count
FROM sys.dm_exec_query_resource_semaphores;
```

Счётчики `SQLServer:Memory Manager\Memory Grants Pending` и `Memory Grants Outstanding` — ждущие и выданные гранты [MS Learn].

**Что делать** [MS Learn; практика]:

1. Найти запросы с крупными грантами и связать их с кодом 1С (техжурнал `DBMSSQL` по имени таблицы, раздел 9.3).
2. Обновить статистику — оценка гранта строится по ней (регламент — `mssql/05-…`; 1С рекомендует ежедневно `FULLSCAN` [ИТС-мет 5837, 2022]).
3. Индексы и условия по стандартам [std 652, 658], вынос подзапросов во временные таблицы [std 655] — меньше строк, другой алгоритм соединения, меньше грант.
4. Обратная связь по грантам памяти (memory grant feedback): в SQL Server 2017 — только для пакетного режима (уровень совместимости 140), для построчного режима (в нём, как правило, выполняются запросы 1С к обычным таблицам [практика]) — с 2019 (уровень 150), в 2022 добавлены сохранение в Query Store и «процентильный» грант [MS Learn] — проверьте уровень совместимости базы (`compatibility_level` в `sys.databases`).
5. Временно ограничить грант конкретного запроса без изменения кода — подсказка `MAX_GRANT_PERCENT` через Query Store (SQL Server 2022+, раздел 11.6) [MS Learn].
6. Проверить `max server memory`, `min memory per query` на необычные значения; при совмещении с сервером 1С — что 1С оставлено достаточно памяти [MS Learn; ИТС-мет 5904, 2019].

### 6.3. 701 и 802: нехватка памяти процесса

Microsoft делит причины на три группы [MS Learn]: **внешнее давление** (другие процессы на машине — у 1С это рабочие процессы `rphost` на том же сервере), **внутреннее давление не от ядра SQL Server** (DLL в процессе: связанные серверы, SQLCLR, `sp_OA*`, антивирус, внедряющий библиотеки), **внутреннее давление ядра** (клерки памяти: кеш планов `CACHESTORE_SQLCP`, гранты `MEMORYCLERK_SQLQERESERVATIONS`, блокировки `OBJECTSTORE_LOCK_MANAGER`).

```sql
-- Кто занял память внутри SQL Server [MS Learn]
SELECT TOP (15) pages_kb / 1024 AS mb, type, name
FROM sys.dm_os_memory_clerks ORDER BY pages_kb DESC;

-- Состояние памяти ОС и процесса [MS Learn]
SELECT total_physical_memory_kb / 1024 AS total_mb, available_physical_memory_kb / 1024 AS available_mb,
       system_memory_state_desc
FROM sys.dm_os_sys_memory;
SELECT physical_memory_in_use_kb / 1024 AS in_use_mb, locked_page_allocations_kb / 1024 AS locked_mb,
       memory_utilization_percentage, process_physical_memory_low, process_virtual_memory_low
FROM sys.dm_os_process_memory;

EXEC sp_configure 'max server memory (MB)';   -- (show advanced options = 1)
```

Большая разница между `Process(sqlservr)\Private Bytes` и `SQL Server:Memory Manager\Total Server Memory (KB)` (без LPIM) указывает на память DLL внутри процесса; подробный разбор — `DBCC MEMORYSTATUS` [MS Learn].

**Для 1С**: при сервере 1С на той же машине верхний порог памяти SQL Server уменьшают на долю 1С и Lock Pages in Memory **не** выдают [ИТС-мет 5904, 2019]; `max server memory` задавать всегда, особенно при LPIM; на ВМ проверить, что память не переподписана [MS Learn]. Временное облегчение — `DBCC FREESYSTEMCACHE ('ALL');`, `DBCC FREESESSIONCACHE;`, `DBCC FREEPROCCACHE;` (теряются кеши, растут компиляции) [MS Learn]; мягче — очистить кеш планов одной базы `ALTER DATABASE SCOPED CONFIGURATION CLEAR PROCEDURE_CACHE;` (2016+).

**SQL Server на Linux.** Предел физической памяти процесса задаёт `memory.memorylimitmb` (умолчание — 80 % физической памяти), `max server memory` работает внутри него: `sudo /opt/mssql/bin/mssql-conf set memory.memorylimitmb 12288` и перезапуск службы [MS Learn]. Сервер 1С с такой ВМ не совмещается (рабочие процессы Linux с MS SQL не работают, 2.5), так что делить память приходится только с ОС и агентами.

### 6.4. 8623: слишком сложный запрос

Состояние 1 — оптимизатор не уложился по времени, 2 — по памяти; ожидается «для чрезвычайно сложных запросов или запросов к очень большому числу таблиц» [MS Learn]. В 1С такие запросы получаются из «через точку» от полей составного типа (соединение со всеми таблицами типов — в примере стандарта 56 левых соединений) и ограничений доступа на уровне записей, которые добавляют соединения и подзапросы `EXISTS` [std 654, 657]; отчёт с полем составного типа «через точку» и RLS — пример ИТС того, как запрос «может оказаться очень длинным, содержать большое количество соединений» [ИТС-мет 5945, 2018].

Что делать: разработчику — `ВЫРАЗИТЬ` для составных полей, временные таблицы вместо вложенных запросов, не больше 5–7 таблиц в запросе [std 654, 655, 729]; Microsoft советует разбить запрос на части через временную таблицу (вынос в подзапрос или CTE не помогает — оптимизатор склеит их обратно) или подсказку `OPTION (FORCE ORDER)` [MS Learn]. Администратору — передать запрос из ТЖ (`Sql`, `Context`) разработчику; временно — подсказка `FORCE ORDER` через Query Store (2022+) ⚠ (на запросах 1С не проверялось).

### 6.5. Рабочие потоки и соединения: `THREADPOOL`, 17884, 17809

- Ожидание `THREADPOOL` — задача (запрос, вход или выход) ждёт свободный рабочий поток: чаще всего потому, что потоки заняты долго выполняющимися пакетами, реже — неверный `max worker threads` [MS Learn]. В базах 1С типичная причина — длинная цепочка блокировок, на которой «повисли» сотни запросов [практика]: сначала раздел 3.2.
- 17884 «New queries assigned to process on Node … haven't been picked up by a worker thread in the last … seconds …» — та же ситуация в тяжёлой форме [MS Learn].
- Когда обычные соединения не проходят, подключаться через выделенное административное соединение (DAC): `sqlcmd -S sql01 -E -A` или в SSMS `admin:sql01`; для подключения по сети нужен `remote admin connections` = 1 [ИТС-мет 6008, 2023; ИТС-мет 5904, 2019; MS Learn]. Настройка — `mssql/02-…`.
- 17809 — исчерпан `user connections` (2.3).

## 7. Параллелизм и долгая реструктуризация

### 7.1. `max degree of parallelism`: позиция 1С и что изменилось в версиях

- **1С**: в продуктиве `max degree of parallelism` = 1 [ИТС-мет 5904, 2019; 6008, 2023; 5945, 2018]: один длинный запрос с плохим планом (поле составного типа «через точку» и RLS) за счёт параллелизма съедает процессоры у остальных; время запроса «гуляет»; ожидания `CXPACKET` и ввода-вывода; редкие внутренние взаимоблокировки (3.4) [ИТС-мет 5945, 2018]. Больше 1 — для OLAP с малым числом соединений [ИТС-мет 6008, 2023].
- **Microsoft**: по умолчанию 0, рекомендации по ядрам NUMA-узла (не больше 8) — `mssql/02-…` [MS Learn]; для 1С сознательно отступаем.
- **MAXDOP базы** (2016+): `USE [buh]; ALTER DATABASE SCOPED CONFIGURATION SET MAXDOP = 1;` — если не 0, **перекрывает** серверный [MS Learn]; помнить при реструктуризации (7.2).

**Ожидания параллелизма по версиям** [MS Learn]: до 2016 SP2 / 2017 CU3 `CXPACKET` включает всё; с 2016 SP2 / 2017 CU3 потребитель вынесен в `CXCONSUMER` (это нормально); с 2022 синхронизация вынесена в `CXSYNC_PORT`/`CXSYNC_CONSUMER`, а `CXPACKET` — только ожидание производителей. При избыточных `CXPACKET` Microsoft советует сначала настраивать запрос, затем `cost threshold for parallelism` или степень параллелизма [MS Learn]. Доля в ожиданиях — по методичке [ИТС-мет 5945, 2018]:

```sql
WITH waits AS (SELECT wait_type, wait_time_ms, waiting_tasks_count FROM sys.dm_os_wait_stats)
SELECT w.wait_type, w.waiting_tasks_count, w.wait_time_ms,
       100.0 * w.wait_time_ms / t.total AS pct
FROM waits AS w CROSS JOIN (SELECT SUM(wait_time_ms) AS total FROM waits) AS t
WHERE w.wait_type IN (N'CXPACKET', N'CXCONSUMER', N'CXSYNC_PORT', N'CXSYNC_CONSUMER');
```

Статистика ожиданий накапливается с запуска службы; сброс — `DBCC SQLPERF ('sys.dm_os_wait_stats', CLEAR);` [ИТС-мет 6008, 2023; MS Learn]. Полный разбор ожиданий и «безопасных» типов — `mssql/06-monitoring-i-diagnostika.md`.

```sql
-- Установить MAXDOP = 1 для экземпляра (sysadmin; действует сразу, без перезапуска) [ИТС-мет 5945, 2018]
EXEC sp_configure 'show advanced options', 1; RECONFIGURE;
EXEC sp_configure 'max degree of parallelism', 1; RECONFIGURE;
-- проверка
SELECT name, value, value_in_use FROM sys.configurations WHERE name = N'max degree of parallelism';
```

### 7.2. Долгая реструктуризация (обновление конфигурации БД)

**Позиция 1С** [ИТС-мет 5945, 2018]: операции реструктуризации (добавление колонок, перенос данных `INSERT … SELECT`/`UPDATE`, пересоздание индексов, пересчёт итогов) — простые по синтаксису и огромные по объёму, они хорошо параллелятся. На время реструктуризации рекомендуется `max degree of parallelism` = 0, после — вернуть исходное значение; изменение действует сразу. В тестах ИТС ускорение при 0 против 1: перенос данных регистра бухгалтерии БГУ (таблицы больше 170 ГБ) — 65 %; обновление ERP 2.1→2.2 (база больше 200 ГБ) — 18 % на переносе данных и 54 % на пересчёте итогов. Во время работы следить за ожиданиями и дисками.

```sql
-- Перед реструктуризацией (sysadmin)
EXEC sp_configure 'max degree of parallelism', 0; RECONFIGURE;
-- Если для базы задан свой MAXDOP, он перекрывает серверный [MS Learn]:
SELECT name, value FROM [buh].sys.database_scoped_configurations WHERE name = N'MAXDOP';
-- После реструктуризации
EXEC sp_configure 'max degree of parallelism', 1; RECONFIGURE;
```

Представление `sys.database_scoped_configurations` (колонки `name`, `value`) — [MS Learn].

**Механизм реструктуризации.**

- Оптимизированный механизм (v2, с 8.3.11) переносит максимум работы на уровень СУБД [ИТС-мет 5945, 2018]; включается параметром `UpdateDBCfg` = `v2` (умолчание `v1`) и работает с MS SQL **только по TCP/IP**: при подключении через разделяемую память или именованные каналы он не поддерживается [ИТС-адм прил. 3, разд. 3.17.23]. Для него на серверах кластера нужна Java 1.8+ той же разрядности, что и кластер [ИТС-КС разд. 1.3.1].
- Пересчёт итогов при реструктуризации делают системные фоновые задания; их число — параметр ИБ «Количество заданий пересчета итогов», по умолчанию 4 [ИТС-адм разд. 6.6.3].
- Техжурнал для разбора: для v1 — `EXCP`, `EXCPCNTX`, `DBMSSQL` со всех серверов кластера; для v2 — события с `EventType` = `Workflow`, `Analysis`, `Restructuring` и системные события компоненты `dmf` [ИТС-мет 6005, 2022; `../its-metod/sbor-dannyh-dlya-rassledovaniya-problem.md`, разд. 1.10 и шаблон Р2].

**Сопутствующие проблемы** [практика]: журнал растёт в разы (перенос данных в модели FULL — заранее увеличить журнал, на время BULK_LOGGED, см. `mssql/04-…`); растёт `tempdb` (сортировки при построении индексов, раздел 5); реструктуризация «стоит» — её блокирует сеанс или фоновое задание (3.2) ⚠; ошибка длины ключа индекса — 8.3. Уточнено 20.10.2026 по MS Learn (`sys.dm_exec_requests`): `percent_complete` заполняется только для перечисленных в документации команд (`ALTER INDEX REORGANIZE`, `BACKUP`/`RESTORE DATABASE`, `DBCC CHECKDB`, `DBCC SHRINKFILE`/`SHRINKDATABASE`, `ROLLBACK`, `RECOVERY` и др.), а `estimated_completion_time` — «только для внутреннего использования»; для операторов реструктуризации (`INSERT … SELECT`, `UPDATE`, `CREATE INDEX`) хода выполнения там нет — судить по ТЖ и ожиданиям.

## 8. Смещение дат, сортировка, ограничения размера

### 8.1. Смещение дат 2000

**Зачем.** В 1С даты от 01.01.0001 до 31.12.9999 (в базу пишутся до 31.12.3999), «нулевая» дата — 01.01.0001 00:00:00, время без даты — в пределах 01.01.0001; тип `datetime` SQL Server хранит только с 01.01.1753 по 31.12.9999 [ИТС-мет 4055, 2010; MS Learn]. Параметр ИБ «Смещение дат» (0 или 2000) прибавляет это число лет при записи и вычитает при чтении [ИТС-адм разд. 5.2.1.3.2].

| Смещение | Поведение [ИТС-мет 4055, 2010] |
|---|---|
| 0 | 01.01.0001 00:00:00–23:59:59 переводятся в 01.01.1753 и обратно; даты с 02.01.1753 по 31.12.3999 пишутся как есть; **запись дат с 02.01.0001 по 01.01.1753 даёт ошибку** |
| 2000 | к любой дате прибавляется 2000 лет; можно записать любую дату 1С; немного медленнее; внешние инструменты видят все даты сдвинутыми |

- Значение задаётся только при создании ИБ и потом не меняется; при регистрах накопления или бухгалтерии нужно 2000; если создали с 0 — выгрузить ИБ в `.dt`, создать базу заново со смещением 2000 и загрузить [ИТС-адм разд. 5.2.1.3.2; ИТС-мет 4055]. В диалоге 8.2 по умолчанию предлагалось 2000 [ИТС-мет 4055]; умолчания `CREATEINFOBASE` (`SQLYOffs`) и `ibcmd --date-offset` различаются — указывать явно (`../1c-windows/02-…`, разд. 5.2).
- Проверка — таблица `_YearOffset` с единственным полем `Offset`, существует только на MS SQL [`../its-metod/razmeshchenie-dannyh-tablicy-i-polya.md`]:

```sql
SELECT Offset FROM [buh].dbo._YearOffset;     -- 2000 или 0
```

- **Симптом смещения 0:** ошибка СУБД при записи документа или регистра с «пустой» или очень старой датой (например, дата рождения до 1753 года, неправильно заполненная дата) [ИТС-мет 4055]. Точный текст сообщения SQL Server ⚠ (зависит от того, как платформа передаёт параметр).
- **Симптом смещения 2000 у внешних потребителей:** отчёты BI, ETL, внешние запросы прямо к таблицам видят 4026 год вместо 2026 [ИТС-мет 4055]. Читать данные 1С прямыми запросами к таблицам вообще не стоит (структура меняется при реструктуризации) [практика]; если приходится — вычитать: `DATEADD(year, -2000, T1._Date_Time)`.

### 8.2. Сортировка (collation)

- **Экземпляр** получает сортировку по умолчанию из языка ОС при установке: русская Windows — `Cyrillic_General_CI_AS`, узбекская кириллица — `Cyrillic_General_CI_AS`, **узбекская латиница — `Uzbek_Latin_90_CI_AS`** [MS Learn]. Уточнено 20.10.2026 по той же таблице MS Learn: английский (США) — `SQL_Latin1_General_CP1_CI_AS`, другие английские локали (например, Великобритания) — `Latin1_General_CI_AS`; если сортировка базы 1С на таком экземпляре другая, она будет отличаться и от сортировки `tempdb` (см. следующий пункт).
- **`tempdb` всегда использует сортировку экземпляра**; временные таблицы лежат в `tempdb`, и сравнение строк базы со строками временной таблицы может дать ошибку конфликта сортировок, если сортировки разные [MS Learn] — это ошибка 468 «Cannot resolve the collation conflict between "…" and "…" in the … operation.» (уточнено 20.10.2026 по списку сообщений Database Engine SQL Server 2022, MS Learn). Платформа 1С массово использует временные таблицы (5.1), поэтому сортировку экземпляра лучше сразу выбирать совпадающей с сортировкой баз 1С [практика]; указывает ли платформа `COLLATE` при создании `#tt…`, в ИТС не сказано ⚠.
- Какую сортировку платформа назначает базе для разных значений «Язык (страна)», ИТС прямо не пишет ⚠. Известно одно: при стране «Казахстан» казахский порядок сортировки в базе MS SQL не используется — будет `Cyrillic_General_CI_AS`, как для России [ИТС-разр прил. 8, разд. 8.4] (в тексте ИТС опечатка `Cyrillic_Generic_CI_AS`).
- Ограничение на смену «Язык (страна)» существующей ИБ ИТС называет только для PostgreSQL (лишь на язык с той же сортировкой) и IBM Db2 (не поддерживается) [ИТС-адм разд. 6.5]; для MS SQL ограничений не названо ⚠ (как платформа при этом меняет сортировку колонок, не описано — делать на копии).

```sql
SELECT SERVERPROPERTY('Collation') AS instance_collation,
       DATABASEPROPERTYEX(N'buh', 'Collation') AS db_collation;
SELECT name, collation_name FROM sys.databases;
```

**Сменить сортировку экземпляра** — разрушительная операция: выгрузить данные, удалить пользовательские базы, перестроить системные базы (`Setup /QUIET /ACTION=REBUILDDATABASE /INSTANCENAME=… /SQLSYSADMINACCOUNTS=… /SQLCOLLATION=…`), создать базы заново [MS Learn]. Для 1С проще: новый экземпляр с нужной сортировкой и перенос баз копиями или `.dt` [практика]. `ALTER DATABASE … COLLATE` меняет сортировку только для новых объектов, существующие колонки не трогает [MS Learn]. На Linux сортировку экземпляра меняет `sudo /opt/mssql/bin/mssql-conf set-collation` при остановленной службе [MS Learn].

**Сравнение строк**: язык запросов 1С не учитывает концевые пробелы — «bb» и «bb » в запросе равны, во встроенном языке — нет [ИТС-разр прил. 8, разд. 8.1].

### 8.3. Ограничения размера записи и ключа

| Предел | ИТС (прил. 8) | Microsoft | Что видно |
|---|---|---|---|
| Запись таблицы | не больше 8060 байт [разд. 8.4] | 8060 байт; колонки переменной длины могут уходить за пределы строки (row-overflow) [MS Learn] | ошибка при записи широкой строки ⚠ |
| Ключ индекса | не больше 900 байт; ошибка возникает **не при обновлении конфигурации, а при вставке** значения, дающего длинный ключ [разд. 8.4] | 900 байт для кластерного, 1700 — для некластерного; в SQL Server 2014 и старше — 900 для всех [MS Learn] | ошибка при записи объекта с длинной строкой в индексированном реквизите |

## 9. Высокая загрузка процессора на сервере СУБД

### 9.1. Убедиться, что грузит именно SQL Server

- `Process(sqlservr)\% User Time` устойчиво выше 90 % (сумма по ядрам) — нагрузку создаёт SQL Server; если высок `% Privileged Time` — антивирус, драйверы, ОС [MS Learn].
- Диспетчер задач может вводить в заблуждение: SQL Server сам планирует потоки (SQLOS) — правильнее смотреть ожидания [ИТС-мет 6008, 2023]. `SOS_SCHEDULER_YIELD` в лидерах — задачи стоят в очереди к процессору, чаще всего из-за сканирований индексов и таблиц [MS Learn].
- Доля процессора, занятая запросами прямо сейчас (5-секундный замер по `sys.dm_exec_requests.cpu_time` и `sys.dm_os_schedulers`) — запрос в статье Microsoft «Troubleshoot high-CPU-usage issues» [MS Learn].

### 9.2. Найти базу и запросы-лидеры

```sql
-- 1. Процессор по базам за время жизни кеша планов [ИТС-мет 5861, 2015; 5910, 2016]
WITH db_cpu AS (
    SELECT CONVERT(int, pa.value) AS database_id, SUM(qs.total_worker_time) AS cpu_us
    FROM sys.dm_exec_query_stats AS qs
    CROSS APPLY sys.dm_exec_plan_attributes(qs.plan_handle) AS pa
    WHERE pa.attribute = N'dbid'
    GROUP BY CONVERT(int, pa.value))
SELECT DB_NAME(database_id) AS db, cpu_us / 1000 AS cpu_ms,
       CAST(cpu_us * 100.0 / SUM(cpu_us) OVER () AS decimal(5, 2)) AS cpu_pct
FROM db_cpu
WHERE database_id > 4 AND database_id <> 32767
ORDER BY cpu_us DESC OPTION (RECOMPILE);

-- 2. Лидеры по суммарному процессору за последний час [по мотивам ИТС-мет 5861, 2015]
SELECT TOP (20)
       qs.total_worker_time / 1000 AS cpu_ms, qs.execution_count,
       qs.total_worker_time / qs.execution_count / 1000 AS avg_cpu_ms,
       qs.total_logical_reads / qs.execution_count AS avg_reads,
       DB_NAME(CONVERT(int, pa.value)) AS db,
       SUBSTRING(st.text, qs.statement_start_offset / 2 + 1,
           (CASE qs.statement_end_offset WHEN -1 THEN DATALENGTH(st.text)
                 ELSE qs.statement_end_offset END - qs.statement_start_offset) / 2 + 1) AS statement_text,
       qp.query_plan
FROM sys.dm_exec_query_stats AS qs
CROSS APPLY sys.dm_exec_sql_text(qs.sql_handle) AS st
CROSS APPLY sys.dm_exec_query_plan(qs.plan_handle) AS qp
CROSS APPLY sys.dm_exec_plan_attributes(qs.plan_handle) AS pa
WHERE pa.attribute = N'dbid'
  AND qs.last_execution_time > DATEADD(HOUR, -1, GETDATE())
ORDER BY qs.total_worker_time DESC;
```

`total_worker_time` — в микросекундах (точность — до миллисекунд) [MS Learn]. Уточнено 20.10.2026 по MS Learn (`sys.dm_exec_sql_text`, `sys.dm_exec_plan_attributes`): `dbid` из `sys.dm_exec_sql_text` заполняется только для статического SQL хранимых процедур, для нерегламентированных и подготовленных операторов (а запросы 1С идут через `sp_executesql`) он `NULL`; база такого оператора — атрибут `dbid` плана (`plan_handle`), поэтому оба запроса берут её из `sys.dm_exec_plan_attributes`. Методичка считает доли `percent_worker_time`/`percent_elapsed_time`: нагрузка не должна быть «размазана» [ИТС-мет 5861, 2015]. История — Query Store (`mssql/06-…`).

### 9.3. Связать запрос с кодом 1С

Техжурнал на рабочем сервере с отбором по имени таблицы из найденного запроса и со сбором планов — стек на встроенном языке будет в свойстве `Context` события [ИТС-мет 5861, 2015; ИТС-мет 5813, 2015]:

```xml
<?xml version="1.0" encoding="UTF-8"?>
<config xmlns="http://v8.1c.ru/v8/tech-log">
  <log location="D:\1c_logs\sql_cpu" history="2">
    <event>
      <eq property="Name" value="DBMSSQL"/>
      <like property="Sql" value="%_Reference5774%"/>
    </event>
    <property name="all"/>
  </log>
  <plansql/>
</config>
```

- В примерах методичек путь `С:\Sql_Reads` набран с **кириллической «С»** — журнал не пишется [ИТС-мет 5861; 5813]; набирайте путь вручную. `<plansql/>` замедляет запросы — только на время расследования [ИТС-адм прил. 3, разд. 3.24.2.10].
- `planSQLText` для MS SQL — упрощённый: поля `Rows, Executes, EstimateRows, EstimateIO, EstimateCPU, AvgRowSize, TotalSubtreeCost, EstimateExecutions, StmtText` через запятую [ИТС-адм прил. 3, разд. 3.24.2.10.3].
- Если нагрузку дают несколько сеансов одним запросом — по `session_id` найти их в консоли, записать номер и время начала, завершить, по журналу регистрации понять, что они делали [ИТС-мет 5861, 2015].

### 9.4. «Размазанная» нагрузка

Если ни один запрос не выделяется, причина — большие пакетные запросы или динамически собираемые тексты: на уровне СУБД один запрос 1С распадается на множество мелких [ИТС-мет 5910, 2016]. Методика ИТС: синхронно собрать серверную трассировку (события `RPC:Completed` и `SQL:BatchCompleted`, отбор по базе) и техжурнал `DBMSSQL` с отбором по базе; нормализовать тексты (убрать имена временных таблиц `#tt` + цифры, параметры `@P` + цифры, префикс `execsp_executesqlN'`, пробелы, кавычки), посчитать MD5 и сгруппировать нагрузку трассировки по первой и последней строке контекста из ТЖ [ИТС-мет 5910, 2016]. Трассировку — серверную (`sp_trace_create`), не SQL Server Profiler: Profiler сильно нагружает сервер и при высокой нагрузке теряет события [ИТС-мет 5910, 2016].

Сегодня [MS Learn]: SQL Trace и Profiler объявлены устаревшими, вместо них — расширенные события (`sqlserver.rpc_completed`, `sqlserver.sql_batch_completed`; подтверждено 20.10.2026 по статье поддержки Microsoft «Query is slower in database application than in SSMS», где эти события добавляются в сессию) с загрузкой из `.xel` через `sys.fn_xe_file_target_read_file` (пример загрузки в таблицу с полями `sql_text`, `duration`, `cpu_time`, `physical_reads`, `writes` — `../its-metod/vzaimoblokirovki-i-oshibki-blokirovok.md`, раздел 2.4.6) или Query Store с группировкой по `query_hash` [MS Learn]. Группировку по контексту 1С даёт только техжурнал: см. также `../its-metod/tehzhurnal-bash-i-potreblenie-resursov.md` (топ запросов по нормализованному тексту `bash`/`perl`, замена `tt\d+`).

### 9.5. Типичные причины и действия

| Причина | Признак | Действие |
|---|---|---|
| Сканирования (нет индекса, несаргабельное условие) | `Index Scan` у лидера, `SOS_SCHEDULER_YIELD` | разработчик [std 652, 658]; `sys.dm_db_missing_index_details` — лишь подсказка, индексы 1С задаются в конфигураторе [MS Learn; практика] |
| Устаревшая статистика | нелепые оценки строк в плане | статистика ежедневно `FULLSCAN` + очистка кеша планов [ИТС-мет 5837, 2022] |
| Параллелизм | `CXPACKET`, отчёт ест все ядра | MAXDOP 1 (7.1) |
| Чувствительность к параметрам | запрос то быстрый, то медленный | 11.2 |
| RLS и составные поля «через точку» | огромный текст, десятки соединений | [std 654, 657, 658 п. 7] |
| Однотипные запросы в цикле | лидер по `execution_count` | разработчик [std 436, см. `../postgresql/10-…`] |
| Трассировка, схема питания, ВМ | Profiler, не «Высокая производительность», переподписка CPU | выключить лишнее, «Высокая производительность», настроить ВМ [ИТС-мет 5904; MS Learn] |

## 10. Высокая нагрузка на диски сервера СУБД

### 10.1. Ориентиры

- Время отклика: диск с файлами данных — 10–20 мс, диск журнала — 1–5 мс [ИТС-мет 5904, 2019; ИТС-мет 6008, 2023].
- В статье 1С о дисковой нагрузке высокая нагрузка определяется как устойчивые (не пиковые) `Avg. Disk sec/Read` или `Avg. Disk sec/Write` **больше 2000 мс** [ИТС-мет 5813, 2015] — по смыслу и по сравнению с ориентирами выше это, вероятно, опечатка ⚠; ориентируйтесь на 10–20 и 1–5 мс.
- Убедиться через «Монитор ресурсов», что диск нагружает именно SQL Server, а не другие процессы [ИТС-мет 5813, 2015].

### 10.2. Ожидания и файлы

| Ожидание | Смысл | Источник |
|---|---|---|
| `PAGEIOLATCH_SH`/`_EX` долгие | медленное чтение страниц данных (`.mdf`) с диска | [ИТС-мет 6008; MS Learn] |
| `WRITELOG` | медленный сброс журнала (`.ldf`) при фиксации транзакций | [ИТС-мет 6008; MS Learn] |
| `LOGBUFFER` | следствие `WRITELOG`: буфер журнала полон, сервер занят сбросом | [ИТС-мет 6008] |
| `IO_COMPLETION` | медленный диск при создании базы, записи трассировки, сортировке | [ИТС-мет 6008] |
| `ASYNC_IO_COMPLETION` большое | частое расширение файлов журнала | [ИТС-мет 6008] |

```sql
-- Задержки по файлам с момента запуска (мс на операцию) [колонки — MS Learn]
SELECT DB_NAME(vfs.database_id) AS db, mf.type_desc, mf.physical_name,
       vfs.num_of_reads, vfs.io_stall_read_ms / NULLIF(vfs.num_of_reads, 0) AS avg_read_ms,
       vfs.num_of_writes, vfs.io_stall_write_ms / NULLIF(vfs.num_of_writes, 0) AS avg_write_ms
FROM sys.dm_io_virtual_file_stats(NULL, NULL) AS vfs
JOIN sys.master_files AS mf ON mf.database_id = vfs.database_id AND mf.file_id = vfs.file_id
ORDER BY vfs.io_stall_read_ms + vfs.io_stall_write_ms DESC;
```

### 10.3. Найти базу и запросы

По аналогии с процессором — по `total_physical_reads` и `total_logical_reads` в `sys.dm_exec_query_stats` за последний час и по базам через `sys.dm_exec_plan_attributes` [ИТС-мет 5813, 2015]; запросы 9.2 с заменой `total_worker_time` на `total_physical_reads`. Там же в методичке — использование буферного кеша по базам через `sys.dm_os_buffer_descriptors` и свободное место в `tempdb` [ИТС-мет 5813]. Запрос «использование кешей» из той же статьи обращается к колонке `single_pages_kb` в `sys.dm_os_memory_clerks` — её нет с SQL Server 2012, используйте `pages_kb` [MS Learn; `../1c-windows/02-…`].

```sql
-- Сколько буферного пула занимает каждая база [ИТС-мет 5813, 2015]
SELECT DB_NAME(database_id) AS db, COUNT(*) * 8 / 1024 AS buffer_mb
FROM sys.dm_os_buffer_descriptors GROUP BY database_id ORDER BY buffer_mb DESC;
```

### 10.4. Причины

- Сканирования больших таблиц (индексы, условия, виртуальные таблицы с условием в `ГДЕ`) [std 652, 657, 658].
- Мало памяти — буферный пул вытесняется, растут физические чтения (6.3).
- Автоприрост файлов без мгновенной инициализации: пока новое место заполняется нулями, транзакции не могут изменять данные; для журнала мгновенная инициализация не работает [ИТС-мет 6008, 2023] (уточнение Microsoft: с SQL Server 2022 рост журнала до 64 МБ тоже мгновенный [MS Learn]).
- Журнал и данные на одном массиве, сжатие файлов, резервное копирование файловыми системами копирования поверх «живых» файлов — 1С велит проверить отсутствие сжатия файлов данных и журналов и исключить их из систем автоматического копирования [ИТС-мет 5904, 2019].
- Порядок действий 1С: базы и запросы-лидеры → код по ТЖ → сеансы по `session_id` → долгие транзакции → исправить запрос → убедиться, что нагрузка упала [ИТС-мет 5813, 2015].

## 11. Запросы 1С в T-SQL

### 11.1. Путь запроса: от текста 1С до оператора SQL Server

1. Запрос языка 1С выполняет рабочий процесс кластера: он переводит текст в SQL для СУБД (в техжурнале это видно парой событий: `SDBL` — запрос на внутреннем языке платформы, `DBMSSQL` — оператор SQL Server) [ИТС-адм прил. 3, разд. 3.24].
2. **Каждый запрос пакета исполняется на СУБД отдельным запросом**; запросы пакета связаны временными таблицами и выполняются последовательно [ИТС-разр разд. 8.4.7.4].
3. Оператор **параметризован**: в свойстве `Sql` события `DBMSSQL` вместо значений стоят `?`, а значения перечислены строками `p_0: …`; в плане SQL Server те же параметры называются `@P1`, `@P2`… Пример ИТС: `SELECT T1._Version FROM _Reference85 T1 WHERE T1._IDRRef = ?` с `p_0: 0xB8DC002590380BA011E1E1FAC99ECB37` и планом `Clustered Index Seek … SEEK:([T1].[_IDRRef]=[@P1])` [ИТС-мет 5808, 2015]. Значение ссылки — 16 байт (32 шестнадцатеричные цифры) [там же].
4. На сервер оператор приходит **вызовом `sp_executesql`**: методика ИТС при нормализации текстов трассировки вырезает префикс `execsp_executesqlN'` и параметры `@P` + цифры, а скрипт разбора ТЖ — префикс `{call sp_executesql(N'` в свойстве `Sql` [ИТС-мет 5910, 2016]. В трассировке это событие `RPC:Completed` (класс 10) [ИТС-мет 5910, 2016]. В `sys.dm_exec_sql_text` такой текст начинается с объявления параметров вида `(@P1 varbinary(16),…)SELECT …` [практика ⚠].
5. **Имена**: таблицы `_Reference85`, `_Document…`, `_InfoRg13229`, `_AccumRg…`, поля `_IDRRef`, `_Version`, `_Fld13230RRef`, служебная `_YearOffset` [ИТС-мет 5808; 5910; `../its-metod/razmeshchenie-dannyh-tablicy-i-polya.md`]; `ВЫБРАТЬ ПЕРВЫЕ` превращается в `SELECT TOP` (фильтр `%SELECT TOP%Reference5774%` в методичке) [ИТС-мет 5861, 2015]. Соответствие имён объектам конфигурации — метод `ПолучитьСтруктуруХраненияБазыДанных()` [ИТС-мет 6006, 2022].
6. **Что добавляется к тексту**, которого нет в запросе 1С: соединения для каждого обращения «через точку» (для составного типа — со всеми таблицами типов) [std 654]; условия и подзапросы ограничений доступа на уровне записей (RLS) [std 654, 657, 658]; вложенный запрос виртуальной таблицы [std 733].
7. **Типы**: даты — `datetime` (отсюда смещение дат) [ИТС-адм разд. 5.2.1.3.2]; ссылки — 16-байтовые двоичные значения [ИТС-мет 5808]. Точные типы колонок (`binary(16)`, `nvarchar`, `numeric`) в документации 1С не перечислены ⚠ — смотреть `sys.columns` своей базы.

Как получить оператор целиком: техжурнал `DBMSSQL` с `<property name="all"/>` (и `<plansql/>` на время расследования) [ИТС-адм прил. 3, разд. 3.24.2.10]; готовые `logcfg.xml` — `../1c/07-…`, раздел 7, и `../its-metod/vzaimoblokirovki-i-oshibki-blokirovok.md`, раздел 2.4.3. Повторить оператор вручную в SSMS можно, обернув его в `EXEC sp_executesql N'…', N'@P1 varbinary(16)', @P1 = 0x…` [MS Learn — синтаксис `sp_executesql`]; типы параметров — из начала текста в кеше планов ⚠.

### 11.2. Кеш планов, параметры и «то быстро, то медленно»

Текст в `sp_executesql` между выполнениями не меняется, поэтому оптимизатор обычно повторно использует план первой компиляции [MS Learn]. Обратная сторона — **чувствительность плана к параметрам**: план, построенный под значение с малым числом строк (маленькая организация), получает значение с миллионами строк, и наоборот [MS Learn]. Признаки: один отчёт у одних пользователей быстрый, у других медленный; после обновления статистики или очистки кеша «само проходит» и возвращается [практика]; у одного `query_id` в Query Store несколько планов с разным `avg_duration` [MS Learn].

| Средство [MS Learn] | Версия | Замечание для 1С |
|---|---|---|
| PSP — несколько вариантов плана для одного запроса | 2022, уровень совместимости базы 160; отключение — `ALTER DATABASE SCOPED CONFIGURATION SET PARAMETER_SENSITIVE_PLAN_OPTIMIZATION = OFF` | без изменения кода; на запросах 1С не проверялось ⚠ |
| `PARAMETER_SNIFFING = OFF` для базы / флаг 4136 для экземпляра | 2016+ / все | грубо — все запросы «под среднее»; без теста не включать ⚠ |
| `RECOMPILE`, `OPTIMIZE FOR UNKNOWN` для одного запроса через Query Store | 2022+ | 11.6 |
| `OPTIMIZED_SP_EXECUTESQL` (сериализует компиляцию одинаковых пакетов `sp_executesql` — против «штормов компиляции», а не против чувствительности к параметрам) | 2025 | SQL Server 2025 нет в списках 1С |

- Регламент 1С после обновления статистики очищает кеш планов (`DBCC FREEPROCCACHE`), чтобы не взять старый план [ИТС-мет 5837, 2022]; на 2016+ — только своей базы: `ALTER DATABASE SCOPED CONFIGURATION CLEAR PROCEDURE_CACHE;` [MS Learn]. Каждая очистка — всплеск компиляций [практика].
- Имена `#tt` с номером меняются от выполнения к выполнению, поэтому одинаковые по смыслу запросы дают разные тексты; ИТС при группировке заменяет `#tt` + цифры на постоянное имя [ИТС-мет 5910, 2016]. В кеше планов и Query Store это много записей с одной логикой ⚠ — группировать по `query_hash` [MS Learn].
- Исправления оптимизатора с уровня 130 попадают только в последний уровень совместимости, исправления после выпуска — флагом 4199 или `QUERY_OPTIMIZER_HOTFIXES` (2016+); новая база получает уровень по умолчанию для версии сервера, если у `model` не ниже [MS Learn]. После переноса базы на новую версию SQL Server проверить `compatibility_level` и менять его с тестом ключевых операций [практика].

### 11.3. Временные таблицы (`ПОМЕСТИТЬ`, `ИНДЕКСИРОВАТЬ ПО`)

- `ПОМЕСТИТЬ` создаёт локальную временную таблицу SQL Server `#tt…` в `tempdb` [ИТС-мет 5910, 2016; ИТС-мет 2374, 2008]. Временная таблица 1С живёт, пока её не уничтожат `УНИЧТОЖИТЬ`, пока существует объект `Запрос` (без менеджера временных таблиц) или менеджер временных таблиц [ИТС-разр разд. 8.4.10.1]; на стороне SQL Server локальные временные таблицы удаляются при отключении сеанса [MS Learn].
- Пока сеанс 1С удерживает менеджер временных таблиц хотя бы с одной таблицей, соединение с СУБД захвачено этим сеансом — в консоли кластера видно «Соединение с СУБД» [ИТС-КС разд. 5.2.11.1]. Долгоживущий менеджер временных таблиц в сеансе = удержанное соединение и место в `tempdb` [практика].
- **Индексы**: `ИНДЕКСИРОВАТЬ ПО` или `ИНДЕКСИРОВАТЬ ПО НАБОРАМ`; индексы создаются только в запросе с `ПОМЕСТИТЬ`; **первый индекс на MS SQL кластерный**, остальные — обычные; уникальным (`УНИКАЛЬНО`) может быть только один индекс; индексы предназначены для производительности, а не для контроля уникальности — поведение СУБД здесь различается [ИТС-разр разд. 8.4.10.4]. Порядок записей во временной таблице не гарантирован [ИТС-разр разд. 8.4.10.3].
- Кластерный индекс означает, что строки при вставке упорядочиваются по ключу: в плане `INSERT` появляется сортировка, нужен грант памяти и, при нехватке, сброс в `tempdb` [практика ⚠]. Поэтому первым в `НАБОРАМ` разумно ставить набор полей основного соединения [практика].
- Правила стандарта [std 777]: не помещать сотни тысяч записей (замедление записи и исчерпание места на диске — то есть `tempdb`), выбирать только нужные строки и поля, не создавать и удалять временные таблицы в цикле, не копировать таблицу ради переименования; индексировать, если большая временная таблица участвует в соединении или в `В (…)` (поля условия `ПО` или поля, сопоставляемые в `В`); таблицы меньше 1000 записей не индексировать.
- Тип колонок временной таблицы фиксируется при создании; добавление значений другой длины или разрядности даёт ошибку несоответствия типов — расширять тип через `ВЫБОР`/`ВЫРАЗИТЬ` [ИТС-разр разд. 8.4.10.2].

### 11.4. Read Committed Snapshot в управляемом режиме

**Что говорит 1С.** Управляемый режим на SQL Server 2005+ работает на уровне Read Committed Snapshot; чтение вне транзакции согласованное [ИТС-разр разд. 9.2.3.2].

**Что это на SQL Server** [MS Learn]:

- Read Committed Snapshot — это `READ COMMITTED` при включённом параметре базы `READ_COMMITTED_SNAPSHOT`: каждый оператор видит снимок данных на момент своего начала, чтение не ставит разделяемых блокировок; изменения при этом блокируют как обычно.
- При `ON` **все** изменения в базе порождают версии строк, даже если никто их не читает; версии хранятся в `tempdb` (при включённом ADR — в самой базе, PVS); к строке добавляется до 14 байт служебной информации — таблицы могут вырасти до 14 % при строке около 100 байт.
- Включить или выключить параметр можно, только когда в базе нет других соединений, кроме выполняющего `ALTER DATABASE` (однопользовательский режим не обязателен); в `master`, `tempdb`, `msdb` нельзя; значение в `model` наследуют новые базы.

```sql
SELECT name, is_read_committed_snapshot_on, snapshot_isolation_state_desc,
       is_accelerated_database_recovery_on, compatibility_level, collation_name
FROM sys.databases WHERE name = N'buh';
```

- Включает ли платформа `READ_COMMITTED_SNAPSHOT` сама и когда, в ИТС прямо не сказано ⚠ (`../1c-windows/02-…` отмечает то же). **Не меняйте параметр вручную**: при `OFF` в управляемом режиме чтения начнут ставить разделяемые блокировки и ждать пишущих [MS Learn — поведение `READ COMMITTED` без версионирования], при `ON` в базе конфигурации в автоматическом режиме вы получите расход `tempdb` без выгоды [практика].
- Изоляция `SNAPSHOT` (`ALLOW_SNAPSHOT_ISOLATION`) в таблице режимов 1С не упоминается [ИТС-разр разд. 9.2.3.2]; ошибки 3960/3961 (конфликт обновления и изменение метаданных в транзакции `SNAPSHOT`) для 1С не типичны [MS Learn; практика ⚠].
- Цена версионирования — раздел 5: рост `tempdb`, долгие транзакции (даже читающие) удерживают хранилище версий.

### 11.5. `ПОЛНОЕ СОЕДИНЕНИЕ` на MS SQL

- Ключевое слово `ПОЛНОЕ` соответствует `FULL` [ИТС-разр гл. 8, таблица ключевых слов]; на MS SQL это настоящий `FULL OUTER JOIN`.
- Хеш-соединение поддерживает левое, правое и полное внешнее соединение, а подсказку `LOOP` вместе с `RIGHT` или `FULL` задать нельзя [MS Learn]; на практике полное соединение в плане 1С — `Hash Match` или `Merge Join` по отсортированным входам [практика] (что `FULL` выполняется только этими двумя алгоритмами, документация прямо не пишет). Для больших входов это означает грант памяти под хеш или сортировку и риск сброса в `tempdb` (6.2, 5.4) [MS Learn; практика].
- Условия по результату, построенные на `ЕСТЬNULL(Т1.Поле, Т2.Поле)`, не используют индексы [std 658] — следующие соединения по такому полю идут сканированием [практика].
- Стандарт 435 запрещает сочетать `ПОЛНОЕ СОЕДИНЕНИЕ` с обращением к табличным частям в `ВЫБРАТЬ` и советует избегать конструкции из-за **PostgreSQL**, где она реализована неэффективно, а платформа подменяет её эквивалентной [std 435; ИТС-разр прил. 8, разд. 8.6]. На MS SQL это требования переносимости: рекомендованная замена `ОБЪЕДИНИТЬ ВСЕ` + `СГРУППИРОВАТЬ ПО` работает и здесь, обычно без проигрыша [std 435; практика ⚠].

### 11.6. Подсказки (hints): что видно, что может администратор

**Что ставит платформа.** Какие табличные подсказки и параметры сеанса платформа добавляет к T-SQL (изоляция, `LOCK_TIMEOUT`, чтение вне транзакции в автоматическом режиме, `ДЛЯ ИЗМЕНЕНИЯ`), документация 1С не описывает ⚠ — смотреть текст `Sql` в ТЖ и колонки `transaction_isolation_level`, `lock_timeout` сеансов (1.2). Подсказок оптимизатору в языке запросов 1С нет [практика].

**Влиять на план без изменения конфигурации** [MS Learn]:

| Средство | Версия | Команда | Ограничения |
|---|---|---|---|
| Подсказки Query Store | 2022+ | `EXEC sys.sp_query_store_set_hints @query_id = 39, @query_hints = N'OPTION (MAXDOP 1, RECOMPILE)';` снять — `EXEC sys.sp_query_store_clear_hints @query_id = 39;` | только подсказки запроса (`RECOMPILE`, `MAXDOP`, `OPTIMIZE FOR UNKNOWN`, `{LOOP\|MERGE\|HASH} JOIN`, `FORCE ORDER`, `MAX_GRANT_PERCENT`, `USE HINT`…); табличные (`FORCESEEK`, `INDEX`) и `OPTIMIZE FOR (@p = …)` — нет; право `ALTER` на базу; перекрывают подсказки в тексте и руководства планов |
| Принудительный план | 2016+ | `EXEC sp_query_store_force_plan @query_id = 39, @plan_id = 120;` (отмена — `sp_query_store_unforce_plan`) | пересматривать при росте данных |
| Руководство плана | все | `sys.sp_create_plan_guide @name, @stmt, @type = N'SQL', @params, @hints` | `@stmt` и `@params` должны точно совпасть с оператором; зависит от редакции |

```sql
-- query_id запроса 1С по имени таблицы (Query Store базы buh) [имена представлений — MS Learn]
USE [buh];
SELECT TOP (20) q.query_id, p.plan_id, p.is_forced_plan, SUM(rs.count_executions) AS execs,
       AVG(rs.avg_cpu_time) AS avg_cpu, LEFT(qt.query_sql_text, 300) AS query_text
FROM sys.query_store_query_text AS qt
JOIN sys.query_store_query AS q ON q.query_text_id = qt.query_text_id
JOIN sys.query_store_plan AS p ON p.query_id = q.query_id
JOIN sys.query_store_runtime_stats AS rs ON rs.plan_id = p.plan_id
WHERE qt.query_sql_text LIKE N'%_AccumRg1234%'
GROUP BY q.query_id, p.plan_id, p.is_forced_plan, LEFT(qt.query_sql_text, 300)
ORDER BY SUM(rs.count_executions * rs.avg_cpu_time) DESC;
```

**Риски для 1С** ⚠ (не проверялось): тексты с разными `#tt…` дают разные `query_id` — подсказка может не сработать на следующем выполнении; обновление конфигурации и реструктуризация меняют тексты, и подсказки молча «отваливаются» (Microsoft и сама советует пересматривать их при изменении данных и миграциях [MS Learn]). Это временная мера, пока разработчик исправляет запрос; фиксировать, что и на какой `query_id` навешено.

### 11.7. Что из стандартов особенно важно на MS SQL

| Стандарт | Требование | Проявление на SQL Server | Что видно |
|---|---|---|---|
| [std 652] | условия — по началу индекса, подряд; иначе скан и больше блокировок | скан кластерного индекса; в транзакции — тысячи блокировок → эскалация (3.5), 1222 у соседей; при RCSI блокируют `UPDATE`/`DELETE` со сканом | `Index Scan` в плане, лидеры по `logical_reads`, `lock_escalation` |
| [std 654] | «через точку» от составного поля — соединение со всеми таблицами типов (в примере — 56) и их RLS; ограничивать `ВЫРАЗИТЬ` | огромный план, долгая компиляция (`RESOURCE_SEMAPHORE_QUERY_COMPILE`), 8623, параллелизм | гигантский `Sql` в ТЖ, высокий `avg_compile_duration` в Query Store |
| [std 655], [std 656] | не соединять с вложенными запросами и виртуальными таблицами, не ставить подзапрос в `ПО` — временные таблицы с индексом | оптимизатор не знает числа строк → вложенные циклы по миллионам строк или огромный хеш; нестабильность после статистики | несколько планов у `query_id`, «гуляющая» длительность |
| [std 657], [std 733] | условия — в параметры виртуальной таблицы; «Остатки» без даты и со всеми измерениями | иначе — сборка всей виртуальной таблицы с группировкой и чтение движений | лишние агрегаты и чтения таблиц итогов и движений |
| [std 658] | основное условие — `=` и `И` по индексу, на последнем поле `>`, `<`, `МЕЖДУ`, `ПОДОБНО "x%"`, `В`; `ИЛИ` по разным полям — `ОБЪЕДИНИТЬ ВСЕ`; одна роль с RLS на право | несаргабельное условие → скан; две роли с RLS → `ИЛИ` во всех запросах к объекту | `Index Scan` при наличии «правильного» индекса |
| [std 777], [std 729] | временные таблицы — без сотен тысяч строк, с индексом от 1000 строк при соединении; 5–7 таблиц в запросе уже много | рост и конкуренция в `tempdb`, сортировка при вставке в таблицу с кластерным индексом ⚠, плохие планы многотабличных запросов | `user_objects_mb` (5.3), `PAGELATCH_*` на `tempdb` |
| [std 460] | управляемый режим, явная блокировка до чтения, без `ДЛЯ ИЗМЕНЕНИЯ` | без него — Serializable и блокировки диапазонов (3.3) | `LCK_M_R*` |

### 11.8. Отличия от PostgreSQL для тех же запросов

Подробно о PostgreSQL — `../postgresql/10-zaprosy-1c-v-postgresql.md`.

| Аспект | MS SQL Server | PostgreSQL для 1С |
|---|---|---|
| Управляемый режим | Read Committed Snapshot, версии в `tempdb` (или в базе при ADR) [ИТС-разр 9.2.3.2; MS Learn] | Read Committed, версии в таблицах, очистка `VACUUM` [ИТС-разр 9.2.3.2] |
| Автоматический режим | блокировки записей, Repeatable Read/Serializable | блокировки таблиц, Serializable [ИТС-разр прил. 8, разд. 8.6] |
| Класс СУБД по ИТС | «блокировочная» | «версионная» [ИТС-адм разд. 6.6.4] |
| Эскалация | есть; 1С советует запрещать флагами [ИТС-мет 5946] | эскалации строк до таблицы нет [практика] |
| Временные таблицы | `#tt…` в общей `tempdb`, первый индекс кластерный [ИТС-разр 8.4.10.4] | `pg_temp.tt…`, `fasttrun`, `plantuner` |
| `ПОЛНОЕ СОЕДИНЕНИЕ` | нативно, обычно хеш или слияние [MS Learn; практика] | подменяется эквивалентом, медленно [std 435] |
| Кеш планов | план `sp_executesql` переиспользуется (11.2) [MS Learn] | планы 1С, как правило, не кешируются ⚠ (не сверялось) |
| План без изменения кода | Query Store hints, принудительные планы, руководства планов | `plantuner`; `pg_hint_plan` — в Postgres Pro Standard (`../postgresql/06-…`) |
| Даты | `datetime` с 1753 года, смещение 2000 | смещения нет |
| Разрыв долгого запроса из консоли | работает при `processadmin` [ИТС-КС 5.2.12.3] | не работает — снимать на стороне СУБД |
| Тайм-аут блокировки | `LOCK_TIMEOUT` сеанса ⚠ | `lock_timeout` от платформы |
| Обслуживание | статистика `FULLSCAN` + очистка кеша планов, индексы (страничные блокировки с 8.3.22) [ИТС-мет 5837] | `VACUUM`/`ANALYZE`, `REINDEX` [ИТС-разр прил. 8, разд. 8.6] |
| Реструктуризация v2 | только по TCP/IP [ИТС-адм прил. 3, 3.17.23] | поддерживается |

## 12. Порядок действий при жалобе «всё встало»

1. Не входит SSMS — DAC: `sqlcmd -S sql01 -E -A` [ИТС-мет 6008, 2023; MS Learn].
2. Ожидания сейчас (`sys.dm_os_waiting_tasks`, `sys.dm_exec_requests`): `LCK_M_*` → 3; `PAGEIOLATCH_*`, `WRITELOG` → 10; `RESOURCE_SEMAPHORE` → 6.2; `CXPACKET` → 7.1; `THREADPOOL` → 6.5; `PAGELATCH_*` на `2:…` → 5.4 [ИТС-мет 6008; MS Learn]. Накопленные ожидания — `mssql/06-…`.
3. Цепочки и «головы» (3.2) → сеанс 1С по `session_id` → журнал регистрации и ТЖ.
4. Журнал и `tempdb` (4.2, 5.3), долгие транзакции (4.3), место на дисках.
5. Лидеры по процессору и дискам (9.2, 10.2); журнал ошибок: `EXEC sys.sp_readerrorlog 0, 1;`.
6. Код 1С: ТЖ `DBMSSQL` с отбором (9.3), `<dbmslocks/>` (3.2), `system_health` (3.4).
7. Действие: завершить сеанс средствами 1С (3.7), освободить журнал (4.4), MAXDOP 1 (7.1); разработчику — запрос, `Context` и номер стандарта (11.7). Что собрать для обращения в 1С — `../its-metod/sbor-dannyh-dlya-rassledovaniya-problem.md` (разд. 1.14, 1.16, 1.21, 1.23) [ИТС-мет 6005, 2022].
