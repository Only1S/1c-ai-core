## Кратко — главные факты

1. **1С допускает кластер на уровне СУБД** для MS SQL [ИТС-КС разд. 5.5.3], но кластер серверов 1С сервер СУБД не резервирует [ИТС-КС разд. 2.2.5]; инструкции 1С по Always On нет — механика по документации Microsoft.
2. **MS SQL — только при рабочих серверах 1С на Windows** [ИТС-КС разд. 1.5.4, 2.3]; сам SQL Server может быть на Linux [v8.1c.ru], группы там — на Pacemaker [MS Learn].
3. **Версии:** 8.3.27 и 8.5.1 — до SQL Server 2022 [ИТС-КС разд. 1.5.4; `otlichiya-8.5.1`]; v8.1c.ru (20.10.2026) — 2016, 2017, 2019, 2022. **2025 в требованиях 1С нет.**
4. **Выбор:** группа доступности — Enterprise (до 8 вторичных, с 2019 до 5 синхронных вместе с первичной); **базовая группа** в Standard — 2 реплики, **одна база**, вторичная не читается → «одна группа на одну ИБ»; FCI — общий диск, Standard 2 узла, Enterprise 16; доставка журналов — ручное переключение; зеркалирование устарело [MS Learn].
5. **База в группе:** полная модель, есть полная копия, многопользовательский режим, без `AUTO_CLOSE`; на всех репликах одна версия и одна сортировка экземпляра; узлы — в одном WSFC [MS Learn].
6. **Не реплицируются** логины, задания Agent, настройки экземпляра, `tempdb` [MS Learn]. Логины SQL — с тем же SID (`sp_help_revlogin` [MS Learn], `Copy-DbaLogin` [сторонний]); исключение — содержащиеся группы (2022+, Enterprise).
7. **Синхронная фиксация** — без потерь при переключении на `SYNCHRONIZED`-реплику, но каждая фиксация ждёт вторичную (`HADR_SYNC_COMMIT`); после тайм-аута сеанса (10 с) первичная перестаёт её ждать, если не задан `REQUIRED_SYNCHRONIZED_SECONDARIES_TO_COMMIT` [MS Learn].
8. **Автопереключение** — две синхронные реплики с `FAILOVER_MODE = AUTOMATIC`, вторичная `SYNCHRONIZED`, кворум WSFC; `FAILURE_CONDITION_LEVEL` = 3, `HEALTH_CHECK_TIMEOUT` = 30000 мс по умолчанию; `DB_FAILOVER` (2016+) **выключен по умолчанию** — включите [MS Learn].
9. **1С подключается к листенеру:** «Сервер баз данных» = имя листенера (при порте не 1433 — `листенер,порт` ⚠: формат драйвера [MS Learn], для 1С не описан).
10. **`MultiSubnetFailover`** поддерживает OLE DB Driver (с 18.0.2), но не OLE DB Native Client 11 [MS Learn]; передать его из 1С нельзя ⚠ → синхронные реплики в одной подсети или `RegisterAllProvidersIP = 0` + `HostRecordTTL = 300` [MS Learn].
11. **При переключении** соединения рвутся, незафиксированное откатывается [MS Learn]; у сеансов 1С — ошибка СУБД, текущая операция прерывается ⚠. Плановые переключения — при заблокированных сеансах и заданиях.
12. **Читаемая вторичная для ИБ 1С не годится** (только чтение, `ApplicationIntent` из 1С не задать ⚠); отчёты с неё — только через механизм копий БД и после проверки ⚠ [ИТС-разр гл. 26].
13. **Операции 1С:** новая ИБ в группу сама не попадает (копия + `ADD DATABASE`); базу в группе нельзя удалить [MS Learn]; для `.dt` 1С советует простую модель [ИТС-адм разд. 6.8] — базу на время выводят из группы.
14. **Журнал** не усекается, пока вторичные не приняли записи (`AVAILABILITY_REPLICA`); приостановленная вторичная → рост журнала до 9002 [MS Learn].
15. **Копии БД `Версия2` (CDC):** после переключения — `sys.sp_cdc_add_job` для `capture` и `cleanup` на новой первичной [MS Learn; ИТС-разр гл. 26].
16. **FCI:** одна копия данных на общем хранилище (оно — единая точка отказа); переключение = перезапуск службы с холодным кешем; логины и задания общие [MS Learn].
17. **Доставка журналов:** RPO = период копирования журнала + копирование + восстановление; после переключения сервер СУБД в свойствах ИБ меняют вручную (`rac infobase update --db-server`) ⚠.
18. **Обновления:** с 2017 нет SP — только CU и GDR; после первого CU возврат на ветку GDR — только удалением всех CU [MS Learn]. На 20.10.2026: 2022 CU27 (16.0.4295.3), 2019 — последний CU32 и далее только GDR, 2025 CU9 [MS Learn]. 1С требует последний CU [ИТС-мет 5904, 2019].
19. **CU:** `<пакет>.exe /qs /IAcceptSQLServerLicenseTerms /Action=Patch /InstanceName=…`; Cluster-Aware Updating для групп доступности не поддерживается [MS Learn].
20. **Скользящее обновление группы:** снять автопереключение → обновить вторичные → плановое переключение → обновить бывшую первичную → вернуть автопереключение; при смене **версии** после переключения назад пути нет [MS Learn].
21. **Уровень совместимости** при обновлении сохраняется; новый оптимизатор и оценщик кардинальности включаются только на уровне новой версии (2022 — 160, 2025 — 170) → поднимать отдельным шагом с Query Store [MS Learn]; рекомендации 1С по уровню нет ⚠.
22. **Флаг 4199:** 1С — включать всегда [ИТС-мет 5946, 2019]; Microsoft — после обновления нужен только для исправлений, вышедших после выпуска версии (`QUERY_OPTIMIZER_HOTFIXES`) [MS Learn].
23. **Новая версия — на новом сервере** (откат = старый сервер), логины с SID, задания, настройки, смена сервера СУБД у ИБ; на серверах 1С — OLE DB Driver (Native Client не младше версии SQL Server [ИТС-КС разд. 1.5.4], последний — 11 из 2012 [MS Learn]).
24. **Перенос MS SQL → PostgreSQL** — `ibcmd infobase replicate` (8.3.23+) на Windows-машине или `.dt` [ИТС-адм разд. 7.2, 7.4.17, 6.7–6.8]; раздел 12.

## 1. Что выбрать: карта отказоустойчивости для баз 1С на MS SQL

### 1.1. Что даёт 1С и чего не даёт

| Уровень | Что защищает | Источник |
|---|---|---|
| Отказоустойчивый кластер серверов 1С (уровень отказоустойчивости, резервные рабочие процессы, несколько центральных серверов) | отказ рабочего процесса, менеджера кластера, рабочего сервера 1С | [ИТС-КС разд. 2.2.5]; `../1c/10`, разд. 5 |
| Сервер СУБД | **не защищается** кластером 1С — нужна схема на уровне СУБД | [ИТС-КС разд. 5.5.3]; `../1c/10`, разд. 5.1 |
| Хранилище двоичных данных, журнал регистрации | средствами СУБД не копируются и не реплицируются — нужны свои средства | [ИТС-КС разд. 5.1.1; ИТС-адм разд. 6.9.2] |
| Выгрузка `.dt` | **не** резервная копия: долго, нужен монопольный режим, может не загрузиться | [ИТС-адм разд. 6.7] |
| Механизм копий базы данных | копия таблиц для отчётов и Дата акселератора; **не** резервная копия и не информационная база | [ИТС-разр гл. 26] |

Из этого следует [практика]: отказоустойчивость базы 1С на MS SQL складывается из трёх независимых слоёв — кластер 1С (два и более сервера 1С), схема СУБД (раздел 2–8) и отдельное резервирование файлов на серверах 1С (журнал регистрации, хранилище двоичных данных, если оно не в S3) — плюс обычные резервные копии (`mssql/04`). Реплика — не резервная копия: удаление или порча данных из 1С мгновенно реплицируется [MS Learn — «Secondary databases aren't backups»].

### 1.3. Типовые схемы для 1С

| Задача | Схема | Комментарий |
|---|---|---|
| Несколько ИБ, Standard, локальная отказоустойчивость | на каждую ИБ своя базовая группа (`WITH (BASIC)`), у каждой свой листенер, два узла Standard + свидетель WSFC | базовая группа — одна база [MS Learn]; несколько базовых групп на одном экземпляре допустимы [MS Learn]; листенеров станет столько же, сколько ИБ [практика] |
| Enterprise, все ИБ переключаются вместе | одна группа на все базы 1С, синхронная реплика с автопереключением в том же ЦОД + асинхронная в резервном | переключение — по группе целиком [MS Learn]; единый листенер для всех ИБ [практика] |
| Есть SAN, нужна защита от отказа сервера, а не диска | FCI на два узла | не защищает от отказа хранилища [MS Learn]; дополнить доставкой журналов или асинхронной репликой |
| Резервный ЦОД с «тёплой» копией, допустимы минуты потерь | доставка журналов (каждые 5–15 мин) или асинхронная реплика | переключение ручное [MS Learn] |
| Переезд на новую версию/ЦОД с минимальным простоем | распределённая группа (Enterprise, 2017+ допускает разные версии) или временная доставка журналов | раздел 8.2, 11.3 |

**Не надо** [практика]: строить группу доступности на одном физическом хосте виртуализации (две ВМ на одном хосте — формально разные узлы [MS Learn], но отказ хоста кладёт обе); использовать синхронную фиксацию через медленный WAN (каждая транзакция 1С будет ждать подтверждения удалённой стороны, раздел 2.4).

### 1.4. Смешанная среда и SQL Server на Linux

- Сервер 1С на Linux (ваш случай) MS SQL как СУБД информационной базы не использует — схемы этой статьи к нему неприменимы [ИТС-КС разд. 2.3]. Для перехода баз с MS SQL на ваш «PostgreSQL для 1С» — раздел 12.
- SQL Server на Linux при серверах 1С на Windows поддерживается [v8.1c.ru]. Отказоустойчивость там: группы доступности с `CLUSTER_TYPE = EXTERNAL` под управлением Pacemaker (`FAILOVER_MODE = EXTERNAL`, ресурс-агент — пакет `mssql-server-ha`) или `CLUSTER_TYPE = NONE` (только ручное переключение, для чтения и миграций) [MS Learn]. На Linux листенер — это IP-ресурс Pacemaker и запись в DNS; при переключении IP переезжает с узла на узел и короткий разрыв неизбежен [MS Learn]. Для двух узлов Standard автоматическому переключению нужен третий узел — **реплика только для конфигурации** (`AVAILABILITY_MODE = CONFIGURATION_ONLY`, может быть даже на Express) [MS Learn].
- Группа с WSFC или Pacemaker не может иметь реплики на разных ОС; кросс-платформенные реплики — только у групп с `CLUSTER_TYPE = NONE` и у распределённых групп [MS Learn]. Это удобный путь переезда SQL Server с Windows на Linux без смены СУБД [MS Learn]; для 1С он ничего не меняет — сервер 1С по-прежнему должен быть на Windows.

## 2. Группы доступности Always On: устройство, требования, настройка

### 2.1. Термины

- **Группа доступности** — набор пользовательских баз, которые переключаются вместе; **реплика** — экземпляр SQL Server, хранящий копию всех баз группы; одна **первичная** (чтение-запись) и до восьми **вторичных** (только чтение) [MS Learn].
- **Синхронизация данных** идёт на уровне базы: первичная отправляет записи журнала транзакций, вторичная их «закрепляет» на диске (harden) и применяет (redo) [MS Learn].
- **WSFC** (Windows Server Failover Cluster) — кластер Windows, который следит за здоровьем первичной реплики и решает о переключении; для каждой группы создаётся роль кластера; кворум считается по всем узлам WSFC, свидетеля в смысле зеркалирования у групп нет [MS Learn].
- **Листенер** — виртуальное сетевое имя (VNN), один или несколько виртуальных IP и TCP-порт; соединения через него идут на текущую первичную реплику (или, при read-only routing, на читаемую вторичную) [MS Learn].
- **Конечная точка зеркалирования** (`FOR DATABASE_MIRRORING`) — TCP-порт обмена журналом между репликами (в примерах Microsoft — 5022), одна на экземпляр [MS Learn].

### 2.2. Требования и ограничения

**Узлы Windows** [MS Learn]: все — в одном WSFC, не контроллеры домена; одна реплика группы на узел (ВМ на одном хосте считаются разными узлами); сопоставимое «железо», желательно отдельная сеть репликации, **одинаковая раскладка дисков** (иначе подготовка вторичной через `RESTORE … WITH MOVE`, а добавление файла на первичной приостановит вторичную); общие сетевые пути для WSFC и реплик; администратор WSFC — администратор каждого узла.

**Экземпляры** [MS Learn]: одна версия SQL Server (смешение — только на время скользящего обновления, 10.5, 11.6); **одна сортировка экземпляра** (`SELECT SERVERPROPERTY('Collation');` — сравнить до построения группы; для 1С — `mssql/02`); Always On включён (перезапуск службы); конечная точка зеркалирования на каждом; для Kerberos через листенер — одна доменная учётная запись службы на всех экземплярах и SPN листенера (`MSSQLSvc/<FQDN листенера>:<порт>`) на ней. Потоки: до `max worker threads` − 40; поток захвата журнала на каждую первичную базу и поток отправки на каждую вторичную; параллельный redo — до 16 потоков на базу и 100 на экземпляр до 2019, в 2022 — общий пул [MS Learn]. Для десятков баз 1С на экземпляре это ощутимо [практика].

**Базы** [MS Learn]: пользовательская, чтение-запись, многопользовательская, без `AUTO_CLOSE`, **полная модель**, полная копия после перевода в полную модель, не в другой группе и не в зеркалировании; базу в группе нельзя удалить. Монопольный режим 1С не переводит базу в однопользовательский режим [ИТС-адм разд. 6.7] — конфликта нет.

**Лимиты** [MS Learn]: до 8 вторичных; синхронных — до 5 вместе с первичной в 2019+ (3 в 2017); имя группы — до 128 символов; жёсткого предела групп и баз на экземпляр нет (Microsoft проверяла 10 групп и 100 баз на физический сервер).

### 2.3. Редакции: Enterprise, Standard (базовая группа), Express

| Возможность | Enterprise | Standard | Express |
|---|---|---|---|
| Группы доступности (полные) | да | нет | нет |
| Базовые группы доступности | нет | да | нет |
| Содержащиеся (contained) группы | да | нет | нет |
| Распределённые группы | да | нет | нет |
| Группа без кластера (`CLUSTER_TYPE = NONE`) | да | да | нет |
| FCI | да, до 16 узлов | да, 2 узла | нет |
| Доставка журналов | да | да | нет |

Источник: таблицы «Editions and supported features» SQL Server 2022 и 2025 [MS Learn]. Там же есть строки «Failover servers for high availability / disaster recovery» (Enterprise и Standard) — это лицензионное право на пассивную реплику; его условия описаны в лицензионном руководстве Microsoft, а не в технической документации ⚠ (не сверялось; уточняйте у поставщика лицензий).

**Ограничения базовой группы** [MS Learn]: только две реплики (на Linux 2017+ — плюс реплика только для конфигурации); вторичную нельзя читать, нельзя делать на ней копии и `DBCC CHECKDB`; одна база в группе; реплики — SQL Server 2016+; базовую группу нельзя превратить в обычную — только удалить и создать заново на Enterprise; базовая группа не может входить в распределённую; на одном экземпляре допускается несколько базовых групп. Создаётся `CREATE AVAILABILITY GROUP … WITH (BASIC, …)`, обе реплики указываются сразу.

Для 1С на Standard [практика]: каждая ИБ — своя базовая группа и свой листенер; копии и `DBCC CHECKDB` — только на первичной (`mssql/04`, `mssql/05`); помните про суммарную нагрузку — на одном узле окажутся первичные реплики всех групп, если их не разнести вручную.

### 2.4. Режимы фиксации: синхронный и асинхронный

| | Синхронная фиксация (`SYNCHRONOUS_COMMIT`) | Асинхронная (`ASYNCHRONOUS_COMMIT`) |
|---|---|---|
| Когда клиент получает подтверждение | после того как вторичная закрепила журнал на диске | сразу после записи журнала на первичной |
| Потери при отказе первичной | нет, если вторичная была `SYNCHRONIZED` | возможны (всё, что лежало в очереди отправки) |
| Виды переключения | автоматическое (при `FAILOVER_MODE = AUTOMATIC` у обеих) и плановое ручное | только принудительное (`FORCE_FAILOVER_ALLOW_DATA_LOSS`) |
| Цена | рост времени каждой фиксации, ожидание `HADR_SYNC_COMMIT` | отставание вторичной (лаг) |
| Источник | [MS Learn] | [MS Learn] |

Важные детали [MS Learn]:

- Синхронная фиксация действует, только если **обе** стороны (первичная и данная вторичная) настроены синхронными. Если первичная настроена асинхронной, она фиксирует асинхронно для всех.
- **Тайм-аут сеанса** реплики — по умолчанию 10 с (минимум 5 с, меньше 10 не советуют). Если синхронная вторичная не ответила за это время, она переходит в `DISCONNECTED`, базы — в `NOT SYNCHRONIZING`, и первичная **перестаёт ждать** её подтверждений — транзакции продолжаются без защиты.
- **`REQUIRED_SYNCHRONIZED_SECONDARIES_TO_COMMIT`** (2017+): сколько синхронных вторичных обязаны подтвердить фиксацию. При `1` и недоступной синхронной вторичной первичная **перестаёт принимать запись** — так меньше риск потерь, но выше риск простоя; при скользящем обновлении это надо учитывать.
- SQL Server 2016+ группирует фиксации в блоки журнала с задержкой до 10 мс; в 2025 её можно уменьшить параметром `availability group commit time` (`sp_configure`, `0` — значение по умолчанию 10 мс).

Для 1С [практика]: учётные базы дают много коротких транзакций (проведение документов, запись регистров) и тяжёлые пакеты (закрытие месяца, обмены, реструктуризация). Синхронная реплика в том же ЦОД с быстрым диском под журнал обычно незаметна; через WAN — заметна каждому пользователю. Признак — рост `HADR_SYNC_COMMIT` в `sys.dm_os_wait_stats` и счётчик «Transaction Delay» [MS Learn]. Удалённую площадку держите асинхронной.

### 2.5. Автоматическое переключение и политика отказа

Условия автоматического переключения [MS Learn]: первичная и целевая вторичная — синхронные, у обеих `FAILOVER_MODE = AUTOMATIC`, вторичная в состоянии `SYNCHRONIZED`, у WSFC есть кворум, выполнены условия гибкой политики. Реплика на FCI автоматически в группе не переключается — только вручную.

**Гибкая политика** — две настройки группы [MS Learn]:

| Параметр | Значения | Умолчание | Смысл |
|---|---|---|---|
| `FAILURE_CONDITION_LEVEL` | 1–5 | **3** | 1 — служба остановлена или истекла аренда (lease); 2 — экземпляр не отвечает (нет ответа `sp_server_diagnostics` за `HEALTH_CHECK_TIMEOUT`); 3 — критические внутренние ошибки (осиротевшие спин-блокировки, нарушения доступа, много дампов); 4 — умеренные ошибки; 5 — любые квалифицированные условия (взаимоблокировка планировщиков и т. п.) |
| `HEALTH_CHECK_TIMEOUT` | 15000 – 4294967295 мс | **30000** | сколько ждать данных `sp_server_diagnostics`; опрос идёт с интервалом 1/3 тайм-аута |
| `DB_FAILOVER` (2016+) | `ON` / `OFF` | **`OFF`** | переключение при проблеме с самой базой (не `ONLINE`: `SUSPECT`, `OFFLINE`, не восстановилась) |

Без `DB_FAILOVER = ON` повреждённая или «подозрительная» база **не** вызывает переключение [MS Learn]. Для 1С имеет смысл включить [практика]: `ALTER AVAILABILITY GROUP [ag_buh] SET (DB_FAILOVER = ON);` (от имени `sysadmin` на первичной), проверка — `SELECT name, db_failover FROM sys.availability_groups;` [MS Learn].

Прочие таймеры [MS Learn]: аренда (lease) — 20000 мс, защищает от «раздвоения мозга»; тайм-аут сеанса — 10000 мс; уменьшать любые из них ниже умолчаний Microsoft не советует. В WSFC есть порог отказов роли (по умолчанию n−1 отказов за 6 часов, n — число узлов WSFC): если его превысить, автоматического переключения не будет, роль останется в состоянии сбоя до ручного вмешательства. В 2025 появился быстрый переход при устойчивых проблемах здоровья (`RestartThreshold = 0` у ресурса группы).

**Не управляйте группой из диспетчера отказоустойчивости кластеров** (Failover Cluster Manager): не переключайте, не меняйте владельцев и зависимости роли — только T-SQL, SSMS или PowerShell SQL Server, иначе состояние WSFC и SQL Server расходится [MS Learn].

### 2.6. Кворум WSFC

Режимы [MS Learn]: большинство узлов; большинство узлов и файлового ресурса (свидетель — общая папка); большинство узлов и диска; только диск. Рекомендации: нечётное число голосов — при чётном числе узлов добавить свидетеля; свидетель-папку размещать **не** на узле кластера, она должна быть видна всем узлам; голос узла можно исключить настройкой `NodeWeight`. Посмотреть участников кворума из SQL Server: `SELECT member_name, member_type_desc, member_state_desc, number_of_quorum_votes FROM sys.dm_hadr_cluster_members;` [MS Learn].

Для двух узлов SQL Server (типичная схема 1С) [практика]: файловый свидетель на третьем сервере (файловом, контроллере домена или любом постоянно работающем) или облачный свидетель; без свидетеля отказ одного из двух узлов оставляет кластер без кворума.

**Группа без домена** (domain independent, Windows Server 2016+, workgroup cluster) [MS Learn]: узлы вне домена или в разных доменах; конечные точки на сертификатах; свидетель — только диск или облако; кластер создаётся только PowerShell; Kerberos нет — приложения подключаются по логину SQL Server. 1С и так подключается к SQL Server по логину и паролю ИБ (`mssql/03`), так что этот вариант для 1С работоспособен ⚠ (не проверялось).

### 2.7. Пошаговая настройка группы для базы 1С (Enterprise или базовая)

Пример: узлы `sql01`, `sql02` в домене `CORP`, SQL Server 2022, база `buh` на `sql01`. Перед началом — копия базы и `DBCC CHECKDB` (`mssql/04`, `mssql/05`).

**Шаг 1. WSFC** (PowerShell, администратор обоих узлов) [MS Learn]:

```powershell
Install-WindowsFeature -Name Failover-Clustering -IncludeManagementTools        # на каждом узле
Test-Cluster -Node sql01, sql02                                                 # путь к HTML-отчёту команда печатает в выводе
New-Cluster -Name sqlclu -Node sql01, sql02 -StaticAddress 10.10.0.40 -NoStorage
Set-ClusterQuorum -Cluster sqlclu -FileShareWitness \\fs01\witness$             # свидетель на третьем сервере
Get-ClusterNode -Cluster sqlclu                                                 # проверка
```

Параметры `New-Cluster` и `Set-ClusterQuorum` (`-FileShareWitness`, `-CloudWitness`, `-DiskWitness`, `-NoWitness`) сверены со справкой модуля FailoverClusters (Windows Server 2025) [MS Learn]. Объекту кластера (CNO) нужно право **Create Computer objects** в OU: без него он создаст не более 10 объектов листенеров, и удалённые листенеры лимит не освобождают [MS Learn].

**Шаг 2. Включить Always On** по очереди на каждом экземпляре (служба перезапускается) [MS Learn]:

```powershell
Enable-SqlAlwaysOn -Path SQLSERVER:\SQL\sql01\DEFAULT -Force    # модуль SqlServer; DEFAULT — экземпляр по умолчанию [практика]
Enable-SqlAlwaysOn -Path SQLSERVER:\SQL\sql02\DEFAULT -Force
```

Проверка — `SELECT SERVERPROPERTY('IsHadrEnabled');` → `1`; то же — в SQL Server Configuration Manager (вкладка Always On) [MS Learn].

**Шаг 3. Конечные точки** (`sysadmin`, на каждом экземпляре) [MS Learn]:

```sql
CREATE ENDPOINT [Hadr_endpoint] STATE = STARTED
    AS TCP (LISTENER_PORT = 5022) FOR DATABASE_MIRRORING (ROLE = ALL);
-- если службы работают под разными доменными учётными записями:
CREATE LOGIN [CORP\svc-sql] FROM WINDOWS;
GRANT CONNECT ON ENDPOINT::[Hadr_endpoint] TO [CORP\svc-sql];
SELECT name, state_desc, role_desc FROM sys.database_mirroring_endpoints;   -- проверка
```

Брандмауэр: 5022/TCP между узлами, 1433/TCP от рабочих серверов 1С [практика]; порты WSFC — Уточнено 20.10.2026 по MS Learn («Service overview and network port requirements for Windows», раздел Cluster service): между узлами UDP 3343 (DTLS) и TCP 3343 (присоединение узла), TCP 135 (RPC) и динамические TCP 49152–65535, TCP 445 и ICMP (присоединение узла, проверка кластера), UDP 137; TCP 5985 — при облачном свидетеле.

**Шаг 4. Логины 1С с тем же SID на всех репликах** — раздел 2.8, до первого переключения.

**Шаг 5. База** (на `sql01`, `sysadmin`) [MS Learn]:

```sql
ALTER DATABASE [buh] SET RECOVERY FULL;
BACKUP DATABASE [buh] TO DISK = N'\\fs01\sqlbackup\buh_full.bak' WITH CHECKSUM, COMPRESSION;  -- COMPRESSION: Enterprise/Standard
SELECT name, recovery_model_desc, user_access_desc, is_auto_close_on FROM sys.databases WHERE name = N'buh';
```

**Шаг 6. Группа** (на `sql01`) — Enterprise, с автоматическим заполнением вторичной [MS Learn]:

```sql
CREATE AVAILABILITY GROUP [ag_buh]
WITH (AUTOMATED_BACKUP_PREFERENCE = PRIMARY, DB_FAILOVER = ON,
      FAILURE_CONDITION_LEVEL = 3, HEALTH_CHECK_TIMEOUT = 30000)
FOR DATABASE [buh]
REPLICA ON
  N'sql01' WITH (ENDPOINT_URL = N'TCP://sql01.corp.local:5022',
                 AVAILABILITY_MODE = SYNCHRONOUS_COMMIT, FAILOVER_MODE = AUTOMATIC,
                 SEEDING_MODE = AUTOMATIC, SECONDARY_ROLE (ALLOW_CONNECTIONS = NO)),
  N'sql02' WITH (ENDPOINT_URL = N'TCP://sql02.corp.local:5022',
                 AVAILABILITY_MODE = SYNCHRONOUS_COMMIT, FAILOVER_MODE = AUTOMATIC,
                 SEEDING_MODE = AUTOMATIC, SECONDARY_ROLE (ALLOW_CONNECTIONS = NO));
GO
-- на sql02:
ALTER AVAILABILITY GROUP [ag_buh] JOIN;
ALTER AVAILABILITY GROUP [ag_buh] GRANT CREATE ANY DATABASE;   -- нужно для автоматического заполнения
```

Для Standard добавьте `BASIC` в `WITH (…)` (пример Microsoft ещё задаёт `DTC_SUPPORT = NONE`, `REQUIRED_SYNCHRONIZED_SECONDARIES_TO_COMMIT = 0`); разрешить чтение в базовой группе нельзя — ошибка [MS Learn]. Пока идёт заполнение, журнал первичной не усекается; сжатие трафика — флаг 9567; ход — `sys.dm_hadr_automatic_seeding` (`current_state`, `failure_state_desc`) и `sys.dm_hadr_physical_seeding_stats` [MS Learn]. Для баз в сотни гигабайт [практика] надёжнее ручная подготовка: полная копия и журнал, восстановление на `sql02` `WITH NORECOVERY`, затем там же `ALTER DATABASE [buh] SET HADR AVAILABILITY GROUP = [ag_buh];` [MS Learn].

**Шаг 7. Листенер** (на первичной) [MS Learn]:

```sql
ALTER AVAILABILITY GROUP [ag_buh]
    ADD LISTENER N'ag-buh' (WITH IP ((N'10.10.0.50', N'255.255.255.0')), PORT = 1433);
SELECT dns_name, port, ip_configuration_string_from_cluster FROM sys.availability_group_listeners;
```

Имя — уникально в домене и NetBIOS, буквы, цифры, `-`, `_`, до 63 символов (в SSMS до 15; NetBIOS учитывает первые 15); адрес статический; порт 1433 допустим, если его не занимает **другой** процесс (экземпляр по умолчанию не мешает) [MS Learn].

**Шаг 8. Проверка** (на первичной) [MS Learn — имена столбцов; `secondary_lag_seconds` — с 2016]:

```sql
SELECT ar.replica_server_name, ars.role_desc, ars.connected_state_desc, ars.synchronization_health_desc,
       ar.availability_mode_desc, ar.failover_mode_desc
FROM sys.availability_replicas ar JOIN sys.dm_hadr_availability_replica_states ars ON ars.replica_id = ar.replica_id;
SELECT DB_NAME(drs.database_id) AS db, ar.replica_server_name, drs.synchronization_state_desc,
       drs.log_send_queue_size, drs.redo_queue_size, drs.last_commit_time, drs.secondary_lag_seconds
FROM sys.dm_hadr_database_replica_states drs JOIN sys.availability_replicas ar ON ar.replica_id = drs.replica_id;
```

Норма — `SYNCHRONIZED`/`HEALTHY`, очереди около нуля. С рабочего сервера 1С: `sqlcmd -S ag-buh -E -M -Q "SELECT @@SERVERNAME"` (`-M` — `MultiSubnetFailover`) [MS Learn]. Затем — пробное плановое переключение (4.3). Сеанс расширенных событий `alwayson_health` создаётся с группой, но если группа создана не мастером, может не запуститься — `ALTER EVENT SESSION [AlwaysOn_health] ON SERVER STATE = START;` на каждой реплике [MS Learn]; написание имени в документации разное ⚠ — сверить с `sys.server_event_sessions`.

### 2.8. Что не реплицируется: логины, задания, настройки экземпляра

Группа переносит только базы; логины, задания Agent и прочие объекты `master`/`msdb` поддерживаются одинаковыми на всех репликах вручную [MS Learn].

**Логины.** Пользователь базы связан с логином по SID. У доменных логинов SID везде одинаков; у логина SQL Server (`buh_1c`) SID генерируется при создании — на другой реплике пользователь «осиротеет», и после переключения 1С получит отказ во входе [MS Learn]. Способы:

1. **`sp_help_revlogin`** [MS Learn, KB 918992]: процедуры `sp_hexadecimal` и `sp_help_revlogin` из статьи «Transfer logins and passwords between instances of SQL Server»; `EXEC sp_help_revlogin;` выдаёт `CREATE LOGIN … PASSWORD = 0x… HASHED, SID = 0x…` для других реплик. База по умолчанию не переносится; занятый SID — ошибка «Supplied parameter sid is in use».
2. **Вручную с тем же SID** [MS Learn; практика]:

```sql
SELECT name, sid FROM sys.server_principals WHERE name = N'buh_1c';          -- на первичной
CREATE LOGIN [buh_1c] WITH PASSWORD = N'<пароль>', SID = 0x<sid>, CHECK_POLICY = OFF;  -- на вторичной, sysadmin
ALTER SERVER ROLE [processadmin] ADD MEMBER [buh_1c];   -- роль, требуемая платформой [ИТС-КС разд. 3.2.3]
```

3. **dbatools** [сторонний]: `Copy-DbaLogin -Source sql01 -Destination sql02 -Login buh_1c` (пароли, SID, роли, права); `Sync-DbaAvailabilityGroup -Primary sql01 -AvailabilityGroup ag_buh` (логины, задания и другие объекты сервера с первичной на вторичные).

Проверка «сирот» после переключения [MS Learn; практика]:

```sql
USE [buh];
SELECT dp.name, dp.sid FROM sys.database_principals dp
LEFT JOIN sys.server_principals sp ON sp.sid = dp.sid
WHERE dp.type = 'S' AND sp.sid IS NULL AND dp.name NOT IN (N'guest', N'INFORMATION_SCHEMA', N'sys');
-- исправление на первичной: ALTER USER [buh_1c] WITH LOGIN = [buh_1c];
```

Права логина 1С на всех репликах одинаковы: `processadmin` или `sysadmin`, чтение `master`, полный доступ к `tempdb` [ИТС-адм разд. 5.2.1.3.2]. Если ИБ подключается без логина (аутентификация ОС от имени рабочего процесса) [ИТС-адм разд. 5.2.1.3.2] — логин Windows этой доменной учётной записи нужен на каждой реплике [MS Learn]. Владелец базы после восстановления на другом сервере может остаться без логина: `SELECT name, SUSER_SNAME(owner_sid) FROM sys.databases;` (`NULL`) [практика]; влияние на 1С не описано ⚠.

**Задания Agent** (копии, регламент, CDC) копируются на все реплики; в начале шага — проверка роли [MS Learn]:

```sql
IF sys.fn_hadr_is_primary_replica(N'buh') <> 1 RETURN;   -- 1 — первичная, 0 — вторичная, NULL — базы нет или не в группе
```

Для копий — `sys.fn_hadr_backup_is_preferred_replica` с учётом `AUTOMATED_BACKUP_PREFERENCE`; планы обслуживания используют её сами [MS Learn].

**Настройки экземпляра** — одинаковые на всех репликах: после переключения база работает с настройками нового экземпляра [MS Learn — список того, что надо воссоздать; практика]. Для 1С (`mssql/02`): `max server memory (MB)`, `max degree of parallelism` = 1 [ИТС-мет 5904, 2019], флаги 1224 (или 1211) и 4199 [ИТС-мет 5946, 2019], файлы `tempdb`, `remote admin connections`, Database Mail и операторы. Сверка: `SELECT name, value_in_use FROM sys.configurations WHERE name IN (N'max server memory (MB)', N'max degree of parallelism', N'remote admin connections');` и `DBCC TRACESTATUS(-1);`.

**Содержащиеся группы** (2022+, Enterprise) [MS Learn]: свои `master` и `msdb` группы (`<группа>_master`, `<группа>_msdb`); логины, права и задания, созданные **через листенер группы**, одинаковы на всех репликах, задания идут только на первичной. Системные базы группы заполняются только автоматически; локальные логины экземпляра (кроме `sysadmin`) в группе не видны; большинство операций уровня базы — только из подключения к экземпляру. Сможет ли кластер 1С создавать базы через листенер такой группы — ⚠ не проверялось.

### 2.9. Читаемые вторичные реплики — можно ли 1С

**Регистрировать ИБ на вторичной реплике бессмысленно** [MS Learn; практика]: база там только для чтения, а 1С пишет; подключение по умолчанию идёт с `ApplicationIntent=ReadWrite` и к вторичной с `ALLOW_CONNECTIONS = READ_ONLY` не пройдёт (с `NO` — никакое) [MS Learn]; поля для `ApplicationIntent` в параметрах ИБ нет [ИТС-адм разд. 5.2.1.3.2] ⚠; в базовой группе вторичная не читается вовсе [MS Learn].

Если читаемые вторичные (Enterprise) используют внешние отчётные системы [MS Learn]: запросы там идут в изоляции моментального снимка (подсказки блокировок игнорируются), временные таблицы в `tempdb` создавать можно; первичная добавляет к изменяемым строкам 14 байт указателя версии; длинные запросы на вторичной задерживают очистку «призрачных» записей на первичной, а их блокировки `Sch-S` тормозят применение DDL (реструктуризация 1С — это DDL; событие `sqlserver.lock_redo_blocked`); статистика для вторичной создаётся временно в `tempdb` и пропадает при переключении; данные отстают на секунды и больше.

**Отчёты 1С с вторичной** возможны лишь через механизм копий БД [ИТС-разр гл. 26]: средствами СУБД копию вести можно, только если она используется только через механизм копий и содержит **все** таблицы основной базы (тип репликации «Внешний» — платформа считает копию актуальной и лишь направляет в неё запросы). Для PostgreSQL ИТС строит промежуточную доступную на запись базу с `postgres_fdw`, потому что резервный сервер не даёт создать даже временные таблицы [ИТС-мет 5971, 2020]. На MS SQL временные таблицы на вторичной возможны [MS Learn], но: одна база СУБД может быть связана только с одной копией, допустимость проверяет `Обновить()` по сведениям об использовании базы копии [ИТС-разр гл. 26] — по разд. 26.6 база, в которой располагается информационная база, получает вариант `ИспользуетсяИнформационнойБазой`, и данные копии в ней размещать нельзя (реплика основной базы — именно такая база); применяется ли эта проверка к внешнему типу репликации, не описано ⚠; соединение копии идёт прямо к вторичной с `ReadWrite` → нужно `SECONDARY_ROLE (ALLOW_CONNECTIONS = ALL)` [MS Learn]; после переключения «отчётная» вторичная может стать первичной. Итог [практика]: без стенда не подключать; штатный путь 1С — копия в **отдельной** базе со стандартной репликацией или Дата акселератор.

### 2.10. Резервное копирование в группе (коротко; подробно — `mssql/04`)

- Где делать копии — подсказка группы `AUTOMATED_BACKUP_PREFERENCE` (`PRIMARY`, `SECONDARY_ONLY`, `SECONDARY`, `NONE`) и `BACKUP_PRIORITY` реплик; SQL Server её не навязывает — её должна учитывать логика заданий (`sys.fn_hadr_backup_is_preferred_replica`) [MS Learn].
- На вторичной (Enterprise; читаемой она быть не обязана — копии проходят и при `ALLOW_CONNECTIONS = NO` [MS Learn]) можно копировать журнал и делать полную копию **только `COPY_ONLY`**; разностные копии на вторичной до 2025 не поддерживаются; в 2025 — ещё полные и разностные копии на любой вторичной [MS Learn]. Базовая группа копий на вторичной не допускает [MS Learn].
- Цепочка журналов общая для всех реплик: Подтверждено 20.10.2026 (MS Learn, «Offload supported backups to secondary replicas»): согласованная цепочка обеспечивается для копий журнала, сделанных на любой реплике, первичной или вторичной, независимо от режима фиксации.
- Копия на вторичной удерживает поток на первичной на всё время копирования [MS Learn].
- Журнал регистрации и хранилище двоичных данных 1С по-прежнему копируются отдельно [ИТС-КС разд. 5.1.1].

### 2.11. Наблюдение за группой (коротко; подробно — `mssql/06`)

| Что | Где смотреть | Норма |
|---|---|---|
| Роль и связь реплик | `sys.dm_hadr_availability_replica_states` (`role_desc`, `connected_state_desc`, `synchronization_health_desc`, `last_connect_error_description`) | `CONNECTED`, `HEALTHY` |
| Состояние баз | `sys.dm_hadr_database_replica_states` (`synchronization_state_desc`, `is_suspended`, `suspend_reason_desc`, `database_state_desc`) | `SYNCHRONIZED` у синхронных, `SYNCHRONIZING` у асинхронных |
| Возможная потеря данных (RPO) | `log_send_queue_size` (КБ) и разница `last_commit_time` первичной и вторичной | около нуля |
| Время переключения (RTO) | `redo_queue_size` / `redo_rate` | секунды |
| Готовность к переключению | `sys.dm_hadr_database_replica_cluster_states.is_failover_ready` | `1` |
| Задержка фиксаций | ожидание `HADR_SYNC_COMMIT`, счётчик «Transaction Delay»; управление потоком — `HADR_DATABASE_FLOW_CONTROL`, `HADR_TRANSPORT_FLOW_CONTROL` | стабильно, без всплесков |
| Журнал первичной не усекается | `sys.databases.log_reuse_wait_desc = AVAILABILITY_REPLICA` | кратковременно |

Все имена представлений, столбцов и ожиданий — [MS Learn]. Формулы RPO и RTO и готовые процедуры их оценки — в статье Microsoft «Monitor performance for availability groups» [MS Learn].

## 3. Подключение кластера 1С к листенеру

### 3.1. Что указать в свойствах информационной базы

По документации 1С поле «Сервер баз данных» для MS SQL — имя компьютера (если на нём один экземпляр) или имя экземпляра в форме `Server/instance`; для связи через общую память на том же компьютере — префикс `lpc:` [ИТС-адм разд. 5.2.1.3.2]. Сам драйвер принимает имя сервера в форме `[протокол:]сервер[,порт]`, где протокол — `tcp`, `lpc` или `np`, а порт по умолчанию 1433 [MS Learn — ключевое слово `Server` OLE DB Driver]. Отсюда для группы доступности:

| Ситуация | Значение «Сервер баз данных» | Статус |
|---|---|---|
| Листенер на порту 1433 | `ag-buh` (или FQDN `ag-buh.corp.local`) | имя листенера в строке подключения — [MS Learn]; для 1С — [практика] |
| Листенер на нестандартном порту, например 14330 | `ag-buh,14330` | формат `имя,порт` — [MS Learn]; что 1С передаёт поле драйверу без изменений — ⚠ (вывод из описания префикса `lpc:` [ИТС-адм разд. 5.2.1.3.2]) |
| Принудительно TCP | `tcp:ag-buh` | ⚠ то же |
| `lpc:` | **не применять** — общая память работает только на том же компьютере, а листенер всегда сетевой | [MS Learn — список протоколов; практика] |
| Именованный экземпляр за листенером | имя листенера (и порт листенера), **без** `\экземпляр` | к листенеру подключаются по имени и порту листенера [MS Learn] |

Изменить сервер СУБД у существующей ИБ — консоль кластера 1С (свойства ИБ) или `rac` (сервер 1С на Windows, от имени администратора кластера; синтаксис сверить с `rac help infobase` своей версии):

```bat
:: сначала заблокировать сеансы и задания (раздел 4.3), база уже должна быть в группе на первичной
"C:\Program Files\1cv8\8.3.27.2074\bin\rac.exe" infobase update --cluster=<uuid кластера> ^
    --infobase=<uuid ИБ> --infobase-user="Администратор" --infobase-pwd="***" ^
    --db-server=ag-buh localhost:1545
:: проверка
"C:\Program Files\1cv8\8.3.27.2074\bin\rac.exe" infobase info --cluster=<uuid кластера> ^
    --infobase=<uuid ИБ> --infobase-user="Администратор" --infobase-pwd="***" localhost:1545
```

Параметр `--db-server` у `infobase update` — `../1c/03-administrirovanie-klastera-ras-rac.md` (сверено со справкой `rac help infobase` 8.3.1x); `localhost:1545` — `ras` на порту по умолчанию [ИТС-КС прил. 3, разд. 3.8]. Рабочие серверы 1С должны разрешать имя листенера в DNS и иметь доступ к его IP и порту через брандмауэр [практика].

### 3.2. `MultiSubnetFailover`: что поддерживает драйвер и что можно сделать без него

**Смысл ключа** [MS Learn]: при `MultiSubnetFailover=Yes` драйвер подключается ко **всем** адресам имени параллельно и берёт первый ответивший; для одного IP — чаще повторяет попытки TCP. Без него адреса перебираются по очереди, и неответивший адрес может съесть весь тайм-аут подключения (по умолчанию 15 с). Microsoft советует ключ и для одной подсети; само переключение он не ускоряет. Только TCP, несовместим с `Failover_Partner`, до 64 IP-адресов.

**Поддержка** [MS Learn]: OLE DB-провайдер Native Client 11 (`SQLNCLI11`) — **нет** (при многоподсетевом листенере до половины подключений упирается в тайм-аут); ODBC Native Client 11 — да; Microsoft OLE DB Driver (`MSOLEDBSQL`, `MSOLEDBSQL19`) — да, с 18.0.2, плюс `TransparentNetworkIPResolution` (с 18.4.0, включён по умолчанию: при `MultiSubnetFailover=No` — сначала один IP, затем все параллельно).

**1С** перебирает провайдеры MS SQL от самого нового к старым до первого успешного соединения; выбор видно в событии `DBMSSQLCONN` по свойствам `hResult…` [ИТС-адм прил. 3, разд. 3.24.2.3, 3.24.2.4.2]; 8.5.1 знает `MSOLEDBSQL19` и `MSOLEDBSQL` [`otlichiya-8.5.1`, п. 16]. **Задать `MultiSubnetFailover`, `ApplicationIntent`, `Connect Timeout`, `ConnectRetryCount` из свойств ИБ нельзя** ⚠; запись через `;` в поле сервера не описана и не проверялась ⚠.

**Что делать** [MS Learn — параметры листенера; практика — выбор схемы]:

1. Синхронные реплики с автопереключением — **в одной подсети**: у листенера один IP, WSFC переносит его на новый узел, DNS не меняется.
2. На рабочих серверах 1С — **OLE DB Driver**: у OLE DB Native Client нет многоподсетевого переключения; к тому же Native Client должен быть не младше SQL Server [ИТС-КС разд. 1.5.4], а последний — 11 (2012) [MS Learn].
3. Если листенер многоподсетевой — для клиентов без ключа `RegisterAllProvidersIP = 0` (в DNS только активный адрес) и меньший `HostRecordTTL` (по умолчанию запись кешируется 20 минут) [MS Learn]:

```powershell
# администратор узла WSFC; имя ресурса листенера смотрите в выводе первой команды (ниже — условное)
Get-ClusterResource | Where-Object ResourceType -eq 'Network Name' | Format-Table Name, OwnerGroup, State
Get-ClusterResource "ag_buh_ag-buh" | Set-ClusterParameter RegisterAllProvidersIP 0
Get-ClusterResource "ag_buh_ag-buh" | Set-ClusterParameter HostRecordTTL 300
Stop-ClusterResource "ag_buh_ag-buh"; Start-ClusterResource "ag_buh_ag-buh"; Start-ClusterGroup "ag_buh"
Get-ClusterResource "ag_buh_ag-buh" | Get-ClusterParameter RegisterAllProvidersIP, HostRecordTTL   # проверка
```

Плата: после переключения между подсетями клиенты найдут сервер только после TTL и репликации DNS — Microsoft пишет о 15 минутах и более; предупреждение мастера проверки WSFC о `RegisterAllProvidersIP = 1` можно игнорировать [MS Learn]. На серверах 1С может понадобиться `ipconfig /flushdns` [практика].

**Устойчивость простаивающих соединений** (`ConnectRetryCount` = 1, `ConnectRetryInterval` = 10 с по умолчанию; с 18.6.0) восстанавливает простаивающее соединение после сетевого сбоя, если сервер подтвердит восстановление [MS Learn]; при переключении группы сеанса на новой первичной нет — прозрачного продолжения ждать не стоит ⚠.

### 3.3. Шифрование и сертификат листенера

- OLE DB Driver 19 по умолчанию требует шифрования (`Encrypt=Mandatory`) и проверяет сертификат; версия 18 и более ранние по умолчанию не шифруют [MS Learn]. С драйвером 19 клиент с настройками по умолчанию не подключится к серверу с недоверенным (самоподписанным) сертификатом [MS Learn].
- При подключении через листенер сертификат каждого узла должен содержать в Subject Alternative Name и FQDN узла, и FQDN всех листенеров группы (иногда и короткие NetBIOS-имена), например `SAN: sql01.corp.local, ag-buh.corp.local` [MS Learn].
- Как платформа 1С задаёт `Encrypt`/`TrustServerCertificate`, ИТС не пишет ⚠ (`../1c-windows/02`, разд. 3.5). Порядок [практика]: выпустить сертификаты из доменного УЦ с SAN для узлов и листенеров, установить на все реплики, проверить с рабочего сервера 1С (`sqlcmd -S ag-buh -E -M -N -Q "SELECT encrypt_option FROM sys.dm_exec_connections WHERE session_id = @@SPID"` — `-N` включает шифрование; Уточнено 20.10.2026 по MS Learn (sqlcmd utility): в `sqlcmd` (ODBC) ключ имеет вид `-N[s|m|o]`, без ключа в новых версиях действует `-Nm` (в версиях для 2022 и старше — `-No`), в `sqlcmd` (Go) — `-N true|false|disable`; если задан `-N` без `-C`, сертификат сервера проверяется) и посмотреть `encrypt_option` у соединений 1С.
- В SQL Server 2025 обмен WSFC с репликами можно перевести на TDS 8.0/TLS 1.3 (`CLUSTER_CONNECTION_OPTIONS = 'Encrypt=Strict'` при создании или изменении группы, затем переключение) — при `Strict` параметр `TrustServerCertificate` игнорируется [MS Learn]. Для 1С это внутренняя связь кластера, на подключение рабочих процессов не влияет [практика].

### 3.4. Kerberos и SPN для листенера

Если ИБ подключается к СУБД без логина SQL (аутентификация ОС от имени учётной записи рабочего процесса 1С) [ИТС-адм разд. 5.2.1.3.2], Kerberos через листенер требует SPN листенера на **учётной записи службы SQL Server**, и для работы на всех репликах все экземпляры должны работать под одной доменной учётной записью [MS Learn]:

```bat
:: от имени администратора домена (или с делегированным правом на запись SPN)
setspn -S MSSQLSvc/ag-buh.corp.local:1433 CORP\svc-sql
setspn -L CORP\svc-sql
```

Пример Microsoft использует `setspn -A`; `-S` перед добавлением проверяет дубликаты, `-L` выводит список SPN учётной записи [MS Learn — справка `setspn`]. С логином SQL (обычная схема для 1С — свой логин на каждую ИБ [практика; ИТС-КС прил. 3, разд. 3.7 требует давать пользователю СУБД только нужные кластеру права]) SPN листенера для 1С не нужен [практика].

### 3.5. Проверка подключения 1С через листенер

```sql
-- на текущей первичной: какие соединения 1С есть, по какому протоколу, зашифрованы ли
SELECT s.login_name, s.host_name, s.program_name, c.client_net_address,
       c.net_transport, c.encrypt_option, c.local_tcp_port
FROM sys.dm_exec_connections c
JOIN sys.dm_exec_sessions s ON s.session_id = c.session_id
WHERE s.login_name = N'buh_1c';
```

`local_tcp_port` у соединений через листенер — порт листенера [практика ⚠]. Со стороны 1С — событие `DBMSSQLCONN` техжурнала (раздел 4.5) и тестовый вход в базу. Имена столбцов `sys.dm_exec_connections` — [MS Learn].

## 4. Что происходит с сеансами 1С при переключении

### 4.1. Со стороны SQL Server

- При переключении группы все постоянные соединения с её базами разрываются; клиент должен открыть новое соединение. Пока идёт переключение, новое подключение не проходит; Microsoft советует увеличенный тайм-аут подключения и повтор подключения в приложении — это повышает шанс подключиться после переключения [MS Learn].
- Новая первичная доприменяет журнал из очереди redo, затем **откатывает незафиксированные транзакции**; откат идёт в фоне под блокировками, база уже доступна; зафиксированные транзакции не теряются (при синхронной реплике в `SYNCHRONIZED`) [MS Learn].
- Время переключения ≈ время применения очереди redo и восстановления; оценка — `redo_queue_size` / `redo_rate` [MS Learn].
- Согласованность между **разными** базами группы при переключении не гарантируется (каждая синхронизируется отдельно) [MS Learn] — для 1С это важно, если обработки пишут в несколько ИБ в одной логической операции [практика].
- Временная статистика читаемых вторичных удаляется [MS Learn]; кеш планов на новой первичной холодный → первые минуты после переключения запросы компилируются заново [практика].

### 4.2. Со стороны 1С

ИТС описывает поведение отказоустойчивого кластера 1С при сбоях **рабочих процессов и серверов 1С** (повтор вызова, если ошибка передачи данных получена до фиксации первой транзакции вызова; завершение сеанса, если после) [ИТС-КС разд. 2.2.5]. Что делает платформа при разрыве соединения **с СУБД**, ИТС не описывает ⚠. По механике СУБД и общему поведению платформы ожидаемо [практика ⚠]:

| Что было в момент переключения | Ожидаемый результат |
|---|---|
| Сеанс ничего не делал с базой | при следующем обращении рабочий процесс устанавливает новое соединение; ошибки может не быть, может быть одна ошибка СУБД ⚠ |
| Шёл запрос или транзакция (проведение, запись) | ошибка СУБД у пользователя, транзакция откачена на сервере СУБД, операцию нужно повторить |
| Фоновое или регламентное задание (обмен, закрытие месяца, загрузка из внешних систем) | задание завершается с ошибкой; регламентное запустится по расписанию; проверить результат и при необходимости перезапустить |
| Реструктуризация (обновление конфигурации БД), загрузка `.dt`, «Тестирование и исправление» | операция прерывается; повторить после переключения; перед такими операциями держите копию (`mssql/04`) |
| Механизм копий БД (`Версия2`, CDC) | задания CDC на новой первичной нужно создать (раздел 5.6) |

Если после переключения ошибки соединения у сеансов не проходят, [практика ⚠]: перезапустить рабочие процессы кластера 1С (консоль кластера или `rac`), проверить разрешение имени листенера (`nslookup ag-buh`), DNS-кеш, событие `DBMSSQLCONN`.

### 4.3. Плановое переключение: регламент

Когда: обслуживание узла, установка CU, проверка схемы. Условия: обе реплики синхронные, целевая — `SYNCHRONIZED`; команда выполняется **на целевой вторичной** [MS Learn].

**1. Заблокировать сеансы и регламентные задания ИБ** (сервер 1С на Windows, администратор кластера; параметры — `../1c/03`, сверить с `rac help infobase`):

```bat
set RAC="C:\Program Files\1cv8\8.3.27.2074\bin\rac.exe"
%RAC% infobase update --cluster=<uuid> --infobase=<uuid> --infobase-user="Администратор" --infobase-pwd="***" ^
    --sessions-deny=on --scheduled-jobs-deny=on --denied-message="Переключение сервера СУБД" ^
    --permission-code=SWITCH2026 localhost:1545
%RAC% session list --cluster=<uuid> --infobase=<uuid> localhost:1545
:: оставшиеся сеансы завершить: %RAC% session terminate --cluster=<uuid> --session=<uuid> localhost:1545
```

**2. Проверить готовность** (на целевой вторичной `sql02`, `sysadmin`) [MS Learn]:

```sql
SELECT database_name, is_failover_ready FROM sys.dm_hadr_database_replica_cluster_states
WHERE replica_id IN (SELECT replica_id FROM sys.availability_replicas WHERE replica_server_name = @@SERVERNAME);  -- IN: на экземпляре может быть несколько групп
SELECT DB_NAME(database_id) AS db, synchronization_state_desc, redo_queue_size
FROM sys.dm_hadr_database_replica_states WHERE is_local = 1;
```

Все базы — `is_failover_ready = 1`, `SYNCHRONIZED`.

**3. Переключить** (на `sql02`) [MS Learn]:

```sql
ALTER AVAILABILITY GROUP [ag_buh] FAILOVER;
```

или PowerShell: `Switch-SqlAvailabilityGroup -Path SQLSERVER:\Sql\sql02\DEFAULT\AvailabilityGroups\ag_buh` [MS Learn]. Команда возвращается, как только цель приняла команду; восстановление баз продолжается асинхронно [MS Learn].

**4. Проверить:** `sqlcmd -S ag-buh -E -M -Q "SELECT @@SERVERNAME"` → `SQL02`; запрос состояния из раздела 2.7, шаг 8; на новой первичной включены и работают нужные задания Agent (раздел 2.8), задания CDC (раздел 5.6).

**5. Проверить 1С:** вход с кодом разрешения (`/UC SWITCH2026`), открыть журналы, провести тестовый документ в копии или отменить проведение; затем снять блокировку:

```bat
%RAC% infobase update --cluster=<uuid> --infobase=<uuid> --infobase-user="Администратор" --infobase-pwd="***" ^
    --sessions-deny=off --scheduled-jobs-deny=off localhost:1545
```

### 4.4. Аварийное переключение с возможной потерей данных

Когда автоматическое переключение невозможно (первичная недоступна, вторичная асинхронная или не синхронизирована) [MS Learn]:

1. **Кворум WSFC.** Принудительное переключение требует кворума; если его нет — сначала принудительный кворум (это отдельная процедура WSFC, есть риск «раздвоения мозга») [MS Learn].
2. **Оценить потери до команды**, если возможно: у синхронной реплики, бывшей `SYNCHRONIZED`, — `is_failover_ready = 1` → потерь не будет; иначе — отставание по `last_commit_time`/`last_hardened_lsn`; при нескольких вторичных выбирать наименее отстающую (`end_of_log_lsn`) [MS Learn].
3. **На выбранной вторичной:**

```sql
ALTER AVAILABILITY GROUP [ag_buh] FORCE_FAILOVER_ALLOW_DATA_LOSS;
```

4. **После:** все остальные вторичные базы и бывшая первичная (когда вернётся) — в `SUSPENDED`; их нужно возобновить вручную на каждой реплике [MS Learn]:

```sql
-- на каждой вторичной реплике, для каждой базы
ALTER DATABASE [buh] SET HADR RESUME;
```

При возобновлении бывшая первичная откатывает всё, чего нет на новой первичной, — эти транзакции теряются окончательно; если важно их изучить, до возобновления сделайте моментальный снимок базы на приостановленной вторичной [MS Learn]. Пока вторичная приостановлена, журнал первичной не усекается [MS Learn] — не тяните.

5. **Для 1С** [практика ⚠]: потерянные транзакции — это проведённые документы и записи последних секунд или минут, причём журнал регистрации и хранилище двоичных данных лежат вне СУБД и **не откатываются** — в журнале регистрации могут остаться записи о действиях, которых в базе нет, а в хранилище — файлы без ссылок. Сообщите пользователям интервал, за который нужно перепроверить ввод; проверьте `DBCC CHECKDB` на новой первичной; оцените нумерацию документов (могут быть «дыры»).

### 4.5. Что смотреть в технологическом журнале 1С

События [ИТС-адм прил. 3, разд. 3.24.2.3]: `EXCP` — исключения, в том числе невосстановимые ошибки базы данных (уровень `ERROR`) [ИТС-адм прил. 3, разд. 3.24.2.4.3]; `DBMSSQL` — выполнение операторов SQL; `DBMSSQLCONN` — первое соединение с MS SQL и выбор провайдера (свойства `hResult…`). Пример `logcfg.xml` на время работ (формат — [ИТС-адм прил. 3, разд. 3.24]; каталог условный):

```xml
<config xmlns="http://v8.1c.ru/v8/tech-log">
  <log location="D:\1c_logs\failover" history="48">
    <event><eq property="name" value="EXCP"/></event>
    <event><eq property="name" value="DBMSSQLCONN"/></event>
    <property name="all"/>
  </log>
</config>
```

Возникает ли `DBMSSQLCONN` повторно при переподключении рабочего процесса после переключения (в описании — «при первом соединении»), не проверялось ⚠. Подробно о техжурнале — `../1c/07-tehzhurnal-diagnostika-zhurnal-registracii.md`.

## 5. Эксплуатация баз 1С в группе доступности

### 5.1. Новая информационная база

Кластер 1С создаёт базу командой СУБД на сервере, указанном в «Сервер баз данных», — то есть через листенер на **текущей первичной** [практика]. В группу она сама не попадает. Порядок:

1. Создать ИБ (консоль кластера или `rac infobase create --create-database --dbms=MSSQLServer --db-server=ag-buh --db-name=zup --db-user=zup_1c --db-pwd=… --date-offset=2000 --locale=ru_RU …`, параметры — `../1c/03`; смещение дат — `../1c-windows/02`, разд. 5.2, и [ИТС-адм разд. 5.2.1.3.2]).
2. Модель восстановления новой базы берётся из `model`, а у `model` она зависит от редакции [MS Learn] (в Standard и Enterprise — полная [практика; `../1c-windows/02`]); проверить `recovery_model_desc`.
3. Создать логин `zup_1c` с тем же SID на всех репликах (раздел 2.8).
4. Полная копия и добавление в группу (на первичной) [MS Learn]:

```sql
BACKUP DATABASE [zup] TO DISK = N'\\fs01\sqlbackup\zup_full.bak' WITH CHECKSUM;
ALTER AVAILABILITY GROUP [ag_all] ADD DATABASE [zup];
```

При автоматическом заполнении (`SEEDING_MODE = AUTOMATIC` и `GRANT CREATE ANY DATABASE` на вторичных) вторичная копия создастся сама; иначе — восстановление `WITH NORECOVERY` и `ALTER DATABASE [zup] SET HADR AVAILABILITY GROUP = [ag_all];` на каждой вторичной [MS Learn].

В Standard для новой ИБ создаётся новая базовая группа со своим листенером (раздел 2.3).

Если базу создаёт администратор СУБД заранее (сценарий «база уже есть», `mssql/03`) — включите её в группу до регистрации в 1С или после, разницы нет [практика].

### 5.2. Удаление информационной базы

Базу, входящую в группу, удалить нельзя [MS Learn] — удаление ИБ из консоли 1С с флажком удаления базы данных завершится ошибкой ⚠ (текст не проверялся). Порядок [MS Learn]:

```sql
-- на первичной: вывести базу из группы (первичная остаётся ONLINE, вторичные — RESTORING)
ALTER AVAILABILITY GROUP [ag_all] REMOVE DATABASE [zup];
-- на каждой вторичной: удалить оставшуюся копию
DROP DATABASE [zup];
```

Затем удалить ИБ в консоли 1С (с удалением базы или без — по ситуации). Перед удалением — копия (`mssql/04`).

### 5.3. Загрузка `.dt`, восстановление поверх, «чистая» перезаливка

- Для ускорения загрузки `.dt` 1С рекомендует простую модель или модель с неполным протоколированием [ИТС-адм разд. 6.8]; базы в группе обязаны быть в полной модели [MS Learn]. Варианты [практика]: (а) грузить как есть — дольше, журнал разрастается и передаётся на вторичные (следите за местом под журнал и `log_send_queue_size`); (б) вывести базу из группы → `ALTER DATABASE … SET RECOVERY SIMPLE` → загрузить → `SET RECOVERY FULL` → полная копия → вернуть в группу (раздел 5.1, шаг 4). Для больших баз вариант (б) обычно быстрее и безопаснее.
- **Восстановление из копии поверх рабочей базы** (откат после ошибки) [MS Learn; практика]: `RESTORE` в базу, входящую в группу, не выполнить — сначала `REMOVE DATABASE`, удалить копии на вторичных, восстановить на первичной (к базе не должно быть подключений, в том числе фоновых заданий и средств администрирования [ИТС-КС разд. 5.1.1]), затем полная копия и снова `ADD DATABASE`. Порядок восстановления — `mssql/04`.
- После любой из этих операций проверить логины-«сироты» (раздел 2.8) и права.

### 5.4. Реструктуризация, обслуживание индексов, статистика

- Реструктуризация 1С и перестроение индексов пишут в журнал объёмы, сравнимые с размером таблиц; в группе этот журнал передаётся и применяется на всех репликах — растут `log_send_queue_size` и `redo_queue_size`, при синхронной реплике тормозят все фиксации [MS Learn — механика; практика — для 1С]. Планируйте такие работы на окно, следите за очередями (раздел 2.11).
- Запросы на читаемой вторичной могут блокировать применение DDL (`Sch-S` против `Sch-M` у redo) [MS Learn] — перед реструктуризацией остановите отчётные нагрузки на вторичных.
- `max degree of parallelism = 0` на время реструктуризации [ИТС-мет 5945, 2018] задаётся на экземпляре **текущей первичной**; если во время работ случится переключение, на новой первичной будет её собственное значение [практика].
- Перестроение индексов в режиме `ONLINE` есть только в Enterprise [MS Learn]; страничные блокировки индексов 1С (8.3.22+) и `REORGANIZE` — `mssql/05` [ИТС-мет 5837, 2022].
- Статистику и индексы обслуживают **на первичной** — изменения попадают на вторичные через журнал; задания регламента на всех репликах с проверкой роли (раздел 2.8) [MS Learn; практика].

### 5.5. Журнал транзакций и место на дисках

- Журнал первичной не усекается, пока все вторичные не приняли записи (`log_reuse_wait_desc = AVAILABILITY_REPLICA`); копирование журнала по-прежнему обязательно [MS Learn].
- Приостановленная (`SUSPENDED`) или отключённая вторичная — главная причина бесконтрольного роста журнала до ошибки 9002 [MS Learn]. Решение — возобновить (`ALTER DATABASE … SET HADR RESUME;` на вторичной) или удалить реплику/базу из группы, если она не вернётся.
- Автоматическое заполнение (seeding) тоже удерживает журнал первичной до окончания [MS Learn].
- Добавление файла в базу при разной раскладке дисков приостанавливает вторичную [MS Learn] — держите одинаковые пути на всех репликах.

```sql
-- почему не усекается журнал
SELECT name, recovery_model_desc, log_reuse_wait_desc FROM sys.databases WHERE name = N'buh';
-- отставание и приостановка
SELECT ar.replica_server_name, DB_NAME(drs.database_id) AS db, drs.is_suspended, drs.suspend_reason_desc,
       drs.log_send_queue_size, drs.redo_queue_size
FROM sys.dm_hadr_database_replica_states drs JOIN sys.availability_replicas ar ON ar.replica_id = drs.replica_id;
```

### 5.6. Механизм копий БД 1С (`Версия2`, CDC) в группе

- `Версия2` стандартной репликации копий на MS SQL использует Change Data Capture; нужен SQL Server Agent; при отсутствии у логина роли `sysadmin` администратор выполняет `sys.sp_cdc_enable_db` и задаёт `max text repl size = -1`; в SQL Server 2019 CU20, 2022 CU2 и новее CDC несовместим с `DELAYED_DURABILITY` [ИТС-разр гл. 26].
- CDC в группе поддерживается, настраивается на первичной; захват выполняет задание Agent на экземпляре, поэтому **после переключения на новой первичной нужно создать задания захвата и очистки**, а на бывшей первичной — отключить [MS Learn]:

```sql
-- на новой первичной, в базе ИБ, sysadmin или db_owner
USE [buh];
EXEC sys.sp_cdc_add_job @job_type = 'capture';
EXEC sys.sp_cdc_add_job @job_type = 'cleanup';
```

- При скользящем обновлении с CDC может понадобиться `EXECUTE [master].[sys].[sp_vupgrade_replication];` на новой первичной (до SQL Server 2019 CU1; с 2019 CU1 шаг не нужен) [MS Learn].
- На вторичных CDC включить нельзя, читать таблицы изменений там можно [MS Learn].

### 5.7. Что живёт вне базы СУБД

- Журнал регистрации и хранилище двоичных данных (встроенное) лежат на серверах 1С; СУБД их не копирует и не реплицирует [ИТС-КС разд. 5.1.1]. Их отказоустойчивость — средства кластера 1С (журнал регистрации стал отказоустойчивым в 8.5.4, `../1c/10`, разд. 5.1) и копирование файлов.
- Данные полнотекстового поиска 1С, сеансовые данные, кеши — на серверах 1С, к группе доступности отношения не имеют [практика].
- Полнотекстовый поиск самого SQL Server 1С не использует (у 1С свой индекс ППД) [практика] — поэтому изменение компонентов полнотекстового поиска в SQL Server 2025 [MS Learn] базы 1С не затрагивает ⚠.

## 6. Экземпляр отказоустойчивого кластера (FCI)

### 6.1. Устройство

- FCI — **один** экземпляр SQL Server, установленный на нескольких узлах WSFC; в каждый момент службы работают только на узле-владельце группы ресурсов. Ресурсы группы: сетевое имя, IP-адрес, общие диски, службы Database Engine и SQL Server Agent [MS Learn].
- Хранилище общее для всех узлов: диски кластера (iSCSI, Fibre Channel), SAN, Storage Spaces Direct, общие папки SMB; поддерживаются CSV. **Хранилище — единая точка отказа** [MS Learn].
- Двоичные файлы SQL Server ставятся на каждый узел локально; службы запускает WSFC, а не автозапуск [MS Learn].
- Узлы должны быть одинаковыми по ОС, её обновлениям, версии и обновлениям SQL Server, составу компонентов и имени экземпляра [MS Learn].
- Редакции: Enterprise — до 16 узлов, Standard — 2 [MS Learn]. На Windows Server 2016–2022 (Standard и Datacenter), 2012/2012 R2 [MS Learn — список поддерживаемых ОС в статье FCI].
- Логины, задания, настройки экземпляра, `tempdb` — общие (это тот же экземпляр), отдельная синхронизация не нужна [MS Learn — вывод из устройства «один экземпляр»; практика].

### 6.2. Переключение и что видит 1С

Последовательность переключения [MS Learn]: (если это не аппаратный сбой) сброс «грязных» страниц на диск → остановка служб на активном узле → передача группы ресурсов → запуск служб на новом узле → клиенты подключаются к тому же сетевому имени.

Для 1С [практика ⚠]: в поле «Сервер баз данных» — сетевое имя FCI (для именованного экземпляра — `имя_FCI\экземпляр`, в нотации 1С `имя_FCI/экземпляр` [ИТС-адм разд. 5.2.1.3.2]); при переключении все соединения рвутся так же, как в группе доступности (раздел 4); после переключения **кеш буферов и планов пуст** — первые минуты работа медленнее. Время переключения зависит от времени восстановления баз: с SQL Server 2016 новые базы по умолчанию используют косвенные контрольные точки с целевым временем восстановления 1 минута; у баз, созданных в более ранних версиях, `TARGET_RECOVERY_TIME` остаётся 0 (автоматические контрольные точки) [MS Learn]. Проверьте после переноса или обновления: `SELECT name, target_recovery_time_in_seconds FROM sys.databases;` — для предсказуемого переключения FCI Microsoft советует косвенные контрольные точки [MS Learn].

```sql
-- задать косвенную контрольную точку (sysadmin; применяется сразу)
ALTER DATABASE [buh] SET TARGET_RECOVERY_TIME = 60 SECONDS;
```

`MultiSubnetFailover` важен и для многоподсетевого FCI: его сетевое имя получает IP в каждой подсети; поиск именованного экземпляра на многоподсетевом FCI — тоже возможность этого ключа [MS Learn]. Ограничения 1С — раздел 3.2.

### 6.3. Политика отказа FCI

Ресурсная DLL SQL Server держит отдельное соединение и вызывает `sp_server_diagnostics` с интервалом 1/3 от `HealthCheckTimeout`; что считать отказом, задаёт `FailureConditionLevel` (уровни 0–5: 0 — никаких автоматических перезапусков и переключений, только для обслуживания; по умолчанию 3 — служба остановлена, экземпляр не отвечает, `sp_server_diagnostics` вернул «system error») [MS Learn]. Настраиваются в диспетчере кластера или T-SQL на активном узле [MS Learn]:

```sql
ALTER SERVER CONFIGURATION SET FAILOVER CLUSTER PROPERTY FailureConditionLevel = 3;
ALTER SERVER CONFIGURATION SET FAILOVER CLUSTER PROPERTY HealthCheckTimeout = 60000;   -- мс
```

### 6.4. Установка (коротко; общее — `mssql/02`)

Параметры `setup.exe` для FCI [MS Learn]: `/ACTION=InstallFailoverCluster` (установка на первый узел), затем `AddNode` на остальных (или пара `PrepareFailoverCluster`/`CompleteFailoverCluster`); обязательные `/FAILOVERCLUSTERNETWORKNAME` (сетевое имя) и `/FAILOVERCLUSTERIPADDRESSES` (формат `<тип>;<адрес>;<сеть>;<маска>`, типы DHCP, IPv4, IPv6), необязательные `/FAILOVERCLUSTERDISKS` и `/FAILOVERCLUSTERGROUP`. Установку на узлы FCI выполняет локальный администратор с правами входа как служба и работы как часть ОС на всех узлах [MS Learn]. В SQL Server 2025 установка FCI завершается ошибкой, если на машине отключён TLS 1.2 [MS Learn]. В рабочей среде — статические IP: DHCP Microsoft для рабочей среды не рекомендует [MS Learn — о листенере; для FCI — практика].

### 6.5. FCI вместе с группой доступности

FCI может быть репликой группы доступности (например, FCI в основном ЦОД + асинхронная реплика в резервном) [MS Learn]. Ограничения [MS Learn]: реплика на FCI переключается **только вручную**; узлы, которые могут владеть FCI, не должны держать другую реплику той же группы (иначе при переезде FCI реплику можно потерять); сменить сетевое имя FCI-реплики — удалить и заново добавить реплику. FCI сам по себе с доставкой журналов совместим [MS Learn].

## 7. Доставка журналов (log shipping)

### 7.1. Как устроена

Три задания SQL Server Agent [MS Learn]: копирование журнала на первичном сервере в папку (категория «Log Shipping Backup») → копирование файлов на вторичный («Log Shipping Copy») → восстановление на вторичном («Log Shipping Restore»); необязательный сервер-монитор хранит историю и поднимает оповещения («Log Shipping Alert»); монитор нельзя добавить позже без пересоздания конфигурации. Автоматического переключения нет [MS Learn].

Требования [MS Learn]: первичная база в полной модели или модели с неполным протоколированием (перевод в простую ломает доставку); общая папка для копий журнала (если служба SQL Server работает от `LocalSystem` — локальный путь); хранимые процедуры доставки журналов — `sysadmin`; SQL Server Agent обязателен. Редакции: Enterprise, Standard (до 2022 включительно ещё Web; в 2025 редакции Web нет), не Express [MS Learn].

Вторичная база — в `RESTORING` (режим `NORECOVERY`) или `STANDBY` (только чтение между восстановлениями; при восстановлении пользователей можно отключать) [MS Learn]. `STANDBY` возможен только при одинаковой мажорной версии первичного и вторичного серверов [MS Learn]. Плюс доставки журналов — **задержка восстановления**: можно держать вторичную на N минут позади, чтобы успеть достать данные до ошибочного изменения [MS Learn].

### 7.2. Для 1С

- RPO = период копирования журнала + копирование + восстановление (обычно 5–30 минут) [практика]; RTO — минуты-часы: ручное переключение и перенастройка 1С.
- Вторичная в `STANDBY` доступна только на чтение — 1С с ней работать не будет (раздел 2.9) [практика].
- После переключения 1С должна указывать на новый сервер [практика ⚠]: (а) `rac infobase update --db-server=<новый сервер>` для каждой ИБ (раздел 3.1); (б) заранее завести для ИБ DNS-имя (CNAME, например `sql-buh`) и переключать его — тогда не трогать 1С, но помнить про кеш DNS и Kerberos-SPN под новое имя; (в) псевдоним клиента SQL Server на рабочих серверах 1С — драйвер принимает в качестве имени сервера псевдоним SQL Server Configuration Manager [MS Learn], но где его создавать для OLE DB Driver, в источниках сессии не сверялось ⚠.
- Логины с тем же SID и задания на вторичном сервере — заранее (раздел 2.8): проблема «сирот» относится и к доставке журналов [MS Learn].
- Хорошее применение для 1С — **резервный сервер в другом здании** вместе с локальной отказоустойчивостью (базовая группа или FCI) и **инструмент переезда** на новый сервер или версию (раздел 11.3) [практика].

### 7.3. Настройка

Удобнее всего — SSMS (свойства базы → «Transaction Log Shipping»), где задаются папка копий, расписания трёх заданий, режим восстановления и монитор [MS Learn]. T-SQL-набор: на первичном `sp_add_log_shipping_primary_database` и `sp_add_log_shipping_primary_secondary`, на вторичном `sp_add_log_shipping_secondary_primary` и `sp_add_log_shipping_secondary_database`, плюс расписания заданий [MS Learn]. Фрагмент для первичного (параметры — из примера Microsoft; `sysadmin`, база `msdb`):

```sql
DECLARE @LS_BackupJobId uniqueidentifier, @LS_PrimaryId uniqueidentifier;
EXEC master.dbo.sp_add_log_shipping_primary_database
    @database = N'buh',
    @backup_directory = N'E:\lsbackup',
    @backup_share = N'\\sql01\lsbackup',
    @backup_job_name = N'LSBackup_buh',
    @backup_retention_period = 4320,          -- минуты
    @backup_compression = 2,                  -- 0 — не сжимать, 1 — сжимать, 2 (умолчание) — по 'backup compression default'
    @monitor_server = N'sqlmon',
    @monitor_server_security_mode = 1,
    @backup_threshold = 60,
    @threshold_alert_enabled = 1,
    @history_retention_period = 5760,
    @backup_job_id = @LS_BackupJobId OUTPUT,
    @primary_id = @LS_PrimaryId OUTPUT,
    @overwrite = 1;
```

В SQL Server 2025 у процедур появились параметры строк подключения (`@primary_connection_options`, `@monitor_connection_options`, например `N'Encrypt=Mandatory;TrustServerCertificate=Yes;'`) для TDS 8.0; удалённый монитор на 2025 может перестать работать, если остальные серверы топологии на более ранних версиях, — конфигурацию пересоздают [MS Learn].

### 7.4. Переключение на вторичный сервер

[MS Learn]:

1. Скопировать все нескопированные файлы журнала в папку вторичного и применить все неприменённые копии по порядку.
2. Если первичная база доступна — снять **хвост журнала** `WITH NORECOVERY` (база уйдёт в `RESTORING`, её потом можно догнать журналами с нового первичного) и применить его на вторичном.
3. Восстановить вторичную базу в рабочее состояние и направить клиентов на этот сервер.
4. Отключить задания доставки журналов на старой паре; при необходимости настроить доставку в обратную сторону (смену ролей).

```sql
-- на старом первичном (если жив), sysadmin; сначала заблокировать сеансы 1С (раздел 4.3)
BACKUP LOG [buh] TO DISK = N'\\fs01\sqlbackup\buh_tail.trn' WITH NORECOVERY, CHECKSUM;
-- на вторичном: применить оставшиеся копии журнала и хвост, затем открыть базу
RESTORE LOG [buh] FROM DISK = N'\\fs01\sqlbackup\buh_tail.trn' WITH NORECOVERY;
RESTORE DATABASE [buh] WITH RECOVERY;
-- проверка
SELECT name, state_desc, recovery_model_desc FROM sys.databases WHERE name = N'buh';
```

Затем — логины-«сироты» (раздел 2.8), сервер СУБД в свойствах ИБ (раздел 7.2), задания, копирование (`mssql/04`). `RESTORE DATABASE <база> WITH RECOVERY` без указания устройства — штатный способ перевести базу из `RESTORING` в рабочее состояние без восстановления данных [MS Learn — «Recover a Database Without Restoring Data»].

### 7.5. Наблюдение

```sql
-- на мониторе или вторичном сервере: когда последний раз копировали и восстанавливали
SELECT secondary_server, secondary_database, primary_server, last_copied_file, last_copied_date,
       last_restored_file, last_restored_date, last_restored_latency, restore_threshold
FROM msdb.dbo.log_shipping_monitor_secondary;
-- на мониторе или первичном: последняя копия журнала
SELECT primary_server, primary_database, last_backup_file, last_backup_date, backup_threshold
FROM msdb.dbo.log_shipping_monitor_primary;
```

Столбцы таблиц и процедуры `sp_help_log_shipping_monitor_primary`, `sp_help_log_shipping_monitor_secondary`, `sp_refresh_log_shipping_monitor` — [MS Learn]. Отчёт SSMS «Transaction Log Shipping Status» — на сервере-мониторе [MS Learn].

## 8. Зеркалирование, распределённые группы, группы без кластера — кратко

### 8.1. Зеркалирование базы данных (устарело)

- Помечено как устаревшее; для высокой доступности Microsoft рекомендует группы доступности [MS Learn]. В Standard — только режим полной защиты (синхронный), в Express — только свидетель [MS Learn]. Работает только с полной моделью восстановления [MS Learn].
- Клиент находит новый основной сервер через ключевое слово `Failover Partner` строки подключения [MS Learn]; задать его в свойствах ИБ 1С нельзя ⚠ — без него после переключения 1С продолжит стучаться к старому серверу [практика ⚠].
- **Для 1С на Standard зеркалирование заменяется базовой группой доступности** — она и создана как замена зеркалированию [MS Learn]. Пока у группы две реплики и вторичная нечитаема, клиенты могут подключаться и строкой зеркалирования — это вариант переходного периода [MS Learn]; для 1С неприменим по той же причине (`Failover Partner`).
- Старое зеркалирование можно использовать как инструмент переезда на новую версию: скользящее обновление зеркалируемых экземпляров стоит одного переключения [MS Learn].

### 8.2. Распределённые группы доступности (Enterprise)

Группа из двух групп доступности в разных WSFC (или Pacemaker), даже в разных доменах и на разных ОС; данные идут от первичной первой группы к «пересылающей» (forwarder) первичной второй; у распределённой группы нет своего листенера — используются листенеры составляющих групп; переключение между группами — только вручную [MS Learn]. С SQL Server 2017 составляющие группы могут быть **разных мажорных версий** (группа с первичной — та же или младше) — это штатный путь миграции на новую версию или в новый ЦОД с минимальным простоем [MS Learn]. Базовые группы в распределённые не входят [MS Learn]. Для 1С после переключения распределённой группы ИБ перенаправляют на листенер второй группы (раздел 3.1) [практика].

### 8.3. Группы без кластера и SQL Server на Linux

- `CLUSTER_TYPE = NONE` (2017+): группа без WSFC/Pacemaker — для масштабирования чтения и миграций, **не** для высокой доступности; только ручное переключение [MS Learn].
- На Linux: `CLUSTER_TYPE = EXTERNAL` + Pacemaker, автоматическое переключение при `FAILOVER_MODE = EXTERNAL`; `REQUIRED_SYNCHRONIZED_SECONDARIES_TO_COMMIT` там управляется Pacemaker; для двух узлов нужна реплика только для конфигурации; читаемые вторичные — только Enterprise; распределённые транзакции (DTC) в группах на Linux не поддерживаются [MS Learn]. 1С распределённые транзакции к ИБ не применяет [практика ⚠].

## 9. Резервирование на уровне 1С

### 9.1. Отказоустойчивый кластер серверов 1С

Защищает от отказа рабочих процессов и серверов 1С, но не СУБД (`../1c/10`, разд. 5) [ИТС-КС разд. 2.2.5]. В схеме «два сервера 1С + группа доступности на двух узлах SQL Server» оба слоя дополняют друг друга [практика]. Не размещайте сервер 1С и реплику SQL Server на одном узле WSFC без расчёта памяти: при переключении группы на этот узел он получит нагрузку и 1С, и СУБД (`mssql/02` — память при совмещении) [практика].

### 9.2. Механизм копий базы данных и Дата акселератор

[ИТС-разр гл. 26; `../its-docs/dev-gl26-kopii-bazy-dannyh.md`]:

- копия — это таблицы выбранных объектов в **другой** базе (можно на другом сервере и даже другой СУБД — MS SQL, Oracle, PostgreSQL), только для запросов и отчётов; не резервная копия и не информационная база; лицензия КОРП;
- стандартная репликация: `Версия1` (изменения отслеживает кластер 1С) или `Версия2` (на MS SQL — CDC, раздел 5.6); внешняя — средствами администратора, при условии полной копии и использования только через механизм копий;
- запрос не уходит в копию, если в сеансе открыта транзакция или используется менеджер временных таблиц; после ошибки копии она перестаёт использоваться до обновления или перезапуска кластера, а запрос, не требовавший «только копии», повторяется на основной базе.

Для отказоустойчивости механизм копий **не** подходит — он разгружает основную базу от отчётов [ИТС-разр гл. 26]. Использование вторичной реплики группы как внешней копии — раздел 2.9 (⚠).

### 9.3. Сравнение с PostgreSQL

Для PostgreSQL 1С описала аналог Always On: Patroni + etcd + HAProxy, с адресом HAProxy в свойствах ИБ [ИТС-мет 5971, 2020; `../its-metod/pg-otkazoustojchivyj-klaster-i-kopii-bd.md`]; подробности и современные версии — `../postgresql/07`. У вас целевая СУБД — «PostgreSQL для 1С», поэтому для новых систем строить отказоустойчивость на MS SQL имеет смысл только там, где серверы 1С остаются на Windows [практика].

## 10. Обновления SQL Server: CU, GDR и их установка

### 10.1. Модель обслуживания

| Вид | Что содержит | Как часто | Источник |
|---|---|---|---|
| Накопительное обновление (CU) | все исправления и доработки с выхода версии (для 2016 и старше — с последнего SP) | 2017+: ежемесячно первый год, затем раз в два месяца до конца основной поддержки (5 лет) | [MS Learn] |
| GDR | только исправления безопасности и критические; бывает на базе RTM (RTM-GDR) или на базе CU (CUnn-GDR); заказать нельзя, выпускает Microsoft | по мере необходимости | [MS Learn] |
| Исправление по запросу (OD) | критическое исправление для конкретной базовой сборки | без расписания | [MS Learn] |
| Пакет обновлений (SP) | для 2017 и новее **не выпускается** | — | [MS Learn] |

По фазам поддержки [MS Learn]: основная поддержка — CU, OD, GDR; расширенная — только GDR (обновления безопасности); после окончания — обновления безопасности только по подписке ESU. Последний CU для 2017 — CU31; для 2016 и старше CU больше не выходят [MS Learn].

**Две ветки** [MS Learn]: от RTM идут ветка GDR (только безопасность) и ветка CU (всё). После первого CU экземпляр — на ветке CU; **вернуться на GDR можно только удалив все CU**. Microsoft Update/WSUS предлагают CU чистому RTM или экземпляру на ветке CU; экземпляр с GDR один раз обновляют до CU вручную.

Для 1С [ИТС-мет 5904, 2019; практика]: нужен последний CU, то есть ветка **CU**; сначала стенд с копией рабочей базы, через 1–2 недели — рабочие серверы.

**Текущие сборки на 20.10.2026** (страница Microsoft «Latest updates and version history for SQL Server») [MS Learn]:

| Версия | Последний CU | CU + GDR | GDR на RTM | Комментарий |
|---|---|---|---|---|
| SQL Server 2025 (17.x) | CU9 — 17.0.5005.3 (сентябрь 2026) | 17.0.5015.4 (октябрь 2026) | 17.0.1145.4 | нет в требованиях 1С |
| SQL Server 2022 (16.x) | CU27 — 16.0.4295.3 (сентябрь 2026) | 16.0.4305.5 (октябрь 2026) | 16.0.1210.3 | основная поддержка до 11.01.2028 |
| SQL Server 2019 (15.x) | CU32 — 15.0.4430.1 (февраль 2025) | 15.0.4500.2 (октябрь 2026) | 15.0.2200.2 | расширенная поддержка: новых CU нет, только GDR |
| SQL Server 2017 (14.x) | CU31 — 14.0.3456.2 (сентябрь 2022) | 14.0.3560.2 (октябрь 2026) | 14.0.2140.2 | расширенная поддержка до 12.10.2027 |
| SQL Server 2016 (13.x) | SP3, CU больше нет | GDR для SP3 — 13.0.6500.1 (июль 2026) | — | расширенная поддержка закончилась 14.07.2026 |

Даты окончания поддержки — [MS Learn, lifecycle], подробнее — `mssql/01`. Список изменчив: перед обновлением открывайте страницу Microsoft заново.

### 10.2. Как узнать текущую сборку

```sql
SELECT SERVERPROPERTY('ProductVersion')         AS version,   -- major.minor.build.revision
       SERVERPROPERTY('ProductLevel')           AS level,     -- RTM / SPn
       SERVERPROPERTY('ProductUpdateLevel')     AS cu,        -- CUn или NULL
       SERVERPROPERTY('ProductUpdateReference') AS kb,
       SERVERPROPERTY('Edition')                AS edition,
       SERVERPROPERTY('IsClustered')            AS is_fci,
       SERVERPROPERTY('IsHadrEnabled')          AS hadr;
SELECT @@VERSION;
```

Свойства — [MS Learn, `SERVERPROPERTY`]; `ProductUpdateLevel` и `ProductUpdateReference` есть начиная с 2014 CU10 / 2014 SP1 CU3 [MS Learn]. Версию также пишут первые строки `ERRORLOG` [MS Learn].

### 10.3. Установка CU из командной строки

От имени локального администратора на узле SQL Server [MS Learn]:

```bat
:: один экземпляр и общие компоненты, только окно прогресса
SQLServer2022-KB<номер>-x64.exe /qs /IAcceptSQLServerLicenseTerms /Action=Patch /InstanceName=MSSQLSERVER
:: все экземпляры на машине
SQLServer2022-KB<номер>-x64.exe /qs /IAcceptSQLServerLicenseTerms /Action=Patch /AllInstances
:: удаление обновления с экземпляра
SQLServer2022-KB<номер>-x64.exe /qs /Action=RemovePatch /InstanceName=MSSQLSERVER
```

Ключи `/Action=Patch|RemovePatch`, `/InstanceName`, `/InstanceID`, `/AllInstances`, `/qs`, `/quiet`, `/IAcceptSQLServerLicenseTerms` (нужен при `/q` и `/qs`), `/UpdateEnabled` — [MS Learn]; имя файла пакета условное (зависит от версии и KB). Установка блокируется, если ожидается перезагрузка или не работает служба Windows Installer [MS Learn — для обновления версии; для CU — практика ⚠]. Журналы установки — `%programfiles%\Microsoft SQL Server\<nnn>\Setup Bootstrap\Log` (`Summary.txt`, подкаталог с датой: `Detail.txt`) [MS Learn]. Проверка — запрос из 10.2.

### 10.4. CU на одиночном сервере с базами 1С

Простой — на время установки и перезапуска службы [практика]. Регламент:

1. Копия всех баз 1С и системных баз (`mssql/04`), `DBCC CHECKDB` по графику (`mssql/05`).
2. Заблокировать сеансы и регламентные задания ИБ (раздел 4.3, шаг 1), дождаться завершения фоновых заданий.
3. Установить CU (10.3), перезагрузить, если установщик просит.
4. Проверить сборку (10.2), журнал `ERRORLOG` (ошибки скриптов обновления), что все базы `ONLINE`: `SELECT name, state_desc FROM sys.databases;`.
5. Вход в 1С с кодом разрешения, контрольные операции (раздел 11.8), снять блокировку.

### 10.5. CU в группе доступности (скользящее)

Порядок Microsoft — тот же для CU, новой версии и обновлений Windows [MS Learn]:

1. **Подготовка:** пробное плановое переключение; полная копия каждой базы; `DBCC CHECKDB`; копии — только на первичной (`AUTOMATED_BACKUP_PREFERENCE = PRIMARY`): обновляемую базу копировать нельзя.
2. **Снять автопереключение** со всех синхронных реплик:

```sql
-- на первичной, sysadmin
ALTER AVAILABILITY GROUP [ag_buh] MODIFY REPLICA ON N'sql01' WITH (FAILOVER_MODE = MANUAL);
ALTER AVAILABILITY GROUP [ag_buh] MODIFY REPLICA ON N'sql02' WITH (FAILOVER_MODE = MANUAL);
```

3. **Обновить** асинхронные вторичные, затем удалённые синхронные, затем локальные синхронные. Выключенная синхронная вторичная транзакции первичной не задерживает — кроме случая `REQUIRED_SYNCHRONIZED_SECONDARIES_TO_COMMIT` = 1 или 2 (первичная может стать недоступной на запись).
4. Дождаться `SYNCHRONIZED`, затем **плановое переключение** на обновлённую синхронную вторичную (4.3, с блокировкой 1С); на асинхронную — никогда.
5. **Обновить бывшую первичную**, при необходимости `ALTER DATABASE … SET HADR RESUME;`.
6. **Вернуть** `FAILOVER_MODE = AUTOMATIC`; при желании — обратное плановое переключение.

Предупреждения [MS Learn]: **Cluster-Aware Updating** для групп доступности не поддерживается; первичную раньше вторичных не обновлять (журнал с новой сборки на старую не идёт); установка **новой версии или экземпляра** на узел с репликой обновляет модуль высокой доступности WSFC (`RHS.EXE`) и может прервать группы, где узел первичный, — делать в окно или после переключения; для баз с CDC/репликацией может понадобиться `EXECUTE [master].[sys].[sp_vupgrade_replication];` на первичной (до 2019 CU1).

### 10.6. CU на FCI и в доставке журналов

- **FCI** [MS Learn]: обновлять узлы по одному, начиная с пассивных; установщик сам исключает обновляемый узел из возможных владельцев и, когда обновлено половина узлов или больше, при обновлении следующего переносит группу на обновлённый узел; простой — одно переключение плюс время скриптов обновления. Управление переносом — ключ `/FAILOVERCLUSTERROLLOWNERSHIP` (0 — не переносить и не добавлять узел во владельцы; 1 — переносить и добавлять; 2 — по умолчанию, решает установщик).
- **Доставка журналов** [MS Learn]: сначала все вторичные (монитор — в любой момент), затем первичный: копия журнала с новой версии не восстанавливается на старой. Пока вторичный обновляется, копии журнала копятся на первичном — нужно место. При переходе на **новую версию** вторичная база **не** обновляется до тех пор, пока её не откроют; режим `STANDBY` для базы, требующей обновления до новой версии, не поддерживается — после такого обновления вторичного сервера доставку на `STANDBY`-базу придётся настроить заново (статья Microsoft описывает обновление версии).

## 11. Переход на новую версию SQL Server

### 11.1. Сначала — поддержка 1С

- 8.3.27: SQL Server 2000 SP1 … 2022; при режиме совместимости конфигурации выше 8.3.7 — минимум 2005 и OLE DB Driver актуальной версии или Native Client не младше версии SQL Server [ИТС-КС разд. 1.5.4]. 8.5.1 — то же [`otlichiya-8.5.1`]. v8.1c.ru на 20.10.2026: x86-64 — 2016, 2017, 2019, 2022; 2008 R2, 2012, 2014; 2008 SP1; 2005 SP3 [v8.1c.ru].
- **SQL Server 2025 в требованиях 1С нет** (ни в документации 8.3.27/8.5.1, ни на v8.1c.ru 20.10.2026) [ИТС-КС разд. 1.5.4; v8.1c.ru]. Для баз 1С целевая версия на октябрь 2026 — **SQL Server 2022 с последним CU** [практика]; 2025 — только на стенде, и только после появления в требованиях своей версии платформы (`1cv8upd`, v8.1c.ru).
- Сроки Microsoft: 2016 — расширенная поддержка закончилась 14.07.2026; 2017 — до 12.10.2027; 2019 — до 08.01.2030; 2022 — основная до 11.01.2028, расширенная до 11.01.2033; 2025 — вышла 18.11.2025, основная до 06.01.2031, расширенная до 06.01.2036 [MS Learn, lifecycle; в разметке страниц срок записан как 06:59:59 UTC следующего дня, то есть конец указанного дня по тихоокеанскому времени].

### 11.2. Допустимые пути обновления на месте

| Целевая версия | Обновление на месте возможно с | Источник |
|---|---|---|
| SQL Server 2022 | 2012 SP4, 2014 SP3, 2016 SP3, 2017, 2019 | [MS Learn] |
| SQL Server 2025 | 2014 SP3, 2016 SP3, 2017, 2019, 2022 | [MS Learn] |

Прочее [MS Learn]: только 64-разрядные; обновить 32-разрядный экземпляр до 64-разрядного установщиком нельзя (только перенос базы копией или отсоединением); при обновлении нельзя добавлять компоненты; смешанные версии компонентов Database Engine внутри экземпляра не поддерживаются; в 2025 **нет редакции Web** (Web → Standard или Enterprise), Express 2025 включает возможности бывшего Express with Advanced Services; появились Enterprise Developer и Standard Developer. Более старые версии (для 2022 — 2008 R2 и старше; для 2025 — ещё и 2012) — только перенос базы на новый сервер [MS Learn]. Перед обновлением и 2022, и 2025 требуют, чтобы для SQL Server Agent была включена проверка подлинности Windows, а его учётная запись входила в `sysadmin`, и блокируют обновление при ожидающей перезагрузке или остановленной службе Windows Installer [MS Learn].

### 11.3. На месте или перенос на новый сервер

| | Обновление на месте | Перенос на новый сервер |
|---|---|---|
| Простой | обновление экземпляра и баз | последняя копия журнала и переключение (минуты при доставке журналов или группе) |
| Откат | долгий: экземпляр перезаписан, базу новой версии на старой не открыть | старый сервер нетронут |
| ОС, логины, задания | остаются | новая ОС; `master`/`msdb` переносить вручную |
| Когда | стенды, некритичные серверы | рабочие серверы 1С, смена ОС или «железа», старые версии |

Новая установка снижает риск и простой; при обновлении на месте прежний экземпляр перестаёт существовать [MS Learn]. Для 1С [практика]: рабочие серверы — перенос, на месте — стенды.

**Перенос базы 1С на новый сервер** (команды копий — `mssql/04`):

1. Новый сервер: 2022 с последним CU, сортировка **как на старом**, настройки под 1С (`mssql/02`).
2. Логины с теми же SID и паролями (2.8), роли `processadmin`/`sysadmin` [ИТС-адм разд. 5.2.1.3.2]; задания, операторы, Database Mail, связанные серверы [MS Learn — «Manage metadata when making a database available on another server»]. Помощник — `Start-DbaMigration -Source sql-old -Destination sql01 -BackupRestore -SharedPath \\fs01\sqlbackup` [сторонний], сначала с `-WhatIf` на стенде.
3. Минимальный простой: полная копия → восстановление `WITH NORECOVERY` → журналы `WITH NORECOVERY` (или временная доставка журналов, 7.3) → в окно: блокировка 1С, хвост журнала `WITH NORECOVERY` на старом, `WITH RECOVERY` на новом [MS Learn; практика].
4. `DBCC CHECKDB` [MS Learn]; «сироты»; `SELECT name, compatibility_level, target_recovery_time_in_seconds, is_read_committed_snapshot_on FROM sys.databases;`.
5. В 1С — сменить «Сервер баз данных» каждой ИБ (`rac infobase update --db-server=…`, 3.1) или DNS-имя ⚠; старую базу не удалять до конца гарантийного периода [практика].

Для Enterprise — распределённая группа между старым и новым кластером (2017+ допускает разные версии, первичная — младше или та же) [MS Learn]; для Standard — доставка журналов [MS Learn].

### 11.4. Драйверы на рабочих серверах 1С

- Версия Native Client должна быть не младше версии SQL Server [ИТС-КС разд. 1.5.4]; последний Native Client — 11 (из SQL Server 2012), с 2022 он не поставляется [MS Learn; `../1c-windows/02`, разд. 3.5]. Значит, при переходе на 2014 и новее на всех рабочих серверах 1С должен стоять **OLE DB Driver for SQL Server** [вывод из ИТС-КС разд. 1.5.4 и MS Learn].
- OLE DB Driver 19 по умолчанию шифрует и проверяет сертификат; версии 18 и 19 ставятся рядом (`MSOLEDBSQL`, `MSOLEDBSQL19`); реестровый параметр Force Protocol Encryption и строка подключения — берётся более строгое [MS Learn]. Поддерживает ли 8.3.27 драйвер 19, ИТС не пишет; 8.5.1 знает `MSOLEDBSQL19` [`otlichiya-8.5.1`, п. 16] ⚠.
- SQL Server 2025 по умолчанию использует OLE DB Driver 19 для своих связанных серверов (в том числе в доставке журналов и репликации) — после обновления до 2025 ломаются связанные серверы и удалённые мониторы/дистрибьюторы без доверенного сертификата [MS Learn]. Если у 1С есть внешние источники данных или обработки, работающие через связанные серверы, проверьте их [практика].
- Последние версии драйвера на 20.10.2026: 19.4.3 (9 октября 2026), ветка 18 — 18.7.6 [MS Learn, release notes].

### 11.5. Уровень совместимости базы и оценщик кардинальности

Уровни по умолчанию [MS Learn]: 2025 — 170 (допустимы 170 … 100), 2022 — 160 (160 … 100), 2019 — 150, 2017 — 140, 2016 — 130 (130 … 100), 2014 — 120, 2012 — 110 (110, 100, 90).

- При обновлении на месте, восстановлении или подключении уровень базы **сохраняется**, если он не ниже минимального (90 → 100); `tempdb`, `model`, `msdb` получают уровень новой версии, `master` — прежний; новые базы создаются с уровнем `model` [MS Learn]. Новая ИБ 1С на 2022 получит 160, перенесённые — старый уровень [практика].
- С уровня 130 изменения оптимизатора и **оценщика кардинальности** (CE) включаются только на уровне новой версии; исправления, выпущенные под 4199 для прежних версий, на новом уровне включены по умолчанию [MS Learn]. Модель CE 120 появилась в 2014; уровень 110 и ниже — модель CE 70 [MS Learn].
- Привязка к уровням [MS Learn]: 140 — адаптивные соединения, чередующееся выполнение; 150 — пакетный режим на построчном хранении, обратная связь по памяти, отложенная компиляция табличных переменных, встраивание скалярных UDF; 160 — **PSP** (несколько планов для параметризованного запроса), `CE_FEEDBACK` (`ON` на 160), `DOP_FEEDBACK` (в 2022 — `OFF`; в 2025 по «What's new» включён по умолчанию, хотя справочник `ALTER DATABASE SCOPED CONFIGURATION` по-прежнему пишет `OFF` ⚠ — проверять `sys.database_scoped_configurations`); 170 — `OPTIONAL_PARAMETER_OPTIMIZATION` (`ON` на 170), PSP для DML и `tempdb`. `OPTIMIZED_SP_EXECUTESQL` и `OPTIMIZED_LOCKING` (2025) по умолчанию выключены. Пакетный режим и автоматическая настройка — только Enterprise; PSP и подсказки Query Store — все редакции [MS Learn — таблицы редакций].

**Риски для 1С** [практика ⚠ — рекомендации ИТС по уровню совместимости и CE нет]: 1С генерирует огромное число разных параметризованных запросов с временными таблицами; смена модели оценки или PSP может ускорить большинство запросов и резко замедлить отдельные (отчёты, проведение по регистрам с большими остатками). Поэтому **уровень не поднимают одновременно с обновлением версии**. Оптимизированные блокировки (LAQ действует только при RCSI [MS Learn]; управляемые блокировки 1С на MS SQL используют Read Committed Snapshot [ИТС-разр гл. 9]) для 1С не исследованы ⚠ — не включать на рабочих базах.

**Порядок Microsoft** [MS Learn]: (1) обновить SQL Server, не меняя уровень; (2) Query Store собирает базу сравнения за полный цикл (для учётных баз — минимум закрытие месяца [практика]); (3) поднять уровень; (4) регрессии («Regressed Queries» в SSMS) лечить фиксацией прежнего плана — с 2017 автоматически `AUTOMATIC_TUNING (FORCE_LAST_GOOD_PLAN = ON)`, только Enterprise; (5) не помогло — вернуть уровень.

```sql
-- на первичной, db_owner/sysadmin
SELECT name, compatibility_level FROM sys.databases WHERE name = N'buh';
USE [buh];
SELECT actual_state_desc, desired_state_desc, readonly_reason FROM sys.database_query_store_options;
ALTER DATABASE [buh] SET QUERY_STORE = ON (OPERATION_MODE = READ_WRITE, QUERY_CAPTURE_MODE = AUTO);
-- … сбор базы сравнения …
ALTER DATABASE [buh] SET COMPATIBILITY_LEVEL = 160;   -- откат: прежнее значение, например 150
```

При смене уровня все хранимые процедуры базы перекомпилируются [MS Learn] — у 1С волна компиляций в первые минуты [практика]. `READ_ONLY` при `readonly_reason` = 65536 — у Query Store кончилось место [MS Learn]; настройки — `mssql/06`.

**Точечные «откаты» без смены уровня** [MS Learn]:

| Средство | Область | Версия |
|---|---|---|
| `ALTER DATABASE SCOPED CONFIGURATION SET LEGACY_CARDINALITY_ESTIMATION = ON;` | вся база — CE 70 при прочих улучшениях (как флаг 9481) | 2016+ |
| `EXEC sys.sp_query_store_set_hints @query_id = <id>, @query_hints = N'OPTION(USE HINT(''FORCE_LEGACY_CARDINALITY_ESTIMATION''))';` (снять — `sys.sp_query_store_clear_hints`) | один запрос без изменения текста | 2022+ |
| `sys.sp_query_store_force_plan` / `sys.sp_query_store_unforce_plan` (или «Force Plan» в SSMS) | один запрос | 2016+ |
| `ALTER DATABASE SCOPED CONFIGURATION SET PARAMETER_SENSITIVE_PLAN_OPTIMIZATION = OFF;` | PSP в базе | 2022+ |
| `ALTER DATABASE SCOPED CONFIGURATION SET OPTIONAL_PARAMETER_OPTIMIZATION = OFF;` | OPPO | 2025 |

Подсказки в тексте запросов 1С недоступны (их генерирует платформа) — остаются настройки базы и средства Query Store [практика]; фиксация по `query_id` для 1С может быть ненадёжной: текст меняется с именами временных таблиц ⚠. Синтаксис `sp_query_store_force_plan` — Подтверждено 20.10.2026 (MS Learn): `@query_id`, `@plan_id` (bigint), необязательные `@disable_optimized_plan_forcing`, `@replica_group_id`. Query Store на вторичных: в 2022 — ограниченная предварительная версия (флаг 12606, не для рабочих сред), в 2025 — доступен (Enterprise), но статья Microsoft о функции по-прежнему помечает её как предварительную версию [MS Learn].

**Флаг 4199.** 1С рекомендует включать глобально всегда [ИТС-мет 5946, 2019]; на SQL Server 2014 платформа сама пытается включать его для каждого соединения [ИТС-адм разд. 5.2.1.3.2]. Microsoft: на новом уровне исправления до выхода версии уже включены, после обновления «проверьте, что 4199 не включён»; исправления из CU по-прежнему требуют 4199 или `QUERY_OPTIMIZER_HOTFIXES = ON` (2016+) [MS Learn]. Компромисс [практика]: на 2016+ следовать 1С, но вводить флаг через замер на стенде; на 2014 — обязательно.

### 11.6. Скользящее обновление версии в группе доступности

Порядок тот же, что для CU (10.5) [MS Learn], но с важными отличиями смены **версии**:

- После планового переключения на реплику новой версии базы проходят **обновление до новой версии**; пока оно идёт, читаемых реплик нет; при обратном переключении на исходную (уже обновлённую) первичную этот шаг не повторяется [MS Learn].
- Обновлённая на месте вторичная держит базы в состоянии «Synchronizing/Synchronized / In Recovery» до переключения на неё [MS Learn].
- После переключения на новую версию первичная **не может** передавать журнал вторичным старой версии — пока они не обновлены, синхронизации и автоматического переключения нет, данные уязвимы [MS Learn]. Поэтому сначала обновляют **все** вторичные, затем переключаются.
- Смешение версий в группе — только на время обновления; копии на обновляемой базе не делаются; при версионном обновлении ни одна реплика не читается [MS Learn].
- Если группа построена только для аварийного восстановления (единственная удалённая асинхронная реплика), перед переключением её переводят в синхронный режим и ждут `SYNCHRONIZED`, а потом возвращают асинхронный [MS Learn].
- Обновление Windows Server на узлах WSFC — отдельная процедура (Cluster OS Rolling Upgrade, с Windows Server 2012 R2) [MS Learn].

Для 1С [практика]: точка невозврата — плановое переключение на реплику новой версии. До неё откат — просто не переключаться; после — только восстановление из копии на сервере старой версии (копия **новой** версии на старой не восстановится). Поэтому перед переключением — свежая полная копия на старой версии и проверенный план отката.

### 11.7. Обновление версии FCI

Установщиком на каждом узле по очереди, начиная с пассивных; при обновлении половины и более узлов установщик переносит FCI на обновлённый узел (управление — `/FAILOVERCLUSTERROLLOWNERSHIP`, 10.6); простой — одно переключение плюс скрипты обновления баз [MS Learn]. Нельзя: превратить одиночный экземпляр в FCI обновлением, добавить компоненты при обновлении, понизить FCI до одиночного экземпляра; ключ продукта на всех узлах один [MS Learn]. Командная строка обновления — `setup.exe /q /ACTION=Upgrade /INSTANCENAME=MSSQLSERVER /INSTANCEID=<ID экземпляра> /IACCEPTSQLSERVERLICENSETERMS …` (`/INSTANCEID` по справке обязателен при обновлении с 2008 и новее; полный набор ключей — `mssql/02`) [MS Learn].

## 12. Перенос баз 1С с MS SQL на PostgreSQL (кратко)

Для вашей площадки это основной сценарий: серверы 1С на Linux с MS SQL не работают [ИТС-КС разд. 2.3], целевая СУБД — «PostgreSQL для 1С» 16 (`en_US.UTF-8`). Подробно — `../1c/06-infobazy-ibcmd-paketnyj-rezhim.md` (разд. 3.5), `../1c/10-proizvoditelnost-otkazoustojchivost-ekspluataciya.md` (разд. 7), `../postgresql/01-sborki-postgresql-dlya-1c-ustanovka.md`, `../guides/07-postgresql-dlya-1c-s-1c-postgres-ru.md`, `../1c-windows/02-ms-sql-server-dlya-1c.md` (разд. 12.2).

- **`ibcmd infobase replicate`** (8.3.23+) — перенос клиент-серверной базы между СУБД без `.dt` (из файловой — нельзя) [ИТС-адм прил. 4, разд. 4.10.4.6; разд. 7.4.17]. Источник — общие параметры `--dbms`, `--database-server`, `--database-name`, `--database-user`, `--database-password` / `--request-database-password`, `--data` [ИТС-адм прил. 4, разд. 4.10.2]; приёмник — `--target-…`, `--target-create-database`; `--jobs-count`/`--target-jobs-count` (по умолчанию — число ядер), `--batch-size` (10 000), `--batch-data-size` (10 485 760), `--force` [ИТС-адм прил. 4, разд. 4.10.4.6].
- **Где запускать:** автономный сервер на Linux с MS SQL не работает [ИТС-адм разд. 7.2] → `ibcmd.exe` на Windows-машине с той же версией платформы; в `pg_hba.conf` приёмника разрешить её адрес [`../1c-windows/02`, разд. 12.2]. Если база в группе доступности — источник через листенер, пользователей в базе нет [практика].
- **Через `.dt`**: выгрузка → новая ИБ в PostgreSQL → загрузка; перед выгрузкой — тестирование и исправление; в `.dt` попадают и данные хранилищ двоичных данных [ИТС-адм разд. 6.7–6.8].

```bat
:: Windows, cmd; пароли запрашиваются из stdin
ibcmd infobase replicate --data=D:\ss-data\replicate --dbms=MSSQLServer --database-server=ag-buh ^
  --database-name=buh --database-user=buh_1c --request-database-password ^
  --target-dbms=PostgreSQL --target-database-server=srv-1c-db --target-database-name=buh ^
  --target-database-user=buh_1c --target-request-database-password --target-create-database ^
  --jobs-count=4 --target-jobs-count=4 --force
```

- **После:** регистрация базы в кластере 1С на Linux без `--create-database`, регламентные задания до проверки — `--scheduled-jobs-deny=on` [`../1c/10`, разд. 7.4]; `vacuumdb --analyze` [`../postgresql/05`]; журнал регистрации и хранилище двоичных данных — отдельно [`../1c/10`, разд. 7.7]; смещение дат в PostgreSQL не используется [`../1c/10`, разд. 7.1]. Отказоустойчивость новой стороны — `../postgresql/07`.

## Типичные ошибки (симптом → причина → решение)

| # | Симптом | Причина | Решение |
|---|---|---|---|
| 1 | После переключения 1С: ошибка входа `buh_1c` | логина нет на новой первичной или другой SID («сирота») [MS Learn] | логин с тем же SID; `ALTER USER [buh_1c] WITH LOGIN = [buh_1c];` (2.8) |
| 2 | После переключения не идут копии и регламент | задания Agent не реплицируются [MS Learn] | задания на всех репликах с `sys.fn_hadr_is_primary_replica` (2.8) |
| 3 | Подключение к листенеру 15–30 с или тайм-аут | многоподсетевой листенер, клиент без `MultiSubnetFailover` [MS Learn] | одна подсеть; `RegisterAllProvidersIP = 0`, `HostRecordTTL = 300`; OLE DB Driver (3.2) |
| 4 | После переключения между подсетями 1С долго «не видит» сервер | кеш DNS-записи листенера (20 мин по умолчанию) [MS Learn] | уменьшить `HostRecordTTL`; `ipconfig /flushdns` [практика] |
| 5 | Удаление ИБ с базой из консоли 1С — ошибка | базу в группе удалить нельзя [MS Learn] | `REMOVE DATABASE`, `DROP DATABASE` на вторичных (5.2) |
| 6 | Растёт журнал, `log_reuse_wait_desc = AVAILABILITY_REPLICA` | вторичная отстаёт, отключена, приостановлена или идёт заполнение [MS Learn] | `SET HADR RESUME` или убрать реплику; копии журнала не прекращать (5.5) |
| 7 | Проведение стало медленнее, растёт `HADR_SYNC_COMMIT` | синхронная фиксация ждёт медленный диск или сеть вторичной [MS Learn] | быстрый диск журнала на вторичной; удалённые реплики — асинхронные (2.4) |
| 8 | Первичная упала, автопереключения нет | вторичная не `SYNCHRONIZED`, режим `MANUAL`, реплика на FCI, нет кворума, превышен порог отказов [MS Learn] | `is_failover_ready`, режимы, `sys.dm_hadr_cluster_members`; при необходимости принудительное переключение (4.4) |
| 9 | База `SUSPECT`, а переключения нет | `DB_FAILOVER = OFF` по умолчанию [MS Learn] | `ALTER AVAILABILITY GROUP … SET (DB_FAILOVER = ON);` |
| 10 | После принудительного переключения вторичные `SUSPENDED` | так работает `FORCE_FAILOVER_ALLOW_DATA_LOSS` [MS Learn] | оценить потери, затем `SET HADR RESUME` на каждой вторичной |
| 11 | Не поднимается сетевое имя листенера | у CNO нет права Create Computer objects, лимит 10 объектов, совпали первые 15 символов имён [MS Learn] | права CNO в OU, чистка старых объектов, короткое имя |
| 12 | Загрузка `.dt` в базу в группе очень долгая | полная модель, весь объём — в журнал и на вторичные [ИТС-адм разд. 6.8; MS Learn] | вывести из группы, `SIMPLE`, загрузить, `FULL`, копия, вернуть (5.3) |
| 13 | После повышения уровня совместимости часть запросов 1С в разы медленнее | новые правила оптимизатора и CE [MS Learn] | Query Store: фиксация плана, `LEGACY_CARDINALITY_ESTIMATION`, отключить PSP; откат уровня (11.5) |
| 14 | После OLE DB Driver 19 / перехода на 2025 — ошибка сертификата | драйвер 19 по умолчанию шифрует и проверяет сертификат; в сертификате нет имени листенера [MS Learn] | сертификат доменного УЦ с SAN узлов и листенеров (3.3) |
| 15 | На новом сервере: «Компоненты OLE DB провайдера не найдены» | нет провайдера на рабочем сервере 1С [ИТС-КС разд. 1.5.4] | OLE DB Driver на все рабочие серверы 1С |
| 16 | Копия БД 1С (`Версия2`) не обновляется после переключения | задания CDC остались на прежней первичной [MS Learn] | `sys.sp_cdc_add_job` для `capture` и `cleanup` (5.6) |
| 17 | При скользящем обновлении вторичные не синхронизируются | первичную обновили раньше вторичных [MS Learn] | обновить вторичные, `SET HADR RESUME`; порядок — 10.5 |
| 18 | После переключения доставки журналов 1С ходит на старый сервер | в ИБ указан конкретный сервер СУБД [практика] | `rac infobase update --db-server=…` или DNS-имя (7.2) |
| 19 | После переключения FCI первые минуты всё медленно | экземпляр перезапущен: пустые кеши [MS Learn — механика] | ожидаемо; косвенные контрольные точки (6.2) |
| 20 | В базовую группу не добавляется вторая база | базовая группа — одна база [MS Learn] | отдельная группа и листенер на каждую ИБ |

| Доставка журналов | `msdb.dbo.log_shipping_monitor_secondary` (`last_restored_date`); переключение — `BACKUP LOG … WITH NORECOVERY`, `RESTORE DATABASE [buh] WITH RECOVERY` |
