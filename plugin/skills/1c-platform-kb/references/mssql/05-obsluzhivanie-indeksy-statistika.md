## Кратко — главные факты

1. **Что разрешено на уровне СУБД**: проверка целостности, реиндексация, дефрагментация, реорганизация, резервное копирование, очистка процедурного кеша, сбор статистики [ИТС-КС разд. 5.5.8]. Сжатие данных средствами СУБД ИТС допускает только для Oracle [ИТС-КС разд. 5.5.4] — `DATA_COMPRESSION` в базах 1С не применять ⚠ (трактовка).
2. **Регламенты СУБД и 1С не заменяют друг друга**: «Тестирование и исправление ИБ» — логическая и ссылочная целостность, пересчёт итогов, реиндексация, почти всегда монопольно [ИТС-адм разд. 6.10.2]; `DBCC CHECKDB` — целостность страниц и структур SQL Server [MS Learn].
3. **Базы 8.3.22+: страничные блокировки индексов выключены** — перед дефрагментацией их включают, после выключают [ИТС-мет 5837, 2022]. `REORGANIZE` и `DBCC INDEXDEFRAG` при `ALLOW_PAGE_LOCKS = OFF` невозможны; `REBUILD` без явного параметра сохраняет значения из `sys.indexes`, то есть `OFF` [MS Learn].
4. **Редакции**: онлайн- и возобновляемое перестроение, параллельные операции с индексами и параллельная проверка целостности — только Enterprise (и Developer) в 2022 и 2025 [MS Learn]. В Standard `REBUILD` держит Sch-M на таблицу всё время — только в окно.
5. **Фрагментация сама по себе не повод**: Microsoft не даёт фиксированных порогов, советует мерить эффект; часто выигрыш от перестроения — свежая статистика [MS Learn]. Пороги: 25 % [ИТС-мет 1794, 2007]; 10/30 % — «произвольная точка» в примере Microsoft [MS Learn]; 5/30 % и 1000 страниц — Ola Hallengren [сторонний].
6. **Плотность страниц** часто важнее фрагментации [MS Learn]; режим `LIMITED` её не возвращает — нужен `SAMPLED`/`DETAILED`.
7. **`FILLFACTOR`**: умолчание 0 (= 100), снижать только для индексов с частыми разделениями страниц (например, ведущий неупорядоченный GUID) [MS Learn]; кластерные индексы объектных таблиц 1С — по «Ссылке» [ИТС-мет, `razmeshchenie-dannyh-i-indeksy`] — менять только по замеру.
8. **Автостатистика**: `AUTO_CREATE_STATISTICS` и `AUTO_UPDATE_STATISTICS` по умолчанию `ON`, не выключать; порог автообновления с 2016 при уровне совместимости ≥ 130 — `MIN(500 + 0,20·n; SQRT(1000·n))`, ниже — `500 + 0,20·n` (или флаг 2371) [MS Learn].
9. **`FULLSCAN`**: 1С требует ежедневно обновлять статистику полным просмотром [ИТС-мет 5837, 2022], Microsoft считает обычно достаточной выборку [MS Learn]. Для 1С — `FULLSCAN` только изменившихся статистик и явный `MAXDOP` (2016 SP2/2017 CU3+), т. к. на сервере `max degree of parallelism = 1` [ИТС-мет 5904, 2019].
10. **`sp_updatestats`** — только изменившиеся статистики и **выборкой по умолчанию** [MS Learn]; после `REBUILD`/`FULLSCAN` он ухудшит статистику [вывод]. После восстановления базы на 2022 — один раз выполнить (метаданные `AUTO_DROP`) [MS Learn].
11. **Сначала индексы, потом статистика**: перестроение обновляет статистику индекса полным просмотром, реорганизация — нет, столбцовую статистику не трогает ни то, ни другое [MS Learn].
12. **Асинхронное автообновление** 1С советует включать в `model` [ИТС-мет 5904, 2019]; Microsoft предупреждает о блокировках Sch-M при частых компиляциях, с 2022 — `ASYNC_STATS_UPDATE_WAIT_AT_LOW_PRIORITY` [MS Learn].
13. **Кеш планов**: `DBCC FREEPROCCACHE` [ИТС-мет 5837] очищает **весь экземпляр**; с 2016 — `ALTER DATABASE SCOPED CONFIGURATION CLEAR PROCEDURE_CACHE` для базы, с 2019 — для одного `plan_handle` [MS Learn]. Зависимые планы после обновления статистики перекомпилируются сами [MS Learn].
14. **Кеш планов чистит и `RECONFIGURE`** `max degree of parallelism`, `max server memory`, `cost threshold for parallelism` и др. [MS Learn] — например, при смене MAXDOP на время реструктуризации [ИТС-мет 5945, 2018].
15. **`DBCC CHECKDB`** работает по внутреннему снимку (с 2014 — разреженные файлы `<файл>_MSSQL_DBCC<id>` рядом с базой); `PHYSICAL_ONLY` — часто, полная — периодически; при ошибках — восстановление из копии, `REPAIR_ALLOW_DATA_LOSS` — крайняя мера [MS Learn].
16. **Последняя успешная проверка** — `DATABASEPROPERTYEX(N'buh', 'LastGoodCheckDbTime')` (2016 SP2, 2017 CU9, 2019+) [MS Learn]; полную проверку удобно делать на восстановленной копии [практика].
17. **Устаревшее**: `DBCC INDEXDEFRAG`, `DBCC DBREINDEX` → `ALTER INDEX` [MS Learn]; `sp_msforeachtable` не документирована [практика]; флаги 2371 (при уровне совместимости ≥ 130), 1117, 1118, 8048 на 2016+ не действуют, 610 не нужен (минимальное журналирование включено по умолчанию) [MS Learn; ИТС-мет 5946].
18. **Планы обслуживания** — пакет SSIS, выполняемый агентом; в Express агента нет [MS Learn]; «Reorganize Index Task» на базах 8.3.22+ падает [вывод].
19. **Ola Hallengren `IndexOptimize`** при выключенных страничных блокировках вместо реорганизации берёт следующее действие списка — по умолчанию онлайн-, а в Standard **офлайн-перестроение**; установщик создаёт задания **без расписаний**, задание индексов статистику по умолчанию не обновляет [сторонний, код].
20. **Окно**: офлайн-`REBUILD`, полную `CHECKDB` и полную копию не совмещать с рабочими часами, ночными заданиями 1С и закрытием периода; `BACKUP LOG` во время регламента не останавливать [практика].
21. **`tempdb`** нагружают `SORT_IN_TEMPDB`, онлайн-перестроение, `CHECKDB` (оценка — `WITH ESTIMATEONLY`) и версии строк RCSI [MS Learn].
22. **Автоприращение — страховка**: размеры заранее, `AUTO_SHRINK` выключен, сжатие фрагментирует индексы; IFI — для данных, для журнала с 2022 до 64 МБ [MS Learn].
23. **Фантомные записи** удаляет один фоновый поток на экземпляр; флаг 661 его выключает — постоянно не рекомендуется [MS Learn].
24. **SQL Server на Linux**: агент с 2017 CU4 входит в `mssql-server`, выключен по умолчанию (`mssql-conf set sqlagent.enabled true`), подсистема SSIS не поддерживается [MS Learn] — регламент T-SQL-шагами.

## 1. Кто что обслуживает: СУБД и 1С

### 1.1. Что разрешено на уровне СУБД

ИТС в разделе «Администрирование СУБД» перечисляет действия, которые не влияют на работоспособность прикладного решения и не затрагивают представление структуры данных, которое использует «1С:Предприятие», включая реструктуризацию [ИТС-КС разд. 5.5.1]. Для Microsoft SQL Server там названы:

| Действие | Раздел | Комментарий для регламента |
|---|---|---|
| Шифрование средствами СУБД | 5.5.2 (2008 и новее) | к обслуживанию не относится |
| Кластер серверов СУБД | 5.5.3 | `07-otkazoustojchivost-…` |
| Перенос файла базы данных и журнала | 5.5.6, 5.5.7 | `02-ustanovka-…` |
| Проверка целостности, реиндексация, дефрагментация, реорганизация, резервное копирование, очистка процедурного кеша, сбор статистики | 5.5.8 | предмет этой статьи |
| Сжатие данных | 5.5.4 — **только Oracle** | `DATA_COMPRESSION = ROW/PAGE` для MS SQL не указано ⚠ |

Источник: [ИТС-КС разд. 5.5.2–5.5.8].

Чего в списке нет и что, следовательно, делать не нужно [вывод из ИТС-КС разд. 5.5.1]: создавать свои индексы и статистики, менять ключи и состав индексов, секционировать таблицы, менять параметры столбцов. Индексы базы определяет платформа по свойствам объектов конфигурации (раздел 1.3); недостающий индекс добавляется через конфигурацию (свойство «Индексировать» и т. п.), а не в SSMS [практика]. Подсказки `sys.dm_db_missing_index_*` использовать как материал для разработчика, а не как готовую команду [практика].

| Профилактический пересчёт итогов | записи итогов с нулевыми ресурсами копятся и замедляют запросы — пересчитывать регулярно | [ИТС-мет 5371, 2013] |
| Монопольный режим | не переводит базу MS SQL в `SINGLE_USER` | [ИТС-адм разд. 6.10.2] |

Какие команды SQL Server выполняет реиндексация 1С — не описано ⚠; из-за монопольного режима для регламента в рабочее время она не подходит [вывод]. Аналога `/IBCheckAndRepair` в `ibcmd` 8.3.27 нет: в группе `infobase config` — только проверка конфигурации `check` и восстановление после незавершённой операции `repair` [ИТС-адм прил. 4, разд. 4.10.4.7.4, 4.10.4.7.7]; утилита административной консоли `1cv8a ib-check-and-repair` выполняет лишь ограниченный набор проверок — узлы планов обмена, история данных, хеш-поля итогов, без реиндексации [ИТС-адм прил. 4, разд. 4.6] (уточнено 20.10.2026 по полному тексту прил. 4).

Разделение обязанностей [практика]: **СУБД** — индексы, статистика, `DBCC CHECKDB`, кеш планов, рост файлов, `tempdb` (заданиями агента, без остановки работы, кроме офлайн-перестроения); **1С** — тестирование и исправление после сбоев питания и оборудования [ИТС-адм разд. 6.10.1], пересчёт итогов, перестроение агрегатов в часы минимальной нагрузки [`../its-docs/dev-gl05-obekty-konfiguracii.md`], удаление помеченных (`../its-metod/medlennye-operacii-zadaniya-vremennye-fajly-hranilishche.md`). После любого «ремонта» средствами СУБД (8.7) — тестирование и исправление 1С: `REPAIR_ALLOW_DATA_LOSS` не учитывает связи между таблицами [MS Learn], а ссылочную целостность данных 1С проверяет только платформа [ИТС-адм разд. 6.10.2] [вывод].

### 1.3. Особенности баз 1С, важные для регламента

- **Состав индексов определяет платформа.** У объектных таблиц (справочники, документы, планы счетов и др.) кластерный индекс всегда по полю «Ссылка» (с полями независимых разделителей), у табличных частей — «Ссылка + Ключ»; у регистров сведений основной индекс включает все измерения в порядке конфигуратора, у периодических — ещё «Период» (у непериодического регистра, подчинённого регистратору, кластерный — «Регистратор + НомерСтроки»); у основной таблицы регистров накопления кластерный индекс — «Период + Регистратор + НомерСтроки» (так же у регистра бухгалтерии) [ИТС-мет, конспект `../its-metod/razmeshchenie-dannyh-i-indeksy.md`, разд. 2.7–2.8]. Индексы часто широкие, а кластерный ключ по «Ссылке» — 16-байтовый идентификатор (`binary(16)` — практика, в прочитанных источниках тип не указан ⚠); насколько последовательно платформа генерирует значения «Ссылки» на MS SQL, в документации не сказано ⚠ — от этого зависят разделения страниц и смысл `FILLFACTOR` (раздел 5).
- **Ограничения ключа**: в индексе не более 16 полей; одна запись индекса на MS SQL — не более 900 байт, ошибка возникает при вставке, а не при обновлении конфигурации [ИТС-разр прил. 8, разд. 8.1, 8.4].
- **Уровни изоляции.** В режиме управляемых блокировок на SQL Server 2005+ платформа работает в Read Committed Snapshot, в автоматическом — Repeatable Read или Serializable [ИТС-разр гл. 9, разд. 9.2.3.2]. При `READ_COMMITTED_SNAPSHOT = ON` каждая строка при изменении получает до 14 байт версии, что может вызывать разделения страниц, а версии строк хранятся в `tempdb` (при включённом ADR — в самой базе, в постоянном хранилище версий PVS) [MS Learn]. Включает ли платформа `READ_COMMITTED_SNAPSHOT` для базы сама — ⚠ (см. `../1c-windows/02-…`); проверка: `SELECT is_read_committed_snapshot_on FROM sys.databases WHERE name = N'buh';`.
- **Временные таблицы.** Платформа широко использует временные таблицы, а `tempdb` нужна и для сортировок и группировок [ИТС-мет 2374, 2008].
- **MAXDOP.** Для 1С на уровне сервера `max degree of parallelism = 1` [ИТС-мет 5904, 2019; 6008, 2023]; регламентные команды поэтому без явного `MAXDOP` выполняются в один поток (раздел 3.6).
- **8.3.22+**: выключенные страничные блокировки индексов (раздел 4).
- **База создаётся из `model`**: параметры автоприращения, модель восстановления, асинхронное обновление статистики наследуются от `model` [ИТС-мет 5904, 2019]. Уточнено 20.10.2026 по MS Learn (ALTER DATABASE compatibility level): новая база получает уровень совместимости по умолчанию для версии движка, если у `model` он не ниже, иначе — уровень `model`; задаёт ли платформа 1С уровень явно при создании базы — не описано ⚠. Базы, подключённые или восстановленные со старых серверов, сохраняют прежний уровень (если он не ниже минимально допустимого) — от него зависят порог автообновления статистики (раздел 6.2) и исправления оптимизатора [MS Learn].

### 1.5. Смешанная среда и SQL Server на Linux

- Рабочий процесс кластера 1С на Linux не может взаимодействовать с MS SQL Server [ИТС-КС разд. 2.3]; MS SQL не поддерживается и при кластере на процессорах ARM64 или E2K [ИТС-КС разд. 1.5.4]. Значит, при SQL Server на Linux рабочие серверы 1С — на Windows.
- SQL Server Agent на Linux: с 2017 CU4 входит в пакет `mssql-server` и **по умолчанию выключен**; включение — `sudo /opt/mssql/bin/mssql-conf set sqlagent.enabled true` [MS Learn] (от имени `root` через `sudo`, затем `sudo systemctl restart mssql-server` — подтверждено 20.10.2026 по MS Learn, «Install SQL Server Agent on Linux»; там же: имя хоста с доменом и без него должно быть в `/etc/hosts`).
- На Linux у агента не поддерживаются подсистемы CmdExec, PowerShell, SSIS и др., не поддерживаются оповещения агента (Alerts) [MS Learn]. Планы обслуживания — это пакеты SSIS, которые выполняет агент [MS Learn], поэтому на Linux они не подойдут [вывод] ⚠; регламент — шагами T-SQL (скрипты раздела 12 или Ola Hallengren — его установщик для Linux создаёт задания с выводом в файл [сторонний, код]).
- Онлайн-перестроение и возобновляемые операции на Linux — тоже только Enterprise [MS Learn, редакции SQL Server на Linux 2022/2025].
- Сами команды `ALTER INDEX`, `UPDATE STATISTICS`, `DBCC CHECKDB` от ОС не зависят; отличаются пути к файлам и способ запуска (`sqlcmd` из пакета `mssql-tools18` — подтверждено 20.10.2026 по MS Learn, `linux/install-upgrade/setup-tools`; см. также `03-administrirovanie-…`).

## 2. Фрагментация и плотность страниц: когда это важно

### 2.1. Понятия

- **Логическая фрагментация** — в индексе-B-дереве логический порядок страниц по ключу не совпадает с физическим. Возникает при вставках, изменениях и удалениях, в первую очередь из-за разделения страниц (page split) [MS Learn]. Мешает запросам, которые читают много страниц (полный или диапазонный просмотр индекса): вместо нескольких крупных операций ввода-вывода нужно много мелких, и упреждающее чтение работает хуже [MS Learn].
- **Плотность страниц** (заполненность) — доля полезных данных на странице. При низкой плотности те же данные занимают больше страниц: больше ввода-вывода и памяти буферного пула, может вырасти число промежуточных уровней B-дерева, оптимизатор оценивает стоимость чтения выше и может выбрать другой план [MS Learn].
- **Разделение страницы (page split)** — при вставке в полную страницу примерно половина строк переносится на новую; дорогая операция, если происходит в середине индекса, и источник фрагментации [MS Learn].
- **Фантомные записи (ghost)** — удалённые строки, физически ещё лежащие на странице до фоновой очистки (раздел 14.3) [MS Learn].

Microsoft: во многих нагрузках повышение плотности страниц даёт больший эффект, чем снижение фрагментации [MS Learn]. На хранилищах, где последовательное и случайное чтение одинаково быстры (типично для SSD и облачных дисков), влияние фрагментации меньше [MS Learn — сказано про Azure SQL; для локальных SSD — вывод].

### 2.2. Как измерить

`sys.dm_db_index_physical_stats(database_id, object_id, index_id, partition_number, mode)` [MS Learn]:

| Режим | Что читает | Что возвращает |
|---|---|---|
| `LIMITED` (умолчание, `NULL`) | только страницы над листовым уровнем (у кучи — PFS и IAM) | фрагментацию и размер; **`avg_page_space_used_in_percent`, `ghost_record_count`, `version_ghost_record_count` — `NULL`** |
| `SAMPLED` | выборку 1 % страниц; у индекса меньше 10 000 страниц — все страницы (как `DETAILED`) | всё, приблизительно |
| `DETAILED` | все страницы | всё, точно; долго на больших таблицах |

Функция берёт только блокировку намерения IS на таблицу в любом режиме; на читаемой вторичной реплике группы доступности эта IS может блокировать поток REDO [MS Learn]. Права: `VIEW DATABASE STATE` (в 2022 — или `VIEW DATABASE PERFORMANCE STATE`) для всех объектов базы [MS Learn].

Запрос для базы 1С — крупные индексы, листовой уровень, вместе с признаками, нужными для выбора действия [MS Learn — столбцы; запрос — практика]:

```sql
USE [buh];   -- sysadmin / db_owner или VIEW DATABASE STATE
SELECT OBJECT_SCHEMA_NAME(ips.object_id) AS schema_name,
       OBJECT_NAME(ips.object_id)        AS table_name,
       i.name                            AS index_name,
       i.type_desc,
       i.allow_page_locks,               -- 0 у баз 8.3.22+ (раздел 4)
       i.fill_factor,                    -- 0 = 100 %
       ips.page_count,
       CAST(ips.avg_fragmentation_in_percent  AS decimal(5,1)) AS frag_pct,
       CAST(ips.avg_page_space_used_in_percent AS decimal(5,1)) AS density_pct,
       ips.ghost_record_count, ips.version_ghost_record_count
FROM sys.dm_db_index_physical_stats(DB_ID(), NULL, NULL, NULL, 'SAMPLED') AS ips
JOIN sys.indexes AS i ON i.object_id = ips.object_id AND i.index_id = ips.index_id
WHERE ips.index_id > 0                      -- без куч
  AND ips.alloc_unit_type_desc = N'IN_ROW_DATA'
  AND ips.index_level = 0                   -- нелистовые уровни возвращаются только в DETAILED
  AND ips.page_count >= 1000
ORDER BY ips.page_count DESC;
```

На базе в сотни гигабайт `SAMPLED` по всей базе идёт долго и читает диск — запускать вне рабочих часов или по списку таблиц (`OBJECT_ID(N'dbo._Document123')` во втором параметре) [практика].

**Разделения страниц по индексам** — `sys.dm_db_index_operational_stats`: `leaf_allocation_count` (для индекса выделение страницы листового уровня соответствует разделению) и `nonleaf_allocation_count` [MS Learn]. Счётчики живут, пока метаданные объекта в кеше, и обнуляются при повторной загрузке — это не история, а «с момента …» [MS Learn]:

```sql
USE [buh];
SELECT TOP (30) OBJECT_NAME(os.object_id) AS table_name, i.name AS index_name,
       os.leaf_allocation_count, os.nonleaf_allocation_count,
       os.page_lock_wait_count, os.row_lock_wait_count
FROM sys.dm_db_index_operational_stats(DB_ID(), NULL, NULL, NULL) AS os
JOIN sys.indexes AS i ON i.object_id = os.object_id AND i.index_id = os.index_id
WHERE os.index_id > 0
ORDER BY os.leaf_allocation_count DESC;
```

Обращения к индексам — `sys.dm_db_index_usage_stats` (поиски, просмотры, обновления); счётчики обнуляются при каждом запуске SQL Server [MS Learn]. В методичке 1С по загрузке CPU на его основе ищут «индексы с высокими издержками» (много обновлений, мало чтений) [ИТС-мет 5861, 2015] — для базы 1С это повод для разговора с разработчиком, а не для удаления индекса [практика]. Флаг 2330, которым ИТС предлагает отключать сбор этой статистики, — **недокументированный** [ИТС-мет 5946, 2019]; в документации Microsoft его нет [MS Learn].

### 2.3. Когда обслуживание индексов даёт эффект

Стратегия Microsoft [MS Learn]: не считать, что обслуживание индексов всегда помогает; измерять эффект на своей нагрузке (Query Store «до/после» — `06-monitoring-i-diagnostika.md`); если помогло перестроение — попробовать заменить его обновлением статистики; следить за фрагментацией и плотностью во времени и обслуживать в первую очередь индексы медленных запросов; частоту определять по замерам, а не «по календарю»; выполнять в часы малой нагрузки.

Почему «после реиндексации стало быстрее»: перестроение обновляет статистику ключевых столбцов полным просмотром, и зависимые планы перекомпилируются; эффект ошибочно приписывают дефрагментации, хотя обновление статистики даёт его за минуты вместо часов [MS Learn].

Фрагментация практически не важна [MS Learn]: у маленьких индексов (их обслуживание фрагментацию обычно не снижает); при нагрузке без крупных просмотров (главный эффект фрагментации — хуже упреждающее чтение); на хранилищах без разницы между последовательным и случайным чтением.

Стоит заняться [MS Learn; практика для 1С]: после массовых удалений и изменений (удаление помеченных, свёртка, перепроведение, загрузка данных) — проверить фрагментацию **и плотность**; если отчёты по большим диапазонам регистров замедлились при тех же планах; если плотность крупных индексов заметно ниже `FILLFACTOR` (лишние гигабайты в буферном пуле).

Автоматическое уплотнение индексов (`ALTER DATABASE … SET AUTOMATIC_INDEX_COMPACTION = ON`) на 08.10.2026 есть **только в Azure SQL Database, Managed Instance и SQL database in Fabric** [MS Learn]; в SQL Server 2016–2025 его нет.

### 2.4. Пороги: откуда цифры

| Источник | Порог | Статус |
|---|---|---|
| [ИТС-мет 1794, 2007] (SQL Server 2005) | `avg_fragmentation_in_percent` > 25 % — дефрагментировать | исторический ориентир |
| [ИТС-мет 2372, 2008] | днём дефрагментация (`DBCC INDEXDEFRAG`), ночью реиндексация (`DBCC DBREINDEX`) | команды устарели (раздел 9) |
| [ИТС-мет 5837, 2022] | порогов нет: дефрагментация не реже раза в неделю, реиндексация — раз в неделю в минимальную нагрузку | частота «по календарю» — см. 2.3 |
| [MS Learn], пример скрипта к `sys.dm_db_index_physical_stats` | обрабатывать > 10 %; ≥ 30 % — `REBUILD`, иначе `REORGANIZE`; 30 % названо «произвольной точкой переключения» | пример, не рекомендация |
| [MS Learn], текущая статья об обслуживании индексов | фиксированных порогов нет; решение по нескольким факторам, включая стоимость | действующая позиция |
| Планы обслуживания SSMS 2016+ | фильтры «Fragmentation > (%)», «Page Count >», «Used in last (days)»; режим сканирования Fast/Sampled/Detailed [MS Learn] | инструмент |

Стартовые значения для базы 1С [практика]: обрабатывать только индексы от 1000 страниц (≈ 8 МБ); реорганизация при фрагментации от 10–15 % **или** плотности ниже ~75 %; перестроение — при фрагментации от 30–40 % или плотности ниже ~60 %, в Standard — только в окне; через 2–4 недели сравнить длительность ключевых запросов (Query Store) и поправить пороги. Эти цифры — не из первоисточника, а отправная точка для замеров.

## 3. `REORGANIZE` и `REBUILD`

### 3.1. Сравнение

| | `ALTER INDEX … REORGANIZE` | `ALTER INDEX … REBUILD` (офлайн) | `REBUILD WITH (ONLINE = ON)` |
|---|---|---|---|
| Что делает | переупорядочивает и уплотняет **только листовой уровень** до `FILLFACTOR` | удаляет и создаёт индекс заново, все уровни, с текущим или новым `FILLFACTOR` | то же, данные доступны |
| Блокировки | всегда онлайн, долгих блокировок объекта нет; короткие блокировки страниц | **Sch-M на таблицу на всё время** (кластерный и некластерный индекс) — таблица недоступна | IS на основном этапе; короткая S в начале; Sch-M в конце |
| При `ALLOW_PAGE_LOCKS = OFF` | **невозможна** | работает | работает |
| Статистика индекса | не обновляется | обновляется полным просмотром | полным просмотром; у возобновляемого — выборкой |
| Понизить плотность до меньшего `FILLFACTOR` | нет (не переносит строки с уже полных страниц) | да | да |
| Прерывание | сделанное сохраняется, можно запускать частями | откат всего | откат; у `RESUMABLE` — пауза |
| Откат пользовательской транзакции | не откатывается | откатывается | откатывается |
| Место | свободное место **в том же файле** данных (иначе ошибка 1105) | две копии индекса на время работы | больше, чем офлайн (+ временный индекс сопоставления для кластерного) |
| Журнал | полностью журналируется ⚠ (в прочитанных статьях отдельно не сказано) | полностью; минимально — в моделях SIMPLE и BULK_LOGGED (см. оговорку в 3.6) | полностью |
| Параллелизм | однопоточно, `MAXDOP` указать нельзя (подтверждено 20.10.2026 по MS Learn — `ALTER INDEX`, «Configure parallel index operations») | `MAXDOP` — только Enterprise | `MAXDOP` — только Enterprise |
| Редакция | все | все | **Enterprise/Developer** |

Источники: [MS Learn — `ALTER INDEX`, «Optimize index maintenance…», «Guidelines for online index operations», `sys.dm_db_index_physical_stats`, редакции 2022/2025].

Microsoft: реорганизация дешевле перестроения и должна быть методом по умолчанию, если нет причин для перестроения [MS Learn]. **Для баз 1С 8.3.22+ это правило упирается в выключенные страничные блокировки** (раздел 4): реорганизация возможна только с временным включением `ALLOW_PAGE_LOCKS`.

### 3.2. `REORGANIZE` подробно

```sql
USE [buh];   -- db_owner / sysadmin
ALTER INDEX [_Document123_ByNumber] ON [dbo].[_Document123] REORGANIZE;
ALTER INDEX [_Document123_ByNumber] ON [dbo].[_Document123] REORGANIZE WITH (LOB_COMPACTION = OFF);
ALTER INDEX ALL ON [dbo].[_Document123] REORGANIZE;      -- падает, если у любого индекса выключены страничные блокировки
```

Имена таблиц и индексов условные — их генерирует платформа; соответствие объектам конфигурации даёт метод `ПолучитьСтруктуруХраненияБазыДанных()` (выполняется на сервере 1С; см. `../postgresql/06-monitoring-i-diagnostika-zaprosov.md`); номера в именах в разных базах одной конфигурации различаются [практика].

- `LOB_COMPACTION = ON` (умолчание) уплотняет страницы LOB (`image`, `text`, `ntext`, `varchar(max)`, `nvarchar(max)`, `varbinary(max)`, `xml`, `json`); для кластерного индекса — все LOB-столбцы таблицы [MS Learn]. Хранилища значений 1С, вероятно, в таких столбцах ⚠ (типы не сверялись) — при нехватке окна отключать [практика].
- Внутри явной транзакции блокировки `REORGANIZE` строже — запускать вне `BEGIN TRAN` [MS Learn]. Прерванная реорганизация сохраняет сделанное — большие индексы можно обрабатывать за несколько ночей [MS Learn].
- Нужно свободное место в том же файле: иначе ошибка 1105 «Could not allocate space … filegroup is full», даже если в других файлах группы место есть [MS Learn].

### 3.3. `REBUILD` офлайн

```sql
USE [buh];
ALTER INDEX [_Document123_ByNumber] ON [dbo].[_Document123] REBUILD;                   -- параметры из sys.indexes
ALTER INDEX ALL ON [dbo].[_Document123] REBUILD;
ALTER INDEX [_Document123_ByNumber] ON [dbo].[_Document123] REBUILD WITH (SORT_IN_TEMPDB = ON);
```

- Без указанных параметров применяются значения из `sys.indexes` (`FILLFACTOR`, `PAD_INDEX`, `ALLOW_PAGE_LOCKS`, `ALLOW_ROW_LOCKS` и др.); `ONLINE`, `MAXDOP`, `SORT_IN_TEMPDB` в каталоге не хранятся [MS Learn].
- Офлайн-перестроение кластерного **и некластерного** индекса берёт Sch-M на таблицу на всё время [MS Learn — `ALTER INDEX`, `ONLINE = OFF`]; в статье об устаревшем `DBCC DBREINDEX` для некластерного сказано про общую блокировку S [MS Learn] — ориентироваться на `ALTER INDEX`. Для пользователей 1С — ожидание и таймауты [практика].
- Перестроение кластерного индекса некластерные не перестраивает (кроме `ALL`); у индексов больше 128 экстентов старые страницы освобождаются в фоне [MS Learn].
- Офлайн-перестроение некластерного индекса может устранить часть несогласованностей, найденных `CHECKDB`, онлайн — нет [MS Learn].

### 3.4. `REBUILD` онлайн (Enterprise/Developer)

```sql
USE [buh];
ALTER INDEX [_Document123_ByNumber] ON [dbo].[_Document123]
REBUILD WITH (ONLINE = ON (WAIT_AT_LOW_PRIORITY (MAX_DURATION = 5 MINUTES, ABORT_AFTER_WAIT = SELF)),
              MAXDOP = 4);
```

- Основной этап — только IS на таблицу; в начале — кратковременная S, в конце при перестроении — кратковременная Sch-M [MS Learn]. Без `WAIT_AT_LOW_PRIORITY` операции, чтобы начаться и закончиться, нужно дождаться завершения всех транзакций, держащих блокировки на таблице, а пока она ждёт Sch-M, за ней встают новые запросы — классическая «пробка» [MS Learn]. `WAIT_AT_LOW_PRIORITY (MAX_DURATION = n MINUTES, ABORT_AFTER_WAIT = NONE | SELF | BLOCKERS)`: ждать с низким приоритетом и по истечении — продолжать ждать обычным образом, отменить себя или **завершить блокирующие транзакции** [MS Learn]. Для базы 1С — только `SELF` [практика]: `BLOCKERS` оборвёт транзакции пользователей 1С.
- Пока идёт онлайн-перестроение, каждое изменение индексированных столбцов обновляет и копию индекса — изменения данных немного медленнее [MS Learn]; онлайн-операции обычно медленнее офлайн и могут изредка вызывать взаимоблокировки, жертвой выбирается пользовательская операция [MS Learn]; на таблицу на время операции добавляется информация версий строк (+14 байт на строку) [MS Learn].
- Нельзя онлайн: XML- и пространственные индексы, отключённый кластерный индекс, кластерный индекс таблицы с `image`, `ntext`, `text` (с 2012 — `varchar(max)`/`varbinary(max)` не мешают) [MS Learn]. В базах 1С столбцы `image`/`ntext` возможны ⚠ (типы столбцов 1С на MS SQL не сверялись) — такие индексы скрипт должен перестраивать офлайн в окне или пропускать.
- Не запускать онлайн-перестроение внутри явной транзакции: S или Sch-M финального этапа будет держаться до её конца [MS Learn].
- `ELEVATE_ONLINE` (2019+) на уровне базы автоматически делает онлайн все поддерживающие это DDL [MS Learn]; для баз 1С **не включать** — это коснётся и DDL реструктуризации платформы ⚠ [вывод; влияние на реструктуризацию не проверено].

### 3.5. Возобновляемое перестроение (2017+, Enterprise)

```sql
USE [buh];
ALTER INDEX [_AccumRg456_ByDims] ON [dbo].[_AccumRg456]
      REBUILD WITH (ONLINE = ON, RESUMABLE = ON, MAX_DURATION = 120, MAXDOP = 4);   -- через 120 мин — пауза
ALTER INDEX [_AccumRg456_ByDims] ON [dbo].[_AccumRg456] PAUSE;
ALTER INDEX [_AccumRg456_ByDims] ON [dbo].[_AccumRg456] RESUME WITH (MAX_DURATION = 120);
ALTER INDEX [_AccumRg456_ByDims] ON [dbo].[_AccumRg456] ABORT;
SELECT name, state_desc, percent_complete, start_time, last_pause_time, total_execution_time
FROM sys.index_resumable_operations;
```

- `RESUMABLE = ON` требует `ONLINE = ON`; параметр не хранится в метаданных и указывается в каждой команде; с `ALL` не работает; внутри явной транзакции нельзя; `SORT_IN_TEMPDB = ON` не поддерживается [MS Learn].
- Приостановленная операция продолжает замедлять изменения (поддерживается вторая копия) — если доделывать не собираетесь, выполнять `ABORT`, а не оставлять на паузе [MS Learn]. С 2022 приостановленная операция автоматически прерывается через `PAUSED_RESUMABLE_INDEX_ABORT_DURATION_MINUTES` (по умолчанию 1440 мин = сутки; `0` — никогда) [MS Learn].
- Статистика индекса при возобновляемом перестроении обновляется выборкой, а не полным просмотром [MS Learn] — после него обновить статистику индекса отдельно `FULLSCAN` (раздел 6.4) [вывод].
- Возобновляемая операция журналирует меньше и позволяет усекать журнал во время работы [MS Learn] — полезно для больших регистров в модели FULL.

### 3.6. Журнал, `MAXDOP`, `SORT_IN_TEMPDB`

- **Журнал.** Операции с индексами пишут много журнала; до конца операции журнал не усекается, но копии журнала делать можно и нужно [MS Learn] — задание `BACKUP LOG` на время окна не останавливать [практика; `04-…`]. В `ALTER INDEX` сказано, что в SIMPLE и BULK_LOGGED перестроение может журналироваться минимально, в руководстве по онлайн-операциям — что офлайн- и онлайн-перестроение журналируются полностью [MS Learn]; рабочие базы 1С обычно в FULL — рассчитывать на полный объём [вывод]. Переводить базу в BULK_LOGGED ради регламента не советую: теряется восстановление на момент времени внутри интервала копии журнала ⚠ [практика]. Большой объём журнала — это и отставание реплик Always On (`07-…`) [вывод]. С ADR онлайн-операции не раздувают журнал, но растёт постоянное хранилище версий [MS Learn].
- **`MAXDOP`** в `ALTER INDEX` переопределяет серверный параметр для операции [MS Learn]. При серверном `MAXDOP = 1` [ИТС-мет 5904] явный `MAXDOP` в Enterprise ускоряет перестроение ценой CPU; в Standard параллельных операций обслуживания индексов нет [MS Learn] — параметр там бесполезен [вывод]. Серверный `max degree of parallelism` ради регламента не менять: его `RECONFIGURE` очищает кеш планов экземпляра [MS Learn].
- **`SORT_IN_TEMPDB = ON`** — промежуточная сортировка в `tempdb`: быстрее при отдельном быстром диске, но нужно место там; при сортировке в памяти игнорируется [MS Learn].

### 3.7. Параметры индексов, которые в базе 1С не трогать

| Параметр | Почему | Источник |
|---|---|---|
| `DATA_COMPRESSION = ROW/PAGE` | сжатие средствами СУБД разрешено ИТС только для Oracle | [ИТС-КС разд. 5.5.4] ⚠ трактовка |
| `STATISTICS_NORECOMPUTE = ON` / `UPDATE STATISTICS … NORECOMPUTE` / `sp_autostats … 'OFF'` | отключает автообновление статистики индекса; Microsoft предупреждает о плохих планах | [MS Learn] |

| `OPTIMIZE_FOR_SEQUENTIAL_KEY` (2019+), `IGNORE_DUP_KEY` | меняют поведение вставки; не входят в перечень ИТС | [MS Learn; ИТС-КС разд. 5.5.8] [вывод] |

Изменения параметров через `ALTER INDEX … SET` применяются сразу, без перестроения [MS Learn]. Сохранятся ли такие изменения после реструктуризации 1С, которая может пересоздавать таблицы и индексы [ИТС-мет 5945, 2018], — ⚠ не описано; после обновления конфигурации проверять запросом из раздела 4.2.

## 4. `ALLOW_PAGE_LOCKS = OFF` в базах 8.3.22+

### 4.1. Что известно

- **1С**: начиная с платформы 8.3.22 дефрагментацию индексов выполнять так: включить страничные блокировки (`ALTER INDEX index_name ON table_name SET (ALLOW_PAGE_LOCKS = ON, ALLOW_ROW_LOCKS = ON);`), выполнить дефрагментацию, снова выключить (`… SET (ALLOW_PAGE_LOCKS = OFF, ALLOW_ROW_LOCKS = ON);`) [ИТС-мет 5837, 2022]. Отсюда следует, что индексы, которые создаёт платформа 8.3.22+, имеют `ALLOW_PAGE_LOCKS = OFF` [вывод]; прямого описания в документации 8.3.27 и в изменениях 8.5.1 не нашёл ⚠, причина решения не объяснена ⚠.
- **Microsoft**: индекс с `ALLOW_PAGE_LOCKS = OFF` нельзя реорганизовать (`REORGANIZE`), `DBCC INDEXDEFRAG` его тоже не обрабатывает; `ALTER INDEX ALL … REORGANIZE` падает целиком; выключать блокировки строк или страниц вообще не рекомендуется — возможны проблемы параллелизма и недоступность части функций [MS Learn]. Для минимального журналирования массовых вставок в индексированные таблицы `ALLOW_PAGE_LOCKS` должен быть `ON` [MS Learn — описание флага 610] — это касается, например, `INSERT … SELECT` в больших объёмах [вывод].
- **`REBUILD` выключенные страничные блокировки сохраняет**: без явного параметра применяются значения из `sys.indexes` [MS Learn]. Этим подтверждается непроверенное утверждение в `../1c-windows/02-…`, разд. 10.2 (см. «Уточнения к …02» в конце).
- **`ALTER INDEX … SET (…)`** меняет параметр без перестроения, сразу [MS Learn]; какие блокировки берёт сама команда `SET`, в прочитанной документации не указано ⚠ — выполнять в окне обслуживания [практика].
- **Ошибка при попытке реорганизации** — подтверждено 20.10.2026 по MS Learn (список ошибок движка 2000–2999, SQL Server 2022): ошибка 2552, уровень 16, текст «The index … (partition …) on table … cannot be reorganized because page level locking is disabled».
- **Онлайн-перестроение такого индекса**: при `ALLOW_PAGE_LOCKS = OFF` онлайн-перестроение с `MAXDOP` больше 1 может увеличить фрагментацию [MS Learn — «Guidelines for online index operations»] — поэтому Ola Hallengren ставит для них `MAXDOP = 1` (4.4), так же делает скрипт 12.1.

### 4.2. Проверка состояния

```sql
USE [buh];   -- db_owner / sysadmin
-- сколько индексов с какими флагами блокировок
SELECT i.allow_page_locks, i.allow_row_locks, COUNT(*) AS indexes
FROM sys.indexes AS i
JOIN sys.tables  AS t ON t.object_id = i.object_id
WHERE i.index_id > 0 AND t.is_ms_shipped = 0
GROUP BY i.allow_page_locks, i.allow_row_locks;

-- индексы, у которых страничные блокировки остались включёнными (после сбоя регламента 5837)
SELECT OBJECT_SCHEMA_NAME(i.object_id) AS schema_name, OBJECT_NAME(i.object_id) AS table_name, i.name
FROM sys.indexes AS i
JOIN sys.tables  AS t ON t.object_id = i.object_id
WHERE i.index_id > 0 AND t.is_ms_shipped = 0 AND i.allow_page_locks = 1;
```

Как читать [практика]: у базы, созданной или реструктурированной платформой 8.3.22+, ожидается преобладание `allow_page_locks = 0`. Отдельные индексы с `1` — либо таблицы, которые платформа давно не пересоздавала (база создана старой версией) ⚠ — переводит ли 8.3.22+ существующие индексы в `OFF` при обновлении платформы, не описано, — либо след прерванного регламента. Во втором случае вернуть `OFF` (скрипт 12.1 делает это автоматически). Сохранить результат первой выборки сразу после перехода на 8.3.22+ — это «эталон» для сравнения [практика].

### 4.3. Алгоритм 5837 и его риски

Алгоритм для одного индекса [ИТС-мет 5837, 2022]:

```sql
USE [buh];
ALTER INDEX [_Document123_ByNumber] ON [dbo].[_Document123] SET (ALLOW_PAGE_LOCKS = ON,  ALLOW_ROW_LOCKS = ON);
ALTER INDEX [_Document123_ByNumber] ON [dbo].[_Document123] REORGANIZE;
ALTER INDEX [_Document123_ByNumber] ON [dbo].[_Document123] SET (ALLOW_PAGE_LOCKS = OFF, ALLOW_ROW_LOCKS = ON);
```

Риски и как их снять [практика, если не указано иное]:

1. **Сбой между шагами** (отмена задания, разрыв, перезапуск службы, ошибка 1105) оставляет `ALLOW_PAGE_LOCKS = ON`: платформа продолжит работать с индексом, на котором SQL Server может брать страничные блокировки и укрупнять их — то, чего 1С избегала ⚠. Решение: `TRY/CATCH` с возвратом `OFF` и ежедневная проверка запросом 4.2.
2. **Пока страничные блокировки включены, работают пользователи** — реорганизация берёт короткие блокировки страниц [MS Learn]; поведение 1С в этот момент не описано ⚠. Выполнять в окне малой нагрузки.
3. **Длинная реорганизация** большого индекса: можно прервать без потери сделанного [MS Learn], но тогда **обязательно** вернуть `OFF`. Удобно ограничивать время всего прохода (скрипт 12.1 проверяет срок перед каждым индексом).
4. **Альтернатива без переключений** — `REBUILD`: в Enterprise онлайн с `WAIT_AT_LOW_PRIORITY`, в Standard — офлайн только в окне. Плотность и фрагментация устраняются на всех уровнях, статистика индекса обновляется полным просмотром [MS Learn].
5. **Не применять к таблицам с открытыми долгими транзакциями** — `SET` и `REORGANIZE` будут ждать блокировок; задать `SET LOCK_TIMEOUT` (в скрипте — 60 000 мс) [практика; `LOCK_TIMEOUT` использует и Ola Hallengren — сторонний].

### 4.4. Как это ломает типовые средства

| Средство | Что происходит на индексах с `ALLOW_PAGE_LOCKS = OFF` | Источник |
|---|---|---|
| План обслуживания, «Reorganize Index Task» | задача выполняет `ALTER INDEX … REORGANIZE` → ошибка на каждом таком индексе | [MS Learn — задача использует `ALTER INDEX`; вывод] |
| План обслуживания, «Rebuild Index Task» | работает; в Standard — офлайн, таблицы недоступны на время перестроения | [MS Learn] |
| `DBCC INDEXDEFRAG` (методички 2008–2022) | не обрабатывает индекс с выключенными страничными блокировками | [MS Learn] |
| `sp_msforeachtable … DBCC INDEXDEFRAG` [ИТС-мет 5837] | то же + недокументированная процедура | [MS Learn; практика] |
| Ola Hallengren `IndexOptimize` | `INDEX_REORGANIZE` не входит в допустимые действия → берётся следующее из списка: при умолчаниях — `INDEX_REBUILD_ONLINE` (если `EngineEdition` 3, 5 или 8), иначе `INDEX_REBUILD_OFFLINE`; для онлайн-перестроения такого индекса принудительно `MAXDOP = 1` («обход ограничения SQL Server», KB 2292737) | [сторонний, `IndexOptimize.sql` от 12.09.2026] |

Вывод для Standard [вывод]: «умолчательный» `IndexOptimize` на базе 1С 8.3.22+ превращает «среднюю» фрагментацию в **офлайн-перестроение в рабочее время**, если задание стоит днём. Настройки для 1С — раздел 11.3.

## 5. `FILLFACTOR` и разделения страниц

- `FILLFACTOR` — процент заполнения листовых страниц при создании или перестроении, 1–100; умолчание 0 (0 и 100 равнозначны); движок не поддерживает пустое место динамически; `PAD_INDEX = ON` применяет его к промежуточным уровням; серверное умолчание — расширенный параметр `fill factor` (`sp_configure`, право `ALTER SETTINGS`) [MS Learn].
- `REORGANIZE` уплотняет страницы до `FILLFACTOR`, но не разрежает переполненные — для этого `REBUILD` [MS Learn].
- Microsoft: большинству нагрузок лучше умолчание; `FILLFACTOR` 50 удваивает ввод-вывод и память; чтений даже в «пишущей» нагрузке в 5–10 раз больше записей; при возрастающем ключе пониженный `FILLFACTOR` не помогает; если мешают разделения — перестроить с 70–95 %; менять только для индексов с частыми разделениями (например, ведущий неупорядоченный GUID) [MS Learn].
- Версии строк RCSI добавляют до 14 байт к строке и могут вызывать разделения; понижение `FILLFACTOR` может помочь [MS Learn]. В базах 1С с управляемыми блокировками RCSI используется [ИТС-разр гл. 9, разд. 9.2.3.2].

Для 1С [практика]: серверный `fill factor` и `FILLFACTOR` «всей базе» не менять; кандидаты — индексы с высоким `leaf_allocation_count` и быстро растущей фрагментацией (часто кластерные по «Ссылке» у активно пополняемых документов, если «Ссылки» неупорядочены ⚠); пробовать 90, затем 80, оценивать через неделю; после обновления конфигурации проверять `fill_factor` — реструктуризация может пересоздать индекс ⚠.

```sql
USE [buh];   -- db_owner; в Standard — офлайн, в окно
ALTER INDEX [_Document123_IDRRef] ON [dbo].[_Document123] REBUILD WITH (FILLFACTOR = 90);
SELECT name, fill_factor, is_padded FROM sys.indexes WHERE object_id = OBJECT_ID(N'dbo._Document123');
EXECUTE sp_configure 'show advanced options', 1; RECONFIGURE;   -- sysadmin; только посмотреть
EXECUTE sp_configure 'fill factor';
```

## 6. Статистика

### 6.1. Что это и где смотреть

- Статистика — объект с гистограммой распределения значений **первого** столбца ключа (до 200 шагов) и вектором плотности для каждого префикса столбцов; по ней оптимизатор оценивает число строк и выбирает план [MS Learn].
- Создаётся автоматически для каждого индекса (по ключевым столбцам) и, при `AUTO_CREATE_STATISTICS = ON`, для отдельных столбцов из условий запросов — имена таких статистик начинаются с `_WA` [MS Learn]. В базе 1С их обычно тысячи [практика].
- Где смотреть [MS Learn]: `sys.stats` (`auto_created`, `user_created`, `no_recompute`, `has_persisted_sample`, `auto_drop`), `sys.dm_db_stats_properties` (`last_updated`, `rows`, `rows_sampled`, `steps`, `modification_counter`, `persisted_sample_percent`), функция `STATS_DATE`, `DBCC SHOW_STATISTICS (…) WITH STAT_HEADER | DENSITY_VECTOR | HISTOGRAM`.

```sql
USE [buh];   -- db_owner / sysadmin
-- статистики с наибольшим числом изменений после последнего обновления
SELECT TOP (50)
       OBJECT_NAME(s.object_id) AS table_name, s.name AS stats_name, s.auto_created, s.no_recompute,
       sp.last_updated, sp.rows, sp.rows_sampled,
       CAST(100.0 * sp.rows_sampled / NULLIF(sp.rows, 0) AS decimal(5,1)) AS sample_pct,
       sp.modification_counter,
       sp.persisted_sample_percent          -- 2016 SP1 CU4+, иначе убрать столбец
FROM sys.stats AS s
JOIN sys.tables AS t ON t.object_id = s.object_id
CROSS APPLY sys.dm_db_stats_properties(s.object_id, s.stats_id) AS sp
WHERE t.is_ms_shipped = 0
ORDER BY sp.modification_counter DESC;

-- статистики с отключённым автообновлением (в базе 1С их быть не должно)
SELECT OBJECT_NAME(object_id) AS table_name, name FROM sys.stats
WHERE no_recompute = 1 AND OBJECTPROPERTY(object_id, 'IsMsShipped') = 0;

-- подробности одной статистики
DBCC SHOW_STATISTICS (N'dbo._AccumRg456', N'_AccumRg456_ByDims') WITH STAT_HEADER, HISTOGRAM;
```

`sample_pct` около 100 — статистика построена полным просмотром (после `FULLSCAN` или `REBUILD`); единицы процентов — выборкой (автообновление, `sp_updatestats`) [MS Learn — смысл столбцов; трактовка — практика].

### 6.2. Автоматическое создание и обновление

- `AUTO_CREATE_STATISTICS` и `AUTO_UPDATE_STATISTICS` по умолчанию `ON`, Microsoft рекомендует оставлять умолчание [MS Learn]. При `AUTO_UPDATE_STATISTICS = OFF` статистика по-прежнему помечается устаревшей, но не обновляется, планы строятся по старой — **не выключать** [MS Learn].
- Устаревание проверяется перед компиляцией запроса и перед выполнением плана из кеша [MS Learn]; при синхронном режиме запрос ждёт обновления статистики [MS Learn].
- Порог автообновления (число изменений строк с момента последнего обновления) [MS Learn]:

| Таблица | До 2014 включительно, а также 2016+ при уровне совместимости < 130 | 2016+ при уровне совместимости ≥ 130 |
|---|---|---|
| постоянная, `n` ≤ 500 строк | 500 | 500 |
| `n` > 500 | `500 + 0,20·n` | `MIN(500 + 0,20·n; SQRT(1000·n))` |
| пример: 2 000 000 строк | 400 500 | 44 721 |

- На 2008 R2 … 2014 и на 2016+ с уровнем совместимости 120 и ниже динамический порог включает флаг 2371 [MS Learn]; ИТС рекомендовал его [ИТС-мет 5946, 2019], на 2016+ при уровне 130+ он не действует [MS Learn].
- **Проверить уровень совместимости баз 1С**: базы, восстановленные или подключённые со старых серверов, сохраняют прежний уровень, если он не ниже минимально поддерживаемого (подтверждено 20.10.2026 по MS Learn, ALTER DATABASE compatibility level). Повышение уровня меняет и модель оценки кардинальности, и набор исправлений оптимизатора — делать как отдельное изменение с проверкой (`07-otkazoustojchivost-…`) [MS Learn — назначение уровня; практика].
- Для баз 1С есть регистры с возрастающими ключами («Период», «Регистратор»): новые значения могут не попасть в гистограмму, если изменений мало для срабатывания порога, — оценки по свежим датам занижаются [MS Learn — общий случай возрастающих ключей]. Отсюда пользы от ежедневного обновления статистики «горячих» таблиц даже при работающем автообновлении [вывод; ИТС-мет 5837, 2022].

### 6.3. Синхронное и асинхронное автообновление

- По умолчанию `AUTO_UPDATE_STATISTICS_ASYNC = OFF`: запрос, наткнувшийся на устаревшую статистику, ждёт её обновления [MS Learn].
- 1С: в `model` установить «Auto update statistics asynchronously» = True, рабочие базы наследуют настройки `model` [ИТС-мет 5904, 2019].
- Microsoft: асинхронный режим даёт более предсказуемое время ответа и спасает от таймаутов клиентов, ожидающих статистику; синхронный лучше после операций, резко меняющих распределение (очистка таблицы, массовое изменение большой доли строк) [MS Learn]. Фоновое обновление при записи статистики берёт блокировку Sch-M на метаданные статистики; сеансы, компилирующие запросы (им нужна Sch-S), могут на ней ждать — при очень частых компиляциях и обновлениях вероятность блокировок растёт [MS Learn].
- С **2022**: `ALTER DATABASE SCOPED CONFIGURATION SET ASYNC_STATS_UPDATE_WAIT_AT_LOW_PRIORITY = ON` — фоновый запрос ждёт Sch-M в очереди с низким приоритетом и не мешает компиляции; если за несколько минут блокировку получить не удалось, обновление отменяется до следующего срабатывания [MS Learn].
- Статистика локальных временных таблиц (`#tt…` платформы) всегда обновляется синхронно, независимо от параметра [MS Learn].

```sql
-- sysadmin / db_owner
ALTER DATABASE [buh] SET AUTO_UPDATE_STATISTICS_ASYNC ON;                  -- по рекомендации ИТС-мет 5904
USE [buh];
ALTER DATABASE SCOPED CONFIGURATION SET ASYNC_STATS_UPDATE_WAIT_AT_LOW_PRIORITY = ON;   -- 2022+
SELECT name, value FROM sys.database_scoped_configurations
WHERE name IN (N'ASYNC_STATS_UPDATE_WAIT_AT_LOW_PRIORITY', N'MAXDOP', N'QUERY_OPTIMIZER_HOTFIXES');
SELECT is_auto_update_stats_on, is_auto_update_stats_async_on FROM sys.databases WHERE name = N'buh';
```

`ALTER DATABASE … SET AUTO_UPDATE_STATISTICS_ASYNC` на работающей базе: уточнено 20.10.2026 по MS Learn (ALTER DATABASE SET options) — в описании параметра требования монопольного доступа нет (в отличие от `READ_COMMITTED_SNAPSHOT`, для которого не должно быть других подключений); новое значение действует сразу. Но перед переводом базы в `SINGLE_USER` асинхронное обновление надо выключить: его фоновый поток занимает подключение [MS Learn]. Поведение под нагрузкой не проверялось ⚠ — выполнять в окне [практика].

### 6.4. `FULLSCAN`, выборка, `PERSIST_SAMPLE_PERCENT`, `MAXDOP`

Синтаксис: `UPDATE STATISTICS таблица [ (статистика [, …]) ] [ WITH { FULLSCAN | SAMPLE n { PERCENT | ROWS } } [, PERSIST_SAMPLE_PERCENT = ON | OFF] | RESAMPLE, [ ALL | COLUMNS | INDEX ], NORECOMPUTE, INCREMENTAL, MAXDOP = n, AUTO_DROP ]`; права — `ALTER` на таблицу [MS Learn].

- `FULLSCAN` = `SAMPLE 100 PERCENT`. Без указания — выборка, размер выбирает оптимизатор; Microsoft: для большинства нагрузок полный просмотр не нужен, но при сильно неравномерном распределении может понадобиться [MS Learn]. 1С: «обновление статистик необходимо проводить с включенной опцией Full Scan» [ИТС-мет 5837, 2022].
- `RESAMPLE` — с последней долей выборки (у статистик индексов это может быть полный просмотр) [MS Learn].
- `PERSIST_SAMPLE_PERCENT = ON` (2016 SP1 CU4, 2017 CU1+) — запомнить долю для последующих обновлений, **включая автообновление**; до 2016 SP2 CU17 / 2017 CU26 / 2019 CU10 её сбрасывало перестроение индекса, `TRUNCATE` сбрасывает и сейчас [MS Learn].
- `MAXDOP = n` (2016 SP2, 2017 CU3+, до 64) — только для этой операции; ограничен `MAX_DOP` группы Resource Governor [MS Learn]. При серверном `MAXDOP = 1` без него полный просмотр идёт в один поток [вывод]. Выборочный сбор с 2017 — последовательный при любом уровне совместимости [MS Learn]. Параллельный сбор в Standard ⚠ — в таблицах редакций отдельной строки нет.
- `NORECOMPUTE` выключает автообновление этой статистики — для 1С не использовать [MS Learn — предупреждение].
- Обновление статистики не блокирует таблицы, но нагружает сервер [ИТС-мет 5837, 2022]; зависимые планы перекомпилируются [MS Learn].

Компромисс для больших баз 1С [практика]: ежедневно — `FULLSCAN` только статистик с `modification_counter > 0` (12.2) с `MAXDOP` и лимитом времени; «горячие» таблицы — чаще, отдельным регламентом, как предлагает 1С [ИТС-мет 5837] (частоту ИТС не называет; 2–4 раза в день — практика); таблицы на сотни гигабайт, где окна не хватает, — `SAMPLE 20–50 PERCENT` с `PERSIST_SAMPLE_PERCENT = ON` (отступление от ИТС зафиксировать в регламенте).

```sql
USE [buh];   -- db_owner / sysadmin
UPDATE STATISTICS [dbo].[_AccumRg456] WITH FULLSCAN, MAXDOP = 4;                          -- вся таблица
UPDATE STATISTICS [dbo].[_AccumRg456] ([_AccumRg456_ByDims]) WITH FULLSCAN;              -- одна статистика
UPDATE STATISTICS [dbo].[_AccumRg456] WITH SAMPLE 30 PERCENT, PERSIST_SAMPLE_PERCENT = ON; -- 2016 SP1 CU4+
UPDATE STATISTICS [dbo].[_AccumRg456] WITH FULLSCAN, COLUMNS;                             -- только столбцовые
```

### 6.5. `sp_updatestats`

- Выполняет `UPDATE STATISTICS … ALL` для всех пользовательских и внутренних таблиц текущей базы; для дисковых таблиц — только там, где по `modification_counter` изменилась хотя бы одна строка; выборка по умолчанию, с `@resample = 'resample'` — с последней долей (`RESAMPLE`) [MS Learn].
- Сохраняет последний `NORECOMPUTE` у статистик [MS Learn].
- Обновляет статистику отключённых некластерных индексов, но не отключённых кластерных [MS Learn].
- Права: владелец базы (`dbo`) или `sysadmin` [MS Learn].
- При восстановлении базы на **SQL Server 2022** с более ранней версии Microsoft рекомендует выполнить `sp_updatestats` — для правильных метаданных `AUTO_DROP` [MS Learn].

Чем опасен в регламенте 1С [вывод из описания]: если ночью сначала идёт `REBUILD` (статистика индекса — полным просмотром) или `FULLSCAN`, а затем `sp_updatestats` без `@resample`, то для всех таблиц, где за это время изменилась хоть одна строка, точная статистика будет заменена выборочной. Порядок: `sp_updatestats` — только как быстрый «аварийный» проход днём, ночью — `FULLSCAN` по изменившимся (12.2) [практика].

```sql
USE [buh];
EXEC sys.sp_updatestats;                       -- выборка по умолчанию
EXEC sys.sp_updatestats @resample = 'resample'; -- с последней долей выборки
```

### 6.6. Порядок индексов и статистики

| Ночью сделано | Статистика индекса | Статистика столбцов (`_WA_Sys_…`) | Что делать после |
|---|---|---|---|
| `REBUILD` (непартиционированный, не `RESUMABLE`) | обновлена полным просмотром | не тронута | обновить только столбцовые (`… WITH FULLSCAN, COLUMNS`) или по `modification_counter` |
| `REBUILD … RESUMABLE = ON` или секционированный индекс | обновлена **выборкой** | не тронута | обновить индексную `FULLSCAN` |
| `REORGANIZE` | **не обновлена** | не тронута | обновить все по `modification_counter` |
| ничего | — | — | обновить по `modification_counter` |

Источник: [MS Learn — «Statistics update during index build», «After maintenance operations»]. Ola Hallengren `IndexOptimize` для перестроенных (непартиционированных) индексов статистику индекса не обновляет повторно [сторонний, код]. В планах обслуживания такой логики нет: задача «Update Statistics» после «Rebuild Index» с «Sample by» ухудшит статистику, с «Full scan» — выполнит лишнюю работу [вывод].

### 6.7. Методичка 1С и обновление статистики «горячих» таблиц

ИТС предлагает по анализу планов выделить таблицы, которым нужна более частая статистика, и сделать два регламента — для них и для остальных [ИТС-мет 5837, 2022]. Найти кандидатов без анализа планов можно по скорости накопления изменений [практика]:

```sql
USE [buh];
-- таблицы, где за сутки (с последнего обновления) изменено больше 5 % строк
SELECT OBJECT_NAME(s.object_id) AS table_name,
       MAX(sp.rows) AS rows_at_update,
       MAX(sp.modification_counter) AS max_mods,
       CAST(100.0 * MAX(sp.modification_counter) / NULLIF(MAX(sp.rows), 0) AS decimal(18,2)) AS mods_pct,   -- с запасом: изменений бывает во много раз больше, чем строк
       MIN(sp.last_updated) AS oldest_update
FROM sys.stats AS s
JOIN sys.tables AS t ON t.object_id = s.object_id
CROSS APPLY sys.dm_db_stats_properties(s.object_id, s.stats_id) AS sp
WHERE t.is_ms_shipped = 0
GROUP BY s.object_id
HAVING MAX(sp.modification_counter) * 20 > MAX(sp.rows)
ORDER BY max_mods DESC;
```

Имена `_AccumRg…`, `_AccumRgT…` (итоги), `_InfoRg…`, `_Document…` переводятся в объекты конфигурации методом `ПолучитьСтруктуруХраненияБазыДанных()` (см. 3.2).

### 6.8. Флаги и параметры, влияющие на оценки

| Средство | Действие | Для 1С | Источник |
|---|---|---|---|
| Флаг 2371 | динамический порог автообновления | нужен только на 2008 R2–2014 или при уровне совместимости < 130 | [MS Learn; ИТС-мет 5946, 2019] |
| Флаг 4199 / `QUERY_OPTIMIZER_HOTFIXES = ON` (2016+, уровень базы) | исправления оптимизатора из CU; без флага исправления включены, начиная с уровня 130, а исправления после RTM — выключены | ИТС рекомендует 4199 [ИТС-мет 5946, 2019]; для SQL Server 2014 его требует платформа [ИТС-адм разд. 5.2.1.3.2] | [MS Learn] |
| Флаги 2389, 2390, 4139 | «быстрая» поправка гистограммы для возрастающих ключей; 2389/2390 не действуют при модели оценки 120+ (вместо них 4139) | могут помочь регистрам с «Периодом», но **только после испытаний** — Microsoft требует тщательного тестирования | [MS Learn] |
| Флаг 7471 (2014 SP1+) | несколько `UPDATE STATISTICS` разных статистик одной таблицы одновременно | при параллельных заданиях статистики по одной большой таблице | [MS Learn] |
| `AUTO_DROP` (2022+) | статистики не блокируют изменения схемы | автосозданные всегда ведут себя так | [MS Learn] |

### 6.9. Когда статистика не поможет

- Запросы с соединениями с вложенными запросами и виртуальными таблицами «повышенно чувствительны к актуальности и полноте статистик»: сразу после полного обновления работают быстро, потом снова медленно — это дефект запроса, его исправляют временными таблицами [std 655]. Регламент СУБД такой запрос не вылечит [вывод]; поиск — `06-monitoring-i-diagnostika.md` и `08-tipovye-problemy-…`.
- Несоответствие индексов условиям запроса (нет отбора по первому полю индекса, пропущено измерение в середине) — тоже не лечится статистикой [std 652].
- Временные таблицы платформы получают статистику в `tempdb` и обновляют её синхронно [MS Learn] — регламент их не касается.

## 7. Кеш планов

### 7.1. Зачем 1С советует очищать кеш и что изменилось

- 1С: после обновления статистики SQL Server может по-прежнему брать из кеша старый неоптимальный план, поэтому «всегда после обновления статистик» выполнять `DBCC FREEPROCCACHE` с той же частотой [ИТС-мет 5837, 2022].
- Microsoft: при обновлении статистики планы, которые на неё ссылаются, перекомпилируются; обновление статистики любым способом может вызвать автоматическую перекомпиляцию [MS Learn]. Перед выполнением плана из кеша движок проверяет, что план ссылается на актуальную статистику [MS Learn].
- Вывод [вывод]: на современных версиях полная очистка кеша после регламента статистики не обязательна; если следовать ИТС буквально, очищать **кеш только базы 1С** (`CLEAR PROCEDURE_CACHE`, 2016+), а не весь экземпляр. Оправданная очистка — после смены уровня совместимости, после крупного обновления конфигурации, когда планы «залипли», и точечно для конкретного плана (7.4) [практика].

### 7.2. `DBCC FREEPROCCACHE`

```sql
-- ALTER SERVER STATE (sysadmin имеет)
DBCC FREEPROCCACHE WITH NO_INFOMSGS;                 -- весь кеш планов экземпляра
DBCC FREEPROCCACHE (0x06000500F443610F003B…);        -- один план по plan_handle (значение — из DMV)
```

- Без аргументов удаляет **все** планы экземпляра; новые запросы компилируются заново — возможен резкий временный спад производительности; в журнал ошибок пишется сообщение «SQL Server has encountered %d occurrence(s) of cachestore flush … due to 'DBCC FREEPROCCACHE' or 'DBCC FREESYSTEMCACHE' operations» (не чаще раза в 5 минут) [MS Learn].
- С аргументом — один план по `plan_handle` или `sql_handle` (из `sys.dm_exec_query_stats`, `sys.dm_exec_cached_plans`, `sys.dm_exec_requests` и др.) либо планы пула Resource Governor [MS Learn].
- Права: `ALTER SERVER STATE` [MS Learn].
- Кеш планов очищают также `RECONFIGURE` следующих параметров: `access check cache bucket count`, `access check cache quota`, `clr enabled`, `cost threshold for parallelism`, `cross db ownership chaining`, `index create memory`, `max degree of parallelism`, `max server memory`, `max text repl size`, `max worker threads`, `min memory per query`, `min server memory`, `query governor cost limit`, `query wait`, `remote query timeout`, `user options` [MS Learn]. Переключение `max degree of parallelism` на время реструктуризации [ИТС-мет 5945, 2018] дважды сбрасывает кеш всего экземпляра — планировать на окно [вывод].
- `DBCC FREESYSTEMCACHE ('ALL')` освобождает неиспользуемые записи всех кешей и тоже очищает кеш планов экземпляра [MS Learn] — в регламенте 1С не нужен [практика].
- `DBCC CHECKDB` кеш планов **не очищает** (так было только до SQL Server 2005 SP2) [MS Learn].

### 7.3. `ALTER DATABASE SCOPED CONFIGURATION CLEAR PROCEDURE_CACHE` (2016+)

```sql
USE [buh];   -- нужно ALTER ANY DATABASE SCOPED CONFIGURATION в базе (у db_owner есть — у роли CONTROL DATABASE)
ALTER DATABASE SCOPED CONFIGURATION CLEAR PROCEDURE_CACHE;                       -- только эта база
ALTER DATABASE SCOPED CONFIGURATION CLEAR PROCEDURE_CACHE 0x06000500F443610F…;   -- один план, 2019+
```

- Очищает кеш планов текущей базы; с 2019 — один план по `plan_handle` [MS Learn].
- Право: `ALTER ANY DATABASE SCOPED CONFIGURATION` в базе; выдать его может пользователь с `CONTROL` на базу [MS Learn]. Уточнено 20.10.2026 по MS Learn («Database-level roles»): у `db_owner` — `CONTROL DATABASE`, то есть все права в базе, включая это.
- Про реплики Always On документация противоречива: в описании аргумента — «можно выполнять и на первичной, и на вторичных», в примере — «очистить кеш можно только для первичной базы» [MS Learn] ⚠ — проверять на своей версии.

### 7.4. Точечные способы

- `EXEC sp_recompile N'dbo._AccumRg456';` — для таблицы помечает к перекомпиляции хранимые процедуры, триггеры и функции, которые на неё ссылаются; право `ALTER` на объект [MS Learn]. Запросы 1С приходят как пакеты и параметризованные запросы, а не процедуры [практика] ⚠ — влияние `sp_recompile` таблицы на их планы в прочитанной статье не описано; надёжнее удалить план по `plan_handle`.
- Найти план «плохого» запроса — `sys.dm_exec_query_stats` + `sys.dm_exec_sql_text` или Query Store (`06-monitoring-i-diagnostika.md`), удалить — `DBCC FREEPROCCACHE (plan_handle)` или `CLEAR PROCEDURE_CACHE plan_handle` (2019+) [MS Learn].

Размер кеша планов по базам и типам [MS Learn — столбцы DMV и атрибут `dbid`; запрос — практика]:

```sql
-- VIEW SERVER STATE
SELECT DB_NAME(CONVERT(int, pa.value)) AS db, cp.objtype, COUNT(*) AS plans,
       SUM(CAST(cp.size_in_bytes AS bigint)) / 1048576 AS size_mb,
       SUM(CASE WHEN cp.usecounts = 1 THEN 1 ELSE 0 END) AS single_use
FROM sys.dm_exec_cached_plans AS cp
CROSS APPLY sys.dm_exec_plan_attributes(cp.plan_handle) AS pa
WHERE pa.attribute = N'dbid'
GROUP BY pa.value, cp.objtype
ORDER BY size_mb DESC;
```

Query Store хранит планы и статистику выполнения в самой базе, очистка кеша планов его данные не затрагивает [MS Learn — назначение Query Store; вывод]. Принудительные планы и сравнение «до/после регламента» — `06-monitoring-i-diagnostika.md`.

## 8. `DBCC CHECKDB`

### 8.1. Что проверяет и как работает

- Выполняет `DBCC CHECKALLOC`, `DBCC CHECKTABLE` по каждой таблице и представлению, `DBCC CHECKCATALOG`, проверяет индексированные представления, ссылки FILESTREAM и данные Service Broker — отдельно эти команды запускать не нужно [MS Learn].
- Для согласованности использует **внутренний снимок базы** и не блокирует пользователей; с 2014 снимок — разреженные файлы `<имя файла>.<расширение>_MSSQL_DBCC<id снимка>` в той же папке, что и файлы данных (для журнала разреженный файл не создаётся), удаляются по окончании. Их фактический размер растёт с объёмом изменений в базе во время проверки — на диске с файлами данных нужен запас [MS Learn].
- При внезапной остановке ОС во время проверки такие файлы остаются и могут мешать следующим проверкам — удалить вручную, **убедившись, что `DBCC CHECKDB` не выполняется** [MS Learn].
- `TABLOCK` — вместо снимка блокировки (кратковременная X на базу, общие на таблицы): быстрее под нагрузкой, но снижает параллельность работы; при `TABLOCK` не выполняются `CHECKCATALOG` и проверка Service Broker [MS Learn]. Для работающей базы 1С не использовать [практика].
- Если снимок создать нельзя, `CHECKDB` сам переходит к блокировкам (X на базу для проверок выделения, S на таблицы) [MS Learn]. На `tempdb` проверка выделения и каталога не выполняется [MS Learn].
- Права: `sysadmin` или `db_owner` [MS Learn].

### 8.2. Параметры

```sql
-- sysadmin / db_owner
DBCC CHECKDB (N'buh') WITH NO_INFOMSGS, ALL_ERRORMSGS;            -- полная проверка
DBCC CHECKDB (N'buh') WITH PHYSICAL_ONLY;                         -- физическая (NO_INFOMSGS подразумевается)
DBCC CHECKDB (N'buh') WITH NO_INFOMSGS, MAXDOP = 4;               -- MAXDOP: 2014 SP2+
DBCC CHECKDB (N'buh') WITH ESTIMATEONLY;                          -- сколько нужно tempdb, без проверки
DBCC CHECKDB (N'buh', NOINDEX) WITH NO_INFOMSGS;                  -- без глубокой проверки некластерных индексов
DBCC CHECKDB (N'buh') WITH NO_INFOMSGS, DATA_PURITY;              -- значения столбцов (для баз, перенесённых со старых версий)
```

| Параметр | Смысл | Источник |
|---|---|---|
| `PHYSICAL_ONLY` | только физическая структура страниц, заголовков записей и согласованность выделения; ловит «рваные» страницы, ошибки контрольных сумм и типичные аппаратные сбои; значительно быстрее на больших базах, рекомендован для частого запуска в продуктиве; пропускает FILESTREAM и проверку значений столбцов; несовместим с `REPAIR_*` | [MS Learn] |
| `NOINDEX` | без интенсивных проверок некластерных индексов пользовательских таблиц | [MS Learn] |
| `EXTENDED_LOGICAL_CHECKS` | логические проверки индексированных представлений, XML- и пространственных индексов, а с 2016 — вычисляемых столбцов, UDT, фильтрованных индексов; дорого, только при подозрении | [MS Learn] |
| `DATA_PURITY` | недопустимые и выходящие за диапазон значения столбцов; у баз, обновлённых со старых версий, включается по умолчанию только после одного успешного прогона с этим параметром; такие ошибки (2570) не исправляются `REPAIR`, только вручную | [MS Learn] |
| `ESTIMATEONLY` | оценка места в `tempdb` | [MS Learn] |
| `MAXDOP` | переопределяет серверный `max degree of parallelism`, может его превышать; ограничен Resource Governor | [MS Learn] |
| `ALL_ERRORMSGS` | все сообщения и так выводятся по умолчанию; указание ни на что не влияет | [MS Learn] |
| `REPAIR_REBUILD`, `REPAIR_ALLOW_DATA_LOSS` | исправление; база в однопользовательском режиме; `REPAIR_FAST` оставлен только для совместимости и ничего не делает | [MS Learn] |

### 8.3. Время и нагрузка

- Формулы времени нет; полная проверка на современных версиях дольше, чем на старых (больше проверок), `PHYSICAL_ONLY` сокращает её многократно [MS Learn].
- Параллельная проверка объектов — по умолчанию, степень выбирает обработчик запросов, ограничивает `max degree of parallelism`; флаг 2528 её отключает [MS Learn]. Но **параллельная проверка целостности есть только в Enterprise** [MS Learn — редакции]: в Standard `CHECKDB` однопоточный — планировать окно с запасом [вывод].
- На сервере 1С с серверным `MAXDOP = 1` в Enterprise явно задавать `WITH MAXDOP = n` [MS Learn — параметр; практика].
- Нагрузка — в основном чтение всей базы (плюс снимок и `tempdb`); не совмещать с полной резервной копией и перестроением индексов [практика].
- Флаги 2549 и 2562 ускоряют `CHECKDB … PHYSICAL_ONLY` на некоторых системах (2562 — одна «порция», `tempdb` может вырасти до 5 % и более от размера базы) — только после испытаний [MS Learn].
- Замерить время один раз на восстановленной копии того же размера и на том же классе дисков и вписать в регламент [практика].

### 8.4. Где запускать

| Вариант | Плюсы | Минусы | Источник |
|---|---|---|---|
| Рабочий сервер, `PHYSICAL_ONLY` часто (ежедневно/еженедельно), полная — раз в месяц | проверяется именно рабочая база | нагрузка на диск и `tempdb` в окне | [MS Learn — частота; практика — числа] |
| Восстановленная копия на тестовом сервере, полная | рабочий сервер не нагружается; заодно доказано, что копия восстанавливается | проверяется состояние на момент копии; повреждение, возникшее после, будет найдено позже | [практика] |
| Вторичная реплика группы доступности | разгрузка первичной | реплика — отдельные файлы, физическое повреждение на первичной так не найти ⚠; `LastGoodCheckDbTime` на любой реплике показывает время проверки **первичной** | [MS Learn — `LastGoodCheckDbTime`; остальное — практика] |

Рекомендация [практика]: на рабочем сервере — `PHYSICAL_ONLY` по расписанию + полная проверка, когда позволяет окно; на тестовом — полная проверка каждой восстановленной копии (вместе с регламентом тестового восстановления из `04-rezervnoe-kopirovanie-…`).

### 8.5. Контроль: когда была последняя успешная проверка

```sql
SELECT name, DATABASEPROPERTYEX(name, 'LastGoodCheckDbTime') AS last_good_checkdb
FROM sys.databases WHERE database_id > 4;      -- 2016 SP2, 2017 CU9, 2019+; 1900-01-01 = не проверялась
```

- `LastGoodCheckDbTime` — дата и время последней успешной `DBCC CHECKDB`; `1900-01-01 00:00:00.000`, если проверки не было [MS Learn].
- При запуске базы эта дата («last known clean check») пишется в журнал ошибок и журнал событий Windows (EventID 17573) сообщением «CHECKDB for database '…' finished without errors on …» [MS Learn].
- После каждого `DBCC CHECKDB` в журнал ошибок SQL Server пишется результат и длительность; при прерывании — состояние (`0` — ошибка 8930, повреждение метаданных; `1` — ошибка 8967, внутренняя ошибка DBCC; `2` — сбой ремонта в аварийном режиме (`EMERGENCY`); `3` — повреждение метаданных; `4` — assert или access violation; `5` — неизвестная ошибка) [MS Learn].
- При найденном повреждении в каталоге `LOG` экземпляра создаётся дамп `SQLDump<nnnn>` [MS Learn].

### 8.6. Контрольные суммы страниц и `suspect_pages`

- `PAGE_VERIFY CHECKSUM` (умолчание для новых баз): при записи страницы считается контрольная сумма, при чтении сверяется; несовпадение — ошибка 824 в журнале ошибок и журнале Windows, это признак проблемы на пути ввода-вывода (оборудование, прошивки, драйверы, фильтры вроде антивируса) [MS Learn].
- Повреждённые страницы регистрируются в `msdb.dbo.suspect_pages` (не более 1000 строк): `event_type` 1 — ошибка 823 или 824 (кроме контрольной суммы и «рваной» страницы), 2 — контрольная сумма, 3 — «рваная» страница, 4 — восстановлена и др. [MS Learn].

```sql
SELECT DB_NAME(database_id) AS db, file_id, page_id, event_type, error_count, last_update_date
FROM msdb.dbo.suspect_pages ORDER BY last_update_date DESC;
SELECT name, page_verify_option_desc FROM sys.databases WHERE page_verify_option_desc <> N'CHECKSUM';
```

Оповещения агента на ошибки 823/824 и уровень серьёзности 19–25 — `03-administrirovanie-…` и `06-monitoring-…`.

### 8.7. Что делать, если `CHECKDB` нашёл ошибки

1. Ничего не «чинить» сразу: сохранить полный вывод, посмотреть журнал ошибок и `suspect_pages`, проверить диски [MS Learn; практика].
2. **Основной путь — восстановление из последней исправной копии** (полная + журналы) — Microsoft всегда рекомендует его первым [MS Learn]; порядок — `04-rezervnoe-kopirovanie-…`. ⚠ Восстановление поверх рабочей базы разрушающее: сначала копия текущего состояния и копии файлов.
3. **Ошибки только в некластерных индексах** (index_id > 1): офлайн-перестроение может устранить, онлайн — нет; надёжнее пересоздать индекс [MS Learn]. В базе 1С индексы принадлежат платформе — офлайн `ALTER INDEX … REBUILD` или реиндексация 1С (`/IBCheckAndRepair -ReIndex`, монопольно) [ИТС-адм прил. 7, разд. 7.4.5] [практика].
4. **`REPAIR_REBUILD`** — без потери данных; **`REPAIR_ALLOW_DATA_LOSS`** — может удалить строки и страницы, связи не проверяет; только если восстановление из копии невозможно: копии всех файлов базы, однопользовательский режим, внутри транзакции, затем `DBCC CHECKCONSTRAINTS` и новая полная копия [MS Learn]. В аварийном режиме (`EMERGENCY`) ремонт может перестроить журнал и откатить его транзакцией нельзя [MS Learn].
5. **После любого `REPAIR_*` в базе 1С** — тестирование и исправление с проверкой ссылочной целостности и пересчётом итогов [ИТС-адм разд. 6.10.2] [вывод]; сверить остатки с бухгалтерией.

```sql
-- ⚠ РАЗРУШАЮЩЕ. Только если восстановить из копии невозможно; сначала скопировать все файлы базы.
-- sysadmin; сеансы 1С остановить (блокировка начала сеансов в кластере 1С)
ALTER DATABASE [buh] SET AUTO_UPDATE_STATISTICS_ASYNC OFF;   -- иначе фоновый поток статистики может занять единственное подключение
ALTER DATABASE [buh] SET SINGLE_USER WITH ROLLBACK IMMEDIATE;
BEGIN TRANSACTION;
DBCC CHECKDB (N'buh', REPAIR_ALLOW_DATA_LOSS) WITH NO_INFOMSGS, ALL_ERRORMSGS;
-- просмотреть вывод; затем COMMIT TRANSACTION; или ROLLBACK TRANSACTION;
ALTER DATABASE [buh] SET MULTI_USER;
ALTER DATABASE [buh] SET AUTO_UPDATE_STATISTICS_ASYNC ON;    -- вернуть, если было включено (6.3)
```

Перед `SINGLE_USER` асинхронное обновление статистики выключают: при `ON` его фоновый поток берёт подключение к базе, и войти в однопользовательском режиме не удастся [MS Learn — ALTER DATABASE SET options, `SINGLE_USER`]. В базах 1С оно часто включено по рекомендации ИТС (6.3).

## 10. Методичка 5837: что актуально

Редакция 18.11.2022; примеры — для планов обслуживания SQL Server 2005 [ИТС-мет 5837, 2022].

| Рекомендация 5837 | Оценка на октябрь 2026 | Что делать |

## 11. Планы обслуживания против скриптов Ola Hallengren

### 11.1. Планы обслуживания SQL Server

- План обслуживания создаёт пакет SSIS, который выполняет задание SQL Server Agent; задачи объединяются в подпланы со своими расписаниями; результаты пишутся в текстовый отчёт или в таблицы `msdb` `sysmaintplan_log` и `sysmaintplan_logdetail`, просмотр — «Maintenance Plans → View History» [MS Learn]. Без агента (Express) планы не выполняются [MS Learn — агент отсутствует в Express]. Планы работают только с базами уровня совместимости 80 и выше [MS Learn].
- **Задачи и их параметры** [MS Learn]:

| Задача | Команда | Параметры | Для 1С |
|---|---|---|---|
| Rebuild Index Task | `ALTER INDEX … REBUILD` | «Default free space per page» / «Change free space per page to» (`FILLFACTOR`), «Sort results in tempdb», «Pad index», «Keep index online» (+ что делать с индексами, которые нельзя онлайн: не перестраивать или офлайн), `MAXDOP`, «Low Priority Used» + «Abort after Wait» + «Max Duration»; с SSMS 2016 — «Scan type» Fast/Sampled/Detailed и фильтры «Fragmentation > %», «Page Count >», «Used in last (days)» | работает; «Keep index online» — только Enterprise; «Change free space per page» не трогать |
| Reorganize Index Task | `ALTER INDEX … REORGANIZE` | «Compact large objects» (`LOB_COMPACTION = ON`); те же фильтры с 2016 | **на 8.3.22+ падает** — не использовать |
| Update Statistics Task | `UPDATE STATISTICS` | «All existing statistics» / «Column statistics only» / «Index statistics only»; «Full scan» / «Sample by» | «Full scan» по ИТС [ИТС-мет 5837]; без фильтра «только изменившиеся» |
| Check Database Integrity Task | `DBCC CHECKDB` | «Include indexes», «Physical only», «Tablock» | `Tablock` не включать (8.1) |
| Execute T-SQL Statement Task | произвольный T-SQL | — | так 5837 добавляет `DBCC FREEPROCCACHE`; сюда же можно вставить скрипт 12.1 |

- Для баз 1С план обслуживания годится как «оболочка с расписанием и историей», а реорганизацию с переключением страничных блокировок — только через «Execute T-SQL Statement Task» [вывод].

### 11.2. SQL Server Maintenance Solution (Ola Hallengren) [сторонний]

- Бесплатный набор процедур `DatabaseBackup`, `DatabaseIntegrityCheck`, `IndexOptimize` (+ `CommandExecute`, таблица `dbo.CommandLog`); установщик `MaintenanceSolution.sql` — для SQL Server 2017–2025 и Azure SQL Managed Instance; версия на 20.10.2026 — от 12.09.2026. Уточнено 20.10.2026 по коду: в заголовке установщика те же версии, а процедуры используют `STRING_AGG`, которой нет до SQL Server 2017 [MS Learn] — на SQL Server 2016 текущая версия не установится; там остаётся только старая версия инструмента [вывод].
- **Установка**: `MaintenanceSolution.sql` от `sysadmin` (сценарий это проверяет); объекты создаются в базе из строки `USE [master]` — заменить на служебную `DBA`, **не на базу 1С** [практика]; переменные в начале: `@CreateJobs = 'Y'`, `@BackupDirectory`, `@CleanupTime`, `@OutputFileDirectory`, `@LogToTable = 'Y'` [код].
- Задания (`DatabaseBackup - …`, `DatabaseIntegrityCheck - SYSTEM_DATABASES`/`USER_DATABASES`, `IndexOptimize - USER_DATABASES`, `sp_delete_backuphistory`, `sp_purge_jobhistory`, `CommandLog Cleanup`, `Output File Cleanup`) создаются **без расписаний** — только `sp_add_job`, `sp_add_jobstep`, `sp_add_jobserver` [код].
- Умолчания `IndexOptimize`: `@FragmentationLow = NULL`, `@FragmentationMedium = 'INDEX_REORGANIZE,INDEX_REBUILD_ONLINE,INDEX_REBUILD_OFFLINE'`, `@FragmentationHigh = 'INDEX_REBUILD_ONLINE,INDEX_REBUILD_OFFLINE'`, `@FragmentationLevel1 = 5`, `@FragmentationLevel2 = 30`, `@MinNumberOfPages = 1000`, **`@UpdateStatistics = NULL`**, `@OnlyModifiedStatistics = 'N'`, `@LOBCompaction = 'Y'`, `@MaxDOP`, `@TimeLimit`, `@LockTimeout` — `NULL` [код].
- Важное для 1С [код `IndexOptimize.sql`]: при `allow_page_locks = 0` действие `INDEX_REORGANIZE` недопустимо — берётся следующее из списка; `INDEX_REBUILD_ONLINE` допустимо только при `EngineEdition` 3, 5, 8; онлайн-перестроение индекса без страничных блокировок — принудительно `MAXDOP = 1` (KB 2292737); статистика только что перестроенного (непартиционированного) индекса повторно не обновляется; `@StatisticsSample = 100` — это `FULLSCAN`; `@OnlyModifiedStatistics = 'Y'` — только при `modification_counter > 0`; `@TimeLimit` и `@LockTimeout` — в секундах; `@Execute = 'N'` — только напечатать команды.
- `DatabaseIntegrityCheck`: `@CheckCommands` (`CHECKDB`, `CHECKFILEGROUP`, `CHECKTABLE`, `CHECKALLOC`, `CHECKCATALOG`), `@PhysicalOnly`, `@DataPurity`, `@NoIndex`, `@ExtendedLogicalChecks` (несовместим с `@PhysicalOnly`), `@TabLock`, `@MaxDOP`, `@TimeLimit`, `@LockTimeout`, `@LogToTable`.

## 12. Регламент на собственном T-SQL

Скрипты рассчитаны на SQL Server 2016+ и выполняются шагом задания агента с `@database_name = N'buh'` от имени владельца задания из `sysadmin` (или от учётной записи с `db_owner` в базе) [практика]. Перед вводом в эксплуатацию — прогон на копии базы. Вывод шага направлять в файл (`@output_file_name`) — `PRINT` попадёт туда [MS Learn — параметр `sp_add_jobstep`].

### 12.1. Индексы с учётом 8.3.22+

```sql
/* Обслуживание индексов базы 1С. Реорганизация — по ИТС-мет 5837 (временное включение
   страничных блокировок), перестроение — онлайн в Enterprise/Developer, офлайн в Standard
   только при @AllowOfflineRebuild = 1 (ОКНО ОБСЛУЖИВАНИЯ: офлайн-перестроение блокирует таблицу). */
SET NOCOUNT ON;
SET LOCK_TIMEOUT 60000;                      -- ждать блокировку не дольше 60 с (ошибка 1222)
DECLARE @MinPages            int   = 1000,
        @ReorgFrag           float = 10.0,   -- фрагментация для реорганизации, %
        @RebuildFrag         float = 30.0,   -- фрагментация для перестроения, %
        @LowDensity          float = 70.0,   -- плотность ниже — уплотнить, %
        @MaxDop              int   = 4,      -- для онлайн-перестроения (Enterprise)
        @AllowOfflineRebuild bit   = 0,      -- 1 — разрешить офлайн-перестроение (Standard), только в окне
        @Minutes             int   = 180;    -- лимит прохода; текущая команда доработает до конца
DECLARE @deadline datetime2 = DATEADD(MINUTE, @Minutes, SYSDATETIME()),
        @online   bit = CASE WHEN CAST(SERVERPROPERTY('EngineEdition') AS int) = 3 THEN 1 ELSE 0 END;
DECLARE @schema sysname, @table sysname, @index sysname, @frag float, @dens float, @pages bigint,
        @pagelocks bit, @obj nvarchar(800), @cmd nvarchar(max), @action nvarchar(20);

IF OBJECT_ID(N'tempdb..#work') IS NOT NULL DROP TABLE #work;
SELECT s.name AS schema_name, t.name AS table_name, i.name AS index_name,
       ips.avg_fragmentation_in_percent AS frag,
       ips.avg_page_space_used_in_percent AS dens,      -- NULL в режиме LIMITED
       ips.page_count AS pages, i.allow_page_locks
INTO #work
FROM sys.dm_db_index_physical_stats(DB_ID(), NULL, NULL, NULL, 'SAMPLED') AS ips
JOIN sys.indexes AS i ON i.object_id = ips.object_id AND i.index_id = ips.index_id
JOIN sys.tables  AS t ON t.object_id = i.object_id
JOIN sys.schemas AS s ON s.schema_id = t.schema_id
WHERE ips.index_id > 0 AND ips.index_level = 0 AND ips.alloc_unit_type_desc = N'IN_ROW_DATA'
  AND ips.page_count >= @MinPages AND i.is_disabled = 0 AND t.is_ms_shipped = 0
  AND (ips.avg_fragmentation_in_percent >= @ReorgFrag
       OR ISNULL(ips.avg_page_space_used_in_percent, 100) < @LowDensity);

DECLARE c CURSOR LOCAL FAST_FORWARD FOR
  SELECT schema_name, table_name, index_name, frag, dens, pages, allow_page_locks
  FROM #work ORDER BY pages DESC;
OPEN c;
FETCH NEXT FROM c INTO @schema, @table, @index, @frag, @dens, @pages, @pagelocks;
WHILE @@FETCH_STATUS = 0 AND SYSDATETIME() < @deadline
BEGIN
  SET @obj = QUOTENAME(@index) + N' ON ' + QUOTENAME(@schema) + N'.' + QUOTENAME(@table);
  SET @action = CASE WHEN @frag >= @RebuildFrag OR ISNULL(@dens, 100) < @LowDensity - 10
                     THEN N'REBUILD' ELSE N'REORGANIZE' END;
  IF @action = N'REBUILD' AND @online = 0 AND @AllowOfflineRebuild = 0
     SET @action = N'REORGANIZE';             -- днём в Standard — только реорганизация
  BEGIN TRY
    IF @action = N'REBUILD'
    BEGIN
      SET @cmd = N'ALTER INDEX ' + @obj + N' REBUILD WITH ('
        + CASE WHEN @online = 1
               THEN N'ONLINE = ON (WAIT_AT_LOW_PRIORITY (MAX_DURATION = 5 MINUTES, ABORT_AFTER_WAIT = SELF)), MAXDOP = '
                    + CAST(CASE WHEN @pagelocks = 0 THEN 1 ELSE @MaxDop END AS nvarchar(3))   -- как в Ola: без страничных блокировок MAXDOP > 1 может увеличить фрагментацию (4.1)
               ELSE N'ONLINE = OFF' END
        + N');';
      EXEC sys.sp_executesql @cmd;
    END
    ELSE
    BEGIN
      IF @pagelocks = 0
        EXEC (N'ALTER INDEX ' + @obj + N' SET (ALLOW_PAGE_LOCKS = ON, ALLOW_ROW_LOCKS = ON);');
      EXEC (N'ALTER INDEX ' + @obj + N' REORGANIZE;');
      IF @pagelocks = 0
        EXEC (N'ALTER INDEX ' + @obj + N' SET (ALLOW_PAGE_LOCKS = OFF, ALLOW_ROW_LOCKS = ON);');
    END;
    PRINT CONVERT(nvarchar(19), SYSDATETIME(), 120) + N' ' + @action + N' ' + @obj
        + N' frag=' + CAST(CAST(@frag AS decimal(5,1)) AS nvarchar(10))
        + N' pages=' + CAST(@pages AS nvarchar(20));
  END TRY
  BEGIN CATCH
    PRINT N'ОШИБКА ' + @action + N' ' + @obj + N': ' + ERROR_MESSAGE();
    IF @pagelocks = 0
    BEGIN
      BEGIN TRY
        EXEC (N'ALTER INDEX ' + @obj + N' SET (ALLOW_PAGE_LOCKS = OFF, ALLOW_ROW_LOCKS = ON);');
      END TRY
      BEGIN CATCH
        PRINT N'!!! НЕ УДАЛОСЬ ВЕРНУТЬ ALLOW_PAGE_LOCKS = OFF: ' + @obj + N' — ' + ERROR_MESSAGE();
      END CATCH;
    END;
  END CATCH;
  FETCH NEXT FROM c INTO @schema, @table, @index, @frag, @dens, @pages, @pagelocks;
END;
CLOSE c; DEALLOCATE c;
```

Пояснения [практика, если не указано иное]:

- `SAMPLED` по всей большой базе сам по себе долгий; при нехватке окна — `LIMITED` (тогда `dens` = `NULL`, критерий плотности не работает [MS Learn]) или сбор списка заранее в отдельном задании.
- Пороги — стартовые (2.4). Секционирование таблиц платформа, насколько известно, не использует, и в перечне допустимых операций ИТС его нет [ИТС-КС разд. 5.5] ⚠; если секционированные индексы есть — скрипт обрабатывает каждую секцию как отдельную строку, но команду выполняет для индекса целиком (доработать).
- Скрипт не трогает индексы, у которых страничные блокировки изначально включены, кроме реорганизации; после сбоя — проверка 4.2.
- Онлайн-перестроение недоступно для некоторых индексов (3.4) — ошибка попадёт в `CATCH`, индекс останется необработанным; такие обслуживать офлайн в окне.

### 12.2. Статистика: `FULLSCAN` только изменившихся

```sql
SET NOCOUNT ON;
DECLARE @Minutes int = 120,          -- лимит прохода
        @MaxDop  int = 4;            -- MAXDOP в UPDATE STATISTICS: 2016 SP2 / 2017 CU3+
DECLARE @deadline datetime2 = DATEADD(MINUTE, @Minutes, SYSDATETIME()),
        @stat nvarchar(800), @sql nvarchar(max), @mods bigint;
DECLARE c CURSOR LOCAL FAST_FORWARD FOR
  SELECT QUOTENAME(SCHEMA_NAME(t.schema_id)) + N'.' + QUOTENAME(t.name) + N' (' + QUOTENAME(s.name) + N')',
         sp.modification_counter
  FROM sys.stats AS s
  JOIN sys.tables AS t ON t.object_id = s.object_id
  CROSS APPLY sys.dm_db_stats_properties(s.object_id, s.stats_id) AS sp
  WHERE t.is_ms_shipped = 0 AND sp.modification_counter > 0
  ORDER BY sp.modification_counter DESC;
OPEN c;
FETCH NEXT FROM c INTO @stat, @mods;
WHILE @@FETCH_STATUS = 0 AND SYSDATETIME() < @deadline
BEGIN
  SET @sql = N'UPDATE STATISTICS ' + @stat + N' WITH FULLSCAN, MAXDOP = ' + CAST(@MaxDop AS nvarchar(3)) + N';';
  BEGIN TRY
    EXEC sys.sp_executesql @sql;
  END TRY
  BEGIN CATCH
    PRINT N'ОШИБКА ' + @stat + N': ' + ERROR_MESSAGE();
  END CATCH;
  FETCH NEXT FROM c INTO @stat, @mods;
END;
CLOSE c; DEALLOCATE c;
-- по ИТС-мет 5837 после статистики — очистка кеша; на 2016+ только этой базы (необязательно, 7.1):
-- ALTER DATABASE SCOPED CONFIGURATION CLEAR PROCEDURE_CACHE;
```

- После `REBUILD` у статистики индекса `modification_counter` = 0 [вывод из смысла столбца], и скрипт её не трогает — двойной работы нет (6.6).
- На SQL Server 2016 без SP2 убрать `, MAXDOP = …` [MS Learn — «Applies to»].

### 12.5. Express: планировщик Windows и `sqlcmd`

В Express нет агента [MS Learn]; запуск — «Планировщик заданий» Windows [практика; так же в `../1c-windows/02-…`, разд. 9.6]:

```powershell
# PowerShell от имени администратора; учётная запись задачи должна иметь логин Windows в SQL Server с правами db_owner/sysadmin
$a = New-ScheduledTaskAction -Execute 'sqlcmd.exe' `
     -Argument '-S sql01\SQLEXPRESS -E -b -d buh -i C:\Scripts\buh_stats.sql -o C:\Scripts\logs\buh_stats.log'
$t = New-ScheduledTaskTrigger -Daily -At 01:30
Register-ScheduledTask -TaskName '1C buh statistics' -Action $a -Trigger $t `
     -User 'DOMAIN\svc-sqlmaint' -Password '<пароль вводит администратор>' -RunLevel Highest
# проверка
Get-ScheduledTaskInfo -TaskName '1C buh statistics'
```

`-b` — при ошибке уровня выше 10 `sqlcmd` завершается и возвращает код 1 (`ERRORLEVEL`), `-d` — начальная база (`USE`), `-i`/`-o` — входной файл и файл вывода, `-E` — доверенное подключение, `-S` — экземпляр (подтверждено 20.10.2026 по MS Learn, «sqlcmd utility»). Учётная запись `NT AUTHORITY\SYSTEM` по умолчанию не является `sysadmin` в SQL Server ⚠ (не сверялось) — задачу запускать от отдельной служебной учётной записи [практика].

| Операция | Блокировки | Ресурсы | Влияние на пользователей 1С | Источник |
|---|---|---|---|---|
| `UPDATE STATISTICS … FULLSCAN` | таблицы не блокируются | чтение всей таблицы, CPU | замедление на время работы; перекомпиляция планов | [ИТС-мет 5837; MS Learn] |
| `ALTER INDEX … SET (ALLOW_PAGE_LOCKS …)` | ⚠ не описано | мгновенно | ⚠ | 4.1 |
| `REORGANIZE` | короткие блокировки страниц | журнал, диск | обычно незаметно; возможны короткие ожидания | [MS Learn] |
| `REBUILD` офлайн (Standard) | Sch-M на таблицу всё время | журнал, диск, `tempdb` | **таблица недоступна**: ожидание, таймауты | [MS Learn; практика] |
| `REBUILD` онлайн (Enterprise) | S в начале, Sch-M в конце (кратко) | больше журнала и места, CPU | изменения медленнее; без `WAIT_AT_LOW_PRIORITY` — «пробка» в конце | [MS Learn] |
| `DBCC CHECKDB` | снимок, без блокировок | чтение всей базы, место под снимок, `tempdb` | замедление ввода-вывода | [MS Learn] |
| `DBCC FREEPROCCACHE` | — | компиляции | всплеск CPU, медленные первые запросы во всех базах | [MS Learn] |
| `DBCC SHRINKFILE` | блокировки, конфликтует с запросами | журнал, диск | ожидания; фрагментация после | [MS Learn] |

### 13.2. Согласование с регламентом 1С [практика]

- Узнать у ответственных за 1С время ночных регламентных заданий (обмены, загрузки, расчёты, закрытие месяца), работы удалённых пользователей и полного копирования; `CHECKDB` и полную копию не совмещать — обе читают всю базу.
- Офлайн-перестроение в Standard — только в согласованное окно; если в нём работают регламентные задания 1С, заблокировать их в свойствах ИБ кластера («Блокировка регламентных заданий включена»; `rac infobase update … --scheduled-jobs-deny=on` — сверить с `rac help infobase`). Для статистики, реорганизации и `CHECKDB` блокировка не нужна.
- В конце месяца и квартала пороги не менять, полное перестроение и полную `CHECKDB` переносить.
- После крупных операций 1С (загрузка `.dt`, свёртка, перепроведение, реструктуризация, удаление помеченных, массовая загрузка) — внеплановое обновление статистики затронутых таблиц [MS Learn — «после операций, меняющих распределение»].
- После перевода на новую версию SQL Server или восстановления на 2022+ — `sp_updatestats` (`AUTO_DROP`), статистика `FULLSCAN`, затем решение об уровне совместимости [MS Learn; `07-…`].

### 13.3. Ориентир расписания

| Когда | Standard | Enterprise | Источник |
|---|---|---|---|
| Каждые 15–60 мин, **и во время регламента** | `BACKUP LOG` | то же | [практика; `04-…`] |
| Ежедневно ночью | статистика `FULLSCAN` по изменившимся (12.2) | то же | [ИТС-мет 5837] |
| Ежедневно ночью | реорганизация по порогам с переключением страничных блокировок (12.1, `@AllowOfflineRebuild = 0`) | онлайн-перестроение по порогам (12.1 или Ola 11.3) | [ИТС-мет 5837; MS Learn] |
| «Горячие» таблицы — 2–4 раза в день | статистика по списку (6.7) | то же | [ИТС-мет 5837 — «чаще», без чисел; частота — практика] |
| Еженедельно, окно выходного дня | офлайн-перестроение сильно фрагментированных / разреженных (12.1 с `@AllowOfflineRebuild = 1`) | — | [практика] |
| Еженедельно | `DBCC CHECKDB … PHYSICAL_ONLY` | то же, `MAXDOP` | [MS Learn] |
| Ежемесячно | полная `DBCC CHECKDB` (на рабочем или на восстановленной копии) | то же | [MS Learn; практика] |
| Ежемесячно | тестовое восстановление с замером времени | то же | [ИТС-мет 5904; 5899; `04-…`] |

Для небольших баз (до десятков гигабайт), где полная проверка и перестроение занимают минуты, достаточно одного ночного окна на всё; разносить операции имеет смысл, когда они перестают помещаться в окно [практика].

### 13.4. Контроль одним запросом [практика]

```sql
USE [buh];
SELECT
  (SELECT DATABASEPROPERTYEX(N'buh', 'LastGoodCheckDbTime'))                         AS last_good_checkdb,
  (SELECT MIN(sp.last_updated) FROM sys.stats AS s JOIN sys.tables AS t ON t.object_id = s.object_id
     CROSS APPLY sys.dm_db_stats_properties(s.object_id, s.stats_id) AS sp
     WHERE t.is_ms_shipped = 0 AND sp.modification_counter > 0)                      AS oldest_changed_stats,
  (SELECT COUNT(*) FROM sys.indexes AS i JOIN sys.tables AS t ON t.object_id = i.object_id
     WHERE i.index_id > 0 AND t.is_ms_shipped = 0 AND i.allow_page_locks = 1)        AS indexes_with_page_locks_on,
  (SELECT COUNT(*) FROM msdb.dbo.suspect_pages WHERE database_id = DB_ID())          AS suspect_pages;
```

## 14. `tempdb`, автоприращение, очистка фантомных записей

### 14.1. `tempdb` под регламентом

Настройка `tempdb` (число и размер файлов, размещение) — `02-ustanovka-i-nastrojka-ekzemplyara.md`. Здесь — что нагружает её во время обслуживания:

- **`SORT_IN_TEMPDB = ON`** при перестроении — промежуточная сортировка в `tempdb` [MS Learn].
- **Онлайн-перестроение** — версии строк на время операции [MS Learn].
- **`DBCC CHECKDB`** — рабочие таблицы в `tempdb`; оценка — `WITH ESTIMATEONLY` [MS Learn]; с флагом 2562 до 5 % размера базы и больше [MS Learn].
- **Версии строк RCSI** (управляемые блокировки 1С) копятся в `tempdb`, пока открыты длинные транзакции [MS Learn; ИТС-разр гл. 9, разд. 9.2.3.2]. Microsoft советует при планировании размера `tempdb` прогнать регламент обслуживания индексов и замерить пиковое потребление [MS Learn].
- **SQL Server 2025**: можно включить ADR в `tempdb` (тогда в ней два хранилища версий, нужен запас места; включение и выключение — с перезапуском службы) и ограничить потребление `tempdb` нагрузками через Resource Governor [MS Learn]. Для 1С не проверялось ⚠ — к тому же 2025 нет в перечне 8.3.27.

```sql
-- VIEW SERVER STATE; свободное место и потребители tempdb [MS Learn]
SELECT SUM(unallocated_extent_page_count)    * 8.0 / 1024 AS free_mb,
       SUM(version_store_reserved_page_count) * 8.0 / 1024 AS version_store_mb,
       SUM(internal_object_reserved_page_count) * 8.0 / 1024 AS internal_objects_mb,
       SUM(user_object_reserved_page_count)  * 8.0 / 1024 AS user_objects_mb
FROM tempdb.sys.dm_db_file_space_usage;
-- хранилище версий по базам, 2016 SP2 и 2017+ [MS Learn]
SELECT DB_NAME(database_id) AS db, reserved_space_kb / 1024 AS version_store_mb
FROM sys.dm_tran_version_store_space_usage ORDER BY reserved_space_kb DESC;
-- сеансы — крупнейшие потребители (внутренние объекты: сортировки, хеши) [MS Learn]
SELECT session_id, SUM(internal_objects_alloc_page_count) AS internal_alloc_pages,
       SUM(internal_objects_dealloc_page_count) AS internal_dealloc_pages
FROM sys.dm_db_task_space_usage GROUP BY session_id ORDER BY internal_alloc_pages DESC;
```

`tempdb` при каждом запуске службы создаётся заново по заданным размерам [ИТС-мет 2374, 2008; MS Learn] — разросшуюся `tempdb` правильнее вернуть перезапуском в окно, чем сжимать под нагрузкой [практика]; сжатие `tempdb` описано у Microsoft отдельной статьёй (не читалась) ⚠.

### 14.2. Автоприращение и сжатие файлов

- **Умолчания `FILEGROWTH`**: с 2016 — 64 МБ для данных и журнала; 2005–2014 — 1 МБ и 10 % [MS Learn]. ИТС: прирост 512 МБ, начальный размер данных — ожидаемый за длительный срок, журнал — чтобы не рос между `BACKUP LOG` [ИТС-мет 5904, 2019].
- **KB 315512**: в продуктивной системе автоприращение — только страховка; файлы растить заранее по мониторингу; шаг крупный (для начала — около 1/8 размера файла); задавать `MAXSIZE`; рост журнала заставляет транзакции ждать, частые росты дают много VLF; «рост–сжатие» фрагментирует файловую систему [MS Learn].
- **Обнуление**: без мгновенной инициализации новое место заполняется нулями, и транзакции ждут [ИТС-мет 6008, 2023]; IFI ускоряет рост файлов данных, а рост журнала — с 2022 для приращений до 64 МБ [MS Learn] (утверждение «IFI не работает для журнала» [ИТС-мет 6008] верно до 2022). Включение IFI — `02-ustanovka-…`.
- **`AUTO_SHRINK`** не включать: фоновое сжатие при свободных > 25 %, блокировки и новые росты [MS Learn]. `DBCC SHRINKFILE`/`SHRINKDATABASE` **фрагментируют индексы**; не сжимать регулярно [MS Learn]. С 2022 — `WAIT_AT_LOW_PRIORITY` для сжатия (при неудаче — ошибка 49516) [MS Learn].

```sql
-- параметры роста; минимальные права на строку sys.master_files — CREATE DATABASE, ALTER ANY DATABASE или VIEW ANY DEFINITION [MS Learn]
SELECT DB_NAME(database_id) AS db, name AS logical_name, type_desc, size / 128 AS size_mb,
       CASE WHEN is_percent_growth = 1 THEN CAST(growth AS varchar(10)) + ' %'
            ELSE CAST(growth / 128 AS varchar(10)) + ' MB' END AS growth, max_size
FROM sys.master_files ORDER BY db, type_desc;
-- шаг в МБ (db_owner; логические имена — из запроса выше, у баз 1С свои ⚠)
ALTER DATABASE [buh] MODIFY FILE (NAME = N'buh', FILEGROWTH = 512MB);
-- события роста из трассировки по умолчанию (механизм устаревший; замена — расширенные события, 06-…)
DECLARE @path nvarchar(260) = (SELECT path FROM sys.traces WHERE is_default = 1);
SELECT te.StartTime, te.DatabaseName, te.FileName,
       CASE te.EventClass WHEN 92 THEN N'данные' WHEN 93 THEN N'журнал' END AS file_kind,
       te.IntegerData * 8 / 1024 AS growth_mb,   -- IntegerData — число 8-КБ страниц
       te.Duration / 1000 AS duration_ms          -- в файле трассировки Duration — в микросекундах
FROM sys.fn_trace_gettable(@path, DEFAULT) AS te
WHERE te.EventClass IN (92, 93) ORDER BY te.StartTime DESC;
```

Классы 92 — Data File Auto Grow, 93 — Log File Auto Grow; трассировка по умолчанию — `log.trc` в каталоге `LOG`, путь — `sys.traces.path` при `is_default = 1`; сама она объявлена устаревшей [MS Learn]. Единицы `Duration`: в описании классов 92/93 сказано «миллисекунды», но в общем описании SQL Trace — сервер сообщает длительность в микросекундах, Profiler показывает миллисекунды, а **в файл трассировки пишутся микросекунды** (уточнено 20.10.2026 по MS Learn, «SQL Trace»); поэтому в запросе деление на 1000.

### 14.3. Очистка фантомных записей (ghost cleanup)

- Удалённые из листовых страниц строки не стираются сразу, а помечаются «фантомными»; это нужно для блокировок на уровне строк и для версий строк. Физически их удаляет фоновый процесс очистки — **один поток на экземпляр**; он обходит только базы, помеченные как имеющие фантомные записи, и пропускает базу, если не может взять на ней общую блокировку [MS Learn].
- `ghost_record_count` — готовые к удалению; `version_ghost_record_count` — удерживаемые незавершённой транзакцией со snapshot-изоляцией (в `LIMITED` оба `NULL`) [MS Learn]. В базах 1С с RCSI длинная транзакция или «зависший» сеанс удерживает такие записи [вывод] — поиск длинных транзакций — `06-monitoring-i-diagnostika.md`.
- Флаг **661** отключает очистку; Microsoft допускает это на нагруженных системах с массовыми удалениями, если очистка вытесняет «горячие» страницы из буферного пула, но предупреждает: база растёт, появляются разделения страниц, место может закончиться; постоянно отключать не рекомендуется; при отключённой очистке фантомные строки убирает перестроение индексов [MS Learn]. Для 1С — не включать [практика].
- После массового удаления (удаление помеченных объектов, свёртка, очистка регистров) — проверить фантомные записи и плотность; если очистка не успевает — перестроение затронутых индексов в окно [MS Learn — перестроение не переносит фантомные строки; практика].

```sql
-- приблизительное число фантомных записей по базам [MS Learn]; на больших экземплярах долго — лучше по одной базе
SELECT DB_NAME(database_id) AS database_name, SUM(ghost_record_count) AS total_ghost_records
FROM sys.dm_db_index_physical_stats(NULL, NULL, NULL, NULL, 'SAMPLED')
GROUP BY database_id ORDER BY total_ghost_records DESC;
```

## Что не удалось подтвердить

- ⚠ Что платформа 8.3.22+ создаёт индексы с `ALLOW_PAGE_LOCKS = OFF`, известно только из ИТС-мет 5837 — в документации 8.3.27 и 8.5.1 этого и причины нет; переводит ли платформа в `OFF` индексы старых баз и как ведёт себя при временно включённых страничных блокировках — не описано.
- ⚠ Блокировки самой команды `ALTER INDEX … SET (ALLOW_PAGE_LOCKS = …)`. (Номер ошибки при реорганизации без страничных блокировок — 2552 — подтверждён 20.10.2026, раздел 4.1.)
- ⚠ Какие команды SQL Server выполняет реиндексация 1С (`/IBCheckAndRepair -ReIndex`). (Что аналога в `ibcmd` 8.3.27 нет, а `1cv8a ib-check-and-repair` реиндексацию не делает, — уточнено 20.10.2026 по прил. 4, раздел 1.2.)
- ⚠ Упорядоченность значений «Ссылки» на MS SQL и тип её столбца; типы столбцов хранилищ значений (LOB, онлайн-перестроение); включает ли платформа `READ_COMMITTED_SNAPSHOT` сама; задаёт ли платформа уровень совместимости при создании базы (правило Microsoft для новых баз — раздел 1.3); сохранение изменённых параметров индексов после реструктуризации.
- ⚠ Противоречия документации Microsoft: минимальное журналирование офлайн-`REBUILD` в SIMPLE/BULK_LOGGED (`ALTER INDEX`) против «оба вида перестроения журналируются полностью» (руководство по онлайн-операциям); блокировка при офлайн-перестроении некластерного индекса (Sch-M в `ALTER INDEX`, S в `DBCC DBREINDEX`); `CLEAR PROCEDURE_CACHE` на вторичных репликах («можно» в описании аргумента, «только первичная» в примере). Журналирование `REORGANIZE` прямо не описано (однопоточность подтверждена — раздел 3.1).
- ⚠ Поведение `SET AUTO_UPDATE_STATISTICS_ASYNC` под нагрузкой (требования монопольного доступа в документации нет — раздел 6.3); параллельный сбор статистики в Standard. (Права `db_owner` на `CLEAR PROCEDURE_CACHE` и минимальные права на `sys.master_files` уточнены 20.10.2026.)
- ⚠ Планы обслуживания на Linux (вывод из неподдерживаемой подсистемы SSIS). (Перезапуск после `mssql-conf set sqlagent.enabled true` и пакет `mssql-tools18` подтверждены 20.10.2026.)
- ⚠ dbatools, sp_Blitz, sp_WhoIsActive не рассматривались. (Неподдержка SQL Server 2016 текущей версией Ola и поведение Adaptive Index Defrag на индексах без страничных блокировок уточнены 20.10.2026 по коду — разделы 11.2 и 4.4.)
- ⚠ Права `NT AUTHORITY\SYSTEM`; завершит ли ошибка `CHECKDB` (уровень 16) шаг задания неуспехом; ключ `rac … --scheduled-jobs-deny` (сверять с `rac help`); пакетный запуск `/IBCheckAndRepair` для серверной базы. (Единицы `Duration` в файле трассировки — микросекунды — и ключи `sqlcmd` уточнены 20.10.2026.)
- ⚠ Поддержка SQL Server 2025 платформой (нет в ИТС 8.3.27 и 8.5.1); ADR в `tempdb` и ограничение `tempdb` (2025) для 1С не оценивались (редакции уточнены — раздел 1.4).
