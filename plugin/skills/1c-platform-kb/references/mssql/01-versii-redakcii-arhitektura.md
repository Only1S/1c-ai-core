## Кратко — главные факты

1. **MS SQL — только при рабочих серверах 1С на Windows x86-64.** Рабочий процесс кластера на Linux с MS SQL взаимодействовать не может [ИТС-КС разд. 2.3], автономный сервер `ibsrv` на Linux — тоже [ИТС-адм разд. 7.2]; на ARM64 и E2K MS SQL не поддерживается [ИТС-КС разд. 1.2.1, 1.5.4]. Сам SQL Server может работать на Linux, если рабочие серверы 1С — на Windows [v8.1c.ru].
2. **Платформа 8.3.27 поддерживает** SQL Server 2000 SP1 (реком. SP4), 2005 SP3, 2008 SP1, 2008 R2, 2012, 2014, 2016, 2017, 2019, 2022 [ИТС-КС разд. 1.5.4]; в 8.5.1 строки о MS SQL не менялись [`otlichiya-8.5.1`]. **SQL Server 2025 нет ни в ИТС, ни на v8.1c.ru** (проверено 20.10.2026) ⚠.
3. **Сроки поддержки Microsoft** (последний день): 2016 — расширенная закончилась 14.07.2026, дальше платные ESU до 17.07.2029; 2017 — расширенная до 12.10.2027; 2019 — основная закончилась 28.02.2025, расширенная до 08.01.2030; 2022 — основная до 11.01.2028, расширенная до 11.01.2033; 2025 — выпуск 18.11.2025, основная до 06.01.2031, расширенная до 06.01.2036 [MS Learn].
4. **Выбор для новой установки под 1С на октябрь 2026** — SQL Server 2022 с последним CU (CU27, сборка 16.0.4295.3; с исправлением безопасности — 16.0.4305.5, октябрь 2026) [MS Learn; практика]: версия в основной поддержке и в списке 1С.
5. **Пакетов обновлений (SP) с SQL Server 2017 нет**, только накопительные (CU) и исправления безопасности (GDR) [MS Learn]. Уровень CU показывает `SERVERPROPERTY('ProductUpdateLevel')` [MS Learn].
6. **Номер версии и уровень совместимости:** 2016 — 13.x/130, 2017 — 14.x/140, 2019 — 15.x/150, 2022 — 16.x/160, 2025 — 17.x/170. Новая база получает уровень `model`; восстановленная или подключённая со старого сервера сохраняет свой [MS Learn].
7. **Редакции:** Enterprise, Standard, Express (бесплатная), Developer (бесплатная, только разработка и тесты; в 2025 — Enterprise Developer и Standard Developer), Evaluation (180 дней). Web — только для хостинга и в 2025 отменена; Express with Advanced Services в 2025 слита с Express [MS Learn].
8. **Standard:** до 2022 включительно — меньшее из 4 сокетов или 24 ядер и 128 ГБ буферного пула; в 2025 — 4 сокета или 32 ядра и 256 ГБ; размер базы — 524 ПБ [MS Learn].
9. **Express:** 1 сокет или 4 ядра, 1410 МБ буферного пула, база до 10 ГБ (до 2022) или до 50 ГБ (2025), без SQL Server Agent, Database Mail, сжатия копий и CDC [MS Learn] — только для малых баз 1С.
10. **Только в Enterprise** (все версии): онлайн-перестроение индексов, полноценные группы доступности (в Standard — базовые: 2 реплики, 1 база), упреждающее чтение и «advanced scanning», параллельные операции с индексами и параллельная проверка `DBCC CHECKDB`; функции интеллектуальной обработки запросов (пакетный режим для rowstore, обратная связь по памяти, по оценке кардинальности, по степени параллелизма) [MS Learn].
11. **В виртуальной машине пределы редакции считаются по логическим процессорам**, а не по ядрам [MS Learn]. Больше 64 логических процессоров на узел NUMA SQL Server не поддерживает; с 2022 CU11 служба в такой конфигурации не стартует [MS Learn].
12. **Лицензирование:** Enterprise — только «на ядро»; Standard — «на ядро» или «сервер + CAL»; ядерные лицензии продаются пакетами по 2, минимум 4 лицензии на физический процессор и 4 на виртуальную машину; лицензирование отдельной ВМ — только с Software Assurance или подпиской [MS Лицензирование].
13. **Сервер + CAL и 1С:** пул соединений и мультиплексирование не уменьшают число нужных лицензий [MS Лицензирование] — значит, при модели «сервер + CAL» клиентская лицензия нужна каждому пользователю или устройству 1С, хотя к SQL Server подключается только кластер 1С [практика].
14. **Без SA или подписки нет прав на резервные экземпляры** (пассивные реплики, узлы отказоустойчивого кластера); с SA — один пассивный экземпляр для HA, один для DR и один для DR в Azure на каждый лицензированный экземпляр [MS Лицензирование].
15. **Linux и Windows лицензируются одинаково**, контейнер считается виртуальной средой ОС [MS Лицензирование].
16. **SQLOS** — собственный планировщик SQL Server: кооперативная многозадачность, квант до 4 мс, рабочий поток выделяется только активному запросу; поэтому «Диспетчер задач» плохо отражает картину — смотрите ожидания [MS Learn; ИТС-мет 6008, 2023].
17. **Память:** `max server memory (MB)` по умолчанию 2 147 483 647 — задавать обязательно; с 2012 ограничивает буферный пул и все кеши, но не стеки потоков (2 МБ на поток в x64) и не память сторонних DLL [MS Learn].
18. **Хранение:** страница 8 КБ, экстент 64 КБ, строка до 8060 байт (столбцы переменной длины могут уходить в `ROW_OVERFLOW_DATA`); ключ кластерного индекса до 900 байт, некластерного — до 1700 байт с SQL Server 2016 [MS Learn]. 1С ограничивает индекс 16 полями, запись индекса — 900 байтами [ИТС-разр прил. 8, разд. 8.1, 8.4].
19. **Журнал транзакций:** запись с упреждением (WAL), журнал делится на виртуальные файлы (VLF); их число зависит от шага роста; с 2022 рост до 64 МБ даёт один VLF и использует мгновенную инициализацию [MS Learn].
20. **Контрольные точки:** у баз, созданных в SQL Server 2016 и новее, — косвенные (`TARGET_RECOVERY_TIME` = 60 с); базы, перенесённые с более старых версий, остаются на автоматических, пока не изменить [MS Learn].
21. **Изоляция в 1С:** управляемые блокировки на SQL Server 2005+ — Read Committed Snapshot (согласованное чтение вне транзакции), автоматические — Repeatable Read или Serializable [ИТС-разр гл. 9, разд. 9.2.3.2]. Сами управляемые блокировки держит сервис транзакционных блокировок кластера 1С, а не SQL Server [ИТС-КС разд. 2.2.3.1]. В SQL Server `READ_COMMITTED_SNAPSHOT` по умолчанию выключен [MS Learn] — проверяйте `is_read_committed_snapshot_on`; ⚠ кто включает его для базы 1С, ИТС не пишет.
22. **Хранилище версий:** в базе с RCSI версионируется каждое изменение, к строке добавляется до 14 байт; версии лежат в tempdb и держатся до конца самой длинной транзакции, которой они нужны; при включённом ADR версии хранятся в самой базе (PVS) [MS Learn].
23. **Эскалация блокировок SQL Server:** от 5000 блокировок одного оператора на таблицу (или секцию) либо при 24 % памяти под блокировки; 1С советует отключать её флагами 1224/1211 [MS Learn; ИТС-мет 5946, 2019]. У самой 1С своя эскалация управляемых блокировок — от 100 000 на пространство [ИТС-разр гл. 9, разд. 9.2.3.6].
24. **Query Store** включён по умолчанию для новых баз начиная с 2022 (в 2016–2019 — нет); без него не работают обратная связь по параллелизму и по оценке кардинальности и сохранение обратной связи по памяти; он же — главный инструмент при повышении уровня совместимости [MS Learn].
25. **Как 1С хранит данные:** одна ИБ — одна база SQL Server; таблицы `_Reference<n>`, `_Document<n>`, `_AccumRg<n>`…; типы: число — `NUMERIC(n,k)`, строка — `NCHAR`/`NVARCHAR`/`NTEXT`, дата — `DATETIME`, булево — `BINARY(1)`, хранилище значения — `IMAGE`, ссылка — `BINARY(16)`; поле составного типа — несколько столбцов с суффиксами `_TYPE`, `_RTRef`, `_RRRef` и др. [ИТС-мет 1828, 2013; ИТС-адм разд. 5.2.1.3.2]; таблица `_YearOffset` (смещение дат) есть только на MS SQL [`razmeshchenie-dannyh-tablicy-i-polya.md`].

## 1. Где MS SQL Server стоит в схеме 1С

### 1.1. Кто с кем соединяется

- Каждая информационная база клиент-серверного варианта хранится в отдельной базе СУБД; к СУБД обращаются процессы кластера 1С, а не клиентские приложения [ИТС-КС разд. 2.1, конспект `../its-docs/cs-gl02-klient-servernyj-variant-p1.md`]. Драйвер SQL Server и сетевой доступ к порту СУБД нужны только рабочим серверам 1С и машинам администраторов [практика].
- Рабочий процесс (`rphost`) обращается к SQL Server через Microsoft OLE DB Driver for SQL Server актуальной версии или SQL Server Native Client; наличие драйвера проверяется при создании и загрузке ИБ и при обновлении конфигурации базы данных [ИТС-КС разд. 1.5.4]. Подробно о драйверах и шифровании (OLE DB Driver 19 по умолчанию требует шифрования) — `mssql/02-…` и `../1c-windows/02-ms-sql-server-dlya-1c.md`, раздел 3.5.
- Пользователь СУБД — из свойств ИБ («Пользователь базы данных»); если он не указан, кластер подключается с аутентификацией ОС от имени пользователя конкретного рабочего процесса [ИТС-адм разд. 5.2.1.3.2]. Права и логины — `mssql/03-…`.
- Защита канала «кластер ↔ СУБД» — средствами самой СУБД; все поддерживаемые СУБД умеют шифровать трафик (SSL/TLS) [ИТС-КС разд. 2.2.9.6].
- Транзакционные (управляемые) блокировки 1С хранит **сервис транзакционных блокировок** кластера, в памяти, с разделением по ИБ [ИТС-КС разд. 2.2.3.1]. SQL Server при этом держит собственные блокировки строк и страниц — это два независимых уровня (раздел 13).

### 1.3. Смешанная среда: что делать с базами на MS SQL

| Сценарий | Решение | Источник |

| Нужен MS SQL, а основной кластер на Linux | отдельный кластер 1С на Windows для этих баз | [ИТС-КС разд. 2.3; практика] |
| Хочется держать СУБД на Linux | SQL Server на Linux допустим только при Windows-серверах 1С; для серверов 1С на Linux — PostgreSQL | [v8.1c.ru; ИТС-КС разд. 2.3] |
| Базы сервисов (Redmine, NetBox…) | в отдельной СУБД, не в экземпляре баз 1С | [практика; правило базы знаний] |

### 1.4. Что из SQL Server нужно администратору 1С

Таблицы, индексы и запросы создаёт платформа; на администраторе — версия и редакция, лицензии, параметры экземпляра, файлы и журнал, копии, регламент, мониторинг, обновления. Схему данных 1С вручную не меняют, работать с данными в обход штатных механизмов нельзя [ИТС-мет 1798, 2025]. Дальше — устройство SQL Server в объёме, без которого непонятны рекомендации 1С и Microsoft.

### 2.4. Как узнать версию, выпуск и CU

T‑SQL (SSMS или `sqlcmd`, любой логин; свойства из `SERVERPROPERTY` документированы на MS Learn):

```sql
SELECT @@VERSION;                                         -- строка с версией, CU и выпуском ОС
SELECT SERVERPROPERTY('ProductVersion')        AS product_version,   -- 16.0.4295.3
       SERVERPROPERTY('ProductMajorVersion')   AS major,             -- 16
       SERVERPROPERTY('ProductLevel')          AS product_level,     -- RTM / SPn
       SERVERPROPERTY('ProductUpdateLevel')    AS update_level,      -- CUn или NULL
       SERVERPROPERTY('ProductUpdateReference') AS kb,               -- номер статьи KB
       SERVERPROPERTY('Edition')               AS edition,
       SERVERPROPERTY('EngineEdition')         AS engine_edition,    -- 2 Standard, 3 Enterprise, 4 Express …
       SERVERPROPERTY('InstanceName')          AS instance_name,     -- NULL = экземпляр по умолчанию
       SERVERPROPERTY('IsClustered')           AS is_fci,
       SERVERPROPERTY('IsHadrEnabled')         AS hadr_enabled,
       SERVERPROPERTY('Collation')             AS server_collation;
```

`EngineEdition`: 2 — Standard (в том числе Standard Developer и Web), 3 — Enterprise (в том числе Enterprise Developer, Developer и Evaluation), 4 — Express (в том числе Express with Advanced Services) [MS Learn]. Поэтому по `EngineEdition` Developer от боевой Enterprise не отличить — смотрите `Edition`.

Командная строка Windows (cmd, любой пользователь с доступом к SQL Server по Windows-аутентификации):

```bat
sqlcmd -S sql01 -E -Q "SELECT SERVERPROPERTY('ProductVersion'), SERVERPROPERTY('ProductUpdateLevel'), SERVERPROPERTY('Edition')"
```

Linux (с установленными `mssql-tools`/`sqlcmd`; пример — из руководства по установке [MS Learn]):

```bash
sqlcmd -S localhost -U sa -Q 'select @@VERSION'
```

Проверка результата: `ProductVersion` сравнить с таблицей 2.3; если `ProductUpdateLevel` = `NULL` на 2017+, CU не установлен ни одного [практика].

### 3.2. SQL Server 2025 и 1С

- В ИТС 8.3.27, в изменениях 8.5.1 и на v8.1c.ru SQL Server 2025 не упомянут ⚠ (проверено 20.10.2026). Использовать его для рабочих баз 1С — на свой риск, без поддержки 1С [практика].
- Риски [MS Learn; ⚠ для 1С не проверено]: новые умолчания шифрования (TDS 8.0; OLE DB Driver 19 требует `Encrypt` и проверяет сертификат — без доверенного сертификата ломаются связанные серверы и удалённый дистрибьютор репликации); уровень 170 меняет поведение оптимизатора; полнотекстовые индексы версии 1 после обновления не работают до перестроения (1С полнотекстовый поиск SQL Server, по-видимому, не использует ⚠).
- Если 2025 всё же поставлен: оставить базу 1С на уровне совместимости 160 и проверить на копии [практика].

### 3.3. SQL Server 2014 и флаг 4199

ИТС для SQL Server 2014 требует флаг трассировки 4199 для базы: если он не установлен глобально, платформа пытается включать его на каждом соединении от имени пользователя ИБ, и при нехватке прав выдаёт ошибку [ИТС-адм разд. 5.2.1.3.2]. Флаг 4199 включает исправления оптимизатора из CU и SP; начиная с уровня совместимости 130 исправления, сделанные к прежним выпускам, включены и без флага, а пост-RTM исправления текущей версии — только с флагом или параметром базы `QUERY_OPTIMIZER_HOTFIXES = ON` [MS Learn]. Для 2016+ вопрос флага — `mssql/02-…`.

### 4.3. Как считаются ядра и процессоры

- Предел редакции — максимум сокетов и максимум ядер, видимых ОС, для **одного экземпляра**, а не сервера [MS Learn].
- **В ВМ предел считается по логическим процессорам** (архитектура гостю не видна) [MS Learn]: ВМ Standard 2022 с 32 vCPU использует не больше 24 [вывод]. Для Standard 2025 «32 ядра» означает 32 аппаратных потока [MS Лицензирование].

Проверка, сколько процессоров реально использует экземпляр (T‑SQL, право `VIEW SERVER STATE`; с 2022 — `VIEW SERVER PERFORMANCE STATE`):

```sql
-- топология и выпуск; socket_count, cores_per_socket, numa_node_count — с 2016 SP2 [MS Learn]
SELECT cpu_count, hyperthread_ratio, socket_count, cores_per_socket, numa_node_count,
       scheduler_count, max_workers_count, virtual_machine_type_desc,
       SERVERPROPERTY('Edition') AS edition
FROM sys.dm_os_sys_info;

-- планировщики пользовательских запросов: ONLINE — используются, OFFLINE — не используются
SELECT status, COUNT(*) AS schedulers
FROM sys.dm_os_schedulers
WHERE scheduler_id < 1048576
GROUP BY status;
```

`VISIBLE OFFLINE` по документации означает процессоры, выключенные маской привязки (affinity) [MS Learn]. Что ограничение редакции (например, 24 ядра у Standard) тоже проявляется как `VISIBLE OFFLINE` и сообщением в журнале ошибок при запуске — практика администраторов ⚠ (в прочитанной документации не описано). Если планировщиков `VISIBLE ONLINE` меньше, чем `cpu_count`, проверьте маску привязки и редакцию [практика].

### 4.5. Express под 1С

Пределы Express (раздел 4.2) и отсутствие SQL Server Agent означают [практика]:

- резервные копии и регламент — через планировщик Windows и `sqlcmd` (пример — `../1c-windows/02-…`, раздел 9.6);
- копии базы данных 1С по механизму «Версия2» на MS SQL используют CDC и требуют работающей службы SQL Server Agent [ИТС-разр гл. 26; `../its-docs/dev-gl26-kopii-bazy-dannyh.md`], а в Express нет ни того, ни другого [MS Learn] — значит, «Версия2» на Express работать не будет (вывод);
- буферный пул 1410 МБ — даже база 10 ГБ почти целиком читается с диска; Express уместен для 1–5 пользователей и малых баз [практика].

### 4.6. Как узнать и сменить редакцию

- Узнать — `SERVERPROPERTY('Edition')` и `SERVERPROPERTY('EngineEdition')` (раздел 2.4) [MS Learn].
- Смена редакции (например, Evaluation или Developer → Standard) выполняется установщиком без переустановки — `mssql/07-…`. Перед сменой — полная копия всех баз [практика].

## 5. Лицензирование — только факты Microsoft

Юридически обязывающие условия — Product Terms и ваш договор; «licensing guidance» Microsoft прямо называет себя пояснением, не заменяющим Product Terms [MS Лицензирование]. Ниже — условия программы EA/EAS по Product Terms на 20.10.2026 и пояснения из «SQL Server 2025 licensing guidance». Цены и условия другой программы (CSP, MPSA, OEM, SPLA у хостера) могут отличаться — сверяйте с партнёром.

### 5.1. Две модели лицензирования

| Редакция | «Сервер + CAL» | «На ядро» (Per Core) |
|---|---|---|
| Enterprise | нет (новые лицензии Server/CAL не продаются; действующие клиенты с SA могут продлевать) | да |
| Standard | да | да |
| Express, Developer, Evaluation | бесплатны (Developer и Evaluation — не для промышленной эксплуатации) | — |

Источник: [MS Лицензирование] (Product Terms, licensing guidance, страница цен 2022).

- **«На ядро»**: лицензии покупаются на ядра физического сервера или виртуальной машины; пользователям и устройствам CAL не нужны; ядерные лицензии продаются пакетами по 2 ядра [MS Лицензирование].
- **«Сервер + CAL»** (только Standard, недоступна при оплате по мере использования): лицензия на сервер плюс клиентская лицензия (CAL) на каждого пользователя или каждое устройство, обращающиеся к SQL Server [MS Лицензирование].
- Лицензии не привязаны к платформе — Windows или Linux [MS Лицензирование; MS Learn].

### 5.2. «На ядро»: лицензирование физического сервера

- Число лицензий = число физических ядер сервера, **но не меньше 4 на каждый физический процессор** [MS Лицензирование].
- **Enterprise без SA/подписки:** любое число экземпляров в физической и виртуальных средах ОС (OSE) на этом сервере — числом OSE не больше числа назначенных серверу лицензий; каждая лицензия сверх необходимого минимума добавляет ещё одну OSE. Пример Microsoft: 16 лицензий на 16-ядерный сервер — до 16 OSE, ещё 2 лицензии — до 18 OSE [MS Лицензирование].
- **Enterprise с SA/подпиской:** любое число экземпляров в неограниченном числе OSE на лицензированном сервере («неограниченная виртуализация»); не применяется вместе с License Mobility [MS Лицензирование].
- **Standard:** любое число экземпляров, но **только в физической OSE** сервера — лицензирование ядер хоста Standard не покрывает виртуальные машины на нём [MS Лицензирование].

### 5.3. «На ядро»: лицензирование отдельной виртуальной машины

- Доступно **только для лицензий с SA или по подписке** [MS Лицензирование].
- Число лицензий = число виртуальных ядер ВМ, **не меньше 4 на ВМ**; если виртуальное ядро в какой-то момент сопоставлено больше чем одному аппаратному потоку, лицензия нужна на каждый такой поток [MS Лицензирование].
- В лицензированной ВМ — любое число экземпляров (Enterprise и Standard); с SA — ещё и неограниченное число контейнеров внутри этой ВМ [MS Лицензирование].
- Переназначать лицензии между серверами одной «серверной фермы» можно сколько угодно (это и позволяет переносить ВМ кластера виртуализации); между фермами — не чаще одного раза в 90 дней [MS Лицензирование]. Без SA назначенные серверу лицензии остаются за ним минимум 90 дней [MS Лицензирование].
- Контейнер (docker, cri-o, containerd) считается виртуальной OSE, ядра контейнера — аппаратными потоками; при включённом Hyper-Threading и лицензировании по виртуальной OSE — лицензия на каждый поток, сопоставленный контейнеру, минимум 4 [MS Лицензирование].

### 5.4. «Сервер + CAL» (Standard)

- По разделу «Server/CAL» Product Terms одна серверная лицензия разрешает один работающий экземпляр в физической или виртуальной OSE; в «Running Instances for Standard Edition» того же документа сказано, что на каждую серверную лицензию ПО работает только в одной OSE, но в ней допускается любое число экземпляров; licensing guidance пишет «один экземпляр на лицензию» ⚠ (расхождение формулировок — уточнять у партнёра) [MS Лицензирование].
- «Сервер» — физическая машина; аппаратный раздел или блейд — отдельный сервер [MS Лицензирование].
- CAL нужна **каждому пользователю или устройству**, обращающимся к SQL Server **напрямую или косвенно**, в том числе устройствам без человека; одна CAL даёт доступ к нескольким лицензированным серверам; пользовательская CAL — один пользователь с любых устройств, CAL на устройство — одно устройство для любых пользователей; CAL версии N даёт доступ к версии N и более ранним [MS Лицензирование].
- **Мультиплексирование:** любые аппаратные, программные или автоматизированные средства, которые объединяют соединения в пул или уменьшают число пользователей и устройств, непосредственно обращающихся к продукту, **не уменьшают** число нужных лицензий [MS Лицензирование, Universal License Terms].
- Для чисто административного доступа допускаются два пользователя без CAL [MS Лицензирование, Universal License Terms]; доступ другого лицензированного сервера CAL не требует [MS Лицензирование].

**Следствие для 1С** [практика, вывод из правил выше]: к SQL Server подключается только кластер 1С под одним логином, но это и есть мультиплексирование — при модели «сервер + CAL» CAL нужна каждому пользователю (или устройству) 1С, включая пользователей веб-клиента, мобильных клиентов и внешних систем, которые работают с базой через 1С. Поэтому при большом числе пользователей обычно выгоднее модель «на ядро» (пример — 5.8).

### 5.5. Права на резервные экземпляры (Software Assurance)

- Права на пассивные экземпляры для отказоустойчивости есть **только у лицензий с SA или по подписке**; без них прав на DR и HA нет, **включая узлы отказоустойчивого кластера** [MS Лицензирование].
- На каждую лицензированную «основную нагрузку» разрешены: одна пассивная OSE для любых целей, включая высокую доступность (на любом сервере); две пассивные OSE для аварийного восстановления — одна на любом сервере и одна в Azure [MS Лицензирование].
- Пассивная OSE не отдаёт данные пользователям и не выполняет активную нагрузку; OSE для аварийного восстановления — асинхронные и с ручным переключением; лицензий, которые потребовались бы пассивной OSE, не должно быть больше, чем у основной [MS Лицензирование].
- На пассивной OSE разрешены: проверка `DBCC CHECKDB`, копии журнала, полные копии, мониторинг ресурсов; одновременная работа основной и DR-копии — кратковременно для тестирования DR раз в 90 дней [MS Лицензирование].

**Следствие для 1С** [практика, вывод]: читаемая вторичная реплика, на которую 1С отправляет отчёты или запросы (например, «копия базы данных» для отчётов), — уже активная нагрузка и лицензируется полностью; реплика, на которой только делают копии и `DBCC CHECKDB`, — пассивная (при SA).

### 5.6. Бесплатные редакции и оплата по мере использования

- **Express** — бесплатная; **Developer** (2025: Enterprise Developer и Standard Developer) — только разработка, тестирование и демонстрация, тестовые данные удалить перед промышленным использованием; **Evaluation** — 180 дней, затем переход на Standard или Enterprise [MS Лицензирование; MS Learn].
- **Оплата по мере использования** (pay-as-you-go) — для SQL Server, подключённого к Azure Arc; включает набор прав, аналогичный SA; модель «сервер + CAL» в ней недоступна [MS Лицензирование].
- **Подписка** (на 1 или 3 года, например у партнёра CSP) даёт права, эквивалентные SA, на срок подписки [MS Лицензирование].

## 6. Экземпляры, службы и системные базы

### 6.1. Экземпляр

- **Экземпляр** — отдельная установка Database Engine со своими службами, базами и настройками. На одном компьютере — до 50 экземпляров (отдельный сервер) [MS Learn, «Maximum capacity specifications»].
- **Экземпляр по умолчанию** — служба `MSSQLSERVER`, обращение по имени компьютера; **именованный** — служба `MSSQL$<имя>`, обращение `компьютер\имя`; виртуальная учётная запись службы имеет вид `NT SERVICE\<имя службы>`: `NT SERVICE\MSSQLSERVER`, `NT SERVICE\MSSQL$PAYROLL`, агент — `NT Service\SQLSERVERAGENT` и `NT SERVICE\SQLAGENT$PAYROLL` [MS Learn].
- У каждого экземпляра — своя ветка реестра (пример Microsoft для 2019: `HKLM\Software\Microsoft\Microsoft SQL Server\MSSQL15.MyInstance`) [MS Learn].
- **Разные версии на одном сервере** допустимы (2022 — рядом с 2008–2019); если экземпляр по умолчанию уже занят, новая версия ставится именованным экземпляром [MS Learn].
- **Общие компоненты:** SQL Server Browser и SQL Writer (VSS) общие для всех экземпляров и версий и при установке более новой версии обновляются до неё [MS Learn].
- **В 1С** «Сервер баз данных» — имя компьютера (один экземпляр) или имя экземпляра; в примере ИТС записано `Server/instance` [ИТС-адм разд. 5.2.1.3.2], в нотации Microsoft разделитель — обратная косая черта `Server\instance` ⚠ (какой разделитель принимает платформа, ИТС не уточняет).
- **На Linux** на одном узле допускается только один экземпляр по умолчанию (несколько экземпляров — в контейнерах) [MS Learn].

### 6.2. Службы SQL Server

| Служба | Имя службы (по умолчанию / именованный экземпляр) | Исполняемый файл | Учётная запись по умолчанию | Нужна ли для 1С |
|---|---|---|---|---|
| Database Engine | `MSSQLSERVER` / `MSSQL$<экземпляр>` | `<MSSQLPATH>\MSSQL\Binn\sqlservr.exe` | виртуальная `NT SERVICE\MSSQLSERVER` | да |
| SQL Server Agent | `SQLSERVERAGENT` / `SQLAgent$<экземпляр>` | `<MSSQLPATH>\MSSQL\Binn\sqlagent.exe` | виртуальная `NT Service\SQLSERVERAGENT` | да — задания копий и регламента, CDC для копий базы данных 1С |
| SQL Server Browser | одна на компьютер ⚠ (имя службы — проверить `Get-Service`) | `C:\Program Files (x86)\Microsoft SQL Server\90\Shared\sqlbrowser.exe` | `LOCAL SERVICE` | только для именованных экземпляров без фиксированного порта и DAC к ним |
| SQL Writer | одна на компьютер (SID `NT Service\SQLWriter`) | — | `LOCAL SYSTEM` | для копий через VSS (сторонние системы копирования) |
| Full-text (FD Launcher) | SID `NT Service\MSSQLFDLauncher` / `…$<экземпляр>` | — | виртуальная | нет ⚠ (у 1С свой полнотекстовый поиск) |
| SSAS, SSRS, SSIS, Launchpad, PolyBase | разные | — | — | нет [практика] |
| CEIP (телеметрия) | `SQLTELEMETRY` и др. | — | — | нет |

Источник: «Configure Windows service accounts and permissions» [MS Learn]. Важные детали:

- **SQL Server Agent после установки отключён**, если при установке явно не выбран автозапуск; в Express служба присутствует, но отключена [MS Learn]. Проверьте сразу после установки — иначе задания копий не выполняются.
- При установке именованного экземпляра службу Browser следует запускать автоматически [MS Learn].
- **Учётную запись или пароль службы менять только через SQL Server Configuration Manager**: он заодно обновляет локальное хранилище безопасности, где защищён главный ключ службы; оснастка «Службы» Windows меняет только имя — потом, например, падают шаги заданий агента [MS Learn].
- Виртуальная учётная запись обращается к сетевым ресурсам (например, к папке для копий) от имени учётной записи компьютера `ДОМЕН\ИМЯКОМПЬЮТЕРА$`; для отказоустойчивого кластера виртуальные учётные записи не годятся — нужна доменная или gMSA [MS Learn].
- Права служб выдаются SID службы (например, «Вход в качестве службы», «Замена маркера уровня процесса», «Обход перекрёстной проверки») [MS Learn]; право мгновенной инициализации файлов и «Блокировка страниц в памяти» добавляются отдельно — `mssql/02-…`.

Проверка (PowerShell от имени администратора на сервере SQL; `Get-Service` — штатный командлет Windows):

```powershell
Get-Service -Name 'MSSQL*','SQLAgent*','SQLSERVERAGENT','SQLBrowser','SQLWriter' -ErrorAction SilentlyContinue |
  Select-Object Name, DisplayName, Status, StartType
```

T‑SQL — учётные записи, тип запуска и мгновенная инициализация файлов с точки зрения самого экземпляра (право `VIEW SERVER STATE`; с 2022 — `VIEW SERVER SECURITY STATE`) [MS Learn]:

```sql
SELECT servicename, startup_type_desc, status_desc, service_account,
       instant_file_initialization_enabled, last_startup_time
FROM sys.dm_server_services;
```

Ожидаемо для рабочего сервера 1С [практика]: Database Engine и Agent — `Automatic`/`Running`; `instant_file_initialization_enabled` = `Y`.

### 6.3. Сеть и порты

- Экземпляру по умолчанию при установке назначаются TCP-порт **1433** и именованный канал `\sql\query`; именованные экземпляры и Express по умолчанию используют **динамический порт**, назначаемый при каждом запуске [MS Learn].
- **SQL Server Browser** занимает UDP **1434** и сообщает клиенту порт нужного экземпляра. Без Browser подключение к именованному экземпляру работает только с явным портом, не работает перечисление серверов в SSMS и выделенное административное подключение (DAC) к именованному экземпляру или к экземпляру не на 1433 [MS Learn].
- Установщик SQL Server **не открывает порты** в брандмауэре Windows [MS Learn].
- 1С рекомендует: включить TCP/IP; Shared Memory — включить, если сервер 1С на той же машине; Named Pipes — выключить [ИТС-мет 5904, 2019]; оптимизированная реструктуризация (`UpdateDBCfg=v2`) работает только по TCP/IP [ИТС-адм прил. 3, разд. 3.17.23]. Настройка — `mssql/02-…`.

### 6.4. Системные базы

| База | Назначение | Для 1С |
|---|---|---|
| `master` | вся информация уровня экземпляра (логины, базы, настройки) | пользователь ИБ — `sa` или владелец базы; владельцу нужны чтение `master`, полный доступ к `tempdb` и членство в роли `processadmin` или `sysadmin` [ИТС-адм разд. 5.2.1.3.2] |
| `msdb` | задания и оповещения SQL Server Agent, история копий | копировать вместе с `master` [практика] (`mssql/04-…`) |
| `model` | шаблон новых баз: размер, сортировка, модель восстановления и другие параметры переносятся в каждую новую базу | новая ИБ на MS SQL наследует настройки `model` [ИТС-мет 5904, 2019; MS Learn] |
| `tempdb` | временные объекты и промежуточные результаты, хранилище версий; пересоздаётся при каждом запуске | сильно нагружена 1С (раздел 12) |
| Resource | только для чтения; системные объекты, видимые как схема `sys` в каждой базе | не трогать |

Источник: «System databases» [MS Learn]. Системные базы нельзя размещать на UNC-путях; системные таблицы напрямую не изменяют [MS Learn].

Экземпляр на Linux (служба `mssql-server`, `mssql-conf`) — раздел 16.

## 7. Как SQL Server выполняет работу: SQLOS, планировщики, потоки

### 7.1. SQLOS

- SQLOS — собственная «операционная система» SQL Server: сама распределяет память и процессорное время своих задач, поэтому Диспетчер задач показывает загрузку СУБД неточно — оценивать по ожиданиям; работа идёт квантами около 4 мс, перед квантом проверяется доступность ресурсов, при недоступности задача ждёт и копит время ожидания по типу ресурса [ИТС-мет 6008, 2023]. Через SQLOS идёт и низкоуровневый ввод-вывод буферного менеджера [MS Learn].

### 7.2. Запрос → задача → рабочий поток → планировщик

По «Thread and task architecture guide» [MS Learn]: **запрос** (request) — логическое представление запроса или пакета (есть и у системных операций); **задача** (task) — единица работы (у параллельного запроса — родительская и дочерние); **рабочий поток** (worker) — представление потока ОС, по одному на задачу; **планировщик** (SOS scheduler) — по одному на процессор, worker занимает его не дольше кванта (максимум 4 мс) и уступает сам — **кооперативная (невытесняющая) многозадачность**; с 2016 планирование LDF не даёт одному потоку монополизировать планировщик. Задачи в состоянии `SUSPENDED` ждут ресурс; текущие ожидания — `sys.dm_os_waiting_tasks`, статистика — `sys.dm_os_wait_stats` (`mssql/06-…`).

### 7.3. Сколько потоков: `max worker threads`

- Значение по умолчанию `0` — число рабочих потоков рассчитывается при запуске; формула: *Default Max Workers* + ((логических CPU − 4) × *Workers per CPU*) [MS Learn].
- Для 64-разрядного сервера (2016 SP2 и новее): до 4 CPU — 512; 8 — 576; 16 — 704; 32 — 960; 64 — 1472; 128 — 4480; 256 — 8576. При менее 2 ГБ памяти базовое значение делится на 2 (с 2017) [MS Learn].
- Поток выделяется **только активному запросу** и освобождается по его завершении, даже если соединение остаётся открытым [MS Learn]. Простаивающие соединения 1С потоков не держат [практика, вывод].
- Системные потоки (LazyWriter, Checkpoint, Log Writer и др.) — вне предела; менять параметр без причины Microsoft не советует: нехватка потоков обычно следствие долгих запросов, блокировок или медленного ввода-вывода [MS Learn].
- Память на одно соединение — примерно `3 × network_packet_size + 94 КБ` (пакет по умолчанию 4 КБ) [MS Learn]: 1000 соединений 1С — порядка 100 МБ [практика, расчёт].

Проверка нагрузки на планировщики (право `VIEW SERVER STATE` / `VIEW SERVER PERFORMANCE STATE`; столбцы — [MS Learn]):

```sql
SELECT scheduler_id, cpu_id, status, is_online,
       current_tasks_count, runnable_tasks_count,      -- runnable: ждут процессор
       current_workers_count, active_workers_count,
       work_queue_count                                -- задачи, ждущие свободного потока
FROM sys.dm_os_schedulers
WHERE scheduler_id < 1048576;                          -- без служебных планировщиков (DAC и др.)
```

Постоянно ненулевой `runnable_tasks_count` на многих планировщиках — признак нехватки процессора, ненулевой `work_queue_count` — нехватки рабочих потоков [практика]. Расследование — `mssql/06-…`.

### 7.4. Параллелизм

- `max degree of parallelism` ограничивает число задач (и потоков) **на ветвь плана**, а не на весь запрос: параллельный запрос резервирует примерно «число одновременно выполняемых ветвей × DOP» потоков; фактическая степень параллелизма при выполнении может быть меньше настроенной из-за нехватки памяти или потоков [MS Learn].
- Кешированный параллельный план может выполниться последовательно; число потоков определяется при каждом выполнении [MS Learn].
- 1С рекомендует `max degree of parallelism = 1` [ИТС-мет 5904, 2019; 6008, 2023] и `0` на время реструктуризации [ИТС-мет 5945, 2018]; Microsoft — до 8 в зависимости от NUMA [MS Learn]. Обоснование и команды — `mssql/02-…` и `../1c-windows/02-…`, раздел 6.3.

## 8. Память: буферный пул и другие потребители

### 8.1. Буферный пул

- Буфер — страница 8 КБ в памяти; буферный менеджер читает страницы в буферный пул и записывает изменённые («грязные») обратно; страница остаётся в памяти, пока место не понадобится [MS Learn].
- При запуске резервируется адресное пространство под целевой объём, физическая память берётся по мере нагрузки («ramp-up» ускоряется чтением сразу экстента); текущий и целевой объём — `committed_kb` и `committed_target_kb` в `sys.dm_os_sys_info` [MS Learn].
- SQL Server берёт столько памяти, сколько нужно, не создавая дефицита, и отдаёт её ОС при нехватке; постепенное уменьшение свободной памяти в Диспетчере задач — норма, а не утечка [MS Learn].

### 8.2. Что ограничивает `max server memory (MB)`

| Тип выделения | Под `max server memory` (2012+) |
|---|---|
| Выделения страниц любого размера (буферный пул, кеш планов, память компиляции, гранты памяти запросам, память менеджера блокировок) | да |
| CLR | да (с 2012) |
| Стеки потоков (x64 — 2048 КБ на поток) | **нет** |
| Прямые выделения Windows: DLL расширенных процедур, провайдеры OLE DB связанных серверов, объекты автоматизации, сторонние DLL | **нет** |

Источник: «Memory management architecture guide» [MS Learn]. Отсюда — правило: `max server memory` не равен памяти процесса; нужно оставлять запас ОС и прочим процессам [MS Learn].

- Умолчание `max server memory (MB)` — 2 147 483 647 (без предела), минимум — 128; Microsoft советует ~75 % памяти, не занятой другими процессами; с 2019 установщик Windows предлагает значение [MS Learn]. При сервере 1С на той же машине порог уменьшают на объём для 1С [ИТС-мет 5904, 2019]. Команды — `mssql/02-…`.
- С 2012 процесс может кратковременно превысить `max server memory` (большие гранты, перестроение columnstore, копии); монитор ресурсов затем возвращает память (в 2022 ускоренный возврат включён по умолчанию, в 2019 — флаг 8121) [MS Learn].
- `min server memory` — граница, ниже которой буферный пул не отдаёт набранную память; при `min` = `max` динамическое управление после набора прекращается [MS Learn].

### 8.3. Lock Pages in Memory и модель памяти

- Право «Блокировка страниц в памяти» (LPIM) позволяет держать память процесса в ОЗУ при нехватке памяти у ОС; при LPIM Microsoft настоятельно советует задать конкретный `max server memory` [MS Learn]. Без LPIM при вытеснении памяти процесса в журнале ошибок появляется сообщение MSSQLSERVER_17890 («A significant part of SQL Server process memory has been paged out») [MS Learn].
- 1С: если сервер 1С установлен вместе с SQL Server, LPIM не включать [ИТС-мет 5904, 2019].
- Модель видна в `sys.dm_os_sys_info.sql_memory_model_desc` (столбец есть с 2012 SP4 и 2016 SP1): `CONVENTIONAL` (без LPIM), `LOCK_PAGES`, `LARGE_PAGES` (LPIM плюс флаг 834 в Enterprise) [MS Learn].

### 8.4. Память запросов и вытеснение в tempdb

- Перед выполнением запрос с сортировкой или хешированием получает **грант памяти**; если минимальный грант недоступен, запрос ждёт (ожидание `RESOURCE_SEMAPHORE`), а по истечении `query wait` — получает ошибку тайм-аута [MS Learn; ИТС-мет 6008, 2023].
- В строчном режиме грант не растёт: если памяти не хватило, сортировка «проливается» в рабочую таблицу, хеш — в рабочий файл в tempdb (события Sort Warnings / Hash Warning) [MS Learn]. Отсюда рост tempdb при тяжёлых отчётах 1С [практика].
- Постоянное `RESOURCE_SEMAPHORE` — признак нехватки памяти [ИТС-мет 6008, 2023].

### 8.5. Защита страниц и ошибка 824

- При записи страницы на диск в заголовок добавляется контрольная сумма (`CHECKSUM` — по умолчанию для баз, созданных в 2005 и новее) или подпись «разорванной страницы»; при чтении проверяется. Неудачное чтение SQL Server повторяет 4 раза; если не помогло — ошибка **824** [MS Learn].
- У баз, перенесённых со старых версий, может остаться `TORN_PAGE_DETECTION` или `NONE` — Microsoft рекомендует `CHECKSUM`; новая настройка применяется к странице при следующей её записи [MS Learn]. Проверка: `SELECT name, page_verify_option_desc FROM sys.databases;` Действия при 823/824 и `DBCC CHECKDB` — `mssql/05-…`, `mssql/08-…`.

### 8.6. Запросы для осмотра памяти

```sql
-- память процесса SQL Server (пример с MS Learn)
SELECT physical_memory_in_use_kb / 1024      AS physical_in_use_mb,
       locked_page_allocations_kb / 1024     AS locked_pages_mb,
       memory_utilization_percentage,
       process_physical_memory_low, process_virtual_memory_low
FROM sys.dm_os_process_memory;

-- целевой и текущий объём менеджера памяти, модель памяти
SELECT physical_memory_kb / 1024 AS ram_mb, committed_kb / 1024 AS committed_mb,
       committed_target_kb / 1024 AS target_mb, sql_memory_model_desc
FROM sys.dm_os_sys_info;

-- сколько страниц каждой базы сейчас в буферном пуле (по примеру MS Learn; на больших пулах выполняется долго)
SELECT CASE database_id WHEN 32767 THEN 'ResourceDb' ELSE DB_NAME(database_id) END AS db,
       COUNT(*) * 8 / 1024 AS cached_mb
FROM sys.dm_os_buffer_descriptors
GROUP BY database_id
ORDER BY cached_mb DESC;

-- крупнейшие потребители памяти (клерки), столбец pages_kb — с 2012 [MS Learn]
SELECT TOP (10) type, SUM(pages_kb) / 1024 AS mb
FROM sys.dm_os_memory_clerks
GROUP BY type
ORDER BY mb DESC;
```

Проверка результата: `committed_mb` не превышает `max server memory`; самая большая база 1С занимает основную долю буферного пула; среди клерков лидирует буферный пул (`MEMORYCLERK_SQLBUFFERPOOL` — обычно крупнейший потребитель, страницы данных и индексов), затем кеши планов `CACHESTORE_SQLCP` (запросы ad hoc и подготовленные) и `CACHESTORE_OBJCP` [MS Learn, `sys.dm_os_memory_clerks`; практика].

### 8.7. Память на Linux

- По умолчанию процесс SQL Server на Linux использует только 80 % физической памяти; предел задаётся `memory.memorylimitmb` через `mssql-conf` или переменной окружения `MSSQL_MEMORY_LIMIT_MB` (она главнее) [MS Learn].
- `memory.memorylimitmb` ограничивает всю память процесса (буферный пул, SQLPAL, агент и др.), а `max server memory` — только буферный пул и должен быть меньше `memory.memorylimitmb` [MS Learn].
- Минимум для запуска на Linux — 2 ГБ [MS Learn].

## 9. Кеш планов, параметризация, компиляция

### 9.1. Как устроен кеш планов

- Кеш планов делит память с данными динамически; хранилища: **OBJCP** (процедуры, функции, триггеры) и **SQLCP** (автопараметризованные, динамические и подготовленные запросы — сюда попадают запросы 1С) [MS Learn; практика].
- **Скомпилированный план** — общая структура «только для чтения» (операторы, оценки строк, рабочие таблицы); **контекст выполнения** — данные конкретного выполнения (значения параметров) [MS Learn].
- План переиспользуется, если текст оператора **совпадает посимвольно** (с полностью квалифицированными именами объектов) и совпадают параметры `SET` сеанса (`ANSI_NULLS`, `ANSI_PADDING`, `ARITHABORT`, `DATEFORMAT`, `LANGUAGE`, `QUOTED_IDENTIFIER` и др.) [MS Learn].
- Идентификаторы: *query hash* — хеш текста, *query plan hash* — хеш плана, *plan handle* — ключ плана в кеше, живёт, пока план в кеше [MS Learn]. По ним связывают `sys.dm_exec_query_stats` и Query Store; с техжурналом 1С — по тексту запроса (`mssql/06-…`) [практика].

### 9.2. Как запросы приходят от 1С

- В событии техжурнала `DBMSSQL` из примера ИТС текст запроса содержит маркеры параметров `?` и значения `p_0: 0x…`, а план — поиск по `[@P1]` по кластерному индексу таблицы `_Reference85` [ИТС-мет 5808, 2015]. То есть 1С отправляет **параметризованные** запросы, и план одного текста переиспользуется для разных значений [вывод].
- Уточнено 20.10.2026 по ИТС-мет 5910 (2016): сценарии статьи для разбора трассировки SQL Server и событий `DBMSSQL` техжурнала вырезают из текста запросов обёртку `exec sp_executesql N'…'` (в техжурнале — `{call sp_executesql(N'…`) и параметры `@P<n>` — то есть на 2016 год параметризованные запросы 1С приходили в SQL Server через `sp_executesql`. По MS Learn провайдер OLE DB Native Client при маркерах параметров тоже отправляет операторы через `sp_executesql` [MS Learn]; для современной платформы с OLE DB Driver 18/19 это не проверялось ⚠.
- Временные таблицы 1С (`ПОМЕСТИТЬ` в языке запросов) создаются в tempdb [ИТС-мет 2374, 2008]. Уточнено 20.10.2026 по ИТС-мет 5910 (2016): функция хеширования текстов запросов в статье заменяет имена вида `#tt<цифры>` на общий шаблон, чтобы одинаковые запросы с разными временными таблицами считались одним, — имена временных таблиц 1С имеют вид `#tt<n>`, и номер делает тексты запросов в кеше планов разными [вывод].

### 9.3. Вытеснение, перекомпиляция, очистка

- При нехватке памяти планы вытесняются по «стоимости»: у разовых (ad hoc) планов текущая стоимость изначально 0 — они уходят первыми; часто используемые держатся [MS Learn].
- План помечается недействительным и перекомпилируется при: изменении таблицы (`ALTER TABLE`), изменении или удалении используемого индекса, обновлении статистики (явном или автоматическом), `sp_recompile`, большом числе изменений ключей; перекомпилируется только затронутый оператор, а не весь пакет [MS Learn]. Поэтому после реструктуризации 1С и после обновления статистики планы строятся заново [вывод].
- Очистка вручную: `DBCC FREEPROCCACHE` — весь кеш экземпляра (или один план по `plan_handle`); с SQL Server 2016 — `ALTER DATABASE SCOPED CONFIGURATION CLEAR PROCEDURE_CACHE` только для текущей базы; изменение некоторых параметров `sp_configure` + `RECONFIGURE` тоже сбрасывает кеш (в журнал ошибок пишется сообщение «cachestore flush») [MS Learn].
- 1С рекомендует очищать процедурный кеш после обновления статистики [ИТС-мет 5837, 2022]; ИТС перечисляет очистку кеша среди допустимых административных задач на уровне СУБД [ИТС-КС разд. 5.5.8]. На общем экземпляре — только своей базы (команда выше), подробно — `mssql/05-…`.

```sql
-- осторожно на рабочем сервере: после очистки всё компилируется заново (кратковременный рост CPU)
USE [buh];
ALTER DATABASE SCOPED CONFIGURATION CLEAR PROCEDURE_CACHE;      -- SQL Server 2016+ [MS Learn]
-- DBCC FREEPROCCACHE;                                          -- весь экземпляр, все базы [MS Learn]
```

### 9.4. Чувствительность к параметрам

- При компиляции параметризованного запроса оптимизатор «подсматривает» текущие значения параметров (parameter sniffing) и строит план под них; при неравномерном распределении данных этот план может плохо подходить другим значениям [MS Learn]. Для 1С это типично для отборов по организации, складу, периоду [практика].
- Локальные переменные не подсматриваются: оценка идёт по средней плотности или по эвристикам (10 % для равенства, 30 % для неравенств и диапазонов, если статистики нет) [MS Learn].
- **PSP-оптимизация** (Parameter Sensitive Plan, SQL Server 2022, уровень совместимости 160, параметр базы `PARAMETER_SENSITIVE_PLAN_OPTIMIZATION`, по умолчанию `ON` с уровня 160): несколько планов для одного параметризованного запроса в зависимости от значений [MS Learn]. Доступна во всех редакциях [MS Learn].
- **OPPO** (оптимизация необязательных параметров, `NULL`/не `NULL`) — SQL Server 2025, уровень 170 [MS Learn].
- **`OPTIMIZED_SP_EXECUTESQL`** (2025, параметр базы, по умолчанию `OFF`) — вызовы `sp_executesql` компилируются как объекты, сериализуя компиляцию и снижая «шторм компиляций» [MS Learn]. Для 1С не проверялось ⚠.
- **Принудительная параметризация** (`ALTER DATABASE … SET PARAMETERIZATION FORCED`) заменяет литералы параметрами; полезна для приложений с непараметризованными запросами, может ухудшить планы; переключение сбрасывает планы базы [MS Learn]. 1С и так параметризует запросы (9.2) — для базы 1С не нужна [практика].

### 9.5. Осмотр кеша планов

```sql
-- объём кеша планов по типам объектов (столбцы — MS Learn, sys.dm_exec_cached_plans)
SELECT objtype, cacheobjtype, COUNT(*) AS plans,
       SUM(CAST(size_in_bytes AS bigint)) / 1048576 AS size_mb,
       SUM(CASE WHEN usecounts = 1 THEN 1 ELSE 0 END) AS used_once
FROM sys.dm_exec_cached_plans
GROUP BY objtype, cacheobjtype
ORDER BY size_mb DESC;
```

Ожидаемо для базы 1С [практика]: основная масса — `Prepared`/`Adhoc` в SQLCP; большая доля `used_once` на `Adhoc` — признак непараметризованных запросов (чаще не от 1С, а от отчётов и внешних систем, ходящих в базу напрямую).

## 10. Хранение: файлы, файловые группы, страницы, экстенты

### 10.1. Файлы и файловые группы

По «Database files and filegroups» [MS Learn]: первичный файл (`.mdf`, один на базу, ссылки на остальные файлы), вторичные (`.ndf`), журнал (`.ldf`, минимум один, в файловые группы не входит). У файла логическое имя (для T‑SQL: `DBCC SHRINKFILE`, `ALTER DATABASE … MODIFY FILE`) и физическое (путь). Группа `PRIMARY` содержит первичный файл и системные таблицы. Внутри группы данные пишутся **пропорционально свободному месту** файлов, а автоувеличение идёт по одному файлу, когда все полны, — поэтому файлы группы делают одного размера и прироста. Файлы для чтения-записи нельзя класть на сжатую NTFS; данные и журнал — на разные диски; большинству баз хватает одного файла данных и одного журнала; перед расширением тома (`diskpart`) — копии баз и остановка служб, после — `DBCC CHECKDB`.

Для 1С: каждая ИБ — отдельная база [ИТС-КС разд. 2.1]; ИТС прямо разрешает для MS SQL менять расположение файлов базы и журнала средствами СУБД — это не влияет на работу 1С [ИТС-КС разд. 5.5.6, 5.5.7]. Пользовательские табличные пространства 1С (лицензия КОРП) на MS SQL требуют права `ALTER` на базу [ИТС-КС разд. 5.5.5.2.1]; что именно платформа создаёт на MS SQL под «табличное пространство» (файловую группу с файлом в указанном каталоге), ИТС не описывает ⚠.

### 10.2. Страницы

- Все данные хранятся в **страницах по 8 КБ**: заголовок 96 байт (номер, тип, владелец), строки от начала страницы, массив смещений строк (slot array, по 2 байта на строку) — с конца [MS Learn].
- Типы страниц: данные, индекс, текст/LOB, GAM/SGAM, PFS, IAM, BCM, DCM [MS Learn].
- **Строка — до 8060 байт.** Столбцы переменной длины (`varchar`, `nvarchar`, `varbinary`, `sql_variant`) при превышении уходят в единицу размещения `ROW_OVERFLOW_DATA` (в строке остаётся указатель 24 байта); LOB (`nvarchar(max)`, `varbinary(max)`, `ntext`, `image`, `xml`) хранятся в `LOB_DATA` с указателем 16 байт; отдельный столбец переменной длины — до 8000 байт; столбцы фиксированной длины (`nchar`, `binary`, `numeric`…) в сумме обязаны укладываться в 8060 байт [MS Learn].
- 1С формулирует проще: запись таблицы — не больше 8060 байт, запись индекса — не больше 900 байт, причём ошибка возникает не при обновлении конфигурации, а при вставке значения, дающего слишком длинную запись индекса [ИТС-разр прил. 8, разд. 8.4]. Механизм выноса столбцов переменной длины ИТС не упоминает ⚠ — при проектировании 1С ориентируйтесь на ограничения ИТС.

### 10.3. Экстенты и карты размещения

- **Экстент** — 8 смежных страниц, 64 КБ; бывает однородным (один объект) и смешанным (до 8 объектов) [MS Learn].
- До SQL Server 2014 первые 8 страниц нового объекта брались из смешанных экстентов (флаг 1118 это отключал). **С SQL Server 2016** в пользовательских базах и tempdb используются однородные экстенты (кроме первых 8 страниц цепочки IAM), флаг 1118 не действует; в пользовательских базах поведение задаёт `MIXED_PAGE_ALLOCATION` (по умолчанию `OFF`) [MS Learn]. Рекомендация 1С включать 1118 [ИТС-мет 5904, 2019; 5946, 2019] для 2016+ не нужна — это отмечено и в самой статье 5946.
- Карты размещения [MS Learn]: **GAM/SGAM** — по биту на экстент, один интервал ≈ 64 000 экстентов (≈ 4 ГБ); **PFS** — по байту на страницу (выделена ли страница и насколько заполнена), новая PFS-страница каждые 8088 страниц; степень заполненности учитывается только для страниц куч и LOB; **IAM** — какие экстенты принадлежат единице размещения (`IN_ROW_DATA`, `LOB_DATA`, `ROW_OVERFLOW_DATA`).
- Конкуренция за эти страницы (`PAGELATCH_*`) — классическая проблема tempdb; SQL Server 2019 обновляет PFS под общей защёлкой, 2022 — уменьшил конкуренцию за GAM/SGAM [MS Learn] (раздел 12).

### 10.4. Предельные размеры

| Объект | Предел | Примечание |
|---|---|---|
| Ключ индекса | 900 байт — кластерный; 1700 байт — некластерный | до 2014 включительно — 900 байт для всех [MS Learn] |
| Столбцов в ключе индекса | 32 | [MS Learn]; у 1С — не больше 16 полей базы данных в индексе [ИТС-разр прил. 8, разд. 8.1] |
| Байт в строке | 8060 | с выносом столбцов переменной длины [MS Learn] |
| Байт в `GROUP BY`, `ORDER BY` | 8060 | [MS Learn] |
| Файл данных / файл журнала | 16 ТБ / 2 ТБ | [MS Learn] |
| Размер базы | 524 272 ТБ | (редакция может ограничить, раздел 4.2) [MS Learn] |
| Баз на экземпляр / файлов на базу | 32 767 / 32 767 | [MS Learn] |
| Соединений пользователей | 32 767 | [MS Learn] |
| Параметров процедуры | 2100 | [MS Learn] |
| Таблиц в `SELECT` | ограничено ресурсами | 256 — только у SQL Server 2000/2005 [ИТС-разр прил. 8, разд. 8.4] |

Поле составного типа в индексе 1С занимает три физических поля; Конфигуратор не даст сохранить дополнительный индекс, если физических полей больше 16 [ИТС-разр гл. 9, разд. 9.4.2].

### 10.5. Осмотр файлов базы

```sql
USE [buh];
SELECT file_id, type_desc, name AS logical_name, physical_name,
       size / 128 AS size_mb,
       CASE WHEN max_size = -1 THEN NULL ELSE max_size / 128 END AS max_mb,  -- -1 = без ограничения
       CASE WHEN is_percent_growth = 1 THEN CONCAT(growth, ' %')
            ELSE CONCAT(growth / 128, ' MB') END AS growth
FROM sys.database_files;

-- занято и выделено в файлах данных текущей базы (столбцы — с SQL Server 2012) [MS Learn]
SELECT file_id, total_page_count / 128 AS total_mb,
       allocated_extent_page_count / 128 AS used_mb,
       unallocated_extent_page_count / 128 AS free_mb
FROM sys.dm_db_file_space_usage;
```

Проверка: рост — в МБ, а не в процентах; данные и журнал на разных томах [MS Learn; ИТС-мет 5904, 2019].

## 11. Журнал транзакций, VLF, контрольные точки, восстановление

### 11.1. Как работает журнал

- **Упреждающая запись (WAL):** изменённая страница помечается «грязной» в буферном пуле, а запись журнала о её изменении обязана попасть на диск раньше самой страницы; журнал сбрасывается на диск при фиксации транзакции или заполнении буфера журнала [MS Learn]. Поэтому скорость диска журнала определяет скорость фиксации (ожидание `WRITELOG`) — 1С со ссылкой на рекомендацию Microsoft приводит отклик диска журнала 1–5 мс (диска данных — 10–20 мс) [ИТС-мет 5904, 2019; 6008, 2023].
- Запись журнала имеет **LSN** (растущий номер вида `[VLF:блок:запись]`); журналируются начало и конец транзакций, изменения данных, выделение страниц и экстентов, DDL; под откат транзакция резервирует место; единица ввода-вывода — блок журнала (кратен 512 байтам, до 60 КБ) [MS Learn].
- **Активная часть** — от MinLSN (наименьший из: начала последней контрольной точки, начала самой старой активной транзакции, самой старой недоставленной транзакции репликации) до конца; её усечь нельзя [MS Learn] — главный враг журнала у 1С — долгие транзакции [вывод].
- Журнал кольцевой: когда конец догоняет начало, файл растёт на `FILEGROWTH`, а если нельзя — ошибка **9002** [MS Learn].

### 11.2. Виртуальные файлы журнала (VLF)

Число и размер VLF задать нельзя — они определяются шагом роста [MS Learn]:

| Прирост | Сколько VLF создаётся |
|---|---|
| меньше 1/8 текущего размера журнала (с 2014) | 1 VLF на весь прирост |
| иначе: до 64 МБ | 4 VLF; **с SQL Server 2022 — 1 VLF** при приросте ≤ 64 МБ |
| от 64 МБ до 1 ГБ | 8 VLF |
| больше 1 ГБ | 16 VLF |

- Слишком много VLF (сотни тысяч) замедляют запуск и восстановление базы, присоединение, копии журнала, репликацию и Always On; при восстановлении возможна ошибка **9017** («слишком много VLF») [MS Learn]. Ориентир Microsoft — не больше нескольких тысяч [MS Learn].
- Исправление: при наличии проверенной копии — сжать журнал и вырастить одним шагом до нужного размера (`ALTER DATABASE … MODIFY FILE (NAME = …, SIZE = …)`), затем задать разумный прирост [MS Learn]. Команды — `mssql/04-…`.
- С SQL Server 2022 рост журнала до 64 МБ тоже использует мгновенную инициализацию файлов; крупнее — по-прежнему с обнулением [MS Learn]. ИТС пишет, что мгновенная инициализация для журнала не работает [ИТС-мет 6008, 2023] — для 2022+ это верно только для шагов больше 64 МБ. Вывод тот же: журнал — заранее нужного размера [ИТС-мет 5904, 2019].

```sql
USE [buh];
SELECT COUNT(*) AS vlf_count,
       SUM(CASE WHEN vlf_active = 1 THEN 1 ELSE 0 END) AS active_vlf,
       SUM(vlf_size_mb) AS log_mb
FROM sys.dm_db_log_info(DB_ID());                       -- SQL Server 2016 SP2+ [MS Learn]

SELECT total_log_size_in_bytes / 1048576 AS log_mb, used_log_space_in_percent,
       log_space_in_bytes_since_last_backup / 1048576 AS since_last_log_backup_mb
FROM sys.dm_db_log_space_usage;                         -- текущая база [MS Learn]
```

### 11.3. Усечение журнала

- Усечение освобождает неактивные VLF для повторного использования: в **простой** модели — после контрольной точки; в **полной** и **с неполным протоколированием** — после копии журнала, если с прошлой копии была контрольная точка [MS Learn].
- Что мешает усечению, показывает `sys.databases.log_reuse_wait_desc` [MS Learn]; разбор значений и действий — `mssql/04-…` и `mssql/08-…`.
- 1С: для ускорения загрузки `.dt` — модель «Простая» или «С неполным протоколированием» [ИТС-адм разд. 6.8]; монопольный режим ИБ не переводит базу MS SQL в `SINGLE_USER` [ИТС-адм разд. 6.7].

### 11.4. Контрольные точки

| Вид | Как задаётся | Особенности |
|---|---|---|
| Автоматическая | `sp_configure 'recovery interval'` | по объёму журнала, который можно обработать за интервал; в простой модели ещё при заполнении журнала на 70 %; при задержке записи свыше 50 мс притормаживается |
| Косвенная | `ALTER DATABASE … SET TARGET_RECOVERY_TIME = n SECONDS` | держит число грязных страниц ниже порога; фоновый писатель сбрасывает страницы постоянно; **по умолчанию для баз, созданных в 2016+ (в том числе `model` и tempdb) — 60 с** |
| Ручная | `CHECKPOINT [длительность]` | в текущей базе |
| Внутренняя | — | при копии, создании снимка (в том числе внутреннего для `DBCC CHECKDB`), добавлении/удалении файлов, остановке службы |

Источник: «Database checkpoints» [MS Learn].

- Базы, обновлённые на месте или восстановленные со старой версии, остаются на автоматических контрольных точках, пока им явно не задать `TARGET_RECOVERY_TIME` [MS Learn]. Базы 1С, переезжавшие с 2012/2014, — кандидаты на проверку [практика].
- Косвенные контрольные точки сглаживают всплески записи, но фоновый писатель может добавить нагрузку на запись [MS Learn].
- Долгие незафиксированные транзакции удлиняют восстановление при любом виде контрольных точек [MS Learn].

```sql
SELECT name, recovery_model_desc, target_recovery_time_in_seconds,  -- 0 = автоматические контрольные точки
       log_reuse_wait_desc, is_accelerated_database_recovery_on, delayed_durability_desc
FROM sys.databases
WHERE name = N'buh';
```

### 11.5. Восстановление после сбоя и ADR

- Классическое восстановление (ARIES): анализ → повтор (redo) от самой старой незавершённой транзакции → откат (undo) незавершённых; время пропорционально самой длинной активной транзакции; откат большой транзакции так же долог; долгие транзакции не дают усекать журнал [MS Learn].
- **ADR** (ускоренное восстановление, SQL Server 2019+, Enterprise и Standard): все физические изменения версионируются в **хранилище версий внутри самой базы (PVS)**, есть вторичный поток журнала (SLOG), «логический откат» и очиститель версий. Даёт почти мгновенный откат и восстановление и агрессивное усечение журнала даже при длинных транзакциях [MS Learn].
- Цена ADR: место под PVS в базе, больше записей журнала (версии журналируются), чаще разбиение страниц; при транзакционной репликации, моментальной репликации и **CDC** агрессивное усечение журнала отключается; ADR несовместим с зеркальным отображением базы [MS Learn]. С SQL Server 2022 — многопоточная очистка версий; с 2025 — ADR в tempdb (переключение требует перезапуска службы) [MS Learn].
- **Для 1С:** ИТС ADR не упоминает ⚠. Включение ADR переносит версии строк (раздел 12.4) из tempdb в саму базу 1С — база вырастет; при «копиях базы данных Версия2» (CDC) выигрыш по журналу теряется [вывод из MS Learn]. Без проверки на копии не включать [практика]. Синтаксис — `ALTER DATABASE … SET ACCELERATED_DATABASE_RECOVERY = { ON | OFF }` [MS Learn].

### 11.6. Отложенная фиксация

- `DELAYED_DURABILITY` (`DISABLED`/`ALLOWED`/`FORCED`) позволяет фиксировать транзакцию до сброса журнала на диск — ценой возможной потери последних транзакций при сбое; в tempdb отложенная фиксация включена всегда [MS Learn].
- ИТС: в SQL Server 2019 CU20, 2022 CU2 и новее CDC несовместим с отложенной фиксацией — это ломает «копии базы данных Версия2» [ИТС-разр гл. 26; `../its-docs/dev-gl26-kopii-bazy-dannyh.md`]. Для баз 1С оставлять `DISABLED` [практика].

## 12. tempdb и хранилище версий строк

### 12.1. Что лежит в tempdb

- **Пользовательские объекты:** временные таблицы и индексы на них, табличные переменные, курсоры, временные процедуры [MS Learn]. 1С широко использует временные таблицы [ИТС-мет 2374, 2008]; пока объект `МенеджерВременныхТаблиц` с хотя бы одной временной таблицей удерживается, сеанс 1С держит за собой соединение с СУБД (в консоли кластера видно «Соединение с СУБД») [ИТС-КС разд. 5.2.11.1].
- **Внутренние объекты:** рабочие таблицы (спулы, сортировки, LOB), рабочие файлы хеш-операций, промежуточные результаты `GROUP BY`/`ORDER BY`/`UNION` [MS Learn; ИТС-мет 2374, 2008]. **Хранилища версий:** RCSI и `SNAPSHOT`, онлайн-операции с индексами, MARS, `AFTER`-триггеры [MS Learn].
- tempdb пересоздаётся при каждом запуске, журналируется минимально, не копируется; отложенная фиксация в ней включена всегда; RCSI в ней включить нельзя [MS Learn].

### 12.2. Файлы tempdb

| Параметр | Значение по умолчанию | Источник |
|---|---|---|
| Первичный файл данных | `tempdev`, `tempdb.mdf`, 8 МБ, рост 64 МБ | [MS Learn] |
| Вторичные файлы | `temp#`, `tempdb_mssql_#.ndf`, 8 МБ, рост 64 МБ | [MS Learn] |
| Журнал | `templog`, `templog.ldf`, 8 МБ, рост 64 МБ до 2 ТБ | [MS Learn] |
| Число файлов при установке (2016+) | меньшее из числа логических процессоров и 8 (`/SQLTEMPDBFILECOUNT`) | [MS Learn] |

- Microsoft: до 8 логических процессоров — столько же файлов, больше 8 — 8 файлов; при сохраняющейся конкуренции добавлять кратно 4; все файлы одного размера и с одинаковым приростом (из-за пропорционального заполнения) [MS Learn]. 1С: 4 файла, прирост 512 МБ, начальный размер — 50 % отдельного диска / число файлов либо 1–10 ГБ при общем диске [ИТС-мет 5904, 2019]. Настройка — `mssql/02-…`.
- Начиная с 2016 все файлы tempdb растут одновременно (`AUTOGROW_ALL_FILES` всегда включён для `PRIMARY`), флаг 1117 не нужен [MS Learn].

### 12.3. Улучшения tempdb по версиям

Сверх перечисленного в 2.6 [MS Learn]: 2016 — кеширование временных таблиц и табличных переменных, меньше журналирования; 2017 — установщик предупреждает о файлах больше 1 ГБ без мгновенной инициализации; 2019 — файлы открываются без `FILE_FLAG_WRITE_THROUGH`, метаданные tempdb в памяти (только Enterprise); 2025 — tempdb в `tmpfs` на Linux.

### 12.4. Хранилище версий строк и RCSI

- Когда в базе включён `READ_COMMITTED_SNAPSHOT` (или `ALLOW_SNAPSHOT_ISOLATION`), **каждое** изменение строки сохраняет предыдущую зафиксированную версию в хранилище версий — даже если читателей с версионированием сейчас нет; новая версия ссылается на старую цепочкой [MS Learn].
- В строку добавляется **до 14 байт** версионной информации (номер транзакции и указатель); при средней строке 100 байт таблица может вырасти до 14 %, возможны разбиения страниц [MS Learn].
- Версии хранятся, пока нужны самой старой транзакции; для RCSI версии, созданные операторами транзакции, держатся **до конца транзакции**, хотя каждому оператору нужен снимок только на его начало [MS Learn]. Поэтому одна «зависшая» транзакция 1С держит рост tempdb [вывод; ИТС-мет 2374, 2008].
- Если tempdb заполнилась: SQL Server принудительно сжимает хранилище, жертвами становятся самые долгие транзакции (сообщение 3967), при чтении версии такая транзакция откатывается с ошибкой 3966; если места всё равно нет — запись продолжается без версий (3959), а читатели, которым нужна несозданная версия, получают ошибку 3958 [MS Learn].
- Если в базе включён ADR — хранилище версий этой базы находится **в самой базе** (PVS), а не в tempdb; при переполнении PVS падают `UPDATE` и `DELETE` [MS Learn].
- Оценка размера хранилища: ≈ 2 × объём версий, генерируемых в минуту × длительность самой долгой транзакции в минутах [MS Learn].

### 12.5. Наблюдение за tempdb и версиями

```sql
-- распределение места в tempdb (пример MS Learn)
SELECT SUM(unallocated_extent_page_count)       * 8 / 1024 AS free_mb,
       SUM(version_store_reserved_page_count)   * 8 / 1024 AS version_store_mb,
       SUM(internal_object_reserved_page_count) * 8 / 1024 AS internal_objects_mb,
       SUM(user_object_reserved_page_count)     * 8 / 1024 AS user_objects_mb
FROM tempdb.sys.dm_db_file_space_usage;

-- хранилище версий по базам (2016 SP2+ / 2017+) [MS Learn]
SELECT DB_NAME(database_id) AS db, reserved_space_kb / 1024 AS version_store_mb
FROM sys.dm_tran_version_store_space_usage
ORDER BY reserved_space_kb DESC;

-- самые долгие транзакции, использующие версионирование [MS Learn]
SELECT TOP (10) session_id, transaction_id, is_snapshot, elapsed_time_seconds
FROM sys.dm_tran_active_snapshot_database_transactions
ORDER BY elapsed_time_seconds DESC;
```

Счётчики производительности объекта `SQLServer:Transactions`: `Free Space in tempdb (KB)`, `Version Store Size (KB)`, `Version Generation rate (KB/s)`, `Version Cleanup rate (KB/s)`, `Longest Transaction Running Time` [MS Learn]. Найденный `session_id` сопоставляется с сеансом 1С через «Соединение с СУБД» в консоли кластера [ИТС-КС разд. 5.2.12.2] — `mssql/06-…`.

## 13. Блокировки и уровни изоляции; как их использует 1С

### 13.1. Уровни изоляции SQL Server

| Уровень | Грязное чтение | Неповторяемое чтение | Фантомы | Как реализован |
|---|---|---|---|---|
| `READ UNCOMMITTED` | да | да | да | без блокировок чтения |
| `READ COMMITTED` (по умолчанию) при `READ_COMMITTED_SNAPSHOT OFF` | нет | да | да | разделяемые блокировки снимаются сразу после чтения |
| `READ COMMITTED` при `READ_COMMITTED_SNAPSHOT ON` (RCSI) | нет | да | да | снимок на начало **оператора** из версий строк; читатели берут только `Sch-S` |
| `REPEATABLE READ` | нет | нет | да | блокировки чтения держатся до конца транзакции |
| `SNAPSHOT` (нужен `ALLOW_SNAPSHOT_ISOLATION ON`) | нет | нет | нет | снимок на начало **транзакции**; конфликты обновления |
| `SERIALIZABLE` | нет | нет | нет | плюс блокировки диапазонов ключей |

Источник: «Transaction locking and row versioning guide» [MS Learn]. Важно:

- Уровень изоляции не влияет на блокировки при изменении данных: исключительная блокировка держится до конца транзакции всегда (без оптимизированных блокировок) [MS Learn].
- В SQL Server `READ_COMMITTED_SNAPSHOT` и `ALLOW_SNAPSHOT_ISOLATION` для пользовательских баз **по умолчанию выключены** (в Azure SQL Database — включены) [MS Learn].
- Даже при RCSI запросы берут блокировку стабильности схемы `Sch-S` — их блокирует изменение схемы (`Sch-M`, например реструктуризация или перестроение индекса без `ONLINE`) [MS Learn].

### 13.2. Режимы блокировок 1С на MS SQL

| Режим 1С | Блокировки | Уровень изоляции | Чтение вне транзакции | Неявная транзакция при чтении объектов с табличными частями |
|---|---|---|---|---|
| Автоматический | записей | Repeatable Read или Serializable | «грязное» | да |
| Управляемый, SQL Server 2000 | записей | Read Committed | «грязное» | да |
| **Управляемый, SQL Server 2005+** | записей | **Read Committed Snapshot** | **согласованное** | в режиме совместимости 8.2.16 и ниже — да; 8.2.17 и выше — нет (двойное чтение `ВерсияДанных`) |

Источник: [ИТС-разр гл. 9, разд. 9.2.3.2]. Дополнительно там же: управляемый режим установлен по умолчанию для новых конфигураций (разд. 9.2.3.3); автоматический нужен для совместимости и не рекомендуется для реальной эксплуатации; наборы записей регистров сведений всегда читаются в неявной транзакции с разделяемой управляемой блокировкой.

Что это значит на стороне SQL Server [вывод из ИТС и MS Learn]:

- **Управляемый режим:** чтения не ставят разделяемых блокировок SQL Server и не ждут писателей; логическую согласованность (воспроизводимость чтения в транзакции) обеспечивают **управляемые блокировки 1С** в сервисе транзакционных блокировок кластера [ИТС-КС разд. 2.2.3.1; ИТС-разр гл. 9, разд. 9.2.3.2]. На уровне SQL Server остаются исключительные блокировки строк при записи (конфликты писателей, ожидания `LCK_M_*`, взаимоблокировки СУБД) и рост хранилища версий.
- **Автоматический режим:** Repeatable Read/Serializable — разделяемые блокировки чтения держатся до конца транзакции, при Serializable — ещё и блокировки диапазонов; отсюда массовые ожидания и взаимоблокировки; при `SERIALIZABLE` обращение к пустой таблице блокирует её целиком до конца транзакции [`../its-metod/ekspluataciya-krupnoj-sistemy-blokirovki-tranzakcii.md`, п. 19].
- ИТС в описании параметров ИБ относит MS SQL и Db2 к «блокировочным» СУБД (значение параметра, установленного вне транзакции, видно другим сеансам не позднее чем через 20 секунд), а файловую базу, PostgreSQL и Oracle — к «версионным» [ИТС-адм разд. 6.6.4].

### 13.3. Ресурсы и режимы блокировок SQL Server

- **Ресурсы:** `RID` (строка кучи), `KEY` (строка индекса), `PAGE`, `EXTENT`, `HoBT`, `TABLE`, `FILE`, `APPLICATION`, `METADATA`, `ALLOCATION_UNIT`, `DATABASE`; в 2025 при оптимизированных блокировках — `XACT` (блокировка идентификатора транзакции) [MS Learn].
- **Режимы:** разделяемая `S`, обновления `U`, исключительная `X`, намерения `IS`/`IX`/`SIX`, схемы `Sch-S`/`Sch-M`, массового обновления `BU`, диапазонов ключей (при `SERIALIZABLE`) [MS Learn].
- Чтобы заблокировать строку, SQL Server ставит намерения на страницу и таблицу — иерархия блокировок [MS Learn].

### 13.4. Эскалация блокировок

- SQL Server укрупняет строковые и страничные блокировки **сразу до таблицы** (или до секции при `LOCK_ESCALATION = AUTO`), не до страницы [MS Learn].
- Порог: один оператор набрал **не меньше 5000 блокировок** на одну ссылку на таблицу (индекс); если эскалация не удалась из-за конфликта — новая попытка каждые **1250** блокировок; либо память под блокировки превысила порог — **24 %** памяти Database Engine при `locks` = 0 (по умолчанию), или 40 % от значения `locks` [MS Learn]. Структура блокировки — около 100 байт [MS Learn] (в руководстве по памяти — 64 байта + 32 байта на владельца).
- Флаги: **1224** — отключает эскалацию по числу блокировок, но при нехватке памяти (40 % памяти Database Engine) эскалация возможна; **1211** — отключает эскалацию полностью, рискуя ошибкой 1204 (нехватка ресурса блокировок); если включены оба, действует 1211; Microsoft советует 1224 [MS Learn]. 1С рекомендует 1211 или 1224 [ИТС-мет 5946, 2019]. Включение — `mssql/02-…`.
- **Страничные блокировки у индексов 1С.** Из алгоритма дефрагментации ИТС («начиная с 8.3.22 перед дефрагментацией включить страничные блокировки, после — выключить», `ALLOW_PAGE_LOCKS`) следует, что платформа 8.3.22+ создаёт индексы с `ALLOW_PAGE_LOCKS = OFF` [ИТС-мет 5837, 2022] — прямой формулировки в ИТС нет ⚠. Следствие: `ALTER INDEX … REORGANIZE` на таких индексах без временного включения не выполнится — подтверждено 20.10.2026 (MS Learn, `ALTER INDEX`: реорганизация не допускается при `ALLOW_PAGE_LOCKS = OFF`) (`mssql/05-…`).
- **Эскалация управляемых блокировок 1С** — отдельный механизм: при более чем 100 000 блокировках на одно пространство возможна блокировка всего пространства (при независимых разделителях — в пределах значений разделителей) [ИТС-разр гл. 9, разд. 9.2.3.6]. Ошибка «Неудачная попытка эскалации управляемой блокировки» — это уровень 1С, не SQL Server [`../its-metod/vzaimoblokirovki-i-oshibki-blokirovok.md`].

### 13.5. RCSI в базе 1С: проверить, не трогать

```sql
SELECT name, is_read_committed_snapshot_on, snapshot_isolation_state_desc
FROM sys.databases
WHERE name = N'buh';                -- [MS Learn]
```

- ИТС называет уровень изоляции (Read Committed Snapshot), но не пишет, кто и когда включает `READ_COMMITTED_SNAPSHOT` для базы ИБ ⚠. Ожидаемо для конфигурации в управляемом режиме на SQL Server 2005+ — `is_read_committed_snapshot_on = 1` [практика] ⚠.
- Включение и выключение требует, чтобы в базе не было других соединений (однопользовательский режим не обязателен); параметр принимает `WITH ROLLBACK IMMEDIATE` и подобные условия завершения [MS Learn]. Менять его для базы 1С вручную без указания 1С не следует [практика]. Если всё же требуется (по указанию поддержки 1С): сначала копия базы, блокировка начала сеансов ИБ, затем:

```sql
-- ВНИМАНИЕ: прерывает все соединения с базой и откатывает их транзакции. Только в окно обслуживания, после копии.
ALTER DATABASE [buh] SET READ_COMMITTED_SNAPSHOT ON WITH ROLLBACK IMMEDIATE;   -- синтаксис [MS Learn]
```

### 13.6. Оптимизированные блокировки (SQL Server 2025)

- Два компонента: **блокировка идентификатора транзакции (TID)** — вместо множества блокировок строк до конца транзакции держится одна блокировка `XACT`, блокировки строк снимаются сразу после изменения; **блокировка после отбора (LAQ)** — предикаты `UPDATE`/`DELETE` проверяются по последней зафиксированной версии без блокировок, работает только при RCSI [MS Learn].
- Доступна в SQL Server 2025 (Enterprise и Standard), по умолчанию **выключена**, включается для базы `ALTER DATABASE … SET OPTIMIZED_LOCKING = ON` при отсутствии других соединений; **требует включённого ADR** (а ADR нельзя выключить, пока включены оптимизированные блокировки) [MS Learn].
- LAQ может изменить результат конкурентных операций по сравнению с обычной блокировкой (пример Microsoft: второй `UPDATE` с условием на значение, изменённое первой транзакцией, не находит строку вместо ожидания); подсказки блокировок (`UPDLOCK`, `HOLDLOCK` и др.) снижают эффект [MS Learn].
- **Для 1С:** SQL Server 2025 не в списке поддерживаемых, оптимизированные блокировки платформой не описаны ⚠ — не включать для баз 1С [практика].

### 13.7. Кто кого держит — быстрый взгляд

```sql
-- сводка текущих блокировок по сеансам и видам ресурсов (столбцы — MS Learn, sys.dm_tran_locks)
SELECT request_session_id AS session_id, resource_type, request_mode, request_status, COUNT(*) AS locks
FROM sys.dm_tran_locks
WHERE resource_database_id = DB_ID(N'buh')
GROUP BY request_session_id, resource_type, request_mode, request_status
ORDER BY locks DESC;
```

`request_status = 'WAIT'` — ожидающие запросы. Полная методика (цепочки блокировок, взаимоблокировки, `system_health`, техжурнал `TLOCK`/`TDEADLOCK`) — `mssql/06-…`, `mssql/08-…` и `../its-metod/vzaimoblokirovki-i-oshibki-blokirovok.md`.

## 14. Оптимизатор, статистика, оценщик кардинальности, уровень совместимости

### 14.1. Оптимизатор и статистика

- Оптимизатор SQL Server выбирает план с наименьшей **оценённой** стоимостью; главный вход — оценка числа строк (кардинальность) на каждом шаге, которая берётся из гистограмм статистики [MS Learn]. Плохая оценка — плохой план.
- `AUTO_CREATE_STATISTICS` и `AUTO_UPDATE_STATISTICS` по умолчанию `ON`; автосозданная статистика по столбцам называется `_WA…` [MS Learn].
- Порог автообновления статистики (число изменений): до 2014 и при уровне ниже 130 — `500 + 20 % строк`; с 2016 при уровне 130+ — `MIN(500 + 0,2·n; SQRT(1000·n))` (для 2 млн строк — 44 721 вместо 400 500); флаг 2371 нужен только при уровне 120 и ниже [MS Learn].
- `AUTO_UPDATE_STATISTICS_ASYNC` (по умолчанию `OFF`): запрос не ждёт пересчёта, компилируется по старой статистике; 1С рекомендует `True` для `model` и рабочих баз [ИТС-мет 5904, 2019]. Риск — блокировки `Sch-M` фонового обновления при частых компиляциях; с 2022 его снимает параметр базы `ASYNC_STATS_UPDATE_WAIT_AT_LOW_PRIORITY` [MS Learn].
- Регламентное обновление статистики (1С — ежедневно, с полным просмотром [ИТС-мет 5837, 2022]) — `mssql/05-…`.

### 14.2. Оценщик кардинальности (CE)

- **CE 70** (SQL Server 7.0–2012, уровень ≤ 110) исходит из независимости столбцов, равномерности, «простого вхождения»; **CE 120+** (с 2014, уровень 120+) — из корреляции предикатов одной таблицы и «базового вхождения» при соединениях; каждый новый уровень может менять модель [MS Learn].
- Если после повышения уровня запрос стал медленнее из-за CE, варианты по убыванию охвата: понизить уровень базы; `ALTER DATABASE SCOPED CONFIGURATION SET LEGACY_CARDINALITY_ESTIMATION = ON` (база на старом CE, прочие улучшения остаются); подсказка `USE HINT ('FORCE_LEGACY_CARDINALITY_ESTIMATION')` (2016 SP1+); подсказка Query Store; принудительный план Query Store; флаг 9481 — CE 70 глобально [MS Learn]. Для 1С текст запросов менять нельзя, поэтому реальны уровень базы, параметр базы и Query Store [практика].

### 14.3. Уровень совместимости и исправления оптимизатора

- Новая база получает уровень по умолчанию для версии (или ниже, если ниже у `model`); база, восстановленная или подключённая со старой версии, сохраняет свой уровень, если он не ниже минимального; Microsoft уровень существующих баз сам не повышает [MS Learn].
- Начиная с уровня 130 изменения, влияющие на планы, вводятся только в новых уровнях — так снижается риск регрессий при обновлении SQL Server [MS Learn].
- Исправления оптимизатора, выпущенные в CU после выхода версии, включаются флагом 4199 или параметром базы `QUERY_OPTIMIZER_HOTFIXES = ON` (2016+) [MS Learn].
- Какой уровень совместимости 1С ожидает у своей базы, ИТС не указывает ⚠; платформа создаёт базу через `model` [ИТС-мет 5904, 2019], значит, новая база получает уровень по умолчанию [вывод].

```sql
SELECT name, compatibility_level FROM sys.databases WHERE name = N'buh';              -- [MS Learn]
USE [buh];
SELECT name, value FROM sys.database_scoped_configurations
WHERE name IN (N'LEGACY_CARDINALITY_ESTIMATION', N'QUERY_OPTIMIZER_HOTFIXES',
               N'MAXDOP', N'PARAMETER_SENSITIVE_PLAN_OPTIMIZATION');                  -- [MS Learn]
```

### 14.4. Повышение уровня совместимости базы 1С — порядок

[MS Learn — сценарий Query Store «до/после»; практика]:

1. На **копии** базы: Query Store в `READ_WRITE` (раздел 15), прогнать типовую нагрузку (закрытие месяца, тяжёлые отчёты) на старом уровне.
2. `ALTER DATABASE [buh] SET COMPATIBILITY_LEVEL = 160;` (действует для новых сеансов; процедуры перекомпилируются) [MS Learn].
3. Повторить нагрузку, сравнить в отчёте «Regressed Queries» (SSMS → база → Query Store) [MS Learn].
4. Регрессии — принудительный план `EXEC sys.sp_query_store_force_plan @query_id = …, @plan_id = …;` или `LEGACY_CARDINALITY_ESTIMATION = ON` [MS Learn].
5. На рабочей базе — в окно обслуживания, после копии; откат — `SET COMPATIBILITY_LEVEL = <прежний>`.

### 14.6. Составные типы 1С и оптимизатор

- Сравнение полей составного типа превращается в условие с `OR` по нескольким столбцам, что сильно ограничивает использование индексов; без `OR` (и потому безопасны) — сравнение с литералом, с полем простого типа, равенство полей только ссылочных типов или с одинаковым набором типов [ИТС-мет 1828, 2013].
- Обращение «через точку» к полю составного ссылочного типа порождает соединение со всеми таблицами возможных типов (и их RLS) — крайне нежелательно [std 654].
- Индекс по полю составного типа из разнородных типов создаётся отдельно на каждый тип; при нескольких таких полях число индексов — произведение числа типов [ИТС-мет 1828, 2013].

## 15. Query Store

- Хранит историю запросов, планов и статистики выполнения (и ожиданий — с 2017) **в самой базе**; позволяет найти регрессию после смены плана и принудительно закрепить прежний план без изменения приложения [MS Learn].
- По умолчанию: в 2016–2019 выключен; **с 2022 включён в режиме `READ_WRITE` для новых баз**; в `master` и tempdb не включается [MS Learn]. Базы 1С, перенесённые со старых серверов, — без Query Store, пока его не включить [вывод].
- Умолчания параметров [MS Learn]: `MAX_STORAGE_SIZE_MB` — 100 (2016–2017) / **1000** (2019+); `QUERY_CAPTURE_MODE` — `ALL` (2016–2017) / **`AUTO`** (2019+: запрос попадает при 30 выполнениях, или 1 с компиляции, или 100 мс CPU); `INTERVAL_LENGTH_MINUTES` — 60; `STALE_QUERY_THRESHOLD_DAYS` — 30; сброс на диск — 900 с; `MAX_PLANS_PER_QUERY` — 200; `WAIT_STATS_CAPTURE_MODE` — `ON`; при достижении предела хранилище переходит в `READ_ONLY`, очистка по размеру (`SIZE_BASED_CLEANUP_MODE = AUTO`) включается на 90 % и чистит до ~80 %.
- Microsoft: если хранилищу нужно больше 10 ГБ, пересмотрите нагрузку (непараметризованные запросы) или настройки захвата [MS Learn].
- Без Query Store (в режиме `READ_WRITE`) не работают обратная связь по параллелизму и по оценке кардинальности (CE), сохранение обратной связи по памяти и оптимизированное принудительное применение планов [MS Learn, «Intelligent query processing», таблица требований к Query Store].
- Влияние на большие базы 1С не оценивалось ⚠.

```sql
-- включить (владелец базы или sysadmin) и проверить состояние [MS Learn]
ALTER DATABASE [buh] SET QUERY_STORE = ON (OPERATION_MODE = READ_WRITE, QUERY_CAPTURE_MODE = AUTO);
USE [buh];
SELECT actual_state_desc, desired_state_desc, readonly_reason,
       current_storage_size_mb, max_storage_size_mb, query_capture_mode_desc
FROM sys.database_query_store_options;

-- топ-10 запросов по суммарному CPU за всё хранимое время
SELECT TOP (10) q.query_id, p.plan_id,
       SUM(rs.count_executions) AS executions,
       SUM(rs.avg_cpu_time * rs.count_executions) / 1000 AS total_cpu_ms,
       LEFT(qt.query_sql_text, 200) AS query_text
FROM sys.query_store_runtime_stats AS rs
JOIN sys.query_store_plan AS p        ON p.plan_id = rs.plan_id
JOIN sys.query_store_query AS q       ON q.query_id = p.query_id
JOIN sys.query_store_query_text AS qt ON qt.query_text_id = q.query_text_id
GROUP BY q.query_id, p.plan_id, qt.query_sql_text
ORDER BY total_cpu_ms DESC;
```

Проверка: `actual_state_desc = READ_WRITE`; если `READ_ONLY` — смотреть `readonly_reason` (обычно исчерпан `MAX_STORAGE_SIZE_MB`) [MS Learn]. `avg_cpu_time` и `avg_duration` хранятся в микросекундах — отсюда деление на 1000 [MS Learn]. Работа с Query Store при расследовании — `mssql/06-…`.

## 17. Как 1С хранит данные в SQL Server

### 17.1. Таблицы

- Одна ИБ — одна база; имена таблиц и полей строятся «префикс + номер + суффикс»: `_Reference<n>`, `_Document<n>`, `<pref><n>_VT<k>` (табличные части), `_InfoRg<n>`, `_AccumRg<n>`/`_AccumRgT<n>`/`_AccumRgTn<n>`, `_AccRg<n>`…; служебные — `Config`, `ConfigSave`, `Params`, `DBSchema`, `_v8users`, `_ScheduledJobs`, `_YearOffset` (только MS SQL) [`../its-metod/razmeshchenie-dannyh-tablicy-i-polya.md`].
- Соответствие таблиц объектам метаданных — функция `ПолучитьСтруктуруХраненияБазыДанных()`, размер данных объектов — `ПолучитьРазмерДанныхБазыДанных()` (8.3.15+) [ИТС-мет 6005, 2022].
- У объектных таблиц кластерный индекс по `Ссылка` (с независимыми разделителями), у табличных частей — `Ссылка + Ключ`, у независимого регистра сведений — по всем измерениям (у периодического — плюс `Период`), у подчинённого регистратору — по `Регистратор + НомерСтроки` (если регистр непериодический) [`../its-metod/razmeshchenie-dannyh-i-indeksy.md`; ИТС-мет 1590, 2025]. Дополнительные индексы (лицензия КОРП; параметр ИБ «Использовать дополнительные индексы») — некластерные неуникальные, физически создаются или удаляются при реструктуризации либо при тестировании и исправлении [ИТС-разр гл. 9, разд. 9.4.1].
- Работать с таблицами в обход платформы нельзя [ИТС-мет 1798, 2025].

### 17.2. Типы столбцов

| Тип 1С | Тип в MS SQL | Суффикс поля составного типа |
|---|---|---|
| Число (n, k) | `NUMERIC(n,k)` | `_N` |
| Строка фиксированной длины n | `NCHAR(n)` | `_S` |
| Строка переменной длины n | `NVARCHAR(n)` | `_S` |
| Строка неограниченной длины | `NTEXT` | `_S` |
| Дата | `DATETIME` | `_T` |
| Булево | `BINARY(1)` | `_L` |
| Хранилище значения | `IMAGE` | `_B` |
| Ссылка на объекты одного типа | `BINARY(16)` (суффикс `RRef`) | — |
| Служебные двоичные | `BINARY(n)`, `VARBINARY(n)` | `_B` |
| Тип значения составного поля | `BINARY(1)` | `_TYPE` |
| Номер таблицы ссылки (составной ссылочный тип) | `BINARY(4)` | `_RTRef` |
| Идентификатор ссылки в составном поле | `BINARY(16)` | `_RRRef` |

Источник: [ИТС-мет 1828, 2013]; `DATETIME` для дат подтверждает и [ИТС-адм разд. 5.2.1.3.2].

- Поле одного типа — один столбец; ссылка на несколько типов — три столбца (`_TYPE`, `_RTRef`, `_RRRef`); смесь нессылочных типов — `_TYPE` плюс столбец на каждый тип; последний вариант самый ресурсоёмкий [ИТС-мет 1828, 2013].
- Статья 1828 датирована 2013 годом: Microsoft объявила `ntext`, `text` и `image` устаревшими (заменить на `nvarchar(max)` и `varbinary(max)`) [MS Learn]. Использует ли современная платформа `NTEXT`/`IMAGE` или уже `(max)`-типы — не подтверждено ⚠; проверить запросом ниже.
- `DATETIME` хранит даты с 01.01.1753 по 31.12.9999, точность — округление до .000/.003/.007 с [MS Learn]; поэтому у MS SQL есть смещение дат 0/2000 (`_YearOffset`) [ИТС-адм разд. 5.2.1.3.2]; подробности — `../1c-windows/02-…`, раздел 5.2.
- `nchar(n)`/`nvarchar(n)`: n — в парах байт (до 4000), Unicode UCS-2/UTF-16 [MS Learn]. В операции сложения строк языка запросов строка длиннее 1024 символов считается строкой неограниченной длины [ИТС-разр гл. 8, разд. 8.4.17.1]; шаблон `ПОДОБНО` — не длиннее 1024 символов (ограничение MS SQL 2005) [std 726].
- Для Db2 ИТС отмечает максимальную длину чисел 31 знак «а не 38» и ресурсов регистров накопления и бухгалтерии 25 знаков «а не 32» [ИТС-разр прил. 8, разд. 8.3] — то есть на MS SQL действуют 38 и 32 [вывод].
- Сортировка: для страны «Казахстан» на MS SQL казахский порядок не применяется — используется тот же, что для «Россия»; в ИТС он назван `Cyrillic_Generic_CI_AS` [ИТС-разр прил. 8, разд. 8.4], а у Microsoft сортировка называется `Cyrillic_General_CI_AS` [MS Learn] — по-видимому, опечатка в ИТС.

```sql
-- типы столбцов таблиц базы 1С (только чтение): какие типы реально использует ваша платформа
USE [buh];
SELECT DATA_TYPE, COUNT(*) AS columns
FROM INFORMATION_SCHEMA.COLUMNS
GROUP BY DATA_TYPE
ORDER BY columns DESC;
SELECT Offset FROM dbo._YearOffset;          -- смещение дат базы (0 или 2000)
```

`INFORMATION_SCHEMA.COLUMNS` и столбец `DATA_TYPE` — [MS Learn]. Ожидаемо [практика]: `binary`, `numeric`, `nvarchar`, `datetime`, `nchar`, `varbinary`, `image`/`ntext` или `(max)`-типы.

## Типичные ошибки (симптом → причина → решение)

| Симптом | Причина | Решение |
|---|---|---|
| Сервер 1С на Linux не создаёт базу с типом СУБД MS SQL | рабочие процессы на Linux с MS SQL не работают [ИТС-КС разд. 2.3] | рабочий сервер 1С на Windows или перенос баз в PostgreSQL (раздел 1.3) |
| SQL Server использует не все процессоры; часть планировщиков `VISIBLE OFFLINE` | предел редакции (Standard 24/32 ядра, Express 4), маска привязки или подсчёт vCPU в ВМ по логическим процессорам [MS Learn] | проверить редакцию и `affinity`; уменьшить vCPU ВМ до предела или перейти на Enterprise (раздел 4.3) |
| Standard не берёт память сверх ~128 ГБ под данные | предел буферного пула редакции [MS Learn] | ожидаемо; 2025 Standard — 256 ГБ, иначе Enterprise |
| Служба Database Engine 2022 перестала запускаться после CU на сервере с > 64 логическими ядрами на узел NUMA | изменение в 2022 CU11 [MS Learn] | SNC (Intel) / NPS (AMD) в BIOS так, чтобы на узел приходилось ≤ 64 логических ядер |
| Express: база не растёт, ошибка о превышении лицензионного предела размера | 10 ГБ (до 2022) / 50 ГБ (2025) [MS Learn] | перенос на Standard или PostgreSQL; текст ошибки — ⚠ не сверялся |
| Копии базы данных 1С «Версия2» не работают | нет SQL Server Agent / CDC (Express), либо `DELAYED_DURABILITY` на 2019 CU20+/2022 CU2+ [ИТС-разр гл. 26; MS Learn] | Standard/Enterprise, запустить агента, `DELAYED_DURABILITY = DISABLED` |
| После обновления SQL Server планы те же, новые функции оптимизатора не работают | база сохранила старый уровень совместимости [MS Learn] | осознанно повысить уровень по 14.4 |
| После повышения уровня часть отчётов 1С замедлилась | регрессия планов, новая модель CE [MS Learn] | Query Store: принудительный план; `LEGACY_CARDINALITY_ESTIMATION = ON`; откат уровня |
| Запуск или восстановление базы идёт очень долго, ошибка 9017 | сотни тысяч VLF от мелких приростов журнала [MS Learn] | при наличии копии — сжать и вырастить журнал одним шагом, задать прирост в МБ (11.2) |
| tempdb растёт, место занимает хранилище версий | долгая транзакция в базе с RCSI держит версии [MS Learn; ИТС-мет 2374, 2008] | найти через `sys.dm_tran_active_snapshot_database_transactions` (12.5), сопоставить с сеансом 1С, завершить |
| `ALTER DATABASE … SET READ_COMMITTED_SNAPSHOT` «висит» | ждёт отключения всех соединений с базой [MS Learn] | не менять без указания 1С; при необходимости — по 13.5 (`WITH ROLLBACK IMMEDIATE`, после копии) |
| Не подключиться к именованному экземпляру | остановлен SQL Server Browser при динамическом порте или закрыт UDP 1434 [MS Learn] | запустить Browser или задать статический порт и указать его |
| Учётную запись службы сменили через «Службы» — падают шаги заданий агента | права и хранилище ключа не обновлены [MS Learn] | через Configuration Manager вернуть виртуальную учётную запись, перезапустить, сменить снова (6.2) |
| Аудит: ВМ с SQL Server Standard лицензирована «по ВМ» без SA | лицензирование ВМ — только с SA или по подписке [MS Лицензирование] | купить SA/подписку или лицензировать ядра хоста (для Standard это не покрывает ВМ — 5.2) |
| Аудит: пассивная реплика AG или второй узел FCI без лицензии | без SA прав на резервные экземпляры нет [MS Лицензирование] | SA или полная лицензия на узел |
| Аудит: «сервер + CAL» посчитан по одному логину 1С | мультиплексирование не уменьшает число CAL [MS Лицензирование] | CAL на каждого пользователя/устройство 1С или модель «на ядро» |
| Для 1С поставили SQL Server 2025 | нет в списках 1С ⚠ | 2022; если уже стоит — уровень 160 и тесты (3.2) |
| SQL Server 2022 на Ubuntu 24.04 | 24.04 для 2022 в списке платформ нет [MS Learn] | Ubuntu 22.04 для 2022 или SQL Server 2025 на 24.04 (раздел 16) |
