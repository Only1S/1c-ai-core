## Кратко: главные официальные рекомендации

1. Технологический журнал (ТЖ) настраивается в `logcfg.xml`. Полный журнал (все события, все свойства) допустим для разовых задач; на рабочих серверах при этом нужно следить за свободным местом, а лучше включать только те события, которые нужны для текущего анализа (5927).
2. Событие ТЖ может занимать несколько строк (текст запроса, контекст). Поэтому фильтровать надо события, а не строки: сначала склеить событие в одну строку (perl или awk), убрать BOM, отфильтровать обычными построчными утилитами, при необходимости развернуть обратно (5927).
3. Чтобы однострочные программы работали быстро: отбирать нужные строки как можно ближе к началу конвейера, не оперировать миллионами строк, помнить о цене сортировки на сотнях тысяч строк. При отладке ставить `head` сразу после первого `|`; время измерять утилитой `time` (5927).
4. Универсальная схема «топ-5 чего угодно»: отбор событий нужного типа → отрезать всё до длительности → привести ключ группировки (контекст, текст запроса, Regions) к нормальному виду → `awk` (сумма, среднее, количество) → `sort -rnb | head -n 5` (5927).
5. При группировке текстов запросов СУБД предварительно заменять GUID, числа в скобках и номера временных таблиц на заглушки, иначе одинаковые по сути запросы не свернутся (5927).
6. Ожидания на управляемых блокировках ищутся по событиям TLOCK с непустым `WaitConnections=`; группировка — по полю `Regions` (5927).
7. При поиске по множеству серверов не гонять полный объём журналов: искать точечно, например в последних 1000 строк (5927).
8. ТЖ рекомендуется складывать в zip-архивы и какое-то время не удалять — могут понадобиться для расследования прошедших проблем; хранить архивы не на рабочих серверах, а в отдельном хранилище. Искать можно прямо в архивах через `unzip -p` (5927).
9. При 100 % CPU на сервере приложений: определить процесс-виновник; если это rphost — в консоли кластера найти сеансы, находящиеся в длительном клиент-серверном вызове и при этом не в вызове СУБД, записать номера, время начала и базы, завершить их, убедиться в падении нагрузки и расследовать сценарий по журналу регистрации (5814).
10. Если виновник rmngr — те же сеансы записать и разбирать по журналу регистрации; если виновник непонятен — снять дамп и отправить дампы и ТЖ (если собирался) в 1С с подробным описанием проблемы и симптомов (5814).
11. При исчерпании памяти: найти процесс; если это rphost — отсортировать сеансы по колонке «Память (текущая)», записать номера самых «тяжёлых», завершить их, проверить, сработал ли перезапуск процессов и хватает ли памяти; сценарий искать по журналу регистрации (5815).
12. Всегда настраивать три параметра кластера: «Допустимый объем памяти», «Интервал превышения допустимого объема памяти», «Выключенные процессы останавливать через» (5815).
13. «Допустимый объем памяти» = ОЗУ сервера − память системных процессов − (нормальный размер rphost × штатное число rphost). Смысл: при перезапуске какое-то время одновременно живут «старый» и «новый» rphost, и на новый должно хватить места (5815).
14. Не ставить «Допустимый объем памяти» ниже нормального рабочего объёма rphost — иначе процессы будут перезапускаться постоянно (5815).
15. «Интервал превышения…» и «Выключенные процессы останавливать через» задавать как можно меньше, исходя из характера нагрузки (например, по 60 секунд, если большинство операций укладывается в 60 секунд). Чем больше значения, тем менее эффективен перезапуск, но тем больше вызовов успеет штатно завершиться (5815).
16. Нет смысла отправлять в 1С дампы rmngr, если памяти на сервере действительно очень мало, а rmngr при нормальной работе занимает тот же объём (5815).
17. Анализ памяти процесса силами КОРП-поддержки / ЦКТП: убедиться, что один процесс потребляет значительный объём (например, больше 20 Гб) и это не объясняется известными ресурсоёмкими операциями; по возможности снять два дампа одного и того же PID — «до» и «во время» проблемы (5985).
18. Дамп на Linux снимается утилитой `gcore`; вместе с дампом нужно передать архив библиотек зависимостей, который собирается скриптом `extractLibs.sh` (5985).
19. Сеансовые данные ведёт менеджер кластера (rmngr); это файлы в каталоге `srvinfo/reg_<порт>/snccntx<GUID>`, растущие блоками по 64 Мб; запись идёт только в конец, очистка — сборщиком мусора (5860).
20. При большом числе пользователей файлы сеансовых данных размещать на максимально быстрых дисках, желательно на RAM-диске; отказоустойчивость этих дисков не важна — при потере сеансовых данных важная информация не теряется (5860).
21. Следить за свободным местом на диске с сеансовыми данными и за размером самих данных; не размещать на этом же диске технологический журнал. Для сборки мусора нужен запас свободного места в 25 % от объёма сеансовых данных — иначе кластер завершится аварийно (5860).
22. Каталог сеансовых данных переносится параметром `-d` строки запуска агента сервера; в том же каталоге лежат реестр кластера, индекс полнотекстового поиска и журнал регистрации (5860).
23. Исключать циклические ссылки в формах (иначе данные формы и её сеансовые данные живут до конца сеанса) и по возможности формировать отчёты СКД в фоновом режиме (5860).
24. Причины роста сеансовых данных ищутся по ТЖ: события CONN плюс CALL/SCALL интерфейса хранилища сеансовых данных → три csv-файла → таблицы в СУБД → запросы «топ пользователей» и «топ вызовов» → контекст в ТЖ рабочего процесса (5860).
25. Примеры настройки ТЖ фирма «1С» отсылает смотреть в документации к платформе (1936).

## 1. Анализ технологических журналов с помощью инструментов bash

- **Дата публикации:** 02.04.2021 (рубрика «Технологические вопросы крупных внедрений»)
- **Ссылка:** https://its.1c.ru/db/metod8dev/content/5927/hdoc

**Применимость на октябрь 2026: актуально.** Приёмы работы с grep/sed/perl/awk от версии платформы не зависят, а для Linux-сервера это «родной» инструментарий. Оговорки: примеры готовились на платформе 8.3.10, на журналах Windows-сервера (`C:\LOGS\FULL`, git bash) и для MS SQL Server — фильтры построены на событии `DBMSSQL`; имя события для PostgreSQL в источнике не приводится, под свою СУБД фильтр придётся адаптировать. Замечание о том, что bash в Windows 10 «пока в beta», устарело. В части примеров при склейке события используется `s/.\n/<line>/g` (с точкой) — такой вариант вместе с переводом строки съедает один символ перед ним; в источнике это не объяснено (см. пометку ниже), на своих журналах результат стоит проверить.

### 1.1. Цель и рамки статьи

Статья показывает один способ анализа ТЖ — утилитами командной строки. Его главный плюс — скорость: и разбора журналов, и написания самой «программы». Это не справочник по утилитам (за полным описанием авторы отсылают к man-страницам и исходному коду), а набор готовых примеров, которые можно применять как есть. Авторы настоятельно советуют хотя бы раз проделать всё описанное своими руками. Сами отмечают: способов анализа много, можно пользоваться другими инструментами и ключами, если они удобнее.

### 1.2. Стенд и настройка ТЖ

Для отработки примеров нужны: клиент-серверный вариант платформы (примеры готовились на 8.3.10), СУБД (примеры для MS SQL Server), информационная база (как вариант — СНТ из Корпоративного инструментального пакета). ТЖ настраивается в `logcfg.xml`; на ИТС есть отдельная методика настройки ТЖ для мониторинга (в локальной копии ссылка не раскрыта).

Полный журнал, собираемый в каталог `C:\LOGS\FULL` с хранением 72 часа:

```xml
<?xml version="1.0" encoding="UTF-8"?>
<config xmlns="http://v8.1c.ru/v8/tech-log">
<log location="C:\LOGS\FULL" history="72">
<event>
<ne property="Name" value=""/>
</event>
<property name="all"/>
</log>
</config>
```

(исправлено по смыслу: в источнике перед `72` стоит типографская кавычка вместо прямой.)

Предупреждение авторов: на рабочих серверах при полном журнале нужно следить за местом; лучше полный журнал не включать, а указывать только события, нужные для анализа сейчас. Для целей статьи полный журнал нужен.

### 1.3. Инструменты

- Linux: почти ничего ставить не нужно — утилиты уже есть.
- Windows: встроенный bash в Windows 10 (WSL; в статье — «пока в beta»), cygwin (https://www.cygwin.com/), git bash (https://git-scm.com/, в поставке есть всё нужное). Авторы под Windows предпочитают git bash: достаточно правого клика в каталоге журналов и пункта «Git Bash Here».
- Все примеры рассчитаны на запуск из каталога журнала (после `cd` в него; `pwd` показывает каталог полного журнала), поэтому пути вида `rphost*/*.log` относительные.
- Рекомендованные книги: Скотт Граннеман, «Linux. Необходимый код и команды. Карманный справочник»; Джеффри Фридл, «Регулярные выражения».

### 1.4. Базовые команды

```bash
cp <что_копировать> <куда_копировать>          # копирование файла
scp server:/var/dir/<что_копировать> /home/alex/<куда_копировать>   # копирование с удалённой машины server
mv <что_переместить> <куда_переместить>        # переместить файл; этой же командой — переименовать
rm <что_удалить>                               # удалить файл
rm -rf <что_удалить>                           # удалить всё, включая поддиректории, без подтверждения
ls                                             # список файлов
ls -lhatr                                      # с правами и временем модификации, последние — снизу
ls -1                                          # список в одну колонку
ls -1 | xargs                                  # список в одну строку
history                                        # история команд
find . -name "16091011.log"                    # найти файл по имени в текущей директории
find / -depth -size +10M                       # файлы больше 10 Мб от корня файловой системы
touch -t 05042140 ~/datastamp ; find . -newer ~/datastamp -exec ls -l {} \; ; rm ~/datastamp
                                               # файлы относительно метки 21:40 04.05 текущего года
cat file                                       # вывести файл
less file                                      # вывести и пролистать
head file                                      # первые 10 строк
head file -n 20                                # первые N строк
tail                                           # последние 10 строк
tail file -n 5                                 # последние N строк
tail -f <файл>                                 # следить за изменениями файла
tail -f <множество_файлов*>                    # то же по набору файлов (в источнике оговорка: кроме «новых»)
tail -f rphost*/*.log                          # пример
cmd1 | cmd2                                    # конвейер (pipe)
```

Пометки:
- `cp` — (исправлено по смыслу: в источнике первая буква набрана кириллицей).
- `find . -name "..."` — (исправлено по смыслу: в источнике типографские кавычки).
- Строка с `touch … find … rm` — (исправлено по смыслу: в источнике между `\;` и `rm` нет разделителя команд). ⚠ в источнике неясно: в описании сказано «найти файлы старше 21:40 04.05.2017», тогда как ключ `-newer` отбирает файлы, изменённые позже файла-метки.

### 1.5. grep

```bash
grep <выражение>                    # строки входного потока, содержащие соответствие выражению
grep -r <выражение>                 # поиск во всех подкаталогах
grep <выражение> <файлы>            # поиск в файлах
grep -o <выражение>                 # вывести только совпавший фрагмент
grep -oP <выражение>                # то же с perl-конструкциями
grep <выражение> -C 5               # плюс 5 строк до и после найденного
grep -h <выражение> <файлы>         # без имён файлов и путей
grep -rh <выражение>                # рекурсивно, без имён файлов
grep -oPh ',EXCP,\K(ClientID=\d+)' <файлы>   # вывести только поле ClientID=<номер> из строк с ",EXCP,"
grep <выражение> rphost*/*12.log    # журналы rphost за определённый час (12 часов)
```

### 1.6. sed и perl

```bash
sed 's/найти/заменить/'             # поиск и замена
sed 's/^.*<выражение>//'            # убрать всё от начала строки до выражения
sed 's/<выражение>.*$//'            # убрать всё от выражения до конца строки
perl -pe 's/найти/заменить/'        # альтернатива sed
perl -pe 's/найти/заменить/g'       # для всех вхождений в строке
```

Заменить GUID, номера портов и IP-адреса на короткие имена:

```bash
cat file | sed -r 's/.{8}-.{4}-.{4}-.{4}-.{12}/{GUID}/g' | sed -r 's/\:[0-9]{4,5}/{PORT}/g' | sed -r 's/[0-9]+\.[0-9]+\.[0-9]+\.[0-9]+/{ADDR}/g'
```

Автор предпочитает `perl -pe` вместо `sed` — дело вкуса плюс небольшой выигрыш в производительности и удобстве.

### 1.7. awk

```bash
awk -F<delimiter> 'BEGIN { программа анализа} END {программа}'               # общий вид
awk -F';' '{sum+=$2;} END {print "Sum=" sum}'                                # сумма по 2-й колонке, разделитель ";"
awk -F'Memory=' '{sum+=$2;} END {print "Sum=" sum}'                          # разделителем может быть слово
awk '{count[$1]+=$2;} END {for (i in count) {print i " " count[i]}}'         # группировка: ключ $1, суммируется $2
```

### 1.8. Простые реальные примеры

Топ-10 файлов по числу строк с текстом «Lock request timeout»:

```bash
grep -r 'Lock request timeout' | awk -F: '{print $1}' | sort | uniq -c | sort -r | head
```

Показывать исключения, возникающие прямо сейчас в работающих rphost:

```bash
tail -f rphost*/*.log | grep ',EXCP,'
```

Последние 10 событий фиксации или отката транзакции во всех rphost длительностью более 20 секунд (порог в команде — `20000000`):

```bash
cat rphost*/*.log | sed 's/-/,/' | awk -F',' '{if($2 > 20000000) {print}}' | grep ',SDBL,.*Transaction' | tail
```

Пояснение по смыслу команды (в источнике не расписано): `sed 's/-/,/'` заменяет первый дефис в строке — тот, что стоит между временем и длительностью события, — запятой, после чего длительность становится вторым полем для awk с разделителем `,`.

### 1.9. Запись в несколько строк

В bash перенос строки обозначается символом `\`, поэтому длинную однострочную программу можно записать и выполнить так:

```bash
cat rphost*/*.log | \
sed 's/-/,/' | \
awk -F',' '{if($2 > 20000000) {print}}' | \
grep ',SDBL,.*Transaction' | \
tail
```

В статье это используется только ради читаемости; на практике автор так не пишет. В конспекте длинные конвейеры даны именно в многострочной записи (в источнике каждый приведён дважды — одной строкой и с переносами).

### 1.10. Оптимизация

Однострочник легко написать так, что он будет работать неделями. Правила:

- отбирать нужный объём строк как можно ближе к началу конвейера;
- не оперировать миллионами строк;
- помнить, что сортировка сотен тысяч строк может быть дорогой.

Реальное время выполнения показывает `time`:

```bash
time cat rphost*/*.log | sed 's/-/,/' | awk -F',' '{if($2 > 20000000) {print}}' | grep ',SDBL,.*Transaction' | tail
```

При отладке, чтобы не ждать чтения миллионов строк, сразу после первого `|` добавляют `head` (берутся только 10 строк); если на них программа работает ожидаемо, её пробуют на полном объёме:

```bash
cat rphost*/*.log | head | sed 's/-/,/' | awk -F',' '{if($2 > 20000000) {print}}' | grep ',SDBL,.*Transaction' | tail
```

### 1.11. Фильтрация событий, а не строк

Событие ТЖ может занимать больше одной строки: например, `DBMSSQL` содержит текст запроса и может содержать контекст. Нужен приём, позволяющий отбирать событие целиком вместе с многострочными полями. Пример — все события `DBMSSQL` сеанса `SessionID=2049`:

```bash
cat rphost_*/*.log | \
perl -n -e 'if (/^\d\d:\d\d\.\d+/) {$event =~ s/\n/<line>/g; print $event."\n"; $event = "";} $event .= $_; END{print $event."\n"};' | \
perl -pe 's/\xef\xbb\xbf//g' | \
grep "DBMSSQL.*SessionID=2049" | \
sed 's/<line>/\n/g' | \
less
```

Что здесь ключевое:

1. Склейка события в одну строку — строка, начинающаяся со времени `мм:сс.доли`, считается началом нового события, накопленное до неё выводится одной строкой, переводы строк внутри заменяются маркером `<line>`:
   ```bash
   perl -n -e 'if (/^\d\d:\d\d\.\d+/) {$event =~ s/\n/<line>/g; print $event."\n"; $event = "";} $event .= $_; END{print $event."\n"};'
   ```
2. Удаление символов BOM, которые иначе мешают при работе с разными кодировками:
   ```bash
   perl -pe 's/\xef\xbb\xbf//g'
   ```
3. Обычная построчная фильтрация:
   ```bash
   grep "DBMSSQL.*SessionID=2049"
   ```
4. Обратное преобразование к многострочному виду после всех фильтраций:
   ```bash
   sed 's/<line>/\n/g'
   ```
   Оно нужно не всегда — можно, например, заменить маркер пробелом:
   ```bash
   sed 's/<line>/ /g'
   ```

Альтернатива — склейка средствами awk (есть и другие способы):

```bash
cat rphost*/*.log | awk -vORS= '{if(match($0, "^[0-9][0-9]\:[0-9][0-9]\.[0-9]+\-")) print "\n"$0; else print $0;}' | grep 'DBMSSQL.*SessionID=2049' | sed -e "s/\xef\xbb\xbf/ /g" | head
```

⚠ в источнике неясно: в разделе 1.11 склейка записана как `s/\n/<line>/g`, а во всех последующих примерах — как `s/.\n/<line>/g` (с точкой перед `\n`, то есть вместе с переводом строки удаляется ещё один символ перед ним) и с `END{print $event}` без завершающего `"\n"`. Причина различия в статье не объясняется. Ниже команды приведены так, как в источнике.

### 1.12. Пять наиболее длительных транзакций

По словам авторов, такие задачи решаются за пару минут при наличии только ТЖ и утилит bash.

**Шаг 1.** Только фиксации и откаты транзакций:

```bash
grep -P "SDBL.*Func=(Commit|Rollback)Transaction.*Context" rphost*/*.log | head
```

**Шаг 2.** Все свойства события целиком (склейка → фильтр → обратное преобразование):

```bash
cat rphost*/*.log | \
perl -n -e 'if (/^\d\d:\d\d\.\d+/) {$event =~ s/.\n/<line>/g; print $event."\n"; $event = "";} $event .= $_; END{print $event};' | \
perl -pe 's/\xef\xbb\xbf//g' | \
grep -P "SDBL.*Func=(Commit|Rollback)Transaction.*Context" | \
sed 's/<line>/\n/g' | \
head
```

**Шаг 3.** Событие оставляем одной строкой (без обратного преобразования; переводы строк сразу заменяются пробелом):

```bash
cat rphost*/*.log | \
perl -n -e 'if (/^\d\d:\d\d\.\d+/) {$event =~ s/\n/ /g; print $event."\n"; $event = "";} $event .= $_; END{print $event."\n"};' | \
perl -pe 's/\xef\xbb\xbf//g' | \
grep -P "SDBL.*Func=(Commit|Rollback)Transaction" | \
head
```

**Шаг 4.** Оставляем только нужные поля.

Вариант «длительность и первая строка контекста»:

```bash
cat rphost*/*.log | \
perl -n -e 'if (/^\d\d:\d\d\.\d+/) {$event =~ s/.\n/<line>/g; print $event."\n"; $event = "";} $event .= $_; END{print $event};' | \
perl -pe 's/\xef\xbb\xbf//g' | \
grep -P "SDBL.*Func=(Commit|Rollback)Transaction.*Context" | \
grep -oP "^\d+:\d+.\d+-\K(\d+),SDBL,.*(,Context=[\'\"]<line>[^(<line>)]*)" | \
sed 's/<line>//g' | sed 's/,SDBL,.*Context/,Context/g' | \
head
```

Вариант «длительность и последняя строка контекста»:

```bash
cat rphost*/*.log | \
perl -n -e 'if (/^\d\d:\d\d\.\d+/) {$event =~ s/.\n/<line>/g; print $event."\n"; $event = "";} $event .= $_; END{print $event};' | \
perl -pe 's/\xef\xbb\xbf//g' | \
grep -P "SDBL.*Func=(Commit|Rollback)Transaction.*Context" | \
perl -pe 's/^\d+:\d+.\d+-//g' | \
perl -pe 's/,SDBL,.*Context.*<line>[ \t]+/,Context=/g' | \
perl -pe 's/,SDBL,.*Context=/,Context=/g' | \
sed 's/<line>//g' | \
head
```

Конструкция `s/^\d+:\d+.\d+-//g` отрезает всё до длительности события, чтобы строка начиналась с числа и её было удобно группировать.

**Шаг 5.** Группировка в awk. В тексте шага она дана так:

```bash
awk -F, '{sum[$2]+=$1; count[$2]+=1;} END {for(i in sum) {print s[i] " " sum[i]/count[i] " " count[i] " " i}}'
```

⚠ в источнике неясно: здесь стоит `print s[i]` и разделитель `-F,`, а в итоговой команде — `print sum[i]` и разделитель `-F',Context='`; рабочим следует считать итоговый вариант.

**Результат** (колонки вывода: суммарная длительность, средняя длительность, количество, последняя строка контекста):

```bash
cat rphost*/*.log | \
perl -n -e 'if (/^\d\d:\d\d\.\d+/) {$event =~ s/.\n/<line>/g; print $event."\n"; $event = "";} $event .= $_; END{print $event};' | \
perl -pe 's/\xef\xbb\xbf//g' | \
grep -P "SDBL.*Func=(Commit|Rollback)Transaction.*Context" | \
perl -pe 's/^\d+:\d+.\d+-//g' | \
perl -pe 's/,SDBL,.*Context.*<line>[ \t]+/,Context=/g' | \
perl -pe 's/,SDBL,.*Context=/,Context=/g' | \
sed 's/<line>//g' | \
awk -F',Context=' '{sum[$2]+=$1; count[$2]+=1;} END {for(i in sum) {print sum[i] " " sum[i]/count[i] " " count[i] " " i}}' | \
sort -rnb | \
head -n 5
```

### 1.13. Пять наиболее длительных запросов к СУБД (в статье — MS SQL Server)

Первая мысль — применить тот же приём с группировкой по контексту:

```bash
cat rphost*/*.log | \
perl -n -e 'if (/^\d\d:\d\d\.\d+/) {$event =~ s/.\n/<line>/g; print $event."\n"; $event = "";} $event .= $_; END{print $event};' | \
perl -pe 's/\xef\xbb\xbf//g' | \
grep -P "DBMSSQL.*Context" | \
perl -pe 's/^\d+:\d+.\d+-//g' | \
perl -pe 's/,DBMSSQL,.*Context.*<line>[ \t]+/,Context=/g' | \
perl -pe 's/,DBMSSQL,.*Context=/,Context=/g' | \
sed 's/<line>//g' | \
awk -F',Context=' '{sum[$2]+=$1; count[$2]+=1;} END {for(i in sum) {print sum[i] " " sum[i]/count[i] " " count[i] " " i}}' | \
sort -rnb | \
head -n 5
```

Но контекст есть не у всех событий `DBMSSQL`, поэтому группировать по первой или последней строке контекста нельзя — нужно группировать по тексту запроса. В текстах встречаются числовые параметры и разные имена временных таблиц (`#tt17`, `#tt56`) при одинаковой по сути структуре, значит «уникальные» имена надо свернуть.

Для тренировки авторы намеренно добавляют `grep -v 'Context'` (исключение событий с контекстом) и сами оговаривают: из-за этого в топ попадут только запросы без контекста — так просто удобнее учиться.

Порядок построения: шаг 1 — получить запросы без контекста (звенья до `s/,DBMSSQL,.*Sql=/,Sql=/g` включительно, в конце `| head`); шаг 2 — убрать GUID, числа в скобках и номера временных таблиц (добавляются три замены, в конце `| head`); затем `head` заменяется группировкой и сортировкой.

**Результат:**

```bash
cat rphost*/*.log | \
perl -n -e 'if (/^\d\d:\d\d\.\d+/) {$event =~ s/.\n/<line>/g; print $event."\n"; $event = "";} $event .= $_; END{print $event};' | \
perl -pe 's/\xef\xbb\xbf//g' | \
grep -P "DBMSSQL.*Sql" | \
grep -v 'Context' | \
perl -pe 's/<line>//' | \
perl -pe 's/^\d+:\d+.\d+-//g' | \
perl -pe 's/,DBMSSQL,.*Sql=/,Sql=/g' | \
perl -pe 's/\w+-\w+-\w+-\w+-\w+/{GUID}/g' | \
perl -pe 's/\(\d+\)/({NUM})/g' | \
perl -pe 's/tt\d+/{TempTable}/g' | \
awk -F',Sql=' '{sum[$2]+=$1; count[$2]+=1;} END {for(i in sum) {print sum[i] " " sum[i]/count[i] " " count[i] " " i}}' | \
sort -rnb | \
head -n 5
```

### 1.14. Пять наиболее длительных вызовов

Задача та же, но вывод awk в «удобном для чтения» виде на деле мешает, поэтому он заменён на `printf` с целочисленным форматом:

```bash
awk -F',Context=' '{sum[$2]+=$1; count[$2]+=1;} END {for(i in sum) {printf "%d %d %d %s\n",sum[i],sum[i]/count[i], count[i],i}}'
```

**Результат:**

```bash
cat rphost*/*.log | \
perl -n -e 'if (/^\d\d:\d\d\.\d+/) {$event =~ s/.\n/<line>/g; print $event."\n"; $event = "";} $event .= $_; END{print $event};' | \
perl -pe 's/\xef\xbb\xbf//g' | \
grep -P ",CALL,.*,Context=" | \
perl -pe 's/<line>//' | \
perl -pe 's/^\d+:\d+.\d+-//g' | \
perl -pe 's/,CALL,.*Context/,Context/g' | \
perl -pe 's/,Interface=.*OutBytes=\d+//g' | \
awk -F',Context=' '{sum[$2]+=$1; count[$2]+=1;} END {for(i in sum) {printf "%d %d %d %s\n",sum[i],sum[i]/count[i], count[i],i}}' | \
sort -rnb | \
head -n 5
```

### 1.15. Пять пространств с наибольшими ожиданиями на управляемых блокировках

Приём тот же, но ключ группировки — поле `Regions`, и нужны не все события `TLOCK`, а только те, где при установке управляемой блокировки было ожидание: у них поле `WaitConnections=` непустое.

**Результат:**

```bash
cat rphost*/*.log | \
perl -n -e 'if (/^\d\d:\d\d\.\d+/) {$event =~ s/.\n/<line>/g; print $event."\n"; $event = "";} $event .= $_; END{print $event};' | \
perl -pe 's/\xef\xbb\xbf//g' | \
grep -P ",TLOCK,.*WaitConnections=\d+,Context" | \
perl -pe 's/^\d+:\d+.\d+-//g' | grep -P 'WaitConnections=\d+' | \
perl -pe 's/,Locks=.*$//g' | \
perl -pe 's/,TLOCK,.*Regions=/,Regions=/g' | \
sed 's/<line>//g' | \
awk -F',Regions=' '{sum[$2]+=$1; count[$2]+=1;} END {for(i in sum) {printf "%d %d %d %s\n", sum[i], sum[i]/count[i],count[i],i}}' | \
sort -rnb | \
head -n 5
```

Ту же конструкцию авторы предлагают самостоятельно применять для любых задач вида «топ-5 чего-то».

### 1.16. Поиск по другим журналам (пример — access-лог nginx)

Access-логи nginx тоже пригодны для такого разбора. Пример оценки, на какой «единице масштабирования» запросы выполняются дольше других (зависит от того, как выглядят журналы на конкретной площадке):

```bash
grep -P '24/Mar/2017:12'  /var/log/nginx/access.log | awk -F'|' '{if($6>40) {sum[$8]+=$6; count[$8]+=1; countall+=1;}} END {for (i in sum) {print count[i]*100/countall "% " sum[i] " " sum[i]/count[i] " " count[i] " " i}}' | sort -nb | head -n 50
```

⚠ в источнике неясно: формат access-лога авторов не описан (поля разделены символом `|`; судя по команде, 6-е поле — длительность с порогом отбора 40, 8-е — ключ группировки). Под стандартный формат лога nginx команду нужно переписывать.

### 1.17. Когда серверов много

Если серверы названы `server1 … server100`, их имена перечисляются циклом:

```bash
for i in `seq 1 100`; do echo server$i; done
```

Поиск `EXCP` на всех серверах «в лоб»:

```bash
for i in `seq 1 100`; do ssh server$i 'grep ,EXCP, /var/log/srv1cv8/logs/FULL/rphost*/*.log'; done
```

Предупреждение: журналы большие, и такая команда заставит множество серверов одновременно перемалывать большой объём данных. Лучше искать точечно — например, в последних 1000 строк:

```bash
for i in `seq 1 100`; do ssh server$i 'tail -n 1000 /var/log/srv1cv8/logs/FULL/rphost*/*.log' | grep ",EXCP,"; done
```

Дальше через `|` применяются уже знакомые конструкции.

### 1.18. Поиск в zip-архивах

Рекомендация: ТЖ складывать в zip-архивы и некоторое время не удалять — они могут понадобиться при расследовании уже случившихся проблем; хранить архивы не на рабочих серверах, а в специально отведённых хранилищах. Чтобы не тратить время на распаковку, искать можно прямо по архивам:

```bash
find * -name '*.zip' -print0 | xargs -0 -i -n 1 unzip -p {} '*.log' 2>/dev/null | grep ',EXCP,'
```

Поиск в каталоге с архивами на удалённом сервере, только по журналам rphost и rmngr полного журнала:

```bash
find //server/disk/2017-05-04/logs -name '*.zip' -print0 | xargs -0 -i -n 1 unzip -p {} '*/FULL/rphost*/*.log' '*/FULL/rmngr*/*.log' 2>/dev/null | grep ",EXCP," | head
```

## 3. Высокая загрузка CPU на сервере приложений

- **Дата публикации:** 31.05.2016 (рубрика «Технологические вопросы крупных внедрений»)
- **Ссылка:** https://its.1c.ru/db/metod8dev/content/5814/hdoc

**Применимость на октябрь 2026: частично устарело.** Статья 2016 года и целиком написана под Windows: счётчик Performance Monitor, Process Explorer, ProcDump, bat-файл на `tasklist`. На сервере Ubuntu эти инструменты неприменимы, а Linux-аналогов статья не называет (утилита снятия дампа для Linux — `gcore` — названа в статье 5985, см. раздел 5). Сам порядок действий — определить процесс, по консоли кластера найти сеансы в длительном серверном вызове вне СУБД, зафиксировать, завершить, расследовать по журналу регистрации, при неясной причине передать дампы и ТЖ в 1С — от ОС не зависит и остаётся верным.

### 3.1. Ситуация

Счётчик `Processor(_Total)\% Processor Time` показывает 100 % загрузки CPU на сервере приложений.

### 3.2. Порядок действий

1. Подключиться к серверу.
2. Запустить Process Explorer.
3. Найти процесс-виновник.
4. **Если виновник — rphost:**
   - открыть консоль администрирования кластера серверов;
   - найти сеансы, которые находятся в длительном клиент-серверном вызове (колонка «Время вызова (текущее)») и при этом не в вызове СУБД (колонка «Время вызова СУБД (текущее)»);
   - записать номера этих сеансов, время их начала и информационные базы;
   - завершить эти сеансы;
   - убедиться, что нагрузка упала;
   - по журналу регистрации выяснить, какой сценарий выполняли завершённые сеансы (что именно они делали).
5. **Если виновник — rmngr:**
   - найти сеансы по тому же признаку (длительный клиент-серверный вызов, не вызов СУБД);
   - записать их номера, время начала и базы;
   - по журналу регистрации попытаться понять, что делают эти сеансы.
6. **Если виновник не понятен** — снять дамп утилитой ProcDump (ссылка в источнике: `http://technet.microsoft.com/en-us/sysinternals/dd996900.asp` — оборвана, в статье 5815 та же ссылка оканчивается на `.aspx`).
7. Полученные дампы и технологические журналы (если они собирались) отправить в 1С с подробным описанием проблемы и симптомов.

⚠ в источнике неясно: вложенность списка в локальной копии потеряна — пункты 6–7 могут относиться и к ветке «rmngr», и ко всему алгоритму. Для ветки rmngr завершение сеансов в источнике не упоминается (в отличие от ветки rphost).

### 3.3. Bat-файл для снятия дампов всех процессов кластера (Windows)

Рекомендуется, когда нужно получить дампы кластера серверов. Запускать из каталога, где лежит ProcDump. Снимает полные дампы (`-ma`) всех `rmngr.exe`, `rphost.exe` и `ragent.exe` на сервере, имена файлов — `<процесс>_<PID>`.

```bat
@ echo off

echo Start dumping all rmngrs, rphosts and ragents on this server...

CD %~dp0

for /f "usebackq tokens=2" %%a in (`tasklist /FO list /FI "IMAGENAME eq rmngr.exe" ^| find /i "PID:"`) do (
start /b procdump.exe -ma %%a rmngr_%%a)

for /f "usebackq tokens=2" %%a in (`tasklist /FO list /FI "IMAGENAME eq rphost.exe" ^| find /i "PID:"`) do (
start /b procdump.exe -ma %%a rphost_%%a)

for /f "usebackq tokens=2" %%a in (`tasklist /FO list /FI "IMAGENAME eq ragent.exe" ^| find /i "PID:"`) do (
start /b procdump.exe -ma %%a ragent_%%a)

pause
```

## 4. Значительное потребление памяти процессами кластера на сервере приложений

- **Дата публикации:** 31.05.2016 (рубрика «Технологические вопросы крупных внедрений»)
- **Ссылка:** https://its.1c.ru/db/metod8dev/content/5815/hdoc

**Применимость на октябрь 2026: частично устарело.** Статья 2016 года: диагностика описана через Windows-инструменты (счётчик Performance Monitor, RamMap, ProcDump, bat-файл), которых на Ubuntu нет. Параметры перезапуска названы так, как они выглядели в свойствах кластера на момент публикации; состав и названия настроек ограничения памяти в используемой версии платформы нужно сверять с её документацией (в источнике об изменениях ничего нет, ссылка на подробное описание настроек в локальной копии не раскрыта). Не устарело: порядок разбора инцидента, принцип расчёта порога памяти с запасом на второй rphost и описание того, как проходит перезапуск рабочего процесса.

### 4.1. Ситуация

По счётчику Performance Monitor `\Memory\Available Mbytes` объём доступной памяти близок к нулю.

### 4.2. Порядок действий

1. Подключиться к серверу.
2. Запустить RamMap.
3. Найти процесс, занявший всю доступную оперативную память. Смотреть стоит и на закладку File Summary.
4. Найти причину.
   - **Если это rphost** — открыть консоль администрирования серверов 1С и:
     - перейти на страницу «Сеансы»;
     - найти колонку «Память (текущая)» и упорядочить по ней;
     - записать номера сеансов, использовавших больше всего памяти;
     - завершить эти сеансы;
     - проверить, успело ли сработать условие перезапуска процессов кластера;
     - если есть сеансы в длительном клиент-серверном вызове — записать их номера;
     - завершить эти сеансы и убедиться, что процессы успешно перезапустились;
     - убедиться, что памяти достаточно.
   - **Если это rmngr и виновник не понятен** — снять дамп утилитой ProcDump; дампы и ТЖ (если собирался) отправить в 1С с подробным описанием проблемы и симптомов.
     - Оговорка авторов: отправлять дампы в 1С бессмысленно, если на сервере действительно очень мало доступной памяти, а rmngr при нормальной работе занимает ровно такой же объём.
5. По записанным номерам сеансов найти в журнале регистрации сценарий, который выполнялся в момент проблемы, и проанализировать его.
6. Проверить, настроен ли перезапуск процессов кластера.

### 4.3. Как настроить кластер, чтобы память не заканчивалась

У кластера есть несколько настроек перезапуска процессов по превышению порога памяти; они находятся в параметрах кластера в консоли администрирования (в источнике — рисунок с окном параметров, в локальной копии его нет).

**Рекомендуется всегда настраивать:**

- «Допустимый объем памяти»;
- «Интервал превышения допустимого объема памяти»;
- «Выключенные процессы останавливать через».

**Расчёт «Допустимого объема памяти».** Порог выбирают так, чтобы в момент его срабатывания на сервере хватило места для запуска ещё одного rphost обычного для данной системы размера:

```text
Допустимый объем памяти = ОЗУ сервера
                          − объем, занимаемый процессами системы
                          − (нормальный размер rphost × штатное число процессов rphost)
```

Примеры из статьи (сервер 12 Гб ОЗУ, системные процессы — 2 Гб, характерный размер rphost — около 3 Гб):

| Штатное число rphost | Расчёт | Порог | Смысл |
|---|---|---|---|
| 1 | 12 Гб − 2 Гб − 3 Гб × 1 | 7 Гб | в худшем сценарии rphost может вырасти до 7 Гб |
| 2 | 12 Гб − 2 Гб − 3 Гб × 2 | 4 Гб | в худшем сценарии rphost может вырасти до 4 Гб |

**Почему так — как проходит перезапуск:**

1. rphost превышает «Допустимый объем памяти» в течение «Интервала превышения допустимого объема памяти» секунд — срабатывает условие перезапуска.
2. Запускается «новый» rphost.
3. «Старый» rphost выключается, но не завершается.
4. Соединения назначаются на «новый» rphost, который сразу полноценно включается в работу.
5. «Старый» процесс продолжает исполнять ещё существующие вызовы — не дольше, чем «Выключенные процессы останавливать через» секунд.
6. По истечении этого времени «старый» rphost завершается.
7. «Новый» процесс работает полноценно.

Вывод: в течение времени «Выключенные процессы останавливать через» одновременно работают как минимум два rphost — «старый» и «новый». Отсюда и запас в формуле.

**Ограничения и предупреждения:**

- Нельзя задавать «Допустимый объем памяти» меньше нормального рабочего объёма rphost в данной системе — процессы кластера будут перезапускаться постоянно.
- «Интервал превышения допустимого объема памяти» и «Выключенные процессы останавливать через» нужно стараться задавать как можно меньше, исходя из характера нагрузки. Пример: по 60 секунд, если ожидается, что все операции (или большая их часть) выполняются быстрее 60 секунд.
- Компромисс: чем больше эти значения, тем менее эффективным может оказаться механизм перезапуска, но тем больше вызовов успеет «успешно выполниться».

### 4.4. Bat-файл для снятия дампов всех процессов кластера (Windows)

Запускать из каталога, где расположен ProcDump (`http://technet.microsoft.com/en-us/sysinternals/dd996900.aspx`). Файл совпадает с приведённым в разделе 3.3, отличие только в запятой в строке `echo`.

```bat
@ echo off

echo Start dumping all rmngrs, rphosts, and ragents on this server...

CD %~dp0

for /f "usebackq tokens=2" %%a in (`tasklist /FO list /FI "IMAGENAME eq rmngr.exe" ^| find /i "PID:"`) do (
start /b procdump.exe -ma %%a rmngr_%%a)

for /f "usebackq tokens=2" %%a in (`tasklist /FO list /FI "IMAGENAME eq rphost.exe" ^| find /i "PID:"`) do (
start /b procdump.exe -ma %%a rphost_%%a)

for /f "usebackq tokens=2" %%a in (`tasklist /FO list /FI "IMAGENAME eq ragent.exe" ^| find /i "PID:"`) do (
start /b procdump.exe -ma %%a ragent_%%a)

pause
```

## 5. Анализ потребления памяти процессами платформы 1С:Предприятие

- **Дата публикации:** 03.03.2021 (рубрика «Технологические вопросы крупных внедрений»)
- **Ссылка:** https://its.1c.ru/db/metod8dev/content/5985/hdoc

**Применимость на октябрь 2026: актуально.** Порядок сбора данных и утилиты (`gcore` для Linux, `procdump` и `vmmap` для Windows) не привязаны к версии платформы. Оговорки: это описание услуги, доступной в рамках проектов ЦКТП и КОРП-поддержки платформы, — анализ дампов выполняют специалисты 1С, а не администратор. Путь `/opt/1C/v8.3/x86_64/rmngr` в примере соответствует каталогу установки платформы на момент публикации; на своём сервере нужно указывать фактический путь к исполняемому файлу процесса. Текст скрипта `extractLibs.sh` в локальной копии статьи отсутствует (см. пометку ниже).

### 5.1. Суть

В рамках проектов ЦКТП и в КОРП-поддержке платформы можно заказать анализ памяти процессов платформы, чтобы выявить причины значительного потребления памяти. От администратора требуется корректно собрать и передать дампы.

### 5.2. Порядок действий

1. **Убедиться, что проблема есть.** Один процесс платформы потребляет значительный объём памяти — например, больше 20 Гб, — и это не объясняется известными ресурсоёмкими операциями, которые выполняются на сервере в этот момент.
2. **Оценить воспроизводимость.** Проблема может проявляться в рабочей системе и периодически. Если сценарий воспроизведения известен — передать его в поддержку.
3. **(Необязательно, но упрощает расследование.)** Убедиться, что сейчас проблема не воспроизводится, снять дамп памяти процесса, который будет анализироваться дальше, и запомнить его PID.
4. **Воспроизвести проблему** или дождаться её воспроизведения.
5. **Снять дамп процесса со значительным потреблением памяти.** Если выполнялся шаг 3 — предварительно убедиться, что PID процесса не изменился: нужны два дампа одного и того же процесса.
6. **Упаковать собранные дампы в архив** и передать в КОРП-поддержку или ЦКТП.
7. Специалисты поддержки анализируют данные и выдают заключение с результатами.

### 5.3. Как получить дамп процесса

**Windows** — утилита procdump (https://docs.microsoft.com/en-us/sysinternals/downloads/procdump); `1234` — PID процесса:

```bat
procdump.exe -ma 1234
```

**Linux** — утилита `gcore`; `d.core` — имя файла дампа, `1234` — PID процесса:

```bash
gcore -o d.core 1234
```

(Обе команды исправлены по смыслу: в источнике перед `ma` и `o` стоит длинное тире вместо дефиса.)

**Linux: библиотеки зависимостей.** Кроме дампа нужно собрать библиотеки зависимостей — для этого служит скрипт `extractLibs.sh`. Пример вызова:

```bash
./extractLibs.sh d.core.1234 /opt/1C/v8.3/x86_64/rmngr
```

Здесь `d.core.1234` — имя файла дампа, `/opt/1C/v8.3/x86_64/rmngr` — путь к исполняемому файлу процесса. Скрипт генерирует ещё один скрипт — сборщик библиотек `d.core.1234_getlibs.sh`. После запуска этого сборщика на целевой системе получается архив `libs-d.core.1234.tar.gz`; его нужно передать в поддержку вместе с файлом дампа.

⚠ в источнике неясно: самого текста скрипта `extractLibs.sh` в локальной копии нет — в статье он доступен по кнопке «Копировать», содержимое в текст не попало. Скрипт нужно взять непосредственно со страницы статьи.

**Windows: дополнительно vmmap.** Полезно также снять статистику утилитой vmmap: при запуске выбрать исследуемый процесс, сохранить полученную статистику в файл `*.mmp` и передать его в поддержку вместе с дампом.

## 6. Анализ причин роста сеансовых данных

- **Дата публикации:** 27.06.2018 (рубрика «Технологические вопросы крупных внедрений»)
- **Ссылка:** https://its.1c.ru/db/metod8dev/content/5860/hdoc

**Применимость на октябрь 2026: частично устарело.** Устарело или требует адаптации: варианты `logcfg.xml` даны для версий 8.3.5 и 8.3.6 (для более новых версий ориентир — вариант «для 8.3.6», но его работоспособность на актуальной платформе источником не подтверждена — проверить на своей версии); все пути, счётчики и утилиты — из Windows (`c:\log\sntx`, `rmngr.exe`, диспетчер задач, Performance Monitor, RamMap); база для анализа — MS SQL Server с загрузкой через SQL Server Integration Services, DDL и запросы написаны на T-SQL (для PostgreSQL их придётся переписать — варианта для PostgreSQL в источнике нет). Остаётся ценным: описание устройства сеансовых данных, требования к диску и свободному месту, запрет держать ТЖ на том же диске, влияние циклических ссылок и сама логика методики (ТЖ → csv → СУБД → контекст). Материалы, на которые статья ссылается («см. статью» про отображение файлов в память и про циклические ссылки, обработка для формирования csv), в локальную копию не вошли.

### 6.1. Что такое сеансовые данные

- Это служебная информация, необходимая для работы сеанса; платформа пользуется этим механизмом постоянно. Например, всё введённое в поля формы при серверных вызовах сбрасывается в сеансовые данные.
- Значения, переданные в методы `ПоместитьВоВременноеХранилище`, `ПоместитьФайл`, `НачатьПомещениеФайла`, записываются в сеансовые данные.
- При фоновом исполнении отчёта СКД результат помещается в сеансовые данные и затем передаётся клиентской части.
- На уровне ОС это файлы в каталоге `…\srvinfo\reg_<номер порта>\snccntx<GUID>`; по внутреннему устройству — noSQL-база (key-value storage).

### 6.2. Как платформа работает с сеансовыми данными

- За сеансовые данные отвечает менеджер кластера (rmngr). При нескольких рабочих серверах данные размещаются согласно требованиям назначения функциональности; если требования не заданы — равномерно по всем рабочим серверам.
- Рост идёт блоками по 64 Мб: закончился блок — менеджер кластера выделяет следующий. Блоки большего размера возможны при помещении объёмных данных во временные хранилища.
- Ради скорости новые данные всегда дописываются в конец (как в журнале транзакций СУБД), поэтому размер постоянно растёт, а внутри смешаны актуальные и устаревшие данные.
- Актуальность определяется способом помещения:
  - передан идентификатор формы (`ЭтаФорма.УникальныйИдентификатор`) — данные актуальны, пока форма открыта;
  - передан уникальный идентификатор, не являющийся идентификатором формы (`Новый УникальныйИдентификатор`), — данные актуальны до завершения сеанса пользователя;
  - идентификатор не передан — значение перестаёт быть актуальным при любом следующем серверном вызове.
- Сборка мусора (key value garbage collector): перед выделением очередного блока на диске проверяется, прошло ли 5 секунд с выделения предыдущего. Если прошло — запускается сборщик, который оценивает долю актуальных данных. Если актуальные данные занимают меньше 25 % общего объёма, они копируются в новые файлы, после чего все старые файлы сеансовых данных удаляются.
- Каждый сеанс (клиенты, фоновые задания, web-сервисы) пишет в сеансовые данные постоянно, поэтому при большом числе пользователей очень важна скорость дисковой подсистемы под этими файлами. **Рекомендация:** при большом числе пользователей размещать файлы сеансовых данных на максимально быстрых дисках, желательно на RAM-drive. Отказоустойчивость дисков не важна: при потере сеансовых данных никакая важная информация не теряется.
- Порядок прохождения данных:
  - двоичные данные или файл, помещаемые во временное хранилище, идут потоком байт через rphost в rmngr, который сбрасывает поток на диск;
  - коллекция (таблица значений, результат запроса, массив и т. п.) сначала целиком размещается в памяти rphost, и только потом преобразуется в поток байт и передаётся в rmngr.

### 6.3. Сеансовые данные и оперативная память

- Файлы сеансовых данных отображаются в память (mapping): процесс работает с файлом как с оперативной памятью, причём загружается не весь файл, а только нужная часть.
- В Windows отображённые файлы влияют на счётчик `Memory\Available Mbytes`. При сильном росте сеансовых данных свободное место на диске с ними убывает синхронно со свободной памятью сервера. RamMap при этом показывает, что основная часть ОЗУ отдана под Mapped File; память в колонке Standby — неиспользуемая, фактически свободная: она будет выдана любому процессу по запросу.
- Эту особенность счётчика `Memory\Available Mbytes` нужно учитывать при построении мониторинга и приложений, опирающихся на объём доступной памяти.
- Косвенная оценка эффективности работы ОС с сеансовыми данными — счётчик `Memory\Page Faults/sec` (как часто процессы не находят страницу в памяти и подгружают её с диска). Большое значение может говорить о нехватке ОЗУ для кэширования сеансовых данных; тогда нужно либо добавлять память, либо оптимизировать работу приложения с сеансовыми данными.

(Счётчики и утилита — из Windows; соответствий для Linux источник не приводит.)

### 6.4. Проблемы, связанные с сеансовыми данными

**Ошибка совместного доступа к файлу `snccntx.dat`.** Алгоритм:

1. Проверить права на каталог сеансовых данных для пользователя, от имени которого запущена служба сервера «1С:Предприятия», — должны быть полные права.
2. На рабочем сервере открыть диспетчер задач и включить колонку «Командная строка».
3. Найти процессы `rmngr.exe` с одинаковым значением параметра `-pid`.
4. Открыть консоль кластера и развернуть ветку того кластера, порт которого соответствует параметру `-regport` найденных `rmngr.exe`.
5. Сопоставить PID из диспетчера задач с PID в консоли кластера. Тот `rmngr.exe`, которого в консоли нет, принудительно завершить.

(Имена параметров `-pid`, `-regport` и ниже `-d` исправлены по смыслу: в источнике перед ними длинное тире.)

**Закончилось место на диске с сеансовыми данными.**

- За свободным местом на этом диске нужно следить.
- Не следует размещать файлы технологических журналов на одном диске с сеансовыми данными.
- Что происходит, когда место кончилось: менеджер кластера постоянно завершается с формированием дампа, начинаются сотни попыток запуска рабочих процессов, которые тут же завершаются с ошибками. После появления свободного места сервер «1С:Предприятия» запускается в нормальном режиме.
- Нужно следить и за размером самих сеансовых данных; если он периодически становится существенным — это повод для отдельного разбирательства.
- Для срабатывания сборки мусора требуется свободное место в размере 25 % общего объёма сеансовых данных. Если его нет — кластер завершит работу аварийно.
- Расположение сеансовых данных меняется параметром `-d` в строке запуска службы агента сервера. В этом же каталоге находятся реестр кластера, индекс полнотекстового поиска и журнал регистрации.

### 6.5. Циклические ссылки и рост сеансовых данных

Обычно в `ПоместитьВоВременноеХранилище` передают идентификатор формы, и по документации данные перестают быть актуальными после закрытия формы. Но если в форме есть циклические ссылки, после закрытия она не уничтожается. Последствия:

- данные формы остаются в памяти;
- сеансовые данные, выделенные для формы, считаются актуальными до завершения сеанса.

Рекомендации:

- исключить все циклические ссылки в форме;
- стараться формировать отчёты СКД в фоновом режиме: результат помещает во временное хранилище фоновое задание, и после его завершения результат считается неактуальным.

### 6.7. Методика анализа: разбор ТЖ в три csv-файла

В итоге должно получиться три файла: `scall.csv`, `call.csv`, `conn.csv`. Пример формирования csv из ТЖ авторы дают в виде обработки (в локальную копию не вошла).

**Файл 1 — по каталогам `rmngr_*`** (события CALL). Формат:

```text
<файл ТЖ>;<CallID>;<InBytes>
```

где `<файл ТЖ>` — имя файла журнала, `<CallID>` и `<InBytes>` — значения одноимённых свойств события. Строки с `InBytes=0` из итогового файла нужно исключить: интереса не представляют, а места занимают много.

Пример. Строка из `…/rmngr_7188/15063011.log` (в источнике разбита переносом на две):

```text
00:00.063040-93009,CALL,1,process=rmngr,p:processName=RegMngrCntxt,t:clientID=7518,t:applicationName=ServerProcess,t:computerName=SERVER,Interface=90b77326-8e4a-4195-b980-d758277d1f03,Method=9,CallID=141192031,Memory=1137,MemoryPeak=9258,InBytes=142428,OutBytes=142428
```

превращается в:

```text
15063011;141192031;142428
```

**Файл 2 — по каталогам `rphost_*`** (события SCALL). Формат:

```text
<процесс>;<файл ТЖ>;<t:clientID>;<CallID>
```

где `<процесс>` — имя каталога рабочего процесса, `<файл ТЖ>` — имя файла журнала, `<t:clientID>` и `<CallID>` — значения одноимённых свойств.

Пример. Строка из `…/rphost_1352/15063011.log`:

```text
00:00.064001-108993,SCALL,2,process=rphost,p:processName=DB,t:clientID=518,t:applicationName=1CV8,t:computerName=TSERVER,t:connectID=5880,SessionID=4621,Usr=Пользователь,AppID=1CV8,ClientID=404,Interface=90b77326-8e4a-4195-b980-d758277d1f03,Method=0,CallID=-1814608052
```

превращается в:

```text
rphost_1352;15063011;518;-1814608052
```

**Файл 3 — по каталогам `rphost_*`** (события CONN). Формат:

```text
<процесс>;<t:clientID>;<Usr>
```

где `<процесс>` — имя каталога рабочего процесса, `<t:clientID>` — значение свойства `t:clientID`, `<Usr>` — имя пользователя из свойства `Usr`.

Пример. Строка из `…/rphost_1352/15063011.log`:

```text
06:29.468020-0,CONN,3,process=rphost,p:processName=DB,t:clientID=518,t:applicationName=1CV8,t:computerName= TSERVER,t:connectID=5590,SessionID=3012,Usr= Пользователь,AppID=1CV8,ClientID=555,Protected=0,Txt='Connected, client=(23)[::1]:53147, server=(23)[::1]:1541'
```

по источнику превращается в:

```text
rphost_1352;195;Пользователь
```

⚠ в источнике неясно: в исходной строке `t:clientID=518`, а в результирующей стоит `195` — пример внутренне противоречив; по описанию формата во втором поле должно быть значение `t:clientID`.

### 6.9. Методика анализа: запросы и разбор результатов

**А. Топ-10 пользователей в разрезе процессов и времени** — кто поместил больше всего сеансовых данных за час:

```sql
SELECT TOP 10
 s.[process],
 s.[period],
 s.[ClientID],
 u.[Usr],
 SUM(c.[Mem]) AS Mem
FROM
 [dbo].[call] AS c
 INNER JOIN [dbo].[scall] AS s
 ON s.[period] = c.[period]
 AND s.CallID = c.CallID
 LEFT OUTER JOIN (SELECT DISTINCT process, ClientID, [Usr] FROM [dbo].[usr]) AS u
 ON u.process = s.process
 AND u.ClientID = s.ClientID
GROUP BY
 s.[process],
 s.[period],
 s.[ClientID],
 u.[Usr]
ORDER BY
 Mem Desc
```

Разбирать начинают с верхней строки. В примере статьи это:

```text
rphost_1352 | 15063011 | 518 | Пользователь | 2046616858
```

то есть в процессе `rphost_1352` за час с 11:00 до 12:00 клиент с идентификатором 518 записал в сеансовые данные 2 046 616 858 байт (2 Гб).

**Б. Все вызовы этого клиента за этот час**, по убыванию объёма:

```sql
SELECT
 s.[process],
 s.[period],
 s.[ClientID],
 c.[Mem],
 c.CallID
FROM
 [dbo].[call] AS c
 INNER JOIN [dbo].[scall] AS s
 ON s.[period] = c.[period]
 AND s.CallID = c.CallID
 AND s.[period] = '15063011'
 AND s.[ClientID] = 518
 AND s.[process] = 'rphost_1352'
ORDER BY
 [Mem] DESC
```
