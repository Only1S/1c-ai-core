# ИТС-конспект (методические материалы): Расследование медленных операций; регламентные и фоновые задания; временные файлы; встроенный язык на сервере; хранилище конфигурации
> Источник: статьи раздела «Методическая поддержка» портала 1С:ИТС (ссылки — в разделах). Это конспект своими словами, не дословный текст. Составлен 2026-10-10.

## Кратко: главные официальные рекомендации

1. Методику «медленная форма» применяют, когда операция стабильно медленная при повторах, воспроизводится на тестовой копии, одинаково медленна для администратора и обычного пользователя, а замер производительности в конфигураторе проблем не показывает и резко расходится с замером подсистемы БСП.
2. Опорное неравенство методики: (замер конфигуратором) < (длительность SCALL по техжурналу) < (замер БСП, реальное время). Если оно не выполняется — расследовать обычными методиками по проблемным местам, которые показал техжурнал или замер конфигуратора.
3. Отладка в продуктивном контуре не рекомендуется. Расследовать на копии; если данные нельзя выносить — обезличить, но обязательно сохранить количество объектов и их связи.
4. Замер БСП должен стартовать на клиенте до команды открытия формы (например, в форме списка). Старт замера в обработчиках самой формы («ПриСозданииНаСервере», «ПриОткрытии» и любых других) — некорректен.
5. Существенная разница во времени между пользователем с административными правами и пользователем с ограниченными правами — признак влияния RLS; это расследуется обычным способом, а не данной методикой.
6. Для сопоставления замеров достаточно клиентского техжурнала с событиями SCALL, VRSREQUEST, VRSRESPONSE (все свойства). Фильтр по именам процессов 1cv8 и 1cv8c страхует от сбора всех событий серверных процессов, если такой logcfg.xml окажется на сервере.
7. Типовая причина «потерянного» времени при открытии формы — сериализация и десериализация больших коллекций в реквизитах формы при передаче между сервером и клиентом. Признаки: подозрительно большой ответ сервера и полная загрузка одного потока клиента по ЦП после получения ответа.
8. Опасные с этой точки зрения реквизиты формы: ХранилищеЗначения и Строка(0), большие коллекции (таблица, дерево, список) и особенно реквизиты произвольного типа.
9. Способы лечения: ограничить число элементов коллекции (в примере статьи до 1000 элементов влияние несущественно), накладывать отборы по уже введённым в форме значениям и по пометке удаления, не держать в реквизитах формы то, что быстро получается на сервере, делать серверные процедуры бесконтекстными.
10. В расписании регламентного задания незаданный элемент не участвует: без даты окончания расписание бессрочно, без даты начала — действует с текущего момента. Недельное и месячное расписания работают как фильтры поверх основной периодичности в днях.
11. «Повторять через … сек.» (ПериодПовтораВТечениеДня) отсчитывается от начала предыдущего запуска, «повторять с паузой … сек.» (ПаузаПовтора) — от его завершения. Незавершённый предыдущий запуск планировщик дожидается.
12. Для слишком долгих заданий (например, ночных регламентных процедур) есть принудительное завершение: «завершать после» (ВремяЗавершения) и «завершать через» (ИнтервалЗавершения) — чтобы они не мешали работе пользователей.
13. Все периоды расписания — минимальные интервалы: если задание не может стартовать вовремя, запуск откладывается; при переносе на следующий день время последнего запуска сбрасывается.
14. Блокировка установки соединений с информационной базой запрещает и запуск регламентных заданий; отдельно существует блокировка только регламентных заданий. Обе доступны через консоль кластера и COM-соединение.
15. Журнал регистрации фиксирует начало фонового задания и его успешное завершение либо описание ошибки — это средство контроля, когда прочие недоступны. Программное управление заданиями (МенеджерФоновыхЗаданий, МенеджерРегламентныхЗаданий) доступно только пользователю с административными правами.
16. Имя временного файла получать методом ПолучитьИмяВременногоФайла(): имя уникально, а неудалённый файл платформа уберёт при следующем запуске.
17. Платформа чистит временные файлы только при своём перезапуске, поэтому удалять их нужно самостоятельно; на сервере, который может не перезапускаться регулярно, брошенные временные файлы способны занять значительную часть диска.
18. Время полезной жизни временного файла на сервере — не дольше одного серверного вызова: следующий вызов может попасть на другой физический сервер. Создание и удаление файлов в алгоритмах с возможными исключениями — внутри Попытка-Исключение.
19. Управление переходит на сервер только при вызове процедуры или функции общего модуля, который расположен на сервере и не расположен на клиенте (свойство «Сервер» установлено, «Клиент» — нет).
20. Перенос выполнения на сервер не гарантирует выигрыша и увеличивает нагрузку на сервер как на разделяемый ресурс; решение рекомендуется проверять экспериментом в условиях, близких к реальным.
21. Свойство общего модуля «Привилегированный» отключает проверку прав внутри модуля и позволяет дать пользователю строго ограниченное действие с данными, к которым у него нет доступа.
22. Подключение информационной базы к хранилищу конфигурации полностью заменяет её конфигурацию конфигурацией хранилища. Если с хранилищем соединилась копия подключённой базы, оригинал не сможет работать с этим хранилищем без предварительного отключения от него.
23. Резервная копия хранилища конфигурации — это файл 1cv8ddb.1cd и каталог data (если он есть). Каталог cache копировать необязательно, его можно периодически чистить.
24. У хранилища есть режим совместимости («Версия 8.3.2» / «Не использовать»); смена режима запускает конвертацию базы данных хранилища. В режиме «Не использовать» объекты хранятся в файловой системе; при замедлении работы выполняется оптимизация хранения данных.
25. Перед обновлением конфигурации, подключённой к хранилищу, рекомендуется захватить все объекты: при захвате одного только корня обновления незахваченных объектов применены не будут. В распределённой ИБ к хранилищу подключается только корневой узел.

## 1. Методика расследования причин медленной работы операции на примере открытия управляемой формы

- Дата публикации: 01.07.2022 (рубрика «Технологические вопросы крупных внедрений»)
- Ссылка: https://its.1c.ru/db/metod8dev/content/5983/hdoc

### 1.1. Когда методика применима

Методика рассчитана на узкий класс проблем. Все условия должны выполняться одновременно:

- медленно выполняется операция с управляемой формой — открытие формы либо код формы, которому нужен контекстный серверный вызов;
- при многократном повторении в рабочей базе длительность операции существенно не колеблется;
- проблема воспроизводится на тестовой базе, наполненной данными по аналогии с продуктивной (допустимо обезличивание);
- длительность одинакова для пользователя с административными правами и для любого другого пользователя;
- замер производительности в конфигураторе проблем не выявляет и значительно расходится с временем, которое зафиксировала подсистема БСП (регистр сведений «Замеры времени» или аналогичный);
- при пошаговой отладке замер в конфигураторе «зависает» на строках вида «КонецФункции», «КонецПроцедуры».

### 1.2. Проверка условий и подготовка

Сначала нужно убедиться, что проблема воспроизводится стабильно, в одинаковых условиях, и что перечисленные условия действительно выполнены.

1. Контур для отладки. Если отладка разрешена прямо в продуктивном контуре (авторы этого не рекомендуют) — шаг пропускается. Иначе разворачивается копия продуктивной ИБ в том же или близком по настройкам контуре, где отладка возможна. Если продуктивные данные нельзя разворачивать в тестовом контуре, базу готовят к переносу: обезличивают, но обязательно сохраняют количественный и качественный состав данных — число объектов и связи между ними.
2. Корректность замера БСП. Для проблемной операции должен быть настроен замер средствами подсистем БСП, и он должен совпадать с ручным замером секундомером. Если расходится — замер реализовать или исправить. Правильное место начала замера — непосредственно перед открытием формы (например, в форме списка документов, если исследуется открытие формы документа). Замер, начинающийся в обработчиках формы (в любых, в том числе «ПриСозданииНаСервере» и «ПриОткрытии»), считается некорректным.
3. Влияние прав. Операцию повторяют под пользователем с административными правами и сравнивают с длительностью у пользователей с ограниченными правами. Небольшие отличия допустимы. Если отличия существенные — это повод обычным способом расследовать влияние RLS и оптимизировать.
4. Сопоставление трёх замеров. Настраивают как минимум клиентский технологический журнал на события SCALL, VRSREQUEST, VRSRESPONSE со всеми свойствами и выполняют замер производительности средствами конфигуратора. Должно выполняться неравенство:

```text
(замер конфигуратором) < (замер по ТЖ, событие SCALL) < (замер БСП, реальное время)
```

Если какая-то часть неравенства не выполняется, методика неприменима: нужна оптимизация по обычным методикам с разбором проблемных мест, которые показали техжурнал или замер конфигуратора.

### 1.3. Сбор и анализ стандартных данных (пример из статьи)

Пример — открытие формы документа «Табель учёта рабочего времени». Собран тестовый стенд, где проблема воспроизводится под пользователем с полными правами. К стенду можно подключаться и тонким клиентом напрямую с удалённой рабочей станции, и веб-клиентом через публикацию на веб-сервере.

Вариант настройки технологического журнала на клиенте (в статье приведён для клиента на Windows):

```xml
<?xml version="1.0" encoding="UTF-8"?>
<config xmlns="http://v8.1c.ru/v8/tech-log">
<log location="D:\TJ_Logs\Client_Full" history="24">
    <event>
        <eq property="process" value="1cv8"/>
        <ne property="name" value=""/>
    </event>
    <event>
        <eq property="process" value="1cv8c"/>
        <ne property="name" value=""/>
    </event>

    <property name="Interface">
        <event>
            <eq property="name" value=""/>
        </event>
    </property>
    <property name="all"/>
</log>
</config>
```

Пояснения авторов к этой настройке:

- Фильтр по имени процесса (1cv8, 1cv8c) для самой задачи избыточен. Он нужен как страховка: если такой файл по ошибке окажется на сервере, не начнётся сбор всех событий серверных процессов, который может занять значительный объём.
- Если же настройку включают на сервере осознанно (клиентские приложения запускаются на той же машине, где развёрнут сервер приложений 1С:Предприятия), в каталоге Client_Full окажутся данные только клиентских приложений. Подкаталоги остальных процессов при этом тоже создаются, но остаются пустыми.
- Свойство Interface намеренно не собирается: его дублирует более удобочитаемое свойство IName (в данном примере и оно не обязательно).

Порядок действий: настроить техжурнал, убедиться в корректности замера «Оценки производительности» БСП, затем повторить операцию с включённой отладкой.

Результаты в примере:

| Инструмент | Длительность | Что показывает |
|---|---|---|
| Замер БСП (регистр замеров времени) | 13,022 с | реальное время операции для пользователя |
| Техжурнал, событие SCALL | около 10,1 с | серверный вызов; совпадает с интервалом между VRSREQUEST и VRSRESPONSE |
| Замер отладчиком конфигуратора | 1,523 с | сумма длительностей всех строк кода, связанных с открытием формы |

Как получить точные моменты начала и конца операции из регистра замеров БСП. В колонках «Дата начала замера» и «Дата окончания» лежат миллисекунды UTC, отсчитываемые от 01.01.0001 00:00:00 (обычно значение получено функцией ТекущаяУниверсальнаяДатаВМиллисекундах()). Преобразовать можно любым удобным способом:

- онлайн-инструментом вроде https://www.epochconverter.com/ — интересуют только минуты, секунды и миллисекунды, расхождения в часовых поясах и годах не важны;
- выражением встроенного языка, дающим дату с точностью до секунды:

```bsl
'00010101' + ТекущаяУниверсальнаяДатаВМиллисекундах() / 1000
```

  Миллисекунды — это остаток от деления исходного значения на 1000, то есть три его последние цифры.

В примере получилось (минуты:секунды.миллисекунды): начало замера 25:10.779, окончание 25:23.801.

Сопоставление с техжурналом:

- начало замера БСП почти совпадает с началом вызова — событием VRSREQUEST. Так и должно быть: замер БСП стартует на клиенте непосредственно перед командой открытия формы;
- серверный вызов завершился раньше, чем замер БСП. Эта разница — время работы самого клиентского приложения.

Промежуточный итог: ситуация соответствует условиям методики, неравенство выполняется — 1,5 < 10,1 < 13.

⚠ в источнике неясно: сами записи технологического журнала, список замеров БСП и окно замера конфигуратора были приведены рисунками и в текстовую копию не попали.

### 1.4. Дополнительные инструменты

Стандартными средствами причина не видна, поэтому авторы подключают:

- отладчик уровня операционной системы — Windows Performance Recorder (сбор метрик) и Windows Performance Analyzer (визуализация и анализ);
- анализатор сетевых протоколов Wireshark либо прокси-сервер Fiddler Web Debugger.

**Windows Performance Recorder / Analyzer**

1. Установить и запустить WPR. Путь из статьи:

```text
C:\Program Files (x86)\Windows Kits\8.1\Windows Performance Toolkit\WPRUI.exe
```

2. Задать настройки записи. ⚠ в источнике неясно: конкретные настройки показаны только на рисунке, в текстовой копии их нет.
3. В тонком клиенте открыть форму списка документов и непосредственно перед воспроизведением проблемной операции нажать Start в WPR.
4. Когда форма открылась — остановить запись и открыть её для анализа.
5. В анализаторе найти процесс тонкого клиента по PID (в примере 5508). PID определяется в диспетчере задач ОС или по логам техжурнала.

Что увидели в примере: серьёзной дисковой нагрузки нет, а поток тонкого клиента длительно, вплоть до конца замера, занимает 100 % ЦП.

**Wireshark**

- Запускается Wireshark, операция повторяется в тонком клиенте с прямым подключением к серверу приложений 1С. В дампе ставится отбор по пакетам, источник которых — сервер приложений.
- Каждая строка дампа — кадр (frame), часть одного большого пакета поверх TCP (PDU, Protocol Data Unit). В сумме кадры дали пакет около 70 Кб. Это размер со сжатием; без сжатия данных должно быть порядка 2500–3500 Кб.
- В техжурнале то же число видно в «Content-Length» (или «Body») — 70577 байт.
- Чем полезен такой дамп вообще: можно разбирать отдельные кадры, видеть повторные отправки пакетов и сбросы TCP-соединений. Сбросы способны приводить к ошибкам в работе клиентов — например, из-за антивирусов, которые принимают такое содержимое за подозрительное.
- Для данной проблемы авторы считают более удобным Fiddler, потому что он позволяет анализировать уже HTTP-трафик.

**Fiddler**

1. Установить и запустить Fiddler. На панели инструментов нажать «Browse», выбрать браузер и открыть в нём информационную базу (веб-клиент).
2. Перейти в форму списка документов, то есть подготовить сценарий.
3. Вернуться в Fiddler и включить сбор трафика (F12).
4. В браузере открыть форму документа; после открытия сбор трафика отключить.
5. В списке слева найти относительно большой пакет искомого размера и выбрать его.
6. Справа перейти на страницу Inspectors, выбрать просмотр заголовков (Headers). Пакет представляет собой сериализованный JSON (Content-Type: application/json), поэтому его можно попросить Fiddler десериализовать.
7. В окне предпросмотра появится дерево ответа (response), передаваемого с сервера на клиент. Кнопка Expand All раскрывает дерево целиком, но это может занять время, поэтому сначала стоит понять, что именно искать.

### 1.5. Промежуточные выводы и поиск причины

Что известно к этому моменту:

- медленного прикладного кода 1С и медленных запросов нет;
- большая часть времени открытия формы приходится на сетевое взаимодействие;
- размер пакета с формой подозрительно велик;
- после получения пакетов тонкий клиент (или веб-клиент) сильно загружает ЦП;
- потерянное время лежит где-то между окончанием/началом работы прикладного кода и сетевой передачей.

Самый продуктивный для дальнейшего разбора тезис — о размере пакета. Возможные причины большого пакета с формой:

- форма сама по себе большая и сложная, с большим числом элементов и реквизитов. Случай, по оценке авторов, редкий и неправильный — его лучше исключать на этапе проектирования;
- форма простая, но в её реквизитах (включая данные объекта) много данных. Особенно это касается:
  - реквизитов типа ХранилищеЗначения и Строка(0);
  - больших коллекций — таблица, дерево, список;
  - реквизитов произвольного типа (по выражению авторов, здесь проблемы концентрируются).

Ход рассуждения в примере (авторы оговаривают, что в другой ситуации может быть иначе):

1. Проблема воспроизводится даже при очень малом количестве данных в табличной части, реквизитов у документа немного — значит, данные объекта не причина. Остаются реквизиты формы, отличные от основного реквизита «Объект».
2. Среди них несколько реквизитов произвольного типа.
3. По уже собранному замеру конфигуратора видно, что эти структуры заполняются большим числом элементов — например, 5059 в реквизите «СвойстваИзмерений».
4. В дампе Fiddler находится узел параметров формы (response/props); в нём несколько тысяч элементов, каждый — вложенная структура.
5. Находится прикладной код, заполняющий эти реквизиты: данных действительно много (2–3 Мб), это множество сложных вложенных структур.
6. Проверка гипотезы: заполнение реквизитов отключили — проблема с производительностью формы исчезла. Причина найдена верно.

### 1.6. Выводы и рекомендации авторов

Причина долгого открытия формы — сериализация и десериализация больших коллекций значений при передаче между клиентом и сервером.

Чтобы оценить вклад отдельных факторов, предлагается серия замеров: менять факторы и смотреть, как коррелирует с ними длительность. В примере проблему создавали структуры с данными справочников территорий и условий труда; меняли количество этих элементов и замеряли передачу данных с клиента на сервер (процедура ДанныеДляРедактированияВХранилище).

Оговорка авторов: абсолютные значения таких замеров рассматривать нельзя — они зависят от конфигурации компьютера, сети, версии платформы и других особенностей конкретного примера. Значение имеют только зависимости и их характер (линейная, экспоненциальная и т. д.). Предлагается проанализировать их самостоятельно или повторить замеры на актуальной версии платформы в своей среде.

⚠ в источнике неясно: таблица результатов замеров приведена рисунком и в текстовой копии отсутствует; известен лишь вывод, что при количестве элементов до 1000 влияние на производительность несущественно.

Возможные пути решения:

- ограничивать количество элементов коллекции до приемлемого (по замерам примера — до 1000);
  - этого можно добиться, учитывая уже введённые в форме значения. В документе «Табель» поле «Организация» обязательно к заполнению и является владельцем справочника «Территории» — соответствующий отбор заметно сократил бы число элементов. Дополнительно можно связать выбор с подразделением;
  - если в справочнике много помеченных на удаление элементов, отбор по пометке удаления тоже даст эффект;
- пересмотреть логику формы и не хранить в её реквизитах то, что быстро получается на сервере;
  - в частности, контекстную серверную процедуру ДанныеДляРедактированияВХранилище можно было бы сделать бесконтекстной и тем самым уйти от сериализации/десериализации свойств формы.

### 1.7. Оценка применимости на октябрь 2026

**Актуально.** Статья 2022 года, описывает управляемые формы, технологический журнал и подсистему «Оценка производительности» БСП. Что учитывать:

- расследование ведётся на стороне клиента, и инструменты в примере — для Windows: каталог журнала вида `D:\...`, WPR/WPA, Fiddler. Путь к WPR указан для Windows Kits 8.1 — версия набора в статье старая;
- для администратора сервера на Linux из статьи важны прежде всего критерии «это не сервер и не СУБД» (неравенство трёх замеров, сравнение администратора и обычного пользователя) и предупреждение о фильтре по процессам в клиентском logcfg.xml;
- абсолютные цифры примера переносить на свою систему нельзя — это прямо оговорено авторами.

## 3. Создание расписаний регламентных заданий

- Дата публикации: обновлено 19.07.2007
- Ссылка: https://its.1c.ru/db/metod8dev/content/1593/hdoc

### 3.1. Из чего состоит расписание

Расписание регламентного задания складывается из месячного, недельного и дневного расписаний, а также из одного или нескольких расписаний внутри дня.

Общее соглашение механизма: элемент расписания, который не задан, в формировании расписания не участвует.

Соответствие элементов расписания (как они названы в статье) и свойств расписания во встроенном языке:

| Элемент расписания | Свойство расписания | Значения и смысл |
|---|---|---|
| дата начала | ДатаНачала | не задана — расписание действует с текущего момента; до даты начала не выполняется |
| дата окончания | ДатаКонца | не задана — расписание действует неограниченно долго; после даты окончания не выполняется |
| Повторять каждые … дней | ПериодПовтораДней | 0 — только в пределах текущего дня; 1 — каждый день; 2 — через день и т. д. |
| дни недели (недельное расписание) | ДниНедели | по каким дням недели выполнять (фильтр поверх основной периодичности) |
| Повторять каждые … недель | ПериодНедель | 1 — каждую неделю; 2 — через неделю; значение 0 не используется |
| месяцы (месячное расписание) | Месяцы | по каким месяцам выполнять (фильтр) |
| выполнять в … день месяца | ДеньВМесяце | положительное число — отсчёт дней от начала месяца, отрицательное — от конца |
| выполнять в … день недели в месяце | ДеньНеделиВМесяце | порядковый номер дня недели в месяце; положительный — с начала месяца, отрицательный — с конца |
| время начала | ВремяНачала | не задано — берётся начало дня (00:00) |
| время окончания | ВремяКонца | не задано — берётся конец дня (меньше 00:00 следующего дня) |
| повторять через … сек. | ПериодПовтораВТечениеДня | секунд от начала предыдущего запуска до следующего; 0 — один раз в день |
| повторять с паузой … сек. | ПаузаПовтора | период повтора, отсчитываемый от завершения предыдущего запуска |
| завершать после | ВремяЗавершения | время, после которого задание завершается принудительно |
| завершать через | ИнтервалЗавершения | интервал в секундах от запуска, по истечении которого задание завершается принудительно |

### 3.2. Рекомендуемый порядок составления расписания

1. Начать с дат начала и окончания (ДатаНачала, ДатаКонца).
2. Задать периодичность в днях (ПериодПовтораДней).
3. Определить недельное и месячное расписания. Их удобно понимать как фильтры относительно основного расписания: они только добавляют ограничения к периодичности в днях.
4. Задать расписание внутри дня: время начала и окончания, затем периодичность в течение дня. Планировщик сначала решает, подходит ли день, и лишь для подходящего дня определяет, как выполнять расписание в его пределах. Внутри дня можно задать несколько расписаний.
5. При необходимости — параметры принудительного завершения.

### 3.3. Недельное расписание

- ДниНедели ограничивает выполнение указанными днями недели в дополнение к основной периодичности. Если нужный день недели выпал на пропускаемый по периодичности день, задание выполнено не будет.
- ПериодНедель задаёт период повтора недель и тоже действует как дополнение к основному расписанию.

Примеры (текстовое представление расписания, лишние пробелы вёрстки убраны):

```text
Выполнять: c 11 июля 2007 г. каждый 2-й день, по дням недели [понедельник, среда, пятница]; один раз в день
```

Выполняется через день, но только по понедельникам, средам и пятницам; если такой день приходится на пропускаемый — запуска нет.

```text
Выполнять: каждый день, по дням недели [вторник], через 1 нед.; один раз в день
```

Выполняется по вторникам через неделю.

### 3.4. Месячное расписание

Устроено аналогично недельному.

- Месяцы — в какие месяцы выполнять, в дополнение к основному расписанию.
- ДеньВМесяце — в какой по счёту день месяца; положительные значения считаются от начала месяца, отрицательные — от конца.
- ДеньНеделиВМесяце — порядковый номер дня недели в месяце (положительный — с начала, отрицательный — с конца). Оговорка авторов: порядковый номер дня недели в общем случае не совпадает с порядковым номером недели в месяце.

Примеры:

```text
Выполнять: каждый день, по дням недели [понедельник], последнего числа месяца; один раз в день
```

Выполняется только в те понедельники, которые приходятся на конец месяца.

```text
Выполнять: каждый день, по дням недели [понедельник], 1-й день недели в месяце; один раз в день
```

Выполняется каждый первый понедельник месяца.

### 3.5. Расписание в течение дня

- ВремяНачала и ВремяКонца задают окно внутри дня: с какого и по какое время расписание выполняется.
- ПериодПовтораВТечениеДня — через сколько секунд после начала предыдущего запуска стартовать следующий. Если предыдущий запуск ещё не завершился, планировщик ждёт его завершения. Ноль означает однократное выполнение в течение дня.
- ПаузаПовтора — такой же период повтора, но отсчёт идёт от момента завершения предыдущего запуска.

Пример:

```text
Выполнять: каждый день; каждые 120 сек.
```

Выполняется каждые две минуты.

### 3.6. Принудительное завершение

ВремяЗавершения и ИнтервалЗавершения определяют, соответственно, время и интервал в секундах с момента запуска, после которых задание будет завершено принудительно, если само не закончилось. Назначение по статье — останавливать слишком долгие задания (пример авторов — ночные регламентные процедуры), чтобы они не мешали нормальной работе пользователей.

### 3.7. Оговорка: периоды — это минимальное время

- Все рассмотренные периоды задают минимальное время. Например, период повтора в течение дня — это минимальный интервал, по истечении которого задание будет запущено.
- Если задание по каким-то причинам не может стартовать в назначенное время, запуск откладывается.
- Если отложенный запуск стал возможен в тот же день, при вычислении расписания используется время последнего запуска этого дня.
- Если запуск перенёсся на следующий день, время последнего запуска сбрасывается: считается, что в этот день задание не выполнялось.

### 3.8. Оценка применимости на октябрь 2026

**Актуально по принципам, но статья старая.** Материал 2007 года (в примере фигурирует дата 11 июля 2007 г.) и написан для платформы того времени. Логика расписания, перечень свойств и их смысл изложены как общие принципы; конкретное поведение планировщика следует сверять с документацией к используемой версии платформы. Особенностей клиент-серверного и файлового вариантов эта статья не описывает (см. раздел 2 — там только отсылка к документации).

## 4. Мониторинг и управление регламентными и фоновыми заданиями

- Дата публикации: обновлено 20.09.2007
- Ссылка: https://its.1c.ru/db/metod8dev/content/1622/hdoc

### 4.1. Перечень средств

Статья называет четыре группы средств мониторинга и управления заданиями:

1. программные средства;
2. журнал регистрации;
3. COM-соединение и консоль кластера;
4. консоль заданий.

### 4.2. Программные средства

- Назначение: создание дополнительных утилит администрирования заданий или встраивание функций администрирования в само приложение.
- Основа — объекты встроенного языка МенеджерФоновыхЗаданий и МенеджерРегламентныхЗаданий.
- Возможности: поиск регламентных и фоновых заданий по набору критериев (имя, ключ, состояние и т. д.), получение списка выполняющихся фоновых заданий, отмена выполнения фоновых заданий, ожидание их завершения.
- Доступность: из любого соединения, но только пользователю с административными правами.

### 4.3. Журнал регистрации

- Позволяет отследить выполнение фоновых заданий, когда другие средства недоступны.
- При запуске фонового задания в журнал пишется событие начала выполнения.
- По окончании — событие успешного завершения либо описание ошибки, если задание завершилось с ошибкой.
- Средствами встроенного языка в журнал можно добавлять собственные диагностические сообщения (пример авторов — количество обработанных элементов), чтобы понимать, что происходит в выполняющемся задании в данный момент.

### 4.4. COM-соединение и консоль кластера

Позволяют:

- блокировать установку соединений — эта блокировка одновременно запрещает и запуск регламентных заданий информационной базы;
- блокировать запуск регламентных заданий (отдельно);
- получать список соединений выполняющихся фоновых заданий, с возможностью принудительного закрытия их администратором.

### 4.5. Консоль заданий

Названа наиболее развитым средством. Это внешняя обработка, которая управляет заданиями интерактивно и одновременно демонстрирует возможности встроенного языка по мониторингу и управлению заданиями. Запускается из любого соединения пользователем с административными правами.

Функции:

- создание, удаление, изменение регламентных заданий, установка нового расписания, просмотр списка регламентных заданий;
- выполнение, отмена и мониторинг фоновых заданий;
- автообновление списка заданий для наблюдения за динамикой выполнения.

### 4.6. Оценка применимости на октябрь 2026

**Частично устарело.** Статья 2007 года, перечень средств отражает платформу того времени:

- COM-соединение — технология Windows, поэтому на самом сервере под Linux этот способ в описанном виде неприменим; те же действия (блокировки, список соединений фоновых заданий) статья относит и к консоли кластера;
- более поздние средства администрирования кластера в статье не упоминаются — по этому источнику о них ничего сказать нельзя;
- «консоль заданий» описана как внешняя обработка без указания, где её взять и для каких версий она предназначена (⚠ в источнике неясно).

Принципы остаются верными: блокировка установки соединений останавливает и регламентные задания; есть отдельная блокировка регламентных заданий; журнал регистрации фиксирует старт и результат фонового задания; программное управление требует административных прав.

## 5. Рекомендации по использованию временных файлов в конфигурациях

- Дата публикации: 10.02.2012
- Ссылка: https://its.1c.ru/db/metod8dev/content/4716/hdoc

### 5.1. Содержание

Статья короткая, состоит из четырёх рекомендаций.

1. **Имя временного файла получать методом глобального контекста ПолучитьИмяВременногоФайла().** Что это даёт:
   - уникальность имени файла гарантирована;
   - если файл не будет удалён средствами встроенного языка, платформа удалит его при следующем запуске.
2. **Удаление временных файлов контролировать самостоятельно.** Платформа удаляет их только при своём перезапуске. При активном создании файлов они могут занять значительную часть дискового пространства раньше, чем случится перезапуск. Авторы подчёркивают, что это особенно важно для кода, исполняемого на сервере: регламент эксплуатации сервера может вообще не предполагать регулярных перезапусков.
3. **Время полезной жизни временного файла на сервере — не больше одного обращения к серверу.** Причина: следующее обращение может попасть на другой физический сервер.
4. **В алгоритмах, где возможны исключения, создание и удаление файлов помещать в конструкцию Попытка-Исключение.**

### 5.2. Что из этого следует для администратора сервера

Только то, что прямо вытекает из текста статьи:

- автоматическая очистка временных файлов, созданных через ПолучитьИмяВременногоФайла(), привязана к перезапуску платформы; при долгой непрерывной работе сервера и неаккуратном прикладном коде место под временные файлы может закончиться;
- рассчитывать, что файл, созданный в предыдущем серверном вызове, будет доступен в следующем, нельзя: следующий вызов может обслужить другой физический сервер. Это требование к прикладному коду, а не настройка сервера.

Каталоги временных файлов, пороги заполнения и процедуры очистки в статье не описаны — в этом источнике их нет.

### 5.3. Оценка применимости на октябрь 2026

**Актуально.** Статья 2012 года, но содержит общие правила без привязки к версиям платформы, ОС и СУБД.

## 6. Использование встроенного языка на сервере 1С:Предприятия

- Дата публикации: 12.10.2015
- Ссылка: https://its.1c.ru/db/metod8dev/content/2602/hdoc

### 6.1. Как управление попадает на сервер

- Код встроенного языка вызывается на сервере через общие модули.
- Управление переходит на сервер только при вызове процедуры или функции общего модуля, которая располагается на сервере и не располагается на клиенте. После выполнения управление возвращается на клиент.
- Расположение процедур регулируется двумя способами: свойствами общих модулей (для модуля целиком) и инструкциями препроцессора `#Если` (для отдельных процедур и участков).
- Если процедура общего модуля расположена и на клиенте, и на сервере, ею могут пользоваться и клиентские, и серверные процедуры, но перехода управления на сервер при её вызове не будет.
- Инструкции препроцессора допустимы и в модулях объектов и наборов записей, но там они лишь определяют, будет ли участок модуля использоваться на сервере или на клиенте. Переход управления на сервер возможен только через вызов процедуры общего модуля.

Пример из демонстрационной конфигурации «Примеры ИТС»:

- общий модуль ВыполнениеОперацийНаСервере: свойство «Сервер» установлено, «Клиент» — нет. Его процедур на клиенте нет, поэтому их вызов переводит управление на сервер;
- в модуле — процедура ПровестиДокументыНаСервере(), которая перепроводит все документы указанного вида на сервере;
- вызывается она из обработки ОбработкаДокументов(). В клиент-серверном варианте вызов приводит к переходу на сервер, там процедура выполняется, затем управление возвращается вызывающей процедуре на клиенте.

### 6.2. Ограничения серверного контекста

- На сервере доступно только подмножество типов данных 1С:Предприятия; у части типов на сервере недоступны отдельные свойства и методы. В основном это интерфейсные возможности: механизмы, отвечающие за интерфейс, на сервере недоступны все.
- Из интерфейсных возможностей на сервере работает только вызов метода Сообщить().
- Возможность использования на сервере указана в документации для типов данных, а также для отдельных свойств и методов.
- Если модуль будет использоваться на сервере, участки с обращениями к недоступным на сервере механизмам нужно отключать инструкциями `#Если`.
- Важная оговорка: если объект или набор записей используется на сервере, его модуль компилируется на сервере целиком. Поэтому разграничивать участки модуля нужно независимо от того, собираются ли конкретную процедуру вызывать на сервере.

### 6.3. Ограничения на параметры и возвращаемые значения

Если вызов процедуры общего модуля передаёт управление на сервер, действуют довольно жёсткие ограничения на типы параметров и возвращаемых значений функций. Допустимы:

- типы с немутабельными значениями (значения которых не могут изменяться): примитивные типы, ссылки на объекты базы данных, значения системных перечислений, хранилище значения;
- коллекции Структура, Соответствие, ТаблицаЗначений, Массив — к их содержимому применяются те же ограничения;
- результат запроса.

### 6.4. Производительность: когда перенос на сервер оправдан

Откуда может взяться выигрыш (в описанном примере с перепроведением документов):

- сокращается передача информации между клиентом и сервером;
- массовая операция выполняется на более мощном компьютере.

Оговорки авторов:

- целесообразность оценивается по многим факторам, выигрыш не всегда существенен. Пример: затраты на передачу данных в локальной сети невелики, а основное время уходит на операции сервера баз данных;
- такое решение увеличивает нагрузку на сервер, а он — разделяемый ресурс;
- практическая рекомендация — провести эксперимент в условиях, приближенных к реальным, и по нему оценить, насколько решение повышает эффективность системы.

### 6.5. Ограничение прав доступа: привилегированный модуль

Выполнение кода на сервере применяется не только ради производительности, но и для задач разграничения доступа. Для этого служит свойство общего модуля «Привилегированный»: в таком модуле проверка прав доступа не выполняется.

Пример из конфигурации «Примеры ИТС»:

- роли «Кладовщик» полностью запрещён доступ к регистру УчетНоменклатуры;
- чтобы кладовщик мог вводить и проводить приходные накладные, модуль документа при проведении вызывает процедуру СформироватьДвиженияПриходнойНакладной() общего модуля ВыполнениеОперацийНаСервере, где и записываются движения;
- у этого модуля установлено свойство «Привилегированный», поэтому права в нём не проверяются. Не имея доступа к регистру даже на чтение, кладовщик проводит документ ПриходнаяНакладная, а регистр меняется строго по алгоритму общего модуля;
- даже если разрешить кладовщику запуск произвольных внешних обработок, он не сможет сделать с регистром ничего, кроме предусмотренного в этом модуле;
- у документа ПриходнаяНакладная в свойствах метаданных отключено автоматическое удаление движений — чтобы проведение, вызываемое на клиенте, не обращалось к регистру;
- удаление движений реализовано в модуле документа, в процедуре ОбработкаУдаленияПроведения(). Оно вызывается на клиенте, поэтому пользователь с ролью «Кладовщик» выполнить это действие не сможет.

Дополнительная возможность: результат запроса, выполненного на сервере, можно получить на клиенте. Это позволяет выдавать сотруднику строго ограниченную, отобранную по нужным критериям информацию по данным, доступ к которым ему запрещён.

### 6.6. Оценка применимости на октябрь 2026

**Частично устарело.** Дата публикации — 2015 год, но изложение соответствует модели обычного приложения: проведение документа и удаление движений «на клиенте», переход на сервер исключительно через общие модули.

- Утверждение «переход на сервер возможен только через общий модуль» относится к этой модели. В статье 2022 года из этого же конспекта (раздел 1) фигурируют контекстные и бесконтекстные серверные вызовы из кода управляемой формы — то есть для управляемых форм картина шире, а данная статья этого не описывает.
- Остаются верными как принципы: роль свойств «Сервер»/«Клиент» общего модуля и инструкций `#Если`; недоступность интерфейсных механизмов на сервере; ограничения на типы передаваемых значений; назначение свойства «Привилегированный»; предупреждение о том, что перенос на сервер увеличивает нагрузку на разделяемый ресурс и требует проверки экспериментом.

## 7. Особенности работы с хранилищем конфигурации

- Дата публикации: 02.07.2013 (рубрики «Платформа 1С:Предприятие 8», «Средства конфигурирования»)
- Ссылка: https://its.1c.ru/db/metod8dev/content/2287/hdoc

### 7.1. Назначение и принцип работы

- Хранилище конфигурации — средство коллективной разработки. Это база данных, в которой сохраняются все изменения конфигурации, сделанные при разработке: история, кто и когда вносил изменения. Число разработчиков не ограничено.
- После подключения информационной базы к хранилищу в неё загружается последняя версия конфигурации, и все объекты метаданных становятся недоступными для редактирования.
- Единица редактирования («объект разработки») — основные объекты метаданных (справочники, документы, регистры сведений и т. п.), а также формы и макеты. Разные пользователи редактируют объекты разработки независимо.
- Реквизиты, табличные части и подобное отдельными объектами разработки не являются и редактируются в составе родительского объекта разработки.
- Стратегия параллельной работы — пессимистическая блокировка: пока объект редактирует один пользователь, остальные изменять его не могут.

Четыре простейшие операции:

| Операция | Что происходит |
|---|---|
| Захват объекта | объект становится доступным для редактирования; при захвате из хранилища подтягивается новая версия объекта, если она есть |
| Помещение объекта | изменённая версия попадает в хранилище и становится доступной остальным участникам |
| Получение объекта | в базу загружается актуальное состояние объекта из хранилища (в статье операция названа без расшифровки) |
| Отмена захвата | изменения не помещаются, из хранилища получается прежняя версия объекта |

### 7.2. Полная замена конфигурации при подключении

При подключении информационной базы к хранилищу текущая редактируемая конфигурация полностью заменяется конфигурацией хранилища. Это нужно для полного соответствия идентификаторов объектов метаданных.

Если в базе есть объекты, которые нужно перенести в конфигурацию хранилища, порядок такой:

1. выгрузить конфигурацию информационной базы в файл;
2. подключить информационную базу к хранилищу;
3. захватить объекты, которые нужно заместить;
4. выполнить объединение с требуемой конфигурацией (по смыслу — с файлом, выгруженным на шаге 1).

### 7.3. Версии, история, комментарии

- Предмет разработки — конфигурация целиком, а не отдельные объекты. Хранилище ведёт историю конфигурации.
- Каждое помещение объектов создаёт новую версию конфигурации. Для неё записываются дата создания, пользователь и списки добавленных, изменённых и удалённых объектов разработки.
- История отдельных объектов разработки не ведётся. Просмотреть историю объекта можно, но загрузить из хранилища один объект в состоянии какой-либо версии нельзя — загружается только версия конфигурации целиком.
- Обходной путь, чтобы получить объект определённой версии: захватить объект и выполнить объединение с той версией конфигурации, в которой он находится в нужном состоянии.
- К версии можно записать комментарий. Рекомендуется комментировать версии, чтобы потом было понятно, что изменено. Для наиболее значимых версий (пример — выпуск релиза) рекомендуется ставить метку — короткую строку, описывающую версию.
- Рекомендуется периодически получать актуальное состояние объектов разработки: это избавляет от трудностей при помещении (пример авторов — ситуации с удалением объектов метаданных из конфигурации).
- Средства работы с хранилищем позволяют: просматривать историю версий, сохранять конфигурацию выбранной версии в файл, сравнивать её с другими версиями этого хранилища или с конфигурацией из файла.
- Если хранилище по какой-то причине недоступно, работу с ранее захваченными объектами можно продолжать — постоянная связь с хранилищем для разработки не обязательна.

### 7.4. Два режима использования

Режимы различаются и набором функций, и назначением.

**С подключением информационной базы к хранилищу** — основной режим, для групповой разработки.

- Работа начинается с процедуры подключения базы к хранилищу.
- От имени одного пользователя к одному хранилищу одновременно может быть подключена одна информационная база.
- Если пользователь, у которого уже есть подключённая к этому хранилищу база, попытается подключить другую, он получит предупреждение. Если подключение всё же выполнить, прежняя база не сможет работать с этим хранилищем без предварительного отключения от него.
- Аутентифицироваться в хранилище от имени пользователя, который не подключал данную базу к хранилищу, невозможно.
- При подключении в хранилище регистрируется строка соединения с информационной базой. Если при следующих соединениях она окажется другой (базу переместили на другой ресурс), платформа выдаст предупреждение и после подтверждения обновит строку соединения.
- Предупреждение, важное при копировании баз: если соединение выполнила копия информационной базы, оригинал уже не сможет работать с этим хранилищем без предварительного отключения от него.

**Без подключения информационной базы к хранилищу** — просмотр и администрирование хранилища без замены редактируемой конфигурации.

- Доступно: получить конфигурацию определённой версии, посмотреть историю конфигурации или отдельных объектов разработки, редактировать права пользователей хранилища и менять их состав.
- Работа начинается с открытия хранилища — аутентификации пользователя; она предлагается автоматически при первом действии с хранилищем в текущем сеансе Конфигуратора.
- Чтобы открыть другое хранилище в том же сеансе Конфигуратора, текущее нужно закрыть соответствующим пунктом меню.

Предполагаемое применение второго режима — подготовка дистрибутивов конфигураций на основе файлов выгрузки информационных баз:

1. Создать новую информационную базу.
2. Открыть хранилище конфигурации.
3. Загрузить из хранилища конфигурацию нужной версии.
4. Заполнить информационную базу необходимыми данными.
5. Подготовить дистрибутив конфигурации.
6. При выпуске следующих дистрибутивов повторять процедуру с шага 2; если новые данные вводить не требуется — сразу переходить к подготовке дистрибутива.

### 7.5. Режим совместимости хранилища

- Появился в платформе 8.3.3. Позволяет старшим версиям платформы работать с хранилищами, созданными в младших версиях (начиная с 8.3.2), без конвертации.
- Где задаётся: окно «Администрирование хранилища», закладка «Прочие».
- На момент написания статьи доступны два значения: «Версия 8.3.2» и «Не использовать».
- Смена режима и нажатие кнопки «Установить» запускают конвертацию базы данных хранилища.

| Признак | «Версия 8.3.2» | «Не использовать» |
|---|---|---|
| Контроль ссылочной целостности | строгий, при получении и помещении объектов; охватывает также формы, макеты и интерфейсы | такой же, как на уровне объектов метаданных; формы, интерфейсы и макеты не контролируются |
| Влияние на параллельность разработки | приходится получать/помещать связанные объекты | выше: захватывать нужно меньше зависимых объектов |
| Где хранятся объекты метаданных | в базе данных хранилища | в файловой системе — это существенно увеличивает объём данных, который можно поместить в хранилище |
| Для каких хранилищ действует по умолчанию | для существующих | для вновь создаваемых |

### 7.6. Контроль ссылочной целостности

- Стандартные механизмы конфигурации контролируют ссылки на уровне объектов метаданных: нельзя, например, удалить справочник, на который ссылается реквизит документа. На уровне интерфейсов, форм и макетов такой контроль не ведётся.
- Иллюстрация: удаление справочника «Склады» из демонстрационной конфигурации «Примеры ИТС». Проверка находит ссылки:

```text
"Справочник.Склады" использован в:
Документ.ПриходнаяНакладная.Реквизит.Склад.Тип
Документ.РасходнаяНакладная.Реквизит.Склад.Тип
РегистрНакопления.УчетНоменклатуры.Измерение.Склад.Тип
```

  После удаления этих ссылок справочник успешно удаляется, хотя ссылки на него остаются в интерфейсе «Основной» (кнопка «Склады» подменю «Справочники» с действием открытия справочника) и в формах документов ПриходнаяНакладная и РасходнаяНакладная (поля ввода реквизита «Склад» по-прежнему имеют тип СправочникСсылка.Склады).
- В режиме «Версия 8.3.2» хранилище контролирует ссылки полностью: и на уровне объектов метаданных, и в содержимом их форм и макетов, и в содержимом интерфейсов. Следствие — при действии с объектом может потребоваться получить из хранилища или поместить в него связанные объекты. Хранилище анализирует ссылки и требует дополнительные объекты только при необходимости.
- В режиме «Не использовать» контроль ведётся только на уровне объектов метаданных.
- Анализ ссылок рекурсивный: сначала анализируется объект, над которым выполняется действие; если выявлена необходимость операции над дополнительными объектами, тот же анализ выполняется для них — и так до тех пор, пока не проанализированы ссылки всех затронутых объектов.

### 7.7. Особенности конфигурирования в подключённой базе

- Чтобы редактировать объект, его нужно захватить.
- Чтобы изменить объект метаданных, не являющийся объектом разработки (реквизит, табличная часть), захватывается содержащий его объект разработки.
- Чтобы добавить новый объект метаданных или изменить порядок следования существующих, захватывается родительский объект разработки.

### 7.8. Удаление объектов конфигурации

Авторы выделяют удаление как операцию, требующую особой аккуратности и внимательности.

Что нужно захватить для удаления объекта: сам объект, его родительский объект и все подчинённые ему объекты. После этого объект можно удалить из конфигурации. Но при помещении, если на удалённый объект остались ссылки в других объектах, хранилище потребует поместить и эти объекты — с очищенными ссылками.

Рекомендуемая последовательность:

1. До удаления выполнить поиск ссылок на объект.
2. Захватить все найденные объекты и вычистить из них ссылки на удаляемый объект.
3. В режиме «Версия 8.3.2» дополнительно удалить ссылки из форм, интерфейсов и макетов. В режиме «Не использовать» этого не требуется.
4. Удалить объект из конфигурации и попытаться поместить изменения в хранилище.
5. Если помещение не удалось из-за обнаруженных ссылок на удалённый объект — захватить указанные объекты и повторить попытку.

**Пример: удаление справочника «Склады» в режиме «Версия 8.3.2»**

1. Поиск ссылок (результат тот же, что в п. 7.6: два документа и регистр накопления).
2. Захват этих объектов, удаление из них реквизитов, ссылающихся на справочник «Склады».
3. Захват интерфейса «Основной», удаление кнопки «Склады» из подменю «Справочники».
4. Захват корневого объекта конфигурации и справочника «Склады».
5. Удаление справочника из конфигурации.
6. Попытка поместить корневой объект в хранилище. В окне сообщений:

```text
Ошибка помещения объектов в хранилище.
Для выполнения операции необходимо поместить в хранилище объекты:
	- Документ.ПриходнаяНакладная.Форма.ФормаДокумента	(объект не захвачен пользователем)
	- Документ.РасходнаяНакладная.Форма.ФормаДокумента	(объект не захвачен пользователем)
```

7. Захват объектов, в которых найдены ссылки на удалённый объект.
8. Повторная попытка поместить корневой объект. После подтверждения появляется предупреждение о ссылках на удалённый объект, в окне сообщений:

```text
Операция не может быть выполнена:
	Объект 'Документ.ПриходнаяНакладная.Форма.ФормаДокумента' содержит ссылки на удаленные объекты:
		- Справочник.Склады
	Объект 'Документ.РасходнаяНакладная.Форма.ФормаДокумента' содержит ссылки на удаленные объекты:
		- Справочник.Склады
```

9. Утвердительный ответ на предложение очистить некорректные ссылки: выполняется очистка, конфигурация сохраняется, помещение повторяется автоматически. Итог в окне сообщений:

```text
Объект помещен в хранилище: ПримерыИТС
Объект помещен в хранилище: Документ.ПриходнаяНакладная.Форма.ФормаДокумента
Объект помещен в хранилище: Документ.ПриходнаяНакладная
Объект помещен в хранилище: Документ.РасходнаяНакладная.Форма.ФормаДокумента
Объект помещен в хранилище: РегистрНакопления.УчетНоменклатуры
Объект помещен в хранилище: Интерфейс.Основной
Объект помещен в хранилище: Документ.РасходнаяНакладная
```

10. Удаление завершено.

**Пример: то же удаление в режиме «Не использовать»**

1. Поиск ссылок (тот же результат).
2. Захват найденных объектов, удаление из них реквизитов, ссылающихся на справочник «Склады».
3. Захват корневого объекта конфигурации и справочника «Склады».
4. Удаление справочника из конфигурации.
5. Попытка поместить корневой объект в хранилище — проходит сразу. В окне сообщений:

```text
Объект помещен в хранилище: ПримерыИТС
Объект помещен в хранилище: Документ.ПриходнаяНакладная
Объект помещен в хранилище: РегистрНакопления.УчетНоменклатуры
Объект помещен в хранилище: Документ.РасходнаяНакладная
```

6. Удаление завершено. Судя по перечню помещённых объектов, интерфейс и формы документов при этом не затрагиваются.

### 7.9. Оптимизация хранения данных

- В режиме «Не использовать» объекты метаданных лежат в файловой системе.
- Большое количество файлов может несколько замедлять работу с хранилищем — особенно если хранилище расположено на сетевом диске.
- Если замедление стало заметным, в окне «Администрирование хранилища» на закладке «Прочие» выполняется оптимизация хранения данных хранилища.
- Флажок «Предлагать оптимизацию после выполнения операций с хранилищем» (в том же окне) включает предложение администратору хранилища провести оптимизацию.

### 7.10. Оценка применимости на октябрь 2026

**Частично устарело.** Статья 2013 года, привязана к платформе 8.3.2–8.3.3:

- формулировка о двух значениях режима совместимости дана «на момент написания»; перечень режимов в используемой версии платформы нужно сверять с её документацией;
- примеры построены на обычном интерфейсе («Интерфейс.Основной», подменю «Справочники») — это наследие обычного приложения;
- серверный вариант хранилища и удалённый доступ к нему в статье не рассматриваются: говорится лишь о расположении хранилища, в том числе на сетевом диске.

Остаются верными как принципы: пессимистическая блокировка и четыре операции; полная замена конфигурации при подключении базы; привязка «один пользователь — одна подключённая база» и последствия подключения копии базы; различие режимов по строгости контроля ссылок и по месту хранения объектов; порядок удаления объектов.

## 8. Варианты использования хранилища конфигурации

- Дата публикации: 02.07.2013 (рубрики «Платформа 1С:Предприятие 8», «Средства конфигурирования»)
- Ссылка: https://its.1c.ru/db/metod8dev/content/2289/hdoc

Статья продолжает предыдущую: принципы работы описаны в разделе 7, здесь — сценарии применения без подробностей самого процесса разработки.

### 8.1. Группа разработчиков

- Основное назначение хранилища — совместная разработка конфигурации группой.
- Главное преимущество — несколько разработчиков одновременно изменяют одну и ту же конфигурацию.
- Хранилище ведёт историю изменений: в любой момент можно получить конфигурацию более ранней версии или вернуться к ней.
- У каждой версии может быть комментарий с описанием изменений и метка, выделяющая версию в истории.

### 8.2. Один разработчик

- Частный случай группового варианта: хранилище выступает архивом конфигурации для ведения истории изменений.
- Разработка всё равно ведётся по правилам хранилища: захват объектов, изменение, помещение.
- Поскольку параллельно работающих разработчиков нет, при помещении можно всегда устанавливать признак «Оставить захваченными».

### 8.3. Автономная работа

Разработка в подключённой конфигурации предполагает непосредственную связь с базой данных хранилища. Если нужно конфигурировать без связи:

1. заранее захватить объекты, которые планируется менять;
2. при открытии конфигурации отказаться от соединения с хранилищем, но не отключаться от хранилища — на соответствующее предложение системы ответить отрицательно;
3. все ранее захваченные объекты остаются доступными для редактирования;
4. при следующем подключении по необходимости синхронизировать конфигурацию с хранилищем, поместив захваченные объекты.

### 8.4. Отчёты по истории хранилища

| Отчёт | Содержание |
|---|---|
| По версиям | сведения о версиях конфигурации хранилища: для каждой версии — создавший её пользователь, списки добавленных, изменённых и удалённых объектов, комментарий |
| По объектам | сведения об объектах конфигурации: для каждого объекта — список комментариев к версиям, в которых он добавлялся, изменялся или удалялся |
| По комментариям | версии, сгруппированные по комментариям: для каждого уникального комментария — объекты, добавленные, изменённые или удалённые в версиях с таким комментарием |

Любой отчёт формируется с отбором: по объектам конфигурации, по версиям (диапазон задаётся номерами версий или датами), по пользователям, чьи изменения привели к созданию версий.

### 8.5. Резервное копирование хранилища

Состав резервной копии:

| Что | Копировать? | Пояснение из статьи |
|---|---|---|
| Файл `1cv8ddb.1cd` | да | обязательная часть копии; назначение файла в статье отдельно не поясняется |
| Каталог `data` | да, если существует | появляется при работе в режиме совместимости «Не использовать», содержит файлы объектов метаданных |
| Каталог `cache` | необязательно | вспомогательные файлы с версиями конфигурации; создаётся автоматически; его можно периодически очищать для освобождения места на диске |

После восстановления хранилища из резервной копии сведения о захваченных объектах синхронизируются с приоритетом хранилища: состояние захвата объекта в любом случае берётся из хранилища.

Способ копирования (остановка работы с хранилищем, инструменты, периодичность) в статье не описан — в источнике этого нет.

### 8.6. Хранилище и механизм поддержки

- Механизм поддержки конфигурации и хранилище можно использовать совместно.
- Оба запрещают редактирование объектов по собственной логике. Чтобы изменить объект конфигурации, которая и подключена к хранилищу, и стоит на поддержке, нужно выполнить оба условия: захватить объект в хранилище и сделать его доступным для редактирования средствами механизма поддержки.

**Обновление конфигурации**

- Для корректного обновления конфигурации, подключённой к хранилищу, рекомендуется предварительно захватить все объекты, затем выполнить обновление и поместить объекты обратно.
- Обновление возможно и при захвате только корневого объекта конфигурации. Но тогда, если в поставке есть обновление для незахваченного объекта, оно применено не будет.

**Изменение параметров поддержки**

- Требуется захват корневого объекта конфигурации.
- Остальные разработчики увидят изменённые параметры поддержки только после помещения корневого объекта в хранилище.

### 8.7. Хранилище и распределённая информационная база

- К хранилищу может быть подключена только конфигурация базы, являющейся корневым узлом распределённой ИБ (значение главного узла в такой базе — Неопределено).
- Базы подчинённых узлов подключить к хранилищу нельзя: конфигурация в них изменяется только через сообщения обмена.
- В остальном работа с хранилищем при разработке в рамках распределённой ИБ не отличается от работы в обычной базе.

### 8.8. Оценка применимости на октябрь 2026

**Актуально по принципам.** Статья 2013 года, описывает организационные сценарии без жёсткой привязки к версии платформы.

- Самое полезное для администратора — состав резервной копии хранилища (`1cv8ddb.1cd` + `data`, без обязательного `cache`) и правило синхронизации захватов после восстановления. Состав описан по состоянию на 2013 год (в связанной статье из раздела 7 упоминается платформа 8.3.3); для используемой версии платформы его стоит сверить с документацией.
- Правила совместной работы с механизмом поддержки и с распределённой ИБ сформулированы как принципиальные ограничения.
