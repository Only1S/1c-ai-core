# ИТС-конспект (методические материалы): Kerberos-аутентификация для Linux-сервера 1С, OpenID, сохранение аутентификации
> Источник: статьи раздела «Методическая поддержка» портала 1С:ИТС (ссылки — в разделах). Это конспект своими словами, не дословный текст. Составлен 2026-10-10.

## Кратко: главные официальные рекомендации

### Kerberos для Linux-сервера 1С (статья 2799; пример на 8.1/8.2 — см. оценку применимости)

1. **DNS.** Каждый Linux-компьютер, участвующий в аутентификации, регистрируется в DNS домена вручную (Windows-машины регистрируются сами при включении в домен). На сервере 1С DNS-сервером должен быть DNS контроллера домена.
2. **Время.** Часы сервера 1С синхронизируются с контроллером домена: тикеты Kerberos действуют ограниченное время, большое расхождение часов недопустимо.
3. **Отдельная доменная учётная запись для сервера 1С.** К ней утилитой `ktpass` привязывается имя службы и для неё выгружается keytab-файл с секретным ключом.
4. **Формат имени службы:** `<локальный Linux-пользователь, от которого запущен сервер 1С>/<имя сервера с доменом>@<REALM>` (в примере `usr1cv81/srv1c.krb.local@KRB.LOCAL`). Не путать с доменным пользователем из параметра `-mapuser` (в примере `usr1cv8`).
5. **Шифрование.** Если Kerberos на Linux поддерживает RC4-HMAC — флажок «Use DES encryption types with this account» у учётной записи снять. Если не поддерживает — флажок обязательно установить, `ktpass` запускать с `-crypto DES-CBC-CRC`, в `krb5.conf` прописать DES-типы. (Оценка конспекта: на 2026 год оба алгоритма устаревшие, см. раздел 1.1.)
6. **keytab на сервере 1С:** положить в каталог установки сервера 1С, владелец — пользователь и группа сервера 1С, права `600`. Другое расположение допустимо — тогда нужно исправить переменную `SRV1CV8_KEYTAB` в конфигурационном файле.
7. **Проверять по шагам:** `kinit <доменный пользователь>` → `klist` → `kdestroy`; затем `klist -e -k -t <keytab>` (то ли имя службы и тот ли алгоритм); затем `kinit -k -t <keytab> <имя службы>` — должен отработать молча, без запроса пароля.
8. **Перезапуск сервера 1С после настройки не нужен** — кроме случая, когда в конфигурационном файле меняли расположение keytab-файла.

### OpenID (статья 5872)

9. Платформа поддерживает стандарт OpenID v2. Клиент OpenID (RP) — веб-расширение 1С; провайдер (OP) — публикация информационной базы на веб-сервере.
10. В `default.vrd` клиента — `<openid><rely url="https://…/e1cib/oid2op"/></openid>`; в `default.vrd` провайдера — `<openid><provider><lifetime>…</lifetime></provider></openid>`.
11. Протокол, имя сервера и порт в адресе OP должны быть одинаковыми везде, где к OP обращаются. При расхождении (даже явный `:443` против адреса без порта) проверка идентификатора не проходит, в ТЖ появляется `Rely Party: id_res invalid local id`.
12. Клиента и провайдера нельзя описать в одном `default.vrd`. Делаются две раздельные публикации; они могут работать с одной и той же базой.
13. Цепочка сертификатов, которой подписан сертификат веб-сервера OP, должна быть доверенной: с 8.3.8 — через хранилище доверенных корневых сертификатов ОС; до 8.3.8 и в режиме совместимости с 8.3.7 — через файл `cacert.pem`.
14. К OP обращаются по тому имени, на которое выдан сертификат, а не по алиасу хоста (не `https://localhost`).
15. Главный симптом ошибки настройки — вместо окна OpenID пользователь видит окно локальной аутентификации базы.
16. Диагностика — технологический журнал с `<system level="trace" class="OID2Log"/>` и событием `SYSTEM`. Запись `OP discovery error` означает одно из двух: OP недоступен с клиента по HTTPS либо цепочка сертификатов не прошла проверку.
17. Проверки доступности: `telnet OP_NAME https`; открыть в браузере с машины RP адрес `https://OP_NAME/OP_IB_PUB/e1cib/oid2op` (должен скачаться файл `oid2op`). Адрес лучше копировать из `default.vrd` публикации RP.
18. Прокси: настройки прокси ОС и `inetcfg.xml` платформы не должны отличаться от настроек браузера, в котором проверка проходит. При дешифрующем прокси доверенной должна быть та цепочка сертификатов, которую видит конкретный клиент, то есть сертификат прокси.
19. `returnto` (с 8.3.8): в публикации провайдера — регулярные выражения разрешённых хостов возврата. Элемент необязательный, может повторяться; по умолчанию отсутствует.
20. Если имя пользователя и пароль передаются при входе явно либо у пользователя включена аутентификация средствами ОС — вход выполняется локально, без обращения к OP, даже при включённой OpenID-аутентификации.
21. Перед передачей материалов в поддержку оценить, нет ли в конфигурациях и логах персональных данных и можно ли их передавать.

### Сохранение аутентификации при OpenID (статья 6029, платформа 8.3.26 и выше)

22. С 8.3.26 запоминание входа при OpenID само не включается: появились параметры «Разрешить сохранение аутентификации» и «Сохранять аутентификацию по умолчанию», оба по умолчанию выключены и считываются из настроек сервера OpenID.
23. Чтобы вернуть запоминание входа — включить оба параметра вручную в Конфигураторе (Дополнительные настройки аутентификации) либо выполнить внешнюю обработку `SetSavePassByDefaultInAdditionalAuthSettings.epf` (каталог `\1CITS\EXE\OpenID_settings`).
24. Пример запуска обработки из командной строки: `1cv8 enterprise /Lru /F<infobase> /DisableStartupMessages /Execute SetSavePassByDefaultInAdditionalAuthSettings.epf`.

## 1. Пример настройки Kerberos-аутентификации для Linux-версии сервера 1С:Предприятия 8

- **Дата публикации:** 18.02.2015
- **Ссылка:** https://its.1c.ru/db/metod8dev/content/2799/hdoc
- **Область действия по статье:** версии 1С:Предприятия начиная с 8.1.12 и 8.2.8
- **Оценка применимости на октябрь 2026:** частично устарело

### 1.1. Оценка применимости (суждение конспекта, в статье его нет)

Что устарело:

- **Возраст примера.** Опубликовано 18.02.2015, но сам пример заметно старше: в листингах даты 2008 года (`06/04/08`), сервер на Fedora 6, каталог установки `i386`, платформа 8.1 (8.2 — «по аналогии»), в выводе `klist` присутствует кэш тикетов Kerberos 4.
- **Платформа 8.3 в статье не упоминается.** Имена пользователя и группы (`usr1cv81`/`grp1cv81`, `usr1cv82`/`grp1cv82`), каталог `/opt/1C/v8.1/i386`, а вместе с ними первая часть имени службы и имя keytab-файла относятся к 8.1/8.2. Значений для 8.3 в источнике нет — их нужно брать из действующей документации платформы.
- **Алгоритмы шифрования.** Рассмотрены только RC4-HMAC и DES (`DES-CBC-CRC`, `des-cbc-md5`). На 2026 год оба относятся к устаревшим; вариант с AES статья не описывает. Значения `default_tkt_enctypes` / `default_tgs_enctypes` из примера соответствуют именно этим старым алгоритмам.
- **Инструменты окружения.** `ktpass` из Windows Support Tools с установочного диска, `ntpdate`, ручная правка `/etc/resolv.conf` — приёмы старых систем. Статья сама оговаривает, что настройка DNS зависит от дистрибутива. Как выполнять эти действия на современной Ubuntu, в источнике не описано.

Что остаётся верным (принципы):

- порядок работ: DNS → время → `krb5.conf` → проверка `kinit` паролем → keytab → проверка `kinit` по keytab;
- устройство имени службы: первая часть — локальный пользователь, под которым работает сервер 1С, вторая — имя сервера с доменом, затем область (realm) в верхнем регистре;
- различие между именем службы и доменной учётной записью, к которой оно привязано;
- требования к keytab-файлу: владелец — пользователь сервера 1С, права `600`;
- приёмы проверки утилитами `kinit` / `klist` / `kdestroy`;
- перезапуск сервера 1С нужен только при смене расположения keytab-файла.

### 1.4. Настройка контроллера домена

**Шаг 1. DNS.** Все Linux-компьютеры регистрируются в DNS-сервере домена вручную. Windows-компьютеры регистрируются автоматически при включении в домен. В примере вручную заводится центральный сервер кластера 1С (на нём Linux-версия сервера), а рабочая станция просто включается в домен.

**Шаг 2. Учётная запись.** Создаётся доменный пользователь, с которым будут связаны запросы авторизации к серверу 1С. В примере — `usr1cv8` с паролем `pass1cv8`. В свойствах учётной записи:

- флажок «Use DES encryption types with this account» — **снять**;
- если используемая реализация Kerberos не поддерживает RC4-HMAC — флажок **обязательно установить**.

**Шаг 3. Файл с секретным ключом (keytab).** Для пользователя `usr1cv8` файл генерируется утилитой `ktpass`. По статье она входит в пакет Windows Support Tools (подкаталог `SUPPORT` установочного диска Windows).

Основной вариант (RC4-HMAC поддерживается):

```bat
ktpass -princ usr1cv81/srv1c.krb.local@KRB.LOCAL -mapuser usr1cv8 -pass pass1cv8 -out usr1cv81.keytab
```

Вариант, когда RC4-HMAC не поддерживается (исправлено по смыслу: в источнике команда разорвана вёрсткой на две строки, здесь записана одной):

```bat
ktpass -crypto DES-CBC-CRC -princ usr1cv81/srv1c.krb.local@KRB.LOCAL -mapuser usr1cv8 -pass pass1cv8 -out usr1cv81.keytab
```

Параметры:

| Параметр | Значение в примере | Смысл |
|---|---|---|
| `-princ` | `usr1cv81/srv1c.krb.local@KRB.LOCAL` | стандартное имя службы; первая часть — имя **локального** пользователя, от которого на центральном сервере кластера запускается сервер 1С (`usr1cv81`) |
| `-mapuser` | `usr1cv8` | **доменный** пользователь, созданный на шаге 2 |
| `-pass` | `pass1cv8` | пароль доменной учётной записи `usr1cv8` |
| `-out` | `usr1cv81.keytab` | имя создаваемого файла с ключом |
| `-crypto` | `DES-CBC-CRC` | указывается только в варианте без RC4-HMAC |

Результат: в текущем каталоге (в примере — корень диска `C:`) появляется `usr1cv81.keytab`, а с пользователем `usr1cv8` связывается имя участника службы `usr1cv81/srv1c.krb.local`.

Предупреждение автора: `usr1cv81` и `usr1cv8` — разные сущности. Первое входит в имя службы и совпадает с локальным Linux-пользователем сервера 1С, второе — учётная запись в домене.

### 1.5. Настройка центрального сервера кластера 1С

Нумерация шагов ниже введена в конспекте; в статье это сплошной текст.

**Шаг 1. DNS-клиент.** DNS-сервером для сервера 1С должен быть DNS контроллера домена. Способ настройки зависит от дистрибутива Linux; в примере вручную правится `/etc/resolv.conf`:

```
srv1c:~# cat /etc/resolv.conf
nameserver 192.168.29.150
search krb.local
```

Проверка DNS командой `ping` (короткое имя `main` должно разрешиться в `main.krb.local`):

```
srv1c:~# ping main -c 1
PING main.krb.local (192.168.29.150) 56(84) bytes of data.
64 bytes from 192.168.29.150: icmp_seq=1 ttl=128 time=0.177 ms

--- main.krb.local ping statistics ---
1 packets transmitted, 1 received, 0% packet loss, time 0ms
rtt min/avg/max/mdev = 0.177/0.177/0.177/0.000 ms
```

**Шаг 2. Синхронизация времени.** У компьютеров, участвующих в аутентификации, часы не должны сильно расходиться: аутентификационные пакеты (тикеты) действуют ограниченное время. Время сервера 1С синхронизируется с контроллером домена, в примере — командой `ntpdate`:

```
srv1c:~# ntpdate main
4 Jun 11:51:53 ntpdate[2527]: step time server 192.168.29.150 offset -56.766439 sec
```

**Шаг 3. Файл `/etc/krb5.conf`.** По статье, для него нужно NETBIOS-имя контроллера домена, которое обычно совпадает с именем домена в верхнем регистре; в примере это `KRB.LOCAL`. Итоговое содержимое файла:

```ini
[logging]
default = FILE:/var/log/krb5libs.log
kdc = FILE:/var/log/krb5kdc.log
admin_server = FILE:/var/log/kadmind.log

[libdefaults]
default_realm = KRB.LOCAL
dns_lookup_realm = false
dns_lookup_kdc = false
default_tkt_enctypes = rc4-hmac
default_tgs_enctypes = rc4-hmac

[realms]
KRB.LOCAL = {
    kdc = main.krb.local:88
    default_domain = krb.local
}

[domain_realm]
krb.local = KRB.LOCAL
.krb.local = KRB.LOCAL
KRB.LOCAL = KRB.LOCAL
.KRB.LOCAL = KRB.LOCAL

[kdc]
profile = /var/kerberos/krb5kdc/kdc.conf

[appdefaults]
pam = {
    debug = true
    ticket_lifetime = 36000
    renew_lifetime = 36000
    forwardable = false
    krb4_convert = false
}
```

Если RC4-HMAC не поддерживается, два параметра в секции `[libdefaults]` принимают такие значения (остальное без изменений):

```ini
default_tkt_enctypes = des-cbc-crc des-cbc-md5
default_tgs_enctypes = des-cbc-crc des-cbc-md5
```

**Шаг 4. Проверка аутентификации паролем.** Выполняется `kinit <имя>`, где имя — любой пользователь, зарегистрированный в домене `krb.local` (в примере `user`). После ввода пароля программа не должна выводить никаких сообщений — это признак успеха. Командой `klist` убеждаемся, что от KDC (Key Distribution Center, центр распределения ключей; эту роль выполняет контроллер домена) получен ticket-granting ticket. Затем `kdestroy` очищает локальный кэш тикетов, возвращая систему в исходное состояние.

```
srv1c:~# kinit user
Password for user@KRB.LOCAL:
srv1c:~# klist
Ticket cache: FILE:/tmp/krb5cc_0
Default principal: user@KRB.LOCAL

Valid starting     Expires            Service principal
06/04/08 11:29:21  06/04/08 21:28:28  krbtgt/KRB.LOCAL@KRB.LOCAL
        renew until 06/05/08 11:29:21

Kerberos 4 ticket cache: /tmp/tkt0
klist: You have no tickets cached
srv1c:~# kdestroy
```

**Шаг 5. Размещение keytab-файла.** Файл `usr1cv81.keytab`, полученный на контроллере домена, любым способом передаётся на сервер 1С и копируется в каталог установки сервера 1С (по умолчанию `/opt/1C/v8.1/i386`). Владелец и права:

```
srv1c:~# cd /opt/1C/v8.1/i386
srv1c:i386# chown usr1cv81:grp1cv81 usr1cv81.keytab
srv1c:i386# chmod 600 usr1cv81.keytab
```

Файл можно держать и в другом месте; тогда нужно изменить переменную `SRV1CV8_KEYTAB` в конфигурационном файле, чтобы она указывала на новое расположение.

⚠ в источнике неясно: какой именно конфигурационный файл содержит переменную `SRV1CV8_KEYTAB` — путь и имя файла в статье не названы.

**Шаг 6. Проверка содержимого keytab-файла.**

```
srv1c:~# klist -e -k -t /opt/1C/v8.1/i386/usr1cv81.keytab
```

Ожидаемый вывод при RC4-HMAC:

```
Keytab name: FILE:/opt/1C/v8.1/i386/usr1cv81.keytab
KVNO Principal
---- ---------------------------------------------------------------------
  13 usr1cv81/srv1c.krb.local@KRB.LOCAL (ArcFour with HMAC/md5)
```

Ожидаемый вывод, если RC4-HMAC не поддерживается:

```
Keytab name: FILE:/opt/1C/v8.1/i386/usr1cv81.keytab
KVNO Principal
---- ---------------------------------------------------------------------
  13 usr1cv81/srv1c.krb.local@KRB.LOCAL (DES cbc mode with RSA-MD5)
```

На что смотреть: в колонке `Principal` стоит ровно то имя службы, которое задавали в `ktpass` (шаг 3 настройки контроллера домена), и алгоритм шифрования правильный — `ArcFour with HMAC/md5` для RC4-HMAC либо `DES cbc mode with RSA-MD5` для DES.

**Шаг 7. Проверка Kerberos без пароля, по секретному ключу.** Команде `kinit` указывается файл с ключом и имя службы, ключ которой нужно прочитать. Команда должна завершиться молча, не спросить пароль и вернуть управление в командную строку:

```
srv1c:~# kinit -k -t /opt/1C/v8.1/i386/usr1cv81.keytab usr1cv81/srv1c.krb.local@KRB.LOCAL
```

Результат при успехе:

```
srv1c:~# klist
Ticket cache: FILE:/tmp/krb5cc_0
Default principal: usr1cv81/srv1c.krb.local@KRB.LOCAL

Valid starting     Expires            Service principal
06/04/08 11:44:54  06/04/08 21:43:58  krbtgt/KRB.LOCAL@KRB.LOCAL
        renew until 06/05/08 11:44:54

Kerberos 4 ticket cache: /tmp/tkt0
klist: You have no tickets cached
```

Результат, если что-то настроено неверно:

```
srv1c:~# klist
klist: No credentials cache found (ticket cache FILE:/tmp/krb5cc_1000)
Kerberos 4 ticket cache: /tmp/tkt1000

klist: You have no tickets cached
```

**Шаг 8. Итог.** Если проверка прошла, сервер кластера 1С с этого момента способен обрабатывать запросы на аутентификацию. Перезапускать сервер не требуется. Исключение — если в конфигурационном файле меняли расположение файла с секретным ключом.

### 1.6. Чек-лист по статье

На контроллере домена:

- [ ] Linux-сервер 1С вручную зарегистрирован в DNS домена; рабочая станция включена в домен.
- [ ] Создан доменный пользователь для сервера 1С (в примере `usr1cv8`).
- [ ] Флажок «Use DES encryption types with this account» снят (или установлен — если RC4-HMAC на Linux не поддерживается).
- [ ] `ktpass` выполнен; имя службы начинается с имени локального пользователя сервера 1С; получен keytab-файл.

На сервере 1С:

- [ ] `/etc/resolv.conf`: `nameserver` — адрес контроллера домена, `search` — домен; `ping` по короткому имени контроллера проходит.
- [ ] Время синхронизировано с контроллером домена.
- [ ] `/etc/krb5.conf` заполнен: область (realm), KDC, соответствия `[domain_realm]`, типы шифрования под выбранный алгоритм.
- [ ] `kinit <доменный пользователь>` отработал без сообщений, `klist` показывает `krbtgt/...`, кэш очищен `kdestroy`.
- [ ] keytab-файл лежит в каталоге сервера 1С (или путь задан в `SRV1CV8_KEYTAB`), владелец `usr1cv81:grp1cv81`, права `600`.
- [ ] `klist -e -k -t <keytab>` показывает нужное имя службы и нужный алгоритм.
- [ ] `kinit -k -t <keytab> <имя службы>` отработал без запроса пароля, `klist` показывает тикет для имени службы.
- [ ] Сервер 1С перезапущен только в том случае, если менялось расположение keytab-файла.

### 1.7. Чего в статье нет

- Настройки рабочей станции: в перечне стенда она названа, но отдельного раздела о ней нет (сказано только, что её включают в домен).
- Настройки пользователей информационной базы и проверки входа из клиента 1С.
- Платформы 8.3, 64-разрядных каталогов установки, алгоритма AES, дистрибутива Ubuntu.
- Имени конфигурационного файла с переменной `SRV1CV8_KEYTAB`.

## 2. Вопросы настройки OpenID-аутентификации

- **Дата публикации:** 24.08.2018
- **Ссылка:** https://its.1c.ru/db/metod8dev/content/5872/hdoc
- **Оценка применимости на октябрь 2026:** актуально (ветки для версий ниже 8.3.8 — исторические)

### 2.1. Оценка применимости (суждение конспекта, в статье его нет)

- Статья 2018 года, но описывает не установку конкретных версий, а устройство связки «клиент — провайдер» и методику поиска ошибок. Эта часть от версии ОС и СУБД не зависит и применима как есть.
- Устарели по факту только ветки для платформы ниже 8.3.8 и для режима совместимости с 8.3.7 (файл `cacert.pem`): на актуальных версиях действует правило «цепочка сертификатов — в хранилище доверенных корневых сертификатов ОС».
- Статью нужно читать вместе с разделом 3 этого конспекта: начиная с 8.3.26 запоминание входа при OpenID по умолчанию выключено.
- Модули расширения веб-сервера названы в Windows-варианте (`wsisapi.dll`, `wsapXX.dll`). Linux-специфика (имена модулей, расположение хранилища сертификатов ОС) в источнике не раскрыта.
- Статья рассматривает только стандарт OpenID v2.
- Гиперссылки «здесь» (на подробную инструкцию по настройке, на описание `cacert.pem`, на `inetcfg.xml`) в локальной копии статьи не сохранились.

### 2.2. Стандарт и термины

Платформа «1С:Предприятие 8» поддерживает стандарт аутентификации OpenID v2. Ссылки из статьи: обзор на сайте платформы — http://v8.1c.ru/overview/Term_000000799.htm; текст стандарта (англ.) — http://openid.net/specs/openid-authentication-2_0.html; терминология стандарта — http://openid.net/specs/openid-authentication-2_0.html#terminology.

| Термин | Значение |
|---|---|
| OP | OpenID Provider — провайдер OpenID |
| RP | Relying Party — клиент OpenID; в 1С это веб-расширение платформы |
| Публикация | каталог веб-сервера, все обращения к которому обрабатывает расширение (`wsisapi.dll` или `wsapXX.dll`) и в который добавлен файл `default.vrd` |

Обозначения, принятые в примерах статьи:

- `OP_NAME` — имя сервера с публикацией OP;
- `OP_IB_PUB` — путь к публикации OP;
- везде подразумевается стандартный порт HTTPS; при нестандартном порте его нужно указывать явно.

### 2.3. Настройка OpenID (краткая схема из статьи)

Подробная инструкция по настройке веб-серверов и OpenID находится в документации (⚠ в источнике неясно: ссылка «здесь» в локальной копии потеряна).

**1. Клиент (RP).** В `default.vrd` публикации клиента указывается URL информационной базы, выступающей провайдером:

```xml
<openid>
	<rely url="https://myserver.org/users-ib/e1cib/oid2op"/>
</openid>
```

- `users-ib` — каталог веб-сервера с публикацией OP.
- Если открыть этот адрес в браузере, вернётся XRDS-файл с именем `oid2op`, в котором записаны настройки провайдера OpenID.
- **Предупреждение автора:** протокол, имя сервера и порт в этом адресе должны совпадать с теми, что используются для обращения к OP во всех остальных местах.

⚠ в источнике неясно: в тексте пропало имя элемента `default.vrd`, внутри которого размещается этот фрагмент (фраза «элемент должен содержать» без имени элемента).

**2. Провайдер (OP).** В `default.vrd` публикации провайдера должен присутствовать фрагмент:

```xml
<openid>
	<provider>
		<lifetime>432000</lifetime>
	</provider>
</openid>
```

- `lifetime` — время жизни признака аутентифицированности идентификатора, в секундах. Автор отмечает, что для рассматриваемых задач конкретное значение не важно.

⚠ в источнике неясно: и здесь пропало имя объемлющего элемента («внутри элемента должен присутствовать следующий текст»).

**3. Сертификаты.** Цепочка сертификатов, которыми подписан сертификат веб-сервера с публикацией OP, должна быть известна стороне RP:

| Версия платформы | Куда добавлять цепочку |
|---|---|
| ниже 8.3.8 | в файл `cacert.pem` |
| 8.3.8 и выше | в хранилище доверенных корневых сертификатов ОС |
| режим совместимости с 8.3.7 | хранилищем сертификатов служит `cacert.pem` (отдельно выделено автором как важное) |

Самый простой способ пополнить `cacert.pem`: сохранить сертификат из браузера в формате X.509 Base64-encoded и дописать содержимое полученного файла в `cacert.pem`. Как экспортировать сертификат — в документации браузера или ОС.

**Результат настройки.** Если у пользователя включена OpenID-аутентификация, то при попытке входа в базу RP обращается к публикации OP и вход выполняется через OpenID.

### 2.4. Поиск проблемы

**Типичное проявление.** После настройки по инструкции пользователь видит не окно аутентификации OpenID, а окно аутентификации локальной информационной базы. Как их отличить:

- тонкий клиент: окна похожи; в окне локальной аутентификации имя пользователя выбирается из списка (combobox), в окне OpenID — обычное поле ввода;
- веб-клиент: смотреть адресную строку браузера — при исправном OpenID там адрес и путь публикации OP, а не публикации клиентской базы (RP).

Перечисленные ниже проверки — не строгая последовательность. Это набор действий, которые в комплексе помогают найти причину.

#### 2.4.1. Включить логирование на клиенте OpenID

В `logcfg.xml` добавляются два фрагмента (статья приводит только их; об остальных настройках технологического журнала — в документации).

Внутри элемента `<config>`:

```xml
<system level="trace" class="OID2Log"/>
```

Внутри элемента `<log>`:

```xml
<event>
	<eq property="name" value="SYSTEM"/>
</event>
```

Далее: запустить клиента, дождаться окна аутентификации, изучить созданные логи. Фильтровать события по `class=OID2Log`.

Частая запись — клиент OpenID не может соединиться с сервером:

```
 .... OP discovery error /openID/e1cib/oid2op
```

Она означает одно из двух:

- а) с клиента недоступна публикация OP по HTTPS → проверка сетевой доступности (2.4.2, 2.4.3);
- б) цепочка сертификатов, которой подписан HTTPS-сертификат сайта с провайдером, не прошла проверку → проверка сертификата OP (2.4.4).

#### 2.4.2. Доступность сервера по сети

```
telnet OP_NAME https
```

Если сервер доступен, соединение устанавливается. При ошибке — обращаться к сетевым администраторам.

#### 2.4.3. Тестирование в браузере

С машины, на которой опубликован клиент OpenID, открыть в браузере адрес провайдера:

```
https://OP_NAME/OP_IB_PUB/e1cib/oid2op
```

- Должен скачаться файл `oid2op` с настройками провайдера. (В этом месте статьи файл назван XRDP, в разделе о настройке — XRDS; речь об одном и том же файле, вероятно опечатка.)
- Адрес для проверки лучше не набирать руками, а скопировать из `default.vrd` публикации RP.
- Файл не скачивается → проверять сетевую доступность сервера OP.
- Браузер предупреждает о неверном сертификате веб-сервера → переходить к проверке сертификата.

#### 2.4.4. Проверка сертификата OP

Клиент должен признавать сертификат OP прошедшим валидацию. Это означает одновременно:

- обращение идёт по адресу, на который выдан сертификат (`https://OP_NAME`), а не по алиасу хоста вроде `https://localhost`;
- цепочка сертификатов, которой подписан сертификат публикации OP, проверена.

Как проверить: с компьютера с RP открыть публикацию OP по HTTPS в браузере и посмотреть используемый сертификат; если браузеров несколько — попробовать разные. По адресу

```
https://OP_NAME/OP_IB_PUB
```

должно открываться окно локального входа в информационную базу OP. Современные браузеры цветом показывают состояние проверки сертификата и по щелчку на информационной иконке дают сведения о сертификатах соединения.

**Предупреждение автора:** для платформы младше 8.3.8 успешная проверка сертификата в браузере не гарантирует, что он пройдёт проверку в клиенте 1С. Нужно отдельно убедиться, что необходимые сертификаты есть в `cacert.pem`.

#### 2.4.5. Проверка использования прокси

- Проверить общие для ОС настройки прокси и файл `inetcfg.xml` платформы.
- Если проверки из этого раздела проходят в браузере, а клиент 1С всё равно не работает — убедиться, что конфигурация прокси у браузера и у клиента 1С не различается.
- По возможности на время проверки убрать все прокси. Если нельзя — убедиться, что прокси не изменяют HTTPS-трафик, расшифровывая его.

Дешифрующий прокси:

- в браузере цепочка сертификатов выглядит иначе: вместо сертификата, подписывающего сертификат сайта с публикацией OP, обычно стоит сертификат прокси;
- в доверенные нужно добавлять именно эту цепочку удостоверяющих сертификатов;
- клиенты, идущие через разные цепочки дешифрующих прокси (или вовсе без них), видят разные цепочки.

Общее правило: на каждом конкретном клиенте сертификат сервера должен быть доверенным с учётом той цепочки, какой она видна с этого клиента. При дешифрующем прокси доверенным делают сертификат этого прокси — защищённое соединение клиент устанавливает именно с ним.

#### 2.4.6. Проверка допустимых адресов возврата (`returnto`)

Начиная с 8.3.8 в публикацию OpenID-провайдера добавлен элемент `returnto` — защита от перенаправлений на потенциально опасные сайты.

- Элемент необязательный: может отсутствовать или встречаться несколько раз.
- Содержимое — регулярное выражение, задающее маску разрешённых имён хоста, на который браузер пользователя возвращается (редирект) после исполнения команды openid. Подробности — в документации.
- По умолчанию, из соображений безопасности, элементов `returnto` в публикации нет.

Пример:

```xml
    <openid>
        <provider>
            <lifetime>604800</lifetime>
            <returnto>mysite\.com</returnto>
            <returnto>.*\.1c\.ru</returnto>
        </provider>
    </openid>
```

⚠ в источнике неясно: как именно ведёт себя провайдер при отсутствии элементов `returnto` и как выглядит ошибка при несовпадении маски — статья не поясняет и отсылает к документации.

#### 2.4.7. Соответствие полного имени пользователя и URL провайдера

Для безопасности проверяется, что полное имя пользователя, выданное OP, соответствует URL сервера OP, который его выдал. Сравниваются **протокол, имя сервера и порт**, указанные в публикации (vrd).

- Параметр `openid.identity` передаётся в форме ответа OP к RP на адрес `/e1cib/oid2rp`.
- Перехватить ответы можно прокси-инструментом, например fiddler.
- При несовпадении в технологическом журнале фиксируется ошибка вида:

```
 39:50.223007-0,EXCP,... Rely Party: id_res invalid local id'
```

Пример **некорректной** настройки — не совпадает порт (в одном адресе он указан явно, в другом нет):

```
 identity: https://server.ru:443/openid/e1cib/oid2op?lid=%D0...
 op url:   https://server.ru/openid/
```

### 2.5. Советы для локализации проблемы

- Развернуть провайдера и клиента на одной машине: две публикации на одном и том же сервере.
- Установить клиент 1С на другой компьютер и повторить на нём все проверки; желательно из другой подсети или извне, через интернет.
- Попробовать подключиться к базе и тонким клиентом, и веб-клиентом.

### 2.6. Известные особенности работы

- В один файл `default.vrd` нельзя добавить и клиента, и провайдера. Можно сделать раздельные публикации для клиента и для провайдера, работающие с одной информационной базой.
- Если при аутентификации имя пользователя и пароль передаются явно, вход выполняется локальной аутентификацией базы, без попыток обращения к OP — даже при включённой OpenID-аутентификации. То же самое происходит, если у пользователя включена аутентификация средствами ОС.
- Если до аутентификации открыть публикацию RP сразу в нескольких вкладках браузера, часть последующих вкладок вместо редиректа на публикацию OP покажет пустую страницу.

### 2.7. Что приложить при обращении в поддержку

- версию платформы «1С:Предприятие»;
- тип используемого веб-сервера;
- описание сценария: как именно «не работает» и какой клиент использовался (тонкий, веб);
- файлы из каталогов с публикациями OP и RP;
- файл `inetcfg.xml`, если он есть среди конфигурационных файлов на стороне RP (в источнике в этом месте написано `inetcft.xml` — вероятно, опечатка);
- для платформы ниже 8.3.8: файл `cacert.pem` из каталога платформы, на которой работает RP, и сертификат (HTTPS) веб-сервера OP.

**Предупреждение автора:** в конфигурациях и логах могут быть персональные данные. Перед отправкой нужно оценить, допустимо ли их передавать.

### 2.8. Сводка: признак → причина → проверка

| Признак | Причина по статье | Что проверять |
|---|---|---|
| Вместо окна OpenID — окно локальной аутентификации базы | ошибка в конфигурации OpenID (общий симптом) | все проверки 2.4.1–2.4.7 |
| В ТЖ `OP discovery error …/e1cib/oid2op` | OP недоступен с клиента по HTTPS либо цепочка сертификатов не прошла проверку | 2.4.2, 2.4.3, 2.4.4 |
| Браузер не скачивает `oid2op` | нет сетевой доступности сервера OP | 2.4.2 |
| Браузер предупреждает о сертификате | обращение не по имени из сертификата либо цепочка не доверенная | 2.4.4 |
| В браузере всё работает, в клиенте 1С — нет | разные настройки прокси у браузера и клиента 1С; для платформы ниже 8.3.8 — нет сертификатов в `cacert.pem` | 2.4.5, 2.4.4 |
| В ТЖ `Rely Party: id_res invalid local id` | не совпадают протокол, имя сервера или порт в `openid.identity` и в URL OP | 2.4.7 |
| Пустая страница в части вкладок браузера | известная особенность первичного открытия RP в нескольких вкладках | 2.6 |
| Вход выполняется локально, OP не опрашивается | имя и пароль переданы явно либо у пользователя включена аутентификация ОС | 2.6 |

## 3. Изменение настроек сохранения аутентификации (1С:Предприятие 8.3.26 и выше)

- **Дата публикации:** 14.01.2026
- **Ссылка:** https://its.1c.ru/db/metod8dev/content/6029/hdoc
- **Область действия по статье:** платформа 1С:Предприятие 8.3.26 и выше
- **Оценка применимости на октябрь 2026:** актуально

### 3.1. Оценка применимости (суждение конспекта, в статье его нет)

Статья свежая (январь 2026) и описывает поведение действующих версий платформы — 8.3.26 и новее. Устаревших элементов нет. От ОС сервера и СУБД рекомендации не зависят: настройка выполняется средствами платформы. Ограничения самого источника перечислены в разделе 3.6.

### 3.2. Что изменилось

| | До 8.3.26 | Начиная с 8.3.26 |
|---|---|---|
| Запоминание входа при OpenID | вход запоминался автоматически; флаг «Не запоминать меня» был выключен | управляется двумя новыми параметрами |
| Параметры | — | «Разрешить сохранение аутентификации», «Сохранять аутентификацию по умолчанию» |
| Значения по умолчанию | — | оба параметра выключены |
| Откуда берутся значения | — | считываются из настроек сервера OpenID |

Практическое следствие: после обновления платформы до 8.3.26 пользователи, входящие через OpenID, перестают «запоминаться», пока администратор явно не включит новые параметры.

### 3.3. Способ 1 — вручную через Конфигуратор

В Конфигураторе открыть «Дополнительные настройки аутентификации» и включить оба параметра:

- «Разрешить сохранение аутентификации»;
- «Сохранять аутентификацию по умолчанию».

### 3.4. Способ 2 — программно

Настройки изменяются таким кодом встроенного языка:

```bsl
  НастройкиАвтоматическогоСохраненияПараметровАутентификации =
        ДополнительныеНастройкиАутентификации.ПолучитьНастройкиАвтоматическогоСохраненияАутентификации();
  НастройкиАвтоматическогоСохраненияПараметровАутентификации.РазрешитьСохранение = Истина;
  НастройкиАвтоматическогоСохраненияПараметровАутентификации.СохранятьПоУмолчанию = Истина;
  ДополнительныеНастройкиАутентификации.УстановитьНастройкиАвтоматическогоСохраненияАутентификации(НастройкиАвтоматическогоСохраненияПараметровАутентификации);
```

Соответствие свойств и флажков:

| Свойство в коде | Флажок в интерфейсе |
|---|---|
| `РазрешитьСохранение` | «Разрешить сохранение аутентификации» |
| `СохранятьПоУмолчанию` | «Сохранять аутентификацию по умолчанию» |

### 3.5. Способ 3 — готовая внешняя обработка

Внешняя обработка `SetSavePassByDefaultInAdditionalAuthSettings` автоматически устанавливает оба флажка. Они учитываются при аутентификации через сервер OpenID начиная с платформы 8.3.26.ХХХХ (номер сборки в статье не уточнён).

- Файл: `SetSavePassByDefaultInAdditionalAuthSettings.epf`
- Где лежит: каталог `\1CITS\EXE\OpenID_settings`

Пример запуска из командной строки:

```
1cv8 enterprise /Lru /F<infobase> /DisableStartupMessages /Execute SetSavePassByDefaultInAdditionalAuthSettings.epf
```

Расшифровки ключей командной строки в статье нет — приведена только эта строка; `<infobase>` в ней — место для подстановки своей информационной базы.

### 3.6. Ограничения источника

- ⚠ в источнике неясно: прямо не сказано, в какой информационной базе нужно менять настройки. Указано лишь, что параметры считываются из настроек сервера OpenID; по смыслу это база, выступающая сервером (провайдером) OpenID.
- ⚠ в источнике неясно: пример запуска дан только с ключом `/F<infobase>` (так в источнике); вариант строки запуска для клиент-серверной базы не приведён.
- ⚠ в источнике неясно: каталог `\1CITS\EXE\OpenID_settings` записан в Windows-нотации, без указания, относительно чего он отсчитывается (диск или раздел ИТС).
- Статья не описывает, где именно в Конфигураторе находится пункт «Дополнительные настройки аутентификации», и не содержит снимков экрана.
- Статья короткая: кроме перечисленного выше, другого содержания в ней нет.
