## Кратко: главные официальные рекомендации

Тема состоит из одной статьи-справочника: для каждого типового сценария проблемы дан список того, что нужно собрать, чтобы расследовать её самому или передать в поддержку.

1. Сначала определить сценарий (аварийное завершение, деградация у части или у всех пользователей, блокировки, нагрузка на диск или процессор, рост базы, утечка памяти и т. д.) и собирать данные по списку именно этого сценария, а не «всё подряд».
2. Почти в каждом сценарии первым пунктом идёт «Информация для технической поддержки» из окна «О программе»; если есть возможность сохранить отчёт об ошибке (платформа 8.3.17 и новее) — приложить и его.
3. Почти везде требуются копия файла реестра кластера `1CV8Clst.lst` и файл конфигурации (cf) вместе со всеми расширениями; для проблем обновления — и исходный cf, и тот, на который обновлялись.
4. Технологический журнал (ТЖ) собирают со всех серверов кластера 1С, в котором зарегистрирована база; набор событий зависит от сценария (сводная таблица — раздел 1.4).
5. Примеры `logcfg.xml` в статье написаны для Windows и MS SQL Server (событие `DBMSSQL`); в перечнях событий для других СУБД названы `DBPOSTGRS`, `DBORACLE`, `DB2`.
6. Там, где проблема проявляется на рабочем месте, нужен полный клиентский ТЖ: все события и все свойства (шаблон К).
7. Аварийное завершение процессов кластера или клиента: в `logcfg.xml` должен быть элемент `<dump create="true" ... type="3" .../>`; иногда дополнительно нужен Windows Error Reporting.
8. Деградация у отдельных пользователей: серверный ТЖ с отбором вызовов по имени пользователя (`Usr`), счётчики оборудования с клиента, серверов 1С и СУБД, результат `ПолучитьСтруктуруХраненияБазыДанных()`.
9. Деградация у всех пользователей: ТЖ с событиями `EXCP, PROC, ADMIN, CONN, SESN, CLSTR, SRVC, ATTN, CALL, SCALL` (контекст для `CALL`/`SCALL` не собирается), а в момент зависания — серия дампов всех процессов кластера (`rmngr`, `rphost`, `ragent`).
10. Взаимоблокировки и таймауты на управляемых блокировках 1С: `EXCP, TLOCK` плюс `TDEADLOCK` или `TTIMEOUT` соответственно.
11. Взаимоблокировки в СУБД: `EXCP, EXCPCNTX, SDBL` и событие запросов к СУБД, в примере — с элементом `<dbmslocks/>`. Для PostgreSQL достаточно лога из каталога `pg_log` (в Linux по умолчанию `$PGDATA/pg_log`).
12. Таймауты в СУБД (ошибка «Конфликт блокировок при выполнении транзакции»): `EXCP, EXCPCNTX, SDBL` и событие запросов к СУБД, счётчики оборудования, cf.
13. Конкретный медленный запрос: `EXCP, SDBL` и событие запросов к СУБД с элементами `<plansql/>` и `<dbmslocks/>`, счётчики сервера СУБД, текст запроса.
14. Проблемы с запросами в PostgreSQL: версия СУБД, сам запрос и резервная копия базы — `pg_dump ... -Fp`, проверенная разворачиванием через `psql ... -1 -f файл -v ON_ERROR_STOP=1`.
15. Рост базы на PostgreSQL: выполнить запрос размеров таблиц (раздел 1.8) и сопоставить таблицы с объектами метаданных через `ПолучитьСтруктуруХраненияБазыДанных()`; с платформы 8.3.15 доступен `ПолучитьРазмерДанныхБазыДанных()`.
16. Сеансовые данные лежат в каталоге `…\srvinfo\reg_<номер порта>\snccntx<GUID>`: следить за свободным местом на этом диске и не размещать на нём технологический журнал — исчерпание места может сказаться на стабильности системы.
17. Реструктуризация (долгая или с ошибками): сначала выяснить версию механизма (1 или 2). Версия 1 — события `EXCP` (при ошибках ещё `EXCPCNTX`) и запросы к СУБД; версия 2 — отбор по `EventType` (`Workflow`, `Analysis`, `Restructuring`) и системные события только компоненты `dmf`.
18. Высокая загрузка процессора сервером 1С: `EXCP` и `CALL` с отбором `CpuTime > 0`, список сеансов в длительном вызове вне СУБД, копия журнала регистрации; если виновник не найден — дампы всех процессов кластера.
19. Высокая нагрузка на диск сервера 1С: `EXCP, CALL, SCALL` и счётчики оборудования серверов 1С и СУБД.
20. Утечка памяти рабочего процесса: `EXCP, PROC, ATTN, ADMIN, SESN, CLSTR, CALL, SCALL, LEAKS`, счётчики оборудования и полный дамп процесса с утечкой.
21. Лицензии 1С: `EXCP, PROC, ADMIN, CONN, SESN, CLSTR, SRVC, ATTN, LIC, HASP`. Система лицензирования конфигураций (СЛК): `EXCP, PROC, ADMIN, CONN, SCOM, SESN, CLSTR, SRVC, ATTN, CALL, SCALL`.
22. Ошибки в веб-клиенте: вывод консоли разработчика (F12), последний запрос с закладки Network, HAR-лог, серверный ТЖ.
23. Снижение производительности операций: приложить замеры из регистра сведений «ЗамерыВремени» (подсистема «Оценка производительности» БСП); для отдельной операции — её название или ссылку на конкретный объект.
24. Закрытие месяца в ERP: счётчики, реестр кластера, cf с расширениями и протокол из регистра сведений `ПротоколыРасчетаПартийИСебестоимости`.
25. Везде, где анализируются таблицы СУБД, соответствие имён таблиц объектам конфигурации получают отдельно методом `ПолучитьСтруктуруХраненияБазыДанных()`.

### 1.1. Оценка применимости на октябрь 2026

**Актуально** — с оговорками.

Почему актуально: статья 2022 года описывает не настройки под конкретные версии, а состав диагностических данных — какие события технологического журнала и какие сопутствующие артефакты нужны для каждого типа проблемы. Упоминаемые версии платформы заданы как нижняя граница («начиная с 8.3.17», «начиная с 8.3.15»), поэтому условия продолжают выполняться.

Оговорки (Примечание составителя):
- Все примеры `logcfg.xml` и пути даны для Windows (`D:\LOGS\...`, `C:\LOGS\...`, `C:\Program Files\1cv8\srvinfo\reg_1541\`), а событие запросов к СУБД в примерах — `DBMSSQL`. Готового примера для Linux и PostgreSQL в статье нет: для сервера на Ubuntu с PostgreSQL каталоги нужно подставлять свои, а из перечня событий в скобках брать `DBPOSTGRS`.
- Инструменты снятия дампов и трассировок названы только Windows-овские: ProcDump, Windows Error Reporting, RamMap, WPR, Fiddler, счётчики вида `Memory\Available Mbytes`. Их Linux-аналоги в статье не описаны — их следует брать из других материалов базы знаний, а не из этого конспекта.
- Разделы про MS SQL Server (отчёты SSMS, extended events, Profiler, «Top Transactions by Locks Count») к связке Linux + PostgreSQL неприменимы; оставлены в конспекте для полноты.
- Каталог логов PostgreSQL назван `pg_log` (`$PGDATA/pg_log`). Это имя каталога по умолчанию в старых версиях PostgreSQL (до 9.6 включительно); в актуальных версиях и в пакетных установках расположение лога может быть другим — реальное место нужно смотреть по параметрам журналирования конкретного экземпляра.
- Пример консоли браузера привязан к Google Chrome 88.0.4324.190 (2021 год) — расположение элементов в текущих версиях может отличаться.
- MS SQL Server 2008/2012 как граница выбора инструмента — устаревшая на 2026 год привязка.
- В текстовой копии не сохранились гиперссылки на смежные статьи (настройка WER, методики расследования, инструкция по HAR и др.) и рисунки; такие места помечены.

Раздел 1.9 (сеансовые данные), раздел 1.8 (запрос размеров таблиц PostgreSQL), раздел 1.25 (запросы в PostgreSQL) и пункт про лог PostgreSQL в разделе 1.14 применимы к Linux + PostgreSQL напрямую; остальное — после замены путей и имени события СУБД.

### 1.3. Общие элементы, повторяющиеся в сценариях

Чтобы не повторять одно и то же в каждом разделе, общие пункты и одинаковые примеры собраны здесь.

**Информация для технической поддержки.** Берётся в окне «О программе». Если платформа позволяет сохранить отчёт об ошибке (возможность есть начиная с версии 8.3.17), его тоже прикладывают. Этот пункт присутствует во всех сценариях, кроме аварийного завершения и нагрузки на процессор сервера MS SQL Server (там только отсылка к другой статье).

**Сценарий возникновения проблемы.** По возможности расспросить пользователей: что именно они делали, какая последовательность действий предшествовала ошибке, как её воспроизвести.

**Копия файла реестра кластера 1С `1CV8Clst.lst`.** Пример расположения из статьи (Windows): `C:\Program Files\1cv8\srvinfo\reg_1541\1CV8Clst.lst`. Linux-путь в статье не приводится.

**Файл конфигурации (cf) используемой базы** и, если есть, расширения. Для проблем реструктуризации — исходный cf и cf, на который обновлялись, плюс расширения.

**Счётчики загруженности оборудования.** В зависимости от сценария — с клиентской машины, со всех рабочих серверов кластера 1С, с сервера (серверов) СУБД. Конкретные счётчики названы только в сценарии роста сеансовых данных (раздел 1.9).

**Соответствие таблиц СУБД объектам конфигурации.** Результат метода встроенного языка `ПолучитьСтруктуруХраненияБазыДанных()`, сохранённый в файл.

**Технологический журнал.** Формулировка почти везде одна: ТЖ со всех серверов кластера 1С, в котором прописана база, с перечисленными событиями. В серверных примерах каталог журнала — `D:\LOGS\Tech_logs`, `history="24"`, свойства — `<property name="all"/>`.

#### Шаблон К — полный технологический журнал клиентской машины

Собираются все события со всеми свойствами. Используется в сценариях: деградация у отдельных пользователей, деградация у всех пользователей, открытие формы документа, ошибки в тонком клиенте, снижение производительности отдельной операции.

```xml
<?xml version="1.0" encoding="UTF-8"?>
<config xmlns="http://v8.1c.ru/v8/tech-log">
<log location="C:\LOGS\1cv8" history="4">
   <event>
      <ne property="Name" value=""/>
   </event>
   <property name="all"/>
</log>
</config>
```

#### Шаблон Д — только сбор дампов

Используется в сценариях аварийного завершения и внешних компонент.

```xml
<?xml version="1.0" encoding="UTF-8"?>
<config xmlns="http://v8.1c.ru/v8/tech-log">
<dump create="true" location="D:\LOGS\Dumps" type="3" prntscrn="false" externaldump="false"/>
</config>
```

#### Шаблон Р2 — технологический журнал реструктуризации версии 2 («новой»)

Собираются все события, у которых свойство `EventType` (тип события) равно `Workflow`, `Analysis` или `Restructuring`; системные события ограничены компонентой `dmf`. Используется в двух сценариях реструктуризации (разделы 1.10 и 1.17). В статье назван примером для Windows.

```xml
<?xml version="1.0"?>
<config xmlns="http://v8.1c.ru/v8/tech-log">
    <system level="trace"/>
    <log location="C:\LOGS\Restruct" history="96">
        <event>
            <eq property="EventType" value="Workflow"/>
        </event>
        <event>
            <eq property="EventType" value="Analysis"/>
        </event>
        <event>
            <eq property="EventType" value="Restructuring"/>
        </event>
        <event>
            <eq property="component" value="dmf"/>
        </event>
        <property name="all"/>
    </log>
</config>
```

#### Шаблон П — пакетный файл снятия дампов всех процессов кластера (Windows, ProcDump)

Запускается из каталога, где лежит `procdump.exe`. Для каждого найденного процесса `rmngr.exe`, `rphost.exe`, `ragent.exe` в фоне запускается `procdump.exe -ma <PID>` с именем файла вида `<процесс>_<PID>`. Используется при деградации у всех пользователей (серия дампов в момент зависания) и при высокой загрузке процессора сервером 1С.

```bat
@ echo off
echo Start dumping all rmngrs, rphosts and ragents on this server...
CD %~dp0
for /f "usebackq tokens=2" %%a in (`tasklist /FO list /FI "IMAGENAME eq rmngr.exe" ^| find /i "PID:"`) do (
start /b procdump.exe -ma %%a rmngr_%%a
)
for /f "usebackq tokens=2" %%a in (`tasklist /FO list /FI "IMAGENAME eq rphost.exe" ^| find /i "PID:"`) do (
start /b procdump.exe -ma %%a rphost_%%a
)
for /f "usebackq tokens=2" %%a in (`tasklist /FO list /FI "IMAGENAME eq ragent.exe" ^| find /i "PID:"`) do (
start /b procdump.exe -ma %%a ragent_%%a
)
pause
```

Примечание составителя: скрипт рассчитан только на Windows; способ снятия дампов процессов кластера в Linux в этой статье не описан.

### 1.5. Аварийное завершение процессов кластера или клиентского приложения

Чтобы при падении процесса кластера или клиентского приложения формировался дамп, в настройке технологического журнала должен присутствовать элемент:

```xml
<dump create="true" location="D:\LOGS\Dumps" type="3" prntscrn="false" externaldump="false"/>
```

- Дампы складываются в каталог, указанный в `location`.
- В части случаев этого недостаточно и дополнительно нужен Windows Error Reporting; порядок настройки сбора таких дампов описан в отдельной статье (ссылка не сохранилась).
- Полный пример файла настройки — шаблон Д (раздел 1.3): в нём нет элемента `<log>`, только `<dump>`.

⚠ в источнике неясно: в пояснении каталог дампов назван `D:\Log\DUMPS`, а в самом элементе указан `D:\LOGS\Dumps`. Фактически дампы пишутся туда, куда указывает атрибут `location`.

### 1.6. Деградация производительности операций у отдельных пользователей

Когда применять: часть пользователей жалуется на периодические «зависания» в ходе работы. Человек работает с теми же документами и справочниками, что и всегда, но в какой-то промежуток времени те же операции выполняются заметно дольше, причём это видно только у него или у нескольких пользователей, а не у всех.

Что собрать:

1. Сценарий возникновения: по возможности опросить пользователей и выяснить, какие действия предшествовали проблеме.

8. Сохранённый в файл результат `ПолучитьСтруктуруХраненияБазыДанных()` — для сопоставления таблиц СУБД с таблицами информационной базы.

### 1.8. Значительный рост информационной базы

Когда применять: база стала занимать значительный объём диска. Речь о размере базы в СУБД при клиент-серверной работе — не о сеансовых данных кластера и не о файловых базах. Задача — найти таблицы и конкретные объекты метаданных, занимающие основной объём.

Что собрать:

1. Информацию для технической поддержки и отчёт об ошибке.
2. Для MS SQL Server — размеры таблиц через стандартный отчёт SQL Server Management Studio «Использование дисковой памяти верхними таблицами».
3. Для PostgreSQL — вывод запроса, приведённого ниже. Выполнять можно в pgAdmin или psql.
4. Результат `ПолучитьСтруктуруХраненияБазыДанных()` (возвращает таблицу значений со структурой таблиц базы данных для всех объектов конфигурации) либо результат специальной обработки (ссылка не сохранилась). На платформе 8.3.15 и новее можно использовать метод глобального контекста `ПолучитьРазмерДанныхБазыДанных()`, перебирая объекты метаданных и получая их размер.

Запрос для PostgreSQL. По каждой обычной таблице (`relkind = 'r'`) выдаёт oid, схему, имя, оценку числа строк, полный размер, размер индексов, размер TOAST и размер собственно таблицы — в байтах и в удобочитаемом виде:

```sql
SELECT *, pg_size_pretty(total_bytes) AS total
    , pg_size_pretty(index_bytes) AS index
    , pg_size_pretty(toast_bytes) AS toast
    , pg_size_pretty(table_bytes) AS table
  FROM (
  SELECT *, total_bytes-index_bytes-coalesce(toast_bytes,0) AS table_bytes FROM (
      SELECT c.oid,nspname AS table_schema, relname AS table_name
              , c.reltuples AS row_estimate
              , pg_total_relation_size(c.oid) AS total_bytes
              , pg_indexes_size(c.oid) AS index_bytes
              , pg_total_relation_size(reltoastrelid) AS toast_bytes
          FROM pg_class c
          LEFT JOIN pg_namespace n ON n.oid = c.relnamespace
          WHERE relkind = 'r'
  ) a
) a;
```

Пример получения размера данных средствами платформы (8.3.15+):

```bsl
МассивИменМетаданных = Новый Массив();
МассивИменМетаданных.Добавить("Справочник.Номенклатура");
МассивИменМетаданных.Добавить("Документ.РасходнаяНакладная");
РазмерДанных = ПолучитьРазмерДанныхБазыДанных(Новый Массив(),МассивИменМетаданных);
```

### 1.9. Значительный рост сеансовых данных

Справка о механизме (из статьи):

- Платформа постоянно пользуется механизмом сеансовых данных. В них находится `ВременноеХранилище` и служебная информация, нужная для работы сеанса.
- За работу с сеансовыми данными отвечает менеджер кластера (`rmngr.exe` в терминах статьи).
- Если рабочих серверов несколько, сеансовые данные размещаются согласно требованиям назначения функциональности; если требования не заданы — распределяются равномерно по всем рабочим серверам.
