## Кратко: главные официальные рекомендации

Технологический журнал (статья 2, применимо на любой ОС с заменой путей):

1. Минимальный ТЖ имеет смысл держать включённым всегда и на всех серверах — тестовых, подготовительных, продукционных и серверах разработки. Он почти ничего не стоит и позволяет ответить на вопрос «что именно произошло».
2. Настройка «по умолчанию для любой продукционной площадки»: события `EXCP`, `CONN`, `PROC`, `ADMIN`, `SESN`, `CLSTR`, все свойства, `history="28"`, плюс сбор полных дампов (`type="3"`). По оценке авторов, по такому журналу расследуется до 80 % проблем работы платформы.
3. После любого изменения `logcfg.xml` подождать одну минуту (за это время процессы кластера гарантированно перечитывают файл) и убедиться, что журнал действительно пишется так, как ожидалось. Платформа никак не сообщает о некорректной настройке; в худшем случае на сервере не пишется вообще никакой ТЖ.
4. После включения или изменения ТЖ следить за ростом его объёма «некоторое время» (при настройке через ЦКК — от часа до нескольких часов); то же при ручной настройке.
5. В каталоге ТЖ и в подкаталогах процессов, которые создаёт платформа, не должно быть посторонних файлов — иначе журнал не записывается.
6. Платформа сама удаляет журнал старше `history` (в часах). Чтобы иметь журналы за любой момент, настроить ежедневное копирование со сжатием на другой ресурс планировщиком ОС.
7. Отдельный журнал длительных событий: все события с `Durationus >= 20000000` (20 с в микросекундах). Разбирать в первую очередь `SDBL` с `Func=CommitTransaction` (длительность внешней транзакции) и длительные запросы.
8. Для расследования управляемых блокировок — отдельный журнал `TLOCK` + `TTIMEOUT` + `TDEADLOCK` с короткой ротацией (`history="4"`): он бывает большим.
9. Журнал запросов СУБД с планами (`<plansql/>`) включать только с максимально узкими фильтрами (по базе `p:processName`, по пользователю).
10. Минимального ТЖ хватает, чтобы увидеть проблему и оценить её масштаб, но не для расследования: для расследования нужен ЦУП или более подробный ТЖ.
11. Полный клиентский ТЖ (все события) допустим для клиентского приложения, но такой журнал нельзя настраивать на рабочем сервере; запускать клиентские приложения на продукционных серверах в общем случае не рекомендуется.

Мониторинг и оповещения (статья 2):

12. В ЦКК как минимум настроить четыре контрольные процедуры: контроль подключений, контроль производительности, контроль потребления памяти, контроль устойчивости системы (на каждую — 5–10 минут).
13. Контрольные процедуры ЦКК, которые сами включают ТЖ (например, «Анализ вызовов кластера 1С»), настраивать очень осторожно; при сомнениях не менять значения по умолчанию.
14. Оповещения ЦКК работают только по уже собранным данным: без работающей контрольной процедуры (например, контроля потребления памяти) оповещение по числу сеансов не сработает.
15. Число сеансов — важный индикатор состояния системы (резкое падение вне регламентных работ = сбой; приближение к числу лицензий = пора принимать решение о дополнительных лицензиях).
16. Данные о загрузке оборудования собирать со всех серверов продукционной площадки, с шагом 5 секунд; обеспечить автозапуск сбора после перезагрузки сервера.

Механизмы платформы для мониторинга и аудита (статья 1, Linux):

17. Начиная с платформы 8.3.25 ТЖ можно писать в формате JSON (`format="json"`) и плоским каталогом (`placement="plain"`), что позволяет без самописного разбора отправлять его агентом (fluent-bit) в OpenSearch и искать через OpenSearch Dashboards.
18. Пример `logcfg.xml` «все события, все свойства» из статьи 1 рассчитан на тестовый сервер без нагрузки; если сбор не постоянный — выключать его удалением или переименованием `logcfg.xml`.
19. Журнал регистрации можно выводить в поток вывода утилиты `ibcmd` и отправлять во внешнюю систему; пример — Python-скрипт, который следит за процессом `ibcmd`, перезапускает его и ведёт чекпоинт (дату последнего отправленного события).
20. Сервер администрирования `ras` умеет отдавать метрики кластера для Prometheus: `ras cluster --monitor-base /metrics --monitor-address 0.0.0.0 --monitor-port 1555`; предварительной настройки не требуется.
21. Время выполнения запросов к веб-серверу получают из журнала Apache, добавив `%D` (микросекунды) в `LogFormat`; такие метрики возможны только при работе клиентов через публикацию на веб-сервере.
22. Метрики успешных/неуспешных вызовов к СУБД в примере считаются по данным ТЖ в OpenSearch, т. е. требуют включённой отправки ТЖ.
23. Пример в статье 1 сделан без HTTPS и со стандартной учётной записью OpenSearch; для настройки сертификатов авторы отсылают к руководству OpenSearch.

## Статья 1. Использование механизмов платформы «1С:Предприятие» для мониторинга и аудита

- Дата публикации: 18.01.2024 (рубрика «Инструкции»).
- Ссылка: https://its.1c.ru/db/metod8dev/content/6019/hdoc
- Стенд статьи: Ubuntu 22.04 LTS; платформа 8.3.25 и выше (требование первой части).

### Оценка применимости на октябрь 2026: актуально

Статья описывает действующие механизмы платформы (ТЖ в формате JSON, вывод ЖР через `ibcmd`, режим метрик у `ras`) и написана для Linux — напрямую применима к серверу 1С на Ubuntu. Поправки, которые нужно учитывать (оценка составителя конспекта по датам и версиям в тексте; детали проверять по актуальной документации продуктов):

- Команды установки привязаны к Ubuntu 22.04: в репозитории fluent-bit прописано кодовое имя `jammy`; на другом релизе авторы сами отсылают к инструкциям производителей.
- Репозиторий OpenSearch — ветка `2.x`; ссылка на описание DQL ведёт на документацию версии 2.6. Ключ OpenSearch добавляется через `apt-key`, тогда как для fluent-bit в той же статье уже используется более новый способ (`signed-by` + keyring).
- Prometheus скачивается как «latest»-релиз с GitHub, т. е. в 2026 году будет получена не та версия, что у авторов: состав архива (каталоги `consoles`, `console_libraries`) и набор флагов запуска нужно сверить.
- Учётная запись OpenSearch `admin`/`admin` и отключённый TLS — параметры демонстрационного стенда, а не рекомендация для эксплуатации. Замечание составителя (не из источника): в новых выпусках OpenSearch пароль администратора может требоваться задавать при установке — проверить по документации.
- Зависимости Python ставятся общесистемным `pip3 install`; на более новых релизах Ubuntu порядок установки пакетов Python может отличаться (замечание составителя, не из источника).
- Сами скрипты и конфигурации (`fluentbit_config_1c.tar.gz`, `eventlog-watcher.tar.gz`, `server-follower.tar.gz`) приложены к статье архивами; в текстовой копии их содержимого нет, поэтому в конспекте описаны только параметры, названные в тексте.
- Все три части — демонстрация на тестовом стенде: fluent-bit и Python-скрипты запускаются вручную из консоли, оформление их в службы systemd в статье не описано (служба делается только для Prometheus).

Статья состоит из трёх независимых частей: (1) ТЖ → OpenSearch, (2) ЖР → OpenSearch, (3) метрики → Prometheus.

### 1. Журналирование с помощью технологического журнала

#### 1.1. Требования и идея

- Платформа: 8.3.25 и выше.
- ОС: Linux (в примере Ubuntu 22.04 LTS).
- Инструменты: fluentbit, OpenSearch, OpenSearch Dashboards.

Логика авторов: ТЖ — обычная отправная точка расследования ошибок прикладного кода и проблем параллельной работы. Небольшие логи (например, тонкого клиента) можно читать текстовым редактором, а большие массивы обычно разбирают `grep`, `cat`, `awk`, скриптами и ЦУП, что требует знания ОС и утилит. Чтобы упростить структурирование, в платформе появился вывод ТЖ в разных форматах: настраивается и формат событий, и способ формирования файлов. Ниже — пример быстрой выгрузки ТЖ в OpenSearch.

Стек:

- fluentbit — лёгкий процессор обработки и отправки журналов (https://fluentbit.io/);
- OpenSearch — поиск и фильтрация больших объёмов данных (https://www.opensearch.org/);
- OpenSearch Dashboards — графический интерфейс к OpenSearch (по словам авторов, новое название инструмента Kibana) для поиска и анализа проиндексированных данных.

Размещение в примере:

| Хост | Что установлено |
|------|-----------------|
| Сервер 1 (Ubuntu 22.04) | сервер «1С:Предприятие» + fluent-bit; здесь пишется ТЖ, fluent-bit в реальном времени отправляет его в OpenSearch |
| Сервер 2 (Ubuntu 22.04) | OpenSearch + OpenSearch Dashboards |

#### 1.2. Настройка сервера «1С:Предприятие»

Оговорка авторов: используется тестовый сервер без дополнительной нагрузки, поэтому собираются все события со всеми полями. Предполагается, что сервер 1С уже установлен и запущен.

Шаг 1. Каталог для логов, владелец — пользователь, от имени которого работает сервер 1С:

```bash
sudo mkdir -p /1c/logs
sudo chown usr1cv8:grp1cv8 -R /1c
```

Шаг 2. Файл `logcfg.xml` (`location` заменить на реальный путь; `<x.x.x.x>` — версия установленной платформы). В источнике между строками стоят пустые строки вёрстки — убраны (исправлено по смыслу):

```bash
sudo tee /opt/1cv8/x86_64/<x.x.x.x>/conf/logcfg.xml<<EOF
<?xml version='1.0' encoding='UTF-8'?>
<config xmlns="http://v8.1c.ru/v8/tech-log">
  <log location="/1c/logs" history="4" placement="plain" format="json">
    <event>
      <ne property="Name" value=""/>
    </event>
    <property name="all">
    </property>
  </log>
</config>
EOF
```

Значение ключевых атрибутов:

| Атрибут | Значение | Смысл |
|---------|----------|-------|
| `placement` | `plain` | файлы кладутся прямо в указанный каталог, без промежуточных подкаталогов с именами процессов |
| `format` | `json` | содержимое логов в формате JSON |
| `history` | `4` | глубина хранения журнала; в этой статье единица не названа, в статье 2 такое же значение описано как ротация за 4 часа |
| `location` | `/1c/logs` | каталог логов |

Шаг 3. Владелец файла — пользователь сервера 1С:

```bash
sudo chown usr1cv8:grp1cv8 /opt/1cv8/x86_64/<x.x.x.x>/conf/logcfg.xml
```

Шаг 4. Примерно через минуту должен начаться сбор. Проверка:

```bash
ls -l /1c/logs/
```

Ожидается листинг файлов логов (в источнике — снимок экрана).

Оговорки:

- Если сбор ведётся не постоянно, для отключения ТЖ удалить или переименовать `logcfg.xml`.
- ⚠ в источнике неясно: после команды, которая уже пишет файл в каталог `conf`, сказано, что «полученный файл» нужно сохранить в каталог `conf` дистрибутива платформы после установки остальных компонентов. По смыслу — включать сбор (класть файл в `conf`) стоит, когда остальная цепочка готова принимать данные.

#### 1.3. Установка OpenSearch и OpenSearch Dashboards (сервер 2)

Установка через `apt`; для другой ОС — инструкция https://opensearch.org/docs/latest/install-and-configure/install-opensearch/index/ .

1. Импорт публичного GPG-ключа (в источнике в конце длинное тире вместо дефиса — исправлено по смыслу):

```bash
curl -o- https://artifacts.opensearch.org/publickeys/opensearch.pgp | sudo apt-key add -
```

2. APT-репозиторий OpenSearch:

```bash
echo "deb https://artifacts.opensearch.org/releases/bundle/opensearch/2.x/apt stable main" | sudo tee -a /etc/apt/sources.list.d/opensearch-2.x.list
```

3. APT-репозиторий OpenSearch Dashboards:

```bash
echo "deb https://artifacts.opensearch.org/releases/bundle/opensearch-dashboards/2.x/apt stable main" | sudo tee -a /etc/apt/sources.list.d/opensearch-dashboards-2.x.list
```

4. Проверка репозиториев, установка и включение автозапуска OpenSearch:

```bash
sudo apt-get update
sudo apt-get install opensearch
sudo systemctl enable opensearch
```

5. Правка `/etc/opensearch/opensearch.yml`. В примере HTTPS и сертификаты не используются; настройка TLS — по руководству https://opensearch.org/docs/latest/install-and-configure/install-opensearch/debian/#configure-tls . Изменения (в виде фрагмента YAML; в источнике перечислены словами):

```yaml
# раскомментировать и задать
network.host: 0.0.0.0
# полное имя (FQDN) сервера, на котором запущен OpenSearch, например server1.my.domain
discovery.seed_hosts: ["Полное_имя_сервера"]
# HTTPS в примере не используется
plugins.security.ssl.http.enabled: false
```

6. Запуск и проверка OpenSearch:

```bash
sudo systemctl start opensearch
sudo systemctl status opensearch
```

7. Установка, автозапуск, запуск и проверка OpenSearch Dashboards (в источнике имя службы разорвано пробелом — `opensearch -dashboards`; исправлено по смыслу):

```bash
sudo apt-get install opensearch-dashboards
sudo systemctl enable opensearch-dashboards
sudo systemctl start opensearch-dashboards
sudo systemctl status opensearch-dashboards
```

#### 1.4. Установка и запуск fluent-bit (сервер 1С)

Установка через `apt`; для другой ОС — https://docs.fluentbit.io/manual/installation/getting-started-with-fluent-bit .

1. Импорт GPG-ключа:

```bash
sudo sh -c 'curl https://packages.fluentbit.io/fluentbit.key | gpg --dearmor > /usr/share/keyrings/fluentbit-keyring.gpg'
```

2. APT-репозиторий (в источнике после открывающей кавычки стоит лишний пробел — убран, исправлено по смыслу; `jammy` = Ubuntu 22.04):

```bash
echo "deb [signed-by=/usr/share/keyrings/fluentbit-keyring.gpg] https://packages.fluentbit.io/ubuntu/jammy jammy main" | sudo tee -a /etc/apt/sources.list.d/fluent-bit.list
```

3. Проверка репозитория и установка:

```bash
sudo apt-get update
sudo apt-get install fluent-bit
```

4. Каталог конфигурации, распаковка архива `fluentbit_config_1c.tar.gz` (приложен к статье; предварительно положить в `/tmp`), права на чтение для всех (в источнике у `tar` длинные тире вместо дефисов — исправлено по смыслу):

```bash
sudo mkdir -p /1c/config
sudo tar -xzf /tmp/fluentbit_config_1c.tar.gz -C /1c/config
sudo chmod o+r /1c/config
```

В тексте упомянуты три файла из архива: `techlog.conf` (основные параметры fluent-bit), `techlog_parser.conf` (парсер), `transform_techlog.lua` (Lua-скрипт преобразования). Их содержимое в текстовой копии статьи отсутствует.

5. Что обычно нужно поменять в `techlog.conf`:

| Секция | Параметр | Что указать |
|--------|----------|-------------|
| `[INPUT]` | `Path` | каталог из атрибута `location` файла `logcfg.xml` плюс маска `*.log` |
| `[FILTER]` | `script` | полный путь к `transform_techlog.lua`, например `/1c/config/transform_techlog.lua` |
| `[OUTPUT]` | `Host`, `Port` | хост и порт OpenSearch |
| `[OUTPUT]` | `Http_User`, `Http_Passwd` | логин и пароль OpenSearch. По словам авторов, в OpenSearch автоматически создаётся пользователь `admin` с паролем `admin`; при желании можно создать другого пользователя и указать его |
| `[OUTPUT]` | `Index` | имя индекса OpenSearch для документов ТЖ; по умолчанию `techlog_index` |

⚠ в источнике неясно: в качестве примера `Path` приведено `/1c/config/*.log`, хотя по правилу из того же абзаца (каталог `location` + `*.log`) для данного стенда должно получаться `/1c/logs/*.log`.

6. Запуск (обычный каталог установки — `/opt/fluent-bit/bin`):

```bash
cd /opt/fluent-bit/bin
sudo ./fluent-bit --config /1c/config/techlog.conf --parser /1c/config/techlog_parser.conf
```

При правильной настройке в консоль выводится служебная информация. Строки с событием `[error]` означают ошибку — исправлять по её тексту. Если ошибок нет, переходить к проверке данных в Dashboards.

#### 1.5. Просмотр данных в OpenSearch Dashboards

1. Открыть `http://<имя-сервера>:5601` (`<имя-сервера>` — хост с OpenSearch Dashboards; 5601 — порт по умолчанию). Войти под `admin`/`admin` либо под своей учётной записью.
2. На новой установке появится страница приветствия: нажать «Explore on my own», затем «Confirm».
3. Боковое меню → «Index Management» → «Indices»: убедиться, что индекс создан (имя совпадает с параметром `Index` секции `[OUTPUT]` в `techlog.conf`).
4. Создать шаблон индекса: пиктограмма управления (в источнике картинка) → ссылка «Manage» → в боковом меню «Index Patterns» → «Create index pattern».
5. В поле «Index pattern name» ввести `techlog_index`. Если индексов несколько, можно использовать маску со звёздочкой: при индексах `techlog_index_calls` и `techlog_index_exceptions` шаблон `techlog_index*` охватит оба. Нажать «Next step».
6. В качестве поля времени выбрать `@timestamp`, нажать «Create index pattern».
7. Боковое меню → «Discover»: откроется просмотр событий ТЖ по выбранному шаблону. Единственный шаблон выбирается автоматически; если шаблонов несколько — выбрать в раскрывающемся списке под ссылкой «+ Add filter».

#### 1.6. Поиск данных (язык DQL — формат по умолчанию)

- Поиск по всем событиям и всем полям: просто ввести фразу, например `Ошибка при вызове метода контекста`.
- Поиск по полю: `имя_поля:текст`. Имена полей видны в списке «Available fields» слева от результатов. В тексте допустимы спецсимволы `*` и `?`.
- Логические операции: `OR`, `AND`, `NOT`.

```text
name:EXCP
name:EXCP AND Ошибка при вызове метода контекста
```

Первый запрос показывает только события `EXCP`; второй объединяет фильтр по событию с текстовым поиском. Описание DQL: https://opensearch.org/docs/2.6/dashboards/discover/dql/ .

### 2. Аудит с помощью данных журнала регистрации

#### 2.1. Требования и идея

- ОС: Linux (в примере Ubuntu 22.04 LTS).
- Инструменты: python, OpenSearch, OpenSearch Dashboards.

ЖР используют, чтобы узнать, какие события происходили в конкретный момент и что делал конкретный пользователь; запись в ЖР можно расширять из встроенного языка, если нужна диагностика, которую платформа не пишет сама. Раньше ЖР обычно смотрели в конфигураторе или клиенте 1С. Для анализа ЖР во внешней единой системе в платформе реализован вывод событий ЖР в поток вывода утилиты `ibcmd` (входит в поставку платформы).

#### 2.2. Что делает скрипт (eventlog-watcher)

- Вместо скрипта можно использовать тот же fluent-bit; Python выбран, чтобы показать не только чтение потока `ibcmd`, но и контроль за самим процессом.
- Скрипт запускает `ibcmd` с нужным набором параметров и следит, что процесс существует; если процесс завершился — перезапускает его.
- Полученные события отправляются в OpenSearch.
- После отправки каждого события скрипт создаёт/обновляет файл-чекпоинт с датой последнего отправленного события. При перезапуске утилиты или скрипта отправка продолжается с момента чекпоинта.
- Конкретные параметры вызова `ibcmd` в тексте статьи не приведены (они внутри скрипта из архива).

#### 2.3. Установка Python и настройка скрипта

### 3. Мониторинг серверов платформы «1С:Предприятие» и операционной системы

#### 3.1. Требования и идея

- ОС: Linux (в примере Ubuntu 22.04 LTS).
- Инструменты: Apache 2.4, Python, Prometheus.

Источники метрик:

| Что измеряется | Чем собирается |
|----------------|----------------|
| счётчики потребления ресурсов кластером 1С | сервер администрирования `ras` в режиме метрик |
| счётчики производительности ОС | Python-скрипт (server-follower) |
| успешные/неуспешные вызовы к веб-серверу с опубликованной ИБ и время запросов | тот же скрипт, по журналу Apache |
| успешные/неуспешные вызовы сервера 1С к СУБД | тот же скрипт, по данным ТЖ в OpenSearch |

Все метрики забирает Prometheus — открытое ПО для мониторинга и оповещения (https://prometheus.io/).

#### 3.2. Установка Prometheus

1. Системные группа и пользователь:

```bash
sudo groupadd --system prometheus
sudo useradd -s /sbin/nologin --system -g prometheus prometheus
```

2. Каталоги данных и конфигурации:

```bash
sudo mkdir /var/lib/prometheus
for i in rules rules.d files_sd; do sudo mkdir -p /etc/prometheus/${i}; done
```

3. Обновление списков пакетов, временный каталог, загрузка последнего релиза, распаковка:

```bash
sudo apt-get update
mkdir -p /tmp/prometheus && cd /tmp/prometheus
curl -s https://api.github.com/repos/prometheus/prometheus/releases/latest | grep browser_download_url | grep linux-amd64 | cut -d '"' -f 4 | wget -qi -
tar xvf prometheus*.tar.gz
cd prometheus*/
```

4. Раскладка файлов (исполняемые — в `/usr/local/bin`; в тексте источника опечатка «/ust/local/bin», команда верная):

```bash
sudo mv prometheus promtool /usr/local/bin/
sudo mv prometheus.yml /etc/prometheus/prometheus.yml
sudo mv consoles/ console_libraries/ /etc/prometheus/
cd $HOME
```

5. В `/etc/prometheus/prometheus.yml` добавить два задания: первое собирает метрики кластера 1С (с `ras`), второе — метрики Python-скрипта. По тексту нужно заменить `<server-name>` на реальный адрес сервера (серверов) с платформой 1С и скриптом; в текстовой копии сам заполнитель из строк `targets` выпал (осталось `":1555"` и `":8081"`) — восстановлен, исправлено по смыслу:

```yaml
  - job_name: "cluster_metrics"
    static_configs:
      - targets:
          - "<server-name>:1555"
    params:
      sessions: ["1"]
  - job_name: "os_ws_proc_metrics"
    static_configs:
      - targets:
          - "<server-name>:8081"
```

Пояснения:

- Имена `job_name` произвольные, их можно переименовать.
- `params: sessions: ["1"]` — метрики кластера собираются с учётом данных сеансов. Если секцию `params` удалить, будут выводиться только метрики кластера.
- Порты из `targets` (1555 и 8081) должны совпадать с портами, на которых запускаются источники метрик (`ras` и скрипт).

6. Служба systemd (пустые строки вёрстки убраны; значение `--web.external-url=` в источнике пустое):

```bash
sudo tee /etc/systemd/system/prometheus.service<<EOF
[Unit]
Description=Prometheus
Documentation=https://prometheus.io/docs/introduction/overview/
Wants=network-online.target
After=network-online.target

[Service]
Type=simple
User=prometheus
Group=prometheus
ExecReload=/bin/kill -HUP \$MAINPID
ExecStart=/usr/local/bin/prometheus \
  --config.file=/etc/prometheus/prometheus.yml \
  --storage.tsdb.path=/var/lib/prometheus \
  --web.console.templates=/etc/prometheus/consoles \
  --web.console.libraries=/etc/prometheus/console_libraries \
  --web.listen-address=0.0.0.0:9090 \
  --web.external-url=

SyslogIdentifier=prometheus
Restart=always

[Install]
WantedBy=multi-user.target
EOF
```

7. Владельцы и права:

```bash
for i in rules rules.d files_sd; do sudo chown -R prometheus:prometheus /etc/prometheus/${i}; done
for i in rules rules.d files_sd; do sudo chmod -R 775 /etc/prometheus/${i}; done
sudo chown -R prometheus:prometheus /var/lib/prometheus/
```

8. Перечитать юниты, включить автозапуск, запустить, проверить:

```bash
sudo systemctl daemon-reload
sudo systemctl enable prometheus
sudo systemctl start prometheus
systemctl status prometheus
```

#### 3.3. Установка и настройка Apache 2.4

Число успешных и неуспешных вызовов к серверу и время выполнения запросов считаются только анализом журнала Apache. Поэтому для этих метрик ИБ должна быть опубликована на веб-сервере, а тонкий клиент должен подключаться по ws-ссылке.

Установка:

```bash
sudo apt install apache2
```

Публикация ИБ (`<server_1c>`, `<infobase_name>` — свои значения; `<x.x.x.x>` — версия платформы; в источнике у `-connstr` типографские кавычки — заменены на прямые, исправлено по смыслу):

```bash
sudo /opt/1cv8/x86_64/<x.x.x.x>/webinst -publish -apache24 -wsdir <infobase_name> -dir /var/www/<infobase_name> -connstr "Srvr=<server_1c>;Ref=<infobase_name>;"
```

В `/etc/apache2/apache2.conf` в конце файла заменить строки

```apache
LogFormat "%h %l %u %t \"%r\" %>s %O \"%{Referer}i\" \"%{User-Agent}i\"" combined
LogFormat "%h %l %u %t \"%r\" %>s %O" common
```

на

```apache
LogFormat "%h %l %u %t %D \"%r\" %>s %O \"%{Referer}i\" \"%{User-Agent}i\"" combined
LogFormat "%h %l %u %t %D \"%r\" %>s %O" common
```

Добавленный `%D` выводит время выполнения запроса в микросекундах.

Проверка конфигурации и перезапуск (перезапускать только если `configtest` не показал ошибок; иначе исправлять по тексту ошибок):

```bash
apachectl configtest
sudo systemctl restart apache2
```

#### 3.4. Что делает скрипт (server-follower)

Универсальный Prometheus-клиент на Python. При запуске инициализирует клиент Prometheus, который отдаёт значения метрик в формате, понятном серверу Prometheus. Может отдавать:

- показатели производительности процессов кластера 1С — в разрезе каждого процесса;
- общие метрики системы: загрузка процессора, свободная и занятая оперативная память, скорость чтения/записи диска, скорость приёма/передачи пакетов сетевых интерфейсов;
- число успешных и неуспешных вызовов к веб-серверу, на котором опубликована ИБ;
- время выполнения запросов к этому веб-серверу;
- число успешных и неуспешных вызовов сервера 1С к серверу СУБД. Эти значения берутся из OpenSearch, поэтому должны быть включены сбор и отправка ТЖ в OpenSearch (часть 1 статьи).

Каждый тип метрик включается и отключается отдельно (например, можно оставить только метрики вызовов к СУБД).

#### 3.5. Развёртывание и настройка скрипта

Архив `server-follower.tar.gz` приложен к статье; скопировать на сервер, например в `/tmp`.

```bash
sudo chmod o+r /1c/scripts/server-follower
pip3 install -r /1c/scripts/server-follower/requirements.txt
```

(Длинные тире у `tar` и `pip3` заменены на дефисы — исправлено по смыслу.)

⚠ в источнике неясно: то же расхождение путей, что и в части 2, — распаковка и запуск из `/1c/config/server-follower`, права и зависимости из `/1c/scripts/server-follower`. Использовать один каталог во всех командах. Python должен быть установлен (см. п. 2.3).

Обязательные параметры `settings.yml`:

| Секция | Параметр | Назначение | По умолчанию |
|--------|----------|------------|--------------|

### Оценка применимости на октябрь 2026: частично устарело

- Несмотря на дату 01.08.2025, по содержанию текст заметно старше: в нём упоминаются платформа 8.3.4.437 (в примере имени дампа), БСП версии 2.1.2.23 и «выпущенная на момент написания» БСП 2.2, PowerShell 3.0/4.0, пример для MS SQL Server.
- Статья целиком про Windows: пути `C:\LOGS`, `C:\DUMPS`, Performance Monitor, `logman`, Task Scheduler, PowerShell, `cygwin`. Для сервера 1С на Ubuntu эти части напрямую неприменимы и сохранены в конспекте как справочные.
- Остаются верными и переносимыми на Linux: принципы (всегда держать минимальный ТЖ, контролировать его объём, проверять через минуту, не класть посторонние файлы в каталог ТЖ, архивировать журналы), состав событий в примерах `logcfg.xml`, методика разбора взаимоблокировки по `TLOCK`/`TDEADLOCK`, perl-скрипты разбора (на Linux работают без cygwin), роль ЦКК и состав минимальных контрольных процедур.
- При переносе на Linux нужно заменить пути в `location`; расположение `logcfg.xml` и каталога логов для Linux показано в статье 1 (`/opt/1cv8/x86_64/<x.x.x.x>/conf/logcfg.xml`, `/1c/logs`). Настройка сбора дампов на Linux в этой статье не рассматривается (элемент `<dump>` в примерах — для Windows).
- Пример журнала запросов сделан для MS SQL Server (событие `DBMSSQL`); имя события для PostgreSQL в источнике не приводится. Замечание составителя (не из источника): в ТЖ платформы запросы к PostgreSQL фиксируются событием `DBPOSTGRS` — сверить с документацией платформы.
- Для счётчиков загрузки оборудования на Linux источник аналога не даёт; пример сбора метрик ОС на Linux — в статье 1, часть 3.

### 1. Настройка ЦКК

#### 1.1. Общие сведения

- ЦКК (Центр контроля качества) — типовая конфигурация из состава Корпоративного инструментального пакета. Собирает и агрегирует информацию и оповещает о важных событиях в работе системы.
- Контрольные процедуры настраиваются на рабочем столе конфигурации; общие параметры — в мастере настроек основных параметров (раздел «Настройки»).
- Раздел «Мониторинг»: динамика показателей по настроенным контрольным процедурам; возможность поделиться настроенной статистикой с коллегой; создание оповещений (условий, при которых ЦКК отправит sms или e-mail); журнал оповещений.
- Раздел «Сервис»: подробная аналитика по собранным данным.

Минимальный набор контрольных процедур (настройка каждой — не более 5–10 минут):

1. Контроль подключений.
2. Контроль производительности.
3. Контроль потребления памяти.
4. Контроль устойчивости системы.

Оговорки авторов:

- Настроить все контрольные процедуры желательно — тогда функциональность ЦКК используется полностью. Но не все из них уместны на продукционных серверах (пример — «Контроль нагрузочных тестов»).
- Процедуры, которые настраивают ТЖ (пример — «Анализ вызовов кластера 1С»), требуют большой осторожности: в зависимости от нагрузки может собираться весьма большой журнал. При неуверенности — не менять значения по умолчанию.
- После настройки процедур, связанных с ТЖ, ЦКК показывает предупреждение о включении ТЖ. После нажатия «Продолжить» нужно каждый раз в течение некоторого времени (от часа до нескольких часов) периодически следить за объёмом собираемых данных и за размером базы ЦКК. То же требование действует при ручной настройке ТЖ.
- Статья описывает только минимальный объём механизмов ЦКК и не претендует на полное документирование конфигурации.

#### 1.2. Контроль подключений (рекомендуется настраивать первым)

Задачи: в любой момент проверять возможность входа в ИБ; оповещать, если войти нельзя; копить статистику доступности ИБ.

Минимальная настройка:

- включить флаг «Оповещать о восстановлении»;
- включить флаг «Оповещать о сбое»;
- указать группу ответственных лиц — получателей оповещений;
- выбрать способ подключения (например, web-сервис);
- указать URL, логин и пароль.

Дополнительно:

- Инструкция по использованию web-сервиса — на закладке «Рекомендации» формы настройки контроля подключений.
- Чтобы при сбое получать оповещения повторно, каждые N секунд, пока ИБ недоступна, добавить параметры оповещения при сбое.
- После настройки проверить состав указанной группы ответственных: «Настройки» → «Зоны ответственности».

#### 1.3. Контроль производительности

- Требование: в контролируемую ИБ должна быть встроена подсистема оценки производительности из «1С:Библиотека стандартных подсистем» версии 2.1.2.23 или новее (на момент написания статьи была выпущена БСП 2.2).
- Указать: группу ответственных лиц (оповещения для этой процедуры не обязательны) и каталог файлов оценки производительности, в который настроена выгрузка из контролируемой ИБ.
- Экспорт замеров в этот каталог настраивается в обработке «ОценкаПроизводительности» из одноимённой подсистемы БСП.

#### 1.4. Контроль потребления памяти

- Назначение: оперативно обнаруживать превышение заданного порога оперативной памяти, занятой рабочими процессами сервера.
- Побочная польза: в ЦКК сохраняется информация о сеансах контролируемого кластера. По динамике числа сеансов хорошо видны нарушения работы (например, резкое падение числа сеансов, когда регламентных работ не запланировано).

Указать:

- объект контроля — кластер серверов;
- оповещение о сбое (задача: «Устранить причины превышения порога потребления памяти»);
- группу ответственных лиц;
- период автоматического удаления подробной информации о сеансах — рекомендуется не более 240 часов, иначе растёт база ЦКК.

#### 1.5. Контроль устойчивости системы

Назначение:

- настройка сбора дампов процессов при аварийных завершениях;
- автоматический разбор, сохранение статистики, архивация и перемещение дампов с продукционных серверов;
- настройка минимально необходимого ТЖ для последующего анализа аварийных завершений процессов кластера;
- оповещение ответственных об аварийных завершениях — как с образованием дампа, так и без него.

Указать:

- объект контроля — рабочий сервер;
- оповещения о сбое (рекомендуется минимум два: аварийное завершение с дампом и без дампа);
- сетевой и локальный каталог настройки ТЖ;
- сетевой и локальный путь к каталогу сохранения дампов;
- каталог временных файлов (нужен для архивации дампов);
- каталог, в который экспортируются дампы.

По умолчанию экспортируются только уникальные дампы (уникальность определяется именем, версией и смещением; формулировка в источнике нечёткая — ⚠ в источнике неясно). Свойство «Сохранять все файлы дампов» в настройках дампа включает экспорт всех файлов.

#### 1.6. Гибкие оповещения

В разделе «Мониторинг» оповещения (sms и/или e-mail) настраиваются по любому набору условий на выбранные показатели: выбрать показатель (например, «Число сеансов»), условие сравнения, пороговое значение, период проверки и получателей. Условие можно наложить на абсолютное значение показателя либо на значение, рассчитанное за выбранный период в прошлом (отслеживание отклонений).

Примеры авторов:

- ИБ работает 24/7, пользователи в ней должны быть всегда. Если база формально доступна, но сеансы завершаются, — слишком малое число сеансов сигнализирует о сбое.
- Есть 1000 клиентских лицензий: оповещение при приближении числа сеансов к критичному (например, 950) даёт запас времени на решение об активации дополнительных лицензий.

Предупреждение авторов: оповещения считаются по данным, уже собранным в ЦКК, поэтому нужны работающие контрольные процедуры. Если «Контроль потребления памяти» не настроен, оповещение по числу сеансов работать не будет.

#### 1.7. Использование ЦКК для агрегации своих данных (web-сервис InputStatistics)

- В ЦКК встроен web-сервис `InputStatistics`, принимающий данные от внешних источников, специфичных для вашей системы (для которых может не быть готовой контрольной процедуры).
- В конфигурацию включена тестовая обработка `ТестInputStatistics`, показывающая использование сервиса.
- На вход подаётся строка: уровни иерархии через точку, число — всегда после последней точки.

```text
Группа1.ВложеннаяГруппа2.Значение.Число

Группа.123
Группа.Подгруппа.234
Группа.Подгруппа2.345
Организация.Подразделение.ПлощадкаСерверов.СерверСУБД.AvgDiskQueueLength.7
```

- ЦКК сам группирует значения по переданной иерархии; значения могут храниться и в узлах дерева, и в листьях.
- Просмотр: раздел «Мониторинг», показатель «Счетчики».
- Каждая точка графика — агрегат за выбранный период, поэтому нужно выбрать способ свёртки: сумма, среднее либо количество вызовов web-сервиса с данной иерархией счётчиков.
- По счётчикам (или группе счётчиков) тоже можно настроить гибкие оповещения на отклонение от заданной величины.

#### 1.8. Пример: сбор загрузки оборудования PowerShell-скриптом с агрегацией в ЦКК (только Windows; PowerShell 3.0 или 4.0)

Файлы `srv_perf.ps1` (скрипт) и `srv_perf.xml` (настройки) — из каталога исходных файлов статьи; в текстовой копии их содержимого нет.

1. Скопировать `srv_perf.ps1` и `srv_perf.xml` на контролирующий сервер (тот, с которого ведётся контроль).
2. На всех контролируемых серверах создать пользователя, от имени которого будут читаться данные (в примере `QMC_WS`).
3. Добавить `QMC_WS` в группу Performance Monitor Users на всех контролируемых серверах.
4. На контролирующем сервере открыть `srv_perf.xml`.
5. Если контролируемые серверы — не серверы СУБД с используемым MS SQL Server (т. е. это рабочие серверы 1С), удалить все счётчики между комментариями:

```xml
<!-- For MS SQL Server only -->
<!-- END For MS SQL Server only -->
```

   Все перечисленные в файле счётчики должны нормально собираться Performance Monitor; если какой-то называется иначе — заменить. В файле указаны счётчики логических дисков C, D и E: если таких дисков нет, строки заменить или удалить.

6. В разделе параметров (`<Parameters>`) перечислить все серверы по образцу из примера (⚠ в источнике неясно: фраза про образец оборвана):

```xml
<Servers>
    <Server>Server1C-1</Server>
    <Server>Server1C-2</Server>
</Servers>
```

7. В строке `WSURI` указать путь к опубликованному web-сервису ЦКК:

```xml
<WSURI>http://ServerQMC/qmc/ws/InputStatistics.1cws?wsdl</WSURI>
```

   В примере для подключения к web-сервису требуется аутентификация; используется отдельный пользователь (в примере `QMC`) с паролем.

8. Сохранить `srv_perf.xml`.
9. Один раз запустить скрипт из PowerShell и один раз ввести логин и пароль (в источнике `.\ srv_perf.ps1` с лишним пробелом — исправлено по смыслу; пример вводимых значений в источнике искажён — ⚠ в источнике неясно):

```powershell
.\srv_perf.ps1
```

   Рядом со скриптом должен появиться файл `wsInputStatistics.xml` с сохранёнными данными аутентификации, привязанными к серверу.

10. Открыть `srv_perf.ps1`, найти строки:

```powershell
## need one time to create password file wsInputStatistics.xml. If changed user profile or file deleted we need uncomment line below & run script interactly
$cred = Get-Credential  | EXPORT-CLIXML $cred_xml_path
```

    и закомментировать вторую, чтобы получилось:

```powershell
##$cred = Get-Credential  | EXPORT-CLIXML $cred_xml_path
```

11. Сохранить файл.
12. Создать задачу в Task Scheduler от имени пользователя `QMC_WS` (из шага 2), запускающую скрипт по расписанию, например раз в минуту. На контролирующем сервере у `QMC_WS` должны быть права на запуск скриптов PowerShell.
13. Отладка: при `$debug = $true` журнал создаётся всегда (путь к нему задан в `srv_perf.xml`); при втором значении журнал при безошибочной работе создаваться не должен. В источнике второе значение обрезано (`$debug = $`) — по смыслу `$false`, ⚠ в источнике неясно.

```powershell
$debug = $true
```

14. Убедиться, что в течение 5 минут данные появились в ЦКК: «Мониторинг» → добавить показатель «Счетчики» → выбрать нужный счётчик.

### 2. Настройка технологического журнала

#### 2.1. Общие положения

- Хотя бы минимальный ТЖ стоит настраивать всегда — для отслеживания качества работы системы. Хорошая практика — минимальный журнал на всех серверах: тестовых, подготовительных, продукционных и серверах разработки. Это почти бесплатная возможность всегда ответить на вопрос, что именно произошло.
- Сбор ТЖ настраивается в файле `logcfg.xml`. О расположении файла и его структуре авторы отсылают к отдельным статьям (ссылки в текстовой копии не сохранились).
- При любой настройке ТЖ нужно некоторое время контролировать рост объёма журнала.

Во всех примерах ниже пути — Windows (`C:\LOGS\...`, `C:\DUMPS`); на Linux `location` заменить на локальный каталог (ср. статью 1: `/1c/logs`).

#### 2.2. Серверный ТЖ: минимальная настройка

```xml
<?xml version="1.0" encoding="UTF-8"?>
<config xmlns="http://v8.1c.ru/v8/tech-log">
<dump create="true" location="C:\DUMPS" type="0" prntscrn="false"/>
<log location="C:\LOGS\All" history="28">
  <event>
      <eq property="Name" value="excp"/>
  </event>
   <property name="all"/>
</log>
</config>
```

Что даёт:

- Запись дампов при аварийном завершении любых процессов кластера. Объём дампов минимальный (`type="0"`): без дополнительных сегментов данных и памяти процесса.
- Все исключения, сгенерированные процессами платформы (не кодом на встроенном языке). Не каждое такое исключение — ошибка или явная проблема, но их наличие должно привлечь внимание администратора площадки.

Зачем это нужно:

1. Оценка стабильности — число аварийных завершений процессов. Если у файлов дампов совпадают имя процесса, версия и смещение (вид `rphost_8.3.4.437_01234567`), причина падений, скорее всего, одна и та же.
2. Поиск причины падения по ТЖ. Имя файла дампа, созданного платформой, всегда заканчивается на PID процесса. Порядок:
   - найти журнал с именем процесса и PID (например, `rphost_1234`; в источнике сказано «файл», по смыслу это каталог журнала процесса);
   - открыть последний по времени файл;
   - в его конце обязательно будет событие `EXCP`, где может быть указан стек кода на встроенном языке, при выполнении которого процесс аварийно завершился.
3. Оценка общего числа исключений с группировкой по типам (свойство `Descr`) — чтобы понять, чему уделить внимание в первую очередь.
4. Оценка общего числа ошибок параллельной работы (таймаутов блокировок и взаимоблокировок): все они обязательно попадают в ТЖ.
   - Тексты ошибок блокировок уровня СУБД зависят от СУБД, её локализации и версии, но все ошибки уровня СУБД «подписаны» источником (пример авторов — `Microsoft OLE DB Provider for SQL Server`).
   - Ошибки управляемых блокировок платформы всегда пишутся в ТЖ, и поле `Descr` содержит:

| Ситуация | Текст в `Descr` |
|----------|-----------------|
| таймаут на управляемой блокировке | «Превышено максимальное время ожидания предоставления блокировки» |
| взаимоблокировка на управляемых блокировках | «Неустранимый конфликт блокировок» |

Ограничение: такого минимального журнала недостаточно для расследования ошибок — для этого нужен ЦУП или более подробный ТЖ.

Предупреждения авторов:

- В каталоге журнала (в примере `C:\LOGS\All`) и в каталогах журналов процессов, которые создаёт платформа, не должно быть никаких посторонних файлов, иначе ТЖ записываться не будет.
- Платформа не сообщает о некорректной настройке ТЖ. В худшем случае на сервере не будет писаться ни один технологический журнал.
- Поэтому после каждой настройки ждать одну минуту (за это время все процессы кластера гарантированно перечитают конфигурационный файл) и убеждаться, что журнал собирается и ведётся так, как ожидалось.

#### 2.3. Серверный ТЖ: рекомендуемая настройка по умолчанию для всех продукционных площадок

```xml
<?xml version="1.0" encoding="UTF-8"?>
<config xmlns="http://v8.1c.ru/v8/tech-log">
<dump create="true" location="C:\DUMPS" type="3" prntscrn="false"/>
<log location="C:\LOGS\All" history="28">
  <event>
      <eq property="Name" value="EXCP"/>
  </event>
  <event>
      <eq property="Name" value="CONN"/>
  </event>
  <event>
      <eq property="Name" value="PROC"/>
  </event>
  <event>
      <eq property="Name" value="ADMIN"/>
  </event>
  <event>
      <eq property="Name" value="SESN"/>
  </event>
  <event>
      <eq property="Name" value="CLSTR"/>
  </event>
   <property name="all"/>
</log>
</config>
```

- По оценке авторов, это минимальный объём информации, по которому можно расследовать до 80 % проблем, возникающих при работе платформы.
- `type="3"` — пишутся полные снимки процессов в момент аварийного завершения. При крайне нестабильной работе каталог дампов (`C:\DUMPS`) будет занимать много места; в этом случае рекомендуется автоматический разбор дампов, например контрольной процедурой «Контроль устойчивости» ЦКК.
- Каталог ТЖ при нормальной работе не должен превышать пары сотен мегабайт в сутки. Оговорка авторов: всё зависит от нагрузки и конфигурации системы, оценка может оказаться очень грубой и некорректной.
- `history="28"`: по истечении заданного времени старый журнал автоматически удаляется платформой, чтобы не забивать диск. Поэтому рекомендуется настроить автоматическое копирование всех журналов (например, раз в сутки) со сжатием (например, в zip) на другой ресурс средствами планировщика ОС — тогда будут журналы за любой момент работы системы.

#### 2.4. Журнал длительных событий

```xml
<?xml version="1.0" encoding="UTF-8"?>
<config xmlns="http://v8.1c.ru/v8/tech-log">
<log location="C:\LOGS\LongEvents" history="28">
  <event>
      <ne property="Name" value=""/>
      <ge property="Durationus" value="20000000"/>
  </event>
   <property name="all"/>
</log>
</config>
```

- Настройка приведена для платформы 8.3; в фильтре по `Durationus` — 20 секунд, выраженные в микросекундах.
- При нормальной работе журнал должен быть небольшим; каждое попавшее в него событие — предмет разбора.
- В первую очередь смотреть события `SDBL` со свойством `Func=CommitTransaction`: их длительность — это длительность внешней транзакции (вложенные транзакции платформой не поддерживаются). Транзакция дольше 20 секунд, скорее всего, удерживает транзакционные блокировки и может быть «виновником» ошибок блокировок.
- Также уделять внимание длительным запросам.

### 3. Разбор технологического журнала скриптами

Авторы дают учебный шаблон, который позволяет получить результат с минимальными трудозатратами; из-за своей общности он может быть не самым оптимальным.

- На Windows-сервере для разбора можно использовать специальное ПО, например `cygwin`; нужно установить пакеты `perl`.
- Все команды выполняются из каталога, в котором лежат каталоги журналов процессов кластера (`rphost_<PID>` и т. п.).
- Скрипты читают поток, склеивают многострочные события (новое событие начинается со строки вида `ММ:СС.микросекунды`) и для событий нужного типа печатают строку для последующей агрегации стандартными утилитами.

#### 3.1. Группировка событий EXCP по полю Descr (только процессы rphost)

Результат — таблица «Количество / Descr».

```bash
cat rphost*/*.log | perl descr.pl | sort | uniq -c | sort -rn >> result.txt
```

Содержимое `descr.pl` (в источнике скрипт сжат вёрсткой в несколько строк — переформатирован без изменения кода; выражение `s/|'//g` приведено как в источнике, возможно, оно искажено вёрсткой — ⚠ в источнике неясно):

```perl
#!/usr/bin/perl
use strict;
my $event;
my %actions = (
    'EXCP' => [
                {
                    'action' => sub {
                               my ($event) =@_;
                               my ($garbage, $context) = split /Descr='/, $event;
                               my ($descr, $garbage) = split /'/, $context;
                               $descr =~ s/|'//g;
                               $descr =~ s/\s+/ /g;

                               print "EXCP Descr $descr\n" if $descr;
                    },
                },
    ],
);
while (<>) {
    $event=process_event($event) if /^\d\d:\d\d\.\d+/;
    $event .= $_;
}
sub process_event($) {
    my ($event) = @_;
    return unless $event;
    foreach my $event_type ( keys %actions ) {
                next unless $event =~ /^[^,]+,$event_type,/;
                foreach my $issue ( @{ $actions{$event_type} }) {
                    &{$issue->{action}}($event);
                }
    }
}
```

#### 3.2. Суммарная длительность событий DBMSSQL и SDBL по последней строке стека встроенного языка

Результат — таблица «СуммарнаяДлительность (в микросекундах) / Количество / Контекст».

```bash
cat rphost*/*.log | perl query.pl | awk -F'-' '{mas[$2] += $1; count[$2] += 1;} END {for (i in mas) {print mas[i] " " count[i] " " i};}' | sort -rn >> result.txt
```

Содержимое `query.pl`:

```perl
#!/usr/bin/perl
use strict;
my $event;
my %actions = (
    'DBMSSQL' => [
                {
                    'action' => sub {
                               my ($event) =@_;
                               my ($date, $garbage) = split /,DBMSSQL/, $event;
                               $date =~ s/\d\d:\d\d\.\d+-//g;

                               my ($garbage, $context) = split /Context='/, $event;
                               if ($context =~ /\n/) {
                                   my @mlc = split /\n/, $context;
                                   $context = $mlc[$#mlc];
                               }
                               $context =~ s/^\s+|'$//g;
                               $context =~ s/;'/;/g;
                               print "$date-$context\n" if $context;
                    },
                },
    ],
                'SDBL' => [
                {
                    'action' => sub {
                               my ($event) =@_;
                               my ($date, $garbage) = split /,SDBL/, $event;
                               $date =~ s/\d\d:\d\d\.\d+-//g;
                               my ($garbage, $context) = split /Context='/, $event;
                               if ($context =~ /\n/) {
                                   my @mlc = split /\n/, $context;
                                   $context = $mlc[$#mlc];
                               }
                               $context =~ s/^\s+|'$//g;
                               $context =~ s/;'/;/g;
                               print "$date-$context\n" if $context;
                    },
                },
    ],
);
print "\n";
while (<>) {
    $event=process_event($event) if /^\d\d:\d\d\.\d+/;
    $event .= $_;
}
sub process_event($) {
    my ($event) = @_;
    return unless $event;
    foreach my $event_type ( keys %actions ) {
                next unless $event =~ /^[^,]+,$event_type,/;
                foreach my $issue ( @{ $actions{$event_type} }) {
                    &{$issue->{action}}($event);
                }
    }
}
```

Скрипт берёт в качестве контекста последнюю строку стека вызова на встроенном языке. Чтобы группировать по первой строке стека, достаточно строку

```perl
$context = $mlc[$#mlc];
```

заменить на

```perl
$context = $mlc[1];
```

#### 3.3. Суммарная длительность ожиданий на управляемых блокировках

Вместо `query.pl` используется `tlock.pl` (отдельная команда запуска в источнике не приведена; по смыслу — тот же конвейер, что в п. 3.2, с заменой имени скрипта). Группировка идёт по значению `Regions`.

Содержимое `tlock.pl`:

```perl
#!/usr/bin/perl
use strict;
my $event;
my %actions = (
    'TLOCK' => [
                {
                    'action' => sub {
                               my ($event) =@_;
                               my ($date, $garbage) = split /,TLOCK/, $event;
                               $date =~ s/\d\d:\d\d\.\d+-//g;
                               my ($garbage, $region) = split /Regions=/, $event;
                               my ($region, $garbage) = split /,Locks='/, $region;
                               print "$date-$region\n" if $region;
                    },
                },
    ],
);
while (<>) {
    $event=process_event($event) if /^\d\d:\d\d\.\d+/;
    $event .= $_;
}
sub process_event($) {
    my ($event) = @_;
    return unless $event;
    foreach my $event_type ( keys %actions ) {
                next unless $event =~ /^[^,]+,$event_type,/;
                foreach my $issue ( @{ $actions{$event_type} }) {
                    &{$issue->{action}}($event);
                }
    }
}
```

Замечания:

- Шаблон легко переделывается под конкретную задачу: меняется имя события в `%actions` и то, какие поля вырезаются и печатаются. Для углубления авторы советуют книгу Джеффри Фридла «Регулярные выражения».
- Скрипты рассчитаны на обычный текстовый формат ТЖ с подкаталогами процессов (`rphost*/*.log`). К журналу в формате JSON с `placement="plain"` из статьи 1 они в таком виде не подходят (вывод составителя из сопоставления двух статей; в источниках это прямо не оговорено).
- Примеры в п. 3.2 привязаны к событию `DBMSSQL` (MS SQL Server), см. оценку применимости.

## Как две статьи соотносятся для сервера 1С на Ubuntu

Сопоставление сделано только по содержанию двух источников.

| Задача | Что говорит статья 2 (Windows) | Что даёт статья 1 (Linux) |
|--------|-------------------------------|---------------------------|
| постоянный ТЖ на продуктиве | состав событий и правила (п. 2.1–2.5 статьи 2) | расположение `logcfg.xml` в каталоге `conf` платформы, каталог логов с владельцем `usr1cv8:grp1cv8`, проверка через минуту |
| анализ ТЖ | perl + `sort`/`uniq`/`awk` по текстовому формату | JSON-формат ТЖ (8.3.25+) → fluent-bit → OpenSearch, поиск DQL |
| загрузка оборудования | Performance Monitor, `logman`, шаг 5 с | Python-скрипт-экспортёр + Prometheus (+ Grafana) |
| состояние кластера, сеансы | ЦКК: контроль потребления памяти, число сеансов, гибкие оповещения | `ras` в режиме метрик (`sessions: ["1"]`) → Prometheus |
| доступность ИБ | ЦКК: контроль подключений | метрики успешных/неуспешных вызовов к веб-серверу по журналу Apache |
| аудит действий пользователей | — | вывод ЖР через `ibcmd` → OpenSearch |

Общее предостережение из обеих статей: полный ТЖ («все события, все свойства») допустим на тестовом стенде без нагрузки (статья 1) или для клиентского приложения (статья 2); на рабочем сервере любой ТЖ включают с фильтрами и следят за его объёмом.
