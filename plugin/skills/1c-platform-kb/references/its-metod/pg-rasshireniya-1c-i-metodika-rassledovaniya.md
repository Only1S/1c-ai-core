# ИТС-конспект (методические материалы): Расширения PostgreSQL с патчами 1С (auto_dump, pg_wait_sampling) и методика расследования проблем производительности PostgreSQL
> Источник: статьи раздела «Методическая поддержка» портала 1С:ИТС (ссылки — в разделах). Это конспект своими словами, не дословный текст. Составлен 2026-10-10.

## Кратко: главные официальные рекомендации

Номер в квадратных скобках — номер статьи ИТС (раздел конспекта указан в таблице ниже).

1. [6011] Быстрая оценка «виноваты ли запросы»: собрать минимальный технологический журнал (все события, без свойств) и сложить длительности по типам событий. Если отношение суммарного времени DBPOSTGRS к CALL больше примерно 50 % — есть повод заниматься скоростью запросов.
2. [6011] Текст проблемного запроса берут из технологического журнала по событию DBPOSTGRS. Такой журнал может занять значительный объём диска.
3. [6011] Элемент `<plansql/>` на продуктивных серверах использовать нельзя — только на серверах тестирования или разработки. План получают, выполнив запрос на сервере PostgreSQL с `EXPLAIN` (в примерах — `EXPLAIN ANALYZE VERBOSE`).
4. [6011] Перед `EXPLAIN` нужно выставить те же параметры сеанса, которые ставит платформа (`enable_mergejoin = off`, `cpu_operator_cost = 0.001`, `lock_timeout = 20000` и др.) — тогда план будет идентичен платформенному.
5. [6011] Если запрос использует временные таблицы, нужно собрать вверх по журналу все запросы, которые их создают и заполняют. Автоматизация — скрипт `getPGQueryWithTempTables.sbsl` (1С:Исполнитель).
6. [6031, 6039] Для пакетных запросов в сборках PostgreSQL с патчем 1С есть расширение `auto_dump`: оно само выгружает таблицы запроса, готовит SQL для переноса данных, сохраняет текст запроса и его план — проблему можно воспроизвести без платформы 1С:Предприятие.
7. [6031, 6039] `auto_dump` по умолчанию выключено. Нужны: строка в `shared_preload_libraries`, `auto_dump.enable = on`, обязательный `auto_dump.output_directory` (каталог, доступный на запись пользователю службы СУБД), перезапуск службы и `CREATE EXTENSION auto_dump` в нужной базе.
8. [6031, 6039] Условия срабатывания `auto_dump`: фрагмент текста запроса (`dump_on_query_string`), отмена запроса со стороны СУБД (`dump_on_cancel`), расхождение ожидаемого и фактического числа строк (`dump_on_bad_plan` вместе с двумя порогами), а в версии 1.1 — ещё длительность запроса (`dump_on_duration`, мс).
9. [6031, 6039] По умолчанию в дамп попадают только временные таблицы, участвующие в запросе. Постоянные таблицы выгружаются только при `auto_dump.dump_persistent_tables = on`.
10. [6039] В `auto_dump` 1.1 изменён смысл нулевого значения порогов bad plan (0 = критерий не срабатывает; в первой версии 0 = критерий считается выполненным всегда), добавлены `dump_on_duration` (по умолчанию -1 — выключено), `data_format` (по умолчанию `copy-stdin`), функции ручного запуска и новый набор файлов дампа.
11. [6039] Функции `auto_dump_immediate(pid)`, `auto_dump_current(pid)`, `auto_dump_next(pid)` доступны только суперпользователю; `auto_dump_immediate` отменяет выполняющийся запрос сессии.
12. [6032] Расширение `pg_wait_sampling` доступно в тех же сборках, что и первая версия `auto_dump`. Подключение: `shared_preload_libraries`, `CREATE EXTENSION pg_wait_sampling`, перезапуск сервера. Даёт представления `pg_wait_sampling_current`, `pg_wait_sampling_history`, `pg_wait_sampling_profile`.
13. [6032] Статистика ожиданий `pg_wait_sampling` лежит в оперативной памяти: профиль нужно периодически сбрасывать (`pg_wait_sampling_reset_profile()`), чтобы не переполнить память.
14. [6011] Если конкретного «плохого» запроса нет, а СУБД медленная в целом — собирать статистику ожиданий (`wait_event_type`, `wait_event` из `pg_stat_activity`) и разбираться с ожиданием, которое чаще всего оказывается наверху.
15. [6011] Для передачи проблемы разработчику выгружают только нужные таблицы (`pg_dump -t ...`). Загружать их надо в базу, созданную средствами 1С:Предприятия, — иначе при восстановлении таблиц будет ошибка.
16. [6011] «Лёгкая» копия базы 1С: отдельно схема (`--schema-only`), отдельно данные служебных таблиц (Config, ConfigSave, Params, DBSchema и т. д.).
17. [6011] Загрузку дампа полезно делать одной транзакцией с остановкой на первой ошибке: `psql -1 ... -v ON_ERROR_STOP=1`.
18. [6011] Журнал PostgreSQL: `log_min_duration_statement = 0` пишет все запросы и при высокой нагрузке может ухудшить производительность; `logging_collector` требует перезапуска; `lc_messages = 'C'` — сообщения на английском.
19. [6011] Данные, вставляемые через `COPY … FROM STDIN` (вставка во временную таблицу из таблицы значений), нигде не логируются, поэтому цепочку по технологическому журналу не собрать — планы таких запросов получают через `auto_explain`. Обязательно задавать `auto_explain.log_min_duration` (в примере `10s`): автоматическое построение планов снижает производительность.
20. [6011] `log_min_messages = debug1…debug5` даёт детальный журнал, но он большой и может замедлить СУБД.
21. [6011] Статистика потребления ресурсов запросами — модуль `pg_stat_statements` (`max = 10000`, `track = 'all'`); в статье дан набор готовых запросов (нагрузка по запросам, cache hit ratio, размеры таблиц и индексов, отсутствие индексов, содержимое буферного кэша).
22. [6011] Чтобы видеть полный текст выполняющегося запроса в `pg_stat_activity`, задать `track_activity_query_size = 1048576` (нужен перезапуск кластера).
23. [6011] Загруженность оборудования смотрят через `atop` (интерактивно, запись в файл, служба) и `nmon`. PID самого нагруженного процесса сопоставляют с полем `dbpid` технологического журнала, с PID в журнале PostgreSQL или с `pg_stat_activity`.
24. [6011] Для расследования долгих запросов можно использовать конфигурацию «Центр управления производительностью» из «Корпоративного инструментального пакета», подключив базу в режиме мониторинга.
25. [4208, 1556] На уровне текста запросов 1С: при медленном соединении с виртуальной таблицей СрезПоследних — вынести обращение к ней в отдельный запрос с временной таблицей; конструкцию ПОЛНОЕ ВНЕШНЕЕ СОЕДИНЕНИЕ при работе с PostgreSQL использовать не рекомендуется.

## 1. Расширение auto_dump в PostgreSQL с патчем от 1С (первая версия)

- Дата публикации: 25.06.2025
- Ссылка: https://its.1c.ru/db/metod8dev/content/6031/hdoc
- Оценка применимости на октябрь 2026: **частично устарело**. Статья описывает первую версию расширения; через полгода вышла версия 1.1 (раздел 3, статья 6039) с другим набором файлов дампа, новыми параметрами и изменённым смыслом нулевых порогов. Для сборок PostgreSQL 16.11-1.1C / 17.7-1.1C / 18.1-2.1C и новее ориентироваться на раздел 3. Этот раздел остаётся верным для сборок, перечисленных ниже (где расширение ещё первой версии), а общий принцип работы и порядок включения не изменились. Пример использует systemd-юнит `postgresql@16-main.service`, то есть привычную для Debian/Ubuntu схему именования кластеров.

### 1.1. Назначение

Расширение предназначено для расследования проблем с пакетными запросами. Оно упрощает получение воспроизводимого примера медленного запроса без участия платформы 1С:Предприятие:

- выгружает таблицы, участвующие в запросе (и временные, и постоянные — по настройке);
- формирует SQL для переноса и подготовки данных на другом стенде;
- сохраняет текст проблемного запроса и его план выполнения.

### 1.2. С каких сборок доступно

Расширение добавлено начиная с версий:

- PostgreSQL 17.5-3.1C
- PostgreSQL 16.9-16.1C
- PostgreSQL 17.4-10.1C
- PostgreSQL 16.8-40.1C

### 1.3. Параметры (первая версия)

Общие:

| Параметр | Тип | По умолчанию | Смысл |
|---|---|---|---|
| `auto_dump.enable` | булево | выключено | Включение расширения. |
| `auto_dump.output_directory` | строка | — (обязателен) | Каталог, куда сохраняются файлы дампов. У пользователя, под которым работает служба СУБД, должны быть права доступа к каталогу. |

Критерии срабатывания:

| Параметр | Тип | По умолчанию | Смысл |
|---|---|---|---|
| `auto_dump.dump_on_query_string` | строка | в источнике не указано | Фрагмент текста SQL; если он встречается в запросе — снимается дамп. |
| `auto_dump.dump_on_cancel` | булево | выключено | Дамп запросов, отменённых со стороны СУБД (например, `pg_cancel_backend` или срабатывание lock timeout). |
| `auto_dump.dump_on_bad_plan` | булево | выключено | Для всех запросов сравнивается ожидаемое и фактическое число строк. Дамп формируется, только если одновременно выполнены оба критерия: `bad_plan_percent_threshold` и `bad_plan_count_threshold`. |
| `auto_dump.bad_plan_count_threshold` | число | 0 | Порог по абсолютной разнице ожидаемого и фактического числа строк; проверяются все узлы плана. Критерий выполнен, если разница больше заданного числа. **При 0 критерий считается выполненным всегда** (в версии 1.1 смысл нуля другой, см. раздел 3). |
| `auto_dump.bad_plan_percent_threshold` | число 0–100 | 0 | Порог по разнице в процентах между ожидаемым и фактическим числом строк; проверяются все узлы плана. **При 0 критерий считается выполненным всегда.** |

⚠ в источнике неясно: формула для `bad_plan_percent_threshold` описана как «отношение суммы ожидаемого и фактического количества строк к ожидаемому количеству строк», которое сравнивается со значением параметра. При этом сам параметр назван порогом «разницы в процентах» и ограничен диапазоном 0–100. Точная формула в статье не приведена — при настройке порога проверять поведение опытным путём.

Объём данных в дампе:

| Параметр | Тип | По умолчанию | Смысл |
|---|---|---|---|
| `auto_dump.dump_temporary_tables` | булево | включено | Добавлять временные таблицы сессии, участвующие в текущем запросе. |
| `auto_dump.dump_persistent_tables` | булево | выключено | Добавлять все постоянные таблицы, участвующие в текущем запросе. |
| `auto_dump.dump_all_temp_tables` | булево | выключено | Добавлять все временные таблицы сессии (включая участвующие в текущем запросе). |
| `auto_dump.dump_data` | булево | включено | Записывать содержимое таблиц. Если выключено — в SQL будет только создание таблиц, без заполнения. |
| `auto_dump.dump_indexes` | булево | включено | Записывать создание индексов выгружаемых таблиц. |
| `auto_dump.dump_query` | булево | включено | Формировать файл с SQL-запросом, для которого снят дамп. |
| `auto_dump.dump_create` | булево | включено | Формировать файл с командами создания выгружаемых таблиц. |
| `auto_dump.dump_plan` | булево | включено | Формировать файл с планом выполнения текущего запроса. |

### 1.4. Включение расширения

1. Добавить библиотеку в `postgresql.conf`:

```ini
shared_preload_libraries = 'auto_dump'
```

(исправлено по смыслу: в источнике значение взято в типографские кавычки ‘…’, в конфигурационном файле нужны обычные одинарные.)

2. Описать там же нужные параметры `auto_dump.*`.
3. Перезапустить службу СУБД.
4. Подключиться через `psql` к нужной базе и создать расширение в ней:

```text
$ psql -h localhost -U postgres -d myDB
myDB=# CREATE EXTENSION auto_dump;
```

### 1.5. Пример использования

Исходные данные: из технологического журнала (событие DBPOSTGRS) получен текст запроса:

```sql
SELECT
T3._Q_001_F_000RRef,
T3._Q_001_F_001,
T1._Q_001_F_002,
T1._Q_001_F_001RRef,
T2._Fld23
FROM pg_temp.tt3 T1
LEFT OUTER JOIN _Reference7X1 T2
ON (T1._Q_001_F_001RRef = T2._IDRRef)
INNER JOIN pg_temp.tt2 T3
ON (T1._Q_001_F_000RRef = T3._Q_001_F_000RRef)
```

Шаг 1. В `postgresql.conf` добавлены строки (кавычки исправлены по смыслу):

```ini
shared_preload_libraries = 'auto_dump'
auto_dump.enable = on
auto_dump.output_directory = '/tmp/auto_d'
auto_dump.dump_on_query_string = 'LEFT OUTER JOIN _Reference7X1'
```

Шаг 2. Перезапуск службы PostgreSQL:

```bash
sudo systemctl restart postgresql@16-main.service
```

Шаг 3. Создание расширения в базе (в примере база называется `auto_d`):

```text
$ psql -h localhost -U postgres -d auto_d
auto_d=# create extension auto_dump;
CREATE EXTENSION
```

Шаг 4. Пользователь 1С выполняет действие, которое порождает проблемный запрос. В каталоге `/tmp/auto_d` появляется подкаталог. Формат имени в тексте статьи описан как «PIDПроцесса-ГГГГ-ММ-ДД-ЧЧ-ММ-СС-ПорядковыйНомер», фактически в примере компоненты даты и времени разделены подчёркиваниями:

```text
/tmp/auto_d/71491-2025_06_11_12_42_36_00$ ls -l
-rw------- 1 postgres postgres 3241 июн 11 12:42 create.sql
-rw------- 1 postgres postgres 6743 июн 11 12:42 createwithdata.sql
```

То есть в первой версии формируются два файла, владелец — `postgres`, права — только для владельца.

Файл `create.sql` — создание таблиц и индексов без данных, затем в комментариях текст запроса и два плана:

```sql
CREATE TEMPORARY TABLE tt3 (
    _q_001_f_000rref bytea,
    _q_001_f_001rref bytea,
    _q_001_f_002 numeric(22,2)
);

CREATE INDEX tmpind_1 ON pg_temp.tt3 USING btree (_q_001_f_000rref);

ANALYZE tt3;

CREATE TEMPORARY TABLE tt2 (
    _q_001_f_000rref bytea,
    _q_001_f_001 numeric(16,2)
);

CREATE INDEX tmpind_0 ON pg_temp.tt2 USING btree (_q_001_f_000rref);

ANALYZE tt2;

/*
<текст исходного запроса, завершённый точкой с запятой>
*/
/*
Query Text: <текст запроса>
Hash Join  (cost=8.01..9.51 rows=22 width=79)
  Hash Cond: (t1._q_001_f_000rref = t3._q_001_f_000rref)
  ->  Hash Left Join  (cost=6.76..8.01 rows=22 width=72)
        Hash Cond: (t1._q_001_f_001rref = t2._idrref)
        ->  Seq Scan on tt3 t1  (cost=0.00..1.22 rows=22 width=40)
        ->  Hash  (cost=6.36..6.36 rows=36 width=64)
              ->  Seq Scan on _reference7x1 t2  (cost=0.00..6.36 rows=36 width=64)
  ->  Hash  (cost=1.12..1.12 rows=12 width=24)
        ->  Seq Scan on tt2 t3  (cost=0.00..1.12 rows=12 width=24)
*/
/*
Query Text: <текст запроса>
Hash Join  (cost=8.01..9.51 rows=22 width=79) (actual time=0.027..0.037 rows=22 loops=1)
  Output: t3._q_001_f_000rref, t3._q_001_f_001, t1._q_001_f_002, t1._q_001_f_001rref, t2._fld23
  Hash Cond: (t1._q_001_f_000rref = t3._q_001_f_000rref)
  Buffers: shared hit=6, local hit=2
  ... (остальные узлы плана с actual time, Output, Buffers — сокращено в конспекте)
Settings: enable_mergejoin = 'off', cpu_operator_cost = '0.001'
*/
```

Что видно из примера:

- первый план в комментарии — оценочный (только cost/rows), второй — с фактическими показателями (actual time, Output, Buffers) и строкой `Settings`, в которой видны параметры сеанса платформы (`enable_mergejoin = 'off'`, `cpu_operator_cost = '0.001'`);
- после каждой таблицы идёт `ANALYZE`;
- в выгрузку попали только временные таблицы `tt3` и `tt2`: параметр `dump_persistent_tables` в примере не включали, поэтому постоянная `_Reference7X1` не выгружена;
- отдельных файлов запроса и плана в примере нет — текст запроса и планы находятся в комментариях внутри обоих файлов.

Файл `createwithdata.sql` — то же самое, но между созданием индекса и `ANALYZE` для каждой таблицы добавлена вставка данных командой `INSERT … VALUES` (значения `bytea` записаны как `E'\\x…'`). Фрагмент:

```sql
CREATE TEMPORARY TABLE tt3 (
    _q_001_f_000rref bytea,
    _q_001_f_001rref bytea,
    _q_001_f_002 numeric(22,2)
);

CREATE INDEX tmpind_1 ON pg_temp.tt3 USING btree (_q_001_f_000rref);

INSERT INTO tt3 (_q_001_f_000rref, _q_001_f_001rref, _q_001_f_002) VALUES
    (E'\\x8ca0000d8843cd1b11dc8d043d710079',E'\\x8ca1000d8843cd1b11dc8ea92d97a749',36960.00),
    -- ... остальные строки
    (E'\\x8ca1000d8843cd1b11dc8ea92d97a74a',E'\\x8ca1000d8843cd1b11dc8ea92d97a749',123750.00);

ANALYZE tt3;

-- аналогично для tt2: CREATE TEMPORARY TABLE, CREATE INDEX tmpind_0, INSERT INTO tt2 (...) VALUES ..., ANALYZE tt2;
-- далее те же три блока комментариев: текст запроса, оценочный план, план с фактическими показателями
```

## 2. Расширение pg_wait_sampling в PostgreSQL с патчем от 1С

- Дата публикации: 25.06.2025
- Ссылка: https://its.1c.ru/db/metod8dev/content/6032/hdoc
- Оценка применимости на октябрь 2026: **актуально**. Статья свежая, относится к сборкам PostgreSQL 16/17 с патчем 1С. Материал краткий: описаны только подключение, три представления и сброс профиля; структура столбцов представлений и настройки расширения в статье не приводятся.

### 2.1. С каких сборок доступно

Расширение добавлено для расследования проблем производительности начиная с версий:

- PostgreSQL 17.5-3.1C
- PostgreSQL 16.9-16.1C
- PostgreSQL 17.4-10.1C
- PostgreSQL 16.8-40.1C

### 2.2. Установка

Порядок действий в источнике именно такой:

1. Добавить расширение в переменную `shared_preload_libraries` файла `postgresql.conf`:

```ini
shared_preload_libraries = 'pg_wait_sampling'
```

2. Выполнить в базе:

```sql
CREATE EXTENSION pg_wait_sampling;
```

3. Перезапустить сервер PostgreSQL.

### 2.3. Что появляется после запуска сервера

| Представление | Что показывает | Где хранится |
|---|---|---|
| `pg_wait_sampling_current` | Текущие события ожидания по всем процессам, включая фоновые рабочие процессы | — |
| `pg_wait_sampling_history` | История событий ожидания | Кольцевой буфер в памяти |
| `pg_wait_sampling_profile` | Профиль событий ожидания | Хеш-таблица в памяти |

### 2.4. Примеры использования

```sql
-- 1) все текущие ожидания
SELECT * FROM pg_wait_sampling_current;

-- 2) текущие ожидания одного процесса: функции передаётся идентификатор процесса (вместо pid подставить число)
SELECT * FROM pg_wait_sampling_get_current(pid);

-- 3) динамика недавних ожиданий — история
SELECT * FROM pg_wait_sampling_history;

-- 4) ожидания в базе данных за длительное время — профиль
SELECT * FROM pg_wait_sampling_profile;

-- 5) сброс профиля
SELECT pg_wait_sampling_reset_profile();
```

(исправлено по смыслу: в источнике в пункте 5 приведён только вызов `pg_wait_sampling_reset_profile();` без `SELECT`.)

Предупреждение авторов к пункту 5: статистика ожиданий хранится в оперативной памяти, поэтому профиль нужно время от времени очищать — иначе возможно переполнение памяти.

См. также раздел 4.11 — мониторинг ожиданий скриптами через `pg_stat_activity` (статья 6011, опубликована раньше, чем появилось это расширение).

## 3. Расширение auto_dump 1.1 в PostgreSQL с патчем от 1С

- Дата публикации: 25.12.2025
- Ссылка: https://its.1c.ru/db/metod8dev/content/6039/hdoc
- Оценка применимости на октябрь 2026: **актуально**. Самая свежая статья темы, описывает действующую версию расширения для PostgreSQL 16/17/18 с патчем 1С. Заменяет раздел 1 для сборок, перечисленных ниже, и более новых.
- **Внимание (19.10.2026):** это `auto_dump` сборки PostgreSQL **с патчами 1С**. В сборке Postgres Pro «PostgreSQL для 1С» (стоит у пользователя) документация 16-й ветки описывает другой набор параметров:
  - `auto_dump.dump_on_time` + `auto_dump.timeout` вместо `dump_on_duration`;
  - `auto_dump.dump_copy_data` вместо `data_format`;
  - функций ручного запуска нет;
  - нулевые пороги bad plan — «срабатывать всегда».
  
  Сравнение — `../guides/07-postgresql-dlya-1c-s-1c-postgres-ru.md`, разд. 8.7. Параметры для своего сервера сверять по `pg_settings`.

### 3.1. Что это и где доступно

Расширение `auto_dump` обновлено до версии 1.1 начиная с версий:

- PostgreSQL 16.11-1.1C
- PostgreSQL 17.7-1.1C
- PostgreSQL 18.1-2.1C

Назначение прежнее — расследование проблем с пакетными запросами: расширение выгружает таблицы запроса (временные и, по настройке, постоянные), формирует SQL для переноса и подготовки данных, сохраняет проблемный запрос и его план, чтобы воспроизвести медленное выполнение без платформы 1С:Предприятие.

### 3.2. Чем версия 1.1 отличается от первой (сводка по сравнению статей 6031 и 6039)

| Что | Первая версия (раздел 1) | Версия 1.1 |
|---|---|---|
| Права на `output_directory` | «права на доступ» к каталогу | права **на запись** в каталог |
| `bad_plan_count_threshold = 0`, `bad_plan_percent_threshold = 0` | критерий считается выполненным всегда | критерий срабатывать не будет |
| Срабатывание по длительности | нет | `auto_dump.dump_on_duration` (мс) |
| Формат данных в дампе | `INSERT … VALUES` (по примеру) | настраивается `auto_dump.data_format`: `insert`, `copy-file`, `copy-stdin` (по умолчанию) |
| Ручной запуск | нет | функции `auto_dump_immediate`, `auto_dump_current`, `auto_dump_next` |
| Файлы дампа | `create.sql`, `createwithdata.sql` (запрос и планы — в комментариях) | отдельные файлы: `query.sql`, `create_persistent.sql`, `create_temporary.sql`, `insert_persistent.sql`, `insert_temporary.sql`, `plan_explain.txt`, `plan_analyze.txt`, `readme.txt`, при `copy-file` — `table-<имя>.txt` |

### 3.3. Параметры (версия 1.1)

Общие:

| Параметр | Тип | По умолчанию | Смысл |
|---|---|---|---|
| `auto_dump.enable` | булево | выключено | Включение расширения. |
| `auto_dump.output_directory` | строка | — (обязателен) | Каталог для файлов дампов. Пользователь, под которым запущена служба СУБД, должен иметь право записи в него. |

Критерии срабатывания:

| Параметр | Тип | По умолчанию | Смысл |
|---|---|---|---|
| `auto_dump.dump_on_query_string` | строка | в источнике не указано | Фрагмент текста SQL; при его наличии в запросе снимается дамп. |
| `auto_dump.dump_on_cancel` | булево | выключено | Дамп запросов, отменённых СУБД (например, `pg_cancel_backend`, lock timeout). |
| `auto_dump.dump_on_bad_plan` | булево | выключено | Сравнение ожидаемого и фактического числа строк для всех запросов. Дамп — только при одновременном выполнении двух критериев: `bad_plan_percent_threshold` и `bad_plan_count_threshold`. |
| `auto_dump.bad_plan_count_threshold` | число | 0 | Порог по абсолютной разнице ожидаемого и фактического числа строк; проверяются все узлы плана; критерий выполнен, если разница больше заданного числа. **При 0 критерий срабатывать не будет.** |
| `auto_dump.bad_plan_percent_threshold` | число 0–100 | 0 | Порог по разнице в процентах; проверяются все узлы плана. **При 0 критерий срабатывать не будет.** |
| `auto_dump.dump_on_duration` | число, мс | -1 | Порог по времени выполнения запроса в миллисекундах. `0` — дампы формируются для всех запросов; `-1` — критерий не срабатывает. |

⚠ в источнике неясно: формула `bad_plan_percent_threshold` сформулирована так же, как в первой версии («отношение суммы ожидаемого и фактического количества строк к ожидаемому» сравнивается с параметром) — точная формула не приведена.

Следствие из описания: поскольку для срабатывания `dump_on_bad_plan` должны выполниться оба критерия, а нулевой порог в версии 1.1 означает «не срабатывает», при включении `dump_on_bad_plan` нужно задать ненулевые значения обоих порогов. Прямо в статье это не сказано — вывод из описаний параметров, проверять на стенде.

Объём данных в дампе:

| Параметр | Тип | По умолчанию | Смысл |
|---|---|---|---|
| `auto_dump.dump_temporary_tables` | булево | включено | Временные таблицы сессии, участвующие в текущем запросе. |
| `auto_dump.dump_persistent_tables` | булево | выключено | Все постоянные таблицы, участвующие в текущем запросе. |
| `auto_dump.dump_all_temp_tables` | булево | выключено | Все временные таблицы сессии, включая участвующие в текущем запросе. |
| `auto_dump.dump_data` | булево | включено | Содержимое таблиц. Если выключено — только создание таблиц, без заполнения. |
| `auto_dump.dump_indexes` | булево | включено | Создание индексов выгружаемых таблиц. |
| `auto_dump.dump_query` | булево | включено | Файл с SQL-запросом, для которого снят дамп. |
| `auto_dump.dump_create` | булево | включено | Файл с командами создания выгружаемых таблиц. |
| `auto_dump.dump_plan` | булево | включено | Файл с планом выполнения текущего запроса. |
| `auto_dump.data_format` | строка | `copy-stdin` | Формат сохранения данных, см. ниже. |

Значения `auto_dump.data_format`:

- `insert` — данные записываются как запрос `INSERT`;
- `copy-file` — данные выносятся в отдельный файл с именем вида `table-имя_таблицы.txt`, а в SQL-файл помещается служебная команда psql `\copy`. Режим работает только с psql-совместимыми утилитами; выполнять SQL нужно из каталога с дампом;
- `copy-stdin` — данные в формате `COPY FROM stdin`, как у утилиты `pg_dump`. Значение по умолчанию.

### 3.4. Включение расширения

Порядок тот же, что в первой версии:

```ini
shared_preload_libraries = 'auto_dump'
```

(кавычки исправлены по смыслу: в источнике типографские ‘…’.)

Далее описать нужные параметры `auto_dump.*`, перезапустить службу СУБД, подключиться к базе через `psql` и создать расширение:

```text
$ psql -h localhost -U postgres -d myDB
myDB=# CREATE EXTENSION auto_dump;
```

### 3.5. Функции ручного формирования дампов

Выполнять их может только пользователь с ролью superuser. Аргумент `pid` — число, идентификатор сессии.

| Функция | Действие |
|---|---|
| `auto_dump_immediate(pid)` | **Отменяет** запрос, выполняемый сессией `pid`, и затем снимает дамп. |
| `auto_dump_current(pid)` | Снимает дамп после завершения запроса, который сейчас выполняется в сессии `pid`. |
| `auto_dump_next(pid)` | Снимает дамп следующего запроса в сессии `pid`. |

Различие, следующее из описаний: `auto_dump_immediate` прерывает выполняющийся запрос, две другие функции запрос не отменяют (дамп снимается по завершении текущего либо на следующем запросе).

### 3.6. Файлы дампа

При автоматическом срабатывании по любому критерию или при ручном запуске в каталоге `output_directory` создаётся подкаталог. Формат имени в тексте: «PIDПроцесса-ГГГГ-ММ-ДД-ЧЧ-ММ-СС-ПорядковыйНомер»; в примере компоненты даты и времени разделены подчёркиваниями (`67748-2025_12_02_17_21_48_00`).

| Файл | Содержимое | От каких параметров зависит наличие |
|---|---|---|
| `query.sql` | Текст запроса, для которого делается дамп | `dump_query` |
| `create_persistent.sql` | Команды создания постоянных таблиц и (или) индексов | `dump_create`, `dump_indexes`, `dump_persistent_tables` |
| `create_temporary.sql` | Команды создания временных таблиц и (или) индексов | `dump_create`, `dump_indexes`, `dump_all_temp_tables`, `dump_temporary_tables` |
| `insert_persistent.sql` | Команды заполнения постоянных таблиц | `dump_data`, `dump_persistent_tables` |
| `insert_temporary.sql` | Команды заполнения временных таблиц | `dump_data`, `dump_all_temp_tables`, `dump_temporary_tables` |
| `plan_explain.txt` | План запроса в формате вывода `EXPLAIN` | `dump_plan` |
| `plan_analyze.txt` | План запроса в формате вывода `EXPLAIN (ANALYZE, BUFFERS, SETTINGS)` | `dump_plan` |
| `table-<имя_таблицы>.txt` | Данные таблиц | только при `auto_dump.data_format = "copy-file"` |
| `readme.txt` | Примеры использования перечисленных файлов | — |

### 3.7. Пример использования

Из технологического журнала (событие DBPOSTGRS) получен запрос:

```sql
SELECT
T1._Q_001_F_000RRef,
T1._Q_001_F_001RRef,
T1._Q_001_F_002,
T2._Fld32
FROM pg_temp.tt1 T1
LEFT OUTER JOIN _Reference8 T2
ON (T1._Q_001_F_000RRef = T2._IDRRef)
```

Шаг 1. Строки в `postgresql.conf` (кавычки исправлены по смыслу); в отличие от примера первой версии здесь включена выгрузка постоянных таблиц:

```ini
shared_preload_libraries = 'auto_dump'
auto_dump.enable = on
auto_dump.output_directory = '/tmp/auto_d'
auto_dump.dump_on_query_string = 'LEFT OUTER JOIN _Reference8'
auto_dump.dump_persistent_tables = on
```

Шаг 2. Перезапуск службы:

```bash
sudo systemctl restart postgresql@16-main.service
```

Шаг 3. Создание расширения в базе `auto_d`:

```text
$ psql -h localhost -U postgres -d auto_d
auto_d=# create extension auto_dump;
CREATE EXTENSION
```

Шаг 4. Пользователь 1С выполняет действие с проблемным запросом; в `/tmp/auto_d` появляется подкаталог:

```text
/tmp/auto_d/67748-2025_12_02_17_21_48_00$ ls -l
-rw-rw-r-- 1 postgres postgres 1241 дек  2 14:26 create_persistent.sql
-rw-rw-r-- 1 postgres postgres  120 дек  2 14:26 create_temporary.sql
-rw-rw-r-- 1 postgres postgres 4876 дек  2 14:26 insert_persistent.sql
-rw-rw-r-- 1 postgres postgres 3322 дек  2 14:26 insert_temporary.sql
-rw-rw-r-- 1 postgres postgres 1151 дек  2 14:26 plan_analyze.txt

$ psql -h localhost -U postgres -d testDB
testDB=# \i create_persistent.sql;
testDB=# \i insert_persistent.sql;
testDB=# \i create_temporary.sql;
testDB=# \i insert_temporary.sql;
testDB=# \i query.sql;
```

## 4. Методика расследования проблем производительности на уровне работы СУБД PostgreSQL

- Дата публикации: 21.02.2023 (рубрика «Технологические вопросы крупных решений»)
- Ссылка: https://its.1c.ru/db/metod8dev/content/6011/hdoc
- Оценка применимости на октябрь 2026: **актуально (с мелкими оговорками)**. Статья написана для Linux (apt, systemd, psql), приёмы не привязаны к устаревшим версиям: запросы используют современное имя столбца `total_exec_time` в `pg_stat_statements`, план выводится в современном формате (Planning Time / Execution Time). Оговорки:
  - примеры относятся к состоянию на 2022–2023 годы: платформа 8.3.22.1851 и каталог `/opt/1cv8/e2k/...` (подставлять свой путь установки платформы), файлы atop с датами 2022 года; имя переменной в `/etc/default/atop` и расположение `atop.daily` сверять со своей версией пакета atop;
  - после выхода статьи в сборках PostgreSQL с патчем 1С появились расширения `auto_dump` (разделы 1 и 3) и `pg_wait_sampling` (раздел 2), которые предназначены для тех же задач, что ручной сбор цепочки временных таблиц и скрипты мониторинга ожиданий из этой статьи. Сама статья 6011 об этих расширениях не упоминает (она вышла раньше); ручные способы нужны там, где расширений нет;
  - порядок «изменить параметр → `pg_reload_conf()` либо перезапуск» воспроизведён как в источнике; для каждого параметра сверять по документации PostgreSQL, применяется ли он перечитыванием конфигурации или только перезапуском;
  - в текстовой копии источника не сохранились скриншоты (разделы про ЦУП, nmon, поиск нагруженного процесса), поэтому там остались только общие указания.

Содержание статьи: предварительная оценка → технологический журнал → выгрузка данных для воспроизведения (только нужные таблицы; «лёгкая» копия) → журнал PostgreSQL (запросы, планы, отладка) → статистика исполнения запросов и полезные запросы → запрос, выполняющийся сейчас → Центр управления производительностью → мониторинг ожиданий → загруженность оборудования (atop, nmon) → какой запрос нагружает оборудование.

### 4.1. Предварительная оценка

Цель — быстро понять, какую долю общего времени работы занимают запросы к СУБД. Собирается технологический журнал, в который попадают все события, но без свойств (элемент `<property>` намеренно не указывается). Фрагмент настройки из источника (каталог записан как в статье — `/var/logs/all_mini`):

```xml
<log location="/var/logs/all_mini" history="8">
  <event>
    <ne property="Name" value=""/>
  </event>
</log>
```

Подсчёт суммарной длительности по каждому типу события (первый `awk` отрезает метку времени до дефиса, второй суммирует длительность по имени события):

```bash
cat rphost_*/*.log | awk -F\- '{print $2}' | awk -F\, '{sum[$2]+=$1;} END {for (event in sum) print event" - "sum[event];}'
```

Пример результата из статьи:

```text
DBPOSTGRS - 22189998668
CALL      - 33908470608
TLOCK     - 114341600
...
DBPOSTGRS / CALL = ~0,65
```

Интерпретация: отношение суммарного времени DBPOSTGRS к суммарному времени CALL показывает, какую часть времени серверных вызовов занимают запросы. **Порог: если доля больше примерно 50 % — нужно разбираться со скоростью выполнения запросов.**

### 4.2. Технологический журнал: получение запроса и его плана

Настройка сбора событий DBPOSTGRS со всеми свойствами (`logcfg.xml`):

```xml
<?xml version="1.0"?>
<config xmlns="http://v8.1c.ru/v8/tech-log">
  <log location="/var/log/srv1cv83" history="4">
    <event>
      <eq property="Name" value="DBPOSTGRS"/>
    </event>
    <property name="all"/>
  </log>
</config>
```

Предупреждения авторов:

- такой журнал может занимать значительный объём на диске;
- настройку `<plansql/>` нельзя применять на продуктивных серверах — только на серверах тестирования или разработки.

Как получить план без `<plansql/>`: выполнить запрос непосредственно на сервере PostgreSQL с командой `EXPLAIN`. Платформа «1С:Предприятие» при соединении с PostgreSQL устанавливает собственные параметры сеанса — их тоже нужно задать перед выполнением запроса, чтобы план совпал с платформенным. Рекомендуемая техника: сложить команды и текст запроса в файл, выполнить его из командной строки и перенаправить вывод в файл.

Пример события из технологического журнала (сокращено; важны поля `dbpid` и `Sql`):

```text
38:31.223006-1,DBPOSTGRS,5,process=rphost,p:processName=DATABASE,...,SessionID=2,...,dbpid=11988,Sql="SELECT
T1._IDRRef,
...
FROM _Document1337 T1
WHERE ...",RowsAffected=1,Result=PGRES_TUPLES_OK,Context='Форма.Вызов : ВыполнитьЗапросСервер…
```

Файл `query.sql` — параметры соединения платформы плюс запрос под `EXPLAIN ANALYZE VERBOSE`:

```sql
/* Параметры соединения платформы */
SET client_min_messages=error;
SET lc_messages to 'en_US.UTF-8';
SET enable_mergejoin = off;
SET escape_string_warning = off;
SET cpu_operator_cost = 0.001;
set client_encoding = 'utf8';
SET lock_timeout = 20000;

EXPLAIN ANALYZE VERBOSE -- Получение актуального плана запроса
SELECT
  T1._IDRRef,
  T1._Number,
  T1._Date_Time,
  T1._Fld30743RRef
FROM _Document1337 T1
WHERE ((T1._Fld2830 = CAST(0 AS NUMERIC))) AND (T1._IDRRef = '\\200\\310p\\213\\315U\\034~\\021\\347\\025\\340@\\243\\3650'::bytea)
```

Выполнение и просмотр результата:

```bash
psql -U postgres --dbname=DATABASE --file=query.sql > query.sqlplan
cat query.sqlplan
```

Вывод из статьи (по утверждению авторов, это актуальный план, идентичный платформенному):

```text

   Output: _idrref, _number, _date_time, _fld30743rref
   Index Cond: ((t1._fld2830 = '0'::numeric) AND (t1._idrref = '\x5c3230305c333130705c3231335c333135555c3033347e5c3032315c3334375c3032355c333430405c3234335c33363530'::bytea))

```

⚠ в источнике неясно: в этом выводе фактическое число строк `rows=0`, хотя в событии журнала `RowsAffected=1`, а значение `bytea` в `Index Cond` — это шестнадцатеричная запись самого текста escape-последовательностей (`5c 32 30 30` = символы `\200`), а не байтов ссылки. Статья это расхождение никак не комментирует.

**Запросы с временными таблицами.** Сложность в том, что нужно найти и собрать все запросы, заполняющие эти таблицы, — они расположены выше исследуемого запроса по журналу. Пример собранного файла `query.sql`:

```sql
SET client_min_messages=error;
SET lc_messages to 'en_US.UTF-8';
SET enable_mergejoin = off;
SET escape_string_warning = off;
SET cpu_operator_cost = 0.001;
set client_encoding = 'utf8';
SET lock_timeout = 20000;

-- запрос использует временную таблицу, необходимо ее создать и заполнить перед его выполнением
drop table if exists tt7 cascade;
create temporary table tt7 (_Q_000_F_000RRef bytea ) without oids;
drop index if exists tmpind_0;
create index tmpind_0 on pg_temp.tt7(_Q_000_F_000RRef);

INSERT INTO pg_temp.tt7 (_Q_000_F_000RRef) SELECT
  T1._IDRRef
FROM _Document1017 T1
WHERE (T1._Fld2830 = CAST(0 AS NUMERIC))
;

ANALYZE pg_temp.tt7;

EXPLAIN ANALYZE VERBOSE -- Получение актуального плана запроса
SELECT
  (T1._Fld30691_TYPE || T1._Fld30691_RTRef),
  T1._IDRRef
FROM _Document1337 T1
INNER JOIN pg_temp.tt7 T2 -- временная таблица
ON ('\\010'::bytea = T1._Fld30691_TYPE AND '\\000\\000\\003\\371'::bytea = T1._Fld30691_RTRef AND T2._Q_000_F_000RRef = T1._Fld30691_RRRef)
WHERE ((T1._Fld2830 = CAST(0 AS NUMERIC))) AND ((((T1._Fld30691_TYPE || T1._Fld30691_RTRef) <> '\\010\\000\\000\\004\\021'::bytea)))
```

Структура такого файла: параметры сеанса платформы → `drop/create temporary table` → `drop/create index` → `INSERT … SELECT` заполнения → `ANALYZE` временной таблицы → исследуемый запрос под `EXPLAIN ANALYZE VERBOSE`.

Чтобы не собирать цепочку вручную, авторы предлагают скрипт на языке 1С:Исполнитель `getPGQueryWithTempTables.sbsl`: он формирует файл (или выводит в консоль) со всей цепочкой временных таблиц, нужных для выполнения запроса; в конце вывода скрипт также даёт готовую команду `pg_dump` (см. 4.3). ⚠ в текстовой копии источника ссылка на скачивание скрипта не сохранилась.

### 4.3. Выгрузка данных для воспроизведения проблемы

#### Выгрузка только необходимых данных

Ситуация: разработчику нужно передать «плохой» запрос вместе с данными, чтобы воспроизвести проблему на другом сервере (например, под отладкой), а передать всю базу трудно или невозможно. Решение — выгрузить только те таблицы, из которых строятся запрос и его временные таблицы. Пример для таблиц `_AccumRg1`, `_Reference2`, `_Reference3`:

```bash
pg_dump -h server -U postgres -Fp -b -v -t _AccumRg1 -t _Reference2 -t _Reference3 -d ИМЯБАЗЫ -f /tmp/tables.backup
```

Если цепочка временных таблиц длинная или таблиц в запросе много, список проще получить скриптом. На вход — файл с текстом «плохого» запроса и подготовкой всех его временных таблиц (`bad_query.sql`); на выходе — текст готовой команды `pg_dump` только для нужных таблиц:

```bash
cat bad_query.sql | grep -oP "(^|\s)_[a-zA-Z]+[0-9]+(_[a-zA-Z0-9]+)?" | grep -vP '^\s+_Fld.*' | grep -vP "_LineNo[0-9]+" | sort | uniq | tr -s '\n' '$' | sed 's/ //g' | sed 's/$$//' | sed 's/\$/ -t /g' | sed 's/\$$//g' | xargs -i echo pg_dump -h server -U postgres -Fp -O -t '{}' -f tables.backup [имя_базы]
```

Скрипт команду только печатает (через `echo`), сам дамп не запускает. Если текст запроса собирался скриптом `getPGQueryWithTempTables.sbsl`, команда `pg_dump` уже будет в конце сформированного файла (или вывода в консоль).

**Важное условие загрузки.** Новую базу для загрузки выгруженных таблиц нужно создать на PostgreSQL средствами 1С:Предприятия — иначе при восстановлении таблиц из бэкапа будет ошибка. Создание базы и загрузка (путь и версия платформы — из примера статьи; `DBPwd=postgres` — учебное значение пароля, подставлять своё):

```bash
/opt/1cv8/e2k/8.3.22.1851/1cv8 CREATEINFOBASE Srvr=server\;Ref=ИМЯБАЗЫ\;SchJobDn=Y\;SQLSrvr=СЕРВЕРБД\;DBMS=PostgreSQL\;DB=ИМЯБАЗЫ\;DBUID=postgres\;DBPwd=postgres\;CrSQLDB=Y\;
psql -h server -U postgres -d ИМЯБАЗЫ -1 -f /tmp/tables.backup -v ON_ERROR_STOP=1
```

#### «Лёгкая» копия

Задача: выгрузить базу 1С:Предприятия так, чтобы в ней были полная структура таблиц (без данных), конфигурация и данные только части таблиц.

Шаг 1 — схема данных:

```bash
pg_dump -h server -U postgres --schema-only --dbname=ИМЯБАЗЫ --format=p > schema.sql
```

Шаг 2 — данные нужных таблиц (в примере — служебные таблицы платформы; строки, начинающиеся с `users.usr`, из вывода вырезаются):

```bash
pg_dump -h server -U postgres --format=p -b --dbname=ИМЯБАЗЫ --clean --if-exists -t _YearOffset -t Config -t ConfigCAS -t ConfigCASSave -t ConfigSave -t DBSchema -t DepotFiles -t Files -t IBVersion -t Params -t SchemaStorage | sed '/^users[.]usr/d' > data.sql
```

Восстановление — в два шага:

```bash
psql -h server -U postgres --dbname=ИМЯБАЗЫ < schema.sql
psql -h server -U postgres --dbname=ИМЯБАЗЫ < data.sql
```

#### Полная выгрузка в простом (plain) формате

Без разделения на схему и данные:

```bash
pg_dump -h server -U postgres -d ИМЯБАЗЫ -f database.sql -Fp
```

(исправлено по смыслу: в источнике имя базы слиплось с ключом — «ИМЯБАЗЫ-f».)

Восстановление одним шагом:

```bash
psql -U postgres -h server -d ИМЯБАЗЫ -f database.sql
```

Вариант с загрузкой в одной транзакции и контролем ошибок (остановка на первой же ошибке):

```bash
psql -U postgres -h server -d ИМЯБАЗЫ -1 -f database.sql -v ON_ERROR_STOP=1
```

### 4.4. Журнал PostgreSQL

Запросы можно собирать прямо в журнале PostgreSQL. Настройка через `psql`:

```sql
ALTER SYSTEM SET lc_messages = 'C'; -- все сообщения на английском языке
ALTER SYSTEM SET logging_collector = on; -- потребуется перезапуск сервера
ALTER SYSTEM SET log_directory = 'log';
ALTER SYSTEM SET log_min_duration_statement = 0; -- 0-все запросы. ВНИМАНИЕ. Сбор всех запросов может ухудшить производительность при высокой нагрузке.
ALTER SYSTEM SET log_duration = on;
```

Затем перезапустить кластер любым способом (pg_ctl / pg_ctlcluster / systemd / service / ...). После этого в каталоге кластера, в папке `log`, появится текстовый файл с запросами.

Приведение журнала PostgreSQL к однострочному виду (каждое событие — одна строка; переносы внутри события заменяются на `<line>`):

```bash
cat postgresql.log | awk -vORS= '{if(match($0, "^[0-9][0-9][0-9][0-9]-[0-9][0-9]-[0-9][0-9] ")) print "\n"$0; else print "<line>"$0;}'
```

### 4.5. Планы запросов в журнале PostgreSQL (auto_explain)

Когда это нужно: при вставке во временную таблицу из таблицы значений платформа использует конструкцию `COPY … FROM STDIN`. Вставляемые так данные нигде не логируются, поэтому восстановить цепочку запросов по технологическому журналу не получится. Тогда планы пишут в журнал PostgreSQL модулем `auto_explain`.

Шаг 1. Узнать текущее значение `shared_preload_libraries`:

```sql
SELECT current_setting('shared_preload_libraries');
```

Шаг 2. Дописать к уже подключённым модулям `auto_explain` (потребуется перезапуск кластера):

```sql
ALTER SYSTEM SET shared_preload_libraries = '<модуль1>', '<модуль2>',…, 'auto_explain';
```

Шаг 3. Перезапустить кластер.

Шаг 4. Настроить модуль и применить настройки:

```sql
ALTER SYSTEM SET auto_explain.log_min_duration = '10s'; -- записывать в лог план для запросов >= 10 сек.

ALTER SYSTEM SET auto_explain.log_analyze = true;

SELECT pg_reload_conf(); -- применение настроек
```

(в источнике комментарий к первой команде разорван переносом строки — склеено по смыслу.)

Предупреждение авторов: автоматическое построение планов снижает производительность системы, поэтому параметр `auto_explain.log_min_duration` задавать обязательно — чтобы получать планы только длительных запросов.

### 4.6. Отладочная информация в журнале PostgreSQL

Для более детальной информации о работе PostgreSQL включается отладочный уровень сообщений:

```sql
ALTER SYSTEM SET log_min_messages = 'debug2'; -- debug1...debug5

SELECT pg_reload_conf(); -- применение настроек
```

Предупреждение авторов: такой журнал занимает значительный объём и может привести к замедлению СУБД.

### 4.7. Статистика исполнения запросов (pg_stat_statements)

Назначение: получить статистику потребления ресурсов запросами — процессор, диск, буферный пул, количество исполнений и т. д. Для этого подключается модуль `pg_stat_statements`.

Шаг 1. Добавить модуль в `shared_preload_libraries` (многоточие — уже подключённые модули):

```sql
ALTER SYSTEM SET shared_preload_libraries = …, 'auto_explain', 'pg_stat_statements';
```

Шаг 2. Перезапустить кластер.

Шаг 3. Настроить модуль, создать расширение в нужной базе, при необходимости сбросить накопленное:

```sql
ALTER SYSTEM SET pg_stat_statements.max = 10000;
ALTER SYSTEM SET pg_stat_statements.track = 'all';
SELECT pg_reload_conf(); -- применение настроек
\c ИМЯ_БАЗЫ
CREATE EXTENSION pg_stat_statements;
SELECT pg_stat_statements_reset(); -- для сброса накопленной статистики
```

(исправлено по смыслу: в источнике команда подключения к базе набрана кириллической «с» и с пробелом в имени — «\с ИМЯ _БАЗЫ».)

Подробное описание модуля авторы отсылают к документации: https://www.postgresql.org/docs/current/pgstatstatements.html

### 4.8. Примеры полезных запросов

Нагрузка, создаваемая запросами (псевдонимы колонок — как в источнике: `Memory` — блоки shared, `IO` — блоки local, `Temp` — временные блоки):

```sql
-- Нагрузка, создаваемая запросами
SELECT
  pg_database.datname AS Database,
  pg_stat_statements.query AS Query,
  pg_stat_statements.calls AS ExecutionCount,
  pg_stat_statements.total_exec_time ExecutionTime,
  pg_stat_statements.shared_blks_read + pg_stat_statements.shared_blks_written AS Memory,
  pg_stat_statements.local_blks_read + pg_stat_statements.local_blks_written AS IO,
  pg_stat_statements.temp_blks_read + pg_stat_statements.temp_blks_written AS Temp
FROM
  pg_stat_statements AS pg_stat_statements
  INNER JOIN pg_database AS pg_database
  ON pg_database.oid = pg_stat_statements.dbid
ORDER BY
  ExecutionTime DESC
```

Процент попадания в кэш:

```sql
-- Процент попадания в кэш
SELECT
  round(100 * sum(blks_hit) / sum(blks_hit + blks_read), 3) as cache_hit_ratio
FROM pg_stat_database;
```

Размер таблиц и индексов (плюс уникальность индекса и счётчики его использования):

```sql
-- Размер таблиц и индексов
SELECT
    t.tablename,
    indexname,
    c.reltuples::integer AS num_rows,
    pg_size_pretty(pg_relation_size(quote_ident(t.tablename)::text)) AS table_size,
    pg_size_pretty(pg_relation_size(quote_ident(indexrelname)::text)) AS index_size,
    CASE WHEN x.is_unique = 1  THEN 'Y'
       ELSE 'N'
    END AS UNIQUE,
    idx_scan AS number_of_scans,
    idx_tup_read AS tuples_read,
    idx_tup_fetch AS tuples_fetched
FROM pg_tables t
LEFT OUTER JOIN pg_class c ON t.tablename=c.relname
LEFT OUTER JOIN
       (SELECT indrelid,
           max(CAST(indisunique AS integer)) AS is_unique
       FROM pg_index
       GROUP BY indrelid) x
       ON c.oid = x.indrelid
LEFT OUTER JOIN
    ( SELECT c.relname AS ctablename, ipg.relname AS indexname, x.indnatts AS number_of_columns, idx_scan, idx_tup_read, idx_tup_fetch,indexrelname FROM pg_index x
           JOIN pg_class c ON c.oid = x.indrelid
           JOIN pg_class ipg ON ipg.oid = x.indexrelid
           JOIN pg_stat_all_indexes psai ON x.indexrelid = psai.indexrelid )
    AS foo
    ON t.tablename = foo.ctablename
WHERE t.schemaname='public'
ORDER BY pg_relation_size(quote_ident(indexrelname)::text) desc;
```

Отсутствие индексов (таблицы, где последовательных сканирований больше, чем индексных):

```sql
-- Отсутствие индексов
SELECT
  relname,
  seq_scan - coalesce(idx_scan, 0) AS too_much_seq,
  case when seq_scan - coalesce(idx_scan, 0) > 0 THEN 'Нет индекса?' ELSE 'OK' END AS Message,
  pg_relation_size(relname::regclass) AS rel_size,
  seq_scan,
  coalesce(idx_scan, 0) AS idx_scan
FROM
   pg_stat_all_tables
WHERE
   schemaname='public'
   AND pg_relation_size(relname::regclass)>10000 -- ограничение на размер анализируемых таблиц
ORDER BY
   too_much_seq DESC;
```

Использование буферного кэша (нужно расширение `pg_buffercache`):

```sql
-- Использование буферного КЭШа (необходимо установить расширение pg_buffercache)
CREATE EXTENSION pg_buffercache;

SELECT 'total', pg_size_pretty(count(*) * (SELECT current_setting('block_size')::int)) FROM pg_buffercache
UNION
SELECT 'dirty', pg_size_pretty(count(*) * (SELECT current_setting('block_size')::int)) FROM pg_buffercache WHERE isdirty
UNION
SELECT 'clear', pg_size_pretty(count(*) * (SELECT current_setting('block_size')::int)) FROM pg_buffercache WHERE NOT isdirty
UNION
SELECT 'used', pg_size_pretty(count(*) * (SELECT current_setting('block_size')::int)) FROM pg_buffercache WHERE reldatabase IS NOT NULL
UNION
SELECT 'free',pg_size_pretty(count(*) * (SELECT current_setting('block_size')::int)) FROM pg_buffercache WHERE reldatabase IS NULL
;
```

Содержимое буферного пула (10 отношений, занимающих больше всего буферов; закомментированная строка — вариант отбора по таблице):

```sql
-- Содержимое буферного пула
SELECT
  c.relname,
  pg_size_pretty(pg_relation_size(c.oid)) as relation_size,
  pg_size_pretty(count(b.bufferid) * (SELECT current_setting('block_size')::int)) AS buffered_in_shared_buffers,
  round(100 * count(b.bufferid) * (SELECT current_setting('block_size')::int) / greatest(1,pg_relation_size(c.oid)),1) as pct_of_relation,
  round((100 * count(b.bufferid) / greatest(1,(SELECT setting FROM pg_settings WHERE name = 'shared_buffers')::decimal)),2) AS pct_of_shared_buffers
FROM pg_class c
INNER JOIN pg_buffercache b ON b.relfilenode = c.relfilenode
AND b.reldatabase IN (0, (SELECT oid FROM pg_database WHERE datname = current_database()))

-- WHERE c.relname = 'products' AND usagecount >= 2 – если нужен отбор по таблице

GROUP BY c.oid, c.relname ORDER BY count(b.bufferid) * 8192 DESC LIMIT 10;
```

### 4.11. Мониторинг ожиданий PostgreSQL

Когда применять: конкретного запроса, вызывающего замедление, нет — СУБД в целом работает медленно. Тогда собирают статистику по ожиданиям. Справка по ожиданиям — описание полей `wait_event_type` и `wait_event` представления `pg_stat_activity`: https://www.postgresql.org/docs/current/monitoring-stats.html#MONITORING-PG-STAT-ACTIVITY-VIEW

Простой скрипт наблюдения за текущими ожиданиями `wait_monitor.sh` (очищает экран и раз в 3 секунды выводит сгруппированные ожидания активных сеансов):

```bash
#!/bin/bash
while true
do
        printf "\033c"
        psql -h server -U postgres -c "select wait_event_type, wait_event, count(*) as count from pg_stat_activity where state='active' group by wait_event_type, wait_event order by 3 desc;"
        sleep 3
done
```

```bash
chmod +x ./wait_monitor.sh
./wait_monitor.sh
```

Скрипт запускают в отдельном окне терминала и наблюдают в реальном времени. Оговорка авторов: статистика приблизительная — состояние снимается раз в 3 секунды, всё, что произошло в паузе, теряется; для общей картины этого достаточно.

Дальнейшие действия: взять ожидание, которое чаще всего оказывается на самом верху, и разобраться в его причинах по описанию в таблице событий ожидания: https://www.postgresql.org/docs/current/monitoring-stats.html#WAIT-EVENT-TABLE

Накопление статистики в файл — модифицированный скрипт `wait_monitor_csv.sh` (вывод в CSV с отметкой времени):

```bash
#!/bin/bash

while true
do
        psql -h server -U postgres --no-align --csv --tuples-only -c "select now() as timestamp, wait_event_type, wait_event, count(*) as count from pg_stat_activity where state='active' group by wait_event_type, wait_event;"
        sleep 3
done
```

```bash
chmod +x ./wait_monitor_csv.sh
./wait_monitor_csv.sh >> ./wait.log
```

В файле `wait.log` накапливаются снимки ожиданий. Анализ собранного — средствами `psql`:

```sql
create temp table waits(timestamp timestamp, wait_event_type varchar(100),
wait_event varchar(100), count int);

COPY pg_temp.waits(timestamp, wait_event_type, wait_event, count) FROM '/home/user/wait.log'
DELIMITER ',' CSV;

SELECT wait_event_type, wait_event, SUM(count) FROM pg_temp.waits GROUP BY
wait_event_type, wait_event ORDER BY 3 DESC;
```

В сборках PostgreSQL с патчем 1С, перечисленных в разделе 2, для этой же цели есть расширение `pg_wait_sampling`.

### 4.12. Загруженность оборудования: atop

Установка, интерактивный режим и запись в файл:

```bash
sudo apt install atop            # установка
sudo atop                        # режим интерактивного мониторинга
sudo atop -w atop.log 3 1200     # сбор данных в файл: 1200 снимков с интервалом 3 секунды (1 час)
```

Если запущена служба atop, счётчики оборудования снимаются постоянно. Проверка — `sudo systemctl status atop`; фрагмент вывода из статьи:

```text
Loaded: loaded (/lib/systemd/system/atop.service; enabled; vendor preset: enabled)
. . . . . . .
 CGroup: /system.slice/atop.service
         └─6984 /usr/bin/atop -R -w /var/log/atop/atop_20221220 600
```

(исправлено по смыслу: в источнике символ дерева процессов перед PID заменён на «??».) Число `600` в конце командной строки — интервал между снимками в секундах.

Изменение частоты снятия счётчиков службой — задать значение в `/etc/default/atop` и перезапустить службу:

```bash
sudo vim /etc/default/atop       # в файле задать: INTERVAL=60
sudo systemctl restart atop
```

(исправлено по смыслу: в источнике опечатка «INTERVAl» со строчной «l» на конце.)

Остальные команды:

```bash
# настройки журнала ежедневных счётчиков
sudo vim /usr/share/atop/atop.daily

# сбор данных в формате, пригодном для автоматической обработки (раз в секунду, до остановки по Ctrl+C)
sudo atop -P CPU,DSK,MEM,NET 1  > atop.csv

# преобразование бинарного файла в данные для автоматической обработки
atop -r /var/log/atop/atop_20221221 -P CPU,DSK,MEM,NET > atop.csv

# преобразование бинарного файла в текстовое представление для просмотра
atop -r /var/log/atop/atop_20221221 > atop.txt
```

Визуализация: можно написать собственный «парсер», преобразующий собранные данные в формат вроде csv, и загрузить их в любое ПО для построения графиков; готовые средства предлагается искать в интернете по фразе «atop visualization».

### 4.13. Загруженность оборудования: nmon

nmon авторы называют более продвинутым в визуальном смысле средством мониторинга.

```bash
sudo apt install nmon     # установка
sudo nmon                 # режим интерактивного мониторинга; после запуска нажать C n d t u
nmon -f -s 2 -c 600       # сбор данных в файл: 600 снимков с интервалом 2 секунды
```

Клавиши `C`, `n`, `d`, `t`, `u` в источнике даны без пояснений — результат был показан на скриншоте, который в текстовой копии не сохранился.

Приём: в отдельной консоли запустить монитор ожиданий PostgreSQL (раздел 4.11) — так можно одновременно оценивать состояние PostgreSQL и загрузку сервера.

Файл, сформированный командой `nmon -f ...`, нужно обработать для загрузки в ПО построения графиков либо воспользоваться готовыми средствами (поиск по фразе «nmon visualizer»).

### 4.14. Какой запрос нагружает оборудование

Алгоритм:

1. Взять PID самого нагруженного процесса (как именно — в статье показано скриншотами, которые в текстовой копии не сохранились; раздел идёт сразу после atop и nmon).
2. Найти этот PID в технологическом журнале по полю `dbpid` события DBPOSTGRS. Пример (сокращено):

```text
53:32.515071-125295937,DBPOSTGRS,4,process=rphost,p:processName=erp,OSThread=42008,t:clientID=656,t:applicationName=1CV8C,t:computerName=server,t:connectID=13931,SessionID=190,
Usr=...,AppID=1CV8C,DBMS=DBPOSTGRS,DataBase=127.0.0.1\ERP,Trans=0,dbpid=167172,Sql="
SELECT
T1._Fld836
FROM _InfoRg835 T1
LEFT OUTER JOIN _Document67 T2
ON T1._Fld847RRef = T2._IDRRef
WHERE ...
",RowsAffected=1,Result=PGRES_TUPLES_OK,Context='
```

3. Либо найти его в журнале PostgreSQL — PID стоит в квадратных скобках после метки времени. Пример (сокращено):

```text
2022-12-21 09:53:32.121 MSK [167172] postgres@ERP LOG:  duration: 1251.295 ms  bind <unnamed>: SELECT
T1._Fld836
FROM _InfoRg835 T1
LEFT OUTER JOIN _Document67 T2
ON T1._Fld847RRef = T2._IDRRef
WHERE ...
```

4. Если запрос ещё выполняется — получить его из `pg_stat_activity` по PID:

```sql
SELECT
  datname,
  application_name,
  pid,
  now() - pg_stat_activity.query_start AS duration,
  query
FROM pg_stat_activity
WHERE
  state = 'active'
  and pid = 167172;
```

## 5. Оптимизация использования виртуальной таблицы СрезПоследних при работе с PostgreSQL

- Дата публикации: 15.12.2010
- Ссылка: https://its.1c.ru/db/metod8dev/content/4208/hdoc
- Оценка применимости на октябрь 2026: **частично устарело**. Статья 2010 года, то есть времён PostgreSQL 8.x; версии СУБД и платформы в ней не названы. Упомянутая «ошибка оптимизатора» относится к версиям того времени — для современных сборок PostgreSQL с патчем 1С статья её не подтверждает и не опровергает. Сама рекомендация сформулирована условно (только если запрос работает неудовлетворительно) и как приём переписывания запроса по-прежнему применима.

### Проблема

При работе с PostgreSQL соединение в запросе с виртуальной таблицей СрезПоследних может существенно снижать производительность: из-за ошибки оптимизатора может быть выбран неоптимальный план выполнения.

### Решение

Если в запросе есть соединение с виртуальной таблицей СрезПоследних языка запросов «1С:Предприятия» и производительность такого запроса неудовлетворительна — вынести обращение к виртуальной таблице в отдельный запрос, сохранив его результат во временной таблице, и соединяться уже с ней.

Адресат рекомендации — разработчик прикладного решения: меняется текст запроса 1С; настроек на стороне СУБД статья не предлагает.

## 6. Использование конструкции ПОЛНОЕ ВНЕШНЕЕ СОЕДИНЕНИЕ

- Дата публикации: 18.01.2010
- Ссылка: https://its.1c.ru/db/metod8dev/content/1556/hdoc
- Оценка применимости на октябрь 2026: **частично устарело**. Статья 2010 года (эпоха PostgreSQL 8.x), версии СУБД и платформы не указаны; приведённый текст ошибки и ограничение поддержки FULL OUTER JOIN описывают СУБД того времени. Сохраняется ли преобразование запроса платформой и потеря эффективности на современных версиях — из статьи не следует, это нужно проверять по плану конкретного запроса (раздел 4). Как осторожное правило для разработчика рекомендация сохраняется: статья остаётся в разделе методической поддержки без пометок об отмене.

### Суть

- В СУБД PostgreSQL реализована только частичная поддержка `FULL OUTER JOIN`; сообщение СУБД: `ERROR: "FULL JOIN is only supported with mergejoinable join conditions"`.
- Чтобы конструкция работала полностью, 1С:Предприятие 8 при работе с PostgreSQL преобразует такой запрос в другую форму, дающую эквивалентный результат.
- Цена этого преобразования — снижение эффективности конструкции ПОЛНОЕ ВНЕШНЕЕ СОЕДИНЕНИЕ.

### Рекомендация

При работе с PostgreSQL использовать ПОЛНОЕ ВНЕШНЕЕ СОЕДИНЕНИЕ не рекомендуется. В большинстве случаев без него можно обойтись, переписав исходный запрос.

Для справки: по статье 6011 платформа выставляет в сеансе `SET enable_mergejoin = off` (раздел 4.2). Связь этого параметра с данной рекомендацией в источниках не описана.

- 6031, 6039: типографские кавычки ‘…’ во фрагментах `postgresql.conf` заменены на обычные одинарные.

- ⚠ Нулевое значение порогов `auto_dump.bad_plan_count_threshold` и `auto_dump.bad_plan_percent_threshold`: в статье о первой версии — «критерий выполнен всегда», в статье о версии 1.1 — «критерий срабатывать не будет». Перед настройкой выяснить версию расширения в своей сборке.
- ⚠ Формула критерия `bad_plan_percent_threshold` в обеих статьях описана неясно (говорится об отношении суммы ожидаемого и фактического числа строк к ожидаемому).
