# ИТС-конспект (методические материалы): Лицензирование (в том числе новый механизм 8.5.4), HASP, клиентские лицензии через сервер, Java-интерфейс администрирования и прочее
> Источник: статьи раздела «Методическая поддержка» портала 1С:ИТС (ссылки — в разделах). Это конспект своими словами, не дословный текст. Составлен 2026-10-10.

## Кратко: главные официальные рекомендации

**Лицензирование в 8.5.4 и старше (статья 6041, 30.04.2026)**

1. С версии 8.5.4 лицензии клиентских и серверных приложений проверяет новый механизм. После обновления с 8.3.27/8.5.1 на 8.5.4 и старше может потребоваться донастройка; что именно делать — зависит от того, где размещена лицензия.
2. Программная лицензия или аппаратный ключ на том же локальном компьютере: ничего настраивать не нужно, приложения 8.5.4+ работают сразу после установки.
3. Сетевой ключ защиты + HASP License Manager: на компьютере с ключом **требуется** установить приложение «1С:Предприятие 8 – Менеджер Лицензий» (`rmlic`) и зарегистрировать его как сервис. Это нужно на всех компьютерах с сетевыми ключами.
4. Менеджер Лицензий по умолчанию использует tcp и udp порты **475 и 1544**; обмен по ним должен быть разрешён в сети. В Linux/macOS порт 475 (номер меньше 1024) процесс может занять только с правами администратора.
5. На переходный период `rmlic` можно держать одновременно с HASP License Manager (когда один сетевой ключ используют и 8.3.27/8.5.1, и 8.5.4+). Когда старые версии выведены — остановить сервис HASP License Manager, отключить его автозапуск и перезапустить Менеджер Лицензий.
6. Настройки `nethasp.ini`, сделанные для 8.3.27/8.5.1 (`[NH_COMMON]` — `NH_TCPIP`; `[NH_TCPIP]` — `NH_USE_BROADCAST`, `NH_PORT_NUMBER`, `NH_SERVER_ADDR`), продолжают действовать и для 8.5.4+.
7. На сервере 1С:Предприятия после установки 8.5.4+ рекомендуется первым запустить агента кластера (`ragent`) — раньше любого другого приложения платформы. В кластере с несколькими рабочими серверами (лицензии на рабочем сервере с явно назначенным сервисом лицензирования) — запустить `ragent` 8.5.4+ на всех рабочих серверах до запуска чего-либо ещё.
8. На терминальном сервере с программной или аппаратной лицензией рекомендуется установить `rmlic` и зарегистрировать как сервис.
9. Системное время на компьютерах Менеджера Лицензий и на компьютерах клиентских и серверных приложений не должно расходиться больше чем на **20 минут**.
10. Диагностика «лицензия не найдена»: смотреть «Журнал поиска лицензии» (Отмена → «Не найдена лицензия…» → Подробно); если не стартует `rmlic` — включить технологический журнал с событиями `PROC` и `EXCP`; тонкая настройка — `rmlic.cfg` (менеджер) и `rclic.cfg` (поиск лицензии приложениями).

**Клиентские лицензии через сервер и HASP (статьи 3596 и 3059, 2009 г.)**

11. Клиент ищет лицензию по порядку: свой локальный ключ → сетевой ключ → локальный ключ сервера → сетевой ключ сервера → программная лицензия базовой конфигурации. К серверу за лицензией клиент обращается только если не нашёл её сам.
12. При получении лицензии через сервер лицензию занимает **каждый экземпляр клиента**, даже если несколько экземпляров запущены на одном компьютере (при собственном ключе клиентского компьютера два клиента заняли бы одну лицензию).
13. Сервер может работать только с одним локальным и одним сетевым ключом каждой серии, поэтому через один сервер доступно не более **1800** клиентских лицензий (локальные 100 + 300 + 500 и сетевые 100 + 300 + 500).
14. Чтобы выдавать через сервер больше 1800 лицензий — кластер на 2 и более компьютерах, дополнительные менеджеры кластера, сервис сеансовых данных назначен нескольким менеджерам на разных компьютерах, у каждого свои локальные ключи или свой `nethasp.ini` с адресом своего менеджера лицензий.
15. Чтобы веб-пользователи гарантированно не занимали лицензии офисных пользователей: ключ для веб-доступа вставить в компьютер сервера без установки менеджера лицензий и запретить серверу сетевой поиск ключей в `nethasp.ini`; ключ для локальной сети — на другом компьютере с менеджером лицензий.
16. В один компьютер можно установить не более одного ключа одной серии (ORGL8, ORG8A, ORG8B); ключи разных серий в одном компьютере сочетать можно, это увеличивает число лицензий.
17. HASP License Manager по умолчанию допускает не более **250** одновременных подключений (параметр `NHS_USERLIST` в `nhsrv.ini`); для ключей на 300 и 500 пользователей значение нужно увеличить, перезапустить менеджер и проверить по Activity Log, что файл настроек найден.
18. На компьютере менеджера лицензий должна быть единственная копия `nhsrv.ini`, лежащая в каталоге, откуда запускается менеджер.

**Прочее администрирование (статьи 4985, 4914, 5371, 5867)**

19. Для программного администрирования кластера существует Java-интерфейс (набор jar-пакетов); дистрибутивов два — для платформы 8.3.6–8.3.10 и для 8.3.11 и старше, брать нужно соответствующий версии.
20. Готовый установщик клиента с преднастроенным `1CEStart.cfg` делают утилитами `1CEClientSetupMake.exe` (Windows) и `1CEClientSetupMake.sh` (macOS); результат должен быть подписан двойной (SHA1+SHA256) электронной подписью поставщика.
21. Если растёт время запросов к таблицам итогов регистров — причина может быть в накоплении записей с нулевыми ресурсами; рекомендуется регулярный пересчёт итогов, тем чаще, чем больше позиций выходит из оборота.
22. Повреждённый журнал регистрации формата SQLite (`1Cv8.lgd`, ошибка `database disk image is malformed`) восстанавливают выгрузкой через `sqlite3 .dump` и загрузкой в новый файл. Работать только с копией файла, предварительно остановив кластер (или закрыв все клиенты в файловом варианте).

## 1. Особенности лицензирования при переходе на версии платформы 1С:Предприятие 8.5.4

- **Дата публикации:** 30.04.2026
- **Ссылка:** https://its.1c.ru/db/metod8dev/content/6041/hdoc
- **Применимость на октябрь 2026:** **актуально.** Самая свежая статья темы, описывает действующий механизм 8.5.4+. Оговорка для администратора Linux: примеры (путь к каталогу загрузочных модулей, `netstat`, Диспетчер задач, Process Explorer, Aladdin Monitor) даны для Windows; про Linux прямо сказано только два факта — права на порты ниже 1024 и проверка процесса через `ps`.

### Суть изменения

Начиная с 8.5.4 платформа проверяет лицензии на использование клиентских и серверных приложений по-новому. Переход с 8.3.27/8.5.1 на 8.5.4 и старше может потребовать дополнительной настройки проверки лицензии при запуске приложений. Нужные действия определяются схемой размещения лицензий.

### Что делать в каждой схеме размещения лицензий

| Схема | Действия при переходе на 8.5.4+ |
|---|---|
| Программная лицензия или аппаратный ключ на локальном компьютере | Никаких: клиентские и серверные приложения 8.5.4+ можно использовать сразу после установки |
| Сетевой ключ защиты + HASP License Manager | **Требуется** установить «1С:Предприятие 8 – Менеджер Лицензий» (`rmlic`) и зарегистрировать как сервис; разрешить в сети tcp/udp 475 и 1544 (подробности ниже) |
| Программная или аппаратная лицензия на терминальном сервере | **Рекомендуется** установить `rmlic` и зарегистрировать как сервис. Все приложения платформы, запускаемые на этом терминальном сервере, будут получать лицензии из программных и аппаратных лицензий, установленных на нём же |
| Программная или аппаратная лицензия на сервере 1С:Предприятия | После установки 8.5.4+ менеджер лицензий на сервере сразу готов использовать серверные лицензии и раздавать клиентские. **Рекомендуется** первым запустить `ragent` (подробности ниже) |

### Сетевой ключ и Менеджер Лицензий (rmlic): подробности

- **Порты.** По умолчанию Менеджер Лицензий занимает tcp и udp порты 475 и 1544.
- **Занятые порты.** Если 475 или 1544 (или оба) заняты другим приложением, Менеджер Лицензий всё равно успешно стартует: он занимает свободный порт и выдаёт лицензии локальным приложениям, а приложениям в локальной сети — при условии, что свободный порт найден. ⚠ в источнике неясно: какой именно порт выбирается, когда заняты оба стандартных, и как о нём узнают клиенты, не уточняется.
- **Linux/macOS и порт 475.** Порты с номерами меньше 1024 в этих ОС открывает только пользователь с правами администратора. Без таких прав Менеджер Лицензий не сможет занять порт 475, даже если тот свободен.
- **Совместная работа с HASP License Manager.** Допустимо запускать `rmlic` вместе с HASP License Manager, если сетевой ключ одновременно должны использовать платформа 8.3.27/8.5.1 и платформа 8.5.4+. Когда использование старых версий закончено, рекомендуется остановить сервис HASP License Manager, выключить его автоматический запуск и перезапустить Менеджер Лицензий. (В источнике старые версии обозначены как «8.5.1-» — по смыслу «8.5.1 и младше»; ⚠ в источнике неясно, запись оборвана.)
- **Сеть.** Должно быть разрешено взаимодействие приложений по tcp и udp портам 475 и 1544. После этого все приложения 8.5.4+ используют те же сетевые ключи, которыми пользовались приложения 8.3.27/8.5.1.
- **nethasp.ini.** Настройки, заданные для 8.3.27/8.5.1, продолжают действовать в 8.5.4+. Перечислены параметры:
  - секция `[NH_COMMON]` — `NH_TCPIP`;
  - секция `[NH_TCPIP]` — `NH_USE_BROADCAST`, `NH_PORT_NUMBER`, `NH_SERVER_ADDR`.

### Сервер 1С:Предприятия: порядок первого запуска

- Один сервер: после установки платформы 8.5.4+ запустить агента кластера (`ragent`) версии 8.5.4+ **до** запуска любого другого приложения платформы на этом сервере.
- Кластер с несколькими рабочими серверами, где лицензии установлены на рабочий сервер с явно назначенным на него сервисом лицензирования: запустить `ragent` 8.5.4+ на **всех** рабочих серверах кластера до запуска любого другого приложения платформы на серверах кластера.

Причина такого порядка в статье не объясняется — это рекомендация без обоснования.

### Чек-лист: приложение при запуске не находит лицензию

Вложенность пунктов восстановлена по смыслу (в текстовой копии статьи иерархия списков потеряна).

**Шаг 1. Открыть журнал поиска лицензии.**

1. Если показан диалог получения лицензии — нажать «Отмена»; появится сообщение «Не найдена лицензия…».
2. В этом сообщении нажать «Подробно» — откроется «Журнал поиска лицензии»: перечень всех действий приложения по поиску лицензии и их результатов.

**Шаг 2. Проверить версию «не найден сетевой ключ, который старая платформа (8.3.27/8.5.1) находит».**

1. Убедиться, что на **всех** компьютерах с сетевыми ключами установлен и запущен «1С:Предприятие – Менеджер Лицензий».
2. Список компьютеров локальной сети, где стоят сетевые аппаратные ключи и запущен HASP License Manager, даёт утилита Aladdin Monitor. По состоянию на 04.02.2026 доступна версия 1.4.2 (июль 2008 г.): https://www.scoms.ru/download/aladdin/ (в источнике ссылка с дополнительным трекинг-параметром `ysclid`).
3. Проверить, что Менеджер Лицензий действительно запущен: процесс `rmlic` виден в Диспетчере задач (Windows) или в выводе `ps` (Linux).
4. Проверить, что процесс `rmlic` занял нужные tcp и udp порты (способ для Windows): командой ниже из `cmd`, запущенного «от имени администратора», либо утилитой Process Explorer (https://learn.microsoft.com/en-us/sysinternals/downloads/process-explorer).

```bat
netstat -q -b
```

(исправлено по смыслу: в источнике перед `b` стояло длинное тире вместо дефиса.) Способ проверки занятых портов для Linux в статье не приведён.

5. Если Менеджер Лицензий не запускается — выяснить причину по технологическому журналу. В подкаталог `conf` каталога загрузочных модулей Менеджера Лицензий (пример каталога из статьи: `C:\Program Files\1cv8\8.5.4.866\bin`) положить файл `logcfg.xml` с текстом ниже, заменив «путь» на каталог для журнала, и повторить запуск:

```xml
<?xml version="1.0"?>
<config xmlns="http://v8.1c.ru/v8/tech-log">
  <log location="путь\logs" history="2">
    <event>
      <eq property="name" value="PROC"/>
    </event>
    <event>
      <eq property="name" value="EXCP"/>
    </event>
    <property name="all"/>
  </log>
</config>
```

6. Более тонкая настройка Менеджера Лицензий — параметрами строки запуска и конфигурационным файлом `rmlic.cfg` (сами параметры в статье не перечислены).

**Шаг 3. Если все Менеджеры Лицензий работают — по журналу поиска лицензии определить, с какими менеджерами приложение не соединилось и почему.**

| Что в `nethasp.ini` | Что проверить / сделать |
|---|---|
| Указаны адреса менеджеров | По этим адресам действительно должны быть установлены и запущены «1С:Предприятие – Менеджеры Лицензий»; при необходимости установить и запустить |
| Указан порт, отличный от 475 | Настроить использование нестандартных портов у Менеджеров Лицензий |
| Файла нет или в нём только комментарии | Проверить, что сетевые экраны разрешают широковещательный поиск по udp на портах 475 и/или 1544 |

Дополнительно:

- системное время на компьютерах Менеджера Лицензий и на компьютерах клиентских и серверных приложений платформы не должно отличаться больше чем на 20 минут;
- более тонкая настройка поиска лицензии приложениями платформы — конфигурационным файлом `rclic.cfg` (параметры в статье не перечислены).

**Шаг 4. Где посмотреть, какая лицензия используется.**

- После запуска приложения — диалог «О программе»: в интерфейсе «Такси» свойство «Лицензия» под строкой «Текущая», в интерфейсе «8.5» — отдельная страница «Лицензия». Там показаны используемые клиентская и серверная лицензии.
- Все доступные Менеджеры Лицензий и установленные лицензии — стандартная обработка «Функции для технического специалиста – Стандартные – Управление лицензиями».

### Чего в статье нет

- Команд установки `rmlic` и регистрации его как сервиса (ни для Windows, ни для Linux).
- Расположения каталога `conf` и загрузочных модулей Менеджера Лицензий в Linux.
- Перечня параметров `rmlic.cfg`, `rclic.cfg` и параметров строки запуска `rmlic`, в том числе способа задать нестандартные порты.

## 2. Получение клиентских лицензий через сервер 1С:Предприятия

- **Дата публикации:** 09.12.2009
- **Ссылка:** https://its.1c.ru/db/metod8dev/content/3596/hdoc
- **Применимость на октябрь 2026:** **частично устарело.** Статья 2009 года: рассматривает только аппаратные ключи HASP (программная лицензия упомянута лишь для базовой конфигурации), раздающим лицензии звеном называет менеджер кластера с сервисом сеансовых данных (в статье 6041 от 2026 года фигурирует уже сервис лицензирования и Менеджер Лицензий `rmlic`), в примерах `nethasp.ini` есть протоколы IPX и NetBIOS. Сохраняют ценность принципы: порядок поиска лицензии, подсчёт лицензий «на экземпляр клиента» при выдаче через сервер, ограничение «один ключ одной серии», приём разделения лицензий через `nethasp.ini`. Статья 6041 подтверждает, что параметры `NH_TCPIP`, `NH_USE_BROADCAST`, `NH_PORT_NUMBER`, `NH_SERVER_ADDR` файла `nethasp.ini` действуют и в 8.5.4+; про `NH_IPX` и `NH_NETBIOS` там ничего не сказано. Перед применением на современной платформе сверяться с актуальной документацией.

### Когда сервер выдаёт клиентские лицензии

Клиенту для запуска нужна свободная лицензия в клиентском ключе. Поиск идёт строго по порядку:

| Шаг | Где ищется лицензия | Исключения и уточнения |
|---|---|---|
| 1 | Локальный клиентский ключ | Кроме веб-клиента |
| 2 | Сетевой клиентский ключ | Кроме веб-клиента |
| 3 | Локальный клиентский ключ сервера | Не применяется для информационной базы на локальном компьютере или на компьютере в локальной сети. Для базы на сервере 1С:Предприятия используется локальный ключ компьютера менеджера, на который назначен сервис сеансовых данных. Для файловой базы на веб-сервере — локальный ключ веб-сервера |
| 4 | Сетевой клиентский ключ сервера | Те же исключения. Для базы на сервере 1С к сетевому ключу обращается компьютер менеджера с сервисом сеансовых данных; для файловой базы на веб-сервере — веб-сервер |
| 5 | Программная лицензия базовой конфигурации | — |

Вывод: к серверу за лицензией клиент обращается только тогда, когда не нашёл свободной лицензии на доступных ему самому ключах. Тогда сервер сам ищет и занимает свободную лицензию на одном из ключей, доступных серверу.

### Чем получение лицензий сервером отличается от получения клиентом

Механизм в основном тот же, что у клиента. Отличия вытекают из свойств процесса менеджера кластера с сервисом сеансовых данных (или веб-сервера — для файловой базы):

- он может одновременно занимать несколько клиентских лицензий (клиент — только одну);
- он может подключиться только к одному локальному и одному сетевому ключу одной серии;
- он в общем случае не способен идентифицировать клиентский компьютер, поскольку клиент может приходить через веб-сервер.

### Одна лицензия на экземпляр клиента

Следствие последнего пункта: при выдаче через сервер лицензию занимает каждый запущенный экземпляр клиента, независимо от того, на одном они компьютере или на разных.

- Клиентскому компьютеру доступен свой клиентский ключ → два клиента на нём занимают **одну** лицензию.
- Клиентскому компьютеру ключ недоступен → два клиента на нём занимают через сервер **две** лицензии.

### Локальная установка сетевого клиентского ключа в компьютер сервера

Многопользовательский (сетевой) клиентский ключ можно вставить прямо в компьютер менеджера кластера с сервисом сеансовых данных (для файловой базы — в веб-сервер). Тогда сервер получит из него несколько лицензий в пределах номинала ключа, **даже если менеджер лицензий на этом компьютере не установлен**. Обратная сторона: без менеджера лицензий такой ключ недоступен другим компьютерам локальной сети и терминальным сессиям — только через сервер.

**Применение: изоляция лицензий веб-пользователей от лицензий офиса.** Цель — чтобы клиенты, работающие через веб-сервер, гарантированно не могли занять лицензии пользователей локальной сети.

1. Ключ с лицензиями для доступа через веб-сервер установить в компьютер сервера; менеджер лицензий на нём **не** устанавливать.
2. На компьютере сервера в подкаталог `conf` каталога загрузочных модулей 1С:Предприятия поместить `nethasp.ini`, запрещающий сетевой поиск клиентского ключа, например:

```ini
[NH_COMMON]
NH_IPX = Disabled
NH_NETBIOS = Disabled
NH_TCPIP = Disabled
```

3. Другой клиентский ключ — с лицензиями для пользователей локальной сети — установить в другой компьютер и запустить на нём менеджер лицензий.

**Серии ключей.** Сервер пытается получить лицензию из локальных ключей всех клиентских серий:

| Серия | Номинал |
|---|---|
| ORGL8 | 1–100 пользователей |
| ORG8A | 300 пользователей |
| ORG8B | 500 пользователей |

Установка в компьютер сервера нескольких ключей разных серий увеличивает количество лицензий, доступных через сервер.

### Доступ сервера к сетевому клиентскому ключу

- Не найдя свободной лицензии в локальных ключах, сервер ищет её на сетевых ключах всех клиентских серий согласно настройкам `nethasp.ini`.
- Сервер держит соединение только с **одним** сетевым ключом одной серии. Когда лицензии в этом ключе исчерпаны, другие сетевые ключи той же серии не ищутся.
- Отсюда потолок для одного сервера — **1800** клиентских лицензий:

| Ключ | Лицензий |
|---|---|
| локальный на 100 | 100 |
| локальный на 300 | 300 |
| локальный на 500 | 500 |
| сетевой на 100 | 100 |
| сетевой на 300 | 300 |
| сетевой на 500 | 500 |
| **Итого** | **1800** |

### Больше 1800 лицензий: множественное назначение сервиса сеансовых данных

Последовательность действий:

1. Развернуть кластер серверов 1С:Предприятия на 2 и более компьютерах.
2. На каждом компьютере, кроме первого, запустить дополнительный менеджер кластера.
3. Сервис сеансовых данных назначить нескольким менеджерам на разных компьютерах.
4. Для локальных ключей — установить локальные ключи в каждый компьютер менеджера, которому назначен сервис сеансовых данных.
5. Для сетевых ключей — на компьютерах этих менеджеров задать `nethasp.ini`, указывающие на **разные** менеджеры лицензий.

`nethasp.ini` на компьютере первого менеджера:

```ini
[NH_COMMON]
NH_IPX = Disabled
NH_NETBIOS = Disabled
NH_TCPIP = Enabled
[NH_TCPIP]
NH_SERVER_ADDR = 1.2.3.4 ; Адрес компьютера с менеджером лицензий
NH_USE_BROADCAST = Disabled
```

`nethasp.ini` на компьютере второго менеджера:

```ini
[NH_COMMON]
NH_IPX = Disabled
NH_NETBIOS = Disabled
NH_TCPIP = Enabled
[NH_TCPIP]
NH_SERVER_ADDR = 1.2.3.5 ; Адрес компьютера с менеджером лицензий
NH_USE_BROADCAST = Disabled
```

Результат: кластер равномерно распределяет клиентские сеансы между менеджерами, и через сервер становится доступным произвольное количество клиентских лицензий.

## 3. Использование сетевых ключей HASP на 300 и 500 пользователей

- **Дата публикации:** 18.03.2009
- **Ссылка:** https://its.1c.ru/db/metod8dev/content/3059/hdoc
- **Применимость на октябрь 2026:** **частично устарело.** Статья 2009 года, отсчёт ведётся от платформы 8.1.13.41, всё описание — про HASP License Manager под Windows (`nhsrvw32.exe`, каталоги Windows XP, сервис HASP Loader); вариант менеджера лицензий для Linux не рассматривается. По статье 6041 платформе 8.5.4+ для сетевых ключей нужен уже Менеджер Лицензий `rmlic`, а HASP License Manager после ухода со старых версий рекомендуется остановить; есть ли у `rmlic` аналог ограничения `NHS_USERLIST` — в источниках не сказано. Сведения остаются рабочими там, где ещё эксплуатируется HASP License Manager (платформа 8.3.27/8.5.1 и младше, переходный период); перечень серий ключей и правило «один ключ одной серии на компьютер» полезны как справка.

### Какие ключи поддерживаются

Клиентское приложение и COM-соединение 1С:Предприятия начиная с версии 8.1.13.41 работают со следующими ключами HASP:

| Серия | Тип | Число пользователей |
|---|---|---|
| ORGL8 | локальный клиентский | 1 |
| ORGL8 | сетевой клиентский | 5, 10, 20, 50, 100 |
| ORG8A | сетевой клиентский | 300 |
| ORG8B | сетевой клиентский | 500 |

Ограничение: в один компьютер устанавливается не более одного ключа одной серии.

### Менеджер лицензий (HASP License Manager)

Чтобы сетевой ключ был виден клиентским приложениям по локальной сети, на компьютере с ключом должна работать программа-менеджер лицензий (HASP License Manager). Она входит в поставку 1С:Предприятия. После установки её можно запускать автоматически или вручную, как сервис или как обычное приложение.

### Конфигурационный файл nhsrv.ini

Параметры работы менеджера лицензий задаются в `nhsrv.ini`. Файл с настройками по умолчанию устанавливается в каталог загрузочных модулей менеджера, обычно `C:\Program Files\Aladdin\HASP LM`.

**Порядок поиска `nhsrv.ini` при запуске менеджера:**

1. каталог, из которого запущен загрузочный модуль менеджера лицензий (`nhsrvw32.exe`);
2. текущий каталог Windows;
3. 32-битный системный каталог Windows (пример для Windows XP: `C:\WINDOWS\system32`);
4. системный каталог Windows `C:\WINDOWS\system` (пример для Windows XP; разрядность в тексте методички утеряна);
5. каталоги из переменной окружения `path`.

Уточнено 19.10.2026 по «Руководству администратора» 8.3.27, прил. 3, разд. 3.26 «nhsrv.ini» — актуальный порядок поиска в Windows:
1. каталог исполняемого файла HASP License Manager;
2. текущий каталог;
3. системный каталог — `%SYSTEMROOT%\system32` для 32-разрядной версии, `%SYSTEMROOT%\SysWOW64` для 64-разрядной;
4. `%SYSTEMROOT%`;
5. каталоги из `PATH` — только когда HASP LM установлен как приложение, а не служба.

Рекомендуемое место — каталог исполняемого файла. Прочитан ли файл, видно в Activity Log менеджера. В Linux путь задаётся ключом `-c`, умолчания нет.

**Рекомендации по размещению:**

- На компьютере менеджера лицензий должна быть **единственная** копия `nhsrv.ini`, и лежать она должна в каталоге, из которого запускается менеджер, — так настройка проще.
- Менеджер запускается как приложение → файл должен находиться в каталоге, указанном при установке менеджера: обычно `C:\Program Files\Aladdin\HASP LM` (32-разрядная Windows) или `C:\Program Files (x86)\Aladdin\HASP LM` (64-разрядная Windows).
- Менеджер запускается как сервис Windows → файл лучше поместить в 32-разрядный системный каталог Windows. Этот каталог должен быть указан в строке запуска сервиса: My Computer / контекстное меню / Manage / Services and Applications / Services / HASP Loader / контекстное меню / Properties / Path to executable.

### Максимальное число одновременно подключённых пользователей

Сколько пользователей может быть одновременно подключено к менеджеру лицензий, определяет параметр `NHS_USERLIST` файла `nhsrv.ini`.

| Параметр | Значение по умолчанию | Что ставить |
|---|---|---|
| `NHS_USERLIST` | 250 | нужное число: 300, 500 или другое |

Точная строка и секция файла для этого параметра в статье не приведены — только имя параметра и значения.

**Порядок увеличения лимита:**

1. Разместить `nhsrv.ini` в каталоге, из которого запускается менеджер лицензий.
2. Изменить `NHS_USERLIST` на требуемое значение (300, 500 или иное).
3. Перезапустить менеджер лицензий.
4. По журналу Activity Log / Server Activity Log убедиться, что менеджер лицензий нашёл файл `nhsrv.ini`.

После этого менеджер допускает одновременную работу 300 или 500 пользователей — в зависимости от установленного ключа. Следствие: пока значение не увеличено, для ключей на 300 и 500 пользователей действует лимит по умолчанию — 250 подключений.

## 5. Использование утилит 1CEClientSetupMake.exe и 1CEClientSetupMake.sh

- **Дата публикации:** 26.06.2024 (в шапке статьи: платформа «1С:Предприятие» 8.3.14 и выше)
- **Ссылка:** https://its.1c.ru/db/metod8dev/content/4914/hdoc
- **Применимость на октябрь 2026:** **актуально**, но к серверу на Linux отношения не имеет: утилиты предназначены для подготовки клиентских установщиков под Windows (`.exe`) и macOS (`.sh`). Расширение `.sh` не означает Linux — в статье прямо указано, что скрипт создаёт dmg-образ для macOS. Полезно тому, кто централизованно раздаёт пользователям клиент с готовыми настройками запуска. В тексте говорится о дистрибутиве «8.3»; о 8.5 ничего не сказано.

### Назначение

Утилиты собирают единый установочный файл клиентского приложения: самораспаковывающийся архив (Windows) или dmg-образ (macOS), в который вложены само приложение и настройки для его установки, обновления и запуска.

Что может входить в результат:

- дистрибутив платформы 1С:Предприятие 8.3;
- файл `1CEStart.cfg` с настройками, которые нужно применить на компьютере пользователя; в нём допустимы те же ключи, что и в пользовательском `1CEStart.cfg`.

**Требование к подписи:** полученный дистрибутив должен быть подписан двойной (SHA1+SHA256) электронно-цифровой подписью провайдера — организации, которая поставляет дистрибутив. Подробности о подписи dmg-образа в статье даны ссылкой, которая в текстовую копию не попала.

### Утилита 1CEClientSetupMake.exe (Windows)

Консольное приложение. Создаёт самораспаковывающийся архив `1CEClientSetup.exe`, который помимо дистрибутива платформы может содержать `1CEStart.cfg`. Полученный `1CEClientSetup.exe` запускается только в Windows.

Синтаксис:

```bat
1CEClientSetupMake.exe [/f <Имя файла>] [/d <Имя входного каталога>] /o <Имя выходного каталога> [/h]
```

| Параметр | Полная форма | Назначение |
|---|---|---|
| `/f` | `--input-file=<Имя файла>` | Готовый архив формата .zip, который будет внедрён в `1CEClientSetup.exe` |
| `/d` | `--input-directory=<Имя входного каталога>` | Каталог, содержимое которого будет упаковано в zip-архив и внедрено в `1CEClientSetup.exe` |
| `/o` | `--output-directory=<Имя выходного каталога>` | Каталог для готового `1CEClientSetup.exe`. По описанию — опциональный, по умолчанию текущий каталог |
| `/h` | `--help` | Справка |

- Сокращённые параметры можно начинать как с `/`, так и с `-`.
- ⚠ в источнике неясно: в строке синтаксиса `/o` показан как обязательный (без квадратных скобок), а в описании назван опциональным со значением по умолчанию «текущий каталог».
- ⚠ в источнике неясно: `/f` и `/d` оба показаны необязательными; не сказано, обязателен ли хотя бы один из них и можно ли задавать оба сразу.

### Приложение 1CEClientSetup.exe (результат работы утилиты)

Оконное приложение. Отдельно не поставляется — хранится в ресурсах `1CEClientSetupMake.exe`. Что происходит при запуске у пользователя:

1. Данные из `1CEStart.cfg`, вложенного в архив, переносятся в пользовательский `1CEStart.cfg` — настройки **добавляются** к уже имеющимся.
2. Дистрибутив платформы распаковывается во временный каталог и устанавливается. Пользователь видит только индикатор установки и кнопку «Отмена».
3. После установки временный каталог с дистрибутивом удаляется.
4. Запускается неинтерактивная программа запуска.

### Утилита 1CEClientSetupMake.sh (macOS)

Создаёт dmg-образ клиентского приложения; кроме дистрибутива платформы в образе может быть `1CEStart.cfg`.

Синтаксис:

```bash
1CEClientSetupMake.sh <путь_к_DMG_образу_клиента> [путь_к_новому_DMG_образу_клиента] <путь_к_конфигурационному_файлу> [-h]
```

| Параметр | Назначение |
|---|---|
| `путь_к_DMG_образу_клиента` | Путь к DMG-образу дистрибутива тонкого или толстого клиента «1С:Предприятия» для macOS |
| `путь_к_новому_DMG_образу_клиента` | Опциональный. Путь к создаваемому DMG-образу |
| `путь_к_конфигурационному_файлу` | По описанию — опциональный. Файл, который будет положен в новый образ под именем `1cestart.cfg`. Если не задан, утилита ищет файл `1cestart.cfg` в каталоге, где лежит исходный DMG-образ |
| `-h`, `--help` | Справка |

- **Внимание (оговорка авторов):** если путь к новому образу не указан, результат записывается под именем исходного образа с префиксом `out-`. Пример: исходный `1cv8-thin-client-A.B.C.D.dmg` → новый `out-1cv8-thin-client-A.B.C.D.dmg`.
- ⚠ в источнике неясно: в строке синтаксиса путь к конфигурационному файлу показан в угловых скобках как обязательный, а в описании назван опциональным; как утилита различает два необязательных позиционных параметра, не объяснено.

Поведение при установке dmg-образа с вложенным `1cestart.cfg`: программа установки «1С:Предприятие» сначала устанавливает клиентское приложение, затем переносит данные из вложенного `1cestart.cfg` в пользовательский `1cestart.cfg`, добавляя настройки к существующим; после успешной установки и объединения настроек запускается неинтерактивная программа запуска. (Порядок отличается от Windows-варианта: там настройки переносятся до установки.)

Сами утилиты скачиваются со страницы статьи на ИТС (в текстовой копии ссылка на файлы отсутствует).

## 6. Рекомендации по пересчету итогов

- **Дата публикации:** 05.09.2013
- **Ссылка:** https://its.1c.ru/db/metod8dev/content/5371/hdoc
- **Применимость на октябрь 2026:** **актуально (общий принцип).** Статья 2013 года, но не привязана ни к версии платформы, ни к СУБД, ни к ОС: описывает свойство механизма итогов регистров. Очень краткая — конкретного способа запуска пересчёта и числовых порогов не содержит.

### Проблема

Со временем увеличивается длительность запросов, обращающихся к таблицам итогов регистров.

### Причина

- При интенсивной работе с базой в таблицах итогов регистров накапливаются записи, у которых значения ресурсов равны нулю.
- Сами по себе такие записи проблемой не являются. Проблема возникает в сценариях, где их становится много: объём «пустых» записей начинает влиять на производительность.
- Пример авторов — штучное производство, где каждый товар уникален: после прихода и расхода остаток такого товара нулевой, а запись остаётся. Если производство одновременно массовое и уникальное, число нулевых записей растёт постоянно; запросы к таблицам итогов замедляются, а СУБД тратит на них больше ресурсов.

### Решение

- Регулярно выполнять процедуру пересчёта итогов — как профилактику.
- Периодичность определяется интенсивностью работы с базой: чем больше товаров выходит из оборота, тем чаще нужен пересчёт.

### Чего в статье нет

Не указано, каким способом выполнять пересчёт (режим, команда, регламентная операция), какая конкретно периодичность рекомендуется и как измерить долю нулевых записей.

## 7. Восстановление журнала регистрации

- **Дата публикации:** 20.11.2015
- **Ссылка:** https://its.1c.ru/db/metod8dev/content/5867/hdoc
- **Применимость на октябрь 2026:** **актуально для своего случая** — когда журнал регистрации хранится в формате SQLite (файл `1Cv8.lgd`); другие форматы журнала статья не рассматривает. Статья 2015 года, пошаговый пример дан для Windows (`C:\LogRestore`, `sqlite3.exe`, Notepad++); для Linux сказано только, что утилиту sqlite следует брать из официальных репозиториев (имя пакета и пути к каталогу журнала на Linux не приводятся). Сами команды `sqlite3` от ОС не зависят.

### Проблема (симптомы)

При входе в информационную базу или при обращении к журналу регистрации пользователи получают ошибку вида:

```text
sqlite3_step failed: database disk image is malformed
db: C:\ut11\1Cv8Log\1Cv8.lgd
```

либо другие ошибки, связанные с sqlite.

### Причина и как её подтвердить

- Источником ошибок sqlite может быть повреждение данных в файле журнала регистрации.
- Признак именно этой проблемы — текст `database disk image is malformed`. Он может быть «замаскирован» другими ошибками sqlite, которые видит пользователь.
- Поэтому при любых ошибках sqlite у пользователей нужно искать `database disk image is malformed` в журналах клиентских приложений (для файлового варианта) или менеджеров кластера. Пример записи из статьи (формат технологического журнала, событие `EXCP` процесса `rmngr`):

```text
16:29.504002-0,EXCP,0,process=rmngr,Exception=EventLogException,Descr='sqlite3_exec failed: database disk image is malformed
db: C:\Program Files\1cv8\srvinfo\reg_1541\50b80b42-24a3-4f33-8508-5672acb80621\1Cv8Log\1Cv8.lgd sql: PRAGMA journal_mode = OFF'
```

- Такая запись означает, что повреждён именно тот файл журнала регистрации, путь к которому указан в ошибке (в примере — каталог `1Cv8Log` информационной базы внутри `srvinfo\reg_1541\<идентификатор базы>`).

### Инструмент

Утилита командной строки sqlite:

- Windows — скачать (ссылка на загрузку в текстовую копию статьи не попала);
- Linux — использовать утилиту из официальных репозиториев дистрибутива.

### Порядок восстановления

**ВНИМАНИЕ (предупреждение авторов): все операции выполнять обязательно над копией файла журнала регистрации.**

1. Остановить кластер «1С:Предприятия»; для файлового варианта — завершить все клиентские приложения.
2. Скопировать испорченный файл `1Cv8.lgd` в отдельный каталог, например `C:\LogRestore`.
3. Туда же распаковать `sqlite3.exe` из скачанного архива (шаг для Windows).
4. В командной строке перейти в этот рабочий каталог (`C:\LogRestore`).
5. Выгрузить содержимое базы журнала в SQL-скрипт:

```bash
sqlite3 1Cv8.lgd .dump >> backup.sql
```

6. Открыть `backup.sql`. Файл может быть большим, штатный «Блокнот» Windows его может не открыть — тогда использовать, например, Notepad++.
7. Если самая последняя строка файла — `ROLLBACK;`, заменить её на `COMMIT;` и сохранить файл.
8. Переименовать `1Cv8.lgd` в рабочем каталоге в `1Cv8-orig.lgd`.
9. В том же каталоге загрузить скрипт в новый файл:

```bash
sqlite3 1Cv8.lgd < backup.sql
```

При выполнении могут выводиться ошибки — по словам авторов, это нормально.

10. Открыть полученный `1Cv8.lgd` Конфигуратором пустой файловой базы и убедиться, что данные сохранились.
11. Заменить испорченный файл в его исходном расположении файлом `1Cv8.lgd` из рабочего каталога.

Примечание к тексту источника: в шагах 8 и 10 имя файла набрано с кириллической «С» (`1Сv8.lgd`); здесь приведено как `1Cv8.lgd` (исправлено по смыслу — в остальных местах статьи и в сообщениях об ошибках используется латинская «C»).

### Чего в статье нет

- Не описано, как именно открыть файл журнала «Конфигуратором пустой файловой базы» (⚠ в источнике неясно — сказано только, что так нужно проверить результат).
- О полноте восстановления данных ничего не сказано; единственная проверка — шаг 10.
