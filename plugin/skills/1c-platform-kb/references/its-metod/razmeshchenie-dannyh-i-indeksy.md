## Кратко: главные официальные рекомендации

Размещение данных (статья 1):

1. Вся информационная база (конфигурация, учётные данные, административная информация) хранится в одной базе данных СУБД (в файловом варианте — в одном файле `1cv8.1cd`). Потеря или искажение части этих данных может лишить систему работоспособности.
2. Сведения о таблицах и файлах даются только для понимания. Работать с этими данными способами, не предусмотренными штатными механизмами платформы, нельзя.
3. База данных с информационной базой должна быть защищена от несанкционированного доступа; изменять её допустимо только средствами 1С:Предприятия.
4. В штатном режиме платформа не проверяет ни наличие прикладных таблиц, ни целостность и непротиворечивость данных в них. Для проверки предназначена функция конфигуратора «Администрирование — Тестирование и исправление».
5. При старте проверяется только наличие обязательных служебных таблиц (`Config`, `ConfigSave`, `Files`, `Params`, `DBSchema`, `v8users` и др.). Нет одной из них — сообщение «информационная база разрушена»; нет ни одной — база считается пустой, и таблицы создаются.
6. Резервное копирование и восстановление базы данных с информационной базой выполнять только целиком. Рекомендуются средства резервного копирования самой СУБД; файловую базу копируют файлом `1cv8.1cd`.
7. Альтернативный способ резервирования для обоих вариантов — «Администрирование — Выгрузить информационную базу» / «Загрузить информационную базу» в конфигураторе (в выгрузку попадают все данные информационной базы и только они; загрузка заменяет существующие данные).
8. Журнал регистрации хранится не в базе данных, а в каталоге `1Cv8Log`: в клиент-серверном варианте — в подкаталоге рабочего каталога кластера с именем-идентификатором информационной базы. Для работы прикладного решения он не обязателен, но может быть важен организационно.
9. Данные полнотекстового поиска (`1Cv8FTxt`) лежат на центральном сервере в `<рабочий каталог кластера>/<идентификатор информационной базы>`.
10. Хранилище конфигурации — один файл `1Cv8ddb.1cd` в каталоге хранилища; при групповой разработке он жизненно важен, его рекомендуется резервировать.
11. Файл `srvribrg.lst` (список кластеров на центральном сервере) необходим для нормальной работы приложений, использующих сервер; `1CV8Reg.lst` — файл настройки кластера.
12. Профайлы на логику работы не влияют, их потеря не нарушает работоспособность; кеши конфигурации на клиенте — производная от конфигурации в базе данных, нужны только для ускорения. Профайлы читаются при старте и записываются при штатном завершении, поэтому после аварийного завершения часть пользовательских настроек может не сохраниться.
13. Имя прикладной таблицы = буквенный префикс (назначение) + номер (конкретный объект метаданных). Соответствие объектов метаданных объектам базы данных хранится в таблице `Params`.
14. Таблицы регистрации изменений (`…ChngR…`) создаются только для объектов, участвующих хотя бы в одном плане обмена; `_ConfigChangeRec` и `_ConfigChangeRec_ExtProps` — если есть план обмена с флагом «Распределенная информационная база».

Индексы (статья 2):

15. Индексы создаются платформой неявно — при создании объектов конфигурации и в зависимости от их настроек. Перечнем индексов следует руководствоваться при написании текстов запросов, чтобы сократить время их выполнения.
16. У объектных таблиц (справочник, документ, план счетов, перечисление, бизнес-процесс, задача) всегда есть кластерный индекс по полю Ссылка (с полями независимых разделителей); у табличной части — `Ссылка + Ключ`.
17. Свойство реквизита «Индексировать» даёт индекс `Реквизит + Ссылка`; «Индексировать с доп. упорядочиванием» — индекс, продолженный полем основного представления (Код или Наименование у справочника, Дата у документа, Порядок/Код/Наименование у плана счетов). Включение объекта в критерий отбора даёт индекс по одному полю `Реквизит`.
18. У всех регистров, подчинённых регистратору, всегда есть индекс `Регистратор + НомерСтроки`; основная таблица регистра накопления и регистра бухгалтерии кластеризована по `Период + Регистратор + НомерСтроки`.
19. У регистра сведений основной (кластерный) индекс включает все измерения в том порядке, в каком они заданы в конфигураторе (у периодического — плюс Период).
20. Свойство «Индексировать» или «Ведущее» у измерения регистра сведений добавляет индекс, начинающийся с этого измерения; «Индексировать» у реквизита или ресурса — индекс, начинающийся с реквизита или ресурса.
21. У регистра накопления «Индексировать» на измерении даёт индекс `Измерение + Период + Регистратор + НомерСтроки` по основной таблице, а по таблицам остатков и оборотов — отдельный индекс только начиная со второго измерения.
22. При разделении данных в начало индексов добавляется либо поле единственного независимого разделителя нестрокового типа, либо поле хэша значений разделителей (ОРРХ).
23. Таблицы регистрации изменений всегда имеют два индекса: `Узел + Номер сообщения + Ключ данных` и `Ключ данных + Узел + Номер сообщения`.
24. Механизм «дополнительных индексов» доступен только при наличии КОРП-лицензии; в одном индексе не более 16 физических колонок, число индексов не ограничено; поля из разных источников (объект, табличная часть, виртуальная таблица) в одном индексе смешивать нельзя; поля типа «Двоичные данные» и «Строка» неограниченной длины не индексируются.

## 1. Размещение данных 1С:Предприятия 8

- Дата публикации: 26.03.2019
- Ссылка: https://its.1c.ru/db/metod8dev/content/1591/hdoc
- Применимость на октябрь 2026: **частично устарело**.

Почему «частично устарело». Хотя дата публикации — 2019 год, текст по содержанию относится к эпохе 8.0–8.2: упоминается «1С:Предприятие 8.0», каталоги `1cv82`, пути Windows вида `C:/Documents and Settings/...` и `C:\WINNT\Temp`, скрипт запуска `/etc/init.d/srv1cv82` с файлом параметров `/etc/sysconfig/srv1cv82`, HASP License Manager, IBM DB2 в числе поддерживаемых СУБД. Все примеры путей — для Windows; для Linux названы только два файла `srv1cv82`. Перечень служебных и прикладных таблиц отражает состояние платформы тех лет: во второй статье конспекта (2025 год) упоминаются таблицы, которых здесь нет (история данных, копии базы данных, сервисы интеграции, табличные пространства и др.).

Что остаётся верным как принцип: деление данных на группы по ответственности, хранение всей информационной базы в одной базе данных, набор обязательных служебных таблиц и логика их проверки при старте, схема именования прикладных таблиц (префикс + номер), требование резервировать базу только целиком, размещение журнала регистрации и данных полнотекстового поиска в рабочем каталоге кластера, некритичность профайлов. Конкретные пути, имена каталогов и способ запуска сервера на Linux нужно сверять с актуальной документацией к используемой версии платформы.

### 1.1. Назначение статьи и главная оговорка

- Статья показывает, в каких файлах и таблицах базы данных платформа хранит свои данные и как информация распределена между ними — для файлового и клиент-серверного вариантов.
- Адресаты — разработчики прикладных решений и администраторы информационных баз.
- Оговорка авторов: информация предназначена исключительно для понимания расположения и состава данных. Использовать её для работы с данными способами, не предусмотренными штатными механизмами 1С:Предприятия 8, нельзя.
- Рассматриваются только данные, которые платформа использует всегда, независимо от конфигурации и действий пользователя. Файлы конфигураций, выгрузки данных, внешние обработки и прочие внешние по отношению к платформе файлы не рассматриваются.

### 1.2. Пять групп данных

Данные разделены на пять групп по назначению и степени ответственности.

| Группа | Что содержит | Насколько критична |
|--------|--------------|--------------------|
| Информационная база | Конфигурация, все данные о хозяйственной деятельности, административная информация. Всё это объединено в базу данных. | Наиболее ответственная информация: потеря или искажение части данных может привести к потере работоспособности системы. |
| Хранилище конфигурации | Текущая конфигурация и история её разработки (средства групповой разработки конфигуратора). | Для процесса разработки — «жизненно важная» информация. |
| Журнал регистрации | Список операций, выполненных над информационной базой. | Для работы системы не нужен, но может быть важен с организационной точки зрения. |
| Вспомогательные данные | Служат удобству пользователя, на логику работы не влияют. Две подгруппы: профайлы (расположение окон, текущие позиции, состояние диалогов, прочие настройки комфорта; конфигурации могут хранить в них и другую полезную, но не обязательную информацию) и другие вспомогательные данные (списки информационных баз, зарегистрированных на клиенте или на сервере, и некоторые иные данные). | На логику работы не влияют. Оговорка из того же источника: данные файла `srvribrg.lst` необходимы для нормальной работы приложений, использующих сервер (см. 1.7). |
| Временные данные | Служебные данные приложения, актуальные в пределах одного сеанса. | После завершения сеанса уничтожаются. |

Размещение данных разных групп различается; дополнительное разнообразие вносят два варианта информационных баз — файловый и клиент-серверный.

### 1.3. Организация информационной базы

#### СУБД

Информационная база хранится в базе данных как набор таблиц. Статья называет пять СУБД:

| СУБД | Вариант | Где лежат данные |
|------|---------|------------------|
| Встроенная в 1С:Предприятие 8 | файловый | Всё в одном файле `1cv8.1cd` (двоичный формат; по сути это база данных встроенной СУБД). |
| Microsoft SQL Server | клиент-серверный | В базе данных Microsoft SQL Server. |
| PostgreSQL | клиент-серверный | В базе данных PostgreSQL. |
| IBM DB2 | клиент-серверный | В базе данных IBM DB2. |
| Oracle Database | клиент-серверный | В базе данных Oracle Database. |

На уровне объектов базы данных (таблицы, поля, индексы) формат файлового и клиент-серверного вариантов сходен и отличается несущественными деталями.

#### Обязательные служебные таблицы

Присутствуют в представлении любой информационной базы:

| Таблица | Назначение |
|---------|------------|
| `Config` | Основная конфигурация информационной базы. Соответствует реальной структуре данных и используется в режиме Предприятия. |
| `ConfigSave` | Конфигурация, редактируемая конфигуратором. Переписывается в `Config` при «Обновлении конфигурации базы данных»; обратное направление — операция «Конфигурация — Конфигурация базы данных — Вернуться к конфигурации БД». |
| `Files` | Служебная информация, например о работе с хранилищем конфигурации. |
| `Params` | Параметры информационной базы: национальные настройки; таблица соответствия объектов метаданных объектам базы данных (таблицам, полям, индексам); некоторая другая информация. |
| `_YearOffset` | Смещение дат в базе данных. Создаётся только при использовании Microsoft SQL Server. |
| `DBSchema` | Информация о структуре базы данных 1С:Предприятия; определяет другие объекты базы данных, используемые данной информационной базой. |
| `v8users` | Список пользователей. |
| `_UsersWorkHistory` | История работы пользователей. |
| `_SystemSettings` | Хранилище системных настроек. |
| `_RepSettings` | Хранилище настроек отчётов. |
| `_RepVarSettings` | Хранилище настроек вариантов отчётов. |
| `_CommonSettings` | Хранилище общих настроек. |
| `_FrmDtSettings` | Хранилище настроек данных форм. |

Поведение при старте:

- платформа проверяет наличие перечисленных таблиц;
- отсутствует какая-либо одна — выдаётся сообщение «информационная база разрушена»;
- отсутствуют все — информационная база считается пустой, таблицы будут созданы.

#### Именование прикладных таблиц

- Состав и структура остальных таблиц определяются конфигурацией — объявленными в ней объектами метаданных.
- Имя таблицы = буквенный префикс + номер. Префикс задаёт назначение таблицы, номер различает таблицы одного назначения, относящиеся к разным объектам метаданных.
- IBM DB2: такую структуру имеют не имена таблиц, а их псевдонимы, причём префиксы псевдонимов начинаются сразу с буквенной части, без подчёркивания.
- В именах ниже `<n>`, `<k>`, `<i>` — числовые части имени. Отдельно источник расшифровывает только `<i>` (от 1 до максимального количества субконто); про `<n>` сказано лишь, что номер различает таблицы разных объектов метаданных, `<k>` не поясняется.

#### Таблицы распределённой информационной базы

Создаются, если в конфигурации есть хотя бы один план обмена с установленным флагом «Распределенная информационная база»:

| Таблица | Назначение |
|---------|------------|
| `_ConfigChangeRec` | Регистрация изменений объектов конфигурации. |
| `_ConfigChangeRec_ExtProps` | Имена файлов изменённых внешних свойств объектов конфигурации. |

#### Таблицы по объектам метаданных

Общее правило для таблиц регистрации изменений (`…ChngR…`): создаются, только если соответствующий объект участвует хотя бы в одном плане обмена.

| Объект метаданных | Таблица | Назначение и условие создания |
|-------------------|---------|-------------------------------|
| Константы | `_Consts` | Текущие значения всех констант конфигурации. |
| | `_ConstsChngR` | Регистрация изменений констант. Создаётся, если хотя бы одна константа участвует хотя бы в одном плане обмена. |
| Планы обмена | `_Node<n>` | Таблица плана обмена. |
| | `_Node<n>_VT<k>` | Табличная часть плана обмена — для каждой табличной части. |
| Справочники | `_Reference<n>` | Таблица справочника. |
| | `_Reference<n>_VT<k>` | Табличная часть справочника — для каждой табличной части. |
| | `_ReferenceChngR<n>` | Регистрация изменений справочника (участие в плане обмена). |
| Документы | `_Document<n>` | Таблица документов — для каждого объекта метаданных «документ». |
| | `_Document<n>_VT<k>` | Табличная часть документа — для каждой табличной части каждого документа. |
| | `_DocumentChngR<n>` | Регистрация изменений документа (участие в плане обмена). |
| Последовательности документов | `_Seq<n>` | Таблица регистрации документов — для каждой последовательности. |
| | `_SeqB<n>` | Таблица границ последовательности — для каждой последовательности. |
| | `_SeqChngR<n>` | Регистрация изменений последовательности (участие в плане обмена). |
| Журналы документов | `_DocumentJournal<n>` | Таблица журнала документов — для каждого журнала. |
| Перечисления | `_Enum<n>` | Таблица перечисления — по одной на перечисление. |
| Планы видов характеристик | `_Chrc<n>` | Основная таблица плана видов характеристик. |
| | `_Chrc<n>_VT<k>` | Табличная часть — для каждой табличной части. |
| | `_ChrcChngR<n>` | Регистрация изменений (участие в плане обмена). |
| Планы счетов | `_Acc<n>` | Основная таблица плана счетов. |
| | `_Acc<n>_ExtDim<k>` | Таблица видов субконто. Создаётся, если максимальное количество субконто больше нуля. |
| | `_Acc<n>_VT<k>` | Табличная часть — для каждой табличной части. |
| | `_AccChngR<n>` | Регистрация изменений (участие в плане обмена). |
| Планы видов расчёта | `_CKind<n>` | Основная таблица плана видов расчёта. |

#### Предупреждения авторов: целостность, доступ, резервное копирование

- Таблиц может быть очень много — их количество зависит от функциональности конфигурации.
- В штатном режиме платформа не проверяет наличие этих таблиц, а также целостность и непротиворечивость данных в них.
- Отсюда два требования: база данных должна быть защищена от несанкционированного доступа, а её модификация должна выполняться только средствами 1С:Предприятия.
- Для проверки используется встроенная в конфигуратор функция «Администрирование — Тестирование и исправление».
- Резервное копирование и восстановление базы данных с информационной базой должно выполняться только целиком. Для этого рекомендуются средства резервного копирования, встроенные в используемую СУБД.
- Файловый вариант: резервная копия — это копия файла `1cv8.1cd`.
- Конфигуратор: «Администрирование — Выгрузить информационную базу» выгружает в файл все данные, относящиеся к информационной базе, и никакие другие; «Загрузить информационную базу» заменяет существующие данные текущей базы данными из файла выгрузки. Эти функции тоже можно применять для резервного копирования — и в файловом, и в клиент-серверном варианте.

### 1.4. Хранилище конфигурации

- Используется при групповой разработке; хранит историю версий конфигурации, включая последнюю (текущую).
- Всё хранилище — один файл `1Cv8ddb.1cd` в каталоге, заданном как каталог хранилища конфигурации.
- При разработке с использованием групповых средств данные этого файла жизненно важны, поэтому рекомендуется его резервное копирование.

### 1.5. Журнал регистрации

- Относится к информационной базе; хранит сведения о событиях, возникающих при работе пользователей с ней. Может быть важен организационно, но для функционирования прикладного решения не нужен.
- Хранится в каталогах `1Cv8Log` — по одному на каждую информационную базу.
- Состав каталога:
  - `1Cv8.lgf` — общая информация журнала регистрации;
  - несколько файлов `yyyyMMddhhmmss.lgp` (год, месяц, день, час, минута, секунда), например `20070525200000.lgp`. Каждый файл содержит фрагмент журнала за период; имя файла — момент начала периода. Длина периода задаётся настройкой журнала «Разделять хранение журнала по периодам».
- Расположение:

| Вариант базы | Где лежит журнал | Пример из источника |
|--------------|------------------|---------------------|
| Файловый | В каталоге информационной базы, рядом с файлом базы. | База `C:/EnterpriseInfoBase/1cv8.1cd` → журнал в `C:/EnterpriseInfoBase/1Cv8log` |
| Клиент-серверный | В подкаталоге рабочего каталога кластера; имя подкаталога — идентификатор информационной базы. | `C:/Program Files/1cv82/server/reg_1541/fb9d9cc4-ccd0-4be7-87e8-c5182945291e/1Cv8Log` |

- За подробностями о рабочем каталоге центрального сервера и кластера источник отсылает к разделу «Хранение настроек кластера серверов 1С:Предприятия 8».
- Устаревание: пример пути относится к Windows и версии 8.2; описан только формат хранения в файлах `.lgf`/`.lgp`. Правило «журнал лежит в `<рабочий каталог кластера>/<идентификатор ИБ>/1Cv8Log`» — ориентир, конкретный путь на Linux в источнике не приведён.

### 1.6. Профайлы

- Содержат информацию, не влияющую на логику работы: формат и расположение окон и диалогов, настройки шрифтов, цветов, отборов и т. п. Потеря этой информации не может нарушить работоспособность системы.
- Подробнее о назначении профайлов и хранении пользовательских настроек — в разделе «Сохранение параметров настроек пользователя между сеансами» (ссылка источника).

Хранилище конфигурации и шаблоны:

- Группа файлов `CACHE/ddb<n>.snp` — в каталоге хранилища конфигурации; кеш запрошенных версий конфигурации. Необязательны, ускоряют получение версий.
- `*.1ccr` — конфигурационный файл веб-сервиса для работы с удалённым хранилищем. Имя произвольное, расширение `1ccr` обязательно; формат XML с единственным узлом произвольного имени и атрибутом `connectString`, в котором указывается адрес сервера хранилища в схеме `tcp`.
- `*.mft` — файл-манифест, описывающий шаблон конфигурации. Имя произвольное; лежит в каталоге установленного шаблона конфигурации.

Конфигурационные файлы платформы (каталог конфигурационных файлов системы «1С:Предприятие», если не сказано иное):

- `conf.cfg` — определяет расположение каталога общих конфигурационных файлов. Лежит в `bin\conf` каталога конкретной версии платформы; текстовый документ в UTF-8.
- `adminstall.cfg` — признак того, что установка выполнялась средствами администрирования операционной системы. Текстовый документ в UTF-8.
- `logcfg.xml` — настройка технологического журнала. Наличие необязательно.
- `debugcfg.xml` — настройка дополнительного диапазона портов, используемого при отладке конфигураций. Наличие необязательно.
- `comcntrcfg.xml` — указывает внешнему соединению на необходимость запуска в отладочном режиме. Наличие необязательно (в источнике фраза о расположении и необязательности вынесена отдельным пунктом сразу после этого файла).
- `inetcfg.xml` — настройки прокси по умолчанию; имеет приоритет над настройками прокси по умолчанию в Windows. Наличие необязательно.
- `default.vrd` — настройка веб-клиента и использования веб-сервисов; находится в каталоге виртуального приложения.

Лицензирование:

- `nethasp.ini` — параметры взаимодействия платформы с HASP License Manager. Каталог конфигурационных файлов; наличие необязательно.
- `nhsrv.ini` — часть настроек самого HASP License Manager. При запуске менеджер ищет файл в таком порядке:
  1. каталог, где лежит исполняемый файл HASP License Manager;
  2. текущий каталог Windows;
  3. системный каталог Microsoft Windows (`%SystemRoot%\system32` — для 32-разрядной версии и `%SystemRoot%\system` — для 64-разрядной версии; ⚠ в источнике записано именно так);
  4. каталог Microsoft Windows;
  5. каталоги из переменной окружения `PATH` (только если HASP License Manager установлен как приложение Microsoft Windows).

  Рекомендация: при необходимости размещать `nhsrv.ini` в каталоге исполняемого файла HASP License Manager. Убедиться, что менеджер нашёл и прочитал файл, можно по журналу Activity Log / Server Activity Log.
- `*.lic` — лицензии базовых конфигураций (`C:\Documents and Settings\All Users\Application Data\1C\licenses`). Файлы программных лицензий расположены в каталоге конфигурационных файлов системы «1С:Предприятие».

### 1.8. Временные данные

Временные данные нужны либо нескольким пересекающимся во времени сеансам, либо одному сеансу.

Данные совместного использования файловой базы (относятся к базе в целом, нужны, в частности, для блокировок данных) лежат в том же каталоге, что и файл информационной базы:

| Файл | Назначение |
|------|------------|
| `1Cv8cl` (так в источнике) | Носитель блокировок объектов базы данных, расположенной в файле … ⚠ в источнике неясно: имя файла базы в тексте пропущено, а имя самого файла блокировок записано без точки. |
| `1Cv8Tmp.1cd` | Служебная сеансовая информация, в частности список активных пользователей. |
| `1Cv8Tmp.1cl` | Носитель блокировок данных, расположенных в `1Cv8Tmp.1cd`. |

Аналогичные временные файлы конфигуратор создаёт для хранилища конфигурации — в каталоге хранилища:

| Файл | Назначение |
|------|------------|
| `1Cv8ddb.1cl` | Носитель блокировок данных из хранилища конфигурации. |
| `1Cv8dtmp.1cd` | Служебная сеансовая информация, в частности список активных пользователей хранилища. |
| `1Cv8dtmp.1cl` | Носитель блокировок данных, расположенных в файле `1Cv8ddb.1cd` (⚠ так в источнике; по аналогии с файловой базой ожидалось бы `1Cv8dtmp.1cd`). |

Данные одного сеанса размещаются во временных файлах в каталоге, определённом в Microsoft Windows как каталог временных файлов:

- клиентское приложение — каталог временных файлов текущего пользователя Windows, например `C:\Documents and Settings\User\Local Settings\Temp`;
- сервер 1С:Предприятия — либо системный каталог временных файлов, либо каталог данных приложений пользователя, от имени которого запускаются рабочие процессы сервера, например `C:\WINNT\Temp`.

Про расположение временных файлов сервера в Linux источник ничего не говорит.

## 2. Индексы таблиц базы данных

- Дата публикации: 27.05.2025; в шапке статьи указана версия платформы «1С:Предприятие» 8.3.27
- Ссылка: https://its.1c.ru/db/metod8dev/content/1590/hdoc
- Применимость на октябрь 2026: **актуально**.

Почему «актуально». Публикация свежая (май 2025), привязана к платформе 8.3.27 и охватывает современные механизмы: разделение данных, историю данных, копии базы данных, сервисы интеграции, табличные пространства, дополнительные индексы. Ограничения, о которых стоит помнить: состав индексов описан логически, в терминах полей таблиц языка запросов 1С, без привязки к конкретной СУБД — физические имена индексов и колонок не приводятся, и не сказано, как пометка «Кластерный» реализуется в PostgreSQL. Для платформы новее 8.3.27 перечень следует сверять с текущей редакцией статьи.

### 2.1. Назначение и условные обозначения

- Статья перечисляет индексы, которые система 1С:Предприятие 8 создаёт на таблицах базы данных. Индексы создаются неявно: при создании объектов конфигурации и при тех или иных настройках этих объектов. Там, где создание зависит от настроек, приведено условие.
- Назначение материала по словам авторов: им следует руководствоваться при написании текстов запросов, чтобы оптимизировать время их исполнения.
- Имена индексных полей даны так, как они описаны в разделе документации «Таблицы запросов».

Обозначения:

| Обозначение | Смысл |
|-------------|-------|
| `Измерение1`, `Реквизит1` и т. п. | Условные имена измерений, реквизитов и т. д. |
| `ОРНР` (`ОРНР1`, `ОРНР2`, …) | Общие реквизиты-разделители в режиме «независимо». |
| `ОРСР` | Общие реквизиты-разделители в режиме «независимо и совместно». |
| `ОРР` | Общие реквизиты-разделители, когда режим разделения не важен. |
| `ОРРХ` | Поле со значением хэш-функции набора значений разделителей; может входить в индексы, если в конфигурации определены разделители. |
| `[ … ]` | Необязательные индексные поля. |
| `…` (многоточие) | Набор однотипных полей, например `Реквизит + Измерение1 + [Измерение2 +...]`. |
| `(Кластерный)` | Пометка источника: индекс кластерный. |

Правило для префикса `[ОРРХ | ОРНР1 +]` (действует для всех индексов, где он указан):

- объект разделяется одним независимым разделителем, и тип разделителя не Строка → в индекс входит поле этого разделителя;
- тип разделителя — Строка, либо разделитель «независимый и совместный», либо разделителей больше одного → в индекс входит поле значения хэш-функции значений разделителей.

Префикс `[ОРНР1 + ... +]` означает, что в индекс входят поля независимых разделителей, которыми разделён данный объект.

Сокращения условий в этом конспекте:

- «Индексировать» — у поля свойство «Индексировать» установлено в значение «Индексировать»;
- «с доп. упорядочиванием» — свойство «Индексировать» установлено в значение «Индексировать с доп. упорядочиванием»;
- «критерий отбора» — объект включён в критерий отбора через этот реквизит.

### 2.2. Справочник

Основные индексы:

- `[ОРНР1 + ... +] Ссылка` (Кластерный) — всегда. Входят поля независимых разделителей, разделяющих справочник.
- `[ОРРХ | ОРНР1 +] Код + Ссылка` — «Длина кода» ≠ 0.
- `[ОРРХ | ОРНР1 +] Наименование + Ссылка` — «Длина наименования» ≠ 0.
- `[ОРРХ | ОРНР1 +] Реквизит + Ссылка` — «Индексировать».
- `[ОРРХ | ОРНР1 +] Реквизит + Код + Ссылка` — «с доп. упорядочиванием», при этом «Длина кода» ≠ 0 и «Основное представление» = «В виде кода».
- `[ОРРХ | ОРНР1 +] Реквизит + Наименование + Ссылка` — «с доп. упорядочиванием», при этом «Длина наименования» ≠ 0 и «Основное представление» = «В виде наименования».
- `[ОРРХ | ОРНР1 +] Реквизит` — критерий отбора.
- `[ОРРХ | ОРНР1 +] PredefinedID` — индекс по идентификатору предопределённого объекта метаданных (условие в источнике не указано).

Дополнительные индексы подчинённого справочника (независимо от иерархичности):

- `[ОРРХ | ОРНР1 +] Владелец + Ссылка` — «Длина кода» = 0.
- `[ОРРХ | ОРНР1 +] Владелец + Код + Ссылка` — «Длина кода» ≠ 0.
- `[ОРРХ | ОРНР1 +] Владелец + Наименование + Ссылка` — «Длина наименования» ≠ 0.
- `[ОРРХ | ОРНР1 +] Владелец + Реквизит + Ссылка` — «Индексировать».
- `[ОРРХ | ОРНР1 +] Владелец + Реквизит + Код + Ссылка` — «с доп. упорядочиванием», «Длина кода» ≠ 0, основное представление «В виде кода».
- `[ОРРХ | ОРНР1 +] Владелец + Реквизит + Наименование + Ссылка` — «с доп. упорядочиванием», «Длина наименования» ≠ 0, основное представление «В виде наименования».

Дополнительные индексы иерархического неподчинённого справочника. Состав ниже — для справочника со свойством «Размещать группы сверху»: тогда рядом с полем Родитель в индексах участвует поле ЭтоГруппа. Если группы сверху не размещаются, состав тот же, но без поля ЭтоГруппа.

- `[ОРРХ | ОРНР1 +] Родитель + ЭтоГруппа + Ссылка` — «Длина кода» = 0 и «Длина наименования» = 0.
- `[ОРРХ | ОРНР1 +] Родитель + ЭтоГруппа + Код + Ссылка` — «Длина кода» ≠ 0.
- `[ОРРХ | ОРНР1 +] Родитель + ЭтоГруппа + Наименование + Ссылка` — «Длина наименования» ≠ 0.
- `[ОРРХ | ОРНР1 +] Родитель + ЭтоГруппа + Реквизит + Ссылка` — «Индексировать».
- `[ОРРХ | ОРНР1 +] Родитель + ЭтоГруппа + Реквизит + Код + Ссылка` — «с доп. упорядочиванием», «Длина кода» ≠ 0, основное представление «В виде кода».
- `[ОРРХ | ОРНР1 +] Родитель + ЭтоГруппа + Реквизит + Наименование + Ссылка` — «с доп. упорядочиванием», «Длина наименования» ≠ 0, основное представление «В виде наименования».

Дополнительные индексы иерархического подчинённого справочника. То же правило про «Размещать группы сверху» и поле ЭтоГруппа (без размещения групп сверху поле ЭтоГруппа в индексы не входит).

- `[ОРРХ | ОРНР1 +] Владелец + Родитель + ЭтоГруппа + Ссылка` — «Длина кода» = 0 и «Длина наименования» = 0.
- `[ОРРХ | ОРНР1 +] Владелец + Родитель + ЭтоГруппа + Код + Ссылка` — «Длина кода» ≠ 0.
- `[ОРРХ | ОРНР1 +] Владелец + Родитель + ЭтоГруппа + Наименование + Ссылка` — «Длина наименования» ≠ 0.
- `[ОРРХ | ОРНР1 +] Владелец + Родитель + ЭтоГруппа + Реквизит + Ссылка` — «Индексировать».
- `[ОРРХ | ОРНР1 +] Владелец + Родитель + ЭтоГруппа + Реквизит + Код + Ссылка` — «с доп. упорядочиванием», «Длина кода» ≠ 0, основное представление «В виде кода».
- `[ОРРХ | ОРНР1 +] Владелец + Родитель + ЭтоГруппа + Реквизит + Наименование + Ссылка` — «с доп. упорядочиванием», «Длина наименования» ≠ 0, основное представление «В виде наименования».

Таблица опций справочника:

- `[ОРРХ | ОРНР1 +] Идентификатор` (Кластерный) — всегда.

### 2.3. Документ

- `[ОРНР1 + ... +] Ссылка` (Кластерный) — всегда. Входят поля независимых разделителей, разделяющих документ.
- `[ОРРХ | ОРНР1 +] Дата + Ссылка` — всегда.
- `[ОРРХ | ОРНР1 +] Номер + Ссылка` — «Длина номера» ≠ 0.
- `[ОРРХ | ОРНР1 +] Реквизит + Ссылка` — «Индексировать».
- `[ОРРХ | ОРНР1 +] Реквизит + Дата + Ссылка` — «с доп. упорядочиванием».
- `[ОРРХ | ОРНР1 +] Реквизит` — критерий отбора.
- `[ОРРХ | ОРНР1 +] ПрефиксНомера + Номер + Ссылка` — «Длина номера» ≠ 0.

### 2.4. Журнал документов

- `[ОРРХ | ОРНР1 +] Ссылка` (Кластерный) — всегда.
- `[ОРРХ | ОРНР1 +] Дата + Ссылка` — всегда.
- `[ОРРХ | ОРНР1 +] Графа + Ссылка` — у графы журнала «Индексировать».
- `[ОРРХ | ОРНР1 +] Графа + Дата + Ссылка` — у графы журнала «с доп. упорядочиванием».

### 2.5. Планы видов характеристик, планы счетов, планы видов расчёта, планы обмена

План видов характеристик:

- Индексы — как у справочника, с поправками: длина кода и длина наименования не могут быть равны нулю, и план видов характеристик не может быть подчинённым.
- Таблица опций плана видов характеристик: `Идентификатор` — всегда.

План счетов:

- `[ОРНР1 + ... +] Ссылка` (Кластерный) — всегда. Входят поля независимых разделителей, разделяющих план счетов.
- `[ОРРХ | ОРНР1 +] Код + Ссылка` — всегда.
- `[ОРРХ | ОРНР1 +] Родитель + Код + Ссылка` — всегда.
- `[ОРРХ | ОРНР1 +] Наименование + Ссылка` — всегда.
- `[ОРРХ | ОРНР1 +] Родитель + Наименование + Ссылка` — всегда.
- `[ОРРХ | ОРНР1 +] Порядок + Ссылка` — «Длина порядка» ≠ 0.
- `[ОРРХ | ОРНР1 +] Родитель + Порядок + Ссылка` — «Длина порядка» ≠ 0.
- `[ОРРХ | ОРНР1 +] Реквизит + Ссылка` — «Индексировать».
- `[ОРРХ | ОРНР1 +] Родитель + Реквизит + Ссылка` — «Индексировать».
- `[ОРРХ | ОРНР1 +] Реквизит + Порядок + Ссылка` — «с доп. упорядочиванием» и «Длина порядка» ≠ 0.
- `[ОРРХ | ОРНР1 +] Родитель + Реквизит + Порядок + Ссылка` — «с доп. упорядочиванием» и «Длина порядка» ≠ 0.
- `[ОРРХ | ОРНР1 +] Реквизит + Код + Ссылка` — «с доп. упорядочиванием», «Длина порядка» = 0, основное представление «В виде кода».
- `[ОРРХ | ОРНР1 +] Родитель + Реквизит + Код + Ссылка` — «с доп. упорядочиванием», «Длина порядка» = 0, основное представление «В виде кода».
- `[ОРРХ | ОРНР1 +] Реквизит + Наименование + Ссылка` — «с доп. упорядочиванием», «Длина порядка» = 0, основное представление «В виде наименования».
- `[ОРРХ | ОРНР1 +] Родитель + Реквизит + Наименование + Ссылка` — «с доп. упорядочиванием», «Длина порядка» = 0, основное представление «В виде наименования».
- `[ОРРХ | ОРНР1 +] Реквизит` — критерий отбора.
- `[ОРРХ | ОРНР1 +] PredefinedID` — индекс по идентификатору предопределённого объекта метаданных.
- Таблица опций плана счетов: `Идентификатор` — всегда.

План видов расчёта:

- Индексы — см. основные индексы справочника.
- Таблица опций плана видов расчёта: `Идентификатор` — всегда.

План обмена:

- Индексы — см. основные индексы справочника, с поправкой: длина кода и длина наименования плана обмена не могут быть равны нулю.

Замечание: у таблиц опций плана видов характеристик, плана счетов и плана видов расчёта индекс в источнике записан просто как `Идентификатор` — без префикса разделителей и без пометки «Кластерный», в отличие от таблиц опций справочника и регистров.

### 2.6. Табличная часть

Относится ко всем таблицам, предоставляющим доступ к табличным частям объектов.

- `[ОРНР1 + ... +] Ссылка + Ключ` (Кластерный) — всегда. Входят поля независимых разделителей, разделяющих объект-владелец табличной части.
- `[ОРРХ | ОРНР1 +] Реквизит + Ссылка` — объект конфигурации включён в критерий отбора через реквизит табличной части, либо для реквизита табличной части установлено свойство «Индексировать».
- `[ОРРХ | ОРНР1 +] PredefinedID` — индекс по идентификатору предопределённого объекта метаданных.

### 2.7. Регистр сведений

Непериодический регистр сведений:

- `[ОРРХ | ОРНР1 +] Измерение1 + [Измерение2 +...]` (Кластерный) — есть хотя бы одно измерение. Включает все измерения в порядке, заданном при конфигурировании. Кластерным индекс является, если регистр независимый.
- `[ОРРХ | ОРНР1 +] ИзмерениеN + Измерение1 + [Измерение2 +...]` — измерению ИзмерениеN задано свойство «Индексировать» или «Ведущее», и это не первое и не единственное измерение. Первое поле — ИзмерениеN, далее остальные измерения в порядке конфигурирования.
- `[ОРРХ | ОРНР1 +] Реквизит + Измерение1 + [Измерение2 +...]` — реквизиту задано «Индексировать». Первое поле — Реквизит, далее все измерения в порядке конфигурирования.
- `[ОРРХ | ОРНР1 +] Ресурс + Измерение1 + [Измерение2 +...]` — ресурсу задано «Индексировать». Первое поле — Ресурс, далее все измерения в порядке конфигурирования.

Периодический регистр сведений:

- `[ОРРХ | ОРНР1 +] Период + [Измерение1 + ...]` — всегда.
- `[ОРРХ | ОРНР1 +] Измерение1 + [Измерение2 +...] + Период` (Кластерный) — есть хотя бы одно измерение. Все измерения в порядке конфигурирования, затем поле Период.
- `[ОРРХ | ОРНР1 +] ИзмерениеN + Период + Измерение1 + [Измерение2 +...]` — измерению ИзмерениеN задано «Индексировать» или «Ведущее», и это не единственное измерение. Первое поле — ИзмерениеN, затем Период, затем остальные измерения в порядке конфигурирования.
- `[ОРРХ | ОРНР1 +] Реквизит + Период + [Измерение1 + ...]` — реквизиту задано «Индексировать». Реквизит, затем Период, затем все измерения в порядке конфигурирования.
- `[ОРРХ | ОРНР1 +] Ресурс + Период + [Измерение1 + ...]` — ресурсу задано «Индексировать». Ресурс, затем Период, затем все измерения в порядке конфигурирования.

Дополнительный индекс регистра сведений, подчинённого регистратору:

- `[ОРНР1 + ... +] Регистратор + НомерСтроки` (Кластерный) — всегда. Входят поля независимых разделителей, разделяющих регистр. Кластерным индекс является, если регистр непериодический.

Регистр сведений с периодичностью «По позиции регистратора»:

- `[ОРРХ | ОРНР1 +] Период + Регистратор + НомерСтроки` — всегда.
- `[ОРНР1 + ... +] Регистратор + НомерСтроки` — всегда. Входят поля независимых разделителей, разделяющих регистр.
- `[ОРРХ | ОРНР1 +] Измерение1 + [Измерение2 + ...] + Период + Регистратор + НомерСтроки` (Кластерный) — есть хотя бы одно измерение. Все измерения в порядке конфигурирования, затем Период и Регистратор.
- `[ОРРХ | ОРНР1 +] Измерение + Период + Регистратор + НомерСтроки` — измерению задано «Индексировать».
- `[ОРРХ | ОРНР1 +] Реквизит + Период + Регистратор + НомерСтроки` — реквизиту задано «Индексировать».
- `[ОРРХ | ОРНР1 +] Ресурс + Период + Регистратор + НомерСтроки` — ресурсу задано «Индексировать».

Подразделы «ИтогиСрезПервых» и «ИтогиСрезПоследних» (в источнике это два отдельных подраздела регистра сведений с одинаковым составом индексов):

- `[ОРРХ | ОРНР1 +] Измерение1 + [Измерение2 + ...] + Период` (Кластерный) — есть хотя бы одно измерение. Включает все измерения в порядке конфигурирования.
- `[ОРРХ | ОРНР1 +] Реквизит + [Измерение1 + ...]` — реквизиту задано «Индексировать».
- `[ОРРХ | ОРНР1 +] Ресурс + [Измерение1 + ...]` — ресурсу задано «Индексировать».
- `[ОРРХ | ОРНР1 +] ИзмерениеN + Измерение1 + [Измерение2 +...]` — измерению ИзмерениеN задано «Индексировать» или «Ведущее», и это не единственное измерение. Первое поле — ИзмерениеN, далее остальные измерения в порядке конфигурирования.

### 2.8. Регистр накопления

Основная таблица регистра:

- `[ОРРХ | ОРНР1 +] Период + Регистратор + НомерСтроки` (Кластерный) — всегда.
- `[ОРНР1 + ... +] Регистратор + НомерСтроки` — всегда. Входят поля независимых разделителей, разделяющих регистр.
- `[ОРРХ | ОРНР1 +] Измерение + Период + Регистратор + НомерСтроки` — измерению задано «Индексировать».
- `[ОРРХ | ОРНР1 +] Реквизит + Период + Регистратор + НомерСтроки` — реквизиту задано «Индексировать».

Таблица остатков:

- `[ОРРХ | ОРНР1 +] Период + Измерение1 + ... + ИзмерениеN + [DimHash] + [Splitter]` (Кластерный) — для регистров вида «Остатки».
- `[ОРРХ | ОРНР1 +] Период + Измерение` — измерению задано «Индексировать» (начиная со второго измерения).

Таблица оборотов:

- `[ОРРХ | ОРНР1 +] Период + Измерение1 + ... + ИзмерениеN + [DimHash] + [Splitter]` (Кластерный) — для регистров вида «Обороты».
- `[ОРРХ | ОРНР1 +] Измерение + Период` — измерению задано «Индексировать» (начиная со второго измерения).
- `Период + DimHash` — для регистров, у которых количество измерений не позволяет организовать уникальный индекс по измерениям.

Обратите внимание на порядок полей в источнике: для индексируемого измерения в таблице остатков записано `Период + Измерение`, в таблице оборотов — `Измерение + Период`.

Таблица опций регистра накопления:

- `[ОРРХ | ОРНР1 +] Идентификатор` (Кластерный) — всегда.

Агрегаты регистра накопления:

- Таблица агрегатов: `[ОРРХ | ОРНР1 +] Период + Измерение1 + ... + ИзмерениеN` (Кластерный) — всегда.
- Таблица статистики регистра накопления:
  - `[ОРРХ | ОРНР1 +] Идентификатор + Период + Splitter` (Кластерный) — всегда;
  - «Карта используемых измерений» — всегда. ⚠ в источнике неясно: состав этого индекса не раскрыт, приведено только название.
- Таблица опций сети агрегатов: `[ОРРХ | ОРНР1 +] Идентификатор` (Кластерный) — всегда.
- Таблица буфера новых оборотов регистра накопления: `[ОРРХ | ОРНР1 +] Период + Измерение1 + ... + ИзмерениеN` (Кластерный) — всегда.
- Таблица новых оборотов регистра накопления: `[ОРРХ | ОРНР1 +] Период + Измерение1 + ... + ИзмерениеN (Кластерный) + Splitter` — всегда. ⚠ в источнике неясно: пометка «(Кластерный)» стоит внутри записи, перед `+ Splitter`.
- Таблица кодов измерений регистра накопления: `[ОРРХ | ОРНР1 +] Период + UUID измерения 1 + ... + UUID измеренияN` (Кластерный) — всегда.
- Таблица сети агрегатов: `[ОРРХ | ОРНР1 +] Идентификатор + UUID измерения 1 + ... + UUID измеренияN` (Кластерный) — всегда.

### 2.9. Регистр бухгалтерии

Основная таблица регистра без корреспонденции:

- `[ОРРХ | ОРНР1 +] Период + Регистратор + НомерСтроки` (Кластерный) — всегда.
- `[ОРНР1 + ... +] Регистратор + НомерСтроки` — всегда. Входят поля независимых разделителей, разделяющих регистр.
- `[ОРРХ | ОРНР1 +] Счет + Период + Регистратор` — регистру назначен план счетов.
- `[ОРРХ | ОРНР1 +] Измерение + Период + Регистратор + НомерСтроки` — измерению задано «Индексировать».
- `[ОРРХ | ОРНР1 +] Реквизит + Период + Регистратор + НомерСтроки` — реквизиту задано «Индексировать».

Основная таблица регистра с корреспонденцией — состав тот же, но вместо одного индекса по счёту создаются два:

- `[ОРРХ | ОРНР1 +] СчетДт + Период + Регистратор` — регистру назначен план счетов.
- `[ОРРХ | ОРНР1 +] СчетКт + Период + Регистратор` — регистру назначен план счетов.

Таблица итогов по счёту — один индекс такого состава:

```
[ОРРХ | ОРНР1 +] Период
[+ Счет]
+ ИзмерениеБезПризнакаУчета1 + ...
+ ДополнительноеИзмерение1 + ...
+ ИзмерениеСПризнакомУчета1 + ...
[+ ХэшИзмерений]
[+ РазделительИтогов]
```

- поле «Счет» добавляется, если регистру определён план счетов;
- поле «ХэшИзмерений» добавляется, если количество других полей больше 15;
- поле «РазделительИтогов» добавляется, если включено разделение итогов.

Таблица итогов между счетами (только для регистров с поддержкой корреспонденции) — один индекс; состав приведён так, как он записан в источнике:

```
[ОРРХ | ОРНР1 +]
ИзмерениеДт1 + ИзмерениеКт1 + ...
Измерение1 + ...
[+ ХэшИзмерений]
[+ РазделительИтогов]
```

- строка `ИзмерениеДт1 + ИзмерениеКт1 + ...` — для небалансовых измерений;
- строка `Измерение1 + ...` — для балансовых измерений;
- «ХэшИзмерений» — если количество других полей больше 15; «РазделительИтогов» — если включено разделение итогов.
- ⚠ в источнике неясно: пояснения «для не балансовых измерений» и «для балансовых измерений» стоят в соседней колонке без явной привязки к строкам; соответствие восстановлено по порядку строк.

Таблица со значениями субконто:

- `[ОРРХ | ОРНР1 +] Регистратор + НомерСтроки + Корреспонденция` — всегда.
- `[ОРРХ | ОРНР1 +] Период + Регистратор + НомерСтроки + ВидСубконто + Корреспонденция` (Кластерный) — всегда.
- `[ОРРХ | ОРНР1 +] ВидСубконто + Значение` — всегда.

Таблица опций регистра бухгалтерии:

- `[ОРРХ | ОРНР1 +] Идентификатор` (Кластерный) — всегда.

### 2.10. Регистр расчёта

Основная таблица регистра расчёта (пометки «Кластерный» в источнике нет ни у одного индекса):

- `[ОРРХ | ОРНР1 +] ПериодРегистрации + Регистратор + НомерСтроки` — всегда.
- `[ОРНР1 + ... +] Регистратор + НомерСтроки` — всегда. Входят поля независимых разделителей, разделяющих регистр.
- `[ОРРХ | ОРНР1 +] ПериодРегистрации + [БазовоеИзмерение1 +...]` — всегда. ПериодРегистрации и все базовые измерения (измерения со свойством «Базовое») в порядке конфигурирования.
- `[ОРРХ | ОРНР1 +] [БазовоеИзмерение1 +...] + ПериодРегистрации` — есть хотя бы одно базовое измерение. Все базовые измерения, затем ПериодРегистрации.
- `[ОРРХ | ОРНР1 +] ПериодДействия + [БазовоеИзмерение1 +...]` — установлено свойство регистра расчёта «ПериодДействия». ПериодДействия и все базовые измерения в порядке конфигурирования.
- `[ОРРХ | ОРНР1 +] [БазовоеИзмерение1 +...] + ПериодДействия` — установлено свойство «ПериодДействия» и есть хотя бы одно базовое измерение. ⚠ в источнике неясно: в описании этого индекса сказано «по всем базовым измерениям и полю ПериодРегистрации», хотя в составе указан ПериодДействия.
- `[ОРРХ | ОРНР1 +] Измерение + ПериодРегистрации + Регистратор + НомерСтроки` — измерению задано «Индексировать».
- `[ОРРХ | ОРНР1 +] Реквизит + ПериодРегистрации + Регистратор + НомерСтроки` — реквизиту задано «Индексировать».

Таблица перерасчёта:

- `[ОРРХ | ОРНР1 +] Регистратор + ВидРасчета + [Измерение1 + ...]` — всегда. Регистратор, ВидРасчета и все измерения перерасчёта в порядке конфигурирования.

Таблица фактических периодов действия:

- `[ОРРХ | ОРНР1 +] Регистратор + НомерСтроки` — всегда. В описании источника добавлено, что в индекс входят поля независимых разделителей, разделяющих регистр.

Таблица опций регистра расчёта:

- `[ОРРХ | ОРНР1 +] Идентификатор` (Кластерный) — всегда.

### 2.11. Последовательности, перечисления, бизнес-процессы, задачи

Последовательности — основная таблица:

- `[ОРРХ | ОРНР1 +] Регистратор` — всегда.
- `[ОРРХ | ОРНР1 +] [Измерение1 + ...] + Период + Регистратор` — всегда. Все поля измерений в порядке конфигурирования, затем Период и Регистратор.

Последовательности — таблица границ:

- `[ОРРХ | ОРНР1 +] [Измерение1 + ...] + Период + Регистратор` — всегда. Состав тот же: измерения в порядке конфигурирования, Период, Регистратор.

Перечисления:

- `[ОРРХ | ОРНР1 +] Порядок + Ссылка` — всегда. Поле Порядок соответствует порядку, в котором значения перечисления расположены в дереве конфигурации.
- `[ОРНР1 + ... +] Ссылка` (Кластерный) — всегда. Входят поля независимых разделителей.

Бизнес-процессы — основная таблица:

- `[ОРНР1 + ... +] Ссылка` (Кластерный) — всегда. Входят поля независимых разделителей.
- `[ОРРХ | ОРНР1 +] Дата + Ссылка` — всегда.
- `[ОРРХ | ОРНР1 +] Номер + Ссылка` — «Длина номера» ≠ 0.
- `[ОРРХ | ОРНР1 +] Завершен + Дата + Ссылка` — всегда.
- `[ОРРХ | ОРНР1 +] Стартован + Дата + Ссылка` — всегда.
- `[ОРРХ | ОРНР1 +] ВедущаяЗадача + Ссылка` — всегда.
- `[ОРРХ | ОРНР1 +] Реквизит + Ссылка` — «Индексировать».
- `[ОРРХ | ОРНР1 +] Реквизит + Дата + Ссылка` — «с доп. упорядочиванием».
- `[ОРРХ | ОРНР1 +] Реквизит` — критерий отбора.

Бизнес-процессы — таблица точек маршрута:

- `[ОРНР1 + ... +] Ссылка` (Кластерный) — всегда. Входят поля независимых разделителей.
- `[ОРРХ | ОРНР1 +] Порядок + Ссылка` — всегда. Поле Порядок соответствует порядку, в котором точки маршрута вводились в графическую схему бизнес-процесса.

Задачи:

- `[ОРНР1 + ... +] Ссылка` (Кластерный) — всегда. Входят поля независимых разделителей.
- `[ОРРХ | ОРНР1 +] Дата + Ссылка` — всегда.
- `[ОРРХ | ОРНР1 +] Номер + Ссылка` — «Длина номера» ≠ 0.
- `[ОРРХ | ОРНР1 +] Наименование + Ссылка` — всегда.
- `[ОРРХ | ОРНР1 +] Выполнена + Наименование + Ссылка` — всегда.
- `[ОРРХ | ОРНР1 +] Выполнена + Дата + Ссылка` — всегда.
- `[ОРРХ | ОРНР1 +] БизнесПроцесс + ТочкаМаршрута + Ссылка` — всегда.
- `[ОРРХ | ОРНР1 +] Выполнена + БизнесПроцесс + ТочкаМаршрута + Ссылка` — всегда.
- `[ОРРХ | ОРНР1 +] БизнесПроцесс + Дата + Ссылка` — всегда.
- `[ОРРХ | ОРНР1 +] Реквизит + Ссылка` — «Индексировать».
- `[ОРРХ | ОРНР1 +] Реквизит + Дата + Ссылка` — «с доп. упорядочиванием».
- `[ОРРХ | ОРНР1 +] Реквизит` — критерий отбора.

Неточность источника: в описании кластерного индекса у перечислений, бизнес-процессов, точек маршрута и задач сказано, что в него входят независимые разделители, «которые разделяют этот регистр» — явно перенесённая из другого раздела формулировка; по смыслу речь о разделителях самого объекта.

### 2.12. Сервисы интеграции

Таблица настроек сервиса интеграции:

- `[ОРРХ | ОРНР1 +]` (Кластерный) — всегда. ⚠ в источнике неясно: после префикса разделителей не названо ни одного поля, а в пояснении говорится о разделителях, «которые разделяют этот план счетов» (формулировка из другого раздела).

Таблица очереди отправки канала сервиса интеграции:

- `[ОРРХ | ОРНР1 +] Идентификатор сообщения` (Кластерный) — всегда. Входят поля независимых разделителей, разделяющих сервис интеграции.
- `Позиция сообщения` — всегда.

Таблица очереди получения канала сервиса интеграции:

- `[ОРРХ | ОРНР1 +] Идентификатор сообщения` (Кластерный) — всегда. Входят поля независимых разделителей, разделяющих сервис интеграции.
- `Позиция сообщения` — всегда.

### 2.13. Таблицы регистрации изменений

Таблицы регистрации изменений разных объектов метаданных различаются только составом и типами полей «ключа данных» — набора полей, однозначно определяющих данные:

| Вид объекта | Ключ данных |
|-------------|-------------|
| Объектные типы (Справочник, Документ, ПланСчетов и др.) | Ссылка |
| Регистры, подчинённые регистратору (РегистрНакопления, РегистрБухгалтерии, РегистрСведений, подчинённый регистратору, и др.) | Регистратор |
| Регистры сведений, не подчинённые регистратору | Поля, входящие в основной отбор регистра. ⚠ в источнике неясно: написано «поля, соответствующие изменениям, входящим в основной отбор» — вероятно, имелись в виду измерения. |
| Константы | Идентификатор объекта метаданных Константы |

Индексы (оба — всегда):

- `[ОРРХ | ОРНР1 +] Узел + Номер сообщения + Ключ данных`
- `[ОРРХ | ОРНР1 +] Ключ данных + Узел + Номер сообщения`

### 2.14. Служебные таблицы: пользователи и хранилища настроек

Таблица списка пользователей:

- `Уникальный идентификатор пользователя` (Кластерный) — всегда.
- `Идентификатор набора ролей` — всегда.
- `Имя пользователя ОС` — всегда.
- `[ОРРХ +] Имя пользователя ОС` — в конфигурации определён хотя бы один разделитель.
- `Имя пользователя` — всегда.
- `[ОРРХ +] Имя пользователя` — в конфигурации определён хотя бы один разделитель.
- `[ОРРХ +] Полное имя пользователя` — всегда. Хэш значений разделителей входит в индекс, если в конфигурации определён хотя бы один разделитель.
- `Показывать пользователя в списке для диалога аутентификации` — всегда.
- `Разрешена аутентификация средствами 1С:Предприятия` — всегда.

Таблица истории работы пользователей:

- `[ОРРХ +] Уникальный идентификатор записи` — всегда.
- `[ОРРХ +] Уникальный идентификатор пользователя + Дата время` — всегда.
- `[ОРРХ +] Уникальный идентификатор пользователя + Хеш по URL` — всегда.
- `ОРРХ + ИспользованиеРазделителя1 + ...` — в конфигурации определён хотя бы один разделитель.

Для первых трёх индексов: хэш значений разделителей входит в индекс, если в конфигурации определён хотя бы один разделитель.

Таблицы хранилищ настроек. В источнике подряд идут десять заголовков и одна общая таблица индексов после них (по расположению она относится ко всем перечисленным хранилищам; отдельно это в тексте не оговорено):

- хранилище системных настроек;
- хранилище настроек отчётов;
- хранилище настроек вариантов отчётов;
- хранилище общих настроек;
- хранилище настроек данных форм;
- хранилище настроек динамических списков;
- хранилище настроек обработки ошибок;
- хранилище внешних данных навигационных ссылок;
- хранилище внутренних настроек;
- хранилище настроек стандартного интерфейса OData.

Индексы:

- `[ОРРХ +] Хеш от уникального идентификатора пользователя + Имя предмета настройки + Хеш от имени множественной (именованной) настройки + Версия настройки` — всегда. Хэш значений разделителей входит в индекс, если в конфигурации определён хотя бы один разделитель.
- `ОРРХ + ИспользованиеРазделителя1 + ...` — в конфигурации определён хотя бы один разделитель.

### 2.15. История данных

- Таблица очереди истории данных: `Идентификатор объекта метаданных + Идентификатор данных + Позиция сообщения в очереди` (Кластерный) — всегда.
- Таблица версий данных истории данных: `Идентификатор данных + Номер версии данных` (Кластерный) — всегда.
- Таблицы последних версий истории данных: `[ОРР1 + … + ] + Идентификатор объекта метаданных + Идентификатор данных` (Кластерный) — всегда. В индекс входят поля разделителей.
- Таблица версий метаданных истории данных:
  - `[ОРНР1 + … + ] + Идентификатор объекта метаданных + Флаг версия метаданных сформирована при изменении настроек + Флаг версия метаданных является актуальной + Номер актуальной версии метаданных` (Кластерный) — всегда. В индекс входят поля независимых разделителей;
  - `Идентификатор объекта метаданных + Номер актуальной версии метаданных` — всегда.
- Таблица настроек истории данных: `[ОРНР1 + … + ] + Идентификатор объекта метаданных` (Кластерный) — всегда. В индекс входят поля независимых разделителей.
- Таблица очереди обработки после записи версии истории данных: `[ОРР1 + … + ] + Идентификатор объекта метаданных + Идентификатор данных + Номер версии` (Кластерный) — всегда. В индекс входят поля разделителей.

### 2.16. Копии базы данных

- Таблица копий: `Идентификатор копии + Имя копии` (Кластерный) — всегда.
- Таблица настроек копий: `Идентификатор копии` (Кластерный) — всегда.
- Таблица состояний таблиц копий: `Идентификатор копии + Имя таблицы` (Кластерный) — всегда.
- Таблица изменений в процессе первоначального копирования: `Идентификатор копии + Имя таблицы` (Кластерный) — всегда.
- Таблица объектов изменений: `Идентификатор объекта` (Кластерный) — всегда.
- Таблица с информацией по блокам первоначального копирования: `Идентификатор копии + Имя таблицы + Номер блока` (Кластерный) — всегда.
- Таблица журналов транзакций:
  - `Номер транзакции` (Кластерный) — всегда;
  - `Идентификатор транзакции` — всегда.
- Таблица с изменёнными в транзакциях таблицами:
  - `Номер транзакции + Имя таблицы` (Кластерный) — всегда;
  - `Имя таблицы` — всегда.
- Таблица перенесённых транзакций: `Идентификатор копии + Номер транзакции` (Кластерный) — всегда.

### 2.17. Прочие служебные таблицы

- Таблица временных файлов для обмена с мобильным клиентом с автономным режимом: `Идентификатор записи` — всегда.
- Таблица табличных пространств базы данных:
  - `Имя табличного пространства` (Кластерный) — всегда;
  - `Идентификатор табличного пространства` — всегда.
- Таблица элементов состава табличных пространств базы данных:
  - `Идентификатор объекта метаданных + Признак назначения элемента + Признак размещения данных` (Кластерный) — всегда;
  - `Идентификатор табличного пространства + Признак назначения элемента` — всегда.

### 2.18. Дополнительные индексы (механизм платформы)

Где доступны:

- для всех объектов дерева метаданных объектного типа, для журналов документов и для регистров;
- условие — наличие КОРП-лицензии.

Источник полей дополнительного индекса — один из трёх:

1. объект метаданных;
2. табличная часть объекта метаданных;
3. виртуальная таблица объекта метаданных.

Правила:

- В одном индексе нельзя смешивать поля из разных источников. При этом можно создать несколько индексов с полями из разных источников: например, нельзя сделать индекс одновременно по полям объекта и по полям его табличной части, но можно завести два (или более) индекса — один по полям объекта, другой по полям табличной части.
- Поля объекта метаданных → индекс создаётся на основной таблице объекта.
- Поля табличной части → индекс создаётся на таблице, хранящей данные табличной части.
- Поля виртуальной таблицы → в общем случае создаётся несколько индексов, охватывающих все таблицы, участвующие в формировании виртуальной таблицы. Пример: дополнительный индекс по полям виртуальной таблицы «Остатки» регистра накопления порождает два индекса — на основной таблице регистра и на таблице итогов.
- Поля в составе дополнительного индекса бывают двух видов:
  - «Индексируемые» — входят в ключевые колонки индекса;
  - «Дополнительные» — добавляются в индекс как включённые колонки; если СУБД включённые колонки не поддерживает, такие поля игнорируются.
- Индексировать можно все поля выбранного источника, кроме полей типа «Двоичные данные» и полей типа «Строка» неограниченной длины.
- Количество дополнительных индексов платформа не ограничивает; каждый индекс может содержать не более 16 физических колонок.

Поддерживает ли включённые колонки конкретная СУБД (в том числе PostgreSQL), в источнике не сказано.

### 2.19. Сводка неясных и противоречивых мест источника (статья 2)

- Пометка «Кластерный» дана без пояснения, как она реализуется в разных СУБД.
- Таблица статистики регистра накопления: индекс «Карта используемых измерений» назван без состава полей.
- Таблица новых оборотов регистра накопления: пометка «(Кластерный)» стоит в середине записи состава.
- Регистр расчёта, индекс `[БазовоеИзмерение1 +...] + ПериодДействия`: в описании упомянут ПериодРегистрации.
- Перечисления, бизнес-процессы, точки маршрута, задачи: в описании кластерного индекса сказано «разделяют этот регистр».
- Таблица настроек сервиса интеграции: в составе кластерного индекса нет ни одного поля, в пояснении — «разделяют этот план счетов».
- Таблицы регистрации изменений: «поля, соответствующие изменениям» у регистров сведений, не подчинённых регистратору.
- Таблица итогов между счетами регистра бухгалтерии: привязка пояснений к строкам состава не очевидна.
- Хранилища настроек: одна таблица индексов на десять заголовков без явной оговорки, что она общая.
- Таблицы опций плана видов характеристик, плана счетов и плана видов расчёта: индекс записан без префикса разделителей и без пометки «Кластерный», в отличие от таблиц опций остальных объектов.
