## Кратко: главные официальные рекомендации

Сборка PostgreSQL с патчами 1С (статья 2018 г.):

1. Готовые пакеты PostgreSQL со всеми патчами фирма «1С» публикует у себя на сайте в составе каждого релиза СУБД. Самостоятельная сборка нужна только тем, кто хочет наложить патчи выборочно или внести собственные изменения в исходный код, сохранив совместимость с платформой.
2. Для Debian/Ubuntu сборку ведут в «чистом» chroot-окружении `pbuilder` (создаётся один раз, перед каждой следующей сборкой обновляется), для RPM-систем — через `rpmbuild`, для Windows — скриптами MSVC из исходников PostgreSQL.
3. При выборочном наложении патчей в Debian-сборке состав и порядок задаёт файл `series`; патчи, имя которых начинается с цифры 9, — штатные патчи Debian, их применяют всегда.
4. В RPM-сборке состав и порядок патчей задаёт spec-файл; при неполном наборе патчей в начало spec добавляют макросы `_unpackaged_files_terminate_build 0` и `_missing_doc_files_terminate_build 0`.
5. После сборки автоматически запускаются регрессионные тесты; результат годен, только если сборка прошла без ошибок и предупреждений, а тесты пройдены. В chroot `pbuilder` по умолчанию есть только локаль `C` — тесты с ней не стартуют, поэтому нужно сгенерировать `en_US.UTF-8` и `ru_RU.UTF-8`.

Непрерывное архивирование и восстановление на момент времени (статья 2018 г., PostgreSQL 9.6):

6. Для восстановления на момент времени (PITR) нужны две вещи: базовая (файловая) резервная копия кластера и непрерывная последовательность архивных файлов WAL, начинающаяся не позже момента создания этой копии.
7. `pg_dump` и `pg_dumpall` дают логическую копию без информации для воспроизведения журнала транзакций — для PITR они не подходят.
8. Архивирование WAL включается в `postgresql.conf`: `wal_level = replica`, `archive_mode = on`, `archive_command` (простая команда копирования или собственный скрипт).
9. Если кластер малоактивен и сегменты WAL переключаются редко, задают `archive_timeout` (в примере 60 секунд) — принудительное переключение сегмента.
10. `max_wal_senders` должен быть отличен от 0 (в примере 5); если у кластера уже есть hot_standby-реплика, получающая WAL, — не менее 2. В `pg_hba.conf` пользователю, от имени которого выполняется архивирование, разрешают подключение `replication`. После изменений сервер перезапускают.
11. Базовую копию проще всего делать утилитой `pg_basebackup`. Останавливать кластер не нужно, но копирование нагружает CPU и диски — выполнять в период минимальной нагрузки. Если есть hot_standby-реплика, копию лучше снимать с неё, чтобы не нагружать мастер.
12. Интервал между базовыми копиями выбирают по объёму диска, доступного под архив WAL: хранить нужно все файлы WAL с момента последней базовой копии.
13. При восстановлении текущий каталог данных лучше не удалять, а скопировать во временный каталог; `restore_command` обязана возвращать ненулевой код при ошибке.
14. Точку восстановления задают через `recovery_target_time` или `recovery_target_name` (именованная точка создаётся функцией `pg_create_restore_point`); без указания цели журнал воспроизводится до последнего файла WAL.
15. Если на время проверки после восстановления нужно закрыть сервер от подключений — делать это через `pg_hba.conf`.
16. Перед рискованными изменениями, когда на полный бэкап нет ресурсов или времени, можно зафиксировать точку возврата вызовом `pg_start_backup('метка', true)` без физического копирования и дополнительно сделать снимок виртуальной машины. Это не заменяет регулярные полные резервные копии кластера.

Резервное копирование информационной базы 1С (статьи 2007–2008 гг.):

17. Выгрузка/загрузка информационной базы в файл предназначена прежде всего для получения образа базы, не зависящего от способа хранения (например, для перевода из файлового варианта в клиент-серверный), а не для регулярного резервирования: она требует монопольного (однопользовательского) режима, и на большой базе простой пользователей может быть неприемлемо долгим.
18. Клиент-серверный вариант: резервную копию делать средствами СУБД — пользователи при этом продолжают работать, однопользовательский режим не нужен вообще.
19. Для PostgreSQL статья 2007 г. рекомендует `pg_dump`, потому что он работает без остановки пользователей; копирование файлов базы средствами ОС требует остановки PostgreSQL на всё время копирования.
20. Файловый вариант: копировать файл `1CV8.1CD` в отдельный каталог (вручную или программой резервного копирования); на время копирования работу пользователей нужно запретить, но это всё равно заметно быстрее выгрузки в файл.
21. Копия средствами СУБД или копия файла базы точнее выгрузки: если в базе есть нарушения, при выгрузке часть информации может не попасть в файл, а при копировании сохраняется всё, и после восстановления базу можно исправлять.
22. Для таких копий можно применять специализированные программные средства резервного копирования.

## 1. Методика сборки дистрибутива СУБД PostgreSQL 9.6 c патчами для работы с 1С:Предприятие 8

- Дата публикации: 31.05.2018
- Ссылка: https://its.1c.ru/db/metod8dev/content/5942/hdoc
- Прямая ссылка: https://its.1c.ru/db/content/metod8dev/src/developers/scalability/administration/postgresql/i8105942.htm
- Охват по подзаголовку статьи: Linux x86/x86_64 и Windows 32/64-bit.

### 1.1. Назначение методики

- Готовые пакеты со всеми патчами публикуются на сайте фирмы «1С» в составе релиза каждой версии СУБД — в обычном случае собирать ничего не нужно.
- Методика адресована тем, кому нужно применить патчи не все, а выборочно, либо внести в исходный код PostgreSQL другие изменения, но получить при этом сборку, пригодную для работы с платформой 1С:Предприятие.
- Исходный материал — пакет с исходниками и патчами, публикуемый в составе релиза PostgreSQL на сайте «1С», отдельно для каждой ОС.

### 1.2. Что скачать и какие зависимости нужны

Пакет для Linux (версия из статьи — 9.6.3-1.1C):

```text
https://releases.1c.ru/version_file?nick=AddCompPostgre&ver=9.6.3-1.1C&path=AddCompPostgre\9_6_3_1_1C\Patch_SUBD_PostgreSQL_9.6.3_1.1C.tar.bz2
```

Пакет для Windows:

```text
https://releases.1c.ru/version_file?nick=AddCompPostgre&ver=9.6.3-1.1C&path=AddCompPostgre\9_6_3_1_1C\Patch_SUBD_PostgreSQL_9.6.3_1.1C.zip
```

Поддерживаемые этой версией дистрибутивы Linux:

- RPM — CentOS 7 и Red Hat 7;
- Debian — Ubuntu 16.04.

Для корректной сборки и установки требуются дополнительные модули и библиотеки:

| Группа | Состав |
|--------|--------|
| Общие | `plperl`, `plpython`, `plpython3`, `pltcl`, `test`, `devel`, `docs` |
| Для Debian | `libicu55`, `postgresql-common`, `libicu-dev` |
| Для RPM | `readline`, `libtermcap`, `krb5-libs`, `openssl`, `libicu50`, `libicu-devel` (последний — для целей сборки) |

### 1.3. Сборка для Debian (пример: Ubuntu 16.04 Server, x86_64)

Инструмент — `pbuilder`: он собирает пакеты с учётом зависимостей в «чистом» окружении, которое создаётся отдельно под каждую сборку. Это особенно удобно, когда сборка идёт не на целевой машине и ставить все пакеты-зависимости по-настоящему незачем.

#### Шаг 1. Подготовка исходного пакета

Создать в домашнем каталоге каталог `Postgres`, перенести туда скачанный архив и распаковать:

```bash
mkdir ~/Postgres
mv <каталог_загрузки>/Patch_SUBD_PostgreSQL_9.6.3_1.1C.tar.bz2 ~/Postgres/Patch_SUBD_PostgreSQL_9.6.3_1.1C.tar.bz2
cd ~/Postgres
tar xfv Patch_SUBD_PostgreSQL_9.6.3_1.1C.tar.bz2
```

(исправлено по смыслу: в источнике четыре команды слиты в одну строку; `<каталог_загрузки>` — в источнике на этом месте многоточие, то есть путь, куда был скачан архив.)

После распаковки в `~/Postgres` появляется каталог `Patch_SUBD_PostgreSQL_9.6.3-1.1C`. В нём лежат:

- архив с оригинальными исходниками PostgreSQL (`.orig.tar.bz` — так в тексте; в командах ниже файл называется `postgresql-9.6_9.6.3.orig.tar.bz2`);
- патчи (`.patch`);
- архив с правилами сборки (`.deb.xz` — так в тексте; в командах ниже это `postgresql-9.6_9.6.3-1.1C.debian.tar.xz`);
- файл `.dsc` с описанием пакета.

Перейти в этот каталог:

```bash
cd ~/Postgres/Patch_SUBD_PostgreSQL_9.6.3-1.1C
```

(исправлено по смыслу: в источнике путь начинается с `~/postgres` — со строчной буквы, хотя каталог создан как `~/Postgres`.)

#### Шаг 2. Подготовка сборочного окружения

Установка `pbuilder` и сопутствующих утилит:

```bash
sudo apt-get install pbuilder debootstrap devscripts
```

Создание сборочного окружения (chroot). Простейший случай — архитектура сборки совпадает с целевой (x86_64 для x86_64):

```bash
sudo pbuilder --create
```

Если у пакета есть зависимости из репозиториев, не подключённых по умолчанию (например, `universe`) — а в рассматриваемом случае это именно так:

```bash
sudo pbuilder --create --components "main universe"
```

(исправлено по смыслу: в источнике типографские кавычки вместо прямых.)

Если нужно собирать под архитектуру, отличную от архитектуры сборочной машины, либо задать нестандартные целевые каталоги, адреса основного и дополнительного репозиториев и т. п., `pbuilder` настраивают одним из двух способов:

- через конфигурационный файл `/etc/pbuilderrc` (рекомендуется скопировать его в домашний каталог как `~/.pbuilderrc`);
- через опции команды `create` (а для последующих сборок — `update`).

Пример создания окружения для сборки под x86:

```bash
sudo pbuilder create --debootstrapopts --arch --debootstrapopts i386
```

Подробности по настройке `pbuilder`: https://wiki.ubuntu.com/PbuilderHowto

Окружение создаётся один раз. Перед каждой следующей сборкой его нужно обновлять:

```bash
sudo pbuilder --update --components "main universe" --override-config
```

(исправлено по смыслу: типографские кавычки заменены прямыми.)

Локали в сборочном окружении. По умолчанию в chroot есть только локаль `C`; с ней послесборочные тесты PostgreSQL не запускаются, и сборка завершается неудачей. В статье это описано в конце раздела, после шага сборки, но относится к подготовке окружения. Нужно войти в окружение в режиме, сохраняющем изменения при выходе, и сгенерировать локали:

```bash
# вход в chroot с сохранением результата после выхода
sudo pbuilder login --save-after-login

# внутри chroot: генерация нужных локалей
locale-gen en_US.UTF-8 ru_RU.UTF-8

# внутри chroot: список локалей, доступных для генерации
cat /etc/locale.gen
```

#### Шаг 3. Сборка

Вариант А — со всеми патчами:

```bash
pbuilder --build postgresql-9.6_9.6.3-1.1C.dsc
```

(в источнике эта команда приведена без `sudo`, в отличие от соседних.)

То же для x86:

```bash
sudo ARCH=i386 linux32 pbuilder --build postgresql-9.6_9.6.3-1.1C.dsc
```

Вариант Б — патчи выборочно.

1. Распаковать архив с правилами сборки Debian в отдельный подкаталог:

```bash
mkdir -p ~/Postgres/Debian
tar xfv postgresql-9.6_9.6.3-1.1C.debian.tar.xz -C ~/Postgres/Debian
```

(исправлено по смыслу: в источнике ключ `-С` набран кириллической буквой «С».)

2. В каталоге `~/Postgres/Debian/postgresql-9.6_9.6.3-1.1C.debian/debian/patches` лежат сами патчи и файл `series`, который определяет их состав и порядок наложения. Оставить только нужные патчи. Важно: патчи, имя которых начинается с цифры 9, — штатные для сборки Debian, их нужно применять в любом случае.
3. Сверить набор файлов `.patch` со списком в `series`.
4. Распаковать оригинальный архив исходников в `~/Postgres/Debian/postgresql-9.6_9.6.3-1.1C.debian/debian` и перейти туда:

```bash
tar xfv postgresql-9.6_9.6.3.orig.tar.bz2 -C ~/Postgres/Debian/postgresql-9.6_9.6.3-1.1C.debian/debian
cd ~/Postgres/Debian/postgresql-9.6_9.6.3-1.1C.debian/debian
```

(исправлено по смыслу: кириллическая «С» в ключе `-С` заменена латинской.)

5. Запустить сборку:

```bash
pdebuild
```

Что происходит дальше:

- ход сборки выводится в терминал;
- по окончании автоматически запускаются регрессионные тесты пакета, их ход тоже виден в терминале;
- при ошибке сборка останавливается;
- если сборка прошла без ошибок и предупреждений и тесты пройдены, готовые пакеты `.deb` находятся в каталоге (если в конфигурации не задан другой целевой каталог):

```text
/var/cache/pbuilder/result
```

- до начала сборки пользователю нужно выдать права на запись в целевой каталог.

### 1.4. Сборка для RPM (пример: CentOS 7, x86_64)

Инструмент — утилита `rpmbuild`.

#### Шаг 1. Подготовка сборочного окружения

Для удобства ставится пакет расширений `rpmdevtools`:

```bash
sudo yum install -y rpmdevtools
```

Создание дерева каталогов сборки:

```bash
rpmdev-setuptree
```

Команда создаёт в домашнем каталоге пользователя (расположение по умолчанию) каталог `rpmbuild` с подкаталогами `BUILD`, `BUILDROOT`, `RPMS`, `SOURCES`, `SPECS`, `SRPMS`.

Альтернатива — создать каталоги вручную в другом месте:

```bash
mkdir -p ~/rpmbuild/{RPMS,SRPMS,SPECS,SOURCES,BUILD}
```

В этом случае дополнительно нужно создать файл конфигурации `.rpmmacros`:

```bash
echo '%_topdir %(echo $HOME)/rpmbuild' >~/.rpmmacros
```

#### Шаг 2. Подготовка исходного пакета

Создать каталог `Postgres` в домашнем каталоге, перенести туда скачанный архив и распаковать:

```bash
mkdir ~/Postgres
mv <каталог_загрузки>/Patch_SUBD_PostgreSQL_9.6.3_1.1C.tar.bz2 ~/Postgres/Patch_SUBD_PostgreSQL_9.6.3_1.1C.tar.bz2
cd ~/Postgres
tar xfv Patch_SUBD_PostgreSQL_9.6.3_1.1C.tar.bz2
```

(`<каталог_загрузки>` — в источнике многоточие.)

Из распакованного нужен пакет исходников `postgresql96-9.6.3-1.1C.src.rpm`. Его переносят в отдельный подкаталог и распаковывают:

```bash
mkdir ~/Postgres/Rpm
mv ~/Postgres/postgresql96-9.6.3-1.1C.src.rpm ~/Postgres/Rpm/postgresql96-9.6.3-1.1C.src.rpm
cd ~/Postgres/Rpm
rpm2cpio postgresql96-9.6.3-1.1C.src.rpm | cpio --extract --make-directories --verbose
```

(исправлено по смыслу: в источнике перед `verbose` стоит длинное тире вместо двух дефисов.)

⚠ в источнике неясно: в разделе про Debian сказано, что архив распаковывается в подкаталог `Patch_SUBD_PostgreSQL_9.6.3-1.1C`, а здесь `src.rpm` берётся прямо из `~/Postgres`; где файл окажется фактически, статья не уточняет.

После распаковки в `~/Postgres/Rpm` находятся:

- архив с оригинальными исходниками `postgresql-9.6.3.tar.bz2` (в тексте источника имя набрано с опечаткой — `postgresq-9.6.3.tar.bz2`);
- патчи (`.patch`);
- прочие исходные файлы для формирования rpm-пакета;
- `postgresql-9.6.3.spec` — главный конфигурационный файл, инструкция сборки. В нём перечислены исходные файлы (`Source`), патчи (`Patch`) и зависимости (`BuildRequires` и `Requires`).

Дальнейшие действия:

1. Убедиться, что все файлы, перечисленные в разделе `Source`, присутствуют в `~/Postgres/Rpm`, и перенести их командой `mv` в `~/rpmbuild/SOURCES`.
2. Открыть `postgresql-9.6.3.spec` и исправить пути к источникам — для всех строк `Source`, по образцу:

```text
Source0: ~/rpmbuild/SOURCES/postgresql-9.6.3.tar.bz2
```

3. Раздел `Patch` править только если нужна часть патчей: оставить в spec нужные, сведения об остальных удалить. Патчи накладываются в том порядке, в каком перечислены в файле.
4. Патчи, указанные в spec-файле, перенести в `~/rpmbuild/SOURCES`.
5. Если применяются не все патчи: чтобы сборка не прерывалась из-за найденных, но не упакованных файлов (лежат в `SOURCES`, но не перечислены в spec), и из-за ошибок обратного характера, в начало spec-файла добавить макроопределения:

```text
%define _unpackaged_files_terminate_build 0
%define _missing_doc_files_terminate_build 0
```

6. Перенести spec-файл в `~/rpmbuild/SPECS`:

```bash
mv ~/Postgres/Rpm/postgresql-9.6.3.spec ~/rpmbuild/SPECS/postgresql-9.6.3.spec
```

(исправлено по смыслу: в источнике в целевом пути лишний пробел — `~/rpmbuild/SPECS /postgresql-9.6.3.spec`.)

7. Установить пакеты-зависимости сборки:

```bash
sudo yum-builddep ~/rpmbuild/SPECS/postgresql-9.6.3.spec
sudo yum-builddep ~/rpmbuild/SOURCES/postgresql96-9.6.3-1.1C.src.rpm
```

⚠ в источнике неясно: вторая команда ссылается на `src.rpm` в `~/rpmbuild/SOURCES`, хотя по тексту этот файл был перенесён в `~/Postgres/Rpm`, и о его копировании в `SOURCES` ничего не сказано.

#### Шаг 3. Сборка

Запуск сборки:

```bash
rpmbuild -ba ~/rpmbuild/SPECS/postgresql-9.6.3.spec
```

Сборка под архитектуру x86:

```bash
rpmbuild -bb --target i386 ~/rpmbuild/SPECS/postgresql-9.6.3.spec
```

Результат:

- ход сборки выводится на экран; по завершении автоматически запускаются регрессионные тесты собранных пакетов, их статус тоже выводится;
- при ошибке сборка прекращается;
- при успехе бинарные rpm-пакеты лежат в `~/rpmbuild/RPMS`, а пакет `postgresql96-9.6.3-1.1C.src.rpm` — в `~/rpmbuild/SRPMS`.

## 2. Настройка непрерывного архивирования в PostgreSQL 9.6

- Дата публикации: 15.05.2018
- Ссылка: https://its.1c.ru/db/metod8dev/content/5947/hdoc
- Прямая ссылка: https://its.1c.ru/db/content/metod8dev/src/developers/scalability/administration/postgresql/i8105947.htm
- Подзаголовок статьи: настройка непрерывного архивирования и восстановления на момент времени в PostgreSQL 9.6.
- Все примеры команд и путей в статье даны для Windows (`copy`, `C:\...`, `D:\...`); вариантов для Linux в статье нет.

### 2.1. Что нужно для восстановления на момент времени

Чтобы кластер PostgreSQL и его базы можно было восстановить на заданный момент времени, должны существовать одновременно:

1. **Базовая резервная копия.**
   - `pg_dump` и `pg_dumpall` создают логическую копию. В ней нет информации, необходимой для последующего воспроизведения журнала транзакций, поэтому для восстановления Point-in-Time она не годится.
   - Самый простой способ получить базовую копию — утилита `pg_basebackup`, которая делает копию файловой системы всего кластера.
2. **Непрерывный архив WAL (журнала транзакций).**
   - Нужна непрерывная последовательность архивных файлов WAL, начинающаяся не позднее момента создания файловой копии.
   - После восстановления данных из файловой копии журнал воспроизводится до нужного момента, и система приводится в состояние на этот момент.

### 2.2. Шаг 1 — включить архивирование WAL на уровне сервера

В `postgresql.conf`:

```ini
wal_level = replica
archive_mode = on
archive_command = 'copy "%p" "C:\\PostgreSQLBackup\\%f"'
```

Пояснения к `archive_command`:

- это команда, которая выполняется при архивировании WAL в момент переключения на следующий сегмент журнала;
- `%p` автоматически заменяется полным путём к архивируемому файлу (каталог `...\pg_xlog`);
- `%f` заменяется именем файла;
- `C:\PostgreSQLBackup\` в примере — каталог, куда складывается архив WAL.

Вместо простой команды можно указать скрипт с более сложной логикой (архивирование файлов, пакетная передача и т. п.):

```ini
archive_command = 'local_backup_script.sh "%p" "%f"'
```

Если кластер работает неинтенсивно, переключение сегментов и, следовательно, архивирование происходят слишком редко. Тогда задают период в секундах, по истечении которого переключение на новый сегмент произойдёт принудительно:

```ini
archive_timeout=60
```

Число процессов, передающих WAL:

```ini
max_wal_senders=5
```

- по статье, значение по умолчанию — 0; значение 5 взято для примера, технически подойдёт любое ненулевое;
- если у кластера есть hot_standby-реплика, которая уже получает WAL, значение `max_wal_senders` должно быть не меньше 2.

В `pg_hba.conf` разрешить пользователю, от имени которого выполняется архивирование, подключение для репликации:

```text
host replication     postgres        ::1/128  md5
host replication     postgres         127.0.0.1/32 md5
```

После правок перезапустить службу сервера PostgreSQL.

### 2.3. Шаг 2 — создавать базовые резервные копии

Выбор интервала:

- интервал подбирается индивидуально — по тому, сколько дискового места можно отвести под файлы WAL, и по их объёму;
- хранить нужно все файлы WAL, накопленные с момента создания последней базовой копии.

Условия выполнения:

- копирование утилитой `pg_basebackup` выполняется без остановки кластера;
- при этом оно может заметно нагрузить CPU и дисковую подсистему, поэтому его лучше запускать в периоды наименьшей нагрузки;
- если у кластера есть hot_standby-реплика, копии лучше снимать именно с неё, чтобы не нагружать мастер. Порядок действий на ведомом сервере тот же, но на нём нужно выполнить несколько дополнительных настроек — в статье они не перечислены, дана отсылка к документации по `pg_basebackup`.

Документация по утилите: https://www.postgresql.org/docs/9.6/static/app-pgbasebackup.html

Создание копии:

```bat
pg_basebackup -D "D:\Backup" -X fetch -F tar
```

(исправлено по смыслу: в источнике ключ формата набран с пробелом — `- F tar`.)

| Ключ | Значение |
|------|----------|
| `-D` | каталог, в который копируется содержимое каталога `..\data`; должен быть пустым |
| `-F` | формат; `tar` — содержимое упаковывается в архив |
| `-X` | способ копирования файлов WAL, созданных за время выполнения копии; `fetch` — файлы копируются в конце процесса |

### 2.4. Восстановление из базовой копии и архива WAL

1. Остановить сервер баз данных PostgreSQL.
2. Удалить — а лучше скопировать во временный каталог — содержимое текущего каталога кластера (`...\data`).
3. Развернуть (скопировать) файлы нужной резервной копии в текущий каталог данных кластера (`...\data`). Файлы WAL в каталоге `\pg_xlog` удалить либо заменить содержимым каталога, сохранённого на шаге 2.
4. Создать конфигурационный файл `recovery.conf`. За основу можно взять `recovery.conf.sample`, который обычно лежит в каталоге `...\share`. В нём задать:

```ini
restore_command = 'copy "C:\\PostgreSQLBackup\\%f" "%p"'
```

Пояснения к шагу 4:

- `restore_command` — команда получения ранее созданных архивов WAL, то есть действие, обратное `archive_command` из `postgresql.conf`;
- важно: при ошибке `restore_command` должна возвращать ненулевой код возврата;
- как и в случае `archive_command`, вместо команды можно указать скрипт с более сложной логикой;
- по умолчанию после запуска сервера архивы запрашиваются и воспроизводятся до последнего файла WAL; если нужна конкретная точка, её указывают в `recovery.conf`.

Восстановление на момент времени:

```ini
recovery_target_time = '2018-03-15 12:00:00'
```

Восстановление на именованную точку:

```ini
recovery_target_name = 'our_label'
```

Именованную точку заранее создают запросом, выполненным в контексте любой базы кластера:

```sql
select pg_create_restore_point('our_label');
```

5. Запустить сервер баз данных. Он стартует в режиме recovery и начинает восстановление. По завершении сервер сам переименовывает `recovery.conf` в `recovery.done` и переходит в обычный режим работы, в том числе начинает принимать подключения.

Оговорка: если на время проверки после восстановления подключения к серверу нужно запретить, лучше всего сделать это в `pg_hba.conf`.

### 2.5. Быстрый возврат системы в состояние «до изменений»

Задача. Перед изменениями в системе часто нужно обеспечить возможность быстро их отменить, а сделать дополнительный полный бэкап удаётся не всегда: может не хватать места в хранилище, копирование может идти слишком долго и т. д. По сути, для корректного возврата на нужный момент требуется, чтобы в точке восстановления все изменения базы были сброшены на диск и была выполнена контрольная точка (checkpoint).

Идея решения. Один из самых простых сценариев — использовать функцию `pg_start_backup()`. В паре с `pg_stop_backup()` её использует и `pg_basebackup`; разница в том, что утилита сама выполняет физическое копирование кластера по заданным параметрам, а при ручном вызове ответственность за создание копии лежит на администраторе — и это же позволяет физическое копирование «пропустить».

Действия перед внесением изменений:

1. Убедиться, что архивирование WAL включено.
2. Подключиться к серверу в контексте любой базы и выполнить:

```sql
select pg_start_backup('our_label', true);
```

Параметры вызова: первый — имя метки, которое потом используется при восстановлении; второй (`true`) означает, что контрольная точка будет выполнена как можно скорее, независимо от значения `checkpoint_completion_target`.

3. Штатно дальше следовало бы скопировать каталог данных, но в этом сценарии копирование не требуется — можно приступать к плановым изменениям.
4. Перед изменениями целесообразно сделать снимок виртуальной машины: ресурсов это требует немного, а надёжность повышает; кроме того, снимок при необходимости можно быстро развернуть в тестовом контуре.

Предупреждение авторов: снимок ВМ никак не заменяет регулярные полные резервные копии кластера.

Если изменения нужно откатить. Действия те же, что в алгоритме восстановления из п. 2.4, с одним отличием: каталог кластера удалять и разворачивать на его место резервную копию не нужно. Достаточно запустить сервер в режиме восстановления, указав в `recovery.conf` созданную метку в качестве `recovery_target_name`.

⚠ в источнике неясно: в п. 2.4 именованная точка для `recovery_target_name` создаётся функцией `pg_create_restore_point`, а здесь в том же параметре предлагается использовать метку, переданную в `pg_start_backup`; почему это равнозначно, статья не поясняет.

Если откат не понадобился — вывести сервер из режима резервного копирования:

```sql
select pg_stop_backup();
```

### 2.6. Оценка применимости на октябрь 2026

**Частично устарело: принципы верны, конкретика относится к PostgreSQL 9.6.**

Что остаётся верным:

- схема PITR: базовая файловая копия плюс непрерывный архив WAL, начатый не позже копии;
- `pg_dump`/`pg_dumpall` для PITR не годятся;
- включение архивирования через `wal_level`, `archive_mode`, `archive_command`, при необходимости `archive_timeout`;
- `pg_basebackup` как простейший способ базовой копии, съём копий с реплики, выполнение в период низкой нагрузки;
- требование ненулевого кода возврата у `restore_command`; цели восстановления `recovery_target_time` и `recovery_target_name`; функция `pg_create_restore_point`;
- хранение всех WAL с последней базовой копии; сохранение старого каталога данных перед восстановлением.

Что изменилось в более новых версиях PostgreSQL (статья описывает 9.6, снятую с поддержки в ноябре 2021 года):

- каталог журнала `pg_xlog` с версии 10 называется `pg_wal`;
- с версии 10 значения по умолчанию другие: `wal_level` уже равен `replica`, `max_wal_senders` не равен 0 — утверждение статьи про «0 по умолчанию» относится только к 9.6;
- файл `recovery.conf` упразднён начиная с версии 12: параметры восстановления (`restore_command`, `recovery_target_*`) задаются в `postgresql.conf`, а режим восстановления включается файлом-признаком `recovery.signal`; переименования в `recovery.done` больше нет. Шаги 4–5 из п. 2.4 в буквальном виде к современным версиям неприменимы;
- функции `pg_start_backup`/`pg_stop_backup` в версии 15 переименованы в `pg_backup_start`/`pg_backup_stop`, а монопольный режим резервного копирования, на который опирается приём из п. 2.5, удалён. В описанном виде этот приём на PostgreSQL 15 и новее не воспроизводится — нужно сверяться с документацией используемой версии.

Прочее:

- примеры в статье написаны для Windows (`copy`, пути `C:\\...`); для сервера на Ubuntu команды архивирования и восстановления нужно составлять самостоятельно по документации PostgreSQL — в статье их нет;
- ссылка на документацию ведёт на версию 9.6.

## 3. Резервное копирование базы данных при работе с PostgreSQL

- Дата публикации: 12.12.2007 (в тексте статьи отметка «Обновлено: 14.12.2007»)
- Ссылка: https://its.1c.ru/db/metod8dev/content/1809/hdoc
- Прямая ссылка: https://its.1c.ru/db/content/metod8dev/src/admins/postgresql/i8101809.htm

Статья короткая: в ней названы два способа резервного копирования базы на PostgreSQL и дана рекомендация, какой из них использовать.

### 3.1. Способ 1 — копирование файлов базы данных средствами операционной системы

- Файлы базы данных лежат в каталоге, имя которого совпадает с OID (object identifier) базы данных.
- Идентификатор берут из системного каталога `pg_database`, где хранится информация обо всех базах кластера PostgreSQL. Запрос из статьи:

```sql
select dattablespace from pg_database where datname = 'имя_базы_данных'
```

⚠ в источнике неясно: текст говорит об OID базы данных, а запрос выбирает столбец `dattablespace`; статья это расхождение не объясняет.

- Главный недостаток способа: PostgreSQL приходится останавливать на всё время выполнения резервного копирования.

### 3.2. Способ 2 — утилита `pg_dump`

Простейший вид команды (пример из статьи — для Windows):

```bat
pg_dump.exe -F c -b -f "TestDB.backup" TestDB
```

- Статья рекомендует именно этот способ: `pg_dump` позволяет делать резервную копию, не останавливая работу пользователей.
- Ключи команды в статье не расшифрованы; за описанием параметров `pg_dump` она отсылает к документации PostgreSQL.

### 3.3. Оценка применимости на октябрь 2026

**Частично устарело.**

- Статья 2007 года (по дате — эпоха PostgreSQL 8.x; версия СУБД в самой статье не названа); пример команды — для Windows (`pg_dump.exe`).
- Основной вывод остаётся верным: `pg_dump` снимает копию отдельной базы без остановки пользователей, а простое копирование файлов средствами ОС требует остановки сервера.
- Статья неполна по сегодняшним меркам: в ней нет ни непрерывного архивирования WAL, ни `pg_basebackup`, ни восстановления на момент времени. Эти темы раскрыты в более поздней статье (раздел 2 конспекта), которая прямо указывает, что копия `pg_dump` логическая и для PITR не подходит, а файловую копию всего кластера можно получать без остановки — утилитой `pg_basebackup`.
- Запрос к `pg_database` приведён в статье в виде, не согласованном с пояснением (см. пометку в п. 3.1).

## 4. Рекомендации по организации резервного копирования информационной базы

- Дата публикации: 28.10.2008
- Ссылка: https://its.1c.ru/db/metod8dev/content/2922/hdoc
- Прямая ссылка: https://its.1c.ru/db/content/metod8dev/src/admins/i8102922.htm

### 4.1. Выгрузка информационной базы в файл — не основной способ резервирования

- Платформа умеет выгружать информационную базу в файл и загружать её из файла. Назначение механизма — прежде всего получить образ базы, не зависящий от способа хранения данных. Типичное применение: перевод базы из файлового варианта в клиент-серверный.
- Иногда выгрузку используют и как резервную копию, но у такого применения есть ряд недостатков.
- Главный недостаток: операция требует однопользовательского режима. На большой базе перерыв в работе пользователей может оказаться значительным, что не всегда приемлемо.

### 4.2. Рекомендуемые способы по вариантам работы

| Вариант работы | Рекомендуемый способ | Работа пользователей во время копирования |
|----------------|----------------------|-------------------------------------------|
| Файловый | Копирование файла `1CV8.1CD` в отдельный каталог — вручную либо программой резервного копирования и восстановления данных | Должна быть запрещена — иначе не гарантируются целостность и согласованность данных; при этом копирование занимает существенно меньше времени, чем выгрузка в файл |
| Клиент-серверный | Резервная копия средствами СУБД | Продолжается: в качестве примера приведён SQL Server, который выполняет резервное копирование, когда база находится в многопользовательском режиме и доступна всем пользователям |

### 4.3. Почему эти способы лучше выгрузки

1. **Точность копии.** Копирование файла базы или бэкап средствами СУБД дают максимально точную копию состояния информационной базы; выгрузка/загрузка обеспечивает это не всегда. Пример авторов: если в базе данных есть нарушения, при выгрузке часть информации может не выгрузиться, тогда как при копировании сохраняется всё — и после восстановления базу можно исправить.
2. **Меньше простоя.** В файловом варианте время пребывания базы в однопользовательском режиме заметно сокращается; в клиент-серверном однопользовательский режим не используется вовсе.
3. **Свобода в выборе инструментов.** Для создания копий перечисленными способами можно применять различные специализированные программные средства резервного копирования.

### 4.4. Оценка применимости на октябрь 2026

**Актуально (как общие принципы).**

- Статья 2008 года, но к версиям платформы, ОС и СУБД она не привязана, поэтому её выводы не устарели: выгрузка в файл — средство переноса и получения образа базы, а регулярное резервирование клиент-серверной базы ведётся средствами СУБД без остановки пользователей.
- Ограничение: единственный пример по СУБД — SQL Server; конкретных приёмов для PostgreSQL в статье нет. Они описаны в разделах 2 (PITR, `pg_basebackup`, архив WAL) и 3 (`pg_dump`) конспекта.
