# ИТС-конспект (методические материалы): Размещение данных 1С:Предприятия: таблицы и поля
> Источник: статьи раздела «Методическая поддержка» портала 1С:ИТС (ссылки — в разделах). Это конспект своими словами, не дословный текст. Составлен 2026-10-10.

## Кратко: главные официальные рекомендации

Статья по этой теме одна и она справочная: в ней нет настроек, команд и скриптов, зато есть полный перечень служебных и прикладных таблиц базы и их полей. Поэтому ниже — единственное прямое требование фирмы «1С» (п. 1) и ключевые факты, на которые опирается администратор при разборе базы в СУБД.

1. **Запрет на нештатную работу с данными.** Сведения о таблицах и полях не должны применяться для работы с данными какими-либо способами, не предусмотренными штатными механизмами 1С:Предприятия 8. Статья — для понимания структуры, а не разрешение работать с таблицами напрямую.
2. **Структура не гарантирована на будущее.** Описание справедливо для платформы 8.2 и выше, но в последующих версиях состав таблиц и полей может измениться. Редакция статьи привязана к платформе 8.3.27 (дата 27.05.2025).
3. **Имя поля строится по схеме «префикс + номер + суффикс».** Префикс есть всегда и говорит о назначении; номер (`<n>`, `<i>`, `<k>`) различает однотипные поля и бывает не у всех; суффикс зависит от типа хранимых данных и тоже бывает не у всех.
4. **Составной тип = несколько колонок.** Если в имени поля предусмотрен суффикс, то для некоторых типов данных вместо одной колонки создаётся несколько — с одинаковым префиксом и номером, но разными суффиксами. Правила суффиксов описаны в другом разделе ИТС («Особенности хранения составных типов данных»), в этой статье их нет.
5. **Набор полей определяется видом объекта метаданных верхнего уровня** и составом/типами подчинённых ему объектов (реквизитов, измерений, ресурсов, табличных частей и т. д.).
6. **Основные таблицы объектов:** `_Const<n>`, `_Node<n>`, `_Reference<n>`, `_Document<n>`, `_Seq<n>`/`_SeqB<n>`, `_DocumentJournal<n>`, `_Enum<n>`, `_Chrc<n>`, `_Acc<n>`, `_CKind<n>`, `_InfoRg<n>`, `_AccumRg<n>`, `_AccRg<n>`, `_CRg<n>`, `_BPr<n>`, `_Task<n>`.
7. **Табличные части** хранятся в отдельных таблицах `<pref><n>_VT<k>` и связаны с владельцем полем `<pref><n>_ID<suff>`.
8. **Общие реквизиты** присутствуют почти в каждой таблице как дополнительные поля `_Fld<n>` (в таблицах сервисов интеграции такие поля названы разделителями сервиса интеграции).
9. **Таблицы регистрации изменений (`…ChngR<n>`, `_ConstsChngR`) появляются только при участии объекта в обмене данными.** В них `_MessageNo` = NULL означает, что изменение ещё не выгружалось; иначе там номер сообщения обмена, в которое изменение попало.
10. **Две «формы» таблиц регистрации изменений:** как у справочника (`_Node<suff>`, `_MessageNo`, `_ID<suff>`, `_Fld<n>`) — для ссылочных объектов; как у последовательности (`_Node<suff>`, `_MessageNo`, `_Recorder<suff>`, `_Fld<n>`) — для регистров, подчинённых регистратору, и перерасчётов.
11. **Поле `_Version`** в таблицах ссылочных объектов меняется после каждого обновления записи.
12. **Предопределённые данные:** на всю конфигурацию создаётся по одной таблице опций (`_RefOpt`, `_ChrcOpt`, `_AccOpt`, `_CKindsOpt`) с режимом обновления предопределённых данных, а при наличии предопределённых данных — таблицы проинициализированных областей (`_RefSInf`, `_ChrcSInf`, `_AccSInf`, `_CKindsSInf`).
13. **Регистр накопления:** движения `_AccumRg<n>`, остатки `_AccumRgT<n>` (если регистр поддерживает остатки), обороты `_AccumRgTn<n>` (если поддерживает обороты), общая таблица настроек итогов `_AccumRgOpt`.
14. **`_Splitter` — разделитель итогов**, нужен для параллельного проведения документов; есть в таблицах итогов регистров накопления и бухгалтерии, а включён ли он — видно в `_UseSplitter` таблиц `_AccumRgOpt`/`_AccRgOpt`.
15. **`_DimHash` / `_EDHash<suff>`** — хеш измерений; поле появляется, когда измерений столько, что уникальный индекс по ним построить нельзя.
16. **Регистр бухгалтерии:** движения `_AccRg<n>`, значения субконто `_AccntRegED<n>`, итоги по счёту `_AccRgAT<k><n>` (таблиц столько, каково максимальное число субконто плана счетов), итоги оборотов между счетами `_AccRgCT<n>` (только для регистров с корреспонденцией), настройки `_AccRgOpt`.
17. **Регистр сведений:** движения `_InfoRg<n>`; при включённых признаках РазрешитьИтогиСрезПоследних / РазрешитьИтогиСрезПервых у периодического регистра добавляются `_InfoRgSL<n>` и `_InfoRgSF<n>`.
18. **Конфигурация и служебные данные лежат в самой базе** в виде поименованных двоичных «файлов»: таблицы `Config`, `ConfigSave`, `ConfigCAS`, `ConfigCASSave`, `DepotFiles`, `Files`, `Params` (одинаковый набор из 6 полей); `DBSchema` и `DBChanges` содержат по одной записи с единственным полем `SerializedData`.
19. **Пользователи информационной базы** хранятся в `_v8users`; история работы пользователей — в `_UsersWorkHistory`; девять хранилищ настроек (`_SystemSettings`, `_RepSettings`, `_RepVarSettings`, `_CommonSettings`, `_FrmDtSettings`, `_DynListSettings`, `_ErrorProcessingSettings`, `_URLExternalData`, `_InternalSettings`) имеют одинаковую структуру.
20. **Регламентные задания** — одна таблица `_ScheduledJobs` (создаётся, если в конфигурации есть хотя бы одно регламентное задание); в ней и расписание, и состояние, и время последнего запуска/завершения.
21. **История данных** занимает шесть видов таблиц `_DataHistory…` (очередь, версии, последние версии, версии метаданных, настройки, очередь обработки после записи).
22. **Копии базы данных и Дата акселератор** описываются семейством таблиц `_DbCopies…`; пароль пользователя базы копии (`_DbPassword`) хранится в зашифрованном виде.
23. **Табличные пространства** описываются таблицами `_DbSegments` (имя и путь к каталогу на сервере СУБД) и `_DbSegmentsItems` (что куда размещено, отдельно данные и индексы, с признаком фактического применения).
24. **Зависимости от СУБД, названные в статье:** таблица `_YearOffset` (смещение дат) существует только при работе с Microsoft SQL Server; в IBM DB2 у имён таблиц и полей нет начального символа подчёркивания. Для PostgreSQL отдельных оговорок в статье нет.

### Как устроены имена полей

Состав и имена полей каждой таблицы задаёт соответствующий ей объект метаданных; имена зависят от назначения поля и от типа хранимых данных. Имя поля может включать три части:

| Часть имени | Обозначение в статье | Что означает | Обязательность |
|---|---|---|---|
| Префикс из латинских букв | `<pref>` | Назначение данных в поле | Есть в имени любого поля |
| Числовой номер | `<n>`, `<i>` или `<k>` | Позволяет различать поля со схожим назначением | Есть не у всех полей |
| Суффикс из латинских букв | `<suff>` | Зависит от типа данных, хранимых в поле | Есть не у всех полей |

Важные следствия:

- Наличие суффикса в шаблоне имени означает, что для некоторых типов данных вместо одного поля может быть создано **несколько полей** с одинаковым префиксом и номером (если номер есть), различающихся только суффиксом. Это типичный случай для реквизитов составного типа.
- Какие именно суффиксы создаются для каких типов, описано в разделе ИТС «Особенности хранения составных типов данных» (в данный конспект не входит; здесь разбираются только префиксы и условия появления полей).
- Набор полей определяется видом объекта метаданных верхнего уровня (константы, планы обмена, справочники, документы, последовательности документов, журналы документов, перечисления, планы видов характеристик, планы счетов, планы видов расчёта, регистры сведений, накопления, бухгалтерии, расчёта, бизнес-процессы, задачи), а также составом и типами подчинённых объектов.

Условные обозначения в таблицах ниже: колонка «Когда есть» пуста, если поле присутствует всегда; запись «общие реквизиты» означает поля `_Fld<n>`, создаваемые под общие реквизиты конфигурации.

### Таблицы регистрации изменений: два типовых набора полей

Статья многократно ссылается на «такие же поля, как у таблицы регистрации изменений справочника» или «…последовательности». Чтобы не повторять, оба набора вынесены сюда.

**Набор А — «как у справочника»** (таблицы `_ReferenceChngR<n>`, `_DocumentChngR<n>`, `_ChrcChngR<n>`, `_AccChngR<n>`, `_KindChngR<n>`, `_BPrChngR<n>`, `_TaskChngR<n>`):

| Поле | Назначение |
|---|---|
| `_Node<suff>` | Ссылка на узел плана обмена |
| `_MessageNo` | Номер сообщения обмена, в которое это изменение было выгружено; NULL — изменение ещё не выгружалось |
| `_ID<suff>` | Идентификатор изменённого объекта (элемента справочника и т. п.) |
| `_Fld<n>` | Общие реквизиты |

**Набор Б — «как у последовательности»** (таблицы `_SeqChngR<n>`, `_InfoRgChngR<n>` для регистров, подчинённых регистратору, `_AccumRgChngR<n>`, `_AccRgChngR<n>`, `_CRgChngR<n>`, `_CRgRecalcChngR<n>`):

| Поле | Назначение |
|---|---|
| `_Node<suff>` | Ссылка на узел плана обмена |
| `_MessageNo` | Номер сообщения обмена, в которое изменение выгружено; NULL — ещё не выгружено |
| `_Recorder<suff>` | Ссылка на документ (регистратор), которому соответствует изменённая запись |
| `_Fld<n>` | Общие реквизиты |

Особые случаи — `_ConstsChngR` (см. «Константы») и `_InfoRgChngR<n>` независимого регистра сведений (см. «Регистры сведений»).

### Константы

Таблица `_Const<n>` — отдельная на каждую константу.

| Поле | Назначение | Когда есть |
|---|---|---|
| `RecordKey` | Ключ записи; нужен, чтобы корректно устанавливались транзакционные блокировки | |
| `_Fld<n>` | Значение константы. Для составного типа — несколько полей с общими префиксом и номером и разными суффиксами | |
| `_Fld<n>` | Общие реквизиты | |

Таблица `_ConstsChngR` — регистрация изменений констант; создаётся, если хотя бы одна константа участвует в обмене данными.

| Поле | Назначение |
|---|---|
| `_Node` | Ссылка на узел плана обмена |
| `_MessageNo` | Номер сообщения обмена, в которое изменение выгружено; NULL — ещё не выгружено |
| `_ConstID` | Идентификатор константы, значение которой изменилось |
| `_Fld<n>` | Общие реквизиты |

### Табличная часть

Каждой табличной части соответствует таблица `<pref><n>_VT<k>` (префикс и номер — от таблицы объекта-владельца).

### Другие таблицы и особенности СУБД

- **Microsoft SQL Server:** в таблице `_YearOffset` хранится смещение дат; единственное поле — `Offset` (смещение дат в годах). Таблица упомянута только для этой СУБД.
- **IBM DB2 (примечание авторов):** в начале имён таблиц и полей символ подчёркивания `_` отсутствует.
- Для PostgreSQL отдельных особенностей именования в статье не указано.
