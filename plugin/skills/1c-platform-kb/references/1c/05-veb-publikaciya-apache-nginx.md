## Кратко — главные факты и команды

1. На Linux платформа 1С работает **только с Apache** (официально: IIS и Apache; для Linux — только Apache). В 8.3.x поддерживались Apache 2.0, 2.2 и 2.4; **в 8.5.4 поддержка 2.0 и 2.2 прекращена**, остался только 2.4. nginx загрузить модуль 1С не может — он применяется **только как обратный прокси** перед Apache или перед `ibsrv`.
2. Модуль расширения веб-сервера для Apache 2.4 — файл `/opt/1cv8/x86_64/<версия>/wsap24.so` (компонент установщика `ws`). Подключается строкой `LoadModule _1cws_module "/opt/1cv8/x86_64/<версия>/wsap24.so"`.
3. Публикация одной командой (под root, каталог должен существовать):
   `sudo /opt/1cv8/x86_64/$V/webinst -publish -apache24 -wsdir demo -dir /var/www/demo -connstr "Srvr=srv1c;Ref=demo;" -confpath /etc/apache2/apache2.conf`
4. Файловая база: `-connstr "File=/srv/1c/bases/demo;"`. Пользователю `www-data` нужны права на изменение каталога базы, а Apache должен обслуживать публикацию **одним рабочим процессом** (`ServerLimit 1`).
5. После новой публикации, отключения публикации, смены версии платформы или пути к модулю Apache нужно **перезапустить**: `sudo systemctl restart apache2` (официальное требование).
6. `webinst` делает три вещи: добавляет `LoadModule`, добавляет блок `Alias` + `<Directory>` с `SetHandler 1c-application` и `ManagedApplicationDescriptor`, создаёт `default.vrd` в каталоге публикации. Всё это можно сделать вручную.
7. Официальная рекомендация для Linux: **MPM worker**; остальные MPM «не рекомендуются». В Ubuntu по умолчанию включён `event`. Переключение: `sudo a2dismod mpm_event && sudo a2enmod mpm_worker && sudo systemctl restart apache2`.
8. Версия `webinst` и модуля `wsap24.so` должна **точно совпадать** с версией работающего кластера серверов 1С (вплоть до сборки). В один экземпляр Apache загружается один модуль, то есть одна версия платформы.
9. `default.vrd` — XML с корневым элементом `<point>`: атрибуты `base` (имя публикации), `ib` (строка соединения), `enable` (доступ клиентских приложений), `enableStandardOData`; вложенные элементы `<ws>`, `<httpServices>`, `<pool>`, `<debug>`, `<zones>`, `<openid>`, `<openidconnect>`, `<exitURL>`, `<analytics>`, `<authentication>` и другие.
10. Пул соединений модуля с кластером по умолчанию: `size=100`, `maxAge=20` с, `attempts=5`, `attemptTimeout=0.5` с, `waitTimeout=0.5` с.
11. Адреса после публикации: веб-клиент и тонкий клиент — `http://хост/demo`; SOAP — `http://хост/demo/ws/<имя>?wsdl`; HTTP-сервисы — `http://хост/demo/hs/<корневой URL>/…`; OData — `http://хост/demo/odata/standard.odata/`. Имя публикации **чувствительно к регистру**.
12. Веб-серверу нужен доступ к кластеру по TCP 1541 и 1560–1591 (и разрешение имени сервера 1С). Пользователям — только 80/443 до веб-сервера.
13. HTTPS в Apache: `sudo a2enmod ssl headers && sudo a2ensite default-ssl`, сертификат Let's Encrypt — `sudo certbot --apache -d 1c.example.com`. Блок публикации из `apache2.conf` глобальный и действует во всех виртуальных хостах, включая `*:443`.
14. Сертификаты Let's Encrypt укорачиваются: 90 дней сейчас, 64 дня с 10.02.2027, 45 дней с 16.02.2028 (профиль `classic`). Продление должно быть автоматическим.
15. nginx перед Apache: обязательно `proxy_set_header Host $host`, `X-Forwarded-Proto`, `X-Forwarded-Port`, `X-Forwarded-Host` (официально перечислены 1С в руководстве 8.3 ранней редакции; эталон `docker_fresh` реально задаёт только `Host`, `X-Forwarded-Proto https` и `X-Forwarded-Port 443`), `client_max_body_size` (по умолчанию 1 МБ — мало), увеличенный `proxy_read_timeout`.
16. Эталонная конфигурация 1С (docker_fresh) балансирует несколько веб-серверов через `ip_hash` — то есть с привязкой клиента к веб-серверу.
17. Автономный сервер `ibsrv` публикует одну базу без Apache: встроенный HTTP на `localhost:8314` по умолчанию (`--http-address`, `--http-port`, `--http-base`). **HTTPS он не умеет** — перед ним ставят обратный прокси. Нет аутентификации ОС, 1С:Аналитики, сервисов интеграции.
18. Аутентификация на уровне веб-сервера (официально): анонимная, Basic, ОС. Параметр `-osauth` у `webinst` работает только для IIS. На Linux аутентификация ОС — это Kerberos, настраивается вручную; официальный рецепт 1С (руководство администратора, 2.8.1.3) — модуль `mod_auth_kerb` с `KrbSaveCredentials on` и учётной записью, доверенной для делегирования (раздел 11.3).
19. Пакет `libapache2-mod-auth-kerb` есть в Ubuntu 22.04 (5.4-2.5), но отсутствует в 24.04 и новее; там остаётся `libapache2-mod-auth-gssapi` (1.6.4) — замена, которую 1С официально не описывает.
20. Диагностика: `sudo apachectl configtest`, `apachectl -M | grep 1cws`, `sudo tail -f /var/log/apache2/error.log`, `curl -I http://localhost/demo/`.
21. **Ubuntu 26.04**: юнит `apache2.service` содержит `MemoryDenyWriteExecute=yes` и `ProtectHome=read-only`. Перед публикацией 1С создайте drop-in: `sudo systemctl edit apache2` → `[Service]` / `MemoryDenyWriteExecute=no`, затем `sudo systemctl restart apache2` (раздел 6.1). Проверка: `systemctl show apache2 -p MemoryDenyWriteExecute -p ProtectHome -p ProtectSystem`.
22. `webinst -delete` по документации удаляет и **физический каталог публикации** — никогда не указывайте в `-dir` общий каталог (`/var/www`, `/var/www/html`) или каталог с посторонними файлами.
23. `webinst … -descriptor файл.vrd` при публикации **заменяет** существующий `default.vrd` шаблоном [офиц.]; храните эталон `.vrd` отдельно и публикуйте всегда с ним.

## 1. Что такое веб-публикация и что через неё работает

### 1.1. Схема

Веб-сервер не выполняет прикладной код 1С. Модуль расширения (`wsap24.so`) работает внутри процесса Apache и передаёт вызовы в кластер серверов 1С по тому же протоколу, что и обычный клиент (TCP 1541, затем 1560–1591). Для файловой базы модуль сам открывает файл `1Cv8.1CD`.

```text
 Браузер (веб-клиент)  ┐
 Тонкий клиент по HTTP │ HTTP/HTTPS        ┌───────────────────────┐  TCP 1541,     ┌──────────────┐   ┌────────────┐
 Мобильный клиент      ├──80/443──▶ nginx ─▶ Apache 2.4 + wsap24.so ├─ 1560–1591 ──▶ │ ragent/rmngr │──▶│ PostgreSQL │
 SOAP / REST / OData   ┘  (необязательно)  │ default.vrd на каждую  │                │ rphost       │   └────────────┘
                                           │ публикацию             │                └──────────────┘
                                           └───────────────────────┘
                                                     │ файловая база: модуль сам работает с 1Cv8.1CD
```

Вариант без Apache: `клиент → (nginx с HTTPS) → ibsrv:8314 → файл 1Cv8.1CD или СУБД` (раздел 10).

### 1.2. Что публикуется

| Что | Адрес | Чем включается | Примечание |
|---|---|---|---|
| Веб-клиент | `http://хост/demo` | атрибут `enable` элемента `<point>` (по умолчанию `true`) | Работает в браузере, исполняемых файлов на клиенте нет |
| Тонкий клиент по HTTP | тот же адрес; в списке баз — «На веб-сервере»; в командной строке `/WS"http://хост/demo"` | `enable` | В файле `ibases.v8i` строка `Connect=ws="http://хост/demo";` |
| Мобильный клиент | тот же адрес | `enable` | Нужен HTTPS с сертификатом, которому доверяет устройство |

### 1.4. Сетевые порты

| Откуда → куда | Порт | Зачем |
|---|---|---|
| Пользователи → веб-сервер (или nginx) | 80/tcp, 443/tcp | HTTP, HTTPS |
| Apache (модуль 1С) → центральный сервер 1С | 1541/tcp | менеджер кластера: выдаёт адрес рабочего процесса |
| Apache (модуль 1С) → рабочие серверы 1С | 1560–1591/tcp | рабочие процессы `rphost` |
| nginx → Apache на том же хосте | например 127.0.0.1:8080 | проксирование |
| nginx → `ibsrv` | 8314/tcp (по умолчанию) | встроенный HTTP автономного сервера |

Официальная рекомендация для кластера с веб-публикациями: обеспечить доступность между компьютерами кластера и веб-серверами **по TCP и UDP на одинаковых номерах портов** — это нужно механизму контроля разрыва соединений (период проверки по умолчанию 3 с, таймаут 15 с; меняются параметрами публикации) [офиц., руководство «Клиент-серверный вариант», 2.2.5.6; проверено 2026-10-10]. Там же: для процессов кластера между собой — 1 с / 5 с (меняются параметрами запуска агента сервера), для тонкого клиента — фиксированные 3 с / 15 с, для толстого — 12 с / 60 с. Нулевые значения периода или таймаута не отключают проверку, а включают другой алгоритм (пробный пакет раз в 5 с, разрыв фиксируется через 200 с) — документация так делать не рекомендует. Практическое следствие для `ufw` на сервере 1С: открывать для веб-сервера 1541 и 1560–1591 и по `tcp`, и по `udp`.

Веб-сервер должен разрешать **имя** сервера 1С (кластер возвращает имена рабочих серверов, а не адреса). Если DNS нет — добавьте запись в `/etc/hosts` веб-сервера.

## 2. Требования и ограничения (официально)

Из разделов 8.2, 8.3.1 и 8.10.1 руководства администратора 8.3.27:

- Публикация возможна, только если на компьютере с веб-сервером **установлена платформа 1С** (как минимум компонент «Модули расширения веб-сервера»).
- Публиковать нужно средствами **той же версии**, что и работающий сервер. Пример из руководства: установлены 8.3.24.100 и 8.3.24.150, работает сервер 8.3.24.150 — использовать `webinst` именно из 8.3.24.150.
- **Разрядность** модуля расширения должна совпадать с разрядностью веб-сервера. Сочетание «64-битный веб-сервер + 32-битная платформа» на Linux не поддерживается.
- На Linux для публикации нужны права **root** (`su` или `sudo`). Если прав не хватает, `webinst` выводит диагностическое сообщение, но публикацию продолжает — проверяйте результат.
- Конфигурация базы не должна быть пустой.
- **Перезапуск веб-сервера обязателен**, если: изменилась версия платформы; изменился путь к модулю расширения; сделана новая публикация для Apache; публикация отключена.
- **Несколько версий 1С на одном компьютере**: нужен отдельный экземпляр Apache на каждую версию, публикация в этом случае только ручная.
- **MPM**: на Linux с Apache 2.2 и новее рекомендуется модуль `worker`, остальные MPM не рекомендуются.
- **Файловая база**: модуль расширения сам работает с файлом базы; запросы клиентов выполняются по одному, в порядке поступления. В каждом рабочем процессе веб-сервера работает свой экземпляр модуля расширения. Чтобы корректно получать результаты фоновых заданий, публикацию должен обслуживать **не более чем один рабочий процесс** — в секции worker задать `ServerLimit 1`.
- Каталог (`-dir`) и имя публикации (`-wsdir`) — латиницей.
- При работе через обратный прокси он должен передавать заголовки `X-Forwarded-Port`, `X-Forwarded-Host`, `X-Forwarded-Proto` — по ним платформа восстанавливает внешний адрес запроса [офиц., формулировка из руководства 8.3 более ранней редакции — перепроверено 2026-10-10 на yellow-erp.com: прокси должен «формировать корректные заголовки X-Forwarded-Port, X-Forwarded-Host и X-Forwarded-Proto», чтобы платформа восстановила внешний запрос]. Подтверждено по полному тексту документации 8.3.27, разд. 8.10.3 «Reverse Proxy» (сверено 10.10.2026): прокси должен формировать заголовки `X-Forwarded-Port`, `X-Forwarded-Host` и `X-Forwarded-Proto` — чтобы платформа восстановила исходный запрос, и `X-Forwarded-For` — чтобы она определила адрес клиента; за подробностями настройки документация отсылает к документации самого прокси-сервера. Конспект — `../its-docs/adm-gl08-veb-servery-p2.md`.
- HTTP не обеспечивает защиту соединения; для баз в промышленной эксплуатации через Интернет «настоятельно рекомендуется» HTTPS.

Практические следствия:

- На одном хосте удобно держать кластер 1С и Apache вместе (тогда версия модуля всегда совпадает с версией сервера). На отдельном веб-сервере нужно ставить компонент `ws` той же сборки и обновлять его одновременно с кластером.
- Веб-клиент, тонкий клиент через веб-сервер и мобильный клиент считаются обычными пользовательскими сеансами (раздел 2.2.7.5 руководства «Клиент-серверный вариант» перечисляет их среди пользовательских сеансов через модуль расширения веб-сервера) и потому расходуют клиентские лицензии. Вызовы веб-сервисов, HTTP-сервисов и OData — отдельные типы сеансов (`WSConnection`, `HTTPServiceConnection`, `ODataConnection`), клиентских лицензий они **не требуют** (документация 8.3.27, разд. 10.3.4.8 «Интернет-сервисы, фоновые задания»; сверено по полному тексту 10.10.2026). Прежнее утверждение этой статьи, что сервисные сеансы занимают клиентскую лицензию, было ошибочным. Для клиент-серверной базы при этом по-прежнему нужна серверная лицензия.
- В правилах требований назначения функциональности кластера соединения через веб-сервер описываются объектом `WebServerExtension` (веб-клиент, тонкий клиент через веб-сервер, мобильный клиент, интернет-сервисы) [офиц., 2.2.7.6; проверено 2026-10-10].

### 3.3. MPM: worker, event, prefork

Что сказано официально: «на Linux рекомендуется worker MPM; другие MPM не рекомендуются» и «с Apache 2.2 и новее используйте многопроцессный модуль worker» (руководство 8.3.27, 8.2 и 8.10.1.1).

Что есть на практике:

- В Ubuntu и Debian по умолчанию включён `mpm_event` (если не установлен `libapache2-mod-php`, который переключает на `prefork`).
- Многие инструкции публикуют базу на `event` без переключения, и это работает; образ `1C-Company/docker_fresh` тоже ставит `apache2` из Debian и MPM не меняет. Но поддержка 1С вправе сослаться на документацию, поэтому на рабочем сервере надёжнее включить `worker`.
- `prefork` для 1С плох: каждый процесс — отдельный экземпляр модуля расширения со своим пулом соединений, отсюда лишняя память и соединения с кластером, а для файловой базы — ошибки блокировок.

```bash
apachectl -V | grep -i 'server mpm'      # Server MPM:     event
apachectl -M | grep mpm                  # mpm_event_module (shared)

sudo a2dismod mpm_event                  # сначала выключить текущий MPM
sudo a2enmod mpm_worker
sudo apachectl configtest
sudo systemctl restart apache2           # смена MPM требует полного перезапуска
apachectl -V | grep -i 'server mpm'      # Server MPM:     worker
```

Параметры worker лежат в `/etc/apache2/mods-available/mpm_worker.conf`. Значения по умолчанию в Debian/Ubuntu: `StartServers 2`, `MinSpareThreads 25`, `MaxSpareThreads 75`, `ThreadLimit 64`, `ThreadsPerChild 25`, `MaxRequestWorkers 150`, `MaxConnectionsPerChild 0` [проверено 2026-10-10 по исходникам пакета]. `ServerLimit` в файле не задан — действует значение Apache по умолчанию (16). Настройка под 1С — в разделе 12.

### 3.4. Компонент платформы «Модули расширения веб-сервера»

`wsap24.so` и `webinst` ставятся компонентом `ws` единого дистрибутива (подробно — статья `02-ustanovka-servera-ubuntu.md`).

```bash

На Ubuntu 22.04+ нужен только `wsap24.so`; в 8.5.4 поддержка Apache 2.0/2.2 прекращена.

## 4. Публикация: утилита webinst, конфигуратор, вручную

### 4.1. Синтаксис webinst

Утилита лежит в каталоге версии: `/opt/1cv8/x86_64/<версия>/webinst`. Запускается под root.

```text
webinst [-publish] | -delete  <веб-сервер>
        -wsdir <виртуальный каталог>
        -dir <физический каталог>
        -connstr <строка соединения>
        [-confpath <файл конфигурации Apache>]
        [-descriptor <шаблон default.vrd>]
        [-osauth]
```

| Ключ | Значение |
|---|---|
| `-publish` | Опубликовать. Действие по умолчанию, ключ можно не писать |
| `-delete` | Удалить публикацию. Обязателен только `-wsdir`; остальные ключи можно указать. С `-descriptor` публикация удаляется, только если виртуальный каталог и строка соединения совпадают с шаблоном. **По документации вместе с публикацией удаляется и физический каталог, в котором она располагалась** [офиц., руководство 8.3 ранней редакции; проверено 2026-10-10] — поэтому каталог публикации должен быть отдельным и не содержать ничего, кроме `default.vrd`. Что происходит со строкой `LoadModule` при удалении последней публикации — ⚠ не подтверждено: официально не описано |
| `-apache24` | Тип веб-сервера: Apache 2.4. За один запуск указывается один тип |
| `-apache22`, `-apache2` | Apache 2.2 и 2.0. В 8.5.4 удалены (в V8Update записано «`-apache` и `-apache22`») |
| `-iis` | IIS, только Windows |
| `-wsdir <имя>` | Имя виртуального каталога — последняя часть адреса (`http://хост/<имя>`). Латиница. Попадает в атрибут `base` файла `default.vrd`. Допускается вложенное имя вида `a/demo` (так публикует `1C-Company/docker_fresh`) |
| `-dir <каталог>` | Физический каталог публикации, где будет лежать `default.vrd`. По документации **должен существовать** заранее. Латиница |
| `-connstr <строка>` | Строка соединения с базой. Серверная: `"Srvr=srv1c;Ref=demo;"` (с портом менеджера кластера: `"Srvr=srv1c:1741;Ref=demo;"`). Файловая: `"File=/srv/1c/bases/demo;"` |
| `-confpath <файл>` | Полный путь к конфигурационному файлу Apache. В примерах руководства для Apache 2.4 ключ не указан: на Linux платформа сама ищет файл `apache2.conf` в каталоге `/etc/apache2/` [офиц., 8.10.1.2.3; проверено 2026-10-10] (для Apache 2.0 — в `/etc/httpd/conf/`). В RHEL-подобных системах (`/etc/httpd/conf/httpd.conf`) без `-confpath` файл найден не будет. На практике путь указывают всегда |
| `-descriptor <файл>` | Шаблон в формате `default.vrd`. Из него берутся все настройки публикации; значения `base` и `ib` заменяются тем, что задано в `-wsdir` и `-connstr`. При публикации существующий `default.vrd` **заменяется** файлом шаблона [офиц.; проверено 2026-10-10] |
| `-osauth` | Включить аутентификацию ОС. **Только IIS** |

Правила записи [офиц.]:

- Имя ключа и значение разделяются пробелом. Значения с пробелами и точками с запятой берутся в двойные кавычки.
- Кавычка внутри значения записывается удвоенной: `-connstr "File=""/srv/my db/demo"";"`.
- Каждая часть строки соединения заканчивается точкой с запятой.
- Официальное написание ключа — `-confpath` (строчными): так он записан в руководстве и в сценариях самой фирмы «1С» (`docker_fresh/modules/helper.py`) [проверено 2026-10-10]. В документации РЕД ОС используется `-confPath`, в статьях interface31.ru и Selectel — `-confpath`; обе инструкции рабочие, то есть на практике утилита принимает оба написания. ⚠ не подтверждено официально: нечувствительность ключей к регистру в документации не описана — в сценариях пишите `-confpath`.
- Значение в кавычках не должно заканчиваться обратной косой чертой (актуально для Windows-путей) [офиц.].

### 4.2. Примеры

```bash
V=8.3.27.2074
W=/opt/1cv8/x86_64/$V/webinst

# 1) Серверная (клиент-серверная) база demo, кластер на хосте srv1c
sudo mkdir -p /var/www/demo
sudo $W -publish -apache24 -wsdir demo -dir /var/www/demo \
     -connstr "Srvr=srv1c;Ref=demo;" -confpath /etc/apache2/apache2.conf
sudo systemctl restart apache2

# 2) Файловая база в каталоге /srv/1c/bases/buh (в нём лежит 1Cv8.1CD)
sudo mkdir -p /var/www/buh
sudo chown -R www-data:www-data /srv/1c/bases/buh
sudo $W -publish -apache24 -wsdir buh -dir /var/www/buh \
     -connstr "File=/srv/1c/bases/buh;" -confpath /etc/apache2/apache2.conf
sudo systemctl restart apache2

# 3) Публикация по шаблону (веб-сервисы, HTTP-сервисы, OData, пул — всё из шаблона)
sudo $W -publish -apache24 -wsdir demo -dir /var/www/demo \
     -connstr "Srvr=srv1c;Ref=demo;" -confpath /etc/apache2/apache2.conf \
     -descriptor /etc/1c/vrd/demo.vrd
sudo systemctl restart apache2

# 4) Удаление публикации
#    ВНИМАНИЕ: по документации удаляется и физический каталог публикации (/var/www/demo).
#    Сначала сохраните default.vrd и убедитесь, что в каталоге нет посторонних файлов.
sudo cp -a /var/www/demo/default.vrd /root/demo.vrd.$(date +%F)
sudo cp -a /etc/apache2/apache2.conf /etc/apache2/apache2.conf.$(date +%F)
sudo $W -delete -apache24 -wsdir demo -dir /var/www/demo -confpath /etc/apache2/apache2.conf
grep -n -A8 '1c publication' /etc/apache2/apache2.conf     # блока demo быть не должно
sudo apachectl configtest && sudo systemctl restart apache2
```

Безопасная альтернатива `-delete` — удалить (или закомментировать) блок `Alias` + `<Directory>` нужной публикации в конфигурации вручную и перезапустить Apache: так вы точно знаете, что изменилось.

Официальные примеры из руководства 8.3.27 (Linux):

```text
webinst -apache24 -wsdir DemoWS -dir /var/www/DemoWS -connstr "Srvr=server:1741;Ref=demo;"
webinst -publish -apache24 -wsdir demo-ws -dir /var/www/demo-ws -connstr "Srvr=server:1741;Ref=demo;" -descriptor apache-template.vrd
```

### 4.3. Что делает webinst

Шаги публикации по документации (8.3.1): регистрация модуля расширения веб-сервера; регистрация виртуального приложения; создание каталога приложения и файла `default.vrd`; для файловой базы — выдача прав на каталог базы. На Linux дополнительно: группа пользователя веб-сервера становится группой-владельцем каталога с `default.vrd` и получает право чтения этого файла; для файловой базы та же группа назначается каталогу базы с наследованием [офиц., 8.3.2.1].

В `/etc/apache2/apache2.conf` (в конец файла) добавляется:

```apache
LoadModule _1cws_module "/opt/1cv8/x86_64/8.3.27.2074/wsap24.so"

# 1c publication
Alias "/demo" "/var/www/demo/"
<Directory "/var/www/demo/">
    AllowOverride All
    Options None
    Require all granted
    SetHandler 1c-application
    ManagedApplicationDescriptor "/var/www/demo/default.vrd"
</Directory>
```

Строка `LoadModule` одна на весь Apache; блок `Alias` + `<Directory>` — по одному на публикацию. Вид строки `LoadModule` подтверждён документацией РЕД ОС (`LoadModule _1cws_module "/opt/1cv8/x86_64/8.3.21.1197/wsap24.so"`, дописывается в конец файла) и статьёй interface31.ru [проверено 2026-10-10]. Состав директив блока подтверждён официальным примером ручной настройки из раздела 2.8.1.3 руководства 8.3.27: `<Directory "…">`, `AllowOverride None`, `Options None`, `Order allow,deny` + `Allow from all` (синтаксис 2.2), `SetHandler 1c-application`, `ManagedApplicationDescriptor <путь>/default.vrd` [проверено 2026-10-10]. А вот то, что именно записывает сама утилита `webinst` для Apache 2.4 (в частности `AllowOverride All` вместо `None`, строка-комментарий `# 1c publication`, кавычки вокруг пути), приведено по типовому результату — ⚠ не подтверждено: ни одна из прочитанных при рецензии страниц (руководство 8.3.27, РЕД ОС, interface31.ru, Selectel) вывод утилиты не приводит. Сверьте со своим файлом: `grep -n -A8 '1c publication' /etc/apache2/apache2.conf`. От точного вида блока зависит только одно практическое утверждение этой статьи — что в нём стоит `AllowOverride All` (то есть `.htaccess` в каталоге публикации действует).

Минимальный `default.vrd`, который создаёт `webinst` без шаблона:

```xml
<?xml version="1.0" encoding="UTF-8"?>
<point xmlns="http://v8.1c.ru/8.2/virtual-resource-system"
       xmlns:xs="http://www.w3.org/2001/XMLSchema"
       xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance"
       base="/demo"
       ib="Srvr=srv1c;Ref=demo;">
</point>
```

Проверка результата:

```bash
grep -n '_1cws_module' /etc/apache2/apache2.conf
grep -n -A8 '1c publication' /etc/apache2/apache2.conf
cat /var/www/demo/default.vrd
sudo apachectl configtest && sudo systemctl restart apache2
apachectl -M | grep 1cws            # _1cws_module (shared)
```

### 4.4. Отдельный файл конфигурации вместо apache2.conf (практика)

Чтобы не смешивать публикации 1С с системным `apache2.conf`, можно указать `webinst` собственный файл. ⚠ не подтверждено: официально `-confpath` описан как «полный путь к конфигурационному файлу (httpd.conf) веб-сервера Apache», поведение утилиты с произвольным включаемым файлом не описано; проверьте на стенде. Надёжный вариант без догадок — ручная публикация (раздел 4.6) в файле `conf-available/1c-publish.conf`.

```bash
sudo touch /etc/apache2/conf-available/1c-publish.conf
sudo a2enconf 1c-publish
sudo $W -publish -apache24 -wsdir demo -dir /var/www/demo \
     -connstr "Srvr=srv1c;Ref=demo;" -confpath /etc/apache2/conf-available/1c-publish.conf
sudo apachectl configtest && sudo systemctl restart apache2
```

Важно: `LoadModule _1cws_module` должен встречаться в конфигурации **один раз**. Если он уже есть в `apache2.conf`, вторая строка в другом файле даст предупреждение `module _1cws_module is already loaded, skipping`, а при разных путях загрузится тот модуль, который встретился первым.

### 4.5. Публикация из конфигуратора

Меню конфигуратора: «Администрирование → Публикация на веб-сервере». Конфигуратор должен быть запущен **на компьютере с веб-сервером** с правами root и иметь ту же разрядность, что и веб-сервер. На Ubuntu Server без графики это неудобно, поэтому штатный путь — `webinst`.

Диалог публикации и соответствие полей файлу `default.vrd` [офиц., 8.3.2]:

| Поле диалога | Ключ `webinst` / место в `default.vrd` |
|---|---|
| Имя | `-wsdir`; атрибут `base` элемента `<point>` |
| Веб-сервер | `-apache24` и т. п. (на Linux — только Apache) |
| Каталог | `-dir` (должен существовать) |
| Публиковать доступ для клиентских приложений | атрибут `enable` элемента `<point>` |
| Публиковать стандартный интерфейс OData | атрибут `enableStandardOData` элемента `<point>` |
| Публиковать 1С:Аналитику | элемент `<analytics>` |
| Публиковать дистрибутив тонкого клиента | атрибуты семейства `pubdst*` элемента `<point>` (ZIP-архив дистрибутива) |
| Использовать аутентификацию ОС | только IIS (`-osauth`) |
| Адрес перехода при окончании работы веб-клиента | элемент `<exitURL>` |
| Имя прогрессивного веб-приложения | элемент `<progressiveWebApplication>` |
| Вкладка «Web-сервисы»: Публиковать Web-сервисы | атрибут `enable` элемента `<ws>` |
| …Публиковать Web-сервисы по умолчанию | атрибут `pointEnableCommon` элемента `<ws>` |
| …таблица: флажок, Имя, Адрес | атрибуты `enable`, `name`, `alias` элемента `<ws><point>` |
| …Публиковать Web-сервисы расширений по умолчанию | атрибут `publishExtensionsByDefault` элемента `<ws>` |
| Вкладка «HTTP сервисы»: Публиковать HTTP сервисы по умолчанию | атрибут `publishByDefault` элемента `<httpServices>` |
| …таблица: флажок, Имя | атрибуты `enable`, `name` элемента `<service>` |
| …Публиковать HTTP сервисы расширений по умолчанию | атрибут `publishExtensionsByDefault` элемента `<httpServices>` |
| Вкладка OpenID | элемент `<openid>`: адрес провайдера — `<rely>`, «использовать как провайдер» — `<provider>` |
| Вкладка «Прочие»: Каталог временных файлов | атрибут `temp` элемента `<point>` |
| …Пул соединений | элемент `<pool>` |
| …Отладка | элемент `<debug>` |
| …Разделение данных | элемент `<zones>` (разделители сопоставляются по порядковому номеру, не по имени) |
| …Фоновые задания в файловом варианте | атрибут `allowexecutescheduledjobs` элемента `<point>` |

Кнопки диалога: «Опубликовать», «Отключить» (удаляет приложение с веб-сервера и «при необходимости» каталог публикации [офиц., 8.3.2.1; проверено 2026-10-10]), **«Сохранить»** (записывает настройки в файл формата `default.vrd` — готовый шаблон для `-descriptor`), «Загрузить» (открывает `.vrd`; атрибуты `ib` и `base` при загрузке игнорируются).

Рабочий приём для сервера без графики [офиц., 8.5–8.7]: открыть базу конфигуратором на рабочей станции, настроить в диалоге веб-сервисы, HTTP-сервисы и OData, нажать «Сохранить», перенести полученный `.vrd` на сервер и опубликовать `webinst … -descriptor файл.vrd`.

Сервисы из **расширений** в таблицах диалога не показываются: их публикуют либо флажками «…расширений по умолчанию», либо ручной правкой `default.vrd`.

### 4.6. Ручная публикация

Всё, что делает `webinst`, можно сделать руками. Это единственный способ, когда нужно несколько версий 1С (несколько экземпляров Apache).

```bash
V=8.3.27.2074
sudo mkdir -p /var/www/demo

# 1) дескриптор публикации
sudo tee /var/www/demo/default.vrd >/dev/null <<'EOF'
<?xml version="1.0" encoding="UTF-8"?>
<point xmlns="http://v8.1c.ru/8.2/virtual-resource-system"
       xmlns:xs="http://www.w3.org/2001/XMLSchema"
       xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance"
       base="/demo"
       ib="Srvr=srv1c;Ref=demo;">
</point>
EOF
sudo chown -R root:www-data /var/www/demo
sudo chmod 750 /var/www/demo && sudo chmod 640 /var/www/demo/default.vrd

# 2) модуль и блок публикации
sudo tee /etc/apache2/conf-available/1c-publish.conf >/dev/null <<EOF
LoadModule _1cws_module "/opt/1cv8/x86_64/$V/wsap24.so"

# 1c publication
Alias "/demo" "/var/www/demo/"
<Directory "/var/www/demo/">
    AllowOverride None
    Options None
    Require all granted
    SetHandler 1c-application
    ManagedApplicationDescriptor "/var/www/demo/default.vrd"
</Directory>
EOF
sudo a2enconf 1c-publish
sudo apachectl configtest && sudo systemctl restart apache2
```

Пояснения к директивам:

| Директива | Смысл |
|---|---|
| `LoadModule _1cws_module "<путь>/wsap24.so"` | загрузка модуля расширения 1С; имя модуля — именно `_1cws_module` |
| `Alias "/demo" "/var/www/demo/"` | виртуальный каталог публикации |
| `SetHandler 1c-application` | все запросы к каталогу обрабатывает модуль 1С |
| `ManagedApplicationDescriptor "<файл>"` | путь к `default.vrd` этой публикации |
| `Require all granted` | синтаксис Apache 2.4 (в 2.2 было `Order allow,deny` / `Allow from all`) |
| `AllowOverride All` | разрешает `.htaccess` в каталоге публикации; если он не нужен — `None` |

Изменения `default.vrd` применяются после перезапуска Apache (или `sudo apachectl graceful`). ⚠ не подтверждено: момент перечитывания `default.vrd` модулем расширения в прочитанной документации не описан (официальный перечень случаев обязательного перезапуска — смена версии, смена пути к модулю, новая публикация, отключение публикации — правку `default.vrd` не упоминает). Надёжнее перезапускать всегда: `sudo systemctl restart apache2`.

### 4.7. Встраивание веб-клиента в другие сайты (X-Frame-Options)

Официальный раздел 8.10.1.3: заголовок задаётся в секции публикации, нужен `mod_headers` (`sudo a2enmod headers`).

<Directory "/var/www/demo/">

## 5. Файл default.vrd

`default.vrd` лежит в каталоге публикации и описывает одну публикацию. Кодировка UTF-8. Ниже — сводный пример со всеми значимыми элементами; в реальном файле оставляйте только нужное.

```xml
<?xml version="1.0" encoding="UTF-8"?>
<point xmlns="http://v8.1c.ru/8.2/virtual-resource-system"
       xmlns:xs="http://www.w3.org/2001/XMLSchema"
       xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance"
       base="/demo"
       ib="Srvr=srv1c;Ref=demo;"
       enable="true"
       enableStandardOData="true"
       temp="/var/tmp/1c-web-demo">

    <!-- веб-сервисы (SOAP) -->
    <ws enable="true" pointEnableCommon="false" publishExtensionsByDefault="false">
        <point name="Exchange" alias="exchange.1cws" enable="true"/>
        <point name="EnterpriseDataExchange_1_0_1_1" alias="EnterpriseDataExchange_1_0_1_1.1cws" enable="true"/>
    </ws>

    <!-- HTTP-сервисы (REST) -->
    <httpServices publishByDefault="false" publishExtensionsByDefault="false">
        <service name="ПередачаДанных" rootUrl="dt" enable="true"
                 reuseSessions="autouse" sessionMaxAge="20" poolSize="10" poolTimeout="5"/>
    </httpServices>

    <!-- стандартный интерфейс OData: параметры повторного использования сеансов -->
    <standardOdata enable="true" reuseSessions="autouse" sessionMaxAge="20" poolSize="10" poolTimeout="5"/>

    <analytics enable="false"/>

    <!-- пул соединений модуля расширения с кластером -->
    <pool size="100" maxAge="20" attempts="5" attemptTimeout="0.5" waitTimeout="0.5"/>

    <!-- отладка -->
    <debug enable="false" url="tcp://localhost"/>

    <!-- разделители (по порядку следования в конфигурации) -->
    <zones>
        <zone value="1024" safe="true" specify="false"/>
    </zones>

    <!-- OpenID: эта база доверяет внешнему провайдеру -->
    <openid>
        <rely url="https://auth.example.com/users/e1cib/oid2op"/>
    </openid>

    <exitURL>https://portal.example.com/</exitURL>
</point>
```

### 5.1. Корневой элемент `<point>`

| Атрибут | Значение | По умолчанию |
|---|---|---|
| `base` | Относительный адрес виртуального каталога, например `/demo`. Рекомендуются символы US-ASCII. Соответствует `-wsdir` | — |
| `ib` | Строка соединения с базой. Серверная: `Srvr=srv1c;Ref=demo;`, файловая: `File=/srv/1c/bases/demo;`. Кавычки внутри XML-атрибута пишутся как `&quot;`: `ib="Srvr=&quot;srv1c&quot;;Ref=&quot;demo&quot;;"` | — |
| `enable` | Разрешает работу тонкого, мобильного и веб-клиента с публикацией. `false` — публикация только для сервисов (веб-сервисы, HTTP-сервисы, OData, OpenID-провайдер) | `true` |
| `enableStandardOData` | Публиковать стандартный интерфейс OData (флажок «Публиковать стандартный интерфейс OData» диалога публикации [офиц., 8.3.2.2.1; проверено 2026-10-10]) | **Уточнено 10.10.2026** (полный текст приложения 3 документации 8.3.27): доступностью OData управляет элемент `<standardOData>` с атрибутом `enable`, подчинённый `<point>`; если элемента в `default.vrd` нет, стандартный интерфейс OData недоступен. Ранее было не подтверждено: значение при отсутствии атрибута в приложении 3 не перечитано. Минимальный `default.vrd` от `webinst` атрибута не содержит, и OData при этом не публикуется (практика) — считайте, что `false`, и для OData задавайте `true` явно |
| `temp` | Каталог временных файлов модуля расширения или файловой базы. Если не задан: для файловой базы — подкаталог `1Cv8Tmp` рядом с базой, иначе временный каталог пользователя, от имени которого выполняется запрос | не задан |
| `pubdst*` | Семейство атрибутов с адресами ZIP-архивов дистрибутива тонкого клиента (по вариантам ОС и разрядности) — для автообновления клиента при несовпадении версий. В руководстве 8.3 ранней редакции это был единственный атрибут `pubdst` («полный URL файла с дистрибутивом клиентского приложения; архив ZIP; только Windows») [проверено 2026-10-10]; в 8.3.27 руководство говорит о «семействе `pubdst*`» (по строке таблицы на каждый вариант дистрибутива). **Уточнено 10.10.2026** (полный текст приложения 3 документации 8.3.27): атрибуты называются `pubdst32`, `pubdst64`, `pubdstmac64`, `pubdstlin32`, `pubdstlin64`. Ранее было не подтверждено: точные имена атрибутов семейства (вида `pubdst32`, `pubdst64`, `pubdstmac…`) — приложение 3 закрыто; получите их кнопкой «Сохранить» в диалоге публикации конфигуратора. Сами дистрибутивы для раздачи ставятся на веб-сервер отдельными установщиками с сайта релизов: `all-clients-distr-A.B.C.D-x86_64.run` (клиенты для всех ОС, поддерживающих обновление по HTTP(S)) или `win-mac-clients-distr-A.B.C.D-x86_64.run` (только Windows и macOS); запуск под root, пакетный режим — `--mode unattended`; файлы попадают в подкаталог `distr` каталога платформы и удаляются вместе с этой версией платформы [офиц., 2.8.1.4; проверено 2026-10-10]. Расположение дистрибутивов задаётся также параметром `PublishDistributiveLocation` файла `conf.cfg` [офиц., упоминание в 4.3.6.4] | не заданы |
| `allowexecutescheduledjobs` | Только файловая база: `off` — модуль расширения не выполняет регламентные задания; `force` — выполняет. Если не задан, задания выполняет приложение, первым подключившееся к базе | не задан |

В строку соединения `ib` можно добавить имя и пароль пользователя 1С (`Usr=…;Pwd=…;`): если клиент не передал стандартных HTTP-заголовков аутентификации, модуль расширения возьмёт их из строки соединения [офиц., 4.3.8.2.3.2]. Это способ сделать «анонимный» HTTP-сервис; пароль при этом лежит в открытом виде — ограничивайте права на `default.vrd` и права самого пользователя 1С.

### 5.2. `<ws>` — веб-сервисы

| Элемент / атрибут | Значение | По умолчанию |
|---|---|---|
| `ws/@enable` | `false` — запретить все веб-сервисы этой публикации | `true` |
| `ws/@pointEnableCommon` | Доступны ли сервисы, для которых нет явного `<point enable=…>` («публиковать Web-сервисы по умолчанию») | `true` |
| `ws/@publishExtensionsByDefault` | Публиковать веб-сервисы из расширений конфигурации | — |
| `ws/point/@name` | Имя веб-сервиса из конфигурации | — |
| `ws/point/@alias` | Адрес (синоним). К сервису можно обращаться и по имени, и по адресу | — |
| `ws/point/@enable` | Разрешить или запретить конкретный сервис | `true` |

Пример «опубликовать только один сервис» (из `1C-Company/docker_fresh`):

```xml
<point xmlns="http://v8.1c.ru/8.2/virtual-resource-system" base="/sc" ib="Srvr=srv;Ref=sm;" enable="false">
    <ws pointEnableCommon="false">
        <point name="SessionControl_1_0_1_1" alias="SessionControl_1_0_1_1.1cws" enable="true"/>
    </ws>
</point>
```

### 5.3. `<httpServices>` — HTTP-сервисы

| Элемент / атрибут | Значение | По умолчанию |
|---|---|---|
| `httpServices/@publishByDefault` | Публиковать все HTTP-сервисы конфигурации, не перечисленные явно. Отсутствие элемента равносильно `false` | `false` при отсутствии элемента |
| `httpServices/@publishExtensionsByDefault` | Публиковать HTTP-сервисы расширений | — |
| `service/@name` | Имя HTTP-сервиса в конфигурации | — |
| `service/@rootUrl` | Корневой URL сервиса (часть адреса после `/hs/`) | — |
| `service/@enable` | Разрешить или запретить сервис | `true` |
| `service/@reuseSessions` | Повторное использование сеансов: `dontuse` — на каждый вызов новый сеанс; `use` — сеансом управляет клиент; `autouse` — пул сеансов ведёт платформа | По документации 8.3.27 (приложение 3, сверено по полному тексту 10.10.2026) умолчания атрибута: `autouse` — для `<ws><point>` (разд. 3.21.3.2) и `<service>` (разд. 3.21.4.2), `dontuse` — для `<standardOData>` (разд. 3.21.11); допустимые значения — `dontuse`, `use`, `autouse`. Наблюдение автора: `dontuse` для `<service>` и `<ws><point>`, `autouse` для `<standardOdata>` — так записывает конфигуратор |
| `service/@sessionMaxAge` | Время жизни неиспользуемого сеанса, секунды | (подтверждено документацией 8.3.27, приложение 3; сверено 10.10.2026) 20 |
| `service/@poolSize` | Размер пула сеансов | (по полному тексту приложения 3 документации 8.3.27 атрибут `poolSize` описан только у элемента `<analytics>`, умолчание 500; значение автора не подтверждено:) 10 |
| `service/@poolTimeout` | Время ожидания свободного сеанса из пула, секунды | (по полному тексту приложения 3 документации 8.3.27 атрибут `poolTimeout` описан только у элемента `<analytics>`, умолчание — 5 секунд:) 5 |

Значения `dontuse` / `autouse` подтверждены примером конфигурационного файла автономного сервера в руководстве (`reuse-sessions: mode: dontuse|autouse`). **Уточнено 10.10.2026** (полный текст приложения 3 документации 8.3.27): `reuseSessions` и `sessionMaxAge` (умолчание 20 с) описаны у `<ws><point>`, `<service>` и `<standardOData>`; `poolSize` (умолчание 500) и `poolTimeout` (умолчание 5 с) — только у `<analytics>`; изменённые `reuseSessions` и `sessionMaxAge` начинают действовать после перезапуска сервера 1С. Ранее было не подтверждено: атрибуты `reuseSessions`, `sessionMaxAge`, `poolSize`, `poolTimeout` и значения 20/10/5 приведены по типовому `default.vrd`, который создаёт конфигуратор (строки вида `<service name="…" rootUrl="…" enable="true" reuseSessions="dontuse" sessionMaxAge="20" poolSize="10" poolTimeout="5"/>` и `<standardOdata enable="false" reuseSessions="autouse" sessionMaxAge="20" poolSize="10" poolTimeout="5"/>` — по памяти рецензента, совпадает с памятью автора); описание — раздел 17.7 «Reusing Internet service sessions» руководства разработчика и приложение 3 руководства администратора, оба при рецензии недоступны (англоязычная страница руководства разработчика обрывается раньше главы 17). Те же атрибуты применимы к `<ws><point>` и `<standardOdata>`. Самый надёжный способ получить точные имена и значения для своей версии — сохранить `.vrd` из диалога публикации конфигуратора.

Пример (из `1C-Company/docker_fresh`):

```xml
<httpServices publishByDefault="false">
    <service name="ExternalRegistration" rootUrl="ExternalRegistration" enable="true"/>
</httpServices>
```

Зачем нужно повторное использование сеансов: без него каждый вызов HTTP-сервиса создаёт сеанс (авторизация, установка параметров сеанса) — это медленно и при потоке запросов быстро расходует лицензии. В режиме `use` клиент управляет сеансом сам: первый запрос отправляется с HTTP-заголовком `IBSession: start`, платформа возвращает cookie `ibsession`, которую клиент передаёт в следующих запросах; сеанс завершается запросом с заголовком `IBSession: finish` (или по истечении `sessionMaxAge`). **Подтверждено 11.10.2026** («Руководство разработчика» 8.3.27, разд. 17.7.3.2): управляющий элемент — заголовок HTTP-запроса `IBSession`; значение `start` создаёт сеанс (при неудаче клиент получает 406 Not Acceptable), в ответе приходит `Set-Cookie: ibsession=<ID сеанса>`; дальше клиент передаёт `Cookie: ibsession=<ID сеанса>` (неизвестный или уже завершённый идентификатор даёт 400 Bad Request); значение `finish` завершает указанный сеанс; без заголовка сеанс создаётся и завершается при каждом вызове; сеанс завершается и сам, если за время жизни в нём не было действий. Для стандартного интерфейса OData по умолчанию — автоматическое повторное использование и время жизни 20 секунд. Ранее было не подтверждено: записано по памяти (совпадает у автора и рецензента), описание — раздел 17.7 руководства разработчика, при рецензии недоступен. Через обратный прокси cookie `ibsession` должна проходить без изменений; при нескольких веб-серверах запросы одного сеанса сервиса должны попадать туда, где кластер найдёт сеанс (сеансы хранит кластер, так что привязка к веб-серверу для этого не обязательна).

### 5.4. `<pool>` — пул соединений с кластером

Модуль расширения держит пул соединений с рабочими процессами кластера. В начале каждого вызова сеансу назначается соединение из пула, по окончании вызова соединение возвращается в пул [офиц., «Клиент-серверный вариант», 2.2.4].

| Атрибут | Значение | По умолчанию |
|---|---|---|
| `size` | Максимальное число соединений в пуле | 100 |
| `maxAge` | Время жизни неиспользуемого соединения, секунды | 20 |
| `attempts` | Максимальное число попыток установить соединение с сервером 1С | 5 |
| `attemptTimeout` | Таймаут установки соединения, секунды | 0.5 |
| `waitTimeout` | Пауза между попытками, секунды | 0.5 |

Значения по умолчанию и смысл всех пяти атрибутов перепроверены 2026-10-10 по руководству 8.3 ранней редакции (приложение 3, `default.vrd`); официальный пример оттуда: `<pool size="50" maxAge="10" attempts="2"/>`.

Помните: пул свой у **каждого рабочего процесса Apache** (в каждом процессе — свой экземпляр модуля). Период и таймаут проверки соединения модуля с кластером (3 с и 15 с — подтверждено разделом 2.2.5.6, см. 1.4) тоже меняются «параметрами публикации информационной базы на веб-сервере»; диалог публикации относит их к группе «Пул соединений» (элемент `<pool>`) [офиц., 8.3.2.4]. **Уточнено 11.10.2026** (приложение 3 документации 8.3.27, описание элемента `<pool>` файла `default.vrd`): атрибуты `size` (размер пула, по умолчанию 10 000), `maxAge` (время жизни соединения в пуле, в секундах; по умолчанию 20 минут), `attempts` (число попыток соединения с сервером, по умолчанию 5), `attemptTimeout` и `waitTimeout` (ожидание соединения и пауза между попытками, в секундах; по умолчанию по 500), `serverPingPeriod` (по умолчанию 1000 мс, максимум 65 535) и `serverPingTimeout` (по умолчанию 5000 мс); пример из документации — `<pool size="50" maxAge="10" attempts="2" attemptTimeout="1" waitTimeout="1"/>`. Ранее было не подтверждено: имена соответствующих атрибутов — ни руководство «Клиент-серверный вариант», ни глава 8 их не называют; они описаны в приложении 3 (раздел `default.vrd`), закрытом подпиской. Узнать их можно, задав значения в диалоге публикации конфигуратора и нажав «Сохранить».

### 5.5. `<debug>` — отладка

| Атрибут | Значение |
|---|---|
| `enable` | `true` — разрешить отладку кода, выполняемого через эту публикацию |
| `url` | Адрес отладчика, например `tcp://localhost:1560`. Без порта перебираются порты 1560–1591; `tcp://` равносильно `tcp://localhost`. Если адрес не задан, отладка не применяется |
| `protocol` | `tcp` или `http` (для отладки по HTTP `url` указывает на сервер отладки `dbgs`, по умолчанию `http://хост:1550`). **Уточнено 10.10.2026** (полный текст приложения 3 документации 8.3.27): у элемента `<debug>` описаны три атрибута — `enable`, `protocol` (`tcp` — по умолчанию, `http`) и `url`. Ранее было не подтверждено: в руководстве 8.3 ранней редакции у `<debug>` описаны только `enable` и `url` (проверено 2026-10-10), атрибут `protocol` появился позже вместе с отладкой по HTTP; запись вида `<debug enable="true" protocol="http" url="http://srv1c:1550"/>` приведена по типовым файлам из практики. Порт 1550 как порт сервера отладки по умолчанию подтверждён (параметр `--debug-server` автономного сервера: `http://localhost:1550`) |

### 5.6. `<zones>` — разделение данных

Каждый `<zone>` соответствует разделителю **по порядку** следования разделителей в конфигурации.

| Атрибут | Значение | По умолчанию |
|---|---|---|
| `value` | Явное значение разделителя | не задано |
| `safe` | `true` — сеанс через эту публикацию не может менять значение разделителя и отключать разделение («безопасный режим разделения») | `false` |
| `specify` | `true` — значение разделителя указывается в адресе публикации (`http://хост/demo/1024/…`). Если при этом задано `value`, в адресе должно быть именно оно, иначе ошибка 404 | `false` |

```xml
<zones>
    <zone specify="false" safe="true"/>
    <zone specify="true" safe="true"/>
</zones>
```

### 5.7. `<openid>` — OpenID 2.0

| Элемент | Значение |
|---|---|
| `<rely url="…"/>` | Адрес базы-провайдера: `https://хост/<публикация провайдера>/e1cib/oid2op`. Только HTTPS, без `/` в конце |
| `<provider>` | Эта база сама является OpenID-провайдером |
| `<provider><lifetime>` | Время жизни признака аутентификации, секунды. По умолчанию 86400 (сутки), максимум 604800 (неделя) |
| `<provider><returnto>` | Ограничение адресов, на которые провайдер согласен возвращать пользователя (параметр `openid.return_to`); в `docker_fresh` (`other_files/vrd/openid.vrd`) задано `<returnto>.*</returnto>`, то есть любые [наличие элемента и значение проверены 2026-10-10]. **Уточнено 10.10.2026** (полный текст приложения 3 документации 8.3.27, разд. 3.21.8.3.3): элемент `<returnto>` подчинён `<provider>`, может повторяться неограниченное число раз или отсутствовать; его содержимое — регулярное выражение, задающее маску имён сайтов, на которые разрешена переадресация браузера после команды OpenID-провайдера. Ранее было не подтверждено: точная семантика (регулярное выражение? допускается ли несколько элементов? что при отсутствии элемента) — описание в приложении 3 закрыто. Для провайдера, доступного из Интернета, не оставляйте `.*`: ограничьте шаблон своими адресами, например `https://1c\.example\.com/.*` |

```xml
<!-- база-провайдер: клиентские приложения отключены, работает только как провайдер -->
<point xmlns="http://v8.1c.ru/8.2/virtual-resource-system" base="/users-ib"
       ib="Srvr=srv1c;Ref=oidusers;" enable="false">
    <openid>
        <provider>
            <lifetime>432000</lifetime>
        </provider>
    </openid>
</point>
```

Условия [офиц., 6.2.10.4 и 8.8]: имя пользователя базы должно совпадать с идентификатором, который возвращает провайдер; провайдер должен иметь доступ к адресу публикации; OpenID не работает для веб-сервисов; пароль хранится у провайдера. Ключи запуска клиента: `/OIDA+` (по умолчанию) и `/OIDA-`.

### 5.8. `<openidconnect>` — OpenID Connect

Платформа выступает только клиентом OpenID Connect (провайдером быть не может); поддерживается ЕСИА. Ключ сопоставления со стороны провайдера по умолчанию — адрес электронной почты, со стороны базы — имя пользователя (можно `OSUser`, `Email` или запись `UserMatchingKeys`, заполняемую из встроенного языка) [офиц., 6.2.10.5].

Структура элемента — Имена ключей и элемента подтверждены по полному тексту приложения 3 документации 8.3.27 (сверено 10.10.2026; там же встречаются `providerconfig`, `image` и вложенные в `clientconfig` ключи `authority`, `client_id`, `redirect_uri`, `response_type`, `scope`); значения и полный синтаксис — в `../its-docs/adm-pr03-sluzhebnye-fajly-p2.md`. Исходная пометка автора: записано по памяти (JSON-ключи `name`, `title`, `discovery`, `authenticationClaimName`, `authenticationUserPropertyName`, `clientconfig` и элемент `allowStandardAuthentication`); приложение 3 и подробный раздел об OpenID Connect при рецензии недоступны. Не переносите пример на рабочий сервер без сверки с документацией своей версии:

```xml
<openidconnect>
    <providers><![CDATA[
    [
      {
        "name": "keycloak",
        "title": "Корпоративный вход",
        "discovery": "https://sso.example.com/realms/corp/.well-known/openid-configuration",
        "authenticationClaimName": "email",
        "authenticationUserPropertyName": "email",
        "clientconfig": {
          "authority": "https://sso.example.com/realms/corp",
          "client_id": "1c-demo",
          "redirect_uri": "https://1c.example.com/demo/authform.html",
          "response_type": "id_token token",

        }

Подтверждено официально: у описания провайдера есть поля `title` (подсказка) и `image` (картинка в окне входа); в секции `clientconfig` в 8.3.26 появился параметр `client_certificate_hash` (ЕСИА 3.34); в `redirect_uri` с 8.3.25 можно передавать значения разделителей (ключ `/Z`).

### 5.10. Рекомендации по работе с default.vrd

- Храните эталон каждой публикации отдельно (например, `/etc/1c/vrd/demo.vrd`, под контролем версий) и публикуйте всегда с `-descriptor`: при публикации с шаблоном существующий `default.vrd` заменяется шаблоном [офиц.; проверено 2026-10-10]. Повторный запуск `webinst -publish` **без** шаблона пересоздаёт `default.vrd` в минимальном виде, ручные настройки теряются — ⚠ не подтверждено официально (поведение без `-descriptor` при существующей публикации в документации не описано; это типичный отчёт из практики). Перед любой перепубликацией делайте копию: `sudo cp -a /var/www/demo/default.vrd /root/demo.vrd.$(date +%F)`.
- Права: файл читает только `www-data`; в нём могут быть имя и пароль пользователя 1С. `sudo chown root:www-data /var/www/demo/default.vrd && sudo chmod 640 /var/www/demo/default.vrd`.
- Проверка корректности XML: `xmllint --noout /var/www/demo/default.vrd` (пакет `libxml2-utils`).
- Несколько публикаций одной базы — нормальная практика: одна «для людей» (`enable="true"`), другая «для интеграций» (`enable="false"`, только нужные сервисы, своё ограничение доступа).

## 6. Права и пользователи

Официальные требования (8.4.2, 8.5–8.7): пользователю, от имени которого работает Apache, нужны права **чтения и выполнения** на каталог исполняемых файлов конкретной версии платформы; для файловой базы — права **изменения** каталога базы. В Ubuntu этот пользователь — `www-data`.

| Объект | Что нужно `www-data` | Как обычно получается |
|---|---|---|
| `/opt/1cv8/x86_64/<версия>/` | чтение и выполнение (`r-x`) | установщик ставит каталог с правами `755`, дополнительно ничего делать не нужно (практика) |
| `/var/www/<имя>/` и `default.vrd` | чтение | `webinst` назначает группу веб-сервера группой-владельцем каталога и даёт ей чтение `default.vrd` |
| каталог файловой базы | чтение и запись, создание файлов | `webinst` назначает группу с наследованием; на практике делают владельцем `www-data` |
| `/var/1C/licenses` (если лицензия получается на веб-сервере, файловая база) | чтение | вручную. ⚠ не подтверждено: требование вытекает из общей логики (программную лицензию для файловой базы получает процесс веб-сервера, то есть `www-data`), первоисточник не найден; на Ubuntu 26.04 дополнительно мешают ограничения юнита (раздел 6.1) |
| ключевой файл Kerberos (`HTTP.keytab`) | чтение только `www-data` | вручную: `root:www-data`, `640` (так в `../1c/08`, разд. 5.7, и `../apache/02`; вариант `www-data:www-data 600` тоже рабочий) |

Проверка и исправление:

```bash
V=8.3.27.2074
# видит ли www-data модуль и дескриптор
sudo -u www-data test -r /opt/1cv8/x86_64/$V/wsap24.so && echo "модуль доступен"
sudo -u www-data test -r /var/www/demo/default.vrd      && echo "vrd доступен"
namei -l /var/www/demo/default.vrd          # права по всей цепочке каталогов

# каталог публикации
sudo chown -R root:www-data /var/www/demo
sudo chmod 750 /var/www/demo
sudo chmod 640 /var/www/demo/default.vrd

# файловая база: полный доступ веб-серверу, новые файлы наследуют группу
sudo mkdir -p /srv/1c/bases/buh
sudo chown -R www-data:www-data /srv/1c/bases/buh
sudo chmod -R u=rwX,g=rwX,o= /srv/1c/bases/buh
sudo chmod g+s /srv/1c/bases/buh
```

Замечания:

- Для **серверной** базы веб-серверу не нужны никакие права на данные кластера (`/home/usr1cv8/…`) и на СУБД — он общается с кластером по сети.
- `sudo usermod -aG grp1cv8 www-data` встречается в инструкциях (практика, статья для Альт Сервер) и нужен только там, где Apache должен читать файлы группы `grp1cv8` (общий каталог технологического журнала, общая файловая база). Для обычной серверной публикации не требуется. После изменения групп перезапустите Apache.
- Документация Ubuntu предостерегает от выдачи `www-data` права записи в корень сайта. Каталогу публикации запись и не нужна — только каталогу файловой базы, который лучше держать вне `/var/www` (например, в `/srv/1c/bases`).
- Не размещайте файловую базу, каталог публикации, keytab и шаблоны `.vrd` в домашних каталогах: мешают права `/home/<user>` (в Ubuntu 22.04+ домашние каталоги создаются с правами `750`), а в Ubuntu 26.04 юнит `apache2.service` прямо запрещает запись: `ProtectHome=read-only` делает `/home`, `/root` и `/run/user` доступными только для чтения, а `InaccessiblePaths=/root` закрывает `/root` полностью [проверено 2026-10-10]. В журнале изменений пакета это отмечено как изменение, которое «может сломать» сценарии, пишущие в `/home`.
- Одну файловую базу нельзя одновременно открывать и через веб-сервер, и толстым клиентом/кластером с другими правами: файлы блокировок создаются от разных пользователей. Если доступ нужен обоим — общая группа и `g+s`.

Официальные рекомендации для файловой базы, с которой работают и Apache, и другой пользователь (например, конфигуратор под учётной записью администратора) [руководство администратора 8.3.27, 2.8.1.1 «Recommendations for using file infobases»; добавлено при рецензии 2026-10-10]:

- файл принадлежит тому, кто его создал, поэтому всех пользователей базы включают в одну группу, делают её группой-владельцем каталога базы и ставят на каталог `chmod g+s` — новые файлы наследуют группу;
- платформа создаёт файлы с правами `0660`; `umask` может только убрать права, но не добавить;
- для совместной работы с веб-сервером: пользователя, запускающего конфигуратор, включить в группу `www-data`, сделать владельцем каталога базы, установить setgid и задать веб-серверу **`umask 0002`** — строкой в `/etc/apache2/envvars` (в других дистрибутивах — `/etc/default/apache2`, `/etc/sysconfig/httpd`), а при запуске через systemd — drop-in'ом;
- базу на сетевом ресурсе нельзя монтировать с параметром `nobrl` (`mount.cifs`) и публиковать в Samba с `locking=no` — ломаются блокировки;
- то же относится к общему каталогу хранилища конфигурации.

```bash
# общий доступ к файловой базе: администратор ivanov (конфигуратор) + Apache
sudo usermod -aG www-data ivanov
sudo chown -R ivanov:www-data /srv/1c/bases/buh
sudo chmod -R u=rwX,g=rwX,o= /srv/1c/bases/buh
sudo find /srv/1c/bases/buh -type d -exec chmod g+s {} +

# umask 0002 для Apache (официальная рекомендация): drop-in systemd
sudo systemctl edit apache2
#   [Service]
#   UMask=0002
echo 'umask 0002' | sudo tee -a /etc/apache2/envvars     # для запуска через apache2ctl
sudo systemctl daemon-reload && sudo systemctl restart apache2
systemctl show apache2 -p UMask                           # UMask=0002
```

### 6.1. AppArmor и ограничения systemd

**AppArmor.**

- В Ubuntu у `apache2` **нет профиля AppArmor по умолчанию**: в пакете `apache2` (24.04) нет ни одного файла в `/etc/apparmor.d/`; профиль `/etc/apparmor.d/usr.sbin.apache2` поставляется отдельным пакетом `libapache2-mod-apparmor` [проверено 2026-10-10 по спискам файлов пакетов на packages.ubuntu.com] (а также `apparmor-profiles`). Проверка: `sudo aa-status | grep -i apache`.
- Если профиль в режиме enforce, модулю 1С нужны правила на `/opt/1cv8/**` (чтение, отображение в память), каталог публикации и каталог файловой базы. Быстрая диагностика: `sudo aa-complain /usr/sbin/apache2`, повторить действие, посмотреть `sudo journalctl -k | grep -i apparmor`.

**Ограничения systemd: 22.04/24.04 против 26.04.**

- В Ubuntu 22.04 и 24.04 из ограничений в юните только `PrivateTmp=true`; директивы `MemoryDenyWriteExecute` нет [проверено 2026-10-10, тег `debian/2.4.58-1`]. На этих выпусках ошибка «backbas» из-за юнита не возникает.
- В **Ubuntu 26.04** (и в Debian начиная с пакета `apache2` 2.4.66-1 от декабря 2025 года) юнит содержит `MemoryDenyWriteExecute=yes` и ещё около двух десятков ограничений (полный список — в разделе 3.1) [проверено 2026-10-10, тег `debian/2.4.66-2`; запись в журнале изменений: «Harden systemd services. Set ProtectSystem=full, ProtectHome=read-only, RestrictSUIDSGID=yes»].
- Документация РЕД ОС описывает ошибку веб-клиента «ошибка загрузки компоненты backbas … No such file or directory» для платформы **8.3.25 и новее** и лечит её именно отменой `MemoryDenyWriteExecute` (плюс настройка SELinux, которой в Ubuntu нет) [проверено 2026-10-10]. Вывод: на Ubuntu 26.04 со штатным юнитом модуль `wsap24.so` с высокой вероятностью даст ту же ошибку. ⚠ не подтверждено на стенде: сочетание «Ubuntu 26.04 + 1С» при рецензии не проверялось, а сама 26.04 в списке поддерживаемых 1С систем отсутствует.

Drop-in для Ubuntu 26.04 (минимально необходимое — первая директива; остальные раскомментируйте по ситуации):

```bash
sudo systemctl edit apache2
```

```ini
[Service]
# модулю 1С (8.3.25+) нужна возможность делать память одновременно записываемой и исполняемой
MemoryDenyWriteExecute=no

# файловая база, каталог публикации или keytab лежат в /home (лучше перенести в /srv):
#ProtectHome=no

# программная лицензия/аппаратный ключ для ФАЙЛОВОЙ базы получается процессом Apache
# (привязка к оборудованию читает /proc, /sys и устройства) — ⚠ не подтверждено, включать при ошибках лицензирования:
#ProcSubset=all
#ProtectProc=default
#PrivateDevices=no
#DevicePolicy=auto
```

```bash
sudo systemctl daemon-reload
sudo systemctl restart apache2
systemctl show apache2 -p MemoryDenyWriteExecute -p ProtectHome -p ProtectSystem -p PrivateDevices -p PrivateTmp
sudo journalctl -u apache2 -b --no-pager | tail -n 30
```

Если после `MemoryDenyWriteExecute=no` модуль всё ещё не работает, снимайте остальные ограничения по одному (в порядке: `ProcSubset=all` + `ProtectProc=default`, затем `PrivateDevices=no` + `DevicePolicy=auto`, затем `ProtectHome=no`), каждый раз перезапуская Apache и глядя в `/var/log/apache2/error.log` и `journalctl -u apache2`. Найдя виновника, оставьте в drop-in только его: остальные ограничения полезны и публикации 1С не мешают. Отменить drop-in целиком: `sudo systemctl revert apache2`.

Что делают остальные ограничения 26.04 и чем они грозят публикации 1С:

| Директива | Действие | Последствие для 1С |
|---|---|---|
| `MemoryDenyWriteExecute=yes` | запрещает создавать отображения памяти, одновременно доступные на запись и исполнение, и делать записываемую память исполняемой | ошибка загрузки компонент платформы («backbas») — отключить |
| `ProtectHome=read-only` | `/home`, `/root`, `/run/user` только для чтения | файловая база в `/home` не открывается на запись; временные файлы в домашнем каталоге не создаются |
| `InaccessiblePaths=/root …` | каталоги недоступны совсем | keytab, шаблоны `.vrd`, сертификаты в `/root` Apache не увидит |
| `ProtectSystem=full` | `/usr`, `/boot`, `/efi`, `/etc` только для чтения | на 1С не влияет: `/opt`, `/srv`, `/var` остаются доступными на запись (при обычных правах) |
| `PrivateTmp=true` | собственные `/tmp` и `/var/tmp` | каталог из атрибута `temp` в `default.vrd` не должен лежать в `/tmp` и `/var/tmp`, если его нужно видеть снаружи; используйте, например, `/var/lib/1c-web-tmp` |
| `PrivateDevices=yes`, `DevicePolicy=closed` | нет доступа к физическим устройствам | возможны проблемы с аппаратными ключами защиты, если ключ читает сам процесс Apache (файловая база) ⚠ не подтверждено |
| `ProtectProc=invisible`, `ProcSubset=pid` | в `/proc` видны только собственные процессы, нет `/proc/cpuinfo`, `/proc/meminfo` и т. п. | возможны сбои привязки программной лицензии к оборудованию для файловой базы ⚠ не подтверждено |
| `Type=notify` | Apache сообщает systemd о готовности через `mod_systemd` | на 1С не влияет; `systemctl status apache2` показывает строку состояния с числом запросов |

При обновлении сервера с 24.04 до 26.04 (`do-release-upgrade`) юнит меняется вместе с пакетом — рабочая публикация может перестать открываться сразу после обновления ОС. Добавьте drop-in **до** обновления: неизвестная директива старому systemd не мешает, а `MemoryDenyWriteExecute=no` в 24.04 — просто значение по умолчанию.

- В дистрибутивах семейства RHEL (РЕД ОС) та же ошибка лечится drop-in'ом `/etc/systemd/system/httpd.service.d/override.conf` с `MemoryDenyWriteExecute=no` и, если не помогло, настройкой SELinux: `sudo semanage fcontext -a -t httpd_sys_script_exec_t "/opt/1cv8(/.*)?"`, `sudo restorecon -Rv /opt/1cv8`, `sudo setsebool -P httpd_execmem on`, `sudo setsebool -P httpd_can_network_connect on` [документация РЕД ОС 7.3; проверено 2026-10-10].

## 7. Проверка публикации

### 7.1. Со стороны сервера

```bash
sudo apachectl configtest                       # Syntax OK
apachectl -M | grep 1cws                        # _1cws_module (shared)
sudo ss -tlnp | grep -E 'apache2|:80 |:443 '    # кто слушает 80/443

# веб-клиент: должен ответить модуль 1С (код 200 или перенаправление 301/302), а не 404/500/503
curl -sS -o /dev/null -w '%{http_code}\n' http://localhost/demo/
curl -sI http://localhost/demo/

# веб-сервис: WSDL
curl -sS -u 'Администратор:пароль' 'http://localhost/demo/ws/Exchange?wsdl' | head -n 5

# HTTP-сервис
curl -sS -u 'Администратор:пароль' -w '\n%{http_code}\n' 'http://localhost/demo/hs/dt/ping'

# OData: метаданные и список сущностей в JSON
curl -sS -u 'Администратор:пароль' 'http://localhost/demo/odata/standard.odata/$metadata' | head -c 400
curl -sS -u 'Администратор:пароль' 'http://localhost/demo/odata/standard.odata/?$format=json' | head -c 400

# доступность кластера с веб-сервера
getent hosts srv1c
nc -zv srv1c 1541
nc -zv srv1c 1560

# журналы
sudo tail -n 50 /var/log/apache2/error.log
sudo tail -n 20 /var/log/apache2/access.log
```

Как читать коды ответа:

| Код | Что обычно означает |
|---|---|
| 200, 301, 302 | Публикация отвечает. Запрос `/demo` без завершающей косой черты Apache сам перенаправляет (301) на `/demo/` — это работа `mod_dir`, а не 1С; дальше веб-клиент перенаправляет браузер на адрес с кодом языка интерфейса: по руководству (раздел о запуске веб-клиента, глава 4) выбранный язык дописывается к базовому адресу — `http://localhost/demo` → `http://localhost/demo/en`; язык можно задать параметром адреса `?l=en` (региональные установки — `?vl=en`), а если точной локали (`en_US`) нет, берётся её языковая часть (`en`) [проверено 2026-10-10]. ⚠ не подтверждено: точный код перенаправления (301 или 302) в документации не указан и на стенде не проверялся; ответ на запрос `HEAD` (`curl -I`) может отличаться от ответа на `GET`, поэтому для проверки надёжнее вариант с `-o /dev/null -w '%{http_code}'` и `-L` |
| 401 | Сервис требует аутентификации: не передан или неверен логин/пароль (Basic, UTF-8) |
| 403 | Запрет на уровне Apache (`Require`, права на каталог — см. `AH00035` в `error.log`). ⚠ не подтверждено: что неопубликованный сервис может отвечать 403, а не 404, — предположение автора без источника |
| 404 | Неверный регистр имени публикации; нет `Alias`; сервис не опубликован; OData не включён; значение разделителя в адресе не совпало с `value` |
| 500 | Ошибка модуля: неверный `default.vrd`, нет доступа к кластеру, несовпадение версий, ошибка в коде сервиса. Подробности — в теле ответа и `error.log` |
| 502, 504 | Отвечает уже прокси (nginx): Apache недоступен или не уложился в таймаут |
| 503 | Apache исчерпал рабочие потоки или перезапускается |

Имя и пароль с кириллицей передавайте в UTF-8 (платформа ожидает учётные данные именно в UTF-8 [офиц.]).

### 7.2. Со стороны клиента

- **Браузер**: `http://srv1c/demo`. Появление окна входа 1С или сообщения об отсутствии лицензии означает, что публикация работает (сообщение о лицензии — вопрос лицензирования, а не веб-сервера). Язык интерфейса и региональные установки задаются параметрами адреса: `http://srv1c/demo?l=ru`, `http://srv1c/demo?vl=ru` (неверный код локали — веб-клиент закрывается с ошибкой); после входа адрес принимает вид `http://srv1c/demo/ru` [офиц., глава 4; проверено 2026-10-10]. При обращении через обратный прокси этот дописанный сегмент пути должен проходить без изменений — ещё одна причина не переписывать путь в `proxy_pass`.
- **Несовпадение версий тонкого клиента и сервера**: версии должны совпадать точно; тонкий клиент ищет подходящий дистрибутив в каталоге установки, в каталогах `DistributiveLocation`, по адресу из сообщения о несовпадении версий (его сервер берёт из параметра `PublishDistributiveLocation` файла `conf.cfg` или из атрибута `pubdst` файла `default.vrd`) и через интернет-сервисы при подключении по HTTP [офиц., 4.3.6.4; проверено 2026-10-10].
- **Тонкий клиент**: в окне запуска «Добавить → Добавление в список существующей информационной базы → На веб-сервере», адрес `http://srv1c/demo`. Из командной строки: `1cv8c ENTERPRISE /WS"http://srv1c/demo" /N"Администратор" /P"пароль"`. В `ibases.v8i`: `Connect=ws="http://srv1c/demo";`.
- В меню «Справка → О программе» тонкий клиент показывает, что работа идёт через веб-сервер (практика, interface31.ru).
- **Мобильный клиент**: тот же адрес; для HTTPS сертификат сервера должен быть доверенным на устройстве.
- Сеансы веб-клиента и тонкого клиента через веб-сервер обращаются к кластеру не реже чем раз в 10 минут; по умолчанию сеанс засыпает после 1200 секунд бездействия (параметр информационной базы, задаётся в конфигураторе) [офиц., руководство «Клиент-серверный вариант», 2.2.4; проверено 2026-10-10].
- Автономный сервер: веб-клиент — `http://хост:8314/<базовый путь>`, тонкий клиент по HTTP — `1cv8c ENTERPRISE /WS"http://хост:8314"`, по TCP/IP — `/S хост\имя_базы` [офиц., 7.3.4; проверено 2026-10-10].

## 8. HTTPS

Платформа поддерживает TLS 1.0–1.3 (SSL 3.0 не поддерживается). Сертификат сервера считается действительным, только если подпись верна, срок не истёк и имя совпадает с доменом сайта. В полях сертификата допустимы только US-ASCII или Punycode (не Unicode). Особенность TLS 1.3: **клиентские** сертификаты поддерживаются только с алгоритмами ГОСТ, серверный сертификат может быть любым [офиц., 8.9.2; проверено 2026-10-10]. Если нужна взаимная аутентификация обычными (RSA/ECDSA) клиентскими сертификатами, ограничьте на веб-сервере протокол версией TLS 1.2 для этого хоста.

### 8.1. Включение mod_ssl

```bash
sudo a2enmod ssl headers rewrite
sudo a2ensite default-ssl            # /etc/apache2/sites-available/default-ssl.conf
sudo apachectl configtest
sudo systemctl restart apache2
curl -kI https://localhost/demo/
```

`default-ssl.conf` из коробки использует тестовый самоподписанный сертификат пакета `ssl-cert`: `/etc/ssl/certs/ssl-cert-snakeoil.pem` и `/etc/ssl/private/ssl-cert-snakeoil.key` (перевыпуск: `sudo make-ssl-cert generate-default-snakeoil --force-overwrite`). Для работы его нужно заменить.

Блок публикации 1С, который `webinst` записал в `apache2.conf`, находится в общем контексте сервера и поэтому действует и в `*:80`, и в `*:443` — дублировать его в виртуальном хосте не нужно.

### 8.2. Виртуальный хост для 1С

Файл `/etc/apache2/sites-available/1c-ssl.conf`:

```apache
<VirtualHost *:443>
    ServerName 1c.example.com

    SSLEngine on
    SSLCertificateFile    /etc/letsencrypt/live/1c.example.com/fullchain.pem
    SSLCertificateKeyFile /etc/letsencrypt/live/1c.example.com/privkey.pem

    # HSTS: включать, когда HTTPS уже отлажен
    Header always set Strict-Transport-Security "max-age=31536000"

    ErrorLog  ${APACHE_LOG_DIR}/1c-ssl-error.log
    CustomLog ${APACHE_LOG_DIR}/1c-ssl-access.log combined
</VirtualHost>
```

Файл `/etc/apache2/sites-available/1c-http.conf` (перенаправление на HTTPS, проверка ACME остаётся доступной по HTTP):

```apache
<VirtualHost *:80>
    ServerName 1c.example.com

    RewriteEngine On
    RewriteCond %{REQUEST_URI} !^/\.well-known/acme-challenge/
    RewriteRule ^(.*)$ https://%{HTTP_HOST}$1 [R=301,L]
</VirtualHost>
```

```bash
sudo a2ensite 1c-ssl 1c-http
sudo a2dissite 000-default default-ssl      # если других сайтов нет
sudo apachectl configtest && sudo systemctl restart apache2
```

Пояснения:

- С Apache 2.4.8 цепочка промежуточных сертификатов кладётся в тот же файл, что и сертификат (`fullchain.pem`); директива `SSLCertificateChainFile` устарела.
- Общие параметры TLS (`SSLProtocol`, `SSLCipherSuite`) лежат в `/etc/apache2/mods-available/ssl.conf`. Рекомендуемый набор берите из генератора конфигураций Mozilla — он переехал на configurator.tlsref.org (TLSRef). С версии 5.8 профиль Intermediate пишет `SSLProtocol -all +TLSv1.2 +TLSv1.3` (уточнено 20.10.2026; подробно — `../apache/02-https-bezopasnost-autentifikaciya.md`).
- Перенаправление 301 хорошо для браузеров. Тонким и мобильным клиентам, а также интеграциям сразу выдавайте адрес `https://…`: POST-запрос при перенаправлении может быть повторён как GET.
- **HSTS** (`Strict-Transport-Security`) заставляет браузер ходить только по HTTPS в течение `max-age` секунд. Пока идёт отладка — не включайте или ставьте маленький `max-age`: откатить заголовок у клиентов нельзя. `includeSubDomains` добавляйте, только если все поддомены работают по HTTPS.
- Certbot умеет делать и перенаправление, и HSTS сам: ключи `--redirect` и `--hsts`.

### 8.3. Собственный центр сертификации и самоподписанные сертификаты

Для внутренней сети (ВМ на Windows-хосте, имя вида `srv1c.example.local`) публичный сертификат получить нельзя. Руководство администратора (4.3.9) приводит такой порядок:

```bash
# 1) корневой сертификат (центр сертификации), 10 лет
openssl req -x509 -days 3652 -newkey rsa:2048 -keyout root-ca.key -out root-ca.crt

# 2) файл расширений сервера
cat > server.ext <<'EOF'
authorityKeyIdentifier=keyid,issuer
basicConstraints=CA:FALSE
subjectAltName = @alt_names

[alt_names]
DNS.1 = srv1c.example.local
IP.1 = 192.168.1.50
EOF

# 3) запрос и сертификат сервера на 1 год
openssl req -newkey rsa:2048 -nodes -keyout server.key -out server.csr -subj "/CN=srv1c.example.local"
openssl x509 -req -CAkey root-ca.key -CA root-ca.crt -in server.csr -out server.crt \
        -CAcreateserial -days 365 -extfile server.ext

# 4) установка
sudo install -m 644 server.crt /etc/ssl/certs/1c-server.crt
sudo install -m 600 server.key /etc/ssl/private/1c-server.key
# в виртуальном хосте: SSLCertificateFile /etc/ssl/certs/1c-server.crt
#                      SSLCertificateKeyFile /etc/ssl/private/1c-server.key
```

Ключ `-nodes` (ключ сервера без пароля) и строка `IP.1` добавлены к официальному примеру, чтобы Apache стартовал без запроса пароля и сертификат подходил для обращения по IP-адресу.

Быстрый вариант — один самоподписанный сертификат без своего ЦС:

```bash
sudo openssl req -x509 -nodes -days 825 -newkey rsa:2048 \
     -keyout /etc/ssl/private/1c-selfsigned.key -out /etc/ssl/certs/1c-selfsigned.crt \
     -subj "/CN=srv1c.example.local" \
     -addext "subjectAltName=DNS:srv1c.example.local,IP:192.168.1.50"
```

Как клиенты начинают доверять такому сертификату [офиц., 4.3.9]:

- **Веб-клиент**: импортировать `root-ca.crt` в хранилище доверенных корневых сертификатов компьютера (в Windows — оснастка сертификатов; Firefox использует собственное хранилище).
- **Тонкий клиент**: в свойствах базы, в дополнительных параметрах соединения выбрать «Файл сертификатов УЦ» и указать `root-ca.crt`; клиентский сертификат — «Не предоставлять». Там же есть варианты «Не проверять сертификат сервера» и «Хранилище сертификатов ОС (Windows, Linux или macOS)» [офиц., 5.2.4; проверено 2026-10-10]. Параметры командной строки `/HttpsCA` (источник сертификатов УЦ) и `/HttpsCert` (клиентский сертификат) существуют; **уточнено 10.10.2026** по полному тексту приложения 7 документации 8.3.27 (разд. 7.3.4): `/HttpsCert [-windows] [-linux] [-macos] [-recent] [-auto] [-choose] [-file <path>] [-pwd <password>] [-none]` — источник клиентского сертификата; `/HttpsCA [-windows] [-linux] [-macos] [-file <path>] [-pwd <password>] [-none]` — источник сертификатов удостоверяющих центров; ключи выбора хранилища ОС игнорируются, если заданы `-file` или `-none`. Ранее было не подтверждено: их значения (по памяти рецензента — варианты вида `-file <путь> [-pwd <пароль>]`, `-windows`, `-none`, а также `/HttpsCertSelect -recent|-auto|-choose`) описаны в приложении 7 «Параметры командной строки запуска», которого на англоязычной странице нет, а на ИТС оно закрыто подпиской. Для сценариев используйте настройку в свойствах базы (она сохраняется в `ibases.v8i`).
- **Linux-клиент** доверяет всем сертификатам из `/etc/ssl/certs`; в Debian/Ubuntu/Mint сводный файл — `/etc/ssl/certs/ca-certificates.crt` (в RHEL-подобных — `/etc/pki/tls/certs/ca-bundle.crt`) [офиц.; проверено 2026-10-10]. Добавить свой ЦС: `sudo cp root-ca.crt /usr/local/share/ca-certificates/ && sudo update-ca-certificates`.
- **Мобильный клиент**: импортировать корневой сертификат на устройство.
- Если сама 1С обращается к вашим сервисам по HTTPS (`WSОпределения`, `WSПрокси`, `HTTPСоединение`), в коде передаётся объект `ЗащищенноеСоединениеOpenSSL` [офиц., 8.9.2]. Откуда серверный код берёт корневые сертификаты, описано в приложении 3 руководства (файлы `cacert.pem` и `cacertnx.pem`). **Уточнено 10.10.2026** (полный текст приложения 3 документации 8.3.27, разд. 3.13): начиная с 8.3.20 в режиме совместимости 8.3.8 и выше используется файл `cacertnx.pem`, а затем хранилище сертификатов ОС; в режиме совместимости 8.3.7 и ниже — только `cacert.pem`; с 8.3.8 до 8.3.19 использовалось только хранилище ОС. Расположение файлов в Linux документация не называет. Ранее было не подтверждено: этот раздел прочитать не удалось ни автору, ни рецензенту (в ранней редакции руководства на yellow-erp.com он не найден). Практический способ, не зависящий от этого: передавать в `ЗащищенноеСоединениеOpenSSL` объект `СертификатыУдостоверяющихЦентровФайл` с путём к своему `root-ca.crt` либо объект системного хранилища (`СертификатыУдостоверяющихЦентровLinux`, в новых версиях также `СертификатыУдостоверяющихЦентровОС`) — тогда используется хранилище ОС, куда свой ЦС добавляется командой `update-ca-certificates` (см. пункт про Linux-клиент выше). Имена объектов встроенного языка приведены по памяти рецензента — сверяйте с синтакс-помощником своей версии.

### 8.4. Let's Encrypt (certbot)

Условия: публичное DNS-имя, указывающее на сервер, и доступность порта 80 из Интернета (проверка HTTP-01). Для сервера за NAT пробросьте 80 и 443.

```bash
sudo apt install -y certbot python3-certbot-apache

# получить сертификат и автоматически настроить Apache (HTTPS-хост, перенаправление, HSTS)
sudo certbot --apache -d 1c.example.com --redirect --hsts \
     -m admin@example.com --agree-tos -n

# только получить сертификат, Apache настроить вручную
sudo certbot certonly --apache -d 1c.example.com
# или через каталог сайта, не трогая конфигурацию
sudo certbot certonly --webroot -w /var/www/html -d 1c.example.com

sudo certbot certificates                 # что выпущено и до какого числа
sudo certbot renew --dry-run              # проверка продления
systemctl list-timers | grep -i certbot   # таймер автопродления (certbot.timer)
```

| Ключ certbot | Значение |
|---|---|
| `--apache` | плагин Apache: и проверка, и установка сертификата |
| `certonly` | только получить сертификат, конфигурацию не менять |
| `-d <имя>` | доменное имя (ключ можно повторять) |
| `--redirect` / `--no-redirect` | добавить / не добавлять перенаправление HTTP → HTTPS |
| `--hsts` | добавить заголовок `Strict-Transport-Security` |
| `--staple-ocsp` | включить OCSP stapling |
| `-m <почта>`, `--agree-tos`, `-n` | почта учётной записи, согласие с условиями, без вопросов |
| `--webroot -w <каталог>` | проверка через файлы в `<каталог>/.well-known/acme-challenge` |
| `--standalone` | certbot сам слушает порт 80 (Apache на это время нужно остановить) |
| `--deploy-hook '<команда>'` | выполнить команду после успешного выпуска или продления |
| `--dry-run` | проверка без выпуска |

Файлы сертификата: `/etc/letsencrypt/live/<имя>/fullchain.pem` (сертификат и цепочка), `privkey.pem` (ключ), `cert.pem`, `chain.pem`. В конфигурации ссылайтесь на эти пути, не копируйте файлы.

Продление:

- Пакет certbot ставит таймер systemd; при плагине `--apache` Apache перечитывается автоматически. Если сертификат получен через `certonly --webroot`, добавьте исполняемый сценарий в `/etc/letsencrypt/renewal-hooks/deploy/`, например с командой `systemctl reload apache2` (или `nginx`).
- Версии certbot в репозиториях Ubuntu: 22.04 — 1.21.0, 24.04 — 2.9.0 (`2.9.0-1`), 26.04 — 4.0.0 (`4.0.0-4`) [24.04 и 26.04 проверены 2026-10-10]. Начиная с 4.0.0 (07.04.2025) certbot продлевает сертификат, когда остаётся меньше трети срока; более старые версии — за 30 дней до конца [журнал изменений certbot; проверено 2026-10-10]. Поддержка ACME Renewal Information (ARI — сервер сам сообщает клиенту, когда продлевать) появилась в 4.1.0 (10.06.2025) — в репозиториях Ubuntu её нет ни в одном LTS. Актуальная версия certbot на 2026-10-10 — 5.8.0 (01.09.2026). Свежую версию даёт snap: `sudo snap install --classic certbot`.
- **Сроки действия сокращаются** [офиц., Let's Encrypt; проверено 2026-10-10]: профиль `tlsserver` — 45 дней с 13.05.2026 (по желанию); профиль по умолчанию `classic` — 64 дня с 10.02.2027 (срок повторного использования авторизации — 10 дней) и 45 дней с 16.02.2028 (авторизация — 7 часов). Даты относятся к вновь выпускаемым сертификатам. Let's Encrypt рекомендует клиент с ARI либо продление примерно на двух третях срока; фиксированный интервал «раз в 60 дней» больше не годится. С certbot 1.21/2.9 и правилом «за 30 дней» запас при 45-дневных сертификатах станет небольшим (15 дней на исправление сбоя) — к 2028 году обновите certbot (snap) или следите за продлением. Настройте оповещение о сроке сертификата (команда проверки срока — в шпаргалке).
- Выбор профиля (`--preferred-profile`, `--required-profile`) появился в certbot 4.0.0 — то есть есть в пакете Ubuntu 26.04, но не в 22.04/24.04; сертификаты на IP-адрес (`--ip-address`) — в certbot 5.3.0 (03.02.2026), в репозиториях Ubuntu LTS этого ключа нет, нужен snap [журнал изменений certbot; проверено 2026-10-10].

Без публичного имени (изолированная сеть, ВМ) Let's Encrypt по HTTP-01 недоступен — используйте собственный ЦС (8.3) или проверку DNS-01 для публичного домена.

## 9. nginx как обратный прокси

### 9.1. Когда нужен и что о нём говорит 1С

nginx не может загрузить модуль расширения 1С, поэтому сам базу не публикует. Его ставят **перед** Apache или `ibsrv`, чтобы:

- завершать TLS (для `ibsrv` это единственный способ получить HTTPS — встроенный веб-сервер HTTPS не поддерживает [офиц.]);
- публиковать наружу несколько внутренних веб-серверов под одним именем и сертификатом;
- балансировать нагрузку между несколькими Apache;
- ограничивать доступ, размер тела запроса и частоту запросов.

Официальное требование одно: прокси должен передавать заголовки `X-Forwarded-Port`, `X-Forwarded-Host` и `X-Forwarded-Proto`, чтобы платформа могла восстановить внешний адрес запроса (он используется, например, при перенаправлениях OpenID и в навигационных ссылках) — формулировка руководства 8.3 ранней редакции, для 8.3.27/8.5 не перечитана (см. раздел 2).

Эталон от самой фирмы «1С» — конфигурация nginx в репозитории `1C-Company/docker_fresh` [перечитано 2026-10-10 по файлам `conf/nginx/*.conf`]:

| Файл эталона | Содержимое |
|---|---|
| `1c_common.conf` | `proxy_connect_timeout 5s;` `proxy_read_timeout 75;` `proxy_next_upstream error;` `proxy_set_header Host $host;` `proxy_set_header X-Real-IP $remote_addr;` `proxy_set_header X-For-Forwarded $proxy_add_x_forwarded_for;` (именно так — по-видимому, опечатка вместо `X-Forwarded-For`) `proxy_set_header X-Forwarded-Proto https;` |
| `1c_app.conf` | `include 1c_common.conf;` `proxy_set_header X-Forwarded-Port 443;` |
| `1c_keepalive.conf` | `proxy_http_version 1.1;` `proxy_set_header Connection "";` |
| `1c_upstream.conf` | `upstream backend83 { ip_hash; keepalive 16; server <web>:80; }` |
| `nginx.conf` | `gzip on;` `proxy_buffering on;` `proxy_buffer_size 32k;` `proxy_buffers 20 512k;` `proxy_connect_timeout 5;` `proxy_max_temp_file_size 0;` `keepalive_timeout 300 300;` `client_max_body_size 4096m;` `client_body_buffer_size 256k;` `worker_processes 2;` `worker_connections 1024;` |

Что из этого следует: эталон **не задаёт `X-Forwarded-Host`** (достаточно `Host $host`) и не передаёт заголовки `Upgrade`/`Connection: upgrade` — то есть WebSocket через публикацию в эталонной схеме не проксируется. Обязательный минимум по эталону — `Host`, `X-Forwarded-Proto` и `X-Forwarded-Port`; `X-Forwarded-Host` в конфигурации ниже добавлен по тексту руководства и безвреден.

Версии nginx [проверено 2026-10-10, packages.ubuntu.com и nginx.org]: Ubuntu 22.04 — 1.18.0, Ubuntu 24.04 — 1.24.0, Ubuntu 26.04 — 1.28.3; репозиторий nginx.org — ветка 1.29 (в ней с 1.29.6 директива `sticky` доступна в открытой версии, а с 1.29.7 по умолчанию `proxy_http_version 1.1` и включён `keepalive 32 local` к бэкендам). Во всех трёх LTS-выпусках Ubuntu версия nginx ниже 1.29.6, поэтому там `proxy_http_version` по умолчанию `1.0`, `keepalive` к бэкендам выключен, а `sticky` отсутствует — конфигурация ниже задаёт всё явно и работает на любой версии.

### 9.2. Apache за nginx на одном хосте

Apache переводится на локальный порт, наружу смотрит nginx.

```bash
sudo apt install -y nginx

# Apache слушает только 127.0.0.1:8080
sudo sed -i 's/^Listen 80$/Listen 127.0.0.1:8080/' /etc/apache2/ports.conf
sudo sed -i 's/<VirtualHost \*:80>/<VirtualHost 127.0.0.1:8080>/' /etc/apache2/sites-available/000-default.conf
sudo a2dissite default-ssl 1c-ssl 1c-http 2>/dev/null; sudo a2dismod ssl 2>/dev/null   # HTTPS и перенаправление теперь делает nginx
sudo apachectl configtest && sudo systemctl restart apache2
sudo ss -tlnp | grep apache2            # 127.0.0.1:8080

# реальный адрес клиента в журналах Apache
sudo a2enmod remoteip
printf 'RemoteIPHeader X-Forwarded-For\nRemoteIPInternalProxy 127.0.0.1\n' | \
     sudo tee /etc/apache2/conf-available/remoteip.conf
sudo a2enconf remoteip && sudo systemctl restart apache2
```

Файл `/etc/nginx/conf.d/1c.conf`:

```nginx
# Connection: "upgrade" только для WebSocket, иначе пусто (нужно для keepalive к бэкенду)
map $http_upgrade $connection_upgrade {
    default upgrade;
    ''      '';
}

upstream onec_backend {
    ip_hash;                          # привязка клиента к веб-серверу (как в эталоне 1С)
    server 127.0.0.1:8080;            # Apache + wsap24.so
    # server 192.168.1.52:80 max_fails=3 fail_timeout=30s;   # второй веб-сервер
    keepalive 16;
}

server {
    listen 80;
    server_name 1c.example.com;

    location /.well-known/acme-challenge/ { root /var/www/letsencrypt; }
    location / { return 301 https://$host$request_uri; }
}

server {
    listen 443 ssl;
    server_name 1c.example.com;

    ssl_certificate     /etc/letsencrypt/live/1c.example.com/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/1c.example.com/privkey.pem;
    ssl_protocols       TLSv1.2 TLSv1.3;
    ssl_session_cache   shared:SSL:10m;
    ssl_session_timeout 1d;
    add_header Strict-Transport-Security "max-age=31536000" always;

    # загрузка файлов и обмены: значение по умолчанию 1m слишком мало
    client_max_body_size    1024m;
    client_body_buffer_size 256k;

    location / {
        proxy_pass         http://onec_backend;
        proxy_http_version 1.1;

        proxy_set_header Host              $host;
        proxy_set_header X-Real-IP         $remote_addr;
        proxy_set_header X-Forwarded-For   $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_set_header X-Forwarded-Host  $host;
        proxy_set_header X-Forwarded-Port  $server_port;
        proxy_set_header Upgrade           $http_upgrade;
        proxy_set_header Connection        $connection_upgrade;

        proxy_connect_timeout 5s;
        proxy_send_timeout    600s;
        proxy_read_timeout    600s;       # длительные вызовы: отчёты, обмены, HTTP-сервисы

        proxy_buffering          on;
        proxy_buffer_size        32k;
        proxy_buffers            20 512k;
        proxy_max_temp_file_size 0;       # не писать ответы во временные файлы

        proxy_next_upstream error;        # не повторять запрос на другом сервере по таймауту
        proxy_redirect http://$host/ $scheme://$host/;   # Apache не знает про HTTPS и отдаёт Location с http://
    }
}
```

```bash
sudo nginx -t && sudo systemctl reload nginx
curl -I https://1c.example.com/demo/
```

Что означает каждая группа директив:

| Директива | Значение по умолчанию | Зачем менять для 1С |
|---|---|---|
| `proxy_set_header Host $host` | `$proxy_host` (имя из `proxy_pass`) | 1С и Apache должны видеть внешнее имя сайта |
| `X-Forwarded-Proto/Host/Port` | не передаются | официально требуются 1С для восстановления внешнего адреса |
| `client_max_body_size` | `1m` | иначе загрузка файлов больше 1 МБ и крупные пакеты обмена дают 413 |
| `proxy_read_timeout`, `proxy_send_timeout` | `60s` | таймаут между двумя операциями чтения/записи; долгий серверный вызов без промежуточных данных обрывается с 504 |
| `proxy_connect_timeout` | `60s` (обычно не может превышать 75 с) | короткое значение быстрее выявляет недоступный бэкенд; в эталоне 1С — `5s` |
| `proxy_http_version` | `1.0` до nginx 1.29.7, затем `1.1` | 1.1 нужен для keepalive к бэкенду и для WebSocket |
| `proxy_buffering` | `on` | буферизация ответа; при `on` медленный клиент не держит поток Apache |
| `proxy_buffer_size`, `proxy_buffers` | `4k\|8k`, `8 4k\|8k` | заголовки и ответы 1С бывают крупными; значения взяты из эталона 1С |
| `proxy_max_temp_file_size` | `1024m` | `0` отключает временные файлы на диске |
| `proxy_request_buffering` | `on` | nginx сначала принимает тело запроса целиком; `off` — потоковая передача больших загрузок |
| `proxy_next_upstream` | `error timeout` | с `timeout` nginx может повторить уже выполняющийся запрос на другом сервере; неидемпотентные запросы (`POST`, `LOCK`, `PATCH`), уже отправленные бэкенду, по умолчанию не повторяются (с nginx 1.9.13), но `GET` повторится. В эталоне 1С — `error` |
| `Upgrade` / `Connection` | `Connection: close` | прозрачное проксирование WebSocket |

Замечания:

- `proxy_set_header` наследуется с верхнего уровня, только если на текущем уровне нет ни одной такой директивы. Если добавляете заголовок в `location`, перечислите там все.
- **Таймауты.** В эталоне 1С `proxy_read_timeout 75` и `Timeout 60` у Apache [проверено 2026-10-10] — фирма «1С» считает это достаточным для своего облачного сервиса. Для веб- и HTTP-сервисов с долгой обработкой и для обменов таймаут увеличивают (300–3600 с) — это практика сообщества. ⚠ не подтверждено: держится ли HTTP-запрос тонкого и веб-клиента открытым всё время длительного серверного вызова — в документации не найдено; косвенно на «нет» указывает то, что эталон 1С обходится 75 секундами, а на «да» — жалобы пользователей на 504 при формировании тяжёлых отчётов через nginx с таймаутом 60 с. Безопасная стратегия: поставить 600 с (как в конфигурации выше) и смотреть в `error.log` nginx строки `upstream timed out`.
- **WebSocket.** Заголовки `Upgrade`/`Connection` в конфигурации безвредны; эталон 1С их не передаёт. ⚠ не подтверждено: использует ли платформа входящие WebSocket-соединения через публикацию (сервис оповещения клиента с 8.3.26, см. `--clnt-notif-data`) — V8Update описывает сервис, но не транспорт, а разделы документации закрыты подпиской. Проверить на своём сервере просто: `sudo grep -c ' 101 ' /var/log/nginx/access.log` (код 101 Switching Protocols появляется только при успешном переходе на WebSocket). В 8.3.27 появился WebSocket-**клиент** — это исходящие соединения из 1С, прокси публикации они не касаются.
- `listen 443 ssl http2;` (nginx до 1.25) или `http2 on;` (1.25.1+) включают HTTP/2 для клиентов; для 1С это необязательно.
- Сертификат для nginx: `sudo apt install python3-certbot-nginx && sudo certbot --nginx -d 1c.example.com` либо `certbot certonly --webroot -w /var/www/letsencrypt -d 1c.example.com` и перезагрузка nginx в deploy-hook.

### 9.3. Публикация отдельных баз и ограничение доступа

```nginx
    # наружу — только одна база и только её HTTP-сервисы
    location /demo/hs/ {
        allow 203.0.113.10;               # адрес партнёра
        deny  all;
        proxy_pass http://onec_backend;
        include /etc/nginx/snippets/1c-proxy.conf;   # общий набор proxy_set_header и таймаутов
    }

    # интерактивный доступ — только из офисной сети и VPN
    location /demo/ {
        allow 192.168.1.0/24;
        allow 10.8.0.0/24;
        deny  all;
        proxy_pass http://onec_backend;
        include /etc/nginx/snippets/1c-proxy.conf;
    }

    location / { return 404; }
```

Правила:

- В `proxy_pass` не указывайте путь (`http://onec_backend`, без `/` в конце) — тогда адрес передаётся бэкенду без изменений. Имя публикации снаружи и внутри должно совпадать, включая регистр.
- `/etc/nginx/snippets/1c-proxy.conf` — ваш собственный файл: вынесите в него из раздела 9.2 строки `proxy_http_version`, все `proxy_set_header`, таймауты, буферы и `proxy_redirect`, чтобы не повторять их в каждом `location`.
- Из двух подходящих префиксных `location` nginx выбирает самый длинный, поэтому `/demo/hs/` имеет приоритет над `/demo/`.
- Basic-аутентификация на nginx: `sudo apt install apache2-utils`, `sudo htpasswd -c /etc/nginx/.htpasswd ivanov`, в `location` — `auth_basic "1C";` и `auth_basic_user_file /etc/nginx/.htpasswd;`. Особенности сочетания с аутентификацией 1С — в разделе 11.4.

### 9.4. Балансировка на несколько веб-серверов

```nginx
upstream onec_backend {
    ip_hash;
    server web1.example.local:80 max_fails=3 fail_timeout=30s;
    server web2.example.local:80 max_fails=3 fail_timeout=30s;
    keepalive 32;
}
```

Условия:

- на всех веб-серверах одна и та же сборка платформы (совпадающая с кластером) и одинаковые публикации: то же имя и тот же `default.vrd`;
- каждый веб-сервер видит кластер по 1541 и 1560–1591.

Нужна ли привязка сеанса (sticky):

- Данные сеанса хранятся в кластере (сервис сеансовых данных), а не на веб-сервере [офиц.]. Модуль расширения при вызове существующего сеанса сначала ищет в своём пуле соединение с тем рабочим процессом, который обслуживал предыдущий вызов [офиц., 2.2.7.4]. В 8.5.4 последовательные запросы одного сеанса направляются в один рабочий процесс независимо от числа рабочих процессов и расширений веб-сервера [офиц., V8Update].
- Алгоритм выбора рабочего процесса [офиц., 2.2.7.4; проверено 2026-10-10]: для **нового** сеанса берётся любое свободное соединение из пула модуля расширения, а если его нет — создаётся новое с учётом параметра кластера «Режим распределения нагрузки»; для **существующего** сеанса сначала ищется соединение в пуле с тем рабочим процессом, который обслуживал предыдущий вызов, и только при неудаче процесс выбирается заново (с приоритетом прежнего). Пул — свой у каждого процесса Apache на каждом веб-сервере, поэтому без привязки клиент, попадая на другой веб-сервер, чаще получает соединение с «чужим» рабочим процессом и теряет прогретые кеши.
- ⚠ не подтверждено: прямого требования привязки (sticky) в прочитанной документации нет — это вывод из алгоритма выше и из эталона 1С (`docker_fresh`), который использует **`ip_hash`** в обеих группах серверов (`backend83` и `gate`). Работоспособность без привязки документация не запрещает (сеансовые данные лежат в кластере). Практический вывод: **привязку включать** — она ничего не стоит и повторяет эталон.
- `ip_hash` использует первые три октета IPv4-адреса клиента (вся сеть /24 попадает на один сервер) и поэтому плохо распределяет пользователей, приходящих с одного адреса или из одной подсети (офис за NAT). Альтернативы: `sticky cookie srv_id expires=1h path=/;` (открытый nginx с 1.29.6, раньше — только коммерческая версия; в пакетах nginx из Ubuntu 22.04/24.04/26.04 директивы нет — нужен репозиторий nginx.org) или `hash $remote_addr$http_user_agent consistent;` (есть в любой версии). Тонкий клиент 1С cookie от прокси сохраняет не обязательно ⚠ не подтверждено — при `sticky cookie` проверьте распределение именно тонких клиентов.
- Параметр `backup` нельзя сочетать с `ip_hash` и `hash`. Чтобы временно вывести сервер, сохранив распределение, используйте `down`.

## 10. Автономный сервер ibsrv

### 10.1. Что это и когда применим

`ibsrv` — отдельное серверное приложение для обслуживания **одной** информационной базы управляемого приложения; встроенный веб-сервер публикует базу без Apache. База может быть файловой (`1Cv8.1CD`) или в СУБД. Администрируется утилитой `ibcmd`, ставится вместе с компонентом `server`. Из статуса бета-версии вышел в 8.3.23 [офиц.].

Ограничения (руководство администратора 8.3.27, 7.2) — **не поддерживаются**:

- несколько баз в одном экземпляре и несколько экземпляров на одну базу;
- обычное (неуправляемое) приложение;
- работа с базой, которую в это время обслуживает кластер серверов (возможна порча базы);
- внешнее (COM) соединение и объект `V83.ComConnector`;
- Microsoft SQL Server, если `ibsrv` запущен на Linux;
- управление через `ras`/`rac` и графические средства администрирования;
- фоновая реструктуризация;
- **HTTPS** — нужен обратный прокси;
- **аутентификация операционной системы**;
- 1С:Аналитика, сервисы интеграции, боты системы взаимодействия;
- загрузка конфигурации из XML-файлов линейного формата.

Когда применим: одна небольшая база без кластера, стенды разработки и тестирования, CI/CD, контейнеры, быстрый веб-доступ к файловой базе без Apache. Когда не подходит: нужны кластер и его отказоустойчивость, аутентификация ОС (Kerberos), 1С:Аналитика, сервисы интеграции, несколько баз на общих лицензиях с единым администрированием.

Лицензии [проверено 2026-10-10]: на v8.1c.ru официально сказано, что автономный сервер «позволяет запускать до трёх клиентских сеансов с информационной базой без лицензии на сервер» и работает с файловой базой. Подробности — по практической статье sysadminium.ru (8.3.25): серверная лицензия проверяется при подключении клиента или `ibcmd` к базе **в СУБД** (то есть для PostgreSQL нужна всегда); для файловой базы она нужна, только когда клиентских сеансов больше трёх (фоновые задания не считаются); клиентские лицензии нужны тонкому клиенту и конфигуратору, утилите `ibcmd` — нет. Глава 7 руководства администратора лицензирование не описывает (в примерах есть только ключ `distribute-licenses: yes`) — подтверждено полным текстом документации 8.3.27 (глава 10, сверено 10.10.2026): чтобы автономный сервер выдавал лицензии клиентам, должен быть включён параметр `infobase.distribute-licenses`, а файл лицензии — доступен пользователю, от имени которого запущен сервер; ранее было не подтверждено официальным текстом руководства, сверяйте с лицензионным соглашением.

### 10.3. Конфигурационный файл

Создаётся командой `ibcmd server config init` (вывод идёт в стандартный поток) либо импортом параметров базы из каталога кластера: `ibcmd server config import` (с `--publication` — вместе с настройками публикации из `default.vrd`).

Полный перечень ключей — в `../its-docs/adm-pr03-sluzhebnye-fajly-p6.md`. Ранее было не подтверждено: имена этих секций и ключей записаны автором по памяти, приложение закрыто подпиской ИТС и при рецензии не прочитано. Не вписывайте их в рабочий файл «по аналогии»: задайте нужное ключами командной строки (`--disable-direct-gate`, `--direct-regport` и т. д.) либо получите точные имена из вывода `ibcmd server config init <нужные ключи>` и из справки `ibcmd help server config init`.

### 10.4. Создание базы и запуск

```bash
# создать базу в PostgreSQL (служба должна быть остановлена, каталог данных свободен)
sudo -u usr1cv8 $B/ibcmd infobase create --config=/etc/1c/ibsrv-demo.yml \

sudo -u usr1cv8 $B/ibsrv --data=/var/lib/1c/ibsrv-buh --database-path=/var/lib/1c/ibsrv-buh/db \
     --name=buh --http-base=/buh --http-port=8080 --http-address=any

# демон (официальная форма)

[Service]

Подключение клиентов [офиц., 7.3.4]:

- по HTTP: `http://хост:8314/<базовый путь>`; тонкий клиент — `1cv8c ENTERPRISE /WS"http://localhost:8314/demo"`;
- по TCP/IP (тонкий и толстый клиент, конфигуратор): `/S хост\имя_базы`, где имя совпадает с `--name` (`infobase.name`).

Рекомендуемая схема для доступа извне: `ibsrv` слушает `127.0.0.1:8314`, перед ним nginx с HTTPS (раздел 9.5); прямой и SSH-шлюзы, если не нужны, отключаются ключами `--disable-direct-gate`, `--disable-ssh-gate`.

## 11. Аутентификация и ограничение доступа

### 11.1. Три уровня (официально, раздел 8.9.1)

1. **Прокси-сервер** — если между клиентом и веб-сервером есть прокси с собственной аутентификацией.
2. **Веб-сервер**:
   - *анонимный доступ* — запрос выполняется от имени служебного пользователя веб-сервера; 1С сама запрашивает аутентификацию (для сервисов — Basic из HTTP-запроса);
   - *Basic* — клиент передаёт имя и пароль веб-серверу; эти же учётные данные модуль расширения передаёт в 1С, поэтому пользователь должен существовать и на веб-сервере, и в базе;
   - *аутентификация ОС* — веб-сервер определяет пользователя ОС; если в HTTP-запросе есть имя и пароль, используются они. Для тонкого и веб-клиента это зависит от имперсонации (браузер, веб-сервер, политики домена) и «возможно не всегда». Раздел 8.9.1 настройку не описывает, но она есть в другом месте руководства: 2.8.1.3 «Аутентификация операционной системы при использовании веб-сервера Apache» (см. 11.3) [проверено 2026-10-10].
3. **«1С:Предприятие»** — модуль расширения использует учётные данные, полученные от веб-сервера (Basic или ОС); при анонимном доступе запрашивает Basic. Учётные данные ожидаются в UTF-8.

### 11.2. Пользователи 1С (вариант по умолчанию)

Ничего настраивать на веб-сервере не нужно: веб-клиент и тонкий клиент показывают окно входа 1С, сервисы принимают HTTP Basic.

```bash
# сервисы: имя и пароль пользователя 1С
curl -u 'Обмен:пароль' 'https://1c.example.com/demo/hs/dt/ping'
# тонкий клиент
1cv8c ENTERPRISE /WS"https://1c.example.com/demo" /N"Иванов" /P"пароль"
```

Правила безопасности:

- Basic передаёт пароль фактически открытым текстом — только поверх HTTPS.
- Для интеграций заведите отдельного пользователя 1С с минимальными правами и опубликуйте сервисы отдельной публикацией с `enable="false"`.
- В 8.5.4 появились защита от подбора пароля, период действия учётной записи и флажок «Аутентификация разрешена» — используйте их для учётных записей, доступных из Интернета.

### 11.3. Аутентификация ОС через Apache (Kerberos)

Что подтверждено официально:

- На Linux платформа использует GSS-API; поддерживаются Kerberos и аутентификация по имени и паролю (NTLM — только в Windows-версии сервера). Нужны библиотеки `libkrb5` и `libgssapi_krb5` версии не ниже 1.4.2.
- Пользователь ОС в свойствах пользователя базы задаётся в виде `\\имя_домена\имя_пользователя` (имя — латиницей). Точное написание видно в технологическом журнале: событие `CONN`, свойство `Txt` со строкой `Srvr: DstUserName2`.
- Ключи клиента: `/WA+` (аутентификация ОС, по умолчанию) и `/WA-` (только аутентификация 1С).
- Kerberos обязателен, когда веб-сервер и кластер находятся на разных компьютерах; для учётной записи веб-сервера (или его SPN) на контроллере домена включается **делегирование** — полное или ограниченное.
- Кластеру 1С на Linux нужен собственный keytab: `usr1cv8.keytab` с принципалом `usr1cv8/srv1c.example.local@EXAMPLE.LOCAL` в каталоге версии (`/opt/1cv8/x86_64/<версия>/usr1cv8.keytab`, владелец `usr1cv8:grp1cv8`, права `600`); другой путь задаётся переменной `SRV1CV8_KEYTAB` (после изменения — перезапуск сервера). Часть принципала с именем компьютера — полное имя строчными буквами. Проверки: `klist -e -k -t <keytab>` и `kinit -k -t <keytab> usr1cv8/srv1c.example.local@EXAMPLE.LOCAL` (должна завершиться без вопросов; затем `klist` покажет билет, `kdestroy` очистит кеш). Официальная команда на контроллере домена: `ktpass -princ usr1cv8/srv1c.krb.local@KRB.LOCAL -mapuser usr1cv8 -pass <пароль> -out usr1cv8.keytab` [офиц., «Клиент-серверный вариант», 3.1.6.4–3.1.6.7; проверено 2026-10-10]. Поскольку keytab лежит в каталоге версии, при обновлении платформы его нужно перенести в новый каталог либо один раз задать постоянный путь через `SRV1CV8_KEYTAB`.
- Ключ `-osauth` утилиты `webinst` действует только для IIS; автономный сервер аутентификацию ОС не поддерживает; через Apache на Windows она не работает.

**Официальный рецепт 1С для Apache** — раздел 2.8.1.3 «Operating system authentication when using Apache web server» руководства администратора 8.3.27 [найден и прочитан при рецензии 2026-10-10; автор статьи этот раздел пропустил и ошибочно считал, что настройка официально не описана]. Он построен на модуле **`mod_auth_kerb`**:

```apache
# httpd.conf / apache2.conf — если модуль собран и установлен отдельно:
LoadModule auth_kerb_module /path_to_the_file/mod_auth_kerb.so

# блок виртуального каталога публикации (в оригинале — синтаксис Apache 2.2)
<Directory "/home/usr1cv8/www/MyApp">
    AllowOverride None
    Options None
    Order allow,deny
    Allow from all
    SetHandler 1c-application
    ManagedApplicationDescriptor /home/usr1cv8/www/MyApp/default.vrd

    AuthName "1C:Enterprise web client"
    AuthType Kerberos
    Krb5Keytab /home/usr1cv8/HTTP.keytab
    KrbVerifyKDC off
    KrbDelegateBasic off
    KrbServiceName HTTP/Server.domain@DOMAIN
    KrbSaveCredentials on
    KrbMethodK5Passwd off
    KrbMethodNegotiate on
    Require valid-user
</Directory>
```

Что сказано в этом разделе официально:

- ключ (keytab) создаётся для учётной записи, связанной с принципалом `HTTP/Server.domain@DOMAIN`; файл `HTTP.keytab` должен быть доступен пользователю, от имени которого работает Apache (в Ubuntu — `www-data`);
- для этой учётной записи в домене включается флажок **«Учётная запись доверена для делегирования»**;
- модуль `mod_auth_kerb` «входит в большинство дистрибутивов»: пакет `mod_auth_kerb` в Fedora, `libapache2-mod-auth-kerb` в Debian; после установки из пакета достаточно перезапустить веб-сервер, строка `LoadModule` нужна только при самостоятельной сборке;
- предупреждение: в домене со смешанными контроллерами Windows 2000 и 2003, веб-серверами на Linux и серверами 1С на Windows Kerberos «может не работать»;
- этот же пример — единственное место руководства, где официально показан **вид блока публикации**: `AllowOverride None`, `Options None`, разрешение доступа, `SetHandler 1c-application`, `ManagedApplicationDescriptor <путь>` (для Apache 2.4 вместо `Order allow,deny` / `Allow from all` пишется `Require all granted`; при аутентификации — только `Require valid-user`).

Применимость в Ubuntu [проверено 2026-10-10 по packages.ubuntu.com]:

| Выпуск | `libapache2-mod-auth-kerb` | Что делать |
|---|---|---|
| Ubuntu 22.04 | есть, версия `5.4-2.5` (universe) | официальный рецепт применим как есть: `sudo apt install libapache2-mod-auth-kerb krb5-user && sudo a2enmod auth_kerb`, заменив `Order`/`Allow` на синтаксис 2.4 |
| Ubuntu 24.04, 26.04 | пакета нет (для обоих выпусков packages.ubuntu.com отвечает «Package not available in this suite») | модуль-преемник `libapache2-mod-auth-gssapi` (`1.6.4-3build2` в 24.04, `1.6.4-3build3` в 26.04; universe) — рецепт ниже |

Вариант для Ubuntu 24.04+ на `mod_auth_gssapi` — **практика сообщества**: это перевод официального рецепта на директивы другого модуля. ⚠ не подтверждено: на стенде не проверялся ни автором, ни рецензентом; 1С официально описывает только `mod_auth_kerb`. Соответствие директив: `AuthType Kerberos` → `AuthType GSSAPI`; `Krb5Keytab` → `GssapiCredStore keytab:`; `KrbSaveCredentials on` → `GssapiDelegCcacheDir`; `KrbMethodNegotiate on` + `KrbMethodK5Passwd off` → поведение по умолчанию (`GssapiBasicAuth Off`); `KrbServiceName` → принципал берётся из keytab; `KrbVerifyKDC off` — аналога нет. Существование директив `GssapiCredStore`, `GssapiAllowedMech`, `GssapiDelegCcacheDir` и значения `AuthType GSSAPI` проверено по README модуля.

```bash
sudo apt install -y libapache2-mod-auth-gssapi krb5-user
sudo a2enmod auth_gssapi

# keytab для принципала HTTP/<полное имя веб-сервера>@<ОБЛАСТЬ> создаётся на контроллере домена, например:
#   ktpass -princ HTTP/web1c.example.local@EXAMPLE.LOCAL -mapuser svc-http-1c -pass * ^
#          -ptype KRB5_NT_PRINCIPAL -crypto AES256-SHA1 -out http.keytab
sudo install -o www-data -g www-data -m 600 http.keytab /etc/apache2/http.keytab
sudo -u www-data klist -e -k -t /etc/apache2/http.keytab
sudo install -d -o www-data -g www-data -m 700 /run/apache2/krb5cc
```

```apache
# /etc/apache2/conf-available/1c-kerberos.conf
<Location "/demo">
    AuthType GSSAPI
    AuthName "1C:Enterprise"
    GssapiCredStore keytab:/etc/apache2/http.keytab
    GssapiAllowedMech krb5
    # делегированные учётные данные пользователя: имя кеша передаётся в переменной KRB5CCNAME
    GssapiDelegCcacheDir /run/apache2/krb5cc
    Require valid-user
</Location>
```

Что ещё нужно: `/etc/krb5.conf` с областью домена, синхронное время, прямое и обратное разрешение имён, адрес публикации в зоне «Местная интрасеть» браузера (иначе браузер не отправит билет). Каталог `/run/apache2/krb5cc` пропадает после перезагрузки — создавайте его через `systemd-tmpfiles`. Официальный рецепт для `mod_auth_kerb` (см. выше) использует `AuthType Kerberos`, `Krb5Keytab`, `KrbServiceName`, `KrbMethodNegotiate on`, `KrbMethodK5Passwd off`, `KrbSaveCredentials on`, `KrbVerifyKDC off`, `KrbDelegateBasic off` — аналог `KrbSaveCredentials` в `mod_auth_gssapi` это `GssapiDelegCcacheDir`. То, что официальный пример включает `KrbSaveCredentials on` и требует доверия для делегирования, означает: модулю 1С действительно нужны **делегированные** учётные данные пользователя (чтобы предъявить их кластеру), одного имени в `REMOTE_USER` недостаточно.

Справка по директивам `mod_auth_gssapi` [README модуля; проверено 2026-10-10]:

| Директива | Значение |
|---|---|
| `AuthType GSSAPI` | включает модуль для секции |
| `GssapiCredStore keytab:/путь` | keytab службы (`HTTP/…`); другие формы — `client_keytab:/путь`, `ccache:FILE:/путь` |
| `GssapiAllowedMech krb5` | разрешённые механизмы: `krb5`, `iakerb`, `ntlmssp`; по умолчанию — все доступные |
| `GssapiDelegCcacheDir /каталог` | каталог для делегированных учётных данных клиента; файл кеша называется по имени принципала |
| `GssapiDelegCcacheEnvVar ИМЯ` | переменная окружения запроса, в которую кладётся имя кеша; по умолчанию `KRB5CCNAME` |
| `GssapiDelegCcacheUnique On` | уникальное имя кеша на каждый запрос (суффикс из шести символов); файлы нужно удалять самому. По умолчанию `Off` |
| `GssapiDelegCcachePerms mode:0660 gid:группа` | права и владелец файла кеша |
| `GssapiUseS4U2Proxy On` | ограниченное делегирование (s4u2proxy); требует `GssapiDelegCcacheDir` и `client_keytab:` в `GssapiCredStore` |
| `GssapiSSLonly On` | аутентификация только по TLS; по умолчанию `Off`, в промышленной эксплуатации рекомендуется `On` |
| `GssapiBasicAuth On` | дополнительно принимать Basic (имя и пароль проверяются через Kerberos); по умолчанию `Off` |
| `GssapiNegotiateOnce On` | не предлагать Negotiate повторно после неудачи; по умолчанию `Off` |
| `GssapiLocalName On` | в `REMOTE_USER` попадает локальное имя (`auth_to_local` из `krb5.conf`), полный принципал — в `GSS_NAME`; по умолчанию `Off` |
| `GssapiUseSessions On` | не проходить Negotiate на каждом запросе, а держать сеанс в cookie (нужен `mod_session`); по умолчанию `Off` |

⚠ не подтверждено: подхватывает ли `wsap24.so` делегированный кеш, который `mod_auth_gssapi` передаёт в переменной **запроса** `KRB5CCNAME`, так же, как кеш от `mod_auth_kerb` с `KrbSaveCredentials on` (оба модуля выставляют переменную `KRB5CCNAME` для запроса, поэтому замена выглядит равноценной, но 1С её не описывает), и в каком виде имя пользователя (`REMOTE_USER` = `user@REALM`) сопоставляется с пользователем базы `\\DOMAIN\user`. Без стенда с контроллером домена считать вариант с `mod_auth_gssapi` рабочим нельзя. Если аутентификация ОС через Apache на Linux критична, варианты по убыванию надёжности: (1) Ubuntu 22.04 с пакетным `mod_auth_kerb` — в точности официальный рецепт; (2) собрать `mod_auth_kerb` из исходных текстов на 24.04 (официальный текст такую установку допускает — тогда и нужна строка `LoadModule auth_kerb_module`), но модуль давно не развивается; (3) `mod_auth_gssapi` с проверкой на стенде; (4) OpenID Connect с корпоративным провайдером (Keycloak + Kerberos/SPNEGO на стороне провайдера) — путь официально описан и не зависит от веб-сервера.

На Ubuntu 26.04 учитывайте ограничения юнита (раздел 6.1): keytab и каталог кешей не должны лежать в `/root` и `/home`; `/etc/apache2/http.keytab` читать можно (каталог `/etc` только для чтения — этого достаточно), `/run/apache2/krb5cc` доступен на запись.

### 11.4. Ограничение доступа средствами Apache

Правила кладите в **отдельный файл** (`/etc/apache2/conf-available/1c-access.conf`, затем `sudo a2enconf 1c-access`), а не в блок, созданный `webinst`: при перепубликации утилита этот блок перезапишет. Секция `<Location>` обрабатывается после `<Directory>`, и её директивы авторизации заменяют `Require all granted` из блока публикации. Несколько секций `<Location>` применяются в порядке записи: более частную (`/demo/hs`) пишите ниже общей (`/demo`) — её правила заменят общие.

```apache
# только свои сети
<Location "/demo">
    Require ip 192.168.1.0/24 10.8.0.0/24
</Location>

# сервисы обмена — только с адреса партнёра
<Location "/demo/hs">
    Require ip 203.0.113.10
</Location>

# дополнительный пароль веб-сервера поверх аутентификации 1С
<Location "/buh">
    AuthType Basic
    AuthName "1C"
    AuthUserFile /etc/apache2/.htpasswd-1c
    Require valid-user
</Location>
```

```bash
sudo apt install -y apache2-utils
sudo htpasswd -c -B /etc/apache2/.htpasswd-1c ivanov     # -c — создать файл (затрёт существующий!)
sudo htpasswd -B /etc/apache2/.htpasswd-1c petrov        # добавить пользователя
sudo chown root:www-data /etc/apache2/.htpasswd-1c && sudo chmod 640 /etc/apache2/.htpasswd-1c
sudo apachectl configtest && sudo systemctl reload apache2
```

Особенности Basic-аутентификации веб-сервера:

- Браузер сначала спросит пароль веб-сервера, затем появится окно входа 1С (практика, interface31.ru).
- Тонкий клиент спрашивает пароль веб-сервера при каждом запуске; чтобы не спрашивал — параметры запуска `/WSN <имя> /WSP <пароль>` в свойствах базы.
- Веб- и HTTP-сервисы, OData, мобильный клиент передают один заголовок `Authorization`. Он достанется и веб-серверу, и 1С, поэтому для сервисов имя и пароль в файле `htpasswd` должны **совпадать** с именем и паролем пользователя 1С — либо сервисы исключают из Basic и ограничивают по IP.
- Тот же приём возможен через `.htaccess` в каталоге публикации (в блоке `webinst` стоит `AllowOverride All`), но отдельный файл надёжнее и не требует прав записи в каталог публикации.

### 11.5. OpenID, OpenID Connect, токены доступа

| Способ | Где настраивается | Ключевые условия |
|---|---|---|
| OpenID 2.0 | `<openid><rely url="…/e1cib/oid2op"/>` в публикации базы; `<openid><provider>` в публикации базы-провайдера | Только HTTPS; имя пользователя базы совпадает с идентификатором у провайдера; не действует для веб-сервисов |
| OpenID Connect | `<openidconnect>` с описанием провайдеров | Тонкий, мобильный и веб-клиент; платформа — только клиент; поддержана ЕСИА; сопоставление по e-mail, имени, пользователю ОС или `UserMatchingKeys` |
| Токены доступа (JWT) | `<accessTokenAuthentication>` в `default.vrd` + свойство пользователя «Аутентификация токеном доступа» | Только для опубликованных баз; токен создаётся объектом `ТокенДоступа` и передаётся клиенту параметром запуска |

Служебные адреса OpenID-провайдера на базе 1С [офиц., 8.8.3]: `…/e1cib/oid2op` (описание провайдера, XRDS), `…/e1cib/oid2op?cmd=auth` (аутентификация: параметры `openid.auth.user`, `openid.auth.pwd`, необязательные `openid.return_to`, `openid.auth.check`, `openid.auth.short`; ответ 200 — успех, 400 — отказ, 402 — нужен второй фактор), `?cmd=lookup`, `?cmd=check`, `?cmd=logout`; у базы-клиента — `…/e1cib/oid2rp`. Внешний провайдер для тонкого клиента должен устанавливать cookie `vrs_oid2op_auth`. Дополнительно [офиц., 8.8.3; проверено 2026-10-10]: данные второго фактора передаются параметром `openid.auth.Data2FA`, проверка необходимости второго фактора — адрес `…/e1cib/oid2op/2FACheck`, состояние возвращается в заголовке `Status2FA`; при успешном возврате к адресу добавляется `openid.auth.user` (и `openid.auth.uid`, если запрашивалась проверка). Идентификатор пользователя у провайдера имеет вид `<адрес провайдера>?lid=<имя пользователя>`.

Что из этого важно для обратного прокси: адреса `…/e1cib/oid2op` и `…/e1cib/oid2rp` должны быть доступны **по HTTPS под тем же внешним именем**, которое записано в `<rely url=…>`; в OpenID 2.0 ответ провайдера проверяется прямым запросом «сервер — сервер», поэтому не только браузеры, но и серверная сторона должна разрешать внешнее имя и доверять сертификату (свой ЦС — в системное хранилище, раздел 8.3). ⚠ не подтверждено: какой именно процесс выполняет этот запрос (рабочий процесс кластера или модуль расширения веб-сервера) — обеспечьте доступ к адресу провайдера и с сервера 1С, и с веб-сервера. Ограничивая доступ по IP (11.4, 9.3), не закройте эти адреса для адресов самих серверов.

## 12. Производительность и стабильность

### 12.1. Процессы и потоки Apache (серверная база)

Исходные факты:

- Один одновременный HTTP-запрос занимает один поток Apache. В `worker` поток занят и простаивающим keep-alive-соединением (в `event` — нет).
- В каждом процессе Apache свой экземпляр модуля 1С и свой пул соединений с кластером (`<pool size>` — на процесс). Поэтому для 1С лучше **мало процессов и много потоков**.
- Браузер открывает до шести параллельных соединений на сайт; активный пользователь веб-клиента кратковременно занимает 2–6 потоков.

Пример `/etc/apache2/mods-available/mpm_worker.conf` на 100–150 одновременно работающих пользователей (практика, отправная точка):

```apache
<IfModule mpm_worker_module>
    ServerLimit               4
    StartServers              2
    ThreadLimit             128
    ThreadsPerChild         128
    MinSpareThreads          64
    MaxSpareThreads         256
    MaxRequestWorkers       512
    MaxConnectionsPerChild    0
</IfModule>
```

Правила расчёта [офиц., документация Apache]:

- `MaxRequestWorkers` ≤ `ServerLimit` × `ThreadsPerChild` и должно быть кратно `ThreadsPerChild` (иначе округляется вниз с предупреждением). Значения по умолчанию: `ServerLimit 16`, `ThreadsPerChild 25`, `ThreadLimit 64`, `MaxRequestWorkers 400`.
- `ThreadsPerChild` не может превышать `ThreadLimit`; `ThreadLimit` пишется раньше.
- `MaxSpareThreads` ≥ `MinSpareThreads` + `ThreadsPerChild`.
- Изменения `ServerLimit` и `ThreadLimit` при `reload`/`graceful` игнорируются — нужен `sudo systemctl restart apache2`.
- `MaxConnectionsPerChild 0` — процессы не перезапускаются по счётчику соединений. Ненулевое значение можно ставить для борьбы с утечками памяти, но каждое пересоздание процесса сбрасывает пул соединений с кластером.
- Запросы сверх `MaxRequestWorkers` ждут в очереди (`ListenBackLog`, по умолчанию 511); для пользователя это выглядит как «зависание», а в `error.log` появляется `server reached MaxRequestWorkers setting, consider raising the MaxRequestWorkers setting`. Код сообщения зависит от MPM: `AH00286` — worker, `AH00484` — event, `AH00161` — prefork (коды приведены по памяти рецензента и подтверждены 11.10.2026 исходным кодом Apache 2.4.x (`prefork.c`, `worker.c`, `event.c`) — ищите в журнале по тексту, а не по коду: `sudo grep -c 'reached MaxRequestWorkers' /var/log/apache2/error.log`). Сообщение пишется один раз за запуск, поэтому его отсутствие в свежей части журнала ничего не доказывает — смотрите `server-status`.

Оперативный контроль:

```bash
apachectl -M | grep status                             # mod_status в Ubuntu включён по умолчанию
curl -s 'http://localhost/server-status?auto' | grep -E 'BusyWorkers|IdleWorkers|Scoreboard'
ps -o pid,nlwp,rss,cmd -C apache2                      # процессы, число потоков, память
sudo grep -c 'MaxRequestWorkers' /var/log/apache2/error.log
```

Если с порта 80 настроено перенаправление на HTTPS, страницу состояния запрашивайте так: `curl -sk 'https://localhost/server-status?auto'` (доступ к ней в Ubuntu разрешён только с локального адреса).

### 12.2. Файловая база

Официально: публикацию файловой базы должен обслуживать один рабочий процесс (`ServerLimit 1` в секции worker).

```apache
<IfModule mpm_worker_module>
    ServerLimit               1
    StartServers              1
    ThreadLimit             128
    ThreadsPerChild         128
    MinSpareThreads           1
    MaxSpareThreads         129
    MaxRequestWorkers       128
    MaxConnectionsPerChild    0
</IfModule>
```

- Запросы к файловой базе модуль выполняет строго по одному, поэтому большое число потоков нужно только для удержания соединений.
- Настройка MPM общая для всего Apache: не совмещайте на одном экземпляре файловые и нагруженные серверные базы.
- Регламентные задания в файловой базе через веб-сервер: атрибут `allowexecutescheduledjobs="force"` в `default.vrd` либо отдельный постоянно запущенный клиент.
- Практический предел — несколько одновременных пользователей; при росте переводите базу в клиент-серверный вариант.

### 12.3. Таймауты, KeepAlive, размер запроса

| Директива Apache | По умолчанию в Apache | В `apache2.conf` Ubuntu | В эталоне 1С (docker_fresh) | Комментарий |
|---|---|---|---|---|
| `Timeout` | 60 | 300 | 60 | Ожидание ввода-вывода по соединению. Для долгих вызовов сервисов увеличивают |
| `KeepAlive` | On | On | On | Обязательно включён |
| `MaxKeepAliveRequests` | 100 | 100 | 0 (без ограничения) | |
| `KeepAliveTimeout` | 5 | 5 | 60 | Большое значение при `worker` требует больше потоков |
| `LimitRequestBody` | 1073741824 (1 ГиБ); «в 2.4.53 и более ранних значение по умолчанию было 0 (без ограничения)» | не задано | не задано | Загрузка файла больше 1 ГиБ даст 413 — задайте `LimitRequestBody 0` или нужный размер. В Ubuntu 22.04 (2.4.52) фактическое умолчание — 0, без ограничения: уточнено 20.10.2026 по коду 2.4.52 (`AP_DEFAULT_LIMIT_REQ_BODY = 0`) и всем патчам ветки `ubuntu/jammy-updates` — заплатка CVE-2022-29404 правит только `mod_lua`. В 24.04 и 26.04 — 1 ГиБ |

Все значения таблицы перепроверены 2026-10-10: столбец «по умолчанию» — по документации Apache 2.4 (`core`), столбец Ubuntu — по файлу `debian/config-dir/apache2.conf.in` пакета, столбец эталона — по `docker_fresh/conf/web/apache2.conf`. Оговорка про Ubuntu 22.04: там Apache 2.4.52, но с бэкпортированными исправлениями безопасности; смена значения `LimitRequestBody` по умолчанию пришла в исходном коде вместе с исправлением CVE-2022-29404, поэтому лимит 1 ГиБ может действовать и в 22.04. **Уточнено 11.10.2026** по журналу изменений пакета `apache2` 2.4.52-1ubuntu4.24 (changelogs.ubuntu.com): исправление CVE-2022-29404 описано там как правка одного файла `modules/lua/lua_request.c`, а `LimitRequestBody` в журнале не упоминается ни разу — судя по журналу, в 22.04 умолчание осталось прежним (0, без ограничения). Сам патч не читался, поэтому прежняя оговорка остаётся: не подтверждено (патч Ubuntu не читался) — если загружаются файлы больше 1 ГиБ, задайте `LimitRequestBody` явно на любой версии.

Цепочка таймаутов при работе через nginx должна быть согласована: `proxy_read_timeout` (nginx) ≥ `Timeout` (Apache) ≥ ожидаемой длительности самого долгого вызова.

Со стороны платформы [офиц.]: сеанс веб- или тонкого клиента обращается к серверу не реже раза в 10 минут; время засыпания пассивного сеанса по умолчанию 1200 с (параметр базы); проверка соединения модуля с кластером — каждые 3 с, таймаут 15 с.

### 12.4. Сжатие

- `mod_deflate` в Ubuntu включён по умолчанию для текстовых типов (`/etc/apache2/mods-enabled/deflate.conf`). Состав файла [проверено 2026-10-10 по исходникам пакета]: `AddOutputFilterByType DEFLATE` для `text/html text/plain text/xml text/css text/javascript`, `application/x-javascript application/javascript application/ecmascript`, `application/rss+xml`, `application/wasm`, `application/xml` (внутри `<IfModule mod_filter.c>`). **`application/json` в списке нет** — ответы OData и HTTP-сервисов в JSON по умолчанию не сжимаются. Если интеграции гоняют большие JSON по медленному каналу, добавьте в отдельный файл `conf-available/1c-deflate.conf` строку `AddOutputFilterByType DEFLATE application/json` и включите его (`sudo a2enconf 1c-deflate`). Для веб-клиента дополнительная настройка обычно не нужна.
- При nginx перед Apache сжимайте в одном месте: либо `gzip on;` в nginx (как в эталоне 1С), либо `mod_deflate` в Apache.
- Проверка: `curl -sI -H 'Accept-Encoding: gzip' https://1c.example.com/demo/ | grep -i content-encoding`.

### 12.5. Пул соединений и сервисы

- `<pool size>` (100 по умолчанию) — максимум соединений модуля с кластером на один процесс Apache. Соединение занято только на время серверного вызова, поэтому 100 хватает на сотни интерактивных пользователей. Увеличивать имеет смысл при массовых одновременных вызовах сервисов.
- Неиспользуемое соединение живёт `maxAge` = 20 с. Если в журнале много событий установки соединений при редких запросах — увеличьте `maxAge`.
- При установке монопольного режима кластер просит подключённые веб-серверы очистить пулы [офиц., 2.2.10].
- HTTP- и веб-сервисы: включайте повторное использование сеансов (`reuseSessions="autouse"`), иначе каждый вызов создаёт новый сеанс — это главная причина медленных интеграций и исчерпания лицензий.
- Распределение по рабочим процессам кластера выполняет сам кластер; веб-сервер в это не вмешивается.

### 12.6. Журналы

```bash
sudo tail -f /var/log/apache2/error.log /var/log/apache2/access.log
sudo journalctl -u apache2 -e
# время обработки запроса в журнале доступа: добавить %D (микросекунды) в LogFormat
#   LogFormat "%h %l %u %t \"%r\" %>s %O %D" onec
```

Со стороны 1С запросы через модуль расширения видны в технологическом журнале и в списке соединений кластера:

- События технологического журнала [офиц., приложение 3, `logcfg.xml`; проверено 2026-10-10 по руководству 8.3 ранней редакции]: `VRSREQUEST` — «запрос к серверу за некоторым ресурсом» (свойства `Method`, `URI`, `Headers`, `Body`), `VRSRESPONSE` — «ответ сервера» (свойства `Status`, `Phrase`, `Headers`, `Body`; в англоязычной ранней редакции имя напечатано как `VRSRESPONCE` — опечатка), `VRSCACHE` — операции кеша запросов к серверу.

  ```xml
  <!-- фрагмент logcfg.xml: все запросы и ответы дольше 5 секунд.
       В условии отбора свойство duration задаётся в единицах 1/10000 с (5 с = 50000),
       durationus — в микросекундах (5 с = 5000000); в самом журнале 8.3 длительность пишется в микросекундах.
       Единицы приведены по памяти рецензента — сверьте со статьёй базы знаний о технологическом журнале. -->
  <log location="/var/log/1c/vrs" history="24">
      <event><eq property="name" value="VRSREQUEST"/></event>
      <event><eq property="name" value="VRSRESPONSE"/><gt property="duration" value="50000"/></event>
      <property name="all"/>
  </log>
  ```

  Каталог журнала должен быть доступен на запись пользователю, от имени которого работает пишущий процесс (`usr1cv8` для кластера), и не должен содержать посторонних файлов.

- Модуль расширения — такой же процесс платформы, как и остальные: если на веб-сервере есть `logcfg.xml` (каталог `conf` платформы, см. статью о технологическом журнале), процесс `apache2` пишет собственный журнал в подкаталог вида `apache2_<pid>`; пользователю `www-data` нужно право записи в каталог журнала ⚠ не подтверждено: поведение известно по Windows/IIS (подкаталоги `w3wp_<pid>`), для Apache на Linux записано по аналогии.
- Список соединений: `rac connection list --cluster=<uuid>` — у соединений модуля в поле `application` стоит `"WebServerExtension"` (тип «Модуль расширения веб-сервера»). Имя `WebServerExtension` подтверждено руководством «Клиент-серверный вариант» (2.2.7.6, объект требований назначения функциональности) [проверено 2026-10-10]; что именно эта строка выводится утилитой `rac` — по памяти автора и рецензента.
- Соединение модуля с рабочим процессом живёт до перезапуска веб-сервера либо до удаления из пула (истёк `maxAge` или соединение вытеснено) [офиц., «Клиент-серверный вариант»; проверено 2026-10-10].

## 13. Обновление платформы и публикаций

Порядок при обновлении кластера с `$OLD` на `$NEW` (подробности установки — в статье 02):

```bash
OLD=8.3.27.1859; NEW=8.3.27.2074

# 1) на каждом веб-сервере установить компонент ws новой версии
sudo ./setup-full-$NEW-x86_64.run --mode unattended --disable-components client_full --enable-components ws

# 2) найти все упоминания модуля и сохранить копии
grep -rn 'wsap24.so' /etc/apache2/
sudo cp -a /etc/apache2/apache2.conf /etc/apache2/apache2.conf.$(date +%F)
sudo mkdir -p /root/vrd-backup && sudo cp -a --parents /var/www/*/default.vrd /root/vrd-backup/

# 3а) быстрый способ: поправить путь к модулю
sudo sed -i "s#/opt/1cv8/x86_64/$OLD/#/opt/1cv8/x86_64/$NEW/#g" /etc/apache2/apache2.conf
#     (и в /etc/apache2/conf-available/1c-publish.conf, если публикации лежат там)

# 3б) либо перепубликовать утилитой новой версии по сохранённому шаблону
sudo /opt/1cv8/x86_64/$NEW/webinst -publish -apache24 -wsdir demo -dir /var/www/demo \
     -connstr "Srvr=srv1c;Ref=demo;" -confpath /etc/apache2/apache2.conf -descriptor /etc/1c/vrd/demo.vrd

# 4) проверка и ПОЛНЫЙ перезапуск (смена модуля не применяется через reload)
sudo apachectl configtest
sudo systemctl restart apache2
apachectl -M | grep 1cws
curl -sI http://localhost/demo/ | head -n 1
```

Правила:

- Обновляйте кластер и все веб-серверы в одном окне обслуживания: модуль другой сборки с кластером не работает.
- Способ 3а не трогает `default.vrd`. Способ 3б с `-descriptor` заменяет `default.vrd` шаблоном [офиц.]; без `-descriptor` — пересоздаёт его в минимальном виде и теряет ручные настройки (⚠ не подтверждено официально, см. 5.10). Обновляет ли `webinst` новой версии уже существующую строку `LoadModule` (или дописывает вторую) — ⚠ не подтверждено: официально не описано; после способа 3б обязательно проверьте `grep -rn '_1cws_module' /etc/apache2/` — строка должна быть одна и с путём новой версии.
- Способ 3а (правка пути) официально допустим: руководство требует лишь перезапуска веб-сервера при изменении пути к модулю расширения; этот же способ описан в практических статьях (interface31.ru).
- Старую версию удаляйте только после проверки: `sudo /opt/1cv8/x86_64/$OLD/uninstaller-full`. Если удалить каталог раньше, чем исправлен `LoadModule`, Apache не запустится.
- Откат: вернуть путь в `LoadModule` и перезапустить Apache (старая версия платформы должна оставаться установленной).
- Тонкие клиенты, подключённые по HTTP, после обновления сервера тоже должны обновиться; автоматическая раздача дистрибутива настраивается атрибутами `pubdst*` публикации.
- Переход на 8.5.4: проверьте, что в сценариях не осталось ключей `-apache2` / `-apache22` — они удалены [V8Update 8.5.4; проверено 2026-10-10].
- **Обновление самой ОС до Ubuntu 26.04** меняет не платформу, а окружение публикации: Apache 2.4.58 → 2.4.66 с «закалённым» юнитом (`MemoryDenyWriteExecute=yes`, `ProtectHome=read-only` — раздел 6.1), nginx 1.24 → 1.28, certbot 2.9 → 4.0. Модуль `wsap24.so` собран под API Apache 2.4 и пересборки не требует, но drop-in для `apache2.service` создайте заранее, а после обновления проверьте `systemctl cat apache2`, `apachectl -M | grep -E '1cws|mpm'` (обновление пакета не должно менять включённый MPM, но проверить стоит) и открытие базы. Ubuntu 26.04 на 2026-10-10 в списке поддерживаемых 1С систем отсутствует.
- После любого обновления пакета `apache2` (в том числе автоматического, через `unattended-upgrades`) служба перезапускается сама — сеансы веб-клиентов в этот момент переподключаются. Если это критично, исключите пакет из автообновления или задайте окно обслуживания.

## 14. Сквозной пример: Ubuntu 24.04, серверная база, HTTPS

Дано: Ubuntu Server 24.04, кластер 1С 8.3.27.2074 и PostgreSQL на этом же хосте `srv1c` (192.168.1.50), база `demo` создана в кластере, компонент `ws` установлен. Нужно: веб-доступ по `https://srv1c.example.local/demo`.

```bash
# --- 0. Исходное состояние ---------------------------------------------------
V=8.3.27.2074
RAC=/opt/1cv8/x86_64/$V/rac
ls -l /opt/1cv8/x86_64/$V/wsap24.so /opt/1cv8/x86_64/$V/webinst
systemctl is-active srv1cv8-$V@default
CL=$($RAC cluster list | awk '/^cluster/{print $3}')          # UUID кластера (нужна служба ras)
$RAC infobase summary list --cluster=$CL                       # база demo есть в списке
getent hosts srv1c                                             # имя сервера 1С разрешается в 192.168.1.50

# --- 1. Apache --------------------------------------------------------------
sudo apt update && sudo apt install -y apache2
echo "ServerName srv1c.example.local" | sudo tee /etc/apache2/conf-available/servername.conf
sudo a2enconf servername
sudo a2dismod mpm_event && sudo a2enmod mpm_worker     # рекомендация 1С: worker
sudo systemctl restart apache2
apachectl -V | grep -i 'server mpm'
# ограничения юнита: в 24.04 ожидается только PrivateTmp=yes; если MemoryDenyWriteExecute=yes
# (Ubuntu 26.04) — сначала создайте drop-in из раздела 6.1
systemctl show apache2 -p MemoryDenyWriteExecute -p ProtectHome -p PrivateTmp

# --- 2. Публикация -----------------------------------------------------------
sudo mkdir -p /var/www/demo
sudo /opt/1cv8/x86_64/$V/webinst -publish -apache24 -wsdir demo -dir /var/www/demo \
     -connstr "Srvr=srv1c;Ref=demo;" -confpath /etc/apache2/apache2.conf
grep -n -A8 '1c publication' /etc/apache2/apache2.conf
cat /var/www/demo/default.vrd
sudo apachectl configtest && sudo systemctl restart apache2
apachectl -M | grep 1cws
curl -sS -o /dev/null -w '%{http_code}\n' http://localhost/demo/

# --- 3. HTTPS (внутренняя сеть: собственный сертификат) -----------------------
sudo a2enmod ssl headers rewrite
sudo openssl req -x509 -nodes -days 825 -newkey rsa:2048 \
     -keyout /etc/ssl/private/1c-selfsigned.key -out /etc/ssl/certs/1c-selfsigned.crt \
     -subj "/CN=srv1c.example.local" \
     -addext "subjectAltName=DNS:srv1c.example.local,DNS:srv1c,IP:192.168.1.50"

sudo tee /etc/apache2/sites-available/1c-ssl.conf >/dev/null <<'EOF'
<VirtualHost *:443>
    ServerName srv1c.example.local
    SSLEngine on
    SSLCertificateFile    /etc/ssl/certs/1c-selfsigned.crt
    SSLCertificateKeyFile /etc/ssl/private/1c-selfsigned.key
    ErrorLog  ${APACHE_LOG_DIR}/1c-ssl-error.log
    CustomLog ${APACHE_LOG_DIR}/1c-ssl-access.log combined
</VirtualHost>
EOF

sudo tee /etc/apache2/sites-available/1c-http.conf >/dev/null <<'EOF'
<VirtualHost *:80>
    ServerName srv1c.example.local
    RewriteEngine On
    RewriteCond %{REQUEST_URI} !^/\.well-known/acme-challenge/
    RewriteRule ^(.*)$ https://%{HTTP_HOST}$1 [R=301,L]
</VirtualHost>
EOF

sudo a2dissite 000-default
sudo a2ensite 1c-ssl 1c-http
sudo apachectl configtest && sudo systemctl restart apache2

# --- 4. Брандмауэр -----------------------------------------------------------
sudo ufw allow 'Apache Full'
sudo ufw status

# --- 5. Проверка -------------------------------------------------------------
sudo ss -tlnp | grep apache2                                  # :80 и :443
curl -sI http://srv1c.example.local/demo/ | head -n 3          # 301 → https
curl -skI https://srv1c.example.local/demo/ | head -n 3        # ответ модуля 1С
curl --cacert /etc/ssl/certs/1c-selfsigned.crt -sI https://srv1c.example.local/demo/ | head -n 1
sudo tail -n 20 /var/log/apache2/1c-ssl-error.log
$RAC connection list --cluster=$CL | grep -i -A4 'webserver'   # соединение модуля расширения (после первого входа; application : "WebServerExtension")
```

На рабочих станциях Windows: добавить `192.168.1.50 srv1c.example.local srv1c` в `C:\Windows\System32\drivers\etc\hosts` (если нет DNS), импортировать `1c-selfsigned.crt` в «Доверенные корневые центры сертификации», открыть `https://srv1c.example.local/demo` в браузере или добавить этот адрес в тонкий клиент («На веб-сервере»).

Вариант с публичным именем: вместо шага 3 — `sudo apt install -y certbot python3-certbot-apache && sudo certbot --apache -d 1c.example.com --redirect -m admin@example.com --agree-tos -n`, затем `sudo certbot renew --dry-run`.

## Типичные ошибки и подводные камни (симптом → причина → решение)

Тексты сообщений 1С приведены по смыслу — точная формулировка зависит от версии.

### Apache не запускается или не видит публикацию

| № | Симптом | Причина | Решение |
|---|---|---|---|
| 1 | `apache2: Syntax error … Cannot load /opt/1cv8/x86_64/<версия>/wsap24.so into server: … cannot open shared object file: No such file or directory` | Платформу обновили или удалили, а `LoadModule` указывает на старый каталог | `grep -rn wsap24.so /etc/apache2/`, исправить путь, `sudo apachectl configtest`, `sudo systemctl restart apache2` |
| 2 | `Invalid command 'ManagedApplicationDescriptor', perhaps misspelled or defined by a module not included in the server configuration` | Блок публикации есть, а строки `LoadModule _1cws_module` нет (удалили, закомментировали, либо она в файле, который подключается позже) | Вернуть `LoadModule` перед блоками публикаций |
| 3 | Предупреждение `module _1cws_module is already loaded, skipping` | `LoadModule` записан дважды (в `apache2.conf` и в отдельном файле) | Оставить одну строку; убедиться, что путь в ней — нужной версии |
| 4 | `AH00534: apache2: Configuration error: More than one MPM loaded` или `No MPM loaded` | Включены два MPM либо ни одного | `ls /etc/apache2/mods-enabled/mpm_*`; `sudo a2dismod mpm_event mpm_prefork; sudo a2enmod mpm_worker` |
| 5 | `webinst` отработал, а в `apache2.conf` ничего не появилось | Запуск без root; не найден файл конфигурации; неверный `-confpath` | Запускать через `sudo`, явно указывать `-confpath /etc/apache2/apache2.conf` |
| 6 | `http://хост/demo` → 404 Not Found | Apache не перезапущен после публикации; неверный регистр имени (`/Demo` ≠ `/demo`); нет `Alias` | `sudo systemctl restart apache2`; сверить имя с `-wsdir`; `apachectl -S`, `grep -n Alias /etc/apache2/apache2.conf` |
| 7 | 403 Forbidden; в `error.log` — `AH00035: access to /demo/ denied … because search permissions are missing on a component of the path` | `www-data` не может пройти по каталогам или прочитать `default.vrd`; действует `Require ip …` | `namei -l /var/www/demo/default.vrd`; исправить права (раздел 6); проверить секции `<Location>` |
| 8 | Вместо 1С открывается список файлов каталога или скачивается `default.vrd` | Запрос обрабатывает не модуль 1С: нет `SetHandler 1c-application`, модуль не загружен | Проверить блок публикации и `apachectl -M \| grep 1cws` |
| 8а | После `webinst -delete` пропал каталог со всем содержимым | По документации `-delete` удаляет и физический каталог публикации; в `-dir` был указан общий каталог | Восстановить из копии; публиковать только в отдельный каталог `/var/www/<имя>`; публикации убирать правкой конфигурации |
| 8б | После `apt upgrade` или `do-release-upgrade` публикация перестала открываться, хотя 1С не обновляли | Пакет `apache2` обновился и перезапустил службу; при переходе на 26.04 сменился юнит (ограничения systemd), мог измениться набор включённых модулей | `systemctl status apache2`; `sudo apachectl configtest`; `apachectl -M \| grep -E '1cws\|mpm'`; `systemctl cat apache2`; раздел 6.1 |

### Публикация открывается, но 1С сообщает об ошибке

| № | Симптом | Причина | Решение |
|---|---|---|---|
| 9 | Сообщение о различии версий клиента и сервера с упоминанием модуля расширения веб-сервера | Сборка `wsap24.so` не совпадает со сборкой кластера | Поставить компонент `ws` той же сборки, исправить `LoadModule`, полностью перезапустить Apache |
| 10 | «Сервер 1С:Предприятия не обнаружен», ошибки сетевого доступа, `Connection refused`, ошибка разрешения имени | Веб-сервер не достаёт до кластера: не разрешается имя сервера 1С, закрыты 1541 или 1560–1591, кластер остановлен | `getent hosts <сервер>`; `nc -zv <сервер> 1541`; `nc -zv <сервер> 1560`; запись в `/etc/hosts`; правила `ufw` на сервере 1С |
| 11 | «Информационная база не обнаружена» | Неверное имя базы в `Ref=` (как оно зарегистрировано в кластере) или не тот кластер/порт в `Srvr=` | Исправить атрибут `ib` в `default.vrd`, перезапустить Apache |
| 12 | «Не найдена лицензия…» в веб-клиенте, при этом тонкий клиент с того же места работает | Вопрос лицензирования: веб-клиент не может использовать локальную клиентскую лицензию, её должен выдать сервер | Настроить клиентские лицензии на сервере 1С или сервере лицензирования. Сама публикация при этом исправна |
| 13 | 500 Internal Server Error сразу после правки `default.vrd` | Некорректный XML, неэкранированные кавычки в `ib`, неверное имя элемента | `xmllint --noout default.vrd`; кавычки внутри атрибута — `&quot;`; вернуть копию |
| 14 | «Ошибка загрузки компоненты backbas … No such file or directory» в веб-клиенте (платформа 8.3.25+; РЕД ОС и другие RHEL-подобные; **ожидаемо — Ubuntu 26.04 и Debian с `apache2` ≥ 2.4.66-1**) | Ограничение `MemoryDenyWriteExecute=yes` в юните веб-сервера и/или SELinux | `sudo systemctl edit apache2` (в RHEL — `httpd`) → `[Service]` `MemoryDenyWriteExecute=no`; `sudo systemctl daemon-reload && sudo systemctl restart apache2`; в RHEL дополнительно `setsebool -P httpd_execmem on`. В Ubuntu 22.04/24.04 директивы в юните нет [проверено 2026-10-10], там причина другая (права на `/opt/1cv8/x86_64/<версия>/`, неполная установка компонента `ws`). Для 26.04 — ⚠ не подтверждено на стенде, см. 6.1 |
| 14а | Ubuntu 26.04: файловая база в `/home/...` открывается с ошибкой записи, хотя права `www-data` выданы; Apache «не видит» файлы в `/root` | `ProtectHome=read-only` и `InaccessiblePaths=/root` в штатном юните | Перенести базу в `/srv/1c/bases`, а keytab/шаблоны — в `/etc/apache2` или `/etc/1c`; крайняя мера — drop-in `ProtectHome=no` |
| 14б | Модуль 1С не находит файл, который вы положили в `/tmp` (или вы не видите в `/tmp` временные файлы 1С) | `PrivateTmp=true`: у службы свой `/tmp` (все выпуски Ubuntu) | Использовать каталог вне `/tmp` и `/var/tmp`; реальное расположение — `/tmp/systemd-private-*-apache2.service-*/tmp` |
| 15 | В `journalctl -k` строки `apparmor="DENIED" … profile="/usr/sbin/apache2"` | Включён профиль AppArmor для Apache | Добавить правила на `/opt/1cv8/**`, каталог публикации и каталог базы либо перевести профиль в complain |
| 16 | После перепубликации пропали веб-сервисы, HTTP-сервисы, OData (404 на `/ws`, `/hs`, `/odata`) | `webinst` без `-descriptor` пересоздал `default.vrd` | Восстановить из эталона; всегда публиковать с `-descriptor` |
| 17 | HTTP-сервис отвечает 404, хотя база открывается | Сервис не опубликован: `publishByDefault="false"` и сервиса нет в списке; сервис из расширения без `publishExtensionsByDefault`; неверный `rootUrl` | Дописать `<service … enable="true"/>` или включить публикацию по умолчанию; перезапустить Apache |
| 18 | OData отвечает 404 или пустым списком | Не задан `enableStandardOData="true"`; объекты не включены в состав стандартного интерфейса OData | Исправить `default.vrd`; задать состав в базе |
| 19 | 401 при верном пароле у сервиса | Кириллица не в UTF-8; заголовок `Authorization` перехвачен Basic-аутентификацией веб-сервера или прокси; пользователю не разрешена аутентификация 1С | Передавать UTF-8; согласовать учётные записи (раздел 11.4); проверить свойства пользователя |

### Работа через nginx и HTTPS

| № | Симптом | Причина | Решение |
|---|---|---|---|
| 20 | 502 Bad Gateway | Apache остановлен или перезапускается; неверный адрес в `upstream`; Apache слушает другой интерфейс | `sudo ss -tlnp \| grep apache2`; `sudo tail /var/log/nginx/error.log` |
| 21 | 504 Gateway Time-out на длительных операциях (отчёты, обмены, сервисы) | `proxy_read_timeout` (60 с по умолчанию) или `Timeout` Apache меньше длительности вызова | Увеличить оба таймаута; тяжёлые операции выносить в фоновые задания |
| 22 | 413 Request Entity Too Large при загрузке файла | `client_max_body_size` nginx (1 МБ по умолчанию) или `LimitRequestBody` Apache (1 ГиБ с 2.4.54) | Увеличить лимиты |
| 23 | После входа браузер уходит на `http://…` или на `…:8080` | Apache формирует перенаправление по своей схеме и порту; не переданы `Host` и `X-Forwarded-*` | `proxy_set_header Host $host`; заголовки `X-Forwarded-Proto/Host/Port`; `proxy_redirect http://$host/ $scheme://$host/;` |
| 24 | Тонкий клиент: «Удалённый узел не прошёл проверку» при HTTPS | Самоподписанный сертификат или неизвестный ЦС; имя в сертификате не совпадает с адресом | Указать файл сертификата ЦС в свойствах базы или импортировать корневой сертификат; выпустить сертификат с правильным `subjectAltName` |
| 25 | Сертификат Let's Encrypt не продлился | Закрыт порт 80; перенаправление захватило `/.well-known/acme-challenge/`; нет перезагрузки веб-сервера после продления | Исключение для ACME в перенаправлении; deploy-hook; `sudo certbot renew --dry-run` |
| 26 | После отключения HTTPS браузер упорно открывает `https://` | Браузер запомнил HSTS | Удалить запись HSTS в браузере; впредь включать HSTS после отладки |
| 27 | Все пользователи попадают на один веб-сервер из двух | `ip_hash` при входе всех клиентов с одного адреса (NAT) | `sticky cookie` (nginx 1.29.6+) или `hash` по другому ключу |
| 28 | В журнале Apache у всех запросов адрес 127.0.0.1 | Запросы приходят от прокси | `a2enmod remoteip`, `RemoteIPHeader X-Forwarded-For`, `RemoteIPInternalProxy 127.0.0.1` |

### Нагрузка и зависания

| № | Симптом | Причина | Решение |
|---|---|---|---|
| 29 | Публикация «зависает» у всех, затем отпускает; в `error.log` — `AH00286: server reached MaxRequestWorkers setting` | Исчерпаны потоки Apache | Увеличить `MaxRequestWorkers` / `ThreadsPerChild` (раздел 12.1), уменьшить `KeepAliveTimeout`; смотреть `server-status` |
| 30 | Все потоки Apache заняты, а процессор веб-сервера простаивает | Узкое место дальше: зависший `rphost`, блокировки, медленные запросы СУБД | Диагностировать кластер и СУБД (`rac session list`, `pg_stat_activity`); веб-сервер здесь только ждёт |
| 31 | 503 Service Unavailable | Apache перезапускается или перегружен; бэкенд помечен недоступным в nginx | Журналы Apache и nginx; `max_fails`/`fail_timeout` |
| 32 | Растёт число сеансов и кончаются лицензии при работе интеграций | Каждый вызов сервиса создаёт новый сеанс | `reuseSessions="autouse"` для сервисов; отдельный пользователь |
| 33 | Память процессов `apache2` постоянно растёт | Утечки в длительно живущих процессах | `MaxConnectionsPerChild` с большим значением (например 100000) или плановый `systemctl restart apache2` ночью |

## Быстрая шпаргалка — «задача → команда»

| Задача | Команда |
|---|---|
| Установить Apache | `sudo apt install -y apache2` |
| Версия и MPM | `apache2 -v`; `apachectl -V \| grep -i mpm` |
| Переключить на worker | `sudo a2dismod mpm_event && sudo a2enmod mpm_worker && sudo systemctl restart apache2` |
| Проверить конфигурацию | `sudo apachectl configtest` |
| Перезапустить / перечитать | `sudo systemctl restart apache2` / `sudo systemctl reload apache2` |
| Загружен ли модуль 1С | `apachectl -M \| grep 1cws` |
| Где прописан модуль | `grep -rn 'wsap24.so' /etc/apache2/` |
| Список публикаций | `grep -rn -A7 '1c publication' /etc/apache2/` |
| Опубликовать серверную базу | `sudo /opt/1cv8/x86_64/$V/webinst -publish -apache24 -wsdir demo -dir /var/www/demo -connstr "Srvr=srv1c;Ref=demo;" -confpath /etc/apache2/apache2.conf` |
| Опубликовать файловую базу | `sudo /opt/1cv8/x86_64/$V/webinst -publish -apache24 -wsdir buh -dir /var/www/buh -connstr "File=/srv/1c/bases/buh;" -confpath /etc/apache2/apache2.conf` |
| Опубликовать по шаблону | `… -descriptor /etc/1c/vrd/demo.vrd` |

| Проверить права по цепочке | `namei -l /var/www/demo/default.vrd` |
| Код ответа публикации | `curl -sS -o /dev/null -w '%{http_code}\n' http://localhost/demo/` |
| WSDL веб-сервиса | `curl -u 'user:pwd' 'http://localhost/demo/ws/<Имя>?wsdl'` |

## Что не удалось подтвердить

Поиск в вебе при подготовке статьи был недоступен (исчерпан лимит запросов), поэтому использовались только страницы с заранее известными адресами. Приложения 3 и 4 руководства администратора (описание `default.vrd`, параметры `webinst` и `ibsrv`, конфигурационный файл автономного сервера) и раздел 8.10.3 «Reverse Proxy» прочитать не удалось: на ИТС они закрыты подпиской, а англоязычная страница обрывается раньше.

Состояние после рецензии 2026-10-10 (поиск в вебе и при рецензии был недоступен — лимит запросов исчерпан; перечитаны страницы с известными адресами, в том числе дальние части длинных страниц, недоступные автору). Ниже — что **остаётся** неподтверждённым; то, что удалось закрыть, перечислено отдельно.

1. **`default.vrd`**: полный перечень атрибутов актуальной версии. Остаются не подтверждены: атрибуты `reuseSessions`, `sessionMaxAge`, `poolSize`, `poolTimeout` и их значения по умолчанию (20/10/5; `dontuse`/`autouse`); элемент `<standardOdata>`; имена атрибутов семейства `pubdst*`; имена атрибутов периода и таймаута проверки соединения с кластером; атрибут `protocol` элемента `<debug>`; структура `<authentication>`/`logonView`; JSON-ключи `<openidconnect>` и элемент `allowStandardAuthentication`; значение `enableStandardOData` по умолчанию; семантика `<returnto>`; версия появления `<accessTokenAuthentication>`. Причина: приложение 3 руководства 8.3.27 закрыто подпиской ИТС, на 1c-dn.com страница руководства обрывается на разделе 8.10.2.2, а в ранней редакции (yellow-erp.com) этих элементов ещё нет.
2. **`webinst`**: нечувствительность ключей к регистру (обе формы `-confpath`/`-confPath` встречаются в рабочих инструкциях, официально — только строчная); работа с произвольным файлом в `-confpath`; что `-delete` делает со строкой `LoadModule`; пересоздаёт ли повторная публикация **без** `-descriptor` существующий `default.vrd`; обновляет ли `webinst` новой версии строку `LoadModule`; точный вид блока `<Directory>` (в частности `AllowOverride All`, `Options None`).
3. **Заголовки обратного прокси**: перечень `X-Forwarded-Port/Host/Proto` подтверждён только по руководству 8.3 ранней редакции; раздел 8.10.3 редакции 8.3.27/8.5 не прочитан. Эталон `docker_fresh` передаёт только `X-Forwarded-Proto` и `X-Forwarded-Port` (плюс `Host`).
4. **Привязка сеансов при балансировке**: официального требования не найдено; рекомендация основана на алгоритме выбора рабочего процесса (2.2.7.4) и на эталонной конфигурации 1С с `ip_hash`.
5. **Длительные вызовы**: остаётся ли HTTP-запрос интерактивного клиента открытым на всё время серверного вызова (от этого зависит, насколько критичен `proxy_read_timeout` для веб-клиента).
6. **WebSocket**: используются ли входящие WebSocket-соединения через публикацию (сервис оповещения клиента 8.3.26+). Эталон 1С заголовки `Upgrade` не проксирует.
7. **Kerberos через Apache на Linux**: официальный рецепт найден (руководство 8.3.27, 2.8.1.3, модуль `mod_auth_kerb`) — но пакета `libapache2-mod-auth-kerb` нет в Ubuntu 24.04/26.04. Рецепт-замена с `mod_auth_gssapi` — практика, на стенде не проверен; подхватывает ли `wsap24.so` делегированный кеш от `mod_auth_gssapi` так же, как от `mod_auth_kerb`, не подтверждено. Сами директивы модуля подтверждены по его README.
8. **`ibsrv`**: официальное описание ключей `--direct-regport`/`--direct-range` и портов прямого шлюза по умолчанию (подтверждено только практической статьёй для 8.3.25); эквивалентность `--port`/`--address`/`--base` ключам `--http-port`/`--http-address`/`--http-base`; порт SSH-шлюза по умолчанию; полный состав конфигурационного файла (секции `features`, `gates`, `debug`, `monitor`); текст о лицензировании из руководства.
9. **Ubuntu 26.04 + 1С**: реальное поведение модуля `wsap24.so` под штатным юнитом 26.04 (`MemoryDenyWriteExecute=yes`, `ProcSubset=pid`, `PrivateDevices=yes`) на стенде не проверено; сам файл юнита из пакета Ubuntu не прочитан (вывод сделан по тегу Debian 2.4.66-2 и журналу изменений Ubuntu); действует ли в Ubuntu 22.04 лимит `LimitRequestBody` 1 ГиБ.
10. **Параметры тонкого клиента** `/HttpsCert`, `/HttpsCA` и их значения (приложение 7); точная строка `application` в выводе `rac connection list`; заголовок `IBSession` и cookie `ibsession` (раздел 17.7 руководства разработчика).
11. **Ответ публикации на `curl`**: точный код перенаправления веб-клиента (сам факт перенаправления на адрес с кодом языка подтверждён руководством); ответ на `HEAD`.
12. **Версии**: стала ли 8.5.4 финальной к октябрю 2026 и есть ли более новые сборки 8.5 — на v8.1c.ru в разделе «Новое в платформе» на 2026-10-10 перечислены только 8.5.4, 8.5.1 и 8.3.27, статус сборок не указан, а сайт релизов закрыт; поддержка Ubuntu 26.04 и Apache 2.4.66 платформой официально не заявлена (в системных требованиях — 20.04, 22.04, 24.04).
13. Лицензирование файловой базы через веб-сервер (доступ `www-data` к каталогу лицензий, влияние ограничений юнита 26.04); лицензирование сеансов веб- и HTTP-сервисов.
14. Момент, когда модуль расширения перечитывает изменённый `default.vrd` (нужен ли перезапуск Apache).
15. Коды сообщений Apache `AH00286`/`AH00484`/`AH00161`; единицы измерения `duration` в условиях `logcfg.xml` (в примере раздела 12.6).
