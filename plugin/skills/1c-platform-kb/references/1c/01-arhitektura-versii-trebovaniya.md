## Кратко — 20 главных фактов и команд

1. Платформа работает в трёх вариантах: **файловый** (база — один файл `1Cv8.1CD`), **клиент-серверный** (клиент → кластер серверов 1С → СУБД) и **автономный сервер** `ibsrv` (один процесс со встроенным веб-сервером, одна база). Клиент никогда не обращается к СУБД напрямую — только через кластер [офиц.].
2. Кластер серверов — это три вида процессов: `ragent` (агент сервера, порт **1540**), `rmngr` (менеджер кластера, порт **1541**), `rphost` (рабочие процессы, порты из диапазона **1560–1591**). Запускается один `ragent`, остальное он порождает сам [офиц.].
3. Клиент подключается к `rmngr` на **1541**, получает адрес (имя хоста!) и порт рабочего процесса и дальше работает с `rphost`. Поэтому с клиентов должны быть доступны 1541 и весь диапазон 1560–1591, а имя сервера должно разрешаться в IP [офиц. + практика].
4. Администрирование на Linux: MMC-оснастки нет. Инструменты — сервер администрирования `ras` (порт **1545**) + консольная утилита `rac`, стандартная функция «Управление серверами» в клиенте, либо MMC-консоль с Windows-машины той же версии [офиц.].
5. Каталог установки с 8.3.18: `/opt/1cv8/x86_64/<версия>/` (несколько версий ставятся рядом); общие для всех версий — только `/opt/1cv8/common` (там лежит `1cestart`) и `/opt/1cv8/conf`. До 8.3.18 было `/opt/1C/v8.3/x86_64/` и одна версия на машину [офиц.].
6. Данные кластера (реестр, журналы регистрации, сеансовые данные) по умолчанию лежат в `/home/usr1cv8/.1cv8/1C/1cv8/` (переменная `SRV1CV8_DATA`, параметр `-d`). Каталог `srvinfo` — это Windows; на Linux его нет, пока вы сами так не назовёте каталог [офиц.].
7. Процессы сервера работают от пользователя **`usr1cv8`** (группа **`grp1cv8`**), его создаёт установщик. Автозапуск службы нужно настроить вручную [офиц.].
8. Дистрибутив для Linux x86-64 с 8.3.20 — единый установщик `setup-full-<версия>-x86_64.run` (с 8.3.24 поставляется в zip-архиве `server64_<версия с подчёркиваниями>.zip` вместе с `installAsRoot`) [офиц.]. Наборы deb/rpm-пакетов для x86-64 при этом **по-прежнему публикуются** как альтернатива (архив вида `deb64_8_3_27_2074.zip`, ставит в тот же `/opt/1cv8/x86_64/<версия>/`) [практика: статья Selectel 2026 г.; руководство описывает пакеты с суффиксами `amd64`/`x86_64`]; для ARM64 и Эльбруса пакеты — единственный способ [офиц.]. Способы установки смешивать нельзя: что поставлено `.run` — удаляется `uninstaller-full`, что пакетами — пакетным менеджером.
9. С 8.3.21 служба сервера — шаблонный systemd-юнит `srv1cv8-<версия>@.service` в каталоге версии; SysV-скрипт `srv1cv83` удалён (остался только для Эльбруса) [офиц.]:
   ```bash
   sudo systemctl link /opt/1cv8/x86_64/8.3.27.1688/srv1cv8-8.3.27.1688@.service
   sudo systemctl enable --now srv1cv8-8.3.27.1688@default
   ```
10. Порты и каталог данных задаются переменными `SRV1CV8_PORT`, `SRV1CV8_REGPORT`, `SRV1CV8_RANGE`, `SRV1CV8_DATA` через `systemctl edit …` [офиц.].
11. На Linux рабочие процессы **не умеют** работать с MS SQL Server и с COM-объектами; аутентификация ОС — только Kerberos (NTLM нет) [офиц.].
12. Версии клиента и сервера должны совпадать полностью, до четвёртой цифры сборки (пример документации: сервер 8.3.24.100 и клиент 8.3.24.150 вместе работать не будут) — иначе клиент получает ошибку о различии версий клиента и сервера с двумя номерами сборок в скобках [офиц., гл. 2 «Клиент-серверного варианта»].
13. На 10.10.2026: линейка **8.3** закончилась на **8.3.27** (обновляется исправлениями; в статье Selectel на Хабре, датируемой 2026 г., используется сборка 8.3.27.2074); линейка **8.5**: финальная **8.5.1** (сборка 8.5.1.1150 от 25.12.2025), 8.5.2 и 8.5.3 отдельно не выпускались, следующая — **8.5.4** (известна сборка 8.5.4.1306; ⚠ не подтверждено, что она финальная: записи о выпуске 8.5.4 в блоге разработчиков по 07.10.2026 нет), в работе 8.5.5 и 8.5.6 [офиц.].
14. Официально поддерживаемые Ubuntu для клиента и сервера: **20.04, 22.04, 24.04 LTS** (x86-64 и ARM64). Ubuntu 26.04 в списке ОС платформы на 10.10.2026 отсутствует, хотя сборки PostgreSQL от 1С для 26.04 уже есть [офиц.].
15. PostgreSQL: нужна сборка **с патчем 1С** (от фирмы «1С» или Postgres Pro) либо Postgres Pro Standard/Enterprise, Tantor, Pangolin. Актуальные сборки 1С на 10.10.2026: `18.4-1.1C`, `17.10-2.1C`, `16.14-1.1C`, `15.18-1.1C`, `14.23-1.1C` [офиц.].
16. Лицензия сервера **ПРОФ**: не более 12 ядер и 500 сеансов на базу, без профилей безопасности, фонового обновления БД, копий БД и др.; **КОРП** — только 64-бит, всё включено; ARM64 и Эльбрус — только КОРП; **МИНИ** — 5 сеансов [офиц.].
17. Аппаратные ключи HASP на ARM64 и Эльбрусе не поддерживаются; с **8.5.4** клиентские и серверные приложения платформы больше не получают лицензии напрямую через HASP License Manager — лицензии (программные и аппаратные) раздаёт собственное приложение «1С:Предприятие – менеджер лицензий» (`rmlic`, клиентский файл настроек `rclic.cfg`); сам `rmlic` умеет брать лицензии у HASP License Manager [офиц., V8Update 8.5.4; в анонсе блога от 10.04.2025 эта функциональность была привязана к 8.5.2, которая отдельно не вышла].
18. Файлы программных лицензий на Linux-сервере: `/var/1C/licenses/*.lic` (каталог создаёт установщик: владелец `root`, группа `grp1cv8`, права `rwx`/`rwx`/`r-x`). Полный порядок поиска `*.lic`: `conf` каталога версии → `/opt/1cv8/conf` → `~/.1cv8/conf` → каталог из `ConfLocation` в `conf.cfg` → `/var/1C/licenses` [офиц., гл. 10 руководства администратора].
19. Режим совместимости конфигурации определяет, какими версиями платформы можно открыть базу; каждая версия платформы добавляет значение «предыдущая версия» (в 8.5.4 добавлено «Версия 8.5.1», а совместимость с 8.1 снята) [офиц.].
20. Быстрая диагностика «что запущено и что слушает»:
    ```bash
    systemctl list-units 'srv1cv8*' 'ras*' --all
    ps -eo pid,user,etimes,rss,args | grep -E '[r]agent|[r]mngr|[r]phost|/[r]as |[d]bgs|[c]rserver|[i]bsrv'
    sudo ss -tlnp | grep -E 'ragent|rmngr|rphost|ras|dbgs|crserver|ibsrv'
    ```

## 1. Варианты работы и общая архитектура

### 1.1. Три варианта работы

| Вариант | Где данные | Кто исполняет серверный код | Когда применять |
|---|---|---|---|
| **Файловый** | один файл `1Cv8.1CD` в каталоге базы (локальный диск или SMB/CIFS-ресурс) | сам клиент (толстый/тонкий) либо модуль расширения веб-сервера | 1–5 пользователей, небольшие базы, учебные задачи |
| **Клиент-серверный** | база данных в СУБД (PostgreSQL, MS SQL, Oracle, Db2) | кластер серверов 1С (`ragent`/`rmngr`/`rphost`) | промышленная эксплуатация, много пользователей, фоновые задания |
| **Автономный сервер** (`ibsrv`) | файл `1Cv8.1CD` **или** СУБД | один процесс `ibsrv` со встроенным веб-сервером | небольшие инсталляции без кластера, CI/CD, контейнеры, утилита `ibcmd` |

Ограничения файлового варианта [офиц., гл. 1.5 руководства администратора 8.3.27]:

- все клиенты, работающие с одной файловой базой, должны быть одной версии (разрядность и ОС могут отличаться);
- не более 1024 одновременных соединений с базой;
- совместная работа — только через сетевые ресурсы SMB (CIFS); при монтировании `mount.cifs` нельзя использовать опцию `nobrl`, в Samba — `locking = no`;
- клиент на macOS с сетевыми файловыми базами не работает.

Клиент-серверный вариант требует **серверной лицензии** на каждый компьютер кластера плюс клиентские лицензии (см. раздел 10).

### 1.2. Слои клиент-серверной архитектуры

Документация описывает четыре слоя (исторически говорят «трёхзвенная архитектура»: клиент — сервер приложений — СУБД; веб-сервер — необязательное промежуточное звено) [офиц.]:

1. **Клиентское приложение** — толстый клиент, тонкий клиент, веб-клиент (только браузер), мобильный клиент. Отображает формы, взаимодействует с пользователем, вызывает серверные методы.
2. **Веб-сервер** (Apache/IIS с модулем расширения 1С) — нужен только веб-клиенту, тонкому/мобильному клиенту при подключении по HTTP(S), веб- и HTTP-сервисам, OData. Просто передаёт вызовы в кластер.
3. **Кластер серверов 1С:Предприятия** — исполняет прикладной код, работает с объектами, формирует отчёты, выполняет фоновые и регламентные задания, хранит журнал регистрации и служебные файлы.
4. **Сервер баз данных** — хранит данные; каждой информационной базе соответствует отдельная база данных в СУБД.

```text
 Клиенты                     Веб-сервер                Сервер 1С (Linux, пользователь usr1cv8)          СУБД
┌──────────────────┐                                  ┌───────────────────────────────────────┐   ┌──────────────┐
│ тонкий   1cv8c   │── TCP 1541 ─────────────────────▶│ rmngr  :1541   менеджер кластера      │   │ PostgreSQL   │
│ толстый  1cv8    │── TCP 1560–1591 ────────────────▶│ rphost :1560…  рабочие процессы ──────┼──▶│ :5432        │
│ конфигуратор     │         ┌───────────────┐        │ ragent :1540   агент сервера          │   └──────────────┘
│ веб-клиент       │─ HTTP(S)▶ Apache 2.4     │─ 1541 ─▶│                                       │
│ мобильный клиент │  80/443 │ + wsap24.so   │ 1560+  │ (ibsrv, crserver, dbgs — по надобности)│
└──────────────────┘         └───────────────┘        └───────────────────────────────────────┘
                                                          ▲ TCP 1540
 Администратор:  rac ── TCP 1545 ──▶ ras (сервер администрирования) ──┘
```

Важные следствия:

- Кластер и СУБД могут стоять на одной машине (типичная ВМ «всё в одном») или на разных. Если на разных — между ними рекомендуется гигабитная сеть [офиц.].
- Ключ защиты сервера не сетевой: серверная лицензия должна быть на **каждом** компьютере, где работают рабочие процессы кластера [офиц.].
- Потеря служебных файлов кластера не разрушает информационную базу (данные в СУБД), но теряются журнал регистрации, список баз в кластере, настройки кластера [офиц.].
- Клиент в ВМ с NAT-адаптером не сможет работать с кластером, расположенным на хосте этой ВМ [офиц.]. Для ВМ с сервером 1С на Windows-хосте используйте сетевой мост (bridged) либо проброс портов с корректным разрешением имени сервера.

## 2. Компоненты, процессы и исполняемые файлы

### 2.1. Сводная таблица

Все файлы лежат в каталоге версии `/opt/1cv8/x86_64/<версия>/` (если не указано иное).

| Файл | Что это | Порт по умолчанию | Компонент установщика (`--enable-components`) |
|---|---|---|---|
| `ragent` | агент сервера — «точка входа» рабочего сервера, запускает `rmngr` и `rphost` | 1540/tcp | `server` |
| `rmngr` | менеджер кластера (главный — на центральном сервере) | 1541/tcp (+ порты из диапазона для дополнительных менеджеров) | `server` |
| `rphost` | рабочий процесс: исполняет прикладной код, держит соединения с СУБД | по одному порту из 1560–1591/tcp | `server` |
| `rmstt` | имя, под которым в списке процессов виден специальный менеджер кластера для сервиса распознавания речи; запускается, если в кластере зарегистрирована хотя бы одна модель распознавания речи, независимо от флажка «Менеджер под каждый сервис» [офиц., гл. 2] | — | серверные компоненты |
| `dbda` | Дата акселератор (только в составе 64-разрядного кластера, лицензия КОРП) [офиц., прил. 1] | — | в каталоге версии (серверные компоненты) |
| `ras` | сервер администрирования кластера (Remote Administration Server) | 1545/tcp; HTTP-шлюз метрик — 1555/tcp на `localhost` | `server_admin` («сервер администрирования кластера серверов») [офиц.] |
| `rac` | консольный клиент сервера администрирования | — (клиент) | `server_admin` |
| `ibsrv` | автономный сервер | HTTP 8314/tcp (по умолчанию слушает только `localhost`) | `server` (ставится вместе с кластером серверов, отдельной установки нет) [офиц., гл. 7] |
| `ibcmd` | утилита администрирования автономного сервера и информационных баз (работает и без запущенного сервера) | — | `server` |
| `crserver` | сервер хранилища конфигураций | 1542/tcp [практика: `crserver -port 1542 -d <каталог>` и `EXPOSE 1542` в образе `onec-crs`; в документации платформы адрес хранилища пишется `tcp://host:1542/…`] | `config_storage_server` |
| `dbgs` | сервер отладки (отладка по HTTP) | 1550/tcp, когда его запускает кластер (`/debugServerPort`); у самостоятельно запущенного `dbgs` порта по умолчанию **нет** — нужен `--port` или `--range` [офиц., прил. 4] | лежит в каталоге версии во всех ОС; ⚠ не подтверждено, каким идентификатором компонента установщика он ставится |
| `1cv8` | толстый клиент и конфигуратор (`1cv8 DESIGNER …`, `1cv8 ENTERPRISE …`) | — | `client_full` |
| `1cv8c` | тонкий клиент | — | `client_thin` (без файловых баз), `client_thin_fib` (с поддержкой файловых баз) |
| `1cv8s` | интерактивная программа запуска конкретной версии (окно со списком баз) | — | клиентские компоненты |
| `1cestart` | программа запуска: выбирает нужную установленную версию и стартует клиента. **Лежит не в каталоге версии, а в `/opt/1cv8/common/`**; ставится только при совпадении разрядности ОС и приложения [офиц., прил. 1] | — | клиентские компоненты |
| `1cv8a` | утилита административной консоли: проверка и исправление отдельных проблем ИБ без конфигуратора (`1cv8a ib-check-and-repair …`) [офиц., прил. 4] | — | `additional_admin_functions` |
| `chdbfl`, `cnvdbfl` | тестирование и конвертирование файловой базы `1Cv8.1CD` [офиц.] | — | в каталоге версии |
| `ci` | утилита контроля целостности [офиц.] | — | `integrity_monitoring` |
| `webinst` | утилита публикации базы на веб-сервере | — | `ws` |
| `wsap24.so` | модуль расширения веб-сервера Apache 2.4 | — (работает внутри Apache) | `ws` |

### 2.2. Кластер серверов: понятия

| Понятие | Суть |
|---|---|
| **Кластер серверов** | логическое объединение рабочих серверов (на одном или нескольких компьютерах) и список информационных баз, которые он обслуживает. Идентифицируется портом главного менеджера (обычно 1541) |
| **Рабочий сервер** | компьютер, на котором запущен агент сервера `ragent`. Обычно один компьютер = один рабочий сервер |
| **Центральный сервер** | рабочий сервер с флажком «Центральный сервер» (в англ. документации — *main server*). Хранит реестр кластера, служит точкой подключения клиентов. Их должно быть не меньше одного; число центральных серверов = уровень отказоустойчивости + 1 |
| **Агент сервера** (`ragent`) | представляет рабочий сервер. Ведёт список кластеров и администраторов сервера в файле `1cv8wsrv.lst` в каталоге данных сервера |
| **Менеджер кластера** (`rmngr`) | управляет работой кластера, исполняет сервисы кластера. Главный менеджер ведёт реестр кластера `1CV8Clst.lst` (базы, рабочие серверы, процессы, менеджеры, сервисы, администраторы кластера) в каталоге `reg_<порт>` |
| **Рабочий процесс** (`rphost`) | обслуживает клиентские приложения, работает с СУБД, исполняет серверный код. Количество процессов определяется настройками рабочего сервера и нагрузкой |
| **Сервисы кластера** | функции, распределяемые между менеджерами кластера (см. 2.3). При флажке «Менеджер под каждый сервис» каждому сервису выделяется отдельный `rmngr` на порту из диапазона |
| **Уровень отказоустойчивости** | сколько рабочих серверов может выйти из строя без потери сеансов; центральных серверов нужно на 1 больше |
| **Требования назначения функциональности** | правила, закрепляющие сервисы/соединения/фоновые задания за рабочими серверами (расширенные варианты — только КОРП) |
| **Профили безопасности** | ограничения прикладного кода на сервере (файловая система, внешние компоненты, приложения ОС, интернет-ресурсы). Только КОРП. Настройка «К COM-объектам» на Linux ничего не значит |
| **Уровень безопасности соединения** | «Выключено» / «Только соединение» / «Постоянно». Задаётся при создании кластера и базы; агент использует больший из уровня запуска (`-seclev`, `SRV1CV8_SECLEV`) и уровня кластера |
| **Администраторы** | два независимых списка: администраторы центрального сервера (агента) и администраторы кластера. Пока списки пусты — аутентификация не требуется |

Если при старте `ragent` не находит реестр, он создаёт **кластер по умолчанию**: порт 1541, диапазон 1560:1591, один рабочий процесс, порт отладки по HTTP 1550 [офиц.]. Это типичная причина «пропавших баз» после запуска с другим каталогом данных или от другого пользователя.

### 2.3. Сервисы кластера (по документации 8.3.27)

В русской документации 8.3.27 перечислено 33 сервиса: WebSocket; блокировок объектов; внешнего управления сеансами; времени; вспомогательных функций кластера; Дата акселератора; журналов регистрации; заданий (фоновые и регламентные); интеграционных данных (работа сервисов интеграции); конфигурации кластера; координации полнотекстового поиска v2; лицензирования; мониторинга счётчиков потребления ресурсов; нумерации таблиц и полей БД; нумерации; обновления конфигурации БД (фоновая реструктуризация); повторного использования сеансов (веб-сервисы, HTTP-сервисы, OData); полнотекстового поиска; полнотекстового поиска v2; получения списка сеансов; пользовательских настроек; провайдера OpenID; работы с внешними источниками данных через ODBC и через XMLA; распознавания речи; сеансовых данных; состояния кластера; тестирования; транзакционных блокировок; уведомлений клиента; управления моделями распознавания речи; управления предметами отладки; хранилища двоичных данных. (В консоли формулировки могут немного отличаться.)

Практически важное:

- Сервисы **конфигурации кластера**, **состояния кластера** и **управления предметами отладки** не переносятся — они работают только на центральном сервере, и для них нельзя создать требования назначения функциональности [офиц.].
- **Сервис лицензирования** раздаёт программные лицензии; рабочим процессам и менеджерам нужны права на создание, чтение и изменение файла `1cv8conn.pfl` (лежит в `~/.1cv8/1C/1cv8`). При временной недоступности сервиса такие же лицензии, как уже полученные через него, выдаются не дольше 20 секунд [офиц.]. Сервис можно закрепить за конкретным рабочим сервером — тогда имя сервера при активации лицензии должно совпадать с ним.
- **Сервис сеансовых данных** хранит данные сеансов на диске (каталоги `snccntx…` в каталоге кластера) — диск под каталог данных кластера должен быть быстрым.
- **Сервис журналов регистрации** пишет журнал в каталог кластера (подкаталог `1Cv8Log` каталога базы) — он растёт и не попадает в резервную копию СУБД.
- **Сервис обновления конфигурации БД**: перенос на другой менеджер требует остановки всех рабочих процессов, фоновое обновление после этого окажется приостановленным [офиц.].
- Каталоги данных по умолчанию для сервисов (`<sdf>` — каталог данных сервера, `-d`) [офиц., гл. 2.2.3.2]: журнал регистрации — `<sdf>/reg_<порт>/<uuid базы>/1Cv8Log`; полнотекстовый поиск — `…/<uuid базы>/1Cv8FTxt`, версии 2 — `…/<uuid базы>/1Cv8FTxt2`; сеансовые данные — `<sdf>/reg_<порт>/snccntx/<uuid менеджера>` (так записано в документации; на диске это каталоги вида `snccntx<UUID>` [практика]); счётчики потребления ресурсов — `<sdf>/reg_<порт>/rescntsrv.lst`; хранилище двоичных данных — `<sdf>/reg_<порт>/BinDataStrg/<uuid базы>`; модели распознавания речи — `<sdf>/reg_<порт>/STT`; Дата акселератор — `<sdf>/1Cv8DbDA/<uuid базы>`. Перенос этих каталогов в другое место — только КОРП (с 8.3.26), данные переносит администратор вручную при остановленном кластере.
- В 8.5.4 добавлены/переименованы: отказоустойчивый сервис журнала регистрации (только текстовый формат), сервис обновлений клиентского приложения, сервис блокировок обновления конфигурации БД, сервис регистрации изменений полнотекстового поиска v2; «управление моделями распознавания речи» стало «управлением моделями ИИ» [офиц., V8Update 8.5.4].

### 2.4. Агент сервера `ragent`

**Что делает:** загружает список кластеров из каталога данных, запускает менеджеры кластера и рабочие процессы, принимает подключения средств администрирования (порт 1540).

**Ключевые параметры** [офиц., прил. 4 руководства администратора 8.3.27, п. 4.12]. В документации параметры записаны в форме `/param <значение>`; в примерах для Linux и в юните используется форма `-param <значение>` — обе допустимы. Имя параметра и значение разделяются **пробелом** (не `=`).

| Параметр | Переменная юнита | Назначение | По умолчанию |
|---|---|---|---|
| `-port <порт>` | `SRV1CV8_PORT` | порт агента сервера | 1540 |
| `-regport <порт>` | `SRV1CV8_REGPORT` | порт главного менеджера кластера, **создаваемого по умолчанию** при первом запуске | 1541 |
| `-range <диапазоны>` | `SRV1CV8_RANGE` | начальное значение свойства «Диапазоны IP портов» рабочего сервера, создаваемого по умолчанию; можно несколько: `4549:4567, 7072:7790` | 1560:1591 |
| `-d <каталог>` | `SRV1CV8_DATA` | каталог данных сервера (реестр, журналы, сеансовые данные); путь с пробелами — в кавычках | в юните: `/home/usr1cv8/.1cv8/1C/1cv8`; у самого `ragent` при ручном запуске без `-d` приложение 4 называет `~/.1cv8` (расхождение в документации — указывайте `-d` всегда явно) |
| `-debug [-tcp\|-http]` | `SRV1CV8_DEBUG` (пусто / `-debug` / `-debug -tcp` / `-debug -http`) | разрешить отладку серверного кода; без уточнения — TCP; `-http` — через сервер отладки `dbgs` | выключено |
| `-debugServerAddr <адрес>` | — | адрес компьютера сервера отладки (если сетевых карт несколько) | произвольный адрес компьютера |
| `-debugServerPort <порт>` | — | порт сервера отладки | 1550 |
| `-debugServerPwd <пароль>`, `-debugServerUsers <файл>` | — | пароль доступа к серверу отладки либо файл со списком пользователей отладки (список приоритетнее пароля) | не заданы — отладка никак не ограничена |
| `-seclev <0\|1\|2>` | `SRV1CV8_SECLEV` | уровень безопасности: 0 — выключено, 1 — только соединение, 2 — постоянно | 0 |
| `-pingPeriod <мс>` | `SRV1CV8_PINGPERIOD` | период проверки разрыва соединений | 1000 |
| `-pingTimeout <мс>` | `SRV1CV8_PINGTIMEOUT` | таймаут проверки разрыва соединений | 5000 |
| — | `SRV1CV8_KEYTAB` | keytab-файл Kerberos | `/opt/1cv8/x86_64/<версия>/usr1cv8.keytab` |
| `-daemon` | — | запуск в режиме «демона» (только Linux): фоновое приложение без управляющего терминала; сам по себе автозапуска не даёт. Так запускал SysV-скрипт. По документации в режиме «демона» отладка по HTTP не поддерживается [офиц., гл. 4.2.2.1] | — |
| `/resetServerAdmins`, `/resetClusterAdmins` | — | сброс паролей администраторов сервера / кластера (**8.5.4+**; V8Update называет команды, но не их синтаксис — ⚠ порядок применения смотреть в документации 8.5.4) | — |

Параметры `/instsrvc`, `/rmsrvc`, `/start`, `/stop`, `/usr`, `/pwd` (а также `/srvc /agent` в строке службы) — только Windows.

Замечания:

- **Диапазон по умолчанию.** В таблице переменных (и русской, и английской редакции гл. 4.2.2.4.3) для `SRV1CV8_RANGE` указано `1561:1590`, а в описании параметра `/range`, в описании кластера по умолчанию и в примерах — `1560:1591`. На практике агент, запущенный штатным юнитом, виден в `systemctl status` с `-range 1560:1591` (сборка 8.3.25.1374, публикации сообщества) — то есть `1561:1590` в таблице похоже на опечатку. Фактическое значение всегда смотрите в юните: `systemctl cat srv1cv8-<версия>@default`.
- С **8.3.26** параметры отслеживания разрыва соединений («Период проверки», «Таймаут проверки») можно менять без перезапуска — в свойствах кластера (`rac cluster update --ping-period … --ping-timeout …`); настройки кластера имеют приоритет над параметрами запуска, если хотя бы один из них ненулевой [офиц., V8Update 8.3.26]. Рекомендации документации: таймаут в 3–10 раз больше периода, период не меньше 1000 мс, одинаковые значения на всех серверах кластера.
- В документации 8.5.1 к `/regport` добавлено предупреждение: если на одном компьютере несколько кластеров, у каждого должен быть уникальный порт главного менеджера, иначе менеджеры с одинаковым портом считаются одним кластером с непредсказуемым поведением [офиц.].
- Агент, запущенный как приложение, останавливают сочетанием Ctrl+C.
- Про `-debug -http` и юнит: значение `-debug -http` в списке допустимых значений `SRV1CV8_DEBUG` есть, но там же сказано, что в режиме «демона» отладка по HTTP не поддерживается; как это соотносится со штатным юнитом, документация не поясняет — ⚠ проверять на стенде.

**Примеры** [офиц.]:

```bash
# Запуск как приложения (для отладки/экспериментов), данные в своём каталоге, отладка по HTTP
sudo -u usr1cv8 /opt/1cv8/x86_64/8.3.27.1688/ragent -d /home/usr1cv8/cluster_test -debug -http

# Два экземпляра сервера на одной машине: разные порты и разные каталоги данных
/opt/1cv8/x86_64/8.3.27.1688/ragent -port 1540 -regport 1541 -range 1560:1590 -d /home/usr1cv8/.1cv8/1C/srv1
/opt/1cv8/x86_64/8.3.27.1688/ragent -port 2540 -regport 2541 -range 2560:2590 -d /home/usr1cv8/.1cv8/1C/srv2
```

### 2.5. Менеджер кластера `rmngr` и рабочие процессы `rphost`

Вручную не запускаются — их порождает `ragent`. В списке процессов они видны с параметрами, по которым удобно диагностировать конфигурацию [практика]:

```bash
ps -eo pid,user,etimes,rss,args | grep -E '[r]agent|[r]mngr|[r]phost'
# Примерный вид (значения условные):
#  1201 usr1cv8  86400  45000 /opt/1cv8/x86_64/8.3.27.1688/ragent -d /home/usr1cv8/.1cv8/1C/1cv8 -port 1540 -regport 1541 -range 1560:1591 ...
#  1215 usr1cv8  86390 310000 /opt/1cv8/x86_64/8.3.27.1688/rmngr -port 1541 -host srv1c -range 1560:1591 ...
#  1302 usr1cv8  86380 920000 /opt/1cv8/x86_64/8.3.27.1688/rphost -range 1560:1591 -reghost srv1c -regport 1541 -pid <UUID> ...
```

- `etimes` — время жизни процесса в секундах, `rss` — резидентная память в КБ: по ним видно «распухшие» и недавно перезапущенные `rphost`.
- Параметр `-host`/`-reghost` показывает **имя**, под которым сервер зарегистрирован в кластере, — именно его получают клиенты.
- С 8.3.27 перезапуск рабочих процессов задаётся расписанием в формате cron (`rac cluster|server … --restart-schedule`; из шести полей cron используются первые пять: минута, час, день месяца, месяц, день недели, например `0 3 * * 1-5`), свойство «Интервал перезапуска» объявлено устаревшим; расписание рабочего сервера приоритетнее расписания кластера; процесс можно принудительно выключить (в V8Update — параметр `--turn-off` режима `process`; точную форму команды смотрите в `rac help process`) [офиц., V8Update 8.3.27]. В документации 8.5.1 уточнено: расписание перезапуска не влияет на резервные рабочие процессы.

### 2.6. Сервер администрирования `ras` и утилита `rac`

**`ras`** — посредник между средствами администрирования и агентом сервера. Один `ras` подключается только к одному агенту; к одному кластеру можно подключить несколько `ras`. `ras` соединяется с кластером только на время выполнения операции, поэтому при остановке/перезапуске кластера останавливать `ras` не нужно — кроме смены версии: **версия `ras` должна совпадать с версией кластера серверов**. Аутентификация ОС для администраторов через `ras`/`rac` не поддерживается [офиц., гл. 5.3.3].

Синтаксис [офиц., прил. 4, п. 4.13]:

```bash
# как приложение
/opt/1cv8/x86_64/8.3.27.1688/ras cluster --port=1545 localhost:1540
# как демон
/opt/1cv8/x86_64/8.3.27.1688/ras cluster --daemon --port=1545 localhost:1540
# с HTTP-шлюзом метрик в формате OpenMetrics (8.3.25+, требует лицензии КОРП);
# умолчания: адрес localhost, порт 1555, базовый путь /  — здесь шлюз открыт на всех интерфейсах
/opt/1cv8/x86_64/8.3.27.1688/ras cluster --daemon --port=1545 \
    --monitor-address=any --monitor-port=1555 --monitor-base=/ localhost:1540
```

| Параметр `ras cluster` | Назначение | По умолчанию |
|---|---|---|
| `cluster` | режим администрирования кластера серверов — **обязательное** слово | — |
| `--port=<порт>`, `-p <порт>` | порт, на котором `ras` принимает `rac` | 1545 |
| `--daemon` | работать демоном (Linux) | — |
| `--monitor-address=<адрес>` | адрес HTTP-шлюза показателей производительности (8.3.25+): `localhost`, `any`, IPv4 или IPv6 | `localhost` |
| `--monitor-port=<порт>` | порт HTTP-шлюза показателей производительности | **1555** |
| `--monitor-base=<путь>` | базовый путь публикации показателей, всегда начинается с `/` | `/` |
| `<host[:port]>` | адрес агента сервера | `localhost:1540` |

Для доступа к метрикам через `ras` используется аутентификация «1С:Предприятия» [офиц., V8Update 8.3.25].

С 8.3.21 в дистрибутив входит systemd-сценарий и для `ras` [офиц., V8Update 8.3.21 — без имени файла]. Имя файла юнита — `ras-<версия>.service` в каталоге версии [практика, два независимых источника: статья Selectel 2026 г. для 8.3.27.2074 и 1smonitor.ru; в документации 8.3.27 имя не приведено], подключается так же, как юнит сервера:

```bash
ls /opt/1cv8/x86_64/8.3.27.1688/*.service
sudo systemctl link /opt/1cv8/x86_64/8.3.27.1688/ras-8.3.27.1688.service
sudo systemctl enable --now ras-8.3.27.1688
systemctl cat ras-8.3.27.1688          # что именно запускается: порт ras и адрес агента
```

Это обычный юнит, не шаблон (без `@`). ⚠ Дословный текст штатного юнита `ras` в открытых источниках не найден; если агент слушает нестандартный порт (второй экземпляр), адрес агента для `ras` нужно переопределить через `systemctl edit ras-<версия>` — что именно переопределять (`ExecStart=` или переменные), смотрите в выводе `systemctl cat`.

**`rac`** — консольная утилита. Общий вид: `rac <режим> [команда] [параметры] [host:port сервера ras]` (по умолчанию `localhost:1545`). Вывод — пары `имя : значение`, объекты разделяются пустой строкой, код возврата 0 при успехе, ошибки — в stderr [офиц.]. Режимы: `agent`, `cluster`, `manager`, `server`, `process`, `service`, `infobase`, `connection`, `session`, `lock`, `rule`, `profile`, `counter`, `limit` и др.; точный список и параметры — `rac help`, `rac help <режим>` [практика; проверять справкой своей версии].

```bash
RAC=/opt/1cv8/x86_64/8.3.27.1688/rac
$RAC help                      # список режимов
$RAC cluster list              # кластеры: UUID, host, port, name
CL=$($RAC cluster list | awk '/^cluster/{print $3; exit}')
$RAC server  --cluster=$CL list           # рабочие серверы и их диапазоны портов
$RAC process --cluster=$CL list           # рабочие процессы: порт, pid, память, соединения
$RAC infobase --cluster=$CL summary list  # информационные базы
$RAC session --cluster=$CL list           # сеансы
```

Совместимость версий `rac` ↔ `ras` [офиц.]: 8.3.1–8.3.2, 8.3.3–8.3.4, 8.3.5–8.3.8 работают только внутри своей группы; **8.3.9 и новее совместимы между собой** (более старая `rac` работает с новым `ras` только в объёме возможностей своей версии). При этом **версия `ras` должна совпадать с версией кластера** — берите `ras` из каталога той же версии, что и работающий `ragent` [офиц., гл. 5.3.3.1].

Другие средства администрирования кластера:

- **MMC-консоль** «Администрирование серверов 1С:Предприятия» — только Windows; подключается к агенту Linux-сервера по `tcp`, порт 1540. Версия консоли должна соответствовать версии сервера. Сама не обновляется — «Действие → Обновить». Из консоли нельзя завершать соединения PostgreSQL и создавать/удалять хранилища двоичных данных [офиц.].
- **Стандартная функция «Управление серверами»** (идентификатор `ServersManagement`; меню «Функции для технического специалиста», нужен включённый «Режим технического специалиста») — кроссплатформенный аналог консоли в клиентском приложении. Работает **через сервер администрирования**: доступны только серверы, для которых развёрнут `ras` [офиц., гл. 6 руководства администратора 8.3.27]. ⚠ не подтверждено, в какой именно версии функция появилась (в документации 8.3.27 она есть). В 8.5.4 её и функцию «Управление лицензиями» можно запускать из командной строки клиента ключами `/ManageServers` и `/ManageLicenses` — без информационной базы и без клиентской лицензии [офиц., V8Update 8.5.4].
- **Программный доступ**: объекты администрирования встроенного языка (`АдминистрированиеСервера` и др.), Java-библиотека (на диске ИТС), COM-соединение — объект `V83.COMConnector` (в 8.5 — `V85.COMConnector`), только с Windows-клиента той же версии [офиц.].

### 2.7. Автономный сервер `ibsrv` и утилита `ibcmd`

**`ibsrv`** — специальный сервер для обслуживания **одной** информационной базы управляемого приложения: к нему подключаются тонкий, веб- и мобильный клиенты и конфигуратор, по HTTP и по TCP/IP (что доступно — определяется настройками шлюзов). Содержит встроенный веб-сервер. Вышел из статуса бета-версии в 8.3.23 [офиц.].

Особенности и ограничения [офиц.]:

- один автономный сервер — одна база; одну базу нельзя одновременно обслуживать автономным сервером и кластером (применение `ibsrv`/`ibcmd` к базе, работающей под кластером, **может разрушить базу**);
- только управляемое приложение (обычное приложение не поддерживается); подключение **толстого клиента по TCP/IP** не поддерживается;
- нет: внешних (COM) соединений, HTTPS «из коробки» (нужен обратный прокси), аутентификации ОС, сервисов интеграции, ботов системы взаимодействия, 1С:Аналитики, фоновой реструктуризации, управления через `ras` и через `V83.COMConnector`, графических средств управления; конфигурация из XML загружается только в иерархическом формате;
- на Linux не работает с MS SQL Server; 32-разрядная Windows не поддерживается;
- системные требования — как у кластера серверов; ставится вместе с кластером серверов;
- с одним каталогом данных в каждый момент работает либо один `ibsrv`, либо одна `ibcmd`;
- средств регистрации себя как службы нет: на Linux — `--daemon` + собственный systemd-юнит [практика], на Windows — `sc create`.

Основные параметры `ibsrv` [офиц., прил. 4, п. 4.9; полный список — `ibsrv --help`]:

| Параметр (синонимы) | Назначение | По умолчанию |
|---|---|---|
| `--data=<каталог>`, `-d <каталог>` | каталог данных сервера | Linux: `~/.1cv8/standalone-server` |
| `--config=<файл>`, `-c <файл>` | конфигурационный файл (YAML); расположения по умолчанию у него нет | — |
| `--daemon` | режим демона (только Linux) | — |
| `--name=<имя>`, `-n <имя>` | имя информационной базы | строковое представление идентификатора ИБ |
| `--dbms=<тип>` | `PostgreSQL`, `MSSQLServer`, `IBMDB2`, `OracleDatabase`; не указан — файловая база | файловая база |
| `--database-server=`, `--db-server=` | сервер СУБД | — |
| `--database-name=`, `--db-name=` | имя базы данных | — |
| `--database-user=`, `--db-user=` | пользователь СУБД | — |
| `--database-password=`, `--db-pwd=` | пароль пользователя СУБД | — |

| `--direct-range=<от:до>` | диапазон портов прямого соединения — аналог `/range` | **1560:1591** |
| `--direct-seclevel=<0\|1\|2>` | уровень безопасности прямого соединения | 0 |
| `--ssh-address=`, `--ssh-port=`, `--ssh-host-key=<файл>` | SSH-шлюз администрирования (для `ibcmd --remote`) | `localhost`, **1543** |
| `--debug=[none\|tcp\|http\|server]`, `-D` | отладка; `server` — внешний сервер отладки (`--debug-server-url=<url>`) | — |

Служебные каталоги (`--temp`, `--session-data`, `--log-data`, `--ftext-data`, `--ftext2-data`, `--openid-data`, `--stt-data`, `--users-data`, `--binary-storage-data`, `--clnt-notif-data`) по умолчанию — одноимённые подкаталоги каталога данных; файл блокировки — `lock.pid`.

Значения по умолчанию коротко: HTTP-публикация на `localhost:8314`, базовый путь `/` (веб-клиент — `http://localhost:8314`); прямое подключение по TCP — 1541 + 1560:1591; SSH — 1543; отладка по HTTP — 1550; метрики — 1555; **все адреса по умолчанию — `localhost`**, для доступа с других машин задают `any` или конкретный адрес [офиц.]. Умолчания прямого шлюза (1541, 1560:1591) совпадают с портами кластера по умолчанию, поэтому на машине, где уже работает кластер, автономному серверу нужно отключить прямой шлюз (`--disable-direct-gate`) или задать другие порты [вывод из умолчаний, не цитата документации]. Англоязычная редакция главы 7 называет каталог файловой базы по умолчанию `~/.1cv8/ss-data/db-data` — расхождение редакций; указывайте `--data` явно.

```bash
# Запуск демоном по готовому конфигурационному файлу
/opt/1cv8/x86_64/8.3.27.1688/ibsrv --daemon --config=/etc/1c/ibsrv-demo.yml --data=/var/lib/1c/ibsrv-demo
```

**`ibcmd`** — утилита администрирования: `ibcmd <режим> <команда> [<команда>] [--параметр[=значение]] [файл]`; параметры командной строки приоритетнее файла конфигурации; справка — `ibcmd help`, `ibcmd help <режим>`. Режимы утилиты: `server`, `infobase`, `config`, `extension`, `mobile-app`, `mobile-client`, `session`, `lock`, `eventlog`, `binary-data-storage` [офиц., прил. 4, п. 4.10]. Режимы подключения [офиц.]:

- автономно (offline): `--data=<каталог>` (`-d`) плюс параметры базы (`--dbms`, `--db-server`, `--db-name`, `--db-user`, `--db-pwd` или `-W`) либо `--config=<файл>`; нельзя, пока с этим каталогом данных работает запущенный `ibsrv`; режимы `session` и `lock` в offline недоступны;
- к локальному процессу: `--pid=<PID>` (`-p <PID>`);
- удалённо по SSH-шлюзу: `--remote=ssh://host:port` (`-r`); порт SSH-шлюза по умолчанию 1543.

Пользователь информационной базы, от имени которого выполняется операция, задаётся `--user=<имя>` (`-u`) и `--password=<пароль>` (`-P`). Не путайте короткие ключи: `-p` у `ibsrv` — порт HTTP, у `ibcmd` — PID.

```bash
IBCMD=/opt/1cv8/x86_64/8.3.27.1688/ibcmd
$IBCMD help; $IBCMD help server
# создать базу в PostgreSQL и загрузить в неё выгрузку .dt
$IBCMD infobase create --dbms=postgresql --database-server=localhost --database-name=demo \
       --database-user=postgres --request-database-password --create-database --restore=/tmp/demo.dt
# выгрузить базу в .dt (без активных соединений)
$IBCMD infobase dump --config=/etc/1c/ibsrv-demo.yml --data=/var/lib/1c/ibsrv-demo /backup/demo.dt
# загрузить конфигурацию и применить изменения
$IBCMD infobase config load  --config=/etc/1c/ibsrv-demo.yml --data=/var/lib/1c/ibsrv-demo /tmp/1Cv8.cf
$IBCMD infobase config apply --config=/etc/1c/ibsrv-demo.yml --data=/var/lib/1c/ibsrv-demo --force
# сеансы работающего автономного сервера
$IBCMD --pid=$(pidof ibsrv) session list
```

Имена параметров подключения к СУБД приведены в длинной форме (`--database-server`, `--database-name`, `--database-user`, `--database-password`, `--database-path`); равноправные краткие синонимы — `--db-server`, `--db-name`, `--db-user`, `--db-pwd`, `--db-path`, для запроса пароля — `--request-db-pwd` или `-W` [офиц., прил. 4, пп. 4.9 и 4.10.2]. В примерах самой документации формы смешаны (`--database-server=… --db-user=…`).

`ibcmd infobase dump`/`restore` работают с `.dt` и **не являются резервным копированием** (выгрузка при наличии соединений может дать нецелостный файл) — резервные копии делают средствами СУБД [офиц., гл. 7].

Полезные возможности по версиям [офиц., V8Update]: 8.3.20 — управление запущенным экземпляром (`--pid`/`-p`, `--remote`/`-r`), секции `gates|http` и `gates|ssh` в конфигурационном файле; 8.3.23 — `ibcmd infobase replicate` (перенос базы между СУБД без `.dt`; параметры `--target-dbms`, `--target-db-server`, `--target-db-name`, `--target-db-user`, `--target-create-database`); 8.3.25 — `ibcmd eventlog` (выгрузка журнала регистрации в XML/JSON без подключения к базе), HTTP-метрики (секция `monitor`); 8.3.27 — режим `binary-data-storage`; 8.5.1 — параметр числа потоков у команд группы `import`; 8.5.4 — `ibcmd config checksum`, `ibcmd config update`, `infobase config generation-id`, `--db-schema`.

Лицензирование [офиц., V8Update 8.3.20, раздел изменений после публикации версии]: серверная лицензия требуется при работе `ibcmd` в клиент-серверном варианте и при подключении к автономному серверу по SSH в клиент-серверном варианте; для файловой информационной базы и при работе `ibcmd` с базой без подключения к автономному серверу серверная лицензия не требуется. (Прежнее правило «файловая база — без лицензии до 3 одновременных сеансов» относится к более ранним сборкам.) ⚠ Формулировки V8Update для клиент-серверного варианта неоднозначны («ibcmd в клиент-серверном варианте» — нужна, «ibcmd без подключения к автономному серверу» — не нужна); при сомнениях ориентируйтесь на документацию своей версии.

### 2.8. Сервер хранилища конфигураций `crserver` и сервер отладки `dbgs`

- **`crserver`** — доступ разработчиков к хранилищу конфигураций по TCP (`tcp://host:1542/имя`) или по HTTP через веб-сервер (поэтому пакет `crs` зависит от `common`, `server` и `ws`) [офиц. — состав пакетов]. Запуск на Linux: `crserver -port 1542 -d /home/usr1cv8/repo` — параметры `-port` и `-d` и порт 1542 подтверждены практикой (образ `onec-crs` из `firstBitMarksistskaya/onec-docker`: `crserver -port 1542 -d /home/usr1cv8/.1cv8`, `EXPOSE 1542`); ключ `-daemon` (фоновый запуск) (сверено 10.10.2026 по полному тексту документации 8.3.27: в приложении 4 командной строки `crserver` действительно нет, утилита упомянута только в перечне файлов каталога версии, приложение 1) по-прежнему не подтверждён — в приложении 4 руководства администратора 8.3.27 командная строка `crserver` не описана (вероятно, она в руководстве разработчика — не проверено). Для службы надёжнее собственный systemd-юнит с `User=usr1cv8` без `-daemon` [практика].
- **`dbgs`** — сервер отладки для отладки по протоколу HTTP: и клиент, и рабочие процессы сами подключаются к нему (удобно через NAT/файрвол). Когда `dbgs` запускает сам кластер (агент с `-debug -http`), он слушает порт 1550 (меняется `-debugServerPort`). Самостоятельный запуск [офиц., прил. 4, п. 4.11]: `dbgs --addr=<адрес> --port=<порт>` (или `--range=<диапазон>`; при обоих действует `--range`), дополнительно `--password=<пароль>` или `--debugServerUsers=<файл>`, `--ownerPID=<PID>`, `--notify=<файл>`, `--daemon` (Linux), `--service` (Windows); порта по умолчанию у него нет. **Через `dbgs`, запущенный как служба или «демон», серверные предметы отладки клиент-серверных баз не отлаживаются** — только файловые базы и клиентские предметы отладки. В режиме «демона» агента отладка по HTTP по документации не поддерживается — на практике для отладки агент запускают как приложение (так сделано и в `1C-Company/docker_fresh`: `ragent -debug -http -d <каталог>`).
- **Конфигуратор в режиме агента** (`1cv8 DESIGNER <ИБ> /AgentMode …`) — управление конфигурацией по SSH/SFTP; порт по умолчанию **1543** (`/AgentPort`), по умолчанию слушает только `127.0.0.1` (для доступа извне — `/AgentListenAddress`); без `/AgentSSHHostKey <файл>` или `/AgentSSHHostKeyAuto` агент не запустится; один агент — одна база [офиц., прил. 7]. На сервере без графики конфигуратору нужен виртуальный дисплей (Xvfb) [практика].

### 2.10. Веб-сервер: модуль расширения и `webinst`

- Модуль расширения для Apache 2.4 на Linux — `wsap24.so` в каталоге версии; подключается директивой `LoadModule _1cws_module …/wsap24.so` (её добавляет `webinst`) [практика].
- Разрядность веб-сервера и платформы должна совпадать (на Linux 32-битная платформа с 64-битным Apache не поддерживается) [офиц.].
- Для Linux рекомендуется MPM **worker**; для файловых баз с фоновыми заданиями — `ServerLimit 1` [офиц.].
- Пользователю, от которого работает Apache (`www-data` в Ubuntu), нужны права чтения и исполнения на каталог версии платформы и чтения `default.vrd`; для файловой базы — права изменения каталога базы [офиц.].
- В **8.5.4 сняты с поддержки Apache 2.0 и 2.2** — у `webinst` удалены соответствующие ключи (в документации 8.3.27 это `-apache2` и `-apache22`; в тексте V8Update 8.5.4 они названы «-apache и -apache22»), остаётся `-apache24` [офиц., V8Update 8.5.4].

```bash
# Публикация клиент-серверной базы demo на Apache 2.4 (под root)
sudo /opt/1cv8/x86_64/8.3.27.1688/webinst -publish -apache24 -wsdir demo -dir /var/www/demo \
     -connstr "Srvr=srv1c;Ref=demo;" -confpath /etc/apache2/apache2.conf
sudo systemctl restart apache2
# Удаление публикации
sudo /opt/1cv8/x86_64/8.3.27.1688/webinst -delete -apache24 -wsdir demo -dir /var/www/demo -confpath /etc/apache2/apache2.conf
```

Ключи `webinst` [офиц., прил. 4, п. 4.14]: `-publish` (по умолчанию) / `-delete`; тип сервера — ровно один из `-apache24` (Apache 2.4), `-apache22` (2.2), `-apache2` (2.0), `-iis` (только Windows); неверно указанная версия Apache делает публикацию неработоспособной; `-wsdir <имя>` — имя публикации (виртуальный каталог, латиницей); `-dir <каталог>` — физический каталог с `default.vrd` (должен существовать); `-connstr "<строка соединения>"`; `-confpath <файл конфигурации Apache>` (для Apache 2.4 можно не указывать); `-descriptor <шаблон .vrd>` (существующий `default.vrd` полностью замещается шаблоном); `-osauth` (только IIS). Для удаления публикации достаточно `-delete` и `-wsdir`. Имя параметра и значение разделяются пробелом, значение с пробелами — в кавычках. Запуск — от root.

Что должно быть открыто:

- **клиенты → сервер 1С**: 1541 и весь диапазон 1560–1591 (плюс 1540 для машин администраторов с MMC-консолью). Через веб-сервер — только 80/443 до веб-сервера;
- **веб-сервер → сервер 1С**: 1541, 1560–1591;
- **сервер 1С → СУБД**: 5432;
- **между рабочими серверами одного кластера**: 1540, 1541, диапазоны рабочих процессов — в обе стороны;
- **администратор → `ras`**: 1545 (лучше только из админской сети или только `localhost` + SSH);
- **сервер мониторинга → HTTP-шлюз метрик**: 1555 — только если шлюз включён на внешнем адресе (`--monitor-address`), по умолчанию он доступен лишь с `localhost`;
- **отладка**: 1550 (HTTP) или дополнительные порты из диапазона (TCP-отладка) — только на стендах разработки.

### 3.2. Команды проверки

```bash
# Что слушают процессы 1С (нужен root, чтобы видеть имена процессов)
sudo ss -tlnp | grep -E 'ragent|rmngr|rphost|ras|dbgs|crserver|ibsrv'
# Проверка доступности с клиента Linux
nc -zv srv1c 1541 && nc -zv srv1c 1560
# Проверка с Windows-клиента (PowerShell)
#   Test-NetConnection srv1c -Port 1541
# Разрешить в ufw доступ из подсети 192.168.1.0/24
sudo ufw allow proto tcp from 192.168.1.0/24 to any port 1540,1541,1560:1591 comment '1C server'
sudo ufw allow proto tcp from 192.168.1.10   to any port 1545 comment '1C RAS (admin only)'
sudo ufw status numbered
```

- `ss -tlnp`: `-t` TCP, `-l` только слушающие, `-n` без разрешения имён, `-p` показать процесс.
- `ufw allow proto tcp from <сеть> to any port <список>`: список портов через запятую, диапазон через двоеточие (при списке/диапазоне обязателен `proto`).

### 3.3. Как менять порты

Через drop-in systemd-юнита (подробнее — раздел 6) [офиц.]:

```bash
sudo systemctl edit srv1cv8-8.3.27.1688@default
# в открывшемся редакторе:
#   [Service]
#   Environment=SRV1CV8_PORT=2540
#   Environment=SRV1CV8_REGPORT=2541
#   Environment=SRV1CV8_RANGE=2560:2591
sudo systemctl restart srv1cv8-8.3.27.1688@default
```

Правила [офиц.]:

- у разных агентов на одной машине должны различаться порты агентов и каталоги данных; у разных кластеров — порты кластеров; диапазоны рабочих процессов не должны пересекаться;
- **порты уже работающего экземпляра «на лету» поменять нельзя**: `-regport`/`-range` действуют только на кластер, создаваемый по умолчанию при пустом каталоге данных. Порт существующего кластера и диапазоны рабочих серверов записаны в реестре кластера. Официальный путь — создать новый экземпляр (новые порты + новый каталог данных), зарегистрировать в нём базы, перевести пользователей, старый остановить и удалить вместе с данными кластера;
- при нестандартном порту кластера клиенты указывают его в адресе сервера: `Srvr="srv1c:2541";Ref="demo";`.

### 4.2. Каталог установки

- **С 8.3.18**: `/opt/1cv8/<arch>/<A.B.C.D>/`, где `<arch>` — `x86_64`, `i386`, `arm64` (ARM64) или `e2kv4` (Эльбрус) [офиц., прил. 1]. В 8.3.18 реализована одновременная установка нескольких версий, в том числе отличающихся только четвёртой цифрой, и изменено расположение скрипта запуска `srv1cv83` и его конфигурационного файла [офиц., V8Update 8.3.18]. - **До 8.3.18**: `/opt/1C/v8.3/x86_64/` (32-бит — `/opt/1C/v8.3/i386/`), одна версия на компьютер; конфигурационные файлы — `/opt/1C/v8.3/x86_64/conf/`; служба — `/etc/init.d/srv1cv83`, параметры в `/etc/sysconfig/srv1cv83` (RPM) или в самом скрипте (DEB); пакеты `1c-enterprise83-common|server|ws|…` [офиц. — старая инструкция для 8.3.13].

### 4.3. Каталог данных сервера (кластера)

- По умолчанию `/home/usr1cv8/.1cv8/1C/1cv8` (кратко `~/.1cv8/1C/1cv8`); меняется параметром `-d` / переменной `SRV1CV8_DATA` [офиц.].
- На Windows аналог — `<каталог установки>\srvinfo` (служба) или `%LOCALAPPDATA%\1C\1cv8` (приложение). Упоминания `srvinfo` в инструкциях относятся к Windows; на Linux каталог называют так только по привычке.
- Что здесь хранится: реестр сервера и кластера, **журналы регистрации всех баз**, индексы полнотекстового поиска, сеансовые данные, данные сервисов кластера, встроенное хранилище двоичных данных (если не вынесено).
- Всё это **не входит в резервную копию СУБД** — журнал регистрации и хранилище двоичных данных копируются отдельно [офиц.].
- Агент при каждом изменении способа запуска или учётной записи должен получать тот же путь; если реестр не найден — молча создаётся новый пустой кластер [офиц.].
- С **8.3.26** (только КОРП) для некоторых сервисов кластера можно задать альтернативные каталоги данных — через объект «настройки сервисов» (консоль, «Управление серверами», `rac`, встроенный язык). Перенос данных — вручную при остановленном кластере; для журналов регистрации и хранилища двоичных данных перенос обязателен, иначе кластер может стать неработоспособным; новые каталоги применяются только при запуске кластера [офиц., V8Update 8.3.26 и гл. 2.2.3.2].

```bash
sudo -u usr1cv8 ls -la /home/usr1cv8/.1cv8/1C/1cv8/
sudo du -sh /home/usr1cv8/.1cv8/1C/1cv8/reg_1541/* | sort -h | tail      # что занимает место
sudo find /home/usr1cv8/.1cv8/1C/1cv8/reg_1541 -maxdepth 2 -name 1Cv8Log -exec du -sh {} +   # размеры журналов регистрации
# соответствие «UUID каталога ↔ имя базы»
/opt/1cv8/x86_64/8.3.27.1688/rac infobase --cluster=<UUID кластера> summary list
```

Остановить сервер перед копированием/переносом каталога данных; права после переноса: `chown -R usr1cv8:grp1cv8 <каталог>`.

### 4.4. Конфигурационные файлы (`conf`)

| Файл | Назначение |
|---|---|
| `conf.cfg` | общие параметры платформы: расположение общих конфигурационных файлов, параметры Java для полнотекстового поиска (`FtsJavaOpts`), каталоги моделей, параметры LibreOffice (8.5.4: `LibreOfficePort`, `LibreOfficeLocalPath` …), внешнее управление сеансами и т. п. |
| `logcfg.xml` | настройка технологического журнала (перечитывается каждые 60 с). Без него ведётся только журнал «по умолчанию» в `~/.1cv8/1C/1cv8/logs` |
| `nethasp.ini` | параметры поиска сетевых ключей HASP (до 8.5.4): секция `[NH_TCPIP]`, параметры `NH_SERVER_ADDR`, `NH_PORT_NUMBER` (475), `NH_USE_BROADCAST`. На Linux ищется в каталоге конфигурационных файлов платформы, затем в текущем каталоге, в домашнем каталоге пользователя и в `/etc` [офиц., прил. 3] |
| `rclic.cfg` | конфигурационный файл клиента менеджера лицензий (8.5.4+); ⚠ расположение и состав параметров не подтверждены |
| `swpuser.ini` | пользователи ОС, от имени которых запускать рабочие процессы (`user=`) и менеджеры кластера (`rmngr_user=`) вместо учётной записи агента; параметр `registry=` переносит реестр кластера. **Лежит в каталоге данных сервера, рядом с файлом списка кластеров `1cv8wsrv.lst`.** На Linux для этого агент должен работать от `root`, параметры `password`/`rmngr_pass` игнорируются, а пользователям `rphost`/`rmngr` нужны существующий профиль ОС и полный доступ к `/var/1C` [офиц., прил. 3, п. 3.29] |
| `1cv8conn.pfl` | список центральных серверов в разрезе баз и данные лицензирования; лежит в `~/.1cv8/1C/1cv8` пользователя процесса [офиц.] |
| `location.cfg` | в `~/.1cv8/1C/1cv8/`; параметр `location` задаёт запасной каталог поиска (в т. ч. лицензий) [офиц.] |
| `debugcfg.xml`, `comcntrcfg.xml`, `inetcfg.xml` и др. | отладка, COM (не для Linux), прокси |

Где платформа ищет конфигурационные файлы на Linux — **в таком порядке** [офиц., прил. 1 руководства администратора 8.3.27, п. 1.3.2]:

1. `/opt/1cv8/<arch>/<A.B.C.D>/conf` — каталог `conf` конкретной версии (именно туда монтируются `conf.cfg`, `logcfg.xml`, `nethasp.ini` в `1C-Company/docker_fresh`);
2. `/opt/1cv8/conf` — общий для всех версий каталог корня установки;
3. `~/.1cv8/1C/1cv8/conf` — в домашнем каталоге пользователя, от имени которого работает приложение (для сервера — `/home/usr1cv8/.1cv8/1C/1cv8/conf`);
4. каталог из параметра `ConfLocation` файла `conf.cfg` конкретной версии.

Отсюда правила: настройка «для всех версий на этой машине» (типично — `logcfg.xml`) кладётся в `/opt/1cv8/conf`, и её не нужно переносить при обновлении платформы; настройка только для одной версии — в `conf` каталога этой версии (он исчезает при удалении версии). В каталоге `conf` версии может лежать не сам набор файлов, а только `conf.cfg` с `ConfLocation`. Практическая проверка:

```bash
ls -ld /opt/1cv8/conf /opt/1cv8/x86_64/*/conf /home/usr1cv8/.1cv8/1C/1cv8/conf 2>/dev/null
sudo find /opt/1cv8 /home/usr1cv8/.1cv8 -name 'conf.cfg' -o -name 'logcfg.xml' -o -name 'nethasp.ini' 2>/dev/null
```

### 4.5. Лицензии

- `/var/1C/licenses/` — файлы программных лицензий `*.lic` сервера; каталог создаётся при установке: владелец `root` (`rwx`), группа `grp1cv8` (`rwx`), остальные — `r-x`. В группу `grp1cv8` должны входить все учётные записи, от имени которых работают процессы кластера и запускаются клиентские приложения на этом компьютере; у членов группы должен быть доступ **на запись** к файлам лицензий [офиц., гл. 10.3.7.1]. (В `docker_fresh` на каталог делают `chown -R usr1cv8:grp1cv8` — тоже работает.)
- Порядок поиска файлов `*.lic` на Linux [офиц., гл. 10.3.8.3]: (1) `/opt/1cv8/<arch>/<A.B.C.D>/conf`; (2) `/opt/1cv8/conf`; (3) `~/.1cv8/conf` (домашний каталог пользователя процесса — обратите внимание: не `~/.1cv8/1C/1cv8/conf`); (4) каталог из `ConfLocation` в `conf.cfg` версии; (5) `/var/1C/licenses`. Если нигде не найдено — запасной каталог `~/.1cv8/1C/1cv8/` (или каталог из `location.cfg`, параметр `location`). Составляется общий список файлов (в том порядке, в каком их вернула ОС) и перебирается до первой подходящей лицензии.
- Куда помещает файл мастер получения лицензии: «на сервер» — `/var/1C/licenses`; «для текущего пользователя» — `~/.1cv8/conf`; вариант «для всех пользователей компьютера» на Linux не поддерживается (по соседнему примечанию документации — доступен только при активации от `root`).
- **Не держите один и тот же файл лицензии в нескольких каталогах поиска** и не оставляйте старый файл при повторной активации тем же пин-кодом — платформа может счесть это нарушением и занести лицензию в чёрный список; перед повторным получением старый файл уберите в каталог, где лицензии не ищутся [офиц.].
- `1cv8conn.pfl` — служебный файл со списком центральных серверов в разрезе баз и другими данными лицензирования; лежит в `~/.1cv8/1C/1cv8`; процессам кластера нужны права на его создание, чтение и изменение [офиц.].

```bash
sudo ls -l /var/1C/licenses/
sudo -u usr1cv8 test -r /var/1C/licenses && echo OK
```

### 4.7. Временные файлы, журналы, дампы

- **Временные файлы** сервера — в `/tmp`; пользователю сервера нужны права на каталог временных файлов [офиц.]. Чтобы вынести (например, на быстрый диск), задают `TMPDIR` для процесса сервера. Официальная (старая) инструкция — через `~/.bash_profile` пользователя сервера; для systemd-юнита надёжнее drop-in [практика]:
  ```bash
  sudo install -d -o usr1cv8 -g grp1cv8 -m 750 /var/tmp/1c
  sudo systemctl edit srv1cv8-8.3.27.1688@default     # добавить:  [Service]  /  Environment=TMPDIR=/var/tmp/1c
  sudo systemctl restart srv1cv8-8.3.27.1688@default
  ```
  Если каталог лежит в `/tmp`, исключите его из автоочистки (`systemd-tmpfiles`, в старых системах `tmpwatch`).
- **Технологический журнал**: каталог задаётся в `logcfg.xml` (типично `/var/log/1c/…`, владелец `usr1cv8`); без настройки ведётся только журнал «по умолчанию» (системные события уровня `Error`, хранение 24 часа) в `~/.1cv8/1C/1cv8/logs` (по приложению 3 — `~/.1cv8/logs`; проверьте оба каталога) [офиц.].
- **Журнал регистрации**: `<каталог кластера>/<UUID базы>/1Cv8Log`. Форматы: последовательный (`.lgf` + `.lgp`) и SQLite (`.lgd`); для новых баз с 8.3.22 формат SQLite недоступен [офиц.].
- **Дампы**: на Linux формирование дампов настраивается средствами ОС, а не `logcfg.xml`; по умолчанию выключено [офиц.]. Нужны `ulimit -c unlimited` для процесса (в systemd — `LimitCORE=infinity` в drop-in [практика]) и шаблон имени:
  ```bash
  echo 'kernel.core_pattern = /var/crash/core.%e.%p' | sudo tee /etc/sysctl.d/60-1c-core.conf
  sudo sysctl --system
  ```
  С 8.3.27 механизм мониторинга кластера завершает зависший процесс сигналом `SIGABRT` (раньше `SIGSEGV`; теперь `SIGSEGV` означает именно критическую ошибку приложения) [офиц., V8Update 8.3.27].

  Подводные камни [практика]: каталог из `core_pattern` должен существовать и быть доступен на запись пользователю `usr1cv8` (проверьте `ls -ld /var/crash`; надёжнее завести отдельный каталог: `sudo install -d -o usr1cv8 -g grp1cv8 -m 750 /var/lib/1c-cores` и указать его в `core_pattern`); дампы `rphost` бывают размером в гигабайты — следите за местом; в Ubuntu служба `apport` при старте сама записывает в `kernel.core_pattern` конвейер `|/usr/share/apport/apport …` и перекрывает значение из `sysctl.d` — проверьте `cat /proc/sys/kernel/core_pattern` после перезагрузки и при необходимости отключите её (`sudo systemctl disable --now apport`) ⚠ поведение `apport` на конкретной версии Ubuntu Server проверьте на месте.

## 5. Пользователь `usr1cv8` и группа `grp1cv8`

- Установщик серверных компонентов создаёт пользователя ОС **`usr1cv8`** — от его имени работают `ragent`, `rmngr`, `rphost` (и `ras`, если запускать штатным юнитом) — и группу **`grp1cv8`** («при установке создаётся группа `grp1cv8`») [офиц.: руководство 8.3.27, гл. 3 и гл. 10.3.7.1; подтверждается `1C-Company/docker_fresh`]. В тексте документации пользователь местами назван `USR1CV8` (общий раздел о правах) и `usr1cv83` (диалог активации лицензии «на сервер») — это наследие; фактическое имя на Linux — `usr1cv8`.
- Домашний каталог `/home/usr1cv8` — в нём по умолчанию данные кластера.
- Необходимые права [офиц.]: полные права на каталог данных кластера; чтение каталога временных файлов; создание/чтение/изменение файла `1cv8conn.pfl` для рабочих процессов и менеджеров; членство в `grp1cv8` и запись в `/var/1C/licenses` для всех учётных записей, от имени которых работают процессы кластера. Дополнительно [практика]: доступ к каталогу технологического журнала и к каталогам обмена, если прикладной код работает с файлами на сервере.
- Если рабочие процессы запускаются от отдельного пользователя через `swpuser.ini`, этому пользователю **не** дают доступ к каталогу данных кластера (рекомендация безопасности) [офиц.]. На Linux схема с `swpuser.ini` требует запуска агента от `root` (пароли из файла игнорируются); если агент запущен от суперпользователя, а `swpuser.ini` не задан, весь кластер работает с правами администратора — документация называет это недопустимым для промышленных систем [офиц., прил. 3].
- В старых версиях 8.1/8.2 пользователи назывались `usr1cv81`/`usr1cv82`, группы `grp1cv81`/`grp1cv82` — встречается в старых инструкциях.

```bash
id usr1cv8                                   # uid, gid, группы
getent passwd usr1cv8                        # домашний каталог и оболочка
sudo -u usr1cv8 -H bash -lc 'echo $HOME; ulimit -n; locale'   # окружение, в котором работает сервер
ps -o user=,group=,pid=,args= -C ragent,rmngr,rphost          # от кого реально запущены процессы
sudo chown -R usr1cv8:grp1cv8 /home/usr1cv8/.1cv8 /var/1C/licenses   # вернуть владельца после копирования под root
sudo usermod -aG grp1cv8 www-data            # [практика] дать Apache доступ к файлам группы (например, к общим логам)
```

Типовые задачи с правами [практика]: каталог технологического журнала и каталоги обмена создавать с владельцем `usr1cv8:grp1cv8`; сетевые ресурсы Windows монтировать с `uid=usr1cv8,gid=grp1cv8`; не запускать `ragent` вручную под `root` — он создаст файлы, которые потом не прочитает `usr1cv8`.

## 6. Служба сервера: systemd-юниты (8.3.21+)

Установщик **не** включает автозапуск — это делает администратор, причём заново после каждой смены версии [офиц., V8Update 8.3.21].

```bash
VER=8.3.27.1688
# 1) зарегистрировать шаблон юнита из каталога версии
sudo systemctl link /opt/1cv8/x86_64/$VER/srv1cv8-$VER@.service
# 2) включить автозапуск и запустить экземпляр default
sudo systemctl enable --now srv1cv8-$VER@default
# 3) проверить
systemctl status srv1cv8-$VER@default --no-pager
journalctl -u srv1cv8-$VER@default -n 50 --no-pager
systemctl cat srv1cv8-$VER@default           # фактическое содержимое юнита и drop-in'ов
```

- `systemctl link <путь>` — делает юнит из произвольного каталога известным systemd (симлинк в `/etc/systemd/system`).
- `@default` — имя экземпляра шаблонного юнита; имя произвольное, `default` — по умолчанию.
- Управление: `systemctl start|stop|restart|status|enable|disable srv1cv8-<версия>@<экземпляр>`.
- На CentOS 7 требовался обход: `ln /opt/1cv8/x86_64/$VER/srv1cv8-$VER@{,default}.service` и `systemctl link …@default.service` [офиц.]; для Ubuntu не нужно.
- На Эльбрусе вместо systemd — init-скрипт `srv1cv83` из каталога версии (копируется в `/etc/init.d/<имя>`, конфигурация `srv1cv83.conf` → `/etc/default/<имя>` для DEB или `/etc/sysconfig/<имя>` для RPM; команды `start|stop|restart|status|info`) [офиц.].

Изменение параметров — только через drop-in (сам файл в `/opt/1cv8/...` перезаписывается при установке) [офиц.]:

```bash
sudo systemctl edit srv1cv8-$VER@default
# [Service]
# Environment=SRV1CV8_DATA=/srv/1c/cluster
# Environment=SRV1CV8_DEBUG=-debug
# Environment=SRV1CV8_SECLEV=0
sudo systemctl restart srv1cv8-$VER@default
systemctl show srv1cv8-$VER@default -p Environment
```

Второй экземпляр сервера на той же машине (официальный пример):

```bash
sudo systemctl edit srv1cv8-$VER@2xports
# [Service]
# Environment=SRV1CV8_DATA=/home/usr1cv8/.1cv8/1C/1cv8_2xports
# Environment=SRV1CV8_PORT=2540
# Environment=SRV1CV8_REGPORT=2541
# Environment=SRV1CV8_RANGE=2560:2591
sudo systemctl enable --now srv1cv8-$VER@2xports
```

Обновление версии сервера на Linux (схема) [офиц., гл. 6]: установить новую версию рядом → запретить новые сеансы, сделать резервные копии, завершить сеансы → остановить и отключить юнит старой версии → `systemctl link` + `enable --now` юнита новой версии (с теми же `SRV1CV8_*`, т. е. перенести drop-in) → обновить публикации на веб-серверах (`webinst` новой версии) и перезапустить Apache → обновить клиентов → снять запрет сеансов → позже удалить старую версию `uninstaller-full`.

```bash
OLD=8.3.26.1540; NEW=8.3.27.1688              # номера условные
sudo systemctl disable --now srv1cv8-$OLD@default
sudo systemctl disable --now ras-$OLD 2>/dev/null || true     # ras старой версии с новым кластером работать не должен
sudo mkdir -p /etc/systemd/system/srv1cv8-$NEW@default.service.d
sudo cp /etc/systemd/system/srv1cv8-$OLD@default.service.d/override.conf \
        /etc/systemd/system/srv1cv8-$NEW@default.service.d/ 2>/dev/null || true
sudo systemctl link /opt/1cv8/x86_64/$NEW/srv1cv8-$NEW@.service
sudo systemctl daemon-reload
sudo systemctl enable --now srv1cv8-$NEW@default
sudo systemctl link /opt/1cv8/x86_64/$NEW/ras-$NEW.service && sudo systemctl enable --now ras-$NEW
ps -eo pid,user,args | grep '[r]agent'        # убедиться: агент новой версии и с прежним каталогом -d
```

Юниты привязаны к номеру версии, а общие конфигурационные файлы — нет: то, что лежит в `/opt/1cv8/conf` (например, `logcfg.xml`), продолжит действовать для новой версии, а то, что лежало в `conf` каталога старой версии (в т. ч. `usr1cv8.keytab` в самом каталоге версии), нужно перенести вручную [вывод из порядка поиска конфигурационных файлов].

### 7.3. Политика поддержки версий

- Исправления выходят в виде новых сборок для ограниченного набора актуальных версий. На 10.2026 это 8.3.27 и версии 8.5. Формальный регламент сроков поддержки (сколько версий и как долго) в открытых источниках найти не удалось — ⚠ уточнять по информационным письмам фирмы «1С» и порталу ИТС.
- Дистрибутивы платформы ПРОФ и выше доступны при действующем договоре 1С:ИТС [офиц., письмо № 32567].
- Практическое правило [практика]: для новой инсталляции брать последнюю сборку версии, **рекомендованной поставщиком конфигурации** (минимальная версия платформы указана в описании релиза конфигурации), а не просто самую новую. На 10.2026 консервативный выбор — 8.3.27 последней сборки; 8.5.1 — если её требует или рекомендует конфигурация.
- Тестовые версии (в т. ч. «для ознакомления») в промышленную эксплуатацию не ставят.

### 7.4. Режим совместимости конфигурации

- Свойство конфигурации «Режим совместимости» фиксирует поведение платформы и формат хранения данных на уровне указанной версии. Значения: 8.1 (снято в 8.5.4), 8.2.13, 8.2.16, 8.3.1 … 8.3.27, 8.5.1 (добавлено в 8.5.4), «Не использовать» [офиц.].
- Каждая версия платформы добавляет значение для предыдущей: 8.3.19 → «Версия 8.3.18», …, 8.3.24 → «Версия 8.3.23», 8.5.4 → «Версия 8.5.1» [офиц.].
- Пока режим совместимости не выше версии N, базу можно открыть платформой N и новее. Повышение режима (или «Не использовать») меняет структуру объектов БД; после этого старые версии платформы базу не откроют, пока режим не вернут и не выполнят реструктуризацию [офиц.].
- Для администратора: **обновление платформы на сервере само по себе режим совместимости не меняет** — его меняет разработчик/обновление конфигурации. Перед откатом платформы проверьте режим совместимости (Конфигуратор → свойства конфигурации).
- Не путать с совпадением версий клиента и сервера: в клиент-серверном варианте сборки клиента и сервера должны совпадать полностью; тонкий клиент умеет обновляться автоматически с сервера/веб-сервера (на ARM64 и Эльбрусе автообновление не поддерживается) [офиц. — ограничения; практика].

- ARM64 и Эльбрус: сервер только с лицензией КОРП (исключение из перечня ограничений ПРОФ: на компьютерах с процессорами Apple работа под ПРОФ доступна — это относится к клиентам на macOS); аппаратные ключи не поддерживаются; автообновление клиента не поддерживается; нет MS SQL Server и IBM Db2 (на Эльбрусе также Oracle, Дата акселератора, локального распознавания речи); установка — пакетами deb/rpm (установщик `.run` работает только на x86/x86-64); каталоги установки — `/opt/1cv8/arm64/<версия>` и `/opt/1cv8/e2kv4/<версия>`; служба: на ARM64 — systemd, на Эльбрусе — init-скрипт `srv1cv83`.
- macOS и Windows on ARM для сервера не поддерживаются.

В V8Update 8.5.4 для полнотекстового поиска v2 упомянут диапазон версий Java «от 1.8 до 17» — ⚠ точную формулировку и верхнюю границу сверить по документации 8.5.4.
- **LibreOffice** на серверах кластера — для просмотра офисных документов в 8.5.4+ (параметры `conf.cfg`: `LibreOfficeLocalPath`, `LibreOfficeNumThreads`, `LibreOfficePort`) [офиц., V8Update 8.5.4].
- Клиенту на Linux дополнительно нужны GTK 3, WebKit2GTK и др. (в 8.3.24+ WebKit2 берётся из ОС) — на сервере без графики не требуется.

```bash
unzip server64_8_3_27_1688.zip -d /tmp/1c && cd /tmp/1c
chmod +x setup-full-8.3.27.1688-x86_64.run
# тихая установка сервера, веб-расширения, средств администрирования, русского интерфейса
sudo ./setup-full-8.3.27.1688-x86_64.run --mode unattended \
     --enable-components server,ws,server_admin,liberica_jre,ru
```

- `--mode unattended` — без вопросов; `--enable-components <список>` — идентификаторы компонентов через запятую (перечень — в разделе 2.1).
- `installAsRoot` — обёртка: проверяет права root, при необходимости запрашивает пароль и запускает первый найденный `setup-*.run` в графическом режиме; равнозначно `sudo ./setup-*.run`.
- В официальном `docker_fresh` используется набор `client_full,server,liberica_jre,ws,ru,…`.

Типовые наборы [офиц., «Типовые сценарии установки»]: рабочий сервер — `server` (+`server_admin`, +`ws` для веб-доступа); веб-сервер на отдельной машине — `ws`; сервер хранилища — `config_storage_server`; рабочее место — `client_full` или `client_thin`/`client_thin_fib`.

### 9.3. Учебная версия и лицензия разработчика

**«1С:Предприятие 8.3. Версия для обучения программированию»** — бесплатный дистрибутив (скачивается с v8.1c.ru, есть коробочный вариант), лицензия не нужна. Ограничения [офиц.]:

- нельзя использовать для реального учёта; нельзя собирать мобильные приложения для публикации;
- **клиент-серверный вариант не поддерживается**; РИБ, COM-соединение, хранилище конфигураций, функции поставки — не поддерживаются;
- нет паролей и аутентификации ОС; одно соединение с базой;
- лимиты данных: 2000 записей в таблицах счетов и основных таблицах объектов, 1000 строк в табличных частях, 2000 записей в наборах, 200 записей из внешних источников;
- печать и сохранение табличных документов — только в режиме конфигуратора; в режиме 1С:Предприятия нельзя скопировать больше одной ячейки табличного документа; нет локального распознавания речи; работает медленнее коммерческой версии.

Для стенда «сервер 1С + PostgreSQL» учебная версия **не подходит**. Подходит **лицензия разработчика (community)** [офиц.]:

- бесплатно, после полной регистрации на developer.1c.ru (с подтверждением телефона); платформа 8.3.23+; только программная;
- активируется на обычном (коммерческом) дистрибутиве; покрывает и клиент, и сервер, в том числе на разных компьютерах;
- действует неделю, продлевается автоматически при наличии интернета;
- лимиты: до 3 сеансов прямого подключения на базу, 1 сеанс через веб-сервер, 1 мобильный клиент, 1 сеанс 1С:Аналитики; один рабочий сервер в кластере (при добавлении второго — ошибка); только разработка и тестирование, не для реальной эксплуатации;
- лицензии разработчика не суммируются; в одной базе — не более 2 разных лицензий разработчика; привязка к аппаратному ключу невозможна; к кластеру, у которого серверной лицензией служит лицензия разработчика, нельзя подключаться с клиентскими лицензиями ПРОФ/КОРП; используется, только если не найдена никакая другая лицензия [офиц., гл. 1.6.3.6 руководства администратора];
- отправляет статистику использования возможностей платформы.

| **Основная поставка** | платформа + конфигурация + 1 рабочее место | программная (пин-код) или USB-ключ |
| **Клиентская лицензия** | право работы дополнительного рабочего места (одновременного сеанса); номиналы: 1, 5, 10, 20, 50, 100, 300, 500 (1000 — комплект из двух по 500) [офиц., гл. 10: маркировка ключей] | программная или HASP (локальный/сетевой ключ) |
| **Серверная лицензия** | право запуска сервера 1С на одном компьютере (любое число баз). Для кластера из нескольких машин — на каждую | программная или HASP (серверный ключ) |
| **Лицензия 1С:Аналитики**, расширения, лицензия на сервер взаимодействия, лицензия на тестирование бета-функций | специальные случаи | программные |
| **Базовая версия** | 1 пользователь, без клиент-сервера, без веб-клиента, без расширений | программная, привязана к компьютеру |

- Клиентские лицензии может раздавать сам сервер 1С (сервис лицензирования кластера) — тогда их активируют на сервере, и они расходуются по одной на сеанс [офиц./практика].
- Программные и аппаратные лицензии можно использовать одновременно с одной базой (с 8.2.10) [офиц.].
- Программная лицензия привязывается либо к ключу HASP, либо к **ключевым параметрам компьютера** (на ВМ — к параметрам ВМ) [офиц., гл. 10.3.1.4]: наименование и версия ОС (**в Linux при проверке не анализируются**), сетевое имя компьютера, модель материнской платы, объём оперативной памяти, тип и версия BIOS, список процессоров и их параметры, список сетевых адаптеров и их MAC-адреса, список жёстких дисков и их параметры (серийный номер и дата установки ОС — только Windows). Из сравнения сетевых адаптеров исключаются Bluetooth, адаптеры USB/IEEE 1394, программные адаптеры WAN и RAS, адаптеры без MAC-адреса и без данных `VEN_`/`DEV_`; внешние накопители USB/IEEE 1394 не учитываются.
- Что считается изменением [офиц., гл. 10.3.1.7]: анализируется только **удаление** устройств, не добавление (второй сетевой адаптер добавить можно, заменить единственный — нельзя); оперативную память можно увеличивать, но нельзя уменьшать ниже объёма на момент активации; параметры опрашиваются не чаще раза в сутки. Изменение хотя бы одного ключевого параметра (в т. ч. имени хоста, MAC, состава vCPU или дисков, миграция ВМ) требует повторной активации **новым** пин-кодом — в серверном комплекте пин-кодов всего 3. Рекомендации документации для ВМ: размещать сервис лицензирования на физической машине или ВМ с фиксированными характеристиками либо привязывать программную лицензию к ключу HASP.
- Практическое следствие для Linux [практика]: добавление виртуальных интерфейсов (Docker, VPN) по правилу «анализируется только удаление» лицензию не ломает, но если лицензию активировали при уже существовавшем виртуальном интерфейсе с MAC-адресом, а потом он исчез (удалили Docker, сменился MAC моста), привязка может нарушиться ⚠ — активируйте лицензию на «чистой» сетевой конфигурации со статическим MAC у основного адаптера ВМ.
- Аппаратные ключи HASP, маркировка [офиц., гл. 10.2.2]: `ORGL8` — локальный клиентский; `NET5 ORGL8`, `NET10 ORGL8`, `NET20 ORGL8`, `NET50 ORGL8`, `NET100 ORGL8` — многопользовательские клиентские на 5–100; `NET250+ ORG8A` — на 300; `NET250+ ORG8B` — на 500; `ENSR8` — сервер 32-бит; `EN8SA` — сервер 64-бит (для Linux x86-64 нужен он). На одном компьютере одновременно работает по одному ключу каждой серии (`ORGL8`, `ORG8A`, `ORG8B`). Серверный ключ не сетевой. На Linux нужен драйвер/демон HASP; в ВМ — проброс USB; к HASP License Manager платформа обращается по UDP, порт 475, только IPv4. **На ARM64 и Эльбрусе не поддерживаются** [офиц.].
- С 10.09.2019 все возможности аппаратной лицензии КОРП (ключ HASP) доступны только после её расширения специальной программной лицензией из Центра лицензирования (привязывается к любому доступному ключу 1С); для программной КОРП ничего делать не нужно. Для ПРОФ, приобретённых до 11.02.2019, есть бесплатное расширение, снимающее лимиты 500 сеансов и 12 ядер (см. 10.2) [офиц., гл. 1.6.3.4].
- **8.5.4+**: лицензии (программные и аппаратные, локально и по сети) раздаёт «1С:Предприятие – менеджер лицензий» (`rmlic`): локально — через IPC, по сети — TCP, поиск — широковещательный UDP; работает как приложение или служба; может работать параллельно с HASP License Manager, пока используются версии младше; правила лицензирования при этом не менялись. Новая стандартная функция «Управление лицензиями» показывает доступные и занятые лицензии [офиц.].
- Формат строки описания лицензии (в свойствах сеанса/консоли): `Получена <клиентом|сервером>, PID, сервер, порт, описание лицензии, имя файла` — например `Server, 4524, SERVER-1C, 1560, 8000314159 1 1, file://…/20100521112156.lic` [офиц.].

### 10.2. Серверные лицензии: МИНИ, ПРОФ, КОРП

**КОРП** — только 64-разрядный сервер, вся функциональность.

**ПРОФ** — 32 и 64 бита. Недоступно [офиц., руководство 8.3.27, п. 1.6.3.3]:

1. фоновое обновление конфигурации БД;
2. расширенные требования назначения функциональности (по базам, типам клиентов, фоновым заданиям);
3. гибкое управление нагрузкой: «безопасный расход памяти за один вызов», «количество ИБ на процесс» (по умолчанию 8), режим балансировки «приоритет по памяти»;
4. внешнее управление сеансами (клиент-сервер);
5. профили безопасности;
6. запись событий аудита прав доступа;
7. публикация списка баз и обновление тонкого клиента через веб-/HTTP-сервисы;
8. механизм копий базы данных;
9. более одного Дата акселератора в кластере;
10. управление потреблением ресурсов;
11. пользовательские табличные пространства;
12. произвольные (дополнительные) индексы;
13. хранилище двоичных данных (в том числе вместе с внешним хранилищем по протоколу Amazon S3);
14. HTTP-сервис метрик в формате OpenMetrics;
15. изменение каталогов данных сервисов кластера;
16. **более 500 одновременных сеансов на одну базу** (считаются конфигуратор, внешнее соединение, любое клиентское приложение);
17. **более 12 ядер CPU** (кластер ПРОФ использует не более 12 ядер; «ядро» — физическое ядро или любое ядро ВМ);
18. работа на ARM64 (исключение: на компьютерах с процессорами Apple работа под ПРОФ доступна);
19. работа на Эльбрусе.

(В документации 8.3.27 этот перечень состоит из 21 пункта — три настройки «гибкого управления нагрузкой» из п. 3 идут там отдельными строками. Исключение из п. 8: при серверной лицензии ПРОФ клиентская лицензия «1С:Аналитики» разрешает использовать механизм копий базы данных вместе с одним экземпляром Дата акселератора.)

Что покрывает серверная лицензия на одном физическом компьютере: лицензия 32-разрядного сервера — любое число 32-разрядных рабочих процессов; лицензия 64-разрядного сервера — любое число 32- и 64-разрядных [офиц.].

**МИНИ** — ограничения ПРОФ + один рабочий сервер в кластере, не более 5 клиентских сеансов и 1 сеанса конфигуратора, без 1С:Аналитики.

Правило «10 сеансов» [офиц.]: пока к **каждой** базе кластера подключено не более 10 клиентских сеансов, доступна вся функциональность, включая КОРП (кроме Дата акселератора), даже на лицензиях ПРОФ. Одиннадцатый сеанс при используемой КОРП-функциональности и недостатке лицензий КОРП получит ошибку. Для ПРОФ-лицензий, купленных до 11.02.2019, ограничения 500 сеансов/12 ядер снимаются бесплатным расширением (для программной лицензии — автоматически, для ключа HASP — программной лицензией расширения с портала 1С:ИТС).

Когда лицензий КОРП «достаточно» [офиц., гл. 1.6.4]: все серверные лицензии кластера — уровня КОРП, и либо клиент получил клиентскую лицензию КОРП, либо он получил лицензию ПРОФ и выполняется соотношение `УП <= 1,1 * ЛК`, где `УП` — число уникальных (по имени) пользователей клиентских сеансов кластера, включая начинающийся, `ЛК` — число клиентских лицензий КОРП, доступных для выдачи сервером.

| Имя службы | `1C:Enterprise 8.3 Server Agent` / `… (x86-64)`; в 8.5 — `1C:Enterprise 8.5 Server Agent` | `srv1cv8-<версия>@<экземпляр>` (systemd), `ras-<версия>` |

| Внешние компоненты | DLL (Native API, COM) | только Native API, собранные под Linux нужной архитектуры |

Чем администрировать Linux-сервер 1С:

1. `systemctl`/`journalctl` — служба и её журнал;
2. `ras` + `rac` — кластер, базы, сеансы, соединения, блокировки, правила, профили;
3. стандартная функция «Управление серверами» в клиенте или MMC-консоль с Windows — то же в графике;
4. `ibcmd` — создание/выгрузка/загрузка баз, конфигурации, расширения, журнал регистрации;
5. технологический журнал (`logcfg.xml`) и штатные средства Linux (`ps`, `top`, `ss`, `du`) — диагностика;
6. `webinst` + Apache — публикации;
7. утилита лицензирования `ring license` (скачивается отдельно с портала ИТС, нужна Java); в 8.5.4+ дополнительно стандартная функция «Управление лицензиями» и менеджер лицензий `rmlic` — лицензии.

## Быстрая шпаргалка
