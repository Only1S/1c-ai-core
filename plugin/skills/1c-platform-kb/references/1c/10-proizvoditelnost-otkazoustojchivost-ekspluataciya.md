## Кратко — 20 главных фактов и команд

1. **Официальная методика сайзинга** — измерить загрузку эталонной (работающей или тестовой) системы и линейно пересчитать на целевое число пользователей: `ядра = ядра_эталона × загрузка_CPU% / 100 / польз_эталона × польз_целевых`. Если эталона нет — на каждые 100 пользователей **8 ГБ ОЗУ на все рабочие серверы 1С в сумме и 24 ГБ на сервер СУБД** [офиц., ИТС 5810].
2. **Официальная таблица для типовых решений**: до 100 пользователей — СУБД 8 ядер / 16 ГБ / 500 ГБ, сервер 1С 2 ядра (4 потока) / 8 ГБ / 120 ГБ; до 500 — СУБД 12 ядер / 64 ГБ / 1000 ГБ, 1С 4 ядра (8 потоков) / 24 ГБ / 200 ГБ; от 500 — СУБД 40 ядер / 512 ГБ / 3000 ГБ, 1С 10 ядер (20 потоков) / 64 ГБ / 500 ГБ [офиц., ИТС 5810; значения усреднённые, не минимальные и не окончательные].
3. **Скорость одной операции определяет частота (линейная производительность) ядра, а число ядер — сколько операций идёт одновременно** [офиц. + практика]. Энергосбережение на сервере отключают; на сервере PostgreSQL 1С и Postgres Pro рекомендуют отключать Hyper-Threading [офиц.].
4. **Лицензия сервера ПРОФ использует не более 12 ядер на компьютер и допускает не более 500 сеансов на базу**; в виртуальной машине считаются виртуальные ядра [офиц.]. Давать ВМ с сервером 1С ПРОФ больше 12 vCPU бессмысленно.
5. **Лимиты памяти рабочего сервера** (8.3.15+): «Временно допустимый объём памяти процессов» (0 = 80 % ОЗУ), «Критический объём памяти процессов» (0 = 95 % ОЗУ), «Интервал превышения…» (300 с). Проценты считаются от **всей** памяти компьютера, PostgreSQL на том же хосте в расчёт не входит — на совмещённом сервере лимиты задают явно в байтах [офиц. + практика].
6. При превышении временно допустимого объёма дольше интервала кластер **штатно перезапускает** самые «тяжёлые» `rphost`; при превышении критического — **завершает аварийно** (сеансы получают ошибку) [офиц.].
7. **«Количество соединений на процесс»** по умолчанию 256 (8.3.15+), «Количество ИБ на процесс» и «Безопасный расход памяти за один вызов» доступны только с лицензией КОРП. Официальная рекомендация: без технического обоснования значения по умолчанию не уменьшать [офиц.].
8. **Перезапуск рабочих процессов по расписанию** — с 8.3.27 строка в формате cron (`0 3 * * *`) в свойствах кластера или рабочего сервера; старый «Интервал перезапуска» объявлен устаревшим и не используется [офиц.].
9. **Служебные данные кластера**: `/home/usr1cv8/.1cv8/1C/1cv8/reg_1541/` — реестр `1CV8Clst.lst`, сеансовые данные `snccntx*`, по каталогу на базу: `<UUID>/1Cv8Log` (журнал регистрации), `<UUID>/1Cv8FTxt` и `1Cv8FTxt2` (полнотекстовый индекс) [офиц.].
10. **Сеансовые данные** растут блоками по 64 МБ, пишутся всегда в конец, чистятся сборщиком мусора (нужно ≥ 25 % свободного места от их объёма); если диск с ними заполнится, менеджер кластера падает в цикле. Их держат на самом быстром диске и не вместе с техжурналом [офиц., ИТС 5860].
11. **Каталог временных файлов сервера** на Linux — `/tmp`, меняется переменной окружения `TMPDIR` пользователя/службы сервера [офиц., ИТС 1736].
12. **Очистка серверного кэша** — только при остановленной службе: удалить `reg_<порт>/snccntx*` и `*.pfl`; реестр `1CV8Clst.lst` и каталоги `<UUID>/1Cv8Log` не трогать [офиц. сценарий для Windows из ИТС 5899, пути Linux — по документации]:
    ```bash
    sudo systemctl stop ras-$V.service srv1cv8-$V@default
    sudo find /home/usr1cv8/.1cv8/1C/1cv8/reg_* -maxdepth 1 -name 'snccntx*' -exec rm -rf {} +
    sudo systemctl start srv1cv8-$V@default ras-$V.service
    ```
13. **Блокировка регламентных заданий базы** (обязательна для копий рабочих баз): `rac infobase update --cluster=$CL --infobase=<UUID> --infobase-user=… --infobase-pwd=… --scheduled-jobs-deny=on` [офиц.].
14. **Отказоустойчивый кластер**: число центральных серверов = уровень отказоустойчивости + 1; клиенту в строке соединения дают список центральных серверов без пробелов: `Srvr="srv1,srv2:1541";Ref="erp";`; серверная лицензия нужна на каждый компьютер кластера [офиц.].
15. **Порядок запуска**: PostgreSQL → сервер 1С → RAS → Apache; **остановки** — в обратном порядке. Сначала запрет новых сеансов и завершение работающих.
16. **Технологический журнал чистит себя сам** по атрибуту `history` (часы) в `logcfg.xml`; есть ротация по времени/размеру и сжатие (`rotation`, `rotationperiod`, `rotationsize`, `compress="zip"`). Журнал по умолчанию хранится 24 часа [офиц.].
17. **Рабочие процессы 1С на Linux не работают с MS SQL Server** [офиц.]. Перенос базы MS SQL → PostgreSQL: через `.dt` либо без промежуточного файла командой `ibcmd infobase replicate` (8.3.23+) [офиц.].
18. **Выгрузка в `.dt` — не резервная копия**: монопольный режим, долго, много памяти, может не загрузиться при ошибках в базе; при загрузке на сервере 1С нужно свободное место под временные файлы примерно в размер развёрнутой базы [офиц.].
19. **APDEX** = (NS + NT/2) / N, где NS — замеры до T, NT — от T до 4T. Шкала: < 0,50 неприемлемо; 0,50–0,70 очень плохо; 0,70–0,85 плохо; 0,85–0,94 хорошо; 0,94–1,00 отлично [офиц., ИТС 5807].
20. **Быстрая проверка «виновата ли СУБД»** — отношение суммарной длительности событий `DBPOSTGRS` к `CALL` в техжурнале: больше ~50 % — разбираться с запросами [офиц., ИТС 6011]. Пороги по ОС: `vmstat` — `si` ≈ 0, `us` ≤ 70, `sy` ≤ 35, очередь `r` ≤ 2 × ядер [офиц., ИТС 5824].

## 1. Сайзинг: CPU, память, диски, сеть

### 1.1. Официальная методика (ИТС, «Расчёт параметров серверного оборудования»)

Суть методики [офиц., ИТС 5810]: берётся **эталонная система**, совпадающая с целевой по конфигурации, варианту работы, расположению компонентов и версии СУБД, на ней измеряется загрузка оборудования, результат линейно экстраполируется.

| Вид эталонной системы | Трудозатраты | Точность | Когда применять |
|---|---|---|---|
| Однопользовательский тест (операции выполняются вручную, загрузка замеряется по каждой) | небольшие (1–3 дня) | низкая | предпродажная оценка |
| Многопользовательский тест (Тест-центр из КИП) | очень большие (от 1 человеко-месяца) | выше, чем у однопользовательского (в сводной таблице ИТС — «небольшая») | перед вводом новой системы |
| Рабочая система с реальными пользователями | незначительные | высокая | рост числа пользователей, переезд на новое оборудование |
| Рабочая система-аналог в другой организации | незначительные | средняя | внедрение типового решения |

Формулы [офиц.]:

```text
Ядра целевого сервера      tCPU = mCPU × mPT / 100 / mU × tU
Относит. произв-ть дисков  tRDP = mDUtil / 100 × tU / mU

mCPU   — физических ядер на эталонном сервере
mPT    — средняя загрузка CPU эталона, %  (Linux: колонка us команды vmstat)
mDUtil — загрузка дисков эталона, %       (Linux: %util команды iostat -d -x)
mU, tU — среднее число активных пользователей эталонной и целевой системы
```

Правила измерения [офиц.]:

- загрузку снимают не менее часа непрерывной интенсивной работы, без обеда и нерабочего времени, без посторонней нагрузки на сервере;
- перед замером дисков убедиться, что памяти хватает: по `free` свободно не менее 500 МБ, иначе диск нагружен подкачкой и цифры бессмысленны;
- расчёт делается отдельно для каждого сервера (1С по эталонному серверу 1С, СУБД по эталонной СУБД); при цикличной нагрузке (закрытие месяца, расчёт зарплаты) считают каждый этап и берут максимум.

Пример: эталон — 8 ядер, средняя загрузка 35 %, 60 активных пользователей; цель — 150 пользователей. `8 × 35 / 100 / 60 × 150 = 7` условных ядер такой же или большей линейной производительности.

Память [офиц.]:

- **сервер 1С** — сумма памяти процессов `ragent`, `rmngr`, всех `rphost` в пике на эталоне (на Linux методика предлагает `pmap`), пересчитанная пропорционально пользователям;
- **сервер СУБД** — занятую память можно брать в расчёт, только если СУБД не испытывает её нехватки: доля попаданий в кэш (Cache Hit Ratio) не ниже 80 %. Если показателя нет — «выделяйте для СУБД в 4 раза больше памяти, чем для всех рабочих серверов 1С в сумме» (грубая оценка);
- **если эталона нет** — на каждые 100 пользователей 8 ГБ на все рабочие серверы 1С в сумме и 24 ГБ на сервер СУБД.

Команды для замеров на Linux:

```bash
vmstat -n 15 480 > StatResult.txt          # 2 часа, шаг 15 с (так предлагает ИТС 5824)
iostat -dxm 15 480 > IoResult.txt          # пакет sysstat: r_await, w_await, aqu-sz, %util
free -m                                     # available должен быть > 500 МБ

# Память процессов кластера. По документации «память процесса» на Linux = VmRSS + VmSwap
pgrep -u usr1cv8 'rphost|rmngr|ragent' | while read p; do
  awk -v pid="$p" '/^Name:/{n=$2} /^VmRSS:/{r=$2} /^VmSwap:/{s=$2}
       END{printf "%-7s %-8s %8.0f МБ\n", n, pid, (r+s)/1024}' /proc/$p/status
done

# Доля попаданий в кэш PostgreSQL (запрос из ИТС 6011)
sudo -u postgres psql -c "SELECT round(100 * sum(blks_hit) / sum(blks_hit + blks_read), 3) AS cache_hit_ratio FROM pg_stat_database;"
```

Официальная таблица «Выбор оборудования» для типовых решений [офиц., ИТС 5810]. В статье подчёркнуто: требования усреднённые, не минимальные, «не являются точной оценкой и не могут использоваться как окончательные, особенно для крупных внедрений».

| Тип внедрения | СУБД: CPU / ОЗУ / диск | Сервер 1С: CPU / ОЗУ / диск | Веб-сервер: CPU / ОЗУ / диск |
|---|---|---|---|
| Малое (до 100 пользователей) | 8 ядер / 16 ГБ / 500 ГБ | 2 ядра (4 потока) / 8 ГБ / 120 ГБ | 1 ядро (2 потока) / 4 ГБ / 80 ГБ |
| Среднее (до 500 пользователей) | 12 ядер / 64 ГБ / 1000 ГБ | 4 ядра (8 потоков) / 24 ГБ / 200 ГБ | 1 ядро (2 потока) / 4 ГБ / 80 ГБ |
| Крупное (от 500 пользователей) | 40 ядер / 512 ГБ / 3000 ГБ | 10 ядер (20 потоков) / 64 ГБ / 500 ГБ | 2 ядра (4 потока) / 8 ГБ / 120 ГБ |

Минимальные требования к 64-разрядному рабочему серверу кластера по руководству администратора 8.3.27: ОЗУ минимум 4 ГБ, рекомендуется от 8 ГБ; для установки нужен 1 ГБ диска (без учёта баз); «рекомендуются несколько ядер или процессоров, так как они влияют на пропускную способность кластера, особенно при большом числе одновременных пользователей» [офиц.]. Для PostgreSQL под 1С и 1С (ИТС 5866), и Postgres Pro называют одинаковую «вилку» производительного сервера: 8–512 ГБ ОЗУ, 4–256 ядер, RAID 0-1 или SSD [офиц.].

### 1.2. Ориентиры на 10 / 50 / 100 / 300 / 1000 пользователей

Таблица ниже — **расчёт автора** по официальным правилам из 1.1 (8 ГБ и 24 ГБ на 100 пользователей, официальная таблица, минимумы платформы) с практическим запасом. Это стартовая точка для закупки или создания ВМ, а не гарантия: реальная потребность зависит от конфигурации (ERP и «Бухгалтерия» нагружают по-разному), доли тяжёлых операций, фоновых заданий и обменов. После запуска всё проверяется мониторингом (разделы 6 и 8).

| Одновременных пользователей | Размещение | Сервер 1С (CPU / ОЗУ) | PostgreSQL (CPU / ОЗУ) | Диски |
|---|---|---|---|---|
| до 10 | один хост или ВМ «всё в одном» | вместе: 4 ядра / 16 ГБ | — | SSD от 100 ГБ + место под копии |

| ~300 | раздельно: сервер 1С и сервер СУБД | 8–12 ядер / 24–48 ГБ | 12–16 ядер / 64–96 ГБ | NVMe/SSD-массив; отдельные тома под данные, WAL, временные таблицы |
| ~1000 | раздельно; 2+ рабочих сервера 1С, отдельный веб-сервер; лицензии КОРП | в сумме 20+ ядер / 64–128 ГБ | 32–40+ ядер / 256–512 ГБ | промышленное хранилище; расчёт только по методике и нагрузочному тесту |

Пояснения:

- Строки «до 10» и «~50» опираются на минимумы платформы (8 ГБ рекомендуется серверу 1С) и PostgreSQL (минимум 8 ГБ по ИТС 5866) — правило «8 + 24 ГБ на 100 пользователей» для малых баз даёт меньше этих минимумов.
- Для 100 пользователей официальная таблица даёт СУБД 16 ГБ, а правило — 24 ГБ; берите большее. Память — самый дешёвый способ избежать проблем с диском.
- Более 500 одновременных сеансов в одной базе или более 12 ядер на сервере 1С требуют лицензий КОРП [офиц.].
- Примеры реальных внедрений из проектов ЦКТП — в разделе 1.9.

### 1.3. Память: сеанс, rphost, PostgreSQL

Что известно официально:

- расчётная норма 8 ГБ на 100 пользователей на стороне 1С — это в среднем ~80 МБ на пользователя вместе с общими структурами процессов [офиц., ИТС 5810];
- процессы кластера «выделяют ровно столько памяти, сколько им нужно для выполнения текущих задач», а СУБД при нехватке памяти продолжает работать, но медленнее (уменьшает кэши, чаще ходит на диск) [офиц.];
- поводом обращаться в поддержку 1С за анализом памяти считается потребление одним процессом платформы порядка 20 ГБ и более, не объяснимое известными тяжёлыми операциями [офиц., ИТС 5985].

Практические ориентиры ⚠ (сильно зависят от конфигурации и версии платформы; проверять замером):

- `rphost` после загрузки метаданных крупной конфигурации (ERP, КА, ЗУП) занимает от нескольких сотен МБ до 1–2 ГБ ещё до пользователей; у каждого `rphost` своя копия кэша конфигурации, поэтому много мелких `rphost` расходуют память неэффективно — об этом прямо предупреждает ИТС 5908 [офиц.];
- обычный интерактивный сеанс тонкого клиента — десятки МБ, с открытыми тяжёлыми формами и отчётами — 100–300 МБ;
- фоновые задания (закрытие месяца, обмены, формирование отчётов, полнотекстовая индексация) могут кратковременно занимать гигабайты — именно они чаще всего приводят к срабатыванию лимитов памяти;
- `rmngr` — от сотен МБ; растёт вместе с сеансовыми данными, которые отображаются в память (раздел 3.3).

Как посмотреть фактическое потребление:

```bash
ps -C rphost,rmngr,ragent -o pid,rss,vsz,etimes,args --sort=-rss      # RSS в КБ
$RAC process list --cluster=$CL          # memory-size (КБ), connections, avg-call-time, avg-db-call-time
$RAC session list --cluster=$CL          # memory-current, memory-total (байты за вызов / за сеанс), cpu-time-total
```

Память PostgreSQL планируют по формулам, одинаковым у 1С (ИТС 5866, ред. 19.06.2025) и Postgres Pro [офиц.]: `shared_buffers = ОЗУ/4`, `effective_cache_size = ОЗУ − shared_buffers`, `work_mem = ОЗУ/32..64` или 32–256 МБ, `maintenance_work_mem = ОЗУ/16..32` или 256 МБ–4 ГБ, `temp_buffers = 32..256 МБ`. Под «ОЗУ» понимается память, **доступная PostgreSQL**: если на сервере есть другие приложения (сервер 1С), её объём вычитают. Число соединений: `max_connections = 500..8000` (1С) / `500..10000` (Postgres Pro); ИТС добавляет ориентир — для обычной работы нужно примерно от 1/8 до 1/4 от числа сеансов кластера 1С. Подробности настройки — в статьях базы знаний о PostgreSQL.

### 1.4. Процессор: частота против числа ядер

- Серверный вызов одного сеанса исполняется в одном потоке, поэтому время проведения документа или формирования отчёта определяется **линейной производительностью ядра**. Методика 1С требует выбирать процессор «с такой же или большей линейной производительностью, чем процессор эталонной системы» — того же производителя и назначения, того же или более позднего поколения, с такой же или большей тактовой частотой [офиц., ИТС 5810].
- Число ядер определяет, сколько вызовов идёт одновременно без очереди. Критерий нехватки: в `vmstat` очередь `r` длительно больше `2 × число ядер`, `us` выше 70 % [офиц., ИТС 5824].
- Энергосбережение: для серверов 1С (чек-лист ИТС 5899) требуется схема «Высокая производительность»; для сервера PostgreSQL — «отключить Energy Saving, в противном случае могут непредсказуемо вырастать задержки ответов БД» и «рекомендуется отключать HyperThreading» [офиц., ИТС 5866 и Postgres Pro].
- Лицензии: ПРОФ использует до 12 первых ядер на каждом сервере (кластер из двух серверов ПРОФ — до 24); на физическом сервере с Hyper-Threading считаются физические ядра, в виртуальной машине — виртуальные [офиц., ответы на вопросы по лицензированию на v8.1c.ru].

Проверка и настройка на Linux:

```bash
lscpu | grep -E 'Model name|^CPU\(s\)|Thread|Core|Socket|NUMA|MHz'
grep MHz /proc/cpuinfo | sort -t: -k2 -n | head -3          # фактические частоты ядер
cat /sys/devices/system/cpu/cpu0/cpufreq/scaling_governor   # на «железе»; в ВМ файла обычно нет
sudo apt install linux-tools-common linux-tools-$(uname -r)  # утилита cpupower
sudo cpupower frequency-set -g performance                   # до перезагрузки; постоянно — службой или в BIOS
```

В виртуальной машине управление частотой принадлежит гипервизору и хосту: на Windows-хосте включают план «Высокая производительность» (`powercfg /setactive 8c5e7fda-e8bf-4a96-9a85-a6e23a8c635c`), в BIOS — максимальную производительность и Turbo Boost [практика; на значимость этих настроек указывает и автор теста Гилёва].

### 1.5. NUMA и число рабочих процессов

Официальная позиция (ИТС 5903, 2016 г.) [офиц.]: поддержка NUMA в кластере «полноценно пока не реализована», сервер 1С полагается на операционную систему, из-за чего на многопроцессорных машинах может быть загружена только часть ядер. Рекомендация — чтобы на таком сервере работало больше одного `rphost`:

```text
ЧислоСоединенийНаПроцесс = РасчётноеМаксимальноеКоличествоСоединений / КоличествоNUMAузлов
если перекос остаётся:   … / (КоличествоNUMAузлов × Коэффициент),  Коэффициент = 2, далее +1 при каждой подстройке
```

```bash
lscpu | grep -i numa                 # число узлов и распределение CPU
numactl --hardware                   # пакет numactl: память и расстояния между узлами
numastat -p $(pgrep -o rphost)       # размещение памяти процесса по узлам
```

Для виртуальных машин [практика]: не давайте ВМ больше vCPU и памяти, чем помещается в один NUMA-узел хоста, либо включайте проброс топологии (vNUMA). Тест Гилёва отдельно диагностирует «некорректные настройки по сокетам» в ВМ.

### 1.6. Диски

Что требует официальная методика [офиц.]:

- производительность дисков подбирается относительно эталона (коэффициент `tRDP`), на основании рекомендаций производителя, независимых тестов или собственного сравнительного теста;
- признаки нехватки: очередь к дискам — колонка `b` в `vmstat` длительно больше `2 × число параллельно работающих дисков` (ИТС 5824);
- для PostgreSQL: `fsync = on` (выключать только при кэширующем контроллере с батареей и ИБП), `synchronous_commit = off` допускается — риск ограничен потерей транзакций за последние 0,5–1 с, целостность базы сохраняется; `random_page_cost = 1.5–2.0` для RAID и `1.1–1.3` для SSD; временные таблицы можно вынести на отдельные быстрые диски (`temp_tablespaces`) [офиц., ИТС 5866, Postgres Pro];
- сеансовые данные кластера 1С — на максимально быстрых дисках, отказоустойчивость для них не важна [офиц., ИТС 5860];
- каталог кластера не размещают на сжатых томах и не включают в файловое резервное копирование (сеансовые данные копировать не нужно, это лишняя нагрузка) [офиц., ИТС 5908].

Практические требования ⚠ (цифры — ориентир сообщества, не норматив 1С):

- серверные SSD/NVMe с защитой от потери питания (PLP); «домашние» NVMe после исчерпания SLC-кэша резко теряют скорость записи — это показывает дисковый тест Гилёва;
- WAL критичен к задержке синхронной записи: хорошим считается время `fdatasync` до 1–2 мс, тревожным — десятки мс;
- типичная OLTP-нагрузка 1С — случайные чтение и запись блоками 8 КБ; ориентир от тысяч IOPS на сотню активных пользователей;
- раскладка томов при росте: данные, WAL, временные таблицы, резервные копии, каталог кластера 1С, техжурнал — на разных томах, чтобы переполнение одного не останавливало остальное.

Проверка:

```bash
# Задержка синхронной записи там, где лежит WAL (утилита из состава PostgreSQL; файл — на ФС с pg_wal)
sudo -u postgres /usr/lib/postgresql/17/bin/pg_test_fsync -f /var/lib/postgresql/17/main/pg_test_fsync.out -s 5

# Случайная запись 8 КБ с fdatasync (пакет fio); тестовый файл потом удалить
sudo fio --name=pg8k --filename=/var/lib/postgresql/fio.test --size=2G --rw=randwrite --bs=8k \
         --ioengine=psync --fdatasync=1 --runtime=60 --time_based --group_reporting
sudo rm /var/lib/postgresql/fio.test

iostat -dxm 5        # в работе: w_await/r_await (мс), aqu-sz (очередь), %util
```

Путь к `pg_test_fsync` зависит от сборки: у пакетов в стиле Debian/Ubuntu — `/usr/lib/postgresql/<версия>/bin/`, у Postgres Pro — `/opt/pgpro/std-<версия>/bin/` ⚠ (проверьте `dpkg -L` своего пакета). По документации PostgreSQL 18 ключ `-f` задаёт файл (должен лежать на той же ФС, что `pg_wal`), `-s` — секунд на тест (по умолчанию 5).

### 1.7. Один хост или два; сеть между 1С и СУБД

**Совмещение ролей (сервер 1С + PostgreSQL на одной машине)** [практика, если не указано иное]:

- плюсы: нет сетевой задержки между 1С и СУБД, проще администрирование, одна ВМ; для многопоточной загрузки `.dt` фирма «1С» прямо называет это желательным вариантом: кластер и СУБД должны располагаться «на одном компьютере» либо быть связаны «каналом с высокой пропускной способностью (1 Гбайт/с и выше)» — так в тексте V8Update для 8.3.19 [офиц.];
- минусы: конкуренция за память, CPU и диск. Автоматические лимиты памяти кластера (80 % и 95 % ОЗУ) не знают о PostgreSQL — их нужно задать явно (раздел 2.3); формулы памяти PostgreSQL применяют к памяти за вычетом доли 1С;
- ограничение ПРОФ в 12 ядер относится только к процессам 1С; PostgreSQL использует все ядра ВМ.

**Разнесение** оправдано, когда не хватает ресурсов одной машины, нужны отказоустойчивость или разные циклы обслуживания. Требования: сеть не хуже 1 Гбит/с (KB-статья 01, раздел о слоях архитектуры), минимум промежуточных устройств, один сегмент, стабильное разрешение имён; загрузка сети — не более 65 % пропускной способности адаптера [офиц., ИТС 5824].

**Как сервер 1С подключается к PostgreSQL.** Рабочий процесс `rphost` открывает обычные клиентские соединения PostgreSQL по TCP к адресу из свойства базы «Сервер баз данных» (порт по умолчанию 5432), в том числе когда СУБД стоит на той же машине — тогда это `localhost`/`127.0.0.1`. В техжурнале это видно в событиях `DBPOSTGRS`: `DataBase=127.0.0.1\ERP` [офиц., пример из ИТС 6011]. Платформа при подключении сама выставляет параметры сеанса — в методике 1С для воспроизведения плана запроса их перечисляют так [офиц.]:

```sql
SET client_min_messages=error;
SET lc_messages to 'en_US.UTF-8';
SET enable_mergejoin = off;
SET escape_string_warning = off;
SET cpu_operator_cost = 0.001;
SET client_encoding = 'utf8';
SET lock_timeout = 20000;
```

Практические детали [практика]:

- нестандартный порт указывают в том же поле: `pg-host port=5433`;
- в `pg_hba.conf` нужна строка `host` для адреса сервера 1С (для совмещённого хоста — `127.0.0.1/32`), в `postgresql.conf` — `listen_addresses` с нужным интерфейсом; `ssl = off` рекомендуют и 1С, и Postgres Pro (шифрование добавляет нагрузку на CPU) [офиц.] — внутри доверенного сегмента;
- проверить, как реально подключены сеансы: `SELECT client_addr, count(*) FROM pg_stat_activity WHERE backend_type = 'client backend' GROUP BY 1;` (`NULL` означал бы Unix-сокет);
- ⚠ не подтверждено: встречаются сообщения, что в поле «Сервер баз данных» можно указать каталог Unix-сокета (`/var/run/postgresql`) и получить небольшой выигрыш; официально такой вариант не описан.

### 1.8. Виртуализация (в том числе ВМ на Windows-хосте)

Официальные требования чек-листа 1С для рабочих серверов [офиц., ИТС 5899]: «На виртуальных машинах обеспечено гарантированное выделение ресурсов, суммарный объём выданной оперативной памяти в виртуальных машинах меньше объёма имеющейся памяти на хосте». Методика сайзинга допускает ВМ как способ получить ровно нужное число ядер.

Практика [практика]:

- выключить динамическую память (ballooning) и переподписку CPU для ВМ с 1С и СУБД; резервировать память целиком;
- диск ВМ — фиксированного размера (не динамически расширяемый), на SSD/NVMe хоста; контроллер — паравиртуальный (virtio / VMware PVSCSI / Hyper-V SCSI); файлы дисков исключить из антивирусной проверки хоста;
- для ВМ на рабочей станции с Windows (VirtualBox, VMware Workstation, Hyper-V): план электропитания хоста «Высокая производительность», запрет сна; сеть — мост (bridged), а не NAT (клиент не сможет работать с кластером за NAT без проброса портов и разрешения имён — см. статью 01);
- время в ВМ синхронизировать (chrony/systemd-timesyncd): расхождение часов ломает лицензирование 8.5.4 (допуск 20 минут между менеджером лицензий и приложениями [офиц., ИТС 6041]) и Kerberos;
- программная лицензия 1С привязана к параметрам компьютера; изменение состава ВМ (CPU, память, сетевые адаптеры, диск) может потребовать повторной активации ⚠ — конфигурацию ВМ с активированной лицензией фиксируют заранее;
- «штраф» виртуализации измеряют сравнением с физическим сервером: автор теста Гилёва рекомендует сначала убедиться, что на «железе» всё хорошо, затем сравнить результат в ВМ.

## 2. Настройки кластера под нагрузку

Все параметры меняются в консоли кластера (MMC с Windows-машины той же версии), в стандартной функции «Управление серверами» или утилитой `rac`. Подготовка переменных для примеров:

```bash
V=8.3.27.2074; RAC=/opt/1cv8/x86_64/$V/rac
CL=$($RAC cluster list | awk '/^cluster /{print $3}')
SRV=$($RAC server list --cluster=$CL | awk '/^server /{print $3}')     # если рабочий сервер один
$RAC cluster info --cluster=$CL
$RAC server info  --cluster=$CL --server=$SRV
# если заданы администраторы: --cluster-user=… --cluster-pwd=… (кластер), --agent-user=… --agent-pwd=… (агент)
```

Имена ключей `rac` в таблицах ниже взяты из справки утилиты (`rac help cluster`, `rac help server`) и файла изменений V8Update. Ключи, появившиеся в 8.3.15 и позже, помечены ⚠ там, где их написание не удалось сверить со справкой актуальной сборки, — проверьте `$RAC help server` на своём сервере.

**Как работает контроль памяти** [офиц., раздел «Cluster monitoring system» руководства 8.3.27]:

1. Система мониторинга кластера каждые 5 секунд сравнивает суммарную память всех `rphost` и `rmngr` рабочего сервера (на Linux — `VmRSS + VmSwap` каждого процесса) с настройками. Отрицательные результаты проверок пишутся в техжурнал событием `ATTN`.
2. Превышен **временно допустимый объём** → серверу перестают назначать новые соединения. Если по истечении интервала превышение сохраняется, нужное число рабочих процессов **перезапускается штатно**, начиная с самого большого, пока память оставшихся не уложится в лимит.
3. Превышен **критический объём** → нужное число рабочих процессов **завершается** (и запускается заново), начиная с самого большого; в техжурнал на каждой итерации пишется `ATTN` с идентификаторами процессов и объёмами памяти.
4. Контроль отдельного вызова: каждый рабочий процесс раз в 2 секунды узнаёт память процессов кластера на сервере. В начале серверного вызова вычисляется лимит на вызов = «временно допустимый объём» − «текущая память» (но не меньше «безопасного расхода за один вызов»). Если вызов при выделении памяти превышает этот лимит, он **прерывается исключением**, в техжурнале остаётся событие `EXCP` с текстом и контекстом.
5. Проблемными считаются также процессы, не ответившие на проверку соединения (таймаут 20 с) и не завершившиеся за 7,5 с после удаления из реестра; с ними поступают согласно «Принудительно завершать проблемные процессы».

### 2.3. Расчёт лимитов памяти (особенно для совмещённого сервера)

Принцип из методики 1С (ИТС 5815; сформулирован для прежнего параметра «Допустимый объём памяти», но логика перезапуска та же) [офиц.]: при срабатывании порога запускается новый `rphost`, а старый ещё некоторое время дорабатывает вызовы, то есть **одновременно живут оба**. Поэтому порог выбирают так, чтобы после его срабатывания на сервере осталось место ещё под один рабочий процесс обычного размера, и «не следует указывать допустимый объём меньше нормального рабочего объёма памяти процесса rphost… в противном случае у вас постоянно будут перезапускаться процессы». Интервалы «следует стараться указывать как можно меньше исходя из характера нагрузки, например, по 60 секунд».

Порядок расчёта для сервера «всё в одном» [практика]:

```text
Память_1С = ОЗУ − ОС (2–4 ГБ) − бюджет PostgreSQL (shared_buffers + память сеансов + желаемый файловый кэш)
Временно допустимый объём = Память_1С − размер одного «нормального» rphost
Критический объём         = Память_1С (или чуть меньше)
```

Пример: ВМ 64 ГБ; PostgreSQL отдано 36 ГБ (`shared_buffers = 9GB`), ОС — 4 ГБ, серверу 1С — 24 ГБ; обычный суммарный объём процессов 1С в пике ~12 ГБ, один `rphost` ~4–6 ГБ.

```bash
$RAC server update --cluster=$CL --server=$SRV \
     --temporary-allowed-total-memory=19327352832 \
     --temporary-allowed-total-memory-time-limit=120 \
     --critical-total-memory=23622320128            # 18 ГиБ / 120 с / 22 ГиБ; ⚠ имена ключей — см. rac help server
$RAC server info --cluster=$CL --server=$SRV | grep -E 'memory|limit'
```

Без явных значений тот же сервер считал бы допустимыми 51 ГБ (80 %) и 61 ГБ (95 %) — то есть память PostgreSQL и файловый кэш были бы вытеснены раньше, чем кластер 1С что-либо заметил, и первым сработал бы OOM killer ядра.

Страховка на уровне ОС [практика]:

```bash
# Ограничить группу процессов сервера 1С средствами cgroup v2 (Ubuntu 22.04+): при превышении OOM убьёт rphost, а не postgres
sudo systemctl edit srv1cv8-$V@default
#   [Service]
#   MemoryHigh=22G
#   MemoryMax=26G
systemctl show srv1cv8-$V@default -p MemoryCurrent -p MemoryMax

# Убедиться, что postmaster защищён от OOM killer (в юнитах postgresql-common обычно уже задано OOMScoreAdjust=-900 — подтверждено исходным текстом юнита postgresql@.service в репозитории postgresql-common, 11.10.2026)
systemctl cat 'postgresql@*' 2>/dev/null | grep -i oom
journalctl -k --since "-7d" | grep -i -E 'out of memory|oom-kill'     # был ли OOM
```

Документация PostgreSQL для выделенных серверов СУБД рекомендует строгий режим `vm.overcommit_memory=2` и `oom_score_adj=-1000` для postmaster [офиц., postgresql.org]. На совмещённом с 1С хосте строгий overcommit включать не стоит ⚠ [практика]: процессы 1С резервируют много виртуальной памяти и начнут получать отказы в выделении.

Разбор инцидента «память кончилась» по методике 1С [офиц., ИТС 5815, 5814]: найти процесс-виновник (`ps … --sort=-rss`); если это `rphost` — в списке сеансов отсортировать по памяти и по длительности текущего вызова (`rac session list`: `memory-current`, `memory-total`, `duration-current`, `duration-current-dbms`), записать номера сеансов, завершить их (`rac session terminate --cluster=$CL --session=<UUID>`), убедиться, что сработал перезапуск процесса, затем по журналу регистрации выяснить, что именно делали эти сеансы.

### 2.4. Количество ИБ и соединений на процесс

Что говорит фирма «1С» [офиц., ИТС 5908, 5899, 5903]:

- «Не стоит просто так уменьшать параметр "Число соединений на процесс" или "Число информационных баз на процесс". Если у вас нет технического обоснования… рекомендуем оставить значения по умолчанию».
- Настройка не должна приводить «к запуску 100 процессов rphost, т.к. значительное число процессов rphost приводит к неэффективному использованию памяти».
- Пример неверной настройки из чек-листа: «1 rphost на 1 информационную базу при наличии большого числа информационных баз в кластере».
- На многопроцессорных (NUMA) серверах, наоборот, должно работать больше одного `rphost`: число соединений на процесс = расчётный максимум соединений / число NUMA-узлов (раздел 1.5).

Как кластер выбирает процесс [офиц.]: при старте на каждом рабочем сервере запускается один `rphost`. Новое соединение получает процесс, у которого не достигнуты оба лимита и который не готовится к перезапуску; предпочтение — процессу, уже обслуживающему эту базу. Если подходящего нет — запускается новый `rphost`. Если два процесса 20 минут подряд вместе укладываются в лимиты одного, менее загруженный помечается устаревшим и останавливается после закрытия последнего соединения.

Сценарии [практика, если не указано иное]:

| Сценарий | Настройка | Зачем и чем платим |
|---|---|---|
| Одна-две рабочие базы, до ~200 сеансов, один сервер | значения по умолчанию (256 соединений, 8 ИБ) | 1–2 `rphost`; минимум накладных расходов |
| Одна большая база, 2 NUMA-узла, 600 соединений | соединений на процесс = 600 / 2 = 300 [офиц. формула] | равномерная загрузка сокетов |
| Несколько критичных баз, нужна изоляция сбоев и понятная картина «кто съел память» (КОРП) | ИБ на процесс = 1 | у каждой базы свой `rphost`; сбой одной не роняет сеансы другой; расход памяти выше |
| Десятки и сотни мелких баз (хостинг) | ИБ на процесс 8–20, плюс параметры «пассивных» баз (раздел 4.3) | не плодить процессы; каждый лишний `rphost` — сотни МБ |
| Тяжёлые фоновые задания мешают интерактивной работе (КОРП, 2+ сервера) | требования назначения функциональности (раздел 4.4) | фоновые задания на отдельном сервере |

### 2.5. Плановый перезапуск рабочих процессов

**8.3.27 и новее — расписание в формате cron** [офиц., приложение 2 руководства администратора]. Строка из пяти полей: минута (0–59), час (0–23), день месяца (1–31), месяц (1–12), день недели (0–6, воскресенье = 0). Допускаются число, список через запятую, диапазон через дефис, `*` и шаг через `/`. Метасимволы вида `@daily` использовать нельзя.

```bash
$RAC cluster update --cluster=$CL --restart-schedule="0 3 * * *"                  # ежедневно в 03:00
$RAC server  update --cluster=$CL --server=$SRV --restart-schedule="30 3 * * 6"   # для одного сервера: суббота, 03:30
$RAC cluster update --cluster=$CL --lifetime-limit=86400                          # 8.3.26 и старше: раз в сутки от старта процесса
```

| Пример | Значение |
|---|---|
| `0 0 * * *` | каждый день в полночь |
| `0 3 * * 6` | каждую субботу в 03:00 |
| `0 3 * * 1-5` | с понедельника по пятницу в 03:00 |
| `0 3 1 * *` | в 03:00 первого числа месяца |
| `*/10 * * * *` | каждые 10 минут (для перезапуска бессмысленно; пример формата) |

Как проходит перезапуск [офиц.]: старый процесс выключается (дорабатывает старые соединения, новых к «чужим» базам не принимает) → регистрируется и стартует новый процесс → в нём системными фоновыми заданиями (`SystemBackgroundJob`) заранее создаются контексты баз, которые обслуживал старый → старый перестаёт принимать соединения и «передаёт» существующие новому → старый завершается, когда все соединения переданы **или** истекло время «Проблемные процессы завершать через». Несколько процессов одного сервера перезапускаются последовательно, разные серверы — одновременно.

Замечания:

- Сеансы пользователей при штатном перезапуске сохраняются, но вызов, не успевший завершиться за отведённое время, оборвётся — поэтому расписание ставят на нерабочее время и согласуют с длительными фоновыми заданиями (закрытие месяца, обмены, резервное копирование).
- Плановый перезапуск — страховка от накопления памяти, а не лечение: если без него сервер не живёт сутки, нужно искать утечку или тяжёлую операцию (раздел 8) [практика].
- В 8.3.27 появилась возможность выключить конкретный рабочий процесс (в `rac` — режим `process`, команда `turn-off`) [офиц., V8Update; точный синтаксис ⚠ — `$RAC help process`].

### 2.6. Официальный чек-лист рабочего сервера (выжимка)

Из «Check-list по настройке рабочих серверов в продукционной зоне» и «Инструкции по настройке рабочих серверов» [офиц., ИТС 5899 и 5908; написаны на примерах Windows, применимое к Linux — ниже]:

- на рабочих серверах только рабочие кластеры и базы; копий, тестовых баз и баз разработки быть не должно. Копия рабочей базы в том же кластере — только без доступа пользователей, с выключенными регламентными заданиями и не участвующая в обменах;
- настроен техжурнал: каталог `ALL` (события `EXCP`, `PROC`, `CONN`, `SESN`, `CLSTR`, `SRVC`, `ADMIN`) и при наличии места `CALLSCALL` (`CALL`, `SCALL` без контекстов); хранение 28 часов, при нехватке места — только `ALL` на 12 часов; настроен сбор дампов;
- настроены перезапуск процессов по памяти и ограничения безопасного расхода — либо по умолчанию, либо значения, которые реально могут сработать на этом оборудовании; нельзя ставить значения, фактически отключающие контроль;
- число `rphost` адекватно задаче;
- в кластере из двух и более серверов явно закреплены требованиями назначения сервис лицензирования, сервис полнотекстового поиска, сервис журнала регистрации (и сервис работы с внешними источниками данных), продумано расположение лицензий и сеансовых данных;
- пользователь СУБД у каждой рабочей базы свой, с именем, совпадающим с именем базы, — так в отчётах и трассировках СУБД сразу видно, чья нагрузка;
- схема электропитания — высокая производительность; виртуальным машинам ресурсы выделены гарантированно;
- на серверах не используются одновременно IPv4 и IPv6; сетевой экран не мешает портам кластера и RAS;
- хотя бы раз проведено тестовое восстановление из резервной копии с замером времени; настроены пересчёт итогов и обслуживание СУБД; нет лишней регистрации изменений в планах обмена;
- настроены оповещения мониторинга: свободного места меньше 10 %, свободной памяти меньше 200 МБ (кроме СУБД), CPU выше 90 % — каждое в течение 5 минут;
- каталог кластера не архивируется файловыми средствами и не лежит на сжатом томе; сеансовые данные — на быстрых дисках, на дисках достаточно места;
- антивирус на рабочих серверах в закрытом сегменте не нужен: он заметно снижает производительность при малом выигрыше в защите.

```text
    ├── snccntx*/                            сеансовые данные (в документации 8.3.27 — snccntx/<UUID менеджера>)

    ├── <UUID базы>/1Cv8FTxt/                индекс полнотекстового поиска (версия 1)
    ├── <UUID базы>/1Cv8FTxt2/               индекс полнотекстового поиска (версия 2)
    ├── BinDataStrg/<UUID базы>/             встроенное хранилище двоичных данных (КОРП)
    ├── 1Cv8DbDA/<UUID базы>/                Дата акселератор
    ├── STT/                                 модели распознавания речи
    └── rescntsrv.lst                        счётчики потребления ресурсов

/opt/1cv8/x86_64/<версия>/conf/              conf.cfg и logcfg.xml этой версии платформы
/var/1C/licenses/                            файлы программных лицензий (*.lic)
/tmp  (или $TMPDIR)                          временные файлы процессов сервера
```

Источники структуры: таблица «каталог данных сервиса по умолчанию» руководства администратора 8.3.27 и описания файлов `1cv8wsrv.lst`, `1CV8Clst.lst`, `1cv8conn.pfl` [офиц.]. Если каталог данных перенесён (`SRV1CV8_DATA`), всё дерево находится там, но `1cv8conn.pfl` по документации лежит в `~/.1cv8/1C/1cv8` пользователя, от имени которого работает приложение [офиц.].

Соответствие «UUID каталога ↔ имя базы»:

```bash
$RAC infobase summary list --cluster=$CL            # infobase : <UUID>, name : <имя>
sudo du -sh /home/usr1cv8/.1cv8/1C/1cv8/reg_1541/*/ | sort -h     # что сколько занимает
```

Потеря каталога кластера не разрушает базу (данные в СУБД), но теряются список баз, настройки кластера, журналы регистрации и полнотекстовые индексы. Если агент при старте не находит реестр (другой каталог, другой пользователь), он создаёт новый пустой кластер — типичная причина «пропавших баз» [офиц.].

### 3.2. Временные файлы сервера

- По умолчанию процессы сервера пишут временные файлы в `/tmp`. Официальная статья ИТС «Изменение каталога временных файлов сервера 1С:Предприятия» (2010 г.) предписывает менять его переменной окружения `TMPDIR` пользователя, от которого работает сервер, и следить, чтобы системная очистка `/tmp` не удаляла файлы работающего сервера («могут возникать нештатные ситуации, связанные с отсутствием файлов во временном каталоге») [офиц., ИТС 1736].
- Что туда попадает: файлы, создаваемые прикладным кодом на сервере (`ПолучитьИмяВременногоФайла()`, каталог `КаталогВременныхФайлов()`), временные файлы загрузки `.dt` (объём — порядка развёрнутой базы, раздел 7.4), временные данные полнотекстового индексирования, промежуточные файлы обменов и печати.
- Файлы защищены правами: создающий их пользователь `usr1cv8` получает полный доступ, остальным доступ закрыт [офиц.].

Перенос на отдельный быстрый том в современных версиях (служба systemd) [практика; официальная статья описывает тот же `TMPDIR`, но через `.bash_profile` старого init-сценария]:

```bash
sudo install -d -o usr1cv8 -g grp1cv8 -m 0750 /var/lib/1c/tmp      # каталог (или точка монтирования быстрого диска)
sudo systemctl edit srv1cv8-$V@default
#   [Service]
#   Environment=TMPDIR=/var/lib/1c/tmp
sudo systemctl restart srv1cv8-$V@default
sudo cat /proc/$(pgrep -o rphost)/environ | tr '\0' '\n' | grep TMPDIR    # проверка: переменная дошла до rphost
```

Очистка:

```bash
# безопасно — только при остановленной службе
sudo systemctl stop srv1cv8-$V@default && sudo find /var/lib/1c/tmp -mindepth 1 -delete && sudo systemctl start srv1cv8-$V@default
# на работающем сервере — только заведомо старые файлы
sudo find /var/lib/1c/tmp -type f -mtime +3 -delete
```

Про системную очистку (уточнено 11.10.2026 по тексту правки Debian и журналам изменений пакета systemd в Ubuntu — см. `../linux/07-diski-fs-lvm.md`, раздел о каталоге `/tmp`): политика `systemd-tmpfiles` для `/tmp` и `/var/tmp` отличается между выпусками Ubuntu (очистка `/tmp` при загрузке, удаление старых файлов из `/var/tmp` по возрасту; в новых выпусках возможен `/tmp` на tmpfs). Проверьте у себя: `systemd-tmpfiles --cat-config | grep -E '\s/(var/)?tmp\s'` и `findmnt /tmp`. Отдельный каталог вне `/tmp` и `/var/tmp` (как в примере) под эти правила не попадает. Размещать `TMPDIR` сервера на tmpfs не стоит: загрузка большого `.dt` или тяжёлый обмен займут оперативную память.

### 3.3. Сеансовые данные

Факты из методической статьи «Анализ причин роста сеансовых данных» [офиц., ИТС 5860]:

- в сеансовых данных хранится служебная информация сеансов: содержимое форм управляемого приложения между серверными вызовами, временное хранилище (`ПоместитьВоВременноеХранилище`, `ПоместитьФайл`), результаты отчётов, сформированных в фоне;
- физически это key-value хранилище в каталоге `reg_<порт>/snccntx…`, которым управляет менеджер кластера `rmngr`; в кластере из нескольких серверов размещение определяется требованиями назначения, без них — равномерно по серверам;
- данные растут блоками по 64 МБ и всегда дописываются в конец (как журнал транзакций). Перед выделением нового блока, если с предыдущего прошло 5 секунд, запускается сборщик мусора: когда актуальных данных меньше 25 %, они копируются в новые файлы, старые удаляются. Для этого нужно свободное место не менее 25 % объёма сеансовых данных — иначе кластер завершится аварийно;
- файлы отображаются в память (mmap), поэтому большой объём сеансовых данных «съедает» файловый кэш;
- при большом числе пользователей «рекомендуется располагать файлы сеансовых данных на максимально быстрых дисках. Желательно RAM-drive. Отказоустойчивость дисков не важна»;
- «не следует размещать файлы технологических журналов на одном диске с сеансовыми данными»;
- если диск с сеансовыми данными заполнится, «менеджер кластера будет постоянно завершаться с формированием дампа, начнутся сотни попыток запусков рабочих процессов»; после освобождения места сервер запускается нормально;
- рост вызывают циклические ссылки в формах (данные формы не освобождаются до конца сеанса) и отчёты, формируемые не в фоне.

Контроль:

```bash
sudo du -sh /home/usr1cv8/.1cv8/1C/1cv8/reg_1541/snccntx*          # текущий объём
df -h /home/usr1cv8/.1cv8/1C/1cv8                                  # свободное место на томе
```

С 8.5.4 текущий объём сеансовых данных доступен и как метрика HTTP-мониторинга кластера (`e1c_session_data_current`) [офиц., V8Update].

### 3.4. Вынос служебных данных на быстрый диск

1. **Весь каталог данных сервера** (любая лицензия): остановить службу, перенести каталог, задать `SRV1CV8_DATA` в drop-in юнита. Пошагово — раздел 6.4 статьи `02-ustanovka-servera-ubuntu.md`.
2. **Каталоги отдельных сервисов** (только КОРП) [офиц.]: в консоли кластера у рабочего сервера ветка «Настройки сервисов» — выбрать сервис (журнал регистрации `EventLogService`, полнотекстовый поиск `FulltextSearchService` / `FullTextSearchServiceV2`, сеансовые данные `SessionDataService`, хранилище двоичных данных `BinaryDataStorageService`, счётчики `CounterService`), указать каталог, при необходимости — имя базы; затем «Применить настройки». В `rac` это режим `service-setting` (8.3.2x) / `service-setting-server` (с 8.5.4) — синтаксис смотрите в `$RAC help`. Официальный порядок:
   - создать настройки → запретить вход пользователям и запуск регламентных заданий → дождаться завершения фоновых заданий, отключить пользователей → применить настройки → остановить кластер → перенести данные сервисов в новые каталоги → запустить кластер → разрешить работу;
   - новые каталоги начинают использоваться только после перезапуска **всего** кластера; в новом месте данные лежат в `<новый каталог>/reg_<порт>/…` с прежней структурой;
   - для журнала регистрации и хранилища двоичных данных перенос файлов обязателен — без него «кластер может стать полностью неработоспособным»; сам кластер данные не переносит;
   - не назначать сетевой ресурс (резко падает производительность) и один каталог сервисам разных кластеров.
3. **Сеансовые данные в оперативной памяти** [офиц. рекомендация «желательно RAM-drive»; реализация через tmpfs — практика]: том tmpfs, владелец `usr1cv8`, размер с запасом (объём сеансовых данных в пике + 25 % на сборку мусора; переполнение = падение кластера). При перезагрузке содержимое теряется — для сеансовых данных это допустимо.
   ```bash
   id -u usr1cv8; id -g usr1cv8                                    # подставить числа ниже
   echo 'tmpfs /mnt/1c-sess tmpfs size=8G,uid=<UID>,gid=<GID>,mode=0750 0 0' | sudo tee -a /etc/fstab
   sudo mkdir -p /mnt/1c-sess && sudo mount /mnt/1c-sess
   ```
   Каталог назначают сервису сеансовых данных через «Настройки сервисов» (КОРП). С лицензией ПРОФ отдельного каталога для сервиса нет — остаётся вариант 1.

### 3.5. Корректная очистка серверного кэша

Когда нужна [практика]: после аварийных завершений, при ошибках вида «Ошибка формата потока», «Ошибка совместного доступа к файлу snccntx.dat», после восстановления базы средствами СУБД «из-под работающего кластера», при разросшихся сеансовых данных. Официальный сценарий «Остановка службы с очисткой временных файлов» из чек-листа ИТС 5899 (для Windows) удаляет три вещи: `snccntx*` в каталоге кластера, `*.pfl` в общем каталоге данных 1С и содержимое временного каталога. Тот же порядок для Linux:

```bash
V=8.3.27.2074
D=/home/usr1cv8/.1cv8/1C/1cv8                  # каталог данных сервера (значение SRV1CV8_DATA)

# 1. Остановить RAS и сервер, убедиться, что процессов не осталось
sudo systemctl stop ras-$V.service srv1cv8-$V@default
sleep 5
pgrep -u usr1cv8 -a 'ragent|rmngr|rphost' && sudo pkill -9 -u usr1cv8 'ragent|rmngr|rphost'

# 2. Удалить сеансовые данные и профили (реестр и журналы не трогаем)
sudo find "$D"/reg_* -maxdepth 1 -name 'snccntx*' -exec rm -rf {} +
sudo rm -f /home/usr1cv8/.1cv8/1C/1cv8/*.pfl

# 3. Очистить временный каталог сервера, если он выделен отдельно (см. 3.2)
sudo find /var/lib/1c/tmp -mindepth 1 -delete 2>/dev/null

# 4. Запустить и проверить
sudo systemctl start srv1cv8-$V@default ras-$V.service
sleep 10; $RAC cluster list && $RAC infobase summary list --cluster=$($RAC cluster list | awk '/^cluster /{print $3}')
```

Чего делать нельзя:

- удалять или править `1CV8Clst.lst` и `1cv8wsrv.lst` — пропадёт список баз и настройки кластера;
- удалять каталоги `<UUID базы>` целиком — вместе с ними исчезнут журнал регистрации и полнотекстовый индекс;
- чистить что-либо при работающих `rmngr`/`rphost`;
- бездумно выполнять `rm -rf /tmp/*` на работающем сервере.

«Кэш» на стороне клиента (каталоги `%APPDATA%\1C\1cv8` и `%LOCALAPPDATA%\1C\1cv8` в Windows, `~/.1cv8/1C/1cv8` в Linux) — отдельная сущность; его чистят на рабочем месте пользователя.

### 3.6. Полнотекстовый поиск (ППД)

- Индекс хранится в каталоге кластера: `<UUID базы>/1Cv8FTxt` (версия 1) и `<UUID базы>/1Cv8FTxt2` (версия 2); в резервную копию СУБД не входит и при потере строится заново [офиц.].
- **Версия 2** появилась в 8.3.22: отдельные сервисы кластера («Сервис полнотекстового поиска v2», «Сервис координации…»), событие техжурнала `FTS`, для работы нужна Java на серверах кластера (8 и новее; в 8.5.4 — версии от 1.8 до 17). Версия механизма переключается методом `ПолнотекстовыйПоиск.УстановитьВерсиюПолнотекстовогоПоиска()`; параметры JVM — `FtsJavaOpts` в `conf.cfg` (например `FtsJavaOpts=-Xmx8G`) [офиц.]. С 8.5.4 v2 поддерживает отказоустойчивый кластер (число экземпляров сервиса = уровень отказоустойчивости + 1) [офиц.].
- Обновление индекса выполняют регламентные задания конфигурации: в решениях на БСП это «Обновление индекса ППД» (частое) и «Слияние индекса ППД» (раз в сутки) [практика]. Первая полная индексация большой базы надолго нагружает CPU и диск — её запускают в нерабочее время.
- Отключение: в прикладном решении — флажок «Полнотекстовый поиск данных» в настройках администрирования (место зависит от конфигурации); универсально — стандартная функция «Управление полнотекстовым поиском» («Функции для технического специалиста»); программно — `ПолнотекстовыйПоиск.УстановитьРежимПолнотекстовогоПоиска(РежимПолнотекстовогоПоиска.Запретить)`. Отключение имеет смысл на слабых серверах и на копиях баз [практика].
- В кластере из нескольких серверов сервис полнотекстового поиска закрепляют за конкретным сервером требованием назначения — он привязан к файлам на диске и не должен «переезжать» [офиц., ИТС 5899].
- Перестроение: «Очистить индекс» → «Обновить индекс» в стандартной функции. При переходе на некоторые версии платформы перестроение рекомендовано официально (например, 8.3.15; для v2 при переходе на 8.5.4 с разнесёнными сервисами) [офиц., V8Update].

### 3.7. Журнал регистрации и производительность

Факты [офиц., руководство администратора 8.3.27]:

- журнал не входит в базу данных, не попадает ни в резервную копию СУБД, ни в `.dt`; в клиент-серверном варианте лежит в `<каталог кластера>/<UUID базы>/1Cv8Log`;
- форматы: последовательный (`1Cv8.lgf` + фрагменты `*.lgp` + индексы `*.lgx`, размер индекса ~10 % фрагмента) и SQLite (`1Cv8.lgd`). С 8.3.12 по умолчанию последовательный; с 8.3.22 для новых баз только он, конвертация в SQLite запрещена, в следующих версиях SQLite перестанет поддерживаться. Формат запоминается в базе и «переезжает» вместе с резервной копией или `.dt`;
- в клиент-серверном варианте журнал индексируется; число потоков индексации — половина ядер компьютера менеджера кластера, но не более 8 и не менее 1;
- для новой базы регистрируются события всех уровней, новый файл создаётся раз в неделю; период разделения (час, день, неделя, месяц, год) и уровень регистрации задаются в конфигураторе: «Администрирование → Настройка журнала регистрации». Там же «Сократить» — удалить события старше даты, при желании с записью в файл архива;
- полноценная копия базы = копия БД средствами СУБД + копия каталога журнала регистрации (+ хранилище двоичных данных); восстанавливать журнал из копии нужно при остановленном кластере;
- с 8.5.4 сервис журнала регистрации поддерживает отказоустойчивость (только текстовый формат), синхронизация экземпляров — асинхронная [офиц., V8Update].

Практика:

- журнал в формате SQLite на больших объёмах заметно замедляет и запись событий, и просмотр; при повреждении файла `1Cv8.lgd` пользователи получают ошибки `sqlite3_step failed: database disk image is malformed` — лечится по статье ИТС «Восстановление журнала регистрации» либо переводом в последовательный формат (в диалоге настройки это действие помечено как рекомендуемое) [офиц.];
- том с каталогом кластера должен иметь запас: журнал активной базы легко вырастает на гигабайты в месяц. Контроль: `sudo du -sh /home/usr1cv8/.1cv8/1C/1cv8/reg_1541/*/1Cv8Log | sort -h`;
- сокращать журнал регулярно (раз в квартал/год) средствами платформы; удаление старых `*.lgp`/`*.lgx` вручную допустимо только при остановленном сервере и только целыми периодами ⚠ [практика];
- уровень регистрации «Ошибки, предупреждения, информация» вместо «…, примечания» сокращает объём записи; полное отключение журнала лишает возможности расследовать инциденты (методики 1С опираются на журнал при поиске «что делал сеанс»).

### 3.8. Технологический журнал: объём и ротация

- Файл настройки `logcfg.xml` лежит в каталоге конфигурационных файлов: `/opt/1cv8/x86_64/<версия>/conf/` либо `~usr1cv8/.1cv8/1C/1cv8/conf` [офиц.]. Платформа перечитывает его каждые 60 секунд — перезапуск сервера не нужен. После обновления платформы файл из каталога старой версии нужно перенести в каталог новой.
- Без `logcfg.xml` обычный техжурнал выключен, работает только журнал по умолчанию: события `SYSTEM` уровня `ERROR`, хранение 24 часа, каталог `~/.1cv8/1C/1cv8/logs` (в другом месте документации — `~/.1cv8/logs` ⚠) [офиц.].
- Каталог журнала должен быть доступен на запись пользователю `usr1cv8`; разные элементы `<log>`, `<dump>`, `<defaultlog>` — в разные каталоги. Больше 20 элементов `<log>` не рекомендуется — заметно падает производительность [офиц.].
- Элемент `<plansql/>` (сбор планов запросов) «нельзя использовать на продуктивных серверах», только на тестовых [офиц., ИТС 6011].

Атрибуты `<log>`, управляющие объёмом [офиц., руководство администратора 8.3.27; в старых версиях части атрибутов может не быть]:

| Атрибут | Значения | По умолчанию | Смысл |
|---|---|---|---|
| `history` | часы | — | Через сколько часов файлы удаляются. `0` — не удалять (тогда чистить обязаны внешние средства) |
| `rotation` | `period` / `size` | `period` | Ротация файлов по времени или по размеру |
| `rotationperiod` | часы | 1 | Период ротации |
| `rotationsize` | МБ | 100 | Размер файла для ротации |
| `compress` | `none` / `zip` | `none` | Сжатие устаревших файлов при ротации |
| `format` | `text` / `json` | `text` | Формат файлов |
| `placement` | `folders` / `plain` | `folders` | Подкаталоги по процессам или плоская структура |

Рабочая настройка для промышленного сервера — адаптация примера из чек-листа 1С (каталоги Linux, хранение 28 часов) [офиц. состав событий]:


```bash
sudo install -d -o usr1cv8 -g grp1cv8 -m 0750 /var/log/1c /var/log/1c/all

```

Событие `ATTN` добавлено к официальному набору, чтобы видеть срабатывания мониторинга памяти (раздел 2.2). Запись `CALL`/`SCALL`/`DBPOSTGRS` включают временно, на время расследования: на нагруженном сервере это гигабайты в час. Том с техжурналом — не тот, где сеансовые данные [офиц.].

Остальные журналы сервера и их ротация [практика]:

```bash

```

## 4. Регламентные и фоновые задания

### 4.1. Как это устроено

- **Фоновое задание** — выполнение процедуры общего модуля на сервере в отдельном сеансе без клиентского приложения (в списке сеансов — приложение `BackgroundJob`). **Регламентное задание** — объект конфигурации с расписанием; в клиент-серверном варианте планировщик кластера (сервис заданий менеджера `rmngr`) в нужное время запускает его как фоновое задание в одном из рабочих процессов [офиц.].
- Системные фоновые задания платформы (`SystemBackgroundJob`) — предзагрузка контекста базы при перезапуске процесса, фоновая реструктуризация, пересчёт итогов. Задания предзагрузки контекста выполняются без создания сеанса, не пишутся в журнал регистрации и запускаются без учёта требований назначения функциональности; реструктуризацию и пересчёт итогов можно закреплять за серверами (раздел 4.4) [офиц.].
- Регламентные задания выполняются на сервере независимо от того, запущены ли клиенты; исключение — «пассивные» базы, для которых запуск можно разрежать (раздел 4.3).

Посмотреть, что выполняется сейчас:

```bash
# сеансы фоновых заданий (rac выводит объекты блоками, разделёнными пустой строкой)
$RAC session list --cluster=$CL | awk -v RS= -v ORS='\n\n' '/app-id *: *BackgroundJob/'
# сколько сеансов каждого вида
$RAC session list --cluster=$CL | awk -F' *: *' '/^app-id/{a[$2]++} END{for(k in a) print a[k], k}' | sort -rn
# прервать зависшее задание
$RAC session terminate --cluster=$CL --session=<UUID сеанса>
```

В прикладных решениях на БСП расписания, включение и отключение отдельных заданий, история запусков доступны в обработке «Регламентные и фоновые задания» (раздел администрирования; точный путь зависит от конфигурации) [практика].

### 4.2. Блокировка регламентных заданий базы

Свойство информационной базы в кластере «Блокировка регламентных заданий включена»: пока флажок установлен, регламентные задания этой базы не запускаются [офиц.]. Это обязательная мера для любых копий рабочих баз (тест, разработка, копия «на посмотреть»): иначе копия начнёт рассылать почту, выполнять обмены и загрузки от имени рабочей системы. Требование прямо записано в инструкции 1С: в копии базы должны быть «выключены регламентные задания», а сама копия «не участвует в обменах» [офиц., ИТС 5908].

```bash
IB=$($RAC infobase summary list --cluster=$CL | awk -v RS= '/name *: *"?erp_copy"?/' | awk '/^infobase /{print $3}')
$RAC infobase update --cluster=$CL --infobase=$IB --infobase-user=Администратор --infobase-pwd='***' --scheduled-jobs-deny=on
$RAC infobase info   --cluster=$CL --infobase=$IB --infobase-user=Администратор --infobase-pwd='***' | grep scheduled-jobs-deny
```

- Параметры `--infobase-user`/`--infobase-pwd` — администратор самой базы (нужны, если в базе есть пользователи).
- При создании базы блокировку ставят сразу: флажок в диалоге «Новая информационная база» или параметр `SchJobDn=Y` в строке соединения пакетного создания, например `1cv8 CREATEINFOBASE Srvr=srv1c\;Ref=erp_copy\;SchJobDn=Y\;SQLSrvr=127.0.0.1\;DBMS=PostgreSQL\;DB=erp_copy\;DBUID=postgres\;DBPwd=***\;CrSQLDB=Y\;` [офиц., пример из ИТС 6011].
- В конфигурациях на БСП есть собственный механизм «блокировка работы с внешними ресурсами»: при обнаружении, что база перемещена или скопирована, задания, работающие с внешними ресурсами, приостанавливаются до решения администратора [практика]. Он не заменяет блокировку на уровне кластера.

Блокировка начала сеансов (для обслуживания) — соседние свойства той же базы [офиц.]:

```bash
$RAC infobase update --cluster=$CL --infobase=$IB --infobase-user=… --infobase-pwd=… \
     --sessions-deny=on --denied-from="2026-10-10T22:00:00" --denied-to="2026-10-11T02:00:00" \
     --denied-message="Обновление до 02:00" --permission-code="svc123"
```

Существующие сеансы при этом продолжают работать (их нужно завершить отдельно), новые не открываются. С кодом разрешения можно войти: параметр `/UC svc123` в строке запуска клиента или `UC=svc123` в строке соединения. Формат дат — как в выводе `rac infobase info` ⚠ (проверьте на своей версии).

### 4.3. «Пассивные» базы: разрежение запуска заданий

Для кластеров с большим числом редко используемых баз у информационной базы есть три свойства [офиц., руководство администратора 8.3.27]:

| Свойство | Диапазон | Смысл |
|---|---|---|
| Задержка выгрузки конфигурации рабочим процессом | 0–4 294 967 с | Сколько секунд `rphost` держит загруженные данные базы после разрыва последнего соединения; ускоряет следующие подключения и старты заданий |
| Минимальный период запуска регламентных заданий | 0–4 294 967 с | Если в базе нет активных пользовательских сеансов, задания запускаются не чаще этого периода, пачкой за одну загрузку контекста |
| Максимальное смещение запуска регламентных заданий | 0–4 294 967 с | Случайная задержка от 0 до значения, чтобы задания разных баз не стартовали одновременно. Действует, только если минимальный период не 0 |

База считается пассивной, если в ней нет не спящих пользовательских сеансов (конфигуратор, толстый и тонкий клиент, веб-клиент, мобильный клиент, COM-соединение дольше 20 с); фоновые задания, HTTP- и веб-сервисы пользовательскими сеансами не считаются. В активной базе и при нулевых значениях обоих параметров задания запускаются строго по расписанию.

### 4.4. Вынос фоновых заданий на отдельный рабочий сервер

Механизм — **требования назначения функциональности** рабочего сервера [офиц.]:

- требование = объект (сервис кластера, «Клиентское соединение с ИБ» или «Любой объект требования») + тип («Назначать», «Не назначать», «Авто») + необязательные имя базы и значение дополнительного параметра;
- требования сервера просматриваются сверху вниз, срабатывает **первое** подходящее; серверы с явным «Назначать» получают объект в первую очередь, серверы с «Не назначать» исключаются; если подходящих серверов нет — клиент получает ошибку;
- изменения начинают действовать только после команды «Применить требования назначения функциональности» — частичной (переносятся сервисы, мигрирующие без потери данных) или полной (может оборвать клиентские сеансы);
- **ограничение ПРОФ**: требования допустимы, только если у всех правил пустые «Имя ИБ» и «Значение дополнительного параметра». То есть закрепить сервис лицензирования за сервером можно, а отделить фоновые задания — только с лицензией КОРП.

Значения дополнительного параметра для объекта «Клиентское соединение с ИБ» [офиц., руководство 8.3.27]:

| Что закрепляем | Значение дополнительного параметра |
|---|---|
| Все фоновые задания, запущенные из встроенного языка | `BackgroundJob.CommonModule` |
| Конкретную процедуру | `BackgroundJob.CommonModule.<Модуль>.<Метод>` |
| Конкретное регламентное задание | `BackgroundJob.ScheduledJob.<Имя объекта конфигурации>` |
| Формирование отчётов | `BackgroundJob.GenerateReport.<Полное имя объекта>` |
| Обновление полнотекстового индекса | `BackgroundJob.FullTextSearchIndexUpdate` |
| Системные фоновые задания: реструктуризация, пересчёт итогов | `SystemBackgroundJob.DBConfigUpdate`, `SystemBackgroundJob.RecalcTotals` |
| Тонкий клиент напрямую / толстый клиент / конфигуратор | `1CV8CDirect` / `1CV8` / `Designer` |
| Всё, что приходит через веб-сервер | `WebServerExtension` |
| Сеансы конкретного пользователя или группы (8.3.27+) | `UserName.<Имя>` / `UserAssignmentRuleKey.<Значение>` |

Пример: два рабочих сервера, все фоновые задания — на `srv1c-2`, пользователи — на `srv1c-1`.

```bash
$RAC server list --cluster=$CL | grep -E '^server |agent-host'           # UUID серверов → SRV1, SRV2
# srv1c-2: фоновые задания назначать, остальные клиентские соединения — нет
$RAC rule insert --cluster=$CL --server=$SRV2 --position=0 --object-type=Connection \
     --rule-type=always --application-ext='BackgroundJob.CommonModule'
$RAC rule insert --cluster=$CL --server=$SRV2 --position=1 --object-type=Connection --rule-type=never
# srv1c-1: фоновые задания не назначать
$RAC rule insert --cluster=$CL --server=$SRV1 --position=0 --object-type=Connection \
     --rule-type=never --application-ext='BackgroundJob.CommonModule'
$RAC rule list  --cluster=$CL --server=$SRV2
$RAC rule apply --cluster=$CL --partial
```

⚠ Идентификатор объекта требования (`--object-type=Connection`) записан по памяти; допустимые значения смотрите в `$RAC help rule` и в выводе `$RAC service list --cluster=$CL` (имена сервисов: `LicenseService`, `EventLogService`, `FulltextSearchService`, `SessionDataService` и т. д.). Ключи `--rule-type=auto|always|never`, `--application-ext`, `--infobase-name`, `--position`, `--priority`, команды `rule apply --full|--partial` — из справки `rac` [офиц.].

Вывести сервер из работы без обрыва сеансов (перед удалением из кластера или обслуживанием) [офиц.]: добавить ему первым правилом «Любой объект требования — Не назначать», применить требования, дождаться, пока сеансы уйдут на другие серверы. В 8.5.4 для отказоустойчивого кластера с лицензией КОРП появились команды `rac server disable` / `enable` и свойство «Сервер включён» [офиц., V8Update].

## 5. Отказоустойчивость и масштабирование кластера 1С

### 5.1. Что даёт отказоустойчивый кластер

По документации отказоустойчивый кластер обеспечивает бесперебойную работу пользователей при (а) плановом или аварийном перезапуске рабочих процессов и менеджеров и (б) выходе из строя сервера, входящего в кластер [офиц.]. Составляющие:

- **Транзакционность сеансовых данных** — сеанс сохраняется при сбоях и восстанавливается после переподключения.
- **Повтор последнего вызова** — если ошибка передачи данных получена до фиксации первой транзакции серверного вызова (и вызов был вне транзакции), клиент сам переподключается и повторяет вызов, пользователь продолжает работу. Если ошибка получена **после** фиксации первой транзакции вызова — сеанс завершается, клиентское приложение нужно перезапустить.
- **Резервирование рабочих процессов** (8.3.16+) — для баз с флажком «Резервирование рабочих процессов» кластер заранее держит запущенные резервные `rphost` с загруженными метаданными; при падении рабочего процесса сеансы переключаются на резервный без долгой паузы. Число резервных процессов определяется свойством «Количество ИБ на процесс». В `rac` — параметр `reserve-working-processes` команд `infobase` ⚠ (точное написание — `$RAC help infobase`).
- **Уровень отказоустойчивости** — максимальное число рабочих серверов, одновременный отказ которых не приводит к аварийному завершению сеансов. Сервисы с поддержкой репликации размещаются на `уровень + 1` серверах: один экземпляр активный, остальные резервные; репликация асинхронная, синхронизация раз в секунду. Экземпляр сервиса сеансовых данных создаётся на каждый сеанс и тоже держится на `уровень + 1` серверах.

Главная формула [офиц.]:

```text
Число центральных серверов = Уровень отказоустойчивости + 1
```

Центральные серверы хранят реестр кластера и принимают подключения клиентов. Разбор на примере трёх рабочих серверов с уровнем 1 [офиц.]:

| Что отказало | Центральных серверов в кластере: 1 | Центральных серверов: 2 |
|---|---|---|
| Обычный рабочий сервер | сеансы сохраняются, новые подключения возможны | то же |
| Центральный сервер | кластер перестаёт обслуживать пользователей, хотя два сервера живы | работа продолжается через второй центральный |
| Два сервера сразу | уровень превышен: сеансы упавших серверов закрываются | то же; пользователи оставшегося сервера работают |

Цена [офиц.]: «любое повышение уровня отказоустойчивости сказывается на производительности кластера», так как ресурсы тратятся на синхронизацию данных между серверами; «не нужно просто так указывать максимально возможный уровень» (ИТС 5908). **Уточнено 11.10.2026** (документация 8.3.27, «Руководство администратора», разд. 1.6.3.3): серверная лицензия ПРОФ даёт все возможности сервера, кроме явно перечисленных, и уровня отказоустойчивости в этом перечне нет — то есть ненулевой уровень отказоустойчивости с лицензией ПРОФ доступен. В перечень исключений входят дополнительное управление распределением по рабочим серверам (в разрезе баз, видов клиентских приложений и фоновых заданий), профили безопасности, внешнее управление сеансами, «Количество ИБ на процесс» и «Безопасный расход памяти за один вызов», режим распределения нагрузки «Приоритет по памяти», более 500 сеансов в одной базе и более 12 ядер процессора. Управление состоянием сервера «включён/выключен» в перечне 8.3.27 не упоминается. Ранее было: Доступность ненулевого уровня отказоустойчивости с лицензией ПРОФ в сессии подтвердить не удалось; расширенные требования назначения и управление сервером «включён/выключен» требуют КОРП.

Чего кластер 1С **не** резервирует: сервер СУБД (нужна своя схема — потоковая репликация PostgreSQL с автоматическим переключением, см. статью ИТС 5971 и статьи базы знаний о PostgreSQL), веб-серверы (нужен балансировщик или несколько публикаций), файлы на диске конкретного сервера (журнал регистрации стал отказоустойчивым только в 8.5.4, полнотекстовый поиск v2 — тоже с 8.5.4).

### 5.2. Настройка второго центрального сервера (пошагово)

Предварительные условия [практика, требования к версиям и лицензиям — офиц.]:

- на втором сервере установлена платформа **той же сборки**, служба `srv1cv8-…@default` запущена от `usr1cv8`;
- имена всех серверов кластера разрешаются в IP на каждом сервере, на веб-серверах и на клиентах (DNS или `/etc/hosts`); в `/etc/hosts` имя сервера не должно указывать на `127.0.1.1`;
- между серверами и от клиентов открыты 1540, 1541, 1560–1591/tcp; время синхронизировано;
- на втором сервере есть серверная лицензия (раздел 5.4);
- свежеустановленный сервер при первом старте создал собственный локальный кластер на порту 1541 — его нужно удалить, иначе порт менеджера будет занят.

```bash
# на втором сервере (srv1c-2): удалить его локальный кластер
/opt/1cv8/x86_64/$V/ras cluster --daemon                                  # если RAS ещё не запущен как служба
C2=$($RAC cluster list | awk '/^cluster /{print $3}'); $RAC cluster remove --cluster=$C2

# на первом сервере (srv1c-1): добавить srv1c-2 как центральный и задать уровень отказоустойчивости
$RAC server insert --cluster=$CL --agent-host=srv1c-2 --agent-port=1540 --port-range=1560:1591 \
     --name=srv1c-2 --using=main --cluster-port=1541
$RAC cluster update --cluster=$CL --session-fault-tolerance-level=1
$RAC server list  --cluster=$CL
$RAC manager list --cluster=$CL
```

Дальше: закрепить требованиями назначения сервисы, привязанные к файлам и лицензиям (сервис лицензирования, журнал регистрации, полнотекстовый поиск), и исправить строки соединения клиентов и публикаций.

### 5.3. Поведение клиентов: список серверов в строке соединения

Клиент должен знать адреса всех центральных серверов. Документация: при использовании кластера с несколькими центральными серверами их список указывают прямо в поле «Кластер серверов» через запятую без пробелов; формат — `Server1,Server2:Port,Server3` [офиц., руководство администратора и ИТС 5908].

```text
Диалог добавления базы, поле «Кластер серверов»:   srv1c-1,srv1c-2:1541
Строка соединения:                                  Srvr="srv1c-1,srv1c-2";Ref="erp";
Файл списка баз ibases.v8i:                         Connect=Srvr="srv1c-1,srv1c-2";Ref="erp";
Публикация на веб-сервере (default.vrd):            ib="Srvr=&quot;srv1c-1,srv1c-2&quot;;Ref=&quot;erp&quot;;"
Командная строка клиента (список адресов кластера через запятую без пробелов подтверждён приложением 7 документации 8.3.27 (параметр `Srvr` строки соединения); на практике не подтверждено):       1cv8c ENTERPRISE /S"srv1c-1,srv1c-2\erp"
```

- Клиент перебирает адреса из списка, пока не подключится к работающему центральному серверу; дальше менеджер кластера сообщает ему адрес рабочего процесса (имя хоста и порт из диапазона).
- После сбоя сервера, на котором работал сеанс: либо незаметное переподключение с повтором вызова, либо сообщение об ошибке и необходимость перезапустить клиент — по правилам из раздела 5.1.
- Веб-публикации правят в `default.vrd` каждого веб-сервера и перезапускают Apache.

### 5.4. Лицензии в отказоустойчивом кластере

- Серверная лицензия нужна **на каждый компьютер**, на котором работают процессы кластера: «если кластер серверов работает на нескольких компьютерах, то нужно приобрести отдельную лицензию на каждый компьютер» [офиц., ответы на вопросы по лицензированию].
- На серверах, которые играют роль центральных, клиентских лицензий должно хватать «для работы всех пользователей при отсутствии одного из центральных серверов» [офиц., ИТС 5908].
- Программная лицензия привязана к компьютеру, на котором активирована. Сервис лицензирования явно назначают на этот сервер требованием назначения, а при активации через сервер 1С указывают имя именно этого сервера — иначе кластер не сможет использовать лицензию [офиц.]. Сервис поддерживает миграцию без потери данных; если выдавший лицензии экземпляр временно недоступен, сервис не более 20 секунд выдаёт их дубликаты [офиц.].
- Аппаратные ключи: клиентские лицензии через сервер раздаёт менеджер кластера, на который назначен сервис сеансовых данных, — он использует локальный ключ своего компьютера и один сетевой ключ каждой серии; для распределения сеансов по нескольким ключам сервис сеансовых данных назначают менеджерам на разных компьютерах [офиц., ИТС 3596].
- 8.5.4 и новее: HASP License Manager заменён «1С:Предприятие 8 — Менеджер лицензий» (`rmlic`), порты 475 и 1544 (TCP и UDP); на Linux порт ниже 1024 требует прав администратора. Рекомендация для кластера: после установки 8.5.4 запускать `ragent` на всех рабочих серверах раньше любых других приложений платформы; часы серверов и менеджера лицензий не должны расходиться больше чем на 20 минут [офиц., ИТС 6041].
- Проверка: `$RAC process list --cluster=$CL --licenses` (серверные), `$RAC session list --cluster=$CL --licenses` (клиентские; поля `license-type`, `issued-by-server`, `rmngr-address`).

### 5.5. Масштабирование: несколько рабочих серверов

Два пути [офиц.]: нарастить мощность единственного сервера или добавить рабочие серверы. Кластер сам распределяет сервисы по серверам равномерно (по типам сервисов, базам и сеансам), а соединения — по процессам с учётом «доступной производительности».

- **Доступная производительность** рабочего процесса = 10 000 / среднее за 5 минут время эталонных операций (память, файл, оценка загрузки CPU), измеряется каждые 5 секунд. Различие в 25 % считается существенным; при изменении соотношения клиенты перераспределяются в течение ~10 минут [офиц.].
- **Режим распределения нагрузки** (свойство кластера; выбор режима — только КОРП) [офиц.]:
  - «по производительности» — подходят серверы и процессы с производительностью не ниже 75 % от лучшего; среди них выбирается процесс с наибольшим числом соединений с нужной базой, из лучших процессов всех серверов — случайный;
  - «по памяти» — подходят серверы с производительностью не ниже 25 % от лучшего; среди процессов, уже обслуживающих базу, выбирается тот, у кого больше свободной памяти.
  - существующее соединение может переехать на другой процесс, только если нет исполняемого вызова, открытой транзакции и временных таблиц.
- **Обычный (не центральный) рабочий сервер** добавляют той же командой `rac server insert … --using=normal`. Уровень отказоустойчивости при этом можно оставить 0: это масштабирование без резервирования.
- **Менеджер под каждый сервис** (`--dedicate-managers=all`) позволяет увидеть нагрузку отдельных сервисов и развести их по процессам.
- Нагрузку процессов показывает `rac process list`: `available-perfomance` (так в выводе), `avg-call-time`, `avg-server-call-time`, `avg-db-call-time`, `avg-lock-call-time`, `avg-threads`, `connections`, `memory-size`.
- В 8.3.27 появилась возможность распределять сеансы конкретных пользователей по серверам (требования с `UserName.<Имя>` или ключом требования назначения пользователя) [офиц.].

Типовая схема на 500+ пользователей [практика]: два центральных сервера с пользовательскими сеансами (уровень отказоустойчивости 1), третий рабочий сервер под фоновые задания и обмены, отдельные веб-серверы за балансировщиком, отказоустойчивый PostgreSQL за единым адресом.

## 6. Эксплуатационные регламенты (runbook)

Общие правила из методики 1С «Организация эксплуатации крупной информационной системы» [офиц., ИТС 5905]: все изменения рабочей системы сначала проходят подготовительный стенд (копия рабочей базы, та же платформа, СУБД, ОС и настройки); изменения в рабочей зоне вносятся по заранее подготовленным чек-листам; ведётся журнал проведённых работ («кто, когда, на каком сервере, что сделал»); стенд разворачивается из рабочих резервных копий — этим же проверяется, что копии пригодны и сколько времени занимает восстановление; допустимое время простоя при откате на предыдущую версию — 10 минут.

Переменные для всех примеров раздела:

```bash
V=8.3.27.2074; RAC=/opt/1cv8/x86_64/$V/rac
CL=$($RAC cluster list | awk '/^cluster /{print $3}')
D=/home/usr1cv8/.1cv8/1C/1cv8          # каталог данных сервера 1С
IB=<UUID базы>                         # из вывода: $RAC infobase summary list --cluster=$CL
```

### 6.1. Ежедневные проверки (5–10 минут)

```bash
# 1. Службы и сбои
systemctl is-active srv1cv8-$V@default ras-$V.service postgresql apache2
systemctl --failed --no-pager

# 2. Ресурсы: нагрузка, память, место, inode
uptime; free -h
df -h -x tmpfs -x devtmpfs
df -i | awk 'NR==1 || $5+0 > 70'

# 3. Процессы кластера: размер и возраст (перезапускались ли ночью)
ps -C ragent,rmngr,rphost -o pid,rss,etimes,args --sort=-rss

# 4. Сеансы
$RAC session list --cluster=$CL | grep -c '^session '
$RAC session list --cluster=$CL | awk -F' *: *' '/^app-id/{a[$2]++} END{for(k in a) print a[k], k}' | sort -rn

# 5. Ошибки за сутки
journalctl -u "srv1cv8-$V@default" --since "-24h" -p warning --no-pager | tail -20
journalctl -k --since "-24h" --no-pager | grep -i -E 'out of memory|oom-kill|i/o error|ext4-fs error|xfs.*error'
grep -rh ',ATTN,' /var/log/1c/all 2>/dev/null | tail -5                       # срабатывания мониторинга кластера
grep -rhoP ',EXCP,.*?Descr=\K.{0,100}' /var/log/1c/all 2>/dev/null | sort | uniq -c | sort -rn | head

# 6. PostgreSQL
pg_isready -h 127.0.0.1 -p 5432
sudo -u postgres psql -x -c "SELECT count(*) AS total, count(*) FILTER (WHERE state='active') AS active,
       count(*) FILTER (WHERE wait_event_type='Lock') AS waiting_lock,
       max(now()-xact_start) AS oldest_xact FROM pg_stat_activity WHERE backend_type='client backend';"
sudo tail -n 50 /var/log/postgresql/postgresql-*-main.log | grep -E 'ERROR|FATAL|PANIC'

# 7. Резервные копии: последняя копия существует, свежая и не нулевого размера
ls -lht /backup/pg/ | head -5
```

Что считать отклонением: служба не `active`; свободного места меньше 10–15 %; `available` памяти меньше 5–10 % ОЗУ или активный своп (`vmstat 5`, колонки `si`/`so`); `rphost` существенно больше обычного размера; события `ATTN` и массовые `EXCP`; транзакции старше десятков минут; ошибки `FATAL`/`PANIC` в журнале PostgreSQL; нет свежей резервной копии. Пороги оповещений из чек-листа 1С: место < 10 %, свободная память < 200 МБ, CPU > 90 % — каждое в течение 5 минут [офиц.].

### 6.2. Еженедельные проверки

| Что | Команда / действие | Зачем |
|---|---|---|
| Рост каталогов | `sudo du -sh $D/reg_*/* \| sort -h \| tail`; `sudo du -sh /var/lib/postgresql /var/log/1c /backup` | Спрогнозировать заполнение дисков (журнал регистрации, индекс поиска, WAL, копии) |
| Размеры баз | `SELECT datname, pg_size_pretty(pg_database_size(datname)) FROM pg_database WHERE NOT datistemplate ORDER BY pg_database_size(datname) DESC;` | Тренд роста |
| «Мёртвые» строки и автоочистка | `SELECT relname, n_live_tup, n_dead_tup, last_autovacuum, last_autoanalyze FROM pg_stat_user_tables ORDER BY n_dead_tup DESC LIMIT 15;` | Автоочистка успевает? (выключать её нельзя — «это приведёт к росту размеров базы и серьёзной деградации производительности» [офиц.]) |
| Временные файлы | `SELECT sum(temp_files) AS temp_files, pg_size_pretty(sum(temp_bytes)) AS temp_size FROM pg_stat_database;` | Подбор `work_mem` [офиц., ИТС 5866] |
| Попадание в кэш | `SELECT round(100*sum(blks_hit)/sum(blks_hit+blks_read),3) FROM pg_stat_database;` | Ниже ~80 % — СУБД не хватает памяти [офиц. критерий из методики сайзинга] |
| Контрольные точки | PostgreSQL ≤ 16: `SELECT checkpoints_timed, checkpoints_req FROM pg_stat_bgwriter;`; 17+: `SELECT num_timed, num_requested FROM pg_stat_checkpointer;` | Много «по требованию» — мал `max_wal_size` |
| Слоты и архив WAL | `SELECT slot_name, active, pg_size_pretty(pg_wal_lsn_diff(pg_current_wal_lsn(), restart_lsn)) FROM pg_replication_slots;` `SELECT * FROM pg_stat_archiver;` | Причины роста `pg_wal` |
| Обновления ОС | `apt list --upgradable 2>/dev/null \| head`; `cat /var/run/reboot-required 2>/dev/null` | Плановое окно обновлений и перезагрузки |
| Техжурнал 1С | выборка `EXCP`, `ATTN`, `TTIMEOUT`, `TDEADLOCK` за неделю | Повторяющиеся ошибки, таймауты и взаимоблокировки |
| APDEX | отчёт подсистемы «Оценка производительности» | Не ухудшились ли ключевые операции (раздел 8.1) |
| Лицензии | раздел 6.10 | Запас клиентских лицензий |
| Сертификаты, диски | `openssl x509 -enddate -noout -in <сертификат>`; `sudo smartctl -H /dev/sda` (на «железе») | Не пропустить истечение и деградацию |

Раз в месяц–квартал: тестовое восстановление из резервной копии с замером времени (в чек-листе 1С — обязательный пункт [офиц.]); пересчёт итогов регистров — при интенсивной работе в таблицах итогов копятся записи с нулевыми ресурсами, из-за которых замедляются запросы к остаткам [офиц., ИТС 5371]; сокращение журнала регистрации; пересмотр лимитов памяти кластера по фактическому потреблению; проверка, что в рабочем кластере не появилось тестовых баз.

### 6.3. Правильная последовательность остановки и запуска

Принцип: сервер 1С — клиент СУБД, веб-сервер — клиент сервера 1С. Останавливают «сверху вниз», запускают «снизу вверх».

**Остановка (сервер «всё в одном»):**

```bash
# 0. Предупредить пользователей; запретить новые сеансы и регламентные задания (на время работ)
$RAC infobase update --cluster=$CL --infobase=$IB --infobase-user=… --infobase-pwd=… \
     --sessions-deny=on --scheduled-jobs-deny=on --permission-code="svc123" --denied-message="Регламентные работы"
# 1. Посмотреть, кто остался и идут ли фоновые задания; при необходимости завершить сеансы
#    (цикл ниже завершает ВСЕ сеансы кластера; для одной базы добавьте к session list ключ --infobase=$IB)
$RAC session list --cluster=$CL | grep -E '^(session |user-name|app-id)'
for s in $($RAC session list --cluster=$CL | awk '/^session /{print $3}'); do $RAC session terminate --cluster=$CL --session=$s; done
# 2. Веб-сервер → RAS → сервер 1С
sudo systemctl stop apache2
sudo systemctl stop ras-$V.service
sudo systemctl stop srv1cv8-$V@default
pgrep -u usr1cv8 -a 'ragent|rmngr|rphost' || echo "процессов 1С нет"
# 3. Убедиться, что к базам никто не подключён, и остановить СУБД
sudo -u postgres psql -Atc "SELECT datname, count(*) FROM pg_stat_activity WHERE backend_type='client backend' AND pid<>pg_backend_pid() GROUP BY 1;"
sudo systemctl stop postgresql
```

**Запуск:**

```bash
sudo systemctl start postgresql
until pg_isready -q -h 127.0.0.1 -p 5432; do sleep 1; done
sudo systemctl start srv1cv8-$V@default
sudo systemctl start ras-$V.service
sudo systemctl start apache2
sudo ss -tlnp | grep -E ':(1540|1541|1545|15[6-9][0-9]|5432|80|443)\s'
$RAC cluster list && $RAC infobase summary list --cluster=$CL
# снять блокировки, поставленные на шаге 0
$RAC infobase update --cluster=$CL --infobase=$IB --infobase-user=… --infobase-pwd=… --sessions-deny=off --scheduled-jobs-deny=off
```

Замечания:

- Если `systemctl stop srv1cv8-…` «висит» — systemd ждёт завершения процессов (по умолчанию до 90 с), затем принудительно завершает их; вручную: `sudo pkill -9 -u usr1cv8 'ragent|rmngr|rphost'`. После принудительного завершения стоит выполнить очистку кэша (раздел 3.5).
- Имя юнита PostgreSQL зависит от сборки: у пакетов в стиле Debian/Ubuntu (в том числе сборок 1С) — зонтичный `postgresql.service` и экземпляр `postgresql@17-main.service`; у Postgres Pro — `postgrespro-std-17.service` ⚠ (проверьте `systemctl list-units 'postgres*'`).
- Чтобы порядок соблюдался и при перезагрузке ОС, на совмещённом сервере добавьте зависимость в drop-in юнита 1С [практика]:
  ```bash
  sudo systemctl edit srv1cv8-$V@default
  #   [Unit]
  #   After=postgresql.service postgresql@17-main.service
  #   Wants=postgresql.service
  ```
  systemd останавливает юниты в порядке, обратном `After=`, поэтому при выключении сервер 1С будет остановлен раньше PostgreSQL. Drop-in привязан к номеру версии платформы — после обновления его нужно перенести.
- В кластере из нескольких рабочих серверов останавливают сначала обычные рабочие серверы, центральный — последним; запускают в обратном порядке (центральный первым) [практика].
- Блокировка сеансов, установленная в свойствах базы, хранится в кластере и переживает перезапуск — не забудьте её снять.

### 6.4. Очистка серверного кэша

Порядок и сценарий — в разделе 3.5. В журнал работ записывают причину: регулярная потребность в очистке — признак проблемы (аварийные завершения процессов, рост сеансовых данных), а не норма.

### 6.5. Ротация логов и техжурнала

| Журнал | Где | Кто чистит | Проверка |
|---|---|---|---|
| Техжурнал 1С | каталоги из `logcfg.xml` (например `/var/log/1c/…`) | сама платформа по `history` (часы) | `sudo du -sh /var/log/1c/*` |
| Техжурнал по умолчанию | `~usr1cv8/.1cv8/1C/1cv8/logs` | платформа, 24 часа | `sudo du -sh /home/usr1cv8/.1cv8/1C/1cv8/logs` |
| Журнал регистрации | `$D/reg_1541/<UUID>/1Cv8Log` | **никто**; вручную «Сократить» в конфигураторе | `sudo du -sh $D/reg_*/*/1Cv8Log` |
| Журнал systemd | `/var/log/journal` | journald (`SystemMaxUse=`) | `journalctl --disk-usage` |
| PostgreSQL | `/var/log/postgresql/` или `<PGDATA>/log` | logrotate либо сам PostgreSQL | `ls -lh /var/log/postgresql/` |
| Apache | `/var/log/apache2/` | logrotate (`/etc/logrotate.d/apache2`) | `ls -lh /var/log/apache2/` |
| Дампы аварийных завершений | `/var/lib/systemd/coredump`, `/var/crash` ⚠ (зависит от настройки ОС) | `systemd-coredump` по лимитам / вручную | `coredumpctl list 2>/dev/null \| tail`; `sudo du -sh /var/crash /var/lib/systemd/coredump` |

Настройки и примеры — в разделе 3.8. Аварийные дампы на Linux создаются средствами ОС (платформа посылает процессу сигнал `SIGABRT`), а не настройками `logcfg.xml` [офиц.]; один дамп `rphost` может занимать гигабайты.

### 6.6. Обновление платформы

Официальный порядок (глава «Обновление кластера серверов» руководства администратора 8.3.27) [офиц.]:

*Подготовка (без ограничения по времени):* получить дистрибутивы сервера и клиента одной версии; получить права администратора ОС и СУБД; выложить клиентский дистрибутив на сетевой ресурс или веб-сервер; провести приёмочное тестирование новой версии на тестовом контуре; подготовить сценарии регистрации автозапуска (для Linux — команды systemd); **заранее установить новую версию платформы на все компьютеры кластера** (версии ставятся рядом в `/opt/1cv8/x86_64/<версия>/`).

*Обновление (как можно быстрее):*

1. Заблокировать начало новых сеансов во всех базах кластера.
2. Сделать резервные копии средствами СУБД.
3. Отключить всех пользователей.
4. Остановить кластер.
5. Переключить автозапуск на новую версию (на всех компьютерах кластера).
6. Запустить кластер.
7. Обновить публикации на веб-серверах (конфигуратором или `webinst`).
8. Перезапустить веб-серверы.
9. Разрешить начало сеансов.

Команды для Linux (подробности, drop-in, откат — раздел 13 статьи `02-ustanovka-servera-ubuntu.md`):

```bash
OLD=8.3.27.1688; NEW=8.3.27.2074
sudo systemctl disable --now ras-$OLD.service srv1cv8-$OLD@default
sudo cp -a /home/usr1cv8/.1cv8/1C/1cv8 /root/1c-cluster-backup-$(date +%F)       # реестр и настройки кластера
sudo systemctl link /opt/1cv8/x86_64/$NEW/srv1cv8-$NEW@.service /opt/1cv8/x86_64/$NEW/ras-$NEW.service
sudo systemctl enable --now srv1cv8-$NEW@default ras-$NEW.service
sudo cp -a /opt/1cv8/x86_64/$OLD/conf/logcfg.xml /opt/1cv8/x86_64/$NEW/conf/ 2>/dev/null   # техжурнал
grep -rn "x86_64/$OLD" /etc/apache2/ /etc/systemd/system/ 2>/dev/null                      # где остались пути старой версии
sudo systemctl restart apache2
```

После обновления: версии клиентов должны совпасть с сервером (иначе «Версия клиента отличается от версии сервера»); при переходе на 8.5.4 — учесть новый менеджер лицензий (раздел 5.4); при смене «большой» версии прочитать `V8Update.htm` новой версии (`/opt/1cv8/x86_64/<версия>/docs/ru/V8Update.htm`) на предмет обязательных действий (например, перестроение полнотекстового индекса).

### 6.7. Обновление конфигураций

Порядок [практика, опирается на официальные правила резервного копирования и блокировок]:

1. **Резервная копия** средствами СУБД (`pg_dump -Fc` или физическая копия) и проверка, что она читается. Выгрузка в `.dt` резервной копией не является [офиц.].
2. **Блокировка** сеансов и регламентных заданий с кодом разрешения, завершение сеансов (раздел 6.3, шаги 0–1).
3. **Обновление**. Конфигуратор запускают в пакетном режиме либо с рабочего места администратора (Windows или Linux с графикой, та же сборка платформы), либо на сервере (нужен компонент толстого клиента и виртуальный дисплей):
   ```bash
   sudo apt install xvfb
   xvfb-run -a /opt/1cv8/x86_64/$V/1cv8 DESIGNER /S"srv1c\erp" /N"Администратор" /P"***" /UC svc123 \
        /UpdateCfg /distr/erp/1Cv8.cfu /UpdateDBCfg /DisableStartupDialogs /Out /tmp/update-erp.log
   cat /tmp/update-erp.log
   ```
   Для конфигураций без поддержки (собственная разработка, выгруженный `.cf`) подходит `ibcmd`, которому графика не нужна; он работает с базой напрямую, поэтому в базе не должно быть ни одного сеанса [офиц., описание ограничений `ibcmd`]:
   ```bash
   IBCMD=/opt/1cv8/x86_64/$V/ibcmd
   DB="--dbms=PostgreSQL --database-server=127.0.0.1 --database-name=erp --database-user=postgres --database-password=ПАРОЛЬ_СУБД --data=/var/lib/1c/ibcmd-erp"
   $IBCMD infobase config load  $DB --user=Администратор --password=ПАРОЛЬ /distr/erp/1Cv8.cf
   $IBCMD infobase config apply $DB --user=Администратор --password=ПАРОЛЬ --force
   ```
   Команды обновления по файлу `.cfu` у `ibcmd` в справочнике команд 8.3.27 нет — конфигурации на поддержке обновляют конфигуратором.
4. **Обработчики обновления** прикладного решения: первый вход администратора с кодом разрешения (`/UC svc123`) — БСП выполнит обновление данных; дождаться завершения отложенных обработчиков, если этого требует описание релиза.
5. **Проверка** (вход, ключевые документы и отчёты, обмены), **снятие блокировок**, запись в журнал работ; резервную копию хранить до уверенности в результате.

Что учитывать на PostgreSQL: реструктуризация больших таблиц требует свободного места (временная копия таблицы и рост WAL) и времени — оценивают на копии базы; после массовых изменений данных полезно выполнить `ANALYZE` (`sudo -u postgres vacuumdb -d erp --analyze-only --jobs=4`); динамическое обновление на рабочей базе в часы работы пользователей лучше не применять [практика].

### 6.8. Перезагрузка ОС

```bash
cat /var/run/reboot-required 2>/dev/null; cat /var/run/reboot-required.pkgs 2>/dev/null     # нужна ли перезагрузка и из-за чего
# 1. Блокировка сеансов и заданий, завершение сеансов — как в 6.3
# 2. Штатная остановка прикладных служб сверху вниз (apache2 → ras → srv1cv8 → postgresql)
sudo systemctl stop apache2 ras-$V.service srv1cv8-$V@default && sudo systemctl stop postgresql
# 3. Перезагрузка
sudo systemctl reboot
# 4. После загрузки
systemctl is-active postgresql srv1cv8-$V@default ras-$V.service apache2
systemctl --failed --no-pager; journalctl -b -p err --no-pager | tail -30
timedatectl | grep -E 'synchronized|Time zone'
df -h; findmnt --verify                      # все ли тома смонтированы (особенно отдельные под данные и tmpfs)
$RAC cluster list && $RAC infobase summary list --cluster=$CL
```

- Перед перезагрузкой после обновления ядра убедитесь, что автозапуск служб включён: `systemctl is-enabled srv1cv8-$V@default ras-$V.service postgresql`.
- Если сеансовые данные лежат на tmpfs, после загрузки каталог пуст — это нормально; если на tmpfs лежит что-то ещё из каталога кластера — это ошибка настройки.
- Минорные обновления PostgreSQL ставят в том же окне: остановить сервер 1С → обновить пакеты СУБД → запустить СУБД → запустить 1С. Пакеты сборки 1С (или Postgres Pro) удерживают от случайной замены «ванильными» (`apt-mark hold`, см. статью о пакетах) [практика].
- Перезагружать ОС «для профилактики» не требуется; основания — обновление ядра и системных библиотек, изменение параметров, требующих перезагрузки.

### 6.9. Действия при заполнении диска

**Симптомы:** сеансы завершаются с ошибками записи, `rmngr` падает в цикле и плодит дампы (кончилось место под сеансовые данные [офиц.]), PostgreSQL останавливается с `PANIC: could not write to file "pg_wal/…": No space left on device`, запросы падают на записи временных файлов.

```bash
# 1. Что заполнено: место или inode
df -h; df -i
# 2. Кто занял (не выходя за пределы файловой системы)
sudo du -xh --max-depth=2 / 2>/dev/null | sort -h | tail -25
sudo du -sh $D/reg_*/* /var/log/1c/* /var/lib/postgresql/*/main/pg_wal /var/log/* /var/tmp /tmp /var/crash /var/lib/systemd/coredump 2>/dev/null | sort -h | tail -20
# 3. Удалённые, но ещё открытые файлы (место не освобождается, пока жив процесс)
sudo lsof -nP +L1 2>/dev/null | head
```

Что можно освобождать и в каком порядке:

| Что | Как | Риск |
|---|---|---|
| Кэш пакетов, старые ядра | `sudo apt-get clean; sudo apt-get autoremove --purge` | нет |
| Журнал systemd | `sudo journalctl --vacuum-size=500M` | теряется история |
| Аварийные дампы | `sudo rm /var/crash/*` ; `sudo coredumpctl list` и очистка `/var/lib/systemd/coredump` | теряется материал для разбора — скопировать нужное |
| Техжурнал 1С | уменьшить `history` в `logcfg.xml` или убрать лишние `<log>`; старые каталоги удалить | теряются данные расследования |
| Временный каталог сервера 1С | старые файлы: `find $TMPDIR -type f -mtime +1 -delete` | при работающем сервере — только старые |
| Сеансовые данные | остановить сервер 1С, удалить `snccntx*` (раздел 3.5) | пользователи потеряют несохранённое |
| Старые резервные копии, `.dt`, дистрибутивы | перенести на другой носитель | — |
| Журнал регистрации | «Сократить» средствами платформы после восстановления работы | теряется история |
| Полнотекстовый индекс | удалить `1Cv8FTxt*` при остановленном сервере; индекс построится заново | поиск недоступен до перестроения |

Чего делать нельзя:

- **удалять файлы из `pg_wal`** (и вообще что-либо внутри каталога данных PostgreSQL) вручную — это разрушит базу. Причины роста WAL устраняют штатно: неработающая `archive_command` (смотреть `pg_stat_archiver`), неактивный слот репликации (`pg_replication_slots`, удалить `pg_drop_replication_slot('имя')`), слишком большой `max_wal_size`/`wal_keep_size`, зависшая длинная транзакция;
- удалять `1CV8Clst.lst` и каталоги баз в `reg_<порт>` целиком.

Расширение тома (Ubuntu Server по умолчанию ставится на LVM и часто оставляет свободное место в группе томов):

```bash
sudo vgs; sudo lvs                                             # есть ли VFree
sudo lvextend -r -l +100%FREE /dev/ubuntu-vg/ubuntu-lv         # расширить LV вместе с файловой системой
# если увеличен виртуальный диск ВМ: сначала раздел и PV
sudo growpart /dev/sda 3 && sudo pvresize /dev/sda3            # пакет cloud-guest-utils; номер раздела — по lsblk
```

После восстановления места: запустить PostgreSQL (он сам выполнит восстановление после сбоя), затем сервер 1С; проверить журналы; завести мониторинг с порогом 10–15 % свободного места и развести по разным томам данные СУБД, WAL, каталог кластера, техжурнал и резервные копии.

### 6.10. Контроль лицензий

```bash
ls -l /var/1C/licenses/                                            # файлы программных лицензий сервера (*.lic)
$RAC process list --cluster=$CL --licenses                         # серверные лицензии рабочих процессов
$RAC session list --cluster=$CL --licenses | grep -E '^(user-name|app-id|license-type|issued-by-server|max-users-cur|short-presentation)'
$RAC session list --cluster=$CL | grep -c '^session '              # всего сеансов
$RAC session list --cluster=$CL | awk -F' *: *' '/^infobase/{a[$2]++} END{for(k in a) print a[k], k}' | sort -rn   # сеансов по базам (UUID)
```

Что контролировать:

- запас клиентских лицензий: число занятых против номинала (поля `max-users-all`/`max-users-cur` в выводе с `--licenses`); спящие сеансы лицензию освобождают, при пробуждении пытаются получить её снова [офиц.];
- лимиты ПРОФ: 500 одновременных сеансов на одну базу (501-й пользователь не войдёт) и 12 ядер на сервер [офиц.];
- свойство базы «Разрешить выдачу лицензий сервером 1С:Предприятия» (`--license-distribution=allow|deny`): при «нет» клиент, не нашедший лицензию сам, получит «Не найдена лицензия. Не обнаружен ключ защиты программы или полученная программная лицензия» [офиц.];
- сохранность файлов `*.lic` и неизменность оборудования/параметров ВМ, к которым привязана программная лицензия; файлы включают в резервную копию настроек сервера вместе с пин-кодами и регистрационными данными;
- 8.5.4+: процесс `rmlic` запущен, порты 475/1544 доступны; диагностика — «Журнал поиска лицензии» в сообщении «Не найдена лицензия…» и стандартная обработка «Управление лицензиями» [офиц., ИТС 6041];
- фоновые задания и сеансы консоли кластера клиентских лицензий не расходуют [практика].

## 7. Миграция с Windows на Linux и с MS SQL Server на PostgreSQL

### 7.1. Что меняется при переезде

| Было (Windows + MS SQL) | Станет (Linux + PostgreSQL) | Комментарий |
|---|---|---|
| Сервер 1С работает с MS SQL Server | Рабочие процессы на Linux **не могут** работать с MS SQL Server | Ограничение платформы [офиц.]; базу обязательно переносить в PostgreSQL (или другую поддерживаемую на Linux СУБД) |
| COM-объекты на сервере (`Новый COMОбъект`, Excel/Word/ADODB, `V83.COMConnector`) | Недоступны: модуль компилируется, но при выполнении — ошибка | [офиц.]; код переписывают на встроенные средства, HTTP/веб-сервисы, внешние компоненты Native API |
| Аутентификация ОС по NTLM/Kerberos | Только Kerberos (или логин/пароль) | [офиц.]; нужна настройка keytab |
| Внешние компоненты `.dll` | Нужны сборки для Linux (`.so`) под архитектуру сервера | проверить поставку каждой компоненты |
| Пути `C:\…`, `\\server\share`, разделитель `\` | `/…`, монтирование SMB/NFS, разделитель `/`, имена файлов чувствительны к регистру | в коде — `ПолучитьРазделительПути()`, каталоги — из настроек |
| Службы Windows, планировщик, SQL Agent, `bat`-файлы | systemd, cron/timers, bash | резервные копии и обслуживание СУБД создаются заново |
| Каталог кластера `C:\Program Files\1cv8\srvinfo` | `/home/usr1cv8/.1cv8/1C/1cv8` | реестр кластера создаётся заново |
| Типы строк MS SQL, сравнение без учёта регистра | Типы `mchar`/`mvarchar`, оператор `fulleq`, модуль `fasttrun` — из патча 1С / Postgres Pro «для совместимости с MS SQL Server» | [офиц., Postgres Pro]; поэтому нужна сборка PostgreSQL для 1С, «ванильная» не подходит |
| Смещение дат 2000 (особенность MS SQL) | Не используется | параметр `date-offset` относится только к MS SQL [офиц.] |
| Автообновление статистики, параллелизм запросов, tempdb | autovacuum/autoanalyze, временные таблицы как файлы, параллельные запросы для 1С обычно отключают | раздел 7.9 |

### 7.2. План миграции

Фирма «1С» публикует «Дорожную карту по переводу информационных систем на Linux + PostgreSQL»: процесс основан на **сравнительном нагрузочном тестировании** (рекомендуемый инструмент — Тест-центр из КИП), при выборе ОС и СУБД нужно ориентироваться на список поддерживаемых версий [офиц., v8.1c.ru]. Практический план [практика]:

1. **Инвентаризация**: версии платформы и режимы совместимости конфигураций, размеры баз, число пользователей, интеграции (обмены, веб-сервисы, почта, FTP, файловые каталоги), внешние компоненты, прямые обращения к MS SQL из других систем и отчётов, задания SQL Agent, способы аутентификации, лицензии (тип, ПРОФ/КОРП, ключи или пин-коды).
2. **Стенд**: Linux + PostgreSQL (сборка для 1С) + та же сборка платформы; настройки по статьям базы знаний.
3. **Проверка конфигурации на совместимость** (раздел 7.3) и исправление кода.
4. **Пробный перенос** копии базы (разделы 7.4–7.6) с замером времени — это и есть будущий простой.
5. **Функциональная проверка и сравнение производительности**: APDEX ключевых операций «до» и «после», тест Гилёва для оценки среды, длительные регламентные операции (закрытие месяца, обмены, отчёты).
6. **Оптимизация** найденных медленных запросов и настроек PostgreSQL.
7. **Перенос окружения**: настройки кластера, публикации, лицензии, расписания, резервное копирование и мониторинг (раздел 7.7).
8. **Репетиция переключения** по чек-листу, план отката.
9. **Переключение**: запрет сеансов в старой базе → финальный перенос → проверка (раздел 7.8) → переключение клиентов (строки соединения, DNS-псевдоним, публикации) → старая система остаётся доступной только на чтение на время гарантийного периода.
10. **Усиленное наблюдение** первые недели: техжурнал, статистика запросов, APDEX.

### 7.3. Проверка конфигурации на совместимость

Специальной кнопки «проверить для Linux/PostgreSQL» в платформе нет; проверка складывается из поиска по коду и тестов [практика]. Выгрузите конфигурацию в файлы (`/DumpConfigToFiles` конфигуратора или `ibcmd infobase config export`) и найдите заведомо проблемные места:

```bash
cd /work/cfg-xml
# COM и запуск внешних программ
grep -rnE 'COMОбъект|COMObject|ПолучитьCOMОбъект|GetCOMObject|ЗапуститьПриложение|RunApp|КомандаСистемы' --include='*.bsl' . | head -50
grep -rnE 'ADODB|WScript|Scripting\.FileSystemObject|Excel\.Application|Word\.Application|V83\.COMConnector' --include='*.bsl' .
# жёстко заданные пути Windows: "C:\… и "\\server\…
grep -rnE '"[A-Za-z]:\\|"\\\\' --include='*.bsl' .
# конструкции запросов, проблемные на PostgreSQL
grep -rniE 'ПОЛНОЕ +(ВНЕШНЕЕ +)?СОЕДИНЕНИЕ|FULL +(OUTER +)?JOIN' --include='*.bsl' .
```

Что проверить помимо кода:

- **режим управления блокировками данных** в свойствах конфигурации — должен быть «Управляемый» (раздел 7.9);
- **режим совместимости** — на старых режимах недоступны оптимизации новых версий платформы; менять его нужно отдельно от миграции;
- **внешние обработки и отчёты**, расширения, внешние компоненты — тот же поиск по ним;
- **печать и экспорт**: шрифты (на сервере Linux должны быть установлены шрифты, см. статью об установке), формирование PDF/XLSX без COM;
- **обмены**: каталоги обмена (права пользователя `usr1cv8`, монтирование общих ресурсов), почта, сертификаты, криптопровайдеры;
- **внешние источники данных** и ODBC-драйверы для Linux;
- статический анализ: «1С:Автоматизированная проверка конфигураций», диагностики BSL Language Server/SonarQube ⚠ (состав правил, относящихся к Linux, в сессии не проверялся).

### 7.4. Перенос через выгрузку в `.dt`

Самый простой способ; подходит для небольших и средних баз. Официальные ограничения [офиц., руководство администратора 8.3.27]:

- выгрузка требует монопольного режима, занимает много времени и **предъявляет высокие требования к оперативной памяти**;
- файл может не загрузиться, если в исходной базе есть ошибки, — перед выгрузкой рекомендуется выполнить «Тестирование и исправление» и устранить найденное;
- при загрузке нужно свободное место под временные файлы примерно в размер **развёрнутой** базы: для клиент-серверного варианта — на компьютере сервера 1С (каталог временных файлов, раздел 3.2); итоговая база может быть в несколько раз больше файла `.dt`;
- журнал регистрации в `.dt` не входит; данные встроенного хранилища двоичных данных (КОРП) при переносе базы на другой компьютер нужно переносить отдельно, иначе они будут потеряны (входит ли их содержимое в `.dt`, в сессии не уточнялось ⚠; с 8.5.4 при загрузке `.dt` данные можно сразу размещать в хранилище);
- загрузка **безвозвратно уничтожает** содержимое базы-приёмника;
- файлы `.dt`, созданные 8.3, в версии младше 8.3.1 не загружаются.

Ускорение загрузки [офиц., V8Update]: с 8.3.19 загрузка в клиент-серверную базу идёт несколькими фоновыми заданиями (параметр `-JobsCount` команды `/RestoreIB`), с 8.3.18 ускорена загрузка через `ibcmd`. Существенный выигрыш — когда кластер и СУБД на одном компьютере или связаны быстрым каналом.

```bat
:: Windows, старый сервер: выгрузка (пользователи отключены, сеансы запрещены)
"C:\Program Files\1cv8\8.3.27.2074\bin\1cv8.exe" DESIGNER /S"oldsrv\erp" /N"Администратор" /P"***" ^
    /DumpIB D:\dump\erp.dt /DisableStartupDialogs /Out D:\dump\dump.log
```

```bash
# Linux, новый сервер. Вариант А — ibcmd: создать базу данных в PostgreSQL и сразу загрузить .dt
IBCMD=/opt/1cv8/x86_64/$V/ibcmd
sudo -u usr1cv8 $IBCMD infobase create --dbms=PostgreSQL --database-server=127.0.0.1 \
     --database-name=erp --database-user=postgres --database-password='***' --create-database \
     --data=/var/lib/1c/ibcmd-erp --restore=/data/dump/erp.dt
# …и зарегистрировать уже существующую базу данных в кластере (без --create-database)
$RAC infobase create --cluster=$CL --name=erp --dbms=PostgreSQL --db-server=127.0.0.1 --db-name=erp \
     --locale=ru_RU --db-user=postgres --db-pwd='***' --license-distribution=allow --scheduled-jobs-deny=on

# Вариант Б — конфигуратор: базу создать в кластере (консоль / rac … --create-database), затем загрузить
xvfb-run -a /opt/1cv8/x86_64/$V/1cv8 DESIGNER /S"srv1c\erp" /N"Администратор" /P"***" \
     /RestoreIB /data/dump/erp.dt -JobsCount 8 /DisableStartupDialogs /Out /tmp/restore.log
```

- При регистрации база с уже существующими данными 1С подключается как есть: «если существующая база данных уже содержит данные информационной базы, будет установлено соединение с существующей информационной базой» [офиц.].
- Базу данных под 1С должна создавать сама платформа (кластер, конфигуратор или `ibcmd`), а не `CREATE DATABASE` вручную [офиц., замечание в ИТС 6011]; кластер PostgreSQL должен быть инициализирован с активной русской локалью `ru_RU.UTF-8` [офиц., Postgres Pro].
- Регламентные задания новой базы до окончания проверки держат заблокированными (`--scheduled-jobs-deny=on`).
- Ориентиры по размеру ⚠ [практика]: базы до десятков гигабайт переносятся через `.dt` за часы; для баз в сотни гигабайт время и требования к памяти/временному месту обычно неприемлемы — используйте `ibcmd infobase replicate`.
- На время загрузки в PostgreSQL полезно увеличить `max_wal_size` и `maintenance_work_mem`; после загрузки — `sudo -u postgres vacuumdb -d erp --analyze --jobs=4` [практика].

### 7.5. Большие базы: `ibcmd infobase replicate`

С 8.3.23 утилита `ibcmd` умеет конвертировать клиент-серверную базу из одной СУБД в другую **без промежуточного `.dt`**; конвертация из файловой базы не поддерживается [офиц., V8Update и руководство администратора]. Пример из документации:

```bat
:: пример из документации (Windows; одна команда, перенесена символом ^)
ibcmd infobase replicate --data=d:\ss-data\cs-data ^
   --dbms=MSSQLServer --database-server=localhost --database-name=dbMsSql --database-user=msUser --database-password=123 ^
   --target-dbms=PostgreSQL --target-database-server=localhost --target-database-name=dbPgSql ^
   --target-database-user=pgUser --target-database-password=123 --target-create-database
```

Здесь `--data` — каталог данных автономного сервера (служебный рабочий каталог утилиты), первая группа параметров описывает источник (MS SQL Server), группа `--target-…` — приёмник (PostgreSQL); в примере обе СУБД на локальном компьютере.

| Параметр | Значение по умолчанию | Смысл [офиц.] |
|---|---|---|
| `--target-dbms=<вид>` | файловая база | `MSSQLServer`, `PostgreSQL`, `IBMDB2`, `OracleDatabase` |
| `--target-database-server`, `--target-database-name`, `--target-database-user`, `--target-database-password` (короткие формы `--target-db-…`) | — | адрес, имя базы и учётная запись СУБД-приёмника |
| `--target-request-database-password` | — | запросить пароль приёмника через stdin |
| `--target-create-database` | — | создать базу-приёмник, если её нет |
| `--jobs-count=<n>`, `-j` | число логических ядер | потоков и соединений с СУБД при чтении источника |
| `--target-jobs-count=<n>`, `-J` | число логических ядер | потоков и соединений с СУБД-приёмником |
| `--batch-size=<n>`, `-B` | 10 000 | строк таблицы в одной порции |
| `--batch-data-size=<n>` | 10 485 760 | размер порции данных, байт |
| `--force` | — | принудительно завершить сеансы исходной базы перед репликацией |
| `--target-date-offset=<лет>` | 2000 | только для приёмника MS SQL Server |
| `--target-database-schema` (8.5.4+) | — | схема базы-приёмника |

Практические замечания:

- ⚠ Где запускать. Утилите нужен доступ к обеим СУБД. Рабочие процессы на Linux с MS SQL Server не работают [офиц.]; распространяется ли ограничение на `ibcmd` для Linux, в сессии подтвердить не удалось. Надёжный вариант — запускать `ibcmd.exe` **на Windows-машине** с установленной платформой той же версии (обычно на старом сервере 1С), указывая PostgreSQL на Linux как приёмник; в `pg_hba.conf` должен быть разрешён вход с этого адреса.
- Исходная база на время репликации должна быть свободна от пользователей; сама она не изменяется, поэтому откат прост.
- Число потоков подбирают по ядрам и дискам обеих сторон; узким местом обычно становится запись в PostgreSQL (WAL, контрольные точки) — на время переноса увеличивают `max_wal_size`, после — `VACUUM ANALYZE`.
- После репликации базу регистрируют в кластере Linux командой `rac infobase create` без `--create-database` (как в 7.4) и проверяют.
- Журнал регистрации и встроенное хранилище двоичных данных переносятся отдельно (раздел 7.7).

### 7.6. Другие способы

- **Обмен данными / РИБ** [практика]: в PostgreSQL разворачивается новая база (узел распределённой базы или база с синхронизацией), данные доезжают обменом, переключение пользователей занимает минуты. Подходит, когда конфигурация поддерживает обмен в нужном объёме; не переносит то, что не входит в состав плана обмена (историю, настройки пользователей, журнал регистрации). Требует самой тщательной сверки данных.
- **Свёртка и перенос остатков** — если переезд совмещают с началом учёта «с чистого листа».
- **Сторонние SQL-конвертеры** (перенос таблиц MS SQL → PostgreSQL в обход платформы) ⚠: структура хранения 1С использует собственные типы и служебные таблицы, соответствие которых обеспечивает только платформа; такие инструменты не поддерживаются фирмой «1С», а результат невозможно гарантировать. Использовать только при невозможности штатных способов и с полной сверкой.

### 7.8. Проверка результата

- **Целостность**: «Тестирование и исправление» в режиме проверки логической и ссылочной целостности на новой базе; отсутствие ошибок в журнале загрузки.
- **Сверка данных** «до/после» на одинаковый момент: оборотно-сальдовая ведомость и остатки по ключевым регистрам, количество документов по видам и периодам, контрольные отчёты, которые формирует бизнес.
- **Функции**: вход под ролями разных групп пользователей, проведение и перепроведение документов, закрытие месяца на копии, печатные формы (шрифты, PDF, Excel), обмены и интеграции, почта, электронная подпись, фоновые и регламентные задания (после снятия блокировки).
- **Сортировка и поиск**: порядок строк в списках, поиск по подстроке, отборы без учёта регистра — на реальных справочниках.
- **Производительность**: APDEX ключевых операций против значений старой системы, длительность ночных регламентов, тест Гилёва как оценка среды.
- **Эксплуатация**: резервная копия снимается и восстанавливается, мониторинг и оповещения работают, лимиты памяти кластера заданы, техжурнал пишется и чистится.

### 7.9. Типовые проблемы производительности после переезда на PostgreSQL

| Проблема | Причина | Что делать |
|---|---|---|
| Пользователи ждут друг друга, ошибки «Конфликт блокировок…» при одновременном проведении | Конфигурация в **автоматическом режиме** управления блокировками: изоляцию обеспечивает СУБД, и для PostgreSQL платформа блокирует таблицы целиком — подтверждено «Руководством разработчика» 8.3.27 (глава 9, таблица режимов блокировок, и приложение 8, разд. 8.6: «В автоматическом режиме PostgreSQL использует табличные блокировки… транзакция, захватившая одну запись в таблице, блокирует эту таблицу целиком»; уровень изоляции — Serializable; там же автоматический режим назван нерекомендуемым для реальной эксплуатации); сверено 11.10.2026; ранее было отмечено: (по документации платформы; в сессии не перечитано). Платформа задаёт `lock_timeout = 20000` — после 20 с ожидания вызов падает [офиц.] | Перевести конфигурацию в управляемый режим (типовые давно в нём). По позиции 1С, в управляемом режиме ожиданий на блокировках PostgreSQL «возникать не должно», они должны возникать только на управляемых блокировках [офиц., ИТС 6006] |
| Запрос, быстрый на MS SQL, выполняется минутами | Другой оптимизатор; платформа выключает `enable_mergejoin` и меняет `cpu_operator_cost` для своих сеансов [офиц.]; неудачные оценки числа строк | Найти запрос (раздел 8.5), получить план с теми же параметрами сеанса, переписать: соединения с подзапросами и виртуальными таблицами вынести во временные таблицы, убрать `ИЛИ` в условиях соединений и отборах, сократить большие списки в `В (…)` |
| Запросы с `ПОЛНОЕ ВНЕШНЕЕ СОЕДИНЕНИЕ` медленные | PostgreSQL поддерживает FULL JOIN ограниченно; платформа трансформирует запрос в эквивалентную, но менее эффективную форму | «Не рекомендуется использовать ПОЛНОЕ ВНЕШНЕЕ СОЕДИНЕНИЕ при работе с PostgreSQL» — переписать запрос [офиц., ИТС 1556] |
| Медленное соединение с виртуальной таблицей `СрезПоследних` | Неоптимальный план | Вынести обращение к виртуальной таблице в отдельный запрос с результатом во временной таблице [офиц., ИТС 4208] |
| Всё, что активно использует временные таблицы, работает хуже; растут системные каталоги | Каждая временная таблица — файлы на диске и записи в `pg_class`/`pg_attribute` | Не отключать autovacuum; `temp_tablespaces` на быстром диске; в сборках 1С — `enable_temp_memory_catalog` (с 16.4) и `enable_temp_rd_buffers` (с 17.5-11.1C и 16.9-34.1C), оба дают выигрыш ценой CPU/памяти и включаются осознанно [офиц., ИТС 5866 и 6035] |
| Планы «плывут», после массовых загрузок запросы медленные | Статистика обновляется фоном (autoanalyze), а не синхронно | Проверить настройки автоочистки (`autovacuum_naptime = 20s`, `autovacuum_max_workers` ≥ 4 [офиц.]); после массовых операций — `ANALYZE`. Модуль `online_analyze` для современных версий 1С не рекомендуют ни 1С («в общем случае»), ни Postgres Pro — включать только при доказанной пользе [офиц.] |
| Отдельные аналитические запросы стали медленнее | Для 1С рекомендуют `max_parallel_workers_per_gather = 0` и `jit = off` — в MS SQL такие запросы распараллеливались | Оптимизировать сам запрос; менять общие настройки ради одного отчёта не стоит [офиц. значения — Postgres Pro и ИТС 5866] |
| База и время отклика растут со временем | Длинные транзакции и «зависшие» сеансы мешают очистке; раздувание таблиц и индексов | Искать транзакции старше нескольких минут (раздел 6.1), контролировать `n_dead_tup`, при необходимости `VACUUM`/`REINDEX` в окно обслуживания |
| Запросы к остаткам замедляются | Нулевые записи в таблицах итогов | Регулярный пересчёт итогов [офиц., ИТС 5371] |
| Иной порядок строк в списках, «не находит» при поиске | Сравнение и сортировка строк определяются локалью кластера PostgreSQL и типами `mchar`/`mvarchar`, а не параметрами сортировки MS SQL ⚠ (детали в сессии не проверялись) | Кластер PostgreSQL должен быть инициализирован с активной локалью `ru_RU.UTF-8`; списки и отборы проверить на тесте заранее: локаль уже созданной базы изменить нельзя — только новая база (кластер) и повторный перенос |
| «Всё медленнее на 10–30 %» при тех же ресурсах | Не настроен PostgreSQL (значения по умолчанию), нет памяти под кэш, включено энергосбережение, медленный диск под WAL | Настройки по ИТС 5866 / Postgres Pro, проверки из разделов 1 и 8 |

## 8. Методика анализа производительности

### 8.1. APDEX и подсистема «Оценка производительности» БСП

Методика APDEX рекомендована фирмой «1С» как объективная, прикладная, интегральная и количественная оценка [офиц., ИТС 5807]. Этапы:

1. Составить список **ключевых операций** вместе с заказчиком: критичные для бизнеса; выполняемые одновременно более чем 10 пользователями; те, на которые жалуются.
2. Каждой назначить **приоритет** (1 — высший).
3. Каждой назначить **целевое время T** — не вычисляется, а назначается: «если операция всегда будет выполняться за время ≤ T, это полностью устроит заказчика».
4. Собрать **все** замеры времени выполнения за период не менее полного рабочего дня.
5. Посчитать `APDEX = (NS + NT/2) / N`: N — всего выполнений, NS — с временем от 0 до T, NT — от T до 4T.

| APDEX | Оценка |
|---|---|
| 0,94 – 1,00 | отлично |
| 0,85 – 0,94 | хорошо |
| 0,70 – 0,85 | плохо |
| 0,50 – 0,70 | очень плохо |
| 0,00 – 0,50 | неприемлемо |

Система работает с достаточной производительностью, если показатели всех ключевых операций — в зоне «хорошо» и выше; иначе оптимизируют операции в порядке приоритетов [офиц.].

Инструмент сбора — подсистема БСП **«Оценка производительности»** [офиц., документация БСП 3.1.11]:

- ключевые операции задаются именами в справочнике «Ключевые операции»; замеры пишутся в регистр сведений «Замеры времени»; анализ — отчёт/обработка «Оценка производительности»; целевое время можно подобрать автоматически по известному APDEX;
- в код конфигурации в местах выполнения ключевых операций вставляются вызовы общих модулей `ОценкаПроизводительностиКлиент`/`ОценкаПроизводительности` (в английской редакции — `PerformanceMonitorClient.TimeMeasurement()`, `PerformanceMonitor.StartTimeMeasurement()`/`EndTimeMeasurement()`); типовые конфигурации уже содержат замеры основных операций;
- включение — константа «Выполнять замеры производительности» (флажок «Оценка производительности» в настройках администрирования); объекты подсистемы не включают в планы обмена;
- результаты можно выгружать в «Центр контроля качества» (КИП).

Как анализировать замеры [офиц., ИТС 5808]: нужна значимая выборка (больше 100 замеров); строят распределение времени выполнения; пик около нуля означает неверно встроенный замер (операции, оборвавшиеся ошибкой), несколько пиков — под одним именем скрываются разные операции. Медленное выполнение воспроизводят в тех же условиях, что у пользователей: на копии рабочей базы с данными, на той же платформе и той же СУБД, под пользователем с ограниченными правами, с теми же данными; **не** в файловой базе, **не** под полными правами, **не** на пустой базе.

### 8.2. Тест Гилёва (TPC-1C)

Что это [по описанию автора, gilev.ru]: бесплатный синтетический **однопоточный** тест — выполняется фиксированное число операций (акцент на проведении документов) и измеряется время; результат — индекс в условных баллах. Измеряет «потоковую скорость» среды (сколько эталонных операций в единицу времени выполняет один сеанс), а не суммарную пропускную способность и не качество конфигурации: «быстрая среда не значит быстрая работа конфигурации… а вот медленная среда — это уже вряд ли быстрый код». Работает со всеми СУБД, поддерживаемыми 1С, рассчитан на клиент-серверный вариант; актуальная версия запускается на платформе от 8.3.15, работает на 8.5, опрашивает оборудование в Linux и PostgreSQL и параметры кластера через RAS (для подключения к PostgreSQL использует `psql` и файл `.pgpass` в профиле пользователя сервера 1С).

Что влияет на результат (перечень автора): частота процессора и настройки BIOS (Turbo Boost, энергосбережение); частота и расположение модулей памяти по каналам; гипервизор и его настройки; в Linux — режим энергосбережения и заплатки от уязвимостей процессоров; версия платформы и СУБД; включённый техжурнал и режим отладки на сервере; скорость дисков под базу, каталог кластера и временные файлы; канал между 1С и СУБД; зеркалирование/репликация; расположение лицензий (удалённый ключ, отдельный сервер лицензирования), несколько рабочих серверов в кластере; антивирус.

Как интерпретировать на Linux/PostgreSQL:

- сравнивать можно только **одинаково выполненные** замеры: в ненагруженный период, без пользователей и фоновых заданий, без `logcfg.xml` и отладки, в клиент-серверном варианте; сначала тест на «железе», затем в ВМ — разница и есть «штраф» виртуализации;
- если сервер 1С и СУБД на разных машинах, автор советует сначала проверить каждую по отдельности (с локальной СУБД);
- низкий индекс — повод искать проблемы среды (частота CPU, электропитание, диск под WAL, сеть до СУБД, `synchronous_commit`), высокий — не гарантия, что рабочая конфигурация будет быстрой и что сервер выдержит нужное число пользователей;
- шкала оценок в актуальной версии, по словам автора, ужесточена относительно старой; старые ориентиры из статей сообщества (например, «от 15 — хорошо, от 35 — отлично») относятся к прежним версиям теста ⚠ и для сравнения с новыми результатами не годятся; 100 баллов автор называет достижимыми лишь в частных случаях;
- для многопользовательской оценки нужен нагрузочный тест (Тест-центр), а для оценки реальной работы — APDEX.

### 8.4. Загрузка оборудования: что и с какими порогами смотреть

Официальные критерии для Linux [офиц., ИТС 5824] по данным `vmstat -n 15 480` (первую строку отбросить — это среднее с загрузки):

| Показатель | Колонка | Критерий | Узкое место |
|---|---|---|---|
| Подкачка с диска | `si` | среднее ≈ 0, максимум ≤ 20 | не хватает оперативной памяти |
| Загрузка процессоров | `us`, `sy` | максимум `us` ≤ 70, `sy` ≤ 35 | не хватает процессора |
| Очередь к процессорам | `r` | длительно ≤ 2 × число ядер | не хватает процессора |
| Очередь к дискам | `b` | ≤ 2 × число параллельно работающих дисков | не хватает дисковой подсистемы |
| Сеть | макс. байт/с | ≤ 65 % пропускной способности адаптера | не хватает сети |

Инструменты, которые использует сама методика 1С для PostgreSQL [офиц., ИТС 6011]:

```bash
sudo apt install atop nmon sysstat
sudo atop                                  # интерактивно
sudo atop -w atop.log 3 1200               # 1200 снимков через 3 с (1 час) в файл
atop -r /var/log/atop/atop_20261010        # просмотр записанного службой atop (интервал — INTERVAL в /etc/default/atop)
sudo atop -P CPU,DSK,MEM,NET 1 > atop.csv  # вывод для автоматической обработки
nmon -f -s 2 -c 600                        # 600 снимков через 2 с в файл
iostat -dxm 5; pidstat -u -r -d 5 3        # диски; CPU/память/ввод-вывод по процессам
```

### 8.5. Техжурнал 1С + статистика СУБД

**Шаг 1. Доля СУБД во времени вызовов** [офиц., ИТС 6011]. Временно включить сбор всех событий без свойств (здесь и ниже показан только элемент `<log>` — он вставляется внутрь `<config xmlns="http://v8.1c.ru/v8/tech-log">` файла `logcfg.xml`, раздел 3.8):

```xml
<log location="/var/log/1c/all_mini" history="8">
  <event><ne property="Name" value=""/></event>
</log>
```

```bash
cd /var/log/1c/all_mini
cat rphost_*/*.log | awk -F\- '{print $2}' | awk -F\, '{sum[$2]+=$1;} END {for (event in sum) print event" - "sum[event];}'
# DBPOSTGRS - 22189998668
# CALL      - 33908470608      → DBPOSTGRS / CALL ≈ 0,65
```

Если доля `DBPOSTGRS` в `CALL` превышает примерно 50 % — разбираться со скоростью запросов; если мала — время уходит в код на сервере 1С, блокировки (`TLOCK`) или клиент-серверный обмен.

**Шаг 2. Найти запросы.** Техжурнал с событием `DBPOSTGRS` и всеми свойствами (объём большой, включать на время):

```xml
<log location="/var/log/1c/dbpostgrs" history="4">
  <event><eq property="Name" value="DBPOSTGRS"/></event>
  <property name="all"/>
</log>
```

Статистика на стороне PostgreSQL [офиц., ИТС 6011]:

```sql
-- postgresql.conf: shared_preload_libraries = 'pg_stat_statements,auto_explain' (нужен перезапуск СУБД)
ALTER SYSTEM SET pg_stat_statements.max = 10000;
ALTER SYSTEM SET pg_stat_statements.track = 'all';
ALTER SYSTEM SET auto_explain.log_min_duration = '10s';    -- планы запросов дольше 10 с — в журнал PostgreSQL
ALTER SYSTEM SET auto_explain.log_analyze = true;          -- снижает производительность: только с порогом длительности
ALTER SYSTEM SET track_activity_query_size = 1048576;      -- хранить тексты запросов до 1 МБ (нужен перезапуск)
SELECT pg_reload_conf();
-- в базе 1С:
CREATE EXTENSION IF NOT EXISTS pg_stat_statements;
SELECT pg_stat_statements_reset();

-- самые «дорогие» запросы
SELECT d.datname, s.calls, round(s.total_exec_time) AS total_ms, round(s.mean_exec_time) AS mean_ms,
       s.temp_blks_read + s.temp_blks_written AS temp_blks, left(s.query, 120) AS query
FROM pg_stat_statements s JOIN pg_database d ON d.oid = s.dbid
ORDER BY s.total_exec_time DESC LIMIT 20;

-- что выполняется прямо сейчас
SELECT datname, application_name, pid, now() - query_start AS duration, left(query, 120) AS query
FROM pg_stat_activity WHERE state = 'active' ORDER BY duration DESC LIMIT 10;

-- на чём ждут активные сеансы (запускать циклом раз в 3 с и копить)
SELECT wait_event_type, wait_event, count(*) FROM pg_stat_activity WHERE state = 'active' GROUP BY 1, 2 ORDER BY 3 DESC;
```

Связать процесс PostgreSQL с сеансом 1С: PID нагруженного процесса `postgres` (из `top`/`atop`) ищется в техжурнале по свойству `dbpid=`; в той же строке — `SessionID`, `Usr`, текст `Sql` и `Context` (строка кода 1С) [офиц.].

**Шаг 3. Получить план «как у платформы».** Запрос из техжурнала выполняют в `psql` с теми же параметрами сеанса, что выставляет платформа (список — в разделе 1.7), добавив `EXPLAIN ANALYZE VERBOSE`; если запрос использует временные таблицы — сначала воссоздают и заполняют их запросами выше по журналу и выполняют `ANALYZE` для каждой [офиц.].

```bash
psql -U postgres --dbname=erp --file=query.sql > query.sqlplan
```

**Блокировки** [офиц., ИТС 6006]: для журнала ожиданий — `log_lock_waits = on` (плюс `log_min_duration_statement`, `log_checkpoints`, `log_temp_files = 0`, `log_autovacuum_min_duration = 0`, `log_line_prefix = '%t [%p]: [%l-1] user=%u,db=%d,app=%a,client=%h '` на время расследования); текущие блокировки — представление `pg_locks`, кто кого ждёт — соединение `pg_locks` с `pg_stat_activity` по `NOT granted`; отчёт по журналу PostgreSQL удобно строить утилитой pgBadger. В техжурнале 1С управляемые блокировки — события `TLOCK`, `TTIMEOUT`, `TDEADLOCK`.

### 8.6. «1С тормозит»: типовые причины и порядок локализации

Порядок [практика, составлен по методикам ИТС 5808, 5814, 5815, 5983, 6011]:

1. **Уточнить симптом**: у всех или у одного пользователя; все операции или одна; постоянно или в определённые часы; после какого изменения началось (журнал работ!). «Одна операция у всех» — почти всегда код или запрос; «всё у всех» — ресурсы или блокировки; «всё у одного» — рабочее место, сеть, права (RLS).
2. **Ресурсы серверов** (раздел 8.4): CPU, память и своп, диски, сеть — на сервере 1С и на сервере СУБД отдельно.
3. **Кластер 1С**: `rac process list` (память, `avg-call-time` и его составляющие `avg-db-call-time`, `avg-lock-call-time`, `avg-server-call-time`), `rac session list` (сеансы с большим `duration-current`: если велик и `duration-current-dbms` — ждём СУБД; `blocked-by-ls` ≠ 0 — управляемая блокировка, `blocked-by-dbms` ≠ 0 — блокировка СУБД). По методике 1С: записать номера и базы «тяжёлых» сеансов, завершить их, убедиться, что нагрузка упала, затем по журналу регистрации выяснить сценарий.
4. **СУБД**: активные запросы и ожидания, длинные транзакции, автоочистка, контрольные точки, временные файлы (раздел 8.5).
5. **Техжурнал**: доля `DBPOSTGRS`, топ длительных `CALL` по контекстам, `EXCP`, таймауты и взаимоблокировки.
6. **Код**: воспроизвести на копии (правила — раздел 8.1), замер производительности в конфигураторе, план запроса; если замер отладчика заметно меньше замера БСП — время уходит вне прикладного кода (передача данных формы, клиент-серверные вызовы) [офиц., ИТС 5983].
7. **Клиент**: скорость и задержка сети до сервера (тонкий клиент чувствителен к задержкам), антивирус, работа через веб-сервер. Толстый клиент и конфигуратор, запускаемые ярлыком без регистрации базы в списке баз, не используют локальный кэш конфигурации и работают заметно медленнее [офиц., ИТС 5847].

| Типовая причина | Признак | Где смотреть |
|---|---|---|
| Нехватка памяти, своп, OOM | `si/so` > 0, `available` мал, сообщения ядра | `vmstat`, `free`, `journalctl -k` |
| Лимиты памяти кластера заданы неверно (или не заданы на совмещённом сервере) | частые перезапуски `rphost`, события `ATTN`, ошибки «недостаточно памяти» у пользователей | техжурнал, `rac server info` |
| Медленный диск под WAL / переполненный том | высокий `w_await`, ожидания `WALWrite`/`DataFileRead` | `iostat`, `pg_stat_activity` |
| PostgreSQL с настройками по умолчанию | `shared_buffers = 128MB`, много временных файлов, частые контрольные точки | `SHOW …`, `pg_stat_database` |
| Автоматический режим блокировок, избыточные блокировки | очереди на проведении, `TTIMEOUT`, ожидания `Lock` | техжурнал, `pg_locks` |
| Неоптимальные запросы после смены СУБД | один-два запроса в топе `pg_stat_statements` | раздел 7.9 |
| Длинные транзакции, раздувание таблиц | растёт `n_dead_tup`, старый `xact_start` | `pg_stat_activity`, `pg_stat_user_tables` |
| Тяжёлые фоновые задания в рабочее время | сеансы `BackgroundJob` с большим CPU/временем | `rac session list`, расписания |
| Рост сеансовых данных | `snccntx*` на гигабайты, растёт `rmngr` | раздел 3.3 |
| Включён «тяжёлый» техжурнал или отладка на сервере | `logcfg.xml` с `CALL`/`DBPOSTGRS`/`<plansql/>`, ключ `-debug` | `conf/logcfg.xml`, параметры службы |
| Энергосбережение, «плавающая» частота, переподписка CPU в ВМ | низкий индекс теста Гилёва при свободном CPU | BIOS, хост, гипервизор |
| Сеть между 1С и СУБД, DNS | большая доля времени СУБД при быстрых запросах в `pg_stat_statements` | `ping`, `mtr`, разрешение имён |
| Нулевые итоги, устаревшие агрегаты | медленные отчёты по остаткам | пересчёт итогов |
| Лицензии: удалённый ключ, недоступный менеджер лицензий | долгий вход в программу, паузы при старте сеансов | раздел 5.4 |

Применимость [практика]:

| Сценарий | Оценка |
|---|---|
| CI/CD: сборка конфигураций, автотесты, проверка кода | основное назначение существующих образов; оправдано |

Технические особенности контейнера с сервером 1С [практика]:

- **Имя хоста и порты**: менеджер кластера сообщает клиенту имя хоста и порт рабочего процесса, поэтому имя контейнера (`--hostname`) должно разрешаться на клиентах в адрес хоста, а порты 1540, 1541, 1545 и весь диапазон 1560–1591 — быть опубликованы один к одному (либо `--network host`).
- **Состояние — только в томах**: каталог данных кластера (`/home/usr1cv8/.1cv8`), `/var/1C/licenses`, каталог `conf` (`logcfg.xml`, `conf.cfg`), каталоги техжурнала и временных файлов. Без тома каждый пересозданный контейнер стартует с пустым кластером «по умолчанию».
- **Память**: лимиты «80 % / 95 % ОЗУ» платформа считает от памяти компьютера; учитывает ли она ограничение cgroup контейнера — не подтверждено ⚠. В контейнере с ограничением памяти лимиты кластера задают явно (раздел 2.3).
- **Версии**: `ras`/`rac` и клиенты — той же сборки, что сервер; образ привязан к конкретной версии платформы.

Пример запуска самостоятельно собранного образа (пути внутри образа зависят от Dockerfile ⚠):

```bash
docker run -d --name srv1c --hostname srv1c \
  -p 1540-1541:1540-1541 -p 1545:1545 -p 1560-1591:1560-1591 \
  -v srv1c-data:/home/usr1cv8/.1cv8 \
  -v /var/1C/licenses:/var/1C/licenses \
  registry.example.local/onec-server:8.3.27.2074
```

Лицензирование:

- серверная лицензия нужна на каждый компьютер, где работают процессы кластера [офиц.]; контейнер от этого требования не освобождает;
- варианты, которые перечисляет README официального `docker_fresh` [офиц.]: проброс аппаратных ключей HASP в контейнер; активация программных лицензий утилитой `ring` внутри образа; файл `nethasp.ini` с адресом сервера лицензий (для 8.5.4+ вместо HASP License Manager — менеджер лицензий `rmlic`);
- программная лицензия привязана к параметрам компьютера; при пересоздании контейнера, смене узла или параметров окружения привязка может нарушиться и потребовать повторной активации (число активаций ограничено) ⚠ [практика]. Поэтому для контейнеров предпочитают сетевые ключи/внешний сервер лицензий либо лицензии разработчика на непромышленных стендах;
- дистрибутив платформы доступен по вашей учётной записи releases.1c.ru; образы с платформой держат в закрытом реестре организации, публиковать их в открытом доступе нельзя ⚠ (следует из условий распространения дистрибутивов; точную формулировку уточняйте в лицензионном соглашении).

### 9.2. Ansible и автоматизация

Что рекомендует фирма «1С» по сути (без привязки к инструменту) [офиц., ИТС 5905]: иметь шаблоны машин «рабочий сервер», «сервер СУБД», «веб-сервер» и сценарии донастройки сервера до заданных параметров, установки платформы и СУБД, запуска и остановки служб, развёртывания баз; подготовительный стенд разворачивать этими же сценариями из рабочих резервных копий — так одновременно проверяются сценарии, копии и время восстановления.

Обзор готового [практика]:

- **Сервер 1С**: официальных Ansible-ролей от фирмы «1С» не найдено ⚠; роли сообщества существуют, но привязаны к конкретным версиям и способам установки (до 8.3.20 — deb-пакеты, с 8.3.20 — установщик `.run`), поэтому их приходится проверять и дорабатывать. Собственная роль невелика — см. пример ниже.
- **PostgreSQL**: распространённые роли общего назначения — `geerlingguy.postgresql` и `ANXS.postgresql` (установка из репозиториев дистрибутива/PGDG, управление `postgresql.conf`, `pg_hba.conf`, пользователями и базами); для отказоустойчивого кластера на Patroni — проект `autobase` (ранее `vitabaks/postgresql_cluster`). Все они ставят «ванильный» PostgreSQL: для 1С нужно подменить источник пакетов на сборку 1С (deb-файлы с releases.1c.ru) или репозиторий Postgres Pro и задать параметры из рекомендаций для 1С. У Postgres Pro есть утилита автонастройки `pgpro_tune` с готовым набором `1c.tune` [офиц., документация Postgres Pro].
- **Вокруг**: резервное копирование — `pg_probackup` (Postgres Pro) или сценарии с `pg_basebackup`/`pg_dump`. Открытый `pg_probackup`, собранный под ванильный PostgreSQL, отказывается работать с сервером, где есть `pg_catalog.pgpro_edition()` — брать версию для своей сборки, см. `../postgresql/04-…`, разд. 5.1; анализ журналов — pgBadger; управление кластером 1С из сценариев — `rac` (или библиотеки-обёртки над ним).

Минимальный сценарий установки сервера 1С встроенными модулями Ansible (набор компонентов и имена файлов — как в статье об установке):

```yaml
- hosts: onec_servers
  become: true
  vars:
    onec_version: "8.3.27.2074"
    onec_dir: "/opt/1cv8/x86_64/{{ onec_version }}"
  tasks:
    - name: Каталог для дистрибутива
      ansible.builtin.file:
        path: /opt/distr
        state: directory
        mode: "0755"

    - name: Распаковать дистрибутив (на целевом узле нужен unzip)
      ansible.builtin.unarchive:
        src: "files/server64_{{ onec_version | replace('.', '_') }}.zip"
        dest: /opt/distr/

    - name: Установить платформу в пакетном режиме
      ansible.builtin.command:
        cmd: "/opt/distr/setup-full-{{ onec_version }}-x86_64.run --mode unattended --enable-components server,ws,server_admin"
        creates: "{{ onec_dir }}/ragent"

    - name: Зарегистрировать юниты (аналог systemctl link)
      ansible.builtin.file:
        src: "{{ onec_dir }}/{{ item }}"
        dest: "/etc/systemd/system/{{ item }}"
        state: link
      loop:
        - "srv1cv8-{{ onec_version }}@.service"
        - "ras-{{ onec_version }}.service"

    - name: Включить и запустить службы
      ansible.builtin.systemd:
        name: "{{ item }}"
        enabled: true
        state: started
        daemon_reload: true
      loop:
        - "srv1cv8-{{ onec_version }}@default.service"
        - "ras-{{ onec_version }}.service"
```

Что ещё обычно автоматизируют: зависимости и шрифты, `/etc/hosts` и имя узла, drop-in юнитов (каталог данных, `TMPDIR`, лимиты памяти), `logcfg.xml`, правила сетевого экрана, параметры кластера через `rac` (идемпотентность — сравнением с выводом `rac … info`), публикации `webinst`, задания резервного копирования и мониторинга.

### 9.3. Что предлагает сама фирма «1С»: «1С:Центр администрирования»

Добавлено 10.10.2026 по статье ИТС «Подготовка окружения для групповой разработки и автоматизации тестирования с доставкой изменений в рабочие базы» (10.10.2023, `https://its.1c.ru/db/metod8dev/content/6015/hdoc`).

Он описывает и разворачивает инфраструктуру, выполняя внешние скрипты на целевых серверах; язык скриптов и интерпретатор — любые.
- 1С:ЦА вызывается из конвейеров CI/CD через сервисы удалённого управления и связывается с системами мониторинга.

Всё, что сказано о них в разделах 9.1, 9.2 и 9.4, — практика сообщества.
- Документация КИП на ИТС (`its.1c.ru/db/kip`) для этой базы знаний не читалась.

### 9.4. Kubernetes

Официальных материалов фирмы «1С» о запуске кластера серверов в Kubernetes не найдено (см. 9.3). Ниже — оценка по устройству платформы и опыту сообщества [практика].

**Что переносится в Kubernetes сравнительно легко — веб-уровень.** Модуль расширения веб-сервера (Apache с `wsap24.so` и каталогами публикаций) не хранит состояния: под с Apache можно пересоздавать и размножать, а перед ним ставить балансировщик. Такой опыт описан в сообществе (публикация «Ферма приложений на Kubernetes», Infostart): Kubernetes использовали для централизованной публикации и мониторинга интернет-сервисов 1С. Версия модуля в образе должна точно совпадать с версией кластера серверов.

**Что переносится плохо — сам кластер серверов 1С:**

| Свойство платформы | Чем мешает в Kubernetes |
|---|---|
| Клиент получает от менеджера кластера **имя хоста** рабочего сервера и порт из диапазона 1560–1591 | имя пода должно разрешаться у клиентов, а весь диапазон портов — быть доступен снаружи один к одному; обычный `Service` этого не даёт, приходится использовать сеть хоста (`hostNetwork`) и закреплять под за узлом |
| Реестр кластера, сеансовые данные, журнал регистрации лежат в каталоге данных | нужен постоянный том и ровно один экземпляр (`StatefulSet` с одной репликой); «масштабирование подами» невозможно — кластер 1С масштабируется добавлением рабочих серверов своими средствами |
| Программная лицензия привязана к параметрам компьютера (имя, процессоры, сетевые адаптеры, диски, память) | пересоздание пода или перенос на другой узел может нарушить привязку; нужен сетевой ключ, сервис лицензирования на отдельной постоянной машине либо жёсткое закрепление пода за узлом |
| Пороги памяти кластера считаются от памяти компьютера | учитывает ли платформа ограничение памяти контейнера, не подтверждено; пороги нужно задавать явно, иначе под будет убит по лимиту раньше, чем сработает собственная защита кластера |
| Аварийное завершение `rphost` — штатная ситуация, которую кластер обрабатывает сам | проверки живости пода не должны перезапускать весь сервер из-за одного рабочего процесса |

**PostgreSQL для 1С в Kubernetes.** Распространённые операторы (CloudNativePG, Zalando и подобные) ставят «ванильный» PostgreSQL; для 1С нужна сборка с патчами 1С или Postgres Pro, то есть собственный образ и проверка совместимости с оператором. Выигрыша перед отдельной машиной с пакетной установкой для одной-двух баз обычно нет.

**Вывод.** Для рабочего сервера 1С с пользователями и для его СУБД предпочтительны виртуальные машины, описанные сценариями (Ansible, 1С:ЦА). Kubernetes оправдан для веб-уровня, конвейеров сборки и тестовых стендов. ⚠ Всё в этом разделе, кроме ссылок на раздел 9.3, не подтверждено официальными источниками и на стенде не проверялось.

## Типичные ошибки и подводные камни (симптом → причина → решение)

| Симптом | Причина | Решение |
|---|---|---|
| Ядро убивает `postgres` или `rphost` (OOM), сервер «встаёт» | На совмещённом сервере лимиты памяти кластера оставлены по умолчанию (80 % / 95 % всей ОЗУ) и не учитывают PostgreSQL | Задать «Временно допустимый» и «Критический» объёмы явно (раздел 2.3); `MemoryMax=` для службы 1С; проверить память PostgreSQL |
| `rphost` перезапускается каждые несколько минут, пользователи получают ошибки | Лимит памяти меньше нормального рабочего объёма процессов | Поднять лимит выше обычного потребления; найти сеанс-виновник по `memory-current`/`duration-current` |
| После перезапуска службы «пропали все базы», кластер пустой | Агент стартовал с другим каталогом данных или от другого пользователя и создал новый кластер | Вернуть `SRV1CV8_DATA` и пользователя; не удалять старый каталог; восстановить из копии реестра |
| Менеджер кластера падает в цикле, растут дампы, не запускаются `rphost` | Кончилось место на томе с сеансовыми данными | Освободить место (раздел 6.9); держать техжурнал и сеансовые данные на разных томах; запас ≥ 25 % объёма сеансовых данных |
| Ошибки «отсутствует файл» во временном каталоге, сбои печати/обменов по утрам | Системная очистка `/tmp` удалила файлы работающего сервера | Отдельный каталог через `TMPDIR` (раздел 3.2) |
| «Ошибка совместного доступа к файлу snccntx.dat» | Нет прав на каталог сеансовых данных либо остался «лишний» `rmngr` с тем же идентификатором | Проверить владельца каталога (`usr1cv8`); завершить `rmngr`, которого нет в списке менеджеров кластера; при необходимости очистка кэша |
| Копия рабочей базы рассылает письма и выполняет обмены | В копии не заблокированы регламентные задания | `--scheduled-jobs-deny=on` сразу при создании/регистрации копии; копии не держать в рабочем кластере |
| После обновления платформы техжурнал перестал писаться | `logcfg.xml` остался в каталоге `conf` старой версии | Скопировать в `/opt/1cv8/x86_64/<новая версия>/conf/` |
| После обновления платформы служба стартует с настройками по умолчанию | Drop-in systemd привязан к имени юнита со старым номером версии | Перенести drop-in на новый юнит (статья об установке, раздел 13) |
| При отказе центрального сервера клиенты не подключаются, хотя второй сервер жив | В строке соединения указан один сервер, либо второй сервер не центральный | Список центральных серверов в строке соединения; флажок «Центральный сервер» и уровень отказоустойчивости ≥ 1 |
| В кластере из двух серверов «пропадают» лицензии / журнал регистрации / поиск | Сервисы лицензирования, журнала регистрации, полнотекстового поиска «переехали» на другой сервер | Закрепить эти сервисы требованиями назначения за конкретными серверами [офиц.] |
| Загрузка `.dt` падает с нехваткой памяти или места | Высокие требования к ОЗУ; временные файлы размером с развёрнутую базу в `/tmp` | Больше ОЗУ/свопа на время загрузки, `TMPDIR` на большой том, `-JobsCount`; для больших баз — `ibcmd infobase replicate` |
| После переезда на PostgreSQL проведение идёт «по одному» | Автоматический режим блокировок | Перевод конфигурации в управляемый режим (раздел 7.9) |
| После переезда отдельные отчёты в разы медленнее | Запросы, оптимизированные под MS SQL (FULL JOIN, соединения с подзапросами и виртуальными таблицами) | Раздел 7.9; план запроса с параметрами сеанса платформы |
| PostgreSQL остановился: `No space left on device` в `pg_wal` | Переполнен том (неработающий архив WAL, слот репликации, длинная транзакция) | Устранить причину, расширить том; **не удалять** файлы `pg_wal` вручную |
| Тест Гилёва показывает мало баллов при свободном сервере | Энергосбережение, низкая частота ядер, штраф гипервизора, включён техжурнал/отладка, медленный диск | Раздел 8.2; проверить `lscpu`, настройки хоста и BIOS |
| Плановый перезапуск «не срабатывает» после обновления до 8.3.27 | «Интервал перезапуска» объявлен устаревшим и не используется | Задать «Расписание перезапуска» в формате cron |
| Сервер ПРОФ в ВМ с 24 vCPU загружает только часть ядер | Лицензия ПРОФ использует до 12 ядер | Не выделять лишнее; при необходимости — КОРП или второй рабочий сервер |
| Долгий вход в программу, паузы при открытии сеансов | Поиск лицензии по сети, недоступный менеджер лицензий, расхождение часов (8.5.4+) | Раздел 5.4; `nethasp.ini`/`rclic.cfg`, синхронизация времени |
| Журнал регистрации открывается минутами, ошибки `sqlite3_step failed` | Журнал в формате SQLite, большой или повреждённый файл `1Cv8.lgd` | Перевести в последовательный формат; восстановление по ИТС 5867 |
| Запросы к `rac` «висят» или возвращают ошибку версии | `ras` не запущен, остался от старой версии или порт 1545 закрыт | `systemctl status ras-$V`; версии `ras`/`rac`/сервера должны совпадать |

## Быстрая шпаргалка — таблица «задача → команда»

Обозначения: `V` — версия платформы, `RAC=/opt/1cv8/x86_64/$V/rac`, `CL` — UUID кластера, `SRV` — UUID рабочего сервера, `IB` — UUID базы, `D=/home/usr1cv8/.1cv8/1C/1cv8`.

| Задача | Команда |
|---|---|
| UUID кластера / сервера | `CL=$($RAC cluster list \| awk '/^cluster /{print $3}')`; `$RAC server list --cluster=$CL` |
| Параметры кластера и сервера | `$RAC cluster info --cluster=$CL`; `$RAC server info --cluster=$CL --server=$SRV` |
| Память процессов кластера | `ps -C rphost,rmngr,ragent -o pid,rss,etimes,args --sort=-rss`; `$RAC process list --cluster=$CL` |
| Задать лимиты памяти (байты) ⚠ ключи — `rac help server` | `$RAC server update --cluster=$CL --server=$SRV --temporary-allowed-total-memory=N --critical-total-memory=M --temporary-allowed-total-memory-time-limit=120` |
| Соединений на процесс | `$RAC server update --cluster=$CL --server=$SRV --connections-limit=256` |
| Расписание перезапуска (8.3.27+) | `$RAC cluster update --cluster=$CL --restart-schedule="0 3 * * *"` |
| Список сеансов / по видам приложений | `$RAC session list --cluster=$CL`; `… \| awk -F' *: *' '/^app-id/{a[$2]++} END{for(k in a) print a[k],k}'` |
| Завершить сеанс | `$RAC session terminate --cluster=$CL --session=<UUID>` |
| Запретить регламентные задания базы | `$RAC infobase update --cluster=$CL --infobase=$IB --infobase-user=U --infobase-pwd=P --scheduled-jobs-deny=on` |
| Запретить новые сеансы с кодом доступа | `… --sessions-deny=on --permission-code=svc123 --denied-message="Работы"` |
