- [офиц.] — документация 1С (its.1c.ru, kb.1ci.com), заметки о выпуске версий (V8Update). [практика] — статьи и скрипты сообщества.

Как проверялись списки параметров `rac`. Официальная документация не перечисляет команды `rac` — она отсылает к встроенной справке `rac help`. Поэтому справочник собран из трёх слоёв: вывод `rac help` для версий 8.3.1x (сохранён в репозитории библиотеки irac), заметки о выпуске 8.3.12–8.3.27 и 8.5.1 (что добавлено в `rac` в каждой версии), документация 8.3.27 и 8.5.1 (смысл свойств). Свежий вывод `rac help` для 8.3.27/8.5 в открытых источниках найти не удалось, поэтому первым делом сохраните справку своей версии:

```bash
RAC=/opt/1cv8/x86_64/$V/rac
for m in agent cluster manager server process service infobase connection session \
         lock rule profile counter limit service-setting service-setting-server \
         service-setting-cluster binary-data-storage; do
  echo "===== $m ====="; "$RAC" help "$m"
done > ~/rac-help-$V.txt 2>&1
```

В списке есть и `service-setting` (имя режима в 8.3.26–8.5.1), и `service-setting-server` с `service-setting-cluster` (имена в 8.5.4): для отсутствующего в вашей версии режима в файл просто попадёт сообщение об ошибке.

Что дала проверка рецензента (2026-10-10). По первоисточникам сверены: справка `rac help` 8.3.1x по всем режимам (синтаксис команд, имена параметров и полей — совпадает с текстом статьи), заметки о выпуске 8.3.9–8.3.27 и 8.5.4 (версии появления параметров, умолчания 8.3.15, все изменения `rac` в 8.5.4), описание протокола сервера администрирования в `v8platform/protos` (какие операции вообще умеет `ras`). Не закрыты первоисточником только те места, что помечены «⚠»: для них нужен вывод `rac help` версий 8.3.26+ или закрытая документация ИТС.

## Кратко — главные факты и команды

1. Цепочка администрирования на Linux: `rac` → `ras` (порт **1545**) → `ragent` (порт **1540**) → кластер. MMC-консоль с Windows подключается к `ragent` напрямую и `ras` не использует [офиц.].
2. Запуск `ras`: `ras cluster [--daemon] [--port=1545] [<хост агента>[:<порт>]]`. Слово `cluster` обязательно. Адрес агента по умолчанию `localhost:1540`, порт `ras` по умолчанию 1545 [офиц.].
3. Как служба: `sudo systemctl link /opt/1cv8/x86_64/$V/ras-$V.service && sudo systemctl enable --now ras-$V.service` (юнит поставляется с 8.3.21).
4. Версия `ras` обязана совпадать с версией кластера. `rac` версии 8.3.9 и новее работает с `ras` версии 8.3.9 и новее; более старая `rac` просто не знает новых команд [офиц.].
5. Синтаксис `rac`: `rac <режим> [--cluster=<uuid>] [--cluster-user=… --cluster-pwd=…] <команда> [параметры] [<хост ras>[:<порт>]]`. Адрес `ras` по умолчанию `localhost:1545`. Справка: `rac help`, `rac help infobase`, `rac --version`.
6. Вывод — блоки строк `имя : значение`, записи разделены пустой строкой. Код возврата 0 — успех, иначе текст ошибки в stderr [офиц.].
7. UUID кластера: `CL=$(rac cluster list | awk '$1=="cluster"{print $3; exit}')`. Он нужен почти во всех командах.
8. Список баз: `rac infobase summary list --cluster=$CL`. Полные свойства: `rac infobase info --cluster=$CL --infobase=$IB --infobase-user=… --infobase-pwd=…`.
9. Три независимых уровня аутентификации: администратор центрального сервера (`--agent-user`/`--agent-pwd`), администратор кластера (`--cluster-user`/`--cluster-pwd`), администратор информационной базы (`--infobase-user`/`--infobase-pwd`). Аутентификацию средствами ОС `rac` не поддерживает [офиц.].
10. После установки списки администраторов пусты — любой, кто достучался до портов 1540/1545, управляет кластером. Создайте администраторов и закройте порт 1545 сетевым экраном [офиц.].
11. Сеансы: `rac session list --cluster=$CL [--infobase=$IB]`, завершить — `rac session terminate --cluster=$CL --session=<uuid>`.
12. Блокировка начала сеансов: `rac infobase update … --sessions-deny=on --denied-from=… --denied-to=… --denied-message=… --permission-code=…`, регламентные задания — `--scheduled-jobs-deny=on`. Вход при блокировке — параметр запуска клиента `/UC <код>` [офиц.].
13. Создать базу в PostgreSQL: `rac infobase create --cluster=$CL --create-database --name=demo --dbms=PostgreSQL --db-server=localhost --db-name=demo --locale=ru_RU --db-user=postgres --db-pwd=… --license-distribution=allow`.
14. Удалить регистрацию базы: `rac infobase drop --cluster=$CL --infobase=$IB` (+ `--drop-database` — удалить и базу СУБД, `--clear-database` — очистить её).
15. Требования назначения функциональности (режим `rule`) начинают действовать только после `rac rule --cluster=$CL apply --partial|--full` [офиц.].
16. Для PostgreSQL разрыв соединения, занятого запросом к СУБД, из кластера не работает: команда ничего не делает [офиц.]. Запрос снимают на стороне PostgreSQL (`pg_cancel_backend`, `pg_terminate_backend`).
17. Пороги памяти задаются у рабочего сервера: `--temporary-allowed-total-memory` (0 → 80% ОЗУ), `--critical-total-memory` (0 → 95% ОЗУ), `--temporary-allowed-total-memory-time-limit` (300 с) [офиц.].
18. С 8.3.27 перезапуск рабочих процессов задаётся расписанием в формате cron (`--restart-schedule` у кластера и рабочего сервера); «Интервал перезапуска» (`--lifetime-limit`) объявлен устаревшим и на поведение кластера больше не влияет [офиц., V8Update 8.3.27].
19. Сеансовые данные лежат в каталогах `snccntx*` внутри `/home/usr1cv8/.1cv8/1C/1cv8/reg_1541/` и переживают перезапуск сервера. Удалять их можно только при остановленной службе. Нельзя удалять `1cv8wsrv.lst`, `reg_1541/1CV8Clst.lst` и каталоги баз с журналом регистрации `1Cv8Log`.
20. Графика: MMC-оснастка есть только под Windows (версия оснастки = версия сервера); кроссплатформенный аналог — стандартная функция «Управление серверами» в клиентском приложении, она работает через `ras` [офиц.].
21. Умолчания нового кластера и нового рабочего сервера начиная с 8.3.15 [офиц., V8Update 8.3.15]: «Принудительно завершать проблемные процессы» включено, «Проблемные процессы завершать через» = 60 секунд, «Количество соединений на процесс» = 256 (раньше было 128), «Количество ИБ на процесс» = 8.
22. Нестандартный порт PostgreSQL в свойствах базы задаётся в адресе сервера СУБД: `--db-server="pg-host port=5433;"` — формат `<имя> port=<номер>;` описан в документации [офиц.].
23. В 8.5.4 интерфейс `rac` заметно изменился [офиц., V8Update 8.5.4]: режим `service-setting` переименован в `service-setting-server`, добавлены `service-setting-cluster`, `rac server enable|disable`, `rac agent info|update`, администраторы «только просмотр» (`--read-only`), версии настроек (`--get-data-version`, `--data-version`); у команд `rac connection` и `rac binary-data-storage` убраны `--infobase-user` и `--infobase-pwd`. Скрипты после перехода на 8.5.4 нужно перепроверить (раздел 9.1).
24. Забытый пароль администратора: до 8.5.4 штатного сброса нет; в 8.5.4 у агента сервера появились команды `/resetServerAdmins` и `/resetClusterAdmins` (раздел 4.6).

## 1. Как устроено администрирование кластера

```text
rac (командная строка) ───────────────┐
«Управление серверами» (клиент 1С) ───┼──► ras :1545 ──► ragent :1540 ──► rmngr :1541
Java-библиотека, irac, свои скрипты ──┘                                   rphost :1560-1591

MMC-консоль (только Windows) ─────────────────────────► ragent :1540  (напрямую, без ras)
```

Что важно знать [офиц., документация 8.3.27 и 8.5.1, раздел о сервере администрирования]:

| Факт | Следствие для администратора |
|---|---|
| `ras` и `rac` входят в состав сервера 1С (компонент установщика `server_admin`) и работают в любой поддерживаемой ОС | На Linux это основной способ управления кластером |
| Один `ras` работает с одним агентом сервера (`ragent`) | Для второго экземпляра сервера нужен второй `ras` на другом порту |
| К одному кластеру можно подключить несколько `ras` | Можно держать отдельный `ras` для мониторинга |
| `ras` подключается к кластеру только на время операции и затем отключается | При плановой остановке или перезапуске кластера останавливать `ras` не обязательно |
| Версия `ras` должна совпадать с версией кластера | При обновлении платформы меняется и юнит `ras-<версия>.service` |
| `rac` 8.3.9+ совместима с `ras` 8.3.9+; если `rac` старше `ras`, доступны только функции версии `rac` | Используйте `rac` из того же каталога версии, что и сервер |
| Обмен `rac` ↔ `ras` идёт по порту 1545 (меняется параметром `--port`) | Порт 1545 открывать только доверенным хостам |
| Все параметры `rac` передаются в командной строке | Пароли видны в списке процессов на время вызова (раздел 4.5) |
| `rac` не поддерживает аутентификацию средствами ОС (администраторы кластера, центрального сервера и ИБ) | Администратору, которым будете пользоваться из `rac`, нужна парольная аутентификация |

Группы совместимости `rac` и `ras` [офиц.]: 8.3.1–8.3.2; 8.3.3–8.3.4; 8.3.5–8.3.8; 8.3.9 и новее. Внутри группы версии могут различаться.

## 2. Сервер администрирования ras

### 2.1. Командная строка

```text
ras cluster [--daemon] [--port=<порт>] [--monitor-address=<адрес>] [--monitor-port=<порт>]
            [--monitor-base=<путь>] [<хост агента>[:<порт агента>]]
```

| Параметр | Назначение | Умолчание |
|---|---|---|
| `cluster` | Режим администрирования кластера серверов. Обязательный первый аргумент | — |
| `<хост>[:<порт>]` | Адрес агента сервера (`ragent`), которым будет управлять этот `ras` | `localhost:1540` |
| `--port=<порт>`, `-p <порт>` | Порт, на котором `ras` принимает подключения `rac` | `1545` |
| `--daemon` | Запуск в режиме демона (только Linux): процесс отвязывается от терминала | выключено |
| `--service` | Используется в командной строке службы Windows (в образце `register-ras.bat`) | — |
| `--monitor-address=<адрес>` | Адрес HTTP-шлюза показателей производительности: `localhost`, `any`, адрес IPv4 или IPv6 | `localhost` |
| `--monitor-port=<порт>` | Порт HTTP-шлюза показателей | `1555` |
| `--monitor-base=<путь>` | Базовый путь публикации показателей, начинается с `/` | `/` |

Источник таблицы — раздел документации 8.3.27 о командной строке `ras` [офиц.]. Параметры `--monitor-*` появились в 8.3.25: `ras` отдаёт показатели производительности кластера в формате OpenMetrics, функция требует лицензию КОРП, доступ к метрикам — с аутентификацией платформы [офиц., V8Update 8.3.25].

Справка самой программы: `ras help`, `ras help cluster`.

Примеры:

```bash
# в терминале (для проверки), Ctrl+C — остановить
/opt/1cv8/x86_64/$V/ras cluster --port=1545 localhost:1540

# в фоне
/opt/1cv8/x86_64/$V/ras cluster --daemon --port=1545 localhost:1540

# ras для второго экземпляра сервера (агент на 2540)
/opt/1cv8/x86_64/$V/ras cluster --daemon --port=2545 localhost:2540

# ras с метриками OpenMetrics на всех интерфейсах (8.3.25+, КОРП)
/opt/1cv8/x86_64/$V/ras cluster --port=1545 --monitor-address=any --monitor-port=1555 \
    --monitor-base=/metrics localhost:1540
```

Ключ `--daemon` сам по себе автозапуск после перезагрузки не даёт — для этого нужна служба systemd.

### 2.2. Служба systemd

С версии 8.3.21 в дистрибутив входит юнит `ras-<версия>.service`, он лежит в каталоге версии [офиц., V8Update 8.3.21]. Автоматически он не регистрируется.

```bash
V=8.3.27.2074
sudo systemctl link /opt/1cv8/x86_64/$V/ras-$V.service   # зарегистрировать юнит (нужен полный путь)
sudo systemctl enable --now ras-$V.service               # автозапуск и немедленный старт
systemctl status ras-$V.service --no-pager               # ожидается Active: active (running)
systemctl cat ras-$V.service                             # посмотреть, что именно запускается
journalctl -u ras-$V.service -n 50 --no-pager            # журнал службы
```

⚠ не подтверждено дословно: содержимое штатного юнита (тип службы, пользователь, строка `ExecStart`). Сам файл вендора в открытых источниках не опубликован, документация на ИТС закрыта. Что известно косвенно [практика]:

- `systemctl status` показывает описание службы «1C:Enterprise Remote Administration Server 8.3» (вывод в статье 1smonitor.ru для 8.3.27.2074);
- в руководстве k1c.proapdex.ru копия, сделанная из штатного файла 8.3.22.1750, содержит `Type=simple`, порт в переменной `Environment=RAS_PORT=1545`, адрес кластера в переменной `Environment=RAS_CLUSTER_ADDRESS=<хост>:<порт>` и строку `ExecStart=/opt/1cv8/x86_64/8.3.22.1750/ras cluster --port=${RAS_PORT} $RAS_CLUSTER_ADDRESS`, то есть запуск без `--daemon`. Насколько эта копия совпадает с оригиналом, по тексту руководства судить нельзя.

Поэтому перед правкой всегда смотрите `systemctl cat ras-$V.service`. Если в вашем файле порт и адрес действительно заданы переменными окружения, в drop-in достаточно переопределить их (`Environment=RAS_PORT=2545`), не трогая `ExecStart`.

Изменить порт или адрес агента — через drop-in, а не правкой файла в `/opt`:

```bash
sudo systemctl edit ras-$V.service
```

```ini
[Service]
ExecStart=
ExecStart=/opt/1cv8/x86_64/8.3.27.2074/ras cluster --port=1545 localhost:1540
```

Пустая строка `ExecStart=` сбрасывает исходную команду. Если в штатном юните `Type=forking`, в новой строке нужен ключ `--daemon`; если `Type=simple` — без него.

Свой юнит (когда штатный не подходит, например для второго экземпляра сервера) [практика]:

```ini
# /etc/systemd/system/ras-1c-2545.service
[Unit]
Description=1C:Enterprise Remote Administration Server (agent 2540)
After=network-online.target
Wants=network-online.target

[Service]
Type=simple
User=usr1cv8
Group=grp1cv8
ExecStart=/opt/1cv8/x86_64/8.3.27.2074/ras cluster --port=2545 localhost:2540
Restart=on-failure
RestartSec=5

[Install]
WantedBy=multi-user.target
```

```bash
sudo systemctl daemon-reload
sudo systemctl enable --now ras-1c-2545.service
```

При обновлении платформы: `sudo systemctl disable --now ras-$OLD.service`, затем `link` и `enable --now` для новой версии. Старый `ras` с новым кластером работать не будет.

### 2.3. Проверка

```bash
sudo ss -tlnp | grep -E ':1545|:1540'        # слушают ли ras и ragent
pgrep -a ras                                  # командная строка процесса ras
/opt/1cv8/x86_64/$V/rac cluster list          # если вернул UUID — цепочка rac → ras → ragent работает
/opt/1cv8/x86_64/$V/rac agent version         # версия агента сервера (8.3.16+)
```

### 2.4. Безопасность

- У `ras` нет собственных паролей: он лишь передаёт команды агенту. Защита — списки администраторов центрального сервера и кластера (раздел 4) и сетевой экран.
- Открывайте порт 1545 только рабочим местам администраторов и серверу мониторинга:

```bash
sudo ufw allow from 192.168.1.10 to any port 1545 proto tcp comment '1C RAS'
sudo ufw deny 1545/tcp
```

- Если `rac` запускается только на самом сервере (по SSH), порт 1545 наружу не открывайте вовсе.
- У администратора есть флажок «Аутентификация паролем только с локального компьютера» (вход по паролю только с компьютеров, где работает кластер); документация не рекомендует его снимать [офиц.]. Когда `ras` работает на том же хосте, что и `ragent`, флажок не мешает.
- **Уточнено 10.10.2026** (полный текст приложения 4 документации 8.3.27): у `ras` описаны только `--port`, `--monitor-address`, `--monitor-port`, `--monitor-base` и адрес агента — параметра, ограничивающего адрес прослушивания основного порта, нет. Ранее было не подтверждено: есть ли у `ras` параметр, ограничивающий адрес прослушивания основного порта (как `--monitor-address` для шлюза метрик). В документации такого параметра нет.

## 3. Утилита rac: общий синтаксис

### 3.1. Строка запуска и справка

```text
rac [<режим>] [<команда>] [<параметры>] [<хост ras>[:<порт>]]
```

| Элемент | Значение |
|---|---|
| `<режим>` | Что администрируем: `agent`, `cluster`, `server`, `infobase`, `session` и т. д. (таблица в 3.2) |
| `<команда>` | Действие в режиме: `list`, `info`, `insert`, `update`, `remove` и др. У части режимов есть вложенные команды (`cluster admin list`, `infobase summary list`, `profile acl directory list`) |
| Параметры режима | Общие для всех команд режима: `--cluster=<uuid>`, `--cluster-user=<имя>`, `--cluster-pwd=<пароль>` (в режиме `agent` — `--agent-user`, `--agent-pwd`) |
| Параметры команды | Вида `--имя=значение`; флаги без значения (`--licenses`, `--create-database`) |
| `<хост>[:<порт>]` | Адрес `ras`. По умолчанию `localhost:1545` |
| `--version`, `-v` | Версия утилиты |
| `--help`, `-h`, `-?` | Краткая справка |

```bash
rac help                 # список режимов
rac help infobase        # все команды и параметры режима infobase
rac --version
```

Практические замечания:

- Режим всегда идёт первым. Параметры режима встречаются и до команды, и после неё: в рабочих скриптах сообщества используются обе записи — `rac infobase --cluster=$CL summary list` и `rac session list --cluster=$CL` [практика].
- Адрес `ras` обычно пишут последним аргументом: `rac cluster list srv1c:1545`.
- Значения с пробелами и кириллицей берите в кавычки оболочки: `--denied-message="Идут регламентные работы"`.
- Запись `--cluster <uuid>` (через пробел) тоже встречается в рабочих скриптах [практика]; документированная форма — через `=`.
- `rac` может ждать ответа долго, если `ras` или агент недоступны. В скриптах оборачивайте вызов в `timeout`: `timeout 30 rac …` [практика].

### 3.3. Формат вывода и разбор в bash

Правила вывода [офиц.]:

- результат идёт в stdout, ошибка — в stderr, код возврата 0 при успехе;
- каждое свойство — отдельная строка `<имя> : <значение>`; пустая строка завершает описание объекта;
- имена свойств совпадают с ключами командной строки; у свойств только для чтения имя образовано от имени свойства COM-объекта в нижнем регистре через дефис (`MemoryExcessTime` → `memory-excess-time`);
- команды создания (кроме создания администраторов) печатают идентификатор созданного объекта в том же формате, например `infobase : <uuid>`;
- строки с произвольными символами выводятся в двойных кавычках, кавычка внутри строки удваивается;
- даты — в формате XML dateTime: `2026-10-10T14:05:31`.

Пример (иллюстрация формата; набор полей зависит от версии):

```text
$ rac cluster list
cluster                       : 0d1c7a3e-6f5b-4a52-9d0e-3b7c2f4a8e11
host                          : srv1c
port                          : 1541
name                          : "Локальный кластер"
expiration-timeout            : 60
lifetime-limit                : 0
max-memory-size               : 0
max-memory-time-limit         : 0
security-level                : 0
session-fault-tolerance-level : 0
load-balancing-mode           : performance
errors-count-threshold        : 0
kill-problem-processes        : 1
kill-by-memory-with-dump      : 0
```

Пояснения к примеру:

- Значения `expiration-timeout : 60` и включённое `kill-problem-processes` — умолчания кластера, созданного платформой 8.3.15 и новее [офиц., V8Update 8.3.15]. У кластера, созданного более старой версией, там стоят `0`.
- ⚠ не подтверждено первоисточником: вид логических значений именно в этих двух полях (`1`/`0`). В командной строке они задаются как `yes|no` (справка `rac help cluster`), в других местах вывода `rac` логические поля печатаются словами (`is-enable : yes`, `hibernate : no`, `issued-by-server : yes`). В скриптах сравнивайте с обоими вариантами: `[[ $v == 1 || $v == yes ]]`.
- В 8.3.26+ в выводе `cluster info` добавляются `ping-period`, `ping-timeout` и `allow-access-right-audit-events-recording` (последнее — и в `cluster list`) [офиц., V8Update 8.3.26]. В 8.3.27+ по общему правилу («имя поля совпадает с ключом командной строки») ожидается поле `restart-schedule`.

Одно значение достаётся через `awk` по первому полю (в строке `cluster : <uuid>` это третье слово):

```bash
CL=$(rac cluster list | awk '$1=="cluster"{print $3; exit}')
```

Для табличной обработки удобна функция, которая превращает блоки `имя : значение` в строки с табуляцией. Имя отделяется от значения по первому двоеточию, поэтому даты и пути со своими двоеточиями не ломаются:

```bash
# использование: rac session list … | rac_table session-id user-name app-id
rac_table() {
  awk -v fields="$*" '
    BEGIN { n = split(fields, f, " ") }
    function flush(   i, v, line) {
      if (!have) return
      line = ""
      for (i = 1; i <= n; i++) {
        v = rec[f[i]]; if (v == "") v = "-"
        line = line (i > 1 ? "\t" : "") v
      }
      print line
      split("", rec); have = 0
    }
    /^[[:space:]]*$/ { flush(); next }
    {
      p = index($0, ":"); if (p == 0) next
      key = substr($0, 1, p - 1); gsub(/^[ \t]+|[ \t]+$/, "", key)
      val = substr($0, p + 1);    gsub(/^[ \t]+|[ \t\r]+$/, "", val)
      if (val ~ /^".*"$/) { val = substr(val, 2, length(val) - 2); gsub(/""/, "\"", val) }
      rec[key] = val; have = 1
    }
    END { flush() }'
}
```

Пустые значения заменяются на `-`, чтобы столбцы не съезжали при выводе через `column -t`.

## 4. Аутентификация администраторов

### 4.1. Три уровня

| Уровень | Что разрешает | Параметры `rac` | Где хранится список |
|---|---|---|---|
| Администратор центрального сервера (агента) | Действия с центральным сервером: создание и изменение кластеров, список администраторов центрального сервера | `--agent-user`, `--agent-pwd` | Реестр сервера `1cv8wsrv.lst` в каталоге данных сервера |
| Администратор кластера | Всё внутри кластера: рабочие серверы, базы, сеансы, соединения, требования, профили | `--cluster-user`, `--cluster-pwd` | Реестр кластера `reg_<порт>/1CV8Clst.lst` |
| Администратор информационной базы | Чтение и изменение свойств базы, удаление базы, подробный список соединений базы | `--infobase-user`, `--infobase-pwd` | Пользователь самой базы с административными правами |

Правила [офиц.]:

- Сразу после установки оба списка администраторов пусты, и аутентификация не запрашивается: любой подключившийся к центральному серверу может всё.
- Аутентификация включается автоматически, как только в соответствующем списке появляется первый администратор.
- Права двух списков не пересекаются. Вход администратором центрального сервера не даёт прав на кластер, и наоборот: для действий с кластером достаточно администратора кластера.
- Способы аутентификации администратора: паролем, средствами ОС, открытым ключом (пара ключей; документация рекомендует этот способ). В `rac` аутентификация средствами ОС не поддерживается. ⚠ не подтверждено: поддерживает ли `rac` аутентификацию открытым ключом. Способ описан для консоли и для объекта встроенного языка `АдминистрированиеСервера`; в справке `rac` 8.3.1x параметр `--auth` принимает только `pwd[,os]`, в заметках о выпуске 8.3.9–8.3.27 и 8.5.4 параметров `rac` для ключей нет, в открытом описании протокола сервера администрирования (`v8platform/protos`) есть только запросы аутентификации именем и паролем. Практический вывод: администратору, которым вы пользуетесь из `rac`, оставляйте парольную аутентификацию.
- С 8.5.4 [офиц., V8Update 8.5.4]: администратору кластера или центрального сервера можно дать «Доступ только на просмотр» (параметр `--read-only` команд `rac agent admin register` и `rac cluster admin register`) — такой администратор видит настройки, но не может их менять; платформа не принимает слабые пароли администраторов (проверка по встроенному списку); подбор пароля блокируется параметрами кластера `--max-unsuccessful-cluster-admin-auth-attempts-count` (сколько неудачных попыток допускается) и `--cluster-admin-auth-lock-duration` (длительность блокировки). ⚠ Формат значения `--read-only`, единицы и умолчания двух параметров блокировки в заметках о выпуске не указаны — смотрите `rac help agent` и `rac help cluster`.
- Администратор без единого включённого способа аутентификации может выполнять только действия, не требующие аутентификации.
- Пароли администраторов в служебных данных хранятся в виде хеша SHA1; пароли доступа к СУБД — с возможностью восстановления (AES128). Поэтому каталог данных кластера должен быть доступен только пользователю `usr1cv8`.
- Если в базе нет ни одного пользователя, параметры `--infobase-user` и `--infobase-pwd` не нужны.
- Рабочий сервер, не являющийся центральным, но имеющий свой непустой список администраторов, должен содержать администратора с тем же именем и паролем, что у администратора центрального сервера кластера (либо администратора с аутентификацией ОС для пользователя, от имени которого работает `ragent` центрального сервера).

### 4.2. Администраторы центрального сервера: режим agent

```text
rac agent [--agent-user=<имя> --agent-pwd=<пароль>] admin list
rac agent [--agent-user=… --agent-pwd=…] admin register --name=<имя> [--pwd=<пароль>]
          [--descr=<описание>] [--auth=pwd[,os]] [--os-user=<пользователь ОС>]
rac agent  --agent-user=… --agent-pwd=…  admin remove --name=<имя>
rac agent version
```

| Параметр | Назначение |
|---|---|
| `--name=<имя>` | Имя администратора (обязательный). Уникально в пределах центрального сервера, после создания не меняется |
| `--pwd=<пароль>` | Пароль при парольной аутентификации |
| `--descr=<описание>` | Произвольное описание |
| `--auth=pwd[,os]` | Способы аутентификации: `pwd` — имя и пароль, `os` — средствами ОС. В выводе встречаются значения `pwd`, `os`, `pwd\|os` |
| `--os-user=<имя>` | Пользователь ОС в формате `\\домен\пользователь` |

```bash
# первый администратор центрального сервера (список пуст — аутентификация не нужна)
rac agent admin register --name=agentadmin --pwd='S3cret!' --auth=pwd --descr="Администратор сервера"

# дальше любые действия уровня агента требуют имя и пароль
rac agent admin list --agent-user=agentadmin --agent-pwd='S3cret!'
rac agent admin remove --name=old --agent-user=agentadmin --agent-pwd='S3cret!'
```

Сверено со справкой `rac help agent` 8.3.1x: `--agent-user` и `--agent-pwd` — параметры режима `agent`; у `admin register` обязателен только `--name`; поле `pwd` в выводе не показывается (только запись); значения поля `auth` — пусто, `pwd`, `os`, `pwd|os`.

Добавлено в 8.5.4 [офиц., V8Update 8.5.4]: команды `rac agent info` и `rac agent update` (свойства центрального сервера; их параметры в заметках о выпуске не перечислены ⚠ — `rac help agent`), параметр `--read-only` у `admin register`, параметры версии настроек `--get-data-version` (у `agent admin list`) и `--data-version` (у `agent admin register` и `agent admin remove`) — см. 9.1.

### 4.3. Администраторы кластера: cluster admin

```text
rac cluster admin list     --cluster=<uuid> [--cluster-user=… --cluster-pwd=…]
rac cluster admin register --cluster=<uuid> --name=<имя> [--pwd=<пароль>] [--descr=…]
                           [--auth=pwd[,os]] [--os-user=…]
                           [--agent-user=… --agent-pwd=…] [--cluster-user=… --cluster-pwd=…]
rac cluster admin remove   --cluster=<uuid> --name=<имя> [--cluster-user=… --cluster-pwd=…]
```

```bash
# первый администратор кластера
rac cluster admin register --cluster=$CL --name=cladmin --pwd='Cl-S3cret!' --auth=pwd \
    --agent-user=agentadmin --agent-pwd='S3cret!'

# проверка: без пароля теперь должно быть отказано, с паролем — список
rac cluster admin list --cluster=$CL
rac cluster admin list --cluster=$CL --cluster-user=cladmin --cluster-pwd='Cl-S3cret!'
```

Параметры `--agent-user` и `--agent-pwd` у `cluster admin register` нужны, когда список администраторов центрального сервера не пуст; `--cluster-user` и `--cluster-pwd` — когда в кластере уже есть администраторы. Состав параметров сверен со справкой `rac help cluster` 8.3.1x: у `admin register` там перечислены `--name` (обязательный), `--pwd`, `--descr`, `--auth=pwd[,os]`, `--os-user`, `--agent-user`, `--agent-pwd`; у `admin remove` — только `--name`.

С 8.5.4 у `cluster admin register` есть параметр `--read-only` (администратор «только просмотр»), у `cluster admin list` — `--get-data-version`, у `cluster admin register` и `cluster admin remove` — `--data-version` [офиц., V8Update 8.5.4].

### 4.4. Рекомендуемый порядок первичной настройки

1. Убедиться, что `rac cluster list` работает без паролей (свежий сервер).
2. Создать администратора центрального сервера (`rac agent admin register`).
3. Создать администратора кластера (`rac cluster admin register`).
4. В каждой рабочей базе завести пользователя с административными правами — он понадобится для `infobase info`, `update`, `drop`.
5. Ограничить порт 1545 сетевым экраном (раздел 2.4).
6. Записать имена и пароли в защищённое хранилище. Штатного «сброса пароля» у кластера до версии 8.5.4 нет (раздел 4.6).

### 4.5. Пароли в командной строке

`rac` принимает все параметры только из командной строки [офиц.], поэтому пароль на время вызова виден в `ps` другим пользователям сервера и может осесть в истории команд. Как снизить риск [практика]:

```bash
# файл с параметрами: читает только root
sudo install -m 600 -o root -g root /dev/null /etc/1c-rac.env
sudoedit /etc/1c-rac.env
#   RAS=localhost:1545
#   CL_USER=cladmin
#   CL_PWD='Cl-S3cret!'
#   IB_USER='Администратор'
#   IB_PWD='Ib-S3cret!'

# интерактивно: спросить пароль, не показывая и не записывая в историю
read -rsp 'Пароль администратора кластера: ' CL_PWD; echo

# не сохранять команду в истории bash: начать её с пробела (нужно HISTCONTROL=ignorespace или ignoreboth)
 rac cluster admin list --cluster=$CL --cluster-user=cladmin --cluster-pwd="$CL_PWD"
```

Дополнительно: держите на сервере 1С минимум интерактивных пользователей и закройте `/proc` чужих процессов (опция монтирования `hidepid=2`), если это допустимо в вашей системе.

### 4.6. Если пароль администратора утерян

**Платформа 8.5.4 и новее** [офиц., V8Update 8.5.4]: реализован штатный сброс забытого пароля администратора кластера или сервера. У агента сервера (`ragent`) появились команды `/resetServerAdmins` (администраторы центрального сервера) и `/resetClusterAdmins` (администраторы кластера); после сброса средства администрирования предлагают создать администратора заново с новым паролем. ⚠ не подтверждено: точный порядок применения (нужно ли останавливать службу, как передавать каталог данных `/d` и порты, какой кластер сбрасывается при нескольких кластерах) — в заметках о выпуске названы только имена команд; описание в документации 8.5.4 на ИТС закрыто подпиской. До чтения документации исходите из того, что команду запускают от пользователя `usr1cv8` при остановленной службе, с тем же каталогом данных, что и у службы, и предварительно делают копию каталога данных кластера.

**Платформа до 8.5.4 (8.3.x, 8.5.1)**: штатной команды сброса нет. Практика сообщества [практика, ⚠ не подтверждено официальной документацией]: остановить службу сервера, сделать копию каталога данных кластера и либо восстановить реестр из резервной копии, сделанной до назначения администраторов, либо пересоздать кластер (убрать `1cv8wsrv.lst` и `reg_<порт>` — кластер создастся заново, базы придётся зарегистрировать повторно). Ручная правка файлов `*.lst` — на свой риск и только с копией.

Чего делать не надо: удалять каталог `reg_<порт>` без копии — в нём журналы регистрации всех баз (раздел 7.2); удалять один из двух реестров, оставляя другой, — `1cv8wsrv.lst` хранит список кластеров сервера, `1CV8Clst.lst` — состав самого кластера [офиц.], и поведение агента при таком рассогласовании не документировано.

## 5. Справочник режимов и команд rac

Во всех режимах, кроме `agent` и части команд `cluster`, обязателен параметр `--cluster=<uuid>`; `--cluster-user` и `--cluster-pwd` нужны, если в кластере есть администраторы. В синтаксических схемах они для краткости опущены, в примерах обозначены переменной `$AUTH`:

```bash
CL=$(rac cluster list | awk '$1=="cluster"{print $3; exit}')
AUTH="--cluster-user=cladmin --cluster-pwd=$CL_PWD"   # пусто, если администраторов кластера нет
```

Такая запись годится для имени и пароля без пробелов. В скриптах надёжнее массив bash (раздел 6.1).

### 5.1. Режим cluster

```text
rac cluster list
rac cluster info   --cluster=<uuid>
rac cluster insert --host=<хост> --port=<порт> [--name=<имя>] [свойства] [--agent-user=… --agent-pwd=…]
rac cluster update --cluster=<uuid> [--name=<имя>] [свойства] [--agent-user=… --agent-pwd=…]
rac cluster remove --cluster=<uuid> [--cluster-user=… --cluster-pwd=…]
rac cluster admin list|register|remove …        (см. 4.3)
```

Свойства кластера:

| Параметр `rac` | Свойство в консоли | Смысл | Значения, замечания |
|---|---|---|---|
| `--host=<хост>` | Компьютер | Компьютер, на котором лежит реестр кластера и работает главный менеджер | Только `insert`. Имя должно совпадать с тем, как сервер записан везде в кластере |
| `--port=<порт>` | IP порт | Порт главного менеджера кластера | Только `insert`. По умолчанию при создании кластера платформой — `1541`. Порты менеджеров уникальны в пределах центрального сервера |
| `--name=<имя>` | Имя кластера | Произвольное представление | — |
| `--security-level=<n>` | Защищённое соединение | Уровень защиты соединений | `0` — выключено, `1` — только соединение, `2` — постоянно. После изменения нужен перезапуск кластера [офиц.] |
| `--session-fault-tolerance-level=<n>` | Уровень отказоустойчивости | Сколько рабочих серверов может одновременно выйти из строя без аварийного завершения сеансов | `0` — нет резервирования. Реплицируемые сервисы размещаются на «уровень + 1» серверах |
| `--load-balancing-mode=performance\|memory` | Режим распределения нагрузки | Критерий выбора рабочего процесса для нового соединения | `performance` — приоритет по доступной производительности; `memory` — по доступной памяти |
| `--kill-problem-processes=yes\|no` | Принудительно завершать проблемные процессы | Разрешить кластеру завершать средствами ОС процессы, признанные мониторингом проблемными | На сам мониторинг не влияет. У нового кластера 8.3.15+ включено по умолчанию [офиц., V8Update 8.3.15] |
| `--expiration-timeout=<сек>` | Проблемные процессы завершать через … секунд (в старых версиях — «Выключенные процессы останавливать через») | Через сколько секунд проблемный или выключенный процесс останавливается принудительно, даже если у него есть соединения | `0` — принудительное завершение не выполняется. Соединения процесса при этом рвутся аварийно. Меняется на работающем кластере. У нового кластера 8.3.15+ по умолчанию `60` [офиц., V8Update 8.3.15]. Это же время ограничивает передачу соединений при перезапуске по расписанию и при выключении процесса |
| `--kill-by-memory-with-dump=yes\|no` | Записывать дамп процесса при превышении критического объёма памяти | Формировать дамп, когда кластер завершает процесс из-за превышения «Критического объёма памяти процессов» рабочего сервера | С 8.3.15. На Linux дамп пишется по сигналу `SIGABRT`, действуют настройки дампов ОС |
| `--restart-schedule=<cron>` | Расписание перезапуска | Расписание перезапуска рабочих процессов кластера | С 8.3.27. Формат — ниже. Расписание рабочего сервера имеет приоритет. Не задано нигде — перезапуска по расписанию нет |
| `--ping-period=<мс>`, `--ping-timeout=<мс>` | Период проверки, Таймаут проверки | Параметры системы отслеживания разрыва соединений | С 8.3.26, команда `cluster update`. Если хотя бы один не равен `0`, действуют значения кластера, иначе — параметры запуска `ragent` (по умолчанию 1000 и 5000 мс) |
| `--allow-access-right-audit-events-recording=…` | Разрешать запись событий аудита прав доступа | Запись событий аудита прав доступа в журнал регистрации для всех баз кластера | С 8.3.26, КОРП, по умолчанию выключено. Параметр есть у `cluster insert` и `cluster update`, значение выводится в `cluster list` и `cluster info` [офиц., V8Update 8.3.26]. ⚠ допустимые значения (`yes\|no`) сверить по `rac help cluster` |
| `--security-profile-name=<имя>` | Профиль безопасности (кластера) | Профиль безопасности по умолчанию: применяется ко всем информационным базам, которые обслуживает кластер | С 8.5.4, команды `cluster insert` и `cluster update` [офиц., V8Update 8.5.4] |
| `--max-unsuccessful-cluster-admin-auth-attempts-count=<n>` | Максимальное количество неуспешных попыток аутентификации администратора кластера | Защита от подбора пароля администратора | С 8.5.4, `cluster insert` и `cluster update`. ⚠ умолчание в заметках о выпуске не указано |
| `--cluster-admin-auth-lock-duration=<n>` | Длительность блокировки аутентификации администратора кластера | На сколько блокируется аутентификация после исчерпания попыток | С 8.5.4. ⚠ единицы и умолчание в заметках о выпуске не указаны |
| `--lifetime-limit=<сек>` | Интервал перезапуска | Периодический перезапуск рабочих процессов | С 8.3.27 объявлен устаревшим и на поведение кластера не влияет (заменён расписанием) [офиц., V8Update 8.3.27]. До 8.3.27: `0` — не перезапускать |
| `--max-memory-size=<КБ>` | Допустимый объём памяти | Старый порог памяти рабочего процесса | Удалён из свойств кластера в 8.3.15: вместо него — пороги памяти рабочего сервера (5.3). Параметр остался для совместимости со старыми версиями кластера [офиц., V8Update 8.3.15] |
| `--max-memory-time-limit=<сек>` | Интервал превышения допустимого объёма памяти | Старый допуск по времени превышения | Удалён из свойств кластера в 8.3.15, оставлен для совместимости |
| `--errors-count-threshold=<%>` | Допустимое отклонение количества ошибок сервера | Порог мониторинга по доле ошибок | Удалён из свойств кластера в 8.3.15 (свойство `ErrorsCountThreshold` объявлено устаревшим) [офиц., V8Update 8.3.15]; в справке `rac` 8.3.1x параметр есть, в новых версиях не используйте |

Какая аутентификация какой команде нужна (по справке `rac help cluster` 8.3.1x): `cluster insert` и `cluster update` принимают `--agent-user` и `--agent-pwd` (администратор центрального сервера), `cluster remove` — `--cluster-user` и `--cluster-pwd` (администратор кластера); у `cluster list` и `cluster info` параметров аутентификации в справке нет (в рабочих скриптах мониторинга `rac cluster list` вызывается без имени и пароля и при заданных администраторах [практика]). Параметры `--host` и `--port` есть только у `insert`: перенести кластер на другой компьютер или порт командой `update` нельзя.

С 8.5.4 у `cluster list` и `cluster info` есть параметр `--get-data-version`, у `cluster update` — `--data-version`: версия настроек не даёт двум администраторам одновременно перезаписать одни и те же настройки (раздел 9.1).

Формат расписания перезапуска [офиц., приложение «Формат строки расписания перезапуска рабочих процессов»]: пять полей через пробел — минута (0–59), час (0–23), день месяца (1–31), месяц (1–12), день недели (0–6, 0 — воскресенье). В поле допускаются число, список через запятую, диапазон `a-b`, `*` (каждое значение) и шаг `/n`. Названия месяцев и дней, а также макросы вида `@yearly` не используются.

| Строка | Когда срабатывает |
|---|---|
| `0 3 * * *` | Каждый день в 03:00 |
| `0 3 * * 6` | Каждую субботу в 03:00 |
| `0 3 * * 1-5` | С понедельника по пятницу в 03:00 |
| `0 3 1 * *` | Первого числа каждого месяца в 03:00 |
| `*/10 * * * *` | Каждые 10 минут (для проверки, не для работы) |

Как проходит перезапуск по расписанию и выключение процесса [офиц.]: старый процесс выключается, но продолжает обслуживать свои соединения; запускается новый процесс, в него системными фоновыми заданиями (`SystemBackgroundJob`) загружаются контексты тех же баз; затем соединения передаются новому процессу. Старый процесс завершается, когда переданы все соединения либо когда истекло время `--expiration-timeout`. Процессы одного сервера перезапускаются по очереди, на разных серверах — параллельно. Резервные рабочие процессы расписание не затрагивает.

Примеры:

```bash
rac cluster info --cluster=$CL

# имя кластера и параметры мониторинга
rac cluster update --cluster=$CL --name="Основной кластер" \
    --kill-problem-processes=yes --expiration-timeout=60 --kill-by-memory-with-dump=no \
    --agent-user=agentadmin --agent-pwd="$AGENT_PWD"

# ночной перезапуск рабочих процессов (8.3.27+)
rac cluster update --cluster=$CL --restart-schedule="0 3 * * *" \
    --agent-user=agentadmin --agent-pwd="$AGENT_PWD"

# до 8.3.27: перезапуск раз в сутки (86400 секунд)
rac cluster update --cluster=$CL --lifetime-limit=86400

# второй кластер на том же центральном сервере
rac cluster insert --host=srv1c --port=2541 --name="Тестовый кластер" \
    --agent-user=agentadmin --agent-pwd="$AGENT_PWD"

# удаление кластера: аварийно завершает все соединения с ним (CL2 — UUID удаляемого кластера)
rac cluster remove --cluster="$CL2" --cluster-user=cladmin --cluster-pwd="$CL_PWD"
```

### 5.2. Режим manager

```text
rac manager list --cluster=<uuid>
rac manager info --cluster=<uuid> --manager=<uuid>
```

Поля: `manager` (UUID), `pid` (PID процесса `rmngr` в ОС), `using` (вариант использования, например `normal`), `host`, `port`, `descr` (описание: «Главный менеджер кластера» либо «Дополнительный менеджер кластера (<сервис>)»). Создавать и удалять менеджеры вручную нельзя: их число определяют требования назначения и свойства рабочего сервера «Менеджер под каждый сервис» и «Центральный сервер» [офиц.].

### 5.3. Режим server (рабочие серверы)

```text
rac server list   --cluster=<uuid>
rac server info   --cluster=<uuid> --server=<uuid>
rac server insert --cluster=<uuid> --agent-host=<хост> --agent-port=<порт> --port-range=<мин>:<макс>
                  [--name=<описание>] [свойства]
rac server update --cluster=<uuid> --server=<uuid> [свойства]
rac server remove --cluster=<uuid> --server=<uuid>
rac server enable|disable --cluster=<uuid> --server=<uuid>      (8.5.4+, КОРП; параметры — по rac help server ⚠)
```

Сверено со справкой `rac help server` 8.3.1x: у `insert` обязательны `--agent-host`, `--agent-port` и `--port-range`; параметры `--agent-host`, `--agent-port`, `--name` и `--cluster-port` есть только у `insert` — командой `update` их не поменять (сервер с другим именем или портом агента регистрируют заново). Проверьте по `rac help server` своей версии, не расширился ли состав параметров `update`.

| Параметр `rac` | Свойство в консоли | Смысл | Значения, умолчания |
|---|---|---|---|
| `--agent-host=<хост>` | Компьютер | Адрес рабочего сервера, где запущен агент | Только `insert`. Пишите имя так же, как оно записано в остальных местах кластера |
| `--agent-port=<порт>` | IP порт | Порт агента на этом компьютере | Только `insert`. По умолчанию `1540` |
| `--port-range=<мин>:<макс>` | Диапазоны IP портов | Порты для рабочих процессов и дополнительных менеджеров | По умолчанию `1560:1591`. Можно несколько диапазонов |
| `--name=<имя>` | Описание | Произвольное описание сервера | — |
| `--using=main\|normal` | Центральный сервер | `main` — с сервером синхронизируется реестр кластера, его адрес годится клиентам для подключения | Последний центральный сервер удалить нельзя |
| `--cluster-port=<порт>` | Порт главного менеджера кластера | Порт главного менеджера на этом сервере | Учитывается только для центрального сервера. Обычно `1541` |
| `--dedicate-managers=all\|none` | Менеджер под каждый сервис | `all` — отдельный `rmngr` под каждый тип сервиса, `none` — все сервисы в одном менеджере | Каждый дополнительный менеджер занимает порт из диапазона |
| `--infobases-limit=<n>` | Количество ИБ на процесс | Сколько баз обслуживает один рабочий процесс | `0` — без ограничения. КОРП. Умолчание `8` [офиц., документация: таблица различий ПРОФ и КОРП] |
| `--connections-limit=<n>` | Количество соединений на процесс | Сколько соединений обслуживает один рабочий процесс | `0` — без ограничения. Умолчание для нового рабочего сервера — `256` начиная с 8.3.15; до 8.3.15 предлагалось `128` [офиц., V8Update 8.3.15]. У серверов, созданных старыми версиями, остаётся прежнее значение — проверьте `rac server info`. Число `128` в библиотеке irac — её собственное значение, а не умолчание платформы |
| `--temporary-allowed-total-memory=<байты>` | Временно допустимый объём памяти процессов | Суммарная память `rphost` и `rmngr`, при превышении которой на сервер перестают назначаться новые соединения | С 8.3.15. `0` — 80% ОЗУ (умолчание), `-1` — не ограничено |
| `--temporary-allowed-total-memory-time-limit=<сек>` | Интервал превышения допустимого объёма памяти | Сколько можно превышать временно допустимый объём | С 8.3.15. По умолчанию `300`. По истечении самые «тяжёлые» процессы перезапускаются неаварийно |
| `--critical-total-memory=<байты>` | Критический объём памяти процессов | Суммарная память, при превышении которой процессы завершаются аварийно и запускаются заново | С 8.3.15. `0` — 95% ОЗУ (умолчание), `-1` — не ограничено |
| `--safe-call-memory-limit=<байты>` | Безопасный расход памяти за один вызов | Расход памяти одним серверным вызовом, который не приводит к прерыванию вызова при превышении временно допустимого объёма | КОРП. `0` — 10% от временно допустимого объёма; `-1` — любой вызов прерывается при превышении |
| `--service-principal-name=<spn>` | Имя службы (SPN) сервера | SPN для ограниченного делегирования Kerberos | С 8.3.19. Нужно кластеру под Windows. Свойство «Имя службы (SPN)» рабочего сервера описано в ИТС-КС разд. 5.2.6.1. Имя ключа `rac` и версия появления документацией 8.3.27 не подтверждаются ⚠ (19.10.2026) — сверять с `rac server help` |
| `--restart-schedule=<cron>` | Расписание перезапуска | Расписание перезапуска процессов этого сервера | С 8.3.27. Приоритетнее расписания кластера |
| `--add-prohibiting-assignment-rule=…` | Установить запрещающее требование назначения функциональности | Создать сервер «закрытым»: сразу добавляется и применяется требование «любой объект — не назначать», приоритет 0 | С 8.3.25 (имя параметра подтверждено: V8Update 8.3.25), только при создании. ⚠ не подтверждено: это флаг без значения или параметр вида `=yes\|no` — сверить по `rac help server` |
| `--safe-working-processes-memory-limit=<байты>` | (старое) Максимальный объём памяти рабочих процессов | Порог памяти рабочих процессов до 8.3.15 | Свойство удалено из параметров рабочего сервера в 8.3.15, значение сохраняется в реестре только для совместимости [офиц., V8Update 8.3.15]; управление памятью — тремя параметрами выше |
| `--memory-limit=<КБ>` | (старое) предел использования памяти рабочими процессами | Объём памяти рабочих процессов, до которого сервер считался производительным (до 8.3.15) | Свойство удалено в 8.3.15 вместе с предыдущим [офиц., V8Update 8.3.15]. В текущих версиях не используйте |

Как работает контроль памяти [офиц.]:

- «Память процесса» на Linux — это `VmRSS + VmSwap`. С порогами сравнивается сумма по всем `rphost` и `rmngr` сервера.
- Превышен временно допустимый объём — новые соединения на сервер не назначаются; если превышение держится дольше интервала, процессы мягко перезапускаются, начиная с самого большого.
- Превышен критический объём — процессы завершаются аварийно (начиная с самого большого) и запускаются заново; в технологический журнал пишется событие `ATTN`.
- Контроль отдельного вызова: в начале вызова вычисляется предел «временно допустимый объём − текущая память процессов» (но не меньше безопасного расхода за вызов). Если вызов израсходовал больше — он прерывается исключением, в технологическом журнале появляется `EXCP`.
- При лицензии ПРОФ пороги влияют только на перезапуск процессов; прерывание вызовов по памяти — только КОРП [офиц., V8Update 8.3.15].

Рекомендации по значениям:

| Ситуация | Что задать | Источник |
|---|---|---|
| Сервер 1С на отдельной машине | Оставить умолчания: `0` в обоих порогах памяти (то есть 80% и 95% ОЗУ) и интервал превышения 300 с | [офиц.] умолчания |
| Сколько соединений и баз на процесс | Без технического обоснования не уменьшать умолчания (256 соединений, 8 баз на процесс) и не доводить число `rphost` до десятков | [офиц.] методические материалы ИТС (чек-лист и инструкция по настройке рабочих серверов) |
| 1С и PostgreSQL на одной машине | Задать пороги явно в байтах, чтобы 1С не вытеснял СУБД: временно допустимый ≈ ОЗУ − (`shared_buffers` + запас под сеансы PostgreSQL и ОС); критический — на 10–20% выше | [практика] |
| Базы должны быть изолированы друг от друга | `--infobases-limit=1`: под каждую базу отдельный `rphost` | [офиц.] пример документации |
| Мало портов в сетевом экране | Не включать `--dedicate-managers=all`: каждый менеджер занимает порт, а сервисов больше тридцати | [офиц.] по смыслу свойства |
| Нужен ночной перезапуск | `--restart-schedule="0 3 * * *"` у кластера (8.3.27+) | [офиц.] |

```bash
SRV=$(rac server list --cluster=$CL $AUTH | awk '$1=="server"{print $3; exit}')
rac server info --cluster=$CL --server=$SRV $AUTH

# машина 32 ГБ, на ней же PostgreSQL: временно допустимый 12 ГБ, критический 16 ГБ
rac server update --cluster=$CL --server=$SRV $AUTH \
    --temporary-allowed-total-memory=$((12*1024**3)) \
    --critical-total-memory=$((16*1024**3)) \
    --temporary-allowed-total-memory-time-limit=300

# расширить диапазон портов (и не забыть про ufw)
rac server update --cluster=$CL --server=$SRV $AUTH --port-range=1560:1691

# второй рабочий сервер (обычный, не центральный)
rac server insert --cluster=$CL $AUTH --agent-host=srv1c-2 --agent-port=1540 \
    --port-range=1560:1591 --name="Второй рабочий сервер" --using=normal
# вывод: server : <uuid нового сервера>

# чтобы новый сервер сразу не получил нагрузку (8.3.25+), добавьте к команде выше
# параметр --add-prohibiting-assignment-rule (⚠ форму записи значения уточните: rac help server),
# либо сразу после создания закройте сервер требованием — сценарий 5 в разделе 5.10
```

Временный вывод рабочего сервера из работы (8.5.4+) [офиц., V8Update 8.5.4]: команды `rac server disable` и `rac server enable` выключают и включают рабочий сервер на время обслуживания. Возможность есть только в отказоустойчивом кластере и требует лицензию КОРП; сервер нельзя выключить, если с него не удаётся перенести работающие сервисы и пользователей. В выводе `rac server info` появились поля `enabled` и `status`. До 8.5.4 (и без КОРП) сервер «закрывают» требованием назначения — см. ниже.

Безопасное исключение сервера из кластера [офиц.]: добавить этому серверу первым по порядку требование «любой объект требования — не назначать» (`rac rule … insert --position=0 --rule-type=never`), применить требования, дождаться разрыва соединений, затем `rac server remove`.

### 5.4. Режим process (рабочие процессы)

```text
rac process list --cluster=<uuid> [--server=<uuid>] [--licenses]
rac process info --cluster=<uuid> --process=<uuid> [--licenses]
```

Создавать и удалять рабочие процессы вручную нельзя — их число определяет кластер. Процесс можно только выключить: в консоли это команда «Выключить», в `rac` возможность появилась в 8.3.27. В заметках о выпуске 8.3.27 она записана дословно так: «Для режима process реализована команда `--turn-off`»; там же названы метод COM-соединения `IServerAgentConnection.TurnOffWorkingProcess()`, метод Java-интерфейса `turnOffWorkingProcess()` и метод встроенного языка `АдминистрированиеРабочийПроцесс.Выключить()` [офиц., V8Update 8.3.27]. ⚠ не подтверждено: полная форма команды `rac` (скорее всего `rac process --cluster=<uuid> … --process=<uuid>` с `--turn-off` либо отдельная команда) — смотрите `rac help process` на версии 8.3.27+ и не подбирайте её на рабочем сервере наугад. Выключение идёт по той же схеме, что и перезапуск по расписанию (5.1): процесс доживает, пока его соединения не переданы новому процессу или не истёк `--expiration-timeout`.

Справка 8.3.1x для режима `process` содержит только `list` (необязательный `--server`, флаг `--licenses`) и `info` (обязательный `--process`, флаг `--licenses`).

Поля `process list` и `process info`:

| Поле | Свойство в консоли | Смысл и единицы |
|---|---|---|
| `process` | — | UUID рабочего процесса в кластере |
| `host` | Компьютер | Рабочий сервер, на котором работает процесс |
| `port` | IP порт | Порт процесса; выделяется из диапазона портов сервера при запуске |
| `pid` | PID процесса ОС | PID `rphost` — по нему ищут процесс в `ps`, `top`, `/proc` |
| `is-enable` | Включён | Процесс включён и может использоваться. В 8.3.27 свойство COM-объекта `IWorkingProcessInfo.IsEnable` объявлено устаревшим, вместо него введено `TurnedOn` (английское имя свойства встроенного языка изменено с `Enable` на `TurnedOn`) [офиц., V8Update 8.3.27]. ⚠ не подтверждено: как поле называется в выводе `rac` 8.3.27+ — `is-enable`, `turned-on` или оба; в скриптах проверяйте оба имени |
| `running` | Активен | Процесс сейчас запущен и используется |
| `started-at` | Время запуска | Момент последнего запуска |
| `use` | — | Использование процесса: `used` — используется; встречаются также значения для неиспользуемого и резервного процесса ⚠ |
| `reserve` | Резервный | Признак резервного рабочего процесса (с 8.3.16) |
| `available-perfomance` | Доступная производительность | 10 000, делённое на среднее за 5 минут время эталонных операций. Чем больше, тем свободнее процесс. Имя поля в выводе написано именно так, с опечаткой |
| `capacity` | — | Относительная производительность процесса, от 1 до 1000 (наследие ранних версий) |
| `connections` | Соединений | Текущее число соединений процесса |
| `memory-size` | Занято памяти | Память процесса в килобайтах |
| `memory-excess-time` | — | Сколько секунд процесс превышает порог памяти |
| `selection-size` | — | Число вызовов, по которым посчитана статистика |
| `avg-call-time` | Реакция сервера | Среднее время обслуживания одного обращения, секунды. Равно сумме трёх следующих |
| `avg-server-call-time` | Затрачено сервером | Среднее время, которое тратит сам рабочий процесс |
| `avg-db-call-time` | Затрачено СУБД | Среднее время обращений к СУБД |
| `avg-lock-call-time` | Затрачено менеджером блокировок | Среднее время обращений к менеджеру блокировок |
| `avg-back-call-time` | Затрачено клиентом | Среднее время обратных вызовов к клиенту |

С флагом `--licenses` выводятся лицензии, выданные процессом: `process`, `host`, `port`, `pid`, `full-name` (полное имя файла лицензии или ключа), `series` (серия), `issued-by-server` (`yes`/`no` — выдана сервером), `license-type` (тип: `soft` — программная лицензия, `HASP` — аппаратный ключ), `net` (`yes`/`no` — сетевая), `max-users-all` (всего пользователей в лицензии), `max-users-cur` (занято сейчас), `rmngr-address`, `rmngr-port`, `rmngr-pid` (менеджер, выдавший лицензию), `short-presentation`, `full-presentation` (текстовые представления).

```bash
rac process list --cluster=$CL $AUTH | rac_table host port pid connections memory-size available-perfomance \
  | column -t -s$'\t'

# сверить память rphost с данными ОС
ps -o pid,rss,vsz,etime,cmd -C rphost

# серверные лицензии
rac process list --cluster=$CL $AUTH --licenses
```

### 5.5. Режим service

```text
rac service list --cluster=<uuid>
```

Поля: `name` — идентификатор сервиса (например `LicenseService`, `SessionDataService`, `EventLogService`), `main-only` — сервис работает только на центральном сервере, `manager` — UUID менеджера (или менеджеров), где размещён сервис, `descr` — описание. Идентификаторы из поля `name` используются как тип объекта в требованиях назначения (5.10). Набор полей (`name`, `main-only`, `manager`, `descr`) сверен со справкой `rac help service` 8.3.1x.

С 8.5.4 сервисы кластера идентифицируются не именем, а типом: в выводе `rac service list` появилось поле `type` с идентификатором сервиса, и именно его принимают новые параметры `--service` (у `rac rule insert` и у команд настроек сервисов). Причина изменения, названная в заметках о выпуске, — проблемы при переименовании сервисов [офиц., V8Update 8.5.4].

```bash
# какие сервисы есть в кластере и на каких менеджерах они размещены
rac service list --cluster=$CL $AUTH | rac_table name main-only manager | column -t -s$'\t'
```

### 5.6. Режим infobase (информационные базы)

```text
rac infobase summary list   --cluster=<uuid>
rac infobase summary info   --cluster=<uuid> --infobase=<uuid>
rac infobase summary update --cluster=<uuid> --infobase=<uuid> --descr=<описание>
rac infobase info   --cluster=<uuid> --infobase=<uuid> [--infobase-user=… --infobase-pwd=…]

                    --db-name=<имя БД> --locale=<код> [прочие параметры]
rac infobase update --cluster=<uuid> --infobase=<uuid> [--infobase-user=… --infobase-pwd=…] [параметры]
```

`summary` — краткие сведения (`infobase`, `name`, `descr`), для них не нужен администратор базы. `info`, `update`, `drop` требуют имя и пароль администратора базы, если в базе есть пользователи.

| `--minimum-scheduled-jobs-start-period-without-active-users=<сек>` | U | Минимальный период запуска регламентных заданий в базе без активных сеансов | С 8.3.25 |
| `--maximum-scheduled-jobs-start-shift-without-active-users=<сек>` | U | Максимальный случайный сдвиг запуска заданий (работает, только если минимальный период не 0) | С 8.3.25 |
| `--drop-database` | drop | Удалить и базу данных на сервере СУБД | Если в базе есть соединения, регистрация удалится, а СУБД вернёт ошибку и базу не удалит [офиц.] |
| `--clear-database` | drop | Очистить базу данных (пустая база останется на сервере СУБД) | Без обоих флагов удаляется только регистрация в кластере |

Поведение при регистрации базы [офиц.]: если в указанной базе данных уже есть данные 1С — кластер подключает её; если база пустая — создаёт в ней новую информационную базу; `--create-database` дополнительно создаёт саму базу данных на сервере СУБД.

Поведение блокировки начала сеансов [офиц.]: существующие сеансы продолжают работать и могут запускать фоновые задания; новые сеансы и новые соединения запрещены. Пользователей нужно выгонять отдельно (5.8). Текст сообщения может быть форматированной строкой.

Параметры трёх последних «…without-active-users» относятся к базам без активных пользователей («пассивным»): кластер прореживает запуск регламентных заданий и дольше держит загруженную конфигурацию, чтобы не тратить ресурсы на редко используемые базы [офиц., V8Update 8.3.25].

Что сверено со справкой `rac help infobase` 8.3.1x. У `create` обязательны `--name`, `--dbms`, `--db-server`, `--db-name`, `--locale`; кроме них принимаются `--create-database`, `--db-user`, `--db-pwd`, `--descr`, `--date-offset`, `--security-level`, `--scheduled-jobs-deny=on|off`, `--license-distribution=deny|allow`. Блокировку сеансов (`--sessions-deny`, `--denied-*`, `--permission-code`), внешнее управление сеансами и профили безопасности в этих версиях можно задать только командой `update` — то есть создать базу сразу закрытой для входа нельзя, нужно два вызова. У `drop` — `--infobase`, `--infobase-user`, `--infobase-pwd`, `--drop-database`, `--clear-database`.

Изменения 8.5.4 [офиц., V8Update 8.5.4]:

- `rac infobase create` принимает все параметры информационной базы, как `rac infobase update` (раньше после создания приходилось отдельно вызывать `update`); полный перечень — во встроенной справке;
- вывод `rac infobase info` дополнен именем, версией и поставщиком конфигурации (имена полей в заметках о выпуске не приведены ⚠; в COM-объекте это `ConfigName`, `ConfigVersion`, `ConfigVendor`);
- у `infobase info`, `infobase summary list`, `infobase summary info` появился `--get-data-version`, у `infobase update` и `infobase summary update` — `--data-version` (раздел 9.1).

```bash
# создать базу и базу данных PostgreSQL (сервер СУБД на этой же машине)
rac infobase create --cluster=$CL $AUTH --create-database \
    --name=demo --descr="Демонстрационная база" \
    --dbms=PostgreSQL --db-server=localhost --db-name=demo \
    --db-user=postgres --db-pwd="$PG_PWD" --locale=ru_RU \
    --scheduled-jobs-deny=on --license-distribution=allow
# вывод: infobase : <uuid новой базы>

# подключить уже существующую базу данных
rac infobase create --cluster=$CL $AUTH --name=buh --dbms=PostgreSQL --db-server=localhost \
    --db-name=buh --db-user=postgres --db-pwd="$PG_PWD" --locale=ru_RU --license-distribution=allow

# PostgreSQL на другом сервере и на нестандартном порту (формат «<имя> port=<номер>;»)
rac infobase create --cluster=$CL $AUTH --name=zup --dbms=PostgreSQL --db-server="pg-host port=5433;" \
    --db-name=zup --db-user=usr1cv8 --db-pwd="$PG_PWD" --locale=ru_RU --license-distribution=allow

# перевести существующую базу на другой адрес СУБД (после переноса PostgreSQL)
rac infobase update --cluster=$CL --infobase=$IB $AUTH --infobase-user="Администратор" \
    --infobase-pwd="$IB_PWD" --db-server="new-pg-host port=5432;"

# полные свойства
rac infobase info --cluster=$CL --infobase=$IB $AUTH --infobase-user="Администратор" --infobase-pwd="$IB_PWD"

# сменить пароль пользователя СУБД в свойствах базы (после смены пароля в PostgreSQL)
rac infobase update --cluster=$CL --infobase=$IB $AUTH --infobase-user="Администратор" \
    --infobase-pwd="$IB_PWD" --db-pwd="$NEW_PG_PWD"

# включить регламентные задания
rac infobase update --cluster=$CL --infobase=$IB $AUTH --infobase-user="Администратор" \
    --infobase-pwd="$IB_PWD" --scheduled-jobs-deny=off

# удалить только регистрацию (база данных остаётся)
rac infobase drop --cluster=$CL --infobase=$IB $AUTH --infobase-user="Администратор" --infobase-pwd="$IB_PWD"
```

### 5.7. Режим connection (соединения)

```text
rac connection list       --cluster=<uuid> [--process=<uuid>] [--infobase=<uuid>]
                          [--infobase-user=… --infobase-pwd=…]
rac connection info       --cluster=<uuid> --connection=<uuid>
rac connection disconnect --cluster=<uuid> --process=<uuid> --connection=<uuid>
                          [--infobase-user=… --infobase-pwd=…]
```

Соединение — канал доступа к кластеру, а не «пользователь». Сеанс тонкого и веб-клиента назначается соединению только на время обращения, поэтому соединений обычно меньше, чем сеансов [офиц.].

Основные поля (есть всегда):

| Поле | Свойство в консоли | Смысл |
|---|---|---|
| `connection` | — | UUID соединения |
| `conn-id` | Соединение | Номер соединения. `0` — служебное соединение, не связанное с базой. Нумерация базы начинается с 1 заново только после отключения всех клиентов, включая фоновые задания |
| `host` | Компьютер | Имя компьютера, установившего соединение |
| `process` | — | UUID рабочего процесса, который обслуживает соединение |
| `infobase` | Инф. база | UUID базы; нули — служебное соединение |
| `application` | Приложение | Идентификатор приложения (таблица ниже) |
| `connected-at` | Начало работы | Момент установки соединения |
| `session-number` | Сеанс | Номер сеанса, назначенного соединению; `0` — сеанс не назначен |
| `blocked-by-ls` | Заблокировано | Номер соединения (сеанса), из-за которого соединение ждёт транзакционную блокировку; `0` — не ждёт |

Девять основных полей и состав команд (`info --connection`; `list` с необязательными `--process`, `--infobase`, `--infobase-user`, `--infobase-pwd`; `disconnect` с обязательными `--process` и `--connection`) сверены со справкой `rac help connection` 8.3.1x.

Изменение 8.5.4 [офиц., V8Update 8.5.4]: у команд семейства `rac connection` (и `rac binary-data-storage`) параметры `--infobase-user` и `--infobase-pwd` удалены — учётные данные пользователя информационной базы для них больше не нужны, достаточно администратора кластера. Скрипт, который передаёт эти параметры, на 8.5.4 нужно поправить; чтобы один скрипт работал на обеих версиях, выбирайте набор параметров по `rac --version`.

Расширенные поля появляются для соединений конкретной базы (список с `--process` и `--infobase`; до 8.5.4 — ещё и с аутентификацией администратора базы). Набор взят из описания свойств в библиотеке irac (файл `ТипыОбъектовКластера.json`) и из документации консоли; в справке `rac` 8.3.1x эти поля не перечислены ⚠ — на своей версии проверьте фактический вывод:

| Поле | Свойство в консоли | Смысл и единицы |
|---|---|---|
| `thread-mode` | — | Режим потока |
| `ib-conn-mode` | ИБ монопольно | Режим соединения с информационной базой: `shared` или `exclusive` |
| `db-conn-mode` | База данных / Монопольно | Режим соединения с базой данных: `none`, `shared`, `exclusive` |
| `blocked-by-dbms` | Заблокировано СУБД | Идентификатор процесса СУБД, который блокирует это соединение |
| `db-proc-info` | Соединение с СУБД | Идентификатор процесса сервера баз данных; виден, пока идёт обращение к СУБД |

| Идентификатор | Что это |
|---|---|

Разрыв соединения (`disconnect`) [офиц.]:

- Если клиент выполняет код на сервере 1С — сервер пытается разорвать соединение; пользователь получает сообщение «Сеанс работы завершен администратором». Нужны права администратора кластера и администратора базы.
- Если соединение занято запросом к **PostgreSQL** — команда не выполняет никаких действий. Разрыв длительного запроса поддержан только для MS SQL Server, IBM Db2 и Oracle Database.
- Соединение нельзя разорвать, пока исполнение «стоит» внутри одной строки встроенного языка (долгий HTTP-вызов, вызов внешней компоненты).
- Служебные соединения (`JobScheduler`, `SrvrConsole`, `RAS`) принудительно не разрываются.

Для PostgreSQL зависший запрос снимают на стороне СУБД [практика]: значение `db-proc-info` сеанса — это идентификатор серверного процесса PostgreSQL (`pid` в `pg_stat_activity`).

```bash
sudo -u postgres psql -c "SELECT pid, state, now()-query_start AS dur, left(query,80) FROM pg_stat_activity WHERE pid = 12345;"
sudo -u postgres psql -c "SELECT pg_cancel_backend(12345);"      # отменить текущий запрос
sudo -u postgres psql -c "SELECT pg_terminate_backend(12345);"   # завершить соединение целиком
```

### 5.8. Режим session (сеансы)

```text
rac session list  --cluster=<uuid> [--infobase=<uuid>] [--licenses]
rac session info  --cluster=<uuid> --session=<uuid> [--licenses]
rac session terminate --cluster=<uuid> --session=<uuid> [--error-message=<текст>]
rac session interrupt-current-server-call --cluster=<uuid> --session=<uuid> [--error-message=<текст>]
```

Что подтверждено и чем:

- `list` (необязательные `--infobase`, `--licenses`), `info` (`--session`, `--licenses`) и `terminate --session=<uuid>` — справка `rac help session` 8.3.1x (сохранена в репозитории irac). В этой старой справке у `terminate` нет `--error-message` и нет команды `interrupt-current-server-call`.
- Сами операции сервер администрирования поддерживает: в открытом описании протокола `ras` (`v8platform/protos`) запрос завершения сеанса `TerminateSessionRequest` имеет поле `message` (текст для пользователя), а среди типов сообщений есть `INTERRUPT_SESSION_CURRENT_SERVER_CALL_REQUEST` (прерывание текущего серверного вызова сеанса); в клиенте `khorevaa/ras-client` функция `TerminateSession` принимает строку сообщения [практика].
- Имена `interrupt-current-server-call` и `--error-message` документированы для режима `session` утилиты `ibcmd` (документация 8.3.27) [офиц.]; в консоли кластера обе операции есть и обе предлагают ввести текст сообщения [офиц.].
- ⚠ не подтверждено: что в `rac` команда и параметр называются именно так же, и с какой версии они есть. В заметках о выпуске 8.3.9–8.3.27 и 8.5.4 строки об их добавлении в `rac` нет. Проверка на своей версии: `rac help session | grep -E -A3 'interrupt|error-message'`. Если параметра нет — вызывайте `terminate` без `--error-message` (скрипт 6.4 это учитывает).

Поведение [офиц.]:

- `terminate` (в консоли «Удалить сеанс») сначала прерывает текущий серверный вызов, затем удаляет сеанс. Если сеанс назначен соединению — делается попытка разорвать соединение.
- `interrupt-current-server-call` прерывает только выполняющийся вызов; сеанс остаётся. Работает для тонкого, веб- и мобильного клиента, срабатывает при переходе на следующую строку кода.
- Текст из `--error-message` увидит пользователь. Без текста — стандартное «Выполнение текущей операции прервано администратором».
- Если в удаляемом сеансе не было серверного вызова, он удаляется молча, а при следующем действии пользователь получит «Сеанс отсутствует или удален».
- Возможна потеря несохранённых данных пользователя. Нужны права администратора кластера.

Все поля `session list` и `session info`:

| Поле | Свойство в консоли | Смысл и единицы |
|---|---|---|
| `session` | — | UUID сеанса (нужен для `terminate`) |
| `session-id` | Номер сеанса | Номер сеанса в базе — тот же, что в журнале регистрации и технологическом журнале |
| `infobase` | Информационная база | UUID базы |
| `connection` | Соединение | UUID соединения, которому сейчас назначен сеанс; нули — не назначен |
| `process` | Процесс ОС, Порт | UUID рабочего процесса, обслуживающего сеанс; нули — не назначен |
| `user-name` | Пользователь | Имя пользователя базы; пусто — база без пользователей |
| `host` | Компьютер | Имя компьютера клиента. Пусто у веб-клиента, тонкого клиента через веб-сервер и Web-сервисов |
| `app-id` | Приложение | Идентификатор приложения (таблица в 5.7) |
| `locale` | Язык | Язык интерфейса, например `ru_RU` |
| `started-at` | Время начала | Когда создан сеанс |
| `last-active-at` | Последняя активность | Время последней активности |
| `hibernate` | Спящий | `yes` — сеанс спит (клиент давно не обращался); спящий сеанс освобождает клиентскую лицензию |
| `passive-session-hibernate-time` | Заснуть через | Через сколько секунд неактивный сеанс станет спящим. По умолчанию 1200 |
| `hibernate-session-terminate-time` | Завершить через | Через сколько секунд спящий сеанс будет завершён. ⚠ умолчание в практике 86400 |
| `blocked-by-dbms` | Заблокировано СУБД | Номер сеанса, чья транзакция держит блокировку СУБД, которую ждёт этот сеанс. `0` — не ждёт |
| `blocked-by-ls` | Заблокировано упр. | Номер сеанса, удерживающего управляемую транзакционную блокировку, которую ждёт этот сеанс. `0` — не ждёт |
| `bytes-all`, `bytes-last-5min` | Объём данных (всего, 5 мин) | Передано и получено между клиентом и сервером, байты |
| `calls-all`, `calls-last-5min` | Количество вызовов | Число завершённых серверных вызовов |
| `dbms-bytes-all`, `dbms-bytes-last-5min` | Данных СУБД | Обмен между сервером 1С и сервером БД, байты |
| `db-proc-info` | Соединение с СУБД | Идентификатор процесса сервера баз данных. Виден, только пока соединение с БД захвачено сеансом: идёт запрос, открыта транзакция или удерживаются временные таблицы |
| `db-proc-took` | Захвачено СУБД | Сколько времени сеанс удерживает соединение с БД (мс ⚠) |

| `duration-current` | Время вызовов (текущее) | Длительность текущего незавершённого серверного вызова. `0` — сеанс сейчас ничего не выполняет |
| `duration-current-dbms` | Время вызова СУБД (текущее) | Время обращений к СУБД внутри текущего вызова |

| `memory-current` | Память (текущая) | Разность занятой и освобождённой памяти в текущем вызове, байты. Может быть отрицательной |
| `memory-last-5min`, `memory-total` | Память (5 мин, всего) | Та же разность за 5 минут и с начала сеанса, байты |
| `read-current`, `read-last-5min`, `read-total` | Чтение | Прочитано с диска, байты |
| `write-current`, `write-last-5min`, `write-total` | Запись | Записано на диск, байты |
| `duration-current-service` | Время вызовов сервисов (текущее) | Время работы сервиса кластера в текущем вызове (с 8.3.12) |
| `current-service-name` | Текущий сервис | Имя выполняющегося сервиса кластера; пусто — сервис не вызывается |
| `duration-last-5min-service`, `duration-all-service` | Время вызовов сервисов | То же за 5 минут и с начала сеанса |
| `cpu-time-current` | Процессорное время (текущее) | Процессорное время текущего вызова (с 8.3.13) |
| `cpu-time-last-5min`, `cpu-time-total` | Процессорное время (5 мин, всего) | То же за 5 минут и с начала сеанса. В заметках о выпуске 8.3.13 поле названо `cpu-time-5min-last` |
| `data-separation` | — | Значения разделителей области данных (как в параметре `/Z`) |
| `client-ip` | IP клиента | IP-адрес клиента (с 8.3.17). Через веб-сервер — из заголовков; за обратным прокси нужен `X-Forwarded-For`. У фоновых заданий пусто |

Единицы времени. Консоль показывает времена в секундах (процессорное — с тремя знаками после запятой). `rac` выводит «сырое» значение свойства: по описаниям свойств и счётчиков потребления ресурсов это миллисекунды [офиц. для счётчиков; для полей `rac` ⚠]. Проверка на своём сервере: запустите заведомо долгую операцию и сравните `duration-current` с часами.

С флагом `--licenses` вместо показателей выводятся сведения о клиентской лицензии сеанса: `session`, `user-name`, `host`, `app-id`, `full-name`, `series`, `issued-by-server`, `license-type`, `net`, `max-users-all`, `max-users-cur`, `rmngr-address`, `rmngr-port`, `rmngr-pid`, `short-presentation`, `full-presentation` (смысл — как у лицензий процесса в 5.4).

```bash
rac session list --cluster=$CL $AUTH --infobase=$IB \
  | rac_table session-id user-name app-id host started-at hibernate | column -t -s$'\t'

# SID — значение поля session нужного сеанса
rac session terminate --cluster=$CL $AUTH --session="$SID" \
    --error-message="Сеанс завершён администратором: обновление базы"

rac session list --cluster=$CL $AUTH --licenses | rac_table user-name app-id short-presentation
```

### 5.9. Режим lock (блокировки)

```text
rac lock list --cluster=<uuid> [--infobase=<uuid>] [--connection=<uuid>] [--session=<uuid>]
```

Поля: `connection` (UUID соединения-источника), `session` (UUID сеанса-источника; нули — блокировку держит соединение без сеанса или серверный процесс), `object` (UUID заблокированного объекта, если есть), `locked` (момент установки), `descr` (представление вида блокировки и её параметров).

Виды блокировок в представлении [офиц.]: «БД» — блокировка базы данных (разделяемая или исключительная), «ИБ» — блокировка информационной базы, «Конфигуратор» — исключительная блокировка конфигуратора, «Объект БД» — пессимистическая блокировка объекта, «Менеджер кластера» и «Рабочий процесс» — активность процессов кластера, «Соединение» — соединение с рабочим процессом или регламентное задание. Ожидания на транзакционных блокировках в этом списке не видны — их показывают поля `blocked-by-ls` и `blocked-by-dbms` у сеансов.

```bash
rac lock list --cluster=$CL $AUTH --infobase=$IB | rac_table locked descr
```

### 5.10. Режим rule (требования назначения функциональности)

Требование назначения функциональности (ТНФ) создаётся для конкретного рабочего сервера и говорит, может ли этот сервер обслуживать некоторый объект: клиентские соединения, сервис кластера или «любой объект». Требования действуют только после применения [офиц.].

```text
rac rule list   --cluster=<uuid> --server=<uuid>
rac rule info   --cluster=<uuid> --server=<uuid> --rule=<uuid>
rac rule insert --cluster=<uuid> --server=<uuid> --position=<n> [--object-type=<id>]
                [--infobase-name=<имя>] [--rule-type=auto|always|never]
                [--application-ext=<значение>] [--priority=<n>]
rac rule update --cluster=<uuid> --server=<uuid> --rule=<uuid> --position=<n> [те же параметры]
rac rule remove --cluster=<uuid> --server=<uuid> --rule=<uuid>
rac rule apply  --cluster=<uuid> [--full | --partial]
```

| Параметр | Поле в консоли | Смысл |
|---|---|---|
| `--server=<uuid>` | — | Рабочий сервер, которому принадлежит требование |
| `--position=<n>` | Номер | Место в списке требований сервера, счёт с 0. Требования просматриваются по порядку; чем меньше номер, тем выше приоритет |
| `--object-type=<id>` | Объект требования | Идентификатор объекта (таблица ниже). Не указан — «Любой объект требования» |
| `--infobase-name=<имя>` | Имя ИБ | Требование относится только к этой базе. Не указано — ко всем. Регистр не различается. К сервису лицензирования не применимо |
| `--rule-type=auto\|always\|never` | Тип требования | `always` — «Назначать»: сервер становится кандидатом. `never` — «Не назначать». `auto` — «Авто» (по умолчанию): сервер используется, если нет серверов с явным «Назначать» |
| `--application-ext=<значение>` | Значение дополнительного параметра | Уточнение для клиентских соединений, сервиса сеансовых данных и Дата акселератора |
| `--priority=<n>` | Приоритет | Числовой приоритет требования; при размещении сервисов из работоспособных серверов отбираются серверы с максимальным приоритетом |
| `apply --partial` | Применить (частичное) | Переназначаются сервисы, которые переносятся без потери данных; остальные — только если по новым требованиям не могут остаться на месте |
| `apply --full` | Применить (полное) | Переназначаются все сервисы; могут аварийно завершиться все клиентские приложения кластера. Режим по умолчанию |

Типы объектов требований (`--object-type`). Идентификаторы совпадают с именами сервисов из `rac service list`:

| Идентификатор | Объект |
|---|---|
| не указан | Любой объект требования |
| `Connection` | Клиентское соединение с информационной базой |
| `LicenseService` | Сервис лицензирования |
| `SessionDataService` | Сервис сеансовых данных |
| `JobService` | Сервис заданий |
| `EventLogService` | Сервис журналов регистрации |
| `FulltextSearchService` | Сервис полнотекстового поиска |
| `DataBaseConfigurationUpdateService` | Сервис обновления конфигурации базы данных |
| `SettingsService` | Сервис пользовательских настроек |
| `TransactionLockService` | Сервис транзакционных блокировок |
| `DataEditLockService` | Сервис блокировок объектов |
| `NumerationService` | Сервис нумерации |
| `TimestampService` | Сервис времени |
| `AuxiliaryService` | Сервис вспомогательных функций кластера |
| `ExternalSessionManagerService` | Сервис внешнего управления сеансами |
| `ExternalDataSourceODBCService`, `ExternalDataSourceXMLAService` | Сервисы работы с внешними источниками данных |
| `OpenID2ProviderContextService` | Сервис провайдера OpenID |
| `SessionReuseService` | Сервис повторного использования сеансов |
| `ClientTestingService` | Сервис тестирования |
| `DataAcceleratorService`, `FullTextSearchServiceV2` и другие сервисы новых версий | Идентификатор `FullTextSearchServiceV2` подтверждён полным текстом документации 8.3.27 (таблица каталогов сервисов, «Клиент-серверный вариант», глава 2; сверено 10.10.2026). Остальное: идентификаторы взяты из документации о каталогах сервисов; для требований сверяйте с `rac service list` своей версии |

Сервисы, которые «не переносятся» (конфигурации кластера, состояния кластера, управления предметами отладки), объектом требования быть не могут — они работают на всех центральных серверах [офиц.].

Значения дополнительного параметра (`--application-ext`) [офиц.]:

| Объект | Значение | Что отбирает |
|---|---|---|
| Клиентское соединение | `Designer`, `1CV8`, `1CV8C`, `1CV8CDirect`, `COMConnection`, `WebServerExtension` | Конфигуратор, толстый клиент, тонкий клиент, тонкий клиент с прямым подключением, COM-соединение, всё, что идёт через веб-сервер |
| Клиентское соединение | `BackgroundJob` | Все фоновые задания (сравнение идёт по словам слева направо) |
| Клиентское соединение | `BackgroundJob.CommonModule.<Модуль>.<Метод>` | Фоновое задание, запущенное из встроенного языка |
| Клиентское соединение | `BackgroundJob.ScheduledJob.<Имя регламентного задания>` | Регламентное задание |
| Клиентское соединение | `BackgroundJob.GenerateReport.<Полное имя объекта>` | Фоновое формирование отчёта |
| Клиентское соединение | `BackgroundJob.FullTextSearchIndexUpdate`, `BackgroundJob.DynamicListSearch…`, `BackgroundJob.InputByString…` | Индексация поиска, поиск в списке, ввод по строке |
| Клиентское соединение | `SystemBackgroundJob.DBConfigUpdate`, `SystemBackgroundJob.RecalcTotals` | Фоновая реструктуризация, пересчёт итогов |
| Клиентское соединение | `UserName.<Имя>` | Соединения указанного пользователя базы (с 8.3.27) |
| Клиентское соединение | `UserAssignmentRuleKey.<Значение>` | Пользователи, у которых заполнено свойство «Ключ требования назначения» (с 8.3.27) |
| Сервис сеансовых данных | `Designer`, `1CV8`, `1CV8C`, `WebClient`, `COMConnection`, `WSConnection`, `HTTPServiceConnection`, `ODataConnection`, `MobileClient`, `BackgroundJob`, `SystemBackgroundJob` | Вид сеанса, данные которого размещаются |
| Дата акселератор | имя копии базы данных | Какая копия обслуживается на сервере |

Правила сравнения: значение — слова через точку; требование совпадает с объектом, если все слова требования равны первым словам параметра объекта («префикс по словам»); пустое значение подходит к любому объекту. В одном требовании — одно значение: списки и шаблоны не поддерживаются.

Как кластер выбирает сервер [офиц.]:

1. У каждого сервера по порядку просматривается его список и берётся первое подходящее требование (по объекту, базе и дополнительному параметру).
2. Серверы с подходящим «Не назначать» исключаются.
3. Если есть серверы с явным «Назначать» — объект обслужит один из них; иначе используются серверы с «Авто» и серверы без требований.
4. Если подходящих серверов не осталось, клиентское приложение завершается с ошибкой.

Лицензии [офиц.]: полный механизм — КОРП. С лицензией ПРОФ требования допустимы, только если у всех требований пусты «Имя ИБ» и «Значение дополнительного параметра» — этого достаточно, чтобы вынести сервис (например, лицензирования) на отдельный сервер.

Типовые сценарии:

```bash
# SRV2 — UUID второго рабочего сервера (поле server в выводе rac server list)
SRV2=$(rac server list --cluster=$CL $AUTH | rac_table server agent-host | awk -F'\t' '$2=="srv1c-2"{print $1}')

# 1) все фоновые и регламентные задания — на второй сервер (КОРП)
rac rule insert --cluster=$CL $AUTH --server=$SRV2 --position=0 \
    --object-type=Connection --rule-type=always --application-ext=BackgroundJob
rac rule apply --cluster=$CL $AUTH --partial

# 2) сервис лицензирования — на выделенный сервер, больше на нём ничего (работает и на ПРОФ)
rac rule insert --cluster=$CL $AUTH --server=$SRV2 --position=0 --object-type=LicenseService --rule-type=always
rac rule insert --cluster=$CL $AUTH --server=$SRV2 --position=1 --rule-type=never
rac rule apply --cluster=$CL $AUTH --partial
#    программная лицензия при этом активируется на имя этого сервера

# 3) базу demo обслуживает только второй сервер (КОРП)
rac rule insert --cluster=$CL $AUTH --server=$SRV2 --position=0 --infobase-name=demo --rule-type=always
rac rule apply --cluster=$CL $AUTH --partial

# 4) сеансы пользователя «Обмен» — на второй сервер (8.3.27+, КОРП)
rac rule insert --cluster=$CL $AUTH --server=$SRV2 --position=0 \
    --object-type=Connection --rule-type=always --application-ext="UserName.Обмен"

# 5) закрыть сервер перед обслуживанием или исключением из кластера
rac rule insert --cluster=$CL $AUTH --server=$SRV2 --position=0 --rule-type=never
rac rule apply --cluster=$CL $AUTH --partial

# посмотреть и удалить
rac rule list --cluster=$CL $AUTH --server=$SRV2
rac rule remove --cluster=$CL $AUTH --server=$SRV2 --rule="$RULE"      # RULE — поле rule из списка
rac rule apply --cluster=$CL $AUTH --partial
```

Пояснение к сценарию 1: значение `BackgroundJob` захватывает все виды фоновых заданий, включая фоновые отчёты и поиск в списках. В примере документации для «всех фоновых заданий» указано `BackgroundJob.CommonModule` — это только задания, запущенные из встроенного языка. Сценарий «одна база — один рабочий процесс» решается не требованием, а свойством сервера `--infobases-limit=1` (5.3).

Поля `rule list`: `rule` (UUID), `object-type`, `infobase-name`, `rule-type`, `application-ext`, `priority`.

### 5.11. Режим profile (профили безопасности)

Профиль безопасности ограничивает серверный код конфигурации: доступ к файловой системе, внешним компонентам, внешним модулям, приложениям ОС, интернету, привилегированному режиму.

```text
rac profile list   --cluster=<uuid>
rac profile update --cluster=<uuid> --name=<имя> [--descr=<текст>] [--config=yes|no] [--priv=yes|no]
                   [--crypto=yes|no] [--right-extension=yes|no]
                   [--right-extension-definition-roles=<роль[;роль…]>]
                   [--all-modules-extension=yes|no]
                   [--modules-available-for-extension=<имя[;имя…]>]
                   [--modules-not-available-for-extension=<имя[;имя…]>]
rac profile remove --cluster=<uuid> --name=<имя>
rac profile acl    --cluster=<uuid> --name=<имя профиля> <вид> list|update|remove [параметры]
```

`update` создаёт профиль, если его нет. `--config` — можно ли использовать профиль как профиль безопасного режима из конфигурации, `--priv` — доступ к привилегированному режиму, `--crypto` — функции криптографии (с 8.3.7), параметры расширений — с 8.3.9. В 8.3.16 добавлены `--privileged-mode-roles` (роли привилегированного режима) и параметр полного доступа к привилегированному режиму (`full-privileged-mode`) [офиц., V8Update 8.3.16].

Списки доступа (`acl`), вид объекта и его параметры:

| Вид | Что ограничивает | Параметры `update` |
|---|---|---|
| `directory` | Каталоги файловой системы сервера | `--alias=<логический URL>` (обяз.), `--descr`, `--physicalPath=<путь>`, `--allowedRead=yes\|no`, `--allowedWrite=yes\|no` |
| `com` | COM-классы (для сервера под Linux смысла не имеет) | `--name` (обяз.), `--descr`, `--fileName`, `--id=<uuid>`, `--host` |
| `addin` | Внешние компоненты | `--name` (обяз.), `--descr`, `--hash=<контрольная сумма base64>` |
| `module` | Внешние модули (внешние обработки и отчёты, расширения) | `--name` (обяз.), `--descr`, `--hash` |
| `app` | Приложения операционной системы | `--name` (обяз.), `--descr`, `--wild=<шаблон строки запуска>` |
| `inet` | Ресурсы интернета | `--name` (обяз.), `--descr`, `--protocol`, `--url`, `--port` (0 — допускается любой порт, по «Клиент-серверному варианту» 8.3.27, 2.2.8.7; сверить с `rac help profile` своей версии) |

Для каждого вида задаётся режим `--access=list|full`: `list` — доступ по списку (пустой список означает запрет), `full` — полный доступ, список игнорируется.

```bash
# профиль «только каталог обмена и ничего больше»
rac profile update --cluster=$CL $AUTH --name=Exchange --descr="Только каталог обмена" --config=no --priv=no
rac profile acl --cluster=$CL $AUTH --name=Exchange directory update \
    --alias=/exchange --physicalPath=/srv/1c/exchange --allowedRead=yes --allowedWrite=yes
rac profile acl --cluster=$CL $AUTH --name=Exchange directory list

# назначить профиль базе
rac infobase update --cluster=$CL --infobase=$IB $AUTH --infobase-user="Администратор" \
    --infobase-pwd="$IB_PWD" --security-profile-name=Exchange
```

⚠ не подтверждено: точное положение `--name` и `--access` относительно вложенных команд `acl` — в справке они показаны после вложенных блоков. Сверьте с `rac help profile`.

### 5.12. Режимы counter и limit (управление потреблением ресурсов)

Только лицензия КОРП, с версии 8.3.13. Счётчик накапливает показатели сеансов, ограничение выполняет действие, когда показатели счётчика превысили пороги [офиц.].

```text
rac counter list   --cluster=<uuid>
rac counter info   --cluster=<uuid> --counter=<имя>
rac counter update --cluster=<uuid> --name=<имя> --collection-time=<число|current-call>
                   --group=users|data-separation --filter-type=all-selected|all-but-selected|all
                   --filter=<отбор> [--duration=analyze|not-analyze] [--cpu-time=…] [--memory=…]
                   [--read=…] [--write=…] [--duration-dbms=…] [--dbms-bytes=…] [--service=…]
                   [--call=…] [--number-of-active-sessions=…] [--number-of-sessions=…] [--descr=<текст>]
rac counter values --cluster=<uuid> --counter=<имя> [--object=<отбор>]
rac counter remove --cluster=<uuid> --name=<имя>

rac limit list   --cluster=<uuid>
rac limit info   --cluster=<uuid> --limit=<имя>
rac limit update --cluster=<uuid> --name=<имя>
                 --action=none|set-low-priority-thread|interrupt-current-call|interrupt-session
                 [--counter=<имя счётчика>] [--duration=<n>] [--cpu-time=<n>] [--memory=<n>] [--read=<n>]
                 [--write=<n>] [--duration-dbms=<n>] [--dbms-bytes=<n>] [--service=<n>] [--call=<n>]
                 [--number-of-active-sessions=<n>] [--number-of-sessions=<n>]
                 [--error-message=<текст>] [--descr=<текст>]
rac limit remove --cluster=<uuid> --name=<имя>
```

| Параметр счётчика | Смысл |
|---|---|
| `--collection-time` | Длительность сбора: `current-call` — по текущему серверному вызову (каждый сеанс — отдельный экземпляр счётчика) либо число — интервал скользящего окна (сеансы суммируются) |
| `--group` | Группировка экземпляров: `users` — по пользователям, `data-separation` — по областям данных. Смена группировки очищает счётчик |
| `--filter` | Отбор сеансов: условия `infobase=`, `user=`, `appID=`, `data-separation=`, `safe-mode=on\|off`, `safe-mode-profile-name=`. Условия через `;` объединяются по «И», группы через `\|` — по «ИЛИ»; сравнение `=` и `<>` (с 8.3.14) |
| `--filter-type` | `all-selected` — только отобранные, `all-but-selected` — все, кроме отобранных, `all` — все |
| `--duration`, `--cpu-time`, `--duration-dbms`, `--service` | Анализировать время вызовов, процессорное время, время СУБД, время сервисов. Единицы — миллисекунды |
| `--memory`, `--read`, `--write`, `--dbms-bytes` | Анализировать память, чтение и запись на диск, обмен с СУБД. Единицы — байты |
| `--call`, `--number-of-active-sessions`, `--number-of-sessions` | Количество вызовов, активных сеансов, сеансов |

Действия ограничения: `none` — только запись в технологический журнал, `set-low-priority-thread` — понизить приоритет потока, `interrupt-current-call` — прервать серверный вызов, `interrupt-session` — прервать вызов и завершить сеанс. Действие выполняется, только когда превышены все заданные пороги сразу; любое срабатывание пишет в технологический журнал событие `ATTN`. У счётчика «за интервал» прерывание блокирует новые вызовы, пока показатели не опустятся ниже порога.

В 8.3.15 в режим `counter` добавлены очистка накопленных значений (`clear`), вывод накопленных значений (в заметках о выпуске команда записана как `accumalated-values` — ⚠ сверить написание по справке) и поле `time` в значениях.

```bash
# счётчик долгих вызовов в базе buh, сначала только наблюдение
rac counter update --cluster=$CL $AUTH --name=long_calls --collection-time=current-call --group=users \
    --filter-type=all-selected --filter="infobase=buh" --duration=analyze --memory=analyze \
    --descr="Долгие серверные вызовы"
rac limit update --cluster=$CL $AUTH --name=watch_long --counter=long_calls --action=none --duration=600000

rac counter values --cluster=$CL $AUTH --counter=long_calls

# после наблюдения — прерывать вызовы дольше 10 минут
rac limit update --cluster=$CL $AUTH --name=watch_long --counter=long_calls \
    --action=interrupt-current-call --duration=600000 \
    --error-message="Операция выполнялась дольше 10 минут и прервана администратором"
```

### 5.13. Режим service-setting (каталоги данных сервисов)

С версии 8.3.26, только КОРП. Настройка сервиса переносит каталог данных сервиса в другое место (например, журнал регистрации — на отдельный диск) [офиц.].

Сервисы, для которых это возможно, и их каталоги по умолчанию (`<sdf>` — каталог данных сервера, на Linux `/home/usr1cv8/.1cv8/1C/1cv8`):

| Сервис | Идентификатор | Путь по умолчанию |
|---|---|---|
| Журналов регистрации | `EventLogService` | `<sdf>/reg_<порт>/<uuid базы>/1Cv8Log` |
| Полнотекстового поиска | `FulltextSearchService` | `<sdf>/reg_<порт>/<uuid базы>/1Cv8FTxt` |
| Полнотекстового поиска, версия 2 | `FullTextSearchServiceV2` | `<sdf>/reg_<порт>/<uuid базы>/1Cv8FTxt2` |
| Сеансовых данных | `SessionDataService` | `<sdf>/reg_<порт>/snccntx…` |
| Хранилища двоичных данных | `BinaryDataStorageService` | `<sdf>/reg_<порт>/BinDataStrg/<uuid базы>` |
| Мониторинга счётчиков потребления ресурсов | `CounterService` | `<sdf>/reg_<порт>/rescntsrv.lst` |
| Управления моделями распознавания речи | `SpeechToTextModelManagementService` | `<sdf>/reg_<порт>/STT` |
| Дата акселератора | `DataAcceleratorService` | каталог `1Cv8DbDA` в `<sdf>` |

Свойства настройки: имя сервиса, каталог данных сервиса, имя базы (для сервисов, которые делятся по базам). Существующую настройку изменить нельзя — её удаляют и создают заново. После создания или удаления настройки нужно выполнить «Применить настройки» для рабочего сервера, а фактически каталоги меняются только при запуске кластера [офиц.].

Порядок переноса [офиц.]: создать настройки → запретить вход пользователей и регламентные задания → завершить фоновые задания и сеансы → применить настройки → остановить кластер → перенести данные вручную → запустить кластер → снять запреты. Для журналов регистрации и хранилища двоичных данных перенос данных обязателен, иначе кластер может стать неработоспособным. Сетевые каталоги не рекомендуются.

⚠ не подтверждено: имена команд и параметров режима `service-setting` в `rac`. По составу методов программного интерфейса (создать настройку, получить список, получить по идентификатору, удалить, применить, получить каталоги данных для переноса) ожидаются команды вида `list`, `info`, `insert`, `remove`, `apply` и команда получения каталогов для переноса. Точный синтаксис — `rac help service-setting`.

### 5.14. Режим binary-data-storage (хранилища двоичных данных)

С версии 8.3.27. Хранилище двоичных данных выносит большие двоичные данные базы из СУБД во встроенное хранилище кластера или во внешнее S3-хранилище. Подключают и отключают хранилища в конфигураторе или стандартной функцией; средствами администрирования кластера их просматривают, очищают и резервируют (для встроенного хранилища) [офиц.].

Команды режима в документации 8.3.27 описаны для утилиты `ibcmd` (автономный сервер); в `rac` режим с тем же именем добавлен той же версией. ⚠ Для `rac` состав команд ожидается таким же, плюс `--cluster` и идентификатор базы; сверить по `rac help binary-data-storage`.

| Команда (по `ibcmd`) | Действие | Параметры |
|---|---|---|
| `list` | Список подключённых хранилищ | — |
| `info` | Сведения о хранилище | `--name=<имя>` или `--storage=<идентификатор>` |
| `clear-unused-space` | Очистить неиспользуемые данные встроенного хранилища | `--by-universal-date=<дата>` (приоритетнее) или `--keep-days=<n>` |
| `create-full-backup` | Полная резервная копия встроенного хранилища | `--server-path=<файл>` |
| `create-diff-backup` | Дифференциальная копия | `--full-backup-server-path=<файл полной копии>`, `--server-path=<файл>` |
| `load-full-backup` | Восстановление из полной копии | `--server-path=<файл>` |
| `load-diff-backup` | Восстановление из дифференциальной копии | `--full-backup-server-path=<файл>`, `--server-path=<файл>` |

Пути в `--server-path` — это пути на сервере хранилища, файлы должны быть доступны пользователю, от имени которого работает сервер (`usr1cv8`). Резервная копия СУБД двоичные данные встроенного хранилища не содержит — их копируют отдельно.

### 6.1. Заготовка: параметры и библиотека функций

Файл параметров `/etc/1c-rac.env` (права `600`, владелец `root`):

```bash

CL_PWD='Cl-S3cret!'
IB_USER='Администратор'      # администратор информационных баз (если одинаков во всех базах)
IB_PWD='Ib-S3cret!'
```

Библиотека `/usr/local/lib/1c-rac.sh`:

```bash
# подключение: source /usr/local/lib/1c-rac.sh
source /etc/1c-rac.env

RAC_BIN=${RAC_BIN:-$(ls -d /opt/1cv8/x86_64/*/rac 2>/dev/null | sort -V | tail -n1)}
RAS=${RAS:-localhost:1545}

CL_AUTH=(); [[ -n ${CL_USER:-} ]] && CL_AUTH=(--cluster-user="$CL_USER" --cluster-pwd="${CL_PWD:-}")
IB_AUTH=(); [[ -n ${IB_USER:-} ]] && IB_AUTH=(--infobase-user="$IB_USER" --infobase-pwd="${IB_PWD:-}")

# вызов rac с ограничением времени и без чтения stdin
rac() { timeout "${RAC_TIMEOUT:-60}" "$RAC_BIN" "$@" </dev/null; }

# функция rac_table — из раздела 3.3 (скопировать сюда)

# умеет ли эта версия rac параметр --error-message у session terminate (в справке 8.3.1x его нет)
if rac help session 2>&1 | grep -q -- '--error-message'; then RAC_HAS_ERRMSG=1; else RAC_HAS_ERRMSG=0; fi

cluster_id() { rac cluster list "$RAS" | awk '$1=="cluster" && !d {print $3; d=1}'; }
CL=${CL:-$(cluster_id)}

ib_id() {                      # ib_id <имя базы>  →  UUID базы
  rac infobase summary list --cluster="$CL" "${CL_AUTH[@]}" "$RAS" |
    awk -v want="$1" '
      $1=="infobase" { id = $3 }
      $1=="name"     { n = $3; gsub(/"/, "", n)
                       if (!d && tolower(n) == tolower(want)) { print id; d = 1 } }'
}

declare -A IB_NAME             # UUID базы → имя
load_ib_names() {
  local id name
  while IFS=$'\t' read -r id name; do IB_NAME[$id]=$name; done < <(
    rac infobase summary list --cluster="$CL" "${CL_AUTH[@]}" "$RAS" | rac_table infobase name)
}

sessions() {                   # sessions [UUID базы]  →  сырой вывод rac session list
  local a=(); [[ -n ${1:-} ]] && a=(--infobase="$1")
  rac session list --cluster="$CL" "${a[@]}" "${CL_AUTH[@]}" "$RAS"
}
```

Замечания: массивы `CL_AUTH` и `IB_AUTH` корректно передают имена и пароли с пробелами и кириллицей; `tolower` в `awk` надёжно работает только для латиницы — имена баз обычно латинские.

### 6.4. Завершить все сеансы базы

```bash
kill_sessions() {              # kill_sessions <UUID базы> [сообщение пользователям]
  local ib=$1 msg=${2:-"Сеанс завершён администратором"} sid app user m=()
  (( ${RAC_HAS_ERRMSG:-0} )) && m=(--error-message="$msg")   # параметр передаём, только если rac его знает
  sessions "$ib" | rac_table session app-id user-name |
  while IFS=$'\t' read -r sid app user; do
    case $app in SrvrConsole|RAS) continue ;; esac        # служебные сеансы не трогаем
    echo "завершаю: $user ($app) $sid"
    rac session terminate --cluster="$CL" --session="$sid" "${m[@]}" \
        "${CL_AUTH[@]}" "$RAS" || echo "  не удалось завершить $sid" >&2
  done
}

kill_sessions "$IB" "База закрывается на обслуживание"
sleep 10
sessions "$IB" | rac_table session-id user-name app-id     # проверка: вывод должен быть пустым
```

Если `rac` вашей версии не принимает `--error-message`, уберите этот параметр. Без блокировки начала сеансов (6.5) пользователи и регламентные задания тут же зайдут снова.

### 6.5. Блокировка начала сеансов и регламентных заданий с кодом разрешения

```bash
ib_lock() {                    # ib_lock <UUID базы> <код разрешения> <минут> [сообщение]
  local ib=$1 code=$2 minutes=$3 msg=${4:-"Идут регламентные работы"}
  rac infobase update --cluster="$CL" --infobase="$ib" "${CL_AUTH[@]}" "${IB_AUTH[@]}" \
      --sessions-deny=on --scheduled-jobs-deny=on \
      --denied-from="$(date '+%Y-%m-%dT%H:%M:%S')" \
      --denied-to="$(date -d "+${minutes} min" '+%Y-%m-%dT%H:%M:%S')" \
      --denied-message="$msg" --permission-code="$code" "$RAS"
}

ib_unlock() {                  # ib_unlock <UUID базы>
  rac infobase update --cluster="$CL" --infobase="$1" "${CL_AUTH[@]}" "${IB_AUTH[@]}" \
      --sessions-deny=off --scheduled-jobs-deny=off \
      --denied-from= --denied-to= --denied-message= --permission-code= "$RAS"
}

ib_lock_state() {              # показать текущее состояние блокировки
  rac infobase info --cluster="$CL" --infobase="$1" "${CL_AUTH[@]}" "${IB_AUTH[@]}" "$RAS" |
    grep -E '^(sessions-deny|scheduled-jobs-deny|denied-|permission-code)'
}

ib_lock "$IB" "K7m2Qx" 120 "Обновление базы до 01:00"
ib_lock_state "$IB"
ib_unlock "$IB"
```

Пояснения:

- Блокировка не завершает уже работающие сеансы — после `ib_lock` вызывайте `kill_sessions`.
- `--denied-to` — страховка: если скрипт упадёт, вход откроется сам по истечении срока. Блокировка регламентных заданий сроком не ограничена, её нужно снять явно.
- Если в базе регламентные задания были выключены намеренно (копия рабочей базы), уберите `--scheduled-jobs-deny=off` из `ib_unlock`.
- ⚠ не подтверждено: что пустые значения (`--denied-from=` и т. д.) сбрасывают поля во всех версиях. Проверьте `ib_lock_state` после снятия. Время указывается местное серверное [практика].
- Вход при действующей блокировке — с кодом разрешения [офиц.]:

```bash
# тонкий клиент
/opt/1cv8/x86_64/$V/1cv8c ENTERPRISE /S"srv1c\buh" /N"Администратор" /P"пароль" /UC"K7m2Qx"
# конфигуратор в пакетном режиме: обновление конфигурации базы данных
/opt/1cv8/x86_64/$V/1cv8 DESIGNER /S"srv1c\buh" /N"Администратор" /P"пароль" /UC"K7m2Qx" /UpdateDBCfg
# в строке соединения: Srvr="srv1c";Ref="buh";UC="K7m2Qx"
```

### 6.6. Окно обслуживания целиком

```bash
#!/usr/bin/env bash
# /usr/local/sbin/1c-maintenance.sh <имя базы> <команда обслуживания …>
set -euo pipefail
source /usr/local/lib/1c-rac.sh
# сюда же скопировать функции kill_sessions, ib_lock, ib_unlock из 6.4 и 6.5

IB=$(ib_id "$1"); shift
[[ -n $IB ]] || { echo "база не найдена" >&2; exit 1; }
CODE=$(openssl rand -hex 6)

trap 'ib_unlock "$IB"' EXIT                       # снять блокировку при любом исходе
ib_lock "$IB" "$CODE" 120 "Регламентные работы, вход закрыт не более чем на 2 часа"
kill_sessions "$IB" "База закрыта на регламентные работы"

n=1
for _ in {1..30}; do                              # ждём завершения сеансов до 5 минут
  out=$(sessions "$IB")
  n=$(rac_table app-id <<<"$out" | grep -cvE '^(SrvrConsole|RAS)$' || true)
  (( n == 0 )) && break
  sleep 10
done
(( n == 0 )) || { echo "остались сеансы: $n" >&2; exit 2; }

UC_CODE=$CODE "$@"                                # код разрешения доступен команде в переменной UC_CODE
```


### 6.7. Создать и удалить информационную базу

```bash
ib_create() {                  # ib_create <имя> [описание]  — база данных PostgreSQL с тем же именем
  rac infobase create --cluster="$CL" "${CL_AUTH[@]}" --create-database \
      --name="$1" --descr="${2:-$1}" --dbms=PostgreSQL --db-server="${PG_HOST:-localhost}" \
      --db-name="$1" --db-user="${PG_USER:-postgres}" --db-pwd="$PG_PWD" --locale=ru_RU \

ib_drop() {                    # ib_drop <имя> [--drop-database | --clear-database]
```

### 6.8. Найти «тяжёлые» сеансы

```bash
heavy() {                      # heavy [порог длительности текущего вызова, мс; по умолчанию 5000]
  local thr=${1:-5000} ib rest
  load_ib_names
  { printf 'База\tN\tПользователь\tПриложение\tВызов\tСУБД\tПамять\tCPU\tЖдёт-упр\tЖдёт-СУБД\tPID-СУБД\n'
    sessions | rac_table infobase session-id user-name app-id duration-current duration-current-dbms \
                         memory-current cpu-time-current blocked-by-ls blocked-by-dbms db-proc-info |
      awk -F'\t' -v t="$thr" '$5+0 >= t' | sort -t$'\t' -k5,5nr |
      while IFS=$'\t' read -r ib rest; do printf '%s\t%s\n' "${IB_NAME[$ib]:-$ib}" "$rest"; done
  } | column -t -s$'\t'
}
heavy 10000

# топ-10 по процессорному времени за последние 5 минут
sessions | rac_table session-id user-name app-id cpu-time-last-5min duration-last-5min calls-last-5min \
  | sort -t$'\t' -k4,4nr | head

# топ-10 по памяти и по обмену с СУБД с начала сеанса
sessions | rac_table session-id user-name app-id memory-total     | sort -t$'\t' -k4,4nr | head
sessions | rac_table session-id user-name app-id dbms-bytes-all   | sort -t$'\t' -k4,4nr | head

# сеансы, которые давно спят (кандидаты на освобождение)
sessions | rac_table session-id user-name app-id hibernate last-active-at | awk -F'\t' '$4=="yes"'
```

Как читать: большой `duration-current` при малом `duration-current-dbms` и растущем `cpu-time-current` — тяжёлый код на сервере 1С; `duration-current-dbms` почти равен `duration-current` — время уходит в PostgreSQL (смотрите запрос по `db-proc-info` в `pg_stat_activity`); ненулевые `blocked-by-ls` или `blocked-by-dbms` — сеанс не работает, а ждёт блокировку.

```bash
rac process list --cluster="$CL" --licenses "${CL_AUTH[@]}" "$RAS" \
  | rac_table host pid license-type max-users-all max-users-cur short-presentation
```

## 7. Остановка и запуск сервера, очистка сеансовых данных

### 7.1. Остановка, запуск, перезапуск

```bash
V=8.3.27.2074
sudo systemctl stop  srv1cv8-$V@default.service        # остановить кластер (ragent, rmngr, rphost)
pgrep -u usr1cv8 -a -x 'ragent|rmngr|rphost'           # проверка: вывод должен быть пустым
sudo systemctl start srv1cv8-$V@default.service
sudo systemctl restart srv1cv8-$V@default.service      # то же одной командой
systemctl status srv1cv8-$V@default.service --no-pager
```

Правила:

- Перед остановкой предупредите пользователей и закройте вход в базы (6.5): при остановке сеансы толстых клиентов и конфигураторов обрываются.
- `ras` при плановой остановке кластера останавливать не обязательно [офиц.].
- Данные сеансов хранит сервис сеансовых данных на диске, и при перезапуске кластера они сохраняются [офиц.]. Поэтому тонкие и веб-клиенты после перезапуска могут продолжить работу, а «зависшие» сеансы перезапуском не лечатся.
- Перезапустить только рабочие процессы, не останавливая службу, можно расписанием перезапуска или выключением процесса (5.1, 5.4).
- Если после `stop` процессы остались, подождите (systemd сам завершит их по истечении таймаута остановки) или завершите вручную: `sudo pkill -u usr1cv8 -x rphost`, в крайнем случае с `-9`.

### 7.2. Что лежит в каталоге данных кластера и что можно удалять

Каталог данных сервера на Linux по умолчанию — `/home/usr1cv8/.1cv8/1C/1cv8` (переменная `SRV1CV8_DATA`, параметр `/d` агента). Если агент при запуске не найдёт в нём реестр, он создаст новый пустой кластер [офиц.].

| Объект | Путь | Можно ли удалять |
|---|---|---|
| Реестр сервера: список кластеров и администраторы центрального сервера | `1cv8wsrv.lst` | **Нельзя** |
| Реестр кластера: базы, рабочие серверы, требования, администраторы кластера, профили | `reg_1541/1CV8Clst.lst` (в документации имя пишется `1cv8clst.lst`) | **Нельзя**. Потеря файла — потеря списка баз и настроек |
| Каталог базы | `reg_1541/<uuid базы>/` | **Нельзя** |
| Журнал регистрации | `reg_1541/<uuid базы>/1Cv8Log/` | **Нельзя**: журнал хранится только здесь, в резервную копию СУБД не входит |
| Индекс полнотекстового поиска | `reg_1541/<uuid базы>/1Cv8FTxt/`, `1Cv8FTxt2/` | Допустимо при остановленной службе; потом нужна полная переиндексация [практика] |
| Встроенное хранилище двоичных данных | `reg_1541/BinDataStrg/<uuid базы>/` | **Нельзя**: это данные базы |
| Настройки счётчиков потребления ресурсов | `reg_1541/rescntsrv.lst` | Не трогать |
| Сеансовые данные | `reg_1541/snccntx*` | Можно, **только при остановленной службе** [практика]. Все сеансы будут потеряны |
| Файлы лицензий | `/var/1C/licenses/*.lic` | **Нельзя** |
| Конфигурационные файлы (`conf.cfg`, `logcfg.xml` и др.) | `/opt/1cv8/x86_64/$V/conf/` (в практике встречается и общий `/opt/1cv8/conf/` — он официально входит в порядок поиска конфигурационных файлов (приложение 1 документации 8.3.27, сверено 10.10.2026)) | **Нельзя** |

В документации путь сеансовых данных записан как `reg_<порт>/snccntx/<uuid менеджера>`, на практике встречаются каталоги вида `snccntx<uuid>` — поэтому в командах используется маска `snccntx*`.

Важно для Linux: каталог данных кластера по умолчанию совпадает с каталогом профиля 1С пользователя `usr1cv8`. Рецепты «очистки кэша клиента» (удалить все каталоги с именами-UUID в профиле 1С) применять к нему нельзя — так удаляются каталоги баз вместе с журналами регистрации. Клиентский кэш лежит на клиентских машинах (`~/.1cv8/1C/1cv8/` у пользователя Linux, `%APPDATA%\1C\1cv8` и `%LOCALAPPDATA%\1C\1cv8` в Windows) и к серверу отношения не имеет.

Когда чистить сеансовые данные: «зависшие» сеансы, которые не удаляются командой `terminate` и переживают перезапуск; ошибки сеансовых данных после аварийного отключения сервера или переполнения диска; каталог `snccntx*` разросся. Это не регулярная процедура. Официальной инструкции 1С по очистке для Linux найти не удалось — приём общепринятый в сообществе.

### 7.3. Скрипт очистки сеансовых данных

```bash
#!/usr/bin/env bash
# /usr/local/sbin/1c-clear-session-data.sh — остановить сервер 1С, удалить сеансовые данные, запустить
set -euo pipefail
V=8.3.27.2074
UNIT="srv1cv8-$V@default.service"
DATA=/home/usr1cv8/.1cv8/1C/1cv8                 # каталог данных сервера (SRV1CV8_DATA)

[[ $EUID -eq 0 ]] || { echo "нужны права root" >&2; exit 1; }
[[ -f $DATA/1cv8wsrv.lst ]] || { echo "в $DATA нет реестра сервера — проверьте путь" >&2; exit 1; }

systemctl stop "$UNIT"
for _ in {1..30}; do                             # ждём завершения процессов до минуты
  pgrep -u usr1cv8 -x 'ragent|rmngr|rphost' >/dev/null || break
  sleep 2
done
if pgrep -u usr1cv8 -x 'ragent|rmngr|rphost' >/dev/null; then
  echo "процессы кластера не завершились, останавливаю принудительно" >&2
  pkill -9 -u usr1cv8 -x 'ragent|rmngr|rphost' || true
  sleep 2
fi

# страховочная копия реестров
cp -a "$DATA/1cv8wsrv.lst" "/root/1cv8wsrv.lst.$(date +%F-%H%M)"
for f in "$DATA"/reg_*/1CV8Clst.lst; do
  [[ -f $f ]] && cp -a "$f" "/root/$(basename "$(dirname "$f")")-1CV8Clst.lst.$(date +%F-%H%M)"
done

ls -d "$DATA"/reg_*/snccntx* 2>/dev/null || echo "каталогов snccntx нет"
rm -rf -- "$DATA"/reg_*/snccntx*                 # только сеансовые данные

systemctl start "$UNIT"
systemctl --no-pager --lines=0 status "$UNIT"
```

После запуска проверьте: `rac cluster list` возвращает прежний UUID кластера, `rac infobase summary list` показывает все базы. Если кластер создался заново (другой UUID, баз нет) — значит, служба запущена с другим каталогом данных; остановите её и разберитесь с `SRV1CV8_DATA`.

## 8. Графические средства и программный доступ

### 8.1. MMC-оснастка на Windows

- Утилита администрирования кластера — оснастка консоли MMC, работает только в Windows [офиц.]. Запуск: Пуск → 1С Предприятие 8 (x86-64) → Дополнительно → Администрирование серверов 1С Предприятия; либо `mmc` → добавить оснастку «1C:Enterprise 8.3 Servers» (в 8.5 — «1C:Enterprise 8.5 Servers»).
- К серверу на Linux подключается напрямую к агенту: протокол `tcp`, порт 1540; `ras` не нужен. С Windows-машины должны быть доступны порты 1540, 1541, 1560–1591, а имя Linux-сервера должно разрешаться.
- Версия оснастки должна совпадать с версией сервера; при нескольких версиях платформы на Windows регистрируют оснастку нужной версии (см. статью `02-ustanovka-servera-ubuntu.md`, раздел 10).
- Имя сервера пишите везде одинаково: система не считает `srv1c`, IP-адрес и `localhost` одним и тем же сервером [офиц.].
- Данные в консоли не обновляются сами: «Действие → Обновить».
- Ограничения: для PostgreSQL нельзя разорвать соединение, занятое запросом; создавать и удалять хранилища двоичных данных в консоли нельзя [офиц.].

### 8.2. Стандартная функция «Управление серверами» (кроссплатформенно)

- Отдельной графической консоли кластера для Linux в поставке нет. Её аналог — стандартная функция «Управление серверами» клиентского приложения (идентификатор `ServersManagement`), доступная в режиме технического специалиста [офиц.].
- Работает только через сервер администрирования: доступны те серверы, для которых развёрнут `ras`. Клиент может быть запущен в Linux, macOS или Windows и работать с любой базой, даже файловой и не связанной с администрируемым кластером.
- Версии клиента, `ras` и кластера совпадать не обязаны (с учётом правил совместимости `ras`), потому что функция построена на объекте встроенного языка `АдминистрированиеСервера` (появился в 8.3.14) [офиц.].
- С 8.3.25 умеет сохранять параметры администрируемых серверов в XML-файл и восстанавливать их; с 8.3.26 — редактировать каталоги сервисов, параметры проверки соединений и флажок аудита прав доступа; с 8.3.27 — показывать хранилища двоичных данных [офиц., V8Update].
- По данным статьи `01-arhitektura-versii-trebovaniya.md`, в 8.5.4 функцию можно запускать из командной строки без лицензии и без информационной базы.
- Утилита `1cv8a` («административная консоль», компонент `additional_admin_functions`) — это не консоль кластера, а средство проверки и исправления информационных баз.

### 8.3. Программный доступ

| Способ | Где работает | Что нужно знать |

## Типичные ошибки и подводные камни (симптом → причина → решение)

| № | Симптом | Причина | Решение |
|---|---|---|---|
| 1 | `rac` сообщает об ошибке соединения с сервером | `ras` не запущен, слушает другой порт или порт закрыт | `systemctl status ras-$V`, `ss -tlnp \| grep 1545`, указать адрес явно: `rac cluster list srv1c:1545` |
| 2 | `ras` работает, но `rac cluster list` возвращает ошибку обращения к агенту | Не запущен `ragent`, `ras` смотрит на другой адрес или порт агента | `systemctl status srv1cv8-$V@default`, проверить строку запуска: `pgrep -a ras` |
| 3 | После обновления платформы `rac` перестал работать | Остался запущен `ras` старой версии; версия `ras` должна совпадать с версией кластера | `systemctl disable --now ras-$OLD`, затем `link` и `enable --now` для новой версии |
| 4 | «Недостаточно прав пользователя на управление кластером» | В кластере есть администраторы, а `--cluster-user`/`--cluster-pwd` не указаны или неверны | Передать имя и пароль администратора кластера |
| 5 | Ошибка аутентификации администратора центрального сервера | Действие уровня агента (`cluster insert`, `agent admin …`) без `--agent-user`/`--agent-pwd` | Передать имя и пароль администратора центрального сервера |
| 6 | «Недостаточно прав пользователя на информационную базу» при `infobase info`, `update`, `drop` | Не указан администратор базы | Добавить `--infobase-user` и `--infobase-pwd` пользователя с административными правами |
| 7 | Администратор создан, но войти через `rac` нельзя | У администратора включена только аутентификация ОС; `rac` её не поддерживает | Создавать администраторов с `--auth=pwd` |
| 8 | Любой в сети может управлять кластером | Списки администраторов пусты, порты 1540 и 1545 открыты | Создать администраторов (раздел 4), ограничить порты в `ufw` |
| 9 | Пароль администратора виден в `ps` и в истории команд | `rac` принимает параметры только в командной строке | Файл параметров с правами 600, запуск от root, пробел перед командой (4.5) |
| 10 | После `session terminate` пользователи сразу появляются снова | Не закрыт вход и не выключены регламентные задания | Сначала `--sessions-deny=on --scheduled-jobs-deny=on`, затем завершать сеансы |
| 11 | Блокировка установлена, а пользователи продолжают работать | Блокировка запрещает только новые сеансы | Завершить существующие сеансы (6.4) |
| 12 | Никто не может войти, код разрешения забыт | Действует `sessions-deny` | `rac infobase update … --sessions-deny=off` — `rac` блокировка не мешает |
| 13 | Регламентные задания не выполняются после переноса или копирования базы | В свойствах базы осталось `scheduled-jobs-deny : on` | `rac infobase update … --scheduled-jobs-deny=off` (для копий — оставить включённым) |
| 14 | `connection disconnect` или удаление соединения в консоли ничего не делает | Соединение занято запросом к PostgreSQL — для этой СУБД разрыв не поддерживается | `pg_cancel_backend` или `pg_terminate_backend` по `db-proc-info` (5.7) |
| 15 | Сеанс не завершается командой `terminate` | Исполнение стоит внутри одной строки кода (долгий HTTP-вызов, внешняя компонента) либо в запросе к СУБД | Снять запрос в PostgreSQL; выключить рабочий процесс; в крайнем случае `kill` процесса `rphost` по `pid` |
| 16 | Требования назначения добавлены, но ничего не изменилось | Требования не применены | `rac rule apply --partial` (или `--full`) |
| 17 | После применения требований клиенты получают ошибку при подключении | Ни один сервер не может обслужить объект (везде «не назначать») | Проверить порядок требований: первое подходящее побеждает; добавить разрешающее требование |
| 18 | На лицензии ПРОФ требование не работает | Заполнены «Имя ИБ» или «Значение дополнительного параметра» | На ПРОФ допустимы только требования без этих полей; остальное — КОРП |
| 19 | Создание базы завершается ошибкой СУБД об отсутствии базы данных | Не указан `--create-database` | Добавить флаг либо создать базу данных в PostgreSQL заранее |
| 20 | В примерах из интернета `--license-distribution="true"`, `--locale="RU_ru"` | Недокументированные значения | Использовать `allow`/`deny` и локаль вида `ru_RU` |
| 21 | После очистки «кэша» пропали все базы | Удалён `1CV8Clst.lst` или весь каталог `reg_1541` | Восстановить реестр из копии при остановленной службе; удалять только `snccntx*` |
| 22 | После запуска службы кластер пустой, UUID другой | Агент запущен с другим каталогом данных и создал новый кластер | Проверить `SRV1CV8_DATA` в юните и drop-in, вернуть прежний каталог |
| 23 | Каталог `snccntx*` удалён на работающем сервере | Нарушена работа сервиса сеансовых данных | Перезапустить службу; впредь чистить только при остановленном сервере |
| 24 | Память сервера исчерпана, `rphost` убивает ядро (OOM) | Пороги памяти по умолчанию считаются от всей ОЗУ и не учитывают PostgreSQL на той же машине | Задать `--temporary-allowed-total-memory` и `--critical-total-memory` явно (5.3) |
| 25 | Свойство «Защищённое соединение» изменено, но не действует | Нужен перезапуск кластера | Перезапустить службу сервера |
| 26 | `rac` надолго «зависает» в скрипте мониторинга | Недоступен `ras` или агент | Оборачивать вызовы в `timeout` |
| 27 | Имя сервера в `rac cluster list` не то, что ожидалось; клиенты не подключаются | Кластер создан со старым именем хоста | Использовать одно имя везде; при смене имени хоста кластер пересоздают (статья 02) |
| 28 | После `rac rule apply` у всех пользователей оборвалась работа | Без параметров выполняется полное применение требований | В рабочее время использовать `rac rule apply --partial` |

## Быстрая шпаргалка — «задача → команда»

Обозначения: `$CL` — UUID кластера, `$IB` — UUID базы, `$SRV` — UUID рабочего сервера, `$AUTH` — `--cluster-user=… --cluster-pwd=…`, `$IBAUTH` — `--infobase-user=… --infobase-pwd=…`.

| Задача | Команда |
|---|---|
| Запустить `ras` вручную | `/opt/1cv8/x86_64/$V/ras cluster --daemon --port=1545 localhost:1540` |
| `ras` как служба | `sudo systemctl link /opt/1cv8/x86_64/$V/ras-$V.service && sudo systemctl enable --now ras-$V.service` |
| Справка по режиму | `rac help infobase` |
| Версия агента | `rac agent version` |
| UUID кластера | `CL=$(rac cluster list \| awk '$1=="cluster"{print $3; exit}')` |
| Свойства кластера | `rac cluster info --cluster=$CL` |
| Создать администратора центрального сервера | `rac agent admin register --name=agentadmin --pwd=… --auth=pwd` |
| Создать администратора кластера | `rac cluster admin register --cluster=$CL --name=cladmin --pwd=… --auth=pwd --agent-user=… --agent-pwd=…` |
| Список администраторов кластера | `rac cluster admin list --cluster=$CL $AUTH` |
| Рабочие серверы | `rac server list --cluster=$CL $AUTH` |
| Пороги памяти сервера | `rac server update --cluster=$CL --server=$SRV $AUTH --temporary-allowed-total-memory=<байты> --critical-total-memory=<байты>` |
| Ночной перезапуск процессов (8.3.27+) | `rac cluster update --cluster=$CL --restart-schedule="0 3 * * *"` |
| Рабочие процессы и память | `rac process list --cluster=$CL $AUTH` |
| Менеджеры кластера | `rac manager list --cluster=$CL $AUTH` |
| Сервисы кластера | `rac service list --cluster=$CL $AUTH` |
| Список баз | `rac infobase summary list --cluster=$CL $AUTH` |
| Свойства базы | `rac infobase info --cluster=$CL --infobase=$IB $AUTH $IBAUTH` |
| Создать базу в PostgreSQL | `rac infobase create --cluster=$CL $AUTH --create-database --name=demo --dbms=PostgreSQL --db-server=localhost --db-name=demo --db-user=postgres --db-pwd=… --locale=ru_RU --license-distribution=allow` |
| Удалить регистрацию базы | `rac infobase drop --cluster=$CL --infobase=$IB $AUTH $IBAUTH` |
| Удалить базу вместе с базой данных | `rac infobase drop --cluster=$CL --infobase=$IB $AUTH $IBAUTH --drop-database` |
| Закрыть вход в базу | `rac infobase update --cluster=$CL --infobase=$IB $AUTH $IBAUTH --sessions-deny=on --denied-message="…" --permission-code=…` |
| Открыть вход | `rac infobase update --cluster=$CL --infobase=$IB $AUTH $IBAUTH --sessions-deny=off` |
| Выключить и включить регламентные задания | `rac infobase update … --scheduled-jobs-deny=on` и `…=off` |
| Сменить пароль пользователя СУБД в свойствах базы | `rac infobase update --cluster=$CL --infobase=$IB $AUTH $IBAUTH --db-pwd=…` |
| Сеансы базы | `rac session list --cluster=$CL --infobase=$IB $AUTH` |
| Завершить сеанс | `rac session terminate --cluster=$CL --session=<uuid> $AUTH` |
| Прервать текущий вызов сеанса | `rac session interrupt-current-server-call --cluster=$CL --session=<uuid> $AUTH` ⚠ |
| Клиентские лицензии сеансов | `rac session list --cluster=$CL --licenses $AUTH` |
| Соединения | `rac connection list --cluster=$CL $AUTH` |
| Блокировки базы | `rac lock list --cluster=$CL --infobase=$IB $AUTH` |
| Требования назначения сервера | `rac rule list --cluster=$CL --server=$SRV $AUTH` |
| Фоновые задания — на сервер `$SRV` | `rac rule insert --cluster=$CL --server=$SRV --position=0 --object-type=Connection --rule-type=always --application-ext=BackgroundJob $AUTH` |
| Применить требования | `rac rule apply --cluster=$CL --partial $AUTH` |
| Профили безопасности | `rac profile list --cluster=$CL $AUTH` |
| Остановить и запустить сервер | `sudo systemctl stop srv1cv8-$V@default` и `sudo systemctl start srv1cv8-$V@default` |
| Очистить сеансовые данные | служба остановлена → `sudo rm -rf /home/usr1cv8/.1cv8/1C/1cv8/reg_1541/snccntx*` → запуск |
| Снять зависший запрос в PostgreSQL | `sudo -u postgres psql -c "SELECT pg_cancel_backend(<db-proc-info>);"` |

## Что не удалось подтвердить

Всё перечисленное проверяется одной командой `rac help <режим>` на установленной версии.

1. Актуальный вывод `rac help` для 8.3.27 и 8.5.x: списки параметров собраны из справки 8.3.1x и заметок о выпуске.
2. Наличие и написание в `rac` команды `session interrupt-current-server-call` и параметра `--error-message` (подтверждены только для `ibcmd` и консоли).
3. Форма команды выключения рабочего процесса (`process … turn-off`), формат значений `--add-prohibiting-assignment-rule`, `--disable-local-speech-to-text`, `--allow-access-right-audit-events-recording`, точное имя параметра резервирования рабочих процессов.
4. Команды и параметры режимов `service-setting` и `binary-data-storage` утилиты `rac`.
5. Единицы полей `duration-*`, `db-proc-took`, `cpu-time-*` в выводе `rac` (по косвенным данным — миллисекунды).
6. Состав расширенных полей `connection list` и условия их появления.
7. Содержимое штатного юнита `ras-<версия>.service`.
8. Формат даты и сброс пустым значением для `--denied-from` и `--denied-to`; запись адреса PostgreSQL с нестандартным портом в `--db-server`.
9. Умолчание `--connections-limit` (128) и время жизни спящего сеанса (86400 с).
10. Поддержка в `rac` аутентификации администратора открытым ключом.
11. Процедура восстановления доступа при утере пароля администратора кластера.
12. Изменения `rac` и `ras` в 8.5.4.
