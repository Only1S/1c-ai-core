## Кратко

1. **ТЖ настраивается файлом `logcfg.xml`** в каталоге конфигурационных файлов 1С. Платформа опрашивает эти каталоги **каждые 60 секунд** и применяет изменения **без перезапуска** процессов `[офиц. 8.5.1]`.
2. **Порядок поиска на Linux** `[офиц. 8.5.1]`: `/opt/1cv8/x86_64/<версия>/conf` → `/opt/1cv8/conf` → `~/.1cv8/1C/1cv8/conf` (для сервера `~` = `/home/usr1cv8`) → каталог из параметра `ConfLocation` файла `conf.cfg`. Для сервера удобнее всего `/opt/1cv8/conf/logcfg.xml` — он общий для всех версий и переживает обновление платформы.
3. **Без `logcfg.xml` работает «ТЖ по умолчанию»**: события `SYSTEM` уровня `ERROR`, хранение 24 часа `[офиц. 8.3.27]`. Каталог на Linux в документации указан **двумя способами**: `~/.1cv8/logs` (приложение 3, разделы 3.24.1 и 3.24.2.11) и `~/.1cv8/1C/1cv8/logs` (глава 6, раздел 6.14.3). Для сервера проверяйте оба: `/home/usr1cv8/.1cv8/1C/1cv8/logs` и `/home/usr1cv8/.1cv8/logs` (⚠ какой из двух путей действует в вашей сборке — посмотрите на сервере). Это первое место, куда стоит заглянуть при сбое.
4. **Каталог журнала должен быть доступен на запись пользователю `usr1cv8`**; у каждого элемента `<log>`, `<dump>` и `<defaultlog>` — свой отдельный каталог `[офиц. 8.5.1]`. В каталоге журнала не должно быть посторонних файлов — иначе журнал не пишется `[офиц. ИТС 5809]`.
5. **Структура файлов**: `<location>/<процесс>_<PID>/<ГГММДДЧЧ>.log`, новый файл каждый час. Строка события: `мм:сс.микросекунды-длительность,ИМЯ,вложенность,свойства…` (с 8.3.25 первым свойством идёт `level=…`). Длительность в файле — в **микросекундах**; метка времени — момент **окончания** события.
6. **В фильтрах `logcfg.xml` свойство `duration` измеряется в 1/10000 секунды** (сотни микросекунд), а `durationus` — в микросекундах `[офиц. 8.5.1]`. «Дольше 1 секунды» = `duration ≥ 10000` или `durationus ≥ 1000000`.
7. **Элементы-генераторы** (`<plansql/>`, `<dbmslocks/>`, `<mem/>`, `<leaks>`, `<system>`, `<query>` и др.) включают сбор данных; без них фильтр по соответствующему событию или свойству ничего не даст. Они замедляют сервер независимо от фильтров, особенно `<plansql/>`: по методике 1С для PostgreSQL его **нельзя включать на продуктивных серверах** — только на тестовых и серверах разработки `[офиц. ИТС 6011]`.
8. **История хранится `history` часов.** `history="0"` у `<log>` отключает автоудаление (с 8.3.25 `[офиц. V8Update]`). Полный ТЖ на рабочем сервере включают на минуты или часы, а не постоянно.
9. **Элемент `<dump>` на Linux игнорируется**: дампы формирует сама ОС `[офиц. 8.5.1]`. На Ubuntu обработчик дампов по умолчанию — apport (`cat /proc/sys/kernel/core_pattern`). Обычный аварийный дамп возникает по сигналу `SIGSEGV`; дамп процесса, который кластер завершает за превышение критического объёма памяти, — по `SIGABRT` (до 8.3.27 — тоже `SIGSEGV`) `[офиц. 8.3.27, V8Update]`.
10. **Три условия появления core dump**: ненулевой лимит `RLIMIT_CORE` у процесса (для службы — `LimitCORE=` в юните), обработчик или путь в `kernel.core_pattern`, доступный на запись каталог с достаточным местом.
11. **События для PostgreSQL**: `DBPOSTGRS` (свойства `Sql`, `planSQLText`, `Rows`, `RowsAffected`, `dbpid`, `Trans`), `SDBL` (запрос на уровне модели базы данных 1С, границы транзакций), `TLOCK` / `TTIMEOUT` / `TDEADLOCK` (управляемые блокировки), `EXCP` (исключения).
12. **Анализ в bash** строится в два шага: склеить многострочные события в одну строку, затем агрегировать (`awk`, `perl`, `sort | uniq -c`).
13. **Журнал регистрации** кластера лежит в `<SRV1CV8_DATA>/reg_<порт>/<UUID базы>/1Cv8Log/`. Последовательный формат — `1Cv8.lgf` + `*.lgp` + индексы `*.lgx`; формат SQLite — `1Cv8.lgd`. С 8.3.22 новый журнал в SQLite создать нельзя, обратное преобразование не поддерживается `[офиц. 8.5.1]`. С 8.3.25 журнал выгружается в XML или JSON без подключения к базе: `ibcmd eventlog export` `[офиц. 8.3.27]`.
14. **Отладка на сервере** включается переменной `SRV1CV8_DEBUG`: `-debug` (TCP, порты 1560–1591) или `-debug -http` (сервер отладки `dbgs`, порт 1550) `[офиц. 8.5.1]`. Режим отладки снижает производительность — только для стендов.
15. **Мониторинг**: `rac process list`, `rac session list` через сервер администрирования `ras` (порт 1545); с 8.3.25 `ras` сам отдаёт метрики в формате OpenMetrics (`--monitor-address`, `--monitor-port` 1555, `--monitor-base`; лицензия КОРП); готовые решения — шаблон Zabbix `slothfk/1c_zabbix_template_ce`, экспортер Prometheus `LazarenkoA/prometheus_1C_exporter`, ЦУП и ЦКК из состава 1С:КИП.
16. **Новое в `<log>` с версии 8.3.25** `[офиц. V8Update]`: `format="json"`, `placement="plain"`, `rotation="size"`, `rotationperiod`, `rotationsize`, `compress="zip"`, а также свойство `level` у всех событий.
17. **Первые команды при сбое сервера**:

```bash
V=8.3.27.2074
systemctl status "srv1cv8-$V@default" --no-pager
journalctl -u "srv1cv8-$V@default" --since "-1h" --no-pager | tail -100
journalctl -k --since "-1h" | grep -iE 'segfault|out of memory|killed process'
# ТЖ по умолчанию: в документации указаны оба каталога, смотрим оба
sudo sh -c 'ls -lt /home/usr1cv8/.1cv8/1C/1cv8/logs/*/ /home/usr1cv8/.1cv8/logs/*/ 2>/dev/null | head -20'
```

(`sudo sh -c '…'` нужен потому, что шаблон `*` должен раскрываться с правами root: домашний каталог `usr1cv8` обычному пользователю недоступен.)

## 1. Технологический журнал: назначение и принцип работы

Технологический журнал — набор текстовых файлов, в которые **каждый процесс 1С** на компьютере (сервер `ragent` / `rmngr` / `rphost`, клиенты `1cv8` / `1cv8c`, утилиты `ras`, `rac`, `ibcmd`, расширение веб-сервера) записывает сведения о своей работе `[офиц. 8.5.1]`. По ТЖ:

- служба поддержки 1С расследует ошибки платформы и аварийные завершения;
- администратор и эксперт по производительности ищут длительные запросы, ожидания на блокировках, взаимоблокировки, утечки памяти, причины исключений.

Ключевые свойства механизма `[офиц. 8.5.1]`:

- Настройка — один файл `logcfg.xml`. Файла по умолчанию нет; пока его нет, действует «ТЖ по умолчанию» (см. 2.3).
- Каждые **60 секунд** платформа опрашивает каталоги конфигурационных файлов, находит `logcfg.xml` и разбирает его. Изменения применяются без перезапуска приложений.
- Настройки ТЖ действуют на **все** процессы 1С, которые видят этот файл, а не только на сервер. Запуски `rac` из скриптов мониторинга тоже создают свои каталоги `rac_<PID>` `[практика]` — ограничивайте журнал условием по свойству `process` (см. 3.3).
- Состав событий и свойств меняется от версии к версии. Формат журнала не считается стабильным интерфейсом.

ТЖ — не то же самое, что журнал регистрации. ЖР хранит прикладные события информационной базы (вход, изменение данных, ошибки выполнения) и относится к конкретной базе; ТЖ — низкоуровневая трассировка работы платформы на конкретном компьютере.

## 2. Где лежит `logcfg.xml` на Linux и как он применяется

### 2.1. Каталоги и порядок поиска

Порядок поиска конфигурационных файлов (в том числе `logcfg.xml`, `nethasp.ini`, `debugcfg.xml`) на Linux `[офиц. 8.5.1, приложение 1.3.2]`:

| № | Каталог | Смысл |
|---|---|---|
| 1 | `/opt/1cv8/<arch>/<A.B.C.D>/conf` — например `/opt/1cv8/x86_64/8.3.27.2074/conf` | Настройки одной конкретной версии |
| 2 | `/opt/1cv8/conf` | Общие настройки для всех установленных версий и компонентов |
| 3 | `~/.1cv8/1C/1cv8/conf` | Настройки пользователя ОС, от имени которого работает процесс. Для сервера это `/home/usr1cv8/.1cv8/1C/1cv8/conf` |
| 4 | Каталог из параметра `ConfLocation` файла `conf.cfg` конкретной версии | Произвольное место |

Пояснения:

- Документация описывает именно порядок поиска и три сценария: «одна настройка на все версии — файл только в общем `conf`», «своя настройка для каждой версии — файл только в `conf` версии», «разные настройки для разных компонентов — пользовательские каталоги». Прямой фразы «берётся первый найденный файл» в документации нет, но описание параметра `ConfLocation` сформулировано именно так: это каталог, где файлы ищутся, «если они не найдены по стандартным путям поиска» `[офиц. 8.3.27, 3.17.2]`. Практический вывод тот же: держите **один** экземпляр `logcfg.xml`.
- Рекомендация для сервера: `/opt/1cv8/conf/logcfg.xml`. Каталог версии исчезает при удалении этой версии, а общий — нет. В инструкции 1С по сбору ТЖ в OpenSearch файл кладут в каталог версии — `/opt/1cv8/x86_64/<версия>/conf/logcfg.xml` `[офиц. ИТС 6019]`; это тоже работает, но после обновления платформы файл придётся переносить.
- В старых версиях (каталог установки `/opt/1C/v8.3/x86_64/`) файл лежал в `/opt/1C/v8.3/x86_64/conf`. Версионные каталоги `/opt/1cv8/<arch>/<версия>/` появились в 8.3.18, когда была реализована установка нескольких версий рядом `[офиц. V8Update]`.
- Пункт 3 в документации описан как каталог пользователя, «от имени которого работает клиентское приложение»; для сервера это домашний каталог `usr1cv8`.

Найти все экземпляры файла:

```bash
sudo find /opt/1cv8 /home/usr1cv8/.1cv8 -name logcfg.xml -o -name conf.cfg 2>/dev/null
```

### 2.2. Включение журнала: пошагово

```bash
# 1. Каталоги журнала: отдельный каталог на каждый <log>, владелец — пользователь сервера
sudo install -d -o usr1cv8 -g grp1cv8 -m 0750 /var/log/1c/tj/excp

# 2. Общий каталог настроек (если его нет)
sudo install -d -m 0755 /opt/1cv8/conf

# 3. Файл настроек: пишем во временный файл, проверяем XML, затем кладём на место одной операцией
sudo apt install -y libxml2-utils
xmllint --noout /tmp/logcfg.xml && sudo install -o root -g root -m 0644 /tmp/logcfg.xml /opt/1cv8/conf/logcfg.xml

# 4. Через 1–2 минуты появятся подкаталоги процессов
sudo ls -l /var/log/1c/tj/excp/
```

Требования и подводные камни:

- **Права.** Пользователь процесса должен иметь право записи в каталог журнала `[офиц. 8.5.1]` и право чтения самого `logcfg.xml`. Для Windows документация требует ещё и чтения каталога-владельца; на Linux по аналогии все каталоги пути должны быть проходимы (`x`) для `usr1cv8`.
- **Разные каталоги.** Значения `location` у всех `<log>`, у `<dump>` и у `<defaultlog>` должны различаться `[офиц. 8.5.1]`.
- **Только файлы ТЖ.** В каталоге журнала и в каталогах процессов, которые создаёт платформа, не должно быть никаких посторонних файлов — иначе журнал записываться не будет `[офиц. ИТС 5809]` (то же требование было в руководстве для ранних 8.3). Не кладите туда архивы, заметки и резервные копии `logcfg.xml`.
- **Не более 20 элементов `<log>`**: большее число заметно снижает производительность `[офиц. 8.5.1]`.
- **Ошибка в настройке** — платформа о ней не сообщает; в худшем случае на сервере перестаёт писаться вообще весь ТЖ `[офиц. ИТС 5809]`. Поэтому `xmllint --noout` перед установкой, а после каждой правки — подождать минуту и убедиться, что журнал действительно пишется так, как ожидалось.
- **Контролируйте рост.** После любой настройки ТЖ некоторое время следите за объёмом каталога `[офиц. ИТС 5809]` (команды — в 7.6).
- **Атомарная замена.** Платформа может прочитать файл в момент записи. Готовьте файл в стороне и подменяйте командой `install` или `mv`.
- **Отдельный раздел диска.** Переполнение корневого раздела журналом останавливает и сервер 1С, и PostgreSQL. Каталог ТЖ лучше держать на отдельном томе.

Выключение журнала — удалить или переименовать файл; через минуту запись прекратится:

```bash
sudo mv /opt/1cv8/conf/logcfg.xml /opt/1cv8/conf/logcfg.xml.off
```

### 2.3. Что действует без `logcfg.xml`

`[офиц. 8.5.1, 3.24.1; 8.3.27, 3.24.1, 3.24.2.11 и 6.14.3]`

| Параметр | Значение по умолчанию |
|---|---|
| Обычный ТЖ (`<log>`) | Выключен |
| ТЖ по умолчанию (`<defaultlog>`) | Включён, хранение 24 часа |
| Что пишется | События `SYSTEM` уровня `ERROR` для всех компонентов, все свойства |
| Каталог на Linux | В приложении 3 документации (3.24.1, 3.24.2.11) — `~/.1cv8/logs`; в главе 6 (6.14.3) — `~/.1cv8/1C/1cv8/logs`. Для сервера это `/home/usr1cv8/.1cv8/logs` и `/home/usr1cv8/.1cv8/1C/1cv8/logs` — проверяйте оба (⚠ документация расходится) |
| Каталог на Windows | `%LOCALAPPDATA%\1C\1cv8\logs` |
| Дампы | Только на Windows: минимальные, в `%LOCALAPPDATA%\1C\1cv8\dumps` |

Файлы ТЖ по умолчанию создаются только тогда, когда событие действительно произошло, поэтому каталог может быть пустым или отсутствовать.

Найти каталог ТЖ по умолчанию на сервере, не гадая:

```bash
sudo find /home/usr1cv8/.1cv8 -maxdepth 4 -type d -name logs -exec ls -ld {} +
```

### 2.4. Файл `conf.cfg`

`conf.cfg` лежит в каталоге `conf` конкретной версии и задаёт, в частности, параметр `ConfLocation` — каталог, в котором платформа ищет конфигурационные файлы (`logcfg.xml`, `nethasp.ini` и т. д.), если они не найдены по стандартным путям поиска. Значение по умолчанию на Linux — `/opt/1cv8/conf` `[офиц. 8.3.27, 3.17.2]`. Пример:

```ini
ConfLocation=/etc/1c/conf
```

## 3. Структура `logcfg.xml`

### 3.1. Каркас файла

`[офиц. 8.5.1, 3.24.2.1]`

```xml
<?xml version="1.0" encoding="UTF-8"?>
<config xmlns="http://v8.1c.ru/v8/tech-log">
  <log location="/var/log/1c/tj/main" history="24">
    <event>
      <eq property="name" value="EXCP"/>
    </event>
    <property name="all"/>
  </log>
  <!-- ещё <log>…</log> при необходимости -->
  <dump create="0"/>                 <!-- на Linux игнорируется -->
  <leaks collect="0"/>
  <mem/>
  <ftextupd logfiles="1"/>
  <query checkActualNullable="1"/>
  <plansql/>
  <dbmslocks/>
  <inputbystring/>
  <scriptcircrefs/>
  <sessiondatacontext/>
  <system level="error"/>
  <defaultlog location="/var/log/1c/tj/default" history="24"/>
</config>
```

**Не копируйте этот каркас на сервер как есть**: в нём для наглядности перечислены все элементы, в том числе генераторы, замедляющие работу (`<plansql/>`, `<mem/>`, `<scriptcircrefs/>`, `<sessiondatacontext/>`, `<query …/>`). В рабочий файл включают только нужные элементы; готовые варианты — в разделе 7.

Сколько раз элемент может встречаться `[офиц. 8.3.27, 3.24.2.1]`: `<log>` — один или несколько; `<system>` — ни одного, один или несколько; все остальные (`<dump>`, `<leaks>`, `<mem>`, `<plansql>`, `<dbmslocks>`, `<ftextupd>`, `<query>`, `<inputbystring>`, `<scriptcircrefs>`, `<sessiondatacontext>`, `<defaultlog>`) — не больше одного.

Элементы делятся на три группы `[офиц. 8.5.1]`:

| Группа | Элементы | Что делают |
|---|---|---|
| Размещение данных | `<log>` (несколько), `<defaultlog>` (один), `<dump>` (один) | Задают каталоги и срок хранения |
| Фильтры | `<event>`, `<property>` внутри `<log>` | Только **уменьшают** объём записи; добавить в журнал то, что не генерируется, не могут |
| Генераторы событий | `<dump>`, `<leaks>`, `<mem>`, `<plansql>`, `<ftextupd>`, `<system>`, `<query>`, `<scriptcircrefs>`, `<inputbystring>`, а также `<dbmslocks>`, `<sessiondatacontext>` | Включают сбор данных. Если элемента нет — событие или свойство не формируется, и фильтр по нему бесполезен |

### 3.2. Элемент `<log>`

`[офиц. 8.3.27 и 8.5.1, 3.24.2.2]`

| Атрибут | Значения | По умолчанию | Назначение |
|---|---|---|---|
| `location` | путь к каталогу | — | Каталог журнала. Должен отличаться от каталогов других `<log>`, `<dump>`, `<defaultlog>` |
| `history` | число часов | — | Через сколько часов файлы удаляются. `0` — автоудаление выключено, чистить придётся самому (значение `0` в этом смысле — с 8.3.25) |
| `format` | `text`, `json` | `text` | `json` — файл представляет собой последовательность JSON-объектов |
| `placement` | `folders`, `plain` | `folders` | `folders` — подкаталоги `<процесс>_<PID>`; `plain` — все файлы в одном каталоге |
| `rotation` | `period`, `size` | `period` | Признак смены файла: по времени или по размеру |
| `rotationperiod` | часы, минимум 1 | `1` | Период смены файла при `rotation="period"` |
| `rotationsize` | мегабайты, шаг 1 | `100` | Размер файла при `rotation="size"` |
| `compress` | `none`, `zip` | `none` | Сжимать файл при ротации (расширение `.zip`) |

Атрибуты `format`, `placement`, `rotation`, `rotationperiod`, `rotationsize`, `compress` реализованы в версии **8.3.25**; тогда же появились отключение автоудаления значением `history="0"` и свойство `level` у всех событий `[офиц. V8Update, раздел 8.3.25]`. В более старых версиях у `<log>` есть только `location` и `history`, а строки журнала не содержат `level=…`. В 8.3.27 удаление устаревших файлов ТЖ перенесено в фон и больше не блокирует работу пользователей (раньше при большом числе файлов могло блокировать) `[офиц. V8Update]`.

Внутри `<log>` находятся элементы `<event>` и `<property>`. **Если нет ни одного `<event>`, в журнал не пишется ничего** `[офиц. 8.5.1]`.

### 3.3. Элемент `<event>` и условия

`[офиц. 8.5.1, 3.24.2.3]`

Условие сравнения — элемент с атрибутами `property` (имя свойства события) и `value`:

| Элемент | Смысл |
|---|---|
| `eq` | равно |
| `ne` | не равно |
| `gt` | больше |
| `ge` | больше или равно |
| `lt` | меньше |
| `le` | меньше или равно |
| `like` | соответствует маске |

Логика:

- условия **внутри одного** `<event>` объединяются по **И**;
- **несколько** `<event>` объединяются по **ИЛИ**;
- событие попадает в журнал, если выполнены все условия хотя бы одного `<event>`.

Маска `like`:

| Шаблон | Значение |
|---|---|
| `%` | любое число любых символов, включая ноль |
| `_` | ровно один любой символ |
| `[...]` | один из перечисленных символов, допустимы диапазоны `a-z` |
| `[^...]` | любой символ, кроме перечисленных |
| `\` | экранирует следующий символ |

Сравнение по маске регистронезависимо. Фильтрация по маске медленнее остальных сравнений; сложные маски на нагруженном сервере снижают производительность.

Имена свойств в условиях нечувствительны к регистру. Часто используемые свойства для фильтров:

| Свойство | Пример условия | Комментарий |
|---|---|---|
| `name` | `<eq property="name" value="DBPOSTGRS"/>` | Имя события |
| `duration` | `<ge property="duration" value="10000"/>` | Длительность в **1/10000 с**; 10000 = 1 секунда |
| `durationus` | `<ge property="durationus" value="1000000"/>` | Длительность в микросекундах |
| `p:processName` | `<eq property="p:processName" value="buh"/>` | Имя серверного контекста, обычно имя информационной базы |
| `process` | `<eq property="process" value="rphost"/>` | Имя исполняемого файла процесса |
| `Usr` | `<eq property="usr" value="Иванов"/>` | Пользователь информационной базы |
| `level` | `<eq property="level" value="error"/>` | Уровень события |
| `func` | `<eq property="func" value="CommitTransaction"/>` | Действие, например для `SDBL` |

Условие «все события» из документации 1С:

```xml
<event>
  <ne property="name" value=""/>
</event>
```

### 3.4. Элемент `<property>`

`[офиц. 8.5.1, 3.24.2.4]`

- `<property name="all"/>` — записывать все свойства события. Это типовой вариант.
- `<property name="sql"/>` — записывать только названное свойство. Свойство, для которого нет элемента `<property>`, в журнал не попадает.
- Внутри `<property>` можно вложить `<event>` с условиями — тогда свойство пишется только для подходящих событий:

```xml
<property name="context">
  <event>
    <eq property="name" value="EXCP"/>
  </event>
</property>
```

Свойство `Context` (стек встроенного языка) записывается только если оно явно названо или действует `name="all"`.

Ещё правила `[офиц. 8.3.27, 3.24.2.4.1]`:

- `<property>` без вложенных `<event>` — свойство пишется для всех попавших в журнал событий, у которых оно есть; с вложенными `<event>` — только для событий, удовлетворяющих условию.
- У события может быть несколько свойств с одинаковыми именами.
- При записи контекста платформа добавляет его в само событие (контекст исполнения в текущем процессе), а сразу за ним пишет отдельное мгновенное событие с контекстом клиентского процесса — в журнале это строки с именем события `Context` `[офиц. 8.3.27; имя события — практика]`.

Как записать все свойства, **кроме** контекста (приём из примеров документации: условие с пустым именем события не выполняется никогда, поэтому свойство `context` не пишется, а `name="all"` включает остальные):

```xml
<property name="all"/>
<property name="context">
  <event>
    <eq property="name" value=""/>
  </event>
</property>
```

### 3.5. Элементы-генераторы

| Элемент | Что включает | Замечания |
|---|---|---|
| `<plansql/>` | Сбор планов запросов СУБД; план попадает в свойство `planSQLText` событий `DBPOSTGRS`, `DBMSSQL`, `DBORACLE`, `DB2`, `DBV8DBENG`, `EDS` | Замедляет выполнение запросов, для некоторых СУБД существенно. Только на время анализа `[офиц. 8.5.1]`; для PostgreSQL — **не на продуктивных серверах** `[офиц. ИТС 6011]`. Сбор включается для всех баз и всех запросов, а записываются планы только у событий, прошедших фильтры `[офиц. ИТС 5809]`. Для PostgreSQL и Oracle формат плана совпадает с форматом из документации СУБД. Вместе с `planSQLText` документация советует записывать и свойство `Sql`. ⚠ не подтверждено официально, каким способом платформа получает план для PostgreSQL; по практике в `planSQLText` видны фактические значения (`actual time`, `rows`, `loops`), то есть используется `EXPLAIN ANALYZE` и запрос выполняется дополнительно |
| `<dbmslocks/>` | Сбор сведений о блокировках СУБД; в события добавляются свойства `lka`, `lkp`, `lkpid`, `lkaid`, `lksrc`, `lkpto`, `lkato` | При обращениях к СУБД, но не чаще одного раза в 2 секунды, выполняется дополнительный запрос «кто кого блокирует» `[офиц. 8.3.27, 3.24.5]`. См. 4.5 |
| `<mem/>` | Событие `MEM`: рост числа и объёма невозвращённых фрагментов памяти серверных процессов между моментами простоя | Несколько снижает производительность, особенно при многих пользователях. Длительность события `MEM` — интервал между двумя последними моментами простоя процесса |
| `<leaks collect="1">` | Событие `LEAKS`: утечки памяти из-за кода конфигурации между контрольными точками `<point …/>` | Точки: `call="server"` или `call="client"`; `proc="ИмяМодуля/ИмяМетода"`; `on="ИмяМодуля/НомерСтроки" off="ИмяМодуля/НомерСтроки"`. Вложенные точки игнорируются; нумерация строк с 1; конечной точкой не может быть последняя строка процедуры |
| `<system level="…" component="…" class="…"/>` | События `SYSTEM` | Уровни по возрастанию значимости: `trace`, `debug`, `info`, `warning`, `error`, `none` (отключить). Без элемента — `error` для всех компонентов. Имена компонента и класса чувствительны к регистру. События `SYSTEM` попадают сразу во все настроенные журналы, включая журнал по умолчанию. Включать только по указанию поддержки: объём журнала резко растёт |
| `<query checkActualNullable="1"/>` | Событие `QERR` для полей с недопустимым `NULL` в запросах к внешним источникам данных | Сбор включает атрибут `checkActualNullable="1"` (`true`); при `0` или без элемента сведения не собираются. Может существенно замедлить выполнение запросов |
| `<ftextupd logfiles="1"/>` | Расширенные сведения об обновлении индекса полнотекстового поиска (`FTEXTUPD`): свойства `Files`, `FilesCount`, `FilesTotalSize`, `Folder` | `logfiles`: `1` (`true`) — включать, `0` (`false`) — нет |
| `<inputbystring/>` | Событие `INPUTBYSTRING` — сведения о вводе по строке | — |
| `<scriptcircrefs/>` | Событие `SCRIPTCIRCREFS` — циклические ссылки во встроенном языке | Сильно снижает производительность; только для целевого поиска. Выполнение прикладного решения не прерывается |
| `<sessiondatacontext/>` | Список операций изменения сеансовых данных (`SET`, `COPY`, `DELETE`) и их контексты; выводится в свойство `Context` события `CALL` в журнале менеджера кластера (`rmngr`) для методов `seanceParametersCommit` и `finishSeance` | С 8.3.23. Замедляет работу — только на время анализа роста сеансовых данных |
| `<systemmemoryprofile>` | Отслеживание использования памяти полнотекстовым поиском; данные попадают в события `SYSTEM` | С 8.3.26. Настройка и события не документированы, элемент предназначен для специалистов 1С `[офиц. V8Update]` |
| `<defaultlog location="…" history="…"/>` | Каталог и срок хранения ТЖ по умолчанию | `history="0"` отключает ТЖ по умолчанию. Фильтр фиксирован: `SYSTEM` уровня `error` |
| `<dump …/>` | Дампы аварийного завершения | **Только Windows.** На Linux и macOS игнорируется (атрибуты — в 9.1) |

Пример `<leaks>` (имена модулей пишутся так, как их показывает отладчик, без имени конфигурации: `ОбщийМодуль.<Имя>.Модуль`, `МодульСеанса.Модуль`, `Справочник.<Имя>.МодульОбъекта`, `Обработка.<Имя>.Форма.<ИмяФормы>.Форма`) `[офиц. 8.3.27, 3.24.2.6]`:

```xml
<leaks collect="1">
  <point call="server"/>
  <point proc="ОбщийМодуль.ОбщийМодуль1.Модуль/МояПроцедура"/>
  <point on="ОбщийМодуль.Сервисы.Модуль/9" off="ОбщийМодуль.Сервисы.Модуль/11"/>
</leaks>
```

Чтобы событие `LEAKS` попало в файл, в `<log>` должен быть отбор `<eq property="name" value="leaks"/>` (обычно вместе с `call`). В событии для каждого неосвобождённого объекта указан стек встроенного языка на момент его создания.

Примеры `<system>` из документации:

```xml
<system level="info"/>
<system level="debug" class="core::FileSystem"/>
<system level="warning" component="core82"/>
```

### 4.2. Запись контекста исключения (`EXCPCNTX`)

`[офиц. 8.5.1, 3.24.4]`

Контекст исключения — последовательность событий `EXCPCNTX`, перечисленных по убыванию уровня вложенности. Каждое из них — длительное событие, которое началось, но не завершилось к моменту аварии. Тип исходного события записывается в свойство `SrcName`. Условия записи:

1. журнал включён, то есть в `logcfg.xml` есть хотя бы один `<log>`;
2. произошла одна из ситуаций: исключение ОС с аварийным завершением процесса и формированием дампа либо исключение базы данных с сообщением об ошибке и завершением работы 1С.

Событие `EXCP` для ошибки базы данных пишется только при выполнении условий фильтра в `logcfg.xml`.

### 4.5. Сведения о блокировках СУБД (`<dbmslocks/>`)

`[офиц. 8.5.1 и 8.3.27, 3.24.5]`

Если в `logcfg.xml` есть `<dbmslocks/>`, то при обращениях к базе данных, но **не чаще одного раза в 2 секунды**, один рабочий процесс кластера выполняет дополнительный запрос к СУБД «кто кого заблокировал» (запросы нумеруются). Результат — пары «жертва — источник», где жертва — соединение с СУБД, ожидающее блокировку, а источник — соединение, установившее её. Сведения прикрепляются к контексту потока и выводятся как свойства **очередного события ТЖ, которое завершится в этом потоке**:

| Свойство | Значение | Пример |
|---|---|---|
| `lka` | `1` — поток является источником блокировки | `lka='1'` |
| `lkp` | `1` — поток является жертвой блокировки | `lkp='1'` |
| `lkpid` | Номер запроса «кто кого заблокировал», в котором поток найден жертвой | `lkpid='423'` |
| `lkaid` | Список номеров запросов, в которых поток найден источником | `lkaid='271,273,274'` |
| `lksrc` | Номер соединения источника (только у жертвы) | `lksrc='23'` |
| `lkpto` | Секунд с момента, когда поток обнаружен как жертва | `lkpto='15'` |
| `lkato` | Секунд с момента, когда поток обнаружен как источник | `lkato='21'` |

Данные жертвы сбрасываются после вывода, данные источника — при завершении или откате его транзакции. Порядок анализа из документации: в журналах `rphost` найти первое событие со свойствами `lka` и `lkp`, взять значения `lkaid` и `lkpid`, найти события с этими значениями в журналах всех рабочих процессов кластера и восстановить картину: кто кого блокировал, сколько времени и что происходило в этот период.

Дополнения:

- В первой редакции этой статьи стояло «не чаще раза в секунду» — так было прочитано в англоязычном тексте 8.5.1; в русской документации 8.3.27 указано «1 раз в 2 секунды», а сравнение редакций 8.5.1 и 8.3.27 изменений в этом разделе не показывает.
- Запрос выполняет «Сервис вспомогательных функций кластера»; в методической статье он приведён только для MS SQL Server (`SELECT spid, blocked FROM master.dbo.sysprocesses …`) `[офиц. ИТС 6006]`. ⚠ не подтверждено: каким запросом и насколько полно механизм работает с PostgreSQL — проверьте на стенде, появляются ли свойства `lk*`. Для PostgreSQL методика 1С опирается на журнал СУБД (`log_lock_waits = on`) и представления `pg_locks`, `pg_stat_activity` — см. статьи о PostgreSQL.
- Позиция разработчиков платформы: в управляемом режиме блокировок ожиданий на уровне PostgreSQL возникать не должно — только на управляемых блокировках; каждый воспроизводимый случай ожидания на уровне СУБД рекомендуется документировать и отправлять в поддержку `[офиц. ИТС 6006]`.
- В свойстве `Txt` события `TLOCK` может отображаться пространство имён, в котором наложена блокировка `[офиц. 8.3.27]`.

| `t:connectID` | Идентификатор соединения с информационной базой. Именно эти номера фигурируют в `WaitConnections` и `DeadlockConnectionIntersections` |

| `Context` | Контекст исполнения: стек встроенного языка (имя модуля, номер строки, текст строки) либо контекст интерфейса (форма, элемент, действие) |

ИТС 6011]`. Это код результата libpq: `PGRES_TUPLES_OK` — запрос вернул строки, `PGRES_COMMAND_OK` — команда выполнена без набора строк (второе значение — по документации PostgreSQL, в примерах 1С не встречалось).

ИТС 5809]`: таймаут — «Превышено максимальное время ожидания предоставления блокировки»; взаимоблокировка — «Неустранимый конфликт блокировок». ## 6. Формат файлов журнала

### 6.1. Каталоги и имена файлов

`[офиц. 8.3.27 и 8.5.1, 3.24.3.2–3.24.3.3]`

При настройках по умолчанию (`placement="folders"`, `rotation="period"`, `rotationperiod="1"`):

```
/var/log/1c/tj/main/
├── ragent_1203/
│   └── 26101014.log          # ГГММДДЧЧ.log — 10 октября 2026 г., час 14
├── rmngr_1257/
│   └── 26101014.log
├── rphost_1311/
│   ├── 26101013.log
│   └── 26101014.log
└── rac_20455/
    └── 26101014.log
```

- Подкаталог — `<имя процесса>_<PID>`: имя исполняемого файла (`1cv8`, `1cv8c`, `rphost`, …) и идентификатор процесса ОС.
- Имя файла — время создания, кратное периоду ротации, в формате `ГГММДДЧЧ`.
- Каждый перезапуск `rphost` порождает новый подкаталог, потому что меняется PID.

Общий шаблон имени `[офиц.]`: `appName_pid_timestamp.log.counter.zip`. Какие части присутствуют:

| Часть имени | Когда появляется | Пример |
|---|---|---|
| `appName_pid` | `placement="plain"` или `rotation="size"` | `ragent_18972.log` |
| `timestamp` | `placement="folders"` или `rotation="period"` | `23080116.log` |
| `.counter` | `rotation="size"`; меньший номер — более старый файл | `ragent_18972.log.1`, `ragent_18972.log.2` |
| `.zip` | `compress="zip"`; сжимается файл, ушедший в ротацию | `23080116.log.zip`, `ragent_18972.log.1.zip` |

Удаление по `history` `[офиц.]`: файлы, которые не использовались дольше заданного числа часов, удаляются; каталог, опустевший после удаления, тоже удаляется. Удаление выполняется только для приложений, запущенных в момент удаления. На практике после аварийных завершений в каталоге могут оставаться «осиротевшие» подкаталоги — страховочная очистка приведена в 7.7.

### 6.2. Формат записи (`format="text"`)

`[офиц. 8.3.27 и 8.5.1, 3.24.3.4]`

```
мм:сс.тттттт-д,<событие>,<вложенность>,<уровень>,<свойства>
```

| Поле | Значение |
|---|---|
| `мм` | Минута текущего часа |
| `сс` | Секунда текущей минуты |
| `тттттт` | Микросекунда текущей секунды |
| `д` | Длительность события в **микросекундах** |
| `<событие>` | Имя события (`CALL`, `DBPOSTGRS`, …) |
| `<вложенность>` | Уровень события в стеке текущего потока |
| `<уровень>` | Уровень события журнала; в файле записывается как первое свойство — `level=INFO`, `level=DEBUG` и т. д. (так в примере документации: `45:31.831006-1,SCALL,2,level=INFO,process=1cv8,…`). Появился в 8.3.25; в журналах более старых версий этого поля нет, сразу после вложенности идёт `process=…` |
| `<свойства>` | Пары `имя=значение` через запятую |

Правила, без которых журнал не разобрать:

- **Дата и час в строке отсутствуют** — они берутся из имени файла `ГГММДДЧЧ.log`.
- **Метка времени — момент окончания события.** Прямой фразы об этом в документации нет, но это следует из описаний событий: `SESN` с `Func=Wait` «выводится в момент окончания ожидания, длительность — время ожидания», `SDBL` с `Func=Transaction` «начинается при начале транзакции и заканчивается при её завершении», блокировочные свойства дописываются «к очередному событию, которое завершится в потоке» `[офиц. 8.3.27]`; то же видно в учебном примере 1С, где ожидавший 2 секунды `TLOCK` записан одновременно с `TDEADLOCK` `[офиц. ИТС 5809]`. Начало события = метка времени минус длительность. При поиске «что происходило в 14:45:31» учитывайте, что длинное событие будет записано позже, а события внутри файла идут в порядке окончания, а не начала.
- **Кавычки.** Если значение содержит запятую или перевод строки, оно заключается в апострофы или в двойные кавычки — выбирается тот символ, который реже встречается в значении. Такой же символ внутри значения удваивается `[офиц.]`. Встречаются оба варианта: в примере из методической статьи 1С `Sql="SELECT …"` записан в двойных кавычках, а `Context='…'` — в апострофах `[офиц. ИТС 6011]`; разбирающий скрипт обязан понимать и то и другое.
- **Многострочность.** Значения `Sql`, `planSQLText`, `Context`, `Descr`, `Locks` обычно содержат переводы строк, поэтому одно событие занимает несколько строк файла. Новое событие начинается со строки вида `^\d\d:\d\d\.\d+-\d+,`.
- **Кодировка и BOM.** Файлы пишутся в UTF-8 с меткой порядка байтов (`EF BB BF`). В методике 1С метку удаляют командой `perl -pe 's/\xef\xbb\xbf//g'`, «иначе она мешает при работе с разными кодировками» `[офиц. ИТС 5927]`. Из-за BOM первая строка файла не совпадает с шаблоном `^\d\d:\d\d` — метку нужно удалять.
- ⚠ не подтверждено: символ конца строки в файлах на Linux (`\n` или `\r\n`). В методике 1С, написанной на журналах Windows-сервера, склейка выполняется выражением `s/.\n/<line>/g` — точка перед `\n` «съедает» символ `\r`; на журнале с окончаниями `\n` такое выражение удалит последний значащий символ строки. Скрипты раздела 8 удаляют `\r` явно и работают в обоих случаях. Проверить свой журнал: `head -c 300 rphost_*/*.log | od -c | head`.

Иллюстрация (набор и порядок свойств зависят от версии платформы; значения условные):

```
45:31.830991-2177,DBPOSTGRS,5,level=DEBUG,process=rphost,p:processName=buh,OSThread=23514,t:clientID=412,t:applicationName=1CV8C,t:computerName=PC-07,t:connectID=18,SessionID=7,Usr=Иванов,DBMS=DBPOSTGRS,DataBase=pg01\buh,Trans=0,dbpid=40211,Sql='SELECT
T1._IDRRef
FROM _Reference45 T1
WHERE (T1._Fld628 = 0) AND (T1._Description LIKE ''Тест%'')',Rows=12,RowsAffected=-1,Result=PGRES_TUPLES_OK,Context='Форма.Вызов : Справочник.Номенклатура.Форма.ФормаСписка.Модуль.ПриСозданииНаСервере
Справочник.Номенклатура.Форма.ФормаСписка.Форма : 42 : Выборка = Запрос.Выполнить().Выбрать();'
45:31.831006-15625,CALL,1,level=INFO,process=rphost,p:processName=buh,OSThread=23514,t:clientID=412,t:applicationName=1CV8C,t:computerName=PC-07,t:connectID=18,SessionID=7,Usr=Иванов,Memory=1048576,MemoryPeak=4194304,InBytes=0,OutBytes=8192,CpuTime=12011
```

### 6.3. Отличия при `placement="plain"` и `format="json"`

`[офиц. 8.3.27 и 8.5.1]`

- `placement="plain"`: строка начинается с полной даты и времени в формате XML, затем через дефис идёт длительность в микросекундах, например `2023-08-01T15:01:45.259000-14998`. Остальная часть записи не меняется. **Скрипты раздела 8 рассчитаны на формат по умолчанию и с этим вариантом не работают** (в дате есть дефисы).
- `format="json"`: каждое событие — объект JSON. Безымянные поля получают имена: `ts` (дата и время с точностью до микросекунд), `duration` (микросекунды), `depth` (уровень в стеке потока), `name` (имя события); остальные свойства — обычные пары «ключ — значение» (`level`, `process`, `OSThread`, `CallID`, …). Такой журнал удобно отдавать в Vector, Filebeat, Fluent Bit или разбирать утилитой `jq`.

Пример записи JSON из документации `[офиц. 8.3.27, 3.24.3.4]`:

```json
{"ts":"2023-08-02T08:48:05.982000","duration":"46998","name":"SCALL","depth":"0","level":"INFO","process":"1cv8c","OSThread":"15968","ClientID":"8","Interface":"bc15bd01-10bf-413c-a856-ddc907fcd123","IName":"IVResourceRemoteConnection","Method":"0","CallID":"28284","MName":"send","DstClientID":"122"}
```

Обратите внимание: **все значения, включая `duration` и `depth`, — строки**, а регистр ключей свойств такой же, как в текстовом журнале (`OSThread`, `IName`, `CallID`). При числовых сравнениях в `jq` значения нужно приводить к числу (`tonumber`), см. 8.10.

Официальный пример настройки для выгрузки ТЖ во внешнюю систему (стенд 1С: Ubuntu 22.04, платформа 8.3.25+, fluent-bit → OpenSearch) `[офиц. ИТС 6019]`:

```xml
<?xml version='1.0' encoding='UTF-8'?>
<config xmlns="http://v8.1c.ru/v8/tech-log">
  <log location="/1c/logs" history="4" placement="plain" format="json">
    <event>
      <ne property="Name" value=""/>
    </event>
    <property name="all"/>
  </log>
</config>
```

В статье оговорено, что это тестовый сервер без нагрузки, поэтому собираются все события; на рабочем сервере отбор нужно сузить.

## 7. Готовые файлы `logcfg.xml`

### 7.1. Общие правила

- Во всех примерах каталоги нужно создать заранее с владельцем `usr1cv8:grp1cv8` (см. 2.2). Один `<log>` — один каталог.
- Сравнение значений в условиях нечувствительно к регистру у `like` `[офиц.]`; в примерах документации имена событий пишутся строчными (`proc`, `dbmssql`), так что `value="EXCP"` и `value="excp"` равнозначны.
- Чтобы ограничить журнал одной базой, добавьте в `<event>` условие `<eq property="p:processName" value="имя_базы"/>`. У событий `ragent` и `rmngr` этого свойства может не быть — они в такой журнал не попадут.
- После установки файла подождите не меньше минуты: настройки перечитываются раз в 60 секунд.

### 7.2. (а) Постоянный лёгкий журнал: только ошибки

Минимальный вариант — только исключения:

```xml
<?xml version="1.0" encoding="UTF-8"?>
<config xmlns="http://v8.1c.ru/v8/tech-log">
  <log location="/var/log/1c/tj/excp" history="168">
    <event>
      <eq property="name" value="EXCP"/>
    </event>
    <property name="all"/>
  </log>
</config>
```

Расширенный вариант для постоянной работы: исключения с контекстом, жизненный цикл процессов, мониторинг кластера, действия администратора, ошибки запросов, таймауты и взаимоблокировки. Все эти события редкие и небольшие.

```xml
<?xml version="1.0" encoding="UTF-8"?>
<config xmlns="http://v8.1c.ru/v8/tech-log">
  <log location="/var/log/1c/tj/errors" history="168">
    <event><eq property="name" value="EXCP"/></event>
    <event><eq property="name" value="EXCPCNTX"/></event>
    <event><eq property="name" value="PROC"/></event>
    <event><eq property="name" value="ATTN"/></event>
    <event><eq property="name" value="ADMIN"/></event>
    <event><eq property="name" value="QERR"/></event>
    <event><eq property="name" value="TTIMEOUT"/></event>
    <event><eq property="name" value="TDEADLOCK"/></event>
    <property name="all"/>
  </log>
</config>
```

Официальные ориентиры для постоянного журнала:

- **Минимальный журнал — на всех серверах** (тестовых, подготовительных, рабочих, серверах разработки): только `EXCP`. По нему оценивают число исключений по типам (`Descr`), находят причину падения процесса (последний файл в каталоге `rphost_<PID>` заканчивается событием `EXCP`, часто со стеком встроенного языка) и считают ошибки параллельной работы — таймауты и взаимоблокировки туда попадают всегда `[офиц. ИТС 5809]`.
- **Рекомендуемый по умолчанию для рабочих площадок**: `EXCP`, `CONN`, `PROC`, `ADMIN`, `SESN`, `CLSTR`, все свойства, `history="28"`. По оценке 1С, этого хватает для расследования до 80 % проблем платформы, а объём при нормальной работе — порядка пары сотен мегабайт в сутки (оценка грубая, зависит от нагрузки) `[офиц. ИТС 5809]`.
- **Вариант из руководства администратора** («действия администратора и ошибки»): `admin`, `conn`, `excp`, `proc`, `qerr`, `scom`, `history="168"` — «в большинстве случаев достаточно для расследования ошибок и в конфигурации, и в платформе» `[офиц. 8.3.27, 6.14.6.4]`.
- **Журнал длительных событий** — отдельным элементом `<log>` со своим каталогом; при нормальной работе он мал, и каждое событие в нём — повод для разбора. В первую очередь смотрят `SDBL` с `Func=CommitTransaction`: транзакция длиннее 20 секунд, скорее всего, держит блокировки и может быть виновником ошибок блокировок `[офиц. ИТС 5809]`:

```xml
<log location="/var/log/1c/tj/long" history="28">
  <event>
    <ne property="name" value=""/>
    <ge property="durationus" value="20000000"/>
  </event>
  <property name="all"/>
</log>
```

- Поскольку платформа удаляет журнал по истечении `history`, 1С советует раз в сутки копировать журналы со сжатием на другой ресурс средствами планировщика ОС и хранить архивы не на рабочем сервере `[офиц. ИТС 5809, 5927]`. Копировать нужно **из** каталога ТЖ наружу; сам каталог ТЖ посторонними файлами не засорять.

### 7.3. (б) Длительные запросы к PostgreSQL с планами

```xml
<?xml version="1.0" encoding="UTF-8"?>
<config xmlns="http://v8.1c.ru/v8/tech-log">
  <log location="/var/log/1c/tj/slowsql" history="24">
    <!-- duration измеряется в 1/10000 с: 20000 = 2 секунды -->
    <event>
      <eq property="name" value="DBPOSTGRS"/>
      <ge property="duration" value="20000"/>
    </event>
    <event>
      <eq property="name" value="SDBL"/>
      <ge property="duration" value="20000"/>
    </event>
    <property name="all"/>
  </log>
  <plansql/>
</config>
```

Пояснения:

- `<plansql/>` включает получение планов **для всех** запросов всех баз, а не только для тех, что прошли фильтр: «сбор планов включается на СУБД для всех баз, но записываются планы только для событий, прошедших фильтры» `[офиц. ИТС 5809]`. Фильтр уменьшает объём файла, но не накладные расходы на СУБД.
- **Для PostgreSQL методика 1С запрещает `<plansql/>` на продуктивных серверах** — только на серверах тестирования и разработки `[офиц. ИТС 6011]`. Руководство администратора мягче: планы «в обычном режиме не собирают, только на время анализа» `[офиц. 8.3.27, 3.24.2.10]`. На рабочем сервере безопаснее вариант без `<plansql/>`: журнал даёт текст запроса, `dbpid` и контекст, а план получают отдельно (см. ниже) либо через `auto_explain`.
- План в `planSQLText` для PostgreSQL имеет тот же вид, что и вывод `EXPLAIN` из документации PostgreSQL `[офиц. 8.5.1]`.
- **Как получить «платформенный» план без `<plansql/>`** `[офиц. ИТС 6011]`: взять текст запроса из свойства `Sql`, выполнить его в `psql` под `EXPLAIN ANALYZE VERBOSE`, предварительно выставив те же параметры сеанса, что и платформа. Внимание: `EXPLAIN ANALYZE` **реально выполняет** запрос — для `INSERT`/`UPDATE`/`DELETE` оборачивайте в `BEGIN; … ROLLBACK;` и работайте на копии базы.

```sql
/* параметры сеанса, которые устанавливает платформа 1С */
SET client_min_messages = error;
SET lc_messages TO 'en_US.UTF-8';
SET enable_mergejoin = off;
SET escape_string_warning = off;
SET cpu_operator_cost = 0.001;
SET client_encoding = 'utf8';
SET lock_timeout = 20000;

EXPLAIN ANALYZE VERBOSE
SELECT …;   -- текст из свойства Sql
```

```bash
psql -U postgres --dbname=<имя_базы> --file=query.sql > query.sqlplan
```

Если запрос использует временные таблицы (`tt1`, `tt2` …), их придётся воссоздать в том же файле; данные, вставленные платформой через `COPY … FROM STDIN`, в журналах не видны — в этом случае методика предлагает `auto_explain` на стороне PostgreSQL `[офиц. ИТС 6011]`.
- Событие `SDBL` показывает тот же запрос на уровне модели базы данных 1С и помогает сопоставить SQL с объектами метаданных.
- Эквивалентное условие в микросекундах: `<ge property="durationus" value="2000000"/>`.
- Альтернатива и дополнение со стороны СУБД — `log_min_duration_statement`, модули `auto_explain` и `pg_stat_statements` (см. статью о PostgreSQL для 1С). Они не знают контекста 1С (`Context`, `Usr`), зато не нагружают сервер приложений; связь с ТЖ — через `dbpid`.

### 7.4. (в) Управляемые блокировки, таймауты и взаимоблокировки

Вариант для расследования (пишутся все установки блокировок и границы транзакций). Состав событий совпадает с настройкой из методики 1С «Расследование ошибок блокировок»: `TLOCK`, `TTIMEOUT`, `TDEADLOCK` и `SDBL` с `Func` = `BeginTransaction` / `CommitTransaction` / `RollbackTransaction` `[офиц. ИТС 6006]`; здесь добавлен `EXCP`. Перечень данных для поддержки при таких ошибках: ТЖ с `EXCP`, `TLOCK`, `TTIMEOUT` (или `TDEADLOCK`) со всех серверов кластера, файл конфигурации с расширениями, копия `1CV8Clst.lst` `[офиц. ИТС 6005]`.

```xml
<?xml version="1.0" encoding="UTF-8"?>
<config xmlns="http://v8.1c.ru/v8/tech-log">
  <log location="/var/log/1c/tj/locks" history="24">
    <event><eq property="name" value="TLOCK"/></event>
    <event><eq property="name" value="TTIMEOUT"/></event>
    <event><eq property="name" value="TDEADLOCK"/></event>
    <event>
      <eq property="name" value="SDBL"/>
      <eq property="func" value="BeginTransaction"/>
    </event>
    <event>
      <eq property="name" value="SDBL"/>
      <eq property="func" value="CommitTransaction"/>
    </event>
    <event>
      <eq property="name" value="SDBL"/>
      <eq property="func" value="RollbackTransaction"/>
    </event>
    <event><eq property="name" value="EXCP"/></event>
    <property name="all"/>
  </log>
</config>
```

Почему нужны все `TLOCK`, а не только ожидавшие: виновник таймаута свою блокировку получил без ожидания, и найти строку кода, где он её установил, можно только по его собственному событию `TLOCK`. В методике 1С это сформулировано как правило: блокировки виновника нельзя искать в журналах, собранных с ограничением по длительности, — их там может не оказаться `[офиц. ИТС 6006]`. Журнал может быть большим; в примерах 1С для него задают `history="2"`–`"4"`.

Лёгкий вариант для постоянного наблюдения — только ожидания (значение `WaitConnections` непустое), таймауты и взаимоблокировки:

```xml
<?xml version="1.0" encoding="UTF-8"?>
<config xmlns="http://v8.1c.ru/v8/tech-log">
  <log location="/var/log/1c/tj/lockwait" history="72">
    <event>
      <eq property="name" value="TLOCK"/>
      <ne property="waitconnections" value=""/>
    </event>
    <event><eq property="name" value="TTIMEOUT"/></event>
    <event><eq property="name" value="TDEADLOCK"/></event>
    <property name="all"/>
  </log>
</config>
```

Вариант для блокировок на уровне СУБД (автоматический режим блокировок, ожидания внутри PostgreSQL):

```xml
<?xml version="1.0" encoding="UTF-8"?>
<config xmlns="http://v8.1c.ru/v8/tech-log">
  <log location="/var/log/1c/tj/dbmslocks" history="24">
    <event>
      <eq property="name" value="DBPOSTGRS"/>
      <ge property="duration" value="30000"/>
    </event>
    <event><eq property="name" value="EXCP"/></event>
    <event><eq property="name" value="EXCPCNTX"/></event>
    <property name="all"/>
  </log>
  <dbmslocks/>
</config>
```

Для обращения в поддержку по взаимоблокировкам и таймаутам **в СУБД** 1С просит журнал без отбора по длительности: `EXCP`, `EXCPCNTX`, `SDBL`, `DBPOSTGRS` со всех серверов кластера (в примере — с `<dbmslocks/>`), а для PostgreSQL дополнительно — журнал самого сервера СУБД `[офиц. ИТС 6005]`. Отбор по длительности из примера выше годится для самостоятельного наблюдения, но, как и в случае управляемых блокировок, прячет запросы «виновника».

Вариант для расследования высокой загрузки процессора сервером 1С — исключения и серверные вызовы с ненулевым процессорным временем `[офиц. ИТС 6005]`:

| Взаимоблокировки / таймауты в СУБД | `EXCP`, `EXCPCNTX`, `SDBL`, `DB*` | `<dbmslocks/>`; журнал PostgreSQL |
| Конкретный медленный запрос | `EXCP`, `SDBL`, `DB*` | `<plansql/>`, `<dbmslocks/>` — на стенде |
| Нагрузка на диск сервера 1С | `EXCP`, `CALL`, `SCALL` | — |

### 7.7. Ротация и очистка

- `history` задаётся **в часах**: `history="24"` — сутки, `history="168"` — неделя. Удаляются файлы, не использовавшиеся дольше этого срока, вместе с опустевшими каталогами.
- `history="0"` у `<log>` отключает автоудаление; у `<defaultlog>` — отключает сам ТЖ по умолчанию `[офиц. 8.5.1]`.
- Смена файла по умолчанию — раз в час. Начиная с 8.3.25 можно менять период (`rotationperiod`), перейти на ротацию по размеру (`rotation="size" rotationsize="100"`) и сжимать ушедшие в ротацию файлы (`compress="zip"`). Сжатые файлы читаются командой `unzip -p файл.log.zip` (пакет `unzip`). Пример:

```xml
<log location="/var/log/1c/tj/errors" history="720" rotation="period" rotationperiod="24" compress="zip">
  <event><eq property="name" value="EXCP"/></event>
  <property name="all"/>
</log>
```

- `logrotate` для ТЖ не нужен и вреден: платформа сама управляет файлами.
- Страховочная очистка «осиротевших» каталогов завершившихся процессов `[практика]`. Срок в минутах должен быть больше самого большого `history`:

```bash
# /etc/cron.d/1c-tj-clean — раз в час удалять файлы старше 8 суток и пустые каталоги процессов
17 * * * * root find /var/log/1c/tj -type f \( -name '*.log' -o -name '*.log.*' \) -mmin +11520 -delete; find /var/log/1c/tj -mindepth 2 -type d -empty -delete
```

## 8. Анализ технологического журнала в bash

Приёмы этого раздела — общепринятая методика анализа ТЖ (в стиле курса «1С:Эксперт по технологическим вопросам»). Её основа опубликована самой фирмой «1С»: статья «Анализ технологических журналов с помощью инструментов bash» `[офиц. ИТС 5927]` и шаблоны perl-скриптов в статье «Мониторинг на продукционных серверах» `[офиц. ИТС 5809]`; официальные однострочники приведены в 8.12. Функции `tj1`/`tj1h` и сценарии 8.3–8.9 — авторская переработка тех же приёмов под PostgreSQL и под оба варианта конца строки `[практика]`. Команды рассчитаны на формат по умолчанию (`format="text"`, `placement="folders"`). **Сценарии проверены чтением, но не прогонялись на реальных журналах — проверьте на копии.** Нужны `grep` с поддержкой `-P`, `sed`, `awk` (подойдёт и `mawk` из поставки Ubuntu) и `perl` — всё это есть в Ubuntu Server.

Общие советы:

- Работайте в каталоге журнала: `cd /var/log/1c/tj/full`. Если каталог недоступен обычному пользователю, работайте с копией журнала (и не создавайте файлов внутри каталога ТЖ — результаты пишите в другое место).
- Ключ `grep -a` заставляет считать файл текстом, даже если в нём встретились «двоичные» байты.
- Для больших журналов сначала отфильтруйте нужный час (`rphost_*/26101014.log`) и нужное событие, потом агрегируйте. Правила 1С: отбирать строки как можно ближе к началу конвейера, не оперировать миллионами строк, помнить о цене сортировки; при отладке ставить `head` сразу после первого `|`; время измерять командой `time` `[офиц. ИТС 5927]`.
- Суммы длительностей разных событий складывать нельзя: события вложены друг в друга (`CALL` включает `SDBL`, тот включает `DBPOSTGRS`).
- Универсальная схема «топ-5 чего угодно» `[офиц. ИТС 5927]`: отбор событий нужного типа → отрезать всё до длительности → привести ключ группировки (контекст, текст запроса, `Regions`) к нормальному виду → `awk` (сумма, среднее, количество) → `sort -rnb | head -n 5`.

### 8.1. Быстрые проверки без склейки

```bash
# Сколько событий каждого типа (BOM в начале файлов убирается, чтобы первая строка тоже считалась)
cat rphost_*/*.log | LC_ALL=C sed 's/^\xEF\xBB\xBF//' | grep -aoP '^\d\d:\d\d\.\d+-\d+,\K\w+' | sort | uniq -c | sort -rn

# Сколько исключений в каждом файле (по часам и процессам)
grep -ac ',EXCP,' */*.log | grep -v ':0$'

# В каких файлах встречается текст ошибки
grep -arl 'Недостаточно памяти' .

# События одного соединения за нужную минуту (строки-продолжения сюда не попадут)
grep -a '^45:' rphost_*/26101014.log | grep -a ',t:connectID=18,'
```

### 8.2. Склейка многострочных событий

Все дальнейшие приёмы опираются на две функции. Сохраните их в файл, например `~/tj.sh`, и подключайте командой `source ~/tj.sh`.

```bash
# tj1: одно событие — одна строка; переводы строк внутри события заменяются на "<line>".
# Использование: tj1 rphost_*/*.log | ...     или     zcat архив.log.gz | tj1 | ...
tj1() {
  cat -- "$@" | LC_ALL=C sed -e 's/^\xEF\xBB\xBF//' -e 's/\r$//' |
  awk '/^[0-9][0-9]:[0-9][0-9]\.[0-9]+-[0-9]+,/ { if (n++) printf "\n"; printf "%s", $0; next }
       { printf "<line>%s", $0 }
       END { if (n) printf "\n" }'
}

# tj1h: то же, но перед каждой строкой ставится час из имени файла: "26101014:45:31.830991-2177,..."
# Нужна, чтобы склеивать и сортировать по времени события разных часов и разных процессов.
tj1h() {
  local f
  for f in "$@"; do
    LC_ALL=C sed -e '1s/^\xEF\xBB\xBF//' -e 's/\r$//' "$f" |
    awk -v h="$(basename "${f%.log}")" '
      /^[0-9][0-9]:[0-9][0-9]\.[0-9]+-[0-9]+,/ { if (n++) printf "\n"; printf "%s:%s", h, $0; next }
      { printf "<line>%s", $0 }
      END { if (n) printf "\n" }'
  done
}
```

Как это работает:

- `sed` удаляет метку BOM (`EF BB BF`) в начале файла и символ `\r` в конце строк.
- `awk` считает началом события строку, которая начинается с `мм:сс.микросекунды-длительность,`. Перед каждым новым событием (кроме первого) печатается перевод строки; строки-продолжения приклеиваются через маркер `<line>`.
- После склейки можно применять обычные `grep`, `sort`, `uniq`, а исходные переводы строк при необходимости возвращаются командой `sed 's/<line>/\n/g'`.

Проверка склейки: число событий должно совпасть с числом строк.

```bash
tj1 rphost_*/26101014.log | wc -l
cat rphost_*/26101014.log | LC_ALL=C sed 's/^\xEF\xBB\xBF//' | grep -acP '^\d\d:\d\d\.\d+-\d+,'
```

Хронологическая лента по всем процессам (помните: время в строке — момент окончания события):

```bash
tj1h */2610101[34].log | sort | less -S
```

### 8.3. Топ по суммарной длительности

По типам событий:

```bash
tj1 rphost_*/*.log | awk -F'[-,]' '{ d[$3] += $2; c[$3]++ }
  END { for (e in d) printf "%12.1f с %10d шт  %s\n", d[e]/1000000, c[e], e }' | sort -rn | head -20
```

Разделитель полей — дефис или запятая, поэтому `$2` — длительность в микросекундах, `$3` — имя события.

Как читать результат `[офиц. ИТС 6011]`: отношение суммарного времени `DBPOSTGRS` к суммарному времени `CALL` показывает, какую долю времени серверных вызовов занимают запросы к СУБД. Если доля больше примерно 50 % — разбираться нужно со скоростью запросов (в примере 1С: `DBPOSTGRS` 22 189 998 668 мкс, `CALL` 33 908 470 608 мкс, отношение ≈ 0,65). Вариант той же команды из статьи 1С — без склейки, по сырым строкам (строки-продолжения дают «мусорные» ключи, которые при чтении результата просто игнорируют):

```bash
cat rphost_*/*.log | awk -F\- '{print $2}' | awk -F\, '{sum[$2]+=$1;} END {for (event in sum) print event" - "sum[event];}'
```

По пользователям (суммарная длительность серверных вызовов):

```bash
tj1 rphost_*/*.log | grep -a ',CALL,' | perl -ne '
  next unless /^(?:\d{8}:)?\d\d:\d\d\.\d+-(\d+),/; $d = $1;
  $u = /,Usr=([^,]*)/ ? $1 : "-";
  $t{$u} += $d; $c{$u}++;
  END { for (sort { $t{$b} <=> $t{$a} } keys %t) { printf "%10.1f с %8d шт  %s\n", $t{$_}/1e6, $c{$_}, $_ } }' | head -20
```

Самые длительные отдельные события (например, запросы):

```bash
tj1 rphost_*/*.log | grep -a ',DBPOSTGRS,' | awk -F'[-,]' '{ print $2 "\t" $0 }' | sort -rn | head -5 | cut -c1-1500 | sed 's/<line>/\n/g'
```

### 8.4. Группировка запросов по нормализованному тексту

Одинаковые по смыслу запросы различаются именами временных таблиц (`tt1`, `tt25`), значениями параметров и ссылок. Перед группировкой текст нормализуют.

```bash
tj1 rphost_*/*.log | grep -a ',DBPOSTGRS,' | perl -ne '
  next unless /^(?:\d{8}:)?\d\d:\d\d\.\d+-(\d+),/; $d = $1;
  next unless /,Sql=(\x27(?:[^\x27]++|\x27\x27)*+\x27|"(?:[^"]++|"")*+"|[^,]*)/; $s = $1;
  if    ($s =~ s/^\x27(.*)\x27$/$1/s) { $s =~ s/\x27\x27/\x27/g }   # снять внешние апострофы
  elsif ($s =~ s/^"(.*)"$/$1/s)       { $s =~ s/""/"/g }             # или внешние кавычки
  $s =~ s/<line>/ /g;                         # переводы строк
  $s =~ s/\x27[^\x27]*\x27(?:::\w+)?/?/g;     # строковые и bytea-литералы
  $s =~ s/\btt\d+\b/ttN/gi;                   # имена временных таблиц
  $s =~ s/\b\d+(?:\.\d+)?\b/N/g;              # числовые литералы
  $s =~ s/\s+/ /g;
  $t{$s} += $d; $c{$s}++;
  END { for (sort { $t{$b} <=> $t{$a} } keys %t) {
          printf "%10.1f с %8d шт  %s\n", $t{$_}/1e6, $c{$_}, substr($_, 0, 400);
          last if ++$n >= 20 } }'
```

Что делает сценарий:

- `\x27` — это апостроф; такая запись позволяет держать весь сценарий в одинарных кавычках оболочки.
- Значение `Sql` извлекается с учётом правил кавычек ТЖ: значение в апострофах (внутренние апострофы удвоены), значение в двойных кавычках либо значение без кавычек до ближайшей запятой.
- Шаблон `\b\d+\b` не затрагивает цифры внутри идентификаторов (`_Reference45`, `T1`, `_Fld628`), потому что между буквой и цифрой нет границы слова.
- Результат: суммарное время, число выполнений и первые 400 символов нормализованного текста для 20 самых «дорогих» запросов.

### 8.5. Группировка по контексту (строке кода)

Последняя строка `Context` — та строка встроенного языка, которая породила событие.

```bash
tj1 rphost_*/*.log | grep -a ',DBPOSTGRS,' | perl -ne '
  next unless /^(?:\d{8}:)?\d\d:\d\d\.\d+-(\d+),/; $d = $1;
  $x = /,Context=(\x27(?:[^\x27]++|\x27\x27)*+\x27|"(?:[^"]++|"")*+"|[^,]*)/ ? $1 : "";
  $x =~ s/^[\x27"]|[\x27"]$//g;
  @l = grep { /\S/ } split /<line>/, $x;
  $k = @l ? $l[-1] : "(контекст не записан)"; $k =~ s/^\s+//;
  $t{$k} += $d; $c{$k}++;
  END { for (sort { $t{$b} <=> $t{$a} } keys %t) {
          printf "%10.1f с %8d шт  %s\n", $t{$_}/1e6, $c{$_}, $_;
          last if ++$n >= 20 } }'
```

Чтобы группировать по первой строке контекста (точке входа: обработчику формы, регламентному заданию), замените `$l[-1]` на `$l[0]`. Тот же сценарий подходит для `SDBL`, `TLOCK`, `EXCP` — меняется только шаблон в `grep`.

### 8.6. Причины `TTIMEOUT`: жертва и виновник

Шаг 1. Список таймаутов: время, соединение-жертва, соединения-виновники, пользователь, контекст жертвы.

```bash
tj1 rphost_*/*.log | grep -a ',TTIMEOUT,' | perl -ne '
  ($ts)  = /^(\S+?)-\d+,/;
  ($vic) = /,t:connectID=(\d+)/;
  ($cul) = /,WaitConnections=(\x27[^\x27]*\x27|"[^"]*"|[^,]*)/;
  ($usr) = /,Usr=([^,]*)/;
  ($ctx) = /,Context=(.*)$/; $ctx = "" unless defined $ctx; $ctx =~ s/<line>\s*/ | /g;
  printf "%s  жертва=%s  виновники=%s  Usr=%s\n    %s\n", $ts, $vic // "?", $cul // "?", $usr // "?", substr($ctx, 0, 300);'
```

- **Жертва** (ожидающая транзакция) — соединение, в журнале которого записано событие `TTIMEOUT`: его номер в свойстве `t:connectID`. Жертва потратила ненулевое время, дожидаясь возможности установить блокировку.
- **Виновники** (ожидаемые транзакции) — номера соединений из свойства `WaitConnections`. `WaitConnections` содержит значение `t:connectID` того соединения, которого пришлось ждать; `t:connectID` не меняется в пределах транзакции. Виновник мог установить свою блокировку сразу, без ожидания `[офиц. ИТС 6006]`.

Быстрый поиск ожиданий без склейки (команды из методики 1С, выполняются в каталоге журнала) `[офиц. ИТС 6006]`:

```bash
grep -rP 'TLOCK.*WaitConnections=\d+'                 # все TLOCK, которым пришлось ждать
grep -rP '\d{6,},TLOCK.*WaitConnections=\d+'          # ожидания длительностью от 0,1 с (шесть и более цифр в длительности)
# блокировки виновника (соединение 16) по тому же пространству и тем же значениям полей:
grep -rP 'TLOCK.*t:connectID=16,.*InfoRg404.DIMS.*Fld405=4216B7C0FEBDF74182BCEFF80930A8AD'
```

Шаг 2. Лента событий жертвы и виновника за нужный час: блокировки и границы транзакций.

```bash
VIC=18; CUL=17; H=26101014        # номера соединений из шага 1 и час (имя файла)
tj1 rphost_*/$H.log | grep -aP ",t:connectID=($VIC|$CUL)," |
  grep -aiP ',(TLOCK|TTIMEOUT|TDEADLOCK),|,SDBL,.*Func=(Begin|Commit|Rollback)Transaction' |
  sort | cut -c1-900 | less -S
```

Шаг 3. Как читать ленту:

1. У жертвы найдите `TTIMEOUT` и записанный рядом с ним `TLOCK`: свойства `Regions` и `Locks` показывают, какое пространство блокировок и с какими значениями полей она не смогла заблокировать. Длительность ожидания близка к «времени ожидания блокировки данных» из параметров информационной базы (Конфигуратор → Администрирование → Параметры информационной базы; по умолчанию 20 секунд).
2. У виновника найдите **последний `TLOCK` до момента таймаута**, у которого то же пространство в `Regions` и пересекающиеся значения в `Locks`, причём режимы несовместимы (`Exclusive` несовместим ни с чем, `Shared` — только с `Exclusive`). Свойство `Context` этого события указывает строку кода, установившую блокировку.
3. По событиям `SDBL` с `Func=BeginTransaction`, `CommitTransaction` или `RollbackTransaction` у виновника определите, сколько длилась его транзакция и что в ней занимало время (для этого нужен журнал с `DBPOSTGRS` и `CALL`).
4. Типовые причины: длинная транзакция (запросы, обращения к внешним ресурсам или диалог с пользователем внутри транзакции), избыточная блокировка (заблокировано больше, чем нужно — не по всем измерениям), разный порядок захвата ресурсов.

Правила, которые методика 1С советует держать в голове `[офиц. ИТС 6006]`:

- управляемые блокировки удерживаются до конца транзакции;
- блокировки в рамках одной транзакции совместимы между собой;
- блокировки по разным пространствам или по разным данным совместимы;
- блокировки совместимых типов совместимы (`Shared` с `Shared`);
- пропущенное в блокировке измерение пространства равносильно блокировке всех его значений;
- пути решения всего два: убрать избыточную блокировку (пересмотреть гранулярность) или сократить время её удержания (укоротить транзакцию-виновника, установить блокировку ближе к концу транзакции). Просто «убрать блокировку» нельзя — она обеспечивает целостность данных.

ЦУП выполняет то же расследование автоматически (кнопка «Анализ» по показателям групп «Только блокировки 1С» и «Анализ»); при нехватке времени или опыта 1С рекомендует именно его `[офиц. ИТС 6006]`.

### 8.7. Причины `TDEADLOCK`

```bash
tj1 rphost_*/*.log | grep -a ',TDEADLOCK,' | perl -ne '
  ($ts) = /^(\S+?)-\d+,/;
  ($c)  = /,t:connectID=(\d+)/;
  ($i)  = /,DeadlockConnectionIntersections=(\x27[^\x27]*\x27|"[^"]*"|[^,]*)/;
  ($ctx) = /,Context=(.*)$/; $ctx = "" unless defined $ctx; $ctx =~ s/<line>\s*/ | /g;
  print "$ts  соединение=", $c // "?", "\n  пересечения: ", $i // "?", "\n  контекст: ", substr($ctx, 0, 300), "\n";'
```

- `DeadlockConnectionIntersections` — список пар транзакций, образующих взаимоблокировку `[офиц. 8.5.1]`. Формат виден в учебном примере 1С `[офиц. ИТС 5809]`: элементы разделены запятыми, каждый имеет вид `<соединение> <соединение> <пространство> <режим> <поля=значения>` — пара номеров `t:connectID` (кто кого ждёт), затем пространство блокировок, режим и значения полей, на которых транзакции пересеклись:

```text
11:05.519001-0,TDEADLOCK,5,process=rphost,...,t:connectID=17,SessionID=10,...,DeadlockConnectionIntersections='17 16 InfoRg10.DIMS Exclusive Fld11="Test1" Fld12="Test2",16 17 InfoRg10.DIMS Exclusive Fld11="Test1" Fld12="Test2"',Context='... ВторойУчастникНаСервере ... : 58 : НаборЗаписейРегистрСведений1.Записать();'
11:05.519003-16002,TLOCK,4,process=rphost,...,t:connectID=17,...,Regions=InfoRg10.DIMS,Locks='InfoRg10.DIMS Exclusive Fld11="Test1" Fld12="Test2"',WaitConnections=16,Context='... : 58 : НаборЗаписейРегистрСведений1.Записать();'
11:05.519024-1997023,TLOCK,4,process=rphost,...,t:connectID=16,...,Regions=InfoRg10.DIMS,Locks='InfoRg10.DIMS Exclusive Fld11="Test1" Fld12="Test2"',WaitConnections=17,Context='... : 26 : НаборЗаписейРегистрСведений1.Записать();'
```

- В этом примере `TDEADLOCK` записан в журнале соединения 17 — того, чья попытка установить блокировку замкнула цикл ожидания и чья транзакция получила ошибку «Неустранимый конфликт блокировок»; соединение 16 после этого получило свою блокировку (его `TLOCK` завершился спустя 2 секунды ожидания с `WaitConnections=17`). То есть событие пишется у **жертвы** — это следует из примера, прямой формулировки в документации нет.
- Порядок разбора по методике 1С `[офиц. ИТС 5809]`: (1) найти `TDEADLOCK` и выписать `DeadlockConnectionIntersections` — объект, режим, значения полей и номера соединений-участников; (2) выше по журналу найти события `TLOCK` тех же соединений — по ним видно, какие блокировки каждый участник уже удерживал (в примере оба сначала получили `Shared` при чтении набора записей) и из какой строки кода; (3) найти `TLOCK` с попыткой несовместимой блокировки и непустым `WaitConnections` — кто кого ждал.
- Что нужно знать о поведении платформы: при чтении набора записей в транзакции платформа сама ставит разделяемую управляемую блокировку, при записи — исключительную; снимаются они только в конце внешней транзакции. Учебный случай называется «повышение уровня блокировки ресурса в рамках одной транзакции»; исправление — сразу ставить блокировку максимально необходимого уровня (явная исключительная блокировка перед чтением) `[офиц. ИТС 5809, 4051]`. Второй типовой случай — захват ресурсов в разном порядке; лечение — единый порядок захвата.
- Сценарий из 8.6 (шаг 2) с номерами соединений из пересечений даёт нужную ленту событий обоих участников.
- Для взаимоблокировок на уровне PostgreSQL событие `TDEADLOCK` не формируется: появляется `EXCP` с текстом ошибки СУБД (`deadlock detected`), а подробности ищут в журнале PostgreSQL и по свойствам `lk*` (см. 4.5).

### 8.10. Журнал в формате JSON

Если журнал пишется с `format="json"`, склейка не нужна — подойдёт `jq` (`sudo apt install jq`). Имена ключей совпадают с именами свойств текстового журнала, включая регистр (в примере документации — `OSThread`, `IName`, `CallID`), а **все значения — строки**, в том числе `duration` и `depth` `[офиц. 8.3.27, 3.24.3.4]`. Поэтому числа перед сравнением приводят через `tonumber`: в `jq` любая строка считается «больше» любого числа, и условие `.duration > 1000000` без приведения выполнялось бы всегда. Точное написание ключей для событий СУБД (`Sql`, `Usr`, `Context`) проверьте в своём файле: `head -3 файл.log | jq 'keys'`.


## 9. Дампы и аварийные завершения на Linux

### 9.1. Что говорит документация 1С

`[офиц. 8.5.1, 3.24.2.5]`

- Элемент `<dump>` в `logcfg.xml` работает **только на Windows**. На Linux и macOS формированием дампов управляет ОС, элемент игнорируется. Атрибуты `location`, `create`, `type`, `prntscrn`, `externaldump` на Linux значения не имеют.
- По умолчанию дампы в Linux отключены. По словам документации, поставщики дистрибутивов советуют включать их только на машинах разработки, а не на рабочих.
- Рекомендации документации (оговорено, что они написаны для Fedora Core 4 и подобных систем):

```
# /etc/security/limits.conf — для пользователя, от имени которого работает 1С
usr1cv8 soft core unlimited
usr1cv8 hard core unlimited
```

```bash
# шаблон имени и место хранения дампов; действует на все процессы всех пользователей
sysctl -w kernel.core_pattern=/tmp/core.%e.%p           # до перезагрузки
# постоянно: строка kernel.core_pattern=/tmp/core.%e.%p в /etc/sysctl.conf, затем sysctl -p
```

- Настройка кластера «Записывать дамп процесса при превышении критического объёма памяти»: дамп формируется по действующим в ОС настройкам аварийных дампов `[офиц. 8.5.1, свойства кластера]`.
- **Сигналы** `[офиц. 8.3.27, глава 2 «Клиент-серверный вариант», мониторинг кластера]`: в Linux обычный дамп аварийного завершения формируется по сигналу `SIGSEGV`; когда кластер принудительно завершает процесс с записью дампа (превышение критического объёма памяти), он посылает процессу `SIGABRT`. До версии 8.3.27 механизм мониторинга тоже использовал `SIGSEGV`; сигнал заменили, чтобы поддержка могла отличать дампы, созданные мониторингом, от дампов из-за критических ошибок `[офиц. V8Update 8.3.27]`. В журнале ядра и в выводе `coredumpctl` это видно по номеру сигнала: 11 — `SIGSEGV`, 6 — `SIGABRT`.
- Дампы, которые 1С просит снять **с работающего** процесса (зависание, рост памяти), делаются утилитой `gcore` `[офиц. ИТС 5985]` — см. 9.7 и 9.8.

Атрибуты `<dump>` — справочно, **действуют только в Windows** `[офиц. 8.3.27, 3.24.2.5.4]`:

| Атрибут | Значения |
|---|---|
| `create` | `0` (`false`) — не создавать дамп, `1` (`true`) — создавать |
| `location` | Каталог дампов; должен отличаться от каталогов `<log>` и `<defaultlog>`. Без элемента `<dump>` — `%LOCALAPPDATA%\1C\1cv8\dumps` |
| `type` | Сумма флагов (десятичное число или шестнадцатеричное с префиксом `x`): `0` — минимальный; `1` — дополнительный сегмент данных; `2` — вся память процесса; `4` — данные хэндлов; `8` — только сведения для восстановления стеков; `16` — если стек ссылается на память модулей, добавить флаг 64; `32` — память из-под выгруженных модулей; `64` — память, на которую есть ссылки; `128` — подробные сведения о файлах модулей; `256` — локальные данные потоков; `512` — всё доступное виртуальное адресное пространство. В большинстве случаев достаточно `type="3"` |
| `prntscrn` | `1` — сохранять снимок экрана клиента (`.png` рядом с дампом), `0` — нет |
| `externaldump` | `1` — дамп формирует внешняя программа `dumper.exe` из поставки (исключает зависание при создании дампа), `0` — сам процесс (по умолчанию). В Linux утилиты `dumper` нет |

В методических статьях 1С для Windows-серверов встречается `<dump create="true" location="…" type="3" prntscrn="false" externaldump="false"/>` `[офиц. ИТС 6005]` — на Linux такая строка в `logcfg.xml` безвредна, но ничего не делает.

Как это ложится на современную Ubuntu:

| Рекомендация документации | Что на Ubuntu 22.04–26.04 |
|---|---|
| `limits.conf` | Действует только на сеансы PAM (вход по SSH, `su`, `sudo -i`). **На службу systemd не действует** — для неё лимит задаётся директивой `LimitCORE=` в юните |
| `kernel.core_pattern=/tmp/…` | По умолчанию шаблон занят apport. Кроме того, путь из шаблона раскрывается в окружении упавшего процесса («Paths are interpreted according to the settings that are active for the crashing process») `[офиц. core(5)]`: если в юните сервера 1С задано `PrivateTmp=true`, файл окажется в частном `/tmp` службы (на хосте это `/tmp/systemd-private-…/tmp`). Используйте каталог вне `/tmp` |
| «Дампы только на машинах разработки» | Дамп `rphost` занимает столько же, сколько его память — гигабайты и десятки гигабайт. На рабочем сервере нужен отдельный том и контроль места |

### 9.2. Условия появления дампа и проверка текущего состояния

Дамп **не создаётся**, если `[офиц. core(5)]`: лимит `RLIMIT_CORE` (или `RLIMIT_FSIZE`) равен нулю — кроме случая, когда `core_pattern` начинается с `|`: тогда лимит ядром не применяется, но обработчик может его учитывать (apport при нулевом лимите файл не пишет, `systemd-coredump` обрабатывает дамп «только при достаточных лимитах»); у процесса нет права записи в каталог либо каталог не существует; файловая система заполнена или смонтирована только для чтения; файл с таким именем уже существует и имеет больше одной жёсткой ссылки; у исполняемого файла нет права чтения; `core_pattern` пуст, а `core_uses_pid` равен 0. Кроме того, дампа не будет, если процесс завершён сигналом, который его не порождает (`SIGKILL` от OOM-killer ядра).

```bash
V=8.3.27.2074

# 1. Кто обрабатывает дампы ядра
cat /proc/sys/kernel/core_pattern
systemctl is-active apport.service; grep -H '^enabled' /etc/default/apport

# 2. Лимит размера дампа у работающих процессов сервера
for p in $(pgrep -x ragent; pgrep -x rmngr; pgrep -x rphost); do
  printf '%s %-7s ' "$p" "$(cat /proc/$p/comm)"; grep -i 'max core file size' /proc/$p/limits
done
systemctl show "srv1cv8-$V@default" -p LimitCORE -p LimitCORESoft

# 3. Важные директивы юнита
systemctl cat "srv1cv8-$V@default" | grep -iE 'PrivateTmp|LimitCORE|^User|^ExecStart'

# 4. Следы недавних падений
journalctl -k --since "-24h" | grep -iE 'segfault|general protection|traps:|out of memory|killed process'
journalctl -u "srv1cv8-$V@default" --since "-24h" --no-pager | grep -iE 'core|signal|killed|abort|exited'
```

По man-странице `systemd-system.conf` (Ubuntu 24.04) у параметра `DefaultLimitCORE=` нет собственного значения по умолчанию, а PID 1 устанавливает `RLIMIT_CORE` в `infinity`, и это наследуют дочерние процессы. Поэтому у служб лимит обычно уже `unlimited`, а в интерактивной оболочке `ulimit -c` обычно показывает `0`. Проверяйте фактическое значение командой из пункта 2.

⚠ не подтверждено: наличие `PrivateTmp=true` в штатном юните `srv1cv8-<версия>@.service` (по памяти — есть). Проверяется командой из пункта 3.

### 9.3. Что делает apport (поведение Ubuntu по умолчанию)

`[офиц. Ubuntu: исходный код apport, ветка main]`

- Служба `apport.service` при старте (действие `--start` обработчика) записывает в `kernel.core_pattern` конвейер вида `|/usr/share/apport/apport -p%p -s%s -c%c -d%d -P%P -u%u -g%g -- %E` (точный набор ключей зависит от версии apport), а также `core_pipe_limit=10` и `fs.suid_dumpable=2`. При остановке службы значения возвращаются.
- Если у упавшего процесса лимит дампа равен нулю, apport файл дампа не пишет. При ненулевом лимите дамп записывается в каталог **`/var/lib/apport/coredump/`** с именем `core.<путь к исполняемому файлу, где "/" и "." заменены на "_">.<uid>.<boot_id>.<pid>.<время>`.
- В этом каталоге хранится не больше **5 дампов на одного пользователя** — более старые удаляются. Размер дампа ограничен примерно 3/4 доступной оперативной памяти.
- Отчёты `.crash` складываются в `/var/crash`. Для исполняемого файла, не принадлежащего пакету, отчёт не создаётся; в журнал пишется строка `executable does not belong to a package, ignoring`. Дамп при этом всё равно может быть записан (зависит от лимита).
- Журнал apport — `/var/log/apport.log`.

Что из этого следует для 1С: при настройках Ubuntu по умолчанию дамп упавшего `rphost` стоит искать в `/var/lib/apport/coredump/`, а причину его отсутствия — в `/var/log/apport.log`. Для расследований удобнее один из двух вариантов ниже.

### 9.4. Вариант А: файл дампа в выделенном каталоге

```bash
V=8.3.27.2074

# 1. Отключить apport: иначе при каждой загрузке он заново займёт core_pattern
sudo systemctl disable --now apport.service
sudo sed -i 's/^enabled=1/enabled=0/' /etc/default/apport

# 2. Каталог для дампов: вне /tmp, доступен на запись пользователю сервера 1С
sudo install -d -o usr1cv8 -g grp1cv8 -m 0750 /var/dumps/1c

# 3. Шаблон имени: имя программы, PID, время (секунды с 1970 года)
printf 'kernel.core_pattern=/var/dumps/1c/core.%%e.%%p.%%t\n' | sudo tee /etc/sysctl.d/60-1c-coredump.conf
sudo sysctl --system
cat /proc/sys/kernel/core_pattern

# 4. Лимит для службы (если проверка из 9.2 показала не unlimited)
sudo systemctl edit "srv1cv8-$V@default"
```

В открывшемся редакторе:

```ini
[Service]
LimitCORE=infinity
```

```bash
# 5. Перезапуск службы (завершит сеансы пользователей!) и проверка лимита
sudo systemctl restart "srv1cv8-$V@default"
grep -i 'max core file size' /proc/$(pgrep -x ragent | head -1)/limits
```

Спецификаторы `core_pattern` `[офиц. core(5)]`: `%e` — имя программы (до 15 символов), `%E` — путь к исполняемому файлу с заменой `/` на `!`, `%p` — PID, `%P` — PID в начальном пространстве имён, `%t` — время в секундах с начала эпохи, `%s` — номер сигнала, `%u` — UID, `%g` — GID, `%h` — имя хоста. Длина итогового имени — не более 128 байт.

Проверка на безвредном процессе (сервер 1С не затрагивается):

```bash
sudo -u usr1cv8 bash -c 'ulimit -c unlimited; sleep 600 & sleep 1; kill -SEGV $!; wait'
sudo ls -l /var/dumps/1c/          # должен появиться файл core.sleep.<PID>.<время>
sudo rm /var/dumps/1c/core.sleep.*
```

### 9.5. Вариант Б: `systemd-coredump` и `coredumpctl`

`[офиц. Ubuntu: systemd-coredump(8), coredump.conf(5), coredumpctl(1) для 24.04]`

```bash
sudo apt install systemd-coredump     # внимательно прочтите, какие пакеты apt предлагает удалить
cat /proc/sys/kernel/core_pattern      # должен начинаться с |/usr/lib/systemd/systemd-coredump
```

Пакет `apport-core-dump-handler` подтверждён по packages.ubuntu.com 10.10.2026: он есть в 24.04 и 26.04, в 22.04 его нет. Остальное не подтверждено: на Ubuntu установка `systemd-coredump` заменяет обработчик apport (в 24.04 обработчик вынесен в отдельный пакет `apport-core-dump-handler`); какие именно пакеты будут удалены, покажет `apt`.

Как работает:

- Шаблон ядра задаёт файл `/usr/lib/sysctl.d/50-coredump.conf`; ядро передаёт дамп программе `systemd-coredump`, та запускает непривилегированный экземпляр `systemd-coredump@.service`.
- Дампы по умолчанию хранятся в `/var/lib/systemd/coredump/` в сжатом виде (в 24.04 — `.zst`), сведения о падении и трассировка стека — в журнале systemd.
- Старые дампы удаляет `systemd-tmpfiles` «через несколько дней» (настройка в `/usr/lib/tmpfiles.d/systemd.conf`; по памяти — 3 дня, подтверждено 11.10.2026 исходным файлом systemd 255 `tmpfiles.d/systemd.conf.in` — строка `d /var/lib/systemd/coredump 0755 root root 3d`; ранее было не подтверждено). Нужный дамп сразу копируйте в другое место.

Параметры `/etc/systemd/coredump.conf` (секция `[Coredump]`) и их значения по умолчанию в 24.04:

| Параметр | По умолчанию | Смысл |
|---|---|---|
| `Storage=` | `external` | `external` — файлы в `/var/lib/systemd/coredump/`; `journal` — в журнале; `none` — не хранить |
| `Compress=` | `yes` | Сжимать файлы дампов |
| `ProcessSizeMax=` | 32G на 64-битных системах | Максимальный размер дампа, который обрабатывается (с построением стека) |
| `ExternalSizeMax=` | 32G на 64-битных системах | Максимальный размер дампа, сохраняемого файлом; `infinity` — без ограничения |
| `JournalSizeMax=` | 767M | Максимальный размер дампа, сохраняемого в журнале |
| `MaxUse=` | 10 % размера диска | Сколько места могут занимать дампы; при превышении удаляются старые |
| `KeepFree=` | 15 % размера диска | Сколько места оставлять свободным |

**Уточнено 11.10.2026** по файлу `src/coredump/coredump.conf` из исходных текстов systemd: в версиях 249–252 умолчания `ProcessSizeMax=2G` и `ExternalSizeMax=2G`, начиная с версии 253 — `32G` (в Ubuntu 22.04 systemd 249, в 24.04 — 255). Граница, таким образом, — версия 253, а не 251. Ранее было не подтверждено: в systemd до версии 251 (Ubuntu 22.04 поставляется с 249) значения `ProcessSizeMax` и `ExternalSizeMax` по умолчанию были 2G — дампы большого `rphost` обрезались бы. Проверьте `man coredump.conf` на своей системе и при необходимости увеличьте лимиты.

Настройка под большие процессы 1С (вступает в силу со следующего дампа, перезапуск не нужен):

```bash
sudo install -d /etc/systemd/coredump.conf.d
printf '[Coredump]\nStorage=external\nCompress=yes\nProcessSizeMax=64G\nExternalSizeMax=64G\nMaxUse=100G\nKeepFree=20G\n' | sudo tee /etc/systemd/coredump.conf.d/10-1c.conf
```

Работа с дампами:

```bash
coredumpctl list                                   # все зарегистрированные падения
coredumpctl list rphost --since "2026-10-09"       # только rphost, с даты
coredumpctl -1 info rphost                         # подробности последнего падения rphost, включая стек
coredumpctl info 12345                             # по PID
sudo coredumpctl dump 12345 -o /var/dumps/1c/rphost.12345.core   # извлечь дамп в файл
sudo coredumpctl debug 12345                       # открыть в gdb
sudo coredumpctl debug 12345 --debugger-arguments="-batch -ex 'thread apply all bt'" > /tmp/rphost_12345_bt.txt
```

В столбце `COREFILE` вывода `list`: `present` — файл на месте, `journal` — дамп в журнале, `truncated` — обрезан, `missing` — уже удалён, `error` — недоступен (обычно права), `none` — не сохранялся.

### 9.6. Стек вызовов через `gdb`

```bash
sudo apt install gdb
V=8.3.27.2074
CORE=/var/dumps/1c/core.rphost.12345.1791632400

# Сводка: сигнал, список потоков, стеки всех потоков, загруженные библиотеки
sudo gdb -q -batch \
  -ex 'set pagination off' \
  -ex 'info threads' \
  -ex 'thread apply all bt' \
  -ex 'info sharedlibrary' \
  /opt/1cv8/x86_64/$V/rphost "$CORE" > /tmp/rphost_12345_bt.txt 2>&1

# Интерактивно
sudo gdb /opt/1cv8/x86_64/$V/rphost "$CORE"
# (gdb) bt                    — стек упавшего потока
# (gdb) info threads          — потоки
# (gdb) thread apply all bt   — стеки всех потоков
# (gdb) info sharedlibrary    — библиотеки и их адреса
# (gdb) quit
```

Правила:

- Исполняемый файл в команде `gdb` должен быть **той же сборки**, что и упавший процесс, и анализ лучше выполнять на той же машине: `gdb` подгружает библиотеки платформы и системы по тем же путям.
- Отладочных символов платформы в открытой поставке нет (⚠ не подтверждено), поэтому в стеке будут имена библиотек (`core83.so`, `backbas.so` и т. п.) и адреса, а не имена функций. Для разработчиков 1С этого достаточно вместе с самим дампом; для администратора стек полезен тем, что показывает, не падает ли процесс в сторонней библиотеке (шрифты, криптография, внешняя компонента, драйвер ODBC).
- Дамп, сжатый `systemd-coredump`, перед открытием в `gdb` нужно извлечь командой `coredumpctl dump` либо распаковать (`zstd -d`).

### 9.7. Дамп и стек работающего (зависшего) процесса

```bash
PID=12345
sudo gdb -q -batch -p "$PID" -ex 'set pagination off' -ex 'thread apply all bt' > /tmp/rphost_${PID}_live_bt.txt 2>&1
sudo gcore -o /var/dumps/1c/rphost_live "$PID"      # создаст /var/dumps/1c/rphost_live.12345
```

- `gcore` входит в пакет `gdb`. На время снятия дампа процесс приостанавливается; на большом `rphost` это десятки секунд.
- В Ubuntu подключаться отладчиком к чужому процессу может только root (ограничение `kernel.yama.ptrace_scope`), поэтому команды выполняются через `sudo`.
- Перед снятием дампа убедитесь, что на томе хватает места: размер файла сравним с памятью процесса (`ps -o pid,rss,vsz -p $PID`).

### 9.8. Что отправлять в поддержку 1С

Официальный перечень в этой сессии проверить не удалось (страницы ИТС недоступны) — ниже состав, принятый на практике `[практика]`:

1. Точная версия платформы и разрядность (`8.3.27.2074 x86_64`), режим работы, СУБД и её версия.
2. Версия ОС: вывод `lsb_release -a` и `uname -a`.
3. Файл дампа, сжатый (`zstd -T0 файл` или `xz -T0 файл`), и текстовый стек из 9.6.
4. Технологический журнал за период сбоя с событиями `EXCP`, `EXCPCNTX`, `PROC`, `ATTN`, `ADMIN`, `CONN`; по запросу поддержки — с `<system level="debug"/>` или полный.
5. Системные журналы за тот же период: `journalctl -u "srv1cv8-$V@default"`, `journalctl -k`.
6. Описание сценария: что делали пользователи, воспроизводится ли, после каких изменений началось (обновление платформы, конфигурации, ОС).
7. Версии системных библиотек, если падение в сторонней библиотеке: `dpkg -l | grep -E 'libc6|libstdc|libfontconfig|libfreetype|libgssapi|unixodbc'`.

Сбор пакета одной командой:

```bash
V=8.3.27.2074; T=/var/tmp/1c_case_$(date +%F_%H%M); sudo mkdir -p "$T"
sudo sh -c "lsb_release -a > $T/os.txt 2>&1; uname -a >> $T/os.txt; dpkg -l | grep -iE '1c-enterprise|libc6|libstdc' >> $T/os.txt"
sudo sh -c "journalctl -u 'srv1cv8-$V@default' --since '-6h' --no-pager > $T/journal_srv1cv8.txt; journalctl -k --since '-6h' --no-pager > $T/journal_kernel.txt"
sudo cp /tmp/rphost_*_bt.txt "$T"/ 2>/dev/null
sudo tar -C /var/log/1c/tj -I 'zstd -T0' -cf "$T/tj_errors.tar.zst" errors
sudo ls -lh "$T"
```

### 9.9. «Падения» без дампа

| Признак | Причина | Где смотреть |
|---|---|---|
| `Out of memory: Killed process … (rphost)` в журнале ядра | OOM-killer ядра: кончилась память на машине | `journalctl -k \| grep -iE 'out of memory\|killed process'`; дамп не создаётся (`SIGKILL`) |
| `rphost` исчез, в ТЖ события `ATTN` о превышении критического объёма памяти | Кластер сам завершил процесс по настройкам рабочего сервера | ТЖ (`ATTN`, `CLSTR`); дамп — только если в свойствах кластера включена запись дампа |
| Процесс перезапущен по расписанию | Настройка «Расписание перезапуска» кластера или рабочего сервера | ТЖ: `CLSTR` с `Event=process restart required` |
| `segfault at … ip … in core83.so` и т. п. в журнале ядра | Настоящий аварийный останов | Дамп (9.3–9.5), ТЖ (`EXCP`, `EXCPCNTX`) |

## 10. Журнал регистрации

### 10.1. Назначение и расположение

Журнал регистрации фиксирует события информационной базы и действия пользователей: аутентификацию, изменение данных, проведение, ошибки выполнения, события, записанные кодом конфигурации. Он **не является частью базы данных**: при выгрузке и загрузке `.dt` не сохраняется и не очищается `[офиц. 8.5.1]`.

| Вариант | Где лежит |
|---|---|
| Файловая база | Подкаталог `1Cv8Log` каталога информационной базы |
| Клиент-серверная база | Подкаталог `1Cv8Log` каталога информационной базы внутри каталога служебных файлов кластера: `<SRV1CV8_DATA>/reg_<порт менеджера>/<UUID базы>/1Cv8Log/` |

На Linux со значениями по умолчанию: `/home/usr1cv8/.1cv8/1C/1cv8/reg_1541/<UUID базы>/1Cv8Log/`. Идентификатор базы берётся из реестра кластера.

```bash
V=8.3.27.2074; RAC=/opt/1cv8/x86_64/$V/rac
CL=$($RAC cluster list | awk '/^cluster/ {print $3}')

# Соответствие «UUID — имя базы»
$RAC infobase summary list --cluster="$CL"

# Размеры журналов всех баз
sudo sh -c 'du -sh /home/usr1cv8/.1cv8/1C/1cv8/reg_1541/*/1Cv8Log 2>/dev/null | sort -h'

# Состав журнала одной базы
sudo ls -lh /home/usr1cv8/.1cv8/1C/1cv8/reg_1541/<UUID>/1Cv8Log | tail -20
```

Если каталог данных кластера перенесён (`SRV1CV8_DATA`), путь меняется соответственно. Узнать его можно из командной строки агента: `ps -o args= -C ragent` (ключ `-d`).

### 10.2. Форматы журнала

`[офиц. 8.5.1, 6.13.1]`

| Версия платформы | Формат по умолчанию | Смена формата |
|---|---|---|
| 8.3.4 и младше | Последовательный | Формат единственный |
| 8.3.5 – 8.3.11 | SQLite (`.lgd`) | Не поддерживается |
| 8.3.12 – 8.3.21 | Последовательный | Можно менять в обе стороны |
| 8.3.22 и старше, включая 8.5 | Последовательный | В новых базах SQLite использовать нельзя; преобразование **в** SQLite отключено; имеющийся журнал SQLite можно просматривать и преобразовать в последовательный |

Документация предупреждает, что в следующих версиях поддержка формата SQLite будет прекращена. Выбранный формат хранится в информационной базе и восстанавливается вместе с ней из резервной копии или `.dt`; если база с журналом SQLite, выгруженная в старой версии, загружается в 8.3.22 и новее — на формат журнала нужно обратить внимание.

Файлы последовательного формата `[офиц. 8.5.1, 6.13.2]`:

| Файл | Содержимое |
|---|---|
| `1Cv8.lgf` | Общие сведения журнала (справочные данные: пользователи, компьютеры, события, метаданные). Без него фрагменты прочитать нельзя |
| `*.lgp` | Фрагменты журнала — по одному на период разделения. На практике имя имеет вид `ГГГГММДДччммсс.lgp` `[практика]` |
| `*.lgx` | Индексные файлы; имя совпадает с именем фрагмента, размер — около 10 % размера фрагмента |
| `1Cv8.lgd` | Журнал в формате SQLite (одна база данных SQLite) |

Индексирование `[офиц. 8.5.1]`: в файловом варианте журнал не индексируется; в клиент-серверном — индексируется, число потоков индексирования равно половине числа ядер компьютера менеджера кластера, но не больше 8 и не меньше 1. Работу индексатора отражает событие ТЖ `EVENTLOG`.

### 10.3. Настройка: уровни и разделение по периодам

Диалог: Конфигуратор → «Администрирование» → «Настройка журнала регистрации» `[офиц. 8.5.1, 6.13.5]`.

- Для новой базы регистрируются события всех уровней важности, новый файл журнала начинается каждую неделю.
- Поле «Разделять хранение журнала по периодам»: Час, День, Неделя, Месяц, Год.
- Сохранить настройку можно только тогда, когда с базой не работает никто, кроме администратора.
- Уровни регистрации в диалоге (состав уровней подтверждён главой 22 «Руководства разработчика» 8.3.27 — перечисление `УровеньЖурналаРегистрации`: Ошибка, Предупреждение, Информация, Примечание (сверено 11.10.2026); подписи вариантов в диалоге — названия по памяти): не регистрировать; ошибки; ошибки и предупреждения; ошибки, предупреждения, информация; ошибки, предупреждения, информация, примечания.

Рекомендации `[практика]`: для нагруженной базы разделение «День»; уровень «Примечания» включать только при необходимости; события доступа к данным («Доступ. Доступ») включать точечно — они дают самый большой объём.

### 10.4. Сокращение журнала

`[офиц. 8.5.1, 6.13.5.2]`

В диалоге настройки журнала — кнопка «Сократить»:

- «Удалить события до» — после сокращения в журнале остаются записи с 00:00 указанной даты;
- «Записать удаляемые события в файл» — сохранить копию удаляемых записей в файл архива;
- «Сохранить разделение журнала по периодам и объединить с ранее сохранённым журналом» — для регулярных сокращений с возможностью просмотра архива.

Пакетный режим конфигуратора (ключи — по документации платформы; **Уточнено 10.10.2026** (полный текст приложения 7 документации 8.3.27, разд. 7.4.11): `/ReduceEventLogSize <Date> [-saveAs <имя файла>] [-KeepSplitting]`, где `Date` — новая граница журнала в формате ГГГГ-ММ-ДД, `-saveAs` — файл для копии удаляемых записей, `-KeepSplitting` — сохранить разделение на файлы по периодам. Ранее было не подтверждено: полный синтаксис, на странице 8.5.1 приведено только упоминание `/ReduceEventLogSize` и `KeepSplitting`):

```
1cv8 DESIGNER /S "srv1c\buh" /N "Администратор" /P "***" /ReduceEventLogSize 2026-07-01 -saveAs "D:\archive\buh_до_2026-07-01.lgf" -KeepSplitting /Out "D:\archive\reduce.log" /DisableStartupDialogs
```

Команду удобно запускать с рабочего места администратора (в том числе с Windows-хоста), а не с сервера Linux: конфигуратору нужна графическая среда.

Просмотр сохранённого архива выполняется в конфигураторе; порядок описан в разделе 6.13.4 руководства администратора (теперь раздел доступен в конспекте `../its-docs/adm-gl06-administrirovanie-ib-p3.md`; при написании статьи текст раздела не прочитан, путь в меню не проверен).

### 10.5. Преобразование из SQLite в последовательный формат

`[офиц. 8.5.1, 6.13.5.3]`

1. Открыть настройку журнала регистрации. Если журнал в формате SQLite, появится диалог.
2. Нажать «Перейти на последовательный формат (рекомендуется)», при желании включить разделение по периодам.
3. Дождаться окончания: преобразование занимает значительное время.
4. После успешного преобразования **удалить файл журнала SQLite** (`1Cv8.lgd`) — сам он не удаляется.

Особенности: обратное преобразование не поддерживается; в файловом варианте нужен монопольный доступ; в клиент-серверном формат можно менять при работающих пользователях, события при этом не теряются. Смена формата фиксируется событием «Информационная база. Изменение параметров журнала регистрации» (`_$InfoBase$_.EventLogSettingsUpdate`). При ошибке записи нового журнала формат остаётся SQLite; при ошибке чтения старого — журнал остаётся в последовательном формате.

### 10.6. Архивация файлами

`[практика]` — официального описания этого способа найти не удалось, применяйте осознанно:

- при включённом разделении по периодам закрытые периоды — это отдельные пары файлов `*.lgp` + `*.lgx`. Их переносят в архив средствами ОС; в журнале базы эти периоды перестают отображаться;
- **нельзя** трогать `1Cv8.lgf` и фрагмент текущего периода;
- надёжнее выполнять перенос при остановленном сервере 1С либо в технологическое окно;
- копирование каталога `1Cv8Log` целиком (например, `rsync`) — корректный способ резервного копирования журнала.

```bash
# Пример: перенести фрагменты старше 180 дней в архив (сервер 1С остановлен или окно обслуживания)
L=/home/usr1cv8/.1cv8/1C/1cv8/reg_1541/<UUID>/1Cv8Log
A=/backup/1c/eventlog/<имя_базы>
sudo install -d "$A"
sudo find "$L" -maxdepth 1 -type f \( -name '*.lgp' -o -name '*.lgx' \) -mtime +180 -exec mv -t "$A" {} +
```

### 10.7. Влияние на производительность

`[практика]`

- Журнал SQLite на больших объёмах — частая причина замедления записи и «зависаний» при просмотре и отборе; это одна из причин отказа от формата.
- Последовательный формат быстрее на запись; отбор по большому журналу без разделения по периодам медленный и нагружает менеджер кластера (`rmngr`).
- Журнал растёт без ограничений: без регулярного сокращения каталог `reg_<порт>` занимает десятки гигабайт и может переполнить том с домашним каталогом `usr1cv8`. Следите за размером (команда `du` из 10.1) и держите каталог данных кластера на отдельном томе.
- Массовая запись в журнал из кода конфигурации (`ЗаписьЖурналаРегистрации` в цикле) и высокий уровень детализации заметно увеличивают время проведения документов.
- Для внешнего анализа журнал выгружают в ClickHouse или Elasticsearch, например утилитой `akpaevj/OneSTools.EventLog` (читает `lgf` / `lgp`, работает службой Windows или юнитом systemd, требует .NET 5).

## 11. Отладка серверного кода на Linux

### 11.1. Два протокола отладки

`[офиц. 8.3.27, руководство разработчика, 31.2]`

| | TCP/IP | HTTP |
|---|---|---|
| Ключ запуска сервера | `-debug` или `-debug -tcp` | `-debug -http` |
| Как связаны отладчик и предметы отладки | Напрямую | Только через сервер отладки `dbgs`; отладчик и предметы отладки друг с другом не соединяются |
| Порты | Диапазон 1560–1591 на всех участвующих компьютерах; серверные предметы отладки используют порты процессов `rmngr` и `rphost` | Один порт сервера отладки, в клиент-серверном варианте по умолчанию **1550**; открыть нужно только его |
| Что можно отлаживать | Клиенты, сервер, фоновые задания, внешние соединения | То же, плюс мобильные приложения и мобильный клиент |
| Дополнительные диапазоны портов | Файл `debugcfg.xml` в каталоге конфигурационных файлов | Не нужны |

Общие ограничения:

- Код на сервере 1С нельзя отлаживать, пока сервер не запущен в режиме отладки.
- В режиме отладки объекты конфигурации загружаются по требованию, производительность ниже. **Для работы реальных пользователей режим отладки не предназначен.**
- Если сеанс во время отладки переназначается другому рабочему процессу, отладка становится невозможной — на стенде удобнее иметь один рабочий процесс.
- При закрытых портах отладка недоступна, а клиент может запускаться дольше.

### 11.2. Включение отладки на сервере Linux

Параметр `SRV1CV8_DEBUG` `[офиц. 8.5.1]`: пусто — отладка выключена (по умолчанию); `-debug` или `-debug -tcp` — отладка по TCP; `-debug -http` — отладка по HTTP.

```bash
V=8.3.27.2074
sudo systemctl edit "srv1cv8-$V@default"
```

```ini
[Service]
Environment="SRV1CV8_DEBUG=-debug -http"
```

```bash
sudo systemctl restart "srv1cv8-$V@default"       # перезапуск обязателен; сеансы пользователей завершатся
ps -eo pid,args | grep -E '[r]agent|[d]bgs'        # в командной строке ragent должны быть -debug -http, рядом — процесс dbgs
sudo ss -ltnp | grep -E ':1550\b'                  # сервер отладки слушает порт 1550
curl -s http://localhost:1550/ | head -3           # ответ вида «1C:Enterprise 8.3 Debug Server … it works!»
```

Важные детали:

- **Кавычки обязательны.** В директиве `Environment=` пробел разделяет разные переменные; без кавычек `-http` станет отдельным (некорректным) присваиванием и будет отброшен.
- В англоязычной документации имя службы местами напечатано как `srvc1v8-…` — это опечатка, правильно `srv1cv8-<версия>@<экземпляр>`.
- Дополнительные ключи агента `[офиц. 8.5.1, приложение 4.12.1]`: `-debugServerAddr <адрес>` — адрес компьютера сервера отладки (нужен при нескольких сетевых интерфейсах); `-debugServerPort <порт>` — порт сервера отладки, по умолчанию 1550; `-debugServerPwd <пароль>` — пароль подключения к серверу отладки; `-debugServerUsers <файл>` — файл со списком пользователей отладки (имеет приоритет над паролем). В документации 8.5.1 ключи записаны со знаком `/` (`/debug -http`), в юните systemd и на практике используется дефис.
- ⚠ не подтверждено: дополнительные ключи можно дописать в ту же переменную (`Environment="SRV1CV8_DEBUG=-debug -http -debugServerPort 1550"`), так как её значение подставляется в конец командной строки `ragent`. Проверяйте по `ps`.
- Для автономного сервера `ibsrv`: ключ `--debug=http` или `--debug=tcp`, порт — `--debug-port` `[офиц. 8.3.27]`.
- Откройте порты в межсетевом экране только для рабочих мест разработчиков: `sudo ufw allow from 192.168.1.0/24 to any port 1550 proto tcp` (HTTP) либо диапазон `1560:1591` (TCP).

Отключение: удалить строку из drop-in (`sudo systemctl edit …`) или весь drop-in (`sudo systemctl revert "srv1cv8-$V@default"` — уберёт **все** переопределения юнита), затем перезапустить службу.

### 11.3. Сервер отладки `dbgs`

`[офиц. 8.5.1, приложение 4.11.1]`

Исполняемый файл — `/opt/1cv8/x86_64/<версия>/dbgs`. При включённой HTTP-отладке кластер запускает его сам и сам передаёт параметры. Ручной запуск:

```
dbgs --version|--help --service|--daemon --addr=<хост> --port=<порт>|--range=<диапазон> --ownerPID=<PID> --password=<пароль> --notify=<файл> --debugServerUsers=<файл>
```

| Ключ | Назначение |
|---|---|
| `--addr=<хост>`, `-a` | IP-адрес сервера отладки; без ключа берётся адрес произвольного сетевого интерфейса |
| `--port=<порт>`, `-p` | Порт. Значения по умолчанию нет; при запуске из кластера используется 1550 |
| `--range=<диапазон>`, `-r` | Набор портов для выбора, например `2560:2590,4567`; при одновременном указании `--port` игнорируется |
| `--daemon` | Фоновый режим в Linux (без автозапуска после перезагрузки) |
| `--service` | Режим службы Windows |
| `--ownerPID=<PID>`, `-opid` | Процесс-владелец: сервер отладки завершается вместе с ним. Из кластера не используется |
| `--password=<пароль>`, `-pwd` | Пароль для всех подключающихся отладчиков |
| `--debugServerUsers=<файл>`, `-dbgsUsers` | Файл со списком разрешённых пользователей отладки; при указании пароль игнорируется |
| `--notify=<файл>` | Файл, в который сервер записывает свой адрес |

Ограничение `[офиц.]`: сервер отладки, запущенный отдельно как демон или служба, обслуживает предметы отладки файловых баз и **клиентские** предметы отладки клиент-серверных баз. Серверные предметы отладки клиент-серверной базы в этом режиме не поддерживаются — для них `dbgs` должен быть запущен самим кластером (`-debug -http`).

### 11.4. Настройка в конфигураторе

`[офиц. 8.3.27, 31.2.2]`

HTTP:

1. «Сервис» → «Параметры» → закладка «Отладка»: протокол отладки — HTTP; сервер отладки — `http://<сервер>:1550` (путь «Сервис — Параметры», закладка «Отладка» и свойство «Протокол отладки» подтверждены главой 31 «Руководства разработчика» 8.3.27 (сверено 11.10.2026); для поля с адресом сервера отладки остаётся: точные подписи полей — по памяти).
2. «Отладка» → «Подключение»: списки доступных и подключённых предметов отладки, кнопки «Подключить», «Отключить», «Завершить», «Остановить»; кнопка «Настройки» показывает адрес сервера отладки и имя информационной базы.
3. «Отладка» → «Подключение» → автоматическое подключение: отметить типы предметов отладки (сервер, фоновое задание, тонкий клиент и т. д.) и отборы по пользователям. Предмет подключается, если подходит под **любой** включённый тип или отбор.
4. «Отладка» → «Начать отладку» — запуск клиента из конфигуратора с нужными параметрами.

TCP/IP:

1. «Сервис» → «Параметры» → закладка «Отладка»: протокол — «Отладка по TCP/IP».
2. «Отладка» → «Подключение»: флажок «Поиск предметов отладки на удалённом компьютере» и имя либо адрес сервера 1С; кнопка «Параметры» задаёт диапазон портов для поиска.
3. Автоматическое подключение работает для серверов в режиме отладки; для фоновых заданий отладка должна быть разрешена и в клиенте.

Подключение уже запущенного клиента и других предметов отладки:

| Что | Как |
|---|---|
| Тонкий и толстый клиент из командной строки | `/debug -tcp` либо `/debug -http -attach /debuggerURL http://<сервер>:1550` (ключ `/debuggerURL <адрес отладчика>` подтверждён полным текстом приложения 7 документации 8.3.27, сверено 10.10.2026; остальное: вторая форма — по памяти) |
| Работающий клиент | Настройки клиента → параметр «Отладка в текущем сеансе» и адрес сервера отладки; до конца сеанса отключить нельзя |
| Веб-клиент | `http://<сервер>/<база>?debug=http,attach&debuggerURL="<адрес>"` либо `?debug=tcp&debuggerurl="<адрес>"` |
| Внешнее соединение | Файл `comcntrcfg.xml` в каталоге конфигурационных файлов: `<debugconfig debug="true" protocol="http" debuggerURL="http://<сервер>:1550"/>` |
| Веб-сервисы, HTTP-сервисы, OData клиент-серверной базы | Достаточно режима отладки на сервере 1С. Элемент `<debug …/>` в `default.vrd` нужен только для файловых баз |
| Пользователи | В списке пользователей базы должны быть учётные записи, под которыми аутентифицируются и конфигуратор, и предмет отладки |

Файл `debugcfg.xml` (только для отладки по TCP/IP; без него используется диапазон 1560–1591) `[офиц. 8.5.1, 3.19]`:

```xml
<config xmlns="http://v8.1c.ru/v8/debugcfg">
  <debugports range="1540:1550"/>
</config>
```

Если отлаживаемое приложение и конфигуратор находятся на разных компьютерах, одинаковый диапазон задаётся с обеих сторон.

## 12. Мониторинг сервера 1С

### 12.1. Быстрая проверка средствами ОС

```bash
V=8.3.27.2074
systemctl is-active "srv1cv8-$V@default" "ras-$V.service"
ps -o pid,ppid,rss,vsz,pcpu,etime,args -C ragent,rmngr,rphost --sort=-rss      # rss и vsz — в килобайтах
sudo ss -ltnp | grep -E 'ragent|rmngr|rphost|ras|dbgs'                           # кто какие порты слушает
free -h; df -h / /home /tmp /var/log/1c
journalctl -u "srv1cv8-$V@default" --since "-1h" --no-pager | tail -30
```

Порты по умолчанию `[офиц. 8.5.1]`: 1540 — агент сервера (`ragent`), 1541 — главный менеджер кластера (`rmngr`), 1560–1591 — рабочие процессы (`rphost`) и дополнительные менеджеры, 1550 — сервер отладки при HTTP-отладке, 1545 — сервер администрирования `ras`.

### 12.2. Показатели через `rac`

Утилита `rac` обращается к серверу администрирования `ras` (он должен быть запущен, см. статью 02 об установке). Если в кластере заведён администратор, к командам добавляются `--cluster-user=<имя> --cluster-pwd=<пароль>`.

```bash
V=8.3.27.2074; RAC=/opt/1cv8/x86_64/$V/rac
CL=$($RAC cluster list | awk '/^cluster/ {print $3}')

$RAC process list    --cluster="$CL"        # рабочие процессы
$RAC session list    --cluster="$CL"        # сеансы
$RAC connection list --cluster="$CL"        # соединения
$RAC lock list       --cluster="$CL"        # блокировки
$RAC server list     --cluster="$CL"        # рабочие серверы и их параметры
$RAC infobase summary list --cluster="$CL"  # информационные базы
```

Поля `rac process list` (⚠ имена полей и единицы — по практике, сверяйте со своим выводом; опечатка `perfomance` присутствует в самой утилите):

| Поле | Смысл |
|---|---|
| `process`, `host`, `port`, `pid` | Идентификатор процесса в кластере, сервер, порт, PID в ОС |
| `started-at` | Время запуска |
| `running`, `use`, `reserve` | Процесс активен; режим использования (`used` / `not-used`); является ли резервным |
| `connections` | Число соединений |
| `memory-size` | Занятая память, килобайты |
| `memory-excess-time` | Сколько секунд процесс превышает допустимый объём памяти |
| `available-perfomance` | Доступная производительность |
| `capacity` | Относительная производительность (по умолчанию 1000) |
| `avg-call-time` | Среднее время обслуживания одного обращения = сумма трёх следующих |
| `avg-server-call-time` | Затраты самого рабочего процесса |
| `avg-db-call-time` | Затраты СУБД |
| `avg-lock-call-time` | Затраты менеджера блокировок |
| `avg-threads` | Среднее число клиентских потоков |
| `selection-size` | Объём выборки, по которой посчитаны средние |

Соответствие с консолью администрирования `[офиц. 8.5.1, 5.2.10]`: «Доступная производительность»; «Реакция сервера» = «Затрачено сервером» + «Затрачено СУБД» + «Затрачено менеджером блокировок»; «Клиентских потоков» — по этому показателю система рассчитывает производительность процесса; «Занято памяти»; «Соединений»; «Включён», «Активен», «Резервный».

Как читать: рост `avg-db-call-time` — проблема на стороне PostgreSQL (запросы, диски, блокировки СУБД); рост `avg-lock-call-time` — ожидания на управляемых блокировках; рост `avg-server-call-time` при низкой загрузке СУБД — нехватка процессора на сервере 1С или тяжёлый код; `memory-size`, растущий от суток к суткам, — утечка либо отсутствие перезапуска по расписанию.

Поля `rac session list`, полезные для диагностики (⚠ по практике):

| Поле | Смысл |
|---|---|
| `session-id`, `user-name`, `host`, `app-id`, `started-at`, `last-active-at` | Кто, откуда, каким приложением, когда начал и когда был активен |
| `hibernate` | Сеанс в «спящем» состоянии |
| `blocked-by-dbms`, `blocked-by-ls` | Номер сеанса, который блокирует данный на уровне СУБД и на уровне управляемых блокировок |
| `duration-current`, `duration-current-dbms` | Длительность текущего вызова и время в СУБД в нём, миллисекунды |
| `duration-last-5min`, `duration-all` и их варианты `-dbms` | То же за последние 5 минут и за всё время сеанса |
| `calls-last-5min`, `calls-all` | Число вызовов |
| `bytes-last-5min`, `bytes-all`, `dbms-bytes-last-5min`, `dbms-bytes-all` | Объём данных между клиентом и сервером и между сервером и СУБД |
| `memory-current`, `memory-last-5min`, `memory-total` | Память, выделенная в текущем вызове, за 5 минут и за сеанс, байты |
| `cpu-time-current`, `cpu-time-last-5min`, `cpu-time-total` | Процессорное время |
| `read-*`, `write-*` | Объём чтения с диска и записи на диск |
| `db-proc-info`, `db-proc-took`, `db-proc-took-at` | Номер соединения с СУБД (для PostgreSQL — PID серверного процесса), сколько миллисекунд оно захвачено и с какого момента |

Топ сеансов по длительности текущего вызова:

```bash
$RAC session list --cluster="$CL" | awk -v RS= -F'\n' '{
  split("", r)
  for (i = 1; i <= NF; i++) {
    p = index($i, ":"); k = substr($i, 1, p - 1); v = substr($i, p + 1)
    gsub(/^ +| +$/, "", k); gsub(/^ +| +$/, "", v); r[k] = v
  }
  printf "%10s %14s %6s  %-24s %s\n", r["duration-current"], r["memory-total"], r["session-id"], r["user-name"], r["app-id"]
}' | sort -rn | head -15
```

Сценарий читает вывод «абзацами» (записи разделены пустой строкой), раскладывает каждую запись в массив «поле — значение» и печатает длительность текущего вызова, память, номер сеанса, пользователя и приложение. Чтобы сортировать по памяти, поменяйте местами первые два столбца.

### 12.3. Что стоит отслеживать постоянно

| Группа | Показатель | Источник |
|---|---|---|
| Доступность | Служба активна; порты 1540, 1541, 1545 слушаются; есть хотя бы один `rphost` | `systemctl is-active`, `ss -ltn`, `pgrep -x rphost` |
| Память | RSS каждого `rphost` и `rmngr`; свободная память и подкачка | `ps`, `rac process list`, `free` |
| Производительность | `avg-call-time` и его составляющие; число сеансов; длительные текущие вызовы | `rac process list`, `rac session list` |
| Лицензии | Число занятых клиентских лицензий | `rac session list --licenses` |
| Ошибки | Число `EXCP`, `TTIMEOUT`, `TDEADLOCK`, `ATTN` за интервал | Лёгкий ТЖ из 7.2 |
| Диски | Свободное место на томах ТЖ, каталога данных кластера (журнал регистрации), `/tmp`, данных PostgreSQL | `df` |
| СУБД | Соединения, длительные транзакции, блокировки, «раздувание» таблиц | `pg_stat_activity`, `pg_locks`, `pg_stat_statements` — см. статьи о PostgreSQL |

### 12.4. Zabbix

`slothfk/1c_zabbix_template_ce` (GitHub) — шаблоны и скрипты для серверов 1С 8.3 на GNU/Linux и Windows (сведения из README и `docs/install.md` репозитория):

- четыре шаблона: центральный сервер (`1c_central_server.xml`), рабочий сервер (`1c_work_server.xml`), сервер лицензирования (`1c_license_server.xml`), файлы программных лицензий (`1c_license_files.xml`);
- на сервере 1С: скрипты из каталога `scripts` копируются в `/var/lib/zabbix/scripts`, файлы `userparameter_1c-*.conf` — в `/etc/zabbix/zabbix_agentd.d`, затем перезапуск `zabbix-agent`;
- нужны запущенный `ras` на центральном сервере, утилиты `zabbix-sender` и `zabbix-get`, на Debian-подобных системах — `gawk` вместо `mawk`;
- шаблон сам использует ТЖ: секции `<log>` из `configs/logcfg.xml` репозитория переносятся в рабочий `logcfg.xml`; каталог журналов по умолчанию `/var/log/1C`, в нём `zabbix/` с подкаталогами `calls`, `excps`, `locks` (владелец `usr1cv8:grp1cv8`) и `problem_log` (владелец `zabbix:grp1cv8`);
- пользователю `zabbix` дают доступ к журналам: `sudo usermod -a -G grp1cv8 zabbix`;
- порты нескольких служб RAS перечисляются в макросе `{$RAS_PORTS}`;
- в README заявлена версия Zabbix 4.4; с актуальными версиями Zabbix проверяйте импорт шаблонов на стенде. В инструкции репозитория путь к `logcfg.xml` указан для старой раскладки (`/opt/1C/v8.3/<архитектура>/conf/`) — для актуальных версий используйте `/opt/1cv8/conf/`.

### 12.5. Prometheus

`LazarenkoA/prometheus_1C_exporter` (GitHub, язык Go) — экспортер, получающий данные через `rac` (сведения из README):

- метрики: `available_performance`, `sessions_data`, `session`, `connect`, `client_lic`, `shedule_job` (признак блокировки регламентных заданий), `cpu`, `processes`, `disk`;
- точки сбора: `/metrics` (всё), `/metrics_rac` (данные `rac`), `/metrics_os` (процессор, память, диски);
- запуск: `./1C_exporter -port=9095 --settings=/path/to/settings.yaml`;
- в `settings.yaml` задаются путь к `rac` (`RAC.Path`) и кластер (`RAC.Cluster`: идентификатор, имя либо `host:port` менеджера кластера);
- сбор отдельных метрик можно приостанавливать запросом `GET /Pause?metricNames=…&offsetMin=5` и возобновлять `GET /Continue?metricNames=…`;
- для нескольких кластеров запускают по экземпляру экспортера на кластер.

**Уточнено 29.10.2026** по README и `examples_settings.yaml` выпуска v1.5.2 (последний на эту дату):
- лицензия MPL-2.0; в выпуске два готовых файла — `prometheus_1C_exporter-linux-amd64` и `…-windows-amd64.exe`, **контрольных сумм нет** (для проверки — сборка из исходников, `go build`);
- набор метрик задаётся списком `Exporters` (`client_lic`, `available_performance`, `shedule_job`, `session`, `connect`, `sessions_data`, `processes`, `cpu`, `disk`); `cpu` и `disk` дублируют `node_exporter`;
- **`shedule_job` требует `DBCredentials`** — внешний HTTP-сервис, отдающий JSON с именами баз и учётными данными; без такого сервиса метрику не включать;
- раздел `RAC`: `Path` (полный путь к `rac` — меняется при обновлении платформы), `Host`, `Port` (по умолчанию `localhost`, `1545` — нужен запущенный `ras`), `Login`/`Pass` администратора кластера; переменные окружения `RAC_LOGIN`, `RAC_PASSWORD` важнее файла;
- `LogDir` по умолчанию — каталог исполняемого файла (при установке в `/usr/local/bin` задать свой), `LogLevel` от 2 до 5, в образце стоит 5 (отладка); `LabelModes.MetricNamePrefix` добавляет префикс к именам метрик;
- `MetricKinds.Session` — вид метрики сеансов: `Summary` (по умолчанию), `Gauge`, `NativeHistogram`;
- в README порт запуска 9095, а в примере `prometheus.yml` — 9091: цель в Prometheus указывать по тому `-port`, с которым запущен экспортер.

Встроенная выдача метрик `ras` (`--monitor-*`, OpenMetrics) требует лицензии КОРП (`../its-docs/adm-pr06-…`, разд. 6.4); при лицензии ПРОФ остаётся этот экспортер или свой сценарий на `rac`.

Дополнительно на том же хосте обычно ставят `node_exporter` (ОС) и `postgres_exporter` (СУБД) `[практика]`.

## Типичные ошибки и подводные камни (симптом → причина → решение)

Раздел по большей части основан на практике сообщества; тексты сообщений платформы в разных версиях отличаются. Команды, останавливающие службу, прерывают работу пользователей.

### Технологический журнал

| Симптом | Причина | Решение |
|---|---|---|
| Журнал не появляется | Прошло меньше минуты; файл лежит не в том каталоге `conf`; ошибка XML; нет ни одного `<event>`; у `usr1cv8` нет прав на каталог | Подождать 60–90 с; `sudo find /opt/1cv8 /home/usr1cv8/.1cv8 -name logcfg.xml`; `xmllint --noout`; `sudo -u usr1cv8 test -w /var/log/1c/tj/excp && echo ok` |
| Работает только один из двух `<log>` | Одинаковый `location` у двух элементов | Каждому `<log>`, `<dump>`, `<defaultlog>` — свой каталог |
| Фильтр по длительности «не срабатывает» | `duration` в фильтре — в 1/10000 с, а в файле длительность в микросекундах | 1 секунда = `duration` 10000 = `durationus` 1000000 |
| `planSQLText` пустой либо его нет | Нет `<plansql/>` либо свойство не включено | Добавить `<plansql/>` и `<property name="all"/>` (или `plansqltext`) |
| Нет свойства `Context` | Свойство не выбрано | `<property name="all"/>` или `<property name="context"/>` |
| Событий `MEM`, `LEAKS`, свойств `lk*` нет, хотя фильтр задан | Нет элемента-генератора | Добавить `<mem/>`, `<leaks collect="1">…`, `<dbmslocks/>` |
| Множество каталогов `rac_<PID>` | `logcfg.xml` действует на все процессы 1С, включая запуски `rac` системой мониторинга | Добавить в каждый `<event>` условие `<eq property="process" value="rphost"/>` либо держать файл в каталоге, который видит только сервер |
| Диск заполнен журналом | Полный ТЖ оставлен включённым; `history="0"`; «осиротевшие» каталоги | Вернуть лёгкий `logcfg.xml`; задать `history`; очистка из 7.7; отдельный том |
| Сервер замедлился после включения ТЖ | `<plansql/>`, полный журнал, `<system level="debug">`, сложные маски `like` | Убрать генераторы, сузить фильтры по базе и пользователю, включать на короткое время |
| Скрипт не видит первое событие файла | Метка BOM в начале файла | Удалять BOM: `sed 's/^\xEF\xBB\xBF//'` (функции из 8.2 это делают) |
| Время события «не совпадает» с моментом проблемы | Метка времени — момент окончания события; час — в имени файла | Начало = время минус длительность; смотреть соседние часовые файлы |

### Дампы

| Симптом | Причина | Решение |
|---|---|---|
| `rphost` упал, дампа нет | Процесс убит `SIGKILL` (OOM-killer, кластер); дамп забрал apport; лимит 0; каталог недоступен; нет места | `journalctl -k`; `/var/lib/apport/coredump/` и `/var/log/apport.log`; проверки из 9.2 |
| Дамп пишется «в никуда» при `core_pattern=/tmp/…` | `PrivateTmp=true` в юните: файл в частном `/tmp` службы | Каталог вне `/tmp` (9.4) |
| После перезагрузки `core_pattern` снова указывает на apport | Служба apport включена | `sudo systemctl disable --now apport.service`, `enabled=0` в `/etc/default/apport` |
| `coredumpctl` показывает `truncated` или `missing` | Превышен `ProcessSizeMax` / `ExternalSizeMax`; файл удалён очисткой | Увеличить лимиты (9.5); сразу извлекать дамп `coredumpctl dump` |
| В `limits.conf` задано `core unlimited`, а у службы лимит другой | `limits.conf` не действует на службы systemd | `LimitCORE=infinity` в drop-in юнита |
| `gdb` показывает одни `??` | Исполняемый файл другой сборки; нет нужных библиотек | Указать `rphost` той же версии; анализировать на той же машине |

### Запуск сервера и подключение клиентов

| Симптом | Причина | Решение |
|---|---|---|
| `ragent` не запускается | Порты 1540/1541/1560+ заняты другим экземпляром или «осиротевшими» процессами; каталог данных принадлежит root (сервер однажды запускали от root); юнит не подключён; не хватает библиотек; повреждены файлы реестра кластера | `journalctl -u "srv1cv8-$V@default" -e`; `sudo ss -ltnp \| grep -E ':15(4[01]\|[6-9][0-9])'`; `pgrep -a -u usr1cv8`; `sudo chown -R usr1cv8:grp1cv8 /home/usr1cv8/.1cv8`; `ldd /opt/1cv8/x86_64/$V/ragent \| grep 'not found'`; восстановить `1cv8wsrv.lst` и `reg_1541/1CV8Clst.lst` из копии |
| «Сервер 1С:Предприятия не обнаружен», «Не запущен ни один рабочий процесс», ошибка сети при обращении к `tcp://<имя>:1560` | Клиент не разрешает имя сервера, под которым тот зарегистрирован в кластере; закрыты порты 1540, 1541, 1560–1591; имя сервера на самом сервере разрешается в `127.0.1.1`; `rphost` не стартовал | На клиенте: запись в DNS или `hosts` для имени сервера; на сервере: в `/etc/hosts` строка `<реальный IP> <имя>` вместо `127.0.1.1 <имя>`; `ufw`/межсетевой экран; `pgrep -a rphost`, ТЖ (`EXCP`, `ATTN`) |
| После смены имени хоста кластер не работает | В `1cv8wsrv.lst` и `reg_<порт>/1CV8Clst.lst` записано старое имя | Остановить службу, сделать копию каталога данных кластера; затем либо пересоздать кластер (убрать старый каталог данных, запустить, заново зарегистрировать базы — см. статью 02), либо заменить старое имя на новое в обоих файлах. Программные лицензии потребуют повторной активации: сетевое имя компьютера входит в ключевые параметры привязки (документация 8.3.27, разд. 10.3.1.4; конспект — `../its-docs/adm-gl10-zashchita-licenzii-p1.md`) |
| «Превышено время ожидания…», разрывы соединений | Контроль разрыва соединений при нестабильной сети; перегруженный `rphost`; подкачка; межсетевой экран рвёт простаивающие соединения | События `CONN` в ТЖ; параметры `pingPeriod` / `pingTimeout` (по умолчанию 1000 и 5000 мс; таймаут — в 3–10 раз больше периода, период не меньше 1000 мс `[офиц.]`); `free -h`, `vmstat 5` |
| Таймаут на управляемой блокировке, «конфликт блокировок» | Ожидание на блокировке дольше времени ожидания блокировки данных (20 с по умолчанию) | Журнал из 7.4 и разбор из 8.6 |
| Клиенту не хватает лицензии | Сервер не видит ключ или файл лицензии | События `LIC`, `HASP` в ТЖ; `nethasp.ini` в каталоге `conf`; права `usr1cv8` на каталог лицензий `/var/1C/licenses` |

### Память и падения рабочих процессов

| Симптом | Причина | Решение |
|---|---|---|
| `rphost` периодически исчезает и запускается заново | OOM-killer; завершение кластером по порогам памяти; перезапуск по расписанию; ошибка платформы или сторонней библиотеки | Таблица из 9.9; обновить платформу до актуальной сборки; проверить внешние компоненты и шрифты |
| Память `rphost` растёт сутками | Утечки в коде конфигурации (циклические ссылки), «тяжёлые» сеансы, отсутствие перезапуска | «Расписание перезапуска» в свойствах кластера или рабочего сервера (формат cron) `[офиц.]`; поиск: журнал памяти из 7.5, `<leaks>`, `<scriptcircrefs/>` на стенде |
| «Недостаточно памяти на сервере 1С:Предприятия», вызов прерван из-за расхода памяти | Сработали пороги рабочего сервера либо память действительно кончилась | Параметры рабочего сервера, см. ниже; добавить память; найти «тяжёлый» вызов по `MemoryPeak` (8.9) |
| Сервер перестал принимать новые соединения, старые работают | Превышен «временно допустимый объём памяти процессов» | Те же параметры; события `ATTN` |

Параметры рабочего сервера, управляющие памятью `[офиц. 8.5.1, 5.2.6.1]`:

| Параметр | Значения | Действие |
|---|---|---|
| Временно допустимый объём памяти процессов | байты; `0` — 80 % оперативной памяти сервера; `-1` — без ограничения | При превышении серверу не назначаются новые соединения |
| Интервал превышения допустимого объёма памяти | секунды, по умолчанию 300 | Сколько времени допускается превышение временно допустимого объёма |
| Критический объём памяти процессов | байты; `0` — 95 % оперативной памяти; `-1` — без ограничения | Порог для подсистемы мониторинга кластера; процесс, превысивший его, принудительно завершается (событие `ATTN`) |
| Безопасный расход памяти за один вызов | байты; `0` — 10 % временно допустимого объёма; `-1` — при превышении временного лимита прерывается любой вызов | Вызов, израсходовавший больше допустимого, завершается исключением; пишется `EXCP` с текстом и контекстом |

Механика контроля вызова `[офиц.]`: объём памяти процессов кластера обновляется каждые 2 секунды; в начале вызова вычисляется разница между временно допустимым объёмом и текущим расходом — это лимит на вызов (но не меньше безопасного расхода); вызов, выделивший больше, прерывается.

### Данные и СУБД

| Симптом | Причина | Решение |
|---|---|---|
| «Ошибка формата потока» | Повреждён кеш клиента или сеансовые данные сервера; реже — повреждение конфигурации или базы | Клиент: очистить кеш пользователя (на Windows — каталоги с именами-идентификаторами в `%LOCALAPPDATA%\1C\1cv8` и `%APPDATA%\1C\1cv8`, на Linux — в `~/.1cv8/1C/1cv8/`). Сервер: остановить службу, удалить каталоги `snccntx*` в `reg_<порт>` (только их!), запустить: `sudo sh -c 'rm -rf /home/usr1cv8/.1cv8/1C/1cv8/reg_1541/snccntx*'`. Если не помогло — тестирование и исправление базы |
| «Ошибка СУБД: …» при входе или создании базы | Нет подключения к PostgreSQL (`pg_hba.conf`, пароль, `listen_addresses`); сборка PostgreSQL без доработок для 1С (нет типов `mchar` / `mvarchar`, модулей `fasttrun`, `fulleq`); неверная локаль кластера | `psql -h <сервер> -U postgres`; журнал PostgreSQL; использовать сборку PostgreSQL для 1С или Postgres Pro — см. статьи о PostgreSQL |
| `deadlock detected`, `canceling statement due to lock timeout` в тексте `EXCP` | Взаимоблокировка либо таймаут на блокировках СУБД | `<dbmslocks/>` (4.5, 7.4), журнал PostgreSQL, `pg_locks` |
| `too many connections` / `remaining connection slots are reserved` | Мало `max_connections` для числа сеансов и фоновых заданий | Увеличить `max_connections` (с оглядкой на память), проверить «зависшие» сеансы |
| Запросы внезапно замедлились | Устаревшая статистика, раздувание таблиц, смена плана | Журнал из 7.3; `ANALYZE`, проверка autovacuum — см. статьи о PostgreSQL |

### Окружение Linux

| Симптом | Причина | Решение |
|---|---|---|
| «Отказано в доступе», сервер не может записать файл | Владелец каталогов — не `usr1cv8` (работали от root, восстановили копию) | `sudo chown -R usr1cv8:grp1cv8 /home/usr1cv8/.1cv8 /var/log/1c`; для обменных каталогов — права группе `grp1cv8` |

| Отчёты и печатные формы «съезжают», другая ширина колонок, ошибки при формировании PDF | Нет шрифтов Microsoft и/или `fontconfig` на сервере | `sudo apt install fontconfig ttf-mscorefonts-installer` (раздел `multiverse`), `sudo fc-cache -fv`, `fc-list \| grep -iE 'arial\|times'`, перезапуск сервера 1С |

| `Too many open files` | Лимит открытых файлов для службы | Drop-in юнита: `LimitNOFILE=65536`; проверка: `grep -i 'open files' /proc/$(pgrep -x rmngr \| head -1)/limits` |
| Не работает Kerberos, внешние источники данных, почта | Не установлены библиотеки, которые нужны отдельным возможностям сервера | `ldd` по модулям платформы; пакеты `libgssapi-krb5-2`, `unixodbc` и др. — см. статью 02 |

### Журнал регистрации и отладка

| Симптом | Причина | Решение |
|---|---|---|
| Каталог `reg_1541` занимает десятки гигабайт | Журнал регистрации не сокращается | Сокращение (10.4), разделение по периодам, архивация (10.6) |
| Просмотр журнала регистрации «вешает» клиент или сервер | Журнал SQLite большого объёма; отбор по огромному журналу без разделения | Преобразовать в последовательный формат (10.5); сократить; разделить по дням |
| В 8.3.22+ нельзя выбрать формат SQLite | Так задумано | Использовать последовательный формат |
| Конфигуратор не видит серверные предметы отладки | Сервер запущен без `-debug`; протокол в конфигураторе не совпадает с протоколом сервера; закрыты порты; `dbgs` запущен отдельно, а не кластером | Проверки из 11.2; одинаковый протокол с обеих сторон; порт 1550 (HTTP) или 1560–1591 (TCP) |
| После включения отладки сервер работает медленно | Режим отладки | Отключить `SRV1CV8_DEBUG` на рабочем сервере |
| `-http` не попал в командную строку `ragent` | Значение `Environment=` без кавычек | `Environment="SRV1CV8_DEBUG=-debug -http"` |

| Объём журнала по процессам | `sudo sh -c 'du -sm /var/log/1c/tj/*/* \| sort -n \| tail'` |
| Число событий по типам | `cat rphost_*/*.log \| LC_ALL=C sed 's/^\xEF\xBB\xBF//' \| grep -aoP '^\d\d:\d\d\.\d+-\d+,\K\w+' \| sort \| uniq -c \| sort -rn` |
| Склеить многострочные события | `tj1 rphost_*/*.log` (функция из 8.2) |
| Топ запросов по суммарному времени | сценарий из 8.4 |
| Найти виновника таймаута | сценарии из 8.6 (`t:connectID` — жертва, `WaitConnections` — виновники) |
| Кто обрабатывает дампы | `cat /proc/sys/kernel/core_pattern` |
| Лимит дампа у процесса | `grep -i 'max core file size' /proc/<PID>/limits` |
| Лимит дампа для службы | drop-in: `[Service]` + `LimitCORE=infinity`, затем перезапуск |
| Список дампов (`systemd-coredump`) | `coredumpctl list rphost` |
| Извлечь дамп | `sudo coredumpctl dump <PID> -o /var/dumps/1c/rphost.<PID>.core` |
| Стек всех потоков из дампа | `sudo gdb -q -batch -ex 'thread apply all bt' /opt/1cv8/x86_64/$V/rphost <дамп>` |
| Дамп работающего процесса | `sudo gcore -o /var/dumps/1c/rphost_live <PID>` |
| Убит ли процесс OOM-killer | `journalctl -k \| grep -iE 'out of memory\|killed process'` |
| Журнал службы сервера | `journalctl -u "srv1cv8-$V@default" --since "-1h"` |
| Размеры журналов регистрации | `sudo sh -c 'du -sh /home/usr1cv8/.1cv8/1C/1cv8/reg_1541/*/1Cv8Log \| sort -h'` |

| Включить отладку по HTTP | drop-in: `Environment="SRV1CV8_DEBUG=-debug -http"`, перезапуск; порт 1550 |

| Рабочие процессы и их показатели | `$RAC process list --cluster="$CL"` |
| Сеансы | `$RAC session list --cluster="$CL"` |
