## Кратко — главные факты и команды

1. Защита бывает **аппаратная** (USB-ключи HASP4 Net) и **программная** (система программного лицензирования, файлы `*.lic`, активация пинкодом). Их можно сочетать: лицензии складываются, сначала расходуются программные, затем из ключей HASP [офиц.].
2. Для клиент-серверной базы нужна **серверная лицензия** (на каждый компьютер с рабочими процессами `rphost`) и **клиентские лицензии**. Web-сервисы, HTTP-сервисы, OData и фоновые задания клиентских лицензий не расходуют [офиц.].
3. Каталог программных лицензий сервера на Linux — **`/var/1C/licenses`** (владелец `root`, группа `grp1cv8`, права `rwxrwxr-x`). Порядок поиска файлов `*.lic`: `/opt/1cv8/x86_64/<версия>/conf` → `/opt/1cv8/conf` → `~/.1cv8/conf` → каталог из `ConfLocation` в `conf.cfg` → `/var/1C/licenses`; запасной — `~/.1cv8/1C/1cv8/` (с учётом `location.cfg`) [офиц.].
4. Один и тот же файл лицензии **нельзя держать в двух каталогах поиска** и нельзя использовать в сети два файла с одним пинкодом и номером комплекта — файл попадает в чёрный список [офиц.].
5. Программная лицензия привязана к **ключевым параметрам компьютера**: сетевое имя, модель материнской платы, объём ОЗУ, тип и версия BIOS, процессоры, сетевые адаптеры и MAC-адреса, жёсткие диски. В Linux название и версия ОС не проверяются. Анализируется только **удаление** устройств; ОЗУ можно увеличивать, но нельзя уменьшать ниже объёма на момент активации. Опрос параметров — не чаще раза в сутки [офиц.].
6. В ВМ лицензия привязана к параметрам ВМ. Перед активацией: окончательное имя хоста, **статический MAC**, фиксированная память, окончательное число vCPU и состав дисков.
7. В комплекте серверной и многопользовательской лицензии **3 пинкода, активен 1** (2 резервных). При изменении ключевых параметров — «Восстановление» с резервным пинкодом; кончились пинкоды — Центр лицензирования 1С [офиц.].
8. Активация на сервере без графики, способ 1: в Конфигураторе (или клиенте) на любом другом компьютере — «Сервис — Получение лицензии… — Дополнительно — Установка на сервер», указать имя сервера и порт. Файл появится на сервере в `/var/1C/licenses` [офиц.].
9. Способ 2 — утилита **`ring license`** (отдельный дистрибутив `EnterpriseLicenseTools`, нужны Java 8+ и GNU Awk): `ring license activate …`, `list`, `info`, `validate`, `get`, `put`, `remove`, `update`, а для активации без интернета — `prepare-request` → `acquire` → `generate` [офиц.].
10. Проверка привязки: `sudo ring license validate --name <пинкод-номер>`; код возврата `1` — изменились параметры компьютера, `2` — ошибка подписи лицензии [офиц.].
11. Клиент ищет лицензию сначала у себя (файлы `*.lic`, локальный HASP, сетевой HASP через HASP License Manager), затем на менеджере кластера с **сервисом сеансовых данных**, затем на менеджере с **сервисом лицензирования**. Сервер выдаёт клиентские лицензии, только если у базы включён параметр «Разрешить выдачу лицензий сервером 1С:Предприятия» (`rac infobase update … --license-distribution=allow`) [офиц.].
12. Лицензия, выданная сервером, расходуется **«на сеанс»**; полученная клиентом локально — **«на компьютер»** [офиц.].
13. **Серверный ключ HASP — только локальный**: он должен стоять в том же компьютере, где работает `rphost`. **USB over IP для ключей защиты официально не поддерживается**; для ВМ 1С рекомендует программные лицензии или сервис лицензирования на физическом компьютере [офиц.].
14. Драйвер ключа на Linux: Sentinel LDK Run-time Environment (пакет `aksusbd`, службы `aksusbd` и `hasplmd`, порт 1947; на 10.2026 актуальна версия 10.33, deb-пакет официально поддерживает Ubuntu 24.04 и 26.04) либо пакет `haspd` от Etersoft (готовые сборки — только до Ubuntu 22.04). Сетевые ключи 1С платформам 8.3.x и 8.5.1 раздаёт **HASP License Manager** (`hasplm`), UDP-порт **475**, только IPv4; клиент настраивается файлом `nethasp.ini` [офиц./практика]. Платформе 8.5.4 и новее сетевой ключ раздаёт уже «Менеджер Лицензий» `rmlic` — см. п. 20.
15. **Сервис лицензирования кластера** можно закрепить требованием назначения функциональности за отдельным рабочим сервером (в том числе физическим, в том числе на Windows): тогда `*.lic` привязаны к нему, а ВМ с рабочими процессами можно пересоздавать. Такие требования (без имени ИБ и без дополнительного параметра) разрешены и на лицензии ПРОФ [офиц.].
16. Уровень **ПРОФ**: не более 12 ядер и 500 сеансов на базу, без профилей безопасности, фонового обновления БД и др.; **КОРП** — только 64-разрядный сервер, всё доступно; **МИНИ** — ограничения ПРОФ плюс один рабочий сервер, 5 клиентских сеансов и 1 конфигуратор. Пока к каждой базе кластера подключено не более 10 сеансов, возможности КОРП работают и на ПРОФ [офиц.].
17. **Лицензия для разработчиков (community)** — бесплатная, только программная, с 8.3.23; срок 1 неделя с автопродлением через интернет; один клиентский и один серверный компьютер; `ring` её активировать не умеет [офиц.].
18. Просмотр выданных лицензий: `$RAC session list --cluster=$CL --licenses`, `$RAC process list --cluster=$CL --licenses`. Технологический журнал: события `LIC` (свойство `res`: `seize`, `reuse`, `release`, `binding`, `error`, `must be removed`) и `HASP` [офиц.].
19. Тексты ошибок: «Не найдена лицензия. Не обнаружен ключ защиты программы или полученная программная лицензия!» и вариант «На сервере 1С:Предприятия не найдена лицензия…». В тексте документации 8.3.27 (п. 10.4.3) окончание записано как «…или полученная электронная лицензия!»; на экране современных сборок — «…программная лицензия!» [практика]. Искать в журналах и переписке надёжнее по неизменной части: «Не обнаружен ключ защиты программы». Кнопка «Подробно» открывает «Журнал поиска ключа» с причинами [офиц.].
20. **8.5.4**: платформа больше не получает лицензии через HASP License Manager. Лицензии раздаёт собственное приложение «1С:Предприятие — менеджер лицензий» (`rmlic`, файл настроек `rclic.cfg`); появилась стандартная функция «Управление лицензиями» (ключ запуска `/ManageLicenses`), которая показывает занятые лицензии и умеет активировать программные [офиц.].

## 2. Виды лицензий

### 2.1. Аппаратная и программная защита: что умеет каждая

| Возможность | Программная лицензия | Аппаратная (ключ HASP) |
|---|---|---|
| Размещение на компьютере пользователя | да | да |
| Размещение на компьютере сервера 1С | да | да |
| Размещение на другом компьютере локальной сети | нет | да |
| Произвольное суммирование лицензий на одном компьютере | да | нет, только ключи разных серий |
| Раздача по сети для любых видов баз (менеджер лицензий) | нет (до 8.5.4) | да |
| Использование сервиса лицензирования кластера | да, клиентские и серверные | нет |

Как расходуется клиентская лицензия [офиц.]:

| Как получена | Программная | Аппаратная |
|---|---|---|
| Клиент получил её на своём компьютере | на компьютер | на компьютер |
| Клиент получил по сети от HASP License Manager | не поддерживается | на компьютер |
| Клиенту выдал сервер 1С | на сеанс | на сеанс |
| Веб-клиент, мобильный клиент | на сеанс | на сеанс |

- **«На компьютер»** — этот компьютер запускает любое число клиентских приложений с любым числом баз.
- **«На сеанс»** — каждый сеанс занимает отдельную лицензию: два окна одной базы на одном компьютере = две лицензии.

### 2.2. Клиентские лицензии

| Вид | Что разрешает | Где размещается |
|---|---|---|
| Однопользовательская | любое число клиентских приложений на одном компьютере | на клиентском компьютере (или на сервере — см. ниже) |
| Многопользовательская (5, 10, 20, 50, 100, 300, 500) | не более номинала одновременных сеансов с любых компьютеров | на сервере 1С, на компьютере модуля расширения веб-сервера, на терминальном сервере |
| Комбинированная (5, 10, 20) | либо набор однопользовательских, либо одна многопользовательская — определяется **первой активацией** и потом не меняется | по выбранному варианту |
| Базовая | 1 пользователь, без клиент-сервера, веб-клиента, расширений, внешнего соединения, правки конфигурации | на компьютере пользователя |
| Клиентская «1С:Аналитика» | сеансы «1С:Аналитики» по номиналу | на сервере |

Правила [офиц.]:

- На клиентском компьютере имеют смысл **только однопользовательские** лицензии. Активировать многопользовательскую на клиентский компьютер бессмысленно.
- Программные лицензии на сервере суммируются без ограничений.
- Лицензия на 1000 пользователей — это комплект из двух лицензий на 500.
- Клиентская лицензия «1С:Аналитика» совместима с любой серверной лицензией. Если в базе одновременно обслуживается не более 5 сеансов клиентских приложений, технически и лицензионно допускается 1 сеанс «1С:Аналитики» без такой лицензии (п. 1.6.3.2).
- Клиентские лицензии тоже делятся на уровни: клиентская КОРП даёт все возможности, клиентская ПРОФ — в пределах ограничений серверной лицензии ПРОФ (раздел 2.4).

Состав комплектов программных лицензий (пинкоды) [офиц.]:

| Комплект | Лицензий | Пинкод на пользователей | Активных пинкодов | Поставляется пинкодов |
|---|---|---|---|---|
| Однопользовательская | 1 | 1 | 1 | 3 |
| Комбинированная 5 — как однопользовательские | 5 | 1 | 5 | 8 |
| Комбинированная 5 — как многопользовательская | 5 | 5 | 1 | 3 |
| Комбинированная 10 — как однопользовательские | 10 | 1 | 10 | 14 |
| Комбинированная 10 — как многопользовательская | 10 | 10 | 1 | 3 |
| Комбинированная 20 — как однопользовательские | 20 | 1 | 20 | 25 |
| Комбинированная 20 — как многопользовательская | 20 | 20 | 1 | 3 |
| Многопользовательская 50 / 100 / 300 / 500 | номинал | номинал | 1 | 3 |
| Многопользовательская 1000 | 1000 | 2 × 500 | 2 × 1 | 2 × 3 |
| Серверная 32-разрядная, 64-разрядная, МИНИ | — | — | 1 | 3 |

Пинкоды сверх «активных» — **резервные**: они нужны, когда изменились ключевые параметры компьютера.

### 2.3. Серверные лицензии

| Вид | Что разрешает | Примечание |
|---|---|---|
| На 32-разрядный сервер | любое число 32-разрядных `rphost` на одном физическом компьютере | ключ HASP `ENSR8` |
| На 64-разрядный сервер | любое число 32- и 64-разрядных `rphost` на одном физическом компьютере | ключ HASP `EN8SA`; на Linux x86_64 нужна именно она |
| МИНИ (сервер «на 5 подключений») | один рабочий сервер любой разрядности; не более 5 клиентских сеансов (толстый, тонкий, веб-клиент, внешнее соединение) и 1 сеанса конфигуратора | клиентские лицензии нужны отдельно; «1С:Аналитика» не поддерживается; не более одного рабочего сервера в кластере |

Правила [офиц.]:

- Серверная лицензия проверяется **в момент подключения клиентского приложения к рабочему процессу**, а не при запуске службы. Поэтому сервер без лицензии стартует, а ошибка появляется у клиента.
- Программная серверная лицензия активируется для компьютера, где работает `rphost`, **или** для компьютера, где работает `rmngr` с назначенным сервисом лицензирования.
- Не раздавать одним сервисом лицензирования лицензии и 32-, и 64-разрядного сервера: на запрос 32-разрядного сервера может уйти 64-разрядная лицензия (берётся первая свободная в порядке файлов каталога).
- Кластер из нескольких компьютеров с рабочими процессами требует серверной лицензии на каждый такой компьютер (v8.1c.ru, «Вопросы по лицензированию»).

### 2.4. Уровни ПРОФ и КОРП

Информационное письмо 1С № 25491 от 11.02.2019 разделило лицензии на ПРОФ и КОРП. Технические ограничения реализованы начиная с версий **8.3.12.1852, 8.3.13.1791 и 8.3.14.1592**; привязка программных лицензий к аппаратному ключу — с 8.3.12.1790, 8.3.13.1644, 8.3.14.1565; ограничения полностью вступили в силу с **10.09.2019** [офиц.].

| Уровень | Сервер | Суть |
|---|---|---|
| КОРП | только 64-разрядный | все возможности платформы |
| ПРОФ | 32- и 64-разрядный | всё, кроме перечня ниже |
| МИНИ | 32- и 64-разрядный | ограничения ПРОФ + свои (раздел 2.3) |

Что недоступно на серверной лицензии ПРОФ (руководство 8.3.27, п. 1.6.3.3) [офиц.]:

1. фоновое обновление конфигурации базы данных;
2. дополнительное управление распределением сервисов кластера и соединений по рабочим серверам в разрезе баз, видов клиентов и фоновых заданий;
3. параметр «Безопасный расход памяти за один вызов» (остаётся 0);
4. параметр «Количество ИБ на процесс» (остаётся 8);
5. режим распределения нагрузки «Приоритет по памяти»;
6. внешнее управление сеансами;
7. профили безопасности;
8. запись событий аудита прав доступа;
9. публикация списка баз и обновлений тонкого клиента через Web- или HTTP-сервисы;
10. механизм копий базы данных (исключение: при наличии клиентской лицензии «1С:Аналитика» копии базы разрешены вместе с Дата акселератором, запущенным в одном экземпляре);
11. более одного процесса Дата акселератора в кластере;
12. управление потреблением ресурсов;
13. пользовательские табличные пространства;
14. произвольные индексы для некоторых объектов метаданных;
15. хранилище двоичных данных (включая S3);
16. HTTP-сервис метрик OpenMetrics;
17. изменение каталогов данных сервисов кластера;
18. **более 500 одновременных сеансов в одной базе** (считаются конфигуратор, внешнее соединение, любые клиенты);
19. **более 12 ядер процессора** (если ядер больше, кластер использует 12; «ядро» — физическое ядро или любое ядро ВМ);
20. работа на ARM64 (кроме процессоров Apple) и на E2K (в документации это два отдельных пункта — всего в перечне 21 позиция).

Как считаются ядра [офиц., v8.1c.ru «Ответы на типовые вопросы по лицензированию», вопросы XIII.7–XIII.9]: на физическом сервере с Hyper-Threading учитываются только физические ядра; в виртуальной машине (Hyper-V, VMware, VirtualBox и т. п.) — виртуальные ядра, заданные в настройках ВМ. Ограничение «12 ядер» действует на каждый сервер кластера. Следствие для ВМ с Ubuntu: при лицензии ПРОФ нет смысла выдавать серверу 1С больше 12 vCPU «ради 1С» — лишние ядра достанутся только PostgreSQL и ОС.

Правило «10 сеансов» [офиц.]: пока к **каждой** базе кластера подключено не более 10 клиентских сеансов, все возможности, включая уровень КОРП (кроме Дата акселератора), доступны и на лицензиях ПРОФ. Одиннадцатый сеанс получит ошибку, если возможности КОРП используются, а лицензий КОРП недостаточно.

Достаточность лицензий КОРП [офиц.]: все серверные лицензии кластера — КОРП, и либо клиент получил клиентскую лицензию КОРП, либо клиент получил лицензию ПРОФ и выполняется `УП <= 1,1 * ЛК` (`УП` — число уникальных пользователей всех сеансов кластера, `ЛК` — число клиентских лицензий КОРП, доступных для выдачи сервером). Смешивать ПРОФ и КОРП в одном кластере и в одной информационной базе юридически нельзя: все лицензии кластера должны быть уровня КОРП (v8.1c.ru, вопросы XIII.19 и XIII.21); техническая возможность входа 10 % пользователей с лицензиями ПРОФ — только страховка от массового отказа, правомерной такая работа не считается [офиц.].

Расширения лицензий [офиц.]:

- ПРОФ, купленная до 11.02.2019: ограничения «500 сеансов» и «12 ядер» снимаются бесплатным расширением. Для программной лицензии — автоматически; для ключа HASP — специальной программной лицензией с портала 1С:ИТС, привязанной к аппаратному ключу.
- КОРП на ключах HASP: с 10.09.2019 все возможности доступны только после расширения программной лицензией из Центра лицензирования, привязанной к ключу. Программной лицензии КОРП ничего дополнительно не нужно.

**Лицензия для разработчиков (community)** [офиц., руководство 8.3.27, п. 1.6.3.6 и 10.3.6; письмо 1С № 30506]:

| Свойство | Значение |

Действие лицензии прекращается, если нет доступа к интернет-ресурсам 1С (нельзя продлить), учётная запись заблокирована или выдача приостановлена на портале.

Информационное письмо № 30506 вышло 27.04.2023 вместе с версией 8.3.23 [офиц., проверено]: лицензию получает любой, кто прошёл на `developer.1c.ru` полную регистрацию с подтверждением номера мобильного телефона; она работает и в файловом, и в клиент-серверном варианте (обеспечивает и клиент, и сервер); решать с ней реальные учётные и управленческие задачи нельзя.

**Учебная версия** («Версия для обучения программированию») работает без лицензии, но для стенда «сервер 1С + PostgreSQL» не годится: нет клиент-серверного варианта, один сеанс на базу, до 2000 записей в главных таблицах объектов и в наборах записей, до 1000 в табличных частях, нет COM-соединения, паролей пользователей, хранилища конфигурации, скорость ниже [офиц.].

**NFR (Not For Resale)** — комплекты для партнёров фирмы 1С: демонстрация, обучение, разработка; использовать у заказчика для реального учёта нельзя. Технически это обычные лицензии (программные или HASP) с теми же правилами привязки [практика]. На v8.1c.ru («Ответы на типовые вопросы по лицензированию») NFR-продукты для партнёров только упомянуты в одном ряду с пользовательскими лицензиями и лицензиями для разработчиков. ⚠ не подтверждено: состав и номиналы NFR-комплектов — открытых первоисточников нет, это партнёрская информация (уточнять у фирмы «1С» или дистрибьютора).

**Лицензия для тестирования выделенной функциональности** — дополнение к обычной лицензии для механизмов в статусе бета; запрашивается по адресу `betaplatform@1c.ru`; может раздаваться сервисом лицензирования [офиц.].

## 3. Программные лицензии: привязка, файлы, каталоги

### 3.1. Как это устроено

- Основа — **файл программной лицензии** (расширение `.lic`). В начале файла зашифрованный блок с параметрами лицензии и объекта привязки; после него — человекочитаемая копия тех же сведений, которая ни на что не влияет и может редактироваться [офиц.].
- **Активация (привязка)** — получение файла лицензии по **регистрационному номеру комплекта** и **пинкоду**. Привязать можно к параметрам компьютера либо к ключу HASP (локальному или сетевому) [офиц.].
- Имя файла — отметка времени активации, например `20100521112156.lic` (пример из документации).
- Приложение при запросе лицензии перебирает файлы во всех каталогах поиска, читает параметры, сверяет объект привязки с текущим компьютером, затем проверяет тип лицензии и число пользователей [офиц.].
- Доступ регулируется **правами ОС**: если пользователь, под которым работает процесс (`usr1cv8` для сервера), не может прочитать файл или каталог — лицензии «нет» [офиц.].

### 3.2. Ключевые параметры компьютера

Перечень из документации 8.3.27 (п. 10.3.1.4) [офиц.]:

| Параметр | Уточнение для Linux и ВМ |
|---|---|
| Наименование операционной системы | **в Linux при проверке не анализируется** |
| Версия операционной системы | в Linux не анализируется (в Windows — первые две цифры) |
| Серийный номер и дата установки ОС | только Windows (кроме Windows 10) |
| **Сетевое имя компьютера** | имя хоста (`hostnamectl`) |
| **Модель материнской платы** | в ВМ — виртуальная плата; зависит от гипервизора, поколения и версии ВМ |
| **Объём оперативной памяти** | см. правила ниже |
| **Тип и версия BIOS** | в ВМ — виртуальная прошивка |
| **Список процессоров и их параметры** | число и модель vCPU |
| **Список сетевых адаптеров и их MAC-адреса** | исключаются: Bluetooth; адаптеры, подключённые по USB или IEEE 1394; программные адаптеры WAN и RAS; адаптеры без MAC-адреса и без данных `VEN_`/`DEV_` в PnP-идентификаторе |
| **Список жёстких дисков и их параметры** | внешние накопители USB и IEEE 1394 не учитываются |

Привязка к ключу HASP: ключевые параметры — серия ключа, тип ключа, идентификатор ключа [офиц.].

Что именно читает платформа в Linux (какие файлы `/sys`, `/proc`, какие идентификаторы дисков) — документация не раскрывает. Правило исключения адаптеров сформулировано в терминах Windows (`VEN_`/`DEV_` в PnP-идентификаторе), для Linux отдельного правила в документации нет. ⚠ не подтверждено [практика]: в перечень сетевых адаптеров могут попадать виртуальные интерфейсы (мосты Docker, VPN), поэтому их появление и исчезновение на сервере с лицензией нежелательно. Поскольку анализируется только **удаление** устройств, опасен именно тот интерфейс, который существовал в момент активации и позже исчез (остановлен Docker, удалён VPN-клиент). Надёжная проверка одна — `ring license validate` до и после изменения (раздел 8.5): при расхождении утилита печатает, какого именно устройства не хватает.

Посмотреть текущие значения параметров средствами ОС (для записи «паспорта» ВМ перед активацией):

```bash
hostnamectl --static                                  # сетевое имя
sudo dmidecode -s baseboard-product-name              # модель материнской платы
sudo dmidecode -s bios-vendor; sudo dmidecode -s bios-version
free -m | awk '/^Mem:/{print $2" МБ"}'                # объём ОЗУ
lscpu | grep -E '^(Model name|CPU\(s\)|Socket)'       # процессоры
ip -br link                                           # адаптеры и MAC-адреса
lsblk -d -o NAME,SIZE,MODEL,SERIAL,TRAN               # диски
```

### 3.3. Правила сравнения

[офиц., п. 10.3.1.4 и 10.3.1.7]

- Сравнивается **текущее состояние** компьютера с состоянием **на момент активации**.
- Анализируется только **удаление** устройств, не добавление. Был один сетевой адаптер — второй добавить можно; заменить один адаптер другим нельзя (это удаление).
- Оперативную память можно увеличивать и затем уменьшать, но **не ниже объёма на момент активации**. Пример из документации: активация при 2 ГБ → можно 6 ГБ → можно 4 ГБ → ниже 2 ГБ нельзя.
- Изменение хотя бы одного ключевого параметра требует повторной активации **новым пинкодом**.
- Параметры компьютера опрашиваются **не чаще одного раза в сутки**. Следствие [практика]: после изменения ВМ лицензия может «отвалиться» не сразу, а при следующей проверке или после перезапуска службы.
- Ограничения доступа к одному файлу лицензии: не более 256 процессов из одного сеанса ОС и не более 256 сеансов ОС.

### 3.4. Какие действия с ВМ ломают лицензию

| Действие | Затронутый параметр | Результат |
|---|---|---|
| Переименование хоста (`hostnamectl set-hostname`) | сетевое имя | лицензия перестаёт работать |
| Смена MAC: динамический MAC после импорта или переноса ВМ, пересоздание адаптера, клонирование, «I copied it» в VMware | сетевые адаптеры | перестаёт работать |
| Замена типа адаптера (e1000 → vmxnet3, legacy → synthetic) | сетевые адаптеры | перестаёт работать (удаление + добавление) |
| Добавление второго адаптера | — | допустимо |
| Уменьшение ОЗУ ниже объёма на момент активации; динамическая память, ballooning | объём ОЗУ | перестаёт работать (или «плавает») |
| Увеличение ОЗУ | — | допустимо |
| Уменьшение числа vCPU, смена модели CPU (другой хост, режим совместимости процессора) | процессоры | высокий риск ⚠ |
| Увеличение числа vCPU | процессоры | **Уточнено 10.10.2026** (полный текст документации 8.3.27, разд. 10.3.1.4): список процессоров и их параметры входит в ключевые параметры привязки; общее правило — анализируется только удаление устройств, а не добавление, но примеры даны лишь для сетевых адаптеров и памяти. Отдельно про увеличение числа процессоров документация прямо не описывает; планировать как повторную активацию |
| Удаление или замена диска, перенос системы на новый диск, конвертация формата диска | жёсткие диски | перестаёт работать |
| Добавление диска | — | допустимо |
| Расширение существующего диска | параметры диска | ⚠ на форумах описаны оба исхода |
| Обновление версии или поколения ВМ, смена чипсета, миграция между гипервизорами | материнская плата, BIOS | высокий риск |
| Клонирование ВМ | имя, MAC, диски | в клоне лицензия недействительна; кроме того, два экземпляра одного файла в сети → чёрный список |
| Обновление ядра и ОС (`apt full-upgrade`, `do-release-upgrade`) | ОС в Linux не анализируется | безопасно по документации |
| Восстановление ВМ из копии на тот же хост с теми же параметрами и MAC | — | безопасно |

Подробные настройки гипервизоров (статический MAC, фиксированная память) — в `kb/linux/11-ustanovka-ubuntu-server-i-vm.md`, разделы 6–8.

### 3.5. Когда файл лицензии считается доступным

Все условия одновременно [офиц., п. 10.3.1.5]:

1. файл не в чёрном списке;
2. формат корректен;
3. файл привязан к текущему компьютеру, либо на компьютере доступен ключ HASP, к которому выполнена привязка;
4. в файле есть свободная лицензия;
5. в сети не используются другие файлы, полученные для тех же пинкода и номера комплекта.

Про дубли:

- обнаружено дублирование **в сети** — файл становится непригодным и попадает в чёрный список;
- несколько файлов одного комплекта **на одном компьютере** — в чёрный список не заносятся, используется один: созданный или использованный позже всех;
- один и тот же файл в нескольких каталогах поиска — расценивается как нарушение, файл может стать непригодным; причина может быть записана текстом в начало файла.

### 3.6. Каталоги поиска файлов `*.lic`

Linux, в порядке поиска [офиц., п. 10.3.8.3]:

| № | Каталог | Комментарий |
|---|---|---|
| 1 | `/opt/1cv8/x86_64/<версия>/conf` | каталог `conf` конкретной версии (`/opt/1cv8/i386/…` для 32 бит) |
| 2 | `/opt/1cv8/conf` | каталог `conf` корневого каталога установки |
| 3 | `~/.1cv8/conf` | `~` — домашний каталог пользователя, под которым работает процесс; для сервера это `/home/usr1cv8/.1cv8/conf` |
| 4 | каталог из параметра `ConfLocation` файла `conf.cfg` | берётся `conf.cfg` из каталога `conf` версии; умолчание для Linux — `/opt/1cv8/conf` |
| 5 | **`/var/1C/licenses`** | общий каталог компьютера; сюда кладёт файлы сервер и `ring` |
| запасной | `~/.1cv8/1C/1cv8/` | используется, если нигде выше лицензия не найдена; если в каталоге есть `location.cfg`, поиск идёт в каталоге из его параметра `location` |

Внутри списка файлы перебираются в том порядке, в каком их возвращает ОС, до первой подходящей лицензии.

Windows (для справки, когда сервис лицензирования или клиент находятся на Windows) [офиц.]: `C:\Program Files\1cv8\<версия>\bin\conf` → `%LOCALAPPDATA%\1C\1cv8\conf` → каталог из `ConfLocation` → `%ALLUSERSPROFILE%\1C\1cv8\conf` → `%ALLUSERSPROFILE%\1C\licenses` (он же `%ProgramData%\1C\licenses`); запасной — `%APPDATA%\1C\1cv8\` с учётом `location.cfg`.

Куда файл попадает при автоматическом получении [офиц., п. 10.3.7.1]:

| Сценарий | Linux | Windows |
|---|---|---|
| Лицензия для сервера 1С (в том числе «Установка на сервер» с другого компьютера) | `/var/1C/licenses` | `%ALLUSERSPROFILE%\1C\licenses` |
| Текущий компьютер, «для текущего пользователя» | `~/.1cv8/conf` | `%LOCALAPPDATA%\1C\1cv8\conf` |
| Текущий компьютер, «для всех пользователей» | не поддерживается; по примечанию документации возможно только при активации от `root` | `%ALLUSERSPROFILE%\1C\licenses` |

Найти все файлы лицензий на сервере:

```bash
# шаблон /home/*/.1cv8 должен раскрываться от имени root: домашние каталоги (в Ubuntu 22.04+ права 750) обычному
# пользователю не видны, и без sh -c лицензии в /home/usr1cv8/.1cv8 будут молча пропущены
sudo sh -c "find /var/1C/licenses /opt/1cv8 /home/*/.1cv8 /root/.1cv8 -name '*.lic' -ls 2>/dev/null"
# одинаковые по содержимому файлы (дубли одного файла в разных каталогах)
sudo sh -c "find /var/1C/licenses /opt/1cv8 /home/*/.1cv8 /root/.1cv8 -name '*.lic' -exec sha256sum {} + 2>/dev/null" | sort | uniq -w 64 -D
```

Если один и тот же файл найден в двух местах — оставить один (переместить лишний за пределы каталогов поиска, не удалять).

### 3.7. Права на каталог и файлы

Каталог `/var/1C/licenses` создаётся при установке платформы [офиц.]:

| Кто | Значение | Права |
|---|---|---|
| Владелец | `root` | `rwx` |
| Группа | `grp1cv8` | `rwx` |
| Остальные | — | `r-x` |

В группу `grp1cv8` должны входить все учётные записи, от имени которых работают демоны кластера и запускаются клиентские приложения на этом компьютере. Членам группы нужен доступ **на запись** к файлам лицензий [офиц.].

```bash
ls -ld /var/1C/licenses; ls -l /var/1C/licenses
id usr1cv8                                            # должен быть в grp1cv8

# привести права в порядок [практика]
sudo chown root:grp1cv8 /var/1C/licenses
sudo chmod 775 /var/1C/licenses
sudo chown usr1cv8:grp1cv8 /var/1C/licenses/*.lic
sudo chmod 664 /var/1C/licenses/*.lic

# проверить, что сервер действительно может читать файлы
sudo -u usr1cv8 sh -c 'ls -l /var/1C/licenses && head -c 64 /var/1C/licenses/*.lic >/dev/null && echo OK'
```

Ещё один файл, от которого зависит получение лицензий: `~/.1cv8/1C/1cv8/1cv8conn.pfl` (для сервера — `/home/usr1cv8/.1cv8/1C/1cv8/1cv8conn.pfl`). Процессам `rphost` и `rmngr` нужны права на создание, чтение и изменение этого файла [офиц.].

### 3.8. Резервная копия и восстановление

Резервная копия [практика, согласуется с требованиями документации]:

```bash
sudo install -d -m 700 /root/backup-1c-lic
sudo cp -a /var/1C/licenses/*.lic /root/backup-1c-lic/
sudo sh -c 'hostnamectl; ip -br link; lsblk -d -o NAME,SIZE,MODEL,SERIAL; free -m; lscpu' \
  | sudo tee /root/backup-1c-lic/passport-$(date +%F).txt >/dev/null
```

- Копию хранить **вне каталогов поиска** (не в `~/.1cv8`, не в `/opt/1cv8`) и лучше также вне сервера.
- Копия пригодна только на компьютере с теми же ключевыми параметрами. Восстановление ВМ из бэкапа на тот же хост с тем же MAC — рабочий сценарий; перенос файла на другую машину — нет.
- Вместе с файлами сохранить **регистрационные данные владельца** в точности так, как они введены при первой активации (см. 4.3), и учёт использованных пинкодов.

Что делать, если лицензия перестала работать:

| Ситуация | Действие |
|---|---|
| Ключевые параметры не менялись (файл удалён, испорчен; Linux переустановлен на том же оборудовании с тем же именем хоста) | вернуть файл из копии; либо «Восстановление» с флажком «Я уверен(-а), что ключевые параметры компьютера не изменялись» — тем же пинкодом |
| Параметры изменились, изменение можно откатить | вернуть прежние имя хоста, MAC, объём ОЗУ, диск — файл снова соответствует компьютеру, активация не нужна [практика; сравнение идёт с состоянием на момент активации] |
| Параметры изменились окончательно | «Восстановление» с **резервным пинкодом**; старый файл предварительно убрать из каталогов поиска |
| Резервные пинкоды закончились | обращение в Центр лицензирования 1С с регистрационным номером и описанием причины (обычно через обслуживающего партнёра). ⚠ не подтверждено: адрес `lic@1c.ru` — приведён по практике сообщества; ни в документации 8.3.27, ни в письме № 25491, ни на странице v8.1c.ru с ответами по лицензированию этого адреса нет (при повторной проверке 10.10.2026 первоисточник так и не найден). Контакты брать из текста ответа Центра лицензирования в помощнике получения лицензии или у партнёра |

Важно [офиц.]: перед повторным получением или обновлением лицензии файл текущей лицензии (того же пинкода и комплекта) нужно **переместить в каталог, который система не использует для поиска** — иначе и новая, и существующая лицензии попадут в чёрный список. Перед повторной активацией убедиться, что в локальной сети нет приложений, использующих прежний файл этого комплекта.

## 4. Активация программной лицензии

### 4.1. Способы и инструменты

Инструменты [офиц., п. 10.3.7.1]:

| Инструмент | Как вызвать | Ограничения |
|---|---|---|
| Помощник в Конфигураторе | «Сервис — Получение лицензии…» | нужен графический клиент |
| Помощник в режиме 1С:Предприятие | «Сервис и настройки — Функции для технического специалиста — Стандартные — Получение лицензии» | функции для технического специалиста должны быть включены |
| Утилита `ring` (модуль `license`) | командная строка | не активирует лицензии «1С:Аналитики» и лицензии для разработчиков |
| «Управление лицензиями» | только 8.5.4+, ключ запуска `/ManageLicenses` | см. 4.9 |

Способы получения [офиц.]:

| Способ | Суть |
|---|---|
| Автоматический | компьютер, выполняющий активацию, сам обращается к веб-сервису Центра лицензирования (`http://users.v8.1c.ru/LicenseCenter/ws/lm.1cws`) |
| На электронном носителе («из файла») | создаётся файл запроса; он передаётся в Центр лицензирования через страницу `https://portal.1c.ru/support/license/license-from-file?lang=ru` (международная версия — `https://portal.1c.eu/…`) с любого компьютера с интернетом; полученный файл-ответ загружается в помощник |
| По телефону | оператору диктуется 48 цифр из помощника, в ответ вводится 120 цифр |

Правила [офиц.]:

- Способ фиксируется первой активацией. Первая активация по интернету или «из файла» → повторная и обновление возможны только по интернету или «из файла». Первая по телефону → дальше только по телефону.
- Дополнительную клиентскую лицензию на компьютере, где уже есть программная лицензия, активируют тем же способом, что и первую.
- При получении «из файла» параметры компьютера в момент формирования запроса и в момент загрузки ответа должны совпадать **с учётом устройств USB и IEEE 1394**. Иначе ошибка «Ответ Центра лицензирования не соответствует введенным данным лицензии или владельца…». Лечение: вернуть конфигурацию (например, вставить ту же флешку) и повторно загрузить тот же файл ответа.
- Какие серверы Центра лицензирования используются, задаёт параметр `ExternalResourcesMode` в `conf.cfg`: `D` (по умолчанию) — в России, `A` — в Европе.

### 4.2. Шаги помощника «Получение лицензии»

1. Действие: **«Получить лицензию»**, **«Загрузить файл-ответ»** (вторая половина способа «из файла») или **«Активировать community-лицензию»**.
2. Номер комплекта и пинкод.
3. Ссылка **«Дополнительно»**:
   - флажок **«Установка на сервер»**, поля **«Сервер»** и **«Порт»** — привязать лицензию к компьютеру сервера 1С (см. 4.4);
   - флажок **«Автоматическое получение»**: установлен — попытка автоматической активации; сброшен — на последнем шаге выбор из трёх способов.
4. Операция: **«Первый запуск»** (первичное получение) или **«Восстановление»** (повторное получение или обновление).
5. «Первый запуск»: параметры владельца лицензии, затем объект привязки — компьютер (показываются его характеристики) или один из доступных ключей HASP.
6. «Восстановление»: параметры компьютера не менялись — оставить флажок «Я уверен(-а), что ключевые параметры компьютера не изменялись»; менялись — снять флажок и ввести следующий неиспользованный пинкод в поле **«Резервный пинкод»**. Затем проверить данные владельца.
7. Лицензия активируется для всех пользователей компьютера; нет права записи в общий каталог — помощник предложит активировать только для текущего пользователя.

### 4.3. Регистрационные данные владельца

- При загрузке файла-ответа сведения о владельце и продукте должны **в точности** совпадать с указанными при формировании файла запроса [офиц.].
- При «Восстановлении» помощник просит проверить регистрационные данные владельца [офиц.]; по опыту, расхождение с данными первой активации даже в одном символе (кавычки, «ООО» перед названием, пробел, «ё») приводит к отказу Центра лицензирования [практика].

Поэтому сразу после первой активации сохранить в файл: фамилию, имя, отчество, e-mail, организацию, страну, индекс, область, район, город, улицу, дом, строение, квартиру, номер комплекта, использованный пинкод, способ и дату активации. Хранить вместе с копией `*.lic`.

### 4.4. Активация для сервера без графики — с другого компьютера

Основной способ для Ubuntu Server без графической оболочки [офиц.]. Нужен компьютер с установленным клиентом 1С, сетевой доступ с него к серверу и (для автоматического получения) интернет на этом компьютере. Версия клиента должна совпадать с версией сервера — как при любом клиент-серверном подключении [практика].

1. На сервере: служба запущена (`systemctl status srv1cv8-$V@default`), имя хоста и параметры ВМ окончательные, клиентский компьютер разрешает имя сервера.
2. На клиенте запустить Конфигуратор любой базы (подойдёт пустая файловая) → «Сервис — Получение лицензии…». Если на этом компьютере лицензий нет вообще, помощник получения лицензии откроется сам при запуске.
3. «Получить лицензию» → номер комплекта, пинкод → **«Дополнительно»** → установить **«Установка на сервер»**, в поле «Сервер» — сетевое имя сервера 1С, в поле «Порт» — порт сервера.
4. «Первый запуск» → данные владельца → проверить, что в характеристиках показан **сервер**, а не локальный компьютер → получить лицензию.
5. На сервере проверить результат:

```bash
ls -l /var/1C/licenses/
sudo journalctl -u srv1cv8-$V@default --since "10 min ago" | tail -n 20
```

Пояснения:

- Файл в этом режиме всегда размещается на компьютере сервера; в Linux каталог для сервера — `/var/1C/licenses` [офиц.].
- ⚠ не подтверждено: какое значение стоит в поле «Порт» по умолчанию (в документации 8.3.27, п. 10.3.7.1, сказано только «параметры доступа к серверу»; при повторной проверке источник со значением не найден). При стандартных портах оставить предложенное значение; если сервер запущен на нестандартных портах — указать порт менеджера кластера (`SRV1CV8_REGPORT`, по умолчанию 1541), при неудаче — порт агента (1540). Независимо от поля, между клиентским компьютером и сервером должны быть открыты 1540, 1541 и 1560–1591/tcp — как для обычного клиент-серверного подключения.
- В тексте документации про этот режим сказано, что файл кладётся «в каталог профиля пользователя, от имени которого работает сервер (по умолчанию `usr1cv83`)» — формулировка и имя пользователя относятся к Windows. Для Linux та же документация в таблице размещения называет `/var/1C/licenses`, а пользователь сервера — `usr1cv8`. Если после активации файла в `/var/1C/licenses` нет, искать его командой `find` из раздела 3.6 (в первую очередь в `/home/usr1cv8/.1cv8/`).
- Если в кластере есть выделенный сервер с сервисом лицензирования, в поле «Сервер» указывается **его** имя — иначе лицензия будет активирована для другого компьютера, и кластер не сможет её использовать [офиц.].
- Серверную и многопользовательскую клиентскую лицензии активируют одинаково и на один и тот же компьютер. Если на сервере можно запустить Конфигуратор — документация рекомендует активировать обе прямо с него.
- Если на клиентском компьютере нет интернета: снять «Автоматическое получение», выбрать получение на электронном носителе, сохранить файл запроса, отправить его через `portal.1c.ru/support/license/license-from-file`, затем «Загрузить файл-ответ».

Альтернатива [практика]: установить на сервер компонент `client_full` и запустить Конфигуратор через проброс X11 (`ssh -X`) — ради одной активации обычно не оправдано.

### 4.5. Утилита `ring`: установка

`ring` — консольная Java-утилита с модулями; утилита лицензирования — это `ring` + модуль `license`. Отдельно «голая» `ring` не ставится [офиц., приложение 4, п. 4.4–4.5].

Требования [офиц.]:

- Java 8 или новее той же разрядности; документация рекомендует Liberica. В составе платформы есть компонент установщика `liberica_jre` (каталог `<версия>/jre`).
- На Linux — установленный **GNU Awk**, используемый по умолчанию.
- Модулю `license` нужна `ring` не ниже 0.8.2.
- Настройка криптографии Java: до 1.8 update 151 — установить JCE; 1.8 update 151 и новее — `crypto.policy=unlimited` в `java.security` либо JCE; Java 9 и новее — `crypto.policy=unlimited` в `$JAVA_HOME/conf/security/java.security` (в современных сборках OpenJDK это значение по умолчанию [практика]).

Дистрибутив: портал «1С:Обновление программ», `https://releases.1c.ru/project/EnterpriseLicenseTools` (нужна учётная запись с доступом). Пример состава архива для Linux x86_64 из документации:

```text
1c-enterprise-installer-1.9.1+3-linux-anyarch.e1c.car
1c-enterprise-license-tools-0.15.0+2-linux-x86_64.e1c.car
1c-enterprise-license-tools-0.15.0+2-linux-x86_64.e1c.dar
1c-enterprise-license-tools-0.15.0+2-linux-x86_64.e1c.par
1c-enterprise-ring-0.19.5+12-linux-x86_64.e1c.car
1ce-installer
1ce-installer-cli
```

Из имён читаются версии: установщик 1.9.1.3, `ring` 0.19.5.12, license tools 0.15.0.2.

Установка на Ubuntu Server:

```bash
sudo apt update
sudo apt install -y gawk openjdk-11-jre-headless unzip      # либо использовать JRE из состава платформы
sudo update-alternatives --set awk /usr/bin/gawk            # GNU Awk должен быть awk по умолчанию

# найти исполняемый файл ring и проверить модуль
```

Пояснения:

- `1ce-installer` — графический установщик, `1ce-installer-cli` — консольный [офиц.]. ⚠ не подтверждено: точная форма команды установки (`install`) и каталог установки. Документация программы установки (`https://its.1c.ru/db/inst10doc`, содержимое — `…/db/inst10doc/content/10000/hdoc`) закрыта подпиской, а в приложении 4 руководства администратора команда не приведена — при повторной проверке 10.10.2026 первоисточник получить не удалось. По практике сообщества: команда — `sudo ./1ce-installer-cli install`; если установщик останавливается на предупреждении о подписи компонентов, добавляют ключ `--ignore-signature-warnings`; компоненты ставятся в `/opt/1C/1CE/components/1c-enterprise-ring-<версия>-x86_64/ring` (в имени каталога версия записана как в имени файла, например `0.19.5+12`); в старых поставках (deb-пакеты `1c-enterprise-ring`, `1c-enterprise-license-tools`) — `/opt/1C/1CE/x86_64/ring/ring`. Перед запуском посмотреть встроенную справку: `./1ce-installer-cli --help`. Поскольку путь зависит от версии, в скриптах искать исполняемый файл командой `find`, а не прописывать путь жёстко.
- Версия Java [практика, ⚠ не подтверждено]: документация требует «Java 8 и выше» без верхней границы; у старых версий `ring` (0.11.x и ранее) известны сбои на новых JDK. Если `ring` падает с ошибкой Java на свежей JDK — попробовать JRE из состава платформы (`/opt/1cv8/x86_64/$V/jre`, компонент `liberica_jre`) или OpenJDK 11.
- Реестр модулей: центральный `/etc/1C/1CE/ring-commands.cfg`, пользовательский `~/.1C/1CE/ring-commands.cfg` [офиц.].
- Удобно завести переменную: `RING=$(sudo find /opt/1C -name ring -type f | head -n 1)`.
- Если Java несколько, задать `JAVA_HOME`, например `export JAVA_HOME=/opt/1cv8/x86_64/$V/jre` [практика].
- Язык вывода: `export RING_OPTS="-Duser.country=ru -Duser.language=RU"` [офиц.; в документации значение показано без кавычек, в bash кавычки обязательны].
- Запускать от `root` (`sudo`): нужна запись в `/var/1C/licenses` и чтение аппаратных параметров [практика]. После активации выправить владельца файла (раздел 3.7).
- Подводный камень `sudo`: в Ubuntu `sudo` по умолчанию очищает окружение (`env_reset`), поэтому `JAVA_HOME` и `RING_OPTS`, экспортированные в своей оболочке, до `ring` не дойдут. Передавать их в самой команде: `sudo env JAVA_HOME=/opt/1cv8/x86_64/$V/jre RING_OPTS="-Duser.country=ru -Duser.language=RU" "$RING" license list` — либо работать в оболочке `root` (`sudo -i`) и экспортировать переменные уже там.
- По умолчанию утилита отправляет статистику в сервис «1С:Пульт» (`pult.1c.com:443`): тип и имя ОС, версии утилиты и Java, имя команды, хеши на основе MAC-адреса. Отключается параметром `--send-statistics false` [офиц.].

### 4.6. Команды `ring license`

Общий вид: `ring license <команда> [--параметр "значение"]`. Значение с пробелами заключать в кавычки. Код возврата `0` — успех, иначе ошибка (текст — в стандартном выводе).

**Имя лицензии** для команд — `пинкод-номер` без дефисов в пинкоде: пинкод `123-456-789-012` и комплект `8000314159` → `123456789012-8000314159` [офиц.].

| Команда | Назначение |
|---|---|
| `activate` | активировать лицензию через веб-сервис Центра лицензирования и положить файл в хранилище |
| `list` | список имён лицензий в хранилище |
| `info` | сведения о лицензии (владелец, продукт, тип, привязка); оборудование не проверяет |
| `validate` | сверить оборудование компьютера с зафиксированным при активации |
| `get` | выгрузить лицензию из хранилища в файл |
| `put` | поместить файл активированной лицензии в хранилище |
| `remove` | удалить лицензию из хранилища |
| `update` | переполучить все лицензии хранилища с теми же параметрами; старые файлы сохраняются с расширением `.oldlic` |
| `prepare-request` | подготовить файл запроса в Центр лицензирования |
| `acquire` | получить файл ответа по файлу запроса через веб-сервис |
| `generate` | сформировать файл лицензии из запроса и ответа |

Общие параметры [офиц.]:

| Параметр | Назначение | Умолчание |
|---|---|---|
| `--path <каталог>` | хранилище лицензий | Linux `/var/1C/licenses`, Windows `%ProgramData%\1C\licenses` |
| `--send-statistics <true\|false>` | отправка статистики в «1С:Пульт» | `true` |
| `--conf-location <каталог>` | каталог с `conf.cfg`, откуда берётся `ExternalResourcesMode` (выбор Центра лицензирования); есть у `activate`, `acquire`, `update`; у `prepare-request` такого параметра (как и `--path`) нет | Linux `~/.1cv8/1C/1cv8/conf`. По документации для `activate` и `acquire` `~` — домашний каталог пользователя **сервера 1С** (`/home/usr1cv8`), для `update` — пользователя, запустившего утилиту. При запуске через `sudo` и нестандартном `ExternalResourcesMode` указывать каталог явно |
| `--all` (только `remove`) | удалить все лицензии с заданным именем в хранилище | — |

Параметры владельца и продукта (`activate`, `prepare-request`) [офиц.]:

| Параметр | Содержание | Условия |
|---|---|---|
| `--first-name`, `--middle-name`, `--last-name` | имя, отчество, фамилия | необязательны, если задан `--company` |
| `--email` | электронная почта | необязателен |
| `--company` | организация | необязателен, если заданы ФИО; не короче 5 символов; не более 3 одинаковых символов подряд |
| `--country`, `--zip-code`, `--town`, `--street` | страна, индекс, город, улица | не могут быть пустыми |
| `--region`, `--district` | область, район | необязательны |
| `--house`, `--building`, `--apartment` | дом, строение, квартира | достаточно одного из трёх; указанный не может быть пустым |
| `--serial` | регистрационный номер комплекта | — |
| `--pin` | пинкод | — |
| `--previous-pin` | при повторной активации — пинкод первичной активации | не должен совпадать с `--pin` |
| `--validate` | завершить команду ошибкой, если какой-либо ключевой параметр не удалось получить | **указывать всегда**: без него лицензия активируется с пустыми полями и потом непригодна |

Примеры:

```bash
RING=$(sudo find /opt/1C -name ring -type f | head -n 1)
NOSTAT="--send-statistics false"

# данные владельца задаются один раз — в точности как при первой активации
OWNER=(--first-name "Иван" --middle-name "Иванович" --last-name "Иванов"
       --email admin@example.org --company "ООО Пример"
       --country "Россия" --zip-code 123456 --town "Москва" --street "Примерная" --house 1)

# 1. Первичная активация серверной лицензии (нужен интернет на сервере)
sudo "$RING" license activate "${OWNER[@]}" \
  --serial 8100000000 --pin 111-222-333-444-555 \
  --path /var/1C/licenses --validate $NOSTAT

# 2. Что лежит в хранилище
sudo "$RING" license list $NOSTAT
sudo "$RING" license info --name 111222333444555-8100000000 $NOSTAT

# 3. Соответствует ли компьютер лицензии
sudo "$RING" license validate --name 111222333444555-8100000000 $NOSTAT; echo "код=$?"

# 4. Повторная активация после изменения ВМ: резервный пинкод.
#    Сначала убрать из хранилища старый файл ЭТОГО комплекта (и только его)
sudo install -d -m 700 /root/lic-old
sudo "$RING" license get    --name 111222333444555-8100000000 --license /root/lic-old/111222333444555-8100000000.lic $NOSTAT
sudo "$RING" license remove --name 111222333444555-8100000000 $NOSTAT
sudo "$RING" license activate "${OWNER[@]}" \
  --serial 8100000000 --pin 666-777-888-999-000 --previous-pin 111-222-333-444-555 \
  --path /var/1C/licenses --validate $NOSTAT

# 5. Выгрузить и загрузить файл лицензии
sudo "$RING" license get --name 666777888999000-8100000000 --license /root/backup-1c-lic/server.lic $NOSTAT
sudo "$RING" license put --license /root/backup-1c-lic/server.lic --path /var/1C/licenses $NOSTAT

# 6. Удалить лицензию из хранилища
sudo "$RING" license remove --name 666777888999000-8100000000 $NOSTAT

# после любой активации — права и перезапуск не требуется, но владельца стоит поправить
sudo chown usr1cv8:grp1cv8 /var/1C/licenses/*.lic && sudo chmod 664 /var/1C/licenses/*.lic
```

Замечания:

- ⚠ не подтверждено: допустимы ли в `--pin` и `--previous-pin` дефисы. В документации (приложение 4, п. 4.5.1) показано только, что пинкод комплекта печатается с дефисами (`123-456-789-012`), а в *имени* лицензии их нет; формат значения `--pin` не оговорён. В примерах сообщества пинкод передаётся с дефисами, как напечатан в комплекте [практика]. Если команда отвергает пинкод — ввести без дефисов.
- В строках синтаксиса документации у `get` и `remove` параметр записан как `-name` (один дефис); у `info` и `validate` — `--name` (сверено с конспектом приложения 4: расхождение есть в самом первоисточнике, вероятно опечатка). Если `--name` не принимается, попробовать `-name`.
- У `remove` есть флаг `--all` — удалить все лицензии с заданным именем в хранилище [офиц.].
- Повторная активация **тем же** пинкодом на компьютере с неизменными параметрами — это та же команда `activate` с теми же данными владельца и комплекта, без `--previous-pin`: по документации при повторном вводе идентичных данных на той же машине формируется такой же файл лицензии. Прежний файл перед этим всё равно убрать из хранилища (правило о дублях, раздел 3.8).
- Откат после неудачной повторной активации (пример 4): вернуть сохранённый файл — `sudo "$RING" license put --license /root/lic-old/111222333444555-8100000000.lic --path /var/1C/licenses`. Это имеет смысл, только если параметры компьютера возвращены к состоянию на момент первой активации.
- У `update` параметр `--validate` в таблице документации описан со значениями `true` | `false` (умолчание `false`), а в строке синтаксиса — как флаг без значения; у `activate` и `prepare-request` это флаг без значения. Перед использованием `update` на рабочем сервере проверить форму на стенде.
- `info` без `--name` и `validate` без `--name` ждут **содержимое** файла лицензии на стандартном вводе: `sudo "$RING" license validate < /var/1C/licenses/20260101120000.lic`.
- Коды возврата `validate`: `0` — оборудование соответствует; `1` — изменены параметры компьютера (выводится перечень различий); `2` — ошибка проверки цифровой подписи лицензии [офиц.].
- Раздел `TechnicalInfo` вывода `info` всегда на английском и пригоден для скриптов. `LicenseType`: `ClientLicense`, `ServerLicenseFor32BitServer`, `ServerLicenseFor64BitServer`, `ServerLicenseWithLimitedNumberOfConcurrentSessions` (МИНИ), `CorporateLicense`, `ProfLicenseUpdate`, `EntirePlatformFunctionality`, `MoreThan500UsersInInfobase`, `MoreThan12CpuCores`, `LicenseForDedicatedFunctionalityTesting`. `LicenseAssociationType`: `Computer` или `HardwareProtectionKey` [офиц.].
- `update`: `ring license update --conf-location <каталог> [--force true|false] [--path <каталог>] [--validate]`. Переполучает все лицензии хранилища с теми же номером, пинкодом и ключевыми параметрами; прежние файлы остаются с расширением `.oldlic`. `--force false` (умолчание) — при ошибке обработка прерывается и всё восстанавливается из копий; `--force true` — проблемный файл пропускается. Запуском `ring` на компьютере менеджера кластера с сервисом лицензирования в 2019 году обновляли лицензии под разделение ПРОФ/КОРП (письмо № 25491) [офиц.].

### 4.7. Активация через `ring`, если на сервере нет интернета

Три команды по очереди [офиц., п. 4.5.1, 4.5.4]:

```bash
# на сервере 1С (без интернета): подготовить запрос
sudo "$RING" license prepare-request \
  --company "ООО Пример" --country "Россия" --zip-code 123456 --town "Москва" --street "Примерная" --house 1 \
  --serial 8100000000 --pin 111-222-333-444-555 \
  --request /root/lic/request.txt --validate --send-statistics false

# на любом компьютере с интернетом и установленной ring: получить ответ
ring license acquire --request request.txt --response response.txt --send-statistics false

# снова на сервере 1С: собрать лицензию и положить в хранилище
sudo "$RING" license generate --request /root/lic/request.txt --response /root/lic/response.txt \
  --license /root/lic/server.lic --send-statistics false
sudo "$RING" license put --license /root/lic/server.lic --path /var/1C/licenses --send-statistics false
```

- Вместо `acquire` файл запроса можно передать в Центр лицензирования по электронной почте и получить файл ответа [офиц.].
- ⚠ не подтверждено: совместим ли файл запроса `ring` со страницей `portal.1c.ru/support/license/license-from-file` (она описана для запросов, созданных помощником платформы).
- Между `prepare-request` и `generate` не менять конфигурацию сервера (в том числе не вынимать и не вставлять USB-накопители).

### 4.8. Лицензия для разработчиков (community) на сервере

- Активация — в помощнике: «Активировать community-лицензию», ввод имени и пароля учётной записи портала `developer.1c.ru` (профиль должен быть подтверждён) [офиц.].
- `ring` эту лицензию не активирует [офиц.].
- ⚠ не подтверждено: работает ли для community-лицензии режим «Установка на сервер» с другого компьютера и в какой каталог попадает файл на Linux-сервере. Проверить на стенде; запасной вариант — запуск Конфигуратора на самом сервере (X11).
- Серверу нужен постоянный выход в интернет к ресурсам 1С: срок лицензии — неделя, продление автоматическое [офиц.].

### 4.9. Платформа 8.5.4: менеджер лицензий

Что известно из открытых источников (V8Update 8.5.4, блог 1С от 10.04.2025) [офиц.]:

- Реализовано приложение **«1С:Предприятие — менеджер лицензий»**, исполняемый файл `rmlic` (в Windows `rmlic.exe`). Устанавливается вместе с любым компонентом платформы или отдельно из дистрибутива. Это консольное приложение; запускается как обычное приложение или как служба — и в Windows, и в Linux.
- Менеджер раздаёт программные и аппаратные лицензии со своего компьютера: локальным приложениям — через межпроцессное взаимодействие ОС (IPC), по сети — по TCP; клиенты находят его в том числе широковещательным поиском по UDP.
- Менеджер умеет активировать новые лицензии и показывает свободные и занятые.
- **Получение лицензий через HASP License Manager клиентскими и серверными приложениями платформы прекращено.** Сам менеджер лицензий работает с HASP License Manager и может получать лицензии через него. Оба менеджера могут работать параллельно; если версии младше больше не используются, автозапуск HASP License Manager рекомендуется отключить.
- Программные лицензии теперь можно получать по сети и для **файловых** баз: локальные выдаются «на компьютер», удалённые — «на сеанс».
- Выдачу лицензий можно ограничивать по пространствам лицензирования, информационным базам и установленным продуктам.
- Конфигурационный файл клиента менеджера лицензий — `rclic.cfg`.
- Стандартная функция **«Управление лицензиями»**: показывает менеджеры лицензий, доступные по правилам поиска, количество лицензий каждого вида и число занятых, а при включённом переключателе «Приложения, занявшие лицензии» — кто их занял; позволяет активировать программные лицензии. Отвечает на вопросы «почему недостаточно лицензий», «кто занял», «почему недоступна функциональность КОРП».
- Ключи командной строки клиента **`/ManageLicenses`** и **`/ManageServers`** открывают функции «Управление лицензиями» и «Управление серверами» без информационной базы и без клиентской лицензии.
- Встроенный язык: свойство глобального контекста `МониторингЛицензий` (в кластере — только администратору кластера); методы `ПолучитьДоступныеМенеджерыЛицензий()`, `ПроверитьДоступностьМенеджераЛицензий()`, `ПолучитьОтветЦентраЛицензирования()`.
- По заявлению 1С, правила лицензирования не изменились; остальная часть системы лицензирования (файлы `*.lic`, привязка, сервис лицензирования кластера) осталась прежней.

Чем это заменяет `ring`: в 8.5.4 активировать программную лицензию и смотреть занятость можно из стандартной функции «Управление лицензиями» (в том числе запущенной ключом `/ManageLicenses` с другого компьютера). ⚠ не подтверждено: исключена ли `ring license` из поддерживаемых средств в 8.5.4 и есть ли у `rmlic` собственные команды активации из командной строки.

Уточнения по результатам повторной проверки (10.10.2026) [офиц., V8Update 8.5.4 и блог 1С]:

- В V8Update файл назван `rmlic.exe` («запускается с помощью файла rmlic.exe»); имя `rmlic` без расширения для Linux — вывод по аналогии с остальными утилитами платформы, в открытых источниках оно прямо не названо.
- «Менеджер лицензий поддерживает работу с HASP License Manager и может получать лицензии через эту утилиту»; при этом «прекращена поддержка HASP License Manager для получения лицензий в клиентских и серверных приложениях». То есть при сетевых ключах цепочка в 8.5.4 такая: ключ → HASP License Manager (как раньше) → `rmlic` → клиент или сервер 1С.
- До 8.5.4, по формулировке V8Update, «менеджер лицензий существовал только для аппаратных лицензий», программные лицензии для файловых баз по сети не раздавались, средств мониторинга свободных и занятых лицензий не было.
- Свойство `МониторингЛицензий` доступно в толстом и тонком клиенте и на сервере; у методов менеджера получения лицензий появился параметр типа `УстановленныйПродуктМониторингаЛицензий`.
- В 8.5.4 интерфейс стандартной функции «Управление лицензиями» адаптирован к интерфейсу «Версия 8.5».
- Ни один открытый источник не упоминает в связи с 8.5.4 ни `ring`, ни `nethasp.ini`, ни номера портов.

Что нужно выяснить по закрытой документации 8.5.4 перед переходом (перечень страниц — в конце раздела 12): номера портов TCP и UDP менеджера лицензий, параметры запуска `rmlic` и имя systemd-юнита, расположение и параметры `rclic.cfg`, судьба `nethasp.ini`, порядок поиска лицензий клиентом и сервером, действия при переходе с 8.3.27 при использовании сетевых ключей.

Как получить эти сведения самому на **тестовой** машине с установленной 8.5.4, не дожидаясь документации [практика; все команды, кроме вызова справки `rmlic`, только читают состояние системы; на рабочем сервере `rmlic` вручную не запускать]:

```bash
V=8.5.4.1306
ls -l /opt/1cv8/x86_64/$V/ | grep -i -E 'rmlic|rclic'                 # есть ли исполняемый файл менеджера лицензий
sudo find /opt/1cv8 /etc /home/usr1cv8/.1cv8 -iname 'rclic.cfg' 2>/dev/null   # где лежит конфигурационный файл клиента
/opt/1cv8/x86_64/$V/rmlic --help 2>&1 | head -n 40                    # встроенная справка (⚠ ключ справки не подтверждён: если вместо справки
                                                                      #  менеджер запустился и «повис» — прервать Ctrl+C и проверить `pgrep -a rmlic`)
systemctl list-unit-files | grep -i -E 'rmlic|1cv8|srv1c'             # какие юниты поставил пакет
ls /opt/1cv8/x86_64/$V/*.service 2>/dev/null                          # шаблоны юнитов в каталоге версии
sudo ss -tulpn | grep -i rmlic                                        # какие порты TCP и UDP слушает запущенный менеджер
grep -a -i -o -E '.{0,200}rmlic.{0,400}' /opt/1cv8/x86_64/$V/docs/ru/V8Update.htm | head   # описание в заметках о выпуске
```

Каталог `/opt/1cv8/x86_64/<версия>/docs/ru/` с файлом `V8Update.htm` назван на странице v8.1c.ru «Новое в платформе 8.5.4» [офиц.]. Найденные таким способом номера портов считать предварительными: открывать их в межсетевом экране рабочего сервера только после сверки с документацией 8.5.4.

## 5. Как клиент и сервер находят лицензии

Описание для 8.3.27 и 8.5.1 [офиц., п. 10.4]. Поиск идёт по шагам и прекращается на первой найденной лицензии.

### 5.1. Клиентская лицензия

**Шаг 1. На компьютере клиента:**

1. источник, из которого лицензия была получена при последнем успешном подключении (тот же файл `*.lic` или ключ HASP той же серии и типа);
2. файлы программных лицензий на локальном компьютере (каталоги из раздела 3.6);
3. локальный ключ HASP;
4. многопользовательский ключ HASP через HASP License Manager, в порядке серий `ORGL8` → `ORG8A` → `ORG8B`; при нескольких менеджерах с ключами одной серии ключ выбирается случайно либо в порядке из `nethasp.ini`;
5. для базовой конфигурации — лицензия базовой версии.

**Шаг 2. На компьютере менеджера кластера с сервисом сеансовых данных:**

1. запомненный источник;
2. файлы программных лицензий на этом компьютере;
3. многопользовательские ключи HASP, вставленные в этот компьютер;
4. многопользовательский ключ HASP через HASP License Manager.

**Шаг 3. На компьютере менеджера кластера с сервисом лицензирования:**

1. запомненный файл программной лицензии;
2. файлы программных лицензий на этом компьютере.

Шаги 2 и 3 выполняются, только если у информационной базы включена выдача лицензий сервером (раздел 5.3).

### 5.2. Серверная лицензия

Проверяется при установке соединения клиента с рабочим процессом.

**Шаг 1. На компьютере рабочего процесса, обслуживающего соединение:**

1. запомненный источник (файл или ключ);
2. программная лицензия 32-разрядного сервера (только для 32-разрядного сервера);
3. программная лицензия 64-разрядного сервера;
4. локальный ключ 32-разрядного сервера (только для 32-разрядного сервера);
5. локальный ключ 64-разрядного сервера.

**Шаг 2. На менеджере кластера с сервисом лицензирования:** запомненный файл; программная лицензия 32-разрядного сервера (для 32-разрядного сервера); программная лицензия 64-разрядного сервера.

Сводная таблица «что где ищется»:

| Место поиска | Клиентская лицензия | Серверная лицензия |
|---|---|---|
| Компьютер клиента | файлы `*.lic`, локальный HASP, сетевой HASP через HASP LM, базовая | — |
| Компьютер `rphost` | — | файлы `*.lic`, локальный серверный ключ HASP |
| Менеджер с сервисом сеансовых данных | файлы `*.lic`, многопользовательские HASP на этом компьютере, HASP через HASP LM | — |
| Менеджер с сервисом лицензирования | только файлы `*.lic` | только файлы `*.lic` |

Следствия:

- **Ключи HASP сервис лицензирования не раздаёт** — только программные лицензии.
- Сетевой многопользовательский ключ сервер может использовать и «локально» (ключ вставлен в компьютер сервера, HASP License Manager не нужен), и через HASP License Manager. Считает такие лицензии менеджер кластера с сервисом сеансовых данных, расход — «на сеанс» [офиц., п. 10.2.5.3.3].
- Когда клиентских и серверных источников много, запуск клиента должен приводить к однозначному выбору лицензии, иначе возможен перерасход (предупреждение документации).

### 5.3. Параметр базы «Разрешить выдачу лицензий сервером 1С:Предприятия»

| Значение | Поведение [офиц.] |
|---|---|
| Да (`allow`) | сервер выдаёт клиентскую лицензию, когда клиент не смог получить её сам |
| Нет (`deny`) | сервер не выдаёт; клиент без собственной лицензии получает «Не найдена лицензия. Не обнаружен ключ защиты программы или полученная программная лицензия!» |

Где задаётся: диалог создания базы в клиенте, свойства базы в консоли кластера или в «Управлении серверами», утилита `rac`:

```bash
V=8.3.27.2074; RAC=/opt/1cv8/x86_64/$V/rac
CL=$($RAC cluster list | awk '/^cluster /{print $3}')

$RAC infobase summary list --cluster=$CL                       # имена и идентификаторы баз
IB='подставить-uuid-базы'                                        # из вывода предыдущей команды

# посмотреть (нужен администратор базы)
$RAC infobase info --cluster=$CL --infobase=$IB \
     --infobase-user=Администратор --infobase-pwd='***' | grep license-distribution

# включить выдачу лицензий сервером
$RAC infobase update --cluster=$CL --infobase=$IB \
     --infobase-user=Администратор --infobase-pwd='***' --license-distribution=allow

# при создании базы
$RAC infobase create --cluster=$CL --create-database --name=demo --dbms=PostgreSQL \
     --db-server=localhost --db-name=demo --locale=ru_RU --db-user=postgres --db-pwd='***' \
     --license-distribution=allow
```

- Значения параметра `--license-distribution`: `allow` | `deny`.
- ⚠ не подтверждено: значение по умолчанию при создании базы через `rac` без этого параметра (в документации справочника по `rac` нет; по опыту сообщества база создаётся с `deny` [практика]). Указывать явно и после создания проверять: `$RAC infobase info … | grep license-distribution`.
- У автономного сервера (`ibsrv`) аналог — параметр `infobase.distribute-licenses` конфигурационного файла (в примерах документации `distribute-licenses: yes`; допустимы `enable`/`allow`/`yes`/`true` и `disable`/`deny`/`no`/`false`) или ключ командной строки `--distribute-licenses=<флаг>` (`allow`/`yes`/`true` либо `deny`/`no`/`false`; по умолчанию `allow`) [офиц., приложения 3 и 4].
- При создании базы клиентом из командной строки (`1cv8 CREATEINFOBASE 'Srvr=…;Ref=…;…;LicDstr=Y'`) тому же свойству соответствует параметр строки `LicDstr`: `Y` — получать лицензии через сервер, `N` — нет; **по умолчанию `N`** [офиц., приложение 7]. Это косвенно подтверждает, что и у `rac infobase create` без явного `--license-distribution=allow` выдача будет выключена. Подробнее — `kb/1c/06-infobazy-ibcmd-paketnyj-rezhim.md`.

### 5.4. Отключение поиска ключа HASP на клиенте

Если клиентские лицензии выдаёт сервер, поиск ключа только замедляет запуск [офиц.]:

| Способ | Как |
|---|---|
| Файл `1cestart.cfg` | `UseHwLicenses=0` (умолчание `1`). Linux: `~/.1C/1cestart/1cestart.cfg`; Windows: `%APPDATA%\1C\1CEStart\1cestart.cfg` |
| Диалог запуска | «Настройка… — Использовать аппаратную лицензию (ключ защиты)» — меняет тот же параметр |
| Командная строка клиента | `/UseHwLicenses-` (не искать), `/UseHwLicenses+` (искать) |

Поведение платформы: если поиск включён, ключ не найден, запуск успешен, а поиск занял больше 3 секунд — пользователю предлагается его отключить; если поиск отключён, а лицензия не получена ни от сервера, ни от расширения веб-сервера — предлагается включить. При `UseHwLicenses=0` не используется и запомненный ключ.

### 5.5. Особые случаи, о которые спотыкаются на сервере без графики

Всё по документации 8.3.27, глава 10 [офиц.]:

| Случай | Что с лицензиями |
|---|---|
| Пакетный запуск Конфигуратора на сервере (`1cv8 DESIGNER …`, в том числе под `xvfb-run`) | Конфигуратор — клиентское приложение: ему нужна **клиентская** лицензия. На сервере, где лежит только серверная лицензия, он получит «Не найдена лицензия…», пока у базы не включена выдача лицензий сервером и на сервере нет клиентской лицензии |
| `ibcmd` в автономном режиме (`--data=…`) с клиент-серверной базой | требует **серверную** лицензию — запускать только на компьютере, где она доступна (п. 10.3.5.2) |
| `ibcmd` с подключением к работающему автономному серверу (`--pid`, `--remote`) и не файловой базой | автономный сервер проверяет серверную лицензию |
| Автономный сервер (`ibsrv`) с файловой базой | до 3 клиентских сеансов включительно серверная лицензия не требуется и не проверяется; фоновые задания и интернет-сервисы в счёт не идут |
| Web-сервисы, HTTP-сервисы, OData, фоновые и регламентные задания | клиентскую лицензию не занимают; серверная лицензия для клиент-серверной базы нужна |
| COM-соединение (внешнее соединение; только Windows) | порядок поиска для программных лицензий: однопользовательские → многопользовательские → лицензии на сервере 1С. Если внутрипроцессный COM-сервер запущен из кода на сервере 1С, работающем по программной серверной лицензии, COM-соединение использует серверную лицензию |
| Веб-клиент и однопользовательская лицензия (или локальный ключ) на компьютере сервера 1С либо веб-сервера | допускается одно произвольное клиентское приложение (включая веб-клиент) на компьютере без собственной лицензии — этого хватает для разработки и отладки; с локальным ключом запускается только один веб-клиент, для второго сеанса нужна многопользовательская лицензия (п. 10.2.5.6, 10.3.4.6) |
| Мобильный клиент | всегда занимает отдельную лицензию из многопользовательского комплекта («на сеанс») |
| Тонкий клиент через веб-сервер | сначала пробует свою лицензию (тогда расход «на компьютер»), иначе лицензию выдаёт сервер или модуль расширения веб-сервера («на сеанс») |

Спящие сеансы [офиц., см. `kb/1c/10-proizvoditelnost-otkazoustojchivost-ekspluataciya.md`]: уснувший сеанс клиентскую лицензию освобождает, при пробуждении пытается получить её снова — поэтому «потерянных» лицензий среди спящих сеансов искать не нужно, а пользователь после паузы может получить отказ, если лицензии за это время заняты.

## 6. Аппаратные ключи HASP на Linux

### 6.1. Ключи 1С: маркировка и ограничения

| Назначение | Маркировка | Серия (так она видна в строке описания лицензии и в событии `LIC`) |
|---|---|---|
| Локальный клиентский ключ (1 рабочее место) | `ORGL8` | `ORGL8` (`client`) |
| Многопользовательский клиентский на 5, 10, 20, 50, 100 | `NET5 ORGL8`, `NET10 ORGL8`, `NET20 ORGL8`, `NET50 ORGL8`, `NET100 ORGL8` | `ORGL8` (`client`) |
| Многопользовательский на 300 | `NET250+ ORG8A` | `ORG8A` (`client 300`) |
| Многопользовательский на 500 | `NET250+ ORG8B` | `ORG8B` (`client 500`) |
| Локальный ключ 32-разрядного сервера | `ENSR8` | `ENSR8` (`server 32`) |
| Локальный ключ 64-разрядного сервера | `EN8SA` | `EN8SA` (`server 64`) |

В строке описания лицензии после серии идёт тип — `Локальный` (ключ в том же компьютере, который получил лицензию) или `Сетевой` (через HASP License Manager) — и число лицензий ключа, например `ORG8A Сетевой 300` (раздел 8.3).

Правила [офиц., п. 10.2.1–10.2.6]:

- Защита — HASP4 Net. Считает пользователей либо HASP License Manager, либо сервер 1С.
- На одном компьютере одновременно работает **по одному ключу каждой серии** (`ORGL8`, `ORG8A`, `ORG8B`). Несколько ключей одной серии в одном компьютере бессмысленны: они неразличимы, используется один произвольный. Поэтому два ключа `NET20 ORGL8` разносят по разным компьютерам с HASP License Manager.
- Комплект на 1000 пользователей — два ключа `NET250+ ORG8B` (тоже на разных компьютерах).
- **Серверный ключ — локальный, по сети недоступен.** Он ставится в компьютер, где выполняется хотя бы один `rphost`.
- Локальный клиентский ключ в терминальной сессии не работает (Windows 7 / Server 2012 и новее).
- Запоминается ключ, из которого лицензия получена в прошлый раз; следующая попытка сначала идёт к нему.
- Не использовать один и тот же многопользовательский ключ одновременно через HASP License Manager и через сервер 1С: лицензии с `Timeout = 0` (по Aladdin Monitor) сервер считает занятыми.
- На ARM64 и E2K аппаратные ключи не поддерживаются.

### 6.2. Официальная позиция по виртуальным машинам

Документация 8.3.27 (п. 10.2.3) прямо говорит: **при использовании ключей защиты USB over IP не поддерживается** (проброс USB-устройства физического компьютера в ВМ по сети). Для работы в ВМ рекомендуется система программного лицензирования либо сервис лицензирования кластера, размещённый на физическом компьютере [офиц.].

На практике ключи в ВМ работают — через штатный проброс USB гипервизора и через USB/IP [практика], — но при обращении в поддержку 1С такая конфигурация формально вне поддержки. Варианты по убыванию надёжности:

1. программные лицензии + сервис лицензирования на физическом компьютере (раздел 7);
2. программные лицензии в ВМ с зафиксированными параметрами (раздел 9);
3. программная лицензия, привязанная к ключу HASP, который доступен ВМ до и после миграции (п. 6.8);
4. ключ HASP, проброшенный в ВМ (п. 6.9).

### 6.3. Драйвер ключа: три варианта

Сначала установить драйвер, потом вставлять ключ. На работающей системе ключ не вынимать [офиц.].

**Вариант А — как в документации 1С** [офиц., п. 10.2.7.2]. Дистрибутив «HASP Device Driver» берётся с `https://releases.1c.ru/project/AddCompDriverHASP`:

```bash
tar xzf HASP_SRM_LINUX_3.50_Run-time_Installer_script.tar.gz
cd HASP_SRM_LINUX_3.50_Run-time_Installer_script
sudo ./dinst .          # точка в конце обязательна
# удаление: sudo ./dunst   (из того же каталога)
```

Имя архива в документации не менялось много лет; фактическое имя файла на портале может отличаться — подставить своё.

**Вариант Б — Sentinel LDK Run-time Environment от Thales (`aksusbd`)** [офиц. Thales для самого драйвера; практика — для его применения с ключами 1С]. Это современное название того же драйвера. Поставляется как deb-пакет, rpm-пакет, архив со сценарием `dinst` или образ Docker; берётся с портала поддержки Thales (`https://supportportal.thalesgroup.com/csm?id=sentinel`) либо из архива с releases.1c.ru.

| Поддерживаемые ОС для deb-пакета 10.33 | Ubuntu Server и Desktop **24.04 и 26.04**, Debian 13. Ubuntu 22.04 в перечне 10.33 нет: формально для 22.04 нужна более ранняя версия RTE, в readme которой 22.04 значится (⚠ какая именно — смотреть readme конкретной версии на портале Thales), либо вариант со сценарием `dinst`; на практике пакет может установиться и работать и вне перечня, но это уже вне поддержки Thales |
| 32-разрядные библиотеки совместимости | **не требуются** начиная с версии 7.80 (в истории изменений: «native support for both 32-bit and 64-bit architectures», пакеты совместимости x86 больше не нужны). `libc6:i386` нужен только очень старым версиям драйвера и пакету `haspd` Etersoft |
| Службы | `aksusbd` (драйвер ключей) и `hasplmd` (Sentinel License Manager) |

```bash
# по инструкции Thales: перед установкой ВЫНУТЬ ключ, после установки вставить обратно
sudo dpkg -i aksusbd_10.33-1_amd64.deb        # подставить свою версию; работа 10.11 на Ubuntu 24.04 подтверждена на форуме Infostart
systemctl status aksusbd hasplmd              # две службы: драйвер ключей и менеджер лицензий Sentinel
sudo ss -tulpn | grep 1947                    # Sentinel License Manager слушает порт 1947 (TCP и UDP)
# удаление: sudo dpkg -r aksusbd

# тот же драйвер в виде архива со сценарием (аналог варианта А в современной поставке): из каталога распакованного архива
sudo ./dinst .                                # точка в конце обязательна
```

- Службы `aksusbd.service` и `hasplmd.service`; веб-интерфейс Sentinel Admin Control Center — `http://localhost:1947`.
- Порядок при обновлении драйвера на сервере, где ключ уже работает (совмещает требование 1С «не вынимать ключ во время работы» и требование Thales «вынуть ключ перед установкой»): технологическое окно → остановить сервер 1С (`sudo systemctl stop srv1cv8-$V@default`) → вынуть ключ (в ВМ — отключить проброс) → установить пакет → вставить ключ, дождаться окончания мигания → `systemctl status aksusbd hasplmd` и `lsusb | grep -i 0529` → запустить сервер 1С → проверить выдачу лицензии (раздел 8.3).
- Известная проблема из документации Thales (SM-116811): после установки одной версии поверх другой (переход через границу 8.13 ↔ 8.15 в любую сторону) демон `hasplmd` может не запуститься автоматически. Лечение: запустить установку второй раз либо `sudo systemctl start hasplmd`.
- Понижение версии драйвера может сделать хранилище лицензий Sentinel недоступным (ошибка `HASP_DEVICE_ERR`) — к ключам 1С (HASP4/HASP HL) это отношения почти не имеет, но ставить старую версию поверх новой без нужды не следует.
- После подключения ключа драйвер может автоматически обновить микропрограмму старых ключей HASP HL: ключ в это время непрерывно мигает, вынимать его нельзя [офиц. Thales].
- ⚠ не подтверждено первоисточником 1С: с какими версиями Sentinel RTE фирма «1С» тестировала свои ключи. Документация 1С до сих пор называет архив `HASP_SRM_LINUX_3.50_Run-time_Installer_script`, а практика сообщества — пакеты `aksusbd` 7.x–10.x. Перед обновлением драйвера на рабочем сервере с ключом проверить новую версию на стенде.

**Вариант В — пакет `haspd` от Etersoft** [офиц. для ИТС-инструкции по Ubuntu 16.04; практика для новых версий]. Статья ИТС «Установка Платформы „1С:Предприятие“ в ОС Linux» использует именно его:

```bash
sudo dpkg --add-architecture i386 && sudo apt update
sudo apt-get -y install libc6:i386
sudo dpkg -i haspd_8.53-eter1ubuntu_amd64.deb || sudo apt -f install
sudo systemctl start haspd
sudo systemctl status haspd
```

- Каталог сборок: `https://download.etersoft.ru/pub/Etersoft/HASP/`. На 10.10.2026: каталог `last/` указывает на 8.23 (`haspd_8.23-eter3ubuntu_amd64.deb`, август 2022); новейшая версия 8.53 (`8.53/x86_64/Ubuntu/22.04/haspd_8.53-eter1ubuntu_amd64.deb`, 31.03.2023). **Сборки для Ubuntu 24.04 нет** — на 24.04 использовать вариант Б.
- В пакет входят драйвер ключей и менеджеры лицензий (служба одна — `haspd`); по описанию Etersoft, загружаются только драйверы для вставленных ключей. Проверка: `sudo systemctl status haspd` (в документации Etersoft — `serv haspd status`).
- `haspd` и `aksusbd` — взаимоисключающие пакеты (оба содержат демон `aksusbd`); ставить один [практика].

### 6.4. Проверка, что ключ виден

```bash
lsusb | grep -i 0529                 # 0529:0001 Aladdin Knowledge Systems HASP copy protection dongle
sudo dmesg | grep -i -E 'hasp|aladdin|0529' | tail
systemctl status aksusbd hasplmd     # вариант Б;  для варианта В: systemctl status haspd
sudo ss -tulpn | grep -E ':(475|1947)\b'

# Sentinel Admin Control Center без браузера на сервере [практика]
curl -s -o /dev/null -w '%{http_code}\n' http://localhost:1947/      # отвечает ли менеджер (ожидается 200 или перенаправление 30x)
# список ключей: страница «Sentinel Keys» (/_int_/devices.html) заполняется скриптом, поэтому в самом HTML ключей нет.
# Данные таблицы отдаёт служебный адрес (⚠ не подтверждено документацией Thales, используется в скриптах мониторинга):
curl -s 'http://localhost:1947/_int_/tab_devices.html?haspid=0&featureid=-1&vendorid=0&productid=0&filterfrom=1&filterto=20'
# надёжнее — туннель с рабочего места и открыть http://localhost:1947 в браузере (раздел «Sentinel Keys»)
ssh -L 1947:localhost:1947 admin@srv1c
```

- По умолчанию Admin Control Center доступен только с самого сервера. Удалённый доступ включается в самом ACC: «Configuration — Basic Settings — **Allow Remote Access to ACC**» (по умолчанию выключено; Thales рекомендует не включать без необходимости), при этом на вкладке «Network» параметр **Network Visibility** должен быть «All Network Adapters» [офиц. Thales]. Настройки сохраняются в `/etc/hasplm/hasplm.ini` (на Linux и macOS; файл появляется только после первого изменения настроек через ACC) [офиц. Thales]. ⚠ не подтверждено: имя параметра в файле — по практике `accremote = 1` в секции `[SERVER]` (страница документации о `hasplm.ini` перечня параметров не содержит). Проще и безопаснее SSH-туннель.
- ⚠ не подтверждено [практика]: в ACC ключи 1С показываются с числовым идентификатором производителя и типом ключа (HASP HL / HASP4), а серию 1С (`ORGL8`, `EN8SA`) ACC не показывает — её смотрят по маркировке на корпусе ключа и в событии `LIC` технологического журнала (раздел 8.4).
- Окончательная проверка — со стороны 1С: запустить клиент и посмотреть, какая лицензия выдана (раздел 8.3), или включить события `HASP` в технологическом журнале (раздел 8.4).
- После установки или переустановки драйвера перезапустить сервер 1С: `sudo systemctl restart srv1cv8-$V@default` [практика].

### 6.5. Два разных «менеджера лицензий» и их порты

| Программа | Порт | Что раздаёт | Нужен ли 1С |
|---|---|---|---|
| **HASP License Manager** (`hasplm` в Linux; `nhsrvw32.exe` / служба «HASP Loader» в Windows) | **475**, обращение всегда по **UDP**; только **IPv4** | сетевые ключи HASP4 Net старым API — именно им пользуется 1С до 8.5.4 | да, если клиенты должны получать лицензии с многопользовательского ключа по сети |
| Sentinel License Manager (`hasplmd`, часть Sentinel LDK RTE) | 1947 TCP/UDP | ключи для приложений на новом API Sentinel; Admin Control Center | как драйвер и средство диагностики. Сетевые лицензии клиентам 1С он не раздаёт: документация 1С знает единственный способ сетевой раздачи ключа — HASP License Manager (отдельный дистрибутив `AddCompNetHASP`, порт 475, UDP) [офиц. для способа раздачи; ⚠ прямого утверждения «hasplmd не раздаёт ключи 1С» в документации 1С и Thales нет — это вывод и опыт сообщества] |

Когда HASP License Manager **не нужен**:

- серверный ключ (`EN8SA`) вставлен в сервер 1С — достаточно драйвера;
- многопользовательский ключ вставлен в сервер 1С, и лицензии клиентам выдаёт сам сервер («локальный многопользовательский ключ без HASP License Manager») — достаточно драйвера и параметра базы «Разрешить выдачу лицензий сервером».

Установка HASP License Manager в Linux по документации [офиц., п. 10.2.8.2]. Дистрибутив: `https://releases.1c.ru/project/AddCompNetHASP`; драйвер ключа должен быть уже установлен.

```bash
sudo mkdir -p /opt/hasplm && sudo cp hasplm_linux_8.30.tgz /opt/hasplm/ && cd /opt/hasplm
sudo tar xzf hasplm_linux_8.30.tgz
sudo /opt/hasplm/hasplm                         # запуск вручную
sudo /opt/hasplm/hasplm -c /etc/nhsrv.ini       # запуск с файлом настроек
```

Документация предлагает автозапуск строкой в `/etc/rc.local`; в Ubuntu с systemd удобнее юнит [практика, ⚠ тип службы подобрать по поведению `hasplm` — уходит ли он в фон]:

```ini
# /etc/systemd/system/hasplm.service
[Unit]
Description=HASP License Manager (NetHASP, UDP 475)
After=network-online.target aksusbd.service
Wants=network-online.target

[Service]
Type=forking
ExecStart=/opt/hasplm/hasplm -c /etc/nhsrv.ini
Restart=on-failure

[Install]
WantedBy=multi-user.target
```

```bash
sudo systemctl daemon-reload && sudo systemctl enable --now hasplm
sudo ufw allow 475/udp                           # если включён ufw и ключ раздаётся в сеть
```

Пакет `haspd` от Etersoft уже содержит `hasplm`, отдельно ставить не нужно [практика].

### 6.6. `nethasp.ini` — настройка клиента 1С для работы с HASP License Manager

Файл читает приложение 1С, которое **ищет** сетевой ключ: клиент на рабочем месте, сервер 1С, модуль расширения веб-сервера.

Расположение [офиц., приложение 3, п. 3.25]:

- каталог конфигурационных файлов платформы. В Linux они ищутся в порядке: `/opt/1cv8/x86_64/<версия>/conf` → `/opt/1cv8/conf` → `~/.1cv8/1C/1cv8/conf` → каталог из `ConfLocation`;
- если там файла нет: текущий каталог → домашний каталог пользователя → `/etc`;
- образец с полным перечнем параметров (почти всё закомментировано) копируется при установке в каталог `conf` установочного каталога платформы.

Для сервера 1С практичный вариант — `/opt/1cv8/conf/nethasp.ini` (не зависит от номера версии) [практика].

Структура: секции `[NH_COMMON]`, `[NH_IPX]`, `[NH_NETBIOS]`, `[NH_TCPIP]`. Параметр в секции протокола приоритетнее того же параметра в `[NH_COMMON]`. Комментарий — с `;`. Регистр имён не важен.

| Секция | Параметр | Значения | Умолчание | Смысл |
|---|---|---|---|---|
| `[NH_COMMON]` | `NH_IPX`, `NH_NETBIOS`, `NH_TCPIP` | `Enabled` / `Disabled` | `Enabled` | использовать ли протокол |
| `[NH_COMMON]` | `NH_SESSION` | секунды | 2 | сколько времени пытаться соединиться с менеджером |
| `[NH_COMMON]` | `NH_SEND_RCV` | секунды | 1 | максимальное время отправки или получения пакета |
| `[NH_TCPIP]` | `NH_SERVER_ADDR` | адреса или имена через запятую | — | адреса всех HASP License Manager; число не ограничено |
| `[NH_TCPIP]` | `NH_SERVER_NAME` | до 6 имён по 7 символов | — | имена менеджеров |
| `[NH_TCPIP]` | `NH_PORT_NUMBER` | число | `475` | порт |
| `[NH_TCPIP]` | `NH_TCPIP_METHOD` | `TCP` / `UDP` | `UDP` | значение `TCP` игнорируется — обращение всегда по UDP |
| `[NH_TCPIP]` | `NH_USE_BROADCAST` | `Enabled` / `Disabled` | `Enabled` | широковещательный поиск |
| `[NH_TCPIP]` | `NH_SESSION`, `NH_SEND_RCV` | секунды | 2 / 1 | то же, для протокола |

Типовой файл — явный адрес менеджера, без широковещания (нужно, когда ключ в другой подсети или менеджеров несколько):

```ini
[NH_COMMON]
NH_IPX=Disabled
NH_NETBIOS=Disabled
NH_TCPIP=Enabled

[NH_TCPIP]
NH_SERVER_ADDR=192.168.1.20, 192.168.1.21
NH_PORT_NUMBER=475
NH_TCPIP_METHOD=UDP
NH_USE_BROADCAST=Disabled
NH_SESSION=4
NH_SEND_RCV=2
```

```bash
sudo install -m 644 -o root -g root nethasp.ini /opt/1cv8/conf/nethasp.ini
sudo systemctl restart srv1cv8-$V@default
```

Замечания: по умолчанию протокол определяется автоматически, и менять это стоит только при нестабильной работе или задержках [офиц.]. Увеличение `NH_SESSION` и `NH_SEND_RCV` помогает на медленных каналах [практика].

### 6.7. `nhsrv.ini` — настройки самого HASP License Manager

В Linux путь задаётся только параметром `-c`; расположения по умолчанию нет. Секция `[NHS_SERVER]` [офиц.]:

| Параметр | Значения | Умолчание | Смысл |
|---|---|---|---|
| `NHS_IP_LIMIT` | `10.1.1.1`, `10.1.1.*`, `10.1.1.1/24` | — | какие станции обслуживать |
| `NHS_ADAPTER` | адрес и маска | — | через какую сетевую карту работать (для Win32) |
| `NHS_USERLIST` | число | `250` | максимум одновременно подключённых пользователей |

Для ключей на 300, 500 и 1000 пользователей `NHS_USERLIST` нужно обязательно увеличить [офиц.]:

```ini
[NHS_SERVER]
NHS_USERLIST=600
NHS_IP_LIMIT=192.168.1.*
```

### 6.8. Программная лицензия, привязанная к ключу HASP

- При активации объектом привязки выбирается не компьютер, а один из доступных ключей HASP — любой ключ 1С, локальный или сетевой [офиц.].
- Один пинкод активируется только с одним ключом; повторять активацию с тем же ключом и теми же данными владельца можно неограниченно, тем же пинкодом.
- Для сетевого ключа проверка привязки занимает **1 свободную лицензию на 1 секунду** не чаще раза в 20 секунд — в ключе всегда должна оставаться хотя бы одна свободная лицензия.
- Если в сети несколько ключей одной серии, нужный менеджер прописать в `nethasp.ini` на компьютере, где лежит файл лицензии.
- Так выдаются расширения ПРОФ и КОРП для аппаратных лицензий (раздел 2.4). Community-лицензию к ключу привязать нельзя.

### 6.9. Проброс USB-ключа в виртуальную машину

Напоминание: 1С официально не поддерживает USB over IP для ключей (п. 6.2). Ниже — практика.

| Гипервизор | Способ | Ограничения |
|---|---|---|
| **Hyper-V** (в том числе на Windows 10/11) | штатного проброса произвольных USB-устройств **нет**. Варианты: USB/IP (`usbipd-win` на хосте + `usbip` в госте), аппаратные сетевые USB-концентраторы (Digi AnywhereUSB, SEH и подобные — нужен их клиент для Linux), сетевой клиентский ключ на физическом компьютере с HASP License Manager | серверный ключ по сети не раздаётся — ему нужен именно проброс; при потере связи ключ «пропадает». Проброс целого USB-контроллера (Discrete Device Assignment) есть только в Hyper-V на Windows Server, на Windows 10/11 его нет [практика] |
| **VMware Workstation** | штатно: USB-контроллер в ВМ, «VM — Removable Devices — … — Connect (Disconnect from Host)» | ключ принадлежит одной ВМ |
| **VMware ESXi** | USB passthrough с хоста | привязка ВМ к хосту, сложности с миграцией [практика] |
| **VirtualBox** | фильтр USB: `VBoxManage usbfilter add 0 --target "srv1c" --name "HASP" --vendorid 0529 --productid 0001` | в ВМ должен быть включён USB-контроллер (`VBoxManage modifyvm "srv1c" --usbohci on`, для USB 2.0/3.0 — `--usbehci on` / `--usbxhci on`); в VirtualBox до 7.0 контроллеры USB 2.0/3.0 требовали Extension Pack [практика] |
| **Proxmox / KVM** | `qm set <vmid> -usb0 host=0529:0001`; при нескольких одинаковых ключах — по порту: `qm set <vmid> -usb0 host=2-1.2`; для порта USB 3 — `host=…,usb3=yes` | USB-концентраторы пробросить нельзя; одинаковые ключи различать только по порту; подключение через монитор (`device_add usb-host,…`) действует до остановки ВМ [офиц. Proxmox wiki] |

USB/IP с Windows-хоста в гостевую Ubuntu [практика; команды `usbip` — по man-странице Ubuntu]:

```powershell
# хост Windows, PowerShell от администратора
winget install usbipd
usbipd list                       # найти ключ и его BUSID, например 2-3
usbipd bind --busid=2-3           # разрешить экспорт устройства (сохраняется после перезагрузки)
# служба usbipd слушает TCP 3240; установщик создаёт правило брандмауэра «usbipd» для локальных подсетей.
# Сторонний межсетевой экран нужно настроить вручную: входящие на 3240/tcp только с адреса ВМ.
```

```bash
# гость Ubuntu
sudo apt install -y linux-tools-generic hwdata     # usbip входит в linux-tools для текущего ядра (для ядра -virtual: linux-tools-virtual)
# надёжнее привязаться к работающему ядру: команда-обёртка /usr/bin/usbip из linux-tools-common ищет /usr/lib/linux-tools/$(uname -r)/usbip
sudo apt install -y "linux-tools-$(uname -r)"
# модуль vhci-hcd в Ubuntu лежит в пакете дополнительных модулей; если modprobe отвечает «Module vhci-hcd not found» [практика]:
sudo apt install -y "linux-modules-extra-$(uname -r)"
sudo modprobe vhci-hcd
usbip list --remote=192.168.1.10                   # что экспортирует хост
sudo usbip attach --remote=192.168.1.10 --busid=2-3
usbip port                                          # импортированные устройства
lsusb | grep -i 0529
sudo usbip detach --port=0                          # отключить
```

Автоподключение ключа до запуска сервера 1С [практика]:

```ini
# /etc/systemd/system/usbip-hasp.service
[Unit]
Description=Attach HASP key via USB/IP
After=network-online.target
Wants=network-online.target
Before=aksusbd.service

[Service]
Type=oneshot
RemainAfterExit=yes
ExecStartPre=/sbin/modprobe vhci-hcd
ExecStart=/usr/bin/usbip attach --remote=192.168.1.10 --busid=2-3
ExecStop=/usr/bin/usbip detach --port=0

[Install]
WantedBy=multi-user.target
```

```bash
echo vhci-hcd | sudo tee /etc/modules-load.d/usbip.conf
sudo systemctl daemon-reload && sudo systemctl enable --now usbip-hasp

# чтобы сервер 1С стартовал только после подключения ключа — дополнение (drop-in) к юниту сервера
# (то же делает интерактивная команда: sudo systemctl edit srv1cv8-$V@default)
sudo install -d "/etc/systemd/system/srv1cv8-$V@default.service.d"
printf '[Unit]\nWants=usbip-hasp.service\nAfter=usbip-hasp.service\n' \
  | sudo tee "/etc/systemd/system/srv1cv8-$V@default.service.d/usbip-hasp.conf" >/dev/null
sudo systemctl daemon-reload
systemctl cat "srv1cv8-$V@default" | tail -n 6     # проверить, что дополнение применилось
```

В самом юните `usbip-hasp.service` порядок относительно сервера 1С не задан (имя юнита сервера содержит номер версии и меняется при обновлении платформы), поэтому зависимость задаётся дополнением к юниту сервера и после обновления платформы её нужно повторить для нового юнита [практика].

Слабые места USB/IP: после перезагрузки хоста или обрыва сети устройство нужно подключать заново; обновление ядра гостя требует соответствующего пакета `linux-tools-*`; между потерей ключа и его возвратом сервер 1С остаётся без лицензий. Для рабочего контура предпочтительнее программные лицензии.

## 7. Сервис лицензирования кластера на отдельном сервере

### 7.1. Что это

- **Сервис лицензирования** — один из сервисов менеджера кластера; выдаёт **программные** лицензии (клиентские и серверные). Характеристика «Перенос+»: его можно назначить на определённый рабочий сервер [офиц., п. 2.2.3].
- Получение клиентских лицензий обеспечивает **сервис сеансовых данных**: менеджер, на который он назначен, сам ищет файлы `*.lic` и многопользовательские ключи HASP на своём компьютере (шаг 2 в разделе 5.1). Сервис лицензирования — следующая ступень поиска (шаг 3), и раздаёт он только файлы.
- Если сервис лицензирования временно недоступен, а лицензии через него уже получались, то временно выдаются такие же лицензии, но **не дольше 20 секунд** [офиц.]. Дальше новые сеансы лицензию не получат.
- Сервис лицензирования нужно **явно** разместить требованием назначения функциональности на том рабочем сервере, к которому привязаны лицензии [офиц., п. 2.2.7.4.2].

Зачем выносить: файлы `*.lic` привязываются к компьютеру, на котором работает менеджер с сервисом лицензирования. Если это физический компьютер или маленькая ВМ с неизменными параметрами, то серверы с рабочими процессами (в том числе ВМ с Ubuntu) можно пересоздавать, мигрировать и менять им ресурсы без повторной активации. Это рекомендация самой документации для виртуальных сред (п. 10.3.1.6).

### 7.2. Схема

```text
            клиенты 1С
                │ 1541, 1560–1591
                ▼
┌──────────────────────────────┐        1540, 1541, 1560–1591         ┌─────────────────────────────┐
│ srv1c  (ВМ Ubuntu)           │◄────────────────────────────────────►│ lic1c (физический ПК или    │
│ центральный сервер кластера  │                                      │ ВМ с фиксированными         │
│ ragent, rmngr, rphost        │                                      │ параметрами; Linux/Windows) │
│ базы, сеансы, PostgreSQL     │                                      │ ragent, rmngr               │
│ лицензий НЕТ                 │                                      │ только сервис лицензирования│
└──────────────────────────────┘                                      │ /var/1C/licenses/*.lic      │
                                                                      │ или %ProgramData%\1C\licenses│
                                                                      └─────────────────────────────┘
```

Требования назначения функциональности для `lic1c` (пример из документации, п. 2.2.7.5.3) [офиц.]:

| № | Объект требования | Тип требования | Имя ИБ | Значение дополнительного параметра |
|---|---|---|---|---|
| 1 | Сервис лицензирования | Назначать | — | — |
| 2 | Любой объект требования | Не назначать | — | — |

Требование 1 размещает сервис на `lic1c`; требование 2 запрещает на нём всё остальное (сеансы, рабочие процессы с базами, прочие сервисы). Порядок важен: в списке сервера применяется **первое** подходящее требование. На остальных серверах требований не нужно: если есть сервер с явным «Назначать», используются только такие серверы.

### 7.3. Пошагово

1. **Подготовить `lic1c`.** Физический компьютер (подойдёт и Windows-хост виртуализации — кластер может состоять из серверов на разных ОС, в примере документации `SRV1` — Windows, `SRV2` — Linux) либо ВМ со статическим MAC и неизменными ресурсами. Имя хоста окончательное; серверы взаимно разрешают имена друг друга.
2. **Установить на `lic1c` сервер 1С той же версии**, что и в кластере, и запустить агент сервера (`ragent`): в Linux — как в `kb/1c/02-ustanovka-servera-ubuntu.md`, в Windows — служба «Агент сервера 1С:Предприятия». Открыть между серверами порты 1540, 1541, 1560–1591/tcp.
3. **Добавить `lic1c` в кластер как рабочий сервер** (не центральный): консоль кластера или «Управление серверами» → «Рабочие серверы — Создать — Рабочий сервер». Документация (п. 3.1.5.1.3) советует после добавления «удалить регистрацию главного сервера кластера» на добавленном компьютере. ⚠ Трактовка автора: на `lic1c` не должно оставаться собственного локального кластера, который агент создал при первом запуске (иначе его менеджер занимает порт 1541).
4. **Создать два требования** из таблицы 7.2 в ветке «Требования назначения функциональности» сервера `lic1c`.
5. **Применить требования**: контекстное меню кластера → «Применить требования назначения функциональности (частичное)». Полное применение может аварийно завершить все клиентские приложения — выполнять в технологическое окно.
6. **Активировать лицензии для `lic1c`**: в помощнике «Получение лицензии» → «Дополнительно — Установка на сервер», в поле «Сервер» указать **`lic1c`**. Иначе лицензия привяжется к другому компьютеру, и кластер её не увидит [офиц.]. Либо `ring license activate` прямо на `lic1c`. Сюда активируются и серверные, и многопользовательские клиентские лицензии.
7. **Проверить**: подключиться клиентом и посмотреть `rac session list --licenses` — в поле `rmngr-address` должен быть `lic1c`, в имени файла — путь на `lic1c`.

То же через `rac` [⚠ параметры `rac server insert` и `rac rule insert` приведены по встроенной справке по памяти — сверить с `rac server help`, `rac rule help`]:

```bash
V=8.3.27.2074; RAC=/opt/1cv8/x86_64/$V/rac
CL=$($RAC cluster list | awk '/^cluster /{print $3}')

# добавить рабочий сервер
$RAC server insert --cluster=$CL --agent-host=lic1c --agent-port=1540 \
     --port-range=1560:1591 --name=lic1c --using=normal
$RAC server list --cluster=$CL                     # узнать идентификатор сервера lic1c
SRV='подставить-uuid-сервера-lic1c'

# требования назначения функциональности
$RAC rule list --cluster=$CL --server=$SRV
$RAC service list --cluster=$CL | grep -i -B1 -A3 licen   # узнать идентификатор сервиса лицензирования (поле name)
$RAC rule insert --cluster=$CL --server=$SRV --position=0 \
     --object-type=LicenseService --rule-type=always       # ⚠ идентификатор сверить с выводом предыдущей команды
$RAC rule insert --cluster=$CL --server=$SRV --position=1 --rule-type=never

# применить (частично) и проверить
$RAC rule apply --cluster=$CL --partial
$RAC rule list --cluster=$CL --server=$SRV
```

- Типы требований в `rac`: `auto` (Авто), `always` (Назначать), `never` (Не назначать).
- ⚠ не подтверждено первоисточником 1С: значение `--object-type` для сервиса лицензирования. В документации справочника по `rac` нет; по практике идентификатор объекта требования совпадает с именем сервиса в выводе `rac service list` (поле `name`), для сервиса лицензирования это `LicenseService` (так же записано в `kb/1c/03-administrirovanie-klastera-ras-rac.md`, раздел 5.10; у независимой реализации протокола `ras` — библиотеки `ras-client` — имена сервисов того же вида, например `EventLogService`). Перед выполнением на рабочем кластере: (1) посмотреть `rac service list`; (2) посмотреть `rac rule help`; (3) либо создать требование в графической консоли («Управление серверами» работает и на Linux-клиенте), выполнить `rac rule list` и взять значение `object-type` оттуда.
- Требование без `--object-type` означает «Любой объект требования»; `--position` считается с 0 [практика, по встроенной справке `rac`].
- Параметры `rac server insert`: `--agent-host`, `--agent-port`, `--port-range=<мин>:<макс>`, `--name`, `--using=main|normal` (`normal` — рабочий сервер, `main` — центральный). ⚠ В документации 1С перечня нет — сверить командой `rac server help` своей версии.
- Локальный кластер, который агент на `lic1c` создал при первом запуске, удаляется через сервер администрирования, подключённый к агенту `lic1c` (на `lic1c`: `ras cluster --daemon --port=1545 localhost:1540`, затем `rac cluster list` и `rac cluster remove --cluster=<uuid>`), либо в графической консоли [практика, ⚠ сверить с `rac cluster help`]. **Безопасный порядок — удалить локальный кластер ДО добавления `lic1c` в основной кластер**: в этот момент у агента `lic1c` зарегистрирован только он, и перепутать нечего. Если `lic1c` уже добавлен, агент знает оба кластера — перед `rac cluster remove` сверить UUID, имя и компьютер кластера по `rac cluster list` и убедиться, что удаляется именно локальный кластер `lic1c`: удаление не того кластера уничтожит рабочий реестр со списком баз. Перед любым удалением сделать копию каталога данных кластера (`/home/usr1cv8/.1cv8/1C/1cv8/`) на обоих серверах.

### 7.4. ПРОФ или КОРП

- Полнофункциональные требования назначения — возможность уровня **КОРП**.
- На серверной лицензии **ПРОФ** требования допускаются, только если **во всех** требованиях пусты «Имя ИБ» и «Значение дополнительного параметра». Вынос сервисов кластера на отдельные рабочие серверы, в частности сервиса лицензирования, при этом разрешён — это прямо сказано в документации (п. 2.2.7.4.1) [офиц.].
- У требования для сервиса лицензирования поле «Имя ИБ» неприменимо в принципе.
- Лицензия для разработчиков и МИНИ допускают только один рабочий сервер в кластере — схема с выделенным сервером лицензирования с ними невозможна [офиц.].

### 7.5. Особенности и риски

- `lic1c` становится **единой точкой отказа**: при его недоступности дольше 20 секунд новые сеансы не получают лицензий. Нужны автозапуск службы, ИБП, мониторинг порта 1540 и процесса `rmngr`.
- Версия платформы на `lic1c` обновляется вместе с остальным кластером.
- Не раздавать одним сервисом лицензии 32- и 64-разрядного сервера.
- Серверная лицензия для `lic1c`. Технически [офиц.]: наличие серверной лицензии проверяется при подключении клиента к рабочему процессу, а на `lic1c` рабочих процессов с базами нет — платформа для него лицензию не запрашивает. Юридически [офиц., v8.1c.ru, вопрос I.16]: формулировка — «если кластер работает на нескольких компьютерах, нужно приобрести отдельную лицензию на каждый компьютер», без исключения для сервера без рабочих процессов; случай выделенного сервера лицензирования на странице не разобран. ⚠ не подтверждено: требуется ли отдельная серверная лицензия на `lic1c` — исходить из того, что требуется, пока партнёр 1С письменно не подтвердит обратное.
- Ключи HASP на `lic1c` сервис лицензирования раздавать не будет; серверный ключ должен стоять там, где работает `rphost`.
- В кластере из одной машины ничего выносить не нужно: все сервисы, включая лицензирование, работают на ней, а лицензии лежат в её `/var/1C/licenses`.

## 8. Диагностика

### 8.1. Порядок действий

1. **Прочитать текст ошибки целиком** и нажать «Подробно» — откроется «Журнал поиска ключа»: где искали лицензию, статус каждого поиска, причина неуспеха [офиц.].
2. **Определить, какой лицензии нет**: клиентской («Не найдена лицензия…») или серверной («На сервере 1С:Предприятия не найдена лицензия…»).
3. На сервере проверить файлы и права: `ls -l /var/1C/licenses`, поиск дублей (раздел 3.6), доступ `usr1cv8` (раздел 3.7).
4. Проверить привязку: `ring license validate` (раздел 8.5) или событие `LIC` с `res=binding` в технологическом журнале.
5. Проверить параметр базы `license-distribution` (раздел 5.3).
6. Посмотреть, кому и какие лицензии выданы: `rac session list --licenses`, `rac process list --licenses` (раздел 8.3).
7. Для HASP: `lsusb`, службы драйвера, порт 475, `nethasp.ini`, события `HASP` в технологическом журнале.
8. Если причина не видна — включить технологический журнал по событиям `LIC` и `HASP` (раздел 8.4), воспроизвести, прочитать `txt`.

### 8.2. Тексты ошибок и их смысл

| Сообщение (или его начало) | Что означает | Куда смотреть |
|---|---|---|
| «Не найдена лицензия. Не обнаружен ключ защиты программы или полученная программная лицензия!» (в тексте документации 8.3.27, п. 10.4.3, окончание — «…полученная электронная лицензия!»; на экране современных сборок — «программная» [практика]) | клиент не нашёл клиентскую лицензию ни у себя, ни на сервере | у базы `license-distribution=deny`; на сервере нет клиентских `*.lic`; закончились лицензии; нет доступа к ключу |
| «На сервере 1С:Предприятия не найдена лицензия. Не обнаружен ключ защиты программы или полученная программная лицензия!» | нет **серверной** лицензии там, где работает `rphost`, и на сервере с сервисом лицензирования | файл серверной лицензии, права, привязка, серверный ключ HASP |
| Диалог с предложением получить лицензию при запуске Конфигуратора, тонкого или толстого клиента («Не обнаружена лицензия для использования программы» — по документации 8.3.27 (разд. 10.4.3, сверено 11.10.2026) конфигуратор, тонкий и толстый клиенты при отсутствии лицензии запускают помощник получения лицензии, а при отказе от него выводят «Не найдена лицензия. Не обнаружен ключ защиты программы или полученная электронная лицензия!» (вариант — «На сервере 1С:Предприятия не найдена лицензия. …»); кнопка «Подробно» открывает «Журнал поиска ключа». Для текста в скобках остаётся оговорка: точная формулировка по версии) | штатное поведение: лицензия не найдена, запускается помощник получения | то же, что в первой строке |
| «Ответ Центра лицензирования не соответствует введенным данным лицензии или владельца…» | при загрузке файла-ответа изменились параметры компьютера (с учётом USB-устройств) либо данные владельца | вернуть конфигурацию, проверить данные (раздел 4.1) |
| Сообщение о повторном использовании пинкода или превышении числа активаций ⚠ точный текст не проверялся | пинкод уже активирован для компьютера с другими параметрами | «Восстановление» с резервным пинкодом; Центр лицензирования |
| Сообщение о двух копиях одного файла программной лицензии ⚠ точный текст не проверялся | один файл лежит в двух каталогах поиска или на двух компьютерах | оставить один экземпляр (раздел 3.5) |
| «Недостаточно лицензий» (так ошибка названа в блоге 1С от 10.04.2025 при описании функции «Управление лицензиями»; ⚠ полный текст сообщения и вариант «Не обнаружено свободной лицензии» первоисточником не подтверждены) | все лицензии заняты | `rac session list --licenses`; зависшие сеансы; причина `no licenses left` в событии `LIC`; в 8.5.4 — «Управление лицензиями» с переключателем «Приложения, занявшие лицензии» |
| Ошибка у 11-го сеанса при работающих первых десяти | используются возможности КОРП на лицензиях ПРОФ | раздел 2.4 |

Про строки таблицы с пометкой ⚠: точные тексты сообщений о повторном использовании пинкода, о двух копиях файла лицензии и диалога «Не обнаружена лицензия для использования программы» при повторной проверке (10.10.2026) первоисточником подтвердить не удалось — в документации 8.3.27 есть только два текста «Не найдена лицензия…» и текст про ответ Центра лицензирования. Поэтому при диагностике опираться не на формулировку окна, а на «Журнал поиска ключа» (кнопка «Подробно») и на причины из события `LIC`, которые документированы и не зависят от локализации.

Причины в `txt` события `LIC` для программных лицензий [офиц.]:

| Причина | Смысл |
|---|---|
| `stop list` | файл в чёрном списке |
| `bad format` | неверный формат файла |
| `bad signature` | неверная подпись Центра лицензирования |
| `second server lite` | повторная лицензия на сервер МИНИ |
| `binding error` | ошибка привязки (изменились ключевые параметры) |
| `incorrect license type` | неподходящий тип лицензии (например, 32-разрядная серверная для 64-разрядного сервера) |
| `no licenses left` | лицензии закончились |
| `exception(…)` | иное исключение, текст в скобках |

Причины для аппаратных ключей: `not available` (ключ отсутствует, ошибка интерфейса HASP), `no licenses left` и `no slots left` (лицензии закончились), `absent` (ключ стал недоступен, например извлечён), `local and single key is already used` (локальный однопользовательский ключ уже занят) [офиц.].

### 8.3. Кому и какие лицензии выданы: `rac`

```bash
V=8.3.27.2074; RAC=/opt/1cv8/x86_64/$V/rac
CL=$($RAC cluster list | awk '/^cluster /{print $3}')

$RAC session list --cluster=$CL --licenses           # клиентские лицензии по сеансам
$RAC session info --cluster=$CL --session='uuid-сеанса' --licenses
$RAC process list --cluster=$CL --licenses           # серверные лицензии по рабочим процессам
$RAC process info --cluster=$CL --process='uuid-процесса' --licenses

# сколько лицензий занято и из каких источников
$RAC session list --cluster=$CL --licenses | grep -E '^short-presentation' | sort | uniq -c
# сколько лицензий выдано сервером, а сколько клиенты получили сами
$RAC session list --cluster=$CL --licenses | grep -E '^issued-by-server' | sort | uniq -c
```

Если у кластера заданы администраторы, добавить `--cluster-user=… --cluster-pwd=…`. `ras` должен быть запущен (порт 1545).

Поля вывода с ключом `--licenses` [практика: в документации 1С перечня нет; состав полей сверен с независимой реализацией протокола сервера администрирования — структурой `LicenseInfo` библиотеки `ras-client` (те же поля: `full_name`, `series`, `issued_by_server`, `license_type`, `net`, `max_users_all`, `max_users_cur`, `rmngr_address`, `rmngr_port`, `rmngr_pid`, `short_presentation`, `full_presentation`); в новых версиях платформы состав может расширяться]:

| Поле | Содержание |
|---|---|
| `session` / `process` | идентификатор сеанса или процесса |
| `user-name`, `host`, `app-id` | пользователь, компьютер, вид клиента (`1CV8C`, `1CV8`, `Designer`, `WebClient`…) |
| `full-name` | полное имя файла лицензии (`file:///var/1C/licenses/….lic`); для ключа HASP пусто |
| `series` | серия ключа или номер комплекта |
| `issued-by-server` | `yes` — лицензию выдал сервер, `no` — клиент получил сам |
| `license-type` | `soft` или `HASP` |
| `net` | сетевой ключ или нет |
| `max-users-all`, `max-users-cur` | числа пользователей лицензии: общий номинал и номинал текущего ключа или файла (в примере `ras-client` для ключа `ORG8A` оба равны 300). ⚠ не подтверждено: точная семантика каждого поля. Судя по этому примеру, оба поля — номиналы, а не счётчик занятых лицензий (в `kb/1c/03-…` поле `max-users-cur` истолковано как «занято сейчас» — на стенде проверить, какое толкование верно); число **занятых** лицензий надёжнее получать подсчётом сеансов (команды выше) |
| `rmngr-address`, `rmngr-port`, `rmngr-pid` | менеджер кластера, выдавший лицензию |
| `short-presentation`, `full-presentation` | строка описания лицензии (формат ниже) |

Формат строки описания лицензии [офиц., приложение 1 книги «Клиент-серверный вариант»]:

```text
Кем получено, PID, Сервер, Порт, Описание лицензии, Имя файла с лицензией
```

| Поле | Значение |
|---|---|
| Кем получено | `Клиент` или `Сервер` |
| PID | идентификатор процесса ОС, получившего лицензию (только в полном виде) |
| Сервер, Порт | имя сервера 1С и порт процесса `rphost` или `rmngr` (отсутствуют, если лицензию получил клиент) |
| Описание лицензии | ключ: `<Серия> <Локальный\|Сетевой> <Количество>`; программная: `<Номер комплекта> <Тип> <Количество>` |
| Имя файла | `file://…/*.lic`; для ключа отсутствует |

«Тип» программной лицензии: `1` — однопользовательская или серверная; значение, равное количеству, — многопользовательская.

Примеры из документации:

```text
Клиент, 4648, ORGL8 Локальный 1
Клиент, 3840, ORG8A Сетевой 300
Сервер, 1648, SERVER-1C, 1560, ORG8B Сетевой 500
Сервер, 1970, ENSR8 Локальный 1
Сервер, 4524, SERVER-1C, 1560, 8000314159 1 1, file://C:/Users/USR1CV8/AppData/Local/1C/1cv8/conf/20100521112156.lic
Сервер, 896, SERVER-1C, 1564, 8000453822 20 20, file://C:/Documents and Settings/USR1CV8/Local Settings/Application Data/1C/1cv8/conf/20110812100013.lic
```

Те же сведения видны в консоли кластера и в «Управлении серверами»: колонка «Лицензия» в списках сеансов и рабочих процессов, полная строка — в свойствах.

### 8.4. Технологический журнал: события `LIC` и `HASP`

Файл настройки `logcfg.xml` ищется в каталогах конфигурационных файлов: `/opt/1cv8/x86_64/<версия>/conf` → `/opt/1cv8/conf` → `~/.1cv8/1C/1cv8/conf` → каталог из `ConfLocation`. Сервер перечитывает его без перезапуска.

```bash
# сначала проверить, нет ли уже настроенного журнала: файл в каталоге версии имеет приоритет над /opt/1cv8/conf
sudo sh -c 'ls -l /opt/1cv8/x86_64/*/conf/logcfg.xml /opt/1cv8/conf/logcfg.xml /home/usr1cv8/.1cv8/1C/1cv8/conf/logcfg.xml 2>/dev/null'

sudo install -d -o usr1cv8 -g grp1cv8 -m 750 /var/log/1c/lic
if [ -e /opt/1cv8/conf/logcfg.xml ]; then
  echo 'logcfg.xml уже существует: не перезаписывать, добавить элемент <log> вручную'
else
  sudo tee /opt/1cv8/conf/logcfg.xml >/dev/null <<'EOF'
<?xml version="1.0" encoding="UTF-8"?>
<config xmlns="http://v8.1c.ru/v8/tech-log">
  <log location="/var/log/1c/lic" history="24">
    <event><eq property="name" value="LIC"/></event>
    <event><eq property="name" value="HASP"/></event>
    <property name="all"/>
  </log>
</config>
EOF
fi
```

- Каталог журнала должен принадлежать пользователю сервера и использоваться только под технологический журнал: платформа удаляет из него посторонние файлы.
- Если `logcfg.xml` уже существует — не затирать, а добавить отдельный элемент `<log>`.
- После диагностики настройку убрать: событий `HASP` бывает много.

Событие **`LIC`** — получение и освобождение программных и аппаратных лицензий, лицензий базовых версий, периодическая проверка соответствия оборудования [офиц.]. Свойство `res`:

| `res` | Смысл | Что в `txt` |
|---|---|---|
| `seize` | занята новая лицензия | получатель, идентификатор сеанса или сервера, запрошенный вид лицензии, сведения о просмотренных ключах и файлах, источник полученной лицензии |
| `reuse` | повторно использована уже занятая лицензия | то же |
| `release` | лицензия освобождена | идентификатор объекта лицензии, время создания, кто получил, вид (`client`, `server32`, `server64`, `server lite`) |
| `binding` | проверка оборудования на соответствие зафиксированному при активации | при расхождении — строка `Computer binding parameter changed` и по каждому файлу: имя, номер комплекта, пинкод, отличия оборудования |
| `error` | ошибка при обращении к механизму лицензирования | описание |
| `must be removed` | файл лицензии не используется и должен быть удалён | имя файла |

Запрошенный вид лицензии в `txt`: `local Designer`, `local application`, `local COM connector 32`, `local COM connector 64`, `local server 32`, `local server 64`, `remote application`. Для программных лицензий признак `soft`, вариант подписи `Short` (получена по телефону) или `Long` (по интернету или на носителе); для аппаратных — признак `hard`, серия `client`, `client 300`, `client 500`, `server 32`, `server 64`. Отличия оборудования выводятся блоками `Removed after license acquisition` и `Available in current computer configuration` (для лицензий, активированных версией 8.2.15 и новее). У события `LIC` также бывает свойство `Func` со значением `initialize` (инициализация подсистемы лицензирования).

Событие **`HASP`** — одно обращение к аппаратному ключу. Свойство `Txt` имеет вид `<Операция>(<входные параметры>)-><выходные параметры>` [офиц.].

Разбор журнала:

```bash
cd /var/log/1c/lic
# что происходило с лицензиями за последний час
grep -rh ',LIC,' --include='*.log' . | tail -n 50
# ошибки и срабатывания проверки привязки
grep -rhE ",LIC,.*res='?(error|binding|must be removed)" --include='*.log' . | tail
# причины отказа по файлам лицензий
grep -rhoE "(stop list|bad format|bad signature|binding error|incorrect license type|no licenses left|second server lite)" \
     --include='*.log' . | sort | uniq -c
# обращения к ключу, завершившиеся не нулём (формат результата зависит от операции)
grep -rh ',HASP,' --include='*.log' . | tail -n 20
```

### 8.5. Проверка привязки утилитой `ring`

```bash
RING=$(sudo find /opt/1C -name ring -type f | head -n 1)
for n in $(sudo "$RING" license list --send-statistics false | awk '{print $1}'); do
  echo "== $n"
  sudo "$RING" license validate --name "$n" --send-statistics false
  echo "код возврата: $?"
done
```

- `0` — оборудование соответствует; `1` — параметры компьютера изменены (в выводе перечень различий: что было при активации и что сейчас); `2` — ошибка цифровой подписи (файл повреждён или отредактирован в зашифрованной части) [офиц.].
- ⚠ формат строк `ring license list` (есть ли после имени дополнительный текст) зависит от версии утилиты; при необходимости поправить `awk`.
- Удобно выполнять `validate` **до и после** любых изменений ВМ, пока есть возможность откатиться.

### 8.6. Параметры конфигурационных файлов, влияющие на лицензирование

| Файл | Параметр | Значения | Действие |
|---|---|---|---|
| `conf.cfg` | `ConfLocation` | каталог | резервный каталог конфигурационных файлов; в нём же ищутся `*.lic` (п. 4 порядка поиска). Умолчание в Linux `/opt/1cv8/conf` |
| `conf.cfg` | `ExternalResourcesMode` | `D` (умолчание), `A` | набор интернет-ресурсов: серверы программного лицензирования в России (`D`) или в Европе (`A`) |
| `conf.cfg` | `LicConfigDebugTimeouts` | `true`, `false` (умолчание) | укороченные периоды проверок при работе с Центром лицензирования: сервер — 60 с вместо 1 ч, клиенты — 30 с вместо 1 ч, повтор — 15 с вместо 10 мин. Только для отладки. Параметр относится к проверке правомерности использования **конфигурации** («клиент лицензирования», раздел 8.7), а не к файлам `*.lic` платформы |
| `conf.cfg` | `JavaHome` | каталог | где сервер берёт Java (к `ring` не относится, она использует `JAVA_HOME`) |
| `location.cfg` (`~/.1cv8/1C/1cv8/`) | `location` | каталог | каталог пользовательских настроек; запасное место поиска `*.lic` |
| `1cestart.cfg` | `UseHwLicenses` | `1` (умолчание), `0` | искать ли ключ HASP при запуске клиента |
| `nethasp.ini` | секции `NH_*` | раздел 6.6 | поиск HASP License Manager |
| `nhsrv.ini` | `NHS_USERLIST`, `NHS_IP_LIMIT` | раздел 6.7 | настройки HASP License Manager |
| `rclic.cfg` | ⚠ состав не установлен | — | клиент менеджера лицензий, только 8.5.4+ |
| конфигурация автономного сервера (YAML) | `infobase.distribute-licenses` | `enable`/`allow`/`yes`/`true` — выдавать; `disable`/`deny`/`no`/`false` — не выдавать (в примерах документации — `yes`; умолчание для файла в документации не указано) | выдача клиентских лицензий автономным сервером |
| командная строка `ibsrv` | `--distribute-licenses=<флаг>` | `allow`/`yes`/`true` (умолчание `allow`), `deny`/`no`/`false` | то же, параметром запуска |
| строка `CREATEINFOBASE` клиента | `LicDstr` | `Y`, `N` (умолчание) | разрешить получение клиентских лицензий через сервер для создаваемой базы |
| командная строка клиента | `/UseHwLicenses+`, `/UseHwLicenses-` | — | включить или отключить поиск ключа для одного запуска |
| свойства базы в кластере | `license-distribution` | `allow` / `deny` | выдача клиентских лицензий сервером (раздел 5.3) |

Где лежит `conf.cfg` в Linux: каталог `conf` конкретной версии (`/opt/1cv8/x86_64/<версия>/conf/conf.cfg`) и `~/.1cv8/1C/1cv8/conf` пользователя сервера. Формат — текст UTF-8, строки `Параметр=значение`. Параметр `ConfLocation` имеет смысл только в `conf.cfg` из каталога версии [офиц.].

Сетевые адреса, к которым обращается лицензирование (для настройки межсетевого экрана и прокси):

| Адрес | Назначение |
|---|---|
| `users.v8.1c.ru` (`/LicenseCenter/ws/lm.1cws`) | веб-сервис автоматического получения лицензии |
| `portal.1c.ru`, `portal.1c.eu` (`/support/license/license-from-file`) | получение лицензии по файлу запроса |
| `developer.1c.ru`, `1c-dn.com` | лицензия для разработчиков |
| `1cv8update.com:443` | проверка правомерности использования конфигурации после обновления (механизм «клиент лицензирования») |
| `pult.1c.com:443` | статистика утилиты `ring` (отключается `--send-statistics false`) |
| TCP 3240 (хост Windows с `usbipd-win`) | USB/IP: проброс ключа в ВМ (п. 6.9) |
| UDP 475 | HASP License Manager (п. 6.5); TCP/UDP 1947 — Sentinel License Manager и Admin Control Center |

### 8.7. «Нелицензионное использование конфигурации»: проверка правомерности обновлений

Это отдельный механизм — «клиент лицензирования» (документация 8.3.27, п. 10.5) [офиц.]. К файлам `*.lic` и ключам он отношения не имеет, но администратор сталкивается с ним в том же месте — в диалоге «О программе» и в сообщениях пользователям.

- Когда срабатывает: после завершения обновления конфигурации базы данных платформа отправляет в Центр лицензирования сведения о прикладном решении и данные клиента лицензирования (учётная запись Портала 1С:ИТС, на которую зарегистрированы продукт и договор сопровождения).
- Что нужно серверу: доступ к `https://1cv8update.com`, порт 443. В актуальных версиях (8.3.27, 8.5.x) проверка выполняется во всех вариантах информационной базы, включая клиент-серверный; по V8Update раньше она выполнялась только в файловом варианте и с сервером МИНИ (⚠ точный номер версии, в которой это изменено, не установлен — запись находится в части V8Update, относящейся к версиям до 8.3.23).
- Не проверяются: базовые версии; загрузка базы из файла `*.dt`.
- Данные клиента лицензирования задаются в каждой базе: Конфигуратор → «Администрирование — Установить настройки клиента лицензирования»; в распределённой базе — в каждом узле; в разделённой базе — один раз на всю базу.
- Статусы в диалоге «О программе»:

| Статус | Что означает |
|---|---|
| «Проверка лицензионного использования не выполнялась» | платформа ещё не обращалась в Центр лицензирования |
| «Проверка лицензионного использования выполнена успешно» | правомерность подтверждена |
| «Нелицензионное использование конфигурации» | Центр лицензирования правомерность не подтвердил; всем пользователям базы периодически показывается диалог с причинами |
| «Недоступен центр лицензирования» | нет связи с `1cv8update.com:443` — проверить межсетевой экран, прокси, DNS |

- Проверка с сервера: `curl -sS -o /dev/null -w '%{http_code}\n' --max-time 10 https://1cv8update.com/` (любой HTTP-код означает, что соединение и TLS работают; тайм-аут или ошибка — закрыт доступ).
- Для отладки интервалов есть параметр `LicConfigDebugTimeouts` в `conf.cfg` (раздел 8.6) — на рабочем сервере не включать.

## 9. Практические рекомендации для сервера 1С в виртуальной машине

**До активации:**

1. Задать окончательное имя хоста и адрес: `sudo hostnamectl set-hostname srv1c`, запись в `/etc/hosts`.
2. Назначить сетевому адаптеру ВМ **статический MAC** (Hyper-V: `Set-VMNetworkAdapter -VMName srv1c -StaticMacAddress 00155D010A01`; VMware, VirtualBox, Proxmox — в свойствах адаптера). Выбрать окончательный тип адаптера.
3. Отключить динамическую память и ballooning; выдать память с запасом — уменьшать её потом нельзя. Hyper-V (ВМ должна быть выключена): `Set-VM -Name srv1c -StaticMemory -MemoryStartupBytes 16GB` — ключ `-StaticMemory` переключает ВМ на статическую память, объём задаётся параметром `-MemoryStartupBytes` [офиц. Microsoft Learn, `Set-VM`]. Проверка: `Get-VMMemory -VMName srv1c` (свойство `DynamicMemoryEnabled` должно быть `False`).
4. Определиться с числом vCPU (для сервера ПРОФ больше 12 ядер кластер не использует) и не включать режимы, меняющие модель процессора.
5. Сформировать окончательный состав дисков: система отдельно, данные PostgreSQL и кластера 1С — на отдельных дисках с запасом. Добавлять диски потом можно, удалять и заменять — нельзя.
6. Установить и запустить сервер 1С, убедиться, что кластер работает.
7. Записать «паспорт» ВМ (команды из раздела 3.2).

**Активация:**

8. Сохранить регистрационные данные владельца в файл (раздел 4.3).
9. Активировать серверную и клиентские лицензии (раздел 4.4 или 4.6), проверить `ls -l /var/1C/licenses` и подключение клиента.
10. Сразу сделать копию `*.lic` и паспорта ВМ вне сервера (раздел 3.8).

**Эксплуатация:**

11. Не менять имя хоста, MAC, объём ОЗУ в меньшую сторону, число и модель CPU, не удалять диски и адаптеры. Перед любым изменением оборудования ВМ — `ring license validate`, контрольная точка ВМ, проверка наличия резервного пинкода.
12. Не устанавливать на сервер 1С программы, создающие и удаляющие сетевые интерфейсы (Docker, VPN-клиенты) без необходимости ⚠ [практика].
13. Резервное копирование ВМ целиком и восстановление на тот же хост с теми же параметрами лицензию сохраняет.
14. Обновления Ubuntu и ядра на привязку не влияют (ОС в Linux не анализируется) [офиц.].

**Миграция на другой хост или гипервизор:**

15. Перенос с сохранением идентификаторов ВМ и MAC (экспорт и импорт «на месте», VMware «I moved it») обычно безопасен; изменение модели CPU, прошивки или виртуальной платы — нет [практика]. Планировать как повторную активацию: резервный пинкод, данные владельца, окно работ.
16. До миграции выполнить `ring license validate` и сохранить вывод; после — снова. Код `1` — восстановить прежние параметры либо активировать резервным пинкодом, предварительно убрав старый файл из каталогов поиска.

**Клонирование:**

17. Клон с активированной лицензией использовать нельзя: привязка не совпадёт, а одновременная работа двух файлов одного пинкода в сети отправит лицензию в чёрный список.
18. В шаблон ВМ не включать файлы `*.lic`, реестр кластера и базы. Перед снятием шаблона убрать лицензии из каталогов поиска — **только в ВМ-шаблоне, никогда на рабочем сервере**; безопаснее не удалять, а перенести на внешний носитель: `sudo mkdir -p /root/lic-out && sudo mv /var/1C/licenses/*.lic /root/lic-out/`, затем забрать каталог `/root/lic-out` из шаблона и удалить его там. Команду с `rm` для файлов лицензий не использовать: удалённый по ошибке файл на рабочем сервере восстанавливается только из копии или повторной активацией.
19. Тестовым стендам — отдельные лицензии либо лицензия для разработчиков.

**Если ВМ часто пересоздаётся или мигрирует:**

20. Вынести сервис лицензирования на физический компьютер или на маленькую неизменяемую ВМ (раздел 7). Для сервера 1С в ВМ на Windows-хосте таким физическим компьютером может быть сам хост: на него ставится сервер 1С той же версии, он добавляется в кластер рабочим сервером с двумя требованиями назначения, лицензии активируются для него.
21. Альтернатива — программная лицензия, привязанная к ключу HASP (п. 6.8), если ключ надёжно доступен ВМ.

## 10. Типичные ошибки и подводные камни

| Симптом | Причина | Решение |
|---|---|---|
| Клиент: «Не найдена лицензия…», хотя на сервере клиентские лицензии есть | у базы выключена выдача лицензий сервером | `rac infobase update … --license-distribution=allow` |
| Клиент: «На сервере 1С:Предприятия не найдена лицензия…» сразу после установки сервера | серверная лицензия не активирована или лежит не там | активировать для сервера (раздел 4.4); файл должен быть в `/var/1C/licenses` |
| Лицензия есть в `/var/1C/licenses`, сервер её «не видит» | нет прав у `usr1cv8`; пользователь службы не в `grp1cv8`; служба запущена под другим пользователем | раздел 3.7; `systemctl cat srv1cv8-$V@default` — проверить `User=` |
| Лицензия пропала после переноса файла или обновления платформы | одна и та же лицензия оказалась в двух каталогах (`~/.1cv8/conf` и `/var/1C/licenses`) | оставить один экземпляр; при чёрном списке — повторная активация |
| Лицензия пропала после изменения ВМ (MAC, ОЗУ, диск, имя) | нарушена привязка; в журнале `res=binding`, `binding error` | вернуть параметр либо «Восстановление» с резервным пинкодом |
| Лицензия пропала «сама» через несколько часов после изменения ВМ | параметры опрашиваются не чаще раза в сутки | то же; изменение ищите в журнале гипервизора |
| После клонирования ВМ лицензия не работает на обеих машинах | два файла одного пинкода в сети → чёрный список | клон отключить; на оригинале — повторная активация |
| Активация `ring` прошла, но лицензия не работает | активация без `--validate`: часть ключевых параметров не прочиталась, поля пустые | удалить лицензию, активировать заново от `root` с `--validate` |
| `ring` не запускается или падает при шифровании | нет Java или `gawk`; старая Java без неограниченной криптографии | `apt install gawk openjdk-11-jre-headless`; `crypto.policy=unlimited` |
| После `ring license activate` сервер не читает файл | файл создан `root` с правами только для владельца | `chown usr1cv8:grp1cv8`, `chmod 664` |
| Повторная активация тем же способом отвергается | первая активация была по телефону, повторная — по интернету (или наоборот) | использовать тот же способ |
| Загрузка файла-ответа: «Ответ Центра лицензирования не соответствует…» | между запросом и ответом изменился состав USB-устройств или данные владельца | вернуть устройства, загрузить тот же ответ |
| Лицензию активировали с клиента, а она оказалась на клиентском компьютере | не установлен флажок «Установка на сервер» или в поле «Сервер» указан не тот компьютер | файл с клиента убрать из каталогов поиска; активировать для сервера заново — потребуется резервный пинкод, потому что привязка выполняется к другому компьютеру |
| Многопользовательская лицензия активирована на рабочее место | на клиенте она бессмысленна | активировать на сервер резервным пинкодом |
| Комбинированная лицензия на 20 «превратилась» в 20 однопользовательских | первой была активирована однопользовательская | вид комплекта определяется первой активацией; обращаться в Центр лицензирования |
| Сервер использует только 12 ядер из 16 | лицензия ПРОФ | КОРП либо расширение ПРОФ для лицензий до 11.02.2019 |
| 11-й пользователь получает ошибку | включена возможность КОРП (профиль безопасности, фоновое обновление и т. п.) на ПРОФ | отключить возможность либо КОРП |
| Требования назначения функциональности «не работают» на ПРОФ | в каком-то требовании заполнено «Имя ИБ» или дополнительный параметр | оставить только требования с пустыми полями |
| После выноса сервиса лицензирования лицензии не находятся | лицензии активированы для другого сервера; требования не применены; `lic1c` недоступен | активировать с именем `lic1c`; `rac rule apply`; проверить связь и версию |
| Ключ HASP виден в `lsusb`, 1С лицензию не получает | не запущен драйвер; сервер запущен раньше драйвера; два ключа одной серии; 32-разрядный серверный ключ `ENSR8` для 64-разрядного сервера | `systemctl status aksusbd`; перезапустить сервер 1С; развести ключи; нужен `EN8SA` |
| Клиенты не находят сетевой ключ | широковещание не проходит между подсетями; закрыт UDP 475; IPv6-only | `nethasp.ini` с `NH_SERVER_ADDR` и `NH_USE_BROADCAST=Disabled`; открыть 475/udp; IPv4 |
| С ключа на 300 или 500 лицензий выдаётся только 250 | `NHS_USERLIST` по умолчанию 250 | `nhsrv.ini`: `NHS_USERLIST=600` |
| Лицензий «не хватает», хотя пользователей меньше номинала | один ключ используется и через HASP License Manager, и через сервер; один пользователь открыл несколько сеансов «на сеанс»; клиенты берут лицензии и локально, и с сервера | развести способы; `UseHwLicenses=0` на клиентах; `rac session list --licenses` |
| Ключ в ВМ периодически пропадает | USB/IP после обрыва сети или перезагрузки хоста; автоотключение USB | юнит автоподключения; перейти на программные лицензии |
| После перехода на 8.5.4 клиенты не получают лицензии с сетевого ключа | 8.5.4 не обращается к HASP License Manager напрямую | установить и запустить менеджер лицензий `rmlic`, настроить `rclic.cfg` (документация 8.5.4) |
| Community-лицензия перестала работать | сервер неделю без интернета; лицензия приостановлена на портале; активировано более 3 компьютеров | открыть доступ к ресурсам 1С; проверить кабинет на developer.1c.ru |
| Пакетный запуск Конфигуратора на сервере (`1cv8 DESIGNER …`) завершается «Не найдена лицензия…» | Конфигуратору нужна клиентская лицензия, а на сервере только серверная либо у базы `license-distribution=deny` | клиентская лицензия в `/var/1C/licenses` + `--license-distribution=allow` (п. 5.5) |
| `ibcmd … --data=…` с клиент-серверной базой сообщает об отсутствии лицензии | автономный режим `ibcmd` требует серверную лицензию на этом компьютере | запускать там, где доступна серверная лицензия (п. 5.5) |
| После обновления драйвера Sentinel порт 1947 не слушается, ключ не виден | `hasplmd` не запустился после установки версии поверх другой (известная проблема Thales SM-116811) | `sudo systemctl start hasplmd`; при необходимости повторить установку пакета |
| Admin Control Center не открывается с рабочего места (`http://srv1c:1947`) | удалённый доступ к ACC по умолчанию выключен | SSH-туннель `ssh -L 1947:localhost:1947 …` либо включить «Allow Remote Access to ACC» (п. 6.4) |
| `modprobe: FATAL: Module vhci-hcd not found` в гостевой Ubuntu | модуль USB/IP лежит в пакете дополнительных модулей ядра | `sudo apt install "linux-modules-extra-$(uname -r)"` [практика] |
| `usbip` перестал запускаться после обновления ядра | нет пакета `linux-tools` для нового ядра | `sudo apt install "linux-tools-$(uname -r)"`; держать метапакет `linux-tools-generic` (или `-virtual`) |
| В «О программе» — «Нелицензионное использование конфигурации» или «Недоступен центр лицензирования» | проверка правомерности обновления конфигурации, не лицензия платформы | раздел 8.7: доступ к `1cv8update.com:443`, настройки клиента лицензирования |
| Клиент сообщает «Не найдена лицензия…» только при запуске нескольких окон или с нескольких устройств | лицензии, выданные сервером, расходуются «на сеанс» | считать сеансы, а не пользователей; однопользовательские лицензии на рабочих местах расходуются «на компьютер» |

### Что осталось непроверенным

Состояние после независимой сверки 10.10.2026 («открыто» — по-прежнему не подтверждено; «частично» — подтверждена часть; «закрыто» — подтверждено первоисточником):

В открытых источниках этих сведений нет; нужны страницы ИТС из таблицы ниже либо проверка на стенде (команды — в конце раздела 4.9).

6. **Открыто.** Community-лицензия на сервере без графики: работает ли «Установка на сервер» и куда кладётся файл.
