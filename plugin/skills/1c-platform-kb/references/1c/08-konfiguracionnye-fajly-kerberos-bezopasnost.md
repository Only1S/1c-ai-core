## Кратко — главные факты и команды

1. Конфигурационные файлы сервера лежат в каталоге `conf`. На Linux их три: `/opt/1cv8/x86_64/<версия>/conf/` (каталог версии), `/opt/1cv8/conf/` (общий, значение `ConfLocation` по умолчанию), `~/.1cv8/1C/1cv8/conf/` (домашний каталог пользователя сервера, то есть `/home/usr1cv8/.1cv8/1C/1cv8/conf/`) [офиц.].
2. `conf.cfg` — текстовый файл UTF-8 вида `Параметр=Значение`. В 8.3.27/8.5.1 документировано 22 параметра, для сервера важны: `ConfLocation`, `SystemLanguage`, `DisableUnsafeActionProtection`, `JavaHome`, `FtsJavaOpts`, `RestructJavaOpts`, `UpdateDBCfg`, `IgnoreServerCertificatesChainRevocationSoftFail` [офиц.].
3. Реестр кластера — два файла в каталоге данных сервера: `1cv8wsrv.lst` (список кластеров и администраторы центрального сервера) и `reg_<порт>/1CV8Clst.lst` (базы, серверы, процессы, сервисы, администраторы кластера). Пароли администраторов хранятся как SHA1, пароли к СУБД — обратимо, AES128 [офиц.]. Копии реестра — секретные данные.
4. Параметры `ragent`: `-port` 1540, `-regport` 1541, `-range` 1560:1591, `-d <каталог>`, `-seclev 0|1|2`, `-pingPeriod` 1000, `-pingTimeout` 5000, `-debug [-tcp|-http]`, `-debugServerAddr`, `-debugServerPort` 1550, `-debugServerPwd`, `-debugServerUsers`, `-daemon` (только Linux) [офиц.].
5. В юните systemd им соответствуют `SRV1CV8_PORT`, `SRV1CV8_REGPORT`, `SRV1CV8_RANGE`, `SRV1CV8_DATA`, `SRV1CV8_SECLEV`, `SRV1CV8_PINGPERIOD`, `SRV1CV8_PINGTIMEOUT`, `SRV1CV8_DEBUG`, `SRV1CV8_KEYTAB`. Менять только через `sudo systemctl edit srv1cv8-<версия>@default` [офиц.].
6. Сервер 1С на Linux поддерживает аутентификацию ОС **только по Kerberos** (NTLM нет) [офиц.]. Нужны: рабочий DNS, время в пределах 5 минут, учётная запись в AD, keytab с принципалом `usr1cv8/<fqdn сервера строчными>@<REALM ПРОПИСНЫМИ>`.
7. Keytab создаётся на контроллере домена: `ktpass -princ usr1cv8/srv1c.example.local@EXAMPLE.LOCAL -mapuser usr1cv8 -pass * -crypto AES256-SHA1 -ptype KRB5_NT_PRINCIPAL -out usr1cv8.keytab`. В документации 1С пример без `-crypto` и `-ptype` (эпоха RC4); Microsoft рекомендует всегда указывать `-crypto`.
8. Keytab кладут в каталог версии `/opt/1cv8/x86_64/<версия>/usr1cv8.keytab` (значение `SRV1CV8_KEYTAB` по умолчанию) или в любой другой каталог, указав путь в `SRV1CV8_KEYTAB`. Права: `chown usr1cv8:grp1cv8`, `chmod 600` [офиц.].
9. Проверка: `klist -e -k -t <keytab>` и `kinit -k -t <keytab> usr1cv8/srv1c.example.local@EXAMPLE.LOCAL && klist` от имени `usr1cv8` [офиц.].
10. В свойствах пользователя 1С имя пользователя ОС пишется как `\\имя_домена\имя_пользователя`. Точное написание домена показывает событие `CONN` технологического журнала, свойство `Txt` со строкой `Srvr: DstUserName2` [офиц.].
11. Уровень безопасности соединений: 0 — выключено, 1 — только соединение (защищены пароли), 2 — постоянно. Алгоритмы — RSA и Triple DES [офиц.]. Фактический уровень — наибольший из заданных у базы, кластера, агента (`-seclev`) и клиента (`/SLev`).
12. Соединение сервера 1С с СУБД платформа сама не шифрует: «защита обеспечивается средствами СУБД; все поддерживаемые СУБД умеют SSL» [офиц.]. Для PostgreSQL это `ssl = on` и строки `hostssl` в `pg_hba.conf`.
13. Администраторы центрального сервера и администраторы кластера — два независимых списка. Пока оба пусты, управлять кластером может любой, кто достучался до порта 1540/1545 [офиц.]. Первое действие после установки — создать обоих.
14. Профили безопасности ограничивают серверный код: файловая система, COM, внешние компоненты, внешние модули, приложения ОС, интернет-ресурсы, привилегированный режим, криптография, расширения. Требуют лицензии КОРП [офиц.].
15. Официальные рекомендации по паролям: минимум 8 символов при двухфакторной аутентификации и 14 без неё; алгоритм хеша `PBKDF2-SHA256` (8.3.26+); не показывать список пользователей в окне входа [офиц.].
16. Порты кластера для сетевого экрана: 1540 (`ragent`), 1541 (`rmngr`), 1545 (`ras`), 1550 (`dbgs`), 1560–1591 (`rphost`). Если пользователи работают только через веб-сервер, порты кластера закрывают совсем [офиц.].
17. Сервер должен работать от непривилегированного `usr1cv8`. Запуск `ragent` от `root` нужен только для схемы с `swpuser.ini`, и без этого файла он опасен: все процессы кластера будут работать с правами суперпользователя [офиц.].
18. На 10.10.2026: линейка 8.3 закончилась на 8.3.27; 8.5.1 — финальная; 8.5.4 описана на v8.1c.ru (защита от подбора паролей администраторов кластера, доступ «только просмотр», профиль безопасности для всего кластера, отказ от HASP License Manager); план задач на 8.5.6 опубликован 07.10.2026 [офиц.].

## 1. Каталоги конфигурационных файлов и порядок поиска

### 1.1. Три каталога `conf` на Linux

| Каталог | Назначение | Источник |
|---|---|---|
| `/opt/1cv8/x86_64/<версия>/conf/` | Каталог `conf` конкретной версии. Здесь установщик оставляет образцы (`nethasp.ini` и др.). Файл `conf.cfg` отсюда действует только на эту версию | [офиц.] 8.5.1, прил. 3.17.1 |
| `/opt/1cv8/conf/` | Общий каталог для всех версий. Это значение параметра `ConfLocation` по умолчанию на Linux | [офиц.] 8.5.1, прил. 3.17.2 |
| `~/.1cv8/1C/1cv8/conf/` | Каталог пользователя, от имени которого запущено приложение. Для сервера `~` — это `/home/usr1cv8` | [офиц.] 8.5.1, прил. 3.17.1 |

Для сравнения, в Windows: `bin\conf` каталога версии, `%LOCALAPPDATA%\1C\1cv8\conf`, `%PROGRAMFILES%\1cv8\conf`.

Старые версии: до 8.3.18 каталог версии назывался `/opt/1C/v8.3/x86_64/conf/` (32-бит — `/opt/1C/v8.3/i386/conf/`).

### 1.2. Порядок поиска

Что известно точно [офиц.]:

- `conf.cfg` ищется в каталоге `conf` версии и в `~/.1cv8/1C/1cv8/conf/`.
- Остальные конфигурационные файлы (`logcfg.xml`, `nethasp.ini`, `inetcfg.xml`, `debugcfg.xml`, `testcfg.xml` и т. д.) лежат в «каталоге конфигурационных файлов». Если файла нет в стандартных местах, он ищется в каталоге из параметра `ConfLocation` файла `conf.cfg`. По умолчанию это `/opt/1cv8/conf`.
- Параметр `ConfLocation` имеет смысл только в том `conf.cfg`, который лежит в каталоге `conf` конкретной версии (документация 8.3.27, прил. 3, разд. 3.17.2). В `conf.cfg` из домашнего каталога он не нужен.
- Для параметров внешнего управления сеансами файловой базы документация приводит порядок (разд. 3.17.10): каталог `conf` версии → общий каталог (`/opt/1cv8/conf`) → каталог из `ConfLocation` файла версии → каталог информационной базы → каталог из `ConfLocation` файла, лежащего в каталоге базы. Используется первое найденное значение.
- `nethasp.ini`, если его нет в каталоге конфигурационных файлов, на Linux дополнительно ищется: в текущем каталоге → в домашнем каталоге пользователя → в `/etc` (разд. 3.25.1).
- Некоторые параметры `conf.cfg` читаются только из файла в каталоге файловой информационной базы (`DisableLocalSpeechToText`, `EnableAccessRightAuditEventsWrite`); это оговорено в описании параметра.

⚠ не подтверждено: полный формальный алгоритм поиска для каждого файла. Раздел 3.1 «Общая информация» приложения 3 и в русской документации 8.3.27 состоит из одной фразы; порядок описан только для отдельных файлов и параметров (см. выше). На живом сервере действующий файл определяют проверкой: `find` из примера ниже и наблюдение за результатом.

Практическое правило [практика]:

- настройки, которые должны пережить обновление платформы, кладите в общий каталог `/opt/1cv8/conf/` или в `/home/usr1cv8/.1cv8/1C/1cv8/conf/`;
- каталог версии `/opt/1cv8/x86_64/<версия>/conf/` удаляется вместе с версией, после обновления файлы придётся переносить;
- не держите один и тот же файл в двух местах: потом трудно понять, какой из них действует.

```bash
V=8.3.27.2074
# какие каталоги conf существуют
ls -ld /opt/1cv8/conf /opt/1cv8/x86_64/*/conf /home/usr1cv8/.1cv8/1C/1cv8/conf 2>/dev/null

# где лежат конкретные файлы
sudo find /opt/1cv8 /home/usr1cv8/.1cv8 /etc -maxdepth 6 \
  \( -name conf.cfg -o -name logcfg.xml -o -name nethasp.ini -o -name inetcfg.xml \
     -o -name debugcfg.xml -o -name swpuser.ini -o -name '*.keytab' \) 2>/dev/null

# создать общий каталог и дать серверу право читать его
sudo install -d -o root -g grp1cv8 -m 750 /opt/1cv8/conf
```

Права: процессы сервера только читают конфигурационные файлы. Достаточно владельца `root`, группы `grp1cv8` и режима `640` на файлы. Тогда прикладной код, работающий в `rphost` от `usr1cv8`, не сможет подменить настройки.

## 2. conf.cfg — полный перечень параметров

Формат: текст в UTF-8, по одной паре `Имя=Значение` в строке. Перечень ниже — все параметры, описанные в приложении 3.17 «Руководства администратора» 8.3.27 и 8.5.1 [офиц.].

| Параметр | Значения, по умолчанию | Что делает | Кому нужен |
|---|---|---|---|
| `ConfLocation` | путь; по умолчанию на Linux `/opt/1cv8/conf` | Каталог, где ищутся конфигурационные файлы (`logcfg.xml`, `nethasp.ini` и т. п.), если их нет в стандартных местах. Имеет смысл только в `conf.cfg` из каталога `conf` конкретной версии (разд. 3.17.2) | сервер, клиент |
| `SystemLanguage` | код языка (`RU`, `EN`, …) или `System` | Язык интерфейса и системных сообщений. `System` — по региональным настройкам ОС. Нет интерфейса на выбранном языке — используется английский. Параметр не задан — язык определяется по файлу `*.res`, а если его нет — по региональным настройкам ОС (разд. 3.17.22) | сервер, клиент |
| `DisableUnsafeActionProtection` | список регулярных выражений через `;` | Отключает защиту от опасных действий для баз, строка соединения которых подходит под любое выражение. Синтаксис — POSIX Basic Regular Expressions. Параметр читает тот процесс, который выполняет действие: для серверного кода — `rphost`, для открытия табличного документа и URL в поле HTML-документа — только клиент (разд. 3.17.6) | сервер, клиент |
| `JavaHome` | путь к каталогу установки Java | Где сервер ищет Java. Порядок: `JavaHome` → переменная `JAVA_HOME` → реестр (только Windows). Задаётся на компьютере, где расположен кластер серверов | сервер |
| `FtsJavaOpts` | параметры JVM без кавычек | Параметры JVM полнотекстового поиска версии 2: `-Xms2G` (начальный размер кучи), `-Xmx8G` (предел памяти), `-Dconsole` со значением `none` (по умолчанию), `all` или `start\|stop` (только строки запуска и остановки). При Java 17 и новее обязательно значение `--add-opens java.base/java.lang=ALL-UNNAMED` (документация 8.3.27, разд. 2.8.3 «Настройка Java» и прил. 3, разд. 3.17.14) | сервер |
| `RestructJavaOpts` | параметры JVM без кавычек | Параметры JVM механизма оптимизированной реструктуризации, например `-Xmx2048m`. Задаётся на компьютере, где расположен кластер серверов (разд. 3.17.20) | сервер |
| `UpdateDBCfg` | `v1` (по умолчанию), `v2` | Механизм реструктуризации, применяемый, когда он не указан явно: `v1` — стандартный, `v2` — оптимизированный (только клиент-серверные базы на MS SQL Server и PostgreSQL). Задаётся на компьютере, **где запускается конфигуратор**, а не на сервере (разд. 3.17.23) | конфигуратор |
| `IgnoreServerCertificatesChainRevocationSoftFail` | `true` (по умолчанию), `false` | Что делать, если цепочка сертификата сервера верна, но проверить отзыв не удалось: `true` — соединяться, `false` — исключение | сервер, клиент |
| `IgnoreInternetMailServerCertificateVerificationList` | имена хостов через `;`, маски `*` и `?` | Почтовые серверы, для которых `ИнтернетПочта.Подключиться()` не проверяет сертификат | сервер, клиент |
| `ForceTLS1_0`, `ForceTLS1_1`, `ForceTLS1_2` | `true` / `false` (по умолчанию) | Ограничивает сверху версию TLS клиентского приложения. Без параметра — любая до TLS 1.3. Задавать только один из трёх | клиент |
| `CryptoAPILibraryLocation` | пути через `;` | Где искать библиотеку КриптоПро CSP (только Linux и macOS) | сервер, клиент |
| `ExternalResourcesMode` | `D` (по умолчанию), `A` | Набор интернет-ресурсов: `D` — российские (центр лицензирования, система взаимодействия, PUSH), `A` — альтернативные (европейские) | сервер, клиент |
| `LicConfigDebugTimeouts` | `true` / `false` (по умолчанию) | Сокращённые периоды проверки лицензий конфигураций: сервер — раз в 60 секунд, клиенты — раз в 30 секунд (вместо часа), повторная проверка клиентами — через 15 секунд вместо 10 минут (разд. 3.17.18). Только для отладки | сервер |
| `PublishDistributiveLocationLinux32`, `…Linux64`, `…LinuxDeb32`, `…LinuxDeb64`, `…LinuxRpm32`, `…LinuxRpm64`, `…MacOS64`, `…Windows32`, `…Windows64` | путь или URL | Где лежит дистрибутив клиентского приложения для автообновления. Аналог атрибутов `pubdst*` в `default.vrd`. Изменение подхватывается через 10 секунд | сервер, веб-сервер |
| `SpeechToTextModelLocation` | путь | Единый каталог моделей распознавания речи. Без параметра в клиент-серверном варианте — подкаталог `STT` каталога реестра кластера. Модели сами не удаляются | сервер |
| `DisableLocalSpeechToText` | `0` (по умолчанию), `1` | `1` — локальное распознавание речи в файловой базе запрещено, в том числе при работе через публикацию на веб-сервере. Читается только из `conf.cfg` в каталоге информационной базы (или в каталоге его `ConfLocation`); в остальных `conf.cfg` не используется (документация 8.3.27, прил. 3, разд. 3.17.5) | файловый вариант |
| `EnableCheckScriptCircularRefs` | `true` / `false` (по умолчанию) | Поиск циклических ссылок при выполнении кода встроенного языка | разработка |
| `FileNamesEncodingInZipFile` | `UTF8` (по умолчанию), `OSEncodingWithUTF8` | Кодировка имён файлов в создаваемых ZIP-архивах | сервер, клиент |
| `DBFormatVersion` | `8.2.14` (по умолчанию), `8.3.8` | Формат новых файловых баз | файловый вариант |
| `EnableAccessRightAuditEventsWrite` | `true` / `false` (по умолчанию) | Запись событий аудита прав доступа в журнал регистрации. Только файловые базы, только лицензия КОРП. Читается из каталога базы или из каталога `ConfLocation` | файловый вариант |
| `ExternalSessionManagementConnectionString` | строка `wsdl=…;ns=…;srvc=…;port=…;tout=5;wsver=4;` | Веб-сервис внешнего управления сеансами для файловой базы | файловый вариант |
| `ExternalSessionManagementRequired` | `0` (по умолчанию), `1` | Обязательность внешнего управления сеансами для файловой базы | файловый вариант |

Замечания:

- В 8.5.4 добавлены параметры LibreOffice (`LibreOfficePort`, `LibreOfficeLocalPath` и др.) — ⚠ по описанию изменений версии, в документации 8.5.1 их нет.
- В документации не сказано, когда файл перечитывается. Считайте, что нужен перезапуск службы [практика]. Исключение, описанное официально: значения `PublishDistributiveLocation*` кешируются рабочим процессом при подключении первого клиента и после изменения файла обновляются через 10 секунд (документация 8.3.27, прил. 3, разд. 3.17.19).
- Параметры `ForceTLS1_0`/`ForceTLS1_1`/`ForceTLS1_2` действуют на **клиентское приложение**; любое значение, кроме `true`, равносильно `false`; указывать одновременно несколько параметров запрещено — поведение не определено (разд. 3.17.13).
- `UpdateDBCfg=v2` в `conf.cfg` сервера действует только тогда, когда конфигуратор (в том числе пакетный запуск `1cv8 DESIGNER … /UpdateDBCfg`) запускается на этом же компьютере. Если конфигуратор запускают с рабочего места администратора, параметр задают там.
- Официальный контейнерный стенд 1С (`1C-Company/docker_fresh`) кладёт в каталог `conf` версии файл из двух строк: `SystemLanguage=System` и `DisableUnsafeActionProtection=.*`.

Пример для рабочего сервера:

```bash
sudo install -d -o root -g grp1cv8 -m 750 /home/usr1cv8/.1cv8/1C/1cv8/conf
sudo tee /home/usr1cv8/.1cv8/1C/1cv8/conf/conf.cfg >/dev/null <<'EOF'
SystemLanguage=RU
JavaHome=/usr/lib/jvm/java-17-openjdk-amd64
FtsJavaOpts=--add-opens java.base/java.lang=ALL-UNNAMED -Xms1G -Xmx4G
UpdateDBCfg=v2
EOF
sudo chown root:grp1cv8 /home/usr1cv8/.1cv8/1C/1cv8/conf/conf.cfg
sudo chmod 640 /home/usr1cv8/.1cv8/1C/1cv8/conf/conf.cfg
sudo systemctl restart srv1cv8-8.3.27.2074@default
```

Пояснения:

- Путь `JavaHome` — пример для пакета `openjdk-17-jre-headless`. Свой путь: `readlink -f "$(command -v java)"` (вернёт `…/bin/java`; в `JavaHome` пишется каталог без `/bin/java`).
- Строки `ConfLocation` в примере нет намеренно: по документации параметр имеет смысл только в `conf.cfg` каталога версии, а его значение по умолчанию на Linux и так `/opt/1cv8/conf` (документация 8.3.27, прил. 3, разд. 3.17.2).
- При Java 17 и новее для полнотекстового поиска версии 2 в `FtsJavaOpts` обязательно значение `--add-opens java.base/java.lang=ALL-UNNAMED`; для Java младше 17 оно не нужно (документация 8.3.27, «Руководство администратора», разд. 2.8.3 «Настройка Java»; конспект `../its-docs/adm-gl02-ustanovka-p2.md`). В примере выше оно уже стоит первым, параметры памяти добавлены через пробел. ⚠ Как именно записывать несколько параметров JVM в одной строке `FtsJavaOpts`, документация показывает только по одному параметру на пример; запись через пробел без кавычек — практика, после перезапуска убедитесь по `ps -ef | grep -i java`, что процесс поиска получил все параметры.
- Каталог `~/.1cv8/1C/1cv8/conf` переживает обновление платформы, но лежит внутри домашнего каталога службы: пользователь `usr1cv8` как владелец родительского каталога может его подменить. Если важна защита настроек от прикладного кода, держите `conf.cfg` в каталоге версии, а остальные файлы — в `/opt/1cv8/conf`.
- Строку `DisableUnsafeActionProtection=.*` (отключить защиту для всех баз) допустимо держать на тестовом стенде. На рабочем сервере перечисляйте конкретные базы: `DisableUnsafeActionProtection=test_.*;stage_.*;`.
- Регулярное выражение сравнивается со строкой соединения базы. Для клиент-серверной базы она выглядит как `Srvr="srv1c";Ref="demo";`.

## 3. Остальные конфигурационные и служебные файлы

### 3.1. logcfg.xml — технологический журнал

- Лежит в каталоге конфигурационных файлов. Файл необязателен [офиц.].
- Без файла: обычный технологический журнал (`<log>`) выключен, работает только журнал «по умолчанию» (`<defaultlog>`): хранение 24 часа, уровень событий `<system>` — `Error` [офиц.].
- ⚠ Каталог журнала «по умолчанию» на Linux: в приложении 3.24.1 документации 8.5.1 указан `~/.1cv8/logs`, в других местах документации и на практике встречается `~/.1cv8/1C/1cv8/logs`. Проверьте оба: `sudo ls -ld /home/usr1cv8/.1cv8/logs /home/usr1cv8/.1cv8/1C/1cv8/logs`.
- Файл перечитывается работающими процессами примерно раз в 60 секунд, перезапуск не нужен (см. статью об архитектуре).
- Формирование дампов через элемент `<dump>` работает только в Windows. В Linux дампы настраиваются средствами ОС (`ulimit -c`, `kernel.core_pattern`) [офиц.].
- Каталог журнала должен быть доступен на запись пользователю `usr1cv8`. Тот же `logcfg.xml` читают `ras`, `rac` и модуль веб-сервера, запущенные от других пользователей: им тоже нужен доступ на запись, иначе их журнал молча не пишется [практика].

Минимальный файл для аудита (ошибки, действия администратора кластера, соединения):

```bash
sudo install -d -o usr1cv8 -g grp1cv8 -m 750 /var/log/1c/audit
sudo tee /opt/1cv8/conf/logcfg.xml >/dev/null <<'EOF'
<?xml version="1.0" encoding="UTF-8"?>
<config xmlns="http://v8.1c.ru/v8/tech-log">
  <log location="/var/log/1c/audit" history="168">
    <event><eq property="name" value="excp"/></event>
    <event><eq property="name" value="admin"/></event>
    <event><eq property="name" value="conn"/></event>
    <property name="all"/>
  </log>
</config>
EOF
sudo chown root:grp1cv8 /opt/1cv8/conf/logcfg.xml && sudo chmod 640 /opt/1cv8/conf/logcfg.xml
```

`history` — срок хранения в часах (здесь 7 суток). Событие `CONN` на нагруженном сервере пишется часто — включайте его на время диагностики. Подробно о журнале — в отдельной статье о диагностике.

### 3.2. nethasp.ini, nhsrv.ini и менеджер лицензий

`nethasp.ini` настраивает поиск сетевых ключей HASP клиентом и сервером 1С [офиц.]:

- Сначала ищется в каталоге конфигурационных файлов. Если там нет — на Linux: текущий каталог → домашний каталог пользователя → `/etc`.
- Установщик кладёт образец в `conf` версии: почти все строки закомментированы, значения по умолчанию не меняются.
- Комментарий начинается с `;`. Имена параметров нечувствительны к регистру.
- Секции: `[NH_COMMON]` (общие), `[NH_IPX]`, `[NH_NETBIOS]`, `[NH_TCPIP]`. Значение из секции протокола перекрывает значение из `[NH_COMMON]`.

| Секция | Параметр | Значения | По умолчанию |
|---|---|---|---|
| `[NH_COMMON]` | `NH_IPX`, `NH_NETBIOS`, `NH_TCPIP` | `Enabled` / `Disabled` | `Enabled` |
| `[NH_COMMON]` | `NH_SESSION` | секунды попыток соединения | 2 |
| `[NH_COMMON]` | `NH_SEND_RCV` | секунды на приём или передачу пакета | 1 |
| `[NH_TCPIP]` | `NH_SERVER_ADDR` | IP-адреса и имена менеджеров лицензий, без ограничения числа | — |
| `[NH_TCPIP]` | `NH_SERVER_NAME` | до 6 имён, каждое до 7 символов | — |
| `[NH_TCPIP]` | `NH_PORT_NUMBER` | порт | 475 |
| `[NH_TCPIP]` | `NH_TCPIP_METHOD` | `TCP` / `UDP`; значение `TCP` игнорируется, обмен всегда по UDP | `UDP` |
| `[NH_TCPIP]` | `NH_USE_BROADCAST` | `Enabled` / `Disabled` | `Enabled` |

Типовой файл, когда ключ стоит на другой машине и широковещательный поиск не проходит:

```ini
[NH_COMMON]
NH_TCPIP = Enabled
[NH_TCPIP]
NH_SERVER_ADDR = 192.168.1.20
NH_USE_BROADCAST = Disabled
```

`nhsrv.ini` — настройки самого HASP License Manager: секция `[NHS_SERVER]`, параметры `NHS_IP_LIMIT` (каким адресам раздавать лицензии, маски и CIDR), `NHS_ADAPTER`, `NHS_USERLIST` (максимум пользователей, по умолчанию 250). На Linux путь к файлу задаётся ключом `-c` [офиц.].

Изменение в линейке 8.5 [офиц., блог 10.04.2025 и «Новое в 8.5.4»]: платформа больше не использует HASP License Manager. Лицензии (программные и аппаратные) раздаёт собственное консольное приложение «1С:Предприятие — менеджер лицензий»: локально через IPC, по сети по TCP, с широковещательным поиском по UDP. В блоге изменение отнесено к версии 8.5.2, на v8.1c.ru — к 8.5.4 (версии 8.5.2 и 8.5.3 отдельно не выпускались). Если версии ниже не используются, автозапуск HASP License Manager рекомендуют отключить. Файлы и порты нового менеджера — по статье ИТС «Особенности лицензирования при переходе на версии платформы 8.5.4» (30.04.2026, конспект `../its-metod/licenzii-hasp-java-api-prochee-administrirovanie.md`): приложение `rmlic`, порты 475 и 1544 (TCP и UDP), настройки — `rmlic.cfg` у менеджера и `rclic.cfg` у приложений; расположение этих файлов не подтверждено.

Отключить поиск аппаратных ключей на клиенте: `UseHwLicenses=0` в `1cestart.cfg`.

### 3.3. swpuser.ini — отдельные пользователи ОС для rphost и rmngr

Назначение [офиц., прил. 3.29]: по умолчанию `rmngr` и `rphost` работают от того же пользователя, что и `ragent`. Файл `swpuser.ini` позволяет запускать их от других учётных записей, чтобы прикладной код в `rphost` не имел доступа к каталогу данных кластера.

Где лежит: в каталоге данных сервера, рядом с файлом списка кластеров (`1cv8wsrv.lst`). На Linux по умолчанию это `/home/usr1cv8/.1cv8/1C/1cv8/swpuser.ini`.

Формат:

```ini
user=usr1c_rphost
password=
rmngr_user=usr1c_rmngr
rmngr_pass=
registry=/var/lib/1c/registry
1541:
user=usr1c_rphost_1541
rmngr_user=usr1c_rmngr_1541
registry=/var/lib/1c/registry_1541
```

| Ключ | Смысл |
|---|---|
| `user`, `password` | Пользователь рабочих процессов `rphost` и его пароль. Нет ключа — `rphost` работает от пользователя агента |
| `rmngr_user`, `rmngr_pass` | Пользователь менеджеров кластера `rmngr` и его пароль |
| `registry` | Корневой каталог, в котором создаются каталоги реестров `reg_<порт>`. Нет ключа — каталог данных главного менеджера |
| `<порт>:` | Начало секции для кластера с этим портом менеджера. Строки до первой секции действуют на все кластеры сервера |

Особенности Linux [офиц.]:

- агент сервера `ragent` должен быть запущен от суперпользователя `root`;
- значения `password` и `rmngr_pass` игнорируются;
- пользователям из файла нужны права и полный доступ к `/var/1C`;
- каталог из `registry` должен быть полностью доступен пользователю менеджера кластера.

Порядок настройки [офиц.]: дать права целевым пользователям → создать их профили (войти под ними хотя бы раз) → создать `swpuser.ini` → изменить запуск агента, чтобы он работал от нужного пользователя → перезапустить агент.

Предупреждение документации: если сменить пользователя агента на `root`, но не создать `swpuser.ini`, все процессы кластера будут работать с правами администратора системы. В рабочей системе так делать нельзя.

Оценка [практика]: на Linux эта схема означает `User=root` в drop-in юнита. Штатный юнит на неё не рассчитан, в сообществе она почти не описана. Для одиночного сервера чаще достаточно работы всего кластера от `usr1cv8` плюс ограничений из раздела 10. ⚠ Работоспособность схемы со штатным юнитом 8.3.27/8.5 в этой сессии не проверялась.

### 3.4. debugcfg.xml, comcntrcfg.xml, testcfg.xml

`debugcfg.xml` — дополнительный диапазон портов для отладки по TCP/IP. Без файла используется 1560–1591. Серверным предметам отладки файл не нужен: они используют порты `rmngr` и `rphost` [офиц.].

```xml
<config xmlns="http://v8.1c.ru/v8/debugcfg">
  <debugports range="1540:1550"/>
</config>
```

`comcntrcfg.xml` — включает отладку внешнего соединения (COM). Только Windows, на Linux не применяется [офиц.]. Атрибуты элемента `<debugconfig>`: `debug` (`true`/`false`), `protocol` (`tcp` по умолчанию или `http`), `debuggerURL`.

`testcfg.xml` — порты обмена менеджера и клиента тестирования при автоматизированном тестировании в веб-клиенте. Без файла — 1538:1539 [офиц.].

```xml
<config xmlns="http://v8.1c.ru/v8/testcfg">
  <testports range="1538:1539"/>
</config>
```

### 3.5. inetcfg.xml — прокси-сервер

Задаёт прокси по умолчанию для обращений платформы в интернет (HTTP, HTTPS, FTP). Лежит в каталоге конфигурационных файлов, необязателен [офиц.].

Порядок на Linux [офиц.]:

1. есть `inetcfg.xml` — используются его настройки;
2. нет файла — переменные окружения `http_proxy`, `https_proxy`, `ftp_proxy`, `ftps_proxy` по протоколу;
3. они не заданы — переменная `all_proxy`;
4. некорректные значения переменных молча игнорируются.

Корневой элемент — `<InternetProxy>`, все атрибуты необязательны:

| Атрибут | Значение |
|---|---|
| `protocols` | `[Протокол=]хост:порт`, записи через пробел. Имена `HTTP`, `HTTPS`, `FTP` чувствительны к регистру (в примере документации — строчными). Запись без имени протокола действует на все остальные протоколы |
| `user`, `password` | Учётные данные прокси, пароль в открытом виде |
| `bypassOnLocal` | `true` — не использовать прокси для локальных адресов (имена без точек) |
| `bypassOnAddresses` | Список хостов через пробел, маски `*` и `?` |
| `ntlm` | `true` (по умолчанию) — разрешить NTLM-аутентификацию на прокси |

```xml
<InternetProxy
  protocols="http=10.1.0.8:8080 10.1.0.9:8080"
  user="proxyUser"
  password="proxyPassword"
  bypassOnLocal="true"
  bypassOnAddresses="127.0.0.1 *.example.local"
/>
```

Для серверных процессов переменные окружения задаются в drop-in юнита: `Environment=https_proxy=http://10.1.0.8:8080`. Файл с паролем прокси — режим `640`, владелец `root:grp1cv8`.

### 3.7. Реестр сервера и кластера: 1cv8wsrv.lst, 1CV8Clst.lst, rescntsrv.lst

| Файл | Что хранит [офиц.] | Путь по умолчанию на Linux |
|---|---|---|
| `1cv8wsrv.lst` | Список кластеров, зарегистрированных на этом сервере; по описанию главы 2 — также администраторы центрального сервера | `/home/usr1cv8/.1cv8/1C/1cv8/1cv8wsrv.lst` |
| `1CV8Clst.lst` | Реестр кластера: информационные базы, рабочие серверы, рабочие процессы, менеджеры, сервисы, администраторы кластера | `/home/usr1cv8/.1cv8/1C/1cv8/reg_1541/1CV8Clst.lst` |
| `rescntsrv.lst` | Текущие значения счётчиков потребления ресурсов, обновление раз в 20 секунд | каталог данных центрального сервера |

Что важно знать:

- Каталог данных задаётся ключом `-d` агента (переменная `SRV1CV8_DATA`). Если агент при старте не находит реестр по этому пути, он **молча создаёт новый пустой кластер** [офиц.]. Это первое, что нужно проверить, если после смены юнита или пользователя «пропали все базы».
- Если центральных серверов несколько, каждый главный менеджер ведёт свою копию реестра, копии синхронизируются [офиц.].
- Пароли в реестре [офиц., п. 2.2.9.4]: пароли администраторов центрального сервера и кластера — контрольная сумма SHA1 (необратимо); пароли, которые нужно восстанавливать, например пароль пользователя СУБД, — AES128 (обратимо). Доступ к этим файлам должен быть только у `ragent` и `rmngr`.
- Формат — текст UTF-8 во внутренней скобочной записи 1С. Документация не описывает формат и не предусматривает ручного редактирования.

Можно ли править вручную [практика, ⚠ неофициально]: только при остановленном сервере и после резервной копии. Реальные случаи — убрать запись о базе, из-за которой менеджер не стартует, или восстановить реестр после сбоя. Любая ошибка в скобках приводит к тому, что кластер не поднимется или создаст новый реестр. Штатный путь — консоль администрирования, `rac`, функция «Управление серверами».

Резервное копирование реестра:

```bash
V=8.3.27.2074
DATA=/home/usr1cv8/.1cv8/1C/1cv8
sudo install -d -m 700 /var/backups/1c-cluster

# надёжный вариант: с остановкой службы (секунды простоя)
sudo systemctl stop srv1cv8-$V@default
# шаблон reg_* должна раскрыть оболочка, работающая от root, поэтому sh -c
sudo sh -c "cd '$DATA' && tar -czf /var/backups/1c-cluster/registry_$(date +%F_%H%M).tar.gz \
     1cv8wsrv.lst reg_*/1CV8Clst.lst"
sudo systemctl start srv1cv8-$V@default

# проверить содержимое последнего архива (каталог закрыт режимом 700, поэтому тоже через sh -c)
sudo sh -c 'tar -tzf "$(ls -t /var/backups/1c-cluster/registry_*.tar.gz | head -1)"'
```

Копировать файлы на работающем сервере можно (они маленькие и переписываются целиком), но целостность такой копии документация не гарантирует [практика]. Полный сценарий резервного копирования настроек — в разделе 10.8.

### 3.8. cacert.pem и cacertnx.pem — доверенные корневые сертификаты

Какой источник использует платформа [офиц., прил. 3.13]:

| Версия платформы и режим совместимости | Источник корневых сертификатов |
|---|---|
| до 8.3.8, а также режим совместимости 8.3.7 и ниже | только `cacert.pem` |
| 8.3.8–8.3.19, режим совместимости 8.3.8 | только хранилище сертификатов ОС |
| 8.3.20 и новее, режим совместимости 8.3.8 и выше | сначала `cacertnx.pem`, затем хранилище сертификатов ОС |

Следствия для Ubuntu [практика]:

- корневой сертификат своего удостоверяющего центра добавляется в хранилище ОС:

```bash
sudo cp corp-root-ca.crt /usr/local/share/ca-certificates/corp-root-ca.crt   # формат PEM, расширение .crt
sudo update-ca-certificates
```

- при ошибках проверки сертификата на сервере 1С сначала проверьте цепочку средствами ОС: `openssl s_client -connect host:443 -servername host </dev/null | openssl x509 -noout -issuer -subject -dates`;
- Сверено 10.10.2026 по полному тексту приложения 3 документации 8.3.27 (разд. 3.13): расположение `cacert.pem` и `cacertnx.pem` на Linux в прочитанной странице не указано (ожидаемо — каталог версии): `find /opt/1cv8 -name 'cacert*.pem'`.

Связанные параметры `conf.cfg`: `IgnoreServerCertificatesChainRevocationSoftFail`, `ForceTLS1_x`, `IgnoreInternetMailServerCertificateVerificationList`.

## 4. Параметры командной строки ragent, rmngr, rphost, ras

### 4.1. Агент сервера ragent

Строка запуска из документации 8.5.1 (приложение 4.12.1) [офиц.]:

```text
./ragent /daemon /instsrvc /rmsrvc /start /stop /usr <значение> /pwd <значение>
         /port <значение> /regport <значение> /range <значение> /seclev <значение>
         /d <значение> /pingPeriod <значение> /pingTimeout <значение>
         /debug -<значение> /debugServerAddr <значение> /debugServerPort <значение>
         /debugServerPwd <значение> /debugServerUsers <значение>
```

Правила:

- Имя параметра и значение разделяются пробелом. Путь с пробелами берётся в кавычки.
- Документация пишет параметры через `/`. Штатный юнит systemd использует форму с дефисом (`-port 1540`). На Linux работают обе.
- Агент запускается как приложение (останавливается Ctrl+C), как демон (только Linux) или как служба ОС.

| Параметр | Переменная юнита | Назначение | По умолчанию | ОС |
|---|---|---|---|---|
| `-d <каталог>` | `SRV1CV8_DATA` | Каталог данных сервера: список кластеров, реестры, журналы регистрации | для агента без ключа — `~/.1cv8`; в юните — `/home/usr1cv8/.1cv8/1C/1cv8` | все |
| `-port <порт>` | `SRV1CV8_PORT` | Порт агента. К нему подключаются консоль кластера и `ras` | 1540 | все |
| `-regport <порт>` | `SRV1CV8_REGPORT` | Порт менеджера кластера, создаваемого по умолчанию при первом запуске | 1541 | все |
| `-range <диапазоны>` | `SRV1CV8_RANGE` | Диапазоны портов для рабочих процессов. Начальное значение свойства «Диапазоны IP портов» рабочего сервера. Несколько диапазонов через запятую | 1560:1591 | все |
| `-seclev <0\|1\|2>` | `SRV1CV8_SECLEV` | Уровень безопасности соединений с агентом: 0 — незащищённые, 1 — защита только на время аутентификации, 2 — постоянно защищённые | 0 | все |
| `-pingPeriod <мс>` | `SRV1CV8_PINGPERIOD` | Период проверки разрыва соединений | 1000 | все |
| `-pingTimeout <мс>` | `SRV1CV8_PINGTIMEOUT` | Таймаут проверки разрыва соединений | 5000 | все |
| `-debug [-tcp\|-http]` | `SRV1CV8_DEBUG` | Режим отладки серверного кода. `-tcp` — по умолчанию, `-http` — через сервер отладки `dbgs`. Снижает производительность | выключен | все |
| `-debugServerAddr <адрес>` | — | Адрес компьютера с сервером отладки. Нужен, если сетевых интерфейсов несколько | произвольный адрес компьютера | все |
| `-debugServerPort <порт>` | — | Порт сервера отладки | 1550 | все |
| `-debugServerPwd <пароль>` | — | Пароль подключения к серверу отладки. Игнорируется, если задан `-debugServerUsers` | не задан | все |
| `-debugServerUsers <файл>` | — | Файл со списком пользователей отладки. Без него отладка не ограничена | — | все |
| `-daemon` | — | Запуск в фоне без привязки к терминалу. Автозапуск после перезагрузки не настраивает | — | Linux |
| `-instsrvc`, `-rmsrvc`, `-start`, `-stop`, `-usr`, `-pwd` | — | Регистрация, удаление, запуск и остановка службы Windows и её учётная запись | — | Windows |
| `/resetServerAdmins`, `/resetClusterAdmins` | — | Сброс паролей администраторов центрального сервера и кластера | — | 8.5.4+ ⚠ |

Замечания:

- ⚠ `/resetServerAdmins` и `/resetClusterAdmins` взяты из описания изменений 8.5.4 (см. статью об архитектуре); в документации 8.5.1 их нет, синтаксис в этой сессии не перепроверен.
- `SRV1CV8_KEYTAB` (keytab Kerberos) — переменная юнита без парного ключа `ragent`.
- В таблице переменных документации для `SRV1CV8_RANGE` указано `1561:1590`, а для ключа `-range` — `1560:1591`. Реальные процессы стартуют с `1560:1591`. Смотрите файл юнита.
- Параметры пинга действуют на все исходящие соединения процессов кластера, запущенных этим агентом. Рекомендации документации: таймаут в 3–10 раз больше периода, период не меньше 1000 мс, одинаковые значения на всех серверах кластера. Если в свойствах кластера «Период проверки» или «Таймаут проверки» ненулевые, используются они.
- По документации, в режиме демона отладка по HTTP не поддерживается.
- Если запустить `ragent` вручную без `-d` и от другого пользователя, он создаст новый пустой кластер в домашнем каталоге этого пользователя. Не запускайте агент вручную от `root`: появятся файлы, которые потом не прочитает `usr1cv8`.

Допустимые значения `SRV1CV8_DEBUG` [офиц.]: пусто (отладка выключена), `-debug` (TCP), `-debug -tcp` (TCP), `-debug -http` (HTTP).

Примеры:

```bash
V=8.3.27.2074

# посмотреть, с какими параметрами агент работает сейчас
systemctl status srv1cv8-$V@default --no-pager | grep ragent
ps -o user=,pid=,args= -C ragent,rmngr,rphost

# запуск вручную как приложения в отдельном каталоге (стенд, отладка)
sudo -u usr1cv8 /opt/1cv8/x86_64/$V/ragent -d /home/usr1cv8/cluster_test \
     -port 2540 -regport 2541 -range 2560:2591 -debug -http

# изменить параметры штатной службы
sudo systemctl edit srv1cv8-$V@default
```

Содержимое drop-in:

```ini
[Service]
Environment=SRV1CV8_SECLEV=1
Environment=SRV1CV8_RANGE=1560:1591
Environment="SRV1CV8_DEBUG=-debug -http"
Environment=SRV1CV8_KEYTAB=/etc/1c/usr1cv8.keytab
```

```bash
sudo systemctl restart srv1cv8-$V@default
systemctl show srv1cv8-$V@default -p Environment
```

Дополнительные ключи агента (`-debugServerAddr`, `-debugServerPwd` и т. п.), для которых переменных нет, добавляют в конец значения `SRV1CV8_DEBUG` либо переопределяют `ExecStart` в drop-in [практика]. Пароль в командной строке виден в `ps`, поэтому для отладки лучше файл `-debugServerUsers`.

### 4.2. Менеджер кластера rmngr и рабочий процесс rphost

Вручную не запускаются: их порождает `ragent` (на других рабочих серверах — агент этого сервера). Параметры видны в списке процессов и полезны для диагностики [практика, наблюдение на 8.3.25]:

| Процесс | Параметры в `ps` | Что означают |
|---|---|---|
| `rmngr` | `-port 1541 -host srv1c -range 1560:1591 -d <каталог>/ -clstid <UUID>` | порт менеджера, имя хоста сервера в кластере, диапазон портов, каталог данных, идентификатор кластера |
| `rphost` | `-range 1560:1591 -reghost srv1c -regport 1541 -pid <UUID>` | диапазон портов, хост и порт менеджера, у которого процесс регистрируется, идентификатор рабочего процесса |

- Значение `-host` / `-reghost` — имя, под которым сервер зарегистрирован в кластере. Его получают клиенты. Держите его согласованным с именем в принципале Kerberos из раздела 5 (⚠ какое именно имя клиент подставляет в запрос билета, документация не уточняет).
- Уровень безопасности обмена `rphost` ↔ `rmngr` определяется свойством кластера; обмена `ragent` ↔ `rmngr` — наибольшим из уровня агента и уровня кластера [офиц.].
- Пользователь ОС этих процессов меняется только через `swpuser.ini` (раздел 3.3).

### 4.3. Сервер администрирования ras

Синтаксис [офиц., прил. 4.13.1]:

```text
ras cluster [--daemon] --port=<порт> --monitor-address=<адрес> --monitor-base=<путь> --monitor-port=<порт> <хост[:порт]>
```

| Параметр | Назначение | По умолчанию |
|---|---|---|
| `cluster` | Режим администрирования кластера, обязателен | — |
| `<хост[:порт]>` | Адрес агента сервера, который обслуживает этот `ras` | `localhost:1540` |
| `--port=<порт>`, `-p <порт>` | Порт самого сервера администрирования | 1545 |
| `--daemon` | Запуск демоном (только Linux) | — |
| `--monitor-address=<адрес>` | Адрес HTTP-шлюза показателей производительности: `localhost`, `any`, адрес IPv4 или IPv6 | `localhost` |
| `--monitor-port=<порт>` | Порт HTTP-шлюза показателей | 1555 |
| `--monitor-base=<путь>` | Базовый путь публикации показателей, начинается с `/` | `/` |

Что важно для безопасности [офиц.]:

- Один `ras` подключается к одному агенту. К кластеру может быть подключено несколько `ras`.
- Версии `ras` и кластера должны совпадать.
- `ras` и `rac` **не поддерживают аутентификацию ОС** для администраторов кластера, рабочего сервера и информационной базы — только имя и пароль.
- В документации нет параметра, ограничивающего адрес, на котором `ras` слушает порт 1545. Доступ к порту ограничивается сетевым экраном (раздел 10.2).

```bash
V=8.3.27.2074
sudo systemctl link /opt/1cv8/x86_64/$V/ras-$V.service
sudo systemctl enable --now ras-$V.service
sudo ss -tlnp | grep -E ':1545|:1555'
/opt/1cv8/x86_64/$V/rac cluster list localhost:1545
/opt/1cv8/x86_64/$V/rac help          # перечень режимов; rac help <режим> — параметры
```

## 5. Аутентификация ОС (Kerberos) для сервера 1С на Linux в домене Active Directory

### 5.1. Как это работает

- Клиент спрашивает у ОС, кто текущий пользователь: в Windows через SSPI, в Linux через GSS-API [офиц.].
- Сервер 1С на Linux понимает только Kerberos и/или имя с паролем. NTLM поддерживает только сервер на Windows [офиц., п. 2.3].
- Клиент получает у контроллера домена сервисный билет для службы `usr1cv8/<fqdn сервера>@<REALM>` и предъявляет его серверу. Сервер расшифровывает билет ключом из keytab-файла и узнаёт имя пользователя домена.
- Это имя сопоставляется с полем «Пользователь» в свойствах пользователя информационной базы.
- Первая часть имени службы — имя пользователя ОС, от которого работает сервер. В старых версиях это были `usr1cv81` и `usr1cv82`, сейчас `usr1cv8` [офиц.]. **Уточнено 10.10.2026** (полный текст документации 8.3.27, «Клиент-серверный вариант», глава 3): в примере документации и участник Kerberos, и файл ключа названы по пользователю, от имени которого работает сервер (`usr1cv8/<полное имя хоста>@<ОБЛАСТЬ>` и `usr1cv8.keytab`). Ранее было отмечено: Для нестандартного пользователя службы имя, вероятно, тоже должно совпадать с ним — не проверено.

### 5.2. Требования

| Что | Требование | Как проверить |
|---|---|---|
| DNS | Сервер 1С зарегистрирован в DNS домена (запись A; желательна PTR). Linux-сервер не регистрируется сам, запись создают вручную [офиц.] | `nslookup srv1c.example.local` на клиенте; `host 192.168.1.50` |
| Разрешение имён на сервере | Сервер использует DNS контроллера домена и находит KDC | `host -t SRV _kerberos._tcp.example.local` |
| Имя сервера | Полное имя в принципале — **строчными буквами**, иначе аутентификация не гарантируется [офиц.] | `hostname -f` |
| Время | Расхождение с контроллером домена не более 5 минут (`clockskew` MIT по умолчанию 300 секунд) | `timedatectl timesync-status`, `chronyc tracking` |
| Клиенты | Компьютер в домене, пользователь вошёл под доменной учётной записью | `klist` в Windows покажет билеты |
| Область (realm) | Пишется **ПРОПИСНЫМИ**: `EXAMPLE.LOCAL` | `/etc/krb5.conf` |
| Типы шифрования | Учётная запись службы, keytab и политика домена должны иметь общий тип (сейчас — AES) | раздел 5.9 |

Подготовка сервера Ubuntu:

```bash
# клиентские утилиты Kerberos: kinit, klist, kvno, kdestroy
sudo apt update
sudo DEBIAN_FRONTEND=noninteractive apt install -y krb5-user

# имя хоста и FQDN
hostnamectl
hostname -f                      # должно вернуть srv1c.example.local
getent hosts srv1c.example.local # реальный адрес, не 127.0.1.1

# DNS контроллера домена (netplan: nameservers.addresses и nameservers.search)
resolvectl status | grep -A3 'DNS Servers'
host -t SRV _kerberos._tcp.example.local
host dc1.example.local

# время
sudo timedatectl set-ntp true
timedatectl timesync-status
```

Если в `/etc/hosts` осталась строка `127.0.1.1 srv1c`, уберите её и пропишите `192.168.1.50 srv1c.example.local srv1c` (см. статью об установке сервера).

### 5.3. Шаги на контроллере домена

1. Создать запись A (и PTR) для `srv1c.example.local` в DNS.
2. Создать в AD учётную запись пользователя для службы. В документации — `usr1cv8`; имя может быть любым, например `svc-1c-srv1c`. Пароль длинный, флажок «Срок действия пароля не ограничен».
3. Включить для учётной записи AES: на вкладке «Учётная запись» — «Данная учётная запись поддерживает 256-разрядное шифрование Kerberos AES» (и 128-разрядное) [практика]. В PowerShell: `Set-ADUser usr1cv8 -KerberosEncryptionType AES128,AES256`.
4. Создать keytab утилитой `ktpass` (в составе RSAT / на контроллере домена), командная строка с правами администратора домена:

```text
ktpass -princ usr1cv8/srv1c.example.local@EXAMPLE.LOCAL -mapuser EXAMPLE\usr1cv8 -pass * -crypto AES256-SHA1 -ptype KRB5_NT_PRINCIPAL -out C:\temp\usr1cv8.keytab
```

Пример из документации 1С 8.5.1 (п. 3.1.6.2.1) для сравнения [офиц.]:

```text
ktpass -princ usr1cv8/srv1c.krb.local@KRB.LOCAL -mapuser usr1cv8 -pass pass1cv8 -out usr1cv8.keytab
```

Параметры `ktpass` [офиц., Microsoft]:

| Параметр | Смысл |
|---|---|
| `-princ usr1cv8/srv1c.example.local@EXAMPLE.LOCAL` | Имя принципала. **Чувствительно к регистру**, утилита его не проверяет и записывает как есть |
| `-mapuser <учётная запись>` | Доменная учётная запись, к которой привязывается принципал |
| `-pass <пароль>` | Пароль учётной записи. `*` — запросить с клавиатуры; `+rndPass` — сгенерировать случайный |
| `-crypto` | Какие ключи записать: `DES-CBC-CRC`, `DES-CBC-MD5`, `RC4-HMAC-NT`, `AES256-SHA1`, `AES128-SHA1`, `All`. Microsoft: «всегда указывайте `/crypto`», умолчания рассчитаны на старые версии MIT |
| `-ptype` | Тип принципала: `KRB5_NT_PRINCIPAL` (общий, рекомендуется), `KRB5_NT_SRV_INST`, `KRB5_NT_SRV_HST` |
| `-kvno <номер>` | Номер версии ключа. По умолчанию 1 |
| `-mapop {add\|set}` | Как записывать атрибут сопоставления. По умолчанию `add` |
| `-out <файл>` | Имя создаваемого keytab-файла |
| `{-\|+}setupn` | Менять ли UPN учётной записи вместе с SPN. По умолчанию меняются оба |

Что делает `ktpass` и что из этого следует:

- задаёт учётной записи пароль из `-pass` — номер версии ключа (kvno) в AD увеличивается;
- записывает SPN `usr1cv8/srv1c.example.local` и по умолчанию меняет UPN учётной записи на это же имя;
- к одной учётной записи нельзя привязать несколько экземпляров службы [офиц., Microsoft]. Для `HTTP/…` (веб-сервер) нужна отдельная учётная запись.

Проверка на контроллере домена (PowerShell):

```text
setspn -L usr1cv8
setspn -Q usr1cv8/srv1c.example.local
Get-ADUser usr1cv8 -Properties servicePrincipalName,userPrincipalName,msDS-KeyVersionNumber,msDS-SupportedEncryptionTypes
```

`msDS-SupportedEncryptionTypes`: 4 — RC4, 8 — AES128, 16 — AES256, 24 — оба AES, 28 — RC4 и оба AES.

5. Передать `usr1cv8.keytab` на сервер 1С защищённым способом (`scp`, WinSCP). Файл равноценен паролю учётной записи.

### 5.4. Шаги на сервере 1С

`/etc/krb5.conf` — современный минимальный вариант [практика; параметры — MIT Kerberos]:

```ini
[libdefaults]
    default_realm = EXAMPLE.LOCAL
    dns_lookup_realm = false
    dns_lookup_kdc = true
    rdns = false
    ticket_lifetime = 24h
    forwardable = true

[realms]
    EXAMPLE.LOCAL = {
        kdc = dc1.example.local
        admin_server = dc1.example.local
        default_domain = example.local
    }

[domain_realm]
    .example.local = EXAMPLE.LOCAL
    example.local = EXAMPLE.LOCAL
```

Пояснения:

- В примере документации 1С в `[libdefaults]` стоят `default_tkt_enctypes = rc4-hmac` и `default_tgs_enctypes = rc4-hmac`, а `dns_lookup_kdc = false` с явным `kdc = main.krb.local:88` [офиц.]. Строки с `rc4-hmac` сегодня вредны: они запрещают AES. MIT рекомендует эти параметры не задавать — с версии 1.18 они берутся из `permitted_enctypes`.
- `permitted_enctypes` по умолчанию в MIT 1.22: `aes256-cts-hmac-sha1-96 aes128-cts-hmac-sha1-96 aes256-cts-hmac-sha384-192 aes128-cts-hmac-sha256-128 des3-cbc-sha1 arcfour-hmac-md5 camellia256-cts-cmac camellia128-cts-cmac` [офиц., MIT].
- `rdns = false` отключает обратный DNS-запрос при построении имени службы. В AD это избавляет от ошибок из-за неверных PTR-записей [практика].
- Имена в `[domain_realm]` — строчными, область — прописными.

Проверка Kerberos обычным пользователем домена [офиц.]:

```bash
kinit ivanov@EXAMPLE.LOCAL     # спросит пароль; молчание означает успех
klist                          # должен показать krbtgt/EXAMPLE.LOCAL@EXAMPLE.LOCAL
kdestroy
```

Размещение keytab [офиц.]:

```bash
V=8.3.27.2074
sudo cp ~/usr1cv8.keytab /opt/1cv8/x86_64/$V/usr1cv8.keytab
sudo chown usr1cv8:grp1cv8 /opt/1cv8/x86_64/$V/usr1cv8.keytab
sudo chmod 600 /opt/1cv8/x86_64/$V/usr1cv8.keytab
rm ~/usr1cv8.keytab
```

Проверка keytab [офиц.]:

```bash
V=8.3.27.2074
KT=/opt/1cv8/x86_64/$V/usr1cv8.keytab

# содержимое: номер версии ключа (KVNO), принципал, тип шифрования
sudo -u usr1cv8 klist -e -k -t "$KT"

# получить билет по keytab без пароля — именно от имени usr1cv8
sudo -u usr1cv8 kinit -k -t "$KT" usr1cv8/srv1c.example.local@EXAMPLE.LOCAL
sudo -u usr1cv8 klist
sudo -u usr1cv8 kdestroy
```

Ожидаемо: `kinit` ничего не выводит, `klist` показывает `Default principal: usr1cv8/srv1c.example.local@EXAMPLE.LOCAL` и билет `krbtgt/EXAMPLE.LOCAL@EXAMPLE.LOCAL`. В строке keytab должен быть тип `aes256-cts-hmac-sha1-96` (для RC4 — `arcfour-hmac`, в старом выводе `ArcFour with HMAC/md5`).

Сверка номера версии ключа с доменом [практика]:

```bash
kinit ivanov@EXAMPLE.LOCAL
kvno usr1cv8/srv1c.example.local@EXAMPLE.LOCAL         # печатает kvno билета из AD
sudo klist -k /opt/1cv8/x86_64/$V/usr1cv8.keytab       # KVNO в keytab должен совпасть
kdestroy
```

Перезапуск: по документации он нужен, только если менялось расположение keytab. На практике после замены файла службу перезапускают:

```bash
sudo systemctl restart srv1cv8-$V@default
```

### 5.5. Свой путь к keytab: SRV1CV8_KEYTAB

Каталог версии удаляется при обновлении платформы. Чтобы не терять keytab, держите его вне `/opt` [практика]:

```bash
V=8.3.27.2074
sudo install -d -o root -g grp1cv8 -m 750 /etc/1c
sudo install -o usr1cv8 -g grp1cv8 -m 600 ~/usr1cv8.keytab /etc/1c/usr1cv8.keytab
sudo systemctl edit srv1cv8-$V@default
```

```ini
[Service]
Environment=SRV1CV8_KEYTAB=/etc/1c/usr1cv8.keytab
```

```bash
sudo systemctl restart srv1cv8-$V@default
systemctl show srv1cv8-$V@default -p Environment | tr ' ' '\n' | grep -i -E 'KEYTAB|KRB5'
```

- `SRV1CV8_KEYTAB` — официальная переменная юнита, значение по умолчанию `/opt/1cv8/x86_64/<версия>/usr1cv8.keytab` [офиц.].
- Библиотеки MIT Kerberos сами читают путь к keytab из переменной окружения `KRB5_KTNAME`. Самодельные юниты сообщества задают именно её: `Environment=KRB5_KTNAME=/opt/1cv8/x86_64/%i/usr1cv8.keytab`. ⚠ Как штатный юнит передаёт значение `SRV1CV8_KEYTAB` процессу, прочитать не удалось: `systemctl cat srv1cv8-$V@default | grep -i -E 'keytab|krb5'`. Если аутентификация со своим путём не работает, добавьте в drop-in ещё и `Environment=KRB5_KTNAME=/etc/1c/usr1cv8.keytab`.
- Drop-in привязан к имени юнита с номером версии. После обновления платформы его переносят на новое имя.

### 5.6. Настройка пользователя 1С

В конфигураторе («Администрирование → Пользователи») или в режиме предприятия у пользователя включается «Аутентификация операционной системы» и заполняется поле «Пользователь».

Формат [офиц., п. 6.2.10.3]: `\\имя_домена\имя_пользователя`, пример документации — `\\d1.d2\user1`. Имя пользователя — только латинские буквы. Точный вид домена и имени зависит от настроек контроллера домена.

Как узнать точное написание [офиц.]: включить в технологическом журнале событие `CONN`, выполнить попытку входа и найти событие, у которого свойство `Txt` начинается с `Srvr: DstUserName2`. Если там `d1.d2\user1`, в свойствах пользователя пишут `\\d1.d2\user1`.

```bash
# после попытки входа пользователя
sudo grep -r -h 'DstUserName2' /var/log/1c/audit | tail -5
```

Практика [⚠ не подтверждено официально]: при сервере на Linux доменная часть — это область Kerberos, и в инструкциях сообщества её пишут полным именем прописными: `\\EXAMPLE.LOCAL\ivanov`, а не коротким NetBIOS-именем `\\EXAMPLE\ivanov`. Не гадайте — смотрите `DstUserName2`.

Параметры запуска клиента [офиц.]: `/WA+` — принудительно аутентификация ОС (включено по умолчанию), `/WA-` — запретить её и показать окно ввода имени и пароля.

Ограничения [офиц.]:

- клиенты на macOS аутентификацию ОС не поддерживают;
- при подключении через веб-сервер Apache в Windows аутентификация ОС не поддерживается;
- для веб-клиента и тонкого клиента через веб-сервер в Windows адрес базы нужно добавить в надёжные узлы браузера;
- администраторов кластера через `ras`/`rac` аутентифицировать средствами ОС нельзя. Ограничение касается только `ras`/`rac`: в консоли кластера (оснастка MMC на Windows) у администратора центрального сервера и администратора кластера есть флажок «Аутентификация операционной системы» с пользователем вида `\\домен\пользователь` [ИТС-КС разд. 5.2.4.1, 5.2.8.1; уточнено 19.10.2026, разбор — `../1c-windows/04-domen-kerberos-klienty-terminalnyj-server.md`].

Клиент на Linux [практика]: пользователь должен иметь билет Kerberos — войти в систему через SSSD/Winbind под доменной записью либо выполнить `kinit ivanov@EXAMPLE.LOCAL`.

### 5.7. Сквозной вход (SSO) для веб-клиента

Что говорит документация [офиц.]:

- веб-сервер может выполнять аутентификацию сам (анонимная, базовая, аутентификация ОС) и передавать результат в 1С;
- для IIS аутентификация ОС включается флажком в диалоге публикации или ключом `-osauth` утилиты `webinst`;
- через Apache в Windows аутентификация ОС не поддерживается;
- для Apache на Linux отдельная процедура описана в главе о настройке веб-серверов.

**Уточнено 11.10.2026**: официальная процедура прочитана — документация 8.3.27, «Руководство администратора», разд. 2.8.1.2 «Аутентификация операционной системы при использовании веб-сервера Apache». В ней: модуль `mod_auth_kerb` (в Debian — пакет `libapache2-mod-auth-kerb`); ключ Kerberos на имя `HTTP/Server.domain@DOMAIN`, у связанной учётной записи — флажок «Учётная запись доверена для делегирования»; в секции `<Directory>` публикации — `AuthName "1C:Enterprise web client"`, `AuthType Kerberos`, `Krb5Keytab <файл>`, `KrbVerifyKDC off`, `KrbDelegateBasic off`, `KrbServiceName HTTP/Server.domain@DOMAIN`, `KrbSaveCredentials on`, `KrbMethodK5Passwd off`, `KrbMethodNegotiate on`, `Require valid-user`; файл ключа должен читаться пользователем, от имени которого работает Apache. Про `mod_auth_gssapi` в документации ничего нет, поэтому сказанное ниже о нём — практика сообщества. Ранее было: Текст этой процедуры в этой сессии прочитать не удалось (на kb.1ci.com раздел 8.10.1 её не содержит, русская документация закрыта). Ниже — практика сообщества, перед применением проверьте на стенде.

Схема [практика]:

1. Отдельная учётная запись AD для веб-сервера (например, `svc-1c-http`) и keytab с принципалом `HTTP/<fqdn веб-сервера>@<REALM>`:

```text
ktpass -princ HTTP/srv1c.example.local@EXAMPLE.LOCAL -mapuser EXAMPLE\svc-1c-http -pass * -crypto AES256-SHA1 -ptype KRB5_NT_PRINCIPAL -out C:\temp\http.keytab
```

2. Модуль Apache `mod_auth_gssapi` (пакет Ubuntu `libapache2-mod-auth-gssapi`). Старый `mod_auth_kerb` с директивами `Krb5Keytab`, `KrbServiceName`, `KrbMethodNegotiate`, `KrbSaveCredentials` из старых инструкций в современных выпусках Ubuntu, как правило, недоступен (по packages.ubuntu.com на 10.10.2026: пакет `libapache2-mod-auth-kerb` есть в 22.04 (5.4-2.5), в 24.04 и 26.04 его нет; `libapache2-mod-auth-gssapi` есть во всех трёх выпусках (1.6.3 в 22.04, 1.6.4 в 24.04 и 26.04); ранее: наличие пакета `libapache2-mod-auth-kerb` в 22.04/24.04 не проверено).

```bash
sudo apt install -y libapache2-mod-auth-gssapi
sudo a2enmod auth_gssapi
sudo install -o root -g www-data -m 640 ~/http.keytab /etc/apache2/http.keytab
sudo -u www-data klist -k /etc/apache2/http.keytab
```

3. Блок в конфигурации публикации (директивы — из документации `mod_auth_gssapi`):

```apache
<Location "/buh">
    AuthType GSSAPI
    AuthName "1C:Enterprise SSO"
    GssapiCredStore keytab:/etc/apache2/http.keytab
    GssapiSSLonly On
    GssapiNegotiateOnce On
    Require valid-user
</Location>
```

4. Если модулю 1С нужны делегированные учётные данные пользователя (сервер 1С на другом компьютере), добавляют `GssapiDelegCcacheDir /run/apache2/krbcache` и разрешают делегирование для учётной записи `svc-1c-http` в AD (вкладка «Делегирование»). Модуль выставляет запросу переменную `KRB5CCNAME` с путём к кешу билетов. **Уточнено 11.10.2026**: в официальной процедуре для `mod_auth_kerb` (документация 8.3.27, разд. 2.8.1.2) делегирование предусмотрено — учётной записи с именем `HTTP/…` ставят флажок «Учётная запись доверена для делегирования», а в настройке каталога задают `KrbSaveCredentials on`. Для `mod_auth_gssapi` официального описания нет. Ранее было: Требуется ли делегирование для модуля `wsap24.so` и как именно он получает имя пользователя — не подтверждено.

5. Браузеры: в Windows — добавить адрес в зону «Местная интрасеть» или в надёжные узлы [практика]; Chrome и Edge — политика `AuthServerAllowlist`; Firefox — `network.negotiate-auth.trusted-uris`. Имена политик подтверждены 20.10.2026 по определениям политик Chromium, справке политик Microsoft Edge и mozilla/policy-templates.

`GssapiSSLonly On` отказывает в аутентификации без TLS. Сквозной вход всегда публикуйте по HTTPS.

### 5.8. Что переносить при обновлении платформы

- keytab, если он лежал в каталоге версии: скопировать в каталог новой версии и восстановить права;
- drop-in юнита с `SRV1CV8_KEYTAB`;
- заново создавать keytab **не нужно**: принципал не зависит от версии платформы.

Keytab пересоздают, когда: сменили пароль учётной записи службы, переименовали сервер, сменили домен, меняют тип шифрования. После пересоздания kvno увеличивается, старый файл перестаёт работать. Клиентам, у которых остался старый сервисный билет, нужно перезайти в систему или выполнить `klist purge`.

### 5.9. Типы шифрования: RC4 и AES

- Документация 1С до сих пор приводит пример с RC4-HMAC и запасной вариант с DES (`-crypto DES-CBC-CRC`) [офиц.]. Это наследие 2000-х годов.
- Microsoft объявила об отказе от RC4 в Kerberos (блог Windows Server, 03.12.2025, дополнение 04.02.2026): к середине 2026 года на контроллерах домена меняются типы шифрования, принимаемые по умолчанию для учётных записей без явной настройки, — остаётся AES-SHA1. Аутентификация, зависящая от RC4, перестаёт работать [офиц., Microsoft].
- Найти использование RC4: события 4768 и 4769 журнала безопасности контроллера домена, поля `msds-SupportedEncryptionTypes`, `Available Keys`, `Session Encryption Type`; сценарии `List-AccountKeys.ps1` и `Get-KerbEncryptionUsage.ps1` из репозитория `microsoft/Kerberos-Crypto` [офиц., Microsoft].
- Вывод: для новых установок — keytab с AES256, учётная запись службы с включённым AES, никаких `rc4-hmac` в `krb5.conf`. ⚠ Работа сервера 1С с AES-keytab в документации 1С не описана; в практике сообщества это обычная конфигурация, а сама проверка билета выполняется системной библиотекой GSS-API (`libgssapi-krb5-2`), которая AES поддерживает.
- Ключи AES зависят от «соли» — имени учётной записи. После `ktpass` UPN учётной записи меняется, и keytab соответствует состоянию на момент создания. Переименовали учётную запись или изменили UPN — пересоздайте keytab.

## 6. Аутентификация пользователей информационной базы

### 6.1. Виды аутентификации в актуальных версиях

Перечень из «Руководства администратора» 8.5.1 (п. 6.2.10) и с v8.1c.ru [офиц.]. Если у пользователя не включён ни один вид аутентификации, доступ к базе для него закрыт.

| Вид | Суть | Где работает, ограничения |
|---|---|---|
| Аутентификация 1С:Предприятия | Имя и пароль проверяет платформа. В базе хранится хеш пароля | Все клиенты |
| Аутентификация ОС | Платформа доверяет ОС: Kerberos, а на сервере Windows ещё и NTLM | Раздел 5. Нет на macOS, нет через Apache в Windows |
| OpenID (версия 2.0) | Вход через OpenID-провайдера. Провайдером может быть информационная база 1С | Нужна публикация на веб-сервере и HTTPS |
| OpenID Connect | Вход через внешнего провайдера поверх OAuth 2.0 (Keycloak, ЕСИА и др.). Сама 1С провайдером OpenID Connect быть не может | Тонкий, мобильный и веб-клиент |
| Токен доступа (JWT, RFC 7519) | Вход по подписанному токену, переданному клиенту параметром запуска `AccessToken` | Только базы, опубликованные на веб-сервере |
| По QR-коду | Есть в перечне документации 8.5.1 | подробности — в конспектах `../its-docs/adm-gl06-administrirovanie-ib-p1.md` и `../its-docs/adm-gl06-administrirovanie-ib-p2.md`; при написании статьи подробности не прочитаны |
| По электронной почте | На адрес из списка пользователей отправляется случайный код для входа (появилось в 8.3.27) | Вход без запоминания пароля, первый вход |
| Двухфакторная | Первый фактор проверяет платформа, второй — внешний «провайдер второго фактора» (HTTP-сервис) | Только вместе с аутентификацией 1С:Предприятия; любой вариант базы и любой клиент |
| Биометрия | Вход в мобильном клиенте | Мобильный клиент |

Новое в линейке 8.5 [офиц., v8.1c.ru и блог]:

- 8.5.4: у пользователя появился флажок «Аутентификация разрешена» (снять — заблокировать вход, сохранив настройки) и даты начала и окончания периода аутентификации; для второго фактора задаются длина и время действия кода, таймаут повторного запроса и текст сообщения; завершение сеанса со сбросом аутентификации; хеш-функции ГОСТ Р 34.11-2012 во встроенном языке.
- 8.5.5 (по плану и анонсам): вход по PIN-коду, администрирование активных сеансов пользователем и администратором базы («выйти на всех устройствах»), развитие OAuth.
- 8.5.6 (план от 07.10.2026): выполнены «доработка OAuth-аутентификации на клиенте» и «интеграция с SIEM-системами»; запланирован «второй фактор на основе электронной подписи».

### 6.2. Политика паролей

Задаётся для всей базы (конфигуратор: «Администрирование → Параметры информационной базы», группа «Требования к паролям») или для отдельных пользователей; программно — объект `UserPasswordPolicy` [офиц., п. 6.2.5].

| Параметр (свойство `UserPasswordPolicy`) | Смысл |
|---|---|
| Проверка сложности пароля (`PasswordStrengthCheck`) | Пароль не короче 7 символов (или `PasswordMinLength`, если оно больше); символы минимум трёх групп из четырёх (прописные, строчные, цифры, специальные); не совпадает с именем пользователя; не является алфавитной последовательностью |
| Проверка компрометации (`PasswordCompromiseCheck`) | Проверка по спискам скомпрометированных паролей, в дополнение к сложности |
| Минимальная длина (`PasswordMinLength`) | Минимальная длина; при включённой проверке сложности — не меньше 7 |
| Действие при несоответствии пароля требованиям при входе (`ActionOnPasswordRequirementsViolationOnAuthentication`) | `None` — ничего; `SuggestPasswordChange` — предложить смену, работу можно продолжить; `RequirePasswordChange` — без смены пароля работать нельзя |
| Максимальный срок действия (`PasswordMaxEffectivePeriod`) | В секундах от установки пароля; 0 — не действует |
| Минимальный срок действия (`PasswordMinEffectivePeriod`) | В секундах; раньше этого срока пароль сменить нельзя; 0 — не действует |
| Срок предупреждения об истечении (`PasswordExpirationNotificationPeriod`) | В секундах; 0 — не действует |
| Запрет повторного использования (`PasswordReuseLimit`) | Сколько последних паролей нельзя повторять; 0 — не действует |

Особенности:

- Проверка сложности действует при смене пароля и создании пользователя, существующие пароли не затрагивает.
- После включения проверки сложности сравнение пароля при входе становится чувствительным к регистру: пользователь с паролем `PaSs` больше не войдёт с `pass`.
- Программно пароль можно установить любой длины, даже если политика задана.

Алгоритм хеширования паролей [офиц., п. 6.6.2]:

| Алгоритм | Соль | Относительное время | Когда использовать |
|---|---|---|---|
| SHA-1 | нет | 1 | Нужен вход из любой версии платформы |
| SHA-256, SHA-512 | есть | 2 и 3 | Доступ только из 8.3.26 и новее |
| PBKDF2-SHA256 | есть | около 1915 | Рекомендуется: наибольшая стойкость к перебору |

Смена алгоритма: в параметрах базы или методами `GetUserPasswordHashAlgorithmType()` / `SetUserPasswordHashAlgorithmType()`; у пользователя — свойство `InfoBaseUser.PasswordHashAlgorithmType`. Порядок перехода: сменить алгоритм → завершить все сеансы → при следующем входе хеш пересчитается → через месяц найти оставшихся на старом алгоритме и заставить сменить пароль. Побочный эффект: все сохранённые входы («Запомнить») становятся недействительными.

Проверка компрометации — три источника, включаются независимо [офиц., п. 6.2.6.5]:

1. стандартный список платформы (обновляется со сменой версии платформы);
2. свой список нежелательных паролей (до 100 000 записей, загрузка из файла);
3. внешний сервис: платформа отправляет `GET <адрес>/<первые 5 символов SHA-1 пароля>` и сама ищет остаток хеша в ответе. Пример — `https://api.pwnedpasswords.com/range/`. Сервис можно написать самим.

Блокировка при подборе пароля (вкладка «Аутентификация» параметров базы) [офиц.]:

- «Максимальное количество неуспешных попыток аутентификации»;
- «Длительность блокировки аутентификации» (секунды);
- «Коды дополнения имени пользователя при блокировке аутентификации».

**Уточнено 11.10.2026** (полный текст главы 6 документации 8.3.27): значения по умолчанию там не названы; сказано только, что блокировка срабатывает на N-й подряд неудачной попытке, значение 0 отключает механизм, а коды дополнения перечисляют через «;». Ранее было: Значения по умолчанию на прочитанной странице не приведены.

Сохранённая аутентификация («Запомнить») [офиц., п. 6.2.6.2]: пароль не хранится, хранится токен с ограниченным сроком, привязанный к паролю. Чтобы сбросить сохранённые входы пользователя, смените ему пароль. Документация не рекомендует включать одновременно сохранение аутентификации и завершение неактивных сеансов. Срок жизни можно задать и в `default.vrd`, значение оттуда имеет приоритет.

Официальные рекомендации (приложение 3.11 клиент-серверного руководства) [офиц.]:

- предпочитать аутентификацию ОС и использовать двухфакторную;
- при парольной: длинные уникальные пароли, проверка сложности и компрометации, минимум **8** символов с двухфакторной аутентификацией и **14** без неё;
- периодически проверять существующие пароли на соответствие политике и принудительно менять несоответствующие;
- отключить показ списка пользователей в окне входа;
- давать пользователям только нужные права; обычным пользователям не разрешать запуск внешних обработок.

### 6.3. OpenID и OpenID Connect

OpenID 2.0 [офиц., its.1c.ru, статья 2018 года]:

- проверяющая сторона (база-клиент), в `default.vrd`:

```xml
<openid>
    <rely url="https://myserver.org/users-ib/e1cib/oid2op"/>
</openid>
```

- провайдер (база со списком пользователей), в `default.vrd`:

```xml
<openid>
    <provider>
        <lifetime>604800</lifetime>
        <returnto>mysite\.com</returnto>
        <returnto>.*\.1c\.ru</returnto>
    </provider>
</openid>
```

- `lifetime` — время жизни признака аутентификации в секундах; `returnto` — регулярные выражения разрешённых адресов возврата (с 8.3.8, по умолчанию ограничений нет);
- адрес провайдера обязан быть HTTPS; цепочка его сертификата должна быть доверенной для сервера проверяющей стороны;
- диагностика: открыть `https://<провайдер>/<база>/e1cib/oid2op` — должен вернуться XRDS-документ; в технологическом журнале включить `<system level="trace" class="OID2Log"/>` и событие `SYSTEM`; типовые ошибки — `OP discovery error` и `Rely Party: id_res invalid local id` (например, в адресе явно указан порт `:443`);
- двухфакторную аутентификацию при OpenID запрашивает провайдер; если провайдер — база 1С, второй фактор настраивается в ней [офиц.].

OpenID Connect [офиц., п. 6.2.10.5]:

- провайдеры описываются в элементе `openidconnect.providers` файла `default.vrd`, у каждого есть имя;
- сопоставление пользователя: со стороны провайдера ключ — адрес электронной почты (или другое поле токена); со стороны 1С — свойство `Name` пользователя базы (или `OSUser`, `Email`, либо значение из коллекции `UserMatchingKeys`, которая заполняется только из встроенного языка);
- поддерживается ЕСИА; для баз с разделением данных может потребоваться параметр `redirect_uri`;
- мобильный клиент выполняет вход во внешнем браузере устройства.

Набросок `default.vrd` для Keycloak [практика, имена ключей `name`, `title`, `discovery`, `authenticationClaimName`, `authenticationUserPropertyName`, `clientconfig` (внутри — `authority`, `client_id`, `redirect_uri`, `response_type`, `scope`) сверены 10.10.2026 с полным текстом приложения 3 документации 8.3.27; ранее: имена ключей не сверены с документацией в этой сессии]:

```xml
<openidconnect>
    <providers>
        <![CDATA[
        [
          {
            "name": "keycloak",
            "title": "Вход через Keycloak",
            "discovery": "https://sso.example.local/realms/corp/.well-known/openid-configuration",
            "authenticationClaimName": "email",
            "authenticationUserPropertyName": "email",
            "clientconfig": {
              "authority": "https://sso.example.local/realms/corp",
              "client_id": "1c-buh",
              "redirect_uri": "https://srv1c.example.local/buh/authform.html",
              "response_type": "id_token token",
              "scope": "openid email"
            }
          }
        ]
        ]]>
    </providers>
    <allowStandardAuthentication>true</allowStandardAuthentication>
</openidconnect>
```

### 6.4. Двухфакторная аутентификация

Схемы [офиц., п. 6.2.10.9]:

1. Код генерирует платформа, провайдер только доставляет сообщение (SMS, почта). Пользователь вводит код в окне клиента, сервер сравнивает.
2. Проверку выполняет сам провайдер (приложение на телефоне и т. п.). Сервер 1С отправляет ему запрос, затем спрашивает результат.

Настройка — из встроенного языка:

- шаблон запроса `SecondAuthenticationFactorSettingTemplate`: свойства `Name`, `AuthenticationHTTPRequest`, `AuthenticationHTTPRequestMethod`, для второй схемы ещё `AuthenticationResultVerificationHTTPRequest` и `AuthenticationResultVerificationHTTPRequestMethod`;
- параметры в запросе начинаются с `&` (`&phone_number`); предопределённый `&secret` — код, сгенерированный платформой;
- привязка к пользователю: свойства `InfobaseUser.SecondAuthenticationFactorSettings` (массив `SecondAuthenticationFactorSetting` с `SettingTemplateName` и `Parameters`) и `SecondAuthenticationFactorSettingsProcessing` (например, `UseNextIfFailed`).

Риск [офиц.]: если провайдер недоступен (нет связи сервера с ним или его с пользователем), пользователь в базу не войдёт. Нужен запасной провайдер или отдельный администратор для аварийного входа.

### 6.5. Токены доступа (JWT)

Порядок настройки [офиц., п. 6.2.10.6]:

1. опубликовать базу на веб-сервере;
2. включить пользователю свойство «Аутентификация токеном доступа»;
3. в `default.vrd` создать элемент `accessTokenAuthentication` с вложенным `issuer` (атрибут `name`; при поиске пользователя не по имени — атрибут `authenticationUserPropertyName`) и подчинённым элементом `accessTokenRecepientName` — уникальное имя приложения-получателя;
4. объектом встроенного языка `AccessToken` сформировать токен: свойство `Issuer` даёт поле `iss`, список получателей — `aud`, `UserMatchingKey` — `sub`;
5. передать строку токена пользователю; клиент запускается с параметром `AccessToken`.

**Уточнено 11.10.2026** (приложение 3 документации 8.3.27, разд. 3.21.14): ключ проверки подписи задаётся атрибутом `keyInformation` элемента `<issuer>` — для алгоритмов HS256, HS384 и HS512 это симметричный ключ, для остальных (в документации назван RS256) — открытый ключ или сертификат в формате PEM; срок действия определяют поля самого токена `exp`, `nbf`, `iat`; для Web-сервисов и HTTP-сервисов элемент `<accessTokenAuthentication>` создают подчинённым `<ws>`/`<point>` и `<httpServices>`/`<service>`; для доступа из-за периметра документация советует асимметричные алгоритмы. Про стандартный интерфейс OData отдельно не сказано. Ранее было: Алгоритмы подписи, хранение ключей, срок жизни токена и применимость к HTTP-сервисам и OData на прочитанной странице не описаны.

## 7. Защита соединений

Общая схема [офиц., п. 2.2.9.1]: данные 1С доступны только через кластер серверов. Кластер защищает обмен «клиент — кластер», «консоль — кластер», «веб-сервер — кластер», обмен внутри кластера и хранение служебных данных. Обмен с СУБД защищает СУБД. Обмен «клиент — веб-сервер» защищает веб-сервер.

### 7.1. Уровень безопасности соединений

| Уровень | В интерфейсе | Что шифруется | Цена |
|---|---|---|---|
| 0 | Выключено / «Никогда» | Только первый обмен (RSA), дальше открыто. Пароли шифруются всегда | минимальная |
| 1 | Только соединение / «Установка соединения» | Первый обмен — RSA, затем Triple DES до конца аутентификации, дальше открыто. Перехватчик не получит пароли | пренебрежимо мала |
| 2 | Постоянно | Весь обмен: первый пакет — RSA, остальное — Triple DES | заметное снижение производительности |

Механика [офиц., п. 2.2.9.2]: клиент генерирует пару ключей RSA и отправляет открытый ключ; кластер выбирает фактический уровень, генерирует сеансовый ключ Triple DES, шифрует его открытым ключом клиента и возвращает. Протокол одинаков для `rmngr` и `rphost`.

Где задаётся и как складывается:

| Место | Как задать | Можно ли изменить |
|---|---|---|
| Информационная база | Свойство «Защищённое соединение» при создании базы в кластере | **Нет**, после создания не меняется [офиц.] |
| Кластер | Свойство кластера «Защищённое соединение» | Да, в процессе работы [офиц.] |
| Агент сервера | Ключ `-seclev` / переменная `SRV1CV8_SECLEV` | Да, перезапуском службы |
| Клиент | Параметр запуска `/SLev` — у конфигуратора, толстого клиента и внешнего соединения; тонкий клиент всегда использует уровень базы | Только повысить |

- Клиент ↔ кластер: наибольшее из уровня базы в реестре и уровня, запрошенного клиентом.
- Консоль ↔ агент: наибольшее из `-seclev` агента и уровней всех кластеров этого центрального сервера.
- `rphost` ↔ `rmngr`: уровень кластера. `ragent` ↔ `rmngr`: наибольшее из уровня агента и уровня кластера.
- Веб-сервер ↔ кластер: RSA и Triple DES, уровень определяется свойствами базы.

Официальная рекомендация (приложение 3.9): для базы и для кластера выбирать «Только соединение» или «Постоянно».

```bash
V=8.3.27.2074
RAC=/opt/1cv8/x86_64/$V/rac
CL=$($RAC cluster list | awk '/^cluster/{print $3; exit}')

# текущий уровень кластера
$RAC cluster list | grep -E '^(cluster|name|security-level)'

# уровень конкретной базы (нужны учётные данные администратора кластера и пользователя базы)
IB=$($RAC infobase --cluster=$CL summary list --cluster-user=admin --cluster-pwd="$CLUSTER_PWD" | awk '/^infobase/{print $3; exit}')
$RAC infobase --cluster=$CL info --infobase=$IB --cluster-user=admin --cluster-pwd="$CLUSTER_PWD" \
     --infobase-user=Администратор --infobase-pwd="$IB_PWD" | grep -E '^(name|security-level)'

# повысить уровень кластера (⚠ параметр сверить: rac help cluster)
$RAC cluster update --cluster=$CL --security-level=1 --agent-user=srvadmin --agent-pwd="$AGENT_PWD"

# уровень агента
sudo systemctl edit srv1cv8-$V@default     # [Service] / Environment=SRV1CV8_SECLEV=1
sudo systemctl restart srv1cv8-$V@default
```

⚠ Имена параметров `rac` в этом и следующих примерах приведены по памяти и практике; в прочитанной документации 8.5.1 перечня параметров `rac` нет. Сверяйте: `rac help cluster`, `rac help infobase`.

Про TLS: в документации 8.3.27 и 8.5.1 собственный протокол кластера защищается только RSA и Triple DES. Triple DES сегодня считается устаревшим шифром. Если требуется современная криптография, публикуйте базы по HTTPS и закрывайте порты кластера, а трафик между серверами выносите в изолированный сегмент или VPN [практика]. ⚠ Появилась ли поддержка TLS для собственного протокола в 8.5.4 и новее — не подтверждено.

### 7.2. HTTPS для веб-клиента и тонкого клиента

Официально [офиц.]:

- обмен клиента с веб-сервером защищается протоколами SSL/TLS средствами веб-сервера (HTTPS);
- на сервере нужен действительный сертификат; клиентские сертификаты — по желанию;
- клиент на Linux не умеет брать клиентские сертификаты из хранилища Windows;
- для баз, доступных из интернета, HTTP использовать не рекомендуется.

Настройка Apache на Ubuntu [практика]:

```bash
sudo a2enmod ssl headers
sudo install -d -m 750 /etc/apache2/tls
sudo install -o root -g root -m 644 srv1c.crt       /etc/apache2/tls/srv1c.crt    # сертификат и цепочка
sudo install -o root -g root -m 600 srv1c.key       /etc/apache2/tls/srv1c.key    # закрытый ключ
sudoedit /etc/apache2/sites-available/1c-ssl.conf
```

```apache
<VirtualHost *:443>
    ServerName srv1c.example.local
    SSLEngine on
    SSLCertificateFile    /etc/apache2/tls/srv1c.crt
    SSLCertificateKeyFile /etc/apache2/tls/srv1c.key
    SSLProtocol -all +TLSv1.2 +TLSv1.3
    Header always set Strict-Transport-Security "max-age=31536000"
    # публикации 1С подключаются здесь же или через IncludeOptional
</VirtualHost>

<VirtualHost *:80>
    ServerName srv1c.example.local
    Redirect permanent / https://srv1c.example.local/
</VirtualHost>
```

```bash
sudo a2ensite 1c-ssl
sudo apachectl configtest && sudo systemctl reload apache2
curl -sI https://srv1c.example.local/buh/ | head -5
openssl s_client -connect srv1c.example.local:443 -servername srv1c.example.local </dev/null 2>/dev/null \
  | openssl x509 -noout -subject -issuer -dates
```

На стороне клиента 1С: источник корневых сертификатов — раздел 3.8; ограничение версии TLS — `ForceTLS1_x` в `conf.cfg`; параметры `HttpsCA`, `HttpsCert` в `ibases.v8i`.

### 7.3. Соединение сервера 1С с PostgreSQL

Официальная позиция [офиц., п. 2.2.9.6]: защита канала «кластер — СУБД» обеспечивается средствами СУБД; все поддерживаемые СУБД умеют обмениваться данными по SSL. Параметров SSL в свойствах информационной базы нет.

Как это работает на практике [практика]:

- Сервер 1С подключается к PostgreSQL через клиентскую библиотеку libpq. У libpq режим `sslmode` по умолчанию — `prefer`: шифровать, если сервер поддерживает SSL, сертификат сервера не проверять [офиц., PostgreSQL].
- Значит, достаточно включить SSL на стороне PostgreSQL и запретить нешифрованные подключения строками `hostssl` в `pg_hba.conf`.
- ⚠ Не подтверждено: собрана ли libpq в составе платформы с поддержкой SSL во всех сборках и учитывает ли сервер 1С переменные окружения libpq. Проверяйте фактом — запросом к `pg_stat_ssl`.

На сервере PostgreSQL (пути для пакетов Debian/Ubuntu; у Postgres Pro свои):

```bash
PGV=17
sudoedit /etc/postgresql/$PGV/main/postgresql.conf
#   ssl = on
#   ssl_cert_file = '/etc/postgresql/tls/server.crt'
#   ssl_key_file  = '/etc/postgresql/tls/server.key'

# самоподписанный сертификат для проверки (команда из документации PostgreSQL)
sudo install -d -o postgres -g postgres -m 700 /etc/postgresql/tls
sudo -u postgres openssl req -new -x509 -days 365 -nodes -text \
     -out /etc/postgresql/tls/server.crt -keyout /etc/postgresql/tls/server.key \
     -subj "/CN=pg1.example.local"
sudo chmod 600 /etc/postgresql/tls/server.key

sudoedit /etc/postgresql/$PGV/main/pg_hba.conf
#   hostssl  all  usr1cv8  192.168.1.50/32  scram-sha-256
#   (строки host для этого адреса убрать)

sudo systemctl reload postgresql       # параметры ssl и pg_hba.conf перечитываются без остановки (PostgreSQL 10+)
sudo -u postgres psql -c "SHOW ssl;" -c "SELECT pg_conf_load_time();"
```

Строки `pg_hba.conf` действуют на новые соединения. Уже открытые соединения сервера 1С останутся прежними до переподключения — чтобы проверить результат, перезапустите рабочие процессы или службу 1С в окно обслуживания.

Проверка, что соединения 1С действительно шифруются:

```bash
sudo -u postgres psql -c "
SELECT a.usename, a.client_addr, a.datname, s.ssl, s.version, s.cipher
FROM pg_stat_ssl s JOIN pg_stat_activity a USING (pid)
WHERE a.client_addr IS NOT NULL ORDER BY 1,3;"
```

В столбце `ssl` должно быть `t`. Если после перехода на `hostssl` сервер 1С не может подключиться к базе, значит, его libpq не устанавливает SSL — верните строку `host` и разбирайтесь.

Проверка подлинности сервера СУБД (защита от подмены) [практика, ⚠ не подтверждено для 1С]: libpq читает переменные окружения, если приложение не задало параметр явно. Их можно задать службе 1С:

```ini
[Service]
Environment=PGSSLMODE=verify-full
Environment=PGSSLROOTCERT=/etc/1c/pg-root.crt
```

При `verify-full` имя сервера СУБД в свойствах базы должно совпадать с именем в сертификате.

Если 1С и PostgreSQL на одном хосте: укажите сервер СУБД как `localhost`, оставьте `listen_addresses = 'localhost'` — шифрование не требуется, порт 5432 снаружи недоступен.

### 7.4. Отладка

- Режим отладки (`-debug`) открывает удалённое выполнение и просмотр кода и снижает производительность. На рабочем сервере держите его выключенным (`SRV1CV8_DEBUG=` пусто).
- Если отладка нужна: сервер отладки `dbgs` (порт 1550) защищают паролем (`-debugServerPwd`) или списком пользователей (`-debugServerUsers <файл>`). Официальная рекомендация: при включённом сервере отладки использовать стойкие пароли [офиц.].
- Порт 1550 и диапазон из `debugcfg.xml` открывайте только для рабочих мест разработчиков.

## 8. Администраторы центрального сервера и кластера

### 8.1. Как устроено

[офиц., п. 2.2.9.9 и приложение 3.2–3.3]

- Два независимых списка: администраторы **центрального сервера** (управляют самим сервером: список кластеров, администраторы сервера) и администраторы **кластера** (управляют конкретным кластером: базы, сеансы, рабочие серверы, профили). Полномочия не пересекаются.
- По умолчанию оба списка пусты, аутентификация отключена. Любой, кто может подключиться к центральному серверу, выполняет любые административные действия.
- Аутентификация включается автоматически, как только в список добавлен первый администратор.
- После включения не-администратор сервера может только смотреть и менять параметры соединения с сервером в консоли; не-администратор кластера — только смотреть свойства кластера.
- У администратора: имя, описание, аутентификация паролем и/или аутентификация ОС (пользователь ОС в виде `\\домен\пользователь`).
- Рекомендация: в каждом списке должен быть **хотя бы один администратор с паролем** (стойким); дополнительные могут использовать аутентификацию ОС.
- Через `ras`/`rac` аутентификация ОС для администраторов не работает — только имя и пароль.
- На рабочем сервере, который не является центральным, непустой список администраторов должен содержать либо администратора с аутентификацией ОС для пользователя, от которого работает `ragent` центрального сервера, либо администратора с тем же именем и паролем, что на центральном.

Новое в 8.5.4 [офиц., v8.1c.ru и блог 27.05.2025]:

- защита от подбора: по умолчанию после **10** неуспешных попыток вход блокируется на **15 минут**; число попыток и время блокировки (в секундах) настраиваются для сервера и для кластера из встроенного языка, `rac`, COM- и Java-интерфейсов (⚠ имена параметров `rac` не опубликованы в анонсе);
- пароли администраторов при установке проверяются по встроенному списку скомпрометированных;
- уровень доступа «Только просмотр» для администраторов кластера и центрального сервера (служба безопасности, поддержка, аудит);
- одновременная работа нескольких администраторов с настройками кластера;
- завершение всех сеансов пользователя из консоли и функции «Управление серверами».

### 8.2. Команды rac

⚠ Синтаксис по практике; сверяйте с `rac help agent` и `rac help cluster` своей версии.

```bash
V=8.3.27.2074
RAC=/opt/1cv8/x86_64/$V/rac
CL=$($RAC cluster list | awk '/^cluster/{print $3; exit}')

# 1. Администратор центрального сервера (пока список пуст, учётные данные не нужны)
$RAC agent admin register --name=srvadmin --pwd="$AGENT_PWD" --descr="Администратор сервера" --auth=pwd
$RAC agent admin list --agent-user=srvadmin --agent-pwd="$AGENT_PWD"

# 2. Администратор кластера
$RAC cluster admin register --cluster=$CL --name=admin --pwd="$CLUSTER_PWD" \
     --descr="Администратор кластера" --auth=pwd \
     --agent-user=srvadmin --agent-pwd="$AGENT_PWD"
$RAC cluster admin list --cluster=$CL --cluster-user=admin --cluster-pwd="$CLUSTER_PWD"

# 3. Дальше все команды кластера требуют --cluster-user / --cluster-pwd
$RAC infobase --cluster=$CL summary list --cluster-user=admin --cluster-pwd="$CLUSTER_PWD"
$RAC session  --cluster=$CL list         --cluster-user=admin --cluster-pwd="$CLUSTER_PWD"

# удалить администратора
$RAC cluster admin remove --cluster=$CL --name=olduser --cluster-user=admin --cluster-pwd="$CLUSTER_PWD"
$RAC agent admin remove --name=olduser --agent-user=srvadmin --agent-pwd="$AGENT_PWD"
```

Пароли в примерах берутся из переменных окружения — как хранить их в сценариях, см. раздел 10.7.

### 8.3. Если пароль администратора утерян

- 8.5.4 и новее: ключи запуска агента `/resetServerAdmins` и `/resetClusterAdmins` (⚠ по описанию изменений версии; синтаксис и порядок действий сверить с документацией 8.5.4).
- 8.3.x и 8.5.1 [практика, ⚠ неофициально]: остановить службу, сделать копию каталога данных, затем либо восстановить реестр из резервной копии, сделанной до установки пароля, либо удалить список администраторов правкой `1cv8wsrv.lst` / `1CV8Clst.lst` (раздел 3.7), либо пересоздать кластер и заново зарегистрировать базы. Журналы регистрации лежат в подкаталогах `reg_<порт>/<UUID базы>/` — при пересоздании кластера их нужно сохранить.
- Вывод: пароли администраторов кластера храните в менеджере паролей организации, а копию реестра делайте после каждого изменения состава администраторов.

## 9. Профили безопасности, безопасный режим, защита от опасных действий

### 9.1. Профиль безопасности

[офиц., п. 2.2.8 клиент-серверного руководства 8.5.1]

- Профиль безопасности — набор явно заданных разрешений на доступ серверного кода к внешним ресурсам. Создаёт его администратор кластера.
- Доступен **только с лицензией КОРП**.
- Назначается базе в её свойствах: «Профиль безопасности» (весь серверный код базы) и отдельно «Профиль безопасности безопасного режима» (фрагменты кода, выполняемые в безопасном режиме).
- Каждое разрешение устроено одинаково: флажок установлен — полный доступ к категории; флажок снят и список пуст — доступа нет; флажок снят и список заполнен — доступ только к перечисленным ресурсам.
- Официальная рекомендация: настроенные профили для обычной работы и для безопасного режима, по принципу минимальных привилегий. Для баз на «Библиотеке стандартных подсистем» список нужных ресурсов даёт отчёт «Внешние ресурсы, используемые программой и дополнительными модулями».

| Разрешение | Что контролирует | Особенности |
|---|---|---|
| Может использоваться как профиль безопасности безопасного режима | Можно ли указывать имя профиля при включении безопасного режима и подключении внешних отчётов и обработок | — |
| Файловая система сервера | Доступ к каталогам сервера через виртуальные каталоги | Раздел 9.2 |
| COM-объекты | Работа с COM на сервере | Только сервер Windows; на Linux не действует |
| Внешние компоненты | Разрешённые компоненты: имя и контрольная сумма (SHA-1 в base64) | Компоненте Native API нужна отдельная запись на каждую платформу (Windows и Linux, 32 и 64 бита). Неразрешённая компонента — исключение при подключении |
| Внешние модули | Внешние отчёты, обработки и расширения, которые можно использовать **без** безопасного режима: имя и контрольная сумма | Если снят флажок «Разрешён полный доступ: внешние модули», `Выполнить()` и `Вычислить()` работают только в безопасном режиме |
| Приложения ОС | Шаблоны разрешённых строк запуска | Раздел 9.3 |
| Интернет-ресурсы | Имя, адрес (без протокола), порт (0 — любой), протокол: `imap`, `pop3`, `smtp`, `http`, `https`, `ftp`, `ftps` | При ограничении объект `ИнтернетСоединение` недоступен совсем; `ИнтернетПочта`, `HTTPСоединение`, `FTPСоединение`, `WSОпределения` — только к разрешённым ресурсам |
| Привилегированный режим | Можно ли включать привилегированный режим, когда профиль используется как профиль безопасного режима | При снятом флажке действуют «Роли привилегированного режима» |
| Криптографические функции | Методы `МенеджерКриптографии` на сервере: шифрование, подпись, проверка, хранилище сертификатов | Без разрешения — исключение |
| Расширение прав доступа | Могут ли расширения конфигурации расширять права | — |
| Расширение всех модулей конфигурации | Какие модули доступны для расширения | Поддерживаются белый и чёрный списки |

Контрольную сумму внешней компоненты или обработки получают объектом `ХешированиеДанных` и функцией `Base64Строка()`; для расширения — в конфигураторе: «Конфигурация → Расширения конфигурации → Действия → Показать контрольную сумму» [офиц.].

Новое в 8.5.4 [офиц., v8.1c.ru и блог 26.08.2025]:

- профиль можно назначить всему кластеру — он действует на базы без собственного профиля;
- новая настройка «Изменение технологических настроек»: без неё недоступны операции с хранилищем двоичных данных, полнотекстовым поиском, журналом регистрации, копиями базы и табличными пространствами;
- сообщения о нарушении профиля содержат имя COM-объекта, внешней компоненты или адрес интернет-ресурса; во встроенном языке — `КатегорияОшибки.ОграничениеПрофиляБезопасности`; в журнал регистрации добавлены события о таких ошибках.

### 9.2. Виртуальные каталоги

Каждый профиль имеет виртуальную файловую систему. Код передаёт логический путь, платформа подменяет его физическим; физического пути прикладной код не видит. Если в профиле заданы виртуальные каталоги, доступны только они [офиц.].

Параметры виртуального каталога: логический URL (начало пути, уникален в профиле), физический URL (локальный каталог или сетевой ресурс, допускает подстановки), флажки «Чтение данных» и «Запись данных». Предопределённые логические URL: `/bin` (исполняемые модули платформы, функция `КаталогПрограммы()`) и `/temp` (временные файлы, функция `КаталогВременныхФайлов()`).

| Подстановка | Значение |
|---|---|
| `%r` | имя информационной базы в кластере |
| `%i` | идентификатор информационной базы |
| `%z` | значения разделителей текущего сеанса (в формате параметра `/Z`) |
| `%s` | номер сеанса |
| `%c` | номер соединения |
| `%p` | идентификатор входа в безопасный режим |
| `%e` | каталог исполняемых модулей платформы |
| `%t` | каталог временных файлов ОС |
| `%u` | каталог данных приложений текущего пользователя |
| `%a` | каталог данных приложений всех пользователей |
| `%n` | имя текущего пользователя информационной базы |
| `%%` | символ процента |

Недопустимые в пути символы заменяются подчёркиванием. Каталоги с `%s` удаляются при завершении сеанса, с `%p` — при выходе из безопасного режима.

Пример: логический URL `/temp`, физический `%t/1c/%r/%s`, чтение и запись — у каждой базы и каждого сеанса свой временный каталог, который очищается сам.

### 9.3. Приложения ОС

Разрешённое приложение описывается именем и шаблоном строки запуска — набором слов-масок через пробел [офиц.]:

| Символ маски | Значение |
|---|---|
| `%` | любая последовательность символов |
| `_` | один любой символ |
| `*` в начале слова | путь в виртуальном каталоге; перед запуском заменяется физическим путём |
| `\` перед словом | слово понимается буквально, без масок |

Пример из документации: `xcopy */temp/% */userdata/%` — разрешено копирование из виртуального каталога `/temp` в `/userdata`. Вызов `ЗапуститьПриложение()` с приложением или параметрами не из списка вызывает исключение. Пустой список — запуск приложений запрещён.

### 9.4. Команды rac для профилей

⚠ Синтаксис по практике, сверяйте: `rac help profile`, `rac help infobase`.

```bash
V=8.3.27.2074
RAC=/opt/1cv8/x86_64/$V/rac
CL=$($RAC cluster list | awk '/^cluster/{print $3; exit}')
AUTH="--cluster-user=admin --cluster-pwd=$CLUSTER_PWD"

# список профилей
$RAC profile --cluster=$CL list $AUTH

# создать или изменить профиль: можно использовать как профиль безопасного режима, привилегированный режим запрещён
$RAC profile --cluster=$CL update --name=restricted --descr="Ограниченный" --config=yes --priv=no $AUTH

# разрешённый каталог в профиле
$RAC profile --cluster=$CL acl --name=restricted directory update \
     --alias=/exchange --physicalPath=/srv/1c/exchange/%r --allowedRead=yes --allowedWrite=yes $AUTH

# разрешённый интернет-ресурс
$RAC profile --cluster=$CL acl --name=restricted inet update \
     --name=its --protocol=https --url=its.1c.ru --port=443 $AUTH

# назначить профили базе
IB=$($RAC infobase --cluster=$CL summary list $AUTH | awk '/^infobase/{print $3; exit}')
$RAC infobase --cluster=$CL update --infobase=$IB --infobase-user=Администратор --infobase-pwd="$IB_PWD" \
     --security-profile-name=restricted --safe-mode-security-profile-name=restricted $AUTH
```

Вводите профиль сначала на копии базы: слишком строгий профиль проявляется ошибками «…запрещено профилем безопасности» в самых разных местах (обмены, печать, загрузка классификаторов).

### 9.5. Безопасный режим

Безопасный режим включается из встроенного языка (`УстановитьБезопасныйРежим()`), а также при подключении внешних отчётов и обработок. Параметром может быть `Истина` либо имя профиля безопасности, помеченного «может использоваться как профиль безопасного режима» [офиц.].

В безопасном режиме без профиля платформа запрещает то, что выходит за пределы базы: привилегированный режим (отменяется, попытки включить его игнорируются), COM-объекты, загрузку внешних компонент, доступ к файловой системе, доступ в интернет (Уточнено 11.10.2026 по «Руководству разработчика» 8.3.27, разд. 5.5.4.3 — конспект `../its-docs/dev-gl05-obekty-konfiguracii.md`: перечень документации состоит именно из этих групп операций с поимённым списком методов; исключения для временных файлов в нём нет, а запуск приложений операционной системы в перечне безопасного режима не назван — он относится к механизму защиты от опасных действий, раздел 9.6 ниже и `../its-docs/dev-pr07-osobennosti-rezhimov.md`, разд. 7.10).

Практический смысл для администратора: внешние обработки и расширения из недоверенных источников должны выполняться в безопасном режиме, а право «Интерактивное открытие внешних обработок» у обычных пользователей должно быть снято — это прямая рекомендация документации.

### 9.6. Защита от опасных действий

- У пользователя информационной базы есть флажок «Защита от опасных действий» (появился в 8.3.9). При включённой защите платформа предупреждает или блокирует потенциально опасные действия.
- Действия, на которые влияет защита [офиц., описание параметра `DisableUnsafeActionProtection`]: загрузка внешних отчётов, обработок и расширений конфигурации (на сервере); загрузка внешних компонент; запуск внешнего приложения; открытие табличного документа и переход по ссылке в поле HTML-документа (на клиенте).
- Отключение для отдельных баз — параметр `DisableUnsafeActionProtection` в `conf.cfg` (раздел 2): список регулярных выражений, сравниваемых со строкой соединения базы.
- Не отключайте защиту «для всех» (`.*`) на рабочем сервере только затем, чтобы убрать предупреждения. Сначала снимите у пользователей право открывать внешние обработки.

## 10. Безопасность на уровне ОС

### 10.1. Пользователь службы и права на каталоги

Официальные требования к пользователю, от которого работает кластер [офиц., п. 1.3.2 и приложение 3.4–3.5]:

- полные права на каталог данных кластера;
- на Linux — право чтения каталога временных файлов;
- если рабочие процессы запущены от отдельного пользователя через `swpuser.ini`, у него **не должно** быть доступа к каталогу данных кластера;
- пользователям ОС и домена не давать доступа к файловой системе сервера 1С (особенно к каталогу данных кластера) и к компьютеру с СУБД.

Рекомендуемая раскладка прав [практика]:

| Каталог или файл | Владелец:группа | Режим | Зачем |
|---|---|---|---|
| `/home/usr1cv8` | `usr1cv8:grp1cv8` | `750` | домашний каталог службы |
| `/home/usr1cv8/.1cv8/1C/1cv8` (каталог данных) | `usr1cv8:grp1cv8` | `700` | реестр, журналы регистрации, сеансовые данные |
| `…/1cv8wsrv.lst`, `…/reg_*/1CV8Clst.lst` | `usr1cv8:grp1cv8` | `600` | хеши паролей администраторов, пароли СУБД (AES128) |
| `/opt/1cv8/conf`, файлы в нём | `root:grp1cv8` | `750` / `640` | сервер читает, изменить не может |
| `/etc/1c/usr1cv8.keytab` или keytab в каталоге версии | `usr1cv8:grp1cv8` | `600` | ключ Kerberos |
| `/var/1C/licenses` | `usr1cv8:grp1cv8` | `750` | программные лицензии |
| `/var/log/1c/…` (технологический журнал) | `usr1cv8:grp1cv8` | `750` | запись журнала |
| каталоги обмена | `usr1cv8:grp1cv8` или отдельная группа | `770` | только то, что нужно обменам |
| `/opt/1cv8/x86_64/<версия>` | `root:root` | как установлено | серверу достаточно чтения и исполнения |

```bash
# проверить, от кого работают процессы
ps -o user=,group=,pid=,args= -C ragent,rmngr,rphost,ras

# найти файлы в каталоге данных, принадлежащие не usr1cv8 (последствие запуска от root)
sudo find /home/usr1cv8/.1cv8 ! -user usr1cv8 -ls | head

# исправить владельца и закрыть каталог данных от посторонних
sudo chown -R usr1cv8:grp1cv8 /home/usr1cv8/.1cv8
sudo chmod 700 /home/usr1cv8/.1cv8/1C/1cv8

# у пользователя службы не должно быть sudo и входа по паролю
sudo -l -U usr1cv8
sudo passwd -S usr1cv8          # L — пароль заблокирован
```

Правила:

- Никогда не запускайте `ragent` от `root` «на минутку». Исключение — осознанная схема с `swpuser.ini`.
- Не добавляйте `usr1cv8` в группы `sudo`, `adm`, `docker`.
- Добавлять `www-data` в `grp1cv8` (чтобы модуль веб-сервера писал технологический журнал) можно, но тогда веб-сервер получает доступ ко всему, что открыто группе. Каталог данных кластера держите с режимом `700`.
- Каталог временных файлов сервера лучше вынести из общего `/tmp` (`Environment=TMPDIR=/var/tmp/1c`, владелец `usr1cv8`, режим `700`).

### 10.2. Сетевой экран

Официально [офиц., приложение 3.8]: разрешать входящие соединения только на порты, нужные кластеру; если пользователи работают только через веб-сервер (80/443), порты кластера закрыть; при нестандартных портах в строке запуска — ограничивать их.

| Порт | Процесс | Кому открыт |
|---|---|---|
| 1540/tcp | `ragent` | консоли администрирования, другим серверам кластера, `ras` (если он на другой машине) |
| 1541/tcp | `rmngr` | клиентам (тонкий и толстый клиент, конфигуратор), веб-серверу, серверам кластера |
| 1560–1591/tcp | `rphost` | тем же, кому 1541 |
| 1545/tcp | `ras` | только рабочим местам администраторов; если `rac` запускается на самом сервере — никому |
| 1550/tcp | `dbgs` | только разработчикам и только при включённой отладке |
| 1555/tcp | HTTP-шлюз показателей `ras` | системе мониторинга (по умолчанию слушает только `localhost`) |
| 5432/tcp | PostgreSQL | только серверу 1С |
| 80, 443/tcp | Apache | пользователям веб-клиента |

Процессы 1С слушают на всех интерфейсах; параметра привязки к адресу в документации нет. Единственное средство ограничения — сетевой экран.

```bash
sudo ufw default deny incoming
sudo ufw default allow outgoing
sudo ufw allow from 192.168.1.0/24 to any port 22 proto tcp comment 'SSH'

# клиенты 1С из локальной сети
sudo ufw allow from 192.168.1.0/24 to any port 1540,1541 proto tcp comment '1C ragent, rmngr'
sudo ufw allow from 192.168.1.0/24 to any port 1560:1591 proto tcp comment '1C rphost'

# сервер администрирования — только с рабочего места администратора
sudo ufw allow from 192.168.1.10 to any port 1545 proto tcp comment '1C ras'

# веб-клиент
sudo ufw allow 443/tcp comment 'HTTPS'

sudo ufw enable
sudo ufw status numbered

# что реально слушает и на каких адресах
sudo ss -tlnp | grep -E 'ragent|rmngr|rphost|ras|dbgs|postgres|apache2'
```

Вариант «только веб»: правила для 1540, 1541, 1560:1591 не создаются вовсе; Apache и кластер на одном хосте общаются через `localhost`.

### 10.3. PostgreSQL

- Официально [офиц., приложение 3.7]: пользователь СУБД, через которого работает кластер, должен иметь только необходимые кластеру привилегии; настоятельно рекомендуется **отдельный пользователь СУБД на каждую информационную базу**.
- Не подключайте базы 1С под суперпользователем `postgres`. Заведите роль-владельца базы [практика]. **Уточнено 10.10.2026** (полный текст документации 8.3.27, глава 5, разд. 5.2.1.3.3): для создания информационной базы пользователю СУБД нужен `SUPERUSER`, причём только на момент создания — потом привилегию можно отозвать (`alter user dbuser with nosuperuser;`). Прежняя формулировка автора про `CREATEDB` документацией не подтверждается: Минимально достаточный набор привилегий для роли в документации 1С не перечислен: для создания базы средствами 1С роли нужен `CREATEDB`, для работы с готовой базой — быть её владельцем; проверьте на своей сборке СУБД.
- `listen_addresses` — только нужные адреса (`localhost`, если СУБД на том же хосте).
- В `pg_hba.conf` — конкретная роль, конкретный адрес сервера 1С, метод `scram-sha-256`, никаких `trust` и `0.0.0.0/0`.

```bash
sudo -u postgres psql -c "CREATE ROLE buh_owner LOGIN PASSWORD 'длинный-пароль';"
sudo -u postgres psql -c "ALTER ROLE buh_owner CREATEDB;"      # нужно, только если базу будет создавать сама 1С
# pg_hba.conf:
#   hostssl  buh  buh_owner  192.168.1.50/32  scram-sha-256
sudo -u postgres psql -c "SHOW listen_addresses;" -c "SHOW password_encryption;"
sudo -u postgres psql -c "SELECT rolname, rolsuper, rolcreatedb FROM pg_roles WHERE rolcanlogin;"
```

Пароль роли хранится в реестре кластера обратимо (AES128) — ещё одна причина беречь файл `1CV8Clst.lst` и его копии. Подробности настройки СУБД — в статьях о PostgreSQL.

### 10.4. AppArmor и ограничения systemd

AppArmor [практика]:

- Платформа 1С не поставляет профилей AppArmor: процессы `ragent`, `rmngr`, `rphost` работают без ограничений AppArmor (⚠ утверждение по опыту, в документации 1С AppArmor не упоминается).
- Проверка: `sudo aa-status` — в списке профилей не должно быть процессов 1С; `sudo journalctl -k | grep -i 'apparmor.*DENIED'` — отказы, если они есть.
- Свой профиль писать можно (`sudo apt install apparmor-utils`, затем `aa-genprof`, сначала в режиме `complain`), но серверу 1С нужны запись в каталог данных, временные файлы, сеть, запуск Java, LibreOffice и внешних программ. Строгий профиль легко ломает редкие функции (печать в PDF, полнотекстовый поиск, реструктуризацию v2). Официально такие профили не поддерживаются.
- Если AppArmor мешает другому компоненту (например, пользовательский профиль для Apache блокирует `wsap24.so`), временно переведите профиль в режим жалоб: `sudo aa-complain /etc/apparmor.d/<профиль>`.

Ограничения systemd в drop-in [практика, ⚠ на 1С не проверено — вводить на стенде и по одной директиве]:

```ini
[Service]
NoNewPrivileges=yes
ProtectSystem=full
ProtectKernelTunables=yes
ProtectControlGroups=yes
RestrictSUIDSGID=yes
```

- `ProtectSystem=full` делает `/usr`, `/boot` и `/etc` доступными только для чтения — серверу 1С запись туда не нужна.
- `NoNewPrivileges=yes` несовместим со схемой `swpuser.ini` и с прикладным кодом, вызывающим `sudo`.
- `PrivateTmp=yes` и `ProtectHome=yes` **не включайте**: первое ломает обмен файлами через `/tmp` с другими службами, второе закрывает каталог данных в `/home/usr1cv8`.
- Оценка текущего состояния: `systemd-analyze security srv1cv8-<версия>@default`.

### 10.5. Антивирус и исключения

[практика; официальный текст 1С об исключениях для Linux в этой сессии не найден]

Проверка «на лету» файлов, которые сервер 1С и СУБД непрерывно переписывают, даёт замедление и ошибки блокировки. Из постоянной защиты исключают:

- каталог данных кластера `/home/usr1cv8/.1cv8/1C/1cv8` (реестр, журналы регистрации, сеансовые данные, индексы поиска);
- каталог временных файлов сервера (`/tmp` или свой `TMPDIR`);
- каталог технологического журнала (`/var/log/1c`);
- каталог данных PostgreSQL (`/var/lib/postgresql/<версия>/main` или каталог Postgres Pro) и каталог WAL;
- процессы `ragent`, `rmngr`, `rphost`, `ras`, `postgres`.

Каталоги обмена и загрузки файлов пользователей исключать **не надо** — это как раз точка входа вредоносных файлов. Каталог `/opt/1cv8` проверяйте по расписанию.

### 10.6. Аудит

Журнал регистрации базы [офиц., приложение 3.10]:

- журнал регистрации должен быть включён, регистрировать нужно все события;
- для контроля обращений к критичным объектам настраивают события «Доступ» и «Отказ в доступе»;
- с лицензией КОРП включаются события аудита прав доступа (для файловых баз — параметр `EnableAccessRightAuditEventsWrite`);
- 8.5.4: для событий «Информационная база. Изменение роли» и «Пользователи. Изменение прав доступа» детали показываются деревом — видно, какие именно права изменились; 8.5.6 (выполнено по плану) — интеграция с SIEM-системами.

Что смотреть в журнале регистрации в первую очередь [практика]: «Сеанс. Аутентификация», «Сеанс. Ошибка аутентификации», «Пользователи. Добавление / Изменение / Удаление», «Доступ. Отказ в доступе», изменение конфигурации базы данных. Файлы журнала лежат в `<каталог данных>/reg_<порт>/<UUID базы>/1Cv8Log` и в резервную копию СУБД не входят.

Технологический журнал [офиц.: в таблице событий документации 8.3.27 `ADMIN` — управляющие воздействия администратора кластера серверов; сверено по полному тексту 10.10.2026]: событие `ADMIN` фиксирует управляющие действия администратора кластера (через консоль, `rac`, программный интерфейс). Пример настройки — в разделе 3.1.

```bash
# действия администраторов кластера за сегодня
sudo grep -r -h ',ADMIN,' /var/log/1c/audit --include="$(date +%y%m%d)*.log" | tail -20
# попытки соединения и имена пользователей ОС
sudo grep -r -h ',CONN,' /var/log/1c/audit | grep -i 'DstUserName' | tail
```

Уровень ОС [практика]:

```bash
sudo apt install -y auditd
# правила пишите только для существующих путей: строка с несуществующим каталогом даёт ошибку загрузки
sudo tee /etc/audit/rules.d/1c.rules >/dev/null <<'EOF'
-w /opt/1cv8/conf -p wa -k 1c_conf
-w /home/usr1cv8/.1cv8/1C/1cv8/conf -p wa -k 1c_conf
-w /etc/1c -p wa -k 1c_secrets
-w /home/usr1cv8/.1cv8/1C/1cv8/1cv8wsrv.lst -p wa -k 1c_registry
-w /etc/systemd/system -p wa -k systemd_units
EOF
sudo augenrules --load
sudo ausearch -k 1c_conf -ts today
sudo ausearch -k 1c_secrets -ts this-week

# журнал службы: запуски, остановки, падения
journalctl -u 'srv1cv8-*' --since "7 days ago" --no-pager | grep -E 'Started|Stopped|Failed|Main process exited'
```

### 10.7. Пароли в сценариях

Проблемы:

- `rac`, `ibcmd`, `1cv8 DESIGNER` принимают пароли параметрами командной строки. Пока команда выполняется, параметры видны всем локальным пользователям в `ps aux` и в `/proc/<pid>/cmdline`.
- Пароли в тексте сценария попадают в резервные копии, системы контроля версий и историю оболочки.

Приёмы [практика]:

```bash
# 1. Файл с секретами, доступный только root.
#    Каталог /etc/1c — root:grp1cv8 750 (как в разделе 5.5): серверу нужен вход в него ради keytab,
#    а сам файл rac.env серверу недоступен (600, root)
sudo install -d -o root -g grp1cv8 -m 750 /etc/1c
sudo install -o root -g root -m 600 /dev/null /etc/1c/rac.env
sudoedit /etc/1c/rac.env
#   AGENT_USER=srvadmin
#   AGENT_PWD=...
#   CLUSTER_USER=admin
#   CLUSTER_PWD=...

# 2. В сценарии — читать файл, а не хранить пароль в тексте
set -a; . /etc/1c/rac.env; set +a
"$RAC" session --cluster="$CL" list --cluster-user="$CLUSTER_USER" --cluster-pwd="$CLUSTER_PWD"

# 3. Интерактивно — не оставлять пароль в истории
read -rs -p 'Пароль администратора кластера: ' CLUSTER_PWD; echo
```

- В юните systemd для регламентного сценария: `EnvironmentFile=/etc/1c/rac.env` (файл `600`, владелец `root`) или `LoadCredential=rac_pwd:/etc/1c/rac.pwd` — тогда сценарий читает пароль из `$CREDENTIALS_DIRECTORY/rac_pwd`.
- Для PostgreSQL — файл `~/.pgpass` (режим `600`, строки `хост:порт:база:роль:пароль`) или переменная `PGPASSFILE`. Не передавайте пароль в `PGPASSWORD` в командной строке.
- Видимость чужих процессов можно закрыть опцией `hidepid=2` для `/proc` (⚠ на системах с systemd требует настройки группы-исключения, проверяйте на стенде). Проще не давать посторонним вход на сервер.
- Для регламентных операций заведите отдельного администратора кластера и отдельного пользователя базы с минимальными правами, а не используйте личные учётные записи.
- Сценарии с секретами не храните в общих каталогах и репозиториях. Проверка: `sudo grep -rIl -E 'cluster-pwd=|infobase-pwd=|db-pwd=' /usr/local /opt /home /etc 2>/dev/null`.

### 10.8. Резервное копирование настроек кластера

Что входит в «настройки» (помимо самих баз в СУБД):

| Что | Где | Замечание |
|---|---|---|
| Реестр сервера и кластера | `<каталог данных>/1cv8wsrv.lst`, `reg_*/1CV8Clst.lst`, `swpuser.ini` | список баз с параметрами подключения к СУБД, администраторы, профили, требования назначения |
| Конфигурационные файлы | `/opt/1cv8/conf`, `/opt/1cv8/x86_64/<версия>/conf`, `<каталог данных>/conf` | `conf.cfg`, `logcfg.xml`, `nethasp.ini` и др. |
| Параметры службы | `/etc/systemd/system/srv1cv8-*.service.d/`, `ras-*.service.d/` | drop-in с `SRV1CV8_*` |
| Kerberos | `/etc/1c/*.keytab` или keytab в каталоге версии, `/etc/krb5.conf` | keytab можно и пересоздать, но это простой |
| Лицензии | `/var/1C/licenses` | привязаны к оборудованию, но копия нужна |
| Веб-публикации | `/var/www/*/default.vrd`, конфигурация Apache, сертификаты TLS | — |
| Текстовый снимок | вывод `rac` | чтобы восстановить настройки вручную, если реестр несовместим |

Журналы регистрации, хранилище двоичных данных и индексы поиска лежат в том же каталоге данных, но это данные, а не настройки, и копируются по своим правилам (см. статью о резервном копировании).

```bash
#!/usr/bin/env bash
# /usr/local/sbin/1c-settings-backup.sh — запускать от root (cron или таймер systemd)
set -euo pipefail
umask 077
V=8.3.27.2074
DATA=/home/usr1cv8/.1cv8/1C/1cv8
DST=/var/backups/1c-cluster
RAC=/opt/1cv8/x86_64/$V/rac
TS=$(date +%F_%H%M)
WORK=$(mktemp -d); trap 'rm -rf "$WORK"' EXIT
install -d -m 700 "$DST"

# 1. текстовый снимок настроек (служба не останавливается)
set -a; . /etc/1c/rac.env; set +a
CL=$("$RAC" cluster list | awk '/^cluster/{print $3; exit}')
AUTH=(--cluster-user="$CLUSTER_USER" --cluster-pwd="$CLUSTER_PWD")
{
  echo '== cluster';   "$RAC" cluster list
  echo '== servers';   "$RAC" server   --cluster="$CL" list "${AUTH[@]}"
  echo '== infobases'; "$RAC" infobase --cluster="$CL" summary list "${AUTH[@]}"
  echo '== profiles';  "$RAC" profile  --cluster="$CL" list "${AUTH[@]}"
} > "$WORK/rac-settings.txt" 2>&1 || true

# 2. список файлов
{
  find "$DATA" -maxdepth 2 \( -name 1cv8wsrv.lst -o -name 1CV8Clst.lst -o -name swpuser.ini \)
  find /opt/1cv8/conf /opt/1cv8/x86_64/*/conf "$DATA/conf" /etc/1c /var/1C/licenses -type f 2>/dev/null || true
  find /etc/systemd/system -maxdepth 2 -type f \( -path '*srv1cv8*' -o -path '*ras-*' \) 2>/dev/null || true
  find /var/www -maxdepth 2 -name default.vrd 2>/dev/null || true
  if [ -f /etc/krb5.conf ]; then echo /etc/krb5.conf; fi
  echo "$WORK/rac-settings.txt"
} > "$WORK/files.lst"

# 3. архив и ротация (хранить 30 дней)
#    tar возвращает 1, если файл изменился во время чтения, — это не повод прерывать сценарий
tar -czf "$DST/1c-settings_$TS.tar.gz" --ignore-failed-read -T "$WORK/files.lst" 2>/dev/null \
  || echo "tar завершился с предупреждениями, проверьте архив" >&2
tar -tzf "$DST/1c-settings_$TS.tar.gz" >/dev/null      # архив читается — только после этого удаляем старые
find "$DST" -name '1c-settings_*.tar.gz' -mtime +30 -delete
ls -lh "$DST" | tail -3
```

Пояснения:

- Архив содержит keytab, файл с паролями `rac.env` и реестр с обратимо зашифрованными паролями СУБД. Храните его как секрет: режим `600`, шифрование при выносе с сервера (`gpg -c` или средствами системы резервного копирования).
- Реестр копируется «на горячую». Для гарантированно целостной копии используйте вариант с остановкой службы из раздела 3.7 — например, раз в неделю в окно обслуживания и после каждого изменения состава баз или администраторов.

Восстановление реестра:

```bash
V=8.3.27.2074
DATA=/home/usr1cv8/.1cv8/1C/1cv8
sudo systemctl stop srv1cv8-$V@default
sudo cp -a "$DATA" "$DATA.broken.$(date +%F_%H%M)"          # сохранить текущее состояние
sudo tar -xzf /var/backups/1c-cluster/1c-settings_2026-10-09_0300.tar.gz -C / \
     "${DATA#/}/1cv8wsrv.lst" --wildcards "${DATA#/}/reg_*/1CV8Clst.lst"
sudo chown -R usr1cv8:grp1cv8 "$DATA"
sudo systemctl start srv1cv8-$V@default
/opt/1cv8/x86_64/$V/rac cluster list
```

Реестр восстанавливайте на ту же версию платформы и то же имя хоста. Реестр от более новой версии старая может не прочитать; при другом имени хоста кластер будет ссылаться на несуществующий сервер [практика].

## Типичные ошибки и подводные камни

### Конфигурационные файлы и запуск

| Симптом | Причина | Решение |
|---|---|---|
| Изменили `logcfg.xml` или `conf.cfg`, а ничего не поменялось | Файл лежит не в том каталоге `conf`; файлов два; у `usr1cv8` нет права чтения; для `conf.cfg` не перезапущена служба | `sudo find /opt/1cv8 /home/usr1cv8/.1cv8 -name <файл>`; оставить один экземпляр; `sudo -u usr1cv8 cat <файл>`; перезапуск |
| После обновления платформы пропали технологический журнал, настройки HASP, вход по ОС | Файлы лежали в каталоге старой версии `/opt/1cv8/x86_64/<версия>/` | Хранить в `/opt/1cv8/conf` и `/etc/1c`; перенести drop-in юнита на новое имя |
| После перезапуска «исчезли» все базы, кластер пустой | Агент запущен с другим `-d` или от другого пользователя и создал новый реестр | `ps -o user=,args= -C ragent`; вернуть `SRV1CV8_DATA`; старый реестр цел в прежнем каталоге |
| В каталоге данных появились файлы владельца `root`, служба не стартует | Кто-то запускал `ragent` вручную от `root` | `sudo chown -R usr1cv8:grp1cv8 /home/usr1cv8/.1cv8` |
| Значение `SRV1CV8_DEBUG=-debug -http` применилось наполовину | В drop-in значение с пробелом не взято в кавычки | `Environment="SRV1CV8_DEBUG=-debug -http"` |
| Сервер не находит сетевой ключ HASP | Широковещательный поиск не проходит через маршрутизатор; `nethasp.ini` не в том каталоге | `NH_SERVER_ADDR`, `NH_USE_BROADCAST = Disabled`; для 8.5.4+ — новый менеджер лицензий |
| `swpuser.ini` на Linux не действует | Агент работает не от `root` | Либо схема с `root` и `swpuser.ini` целиком, либо не использовать файл |
| Технологический журнал не пишут `ras` или модуль Apache | У их пользователей нет записи в каталог журнала | Общая группа и режим `770` на каталог журнала |

### Kerberos

| Симптом | Причина | Решение |
|---|---|---|
| Вместо сквозного входа — окно имени и пароля | Любое звено цепочки: DNS, время, SPN, keytab, имя пользователя в 1С | Пройти по порядку разделы 5.2–5.6; начать с `kinit -k -t` на сервере и `klist` на клиенте |
| `kinit: Clock skew too great` | Время расходится больше чем на 5 минут | `timedatectl timesync-status`; синхронизация с контроллером домена |
| `kinit: Cannot find KDC for realm` или `Cannot contact any KDC` | Область в неверном регистре; сервер не использует DNS домена; закрыт порт 88 | `default_realm = EXAMPLE.LOCAL`; `host -t SRV _kerberos._tcp.example.local`; `nc -vz dc1.example.local 88` |
| `kinit -k`: `Preauthentication failed` | Пароль учётной записи менялся после создания keytab; не совпадает kvno; изменился UPN (соль AES) | Пересоздать keytab `ktpass`, заменить файл, перезапустить службу |
| `kinit -k`: `Client … not found in Kerberos database` | У учётной записи UPN не равен имени принципала (keytab создан не `ktpass` или с `-setupn`); опечатка или регистр в имени | `Get-ADUser … -Properties userPrincipalName,servicePrincipalName`; пересоздать keytab. Сквозной вход при этом может работать: серверу для проверки билета нужен только ключ |
| `KDC has no support for encryption type` | В keytab только RC4, а в домене RC4 отключён; либо в `krb5.conf` остались `default_tkt_enctypes = rc4-hmac` | Keytab с `-crypto AES256-SHA1`, включить AES у учётной записи, убрать строки `default_*_enctypes` |
| На клиенте есть билет `usr1cv8/srv1c…`, а 1С не пускает | Keytab устарел (kvno); сервер не читает keytab (права, путь, `SRV1CV8_KEYTAB`); имя пользователя в 1С записано не так | `kvno` против `klist -k`; `sudo -u usr1cv8 klist -k <keytab>`; искать `DstUserName2` в событиях `CONN` |
| На клиенте нет билета для `usr1cv8/…` (`klist` в Windows) | SPN не зарегистрирован или продублирован; клиент обращается к серверу по IP или по имени, которого нет в SPN | `setspn -Q usr1cv8/srv1c.example.local`, `setspn -X`; подключаться по тому FQDN, который записан в принципале |
| Перестало работать после обновлений контроллеров домена в 2026 году | Отключение RC4 по умолчанию | Раздел 5.9 |
| Перестало работать после смены пароля служебной учётной записи | Увеличился kvno, старый keytab недействителен | Пересоздать keytab; на клиентах `klist purge` |
| `klist: Permission denied` при чтении keytab | Проверка запущена не от `usr1cv8` или режим файла не `600 usr1cv8` | `sudo -u usr1cv8 klist -k …`; `chown`, `chmod 600` |
| Входит под другим пользователем или «пользователь ИБ не идентифицирован» | В поле «Пользователь» короткое имя домена вместо полного или иной регистр | Записать ровно то, что показывает `DstUserName2`, с префиксом `\\` |

### Аутентификация, администрирование, профили

| Симптом | Причина | Решение |
|---|---|---|
| `rac` отвечает, что администратор кластера не аутентифицирован | В кластере появились администраторы | Добавлять `--cluster-user` и `--cluster-pwd` (для операций агента — `--agent-user`, `--agent-pwd`) |
| Через `rac` не проходит администратор с аутентификацией ОС | `ras`/`rac` её не поддерживают | Иметь администратора с паролем |
| Забыт пароль администратора кластера | — | Раздел 8.3 |
| После включения уровня «Постоянно» работа замедлилась | Весь трафик шифруется Triple DES | Уровень «Только соединение» плюс HTTPS или изолированная сеть |
| Ошибка «…запрещено профилем безопасности» | Ресурса нет в списке разрешённых | Добавить каталог, компоненту, адрес в профиль; в 8.5.4 сообщение называет ресурс |
| Внешняя обработка не открывается или выдаёт предупреждение безопасности | Защита от опасных действий, нет права на открытие внешних обработок | Подключать обработки через справочник дополнительных обработок; право и флажок у пользователя; `DisableUnsafeActionProtection` только для тестовых баз |
| После включения проверки сложности пользователь не входит со «старым» паролем | Сравнение стало чувствительным к регистру | Вводить пароль в точном регистре или сменить его |
| У всех сбросилось «Запомнить меня» | Сменили алгоритм хеширования или пароли | Ожидаемое поведение, войти заново |
| 1С не доверяет HTTPS-сертификату внутреннего удостоверяющего центра | Корневого сертификата нет в хранилище ОС сервера (или режим совместимости ниже 8.3.8 и нужен `cacert.pem`) | `update-ca-certificates`; раздел 3.8 |
| После перевода `pg_hba.conf` на `hostssl` сервер 1С не подключается к СУБД | Соединение 1С идёт без SSL либо выше осталась конфликтующая строка | Журнал PostgreSQL; `pg_stat_ssl`; порядок строк в `pg_hba.conf` |
| Порт 1545 (`ras`) доступен всей сети | `ras` слушает все интерфейсы | Правило `ufw` только для администраторов |
| Вторым фактором нельзя воспользоваться — никто не может войти | Недоступен провайдер второго фактора | Резервный провайдер (`UseNextIfFailed`), аварийная учётная запись |

Что в статье осталось неподтверждённым (помечено ⚠ по тексту):

- каталог технологического журнала «по умолчанию» на Linux (`~/.1cv8/logs` или `~/.1cv8/1C/1cv8/logs`);
- как штатный юнит передаёт `SRV1CV8_KEYTAB` процессу и нужен ли `KRB5_KTNAME`;
- регистр доменной части имени пользователя ОС при сервере на Linux;
- работа сервера 1С с AES-keytab (в документации только RC4 и DES);
- процедура сквозного входа через Apache на Linux и необходимость делегирования;
- структура `<openidconnect>` и `<accessTokenAuthentication>` в `default.vrd`;
- синтаксис `rac` для администраторов, профилей и уровня безопасности;
- ключи `/resetServerAdmins`, `/resetClusterAdmins` и параметры блокировки в 8.5.4;
- поддержка SSL библиотекой libpq в составе платформы и учёт переменных `PGSSL*`;
- значения по умолчанию блокировки аутентификации пользователей базы;
- наличие TLS для собственного протокола кластера в 8.5.4 и новее;
- минимальный набор привилегий роли PostgreSQL для 1С;
- перечень файлов `*.pfl`, расположение `location.cfg` и `cacert*.pem` на Linux.
