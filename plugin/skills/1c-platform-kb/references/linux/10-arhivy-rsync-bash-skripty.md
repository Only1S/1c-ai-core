# Архивация, rsync и bash-скрипты для автоматизации (Ubuntu Server + 1С + PostgreSQL)

> Версии: Ubuntu Server 22.04 LTS (jammy) / 24.04 LTS (noble) / 26.04 LTS (resolute, вышла 23.04.2026); bash 5.1 / 5.2 / 5.3; PostgreSQL 14–18 (актуальная — 18.6; PostgreSQL 19 на 10.10.2026 ещё не выпущен: Beta 4 от 24.09.2026, релиз по официальному roadmap — «октябрь 2026», точная дата ⚠ не подтверждена; поддержка PostgreSQL 14 заканчивается 12.11.2026); платформа 1С 8.3.21+ (единый дистрибутив, systemd-юнит `srv1cv8-<версия>@default`) и 8.5.x (на ИТС опубликована документация для 8.3.27, 8.5.1 и 8.5.4).

## Кратко — главные факты и команды

1. **Универсальный архив каталога:** `tar --zstd -cpf /backup/etc_$(date +%F).tar.zst -C / etc`; распаковать: `tar -xpf файл.tar.zst -C /куда`; посмотреть: `tar -tvf файл`. При чтении из файла tar сам определяет компрессор, флаг сжатия нужен только при чтении из конвейера.
2. **Лучший компрессор для дампов БД — zstd:** `zstd -T0 -6 файл` (все ядра, уровень 6). Уровни 1–19 (по умолчанию 3), `--ultra` открывает 20–22; распаковка одинаково быстрая на любом уровне. В отличие от gzip/xz/bzip2 zstd **не удаляет** исходный файл (нужен `--rm`). Число потоков указывайте явно (`-T N`): умолчание зависит от версии (zstd ≤ 1.5.6 — один поток; zstd 1.5.7 в Ubuntu 26.04 — до 4 потоков).
3. **gzip однопоточный**; его многопоточная замена — `pigz` (тот же формат .gz, по умолчанию потоков = числу ядер). `xz` даёт максимальное сжатие, но очень медленный; `bzip2` устарел.
4. **pg_dump сам умеет сжимать:** `pg_dump -Fc -Z zstd:6 -f base.dump base` (и zstd, и lz4 в pg_dump — **с PostgreSQL 16**; в 15 и старше — только gzip: `-Z 0..9`; по умолчанию gzip). Параллельный дамп — только формат каталога: `pg_dump -Fd -j 4 -f dir base`. Tar-формат pg_dump сжатие не поддерживает.
5. **Проверка дампа без восстановления:** `pg_restore -l base.dump >/dev/null` (читает оглавление) плюс код возврата `pg_dump` (0 — успех). Единственная полноценная проверка — пробное восстановление.
6. **rsync:** `rsync -aH --delete --info=progress2 /src/ /dst/`. `-a` = `-rlptgoD` и **не** включает `-H` (жёсткие ссылки), `-A` (ACL), `-X` (xattr). Слеш в конце источника: `/src/` — копировать содержимое, `/src` — создать каталог `src` внутри приёмника.
7. **Всегда сначала `--dry-run` (`-n`)** при использовании `--delete`. Код возврата rsync 24 («исчезнувшие файлы») — обычно не ошибка, 23 — частичная передача.
8. **Инкрементальные «снимки» с жёсткими ссылками:** `rsync -aH --delete --link-dest=/backup/prev /src/ /backup/new/` — неизменённые файлы не копируются, а становятся жёсткими ссылками на предыдущую копию.
9. **Строгий режим bash:** первая строка `#!/usr/bin/env bash`, вторая `set -Eeuo pipefail`. `-e` — выход при ошибке, `-u` — ошибка при обращении к неустановленной переменной, `pipefail` — код конвейера = код последней упавшей команды, `-E` — ловушка ERR наследуется функциями и подоболочками.
10. **Всегда кавычки:** `"$var"`, `"$@"`, `"${arr[@]}"`. Без кавычек значение бьётся по пробелам и раскрывает `*`.
11. **Защита от параллельного запуска:** `exec 9>/run/lock/job.lock; flock -n 9 || exit 0` либо в crontab: `flock -n /run/lock/job.lock /usr/local/bin/job.sh`.
12. **Очистка старых файлов:** `find /backup/pg -maxdepth 1 -type f -name '*.dump' -mtime +14 -delete` (сначала запустить с `-print` вместо `-delete`). `-mtime +14` означает «возраст 15 суток и больше» (возраст считается в целых сутках, дробная часть отбрасывается).
13. **Ограничение времени:** `timeout 6h pg_dump …` — код 124 при срабатывании таймаута.
14. **Cron запускает команды в `/bin/sh` с урезанным `PATH` (на практике `/usr/bin:/bin`)**, без `~/.bashrc`; символ `%` в строке crontab означает перевод строки и должен экранироваться: `date +\%F`. В `/etc/cron.d/` имя файла не должно содержать точек.
15. **systemd timer** — альтернатива cron: журнал в journald, `Persistent=true` (догоняет пропущенный запуск), не запускает второй экземпляр, пока первый работает. Проверка выражения: `systemd-analyze calendar "Mon..Fri *-*-* 02:30"`.
16. **Пароли PostgreSQL — в `~/.pgpass`** (формат `host:port:db:user:password`, права `0600`, иначе файл игнорируется). Лучше всего — локальный запуск от пользователя `postgres` через сокет (peer-аутентификация, пароль не нужен вовсе).
17. **Шифрование бэкапа паролем:** `gpg --batch --pinentry-mode loopback --passphrase-file /etc/backup/gpg.pass -c --cipher-algo AES256 -o f.gpg f` (по умолчанию gpg использует AES-128). Для автоматизации без пароля на сервере — шифрование открытым ключом (`gpg -e -r` или `age -r`).
18. **Контрольные суммы:** `sha256sum файл > файл.sha256`; проверка: `sha256sum -c файл.sha256`.
19. **Ubuntu 26.04:** базовые утилиты (`date`, `dd`, `sort`, `sha256sum`, `split`, `timeout`, `df`, `du`…) — из **rust-coreutils (uutils)**, GNU остались только `cp`, `mv`, `rm`; GNU-версии доступны с префиксом `gnu` (`gnudate`, `gnudd`, `gnusort` — файлы пакета `gnu-coreutils`). `/tmp` — tmpfs (в ОЗУ): дампы туда не писать. `sudo` — это `sudo-rs`.
20. **Сервис сервера 1С** (8.3.21+): `systemctl stop|start srv1cv8-8.3.XX.YYYY@default.service`; данные кластера — `/home/usr1cv8/.1cv8/1C/1cv8/`, сеансовые данные — каталоги `reg_1541/snccntx*` (чистить только при остановленном сервере — практика сообщества).

### Особенности Ubuntu 26.04, влияющие на скрипты (официальные release notes)

- **rust-coreutils вместо GNU coreutils.** Canonical прямо пишет, что утилиты «not fully compatible yet», поэтому GNU-версии сохранены и вызываются с префиксом `gnu`: `gnuls`, `gnudate`, `gnudd`, `gnusort`, `gnustat`, `gnudu`, `gnudf`, `gnusplit`, `gnutimeout`, `gnusha256sum` и т. д. (наличие этих файлов в `/usr/bin` пакета `gnu-coreutils` для resolute проверено по packages.ubuntu.com; в release notes приведён только пример `gnuls`). `cp`, `mv`, `rm` в 26.04 остаются GNU («because of unresolved bugs»). Какие именно ключи отдельных утилит ведут себя иначе, release notes не перечисляют (⚠ конкретного списка несовместимостей нет) — скрипты, использующие сложные выражения `date -d`, редкие ключи `sort`/`stat`/`du`/`dd`, **обязательно тестировать на 26.04**.
- Переключить всю систему на GNU coreutils: `sudo apt install coreutils-from-gnu coreutils-from-uutils- --allow-remove-essential` (обратно: `sudo apt install coreutils-from-uutils coreutils-from-gnu- --allow-remove-essential`).
- В rust-coreutils 0.8.0 (версия на момент выпуска 26.04) были серьёзные дефекты (например, LP #2158615: `install` портил файлы на eCryptfs; статус Fix Released с 25.08.2026). В `resolute-updates` лежит уже 0.10.0 — держите систему обновлённой (`apt policy rust-coreutils`).
- **Время:** в новых установках 26.04 демон времени по умолчанию — **chrony** (вместо `systemd-timesyncd`); `apt-key` удалён. На скрипты бэкапа это не влияет, но влияет на проверки вида `systemctl is-active systemd-timesyncd`.
- **`/tmp` — tmpfs** (файлы в ОЗУ/свопе, пропадают при перезагрузке). Временные файлы большого размера (дампы, архивы) создавать в каталоге на диске: `mktemp -p /backup/tmp`.
- **`sudo` — это `sudo-rs`** (классический доступен как `sudo.ws`). Экзотические опции sudoers в скриптах проверять.
- `tar`, `gzip`, `zstd`, `xz`, `rsync`, `bash`, `curl` — отдельные пакеты, замена coreutils их не затрагивает.
- systemd 259: по release notes 26.04 — последний выпуск Ubuntu с поддержкой совместимости со скриптами System V init (старые init-скрипты переводить на юниты); поддержка cgroup v1 удалена.

## 2. tar — упаковка каталогов

`tar` (GNU tar) склеивает файлы в один поток, сохраняя права, владельцев, времена, ссылки. Сжатие — внешним компрессором (через ключ или конвейер).

### 2.1. Режимы и основные ключи

| Ключ | Значение |
|---|---|
| `-c` / `-x` / `-t` | создать / извлечь / показать оглавление |
| `-r`, `-u` | дописать файлы / дописать только более новые (не работает со сжатыми архивами) |
| `-d` (`--diff`) | сравнить архив с файловой системой |
| `-f ФАЙЛ` | имя архива; `-f -` — stdin/stdout |
| `-v` | подробно (`-vv` — ещё подробнее) |
| `-C КАТАЛОГ` | перейти в каталог **перед** обработкой последующих аргументов (порядок важен) |
| `-z` / `-j` / `-J` / `--zstd` | сжатие gzip / bzip2 / xz / zstd |
| `-a` (`--auto-compress`) | выбрать компрессор по расширению архива (`.tar.gz`, `.tgz`, `.tar.bz2`, `.tar.xz`, `.tar.zst`) |
| `-I 'КОМАНДА'` (`--use-compress-program`) | произвольный компрессор; команда обязана понимать `-d` для распаковки |
| `-p` (`--preserve-permissions`) | при извлечении выставлять права точно как в архиве (без учёта umask); для root включено по умолчанию |
| `--same-owner` | восстанавливать владельцев (по умолчанию для root) |
| `--numeric-owner` | хранить/восстанавливать числовые UID/GID, не сопоставляя имена |
| `--acls`, `--xattrs` | сохранять POSIX ACL и расширенные атрибуты |
| `--exclude='ШАБЛОН'`, `-X ФАЙЛ` | исключения (glob); ставить **до** списка путей |
| `--exclude-caches`, `--exclude-vcs` | пропустить каталоги с `CACHEDIR.TAG` / служебные каталоги VCS |
| `--one-file-system` | не выходить за пределы файловой системы (не заходить в `/proc`, смонтированные тома) |
| `-P` (`--absolute-names`) | не отрезать ведущий `/` (по умолчанию отрезается — и это хорошо) |
| `--strip-components=N` | при извлечении отбросить N ведущих компонентов пути |
| `--wildcards` | при извлечении/просмотре трактовать аргументы как шаблоны |
| `-T ФАЙЛ` (`--files-from`), `--null` | список файлов из файла; `--null` — разделитель NUL (для `find -print0`) |
| `-O` (`--to-stdout`) | извлечь содержимое файла в stdout |
| `-g ФАЙЛ` (`--listed-incremental`), `--level=0` | инкрементальные архивы (см. 2.4) |
| `--remove-files` | удалить исходные файлы после добавления в архив |
| `-S` (`--sparse`) | эффективно хранить разрежённые файлы |
| `-W` (`--verify`) | проверить архив после записи (несовместимо со сжатием) |
| `--totals`, `--checkpoint=N` | итоговая статистика / индикатор прогресса |
| `--warning=no-file-changed` | подавить сообщение «file changed as we read it» |

**Коды возврата tar:** `0` — успех; `1` — «some files differ»: при создании это значит, что файлы менялись во время чтения (архив создан, но может быть несогласованным); `2` — фатальная ошибка. Если упал компрессор, tar возвращает его код.

### 2.2. Создание

```bash
# каталог /etc -> архив с zstd; -C / чтобы в архиве были относительные пути "etc/..."
tar --zstd -cpf /backup/etc_$(date +%F).tar.zst -C / etc

# gzip (совместимо со всем на свете)
tar -czpf /backup/home_usr1cv8.tar.gz -C /home usr1cv8

# многопоточное сжатие zstd с выбором уровня
tar -I 'zstd -T0 -6' -cpf /backup/data.tar.zst -C /srv data
# то же через конвейер (удобно добавить шифрование или подсчёт суммы)
tar -cpf - -C /srv data | zstd -T0 -6 -o /backup/data.tar.zst

# многопоточный gzip через pigz
tar -I pigz -cpf /backup/data.tar.gz -C /srv data

# исключения и «не выходить за пределы ФС» (каталог с самим архивом исключён, чтобы tar не упаковывал свой же результат)
tar --zstd -cpf /backup/root.tar.zst --one-file-system \
    --exclude='./backup/*' --exclude='./var/cache/*' --exclude='./tmp/*' --exclude='*.log' -C / .

# с ACL и xattr (например, если используются ACL на каталогах обмена)
tar --zstd --acls --xattrs -cpf /backup/share.tar.zst -C /srv share

# список файлов от find (только изменённые за сутки), безопасно для любых имён
find /srv/data -type f -mtime -1 -print0 | tar --null -T - --zstd -cpf /backup/changed.tar.zst
```

Пояснения:
- Пишите `-f` **последним** в связке коротких ключей (`-cpf файл`): всё после `f` считается именем архива.
- `-C / etc` предпочтительнее, чем `/etc`: путь в архиве сразу относительный, нет предупреждения «Removing leading `/' from member names».
- Архив **не кладите внутрь архивируемого каталога** (либо исключайте его `--exclude`), иначе tar попытается упаковать сам себя.

### 2.3. Просмотр, извлечение, проверка

```bash
tar -tvf /backup/etc_2026-10-10.tar.zst            # оглавление (компрессор определяется сам)
tar -tf  archive.tar.gz | head                     # только имена

tar -xpf archive.tar.zst -C /restore               # распаковать всё в /restore
tar -xpf archive.tar.zst -C /restore etc/fstab     # один файл (путь — как в оглавлении)
tar -xpf archive.tar.zst -C /restore --wildcards 'etc/postgresql/*'
tar -xpf archive.tar.gz  -C /opt/app --strip-components=1   # убрать верхний каталог
tar -xOf archive.tar.zst etc/hosts                 # вывести файл в stdout

zstd -dc archive.tar.zst | tar -xpf - -C /restore  # из конвейера: компрессор указывать явно
tar --zstd -xpf - -C /restore < archive.tar.zst    # то же

tar -df archive.tar -C /                           # сравнить архив с ФС
zstd -t archive.tar.zst && tar -tf archive.tar.zst >/dev/null && echo OK   # проверка целостности

# копирование дерева на другой сервер с сохранением прав
tar -cpf - -C /srv data | ssh backup@nas 'tar -xpf - -C /srv/restore'
```

- При восстановлении **на другую машину** UID/GID пользователей (`usr1cv8`, `postgres`) могут отличаться. Тогда либо создайте пользователей с теми же ID заранее, либо после распаковки `chown -R`. `--numeric-owner` заставляет tar не сопоставлять имена.
- Распаковка от обычного пользователя не восстанавливает владельцев — для системных бэкапов распаковывать от root.

### 2.4. Инкрементальные архивы (`--listed-incremental`)

GNU tar хранит в отдельном **файле-снимке** (`.snar`) метаданные о том, что уже заархивировано. Если файла-снимка нет — создаётся архив уровня 0 (полный); если есть — в архив попадает только изменённое/добавленное, а снимок **перезаписывается**.

```bash
# Воскресенье: полный архив (уровень 0). --level=0 обнуляет снимок, даже если он существует
tar --zstd -cpf /backup/data_full.tar.zst \
    --listed-incremental=/backup/data.snar --level=0 -C /srv data

# Пн..Сб, вариант А — «инкременты» (каждый относительно предыдущего): снимок обновляется
tar --zstd -cpf /backup/data_inc_$(date +%F).tar.zst \
    --listed-incremental=/backup/data.snar -C /srv data

# вариант Б — «дифференциальные» (каждый относительно полного): работаем с КОПИЕЙ снимка уровня 0
cp /backup/data.snar /backup/data.snar-1
tar --zstd -cpf /backup/data_diff_$(date +%F).tar.zst \
    --listed-incremental=/backup/data.snar-1 -C /srv data

# Восстановление: строго по порядку, полный, затем инкременты; снимок не нужен -> /dev/null
tar --zstd -xpf /backup/data_full.tar.zst            --listed-incremental=/dev/null -C /restore
tar --zstd -xpf /backup/data_inc_2026-10-06.tar.zst  --listed-incremental=/dev/null -C /restore

# посмотреть содержимое инкрементального архива (Y — файл в архиве, N — нет, D — каталог)
tar --list --incremental --verbose --verbose --file /backup/data_inc_2026-10-06.tar.zst
```

Важно (руководство GNU tar):
- при извлечении в инкрементальном режиме tar **удаляет** файлы, которых не было в каталоге на момент создания архива, — распаковывать только в предназначенный для восстановления каталог;
- надёжность зависит от меток времени: перевод часов назад ломает логику;
- снимок содержит номера устройств; на NFS и LVM-снапшотах они нестабильны — использовать `--no-check-device`;
- формат — расширение GNU, другие реализации tar такие архивы могут не прочитать.

Для бэкапов **баз данных** инкрементальный tar неприменим (дамп каждый раз новый файл; каталог данных PostgreSQL копировать tar/rsync «на живую» нельзя — см. раздел 5.6).

### 2.5. Что, кроме баз, стоит архивировать на сервере 1С + PostgreSQL (практика сообщества)

Дамп базы не содержит настроек сервера. Чтобы поднять сервер заново, нужны ещё несколько небольших каталогов — их удобно складывать tar-архивом рядом с дампами:

```bash
install -d -m 750 /backup/cfg
# 1. Конфигурация ОС и PostgreSQL (в пакетах Ubuntu/PGDG конфиги кластера лежат в /etc/postgresql/NN/main)
tar --zstd -cpf /backup/cfg/etc_$(date +%F).tar.zst -C / etc
# 2. Реестр кластера 1С и журналы регистрации; сеансовые данные (snccntx*) исключены.
#    Согласованную копию даёт только архивация при ОСТАНОВЛЕННОМ сервере 1С (иначе возможен код возврата 1 — «файл изменился»)
tar --zstd -cpf /backup/cfg/1c-cluster_$(date +%F).tar.zst --exclude='snccntx*' -C /home/usr1cv8/.1cv8/1C 1cv8
# 3. Файлы программных лицензий 1С (*.lic)
tar --zstd -cpf /backup/cfg/1c-licenses_$(date +%F).tar.zst -C /var/1C licenses
```

- У Postgres Pro `postgresql.conf` и `pg_hba.conf` лежат в каталоге данных (`/var/lib/pgpro/std-NN/data/`), а не в `/etc` — их нужно копировать отдельно (`cp -a` двух-трёх файлов; сам каталог данных tar'ом «на живую» не архивируют).
- Каталог лицензий `/var/1C/licenses` и каталог кластера `/home/usr1cv8/.1cv8/1C/1cv8` — типовые пути для Linux по материалам сообщества (каталоги `/var/1C/licenses` и `/home/usr1cv8/.1cv8/1C/1cv8` подтверждены документацией 8.3.27 (сверено 10.10.2026); остальное не подтверждено документацией ИТС: проверьте на своём сервере — `ls /var/1C/licenses`, значение `SRV1CV8_DATA` в `systemctl cat srv1cv8-…@default`). Программная лицензия привязана к оборудованию: на другом сервере файл `*.lic` из архива не заработает без повторной активации, но при восстановлении того же сервера он нужен.
- Журнал регистрации (`1Cv8Log`) может занимать десятки гигабайт — оцените размер (`du -sh /home/usr1cv8/.1cv8/1C/1cv8/reg_1541/*/1Cv8Log`) и при необходимости исключите его (`--exclude='1Cv8Log'`) либо копируйте rsync'ом (раздел 5.3, пример 7).

## 3. Компрессоры

### 3.1. gzip и pigz

`gzip` — формат .gz, однопоточный, есть везде. `pigz` (пакет `pigz`) — параллельная реализация того же формата: файлы взаимозаменяемы.

| Ключ | gzip | pigz |
|---|---|---|
| уровень | `-1`…`-9`, по умолчанию `-6` | `-0`…`-9`, `-11` (zopfli, очень медленно), по умолчанию `-6` |
| потоки | нет | `-p N`, по умолчанию — число ядер |
| оставить исходник | `-k` | `-k` |
| в stdout | `-c` | `-c` |
| распаковать | `-d` (`gunzip`, `zcat`) | `-d` (`unpigz`) |
| проверить | `-t` | `-t` |
| сведения | `-l` | `-l` |
| дружественность к rsync | `--rsyncable` | `-R` (`--rsyncable`) |

```bash
gzip -k -9 big.sql                 # -> big.sql.gz, исходник сохранён (без -k удаляется!)
pigz -p 8 -6 big.sql               # 8 потоков
pg_dump -Fp base | pigz > base.sql.gz
pigz -dc base.sql.gz | psql -X base        # распаковка в конвейер
zcat file.gz | head ; zgrep ERROR app.log.gz ; zless file.gz
gzip -t file.gz && echo OK
```

Распаковка у pigz **не** параллельна (основной поток распаковывает, ещё три занимаются чтением, записью и контрольной суммой), поэтому выигрыш — только при сжатии.

### 3.2. bzip2

Формат .bz2, сжимает лучше gzip, но в разы медленнее и при сжатии, и при распаковке. Сегодня практически вытеснен zstd и xz. Ключи аналогичны gzip: `-k`, `-c`, `-d` (`bunzip2`, `bzcat`), `-t`, `-1`…`-9` (размер блока 100–900 КБ, по умолчанию `-9`). Параллельные реализации — `pbzip2`, `lbzip2` (отдельные пакеты). Использовать только для совместимости со старыми архивами.

### 3.3. xz

Формат .xz (LZMA2): максимальная степень сжатия, очень медленное сжатие, средняя по скорости распаковка.

- Уровни `-0`…`-9`, по умолчанию `-6`; `-e` (extreme) — ещё медленнее. Память: `-6` — 94 МиБ на сжатие / 9 МиБ на распаковку; `-9` — 674 / 65 МиБ (на поток).
- `-T N` — потоки, `-T0` — по числу ядер. В Ubuntu 22.04/24.04 (xz 5.2/5.4) по умолчанию один поток; начиная с xz 5.6.0 (Ubuntu 26.04 — 5.8.3) многопоточный режим включён по умолчанию — подтверждено файлом NEWS xz 5.6.0: «Multithreaded mode is now the default… at the cost of increased memory usage and slightly worse compression ratio». То же в man xz 5.8.3 (resolute): «The default value for threads is 0. In xz 5.4.x and older the default is 1». Следствие для 26.04: `xz` без ключей использует до всех ядер (число потоков может быть урезано системным «мягким» лимитом памяти — см. `xz --info-memory`) и требует памяти «на поток» × число потоков; на рабочем сервере 1С ограничивайте явно (`-T 2`, `nice`).
- Многопоточная распаковка — с xz 5.4 и только для файлов, сжатых в многопоточном режиме (несколько блоков).
- `-k` оставить исходник, `-c` в stdout, `-d` распаковать (`unxz`, `xzcat`), `-t` проверить, `-l` сведения, `--memlimit=` ограничить память.
- Коды возврата: 0 — успех, 1 — ошибка, 2 — предупреждение.

```bash
xz -T0 -6 -k big.sql               # -> big.sql.xz
xz -dc big.sql.xz | psql -X base
tar -I 'xz -T0 -6' -cpf arch.tar.xz dir
```

Где уместен: долговременный архив, который пишется один раз и почти никогда не читается, и критичен размер. Для ежедневных дампов — слишком медленно.

### 3.4. zstd — основной выбор

Формат .zst (Zstandard). Сочетает скорость уровня lz4/gzip-1 со сжатием уровня gzip-9…xz в зависимости от уровня; распаковка очень быстрая и не зависит от уровня сжатия.

| Ключ | Значение |
|---|---|
| `-1`…`-19` | уровень; по умолчанию `-3` |
| `--ultra -20`…`-22` | сверхвысокие уровни (много памяти) |
| `--fast[=N]` | сверхбыстрые «отрицательные» уровни |
| `-T N`, `-T0` | потоки; `0` — по числу **физических** ядер. Умолчание зависит от версии: zstd ≤ 1.5.6 (Ubuntu 22.04/24.04) — 1 поток; **zstd 1.5.7 (Ubuntu 26.04)** — несколько потоков в зависимости от числа ядер, но не более 4 (release notes v1.5.7: 4 ядра с HT → 2 потока, 8 ядер с HT → 4; man-страница 1.5.7 при этом по-прежнему пишет «default: 1») |
| `--max` | (zstd ≥ 1.5.7) максимальное сжатие — медленнее и прожорливее по памяти, чем `--ultra -22`; для регулярных бэкапов не нужно |
| `--long[=N]` | поиск дальних совпадений, окно 2^N байт (по умолчанию N=27, т. е. 128 МиБ) — заметно улучшает сжатие больших дампов с повторяющимися данными |
| `--rsyncable` | периодически сбрасывать состояние, чтобы сжатый файл хорошо передавался rsync-дельтой |
| `--adapt[=min=N,max=M]` | подстраивать уровень под скорость ввода-вывода (для сетевых конвейеров) |
| `-c` | в stdout; `-o ФАЙЛ` — имя результата |
| `-d` | распаковать (`unzstd`, `zstdcat` = `zstd -dc`) |
| `-k` / `--rm` | оставить (по умолчанию) / удалить исходник после успеха |
| `-t` | проверить целостность; `-l` — сведения о файле |
| `-q` / `-v` | тише / подробнее |
| `-C` / `--no-check` | контрольная сумма содержимого (включена по умолчанию) |
| `-B N` | размер задания при многопоточности |
| `-b N -e M` | встроенный бенчмарк уровней N…M на вашем файле |

Переменные окружения: `ZSTD_CLEVEL` (уровень по умолчанию, 1–19), `ZSTD_NBTHREADS` (потоки по умолчанию). `zstdmt` — то же, что `zstd -T0`. Из-за разного умолчания по потокам в 1.5.5 и 1.5.7 в скриптах всегда указывайте `-T N` явно — тогда нагрузка на сервер одинакова на любой версии Ubuntu.

```bash
zstd -T0 -6 base.dump                      # -> base.dump.zst, исходник остаётся
zstd -T0 -10 --long --rm big.sql           # сильнее, окно 128 МиБ, удалить исходник
zstd -dc base.sql.zst | psql -X base       # распаковка в конвейер
zstd -d base.dump.zst -o /restore/base.dump
zstd -t /backup/*.zst                      # проверка всех архивов
zstd -l base.dump.zst                      # размеры, степень сжатия, тип контрольной суммы
zstd -b1 -e12 -T0 sample.sql               # померить уровни 1..12 на своих данных
pg_dump -Fc -Z0 base | zstd -T0 -6 -o /backup/base.dump.zst   # несжатый custom-дамп + внешний многопоточный zstd
```

Если при сжатии использовался `--long` с окном больше 27 (например, `--long=30`), при распаковке нужно указать тот же `--long=30` (или `--memory=`); для значения по умолчанию (27) ничего указывать не надо.

### 3.5. zip / unzip

Формат .zip — для обмена с Windows. Пакеты `zip`, `unzip`.

```bash
zip -r -9 arch.zip dir/ -x '*.log'         # рекурсивно, макс. сжатие, с исключением
zip -r -s 2g arch.zip dir/                 # многотомный архив по 2 ГБ
zip -T arch.zip                            # проверка
unzip -l arch.zip                          # оглавление
unzip -t arch.zip                          # тест
unzip -q arch.zip -d /dst                  # распаковать тихо в каталог
unzip -o arch.zip -d /dst                  # перезаписывать без вопросов
unzip -O cp866 win.zip -d /dst             # архив из Windows с кириллицей в именах; -O CHARSET — кодировка имён для архивов DOS/Windows
                                           # (ключ есть в unzip 6.0 из Debian/Ubuntu — man unzip, noble; в «чистом» Info-ZIP его нет); -I CHARSET — то же для UNIX-архивов
```

- Уровни `-0`…`-9`, по умолчанию `-6`; `-j` — без путей; `-m` — переместить в архив; `-y` — хранить симлинки как ссылки; `-X` — не сохранять uid/gid и времена.
- Zip64 (файлы и архивы больше 4 ГБ) включается автоматически; для распаковки нужен unzip 6.0+.
- Шифрование `zip -e` (а тем более `-P пароль` — пароль виден в `ps`) — **слабое** («relatively weak standard encryption», man zip); для защиты данных использовать gpg/age/7z.
- Коды возврата zip: 0 — успех, 12 — «нечего делать», 18 — не удалось открыть файл и др.

### 3.6. 7z

Пакет: `7zip` (Ubuntu 24.04/26.04) или `p7zip-full` (22.04). Исполняемые файлы пакета `7zip`: `7z` (полный, с плагинами), `7zz` (полный, одним бинарником), `7za` (основные форматы), `7zr` (только 7z/lzma/xz).

```bash
7z a -t7z -mx=5 -mmt=on arch.7z dir/       # создать (уровень 5, многопоточно)
7z a -p -mhe=on secret.7z dir/             # AES-256, пароль спросит; -mhe=on шифрует и имена файлов
7z a -v2g arch.7z bigfile                  # тома по 2 ГБ: arch.7z.001, .002 ...
7z l arch.7z ; 7z t arch.7z                # оглавление ; тест
7z x arch.7z -o/dst -y                     # распаковать с путями (между -o и путём пробела НЕТ)
7z e arch.7z -o/dst                        # распаковать без путей
tar -cpf - -C /srv data | 7z a -si data.tar.7z      # сохранить права/владельцев: tar внутри 7z
7z x -so data.tar.7z | tar -xpf - -C /restore
```

**Формат 7z не хранит владельца и группу файлов** — для резервных копий Linux-каталогов использовать tar (при необходимости tar внутри 7z, как в примере). Основное применение 7z на сервере — распаковка того, что прислали с Windows, и создание архивов для Windows-пользователей.

## 4. Что выбирать для дампов БД

### 4.1. Ориентиры по скорости и сжатию

Официальный бенчмарк zstd (корпус Silesia, lzbench, Core i7-9700K, один поток) — подтверждённые цифры:

| Компрессор | Степень сжатия | Сжатие, МБ/с | Распаковка, МБ/с |
|---|---|---|---|
| zstd 1.5.7 `-1` | 2.896 | 510 | 1550 |
| zlib 1.3.1 `-1` (≈ gzip -1) | 2.743 | 105 | 390 |
| zstd `--fast=1` | 2.439 | 545 | 1850 |
| lz4 1.10.0 | 2.101 | 675 | 3850 |

Качественное сравнение для SQL-дампов (порядки величин, **мерить на своих данных** командой `zstd -b`; цифры в столбцах «скорость» — ориентиры, ⚠ не из первоисточника):

| Инструмент | Сжатие | Скорость сжатия (1 поток) | Распаковка | Многопоточность | Вывод |
|---|---|---|---|---|---|
| lz4 | слабое | очень высокая | самая быстрая | нет (и не нужна) | когда упор в CPU, а диск/сеть быстрые |
| gzip -6 | среднее | низкая (десятки МБ/с) | средняя | нет | совместимость; умолчание pg_dump |
| pigz -6 | как gzip | ×число ядер | как gzip | сжатие | замена gzip в конвейерах |
| zstd -3 | ≈ gzip -6…-9 | высокая (сотни МБ/с) | очень быстрая | `-T0` | **ежедневные дампы** |
| zstd -10…-15 `--long` | заметно лучше gzip -9 | средняя | очень быстрая | `-T0` | недельные/месячные копии |
| zstd -19 | близко к xz | низкая | очень быстрая | `-T0` | архив на долгое хранение |
| bzip2 -9 | лучше gzip | очень низкая | низкая | pbzip2 | не использовать |
| xz -6 | максимальное | очень низкая | средняя | `-T0` | долговременный архив, когда важен каждый ГБ |

Особенность баз 1С: значительная часть объёма — двоичные данные (`bytea`: хранилища значений, конфигурация, присоединённые файлы), часто уже сжатые; они почти не сжимаются. Текстовые и числовые таблицы (регистры, документы) сжимаются хорошо. Итоговая степень сжатия сильно зависит от конкретной базы — оценивать по факту (`pg_restore -l` + сравнение `pg_database_size()` с размером дампа). ⚠ не подтверждено: и абзац о сжимаемости баз 1С, и качественная таблица выше — практические наблюдения сообщества; опубликованных сравнительных замеров компрессоров именно на дампах PostgreSQL/1С в первоисточниках не найдено. Решение об уровне и компрессоре принимайте по собственному замеру: `pg_dump -Fc -Z0 база | head -c 2G > /backup/tmp/sample.bin; zstd -b1 -e12 -T4 /backup/tmp/sample.bin` (pg_dump при этом завершится сообщением о разорванном конвейере — для разового образца это ожидаемо; образец потом удалить).

### 4.2. Сжатие средствами pg_dump (официальная документация PostgreSQL 18)

- `-Fc` (custom) и `-Fd` (directory) сжимаются по умолчанию **gzip** «на умеренном уровне»; `-Fp` (plain) по умолчанию не сжимается; `-Ft` (tar) сжатие не поддерживает вообще.
- Синтаксис: `-Z уровень` или `-Z метод[:детали]`, методы `gzip`, `lz4`, `zstd`, `none`. Примеры: `-Z 9`, `-Z zstd`, `-Z zstd:9`, `-Z zstd:level=9,long`, `-Z lz4`, `-Z 0`/`-Z none`. **И lz4, и zstd появились в pg_dump одновременно — в PostgreSQL 16** (release notes 16: «Add LZ4 and Zstandard compression to pg_dump»; там же — режим `long` и единый синтаксис `--compress=метод:уровень`); работают только если сборка скомпилирована с соответствующей библиотекой. В PostgreSQL 15 и старше `-Z` принимает только число 0–9 (gzip). Не путать: в PostgreSQL 15 lz4/zstd появились для `pg_basebackup` и сжатия WAL, но не для pg_dump.
- `-j N` (параллельный дамп) — **только** с `-Fd`; открывает N+1 соединений. `pg_restore -j N` работает с `-Fc` и `-Fd`, но только из обычного файла/каталога (не из конвейера) и несовместим с `--single-transaction`.
- Сжатие в `-Fc` — в одном потоке вместе с выгрузкой таблицы. Чтобы задействовать все ядра: либо `-Fd -j N` (параллельно по таблицам), либо `-Fc -Z0 | zstd -T0` (внешнее многопоточное сжатие; но тогда перед `pg_restore -j` архив придётся распаковать в файл).

```bash
pg_dump -Fc -Z zstd:6 -f /backup/buh.dump buh                 # один файл, zstd (PG 16+)
pg_dump -Fc -f /backup/buh.dump buh                           # один файл, gzip по умолчанию (любая версия)
pg_dump -Fd -j 4 -Z zstd:6 -f /backup/buh.dir buh             # каталог, 4 потока (каталог не должен существовать)
pg_dump -Fc -Z0 buh | zstd -T0 -6 -o /backup/buh.dump.zst     # внешний многопоточный zstd

pg_restore -l /backup/buh.dump | head                         # оглавление = быстрая проверка читаемости
createdb -T template0 buh_test
pg_restore -j 4 -d buh_test /backup/buh.dump                  # параллельное восстановление
zstd -dc /backup/buh.dump.zst | pg_restore -d buh_test        # из конвейера (без -j)
```

Официальная оговорка документации PostgreSQL: pg_dump «generally not the right choice for taking regular backups of production databases» (кроме простых случаев). Для больших рабочих баз основной бэкап — физический (`pg_basebackup` + архив WAL, `pg_probackup`), а логический дамп — дополнительная переносимая копия. Для небольших и средних баз 1С ночной `pg_dump -Fc` остаётся распространённой практикой сообщества.

## 5. rsync — синхронизация каталогов

`rsync` копирует только отличающиеся файлы (по умолчанию сравнивает размер и время изменения), по сети передаёт только изменившиеся блоки, умеет удалять лишнее, сохранять права и жёсткие ссылки. По сети работает поверх SSH (на обеих сторонах должен быть установлен rsync).

### 5.1. Синтаксис и значение слеша

```text
rsync [ключи] ИСТОЧНИК... ПРИЁМНИК
rsync [ключи] /локальный/путь/  user@host:/удалённый/путь/     # push по SSH
rsync [ключи] user@host:/удалённый/путь/  /локальный/путь/     # pull по SSH
```

| Команда | Результат |
|---|---|
| `rsync -a /backup/pg/ /mnt/nas/pg/` | **содержимое** `/backup/pg` оказывается в `/mnt/nas/pg/` |
| `rsync -a /backup/pg /mnt/nas/pg/` | создаётся `/mnt/nas/pg/pg/…` (каталог целиком) |
| `rsync -a /backup/pg /mnt/nas/` | создаётся `/mnt/nas/pg/…` — эквивалент первой строки |

Правило из man rsync: завершающий слеш у **источника** означает «копировать содержимое каталога, не создавая дополнительный уровень в приёмнике». Слеш у приёмника на результат не влияет (но привычка всегда писать его у обоих путей избавляет от ошибок). Особенно опасна ошибка со слешем в сочетании с `--delete`.

### 5.2. Ключи

| Ключ | Значение |
|---|---|
| `-a` (`--archive`) | = `-rlptgoD`: рекурсия, симлинки, права, времена, группа, владелец, устройства. **Не включает** `-H`, `-A`, `-X`, `-U`, `-N` |
| `-H` | сохранять жёсткие ссылки (обязательно при копировании снимков `--link-dest`) |
| `-A`, `-X` | ACL, расширенные атрибуты |
| `-S` (`--sparse`) | эффективно обрабатывать разрежённые файлы |
| `--numeric-ids` | не сопоставлять UID/GID по именам (для бэкапов на другой хост) |
| `-v`, `-h` | подробно; «человеческие» числа |
| `-P` | = `--partial --progress`: сохранять недокачанные файлы и показывать прогресс по файлу |
| `--info=progress2` | общий прогресс всей передачи (одна строка) |
| `--stats` | итоговая статистика |
| `-i` (`--itemize-changes`) | что именно меняется (строка из 11 символов `YXcstpoguax`: `>f` — файл передаётся, `.d` — каталог без изменений, `*deleting` — удаление) |
| `-n` (`--dry-run`) | пробный прогон без изменений; вместе с `-i` показывает план |
| `-z` | сжимать данные при передаче; `--compress-choice=zstd` (`--zc`), `--compress-level=N` (`--zl`). Для уже сжатых дампов и в локальной сети **не нужно** |
| `--delete` | удалять в приёмнике то, чего нет в источнике. Варианты момента: `--delete-before`, `--delete-during` (по умолчанию для rsync ≥ 3.0), `--delete-delay`, `--delete-after`; `--delete-excluded` — удалять и исключённое |
| `--max-delete=N` | не удалять больше N файлов (предохранитель; код возврата 25) |
| `--exclude='ШАБЛОН'`, `--exclude-from=ФАЙЛ`, `--include=` | фильтры; срабатывает первое совпавшее правило. Шаблон с ведущим `/` привязан к корню передачи; с завершающим `/` — только каталоги; `**` — любые символы, включая `/` |
| `-e 'ssh …'` | транспорт: `-e 'ssh -p 2222 -i /root/.ssh/backup_ed25519 -o BatchMode=yes'` |
| `--rsync-path='sudo rsync'` | запускать rsync на удалённой стороне через sudo |
| `--bwlimit=СКОРОСТЬ` | ограничение полосы; без суффикса — в единицах по 1024 байта/с (КиБ/с): `--bwlimit=20000` ≈ 20 МиБ/с; можно `--bwlimit=20m` |
| `--link-dest=КАТАЛОГ` | неизменённые файлы — жёсткие ссылки на файлы из КАТАЛОГА (см. 5.4). Относительный путь считается от каталога-приёмника |
| `-c` (`--checksum`) | сравнивать по контрольной сумме, а не по размеру/времени (медленно: читает все файлы с обеих сторон) |
| `--partial-dir=DIR` | складывать недокачанное в отдельный каталог |
| `--inplace` | писать прямо в файл назначения (без временной копии); небезопасно при обрыве и для открытых файлов |
| `--append-verify` | дозаписывать файлы, которые только растут |
| `-W` (`--whole-file`) | не использовать дельта-алгоритм (умолчание для локальных копий) |
| `--timeout=СЕК`, `--contimeout=СЕК` | таймаут ввода-вывода / подключения к демону |
| `--remove-source-files` | удалять у источника успешно переданные файлы (перенос) |
| `--mkpath` | создать недостающие компоненты пути приёмника (rsync ≥ 3.2.3) |
| `--backup --backup-dir=DIR` | заменяемые и удаляемые файлы не уничтожать, а переносить в DIR |
| `-x` (`--one-file-system`) | не пересекать границы файловых систем |
| `--chown=U:G`, `--chmod=…` | принудительно задать владельца/права в приёмнике |
| `--files-from=ФАЙЛ` | передать точный список файлов |
| `--max-size=`, `--min-size=` | фильтр по размеру |
| `--log-file=ФАЙЛ` | журнал операций |
| `--fsync` | fsync каждого записанного файла на приёмнике |

### 5.3. Примеры

```bash
# 1. Локальная копия дампов на другой диск, с удалением лишнего. Сначала — пробный прогон!
rsync -aH --delete -n -i /backup/pg/ /mnt/disk2/pg/
rsync -aH --delete --info=progress2 /backup/pg/ /mnt/disk2/pg/

# 2. На удалённый сервер по SSH (ключ без пароля, нестандартный порт, ограничение 20 МиБ/с)
rsync -aH --delete --bwlimit=20m --timeout=300 \
      -e 'ssh -p 2222 -i /root/.ssh/backup_ed25519 -o BatchMode=yes' \
      /backup/pg/ backup@nas.example.com:/srv/backup/srv1c/pg/

# 3. Забрать с удалённого сервера (pull) только дампы
rsync -av --include='*.dump' --include='*.sha256' --exclude='*' \
      backup@srv1c:/backup/pg/ /srv/backup/srv1c/pg/

# 4. Большой файл по ненадёжному каналу — с докачкой и прогрессом
rsync -P --partial-dir=.rsync-partial /backup/pg/buh_2026-10-10.dump backup@nas:/srv/backup/

# 5. Перенос (копировать и удалить у источника), затем убрать пустые каталоги
rsync -a --remove-source-files /backup/outbox/ /mnt/nas/inbox/ \
  && find /backup/outbox -mindepth 1 -type d -empty -delete

# 6. Исключения из файла
rsync -aH --delete --exclude-from=/etc/backup/rsync-exclude.txt /home/ /mnt/disk2/home/

# 7. Каталог данных кластера 1С (при ОСТАНОВЛЕННОМ сервере 1С)
rsync -aH --delete --exclude='snccntx*/' /home/usr1cv8/.1cv8/1C/1cv8/ /backup/1c-cluster/
```

Обработка кода возврата в скрипте (24 — файлы исчезли во время передачи — для «живых» каталогов нормально):

```bash
rc=0
rsync -aH --delete /src/ /dst/ || rc=$?
if (( rc != 0 && rc != 24 )); then
    echo "rsync завершился с кодом $rc" >&2
    exit "$rc"
fi
```

### 5.4. Инкрементальные снимки через `--link-dest`

Идея: каждый день создаётся новый каталог-снимок, который выглядит как полная копия, но неизменённые файлы в нём — жёсткие ссылки на файлы предыдущего снимка (место занимают только изменения). Любой снимок можно удалить независимо от остальных.

```bash
#!/usr/bin/env bash
# /usr/local/bin/snapshot_rsync.sh — ежедневные снимки каталога с жёсткими ссылками
set -Eeuo pipefail

SRC=/srv/1c-files/              # слеш в конце: содержимое каталога
DST=/mnt/disk2/snapshots        # здесь появляются каталоги ГГГГ-ММ-ДД
MOUNT=/mnt/disk2                # точка монтирования диска с копиями ('' — не проверять)
KEEP=14                         # сколько снимков хранить

# предохранитель: если диск не примонтирован, mkdir -p создал бы каталог на корневой ФС и копия ушла бы «не туда»
if [[ -n $MOUNT ]] && ! mountpoint -q "$MOUNT"; then
    echo "диск $MOUNT не смонтирован — снимок не создаётся" >&2
    exit 1
fi
if [[ ! -d $SRC ]]; then
    echo "источник $SRC не найден" >&2
    exit 1
fi

today=$(date +%F)
mkdir -p "$DST"
if [[ -e $DST/$today ]]; then
    echo "Снимок $DST/$today уже существует" >&2
    exit 0
fi

opts=(-aH --delete --numeric-ids --stats)
# самый свежий из существующих снимков (имена сортируются как даты)
prev=$(find "$DST" -mindepth 1 -maxdepth 1 -type d -name '20??-??-??' | sort | tail -n 1)
if [[ -n $prev ]]; then
    opts+=(--link-dest="$prev")
fi

rc=0
rsync "${opts[@]}" "$SRC" "$DST/$today.partial/" || rc=$?
if (( rc != 0 && rc != 24 )); then
    echo "rsync: код $rc, снимок не завершён" >&2
    exit "$rc"
fi
mv -- "$DST/$today.partial" "$DST/$today"

# ротация: удалить всё, кроме KEEP последних
mapfile -t snaps < <(find "$DST" -mindepth 1 -maxdepth 1 -type d -name '20??-??-??' | sort)
if (( ${#snaps[@]} > KEEP )); then
    for old in "${snaps[@]:0:${#snaps[@]}-KEEP}"; do
        rm -rf -- "$old"
    done
fi
```

Замечания:
- файлы должны совпадать по всем сохраняемым атрибутам (права, владелец, время), иначе rsync скопирует файл заново;
- `--link-dest` можно указать несколько раз (до 20 каталогов); в сочетании с `--ignore-times` ссылки не создаются;
- снимки и предыдущая копия должны лежать на **одной** файловой системе (жёсткие ссылки не пересекают границы ФС);
- для ежедневных дампов БД (каждый день новый файл с новым именем) `--link-dest` экономии не даёт — он полезен для деревьев файлов (обмены, присоединённые файлы на диске, файловые базы, конфигурация).

### 5.5. Коды возврата rsync

| Код | Значение |
|---|---|
| 0 | успех |
| 1 | ошибка синтаксиса/использования |
| 2 | несовместимость протоколов |
| 3 | ошибка выбора входных/выходных файлов или каталогов |
| 4 | запрошенное действие не поддерживается (например, ключ понимает клиент, но не сервер — разные версии rsync) |
| 5 | ошибка запуска клиент-серверного протокола |
| 6 | демон не смог дописать лог-файл |
| 10 | ошибка сокета |
| 11 | ошибка файлового ввода-вывода (часто — кончилось место) |
| 12 | ошибка потока данных протокола (часто — на удалённой стороне нет rsync или «мусор» от `.bashrc`) |
| 13 | ошибка диагностики программы |
| 14 | ошибка межпроцессного взаимодействия (IPC) |
| 20 | получен SIGUSR1 или SIGINT |
| 21 | ошибка `waitpid()` |
| 22 | не удалось выделить память под буферы |
| 23 | частичная передача из-за ошибки (нет прав, часть файлов не скопирована) |
| 24 | частичная передача: исходные файлы исчезли |
| 25 | сработал `--max-delete` |
| 30 | таймаут передачи данных |
| 35 | таймаут ожидания соединения с демоном |

Список кодов сверен с разделом EXIT VALUES man rsync (3.2.7, noble). Код 255 в этом списке отсутствует: на практике его возвращает `ssh` (не удалось подключиться, отказ в аутентификации), и rsync передаёт его дальше с сообщением «unexplained error (code 255)» — практика сообщества; смотреть нужно на ошибку ssh строкой выше.

### 5.6. Чего rsync'ом делать нельзя

- **Копировать каталог данных работающего PostgreSQL** (`/var/lib/postgresql/NN/main`, `/var/lib/pgpro/…/data`) как резервную копию: получится несогласованный набор файлов. Физический бэкап — только `pg_basebackup`/`pg_probackup` либо при остановленном сервере.
- Копировать файловую базу 1С (`1Cv8.1CD`) при работающих пользователях.
- Использовать `--delete`, не убедившись, что источник смонтирован и не пуст: пустой источник (например, не примонтировался диск) = удаление всего приёмника. Предохранители: проверка `mountpoint -q /mnt/disk2`, проверка наличия файла-маркера, `--max-delete=N`.

## 6. scp, sftp, rclone

### 6.1. scp и sftp

```bash
scp -P 2222 -i ~/.ssh/backup_ed25519 /backup/pg/buh.dump backup@nas:/srv/backup/     # файл на сервер
scp -r backup@nas:/srv/backup/pg /restore/                                           # каталог с сервера
scp -p -l 80000 big.dump backup@nas:/srv/backup/      # -p сохранить времена/права; -l лимит в Кбит/с
scp -J bastion.example.com file.txt user@internal:/tmp/                              # через jump-хост

sftp -P 2222 -i ~/.ssh/backup_ed25519 backup@nas                     # интерактивно: ls, cd, get, put, mkdir, rm, bye
sftp backup@nas:/srv/backup/pg/buh.dump /restore/                    # скачать одной командой
sftp -b /etc/backup/sftp-batch.txt -i ~/.ssh/backup_ed25519 backup@nas   # пакетный режим
```

Пример пакетного файла для `sftp -b` (команда с префиксом `-` не прерывает пакет при ошибке):

```text
cd /srv/backup/pg
-mkdir 2026-10
put /backup/pg/buh_2026-10-10.dump 2026-10/
ls -l 2026-10
bye
```

- Порт: у `scp` и `sftp` — заглавная `-P`, у `ssh` — строчная `-p`.
- Начиная с OpenSSH 9.0 `scp` работает **по протоколу SFTP** (Ubuntu 24.04/26.04); `-O` включает старый протокол SCP (нужен для серверов без SFTP). В Ubuntu 22.04 (OpenSSH 8.9p1 — версия подтверждена packages.ubuntu.com) по умолчанию ещё старый протокол scp/rcp: переключение на SFTP произошло именно в релизе 9.0 («This release switches scp(1) from using the legacy scp/rcp protocol to using the SFTP protocol by default»). Практическое отличие: в режиме SFTP шаблоны и пути на удалённой стороне не проходят через удалённую оболочку, поэтому конструкции вида `scp host:'$(cmd)' .` или экранирование пробелов «для двух оболочек» работают иначе, чем в 22.04.
- `scp` не умеет докачивать и синхронизировать — для бэкапов предпочтителен `rsync -P`. `sftp` уместен, когда на приёмнике разрешён только SFTP (хостинг, NAS, chroot-SFTP).

### 6.2. rclone — S3 и облака (кратко)

`rclone` — «rsync для облачных хранилищ»: S3-совместимые (AWS, MinIO, Ceph, Selectel и др.), Яндекс Диск (отдельный бэкенд), SFTP, WebDAV и десятки других.

Установка: `sudo apt install rclone` (в LTS версия заметно отстаёт: 22.04 — 1.53.3, 24.04 и 26.04 — 1.60.1, это выпуски 2020 и 2022 годов; часть ключей и провайдеров из текущей документации rclone.org в них отсутствует) либо свежий .deb с rclone.org. Настройка — мастером `rclone config`; конфигурация хранится в `~/.config/rclone/rclone.conf` (узнать путь: `rclone config file`; переопределить: `--config ФАЙЛ`). В файле лежат ключи доступа — права `600`.

```ini
# ~/.config/rclone/rclone.conf
[s3backup]
type = s3
provider = Other
access_key_id = ВАШ_КЛЮЧ
secret_access_key = ВАШ_СЕКРЕТ
endpoint = https://s3.example.com
region = ru-1
acl = private
```

```bash
rclone lsd s3backup:                                   # список бакетов
rclone ls s3backup:pg-backups/srv1c                    # список объектов
rclone copy /backup/pg s3backup:pg-backups/srv1c \
       --include '*.dump' --include '*.sha256' --max-age 36h \
       --transfers 4 --bwlimit 20M --log-file /var/log/rclone.log --log-level INFO
rclone sync /backup/pg s3backup:pg-backups/srv1c --dry-run     # sync УДАЛЯЕТ лишнее в приёмнике — сначала dry-run
rclone check /backup/pg s3backup:pg-backups/srv1c              # сверка размеров/хэшей
rclone delete s3backup:pg-backups/srv1c --min-age 60d          # удалить объекты старше 60 дней
pg_dump -Fc -Z zstd:6 buh | rclone rcat s3backup:pg-backups/srv1c/buh_$(date +%F).dump   # потоком, без локального файла
```

- `copy` — только добавляет/обновляет; `sync` — делает приёмник идентичным источнику (удаляет лишнее); `move` — переносит.
- `--bwlimit 10M` — лимит (по умолчанию в КиБ/с; суффиксы B/K/M/G; можно расписание `"08:00,512k;19:00,off"`); `--checkers` по умолчанию 8; `--transfers` по умолчанию 4 (rclone.org/docs: «The default is to run 4 file transfers in parallel»); `-n`/`--dry-run`; `-P` — прогресс; `--immutable` — запрет изменять существующие объекты; `--backup-dir` — складывать заменяемое/удаляемое в отдельный путь.
- Память при многокомпонентной загрузке S3 ≈ `--transfers` × `--s3-upload-concurrency` × `--s3-chunk-size`.
- Шифрование на стороне клиента — бэкенд `crypt` поверх основного (документация: rclone.org/crypt; в этой статье не разбирается); проще шифровать файл заранее (`gpg`/`age`, раздел 8).
- Ротацию в S3 надёжнее делать правилами жизненного цикла (lifecycle) самого хранилища, а версионирование/Object Lock защищают от удаления копий со скомпрометированного сервера.

## 7. dd, split/cat, контрольные суммы

### 7.1. dd — побайтовое копирование

| Операнд | Значение |
|---|---|
| `if=`, `of=` | входной/выходной файл или устройство (по умолчанию stdin/stdout) |
| `bs=N` | размер блока чтения и записи (по умолчанию 512 байт — медленно; ставьте `bs=1M`…`4M`) |
| `count=N` | скопировать N блоков; `skip=N` — пропустить N блоков на входе; `seek=N` — на выходе |
| `status=progress` | периодически показывать прогресс (`none` — молчать, `noxfer` — без итоговой строки) |
| `conv=fsync` | в конце физически сбросить данные и метаданные на диск (`fdatasync` — только данные) |
| `conv=notrunc` | не усекать выходной файл; `conv=noerror,sync` — продолжать при ошибках чтения, дополняя блок нулями; `conv=sparse` — не писать нулевые блоки |
| `oflag=direct` | прямой ввод-вывод в обход кеша страниц; `oflag=dsync` — синхронная запись каждого блока; `iflag=fullblock` — дочитывать блоки целиком (обязательно при чтении из конвейера с `count=`) |

Суффиксы размеров: `K`=1024, `M`=1024², `G`=1024³; `kB`=1000, `MB`=1000², `GB`=1000³.

```bash
lsblk -o NAME,SIZE,TYPE,MOUNTPOINT,MODEL           # ПЕРЕД dd: убедиться, какое устройство какое
dd if=ubuntu-26.04-live-server-amd64.iso of=/dev/sdX bs=4M status=progress conv=fsync   # образ на флешку

dd if=/dev/sdb bs=4M status=progress | zstd -T0 -3 -o /backup/sdb.img.zst               # образ диска со сжатием
zstd -dc /backup/sdb.img.zst | dd of=/dev/sdb bs=4M status=progress conv=fsync          # восстановление образа

# грубая оценка скорости последовательной записи/чтения
dd if=/dev/zero of=/backup/dd.test bs=1M count=4096 conv=fdatasync status=progress
dd if=/backup/dd.test of=/dev/null bs=1M status=progress ; rm /backup/dd.test
# «цена fsync» маленькими блоками — показатель пригодности диска под WAL
dd if=/dev/zero of=/var/lib/postgresql/dd.test bs=8k count=10000 oflag=dsync ; rm /var/lib/postgresql/dd.test

dd if=/dev/sda of=/backup/sda-mbr.bin bs=512 count=1        # первый сектор
kill -USR1 "$(pgrep -x dd)"                                 # попросить работающий dd вывести статистику
```

Опасность: перепутанный `of=` мгновенно уничтожает данные без подтверждения. `dd` — не средство резервного копирования работающей БД (образ «живого» диска несогласован). Для настоящих тестов дисков под PostgreSQL используйте `fio` и `pg_test_fsync`. В Ubuntu 26.04 `dd` — из rust-coreutils; GNU-версия — `gnudd`.

### 7.2. split и cat — резка больших файлов

```bash
split -b 2G -d -a 3 buh.dump buh.dump.part-        # куски buh.dump.part-000, -001, ...
cat buh.dump.part-* > buh.dump                     # склейка (шаблон раскрывается в алфавитном порядке)

pg_dump -Fc buh | split -b 2G -d -a 3 - /backup/buh.dump.part-     # резать на лету
cat /backup/buh.dump.part-* | pg_restore -d buh_test               # восстановить без склейки на диск

pg_dump buh | split -b 2G --filter='zstd -T0 > $FILE.zst' - /backup/buh.sql.part-   # каждый кусок сжать
split -l 1000000 big.csv chunk_                    # по числу строк
split -n 4 big.bin part_                           # на 4 равные части
```

`-b` — размер куска, `-d` — числовые суффиксы, `-a N` — длина суффикса (при `-a 2` максимум 100 кусков — берите с запасом). Нужно, когда приёмник ограничивает размер файла (FAT32 — 4 ГБ, лимиты облаков, почта). После склейки обязательно сверить контрольную сумму.

### 7.3. Контрольные суммы

```bash
sha256sum buh.dump > buh.dump.sha256               # создать (в файле: хэш, два пробела, имя)
sha256sum -c buh.dump.sha256                       # проверить -> "buh.dump: OK"
sha256sum -c --quiet buh.dump.sha256               # печатать только несовпадения
sha256sum -c --status buh.dump.sha256 && echo OK   # ничего не печатать, только код возврата

( cd /backup/pg && sha256sum -- *.dump > SHA256SUMS )            # общий файл сумм с относительными именами
( cd /mnt/nas/pg && sha256sum -c --ignore-missing SHA256SUMS )   # проверить те файлы, что есть
```

- В файле суммы имя записано так, как было передано команде, — создавайте суммы из каталога с файлами (относительные имена), иначе проверка на другой машине не найдёт путь.
- `--ignore-missing` — не считать ошибкой отсутствующие файлы; `--strict` — ненулевой код при кривых строках.
- `md5sum` — те же ключи; MD5 годится только для обнаружения случайной порчи (быстро, но криптографически взломан). Для бэкапов — `sha256sum`; быстрее на 64-битных CPU — `b2sum` (BLAKE2, тоже в coreutils).
- Контрольная сумма подтверждает, что файл **не изменился после создания**, но не то, что дамп пригоден для восстановления, — это проверяет только `pg_restore`.

## 8. Шифрование резервных копий

Шифровать нужно всё, что покидает сервер (облако, внешний диск, чужая площадка). Сжимать — **до** шифрования (зашифрованные данные не сжимаются).

### 8.1. gpg, симметричное шифрование (паролем)

```bash
# подготовка: файл с паролем; писать может только root, читать — root и группа postgres (от неё работает скрипт)
sudo install -d -m 750 -o root -g postgres /etc/backup
sudo sh -c 'umask 027; openssl rand -base64 48 > /etc/backup/gpg.pass'
sudo chgrp postgres /etc/backup/gpg.pass          # итог: -rw-r----- root:postgres

# зашифровать
gpg --batch --yes --pinentry-mode loopback --passphrase-file /etc/backup/gpg.pass \
    --symmetric --cipher-algo AES256 --s2k-digest-algo SHA512 --compress-algo none \
    --output /backup/pg/buh.dump.gpg /backup/pg/buh.dump

# расшифровать
gpg --batch --yes --pinentry-mode loopback --passphrase-file /etc/backup/gpg.pass \
    --decrypt --output /restore/buh.dump /backup/pg/buh.dump.gpg

# потоком: дамп -> шифрование, без незашифрованного файла на диске
pg_dump -Fc -Z zstd:6 buh | gpg --batch --pinentry-mode loopback \
    --passphrase-file /etc/backup/gpg.pass -c --cipher-algo AES256 --compress-algo none \
    -o /backup/pg/buh_$(date +%F).dump.gpg
```

Пояснения (man gpg, GnuPG 2.4):
- `-c` / `--symmetric` — шифрование паролем; шифр по умолчанию — **AES-128**, поэтому `--cipher-algo AES256` указываем явно; хэш для преобразования пароля по умолчанию SHA-1 → `--s2k-digest-algo SHA512`.
- `--passphrase-file` (читается только первая строка) работает лишь вместе с `--batch`, а с GnuPG 2.1 ещё требуется `--pinentry-mode loopback`. `--passphrase 'строка'` не использовать: пароль виден в списке процессов.
- `--compress-algo none` (или `-z 0`) — отключить встроенное сжатие gpg: данные уже сжаты.
- `--yes` — перезаписывать выходной файл без вопроса; `--no-symkey-cache` — не кешировать пароль в gpg-agent.
- gpg нужен домашний каталог с правами записи (`~/.gnupg`). У служебных пользователей и под cron задайте явно: `export GNUPGHOME=/var/lib/backup/gnupg` (каталог с правами `700`).
- **Пароль храните отдельно от бэкапов** (менеджер паролей, сейф). Потеря пароля = потеря всех копий.

### 8.2. gpg, шифрование открытым ключом

На сервере лежит только открытый ключ; расшифровать можно лишь закрытым ключом, которого на сервере нет. Взлом сервера не раскрывает старые копии.

```bash
# на машине администратора: gpg --full-generate-key ; gpg --export -a backup@example.com > backup-pub.asc
gpg --import backup-pub.asc                                    # на сервере
gpg --batch --yes --trust-model always -e -r backup@example.com \
    --compress-algo none -o /backup/pg/buh.dump.gpg /backup/pg/buh.dump
gpg -d -o buh.dump buh.dump.gpg                                # расшифровка там, где есть закрытый ключ
```

### 8.3. age — простая современная альтернатива

`age` (пакет `age` из universe: Ubuntu 22.04 — 1.0.0, 24.04 — 1.1.1, 26.04 — 1.2.1): маленькая утилита без «связок ключей», шифрует получателям по открытым ключам.

```bash
age-keygen -o key.txt                       # создать пару; строка "public key: age1..." — получатель
age -r age1ql3z7hjy54pw3hyww5ayyfg7zqgvc7w3j2elw8zmrj2kg5sfn9aqmcac8p \
    -o /backup/pg/buh.dump.age /backup/pg/buh.dump             # зашифровать открытым ключом
age -R /etc/backup/recipients.txt -o f.age f                   # получатели из файла (по одному в строке)
age -d -i key.txt -o buh.dump buh.dump.age                     # расшифровать закрытым ключом
tar -cpf - -C /srv data | zstd -T0 | age -r age1... > /backup/data.tar.zst.age   # в конвейере
age -r "$(cat ~/.ssh/id_ed25519.pub)" -o f.age f               # можно шифровать на SSH-ключ (ssh-ed25519, ssh-rsa)
```

- Несколько `-r` — файл смогут расшифровать все перечисленные получатели.
- Режим пароля `age -p` — только интерактивный: man age(1) описывает его как «Encrypt with a passphrase, requested interactively from the terminal»; ни ключа «пароль из файла», ни переменной окружения для пароля документация не предусматривает, с `-r`/`-R` он не сочетается. Для автоматизации используйте получателей-ключи: на сервере хранится только открытый ключ `age1…`, закрытый `key.txt` — в сейфе. Нужен именно пароль в скрипте — берите `gpg` (раздел 8.1).
- `-a` — ASCII-вывод (PEM); `-R -` — список получателей со stdin; `ssh-agent` не поддерживается. `age-keygen -pq` — гибридные постквантовые ключи: только age ≥ 1.3.0, т. е. **ни в одном LTS-пакете Ubuntu (1.0.0 / 1.1.1 / 1.2.1) их нет** — понадобится бинарник с GitHub; файл, зашифрованный таким получателем, старой версией не расшифровать.
- Потеря закрытого ключа `key.txt` = потеря всех копий; храните его минимум в двух местах вне сервера и проверьте расшифровку **до** того, как начнёте полагаться на такие бэкапы.

## 9. Bash-скриптинг: руководство

### 9.1. Шебанг, запуск, каркас скрипта

- Первая строка: `#!/usr/bin/env bash` (или `#!/bin/bash`). В Ubuntu `/bin/sh` — это **dash**, а не bash: скрипт с массивами, `[[ ]]`, `set -o pipefail`, `<( )` нельзя запускать как `sh script.sh` и нельзя начинать с `#!/bin/sh`.
- Сделать исполняемым и положить в стандартное место: `sudo install -m 750 -o root -g root script.sh /usr/local/bin/` (`/usr/local/sbin` — для скриптов root).
- Файл, отредактированный в Windows, имеет окончания строк CRLF → ошибка `/usr/bin/env: 'bash\r': No such file or directory` или `$'\r': command not found`. Лечение: `sed -i 's/\r$//' script.sh` (или `dos2unix`); в редакторе на Windows-хосте включить окончания строк LF и кодировку UTF-8 без BOM.
- Проверка синтаксиса без выполнения: `bash -n script.sh`; статический анализ: `shellcheck script.sh` (см. 9.17).

Каркас, с которого стоит начинать любой скрипт:

```bash
#!/usr/bin/env bash
#
# имя_скрипта — что делает, от какого пользователя и как запускается
#
set -Eeuo pipefail
shopt -s inherit_errexit          # bash >= 4.4: set -e действует и внутри $( ... )
export LC_ALL=C.UTF-8             # предсказуемая локаль и UTF-8 (под cron локаль не задана)
umask 027

SCRIPT_NAME=${0##*/}
SCRIPT_DIR=$(cd -- "$(dirname -- "${BASH_SOURCE[0]}")" && pwd)
readonly SCRIPT_NAME SCRIPT_DIR

log() { printf '%s [%s] %s\n' "$(date '+%F %T')" "$SCRIPT_NAME" "$*"; }
die() { log "ОШИБКА: $*" >&2; exit 1; }

cleanup() {
    local rc=$?
    # удалить временные файлы, снять блокировки и т. п.
    exit "$rc"
}
trap cleanup EXIT
trap 'log "сбой в строке $LINENO: «$BASH_COMMAND» вернула $?" >&2' ERR

main() {
    log "старт"
    # ... основная логика ...
    log "готово"
}

main "$@"
```

### 9.2. Строгий режим: `set -Eeuo pipefail`

| Опция | Что делает |
|---|---|
| `-e` (`errexit`) | немедленный выход, если команда (конвейер, список) вернула ненулевой код |
| `-u` (`nounset`) | обращение к неустановленной переменной — ошибка и выход |
| `-o pipefail` | код возврата конвейера — код самой правой команды, завершившейся с ошибкой (без опции — код последней команды: `false \| true` даёт 0) |
| `-E` (`errtrace`) | ловушка `ERR` наследуется функциями, подстановками команд и подоболочками |
| `-x` (`xtrace`) | печатать каждую команду перед выполнением (отладка) |
| `-n` (`noexec`) | только читать команды, не выполнять (проверка синтаксиса) |
| `-C` (`noclobber`) | запретить `>` перезаписывать существующие файлы (обход: `>\|`) |
| `-f` (`noglob`) | отключить раскрытие шаблонов имён файлов |

**Когда `-e` НЕ срабатывает** (man bash): команда находится в условии `if`/`elif`, в условии `while`/`until`, в цепочке `&&`/`||` (кроме последней команды), в конвейере не на последнем месте (без `pipefail`), либо её статус инвертирован `!`. Кроме того, если функция вызвана в таком «игнорирующем» контексте (`if myfunc; then`, `myfunc || true`), то `-e` отключается **для всего тела функции**.

Ловушки строгого режима и как их обходить:

| Ситуация | Что происходит | Как писать |
|---|---|---|
| `local x=$(cmd)` или `export x=$(cmd)` | код возврата `cmd` теряется (возвращается код `local`) | `local x; x=$(cmd)` |
| `(( i++ ))` при `i=0` | выражение равно 0 → код возврата 1 → скрипт завершается | `(( i += 1 ))` или `i=$(( i + 1 ))` |
| `grep шаблон файл` без совпадений | код 1 → выход | `grep … \|\| true` либо `if grep -q …; then` |
| `[[ условие ]] && команда` последней строкой функции | при ложном условии функция возвращает 1 | `if [[ условие ]]; then команда; fi` |
| `cmd \| head -n 1` при `pipefail` | `cmd` может получить SIGPIPE (код 141) | `cmd \| head -n 1 \|\| true`, либо читать через `read`/`mapfile` |
| `read` на последней строке без `\n` | `read` возвращает 1 | `while IFS= read -r line \|\| [[ -n $line ]]; do` |
| `${arr[0]}` у пустого массива при `-u` | «unbound variable» | проверять `${#arr[@]}`; `"${arr[@]}"` у пустого массива безопасно (bash ≥ 4.4) |
| Нужно пережить ошибку | | `cmd \|\| true`; `rc=0; cmd \|\| rc=$?`; `if ! cmd; then …; fi` |

`set -e` — страховочная сетка, а не обработка ошибок: важные команды (дамп, копирование) проверяйте явно через `if`.

### 9.3. Переменные и кавычки

```bash
name=value                    # БЕЗ пробелов вокруг '='
path="/backup/pg"             # двойные кавычки: $переменные и $(команды) раскрываются
msg='цена $100 и `date`'      # одинарные: всё буквально
nl=$'строка1\nстрока2\t!'     # $'...': понимает \n \t \e и т. п.
today=$(date +%F)             # подстановка команды; `обратные кавычки` — устаревшая форма
count=$(( 5 * 3 ))            # арифметика
readonly BACKUP_DIR=/backup   # константа
export PGHOST=localhost       # передать переменную дочерним процессам
unset tmp                     # удалить переменную
echo "Файл: ${path}/file_${today}.dump"   # {} отделяют имя от соседнего текста
```

Правила кавычек:
- **Всегда** `"$var"` и `"$(cmd)"`. Без кавычек значение разбивается по пробелам/табуляции/переводам строк (по `IFS`) и проходит раскрытие шаблонов (`*`, `?`, `[…]`). Имя файла `отчёт за май.txt` без кавычек превратится в три аргумента.
- Кавычки не нужны (но и не мешают) внутри `[[ … ]]` слева от оператора, в `$(( … ))`, в правой части присваивания `a=$b`.
- `"$@"` — все аргументы как отдельные слова (правильно почти всегда); `"$*"` — все аргументы одной строкой через первый символ `IFS`.
- Команду с параметрами собирайте в **массив**, а не в строку: `cmd=(rsync -a --delete); cmd+=("$src" "$dst"); "${cmd[@]}"`.

Атрибуты (`declare`/`local`): `-i` целое, `-r` только чтение, `-a` массив, `-A` ассоциативный массив, `-x` экспорт, `-l`/`-u` приводить к нижнему/верхнему регистру, `-n` ссылка на другую переменную (nameref).

Специальные переменные:

| Переменная | Значение |
|---|---|
| `$0`, `$1`…`$9`, `${10}` | имя скрипта, позиционные параметры |
| `$#` | число аргументов |
| `$@`, `$*` | все аргументы |
| `$?` | код возврата последней команды |
| `$$`, `$!` | PID оболочки; PID последнего фонового процесса |
| `$_` | последний аргумент предыдущей команды |
| `$-` | текущие флаги оболочки |
| `${PIPESTATUS[@]}` | коды возврата всех команд последнего конвейера |
| `$LINENO`, `${FUNCNAME[0]}`, `${BASH_SOURCE[0]}`, `$BASH_COMMAND` | строка, имя функции, файл скрипта, выполняемая команда |
| `$SECONDS` | секунд с запуска оболочки (удобно мерить длительность) |
| `$RANDOM`, `$EUID`, `$UID`, `$HOSTNAME`, `$PWD`, `$OLDPWD`, `$HOME`, `$IFS` | случайное число 0–32767, эффективный UID и т. д. |

### 9.4. Позиционные параметры

```bash
#!/usr/bin/env bash
set -euo pipefail
(( $# >= 1 )) || { echo "Использование: $0 БАЗА [КАТАЛОГ]" >&2; exit 2; }
db=$1
dir=${2:-/backup/pg}          # второй аргумент или значение по умолчанию
shift                         # сдвиг: $2 становится $1 (shift N — на N позиций)
for arg in "$@"; do echo "аргумент: $arg"; done
last=${!#}                    # последний аргумент (то же: "${@: -1}")
rest=("${@:2}")               # все, начиная со второго, — в массив
set -- a b c                  # переназначить позиционные параметры: $1=a $2=b $3=c
```

### 9.5. Арифметика

Bash умеет только целые числа (64 бита со знаком).

```bash
a=7; b=2
echo $(( a + b ))  $(( a - b ))  $(( a * b ))  $(( a / b ))  $(( a % b ))  $(( a ** b ))   # 9 5 14 3 1 49
(( a > b )) && echo "a больше"           # (( )) как условие: «истина», если результат не 0
(( a += 5 )); (( b *= 2 ))               # присваивание внутри (( ))
size_gb=$(( $(stat -c %s file.dump) / 1024 / 1024 / 1024 ))
echo $(( 16#ff ))  $(( 2#1010 ))  $(( 8#17 ))          # другие системы счисления: 255 10 15
pct=$(( used * 100 / total ))                           # проценты в целых
awk "BEGIN { printf \"%.2f\n\", $a / $b }"              # дробные — через awk (или bc -l)
```

Ловушка: число с ведущим нулём считается **восьмеричным** — `$(( 08 + 1 ))` даёт ошибку «value too great for base». Это типично для `date +%d`/`%m`/`%H`. Решение: `$(( 10#$day + 1 ))` либо формат без дополнения `date +%-d`.

### 9.6. Операции со строками (раскрытие параметров)

| Выражение | Результат |
|---|---|
| `${#s}` | длина строки |
| `${s#шаблон}` / `${s##шаблон}` | удалить **префикс**: самый короткий / самый длинный |
| `${s%шаблон}` / `${s%%шаблон}` | удалить **суффикс**: самый короткий / самый длинный |
| `${s/шаблон/замена}` / `${s//шаблон/замена}` | заменить первое / все вхождения |
| `${s/#шаблон/замена}` / `${s/%шаблон/замена}` | заменить только в начале / только в конце |
| `${s:смещение}` / `${s:смещение:длина}` | подстрока (отсчёт с 0); `${s: -3}` — последние 3 символа (пробел перед минусом обязателен) |
| `${s:-умолч}` | значение по умолчанию, если переменная не задана **или пуста** |
| `${s:=умолч}` | то же, но ещё и присвоить |
| `${s:?сообщение}` | если не задана/пуста — вывести сообщение и завершить скрипт |
| `${s:+значение}` | подставить значение, только если переменная задана и не пуста |
| `${s-умолч}`, `${s=…}`, `${s?…}`, `${s+…}` | те же формы без двоеточия проверяют только «не задана» (пустая строка считается значением) |
| `${s^^}` / `${s,,}` / `${s^}` | в верхний / нижний регистр / первая буква заглавная |
| `${!name}` | косвенная ссылка: значение переменной, имя которой лежит в `name` |
| `${!prefix*}` | имена всех переменных с данным префиксом |
| `${s@Q}` | значение в кавычках, пригодное для повторного ввода в shell |

Шаблоны здесь — glob (`*`, `?`, `[…]`), не регулярные выражения.

```bash
f=/backup/pg/buh_2026-10-10.dump.zst
echo "${f##*/}"        # buh_2026-10-10.dump.zst   — имя файла (как basename)
echo "${f%/*}"         # /backup/pg                — каталог (как dirname)
echo "${f%.zst}"       # /backup/pg/buh_2026-10-10.dump — без последнего расширения
echo "${f##*.}"        # zst                       — расширение
echo "${f%%.*}"        # /backup/pg/buh_2026-10-10 — до первой точки
name=${f##*/}
echo "${name%%_*}"     # buh                       — имя базы (до первого '_')
echo "${f/dump/sql}"   # /backup/pg/buh_2026-10-10.sql.zst
echo "${f//-/}"        # /backup/pg/buh_20261010.dump.zst — убрать все дефисы
echo "${f:0:7}"        # /backup
echo "${f: -3}"        # zst
echo "${#f}"           # 34

: "${BACKUP_DIR:=/backup/pg}"          # задать значение по умолчанию (':' — пустая команда)
keep=${KEEP_DAYS:-14}
db=${1:?не указано имя базы}           # аварийно завершиться, если аргумента нет
verbose_opt=${DEBUG:+--verbose}        # опция появляется, только если DEBUG не пуста
upper=${db^^}; lower=${db,,}

s="  текст с пробелами  "              # обрезать пробелы по краям
s="${s#"${s%%[![:space:]]*}"}"; s="${s%"${s##*[![:space:]]}"}"
```

Соединение строк — просто запись рядом: `full="$dir/$name"`; дописать: `s+=" ещё"`. Проверка подстроки: `[[ $s == *"подстрока"* ]]`.

### 9.7. Массивы и ассоциативные массивы

```bash
dbs=(buh zup "ut 11")             # индексированный массив (индексы с 0)
dbs+=(erp)                        # добавить элемент
echo "${dbs[0]}"                  # первый элемент
```

### 9.8. Условия

```bash
if [[ -f $file && -s $file ]]; then
    echo "файл существует и не пуст"
elif [[ -d $file ]]; then
    echo "это каталог"
else
    echo "нет такого файла"
fi

if ! pg_isready -q; then echo "PostgreSQL недоступен"; fi      # условие — код возврата команды
if grep -q '^backup:' /etc/passwd; then echo "пользователь есть"; fi
```

`[[ … ]]` — встроенная конструкция bash (предпочтительна): внутри не происходит разбиение слов и раскрытие шаблонов, работают `&&`, `||`, `==` с шаблонами, `=~` с регулярными выражениями. `[ … ]` и `test` — POSIX-команда: переменные обязательно в кавычках, вместо `&&` — `-a` или `[ … ] && [ … ]`.

| Проверка | Истина, если |
|---|---|
| `-e f` / `-f f` / `-d f` / `-L f` | существует / обычный файл / каталог / симлинк |
| `-s f` | файл существует и не пуст |
| `-r f` / `-w f` / `-x f` | доступен на чтение / запись / исполнение |
| `f1 -nt f2` / `f1 -ot f2` | f1 новее / старее f2 |
| `-z "$s"` / `-n "$s"` | строка пуста / не пуста |
| `$a == $b` / `$a != $b` | строки равны / не равны (в `[[ ]]` правая часть без кавычек — **шаблон**) |
| `$a < $b` / `$a > $b` | лексикографическое сравнение строк |
| `$a =~ regex` | соответствует расширенному регулярному выражению; группы — в `BASH_REMATCH` |
| `-eq -ne -lt -le -gt -ge` | сравнение целых чисел |
| `-v var` | переменная установлена |
| `! выражение` | отрицание |

```bash
[[ $file == *.dump ]]                       # шаблон: оканчивается на .dump
[[ $file == "*.dump" ]]                     # в кавычках — буквальное сравнение со строкой "*.dump"
if [[ $name =~ ^([a-z0-9_]+)_([0-9]{4}-[0-9]{2}-[0-9]{2})\.dump$ ]]; then
    db=${BASH_REMATCH[1]}; day=${BASH_REMATCH[2]}
fi
[[ $n =~ ^[0-9]+$ ]] || die "не число: $n"   # регулярное выражение — БЕЗ кавычек
(( free_gb < 20 )) && die "мало места"       # числа удобнее сравнивать в (( ))
[ "$a" = "$b" ]                              # POSIX-вариант
```

`case` — выбор по шаблонам:

```bash
case $1 in
    start|up)   start_service ;;
    stop)       stop_service ;;
    *.dump)     restore_custom "$1" ;;
    *.sql.gz|*.sql.zst) restore_plain "$1" ;;
    [0-9]*)     echo "начинается с цифры" ;;
    '')         echo "пустой аргумент" ;;
    *)          echo "неизвестно: $1" >&2; exit 2 ;;
esac
```

`;;` — конец ветки; `;&` — «провалиться» в следующую ветку; `;;&` — продолжить проверку остальных шаблонов.

### 9.9. Циклы

```bash
for db in buh zup erp; do echo "$db"; done               # по списку слов
for db in "${DATABASES[@]}"; do …; done                  # по массиву
for f in /backup/pg/*.dump; do                           # по файлам (glob)
    [[ -e $f ]] || continue                              # если совпадений нет, шаблон остаётся строкой
    echo "$f"
done
for (( i = 1; i <= 5; i++ )); do echo "попытка $i"; done # счётчик в стиле C
for i in {1..10}; do …; done ; for i in {0..100..10}; do …; done   # диапазон (не работает с переменными: {1..$n})

n=0
while (( n < 5 )); do (( n += 1 )); done                 # пока условие истинно
until pg_isready -q; do sleep 2; done                    # пока условие ложно
while true; do …; sleep 60; done                         # бесконечный цикл; break — выйти, continue — следующая итерация
```

Построчное чтение файла — единственно правильная форма:

```bash
while IFS= read -r line; do
    [[ -z $line || $line == \#* ]] && continue           # пропустить пустые строки и комментарии
    echo "строка: $line"
done < /etc/backup/databases.txt
```

- `IFS=` — не обрезать пробелы по краям; `-r` — не трактовать `\` как экранирование.
- Последняя строка без завершающего `\n` будет потеряна; защита: `while IFS= read -r line || [[ -n $line ]]; do`.
- Чтение полей: `while IFS=: read -r user _ uid _ _ home shell; do …; done < /etc/passwd`.
- **Конвейер в цикл** (`cmd | while read …`) выполняет тело в подоболочке: изменённые внутри переменные снаружи не видны. Правильно — подстановка процесса: `while IFS= read -r line; do …; done < <(cmd)`.
- Имена файлов с любыми символами: `while IFS= read -r -d '' f; do …; done < <(find /dir -type f -print0)`.
- `ssh`, `ffmpeg` и подобные команды внутри `while read` «съедают» stdin цикла — вызывайте `ssh -n …` или `ssh … </dev/null`.
- Повтор с паузой (ретраи):

```bash
for attempt in 1 2 3; do
    if rsync -a /backup/pg/ nas:/srv/backup/pg/; then break; fi
    echo "попытка $attempt не удалась" >&2
    (( attempt == 3 )) && exit 1
    sleep $(( attempt * 30 ))
done
```

### 9.10. Функции и коды возврата

```bash
backup_db() {                     # объявление; вызывается как команда: backup_db buh /backup/pg/buh.dump
    local db=$1 out=$2            # local — переменная видна только в функции (и в вызванных из неё)
    local rc=0
    pg_dump -Fc -f "$out" "$db" || rc=$?
    return "$rc"                  # код возврата функции: 0..255 (без return — код последней команды)
}

if backup_db buh /backup/pg/buh.dump; then echo "ok"; else echo "ошибка, код $?"; fi

latest_dump() {                   # «вернуть строку» можно только через stdout
    local dir=$1
    find "$dir" -maxdepth 1 -type f -name '*.dump' -printf '%T@ %p\n' | sort -n | tail -n 1 | cut -d' ' -f2-
}
newest=$(latest_dump /backup/pg)

fill_list() {                     # вернуть массив — через ссылку на переменную (nameref, bash >= 4.3)
    local -n ref=$1
    ref=(buh zup erp)
}
fill_list my_dbs; echo "${my_dbs[1]}"     # zup
```

Соглашения о кодах возврата:

| Код | Значение |
|---|---|
| 0 | успех |
| 1 | общая ошибка |
| 2 | неверное использование (синтаксис, аргументы) |
| 124 | команда прервана `timeout` |
| 126 | команда найдена, но не исполняема (нет прав `x`) |
| 127 | команда не найдена (типично под cron из-за `PATH`) |
| 128+N | процесс убит сигналом N: 130 — SIGINT (Ctrl-C), 137 — SIGKILL (в т. ч. OOM killer), 141 — SIGPIPE, 143 — SIGTERM |
| 255 | ошибка ssh; также «код вне диапазона» (`exit 256` превращается в 0 — берётся остаток от деления на 256) |

```bash
cmd; echo "код: $?"                       # $? нужно читать СРАЗУ: любая следующая команда его перезапишет
rc=0; cmd || rc=$?                        # сохранить код и не уронить скрипт при set -e
if ! cmd; then echo "упало" >&2; fi
pg_dump -Fc buh | zstd -q -o buh.dump.zst
st=("${PIPESTATUS[@]}")                   # коды всех звеньев конвейера: st[0] — pg_dump, st[1] — zstd
(( st[0] == 0 && st[1] == 0 )) || echo "ошибка: pg_dump=${st[0]} zstd=${st[1]}" >&2
```

`cmd1 && cmd2 || cmd3` — **не** if/else: `cmd3` выполнится и тогда, когда `cmd1` успешна, а `cmd2` упала. Для ветвления используйте `if`.

### 9.11. trap — ловушки сигналов и событий

```bash
tmpdir=$(mktemp -d -p /backup/tmp job.XXXXXX)     # временный каталог на диске (не в /tmp: в 26.04 это tmpfs)

cleanup() {
    local rc=$?
    trap - EXIT                    # не входить в обработчик повторно
    rm -rf -- "$tmpdir"
    exit "$rc"
}
trap cleanup EXIT                  # любой выход из скрипта: конец, exit, срабатывание set -e
trap 'exit 130' INT                # Ctrl-C  -> обычный выход -> сработает EXIT
trap 'exit 143' TERM               # kill / systemctl stop -> то же
trap 'echo "сбой: строка $LINENO, команда «$BASH_COMMAND», код $?" >&2' ERR
```

| Событие | Когда срабатывает |
|---|---|
| `EXIT` (0) | при выходе из оболочки: конец скрипта, `exit`, срабатывание `set -e`. Чтобы очистка гарантированно выполнялась и при получении сигнала, ставьте ловушки `INT`/`TERM` с `exit` (как в примере). При SIGKILL не выполняется ничего |
| `ERR` | когда команда вернула ненулевой код — с теми же исключениями, что и у `set -e` (условия `if`/`while`, `&&`/`\|\|`, `!`). Без `set -E` не действует внутри функций и подоболочек |
| `INT`, `TERM`, `HUP`, `QUIT`, `USR1`, `USR2` | соответствующие сигналы; `KILL` и `STOP` перехватить нельзя |
| `DEBUG`, `RETURN` | перед каждой командой / при возврате из функции (для отладки) |

- `trap '' INT` — игнорировать сигнал; `trap - INT` — вернуть обработку по умолчанию; `trap -p` — показать установленные ловушки.
- Пишите тело ловушки в **одинарных** кавычках: переменные раскроются в момент срабатывания, а не установки.
- В подоболочке (`( … )`, `$( … )`, звенья конвейера) перехваченные сигналы сбрасываются к исходным значениям.
- Обработчик сигнала выполняется только после завершения текущей внешней команды: скрипт, «спящий» в `sleep 3600`, отреагирует на TERM через час. Чтобы реагировать сразу: `sleep 3600 & wait $!`.

### 9.12. Перенаправления, here-doc, подстановка процессов

| Запись | Смысл |
|---|---|
| `cmd > f` / `cmd >> f` | stdout в файл: перезаписать / дописать |
| `cmd < f` | stdin из файла |
| `cmd 2> f` | stderr в файл |
| `cmd > f 2>&1` | stdout и stderr в один файл (**порядок важен**: `2>&1 > f` оставит stderr на экране) |
| `cmd &> f` / `cmd &>> f` | краткая форма bash для предыдущего |
| `cmd > /dev/null 2>&1` | выбросить весь вывод |
| `cmd1 \| cmd2` / `cmd1 \|& cmd2` | конвейер: только stdout / stdout вместе с stderr |
| `cmd \| tee f` / `tee -a f` | и на экран, и в файл (перезаписать / дописать) |
| `{ cmd1; cmd2; } > f` | общий вывод группы команд (в текущей оболочке); `( … )` — в подоболочке |
| `exec >> f 2>&1` | перенаправить вывод **всего дальнейшего скрипта** |
| `exec 3> f` … `echo x >&3` … `exec 3>&-` | открыть, использовать, закрыть свой файловый дескриптор |
| `cmd <<< "строка"` | here-string: строка на stdin |
| `: > f` | обнулить файл |

Here-document — многострочный текст на stdin команды:

```bash
cat > /etc/backup/backup.conf <<EOF
BACKUP_DIR=$BACKUP_DIR
CREATED=$(date +%F)
EOF

cat <<'EOF'
Метка в кавычках: ничего не раскрывается — $HOME, $(date), `cmd` остаются как есть.
EOF

# SQL в psql; :'db' — безопасная подстановка psql-переменной (работает для stdin/-f, но не для -c)
psql -X -At -v ON_ERROR_STOP=1 -v db="$db" -d postgres <<'SQL'
SELECT pg_size_pretty(pg_database_size(:'db'));
SQL

# выполнить блок команд на удалённом сервере
ssh -o BatchMode=yes backup@nas 'bash -s' <<'EOF'
set -euo pipefail
df -h /srv/backup
find /srv/backup/pg -name '*.dump' -mtime +30 -delete
EOF
```

- Закрывающая метка должна стоять **в начале строки**, без пробелов до и после. Форма `<<-EOF` разрешает отступы, но только **табуляциями** (пробелы не удаляются).
- `<<EOF` — переменные и команды раскрываются; `<<'EOF'` — нет.

Подстановка процессов — вывод команды как «файл» (`<(cmd)`) или «файл», запись в который попадает команде на stdin (`>(cmd)`):

```bash
diff <(ssh nas 'ls /srv/backup/pg') <(ls /backup/pg)              # сравнить два списка
while IFS= read -r f; do echo "$f"; done < <(find /backup -name '*.dump')   # цикл без подоболочки
exec > >(tee -a "$LOG_FILE") 2>&1                                 # весь вывод скрипта — и на экран, и в лог
# дамп и его контрольная сумма за один проход по данным
pg_dump -Fc buh | tee >(sha256sum | awk '{print $1 "  buh.dump"}' > /backup/pg/buh.dump.sha256) > /backup/pg/buh.dump
```

Оболочка не ждёт завершения процессов внутри `>( … )`: сразу после команды файл с суммой может быть ещё не дописан. Если результат нужен немедленно — считайте сумму отдельной командой.

### 9.13. Разбор ключей: getopts

```bash
usage() {
    cat <<EOF
Использование: ${0##*/} [-d КАТАЛОГ] [-k ДНЕЙ] [-n] [-v] БАЗА...
  -d КАТАЛОГ  каталог бэкапов (по умолчанию /backup/pg)
  -k ДНЕЙ     срок хранения в сутках (по умолчанию 14)
  -n          пробный прогон, ничего не менять
  -v          подробный вывод
  -h          эта справка
EOF
}

backup_dir=/backup/pg; keep=14; dry_run=0; verbose=0

while getopts ':d:k:nvh' opt; do
    case $opt in
        d)  backup_dir=$OPTARG ;;
        k)  keep=$OPTARG ;;
        n)  dry_run=1 ;;
        v)  verbose=1 ;;
        h)  usage; exit 0 ;;
        :)  echo "Ключу -$OPTARG нужен аргумент" >&2; usage >&2; exit 2 ;;
        \?) echo "Неизвестный ключ: -$OPTARG" >&2; usage >&2; exit 2 ;;
    esac
done
shift $(( OPTIND - 1 ))                    # убрать разобранные ключи; в "$@" остались базы

(( $# >= 1 )) || { usage >&2; exit 2; }
[[ $keep =~ ^[0-9]+$ ]] || { echo "-k: нужно целое число" >&2; exit 2; }
```

- Строка `':d:k:nvh'`: буква с двоеточием после неё — ключ с аргументом (значение в `$OPTARG`); **ведущее двоеточие** включает «тихий» режим: при неизвестном ключе `opt='?'`, при отсутствии аргумента `opt=':'`, а сам ключ — в `$OPTARG`.
- `getopts` понимает слитные ключи (`-nv`), аргумент слитно и раздельно (`-k14`, `-k 14`), `--` как конец ключей. **Длинные ключи (`--dir`) не поддерживает** — для них пишут цикл вручную:

```bash
while (( $# )); do
    case $1 in
        --dir)      backup_dir=${2:?--dir требует значение}; shift 2 ;;
        --dir=*)    backup_dir=${1#*=}; shift ;;
        --dry-run)  dry_run=1; shift ;;
        -h|--help)  usage; exit 0 ;;
        --)         shift; break ;;
        -*)         echo "Неизвестный ключ: $1" >&2; exit 2 ;;
        *)          break ;;
    esac
done
```

### 9.14. Логирование

```bash
LOG_FILE=/var/log/myjob/myjob.log
log() { printf '%s %-5s %s\n' "$(date '+%F %T')" "$1" "${*:2}"; }
log INFO  "старт"
log ERROR "дамп не создан" >&2
```

| Задача | Приём |
|---|---|
| Весь вывод скрипта в файл | `exec >>"$LOG_FILE" 2>&1` (в начале скрипта) |
| И на экран, и в файл | `exec > >(tee -a "$LOG_FILE") 2>&1` |
| На экран при ручном запуске, в файл — под cron | `if [[ -t 1 ]]; then exec > >(tee -a "$LOG_FILE") 2>&1; else exec >>"$LOG_FILE" 2>&1; fi` |
| Сообщение в syslog/journald | `logger -t myjob -p local0.err -- "текст"` (`-t` тег, `-p facility.level`, по умолчанию `user.notice`; `-s` — продублировать в stderr; `--id=$$` — писать PID скрипта) |
| Весь вывод в journald | `exec > >(logger -t myjob) 2>&1` или запуск `systemd-cat -t myjob script.sh` |
| Читать | `journalctl -t myjob --since today`, `journalctl -u myjob.service -n 100`, `grep myjob /var/log/syslog` |
| Метка времени на каждую строку вывода команды | `cmd 2>&1 \| ts '%F %T'` (`ts` — пакет `moreutils`) |

Уровни syslog: `emerg`, `alert`, `crit`, `err`, `warning`, `notice`, `info`, `debug`; для своих задач удобны facility `local0`…`local7`. Скрипт, запущенный как сервис systemd, получает запись stdout/stderr в журнал автоматически — перенаправлять ничего не нужно.

Ротация собственных логов — logrotate:

```text
# /etc/logrotate.d/pg_backup
/var/log/pg_backup/*.log {
    weekly
    rotate 8
    compress
    delaycompress
    missingok
    notifempty
    su postgres postgres
    create 0640 postgres postgres
}
```

(`su` обязателен, если каталог логов принадлежит не root; проверка: `logrotate -d /etc/logrotate.d/pg_backup`.)

### 9.15. Защита от параллельного запуска (flock) и ограничение времени (timeout)

`flock` (пакет util-linux) берёт блокировку на файл; блокировка снимается автоматически, когда процесс завершается (даже аварийно), — «протухших» lock-файлов не бывает.

```bash
# Вариант 1 — в начале скрипта: дескриптор 9 держит блокировку до выхода из скрипта
exec 9>/run/lock/pg_backup.lock
if ! flock -n 9; then
    echo "уже выполняется другой экземпляр" >&2
    exit 0
fi

# Вариант 2 — снаружи, например в crontab
flock -n /run/lock/pg_backup.lock /usr/local/bin/pg_backup.sh
flock -w 600 /run/lock/pg.lock -c 'pg_dump -Fc -f /backup/a.dump a && echo done'   # ждать блокировку до 10 минут

# Вариант 3 — блокировка только на часть скрипта
(
    flock -n 9 || exit 1
    # ... критическая секция ...
) 9>/run/lock/part.lock
```

| Ключ | Значение |
|---|---|
| `-n` (`--nonblock`) | не ждать: если занято — сразу ошибка |
| `-w СЕК` (`--timeout`) | ждать не дольше указанного |
| `-x` / `-s` | исключительная (по умолчанию) / разделяемая блокировка |
| `-E КОД` | код возврата при занятой блокировке/таймауте (по умолчанию 1) |
| `-o` (`--close`) | закрыть дескриптор перед запуском команды (дочерние процессы не унаследуют блокировку) |
| `-u` | снять блокировку явно |

- Lock-файлы держите в `/run/lock` (tmpfs, доступен на запись всем, очищается при перезагрузке).
- Фоновые процессы, запущенные из скрипта, наследуют дескриптор и **продолжают держать блокировку** после выхода скрипта; запускайте их с `9>&-`.
- В systemd-таймерах flock не нужен: пока сервис активен, повторно он не запускается.

`timeout` (coreutils) убивает команду, работающую слишком долго:

```bash
timeout 6h pg_dump -Fc -f /backup/pg/buh.dump buh       # по истечении 6 часов послать SIGTERM
timeout -k 30s 10m rsync -a /src/ /dst/                 # через 10 мин TERM, ещё через 30 с — KILL
timeout -s INT 60 psql -c 'SELECT pg_sleep(600)'        # другой сигнал
timeout 5 bash -c 'exec 3<>/dev/tcp/127.0.0.1/1541' && echo "порт открыт"
```

Длительность: число с суффиксом `s` (по умолчанию), `m`, `h`, `d`. Коды: **124** — сработал таймаут; 125 — ошибка самого `timeout`; 126/127 — команду не удалось запустить/найти; 137 — команда убита SIGKILL; иначе — код самой команды (`--preserve-status` возвращает код команды и при таймауте).

Нюансы `timeout`:
- `timeout` запускает команду в отдельной группе процессов. Если он вызван из скрипта, а скрипт — из терминала, то **Ctrl-C до команды не доходит**: при ручном пробном запуске `pg_backup.sh` нажатие Ctrl-C не прервёт идущий `pg_dump` (обработчик `INT` в скрипте выполнится только после завершения дампа). Для интерактивной отладки используйте `timeout --foreground …` либо завершайте процесс командой `kill` из другого терминала. Под cron/systemd это роли не играет.
- Обратная сторона `--foreground` (man timeout): в этом режиме потомки команды по таймауту **не** завершаются — сигнал получает только сама команда. В обычном режиме сигнал уходит всей группе процессов. Если команда может проигнорировать TERM, добавляйте `-k` (последующий KILL).
- В Ubuntu 26.04 `timeout` — из rust-coreutils (GNU-версия — `gnutimeout`); перечисленные ключи и коды возврата относятся к GNU coreutils 9.4 — на 26.04 проверьте поведение пробным запуском (`timeout 1 sleep 5; echo $?` должно дать 124).

### 9.16. Даты и время

```bash
date +%F                    # 2026-10-10            (то же, что %Y-%m-%d)
date +%T                    # 14:05:59              (%H:%M:%S)
date '+%F %T'               # 2026-10-10 14:05:59
date +%Y%m%d_%H%M%S         # 20261010_140559       — для имён файлов
date +%s                    # секунды с 1970-01-01 UTC (epoch)
date +%u                    # день недели 1..7 (1 = понедельник);  %a/%A — название
date +%d ; date +%m ; date +%j ; date +%V     # день месяца, месяц, день года, ISO-номер недели
date -Is ; date -u +%FT%TZ  # ISO 8601 с часовым поясом ; время UTC
date -d yesterday +%F       # вчера
date -d '7 days ago' +%F    # неделю назад;  '+2 hours', 'next month', 'last friday'
date -d '2026-10-10 +1 month' +%F          # арифметика от заданной даты
date -d "$(date +%Y-%m-01) -1 day" +%F     # последний день прошлого месяца
date -d @1791000000 '+%F %T'               # из epoch в читаемый вид
date -r /backup/pg/buh.dump '+%F %T'       # время изменения файла
TZ=Asia/Tashkent date ; TZ=UTC date        # в другом часовом поясе

printf '%(%F %T)T\n' -1                    # встроенное средство bash (без запуска date); -1 = «сейчас»
printf -v stamp '%(%F_%H%M%S)T' -1         # результат сразу в переменную

start=$SECONDS; sleep 3; echo "прошло $(( SECONDS - start )) с"                      # длительность
age_days=$(( ( $(date +%s) - $(date -r "$f" +%s) ) / 86400 ))                        # возраст файла в сутках
```

Типовые проверки для схемы «дед-отец-сын»:

```bash
dom=$(date +%d); dow=$(date +%u)
if   [[ $dom == 01 ]]; then kind=monthly      # первое число месяца
elif [[ $dow == 7  ]]; then kind=weekly       # воскресенье
else                        kind=daily
fi
```

Подводные камни:
- сравнивайте `%d`/`%m`/`%H` как **строки** (`== 01`) либо приводите к десятичной системе `$(( 10#$dom ))` — иначе `08` и `09` дают ошибку восьмеричного числа;
- `date -d 'last month'` 31-го числа «перепрыгивает» месяц (31 сентября не существует); считайте от середины месяца: `date -d "$(date +%Y-%m-15) -1 month" +%Y-%m`;
- в crontab символ `%` нужно экранировать: `\%F`;
- в Ubuntu 26.04 `date` — из rust-coreutils; сложные выражения `-d` проверяйте заранее, запасной вариант — `gnudate`;
- проверить часовой пояс сервера: `timedatectl`; сменить: `sudo timedatectl set-timezone Asia/Tashkent` (после смены перезапустить cron: `sudo systemctl restart cron`).

### 9.17. Отладка и shellcheck

```bash
bash -n script.sh                 # только проверка синтаксиса
bash -x script.sh                 # трассировка: каждая команда печатается с префиксом '+'
bash -xv script.sh                # плюс исходные строки по мере чтения
set -x; подозрительный_участок; set +x          # трассировка части скрипта
export PS4='+ ${BASH_SOURCE##*/}:${LINENO}:${FUNCNAME[0]:-main}: '   # информативный префикс трассировки
exec 5>/var/log/myjob/trace.log; BASH_XTRACEFD=5; set -x             # трассировку — в отдельный файл
trap 'echo "строка $LINENO: $BASH_COMMAND" >&2' DEBUG                # печатать каждую команду перед выполнением
declare -p var arr                # показать тип и значение переменных
env -i HOME="$HOME" PATH=/usr/bin:/bin SHELL=/bin/sh /usr/local/bin/job.sh     # запустить «как под cron» (пустое окружение)
```

Внимание: `set -x` печатает значения переменных — пароли и токены попадут в лог. Отключайте трассировку вокруг работы с секретами.

**shellcheck** — статический анализатор shell-скриптов; ловит большинство типовых ошибок. Установка: `sudo apt install shellcheck`.

```bash
shellcheck script.sh                      # проверить
shellcheck -x script.sh                   # следовать по source-файлам
shellcheck -S warning *.sh                # только предупреждения и ошибки (уровни: error, warning, info, style)
shellcheck -s bash -e SC1091 script.sh    # указать диалект; исключить код
shellcheck -f gcc script.sh               # формат для редакторов/CI (tty, gcc, json1, checkstyle, diff, quiet)
```

Коды возврата: 0 — замечаний нет, 1 — есть замечания, 2 — часть файлов не обработана, 3/4 — неверный вызов. Отключить проверку точечно — директивой перед командой: `# shellcheck disable=SC2086`; для подключаемых файлов: `# shellcheck source=/etc/backup/notify.conf` (или `source=/dev/null`). Общие настройки — файл `.shellcheckrc` рядом со скриптом или `~/.shellcheckrc`.

Самые частые замечания:

| Код | Суть | Исправление |
|---|---|---|
| SC2086 | переменная без кавычек | `"$var"` |
| SC2046 | `$(cmd)` без кавычек | `"$(cmd)"` или массив |
| SC2155 | `local x=$(cmd)` скрывает код возврата | объявить и присвоить раздельно |
| SC2164 | `cd` без проверки | `cd dir \|\| exit 1` |
| SC2162 | `read` без `-r` | `read -r` |
| SC2006 | обратные кавычки | `$(cmd)` |
| SC2012, SC2045 | разбор вывода `ls` | glob или `find` |
| SC2115 | `rm -rf "$dir/"*` при пустой `$dir` удалит `/*` | `rm -rf "${dir:?}/"*` |
| SC2181 | проверка `$?` вместо прямой проверки команды | `if cmd; then` |
| SC2034 / SC2154 | переменная не используется / не присвоена | опечатка в имени |
| SC1090 / SC1091 | не найден подключаемый файл | директива `source=` |

### 9.18. Фоновые задания и `wait`

`команда &` запускает команду в фоне; `$!` — её PID; `wait` дожидается завершения. Это простейший способ распараллелить независимые операции (дампы разных баз, сжатие нескольких файлов) без `xargs`/`parallel`.

```bash
pids=()
for db in buh zup erp; do
    pg_dump -Fc -f "/backup/pg/$db.dump.partial" "$db" &
    pids+=("$!")
done

fail=0
for pid in "${pids[@]}"; do
    wait "$pid" || fail=1            # wait PID возвращает код завершения именно этого процесса
done
(( fail == 0 )) || { echo "хотя бы один дамп завершился с ошибкой" >&2; exit 1; }
```

- `wait` **без аргументов** ждёт все фоновые процессы и возвращает 0 — коды ошибок теряются; чтобы узнать результат, ждите каждый PID отдельно, как в примере.
- `set -e` и ловушка `ERR` на падение фоновой команды **не реагируют** — проверка кода через `wait PID` обязательна.
- `wait -n` (bash ≥ 4.3) ждёт завершения любого одного задания и возвращает его код — на нём строят ограничение числа одновременных заданий; `wait -n -p var` (bash ≥ 5.1, т. е. есть во всех трёх LTS) дополнительно кладёт PID завершившегося процесса в `var`.
- `jobs -p` — PID всех фоновых заданий оболочки; в обработчике выхода ими удобно «прибирать» потомков: `trap 'kill $(jobs -p) 2>/dev/null' EXIT`.
- Параллельные `pg_dump` нагружают диск и СУБД одновременно; на сервере, где работают пользователи 1С, обычно разумнее последовательный запуск либо не более 2–3 заданий.
- Чтобы процесс пережил выход из SSH-сессии, одного `&` мало: используйте `systemd-run --unit=имя команда` (вывод попадёт в журнал), `nohup команда >лог 2>&1 &` или `tmux`/`screen`.

## 10. Полезные утилиты для скриптов

### 10.1. find — отбор файлов (основа очистки и ротации)

```bash
find /backup/pg -maxdepth 1 -type f -name '*.dump' -mtime +14 -print      # сначала ПОСМОТРЕТЬ, что найдётся
find /backup/pg -maxdepth 1 -type f -name '*.dump' -mtime +14 -delete     # затем удалить
find /var/log/1c -type f -name '*.log' -mmin +1440 -size +100M -exec zstd -q --rm {} +
find /backup -xdev -type f -newermt '2026-10-01' ! -newermt '2026-10-08' -ls  # изменённые в интервале дат
find /backup/tmp -mindepth 1 -type d -empty -delete                        # убрать пустые каталоги
find /backup/pg -type f -name '*.dump' -printf '%TY-%Tm-%Td %10s %p\n' | sort   # дата, размер, путь
```

- `-mtime N` считает возраст в **целых сутках** (дробная часть отбрасывается): `-mtime +14` — файл изменён более 14 полных суток назад, т. е. ему 15 суток и больше; `-mtime -1` — моложе суток; `-mtime 0` — за последние 24 часа. `-mmin` — то же в минутах. `-daystart` — считать от начала сегодняшних суток.
- `-delete` ставится **последним**: стоя первым, он удалит всё дерево до применения остальных условий. `-delete` включает `-depth`.
- `-maxdepth`/`-mindepth` пишутся сразу после путей, до остальных условий.
- `-exec cmd {} +` — передать много файлов одной командой; `-exec cmd {} \;` — запускать на каждый файл.
- `-xdev` — не выходить за пределы файловой системы.

### 10.2. xargs — аргументы из stdin, параллельный запуск

```bash
find /backup/pg -name '*.sql' -print0 | xargs -0 -r -n 1 -P 4 zstd -q --rm -6      # сжать файлы в 4 потока
printf '%s\n' buh zup erp | xargs -P 3 -I{} pg_dump -Fc -f /backup/pg/{}.dump {}   # 3 дампа одновременно
xargs -a /etc/backup/hosts.txt -I{} -P 5 ssh -n -o BatchMode=yes {} uptime         # команда на списке хостов
```

`-0` — разделитель NUL (в паре с `find -print0`); `-r` — не запускать команду при пустом вводе; `-n N` — по N аргументов на запуск; `-P N` — до N процессов параллельно (`-P 0` — без ограничения); `-I{}` — подставлять строку ввода на место `{}`; `-a ФАЙЛ` — читать из файла. Код возврата 123 — хотя бы один запуск завершился с ошибкой.

### 10.3. GNU parallel

Пакет `parallel`. Удобнее xargs, когда нужен контроль: журнал заданий, остановка по ошибке, аккуратный вывод.

```bash
parallel -j 3 'pg_dump -Fc -f /backup/pg/{}.dump {}' ::: buh zup erp
parallel -j 4 --halt soon,fail=1 --joblog /var/log/parallel.log 'zstd -q --rm {}' ::: /backup/pg/*.sql
find /backup -name '*.dump' | parallel -j 2 'sha256sum {} > {}.sha256'
```

`-j N` — число заданий; `:::` — список аргументов; `{}` — аргумент, `{.}` — без расширения, `{/}` — без каталога; `--halt soon,fail=1` — не запускать новые задания после первой ошибки; `--joblog` — журнал с кодами возврата. При первом запуске выводит просьбу о цитировании — отключается однократно командой `parallel --citation`.

### 10.4. jq — работа с JSON

Пакет `jq`. Нужен для разбора ответов HTTP API (Telegram, S3, мониторинг).

```bash
resp=$(curl -sS --max-time 20 "https://api.example.com/status")
jq -r '.result.name' <<<"$resp"                         # -r: строка без кавычек
jq -e '.ok == true' <<<"$resp" >/dev/null || echo "API вернул ошибку"   # -e: код возврата по результату
jq -r '.items[] | "\(.name)\t\(.size)"' data.json       # перебор массива, вывод через табуляцию
jq -r '.[] | select(.Size > 1000000000) | .Path' <(rclone lsjson s3backup:pg-backups)
payload=$(jq -n --arg chat "$TG_CHAT_ID" --arg text "$msg" '{chat_id: $chat, text: $text}')   # собрать JSON безопасно
```

`-n` — без входных данных; `--arg имя значение` — передать shell-переменную (экранирование выполняет jq — не вставляйте переменные в JSON склейкой строк); `-c` — компактный вывод.

### 10.5. envsubst — шаблоны конфигурации

Пакет `gettext-base`. Подставляет значения переменных окружения вместо `$VAR`/`${VAR}` в тексте.

```bash
export DB_NAME=buh BACKUP_DIR=/backup/pg
envsubst '$DB_NAME $BACKUP_DIR' < backup.conf.tmpl > /etc/backup/buh.conf
```

Список переменных в одинарных кавычках ограничивает подстановку только ими. Без списка заменяются **все** конструкции `$ИМЯ`/`${ИМЯ}` в шаблоне, причём неопределённые переменные превращаются в пустую строку (так портятся, например, `$host` и `$remote_addr` в шаблоне конфигурации nginx).

### 10.6. expect — автоматизация интерактивных программ (кратко)

Пакет `expect`. Последнее средство, когда программа требует ввода с терминала и не имеет неинтерактивного режима.

```tcl
#!/usr/bin/expect -f
set timeout 60
spawn /opt/vendor/install.sh
expect "Install path:"   { send "/opt/app\r" }
expect "Continue?"       { send "y\r" }
expect eof
```

Сначала ищите штатный неинтерактивный режим: `apt-get -y` и `DEBIAN_FRONTEND=noninteractive`, `psql -c`/`-f`, `ssh -o BatchMode=yes`, ключи тихой установки у инсталляторов. Сценарии expect хрупкие (ломаются при изменении текста приглашений) и содержат ответы открытым текстом.

### 10.7. sshpass — и почему лучше ключи

`sshpass` подставляет пароль в запрос ssh: `sshpass -f /root/.ssh/nas.pass ssh user@host` (пароль из файла), `sshpass -e ssh …` (из переменной `SSHPASS`), `sshpass -p 'пароль' …` (**пароль виден всем в `ps`** — никогда так не делать).

Почему ключи лучше:
- пароль лежит на диске открытым текстом и даёт полный интерактивный доступ; ключ можно **ограничить** одной командой и адресом источника;
- ключ не перебирается по сети, парольный вход на сервере можно отключить совсем (`PasswordAuthentication no`);
- `BatchMode=yes` гарантирует, что скрипт не зависнет на запросе пароля.

```bash
ssh-keygen -t ed25519 -N '' -C 'backup@srv1c' -f /root/.ssh/backup_ed25519      # ключ без пароля для автоматизации
ssh-copy-id -i /root/.ssh/backup_ed25519.pub backup@nas.example.com              # установить на приёмник
ssh -i /root/.ssh/backup_ed25519 -o BatchMode=yes backup@nas.example.com true && echo "доступ есть"
```

Ограничение ключа на приёмнике (`~backup/.ssh/authorized_keys`, одна строка):

```text
restrict,from="10.0.0.5",command="rrsync -wo /srv/backup/srv1c" ssh-ed25519 AAAAC3... backup@srv1c
```

`restrict` запрещает проброс портов, агент, pty; `from=` — только с адреса сервера 1С; `command="rrsync …"` — ключ может только запускать rsync в пределах каталога (`-wo` — только запись, `-ro` — только чтение, подразумевает `-no-del` и `-no-lock`; `-no-del` — запретить `--delete*` и `--remove*`; `-munge` — включить `--munge-links`). Скрипт `rrsync` входит в пакет rsync и лежит в `/usr/bin/rrsync` — проверено по спискам файлов пакета для Ubuntu 22.04 (rsync 3.2.7 из обновлений; копия также в `/usr/share/rsync/scripts/rrsync`) и 24.04; man-страница — `man rrsync`. В rsync 3.2.7 rrsync — скрипт на Python 3 (man: «The python version was created by Wayne Davison»; в Ubuntu Server `python3` есть по умолчанию), более старые версии были на Perl. Чтобы скомпрометированный сервер 1С не мог стереть копии на приёмнике, используйте `rrsync -wo -no-del …` и не передавайте `--delete` с этой стороны (ротацию выполняет сам приёмник).

## 11. Безопасное хранение паролей и секретов

Общие правила:
1. **Не передавать секреты в аргументах команд** — командная строка любого процесса видна всем пользователям в `ps aux` и `/proc/PID/cmdline`.
2. Не хранить секреты в самом скрипте (скрипты читают многие, они попадают в git и в бэкапы). Секрет — в отдельном файле с правами `600` (владелец — пользователь, от которого работает задание) или `640 root:группа`.
3. Не выводить секреты в лог (`set -x`, `curl -v`, `msmtp -d`).
4. Лучший пароль — отсутствующий: peer-аутентификация PostgreSQL, SSH-ключи, шифрование открытым ключом.

### 11.1. PostgreSQL: peer-аутентификация и `~/.pgpass`

**Без пароля.** Задание, запущенное на самом сервере СУБД от системного пользователя `postgres`, подключается через Unix-сокет и проходит peer-аутентификацию (строка `local all postgres peer` в `pg_hba.conf`, в пакетах Ubuntu/PGDG она есть по умолчанию): `sudo -u postgres pg_dump -Fc buh`. Пароль не нужен нигде.

**`~/.pgpass`** (официальная документация libpq) — для подключений по TCP или от другого пользователя:

```bash
# файл в домашнем каталоге пользователя, который запускает pg_dump/psql
cat > ~/.pgpass <<'EOF'
# hostname:port:database:username:password
localhost:5432:*:backup:S3cretPass
10.0.0.20:5432:buh:backup:OtherPass
EOF
chmod 0600 ~/.pgpass
pg_dump -h localhost -U backup -w -Fc -f /backup/pg/buh.dump buh       # -w: никогда не спрашивать пароль
```

- Формат строки: `hostname:port:database:username:password`; в первых четырёх полях допустим `*`; используется **первая** подходящая строка (более точные — выше); символы `:` и `\` в значениях экранируются `\`.
- Права должны запрещать доступ группе и остальным (`chmod 0600`), **иначе файл молча игнорируется**.
- Другой путь к файлу: переменная `PGPASSFILE` или параметр подключения `passfile`.
- Для подключения через сокет ищется имя хоста `localhost` (если каталог сокета — каталог по умолчанию для данной сборки libpq).
- Переменная `PGPASSWORD` работает, но менее безопасна (окружение процесса доступно тому же пользователю и root через `/proc/PID/environ`) — использовать только для разовых ручных операций.
- Отдельная роль для дампов вместо суперпользователя (PostgreSQL 14+): `CREATE ROLE backup LOGIN PASSWORD '…'; GRANT pg_read_all_data TO backup;` — практика сообщества; для баз 1С чаще используют `postgres` через peer.

### 11.2. Файл с настройками и секретами для скрипта

```bash
sudo install -d -m 750 -o root -g postgres /etc/backup
sudo install -m 640 -o root -g postgres /dev/null /etc/backup/notify.conf
sudoedit /etc/backup/notify.conf
```

```bash
# /etc/backup/notify.conf — подключается командой source; синтаксис shell
TG_TOKEN='123456789:AAExampleExampleExampleExampleExample'
TG_CHAT_ID='-1001234567890'
MAIL_TO='admin@example.com'
MAIL_FROM='backup@example.com'
```

В скрипте: `source /etc/backup/notify.conf`. Файл, подключаемый через `source`, **исполняется как код** — он должен быть доступен на запись только root. Проверка прав: `stat -c '%a %U:%G %n' /etc/backup/*`.

Передача секрета программе без засветки в `ps`:
- через stdin или файл: `gpg --passphrase-file`, `curl --config -` (URL с токеном читается из stdin), `curl --netrc-file`, `sshpass -f`, `psql` + `.pgpass`;
- ввод вручную без эха: `read -rs -p 'Пароль: ' pass; echo`.

### 11.3. systemd: `EnvironmentFile=` и `LoadCredential=`

```ini
# /etc/systemd/system/pg-backup.service (фрагмент)
[Service]
User=postgres
# файл со строками ИМЯ=значение, права 600 root
EnvironmentFile=/etc/backup/backup.env
# секрет как файл, виден только этому сервису
LoadCredential=tg_token:/etc/backup/tg_token
```

- В юнитах systemd комментарий допустим только отдельной строкой (начинается с `#` или `;`); текст после значения в той же строке станет частью значения.
- `EnvironmentFile=` — файл со строками `ИМЯ=значение` (без `export`; строки с `#` и `;` — комментарии; префикс `-` перед путём — «не ругаться, если файла нет»). Значения из файла перекрывают `Environment=`. Файл читает systemd (root), поэтому права могут быть `600 root:root`, даже если сервис работает от `postgres`.
- Документация systemd прямо предупреждает: переменные окружения **не подходят для секретов** (наследуются дочерними процессами, видны через `systemctl show` и `/proc`). Для секретов предназначен механизм credentials.
- `LoadCredential=ИМЯ:ПУТЬ` — systemd копирует файл в приватный каталог сервиса; путь к каталогу — в `$CREDENTIALS_DIRECTORY`. В скрипте: `TG_TOKEN=$(< "$CREDENTIALS_DIRECTORY/tg_token")`. Данные доступны только пользователю сервиса; суммарный лимит — 1 МБ на юнит.
- `LoadCredentialEncrypted=` / `SetCredentialEncrypted=` + утилита `systemd-creds encrypt` — секрет хранится на диске зашифрованным (ключом хоста и/или TPM2).

### 11.4. Прочее

- **msmtp:** пароль SMTP — в конфигурации с правами `600`, либо `passwordeval "cat /etc/backup/smtp.pass"`.
- **rclone:** ключи в `~/.config/rclone/rclone.conf` (права `600`); конфигурацию можно зашифровать паролем (`rclone config` → пункт установки пароля). Для автоматизации пароль передаётся переменной окружения `RCLONE_CONFIG_PASS` либо ключом `--password-command "команда"` (программа, печатающая пароль) — подтверждено rclone.org/docs, раздел «Configuration encryption»; там же предупреждение: забытый пароль конфигурации восстановить нельзя.
- **Пароль администратора кластера 1С** для утилиты `rac` — в файле `600`, читать в переменную и передавать параметром (`--cluster-user=ИМЯ --cluster-pwd=ПАРОЛЬ`; для администратора центрального сервера — `--agent-user`/`--agent-pwd`, для базы — `--infobase-user`/`--infobase-pwd`). Пароль в аргументе кратковременно виден в `ps` — запускайте такие скрипты только на доверенном сервере. ⚠ не подтверждено: имена параметров приведены по встроенной справке `rac` (по памяти) и материалам сообщества; документация `rac` на ИТС закрыта подпиской, поэтому утверждение «другого способа передать пароль (файл, переменная окружения) нет» не проверено — посмотрите `rac help cluster` на своём сервере.
- **cron:** не пишите секреты в строку crontab — вывод и сама команда попадают в почту (`MAILTO`) и журнал.

## 12. Уведомления: почта и Telegram

### 12.1. Почта через msmtp

`msmtp` — лёгкий SMTP-клиент: отправляет письмо через внешний почтовый сервер (не требует настройки полноценного MTA). Пакеты: `msmtp` (клиент) и `msmtp-mta` (ставит msmtp в роли системного `sendmail`, чтобы работали `mail`, cron `MAILTO` и т. п.).

```bash
sudo apt install msmtp msmtp-mta mailutils
```

Конфигурация: системная — `/etc/msmtprc`, пользовательская — `~/.msmtprc` (или `$XDG_CONFIG_HOME/msmtp/config`); пользовательская имеет приоритет.

```text
# /etc/msmtprc  или  ~/.msmtprc   (права 600: в файле пароль)
defaults
auth           on
tls            on
tls_trust_file /etc/ssl/certs/ca-certificates.crt
logfile        ~/.msmtp.log

account        main
host           smtp.example.com
port           587
tls_starttls   on
from           backup@example.com
user           backup@example.com
password       СЕКРЕТНЫЙ_ПАРОЛЬ

account default : main
```

- Порт 587 — STARTTLS (`tls_starttls on`, это умолчание); порт 465 — TLS с первого байта: `port 465` и `tls_starttls off`.
- Вместо `password` можно `passwordeval "cat /etc/backup/smtp.pass"`.
- Если задание работает не от root (например, от `postgres`), а конфигурация общая, файл `/etc/msmtprc` с правами `600 root` ему недоступен. Что делать — зависит от версии (проверено по changelog и `debian/NEWS` пакета msmtp):
  - **Ubuntu 24.04 и 26.04 (msmtp 1.8.24 / 1.8.32): бинарник msmtp НЕ setgid.** Бит SetGID убран в пакете 1.8.22-1 («Remove SetGID bit on msmtp for security reasons»), поэтому старый рецепт «`chmod 640 /etc/msmtprc; chgrp msmtp /etc/msmtprc`» здесь **не работает**. Рабочие варианты: отдельный файл `~postgres/.msmtprc` (т. е. `/var/lib/postgresql/.msmtprc`, права `600`, владелец `postgres`) либо общий `/etc/msmtprc` с правами `640 root:ГРУППА`, где ГРУППА — группа, в которую входят нужные пользователи (например, `postgres`), либо вызывать `msmtp -C /путь/к/файлу`.
  - **Ubuntu 22.04 (msmtp 1.8.16):** бинарник setgid `msmtp` (введено в 1.8.3-1), рецепт `640 root:msmtp` работает.
- **AppArmor.** Пакет содержит профиль `/etc/apparmor.d/usr.bin.msmtp`. Включать ли его, спрашивает debconf-вопрос `msmtp/apparmor` («Enable AppArmor support?», значение по умолчанию — **false**, т. е. при обычной установке профиль не активен — так в исходниках пакета Debian 1.8.28-3; пакеты Ubuntu — пересборки Debian без изменений, но фактическое состояние на своём сервере обязательно проверьте); переключить: `sudo dpkg-reconfigure msmtp`, проверить: `sudo aa-status | grep msmtp`. Если профиль включён (режим enforce), msmtp может читать только `/etc/msmtprc`, `/etc/aliases`, `/etc/netrc`, `~/.msmtp*`, `~/.config/msmtp/*`, `~/.netrc`, писать лог только в `~/.msmtp*.log`, `~/.cache/msmtp/*.log` и `/var/log/msmtp`; под `~` понимается переменная AppArmor `@{HOME}` (по умолчанию в `/etc/apparmor.d/tunables/home` это `/home/*` и `/root`), поэтому `/var/lib/postgresql/.msmtprc` и `logfile` в произвольном месте будут **отклонены**. Для `passwordeval` разрешён ограниченный набор помощников (`cat`, `head`, `gpg`, `gpg2`, `pass`, `secret-tool` и др.). Отказы видны в `journalctl -k | grep -i apparmor`; свои правила добавляют в `/etc/apparmor.d/local/usr.bin.msmtp` и перечитывают: `sudo apparmor_parser -r -T -W /etc/apparmor.d/usr.bin.msmtp`.

```bash
# проверка связи с сервером и сертификата
msmtp --serverinfo --account=main

# отправка: письмо с заголовками на stdin, получатели — из заголовков (-t)
printf 'To: admin@example.com\nSubject: test\n\nПроверка связи с %s\n' "$(hostname -s)" | msmtp -t

# через mail (mailutils) — нужен msmtp-mta
echo "Дамп buh создан" | mail -s "backup OK $(hostname -s)" admin@example.com
mail -s "журнал бэкапа" -A /var/log/pg_backup/pg_backup.log admin@example.com < /dev/null    # вложение (-A — GNU mailutils)

msmtp -d -t < message.txt        # отладка SMTP-диалога (в выводе может быть пароль!)
```

Письмо с темой на русском нужно кодировать по RFC 2047 (`Subject: =?UTF-8?B?<base64 от темы>?=`) и указывать кодировку тела (`Content-Type: text/plain; charset=UTF-8`) — готовая функция `send_mail` есть в скрипте `notify.sh` (раздел 13.1). Коды возврата msmtp — стандартные sendmail-коды (`sysexits.h`): 0 — успех.

### 12.2. Telegram Bot API через curl

Подготовка: создать бота у `@BotFather` (получить токен вида `123456789:AA…`), написать боту любое сообщение (или добавить его в группу), узнать `chat_id` — вызвать `getUpdates` и найти поле `chat.id` (у групп — отрицательное число).

Официальные факты Bot API (версия 10.3 от 24.08.2026):
- адрес запроса: `https://api.telegram.org/bot<ТОКЕН>/ИМЯ_МЕТОДА`, только HTTPS; методы GET и POST; параметры — в строке запроса, `application/x-www-form-urlencoded`, `application/json` или `multipart/form-data` (для файлов);
- ответ — JSON с полем `ok` (true/false); при ошибке — `error_code` и `description`;
- `sendMessage`: обязательные `chat_id` и `text` (1–4096 символов); полезные необязательные: `parse_mode` (`HTML` или `MarkdownV2`), `disable_notification`, `message_thread_id` (тема в группе-форуме);
- `sendDocument`: `chat_id`, `document` (файл), `caption` (до 1024 символов); через multipart бот может отправить файл до **50 МБ**;
- в режиме `HTML` символы `<`, `>`, `&` в тексте нужно заменять на `&lt;`, `&gt;`, `&amp;`; в `MarkdownV2` экранируется длинный список символов (`_ * [ ] ( ) ~ > # + - = | { } . !` и обратная кавычка) — для служебных уведомлений проще слать **без** `parse_mode`.

```bash
TG_TOKEN='123456789:AAExample'      # в реальном скрипте — из файла с правами 600
TG_CHAT_ID='-1001234567890'

# простое сообщение; URL с токеном передаётся через stdin (--config -), чтобы токен не был виден в ps
curl --silent --show-error --fail-with-body --max-time 20 --retry 3 --retry-delay 5 \
     --data-urlencode "chat_id=${TG_CHAT_ID}" \
     --data-urlencode "text=Дамп buh на $(hostname -s) создан: $(date '+%F %T')" \
     --config - <<< "url = \"https://api.telegram.org/bot${TG_TOKEN}/sendMessage\""

# отправить файл (лог) с подписью
curl -sS --fail-with-body --max-time 120 \
     -F "chat_id=${TG_CHAT_ID}" -F "caption=Лог бэкапа $(hostname -s)" \
     -F "document=@/var/log/pg_backup/pg_backup.log" \
     --config - <<< "url = \"https://api.telegram.org/bot${TG_TOKEN}/sendDocument\""

# узнать chat_id и проверить токен (вручную, один раз)
curl -sS "https://api.telegram.org/bot${TG_TOKEN}/getMe" | jq .
curl -sS "https://api.telegram.org/bot${TG_TOKEN}/getUpdates" | jq '.result[].message.chat'
```

Пояснения к ключам curl: `--data-urlencode` корректно кодирует кириллицу, пробелы и переводы строк; `--fail-with-body` (curl ≥ 7.76) — ненулевой код возврата (22) при HTTP-ошибке, тело ответа с `description` при этом выводится; `--max-time` — общий таймаут (без него зависший запрос подвесит скрипт); `--retry` — повтор при временных ошибках (включая HTTP 429). Если сервер ходит в интернет через прокси: `--proxy http://proxy:3128` или переменная `https_proxy`.

## 13. Готовые скрипты

Скрипты ниже написаны под строгий режим и стиль, который проходит `shellcheck`; логика проверена вычиткой, но **на целевом сервере не запускалась** (эта база знаний собиралась без доступа к нему). Перед вводом в эксплуатацию: `bash -n файл`, `shellcheck файл`, ручной пробный запуск, проверка уведомления об ошибке (например, указать несуществующую базу).

⚠ не подтверждено запуском: при рецензировании (10.10.2026) все шесть скриптов (`snapshot_rsync.sh`, `notify.sh`, `pg_backup.sh`, `cleanup_old.sh`, `check_services.sh`, `srv1c_restart.sh`) повторно вычитаны построчно — синтаксических и логических ошибок не найдено, но **ни `bash -n`, ни `shellcheck`, ни пробный запуск не выполнялись** (на машине, где собиралась база знаний, запускать что-либо запрещено). Внесённые при рецензии изменения: в `pg_backup.sh` ловушки ставятся до взятия блокировки (иначе сбой открытия lock-файла не приводил к уведомлению), в `snapshot_rsync.sh` добавлена проверка точки монтирования. Порядок приёмки на сервере:

```bash
for f in notify.sh pg_backup.sh cleanup_old.sh check_services.sh srv1c_restart.sh snapshot_rsync.sh; do
    bash -n "$f" && shellcheck -s bash "$f" || echo "ПРОБЛЕМА: $f"
done
sudo -u postgres /usr/local/bin/pg_backup.sh; echo "код: $?"       # затем проверить лог, дамп, .sha256
sudo env DRY_RUN=1 /usr/local/bin/cleanup_old.sh                   # пробный прогон очистки (env передаёт переменную сквозь sudo)
```

Запускайте `pg_backup.sh` **всегда от одного и того же пользователя** (`postgres`): lock-файл в `/run/lock` и лог создаёт тот, кто запустил скрипт первым. Если первым его запустил root, последующий запуск от `postgres` упадёт с «Permission denied» на открытии lock-файла (права `600` из-за `umask 077`). Обратная ситуация тоже возможна: при включённой защите ядра `fs.protected_regular` (документация ядра, sysctl/fs; значение на сервере — `sysctl fs.protected_regular`, 1 или 2 означает «включено») в общедоступном каталоге со sticky-битом, каким является `/run/lock`, открыть с `O_CREAT` чужой файл не может даже root — поэтому `sudo flock /run/lock/pg_backup.lock …` при lock-файле, принадлежащем `postgres`, тоже завершится отказом. Лечение: `sudo rm /run/lock/pg_backup.lock; sudo chown -R postgres:postgres /var/log/pg_backup`.

Общая подготовка:

```bash
sudo install -d -m 750 -o root     -g postgres /etc/backup                 # настройки и секреты
sudo install -d -m 750 -o postgres -g postgres /backup/pg /var/log/pg_backup
sudo install -d -m 755 -o root     -g root     /var/lib/check_services
sudo apt install curl jq msmtp msmtp-mta zstd shellcheck
# после копирования скриптов:
sudo install -m 755 -o root -g root     notify.sh         /usr/local/bin/
sudo install -m 750 -o root -g postgres pg_backup.sh      /usr/local/bin/
sudo install -m 750 -o root -g root     cleanup_old.sh check_services.sh /usr/local/bin/
sudo install -m 750 -o root -g root     srv1c_restart.sh  /usr/local/sbin/
```

### 13.1. (г) Уведомления: `notify.sh` — Telegram и почта

Используется остальными скриптами. Настройки — в `/etc/backup/notify.conf` (раздел 11.2); способ, для которого параметры не заданы, пропускается.

```bash
#!/usr/bin/env bash
# /usr/local/bin/notify.sh — уведомление в Telegram и/или на почту.
# Использование:  notify.sh "Тема" "Текст"
#                 команда 2>&1 | notify.sh "Тема"      (текст со stdin)
# Код возврата: 0 — доставлено всеми настроенными способами, 1 — хотя бы один не сработал.
set -uo pipefail
export LC_ALL=C.UTF-8          # без UTF-8-локали обрезка текста может разорвать многобайтный символ

CONF=${NOTIFY_CONF:-/etc/backup/notify.conf}
TG_TOKEN=''; TG_CHAT_ID=''; MAIL_TO=''; MAIL_FROM=''
if [[ -r $CONF ]]; then
    # shellcheck source=/dev/null
    source "$CONF"
fi

subject=${1:-"Уведомление от $(hostname -s)"}
if (( $# >= 2 )); then
    body=$2
elif [[ ! -t 0 ]]; then
    body=$(cat)
else
    body=''
fi

send_telegram() {
    local text resp
    text="${subject}"$'\n'"${body}"
    text=${text:0:4000}                        # лимит sendMessage — 4096 символов
    if ! resp=$(curl --silent --show-error --fail-with-body --max-time 20 \
                     --retry 3 --retry-delay 5 \
                     --data-urlencode "chat_id=${TG_CHAT_ID}" \
                     --data-urlencode "text=${text}" \
                     --config - <<< "url = \"https://api.telegram.org/bot${TG_TOKEN}/sendMessage\"" 2>&1); then
        echo "notify: Telegram: ${resp}" >&2
        return 1
    fi
}

send_mail() {
    local subj_b64
    subj_b64=$(printf '%s' "$subject" | base64 -w0)
    {
        if [[ -n $MAIL_FROM ]]; then printf 'From: %s\n' "$MAIL_FROM"; fi
        printf 'To: %s\n' "$MAIL_TO"
        printf 'Subject: =?UTF-8?B?%s?=\n' "$subj_b64"
        printf 'MIME-Version: 1.0\n'
        printf 'Content-Type: text/plain; charset=UTF-8\n'
        printf 'Content-Transfer-Encoding: 8bit\n\n'
        printf '%s\n' "$body"
    } | msmtp -t
}

rc=0
if [[ -n $TG_TOKEN && -n $TG_CHAT_ID ]]; then
    send_telegram || rc=1
fi
if [[ -n $MAIL_TO ]]; then
    if ! send_mail; then
        echo "notify: не удалось отправить почту" >&2
        rc=1
    fi
fi

# дублируем в системный журнал: сообщение не потеряется, даже если сеть недоступна
flat=${body//$'\n'/; }
logger -t notify -p user.notice -- "${subject}: ${flat:0:500}"
exit "$rc"
```

Проверка: `notify.sh "Тест" "Проверка связи"`; `journalctl -t notify -n 5`. Вызывайте скрипт всегда с двумя аргументами, если stdin вызывающего скрипта занят (например, внутри `while read`).

Ограничения `notify.sh`, о которых стоит знать:
- тема письма кодируется одним «encoded-word» (`=?UTF-8?B?…?=`); RFC 2047 ограничивает длину одного такого слова 75 символами (это примерно 20–25 кириллических букв). Более длинные темы большинство почтовых систем всё равно принимает, но строго по стандарту их нужно разбивать на несколько слов — держите темы короткими;
- текст для Telegram обрезается до 4000 символов; длинный лог отправляйте файлом (`sendDocument`, раздел 12.2);
- токен бота попадает в аргументы только внутри here-string для `curl --config -` и в `ps` не виден, но `bash -x notify.sh` напечатает его в трассировке — не публикуйте такой вывод;
- если сеть недоступна, уведомление останется только в журнале (`journalctl -t notify`) — поэтому мониторинг «бэкап не пришёл» (отсутствие сообщения об успехе) надёжнее, чем ожидание сообщения об ошибке.

### 13.2. (а) Резервное копирование PostgreSQL: `pg_backup.sh`

Что делает: блокировка от параллельного запуска → проверка места и доступности сервера → для каждой базы `pg_dump -Fc` во временный файл с таймаутом → проверка кода возврата, непустого размера и читаемости оглавления (`pg_restore -l`) → атомарное переименование → SHA-256 → ротация (только после успешного дампа, с сохранением минимум N копий) → дамп ролей (`pg_dumpall --globals-only`) → уведомление при любой ошибке.

```bash
#!/usr/bin/env bash
# /usr/local/bin/pg_backup.sh — логический бэкап баз PostgreSQL (pg_dump -Fc) с проверкой и ротацией.
# Запуск: от пользователя postgres (peer-аутентификация через сокет) по cron или systemd timer.
set -Eeuo pipefail
shopt -s inherit_errexit
export LC_ALL=C.UTF-8
umask 077                                   # дампы и логи доступны только владельцу

# ------------------------------ настройки ------------------------------
DATABASES=(buh zup)                         # базы для копирования
BACKUP_DIR=/backup/pg                       # каталог на диске (НЕ /tmp: в Ubuntu 26.04 это tmpfs)
KEEP_DAYS=14                                # удалять дампы старше N суток...
KEEP_MIN=3                                  # ...но всегда оставлять N последних дампов каждой базы
COMPRESS='zstd:6'                           # PostgreSQL 16+; для 15 и старше: COMPRESS='6' (gzip)
PG_BIN=''                                   # каталог утилит, если их нет в PATH (Postgres Pro: /opt/pgpro/std-17/bin)
DUMP_TIMEOUT=6h                             # предельная длительность одного дампа
MIN_FREE_GB=20                              # не начинать, если свободно меньше
LOCK_FILE=/run/lock/pg_backup.lock
LOG_FILE=/var/log/pg_backup/pg_backup.log
NOTIFY=/usr/local/bin/notify.sh
export PGHOST=/var/run/postgresql PGPORT=5432 PGUSER=postgres    # пароль (если нужен) — только из ~/.pgpass
# PGHOST — каталог Unix-сокета. /var/run/postgresql — пакеты Ubuntu/PGDG. У Postgres Pro каталог может быть другим
# (часто /tmp): узнать командой  psql -Atc 'SHOW unix_socket_directories'  и подставить сюда.
# ------------------------------------------------------------------------

if [[ -n $PG_BIN ]]; then PATH="$PG_BIN:$PATH"; fi

log() { printf '%s [%d] %s\n' "$(date '+%F %T')" "$$" "$*"; }

mkdir -p "$BACKUP_DIR" "${LOG_FILE%/*}"
if [[ -t 1 ]]; then exec > >(tee -a "$LOG_FILE") 2>&1; else exec >>"$LOG_FILE" 2>&1; fi

tmp_file=''
failed=()

on_exit() {
    local rc=$?
    trap - EXIT
    if [[ -n $tmp_file ]]; then rm -f -- "$tmp_file"; fi
    if (( rc != 0 )); then
        log "ЗАВЕРШЕНО С ОШИБКОЙ, код $rc; не скопировано: ${failed[*]:-см. лог}"
        "$NOTIFY" "[FAIL] pg_backup на $(hostname -s)" \
                  "Код $rc. Не скопировано: ${failed[*]:-см. лог}. Лог: $LOG_FILE" || true
    fi
    exit "$rc"
}
trap on_exit EXIT
trap 'exit 130' INT
trap 'exit 143' TERM
trap 'log "сбой в строке $LINENO: «$BASH_COMMAND» вернула $?"' ERR

# блокировка берётся ПОСЛЕ установки ловушек: если lock-файл не открылся (чужой владелец, нет прав),
# скрипт завершится с ошибкой через on_exit и отправит уведомление, а не «умрёт молча»
exec 9>"$LOCK_FILE"
if ! flock -n 9; then
    log "уже выполняется другой экземпляр — выхожу"
    exit 0
fi

rotate() {
    local db=$1 f
    local -a all=()
    local pattern="${db}_20[0-9][0-9]-[0-9][0-9]-[0-9][0-9]_[0-9][0-9][0-9][0-9].dump"
    # в именах дата и время, поэтому сортировка по имени = сортировка по возрасту (новые — первыми)
    mapfile -t all < <(find "$BACKUP_DIR" -maxdepth 1 -type f -name "$pattern" -printf '%f\n' | sort -r)
    for f in "${all[@]:KEEP_MIN}"; do                       # первые KEEP_MIN не трогаем никогда
        if [[ -n $(find "$BACKUP_DIR/$f" -mtime +"$KEEP_DAYS" -print) ]]; then
            log "ротация: удаляю $f"
            rm -f -- "$BACKUP_DIR/$f" "$BACKUP_DIR/$f.sha256"
        fi
    done
}

# --- предварительные проверки ---
free_kb=$(df -Pk -- "$BACKUP_DIR" | awk 'NR==2 {print $4}')
if (( free_kb / 1024 / 1024 < MIN_FREE_GB )); then
    log "мало места в $BACKUP_DIR: $(( free_kb / 1024 / 1024 )) ГБ, нужно не меньше $MIN_FREE_GB"
    failed+=("нет места на диске")
    exit 1
fi
if ! pg_isready -q -t 10; then
    log "PostgreSQL не принимает подключения"
    failed+=("сервер СУБД недоступен")
    exit 1
fi

stamp=$(date +%F_%H%M)
log "=== старт; базы: ${DATABASES[*]}; $(pg_dump --version) ==="

# --- дампы баз ---
for db in "${DATABASES[@]}"; do
    out="$BACKUP_DIR/${db}_${stamp}.dump"
    tmp_file="$out.partial"
    started=$SECONDS
    log "дамп базы $db -> $out"
    if timeout "$DUMP_TIMEOUT" pg_dump --format=custom --compress="$COMPRESS" \
               --no-password --lock-wait-timeout=600000 --file="$tmp_file" "$db" \
       && [[ -s $tmp_file ]] \
       && pg_restore --list "$tmp_file" >/dev/null
    then
        mv -- "$tmp_file" "$out"
        ( cd "$BACKUP_DIR" && sha256sum -- "${out##*/}" > "${out##*/}.sha256" )
        log "готово: $db, размер $(du -h -- "$out" | cut -f1), $(( SECONDS - started )) с"
        rotate "$db"
    else
        rc=$?
        log "ОШИБКА: дамп базы $db не создан (код $rc; 124 = превышен таймаут $DUMP_TIMEOUT)"
        rm -f -- "$tmp_file"
        failed+=("$db")
    fi
    tmp_file=''
done

# --- роли и табличные пространства (в дамп отдельной базы не входят) ---
tmp_file="$BACKUP_DIR/globals_${stamp}.sql.partial"
if pg_dumpall --globals-only --no-password --file="$tmp_file"; then
    mv -- "$tmp_file" "$BACKUP_DIR/globals_${stamp}.sql"
    find "$BACKUP_DIR" -maxdepth 1 -type f -name 'globals_*.sql' -mtime +"$KEEP_DAYS" -delete
else
    log "ОШИБКА: pg_dumpall --globals-only"
    rm -f -- "$tmp_file"
    failed+=("globals")
fi
tmp_file=''

if (( ${#failed[@]} > 0 )); then
    exit 1                                  # on_exit запишет итог в лог и отправит уведомление
fi
log "=== все дампы созданы успешно ==="
# при желании — уведомлять и об успехе:
# "$NOTIFY" "[OK] pg_backup на $(hostname -s)" "Базы: ${DATABASES[*]}" || true
# при желании — сразу отправить копию на другой сервер:
# rsync -a --timeout=600 -e 'ssh -i ~/.ssh/backup_ed25519 -o BatchMode=yes' "$BACKUP_DIR"/ backup@nas:/srv/backup/pg/
```

Пояснения:
- **Код возврата pg_dump**: 0 — успех, ненулевой — ошибка (в документации PostgreSQL коды отдельно не описаны; это общее поведение утилит PostgreSQL). Одной проверки кода мало: дамп пишется во временный файл `*.partial` и получает «боевое» имя только после всех проверок — недописанный файл никогда не выглядит как готовый бэкап.
- `--lock-wait-timeout=600000` (мс) — не ждать вечно блокировку таблиц, если в базе идёт, например, реструктуризация из Конфигуратора.
- `-Fc` выбран потому, что это один файл, сжатый, с выборочным и параллельным (`pg_restore -j`) восстановлением. Для очень больших баз — `-Fd -j N` (тогда `tmp_file`/`out` — каталоги, проверки и ротацию нужно адаптировать).
- Файл `globals_*.sql` содержит хэши паролей ролей — `umask 077` обязателен.
- Сервер 1С на время `pg_dump` останавливать не требуется: дамп согласован на момент начала (снимок MVCC).
- Скрипт рассчитан на запуск от `postgres`. При запуске от другого пользователя: `PGUSER=backup`, пароль в `~/.pgpass`, права на `BACKUP_DIR` и `LOG_FILE`.
- **Postgres Pro** (в т. ч. сборка «для 1С»): задайте `PG_BIN` (`/opt/pgpro/std-NN/bin` или `/opt/pgpro/1c-NN/bin`) и проверьте `PGHOST`. Подтверждено 11.10.2026 чтением пакета `postgrespro-1c-16-server` 16.14-1.noble: сокет у сборки Postgres Pro находится в `/tmp` (в `postgresql.conf.sample` — `#unix_socket_directories = '/tmp'`, а скрипт `pg-setup` проверяет занятость порта по файлу `/tmp/.s.PGSQL.<порт>`), а не в `/var/run/postgresql`, как у пакетов Ubuntu/PGDG; фактическое значение на сервере — `SHOW unix_socket_directories;`. При неверном каталоге `pg_isready` вернёт 2, и скрипт завершится на предварительной проверке с уведомлением.
- `pg_dump` должен быть **той же мажорной версии, что и сервер, или новее** (документация: «pg_dump cannot dump from PostgreSQL servers newer than its own major version; it will refuse to even try»). Если на машине стоят клиентские утилиты нескольких версий, первая строка лога (`pg_dump --version`) покажет, какая реально используется.
- Формат `-Fc` сжимает данные в том же процессе, что и выгрузка; уровень `zstd:6` — разумная середина. Нагрузку на рабочий сервер можно снизить, запуская скрипт через `nice -n 10 ionice -c2 -n7` (в юните systemd — `Nice=`/`IOSchedulingClass=`, как в разделе 14.2).

Восстановление из такого дампа:

```bash
cd /backup/pg && sha256sum -c buh_2026-10-10_0130.dump.sha256           # 1. целостность файла
sudo -u postgres psql -X -f /backup/pg/globals_2026-10-10_0130.sql postgres    # 2. роли (на новом сервере)
sudo -u postgres createdb -T template0 -O postgres buh_restore          # 3. пустая база
sudo -u postgres pg_restore -j 4 --exit-on-error -d buh_restore /backup/pg/buh_2026-10-10_0130.dump   # 4. данные
sudo -u postgres psql -X -d buh_restore -c 'ANALYZE;'                    # 5. статистика планировщика
```

Кодировка и локаль новой базы должны совпадать с исходной (посмотреть у исходной: `psql -l`, столбцы Encoding/Collate/Ctype). `createdb -T template0` без уточнений берёт умолчания кластера; если они другие — задайте явно: `createdb -T template0 -E UTF8 -l ru_RU.UTF-8 -O postgres buh_restore` (локаль должна быть сгенерирована в ОС: `locale -a | grep ru_RU`).

`pg_restore` по умолчанию продолжает работу после ошибок и в конце выводит их количество; `-e` (`--exit-on-error`) — остановиться на первой; `-1` — всё в одной транзакции (несовместимо с `-j`). Регулярно выполняйте пробное восстановление в тестовую базу — это единственная настоящая проверка бэкапа.

### 13.3. (б) Очистка старых файлов: `cleanup_old.sh`

```bash
#!/usr/bin/env bash
# /usr/local/bin/cleanup_old.sh — удаление старых файлов по списку правил.
# Пробный прогон (ничего не удаляет):  DRY_RUN=1 cleanup_old.sh
set -Eeuo pipefail

DRY_RUN=${DRY_RUN:-0}

# формат правила: каталог|маска имени|старше N суток|глубина поиска
RULES=(
    '/backup/pg|*.dump|30|1'
    '/backup/pg|*.sha256|30|1'
    '/backup/pg|globals_*.sql|30|1'
    '/backup/pg|*.partial|2|1'
    '/srv/1c/exchange/archive|*.zip|60|3'
)

clean() {
    local dir=$1 mask=$2 days=$3 depth=$4
    # предохранители: только абсолютный существующий путь, не корень; числа — числа
    if [[ -z $dir || $dir != /* || $dir == / || ! -d $dir ]]; then
        echo "пропуск: некорректный или отсутствующий каталог '$dir'" >&2
        return 0
    fi
    if [[ ! $days =~ ^[0-9]+$ || ! $depth =~ ^[0-9]+$ ]]; then
        echo "пропуск: неверные числа в правиле для '$dir'" >&2
        return 0
    fi
    local -a action=(-print)
    if (( DRY_RUN == 0 )); then action+=(-delete); fi
    find "$dir" -xdev -maxdepth "$depth" -type f -name "$mask" -mtime +"$days" "${action[@]}"
}

suffix=''
if (( DRY_RUN != 0 )); then suffix=' [пробный прогон — ничего не удалено]'; fi

for rule in "${RULES[@]}"; do
    IFS='|' read -r dir mask days depth <<< "$rule"
    echo "--- $(date '+%F %T') $dir/$mask старше $days сут.$suffix"
    clean "$dir" "$mask" "$days" "$depth"
done
```

Однострочники для частых случаев:

```bash
# удалить дампы старше 30 суток (сначала посмотреть список, заменив -delete на -print)
find /backup/pg -maxdepth 1 -type f -name '*.dump' -mtime +30 -delete

# оставить только 10 самых новых дампов базы buh (независимо от возраста)
find /backup/pg -maxdepth 1 -type f -name 'buh_*.dump' -printf '%T@ %p\n' \
  | sort -rn | tail -n +11 | cut -d' ' -f2- | xargs -r -d '\n' rm -f --

# сжать логи старше 7 дней и удалить сжатые старше 90
find /var/log/myapp -type f -name '*.log' -mtime +7 -exec zstd -q --rm {} +
find /var/log/myapp -type f -name '*.log.zst' -mtime +90 -delete

# удалить пустые каталоги
find /srv/1c/exchange -mindepth 1 -type d -empty -delete
```

Правила безопасности: каталог — константа или проверенная переменная (`"${dir:?}"`); всегда `-type f`, `-maxdepth`, конкретная маска `-name`; никогда не запускать очистку «вслепую» по результату неудачного `cd`; ротацию бэкапов выполнять **после** успешного создания новой копии, а не до.

### 13.4. (в) Проверка сервисов 1С и PostgreSQL с уведомлением: `check_services.sh`

Проверяет: состояние systemd-юнитов, наличие процессов `ragent`/`rmngr`/`rphost`, TCP-порты 1540/1541, ответ PostgreSQL (`pg_isready`: 0 — принимает подключения, 1 — отклоняет, 2 — не отвечает, 3 — проверка не выполнена), заполнение дисков. Уведомление отправляется только при **изменении** состояния (появилась проблема, изменился список проблем, всё восстановилось) — без спама каждые 5 минут.

```bash
#!/usr/bin/env bash
# /usr/local/bin/check_services.sh — проверка сервера 1С, PostgreSQL и дисков; уведомление при изменении состояния.
# Запуск: от root каждые 5 минут (cron или systemd timer). Код возврата: 0 — всё в порядке, 1 — есть проблемы.
set -uo pipefail                 # без -e: проверки штатно возвращают ненулевые коды
export LC_ALL=C.UTF-8
PATH=/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin

# ------------------------------ настройки ------------------------------
SRV1C_UNIT=''                            # пусто = определить автоматически; иначе 'srv1cv8-8.3.27.1859@default.service'
SRV1C_USER=usr1cv8
SRV1C_PORTS=(1540 1541)                  # ragent и rmngr (рабочие процессы rphost — диапазон 1560:1591)
PG_UNIT='postgresql@18-main.service'     # Postgres Pro: 'postgrespro-std-17.service'
PG_HOST=/var/run/postgresql              # каталог сокета или имя хоста (Postgres Pro: проверить SHOW unix_socket_directories, часто /tmp)
PG_PORT=5432
PG_BIN=''                                # каталог с pg_isready, если его нет в PATH
DISK_PATHS=(/ /var/lib/postgresql /backup /home/usr1cv8)
DISK_LIMIT=90                            # порог заполнения, %
STATE_FILE=/var/lib/check_services/state
NOTIFY=/usr/local/bin/notify.sh
# ------------------------------------------------------------------------

if [[ -n $PG_BIN ]]; then PATH="$PG_BIN:$PATH"; fi
problems=()

detect_1c_unit() {
    # шаблон вида srv1cv8-8.3.27.1859@.service -> экземпляр srv1cv8-8.3.27.1859@default.service
    local tpl
    tpl=$(systemctl list-unit-files --type=service --no-legend 'srv1cv8-*@.service' 2>/dev/null \
          | awk '{print $1}' | sort -V | tail -n 1)
    if [[ -n $tpl ]]; then printf '%s\n' "${tpl/@./@default.}"; fi
}

check_unit() {
    local unit=$1 state
    state=$(systemctl is-active "$unit" 2>/dev/null)
    if [[ $state != active ]]; then
        problems+=("служба $unit: ${state:-unknown}")
    fi
}

check_proc() {
    local name=$1
    if ! pgrep -u "$SRV1C_USER" -x "$name" >/dev/null; then
        problems+=("нет процесса 1С: $name")
    fi
}

check_port() {
    local port=$1
    if ! timeout 3 bash -c "exec 3<>/dev/tcp/127.0.0.1/$port" 2>/dev/null; then
        problems+=("порт $port/tcp не отвечает")
    fi
}

check_pg() {
    local rc=0
    pg_isready -q -h "$PG_HOST" -p "$PG_PORT" -t 5 || rc=$?
    case $rc in
        0) ;;
        1) problems+=("PostgreSQL отклоняет подключения (запуск или восстановление)") ;;
        2) problems+=("PostgreSQL не отвечает ($PG_HOST:$PG_PORT)") ;;
        *) problems+=("pg_isready завершился с кодом $rc (нет утилиты или неверные параметры)") ;;
    esac
}

check_disk() {
    local path=$1 used
    if [[ ! -d $path ]]; then return 0; fi
    used=$(df -P -- "$path" | awk 'NR==2 {sub("%", "", $5); print $5}')
    if [[ $used =~ ^[0-9]+$ ]] && (( used >= DISK_LIMIT )); then
        problems+=("диск $path заполнен на ${used}%")
    fi
}

# --- проверки ---
if [[ -z $SRV1C_UNIT ]]; then SRV1C_UNIT=$(detect_1c_unit); fi
if [[ -n $SRV1C_UNIT ]]; then
    check_unit "$SRV1C_UNIT"
else
    problems+=("юнит сервера 1С не найден (systemctl list-unit-files 'srv1cv8-*')")
fi
for p in ragent rmngr rphost; do check_proc "$p"; done
for port in "${SRV1C_PORTS[@]}"; do check_port "$port"; done
check_unit "$PG_UNIT"
check_pg
for d in "${DISK_PATHS[@]}"; do check_disk "$d"; done

# --- сравнение с прошлым состоянием и уведомление ---
if (( ${#problems[@]} == 0 )); then
    current=OK
else
    current=$(printf '%s\n' "${problems[@]}")
fi
mkdir -p "${STATE_FILE%/*}"
previous=$(cat "$STATE_FILE" 2>/dev/null || echo OK)

if [[ $current != "$previous" ]]; then
    if [[ $current == OK ]]; then
        subject="[OK] $(hostname -s): службы восстановлены"
        text="Все проверки пройдены: $(date '+%F %T')"
    else
        subject="[ALERT] $(hostname -s): проблем — ${#problems[@]}"
        text=$current
    fi
    logger -t check_services -p daemon.warning -- "$subject: ${current//$'\n'/; }"
    if "$NOTIFY" "$subject" "$text"; then
        printf '%s\n' "$current" > "$STATE_FILE"     # запоминаем состояние только после успешной отправки
    fi
fi

[[ $current == OK ]]
```

Замечания:
- если установлено несколько версий платформы, автоопределение берёт шаблон с наибольшим номером версии — надёжнее задать `SRV1C_UNIT` явно;
- имя юнита PostgreSQL: пакеты Ubuntu/PGDG — `postgresql@<версия>-<кластер>.service` (`postgresql@18-main`; `postgresql.service` — лишь «зонтик», он active даже при упавшем кластере); Postgres Pro Standard — `postgrespro-std-17` (подтверждено документацией Postgres Pro 17: служба и пакет называются одинаково). У сборки «для 1С» пакет называется `postgrespro-1c-NN` — подтверждено содержимым публичного репозитория `repo.postgrespro.ru/1c/` (ветки `1c-14` … `1c-18`, сборки для focal/jammy/noble/resolute); что служба называется так же (`postgrespro-1c-NN.service`), следует из аналогии со Standard и материалов сообщества ⚠ не подтверждено документом вендора. Проверить на месте: `systemctl list-units 'postgres*'`;
- проверка порта средствами bash (`/dev/tcp`) не требует `nc`; при желании: `nc -z -w 3 127.0.0.1 1541`;
- более глубокая проверка 1С (список сеансов, рабочих процессов) — утилитой `rac` через сервер администрирования `ras` (порт 1545) — см. статьи раздела `kb/1c`.

### 13.5. (д) Остановка и запуск сервера 1С с очисткой сеансовых данных: `srv1c_restart.sh`

Фон: в каталоге данных кластера (`/home/usr1cv8/.1cv8/1C/1cv8/`, в юните — переменная `SRV1CV8_DATA`) лежит каталог `reg_<порт>` (обычно `reg_1541`), а в нём — каталоги `snccntx<UUID>` с сеансовыми данными. Их удаление при остановленном сервере — распространённый приём сообщества при «зависших» сеансах, ошибках сеансовых данных, разрастании каталога. Официальной статьи ИТС с такой процедурой для Linux найти не удалось (⚠) — применять осознанно.

**Нельзя удалять**: файл списка кластеров `1cv8wsrv.lst`, реестр кластера `reg_1541/1CV8Clst.lst` (в нём базы и администраторы кластера), каталоги баз `reg_1541/<UUID базы>/` с журналом регистрации (`1Cv8Log`) и индексом полнотекстового поиска (`1Cv8FTxt`).

⚠ не подтверждено (состояние на 10.10.2026, повторная проверка рецензентом): документация платформы на ИТС и статья `its.1c.ru/db/metod8dev/content/5953/hdoc` («Установка программы "1С:Предприятие" в ОС Linux») закрыты подпиской, страницы Инфостарта отдавали HTTP 429. Поэтому **не сверены с первоисточником**: (1) сама допустимость удаления `snccntx*` на Linux; (2) точные имена и регистр букв файлов `1cv8wsrv.lst` и `1CV8Clst.lst` в Linux (ФС чувствительна к регистру); (3) содержимое штатного юнита `srv1cv8-<версия>@.service` (`User=`, `Environment=SRV1CV8_DATA=…`, существующие `ExecStartPre=`). Перед первым применением проверьте на своём сервере:

```bash
systemctl cat 'srv1cv8-*@default.service'                    # User=, SRV1CV8_DATA, ExecStart*, TimeoutStopSec
sudo ls -la /home/usr1cv8/.1cv8/1C/1cv8/                      # ожидается 1cv8wsrv.lst и каталог reg_1541
sudo ls -la /home/usr1cv8/.1cv8/1C/1cv8/reg_1541/ | head -30  # ожидается 1CV8Clst.lst, snccntx*, каталоги баз (UUID)
sudo du -sh /home/usr1cv8/.1cv8/1C/1cv8/reg_1541/snccntx*     # размер сеансовых данных
```

Скрипт ниже удаляет **только** каталоги, имя которых начинается с `snccntx`, и только внутри `reg_*`; файлы `*.lst` и каталоги баз он не трогает при любом регистре их имён. Первый раз выполните вручную по шагам (`stop` → посмотреть, что лежит в `reg_1541` → `clean` → `start`) и заранее сделайте архив каталога кластера (раздел 2.5).

```bash
#!/usr/bin/env bash
# /usr/local/sbin/srv1c_restart.sh — остановка сервера 1С, очистка сеансовых данных, запуск.
# Запуск от root:  srv1c_restart.sh [restart|stop|start|clean]     (по умолчанию restart)
set -Eeuo pipefail
export LC_ALL=C.UTF-8
PATH=/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin

# ------------------------------ настройки ------------------------------
SRV1C_UNIT='srv1cv8-8.3.27.1859@default.service'   # точное имя: systemctl list-units 'srv1cv8*'
SRV1C_USER=usr1cv8
CLUSTER_DIR=/home/usr1cv8/.1cv8/1C/1cv8            # каталог данных кластера (SRV1CV8_DATA)
STOP_WAIT=120                                      # секунд ждать завершения процессов после stop
START_WAIT=60                                      # секунд ждать появления rmngr после start
NOTIFY=/usr/local/bin/notify.sh
# ------------------------------------------------------------------------

log() { printf '%s %s\n' "$(date '+%F %T')" "$*"; logger -t srv1c_restart -- "$*"; }

on_error() {
    local rc=$?
    log "ОШИБКА (код $rc) в строке ${BASH_LINENO[0]}"
    "$NOTIFY" "[FAIL] перезапуск 1С на $(hostname -s)" "Код $rc; журнал: journalctl -t srv1c_restart" || true
    exit "$rc"
}
trap on_error ERR

procs_alive() { pgrep -u "$SRV1C_USER" -x 'ragent|rmngr|rphost' >/dev/null; }

stop_1c() {
    log "останавливаю $SRV1C_UNIT"
    systemctl stop "$SRV1C_UNIT"
    local waited=0
    while procs_alive && (( waited < STOP_WAIT )); do
        sleep 2
        waited=$(( waited + 2 ))
    done
    if procs_alive; then
        log "процессы 1С не завершились за $STOP_WAIT с — посылаю SIGKILL"
        pkill -KILL -u "$SRV1C_USER" -x 'ragent|rmngr|rphost' || true
        sleep 3
    fi
    if procs_alive; then
        log "процессы 1С всё ещё работают — прерываю операцию"
        return 1
    fi
    log "сервер 1С остановлен"
}

clean_session_data() {
    if procs_alive; then
        log "сервер 1С работает — очистка запрещена"
        return 1
    fi
    if [[ ! -d $CLUSTER_DIR ]] || ! compgen -G "$CLUSTER_DIR/reg_*" >/dev/null; then
        log "каталог кластера не найден или в нём нет reg_*: $CLUSTER_DIR"
        return 1
    fi
    local reg d
    local -a dirs
    shopt -s nullglob
    for reg in "$CLUSTER_DIR"/reg_*/; do
        dirs=("$reg"snccntx*/)
        for d in "${dirs[@]}"; do
            log "удаляю сеансовые данные: $d"
            rm -rf -- "$d"
        done
    done
    shopt -u nullglob
}

start_1c() {
    log "запускаю $SRV1C_UNIT"
    systemctl start "$SRV1C_UNIT"
    local waited=0
    until systemctl is-active --quiet "$SRV1C_UNIT" && pgrep -u "$SRV1C_USER" -x rmngr >/dev/null; do
        if (( waited >= START_WAIT )); then
            log "сервер 1С не запустился за $START_WAIT с"
            return 1
        fi
        sleep 2
        waited=$(( waited + 2 ))
    done
    log "сервер 1С запущен"
}

if (( EUID != 0 )); then echo "нужны права root" >&2; exit 1; fi
if ! systemctl cat "$SRV1C_UNIT" >/dev/null 2>&1; then
    echo "юнит $SRV1C_UNIT не найден; проверьте: systemctl list-units 'srv1cv8*'" >&2
    exit 1
fi

case ${1:-restart} in
    stop)    stop_1c ;;
    start)   start_1c ;;
    clean)   clean_session_data ;;
    restart) stop_1c
             clean_session_data
             start_1c
             log "перезапуск с очисткой сеансовых данных выполнен" ;;
    *)       echo "использование: ${0##*/} [restart|stop|start|clean]" >&2; exit 2 ;;
esac
```

Замечания:
- **Имя юнита содержит версию платформы.** После обновления 1С (например, 8.3.27.1859 → 8.3.27.2000; номера сборок здесь и в примерах **условные** — подставляйте фактический номер из `ls /opt/1cv8/x86_64/` или `systemctl list-units 'srv1cv8*'`) юнит называется иначе — скрипт и расписание нужно обновить (либо определять имя автоматически, как в 13.4).
- Перезапуск обрывает сеансы всех пользователей и фоновые задания — только в технологическое окно, после предупреждения пользователей.
- `systemctl stop` сам ждёт завершения процессов (`TimeoutStopSec`; если в юните 1С не задано своё значение, действует `DefaultTimeoutStopSec` менеджера — в systemd по умолчанию 90 с) и затем убивает оставшиеся в контрольной группе юнита; цикл ожидания и `pkill` в скрипте — дополнительная страховка. Фактическое значение: `systemctl show -p TimeoutStopUSec srv1cv8-…@default.service`.
- Порты сервера 1С по умолчанию: 1540 (агент `ragent`), 1541 (менеджер кластера `rmngr`), 1560–1591 (рабочие процессы `rphost`), 1545 (`ras`).
- Типовая последовательность «холодного» ночного обслуживания: `srv1c_restart.sh stop` → `sudo -u postgres /usr/local/bin/pg_backup.sh` → `srv1c_restart.sh clean` → `srv1c_restart.sh start`.
- Альтернатива без скрипта (практика сообщества): drop-in к юниту, очищающий сеансовые данные при каждом запуске службы; тогда достаточно `systemctl restart`. Drop-in привязан к имени юнита и после обновления платформы его нужно создать заново:

```ini
# sudo systemctl edit srv1cv8-8.3.27.1859@default.service
[Service]
ExecStartPre=/bin/sh -c 'rm -rf /home/usr1cv8/.1cv8/1C/1cv8/reg_*/snccntx*'
```

Что про этот drop-in проверено, а что нет:
- По systemd.service(5): команды `ExecStartPre=` выполняются перед `ExecStart=`; если команда без префикса `-` завершилась с ошибкой, юнит считается сбойным и `ExecStart=` **не запускается**. `rm -rf` при отсутствии совпадений шаблона возвращает 0 (ключ `-f`), поэтому пустой каталог запуск не сломает; но если каталог кластера у вас в другом месте, команда просто ничего не удалит — проверьте путь по `SRV1CV8_DATA`.
- `ExecStartPre=` выполняется с теми же `User=`/`Group=`, что и основной процесс (полные права дал бы префикс `+`). Каталог кластера принадлежит пользователю сервера 1С, так что прав достаточно в обоих случаях.
- Drop-in добавляет команду к уже имеющимся `ExecStartPre=` юнита (директива накапливается), не заменяя их. После правки: `systemctl daemon-reload` (`systemctl edit` делает это сам), проверка — `systemctl cat srv1cv8-…@default.service`.
- ⚠ не подтверждено: сама идея взята из статьи Инфостарта (infostart.ru/1c/tools/1934093), открыть которую не удалось; штатный юнит 1С не читался. При `Restart=on-failure` (если он задан в штатном юните) очистка будет выполняться и при **автоматическом** перезапуске службы после сбоя, т. е. сеансовые данные будут удаляться при каждом старте без исключений; оцените, приемлемо ли это, или используйте скрипт выше только в технологическое окно.

## 14. Запуск по расписанию

### 14.1. cron

В Ubuntu Server это пакет `cron` (служба `cron.service`). Где лежат задания:

| Место | Особенности |
|---|---|
| `crontab -e` (личный crontab пользователя) | 5 полей времени + команда; хранится в `/var/spool/cron/crontabs/` (вручную не редактировать). `crontab -l` — показать; `sudo crontab -u postgres -e` — чужой |
| `/etc/crontab`, `/etc/cron.d/ИМЯ` | системные; **дополнительное поле «пользователь»** перед командой. Имя файла в `/etc/cron.d` — только буквы, цифры, `_` и `-` (файл `backup.conf` или `job.sh` будет проигнорирован); владелец root, без права записи для группы/остальных |
| `/etc/cron.hourly`, `cron.daily`, `cron.weekly`, `cron.monthly` | исполняемые скрипты, запускаются через `run-parts`; имя — те же ограничения (без точек!) |

Формат строки:

```text
# ┌──────── минута (0-59)
# │ ┌────── час (0-23)
# │ │ ┌──── день месяца (1-31)
# │ │ │ ┌── месяц (1-12 или jan..dec)
# │ │ │ │ ┌ день недели (0-7; 0 и 7 — воскресенье; или mon..sun)
# │ │ │ │ │
  30 1 * * *   команда
```

`*` — любое значение; `1,15` — список; `1-5` — диапазон; `*/5` — шаг; `@reboot`, `@hourly`, `@daily` (= `0 0 * * *`), `@weekly`, `@monthly`, `@yearly` — сокращения. Если заданы **и** день месяца, **и** день недели, задание выполняется, когда совпало **любое** из них.

Пример системного файла для наших скриптов:

```text
# /etc/cron.d/srv1c-maintenance
SHELL=/bin/bash
PATH=/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin
MAILTO=""

# мин час дом мес дн  пользователь  команда
30   1   *   *   *    postgres      /usr/local/bin/pg_backup.sh
*/5  *   *   *   *    root          /usr/local/bin/check_services.sh >/dev/null 2>&1
15   3   *   *   *    root          /usr/local/bin/cleanup_old.sh >>/var/log/cleanup_old.log 2>&1
0    4   *   *   0    root          /usr/local/sbin/srv1c_restart.sh restart >>/var/log/srv1c_restart.log 2>&1
45   2   *   *   *    root          mountpoint -q /mnt/disk2 && flock -n /run/lock/offsite.lock rsync -a --delete --exclude='*.partial' /backup/pg/ /mnt/disk2/pg/ >>/var/log/offsite.log 2>&1
```

В последней строке `mountpoint -q` не даёт rsync писать на корневой диск, если `/mnt/disk2` не смонтирован, а `--exclude='*.partial'` не копирует недописанный дамп, если `pg_backup.sh` к 02:45 ещё работает. Надёжнее вызывать копирование из самого `pg_backup.sh` после успешных дампов (закомментированная строка в конце скрипта), а не по отдельному расписанию.

(Для каждого задания выбирайте **один** механизм — либо строку cron, либо systemd timer из раздела 14.2, иначе задание будет запускаться дважды.)

Окружение cron — главный источник проблем «вручную работает, по расписанию нет»:
- команды выполняет **`/bin/sh`** (dash), а не bash; задайте `SHELL=/bin/bash` в crontab или вынесите логику в скрипт с шебангом;
- **`PATH` урезан — на практике `/usr/bin:/bin`** для пользовательских crontab (в `/etc/crontab` Ubuntu свой PATH задан в начале файла); `~/.bashrc` и `~/.profile` не читаются. Утилиты из `/usr/local/bin`, `/usr/sbin`, `/opt/1cv8/…`, `/opt/pgpro/…/bin` не будут найдены (код 127) — задавайте `PATH` в crontab/скрипте или пишите полные пути. Оговорка: значение `/usr/bin:/bin` — из crontab(5) Debian и наблюдаемое поведение; crontab(5) пакета `cron` в Ubuntu 22.04 формулирует иначе («PATH is inherited from the environment») — не полагайтесь ни на то, ни на другое, задавайте `PATH` явно;
- в строках присваивания переменные не раскрываются: `PATH=$HOME/bin:$PATH` не сработает (crontab(5): значение «is not parsed for environmental substitutions or replacement of variables or tilde(~) expansion»);
- автоматически заданы `SHELL`, `HOME`, `LOGNAME` (и `PATH`, см. выше). Дополнительно cron в Debian/Ubuntu через PAM (`pam_env`) загружает `/etc/environment` и **локаль из `/etc/default/locale`** — так что `LANG` под cron обычно задана, но может отличаться от интерактивной сессии (там её меняет ещё и SSH-клиент через `SendEnv LANG LC_*`). Служба systemd получает окружение менеджера (посмотреть: `systemctl show-environment`), которое тоже может не совпадать с интерактивным. Поэтому в скриптах всё равно стоит `export LC_ALL=C.UTF-8` — результат не зависит от способа запуска;
- символ **`%`** в команде означает перевод строки, а всё после первого `%` подаётся команде на stdin — экранируйте: `date +\%F`;
- последняя строка файла должна заканчиваться переводом строки, иначе она игнорируется;
- вывод задания (stdout/stderr) cron отправляет письмом владельцу (или на `MAILTO`); если MTA не установлен, вывод **теряется** (в журнале: `(CRON) info (No MTA installed, discarding output)`). Поэтому всегда перенаправляйте: `>>/var/log/job.log 2>&1` (порядок именно такой) или `2>&1 | logger -t job`;
- `MAILTO=""` — не слать почту; `MAILTO=admin@example.com` — слать (нужен `msmtp-mta` или другой MTA).

Диагностика: `systemctl status cron`; `journalctl -u cron --since today`; `grep CRON /var/log/syslog`; проверить скрипт в «голом» окружении — см. команду `env -i …` в разделе 9.17. Условие «первая суббота месяца» из-за правила «день месяца ИЛИ день недели» пишется так: `0 3 1-7 * * [ "$(date +\%u)" = 6 ] && /usr/local/bin/job.sh`.

### 14.2. systemd timer (кратко)

Таймер — пара юнитов: `ИМЯ.service` (что запускать) и `ИМЯ.timer` (когда). По умолчанию таймер активирует одноимённый сервис.

```ini
# /etc/systemd/system/pg-backup.service
[Unit]
Description=PostgreSQL logical backup (pg_dump)
After=postgresql.service
OnFailure=notify-failure@%n.service

[Service]
Type=oneshot
User=postgres
Group=postgres
ExecStart=/usr/local/bin/pg_backup.sh
Nice=10
IOSchedulingClass=best-effort
IOSchedulingPriority=7
```

```ini
# /etc/systemd/system/pg-backup.timer
[Unit]
Description=Nightly PostgreSQL backup

[Timer]
OnCalendar=*-*-* 01:30:00
Persistent=true
RandomizedDelaySec=5min

[Install]
WantedBy=timers.target
```

```ini
# /etc/systemd/system/notify-failure@.service — универсальное уведомление о сбое любого юнита
[Unit]
Description=Failure notification for %i

[Service]
Type=oneshot
ExecStart=/usr/local/bin/notify.sh "[FAIL] %i на %H" "Юнит %i завершился с ошибкой. Смотреть: journalctl -u %i -n 50"
```

```bash
sudo systemctl daemon-reload
sudo systemctl enable --now pg-backup.timer        # включить таймер (не сервис!)
systemctl list-timers --all                        # когда сработает / когда срабатывал
sudo systemctl start pg-backup.service             # запустить задание вручную прямо сейчас
systemctl status pg-backup.service                 # результат последнего запуска
journalctl -u pg-backup.service --since yesterday  # вывод задания
systemd-analyze calendar "Mon..Fri *-*-* 02:30"    # проверить выражение и увидеть ближайшее срабатывание
sudo systemd-run --on-calendar='2026-10-11 03:00' --unit=once-restart /usr/local/sbin/srv1c_restart.sh   # разовое задание
```

`OnFailure=` дополняет уведомление из самого скрипта: он срабатывает и тогда, когда скрипт не смог сообщить об ошибке сам (не запустился, убит по таймауту или OOM killer). Если двойные уведомления не нужны — оставьте что-то одно. В шаблоне `notify-failure@.service` спецификатор `%i` — имя упавшего юнита, `%H` — имя хоста.

Параметры `[Timer]` (systemd.timer(5), systemd.time(7)):

| Параметр | Значение |
|---|---|
| `OnCalendar=` | календарное расписание: `[ДеньНедели] Год-Месяц-День Час:Мин:Сек`; можно указывать несколько раз. Сокращения: `minutely`, `hourly`, `daily` (= `*-*-* 00:00:00`), `weekly` (= `Mon *-*-* 00:00:00`), `monthly` (= `*-*-01 00:00:00`), `quarterly`, `yearly` |
| примеры | `*-*-* 01:30:00` — ежедневно в 01:30; `Mon..Fri *-*-* 02:30` — по будням; `Sun *-*-* 04:00` — по воскресеньям; `*-*-01 03:00` — первого числа; `*:0/15` — каждые 15 минут; `*-*-* 00/2:00` — каждые 2 часа |
| `OnBootSec=`, `OnUnitActiveSec=`, `OnUnitInactiveSec=` | монотонные таймеры: через N после загрузки / после последнего запуска / после последнего завершения сервиса (`OnBootSec=10min` + `OnUnitActiveSec=5min` — «каждые 5 минут») |
| `Persistent=true` | запоминать время последнего срабатывания на диске; если сервер был выключен в момент расписания — выполнить сразу после включения (только для `OnCalendar=`) |
| `AccuracySec=` | точность срабатывания, по умолчанию **1min** (таймер может сработать в пределах этого окна); для точности до секунды — `AccuracySec=1s` |
| `RandomizedDelaySec=` | случайная задержка от 0 до указанного значения |
| `Unit=` | какой юнит запускать, если имя отличается |

Отличия от cron:

| | cron | systemd timer |
|---|---|---|
| Вывод задания | почта или потеря; нужно перенаправлять вручную | автоматически в journald (`journalctl -u`) |
| Пропущенный запуск (сервер был выключен) | не выполняется | выполняется при `Persistent=true` |
| Наложение запусков | возможно (нужен `flock`) | невозможно: «if the unit to activate is already active… it is not restarted» |
| Окружение | минимальное, `/bin/sh` | задаётся в юните (`User=`, `Environment=`, `EnvironmentFile=`, `WorkingDirectory=`) |
| Ограничение ресурсов и зависимости | нет | `Nice=`, `CPUQuota=`, `MemoryMax=`, `After=`, `Requires=`, `OnFailure=` |
| Секреты | файлы | `LoadCredential=` (раздел 11.3) |
| Простота | одна строка | два файла |

Для `Type=oneshot` таймаут запуска по умолчанию отключён — подтверждено systemd.service(5), описание `TimeoutStartSec=`: «Defaults to DefaultTimeoutStartSec= set in the manager, except when Type=oneshot is used, in which case the timeout is disabled by default». Длительный бэкап не будет убит; ограничить можно `TimeoutStartSec=8h` или `timeout` внутри скрипта. Особенность `oneshot`: юнит не переходит в состояние `active` (после завершения он `inactive`/`failed`), поэтому результат последнего запуска смотрят так: `systemctl status pg-backup.service` или `systemctl show -p Result,ExecMainStatus pg-backup.service`.

## Типичные ошибки и подводные камни

| Симптом | Причина | Решение |
|---|---|---|
| `bad interpreter: /bin/bash^M` или `$'\r': command not found` | скрипт сохранён в Windows с окончаниями строк CRLF | `sed -i 's/\r$//' script.sh`; в редакторе выбрать LF |
| `Syntax error: "(" unexpected`, `[[: not found`, `set: Illegal option -o pipefail` | скрипт запущен через `sh` (dash): `sh script.sh`, шебанг `#!/bin/sh` или cron без `SHELL=/bin/bash` | шебанг `#!/usr/bin/env bash`, запускать `bash script.sh` или как исполняемый файл |
| Вручную работает, по cron — `command not found` (код 127) | в cron урезанный `PATH` (обычно `/usr/bin:/bin`), нет `~/.bashrc` | задать `PATH` в crontab/скрипте, полные пути (`/opt/pgpro/std-17/bin/pg_dump`) |
| Задание cron с `date +%F` не запускается или создаёт файл со странным именем | `%` в crontab — спецсимвол (перевод строки) | экранировать: `date +\%F`, либо вынести в скрипт |
| Файл в `/etc/cron.d` или `/etc/cron.daily` не выполняется | в имени есть точка (`backup.sh`), нет права `x` (для `cron.daily`), нет поля пользователя (для `cron.d`), нет перевода строки в конце | переименовать, `chmod +x`, добавить пользователя, проверить `journalctl -u cron` |
| rsync создал лишний уровень `/dst/src/…` или (с `--delete`) удалил не то | перепутан слеш в конце источника | `/src/` — содержимое; `/src` — сам каталог; сначала `-n -i` |
| `rsync --delete` очистил резервную копию | источник оказался пустым (не примонтирован диск) | `mountpoint -q` перед запуском, файл-маркер, `--max-delete=N` |
| rsync: `protocol version mismatch -- is your shell clean?` (код 12) | на удалённой стороне `.bashrc` что-то печатает или там нет rsync | убрать вывод из `.bashrc` для неинтерактивных сессий; установить rsync |
| rsync завершился кодом 23 | часть файлов не скопирована (нет прав, занято) | смотреть сообщения; запускать от root / `--rsync-path='sudo rsync'` |
| rsync завершился кодом 24 | файлы исчезли во время передачи | для «живых» каталогов считать успехом (см. 5.3) |
| После rsync жёсткие ссылки превратились в копии, место выросло | `-a` не включает `-H` | добавить `-H` |
| tar: `file changed as we read it`, код 1 | архивируются изменяющиеся файлы | останавливать сервис или архивировать снапшот; код 1 трактовать как предупреждение, 2 — как ошибку |
| tar: `Removing leading '/' from member names` | передан абсолютный путь | это не ошибка; писать `-C / etc` |
| tar распаковал файлы с чужими владельцами (числа вместо имён) | на другой машине другие UID/GID | создать пользователей с теми же ID или `chown -R` после распаковки |
| Скрипт «молча» продолжил работу после ошибки в конвейере (`pg_dump \| gzip`) | без `pipefail` код конвейера = код последней команды | `set -o pipefail`; проверять `PIPESTATUS` |
| Дамп есть, но он 0 байт или обрезан | не проверялся код возврата; кончилось место; запись сразу в «боевое» имя | писать в `*.partial`, проверять код, `-s`, `pg_restore -l`, затем `mv` |
| Скрипт завершается на `(( count++ ))` или `grep` без совпадений | `set -e`: выражение/команда вернули ненулевой код | `(( count += 1 ))`; `grep … \|\| true` |
| `value too great for base (error token is "08")` | число с ведущим нулём трактуется как восьмеричное | `$(( 10#$var ))` или `date +%-d` |
| `unbound variable` | `set -u` и обращение к незаданной переменной/аргументу | `${var:-}`; `${1:?подсказка}` |
| Переменные, изменённые в `cmd \| while read`, «не сохраняются» | тело цикла выполнено в подоболочке | `while …; done < <(cmd)` |

| pg_dump не принимает `-Z zstd` или `-Z lz4` (сообщение вида «unrecognized compression algorithm», «invalid compression level» или «not supported by this build») | pg_dump младше 16 (оба метода появились в 16) или сборка без соответствующей библиотеки | `-Z 6` (gzip) либо внешнее сжатие `-Z0 \| zstd` |

| `pg_dump: error: aborting because of server version mismatch` | pg_dump старше сервера (в PATH утилиты другой версии) | использовать pg_dump версии сервера (или новее): `PG_BIN`, полный путь |
| gpg в cron: `gpg: problem with the agent` / запрос пароля | нет `--batch --pinentry-mode loopback` или недоступен `~/.gnupg` | добавить ключи; задать `GNUPGHOME` |
| Telegram отвечает `400 Bad Request: can't parse entities` | включён `parse_mode`, а в тексте неэкранированные спецсимволы | слать без `parse_mode` либо экранировать |
| Telegram: `400 … strings must be encoded in UTF-8` или «кракозябры» | скрипт выполнился в локали `C`/`POSIX` (локаль под cron/systemd не та, что в интерактивной сессии): обрезка `${text:0:N}` разорвала многобайтный символ | `export LC_ALL=C.UTF-8` в скрипте |

| Скрипт перезапуска 1С сообщает «юнит не найден» после обновления платформы | в имени юнита зашита версия (`srv1cv8-8.3.XX.YYYY@default`) | обновить имя; автоопределение (13.4) |
| zstd/xz «съел» всю память/CPU, сервер 1С тормозит | `-T0` и высокий уровень в рабочее время | `nice`/`ionice`, `-T N` меньше числа ядер, умеренный уровень (3–6), запуск ночью |
| Письма от msmtp не уходят у пользователя `postgres` | нет доступа к `/etc/msmtprc` (600 root) или нет `~/.msmtprc`; на 24.04/26.04 msmtp больше не setgid, рецепт `640 root:msmtp` не действует; при включённом профиле AppArmor не читается `/var/lib/postgresql/.msmtprc` | отдельный `~postgres/.msmtprc` (600) либо `/etc/msmtprc` с `640 root:postgres`; проверить `aa-status \| grep msmtp` (раздел 12.1) |
| `pg_backup.sh` под cron: `/run/lock/pg_backup.lock: Permission denied` | lock-файл (или лог) создан другим пользователем при ручном запуске от root | запускать всегда от `postgres` (`sudo -u postgres …`); удалить lock-файл, вернуть владельца логу |
| `pg_isready`/`pg_dump`: `connection to server on socket "/var/run/postgresql/.s.PGSQL.5432" failed: No such file or directory` при работающем сервере | клиент ищет сокет не в том каталоге (другая сборка: пакеты Ubuntu/PGDG ↔ Postgres Pro) | `PGHOST=<каталог из SHOW unix_socket_directories>` или `-h 127.0.0.1` + `~/.pgpass` |
| Ctrl-C не останавливает скрипт, пока идёт `timeout … pg_dump` | `timeout` увёл команду в отдельную группу процессов | `timeout --foreground` при ручной отладке или `kill` PID `pg_dump` |
| `zstd`/`xz` без `-T` на Ubuntu 26.04 грузит несколько ядер, на 22.04/24.04 — одно | изменилось умолчание (zstd 1.5.7 — до 4 потоков, xz ≥ 5.6 — все ядра) | всегда указывать `-T N` явно |
