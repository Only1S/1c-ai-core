## Кратко

1. Первый взгляд за 60 секунд (чек-лист Брендана Грегга): `uptime` → `sudo dmesg -T | tail` → `vmstat 1` → `mpstat -P ALL 1` → `pidstat 1` → `iostat -xz 1` → `free -m` → `sar -n DEV 1` → `sar -n TCP,ETCP 1` → `top`. Нужен пакет `sysstat` (`sudo apt install sysstat`).
2. Load average в Linux считает не только готовые к выполнению задачи (R), но и задачи в непрерываемом сне (D, обычно ожидание диска). Высокий LA при простаивающем CPU — это диск или блокировки, а не нехватка процессора. Сравнивайте LA с `nproc`.
3. В `free -h` смотрите колонку `available`, а не `free`: `buff/cache` — это возвращаемая память. В procps 4.x (Ubuntu 24.04+) `used = total − available`; в procps 3.3.17 (22.04) `used = total − free − buffers − cache` — числа `used` между версиями несравнимы.
4. Признак реальной нехватки памяти — не «мало free», а устойчиво ненулевые `si`/`so` в `vmstat 1`, рост `majflt/s`, ненулевой `full` в `/proc/pressure/memory`, записи OOM killer в `journalctl -k`.
5. `iostat -xz 1`: `r_await`/`w_await` — среднее время запроса с учётом очереди (мс), `aqu-sz` — средняя длина очереди, `%util` — доля времени с активным вводом-выводом. Для SSD/NVMe/RAID/виртуальных дисков `%util` ≈ 100 % ещё не означает насыщения (так сказано в man iostat) — смотрите на await и очередь.
6. Первая строка `vmstat` и первый отчёт `iostat` — средние с момента загрузки, даже если задан интервал; `mpstat` и `pidstat` без интервала тоже показывают средние с загрузки (а `sar` без интервала читает файл истории за сегодня). Задавайте интервал и отбрасывайте первый отчёт: `iostat -xz -y 1` (есть во всех версиях), `vmstat -y 1` (только procps 4.x, Ubuntu 24.04+; в 22.04 опции `-y` у `vmstat` нет — просто игнорируйте первую строку).
7. `ps`-колонка `%CPU` — это отношение процессорного времени ко времени жизни процесса, а не мгновенная загрузка. Мгновенную загрузку дают `top`, `pidstat 1`.
8. `%CPU` в `top` считается относительно одного ядра: многопоточный `rphost` может показывать 400 % и больше. По потокам: `top -H -p <PID>` или `ps -L -p <PID>`.
9. Сигналы главному процессу PostgreSQL (postmaster): `SIGTERM` — smart shutdown, `SIGINT` — fast shutdown, `SIGQUIT` — immediate shutdown, `SIGHUP` — перечитать конфигурацию. `kill -9` на postmaster или на любой backend — аварийный сценарий: либо осиротевшие процессы и неосвобождённая разделяемая память, либо сброс всех сеансов и crash recovery.
10. Отдельному backend'у PostgreSQL: `SIGINT` = отменить текущий запрос (`pg_cancel_backend(pid)`), `SIGTERM` = завершить сеанс (`pg_terminate_backend(pid)`). Предпочитайте SQL-функции.
11. Останавливать сервер 1С и PostgreSQL нужно через `systemctl stop <юнит>`, а не `kill`. Имена юнитов: `postgresql@NN-main.service` (пакеты Ubuntu/PGDG), `postgrespro-1c-NN.service` (Postgres Pro), `srv1cv8-<версия>@default.service` (платформа 8.3.21+ — с этой версии 1С официально перешла с SystemV на systemd), `srv1cv83` (SysV-скрипт версий до 8.3.20 включительно). Точное имя: `systemctl list-units 'srv1cv8*' 'postgres*'`.
12. OOM killer: искать `journalctl -k -g 'out of memory|oom-kill|killed process'` (шаблон целиком в нижнем регистре — тогда `journalctl` ищет без учёта регистра). Защита postmaster — `oom_score_adj = -1000` плюс `PG_OOM_ADJUST_FILE=/proc/self/oom_score_adj` и `PG_OOM_ADJUST_VALUE=0`, чтобы дочерние процессы остались «убиваемыми» (официальная рекомендация PostgreSQL). В пакетах Debian/Ubuntu это уже сделано: юнит задаёт `OOMScoreAdjust=-900`, а `pg_ctlcluster` выставляет `PG_OOM_ADJUST_FILE`.
13. systemd по умолчанию (`DefaultOOMPolicy=stop`) при убийстве OOM killer'ом одного процесса юнита останавливает весь юнит. Проверьте: `systemctl show -p OOMPolicy <юнит>`.
14. Ограничения ресурсов — через cgroups v2 и systemd: `systemctl set-property <юнит> MemoryHigh=… MemoryMax=… CPUWeight=… CPUQuota=…`; разовый запуск с лимитами — `systemd-run -p …`. В Ubuntu 26.04 (systemd 259) cgroup v1 удалён полностью.
15. История нагрузки: `sysstat` (файлы `/var/log/sysstat/saDD`, чтение `sar -u/-r/-b/-d/-q/-n DEV -f файл`) и `atop` (файлы `/var/log/atop/atop_YYYYMMDD`, чтение `atop -r`). По умолчанию сбор sysstat в Ubuntu выключен — его надо включить.
16. Память процессов PostgreSQL нельзя суммировать по RSS: каждый backend показывает в RSS «потроганную» им часть `shared_buffers`. Считайте по PSS (`smem`, `/proc/<pid>/smaps_rollup`) или по `RssAnon` из `/proc/<pid>/status`.
17. `strace -p` и `gdb -p` замедляют или полностью приостанавливают процесс. На боевом `rphost`/postgres — только кратко и осознанно; для сводки достаточно `strace -c -f -p <PID>` на 10–20 секунд.
18. PSI (`/proc/pressure/{cpu,memory,io}`) — самый прямой показатель «процессам не хватает ресурса»: `some` — доля времени, когда хотя бы одна задача ждала ресурс, `full` — когда ждали все неидущие в простое задачи.
19. В виртуальной машине смотрите `st` (steal) в `top`/`vmstat`/`mpstat`: это время, когда гипервизор не дал vCPU. Но нулевой steal не доказывает отсутствие конкуренции на хосте — не все гипервизоры его сообщают: в ядре Linux учёт steal реализован для KVM, Xen и VMware (с ядра 5.7 и только если гипервизор поддерживает соответствующий гипервызов), а для Hyper-V на x86 такой реализации в основной ветке ядра нет — в госте Hyper-V `st` всегда 0 (подробности и оговорки — в разделе 7.5).
20. Удалённый, но открытый файл продолжает занимать место: `sudo lsof +L1`. Типичный случай — `rm` большого лога технологического журнала 1С или лога PostgreSQL при работающем процессе.

|---|---|---|---|
| `ragent` | агент сервера; главный процесс службы (Main PID юнита), порождает остальные | 1540 | параметры запуска: `-daemon`, `-port`, `-regport`, `-range`, `-d <каталог данных кластера>`, `-debug` |
| `rmngr` | менеджер кластера: реестр кластера, сервисы (блокировки, сеансовые данные, журнал регистрации, полнотекстовый поиск, лицензии) | 1541 | дочерний к `ragent` |

- Каталог установки: `/opt/1cv8/x86_64/<версия>/` (исполняемые файлы `ragent`, `rmngr`, `rphost`, `ras`, `rac`, `ibcmd`).
- Пользователь и группа ОС: `usr1cv8` / `grp1cv8`.
- Каталог данных кластера по умолчанию: `/home/usr1cv8/.1cv8/1C/1cv8/` (подкаталог `reg_1541`).
- Юнит systemd. Официально (список изменений платформы 8.3.21, раздел «Работа в ОС Linux»): начиная с 8.3.21 «прекращено использование подсистемы инициализации и управления службами SystemV», вместо неё используется systemd; «в состав дистрибутива включён systemd-сценарий запуска кластера серверов и сервера администрирования (ras)» и их конфигурационные файлы; SystemV-сценарий (служба `srv1cv83`) и его конфигурационный файл из дистрибутива удалены; после каждой смены версии платформы автозапуск кластера нужно настраивать заново. На практике это шаблон `srv1cv8-<версия>@.service`, лежащий в каталоге установки версии (`/opt/1cv8/x86_64/<версия>/`), экземпляр обычно `srv1cv8-<версия>@default.service` (пример с форума: `srv1cv8-8.3.23.1912@default.service`, Main PID — `ragent`); для сервера администрирования — отдельный юнит `ras-<версия>.service` (уточнено 10.10.2026: в документации 8.3.27 назван только юнит сервера `srv1cv8-A.B.C.D@.service`, юнит `ras` в ней не упоминается; ранее: точные имена файлов юнитов в официальном тексте не названы — сверяйте `ls /opt/1cv8/x86_64/<версия>/*.service`). Для версий до 8.3.20 включительно — SysV-служба `srv1cv83`. Точное имя на конкретной машине:

```bash
systemctl list-units --type=service --all 'srv1cv8*'
U1C=$(systemctl list-units --type=service --no-legend --plain 'srv1cv8*' | awk '{print $1; exit}')
systemctl status "$U1C"        # Main PID = ragent, ниже дерево процессов и их cgroup
systemctl cat "$U1C"           # что именно запускается, KillMode, лимиты
```

### 1.2. PostgreSQL

Официальное описание заголовков процессов — глава «Standard Unix Tools» документации PostgreSQL. Каждый backend выставляет заголовок вида `postgres: <пользователь> <база> <хост> <активность>`, где активность — `idle`, `idle in transaction`, имя команды (`SELECT`, `INSERT`, …) и суффикс `waiting`, если процесс ждёт блокировку другой сессии.

| Процесс (как виден в `ps`) | Что это |
|---|---|
| `/usr/lib/postgresql/NN/bin/postgres -D … -c config_file=…` | postmaster — главный процесс; принимает соединения, порождает остальные |
| `postgres: checkpointer` | контрольные точки: сброс «грязных» буферов на диск (пики записи) |
| `postgres: background writer` | фоновая запись буферов |
| `postgres: walwriter` | запись WAL |
| `postgres: autovacuum launcher` / `autovacuum worker <база>` | автоочистка |
| `postgres: logical replication launcher` | запускатель логической репликации (есть всегда) |
| `postgres: io worker N` | PostgreSQL 18+: рабочие асинхронного ввода-вывода (`io_method = worker` — по умолчанию, `io_workers = 3`); N — номер рабочего, с нуля (`io worker 0`, `1`, `2`). Вид заголовка подтверждён по исходному коду PostgreSQL 18 (`method_worker.c`: в заголовок пишется номер рабочего; `int io_workers = 3`), в документации он не описан |
| `postgres: parallel worker for PID N` | параллельный исполнитель запроса backend'а N |
| `postgres: usr1cv8 buh 127.0.0.1(48712) idle in transaction` | клиентский backend: роль, база, адрес(порт клиента), состояние |
| `postgres: startup recovering …` | восстановление после сбоя или реплика |

- Если задан `cluster_name`, он добавляется в заголовок: `postgres: 17/main: checkpointer`. В пакетах Debian/Ubuntu это происходит всегда: `pg_createcluster` копирует в `postgresql.conf` нового кластера параметры из `/etc/postgresql-common/createcluster.conf`, а там по умолчанию стоит `cluster_name = '%v/%c'` (то есть `17/main`; комментарий в файле — «Show cluster name in process title»), а также `log_line_prefix = '%m [%p] %q%u@%d '` и `ssl = on`. Следствие для скриптов: шаблон `grep '^postgres: '` находит и такие строки, а вот `grep '^postgres: checkpointer'` на Ubuntu ничего не найдёт — пишите `grep -E '^postgres: (NN/main: )?checkpointer'` или ищите по подстроке.
- Параметр `update_process_title = off` отключает обновление активности в заголовке.
- Пути (пакеты Ubuntu/PGDG): бинарники `/usr/lib/postgresql/NN/bin`, данные `/var/lib/postgresql/NN/main`, конфигурация `/etc/postgresql/NN/main`, лог `/var/log/postgresql/postgresql-NN-main.log`, юнит `postgresql@NN-main.service`.
- Пути (Postgres Pro для 1С): бинарники `/opt/pgpro/1c-NN/bin`, данные `/var/lib/pgpro/1c-NN/data`, юнит `postgrespro-1c-NN.service`.
- Для 1С состояние `idle in transaction` у backend'ов — обычное явление (платформа держит транзакцию открытой, пока выполняется серверный код между запросами). Тревожный признак — `idle in transaction` десятки минут и цепочка `waiting` за ним.

### 1.3. Быстрый обзор «что сейчас запущено»

```bash
# дерево процессов 1С и PostgreSQL с потреблением
ps -eo pid,ppid,user,stat,nlwp,pcpu,pmem,rss,etime,args --forest \
  | grep -E 'ragent|rmngr|rphost|ras |postgres' | grep -v grep

# сколько рабочих процессов и backend'ов
pgrep -c rphost
pgrep -u postgres -c postgres          # все процессы postgres, включая служебные

# какие порты слушают
sudo ss -ltnp | grep -E 'ragent|rmngr|rphost|ras|postgres'

# к какому юниту/cgroup относится произвольный PID
systemctl status <PID>
ps -o pid,unit,cgroup -p <PID>
```

## 2. Просмотр процессов: ps, pstree, pgrep/pkill, pidof

### 2.1. ps

`ps` понимает три стиля опций, которые можно смешивать: UNIX (с дефисом, `-ef`), BSD (без дефиса, `aux`), GNU (длинные, `--sort`). `ps aux` и `ps -aux` — не одно и то же.

| Вызов | Что показывает |
|---|---|
| `ps aux` | все процессы; колонки `USER PID %CPU %MEM VSZ RSS TTY STAT START TIME COMMAND` |
| `ps -ef` | все процессы; колонки `UID PID PPID C STIME TTY TIME CMD` (есть PPID) |
| `ps -eLf` | все потоки; добавляются `LWP` (TID потока) и `NLWP` (число потоков) |
| `ps -eo <поля>` | свой набор колонок |
| `ps -ef --forest` / `ps axf` | дерево процессов ASCII-графикой |
| `ps -C rphost -o …` | выбор по имени команды (не по полной строке) |
| `ps -u postgres -o …` | выбор по эффективному пользователю |
| `ps -p 1234,5678 -o …` | выбор по PID |
| `ps --ppid 1234` | дочерние процессы указанного PID |
| `ps -L -p 1234` / `ps -T -p 1234` | потоки одного процесса |
| `ps auxww` | не обрезать командную строку (два `w` — неограниченная ширина) |
| `ps -eo pid= -o comm=` | без заголовков (также `--no-headers`) |

Полезные поля для `-o`: `pid`, `ppid`, `tid`/`lwp`, `nlwp`, `user`, `stat` (или `s`/`state`), `pcpu` (`%cpu`), `pmem` (`%mem`), `rss` (резидентная память, КиБ), `vsz` (виртуальная, КиБ), `pss`, `uss` (procps 4.x; дорогое чтение smaps, чужие процессы — только root), `etime`/`etimes` (время жизни), `time`/`cputime` (накопленное CPU-время), `lstart` (полная дата запуска), `ni`, `pri`, `cls` (класс планирования), `rtprio`, `psr` (последний CPU), `comm` (имя), `args` (полная командная строка), `wchan`, `cgroup`, `unit` (юнит systemd), `oom`, `oomadj` (procps 4.x), `maj_flt`, `min_flt`.

Сортировка: `--sort=-pcpu` (минус — по убыванию), несколько ключей через запятую: `--sort=-rss,pid`.

Коды состояния (`STAT`): `R` — выполняется или в очереди на CPU; `S` — прерываемый сон; `D` — непрерываемый сон (обычно ввод-вывод); `I` — простаивающий поток ядра; `T` — остановлен сигналом управления заданиями; `t` — остановлен отладчиком; `Z` — зомби (завершён, родитель не забрал статус). Дополнительные символы: `<` — высокий приоритет, `N` — пониженный, `L` — есть заблокированные в памяти страницы, `s` — лидер сеанса, `l` — многопоточный, `+` — в группе переднего плана.

Важно: `%CPU` в `ps` — это «CPU-время / время жизни процесса» (по man: «It will not add up to 100% unless you are lucky»). Процесс, который час простаивал и минуту назад занял ядро целиком, покажет единицы процентов.

```bash
# топ-15 по CPU-времени за жизнь и по памяти
ps -eo pid,user,pcpu,pmem,rss,nlwp,etime,args --sort=-pcpu | head -16
ps -eo pid,user,rss,vsz,pmem,etime,args --sort=-rss | head -16

# рабочие процессы 1С: когда запущены, сколько потоков, память (МиБ)
ps -C rphost -o pid,lstart,etime,nlwp,pcpu,rss,args \
  | awk 'NR==1{print;next}{$10=sprintf("%dM",$10/1024);print}'

# backend'ы PostgreSQL: сколько всего, сколько ждут блокировку, сколько в открытой транзакции
ps -u postgres -o args= | grep -cE '^postgres: '
ps -u postgres -o args= | grep -cE ' waiting$'
ps -u postgres -o args= | grep -c 'idle in transaction'

# давно висящие idle in transaction (etime — время жизни процесса, не транзакции;
# длительность транзакции точнее смотреть в pg_stat_activity.xact_start)
ps -u postgres -o pid,etime,args | grep 'idle in transaction'

# потоки одного rphost (здесь — самого старого; подставьте нужный PID), самые занятые сверху
ps -L -p "$(pgrep -o rphost)" -o tid,psr,stat,pcpu,time,comm --sort=-pcpu | head

# процессы в непрерываемом сне (ждут диск) и зомби
ps -eo state,pid,ppid,user,args | awk '$1=="D" || $1=="Z"'
```

### 2.2. pstree

Дерево процессов (пакет `psmisc`). Потоки показываются в фигурных скобках.

| Флаг | Назначение |
|---|---|
| `-p` | показывать PID |
| `-a` | показывать аргументы командной строки |
| `-u` | показывать смену пользователя |
| `-s <PID>` | показать цепочку родителей указанного процесса |
| `-T` | скрыть потоки |
| `-t` | показывать имена потоков |
| `-l` | не обрезать длинные строки |
| `-h` | подсветить текущий процесс и его предков |

```bash
pstree -apT "$(pgrep -o ragent)"       # ragent → rmngr, rphost
pstree -ps "$(pgrep -n rphost)"        # от systemd до конкретного rphost
pstree -apT postgres                   # всё, что принадлежит пользователю postgres
```

### 2.3. pgrep, pkill, pidof

`pgrep` ищет процессы по регулярному выражению и печатает PID; `pkill` с теми же критериями посылает сигнал (по умолчанию `SIGTERM`). По умолчанию шаблон сравнивается с именем процесса (не более 15 символов); с `-f` — со всей командной строкой.

| Флаг | Назначение |
|---|---|
| `-u <user>` | по эффективному пользователю |
| `-f` | сравнивать со всей командной строкой |
| `-x` | точное совпадение имени |
| `-a` | печатать PID и полную командную строку |
| `-l` | печатать PID и имя |
| `-c` | только число совпадений |
| `-n` / `-o` | самый новый / самый старый |
| `-P <ppid>` | по родителю |
| `-d <разделитель>` | разделитель вывода (удобно `-d,` для `top -p`) |
| `-<SIG>` / `--signal <SIG>` | (pkill) какой сигнал послать |

```bash
pgrep -a ragent                        # PID и полная строка запуска агента
pgrep -c rphost                        # число рабочих процессов
pgrep -u postgres -fa 'idle in transaction'
top -p "$(pgrep -d, rphost)"           # top только по rphost (не более 20 PID)
pgrep -u usr1cv8 -l                    # все процессы пользователя 1С
```

Осторожно: `pkill -f postgres` или `pkill -9 -u postgres` убьёт всё, что совпало, включая postmaster. Перед `pkill` всегда выполняйте тот же запрос через `pgrep -a` и читайте список.

`pidof <имя>` — PID по точному имени программы, через пробел: `pidof rphost`; `pidof -s rphost` — только один PID.

## 3. Интерактивные мониторы: top, htop, atop, btop

### 3.1. top

Сводная область (по man top, procps 4.0.4):

- строка 1 — время, аптайм, число пользователей, load average за 1/5/15 минут;
- `Tasks` — всего, running, sleeping, stopped, zombie;
- `%Cpu(s)`: `us` — пользовательский код, `sy` — ядро, `ni` — пользовательский код с изменённым nice, `id` — простой, `wa` — простой в ожидании ввода-вывода, `hi` — аппаратные прерывания, `si` — программные прерывания, `st` — время, «украденное» гипервизором;
- `MiB Mem`: `total`, `free`, `used`, `buff/cache`; `MiB Swap`: `total`, `free`, `used`; `avail Mem` — оценка памяти, доступной новым приложениям без свопа.

Колонки процессов: `PID`, `USER`, `PR` (приоритет планировщика), `NI` (nice), `VIRT` (виртуальная память), `RES` (резидентная), `SHR` (разделяемая часть RES), `S` (состояние), `%CPU`, `%MEM`, `TIME+` (CPU-время с сотыми), `COMMAND`. Дополнительно через `f`: `SWAP`, `USED` (RES+SWAP), `nTH` (число потоков), `P` (последний CPU), `RSan`/`RSfd`/`RSsh` (анонимная / файловая / разделяемая части RES), `PSS`, `OOMs`/`OOMa`, `CGROUPS`.

Клавиши:

| Клавиша | Действие |
|---|---|
| `1` | по каждому CPU отдельно / сводно |
| `t` / `m` | переключить вид строк CPU / памяти |
| `P` / `M` / `T` / `N` | сортировка по %CPU / %MEM / TIME+ / PID |
| `<` `>` | сдвинуть колонку сортировки; `R` — обратный порядок; `x` — подсветить колонку сортировки |
| `c` | полная командная строка / имя программы |
| `H` | показать потоки |
| `V` | дерево процессов |
| `i` | скрыть простаивающие задачи |
| `u` / `U` | фильтр по пользователю (эффективному / любому) |
| `o` / `O` | фильтр по полю, например `COMMAND=rphost` или `%CPU>10.0` |
| `L`, `&` | поиск строки и следующее совпадение |
| `f` | выбор и порядок колонок |
| `e` / `E` | единицы памяти в списке задач / в сводке |
| `k` | послать сигнал процессу (по умолчанию `SIGTERM`) |
| `r` | изменить nice |
| `d` или `s` | интервал обновления |
| `I` | режим Irix/Solaris: в режиме Solaris %CPU делится на число CPU |
| `2`, `3` | сводка по NUMA-узлам |
| `W` | сохранить настройки (`~/.config/procps/toprc`) |
| `h` / `q` | справка / выход |

Опции командной строки: `-b` — пакетный режим (для записи в файл), `-n N` — число итераций, `-d сек` — интервал, `-p PID[,PID…]` — только эти PID (до 20), `-u пользователь`, `-H` — потоки, `-o поле` — сортировка (`-o %MEM`, `-o -PID`), `-O` — список имён полей, `-c` — командные строки, `-w N` — ширина вывода, `-i` — скрыть простаивающие, `-E k|m|g` и `-e k|m|g` — единицы памяти, `-1` — CPU по отдельности.

```bash
top -b -n 1 -o %CPU -c -w 200 | head -25          # срез «кто грузит CPU» в файл/на экран
top -b -n 1 -o %MEM -c -w 200 | head -25          # срез по памяти
top -b -d 5 -n 12 -c -w 200 > /var/tmp/top-$(date +%H%M).log   # минута наблюдений, шаг 5 с
top -H -p "$(pgrep -d, rphost)"                   # потоки рабочих процессов 1С
top -u postgres -c                                # только PostgreSQL с заголовками процессов
```

Замечание: первая итерация `top -b` показывает `%CPU` за короткий стартовый интервал; для точных чисел берите вторую и последующие (`-n 2` и смотреть последний блок).

### 3.2. htop

Цветной интерактивный монитор (пакет `htop`). Чем удобнее `top`: прокрутка, мышь, дерево, поиск, пометка нескольких процессов, встроенные `strace`/`lsof`.

| Клавиша | Действие |
|---|---|
| `F1`/`h` | справка |
| `F2`/`S` | настройка (метры в шапке, колонки, цвета) |
| `F3` или `/` | поиск; `F4` или `\` — фильтр по подстроке |
| `F5`/`t` | дерево процессов |
| `F6` или `<` `>` | выбор колонки сортировки; `P`/`M`/`T` — по CPU/памяти/времени; `I` — инвертировать |
| `F7`/`F8` | уменьшить/увеличить nice |
| `F9`/`k` | послать сигнал (выбор из списка) |
| `H` | скрыть/показать пользовательские потоки; `K` — потоки ядра |
| `u` | фильтр по пользователю |
| `p` | полный путь программы |
| `Space`, `c`, `U` | пометить процесс / с потомками / снять пометки |
| `a` | привязка к CPU (affinity) |
| `i` | приоритет ввода-вывода (ionice) |
| `e` | окружение процесса |
| `l` | открытые файлы (`lsof`) |
| `s` | трассировка системных вызовов (`strace`) |
| `Tab` | переключение вкладок-экранов, в том числе «I/O» (есть в htop 3.3.0 из 24.04 и новее; в htop 3.0.5 из 22.04 вкладок нет) |
| `x` | активные файловые блокировки процесса |
| `w` | командная строка процесса с переносом по строкам |
| `N` | сортировка по PID; `Z` — пауза обновления экрана |
| `F10`/`q` | выход |

Клавиши `e` (окружение) и `i` (приоритет ввода-вывода) в man-странице htop 3.3.0 не описаны, но перечислены во встроенной справке (`F1`); остальные строки таблицы сверены с man htop (noble).

```bash
htop -u postgres                 # только процессы пользователя
htop -p "$(pgrep -d, rphost)"    # только указанные PID
htop -t                          # сразу деревом
htop -d 20                       # интервал 2 секунды (единица — десятые доли секунды)
sudo htop                        # с root видны колонки ввода-вывода чужих процессов
```

В настройке (`F2`) полезно добавить метры давления PSI (CPU/IO/Memory pressure; в man-странице не описаны, набор зависит от версии htop), `Disk IO`, `Network IO` и колонки ввода-вывода и задержек. Имена колонок по man htop 3.3.0: `IO_READ_RATE` (заголовок `DISK READ`), `IO_WRITE_RATE` (`DISK WRITE`), `IO_RATE` (`DISK R/W`), `IO_PRIORITY` (`IO`), `RBYTES`/`WBYTES`, `PERCENT_CPU_DELAY` (`CPUD%`), `PERCENT_IO_DELAY` (`IOD%`), `PERCENT_SWAP_DELAY` (`SWAPD%`). Колонки задержек (`*_DELAY`) заполняются только при включённом учёте задержек `kernel.task_delayacct=1` (см. раздел 8.2); колонки ввода-вывода чужих процессов видны только root.

### 3.3. atop

`atop` (пакет `atop`, universe) одновременно показывает нагрузку на уровне системы и процессов и, главное, пишет историю. По умолчанию в Ubuntu после установки работает `atop.service`: снимок каждые 600 секунд в `/var/log/atop/atop_YYYYMMDD`, хранение 28 дней; настройки — `/etc/default/atop` (`LOGINTERVAL`, `LOGGENERATIONS`, `LOGPATH`, `LOGOPTS`).

Системные строки: `PRC` (CPU-время sys/user, число процессов и потоков, зомби), `CPU`/`cpu` (sys, user, irq, idle, wait, steal, guest — сводно и по ядрам), `CPL` (load average, переключения контекста, прерывания), `MEM`, `SWP`, `PAG` (сканирование страниц, swap in/out, OOM kills), `PSI`, `LVM`/`MDD`/`DSK` (занятость, чтения/записи, очередь), `NET`. Красный цвет — критический уровень, голубой — «почти критический» (80 % от критического порога). Пороги по умолчанию (man atop): CPU — 90 % занятости, сеть — 90 %, память — 90 %, swap — 80 %; диск — 90 % в atop 2.10 (24.04) и 70 % в atop 2.7.1 (22.04). Пороги меняются в `/etc/atoprc` или `~/.atoprc`.

| Клавиша | Действие |
|---|---|
| `g` / `m` / `d` / `n` | вид процессов: общий / память / диск / сеть (сеть по процессам требует модуль netatop) |
| `c` | полная командная строка |
| `s` / `v` | планирование / прочие характеристики |
| `p` / `u` | агрегировать по имени программы / по пользователю |
| `y` | показать потоки |
| `C` / `M` / `D` / `A` | сортировка по CPU / памяти / диску / автоматически по самому загруженному ресурсу |
| `P`, `U`, `/` | фильтр по имени процесса, пользователю, командной строке (regex) |
| `a` | все процессы / только активные |
| `1` | значения в пересчёте на секунду |
| `i` | сменить интервал; `z` — пауза |
| `t` / `T` | (при чтении файла) следующий / предыдущий снимок |
| `b` | (при чтении файла) перейти к времени |
| `q` | выход |

```bash
atop 5                                              # живой режим, шаг 5 с
atop -r                                             # сегодняшний файл истории
atop -r y -b 1400 -e 1500                           # вчера, с 14:00 до 15:00
atop -r /var/log/atop/atop_20261009 -b 0930         # конкретный день, начиная с 09:30
atopsar -c -r /var/log/atop/atop_20261009           # CPU в стиле sar из файла atop
atopsar -m -d -r y                                  # память и диски за вчера
```

Формат времени для `-b`/`-e` (сверено по man обеих версий): в atop 2.7.1 (22.04) — `[YYYYMMDD]hhmm`, в atop 2.10 (24.04) — `[YYYYMMDD]hhmm[ss]`. То есть запись `-b 1400` работает в обеих LTS, секунды (`-b 140030`) — только с 2.10; запись через двоеточие (`14:00`) относится к ещё более старым версиям atop и здесь не нужна. В man atop 2.10 (24.04) описаны также клавиши `B` (графический режим столбиками / текстовый), `X` (сведения cgroup v2 по процессам), `j`/`J` (агрегация и фильтр по контейнерам) — в atop 2.7.1 из 22.04 части этих режимов может не быть, смотрите `h` (справка) в своей версии; при чтении файла `r` перематывает в начало.

Для разбора инцидентов 10-минутный интервал груб. Практика: `LOGINTERVAL=60` в `/etc/default/atop`, затем `sudo systemctl restart atop`. Объём файлов вырастет примерно пропорционально.

### 3.4. btop

`btop` (пакет `btop`, universe) — наглядный монитор с графиками CPU, памяти, дисков, сети и списком процессов; управляется мышью и клавишами, подсказки — в рамках панелей. `Esc` или `m` — меню, `F1`/`h` — справка, `F2`/`o` — настройки, `q` — выход. Хорош для обзора, но не пишет историю и не заменяет `sar`/`atop`.

## 4. Сигналы: kill, killall, pkill — и что они значат для PostgreSQL и 1С

### 4.1. Основные сигналы (signal(7), x86)

| Сигнал | № | Действие по умолчанию | Смысл |
|---|---|---|---|
| `SIGHUP` | 1 | завершить | обрыв терминала; многие демоны трактуют как «перечитать конфигурацию» |
| `SIGINT` | 2 | завершить | прерывание с клавиатуры (`Ctrl+C`) |
| `SIGQUIT` | 3 | завершить + core dump | выход с дампом (`Ctrl+\`) |
| `SIGABRT` | 6 | завершить + core dump | `abort()` |
| `SIGKILL` | 9 | завершить | безусловное уничтожение ядром |
| `SIGSEGV` | 11 | завершить + core dump | обращение к недопустимой памяти |
| `SIGTERM` | 15 | завершить | вежливая просьба завершиться (сигнал `kill` по умолчанию) |
| `SIGCHLD` | 17 | игнорировать | завершился дочерний процесс |
| `SIGCONT` | 18 | продолжить | продолжить остановленный процесс |
| `SIGSTOP` | 19 | остановить | приостановить (заморозить) процесс |
| `SIGTSTP` | 20 | остановить | остановка с терминала (`Ctrl+Z`) |
| `SIGUSR1` / `SIGUSR2` | 10 / 12 | завершить | определяются приложением |

`SIGKILL` и `SIGSTOP` нельзя перехватить, заблокировать или проигнорировать: процесс не получает шанса закрыть файлы, откатить работу, освободить ресурсы.

### 4.2. Команды

```bash
kill -l                         # список сигналов
kill 1234                       # SIGTERM
kill -TERM 1234                 # то же (также -15, -s TERM, -SIGTERM)
kill -INT 1234                  # SIGINT
kill -HUP 1234                  # SIGHUP
kill -STOP 1234; kill -CONT 1234   # заморозить и разморозить
kill -0 1234 && echo жив        # проверка существования процесса, сигнал не посылается
kill -TERM -- -4321             # сигнал всей группе процессов с PGID 4321
killall -TERM имя               # всем процессам с таким именем (psmisc)
killall -u пользователь -TERM   # всем процессам пользователя
pkill -TERM -u usr1cv8 -x rphost   # по критериям pgrep
timeout 30 команда              # запустить и послать SIGTERM через 30 с; -k 10 — добить SIGKILL ещё через 10 с
```

`kill` — встроенная команда bash (есть и `/usr/bin/kill` из procps). Флаги `killall`: `-s SIG`, `-u user`, `-e` (точное имя для длинных имён), `-r` (regex), `-i` (спрашивать подтверждение), `-w` (ждать завершения), `-o`/`-y ВРЕМЯ` (старше/моложе).

Для процессов, работающих как служба systemd, сигнал удобнее и безопаснее посылать через `systemctl kill` — не нужно искать PID, и сигнал гарантированно уйдёт процессам именно этого юнита (man systemctl):

```bash
sudo systemctl kill --kill-whom=main -s SIGHUP postgresql@17-main   # сигнал только главному процессу юнита (postmaster) = reload
sudo systemctl kill -s SIGTERM some-batch.service                   # без --kill-whom сигнал получают ВСЕ процессы юнита
```

`--kill-whom=` принимает `main` (главный процесс), `control` (управляющий) или `all` (по умолчанию); сигнал по умолчанию — `SIGTERM`. В systemd 249 (Ubuntu 22.04) опция называется `--kill-who=`; новое имя `--kill-whom=` появилось в systemd 252. Осторожно: `systemctl kill` без `--kill-whom=main` для юнита PostgreSQL пошлёт `SIGTERM` и postmaster'у, и каждому backend'у; для штатных операций используйте `systemctl reload|stop|restart`.

Правильная лестница эскалации для обычного процесса: `SIGTERM` → подождать → разобраться, почему не завершается (`strace -p`, `/proc/<pid>/stack`, состояние `D`) → и только потом `SIGKILL`. Процесс в состоянии `D` (ждёт ввод-вывод в ядре) `SIGKILL` не убьёт, пока ядро не вернётся из операции.

### 4.3. PostgreSQL: что делает каждый сигнал (официально)

Сигналы главному процессу (postmaster; его PID — первая строка `postmaster.pid` в каталоге данных):

| Сигнал | Режим | Поведение |
|---|---|---|
| `SIGTERM` | Smart Shutdown | новые подключения запрещены, существующие сеансы работают до естественного завершения; сервер остановится только когда отключатся все |
| `SIGINT` | Fast Shutdown | новые подключения запрещены, всем серверным процессам посылается `SIGTERM`, они прерывают текущие транзакции и выходят; затем штатная остановка |
| `SIGQUIT` | Immediate Shutdown | всем дочерним процессам посылается `SIGQUIT`; не завершившимся за 5 секунд — `SIGKILL`; штатная процедура остановки не выполняется, при следующем запуске будет восстановление по WAL. «Recommended only in emergencies» |
| `SIGHUP` | — | перечитать `postgresql.conf`, `pg_hba.conf` и т. п. (то же, что `pg_ctl reload` / `SELECT pg_reload_conf()`) |
| `SIGKILL` | — | документация: «It is best not to use SIGKILL to shut down the server» — сервер не освободит разделяемую память и семафоры, а postmaster не сможет передать сигнал дочерним процессам, их, возможно, придётся убивать вручную |

Соответствие `pg_ctl stop -m smart|fast|immediate`; режим по умолчанию у `pg_ctl` — `fast`, тайм-аут ожидания — `PGCTLTIMEOUT` или 60 секунд. В Ubuntu `pg_ctlcluster NN main stop` тоже использует `fast` по умолчанию (man pg_ctlcluster и в 22.04, postgresql-common 238, и в 24.04, версия 257: «By default, "fast" shutdown mode is used»); ключ `-m smart|fast|immediate` задаёт режим явно; ключ `-f/--force` последовательно пробует fast → immediate → убийство процесса `postgres` (man: «This mode should only be used when the machine is about to be shut down»).

Что реально написано в юните `postgresql@.service` пакета postgresql-common (сверено по исходникам пакета, ветка master на 10.10.2026):

```ini
[Service]
Type=forking
ExecStart=-/usr/bin/pg_ctlcluster --skip-systemctl-redirect %i start
TimeoutStartSec=infinity
ExecStop=/usr/bin/pg_ctlcluster --skip-systemctl-redirect -m fast %i stop
TimeoutStopSec=1h
ExecReload=/usr/bin/pg_ctlcluster --skip-systemctl-redirect %i reload
PIDFile=/run/postgresql/%i.pid
SyslogIdentifier=postgresql@%i
OOMScoreAdjust=-900
#Restart=on-failure
```

Выводы из этого: `systemctl stop postgresql@NN-main` — это fast shutdown; systemd ждёт остановки до часа (`TimeoutStopSec=1h`), прежде чем добивать процессы `SIGKILL`; строка `Restart=` в юните закомментирована (в комментарии авторов пакета сказано, что автоперезапуск мешал бы `pg_ctlcluster … stop`, а postmaster и так сам перезапускает дочерние процессы после большинства сбоев) — значит, после остановки всего юнита (например, из-за `OOMPolicy=stop`, раздел 6.7) PostgreSQL сам не поднимется; `OOMPolicy=` в юните не задан, действует значение по умолчанию; `pg_ctlcluster`, запущенный вручную от root, перенаправляет действие в `systemctl` (поэтому в самом юните стоит `--skip-systemctl-redirect`). В выпусках пакета для 22.04/24.04 отдельные строки могут отличаться (например, тайм-аут запуска мог быть записан как `0`, что равнозначно `infinity`) — проверяйте свой вариант: `systemctl cat postgresql@NN-main`.

Практические следствия для связки с 1С:

- Smart shutdown (`SIGTERM` postmaster'у или `pg_ctl stop -m smart`) при работающем сервере 1С, как правило, не завершится никогда: рабочие процессы `rphost` держат пул соединений с СУБД открытым. Используйте fast: `sudo systemctl stop postgresql@NN-main` (юнит Ubuntu вызывает `pg_ctlcluster … -m fast … stop`, см. выше).
- Правильный порядок остановки стенда: сначала сервер 1С, затем PostgreSQL; запуск — в обратном порядке.

Сигналы отдельному backend'у:

| Сигнал | Эквивалент | Результат |
|---|---|---|
| `SIGINT` | `SELECT pg_cancel_backend(pid);` | отменяется текущий запрос, сеанс остаётся |
| `SIGTERM` | `SELECT pg_terminate_backend(pid);` | сеанс завершается, транзакция откатывается (документация прямо допускает оба способа) |
| `SIGKILL` (в том числе от OOM killer), `SIGSEGV`, `SIGQUIT` | — | postmaster считает это аварией: в журнале «server process (PID N) was terminated by signal 9: Killed», затем «terminating any other active server processes» и «all server processes terminated; reinitializing» — все сеансы всех баз разорваны, выполняется crash recovery |
| `SIGSTOP` | — | backend замирает, удерживая блокировки; остальные встают в очередь. Не использовать |

```sql
-- найти, что делает процесс с данным PID, и аккуратно его остановить
SELECT pid, usename, datname, client_addr, client_port, state, wait_event_type, wait_event,
       now() - xact_start AS xact_age, now() - query_start AS query_age, left(query, 120) AS query
FROM pg_stat_activity WHERE pid = 12345;

SELECT pg_cancel_backend(12345);      -- сначала отменить запрос
SELECT pg_terminate_backend(12345);   -- если не помогло — завершить сеанс
```

Чем опасен `kill -9` на postmaster: дочерние процессы остаются без родителя и какое-то время продолжают работать с разделяемой памятью; новый postmaster не запустится, пока они не выйдут. Удалять вручную `postmaster.pid` и запускать второй экземпляр поверх ещё живых «сирот» нельзя — это прямой путь к повреждению данных. Если postmaster всё же убит: дождаться завершения всех `postgres`-процессов (`pgrep -u postgres -a postgres`), оставшихся завершить `SIGQUIT`/`SIGKILL` по одному, и только потом `systemctl start`.

### 4.4. Процессы 1С: ragent, rmngr, rphost

Что известно официально (первоисточники 1С):

- Механизм мониторинга кластера сам посылает сигналы процессам. Список изменений платформы 8.3.27 (раздел «Кластер серверов»): для завершения зависшего («проблемного») процесса и формирования его дампа механизм мониторинга теперь использует сигнал `SIGABRT`; в предыдущих версиях для этого использовался `SIGSEGV` (замена сделана, чтобы поддержка могла отличать дампы, снятые мониторингом, от настоящих аварий). Следствие для администратора Linux: запись в журнале ядра/systemd или core-файл `rphost`, завершённого по `SIGABRT` (8.3.27+, 8.5) либо `SIGSEGV` (8.3.26 и старше), — не обязательно ошибка платформы; это может быть работа самого кластера. Включается это свойствами кластера «Принудительно завершать проблемные процессы» и задержкой завершения в секундах (англ. *Terminate corrupted processes*, *Terminate corrupted processes in … seconds*; при снятом флажке или нулевой задержке зависшие процессы средствами ОС принудительно не завершаются).
- При превышении «Критического объёма памяти процессов» кластер завершает и перезапускает рабочие процессы, начиная с самого «тяжёлого»; писать ли при этом дамп, определяет свойство кластера «Формировать дамп процесса при превышении критического объёма памяти» (*Write process dump when critical memory amount is exceeded*). Подробнее — раздел 6.4.
- В технологический журнал при превышении критического порога пишется событие `ATTN` с идентификаторами процессов кластера и объёмом их памяти.

Официального описания реакции процессов кластера 1С на `SIGTERM`, `SIGINT`, `SIGHUP`, `SIGSTOP`, посланные администратором, найти не удалось (⚠ не подтверждено); ниже — практика сообщества и общие свойства systemd.

- Штатная остановка — `sudo systemctl stop <юнит srv1cv8…>`. systemd посылает процессам юнита сигнал, заданный в `KillSignal=` (по умолчанию `SIGTERM`; по умолчанию `KillMode=control-group` — всем процессам cgroup), ждёт `TimeoutStopSec` (по умолчанию 90 с) и добивает оставшиеся `SIGKILL`. Что задано в конкретном юните 1С — `systemctl cat <юнит>` и `systemctl show <юнит> -p KillMode -p KillSignal -p TimeoutStopUSec -p Restart -p RestartUSec -p OOMScoreAdjust -p OOMPolicy -p PrivateTmp -p LimitNOFILE -p TasksMax -p Environment`.
- ⚠ не подтверждено (приведено рецензентом по памяти и по публикациям сообщества, с первоисточником в этой сессии не сверено): в штатном юните `srv1cv8-<версия>@.service` заданы `Type=simple`, `User=usr1cv8`, `Group=grp1cv8`, `ExecStart=…/ragent -d ${SRV1CV8_DATA} -port ${SRV1CV8_PORT} -regport ${SRV1CV8_REGPORT} -range ${SRV1CV8_RANGE} -seclev ${SRV1CV8_SECLEV} -pingPeriod … -pingTimeout … $SRV1CV8_DEBUG`, `Restart=always`, `RestartSec=3`, `KillSignal=SIGINT`, `PrivateTmp=true`, а параметры запуска вынесены в строки `Environment=SRV1CV8_*`. Если это так на вашей версии, то: (а) `systemctl stop` посылает процессам 1С `SIGINT`, а не `SIGTERM`; (б) убитый вручную `ragent` systemd поднимет снова через 3 секунды — «остановить сервер 1С командой kill» не получится, нужен `systemctl stop`; (в) у службы собственный `/tmp` (`PrivateTmp`) — временные файлы `rphost` в общем `/tmp` хоста не видны, ищите их в `/tmp/systemd-private-*-srv1cv8-*/tmp`. Обязательно проверьте `systemctl cat` на своей машине, прежде чем на это опираться.
- Менять параметры запуска (каталог кластера, порты, `-debug`) нужно не правкой файла в `/opt/1cv8/…` (он принадлежит дистрибутиву конкретной версии, у следующей версии будет свой файл), а drop-in'ом: `sudo systemctl edit srv1cv8-<версия>@default.service` → секция `[Service]` со строками `Environment=…`. Имя юнита содержит номер версии, поэтому после смены версии платформы и автозапуск, и drop-in настраиваются заново (в списке изменений 8.3.21 прямо сказано: «После смены версии необходимо заново сконфигурировать возможность автоматического запуска кластера серверов»).
- Предпочтительный способ избавиться от проблемного сеанса или рабочего процесса — средства кластера: консоль администрирования или `rac` (`rac session terminate`, вывод рабочего процесса из работы, перезапуск по порогам памяти). Тогда кластер сам переведёт сеансы на другой `rphost`.
- `kill -TERM <PID rphost>`: процесс завершается; сеансы, обслуживавшиеся им, получают ошибку текущего вызова и переподключаются, незавершённые транзакции СУБД откатываются (соединения с PostgreSQL рвутся), менеджер кластера запускает новый `rphost`. Целостность данных базы обеспечивает транзакционность СУБД, но теряется несохранённая работа пользователей и фоновые задания этого процесса.
- `kill -9 <PID rphost>`: то же, но без шанса на штатное завершение; применять только если `SIGTERM` не сработал за разумное время.
- `kill -9` для `rmngr` и `ragent`: риск повредить файлы кластера, которые они ведут (реестр кластера в `reg_1541`, сеансовые данные, журнал регистрации, индекс полнотекстового поиска). Вместо этого — остановка службы целиком.
- `SIGSTOP` рабочему процессу: кластер перестаёт получать от него отклики и может счесть его проблемным. Не использовать как «паузу».
- `SIGHUP` не является для процессов 1С командой «перечитать настройки» (⚠ не подтверждено); параметры кластера меняются через консоль/`rac`, а файл настройки технологического журнала (`logcfg.xml`) платформа перечитывает сама, периодически (по документации платформы — раз в 60 секунд; интервал подтверждён документацией 8.3.27 (глава 6, сверено 10.10.2026); ранее: интервал в этой сессии не сверен), перезапуск и сигналы для этого не нужны.
- Получить дамп «зависшего» рабочего процесса вручную можно тем же способом, каким это делает сам кластер: `sudo kill -ABRT <PID rphost>` (процесс при этом завершится; core-файл появится, только если это разрешено лимитом и настройками ОС — раздел 12.3). Без завершения процесса — `gcore` (раздел 12.3).

Проверка, что после остановки ничего не осталось (иначе новый запуск может не подняться из-за занятых портов и файлов):

```bash
sudo systemctl stop "$U1C"
pgrep -u usr1cv8 -a 'ragent|rmngr|rphost' && echo "ещё есть процессы 1С"
sudo ss -ltnp | grep -E ':(1540|1541|15[6-9][0-9])\b'
```

## 5. Приоритеты и привязка: nice, renice, ionice, chrt, taskset

Общая рекомендация: процессам `postgres` и `rphost` приоритеты вручную не меняют — понижают приоритет фоновым и обслуживающим задачам (резервное копирование, сжатие, `rsync`, выгрузки), чтобы они не мешали рабочей нагрузке.

### 5.1. nice и renice (приоритет CPU)

Значение nice от −20 (самый высокий приоритет) до 19 (самый низкий), по умолчанию 0. Понижать приоритет может любой пользователь, повышать (отрицательные значения) — только root.

```bash
nice -n 19 pg_dump -Fc -f /backup/buh.dump buh     # запустить с минимальным приоритетом
renice -n 10 -p 1234                               # изменить у работающего процесса
sudo renice -n -5 -p 1234                          # повысить (только root)
renice -n 15 -u backupuser                         # всем процессам пользователя
ps -o pid,ni,pri,cls,comm -p 1234                  # проверить
```

Nice влияет только на распределение CPU при конкуренции; если ядра свободны, процесс с nice 19 работает на полной скорости.

### 5.2. ionice (приоритет ввода-вывода)

Классы: `1` realtime (только root), `2` best-effort (по умолчанию; уровни 0–7, 0 — высший, по умолчанию 4), `3` idle (диск достаётся, только когда он никому больше не нужен).

```bash
ionice -c 3 -p 1234                  # перевести процесс в класс idle
ionice -c 2 -n 7 tar czf …           # best-effort с низшим уровнем
ionice -p 1234                       # показать текущий класс
nice -n 19 ionice -c 3 rsync -a /backup/ /mnt/nas/backup/    # типовая связка для фоновой задачи
```

Подводный камень: классы ionice учитывает не всякий планировщик ввода-вывода. man ionice (util-linux 2.39) до сих пор упоминает только давно удалённый CFQ; актуальная документация ядра («Block io priorities») говорит: «Support for io priorities is io scheduler dependent and currently supported by bfq and mq-deadline». То есть на `bfq` и `mq-deadline` классы работают (в `mq-deadline` поддержка классов появилась в ядре 5.14, значит, есть во всех актуальных Ubuntu LTS), а на `none` (типичный выбор ядра для NVMe и многоочередных виртуальных дисков) и `kyber` — не действуют вовсе. Проверить планировщик: `cat /sys/block/sda/queue/scheduler` (текущий — в квадратных скобках); в виртуальной машине там часто стоит именно `none`, и тогда `ionice -c 3` бесполезен. Сменить до перезагрузки: `echo mq-deadline | sudo tee /sys/block/sda/queue/scheduler`. Надёжная альтернатива, не зависящая от планировщика, — лимиты cgroup `IOReadBandwidthMax`/`IOWriteBandwidthMax` (раздел 13).

### 5.3. chrt (класс планирования)

```bash
chrt -p 1234                 # показать политику и приоритет
chrt -b 0 команда            # SCHED_BATCH — для пакетных CPU-задач
chrt -i 0 команда            # SCHED_IDLE — выполнять, только когда CPU простаивает
sudo chrt -o -p 0 1234       # вернуть обычную политику SCHED_OTHER
```

Политики реального времени (`-f` FIFO, `-r` RR) для `postgres`/`rphost` не применяют: зависший RT-процесс способен занять ядро целиком.

### 5.4. taskset (привязка к CPU)

```bash
taskset -cp 1234             # показать список разрешённых CPU
taskset -cp 0-3 1234         # привязать процесс к CPU 0–3
taskset -a -cp 0-7 1234      # -a: применить ко всем потокам (важно для многопоточного rphost)
taskset -c 8-11 команда      # запустить с привязкой
```

Привязка через `taskset` не переживает перезапуск процесса и не наследуется уже существующими потоками без `-a`. Для служб правильнее задавать `AllowedCPUs=` (cgroup cpuset) или `CPUAffinity=` в юните systemd.

## 6. Память

### 6.1. free

```bash
free -h            # человекочитаемо (Ki/Mi/Gi)
free -m            # в мебибайтах
free -h -w         # buffers и cache раздельно
free -h -s 5 -c 6  # 6 замеров с шагом 5 с
free -h -t         # плюс строка Total (RAM + swap)
free -m -v         # (procps 4.x) плюс строка Comm: лимит и объём выделенной (committed) памяти — важно при vm.overcommit_memory=2
```

Колонки (man free, procps 4.0.4; источник — `/proc/meminfo`):

| Колонка | Значение |
|---|---|
| `total` | вся доступная ОС память (`MemTotal`) |
| `used` | `total − available` (procps 4.x). В procps 3.3.17 (Ubuntu 22.04): `total − free − buffers − cache` |
| `free` | совсем не используемая память (`MemFree`) |
| `shared` | в основном tmpfs и разделяемая память (`Shmem`); сюда попадает и `shared_buffers` PostgreSQL, если не используются huge pages |
| `buff/cache` | `Buffers` + `Cached` + `SReclaimable` — страничный кэш и возвращаемая часть slab |
| `available` | оценка памяти, которую можно отдать новым приложениям без свопа (`MemAvailable`) |

Как читать: малое `free` при большом `buff/cache` — норма, Linux использует свободную память под файловый кэш (для PostgreSQL этот кэш — второй уровень кэша данных после `shared_buffers`). Тревожно — малое `available` (ориентир: меньше 5–10 % от `total`) и растущий `used` в строке `Swap`.

### 6.2. /proc/meminfo

```bash
grep -E 'MemTotal|MemFree|MemAvailable|Buffers|^Cached|SwapTotal|SwapFree|Dirty|Writeback:|AnonPages|Shmem:|Slab|SReclaimable|SUnreclaim|PageTables|CommitLimit|Committed_AS|HugePages_|Hugepagesize|AnonHugePages' /proc/meminfo
```

| Поле | Смысл и на что обратить внимание |
|---|---|
| `MemAvailable` | главная цифра «сколько ещё можно занять» |
| `AnonPages` | анонимная память процессов (куча `rphost`, локальная память backend'ов: `work_mem`, `temp_buffers`, кэши каталога) |
| `Shmem` | разделяемая память и tmpfs (`shared_buffers` без huge pages, `/dev/shm`, `/run`) |
| `Cached`, `Buffers` | страничный кэш файлов |
| `Dirty`, `Writeback` | изменённые страницы, ждущие записи / пишущиеся сейчас; постоянно большие значения — диск не успевает |
| `Slab`, `SReclaimable`, `SUnreclaim` | память структур ядра; рост `SUnreclaim` — повод смотреть `slabtop` |
| `PageTables` | таблицы страниц; гигабайты здесь — сотни backend'ов, отображающих большой `shared_buffers` обычными страницами 4 КиБ → лечится huge pages |
| `CommitLimit`, `Committed_AS` | лимит и текущий объём обязательств по памяти; при `vm.overcommit_memory=2` превышение лимита означает отказ в `malloc` |
| `HugePages_Total/Free/Rsvd`, `Hugepagesize` | пул явных huge pages (для `huge_pages = on|try` в PostgreSQL) |
| `AnonHugePages` | объём памяти под transparent huge pages |
| `SwapTotal`, `SwapFree` | подкачка |

### 6.4. Кто сколько занимает: ps, smem, pmap, /proc

Термины: VSZ/VIRT — зарезервированное адресное пространство (почти бесполезно для оценки); RSS/RES — страницы в оперативной памяти, включая разделяемые (суммирование RSS завышает итог); PSS — RSS с разделяемыми страницами, поделёнными между пользователями (сумма PSS по процессам корректна); USS — только собственные страницы процесса; `RssAnon`/`RssFile`/`RssShmem` — разбивка RSS на анонимную, файловую и разделяемую части.

```bash
# RSS-рейтинг (быстро, но для PostgreSQL завышает из-за shared_buffers)
ps -eo pid,user,rss,pmem,nlwp,args --sort=-rss | head -15

# честная картина по PSS/USS (smem нужен root, чтобы видеть чужие процессы)
sudo smem -t -k -s pss -r -c "pid user command swap uss pss rss" | head -20
sudo smem -t -k -P 'postgres|rphost|rmngr|ragent'      # только интересующие процессы
sudo smem -u -t -k                                     # итог по пользователям: postgres, usr1cv8

# разбивка одного процесса
grep -E 'VmPeak|VmSize|VmHWM|VmRSS|RssAnon|RssFile|RssShmem|VmSwap|VmPTE|HugetlbPages|Threads' /proc/1234/status
sudo cat /proc/1234/smaps_rollup                       # Rss, Pss, Pss_Anon, Pss_File, Pss_Shmem, Swap, SwapPss …
sudo pmap -x 1234 | tail -1                            # итог: Kbytes / RSS / Dirty
sudo pmap -x 1234 | sort -k3 -n -r | head -20          # самые большие отображения по RSS
sudo pmap -XX 1234 | less                              # всё, что даёт ядро в smaps

# суммарная анонимная память всех rphost и всех backend'ов (КиБ)
for n in rphost postgres; do
  printf '%s: ' "$n"
  for p in $(pgrep -x "$n"); do awk '/^RssAnon:/{print $2}' "/proc/$p/status"; done | awk '{s+=$1} END{print s+0, "kB"}'
done
```

Особенности PostgreSQL:

- RSS backend'а растёт по мере того, как он «трогает» страницы `shared_buffers` (`RssShmem`); это не утечка. Собственную память сеанса показывает `RssAnon`.
- При `huge_pages = on` разделяемая память в RSS не входит вовсе — она видна как `HugetlbPages` в `/proc/<pid>/status` и как занятые страницы в `HugePages_*` из `/proc/meminfo`.
- Локальная память сеанса: `work_mem` (на каждую операцию сортировки/хеширования, может быть несколько на запрос), `maintenance_work_mem`, `temp_buffers` (кэш временных таблиц — 1С использует их очень активно), кэши системного каталога и планов. Из SQL: `SELECT pg_log_backend_memory_contexts(<pid>);` (PostgreSQL 14+, результат в журнале сервера).

Особенности 1С: память `rphost` почти целиком анонимная (`RssAnon`). Рост без возврата — фрагментация кучи, кэши, утечки в коде конфигурации или платформы; штатный ответ — пороги памяти и автоматический перезапуск рабочих процессов в свойствах рабочего сервера кластера. Соответствие PID ↔ рабочий процесс кластера: `rac process list --cluster=<UUID>` (в выводе есть поля `pid`, `memory-size` — в килобайтах, `memory-excess-time`, `connections`, `avg-call-time`; ⚠ перечень полей приведён не по документации — сверяйте с фактическим выводом `rac`).

Как кластер 1С считает память и что делает (официально: «Руководство администратора. Клиент-серверный вариант», платформа 8.5.1, разделы «Система мониторинга кластера» и «Добавление рабочего сервера»; англоязычная редакция на kb.1ci.com. Русские названия свойств даны так, как они выглядят в консоли кластера; с русским текстом документации на ИТС они в этой сессии не сверялись, английские названия и все числа — дословно из документации 8.5.1. Раздел «Cluster monitoring system» редакции 8.3.27 прочитан отдельно — интервал 5 с, формула vmSwap + vmRSS, пороги 80 % и 95 % и порядок перезапуска там те же; для более старых версий 8.3 сверяйте с документацией своей версии):

- Проверка идёт каждые 5 секунд. Память процесса кластера в Linux считается как сумма `VmRSS` + `VmSwap` (в Windows — PagefileUsage). С порогами сравнивается суммарная память всех рабочих процессов и менеджеров кластера на данном рабочем сервере — не каждого `rphost` в отдельности. Тем же способом значение можно получить самому (см. команду ниже).
- «Временно допустимый объём памяти процессов» (*Temporarily allowed amount of process memory*), байты; по умолчанию `0` = 80 % оперативной памяти сервера; `-1` — без ограничения. При превышении серверу перестают назначаться новые соединения с информационными базами. Если превышение держится дольше интервала (следующий пункт), кластер штатно (не аварийно) перезапускает минимально необходимое число рабочих процессов, начиная с самого «тяжёлого».
- «Интервал превышения допустимого объёма памяти процессов» (*Period of exceeding the memory threshold*), секунды; по умолчанию 300. Действует, только если он не равен 0 и «временно допустимый объём» не равен `-1`.
- «Критический объём памяти процессов» (*Critical amount of process memory*), байты; по умолчанию `0` = 95 % оперативной памяти сервера; `-1` — без ограничения. При превышении нужное число рабочих процессов завершается и запускается заново, начиная с самого «тяжёлого»; в технологический журнал пишется событие `ATTN`.
- «Безопасный расход памяти за один вызов» (*Safe memory consumption per call*), байты; `0` — вычисляется автоматически как 10 % от «временно допустимого объёма памяти процессов»; `-1` — любой серверный вызов прерывается, если превышен «временно допустимый объём». Смысл (по документации): в начале серверного вызова рабочий процесс фиксирует текущую память процессов кластера на этом сервере (обновляется каждые 2 секунды) и вычисляет лимит памяти на вызов = «временно допустимый объём» − текущая память, но не меньше «безопасного расхода за один вызов»; если вызов при выделении памяти превысил свой лимит, он аварийно завершается исключением (в технологическом журнале — событие `EXCP` с текстом и контекстом исключения), остальные сеансы продолжают работать. Иначе говоря, когда память уже подошла к «временно допустимому объёму», каждому вызову гарантирован только «безопасный расход». Свойство относится к функциональности уровня КОРП (как и «Количество ИБ на процесс»).
- Свойства рабочего сервера «Количество ИБ на процесс» и «Количество соединений на процесс» (`0` — без ограничения) определяют, когда кластер создаёт дополнительный `rphost`; от них зависит, сколько рабочих процессов вы увидите в `ps`.
- Начиная с платформы 8.3.27 у кластера и рабочего сервера есть «Расписание перезапуска» рабочих процессов в формате cron (расписание сервера имеет приоритет над расписанием кластера; перезапуск идёт по одному процессу), а прежнее свойство «Интервал перезапуска» объявлено устаревшим (список изменений 8.3.27).

```bash
# то, что кластер 1С сравнивает с порогами: сумма VmRSS + VmSwap по всем rphost и rmngr, в ГиБ
for p in $(pgrep -x 'rphost|rmngr'); do
  awk '/^VmRSS:|^VmSwap:/{s+=$2} END{print s+0}' "/proc/$p/status"
done | awk '{t+=$1} END{printf "1C cluster memory: %.1f GiB\n", t/1048576}'
awk '/^MemTotal:/{printf "80%% RAM = %.1f GiB, 95%% RAM = %.1f GiB\n", $2*0.8/1048576, $2*0.95/1048576}' /proc/meminfo
```

Важное следствие для общего хоста «сервер 1С + PostgreSQL» (вывод из приведённых выше официальных значений по умолчанию; практика): пороги по умолчанию отсчитываются от всей оперативной памяти машины и ничего не знают о PostgreSQL. При значениях `0` кластер 1С начнёт ограничивать себя только после того, как его собственные процессы займут 80 % RAM, — к этому моменту на `shared_buffers`, память backend'ов и файловый кэш места уже не останется, и первым придёт OOM killer. На совмещённом сервере оба порога нужно задавать явно, в байтах, исходя из доли памяти, отведённой серверу 1С (например, RAM минус `shared_buffers`, минус запас на backend'ы, файловый кэш и ОС). Задаются они в консоли администрирования кластера (свойства рабочего сервера) или через `rac server update` (⚠ имена ключей `--temporary-allowed-total-memory`, `--temporary-allowed-total-memory-time-limit`, `--critical-total-memory`, `--safe-call-memory-limit` приведены по памяти рецензента — сверяйте по встроенной справке `rac server help`).

### 6.5. slabtop

Память структур ядра (`Slab` в meminfo), нужен root:

```bash
sudo slabtop -o -s c | head -20      # разово, сортировка по размеру кэша
sudo slabtop -s c                    # интерактивно; q — выход
```

Обычные лидеры — `dentry`, `inode_cache`, `ext4_inode_cache`/`xfs_inode`, `buffer_head`: это возвращаемые кэши файловой системы. Если гигабайты в невозвращаемых кэшах (`SUnreclaim`) — это вопрос к ядру/драйверам, а не к 1С или PostgreSQL.

### 6.6. Swap и swappiness

```bash
swapon --show                         # устройства/файлы подкачки, размер, занято
cat /proc/swaps
sysctl vm.swappiness                  # текущее значение
sudo sysctl -w vm.swappiness=10       # изменить до перезагрузки
echo 'vm.swappiness = 10' | sudo tee /etc/sysctl.d/90-swappiness.conf && sudo sysctl --system   # постоянно

# кто сидит в swap (КиБ, по убыванию)
for f in /proc/[0-9]*/status; do
  awk '/^Name:/{n=$2} /^Pid:/{p=$2} /^VmSwap:/{if ($2>0) print $2, p, n}' "$f" 2>/dev/null
done | sort -rn | head -15
```

- `vm.swappiness` (документация ядра): диапазон 0–200, по умолчанию 60; 100 — равная «стоимость» вытеснения анонимной памяти в swap и файлового кэша; меньше — ядро предпочитает сбрасывать кэш; при 0 ядро не начинает свопинг, пока объём свободных и файловых страниц не упадёт ниже верхней отметки зоны.
- Занятый swap сам по себе не проблема (ядро могло вытеснить давно не используемые страницы). Проблема — активная подкачка: `si`/`so` в `vmstat`, `pswpin/s`/`pswpout/s` в `sar -W`.
- Практика для серверов СУБД и 1С: `vm.swappiness` в диапазоне 1–10 и небольшой swap как «подушка» перед OOM (источники расходятся: 1, 2, 10). Официальная документация PostgreSQL swappiness не нормирует, но отмечает, что увеличение swap помогает избежать OOM, поскольку OOM killer вызывается только при исчерпании и физической памяти, и swap.
- Установщик Ubuntu Server по умолчанию создаёт файл подкачки `/swap.img` (запись в `/etc/fstab`).
- `sudo swapoff -a && sudo swapon -a` принудительно возвращает всё из swap в RAM — только если `available` заведомо больше занятого swap, иначе вызовете OOM.

### 6.7. OOM killer

Когда физическая память и swap исчерпаны (или исчерпан лимит `memory.max` cgroup), ядро выбирает жертву по «badness score» (0…1000, пропорционален занятой памяти, со сдвигом `oom_score_adj`) и убивает её `SIGKILL`.

Как найти следы:

```bash
sudo dmesg -T | grep -iE 'out of memory|oom-kill|killed process|invoked oom-killer'
journalctl -k -g 'out of memory|oom-kill|killed process' --since '-7d' --no-pager   # шаблон в нижнем регистре = поиск без учёта регистра
journalctl -k -b -1 -g 'oom' --no-pager                # в предыдущей загрузке
journalctl -u "$U1C" -g 'oom' --no-pager               # реакция systemd на OOM в юните
cat "/sys/fs/cgroup$(systemctl show -p ControlGroup --value "$U1C")/memory.events"   # счётчики oom и oom_kill юнита
```

Как выглядят сообщения (вид строк ядра; значения условные):

```text
rphost invoked oom-killer: gfp_mask=0x140cca(...), order=0, oom_score_adj=0
oom-kill:constraint=CONSTRAINT_NONE,nodemask=(null),cpuset=/,mems_allowed=0,global_oom,task_memcg=/system.slice/...,task=rphost,pid=23456,uid=998
Out of memory: Killed process 23456 (rphost) total-vm:18345678kB, anon-rss:14234567kB, file-rss:1234kB, shmem-rss:0kB, UID:998 pgtables:30212kB oom_score_adj:0
```

- `constraint=CONSTRAINT_NONE` и `global_oom` — кончилась память всей системы; `CONSTRAINT_MEMCG` и строка «Memory cgroup out of memory» — сработал лимит cgroup (`MemoryMax=`).
- `anon-rss` — сколько реально занимала жертва; перед этими строками ядро печатает таблицу всех процессов с их `rss` и `oom_score_adj` (если `vm.oom_dump_tasks=1`, по умолчанию так).
- В журнале systemd: «<юнит>: A process of this unit has been killed by the OOM killer.» и результат юнита `oom-kill`.

Оценки и защита:

```bash
# текущие оценки для процессов 1С и PostgreSQL
for p in $(pgrep 'postgres|rphost|rmngr|ragent'); do
  printf '%7s score=%-5s adj=%-6s %s\n' "$p" "$(cat /proc/$p/oom_score)" "$(cat /proc/$p/oom_score_adj)" \
    "$(tr '\0' ' ' < /proc/$p/cmdline | cut -c1-70)"
done

choom -p 1234                         # показать oom_score и oom_score_adj
sudo choom -n -1000 -p 1234           # запретить убивать (до перезапуска процесса)
```

`oom_score_adj`: от −1000 (никогда не убивать) до +1000 (убивать первым); значение наследуется дочерними процессами.

Защита postmaster (официальная рекомендация PostgreSQL, раздел «Linux Memory Overcommit»):

1. Выставить postmaster'у `oom_score_adj = -1000`. Документация описывает это как `echo -1000 > /proc/self/oom_score_adj` в скрипте запуска, работающем от root; в юните systemd ту же роль выполняет директива `OOMScoreAdjust=-1000`.
2. Обязательно задать переменные окружения `PG_OOM_ADJUST_FILE=/proc/self/oom_score_adj` и `PG_OOM_ADJUST_VALUE=0`: тогда дочерние процессы сбросят себе оценку в 0 и останутся доступными для OOM killer. Без `PG_OOM_ADJUST_FILE` дети унаследуют −1000, что документация называет неразумным.
3. Альтернатива или дополнение — строгий учёт памяти `vm.overcommit_memory=2` (и подбор `vm.overcommit_ratio`): OOM killer почти не вызывается, вместо этого процессы получают отказ в выделении памяти. На общем с 1С хосте это означает ошибки «Недостаточно памяти» в `rphost` при неверном расчёте — режим нужно проверять под нагрузкой (практика расходится: часть руководств оставляет 0).

```bash
# что реально настроено в юните и у процессов
systemctl show postgresql@17-main -p OOMScoreAdjust -p OOMPolicy -p Environment
sudo cat /proc/$(sudo head -1 /var/lib/postgresql/17/main/postmaster.pid)/oom_score_adj   # у postmaster ожидаем -900 (пакеты Ubuntu/PGDG)
cat /proc/$(pgrep -n -u postgres postgres)/oom_score_adj                          # у backend'а ожидаем 0

# drop-in для пакетов Debian/Ubuntu: защита postmaster уже есть, добавить имеет смысл только OOMPolicy
sudo systemctl edit postgresql@17-main
#   [Service]
#   OOMPolicy=continue

# drop-in для сборок, где защиты нет вовсе (самосборный PostgreSQL, собственный юнит) — полный набор
#   [Service]
#   OOMScoreAdjust=-1000
#   Environment=PG_OOM_ADJUST_FILE=/proc/self/oom_score_adj
#   Environment=PG_OOM_ADJUST_VALUE=0
#   OOMPolicy=continue
```

Как это устроено в пакетах Debian/Ubuntu (сверено по исходникам postgresql-common): юнит `postgresql@.service` содержит `OOMScoreAdjust=-900` с комментарием «prevent OOM killer from choosing the postmaster (individual backends will reset the score to 0)»; кроме того, сам `pg_ctlcluster` при действии `start` записывает `-900` в `/proc/self/oom_score_adj` (если файл доступен на запись) и для PostgreSQL 9.5+ выставляет `PG_OOM_ADJUST_FILE=/proc/self/oom_score_adj`, если переменная ещё не задана (`PG_OOM_ADJUST_VALUE` не задаётся — по умолчанию это 0). Итог: postmaster имеет `oom_score_adj = -900`, все дочерние процессы — `0`. Значение −900, а не −1000, оставляет ядру теоретическую возможность убить postmaster, если больше убивать совсем некого. Каталог данных доступен только пользователю `postgres`, поэтому `postmaster.pid` читается через `sudo`. Для Postgres Pro (`postgrespro-1c-NN.service`) содержимое юнита в этой сессии не сверялось (⚠ не подтверждено) — проверьте теми же командами `systemctl show … -p OOMScoreAdjust -p OOMPolicy -p Environment`.

Поведение systemd при OOM (`OOMPolicy=`, man systemd.service): `continue` — событие журналируется, юнит продолжает работать; `stop` — юнит штатно останавливается целиком; `kill` — ядру предписано убить все оставшиеся процессы юнита. Значение берётся из `DefaultOOMPolicy=`; в исходном `system.conf` systemd это `#DefaultOOMPolicy=stop` (сверено по `src/core/system.conf.in` основной ветки systemd), для юнитов с `Delegate=` по умолчанию действует `continue`. В юните `postgresql@.service` из postgresql-common `OOMPolicy=` не задан — то есть действует `stop`. Следствие: если ядро убило один `rphost` или один backend, systemd может остановить весь сервер 1С или весь PostgreSQL, и без `Restart=` служба останется выключенной. Проверьте `systemctl show -p OOMPolicy -p Restart <юнит>` и решите осознанно (для 1С и PostgreSQL обычно уместно `OOMPolicy=continue` — оба умеют переживать гибель дочернего процесса; практика).

`systemd-oomd` (пользовательский OOM-демон, действующий по PSI и cgroup v2: убивает целиком cgroup тех юнитов, у которых `ManagedOOMSwap=` или `ManagedOOMMemoryPressure=` установлены в `kill`) в Ubuntu включён по умолчанию на настольной редакции начиная с 22.04. Это отдельный пакет `systemd-oomd` (есть в 22.04, 24.04, 26.04), и в стандартную установку Ubuntu Server он не входит: в манифесте установочного образа `ubuntu-24.04.3-live-server-amd64` пакета `systemd-oomd` нет. Проверка на своём сервере: `dpkg -l systemd-oomd; systemctl status systemd-oomd`. Ставить его на сервер с 1С и PostgreSQL без понимания последствий не нужно: он убивает не один процесс, а всю cgroup, то есть всю службу.

Что делать после OOM на сервере 1С + PostgreSQL: выяснить, кто вырос (таблица процессов в сообщении ядра, `sar -r`, `atop -r`), и устранять причину — пороги памяти рабочих процессов 1С, число `rphost`, `shared_buffers` + `work_mem × число сеансов` + `temp_buffers`, объём RAM виртуальной машины. Простое добавление swap лишь превращает OOM в многоминутное «замерзание».

## 7. CPU

### 7.1. uptime и load average

```bash
uptime            # 14:02:11 up 12 days, 3:41, 2 users, load average: 6.21, 4.80, 2.10
uptime -s         # дата и время загрузки системы
nproc             # число доступных процессу CPU; nproc --all — всех установленных
cat /proc/loadavg # 6.21 4.80 2.10 7/1234 56789  → LA1 LA5 LA15, выполняется/всего задач, последний PID
```

Трактовка:

- Три числа — экспоненциально сглаженные средние за 1, 5 и 15 минут числа задач в состояниях R (выполняются или ждут CPU) и D (непрерываемый сон, обычно диск).
- Сравнивайте с числом ядер: LA ≈ `nproc` при `id` ≈ 0 — CPU загружен полностью; LA заметно больше `nproc` — очередь. Но LA 20 на 8 ядрах при `id` 70 % и `wa` 25 % — это очередь к диску, а не к процессору.
- Тренд: LA1 > LA5 > LA15 — нагрузка растёт; наоборот — спадает.
- LA не различает причины — это только повод запускать `vmstat 1`, `mpstat`, `iostat`.

### 7.2. mpstat

```bash
mpstat -P ALL 1          # по каждому CPU, шаг 1 с
mpstat -P ALL 5 3        # три замера по 5 с и средние
mpstat 1                 # только сводная строка all
mpstat -I SUM -P ALL 1   # прерывания в секунду по CPU
```

Колонки: `%usr`, `%nice`, `%sys`, `%iowait`, `%irq`, `%soft`, `%steal`, `%guest`, `%gnice`, `%idle`. На что смотреть: одно ядро в 100 % `%usr` при простое остальных — однопоточная задача (один серверный вызов 1С, один запрос PostgreSQL без параллелизма); высокий `%sys` на всех — системные вызовы, переключения контекста, работа с памятью; `%soft`/`%irq` на одном ядре — сетевые прерывания; `%steal` — нехватка CPU на хосте виртуализации.

### 7.3. pidstat

Статистика по процессам с интервалом (пакет `sysstat`). Опции: `-u` CPU (по умолчанию), `-r` память и page faults, `-d` ввод-вывод, `-w` переключения контекста, `-t` потоки, `-l` полная командная строка, `-p PID[,…]|ALL`, `-C шаблон` и `-G шаблон` — фильтр по имени, `-U [пользователь]` — имя вместо UID и фильтр, `-h` — всё в одну строку (для разбора скриптом), `-H` — время в секундах эпохи, `-I` — делить %CPU на число процессоров, `-v` — число потоков и дескрипторов, `-T CHILD|ALL` — учитывать потомков, `--human`.

| Отчёт | Колонки |
|---|---|
| `-u` | `%usr`, `%system`, `%guest`, `%wait` (доля времени ожидания CPU в очереди), `%CPU`, `CPU` |
| `-r` | `minflt/s`, `majflt/s` (обращения к диску за страницей), `VSZ`, `RSS`, `%MEM` |
| `-d` | `kB_rd/s`, `kB_wr/s`, `kB_ccwr/s` (отменённая запись), `iodelay` (задержка в тиках из-за ввода-вывода, включая swap-in) |
| `-w` | `cswch/s` (добровольные переключения — ожидание), `nvcswch/s` (принудительные — вытеснение, нехватка CPU) |
| `-v` | `threads`, `fd-nr` |

```bash
pidstat 1                               # кто потребляет CPU прямо сейчас (только активные)
pidstat -u -r -d -h 5 3                 # CPU + память + диск одной таблицей, 3 замера по 5 с
pidstat -l -C 'rphost|postgres' 5       # только 1С и PostgreSQL, с командной строкой
pidstat -t -p "$(pgrep -o rphost)" 1    # по потокам конкретного rphost
pidstat -w -C postgres 5                # переключения контекста backend'ов
pidstat -d -l 5                         # кто читает и пишет на диск
pidstat -v -C rphost 10 1               # число потоков и открытых дескрипторов rphost
```

Высокий `%wait` у многих процессов одновременно при `r` > числа ядер — прямой признак нехватки CPU.

### 7.4. lscpu, nproc и топология

```bash
lscpu                                    # модель, сокеты/ядра/потоки, NUMA, кэши, гипервизор, флаги
lscpu -e                                 # таблица: CPU, NODE, SOCKET, CORE, ONLINE, частоты
lscpu | grep -E 'Model name|^CPU\(s\)|Thread|Core|Socket|NUMA|Hypervisor|Virtualization'
nproc
grep -c ^processor /proc/cpuinfo
cat /sys/devices/system/cpu/online       # список активных CPU
cat /sys/devices/system/cpu/cpu0/cpufreq/scaling_governor 2>/dev/null   # в ВМ файла обычно нет
```

В виртуальной машине `Hypervisor vendor` покажет `Microsoft` (Hyper-V), `VMware`, `KVM` и т. п. Число vCPU ВМ не должно превышать число физических ядер хоста, а с учётом других ВМ — оставлять запас, иначе получите steal.

Замечание по лицензиям. Официально (страница «Расширенная функциональность уровня КОРП» на v8.1c.ru, перечень для платформы 8.3.13): к функциональности уровня КОРП отнесена «возможность использования в одной информационной базе более 500 одновременных сеансов пользователей и более 12 ядер процессора», а также «гибкое управление нагрузкой в кластере» (безопасный расход памяти за один вызов; количество ИБ на процесс; объём памяти рабочих процессов, до которого сервер считается производительным; максимальный объём памяти рабочих процессов; стратегия балансировки). Практическая трактовка сообщества (Хабр): сервер 1С с лицензией ПРОФ не использует более 12 физических ядер, логические ядра Hyper-Threading в лимит не входят (по документации 8.3.27 (глава 1 «Руководства администратора», сверено 10.10.2026) ядро виртуальной машины считается ядром; ранее: как именно платформа считает ядра в виртуальной машине, первоисточником не подтверждено). Выделение ВМ большего числа vCPU серверу 1С уровня ПРОФ не поможет, но поможет PostgreSQL на том же хосте.

### 7.5. Steal time в виртуальной машине

`st` (`%steal`) — время, когда виртуальный CPU был готов работать, но гипервизор отдал физический процессор другому. Видно в `top` (`st`), `vmstat` (`st`), `mpstat` (`%steal`), `sar -u` (`%steal`), `/proc/stat`.

- Ориентир: устойчиво больше 5–10 % — vCPU не хватает на хосте (переподписка, соседние ВМ, сам Windows-хост). Лечится на стороне гипервизора: уменьшить число vCPU у ВМ, разгрузить хост, закрепить ресурсы.
- Нулевой steal не гарантирует отсутствия проблемы: гость видит steal, только если гипервизор передаёт эту метрику, а ядро гостя умеет её читать (паравиртуальный «steal clock»). По исходному коду ядра Linux (основная ветка, проверено 10.10.2026): реализации есть для KVM, Xen и VMware (`arch/x86/kernel/cpu/vmware.c`: гипервызов `STEALCLOCK`, добавлен в ядре 5.7; работает, только если гипервизор на этот вызов отвечает; отключается параметром загрузки `no-steal-acc`); в коде поддержки Hyper-V (`arch/x86/kernel/cpu/mshyperv.c`) steal clock не реализован — в госте Hyper-V колонка `st` всегда равна 0, сколько бы хост ни отбирал процессорного времени. Для VirtualBox отдельной реализации в ядре тоже нет (⚠ передаёт ли VirtualBox steal через интерфейс KVM-паравиртуализации, и поддерживает ли гипервызов `STEALCLOCK` VMware Workstation, а не только ESXi, — не подтверждено). Проверить, включён ли учёт у вас: `sudo dmesg | grep -i steal` и ненулевое ли восьмое число в строке `cpu` файла `/proc/stat` после работы под нагрузкой.
- Косвенные признаки конкуренции на хосте при `st` = 0: «рваное» время выполнения одинаковых операций, задержки планирования при низкой загрузке гостя, рост `%sys` без причины, скачки времени в `dmesg` (`clocksource`, `hrtimer: interrupt took …`). Проверяйте загрузку CPU на самом Windows-хосте (Диспетчер задач, счётчики Hyper-V «Hypervisor Logical Processor \ % Total Run Time» и «Hyper-V Hypervisor Virtual Processor \ CPU Wait Time Per Dispatch»).

### 7.6. perf (кратко)

`perf` показывает, какие функции потребляют CPU. В Ubuntu `kernel.perf_event_paranoid` по умолчанию ограничивает непривилегированное использование — запускайте через `sudo`.

```bash
sudo perf top                                   # системно, «горячие» функции вживую
sudo perf top -p "$(pgrep -d, rphost)"          # только указанные процессы
sudo perf record -F 99 -g -p 1234 -- sleep 30   # 30 секунд сэмплирования стеков процесса
sudo perf report --stdio | head -60             # отчёт
sudo perf stat -p 1234 -- sleep 10              # счётчики: переключения контекста, миграции, page faults
```

- В ВМ аппаратные счётчики (cycles, instructions) часто недоступны — `perf` переходит на программный таймер `cpu-clock`; это нормально.
- Для `postgres` имена функций видны (для строк исходников нужен пакет отладочных символов). Для `rphost` символов нет: будут видны только имена модулей платформы (`.so`) и адреса — этого достаточно, чтобы отличить «код 1С» от ядра, libc, сети.
- `perf` — инструмент углублённого анализа; в первые минуты инцидента важнее `top`, `pidstat`, технологический журнал 1С и `pg_stat_activity`.

## 8. Диск

### 8.1. iostat -xz

```bash
iostat -xz 1                 # расширенная статистика, без простаивающих устройств, шаг 1 с
iostat -xz -y 5 3            # без первого отчёта «с загрузки», 3 замера по 5 с
iostat -xzt 1                # с отметкой времени
iostat -xz -m 1              # в МБ/с вместо кБ/с
iostat -xz -p sda 1          # устройство и его разделы
iostat -xz -N 1              # имена device-mapper (LVM) вместо dm-N
iostat -xzh 1                # человекочитаемо, имя устройства справа
iostat -c 1                  # только CPU
iostat -xz -o JSON 1 3       # JSON для скриптов
```

Опции: `-x` — расширенная статистика, `-z` — не показывать устройства без активности, `-d` — только устройства, `-c` — только CPU, `-k`/`-m` — кБ/МБ, `-p [устройство|ALL]` — с разделами, `-t` — время, `-y` — пропустить первый отчёт, `-N` — имена LVM, `-h` = `--human --pretty`, `-s` — короткий формат на 80 колонок, `--dec={0,1,2}`, `-j ID|LABEL|PATH|UUID` — постоянные имена.

Расшифровка колонок (man iostat, sysstat 12.6):

| Колонка | Значение |
|---|---|
| `r/s`, `w/s` | завершённых запросов чтения / записи в секунду (после слияния) — это IOPS |
| `d/s`, `f/s` | запросов discard / flush в секунду |
| `rkB/s`, `wkB/s` | кБ в секунду прочитано / записано — пропускная способность |
| `rrqm/s`, `wrqm/s`, `%rrqm`, `%wrqm` | слитых запросов в секунду и их доля |
| `r_await`, `w_await`, `d_await` | среднее время выполнения запроса в миллисекундах, включая ожидание в очереди и обслуживание |
| `f_await` | среднее время запроса flush, мс (блочный слой выполняет не более одного flush одновременно) — для СУБД это цена `fsync` |
| `aqu-sz` | средняя длина очереди запросов к устройству (раньше называлась `avgqu-sz`) |
| `rareq-sz`, `wareq-sz` | средний размер запроса чтения / записи, кБ |
| `%util` | доля времени, в течение которого устройству выдавались запросы |

Блок CPU в начале: `%user`, `%nice`, `%system`, `%iowait`, `%steal`, `%idle`.

Как читать:

- `%util` близкий к 100 % означает насыщение только для устройств, обслуживающих запросы последовательно (одиночный HDD). Для RAID, SSD/NVMe и виртуальных дисков, выполняющих запросы параллельно, это, по словам man iostat, ненадёжный показатель.
- Главные показатели качества — `r_await`/`w_await` и `aqu-sz`. Ориентиры (эвристика): для SSD/NVMe единицы миллисекунд и меньше; десятки миллисекунд под OLTP-нагрузкой — диск не справляется; для HDD 10–20 мс — обычно, больше 30–50 мс — плохо. `aqu-sz` устойчиво больше 1–2 на одиночном устройстве — очередь.
- Маленький `rareq-sz` (4–16 кБ) при высоком `r/s` — случайное чтение (индексный доступ, данные не помещаются в кэш); большой `wareq-sz` при пиках `wkB/s` раз в несколько минут — контрольные точки PostgreSQL.
- В ВМ на Windows-хосте виртуальный диск — файл (VHDX/VMDK/VDI) на диске хоста: задержки могут происходить выше, на хосте (антивирус, динамически расширяемый диск, снапшоты, общий с другими ВМ накопитель). Внутри гостя вы увидите только рост await.

### 8.2. Кто грузит диск: iotop, pidstat -d

```bash
sudo iotop -oPa               # -o только активные, -P процессы (не потоки), -a накопленный итог с запуска
sudo iotop -o -b -n 5 -d 2    # пакетный режим: 5 замеров по 2 с — в лог
sudo iotop -o -u postgres     # только пользователь
sudo iotop -p 1234            # только процесс
pidstat -d -l 5               # альтернатива без root для своих процессов; с sudo — для всех
sudo cat /proc/1234/io        # счётчики одного процесса (см. раздел 11)
```

- Колонки iotop: `DISK READ`, `DISK WRITE`, `SWAPIN` (доля времени на подкачку), `IO>` (доля времени в ожидании ввода-вывода), `COMMAND`.
- На ядрах 5.14+ (то есть на всех актуальных Ubuntu LTS) учёт задержек по задачам выключен по умолчанию, и колонки `SWAPIN`/`IO%` недоступны, пока не включить: `sudo sysctl kernel.task_delayacct=1` (постоянно — файл в `/etc/sysctl.d/`). Объёмы чтения и записи видны и без этого.
- Рекомендуемая реализация — `iotop-c` (на C). В пакете Ubuntu исполняемый файл называется `/usr/sbin/iotop-c` (проверено по списку файлов пакета `iotop-c` в noble: кроме него в пакете только man-страница `iotop-c.8` и документация); в самой man-странице команда записана как `iotop`. Команда `iotop` при этом тоже доступна — пакет регистрирует её через механизм альтернатив Debian (в исходниках пакета есть файл `debian/iotop-c.alternatives`; какой вариант сейчас выбран, показывает `update-alternatives --display iotop`). Если `iotop: command not found` — запускайте `sudo iotop-c` с теми же ключами `-o -P -a -b -n -d -u -p -k -t -q`. В интерактивном режиме `iotop-c` клавиша `Ctrl-T` включает и выключает `kernel.task_delayacct` на лету; man рекомендует держать учёт задержек выключенным, когда мониторинг не идёт, так как он влияет на производительность.
- Запись через страничный кэш учитывается на того, кто «испачкал» страницу, а реально на диск её часто сбрасывают потоки ядра (`kworker/…flush`); `fsync` WAL виден у `walwriter` и у самих backend'ов.

Типичные «писатели» и «читатели» на сервере 1С + PostgreSQL:

| Процесс | Что означает активный ввод-вывод |
|---|---|
| `postgres: checkpointer` | контрольная точка; слишком частые или «залповые» — настраивать `max_wal_size`, `checkpoint_timeout`, `checkpoint_completion_target` |
| `postgres: walwriter`, backend'ы с большой записью | поток WAL: массовые изменения, перепроведения, загрузки |
| `postgres: autovacuum worker` | очистка и сбор статистики больших таблиц |
| backend с записью в `base/pgsql_tmp` | сортировки и хеши не помещаются в `work_mem` → временные файлы (см. `log_temp_files`) |
| backend с большим чтением | последовательные сканирования, данные не в кэше |
| `rphost` | временные файлы, сеансовые данные, технологический журнал, выгрузки/загрузки |
| `rmngr` | журнал регистрации, полнотекстовый индекс, сеансовые данные |
| `kswapd0` в топе CPU + `si`/`so` | это не диск, а нехватка памяти |

### 8.3. dstat / dool

`dstat` — «всё в одной строке» (CPU, диск, сеть, подкачка, система) с интервалом. Состояние в Ubuntu: в 22.04 — настоящий пакет `dstat` 0.7.4 (оригинальный проект заброшен); в 24.04 и новее `dstat` — виртуальный пакет, который предоставляет `pcp` (реализация `pcp-dstat`). `dool` — поддерживаемый форк dstat на Python 3 с тем же синтаксисом; в архиве Ubuntu его нет ни в одном выпуске (проверено 10.10.2026 запросом к madison по всем выпускам, включая 26.04 и разрабатываемый 26.10), ставится из репозитория проекта `scottchiefbaker/dool` (сторонний источник — на рабочий сервер только осознанно).

```bash
dstat -tcdngy 5                              # время, CPU, диск, сеть, paging, system; шаг 5 с
dstat -tcmsdn --top-cpu --top-io 5           # плюс память, swap и «чемпионы» по CPU и I/O (в оригинальном dstat/dool)
dool --time --cpu --mem --disk --io --net --sys 5
```

Если ни того, ни другого нет — те же данные дают `vmstat 1`, `iostat -xz 1`, `sar -n DEV 1`.

### 8.4. Место на диске как причина «всё встало»

Переполнение раздела с данными PostgreSQL (WAL, временные файлы) или с каталогом кластера 1С и технологическим журналом выглядит как зависание. Проверки на первой минуте:

```bash
df -hT                                         # занятость файловых систем
df -i                                          # иноды
sudo du -xh --max-depth=1 /var/lib/postgresql | sort -h | tail
sudo du -sh /var/lib/postgresql/*/main/pg_wal /var/lib/postgresql/*/main/base/pgsql_tmp 2>/dev/null
sudo lsof +L1                                  # удалённые, но открытые файлы (место не освобождено)
```

### 8.5. eBPF-инструменты bcc и bpftrace (кратко)

В Ubuntu 24.04 и 26.04 пакеты `bpfcc-tools` и `bpftrace` находятся в main; в 24.04 они входят в стандартную установку Ubuntu Server (есть в манифесте установочного образа 24.04.3; для 26.04 состав установки по умолчанию в этой сессии не сверялся — ⚠ проверьте `dpkg -l bpfcc-tools bpftrace`). В 22.04 они в universe и ставятся вручную. Они показывают то, чего не дают усреднённые счётчики `iostat`/`vmstat`: распределение задержек (гистограммы) и отдельные медленные операции. В Debian/Ubuntu все утилиты bcc имеют суффикс `-bpfcc`. Нужен root; накладные расходы малы, но это всё же трассировка ядра — на рабочем сервере запускать кратко.

```bash
sudo biolatency-bpfcc -mT 5 3        # гистограмма задержек блочного ввода-вывода в мс, 3 замера по 5 с; -D — отдельно по дискам, -Q — с учётом времени в очереди
sudo runqlat-bpfcc -mT 5 3           # гистограмма ожидания задач в очереди на CPU (прямая мера нехватки CPU); -P — по процессам, -p PID — один процесс
sudo ext4slower-bpfcc 10             # операции ext4 (чтение, запись, открытие, sync) дольше 10 мс — кто именно и с каким файлом; порог по умолчанию 10 мс; для XFS — xfsslower-bpfcc
sudo oomkill-bpfcc                   # в реальном времени: кто вызвал OOM killer, кого убили, load average на этот момент
```

Синтаксис сверен по man-страницам Ubuntu 24.04 (`biolatency [-T] [-Q] [-m] [-D] [-F] [-j] [-d DISK] [interval [count]]`; `runqlat [-T] [-m] [-P] [-L] [-p PID] [interval] [count]`; `ext4slower [-j] [-p PID] [min_ms]`). В том же пакете есть `biosnoop-bpfcc`, `biotop-bpfcc`, `cachestat-bpfcc`, `execsnoop-bpfcc`, `opensnoop-bpfcc`, `tcpretrans-bpfcc`, `offcputime-bpfcc` — их ключи смотрите в `man <имя>-bpfcc` (в этой статье не сверялись). Если утилита падает с ошибкой компиляции, обычно не хватает заголовков ядра: `sudo apt install linux-headers-$(uname -r)`.

## 9. Сеть

```bash
ip -br addr                    # интерфейсы и адреса кратко
ip -s link show eth0           # счётчики пакетов, ошибок, отбрасываний
sar -n DEV 1                   # трафик по интерфейсам
sar -n EDEV 1                  # ошибки по интерфейсам
sar -n TCP,ETCP 1              # TCP: соединения и ошибки
ss -s                          # сводка по сокетам
ss -ltnp                       # кто что слушает (TCP), с PID и именем процесса (нужен sudo для чужих)
ss -Htn state established '( sport = :5432 )' | wc -l    # число установленных соединений к PostgreSQL
sudo ss -Htnp 'dport = :5432' | grep -c rphost           # соединения rphost → PostgreSQL
ss -tin 'dport = :5432' | head                           # детали TCP: rtt, cwnd, retrans
nstat -az | grep -iE 'retrans|listen|overflow'           # счётчики ядра: повторные передачи, переполнение очередей
```

Колонки `sar -n DEV`: `rxpck/s`, `txpck/s` (пакетов в секунду), `rxkB/s`, `txkB/s` (кБ/с), `rxcmp/s`, `txcmp/s`, `rxmcst/s`, `%ifutil` (загрузка интерфейса относительно его скорости; для виртуальных адаптеров может быть неинформативна). `sar -n EDEV`: `rxerr/s`, `txerr/s`, `coll/s`, `rxdrop/s`, `txdrop/s`, `txcarr/s`, `rxfram/s`, `rxfifo/s`, `txfifo/s` — любые ненулевые значения требуют внимания. `sar -n TCP`: `active/s` (исходящие соединения), `passive/s` (входящие), `iseg/s`, `oseg/s`; `sar -n ETCP`: `atmptf/s`, `estres/s`, `retrans/s` (повторные передачи — признак потерь или перегрузки сети), `isegerr/s`, `orsts/s`.

Интерактивные инструменты:

```bash
nload eth0                 # графики входящего/исходящего трафика интерфейса
sudo iftop -i eth0 -nNP    # трафик по парам «хост:порт» (-n без DNS, -N без имён портов, -P показывать порты)
sudo nethogs eth0          # трафик по процессам (кто именно: rphost, postgres, ras…)
```

Имя интерфейса зависит от гипервизора (`eth0`, `ens33`, `enp0s3` …) — смотрите `ip -br link`.

Применительно к 1С: если сервер 1С и PostgreSQL на одной машине, обмен идёт через loopback и сеть узким местом не бывает; сетевые проблемы проявляются между клиентами (тонкий клиент, веб-сервер) и сервером 1С — порты 1540, 1541, 1560–1591. Высокий `retrans/s`, ненулевые `rxdrop/s`, большое число соединений в `ss -s` в состояниях `orphaned`/`timewait` — поводы смотреть сеть и виртуальный коммутатор хоста.

## 10. sysstat и sar: история нагрузки

### 10.1. Установка и включение сбора (Ubuntu)

```bash
sudo apt install sysstat
sudo sed -i 's/^ENABLED="false"/ENABLED="true"/' /etc/default/sysstat
sudo systemctl enable --now sysstat.service
systemctl list-timers 'sysstat*'          # должны появиться sysstat-collect.timer и sysstat-summary.timer
ls -l /var/log/sysstat/                   # через ~10 минут появится файл saDD
```

- Утилиты реального времени (`iostat`, `mpstat`, `pidstat`, `sar 1 5`) работают сразу после установки; историю (`sar` без интервала, `sar -f`) пишет фоновый сбор, который в Ubuntu по умолчанию выключен (`ENABLED="false"` в `/etc/default/sysstat`).
- Сбор выполняет `sa1` (обёртка над `sadc`) раз в 10 минут; ежедневная сводка — `sa2`. Как это упаковано в Debian/Ubuntu (сверено по исходникам пакета sysstat в Debian и по шаблонам юнитов upstream):
  - на системах с systemd работают таймеры `sysstat-collect.timer` (расписание `OnCalendar=*:00/10`, то есть в :00, :10, :20 …) и `sysstat-summary.timer` (`OnCalendar=00:07:00`); оба имеют `WantedBy=sysstat.service`, а в `sysstat.service` (`ExecStart=…/sa1 --boot` — пометка о перезагрузке в файле данных) прописано `Also=` с этими таймерами, поэтому `systemctl enable --now sysstat.service` включает и их;
  - файл `/etc/cron.d/sysstat` (запуск `debian-sa1 1 1` в минуты 5–55 с шагом 10 и `debian-sa1 60 2` в 23:59) тоже устанавливается, но обёртка `debian-sa1` первым делом проверяет наличие `/run/systemd/system` и под systemd сразу завершается («Skip in favour of systemd timer»); только без systemd она читает `ENABLED` из `/etc/default/sysstat`;
  - под systemd переменная `ENABLED` сама по себе на таймеры не влияет — её читает сценарий установки пакета: он берёт ответ на вопрос debconf `sysstat/enable`, записывает его в `ENABLED` и включает либо выключает сразу все три юнита (`sysstat.service`, `sysstat-collect.timer`, `sysstat-summary.timer`). Отсюда правило: меняйте оба места согласованно (как в командах выше) либо используйте штатный способ Debian — `sudo dpkg-reconfigure sysstat` (ответ «Да»). Если оставить `ENABLED="false"` и только включить юниты, очередное обновление пакета может их снова выключить;
  - каталог скриптов `sa1`/`sa2`: `/usr/lib/sysstat/` в 22.04 и 24.04; в свежей упаковке Debian (12.7.5 и новее) — `/usr/libexec/sysstat/` (для 26.04 проверьте `systemctl cat sysstat-collect.service`).
- Файлы данных: `/var/log/sysstat/saDD` (DD — день месяца) либо `saYYYYMMDD`; двоичные, читаются только `sar`/`sadf`.
- Настройки: `/etc/sysstat/sysstat` — `HISTORY` (сколько дней хранить; по умолчанию 7 — это значение сборки upstream, `HISTORY=7` в `configure.ac` sysstat, и упаковка Debian его не переопределяет; проверка: `grep ^HISTORY /etc/sysstat/sysstat`), `COMPRESSAFTER` (через сколько дней сжимать; по умолчанию 10), `SADC_OPTIONS` (по умолчанию `-S DISK`; `-S XALL` — собирать всё; применяется только при создании нового суточного файла), `SA_DIR` (по умолчанию `/var/log/sysstat`), `ZIP` (программа сжатия), `DELAY_RANGE` (случайная задержка `sa2`, чтобы виртуальные машины на общем хранилище не давали всплеск ввода-вывода одновременно).

Сбор раз в минуту вместо десяти (для разбора инцидентов 10 минут — слишком грубо):

```bash
sudo systemctl edit sysstat-collect.timer
#   [Timer]
#   OnCalendar=
#   OnCalendar=*:00/1
sudo systemctl daemon-reload && sudo systemctl restart sysstat-collect.timer
```

И увеличить срок хранения: `HISTORY=28` в `/etc/sysstat/sysstat` (при значении больше 28 файлы именуются `saYYYYMMDD`).

### 10.2. Чтение: sar

Общий синтаксис: `sar [отчёты] [интервал [число]]` — вживую; `sar [отчёты] -f файл [-s ЧЧ:ММ:СС] [-e ЧЧ:ММ:СС]` — из истории; `sar [отчёты] -1` — вчерашний файл, `-2` — позавчерашний.

| Отчёт | Что показывает | Ключевые колонки |
|---|---|---|
| `-u` (`-u ALL`) | CPU сводно | `%user`, `%nice`, `%system`, `%iowait`, `%steal`, `%idle`; с `ALL` ещё `%irq`, `%soft`, `%guest`, `%gnice` |
| `-P ALL` | CPU по ядрам | те же |
| `-q` | очередь и load average | `runq-sz` (очередь на CPU), `plist-sz` (число задач), `ldavg-1/5/15`, `blocked` (ждут ввод-вывод) |
| `-q CPU` / `-q IO` / `-q MEM` (`-q PSI` — все три, `-q ALL` — вместе с LOAD) | PSI из истории; ключевые слова `CPU, IO, LOAD, MEM, PSI` описаны в man sar и для sysstat 12.5.2 (22.04), и для 12.6.1 (24.04). PSI не входит в список необязательных наборов `sadc -S` (там только `DISK, INT, IPV6, POWER, SNMP, XDISK, ALL, XALL`), то есть собирается и при умолчательном `SADC_OPTIONS="-S DISK"`, если ядро отдаёт `/proc/pressure` | `%scpu-10/60/300`, `%sio-…`, `%fio-…`, `%smem-…`, `%fmem-…` |
| `-r` (`-r ALL`) | память | `kbmemfree`, `kbavail`, `kbmemused`, `%memused`, `kbbuffers`, `kbcached`, `kbcommit`, `%commit`, `kbactive`, `kbinact`, `kbdirty` |
| `-S` | swap | `kbswpfree`, `kbswpused`, `%swpused`, `kbswpcad` |
| `-W` | подкачка | `pswpin/s`, `pswpout/s` |
| `-B` | paging | `pgpgin/s`, `pgpgout/s`, `fault/s`, `majflt/s`, `pgscank/s`, `pgscand/s` (прямое сканирование — признак нехватки памяти), `pgsteal/s`, `%vmeff` |
| `-b` | ввод-вывод суммарно | `tps`, `rtps`, `wtps`, `dtps`, `bread/s`, `bwrtn/s` (в блоках по 512 байт) |
| `-d` (`-d -p`) | по устройствам | `tps`, `rkB/s`, `wkB/s`, `areq-sz`, `aqu-sz`, `await`, `%util`; `-p` — понятные имена устройств |
| `-n DEV` / `EDEV` / `TCP` / `ETCP` | сеть | см. раздел 9 |
| `-w` | задачи | `proc/s` (создание процессов), `cswch/s` (переключения контекста) |
| `-v` | таблицы ядра | `dentunusd`, `file-nr`, `inode-nr`, `pty-nr` |
| `-H` | huge pages | `kbhugfree`, `kbhugused`, `%hugused`, `kbhugrsvd` |
| `-A` | всё сразу | |

```bash
sar -u 1 5                                               # CPU вживую
sar -q                                                   # очередь и LA за сегодня
sar -r -f /var/log/sysstat/sa09                          # память за 9-е число
sar -u -f /var/log/sysstat/sa09 -s 14:00:00 -e 15:30:00  # CPU за окно времени
sar -d -p -f /var/log/sysstat/sa09 -s 14:00:00 -e 15:30:00   # диски за то же окно
sar -b -1                                                # суммарный ввод-вывод за вчера
sar -n DEV -1 -s 09:00:00 -e 18:00:00                    # сеть за вчерашний рабочий день
sar -W -B -f /var/log/sysstat/sa09                       # была ли подкачка
sar -A -f /var/log/sysstat/sa09 > /var/tmp/sar-09.txt    # полный текстовый отчёт за день
sadf -d /var/log/sysstat/sa09 -- -u -r -q > /var/tmp/sa09.csv   # выгрузка для таблиц (разделитель «;»)
sadf -g /var/log/sysstat/sa09 -- -u -r -q -d > /var/tmp/sa09.svg  # графики SVG
```

Замечания: опции `-s`/`-e` без значения означают 08:00:00 и 18:00:00; время — локальное на момент просмотра (с `-t` — время создателя файла); строки `LINUX RESTART` отмечают перезагрузки. Файл `saDD` перезаписывается через месяц — при `HISTORY` больше 28 используйте имена `saYYYYMMDD`.

Сценарий «вчера в 15:10 всё тормозило»: `sar -q -1 -s 15:00:00 -e 15:30:00` (очередь и LA) → `sar -u ALL -1 …` (us/sy/iowait/steal) → `sar -r -1 …` и `sar -W -B -1 …` (память, подкачка) → `sar -d -p -1 …` (await по дискам) → `atop -r y -b 1505` (какие процессы).

## 11. /proc и /sys, lsof, fuser

### 11.1. /proc/<pid>/…

| Файл | Содержимое | Как читать |
|---|---|---|
| `status` | имя, состояние, `PPid`, `Uid`/`Gid`, память (`VmPeak`, `VmSize`, `VmHWM` — пик RSS, `VmRSS`, `RssAnon`, `RssFile`, `RssShmem`, `VmSwap`, `VmPTE`, `HugetlbPages`), `Threads`, маски сигналов (`SigBlk`, `SigIgn`, `SigCgt`), `Cpus_allowed_list`, `voluntary_ctxt_switches`, `nonvoluntary_ctxt_switches` | `cat /proc/1234/status` |
| `limits` | действующие лимиты процесса (мягкий и жёсткий): `Max open files`, `Max processes`, `Max core file size`, `Max locked memory` … | `cat /proc/1234/limits`; то же — `prlimit --pid 1234` |
| `fd/` | открытые дескрипторы — символические ссылки на файлы, сокеты, каналы | `sudo ls -l /proc/1234/fd`; число: `sudo ls /proc/1234/fd \| wc -l` |
| `fdinfo/N` | позиция и флаги дескриптора N | `sudo cat /proc/1234/fdinfo/5` |
| `cmdline` | командная строка, аргументы разделены нулевым байтом | `tr '\0' ' ' < /proc/1234/cmdline; echo` |
| `environ` | окружение на момент запуска, разделитель — нулевой байт; доступно владельцу и root | `sudo cat /proc/1234/environ \| tr '\0' '\n'` (перенаправление `<` выполнила бы ваша оболочка без прав root) |
| `io` | счётчики ввода-вывода: `rchar`, `wchar` (байты через read/write, включая кэш и сокеты), `syscr`, `syscw` (число вызовов), `read_bytes`, `write_bytes` (реально с блочных устройств и на них), `cancelled_write_bytes` | `sudo cat /proc/1234/io` |
| `smaps_rollup` | сумма по всем отображениям: `Rss`, `Pss`, `Pss_Anon`, `Pss_File`, `Pss_Shmem`, `Shared_Clean/Dirty`, `Private_Clean/Dirty`, `Anonymous`, `AnonHugePages`, `Swap`, `SwapPss` | `sudo cat /proc/1234/smaps_rollup` |
| `maps`, `smaps`, `numa_maps` | карта адресного пространства; подробно по каждому отображению; раскладка по NUMA-узлам | `sudo less /proc/1234/smaps` |
| `cwd`, `exe`, `root` | ссылки на текущий каталог, исполняемый файл, корень | `sudo ls -l /proc/1234/exe` (пометка `(deleted)` — бинарник заменён обновлением, процесс работает на старом) |
| `oom_score`, `oom_score_adj` | оценка для OOM killer и её сдвиг | раздел 6.7 |
| `cgroup` | к какой cgroup относится процесс | `cat /proc/1234/cgroup` |
| `task/<tid>/…` | то же по каждому потоку | `ls /proc/1234/task \| wc -l` |
| `stack`, `wchan` | стек ядра и функция ожидания (нужен root) | `sudo cat /proc/1234/stack` — где именно в ядре «висит» процесс в состоянии D |
| `sched`, `schedstat` | статистика планировщика (время на CPU, время ожидания в очереди) | `cat /proc/1234/schedstat` |

```bash
# лимит дескрипторов и текущее их число у всех rphost
for p in $(pgrep -x rphost); do
  printf '%s fd=%s limit=%s threads=%s\n' "$p" "$(sudo ls /proc/$p/fd | wc -l)" \
    "$(awk '/Max open files/{print $4}' /proc/$p/limits)" "$(awk '/^Threads/{print $2}' /proc/$p/status)"
done

# скорость ввода-вывода процесса за 10 секунд (по /proc/<pid>/io)
p=1234; a=$(sudo awk '/^write_bytes/{print $2}' /proc/$p/io); sleep 10
b=$(sudo awk '/^write_bytes/{print $2}' /proc/$p/io); echo "$(( (b-a)/10/1024 )) kB/s write"

# с какими параметрами и окружением запущен агент 1С и postmaster
tr '\0' ' ' < /proc/$(pgrep -o ragent)/cmdline; echo
sudo cat /proc/$(pgrep -o -u postgres postgres)/environ | tr '\0' '\n' | grep -E '^(PG|LANG|LC_|PATH)'
```

Изменить лимит у работающего процесса (до его перезапуска): `sudo prlimit --pid 1234 --nofile=65536:65536`. Постоянно для службы — `LimitNOFILE=` в юните.

### 11.3. lsof

`lsof` перечисляет открытые файлы (включая сокеты, каналы, отображённые библиотеки). Для чужих процессов нужен root. По умолчанию условия объединяются по ИЛИ; `-a` делает И.

| Опция | Назначение |
|---|---|
| `-p PID[,PID]` | файлы процесса (`^PID` — исключить) |
| `-u пользователь` | файлы пользователя |
| `-c префикс` | по началу имени команды (`-c /regex/` — регулярное выражение) |
| `-i [4\|6][протокол][@хост][:порт]` | сетевые сокеты: `-i :5432`, `-iTCP:1540-1591`, `-i4TCP@10.0.0.5:5432` |
| `-sTCP:LISTEN` | вместе с `-iTCP` — только слушающие |
| `-n`, `-P` | не преобразовывать адреса в имена / порты в названия служб (быстрее) |
| `+D каталог` | все открытые файлы в каталоге и ниже (медленно на больших деревьях); `+d` — только верхний уровень |
| `+L1` | файлы с числом ссылок меньше 1 — удалённые, но открытые |
| `-d список` | только указанные дескрипторы (`-d cwd,txt,0-2`) |
| `-t` | печатать только PID (для подстановки в другие команды) |
| `-r N` | повторять каждые N секунд |

Колонка `FD`: `cwd` — текущий каталог, `rtd` — корень, `txt` — исполняемый код, `mem` — отображённый в память файл, число с суффиксом `r`/`w`/`u` — дескриптор, открытый на чтение/запись/оба. Колонка `TYPE`: `REG`, `DIR`, `CHR`, `FIFO`, `unix`, `IPv4`, `IPv6`, `DEL` (удалённый отображённый файл).

```bash
sudo lsof -nP -p 1234 | less                       # всё, что открыл процесс
sudo lsof -nP -a -p 1234 -iTCP                     # только его TCP-сокеты
sudo lsof -nP -iTCP -sTCP:LISTEN                   # кто что слушает
sudo lsof -nP -i :5432 | head                      # кто связан с портом PostgreSQL
sudo lsof -nP -a -u usr1cv8 -iTCP:5432 | wc -l     # соединения сервера 1С с PostgreSQL
sudo lsof +D /var/lib/postgresql/17/main/pg_wal | head   # кто держит файлы WAL
sudo lsof -u usr1cv8 | wc -l                       # сколько файлов открыто пользователем 1С
sudo lsof +L1                                      # удалённые, но открытые файлы (колонка SIZE/OFF — сколько места удерживается)
sudo lsof -nP | grep '(deleted)' | sort -k7 -n -r | head
```

Удалённые, но открытые файлы. `rm` убирает только имя; место освобождается, когда файл закроет последний процесс. Симптом: `df` показывает заполненный раздел, а `du` столько не находит. Решения по возрастанию жёсткости:

1. Заставить процесс переоткрыть файл (для журнала PostgreSQL при `logging_collector = on` — `SELECT pg_rotate_logfile();` или `pg_ctl logrotate`; для технологического журнала 1С — файлы закрываются при ротации по часам и по `history` в `logcfg.xml`).
2. Обнулить содержимое через дескриптор, не трогая процесс: `sudo truncate -s 0 /proc/<PID>/fd/<N>` — допустимо только для текстовых журналов, никогда для файлов данных СУБД.
3. Перезапустить процесс, удерживающий файл.

На будущее журналы не удаляют через `rm`, а ротируют (`logrotate` с `copytruncate` либо штатная ротация приложения).

Особенность пакетов Debian/Ubuntu: по умолчанию `logging_collector = off`, журнал `/var/log/postgresql/postgresql-NN-main.log` — это перенаправленный stderr сервера (его открывает `pg_ctlcluster` при запуске, и дескриптор наследуют все процессы `postgres`), а ротацию выполняет `logrotate` по правилу `/etc/logrotate.d/postgresql-common` (сверено по исходникам postgresql-common: `/var/log/postgresql/*.log { weekly; rotate 10; copytruncate; delaycompress; compress; notifempty; missingok; su root root }`) — то есть раз в неделю, 10 поколений, в режиме `copytruncate`. Поэтому `pg_rotate_logfile()` здесь ничего не сделает (он работает только с `logging_collector = on`), а удалённый через `rm` журнал будет удерживаться всеми процессами PostgreSQL до перезапуска кластера — в этой конфигурации применяйте способ 2 (`truncate` через `/proc/<PID postmaster>/fd/<N>`; номер дескриптора журнала — `sudo ls -l /proc/<PID>/fd | grep postgresql-`).

### 11.4. fuser

Кто использует файл, каталог, точку монтирования или порт (пакет `psmisc`).

```bash
sudo fuser -vm /mnt/backup          # все процессы, использующие файловую систему (перед umount)
sudo fuser -v /var/lib/postgresql   # кто держит каталог (c — как cwd, e — исполняемый файл, f — открытый файл, m — отображение)
sudo fuser -v -n tcp 1541           # кто занимает TCP-порт 1541 (также запись 1541/tcp)
sudo fuser -k -TERM -m /mnt/backup  # послать сигнал всем найденным (осторожно; -i — с подтверждением)
```

## 12. Трассировка: strace, ltrace, gdb/gcore

### 12.1. strace

Показывает системные вызовы и сигналы процесса. Для присоединения к чужому процессу нужен root (в Ubuntu `kernel.yama.ptrace_scope=1` разрешает непривилегированному пользователю трассировать только своих потомков).

| Опция | Назначение |
|---|---|
| `-p PID` | присоединиться к работающему процессу (можно несколько `-p`) |
| `-f` | следить за потомками и за всеми потоками (`-p PID -f` присоединяется ко всем потокам многопоточного процесса) |
| `-ff -o файл` | вывод каждого процесса/потока в отдельный файл `файл.PID` |
| `-o файл` | писать в файл, а не в stderr |
| `-e trace=…` | фильтр вызовов: имена (`openat,read,write`) или классы `%file`, `%process`, `%network` (`%net`), `%signal`, `%ipc`, `%desc`, `%memory`; `!` — отрицание. Формы без `%` (`trace=file`) устарели |
| `-e signal=…`, `-e status=failed` | фильтр сигналов; только вызовы с данным статусом |
| `-z` / `-Z` | только успешные / только неуспешные вызовы |
| `-c` | не печатать вызовы, а выдать сводку: время, число вызовов и ошибок по каждому; `-C` — и то и другое |
| `-S time\|calls\|errors\|name` | сортировка сводки |
| `-w` | в сводке считать астрономическое время вызова, а не системное |
| `-T` | длительность каждого вызова |
| `-t` / `-tt` / `-ttt` | время с точностью до секунды / микросекунды / в секундах эпохи |
| `-r` | относительное время между вызовами |
| `-s N` | длина печатаемых строк (по умолчанию 32) |
| `-y` / `-yy` | показывать путь для дескриптора / подробности сокета |
| `-k` | стек пользовательского пространства после каждого вызова |
| `-P путь` | только вызовы, затрагивающие путь |
| `-u пользователь` | запустить команду от имени пользователя |

```bash
sudo strace -c -f -p 1234                       # сводка; остановить Ctrl+C через 10–20 с
sudo strace -c -w -f -p 1234                    # то же по астрономическому времени (видно, где ждёт)
sudo strace -f -tt -T -e trace=%network -p 1234 -o /var/tmp/net.strace     # сетевые вызовы с длительностью
sudo strace -f -tt -T -y -e trace=read,write,pread64,pwrite64,fsync,fdatasync -p 1234 -o /var/tmp/io.strace
sudo strace -f -e trace=%file -Z -p 1234        # неуспешные файловые операции (ENOENT, EACCES)
sudo strace -tt -T -y -p "$(pgrep -n -u postgres postgres)"   # что делает конкретный backend
strace -f -o /var/tmp/start.strace команда      # трассировка запуска программы с нуля
```

Что видно и как читать: процесс «висит» в `futex(...)` — ждёт мьютекс/условную переменную (внутренняя блокировка или ожидание работы); в `epoll_wait`/`poll`/`recvfrom` на сокете — ждёт сеть (для `rphost` — ответ СУБД или клиента; для backend'а — команду клиента); длинные `pread64`/`fdatasync` — медленный диск; частые `EAGAIN` — норма для неблокирующих сокетов.

Предостережения (man strace: «A traced process runs slowly»): трассируемый процесс замедляется в разы; `-f` на `rphost` с сотней потоков даёт огромный поток событий — ограничивайте фильтром `-e` и временем; процесс, присоединённый через `-p`, может получить ложный `EINTR`. Для сводки с меньшими накладными расходами есть `sudo perf trace -p PID` и `-s` (итоги).

### 12.2. ltrace

Трассировка вызовов разделяемых библиотек (пакет `ltrace`, universe): `ltrace -p PID`, `ltrace -c команда` (сводка), `-f` (потомки), `-e шаблон` (фильтр), `-S` (плюс системные вызовы). На практике для 1С и PostgreSQL почти не применяется: накладные расходы выше, чем у strace, а на современных бинарниках работает не всегда. Достаточно знать, что инструмент существует.

### 12.3. gdb и gcore

```bash
sudo apt install gdb
# стеки всех потоков процесса одним выстрелом (процесс на время снятия остановлен)
sudo gdb -p 1234 -batch -ex 'thread apply all bt' > /var/tmp/stack-1234.txt 2>&1

# дамп памяти работающего процесса без его завершения
sudo gcore -o /var/tmp/core-rphost 1234         # получится файл /var/tmp/core-rphost.1234
```

- На время работы `gdb`/`gcore` процесс остановлен (ptrace-stop). Для `rphost` с десятками гигабайт памяти `gcore` идёт минуты, файл займёт место порядка объёма памяти процесса — проверьте `df -h` заранее. Кластер 1С может за это время счесть процесс не отвечающим.
- Никогда не подключайте отладчик к postmaster на рабочем сервере; к отдельному backend'у — кратко и понимая, что он может удерживать блокировки.
- Без отладочных символов стеки платформы 1С малоинформативны для администратора; их назначение — передать в поддержку 1С вместе с дампом. Автоматическое формирование дампов при аварийном завершении процессов 1С на Linux настраивается средствами ОС: лимит core-файла (`LimitCORE=infinity` в юните), `kernel.core_pattern` или `systemd-coredump`; в Ubuntu по умолчанию core-файлы перехватывает `apport`. Официально («Руководство администратора. Клиент-серверный вариант», раздел «Система мониторинга кластера», редакции 8.3.27 и 8.5.1 на kb.1ci.com): «Crash dumps are created according to the following rules… On Windows, settings from logcfg.xml are used. On Linux, the OS settings are used, and the crash dump recording starts by sending a signal to the SIGABRT process. In this case, the standard crash dump is performed by the SIGSEGV signal». То есть в Windows дампы настраиваются элементом `<dump>` файла `logcfg.xml`, а в Linux — настройками ОС: дамп — это core-файл, порождаемый сигналом (`SIGABRT`, когда процесс завершает механизм мониторинга кластера в 8.3.27+; `SIGSEGV` — при обычном аварийном завершении). Атрибуты элемента `<dump>` (`create`, `location`, `type`) на место и состав core-файла в Linux не влияют — это определяют `LimitCORE`/`ulimit -c` и `kernel.core_pattern`. Пошаговая методика 1С по сбору дампов в Linux (статья ИТС) в этой сессии недоступна — см. конец раздела «Источники». Практическая проверка на стенде: `cat /proc/sys/kernel/core_pattern` (куда ядро отдаёт core-файлы; строка, начинающаяся с `|`, — обработчик: `apport` или `systemd-coredump`), `grep -i core /proc/$(pgrep -o rphost)/limits` (нулевой мягкий лимит = дампов не будет), `coredumpctl list` (если установлен `systemd-coredump`), каталог `/var/lib/apport/coredump/` — туда `apport` в актуальных Ubuntu складывает core-файлы (сверено по исходному коду apport, основная ветка: `core_dir = "/var/lib/apport/coredump"`, имя файла `core.<путь_к_программе_с_подчёркиваниями>.<uid>.<boot_id>.<pid>.<время>`, не более 5 файлов на пользователя — более старые удаляются; для программ не из пакетов Ubuntu, к которым относится и платформа 1С, отчёт в `/var/crash` не создаётся, но core-файл пишется, если лимит core-файла процесса ненулевой). Помните о размере: core-файл `rphost` сопоставим с объёмом его памяти, а каталог `/var/lib/apport/coredump` лежит на корневом разделе.
- Ручной способ получить дамп с завершением процесса — `kill -ABRT <PID>` (действие по умолчанию — завершение с core dump), если лимит core-файла это позволяет: `grep core /proc/<PID>/limits`. К процессам PostgreSQL это не применять: у них сигналы имеют собственный смысл (раздел 4.3).

## 13. cgroups v2 и ограничение ресурсов через systemd

### 13.1. Основы

- Все актуальные Ubuntu LTS используют единую иерархию cgroup v2, смонтированную в `/sys/fs/cgroup`. Проверка: `stat -fc %T /sys/fs/cgroup` → `cgroup2fs`. В Ubuntu 26.04 (systemd 259) поддержка cgroup v1 удалена совсем (в NEWS systemd 257 иерархии «legacy» и «hybrid» объявлены устаревшими, а их полное удаление назначено на v258); директивы `CPUShares=`, `MemoryLimit=`, `BlockIO*=` в man systemd.resource-control названы «fully deprecated» начиная с systemd 252 — используйте `CPUWeight=`, `MemoryMax=`, `IO*=`.
- systemd помещает каждую службу в свою cgroup: `system.slice/<юнит>.service`; экземпляры шаблонов — в промежуточный срез (`system.slice/system-postgresql.slice/postgresql@17-main.service`). Сеансы пользователей — в `user.slice`.
- Учёт: `DefaultMemoryAccounting=yes` и учёт CPU включены по умолчанию; учёт ввода-вывода (`IOAccounting=`) по умолчанию выключен.

```bash
systemd-cgls                                  # дерево cgroup с процессами
systemd-cgls -u postgresql@17-main.service    # одна служба
systemd-cgtop                                 # «top» по cgroup: Tasks, %CPU, Memory, Input/s, Output/s
systemd-cgtop -m --depth=4                    # сортировка по памяти, глубже по дереву
systemd-cgtop -b -n 3 -d 5                    # пакетный режим
systemctl status postgresql@17-main           # строки Tasks, Memory, CPU и дерево процессов юнита
systemctl show "$U1C" -p ControlGroup -p MemoryCurrent -p CPUUsageNSec -p TasksCurrent \
  -p MemoryHigh -p MemoryMax -p CPUWeight -p CPUQuotaPerSecUSec -p TasksMax -p OOMPolicy
```

Клавиши `systemd-cgtop`: `p`/`t`/`c`/`m`/`i` — сортировка по пути, числу задач, CPU, памяти, вводу-выводу; `%` — CPU в процентах или времени; `+`/`-` — интервал; `k`/`P` — считать потоки ядра / только процессы; `q` — выход. Колонки ввода-вывода заполняются только при включённом `IOAccounting=yes`.

Прямое чтение файлов cgroup (семантика — документация ядра «Control Group v2»):

```bash
CG="/sys/fs/cgroup$(systemctl show -p ControlGroup --value postgresql@17-main.service)"
cat "$CG/memory.current"        # текущее потребление (включая страничный кэш, отнесённый на cgroup)
cat "$CG/memory.peak"           # пик (ядро 5.19+, т. е. Ubuntu 24.04+)
cat "$CG/memory.events"         # low high max oom oom_kill oom_group_kill
grep -E '^(anon|file|shmem|slab) ' "$CG/memory.stat"
cat "$CG/cpu.stat"              # usage_usec user_usec system_usec nr_periods nr_throttled throttled_usec
cat "$CG/io.stat"               # по устройствам MAJ:MIN: rbytes wbytes rios wios dbytes dios
cat "$CG/cpu.pressure" "$CG/memory.pressure" "$CG/io.pressure"   # PSI по этой службе
cat "$CG/cgroup.procs" | wc -l  # число процессов
```

`memory.events`: `high` — сколько раз процессы притормаживались из-за превышения `memory.high`; `max` — сколько раз потребление упиралось в `memory.max`; `oom_kill` — сколько процессов убито. `cpu.stat`: растущие `nr_throttled`/`throttled_usec` — служба упирается в `CPUQuota=`.

### 13.2. Директивы управления ресурсами (man systemd.resource-control)

| Директива | Файл cgroup | Смысл |
|---|---|---|
| `CPUWeight=1…10000` (по умолчанию 100; `idle`) | `cpu.weight` | относительная доля CPU при конкуренции; без конкуренции не ограничивает |
| `CPUQuota=NN%` | `cpu.max` | жёсткий потолок; 100 % = одно ядро, `400%` = четыре ядра |
| `AllowedCPUs=0-7` | `cpuset.cpus` | на каких CPU разрешено выполняться |
| `MemoryMin=`, `MemoryLow=` | `memory.min`, `memory.low` | защита памяти службы от вытеснения (жёсткая / мягкая) |
| `MemoryHigh=` | `memory.high` | порог торможения: превышение не вызывает OOM, но процессы замедляются и их память активно вытесняется. systemd называет это основным механизмом контроля памяти |
| `MemoryMax=` | `memory.max` | абсолютный предел; при невозможности уложиться — OOM killer внутри cgroup |
| `MemorySwapMax=` | `memory.swap.max` | предел использования swap (`0` — запретить swap для службы) |
| `TasksMax=` | `pids.max` | предел числа процессов и потоков (по умолчанию 15 % от системного максимума) |
| `IOWeight=1…10000` (по умолчанию 100) | `io.weight` | относительная доля ввода-вывода |
| `IOReadBandwidthMax=`, `IOWriteBandwidthMax=` | `io.max` | потолок байт/с по устройству: `/dev/sda 50M` |
| `IOReadIOPSMax=`, `IOWriteIOPSMax=` | `io.max` | потолок IOPS по устройству |
| `IODeviceLatencyTargetSec=` | `io.latency` | целевая задержка: `/dev/sda 25ms` |
| `OOMScoreAdjust=`, `OOMPolicy=` | — | раздел 6.7 |
| `LimitNOFILE=`, `LimitNPROC=`, `LimitCORE=` | — (rlimit) | лимиты процесса, не cgroup |

Значения памяти — в байтах с суффиксами `K`, `M`, `G`, `T` (основание 1024), в процентах от RAM или `infinity`.

Замечание: `IOWeight=` действует только при планировщике BFQ или включённом контроллере `io.cost`. Это подтверждает документация ядра «Control Group v2»: пропорциональное распределение по весам обеспечивает либо контроллер модели стоимости iocost (`CONFIG_BLK_CGROUP_IOCOST`), либо — если для устройства выбран планировщик BFQ — собственная поддержка cgroup в BFQ; при этом iocost «is disabled by default and can be enabled by setting "enable" to 1» в `io.cost.qos` корневой cgroup. То есть на типичном сервере с планировщиком `none` или `mq-deadline` и невключённым `io.cost` директива `IOWeight=` молча ничего не делает. Жёсткие потолки `IO*Max=` (`io.max`) работают независимо от планировщика.

### 13.3. systemctl set-property

Меняет свойства «на лету» и сохраняет их drop-in'ом в `/etc/systemd/system.control/<юнит>.d/` (с `--runtime` — только до перезагрузки, в `/run/systemd/system.control/`).

```bash
# мягкий и жёсткий пределы памяти серверу 1С
sudo systemctl set-property "$U1C" MemoryHigh=24G MemoryMax=28G

# временно (до перезагрузки) отдать PostgreSQL вдвое больший вес CPU
sudo systemctl set-property --runtime postgresql@17-main.service CPUWeight=200

# ограничить службу четырьмя ядрами и включить учёт ввода-вывода
sudo systemctl set-property some-batch.service CPUQuota=400% IOAccounting=yes

# посмотреть и откатить
systemctl cat "$U1C"                      # в конце будут показаны drop-in'ы из system.control
sudo systemctl revert "$U1C"              # удалить все локальные изменения юнита (включая set-property и edit)
```

Постоянные настройки нагляднее держать в обычном drop-in'е: `sudo systemctl edit <юнит>` → секция `[Service]` → `sudo systemctl restart <юнит>` (для директив cgroup перезапуск не обязателен, достаточно `daemon-reload`; для `Limit*=`, `OOMScoreAdjust=`, `Environment=` перезапуск нужен).

Как применять к 1С и PostgreSQL (практика, не норма вендоров):

- Основной механизм ограничения памяти `rphost` — собственные пороги кластера 1С (перезапуск рабочих процессов), а не cgroup. `MemoryMax=` на юните 1С — страховка от того, чтобы сервер 1С не «съел» память PostgreSQL на общем хосте; при срабатывании ядро убьёт самый большой процесс юнита, то есть `rphost` с пользователями.
- `MemoryHigh=` чуть ниже `MemoryMax=` даёт торможение вместо убийства и время на реакцию.
- Жёсткий `MemoryMax=` на PostgreSQL опасен: в `memory.current` входит страничный кэш файлов данных, отнесённый на cgroup, и разделяемая память; при упоре в предел сначала вытесняется кэш (падает производительность), затем OOM убивает backend → crash recovery. Обычно PostgreSQL ограничивают его собственными параметрами (`shared_buffers`, `work_mem`, `max_connections`), а cgroup используют для защиты: `MemoryLow=`/`MemoryMin=`.
- `CPUWeight=` — безопасный способ расставить приоритеты между 1С, PostgreSQL и фоновыми задачами: работает только при конкуренции за CPU.

### 13.4. systemd-run: разовый запуск с лимитами

`systemd-run` запускает команду как временный юнит (service; с `--scope` — в текущем сеансе как scope) с любыми свойствами `-p`.

| Опция | Назначение |
|---|---|
| `-p Свойство=значение` | свойство юнита (как в `set-property`) |
| `--unit=имя` | имя юнита вместо автоматического |
| `--scope` | не служба, а scope: команда остаётся дочерней к вашей оболочке, с вашим окружением и терминалом |
| `--uid=`, `--gid=` | от имени какого пользователя и группы |
| `--nice=` | значение nice |
| `-t`/`--pty` | подключить терминал |
| `--wait` | дождаться завершения и показать итог (время, CPU, код возврата) |
| `-G`/`--collect` | убрать юнит после завершения, даже неуспешного |
| `--slice=` | в какой срез поместить |
| `-E ИМЯ=значение` | переменная окружения |
| `--on-calendar=`, `--on-active=` | запуск по таймеру |

```bash
# резервная копия с пониженным весом CPU и потолком записи, от пользователя postgres
sudo systemd-run --unit=pgdump-buh --uid=postgres --wait --collect \
  -p CPUWeight=20 -p Nice=10 -p IOWriteBandwidthMax='/dev/sda 60M' \
  /usr/bin/pg_dump -Fc -f /backup/buh.dump buh

# сжатие архива не более чем на двух ядрах и с пределом памяти
sudo systemd-run --wait --collect -p CPUQuota=200% -p MemoryMax=2G \
  /usr/bin/zstd -T2 -19 /backup/buh.dump

# интерактивно, в текущем терминале, с ограничением
sudo systemd-run --scope -p MemoryMax=4G -p CPUWeight=50 bash

# отложенный запуск через 30 минут
sudo systemd-run --on-active=30m --unit=late-vacuum --uid=postgres /usr/bin/vacuumdb --all --analyze-only

journalctl -u pgdump-buh        # вывод команды — в журнале
systemctl status pgdump-buh     # состояние и потребление
```

## 14. PSI и NUMA

### 14.1. PSI — Pressure Stall Information

Файлы `/proc/pressure/cpu`, `/proc/pressure/memory`, `/proc/pressure/io` (и `cpu.pressure`, `memory.pressure`, `io.pressure` в каждой cgroup). Формат:

```text
some avg10=2.04 avg60=0.75 avg300=0.40 total=157622151
full avg10=0.00 avg60=0.00 avg300=0.00 total=20023234
```

- `some` — доля времени (в процентах), когда хотя бы одна задача простаивала в ожидании ресурса; `full` — когда одновременно простаивали все не находящиеся в простое задачи (для CPU на уровне системы `full` не определён и показывается нулём).
- `avg10`/`avg60`/`avg300` — средние за 10, 60 и 300 секунд; `total` — накопленное время простоя в микросекундах.
- В отличие от load average PSI различает ресурсы и измеряет именно потерянное время.

```bash
grep . /proc/pressure/*                                  # всё сразу с именами файлов
watch -n 2 'grep . /proc/pressure/*'
cat "$CG/memory.pressure"                                # давление внутри одной службы
sar -q IO 1 5; sar -q MEM 1 5; sar -q CPU 1 5            # то же средствами sysstat
```

Ориентиры (эвристика): `cpu some avg60` десятки процентов — процессам заметно не хватает CPU; `memory full` устойчиво больше нуля — идёт интенсивное вытеснение, близко к «пробуксовке» (thrashing); `io full avg60` больше 10–20 % — работа упирается в диск. Если каталога `/proc/pressure` нет, PSI выключен в ядре (включается параметром загрузки `psi=1`). В штатных ядрах Ubuntu PSI включён: прямо по конфигурации ядра в этой сессии проверить не удалось, но это следует из того, что `systemd-oomd`, которому по man нужна сборка ядра с PSI («The kernel must be compiled with PSI support. This is available in Linux 4.20 and above»), с 22.04 штатно работает в Ubuntu Desktop на том же ядре `linux-generic`. Проверка на месте: `ls /proc/pressure/` и `grep PSI /boot/config-$(uname -r)` (ожидается `CONFIG_PSI=y` и не заданный `CONFIG_PSI_DEFAULT_DISABLED`). Документация ядра: «CPU full is undefined at the system level, but has been reported since 5.13, so it is set to zero for backward compatibility».

### 14.2. NUMA (кратко)

NUMA важна на многопроцессорных физических серверах и на ВМ, которым гипервизор отдал несколько виртуальных NUMA-узлов. Типичная небольшая ВМ имеет один узел — тогда этот раздел можно пропустить.

```bash
lscpu | grep -i numa                 # число узлов и распределение CPU
numactl --hardware                   # узлы, их CPU, объём и свободная память, матрица расстояний
numastat                             # счётчики numa_hit / numa_miss / numa_foreign / other_node по узлам
numastat -m                          # meminfo в разрезе узлов
numastat -p postgres                 # память процессов по узлам (по имени или PID)
numastat -p "$(pgrep -o rphost)"
sysctl kernel.numa_balancing vm.zone_reclaim_mode
```

- Признаки проблем: один узел исчерпан при свободном другом (локальное вытеснение и подкачка при «свободной» в сумме памяти), высокий `numa_miss`, большой `%sys`.
- `vm.zone_reclaim_mode` по умолчанию 0 (так и нужно для СУБД). Автобалансировку `kernel.numa_balancing` на серверах СУБД нередко отключают (практика; официальной рекомендации PostgreSQL нет).
- По материалам сообщества о 1С: рабочий процесс `rphost` тяготеет к одному NUMA-узлу, поэтому на многосокетных серверах увеличивают число рабочих процессов.
- Запуск с политикой: `numactl --interleave=all команда`, `numactl --cpunodebind=0 --membind=0 команда`; для служб — `NUMAPolicy=`/`NUMAMask=` в юните systemd.

## 15. Методика: «сервер тормозит»

### 15.0. До команд

Зафиксируйте: точное время начала; что именно медленно (всё у всех, одна база, одна операция, один пользователь); что менялось (обновление конфигурации или платформы, регламентные задания, резервное копирование, обновление ОС, изменения на хосте виртуализации). Не перезагружайте сервер до снятия среза — перезагрузка уничтожает картину (см. скрипт в 15.6).

### 15.1. Первые 60 секунд (чек-лист Б. Грегга, адаптирован к 1С + PostgreSQL)

| № | Команда | На что смотреть | Что это значит здесь |
|---|---|---|---|
| 1 | `uptime` | три числа LA против `nproc`; тренд 1 → 5 → 15 мин | растёт или уже спадает; LA выше числа ядер — есть очередь (к CPU или к диску) |
| 2 | `sudo dmesg -T \| tail -n 30` | OOM killer, ошибки ввода-вывода (`I/O error`, `blk_update_request`), `hung_task`, ошибки файловой системы, сетевые сообщения | убит `rphost`/`postgres`; диск ВМ отвечает с ошибками или тайм-аутами |
| 3 | `vmstat 1` | `r` против числа ядер; `b`; `si`/`so`; `us`/`sy`/`id`/`wa`/`st`; `cs` | `r` > ядер и `id` ≈ 0 — CPU; `b` > 0 и `wa` высокий — диск; `si`/`so` > 0 — память; `st` > 5–10 % — хост |
| 4 | `mpstat -P ALL 1` | равномерность по ядрам, `%sys`, `%soft`, `%steal` | одно ядро 100 % — однопоточная операция (один вызов 1С или один запрос) |
| 5 | `pidstat 1` | какие процессы и сколько `%usr`/`%system`, `%wait` | `rphost` — код конфигурации/платформы; `postgres` — запросы; `%wait` — стоят в очереди за CPU |
| 6 | `iostat -xz 1` | `r_await`, `w_await`, `aqu-sz`, `r/s`, `w/s`, `rkB/s`, `wkB/s`, `%util` | диск не справляется: await в десятках мс, очередь; затем `iotop -oPa` — кто |
| 7 | `free -m` | `available`, `Swap used` | мало `available` + растущий swap — нехватка памяти |
| 8 | `sar -n DEV 1` | `rxkB/s`, `txkB/s`, `%ifutil` | упираемся ли в пропускную способность интерфейса |
| 9 | `sar -n TCP,ETCP 1` | `active/s`, `passive/s`, `retrans/s` | повторные передачи — потери в сети; всплеск `passive/s` — шторм подключений |
| 10 | `top` (затем `1`, `c`, `H`) | общая картина, `wa`, `st`, лидеры по CPU и памяти, `kswapd0` | перепроверка всего перечисленного |

Дополнительно на первой минуте: `grep . /proc/pressure/*` (PSI), `df -hT` (место), `systemctl --failed` (упавшие службы).

### 15.2. Метод USE

Для каждого ресурса проверяются три вещи: Utilization — насколько занят; Saturation — есть ли очередь (работа, которую ресурс не успевает обслужить); Errors — ошибки. По Греггу: 100 % использования обычно означает узкое место (подтверждайте насыщением); использование выше примерно 70 % уже может вызывать проблемы — усреднение скрывает пики, а непрерываемые ресурсы вроде дисков копят очереди; любое ненулевое насыщение и ненулевые растущие счётчики ошибок — повод разбираться.

| Ресурс | Utilization | Saturation | Errors |
|---|---|---|---|
| CPU | `mpstat -P ALL 1` (100 − `%idle`), `top`, `sar -u` | `vmstat 1` (`r` > ядер), `sar -q` (`runq-sz`), `pidstat` (`%wait`), `/proc/pressure/cpu`, `%steal` | `dmesg` (MCE, `soft lockup`) |
| Память | `free -m` (`available`), `sar -r`, `smem` | `vmstat 1` (`si`/`so`), `sar -B` (`pgscand/s`, `majflt/s`), `sar -W`, `/proc/pressure/memory`, `kswapd0` в `top` | `journalctl -k -g oom`, отказы `malloc` в журналах приложений |
| Диск (ввод-вывод) | `iostat -xz 1` (`%util`, `r/s`, `w/s`, `kB/s`) | `aqu-sz`, `r_await`/`w_await`, `vmstat` (`b`), `/proc/pressure/io` | `dmesg` (`I/O error`), `smartctl` (на физическом сервере), ошибки файловой системы |
| Диск (ёмкость) | `df -hT`, `df -i` | — | «No space left on device» в журналах |
| Сеть | `sar -n DEV 1` (`%ifutil`, кБ/с) | `nstat` (переполнения очередей), `ss -lnt` (очередь accept: Recv-Q против Send-Q) | `sar -n EDEV 1`, `ip -s link`, `retrans/s` |
| Дескрипторы, процессы | `/proc/sys/fs/file-nr`, `ls /proc/<pid>/fd \| wc -l` против `limits`, `TasksCurrent` против `TasksMax` | — | «Too many open files», «Resource temporarily unavailable» (fork) |
| Программные ресурсы | число соединений к PostgreSQL против `max_connections`; число сеансов и `rphost` | backend'ы в `waiting`, ожидания блокировок 1С | ошибки в технологическом журнале 1С и журнале PostgreSQL |

### 15.3. Как отличить нехватку CPU, памяти и диска

| Картина | Диагноз | Следующий шаг |
|---|---|---|
| `us`+`sy` > 85–90 %, `id` ≈ 0, `wa` мал, `r` устойчиво > числа ядер, `si`/`so` = 0, `cpu some` в PSI высок | не хватает CPU | `pidstat 1` / `top`: кто — `rphost` или `postgres` (ниже) |
| `sy` велик (десятки процентов), `cs` в `vmstat` — сотни тысяч | ядро занято: вытеснение памяти, уплотнение THP (`khugepaged`, `kcompactd`), слишком много активных соединений, шторм переключений контекста | `top` (потоки ядра), `perf top`, `pidstat -w`, проверить THP и число активных backend'ов |
| `st` > 5–10 % | CPU отбирает гипервизор | смотреть хост: число vCPU, соседние ВМ |
| `available` мал, swap растёт, `si`/`so` > 0, `kswapd0` в топе, `memory some/full` > 0, возможно OOM в `dmesg`; при этом `wa` тоже растёт (подкачка — это ввод-вывод) | не хватает памяти | `ps --sort=-rss`, `smem`: кто вырос; сверить `shared_buffers`, `work_mem`, число сеансов, память `rphost` |
| `wa` высок, `b` > 0, `id` при этом есть, LA высок; `await` — десятки мс и больше, `aqu-sz` > 1, `io some/full` > 0; `si`/`so` = 0 | не хватает диска | `sudo iotop -oPa`, `pidstat -d 5`: кто пишет и читает |
| LA высок, CPU простаивает, диск спокоен, процессы в `D` | зависший ввод-вывод (сетевое хранилище, проблемы виртуального диска) | `ps` по состоянию `D`, `sudo cat /proc/<pid>/stack`, `dmesg` |
| все ресурсы свободны, а пользователи ждут | ожидания, а не нагрузка: блокировки СУБД (backend'ы `waiting`, `idle in transaction`), управляемые блокировки 1С, однопоточная длинная операция, внешние сервисы, сеть до клиентов | `pg_stat_activity` / `pg_locks`, технологический журнал 1С (события `TLOCK`, `TTIMEOUT`, `TDEADLOCK`, `DBPOSTGRS`, `CALL`), консоль кластера |

Память и диск легко перепутать: при нехватке памяти диск тоже загружен (подкачка и потеря файлового кэша — PostgreSQL начинает читать с диска то, что раньше лежало в кэше ОС). Различитель — `si`/`so` и `pgscand/s`: если они ненулевые, первопричина в памяти.

CPU: кто виноват.

- Лидируют `rphost`: исполняется код конфигурации или платформы (обработка больших коллекций в памяти, обмены, формирование отчётов и печатных форм, фоновые задания). Если занят один поток одного `rphost` — это один серверный вызов; если много — массовая нагрузка или регламентные задания. Лидирует `rmngr` — по публикациям сообщества, чаще всего обновление индекса полнотекстового поиска.
- Лидируют `postgres`: тяжёлые запросы (последовательные сканирования, сортировки, хеш-соединения при данных в кэше), массовая запись, автоочистка. Десятки backend'ов по 100 % одновременно — либо однотипный неудачный запрос, либо не хватает ядер под параллельную нагрузку.
- И те и другие понемногу, а CPU исчерпан — серверу мало ядер под текущую нагрузку, либо 1С и PostgreSQL мешают друг другу: рассмотреть `CPUWeight=`, разнесение по разным ВМ.

### 15.4. На что смотреть у rphost

```bash
# 1. сколько их, как давно живут (частые перезапуски = срабатывают пороги памяти или падения)
ps -C rphost -o pid,lstart,etime,nlwp,pcpu,pmem,rss,vsz

# 2. загрузка по потокам: один поток 100 % или много
top -H -b -n 1 -p "$(pgrep -d, rphost)" | head -40
pidstat -t -p "$(pgrep -o rphost)" 5 1 | sort -k9 -n -r | head   # сортировка по колонке %CPU (9-я при 24-часовом формате времени)

# 3. память: анонимная, пик, swap, число потоков
for p in $(pgrep -x rphost); do echo "== $p"; grep -E 'VmHWM|VmRSS|RssAnon|VmSwap|Threads' /proc/$p/status; done

# 4. дескрипторы против лимита и соединения с СУБД
for p in $(pgrep -x rphost); do echo "$p fd=$(sudo ls /proc/$p/fd | wc -l) pg=$(sudo ss -Htnp 'dport = :5432' | grep -c "pid=$p,")"; done

# 5. чем занят «зависший» рабочий процесс
sudo strace -c -w -f -p <PID>          # 10–20 секунд, Ctrl+C: futex (ожидание), recvfrom/poll (сеть, СУБД), read/write (файлы)
sudo cat /proc/<PID>/stack             # если состояние D
journalctl -u "$U1C" --since '-1h' --no-pager | tail -n 50

# 6. сопоставление с кластером 1С (нужен запущенный ras)
/opt/1cv8/x86_64/<версия>/rac cluster list
/opt/1cv8/x86_64/<версия>/rac process list --cluster=<UUID>      # pid, память, число соединений, средние времена вызовов
/opt/1cv8/x86_64/<версия>/rac session list --cluster=<UUID>      # сеансы: пользователь, база, длительность и потребление текущего вызова
```

Признаки и их смысл:

- RSS/`RssAnon` растёт сутками и не возвращается — фрагментация или утечка; настроить пороги памяти и перезапуск рабочих процессов в кластере, искать «тяжёлые» сеансы через `rac session list`.
- Время жизни `rphost` — минуты, PID постоянно меняются — процесс перезапускается: либо пороги памяти слишком низкие, либо аварийные завершения (ищите core-файлы, записи в `journalctl -u`, события `EXCP` технологического журнала).
- Один поток 100 % долгое время — длинный серверный вызов; какой именно — технологический журнал (`CALL`/`SCALL` с длительностью) и `rac session list`.
- `rphost` почти не потребляет CPU, а пользователи ждут — ждёт СУБД (смотреть backend'ы) или блокировки.
- Число потоков и дескрипторов приближается к лимитам (`TasksMax` юнита, `Max open files`) — поднять `LimitNOFILE=`/`TasksMax=`.

### 15.5. На что смотреть у процессов postgres

```bash
# 1. картина по процессам: заголовок говорит, кто, откуда и что делает
ps -u postgres -o pid,stat,pcpu,pmem,rss,etime,args --sort=-pcpu | head -30
ps -u postgres -o args= | grep -c ' waiting$'                 # ждут блокировку
ps -u postgres -o args= | grep -c 'idle in transaction'       # транзакция открыта, запросов нет

# 2. ввод-вывод: служебные процессы и backend'ы
sudo iotop -oPa -u postgres
pidstat -d -l -C postgres 5 3

# 3. собственная память самых «толстых» backend'ов (RssAnon, КиБ)
for p in $(pgrep -u postgres postgres); do
  printf '%s %s %s\n' "$(awk '/^RssAnon:/{print $2}' /proc/$p/status)" "$p" "$(tr '\0' ' ' < /proc/$p/cmdline | cut -c1-80)"
done | sort -rn | head

# 4. временные файлы (сортировки и хеши мимо work_mem) и WAL
sudo du -sh /var/lib/postgresql/17/main/base/pgsql_tmp /var/lib/postgresql/17/main/pg_wal

# 5. от PID процесса ОС — к запросу
sudo -u postgres psql -X -c "SELECT pid, usename, datname, client_addr, client_port, state, wait_event_type, wait_event,
  now()-xact_start AS xact_age, now()-query_start AS query_age, left(query,150) AS query
  FROM pg_stat_activity WHERE state <> 'idle' ORDER BY xact_start NULLS LAST LIMIT 30;"

# 6. кто кого блокирует
sudo -u postgres psql -X -c "SELECT pid, pg_blocking_pids(pid) AS blocked_by, wait_event_type, wait_event, left(query,100) AS query
  FROM pg_stat_activity WHERE cardinality(pg_blocking_pids(pid)) > 0;"
```

Для Postgres Pro: `psql` лежит в `/opt/pgpro/1c-NN/bin/`, каталог данных — `/var/lib/pgpro/1c-NN/data`.

Сопоставление backend'а с рабочим процессом 1С на одном хосте: в заголовке backend'а и в `pg_stat_activity.client_port` указан порт клиента; тот же локальный порт виден у `rphost`: `sudo ss -Htnp 'dport = :5432' | grep ':<порт> '` → в поле `users:(("rphost",pid=…))` будет PID рабочего процесса.

Признаки и их смысл:

- Backend в состоянии `R` со 100 % CPU — выполняет запрос на процессоре; в `D` — читает или пишет на диск; в `S` с `waiting` в заголовке — ждёт блокировку; в `S` и `idle in transaction` — ждёт следующую команду от `rphost`, удерживая транзакцию.
- `checkpointer` пишет «залпами» с ростом `w_await` — растянуть контрольные точки (`checkpoint_completion_target`, `max_wal_size`).
- `autovacuum worker` постоянно в топе по вводу-выводу — крупные таблицы с высокой сменяемостью строк; не отключать, а настраивать.
- Много backend'ов с растущим `RssAnon` — большие `work_mem`/`temp_buffers`, умноженные на число сеансов; сотни мегабайт на backend при сотне сеансов уже дают десятки гигабайт.
- `startup recovering` в списке процессов — идёт восстановление после сбоя: ждать, не убивать.
- Рост числа соединений до `max_connections` — в журнале «sorry, too many clients already»; проверить число `rphost` и пул соединений.

### 15.6. Срез состояния для последующего разбора

```bash
#!/usr/bin/env bash
# perf-snapshot.sh — срез состояния сервера за ~35 секунд. Запуск: sudo bash perf-snapshot.sh
set -u
D="/var/tmp/perf-$(hostname)-$(date +%F_%H%M%S)"
mkdir -p "$D" && cd "$D" || exit 1
{ date; uptime; echo "nproc: $(nproc)"; } > 00-uptime.txt
dmesg -T | tail -n 300 > 01-dmesg.txt 2>&1
free -m > 02-free.txt; cat /proc/meminfo > 02-meminfo.txt
grep . /proc/pressure/* > 03-psi.txt 2>&1
{ df -hT; df -i; } > 04-df.txt
ps -eo pid,ppid,user,stat,nlwp,pcpu,pmem,rss,vsz,etime,args --sort=-pcpu > 05-ps-by-cpu.txt
ps -eo pid,user,rss,pmem,args --sort=-rss | head -n 50 > 05-ps-by-rss.txt
ss -s > 06-ss.txt; ss -ltnp >> 06-ss.txt
top -b -n 2 -d 5 -c -w 250 > 10-top.txt &
vmstat -w -t 1 30 > 11-vmstat.txt &
mpstat -P ALL 5 6 > 12-mpstat.txt &
pidstat -u -r -d -l -h 5 6 > 13-pidstat.txt &
iostat -xzt 5 6 > 14-iostat.txt &
sar -n DEV 5 6 > 15-sar-net.txt &
sar -n TCP,ETCP 5 6 > 16-sar-tcp.txt &
systemd-cgtop -b -n 2 -d 5 --depth=4 > 17-cgtop.txt 2>&1 &
wait
sudo -u postgres psql -X -c "SELECT now(), pid, usename, datname, client_addr, client_port, state, wait_event_type, wait_event,
  now()-xact_start AS xact_age, now()-query_start AS query_age, pg_blocking_pids(pid) AS blocked_by, left(query,200) AS query
  FROM pg_stat_activity WHERE state <> 'idle' ORDER BY xact_start NULLS LAST;" > 20-pg_stat_activity.txt 2>&1
echo "Готово: $D"
```

После инцидента: `sar … -f /var/log/sysstat/saDD -s … -e …` (раздел 10), `atop -r … -b …` (раздел 3.3), `journalctl --since … --until …`, журнал PostgreSQL, технологический журнал и журнал регистрации 1С.

## Типичные ошибки и подводные камни

| Симптом | Причина | Решение |
|---|---|---|
| Load average 15 на 8 ядрах, а CPU простаивает | LA учитывает задачи в состоянии D (ждут диск) | `vmstat 1` (`b`, `wa`), `iostat -xz 1`, `/proc/pressure/io`; искать диск или зависший ввод-вывод |
| «Свободной памяти 200 МБ, сервер умирает» | смотрят колонку `free`, а не `available`; кэш — возвращаемая память | оценивать `available`, `si`/`so`, PSI memory |
| Сумма RSS процессов postgres больше объёма RAM | каждый backend показывает в RSS «потроганную» часть `shared_buffers` | считать PSS (`smem`) или `RssAnon` |
| `sar` отвечает «Cannot open /var/log/sysstat/saNN: No such file or directory» | фоновый сбор sysstat не включён | `ENABLED="true"` в `/etc/default/sysstat`, `systemctl enable --now sysstat` |
| `iotop` ругается на `CONFIG_TASK_DELAY_ACCT` / `kernel.task_delayacct`, нет колонок SWAPIN и IO | с ядра 5.14 учёт задержек выключен по умолчанию | `sudo sysctl kernel.task_delayacct=1` |
| Первая строка `vmstat`/`iostat` (и `mpstat`, `pidstat` без интервала) показывает «не то» | это средние с момента загрузки | задавать интервал и отбрасывать первый отчёт: `iostat -y` (везде), `vmstat -y` (только procps 4.x, 24.04+; в 22.04 такой опции нет — там первую строку просто пропускают) |
| `ps` показывает у процесса 3 % CPU, а `top` — 100 % | `%CPU` в `ps` — среднее за всю жизнь процесса | `top`, `pidstat 1` |
| `rphost` показывает 800 % CPU | проценты считаются от одного ядра, процесс многопоточный | `top -H -p PID`; делить на число ядер или клавиша `I` в top |
| `pg_ctl stop -m smart`, `pg_ctlcluster … -m smart stop` или `kill -TERM` postmaster'у «висит» | smart shutdown ждёт отключения всех клиентов, а `rphost` держит соединения | использовать fast (`-m fast`, он же по умолчанию у `pg_ctl` и `pg_ctlcluster`; `systemctl stop postgresql@NN-main` в Ubuntu — тоже fast); сначала останавливать сервер 1С |
| `systemctl stop postgresql@NN-main` идёт очень долго | fast shutdown завершает сеансы и выполняет контрольную точку остановки; при большом объёме «грязных» буферов и медленном диске это минуты; юнит ждёт до `TimeoutStopSec=1h` | ждать, смотреть `iostat -xz 1` и журнал PostgreSQL; не посылать `kill -9`; перед плановой остановкой можно заранее выполнить `CHECKPOINT;` |
| После `kill -9` одного backend'а отвалились все пользователи всех баз | postmaster трактует гибель backend'а от сигнала как аварию и перезапускает все серверные процессы с crash recovery | только `pg_cancel_backend()` / `pg_terminate_backend()` |
| После `kill -9` postmaster'а сервер не стартует: разделяемая память ещё используется | остались осиротевшие дочерние процессы | дождаться их выхода или завершить вручную; не удалять `postmaster.pid` при живых процессах |
| PostgreSQL принимает старые соединения, но не принимает новые | OOM killer убил postmaster (описано в документации PostgreSQL) | перезапустить PostgreSQL; настроить `OOMScoreAdjust` + `PG_OOM_ADJUST_FILE`, пересчитать память |
| После OOM одного `rphost` или backend'а остановилась вся служба | `OOMPolicy=stop` (значение systemd по умолчанию) | `OOMPolicy=continue` в drop-in'е, `Restart=`; устранить нехватку памяти |
| OOM при «свободной» по `free` памяти | сработал предел cgroup (`MemoryMax=`; в сообщении ядра «Memory cgroup out of memory») либо исчерпан NUMA-узел | `memory.events` юнита; пересмотреть лимит; `numastat -m` |
| `df` показывает 100 %, `du` столько не находит | удалённые, но открытые файлы (журналы, временные файлы) | `sudo lsof +L1`; переоткрыть или перезапустить держателя; не удалять журналы через `rm` |
| `ionice -c 3` не снижает влияние резервного копирования | у диска планировщик `none` (или `kyber`) — он не учитывает классы; классы поддерживают только `bfq` и `mq-deadline` (документация ядра) | проверить `cat /sys/block/<диск>/queue/scheduler`; лимиты cgroup: `systemd-run -p IOWriteBandwidthMax=…`, либо ограничение скорости в самой утилите |
| `IOWeight=` в юните задан, а эффекта нет | веса ввода-вывода работают только с BFQ или при включённом `io.cost` (по умолчанию выключен) | использовать жёсткие потолки `IOReadBandwidthMax=`/`IOWriteBandwidthMax=` |
| На общем хосте 1С + PostgreSQL память кончается раньше, чем кластер 1С начинает перезапускать `rphost` | пороги рабочего сервера 1С по умолчанию (`0`) — это 80 % и 95 % всей RAM машины, PostgreSQL в них не учитывается | задать «Временно допустимый» и «Критический объём памяти процессов» явно, в байтах (раздел 6.4) |
| `rphost` завершён сигналом `SIGABRT` (8.3.27+) или `SIGSEGV` (старше), в системе появился core-файл | это может быть не авария, а работа механизма мониторинга кластера: он так завершает зависшие процессы и снимает дамп | искать в технологическом журнале события `ATTN` и `EXCP` за это время; проверить свойства кластера «Принудительно завершать проблемные процессы» |
| Скрипт с `grep '^postgres: checkpointer'` на Ubuntu ничего не находит | пакеты Debian/Ubuntu задают `cluster_name = 'NN/main'`, заголовок выглядит как `postgres: 17/main: checkpointer` | искать по подстроке или `grep -E '^postgres: ([0-9]+/[^:]+: )?checkpointer'` |
| Сбор sysstat сам выключился после обновления пакета | юниты включили вручную, а в `/etc/default/sysstat` осталось `ENABLED="false"` — сценарий установки пакета приводит юниты в соответствие с этой настройкой | `ENABLED="true"` и `systemctl enable --now sysstat`, либо `sudo dpkg-reconfigure sysstat` |
| Время в `dmesg -T` не совпадает с реальным временем события | man dmesg: отметки `-T` могут быть неточны — источник времени журнала ядра не обновляется после приостановки системы (в ВМ — после паузы или сохранения состояния) | для времени событий использовать `journalctl -k` (там время записи в журнал) |
| После `echo 3 > /proc/sys/vm/drop_caches` «освободилась память», но всё стало медленнее | сброшен файловый кэш — второй уровень кэша PostgreSQL; данные теперь читаются с диска заново | на рабочем сервере кэш не сбрасывать; `buff/cache` — не «занятая» память |
| `strace -p`: «Operation not permitted» | трассировка чужого процесса без root (`ptrace_scope=1`) | `sudo strace …` |
| `dmesg`: «read kernel buffer failed: Operation not permitted» | `kernel.dmesg_restrict=1` в Ubuntu | `sudo dmesg -T` или `journalctl -k` |
| «Too many open files» в журналах 1С или PostgreSQL, хотя `ulimit -n` в консоли большой | у службы свои лимиты, из юнита systemd | `cat /proc/<PID>/limits`; `LimitNOFILE=` в drop-in'е и перезапуск |
| Процесс `<defunct>` не убивается `kill -9` | зомби уже мёртв; запись держится, пока родитель не заберёт код возврата | разбираться с родителем (PPID); единичные зомби безвредны |
| `kill -9` не действует на процесс в состоянии D | процесс в непрерываемом ожидании в ядре | устранять причину зависшего ввода-вывода; смотреть `/proc/<PID>/stack` |
| `renice`/`taskset`/`ionice`/`choom` «слетели» | действуют до перезапуска процесса | прописывать в юните: `Nice=`, `CPUAffinity=`/`AllowedCPUs=`, `IOSchedulingClass=`, `OOMScoreAdjust=` |
| В ВМ всё медленно, а внутри гостя ресурсы свободны, `st` = 0 | конкуренция на хосте: CPU, диск с файлом виртуального диска, антивирус; steal может не передаваться гостю | проверять нагрузку на Windows-хосте и настройки ВМ |
| `dstat: command not found` на 24.04+ | настоящего пакета dstat больше нет | `sudo apt install pcp` (даёт `dstat`) либо `dool`, либо `vmstat` + `iostat` + `sar` |
| `swapoff -a` «повесил» сервер | содержимое swap не поместилось в RAM | перед `swapoff` сверять `available` с занятым swap |
| `ps aux \| grep rphost` показывает лишнюю строку с самим `grep` | grep находит себя | `pgrep -a rphost` или `grep '[r]phost'` |
| `pkill -f postgres` убил и postmaster, и чужие процессы | `-f` сравнивает со всей командной строкой | сначала `pgrep -fa <шаблон>`, уточнять `-u`, `-x` |
| `gcore`/`gdb -p` «уронили» рабочий процесс 1С | процесс был остановлен на минуты, кластер счёл его зависшим | снимать дамп осознанно, в окно; иметь место на диске под core-файл |
| Перезагрузка «вылечила», причина неизвестна | не снят срез до перезагрузки, не включена история | включить sysstat и atop заранее; скрипт из 15.6 до любых действий |

| Диски: задержки и очередь | `iostat -xz -y 1 10` |

| К какому юниту относится PID | `systemctl status PID` / `ps -o unit= -p PID` |
| Лимиты и дескрипторы процесса | `cat /proc/PID/limits; sudo ls /proc/PID/fd \| wc -l` |
| Командная строка и окружение процесса | `tr '\0' ' ' < /proc/PID/cmdline; sudo cat /proc/PID/environ \| tr '\0' '\n'` |
| Открытые файлы и сокеты процесса | `sudo lsof -nP -p PID` |
| Кто занимает порт | `sudo ss -ltnp \| grep :1541` / `sudo fuser -v -n tcp 1541` |
| Удалённые, но открытые файлы | `sudo lsof +L1` |
| Сводка системных вызовов процесса | `sudo strace -c -w -f -p PID` (10–20 с, Ctrl+C) |
| Стеки всех потоков | `sudo gdb -p PID -batch -ex 'thread apply all bt'` |
| Дамп памяти без остановки службы | `sudo gcore -o /var/tmp/core PID` |
| Горячие функции | `sudo perf top -p PID` |
| Понизить приоритет фоновой задачи | `nice -n 19 ionice -c 3 команда` |
| Запустить с лимитами cgroup | `sudo systemd-run --wait --collect -p CPUWeight=20 -p MemoryMax=2G команда` |
| Ограничить службу на лету | `sudo systemctl set-property ЮНИТ MemoryHigh=24G MemoryMax=28G` |
| Потребление по службам | `systemd-cgtop -m` / `systemctl status ЮНИТ` |
| Счётчики cgroup юнита | `cat "/sys/fs/cgroup$(systemctl show -p ControlGroup --value ЮНИТ)/memory.events"` |
| История за окно времени: CPU | `sar -u -f /var/log/sysstat/saDD -s 14:00:00 -e 15:00:00` (вместо `-u`: `-r` память, `-d -p` диски, `-q` очередь, `-b` ввод-вывод, `-n DEV` сеть) |
| История по процессам | `atop -r /var/log/atop/atop_YYYYMMDD -b 1400` |
| Включить сбор sysstat | `ENABLED="true"` в `/etc/default/sysstat`; `sudo systemctl enable --now sysstat` |
| NUMA | `numactl --hardware; numastat -p PID` |
| Параметры CPU и гипервизор | `lscpu; nproc` |
