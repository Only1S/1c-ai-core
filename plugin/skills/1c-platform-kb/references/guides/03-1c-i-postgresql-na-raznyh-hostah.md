# Сервер 1С и PostgreSQL на разных хостах: что меняется

> Область: перенос СУБД на отдельную машину и добавление второго рабочего сервера 1С | Стек: Ubuntu Server 24.04, «1С:Предприятие» 8.3.27, «PostgreSQL для 1С» 17 | Актуальность: 2026-10-10
>
> **Статус:** собрано по конспектам документации ИТС и статьям базы знаний; на живых серверах не прогонялось. Дополняет `01-razvertyvanie-s-nulya.md`, где оба сервера стоят на одной машине.

## Кратко

1. Сервер 1С обращается к PostgreSQL по TCP, поэтому разнесение — это настройка сети, `pg_hba.conf` и одного свойства информационной базы; сама база не меняется.
2. Документация рекомендует между кластером 1С и СУБД сеть **от 1 Гбит/с** (`../its-docs/cs-gl01-trebovaniya.md`, разд. 1.3.1). Каждый запрос 1С — отдельное обращение по сети, поэтому задержка важнее пропускной способности.
3. Адрес СУБД хранится в свойствах информационной базы. Нестандартный порт задаётся в том же поле: `<имя сервера> port=<номер>;`, например `dbsrv port=5433;` (документация, глава 5 «Ведение списка информационных баз», разд. 5.2.1.3.3).
4. Порт 5432 открывается **только** для адреса сервера 1С. Клиентам 1С доступ к СУБД не нужен.
5. Память делится проще: на хосте СУБД формулы ИТС считаются от всей памяти машины.
6. Резервные копии делаются на хосте СУБД; лицензии и данные кластера остаются на хосте 1С.

## Когда разносить

- Серверу 1С и PostgreSQL перестало хватать общей памяти (OOM killer, swap) или процессора.
- Нужен второй рабочий сервер 1С или реплика PostgreSQL.
- Требования безопасности: СУБД в отдельном сегменте сети.

На небольшой базе (до пары десятков пользователей) одна машина проще и часто быстрее: нет сетевой задержки. Расчёт оборудования — `../its-metod/raschet-oborudovaniya-i-nagruzochnoe-testirovanie.md`.

## Переменные

```bash
APP=srv1c;  APP_IP=192.168.1.50      # сервер 1С
DB=dbsrv;   DB_IP=192.168.1.60       # сервер PostgreSQL
V=8.3.27.2074
RAC=/opt/1cv8/x86_64/$V/rac
PG=/opt/pgpro/1c-17/bin
```

## Шаг 1. Подготовка хоста СУБД

Выполняются этапы 2–4 руководства `01-razvertyvanie-s-nulya.md` (ОС, локаль `ru_RU.UTF-8` до создания кластера, установка «PostgreSQL для 1С»). Отличия — ниже.

### 1.1. Имена и время

На **обоих** хостах имена должны разрешаться в обе стороны, часы — синхронизированы.

```bash
# на каждом хосте: записи о соседе (или записи в DNS)
echo "192.168.1.50 srv1c.example.local srv1c" | sudo tee -a /etc/hosts
echo "192.168.1.60 dbsrv.example.local dbsrv" | sudo tee -a /etc/hosts
getent hosts srv1c dbsrv
timedatectl | grep -i synchronized
```

### 1.2. Слушать сеть и пускать только сервер 1С

```bash
# на хосте СУБД
sudo -u postgres psql -c "ALTER SYSTEM SET listen_addresses = 'localhost,$DB_IP';"
HBA=$(sudo -u postgres psql -At -c "show hba_file")
echo "host    all    all    $APP_IP/32    scram-sha-256" | sudo tee -a "$HBA"
sudo systemctl restart postgrespro-1c-17          # listen_addresses требует перезапуска

sudo ufw allow from $APP_IP to any port 5432 proto tcp
sudo ufw status numbered
```

- Метод `scram-sha-256` работает с платформой 8.3.20 и новее; пароль роли должен быть задан при `password_encryption = scram-sha-256` (умолчание PostgreSQL с 14-й версии). Если сборка настроила `md5`, оставьте `md5` — менять метод без смены пароля нельзя.
- Правила в `pg_hba.conf` читаются сверху вниз, срабатывает первое подходящее. Проверка разбора: `sudo -u postgres psql -c "select line_number, type, address, auth_method, error from pg_hba_file_rules"`.

### 1.3. Роль для 1С

По документации пользователь СУБД должен иметь `SUPERUSER` только в момент создания информационной базы; потом привилегию можно отозвать.

```bash
sudo -u postgres psql <<'SQL'
CREATE ROLE usr1c LOGIN SUPERUSER PASSWORD 'ЗАМЕНИТЕ_ПАРОЛЬ';
SQL
# после создания всех информационных баз:
# sudo -u postgres psql -c "ALTER ROLE usr1c NOSUPERUSER;"
```

Пока привилегия не отозвана, роль всесильна — ограничьте её адресом сервера 1С в `pg_hba.conf` (как выше) и не используйте для ручной работы.

### 1.4. Память и настройки

На выделенном хосте «RAM» в формулах ИТС — вся память машины: `shared_buffers = RAM/4`, `effective_cache_size = RAM − shared_buffers` и так далее (таблица — в `01-razvertyvanie-s-nulya.md`, этап 4.3; официальный источник — `../its-metod/pg-nastrojki-postgresql-dlya-1c.md`). Параметр `ssl` ИТС рекомендует оставить `off` из-за нагрузки на процессор — поэтому защита строится на изоляции сети, а не на шифровании.

Через межсетевой экран с отслеживанием состояний простаивающие соединения 1С могут обрываться. Включите поддержание соединений:

```bash
sudo -u postgres psql <<'SQL'
ALTER SYSTEM SET tcp_keepalives_idle = 60;
ALTER SYSTEM SET tcp_keepalives_interval = 10;
ALTER SYSTEM SET tcp_keepalives_count = 6;
SELECT pg_reload_conf();
SQL
```

## Шаг 2. Проверка с хоста 1С

```bash
# на сервере 1С
nc -zv $DB 5432                                    # порт доступен
ping -c 20 $DB | tail -2                           # задержка: в одной сети — доли миллисекунды
PGPASSWORD='…' $PG/psql -h $DB -U usr1c -d postgres -c "select version()"
```

Если на хосте 1С нет клиента PostgreSQL, поставьте пакет клиента той же сборки или проверяйте подключение созданием базы на шаге 3. Не оставляйте пароль в истории команд: надёжнее файл `~/.pgpass` с правами `600`.

Ошибки и их причины:

| Сообщение | Причина |
|---|---|
| `Connection refused` | PostgreSQL не слушает этот адрес (`listen_addresses`) или не перезапущен |
| тайм-аут | сетевой экран на хосте СУБД или между хостами |
| `no pg_hba.conf entry for host` | нет строки для адреса сервера 1С либо адрес другой (несколько интерфейсов, NAT) |
| `password authentication failed` | неверный пароль либо метод в `pg_hba.conf` не соответствует тому, как сохранён пароль |

## Шаг 3. Информационная база

### Новая база

```bash
CL=$($RAC cluster list | awk '/^cluster/{print $3}')
read -rsp "Пароль роли usr1c: " PGPWD; echo
$RAC infobase create --cluster=$CL --create-database \
    --name=demo --dbms=PostgreSQL --db-server=$DB --db-name=demo \
    --locale=ru_RU --db-user=usr1c --db-pwd="$PGPWD" \
    --license-distribution=allow --scheduled-jobs-deny=on
```

Нестандартный порт СУБД: `--db-server="$DB port=5433;"`.

### Перенос существующей базы на отдельный хост

1. Запретить вход и завершить сеансы (`02-runbooki-i-shpargalki.md`, инструкция 7).
2. На старом хосте: `sudo -u postgres pg_dump -Fc -f /backup/pg/demo_move.dump demo`.
3. Скопировать файл: `rsync -aP /backup/pg/demo_move.dump user@$DB:/backup/pg/`.
4. На новом хосте: `sudo -u postgres createdb demo && sudo -u postgres pg_restore -d demo -j 4 /backup/pg/demo_move.dump`.
5. Переключить базу на новый адрес СУБД:

```bash
IB=<UUID базы>
$RAC infobase update --cluster=$CL --infobase=$IB --infobase-user=<админ ИБ> --infobase-pwd=<пароль> \
    --db-server=$DB --db-user=usr1c --db-pwd="$PGPWD"
```

6. Снять запрет, проверить вход. Старую базу на прежнем хосте удалять только после проверки и свежей копии с нового.

Версия PostgreSQL на новом хосте — та же или новее; сборка — «для 1С» (в дампе используются типы `mchar` и `mvarchar`). ⚠ Параметры `rac` сверяйте со встроенной справкой: `$RAC help infobase`.

## Шаг 4. Что ещё меняется в эксплуатации

- **Порядок запуска.** Зависимость `After=postgrespro-1c-17.service` в юните сервера 1С больше не работает — СУБД на другой машине. Сервер 1С стартует и без СУБД; базы станут доступны, когда PostgreSQL поднимется. При плановых работах: останавливать сначала 1С, потом СУБД; запускать в обратном порядке.
- **Резервные копии** (`pg-backup.sh`, таймер) переезжают на хост СУБД. На хосте 1С остаётся копирование данных кластера (`/home/usr1cv8/.1cv8/1C/1cv8`), лицензий (`/var/1C/licenses`) и настроек.
- **Лицензии** привязаны к хосту 1С и переносом СУБД не затрагиваются.
- **Диагностика «тормозит»** теперь включает сеть: `ping`, `mtr`, `sar -n DEV 1`, а на хосте СУБД — `pg_stat_activity` с колонкой `client_addr`.
- **Временные таблицы.** 1С активно создаёт временные таблицы; на выделенном хосте СУБД их можно вынести на быстрый диск параметром `temp_tablespaces` (рекомендация ИТС).

## Второй рабочий сервер 1С

Когда не хватает уже сервера 1С, в кластер добавляют рабочий сервер. По документации порядок такой (`../its-docs/cs-gl03-ustanovka-komponentov-p1.md`, `../its-docs/cs-gl05-administrirovanie-klastera-p1.md`):

1. Установить на новом узле сервер 1С **той же версии** и запустить службу.
2. Добавить узел в существующий кластер как рабочий сервер (команда `rac server insert`, обязательны адрес и порт агента и диапазон портов рабочих процессов).
3. При необходимости задать требования назначения функциональности (режим `rac rule`) — например, вынести фоновые задания или сервис лицензирования; требования начинают действовать после `rac rule apply`.
4. На новом узле желательно удалить регистрацию его собственного кластера, созданного при первом запуске.

Что учесть:

- Имена всех серверов кластера должны одинаково разрешаться на каждом узле и на клиентах; адреса одного сервера везде записываются одинаково — их тождественность кластер не проверяет.
- У каждого узла свой диапазон портов рабочих процессов (по умолчанию 1560–1591), его нужно открыть клиентам.
- `pg_hba.conf` на хосте СУБД должен пускать **каждый** рабочий сервер.
- Серверная лицензия нужна для каждого компьютера, где работают рабочие процессы, либо назначается сервис лицензирования — `../1c/04-licenzirovanie.md`, `../its-docs/adm-gl10-zashchita-licenzii-p2.md`.
- Отказоустойчивость (несколько центральных серверов, уровень отказоустойчивости) — `../its-docs/cs-gl02-klient-servernyj-variant-p2.md`, `../1c/10-proizvoditelnost-otkazoustojchivost-ekspluataciya.md`.

## Типичные ошибки

| Симптом | Причина | Решение |
|---|---|---|
| После переноса всё стало медленнее | сетевая задержка между хостами; хосты в разных сегментах или через маршрутизатор | один сегмент, сеть от 1 Гбит/с; сверить `ping` и время простого запроса |
| Соединения 1С с СУБД рвутся после простоя | межсетевой экран забывает простаивающие соединения | `tcp_keepalives_*` на СУБД (шаг 1.4) |
| `too many clients already` | каждое соединение рабочих процессов 1С — отдельный процесс PostgreSQL; серверов 1С стало больше | увеличить `max_connections` (нужен перезапуск) и проверить память |
| База создаётся с ошибкой прав | у роли нет `SUPERUSER` в момент создания | выдать на время создания, затем отозвать |
| Клиенты не подключаются ко второму серверу | имя нового рабочего сервера не разрешается на клиентах или закрыт его диапазон портов | DNS или `hosts`, правила `ufw` на новом узле |
