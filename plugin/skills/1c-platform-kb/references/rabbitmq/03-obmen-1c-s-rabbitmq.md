## Кратко — главные факты

1. **Встроенного клиента RabbitMQ (AMQP 0-9-1) в платформе нет.** Есть **сервисы интеграции** — адаптер к сервисной шине по **AMQP** [ИТС-разр гл. 17.1]; официально внешний сервис интеграции — продукт **«1С:Шина»** [ИТС-разр гл. 17.8.1].
2. **Официальный путь 1С ↔ RabbitMQ — через «1С:Шину»:** «Шина» обменивается с RabbitMQ по AMQP (узлы схемы `RabbitMqИсточник`/`RabbitMqНазначение`), с ActiveMQ Artemis — по JMS [ИТС-мет i8105995; оглавление `its.1c.ru/db/esbdoc3`]. Это отдельный сервер и продукт со своей лицензией.
3. **Без «Шины» работают:** внешние компоненты AMQP 0-9-1 (открытая **PinkRabbitMQ**, MIT; **1CRabbitMQ**) и **HTTP API** модуля управления RabbitMQ (`/api/exchanges/<vhost>/<обменник>/publish`). Но получение через HTTP API (`/api/queues/…/get`) по словам самой документации RabbitMQ **не обеспечивает надёжной доставки** и предназначено для диагностики [RMQ-API 4.4.0].
4. **Прямое подключение сервисов интеграции к RabbitMQ 4.x по AMQP 1.0** описано сообществом (Infostart, 30.03.2026): HTTP-сервис 1С «изображает» «Шину», отдавая платформе адреса RabbitMQ (`/exchanges/…`, `/queues/…`). Работает на недокументированном протоколе «платформа ↔ Шина» — **может сломаться при любом обновлении платформы**; поддержки 1С нет ⚠.
5. **Сервисы интеграции дают гарантированную доставку «из коробки»:** исходящее сообщение хранится в базе до подтверждения получения внешним сервисом; входящее сначала сохраняется в базе и только потом подтверждается [ИТС-разр гл. 17.8.1]. Это готовый outbox/inbox.
6. **Обмен идёт, только пока вызывается `СервисыИнтеграции.ВыполнитьОбработку()`:** соединение держится 2 минуты после вызова; документация рекомендует регламентное задание **раз в минуту** [ИТС-разр гл. 17.8.6.1.1].
7. **Порядок:** внутри канала — строго последовательно; если первое сообщение канала не отправилось, следующие ждут. Между каналами и сервисами порядок не определён [ИТС-разр гл. 17.8.1, 17.8.6.2].
8. **Канал «В транзакции» снят → обработчик должен быть идемпотентным**: при сбое отметки обработанности сообщение будет обработано повторно [ИТС-разр гл. 17.8.2].
9. **Автономный сервер (`ibsrv`) сервисы интеграции не поддерживает** [ИТС-адм гл. 7.2] — только кластер или файловый вариант.
10. **Диагностика на стороне 1С:** событие техжурнала **`SINTEG`** (свойства `SrvcName`, `ExtSrvcUrl`, `ExtSrvcUsr`), фоновые задания `BackgroundJob.…IntegrationSystemMessages…`, таблицы очередей `_IntegChannelOutQueue<n>`/`_IntegChannelInQueue<n>` [ИТС-адм прил. 3; ИТС-КС гл. 2; ИТС-мет «Размещение данных»].
11. **Внешнюю компоненту на сервере подключайте изолированно** и держите соединение в долгоживущем фоновом задании, а не открывайте на каждое сообщение — частые подключения RabbitMQ считает отдельной проблемой («connection churn») [ИТС-разр гл. 32.1; RMQ-док 4.4 `production-checklist`].

## 1. Сравнение способов

| Способ | Протокол | Надёжность | Плюсы | Минусы | Когда |
|---|---|---|---|---|---|
| **«1С:Шина»** + узлы RabbitMQ | 1С ↔ Шина: сервисы интеграции; Шина ↔ RabbitMQ: AMQP | Гарантированная доставка платформы | Продукт и поддержка 1С; без кода транспорта в конфигурации | Ещё один сервер и продукт; документация под отдельной подпиской | Много баз 1С, нужна маршрутизация и трансформация |
| **Внешняя компонента** (PinkRabbitMQ, 1CRabbitMQ) | AMQP 0-9-1 | Как напишете: confirms + ручной ack + outbox | Полный AMQP, скорость, нет посредников | Сторонний двоичный код; обновления компоненты; утечки и зависания у части компонент [сторонний] | Средние и большие потоки, есть кому сопровождать |
| **HTTP API** брокера | HTTP | Публикация — ответ `routed`; получение — **ненадёжно** (диагностика) | Только `HTTPСоединение`; просто | Каждое сообщение — HTTP-запрос; нет подтверждений получателя | Отправка небольших объёмов из 1С; приём — не использовать |
| **Сервисы интеграции напрямую** (приём сообщества) | AMQP 1.0 | Гарантированная доставка платформы | Нет компонент и «Шины»; outbox/inbox платформы | Недокументировано; один vhost; риск при обновлении платформы | Эксперимент, стенд; в работе — осознанно ⚠ |
| **Посредник** (своя служба) | HTTP-сервис 1С ↔ AMQP | Как напишете | 1С ничего не знает о брокере | Ещё одна программа | Есть команда интеграции |

Оценки недостатков компонент и прокси приведены по статье сообщества [сторонний: infostart.ru/1c/articles/2652150/].

## 2. Сервисы интеграции платформы: что нужно знать администратору

### 2.1. Устройство

- **Объект конфигурации** «Сервис интеграции» (ветвь «Общие»): адрес внешнего сервиса и список **каналов**; канал — только входящий или только исходящий; у входящего — обработчик получения в модуле сервиса (выполняется на сервере) [ИТС-разр гл. 17.8.1, 17.8.2].
- **Каналы** задаются вручную или загружаются из внешнего сервиса командой «Загрузить каналы» [ИТС-разр гл. 17.8.2].
- **Сообщение** — тело (поток, любые данные) + заголовок; свойства `Идентификатор`, `ИдентификаторСообщенияЗапроса`, `КодОтправителя`, `КодПолучателя` (несколько — через запятую), `Параметры` (строковые пары), `ДатаУстаревания` (UTC, задаётся только при создании), `РазмерТела` [ИТС-разр гл. 17.8.4].
- **Очереди в базе:** таблица настроек `_IntegServiceSettings<n>` (поля `_Active`, `_Content`), очередь отправки `_IntegChannelOutQueue<n>` и получения `_IntegChannelInQueue<n>` на каждый канал своего направления [ИТС-мет «Размещение данных», `../its-metod/razmeshchenie-dannyh-tablicy-i-polya.md`].
- **Сервис кластера «Интеграционных данных»** обеспечивает работу сервисов интеграции; делится по базам, при переносе на другой менеджер не сохраняет состояние («Перенос-») [ИТС-КС гл. 2, таблица сервисов].

### 2.2. Как идут сообщения

**Отправка** [ИТС-разр гл. 17.8.6.2]:

1. `Канал.ОтправитьСообщение(Сообщение)` пишет сообщение в очередь отправки в базе; если вызов в транзакции — запись появится только при её фиксации.
2. `СервисыИнтеграции.ВыполнитьОбработку()` запускает системное фоновое задание обработки очереди отправки, оно физически отправляет.
3. Успех → сообщение удаляется из очереди; неудача → остаётся до отправки или устаревания, **остальные сообщения канала ждут**.
4. Порядок — по порядку фиксации транзакций; внутри одной транзакции — по порядку создания.

**Получение** [ИТС-разр гл. 17.8.6.1]:

1. `ВыполнитьОбработку()` открывает соединение с внешним сервисом и держит его **2 минуты** от последнего вызова (и в файловом, и в клиент-серверном варианте) — отсюда регламентное задание раз в минуту.
2. Внешний сервис уведомляет о сообщении → задание **получения** пишет его в очередь получения базы и подтверждает внешнему сервису.
3. Задание **обработки очереди** запускает задания **обработки сообщений** с нужным пользователем и областью данных.
4. Задание обработки вызывает обработчик канала **в транзакции**; отказ или исключение → откат, сообщение будет обработано повторно; следующие сообщения канала ждут.
5. В клиент-серверном варианте задание обработки после работы «засыпает» на **20 секунд**, ожидая следующих сообщений; задания разных сервисов могут идти параллельно. В файловом — по одному и последовательно.

**Флажок «В транзакции»** у канала [ИТС-разр гл. 17.8.2]: установлен — обработчик и отметка «обработано» в одной транзакции; снят — при сбое во время установки отметки обработчик будет вызван ещё раз, поэтому обработчик обязан выдерживать повтор.

### 2.3. Фоновые задания (для журнала регистрации и консоли кластера)

| Назначение | Имя фонового задания |
|---|---|
| Обработка очереди отправки | `BackgroundJob.SendIntegrationSystemMessagesQueueProcessing.<полное имя сервиса>` |
| Обработка очереди получения | `BackgroundJob.ReceiveIntegrationSystemMessagesQueueProcessing.<полное имя сервиса>` |
| Получение сообщений | `BackgroundJob.ReceivingIntegrationSystemMessages.<полное имя сервиса>` |
| Обработка полученных сообщений | `BackgroundJob.ReceivedIntegrationSystemMessagesProcessing.<полное имя канала>` |

Источник — [ИТС-КС гл. 2, перечень фоновых заданий; конспект `../its-docs/cs-gl02-klient-servernyj-variant-p2.md`].

### 2.4. Настройки и права

- Настройки сервиса — объект `НастройкиСервисаИнтеграции` (`ПолучитьНастройки()`/`УстановитьНастройки()`) или стандартная функция **«Управление сервисами интеграции»** [ИТС-разр гл. 17.8.5; ИТС-адм гл. 6]:
  - `АдресВнешнегоСервисаИнтеграции`;
  - `ИмяПользователяВнешнегоСервисаИнтеграции`, `ПарольПользователяВнешнегоСервисаИнтеграции` — учётная запись **на стороне внешнего сервиса** (для «Шины» — идентификатор и секрет ключа API информационной системы [ИТС-мет i8105995]);
  - `ИмяПользователя` — пользователь **1С**, от имени которого работает задание обработки полученных сообщений; если не задан — права по свойству конфигурации `ОсновныеРоли`, а если и оно пусто — **права не проверяются**.
- Признак **активности** сервиса включается там же; без него обмен не идёт [ИТС-разр гл. 17.8.3; ИТС-мет i8105995].
- Право на стандартную функцию — `IntegrationServicesManagment` (так, без «e», в списке прав) [ИТС-адм прил. 7].
- При разделении данных настройки и активность разделённого сервиса хранятся в области данных; сервис из расширения в разных областях обслуживается одним набором фоновых заданий, если расширения идентичны — рекомендуется подключать такое расширение во все области [ИТС-разр, приложение о разделении данных].
- В режиме совместимости 8.3.25 и ниже `ВыбратьСообщения()` игнорирует `МаксимальноеКоличество` (возвращает все сообщения канала) и нулевой УИД в отборе по `ИдентификаторСообщенияЗапроса` [ИТС-разр, прил. 7, разд. 7.2.22 «С версией 8.3.25»].

### 2.5. Обслуживание очередей из встроенного языка

`Канал.ВыбратьСообщения(Отбор, МаксимальноеКоличество)` — посмотреть не отправленные (исходящие) или не обработанные (входящие) сообщения с отбором по параметрам; `Канал.УдалитьСообщения(Неопределено | МассивИдентификаторов | Отбор)` — удалить; `СервисыИнтеграции.ОстановитьОбработку()` — остановить обмен [ИТС-разр гл. 17.8.4]. Устаревшие сообщения удаляются фоновыми заданиями отправки и получения [там же]. Удобно сделать служебную обработку «Очереди сервисов интеграции» для администратора [практика].

## 3. Способ А: «1С:Шина» → RabbitMQ (официальный)

Порядок по методической статье ИТС (пример: сообщение из RabbitMQ попадает в базу «Офис») [ИТС-мет i8105995]:

1. **RabbitMQ:** создать очередь (в примере `TestChannel1C`).
2. **«1С:Шина»:** создать приложение и проект; процесс интеграции со схемой `RabbitMqИсточник → … → Канал1СНазначение`; параметры процесса `ChannelName` (очередь), `Host`, `Login`, `Password`; опубликовать проект.
3. **Панель «Шины»:** добавить информационную систему (код `office`), выдать ей **ключ API** (идентификатор + секрет), включить её в группу участников процесса, заполнить параметры узла RabbitMQ, запустить процесс.
4. **Конфигурация 1С:** добавить сервис интеграции, «Загрузить каналы» (адрес приложения «Шины», пользователь/пароль = ключ API), написать обработчик получения; регламентное задание, вызывающее `СервисыИнтеграции.ВыполнитьОбработку()`.
5. **Режим «1С:Предприятие»:** «Функции для технического специалиста» → «Стандартные» → «Управление сервисами интеграции» → указать ключ API → «Установить активность».

Расхождение, которое стоит знать: в примере ИТС расписание задания — **каждые 5 секунд**, а «Руководство разработчика» советует **раз в минуту** (соединение и так держится 2 минуты) [ИТС-мет i8105995; ИТС-разр гл. 17.8.6.1.1]. Частый запуск увеличивает число фоновых заданий без выгоды [практика].

Состав узлов «Шины» версии 3 (по оглавлению): каналы 1С, файлы, FTP, **JMS**, очереди шины, **HTTP**, **RabbitMQ** (источник и назначение), **SQL**, маршрутизатор по содержимому, транслятор, таймер [оглавление `esbdoc3`]. Параметры узлов, порты, системные требования и установка «Шины» — в её документации, закрытой для подписки пользователя ⚠.

## 4. Способ Г: сервисы интеграции напрямую к RabbitMQ 4.x (приём сообщества)

> ⚠ Всё в этом разделе — по статье «RabbitMQ нативно в 1С: без компонент, прокси и шины» (Infostart, 30.03.2026) и документации RabbitMQ. Фирма «1С» этот способ не описывает и не поддерживает; протокол между платформой и «Шиной» не документирован и может измениться в любой версии платформы. Проверяйте на стенде при каждом обновлении платформы.

### 4.1. Механика (как описано в статье)

1. При **загрузке каналов** платформа обращается к адресу внешнего сервиса:
   - `POST /auth/oidc/token` с `Authorization: Basic <логин:пароль>` → ожидает `{"id_token": …, "token_type": "Bearer", …}`;
   - `GET /sys/esb/metadata/channels` с полученным токеном → список `{process, channel, access: "WRITE_ONLY" | "READ_ONLY", …}`.
2. При **работе** платформа повторяет получение токена и запрашивает `GET /sys/esb/runtime/channels` → `{"items":[{"process", "channel", "destination"}], "port": <порт>}` — и переключается на **AMQP 1.0** на этот порт, адресуя сообщения по `destination`.
3. RabbitMQ 4.x понимает адреса AMQP 1.0 вида `/exchanges/<обменник>/<ключ>` и `/queues/<очередь>` [RMQ-док 4.4 `amqp`], поэтому в `destination` подставляют их, а `port` = 5672.
4. Для AMQP 1.0 RabbitMQ требует SASL [RMQ-док 4.4 `amqp`]; платформа передаёт полученный токен как имя и пароль, поэтому в RabbitMQ заводят пользователя, у которого имя и пароль равны этому токену (в статье — строка Base64 `логин:пароль` пользователя 1С).
5. Три адреса реализуют HTTP-сервисом самой базы 1С (или любым веб-сервером со статическими ответами) и публикуют через обратный прокси так, чтобы они были в корне адреса (`/auth/…`, `/sys/…`), — платформа обращается к ним от корня.

### 4.2. Ограничения и риски

| Что | Почему | Источник |
|---|---|---|
| Один vhost | Платформа не передаёт `vhost:<имя>` в кадре `open`, RabbitMQ берёт `default_vhost` (умолчание `/`) | [сторонний] + [RMQ-док 4.4 `amqp`]; обойти, задав `default_vhost = erp` в `rabbitmq.conf` — ⚠ (влияет на всех клиентов AMQP 1.0 без явного vhost) |
| Пароль = токен | Токен — Base64 от логина и пароля 1С, то есть фактически пароль в открытом виде | [сторонний]; вывод — практика |
| Шифрование | В статье соединение без TLS; поддерживает ли платформа AMQP 1.0 поверх TLS к произвольному брокеру — не проверено | ⚠ |
| Совместимость | Протокол «платформа ↔ Шина» не описан в документации; изменение в новой версии сломает обмен | ⚠ |
| Поддержка | Обращения в 1С по такому обмену не примут | [практика] |
| Плюсы | Гарантированная доставка платформы (outbox/inbox в базе), идемпотентные ключи, фоновые задания, техжурнал `SINTEG` | [ИТС-разр гл. 17.8] |

Если решите использовать: стенд с той же версией платформы; RabbitMQ 4.x (до 4.0 нужен модуль `rabbitmq_amqp1_0`); отдельный vhost через `default_vhost`; пользователь RabbitMQ с правами только на нужные обменник и очередь; автотест обмена в регламент обновления платформы.

### 5.2. Правила использования на сервере 1С

- Подключение — `ТипПодключенияВнешнейКомпоненты.Изолированно`: падение компоненты не уронит `rphost` [ИТС-разр гл. 32.1]; подробно о подключении, профиле безопасности и обработчике `ОбработкаОтключенияВнешнейКомпонентыПриОшибке()` — `../kafka/03-…`, раздел 7.2.
- **Отправка:** из регламентного задания по очереди отправки 1С (outbox, `../kafka/03-…`, раздел 4); публикация с **подтверждением издателя**; удалять из очереди отправки только после подтверждения; сообщение — постоянное, с `messageId` = идентификатор сообщения 1С.
- **Получение:** долгоживущее фоновое задание с подписчиком (`basic.consume`), `prefetch` 10–100, **ручное подтверждение после фиксации транзакции** в 1С; при ошибке данных — отказ без возврата в очередь (`reject`/`nack` без requeue) → сообщение уйдёт в DLX по политике очереди.
- **Соединение** открывайте один раз на задание и переиспользуйте; переподключение — с паузой. Частые подключения и каналы на каждое сообщение — антипаттерн [RMQ-док 4.4 `production-checklist`, «Connection Churn», «Excessive Channel Usage»].
- Опрос `basic.get` из регламентного задания — допустимый компромисс для небольших объёмов, но документация считает его неэффективным [там же, «Polling Consumers»].

## 6. Способ В: HTTP API модуля управления

### 6.1. Что можно и чего нельзя

- **Публикация:** `POST /api/exchanges/<vhost>/<обменник>/publish`, тело `{"properties":{…},"routing_key":"…","payload":"…","payload_encoding":"string"|"base64"}` (все ключи обязательны), ответ `{"routed": true|false}` — `true`, если сообщение попало хотя бы в одну очередь [RMQ-API 4.4.0]. HTTP API не рассчитан на высокую скорость: на каждое сообщение — новое соединение [там же].
- **Получение:** `POST /api/queues/<vhost>/<очередь>/get`, тело `{"count":5,"ackmode":"ack_requeue_true","encoding":"auto","truncate":50000}`; `ack_requeue_false`/`reject_requeue_false` **удаляют** сообщения сразу при выдаче. Документация прямо пишет: путь `get` предназначен для диагностики, **не реализует надёжной доставки** и является инструментом администратора, а не API обмена [RMQ-API 4.4.0]. Для приёма в 1С не используйте.
- Обмен через HTTP API вообще документация не рекомендует; он оправдан там, где долгие соединения невозможны [RMQ-док 4.4 `management`, «Publishing and Consuming over HTTP API»].
- vhost в пути кодируется: `/` → `%2F` ⚠ (общая практика API; сверить в справочнике).
- Пользователю нужен тег для доступа к HTTP API (минимум `management`) [RMQ-док 4.4 `management`] ⚠ (точный минимальный тег — сверить в разделе о правах веб-интерфейса).

### 6.2. Отправка из 1С через HTTP API

```bsl
// Общий модуль РэббитHTTP (сервер). Возвращает Истина, если сообщение попало в очередь
Функция Опубликовать(Обменник, КлючМаршрутизации, ИдСообщения, ТелоJSON) Экспорт
	Свойства = Новый Соответствие;
	Свойства.Вставить("delivery_mode", 2);              // постоянное
	Свойства.Вставить("content_type", "application/json");
	Свойства.Вставить("message_id", ИдСообщения);
	Тело = Новый Соответствие;
	Тело.Вставить("properties", Свойства);
	Тело.Вставить("routing_key", КлючМаршрутизации);
	Тело.Вставить("payload", ТелоJSON);
	Тело.Вставить("payload_encoding", "string");

	Соединение = Новый HTTPСоединение("rmq01.example.local", 15671, "erp-1c", ПарольRabbit(), , 30,
		Новый ЗащищенноеСоединениеOpenSSL());
	Запрос = Новый HTTPЗапрос("/api/exchanges/erp/" + Обменник + "/publish");
	Запрос.Заголовки.Вставить("Content-Type", "application/json");
	Запрос.УстановитьТелоИзСтроки(ОбменJSON.ВJSON(Тело), КодировкаТекста.UTF8,
		ИспользованиеByteOrderMark.НеИспользовать);
	Ответ = Соединение.ОтправитьДляОбработки(Запрос);
	Текст = Ответ.ПолучитьТелоКакСтроку(КодировкаТекста.UTF8);
	Если Ответ.КодСостояния <> 200 Тогда
		ВызватьИсключение СтрШаблон("RabbitMQ HTTP API: %1 %2", Ответ.КодСостояния, Текст);
	КонецЕсли;
	Возврат ОбменJSON.ИзJSON(Текст).Получить("routed") = Истина;
КонецФункции
```

`ОбменJSON` — модуль из `../kafka/03-…`, раздел 3.2. `routed = Ложь` — сообщение **никуда не попало** (нет привязки под этот ключ): для обмена это ошибка, сообщение должно остаться в очереди отправки 1С. Подтверждает ли HTTP API сохранение сообщения на диск кворумной очереди до ответа (аналог publisher confirms) — не описано ⚠; для критичного обмена — компонента или «Шина».

## 7. Топология и права для обмена 1С

Повторяет `01-…`, раздел 5.1, и `02-…`, раздел 1.1:

- один vhost `erp`, кворумные очереди, обменники `erp.events` (публикует ERP) и `<система>.events` (публикуют другие);
- очередь на каждого получателя (`erp.from-site`, `site.from-erp`, `bi.from-erp`), привязки по ключам `erp.nomenclature.*`, `site.order.*`;
- политика на все очереди: `dead-letter-exchange = dlx`, `delivery-limit` (умолчание кворумных — 20);
- учётная запись `erp-1c`: `write` на `erp.events`, `read` на `erp.from-*`, без `configure`;
- формат сообщения, ключ, идентификатор, outbox и идемпотентный приём — как в `../kafka/03-…`, разделы 3–5; в RabbitMQ идентификатор кладите и в свойство `message_id`.

## 9. Типовые ошибки

| Симптом | Причина | Решение |
|---|---|---|
| Сервис интеграции не отправляет, очередь в базе растёт | Не вызывается `ВыполнитьОбработку()` или сервис не активен | Регламентное задание раз в минуту; «Управление сервисами интеграции» → активность |
| Обмен через сервисы интеграции на автономном сервере не работает | `ibsrv` их не поддерживает | Кластер серверов [ИТС-адм гл. 7.2] |
| Одно сообщение «застряло», остальные канала стоят | Порядок канала: следующие ждут первое; обработчик падает на нём | Исправить данные/обработчик; при необходимости `УдалитьСообщения()` для этого идентификатора |
| Повторная обработка входящих после сбоя | Канал без «В транзакции» | Идемпотентный обработчик или флажок «В транзакции» |
| Права при обработке входящих не проверяются | Не задан `ИмяПользователя` и пусто `ОсновныеРоли` | Задать пользователя в настройках сервиса |
| `ACCESS_REFUSED` от RabbitMQ | Нет прав `write`/`read` на ресурс; с 4.3.1 — и на пассивное объявление | `rabbitmqctl list_user_permissions` (`02-…`, 1.1) |
| HTTP API: `{"routed":false}` | Нет привязки под ключ маршрутизации | Создать привязку; не удалять сообщение из очереди 1С |
| Публикация «висит» / таймаут | Сработал сторож памяти или диска RabbitMQ | `rabbitmq-diagnostics alarms` (`02-…`, раздел 6) |
| Сообщения исчезли из кворумной очереди после многократных ошибок | Предел доставок 20, DLX не настроен | Политика с `dead-letter-exchange` |
| Сеансы 1С аварийно завершаются при работе компоненты | Компонента подключена не изолированно | `Изолированно` + обработчик отключения |
