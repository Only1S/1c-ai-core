## Кратко — 20 главных фактов и команд

1. **Один экземпляр = один главный процесс `postgres` (postmaster) + фоновые процессы + по одному серверному процессу на каждое соединение** [PG]. Потоков нет. Отсюда цена соединения: память процесса и строки в разделяемых таблицах, которые размечаются под `max_connections` при старте.
2. **Сервер 1С держит пул постоянных соединений** в рабочих процессах `rphost`; пользователи 1С к PostgreSQL сами не подключаются. Все соединения идут под одной ролью, один `pid` в разное время обслуживает разных пользователей [1С].
3. **Память делится на общую и локальную.** Общая: `shared_buffers`, `wal_buffers`, таблицы блокировок — выделяется один раз при старте. Локальная: `work_mem` — **на каждую операцию** сортировки или хеширования, `temp_buffers` — на сеанс, `maintenance_work_mem` — на операцию обслуживания [PG]. Точный размер общей памяти: `SHOW shared_memory_size;` (15+).
4. **Файл таблицы:** `SELECT pg_relation_filepath('_reference12');` → `base/<OID базы>/<relfilenode>`. Рядом лежат `…_fsm` (карта свободного места), `…_vm` (карта видимости), сегменты `.1`, `.2` по 1 ГБ. `relfilenode` меняется при `TRUNCATE`, `REINDEX`, `CLUSTER`, `VACUUM FULL` [PG].
5. **Страница — 8 КБ, строка не может пересечь границу страницы.** Значения длиннее примерно 2 КБ сжимаются и выносятся в TOAST-таблицу `pg_toast.pg_toast_<OID>`; предел одного значения — 1 ГБ [PG]. У 1С в TOAST живут строки неограниченной длины и двоичные данные (`bytea`).
6. **WAL — журнал предзаписи:** изменение сначала попадает в WAL и только потом в файлы данных. После сбоя процесс `startup` находит в `pg_control` последнюю контрольную точку и повторяет WAL от её точки REDO [PG].
7. **Контрольная точка** сбрасывает «грязные» страницы на диск; запускается по `checkpoint_timeout` (умолчание 5 мин) или при приближении к `max_wal_size` (1 ГБ) [PG]. Первая правка страницы после контрольной точки пишет в WAL страницу целиком (`full_page_writes`).
8. **`fsync = on` всегда.** `synchronous_commit = off` допустим: при сбое теряются транзакции максимум за 3 × `wal_writer_delay` (600 мс по умолчанию), база остаётся целостной [PG]. В виртуальной машине надёжность зависит ещё и от того, не игнорирует ли гипервизор команду сброса кеша диска.
9. **MVCC:** `UPDATE` не меняет строку на месте, а создаёт новую версию; старая становится «мёртвой» и убирается `VACUUM`. Читатели не блокируют писателей и наоборот. Мусор не убирается, пока жива самая старая транзакция в кластере.
10. **Счётчик транзакций 32-битный.** Старые строки нужно «замораживать», иначе на отметке около 2 млрд транзакций сервер перестанет выдавать новые номера. Этим занимается autovacuum, поэтому выключать его нельзя [PG].
11. **Уровни изоляции PostgreSQL:** Read Committed (по умолчанию; снимок на каждый оператор), Repeatable Read (снимок на транзакцию), Serializable (плюс отслеживание зависимостей). Read Uncommitted работает как Read Committed [PG].
12. **Что использует 1С с PostgreSQL** [1С, «Руководство разработчика» 8.3.27, п. 9.2.3.2]: автоматический режим блокировок — **Serializable и блокировки таблиц**; управляемый режим — **Read Committed и блокировки записей**.
13. **Восемь режимов табличных блокировок** от `ACCESS SHARE` до `ACCESS EXCLUSIVE`. Обычный `SELECT` блокируется только режимом `ACCESS EXCLUSIVE` (`ALTER TABLE`, `TRUNCATE`, `VACUUM FULL`, `REINDEX` без `CONCURRENTLY`, реструктуризация 1С) [PG]. Эскалации блокировок строк до таблицы в PostgreSQL нет.
14. **Планировщик стоимостной:** выбирает план по статистике из `pg_statistic` (читать через `pg_stats`), которую собирает `ANALYZE`. Устаревшая статистика — главная причина плохих планов.
15. **Платформа 1С сама задаёт параметры сеанса** при подключении, в том числе `enable_mergejoin = off`, `cpu_operator_cost = 0.001`, `lock_timeout = 20000` [1С, ИТС 6011].
16. **Индексы 1С — это B-tree,** состав определяется метаданными конфигурации. Свои индексы в базе 1С создавать нельзя по условиям использования платформы; как временная аварийная мера — только `CREATE INDEX CONCURRENTLY`, не уникальный, с понятным именем и с пониманием, что реструктуризация его удалит [практика].
17. **Временные таблицы в PostgreSQL — настоящие таблицы:** строки в системном каталоге, свой файл на диске, локальные буферы `temp_buffers`, без WAL и без autovacuum [PG]. 1С создаёт их тысячами, поэтому системный каталог базы 1С раздувается, а на реплике «только для чтения» 1С работать не может.
18. **Кодировка базы 1С — UTF8, локаль задаётся при создании базы и потом не меняется.** Типы `mchar`/`mvarchar` хранят данные в UTF-16 и сравнивают через ICU без учёта регистра [PGPro]. После обновления ОС (новая glibc или ICU) индексы по текстовым полям нужно перестроить.
19. **Схема `public`:** начиная с PostgreSQL 15 право `CREATE` в ней есть только у владельца базы (роль `pg_database_owner`), а не у всех [PG]. Роль 1С должна быть владельцем базы либо суперпользователем.
20. **`pg_hba.conf`** читается сверху вниз, срабатывает первая подходящая строка. Метод — `scram-sha-256`; `md5` объявлен устаревшим в 18-й версии, `radius` удалён в 19-й [PG]. Применить изменения: `SELECT pg_reload_conf();`.

## 2. Процессы

### 2.1. Модель «процесс на соединение»

PostgreSQL использует модель «один процесс на одного клиента» [PG]. Postmaster слушает порт (5432 по умолчанию) и на каждое входящее соединение порождает (`fork`) отдельный серверный процесс (backend). Этот процесс проверяет подлинность клиента по `pg_hba.conf`, обслуживает его запросы и завершается, когда клиент отключается.

Следствия для администратора:

- **Сбой одного процесса роняет все соединения.** Если серверный процесс убит сигналом `SIGKILL` (в том числе OOM-killer ядра) или упал, postmaster считает общую память потенциально повреждённой, завершает все остальные процессы и выполняет восстановление по WAL. В журнале: `server process (PID N) was terminated by signal 9: Killed`, затем `terminating any other active server processes`. Все сеансы 1С получают ошибку СУБД. Поэтому никогда не применяйте `kill -9` к процессам `postgres`; используйте `pg_cancel_backend(pid)` и `pg_terminate_backend(pid)`.
- **`max_connections` — параметр запуска.** От него зависит размер общей памяти (таблица блокировок, массив процессов), изменение требует перезапуска. На резервном сервере значение должно быть не меньше, чем на основном [PG].
- **Каждое соединение стоит памяти** даже в простое: стек, кеши системного каталога, кеш планов, локальные буферы временных таблиц. В базе 1С десятки тысяч таблиц и индексов, а соединения живут долго, поэтому кеш каталога в процессе со временем вырастает до сотен мегабайт [практика].
- **Для 1С `max_connections` задают с запасом:** не менее 500, диапазон 500–10000 [PGPro]; обоснование — «решения 1С открывают много соединений, в том числе неиспользуемых».
- **Внешний пул соединений в транзакционном режиме (PgBouncer `pool_mode = transaction`) с 1С несовместим:** временные таблицы и параметры сеанса привязаны к соединению [практика]. Пул 1С уже встроен в рабочий процесс `rphost`.
- В PostgreSQL 14 ускорено построение снимков при большом числе соединений, в том числе простаивающих [PG]. Это довод не оставаться на 12–13.

Резерв соединений:

| Параметр | Умолчание | Смысл |
|---|---|---|
| `max_connections` | 100 | всего слотов для клиентов |
| `superuser_reserved_connections` | 3 | последние слоты только для суперпользователей — чтобы администратор мог войти при исчерпании |
| `reserved_connections` (16+) | 0 | слоты для ролей с правом `pg_use_reserved_connections` |

Если роль 1С — суперпользователь, резерв `superuser_reserved_connections` от неё не защищает. Для аварийного входа создайте отдельную роль администратора, а роли 1С ограничьте число соединений: `ALTER ROLE usr1cv8 CONNECTION LIMIT 480;` [практика]. Но учтите: предел «никогда не применяется к суперпользователям» и соблюдается лишь приблизительно [PG, `CREATE ROLE`], поэтому для роли-суперпользователя ограничение бесполезно — ещё один довод не давать роли 1С `SUPERUSER`, если без него можно обойтись.

### 2.2. Список процессов

| Процесс (как виден в `ps`) | `backend_type` | Когда существует | Что делает |
|---|---|---|---|
| `postgres -D …` (postmaster) | — | всегда | Слушает порт, порождает и перезапускает остальные процессы, выделяет общую память. Его PID — первая строка `postmaster.pid` |
| `postgres: … <роль> <база> <адрес>(<порт>) <состояние>` | `client backend` | на каждое соединение | Разбирает, планирует и выполняет запросы клиента |
| `checkpointer` | `checkpointer` | всегда | Выполняет контрольные точки: сбрасывает «грязные» страницы из `shared_buffers` на диск |
| `background writer` | `background writer` | всегда | Между контрольными точками понемногу записывает «грязные» страницы, чтобы серверным процессам доставались чистые буферы |
| `walwriter` | `walwriter` | всегда | Сбрасывает WAL из буферов на диск каждые `wal_writer_delay` (200 мс). При `synchronous_commit = off` именно он определяет окно возможной потери |
| `autovacuum launcher` | `autovacuum launcher` | при `autovacuum = on` | Раз в `autovacuum_naptime` решает, какие таблицы чистить и анализировать |
| `autovacuum worker` | `autovacuum worker` | по требованию, до `autovacuum_max_workers` | Выполняет `VACUUM` и `ANALYZE` одной таблицы |
| `logical replication launcher` | `logical replication launcher` | всегда (пока `max_logical_replication_workers` > 0) | Запускает обработчики подписок логической репликации. Если подписок нет — просто спит |
| `logical replication … worker` | `logical replication worker` | при наличии подписок | Применяет изменения на подписчике |
| `archiver` | `archiver` | при `archive_mode = on` | Копирует заполненные сегменты WAL командой `archive_command` или библиотекой `archive_library` |
| `startup` | `startup` | во время восстановления; на резервном сервере — постоянно | Повторяет записи WAL |
| `walsender` | `walsender` | на каждую реплику, `pg_basebackup`, `pg_receivewal` | Передаёт поток WAL |
| `walreceiver` | `walreceiver` | на резервном сервере | Принимает WAL от основного |
| `walsummarizer` (17+) | `walsummarizer` | при `summarize_wal = on` | Готовит сводки WAL для инкрементных копий |
| `io worker N` (18+) | `io worker` (значение подтверждено исходным кодом PostgreSQL 18 (`miscinit.c`), сверено 11.10.2026; в перечне значений документации 18 не упомянут) | при `io_method = worker` (умолчание), число — `io_workers` (3) | Выполняет операции асинхронного ввода-вывода по поручению серверных процессов |
| `parallel worker for PID N` | `parallel worker` | на время параллельного запроса | Выполняет часть плана под узлом `Gather` |
| `logger` | — | при `logging_collector = on` | Пишет журнал сервера в файлы |
| `slotsync worker` (17+) | `slotsync worker` (по исходному коду PostgreSQL 18, `miscinit.c`; сверено 11.10.2026) | при `sync_replication_slots = on` на резервном сервере | Синхронизирует слоты логической репликации |

Чего больше нет: отдельного процесса сборщика статистики (`stats collector`). Начиная с PostgreSQL 15 накопительная статистика хранится в общей памяти, параметр `stats_temp_directory` удалён [PG]. Рекомендация «вынести `pg_stat_tmp` в tmpfs» относится только к версиям до 14 включительно.

В Debian-раскладке к заголовку каждого процесса добавлено имя кластера: `postgres: 17/main: checkpointer`. Это значение параметра `cluster_name`.

### 2.3. Как посмотреть процессы

```bash
# дерево процессов экземпляра
sudo -u postgres ps -o pid,ppid,stat,rss,etime,cmd --forest -u postgres

# PID postmaster — первая строка файла-блокировки
sudo head -1 /var/lib/postgresql/17/main/postmaster.pid

# сколько серверных процессов (соединений) сейчас
ps -u postgres -o cmd | grep -c -E 'postgres: .*(idle|active|in transaction)'
```

```sql
-- все процессы экземпляра глазами SQL
SELECT pid, backend_type, state, backend_start
FROM pg_stat_activity
ORDER BY backend_type, backend_start;

-- распределение по типам
SELECT backend_type, count(*)
FROM pg_stat_activity
GROUP BY backend_type
ORDER BY count(*) DESC;

-- сколько слотов занято и сколько осталось
SELECT (SELECT count(*) FROM pg_stat_activity WHERE backend_type = 'client backend') AS used,
       current_setting('max_connections')::int AS max_conn,
       current_setting('superuser_reserved_connections')::int AS reserved;
```

Состояния серверного процесса (`pg_stat_activity.state`) [PG]: `starting` (18+, идёт подключение), `active`, `idle`, `idle in transaction`, `idle in transaction (aborted)`, `fastpath function call`, `disabled`. Для 1С нормальна картина «много `idle`, немного `active`». Долгий `idle in transaction` — повод разбираться: такая транзакция держит блокировки и мешает очистке (раздел 6.3).

### 2.4. Запуск и остановка: что происходит

1. Postmaster читает `postgresql.conf`, проверяет `postmaster.pid`, выделяет общую память, открывает порт.
2. Процесс `startup` читает `global/pg_control`. Если сервер был остановлен штатно — восстановление не нужно. Если нет — повторяет WAL от последней контрольной точки (раздел 5.5).
3. После этого запускаются остальные фоновые процессы, сервер начинает принимать соединения: `database system is ready to accept connections`.

Режимы остановки (`pg_ctl stop -m …`; `systemctl stop` в Debian использует `fast`) [PG]:

| Режим | Сигнал postmaster | Поведение |
|---|---|---|
| `smart` | `SIGTERM` | ждёт, пока все клиенты отключатся сами. С пулом соединений 1С не завершится никогда |
| `fast` (умолчание) | `SIGINT` | откатывает активные транзакции, отключает клиентов, выполняет контрольную точку и останавливается |
| `immediate` | `SIGQUIT` | останавливается без контрольной точки; при следующем старте — восстановление по WAL |

Порядок остановки связки: сначала сервер 1С (`systemctl stop srv1cv8-…@default` — точное имя службы зависит от версии платформы), потом PostgreSQL. Запуск — в обратном порядке.

## 3. Память

### 3.1. Общая (разделяемая) память

Выделяется postmaster при старте, видна всем процессам.

| Область | Параметр | Умолчание | Замечания |
|---|---|---|---|
| Буферный кеш | `shared_buffers` | 128MB | Кеш страниц данных по 8 КБ. Отправная точка — 25 % ОЗУ; больше 40 % редко даёт пользу, потому что работает ещё и кеш ОС [PG]. Только перезапуск |
| Буферы WAL | `wal_buffers` | -1 = 1/32 от `shared_buffers`, не меньше 64 КБ и не больше одного сегмента WAL (16 МБ) | Записи WAL до сброса на диск. Только перезапуск |
| Таблица блокировок | `max_locks_per_transaction` объектов на каждый серверный процесс и подготовленную транзакцию (раздел 7.6) | 64 × (100 соединений + служебные процессы) ≈ 7,8–8,7 тыс. | «Не более стольких различных объектов может быть заблокировано одновременно» [PG]. Только перезапуск |
| Таблица предикатных блокировок | `max_pred_locks_per_transaction` | 64 | Используется только транзакциями `SERIALIZABLE` |
| Кеши статусов транзакций (SLRU) | `transaction_buffers`, `subtransaction_buffers`, `commit_timestamp_buffers`, `multixact_offset_buffers`, `multixact_member_buffers` и др. (17+) | первые три — 0 = авто (`shared_buffers`/512, от 16 до 1024 страниц); `multixact_offset_buffers` — 16, `multixact_member_buffers` — 32 страницы | До 17-й версии размеры были зашиты в код |
| Накопительная статистика | — | — | С 15-й версии в общей памяти |

```sql
SHOW shared_buffers;
SHOW shared_memory_size;                    -- 15+: весь основной сегмент общей памяти
SHOW shared_memory_size_in_huge_pages;      -- 15+: он же в огромных страницах
SHOW huge_pages_status;                     -- 17+: реально ли используются huge pages

-- из чего состоит общая память (суперпользователь или pg_read_all_stats)
SELECT name, pg_size_pretty(allocated_size) AS size
FROM pg_shmem_allocations
ORDER BY allocated_size DESC
LIMIT 10;
```

### 3.2. Локальная память серверного процесса

| Параметр | Умолчание | На что выделяется | Сколько раз |
|---|---|---|---|
| `work_mem` | 4MB | Одна операция сортировки (`ORDER BY`, `DISTINCT`, соединение слиянием) или хеширования (хеш-соединение, хеш-агрегация, `Memoize`, хешированный `IN`) до перехода на временные файлы | **На каждую такую операцию.** В одном запросе их может быть несколько, сеансов — много, поэтому суммарно «во много раз больше `work_mem`» [PG] |
| `hash_mem_multiplier` | 2.0 (с 15-й версии; в 13–14 было 1.0) | Множитель лимита для хеш-операций: предел = `work_mem` × множитель | — |
| `maintenance_work_mem` | 64MB | `VACUUM`, `CREATE INDEX`, `ALTER TABLE ADD FOREIGN KEY` | Одна операция на сеанс; параллельные построители индекса делят этот предел между собой, а не умножают [PG] |
| `autovacuum_work_mem` | -1 (= `maintenance_work_mem`) | Память одного процесса autovacuum | До `autovacuum_max_workers` раз |
| `temp_buffers` | 8MB | Локальные буферы временных таблиц сеанса | На сеанс. Память берётся по мере надобности: описатель буфера — около 64 байт, реально использованный буфер — 8192 байта [PG]. Изменить можно только до первого обращения сеанса к временным таблицам |
| `logical_decoding_work_mem` | 64MB | Логическое декодирование | На каждое соединение репликации |
| `max_stack_depth` | 2MB | Предел глубины стека | — |
| кеши каталога и планов | не ограничены параметром | Описания таблиц, индексов, типов, подготовленные планы | Растут за время жизни соединения |

Особенности, важные для 1С:

- **Параллельные процессы умножают `work_mem`.** Каждый параллельный исполнитель — полноценный процесс со своим лимитом: запрос с 4 исполнителями может занять до 5 × `work_mem` на операцию [PG].
- **`temp_buffers` у 1С используется постоянно:** платформа интенсивно работает с временными таблицами. Локальные буферы, однажды выделенные сеансом, до конца сеанса не возвращаются [практика, по устройству менеджера локальных буферов], а соединения 1С долгоживущие. Отсюда официальный совет: «чем больше подключений и меньше ОЗУ, тем меньше значение» (32–256 МБ) [PGPro].
- **Нехватка `work_mem` не ошибка, а запись на диск:** в плане видно `Sort Method: external merge  Disk: …kB` или `Batches: N` больше 1 у хеш-соединения; в журнале — записи `temporary file` при `log_temp_files`.

### 3.3. Кеш операционной системы

PostgreSQL читает и пишет файлы данных через страничный кеш Linux (прямой ввод-вывод по умолчанию не используется). Одна и та же страница может лежать и в `shared_buffers`, и в кеше ОС — это «двойная буферизация», она и объясняет правило «25 %, а не 80 %».

- Параметр `effective_cache_size` (умолчание 4GB) **ничего не выделяет**. Это подсказка планировщику, сколько данных вероятно лежит в кеше (общий буфер плюс кеш ОС). Рекомендация: ОЗУ, доступное СУБД, минус `shared_buffers` [1С][PGPro].
- Свободной памяти на сервере СУБД «не бывает»: всё, что не занято процессами, Linux отдаёт под кеш файлов. Смотреть нужно столбец `available` в `free -h`, а не `free`.

```bash
free -h                                   # available = сколько можно занять без подкачки
grep -E 'MemTotal|MemAvailable|Cached|Dirty|Writeback|HugePages_(Total|Free)' /proc/meminfo
```

### 3.4. Как посчитать общий расход

Оценка сверху [практика]:

```text
Память PostgreSQL ≈ shared_memory_size
                  + N_активных × work_mem × K          (K — операций сортировки/хеширования в запросе, обычно 1–4;
                                                        для хеш-операций ещё × hash_mem_multiplier)
                  + N_соединений × (использованные temp_buffers + 10…50 МБ собственной памяти процесса)
                  + autovacuum_max_workers × autovacuum_work_mem (или maintenance_work_mem)
                  + ручные операции обслуживания × maintenance_work_mem
Остальное ОЗУ    → кеш ОС (он нужен: без него чтение идёт с диска)
```

Пример: ВМ 32 ГБ, сервер 1С на той же машине занимает около 12 ГБ, PostgreSQL отдано 20 ГБ. `shared_buffers = 5GB`, `work_mem = 64MB`, `temp_buffers = 64MB`, `maintenance_work_mem = 1GB`, `autovacuum_max_workers = 4`, 200 соединений, из них 30 активных.

| Статья | Расчёт | Итог |
|---|---|---|
| Общая память | `shared_memory_size` | ≈ 5,3 ГБ |
| Сортировки и хеши | 30 × 64 МБ × 2 | ≈ 3,8 ГБ |
| Временные таблицы (худший случай) | 200 × 64 МБ | 12,8 ГБ |
| Собственная память процессов | 200 × 20 МБ | 4 ГБ |
| Autovacuum (худший случай) | 4 × 1 ГБ | 4 ГБ |
| **Всего в худшем случае** | | **≈ 30 ГБ при бюджете 20 ГБ** |

Вывод из примера: на сервер с сотнями соединений нельзя ставить большие `temp_buffers` и `work_mem`. Худший случай редко наступает одновременно по всем статьям, но OOM-killer срабатывает именно в такие моменты (закрытие месяца, массовое перепроведение).

### 3.5. Диагностика памяти

```bash
# RSS включает затронутые страницы shared_buffers, поэтому сумма RSS завышена в разы
ps -u postgres -o pid,rss,cmd --sort=-rss | head -15

# честная сумма: PSS (общая память делится между процессами поровну)
sudo sh -c 'for p in $(pgrep -u postgres); do cat /proc/$p/smaps_rollup 2>/dev/null; done' \
  | awk '/^Pss:/{s+=$2} END{printf "PSS всего: %.1f ГБ\n", s/1024/1024}'

# собственная (анонимная) память одного процесса
sudo grep -E '^(Rss|Pss|Anonymous):' /proc/12345/smaps_rollup

# был ли OOM
journalctl -k --since "-7 days" | grep -i -E 'out of memory|oom-kill|killed process'
```

```sql
-- память текущего сеанса по контекстам (14+)
SELECT name, pg_size_pretty(total_bytes) AS total
FROM pg_backend_memory_contexts
ORDER BY total_bytes DESC
LIMIT 10;

-- вывести контексты памяти ЧУЖОГО процесса в журнал сервера (14+, суперпользователь)
SELECT pg_log_backend_memory_contexts(12345);

-- чем занят shared_buffers (расширение pg_buffercache; блокировок менеджера буферов не берёт, поэтому работе почти не мешает,
-- но картина по всем буферам не строго согласована [PG]; при большом shared_buffers сам проход занимает время)
CREATE EXTENSION IF NOT EXISTS pg_buffercache;
SELECT c.relname, count(*) * 8 / 1024 AS mb
FROM pg_buffercache b
JOIN pg_class c ON b.relfilenode = pg_relation_filenode(c.oid)
WHERE b.reldatabase = (SELECT oid FROM pg_database WHERE datname = current_database())
GROUP BY c.relname
ORDER BY count(*) DESC
LIMIT 15;
```

Защита от OOM на выделенном сервере СУБД — `vm.overcommit_memory = 2` и huge pages; подробности и значения — в `02-postgresql-conf-tyuning-dlya-1c.md`.

Удалять вручную можно лишь убедившись, что процессов `postgres` нет |

В Debian-раскладке `postgresql.conf`, `pg_hba.conf`, `pg_ident.conf` лежат не здесь, а в `/etc/postgresql/17/main/`. В раскладке Postgres Pro — прямо в каталоге данных.

Права: каталог данных принадлежит пользователю ОС `postgres`, режим `0700` (или `0750`, если кластер создан с `initdb --allow-group-access`). С другими правами сервер не запустится: `FATAL: data directory "…" has invalid permissions`.

### 4.2. OID, relfilenode, слои, сегменты

- У каждой таблицы и индекса есть **OID** (постоянный номер в `pg_class`) и **relfilenode** (имя файла на диске). Изначально они часто совпадают, но не обязаны: `TRUNCATE`, `REINDEX`, `CLUSTER`, `VACUUM FULL` и некоторые формы `ALTER TABLE` создают новый файл, сохраняя OID [PG].
- У некоторых системных таблиц (включая сам `pg_class`) `relfilenode = 0`; настоящее значение даёт `pg_relation_filenode()` [PG].
- Каждое отношение хранится в нескольких **слоях** (fork):

| Слой | Имя файла | Что хранит |
|---|---|---|
| основной (main) | `<relfilenode>` | сами данные |
| карта свободного места (fsm) | `<relfilenode>_fsm` | сколько свободного места в каждой странице; по ней `INSERT` ищет место |
| карта видимости (vm) | `<relfilenode>_vm` | два бита на страницу таблицы: «все версии видны всем» и «все версии заморожены». Нужна `VACUUM` (пропуск чистых страниц) и сканированию только по индексу. У индексов этого слоя нет |
| слой инициализации (init) | `<relfilenode>_init` | только у нежурналируемых (`UNLOGGED`) отношений: пустой образ, из которого объект пересоздаётся после сбоя |

- Файл больше 1 ГБ делится на **сегменты**: `<relfilenode>`, `<relfilenode>.1`, `<relfilenode>.2` … [PG]. Таблица на 50 ГБ — это 50 файлов.
- Файлы временных таблиц называются `t<номер процесса>_<relfilenode>`, где номер — внутренний номер серверного процесса (в документации 16 — backend ID, в 17+ — process number), а не PID [PG].

Как найти файл таблицы и обратно:

```sql
-- имена таблиц 1С в PostgreSQL — в нижнем регистре
SELECT pg_relation_filepath('_reference12');           -- base/16384/16423
SELECT pg_relation_filepath('_reference12_pkey');      -- путь к файлу индекса (имя индекса — ваше)

-- OID базы = имя подкаталога в base/
SELECT oid, datname FROM pg_database ORDER BY oid;

-- обратная задача: чей это файл (0 = табличное пространство базы по умолчанию)
SELECT pg_filenode_relation(0, 16423);

-- OID, relfilenode, табличное пространство, TOAST-таблица
SELECT c.oid, c.relfilenode, c.relkind, c.relpersistence,
       coalesce(t.spcname, '(по умолчанию для базы)') AS tablespace,
       c.reltoastrelid::regclass AS toast
FROM pg_class c
LEFT JOIN pg_tablespace t ON t.oid = c.reltablespace
WHERE c.relname = '_reference12';
```

```bash
# то же из командной строки (утилита из состава сервера)
sudo -u postgres /usr/lib/postgresql/17/bin/oid2name                    # базы и их OID
sudo -u postgres /usr/lib/postgresql/17/bin/oid2name -d base1c -f 16423 # чей файл
sudo -u postgres /usr/lib/postgresql/17/bin/oid2name -d base1c -t _reference12

# все файлы одного отношения
sudo ls -l /var/lib/postgresql/17/main/base/16384/16423*
```

`pg_relation_filepath()` возвращает только первый сегмент основного слоя; остальные файлы получаются добавлением `.N`, `_fsm`, `_vm` [PG]. Значения `relkind`: `r` — таблица, `i` — индекс, `t` — TOAST-таблица, `S` — последовательность, `v` — представление, `m` — материализованное представление, `p` — секционированная таблица. Значения `relpersistence`: `p` — постоянная, `u` — нежурналируемая, `t` — временная.

Зачем это администратору 1С: сопоставить файл из сообщения об ошибке (`could not read block 123 in file "base/16384/16423"`, `invalid page in block …`) с таблицей; понять, какой объект занимает место на диске; убедиться, что после `VACUUM FULL` старый файл удалён.

### 4.3. Страница и версия строки

- Все файлы данных состоят из страниц фиксированного размера, **обычно 8 КБ**; размер задаётся при сборке сервера [PG]. Проверка: `SHOW block_size;`.
- Устройство страницы [PG]: заголовок 24 байта (в нём LSN последнего изменения `pd_lsn`, контрольная сумма `pd_checksum`, границы свободного места) → массив указателей на строки по 4 байта → свободное место → сами версии строк, растущие от конца страницы → специальная область (у индексов).
- Заголовок версии строки — 23 байта: `t_xmin`, `t_xmax`, `t_cid`, `t_ctid`, два поля флагов, смещение данных; затем необязательная битовая карта NULL-значений и данные с выравниванием [PG].
- Адрес версии строки — **ctid**: пара «номер страницы, номер указателя», например `(0,1)`. Индекс хранит именно ctid.
- Версия строки не может пересекать границу страницы. Длинные значения выносятся в TOAST (раздел 4.4).
- Пределы [PG, приложение «Ограничения PostgreSQL»]: таблица — до 32 ТБ при странице 8 КБ, столбцов в таблице — до 1600, одно значение поля — до 1 ГБ, длина идентификатора — 63 байта.

**Контрольные суммы страниц** обнаруживают повреждение данных на диске. `initdb` включает их по умолчанию начиная с PostgreSQL 18 (отключение — `--no-data-checksums`); в 12–17 нужен ключ `--data-checksums` [PG]. `pg_upgrade` требует одинаковой настройки в старом и новом кластере.

```sql
SHOW data_checksums;
```

```bash
# включить или проверить на ОСТАНОВЛЕННОМ кластере (12+)
sudo systemctl stop postgresql@17-main
sudo -u postgres /usr/lib/postgresql/17/bin/pg_checksums --check  -D /var/lib/postgresql/17/main
sudo -u postgres /usr/lib/postgresql/17/bin/pg_checksums --enable -D /var/lib/postgresql/17/main --progress
sudo systemctl start postgresql@17-main
```

### 4.4. TOAST

TOAST — механизм хранения больших значений [PG]:

- Срабатывает, когда версия строки шире примерно 2 КБ (`TOAST_TUPLE_THRESHOLD`). Значения сжимаются и (или) выносятся из строки, пока строка не станет короче 2 КБ (`TOAST_TUPLE_TARGET`; меняется параметром хранения таблицы `toast_tuple_target`).
- Вынесенное значение режется на куски примерно по 2000 байт и хранится в отдельной TOAST-таблице `pg_toast.pg_toast_<OID таблицы>` со столбцами `chunk_id`, `chunk_seq`, `chunk_data` и уникальным индексом по `(chunk_id, chunk_seq)`. В самой строке остаётся указатель размером 18 байт.
- Предел одного значения — 1 ГБ.
- Если при `UPDATE` вынесенное значение не менялось, оно не перезаписывается.

Стратегии хранения столбца:

| Стратегия | Сжатие | Вынос из строки | Где применяется |
|---|---|---|---|
| `PLAIN` | нет | нет | типы фиксированной длины |
| `EXTENDED` | да | да | умолчание для большинства типов переменной длины |
| `EXTERNAL` | нет | да | быстрее операции с подстроками, больше места |
| `MAIN` | да | только в крайнем случае | |

Метод сжатия задаётся для столбца (`COMPRESSION pglz` или `lz4`) либо параметром `default_toast_compression` (14+; умолчание `pglz`, в PostgreSQL 19 — `lz4`) [PG].

Для базы 1С:

- В TOAST попадают строки неограниченной длины (`mvarchar` без длины) и двоичные данные (`bytea`): `ХранилищеЗначения`, присоединённые файлы, сама конфигурация в таблице `config`. Поэтому «размер таблицы» без TOAST вводит в заблуждение.
- `pg_relation_size()` — только основной слой; `pg_table_size()` — таблица вместе с TOAST, картами и без индексов; `pg_total_relation_size()` — всё вместе с индексами.

```sql
-- самые большие таблицы с разбивкой: куча, TOAST, индексы
SELECT c.relname,
       pg_size_pretty(pg_relation_size(c.oid))                         AS heap,
       pg_size_pretty(coalesce(pg_total_relation_size(c.reltoastrelid), 0)) AS toast,
       pg_size_pretty(pg_indexes_size(c.oid))                          AS indexes,
       pg_size_pretty(pg_total_relation_size(c.oid))                   AS total
FROM pg_class c
JOIN pg_namespace n ON n.oid = c.relnamespace
WHERE c.relkind = 'r' AND n.nspname = 'public'
ORDER BY pg_total_relation_size(c.oid) DESC
LIMIT 20;
```

### 4.5. Табличные пространства

Табличное пространство — именованный каталог файловой системы, в котором лежат файлы объектов [PG].

- Встроенные: `pg_default` (это `base/`) и `pg_global` (это `global/`).
- Пользовательское пространство — это символическая ссылка `pg_tblspc/<OID>` на каталог. Внутри сервер создаёт подкаталог версии вида `PG_17_202406281` (число — версия системного каталога), а в нём — подкаталоги по OID баз [PG].
- Каталог должен существовать, быть пустым и принадлежать пользователю ОС `postgres`. Размещать его внутри `PGDATA` не следует.

```bash
sudo install -d -o postgres -g postgres -m 700 /data/pg_index /data/pg_temp
```

```sql
CREATE TABLESPACE fast_temp LOCATION '/data/pg_temp';
SELECT spcname, pg_tablespace_location(oid) AS path, pg_size_pretty(pg_tablespace_size(oid)) AS size
FROM pg_tablespace;                                    -- в psql: \db+
ALTER TABLE имя SET TABLESPACE fast_temp;             -- перезапись таблицы под ACCESS EXCLUSIVE
ALTER DATABASE base1c SET TABLESPACE новое;           -- только когда к базе нет подключений
```

Что с этим делает 1С [1С, «Клиент-серверный вариант. Руководство администратора», п. 3.2.5.1; конспект — `kb/its-docs/cs-gl03-ustanovka-komponentov-p2.md`]:

| Имя | Назначение | Поведение платформы |
|---|---|---|
| `v81c_data` | данные | если существует — используется; если нет — рекомендуется создать |
| `v81c_index` | индексы | если существует — используется; если нет — рекомендуется создать |
| `pg_default` | — | используется, когда двух предыдущих нет |

```sql
-- команды из документации 1С; путь — существующий пустой каталог, владелец postgres
CREATE TABLESPACE v81c_data  LOCATION '/data/v81c_data';
CREATE TABLESPACE v81c_index LOCATION '/data/v81c_index';
```

Разносить данные и индексы имеет смысл только по физически разным устройствам. На одном виртуальном диске ВМ это ничего не даёт и лишь усложняет резервное копирование [практика].

Временные объекты: параметр `temp_tablespaces` задаёт, где создаются временные таблицы, их индексы и временные файлы сортировок. Вынос на отдельный быстрый диск рекомендован для 1С [1С][PGPro]; если характеристики диска другие, пространству задают свою стоимость: `ALTER TABLESPACE fast_temp SET (random_page_cost = 1.1);`.

Подводные камни:

- Табличное пространство — часть кластера, а не «внешний диск»: потеря его каталога делает кластер неработоспособным, даже если там были только временные объекты. Не размещайте табличные пространства на tmpfs и на дисках, которые не переживают перезагрузку ВМ [практика].
- Физическая копия (`pg_basebackup`, копирование файлов) должна включать все табличные пространства. `pg_basebackup` делает это сам, а при восстановлении на другой сервер пути переназначаются ключом `--tablespace-mapping=СТАРЫЙ=НОВЫЙ`.

### 4.6. Временные файлы

Не путать с временными таблицами. Временные файлы создаёт исполнитель запроса, когда сортировке или хешу не хватило `work_mem`.

- Место: `base/pgsql_tmp/` либо `pgsql_tmp/` внутри табличного пространства из `temp_tablespaces`. Имя — `pgsql_tmp<PID>.<N>` [PG].
- Удаляются по окончании операции. После аварии удаляются при старте сервера (`remove_temp_files_after_crash = on`, 14+).
- Ограничение: `temp_file_limit` (умолчание -1 — без ограничения) — предел дискового места под временные файлы одного процесса; при превышении запрос отменяется. Явные временные таблицы в этот предел не входят [PG].
- Журналирование: `log_temp_files = 0` пишет в журнал каждый временный файл; значение в килобайтах задаёт порог.

```sql
-- накопленная статистика по базам
SELECT datname, temp_files, pg_size_pretty(temp_bytes) AS temp_size
FROM pg_stat_database
ORDER BY temp_bytes DESC;

-- что лежит во временном каталоге прямо сейчас (12+)
SELECT name, pg_size_pretty(size) AS size, modification
FROM pg_ls_tmpdir()
ORDER BY size DESC;
```

## 5. WAL и контрольные точки

### 5.1. Зачем нужен WAL

Журнал предзаписи (Write-Ahead Log) решает две задачи:

1. **Надёжность без записи каждой страницы на диск.** При фиксации транзакции достаточно сбросить на диск короткие последовательные записи WAL. Сами страницы данных остаются «грязными» в `shared_buffers` и записываются позже, в фоне.
2. **Основа для всего остального:** восстановления после сбоя, резервных копий с восстановлением на момент времени, физической и логической репликации, механизма копий баз данных 1С.

Правило: запись WAL об изменении страницы должна попасть на диск раньше самой страницы.

Не журналируются: временные таблицы, нежурналируемые (`UNLOGGED`) таблицы — после сбоя они пусты, на реплику не передаются [PG].

### 5.2. LSN и сегменты

- **LSN** (Log Sequence Number) — позиция в потоке WAL: смещение в байтах, монотонно растёт. Тип `pg_lsn`, записывается как два шестнадцатеричных числа: `16/B374D848`.
- WAL хранится в `pg_wal/` **сегментами по 16 МБ** (размер задаётся при `initdb --wal-segsize`). Имя файла — 24 шестнадцатеричные цифры: линия времени (8), старшая часть LSN (8), номер сегмента (8). LSN `16/B374D848` на линии времени 1 лежит в файле `0000000100000016000000B3`.
- В заголовке каждой страницы данных хранится LSN последней изменившей её записи (`pd_lsn`). Так сервер понимает, применено ли уже изменение.

```sql
SELECT pg_current_wal_lsn()        AS write_lsn,     -- до куда записано
       pg_current_wal_insert_lsn() AS insert_lsn,    -- до куда вставлено в буферы
       pg_current_wal_flush_lsn()  AS flush_lsn;     -- до куда гарантированно на диске
SELECT pg_walfile_name(pg_current_wal_lsn());                     -- имя текущего сегмента
SELECT pg_size_pretty(pg_wal_lsn_diff(pg_current_wal_lsn(), '16/B374D848'));  -- объём WAL между точками
SELECT count(*) AS segments, pg_size_pretty(sum(size)) AS total FROM pg_ls_waldir();
SELECT pg_switch_wal();                                           -- принудительно начать новый сегмент

-- сколько WAL порождает операция: измерить до и после
SELECT pg_current_wal_lsn() AS before \gset
-- … выполнить операцию …
SELECT pg_size_pretty(pg_wal_lsn_diff(pg_current_wal_lsn(), :'before'));
```

```bash
# содержимое WAL (диагностика): что записано между двумя LSN
sudo -u postgres /usr/lib/postgresql/17/bin/pg_waldump -p /var/lib/postgresql/17/main/pg_wal \
     --start=16/B3000000 --end=16/B3010000 | head -30
# сводка по типам записей
sudo -u postgres /usr/lib/postgresql/17/bin/pg_waldump -p /var/lib/postgresql/17/main/pg_wal --stats \
     0000000100000016000000B3
```

Уровень подробности журнала — `wal_level` [PG]:

| Значение | Что пишется | Что возможно |
|---|---|---|
| `minimal` | минимум для восстановления после сбоя | ни архива, ни реплик; зато массовые загрузки быстрее |
| `replica` (умолчание) | достаточно для архива и физической репликации | `pg_basebackup`, реплики, восстановление на момент времени |
| `logical` | плюс данные для логического декодирования | логическая репликация; **нужен механизму копий баз данных 1С** |

Изменение `wal_level` требует перезапуска (в PostgreSQL 19 логический уровень включается автоматически по мере надобности при `wal_level = replica` [PG, примечания к 19 Beta]).

### 5.3. Контрольная точка

Контрольная точка — момент, к которому все изменения, сделанные раньше, гарантированно записаны в файлы данных [PG]. Процесс `checkpointer`:

1. запоминает текущую позицию WAL — **точку REDO**;
2. записывает на диск все страницы, которые были «грязными» на этот момент, растягивая запись на долю `checkpoint_completion_target` (0.9) от интервала, чтобы не создавать пик нагрузки;
3. выполняет `fsync` файлов данных;
4. пишет в WAL запись о контрольной точке и обновляет `global/pg_control`;
5. сегменты WAL старше точки REDO больше не нужны для восстановления — они удаляются или переименовываются для повторного использования.

Когда запускается [PG]:

| Причина | Параметр | Умолчание |
|---|---|---|
| по времени | `checkpoint_timeout` | 5min (диапазон 30 с — 1 сутки) |
| по объёму WAL | `max_wal_size` (мягкий предел) | 1GB |
| вручную | команда `CHECKPOINT` (суперпользователь или роль `pg_checkpoint`, 15+) | — |
| при остановке сервера, в начале `pg_basebackup`, при `CREATE DATABASE` со стратегией копирования файлов | — | — |

`max_wal_size` — не жёсткий предел: каталог `pg_wal` может вырасти больше при пиковой нагрузке, сбое архивации, отставшем слоте репликации или большом `wal_keep_size`. `min_wal_size` (80MB) — объём, ниже которого старые сегменты не удаляются, а оставляются для повторного использования.

Если контрольные точки по объёму случаются чаще, чем раз в `checkpoint_warning` (30 с), в журнале появляется сообщение `checkpoints are occurring too frequently (N seconds apart)` с советом увеличить `max_wal_size`.

```sql
-- 17+: статистика контрольных точек
SELECT num_timed, num_requested, write_time, sync_time, buffers_written, stats_reset
FROM pg_stat_checkpointer;

-- до 16 включительно те же счётчики — в pg_stat_bgwriter
SELECT checkpoints_timed, checkpoints_req, buffers_checkpoint, buffers_clean, buffers_backend
FROM pg_stat_bgwriter;

-- последняя контрольная точка
SELECT checkpoint_lsn, redo_lsn, redo_wal_file, checkpoint_time
FROM pg_control_checkpoint();
```

```bash
# то же без подключения к серверу (работает и на остановленном кластере)
sudo -u postgres /usr/lib/postgresql/17/bin/pg_controldata /var/lib/postgresql/17/main \
  | grep -E 'cluster state|checkpoint location|REDO location|REDO WAL file|Time of latest checkpoint|checksum'
```

Здоровая картина: подавляющее большинство контрольных точек — по времени (`num_timed`), а не по объёму (`num_requested`). В журнале при `log_checkpoints = on` (умолчание с 15-й версии) каждая точка описана строкой `checkpoint complete: wrote N buffers (X%); … write=… s, sync=… s, total=… s; … distance=… kB, estimate=… kB`.

### 5.4. Запись полных страниц (full_page_writes)

Страница PostgreSQL — 8 КБ, а диск и файловая система пишут блоками по 4 КБ или 512 байт. Если питание пропадёт посреди записи, на диске окажется страница, наполовину новая, наполовину старая («разорванная»). Применить к ней обычную запись WAL нельзя.

Защита: при **первом изменении страницы после контрольной точки** в WAL записывается её полный образ. При восстановлении страница берётся из WAL целиком [PG].

Следствия:

- Сразу после контрольной точки объём WAL резко возрастает. Чем чаще контрольные точки, тем больше полных образов — поэтому для 1С рекомендуют `checkpoint_timeout = 15min` и увеличенный `max_wal_size` [PGPro].
- `full_page_writes = off` грозит «невосстановимым или скрытым повреждением данных» после сбоя [PG]. Не выключать.
- `wal_compression` (`pglz`, `lz4`, `zstd` — с 15-й версии, в 14-й только `on`/`off`; умолчание `off`) сжимает именно полные образы страниц: меньше WAL ценой процессора.

### 5.5. Восстановление после сбоя

Происходит автоматически при запуске, если сервер не был остановлен штатно:

1. `startup` читает `pg_control`: состояние кластера не «shut down» — значит, нужна процедура восстановления.
2. Находит запись последней контрольной точки и её точку REDO.
3. Последовательно применяет все записи WAL от точки REDO до конца журнала. Запись применяется, только если LSN страницы меньше LSN записи.
4. Транзакции, у которых в WAL нет записи о фиксации, считаются прерванными (их версии строк никто не увидит; уберёт `VACUUM`).
5. Выполняется контрольная точка, сервер открывается для подключений.

В журнале это выглядит так:

```text
LOG:  database system was interrupted; last known up at 2026-10-10 03:12:44 +05
LOG:  database system was not properly shut down; automatic recovery in progress
LOG:  redo starts at 16/B3000028
LOG:  redo done at 16/B7FFFF98 system usage: CPU: user: 3.1 s, system: 1.2 s, elapsed: 9.8 s
LOG:  checkpoint starting: end-of-recovery immediate wait
LOG:  database system is ready to accept connections
```

Время восстановления определяется объёмом WAL, накопленным после последней контрольной точки, то есть сверху — примерно `max_wal_size` и `checkpoint_timeout`. Это плата за редкие контрольные точки: при `checkpoint_timeout = 15min` и `max_wal_size = 8GB` восстановление может занять минуты.

Пока идёт восстановление, подключения отклоняются с `FATAL: the database system is starting up` (а после аварии — `the database system is in recovery mode`). Сервер 1С в это время выдаёт пользователям ошибку СУБД; после открытия базы сеансы восстанавливают соединения сами.

### 5.6. fsync и надёжность

| Параметр | Умолчание | Что будет, если изменить |
|---|---|---|
| `fsync` | `on` | `off` — «невосстановимое повреждение данных» после сбоя питания или ОС [PG]. Допустимо только на одноразовых стендах |
| `synchronous_commit` | `on` | `off` — фиксация не ждёт сброса WAL; при сбое теряются транзакции максимум за 3 × `wal_writer_delay`, **целостность не нарушается** [PG]. Официально рекомендовано для 1С [1С][PGPro] |
| `full_page_writes` | `on` | `off` — риск разорванных страниц (раздел 5.4) |
| `wal_sync_method` | `fdatasync` в Linux | менять только по результатам `pg_test_fsync` |

Что означает потеря при `synchronous_commit = off` для 1С: пользователь получил «документ проведён», а после аварийного отключения питания документа в базе нет. База при этом согласована. Если это неприемлемо (например, обмен с внешней системой уже отправил подтверждение), оставьте `on`.

**Надёжность зависит от всей цепочки до носителя.** `fsync` бесполезен, если какой-то слой подтверждает запись, не доведя её до энергонезависимой памяти:

- диск с включённым кешем записи без защиты по питанию;
- RAID-контроллер с кешем отложенной записи без исправной батареи [PGPro];
- **гипервизор, который кеширует или игнорирует сброс кеша виртуального диска.** Для ВМ на Windows-хосте это главный риск: настройки кеширования виртуального диска и контроллера зависят от продукта (Hyper-V, VMware Workstation, VirtualBox) и от режима кеша хоста. Уточнено 19.10.2026 по руководству VirtualBox (разд. 12.2.2): VirtualBox по умолчанию **игнорирует** команды сброса кеша (IDE/SATA FLUSH CACHE) от гостя; включается для каждого диска `VBoxManage setextradata <ВМ> "VBoxInternal/Devices/ahci/0/LUN#[x]/Config/IgnoreFlush" 0` (для IDE — `piix3ide`), подробнее — `../linux/11-ustanovka-ubuntu-server-i-vm.md`. ⚠ не подтверждено для Hyper-V и VMware Workstation: проверьте по их документации, что команда сброса кеша (flush) из гостя доходит до физического диска хоста.

Проверка утилитой из состава сервера:

```bash
# сколько синхронных записей в секунду реально выдерживает том с данными
sudo -u postgres /usr/lib/postgresql/17/bin/pg_test_fsync -s 5 \
     -f /var/lib/postgresql/17/main/pg_test_fsync.tmp
```

Как читать результат [практика]: обычный SATA SSD без защиты по питанию даёт сотни — единицы тысяч операций `fdatasync` в секунду, жёсткий диск — около сотни. Если в ВМ вы видите десятки тысяч и больше на рядовом оборудовании — скорее всего, сброс кеша где-то игнорируется, и после отключения питания хоста база может оказаться повреждённой.

### 5.7. Связь параметров между собой

| Хочу | Что менять | Цена |
|---|---|---|
| Реже контрольные точки, меньше полных образов страниц, ровнее нагрузка на диск | `checkpoint_timeout` ↑ (15min), `max_wal_size` ↑ | дольше восстановление после сбоя, больше места под `pg_wal` |
| Быстрее фиксация транзакций | `synchronous_commit = off` | потеря до 0,6 с подтверждённых транзакций при сбое |
| Меньше объём WAL | `wal_compression = lz4` (или `zstd`) | процессорное время |
| Групповая фиксация при очень высокой нагрузке | `commit_delay = 1000` (имеет смысл при TPS выше 1000 [PGPro]) | небольшая задержка каждой фиксации |
| Ограничить рост `pg_wal` из-за слота | `max_slot_wal_keep_size` (13+) | слот может стать недействительным |
| Больше `shared_buffers` | вместе с ним увеличить `max_wal_size` [PG] | — |

Конкретные значения для 1С — в `02-postgresql-conf-tyuning-dlya-1c.md`.

Почему может переполниться `pg_wal`: не работает `archive_command` (сегменты ждут архивации), отстала или отключена реплика со слотом, забыт слот логической репликации (в том числе от механизма копий баз 1С), задан большой `wal_keep_size`, идёт массовая операция (реструктуризация, загрузка `.dt`) при маленьком диске.

```sql
SELECT slot_name, slot_type, active, wal_status,
       pg_size_pretty(pg_wal_lsn_diff(pg_current_wal_lsn(), restart_lsn)) AS retained
FROM pg_replication_slots;

SELECT archived_count, failed_count, last_failed_wal, last_failed_time FROM pg_stat_archiver;
```

## 6. MVCC: версии строк, снимки, изоляция

### 6.1. Версии строк

PostgreSQL не изменяет строку на месте. У каждой версии строки есть скрытые системные столбцы:

| Столбец | Смысл |
|---|---|
| `xmin` | номер транзакции, создавшей версию |
| `xmax` | номер транзакции, удалившей версию (или заблокировавшей строку); `0` — версия не удалена |
| `ctid` | физический адрес версии: (страница, указатель) |
| `cmin`, `cmax` | номер команды внутри транзакции |
| `tableoid` | OID таблицы |

- `INSERT` создаёт версию с `xmin` = своя транзакция.
- `DELETE` ставит `xmax` = своя транзакция; сама версия остаётся на месте.
- `UPDATE` = `DELETE` старой версии + `INSERT` новой. В старой версии `t_ctid` указывает на новую.

Посмотреть своими глазами (в любой базе, во временной таблице — постоянные данные не затрагиваются):

```sql
CREATE TEMP TABLE mvcc_demo (id int, v text);
INSERT INTO mvcc_demo VALUES (1, 'a');
SELECT ctid, xmin, xmax, * FROM mvcc_demo;      -- (0,1) | 751 | 0 | 1 | a
UPDATE mvcc_demo SET v = 'b' WHERE id = 1;
SELECT ctid, xmin, xmax, * FROM mvcc_demo;      -- (0,2) | 752 | 0 | 1 | b   — новая версия по новому адресу
DROP TABLE mvcc_demo;
```

Номер транзакции выдаётся только при первом изменении данных; чисто читающая транзакция номера не получает и счётчик не расходует [PG].

```sql
SELECT pg_current_xact_id_if_assigned();   -- 13+: NULL, пока транзакция ничего не меняла
SELECT pg_current_xact_id();               -- 13+: выдать номер (старое имя — txid_current())
```

### 6.2. Снимки и правила видимости

**Снимок** — это ответ на вопрос «какие транзакции считать завершёнными». Он состоит из трёх частей: `xmin` (все транзакции с меньшим номером завершены), `xmax` (все с номером не меньше этого ещё не начинались) и списка активных между ними.

```sql
SELECT pg_current_snapshot();     -- 13+: например 751:755:751,753  (xmin:xmax:активные)
```

Версия строки видна снимку, если:

- транзакция `xmin` зафиксирована и по снимку считается завершённой;
- и при этом `xmax` пуст, либо транзакция `xmax` прервана, либо по снимку ещё не завершена.

Откуда берётся статус транзакции: из `pg_xact/` (2 бита на транзакцию). Чтобы не ходить туда каждый раз, первый читатель записывает в заголовок версии **биты-подсказки** (hint bits) «xmin зафиксирована» и т. п. Отсюда неожиданное для новичков явление: **`SELECT` может пачкать страницы и вызывать запись на диск**, особенно первое чтение после массовой загрузки. При включённых контрольных суммах изменение бита-подсказки после контрольной точки ещё и пишет полный образ страницы в WAL [PG]. После загрузки `.dt` или восстановления из логической копии полезно сразу выполнить `VACUUM (ANALYZE)` — он расставит биты за один проход.

Следствия MVCC:

- Читатель никогда не ждёт писателя, писатель — читателя. Ждут друг друга только два писателя одной и той же строки.
- Откат транзакции мгновенный: достаточно пометить её прерванной в `pg_xact`. Поэтому «отмена длинной операции» в PostgreSQL не занимает часы, как бывает в MS SQL Server; зато остаётся мусор.
- 1С относит PostgreSQL к **версионным СУБД** (вместе с файловым вариантом и Oracle Database) [1С, «Руководство администратора», гл. 6; конспект — `kb/its-docs/adm-gl06-administrirovanie-ib-p3.md`].

### 6.3. Мёртвые строки и горизонт очистки

Версия становится «мёртвой», когда её не может увидеть ни один существующий снимок. До этого `VACUUM` удалить её не вправе. Границу задаёт **горизонт** — самый старый `xmin` среди всех снимков в кластере. Его удерживают:

- транзакция, открытая давно (в том числе сеанс в состоянии `idle in transaction`);
- длинный запрос или `pg_dump`;
- подготовленная транзакция (`pg_prepared_xacts`);
- слот репликации (`pg_replication_slots.xmin`, `catalog_xmin`);
- реплика с `hot_standby_feedback = on`.

Одна забытая транзакция останавливает очистку **во всех таблицах всех баз кластера**. Для 1С типичные виновники: зависший сеанс с открытой транзакцией, многочасовой отчёт или обмен в транзакции, слот от механизма копий баз данных.

```sql
-- кто держит горизонт
SELECT pid, state, xact_start, now() - xact_start AS xact_age,
       age(backend_xid) AS xid_age, age(backend_xmin) AS xmin_age,
       left(query, 60) AS query
FROM pg_stat_activity
WHERE backend_xid IS NOT NULL OR backend_xmin IS NOT NULL
ORDER BY greatest(age(backend_xid), age(backend_xmin)) DESC
LIMIT 10;

-- сколько мусора накоплено
SELECT relname, n_live_tup, n_dead_tup, last_autovacuum, last_autoanalyze
FROM pg_stat_user_tables
ORDER BY n_dead_tup DESC
LIMIT 15;
```

Предохранитель: `idle_in_transaction_session_timeout` завершает сеанс, простаивающий в транзакции дольше заданного. Ставить его для роли 1С нужно осторожно — см. `06-monitoring-i-diagnostika-zaprosov.md`, раздел 2.4. Работа `VACUUM` и autovacuum подробно — в `05-obsluzhivanie-vacuum-analyze-reindex.md`.

### 6.4. HOT-обновления

Обычный `UPDATE` требует новой записи в **каждом** индексе таблицы, даже если индексированные поля не менялись. HOT (Heap-Only Tuple) этого избегает. Условия [PG]:

1. обновление не меняет ни одного столбца, входящего в индексы таблицы (кроме «сводных» индексов — в ядре это только BRIN; это исключение действует с 16-й версии, раньше мешал и BRIN);
2. на той же странице есть место для новой версии.

Что это даёт: новые записи в индексах не создаются; старые версии вычищаются «на ходу» при обычном обращении к странице, в том числе при `SELECT`, не дожидаясь `VACUUM`.

```sql
SELECT relname, n_tup_upd, n_tup_hot_upd,
       round(100.0 * n_tup_hot_upd / nullif(n_tup_upd, 0), 1) AS hot_pct
FROM pg_stat_user_tables
WHERE n_tup_upd > 10000
ORDER BY n_tup_upd DESC
LIMIT 20;
```

Место под HOT оставляет параметр хранения `fillfactor` (для таблиц по умолчанию 100 — страницы заполняются полностью). Для баз 1С менять его как правило не стоит: у таблиц 1С много индексов, обновления часто затрагивают индексированные поля, а параметр, заданный вручную, пропадёт при пересоздании таблицы в ходе реструктуризации [практика].

### 6.5. Заморозка и переполнение счётчика транзакций

- Номер транзакции — 32 бита. Сравнение идёт «по кругу»: для любого номера около 2 млрд номеров считаются прошлым и около 2 млрд — будущим [PG].
- Если версии строки больше 2 млрд транзакций, она «уехала бы в будущее» и стала невидимой. Чтобы этого не случилось, `VACUUM` **замораживает** старые версии: ставит в заголовке флаг «старше любой транзакции».
- Правило: каждая таблица каждой базы должна проходить очистку не реже, чем раз в 2 млрд транзакций [PG].

| Параметр | Умолчание | Смысл |
|---|---|---|
| `vacuum_freeze_min_age` | 50 млн | версии старше — замораживать при очистке |
| `vacuum_freeze_table_age` | 150 млн | при таком возрасте таблицы очистка становится «агрессивной» (читает и страницы, помеченные all-visible) |
| `autovacuum_freeze_max_age` | 200 млн | autovacuum запускается принудительно, **даже если он выключен** [PG] |
| `vacuum_failsafe_age` (14+) | 1,6 млрд | аварийный режим: очистка бросает всё необязательное (индексы, задержки) ради заморозки |

Аналогичные параметры есть для мультитранзакций (`vacuum_multixact_freeze_min_age`, `autovacuum_multixact_freeze_max_age` и др.).

Что произойдёт при запущенной ситуации [PG]:

- когда до переполнения остаётся 40 млн транзакций (в PostgreSQL 19 — 100 млн), в журнал идут предупреждения `WARNING: database "base1c" must be vacuumed within N transactions`;
- когда остаётся меньше 3 млн, сервер перестаёт выдавать номера: `ERROR: database is not accepting commands that assign new transaction IDs to avoid wraparound data loss in database "base1c"` (так с 17-й версии; в 14–16 текст короче — `database is not accepting commands to avoid wraparound data loss in database "base1c"`, а подсказка `HINT` советует остановить сервер и чистить в однопользовательском режиме). Читать можно, изменять нельзя — 1С встанет.

Лечение: найти и завершить то, что держит горизонт (раздел 6.3), затем выполнить обычный `VACUUM` по всей базе под суперпользователем. `VACUUM FULL` и `VACUUM FREEZE` для этого применять не нужно; однопользовательский режим тоже не нужен — документация 14–16 прямо оговаривает, что вопреки подсказке останавливать сервер не нужно [PG].

```sql
-- возраст баз: тревожно, если заметно больше autovacuum_freeze_max_age (200 млн)
SELECT datname, age(datfrozenxid) AS xid_age,
       round(100.0 * age(datfrozenxid) / 2000000000, 1) AS pct_to_wraparound
FROM pg_database
ORDER BY xid_age DESC;

-- самые «старые» таблицы текущей базы (включая их TOAST)
SELECT c.oid::regclass AS table_name,
       greatest(age(c.relfrozenxid), age(t.relfrozenxid)) AS xid_age
FROM pg_class c
LEFT JOIN pg_class t ON c.reltoastrelid = t.oid
WHERE c.relkind IN ('r', 'm')
ORDER BY xid_age DESC
LIMIT 15;
```

Особенность: autovacuum «для предотвращения переполнения» (в `pg_stat_activity` он виден с пометкой `(to prevent wraparound)`) не уступает дорогу запросам, которым нужна конфликтующая блокировка. Обычный autovacuum в такой ситуации прерывается сам. Поэтому реструктуризация 1С может надолго встать в очередь за такой очисткой [PG].

### 6.6. Уровни изоляции в PostgreSQL

| Уровень | «Грязное» чтение | Неповторяемое чтение | Фантомы | Аномалии сериализации |
|---|---|---|---|---|
| Read Uncommitted | допускается стандартом, **в PostgreSQL невозможно** | возможно | возможно | возможны |
| Read Committed (умолчание) | невозможно | возможно | возможно | возможны |
| Repeatable Read | невозможно | невозможно | допускается стандартом, **в PostgreSQL невозможно** | возможны |
| Serializable | невозможно | невозможно | невозможно | невозможны |

Как это работает [PG]:

- **Read Committed.** Снимок берётся в начале **каждого оператора**. Два `SELECT` подряд в одной транзакции могут вернуть разное. Если `UPDATE` или `DELETE` натыкается на строку, которую в этот момент меняет другая транзакция, он ждёт. Если та откатилась — работает с исходной строкой; если зафиксировалась — перечитывает строку, заново проверяет условие `WHERE` и продолжает, только если строка всё ещё подходит.
- **Repeatable Read.** Снимок берётся один раз, при первом операторе транзакции. Если нужную для изменения строку успела изменить и зафиксировать другая транзакция, выдаётся `ERROR: could not serialize access due to concurrent update`, и приложение должно повторить транзакцию целиком. Это «изоляция снимков».
- **Serializable.** То же, плюс отслеживание зависимостей чтения-записи между транзакциями (SSI). Для этого используются предикатные блокировки — в `pg_locks` режим `SIReadLock`. Они **никого не блокируют** и не вызывают взаимоблокировок, а при опасном сочетании одна из транзакций получает `ERROR: could not serialize access due to read/write dependencies among transactions`.
- Все ошибки сериализации имеют код SQLSTATE `40001`.

```sql
SHOW default_transaction_isolation;                 -- уровень по умолчанию для новых транзакций
SHOW transaction_isolation;                         -- уровень текущей транзакции
BEGIN ISOLATION LEVEL REPEATABLE READ;              -- задать для одной транзакции
-- … согласованные между собой запросы-отчёты …
COMMIT;
BEGIN; SET TRANSACTION ISOLATION LEVEL SERIALIZABLE; ROLLBACK;
```

Практическое применение для администратора: несколько диагностических запросов, результаты которых нужно сопоставлять между собой, выполняйте в одной транзакции `REPEATABLE READ` — они увидят один и тот же момент времени. Так же работает `pg_dump`.

### 6.7. Какие уровни использует 1С

Официальная таблица [1С, «Руководство разработчика» 8.3.27, п. 9.2.3.2 «Управляемые блокировки»]:

| СУБД | Автоматический режим блокировок | Управляемый режим блокировок |
|---|---|---|
| Файловая база | блокировки таблиц, Serializable | блокировки таблиц, Serializable |
| Microsoft SQL Server | блокировки записей, Repeatable Read или Serializable | блокировки записей, Read Committed (в версиях 2005 и новее — Read Committed Snapshot) |
| IBM Db2 | блокировки записей, Repeatable Read или Serializable | блокировки записей, Read Committed |
| **PostgreSQL** | **блокировки таблиц, Serializable** | **блокировки записей, Read Committed** |
| Oracle Database | блокировки таблиц, Serializable | блокировки записей, Read Committed |

То же в общем виде сказано на v8.1c.ru: в автоматическом режиме используются уровни Repeatable Read и Serializable, обеспечиваемые СУБД; в управляемом — более низкий уровень Read Committed, а согласованность обеспечивают блокировки, которые ставят объекты встроенного языка и разработчик [1С].

Что из этого следует для PostgreSQL:

- **Автоматический режим на PostgreSQL означает блокировку таблиц целиком.** Два пользователя не могут одновременно проводить документы, пишущие в один регистр. В `pg_stat_activity` это видно как ожидание `wait_event_type = 'Lock'`, `wait_event = 'relation'`. Для многопользовательской работы на PostgreSQL конфигурация должна быть в управляемом режиме (свойство конфигурации «Режим управления блокировкой данных»); все современные типовые конфигурации так и работают.
- **В управляемом режиме целостность обеспечивает не СУБД, а менеджер блокировок кластера 1С.** Управляемые блокировки в `pg_locks` не видны; искать их нужно в технологическом журнале (события `TLOCK`, `TTIMEOUT`, `TDEADLOCK`). Подробно — `06-monitoring-i-diagnostika-zaprosov.md`, раздел 3.
- В управляемом режиме блокировки СУБД всё равно возникают: два сеанса меняют одну и ту же строку (например, строку таблицы итогов регистра), идёт реструктуризация, обслуживание.
- Чтение вне транзакции в 1С по документации «безответственное»: может вернуть уже неактуальные данные и не учитывает блокировок других транзакций [1С, п. 9.2.3.1]. В PostgreSQL при этом читаются только зафиксированные данные — «грязное» чтение невозможно в принципе.
- **Уточнено 11.10.2026** («Руководство разработчика» 8.3.27, глава 9 и приложение 8, разд. 8.6): документация называет для автоматического режима на PostgreSQL блокировки таблиц и уровень изоляции Serializable, для управляемого — блокировки записей и Read Committed; тексты команд SQL она не приводит. Ранее было не подтверждено: какими именно командами SQL платформа реализует автоматический режим на PostgreSQL (явный `LOCK TABLE` и в каком режиме, какой уровень объявляет в `BEGIN`). Проверяется на стенде: событие `DBPOSTGRS` технологического журнала либо кратковременное `log_statement = 'all'`.

```bash
# стенд: увидеть команды управления транзакциями, которые шлёт платформа
sudo -u postgres psql -c "ALTER SYSTEM SET log_statement = 'all'" -c "SELECT pg_reload_conf()"
# … провести документ в 1С …
sudo grep -i -E 'isolation level|lock table|statement: (begin|commit|rollback)' \
     /var/log/postgresql/postgresql-17-main.log | tail -40
sudo -u postgres psql -c "ALTER SYSTEM RESET log_statement" -c "SELECT pg_reload_conf()"
```

На рабочем сервере `log_statement = 'all'` за минуты создаёт гигабайты журнала — только стенд или очень короткий интервал.

## 7. Блокировки

В PostgreSQL несколько независимых механизмов блокировок. Администратору 1С важны первые три строки таблицы.

| Вид | Где хранится | Видна в `pg_locks` | Кто ставит |
|---|---|---|---|
| Блокировки отношений (табличные) | общая память, таблица блокировок | да, `locktype = 'relation'` | любой SQL-оператор автоматически; `LOCK TABLE` явно |
| Блокировки строк | **в самой версии строки** (поле `xmax` и флаги) | только ожидание: `locktype = 'transactionid'` или `'tuple'` | `UPDATE`, `DELETE`, `SELECT … FOR UPDATE/SHARE` |
| Рекомендательные (advisory) | общая память | да, `locktype = 'advisory'` | приложение функциями `pg_advisory_*` |
| Предикатные | общая память | да, `mode = 'SIReadLock'` | транзакции `SERIALIZABLE`; никого не блокируют |
| Лёгкие (LWLock), закрепление буферов | общая память | нет; видны как `wait_event_type = 'LWLock'`, `'BufferPin'` (в 19-й версии тип переименован в `Buffer`) | ядро сервера; управлять ими нельзя |

### 7.1. Табличные блокировки: режимы

Все восемь режимов — блокировки уровня таблицы, даже если в названии есть слово `ROW` (названия исторические). Режимы отличаются только тем, с какими другими режимами конфликтуют [PG].

| Режим | Какие команды берут автоматически |
|---|---|
| `ACCESS SHARE` | `SELECT` — любой запрос, который только читает таблицу |
| `ROW SHARE` | `SELECT … FOR UPDATE`, `FOR NO KEY UPDATE`, `FOR SHARE`, `FOR KEY SHARE` |
| `ROW EXCLUSIVE` | `INSERT`, `UPDATE`, `DELETE`, `MERGE`, `COPY FROM` |
| `SHARE UPDATE EXCLUSIVE` | `VACUUM` (без `FULL`), `ANALYZE`, `CREATE INDEX CONCURRENTLY`, `REINDEX CONCURRENTLY`, `CREATE STATISTICS`, `COMMENT ON`, некоторые формы `ALTER TABLE` и `ALTER INDEX` |
| `SHARE` | `CREATE INDEX` (без `CONCURRENTLY`) |
| `SHARE ROW EXCLUSIVE` | `CREATE TRIGGER`, некоторые формы `ALTER TABLE` |
| `EXCLUSIVE` | `REFRESH MATERIALIZED VIEW CONCURRENTLY` |
| `ACCESS EXCLUSIVE` | `DROP TABLE`, `TRUNCATE`, `REINDEX`, `CLUSTER`, `VACUUM FULL`, `REFRESH MATERIALIZED VIEW` (без `CONCURRENTLY`), большинство форм `ALTER TABLE`; режим по умолчанию для `LOCK TABLE` |

Матрица совместимости (✗ — конфликт: запрошенный режим будет ждать) [PG, таблица 13.2]:

| Запрошен ↓ / Уже удерживается → | AS | RS | RE | SUE | S | SRE | E | AE |
|---|---|---|---|---|---|---|---|---|
| `ACCESS SHARE` (AS) | | | | | | | | ✗ |
| `ROW SHARE` (RS) | | | | | | | ✗ | ✗ |
| `ROW EXCLUSIVE` (RE) | | | | | ✗ | ✗ | ✗ | ✗ |
| `SHARE UPDATE EXCLUSIVE` (SUE) | | | | ✗ | ✗ | ✗ | ✗ | ✗ |
| `SHARE` (S) | | | ✗ | ✗ | | ✗ | ✗ | ✗ |
| `SHARE ROW EXCLUSIVE` (SRE) | | | ✗ | ✗ | ✗ | ✗ | ✗ | ✗ |
| `EXCLUSIVE` (E) | | ✗ | ✗ | ✗ | ✗ | ✗ | ✗ | ✗ |
| `ACCESS EXCLUSIVE` (AE) | ✗ | ✗ | ✗ | ✗ | ✗ | ✗ | ✗ | ✗ |

Как читать:

- Обычный `SELECT` (AS) мешает только `ACCESS EXCLUSIVE`, и только `ACCESS EXCLUSIVE` мешает ему.
- Запись (`RE`) совместима с записью: `INSERT`/`UPDATE`/`DELETE` разных строк одной таблицы идут параллельно.
- `VACUUM`, `ANALYZE` и `CREATE INDEX CONCURRENTLY` (SUE) не мешают ни чтению, ни записи, но мешают друг другу: два `VACUUM` одной таблицы одновременно невозможны, а ручной `ANALYZE` ждёт autovacuum.
- `CREATE INDEX` без `CONCURRENTLY` (S) допускает чтение, но останавливает запись на всё время построения.
- `REINDEX` без `CONCURRENTLY` блокирует запись в таблицу, а на сам индекс берёт `ACCESS EXCLUSIVE`. Планировщик при разборе любого запроса к таблице пытается взять `ACCESS SHARE` на все её индексы, поэтому на деле ждут практически все запросы к таблице, кроме части подготовленных с уже готовым планом [PG, `REINDEX`].

Блокировка удерживается **до конца транзакции**, а не до конца оператора.

### 7.2. Очередь блокировок: почему «безобидный» ALTER останавливает всю работу

Запросы на блокировку встают в очередь. Если запрос `ACCESS EXCLUSIVE` ждёт, все пришедшие после него — включая обычные `SELECT` — встают за ним.

Сценарий: в базе есть сеанс, который час назад прочитал таблицу и не закрыл транзакцию (`idle in transaction`, держит `ACCESS SHARE`). Администратор запускает `ALTER TABLE`, `VACUUM FULL` или 1С начинает реструктуризацию. Команда ждёт старую транзакцию — и за ней выстраиваются все пользователи этой таблицы. Снаружи это выглядит как «всё повисло после безобидной команды».

Защита при ручных операциях:

```sql
SET lock_timeout = '5s';          -- не ждать блокировку дольше 5 секунд
ALTER TABLE …;                    -- при неудаче: ERROR: canceling statement due to lock timeout — повторить позже
RESET lock_timeout;
```

Перед реструктуризацией и регламентными операциями убедитесь, что нет старых открытых транзакций (запрос из раздела 6.3).

### 7.3. Блокировки строк

Четыре режима [PG, таблица 13.3]:

| Запрошен ↓ / Удерживается → | `FOR KEY SHARE` | `FOR SHARE` | `FOR NO KEY UPDATE` | `FOR UPDATE` |
|---|---|---|---|---|
| `FOR KEY SHARE` | | | | ✗ |
| `FOR SHARE` | | | ✗ | ✗ |
| `FOR NO KEY UPDATE` | | ✗ | ✗ | ✗ |
| `FOR UPDATE` | ✗ | ✗ | ✗ | ✗ |

- `DELETE` и `UPDATE`, меняющий ключевые столбцы, берут `FOR UPDATE`; прочие `UPDATE` — `FOR NO KEY UPDATE`.
- Блокировки строк **не мешают чтению**: обычный `SELECT` их не замечает.
- Блокировка хранится в самой версии строки, а не в памяти, поэтому число заблокированных строк ничем не ограничено и **эскалации до блокировки таблицы не бывает** [PG]. Это существенное отличие от MS SQL Server, к которому привязаны многие описания поведения 1С.
- Обратная сторона: `SELECT … FOR UPDATE` изменяет строки на диске (ставит отметку), то есть порождает запись.
- В `pg_locks` удерживаемых блокировок строк нет. Видно только ожидание: ждущий процесс запрашивает `ShareLock` на `transactionid` — номер транзакции, которая держит строку. Посмотреть сами блокировки строк можно расширением `pgrowlocks`.

```sql
-- кто кого ждёт (9.6+)
SELECT a.pid AS waiting_pid, pg_blocking_pids(a.pid) AS blocked_by,
       a.wait_event_type, a.wait_event, now() - a.query_start AS waiting, left(a.query, 60) AS query
FROM pg_stat_activity a
WHERE cardinality(pg_blocking_pids(a.pid)) > 0;
```

### 7.4. Рекомендательные (advisory) блокировки

Блокировки с произвольным числовым ключом, смысл которых определяет приложение; сервер их не навязывает [PG].

| Функция | Действие |
|---|---|
| `pg_advisory_lock(key bigint)` | взять на уровне сеанса; ждать, если занята. Держится до явного снятия или конца сеанса, **переживает откат транзакции** |
| `pg_try_advisory_lock(key)` | попытаться взять без ожидания; возвращает `true`/`false` |
| `pg_advisory_unlock(key)`, `pg_advisory_unlock_all()` | снять |
| `pg_advisory_xact_lock(key)`, `pg_try_advisory_xact_lock(key)` | взять на уровне транзакции; снимается автоматически при её завершении |
| варианты `…_shared` | разделяемая блокировка |

Блокировки сеанса накапливаются: сколько раз взяли, столько раз нужно снять. Память под них общая с обычными блокировками — та же таблица блокировок, размер которой задают `max_locks_per_transaction` и `max_connections` (раздел 7.6).

Где пригодится администратору — не дать регламентному скрипту запуститься вторым экземпляром:

```bash
#!/bin/bash
# блокировка держится, пока живо соединение psql; второй экземпляр сразу выйдет
sudo -u postgres psql -d base1c -v ON_ERROR_STOP=1 <<'SQL'
SELECT pg_try_advisory_lock(20261010) AS got \gset
\if :got
  VACUUM (ANALYZE);
\else
  \echo 'обслуживание уже выполняется, выходим'
\endif
SQL
```

⚠ не подтверждено: использует ли платформа 1С рекомендательные блокировки PostgreSQL. Если в `pg_locks` своей базы строк с `locktype = 'advisory'` нет — не использует.

### 7.5. Взаимоблокировки

Две транзакции ждут друг друга. PostgreSQL обнаруживает это сам: процесс, прождавший блокировку `deadlock_timeout` (1 с), запускает проверку и, найдя цикл, прерывает одну из транзакций — обычно ту, чей процесс цикл обнаружил [практика]; документация предупреждает, что какую именно, предсказать трудно и полагаться на это нельзя [PG]:

```text
ERROR:  deadlock detected
DETAIL:  Process 21535 waits for ShareLock on transaction 5381; blocked by process 21536.
         Process 21536 waits for ShareLock on transaction 5380; blocked by process 21535.
HINT:  See server log for query details.
```

- Код SQLSTATE `40P01`. Счётчик — `pg_stat_database.deadlocks`.
- В журнале сервера рядом записаны тексты обоих запросов — по ним и находят виновников.
- `deadlock_timeout` заодно задаёт порог для `log_lock_waits` (умолчание `off`; в PostgreSQL 19 — `on`): ожидание блокировки дольше этого времени попадает в журнал.
- Лечится на стороне прикладного кода: одинаковый порядок захвата ресурсов во всех транзакциях и сразу максимальный нужный уровень блокировки. Разбор для 1С — `kb/its-metod/vzaimoblokirovki-i-oshibki-blokirovok.md`.

Различайте: взаимоблокировка **СУБД** (`deadlock detected` в журнале PostgreSQL) и взаимоблокировка **управляемых блокировок 1С** (`TDEADLOCK` в технологическом журнале, PostgreSQL о ней ничего не знает).

### 7.6. Таблица блокировок и max_locks_per_transaction

Таблица блокировок в общей памяти рассчитана на `max_locks_per_transaction` объектов на каждый серверный процесс и каждую подготовленную транзакцию [PG]. Серверных процессов в этом расчёте больше, чем `max_connections`: по исходному коду (14–18, `postinit.c`) это `max_connections` + процессы autovacuum и особые фоновые процессы (в 14–16 — `autovacuum_max_workers` + 1, в 17 — `autovacuum_max_workers` + 2, в 18 — `autovacuum_worker_slots` + 2) + `max_worker_processes` + `max_wal_senders`, затем добавляется `max_prepared_transactions`. Это общий пул: одна транзакция может взять больше «своей» доли, пока в пуле есть место. Когда место кончается:

```text
ERROR:  out of shared memory
HINT:  You might need to increase "max_locks_per_transaction".
```

Почему у 1С таблица переполняется легче, чем у обычных приложений:

- при закрытии соединения все его временные таблицы удаляются **одной транзакцией**; если блокировок не хватит, транзакция откатится и оставит «потерянные» временные таблицы [PGPro];
- реструктуризация и запросы к десяткам таблиц;
- `pg_dump` берёт `ACCESS SHARE` на **каждую** таблицу базы, а в базе 1С их десятки тысяч [практика].

Рекомендации: 256 [PGPro], 512–2000 [1С] (см. `02-postgresql-conf-tyuning-dlya-1c.md`). Параметр меняется только с перезапуском. В PostgreSQL 19 умолчание поднято с 64 до 128, при этом изменён расчёт размера: чтобы получить прежнюю ёмкость, значение нужно удваивать [PG, примечания к 19 Beta].

```sql
-- заполненность таблицы блокировок (блокировки «быстрого пути», fastpath, в ней не лежат)
-- ёмкость для 14–16; в 17 вместо «+ 1» нужно «+ 2», в 18+ вместо autovacuum_max_workers + 1 — autovacuum_worker_slots + 2
SELECT count(*) AS locks_now,
       current_setting('max_locks_per_transaction')::int
       * (current_setting('max_connections')::int
          + current_setting('autovacuum_max_workers')::int + 1
          + current_setting('max_worker_processes')::int
          + current_setting('max_wal_senders')::int
          + current_setting('max_prepared_transactions')::int) AS capacity
FROM pg_locks
WHERE locktype <> 'virtualxid' AND NOT fastpath;
```

## 8. Планировщик запросов

Объём раздела — то, что нужно для чтения планов. Сам разбор `EXPLAIN` с типовыми патологиями запросов 1С — в `06-monitoring-i-diagnostika-zaprosov.md`, раздел 7.

### 8.1. Путь запроса

1. **Разбор** — синтаксис, затем привязка имён к объектам каталога.
2. **Переписывание** — подстановка представлений и правил.
3. **Планирование** — перебор способов выполнения и выбор плана с наименьшей оценочной стоимостью.
4. **Выполнение** — узлы плана работают по принципу «дай следующую строку».

Планировщик стоимостной: он не знает, какой план быстрее на самом деле, а сравнивает оценки. Оценки строятся из статистики и констант стоимости. Плохой план почти всегда означает неверную оценку числа строк.

### 8.2. Статистика

| Где | Что хранит | Кто обновляет |
|---|---|---|
| `pg_class.reltuples`, `relpages`, `relallvisible` | оценка числа строк, число страниц, число страниц «видимых всем» | `VACUUM`, `ANALYZE`, `CREATE INDEX` |
| `pg_statistic` (читать через представление `pg_stats`) | распределение значений по каждому столбцу | `ANALYZE` и autovacuum |
| `pg_statistic_ext`, `pg_stats_ext` | расширенная статистика по группам столбцов | `ANALYZE` после `CREATE STATISTICS` |
| `pg_stat_*` (накопительная статистика) | счётчики обращений — **планировщик их не использует** | сервер во время работы |

Столбцы `pg_stats`:

| Столбец | Смысл |
|---|---|
| `null_frac` | доля NULL |
| `avg_width` | средняя ширина значения в байтах |
| `n_distinct` | число различных значений; отрицательное — доля от числа строк (`-1` — все значения уникальны) |
| `most_common_vals`, `most_common_freqs` | самые частые значения и их частоты |
| `histogram_bounds` | границы корзин гистограммы для остальных значений |
| `correlation` | насколько физический порядок строк совпадает с порядком значений (от -1 до 1); влияет на оценку стоимости индексного доступа |

Точность задаёт `default_statistics_target` (умолчание 100): столько элементов в списке частых значений и корзин в гистограмме; `ANALYZE` читает выборку 300 × это число строк (30 000) [PG].

```sql
-- что планировщик думает о таблице
SELECT relname, reltuples::bigint AS rows_est, relpages, relallvisible
FROM pg_class WHERE relname = '_document123';

-- распределение значений по столбцам
SELECT attname, null_frac, avg_width, n_distinct, correlation,
       left(most_common_vals::text, 80) AS mcv
FROM pg_stats
WHERE schemaname = 'public' AND tablename = '_document123'
ORDER BY attname;

-- когда статистика собиралась
SELECT relname, last_analyze, last_autoanalyze, n_mod_since_analyze
FROM pg_stat_user_tables WHERE relname = '_document123';

ANALYZE VERBOSE _document123;                                        -- обновить вручную
ALTER TABLE _document123 ALTER COLUMN _fld456rref SET STATISTICS 1000;  -- точнее для одного столбца
```

Для временных таблиц статистику никто не собирает автоматически (раздел 10) — это отдельная и важная для 1С тема.

### 8.3. Селективность и стоимость

- **Селективность** условия — доля строк, которые его пройдут. Оценка числа строк = `reltuples` × селективность.
- Для нескольких условий по разным столбцам селективности **перемножаются**, как будто столбцы независимы. Если они связаны (в 1С типично: организация и склад, регистратор и период), оценка получается заниженной в разы и на порядки. Итог — соединение вложенным циклом там, где нужен хеш.
- **Стоимость** измеряется в условных единицах: 1,0 = чтение одной страницы при последовательном проходе.

| Параметр | Умолчание | Смысл |
|---|---|---|
| `seq_page_cost` | 1.0 | чтение страницы подряд |
| `random_page_cost` | 4.0 | чтение произвольной страницы. Для SSD рекомендуют 1.1–1.3 [PGPro] |
| `cpu_tuple_cost` | 0.01 | обработка одной строки |
| `cpu_index_tuple_cost` | 0.005 | обработка одной записи индекса |
| `cpu_operator_cost` | 0.0025 | вычисление оператора или функции. Платформа 1С ставит 0.001 (раздел 8.9) |
| `parallel_setup_cost` | 1000 | запуск параллельных исполнителей |
| `parallel_tuple_cost` | 0.1 | передача строки от исполнителя ведущему процессу |
| `effective_cache_size` | 4GB | предполагаемый объём кеша; чем больше, тем привлекательнее индексный доступ |

В плане у каждого узла записано `cost=A..B rows=N width=W`: `A` — стоимость до выдачи первой строки, `B` — полная стоимость, `N` — оценка числа строк, `W` — средняя ширина строки в байтах. Стоимость последовательного чтения таблицы без условий = `relpages` × `seq_page_cost` + `reltuples` × `cpu_tuple_cost`.

### 8.4. Методы доступа к таблице

| Узел плана | Как работает | Когда выбирается |
|---|---|---|
| `Seq Scan` | читает все страницы подряд | условие отбирает большую долю строк, таблица мала или подходящего индекса нет |
| `Index Scan` | идёт по индексу, за каждой строкой обращается в таблицу | условие отбирает мало строк; нужен порядок индекса |
| `Index Only Scan` | берёт данные прямо из индекса, в таблицу ходит только для страниц, не отмеченных в карте видимости | все нужные столбцы есть в индексе. Признак проблемы — большое `Heap Fetches`: таблицу давно не чистил `VACUUM` |
| `Bitmap Index Scan` + `Bitmap Heap Scan` | сначала по индексу строится битовая карта страниц, потом страницы читаются по порядку; карты нескольких индексов можно объединять (`BitmapAnd`, `BitmapOr`) | средняя доля строк, несколько условий по разным индексам. Если карта не помещается в `work_mem`, она становится «грубой» — в плане `Heap Blocks: lossy=N` и перепроверка условий |
| `Tid Scan` | прямое обращение по `ctid` | редко |

В PostgreSQL 18 появился пропускающий просмотр B-дерева (skip scan): многоколоночный индекс может использоваться и тогда, когда на ведущий столбец условия нет [PG].

### 8.5. Методы соединения

| Узел | Как работает | Сильные и слабые стороны |
|---|---|---|
| `Nested Loop` | для каждой строки внешнего набора ищет подходящие во внутреннем | идеален, когда внешний набор мал и по внутреннему есть индекс. Катастрофа, если планировщик ждал 1 строку, а пришло 100 000: в плане `loops=100000` |
| `Hash Join` | строит хеш-таблицу по меньшему набору, затем проходит по большему | большие наборы, только условия равенства. Хеш ограничен `work_mem` × `hash_mem_multiplier`; при нехватке делится на пакеты во временных файлах (`Batches` больше 1) |
| `Merge Join` | сливает два отсортированных набора | оба набора уже отсортированы или велики. **Платформа 1С отключает его для своих сеансов** (`enable_mergejoin = off`, раздел 8.9) |

Другие часто встречающиеся узлы: `Sort` (в памяти — `quicksort`, `top-N heapsort`; на диске — `external merge`), `Incremental Sort` (13+), `HashAggregate` и `GroupAggregate`, `Limit`, `Materialize`, `Memoize` (14+, кеш результатов внутренней стороны вложенного цикла), `Append`, `SubPlan` и `InitPlan` (подзапросы), `CTE Scan`, `Gather` и `Gather Merge` (параллельное выполнение).

Параметры `enable_*` (`enable_nestloop`, `enable_hashjoin`, `enable_seqscan` и др.) не запрещают метод, а делают его очень дорогим. Это инструмент диагностики в отдельном сеансе: `SET enable_nestloop = off;` → повторить `EXPLAIN` → сравнить. В `postgresql.conf` их не выключают.

### 8.6. Порядок соединений и GEQO

Число вариантов порядка соединения растёт факториально, поэтому перебор ограничен:

| Параметр | Умолчание | Смысл |
|---|---|---|
| `join_collapse_limit` | 8 | до стольких таблиц планировщик сам переставляет явные `JOIN`; сверх этого порядок берётся как написан в запросе |
| `from_collapse_limit` | 8 | до стольких элементов подзапросы сливаются с внешним запросом |
| `geqo` | on | генетический оптимизатор для больших запросов |
| `geqo_threshold` | 12 | начиная с такого числа элементов `FROM` вместо полного перебора работает GEQO — быстрее планирует, но план может быть хуже и не обязан повторяться |

Запросы 1С (особенно с ограничениями доступа на уровне записей) легко содержат десятки таблиц. Для 1С рекомендуют `from_collapse_limit = 20`, `join_collapse_limit = 20`, `geqo = on`, `geqo_threshold = 12` [1С][PGPro]. Документация PostgreSQL предупреждает: значения этих двух пределов, равные `geqo_threshold` и больше, включают GEQO и могут давать неоптимальные планы [PG] — то есть для запросов от 12 таблиц при таких настройках работает именно генетический оптимизатор.

### 8.7. Параллельные планы

Узел `Gather` запускает до `max_parallel_workers_per_gather` (умолчание 2) дополнительных процессов из общего пула `max_parallel_workers` (8) и `max_worker_processes` (8).

Ограничения, важные для 1С [PG]:

- **просмотр временных таблиц выполняется только ведущим процессом** (операция «parallel restricted»), как и просмотр общих табличных выражений (CTE);
- запросы, изменяющие данные, параллельно не выполняются (кроме отдельных случаев вроде `CREATE TABLE AS`);
- каждый исполнитель получает собственный `work_mem`.

Запросы 1С в массе короткие и работают с временными таблицами, пользы от параллельности мало, а накладные расходы и расход памяти есть. Рекомендация для 1С — `max_parallel_workers_per_gather = 0` [PGPro]. Параллельное построение индексов и параллельная очистка индексов (`max_parallel_maintenance_workers`) при этом остаются полезными.

### 8.8. JIT

JIT-компиляция выражений через LLVM включается, когда оценка стоимости запроса превышает `jit_above_cost` (100 000). Окупается на долгих аналитических запросах; для потока коротких запросов 1С накладные расходы на компиляцию выше выигрыша, а из-за ошибок оценки JIT срабатывает и там, где не нужен.

- Умолчание `jit = on` в версиях 12–18 (если сервер собран с LLVM), **`off` начиная с PostgreSQL 19** — разработчики признали включение по оценке стоимости ненадёжным [PG].
- Для 1С: `jit = off` [1С][PGPro].
- В плане работа JIT видна блоком `JIT: Functions: N … Timing: … Total …` в конце.

### 8.9. Что платформа 1С задаёт сама

При установке соединения с PostgreSQL платформа выполняет [1С, ИТС 6011; конспект — `kb/its-metod/pg-rasshireniya-1c-i-metodika-rassledovaniya.md`]:

```sql
SET client_min_messages = error;
SET lc_messages TO 'en_US.UTF-8';
SET enable_mergejoin = off;
SET escape_string_warning = off;
SET cpu_operator_cost = 0.001;
SET client_encoding = 'utf8';
SET lock_timeout = 20000;
```

Следствия:

- План запроса 1С, полученный в `psql` без этих `SET`, может **отличаться** от того, что получает платформа. Перед `EXPLAIN` выполните те же команды.
- `lock_timeout = 20000` — это параметр информационной базы «Время ожидания блокировки данных» (20 секунд по умолчанию).
- `lc_messages = 'en_US.UTF-8'` — сообщения об ошибках СУБД в технологическом журнале и в сообщениях 1С идут по-английски. Локаль `en_US.UTF-8` стоит сгенерировать в ОС наряду с `ru_RU.UTF-8` [практика].
- Глобальные значения `enable_mergejoin` и `cpu_operator_cost` в `postgresql.conf` на сеансы 1С не влияют.

Сборки для 1С дополнительно меняют поведение планировщика модулями `plantuner` (в частности, `plantuner.fix_empty_table`) и `online_analyze` — см. `01-sborki-postgresql-dlya-1c-ustanovka.md` и `02-postgresql-conf-tyuning-dlya-1c.md`.

### 8.10. Кеш планов

Для подготовленных операторов сервер первые пять выполнений строит план под конкретные значения параметров, затем может перейти на общий план, если тот не хуже по оценке. Управляет этим `plan_cache_mode` (12+): `auto` (умолчание), `force_custom_plan`, `force_generic_plan` [PG]. Признак общего плана в `EXPLAIN` — параметры вида `$1` в условиях вместо значений.

### 8.11. Как читать план: минимум

```sql
BEGIN;                                           -- EXPLAIN ANALYZE действительно ВЫПОЛНЯЕТ запрос
EXPLAIN (ANALYZE, BUFFERS, VERBOSE, SETTINGS)    -- SETTINGS — 12+; в 18-й BUFFERS включён вместе с ANALYZE
SELECT …;
ROLLBACK;                                        -- откатить, если запрос изменял данные
```

Учебный пример (имена объектов условные):

```text
Nested Loop  (cost=0.85..1250.40 rows=10 width=64) (actual time=0.050..850.120 rows=48211 loops=1)
  Buffers: shared hit=190233 read=1204
  ->  Index Scan using idx_a on _document123 t1  (cost=0.42..8.44 rows=1 width=32) (actual time=0.020..15.300 rows=48211 loops=1)
        Index Cond: (_date_time >= '2026-09-01 00:00:00'::timestamp without time zone)
  ->  Index Scan using idx_b on _accumrg456 t2  (cost=0.43..124.10 rows=10 width=40) (actual time=0.010..0.015 rows=1 loops=48211)
        Index Cond: (_recorderrref = t1._idrref)
Planning Time: 1.200 ms
Execution Time: 870.500 ms
```

Правила чтения:

1. План — дерево; выполнение идёт от самых вложенных узлов к корню.
2. Сравнивайте `rows=` в оценке и в `actual`. Здесь у первого узла оценка 1, факт 48 211 — ошибка в десятки тысяч раз, отсюда вложенный цикл с `loops=48211`.
3. `actual time` и `rows` у узла даны **на один проход**; полное время узла = время × `loops`.
4. `Buffers: shared hit` — страницы из `shared_buffers`, `read` — прочитанные с диска (или из кеша ОС), `dirtied`/`written` — изменённые и записанные, `temp read/written` — временные файлы.
5. Ищите: `Seq Scan` по большой таблице с `Rows Removed by Filter` в миллионы; `Sort Method: external merge  Disk`; `Batches` больше 1; `Heap Fetches` в `Index Only Scan`.

## 9. Индексы

### 9.1. B-tree — основной тип

B-дерево — тип индекса по умолчанию [PG]; именно такие индексы платформа 1С создаёт для своих таблиц (в примерах ИТС — `USING btree`) [практика: убедитесь запросом из раздела 9.4].

- Поддерживает операторы `<`, `<=`, `=`, `>=`, `>`, а также `BETWEEN`, `IN`, `IS NULL`, `IS NOT NULL`; может отдавать строки в отсортированном порядке [PG].
- `LIKE 'абв%'` (шаблон с закреплённым началом) использует B-дерево, только если база в локали `C` либо индекс создан со специальным классом операторов (`text_pattern_ops` и подобные) [PG]. Для типов `mchar`/`mvarchar` поддержка индексов для `LIKE` реализована в самом модуле [PGPro].
- **Многоколоночный индекс** эффективен, когда есть условия на ведущие столбцы. Индекс по `(a, b, c)` хорош для условий на `a`, на `a, b`, на `a, b, c`; для условия только на `c` до версии 18 практически бесполезен. Это правило лежит в основе рекомендаций 1С по порядку измерений и условий в запросах.
- Запись индекса не может быть больше примерно трети страницы; при превышении — ошибка `index row size N exceeds btree version 4 maximum 2704 for index "…"`.
- Улучшения по версиям: 12 — компактнее хранение дубликатов и многоколоночных индексов; 13 — дедупликация одинаковых ключей; 14 — «восходящее» удаление устаревших записей, меньше раздувание при частых `UPDATE`; 17 — быстрее поиск по спискам `IN`; 18 — skip scan [PG]. Улучшения формата 12-й и 13-й версий (упорядоченное хранение дубликатов, дедупликация) индексы, перенесённые `pg_upgrade` со старой версии, получают только после `REINDEX` [PG, примечания к 12 и 13].

### 9.2. Прочие типы

| Тип | Для чего | Отношение к 1С |
|---|---|---|
| Hash | только равенство | платформа не использует |
| GiST | геометрия, диапазоны, поиск ближайших, полнотекстовый поиск | не использует |
| SP-GiST | несбалансированные структуры (префиксные деревья, квадродеревья) | не использует |
| GIN | составные значения: массивы, `jsonb`, полнотекстовый поиск, триграммы | в Postgres Pro Standard (17) есть `pg_trgm_mchar` — триграммный поиск схожих строк по `mchar`/`mvarchar`, только классы операторов GIN; в бесплатной сборке «PostgreSQL для 1С» 16 этого модуля нет (сверено 19.10.2026 по перечню модулей приложения F и индексу пакетов); полнотекстовый поиск самой 1С работает на сервере 1С, а не в СУБД |
| BRIN | очень большие таблицы, где значения коррелируют с физическим порядком | не использует |
| bloom (расширение) | равенство по произвольному набору столбцов | не использует |

### 9.3. Разновидности индексов

| Разновидность | Синтаксис | Смысл |
|---|---|---|
| Уникальный | `CREATE UNIQUE INDEX …` | запрещает дубликаты; NULL-значения по умолчанию считаются различными (`NULLS NOT DISTINCT` — 15+) |
| Покрывающий | `CREATE INDEX … (a, b) INCLUDE (c, d)` | столбцы из `INCLUDE` лежат в индексе как «полезный груз»: искать по ним нельзя, но можно отдать значение без обращения к таблице (`Index Only Scan`) |
| Частичный | `CREATE INDEX … WHERE условие` | индексирует только часть строк; меньше и быстрее. Используется, только если условие запроса гарантированно попадает в условие индекса |
| По выражению | `CREATE INDEX … (lower(name))` | индекс по результату функции |
| С порядком | `(a DESC NULLS LAST)` | нужен для сортировок в смешанных направлениях |

«Кластерного индекса» в смысле MS SQL Server в PostgreSQL **нет**: таблица всегда хранится кучей, а индекс — отдельное отношение. Команда `CLUSTER таблица USING индекс` один раз физически переупорядочивает таблицу под `ACCESS EXCLUSIVE`; дальше порядок не поддерживается. Поэтому пометка «(Кластерный)» в описаниях индексов 1С для PostgreSQL означает обычный B-tree-индекс.

### 9.4. Как индексы создаёт 1С

- Индексы создаются платформой неявно — при создании и реструктуризации объектов конфигурации; состав определяется видом объекта и его свойствами [1С, «Индексы таблиц базы данных»; полный перечень по видам объектов — `kb/its-metod/razmeshchenie-dannyh-i-indeksy.md`].
- Основные правила: у объектных таблиц всегда есть индекс по ссылке; у регистров, подчинённых регистратору, — по `Регистратор + НомерСтроки`; у регистра сведений — по всем измерениям в порядке конфигуратора; свойство «Индексировать» у реквизита даёт индекс `Реквизит + Ссылка`, «Индексировать с доп. упорядочиванием» — с продолжением по коду, наименованию или дате.
- Если существует табличное пространство `v81c_index`, индексы размещаются в нём (раздел 4.5).
- Для временных таблиц индексы появляются из конструкции языка запросов `ИНДЕКСИРОВАТЬ ПО`; в SQL это `create index tmpind_N on pg_temp.ttN(…)` [1С, ИТС 6011].
- Штатные способы добавить индекс: свойство «Индексировать»; включение реквизита в критерий отбора; механизм дополнительных индексов (только при лицензии КОРП; в одном индексе не более 16 физических колонок; поля типа «Строка» неограниченной длины и «Двоичные данные» не индексируются) [1С].

```sql
-- все индексы таблицы с определениями и размерами
SELECT i.indexrelid::regclass AS index_name,
       pg_size_pretty(pg_relation_size(i.indexrelid)) AS size,
       i.indisunique AS uniq, i.indisclustered AS clustered, i.indisvalid AS valid,
       pg_get_indexdef(i.indexrelid) AS definition
FROM pg_index i
WHERE i.indrelid = '_document123'::regclass
ORDER BY 1;
```

В `psql` то же показывает `\d+ _document123`. Пример имени платформенного индекса из ИТС 6011 — `_document1337_s_hpk` (конспект — `kb/its-metod/pg-rasshireniya-1c-i-metodika-rassledovaniya.md`). ⚠ не подтверждено: общая схема именования индексов платформой в PostgreSQL и то, отмечает ли она «кластерные» индексы флагом `indisclustered`, — посмотрите приведённым запросом на своей базе.

### 9.5. Собственные индексы в базе 1С: можно ли и чем это грозит

Официальная позиция: сведения о таблицах и индексах даются «исключительно для понимания»; работать с данными способами, не предусмотренными штатными механизмами платформы, нельзя; изменять базу допустимо только средствами 1С:Предприятия [1С, «Размещение данных 1С:Предприятия 8»]. Индекс, созданный вручную, — это изменение структуры базы мимо платформы.

Риски [практика]:

| Риск | Пояснение |
|---|---|
| Индекс исчезнет без предупреждения | Реструктуризация (обновление конфигурации, изменение объекта метаданных), «Тестирование и исправление» с реструктуризацией, загрузка из `.dt` пересоздают таблицы. Ваш индекс при этом не воссоздаётся |
| Реструктуризация упадёт | Если имя вашего индекса совпадёт с именем, которое платформа захочет дать своему |
| Замедление записи и раздувание | Каждый индекс — дополнительная работа при `INSERT`/`UPDATE` и меньше HOT-обновлений (раздел 6.4) |
| Блокировка при создании | `CREATE INDEX` без `CONCURRENTLY` останавливает запись в таблицу на всё время построения |
| Нарушение логики платформы | Уникальный индекс, которого платформа не ожидает, даст ошибки записи. Никогда не создавайте `UNIQUE` |
| Отказ в поддержке | Проблемы базы с ручными изменениями структуры вендор и разработчики конфигурации разбирать не обязаны |

Когда это всё же делают: как **временную аварийную меру** для конкретного тяжёлого запроса, пока разработчик не добавит индекс штатно. Порядок:

1. Получить план проблемного запроса на копии базы и убедиться, что индекс помогает (`EXPLAIN (ANALYZE, BUFFERS)`).
2. Создать индекс без остановки работы и с именем, по которому сразу видно его происхождение:
   ```sql
   CREATE INDEX CONCURRENTLY adm_document123_fld456 ON _document123 (_fld456rref, _date_time);
   ```
3. Проверить, что индекс построился: при неудаче `CONCURRENTLY` оставляет «недействительный» индекс, который занимает место и замедляет запись.
   ```sql
   SELECT indexrelid::regclass FROM pg_index WHERE NOT indisvalid;
   DROP INDEX CONCURRENTLY adm_document123_fld456;      -- удалить недействительный и повторить
   ```
4. Сохранить команду создания в скрипт и проверять наличие индекса после каждого обновления конфигурации.
5. Через неделю убедиться, что индекс используется (`idx_scan` растёт); если нет — удалить.
6. Передать разработчику задачу сделать то же штатно.

Обратная задача — понять, нужен ли существующий индекс: его можно **временно скрыть от планировщика** в своём сеансе модулем `plantuner` (`SET plantuner.disable_index = 'имя_индекса';`) [PGPro]. Индекс при этом продолжает обновляться, остальные сеансы его видят.

### 9.6. Диагностика индексов

```sql
-- неиспользуемые индексы (с момента сброса статистики; уникальные не трогать)
SELECT s.relname AS table_name, s.indexrelname AS index_name, s.idx_scan,
       pg_size_pretty(pg_relation_size(s.indexrelid)) AS size
FROM pg_stat_user_indexes s
JOIN pg_index i ON i.indexrelid = s.indexrelid
WHERE s.idx_scan = 0 AND NOT i.indisunique
ORDER BY pg_relation_size(s.indexrelid) DESC
LIMIT 20;

-- ход построения индекса (12+)
SELECT pid, phase, blocks_done, blocks_total, tuples_done, tuples_total
FROM pg_stat_progress_create_index;

REINDEX INDEX CONCURRENTLY имя_индекса;     -- 12+: перестроить без блокировки записи
REINDEX TABLE CONCURRENTLY _document123;
```

«Неиспользуемые» индексы, созданные платформой, удалять нельзя: их состав задан метаданными, и при следующей реструктуризации они вернутся (или реструктуризация завершится ошибкой).

## 10. Временные таблицы

### 10.1. Как они устроены в PostgreSQL

Временная таблица в PostgreSQL — почти обычная таблица [PG]:

| Свойство | Как реализовано | Следствие |
|---|---|---|
| Определение | Каждый сеанс сам выполняет `CREATE TEMPORARY TABLE`; общего для всех сеансов определения, как в стандарте SQL, нет | Каждое создание — это вставка строк в `pg_class`, `pg_attribute`, `pg_type`, `pg_depend`, а для индексов — ещё и в `pg_index`. Удаление — их удаление. **Системный каталог раздувается** |
| Схема | Собственная схема сеанса `pg_temp_N`; обращение — через псевдоним `pg_temp` | В `pg_class` администратор видит временные таблицы всех сеансов (`relpersistence = 't'`), но прочитать чужие данные не может |
| Данные | Свой файл на диске `t<номер процесса>_<relfilenode>` (номер — внутренний номер серверного процесса, не PID; раздел 4.2) в каталоге базы или в `temp_tablespaces` | Создание и удаление файлов — нагрузка на файловую систему |
| Кеш | Локальные буферы процесса (`temp_buffers`), а не `shared_buffers` | Память расходуется в каждом сеансе отдельно (раздел 3.2) |
| WAL | Не журналируются | Быстро, но не передаются на реплику. На резервном сервере «только для чтения» создать временную таблицу нельзя |
| Autovacuum | «Не может обращаться к временным таблицам», значит, не чистит и не анализирует их | `ANALYZE` нужно выполнять явно после заполнения, иначе планировщик работает вслепую |
| Параллельность | Просмотр временных таблиц — только в ведущем процессе | Запросы к ним не распараллеливаются |
| Время жизни | До конца сеанса либо до конца транзакции: `ON COMMIT PRESERVE ROWS` (умолчание), `DELETE ROWS`, `DROP` | В долгоживущем соединении таблицы живут долго |

Временные таблицы не следует путать с временными файлами сортировок (раздел 4.6).

### 10.2. Почему это важно для 1С

Платформа 1С использует временные таблицы постоянно: менеджер временных таблиц в запросах, пакетные запросы, ограничения доступа, подстановка списков значений в условия. Цикл жизни в SQL по ИТС 6011 выглядит так: `create temporary table` → `create index tmpind_N` → `INSERT … SELECT` → `ANALYZE pg_temp.ttN` → запрос, который её использует [1С].

Что из этого следует:

- **Раздувание системного каталога.** Таблицы `pg_class`, `pg_attribute`, `pg_type`, `pg_depend`, `pg_index`, `pg_statistic` в базе 1С изменяются непрерывно. Им нужен агрессивный autovacuum, иначе замедляется планирование любого запроса.
- **Модуль `fasttrun`.** Функция `fasttruncate('имя')` быстро очищает временную таблицу; её назначение по документации — не давать системному каталогу `pg_class` неконтролируемо разрастаться (обычный `TRUNCATE` каждый раз назначает таблице новый файл и обновляет её строку в `pg_class`). Очистка не транзакционна: её нельзя откатить, результат сразу виден [PGPro]. Это позволяет платформе переиспользовать уже созданные таблицы соединения вместо постоянного пересоздания [практика].
- **Статистика.** Современные версии платформы сами выполняют `ANALYZE` временной таблицы после заполнения [1С, ИТС 6011]; модуль `online_analyze` с современными версиями 1С использовать не рекомендуется [PGPro] (причину документация Postgres Pro не называет; связь с `ANALYZE` от платформы — вывод автора). `plantuner.fix_empty_table = on` заставляет планировщик считать только что созданную таблицу пустой, а не «неизвестного размера».
- **`max_locks_per_transaction`.** При закрытии соединения все его временные таблицы удаляются одной транзакцией (раздел 7.6).
- **Реплика.** 1С не может выполнять свои запросы на физической реплике: они создают временные таблицы. Для механизма копий баз данных нужен отдельный экземпляр, доступный на запись [1С; конспект — `kb/its-metod/pg-otkazoustojchivyj-klaster-i-kopii-bd.md`].
- **Диск.** Вынос `temp_tablespaces` на быстрый носитель; в сборке с патчем 1С есть параметр `enable_temp_rd_buffers` (с 17.5-11.1C и 16.9-34.1C, по умолчанию `off`): файл временной таблицы не создаётся, пока данные не превысят 32 КБ [1С; конспект — `kb/its-metod/pg-nastrojki-postgresql-dlya-1c.md`].

### 10.3. Диагностика

```sql
-- сколько временных таблиц сейчас существует и в скольких сеансах
SELECT count(*) AS temp_tables, count(DISTINCT c.relnamespace) AS sessions
FROM pg_class c
WHERE c.relpersistence = 't' AND c.relkind = 'r';

-- размер и раздутость ключевых таблиц системного каталога
SELECT c.relname,
       pg_size_pretty(pg_total_relation_size(c.oid)) AS total,
       s.n_live_tup, s.n_dead_tup, s.last_autovacuum
FROM pg_class c
JOIN pg_stat_sys_tables s ON s.relid = c.oid
WHERE c.relname IN ('pg_class', 'pg_attribute', 'pg_type', 'pg_depend', 'pg_index', 'pg_statistic')
ORDER BY pg_total_relation_size(c.oid) DESC;

-- «возраст» временных таблиц: autovacuum не может их заморозить
SELECT c.oid::regclass AS temp_table, age(c.relfrozenxid) AS xid_age
FROM pg_class c
WHERE c.relpersistence = 't' AND c.relkind = 'r'
ORDER BY 2 DESC
LIMIT 10;
```

Ориентиры [практика]: `pg_attribute` размером в гигабайты при небольшой базе — признак запущенного раздувания каталога; лечится `VACUUM` системных таблиц, в тяжёлых случаях — `VACUUM FULL` каталога в технологическое окно (см. `05-obsluzhivanie-vacuum-analyze-reindex.md`). Временная таблица, живущая в соединении очень долго, удерживает `datfrozenxid` базы, потому что заморозить её может только сам сеанс-владелец (уточнено 11.10.2026: документация PostgreSQL 18 (глава «Routine Vacuuming», раздел об автоочистке) прямо говорит, что автоочистка не имеет доступа к временным таблицам и обслуживать их нужно командами в самом сеансе; вывод про `datfrozenxid` — по памяти об устройстве autovacuum, в документации прямо не описано). Если запрос показывает возраст в сотни миллионов — перезапустите рабочие процессы 1С, чтобы соединения пересоздались.

После аварийного завершения серверного процесса его временные таблицы остаются «осиротевшими»; их удаляет autovacuum или следующий сеанс, которому достанется та же временная схема [практика].

## 11. Кодировки, локали и типы mchar/mvarchar

### 11.1. Кодировка

- Кодировка задаётся **для каждой базы** при создании и потом не меняется. Для 1С — `UTF8`: документация платформы требует указывать `UTF-8` при инициализации кластера [1С, «Клиент-серверный вариант», п. 3.2.5.1].
- Кодировка клиента — параметр сеанса `client_encoding`; сервер перекодирует на лету. Платформа ставит `client_encoding = 'utf8'` (раздел 8.9).
- В PostgreSQL 19 удалена кодировка `MULE_INTERNAL` [PG] — 1С это не касается.

### 11.2. Локаль и поставщики правил сортировки

Локаль определяет порядок сортировки строк (`LC_COLLATE`) и классификацию символов — что считать буквой, как менять регистр (`LC_CTYPE`). Эти две категории **фиксируются при создании базы**, потому что от них зависит порядок в индексах; остальные (`lc_messages`, `lc_monetary`, `lc_numeric`, `lc_time`) — обычные параметры, их можно менять [PG].

Поставщики (locale provider):

| Поставщик | Код в `datlocprovider` | Что это | С какой версии выбирается для базы |
|---|---|---|---|
| `libc` | `c` | Библиотека C операционной системы (glibc). Поведение зависит от версии ОС | всегда; умолчание `initdb` |
| `icu` | `i` | Библиотека ICU. Одинаковое поведение на разных платформах, но может измениться с версией ICU | 15 |
| `builtin` | `b` | Встроенная реализация: локали `C`, `C.UTF-8` (17+), `PG_UNICODE_FAST` (18+). Сортировка по кодам символов, не зависит ни от ОС, ни от ICU | 17 |

Сортировка по кодам символов (`C`, `builtin`) самая быстрая и стабильная, но русские строки при `ORDER BY` по обычным типам `text`/`varchar` пойдут не по алфавиту (например, «Ё» окажется вне ряда). Для базы 1С используйте локаль, совпадающую с настройками информационной базы — обычно `ru_RU.UTF-8` (для международных конфигураций WE — `en_US.UTF-8`); для кластера, созданного стандартной (не 1С) версией PostgreSQL, документация 1С допускает работу, только если национальные установки кластера и создаваемой информационной базы совпадают [1С, «Клиент-серверный вариант», п. 3.2.5.1].

```sql
-- 15+ (в 14-й нет столбцов datlocprovider и datcollversion — смотрите \l)
SELECT datname, pg_encoding_to_char(encoding) AS encoding, datlocprovider,
       datcollate, datctype, datcollversion
FROM pg_database;

SHOW server_encoding;  SHOW client_encoding;  SHOW lc_messages;
-- параметры только для чтения lc_collate и lc_ctype удалены в 16-й версии [PG] — смотрите pg_database
```

```bash
locale -a | grep -i -E 'ru_RU|en_US'                        # какие локали есть в ОС
sudo locale-gen ru_RU.UTF-8 en_US.UTF-8                     # создать ДО initdb / создания базы
```

Обычно базу создаёт сама платформа (флажок «Создать базу данных в случае её отсутствия»). Если базу создают вручную:

```sql
CREATE DATABASE base1c
  OWNER usr1cv8
  TEMPLATE template0                 -- обязательно, если локаль отличается от template1
  ENCODING 'UTF8'
  LC_COLLATE 'ru_RU.UTF-8'
  LC_CTYPE 'ru_RU.UTF-8';
```

### 11.3. Версии правил сортировки

Сервер запоминает версию правил сортировки, с которой была создана база (`pg_database.datcollversion`, 15+) или объект `COLLATION` (`pg_collation.collversion`). Если библиотека обновилась, порядок строк мог измениться, а индексы построены по старому порядку. Последствия — индекс «не находит» существующие строки, нарушается уникальность. Сервер предупреждает [PG]:

```text
WARNING:  database "base1c" has a collation version mismatch
DETAIL:  The database was created using collation version 2.35, but the operating system provides version 2.39.
HINT:  Rebuild all objects in this database that use the default collation and run ALTER DATABASE base1c REFRESH COLLATION VERSION, or build PostgreSQL with the right library version.
```

Для `libc` в роли версии выступает версия glibc (Ubuntu 22.04 — 2.35, Ubuntu 24.04 — 2.39). Когда это случается:

- обновление выпуска Ubuntu на месте (`do-release-upgrade`) под существующим кластером;
- перенос каталога данных, восстановление `pg_basebackup` или подключение физической реплики на машине с другим выпуском ОС;
- `pg_upgrade` на сборку, слинкованную с другой версией ICU.

Логическая копия (`pg_dump` и восстановление) этой проблеме не подвержена: индексы строятся заново.

Лечение:

```sql
-- какие правила сортировки устарели и что от них зависит
SELECT pg_describe_object(refclassid, refobjid, refobjsubid) AS "Collation",
       pg_describe_object(classid, objid, objsubid)          AS "Object"
FROM pg_depend d
JOIN pg_collation c ON refclassid = 'pg_collation'::regclass AND refobjid = c.oid
WHERE c.collversion <> pg_collation_actual_version(c.oid)
ORDER BY 1, 2;

REINDEX DATABASE base1c;                               -- в технологическое окно; выполнять, подключившись к этой базе
ALTER DATABASE base1c REFRESH COLLATION VERSION;       -- 15+: зафиксировать новую версию, предупреждение исчезнет
```

`REFRESH COLLATION VERSION` только обновляет запись в каталоге и **не проверяет**, что индексы действительно перестроены [PG]. Сначала `REINDEX`, потом `REFRESH`.

### 11.4. Типы mchar и mvarchar

Модуль `mchar` входит в сборки для 1С и «предоставляет дополнительные типы данных для совместимости с Microsoft SQL Server» [PGPro]:

| Свойство | `mchar` / `mvarchar` | Обычные `char` / `varchar` |
|---|---|---|
| Аналог в MS SQL | `char` / `varchar` | — |
| Сравнение | **без учёта регистра** | с учётом регистра |
| Хвостовые пробелы | обрабатываются по правилам MS SQL | по правилам PostgreSQL |
| Внутреннее хранение | всегда UTF-16, независимо от кодировки базы | в кодировке базы |
| Сравнение и смена регистра | через библиотеку **ICU** — поведение одинаково в разных ОС | по локали базы |
| Операторы без учёта регистра | `<`, `<=`, `=`, `>=`, `>` | — |
| Операторы с учётом регистра | `&<`, `&<=`, `&=`, `&>=`, `&>` | — |
| Индексы | B-tree и hash; поддержка `LIKE`, `SIMILAR TO`, `~` | — |

Между `mchar` и `mvarchar` действует неявное приведение. Авторы модуля — Олег Бартунов и Фёдор Сигаев.

Что это значит для администратора:

- В «ванильном» PostgreSQL этих типов нет, поэтому базу 1С нельзя восстановить на сервере без модуля: `ERROR: type "mvarchar" does not exist`.
- При `pg_dump`, `pg_restore` и `pg_upgrade` возможны ошибки разрешения операторов с нестандартными типами; порядок действий описан в документации Postgres Pro (раздел об обновлении) [PGPro].
- Сравнение строк 1С идёт через ICU, а не через локаль базы. Значит, порядок сортировки строковых полей 1С зависит от версии ICU, с которой собрана сборка. Уточнено 19.10.2026 по индексу пакетов «PostgreSQL для 1С» 16.14: сборка использует системную ICU (`postgrespro-1c-16-server` зависит от `libicu70` в Ubuntu 22.04 и от `libicu74` в 24.04), то есть при смене выпуска Ubuntu версия ICU меняется. ⚠ не подтверждено: нужно ли перестраивать индексы по `mchar`/`mvarchar` после смены версии ICU при обновлении ОС. Осторожный вариант — после переноса кластера на другой выпуск ОС выполнить `REINDEX DATABASE` [практика].
- Запрос в `psql` с условием по строковому полю 1С сравнивает без учёта регистра: `WHERE _description = 'иванов'` найдёт «Иванов».

Как типы 1С выглядят в PostgreSQL (проверьте запросом на своей базе) [практика]:

| Тип 1С | Тип столбца PostgreSQL |
|---|---|
| Строка фиксированной длины | `mchar(n)` |
| Строка переменной длины | `mvarchar(n)` |
| Строка неограниченной длины | `mvarchar` |
| Число | `numeric(p,s)` |
| Булево | `boolean` |
| Дата | `timestamp without time zone` |
| Ссылка, уникальный идентификатор | `bytea` (16 байт) |
| ХранилищеЗначения, двоичные данные | `bytea` |

```sql
SELECT attname, format_type(atttypid, atttypmod) AS type
FROM pg_attribute
WHERE attrelid = '_reference12'::regclass AND attnum > 0 AND NOT attisdropped
ORDER BY attnum;

SELECT extname, extversion FROM pg_extension;     -- в базе 1С должны быть mchar, fulleq, fasttrun
```

## 12. Безопасность

### 12.1. Роли и привилегии

В PostgreSQL нет отдельных «пользователей» и «групп» — есть **роли**. Роль с атрибутом `LOGIN` может подключаться; роль может быть членом другой роли. Роли общие для всего кластера, а не для базы.

| Атрибут | Смысл |
|---|---|
| `LOGIN` | право подключаться |
| `SUPERUSER` | обходит все проверки прав (кроме права на вход) |
| `CREATEDB` | создавать базы |
| `CREATEROLE` | создавать и изменять роли (с версии 16 — только те, на которые есть `ADMIN OPTION`) |
| `REPLICATION` | подключаться для репликации, делать `pg_basebackup` |
| `BYPASSRLS` | обходить политики защиты строк |
| `CONNECTION LIMIT n` | предел одновременных соединений роли |
| `VALID UNTIL 'дата'` | срок действия пароля |

```sql
CREATE ROLE usr1cv8 LOGIN PASSWORD 'СложныйПароль' CREATEDB;     -- пароль лучше задавать через \password
ALTER ROLE usr1cv8 CONNECTION LIMIT 480;
ALTER ROLE usr1cv8 SET statement_timeout = 0;                     -- параметр по умолчанию для сеансов роли
GRANT pg_monitor TO zabbix;                                       -- членство в роли
REVOKE CONNECT ON DATABASE base1c FROM PUBLIC;                    -- закрыть базу от всех, кроме явно допущенных
GRANT  CONNECT ON DATABASE base1c TO usr1cv8;
```

В `psql`: `\du+` — роли, `\l+` — базы и права на них, `\dn+` — схемы, `\dp имя` — права на таблицу, `\ddp` — права по умолчанию.

Встроенные роли, полезные администратору [PG]:

| Роль | С версии | Что даёт |
|---|---|---|
| `pg_monitor` | 10 | чтение всех представлений мониторинга и настроек (включает `pg_read_all_settings`, `pg_read_all_stats`, `pg_stat_scan_tables`) |
| `pg_signal_backend` | 9.6 | `pg_cancel_backend()` и `pg_terminate_backend()` для чужих сеансов (кроме суперпользовательских) |
| `pg_read_all_data` / `pg_write_all_data` | 14 | чтение / запись всех таблиц, представлений и последовательностей |
| `pg_database_owner` | 14 | неявно содержит владельца текущей базы; ей принадлежит схема `public` (15+) |
| `pg_checkpoint` | 15 | право выполнять `CHECKPOINT` |
| `pg_use_reserved_connections` | 16 | право занимать слоты `reserved_connections` |
| `pg_maintain` | 17 | `VACUUM`, `ANALYZE`, `REINDEX`, `CLUSTER`, `REFRESH MATERIALIZED VIEW`, `LOCK TABLE` для любых таблиц |
| `pg_signal_autovacuum_worker` | 18 | прерывать процессы autovacuum |

Привилегии выдаются командами `GRANT`/`REVOKE` на конкретные объекты. У каждого объекта есть **владелец** — роль, которая его создала; владелец может всё, включая удаление, и это право нельзя отозвать. `PUBLIC` — псевдороль «все».

Как это соотносится с 1С:

- Сервер 1С подключается под **одной** ролью, указанной в параметрах информационной базы. Пользователи 1С в PostgreSQL не существуют; разграничение их прав — целиком на стороне платформы.
- Эта роль становится владельцем базы и всех таблиц (если базу создаёт платформа).
- На практике роли 1С дают `SUPERUSER`: модули `mchar`, `fulleq`, `fasttrun` написаны на C, а создание таких расширений требует прав суперпользователя [практика]. **Уточнено 10.10.2026** (полный текст документации 8.3.27, глава 5, разд. 5.2.1.3.3): пользователь СУБД должен обладать `SUPERUSER` только в момент создания информационной базы; затем привилегию можно отозвать (`alter user dbuser with nosuperuser;`). Ранее было не подтверждено: официальные требования 1С к привилегиям роли (см. `01-sborki-postgresql-dlya-1c-ustanovka.md`, раздел о пользователе).
- Раз роль 1С всемогуща, защита строится вокруг неё: сеть, `pg_hba.conf`, пароль, права на файлы.

Отдельные роли стоит завести для администратора (вход при исчерпании соединений), мониторинга (`pg_monitor`) и резервного копирования (`REPLICATION`).

### 12.2. Схема public и изменение в PostgreSQL 15

- Путь поиска по умолчанию: `search_path = "$user", public`. Объекты без указания схемы создаются в первой существующей схеме пути — как правило, в `public` [PG].
- **До 14-й версии включительно** право `CREATE` в схеме `public` было у всех (`PUBLIC`).
- **Начиная с 15-й** это право убрано; владелец схемы — `pg_database_owner`, то есть владелец базы. Изменение действует в новых кластерах и в новых базах существующих кластеров. При `pg_upgrade` и восстановлении из дампа прежние права **сохраняются** [PG].

Что это значит для 1С: если базу создаёт платформа под своей ролью — роль является владельцем базы и всё работает. Проблема возникает, когда базу заранее создал `postgres`, а 1С подключается под другой ролью без прав суперпользователя:

```text
ERROR:  permission denied for schema public
```

```sql
ALTER DATABASE base1c OWNER TO usr1cv8;                 -- правильное решение: роль 1С — владелец базы
-- либо точечно:
GRANT ALL ON SCHEMA public TO usr1cv8;

-- для баз, пришедших с версий до 15 (рекомендация документации)
REVOKE CREATE ON SCHEMA public FROM PUBLIC;

SELECT nspname, nspowner::regrole AS owner, nspacl FROM pg_namespace WHERE nspname = 'public';
```

### 12.3. pg_hba.conf

Файл правил «кто, откуда, к какой базе и каким способом может подключаться». Расположение: `SHOW hba_file;`.

```text
local      БАЗА  РОЛЬ                МЕТОД  [параметры]     # Unix-сокет
host       БАЗА  РОЛЬ  АДРЕС         МЕТОД  [параметры]     # TCP, с SSL или без
hostssl    БАЗА  РОЛЬ  АДРЕС         МЕТОД  [параметры]     # TCP только с SSL
hostnossl  БАЗА  РОЛЬ  АДРЕС         МЕТОД  [параметры]     # TCP только без SSL
```

- **Срабатывает первая строка,** подходящая по типу соединения, адресу, базе и роли. Если проверка по ней не прошла, следующие строки **не рассматриваются**. Если не подошла ни одна — отказ [PG].
- База: имя, `all`, `sameuser`, `samerole`, `replication` (только физическая репликация), `/регулярное_выражение` (16+), `@файл`.
- Роль: имя, `all`, `+группа` (члены роли), `/регулярное_выражение` (16+), `@файл`.
- Адрес: CIDR (`192.168.1.10/32`, `10.0.0.0/8`, `::1/128`), `samehost`, `samenet`, `all`, имя узла.
- С версии 16 поддерживаются `include`, `include_if_exists`, `include_dir` [PG].

Методы [PG]:

| Метод | Смысл | Применение |
|---|---|---|
| `scram-sha-256` | пароль по протоколу SCRAM | основной для 1С |
| `md5` | SCRAM или MD5 — что сохранено у роли; **устарел** (18), будет удалён | только для старых клиентов |
| `peer` | имя пользователя ОС = имя роли; только для `local` | вход `sudo -u postgres psql` |
| `trust` | без проверки | не использовать, кроме аварийного восстановления пароля |
| `reject` | отказ | исключения перед более широким правилом |
| `password` | пароль открытым текстом | не использовать |
| `cert` | клиентский сертификат SSL | редко |
| `gss`, `sspi`, `ldap`, `pam`, `ident`, `bsd` | внешние системы | к 1С не относятся |
| `radius` | **удалён в PostgreSQL 19** | — |
| `oauth` | OAuth 2.0 (18+) | к 1С не относится |

Минимальный файл для сервера 1С на адресе `192.168.1.10` (если 1С и PostgreSQL на одной ВМ — адрес `127.0.0.1/32`):

```text
# TYPE  DATABASE  USER      ADDRESS            METHOD
local   all       postgres                     peer
host    all       usr1cv8   192.168.1.10/32    scram-sha-256
host    all       usr1cv8   127.0.0.1/32       scram-sha-256
```

Сервер 1С подключается по TCP, а не через сокет, поэтому строка `host` нужна даже для `127.0.0.1`. Кроме `pg_hba.conf` сервер должен слушать нужный интерфейс (`listen_addresses`, требует перезапуска), а порт 5432 должен быть открыт в межсетевом экране только для сервера 1С.

```bash
sudoedit /etc/postgresql/17/main/pg_hba.conf
sudo -u postgres psql -c "SELECT pg_reload_conf()"          # перечитать без перезапуска
# проверить, что файл разобран без ошибок и что в нём действует
sudo -u postgres psql -c "SELECT line_number, type, database, user_name, address, auth_method, error FROM pg_hba_file_rules"
```

Типовые сообщения:

| Сообщение | Причина |
|---|---|
| `FATAL: no pg_hba.conf entry for host "192.168.1.10", user "usr1cv8", database "base1c", no encryption` | нет подходящей строки (или есть `hostssl`, а соединение без SSL) |
| `FATAL: password authentication failed for user "usr1cv8"` | неверный пароль, пароль не задан, либо метод `scram-sha-256`, а пароль сохранён как MD5 |
| `FATAL: Peer authentication failed for user "postgres"` | подключение через сокет не от пользователя ОС `postgres` |
| `connection refused` / нет ответа | сервер не слушает адрес (`listen_addresses`) или порт закрыт экраном — до `pg_hba.conf` дело не дошло |

### 12.4. Пароли

- `password_encryption` определяет, в каком виде пароль **сохраняется** при `CREATE/ALTER ROLE … PASSWORD` и `\password`. Умолчание — `scram-sha-256` начиная с 14-й версии [PG].
- В PostgreSQL 18 пароли MD5 объявлены устаревшими: при установке такого пароля выдаётся предупреждение (отключается `md5_password_warnings = off`); в 19-й предупреждение выдаётся и после успешного входа с паролем MD5 [PG].
- Задавайте пароль командой `\password роль` в `psql`: она хеширует пароль на клиенте, и он не попадает открытым текстом ни в журнал сервера, ни в историю команд.

```sql
-- в каком формате сохранены пароли (суперпользователь)
SELECT rolname,
       CASE WHEN rolpassword LIKE 'SCRAM-SHA-256$%' THEN 'scram-sha-256'
            WHEN rolpassword LIKE 'md5%'            THEN 'md5'
            WHEN rolpassword IS NULL                THEN '(нет пароля)'
            ELSE 'другое' END AS format,
       rolvaliduntil
FROM pg_authid
WHERE rolcanlogin;
```

Для скриптов пароль хранят в файле `~/.pgpass` (права `0600`, формат `узел:порт:база:роль:пароль`), а не в командной строке.

### 12.5. SSL/TLS

Сервер [PG]:

| Параметр | Умолчание | Смысл |
|---|---|---|
| `ssl` | `off` | включить TLS |
| `ssl_cert_file` | `server.crt` (относительно каталога данных) | сертификат сервера |
| `ssl_key_file` | `server.key` | закрытый ключ. Права: `0600`, если владелец — `postgres`; `0640`, если владелец — `root` |
| `ssl_ca_file` | пусто | корневые сертификаты для проверки клиентских сертификатов |
| `ssl_min_protocol_version` | `TLSv1.2` | минимальная версия протокола |
| `ssl_ciphers` | `HIGH:MEDIUM:+3DES:!aNULL` | шифры TLS 1.2 и ниже |
| `ssl_tls13_ciphers` (18+) | пусто | наборы шифров TLS 1.3 |
| `ssl_groups` (18+; раньше `ssl_ecdh_curve`) | `X25519:prime256v1` | группы обмена ключами |

Параметры SSL перечитываются по `pg_reload_conf()`, перезапуск не нужен.

В пакетах Debian и Ubuntu кластер обычно создаётся уже с `ssl = on` и самоподписанным сертификатом из пакета `ssl-cert` (`/etc/ssl/certs/ssl-cert-snakeoil.pem`, ключ `/etc/ssl/private/ssl-cert-snakeoil.key`) [практика; проверьте `SHOW ssl; SHOW ssl_cert_file;`].

```bash
# собственный самоподписанный сертификат (пример из документации PostgreSQL, срок увеличен)
sudo openssl req -new -x509 -days 3650 -nodes -text \
     -out /etc/postgresql/17/main/server.crt -keyout /etc/postgresql/17/main/server.key \
     -subj "/CN=pg1c.example.local"
sudo chown postgres:postgres /etc/postgresql/17/main/server.{crt,key}
sudo chmod 600 /etc/postgresql/17/main/server.key
```

```ini
# /etc/postgresql/17/main/conf.d/80-ssl.conf
ssl = on
ssl_cert_file = '/etc/postgresql/17/main/server.crt'
ssl_key_file  = '/etc/postgresql/17/main/server.key'
ssl_min_protocol_version = 'TLSv1.2'
```

```sql
-- какие соединения шифруются
SELECT a.pid, a.usename, a.client_addr, s.ssl, s.version, s.cipher
FROM pg_stat_activity a
JOIN pg_stat_ssl s USING (pid)
WHERE a.backend_type = 'client backend';
```

Применимость к 1С: платформа сама соединение с СУБД не шифрует — «защита обеспечивается средствами СУБД» [1С; см. `kb/1c/08-konfiguracionnye-fajly-kerberos-bezopasnost.md`]. Клиентская библиотека по умолчанию работает в режиме `sslmode=prefer`: шифрует, если сервер это поддерживает, но сертификат сервера не проверяет. Поэтому достаточно включить SSL на сервере и заменить `host` на `hostssl` в `pg_hba.conf`. Если 1С и PostgreSQL на одной ВМ, шифрование не нужно и только тратит процессор — рекомендация `ssl = off` [1С].

### 12.6. Аудит

| Средство | Что даёт | Как включить |
|---|---|---|
| `log_connections`, `log_disconnections` | кто, откуда и когда подключался | `log_connections = on` (в 18-й принимает и список стадий) |
| `log_statement = 'ddl'` | все команды изменения структуры | параметр в `postgresql.conf` |
| `log_line_prefix` | метка времени, PID, роль, база, адрес в каждой строке журнала | например `'%m [%p] %q%u@%d %h '` |
| `pgaudit` | детальный аудит по классам команд и по объектам | расширение, см. ниже |

`pgaudit` (версии: 1.6.x — для PostgreSQL 14, 1.7.x — 15, 16.x — 16, 17.x — 17, 18.x — 18):

```bash
sudo apt install postgresql-17-pgaudit      # пакет Ubuntu/PGDG; в архиве Ubuntu пакета `postgresql-17-pgaudit` нет (на 10.10.2026 есть только `postgresql-18-pgaudit` в 26.04) — для 17-й версии он берётся из PGDG; совместимость со сборкой 1С и наличие в Postgres Pro не проверялись
```

```ini
shared_preload_libraries = 'pgaudit'        # добавить к уже имеющимся библиотекам; нужен перезапуск
pgaudit.log = 'ddl, role'                   # классы: READ, WRITE, FUNCTION, ROLE, DDL, MISC, MISC_SET, ALL
pgaudit.log_catalog = off                   # не шуметь запросами к системному каталогу
```

```sql
CREATE EXTENSION pgaudit;
-- аудит только для «людских» ролей, а не для 1С:
ALTER ROLE admin_ivanov SET pgaudit.log = 'all';
```

Записи идут в обычный журнал сервера с префиксом `AUDIT:`. Ограничения: суперпользователя надёжно аудировать нельзя (он может отключить аудит); записи не транзакционны и могут теряться при сбое.

Применимость к 1С: все действия пользователей 1С выполняются под одной ролью, поэтому аудит СУБД не скажет, **кто из людей** что сделал, — это задача журнала регистрации 1С. Класс `READ, WRITE` для роли 1С зальёт журнал за минуты. Разумное применение `pgaudit` — классы `DDL` и `ROLE` и полный аудит прямых подключений администраторов.

### 12.7. Защита на уровне строк (RLS)

В PostgreSQL есть политики защиты строк: `ALTER TABLE … ENABLE ROW LEVEL SECURITY` и `CREATE POLICY`. Владелец таблицы, суперпользователь и роли с `BYPASSRLS` политики обходят.

К 1С это **не относится**: ограничения доступа на уровне записей 1С реализованы самой платформой — она дописывает условия в текст запроса; политик PostgreSQL в базе 1С нет. Параметр `row_security = off` рекомендован для 1С [PGPro]: при нём запрос, результат которого был бы отфильтрован политикой, завершается ошибкой, а не молча теряет строки.

### 12.8. Сводка: что применимо при работе с 1С

| Механизм | Применимость | Комментарий |
|---|---|---|
| Отдельная роль для 1С | да | одна на сервер 1С или на базу; обычно суперпользователь [практика] |
| Роли для администратора, мониторинга, копирования | да | `pg_monitor`, `REPLICATION`, отдельный вход для людей |
| Разграничение прав пользователей 1С средствами СУБД | нет | пользователи 1С в СУБД не существуют |
| `pg_hba.conf` + `scram-sha-256` | да, обязательно | доступ только с адреса сервера 1С |
| Межсетевой экран, `listen_addresses` | да, обязательно | порт 5432 не должен быть доступен из пользовательской сети |
| SSL (`hostssl`) | по ситуации | нужен, если трафик идёт по недоверенной сети; на одной ВМ — нет |
| Клиентские сертификаты (`cert`) | ⚠ не проверялось | зависит от клиентской библиотеки платформы |
| `pgaudit` | частично | DDL, роли, действия администраторов; не действия пользователей 1С |
| RLS PostgreSQL | нет | у 1С свой механизм |
| Контрольные суммы данных | да | обнаружение порчи данных на диске |
| Права на каталог данных `0700` | да | включая резервные копии: дамп базы = все данные предприятия |
| Прямое изменение данных в таблицах 1С | запрещено | только средствами платформы [1С] |

Работа в `psql` подробно — в `03-administrirovanie-psql-i-utility.md`; большая библиотека готовых запросов — в `06-monitoring-i-diagnostika-zaprosov.md`, раздел 11.

### 13.2. SELECT: отбор, сортировка, выражения

```sql
-- параметры, изменённые относительно умолчаний
SELECT name, setting, unit, source, pending_restart
FROM pg_settings
WHERE source NOT IN ('default', 'override')
ORDER BY name;

-- поиск по шаблону; ILIKE — без учёта регистра, ~ — регулярное выражение
SELECT name, setting FROM pg_settings WHERE name LIKE '%wal%' ORDER BY 1;
SELECT relname FROM pg_class WHERE relkind = 'r' AND relname ~ '^_(document|reference)[0-9]+$' LIMIT 20;

-- CASE, coalesce, nullif, склейка строк
SELECT pid,
       coalesce(usename, '(служебный)')                              AS role,
       CASE WHEN state = 'active' THEN 'работает'
            WHEN state LIKE 'idle in transaction%' THEN 'В ТРАНЗАКЦИИ'
            ELSE coalesce(state, '-') END                            AS what,
       client_addr::text || ':' || client_port                       AS client,
       round(100.0 * 5 / nullif(0, 0), 1)                            AS no_div_by_zero   -- nullif спасает от деления на ноль
FROM pg_stat_activity
ORDER BY backend_start
LIMIT 20;
```

### 13.3. Агрегаты и группировка

```sql
-- соединения по базам и состояниям; FILTER — условный агрегат
SELECT datname,
       count(*)                                            AS total,
       count(*) FILTER (WHERE state = 'active')            AS active,
       count(*) FILTER (WHERE state LIKE 'idle in trans%') AS in_xact,
       max(now() - xact_start)                             AS oldest_xact
FROM pg_stat_activity
WHERE backend_type = 'client backend'
GROUP BY datname
HAVING count(*) > 0
ORDER BY total DESC;

-- структура базы 1С по видам таблиц: префикс имени = вид объекта (_reference, _document, _accumrg, _inforg …)
SELECT regexp_replace(relname, '[0-9].*$', '')              AS kind,
       count(*)                                             AS tables,
       pg_size_pretty(sum(pg_total_relation_size(oid)))     AS size
FROM pg_class
WHERE relkind = 'r' AND relnamespace = 'public'::regnamespace
GROUP BY 1
ORDER BY sum(pg_total_relation_size(oid)) DESC
LIMIT 15;

-- string_agg: собрать список в строку
SELECT auth_method, string_agg(DISTINCT type, ', ') AS types, count(*)
FROM pg_hba_file_rules
GROUP BY auth_method;
```

### 13.4. JOIN

```sql
-- INNER JOIN: таблицы и их схемы
SELECT n.nspname, c.relname, c.reltuples::bigint AS rows_est
FROM pg_class c
JOIN pg_namespace n ON n.oid = c.relnamespace
WHERE c.relkind = 'r' AND n.nspname NOT IN ('pg_catalog', 'information_schema')
ORDER BY c.reltuples DESC
LIMIT 10;

-- LEFT JOIN: оставить строки слева, даже если справа пары нет (таблицы без единого индекса)
SELECT c.relname
FROM pg_class c
LEFT JOIN pg_index i ON i.indrelid = c.oid
WHERE c.relkind = 'r' AND c.relnamespace = 'public'::regnamespace AND i.indexrelid IS NULL;

-- соединение статистики сеансов и блокировок: кто какие табличные блокировки держит
SELECT a.pid, a.usename, l.mode, l.granted, l.relation::regclass AS rel, now() - a.xact_start AS xact_age
FROM pg_locks l
JOIN pg_stat_activity a USING (pid)
WHERE l.locktype = 'relation' AND l.mode IN ('AccessExclusiveLock', 'ExclusiveLock', 'ShareLock')
ORDER BY a.xact_start;

-- LATERAL: для каждой строки слева выполнить подзапрос (развернуть массив блокирующих процессов)
SELECT w.pid AS waiting, b.pid AS blocker, b.state, left(b.query, 60) AS blocker_query
FROM pg_stat_activity w
CROSS JOIN LATERAL unnest(pg_blocking_pids(w.pid)) AS x(blocker_pid)
JOIN pg_stat_activity b ON b.pid = x.blocker_pid;
```

### 13.5. Общие табличные выражения (CTE)

`WITH имя AS (…)` — именованный подзапрос. С 12-й версии простое CTE, использованное один раз, встраивается в основной запрос; `AS MATERIALIZED` заставляет вычислить его отдельно, `AS NOT MATERIALIZED` — встроить [PG].

```sql
-- обычное CTE: посчитать один раз, использовать дважды
WITH sizes AS (
    SELECT c.oid, c.relname, pg_total_relation_size(c.oid) AS total
    FROM pg_class c
    WHERE c.relkind = 'r' AND c.relnamespace = 'public'::regnamespace
)
SELECT relname, pg_size_pretty(total) AS size,
       round(100.0 * total / (SELECT sum(total) FROM sizes), 1) AS pct
FROM sizes
ORDER BY total DESC
LIMIT 10;

-- рекурсивное CTE: дерево ожиданий блокировок (корни — те, кто блокирует других, но сам не ждёт)
WITH RECURSIVE chain AS (
    SELECT a.pid, 0 AS depth, ARRAY[a.pid] AS path
    FROM pg_stat_activity a
    WHERE cardinality(pg_blocking_pids(a.pid)) = 0
      AND EXISTS (SELECT 1 FROM pg_stat_activity w WHERE a.pid = ANY (pg_blocking_pids(w.pid)))
  UNION ALL
    SELECT w.pid, c.depth + 1, c.path || w.pid
    FROM pg_stat_activity w
    JOIN chain c ON c.pid = ANY (pg_blocking_pids(w.pid))
    WHERE w.pid <> ALL (c.path)
)
SELECT repeat('    ', c.depth) || c.pid::text AS tree, a.state, now() - a.xact_start AS xact_age, left(a.query, 60) AS query
FROM chain c
JOIN pg_stat_activity a USING (pid)
ORDER BY c.path;
```

### 13.6. Оконные функции

Оконная функция считает значение по набору строк, **не сворачивая** их, в отличие от `GROUP BY`. Окно задаётся в `OVER (…)`.

```sql
-- доля и накопленная доля: какие таблицы составляют 80 % базы
SELECT row_number() OVER (ORDER BY sz DESC)                                        AS n,
       relname,
       pg_size_pretty(sz)                                                          AS size,
       round(100.0 * sz / sum(sz) OVER (), 1)                                      AS pct,
       round(100.0 * sum(sz) OVER (ORDER BY sz DESC) / sum(sz) OVER (), 1)         AS cum_pct
FROM (SELECT relname, pg_total_relation_size(oid) AS sz
      FROM pg_class
      WHERE relkind = 'r' AND relnamespace = 'public'::regnamespace) t
ORDER BY sz DESC
LIMIT 20;

-- PARTITION BY: ранжирование внутри группы — три самых больших индекса каждой таблицы
SELECT * FROM (
    SELECT indrelid::regclass AS tbl, indexrelid::regclass AS idx,
           pg_relation_size(indexrelid) AS sz,
           rank() OVER (PARTITION BY indrelid ORDER BY pg_relation_size(indexrelid) DESC) AS r
    FROM pg_index
) q
WHERE r <= 3 AND sz > 100 * 1024 * 1024
ORDER BY sz DESC;

-- lag(): разница с предыдущей строкой (прирост между снимками в своей таблице наблюдений)
-- SELECT ts, wal_bytes - lag(wal_bytes) OVER (ORDER BY ts) AS wal_delta FROM my_wal_snapshots;
```

### 13.7. Транзакции

```sql
BEGIN;                         -- начать (синоним: START TRANSACTION)
  UPDATE …;
  SAVEPOINT s1;                -- точка сохранения
  DELETE …;
  ROLLBACK TO SAVEPOINT s1;    -- отменить только DELETE
COMMIT;                        -- зафиксировать; ROLLBACK — отменить всё
```

Что нужно знать:

- Вне `BEGIN` каждый оператор — отдельная транзакция с автоматической фиксацией (в `psql` — `AUTOCOMMIT on`).
- **DDL в PostgreSQL транзакционен:** `CREATE TABLE`, `ALTER TABLE`, `DROP INDEX` можно откатить. Приём для опасных операций: `BEGIN;` → команда → проверка результата → `COMMIT` или `ROLLBACK`.
- После ошибки внутри транзакции все следующие команды отвергаются с `ERROR: current transaction is aborted, commands ignored until end of transaction block`, пока не выполнен `ROLLBACK` (или `ROLLBACK TO SAVEPOINT`).
- Нельзя выполнить внутри блока транзакции: `VACUUM`, `CREATE DATABASE`, `DROP DATABASE`, `CREATE INDEX CONCURRENTLY`, `REINDEX CONCURRENTLY`, `ALTER SYSTEM`, `CREATE TABLESPACE`.
- Открытая и забытая транзакция — источник блокировок и раздувания (разделы 6.3, 7.2). Не оставляйте сеанс `psql` с незакрытым `BEGIN`.
- Точки сохранения не бесплатны: каждая — вложенная транзакция; номер (subxid) она получает, только когда меняет данные. В общей памяти кешируется до 64 открытых subxid на процесс; сверх этого проверки видимости начинают обращаться к `pg_subtrans`, и накладные расходы заметно растут [PG, «Subtransactions»].

Настройки `psql` для скриптов:

```bash
# остановиться на первой ошибке, всё одной транзакцией
sudo -u postgres psql -d base1c -v ON_ERROR_STOP=1 --single-transaction -f script.sql
```

```text
\set ON_ERROR_ROLLBACK interactive   -- в интерактивном сеансе ошибка откатывает только неудачную команду
\set AUTOCOMMIT off                  -- каждая команда неявно открывает транзакцию; не забывайте COMMIT
```

### 13.8. COPY: выгрузка и загрузка

| Вариант | Где читается или пишется файл | Права |
|---|---|---|
| `COPY … TO/FROM 'файл'` | на **сервере**, от имени пользователя ОС `postgres` | суперпользователь либо роли `pg_read_server_files` / `pg_write_server_files` |
| `COPY … TO/FROM PROGRAM 'команда'` | команда выполняется на сервере | суперпользователь либо `pg_execute_server_program` |
| `\copy …` (команда `psql`) | на **клиенте**, от имени запустившего `psql` | обычные права на таблицу |
| `COPY … TO STDOUT` / `FROM STDIN` | поток клиента | обычные права |

```sql
-- результат запроса в CSV на сервере
COPY (SELECT relname, reltuples::bigint, pg_total_relation_size(oid)
      FROM pg_class WHERE relkind = 'r')
TO '/tmp/tables.csv' WITH (FORMAT csv, HEADER, DELIMITER ';');

-- загрузить CSV во временную таблицу для анализа
CREATE TEMP TABLE waits (ts timestamptz, wait_event_type text, wait_event text, cnt int);
COPY waits FROM '/tmp/waits.csv' WITH (FORMAT csv, HEADER);
-- 17+: пропускать строки с ошибками формата
COPY waits FROM '/tmp/waits.csv' WITH (FORMAT csv, HEADER, ON_ERROR ignore);
```

```bash
# то же на стороне клиента: файл появится там, где запущен psql
psql -h 192.168.1.20 -U monitor -d base1c \
     -c "\copy (SELECT now(), datname, numbackends FROM pg_stat_database) TO 'stat.csv' WITH (FORMAT csv, HEADER)"

# быстрая выгрузка в файл без COPY: без рамок, с разделителем
sudo -u postgres psql -d base1c -At -F ';' -c "SELECT relname, reltuples::bigint FROM pg_class WHERE relkind='r'" > tables.csv
```

`COPY` — самый быстрый способ массовой загрузки; на нём основаны `pg_dump` и `pg_restore`.

### 13.10. Функции размеров и времени

| Функция | Что возвращает |
|---|---|
| `pg_database_size('имя')` | размер базы в байтах |
| `pg_relation_size(rel [, 'main' / 'fsm' / 'vm' / 'init'])` | один слой отношения (по умолчанию основной) |
| `pg_table_size(rel)` | таблица + TOAST + карты, без индексов |
| `pg_indexes_size(rel)` | все индексы таблицы |
| `pg_total_relation_size(rel)` | таблица + TOAST + индексы |
| `pg_tablespace_size('имя')` | табличное пространство |
| `pg_column_size(значение)` | сколько байт занимает значение при хранении |
| `pg_size_pretty(байты)` | человекочитаемый вид (`12 GB`) |
| `pg_size_bytes('12 GB')` | обратное преобразование |

| Функция | Что возвращает |
|---|---|
| `now()`, `transaction_timestamp()`, `current_timestamp` | время **начала транзакции** — внутри транзакции не меняется |
| `statement_timestamp()` | время начала текущего оператора |
| `clock_timestamp()` | реальное текущее время; меняется даже внутри одного оператора |
| `current_date` | текущая дата |
| `age(ts)`, `age(ts1, ts2)` | интервал между метками времени |
| `age(xid)` | возраст номера транзакции — совсем другая функция с тем же именем |
| `date_trunc('hour', ts)` | округлить вниз до часа, дня, месяца |
| `extract(epoch FROM интервал)` | интервал в секундах (с 14-й версии результат `numeric`) |
| `to_char(ts, 'YYYY-MM-DD HH24:MI:SS')` | форматирование |
| `pg_postmaster_start_time()` | когда запущен сервер |
| `pg_conf_load_time()` | когда последний раз перечитана конфигурация |

```sql
SELECT pg_size_pretty(pg_database_size(current_database())) AS db_size,
       now() - pg_postmaster_start_time()                    AS uptime,
       pg_conf_load_time()                                   AS conf_loaded;

-- размеры всех баз
SELECT datname, pg_size_pretty(pg_database_size(datname)) AS size
FROM pg_database
ORDER BY pg_database_size(datname) DESC;

-- арифметика времени: сеансы, начатые более 8 часов назад
SELECT pid, backend_start, date_trunc('second', now() - backend_start) AS age
FROM pg_stat_activity
WHERE backend_start < now() - interval '8 hours';
```

## 14. Что изменилось по версиям 12 → 19 (значимое для администратора 1С)

| Версия | Изменение | Влияние |
|---|---|---|
| 12 (2019) | `recovery.conf` упразднён: параметры восстановления в `postgresql.conf`, режимы задаются файлами `standby.signal` и `recovery.signal`; сервер не стартует, если `recovery.conf` существует | старые инструкции по репликации и восстановлению неприменимы |
| 12 | `REINDEX CONCURRENTLY`; `pg_checksums` включает и выключает контрольные суммы на остановленном кластере; представления хода `CREATE INDEX`, `CLUSTER`, `VACUUM FULL` | перестройка индексов без остановки записи |
| 12 | JIT включён по умолчанию; CTE встраиваются в запрос; `plan_cache_mode`; `max_wal_senders` больше не входит в `max_connections` | для 1С `jit = off` |
| 13 (2020) | Дедупликация в B-tree; `wal_keep_segments` → `wal_keep_size`; `max_slot_wal_keep_size`; autovacuum для таблиц «только вставка»; параллельная очистка индексов; хеш-агрегация со сбросом на диск (`hash_mem_multiplier`) | индексы меньше; забытый слот можно ограничить по объёму WAL |
| 14 (2021) | `password_encryption = scram-sha-256` по умолчанию; масштабируемость снимков при тысячах соединений; «восходящая» очистка B-tree; аварийный режим очистки (`vacuum_failsafe_age`); `idle_session_timeout`; `pg_stat_wal`; роли `pg_read_all_data`, `pg_database_owner`; `checkpoint_completion_target = 0.9`; сжатие TOAST `lz4` | старые платформы 1С без SCRAM получают `authentication method 10 not supported`; меньше раздувание индексов |
| 15 (2022) | У `PUBLIC` отнято право `CREATE` в схеме `public`; статистика перенесена в общую память, процесс сборщика и `stats_temp_directory` удалены; исключительный режим копирования удалён, `pg_start_backup()` → `pg_backup_start()`; `log_checkpoints = on`; сжатие WAL `lz4`/`zstd`; ICU как поставщик локали базы; `MERGE`; `hash_mem_multiplier = 2.0` | роль 1С должна быть владельцем базы; старые скрипты копирования перестают работать; совет про `pg_stat_tmp` в tmpfs неактуален |
| 16 (2023) | `pg_stat_io`; `include` и регулярные выражения в `pg_hba.conf`; ужесточение `CREATEROLE`; `reserved_connections`; `VACUUM (BUFFER_USAGE_LIMIT)`; `REINDEX DATABASE` больше не трогает системный каталог; удалены `promote_trigger_file` и параметры только для чтения `lc_collate`, `lc_ctype`; `force_parallel_mode` → `debug_parallel_query` | для системного каталога нужен отдельный `REINDEX SYSTEM`; скрипты с `SHOW lc_collate` перестают работать |
| 17 (2024) | Новая структура памяти `VACUUM` — снят предел 1 ГБ и снижен расход; инкрементные копии (`pg_basebackup --incremental`, `pg_combinebackup`, `summarize_wal`); `pg_stat_checkpointer` (счётчики ушли из `pg_stat_bgwriter`); право `MAINTAIN` и роль `pg_maintain`; встроенный поставщик локали; `transaction_timeout`; `allow_alter_system`; `EXPLAIN (MEMORY, SERIALIZE)`; удалены `old_snapshot_threshold`, `db_user_namespace`, `adminpack` | очистка больших таблиц 1С быстрее; запросы мониторинга к `pg_stat_bgwriter` нужно переписать |
| 18 (2025) | Асинхронный ввод-вывод (`io_method = worker` по умолчанию, `io_workers = 3`, представление `pg_aios`); **контрольные суммы включены по умолчанию**; `pg_upgrade` переносит статистику планировщика; skip scan в B-tree; `EXPLAIN ANALYZE` показывает `BUFFERS` без указания; MD5-пароли объявлены устаревшими; `autovacuum_worker_slots`, `autovacuum_vacuum_max_threshold`; `effective_io_concurrency = 16`; OAuth; `uuidv7()`; виртуальные генерируемые столбцы | новые процессы `io worker`; при `pg_upgrade` со старого кластера без контрольных сумм нужен `initdb --no-data-checksums`; поддержка платформой — с 8.3.27 (см. `01-sborki-postgresql-dlya-1c-ustanovka.md`) |
| 19 (Beta 4, 24.09.2026; выпуска нет) | `standard_conforming_strings` всегда `on`, `escape_string_warning` удалён; `jit = off` по умолчанию; `max_locks_per_transaction` 64 → 128 с изменением расчёта; `log_lock_waits = on`; `default_toast_compression = lz4`; команда `REPACK` (замена `VACUUM FULL` и `CLUSTER`, есть `CONCURRENTLY`); удалена аутентификация RADIUS; предупреждение при входе с MD5; автоматическое масштабирование `io worker`; параллельная очистка индексов в autovacuum | привычный для 1С `standard_conforming_strings = off` задать нельзя — нужна поддержка со стороны платформы и сборок; на 10.10.2026 сборок для 1С нет |

Источник всех строк — примечания к выпускам [PG]. Содержимое строки про 19-ю версию взято из документации Beta 4 и до финального выпуска может измениться; 19.10.2026 все пункты строки сверены с примечаниями к выпуску в редакции «AS OF 2026-10-09» (на сайте уже объявлен RC 1 от 15.10.2026) — расхождений нет.

## Типичные ошибки и подводные камни

| № | Симптом | Причина | Решение |
|---|---|---|---|
| 1 | Все пользователи 1С разом получили ошибку СУБД; в журнале `server process (PID N) was terminated by signal 9` и `terminating any other active server processes` | Серверный процесс убит (`kill -9` или OOM-killer); postmaster перезапустил все процессы и выполнил восстановление по WAL | Не использовать `kill -9`; `journalctl -k` на предмет OOM; уменьшить `work_mem`/`temp_buffers`, пересчитать память (раздел 3.4) |
| 2 | `FATAL: sorry, too many clients already` | Исчерпан `max_connections` | Увеличить (перезапуск); найти, кто держит соединения: `SELECT client_addr, count(*) FROM pg_stat_activity GROUP BY 1` |
| 3 | `ERROR: out of shared memory` + `HINT: You might need to increase "max_locks_per_transaction"` | Переполнена таблица блокировок: много временных таблиц, `pg_dump` большой базы, реструктуризация | `max_locks_per_transaction = 256` и выше, перезапуск (раздел 7.6) |
| 4 | Сервер занял всю память, ушёл в подкачку | `work_mem` или `temp_buffers` умножились на число соединений и операций | Раздел 3.4; `work_mem` повышать точечно, а не глобально |
| 5 | После команды администратора или начала реструктуризации «повисли все» | Запрос `ACCESS EXCLUSIVE` стоит в очереди за старой транзакцией, остальные — за ним | `SET lock_timeout` перед ручным DDL; найти и завершить `idle in transaction` (разделы 6.3, 7.2) |
| 6 | Таблицы и индексы растут, `VACUUM` «ничего не убирает» | Горизонт удерживает длинная транзакция, слот репликации или подготовленная транзакция | Раздел 6.3 |
| 7 | `WARNING: database "…" must be vacuumed within N transactions` | Заморозка не успевает: autovacuum выключен, не справляется или горизонт удержан | Устранить причину, выполнить `VACUUM` по базе (раздел 6.5) |
| 8 | Каталог `pg_wal` занял весь диск, сервер остановился с `PANIC: could not write to file "pg_wal/…": No space left on device` | Сбой `archive_command`, отставший слот репликации, большой `wal_keep_size` | Освободить место **не удаляя файлы WAL вручную**; починить архивацию или удалить слот (`pg_drop_replication_slot`); раздел 5.7 |
| 9 | Частые `checkpoints are occurring too frequently` | Мал `max_wal_size` для такого потока записи | Увеличить `max_wal_size` и `checkpoint_timeout` |
| 10 | После отключения питания хоста база не открывается или в ней `invalid page in block …` | Запись подтверждалась до попадания на диск: кеш диска, контроллера или гипервизора игнорирует сброс; либо `fsync = off` | Проверить `pg_test_fsync` (раздел 5.6); восстановление из резервной копии |
| 11 | Запрос 1С в `psql` выполняется быстро, а из 1С — медленно (или наоборот) | Разные параметры сеанса (`enable_mergejoin`, `cpu_operator_cost`), нет статистики по временным таблицам, другой набор данных во временных таблицах | Перед `EXPLAIN` выполнить `SET` из раздела 8.9; воспроизвести цепочку временных таблиц |
| 12 | В плане `rows=1`, по факту сотни тысяч; вложенные циклы с огромным `loops` | Устаревшая или отсутствующая статистика, связанные условия | `ANALYZE`; проверить autovacuum; для временных таблиц — `plantuner.fix_empty_table`, версия платформы |
| 13 | После обновления Ubuntu `WARNING: database "…" has a collation version mismatch`; позже — дубликаты в уникальных индексах, «пропавшие» строки | Новая glibc изменила порядок сортировки, индексы построены по старому | `REINDEX DATABASE`, затем `ALTER DATABASE … REFRESH COLLATION VERSION` (раздел 11.3) |
| 14 | `ERROR: type "mvarchar" does not exist` при восстановлении дампа | Целевой сервер — «ванильный» PostgreSQL без модулей для 1С | Восстанавливать на сборку с патчем 1С или Postgres Pro |
| 15 | `ERROR: permission denied for schema public` при создании базы 1С | PostgreSQL 15+: право `CREATE` в `public` только у владельца базы | `ALTER DATABASE … OWNER TO роль_1с` (раздел 12.2) |
| 16 | `FATAL: no pg_hba.conf entry for host …` | Нет подходящей строки; или строка `hostssl`, а соединение без SSL | Добавить строку, `SELECT pg_reload_conf()`; проверить `pg_hba_file_rules` |
| 17 | Изменили `pg_hba.conf` или `postgresql.conf`, а ничего не поменялось | Не перечитана конфигурация; параметр требует перезапуска; значение перекрыто в `postgresql.auto.conf` | `pg_reload_conf()`; `SELECT name, pending_restart, sourcefile FROM pg_settings WHERE name = '…'` |
| 18 | Созданный вручную индекс пропал | Реструктуризация 1С пересоздала таблицу | Раздел 9.5: добавить индекс штатно через конфигурацию |
| 19 | `CREATE INDEX CONCURRENTLY` завершился ошибкой, запись в таблицу замедлилась | Остался недействительный индекс | `SELECT indexrelid::regclass FROM pg_index WHERE NOT indisvalid;` → `DROP INDEX CONCURRENTLY` |
| 20 | Планирование даже простых запросов занимает десятки миллисекунд; `pg_attribute` весит гигабайты | Раздут системный каталог из-за временных таблиц | Проверить autovacuum системных таблиц; `VACUUM` каталога; раздел 10.3 |
| 21 | 1С не работает с резервным сервером (репликой) | Запросы 1С создают временные таблицы, а реплика доступна только для чтения | Реплика — только для отказоустойчивости и копий; для отчётов — механизм копий баз данных на отдельном экземпляре |
| 22 | Размер базы по `pg_relation_size` намного меньше, чем место на диске | Не учтены TOAST и индексы | `pg_total_relation_size`, `pg_database_size` (раздел 4.4) |
| 23 | `ERROR: could not serialize access due to concurrent update` в журнале | Конфликт на уровне Repeatable Read / Serializable (у 1С — автоматический режим блокировок) | Перевод конфигурации в управляемый режим; повтор транзакции |
| 24 | `ERROR: current transaction is aborted, commands ignored until end of transaction block` | После ошибки в транзакции не выполнен `ROLLBACK` | `ROLLBACK;` в `psql`: `\set ON_ERROR_ROLLBACK interactive` |

## Быстрая шпаргалка

| Задача | Команда |
|---|---|
| Версия сервера | `SELECT version();` |
| Где каталог данных и конфигурация | `SHOW data_directory; SHOW config_file; SHOW hba_file;` |
| Процессы экземпляра | `ps -o pid,stat,rss,cmd --forest -u postgres` |
| Типы процессов глазами SQL | `SELECT backend_type, count(*) FROM pg_stat_activity GROUP BY 1;` |
| Занято соединений из максимума | `SELECT count(*), current_setting('max_connections') FROM pg_stat_activity WHERE backend_type = 'client backend';` |
| Размер общей памяти (15+) | `SHOW shared_memory_size;` |
| Честный расход памяти процессами | сумма `Pss` из `/proc/<pid>/smaps_rollup` (раздел 3.5) |
| Был ли OOM | `journalctl -k \| grep -i -E 'oom\|killed process'` |
| Файл таблицы | `SELECT pg_relation_filepath('имя');` |
| Таблица по номеру файла | `SELECT pg_filenode_relation(0, 16423);` или `oid2name -d база -f 16423` |
| OID баз | `SELECT oid, datname FROM pg_database;` |
| Размер базы | `SELECT pg_size_pretty(pg_database_size(current_database()));` |
| Размер таблицы с TOAST и индексами | `SELECT pg_size_pretty(pg_total_relation_size('имя'));` |
| Табличные пространства | `\db+` |
| Временные файлы сейчас (12+) | `SELECT * FROM pg_ls_tmpdir();` |
| Включены ли контрольные суммы | `SHOW data_checksums;` |
| Текущий LSN и файл WAL | `SELECT pg_current_wal_lsn(), pg_walfile_name(pg_current_wal_lsn());` |
| Объём каталога WAL | `SELECT count(*), pg_size_pretty(sum(size)) FROM pg_ls_waldir();` |
| Последняя контрольная точка | `SELECT * FROM pg_control_checkpoint();` или `pg_controldata <каталог данных>` |
| Статистика контрольных точек | 17+: `SELECT * FROM pg_stat_checkpointer;` до 16: `SELECT * FROM pg_stat_bgwriter;` |
| Принудительная контрольная точка | `CHECKPOINT;` |
| Проверить честность `fsync` | `pg_test_fsync -f <файл на томе данных>` |
| Слоты репликации и удержанный WAL | `SELECT slot_name, active, wal_status, restart_lsn FROM pg_replication_slots;` |
| Системные столбцы строки | `SELECT ctid, xmin, xmax, * FROM таблица LIMIT 5;` |
| Текущий снимок (13+) | `SELECT pg_current_snapshot();` |
| Кто держит горизонт очистки | `SELECT pid, state, xact_start, age(backend_xmin) FROM pg_stat_activity ORDER BY 4 DESC NULLS LAST LIMIT 5;` |
| Возраст баз до переполнения счётчика | `SELECT datname, age(datfrozenxid) FROM pg_database;` |
| Доля HOT-обновлений | `SELECT relname, n_tup_upd, n_tup_hot_upd FROM pg_stat_user_tables ORDER BY 2 DESC LIMIT 10;` |
| Уровень изоляции | `SHOW transaction_isolation; SHOW default_transaction_isolation;` |
| Кто кого блокирует | `SELECT pid, pg_blocking_pids(pid), left(query, 60) FROM pg_stat_activity WHERE cardinality(pg_blocking_pids(pid)) > 0;` |
| Табличные блокировки | `SELECT pid, mode, granted, relation::regclass FROM pg_locks WHERE locktype = 'relation';` |
| Не ждать блокировку при ручном DDL | `SET lock_timeout = '5s';` |
| Отменить запрос / завершить сеанс | `SELECT pg_cancel_backend(pid);` / `SELECT pg_terminate_backend(pid);` |
| Статистика столбцов таблицы | `SELECT attname, n_distinct, null_frac, correlation FROM pg_stats WHERE tablename = 'имя';` |
| Обновить статистику | `ANALYZE VERBOSE имя;` |
| План с фактическим выполнением | `EXPLAIN (ANALYZE, BUFFERS) запрос;` |
| Параметры планировщика, как у сеанса 1С | `SET enable_mergejoin = off; SET cpu_operator_cost = 0.001;` |
| Индексы таблицы | `\d+ имя` или `SELECT indexname, indexdef FROM pg_indexes WHERE tablename = 'имя';` |
| Недействительные индексы | `SELECT indexrelid::regclass FROM pg_index WHERE NOT indisvalid;` |
| Перестроить индекс без блокировки записи (12+) | `REINDEX INDEX CONCURRENTLY имя;` |
| Сколько временных таблиц | `SELECT count(*) FROM pg_class WHERE relpersistence = 't' AND relkind = 'r';` |
| Кодировка и локаль баз | `\l` или `SELECT datname, pg_encoding_to_char(encoding), datcollate FROM pg_database;` |
| Типы столбцов таблицы | `SELECT attname, format_type(atttypid, atttypmod) FROM pg_attribute WHERE attrelid = 'имя'::regclass AND attnum > 0;` |
| Расширения базы | `\dx` |
| Зафиксировать новую версию правил сортировки (15+) | `REINDEX DATABASE имя; ALTER DATABASE имя REFRESH COLLATION VERSION;` |
| Роли и их атрибуты | `\du+` |
| Формат хранения паролей | `SELECT rolname, left(rolpassword, 14) FROM pg_authid WHERE rolcanlogin;` |
| Проверить `pg_hba.conf` | `SELECT line_number, type, database, user_name, address, auth_method, error FROM pg_hba_file_rules;` |
| Перечитать конфигурацию | `SELECT pg_reload_conf();` или `sudo systemctl reload postgresql@17-main` |
| Какие соединения шифруются | `SELECT pid, ssl, version FROM pg_stat_ssl;` |
| Владелец схемы `public` | `SELECT nspowner::regrole, nspacl FROM pg_namespace WHERE nspname = 'public';` |
| Выгрузить результат запроса в CSV | `\copy (запрос) TO 'файл.csv' WITH (FORMAT csv, HEADER)` |
| Время работы сервера | `SELECT now() - pg_postmaster_start_time();` |
