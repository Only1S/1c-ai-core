## Кратко — главные факты и команды

1. **Обычный («ванильный») PostgreSQL из репозитория Ubuntu или PGDG для баз 1С не подходит.** Платформе нужны типы `mchar`/`mvarchar` (расширение `mchar`), оператор `==` (расширение `fulleq`) и функция `fasttruncate()` (расширение `fasttrun`). В апстриме PostgreSQL их нет. **[офиц.]** — в документации Postgres Pro о модулях `fulleq` и `fasttrun` прямо сказано, что они необходимы для поддержки «1С:Предприятия».
2. **Официальный список СУБД 1С (v8.1c.ru, редакция июля 2026) не содержит «ванильного» PostgreSQL.** Перечислены только: «PostgreSQL с патчем от 1С», Postgres Pro 1С / Standard / Enterprise (+CERT), Tantor SE 1C / Tantor Certified, Pangolin, Jatoba, Nexign NORD, Arenadata Prosperity. Официального подтверждения работы платформы на немодифицированном PostgreSQL нет: при рецензии 10.10.2026 списки изменений платформы за 8.3.15–8.5.4 просмотрены целиком — записей о поддержке PostgreSQL без патча/без `mchar` в них не найдено (подробности — раздел 1.4). **Вывод: на октябрь 2026 «ванильный» PostgreSQL для баз 1С официально не поддерживается.**
3. **Протестированные 1С версии на июль 2026 [офиц.]:** PostgreSQL с патчем от 1С `18.4-1.1C`, `17.10-2.1C`, `16.14-1.1C`, `15.18-1.1C`, `14.23-1.1C`; Postgres Pro 1С `18.4`, `17.10`, `16.14`, `15.18`, `14.23`; Tantor SE 1C `18.3.1`, `17.10.1`, `16.14.0`, `15.18.0`, `14.23.0`.
4. **Минимальная версия платформы 1С по данным списка изменений платформы (V8Update) [офиц.]:** PostgreSQL/Postgres Pro 12–15 — с 8.3.18; Postgres Pro 16 и 17 — с 8.3.22; Postgres Pro 18 — с 8.3.27; поддержка PostgreSQL 18 (x86-64) в сборке от 1С добавлена в 8.3.27. В 8.5.1 прекращена поддержка PostgreSQL до 9.6 включительно.
5. **Жизненный цикл PostgreSQL [офиц., postgresql.org]:** 14 — до 12.11.2026; 15 — до 11.11.2027; 16 — до 09.11.2028; 17 — до 08.11.2029; 18 — до 14.11.2030. PostgreSQL 19 на 10.10.2026 — Beta 4 (от 24.09.2026), на 19.10.2026 — RC 1 (от 15.10.2026), для 1С не поддерживается. Главная несовместимость: в 19 `standard_conforming_strings` всегда `on`, а `escape_string_warning` удалён [PG, примечания к выпуску 19]. 1С требует `off` — подробности в `02-…` (раздел о `standard_conforming_strings`).
6. **Рекомендуемый выбор для нового сервера (октябрь 2026):** Ubuntu 24.04 LTS + платформа 8.3.27 или 8.5.x + PostgreSQL **17** (или 18 при платформе ≥ 8.3.27) в сборке «PostgreSQL для 1С» от Postgres Professional либо в сборке от 1С. PostgreSQL 14 новым не ставить — EOL через месяц.
7. **Бесплатная сборка Postgres Professional** ставится из открытого репозитория без регистрации:
   ```bash
   wget https://repo.postgrespro.ru/1c/1c-17/keys/pgpro-repo-add.sh
   sudo sh pgpro-repo-add.sh
   sudo LANG=ru_RU.UTF-8 apt-get install -y postgrespro-1c-17
   ```
   Каталоги: программы `/opt/pgpro/1c-17`, данные `/var/lib/pgpro/1c-17/data`, служба `postgrespro-1c-17`. **[офиц.]**
8. **Сборка от 1С** скачивается с `https://releases.1c.ru` (проект «PostgreSQL», nick `AddCompPostgre`, нужна учётная запись с действующей подпиской), архив `postgresql_*.tar.bz2` с deb-пакетами; раскладка каталогов дебиановская: `/usr/lib/postgresql/NN/bin` **[офиц., Dockerfile 1С]**, `/etc/postgresql/NN/main`, `/var/lib/postgresql/NN/main`, служба `postgresql@NN-main` (⚠ три последних — по аналогии с пакетами Debian/Ubuntu и по статьям о старых версиях сборки; для 16–18 по содержимому пакетов не проверено — после установки сверьте командой `pg_lsclusters`).
9. **Локаль `ru_RU.UTF-8` должна существовать в ОС ДО создания кластера** (`initdb` / установка серверного пакета):
   ```bash
   sudo locale-gen ru_RU.UTF-8 && sudo update-locale LANG=ru_RU.UTF-8
   locale -a | grep -i ru_RU
   ```
10. **Метапакет `postgrespro-1c-NN` конфликтует с `postgresql-common`** (поле `Conflicts` пакета) — при установке apt предложит удалить дистрибутивный PostgreSQL. Для совместной работы ставят `postgrespro-1c-NN-contrib` и вручную запускают `pg-setup`. **[офиц.]**
11. **Пакеты сборки от 1С называются так же, как в Ubuntu/PGDG** (`postgresql-NN`, `postgresql-client-NN`, `libpq5`), поэтому `apt upgrade` (и автоматический `unattended-upgrades` — обновления PostgreSQL в Ubuntu выходят через карман `-security`) может заменить их «ванильными». Обязательно: `sudo apt-mark hold postgresql-17 postgresql-client-17 libpq5`.
12. **Контрольные суммы данных:** в Postgres Pro и сборке «PostgreSQL для 1С» включены по умолчанию (кластер создаёт `pg-setup`); в апстриме по умолчанию включены начиная с PostgreSQL 18, для 14–17 нужен `initdb --data-checksums`. **[офиц.]**
13. **Кодировка и локаль базы 1С:** `UTF8`, `lc_collate = lc_ctype = ru_RU.UTF-8` (для русскоязычных баз). Проверка: `SELECT datname, pg_encoding_to_char(encoding), datcollate, datctype, datlocprovider FROM pg_database;`
14. **Первичная настройка:** пароль `postgres` (`\password postgres`), `listen_addresses`, строка в `pg_hba.conf` для адреса сервера 1С, перезапуск, проверка `pg_isready -h 127.0.0.1 -p 5432`. **SCRAM и 1С:** по списку изменений платформы **[офиц.]**, в версии **8.3.20** клиентская библиотека `libpq` платформы обновлена до `14.2-3.1C` — значит, платформа 8.3.20 (поздние сборки) и новее умеет `scram-sha-256` (это вывод из версии libpq: SCRAM поддерживается libpq начиная с 10; прямой фразы «поддержан SCRAM» в списках изменений нет). Для 8.3.19 и старше поддержка не подтверждена; типичный симптом — `authentication method 10 not supported`, обход — `md5` (раздел 7.5).
15. **Параметры, специфичные для 1С [офиц., Postgres Pro, приложение K]:** `standard_conforming_strings = off`, `escape_string_warning = off`, `max_locks_per_transaction = 256`, `max_connections = 500..10000`, `row_security = off`, `jit = off`; `shared_preload_libraries = 'plantuner'` + `plantuner.fix_empty_table = on`. `online_analyze` для современных версий 1С **не рекомендуется**. Быстрая установка сборки «PostgreSQL для 1С» эти параметры сама **не выставляет** (применяется только общий пресет `default.tune`; вывод по коду пакетов 16.14, разобранных 11.10.2026) — их задают отдельно: `../guides/07-postgresql-dlya-1c-s-1c-postgres-ru.md`, раздел 3, шаг 7.
16. **Что видно в базе 1С:** расширения `mchar`, `fulleq`, `fasttrun` (`\dx`), таблицы `config`, `params`, `files`, `dbschema`, `v8users`, `_reference…` и т. д. в схеме `public`. С платформы 8.5.4 схему можно задать явно (поле «Схема БД», `--db-schema`). **[офиц.]**
17. **Несколько экземпляров:** разные мажорные версии сборки Postgres Pro живут в разных каталогах `/opt/pgpro/1c-NN` и разных службах; порт меняется командой `pg-setup set-server-port 5433`. В поле «Сервер баз данных» 1С порт указывается так: `hostname port=5433`.
18. **Минорное обновление** = обновить пакеты и перезапустить службу, каталог данных не трогается. Мажорное (17 → 18) — это `pg_upgrade` или выгрузка/загрузка, отдельная процедура.

## 1. Зачем 1С нужна особая сборка PostgreSQL

### 1.1. Суть проблемы

Платформа «1С:Предприятие 8» изначально проектировалась под Microsoft SQL Server и опирается на его семантику строк и сравнения:

- строки сравниваются **без учёта регистра**;
- **хвостовые пробелы** в `CHAR`/`VARCHAR` обрабатываются по правилам MS SQL;
- сравнение `NULL = NULL` в ряде запросов платформы должно давать ИСТИНА;
- временные таблицы создаются и очищаются тысячами, очистка должна быть очень дешёвой.

В стандартном PostgreSQL ничего из этого нет, поэтому для 1С используются сборки с дополнительными модулями (расширениями) и патчами ядра.

### 1.2. Модули, которые добавляют «1С-сборки»

| Модуль | Тип | Что делает | Обязателен для 1С? | Как включается |
|---|---|---|---|---|
| `mchar` | расширение | Типы `mchar` и `mvarchar` — аналоги `CHAR`/`VARCHAR` MS SQL: регистронезависимое сравнение по умолчанию, обработка хвостовых пробелов как в MS SQL, хранение в UTF-16 независимо от кодировки базы; сравнение и смена регистра через библиотеку **ICU** (поведение одинаково на разных ОС). Операторы `< <= = >= >` — без учёта регистра, `&< &<= &= &>= &>` — с учётом. Поддержка B-tree и hash-индексов, `LIKE`/`SIMILAR TO`/`~`. Авторы — О. Бартунов, Ф. Сигаев. **[офиц.]** | Да | `CREATE EXTENSION mchar` в базе (в базах 1С уже создано) |
| `fulleq` | расширение | Оператор `==`: равенство, при котором два `NULL` считаются равными (поведение MS SQL). Определён для `bool, bytea, char, name, int2/4/8, text, varchar, float4/8, date, time, timestamp, timestamptz, interval, inet, cidr, macaddr` и др. По документации Postgres Pro — необходим для поддержки 1С. **[офиц.]** | Да | `CREATE EXTENSION fulleq` |
| `fasttrun` | расширение | Функция `fasttruncate('имя_таблицы')` — быстрая очистка временных таблиц **без транзакционной безопасности** (нельзя откатить, результат сразу виден). Предотвращает разрастание каталога `pg_class`. По документации Postgres Pro — необходим для поддержки 1С. **[офиц.]** | Да | `CREATE EXTENSION fasttrun` |
| `online_analyze` | загружаемая библиотека | Немедленно обновляет статистику таблицы после `INSERT/UPDATE/DELETE/SELECT INTO/COPY`. Исторически рекомендовался для временных таблиц 1С. **[офиц., Postgres Pro 17]:** с современными версиями 1С использовать не рекомендуется; включать только если фоновое обновление статистики не даёт хорошего результата или планировщик часто ошибается в оценке числа строк. | Нет | `shared_preload_libraries` или `LOAD 'online_analyze'` |
| `plantuner` | загружаемая библиотека | Подсказки планировщику: скрыть/вернуть индексы (`plantuner.disable_index`, `plantuner.enable_index`) и, главное для 1С, `plantuner.fix_empty_table = on` — считать только что созданную пустую таблицу пустой (0 страниц, 0 строк), а не «таблицей неизвестного размера». **[офиц.]** | Нет, но рекомендован | `shared_preload_libraries = 'plantuner'` |
| `dbcopies_decoding` | модуль логического декодирования | Модуль, разработанный 1С, для обновления копий баз данных — нужен механизму копий базы данных платформы (версия 2 механизма — с платформы 8.3.25, PostgreSQL ≥ 10). Требует `wal_level = logical`. **[офиц.]** | Только для механизма копий БД (КОРП) | Входит в `-contrib`; настраивается платформой |
| `pg_trgm_mchar` | расширение | Триграммный поиск (GIN, классы операторов `gin_trgm_ops_mvarchar`, `gin_trgm_ops_mchar`) по `mchar`/`mvarchar`. Есть в Postgres Pro. | Нет | `CREATE EXTENSION pg_trgm_mchar CASCADE` |
| `auto_dump` | загружаемая библиотека | Сбор контекста проблемных запросов (DDL и данные временных таблиц) для воспроизведения. Разработан для «PostgreSQL с патчем от 1С» (анонс в «Новое в платформе 8.5.4»), есть также в Postgres Pro и Tantor. **[офиц.]** | Нет | `shared_preload_libraries = 'auto_dump'`, `auto_dump.enable = on` |
| патчи ядра | изменения исходного кода | Оптимизации планировщика и работы с временными таблицами под типовые запросы 1С (оценка соединений, блокировки каталога для временных таблиц и т. п.). Точный состав у каждого вендора свой и отличается от версии к версии. | Нет (на корректность не влияют, влияют на скорость) | Вшиты в бинарники |

Рекомендуемые настройки модулей по документации Postgres Pro (приложение K.4) **[офиц.]**:

```ini
# plantuner — рекомендуется
shared_preload_libraries = 'plantuner'
plantuner.fix_empty_table = on

# online_analyze — ТОЛЬКО если без него планировщик систематически ошибается
# shared_preload_libraries = 'online_analyze, plantuner'
# online_analyze.enable = on
# online_analyze.threshold = 50
# online_analyze.scale_factor = 0.1
# online_analyze.verbose = off
# online_analyze.table_type = 'temporary'
# online_analyze.min_interval = 10000
```

Исторически (PostgreSQL 9.x–12, сборка 1С) в `postgresql.conf` стояло `shared_preload_libraries = 'online_analyze, plantuner'` с `online_analyze.table_type = 'temporary'` и `online_analyze.local_tracking = on` — **[практика]**, встречается на старых серверах. При переносе конфигурации на новую сборку убедитесь, что перечисленные в `shared_preload_libraries` библиотеки в ней реально есть, иначе сервер не запустится (см. «Типичные ошибки»).

### 1.3. Как проверить, что перед вами «1С-сборка»

```bash
# версия и происхождение бинарников
sudo -u postgres psql -Atc "select version();"

# есть ли расширения, без которых 1С не работает
sudo -u postgres psql -c "select name, default_version, installed_version
                          from pg_available_extensions
                          where name in ('mchar','fulleq','fasttrun','pg_trgm_mchar')
                          order by 1;"

# есть ли загружаемые библиотеки (каталог библиотек берём из системного представления pg_config)
LIBDIR=$(sudo -u postgres psql -Atc "select setting from pg_config where name = 'PKGLIBDIR'")
ls "$LIBDIR" | grep -E 'mchar|fulleq|fasttrun|online_analyze|plantuner|dbcopies|auto_dump'
```

Функциональная проверка в отдельной тестовой базе:

```sql
CREATE DATABASE t_mchar;
\c t_mchar
CREATE EXTENSION mchar;
CREATE EXTENSION fulleq;
CREATE EXTENSION fasttrun;
SELECT 'Абв'::mvarchar = 'аБВ'::mvarchar AS ci_equal;   -- ожидается t
SELECT NULL::int4 == NULL::int4 AS null_eq;             -- ожидается t
\c postgres
DROP DATABASE t_mchar;
```

Если `CREATE EXTENSION mchar` отвечает ошибкой об отсутствии файла `mchar.control` — установлен «ванильный» PostgreSQL (или не установлен пакет `-contrib` сборки Postgres Professional). Текст ошибки зависит от версии сервера:

```text
-- современные версии (14–18):
ERROR:  extension "mchar" is not available
DETAIL:  Could not open extension control file "/usr/share/postgresql/17/extension/mchar.control": No such file or directory.
HINT:  The extension must first be installed on the system where PostgreSQL is running.

-- старые версии (до 12 включительно):
ERROR:  could not open extension control file "/usr/share/postgresql/12/extension/mchar.control": No such file or directory
```

(⚠ точная граница версий, на которой изменился текст сообщения, не перепроверена по исходникам; смысл в обоих случаях один — файла расширения в этой сборке нет.)

### 1.4. Что изменилось в последних версиях платформы; «ванильный» PostgreSQL

Что подтверждено официальными источниками на 10.10.2026:

- **Список поддерживаемых СУБД 1С** (страница «Список поддерживаемых СУБД» на v8.1c.ru, упоминает файл «PostgresPRO_07_2026.pdf», то есть обновлялась в июле 2026) перечисляет только сборки с патчем/расширениями 1С и производные коммерческие СУБД. Пункта «PostgreSQL (без патчей)» там **нет**. **[офиц.]**
- В списке изменений платформы (V8Update) для версий 8.3.22–8.5.4 при просмотре не найдено записей об отказе от `mchar` или о поддержке немодифицированного PostgreSQL. (Просмотр выполнялся автоматически по фрагментам большого документа, поэтому не является исчерпывающим.)
- **Повторная проверка при рецензии 10.10.2026:** V8Update 8.5.4.1306 (разделы 8.5.4, 8.5.1, 8.3.27–8.3.22) и V8Update 8.3.22.1709 (разделы 8.3.22–8.3.15) просмотрены целиком, всеми фрагментами, с поиском по словам `mchar`, «без патч», «ванильн», `scram`, `libpq`. Ни одной записи о поддержке PostgreSQL без патча от 1С или без `mchar` нет. Во всех записях о расширении списка СУБД фигурируют только «PostgreSQL» (под которым 1С понимает собственную сборку — см. формулировку «PostgreSQL с патчем от 1С» в списке СУБД) и «Postgres Pro» (1С / Standard / Enterprise / CERT). В планах версий 8.5.5 и 8.5.6 («Заметки из Зазеркалья», записи июля–октября 2026) PostgreSQL без патчей тоже не упоминается.
- **Платформа 8.5.4 [офиц., «Новое в платформе 8.5.4»]:**
  - 1С собрала отдельные дистрибутивы PostgreSQL с патчем от 1С для всех поддерживаемых ОС и архитектур; они публикуются в двух вариантах — пакетами и архивом (архивы предназначены для закрытых контуров корпоративных клиентов);
  - при первоначальной установке сборки от 1С оптимальные параметры конфигурации PostgreSQL выставляются автоматически;
  - разработано расширение `auto_dump` для сборки от 1С;
  - таблицы базы можно размещать **в произвольной схеме** PostgreSQL (раньше — только `public`): поле «Схема БД» в свойствах информационной базы, параметр `--db-schema` у `rac`, `ibsrv`, `ibcmd`, параметр `DBSchema` у `CREATEINFOBASE`;
  - нагрузочный тест «1С:ERP» на 30 000 одновременно работающих пользователей выполнен именно на PostgreSQL с патчем от 1С под Linux.
- **Платформа 8.5.5 (анонс от 30.06.2026, «Заметки из Зазеркалья») [офиц.]:** планируется встроенный «Сервис обслуживания баз данных» (DBMaintenanceService) для PostgreSQL с окнами обслуживания; на 10.10.2026 версия 8.5.5 анонсирована, сведений о финальном выпуске не найдено.
- **Платформа 8.3.25 [офиц.]:** механизм обновления копии базы данных версии 2 для PostgreSQL ≥ 10; требуется `wal_level=logical`, а сама СУБД должна быть установлена или обновлена из дистрибутива 1С (модуль `dbcopies_decoding`).
- **Платформа 8.3.23 [офиц.]:** управление табличными пространствами базы в клиент-серверном варианте.

Вывод для администратора:

- **Официальной поддержки «ванильного» PostgreSQL нет (состояние на 10.10.2026).** Утверждения из сети о том, что «новая платформа 1С работает на ванильном PostgreSQL без патчей», официальными источниками 1С не подтверждаются: такого пункта нет ни в «Списке поддерживаемых СУБД», ни в списках изменений платформы 8.3.15–8.5.4 (проверено дважды, независимо). До появления такого пункта в «Списке поддерживаемых СУБД» считайте, что `mchar`, `fulleq` и `fasttrun` обязательны. **Уточнено 10.10.2026** (полный текст документации 8.3.27, «Клиент-серверный вариант», разд. 3.2.5): оговорки о работе без патча там нет — документация требует модифицированную сборку PostgreSQL, выпущенную фирмой «1С» (конспект — `../its-docs/cs-gl03-ustanovka-komponentov-p2.md`). Ранее было отмечено: Единственное, что не прочитано, — закрытая документация платформы на ИТС (раздел об особенностях работы с PostgreSQL); если там появится оговорка о работе без патча, её нужно внести сюда.
- Сборку «PostgreSQL для 1С» от Postgres Professional сам вендор описывает как сборку **ванильного PostgreSQL с патчами и расширениями** для совместимости с 1С — то есть это апстрим-ядро плюс 1С-модули, а не Postgres Pro Standard. В обиходе именно её иногда называют «ванильной для 1С», отсюда путаница.
- Теоретически расширения `mchar`/`fulleq`/`fasttrun` можно собрать из исходников под апстрим-пакеты PGDG. Это **[практика]** энтузиастов, без поддержки 1С и вендоров; для рабочих баз не использовать.

### 2.2. (1) Сборка PostgreSQL от фирмы «1С»

**Статус [офиц.]:** в списке поддерживаемых СУБД — «PostgreSQL с патчем от 1С» версий `18.4-1.1C`, `17.10-2.1C`, `16.14-1.1C`, `15.18-1.1C`, `14.23-1.1C` (x86-64, ARM, «Эльбрус»); для x86 (32 бита) — только `10.22-1.1C`. Формат версии: `<версия PostgreSQL>-<номер сборки>.1C`.

**Поддерживаемые ОС сборки [офиц., «Список ОС для поддерживаемых СУБД»]:** Ubuntu 20.04, 22.04, 24.04, **26.04**; Debian 9–13; Astra Linux SE 1.7/1.8, CE 2.12; Альт 9/10; РЕД ОС 7.3/8.0; CentOS 7/9; Oracle Linux 9; Windows 7–11, Windows Server 2012–2025 и др.

**Где скачать [офиц.]:** `https://releases.1c.ru/version_files?nick=AddCompPostgre&ver=18.4-1.1C` (номер версии в параметре `ver`). Страница требует входа через `login.1c.ru` — нужна учётная запись с действующим договором сопровождения (ИТС).

**Что внутри:**

- Начиная с 2025–2026 гг. 1С публикует **отдельные дистрибутивы под каждую ОС** в двух видах — пакеты и архив **[офиц.]**. Название файла на портале имеет вид «Дистрибутив СУБД PostgreSQL для Debian 13.0 x86 (64-bit) одним архивом» (формулировка из официального репозитория `1C-Company/docker_fresh`); для Ubuntu, соответственно, выбирайте строку со своей версией Ubuntu.
- Имя архива соответствует маске `postgresql_*.tar.bz2` **[офиц., тот же репозиторий: `images/db/Dockerfile`, команда `tar -xf /tmp/distr_full/postgresql_*.tar.bz2 -C /tmp/pgsql`]**. В том же репозитории (`components_config.py`) зафиксированы nick `AddCompPostgre` и пример номера версии сборки — `18.3-5.1C` (то есть у одной версии PostgreSQL бывает несколько пересборок 1С: `-1.1C` … `-5.1C`). ⚠ не подтверждено: точное имя файла, по исторической схеме — `postgresql_17.10_2.1C_amd64_deb.tar.bz2`; в старых выпусках (до ~12-й версии) рядом лежал архив `…_addon_deb.tar.bz2` с `postgresql-common` и вспомогательными пакетами. В статье 2019 г. о сборке 10.9-5.1C дистрибутив на портале назывался «Дистрибутив СУБД PostgreSQL для Linux x86 (64-bit) одним архивом (DEB)» — то есть раньше архив был один на все deb-дистрибутивы, а теперь отдельный на каждую ОС.
- Внутри — deb-пакеты с **дебиановскими именами**: `libpq5_<версия>.1C_amd64.deb`, `postgresql-client-NN_<версия>.1C_amd64.deb`, `postgresql-NN_<версия>.1C_amd64.deb` (в статьях сообщества для версий 10–15 фигурируют именно эти три пакета **[практика]**; ⚠ состав для 17–18 не проверен — могут добавиться `-dbgsym`, `postgresql-common` и др.).
- Раскладка каталогов — как у пакетов Debian/Ubuntu (`postgresql-common`): программы `/usr/lib/postgresql/NN/bin` **[офиц., Dockerfile 1C-Company]**, конфигурация `/etc/postgresql/NN/main/`, данные `/var/lib/postgresql/NN/main/`, журнал `/var/log/postgresql/postgresql-NN-main.log`, служба `postgresql@NN-main.service` (плюс «зонтичная» `postgresql.service`).

**Особенности:**

- Пакеты называются так же, как в репозиториях Ubuntu и PGDG — отсюда главный риск подмены при `apt upgrade` (раздел 6.5).
- Сборка линкуется с конкретными версиями системных библиотек (`libicuNN`, `libssl`, `libllvmNN`). Пока ставится дистрибутив, собранный **именно под вашу версию Ubuntu**, зависимости закрываются штатным репозиторием. Проблемы возникают, когда ставят «общий» архив прошлых лет на более новую Ubuntu (раздел 6.3).
- В описании механизма копий баз данных (платформа 8.3.25) 1С требует СУБД, установленную или обновлённую из своего дистрибутива. Модуль `dbcopies_decoding` есть также в Postgres Pro и Tantor (в «PostgreSQL для 1С» 16 — в пакете `postgrespro-1c-16-contrib`). Однако «Руководство разработчика» 8.3.27, гл. 26.2, прямо требует СУБД из дистрибутива 1С: со сборкой из другого источника «Версия 2» не используется, работает «Версия 1» (конспект `../its-docs/dev-gl26-kopii-bazy-dannyh.md`; уточнено 19.10.2026). Применимость к своей сборке уточнять у 1С.
- **PostgreSQL 16.15 и новее (13.08.2026, CVE-2026-6471):** модули вывода логического декодирования ограничены списком из нового параметра `output_plugin_libraries`. По умолчанию в нём только `pgoutput` и `test_decoding` [PG, примечания к выпуску 16.15]. Когда выйдет «PostgreSQL для 1С» на этой основе, `dbcopies_decoding` нужно будет добавить в список, иначе копии БД перестанут обновляться. На 19.10.2026 в репозитории сборки последний выпуск — 16.14, ограничения ещё нет.
- При первой установке параметры `postgresql.conf` выставляются автоматически по объёму ОЗУ и числу ядер (с выпусков 2026 г.) **[офиц.]**.

### 2.3. (2) «PostgreSQL для 1С» от Postgres Professional

Раньше продукт назывался «Postgres Pro 1C»; пакеты до сих пор называются `postgrespro-1c-NN`, а репозиторий и установщики — `postgresql-1c-NN`.

**Статус и лицензия [офиц., 1c.postgres.ru]:**

- Это сборки ванильного PostgreSQL с патчами и расширениями для совместимости с 1С; это **не Postgres Pro**, и в реестр российского ПО они не входят.
- Бесплатно можно использовать для любых целей, за двумя исключениями: предоставление СУБД как услуги (DBaaS) и встраивание в собственные продукты.
- Без гарантий и техподдержки; обновления могут отставать от основных веток PostgreSQL и Postgres Pro.
- **Позиционирование самим вендором:** сборка рекомендуется для ИП, малого бизнеса, тестовых и непроизводственных сред — «единицы и десятки пользователей, типовые сценарии»; для сотен и тысяч пользователей вендор предлагает коммерческий Postgres Pro Enterprise для 1С (поддержка 24×7, встроенный отказоустойчивый кластер BiHA, Postgres Pro Backup Enterprise, реестр российского ПО №104, сертификат ФСТЭК). Технического ограничения на число пользователей в бесплатной сборке нет — это маркетинговая рекомендация, но её стоит знать, принимая решение для крупной базы.
- Параметры конфигурации автоматически подбираются под характеристики машины.
- В отличие от сборки от 1С, не требует ручной доустановки системных зависимостей.
- Только 64-битные Windows и Linux. Контакт: `1c@postgrespro.ru`.

- **Установка:** репозиторий по ключу доступа из личного кабинета:
  ```bash
  wget --user access_key --password='' https://repo.postgrespro.ru/std/std-17/keys/pgpro-repo-add.sh
  sudo sh pgpro-repo-add.sh
  sudo apt-get install postgrespro-std-17
  ```
  Каталоги: `/opt/pgpro/std-17`, `/var/lib/pgpro/std-17/data`, служба `postgrespro-std-17`. Для Enterprise — `ent-17` (⚠ по аналогии, не проверено по документации Enterprise).
- **Пресет 1С** после установки Standard/Enterprise: утилита `pgpro_tune` с пресетом `1c` (файл `1c.tune`), затем перезагрузка конфигурации или перезапуск сервера:
  ```bash
  sudo -u postgres /opt/pgpro/std-17/bin/pgpro_tune --show          # список доступных пресетов
  sudo -u postgres /opt/pgpro/std-17/bin/pgpro_tune -D /var/lib/pgpro/std-17/data -P 1c
  sudo systemctl restart postgrespro-std-17
  ```
  По умолчанию `initdb` в Postgres Pro сам запускает `pgpro_tune` (отключается `--no-tune` или переменной окружения `PGPRO_TUNE=disable`, параметры передаются через `--tune=...`). Изменения дописываются отдельным блоком в конец `postgresql.conf`.

  Справка по `pgpro_tune` **[офиц., документация Postgres Pro 17]**: синтаксис `pgpro_tune [параметр...] [-D | --pgdata] каталог имя_пресета`; ключи `-D`/`--pgdata=` (каталог кластера), `-P`/`--preset=` (имя пресета; можно несколько, применяются по порядку), `-O`/`--options=` (параметры пресета), `--default-options=`, `--no-default` (не применять `default.tune`), `--preset-dir=` (каталог пресетов, по умолчанию `share`), `--config-file=`, `--set имя=значение`, `--show` (список пресетов). Штатные пресеты: `default.tune` (применяется первым), `1c.tune` (параметры для 1С; часть требует модуля `plantuner`), `extensions.tune`, `regress.tune`. После ручного запуска нужен `pg_reload_conf()` или перезапуск — в зависимости от изменённых параметров.

  Получение скрипта репозитория для коммерческих редакций **[офиц.]**: ключ доступа берётся в личном кабинете портала поддержки («Администрирование → Набор лицензий → Репозитории», виден только администраторам набора лицензий); в примере документации имя пользователя — `access_key`, пароль пустой (по смыслу вместо `access_key` подставляется ваш ключ; прямо это в документации не оговорено — ⚠ сверяйтесь с инструкцией в личном кабинете); сам `pgpro-repo-add.sh` при запуске от root запросит реквизиты и, если они не введены или неверны, предложит подключить репозиторий без них (тогда их придётся прописать вручную). Для загрузки нужен `wget`; SOCKS5-прокси не поддерживается.

### 2.6. (5) «Ванильный» PostgreSQL из Ubuntu или PGDG — когда допустим

- **Для баз 1С — нет** (нет `mchar`/`fulleq`/`fasttrun`, нет в списке СУБД 1С).
- **Допустим на том же сервере для других приложений** (Zabbix, веб-сервисы и т. п.) — при соблюдении правил сосуществования (раздел 9).
- **Версии в стандартных репозиториях Ubuntu:** 22.04 — PostgreSQL 14; 24.04 — PostgreSQL 16; 26.04 — PostgreSQL 18 (метапакет `postgresql 18+290ubuntu1`).
- **PGDG (apt.postgresql.org) [офиц., wiki.postgresql.org/wiki/Apt, проверено 10.10.2026]:** поддерживаются Ubuntu `jammy` (22.04), `noble` (24.04), `resolute` (26.04), `stonking` (26.10, только amd64); версии PostgreSQL 13–18, 19 beta и 20 devel. Файл источника при ручной настройке — `/etc/apt/sources.list.d/pgdg.sources`, ключ — `/usr/share/postgresql-common/pgdg/apt.postgresql.org.asc`, набор — `<кодовое_имя>-pgdg`.
  ```bash
  sudo apt install -y postgresql-common ca-certificates
  sudo /usr/share/postgresql-common/pgdg/apt.postgresql.org.sh
  sudo apt install postgresql-18
  ```
- **Опасность:** репозиторий PGDG содержит пакеты `postgresql-17`, `libpq5` и т. д. с более свежими минорными версиями. Если на сервере стоит сборка от 1С (те же имена пакетов) и подключён PGDG, первое же `apt upgrade` заменит 1С-сборку «ванильной». Не подключайте PGDG на сервере со сборкой 1С либо жёстко фиксируйте пакеты (раздел 6.5).

Например, PostgreSQL 15.1 «с 8.3.18» записан в «изменениях после публикации» 8.3.22, а Postgres Pro 16.2 «с 8.3.22» — в разделе 8.3.25. Первые сборки ветки (условно 8.3.18.1208 образца 2020 г.) о более поздних СУБД «знать» не могут. Практическое правило: на сервере должна стоять **последняя сборка своей ветки платформы**, и чем новее СУБД, тем новее должна быть платформа; при сомнении сверяйтесь с V8Update именно вашей сборки (`https://dl03.1c.ru/content/Platform/<версия_через_подчёркивания>/1cv8upd_<версия>.htm`).
- Точные записи V8Update, перепроверенные при рецензии **[офиц.]**: «Прекращена поддержка СУБД PostgreSQL версий до 9.6 включительно» (8.5.1); Postgres Pro 1С 16.10, 16.11, 17.6, 17.7 — «начиная с 8.3.22», 18.1 (Standard/Enterprise 18.1.1) — «начиная с 8.3.27», 13.22–15.15 — «начиная с 8.3.18» (все три записи — в разделе 8.5.1); Postgres Pro 1С 17.0 и 16.6/17.2 — «начиная с 8.3.22» (раздел 8.3.26); Postgres Pro 16.2 / 16.3 / 16.4 — «начиная с 8.3.22» (раздел 8.3.25); Postgres Pro 11.19–11.22 — «начиная с 8.3.17»; PostgreSQL 10.19–10.23, 11.14–11.19 — «начиная с 8.3.14», 12.9–12.14, 13.5–13.10, 14.1–14.6, 15.1 — «начиная с 8.3.18» (раздел 8.3.22). По списку изменений 8.3.22.1709: запись «Реализована поддержка СУБД PostgreSQL версии 12 (x86-64)» стоит в разделе 8.3.18, «…версии 13 (x86-64)» — в разделе 8.3.20 (то есть на практике 13-я версия появилась в поддерживаемых в период 8.3.20, хотя для выпусков 13.4+ указано «начиная с 8.3.18»); в 8.3.16 изменена структура базы данных, чтобы стала возможной поддержка PostgreSQL 12. Поддержка Ubuntu 22.04 LTS добавлена в изменениях после публикации 8.3.22, Ubuntu 24.04 LTS (x86, x86-64, ARM64) — в 8.3.24; в 8.3.24 же прекращена поддержка Ubuntu 18.04 LTS.

5. Коммерческие Postgres Pro Standard/Enterprise или Tantor SE 1C — когда нужны поддержка вендора, реестр российского ПО, сертификация, отказоустойчивый кластер.

## 4. Подготовка ОС перед установкой

### 4.1. Локаль `ru_RU.UTF-8` — до создания кластера

Локаль кластера фиксируется в момент `initdb` (в пакетной установке — в момент установки серверного пакета/метапакета). Если русской локали в системе нет или сеанс установки работает в `C`/`en_US`, кластер получится «не тот», и база 1С не создастся.

```bash
# 1. Что есть сейчас
locale -a | grep -iE 'ru_RU|en_US'      # ожидается ru_RU.utf8 (и желательно en_US.utf8)
locale                                   # текущие LANG / LC_*
cat /etc/default/locale                  # системная локаль по умолчанию

# 2. Сгенерировать локали (пакет locales в Ubuntu Server установлен по умолчанию)
sudo locale-gen ru_RU.UTF-8 en_US.UTF-8

# 3. Сделать ru_RU.UTF-8 системной локалью по умолчанию
sudo update-locale LANG=ru_RU.UTF-8
#    эквивалент: sudo localectl set-locale LANG=ru_RU.UTF-8

# 4. Перелогиниться (или перезагрузиться) и проверить
locale | grep LANG                       # LANG=ru_RU.UTF-8
locale -a | grep -i ru_RU                # ru_RU.utf8
```

Пояснения:

- `locale-gen <имя>` — компилирует локаль; `locale -a` — список скомпилированных локалей (в выводе имя выглядит как `ru_RU.utf8` — это то же самое, что `ru_RU.UTF-8`).
- `update-locale LANG=…` — записывает значение в `/etc/default/locale`; действует на новые сеансы.
- Низкоуровневая альтернатива `locale-gen` — `localedef`; именно так локаль создаётся в официальном Dockerfile 1С для образа с PostgreSQL **[офиц., `1C-Company/docker_fresh`]**: `localedef -i ru_RU -c -f UTF-8 -A /usr/share/locale/locale.alias ru_RU.UTF-8`, после чего задаётся `LANG=ru_RU.UTF-8` и выполняется `initdb` без дополнительных ключей. На обычном сервере Ubuntu используйте `locale-gen` — он делает то же самое и запоминает локаль в списке генерируемых (в актуальных выпусках Ubuntu это `/etc/locale.gen`), так что она переживёт обновление пакета `locales`.
- Интерактивная альтернатива: `sudo dpkg-reconfigure locales` (отметить `ru_RU.UTF-8 UTF-8` и `en_US.UTF-8 UTF-8`, выбрать локаль по умолчанию) — именно её приводит документация Postgres Pro (приложение K.1) **[офиц.]**.
- Системную локаль менять на русскую не обязательно — достаточно, чтобы локаль была **сгенерирована**, а при создании кластера была указана явно (`LANG=ru_RU.UTF-8` в окружении команды или `--locale=ru_RU.UTF-8`). Но сделать её системной надёжнее: пакетные скрипты берут локаль из окружения.
- Если сообщения на русском в консоли мешают, оставьте `LANG=ru_RU.UTF-8` и задайте `LC_MESSAGES=C.UTF-8`: `sudo update-locale LANG=ru_RU.UTF-8 LC_MESSAGES=C.UTF-8`. Учтите: `pg-setup initdb` игнорирует `LC_*` и берёт только `LANG` **[офиц.]**.
- **Что делает `pg-setup`, если локаль сеанса не UTF-8** (по тексту скрипта из пакета `postgrespro-1c-16-server` 16.14-1.noble, прочитан 11.10.2026): при локали `C`, `POSIX` или `C.UTF-8` (частое умолчание Ubuntu Server) скрипт сначала берёт локаль входа пользователя, вызвавшего `sudo`, а если и она не годится — перебирает список `ru_RU.UTF-8`, `en_US.UTF-8`, `kk_KZ.UTF-8`, `tr_TR.UTF-8` и использует первую сгенерированную; не найдя ни одной UTF-8-локали, завершается с ошибкой `No suitable locale found`. То есть кластер в `SQL_ASCII` через `pg-setup` не получится, но при сгенерированной русской локали и «никакой» локали сеанса он станет русским, даже если нужен английский. Полный порядок — `../guides/07-postgresql-dlya-1c-s-1c-postgres-ru.md`, раздел 7.

### 4.2. Требования 1С к локали и кодировке кластера/базы

- **Кодировка базы — `UTF8`.**
- **`lc_collate` и `lc_ctype` базы должны соответствовать языку информационной базы**; для русскоязычных баз это `ru_RU.UTF-8`. Требование Postgres Pro **[офиц., приложение K.1]**: русская локаль `ru_RU.UTF-8` должна быть установлена в системе и быть активной для пользователя, создающего кластер; пример из документации (для Debian):
  ```bash
  sudo dpkg-reconfigure locales
  export LANG="ru_RU.UTF-8"
  /opt/pgpro/std-17/bin/pg-setup initdb
  ```
- Платформа при создании информационной базы сама выполняет `CREATE DATABASE` с кодировкой `UTF8` и локалью, соответствующей выбранному «Языку (стране)» базы. Если шаблонная база кластера (`template1`) имеет другую кодировку/сортировку, PostgreSQL отклоняет команду с ошибками `new encoding (UTF8) is incompatible…` / `new collation (ru_RU.UTF-8) is incompatible with the collation of the template database (en_US.UTF-8)` **[практика; точный текст SQL, который формирует платформа, ⚠ не подтверждён]**. Поэтому кластер должен быть создан сразу в `ru_RU.UTF-8`.
- Локаль базы после создания изменить нельзя; локаль кластера — только пересозданием кластера (`initdb` в пустой каталог).
- **Нерусские конфигурации.** Всё сказанное про `ru_RU.UTF-8` относится к русскоязычным базам. Для международных конфигураций (линейка WE), где «Язык (страна)» базы — английский, кластер создают в `en_US.UTF-8`: так предписывает рабочая инструкция пользователя этой базы знаний («иначе конфигурация WE не загрузится»; по первоисточнику причина не проверялась, но она согласуется с правилом «локаль кластера = локаль базы»). Во всех командах этой статьи в таком случае `ru_RU.UTF-8` заменяется на `en_US.UTF-8`. Сверка инструкции — `../guides/07-postgresql-dlya-1c-s-1c-postgres-ru.md`.

**Провайдер сортировки (libc или ICU):**

| Сборка | Провайдер по умолчанию при `initdb` |
|---|---|
| Апстрим PostgreSQL 15–18, PGDG, пакеты Ubuntu | `libc` **[офиц.]** |
| Postgres Pro Standard 17 | выбирается автоматически: для локалей `C`/`POSIX` — `libc`, для остальных — **`icu`** **[офиц., описание `initdb` в документации Postgres Pro]** |
| «PostgreSQL для 1С» (бесплатная сборка Postgres Professional) | `libc` — Уточнено 11.10.2026: открытая документация именно на эту сборку есть (`https://repo.postgrespro.ru/doc/pg1c/<версия>/ru/html/`), и на странице `initdb` версий 16 и 18 сказано: «по умолчанию initdb использует провайдер локали libc», ICU включается ключом `--locale-provider=icu` **[офиц.]**. Приложение K.1 провайдер не упоминает. Фактическое значение на сервере — запросом ниже |
| Сборка от 1С | ⚠ не подтверждено (нет открытой документации); в официальном Dockerfile 1С кластер создаётся `initdb` без ключей при `LANG=ru_RU.UTF-8` — то есть 1С полагается на умолчания своей сборки; проверить запросом ниже |

```sql
-- PostgreSQL 17–18: провайдер (c = libc, i = icu, b = builtin), локали и кодировка всех баз
SELECT datname, pg_encoding_to_char(encoding) AS enc, datlocprovider,
       datcollate, datctype, datlocale
FROM pg_database ORDER BY 1;
-- PostgreSQL 15–16: вместо datlocale столбец называется daticulocale
```

Что важно знать:

- Типы `mchar`/`mvarchar`, в которых 1С хранит строки, **всегда** сравниваются средствами ICU, независимо от провайдера базы **[офиц.]** — поэтому на логику 1С выбор провайдера влияет слабо.
- Оба провайдера работоспособны для 1С **[практика]**. Не меняйте то, что создал штатный установщик сборки, и не задавайте `--locale-provider` вручную без необходимости. **Уточнено 10.10.2026** (полный текст документации 8.3.27, разд. 3.2.5): требования к провайдеру сортировки в документации нет — она требует только кодировку UTF-8 при инициализации кластера и задаёт локаль переменной `LANG=ru_RU.utf-8`. Ранее было отмечено: Официальное требование 1С к провайдеру найти не удалось (документация платформы на ИТС закрыта).
- Правила сортировки зависят от версии системной библиотеки (glibc для `libc`, libicu для `icu`). При обновлении выпуска Ubuntu (22.04 → 24.04 → 26.04) версии меняются; PostgreSQL выдаст предупреждение `collation version mismatch` — потребуется `REINDEX` и `ALTER DATABASE … REFRESH COLLATION VERSION` (см. «Типичные ошибки»).
- В PostgreSQL 16 и новее параметров `lc_collate` и `lc_ctype` в `SHOW` больше нет — смотрите `pg_database` или `\l` в `psql`.

### 4.3. Контрольные суммы страниц данных

Контрольные суммы позволяют обнаружить «тихую» порчу данных диском/контроллером. Цена — несколько процентов производительности.

| Сборка / версия | По умолчанию |
|---|---|
| Postgres Pro, «PostgreSQL для 1С» (через `pg-setup initdb`) | **включены** (так по умолчанию инициализирует кластер `pg-setup`), отключение — `--no-data-checksums` **[офиц.]** |
| Апстрим PostgreSQL 18 | **включены**, отключение — `--no-data-checksums` **[офиц., release notes 18]** |
| Апстрим PostgreSQL 14–17, пакеты Debian/Ubuntu | выключены; включение — `initdb --data-checksums` (`-k`) **[офиц.]** |
| Сборка от 1С 14–17 | ⚠ не подтверждено: предположительно как в апстриме (выключены), но автоматически создаваемый установщиком кластер мог быть создан с иными параметрами — проверяйте `SHOW data_checksums;` сразу после установки. В официальном Dockerfile 1С кластер создаётся командой `initdb` вообще без ключей (то есть с умолчаниями сборки) |

```bash
# проверить на работающем сервере
sudo -u postgres psql -Atc "SHOW data_checksums;"          # on / off

# включить на существующем кластере (только при ОСТАНОВЛЕННОМ сервере; время ~ объёму данных)
sudo systemctl stop postgresql@17-main
sudo -u postgres /usr/lib/postgresql/17/bin/pg_checksums --enable --progress -D /var/lib/postgresql/17/main
sudo systemctl start postgresql@17-main
```

`pg_upgrade` требует одинаковой настройки контрольных сумм в старом и новом кластере — учитывайте при переходе на 18-ю версию, где они включены по умолчанию.

### 4.4. Параметры `initdb`, которые имеют значение

| Параметр | Что делает | Значение для 1С |
|---|---|---|
| `-D каталог`, `--pgdata=` | каталог данных кластера | каталог должен быть пуст и принадлежать `postgres` |
| `--locale=ЛОКАЛЬ` | локаль кластера по умолчанию (все категории) | `ru_RU.UTF-8` |
| `--lc-collate=`, `--lc-ctype=` | то же, но для отдельных категорий | обычно не нужны, достаточно `--locale` |
| `-E`, `--encoding=` | кодировка шаблонных баз | `UTF8` (выводится из локали автоматически) |
| `--locale-provider={builtin\|libc\|icu}` | провайдер локали (PostgreSQL 15+; `builtin` — с 17) | не указывать, оставить по умолчанию сборки |
| `--icu-locale=` | локаль ICU при провайдере `icu` | по умолчанию берётся из `--locale` |
| `-k`, `--data-checksums` / `--no-data-checksums` | контрольные суммы | включить |
| `--auth-local=`, `--auth-host=`, `-A` | методы аутентификации, записываемые в `pg_hba.conf` | `peer` для сокета, `scram-sha-256` (или `md5`) для TCP; не оставлять `trust` |
| `-W`, `--pwprompt`, `--pwfile=файл` | пароль суперпользователя при инициализации | удобно задать сразу |
| `-X каталог`, `--waldir=` | вынести WAL на отдельный диск | по необходимости |
| `-U имя` | имя суперпользователя | оставить `postgres` |
| `--tune=параметры`, `--no-tune` | только Postgres Pro: управление автонастройкой `pgpro_tune` | по умолчанию автонастройка включена |

Пример ручной инициализации (второй кластер сборки Postgres Professional):

```bash
sudo install -d -o postgres -g postgres -m 700 /var/lib/pgpro/1c-17/data2
sudo -u postgres /opt/pgpro/1c-17/bin/initdb -D /var/lib/pgpro/1c-17/data2 \
     --locale=ru_RU.UTF-8 --encoding=UTF8 --data-checksums \
     --auth-local=peer --auth-host=scram-sha-256
```


## 5. Установка варианта (2): «PostgreSQL для 1С» от Postgres Professional

Команды одинаковы для Ubuntu 22.04, 24.04 и 26.04 (скрипт сам подставляет кодовое имя выпуска). В примерах — ветка 17; для другой версии замените `17` на `14`/`15`/`16`/`18` (для 26.04 доступны только 17 и 18).

### 5.1. Быстрая установка — если это единственный PostgreSQL на машине

```bash
# 0. Локаль — раздел 4.1 (обязательно ДО установки)
locale -a | grep -i ru_RU || { sudo locale-gen ru_RU.UTF-8; sudo update-locale LANG=ru_RU.UTF-8; }

# 1. Подключить репозиторий официальным скриптом
cd /tmp
wget https://repo.postgrespro.ru/1c/1c-17/keys/pgpro-repo-add.sh
less pgpro-repo-add.sh                     # любой скрипт перед запуском от root стоит просмотреть
sudo sh pgpro-repo-add.sh

# 2. Убедиться, что репозиторий подключён и пакет виден
cat /etc/apt/sources.list.d/postgresql-1c-17.list
apt-cache policy postgrespro-1c-17

# 3. Посмотреть, что apt собирается сделать (нет ли в списке REMOVED чужих пакетов)
apt-get -s install postgrespro-1c-17 | grep -E '^(Inst|Remv)'

# 4. Установить (LANG передаём явно — от него зависит локаль создаваемого кластера)
sudo LANG=ru_RU.UTF-8 apt-get install -y postgrespro-1c-17

# 5. Проверить
systemctl status postgrespro-1c-17 --no-pager
```

Что делает скрипт `pgpro-repo-add.sh` **[офиц., текст скрипта]**:

- требует запуска от root, читает `/etc/os-release`, проверяет доступность репозитория через `wget` (логин и пароль спрашивает только для закрытых репозиториев — репозиторий `1c` открыт);
- при необходимости ставит `apt-transport-https`;
- кладёт ключ в `/etc/apt/trusted.gpg.d/postgrespro.gpg`;
- создаёт `/etc/apt/sources.list.d/postgresql-1c-17.list` со строкой вида `deb https://repo.postgres.ru/1c/1c-17/ubuntu noble main` (внутри скрипта и в `meta.json` используется имя узла `repo.postgres.ru` — это штатно; сам скрипт скачивался с `repo.postgrespro.ru`);
- выполняет `apt-get update`;
- для неподдерживаемого дистрибутива завершается с ошибкой `Unsupported distribution`; 32-битные системы не поддерживаются.

Уточнения по тексту скрипта (перепроверено 10.10.2026) **[офиц.]**:

- переменные в начале скрипта: `REPO="https://repo.postgres.ru/1c/1c-17"`, `PRODUCT_NAME="Postgresql for 1C 17"`, `LISTNAME="postgresql-1c-17"`; кодовое имя выпуска берётся из `VERSION_CODENAME` файла `/etc/os-release`, жёсткого списка выпусков Ubuntu в скрипте нет — он проверяет наличие `…/ubuntu/dists/<кодовое_имя>/main/binary-<arch>/Release` в репозитории;
- если такого каталога нет, скрипт завершается с сообщением вида `Version <VERSION_ID> of <NAME> distribution is not supported for architecture <ARCH>`;
- **если файл `/etc/apt/sources.list.d/postgresql-1c-17.list` уже существует, скрипт завершается с ошибкой** (код 2) и просит сначала удалить файл — при повторном запуске: `sudo rm /etc/apt/sources.list.d/postgresql-1c-17.list`;
- для Ubuntu 26.04 в скрипт зашит отдельный (другой) блок GPG-ключа — используйте свежий скрипт, а не сохранённую старую копию;
- ключ сначала пишется во временный файл, затем (если существует каталог `/etc/apt/trusted.gpg.d`) преобразуется в `/etc/apt/trusted.gpg.d/postgrespro.gpg`;
- логин и пароль запрашиваются только когда проверка доступа возвращает «репозиторий защищён паролем» (для закрытых репозиториев Standard/Enterprise); реквизиты сохраняются в `/etc/apt/auth.conf.d/<узел>.conf` с правами 0600;
- если нет `wget`, проверка доступности пропускается (скрипт предупреждает и ждёт нажатия ENTER); при ошибке проверки сертификата советует установить `ca-certificates`;
- в `meta.json` репозитория официальная команда загрузки записана с узлом `repo.postgres.ru`: `wget https://repo.postgres.ru/1c/1c-17/keys/pgpro-repo-add.sh` — то есть штатно используются оба имени, `repo.postgres.ru` и `repo.postgrespro.ru` (Сверено 11.10.2026: файл `Release` ветки `1c-16` для `noble` и скрипт `pgpro-repo-add.sh` по адресам `repo.postgres.ru/1c/1c-16/…`, `repo.postgrespro.ru/1c/1c-16/…` и `repo.postgrespro.ru/1c-16/…` побайтно совпадают — одинаковые суммы MD5; короткого пути `repo.postgres.ru/1c-16/…` нет, ответ 404). **Практическое следствие:** apt после работы скрипта ходит на `repo.postgres.ru` — если исходящий доступ с сервера ограничен списком разрешённых узлов или прокси, разрешать нужно именно его (и `repo.postgrespro.ru` для загрузки самого скрипта).

Что делает метапакет `postgrespro-1c-17` **[офиц.]**:

- ставит `-server`, `-client`, `-contrib`, `-libs`;
- запускает `pg-setup` с параметрами по умолчанию: создаёт кластер в `/var/lib/pgpro/1c-17/data` (локаль — из `LANG`, контрольные суммы включены, `pg_hba.conf`: `peer` для локального сокета и `md5` для TCP), включает автозапуск, запускает службу;
- запускает `pg-wrapper links update` — программы (`psql`, `pg_dump`…) становятся доступны в `PATH`;
- параметры конфигурации выставляются автоматически под объём памяти и число ядер машины. Что именно записывают пресеты `default.tune` и `1c.tune` (в том числе `listen_addresses = '*'`, `work_mem = 512MB`, расчёт на NVMe), что обновление пакета само перезапускает сервер и что журнал сервера в `data/log` не очищается — разобрано по содержимому пакета в `../guides/07-postgresql-dlya-1c-s-1c-postgres-ru.md`, раздел 7.

Предупреждение из документации Postgres Pro **[офиц.]**: установка метапакета способна удалить уже имеющиеся на машине инсталляции Postgres Pro или PostgreSQL, поэтому его нельзя использовать для обновления, миграции или нескольких инсталляций на одной машине. Технически это следует из `Conflicts: postgresql-common` — пакет `postgresql-common` нужен дистрибутивному PostgreSQL и сборке от 1С, и apt удалит их вместе с ним.

### 5.2. Расширенная установка — рядом с другим PostgreSQL или с ручной инициализацией

Официальная инструкция из `meta.json` репозитория **[офиц.]**: ставится пакет `-contrib` (он тянет за собой `-server`, `-client`, `-libs`), метапакет не ставится, кластер создаётся вручную.

```bash
wget https://repo.postgrespro.ru/1c/1c-17/keys/pgpro-repo-add.sh
sudo sh pgpro-repo-add.sh

sudo apt-get install -y postgrespro-1c-17-contrib

# инициализация кластера (от root; сам pg-setup работает с БД от имени postgres)
sudo LANG=ru_RU.UTF-8 /opt/pgpro/1c-17/bin/pg-setup initdb

# если порт 5432 занят другим экземпляром — выбрать другой
sudo /opt/pgpro/1c-17/bin/pg-setup find-free-port
sudo /opt/pgpro/1c-17/bin/pg-setup set-server-port 5433

# автозапуск и запуск
sudo /opt/pgpro/1c-17/bin/pg-setup service enable
sudo /opt/pgpro/1c-17/bin/pg-setup service start

# (необязательно) ссылки на программы в PATH; при конфликте с другим PostgreSQL ссылки не создаются
sudo /opt/pgpro/1c-17/bin/pg-wrapper links update
```

Без `pg-wrapper` программы вызываются по полному пути: `/opt/pgpro/1c-17/bin/psql`, `/opt/pgpro/1c-17/bin/pg_dump` и т. д. Удобно добавить каталог в `PATH` пользователю `postgres`: строка `export PATH=/opt/pgpro/1c-17/bin:$PATH` в `~postgres/.profile`.

### 5.3. Справочник `pg-setup` и `pg-wrapper`

`pg-setup` — shell-скрипт из пакета `-server`, лежит в `/opt/pgpro/1c-NN/bin`. Запускается **от root** **[офиц., документация Postgres Pro, для 1С-сборки пути заменяются на `1c-NN`]**.

| Команда | Что делает |
|---|---|
| `pg-setup initdb [параметры_initdb]` | Создаёт кластер от имени `postgres`. По умолчанию: каталог `/var/lib/pgpro/1c-NN/data`, контрольные суммы включены, `auth-local = peer`, `auth-host = md5`, локаль из `LANG` (переменные `LC_*` игнорируются). Допускает обычные параметры `initdb` (например, `--no-data-checksums`, `--locale=ru_RU.UTF-8`). Путь к каталогу данных сохраняется в файле `/etc/default/postgrespro-…`. Конфигурация автоматически подбирается под «железо» в предположении, что на машине работает один сервер БД. |
| `pg-setup find-free-port` | Находит свободный порт. |
| `pg-setup set-server-port ПОРТ` | Задаёт порт сервера (по умолчанию 5432). |
| `pg-setup set ПАРАМЕТР ЗНАЧЕНИЕ` | Записывает параметр в `postgresql.conf`; если он был задан через `ALTER SYSTEM`, старое значение удаляется из `postgresql.auto.conf`. |
| `pg-setup service enable` / `disable` | Включает / выключает автозапуск. |
| `pg-setup service start` / `stop` | Запускает / останавливает службу. |
| `pg-setup service condrestart` | Перезапускает, только если служба работает. |
| `pg-setup service status` | Состояние службы. |

Ограничение: `pg-setup` управляет **только одним** кластером (тем, что записан в `/etc/default/…`).

Про «вариант конфигурации» (tune): по документации Postgres Pro конфигурация по умолчанию подбирается под устанавливаемый продукт, а для иной настройки предлагается аргумент `tune` команды `pg-setup initdb` — без перечисления допустимых значений. В старой документации встречалась форма `pg-setup initdb --tune=1c` — Уточнено 11.10.2026 по документации самой сборки «для 1С» (`https://repo.postgrespro.ru/doc/pg1c/16/ru/html/`, страницы `app-initdb`, `app-pgpro-tune`, приложение K.3; в версии 18 тексты те же): в актуальных версиях такого примера нет. При `initdb` по умолчанию выполняется `pgpro_tune` со стандартным пресетом `default.tune` (подбор под оборудование, редакцию и версию), а параметры, специфичные для 1С, вынесены в отдельный пресет `1c.tune`, о котором приложение K говорит «можно также использовать». Применён ли `1c.tune` при установке сборки «для 1С» автоматически, документация не уточняет. **По коду пакетов (разобраны 11.10.2026) — не применён:** скрипт установки метапакета `postgrespro-1c-16` вызывает `pg-setup initdb` без параметров, а `initdb` запускает `pgpro_tune` только с каталогом данных, то есть с одним стандартным пресетом `default.tune`. Значит, после быстрой установки параметры для 1С (`max_locks_per_transaction = 256`, `standard_conforming_strings = off`, `plantuner` и др.) нужно задать отдельно — порядок в `../guides/07-postgresql-dlya-1c-s-1c-postgres-ru.md`, раздел 3, шаг 7. Запуском это не проверялось; на сервере видно по блоку `pgpro_tune` в конце `postgresql.conf` (команды ниже).

Результат перепроверки 10.10.2026: в документации Postgres Pro Standard 13, 15, 17 и 18 синтаксис везде один — `pg-setup initdb [параметры_initdb]`; фраза «Аргумент `tune` выбирает вариант конфигурации базы данных» есть на странице установки (15, 17, 18), но **ни одного допустимого значения и ни одного примера с `--tune=1c` в этих версиях документации нет**. Документирован только ключ самого `initdb` — `--tune=параметры` (передаёт параметры утилите `pgpro_tune`) и `--no-tune`; поскольку `pg-setup initdb` пробрасывает параметры в `initdb`, форма `pg-setup initdb --tune=…` синтаксически допустима, но конкретное значение `1c` остаётся неподтверждённым. Уточнено 11.10.2026: в документации самой бесплатной сборки (`https://repo.postgrespro.ru/doc/pg1c/16/ru/html/app-pgpro-tune.html`, то же в версии 18) утилита `pgpro_tune` и пресеты `default.tune`, `regress.tune`, `1c.tune`, `extensions.tune` описаны — то есть в сборке «для 1С» они предусмотрены; документированный способ применить пресет — `pgpro_tune -D <каталог данных> --no-default -P /opt/pgpro/1c-NN/share/1c.tune` с последующим перезапуском (путь к пресету — полный, как в примере документации; конспект — `../guides/07-postgresql-dlya-1c-s-1c-postgres-ru.md`). По строкам двоичных файлов пакета: `initdb` подставляет содержимое `--tune` в вызов `pgpro_tune` как есть, а в `pgpro_tune` есть шаблон имени `%s.tune` — поэтому `--tune=1c`, вероятно, по-прежнему означает «выполнить ещё и `1c.tune`», но запуском это не подтверждено. Убедиться на установленном сервере:

```bash
ls /opt/pgpro/1c-17/bin/ | grep -i tune                 # есть ли утилита pgpro_tune
ls /opt/pgpro/1c-17/share/ | grep -i '\.tune$'          # какие пресеты поставляются
sudo -u postgres /opt/pgpro/1c-17/bin/pgpro_tune --show # список пресетов (если утилита есть)
tail -n 60 /var/lib/pgpro/1c-17/data/postgresql.conf    # блок, дописанный автонастройкой при initdb
```

Ещё два факта из документации **[офиц.]**: при расширенной установке (без метапакета) автозапуск сервера по умолчанию **выключен** («чтобы вы могли вручную управлять восстановлением базы данных после перезагрузки системы») — его включают `pg-setup service enable` или `systemctl enable postgrespro-1c-17`; для Debian/Ubuntu кроме unit-файла systemd поставляется и SysV-скрипт в `/etc/init.d/`.

`pg-wrapper` (пакет `-client`) **[офиц.]**:

| Команда | Что делает |
|---|---|
| `pg-wrapper links update` | Создаёт/обновляет символические ссылки на программы сервера и клиента и подключает man-страницы SQL. При наличии `update-alternatives` регистрирует программы как альтернативы с приоритетом; без него — меняет систему только при отсутствии конфликтов. |
| `pg-wrapper links remove` | Удаляет ссылки текущей версии. |

Примеры `pg-setup set`:

```bash
sudo /opt/pgpro/1c-17/bin/pg-setup set listen_addresses "'*'"
sudo /opt/pgpro/1c-17/bin/pg-setup set max_connections 500
sudo /opt/pgpro/1c-17/bin/pg-setup service condrestart
```

### 5.4. Если кластер создался не в той локали

Только пока в кластере нет нужных данных:

```bash
sudo -u postgres psql -c "\l"                      # в столбцах Collate/Ctype должно быть ru_RU.UTF-8
sudo systemctl stop postgrespro-1c-17
sudo mv /var/lib/pgpro/1c-17/data /var/lib/pgpro/1c-17/data.wrong-locale
sudo LANG=ru_RU.UTF-8 /opt/pgpro/1c-17/bin/pg-setup initdb
sudo /opt/pgpro/1c-17/bin/pg-setup service start
sudo -u postgres psql -c "\l"
sudo rm -rf /var/lib/pgpro/1c-17/data.wrong-locale   # когда убедились, что всё в порядке
```

### 5.5. Установка без доступа в интернет

Варианты (скачать на машине с интернетом, перенести на сервер):

1. **Автономный установщик `.run`** из `https://repo.postgrespro.ru/1c/installers/`, например `postgresql-1c-17-ubuntu-24.04-17.10-amd64.run`, `postgresql-1c-18-ubuntu-26.04-18.4-amd64.run` (60–66 МБ). ⚠ не подтверждено: порядок запуска и ключи установщика в открытой документации не описаны (в каталоге `installers/` нет ни README, ни иных файлов, кроме `.run`; на странице 1c.postgres.ru — только форма выбора версии и ОС). Обычно такие самораспаковывающиеся файлы запускаются как `sudo sh ./имя.run`, справка — `sh ./имя.run --help`; перед запуском на рабочем сервере проверьте на тестовой ВМ, что именно он делает (ставит ли пакеты через dpkg/apt, создаёт ли кластер, какую берёт локаль — на всякий случай запускайте с `LANG=ru_RU.UTF-8`). Если есть выбор, для закрытого контура надёжнее вариант 2 ниже (deb-пакеты из пула) — он полностью предсказуем.
2. **Отдельные deb-пакеты** из пула репозитория `https://repo.postgrespro.ru/1c/1c-17/ubuntu/pool/main/p/postgrespro-1c-17/`. Имена: `postgrespro-1c-17-server_17.10-1.noble_amd64.deb`, `postgrespro-1c-17-client_17.10-1.noble_amd64.deb`, `postgrespro-1c-17-libs_…`, `postgrespro-1c-17-contrib_…` (суффикс `jammy`/`noble`/`resolute` — под свой выпуск). Установка:
   ```bash
   sudo apt-get install -y ./postgrespro-1c-17-libs_*.deb ./postgrespro-1c-17-client_*.deb \
        ./postgrespro-1c-17-server_*.deb ./postgrespro-1c-17-contrib_*.deb
   sudo LANG=ru_RU.UTF-8 /opt/pgpro/1c-17/bin/pg-setup initdb
   sudo /opt/pgpro/1c-17/bin/pg-setup service enable
   sudo /opt/pgpro/1c-17/bin/pg-setup service start
   ```
   Системные зависимости (`libicu74`, `libxslt1.1`, `ssl-cert` и др.) apt возьмёт из локального зеркала Ubuntu или с установочного носителя.

### 5.6. Фиксация пакетов

Пакеты `postgrespro-1c-*` не пересекаются по именам с пакетами Ubuntu, подмена дистрибутивными им не грозит. Фиксация нужна для другого: чтобы минорное обновление СУБД (с перезапуском сервера) происходило только в запланированное окно, а не при очередном `apt upgrade`.

```bash
# зафиксировать все установленные пакеты ветки
dpkg-query -W -f='${Package}\n' 'postgrespro-1c-17*' | xargs sudo apt-mark hold
apt-mark showhold

# снять фиксацию перед плановым обновлением
dpkg-query -W -f='${Package}\n' 'postgrespro-1c-17*' | xargs sudo apt-mark unhold
```

Примечания:

- `unattended-upgrades` в Ubuntu по умолчанию обновляет только пакеты из собственных источников безопасности Ubuntu; пакеты из стороннего репозитория Postgres Professional автоматически он не трогает, пока его не добавили в `Allowed-Origins`.
- Чтобы остаться на конкретном минорном выпуске, можно вместо «плавающего» каталога `1c-17` подключить архивный: `https://repo.postgrespro.ru/1c/archive/1c-17.10/` (каталоги `1c-<мажор>.<минор>` существуют для всех выпусков). **Проверено 10.10.2026 [офиц., листинг]:** архивный каталог — полноценный apt-репозиторий той же структуры (`ubuntu/`, `debian/`, `keys/`, `meta.json` …), и в нём лежит **свой** `keys/pgpro-repo-add.sh`, настроенный на этот архив. Например, в `archive/1c-17.9/keys/pgpro-repo-add.sh` заданы `REPO="https://repo.postgres.ru/1c/archive/1c-17.9"` и `LISTNAME="postgresql-1c-17.9"`, то есть скрипт создаёт файл `/etc/apt/sources.list.d/postgresql-1c-17.9.list`:
  ```bash
  # зафиксироваться на конкретном выпуске 17.10 (пакеты называются так же: postgrespro-1c-17*)
  wget https://repo.postgrespro.ru/1c/archive/1c-17.10/keys/pgpro-repo-add.sh -O pgpro-repo-add-17.10.sh
  sudo sh pgpro-repo-add-17.10.sh
  ls /etc/apt/sources.list.d/ | grep postgresql-1c     # ожидается postgresql-1c-17.10.list (по аналогии с проверенным 17.9)
  apt-cache policy postgrespro-1c-17
  ```
  Нюансы: (а) не подключайте одновременно «плавающий» `1c-17` и архивный каталог — apt выберет старшую версию из обоих; (б) в архивном каталоге есть сборки только под те выпуски Ubuntu, которые поддерживались на момент выпуска: в `archive/1c-17.9/ubuntu/dists/` — `focal`, `jammy`, `noble`, `oracular`, `questing`, а `resolute` (26.04) там ещё нет; (в) в архиве есть каталог с суффиксом `-bad` (`1c-16.9-bad` — судя по названию, отозванная сборка; рядом лежит обычный `1c-16.9`) — такие каталоги не использовать; (г) список выпусков в `archive/` на 10.10.2026 для актуальных веток: 16 — `16.0`…`16.4`, `16.6`, `16.8`–`16.11`, `16.13`, `16.14`; 17 — `17.0`, `17.2`, `17.4`–`17.7`, `17.9`, `17.10`; 18 — `18.0`, `18.1`, `18.3`, `18.4` (не каждый минорный выпуск апстрима собирается для 1С).

## 6. Установка варианта (1): сборка PostgreSQL от фирмы «1С»

Содержимое портала releases.1c.ru закрыто авторизацией, поэтому имена файлов и состав пакетов ниже частично восстановлены по официальному репозиторию `1C-Company/docker_fresh` и публикациям сообщества; такие места помечены ⚠. Перед установкой сверяйтесь с файлом описания, приложенным к дистрибутиву.

### 6.1. Получение дистрибутива

1. Войти на `https://releases.1c.ru` → раздел технологических дистрибутивов → «PostgreSQL» → нужная версия, например `17.10-2.1C` (прямая ссылка: `https://releases.1c.ru/version_files?nick=AddCompPostgre&ver=17.10-2.1C`).
2. Выбрать дистрибутив **под свою ОС и архитектуру** — строка вида «Дистрибутив СУБД PostgreSQL для Ubuntu 24.04 x86 (64-bit) одним архивом» (⚠ точная формулировка для Ubuntu не проверена; для Debian она звучит как «…для Debian 13.0 x86 (64-bit) одним архивом»).
3. Передать архив на сервер, например: `scp postgresql_*.tar.bz2 admin@srv:/tmp/`.

### 6.2. Установка

```bash
# 0. Локаль — раздел 4.1 (обязательно ДО установки: кластер main создаётся автоматически)
sudo locale-gen ru_RU.UTF-8 && sudo update-locale LANG=ru_RU.UTF-8

# 1. Распаковать
sudo apt-get install -y bzip2
mkdir -p /tmp/pg1c && tar -xf /tmp/postgresql_*.tar.bz2 -C /tmp/pg1c
find /tmp/pg1c -name '*.deb' | sort

# 2. Посмотреть, что за пакеты и от чего они зависят
for f in $(find /tmp/pg1c -name '*.deb' ! -name '*dbgsym*'); do
  echo "== $f"; dpkg-deb -f "$f" Package Version Depends
done

# 3. Проверка «всухую»: что apt установит, удалит или понизит
apt-get -s install --allow-downgrades /tmp/pg1c/*.deb | grep -E '^(Inst|Remv|Conf)'

# 4. Установка через apt (а не dpkg -i), чтобы зависимости подтянулись из репозитория Ubuntu
sudo LANG=ru_RU.UTF-8 apt-get install -y --allow-downgrades /tmp/pg1c/*.deb

# 5. Проверка
dpkg -l | grep -E 'postgresql|libpq'          # в версии должно быть "…1C"
pg_lsclusters                                  # кластер NN/main, порт, статус online
sudo -u postgres psql -c "\l"                  # Collate/Ctype = ru_RU.UTF-8, Encoding = UTF8
```

Пояснения:

- Команда установки `apt-get install -y --allow-downgrades /tmp/pgsql/*.deb` взята из официального Dockerfile 1С (`1C-Company/docker_fresh`, образ на `debian:trixie`) **[офиц.]**. Если deb-файлы лежат во вложенном каталоге — подставьте его путь.
- `--allow-downgrades` нужен, когда в системе уже стоит `libpq5` или `postgresql-client-common` более новой версии из Ubuntu, чем в архиве.
- Если dbgsym-пакеты не нужны, исключите их из списка установки.
- Старый способ **[практика]** — `sudo dpkg -i libpq5*.deb postgresql-client-NN*.deb postgresql-NN*.deb` строго в этом порядке и затем `sudo apt-get -f install`. Он работает, но не показывает заранее проблемы зависимостей.
- После установки каталоги стандартные для Debian/Ubuntu: `/usr/lib/postgresql/NN/bin`, `/etc/postgresql/NN/main/{postgresql.conf,pg_hba.conf,conf.d/}`, `/var/lib/postgresql/NN/main`, журнал `/var/log/postgresql/postgresql-NN-main.log`; управление — `systemctl {start|stop|restart|status} postgresql@NN-main`, `pg_ctlcluster NN main reload`, `pg_lsclusters`.
- В Dockerfile 1С сервер запускается с `-c jit=off`, а в `postgresql.conf` добавляются `listen_addresses = '*'`, `synchronous_commit = off`, `max_connections = 1000` — это ориентир того, что сам вендор считает разумным для стенда.
- Что ещё видно в том же официальном образе (`images/db/Dockerfile` и `entrypoint.sh`, перепроверено 10.10.2026) **[офиц.]**: базовый образ `debian:trixie`; перед установкой ставятся `curl bzip2 gosu ca-certificates locales`; архив распаковывается командой `tar -xf /tmp/distr_full/postgresql_*.tar.bz2 -C /tmp/pgsql`, пакеты ставятся `apt-get install -y --allow-downgrades /tmp/pgsql/*.deb`; в `PATH` добавляется `/usr/lib/postgresql/${VERSION}/bin`; кластер создаётся в `PGDATA=/var/lib/postgresql/data` командой `gosu postgres initdb` **без каких-либо ключей** (локаль берётся из `LANG=ru_RU.UTF-8`); `max_connections` меняется со 100 на 1000 через `sed`; в `pg_hba.conf` дописывается `host all all 0.0.0.0/0 trust` (только для стенда!); сервер стартует как `gosu postgres postgres -c jit=off`. **Важное наблюдение:** в скрипте нет ни одного `CREATE EXTENSION`, `CREATE ROLE` или `CREATE DATABASE` — то есть всё, что нужно в базе (расширения, типы, таблицы), 1С-платформа создаёт сама при создании информационной базы (либо это уже заложено в шаблонную базу сборки — ⚠ какой из двух вариантов, по этим файлам не видно). SQL-скрипты из каталога `other_files/psql-scripts/` того же репозитория (`CreateDB_site.psql`, `CreateDB_forum.psql`) относятся к базам сайта и форума «Фреш», а не к информационным базам 1С.

### 6.3. Проблемы зависимостей (`libicu`, `libssl`, `libllvm`) и их решение

**Откуда берутся.** Бинарники сборки слинкованы с библиотеками той ОС, на которой собирались. У ICU номер версии входит в имя пакета и в имя `.so`, поэтому пакет, собранный на Ubuntu 22.04, требует именно `libicu70`, а на 24.04 есть только `libicu74`, на 26.04 — `libicu78`. Аналогично с LLVM (`libllvm14` / `libllvm18` / `libllvm21`). Классический пример из прошлого: сборка PostgreSQL 10 от 1С требовала `libicu55` и `libssl1.0.0` от Ubuntu 16.04, и на Ubuntu 18.04/Debian 10 их приходилось ставить вручную из старых выпусков **[практика, interface31.ru]**.

**Диагностика.**

```bash
dpkg-deb -f /tmp/pg1c/postgresql-17_*.deb Depends          # что требует пакет
apt-cache policy libicu70 libicu74 libicu78                 # что есть в системе/репозитории
apt-cache policy libssl3 libssl3t64
ldd /usr/lib/postgresql/17/lib/mchar.so | grep -E 'icu|not found'   # после установки
```

**Решения (в порядке предпочтения).**

1. **Скачать дистрибутив, собранный под вашу версию Ubuntu.** С 2025–2026 гг. 1С публикует отдельные дистрибутивы для всех поддерживаемых ОС **[офиц.]** — это снимает проблему полностью.
2. **Если есть только архив под более старую Ubuntu** — доустановить недостающую версию ICU из репозитория того выпуска. Пакеты разных версий ICU сосуществуют (разные имена пакетов и файлов) **[практика]**:
   ```bash
   # пример: Ubuntu 24.04, а пакет требует libicu70 (из 22.04)
   # deb-файл взять со страницы https://packages.ubuntu.com/jammy/libicu70 и перенести на сервер
   sudo apt-get install -y ./libicu70_*_amd64.deb
   ```
   Минус: такая библиотека не получает обновлений безопасности из репозиториев текущего выпуска.
3. **`libssl`:** на 22.04 пакет называется `libssl3`, на 24.04/26.04 — `libssl3t64`. **Подтверждено [офиц., карточка пакета на Launchpad]:** в Ubuntu 24.04 (amd64) пакет `libssl3t64` версии `3.0.13-0ubuntu3.16` объявляет `Provides: libssl3 (= 3.0.13-0ubuntu3.16)`, `Replaces: libssl3`, `Breaks: libssl3 (<< 3.0.13-0ubuntu3.16)`. Поэтому зависимость вида `libssl3 (>= 3.0.0)` у пакета, собранного под 22.04, на 24.04 удовлетворяется сама, доустанавливать ничего не нужно. Проверка на своей системе: `apt-cache show libssl3t64 | grep -E '^(Version|Provides)'`. Для 26.04 (OpenSSL 3.5) ожидается то же самое, но ⚠ по индексу пакетов 26.04 не проверено. Совсем старые сборки, требующие `libssl1.1` (эпоха Ubuntu 20.04), на 22.04+ лучше не ставить — берите более новую сборку. Обратите внимание: это «спасает» только `libssl`; у `libicu` и `libllvm` номер версии входит в имя пакета, и никакого `Provides` между `libicu70` и `libicu74` нет.
4. **`libllvm`:** нужен только JIT-компилятору, который для 1С всё равно отключают (`jit = off`). Если зависимость на `libllvmNN` не удовлетворяется, ищите дистрибутив под свою ОС; ставить пакет «через силу» не надо.
5. **Чего не делать:** `dpkg -i --force-depends`. Пакет установится, но сервер упадёт при старте или при `CREATE EXTENSION mchar` с `could not load library … cannot open shared object file`.

### 6.4. Локаль автоматически созданного кластера

Серверный пакет в дебиановской раскладке сам создаёт кластер `NN/main` (через `pg_createcluster`) с локалью из окружения установки / `/etc/default/locale`. Если она оказалась не `ru_RU.UTF-8`, пересоздайте кластер, **пока в нём нет данных**:

```bash
pg_lsclusters
sudo cp -a /etc/postgresql/17/main /root/pg17-main-conf.bak      # сохранить конфигурацию, которую выставил установщик
sudo pg_dropcluster --stop 17 main
sudo pg_createcluster --locale ru_RU.UTF-8 --start 17 main -- --data-checksums
pg_lsclusters
sudo -u postgres psql -c "\l"
```

- Синтаксис **[офиц., man pg_createcluster]**: `pg_createcluster [параметры] версия имя [-- параметры_initdb]`; ключи `--locale=`, `-p/--port=`, `-d/--datadir=`, `--start`, `--start-conf=auto|manual|disabled`, `-u/--user=`. По умолчанию каталог данных `/var/lib/postgresql/<версия>/<имя>`, конфигурация `/etc/postgresql/<версия>/<имя>/`, порт — первый свободный начиная с 5432.
- ⚠ Автоматически подобранные установщиком 1С параметры `postgresql.conf` при пересоздании кластера могут потеряться — сравните новый файл с сохранённой копией (`diff -u /root/pg17-main-conf.bak/postgresql.conf /etc/postgresql/17/main/postgresql.conf`) и перенесите нужное.

Способ избежать пересоздания — запретить автоматическое создание кластера до установки сервера, а затем создать его вручную:

```bash
sudo apt-get install -y postgresql-common
sudo sed -i -E "s/^#?create_main_cluster.*/create_main_cluster = false/" /etc/postgresql-common/createcluster.conf
grep create_main_cluster /etc/postgresql-common/createcluster.conf

sudo apt-get install -y --allow-downgrades /tmp/pg1c/*.deb
sudo pg_createcluster --locale ru_RU.UTF-8 --start 17 main -- --data-checksums
```

### 6.5. Фиксация пакетов — обязательна

Пакеты сборки 1С называются `postgresql-17`, `postgresql-client-17`, `libpq5` — точно так же, как пакеты «ванильного» PostgreSQL в репозиториях Ubuntu (22.04 — 14-я версия, 24.04 — 16-я, 26.04 — 18-я) и PGDG. Как только в подключённом репозитории появится пакет с версией «больше» (например, в Ubuntu 24.04 выйдет `postgresql-16 16.15-0ubuntu0.24.04.1` при установленном `16.14-1.1C`), `apt upgrade` молча заменит сборку 1С ванильной. Расширение `mchar` исчезнет, и 1С перестанет работать с базой.

```bash
# зафиксировать
sudo apt-mark hold postgresql-17 postgresql-client-17 libpq5
apt-mark showhold

# контроль: Installed и Candidate должны совпадать, в версии — суффикс 1C
apt-cache policy postgresql-17 postgresql-client-17 libpq5
apt-get -s upgrade | grep -Ei 'postgres|libpq' || echo "apt upgrade не тронет PostgreSQL"

# снять фиксацию перед плановым обновлением сборки
sudo apt-mark unhold postgresql-17 postgresql-client-17 libpq5
```

Когда риск подмены реален, а когда нет (уточнение рецензента):

- **Мажорная версия сборки 1С совпадает с версией PostgreSQL в самом выпуске Ubuntu** (14 на 22.04, 16 на 24.04, 18 на 26.04) — риск максимальный: обновления PostgreSQL в Ubuntu выходят через карман `<выпуск>-security`, а его по умолчанию обрабатывает не только ручной `apt upgrade`, но и служба **`unattended-upgrades`** (в её `Allowed-Origins` по умолчанию входят `${distro_id}:${distro_codename}` и `${distro_id}:${distro_codename}-security`). То есть без фиксации сборка может быть подменена ночью без участия администратора.
- **Мажорная версия другая** (например, сборка 1С 17 на Ubuntu 24.04, где в репозитории только 16) — пакета `postgresql-17` в Ubuntu нет, а `libpq5` из Ubuntu имеет меньшую версию (16.x против 17.x-N.1C), поэтому штатные репозитории Ubuntu сборку не заменят. Риск появляется при подключении PGDG (там есть и `postgresql-17`, и более новый `libpq5`) или после обновления выпуска Ubuntu (`do-release-upgrade`).
- `apt-mark hold` учитывается и `apt`, и `unattended-upgrades`; дополнительно пакеты можно внести в чёрный список автообновлений — файл `/etc/apt/apt.conf.d/51-no-auto-postgresql`:
  ```
  Unattended-Upgrade::Package-Blacklist {
      "postgresql-";
      "libpq5";
  };
  ```
  (⚠ на стенде не проверялось; элементы списка — регулярные выражения по именам пакетов; после создания файла выполните `sudo unattended-upgrade --dry-run --debug 2>&1 | grep -i -E 'postgres|libpq|blacklist'`).
- Обновление выпуска Ubuntu (`do-release-upgrade`) — отдельный риск: зафиксированные пакеты могут помешать расчёту обновления, а после перехода сборка, собранная под старый выпуск, останется без своей версии `libicu` (раздел 6.3). План **[практика]**: резервная копия баз → обновление ОС в окно обслуживания → сразу установка сборки 1С той же мажорной версии, собранной под новый выпуск → `REINDEX` и `ALTER DATABASE … REFRESH COLLATION VERSION` (изменились glibc/ICU) → повторная фиксация пакетов.

Дополнительная страховка через приоритеты apt **[практика]** (⚠ на стенде не проверялось; после создания файла обязательно проверьте вывод `apt-cache policy`):

```bash
sudo tee /etc/apt/preferences.d/99-postgresql-1c >/dev/null <<'EOF'
Package: postgresql-17 postgresql-client-17 libpq5
Pin: version *1C*
Pin-Priority: 1001
EOF
apt-cache policy postgresql-17
```

Что известно о таком закреплении по `man apt_preferences` **[офиц.]** и чего там нет:

- приоритет `P >= 1000` означает «установить эту версию, даже если это понижение версии»; `P < 0` — «никогда не устанавливать»; для конкретного пакета действует **первая подходящая** запись «конкретной формы»;
- в man-странице шаблон в `Pin: version` показан только в виде **префикса** (`Pin: version 5.32*`); сказано, что glob-выражения «могут встречаться везде, где может встречаться строка», но пример с `*` в начале шаблона (`*1C*`) там отсутствует — поэтому работоспособность именно `*1C*` остаётся ⚠ неподтверждённой;
- признак того, что закрепление сработало: в выводе `apt-cache policy postgresql-17` у версии с суффиксом `1C` стоит приоритет `1001`, а строка `Candidate:` совпадает с `Installed:`. Если приоритет остался `100`/`500` — шаблон не сработал, удалите файл и используйте вариант ниже.

Более предсказуемый вариант — не «поднимать» версию 1С, а **запретить чужие источники** для этих пакетов (используются только документированные формы `Pin: release o=…` и отрицательный приоритет):

```bash
sudo tee /etc/apt/preferences.d/99-postgresql-1c >/dev/null <<'EOF'
Explanation: do not take PostgreSQL and libpq5 from the Ubuntu archive (1C build is installed)
Package: postgresql-17 postgresql-client-17 libpq5
Pin: release o=Ubuntu
Pin-Priority: -1

Explanation: ...nor from PGDG, if it ever gets enabled
Package: postgresql-17 postgresql-client-17 libpq5
Pin: release o=apt.postgresql.org
Pin-Priority: -1
EOF
apt-cache policy postgresql-17 libpq5      # у версий из Ubuntu/PGDG должен стоять приоритет -1
```

⚠ Тоже не проверялось на стенде. Комментарии в файлах `preferences` документированным способом записываются строками `Explanation:` в начале записи (так и сделано выше); записи разделяются пустой строкой. Значение `o=` (Origin) своих источников смотрите в выводе `apt-cache policy` без аргументов (строки `release … o=Ubuntu …`). Отрицательное закрепление `libpq5` из Ubuntu безопасно только пока установлен `libpq5` из сборки 1С — другим программам, зависящим от `libpq5`, он подходит. Закрепление не заменяет `apt-mark hold`, а дополняет его.

Ещё правила:

- не подключайте репозиторий PGDG (`apt.postgresql.org`) на сервере со сборкой от 1С;
- не ставьте метапакеты `postgresql`, `postgresql-contrib`, `postgresql-client` из Ubuntu — они притянут ванильные версии;
- после каждого крупного обновления системы проверяйте `dpkg -l postgresql-17 libpq5` (версия с суффиксом `1C`) и `select version()`.

## 7. Первичная настройка после установки

### 7.1. Где что лежит

| | «PostgreSQL для 1С» Postgres Pro (ветка 17) | Сборка 1С / PGDG / пакеты Ubuntu (версия 17) |
|---|---|---|
| `postgresql.conf` | `/var/lib/pgpro/1c-17/data/postgresql.conf` | `/etc/postgresql/17/main/postgresql.conf` (+ `conf.d/*.conf`) |
| `pg_hba.conf` | `/var/lib/pgpro/1c-17/data/pg_hba.conf` | `/etc/postgresql/17/main/pg_hba.conf` |
| Каталог данных | `/var/lib/pgpro/1c-17/data` | `/var/lib/postgresql/17/main` |
| Программы | `/opt/pgpro/1c-17/bin` | `/usr/lib/postgresql/17/bin` |
| Перезапуск | `sudo systemctl restart postgrespro-1c-17` | `sudo systemctl restart postgresql@17-main` |
| Перечитать конфигурацию | `sudo -u postgres psql -c "select pg_reload_conf()"` | то же или `sudo pg_ctlcluster 17 main reload` |
| Журнал | `journalctl -u postgrespro-1c-17`; файловый журнал — по `SHOW log_directory;` | `/var/log/postgresql/postgresql-17-main.log` |

Универсальный способ узнать пути у работающего сервера:

```bash
sudo -u postgres psql -At -c "show config_file" -c "show hba_file" -c "show data_directory" \
                          -c "show port" -c "show log_destination" -c "show logging_collector" -c "show log_directory"
```

### 7.2. Пароль пользователя `postgres`

После установки у роли `postgres` пароля нет; локально под ней можно войти только через сокет методом `peer` (то есть из-под системного пользователя `postgres`). Серверу 1С нужен вход по TCP с паролем.

```bash
sudo -u postgres psql
```
```sql
\password postgres
-- psql дважды спросит пароль и отправит на сервер уже хеш (пароль не попадёт в журнал и историю)

-- альтернатива (пароль виден в истории psql и может попасть в журнал сервера):
-- ALTER ROLE postgres WITH PASSWORD 'СложныйПароль';

-- в каком виде пароль сохранён
SELECT rolname, left(rolpassword, 14) AS fmt FROM pg_authid WHERE rolname = 'postgres';
--   SCRAM-SHA-256$  -> scram-sha-256
--   md5…            -> md5
```

Сообщение `could not change directory to "/home/…": Permission denied` при запуске `sudo -u postgres psql` из домашнего каталога безвредно; чтобы его не было — `cd /tmp` перед командой или `sudo -iu postgres psql`.

### 7.3. `listen_addresses` и порт

| Схема | `listen_addresses` | Что ещё |
|---|---|---|
| Сервер 1С и PostgreSQL на одной машине | `'localhost'` (значение по умолчанию) — менять не нужно | в 1С сервер БД указывать как `localhost` или `127.0.0.1` |
| Сервер 1С на другой машине | `'*'` или явный список: `'localhost,192.168.1.20'` | строка в `pg_hba.conf` + правило межсетевого экрана |

Порт по умолчанию — 5432 (`port`). Оба параметра применяются **только после перезапуска** сервера **[офиц.]**.

```bash
# вариант 1 — ALTER SYSTEM (пишет в postgresql.auto.conf, работает в любой сборке)
sudo -u postgres psql -c "ALTER SYSTEM SET listen_addresses = '*'"

# вариант 2 — pg-setup (сборки Postgres Professional)
sudo /opt/pgpro/1c-17/bin/pg-setup set listen_addresses "'*'"
sudo /opt/pgpro/1c-17/bin/pg-setup set-server-port 5432

# вариант 3 — файл-вставка (дебиановская раскладка: сборка 1С, PGDG)
echo "listen_addresses = '*'" | sudo tee /etc/postgresql/17/main/conf.d/10-network.conf

# перезапуск и контроль
sudo systemctl restart postgrespro-1c-17        # или postgresql@17-main
sudo ss -ltnp | grep -E ':5432\b'
```

Если порт нестандартный, в параметрах информационной базы 1С он указывается в поле «Сервер баз данных» через пробел: `dbhost port=5433` **[практика]**.

### 7.4. `pg_hba.conf` для сервера 1С

Формат строки: `ТИП  БАЗА  ПОЛЬЗОВАТЕЛЬ  АДРЕС  МЕТОД`. Строки просматриваются сверху вниз, срабатывает **первая подходящая**.

```conf
# TYPE  DATABASE  USER      ADDRESS             METHOD

# локальное администрирование через unix-сокет (sudo -u postgres psql)
local   all       postgres                      peer

# сервер 1С на этой же машине (подключается по TCP к 127.0.0.1)
host    all       all       127.0.0.1/32        scram-sha-256
host    all       all       ::1/128             scram-sha-256

# сервер 1С на другой машине: один конкретный адрес, а не вся подсеть
host    all       postgres  192.168.1.10/32     scram-sha-256
```

- В сборке Postgres Professional после `pg-setup initdb` уже есть строки `local … peer` и `host … 127.0.0.1/32 md5`, то есть схема «всё на одной машине» работает сразу после задания пароля.
- Метод `md5` в `pg_hba.conf` при пароле, сохранённом как SCRAM, автоматически превращается в SCRAM-аутентификацию **[офиц.]** — поэтому менять `md5` на `scram-sha-256` в файле не обязательно, но для ясности лучше.
- Не используйте `trust` для TCP и `0.0.0.0/0` в адресе (так сделано в учебном Dockerfile 1С — это стенд, а не образец для рабочего сервера).
- В столбце базы серверу 1С нужен доступ к своим базам и к служебной базе для создания новых; проще и надёжнее оставить `all`.

Применение и проверка (перезапуск не нужен):

```bash
sudo -u postgres psql -c "select pg_reload_conf()"
sudo -u postgres psql -c "select line_number, type, database, user_name, address, auth_method, error
                          from pg_hba_file_rules order by line_number"
```

Столбец `error` в `pg_hba_file_rules` покажет строки с синтаксическими ошибками.

### 7.5. `password_encryption`, SCRAM и платформа 1С

Факты **[офиц., документация PostgreSQL]**:

- `password_encryption` по умолчанию — `scram-sha-256` (начиная с PostgreSQL 14). Параметр определяет, в каком виде сохранится пароль в момент `ALTER ROLE … PASSWORD` / `\password`.
- SCRAM — самый безопасный из парольных методов, но старые клиентские библиотеки его не понимают (нужна libpq версии 10 или новее).
- В PostgreSQL 18 пароли MD5 объявлены устаревшими: `CREATE ROLE`/`ALTER ROLE` с MD5-паролем выдают предупреждение (отключается `md5_password_warnings = off`), поддержка будет удалена в одной из следующих мажорных версий.

Что с 1С:

- Сервер «1С:Предприятия» подключается к PostgreSQL собственной клиентской библиотекой `libpq`, входящей в поставку платформы (системная `libpq5` и `psql` на это не влияют).
- **Что удалось установить при рецензии 10.10.2026 [офиц., список изменений платформы 8.3.22.1709, раздел версии 8.3.20, «Обновление используемых библиотек»]:** «Библиотека libpq обновлена до версии 14.2-3.1C» (там же: OpenSSL — до 1.1.1k). Аутентификация SCRAM-SHA-256 реализована в libpq начиная с версии 10 **[офиц., документация PostgreSQL]**, поэтому платформа с libpq 14.2 её поддерживает. **Вывод: `scram-sha-256` работает с платформой 8.3.20 и новее** (8.3.20–8.3.27, 8.5.x). Оговорки:
  - это вывод из версии библиотеки, а не прямая цитата: фразы «реализована поддержка SCRAM» нет ни в одном из просмотренных целиком списков изменений (8.3.15–8.5.4);
  - PostgreSQL 14.2 вышел в феврале 2022 г., а первые сборки 8.3.20, насколько помнит рецензент, появились раньше (конец 2021 г. — ⚠ дата не перепроверена), поэтому **ранние сборки 8.3.20 могли идти ещё со старой libpq** — используйте последнюю сборку ветки;
  - ⚠ не подтверждено: какая версия libpq была в 8.3.15–8.3.19 — в разделах этих версий записей об обновлении libpq нет. По опыту сообщества **[практика]**, именно на 8.3.1x в связке с PostgreSQL 13/14+ (где `password_encryption = scram-sha-256` по умолчанию с 14-й версии) возникала ошибка `authentication method 10 not supported`;
  - документация платформы на ИТС (раздел об особенностях работы с PostgreSQL) закрыта подпиской и не прочитана — официальную формулировку требований к методу аутентификации стоит сверить там.
- **Симптом** неподдерживаемого SCRAM: при создании/открытии базы 1С ошибка СУБД с текстом `authentication method 10 not supported` (10 — код запроса SASL-аутентификации).
- **Проверка:** после задания пароля создайте тестовую информационную базу с сервера 1С. Успешное подключение `psql` с того же узла ничего не доказывает — у `psql` своя libpq.
- **Обходной путь для старой платформы** (PostgreSQL 14–17):
  ```sql
  ALTER SYSTEM SET password_encryption = 'md5';
  SELECT pg_reload_conf();
  ALTER ROLE postgres WITH PASSWORD 'СложныйПароль';   -- пароль нужно задать заново, чтобы он пересохранился как md5
  ```
  и метод `md5` в соответствующей строке `pg_hba.conf`. В PostgreSQL 18 пароли MD5 ещё работают, но при их задании выдаётся предупреждение об устаревании, а в одной из следующих мажорных версий поддержка будет удалена **[офиц., release notes 18]** — то есть это тупиковый путь: обновляйте платформу. Все платформы, с которыми 1С официально поддерживает PostgreSQL 16–18 (8.3.22+), SCRAM уже умеют, так что на актуальной связке обходной путь не нужен.
- Какой метод реально использован, видно в журнале при `log_connections = on`: строка `connection authenticated: identity="postgres" method=scram-sha-256`.

### 7.8. Минимум параметров, специфичных для 1С

Сборки для 1С, как правило, выставляют их сами при установке; проверить стоит всегда. Значения — из приложения K.3 документации Postgres Pro **[офиц.]**; подробный разбор — в статье `02-postgresql-conf-tyuning-dlya-1c.md`.

```ini
max_connections = 500                 # 500..10000, растёт с числом сеансов 1С
max_locks_per_transaction = 256       # иначе обрывы транзакций при массовом удалении временных таблиц
standard_conforming_strings = off     # обратная косая черта как экранирование — совместимость с 1С
escape_string_warning = off
row_security = off
jit = off
shared_preload_libraries = 'plantuner'
plantuner.fix_empty_table = on
```

Остальные значения из того же приложения K.3 (перепроверено 10.10.2026; это отправная точка, а не догма — разбор в статье `02-…`) **[офиц., Postgres Pro]**: `shared_buffers` = ОЗУ/4; `temp_buffers` = 32–256MB; `work_mem` = ОЗУ/32..64 или 32–256MB; `maintenance_work_mem` = ОЗУ/16..32 или 256MB–4GB; `effective_cache_size` = ОЗУ − `shared_buffers`; `max_files_per_process = 10000`; `bgwriter_delay = 20ms`, `bgwriter_lru_multiplier = 4.0`, `bgwriter_lru_maxpages = 400`; `effective_io_concurrency = 2` (HDD) или сотни (SSD); `max_parallel_workers_per_gather = 0`; `fsync = on`; `synchronous_commit = off`; `checkpoint_timeout = 15min`; `min_wal_size = 512MB..4GB`, `max_wal_size = 2 × min_wal_size`; `commit_delay = 1000` (при TPS > 1000); `random_page_cost = 1.5–2.0` (RAID) или `1.1–1.3` (SSD); `from_collapse_limit = 20`, `join_collapse_limit = 20`; `geqo = on`, `geqo_threshold = 12`; `autovacuum = on`, `autovacuum_max_workers` = число ядер/4..2, но не менее 4; `autovacuum_naptime = 20s`; `temp_tablespaces` — отдельное быстрое табличное пространство для временных таблиц (по возможности). Там же рекомендуется вынести каталог `PGDATA/pg_stat_tmp` на `tmpfs` (актуально только для версий до 14 включительно — подтверждено примечаниями к выпуску PostgreSQL 15 (параметр `stats_temp_directory` удалён; сверено 11.10.2026): в PostgreSQL 15+ статистика хранится в разделяемой памяти и этот каталог не используется) и при сильной фрагментации памяти задать службе переменную окружения `MALLOC_MMAP_THRESHOLD_=8192`. Модуль `pg_hint_plan` (приложение K.4): `pg_hint_plan.hints_anywhere = on` позволяет читать указания планировщику из любого места текста запроса — способ подсказать план запросу 1С, не меняя платформу.

```bash
sudo -u postgres psql -c "select name, setting, source from pg_settings
  where name in ('max_connections','max_locks_per_transaction','standard_conforming_strings',
                 'escape_string_warning','row_security','jit','shared_preload_libraries',
                 'shared_buffers','work_mem','password_encryption','data_checksums')
  order by 1"
```

## 8. Создание информационной базы 1С и проверка в `psql`

### 8.1. Какие права нужны пользователю СУБД

- Платформа от имени указанного пользователя СУБД создаёт базу данных (если отмечено «Создать базу данных в случае её отсутствия»), создаёт в ней расширения и объекты, а в работе постоянно создаёт и очищает временные таблицы.
- **[практика]** Используют суперпользователя: либо саму роль `postgres`, либо отдельную роль с атрибутом `SUPERUSER`. Создание расширений на C (`mchar`, `fulleq`, `fasttrun`) без прав суперпользователя в общем случае невозможно.
  ```sql
  CREATE ROLE usr1cv8 WITH LOGIN SUPERUSER PASSWORD 'СложныйПароль';
  ```
- **Уточнено 10.10.2026:** по полному тексту документации 8.3.27 (глава 5, разд. 5.2.1.3.3) пользователь должен обладать привилегией `SUPERUSER` только в момент создания информационной базы; после успешного создания её можно отозвать (`alter user dbuser with nosuperuser;`). **Ранее было не подтверждено:** точная формулировка требований 1С к привилегиям пользователя PostgreSQL (в документации платформы на ИТС, раздел о создании информационной базы в клиент-серверном варианте) — страница закрыта подпиской. Схемы с пользователем без `SUPERUSER` (только `CREATEDB` или владелец заранее созданной базы) встречаются в сообществе, но считаются неподдерживаемыми.
- Как самому проверить, нужен ли суперпользователь для расширений 1С в вашей сборке (PostgreSQL 13+; столбцы `superuser` и `trusted` системного представления — документированная часть PostgreSQL):
  ```sql
  SELECT name, version, superuser, trusted
  FROM pg_available_extension_versions
  WHERE name IN ('mchar', 'fulleq', 'fasttrun') ORDER BY 1, 2;
  -- superuser = t и trusted = f  -> CREATE EXTENSION может выполнить только суперпользователь
  -- trusted = t                  -> достаточно права CREATE на базу
  ```
  Даже если расширения уже созданы в базе, платформе в работе нужны права владельца базы (создание/удаление таблиц и индексов при реструктуризации) и возможность создавать временные таблицы; при создании новой базы — ещё и `CREATEDB`. Что из этого платформа проверяет явно — ⚠ не подтверждено.
- При рецензии 10.10.2026 требование к привилегиям подтвердить по первоисточнику снова не удалось: в открытых источниках (v8.1c.ru, списки изменений платформы, приложение K документации Postgres Pro) о правах пользователя СУБД ничего не сказано; в официальном образе 1С (`docker_fresh`) подключения к СУБД вообще идут без пароля (`trust`), пользователь явно не создаётся — то есть по умолчанию подразумевается `postgres`.
- Раз пользователь — суперпользователь, защита строится на сети: `pg_hba.conf` только для адреса сервера 1С, порт закрыт экраном, сложный пароль.

### 8.2. Создание базы

Базу создают средствами 1С — консолью администрирования кластера, стандартной обработкой «Управление серверами», окном запуска 1С (добавление новой базы на сервере) либо утилитами `rac` / `ibcmd`. Вручную выполнять `CREATE DATABASE` не требуется. Параметры, относящиеся к СУБД:

| Параметр 1С | Значение |
|---|---|
| Тип СУБД | `PostgreSQL` |
| Сервер баз данных | `localhost` либо `dbhost`; с портом — `dbhost port=5433` |
| Имя базы данных | латиница в нижнем регистре, без пробелов и дефисов (**[практика]**: PostgreSQL приводит имена без кавычек к нижнему регистру) |
| Пользователь / пароль базы данных | роль из 8.1 |
| Создать базу данных в случае её отсутствия | да |
| Язык (Страна) | определяет локаль базы; для `Русский (Россия)` в ОС сервера СУБД должна существовать `ru_RU.UTF-8` |
| Схема БД (платформа 8.5.4+) | по умолчанию `public`; можно задать свою **[офиц.]** |

Примеры из командной строки (синтаксис `rac`/`ibcmd` подробно разобран в статьях раздела о 1С; здесь — только часть, относящаяся к СУБД; ⚠ сверяйте ключи с `rac infobase create --help` своей версии):

```bash
# через сервер администрирования (ras/rac)
/opt/1cv8/x86_64/8.3.27.1326/rac infobase --cluster=<UUID_кластера> create \
    --create-database --name=buh --dbms=PostgreSQL \
    --db-server=localhost --db-name=buh --locale=ru \
    --db-user=postgres --db-pwd='СложныйПароль' --license-distribution=allow

# платформа 8.5.4+: размещение таблиц в своей схеме
#    … --db-schema=buh_schema
```

Новые возможности 8.5.4 по схеме **[офиц., список изменений 8.5.4]**: параметр `--db-schema` у `rac` (команды работы с информационной базой), у `ibsrv`, у `ibcmd` (режим `infobase` и `server config init`); `--target-database-schema` у `ibcmd infobase replicate`; параметр `DBSchema` команды `CREATEINFOBASE`; свойство `IInfoBaseInfo.DatabaseSchema` в COM- и Java-интерфейсах администрирования.

### 8.3. Что 1С создаёт в базе и как это проверить

```bash
sudo -u postgres psql -d buh
```
```sql
-- 1. Кодировка и локаль базы
SELECT datname, pg_encoding_to_char(encoding) AS enc, datcollate, datctype
FROM pg_database WHERE datname = current_database();
--   ожидается: UTF8 | ru_RU.UTF-8 | ru_RU.UTF-8

-- 2. Расширения
\dx
--   ожидается: fasttrun, fulleq, mchar (+ plpgsql)

-- 3. Типы, оператор и функция из расширений
SELECT typname FROM pg_type WHERE typname IN ('mchar', 'mvarchar');
SELECT count(*) AS fulleq_ops FROM pg_operator WHERE oprname = '==';
\df fasttruncate

-- 4. Схемы и таблицы
\dn
SELECT schemaname, count(*) FROM pg_tables
WHERE schemaname NOT IN ('pg_catalog', 'information_schema') GROUP BY 1;
\dt public.config*
\dt public.v8users

-- 5. В каких типах 1С хранит строки
SELECT column_name, udt_name FROM information_schema.columns
WHERE table_schema = 'public' AND table_name = 'v8users' ORDER BY ordinal_position;
--   строковые поля имеют тип mvarchar / mchar, двоичные — bytea

-- 6. Размер базы
SELECT pg_size_pretty(pg_database_size(current_database()));
```

Что обычно видно **[практика]**:

- служебные таблицы платформы: `config`, `configsave`, `configcas`, `configcassave`, `params`, `files`, `dbschema`, `v8users`, `ibversion`, `depotfiles`, `_yearoffset`;
- таблицы объектов конфигурации с префиксом `_`: `_reference…` (справочники), `_document…`, `_inforg…` (регистры сведений), `_accumrg…` (регистры накопления), `_enum…`, `_const…` и т. д.; для типовой конфигурации — тысячи таблиц и индексов;
- всё лежит в схеме `public` (до 8.5.4 — всегда; начиная с 8.5.4 — в схеме, заданной в свойствах базы).

Во время работы платформа создаёт множество временных таблиц (`tt1`, `tt2`, …) в сеансовых схемах `pg_temp_N` и очищает их вызовом `fasttruncate()` — это нормальная картина для 1С.

### 8.4. Как на стенде увидеть, что именно платформа делает при создании базы

Точный SQL (`CREATE DATABASE … ENCODING … LC_COLLATE …`, `CREATE EXTENSION …`) в открытых источниках не опубликован (⚠ см. раздел 11, п. 7). На тестовом сервере его легко снять журналом PostgreSQL — это снимает сразу несколько вопросов (локаль, шаблон, расширения, права):

```bash
# 1. Временно включить запись всех DDL-команд в журнал (перезапуск не нужен)
sudo -u postgres psql -c "ALTER SYSTEM SET log_statement = 'ddl'" -c "SELECT pg_reload_conf()"

# 2. Создать тестовую информационную базу средствами 1С (консоль кластера / rac / ibcmd)

# 3. Посмотреть, что пришло от платформы
#    сборка Postgres Professional (журнал в journald или в каталоге по SHOW log_directory):
sudo journalctl -u postgrespro-1c-17 --since "10 min ago" --no-pager | grep -iE 'create database|create extension|create schema|alter database'
#    дебиановская раскладка (сборка 1С):
sudo grep -iE 'create database|create extension|create schema|alter database' /var/log/postgresql/postgresql-17-main.log | tail -n 40

# 4. Вернуть настройку
sudo -u postgres psql -c "ALTER SYSTEM RESET log_statement" -c "SELECT pg_reload_conf()"
```

Со стороны 1С те же запросы видны в технологическом журнале (событие `DBPOSTGRS`). Результат проверки стоит записать в эту базу знаний вместе с версиями платформы и СУБД — после этого пометки ⚠ в разделах 4.2 и 8.1 можно будет снять.

## 9. Несколько версий и несколько кластеров на одном сервере

Общие правила: у каждого экземпляра свой каталог данных, **свой порт**, своя служба; автонастройка памяти в сборках рассчитана на единственный экземпляр на машине **[офиц.]** — при нескольких экземплярах `shared_buffers`, `work_mem` и т. п. надо уменьшать вручную.

### 9.1. Две мажорные версии сборки Postgres Professional (например, 17 и 18)

Каталоги и службы разные (`/opt/pgpro/1c-17` и `/opt/pgpro/1c-18`), поэтому версии не мешают друг другу. Вторую ставят **без метапакета**:

```bash
wget https://repo.postgrespro.ru/1c/1c-18/keys/pgpro-repo-add.sh -O pgpro-repo-add-18.sh
sudo sh pgpro-repo-add-18.sh
sudo apt-get install -y postgrespro-1c-18-contrib
sudo LANG=ru_RU.UTF-8 /opt/pgpro/1c-18/bin/pg-setup initdb
sudo /opt/pgpro/1c-18/bin/pg-setup set-server-port 5433
sudo /opt/pgpro/1c-18/bin/pg-setup service enable
sudo /opt/pgpro/1c-18/bin/pg-setup service start
/opt/pgpro/1c-18/bin/pg_isready -p 5433
```

### 9.2. Второй кластер той же версии сборки Postgres Professional

`pg-setup` вторым кластером управлять не умеет. Порядок из документации Postgres Pro **[офиц.]**:

1. выполнить `initdb` с другим каталогом данных (пример — в разделе 4.4);
2. задать другой порт в `postgresql.conf` нового кластера (`port = 5433`);
3. для автозапуска скопировать unit-файл `/lib/systemd/system/postgrespro-1c-17.service` под новым именем, исправить в копии путь к каталогу данных и включить копию средствами systemd, а не `pg-setup`:
   ```bash
   sudo cp /lib/systemd/system/postgrespro-1c-17.service /etc/systemd/system/postgrespro-1c-17-second.service
   sudo nano /etc/systemd/system/postgrespro-1c-17-second.service     # путь к каталогу данных (PGDATA / ссылка на файл в /etc/default)
   sudo systemctl daemon-reload
   sudo systemctl enable --now postgrespro-1c-17-second
   ```

### 9.3. Несколько кластеров в дебиановской раскладке (сборка 1С, PGDG, пакеты Ubuntu)

```bash
pg_lsclusters
sudo pg_createcluster --locale ru_RU.UTF-8 --port 5433 --start 17 second -- --data-checksums
sudo systemctl status postgresql@17-second --no-pager
psql -h 127.0.0.1 -p 5433 -U postgres -c "select 1"
sudo pg_dropcluster --stop 17 second          # удаление кластера ВМЕСТЕ с данными и конфигурацией
```

### 9.4. Сборка для 1С рядом с «ванильным» PostgreSQL

| Сочетание | Возможность |
|---|---|
| «PostgreSQL для 1С» Postgres Pro + PostgreSQL из Ubuntu/PGDG | Да, если сборку Postgres Pro ставить через `-contrib` (не метапакет) и развести порты. Программы вызывать по полным путям (`/opt/pgpro/1c-17/bin/psql` и `/usr/lib/postgresql/16/bin/psql`). |
| Сборка 1С + PostgreSQL из Ubuntu/PGDG **той же** мажорной версии | Нет — одинаковые имена пакетов. |
| Сборка 1С + PostgreSQL из Ubuntu/PGDG **другой** мажорной версии | Технически да (общие `postgresql-common`, `libpq5`), но хрупко: `libpq5` в системе один, а любое обновление грозит подменой. Не рекомендуется. |

## 10. Обновление и удаление

### 10.1. Минорное обновление «PostgreSQL для 1С» (например, 17.10 → 17.11)

Формат данных в пределах мажорной версии не меняется: достаточно обновить пакеты и перезапустить сервер. Перед обновлением — резервная копия и чтение замечаний к выпуску (иногда требуется `REINDEX`).

```bash
sudo apt-get update
apt list --upgradable 2>/dev/null | grep postgrespro-1c           # что предлагается

# остановить сервер 1С (имя службы зависит от версии платформы), чтобы не было сеансов
systemctl list-units 'srv1cv8*' --no-pager
sudo systemctl stop 'srv1cv8*'

dpkg-query -W -f='${Package}\n' 'postgrespro-1c-17*' | xargs sudo apt-mark unhold
sudo apt-get install --only-upgrade -y $(dpkg-query -W -f='${Package} ' 'postgrespro-1c-17*')
sudo systemctl restart postgrespro-1c-17

sudo -u postgres psql -Atc "select version()"
# расширения, у которых установленная версия отстала от доступной (выполнить в каждой базе 1С)
sudo -u postgres psql -d buh -c "select name, installed_version, default_version
     from pg_available_extensions
     where installed_version is not null and installed_version <> default_version"
#    при необходимости: ALTER EXTENSION имя UPDATE;

dpkg-query -W -f='${Package}\n' 'postgrespro-1c-17*' | xargs sudo apt-mark hold
# запустить сервер 1С
```

### 10.2. Минорное обновление сборки от 1С

```bash
# скачать новый архив той же мажорной версии с releases.1c.ru, распаковать в /tmp/pg1c-new
sudo apt-mark unhold postgresql-17 postgresql-client-17 libpq5
sudo apt-get install -y /tmp/pg1c-new/*.deb
sudo systemctl restart postgresql@17-main
dpkg -l postgresql-17 libpq5
sudo apt-mark hold postgresql-17 postgresql-client-17 libpq5
```

### 10.3. Мажорное обновление (17 → 18)

Это отдельная процедура, а не обновление пакетов: новая версия ставится рядом (другие каталоги, временно другой порт), данные переносятся `pg_upgrade`, либо `pg_dump`/`pg_restore`, либо выгрузкой/загрузкой `.dt` средствами 1С. Замечания:

- сначала убедитесь, что платформа 1С поддерживает новую версию (таблица 3.3);
- `pg_upgrade` требует одинаковой настройки контрольных сумм; начиная с PostgreSQL 18 он переносит статистику планировщика **[офиц.]**;
- документация Postgres Pro предупреждает, что при `pg_dump`/`pg_restore` и `pg_upgrade` баз с нестандартными типами (`mchar`/`mvarchar`) возможны ошибки разрешения типов — см. её раздел о переносе таких баз **[офиц.]**;
- в новой версии нужны те же расширения, то есть сборка «для 1С» той же линейки.

### 10.4. Удаление

«PostgreSQL для 1С» Postgres Professional:

```bash
sudo systemctl disable --now postgrespro-1c-17
sudo /opt/pgpro/1c-17/bin/pg-wrapper links remove
sudo apt-get purge -y 'postgrespro-1c-17*'
sudo apt-get autoremove -y
ls -la /var/lib/pgpro/1c-17/                 # каталог данных пакетами не удаляется
sudo rm -rf /var/lib/pgpro/1c-17             # ВНИМАНИЕ: это базы данных
sudo rm -f /etc/apt/sources.list.d/postgresql-1c-17.list && sudo apt-get update
```

Сборка от 1С (дебиановская раскладка):

```bash
sudo pg_dropcluster --stop 17 main           # ВНИМАНИЕ: удаляет данные и конфигурацию кластера
sudo apt-mark unhold postgresql-17 postgresql-client-17 libpq5
sudo apt-get purge -y postgresql-17 postgresql-client-17
sudo apt-get autoremove --purge -y           # уберёт postgresql-common, libpq5, если больше не нужны
sudo rm -f /etc/apt/preferences.d/99-postgresql-1c
```

## Типичные ошибки и подводные камни (симптом → причина → решение)

| № | Симптом | Причина | Решение |
|---|---|---|---|
| 1 | При создании базы 1С: `ERROR: new collation (ru_RU.UTF-8) is incompatible with the collation of the template database (en_US.UTF-8)` | Кластер создан в локали `en_US.UTF-8` (установка шла в сеансе с английской локалью) | Пересоздать кластер в `ru_RU.UTF-8`: раздел 5.4 (сборка Postgres Pro) или 6.4 (сборка 1С). Делать до появления рабочих баз |
| 2 | `ERROR: new encoding (UTF8) is incompatible with the encoding of the template database (SQL_ASCII)` | Кластер создан в локали `C`/`POSIX` (при установке `LANG` была не задана) | То же: сгенерировать локаль, пересоздать кластер |
| 3 | `initdb: error: invalid locale name "ru_RU.UTF-8"` или `invalid locale settings; check LANG and LC_* environment variables` | Локаль не сгенерирована в ОС | `sudo locale-gen ru_RU.UTF-8`; проверить `locale -a \| grep -i ru_RU`; повторить инициализацию |
| 4 | `ERROR: type "mvarchar" does not exist` / `type "mchar" does not exist`; 1С сообщает об ошибке СУБД при создании/открытии базы (⚠ в т. ч. «DATABASE не пригодна для использования») | Сервер — «ванильный» PostgreSQL: изначально или после подмены пакетов | `dpkg -l \| grep -E 'postgresql\|libpq\|pgpro'`, `select version()`. Установить сборку для 1С; при подмене — см. № 9 |
| 5 | `ERROR: extension "mchar" is not available` + `DETAIL: Could not open extension control file "…/extension/mchar.control": No such file or directory.` (современные версии); в старых версиях (до 12) — `ERROR: could not open extension control file "…/extension/mchar.control": No such file or directory` | Нет файлов расширения: ванильная сборка либо не установлен пакет `-contrib` | Сборка Postgres Pro: `sudo apt-get install postgrespro-1c-17-contrib`. ## Быстрая шпаргалка — «задача → команда»

| Задача | Команда |
|---|---|
| Сгенерировать русскую локаль | `sudo locale-gen ru_RU.UTF-8 && sudo update-locale LANG=ru_RU.UTF-8` |
| Проверить локали в ОС | `locale -a \| grep -i ru_RU` |
| Подключить репозиторий «PostgreSQL для 1С» 17 | `wget https://repo.postgrespro.ru/1c/1c-17/keys/pgpro-repo-add.sh && sudo sh pgpro-repo-add.sh` |
| Установить (единственный PostgreSQL на машине) | `sudo LANG=ru_RU.UTF-8 apt-get install -y postgrespro-1c-17` |
| Установить рядом с другим PostgreSQL | `sudo apt-get install -y postgrespro-1c-17-contrib && sudo LANG=ru_RU.UTF-8 /opt/pgpro/1c-17/bin/pg-setup initdb` |
| Включить автозапуск и запустить (Postgres Pro) | `sudo /opt/pgpro/1c-17/bin/pg-setup service enable && sudo /opt/pgpro/1c-17/bin/pg-setup service start` |
| Сменить порт (Postgres Pro) | `sudo /opt/pgpro/1c-17/bin/pg-setup set-server-port 5433` + перезапуск |
| Добавить программы в PATH (Postgres Pro) | `sudo /opt/pgpro/1c-17/bin/pg-wrapper links update` |
| Установить сборку 1С из архива | `tar -xf postgresql_*.tar.bz2 -C /tmp/pg1c && sudo LANG=ru_RU.UTF-8 apt-get install -y --allow-downgrades /tmp/pg1c/*.deb` |
| Посмотреть зависимости deb-пакета | `dpkg-deb -f файл.deb Package Version Depends` |
| Зафиксировать сборку 1С | `sudo apt-mark hold postgresql-17 postgresql-client-17 libpq5` |
| Зафиксировать сборку Postgres Pro | `dpkg-query -W -f='${Package}\n' 'postgrespro-1c-17*' \| xargs sudo apt-mark hold` |
| Показать зафиксированные пакеты | `apt-mark showhold` |
| Что изменит `apt upgrade` | `apt-get -s upgrade \| grep -Ei 'postgres\|libpq'` |
| Список кластеров (дебиановская раскладка) | `pg_lsclusters` |
| Пересоздать кластер в русской локали (сборка 1С) | `sudo pg_dropcluster --stop 17 main && sudo pg_createcluster --locale ru_RU.UTF-8 --start 17 main -- --data-checksums` |
| Войти суперпользователем | `sudo -u postgres psql` |
| Задать пароль `postgres` | в `psql`: `\password postgres` |
| Версия и сборка сервера | `sudo -u postgres psql -Atc "select version()"` |
| Кодировка и локаль баз | `sudo -u postgres psql -c "\l"` |
| Провайдер локали | `select datname, datlocprovider, datcollate from pg_database;` |
| Включены ли контрольные суммы | `sudo -u postgres psql -Atc "show data_checksums"` |
| Есть ли расширения 1С | `select name, default_version from pg_available_extensions where name in ('mchar','fulleq','fasttrun');` |
| Расширения в базе 1С | `sudo -u postgres psql -d buh -c "\dx"` |
| Пути к конфигурации | `sudo -u postgres psql -At -c "show config_file" -c "show hba_file"` |
| Слушать все адреса | `sudo -u postgres psql -c "ALTER SYSTEM SET listen_addresses = '*'"` + перезапуск |
| Перечитать `pg_hba.conf` | `sudo -u postgres psql -c "select pg_reload_conf()"` |
| Проверить `pg_hba.conf` на ошибки | `select line_number, type, address, auth_method, error from pg_hba_file_rules;` |
| Перезапуск | `sudo systemctl restart postgrespro-1c-17` / `sudo systemctl restart postgresql@17-main` |
| Готовность сервера | `pg_isready -h 127.0.0.1 -p 5432` |
| Проверка входа по паролю | `psql -h 127.0.0.1 -U postgres -d postgres -c "select 1"` |
| Открыть порт для сервера 1С | `sudo ufw allow from 192.168.1.10 to any port 5432 proto tcp` |
| Кто слушает 5432 | `sudo ss -ltnp \| grep 5432` |
| Минорное обновление (Postgres Pro) | `sudo apt-get update && sudo apt-get install --only-upgrade -y $(dpkg-query -W -f='${Package} ' 'postgrespro-1c-17*') && sudo systemctl restart postgrespro-1c-17` |
| Удалить сборку Postgres Pro | `sudo systemctl disable --now postgrespro-1c-17 && sudo apt-get purge -y 'postgrespro-1c-17*'` (данные в `/var/lib/pgpro/1c-17` остаются) |
| Порт в параметрах базы 1С | поле «Сервер баз данных»: `dbhost port=5433` |
| Зафиксироваться на конкретном минорном выпуске (Postgres Pro) | `wget https://repo.postgrespro.ru/1c/archive/1c-17.10/keys/pgpro-repo-add.sh && sudo sh pgpro-repo-add.sh` (вместо «плавающего» `1c-17`) |
| Повторно подключить репозиторий (скрипт ругается на существующий файл) | `sudo rm /etc/apt/sources.list.d/postgresql-1c-17.list && sudo sh pgpro-repo-add.sh` |
| Нужен ли суперпользователь для расширений 1С | `select name, version, superuser, trusted from pg_available_extension_versions where name in ('mchar','fulleq','fasttrun');` |
| Загружен ли `plantuner` | `sudo -u postgres psql -Atc "show shared_preload_libraries"` |
| Каким методом реально вошёл сервер 1С | `log_connections = on` → в журнале `connection authenticated: … method=scram-sha-256` |
| Увидеть SQL, которым 1С создаёт базу (на стенде) | `ALTER SYSTEM SET log_statement = 'ddl'; SELECT pg_reload_conf();` → создать базу из 1С → смотреть журнал (раздел 8.4) |
| Удовлетворит ли `libssl3t64` зависимость `libssl3` | `apt-cache show libssl3t64 \| grep -E '^(Version\|Provides)'` |
| Не заберёт ли автообновление пакеты PostgreSQL | `sudo unattended-upgrade --dry-run --debug 2>&1 \| grep -iE 'postgres\|libpq'` |
| Что и когда apt менял в PostgreSQL | `grep -iE -B3 'postgres\|libpq' /var/log/apt/history.log \| tail -n 40` |
