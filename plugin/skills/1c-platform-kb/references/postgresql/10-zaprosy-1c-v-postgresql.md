## Кратко — главные факты

1. **Запрос 1С выполняет сервер 1С, а не клиент.** Рабочий процесс переводит текст на SQL для PostgreSQL. Каждый запрос пакета уходит в СУБД отдельным SQL-запросом [ИТС-разр 8.4.7.4].
2. В SQL нет имён «Справочник.Номенклатура» — только `_Reference123`, `_Fld456`, временные таблицы `pg_temp.tt<N>`. Перевод имён — `ПолучитьСтруктуруХраненияБазыДанных()` и `06-…`, разд. 8.
3. **В текст SQL платформа добавляет то, чего нет в тексте 1С:**
   - соединения для каждого обращения «через точку» — для поля составного типа со всеми возможными таблицами [std 654];
   - условия и соединения ограничений доступа на уровне записей (RLS) [std 654, 657, 658];
   - подзапросы виртуальных таблиц [std 733].
4. **Перед запросами платформа выставляет параметры сеанса** (`enable_mergejoin = off`, `cpu_operator_cost = 0.001`, `lock_timeout`). При ручном `EXPLAIN` их нужно повторить, иначе план будет другим [ИТС-мет 6011, `06-…` п. 10 «Кратко»].
5. **Строки 1С в PostgreSQL — типы `mvarchar`/`mchar`.** Сравнение без учёта регистра, концевые пробелы не учитываются, хранение — двухбайтовый Unicode [PGPro F.29]. В языке запросов `"bb" = "bb "` истинно, во встроенном языке — ложно [ИТС-разр 8.4.18.3].
6. **Режим блокировок решает уровень изоляции на PostgreSQL** [ИТС-разр гл. 9]:
   - управляемый — Read Committed и блокировки записей;
   - автоматический — Serializable и **блокировки целых таблиц**, для эксплуатации не рекомендуется [прил. 8].
   
   В управляемом режиме `ДЛЯ ИЗМЕНЕНИЯ` в запросах бессмысленно [std 460].
7. **Условия к виртуальной таблице передавать в её параметры, а не в `ГДЕ`.** Иначе СУБД может сначала собрать всю виртуальную таблицу [std 657].
8. **«Остатки» без даты и с использованием всех измерений во внешнем запросе** читают таблицу текущих итогов без группировки — это самый быстрый вариант [std 733].
9. **Соединение с вложенным запросом или виртуальной таблицей** даёт нестабильные планы: то быстро, то на порядки медленнее, особенно после устаревания статистики. Лечение — вынести во временную таблицу с индексом [std 655].
10. **Подзапрос в условии `ПО` запрещён** — замедление и даже неработоспособность на части СУБД [ИТС-разр 8.4.9.2.1; std 656].
11. **«Через точку» от поля составного типа** (например, `Регистратор.Дата`) — соединение со всеми допустимыми таблицами. В примере стандарта это 56 левых соединений. Лечение — `ВЫРАЗИТЬ(… КАК Документ.X)` [std 654].
12. **Основное условие должно попадать в индекс:**
    - поля — с начала индекса, подряд;
    - только `=` и `И`, на последнем поле допустимы `>`, `<`, `МЕЖДУ`, `ПОДОБНО "x%"`, `В`;
    - без функций, арифметики, `ВЫБОР`, отрицаний;
    - `ИЛИ` по разным полям — через `ОБЪЕДИНИТЬ ВСЕ`
    
    [std 652, 658].
13. **`ПОЛНОЕ ВНЕШНЕЕ СОЕДИНЕНИЕ` на PostgreSQL резко медленнее.** Вместе с обращением к табличным частям в `ВЫБРАТЬ` запрещено [std 435; прил. 8; ИТС-мет 1556].
14. **`ПОДОБНО` — только литерал или параметр.** Спецсимволы `_ % [ ] ^` экранировать через `СПЕЦСИМВОЛ`. Иначе на PostgreSQL ошибка `ERROR: invalid regular expression: invalid character range` [std 726].
15. **Временные таблицы 1С — это временные таблицы PostgreSQL.** Правила:
    - не помещать сотни тысяч строк;
    - индексировать, если в таблице больше 1000 строк и она участвует в соединении или в `В (…)`;
    - не создавать в цикле
    
    [std 777]. Со стороны СУБД им помогают `fasttrun` и `plantuner.fix_empty_table` [PGPro K.4].
16. **5–7 таблиц в одном запросе — уже много.** Время работы оптимизатора растёт нелинейно. Для PostgreSQL неудачный план особенно вероятен [std 729]. ИТС поднимает `from_collapse_limit` и `join_collapse_limit` до 20 и включает `geqo` с порогом 12 [ИТС-мет, `../its-metod/pg-nastrojki-postgresql-dlya-1c.md`].
17. **Однотипные запросы в цикле** заменять одним запросом с `В (&Список)`, `ОБЪЕДИНИТЬ ВСЕ` или пакетом [std 436].
18. **Два роли с разными RLS на одно право одного объекта** объединяют условия по `ИЛИ` — все запросы к объекту медленнее. Пользователю давать одну такую роль [std 658, п. 7].
19. **Где искать медленный запрос:**
    - техжурнал `DBPOSTGRS` (`Sql`, `Context`, `planSQLText` при `<plansql/>` — только на тесте);
    - `pg_stat_statements`;
    - `auto_explain`;
    - `auto_dump`
    
    (`06-…`, разд. 4, 5, 9; `../1c/07-…`).
20. **Исправить сам администратор может мало.** Ему доступны статистика, обслуживание индексов, настройки планировщика и `plantuner`. **Текст запроса меняет разработчик** — передавать ему конкретный запрос из ТЖ, `Context` и номер стандарта.

## 1. Путь запроса: от текста 1С до PostgreSQL

### 1.1. Где и как выполняется

- Объект `Запрос` выполняется на сервере 1С. Рабочий процесс переводит текст языка запросов в SQL нужной СУБД и отправляет его по своему соединению с PostgreSQL. Пакетный запрос — несколько запросов, разделённых `;` и связанных временными таблицами; **каждый запрос пакета выполняется в СУБД отдельно** [ИТС-разр 8.4.7.4].
- Что уходит в СУБД, а что считает сам сервер 1С:
  - «обычные» поля формируются средствами СУБД;
  - «виртуальные» поля дорабатывает сервер 1С: представления, `ВерсияДанных`, `ИмяПредопределенныхДанных`, `МоментВремени`, `ВидДвижения`, поля типов `ХранилищеЗначения`, `УникальныйИдентификатор` и др. [ИТС-разр 8.3];
  - с виртуальными строковыми полями нельзя выполнять строковые операции и сравнивать их со строками [там же].
- Арифметика: `СУММА`, `СРЕДНЕЕ`, `ВЫРАЗИТЬ`, `+`, `-`, `*` над числами дают число произвольной точности. Платформа обеспечивает не меньше 8 знаков после запятой, но не округляет, если СУБД дала больше. На другой СУБД (и в файловом варианте) результат может отличаться в последних знаках [ИТС-разр 8.4.17.1].
- Строки длиной больше 1024 символов считаются строками неограниченной длины. Для них не поддерживается конкатенация `+` в запросе [ИТС-разр 8.4.17.1].

### 1.2. Что добавляется к тексту

| Что в тексте 1С | Что появляется в SQL | Источник |
|---|---|---|
| `Таблица.Ссылка.Реквизит` (поле ссылочного типа) | неявное соединение с таблицей, на которую ссылается поле | [std 654] |
| то же от поля **составного** типа (`Регистратор.Дата`) | соединение со **всеми** таблицами, ссылки на которые допустимы в поле (пример стандарта — 56 левых соединений с таблицами документов) | [std 654] |
| ограничения доступа на уровне записей (RLS) у роли пользователя | дополнительные условия и соединения с таблицами, участвующими в RLS, — и для явных таблиц, и для неявных «через точку» | [std 654, 657] |
| `РАЗРЕШЕННЫЕ` | действует, только если на таблицы наложены ограничения доступа к данным; распространяется на весь запрос, включая вложенные | [ИТС-разр 8.4.7.1] |
| виртуальная таблица (`Остатки`, `ОстаткиИОбороты`, `Обороты`, `СрезПоследних`, `СрезПервых`) | вложенный запрос к таблицам итогов и, если задана дата, к таблице движений | [std 733] |
| временная таблица `ПОМЕСТИТЬ X` | временная таблица PostgreSQL (`pg_temp.tt<N>`; номер разный в разных соединениях) | `06-…`, п. 9 «Кратко» |

### 1.3. Параметры сеанса, которые ставит платформа

По методике ИТС 6011 платформа выставляет в соединении `enable_mergejoin = off`, `cpu_operator_cost = 0.001`, `lock_timeout` (время ожидания блокировки — параметр информационной базы, по умолчанию 20 с) и `escape_string_warning = off`. Подробно и с командами для ручного `EXPLAIN` — `06-…`, п. 6 и 10 раздела «Кратко», разд. 7.

### 1.4. Типы данных

- Строковые реквизиты 1С хранятся в типах `mvarchar` (переменная длина) и `mchar` (фиксированная) модуля `mchar`. Они:
  - совместимы с `varchar`/`char` MS SQL;
  - сравнивают без учёта регистра через ICU;
  - не учитывают концевые пробелы;
  - хранятся двухбайтовым Unicode независимо от кодировки базы;
  - имеют операторы с учётом регистра `&=`, `&<` и т. д.;
  - поддерживают индексы B-дерево и хеш и индексный `LIKE`.
  
  [PGPro F.29]
- Оператор `==` модуля `fulleq` даёт TRUE при двух NULL, как в MS SQL [PGPro F.21]. Платформа использует его при сравнениях, где 1С ожидает поведение MS SQL [практика ⚠].
- Сортировка: на PostgreSQL при возрастании `NULL` идут последними, при убывании — первыми [прил. 8].
- **Риск при восстановлении и обновлении.** Операторы нестандартных типов вне схемы `pg_catalog` могут не находиться при `pg_restore` (пустой `search_path`) и `pg_upgrade` [PGPro 10.2.1]. Поэтому пробное восстановление и пробный `pg_upgrade` на копии — обязательны: `04-…`, `07-…`, `../guides/07-…`, разд. 8.2.

### 1.5. Блокировки и изоляция

| Режим конфигурации | Блокировки на PostgreSQL | Изоляция | Источник |
|---|---|---|---|
| Автоматический | **таблиц** | Serializable | [ИТС-разр гл. 9; прил. 8] |
| Управляемый | записей | Read Committed | [ИТС-разр гл. 9] |

- В автоматическом режиме транзакция, захватившая одну запись, блокирует всю таблицу. Режим оставлен для совместимости и для реальной эксплуатации не рекомендуется [прил. 8].
- В управляемом режиме блокировки данных задаёт сама 1С (менеджер блокировок кластера), а конструкцию `ДЛЯ ИЗМЕНЕНИЯ` в запросах применять не следует как не имеющую смысла [std 460]. По тексту гл. 8 `ДЛЯ ИЗМЕНЕНИЯ` блокирует прочитанные в транзакции данные; в клиент-серверном варианте — только выбранные записи [ИТС-разр 8.4.7.1].
- Ожидание блокировок PostgreSQL ограничено `lock_timeout`, который ставит платформа. Его истечение 1С показывает как «Конфликт блокировок при выполнении транзакции» (`06-…`, п. 6 «Кратко»; `../its-metod/vzaimoblokirovki-i-oshibki-blokirovok.md`).

## 2. Конструкции языка запросов и их цена на PostgreSQL

### 2.1. Виртуальные таблицы регистров

- **Параметры, а не `ГДЕ`.** Все условия, относящиеся к виртуальной таблице, передавать в её параметры [std 657]:
  - **плохо** — `… ИЗ РегистрНакопления.ТоварыНаСкладах.Остатки() ГДЕ Склад = &Склад`: может быть собрана вся таблица, потом отфильтрована;
  - **хорошо** — `… ИЗ РегистрНакопления.ТоварыНаСкладах.Остатки(, Склад = &Склад)`.
- **В параметрах — только простые условия** вида `Измерение = Значение` [std 657, п. 2]:
  - не подзапросы и не соединения (в том числе неявные «через точку» и добавленные RLS);
  - если подзапрос неизбежен — одна таблица без соединений;
  - временная таблица — без `ГДЕ`;
  - для постоянной таблицы условие допустимо, только если оно выполняется для 80 % и более записей;
  - несколько условий `В (…)` по разным полям заменять одним `(Поле1, Поле2, Поле3) В (ВЫБРАТЬ … ИЗ ВременнаяТаблица)`.
- **«Остатки» — самый быстрый вариант** [std 733]: дата не указана (текущие остатки), разделение итогов не используется и **все измерения регистра участвуют во внешнем запросе** — в `ВЫБРАТЬ` или в условии соединения. Тогда платформа читает хранимую таблицу текущих итогов без группировки. Пример стандарта:
  - **плохо** — `ЛЕВОЕ СОЕДИНЕНИЕ РегистрНакопления.ОстаткиТоваров.Остатки(&СегодняшняяДата, Склад = &Склад) … ПО ОстаткиТоваров.Номенклатура = Спр.Ссылка`;
  - **хорошо** — `… .Остатки(, Склад = &Склад) … ПО ОстаткиТоваров.Номенклатура = Спр.Ссылка И ОстаткиТоваров.Склад = &Склад`.
- **Итоги периодических регистров сведений** («Разрешить итоги: срез последних/первых»). Включать, если [std 708]:
  - данных много (цены номенклатуры — да, курсы валют — нет);
  - часто запрашивается срез на текущий момент **без даты**;
  - условия задаются только по измерениям;
  - RLS — только по измерениям.
  
  Тогда выборка идёт из дополнительных таблиц, где хранятся только последние или первые значения. Актуализируются они при каждой записи набора — отдельный пересчёт не нужен. Если запросы всегда идут на конкретную дату (дату документа) или с условиями «через точку», итоги не помогают.
- **`СрезПоследних` в соединении на PostgreSQL.** Если запрос медленный, вынести срез во временную таблицу и соединяться с ней [ИТС-мет 4208, статья 2010 года, частично устарела; совпадает с std 655, п. 2].
- **Однотипные запросы на дату в цикле** допустимы, когда объединение ухудшает план — например, виртуальные таблицы на разные даты [std 436, п. 2].

### 2.2. Соединения

- **Нельзя соединять с вложенным запросом** — с любой стороны. Соединять только объекты метаданных и временные таблицы [std 655]. Последствия: замедление до нескольких порядков, нестабильность («то быстро, то медленно»), разница между СУБД, сильная зависимость от свежести статистики. Лечение — пакет: вложенный запрос → `ПОМЕСТИТЬ` с `ИНДЕКСИРОВАТЬ ПО` → соединение с временной таблицей. Тогда все выборки становятся физическими таблицами с известным размером, и СУБД выбирает план надёжнее.
- **Соединение с виртуальной таблицей**, если запрос медленный, — так же через временную таблицу [std 655, п. 2].
- **Вложенные соединения** `А ЛЕВОЕ СОЕДИНЕНИЕ Б ЛЕВОЕ СОЕДИНЕНИЕ В ПО … ПО …` по сути равны соединению с подзапросом. Заменять последовательными `А ЛЕВОЕ СОЕДИНЕНИЕ Б ПО … ЛЕВОЕ СОЕДИНЕНИЕ В ПО …`. Результаты у этих вариантов могут различаться — проверять [std 655, п. 3].
- **Подзапрос в условии `ПО`** запрещён: замедление и на некоторых СУБД неработоспособность [ИТС-разр 8.4.9.2.1; std 656]. Типичный случай — «срез последних на начало месяца для каждой номенклатуры» внутри `ПО`. Переписывается в два запроса через временную таблицу с максимальными датами.
- **`ПОЛНОЕ ВНЕШНЕЕ СОЕДИНЕНИЕ`** [std 435; прил. 8; ИТС-мет 1556]:
  - на PostgreSQL производительность значительно ниже. Платформа преобразует такой запрос в эквивалентную форму, потому что PostgreSQL поддерживает `FULL JOIN` не для всех условий соединения;
  - одновременно с обращением к табличным частям в `ВЫБРАТЬ` его использовать нельзя;
  - в большинстве случаев переписывается через `ОБЪЕДИНИТЬ ВСЕ` с группировкой.
- **Правое соединение** конструктор запросов всё равно переводит в левое [ИТС-разр 8.4.9.2.4]. На план это не влияет [практика].
- **Число таблиц.** Минимально необходимое. 5–7 таблиц в одном запросе уже могут быть «много». Время оптимизатора растёт нелинейно, и для DB2, PostgreSQL и Oracle неверный план особенно вероятен. Признак — в плане есть «timeout warning» (у MS SQL) [std 729]. Неявные таблицы («через точку», RLS) тоже считаются.
- **Настройки PostgreSQL, связанные с этим** (рекомендации ИТС, `../its-metod/pg-nastrojki-postgresql-dlya-1c.md`):
  - `from_collapse_limit = 20` и `join_collapse_limit = 20` — до скольких элементов `FROM` планировщик переставляет соединения и раскрывает подзапросы;
  - `geqo = on`, `geqo_threshold = 12` — с какого числа элементов включается генетический поиск вместо полного перебора [PG, runtime-config-query].
  
  Запрос из 15–20 таблиц (с RLS и составными типами это быстро) планируется дольше и менее точно.

### 2.3. Обращение «через точку» и составные типы

- Каждый уровень «через точку» — соединение. От составного поля — соединение со всеми допустимыми таблицами плюс их RLS [std 654].
- Что делать [std 654]:
  - ограничить типы `ВЫРАЗИТЬ(Поле КАК Документ.X).Реквизит` и условием `Поле ССЫЛКА Документ.X`;
  - хранить нужное значение прямо в таблице (например, `ДатаРегистратора` в регистре);
  - не делать поля типа «любая ссылка» без необходимости.

### 2.4. Условия и индексы

- **Подходящий индекс** — содержит все поля условия, они в начале индекса и идут подряд [std 652]. Порядок условий в тексте запроса значения не имеет.
- **Индексы, которые платформа создаёт сама** [std 652]:
  - по ссылке у объектных таблиц;
  - по регистратору у таблиц движений;
  - по периоду и всем измерениям у итогов регистров накопления;
  - по периоду, счёту и измерениям у итогов регистров бухгалтерии.
- **Дополнительно индексировать реквизиты** — с доп. упорядочиванием, только под известный запрос [std 652]. Не индексировать:
  - первое измерение регистра — для него подходит основной индекс итогов;
  - малоселективные поля (булево и т. п.).
- **Основное условие** — то, что сильнее всего сужает выборку; составляющие только через `И` [std 658]:
  - для всех полей индекса, кроме последнего, — только `=`;
  - для последнего — также `>`, `<`, `>=`, `<=`, `МЕЖДУ`, `ПОДОБНО "строка%"`, `В`, `ИЛИ`, сводимое к `В`;
  - без функций, арифметики, отрицаний, неравенств `<>`, `ВЫБОР`. Всё это — только в дополнительных условиях через `И`.
- **Где индексировать** [std 658]:
  - для `ГДЕ` и параметров виртуальной таблицы — в основной таблице;
  - для `ПО` левого соединения — в правой таблице;
  - для внутреннего соединения — в большей таблице.
- **Перепись типичных условий** [std 658]:

| Плохо (индекс не используется) | Хорошо |
|---|---|
| `ПОДСТРОКА(Поле, 1, 6) = "строка"` | `Поле ПОДОБНО "строка%"` |
| `ПОДСТРОКА(Поле, 3, 6) = "строка"` или `ПОДОБНО "__строка%"` | вычисляемое при записи индексированное поле |
| `МЕСЯЦ(Поле) = 1` | `Поле МЕЖДУ &НачалоМесяца И &КонецМесяца` |
| `Поле1 = &З1 ИЛИ Поле2 = &З2` | два запроса через `ОБЪЕДИНИТЬ ВСЕ` (оба поля индексированы; проверить, что результат тот же) |
| `Поле - 1 > 0` в основном условии | арифметика — только в дополнительном условии |

- Требования можно не соблюдать, если в таблице всегда меньше 1000 записей или запрос очень редкий [std 658, п. 1.1].
- **Дополнительные индексы** (индекс по нескольким полям с включаемыми полями) применяют в решениях для крупных внедрений с лицензиями **КОРП**; на ПРОФ их использовать нельзя [std 791]. Включает их разработчик в конфигурации, не администратор СУБД.
- В индекс 1С входит не более 16 полей [прил. 8].

### 2.5. `ПОДОБНО`

- Шаблон — только литерал или параметр, не конкатенация и не поле таблицы [std 726].
- Переносимые спецсимволы — только `%` и `_`. Квадратные скобки не работают на IBM Db2. На PostgreSQL `[` и `]` — спецсимволы только в текстовом литерале, но не в выражении [std 726; прил. 8].
- Пользовательский ввод экранировать через `СПЕЦСИМВОЛ` (в БСП — `ОбщегоНазначения.СформироватьСтрокуДляПоискаВЗапросе`). Иначе текст со скобками даст на PostgreSQL `ERROR: invalid regular expression: invalid character range` [std 726]. Это частая ошибка в журнале PostgreSQL при поиске в списках.
- Длина шаблона ограничена СУБД; переносимый предел — 1024 символа [ИТС-разр 8.4.18.8; std 726].
- Сравнение без учёта регистра на любой СУБД [ИТС-разр 8.4.18.8].
- Для индекса пригоден только шаблон с постоянным началом (`"строка%"`) [std 658].

### 2.6. Группировка, объединение, итоги

- Поле группировки нельзя одновременно использовать внутри агрегатной функции. Поведение зависит от СУБД, возможны аварийные ошибки [ИТС-разр 8.4.12.1]. Агрегат в `ВЫБРАТЬ` для проверки условия тоже ведёт себя по-разному на разных СУБД [ИТС-разр 8.4.17.3].
- `ОБЪЕДИНИТЬ` без `ВСЕ` убирает дубликаты — это лишняя сортировка или хеширование в СУБД. Если дубликатов быть не может или они нужны, писать `ОБЪЕДИНИТЬ ВСЕ` [ИТС-разр 8.4.14; std 434].
- Упорядочивание и итоги в объединении считаются над результатом объединения [ИТС-разр 8.4.14].
- `ИТОГИ` и иерархические итоги добавляют обработку; в большинстве случаев её выполняет сервер 1С, а не СУБД ⚠ (в документации прямо не сказано).

### 2.7. Временные таблицы

**Правила языка** [ИТС-разр 8.4.10, 8.5.2]:
- таблица живёт до `УНИЧТОЖИТЬ`, до уничтожения объекта `Запрос` (если менеджер временных таблиц не задан) или до закрытия менеджера временных таблиц;
- при откате транзакции из менеджера удаляются таблицы, созданные в этой транзакции;
- типы колонок задаются неявно при `ПОМЕСТИТЬ`, включая длину строк и разрядность чисел. Если потом `ДОБАВИТЬ` данные шире — ошибка; расширять тип через `ВЫРАЗИТЬ`/`ВЫБОР` при создании;
- индексы — только в запросе с `ПОМЕСТИТЬ`: `ИНДЕКСИРОВАТЬ ПО` или `ИНДЕКСИРОВАТЬ ПО НАБОРАМ`. Первый индекс кластерный только на MS SQL, на PostgreSQL все индексы обычные. Индексы — для скорости, не для контроля уникальности: поведение СУБД различается. `УНИКАЛЬНО` — только у одного индекса;
- поля индекса должны быть в списке выборки;
- `АВТОНОМЕРЗАПИСИ()` — уникальный номер строки во временной таблице; начальное значение зависит от СУБД;
- порядок строк во временной таблице не гарантирован;
- таблица из внешнего источника (таблица значений) требует явно типизированных колонок; в таком запросе нельзя соединения и объединения.

**Правила производительности** [std 777]:
- не помещать очень большие объёмы (сотни тысяч записей) — обрабатывать порциями;
- выбирать только нужные строки и поля;
- не создавать и не удалять таблицы в цикле;
- не копировать таблицу ради переименования;
- индексировать, если таблица участвует в соединении (поля из `ПО`) или в `В (ВЫБРАТЬ … ИЗ ВТ)` (поля списка выбора);
- маленькие (меньше 1000 записей) не индексировать;
- если условий несколько — индекс под самое частое.

**Что это значит для PostgreSQL:**
- **Каталог `pg_class`.** Каждая временная таблица — запись в системном каталоге. Быстрое усечение без разрастания `pg_class` обеспечивает `fasttrun` (`fasttruncate()`, нетранзакционная) [PGPro F.19]. При тысячах временных таблиц в секунду системные каталоги всё равно раздуваются — смотреть `pg_class`/`pg_attribute` (`05-…`) [практика].
- **Статистика.** У только что созданной временной таблицы статистики нет. PostgreSQL оценивает пустую таблицу как большую, и план портится. `plantuner.fix_empty_table = on` обнуляет оценку для таблиц без блоков [PGPro F.45, K.4.3].
  
  `online_analyze` с `table_type = 'temporary'` мгновенно анализирует временные таблицы после заполнения. С современными версиями 1С его **не рекомендуют** — только если оптимизатор систематически ошибается в числе строк [PGPro F.30, K.4.4; ИТС — `enable = off`].
- **Память.** `temp_buffers` — память сеанса под временные таблицы. Рекомендация ИТС — 32–256 МБ (`../its-metod/pg-nastrojki-postgresql-dlya-1c.md`).
  
  `enable_temp_memory_catalog` (с 16.4) и `enable_temp_rd_buffers` описаны для сборок PostgreSQL **с патчами 1С**. Есть ли они в сборке Postgres Pro — сверить: `SELECT name FROM pg_settings WHERE name LIKE 'enable_temp%';` ⚠.
- **Блокировки объектов.** Много временных таблиц и индексов в одной транзакции расходуют слоты блокировок объектов. Отсюда рекомендация ИТС `max_locks_per_transaction = 512…2000`; иначе — `out of shared memory` с подсказкой увеличить этот параметр [ИТС-мет; PG].

### 2.8. Прочее, что встречается в разборах

- Строки в запросах сравниваются без учёта регистра и концевых пробелов, во встроенном языке — с ними. Отсюда «нашёл запросом, но не нашёл `Найти()`» [ИТС-разр 8.4.18.3].
- `ДОБАВИТЬКДАТЕ`/`РАЗНОСТЬДАТ` с большими значениями дают разное поведение на переходе летнего времени и выход за диапазон дат СУБД. Брать единицу, соответствующую задаче (дни, месяцы) [ИТС-разр 8.4.17.4].
- `РАЗМЕРХРАНИМЫХДАННЫХ` на разных СУБД возвращает разные значения [ИТС-разр 8.4.17.4].
- Округление результатов арифметики в запросе — отдельный стандарт [std 535].
- Количество записей считать `КОЛИЧЕСТВО(*)` или `КОЛИЧЕСТВО(<Поле>)`, а не `СУММА(1)`. При 10 млн записей и больше `СУММА(1)` переполняется из-за разрядности числа по умолчанию. Если нужен условный подсчёт через `СУММА`, расширять разрядность `ВЫРАЗИТЬ(1 КАК ЧИСЛО(17, 0))` [std 787].
- Проверка «есть ли строки» — `НЕ Запрос.Выполнить().Пустой()`, без получения выборки [std 438].
- Порядок строк без `УПОРЯДОЧИТЬ ПО` не гарантирован и может меняться при смене СУБД, её версии или параметров. Если от порядка зависит алгоритм или показ пользователю, его задают явно [std 412].
  - Сортировка по полю, которое может быть `NULL`, на разных СУБД разная (на PostgreSQL при возрастании `NULL` последние) — оборачивать в `ЕСТЬNULL` [std 412; прил. 8].
  - `АВТОУПОРЯДОЧИВАНИЕ` подставляет вместо ссылок поля сортировки по умолчанию ссылочных таблиц — это дополнительные соединения [ИТС-разр 8.4.15.4].

## 3. Два случая, которые чаще всего приходят к администратору

### 3.1. «Отчёт то быстрый, то медленный»

Самая частая причина по стандартам — соединение с вложенным запросом или виртуальной таблицей. План зависит от оценок числа строк. После `ANALYZE` запрос быстрый, через несколько дней статистика устаревает, и он медленный [std 655].

| Сторона | Что делать |
|---|---|
| Администратор | проверить свежесть статистики таблиц из плана (`pg_stat_user_tables.last_analyze`, `n_mod_since_analyze` — `05-…`); `ANALYZE` нужных таблиц; убедиться, что `plantuner.fix_empty_table = on`. Это облегчит, но не вылечит |
| Разработчик | переписать запрос: вложенный запрос или виртуальную таблицу — во временную таблицу с индексом [std 655, 777] |

### 3.2. «Ошибка в журнале PostgreSQL при поиске в списке»

`ERROR: invalid regular expression: invalid character range` в журнале PostgreSQL, у пользователя ошибка при поиске строки со скобками или `^`. Причина — шаблон `ПОДОБНО` не экранирован [std 726]. Лечит разработчик: `СПЕЦСИМВОЛ` и экранирование. Администратор находит место по `Context` события `DBPOSTGRS` или `EXCP` в техжурнале (`../1c/07-…`).

## 4. Как найти медленный запрос и связать его с кодом

Подробные команды — в `06-monitoring-i-diagnostika-zaprosov.md`, разд. 4, 5, 7, 9, 11, и `../1c/07-…`. Порядок для запроса 1С:

1. **Техжурнал.** Событие `DBPOSTGRS` (свойства `Sql`, `Rows`, `RowsAffected`, `dbpid`, `Context`) с отбором по длительности. `Context` — строка кода 1С, из которой вызван запрос. `planSQLText` с планом появляется только при `<plansql/>`, а его **на продуктивном сервере включать нельзя** [ИТС-мет 6011] (`../1c/07-…`, разд. 3–5).
2. **`pg_stat_statements`** — общий вклад запроса. Учитывать, что временные таблицы `tt<N>` дробят один запрос на много строк статистики: группировать с заменой `tt\d+` (`06-…`, разд. 4).
3. **План.** `auto_explain` для медленных запросов (`06-…`, разд. 5) или ручной `EXPLAIN (ANALYZE, BUFFERS)` на копии. Перед ним — параметры сеанса как у платформы (п. 1.3).
   
   Запрос с временными таблицами вручную не воспроизвести — их нет в вашем сеансе. Для этого есть `auto_dump`: выгружает запрос, план, временные таблицы и данные. Параметры в сборке Postgres Pro и в сборке с патчами 1С различаются — `../guides/07-…`, разд. 8.7.
4. **Имена.** `_Reference123`, `_Fld456` → объекты метаданных: `ПолучитьСтруктуруХраненияБазыДанных()` и `06-…`, разд. 8.
5. **Что в плане искать** (`06-…`, разд. 7):
   - расхождение оценки и факта числа строк (`rows=` против `actual rows=`) — особенно на временных таблицах и подзапросах виртуальных таблиц;
   - `Seq Scan` по большой таблице при условии из `ГДЕ`, которое по стандарту должно идти по индексу;
   - много `Nested Loop`/`Hash Join` с таблицами документов — признак «через точку» от составного поля.
6. **Решение и передача.** Своими силами — раздел 5. Разработчику передать:
   - текст запроса 1С (по `Context` — модуль и строка);
   - SQL и план;
   - объём таблиц;
   - номер нарушенного стандарта из раздела 2.

## 5. Что может администратор, а что — только разработчик

| Средство | Кто | Когда помогает | Подробно |
|---|---|---|---|
| Свежая статистика (`ANALYZE`, настройки автоочистки для больших таблиц) | администратор | неверные оценки строк на постоянных таблицах | `05-…` |
| Обслуживание индексов (`REINDEX`, раздувание) | администратор | деградация после массовых перепроведений [прил. 8] | `05-…` |
| `plantuner.fix_empty_table = on` | администратор | неверные планы с только что созданными временными таблицами | `../guides/07-…`, разд. 8.5 |
| `from_collapse_limit`, `join_collapse_limit`, `geqo_threshold` по ИТС | администратор | запросы из многих таблиц | `02-…`, `../its-metod/pg-nastrojki-…` |
| `work_mem`, `temp_buffers`, `max_locks_per_transaction` | администратор | сортировки и хеши на диске, много временных таблиц | `02-…` |
| Пересчёт и включение итогов регистров, «Разрешить итоги: срез последних» | администратор (пересчёт), разработчик (свойство регистра) | медленные `Остатки`, `СрезПоследних` | [std 708, 733] |
| Дополнительные индексы, индексирование реквизитов | разработчик (конфигурация) | условие не попадает в индекс | [std 652, 791] |
| Переписывание запроса: временные таблицы, параметры виртуальных таблиц, `ВЫРАЗИТЬ`, `ОБЪЕДИНИТЬ ВСЕ` вместо `ИЛИ`, отказ от `ПОЛНОЕ СОЕДИНЕНИЕ` | разработчик | всё из раздела 2 | [std 435, 654–658, 777] |
| Пересмотр ролей с RLS | разработчик или администратор прав | запросы ко всем таблицам с RLS медленные | [std 658, п. 7] |
| `plantuner.disable_index` / `enable_index` | администратор, **только для расследования** | проверить гипотезу «без этого индекса быстрее» | [PGPro F.45] |

## Типичные ошибки (симптом → причина → решение)

| Симптом | Причина | Решение |
|---|---|---|
| Отчёт то быстрый, то медленный; после `ANALYZE` быстрее, потом опять медленный | соединение с вложенным запросом или виртуальной таблицей | разработчику — временная таблица с индексом [std 655]; администратору — статистика и `fix_empty_table` |
| `ERROR: invalid regular expression: invalid character range` в журнале PostgreSQL | неэкранированный шаблон `ПОДОБНО` с `[`, `]`, `^` | `СПЕЦСИМВОЛ` [std 726] |
| В SQL-тексте десятки `LEFT JOIN` с таблицами документов | «через точку» от поля составного типа (`Регистратор.Дата`) | `ВЫРАЗИТЬ` и `ССЫЛКА` [std 654] |
| `Seq Scan` по большой таблице итогов при запросе остатков | условие во внешнем `ГДЕ` или не по первому измерению | условия в параметры [std 657]; индекс или порядок измерений [std 652] |
| Остатки на текущую дату медленные | в параметр передана дата; не все измерения во внешнем запросе | без даты, все измерения во внешнем запросе [std 733] |
| Запрос с `ПОЛНОЕ СОЕДИНЕНИЕ` медленный на PostgreSQL, на MS SQL нормальный | особенность PostgreSQL | переписать без него [std 435] |
| Ошибка «несоответствие типов» при `ДОБАВИТЬ` во временную таблицу | тип колонки задан первым `ПОМЕСТИТЬ` (длина строки, разрядность) | расширить тип через `ВЫРАЗИТЬ` при создании [ИТС-разр 8.4.10.2] |
| `out of shared memory`, подсказка про `max_locks_per_transaction` | много таблиц и индексов (в том числе временных) в одной транзакции | рекомендации ИТС `512…2000` (`02-…`) |
| Запрос из конструктора медленный только у части пользователей | RLS: у пользователя две роли с разными ограничениями на один объект | одна роль на объект [std 658, п. 7] |
| `EXPLAIN` в `psql` даёт другой план, чем в ТЖ | не выставлены параметры сеанса платформы | `SET enable_mergejoin = off; SET cpu_operator_cost = 0.001; …` (`06-…`) |
| Найдено запросом, но `Справочник.Найти…` не находит | концевые пробелы и регистр в запросе не учитываются | ожидаемое поведение [ИТС-разр 8.4.18.3] |
| Восстановление `pg_restore` падает на операторах `mchar`/`mvarchar` | пустой `search_path`, операторы вне `pg_catalog` | [PGPro 10.2.1]; пробное восстановление; `../guides/07-…`, разд. 8.2 |

## Быстрая шпаргалка — задача → где и что

| Задача | Где и что |
|---|---|
| Какой SQL сгенерирован для запроса 1С | ТЖ, событие `DBPOSTGRS`, свойство `Sql` (`../1c/07-…`) |
| Какая строка кода вызвала запрос | `Context` того же события |
| Какой объект метаданных за `_Reference123` | `ПолучитьСтруктуруХраненияБазыДанных()`; `06-…`, разд. 8 |
| Самые тяжёлые запросы | `pg_stat_statements` с группировкой `tt\d+` (`06-…`, разд. 4) |
| План как у платформы | `SET enable_mergejoin = off; SET cpu_operator_cost = 0.001;` затем `EXPLAIN (ANALYZE, BUFFERS)` |
| Воспроизвести запрос с временными таблицами | `auto_dump` (`../guides/07-…`, разд. 8.7) |
| Включён ли `fix_empty_table` | `SHOW plantuner.fix_empty_table;` (после загрузки библиотеки) |
| Проверить гипотезу про индекс | `LOAD 'plantuner'; SET plantuner.disable_index = 'имя_индекса'; EXPLAIN …` — только на копии или в своём сеансе |
| Свежесть статистики таблицы | `SELECT relname, last_analyze, last_autoanalyze, n_mod_since_analyze FROM pg_stat_user_tables WHERE relname = '_accumrgt123';` |
| Какой стандарт нарушен | раздел 2 этой статьи → `https://its.1c.ru/db/v8std/content/<номер>/hdoc` |

## Что не удалось подтвердить

- Точный вид SQL, который платформа генерирует для виртуальных таблиц, `ПОЛНОЕ ВНЕШНЕЕ СОЕДИНЕНИЕ` на PostgreSQL, `ИТОГИ`. В документации его нет — смотреть `Sql` в техжурнале своей базы.
- Где именно платформа использует оператор `==` модуля `fulleq`.
- Какая часть обработки `ИТОГИ` выполняется в СУБД, а какая на сервере 1С.
- Наличие `enable_temp_memory_catalog` и `enable_temp_rd_buffers` в сборке Postgres Pro (описаны для сборок с патчами 1С).
- Актуальность статей ИТС 4208 и 1556 (2010 год) для PostgreSQL 16–18: рекомендации сохранены как осторожные правила, их подтверждают стандарты 435 и 655.
