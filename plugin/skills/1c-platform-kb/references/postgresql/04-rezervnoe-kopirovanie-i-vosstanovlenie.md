## Кратко — 20 главных фактов и команд

1. Есть три вида копий. **Логическая** (`pg_dump`) — одна база, переносима между версиями и сборками (с оговоркой из п. 5). **Физическая** (`pg_basebackup`, `pg_probackup`) — весь кластер PostgreSQL целиком, только та же старшая версия и та же сборка. **Непрерывное архивирование WAL** поверх физической копии даёт восстановление на любой момент времени (PITR) [офиц.].
2. Минимум для малой базы — ежедневный дамп каждой базы в формате custom:
   ```bash
   sudo -u postgres pg_dump -Fc -f /backup/dump/zup_$(date +%F).dump zup
   ```
3. Восстановление дампа в **новую** базу (базу создают из `template0`) [офиц.]:
   ```bash
   sudo -u postgres createdb -T template0 zup_copy
   sudo -u postgres pg_restore -d zup_copy -j 4 /backup/dump/zup_2026-10-10.dump
   sudo -u postgres vacuumdb -d zup_copy --analyze-only -j 4
   ```
4. Роли и табличные пространства в `pg_dump` не попадают — отдельно: `pg_dumpall --globals-only > globals.sql` [офиц.].
5. Дамп базы 1С содержит типы `mchar`/`mvarchar` и функции модулей `fulleq`, `fasttrun`. В «ванильный» PostgreSQL он не восстановится — нужна сборка с доработками для 1С той же или более новой старшей версии (раздел 2.7).
6. Физическая копия всего кластера одной командой (WAL включён, копию можно запускать как есть) [офиц.]:
   ```bash
   sudo -u postgres pg_basebackup -D /backup/base/$(date +%F) -Ft -z -X stream -c fast -P
   ```
   С PostgreSQL 17 есть встроенные инкрементальные копии: `summarize_wal = on`, `pg_basebackup --incremental=<backup_manifest прошлой копии>`, сборка цепочки — `pg_combinebackup` [офиц.].
7. PITR включается тремя параметрами: `wal_level = replica` (по умолчанию), `archive_mode = on` (нужен перезапуск), `archive_command = '…'` (достаточно reload) [офиц.].
8. Восстановление на момент времени: распаковать базовую копию → задать `restore_command` и `recovery_target_time` → создать пустой файл `recovery.signal` в каталоге данных → запустить сервер [офиц.]. После любого восстановления с переходом на новую линию времени (PITR, promote) сразу делайте новую полную копию.
9. Перед обновлением конфигурации 1С поставьте именованную точку: `SELECT pg_create_restore_point('before_update_2026_10_10');` — потом к ней можно вернуться через `recovery_target_name` [офиц.].
10. Сломанная архивация WAL = сегменты копятся в `pg_wal` → диск заполняется → сервер останавливается с PANIC. Следить: `SELECT * FROM pg_stat_archiver;`. Файлы из `pg_wal` руками не удалять [офиц.].
11. Восстановление физической копии и PITR откатывают **все базы кластера** сразу. Чтобы вернуть одну базу 1С, копию поднимают рядом (другой каталог, порт 5433), а нужную базу переносят дампом (раздел 11.3).
12. `pg_probackup` — основной инструмент для средних и больших баз: инкрементальные копии (DELTA/PAGE/PTRACK), сжатие, параллельность, проверка, политики хранения, PITR. Открытая версия 2.5.16 поддерживает PostgreSQL 13–18; пакеты `pg-probackup-NN` есть для Ubuntu 22.04 и 24.04, бинарник называется `pg_probackup-NN` [офиц.].
13. Минимальная последовательность pg_probackup:
    ```bash
    pg_probackup-17 init -B /backup/pgpro
    pg_probackup-17 add-instance -B /backup/pgpro -D /var/lib/postgresql/17/main --instance=main
    pg_probackup-17 backup -B /backup/pgpro --instance=main -b FULL  --stream --temp-slot -j 4
    pg_probackup-17 backup -B /backup/pgpro --instance=main -b DELTA --stream --temp-slot -j 4
    pg_probackup-17 show -B /backup/pgpro
    ```
14. Восстановление pg_probackup: `pg_probackup-17 restore -B /backup/pgpro --instance=main -j 4` (каталог данных должен быть пуст либо указан режим `-I checksum`); на момент времени — `--recovery-target-time='2026-10-10 14:25:00+05'` (нужен архив WAL) [офиц.].
15. Хранение в pg_probackup: `set-config --retention-redundancy=2 --retention-window=14`, чистка — `delete --delete-expired --delete-wal` [офиц.].
16. Выгрузка в `.dt` — **не резервная копия**: документация 1С прямо не рекомендует её для этой цели (раздел 9.1) [офиц.].
17. Во время восстановления средствами СУБД к информационной базе не должно быть никаких подключений — ни клиентов, ни конфигуратора, ни фоновых и регламентных заданий [офиц.]. Блокировка: `rac infobase update … --sessions-deny=on --scheduled-jobs-deny=on` либо остановка службы сервера 1С.
18. В копию СУБД не попадают: реестр кластера (`1cv8wsrv.lst`, `reg_1541/1CV8Clst.lst`), журнал регистрации (`reg_1541/<UUID базы>/1Cv8Log`), лицензии (`/var/1C/licenses`), конфигурационные файлы, публикации на веб-сервере, хранилище двоичных данных, тома файлов на диске. Их копируют отдельно (раздел 9.5).
19. Копия, которую ни разу не восстанавливали, копией не считается. Минимум раз в месяц — тестовое восстановление на отдельный порт или сервер; между ними — `pg_verifybackup`, `pg_probackup validate`, `pg_restore -l` (раздел 8).
20. Правило 3-2-1: три копии, два разных носителя, одна вне площадки. Копия на диске той же ВМ или того же Windows-хоста от потери хоста не спасает — выносите на NAS, Windows-шару другого компьютера, в S3 (раздел 10).

## 1. Карта методов, термины, пути

### 1.1. Термины

| Термин | Смысл |
|---|---|
| RPO (Recovery Point Objective) | сколько данных допустимо потерять: «копия раз в сутки» = до суток работы; архив WAL с `archive_timeout = 300` = до 5 минут |
| RTO (Recovery Time Objective) | за какое время сервис должен вернуться; определяется скоростью восстановления, а не скоростью копирования |
| Кластер PostgreSQL | один каталог данных (PGDATA), один порт, много баз. Не путать с кластером серверов 1С |
| WAL | журнал предзаписи; сегменты по 16 МБ в `PGDATA/pg_wal` |
| Базовая копия (base backup) | физическая копия каталога данных, снятая на работающем сервере |
| PITR | восстановление базовой копии и воспроизведение архивных WAL до заданной точки |
| Линия времени (timeline) | «ветка истории» кластера; новая создаётся после каждого завершённого восстановления из архива. Номер — первые 8 шестнадцатеричных цифр имени сегмента WAL |

### 1.2. Сравнение методов

| Свойство | `pg_dump` (логическая) | `pg_basebackup` (физическая) | Физическая + архив WAL (PITR) | `pg_probackup` |
|---|---|---|---|---|
| Единица копирования | одна база | весь кластер | весь кластер | весь кластер (восстановить можно часть баз) |
| Работа пользователей во время копирования | не мешает (см. 2.8) | не мешает | не мешает | не мешает |
| Восстановление в другую старшую версию | да (в более новую) | нет | нет | нет |
| Восстановление в другую сборку | да, если есть модули 1С | только та же сборка | только та же сборка | только та же сборка |
| Точка восстановления | момент начала дампа | момент окончания копии | любой момент после окончания базовой копии | любой момент (при архиве WAL) |
| Инкрементальность | нет | с PostgreSQL 17 | — | да (DELTA, PAGE, PTRACK) |
| Скорость восстановления больших баз | медленно (перестроение индексов) | быстро (копирование файлов) | быстро + время проигрывания WAL | быстро, параллельно |
| Обнаруживает логическую порчу при копировании | да (читает все строки таблиц) | нет (копирует блоки; контрольные суммы — если включены) | нет | проверка заголовков страниц всегда, контрольных сумм — если включены |
| Типичное применение | малые базы, перенос, копия перед обновлением, долгое хранение | средние базы, создание реплики | RPO в минутах | средние и большие базы |

## 2. Логические копии: pg_dump, pg_restore, pg_dumpall

### 2.1. pg_dump: что делает и как запускать

`pg_dump` выгружает **одну** базу в согласованном состоянии на момент начала работы. Он не блокирует чтение и запись; мешают ему (и он мешает) только операции, которым нужна исключительная блокировка таблиц, — большинство форм `ALTER TABLE` [офиц.]. Для базы 1С это означает: дамп можно снимать при работающих пользователях, но не одновременно с обновлением конфигурации и реструктуризацией.

Чтобы выгрузить базу целиком, нужны права на чтение всех таблиц — практически это суперпользователь [офиц.]. На сервере проще всего запускать от системного пользователя `postgres` через локальный сокет (аутентификация `peer`, пароль не нужен).

Форматы (`-F`) [офиц.]:

| Ключ | Формат | Что на выходе | Сжатие | Параллельная выгрузка `-j` | Параллельное восстановление | Выборочное восстановление |
|---|---|---|---|---|---|---|
| `-Fp` | plain | SQL-скрипт (по умолчанию), восстанавливается через `psql` | нет (сжимать внешним архиватором или `-Z`) | нет | нет | нет |
| `-Fc` | custom | один файл-архив для `pg_restore` | по умолчанию gzip | нет | да | да |
| `-Fd` | directory | каталог: по файлу на таблицу + оглавление `toc.dat` | по умолчанию gzip | **да** (единственный формат) | да | да |
| `-Ft` | tar | tar-архив | не поддерживается | нет | нет | да, но порядок загрузки данных таблиц изменить нельзя |

Для баз 1С рабочие варианты — `-Fc` (один файл, удобно ротировать и переносить) и `-Fd -j N` (быстрее на больших базах). `-Ft` и `-Fp` для регулярных копий не нужны.

Основные ключи [офиц., документация PostgreSQL 18]:

| Ключ | Назначение |
|---|---|
| `-f файл` | куда писать; для `-Fd` — имя **нового** каталога |
| `-j N` | выгружать N таблиц параллельно (только `-Fd`); открывает N+1 подключений |
| `-Z уровень` / `-Z метод[:параметры]` | сжатие: `gzip`, `lz4`, `zstd`, `none`; параметры — число (уровень) либо `level=…`, для zstd ещё `long`. Примеры: `-Z 6`, `-Z zstd:3`, `-Z zstd:level=9,long=1`, `-Z 0` |
| `-n шаблон` / `-N шаблон` | только указанные схемы / исключить схемы (у 1С всё лежит в `public`) |
| `-t шаблон` / `-T шаблон` | только указанные таблицы / исключить таблицы |
| `--exclude-table-data=шаблон` | определение таблицы выгрузить, данные — нет |
| `-s` / `-a` | только схема / только данные |
| `--section=имя` | часть дампа: `pre-data` (определения), `data` (данные), `post-data` (индексы и ограничения) |
| `-O`, `--no-owner` | не выгружать команды смены владельца |
| `-x`, `--no-privileges` | не выгружать `GRANT`/`REVOKE` |
| `-c`, `--clean` и `--if-exists` | добавить `DROP …` перед созданием объектов (для `-Fp`; для архивных форматов задаётся при `pg_restore`) |
| `-C`, `--create` | добавить `CREATE DATABASE` (для `-Fp`) |
| `--lock-wait-timeout=время` | не ждать блокировку таблицы дольше указанного |
| `--no-sync` | не ждать записи на диск — только для тестов |
| `--filter=файл` | правила include/exclude из файла (17+) |
| `--statistics` | выгрузить статистику планировщика (18+; по умолчанию не выгружается) |
| `-v` | подробный вывод |
| `-h`, `-p`, `-U`, `-d`, `-w`, `-W` | параметры подключения; `-w` — никогда не спрашивать пароль (для скриптов) |

Примеры:

```bash
# 1. Обычная ежедневная копия: один файл, сжатие по умолчанию (gzip)
sudo -u postgres pg_dump -Fc -f /backup/dump/zup_$(date +%F).dump zup

# 2. То же со сжатием zstd (pg_dump 16+; быстрее и компактнее gzip)
sudo -u postgres pg_dump -Fc -Z zstd:3 -f /backup/dump/zup_$(date +%F).dump zup

# 3. Большая база: каталог, 4 параллельных потока
sudo -u postgres pg_dump -Fd -j 4 -Z zstd:3 -f /backup/dump/zup_$(date +%F).dir zup

# 4. Одна таблица (точечное восстановление справочника)
sudo -u postgres pg_dump -Fc -t 'public._reference155' -f /backup/dump/zup_ref155.dump zup

# 5. Копия для разработчика без данных тяжёлой таблицы (НЕ резервная копия!)
sudo -u postgres pg_dump -Fc --exclude-table-data='public._inforg12345' -f /tmp/zup_dev.dump zup

# 6. Удалённо, с паролем из ~/.pgpass (формат строки: хост:порт:база:пользователь:пароль, права 0600)
pg_dump -h 192.168.1.20 -p 5432 -U postgres -w -Fc -f zup.dump zup

# 7. Текстовый дамп с внешним сжатием
sudo -u postgres pg_dump zup | zstd -T0 -3 > /backup/dump/zup.sql.zst
```

Проверка, что сборка `pg_dump` умеет нужный алгоритм: при отсутствии поддержки команда сразу завершится ошибкой вида `this build does not support compression with zstd` — тогда используйте gzip (`-Z 6`).

В Debian-раскладке `/usr/bin/pg_dump` — обёртка `pg_wrapper`, которая выбирает версию утилиты по кластеру. Если на сервере несколько версий, указывайте явно: `/usr/lib/postgresql/17/bin/pg_dump …` или `pg_dump --cluster 17/main …`.

### 2.2. pg_dumpall: роли и глобальные объекты

`pg_dumpall` выгружает весь кластер одним SQL-скриптом; других форматов у него нет (в PostgreSQL 18 ключа `-F` нет) [офиц.]. Снимки разных баз при этом не синхронизированы между собой. На практике его используют только для глобальных объектов, а базы выгружают по одной через `pg_dump`.

| Ключ | Назначение |
|---|---|
| `-g`, `--globals-only` | только роли и табличные пространства |
| `-r`, `--roles-only` | только роли |
| `-t`, `--tablespaces-only` | только табличные пространства |
| `--no-role-passwords` | без хешей паролей (роли читаются из `pg_roles`, а не из `pg_authid`) |
| `-c`, `--clean`, `--if-exists` | с командами `DROP` |
| `--exclude-database=шаблон` | пропустить базы |
| `-f файл` | вывод в файл |

```bash
sudo -u postgres pg_dumpall --globals-only -f /backup/dump/globals_$(date +%F).sql
# восстановление (ошибка «role "postgres" already exists» безвредна):
sudo -u postgres psql -X -f /backup/dump/globals_2026-10-10.sql postgres
```

Файл с глобальными объектами содержит хеши паролей ролей — храните его с правами `0600`.

### 2.3. pg_restore

`pg_restore` восстанавливает архивы форматов custom, directory и tar. Текстовый дамп (`-Fp`) восстанавливается только через `psql`.

| Ключ | Назначение |
|---|---|
| `-d база` | подключиться к базе и восстанавливать прямо в неё. Без `-d` утилита печатает SQL-скрипт |
| `-j N` | параллельно загружать данные и строить индексы и ограничения. Только custom и directory; вход — обычный файл или каталог (не конвейер); несовместим с `-1` |
| `-C`, `--create` | создать базу перед восстановлением. База из `-d` используется только для выполнения `DROP DATABASE`/`CREATE DATABASE`; данные идут в базу **с именем из архива** |
| `-c`, `--clean` | удалять объекты перед созданием; вместе с `-C` — удалить и пересоздать базу целиком |
| `--if-exists` | `DROP … IF EXISTS` (только вместе с `--clean`) |
| `-l`, `--list` | вывести оглавление архива |
| `-L файл`, `--use-list=файл` | восстановить только элементы из файла-списка и в его порядке |
| `-O`, `--no-owner` | не выполнять смену владельца: всё будет принадлежать подключившейся роли |
| `-x`, `--no-privileges` | не восстанавливать права |
| `--role=имя` | выполнить `SET ROLE` после подключения |
| `-n схема`, `-t таблица`, `-I индекс`, `-P 'функция(арг)'`, `-T триггер` | выборочное восстановление. `-t` в `pg_restore` не понимает шаблоны и не тянет зависимые объекты (индексы) — в отличие от `pg_dump -t` |
| `-s` / `-a` / `--section=…` | только схема / только данные / секция |
| `-1`, `--single-transaction` | всё одной транзакцией (подразумевает `-e`) |
| `--transaction-size=N` | фиксировать примерно каждые N объектов (17+; подразумевает `-e`) |
| `-e`, `--exit-on-error` | остановиться на первой ошибке. По умолчанию утилита продолжает и в конце сообщает число ошибок |
| `--no-tablespaces` | создавать объекты в табличном пространстве по умолчанию |
| `-v` | подробный вывод |

```bash
# оглавление архива (заодно быстрая проверка, что файл читается)
pg_restore -l /backup/dump/zup_2026-10-10.dump | head -40

# восстановить в заранее созданную пустую базу, 4 потока
sudo -u postgres pg_restore -d zup_copy -j 4 /backup/dump/zup_2026-10-10.dump

# создать базу с исходным именем (zup) и восстановить в неё
sudo -u postgres pg_restore -C -d postgres -j 4 /backup/dump/zup_2026-10-10.dump

# удалить существующую базу zup, создать заново и восстановить (подключений к zup быть не должно)
sudo -u postgres pg_restore --clean --if-exists -C -d postgres -j 4 /backup/dump/zup_2026-10-10.dump

# выборочно: одну таблицу с индексами через список
pg_restore -l zup.dump > zup.toc
grep -i '_reference155' zup.toc > only.toc          # отредактировать при необходимости
sudo -u postgres pg_restore -d zup_tmp -L only.toc zup.dump

# только структура без данных
sudo -u postgres pg_restore -d zup_schema -s zup.dump
```

После восстановления обязательно собрать статистику — в дампе её нет (до PostgreSQL 18 совсем, в 18 — только при `pg_dump --statistics`), а без неё планировщик строит плохие планы [офиц.]:

```bash
sudo -u postgres vacuumdb -d zup_copy --analyze-only -j 4
```

Код возврата `pg_restore` ненулевой, если были ошибки; в конце вывода — строка `warning: errors ignored on restore: N`. В скриптах проверяйте код возврата и используйте `-e`.

### 2.4. Восстановление базы 1С в новую базу и регистрация в кластере 1С

Задача: развернуть копию рабочей базы под другим именем (тестовая копия, проверка бэкапа, поиск удалённых данных).

```bash
# 1. Глобальные объекты — только если это другой сервер и нужных ролей там нет
sudo -u postgres psql -X -f /backup/dump/globals_2026-10-10.sql postgres

# 2. Пустая база из template0. Кодировка и локаль — как у исходной (посмотреть: psql -l)
sudo -u postgres createdb -T template0 zup_copy

# 3. Данные
sudo -u postgres pg_restore -d zup_copy -j 4 -e /backup/dump/zup_2026-10-10.dump

# 4. Статистика
sudo -u postgres vacuumdb -d zup_copy --analyze-only -j 4
```

Почему `template0`: дамп создаётся относительно `template0`; если в `template1` есть свои объекты, восстановление в базу, созданную из `template1`, даст конфликты [офиц.].

Почему от суперпользователя: в базе 1С есть функции на языке C (модули `mchar`, `fulleq`, `fasttrun`), а создавать такие функции может только суперпользователь (подтверждено 19.10.2026: язык `c` в каталоге `pg_language` недоверенный — исходный файл `pg_language.dat` PostgreSQL 18, а функции на недоверенных языках может создавать только суперпользователь — документация PostgreSQL 18, описание `pg_language.lanpltrusted`) (см. 2.7).

Регистрация восстановленной базы в кластере серверов 1С (утилита `rac`, сервер администрирования `ras` должен быть запущен на порту 1545). Ключ `--create-database` **не указывают** — база данных уже существует:

```bash
V=8.3.27.1688; RAC=/opt/1cv8/x86_64/$V/rac
CL=$($RAC cluster list | awk '/^cluster/{print $3}')
$RAC infobase --cluster=$CL create --name=zup_copy --dbms=PostgreSQL \
     --db-server=localhost --db-name=zup_copy --locale=ru \
     --db-user=postgres --db-pwd='***' \
     --license-distribution=allow --scheduled-jobs-deny=on
$RAC infobase --cluster=$CL summary list
```

Пояснения:

- `--scheduled-jobs-deny=on` — копия создаётся с заблокированными регламентными заданиями. Без этого копия начнёт рассылать почту, выполнять обмены и загрузки наравне с рабочей базой [практика].
- Если у кластера есть администраторы, добавьте `--cluster-user=… --cluster-pwd=…`.
- Если PostgreSQL слушает нестандартный порт, его указывают в строке сервера: `--db-server='localhost port=5433'` (подтверждено 19.10.2026: документация 8.3.27, «Руководство администратора», 5.2.1.3.3 — формат `<имя_сервера> port=<порт>;`, пример `localhost port=6432;`; конспект `../its-docs/adm-gl05-spisok-infobaz.md`).
- То же можно сделать из окна запуска 1С: «Добавить» → «Создание новой информационной базы» → «без конфигурации» → «На сервере 1С:Предприятия», указав имя уже существующей базы данных.
- В конфигурациях на БСП при первом входе в копию появится вопрос о перемещении или восстановлении базы; для копии выбирают вариант «это копия информационной базы» — тогда работа с внешними ресурсами (обмены, почта, синхронизации) остаётся заблокированной [практика].
- Журнал регистрации у новой информационной базы свой (новый UUID каталога в `reg_1541`); журнал исходной базы в копию не переносится.

### 2.5. Восстановление текстового дампа

```bash
sudo -u postgres createdb -T template0 zup_copy
zstd -dc /backup/dump/zup.sql.zst | sudo -u postgres psql -X --set ON_ERROR_STOP=on zup_copy
```

`-X` — не читать `~/.psqlrc`; `ON_ERROR_STOP=on` — остановиться на первой ошибке (иначе `psql` продолжит и база получится неполной); `-1` — всё одной транзакцией [офиц.].

### 2.6. Совместимость версий утилит и сервера [офиц.]

- `pg_dump` **не выгружает** с сервера более новой старшей версии, чем он сам, — откажется сразу.
- `pg_dump` выгружает со старых серверов, вплоть до 9.2.
- Дамп рассчитан на загрузку в сервер той же или **более новой** версии. Загрузка в более старую старшую версию не гарантируется.
- `pg_restore` не читает архив, если версия его формата новее той, что знает утилита (ошибка `unsupported version (1.NN) in file header`). Формат меняется не в каждой старшей версии: 1.14 — PostgreSQL 14–15, 1.15 — 16, 1.16 — 17–18 (исправлено 19.10.2026 по исходному коду, `src/bin/pg_dump/pg_backup_archiver.h` веток 14–18); при совпадающем формате архив прочитается, но SQL из дампа новой версии в старый сервер может не загрузиться — правило «восстанавливать утилитой той же или более новой версии» остаётся.
- Практическое правило при переходе на новую версию: выгружать утилитой `pg_dump` **новой** версии со старого сервера, восстанавливать `pg_restore` той же новой версии. При разных версиях полезен ключ `--quote-all-identifiers`.
- `pg_basebackup` работает с сервером той же или более старой версии; восстановить физическую копию можно только в ту же старшую версию.

### 2.7. Особенности дампов из сборок для 1С

Что есть в базе 1С сверх обычного PostgreSQL:

- типы данных `mchar` и `mvarchar` (модуль `mchar`) — аналоги `CHAR`/`VARCHAR` из MS SQL: сравнение без учёта регистра, особая обработка хвостовых пробелов, хранение в двухбайтовом Unicode независимо от кодировки базы, сравнение и смена регистра через библиотеку ICU [офиц., документация «PostgreSQL для 1С» 16, F.29, сверено 19.10.2026];
- операторы и функции модуля `fulleq`;
- функция `fasttruncate()` модуля `fasttrun` — быстрое нетранзакционное усечение временных таблиц [офиц.];
- модули `online_analyze` и `plantuner` объектов в базе не создают: это библиотеки, подключаемые через `postgresql.conf`.

Следствия для резервного копирования:

1. В дампе базы 1С есть определения типов, функций и операторов, которые ссылаются на библиотеки `$libdir/mchar`, `$libdir/fulleq`, `$libdir/fasttrun`. В «ванильном» PostgreSQL (пакет `postgresql` из Ubuntu или PGDG) этих библиотек нет, поэтому восстановление заканчивается ошибками вида `could not access file "$libdir/mchar": No such file or directory`, а следом — `type "public.mvarchar" does not exist` для всех таблиц ⚠ (точный текст зависит от того, как объекты попали в базу; суть неизменна: в ванильную сборку дамп 1С не загрузится).
2. Восстанавливать можно в любую сборку, где эти модули есть: сборка от «1С», «PostgreSQL для 1С» от Postgres Professional, Postgres Pro Standard / Enterprise — той же или более новой старшей версии. Логический дамп между такими сборками переносим (уточнено 19.10.2026 по документации «PostgreSQL для 1С» 16, раздел 18.4 «Миграция»: выгрузка и загрузка — штатный способ перехода между основными версиями и между продуктами на базе PostgreSQL; пробное восстановление всё равно обязательно — см. п. 5).
3. Физические копии (`pg_basebackup`, `pg_probackup`) переносить между **разными** сборками нельзя (уточнено 19.10.2026 по той же документации, раздел 18.4: разные продукты на базе PostgreSQL даже одной основной версии могут быть двоично несовместимы; у Postgres Pro Enterprise формат заведомо другой). Между сборками переходят через `pg_dump`/`pg_restore`; документация сборки для перехода между основными версиями называет также `pg_upgrade` — его применимость между разными продуктами проверять на копии.
4. Физическая копия, восстановленная на сервере с другой версией ОС, может получить «битые» индексы из-за смены правил сортировки в glibc (вики PostgreSQL, «Locale data changes» — затронуты B-tree-индексы по `text`/`varchar`/`char`) [офиц.]. Поля 1С в основном имеют типы `mchar`/`mvarchar`, сравнение которых идёт через ICU, — смена версии ICU может дать тот же эффект ⚠. После физического восстановления на другой выпуск Ubuntu выполните `REINDEX DATABASE` для каждой базы либо переносите базы дампом.
5. `pg_restore` работает с пустым `search_path` (по сути только `pg_catalog`), поэтому операторы нестандартных типов (`mchar`/`mvarchar`), определённые в другой схеме, могут не найтись, и восстановление или `pg_upgrade` завершится ошибкой; конструкции без явного оператора (`IS DISTINCT FROM`, `IN`, `NULLIF`, `JOIN … USING`, простой `CASE`) так не исправить [офиц., документация «PostgreSQL для 1С» 16, подраздел 10.2.1; добавлено 19.10.2026]. Для баз 1С это ещё один довод за регулярное пробное восстановление дампа (раздел 8.2); подробнее — `../guides/07-postgresql-dlya-1c-s-1c-postgres-ru.md`, раздел 8.2.

Как посмотреть, что именно лежит в базе:

```bash
sudo -u postgres psql -d zup -c '\dx'                       # расширения (часто только plpgsql)
sudo -u postgres psql -d zup -c '\dT public.m*'             # типы mchar, mvarchar
sudo -u postgres psql -d zup -Atc "SELECT DISTINCT probin FROM pg_proc WHERE probin LIKE '\$libdir/%'"
pg_restore -l /backup/dump/zup.dump | grep -ciE 'mchar|fulleq|fasttrun'   # сколько таких объектов в дампе
ls /usr/lib/postgresql/17/lib/ | grep -E 'mchar|fulleq|fasttrun'          # есть ли библиотеки в целевой сборке
```

### 2.8. Подводные камни pg_dump применительно к 1С

- **Обновление конфигурации во время дампа.** `pg_dump` в начале берёт блокировки `ACCESS SHARE` на все таблицы; реструктуризация 1С (`ALTER TABLE`, пересоздание таблиц) будет ждать окончания дампа, а для пользователей это выглядит как зависшее обновление. Расписание копий разводите с окнами обновлений.
- **Время и нагрузка.** Дамп читает все данные и создаёт длинную транзакцию: на это время откладывается очистка «мёртвых» версий строк (растёт раздувание таблиц). Большие базы выгружайте ночью.
- **Восстановление дольше выгрузки.** Основное время `pg_restore` — построение индексов; ускоряется ключом `-j` и временным увеличением `maintenance_work_mem`.
- **Очень большие двоичные значения.** Если в одной строке лежит значение `bytea` в сотни мегабайт (вложенный файл, огромный макет), `pg_dump` может упасть с `invalid memory alloc request size` или `out of memory`: при выгрузке значение преобразуется в текст и перестаёт помещаться в предел 1 ГБ на поле (предел «field size — 1 GB» — приложение K «PostgreSQL Limits» документации PostgreSQL 18, сверено 11.10.2026). Физических копий это ограничение не касается.
- **Строки `\restrict` в текстовых дампах.** Текстовые дампы свежих минорных версий содержат метакоманды `\restrict` / `\unrestrict`; старый `psql` их не знает и выдаёт `invalid command \restrict` — появление команды подтверждено примечаниями к выпускам 17.6, 16.10, 15.14, 14.19 и 13.22 (сверено 11.10.2026), а текст ошибки — обычное сообщение psql о неизвестной команде (появилось в минорных выпусках августа 2025 года). Лечится обновлением клиента `psql`; архивных форматов (`-Fc`, `-Fd`) не касается.
- **Временные таблицы** 1С в дамп не попадают — это нормально.
- **`pg_restore --clean` поверх рабочей базы** удаляет только те объекты, которые есть в архиве; таблицы, появившиеся после снятия дампа, останутся мусором. Для 1С надёжнее удалить базу и создать заново (раздел 9.3).

## 3. Физические копии: pg_basebackup

### 3.1. Что нужно для работы [офиц.]

- Подключение идёт по протоколу репликации: нужна роль с атрибутом `REPLICATION` или суперпользователь, а в `pg_hba.conf` — строка, разрешающая подключение к псевдобазе `replication`.
- `max_wal_senders` должен оставлять свободными минимум два подключения: одно для копии, второе для потоковой передачи WAL (значение по умолчанию — 10).
- `wal_level` — `replica` или выше (это значение по умолчанию). При `wal_level = minimal` ни `pg_basebackup`, ни архивация WAL не работают.
- В стандартном `pg_hba.conf` строки для локальной репликации уже есть (`local replication all peer`), поэтому запуск от пользователя `postgres` на самом сервере работает без настройки.

Отдельная роль для копирования с другого узла:

```bash
sudo -u postgres psql -c "CREATE ROLE backup_repl WITH LOGIN REPLICATION PASSWORD 'СЛОЖНЫЙ_ПАРОЛЬ';"
echo 'host  replication  backup_repl  192.168.1.50/32  scram-sha-256' | sudo tee -a /etc/postgresql/17/main/pg_hba.conf
sudo systemctl reload postgresql@17-main
```

### 3.2. Ключи pg_basebackup [офиц., PostgreSQL 18]

| Ключ | Назначение |
|---|---|
| `-D каталог` | куда писать (обязателен). Каталог создаётся; если существует — должен быть пуст. `-D -` — tar в стандартный вывод (только без потоковой передачи WAL и без дополнительных табличных пространств) |
| `-F p` / `-F t` | формат: `plain` (по умолчанию) — готовый каталог данных; `tar` — `base.tar` и по одному tar на каждое дополнительное табличное пространство |
| `-X none` / `-X fetch` / `-X stream` | WAL: не включать / забрать в конце / передавать потоком во время копии (по умолчанию `stream`). В формате tar WAL пишется в отдельный `pg_wal.tar` |
| `-z` | сжать tar-файлы gzip (уровень по умолчанию) |
| `-Z [client-]метод[:параметры]`, `-Z server-метод[:параметры]` | сжатие на клиенте (по умолчанию) или на сервере: `gzip`, `lz4`, `zstd`, `none` или число (0 — без сжатия, больше 0 — gzip). Параметры: уровень либо `level=`, `long`, `workers=`. `pg_wal.tar` сжимается только клиентским gzip |
| `-c fast` / `-c spread` | контрольная точка в начале копии: `spread` (по умолчанию) — растянутая, копия может стартовать с задержкой в минуты; `fast` — немедленная, с кратковременным всплеском ввода-вывода |
| `-P` | показывать прогресс |
| `-R` | создать `standby.signal` и записать параметры подключения в `postgresql.auto.conf` (для реплики) |
| `-l метка` | метка копии |
| `-r скорость` | ограничить скорость передачи: от 32 кБ/с до 1024 МБ/с, например `-r 50M` |
| `-C -S слот` | создать постоянный слот репликации и использовать его; `--no-slot` — не создавать временный слот |
| `-T старый=новый` | перенос табличного пространства (только plain) |
| `--waldir=путь` | вынести WAL в отдельный каталог (только plain) |
| `-t client`, `-t server:/путь`, `-t blackhole` | куда писать копию; `server:` — на стороне сервера (нужен суперпользователь или роль `pg_write_server_files`; несовместимо с `-X stream`) |
| `-i файл`, `--incremental=файл` | инкрементальная копия относительно манифеста предыдущей (сервер 17+) |
| `--manifest-checksums=алгоритм` | `NONE`, `CRC32C` (по умолчанию), `SHA224`, `SHA256`, `SHA384`, `SHA512` |
| `--no-manifest` | не создавать манифест (не делайте так: `pg_verifybackup` и инкрементальные копии без него не работают) |
| `--no-verify-checksums` | не проверять контрольные суммы страниц при копировании |
| `-N`, `--no-sync` | не ждать записи на диск (только тесты) |
| `-h`, `-p`, `-U`, `-d`, `-w`, `-W` | параметры подключения |

### 3.3. Примеры

```bash
# 1. Основной вариант: tar + gzip, WAL потоком, немедленная контрольная точка
sudo -u postgres pg_basebackup -D /backup/base/$(date +%F) -Ft -z -X stream -c fast -P -l "base $(date +%F)"
#    результат: base.tar.gz, pg_wal.tar.gz, backup_manifest

# 2. Сжатие zstd на клиенте в 4 потока (15+); pg_wal.tar останется несжатым
sudo -u postgres pg_basebackup -D /backup/base/$(date +%F) -Ft -Z client-zstd:level=3,workers=4 -X stream -c fast -P

# 3. plain — готовый к запуску каталог данных
sudo -u postgres pg_basebackup -D /backup/base/plain_$(date +%F) -Fp -X stream -c fast -P

# 4. С другого узла, с ограничением скорости и SHA256 в манифесте
pg_basebackup -h 192.168.1.20 -U backup_repl -w -D /backup/base/$(date +%F) \
              -Ft -z -X stream -c fast -r 50M --manifest-checksums=SHA256

# 5. Заготовка реплики
pg_basebackup -h 192.168.1.20 -U backup_repl -D /var/lib/postgresql/17/main -Fp -X stream -c fast -R -P
```

Что важно помнить:

- Копия с `-X stream` самодостаточна: в ней есть весь WAL, нужный для приведения файлов в согласованное состояние. Восстановить её можно только на момент окончания копирования (без архива WAL — никакого PITR) [офиц.].
- В Debian-раскладке файлы `/etc/postgresql/17/main/*` в копию не входят — копируйте их отдельно (раздел 9.5).
- Если используются дополнительные табличные пространства (1С умеет раскладывать данные и индексы по пространствам `v81c_data` и `v81c_index` — это подтверждено документацией 8.3.27, «Клиент-серверный вариант», гл. 3: пространства с такими именами используются, если существуют, иначе берётся `pg_default`; сверено 11.10.2026), в формате tar каждое пишется в отдельный файл `<OID>.tar`.
- Во время снятия базовой копии не изменяйте шаблонные базы (`template1`): если в это время выполнялся `CREATE DATABASE`, при восстановлении изменения шаблона могут попасть в новую базу. После создания или удаления табличных пространств снимайте новую базовую копию: `CREATE TABLESPACE` записывается в WAL с абсолютным путём и при проигрывании создаёт пространство по тому же пути (исправлено 19.10.2026 по документации PostgreSQL 18, раздел 25.3.8 «Caveats») [офиц.].
- Наблюдать за ходом можно в представлении `pg_stat_progress_basebackup`.

### 3.4. Восстановление из копии pg_basebackup (на момент окончания копии)

Восстанавливается **весь кластер**: все базы возвращаются к моменту копии.

```bash
# 0. Остановить сервер 1С, затем PostgreSQL
sudo systemctl stop srv1cv8-8.3.27.1688@default
sudo systemctl stop postgresql@17-main

# 1. Сохранить повреждённый каталог (если хватает места) и создать пустой
sudo -u postgres mv /var/lib/postgresql/17/main /var/lib/postgresql/17/main.broken
sudo -u postgres install -d -m 700 /var/lib/postgresql/17/main

# 2. Распаковать данные и WAL (владелец — postgres, не root)
sudo -u postgres tar -xzf /backup/base/2026-10-10/base.tar.gz   -C /var/lib/postgresql/17/main
sudo -u postgres tar -xzf /backup/base/2026-10-10/pg_wal.tar.gz -C /var/lib/postgresql/17/main/pg_wal

# 3. Запустить и проверить журнал
sudo systemctl start postgresql@17-main
sudo tail -n 30 /var/log/postgresql/postgresql-17-main.log    # ждём «database system is ready to accept connections»
sudo systemctl start srv1cv8-8.3.27.1688@default
```

Сервер находит в каталоге файл `backup_label`, проигрывает WAL из `pg_wal` до согласованного состояния и открывается на запись. Файл `recovery.signal` в этом сценарии не нужен.

Копия в формате plain восстанавливается ещё проще: `sudo -u postgres cp -a /backup/base/plain_2026-10-10/. /var/lib/postgresql/17/main/` (в пустой каталог с правами `700`).

Для Postgres Pro: каталог `/var/lib/pgpro/1c-17/data`, служба `postgrespro-1c-17`; конфигурация приедет из копии.

### 3.5. pg_verifybackup — проверка копии по манифесту [офиц.]

Что проверяет: наличие и целостность `backup_manifest`, совпадение набора файлов и их размеров, контрольные суммы файлов, читаемость WAL, нужного для восстановления (вызывает `pg_waldump`).

Чего **не** проверяет: что сервер действительно запустится на этой копии; логическую корректность WAL; файлы `postgresql.auto.conf`, `standby.signal`, `recovery.signal`. Документация прямо говорит, что тестовые восстановления всё равно нужны.

| Ключ | Назначение |
|---|---|
| `-e`, `--exit-on-error` | остановиться на первой проблеме |
| `-F p` / `-F t` | формат копии: plain или tar (tar — с версии 18) |
| `-i путь`, `--ignore=путь` | не проверять указанный файл или подкаталог |
| `-m путь` | манифест лежит в другом месте |
| `-n`, `--no-parse-wal` | не разбирать WAL (для tar-копий обязателен) |
| `-s`, `--skip-checksums` | не считать контрольные суммы (проверяются только наличие и размеры) |
| `-w путь`, `--wal-directory=путь` | WAL лежит в другом каталоге |
| `-P`, `-q` | прогресс / молчать при успехе |

```bash
# plain-копия: полная проверка, включая WAL
sudo -u postgres /usr/lib/postgresql/17/bin/pg_verifybackup /backup/base/plain_2026-10-10

# tar-копия (только pg_verifybackup 18+): без разбора WAL
sudo -u postgres /usr/lib/postgresql/18/bin/pg_verifybackup -F t -n /backup/base/2026-10-10

# tar-копия на версиях до 18: проверить хотя бы целостность архивов
gzip -t /backup/base/2026-10-10/base.tar.gz && gzip -t /backup/base/2026-10-10/pg_wal.tar.gz
```

### 3.6. Инкрементальные копии (PostgreSQL 17+) [офиц.]

Принцип: сервер ведёт «сводки WAL» (каталог `pg_wal/summaries`) — списки блоков, изменившихся в каждом диапазоне LSN. `pg_basebackup --incremental` по манифесту предыдущей копии запрашивает только изменившиеся блоки файлов отношений; остальные файлы копируются целиком. Инкрементальную копию нельзя запустить напрямую — сначала её объединяют с предыдущими утилитой `pg_combinebackup`.

```bash
# 1. Включить сводки WAL (перезапуск не нужен)
sudo -u postgres psql -c "ALTER SYSTEM SET summarize_wal = on;" -c "SELECT pg_reload_conf();"
sudo -u postgres psql -c "SELECT * FROM pg_get_wal_summarizer_state();"

# 2. Полная копия (plain)
sudo -u postgres pg_basebackup -D /backup/inc/full_2026-10-04 -c fast -P

# 3. Инкрементальные: каждая ссылается на манифест предыдущей
sudo -u postgres pg_basebackup -D /backup/inc/incr_2026-10-05 -c fast -P \
        --incremental=/backup/inc/full_2026-10-04/backup_manifest
sudo -u postgres pg_basebackup -D /backup/inc/incr_2026-10-06 -c fast -P \
        --incremental=/backup/inc/incr_2026-10-05/backup_manifest

# 4. Восстановление: собрать «синтетическую» полную копию. Порядок — от полной к самой свежей
sudo -u postgres /usr/lib/postgresql/17/bin/pg_combinebackup \
        /backup/inc/full_2026-10-04 /backup/inc/incr_2026-10-05 /backup/inc/incr_2026-10-06 \
        -o /var/lib/postgresql/17/main
sudo -u postgres /usr/lib/postgresql/17/bin/pg_verifybackup /var/lib/postgresql/17/main
```

Ключи `pg_combinebackup`: `-o каталог` (обязателен), `-n` (пробный прогон), `-d` (отладка), `-T старый=новый`, `--clone` (reflink на Btrfs/XFS), `--copy-file-range`, `-k`/`--link` (жёсткие ссылки, 18+; после этого исходные копии нельзя использовать независимо), `--manifest-checksums=…`, `--no-manifest`, `-N`.

Ограничения и подводные камни:

- Сводки хранятся `wal_summary_keep_time` (по умолчанию 10 дней). Если с предыдущей копии прошло больше или `summarize_wal` выключали — инкрементальная копия завершится ошибкой, нужна новая полная.
- PostgreSQL **не отслеживает зависимости** между копиями: удалили любое звено цепочки — все последующие инкременты бесполезны. Ротацию нужно писать самому (или взять pg_probackup, pgBackRest, Barman).
- `pg_combinebackup` проверяет только связность цепочки, а не целостность каждой копии — для этого `pg_verifybackup`.
- `pg_combinebackup` не пересчитывает контрольные суммы страниц: если между копиями включали или выключали контрольные суммы данных (`pg_checksums`), после этого нужна новая полная копия.
- `pg_combinebackup` работает с каталогами; копии в формате tar перед объединением нужно распаковать (подтверждено 19.10.2026: исходный код `src/bin/pg_combinebackup/pg_combinebackup.c` ветки 18 читает входы только как каталоги — `PG_VERSION`, рекурсивный обход, — разбора tar в нём нет; документация PostgreSQL 18, раздел 25.3.5, велит сначала разложить копии по отдельным каталогам).
- Сборки PostgreSQL для 1С версий 17 и 18 существуют, и механизм в них штатный; тем не менее для регулярных инкрементальных копий баз 1С на практике удобнее pg_probackup (раздел 5) — в нём есть учёт цепочек, политика хранения и проверка [практика].

## 4. Непрерывное архивирование WAL и восстановление на момент времени (PITR)

### 4.1. Параметры [офиц.]

| Параметр | По умолчанию | Значения и смысл | Применение |
|---|---|---|---|
| `wal_level` | `replica` | `minimal`, `replica`, `logical`. Для архива и базовых копий — не ниже `replica` | перезапуск |
| `archive_mode` | `off` | `off`, `on`, `always` (архивировать и на реплике). Нельзя включить при `wal_level = minimal` | перезапуск |
| `archive_command` | пусто | команда оболочки, копирующая один завершённый сегмент. `%p` — путь к файлу относительно каталога данных, `%f` — только имя файла, `%%` — знак процента. Должна вернуть 0 **только** при успехе | reload |
| `archive_library` | пусто | библиотека-архиватор вместо команды (15+). Одновременно с `archive_command` задавать нельзя — с версии 16 это ошибка; в 15 библиотека молча перекрывала команду (исправлено 19.10.2026 по замечаниям к выпуску 16) | reload |
| `archive_timeout` | `0` (выкл.) | принудительно переключать сегмент не реже указанного времени. Сегмент всё равно занимает 16 МБ, поэтому слишком малое значение раздувает архив; документация советует порядка минуты | reload |
| `restore_command` | пусто | команда извлечения сегмента из архива при восстановлении; `%f` — имя, `%p` — куда положить. Должна вернуть ненулевой код, если файла нет | reload |
| `recovery_target_time` / `_name` / `_lsn` / `_xid` / `recovery_target = 'immediate'` | не заданы | цель восстановления; одновременно можно задать только одну | только при старте |
| `recovery_target_inclusive` | `on` | остановиться сразу после цели (`on`) или перед ней (`off`) | только при старте |
| `recovery_target_timeline` | `latest` | `latest`, `current` или номер линии времени | только при старте |
| `recovery_target_action` | `pause` | `pause` — встать на паузу для проверки; `promote` — сразу открыть на запись; `shutdown` — остановить сервер | только при старте |
| `summarize_wal` | `off` | сводки WAL для инкрементальных копий (17+) | reload |
| `wal_summary_keep_time` | 10 дней | срок хранения сводок; 0 — не удалять | reload |
| `max_wal_size` | 1 ГБ | **мягкий** предел объёма WAL между контрольными точками; при сбое архивации или отставшем слоте превышается без ограничений | reload |
| `wal_compression` | `off` | `pglz`, `lz4`, `zstd` — сжатие образов страниц в WAL, уменьшает архив | на лету |
| `max_slot_wal_keep_size` | `-1` (без предела) (умолчание подтверждено образцом `postgresql.conf` PostgreSQL 18, сверено 10.10.2026) | сколько WAL разрешено удерживать слоту репликации (13+) | reload |

### 4.2. Включение архивации

Официальный минимальный пример [офиц.] — копирование в каталог с защитой от перезаписи:

```ini
archive_command = 'test ! -f /backup/wal/%f && cp %p /backup/wal/%f'
```

Вариант со сжатием из документации: `archive_command = 'gzip < %p > /backup/wal/%f.gz'` и парный `restore_command = 'gunzip < /backup/wal/%f.gz > %p'`.

Более надёжный вариант — отдельный скрипт: запись во временный файл, сброс на диск, атомарное переименование, проверка повторной отправки [практика]:

```bash
#!/usr/bin/env bash
# /usr/local/bin/pg-wal-archive.sh — archive_command для PostgreSQL
# Вызов: pg-wal-archive.sh %p %f  (текущий каталог — PGDATA, %p — относительный путь)
set -euo pipefail
src="$1"; name="$2"
dir=/backup/wal
dst="$dir/$name.zst"

# если /backup — отдельно смонтированный том, не писать в пустую точку монтирования:
# mountpoint -q /backup || { echo "archive: /backup is not mounted" >&2; exit 1; }

if [[ -f "$dst" ]]; then
    # повторная отправка того же сегмента после сбоя — не ошибка, если содержимое совпадает
    if zstd -dcq "$dst" | cmp -s - "$src"; then exit 0; fi
    echo "archive: $dst already exists and differs from $src" >&2
    exit 1
fi

tmp="$dir/.$name.$$.tmp"
trap 'rm -f "$tmp"' EXIT
zstd -q -3 -f -o "$tmp" "$src"
sync "$tmp"
mv "$tmp" "$dst"
sync "$dir"
```

```bash
sudo apt install zstd
sudo install -o root -g root -m 755 pg-wal-archive.sh /usr/local/bin/pg-wal-archive.sh

sudo tee /etc/postgresql/17/main/conf.d/10-archive.conf >/dev/null <<'EOF'
wal_level = replica
archive_mode = on
archive_command = '/usr/local/bin/pg-wal-archive.sh "%p" "%f"'
archive_timeout = 300
EOF
sudo systemctl restart postgresql@17-main      # archive_mode требует перезапуска — делать в окно обслуживания
```

Для Postgres Pro те же строки добавляют в `/var/lib/pgpro/1c-17/data/postgresql.conf`.

Требования к команде архивации [офиц.]:

- выполняется от пользователя сервера (`postgres`); каталог архива не должен быть доступен на чтение посторонним — в WAL лежат данные баз;
- не должна перезаписывать существующий файл с другим содержимым;
- код возврата 0 — только когда файл действительно сохранён; при ненулевом коде сервер повторяет попытки бесконечно;
- завершение по сигналу или код возврата больше 125 («команда не найдена») приводят к перезапуску процесса архиватора и **не отражаются** в `pg_stat_archiver` — смотрите журнал сервера;
- чтобы сообщения скрипта попадали в журнал сервера, должен быть включён `logging_collector`;
- архив на сетевом ресурсе, который может отвалиться, — прямой путь к переполнению диска (раздел 4.8). Надёжнее архивировать на локальный том и выносить копию отдельным заданием.

Альтернативы:

```ini
# модуль basic_archive (15+): копирование без сжатия, запись через временный файл
archive_mode = on
archive_library = 'basic_archive'
basic_archive.archive_directory = '/backup/wal'      # каталог должен существовать
```

После аварийного завершения сервера в каталоге могут остаться файлы с префиксом `archtemp` — их рекомендуется удалить [офиц.].

`pg_receivewal` — потоковый приём WAL на другом узле в реальном времени (RPO — секунды, `archive_timeout` не нужен). Документация настоятельно рекомендует использовать слот репликации, иначе сервер может удалить сегменты раньше, чем они приняты; обратная сторона — если приёмник остановился, слот удерживает WAL и диск сервера заполняется [офиц.]:

```bash
pg_receivewal -h 192.168.1.20 -U backup_repl -D /backup/wal_stream -S walrecv --create-slot --if-not-exists
pg_receivewal -h 192.168.1.20 -U backup_repl -D /backup/wal_stream -S walrecv -Z gzip:5     # держать запущенным как службу
```

### 4.3. Проверка и наблюдение

```bash
# принудительно закрыть текущий сегмент и убедиться, что он появился в архиве
sudo -u postgres psql -c "SELECT pg_switch_wal();"
ls -lt /backup/wal | head -5

# состояние архиватора
sudo -u postgres psql -x -c "SELECT archived_count, last_archived_wal, last_archived_time,
                                    failed_count, last_failed_wal, last_failed_time
                             FROM pg_stat_archiver;"

# очередь сегментов, ожидающих архивации (норма — единицы)
sudo -u postgres psql -Atc "SELECT count(*) FROM pg_ls_archive_statusdir() WHERE name LIKE '%.ready';"

# объём pg_wal
sudo -u postgres psql -Atc "SELECT pg_size_pretty(sum(size)) FROM pg_ls_waldir();"
sudo du -sh /var/lib/postgresql/17/main/pg_wal

# слоты репликации, удерживающие WAL
sudo -u postgres psql -c "SELECT slot_name, active, restart_lsn,
                                 pg_size_pretty(pg_wal_lsn_diff(pg_current_wal_lsn(), restart_lsn)) AS retained
                          FROM pg_replication_slots;"
```

Поводы для тревоги: `failed_count` растёт; `last_archived_time` в рабочее время старше двух-трёх интервалов `archive_timeout`; файлов `.ready` десятки и больше; `pg_wal` в разы превышает `max_wal_size`.

### 4.4. Базовая копия для PITR

Подходит любая копия `pg_basebackup`, снятая **после** включения архивации. Ключ `-X stream` оставляйте: копия остаётся самодостаточной даже при повреждении архива. Восстановить можно на любой момент **после окончания** этой базовой копии, пока в архиве есть непрерывная цепочка сегментов [офиц.]. При снятии копии в архиве появляется файл истории вида `0000000100001234000055CD.007C9330.backup` — по нему видно, с какого сегмента WAL нужен этой копии.

### 4.5. Восстановление на момент времени — пошагово

Порядок соответствует официальной процедуре (документация PostgreSQL, «Recovering Using a Continuous Archive Backup»), адаптирован под Debian-раскладку.

```bash
# 0. Остановить сервер 1С и PostgreSQL
sudo systemctl stop srv1cv8-8.3.27.1688@default
sudo systemctl stop postgresql@17-main

# 1. Сохранить текущий каталог данных. Минимум — pg_wal: там могут лежать ещё не заархивированные сегменты
sudo -u postgres mv /var/lib/postgresql/17/main /var/lib/postgresql/17/main.before_pitr

# 2. Развернуть базовую копию, снятую ДО нужного момента. pg_wal из копии не распаковываем
sudo -u postgres install -d -m 700 /var/lib/postgresql/17/main
sudo -u postgres tar -xzf /backup/base/2026-10-09/base.tar.gz -C /var/lib/postgresql/17/main

# 3. Только если нужно дойти до самого последнего момента: вернуть незаархивированные сегменты (копировать, не перемещать)
sudo -u postgres sh -c 'cp -n /var/lib/postgresql/17/main.before_pitr/pg_wal/0000* /var/lib/postgresql/17/main/pg_wal/'

# 4. Параметры восстановления и сигнальный файл
sudo tee /etc/postgresql/17/main/conf.d/99-recovery.conf >/dev/null <<'EOF'
restore_command = 'zstd -dcq < /backup/wal/%f.zst > %p'
recovery_target_time = '2026-10-10 14:25:00+05'
recovery_target_action = 'pause'
EOF
sudo -u postgres touch /var/lib/postgresql/17/main/recovery.signal

# 5. Запустить и следить за журналом
sudo systemctl start postgresql@17-main
sudo tail -f /var/log/postgresql/postgresql-17-main.log
```

В журнале последовательно появятся сообщения о начале восстановления на момент времени, строки `restored log file "…" from archive`, затем `recovery stopping before commit of transaction …` и `pausing at the end of recovery` с подсказкой выполнить `pg_wal_replay_resume()`.

```bash
# 6. Сервер на паузе и открыт только на чтение — проверить, что данные те
sudo -u postgres psql -c "SELECT pg_is_in_recovery(), pg_last_xact_replay_timestamp();"
sudo -u postgres psql -d zup -c "SELECT count(*) FROM public._document123;"     # любая содержательная проверка

# 7а. Момент верный — завершить восстановление (сервер откроется на запись на новой линии времени)
sudo -u postgres psql -c "SELECT pg_wal_replay_resume();"

# 7б. Нужен более поздний момент — остановить сервер, увеличить recovery_target_time, запустить снова.
#     Нужен более ранний — заново с шага 2.

# 8. После завершения: убрать цель, запустить 1С, сделать новую полную копию
sudo rm /etc/postgresql/17/main/conf.d/99-recovery.conf
sudo systemctl start srv1cv8-8.3.27.1688@default
sudo -u postgres pg_basebackup -D /backup/base/$(date +%F)_after_pitr -Ft -z -X stream -c fast -P
```

Пояснения:

- Файл `recovery.signal` сервер удаляет сам по окончании восстановления. Если восстановление прервалось — просто запустите сервер ещё раз, оно продолжится [офиц.].
- Время указывайте с явным смещением часового пояса (`+05`), иначе оно будет понято в поясе сервера.
- Цель должна быть позже момента окончания базовой копии; восстановиться «внутрь» копии нельзя [офиц.].
- `recovery_target_action = 'pause'` работает только при `hot_standby = on` (по умолчанию включён); при выключенном `hot_standby` пауза ведёт себя как `shutdown` (подтверждено документацией PostgreSQL 18, параметр `recovery_target_action`; сверено 10.10.2026). Если цель не задана вовсе, сервер проигрывает весь архив и открывается на запись.
- Нормальное восстановление заканчивается сообщением о ненайденном файле в архиве — это не ошибка: так сервер узнаёт, что WAL закончился [офиц.].
- В раскладке Postgres Pro `postgresql.conf` лежит в каталоге данных и будет заменён версией из копии; параметры восстановления дописывайте в него после распаковки.
- Восстановление откатывает все базы кластера. Если нужно вернуть одну базу — см. раздел 11.3.

### 4.6. Цели восстановления и линии времени [офиц.]

| Параметр | Пример | Когда применять |
|---|---|---|
| `recovery_target_time` | `'2026-10-10 14:25:00+05'` | известен момент ошибки (самый частый случай) |
| `recovery_target_name` | `'before_update_2026_10_10'` | заранее поставлена точка `SELECT pg_create_restore_point('…');` |
| `recovery_target_lsn` | `'37/A1000028'` | известна позиция в WAL (из журнала сервера, `pg_waldump`) |
| `recovery_target_xid` | `'1234567'` | известен номер транзакции (на практике редко) |
| `recovery_target = 'immediate'` | — | остановиться, как только копия стала согласованной |
| `recovery_target_inclusive` | `off` | остановиться перед целью, а не после |
| `recovery_target_timeline` | `latest` / `current` / `3` | по умолчанию — самая свежая линия времени в архиве; номер задают, чтобы вернуться на ветку до предыдущего восстановления |

Каждое завершённое восстановление из архива создаёт новую линию времени и файл `0000000N.history` в архиве. Файлы истории маленькие — храните их бессрочно. Восстановиться на линию времени, ответвившуюся раньше базовой копии, нельзя.

Способы перевести сервер из восстановления в обычный режим: `SELECT pg_wal_replay_resume();` (с паузы в конце восстановления), `SELECT pg_promote();`, `sudo pg_ctlcluster 17 main promote`, `pg_ctl promote -D $PGDATA`.

### 4.7. Очистка архива WAL

Сегмент нужен, пока существует хотя бы одна базовая копия, начатая не позже него. Удалять можно всё, что старше начала **самой старой хранимой** базовой копии.

```bash
# какой сегмент нужен самой старой копии: имя .backup-файла начинается с него
ls /backup/wal | grep '\.backup'
# пробный прогон (-n) и удаление всего, что старше указанного сегмента; -x отбрасывает расширение сжатия
/usr/lib/postgresql/17/bin/pg_archivecleanup -n -x .zst /backup/wal 000000010000003700000010
/usr/lib/postgresql/17/bin/pg_archivecleanup    -x .zst /backup/wal 000000010000003700000010
```

Упрощённый вариант по возрасту файлов допустим, только если срок хранения WAL заведомо больше, чем «интервал между базовыми копиями × число хранимых копий» [практика]:

```bash
find /backup/wal -name '*.zst' -mtime +21 -delete     # при еженедельной базовой копии и хранении двух копий
```

pg_probackup, pgBackRest, Barman и WAL-G чистят архив сами, согласованно с политикой хранения копий.

### 4.8. Типовые ошибки архивации

| Симптом | Причина | Решение |
|---|---|---|
| `pg_wal` растёт, место на диске заканчивается, в `pg_stat_archiver` растёт `failed_count` | `archive_command` возвращает ошибку: нет места в архиве, нет прав, отвалилась сетевая шара, каталог не существует | устранить причину; сервер сам дошлёт накопленные сегменты. Порядок действий при уже заполненном диске — раздел 11.5 |
| `pg_wal` растёт, архиватор при этом исправен | неактивный слот репликации (остался от `pg_basebackup -C`, `pg_receivewal`, старой реплики) | `SELECT pg_drop_replication_slot('имя');` и задать `max_slot_wal_keep_size`, например `20GB` |
| Сервер остановился: `PANIC: could not write to file "pg_wal/xlogtemp.NNN": No space left on device` | файловая система с `pg_wal` заполнена | раздел 11.5. Зафиксированные транзакции при этом не теряются [офиц.] |
| В архиве нет свежих файлов, ошибок нет, нагрузка небольшая | сегмент ещё не заполнен, `archive_timeout = 0` | задать `archive_timeout` (60–300 с) |
| Архиватор «молча» не работает, в `pg_stat_archiver` пусто | команда не найдена (код 127) или убита сигналом — такие сбои в статистику не попадают | смотреть журнал сервера; указать полный путь к скрипту, проверить права на исполнение |
| При восстановлении: `could not open file … restored log file … not found`, восстановление останавливается раньше цели | в архиве разрыв (сегмент не был заархивирован или удалён чисткой) | восстановиться можно только до разрыва; взять более позднюю базовую копию |
| `archive_mode` включили, а архивация не началась | нужен перезапуск сервера, reload недостаточен | `systemctl restart postgresql@17-main` |
| После `archive_command = ''` при `archive_mode = on` WAL копится | пустая команда означает «временно не архивировать, но копить» [офиц.] | вернуть рабочую команду |

## 5. pg_probackup

Утилита Postgres Professional для физических копий: полные и инкрементальные копии на уровне страниц, сжатие, параллельность, проверка, политика хранения, собственный архив WAL, восстановление на момент времени, удалённая работа по SSH [офиц.].

### 5.1. Версии и редакции (на 10.10.2026)

| Вариант | Версия | Пакет и бинарник | Примечания |
|---|---|---|---|
| Открытая версия (GitHub `postgrespro/pg_probackup`, репозиторий `repo.postgrespro.ru/pg_probackup`) | 2.5.16 (декабрь 2025) | пакеты `pg-probackup-13` … `pg-probackup-18` (+ `-dbg`); бинарник `pg_probackup-NN` | PostgreSQL 13–18; сжатие `zlib`, `pglz`. Готовые пакеты: Ubuntu 22.04 (jammy), 24.04 (noble), 20.04 (focal, не обновляется). Для 26.04 (resolute) каталога в репозитории нет [офиц.] |
| В составе Postgres Pro Standard / Enterprise | 2.7.x (в документации Postgres Pro 17 примеры от 2.7.3) | `pg-probackup-std-17` (для Enterprise — `pg-probackup-ent-17`, подтверждено 19.10.2026 по документации Postgres Pro Enterprise 17, «Установка из двоичных пакетов»); `/opt/pgpro/std-17/bin/pg_probackup` | дополнительно `lz4` и `zstd` (lz4 — с Postgres Pro 14, zstd — с 15) [офиц.] |
| pg_probackup3 | 3.4.1 | пакеты `pg-probackup3`, `libpgprobackup3`, `libpb3-encoder` в `repo.postgrespro.ru/pg_probackup3` (jammy, noble, resolute) | новое поколение. Условия использования не проверены ⚠; на 1c.postgres.ru инкрементальные копии, PITR и S3 отнесены к платному продукту «Postgres Pro Backup Enterprise» |

С какими сборками для 1С работает открытая версия:

- сборка от «1С» (`postgresql-17`) — используют `pg-probackup-17` [практика] ⚠;
- `postgrespro-1c-17` — в её собственном репозитории пакета pg_probackup нет (проверено по индексу пакетов для noble; 19.10.2026 то же подтверждено для `postgrespro-1c-16` — индексы jammy и noble); ставят `pg-probackup-17` из репозитория `pg_probackup` [практика] ⚠. Для ветки 16 пакет `pg-probackup-16` 2.5.16 в этом репозитории есть (индекс noble, 19.10.2026). Что проверить до внедрения: открытая сборка pg_probackup, собранная под ванильный PostgreSQL, **отказывается работать**, если на сервере есть функция `pg_catalog.pgpro_edition()` — ошибка вида `pg_probackup was built with PostgreSQL 16, but connection is made with Postgres Pro …` (исходный код 2.5.16, `src/backup.c`, функции `check_server_version` и `pgpro_support`, прочитано 19.10.2026). В документации «PostgreSQL для 1С» 16 (раздел 9.26, функции информации о системе) такой функции нет, но на сервере это нужно проверить: `sudo -u postgres psql -Atc "SELECT proname FROM pg_proc WHERE proname = 'pgpro_edition'"` — пустой ответ означает, что эта проверка утилиту не остановит.

Общие ограничения [офиц.]: сервер-источник и сервер восстановления должны совпадать по старшей версии, `block_size` и `wal_block_size` (возможны дополнительные требования по архитектуре процессора и версиям libc/ICU); удалённый режим — только по SSH и только при одинаковой версии pg_probackup на обоих узлах; параллельное восстановление ускоряет копирование файлов, но не проигрывание WAL.

### 5.3. Подготовка кластера

Требования [офиц.]: `wal_level` выше `minimal`; для режима `--stream` — свободное подключение в `max_wal_senders`, роль с атрибутом `REPLICATION` и разрешение на репликацию в `pg_hba.conf`. Утилиту запускает пользователь ОС, имеющий доступ на чтение к каталогу данных, — на практике `postgres`.

**Вариант А (простой, один сервер).** Всё выполняется от `postgres` через локальный сокет, подключение суперпользователем. Документация это допускает, но рекомендует отдельную роль.

**Вариант Б (рекомендуемый документацией).** Отдельная роль с минимальными правами. Для PostgreSQL 15 и новее [офиц.]:

```sql
-- sudo -u postgres psql
CREATE DATABASE backupdb;
\c backupdb
BEGIN;
CREATE ROLE backup WITH LOGIN REPLICATION PASSWORD 'СЛОЖНЫЙ_ПАРОЛЬ';
GRANT USAGE ON SCHEMA pg_catalog TO backup;
GRANT EXECUTE ON FUNCTION pg_catalog.current_setting(text) TO backup;
GRANT EXECUTE ON FUNCTION pg_catalog.set_config(text, text, boolean) TO backup;
GRANT EXECUTE ON FUNCTION pg_catalog.pg_is_in_recovery() TO backup;
GRANT EXECUTE ON FUNCTION pg_catalog.pg_backup_start(text, boolean) TO backup;
GRANT EXECUTE ON FUNCTION pg_catalog.pg_backup_stop(boolean) TO backup;
GRANT EXECUTE ON FUNCTION pg_catalog.pg_create_restore_point(text) TO backup;
GRANT EXECUTE ON FUNCTION pg_catalog.pg_switch_wal() TO backup;
GRANT EXECUTE ON FUNCTION pg_catalog.pg_last_wal_replay_lsn() TO backup;
GRANT EXECUTE ON FUNCTION pg_catalog.txid_current() TO backup;
GRANT EXECUTE ON FUNCTION pg_catalog.txid_current_snapshot() TO backup;
GRANT EXECUTE ON FUNCTION pg_catalog.txid_snapshot_xmax(txid_snapshot) TO backup;
GRANT EXECUTE ON FUNCTION pg_catalog.pg_control_checkpoint() TO backup;
COMMIT;
-- для частичного восстановления (--db-include / --db-exclude) дополнительно:
GRANT SELECT ON TABLE pg_catalog.pg_database TO backup;
```

Для PostgreSQL 14 вместо двух функций `pg_backup_*` права дают на `pg_start_backup(text, boolean, boolean)` и `pg_stop_backup(boolean, boolean)`.

Пароль для скриптов — в `~postgres/.pgpass` (права `0600`); для потокового режима нужна отдельная строка для базы `replication` [офиц.]:

```text
127.0.0.1:5432:backupdb:backup:СЛОЖНЫЙ_ПАРОЛЬ
127.0.0.1:5432:replication:backup:СЛОЖНЫЙ_ПАРОЛЬ
```

### 5.4. Каталог копий: init, add-instance, set-config, show-config

```bash
# каталог копий (пустой), владелец — тот, кто запускает pg_probackup
sudo install -d -o postgres -g postgres -m 700 /backup/pgpro
sudo -u postgres pg_probackup-17 init -B /backup/pgpro

# зарегистрировать экземпляр (кластер PostgreSQL); имя экземпляра произвольное
sudo -u postgres pg_probackup-17 add-instance -B /backup/pgpro -D /var/lib/postgresql/17/main --instance=main

# сохранить в конфигурации экземпляра подключение, хранение, сжатие, журнал
# вариант А: сокет и суперпользователь
sudo -u postgres pg_probackup-17 set-config -B /backup/pgpro --instance=main \
     -h /var/run/postgresql -p 5432 -U postgres -d postgres \
     --retention-redundancy=2 --retention-window=14 \
     --compress-algorithm=zlib --compress-level=1 \
     --external-dirs=/etc/postgresql/17/main \
     --log-level-file=info --log-rotation-size=100MB
# вариант Б: отдельная роль
#    -h 127.0.0.1 -p 5432 -U backup -d backupdb

sudo -u postgres pg_probackup-17 show-config -B /backup/pgpro --instance=main
```

Синтаксис [офиц.]:

```text
pg_probackup init -B backup_dir
pg_probackup add-instance -B backup_dir -D data_dir --instance=instance_name
pg_probackup del-instance -B backup_dir --instance=instance_name
pg_probackup set-config -B backup_dir --instance=instance_name [--pgdata=…]
     [--retention-redundancy=N] [--retention-window=N] [--wal-depth=N]
     [--compress-algorithm=…] [--compress-level=N] [-d dbname] [-h host] [-p port] [-U username]
     [--archive-timeout=сек] [--external-dirs=…] [--restore-command=…]
     [параметры удалённого режима] [параметры журнала]
pg_probackup show-config -B backup_dir --instance=instance_name [--format=plain|json]
```

Переменные окружения: `BACKUP_PATH` заменяет `-B`, `PGDATA` — `-D`, `PGDATABASE`/`PGHOST`/`PGPORT`/`PGUSER` — параметры подключения; пароль — из `PGPASSWORD` или `.pgpass`.

`--external-dirs` (`-E`) включает в каждую копию каталоги вне PGDATA (несколько — через двоеточие). В Debian-раскладке так удобно забирать `/etc/postgresql/17/main`.

Журнал: по умолчанию в файл не пишется (`--log-level-file=off`), на консоль — уровень `info`; каталог журнала по умолчанию `$BACKUP_PATH/log/`, имя файла `pg_probackup.log`.

### 5.5. Режимы копий и доставки WAL [офиц.]

| Режим `-b` | Как находит изменения | Требования | Нагрузка |
|---|---|---|---|
| `FULL` | копирует все файлы данных | — | максимальная |
| `DELTA` | читает все файлы данных и копирует страницы, изменившиеся с прошлой копии | — | чтение сравнимо с полной копией, запись — только изменения |
| `PAGE` | просматривает архив WAL с момента прошлой копии и берёт упомянутые там страницы | настроенный архив WAL (`archive-push`), непрерывный с прошлой копии | минимальное чтение данных; выгоден при малом объёме изменений |
| `PTRACK` | сервер сам отмечает изменённые страницы в битовой карте | расширение `ptrack` и поддерживающая его сборка (раздел 5.14) | самый быстрый инкремент; небольшие накладные расходы на сервере |

Доставка WAL — у каждой копии свой режим:

- `ARCHIVE` (по умолчанию) — согласованность копии обеспечивает архив WAL; без настроенного архива такая копия не снимется;
- `STREAM` (ключ `--stream`) — нужные сегменты WAL передаются по протоколу репликации и складываются внутрь копии. Такая копия автономна и восстанавливается без архива.

Для сервера 1С без архива WAL рабочая схема — `FULL` + `DELTA` с `--stream`. Если нужен PITR, настраивают архив (раздел 5.11); тогда доступен и режим `PAGE`.

### 5.6. backup

```text
pg_probackup backup -B backup_dir -b backup_mode --instance=instance_name
     [-j num_threads] [--progress] [-C] [--stream [-S slot_name] [--temp-slot]] [--backup-pg-log]
     [--no-validate] [--skip-block-validation] [-w] [--archive-timeout=сек]
     [--external-dirs=…] [--no-sync] [--note=…]
     [подключение] [сжатие] [удалённый режим] [хранение] [закрепление] [журнал]
```

| Ключ | Назначение |
|---|---|
| `-b режим` | режим копии: `FULL`, `DELTA`, `PAGE`, `PTRACK` |
| `--stream` | режим доставки WAL STREAM |
| `--temp-slot` | временный слот репликации на время копии (гарантирует, что сервер не удалит нужные сегменты; удаляется сам) |
| `-S имя`, `--slot=имя` | постоянный слот. Осторожно: если копии перестанут сниматься, слот будет удерживать WAL |
| `-C`, `--smooth-checkpoint` | растянутая контрольная точка; по умолчанию — немедленная |
| `-j N` | число потоков |
| `--progress` | показывать ход |
| `--compress` | сжатие с параметрами по умолчанию (в открытой версии — zlib, уровень 1) |
| `--compress-algorithm=имя` | алгоритм: `zlib`, `pglz`, `none` (в версиях для Postgres Pro также `lz4`, `zstd`); по умолчанию `none` |
| `--compress-level=0..9` | уровень, по умолчанию 1 |
| `--backup-pg-log` | включить в копию каталог журналов сервера |
| `-E пути`, `--external-dirs=пути` | внешние каталоги |
| `--no-validate` | не проверять копию сразу после создания (по умолчанию проверка выполняется автоматически) |
| `--skip-block-validation` | не проверять страницы при копировании |
| `--archive-timeout=сек` | сколько ждать появления сегмента в архиве (по умолчанию 300) |
| `--note='текст'` | примечание к копии |
| `--ttl=срок`, `--expire-time='время'` | закрепить копию (не удалять политикой хранения) |
| `--delete-expired`, `--merge-expired`, `--delete-wal`, `--retention-…` | применить политику хранения после копии |

```bash
# полная копия, 4 потока, сжатие, WAL внутри копии
sudo -u postgres pg_probackup-17 backup -B /backup/pgpro --instance=main -b FULL  --stream --temp-slot -j 4 --compress --progress

# инкрементальная
sudo -u postgres pg_probackup-17 backup -B /backup/pgpro --instance=main -b DELTA --stream --temp-slot -j 4 --compress

# копия перед обновлением конфигурации 1С: с примечанием и закреплением на 60 дней
sudo -u postgres pg_probackup-17 backup -B /backup/pgpro --instance=main -b FULL --stream --temp-slot -j 4 --compress \
     --note='before update BP 3.0.180' --ttl=60d

# копия и сразу чистка по политике хранения
sudo -u postgres pg_probackup-17 backup -B /backup/pgpro --instance=main -b DELTA --stream --temp-slot -j 4 \
     --delete-expired --delete-wal
```

Если для инкрементальной копии нет действительной полной копии-родителя, команда завершится ошибкой с требованием сначала создать `FULL`.

### 5.7. show и статусы копий

```bash
sudo -u postgres pg_probackup-17 show -B /backup/pgpro                               # все экземпляры
sudo -u postgres pg_probackup-17 show -B /backup/pgpro --instance=main -i SBOL6J     # подробно об одной копии
sudo -u postgres pg_probackup-17 show -B /backup/pgpro --instance=main --archive     # состояние архива WAL
sudo -u postgres pg_probackup-17 show -B /backup/pgpro --format=json                 # для скриптов и мониторинга
```

Пример вывода (из документации; в открытой версии 2.5 набор столбцов может немного отличаться):


Столбцы: `ID` — идентификатор копии; `Recovery Time` — самый ранний момент, на который копию можно восстановить; `TLI` — линия времени копии / родителя; `Data` — размер данных; `WAL` — несжатый объём WAL, который придётся проиграть (для STREAM-копий полный размер = Data + WAL); `Zratio` — степень сжатия.

| Статус | Смысл |
|---|---|
| `OK` | копия завершена и проверена — можно восстанавливать |
| `DONE` | завершена, но не проверена (снята с `--no-validate`) |
| `RUNNING` | копирование идёт (или процесс был убит — тогда статус «залипает») |
| `MERGING` / `MERGED` | идёт слияние / данные слиты, обновляются метаданные (только у полных копий) |
| `DELETING` | удаляется |
| `CORRUPT` | часть файлов повреждена |
| `ERROR` | копирование прервано ошибкой |
| `ORPHAN` | копия недействительна, потому что повреждён или отсутствует родитель |

### 5.8. validate и checkdb

```bash
# проверить все копии экземпляра (контрольные суммы файлов копии, цепочки родителей)
sudo -u postgres pg_probackup-17 validate -B /backup/pgpro --instance=main -j 4
# одну копию
sudo -u postgres pg_probackup-17 validate -B /backup/pgpro --instance=main -i SBOL6J
# можно ли восстановиться на заданный момент (проверяет непрерывность WAL в архиве)
sudo -u postgres pg_probackup-17 validate -B /backup/pgpro --instance=main --recovery-target-time='2026-10-10 14:25:00+05'

# проверка РАБОТАЮЩЕГО кластера: физическая проверка всех файлов данных
sudo -u postgres pg_probackup-17 checkdb -B /backup/pgpro --instance=main -j 4
# логическая проверка индексов (в каждой базе должно быть расширение amcheck)
sudo -u postgres pg_probackup-17 checkdb -B /backup/pgpro --instance=main -j 4 --amcheck --heapallindexed
```

Если в кластере включены контрольные суммы данных, pg_probackup проверяет по ним каждую страницу; если нет — всегда проверяет хотя бы корректность заголовков страниц [офиц.]. `validate` не заменяет тестового восстановления.

### 5.9. restore

```text
pg_probackup restore -B backup_dir --instance=instance_name
     [-D data_dir] [-i backup_id] [-j num_threads] [--progress]
     [-T OLDDIR=NEWDIR] [--external-mapping=OLDDIR=NEWDIR] [--skip-external-dirs]
     [-R | --restore-as-replica] [--no-validate] [--skip-block-validation] [--force] [--no-sync]
     [--restore-command=cmdline] [--primary-conninfo=…] [-S | --primary-slot-name=…] [-X wal_dir]
     [-I | --incremental-mode=none|checksum|lsn] [--db-include=имя | --db-exclude=имя]
     [цели восстановления] [журнал] [удалённый режим]
```

Цели восстановления: `--recovery-target=immediate|latest`, `--recovery-target-time`, `--recovery-target-lsn`, `--recovery-target-xid`, `--recovery-target-name`, `--recovery-target-inclusive`, `--recovery-target-timeline`, `--recovery-target-action=pause|promote|shutdown` (по умолчанию `pause`). Для STREAM-копий цель по умолчанию — `immediate` (состояние на конец копии), для ARCHIVE-копий — `latest` (проиграть весь архив) [офиц.].

```bash
# 0. Остановить 1С и PostgreSQL; каталог данных должен быть пуст
sudo systemctl stop srv1cv8-8.3.27.1688@default
sudo systemctl stop postgresql@17-main
sudo -u postgres mv /var/lib/postgresql/17/main /var/lib/postgresql/17/main.broken
sudo -u postgres install -d -m 700 /var/lib/postgresql/17/main

# 1. Последняя копия — в исходный каталог
sudo -u postgres pg_probackup-17 restore -B /backup/pgpro --instance=main -j 4 --progress

# 2. Конкретная копия
sudo -u postgres pg_probackup-17 restore -B /backup/pgpro --instance=main -i SBOL6J -j 4

# 3. В другой каталог (тестовое восстановление, поиск удалённых данных)
sudo -u postgres pg_probackup-17 restore -B /backup/pgpro --instance=main -D /var/lib/postgresql/17/restore_test -j 4

# 4. На момент времени (нужен архив WAL) с немедленным открытием на запись
sudo -u postgres pg_probackup-17 restore -B /backup/pgpro --instance=main -j 4 \
     --recovery-target-time='2026-10-10 14:25:00+05' --recovery-target-action=promote

# 5. К именованной точке
sudo -u postgres pg_probackup-17 restore -B /backup/pgpro --instance=main -j 4 \
     --recovery-target-name='before_update_2026_10_10' --recovery-target-action=promote

# 6. Инкрементальное восстановление поверх существующего каталога данных (быстро чинит повреждённый кластер)
sudo -u postgres pg_probackup-17 restore -B /backup/pgpro --instance=main -D /var/lib/postgresql/17/main -I checksum -j 4

# 7. Частичное: только одна база (остальные создаются пустыми файлами — после запуска их удаляют DROP DATABASE)
sudo -u postgres pg_probackup-17 restore -B /backup/pgpro --instance=main -D /var/lib/postgresql/17/pitr \
     --db-include=zup -j 4 --recovery-target-time='2026-10-10 14:25:00+05' --recovery-target-action=promote

sudo systemctl start postgresql@17-main && sudo systemctl start srv1cv8-8.3.27.1688@default
```

Режимы инкрементального восстановления `-I` [офиц.]:

| Режим | Что делает |
|---|---|
| `checksum` | читает все файлы данных, проверяет заголовок и контрольную сумму каждой страницы, заменяет недействительные и отличающиеся. Самый безопасный, рекомендуется по умолчанию |
| `lsn` | по `pg_control` определяет точку расхождения с цепочкой копий и заменяет только более новые страницы. Быстрее, но требует включённых контрольных сумм данных и достоверного `pg_control` |
| `none` | обычное восстановление в пустой каталог |

Что происходит с настройками восстановления: для копий в режиме ARCHIVE, при PITR и при `-R` pg_probackup после копирования файлов записывает параметры (`restore_command` с вызовом `archive-get`, цель) в файл `probackup_recovery.conf`, подключаемый из `postgresql.auto.conf` (PostgreSQL 12+) [офиц.], и создаёт сигнальный файл: `recovery.signal` при проигрывании архива или заданной цели, `standby.signal` при `-R` (подтверждено 19.10.2026 по исходному коду pg_probackup 2.5.16, `src/restore.c`). Самодостаточной STREAM-копии без заданной цели дополнительные настройки не нужны.

При действии по умолчанию (`pause`) после PITR сервер останется в режиме «только чтение» до вызова `SELECT pg_wal_replay_resume();` — для автоматических сценариев указывайте `--recovery-target-action=promote`.

В Debian-раскладке при восстановлении на новый сервер сначала создайте кластер (`sudo pg_createcluster 17 main`), остановите его, очистите каталог данных и только потом выполняйте `restore`: конфигурация в `/etc/postgresql/17/main` сама не появится (её берут из внешнего каталога копии или из отдельного архива).

### 5.10. Политика хранения, слияние, удаление, закрепление [офиц.]

| Параметр | Смысл | По умолчанию |
|---|---|---|
| `--retention-redundancy=N` | хранить N последних полных копий (со всеми их инкрементами) | 0 — выключено |
| `--retention-window=N` | хранить всё необходимое для восстановления на любой момент за последние N дней | 0 — выключено |
| `--wal-depth=N` | для скольких последних копий на каждой линии времени сохранять возможность PITR (остальной WAL можно удалить) | 0 — выключено |
| `--delete-expired` | удалить копии, не удовлетворяющие политике | — |
| `--merge-expired` | слить устаревшие полные копии с их ещё нужными инкрементами (иначе полную копию с «живыми» потомками удалить нельзя) | — |
| `--delete-wal` | удалить сегменты WAL, не нужные ни одной оставшейся копии | — |
| `--dry-run` | показать, что будет сделано, ничего не меняя | — |

Если заданы и избыточность, и окно, учитываются оба условия: при `--retention-redundancy=2 --retention-window=7` останутся две полные копии и всё, что нужно для восстановления за последние 7 дней.

```bash
# задать политику один раз
sudo -u postgres pg_probackup-17 set-config -B /backup/pgpro --instance=main --retention-redundancy=2 --retention-window=14

# посмотреть, что будет удалено, и удалить
sudo -u postgres pg_probackup-17 delete -B /backup/pgpro --instance=main --delete-expired --delete-wal --dry-run
sudo -u postgres pg_probackup-17 delete -B /backup/pgpro --instance=main --delete-expired --delete-wal
# со слиянием устаревших цепочек
sudo -u postgres pg_probackup-17 delete -B /backup/pgpro --instance=main --delete-expired --merge-expired --delete-wal

# удалить конкретную копию (вместе со всеми инкрементами, которые от неё зависят)
sudo -u postgres pg_probackup-17 delete -B /backup/pgpro --instance=main -i SBOL6N
# удалить все копии в заданном статусе
sudo -u postgres pg_probackup-17 delete -B /backup/pgpro --instance=main --status=ERROR

# слить инкрементальную копию с родителями в одну полную
sudo -u postgres pg_probackup-17 merge -B /backup/pgpro --instance=main -i SBOL6P -j 4

# закрепить копию на 90 дней / до даты / снять закрепление
sudo -u postgres pg_probackup-17 set-backup -B /backup/pgpro --instance=main -i SBOL6J --ttl=90d
sudo -u postgres pg_probackup-17 set-backup -B /backup/pgpro --instance=main -i SBOL6J --expire-time='2027-01-31 00:00:00+05'
sudo -u postgres pg_probackup-17 set-backup -B /backup/pgpro --instance=main -i SBOL6J --ttl=0
```

Каталоги копий нельзя удалять и перекладывать вручную (`rm`, `mv`) — только командами pg_probackup, иначе зависимые копии станут `ORPHAN`.

### 5.11. Архив WAL средствами pg_probackup: archive-push и archive-get

```ini
# postgresql.conf (или conf.d/10-archive.conf)
wal_level = replica
archive_mode = on
archive_command = '/usr/bin/pg_probackup-17 archive-push -B /backup/pgpro --instance=main --wal-file-name=%f --compress'
archive_timeout = 300
```

Синтаксис [офиц.]:

```text
pg_probackup archive-push -B backup_dir --instance=instance_name --wal-file-name=%f [--wal-file-path=%p]
     [--compress] [--compress-algorithm=…] [--compress-level=N] [-j num_threads] [--batch-size=N]
     [--overwrite] [--no-sync] [--no-ready-rename] [--archive-timeout=сек] [удалённый режим] [журнал]
pg_probackup archive-get -B backup_dir --instance=instance_name --wal-file-path=%p --wal-file-name=%f
     [-j num_threads] [--batch-size=N] [--prefetch-dir=…] [--no-validate-wal] [удалённый режим] [журнал]
```

- Сегменты складываются в `/backup/pgpro/wal/main/`. `--overwrite` разрешает заменить уже лежащий в архиве сегмент с другим содержимым (одинаковые пропускаются и без него). `-j` и `--batch-size` ускоряют архивацию при большом потоке WAL. Алгоритм `pglz` для `archive-push` не поддерживается.
- После включения архива копии можно снимать без `--stream` (режим ARCHIVE — копия меньше, но зависит от архива) и в режиме `PAGE`.
- В режиме ARCHIVE команда `backup` ждёт появления нужного сегмента в архиве `--archive-timeout` секунд (300 по умолчанию) и падает, если архивация не работает.
- При восстановлении `restore_command` с `archive-get` прописывается автоматически; задать свою можно ключом `--restore-command`.
- Проверка: `pg_probackup-17 show -B /backup/pgpro --instance=main --archive`.
- Сегменты чистятся ключом `--delete-wal` согласованно с копиями; `find … -delete` здесь не применять.

### 5.12. Удалённый режим по SSH [офиц.]

Схема: отдельный сервер копий (`backup_host`) хранит каталог копий и запускает pg_probackup; на сервере баз (`postgres_host`) pg_probackup запускается по SSH как агент. Удалённо работают команды `add-instance`, `backup`, `restore`, `catchup`, `archive-push`, `archive-get`. Сжатие выполняется на стороне сервера баз.

```bash
# 1. На обоих узлах установить pg_probackup ОДНОЙ версии
# 2. На backup_host от пользователя, который делает копии (например, backup):
ssh-copy-id postgres@postgres_host
# 3. Если архив WAL тоже хранится на backup_host — на postgres_host от пользователя postgres:
ssh-copy-id backup@backup_host
# 4. Бинарник должен находиться по SSH: либо в PATH пользователя postgres, либо задать --remote-path

pg_probackup-17 init -B /backup/pgpro
pg_probackup-17 add-instance -B /backup/pgpro -D /var/lib/postgresql/17/main --instance=main \
     --remote-host=postgres_host --remote-user=postgres
pg_probackup-17 set-config -B /backup/pgpro --instance=main \
     --remote-host=postgres_host --remote-user=postgres -h postgres_host -U backup -d backupdb
pg_probackup-17 backup -B /backup/pgpro --instance=main -b FULL --stream --temp-slot -j 4 --compress
```

Параметры удалённого режима: `--remote-proto=ssh|none` (по умолчанию `ssh`), `--remote-host`, `--remote-port` (22), `--remote-user` (по умолчанию — текущий пользователь), `--remote-path` (каталог установки pg_probackup на удалённом узле), `--ssh-options='…'`. Для архива на удалённом узле в `restore_command`: `--archive-host`, `--archive-port`, `--archive-user`.

`archive_command` на сервере баз при удалённом каталоге копий:

```ini
archive_command = '/usr/bin/pg_probackup-17 archive-push -B /backup/pgpro --instance=main --wal-file-name=%f --compress --remote-host=backup_host --remote-user=backup'
```

Замечания: подключение к СУБД (`-h`, `-U`, `-d`) идёт с сервера копий напрямую по сети — в `pg_hba.conf` сервера баз нужны строки и для обычного подключения роли `backup`, и для `replication`. При числе потоков больше 10 возможна ошибка SSH `kex_exchange_identification` — уменьшите `-j` или увеличьте `MaxStartups` в `sshd_config` [офиц.]. На Windows удалённый режим не поддерживается.

### 5.13. Структура каталога копий

```text
/backup/pgpro/
├── backups/
│   └── main/                       # экземпляр
│       ├── pg_probackup.conf       # конфигурация экземпляра (set-config / show-config)
│       ├── SBOL6J/                 # одна копия: backup.control, backup_content.control, database/, external_directories/
│       └── SBOL6N/
├── wal/
│   └── main/                       # архив WAL экземпляра (archive-push)
└── log/                            # журнал pg_probackup, если включён --log-level-file
```

Один каталог копий может обслуживать несколько экземпляров (кластеров PostgreSQL). Каталог целиком можно синхронизировать на другой носитель (`rsync`, `rclone`) — но только когда в нём нет копий в статусе `RUNNING`/`MERGING`.

### 5.14. PTRACK

- Требует расширения `ptrack` версии 2.0+ и поддержки в ядре: входит в Postgres Pro Standard/Enterprise (с 11.9.1), для ванильного PostgreSQL нужен патч ядра [офиц.]. Есть ли `ptrack` в конкретной сборке для 1С, проверяйте запросом: `SELECT * FROM pg_available_extensions WHERE name = 'ptrack';` (уточнено 19.10.2026: в «PostgreSQL для 1С» 16 и 18 модуля `ptrack` нет — его нет в перечне дополнительных модулей, приложение F документации сборки, — значит, режим `PTRACK` на сервере с `postgrespro-1c-16` недоступен, остаются `DELTA` и `PAGE`; для сборки от «1С» проверять запросом).
- Настройка [офиц.]: `CREATE EXTENSION ptrack;` в базе, к которой подключается pg_probackup; параметр `ptrack.map_size` (в мегабайтах) — рекомендуется N/1024, где N — размер кластера в МБ, значения выше 1024 не рекомендуются; перезапуск сервера. В `shared_preload_libraries` нужно добавить `ptrack` (подтверждено 19.10.2026: документация Postgres Pro 17, модуль `ptrack`, и README расширения `postgrespro/ptrack`) — на серверах 1С там обычно уже есть `plantuner` (и иногда `online_analyze`), дописывайте через запятую.
- После изменения `ptrack.map_size` карта сбрасывается — нужна новая полная копия.
- Роль копирования должна иметь доступ ко всем базам кластера.

## 6. pgBackRest, Barman, WAL-G — обзор и выбор

### 6.1. pgBackRest

Версия на 10.10.2026 — 2.59.x (2.59.3 от 04.10.2026; 18.10.2026 вышла 2.60.0 — сверено 19.10.2026 по ленте выпусков GitHub); в архивах Ubuntu: 22.04 — 2.37, 24.04 — 2.50, 26.04 — 2.58 (пакет `pgbackrest`; сверено 19.10.2026 по packages.ubuntu.com). Полные, дифференциальные и инкрементальные копии, блочный инкремент (`repo1-bundle=y` + `repo1-block=y`), параллельность (`process-max`), сжатие (`compress-type=zst`), шифрование репозитория (`repo1-cipher-type=aes-256-cbc`, `repo1-cipher-pass`), репозитории на диске, S3, Azure, GCS, выделенный сервер репозитория, асинхронная архивация (`archive-async=y`, `spool-path`). Всегда работает с архивом WAL.

```ini
# /etc/pgbackrest/pgbackrest.conf  (если его нет, pgBackRest проверяет старое расположение /etc/pgbackrest.conf)
[global]
repo1-path=/var/lib/pgbackrest
repo1-retention-full=2
compress-type=zst
process-max=4
start-fast=y

[main]
pg1-path=/var/lib/postgresql/17/main
```

```ini
# postgresql.conf
archive_mode = on
archive_command = 'pgbackrest --stanza=main archive-push %p'
```

```bash
sudo -u postgres pgbackrest --stanza=main stanza-create
sudo -u postgres pgbackrest --stanza=main check                       # проверка конфигурации и архивации
sudo -u postgres pgbackrest --stanza=main --type=full backup
sudo -u postgres pgbackrest --stanza=main --type=diff backup          # дифференциальная (от последней полной)
sudo -u postgres pgbackrest --stanza=main --type=incr backup          # инкрементальная
sudo -u postgres pgbackrest --stanza=main info
sudo -u postgres pgbackrest --stanza=main expire
# восстановление (сервер остановлен); --delta — поверх существующего каталога
sudo -u postgres pgbackrest --stanza=main --delta restore
sudo -u postgres pgbackrest --stanza=main --delta --type=time "--target=2026-10-10 14:25:00+05" --target-action=promote restore
```

Совместимость с конкретной сборкой для 1С проверяйте командами `stanza-create` и `check` на стенде: pgBackRest сверяет версии управляющего файла и системного каталога и на изменённых сборках может отказаться работать (подтверждено 19.10.2026 по исходному коду pgBackRest 2.59.3, `src/postgres/interface.c`: версия определяется по паре «control version / catalog version» из `pg_control`, при незнакомой паре — ошибка `unexpected control version = … and catalog version = …`; для форков есть параметр `--pg-version-force`, который по документации работает, только если форк не менял формат нужных полей). Совпадает ли эта пара у «PostgreSQL для 1С» с ванильной — проверять на стенде.

### 6.2. Barman

Версия 3.20.1 (29.09.2026), требует Python 3.12+. Рассчитан на выделенный сервер копий: забирает базовые копии через `pg_basebackup` (`backup_method = postgres`) или rsync/SSH, WAL — потоком (`pg_receivewal` со слотом) или через `archive_command`. Умеет политики хранения, инкрементальные копии PostgreSQL 17+, копии в облако (`barman-cloud-*`).

```ini

[pg1c]
description = "PostgreSQL 1C"
conninfo = host=192.168.1.20 user=barman dbname=postgres
streaming_conninfo = host=192.168.1.20 user=streaming_barman
backup_method = postgres
streaming_archiver = on
slot_name = barman
create_slot = auto
retention_policy = RECOVERY WINDOW OF 14 DAYS
```

```bash
barman check pg1c
barman switch-wal --force --archive pg1c
barman backup pg1c --wait
barman list-backups pg1c
barman show-backup pg1c latest
barman restore pg1c latest /var/lib/postgresql/17/main --remote-ssh-command "ssh postgres@192.168.1.20" \
       --target-time "2026-10-10 14:25:00+05"          # в старых версиях команда называлась recover
barman cron                                            # обслуживание; запускается по расписанию из пакета
```

Синтаксис конфигурации и команд сверен 19.10.2026 с документацией Barman 3.20.1 (docs.pgbarman.org: «Quickstart», «Commands», «Retention policies», «Configuration»): параметры секции сервера, `retention_policy = RECOVERY WINDOW OF … DAYS`, `switch-wal --force --archive`, `backup --wait`, псевдоним `latest`, `restore … --remote-ssh-command … --target-time` совпадают; `barman recover` в 3.20 объявлена устаревшей. Python 3.12+ — по `pyproject.toml` выпуска 3.20.1 (на Ubuntu 22.04 с Python 3.10 эта версия из pip не встанет).

### 6.3. WAL-G

Один исполняемый файл (берётся со страницы релизов GitHub `wal-g/wal-g`, кладётся в `/usr/local/bin/wal-g`); ориентирован на объектные хранилища (S3 и совместимые, GCS, Azure, а также файловая система и SSH). Сжатие lz4 (по умолчанию), zstd, lzma, brotli; шифрование (`WALG_LIBSODIUM_KEY`, `WALG_PGP_KEY`); дельта-копии (`WALG_DELTA_MAX_STEPS`). Переменные и команды ниже сверены 19.10.2026 с `docs/README.md` и `docs/PostgreSQL.md` проекта (ветка master): `delete` без `--confirm` — пробный прогон, `backup-push --verify` — проверка контрольных сумм страниц при копировании.

```bash
export WALG_S3_PREFIX=s3://pg-backup/1c            # имена подтверждены файлом docs/STORAGES.md проекта (WALG_S3_PREFIX, AWS_ACCESS_KEY_ID, AWS_SECRET_ACCESS_KEY, AWS_ENDPOINT, AWS_S3_FORCE_PATH_STYLE), 11.10.2026; имена переменных хранилища — по документации STORAGES
export AWS_ENDPOINT=https://s3.example.com
export AWS_ACCESS_KEY_ID=…  AWS_SECRET_ACCESS_KEY=…
export AWS_S3_FORCE_PATH_STYLE=true
export WALG_COMPRESSION_METHOD=zstd
export WALG_DELTA_MAX_STEPS=6

```

```bash
wal-g backup-push /var/lib/postgresql/17/main            # полная или дельта-копия
wal-g backup-list --pretty --detail
wal-g backup-fetch /var/lib/postgresql/17/main LATEST    # восстановление в пустой каталог

wal-g wal-verify integrity timeline                      # проверка непрерывности архива
```

```ini
archive_command = 'wal-g wal-push %p'
restore_command = 'wal-g wal-fetch %f %p'
```

## 7. Готовые скрипты и расписания

Скрипты этого раздела — рабочие заготовки [практика]: перед вводом в эксплуатацию прогоните каждый вручную и проверьте журнал.

### 7.1. Общие правила

- Утилиты PostgreSQL запускаются от пользователя `postgres` (не от root); архивирование файлов 1С и `/etc` — от root.
- Каталог копий — отдельная файловая система. Перед стартом проверять свободное место, а для сетевых ресурсов — что ресурс действительно смонтирован (`mountpoint -q`), иначе копия ляжет на корневой диск.
- Писать во временное имя (`*.partial`) и переименовывать после успеха: недописанная копия не должна выглядеть как готовая.
- Блокировка от параллельного запуска (`flock`), журнал с отметками времени, ненулевой код возврата при любой ошибке, уведомление при сбое.
- Ротацию выполнять только после успешной новой копии и всегда оставлять N последних копий независимо от их возраста.
- В окружении cron минимальный `PATH` — указывайте полные пути.

```bash
sudo install -o root -g root -m 755 pg-dump-all.sh pg-basebackup.sh pg-probackup-run.sh \
     pg-verify-dump.sh backup-notify.sh /usr/local/bin/
```

### 7.2. Ежедневный pg_dump каждой базы с ротацией и журналом

```bash
#!/usr/bin/env bash
# /usr/local/bin/pg-dump-all.sh — логические копии всех баз кластера (запуск от postgres)
# Код возврата 0 — выгружены все базы и глобальные объекты.
set -Euo pipefail
umask 077

BACKUP_ROOT=/backup/dump
KEEP_DAYS=14                        # хранить наборы столько дней
KEEP_MIN=5                          # но не меньше стольких последних наборов
PGBIN=/usr/lib/postgresql/17/bin    # Postgres Pro: /opt/pgpro/1c-17/bin
COMPRESS="-Z 6"                     # pg_dump 16+: можно "-Z zstd:3"
MIN_FREE_GB=20                      # минимум свободного места перед стартом
LOG_DIR=/var/log/pgbackup
NOTIFY=/usr/local/bin/backup-notify.sh
export PGHOST=/var/run/postgresql PGPORT=5432 PGUSER=postgres

stamp=$(date +%F_%H%M)
dest="$BACKUP_ROOT/$stamp"
log="$LOG_DIR/pg-dump-$stamp.log"
mkdir -p "$BACKUP_ROOT" "$LOG_DIR"
exec >>"$log" 2>&1
say() { printf '%s %s\n' "$(date '+%F %T')" "$*"; }
die() { say "FATAL: $*"; [ -x "$NOTIFY" ] && "$NOTIFY" "pg_dump: $*" "$log"; exit 1; }

exec 9>/run/lock/pg-dump-all.lock
flock -n 9 || die "предыдущий запуск ещё работает"

free_gb=$(df -BG --output=avail "$BACKUP_ROOT" | tail -1 | tr -dc '0-9')
(( free_gb >= MIN_FREE_GB )) || die "мало места в $BACKUP_ROOT: ${free_gb} ГБ"

mkdir "$dest.partial" || die "не удалось создать $dest.partial"
say "start, target $dest"
rc=0

"$PGBIN/pg_dumpall" --globals-only -f "$dest.partial/globals.sql" || { say "ERROR globals"; rc=1; }

mapfile -t dbs < <("$PGBIN/psql" -XAt -d postgres -c \
  "SELECT datname FROM pg_database WHERE datallowconn AND NOT datistemplate AND datname <> 'postgres' ORDER BY 1")
(( ${#dbs[@]} > 0 )) || die "список баз пуст"

for db in "${dbs[@]}"; do
    f="$dest.partial/$db.dump"
    t0=$SECONDS
    # shellcheck disable=SC2086
    if "$PGBIN/pg_dump" -Fc $COMPRESS -f "$f" "$db" && "$PGBIN/pg_restore" -l "$f" >/dev/null; then
        say "OK    $db  $(du -h "$f" | cut -f1)  $((SECONDS - t0)) s"
    else
        say "ERROR $db"; rc=1
    fi
done

( cd "$dest.partial" && sha256sum -- * > SHA256SUMS )

if (( rc != 0 )); then
    mv "$dest.partial" "$dest.FAILED"
    die "есть ошибки, набор сохранён как $dest.FAILED"
fi
mv "$dest.partial" "$dest"

# ротация: удалить наборы старше KEEP_DAYS, но всегда оставить KEEP_MIN последних
mapfile -t sets < <(find "$BACKUP_ROOT" -mindepth 1 -maxdepth 1 -type d -name '20??-??-??_????' | sort)
for (( i = 0; i < ${#sets[@]} - KEEP_MIN; i++ )); do
    if [[ -n $(find "${sets[i]}" -maxdepth 0 -mtime +"$KEEP_DAYS") ]]; then
        say "rotate: rm ${sets[i]}"; rm -rf -- "${sets[i]}"
    fi
done
find "$BACKUP_ROOT" -mindepth 1 -maxdepth 1 -type d \( -name '*.FAILED' -o -name '*.partial' \) -mtime +7 -exec rm -rf -- {} +
find "$LOG_DIR" -name 'pg-dump-*.log' -mtime +90 -delete
say "done OK"
```

Результат: `/backup/dump/2026-10-10_0130/{globals.sql, zup.dump, buh.dump, SHA256SUMS}`. `pg_restore -l` после каждого дампа проверяет, что архив читается (оглавление), но не данные — полноценная проверка в разделе 8.

### 7.3. pg_basebackup по расписанию

```bash
#!/usr/bin/env bash
# /usr/local/bin/pg-basebackup.sh — физическая копия кластера (запуск от postgres)
set -Eeuo pipefail
umask 077

BACKUP_ROOT=/backup/base
KEEP=4                              # сколько последних копий хранить
PGBIN=/usr/lib/postgresql/17/bin
LOG_DIR=/var/log/pgbackup
NOTIFY=/usr/local/bin/backup-notify.sh
export PGHOST=/var/run/postgresql PGPORT=5432 PGUSER=postgres

stamp=$(date +%F_%H%M)
dest="$BACKUP_ROOT/$stamp"
log="$LOG_DIR/pg-basebackup-$stamp.log"
mkdir -p "$BACKUP_ROOT" "$LOG_DIR"
exec >>"$log" 2>&1
trap 'rc=$?; echo "$(date "+%F %T") FAILED rc=$rc line $LINENO"; rm -rf -- "$dest.partial";
      [ -x "$NOTIFY" ] && "$NOTIFY" "pg_basebackup FAILED (rc=$rc)" "$log"; exit $rc' ERR

exec 9>/run/lock/pg-basebackup.lock
flock -n 9

echo "$(date '+%F %T') start $dest"
"$PGBIN/pg_basebackup" -D "$dest.partial" -Ft -z -X stream -c fast -w \
        --manifest-checksums=SHA256 -l "auto $stamp"

# pg_verifybackup понимает tar-копии с 18-й версии; на более старых проверяем целостность архивов
ver=$("$PGBIN/pg_verifybackup" -V | sed -E 's/^[^0-9]*([0-9]+).*/\1/')
if (( ver >= 18 )); then
    "$PGBIN/pg_verifybackup" -F t -n -q "$dest.partial"
else
    for f in "$dest.partial"/*.tar.gz; do gzip -t "$f"; done
fi
test -s "$dest.partial/backup_manifest"

mv "$dest.partial" "$dest"
echo "$(date '+%F %T') OK $(du -sh "$dest" | cut -f1)"

# ротация: оставить KEEP последних
mapfile -t all < <(find "$BACKUP_ROOT" -mindepth 1 -maxdepth 1 -type d -name '20??-??-??_????' | sort)
for (( i = 0; i < ${#all[@]} - KEEP; i++ )); do
    echo "rotate: rm ${all[i]}"; rm -rf -- "${all[i]}"
done
find "$LOG_DIR" -name 'pg-basebackup-*.log' -mtime +90 -delete
```

Если включён собственный архив WAL (раздел 4), число хранимых базовых копий и срок хранения WAL должны быть согласованы (раздел 4.7).

### 7.4. pg_probackup: еженедельная FULL и ежедневная DELTA

Предполагается, что каталог копий и экземпляр уже созданы, а подключение, сжатие и политика хранения записаны через `set-config` (раздел 5.4).

```bash
#!/usr/bin/env bash
# /usr/local/bin/pg-probackup-run.sh [FULL|DELTA|PAGE|PTRACK|auto] (запуск от postgres)
set -Euo pipefail
umask 077

PBK=/usr/bin/pg_probackup-17
B=/backup/pgpro
INST=main
JOBS=4
FULL_DOW=7                          # день полной копии: 1 — понедельник … 7 — воскресенье
INCR_MODE=DELTA
LOG_DIR=/var/log/pgbackup
NOTIFY=/usr/local/bin/backup-notify.sh

mode=${1:-auto}
if [[ $mode == auto ]]; then
    if [[ $(date +%u) == "$FULL_DOW" ]]; then mode=FULL; else mode=$INCR_MODE; fi
fi

log="$LOG_DIR/pg-probackup-$(date +%F_%H%M).log"
mkdir -p "$LOG_DIR"
exec >>"$log" 2>&1
say() { printf '%s %s\n' "$(date '+%F %T')" "$*"; }
die() { say "FATAL: $*"; [ -x "$NOTIFY" ] && "$NOTIFY" "pg_probackup: $*" "$log"; exit 1; }

exec 9>/run/lock/pg-probackup.lock
flock -n 9 || die "предыдущий запуск ещё работает"

run() { "$PBK" backup -B "$B" --instance="$INST" -b "$1" --stream --temp-slot -j "$JOBS" --compress; }

say "start mode=$mode"
if [[ $mode == FULL ]]; then
    run FULL || die "FULL не выполнена"
elif ! run "$mode"; then
    say "WARN: $mode не выполнена (нет действительной полной копии?) — делаю FULL"
    "$PBK" delete -B "$B" --instance="$INST" --status=ERROR || true
    run FULL || die "ни $mode, ни FULL не выполнены"
fi

# политика хранения берётся из конфигурации экземпляра (retention-redundancy / retention-window)
"$PBK" delete -B "$B" --instance="$INST" --delete-expired --delete-wal || die "ошибка удаления устаревших копий"

"$PBK" show -B "$B" --instance="$INST"
find "$LOG_DIR" -name 'pg-probackup-*.log' -mtime +90 -delete
say "done OK"
```

Команда `backup` сама проверяет созданную копию (если не указан `--no-validate`), поэтому отдельный `validate` после каждой копии не обязателен; раз в неделю полезно прогонять `validate` по всему каталогу.

### 7.5. Запуск через cron

```bash
# /etc/cron.d/pgbackup — системный crontab: шестое поле — пользователь
SHELL=/bin/bash
PATH=/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin
MAILTO=admin@example.com

# логические копии всех баз — каждый день в 01:30
30 1 * * *   postgres  /usr/local/bin/pg-dump-all.sh
# pg_probackup — каждый день в 03:00 (воскресенье FULL, остальные дни DELTA)
0 3 * * *    postgres  /usr/local/bin/pg-probackup-run.sh auto
# либо pg_basebackup — по воскресеньям в 03:00
#0 3 * * 0   postgres  /usr/local/bin/pg-basebackup.sh
# проверка дампа тестовым восстановлением — по субботам в 05:00
0 5 * * 6    postgres  /usr/local/bin/pg-verify-dump.sh zup
# файлы 1С и конфигурация — каждый день в 00:30
30 0 * * *   root      /usr/local/bin/backup-1c-files.sh
# вынос копий на внешнее хранилище — каждый день в 06:00
0 6 * * *    root      /usr/local/bin/backup-offsite.sh
```

Файл в `/etc/cron.d` должен принадлежать root, иметь права `0644` и имя без точки. `MAILTO` работает только при настроенной отправке почты с сервера. Проверка: `grep CRON /var/log/syslog | tail` или `journalctl -u cron -n 50`.

### 7.6. Запуск через systemd timer

Преимущества перед cron: журнал в journald, `Persistent=true` (пропущенный из-за выключения запуск выполнится после загрузки), зависимости от службы PostgreSQL, штатная реакция на сбой через `OnFailure=`.

```ini
# /etc/systemd/system/pg-probackup.service
[Unit]
Description=pg_probackup backup (PostgreSQL 17 main)
After=postgresql@17-main.service
Requires=postgresql@17-main.service
OnFailure=backup-notify@%n.service

[Service]
Type=oneshot
User=postgres
Group=postgres
ExecStart=/usr/local/bin/pg-probackup-run.sh auto
Nice=10
IOSchedulingClass=best-effort
IOSchedulingPriority=7
TimeoutStartSec=12h
```

```ini
# /etc/systemd/system/pg-probackup.timer
[Unit]
Description=Nightly pg_probackup backup

[Timer]
OnCalendar=*-*-* 03:00:00
RandomizedDelaySec=5min
Persistent=true

[Install]
WantedBy=timers.target
```

```ini
# /etc/systemd/system/backup-notify@.service — шаблон уведомления о сбое любого юнита
[Unit]
Description=Notify about failed unit %i

[Service]
Type=oneshot
ExecStart=/usr/local/bin/backup-notify.sh "systemd unit FAILED: %i"
```

```bash
sudo systemctl daemon-reload
sudo systemctl enable --now pg-probackup.timer
systemctl list-timers 'pg-*'                    # когда следующий запуск
sudo systemctl start pg-probackup.service       # запустить сейчас, не дожидаясь таймера
journalctl -u pg-probackup.service -n 100 --no-pager
systemd-analyze calendar 'Sun *-*-* 03:00:00'   # проверить выражение OnCalendar
```

Аналогично оформляются `pg-dump-all.service/.timer` и остальные задания. Для Postgres Pro в `After=`/`Requires=` указывают `postgrespro-1c-17.service`.

### 7.7. Уведомления об ошибках и контроль «свежести»

```bash
#!/usr/bin/env bash
# /usr/local/bin/backup-notify.sh "тема" [файл_журнала] — уведомление о сбое
subject="$1"; logfile="${2:-}"
host=$(hostname -f 2>/dev/null || hostname)
body=$( [ -n "$logfile" ] && [ -r "$logfile" ] && tail -n 40 "$logfile" )

# 1) системный журнал — всегда
logger -t backup -p user.err -- "$subject"

# 2) почта — если установлен и настроен почтовый клиент (например, пакеты msmtp-mta и bsd-mailx)
if command -v mail >/dev/null 2>&1; then
    printf '%s\n' "$body" | mail -s "[$host] $subject" admin@example.com || true
fi

# 3) Telegram — если есть /etc/backup-notify.env со строками TG_TOKEN=… и TG_CHAT=… (права 0640 root:postgres)
if [ -r /etc/backup-notify.env ]; then
    . /etc/backup-notify.env
    curl -fsS -m 20 "https://api.telegram.org/bot${TG_TOKEN}/sendMessage" \
         --data-urlencode "chat_id=${TG_CHAT}" \
         --data-urlencode "text=[$host] $subject" >/dev/null || true
fi
```

Уведомление о сбое не сработает, если задание вообще не запустилось (сервер выключен, сломан cron, скрипт удалён). Поэтому нужен отдельный контроль «свежести» копий — с другого задания, а лучше с другого узла [практика]:

```bash
#!/usr/bin/env bash
# /usr/local/bin/backup-freshness.sh — тревога, если нет свежих копий (запуск раз в сутки, от postgres)
N=/usr/local/bin/backup-notify.sh
# дамп моложе 26 часов
[ -n "$(find /backup/dump -mindepth 2 -name '*.dump' -mmin -1560 -print -quit)" ] || "$N" "нет дампов моложе 26 ч"
# архив WAL: последний файл моложе 30 минут (если архив включён)
[ -n "$(find /backup/wal -type f -mmin -30 -print -quit 2>/dev/null)" ] || "$N" "архив WAL не пополнялся 30 мин"
# свободное место на томе копий
[ "$(df --output=pcent /backup | tail -1 | tr -dc '0-9')" -lt 85 ] || "$N" "том /backup заполнен более чем на 85 %"
```

Для pg_probackup свежесть удобно брать из `show --format=json` (поля статуса и времени окончания последней копии).

## 8. Проверка резервных копий

### 8.1. Уровни проверки

| Уровень | Что делается | Когда |
|---|---|---|
| 1. Целостность файлов копии | `sha256sum -c SHA256SUMS`, `gzip -t`, `pg_restore -l`, `pg_verifybackup`, `pg_probackup validate`, `pgbackrest verify` | после каждой копии и после переноса на другой носитель |
| 2. Тестовое восстановление | развернуть дамп во временную базу или физическую копию в отдельный кластер на другом порту | раз в неделю — раз в месяц, автоматически |
| 3. Проверка восстановленных данных | `pg_amcheck`, `pg_dump` в `/dev/null`, сверка числа таблиц и строк; для 1С — открыть копию, выполнить «Тестирование и исправление» в режиме проверки | вместе с уровнем 2 |
| 4. Учебное восстановление «с нуля» | новый сервер/ВМ, установка СУБД и 1С, восстановление по инструкции с замером времени (фактический RTO) | один-два раза в год и после смены схемы копирования |

### 8.2. Тестовое восстановление дампа (автоматизация)

```bash
#!/usr/bin/env bash
# /usr/local/bin/pg-verify-dump.sh <база> — восстановить последний дамп во временную базу и сверить (от postgres)
set -Eeuo pipefail
db=${1:?usage: pg-verify-dump.sh <база>}
PGBIN=/usr/lib/postgresql/17/bin
BACKUP_ROOT=/backup/dump
NOTIFY=/usr/local/bin/backup-notify.sh
export PGHOST=/var/run/postgresql PGPORT=5432 PGUSER=postgres
log=/var/log/pgbackup/pg-verify-$db-$(date +%F).log
exec >>"$log" 2>&1
tmpdb="verify_${db}"
trap 'rc=$?; echo "FAILED rc=$rc line $LINENO"; "$PGBIN/dropdb" --if-exists "$tmpdb" || true;
      [ -x "$NOTIFY" ] && "$NOTIFY" "проверка дампа $db: ОШИБКА" "$log"; exit $rc' ERR

last=$(find "$BACKUP_ROOT" -mindepth 1 -maxdepth 1 -type d -name '20??-??-??_????' | sort | tail -1)
f="$last/$db.dump"
echo "$(date '+%F %T') verify $f"
( cd "$last" && sha256sum -c --quiet SHA256SUMS )

"$PGBIN/dropdb" --if-exists "$tmpdb"
"$PGBIN/createdb" -T template0 "$tmpdb"
"$PGBIN/pg_restore" -d "$tmpdb" -j 4 -e "$f"

q="SELECT count(*) FROM pg_class c JOIN pg_namespace n ON n.oid = c.relnamespace
   WHERE n.nspname = 'public' AND c.relkind = 'r'"
src=$("$PGBIN/psql" -XAt -d "$db"    -c "$q")
dst=$("$PGBIN/psql" -XAt -d "$tmpdb" -c "$q")
echo "tables: source=$src restored=$dst"
(( dst > 0 ))
(( src - dst <= 5 && dst - src <= 5 )) || { echo "число таблиц расходится"; false; }
# содержательная проверка: таблица конфигурации 1С не пуста
"$PGBIN/psql" -XAt -d "$tmpdb" -c "SELECT 'config rows: ' || count(*) FROM public.config"

"$PGBIN/dropdb" "$tmpdb"
echo "$(date '+%F %T') OK"
```

Временной базе нужно столько же места, сколько занимает исходная, и восстановление нагружает диск — запускайте в нерабочее время, а лучше на отдельном сервере с той же сборкой PostgreSQL. Небольшое расхождение числа таблиц с рабочей базой допустимо (между дампом и проверкой могла пройти реструктуризация), поэтому в скрипте есть допуск.

### 8.3. Тестовое восстановление физической копии на отдельный кластер и порт

Главная опасность: тестовый экземпляр, поднятый с рабочими настройками, может начать архивировать WAL в рабочий архив или занять рабочий порт. Поэтому порт меняют, архивацию отключают, файл `postgresql.auto.conf` из копии обнуляют.

Вариант для Debian-раскладки (сборка от «1С»):

```bash
# 1. Кластер-заготовка на порту 5433: появятся /etc/postgresql/17/verify и /var/lib/postgresql/17/verify
sudo pg_createcluster 17 verify -p 5433
D=/var/lib/postgresql/17/verify

# 2. Заменить его данные содержимым копии
sudo -u postgres sh -c "rm -rf $D && install -d -m 700 $D"
sudo -u postgres tar -xzf /backup/base/2026-10-10_0300/base.tar.gz   -C $D
sudo -u postgres tar -xzf /backup/base/2026-10-10_0300/pg_wal.tar.gz -C $D/pg_wal
#    для pg_probackup вместо tar:
#    sudo -u postgres pg_probackup-17 restore -B /backup/pgpro --instance=main -D $D -j 4

# 3. Обезвредить настройки, приехавшие из рабочего кластера
sudo -u postgres sh -c ": > $D/postgresql.auto.conf"
sudo pg_conftool 17 verify set archive_mode off
sudo pg_conftool 17 verify set listen_addresses ''        # только локальный сокет

# 4. Запуск и проверки
sudo pg_ctlcluster 17 verify start
pg_lsclusters
sudo -u postgres psql -p 5433 -Atc "SELECT datname, pg_size_pretty(pg_database_size(datname))
                                    FROM pg_database WHERE NOT datistemplate"
sudo -u postgres psql -p 5433 -d zup -Atc "SELECT count(*) FROM public.config"
sudo -u postgres /usr/lib/postgresql/17/bin/pg_amcheck -p 5433 --all --install-missing -j 4 -P
sudo -u postgres pg_dump -p 5433 -Fc -f /dev/null zup     # прочитать все строки всех таблиц

# 5. Убрать за собой
sudo pg_dropcluster 17 verify --stop
```

Вариант для раскладки Postgres Pro (конфигурация лежит в каталоге данных; параметры командной строки перекрывают оба файла конфигурации):

```bash
D=/var/lib/pgpro/1c-17/verify
sudo -u postgres /opt/pgpro/1c-17/bin/pg_ctl -D $D -w -l $D/verify.log \
     -o "-p 5433 -c listen_addresses='' -c archive_mode=off -c shared_buffers=512MB" start
# … те же проверки с -p 5433 …
sudo -u postgres /opt/pgpro/1c-17/bin/pg_ctl -D $D -m fast stop && sudo rm -rf $D
```

Замечания: тестовому кластеру нужно место, равное размеру всего рабочего кластера; если копия восстанавливается с проигрыванием архива (есть `recovery.signal`), значения `max_connections`, `max_worker_processes`, `max_wal_senders`, `max_prepared_transactions`, `max_locks_per_transaction` в тестовом кластере должны быть не меньше рабочих — подтверждено документацией PostgreSQL 18, глава «Hot Standby» (там перечислены `max_connections`, `max_prepared_transactions`, `max_locks_per_transaction`, `max_wal_senders`, `max_worker_processes`; сверено 11.10.2026) (иначе восстановление в режиме горячего резерва остановится) — либо задайте `hot_standby = off`.

Чтобы открыть восстановленную копию в 1С, базу регистрируют в кластере 1С как новую информационную базу с указанием порта (раздел 2.4) и с заблокированными регламентными заданиями.

### 8.4. pg_verifybackup, pg_checksums, amcheck

`pg_verifybackup` — раздел 3.5.

**pg_checksums** — контрольные суммы страниц данных [офиц.]. Работает только на **корректно остановленном** кластере (в том числе на восстановленной копии).

| Ключ | Назначение |
|---|---|
| `-D каталог` | каталог данных |
| `-c`, `--check` | проверить контрольные суммы (режим по умолчанию) |
| `-e`, `--enable` / `-d`, `--disable` | включить / выключить контрольные суммы |
| `-f номер`, `--filenode=номер` | проверить только одно отношение |
| `-P`, `-v` | прогресс / список проверенных файлов |

```bash
sudo -u postgres psql -Atc "SHOW data_checksums;"                      # включены ли
# проверить восстановленную (остановленную) копию
sudo -u postgres /usr/lib/postgresql/17/bin/pg_checksums --check -D /var/lib/postgresql/17/verify -P
# включить на рабочем кластере (в окно обслуживания: читает и переписывает все данные)
sudo systemctl stop postgresql@17-main
sudo -u postgres /usr/lib/postgresql/17/bin/pg_checksums --enable -D /var/lib/postgresql/17/main -P
sudo systemctl start postgresql@17-main
```

С PostgreSQL 18 `initdb` включает контрольные суммы по умолчанию; кластеры, созданные раньше, обычно без них [практика]. Исключение — «PostgreSQL для 1С» от Postgres Professional: `pg-setup initdb` включает контрольные суммы и в ветке 16 (документация сборки 16, раздел о `pg-setup`; дополнено 19.10.2026) — на сервере проверить `SHOW data_checksums;`. Без контрольных сумм повреждение блока на диске обнаруживается только при обращении к нему, а в физические копии попадает незамеченным. После включения сделайте новую полную копию. При наличии реплик состояние контрольных сумм меняют согласованно на всех узлах [офиц.].

**amcheck / pg_amcheck** — логическая проверка индексов B-tree и таблиц.

```bash
# все базы, до 4 подключений; расширение amcheck создаётся при необходимости
sudo -u postgres /usr/lib/postgresql/17/bin/pg_amcheck --all --install-missing -j 4 -P
# одна база, с проверкой «каждая строка таблицы есть в индексе»
sudo -u postgres /usr/lib/postgresql/17/bin/pg_amcheck -d zup --heapallindexed -j 4 -P
```

```sql
CREATE EXTENSION IF NOT EXISTS amcheck;
SELECT bt_index_check('public._reference155_1'::regclass, true);   -- второй аргумент — heapallindexed
SELECT * FROM verify_heapam('public._reference155');               -- проверка таблицы (14+)
```

Ключи `pg_amcheck` [офиц.]: `-a`/`--all`, `-d база`, `-D` (исключить базу), `-t`/`-T` (таблицы), `-i`/`-I` (индексы), `-s`/`-S` (схемы), `--heapallindexed`, `--parent-check`, `--rootdescend`, `--checkunique`, `--on-error-stop`, `--skip=all-frozen|all-visible`, `--no-dependent-indexes`, `--no-dependent-toast`, `--install-missing[=схема]`, `-j N`, `-P`, `-v`. Обычные проверки не мешают работе; `--parent-check` и `--rootdescend` берут более сильные блокировки и останавливают `INSERT`/`UPDATE`/`DELETE` на время проверки отношения — на рабочей базе их запускают только в окно, на тестовой копии — свободно.

### 8.5. Сверка размеров и содержимого

```bash
# размер дампа резко уменьшился относительно предыдущего — повод разобраться
ls -l /backup/dump/*/zup.dump | tail -7

# число таблиц и приблизительное число строк (после ANALYZE) — выполнить в исходной и восстановленной базе
sudo -u postgres psql -d zup -Atc "SELECT count(*), sum(c.reltuples)::bigint
    FROM pg_class c JOIN pg_namespace n ON n.oid = c.relnamespace
    WHERE n.nspname = 'public' AND c.relkind = 'r';"

# точное число строк в нескольких ключевых таблицах
sudo -u postgres psql -d zup -Atc "SELECT count(*) FROM public.config;"
```

Размер восстановленной из дампа базы (`pg_database_size`) обычно **меньше** исходной: в ней нет раздувания таблиц и индексов. Это нормально и ошибкой не является. Физическая копия после восстановления совпадает с исходным кластером по размеру.

## 9. Специфика 1С

### 9.1. Выгрузка в .dt и копия средствами СУБД

Позиция документации 1С [офиц., руководство администратора, разделы 6.7–6.9 и глава об автономном сервере]: использовать выгрузку информационной базы в файл как способ резервного копирования **не рекомендуется**; про `ibcmd infobase dump` сказано прямо — выгрузка в dt-файл средством резервного копирования не является. Для клиент-серверного варианта рекомендуемый инструмент — штатные средства используемой СУБД.

| Свойство | Выгрузка `.dt` | Копия средствами PostgreSQL |
|---|---|---|
| Назначение по документации | образ базы, не зависящий от способа хранения; перенос между СУБД и между файловым и серверным вариантами | резервное копирование |
| Доступ к базе | монопольный: пользователи должны выйти; для `ibcmd` — вообще никаких подключений, иначе возможна потеря целостности файла | работа не прерывается |
| Длительность и ресурсы | долго, большие затраты оперативной памяти; загрузка требует на сервере 1С места под временные файлы примерно в размер развёрнутой базы | `pg_dump` — умеренно; физическая копия — быстро |
| Надёжность | если в базе были ошибки, файл может оказаться незагружаемым — и выяснится это только при загрузке | проверяется (`validate`, `pg_verifybackup`, тестовое восстановление) |
| Точка восстановления | только момент выгрузки | любой момент (PITR) |
| Журнал регистрации | не входит | не входит |
| Автоматизация на сервере без графики | `ibcmd` (нужно отключить всех), пакетный режим конфигуратора требует графического окружения | штатно, из cron/systemd |

Когда `.dt` всё же уместен [практика]: перенос базы на другую СУБД или в файловый вариант; передача базы разработчику или в поддержку; дополнительная, не зависящая от СУБД копия небольшой базы перед рискованной операцией — в дополнение к копии СУБД, а не вместо неё. Перед выгрузкой документация советует выполнить тестирование информационной базы.

```bash
# выгрузка средствами ibcmd напрямую из СУБД (кластер 1С на это время остановить: подключений быть не должно)
/opt/1cv8/x86_64/8.3.27.1688/ibcmd infobase dump --dbms=PostgreSQL --database-server=localhost \
     --database-name=zup --database-user=postgres --request-database-password \
     --data=/tmp/ibcmd-zup /backup/dt/zup_$(date +%F).dt
```

Ключи сверены 19.10.2026 с документацией 8.3.27 («Руководство администратора», 4.10.4.3 и общие параметры offline-режима `ibcmd`; конспекты `../its-docs/adm-pr04-komandnye-stroki-utilit-p2.md` и `…-p3.md`): `--dbms=PostgreSQL` (так значение записано в документации), `--database-server`, `--database-name`, `--database-user`, `--request-database-password` (пароль из stdin), `--data` (каталог данных), путь к dt-файлу последним аргументом. Если в информационной базе есть пользователи, добавьте `--user=… --password=…` (пользователь ИБ). Для своей версии всё равно сверьтесь с `ibcmd infobase dump --help`.

### 9.2. Блокировка сеансов и регламентных заданий перед восстановлением

Требование [офиц.]: во время восстановления средствами СУБД к информационной базе не должно быть никаких подключений — ни конфигуратора, ни клиентских приложений, ни фоновых и регламентных заданий, ни средств администрирования.

Самый простой и надёжный способ на сервере, где допустим общий простой, — остановить службу сервера 1С на время восстановления:

```bash
sudo systemctl stop srv1cv8-8.3.27.1688@default
# … восстановление …
sudo systemctl start srv1cv8-8.3.27.1688@default
```

Если остальные базы должны продолжать работать, блокируют одну базу средствами кластера (`rac`; сервер `ras` запущен):

```bash
V=8.3.27.1688; RAC=/opt/1cv8/x86_64/$V/rac
CL=$($RAC cluster list | awk '/^cluster/{print $3}')
$RAC infobase --cluster=$CL summary list                       # найти UUID базы
IB=<UUID_информационной_базы>

# 1. Запретить новые сеансы и регламентные задания
$RAC infobase --cluster=$CL update --infobase=$IB --infobase-user='Администратор' --infobase-pwd='***' \
     --sessions-deny=on --denied-message='Восстановление базы из резервной копии' \
     --permission-code='restore2026' --scheduled-jobs-deny=on

# 2. Завершить уже открытые сеансы
for s in $($RAC session --cluster=$CL list --infobase=$IB | awk '/^session +:/{print $3}'); do
    $RAC session --cluster=$CL terminate --session=$s
done

# 3. Убедиться, что подключений к базе данных не осталось; оставшиеся — оборвать
sudo -u postgres psql -c "SELECT pid, usename, application_name, client_addr, state
                          FROM pg_stat_activity WHERE datname = 'zup';"
sudo -u postgres psql -c "SELECT pg_terminate_backend(pid) FROM pg_stat_activity
                          WHERE datname = 'zup' AND pid <> pg_backend_pid();"
```

- `--permission-code` — код разрешения: с ним администратор может войти в заблокированную базу (параметр запуска `/UC restore2026`).
- Рабочие процессы 1С держат соединения с СУБД в пуле даже без сеансов, поэтому шаг 3 обязателен [практика].
- Снятие блокировки: тот же `update` с `--sessions-deny=off --scheduled-jobs-deny=off`. Регламентные задания разумно включать только после проверки восстановленной базы.

### 9.3. Восстановление поверх работающей базы (логическая копия)

Порядок [практика], опирающийся на требования из 9.2:

```bash
# 1. Заблокировать сеансы и регламентные задания (9.2) или остановить сервер 1С
# 2. Страховочная копия текущего состояния — даже если база «сломана»
sudo -u postgres pg_dump -Fc -f /backup/dump/zup_before_restore_$(date +%F_%H%M).dump zup

# 3. Убрать старую базу. Вариант А — переименовать (остаётся для разбора; нужно место):
sudo -u postgres psql -c "ALTER DATABASE zup RENAME TO zup_broken_20261010;"
#    Вариант Б — удалить (FORCE обрывает оставшиеся подключения, PostgreSQL 13+):
#    sudo -u postgres psql -c "DROP DATABASE zup WITH (FORCE);"

# 4. Создать пустую базу и восстановить
sudo -u postgres createdb -T template0 zup
sudo -u postgres pg_restore -d zup -j 4 -e /backup/dump/2026-10-10_0130/zup.dump
sudo -u postgres vacuumdb -d zup --analyze-only -j 4

# 5. Снять блокировку (9.2). Если простой остальных баз допустим — перед этим перезапустить сервер 1С:
#    это гарантированно сбрасывает кеши рабочих процессов и пул соединений со старой базой
sudo systemctl restart srv1cv8-8.3.27.1688@default
```

Пояснения:

- Регистрация базы в кластере 1С остаётся прежней: запись в реестре кластера ссылается на имя базы данных, а оно не изменилось.
- Не используйте `pg_restore --clean` поверх существующей базы 1С: объекты, которых нет в дампе, останутся (раздел 2.8).
- После возврата к более ранней копии индекс полнотекстового поиска в каталоге кластера не соответствует данным — его перестраивают средствами конфигурации [практика].
- Журнал регистрации продолжает содержать события, случившиеся после точки восстановления, — это нормально и даже полезно для разбора.
- Если база участвует в обменах (РИБ, синхронизация), возврат к старой копии нарушает нумерацию сообщений обмена — после восстановления обмены требуют проверки и, возможно, повторной выгрузки [практика].

### 9.4. Физическое восстановление и несколько баз в одном кластере PostgreSQL

`pg_basebackup`, `pg_probackup restore` и PITR возвращают в прошлое **весь кластер PostgreSQL**. Если в нём лежат «Бухгалтерия», «Зарплата» и «Торговля», откат ради одной базы уничтожит работу в двух других. Варианты:

- восстанавливать копию в отдельный каталог на другом порту и переносить нужную базу дампом (раздел 11.3) — основной способ;
- `pg_probackup restore --db-include=имя` — ускоряет такое побочное восстановление, остальные базы не копируются;
- критичные базы держать в отдельных кластерах PostgreSQL (`pg_createcluster 17 buh -p 5433`) — тогда у каждой свой архив и своя точка восстановления [практика].

Скрипт для служебных файлов:

```bash
#!/usr/bin/env bash
# /usr/local/bin/backup-1c-files.sh — служебные файлы 1С, конфигурация PostgreSQL и веб-сервера (от root)
set -Euo pipefail
umask 077
DST=/backup/1c-files
SRVDATA=/home/usr1cv8/.1cv8/1C/1cv8        # значение SRV1CV8_DATA
REG=reg_1541
KEEP_DAYS=30
N=/usr/local/bin/backup-notify.sh
stamp=$(date +%F)
mkdir -p "$DST/eventlog"

# 1) небольшие файлы — одним архивом; берём только то, что существует
items=()
for p in "$SRVDATA/1cv8wsrv.lst" "$SRVDATA/$REG/1CV8Clst.lst" /var/1C/licenses \
         /opt/1cv8/conf /opt/1cv8/x86_64/*/conf "$SRVDATA/conf" \
         /etc/postgresql /etc/default/postgrespro-1c-* /etc/apache2 /etc/systemd/system /etc/cron.d /etc/fstab /etc/hosts /etc/netplan \
         /usr/local/bin /var/lib/postgresql/.pgpass /var/www; do
    [ -e "$p" ] && items+=("${p#/}")
done
rc=0
tar -czf "$DST/1c-conf-$stamp.tar.gz" -C / "${items[@]}" || rc=$?
# код 1 у tar — «файл изменился во время чтения»; для живых файлов допустимо
(( rc <= 1 )) || { "$N" "backup-1c-files: tar rc=$rc"; exit "$rc"; }

# 2) журналы регистрации — зеркалом (большие и постоянно дописываются)
rsync -a --prune-empty-dirs --include='*/' --include='*/1Cv8Log/***' --exclude='*' \
      "$SRVDATA/$REG/" "$DST/eventlog/$REG/" || "$N" "backup-1c-files: rsync журнала rc=$?"

find "$DST" -maxdepth 1 -name '1c-conf-*.tar.gz' -mtime +"$KEEP_DAYS" -delete
```

Архив содержит файлы лицензий и пароли (`.pgpass`) — храните его с теми же предосторожностями, что и копии баз.

## 10. Стратегии: RPO/RTO, правило 3-2-1, вынос копий, шифрование, сроки хранения

### 10.1. Типовые схемы по размеру базы

Границы размеров и оценки времени — ориентиры [практика]; фактические RPO и RTO измеряйте учебным восстановлением.

| | Малая база (до ~50 ГБ) | Средняя (~50–500 ГБ) | Большая (от ~500 ГБ) |
|---|---|---|---|
| Основной метод | ежедневный `pg_dump -Fc` каждой базы | pg_probackup: `FULL` раз в неделю, `DELTA` ежедневно, `--stream` | pg_probackup или pgBackRest: `FULL` раз в 1–2 недели, инкремент ежедневно (DELTA / PTRACK / блочный), параллельность |
| PITR | по желанию: архив WAL + еженедельный `pg_basebackup` | архив WAL (`archive-push`), `archive_timeout` 60–300 с | архив WAL обязателен; дополнительно потоковая реплика |
| Дополнительно | `pg_basebackup` раз в неделю | еженедельный `pg_dump` — независимая логическая копия и материал для долгого хранения | `pg_dump` только по необходимости (идёт часами); реплика как средство сокращения RTO |
| Достижимый RPO | 24 ч (минуты — при архиве WAL) | минуты | минуты — секунды |
| RTO (порядок величины) | десятки минут | от получаса до нескольких часов | часы; при переключении на реплику — минуты |
| Хранение | 14 ежедневных, 8 еженедельных, 12 ежемесячных | `--retention-redundancy=2…4`, `--retention-window=14…30`; ежемесячная `FULL` закрепляется (`--ttl`) | то же плюс слияние цепочек (`merge`) |
| Проверка | еженедельное восстановление дампа во временную базу | `validate` еженедельно, тестовое восстановление ежемесячно | автоматическое восстановление на выделенный стенд |

Общие правила:

- Перед обновлением конфигурации, платформы, СУБД, перед групповыми обработками и «Тестированием и исправлением» — внеплановая копия и именованная точка восстановления (`pg_create_restore_point`).
- Снимок (checkpoint, snapshot) виртуальной машины в гипервизоре — удобная страховка на время работ, но не резервная копия: он лежит на том же хранилище, что и ВМ, и не проверяется [практика].
- Реплика — не резервная копия: ошибочное удаление данных мгновенно повторяется на ней.
- Логическая копия нужна и при наличии физических: она независима от сборки и версии СУБД и при выгрузке вычитывает все строки таблиц, обнаруживая повреждения, которые физическая копия молча переносит.

### 10.2. Правило 3-2-1

Три экземпляра данных (рабочий и две копии), на двух разных типах носителей или независимых системах хранения, один экземпляр — вне площадки. Современное дополнение — «3-2-1-1-0»: ещё одна копия должна быть недоступна для изменения (отключённый носитель, неизменяемое хранилище с блокировкой объектов), и ноль ошибок по результатам проверки восстановлением.

Применительно к серверу 1С в виртуальной машине на Windows-хосте:

| Копия | Где | От чего защищает |
|---|---|---|
| 1 | отдельный виртуальный диск ВМ (`/backup`) | ошибка пользователя, сбой СУБД, быстрый откат |
| 2 | другой физический диск хоста, NAS или шара другого компьютера | потеря ВМ, диска ВМ, сбой гипервизора |
| 3 | вне площадки: объектное хранилище (S3), другой офис, вывозимый носитель | пожар, кража, шифровальщик, потеря всего хоста |

Диск `/backup` внутри ВМ, лежащий на том же физическом диске, что и системный, — это одна точка отказа, а не вторая копия. Надёжнее схема, в которой хранилище копий само забирает данные с сервера (pull), а у сервера баз нет прав на удаление копий в хранилище: тогда взлом сервера не уничтожит архив [практика].

### 10.3. Вынос копий

**rsync по SSH на NAS или другой Linux-сервер:**

```bash
rsync -a --partial --exclude='*.partial' -e 'ssh -i /root/.ssh/backup_ed25519' \
      /backup/dump/ backup@nas.example.local:/volume1/pgbackup/dump/
```

Ключ `--delete` зеркалирует и удаления — применяйте его осознанно: ошибочно очищенный источник очистит и копию.

**Windows-шара (CIFS/SMB):**

```bash
sudo apt install cifs-utils
sudo install -d -m 700 /mnt/winbackup
sudo tee /root/.smb-backup >/dev/null <<'EOF'
username=backupuser
password=ПАРОЛЬ
domain=WORKGROUP
EOF
sudo chmod 600 /root/.smb-backup
```

```text
# /etc/fstab
//192.168.1.10/pgbackup  /mnt/winbackup  cifs  credentials=/root/.smb-backup,uid=postgres,gid=postgres,file_mode=0600,dir_mode=0700,vers=3.1.1,nofail,_netdev,x-systemd.automount  0  0
```

```bash
sudo systemctl daemon-reload && sudo mount /mnt/winbackup
mountpoint -q /mnt/winbackup || { echo "шара не смонтирована"; exit 1; }     # обязательно в скриптах
rsync -rt --partial --exclude='*.partial' /backup/dump/ /mnt/winbackup/dump/
```

На CIFS не сохраняются владельцы и права Unix, поэтому вместо `rsync -a` используют `-rt`. Писать на шару напрямую архив WAL или каталог pg_probackup не стоит: при обрыве сети архивация остановится и WAL заполнит диск. Копируйте на локальный том, а на шару — вторым шагом [практика].

**NAS по NFS:** `sudo apt install nfs-common`, строка в `/etc/fstab`: `192.168.1.5:/volume1/pgbackup  /mnt/nas  nfs4  rw,hard,nofail,_netdev  0  0`.

**Объектное хранилище S3 через rclone:**

```bash
sudo apt install rclone
rclone config                       # интерактивно создать удалённое хранилище, например s3backup
```

```ini
# /root/.config/rclone/rclone.conf (права 0600)
[s3backup]
type = s3
provider = Other
endpoint = https://s3.example.com
access_key_id = КЛЮЧ
secret_access_key = СЕКРЕТ
```

```bash
# copy не удаляет файлы в хранилище (в отличие от sync)
rclone copy /backup/dump s3backup:pg-1c/dump --transfers 4 --checkers 8 \
       --log-file /var/log/pgbackup/rclone.log --log-level INFO
rclone check /backup/dump/2026-10-10_0130 s3backup:pg-1c/dump/2026-10-10_0130 --one-way
rclone lsl s3backup:pg-1c/dump | tail
```

Сроки хранения в S3 задают правилами жизненного цикла бакета, а защиту от удаления — версионированием и блокировкой объектов (Object Lock) на стороне хранилища. Ключу, который лежит на сервере баз, достаточно права на запись.

**Каталог pg_probackup** выносят целиком (`rsync -a /backup/pgpro/ …`) в момент, когда нет выполняющихся копий, либо держат основной каталог на отдельном сервере копий и работают в удалённом режиме (раздел 5.12).

Сводный скрипт выноса (упоминается в расписании из раздела 7.5):

```bash
#!/usr/bin/env bash
# /usr/local/bin/backup-offsite.sh — вынос копий на Windows-шару и в S3 (от root)
set -Euo pipefail
N=/usr/local/bin/backup-notify.sh
MNT=/mnt/winbackup
LOG=/var/log/pgbackup/offsite-$(date +%F).log
rc=0

# 1) Windows-шара: писать только если она действительно смонтирована
if mountpoint -q "$MNT" || mount "$MNT"; then
    for d in dump base 1c-files; do
        [ -d "/backup/$d" ] || continue
        rsync -rt --partial --exclude='*.partial' --exclude='*.FAILED' "/backup/$d/" "$MNT/$d/" >>"$LOG" 2>&1 || rc=1
    done
else
    echo "шара $MNT не смонтирована" >>"$LOG"; rc=1
fi

# 2) S3 через rclone (если настроено удалённое хранилище s3backup)
if command -v rclone >/dev/null 2>&1 && rclone listremotes | grep -q '^s3backup:$'; then
    rclone copy /backup/dump     s3backup:pg-1c/dump     --transfers 4 --log-file "$LOG" --log-level INFO || rc=1
    rclone copy /backup/1c-files s3backup:pg-1c/1c-files --transfers 4 --log-file "$LOG" --log-level INFO || rc=1
fi

(( rc == 0 )) || "$N" "вынос копий: есть ошибки" "$LOG"
exit "$rc"
```

Скрипт не удаляет файлы в местах назначения: старые копии там чистят отдельно (правила жизненного цикла в S3, задание на стороне хранилища), чтобы компрометация сервера баз не позволяла стереть архив.

### 10.4. Шифрование

Копии содержат все данные баз, хеши паролей и лицензии. Всё, что покидает сервер, шифруйте.

```bash
# симметрично, паролем из файла (GnuPG)
gpg --batch --yes --pinentry-mode loopback --passphrase-file /root/.backup-pass \
    --symmetric --cipher-algo AES256 -o zup.dump.gpg zup.dump
gpg --batch --pinentry-mode loopback --passphrase-file /root/.backup-pass -d -o zup.dump zup.dump.gpg

# асимметрично: на сервере только открытый ключ, расшифровать можно лишь там, где хранится закрытый
gpg --batch --yes --encrypt --recipient backup@example.com -o zup.dump.gpg zup.dump

# «на лету»
sudo -u postgres pg_dump -Fc zup | gpg --batch --encrypt --recipient backup@example.com -o /backup/dump/zup.dump.gpg
```

Другие варианты: шифрованное удалённое хранилище rclone (тип `crypt` поверх S3 или шары); встроенное шифрование репозитория pgBackRest (`repo1-cipher-type=aes-256-cbc`); шифрование WAL-G; LUKS на диске с копиями. В открытом pg_probackup 2.5 встроенного шифрования нет (в README проекта, ветка master, шифрование среди возможностей не упоминается; сверено 11.10.2026) — шифруют на уровне хранилища.

Ключ или пароль шифрования храните отдельно от копий и в нескольких местах (менеджер паролей, запечатанный конверт в сейфе). Потерянный ключ означает потерянные копии. Расшифровку включайте в тестовое восстановление.

### 10.5. Сроки хранения

- Типовая схема «дед — отец — сын»: ежедневные копии 7–14 дней, еженедельные 4–8 недель, ежемесячные 12 месяцев, годовые — по требованиям организации и законодательства о хранении учётных данных [практика].
- Архив WAL хранят не меньше, чем самую старую базовую копию, с которой возможен PITR; обычно окно PITR — 7–30 дней.
- Долгосрочные (ежемесячные, годовые) копии разумно делать логическими (`pg_dump -Fc`): через несколько лет их можно восстановить в новую версию СУБД, тогда как физическая копия требует той же старшей версии и сборки.
- Вместе с долгосрочной копией сохраняйте сведения о версии платформы 1С и релизе конфигурации (и, по возможности, дистрибутивы): базу мало восстановить, её нужно ещё открыть.
- Объём хранилища считайте заранее: для pg_probackup — полная копия × избыточность + ежедневные инкременты + WAL за окно; следите за заполнением тома (раздел 7.7).

## 11. Восстановление после аварий

### 11.1. Общий порядок действий

1. **Остановиться и не ухудшать.** Если данные портятся или удалены — остановить сервер 1С (пользователи перестанут вносить изменения, которые потом придётся терять). Не запускать «исправляющие» операции наугад.
2. **Зафиксировать время** события (для PITR — как можно точнее: журнал регистрации 1С, журнал сервера PostgreSQL) и собрать журналы: `/var/log/postgresql/`, `journalctl -u postgresql@17-main`, `dmesg -T`, технологический журнал 1С.
3. **Сохранить текущее состояние** до любых попыток ремонта: копию каталога данных остановленного кластера (`cp -a` или `tar`), снимок ВМ, дамп того, что ещё читается. Это страховка от неудачного восстановления.
4. **Выбрать способ** (таблица ниже) и по возможности восстанавливать сначала «в сторону» — в отдельный каталог/кластер, проверять и только потом переключать.
5. **Проверить** результат: сервер запускается, базы открываются в 1С, контрольные документы и отчёты на месте.
6. **После восстановления**: новая полная копия; запись о происшествии и причинах; исправление схемы копирования, если она подвела.

| Что случилось | Чем восстанавливать | Потеря данных |
|---|---|---|
| Потерян сервер или диск целиком | последняя физическая копия (+ архив WAL) либо дампы — на новый сервер | до последней копии; с архивом WAL — до последнего сохранённого сегмента |
| Ошибочно удалены или испорчены данные в одной базе | PITR в отдельный каталог на момент до ошибки → перенос базы или объектов | нет (при исправном архиве WAL) |
| Неудачное обновление конфигурации | копия, снятая перед обновлением, либо PITR к именованной точке | работа после начала обновления |
| Повреждён блок данных, сбой индекса | `REINDEX` (если индекс); `pg_probackup restore -I checksum`; физическая копия + WAL | обычно нет |
| Закончилось место, сервер остановился | освободить или добавить место, запустить | нет |

### 11.2. Сервер потерян целиком

```bash
# 1. Новая ВМ/сервер: желательно тот же выпуск Ubuntu, то же имя хоста и IP-адрес (их помнят клиенты, публикации и реестр кластера 1С)
# 2. Установить ту же сборку PostgreSQL для 1С той же старшей версии (минорная — не ниже, чем была)
# 3. Вернуть конфигурацию из архива служебных файлов
sudo install -d -m 700 /tmp/restore
sudo tar -xzf /mnt/offsite/1c-files/1c-conf-2026-10-10.tar.gz -C /tmp/restore
sudo systemctl stop postgresql@17-main
sudo cp -a /tmp/restore/etc/postgresql/17/main/. /etc/postgresql/17/main/

# 4а. Физическая копия pg_probackup (каталог копий доступен в /backup/pgpro)
sudo apt install pg-probackup-17
sudo -u postgres sh -c 'rm -rf /var/lib/postgresql/17/main && install -d -m 700 /var/lib/postgresql/17/main'
sudo -u postgres pg_probackup-17 restore -B /backup/pgpro --instance=main -j 4 --progress
sudo systemctl start postgresql@17-main

# 4б. Либо логические копии
sudo systemctl start postgresql@17-main
sudo -u postgres psql -X -f /backup/dump/2026-10-10_0130/globals.sql postgres
for db in zup buh; do
    sudo -u postgres createdb -T template0 "$db"
    sudo -u postgres pg_restore -d "$db" -j 4 -e "/backup/dump/2026-10-10_0130/$db.dump"
    sudo -u postgres vacuumdb -d "$db" --analyze-only -j 4
done

# 5. Установить платформу 1С той же версии, что была
# 6. При остановленной службе 1С вернуть реестр кластера и журналы регистрации
sudo systemctl stop srv1cv8-8.3.27.1688@default
sudo cp -a /tmp/restore/home/usr1cv8/.1cv8/1C/1cv8/. /home/usr1cv8/.1cv8/1C/1cv8/
sudo rsync -a /mnt/offsite/1c-files/eventlog/reg_1541/ /home/usr1cv8/.1cv8/1C/1cv8/reg_1541/
sudo chown -R usr1cv8:grp1cv8 /home/usr1cv8/.1cv8
sudo systemctl start srv1cv8-8.3.27.1688@default

# 7. Лицензии, публикации, расписания копирования
```

Что учесть:

- Если имя нового сервера отличается от прежнего, восстановленный реестр кластера может не заработать. Тогда его не восстанавливают: дают серверу 1С создать кластер заново и регистрируют базы командой `rac infobase create` без `--create-database` (раздел 2.4). Журналы регистрации при этом придётся переложить в каталоги новых UUID баз.
- Программные лицензии привязаны к параметрам компьютера: на новой ВМ файл `.lic` из копии, скорее всего, не подойдёт — потребуется активация резервным пин-кодом.
- Если версия ОС на новом сервере другая, после **физического** восстановления перестройте индексы (`REINDEX DATABASE`) — см. раздел 2.7, п. 4. Логического восстановления это не касается.
- Каталог копий pg_probackup на новом сервере достаточно сделать доступным по прежнему пути; `init` и `add-instance` повторять не нужно — конфигурация экземпляра лежит в самом каталоге.
- После запуска — новая полная копия и проверка расписаний.

### 11.3. Удалили данные: восстановление одной базы на момент времени

Условие: есть физическая копия, снятая до события, и непрерывный архив WAL от неё до нужного момента. Рабочий кластер при этом не трогаем — всё делаем рядом.

```bash
# 1. Определить момент T (по журналу регистрации 1С) и взять на 1–2 минуты раньше.
#    Проверить, что восстановление на T возможно:
sudo -u postgres pg_probackup-17 validate -B /backup/pgpro --instance=main --recovery-target-time='2026-10-10 14:25:00+05'

# 2. Восстановить только нужную базу в отдельный каталог
D=/var/lib/postgresql/17/pitr
sudo -u postgres pg_probackup-17 restore -B /backup/pgpro --instance=main -D $D -j 4 --db-include=zup \
     --recovery-target-time='2026-10-10 14:25:00+05' --recovery-target-action=promote

# 3. В Debian-раскладке в каталоге данных нет файлов конфигурации — создать минимальные
sudo -u postgres sh -c "[ -f $D/postgresql.conf ] || touch $D/postgresql.conf;
                        [ -f $D/pg_ident.conf ]  || touch $D/pg_ident.conf;
                        [ -f $D/pg_hba.conf ]    || echo 'local all all peer' > $D/pg_hba.conf"

# 4. Запустить на другом порту; параметры командной строки перекрывают настройки из файлов
sudo -u postgres /usr/lib/postgresql/17/bin/pg_ctl -D $D -w -t 7200 -l $D/pitr.log \
     -o "-p 5433 -c listen_addresses='' -c archive_mode=off -c hot_standby=off -c shared_buffers=1GB" start
sudo -u postgres psql -p 5433 -Atc "SELECT pg_is_in_recovery();"        # должно быть f

# 5. Забрать базу дампом и развернуть рядом с рабочей под другим именем
sudo -u postgres pg_dump -p 5433 -Fc -f /backup/dump/zup_pitr_1425.dump zup
sudo -u postgres createdb -T template0 zup_pitr
sudo -u postgres pg_restore -d zup_pitr -j 4 -e /backup/dump/zup_pitr_1425.dump
sudo -u postgres vacuumdb -d zup_pitr --analyze-only -j 4

# 6. Остановить и удалить временный кластер
sudo -u postgres /usr/lib/postgresql/17/bin/pg_ctl -D $D -m fast stop
sudo rm -rf $D
```

Дальше два пути:

- **Вернуть отдельные объекты.** Зарегистрировать `zup_pitr` в кластере 1С как отдельную базу с заблокированными регламентными заданиями (раздел 2.4) и перенести удалённые документы и элементы справочников средствами 1С (выгрузка и загрузка данных, обмен). Работа, сделанная пользователями после момента T, сохраняется.
- **Заменить рабочую базу целиком** по порядку из раздела 9.3, взяв в качестве источника `zup_pitr_1425.dump`. Всё, что сделано после T, теряется.

Те же шаги без pg_probackup: распаковать копию `pg_basebackup` в `$D`, дописать в `$D/postgresql.conf` строки `restore_command`, `recovery_target_time`, `recovery_target_action = 'promote'`, создать `$D/recovery.signal` и запустить через `pg_ctl` на порту 5433 (в этом случае восстановится весь кластер, а не одна база).

Если архива WAL нет, доступна только точка последней копии до события: разверните её отдельной базой и переносите объекты средствами 1С.

### 11.4. Повреждён блок данных

Признаки в журнале PostgreSQL и в ошибках 1С: `invalid page in block N of relation base/16384/24601`, `could not read block N in file …: Input/output error`, `page verification failed, calculated checksum … but expected …`, `missing chunk number 0 for toast value …`, `unexpected chunk number`.

```bash
# 1. Проверить оборудование: ошибки диска почти всегда повторяются
sudo dmesg -T | grep -iE 'i/o error|medium error|ata|nvme|ext4|xfs' | tail -30
sudo smartctl -a /dev/sda            # пакет smartmontools; в ВМ — смотреть на хосте

# 2. Остановить 1С и PostgreSQL и сделать файловую копию каталога данных КАК ЕСТЬ
sudo systemctl stop srv1cv8-8.3.27.1688@default postgresql@17-main
sudo -u postgres cp -a /var/lib/postgresql/17/main /backup/main.damaged.$(date +%F)
sudo systemctl start postgresql@17-main

# 3. Понять, что повреждено. В пути base/16384/24601: 16384 — OID базы, 24601 — номер файла (relfilenode)
sudo -u postgres psql -Atc "SELECT datname FROM pg_database WHERE oid = 16384;"
sudo -u postgres psql -d zup -c "SELECT pg_filenode_relation(0, 24601);"
sudo -u postgres psql -d zup -c "SELECT relname, relkind FROM pg_class WHERE relfilenode = 24601;"
```

Дальше по ситуации:

- **Повреждён индекс** (`relkind = i`): `REINDEX INDEX public.имя;` или `REINDEX TABLE public.таблица;` — данные не теряются.
- **Повреждена таблица**, есть pg_probackup: остановить сервер и выполнить инкрементальное восстановление поверх каталога данных — заменяются только повреждённые и изменившиеся страницы, затем проигрывается WAL:
  ```bash
  sudo systemctl stop postgresql@17-main
  sudo -u postgres pg_probackup-17 restore -B /backup/pgpro --instance=main -D /var/lib/postgresql/17/main -I checksum -j 4
  sudo systemctl start postgresql@17-main
  ```
  Если копии сняты в режиме STREAM без архива WAL, кластер вернётся на момент последней копии.
- **Повреждена таблица**, есть базовая копия и архив WAL: обычное восстановление с проигрыванием архива до конца (раздел 4.5 без `recovery_target_*`) — потерь нет.
- **Копий нет** (крайний случай): попытаться выгрузить читаемое — `pg_dump` по таблицам, пропуская сбойную; параметр `zero_damaged_pages = on` позволяет прочитать таблицу ценой потери строк на повреждённых страницах. Только на копии каталога данных и только осознавая потери.
- После восстановления: `pg_amcheck` по всей базе, в 1С — «Тестирование и исправление» с проверкой логической и ссылочной целостности, новая полная копия. Включите контрольные суммы данных (раздел 8.4), если их не было.

### 11.5. Закончилось место на диске

Признаки: `No space left on device`, `PANIC: could not write to file "pg_wal/xlogtemp.NNN"`, сервер PostgreSQL остановлен и не запускается; в 1С — ошибки СУБД при записи.

```bash
# 1. Что и где заполнено
df -h; df -i
sudo du -xsh /var/lib/postgresql/17/main/* | sort -h | tail
sudo du -sh /var/lib/postgresql/17/main/pg_wal /var/log/postgresql /backup 2>/dev/null
```

Правила:

- **Не удалять файлы из `pg_wal` вручную** и не запускать `pg_resetwal` — это почти гарантированная потеря данных.
- Сначала вернуть серверу возможность стартовать, затем устранить причину.

```bash
# 2. Быстро освободить место (любой из способов)
sudo journalctl --vacuum-size=200M
sudo apt clean
sudo find /var/log/postgresql -name '*.log.*' -mtime +7 -delete
sudo tune2fs -m 1 /dev/mapper/ubuntu--vg-ubuntu--lv      # ext4: уменьшить резерв для root с 5 % до 1 %
# старые копии на том же томе — только убедившись, что есть более свежие и проверенные

# 3. Или расширить том (LVM; в установке Ubuntu по умолчанию в группе томов часто остаётся свободное место)
sudo vgs; sudo lvs
sudo lvextend -r -l +100%FREE /dev/ubuntu-vg/ubuntu-lv
# если расширен виртуальный диск: sudo growpart /dev/sda 3 && sudo pvresize /dev/sda3, затем lvextend

# 4. Запустить PostgreSQL и найти причину роста WAL
sudo systemctl start postgresql@17-main
sudo -u postgres psql -x -c "SELECT * FROM pg_stat_archiver;"
sudo -u postgres psql -c "SELECT slot_name, active, pg_size_pretty(pg_wal_lsn_diff(pg_current_wal_lsn(), restart_lsn)) AS retained FROM pg_replication_slots;"
```

- Архивация не работает → починить `archive_command` (место в архиве, права, монтирование); сервер сам отправит накопленное и удалит лишние сегменты после контрольной точки (`CHECKPOINT;`).
- Архив недоступен надолго, а сервер нужен сейчас → временно `archive_command = '/bin/true'` и `SELECT pg_reload_conf();`. Цепочка WAL для PITR при этом **рвётся**: после восстановления архивации сразу снять новую полную копию.
- WAL удерживает неактивный слот → `SELECT pg_drop_replication_slot('имя');`.
- Место заняли не WAL, а данные (временные файлы запросов в `base/pgsql_tmp`, раздувшиеся таблицы) → это задача обслуживания (`VACUUM`, поиск тяжёлых запросов), а не резервного копирования.
- Заполнился том копий → копирование молча перестало работать. Именно для этого нужен контроль «свежести» (раздел 7.7) и политика хранения.

Профилактика: держать `pg_wal`, данные и копии на разных томах; мониторить заполнение (порог 80–85 %); задать `max_slot_wal_keep_size`; следить за `pg_stat_archiver`.

## Типичные ошибки и подводные камни

Тексты сообщений сверены 19.10.2026 с исходным кодом PostgreSQL 17 (`REL_17_STABLE`: `pg_backup_db.c`, `pg_backup_archiver.c`, `pg_backup_custom.c`, `pg_restore.c`, `xlog.c`, `xlogrecovery.c`, `proc.c`, `miscinit.c`, `dbcommands.c`, `aclchk.c`, `basebackup_incremental.c`, `psql/command.c`) и pg_probackup 2.5.16 (`restore.c`, `backup.c`) — совпадают. Между версиями они немного отличаются: в 17-й имена параметров взяты в кавычки (`exceeds "max_wal_senders" (currently N)`), к сообщению о контрольной точке добавлен адрес (`could not locate required checkpoint record at X/X`); ориентируйтесь на смысл.

| Симптом | Причина | Решение |
|---|---|---|
| `pg_dump: error: aborting because of server version mismatch` | `pg_dump` старше сервера | запускать утилиту версии сервера или новее: `/usr/lib/postgresql/17/bin/pg_dump` |
| `pg_restore: error: unsupported version (1.NN) in file header` | архив создан более новым `pg_dump` | восстанавливать `pg_restore` той же или более новой версии |
| `could not access file "$libdir/mchar"`, затем `type "public.mvarchar" does not exist` | дамп базы 1С восстанавливают в «ванильный» PostgreSQL | восстанавливать в сборку с доработками для 1С (раздел 2.7) |
| `input file appears to be a text format dump. Please use psql` | текстовый дамп передан `pg_restore` | `psql -X --set ON_ERROR_STOP=on -f файл база` |
| `parallel restore from standard input is not supported` | `pg_restore -j` получил данные из конвейера | сохранить архив в файл; расшифровывать и распаковывать заранее |
| `permission denied for language c` при восстановлении | восстановление не суперпользователем | выполнять от `postgres` |
| `role "…" does not exist` при восстановлении | на сервере нет ролей из исходного кластера | сначала загрузить `globals.sql` либо использовать `--no-owner --no-privileges` |
| `database "zup" is being accessed by other users` при удалении или переименовании базы | рабочие процессы 1С держат пул соединений | заблокировать сеансы, `pg_terminate_backend`, `DROP DATABASE … WITH (FORCE)` или остановить сервер 1С |
| После восстановления 1С работает очень медленно | нет статистики планировщика | `vacuumdb -d база --analyze-only -j 4` |
| Дамп подозрительно маленький или пустой | выгружена не та база (без имени `pg_dump` берёт базу по имени пользователя) либо ошибка была проигнорирована | всегда указывать имя базы, проверять код возврата и `pg_restore -l` |
| Обновление конфигурации 1С «висит» ночью | реструктуризация ждёт блокировки, удерживаемые `pg_dump` | развести расписания; для дампа задать `--lock-wait-timeout` |
| `pg_dump: … invalid memory alloc request size` / `out of memory` на одной таблице | в строке очень большое двоичное значение | физическая копия; найти и вынести «тяжёлый» объект из базы |
| `invalid command \restrict` при загрузке текстового дампа | `psql` старее минорной версии, создавшей дамп | обновить клиентские утилиты |
| `pg_basebackup: … no pg_hba.conf entry for replication connection` | нет строки `replication` в `pg_hba.conf` | добавить строку, `systemctl reload` |
| `number of requested standby connections exceeds max_wal_senders` | заняты все `max_wal_senders` | увеличить параметр (перезапуск) или освободить подключения |
| `WAL level not sufficient for making an online backup` | `wal_level = minimal` | `wal_level = replica`, перезапуск |
| `requested WAL segment … has already been removed` во время копии | режим `-X fetch`, сегменты удалены до конца копирования | использовать `-X stream` |
| Восстановленный сервер не запускается: `could not locate required checkpoint record` | не распакован `pg_wal.tar` или удалён `backup_label` | распаковать WAL в `pg_wal`; `backup_label` не удалять |
| `data directory "…" has invalid permissions` или `… has wrong ownership` | каталог распакован от root либо права шире `0700`/`0750` | `chown -R postgres:postgres`, `chmod 700` |
| PITR «проскочил»: сервер сразу открылся в состоянии копии | не создан `recovery.signal` | создать файл и повторить с шага распаковки |
| `recovery ended before configured recovery target was reached` | цель позже последнего доступного WAL | уточнить цель или добавить недостающие сегменты |
| После PITR: `cannot execute … in a read-only transaction` | сервер стоит на паузе в конце восстановления | `SELECT pg_wal_replay_resume();` либо `recovery_target_action = 'promote'` |
| Тестовый кластер начал писать в рабочий архив WAL | в копии приехали `archive_mode`/`archive_command` | на тестовом кластере всегда `archive_mode = off`, обнулять `postgresql.auto.conf` (раздел 8.3) |
| Инкрементальный `pg_basebackup`: ошибка об отсутствии сводок WAL (`WAL summaries are required …`) | `summarize_wal` выключен или сводки старше `wal_summary_keep_time` | включить `summarize_wal`, снять новую полную копию |
| pg_probackup: инкрементальная копия падает с требованием полной | нет действительной `FULL` на текущей линии времени (первая копия, после PITR, родитель `CORRUPT`) | снять `FULL` |
| pg_probackup: `Restore destination is not empty` | каталог данных не пуст | очистить каталог либо использовать `-I checksum` |
| pg_probackup без `--stream` долго ждёт и падает с `could not be archived in 300 seconds` | режим ARCHIVE, а архивация не настроена или сломана | добавить `--stream` либо починить `archive_command` |
| pg_probackup: копии в статусе `ORPHAN` | повреждён или удалён вручную родитель цепочки | `validate`; при невозможности восстановить родителя — удалить цепочку и снять `FULL` |
| pg_probackup: копия «зависла» в `RUNNING` | процесс был убит (перезагрузка, OOM) | `delete -i ID` и повторить копию |
| Копии «делаются», но на сетевой шаре их нет, а корневой диск заполнен | шара не была смонтирована, скрипт писал в пустую точку монтирования | проверка `mountpoint -q` в начале скрипта |
| Копирование перестало работать, никто не заметил | заполнился том копий, сломался cron, истёк пароль | контроль «свежести» копий отдельным заданием (раздел 7.7) |
| Задание из `/etc/cron.d` не запускается | нет поля пользователя, права файла не `0644`, имя с точкой, нет перевода строки в конце | исправить файл, смотреть `journalctl -u cron` |
| После физического восстановления на другой версии ОС — странная сортировка, дубли, «не находит» записи по индексу | сменились правила сортировки (glibc/ICU) | `REINDEX DATABASE` для каждой базы; впредь переносить дампом |
| Тестовая копия базы рассылает почту и выполняет обмены | регламентные задания не заблокированы | регистрировать копию с `--scheduled-jobs-deny=on` |
| Восстановили одну базу из физической копии — «откатились» все остальные | физическая копия и PITR действуют на весь кластер | восстанавливать в отдельный каталог и переносить базу дампом (раздел 11.3) |
| Файл лицензии из копии не принимается на новом сервере | программная лицензия привязана к параметрам компьютера | повторная активация резервным пин-кодом |
| `.dt` не загружается | в исходной базе были ошибки, либо несовместимы версия платформы и режим совместимости | `.dt` не является резервной копией; восстанавливать из копии СУБД |

## Быстрая шпаргалка

| Задача | Команда |
|---|---|
| Дамп одной базы (один файл) | `sudo -u postgres pg_dump -Fc -f /backup/dump/zup_$(date +%F).dump zup` |
| Дамп большой базы в 4 потока | `sudo -u postgres pg_dump -Fd -j 4 -f /backup/dump/zup.dir zup` |
| Дамп со сжатием zstd (16+) | `pg_dump -Fc -Z zstd:3 -f zup.dump zup` |
| Роли и табличные пространства | `sudo -u postgres pg_dumpall --globals-only -f globals.sql` |
| Оглавление архива | `pg_restore -l zup.dump` |
| Восстановить в новую базу | `createdb -T template0 zup_copy && pg_restore -d zup_copy -j 4 -e zup.dump` |
| Восстановить с пересозданием базы | `pg_restore --clean --if-exists -C -d postgres -j 4 zup.dump` |
| Выборочное восстановление | `pg_restore -l d.dump > toc; pg_restore -L toc -d база d.dump` |
| Восстановить текстовый дамп | `psql -X --set ON_ERROR_STOP=on -f zup.sql zup_copy` |
| Статистика после восстановления | `vacuumdb -d zup_copy --analyze-only -j 4` |
| Зарегистрировать базу в кластере 1С | `rac infobase --cluster=$CL create --name=zup_copy --dbms=PostgreSQL --db-server=localhost --db-name=zup_copy --locale=ru --db-user=postgres --db-pwd='***' --license-distribution=allow --scheduled-jobs-deny=on` |
| Заблокировать сеансы и задания базы 1С | `rac infobase --cluster=$CL update --infobase=$IB --infobase-user=… --infobase-pwd=… --sessions-deny=on --scheduled-jobs-deny=on --permission-code=…` |
| Оборвать подключения к базе | `SELECT pg_terminate_backend(pid) FROM pg_stat_activity WHERE datname='zup' AND pid<>pg_backend_pid();` |
| Физическая копия кластера | `sudo -u postgres pg_basebackup -D /backup/base/$(date +%F) -Ft -z -X stream -c fast -P` |
| Проверить физическую копию | `pg_verifybackup каталог` (tar: `-F t -n`, версия 18+) |
| Инкрементальная копия (17+) | `pg_basebackup -D incr --incremental=full/backup_manifest -c fast` |
| Собрать цепочку инкрементов | `pg_combinebackup full incr1 incr2 -o /var/lib/postgresql/17/main` |
| Включить архив WAL | `archive_mode = on`, `archive_command = '…'`, перезапуск |
| Состояние архивации | `SELECT * FROM pg_stat_archiver;` |
| Переключить сегмент WAL | `SELECT pg_switch_wal();` |
| Именованная точка восстановления | `SELECT pg_create_restore_point('имя');` |
| PITR: параметры | `restore_command`, `recovery_target_time='…+05'`, файл `recovery.signal` |
| Завершить паузу после PITR | `SELECT pg_wal_replay_resume();` |
| Перевести сервер в рабочий режим | `sudo pg_ctlcluster 17 main promote` или `SELECT pg_promote();` |
| Слоты репликации и удерживаемый WAL | `SELECT slot_name, active, restart_lsn FROM pg_replication_slots;` |
| Удалить слот | `SELECT pg_drop_replication_slot('имя');` |
| Очистить свой архив WAL | `pg_archivecleanup -x .zst /backup/wal <самый_старый_нужный_сегмент>` |
| pg_probackup: создать каталог и экземпляр | `pg_probackup-17 init -B /backup/pgpro; pg_probackup-17 add-instance -B /backup/pgpro -D $PGDATA --instance=main` |
| pg_probackup: полная / инкрементальная | `pg_probackup-17 backup -B /backup/pgpro --instance=main -b FULL --stream --temp-slot -j 4 --compress` (инкрементальная — `-b DELTA`) |
| pg_probackup: список копий | `pg_probackup-17 show -B /backup/pgpro [--instance=main] [--archive]` |
| pg_probackup: проверить | `pg_probackup-17 validate -B /backup/pgpro --instance=main -j 4` |
| pg_probackup: восстановить последнюю | `pg_probackup-17 restore -B /backup/pgpro --instance=main -j 4` |
| pg_probackup: на момент времени | `… restore … --recovery-target-time='2026-10-10 14:25:00+05' --recovery-target-action=promote` |
| pg_probackup: в другой каталог, одну базу | `… restore … -D /путь --db-include=zup` |
| pg_probackup: починить каталог данных | `… restore … -D $PGDATA -I checksum` |
| pg_probackup: политика хранения | `… set-config … --retention-redundancy=2 --retention-window=14` |
| pg_probackup: удалить устаревшее | `… delete … --delete-expired --delete-wal [--merge-expired] [--dry-run]` |
| pg_probackup: закрепить копию | `… set-backup … -i ID --ttl=90d` |
| pg_probackup: архив WAL | `archive_command = '/usr/bin/pg_probackup-17 archive-push -B /backup/pgpro --instance=main --wal-file-name=%f --compress'` |
| Проверка контрольных сумм (кластер остановлен) | `pg_checksums --check -D каталог -P` |
| Логическая проверка индексов и таблиц | `pg_amcheck --all --install-missing -j 4 -P` |
| Тестовый кластер на порту 5433 | `sudo pg_createcluster 17 verify -p 5433` … `sudo pg_dropcluster 17 verify --stop` |
| Размеры баз | `SELECT datname, pg_size_pretty(pg_database_size(datname)) FROM pg_database;` |
| Объём `pg_wal` | `SELECT pg_size_pretty(sum(size)) FROM pg_ls_waldir();` |
| Вынести копии в S3 | `rclone copy /backup/dump s3backup:pg-1c/dump --transfers 4` |
| Зашифровать копию | `gpg --batch --encrypt --recipient backup@example.com -o f.gpg f` |
| Таймеры копирования | `systemctl list-timers 'pg-*'`; журнал: `journalctl -u pg-probackup.service` |
