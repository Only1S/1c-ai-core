# /cf-vendor-update — доработанная конфигурация на новый релиз

Подход: старый релиз поставщика — общий предок; ветка `custom` (ваша конфигурация) и ветка нового релиза — две стороны слияния. Идея подхода — `alonehobo/1c-cf-vendor-merge` (без лицензии: код не взят, всё написано заново); грабли — [vendor-release-update](../../docs/platform/vendor-release-update.md), правила шума — [references/noise.md](references/noise.md).

**Рабочую базу скилл не трогает.** Выгрузки и импорт идут через одноразовые файловые базы в каталогах прогона; загрузка результата в рабочую базу — только по прямой команде владельца, по справочнику.

## Что нужно

1. **Полные** файлы старого и нового релиза (`.cf` или `.dt`). Файл обновления `.cfu` не подходит. Старый релиз — ровно тот, на котором стоит ваша конфигурация (версия поставщика в её `Configuration.xml`).
2. XML-выгрузка текущей конфигурации (скилл `db-dump-xml`) — той же платформой, что и релизы.
3. Рабочий каталог вне облачной синхронизации: по 32 тыс. файлов на выгрузку, на ERP — 5–10 ГБ всего.

Порядок шагов и коды: каждый скрипт возвращает `2` на неверные аргументы или невыполненное предусловие и не идёт дальше.

## Шаг 1. Выгрузить релизы

```bash
python "${CLAUDE_SKILL_DIR}/scripts/dump-release.py" --src <старый.cf> --out <work>/xml-<старая версия>
python "${CLAUDE_SKILL_DIR}/scripts/dump-release.py" --src <новый.cf> --out <work>/xml-<новая версия>
```
`ibcmd` ищется по `--ibcmd`, `ONEC_PLATFORM_BIN` или `v8path` из `.v8-project.json`. Скрипт печатает имя, поставщика, версию и формат выгрузки — сверьте версию старого релиза с вашей конфигурацией. На ERP (600 МБ `.cf`) — около 2,5 минуты на релиз.

## Шаг 2. Ветки

```bash
python "${CLAUDE_SKILL_DIR}/scripts/make-branches.py" --repo <work>/repo --old-xml <work>/xml-<старая> --new-xml <work>/xml-<новая> --custom-xml <выгрузка текущей>
```
Ветки `vendor-<старая>`, `vendor-<новая>`, `custom`; у двух последних родитель — старый релиз. Каталоги-источники не меняются (коммит без checkout). `ConfigDumpInfo.xml` в ветки не идёт. Отказ (код 2), если версия вашей конфигурации не равна старому релизу или форматы выгрузки разные — `--force` только с объяснением владельцу.

## Шаг 3. Слияние и отчёт

```bash
python "${CLAUDE_SKILL_DIR}/scripts/merge-release.py" --repo <work>/repo
```
`git merge --no-commit -X no-renames` в `custom`; слияние остаётся незавершённым. Отчёт `<work>/repo-report/merge-report.md` (сводка) и `merge-report.json` (каждый путь):

| Класс | Что значит | Что решать |
|---|---|---|
| оба изменили | файл менялся и у нас, и у поставщика | XML описаний и прав — шаг 4; модуль — основа поставщика, доработку перенести по смыслу ([config-git-forks-and-merges](../../docs/platform/config-git-forks-and-merges.md), развилка по виду артефакта) |
| поставщик удалил | у поставщика файла нет, у нас изменён | `noise: true` — шаг 4 примет удаление; иначе — решение владельца, по умолчанию принять удаление и перенести доработку вручную на преемника, если он есть |
| у нас удалено | мы удалили, поставщик изменил | решение владельца; по умолчанию взять файл поставщика: на него могут ссылаться другие модули релиза |
| двойник | объект с одним именем добавлен с обеих сторон, uuid разные | данные заказчика под угрозой: по умолчанию наш объект переименовать в `Удалить…` с сохранением uuid, взять объект поставщика — решение владельца |
| добавлено с обеих сторон | то же, uuid совпадает или файл не верхнего уровня | отличие только шум — шаг 4 возьмёт версию поставщика; иначе сравнить по существу |
| сирота | наш файл внутри объекта, который поставщик удалил целиком | обычно удалить вместе с объектом — сообщить владельцу; `noise: true` — пустой модуль |
| слито автоматически | файл менялся с обеих сторон, git склеил без конфликта | XML описаний и прав шаг 4 перепроверит структурно; модуль — просмотреть: смысл мог разойтись |

Решения владельцу — окном вариантов с рекомендацией, по одному классу за раз. Отчёт показать сводкой: число по классам и видам артефактов, первые пункты «двойник», «сирота» и «слито автоматически».

Пилот 19.10.2026 (ERPWEENG 2.5.15.49 → 2.5.20.85, синтетическая доработка из 11 правок с заранее известным классом): ветки — 217 с, слияние и отчёт — 85 с; разница релизов настоящая (изменено 5856 модулей и 8944 объекта, удалено 244 объекта), а в отчёт попали только наши правки.

## Шаг 4. Автоматическое разрешение: структурное слияние XML и шум

```bash
python "${CLAUDE_SKILL_DIR}/scripts/resolve-merge.py" --repo <work>/repo [--dry-run]
```
Решает сам и кладёт в индекс (`git add` / `git rm`), каждое действие — в `resolve-report.md` и `.json`:

- **оба изменили, XML с корнем `MetaDataObject` или `Rights`** (описания объектов, `Configuration.xml`, права ролей) — слияние по элементам (`xml_merge.py`): основа — текст поставщика байт в байт, наши правки — поддеревьями; ключ элемента — `uuid`/`name`, единственный тег у родителя, текст листа (`<Catalog>Имя</Catalog>` в составе) или дочерний `<name>`/`<v8:lang>`. Обе стороны изменили одно место по-разному, или реквизит с одним именем и разными uuid — файл не трогается, места конфликта (`Catalog[Товары]/ChildObjects/Attribute[Вес]/Properties/Type`) в отчёте;
- **слито автоматически, такой же XML** — пересборка структурной; разошлась с построчной склейкой git — берётся структурная (git, например, склеивает без конфликта один и тот же объект, добавленный с обеих сторон в разных местах, — получается дубль). Файл, изменённый после слияния, шаг не трогает и называет в отчёте разделом «Изменено вручную», поэтому шаг 4 можно повторять;
- **шум выгрузки** ([references/noise.md](references/noise.md)): у нас только шум — версия поставщика или принятое удаление; у поставщика только шум — наша версия.

Формы, макеты, СКД, командный интерфейс, предопределённые поэлементно не сливаются (поэлементное слияние позиционных форматов ломает импорт) — остаются владельцу с подсказкой. `--dry-run` — только отчёт.

## Шаг 5. Остаток — вручную

Модули с правками с обеих сторон, формы, двойники, «у нас удалено», «поставщик удалил» с доработкой, структурные конфликты из шага 4. BSL переношу сам, модуль за модулем: основа — код поставщика, доработка переносится по смыслу, маркеры конфликтов не склеиваются. Если модулей много, предлагаю параллельных помощников с числом и объёмом — запуск только после «да» владельца на этот прогон ([subagents-on-explicit-consent](../../docs/process/subagents-on-explicit-consent.md)). Форма — целиком с одной стороны, доработка переносится скиллом `form-edit`, затем `form-validate`. Каждое решение — `git add`.

## Шаг 6. Проверки до импорта

```bash
python "${CLAUDE_SKILL_DIR}/scripts/check-merge.py" --repo <work>/repo [--all]
```
По рабочему каталогу слияния, ссылки и права — в нашей дельте (файлы, отличные от нового релиза; `--all` — во всех). Импорт и коммит берут индекс, поэтому каждая правка после отказа шага 6 — тоже `git add`. Код `3` — есть ошибки; отчёт `check-report.md` и `.json`:

| Проверка | Что ловит |
|---|---|
| неразрешённое | путь с конфликтом в индексе, маркер `<<<<<<<` / `=======` / `>>>>>>>` в файле |
| без git add | файл на диске отличается от индекса, стёрт без `git rm` или не добавлен в индекс |
| XML | файл не разбирается |
| состав | объект в `Configuration.xml` без файла, файл объекта не в составе, объект в составе дважды |
| сирота | файлы внутри объекта, описания которого нет (поставщик удалил объект, наш модуль или форма остались) — импорт на них остановится |
| ссылка на удалённый | XML (тип `cfg:CatalogRef.Имя` с любым префиксом пространства `current-config`, например `d5p1:` в схемах; `Catalog.Имя`; тексты запросов `query` и `QueryText`) и модули (`Справочники.Имя`, `Метаданные.Справочники.Имя`, `Справочник.Имя` в тексте запроса и в строке типа, `ОбщийМодуль.Метод`; регистр букв не важен, комментарий и пустая строка внутри запроса учтены) ссылаются на объект, который был в старом релизе или у нас, а после слияния его нет; подсказка — новое имя по тому же uuid |
| право роли | право на объект, реквизит, табличную часть, команду, измерение, ресурс, операцию, подсистему, таблицу и поле внешнего источника, которых нет; подсказка — новое имя по uuid |
| «Удалить…» | наша дельта ссылается на объект с префиксом `Удалить`/`Delete`, а у поставщика в этом файле такой ссылки нет — предупреждение; отдельно — список объектов, которые поставщик так пометил |
| форма | повтор `id`: элементы формы — одно пространство, у реквизитов, команд, колонок реквизита и каждого набора `AdditionalColumns` — свои |

Зонд на настоящем релизе (30.10.2026, все 29 996 файлов ERP 2.5.20.85 против дельты поставщика 2.5.15.49 → 2.5.20.85, 250 с): ложных находок в правах, составе, сиротах и ссылках нет, по 3682 формам — 0; одна настоящая — строка `"CommonTemplate.DocumentScanningAddIn"` в коде самого поставщика, а шаблон переименован в `DocumentScanningAddIn_3_0_1_1033`. Повторный зонд после расширения проверки (30.10.2026, все 32 879 файлов той же выгрузки, 75 с): та же одна находка; с изъятым живым справочником находятся ссылки и в схемах (8 вместо 0), и в формах (18 вместо 14). Чего проверка не видит: коллекции метаданных, кроме менеджеров (`Метаданные.Роли.Имя`), имена, собранные в коде из частей, условия RLS в правах ролей; права глубже таблицы внешнего источника проверяются, только если описание таблицы лежит отдельным файлом.

Пилот 30.10.2026 (те же выгрузки, что в шаге 3): шаг 4 сам принял одно удаление по шуму, 6 путей оставил владельцу (двойники, «у нас удалено», «поставщик удалил» с доработкой, модуль с правками с обеих сторон); шаг 6 — 22 ошибки: 15 неразрешённых мест, 4 ссылки модуля на удалённый поставщиком справочник, 3 сироты, 11 с; после решений владельца — 0 ошибок. Ожидаемые результаты — `expected-slices-2-5.json` в папке пилота.

## Шаг 7. Расширения

```bash
python "${CLAUDE_SKILL_DIR}/scripts/extensions-impact.py" --repo <work>/repo --ext <выгрузка расширения> [--ext …]
```
Скилл `cfe-update-impact` на паре «ветка `custom` → результат слияния»: старая версия — конфигурация с нашими доработками, под которую расширения написаны сейчас, а не голый старый релиз. Сверх него — заимствование без `ExtendedConfigurationObject`: после загрузки такая форма молча перестаёт применяться. Код `1` — есть ПРОБЛЕМА; отчёт `extensions-report.md`, по каждому расширению — полный вывод `cfe-update-impact`. Дальше — его раздел «Дальше по отчёту».

## Шаг 8. Импорт в одноразовую базу и /CheckModules

```bash
python "${CLAUDE_SKILL_DIR}/scripts/import-check.py" --repo <work>/repo --rev vendor-<новая> --ibcmd <bin платформы>   # базовая линия
python "${CLAUDE_SKILL_DIR}/scripts/import-check.py" --repo <work>/repo --ibcmd <bin платформы> --baseline <отчёт базовой линии>
```
Отдельными запусками, стоп на первом провале: выгрузка индекса (или `--rev`) в каталог прогона → `ibcmd infobase create` (пустая файловая база в каталоге прогона) → `ibcmd config import` → `1cv8 DESIGNER /CheckModules -ThinClient -Server` с `/Out` и `/DumpResult` (режимы — `--modes`; `--check-config` — ещё `/CheckConfig -ConfigLogIntegrity -IncorrectReferences`). Вердикт — по коду (0, 1, 101 — найдены ошибки), `/DumpResult` и журналу этого запуска: нет журнала — шаг не пройден. С `--baseline` строки журнала, которые были и у нового релиза, помечаются унаследованными. Без `--rev` нужен ноль неразрешённых путей и свежий `check-report.json` без ошибок; `--dry-run` печатает команды и ничего не запускает. Временная база удаляется (`--keep-db` — оставить), отчёт — `<repo>-import/<прогон>/import-report.md`.

Живой импорт 30.10.2026 (ERP 2.5.20.85, 32 878 файлов, файловая база, платформа 8.3.27): новый релиз — 348 с, результат слияния пилота с шестью развилками, решёнными владельцем, — 330 с (импорт 144 с, `/CheckModules` 163 с); оба прошли, журнал — «Синтаксических ошибок не обнаружено». Регресс на моках платформы — contour-tests §72.
