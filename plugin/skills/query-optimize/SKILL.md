# /query-optimize — Оптимизация запросов 1С

Разбор медленного запроса по чек-листу причин, а не по догадке. Составление запроса с нуля — скилл `query-compose`.

## Чек-лист (порядок = убывание типового выигрыша)

1. **Условия по виртуальной таблице — в параметры ВТ**, не в `ГДЕ`: фильтр применяется на уровне хранения, а не после выборки. — **std657**, `BSLLS:VirtualTableCallWithoutParameters`, `v8cs:ql-virtual-table-filters`
2. **Соединения с подзапросом и с виртуальной таблицей** → вынести во временную таблицу с `ИНДЕКСИРОВАТЬ ПО`. Вложенные соединения (соединение с подзапросом, внутри которого свои соединения) — не применять. — **std655**, `v8cs:ql-join-to-sub-query`, `acc:494`
3. **Составные типы через точку** (`Регистратор.Дата`) порождают неявные соединения со **всеми** возможными типами → `ВЫРАЗИТЬ(… КАК …)`, при нескольких типах — `ВЫБОР … ССЫЛКА …`. — **std654**, `BSLLS:QueryNestedFieldsByDot`, `acc:1377`
4. **`ИЛИ` в `ГДЕ`** блокирует индекс → `В (…)` либо разбиение на `ОБЪЕДИНИТЬ ВСЕ` (после разбиения сверить, что состав строк не изменился). — **std658**, `acc:316`, `BSLLS:LogicalOrInTheWhereSectionOfQuery`; `ИЛИ` в `ПО` — `acc:317`
5. **Выравнивание по индексу**: поля условия должны идти с начала индекса и подряд, без пропусков. Пропуск первого поля = индекс не используется.
6. **`ПРЕДСТАВЛЕНИЕ(Ссылка)`** вместо `Ссылка.Наименование`, когда нужен только текст — экономит соединение.
7. **`ОБЪЕДИНИТЬ ВСЕ` вместо `ОБЪЕДИНИТЬ`**, если дубликаты невозможны — снимается лишняя группировка.
8. **Обращение к «Остатки»** — по правилам эффективного обращения. — **std733**

Отдельно для **СКД**: отбор задавать параметром виртуальной таблицы и условием в тексте набора данных, а не настройками компоновки; `ЕСТЬNULL` для внешних соединений. Правку схемы вести скиллами `skd-edit`/`skd-info`, проверять `skd-validate`.

## Что запросом не лечится

- **Индексы конфигурации** (`Индексировать`, `Индексировать с доп. упорядочиванием`) и денормализация — изменения метаданных: скиллы `meta-edit` → `meta-validate`, и это правка конфигурации, а не запроса.
- **RLS**: сложные шаблоны ограничений с подзапросами и соединениями умножают стоимость плана. Смотреть `role-info`, стандарты ролей; `РАЗРЕШЕННЫЕ` обязателен там, где RLS действует.
- **Запрос в цикле** и чтение объекта целиком ради одного реквизита — это дефект окружающего кода, а не текста запроса. — **std496**, `acc:1419`

## Маршрут проверки

1. `validate_query` (`edt-mcp`) — после каждой переписки запроса; для СКД `dcsMode=true`.
2. **Без EDT переписанный запрос в строковом литерале не проверяет ни один статический чекер**: `bsl-analyzer` и пакетная проверка конфигурации на реальной выгрузке пропустили заведомо нерабочий запрос. Тогда проверка одна — прогон на тестовой базе (`execute_query` — текст, `execute_code` — функция целиком); до прогона — «не проверено».
3. `bsl-analyzer` (контур PostToolUse) и скилл `1c-standards` — по модулю целиком.
4. `v8std` (`v8std_explain_diagnostics`, `v8std_get_page`) — за формулировкой стандарта, а не по памяти.
5. Замер — `execute_query` (`1c-toolkit`) на **тестовой** базе, до и после (`docs/safety/secrets-and-production-database.md`). Утверждать «стало быстрее» без замера — нельзя. Вместе с временем сверить **состав и суммы** результата: переписка не должна внести ловушки из раздела «Ловушки, подтверждённые на данных» скилла `query-compose` — при переносе условия по дате в параметр `Остатки(…)` проверить границу периода, при сворачивании группировок — что ресурс остался под агрегатом, при выносе деления во временную таблицу — защиту от нулевого делителя.

При **ревью чужого запроса** пройти ту же таблицу ловушек `query-compose`: она про корректность на данных, чек-лист выше — про скорость.
