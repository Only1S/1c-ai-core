# /uuid-validate — Дубликаты UUID в MDO (EDT)

Сканирует `*.mdo` рекурсивно, собирает значения атрибутов `uuid`, `typeId`, `valueTypeId` и показывает совпадения: **межфайловые** (два объекта с одним идентификатором — типовое следствие копирования объекта или слияния веток) и **внутрифайловые** (по умолчанию скрыты: в 1С `uuid` объекта штатно совпадает с `typeId` в его же `producedTypes`).

Работает с форматом **EDT** (`.mdo`). Для XML-выгрузки Конфигуратора не применим — там идентификаторы лежат иначе.

## Запуск

```bash
PYTHONIOENCODING=utf-8 python "${CLAUDE_SKILL_DIR}/scripts/check_uuid_duplicates.py" "<путь>"
```

`PYTHONIOENCODING=utf-8` обязателен — без него русский отчёт приходит в кодировке консоли и нечитаем.

| Аргумент | Смысл |
|---|---|
| `<путь>` | папка (рекурсивно) или конкретный `.mdo`; путей можно несколько |
| `--include-intra` | показать ещё и внутрифайловые повторы (по умолчанию скрыты как штатные) |

Код выхода: `0` — дубликатов нет, `1` — есть, `2` — проверка не выполнена (путь не существует, `.mdo`-файлов нет, неизвестный ключ). Код `2` — не «всё чисто».

## ⚠️ Флаг `--fix` — не применять автоматически

У скрипта есть `--fix` (заменить повторы новыми UUID, первое вхождение сохраняется). **Проверено зондом 03.08.2026 — он ломает легитимные ссылки типов:**

```
Sklady.mdo:      <producedTypes typeId="bbbbbbbb-…"/>        ← тип справочника
Postuplenie.mdo: <attributes valueTypeId="bbbbbbbb-…"/>      ← реквизит ссылается на этот тип
```

Это **не** коллизия, а нормальная ссылка. Но скрипт держит `uuid`/`typeId`/`valueTypeId` в одном реестре, поэтому видит «межфайловый дубликат» и при `--fix` перезаписывает `typeId` у владельца на новый случайный, **оставляя `valueTypeId` ссылающимся на старый** — реквизит начинает указывать на несуществующий тип.

Отсюда порядок работы:

1. **Всегда сначала отчёт без `--fix`.** Это диагностика, и в ней скрипт точен.
2. Разобрать каждую находку: коллизия — это совпадение по атрибуту **`uuid`** у двух разных объектов. Совпадение `typeId` ↔ `valueTypeId` — ссылка, её трогать нельзя.
3. Чинить **точечно**: править конкретный `uuid=` в нужном `.mdo`, а не массовым `--fix`. Штатного инструмента правки идентификатора нет (у `edt-mcp` и `meta-edit` его тоже нет), а барьер `guard-skills` отклоняет Edit по `.mdo`. Поэтому точечная правка — **названное исключение** ([use-skills-not-manual-edits](../../docs/tools/use-skills-not-manual-edits.md) п.6): сказать вслух «uuid-validate даёт только отчёт, правлю `uuid=` в <файл> вручную», согласовать с пользователем, править байтобезопасно одной заменой через Bash (python), затем валидация проекта в EDT.
4. Если `--fix` всё же применяется — только по явной просьбе пользователя и только так: git-коммит или копия `src` до запуска → запуск → `git diff` глазами по каждой замене → валидация проекта в EDT (`edt-mcp`, ошибки проекта) → откат при любой порванной ссылке. Операция необратима без бэкапа.

## После правки идентификаторов

- `edt-mcp` — ошибки проекта: битая ссылка на тип вылезет именно там.
- Скиллы `meta-info` / `cf-info` — если конфигурация ведётся ещё и в XML-выгрузке.
- Git-диff — обязательный контроль: замен должно быть ровно столько, сколько разобрано вручную.
