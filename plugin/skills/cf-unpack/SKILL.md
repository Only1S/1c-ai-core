# /cf-unpack — CF/CFE/EPF без платформы

`v8unpack` (Python) разбирает контейнер 1С в человекочитаемые исходники (JSON + BSL с деревом метаданных) и собирает обратно. Платформа, лицензия и Конфигуратор **не нужны** — это его единственное, но решающее преимущество.

## Когда этот скилл, а когда штатный путь

| Задача | Инструмент |
|---|---|
| Заглянуть в **чужой** `.cf`/`.cfe`/`.epf`, платформы под рукой нет либо файл не хочется грузить в базу | **`/cf-unpack`** |
| Сравнить две поставки `.cf` между собой (диффом по распакованному) | **`/cf-unpack`** |
| Выгрузить конфигурацию **своей базы** в файлы для работы | `db-dump-xml` / `db-dump-cf` (платформа) |
| Разобрать `.epf`/`.erf` для правки и сборки обратно | `epf-dump` / `erf-dump` → `epf-build` / `erf-build` (платформа, штатный формат) |

**Важно про формат.** `v8unpack` отдаёт **свой** JSON+BSL, а не XML-выгрузку Конфигуратора. Наши скиллы `meta-info`, `cf-info`, `form-info`, `skd-info` читают XML — **на выходе `v8unpack` они не работают**. По распакованному дереву идти `code-index` / `Grep` / `Read`. Нужен штатный XML — путь через платформу (`db-load-cf` в тестовую базу → `db-dump-xml`).

## Требование среды

```bash
python -m v8unpack --help || pip install v8unpack
```

Проверено 30.10.2026: `v8unpack 1.2.6` запускается (`--help`); ограничения чтения — ниже. Пакет **не бандлится** в ядро (TIER C, `THIRD-PARTY.md` в корне канала `Only1S/1c-ai-core`; в проекте с плагином — `~/.claude/plugins/marketplaces/ones-core/THIRD-PARTY.md`) — в свежей копии его может не быть. Нет Python или пакет не встал — не блокируемся, идём штатным путём через платформу и говорим об этом прямо.

## Команды

**Распаковать:**
```bash
python -m v8unpack -E "<файл.cf>" "<папка_исходников>" --temp "<папка_temp>"
```

**Собрать обратно:**
```bash
python -m v8unpack -B "<папка_исходников>" "<файл.cf>"
```

**Расширение** (нужен суффикс версии конфигурации и режим совместимости):
```bash
python -m v8unpack -E "<расш.cfe>" "<папка>" --descent 3000112
python -m v8unpack -B "<папка>" "<расш.cfe>" --index index.json --descent 3000112 --version 80316
```

**Оглавление** (раскладка исходников по подпапкам): `python -m v8unpack -I "<папка>" --index index.json --core core`
**Пакетно** по описанию продуктов: `-EA products.json` / `-BA products.json`

| Ключ | Смысл |
|---|---|
| `--temp <путь>` | промежуточные стадии (не удаляются — для отладки) |
| `--processes N` | потоки, по умолчанию `cpu_count - 2` |
| `--descent XYYZZZ` | суффикс версии конфигурации (расширения) |
| `--version XYYZZ` | режим совместимости при сборке, напр. `80316` = 8.3.16 |
| `--auto_include` | оглавление из папки, а не из заголовка (вложенные сортируются по алфавиту) |
| `--prefix STR` | префикс имён метаданных 1-го уровня |

## Ограничения (знать до того, как делать выводы по распакованному)

- Свойства объектов и разметка форм лежат в `header`/`raw` **сырыми массивами** — по ним нельзя судить о составе формы; для форм идти `form-info` по XML или `edt-mcp`.
- Файлы больше 1 МБ (макеты, HTML) сохраняются как `.bin` без декодирования.
- Зашифрованные модули остаются бинарными.
- Версия утилиты пишется в `Configuration.json`; при сборке сверяется `major.minor`. Разошлось — собрать старой версией, обновить утилиту, распаковать новой, закоммитить.
- **Часть исправных файлов не читается.** `Ошибка: Unknown Error - invalid literal for int() with base 16: …` — утилита приняла файл за 64-битный контейнер (так бывает, если в файле есть свободные блоки; замер 29.10.2026 на `.epf` 13,8 МБ). Файл при этом цел: пользователю — «v8unpack этот файл не читает», дальше штатный путь `epf-dump` или `db-load-cf` в тестовую базу → `db-dump-xml`.
- **Собранный `.cf` сама утилита обратно не читает** (та же ошибка), хотя платформа его принимает. Сборку проверять платформой: `python ${CLAUDE_SKILL_DIR}/../cf-vendor-update/scripts/dump-release.py --src <собранный.cf> --out <пустой каталог>` и сравнить с выгрузкой оригинала (`diff -r`; отличаться может только `ConfigDumpInfo.xml`).
- После круга «распаковать → собрать» у форм расширения меняется перенос строк base64 в `*.elem.json` — это не правка содержимого.

## Сборка обратно — обращаться как с необратимой операцией

Пересобранный `.cf` — это то, что потом грузится в базу (`db-load-cf`, необратимо). Поэтому: сборка только из распакованного **той же** версией утилиты, исходный файл сохранять, результат перед загрузкой сверять размером и содержимым, загрузка — по правилам `db-load-cf` (бэкап + подтверждение, `docs/safety/secrets-and-production-database.md`).

Скилл — наш; сама утилита вендорная (`saby v8unpack`, PyPI). Разбор кандидатов — `docs/sources/external-skills-review.md`.
