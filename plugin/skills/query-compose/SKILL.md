# /query-compose — Составление запросов 1С

Справочник и маршрут для написания корректного запроса. Полный синтаксический материал — в `references/`, здесь — порядок работы, оформление по стандартам и привязка к нашему стеку.

## Маршрут (не пропускать шаги)

1. **Узнать имена** — реквизиты, ТЧ, измерения/ресурсы регистров. Имена объектов уникальны для каждой конфигурации, **не угадывать**:
   - исходники XML → скилл `meta-info` (не читать XML руками), `nkdk` (XML↔YAML);
   - живой проект EDT → `edt-mcp`;
   - живая база → `get_metadata` (`1c-toolkit`, только тестовая).
2. **Составить** запрос — по материалу ниже и в `references/`.
3. **Проверить** — `validate_query` (`edt-mcp`), для запросов СКД `dcsMode=true`. Ловит несуществующие таблицы/поля и ошибки типов до выполнения.
4. **Выполнить** (если нужен результат) — `execute_query` (`1c-toolkit`), **только на тестовой базе** (`docs/safety/secrets-and-production-database.md`). `execute_code` — не для чтения данных.

Одна лишняя проверка метаданных всегда дешевле отладки упавшего запроса.

## Оформление: два разных контекста — не путать

| Куда идёт запрос | Как оформлять |
|---|---|
| **Код модуля, СКД, отчёт** — то, что остаётся в конфигурации | По **std437**: структурированный текст (`ВЫБРАТЬ` / поля / `ИЗ` — с переносами и отступами), ключевые слова заглавными, каждому полю псевдоним через `КАК`. **Запрос в одну строку запрещён прямо стандартом** (std437 п.3), даже короткий |
| **Транспорт** — текст, передаваемый в `execute_query` разовым зондом | Однострочная запись допустима: это не код конфигурации, а параметр вызова. В модуль такой текст не переносить без переформатирования |

Вендорный материал в `references/` написан под второй случай (там сказано «always write in a single line») — **для кода конфигурации это правило не действует**.

## Правила, за которыми стоит стандарт

Формулировки ниже проверяемы: коды объясняет MCP `v8std` (`v8std_explain_diagnostics`, `v8std_get_page`), нарушения ловят `bsl-analyzer` и скилл `1c-standards`.

| Правило | Стандарт / диагностика |
|---|---|
| Все условия по виртуальной таблице — **в её параметры**, а не в `ГДЕ` | **std657** · `BSLLS:VirtualTableCallWithoutParameters` · `v8cs:ql-virtual-table-filters` |
| Условия пишутся с учётом индексов; `ИЛИ` в `ГДЕ` ломает индекс → `В (…)` или `ОБЪЕДИНИТЬ ВСЕ` | **std658** · `acc:316` · `BSLLS:LogicalOrInTheWhereSectionOfQuery`; `ИЛИ` в `ПО` — `acc:317` |
| Поля составного типа через точку → `ВЫРАЗИТЬ(… КАК …)` | **std654** · `BSLLS:QueryNestedFieldsByDot` · `acc:1377` |
| Не соединять с вложенным запросом и виртуальной таблицей — выносить во временную с `ИНДЕКСИРОВАТЬ ПО` | **std655** · `v8cs:ql-join-to-sub-query` · `acc:494` |
| Эффективное обращение к «Остатки» | **std733** |
| Псевдоним каждому полю через `КАК`; ключевые слова заглавными; не в одну строку; комментарии в сложных запросах | **std437** · `BSLLS:AssignAliasFieldsInQuery` · `acc:254` |
| Тексты, видимые пользователю (в запросе/СКД), — по требованиям локализации | **std762** (языковой профиль — `docs/code/language-profile.md`) |
| В **коде** (не в запросе) обращение к реквизиту через точку от ссылки читает объект целиком | **std496** · `acc:1419` — это довод в пользу запроса вместо `ПолучитьОбъект()` |
| С `РАЗЛИЧНЫЕ` сортировать только по полям из `ВЫБРАТЬ`: поле сортировки неявно попадает в выборку, выбранные поля перестают схлопываться — дубли. Нужен порядок по другому полю — добавить его в выборку или отсортировать таблицу после выгрузки | **std412** п.2 |

`РАЗРЕШЕННЫЕ` — по умолчанию: без него запрос падает с ошибкой доступа там, где действует RLS.

## Ловушки, подтверждённые на данных

Каждая поймана на реальной выгрузке одного из экземпляров. Первые пять синтаксически корректны: их не ловит ни один чекер, только сверка результата на данных. Последние две ловит `validate_query` (EDT), но не `bsl-analyzer` и не пакетная проверка конфигурации.

| Ловушка | Что происходит | Как писать |
|---|---|---|
| **Граница `Остатки(&Период)`** | Остаток считается на момент `&Период` **без** движений, датированных ровно этим моментом. Соседнее условие `Дата <= &Период` такие движения включает — границы расходятся: документ, проведённый в 23:59:59 последнего дня, есть в выборке документов и отсутствует в остатках | Выровнять границы: `Остатки(ДОБАВИТЬКДАТЕ(&Период, СЕКУНДА, 1), …)` — подтверждено на данных. Параметр `Новый Граница(&Период, ВидГраницы.Включая)`: тип `Граница` со свойством `ВидГраницы` в справочнике API есть (`bsl-platform`), на данных **не проверено** |
| **Дата без времени** | Дата из поля выбора приходит с 00:00:00, и `Дата <= &Период` отсекает все документы этого дня, датированные со временем | `КОНЕЦПЕРИОДА(&Период, ДЕНЬ)` — в условии и в параметре виртуальной таблицы одинаково |
| **Группировка по ресурсу** | `СГРУППИРОВАТЬ ПО …, СуммаОборот` без агрегата схлопывает равные суммы: два одинаковых платежа становятся одной строкой, итог занижен | Ресурс — только под агрегатом (`СУММА(СуммаОборот)`), в `СГРУППИРОВАТЬ ПО` — только разрезы. Дубли от соединения снимать ключом (регистратор + номер строки), а не группировкой по сумме |
| **Деление на количество из данных** | Строка остатков с количеством 0 и копеечной суммой (хвост округления) даёт «Деление на ноль» — падает весь запрос или отчёт, а не одна строка | `ВЫБОР КОГДА Количество = 0 ТОГДА 0 ИНАЧЕ Сумма / Количество КОНЕЦ` — на каждом делении на поле из данных |
| **`УПОРЯДОЧИТЬ ПО` по ссылке** | Для пользователя порядок строк выглядит случайным (std412 п.1.3) | По стандарту — по строковому представлению (`ПРЕДСТАВЛЕНИЕ(…)`) или по полю примитивного типа: `.Код` / `.Наименование`; у плана счетов — `.Порядок` (строка для сортировки; есть у объекта плана счетов по `bsl-platform`) |
| **Псевдоним = имя стандартного поля или ТЧ** | Псевдоним, совпадающий с именем стандартного поля или табличной части соединяемой таблицы (`… .ВидыСубконто КАК ВидыСубконто`, `… КАК Родитель`, ТЧ под псевдонимом, равным её имени), даёт «Неоднозначное поле»; позиции в тексте ошибки уводят в сторону | Псевдоним — от роли в запросе (`СубконтоСчета`, `РодительСчета`, `СтрокиОбъекта`), а не повтор имени. Диагностика — двумя зондами `validate_query`: без соединения, затем с переименованным псевдонимом |
| **У плана счетов нет `ЭтоГруппа`** | Поле, привычное по справочникам, у плана счетов отсутствует (`bsl-platform`: у `ПланСчетовОбъект` его нет, у `СправочникОбъект` есть) | Иерархия — через `Родитель` / `В ИЕРАРХИИ` |

## Проверка результата

1. `validate_query` (`edt-mcp`) — без ошибок; для СКД — с `dcsMode=true`.
2. **Без EDT текст запроса в строковом литерале не проверяет ни один статический чекер.** На реальной выгрузке заведомо нерабочий запрос («Неоднозначное поле») прошёл `bsl-analyzer` в полном контексте (0 блокеров) и пакетную проверку конфигурации (лог совпал с эталоном): анализатор разбирает запрос, но неоднозначность не видит, а платформа строковые литералы не разбирает вовсе. В профиле без EDT единственная проверка — прогон на **тестовой** базе: `execute_query` для текста, `execute_code` для функции, которая собирает и выполняет запрос. До прогона статус запроса — «не проверено», а не «проверено чекерами».
3. Запрос в модуле — прогнать `bsl-analyzer` / скилл `1c-standards` (оформление, псевдонимы, `ИЛИ` в `ГДЕ`).
4. Результат сверить на данных с независимым источником (прежний отчёт, оборотно-сальдовая ведомость, ручная выборка): ловушки из таблицы выше синтаксически невидимы.
5. Спорная формулировка стандарта — `v8std`, а не память.

Атрибуция вендорного материала — `THIRD-PARTY.md` в корне репозитория ядра (в проекте с плагином — `~/.claude/plugins/marketplaces/ones-core/THIRD-PARTY.md`).
