# Архитектурное ревью конфигурации 1С — модульная декомпозиция

Критика архитектуры **по бизнес-возможностям, а не по слоям и папкам**. Логическое разделение на автономные возможности важнее технического деления кода на модули, суффиксы и подсистемы. Источник — промпт владельца (`references/source-prompt.md`, 18.10.2026); подход Udi Dahan и Particular Software пересказан своими словами с проекцией на 1С.

**Охват и соседи.** Модульная декомпозиция по Udi Dahan / Particular Software — автономные бизнес-возможности, владение данными, Composite UI. Разбирается: фактические границы подсистем против заявленных, кто пишет какие регистры, связи между возможностями, формы, собранные из нескольких возможностей, и слои внутри модуля. Выход — только критика: места в коде, нарушенная граница, последствия, направление исправления и 3–5 главных проблем. Не этот скилл: горячие точки долга по сигналам — `task-recipes` §15, ревью одного модуля — `two-axis-code-review`.

## Ведущие слова

- **Возможность** (business capability, Service у Dahan) — автономная бизнес-способность со своими данными, правилами и сценариями: «ценообразование», «маркировка», «расчёты с поставщиками». В 1С её носитель — своя подсистема и префикс объектов ([[naming-and-module-design]]), но **заявленная** подсистема ещё не значит **фактическая** граница.
- **Владелец данных** — возможность, которая данные **пишет**: движения регистров, запись реквизитов, проведение. Читать чужое по ссылке можно; писать — только владелец.
- **Композиция экрана** — форма или АРМ могут показывать данные нескольких возможностей. Это не повод сливать их в один объект, модуль или модель.
- **Поправка на 1С.** Одна база и общая нормативно-справочная информация (номенклатура, контрагенты, организации) — это нормальное устройство платформы, а не дефект. Дефект — когда реквизиты, правила и запись одной возможности живут в объектах другой и поэтому меняются вместе.

## Порядок

Каждый факт — от инструмента, не по памяти ([[work-through-tools]]). Чего проверить нечем — так и сказать в отчёте.

0. **Область.** Предмет критики — **своё**: свои подсистемы, свои префиксы, доработки типового. БСП и код поставщика — окружение; их трогают, только где своё в них вросло (правки типовых модулей; состояние поддержки — строка «Поддержка» в выводе `meta-info`, `subsystem-info`, `cf-info`; снятие с поддержки — `support-edit`, только по команде владельца: модель сама его не вызывает). Источники фактов: исходники проекта (`ONEC_PROJECT_SRC`), индекс `code-index`, EDT через `edt-mcp`, если поднят.

1. **Карта возможностей.** Состав своих подсистем — `subsystem-info`, общая структура — `cf-info`, объекты по префиксам — `code-index` `find_path` / `list_files`. Для каждой возможности выписать её объекты: документы, справочники, регистры, общие модули, формы, обработки, HTTP-сервисы. Это **заявленные** границы; шаги 2–4 дают **фактические**.

2. **Владение данными.** По каждому своему регистру — кто его пишет:
   - документы-регистраторы и их движения — `meta-info`;
   - код записи наборов — `code-index` `grep_body` по `Движения.<Регистр>` и `РегистрыСведений.<Регистр>.СоздатьНаборЗаписей` / `РегистрыНакопления.<Регистр>.СоздатьНаборЗаписей`.
   
   Регистр, который пишут объекты нескольких возможностей, — **размытая ответственность**. Справочник или документ, в котором собраны реквизиты, нужные разным возможностям, — **общая модель данных**: проверить, кто какие реквизиты пишет и читает.

3. **Зависимости между возможностями.**
   - Вызовы — `code-index` `get_callers` / `get_callees` / `get_call_tree` по экспортным методам общих модулей каждой возможности.
   - Ссылочные реквизиты и типы на объекты чужой возможности — `meta-info`.
   - Подписки на события, где источник одной возможности, а обработчик — в другой, — `cf-info` и исходники `EventSubscriptions`.
   - Прямые вызовы в чужие служебные модули (`…Служебный`, `…Internal`) — нарушение. Определяемые типы, `…Переопределяемый` и подписки — это швы, через них связь допустима.
   
   Сверить фактический граф с заявленными границами: каждая связь — нужна ли она самой возможности или появилась ради удобства.

4. **Совместное изменение.** Если у проекта есть история (`git log` по исходникам): какие возможности меняются в одних коммитах. Когда правка одной возможности регулярно требует правок в другой, граница размыта. Нет истории — сказать вслух, не подменять догадкой. Горячие точки долга — сигналы из [[task-recipes]] §15.

5. **UI и границы (Composite UI).** Формы и АРМ, которые показывают данные нескольких возможностей: `form-info` даёт реквизиты формы, динамические списки, запросы, команды; модуль формы — запросы к чужим регистрам. Анти-шаблоны:
   - объект или реквизит, заведённый ради удобства формы, который сводит данные разных возможностей;
   - модуль формы, где живут бизнес-правила нескольких возможностей;
   - «общий» документ-витрина, через который возможности обмениваются данными;
   - потребности экрана определяют, какой возможности принадлежат данные, или её зависимости.
   
   Штатная композиция в 1С — сверить версию БСП скиллом `bsp`, не по памяти:
   - подключаемые команды (`ПодключаемыеКоманды`, состав — через `ПодключаемыеКомандыПереопределяемый`);
   - дополнительные реквизиты и сведения (`УправлениеСвойствами`);
   - варианты отчётов и печать (`ВариантыОтчетов`, `Печать`);
   - расширения форм;
   - несколько динамических списков или подчинённых форм на одном экране, у каждого — свой источник.
   
   Решение «экран нужен целиком» — это **композиция**, а не слияние владения.

6. **Внутри модуля возможности.** Разложить по уровням:
   - бизнес-правила и состояние — модуль объекта, модуль менеджера, регистры, проведение;
   - сценарии и оркестрация — серверный общий модуль возможности;
   - инфраструктура — HTTP, обмены, файлы, внешние компоненты, очереди;
   - представление — модуль формы, клиентские модули.
   
   Искать:
   - бизнес-правила в модуле формы — `&НаСервере` с проведением, записью, расчётами;
   - запросы и правила в клиентском коде;
   - оркестрацию внутри проведения — HTTP-вызов или обмен из `ОбработкаПроведения`;
   - обработчик HTTP-сервиса или регламентного задания, в котором живут сами правила, а не вызов сценария;
   - модуль-«бог» — много экспортных методов разной ответственности (`code-index` `get_file_summary`);
   - обратное направление зависимостей — бизнес-правило знает о форме, о транспорте или о конкретной внешней системе.
   
   Папки, суффиксы, интерфейсы и формальные слои **не доказывают** хорошую архитектуру: судить по тому, что код делает, куда текут данные и кого он вызывает.

7. **Карточка проблемы.** Только критика: достоинства не перечислять, стиль, имена и локальные нарушения сюда не входят (это [[two-axis-code-review]] и скилл `1c-standards`).
   - **Где** — полные имена: `ОбщийМодуль.<Имя>.<Метод>`, `Документ.<Имя>.МодульОбъекта.ОбработкаПроведения`, форма, регистр.
   - **Что нарушено** — какая граница или ответственность.
   - **Последствия** — связанность, изменяемость, что придётся менять вместе, что мешает развивать возможности независимо.
   - **Направление** — архитектурное, а не «переименуй метод». Варианты: передать владение данными одной возможности; выделить возможность из общего объекта; заменить прямой вызов швом (`…Переопределяемый`, подписка, определяемый тип); собрать экран композицией.
   - **Сила** — уверен / стоит обсудить / гипотеза.
   - **Чем проверено** — инструменты и запросы.

8. **Итог.** 3–5 главных проблем по важности. Важность — сколько независимого развития проблема блокирует сейчас, а не сколько строк затрагивает. Затем — что осталось не проверенным и почему.

Карту возможностей и связей можно нарисовать скиллом `archify`, если владелец попросил схему.

## Границы

- **Ревью ничего не меняет.** Исправления — через проработку ([[design-before-code]]) и консилиум ([[five-role-design-review]]); дорогое к откату решение — ADR ([[decision-records-and-glossary]]).
- **Широта.** Крупную конфигурацию разбирают веером по возможностям — только после явного «да» владельца на запуск ([[subagents-on-explicit-consent]]). Без веера — 2–4 главные возможности, остальные названы как не смотренные.
- **Где отчёт.** По умолчанию — в ответе. По просьбе — проектный док `docs-project/<слаг>.md`; людям наружу — `.docx` ([[office-formats-for-people]]).
- **Готово, когда:** у каждой карточки место подтверждено инструментом и названо направление; итог из 3–5 пунктов упорядочен; перечислено, что не проверено.
